SECTION 01

디스크에 어떻게 저장되나

DB는 행 단위가 아니라 페이지(블록) 단위로 읽고 씁니다. 한 줄만 고쳐도 페이지 전체가 움직입니다.

DB 의 성능을 이야기할 때 단위는 행이 아니라 페이지입니다. 실행계획의 숫자도 대부분 페이지 수입니다.
DB기본 페이지 크기비고
PostgreSQL8KB컴파일 시 결정 (변경하려면 재빌드)
MySQL InnoDB16KBinnodb_page_size 로 4·8·16·32·64KB
Oracle8KB테이블스페이스마다 다르게 지정 가능
SQLite4KBPRAGMA page_size

페이지 안의 구조

┌─────────────────────────────────────────┐
│ 헤더 (체크섬 · LSN · 여유 공간 위치)      │
├─────────────────────────────────────────┤
│ 슬롯 배열 →→→                            │  각 행이 페이지 안 어디에 있는지 가리킴
│                                          │
│              (빈 공간)                    │  ← 여기가 채워지면 페이지 분할
│                                          │
│                          ←←← 행 데이터   │  뒤에서부터 채워 옵니다
├─────────────────────────────────────────┤
│ 푸터 / 체크섬                             │
└─────────────────────────────────────────┘

이 구조가 만드는 실무적 결과

  • 행 하나를 읽어도 페이지 전체를 읽습니다 — 그래서 관련 행이 물리적으로 가까이 있으면 빠릅니다(지역성)
  • UPDATE 로 행이 커지면 페이지에 안 들어가 다른 페이지로 옮겨가고(row migration), 원래 자리에는 포인터만 남습니다. 조회가 2단계가 되어 느려집니다
  • 가변 길이 컬럼을 자주 늘리면 이 현상이 심해집니다. Oracle의 PCTFREE·PostgreSQL의 fillfactor 는 여유 공간을 미리 남겨 이를 완화합니다
  • 큰 값(TEXT·BLOB)은 별도 저장됩니다 — PostgreSQL은 TOAST, InnoDB는 오버플로 페이지. 조회할 때 추가 IO가 발생하므로 SELECT * 가 더 비싸집니다
-- PostgreSQL : 갱신이 잦은 테이블은 여유 공간을 남겨 HOT 업데이트를 유도
ALTER TABLE orders SET (fillfactor = 80);
VACUUM FULL orders;      -- 또는 pg_repack

-- 물리적 순서를 인덱스 순서로 재배치 (범위 조회가 많을 때)
CLUSTER orders USING idx_orders_dt;
PostgreSQL 의 HOT 업데이트 — 인덱스 컬럼을 건드리지 않는 UPDATE 는 같은 페이지 안에 새 버전을 만들고 인덱스를 갱신하지 않습니다. 훨씬 저렴합니다. fillfactor 로 여유를 남겨 두면 HOT 업데이트 비율이 올라갑니다.
SECTION 02

버퍼 풀 · 캐시 히트율

메모리에 올라와 있으면 마이크로초, 디스크까지 가면 밀리초. 1000배 차이가 여기서 납니다.

1
버퍼 풀에서 찾는다있으면(hit) 즉시 반환 — 수 μs
▼ 없으면
2
디스크에서 페이지를 읽어 올린다SSD 수십 μs · HDD 수 ms
▼ 자리가 없으면
3
오래된 페이지를 밀어낸다 (LRU) 수정된 페이지(더티)라면 먼저 디스크에 써야 합니다.
-- PostgreSQL : 히트율
SELECT datname,
       ROUND(blks_hit * 100.0 / NULLIF(blks_hit + blks_read, 0), 2) AS 히트율
FROM   pg_stat_database WHERE datname = current_database();

-- MySQL InnoDB
SELECT ROUND(100 - (
  (SELECT variable_value FROM performance_schema.global_status
    WHERE variable_name='Innodb_buffer_pool_reads') * 100.0 /
  (SELECT variable_value FROM performance_schema.global_status
    WHERE variable_name='Innodb_buffer_pool_read_requests')), 2) AS 히트율;

-- Oracle
SELECT name, value FROM v$sysstat
WHERE  name IN ('db block gets','consistent gets','physical reads');
히트율 99%가 항상 좋은 것은 아닙니다. 풀스캔이 반복되면 같은 페이지를 계속 읽어 히트율이 오히려 높게 나올 수 있습니다. 히트율만 보지 말고 초당 논리 읽기(logical reads) 수를 함께 보세요. "히트율은 좋은데 CPU가 100%"라면 읽는 양 자체가 과도한 것입니다.

스캔이 캐시를 밀어내는 문제

큰 테이블을 한 번 풀스캔하면 버퍼 풀에 있던 유용한 페이지가 전부 밀려납니다. 그 뒤 한동안 모든 쿼리가 느려집니다. DB들은 이를 완화하는 장치를 둡니다.

  • PostgreSQL — 큰 순차 스캔은 작은 링 버퍼만 사용해 전체를 오염시키지 않습니다
  • InnoDB — LRU 리스트를 young/old 로 나눠, 한 번 읽힌 페이지는 old 영역에 두었다가 재사용될 때만 승격합니다
  • Oracle — 풀스캔 블록을 LRU 끝에 두거나 KEEP·RECYCLE 풀로 분리합니다
메모리 증설이 답인지 판단하려면 — ① 히트율이 낮고 ② 디스크 읽기가 많으며 ③ 데이터 활성 부분이 메모리보다 큰 경우에만 효과가 있습니다. 쿼리가 불필요하게 많이 읽고 있다면 메모리를 늘려도 곧 다시 부족해집니다.
DB 성능 이야기의 대부분은 결국 디스크를 몇 번 건드리느냐로 환원됩니다.
SECTION 03

WAL · REDO · UNDO

DB는 진짜 데이터보다 로그를 먼저 씁니다. 이것이 커밋이 디스크 속도에 묶이는 이유이자, 전원이 나가도 복구되는 이유입니다.

커밋이 디스크 순차 쓰기 한 번으로 끝나는 것이 WAL 의 핵심입니다 — 흩어진 데이터 페이지를 그때마다 쓰면 커밋은 수십 배 느려집니다.
WAL (Write-Ahead Logging) 의 원칙 — 데이터 페이지를 디스크에 쓰기 전에 변경 내용을 로그에 먼저 기록하고, 로그가 디스크에 안전하게 기록된 시점에 커밋을 성공으로 응답합니다. 데이터 파일은 나중에 천천히 반영해도 됩니다 — 로그만 있으면 재현할 수 있으니까요.

REDO 와 UNDO

로그담는 내용쓰는 곳
REDO바뀐 뒤의 값 (다시 적용하기 위한) 크래시 복구 · 복제 · 시점 복구
UNDO바뀌기 전의 값 (되돌리기 위한) ROLLBACK · MVCC의 과거 버전 제공
PostgreSQL
WAL 하나로 REDO 역할
UNDO 는 별도로 없음
→ 옛 버전을 테이블 안에 그대로 남김
→ 그래서 VACUUM 이 필요
MySQL InnoDB
redo 로그 (ib_logfile)
undo 로그 (undo tablespace)
→ 옛 버전은 undo 에 보관
→ purge 스레드가 정리
Oracle
redo 로그 + 아카이브 로그
undo 테이블스페이스
→ Flashback Query 가
   여기서 나옵니다
SQLite
롤백 저널 (기본) = UNDO 방식
WAL 모드 = REDO 방식
둘 중 하나를 선택

커밋이 느린 이유 — fsync

-- 안전성과 속도의 트레이드오프 설정
-- PostgreSQL
synchronous_commit = on        -- 기본·안전 (커밋마다 fsync)
synchronous_commit = off       -- 빠름 · 장애 시 최근 수백 ms 유실 가능 (데이터 파일은 안 깨짐)

-- MySQL
innodb_flush_log_at_trx_commit = 1   -- 기본·안전
innodb_flush_log_at_trx_commit = 2   -- OS 캐시까지만 · OS 크래시 시 유실

-- SQLite
PRAGMA synchronous = FULL;     -- 기본
PRAGMA synchronous = NORMAL;   -- WAL 과 함께면 안전하면서 빠름
그룹 커밋 — DB들은 동시에 들어온 여러 커밋의 fsync 를 한 번에 묶어 처리합니다. 그래서 동시 접속이 많을수록 커밋당 비용이 낮아집니다. 반대로 한 세션이 순차적으로 1만 번 커밋하면 fsync 1만 번이 됩니다 — 대량 적재 시 반드시 트랜잭션으로 묶어야 하는 이유입니다.
SECTION 04

체크포인트와 크래시 복구

체크포인트는 "여기까지는 디스크에 확실히 반영됐다"는 표시입니다. 재시작 시간이 여기서 결정됩니다.

평상시
메모리에서 수정 · 로그만 디스크에 데이터 파일은 아직 옛 상태. 메모리의 더티 페이지가 쌓입니다.
▼
체크포인트
더티 페이지를 디스크에 반영 "이 지점까지의 로그는 이제 없어도 된다"고 기록합니다. IO 스파이크가 발생합니다.
▼
크래시 후
마지막 체크포인트부터 로그 재생 체크포인트 간격이 길수록 재생할 로그가 많아 재시작이 오래 걸립니다.
# PostgreSQL — 체크포인트를 넓게 펴서 IO 스파이크를 줄입니다
checkpoint_timeout = 15min
max_wal_size = 4GB
checkpoint_completion_target = 0.9    # 다음 체크포인트까지 90% 구간에 걸쳐 천천히

# MySQL
innodb_log_file_size = 1G             # 크면 체크포인트가 덜 자주
innodb_io_capacity = 2000             # 백그라운드 플러시 속도
트레이드오프 — 체크포인트가 잦으면 IO 부담이 크지만 재시작이 빠릅니다. 드물면 평소 부담은 적지만 장애 후 복구가 오래 걸립니다. 서비스가 얼마나 빨리 살아나야 하는가(RTO)로 결정하세요.

복구 과정 (ARIES 방식)

  1. 분석 — 마지막 체크포인트부터 로그를 읽어 어떤 트랜잭션이 진행 중이었는지 파악
  2. REDO — 커밋 여부와 무관하게 로그에 있는 모든 변경을 다시 적용해 크래시 직전 상태로
  3. UNDO — 그중 커밋되지 않은 트랜잭션을 되돌립니다
PostgreSQL 이 재시작 후 "recovering" 상태로 한참 있다면 이 과정 중입니다. 강제로 죽이지 마세요 — 다시 처음부터 해야 합니다. 로그로 진행 상황을 확인하며 기다리는 것이 맞습니다.
SECTION 05

MVCC 구현 비교

"읽기가 쓰기를 막지 않는다"는 같은 목표를 세 DB가 완전히 다르게 구현했습니다. 운영 특성의 차이가 전부 여기서 나옵니다.

PostgreSQL — 테이블에 옛 버전을 남김
UPDATE 시
· 새 행 버전을 테이블에 추가
· 옛 행에 xmax 표시

장점
· 롤백이 즉시 (아무것도 안 해도 됨)
· UNDO 영역 관리 불필요

단점
· 테이블이 계속 부풀음 → VACUUM 필수
· 인덱스도 함께 부풀음
· 트랜잭션 ID 랩어라운드 위험
InnoDB — undo 로그에 옛 버전
UPDATE 시
· 행을 제자리에서 수정
· 옛 값은 undo 로그에

장점
· 테이블이 덜 부풀음
· 최신 행 조회가 빠름

단점
· 롤백이 비쌈 (undo 를 되돌려야)
· 긴 트랜잭션이 undo 를 붙들면
  purge 가 밀려 히스토리가 폭증
Oracle — undo 세그먼트
InnoDB 와 유사한 방식

특징
· UNDO 보존 기간 동안 과거 조회 가능
  → Flashback Query
· ORA-01555 (snapshot too old)
  = 필요한 과거 버전이 이미 덮임
SQLite — 사실상 직렬화
WAL 모드에서
· 읽기는 WAL 이전 스냅숏을 봄
· 쓰기는 한 번에 하나

동시 쓰기가 없으므로
MVCC 의 복잡성이 대부분 불필요

실무에서 드러나는 차이

상황PostgreSQLInnoDB · Oracle

SECTION 06

락 매니저와 2PL

DB 안의 교통정리 담당입니다. 무엇이 언제 잠기는지 알면 경합의 원인이 보입니다.

2단계 잠금 (Two-Phase Locking)

확장 단계
락을 획득하기만 합니다필요한 것을 잠그고, 이 단계에서는 절대 풀지 않습니다.
▼
수축 단계
락을 풀기만 합니다보통 커밋 시점에 한꺼번에 풉니다(Strict 2PL). 그래서 트랜잭션이 길면 락도 오래 유지됩니다.

락의 종류와 계층

종류설명
공유 락 (S)읽기용. 여러 개가 동시에 가능
배타 락 (X)쓰기용. 하나만 가능하며 S 와도 충돌
인텐션 락 (IS/IX)테이블 수준에 "안에서 행을 잠글 예정"이라고 표시. 테이블 락과 행 락의 충돌을 빠르게 감지하기 위한 장치
메타데이터 락 (MDL)DDL 과 DML 의 충돌 방지. ALTER TABLE 이 막히는 원인
래치 (latch)메모리 구조 보호용 초경량 락. 트랜잭션과 무관하게 짧게 잡습니다
어드바이저리 락애플리케이션이 임의 목적으로 쓰는 락 (PostgreSQL pg_advisory_lock) — 분산 작업 조율에 유용
-- PostgreSQL 어드바이저리 락 : 배치 중복 실행 방지에 유용합니다
SELECT pg_try_advisory_lock(12345);   -- true 면 획득, false 면 이미 누가 실행 중
-- ... 작업 ...
SELECT pg_advisory_unlock(12345);

-- 세션이 끊기면 자동 해제되므로 "죽은 락"이 남지 않습니다
락 경합이 심한데 튜닝으로 안 풀린다면 — 접근 방식 자체를 바꾸는 것이 답입니다.
· 한 행에 몰리는 카운터 → 여러 행으로 쪼개고 합산(샤딩된 카운터)
· 순차 채번 → 시퀀스 캐시를 늘리거나 UUID 계열로
· 큐 테이블 경합 → FOR UPDATE SKIP LOCKED
· 선착순 이벤트 → DB 밖(Redis)에서 먼저 가리고 확정분만 DB로
SECTION 07

옵티마이저 — 비용 모델 · 조인 순서

옵티마이저는 가능한 실행 경로 중 가장 싸 보이는 것을 고릅니다. 그 계산 방식을 알면 왜 이상한 계획을 골랐는지 역추적할 수 있습니다.

1
파싱 · 재작성문법 검사, 뷰 전개, 서브쿼리 평탄화, 조건 밀어내기(predicate pushdown)
▼
2
후보 계획 생성접근 경로(스캔 vs 인덱스) × 조인 순서 × 조인 방식의 조합
▼
3
비용 추정통계로 각 단계의 행 수(카디널리티)를 추정하고 IO·CPU 비용을 계산
▼
4
최소 비용 선택테이블이 많으면 조합이 폭발하므로 동적 계획법 + 휴리스틱으로 탐색을 제한합니다
옵티마이저가 틀리는 근본 원인은 카디널리티 추정 오차입니다. "이 조건이면 100행 남을 것"이라 추정했는데 실제로 100만 행이면, 그 뒤의 모든 선택(조인 방식·순서)이 연쇄적으로 잘못됩니다. 실행계획에서 추정과 실제 행 수의 차이를 먼저 보는 이유가 이것입니다.

추정이 빗나가는 전형적 상황

  • 컬럼 간 상관관계 — "도시=서울"과 "지역번호=02"는 사실상 같은 조건인데, 옵티마이저는 독립이라 가정해 확률을 곱합니다 → 심하게 과소 추정
  • 편향된 분포 — 히스토그램이 없으면 균등 분포로 가정합니다
  • 함수·표현식 — WHERE f(col) = 1 의 선택도는 추정 불가 → 기본값 사용
  • 바인드 변수 피킹 — 첫 실행의 값으로 계획을 만들어 캐시하는데, 다음 값에는 최악일 수 있습니다
-- PostgreSQL : 상관관계를 알려 주는 확장 통계 (10+)
CREATE STATISTICS stat_city_zip (dependencies, ndistinct)
  ON city, zip_code FROM member;
ANALYZE member;

-- Oracle : 확장 통계
EXEC DBMS_STATS.CREATE_EXTENDED_STATS('APP','MEMBER','(city, zip_code)');

-- MySQL : 히스토그램
ANALYZE TABLE member UPDATE HISTOGRAM ON city WITH 50 BUCKETS;
계획이 불안정할 때의 최후 수단 — Oracle SQL Plan Baseline, MySQL 옵티마이저 힌트, PostgreSQL pg_hint_plan(확장) 으로 계획을 고정할 수 있습니다. 다만 고정한 계획은 데이터가 변해도 그대로이므로, 반드시 왜 그런 계획이 나왔는지 원인을 먼저 찾으세요.
계획이 이상하면 옵티마이저를 의심하기 전에 통계를 보세요.
SECTION 08

조인 알고리즘 3종

조인 방식은 세 가지뿐입니다. 상황마다 최적이 다르고, 잘못 고르면 수백 배 차이가 납니다.

실행계획에서 조인 방식이 바뀌었다면 대개 통계가 예상한 행 수가 바뀐 것입니다 — 방식을 힌트로 고정하기 전에 통계부터 보세요.
방식동작유리한 상황
Nested Loop
중첩 루프		 바깥 테이블의 각 행마다 안쪽을 조회 바깥이 매우 작고 안쪽에 인덱스가 있을 때
Hash Join
해시 조인		 작은 쪽으로 해시 테이블을 만들고 큰 쪽을 훑으며 매칭 양쪽이 크고 등호 조인일 때. 대량 처리의 기본
Merge Join
정렬 병합		 양쪽을 정렬한 뒤 지퍼처럼 맞춰 나감 양쪽이 이미 정렬돼 있거나 범위 조인일 때
Nested Loop        바깥 1000행 × 안쪽 인덱스 조회 = 1000번 탐색
                   → 바깥이 100만 행이면 100만 번 → 재앙

Hash Join          작은 테이블(10만행)로 해시 생성 → 메모리 사용
                   큰 테이블(1억행) 1회 스캔하며 매칭
                   → 메모리가 부족하면 디스크로 넘침(spill) → 급격히 느려짐

Merge Join         양쪽 정렬 비용 + 1회 스캔
                   → 인덱스로 이미 정렬돼 있으면 정렬 비용 0
실무에서 가장 흔한 사고 — 옵티마이저가 바깥 테이블이 작을 것으로 추정해 Nested Loop 를 골랐는데 실제로는 100만 행이었던 경우입니다. 쿼리가 몇 초에서 몇 시간으로 바뀝니다. 실행계획에서 loops 값이 비정상적으로 크면 이 상황입니다.

해시 조인이 디스크로 넘어가지 않게

-- PostgreSQL : 이 세션에서만 work_mem 을 크게
SET LOCAL work_mem = '256MB';
-- 실행계획에 "Batches: 8" 처럼 나오면 메모리 부족으로 나눠 처리한 것입니다

-- MySQL 8.0 : 해시 조인 버퍼
SET SESSION join_buffer_size = 256*1024*1024;

-- Oracle : PGA 자동 관리
ALTER SESSION SET workarea_size_policy = MANUAL;
ALTER SESSION SET hash_area_size = 268435456;
조인 방식을 직접 고르기 전에 — ① 통계를 갱신하고 ② 조인 컬럼에 인덱스가 있는지 확인하고 ③ 불필요한 행을 조인 전에 걸러 내세요. 이 셋으로 대부분 해결됩니다. 힌트는 그다음입니다.
SECTION 09

파티셔닝 · 샤딩 전략

파티셔닝은 한 서버 안에서 나누는 것, 샤딩은 여러 서버로 나누는 것입니다. 샤딩은 되돌리기가 매우 어려우므로 마지막 카드입니다.

구분파티셔닝샤딩
범위한 DB 서버 안여러 DB 서버
해결하는 것큰 테이블의 조회·삭제 효율쓰기 처리량·저장 용량 한계
애플리케이션 변경거의 없음라우팅 로직 필요
조인그대로 가능샤드를 넘는 조인이 어려움
트랜잭션그대로분산 트랜잭션 문제(z11)
되돌리기쉬움사실상 재구축

샤드 키 선택 — 되돌릴 수 없는 결정

기준장단점
해시(사용자 ID) 고르게 분산됩니다. 단, 범위 조회가 전 샤드로 퍼집니다
범위(날짜) 최근 데이터에 부하가 집중됩니다(핫 샤드). 아카이빙에는 유리
디렉터리(매핑 테이블) 유연하지만 매핑 조회가 병목·단일 장애점이 됩니다
지역 법규(데이터 주권)·지연 시간에 유리. 지역 간 편차가 큽니다
샤딩 전에 반드시 소진해야 할 카드들
① 인덱스·쿼리 튜닝 — 대부분 여기서 해결됩니다
② 읽기 복제본 — 조회 부하는 이것으로 나눕니다
③ 캐시 — Redis 로 반복 조회를 흡수
④ 수직 분할 — 도메인별로 DB를 나눕니다(주문 DB · 회원 DB)
⑤ 아카이빙 — 오래된 데이터를 분리
⑥ 하드웨어 증설 — 클라우드에서는 종종 가장 저렴한 해법입니다
이 여섯을 다 해 보고도 안 되면 그때 샤딩입니다.

샤딩 후에 생기는 문제들

  • 전역 유일 ID — AUTO_INCREMENT 를 못 씁니다 → UUID v7·ULID·스노플레이크
  • 샤드를 넘는 조인 — 애플리케이션에서 합치거나, 참조 데이터를 모든 샤드에 복제
  • 전역 집계 — 각 샤드에서 부분 집계 후 합산 (또는 별도 분석 DB로 적재)
  • 리밸런싱 — 샤드를 추가할 때 데이터 이동. 일관된 해싱이나 가상 샤드(논리 샤드를 물리 샤드에 매핑)로 완화
  • 운영 복잡도 — 백업·모니터링·스키마 변경을 샤드 수만큼 해야 합니다
미리 대비하는 법 — 샤딩할 가능성이 조금이라도 있다면 처음부터 전역 유일 ID를 쓰고, 샤드 키가 될 컬럼을 모든 주요 테이블에 넣어 두세요. 나중에 추가하는 것보다 훨씬 쉽습니다.
SECTION 10

복제 · 합의 · HA 설계

서버가 죽어도 서비스가 살아 있게 하는 구성입니다. 자동화에는 함정이 많습니다.

복제 방식커밋 시점트레이드오프
비동기주 서버만 기록하면 즉시 빠름 / 장애 시 최근 데이터 유실 가능
반동기복제본이 받았음을 확인 후 절충안. MySQL 의 semi-sync
동기복제본이 기록까지 완료 후 유실 0 / 지연 증가, 복제본 장애 시 쓰기 중단 위험
합의 기반과반수가 기록하면 유실 0 + 자동 페일오버 (Raft·Paxos)

스플릿 브레인 — 자동 페일오버의 함정

네트워크가 순간 끊겨 복제본이 "주 서버가 죽었다"고 오판하고 스스로 승격하면, 실제로는 살아 있던 원래 주 서버와 둘 다 쓰기를 받는 상태가 됩니다. 데이터가 갈라지고, 복구가 사실상 불가능해집니다.
2노드 구성에서 자동 페일오버를 켜지 마세요. 최소 3노드(과반수 판정 가능) 또는 외부 중재자(witness)가 필요합니다.

RPO 와 RTO — 먼저 정해야 하는 두 숫자

지표뜻영향
RPO얼마만큼의 데이터 유실을 감수할 수 있나 0이면 동기 복제 필수 → 지연·비용 증가
RTO얼마나 빨리 복구돼야 하나 분 단위면 자동 페일오버 필요 → 복잡도 증가
이 두 숫자를 정하지 않고 HA 를 논하면 끝없이 겉돕니다. "결제는 RPO 0 · RTO 1분", "로그는 RPO 5분 · RTO 1시간"처럼 데이터 종류별로 다르게 정하는 것이 현실적입니다. 모든 데이터에 최고 수준을 적용하면 비용이 감당되지 않습니다.

관리형 서비스를 쓸 때

AWS RDS Multi-AZ · Aurora · Cloud SQL 등은 페일오버를 서비스가 처리합니다. 다만 페일오버 시 수십 초의 연결 끊김이 발생하므로, 애플리케이션에 재연결·재시도 로직이 반드시 있어야 합니다(🔌 a11). "관리형이니 알아서 되겠지"라고 두면 페일오버 때마다 장애가 됩니다.

HA 설계의 핵심 질문은 둘입니다 — 얼마나 잃어도 되나 · 얼마나 멈춰도 되나.
SECTION 11

분산 트랜잭션 · 2PC · Saga

여러 DB·서비스에 걸친 작업을 한 덩어리처럼 만드는 방법입니다. 요즘은 2PC 보다 Saga + 아웃박스를 씁니다.

분산 트랜잭션의 선택은 "락을 오래 쥘 것인가, 중간 상태를 감당할 것인가"입니다 — 공짜로 원자성을 얻는 방법은 없습니다.

2PC (2단계 커밋)

1단계
준비 (prepare)코디네이터가 모든 참여자에게 "커밋할 수 있나?" 묻고, 참여자는 락을 잡은 채 "가능"이라 답합니다.
▼
2단계
커밋 (commit)전부 가능이면 커밋 지시, 하나라도 불가면 롤백 지시.
2PC 를 실무에서 잘 안 쓰는 이유
① 코디네이터가 죽으면 참여자들이 락을 잡은 채 무한 대기(blocking)
② 준비~커밋 사이에 모든 참여자의 락이 유지되어 처리량이 급락
③ 마이크로서비스 환경에서 서비스 간 강한 결합을 만듭니다

Saga — 보상 트랜잭션

정상 흐름
  ① 주문 생성   → ② 결제 승인   → ③ 재고 차감   → ④ 배송 요청

③에서 실패하면 (재고 부족)
  ← ②' 결제 취소(보상)   ← ①' 주문 취소(보상)

각 단계는 독립된 로컬 트랜잭션이고,
실패하면 앞 단계를 되돌리는 '보상 작업'을 역순으로 실행합니다.
Saga 의 전제 — 모든 단계에 보상 작업이 정의 가능해야 합니다. "이메일 발송"처럼 되돌릴 수 없는 작업은 가장 마지막에 두거나, "취소 안내 메일"이라는 별도 보상으로 설계합니다.

아웃박스 패턴 — 이중 쓰기 문제 해결

✗ DB 저장 + 메시지 발행
with db.transaction():
    save_order(order)
mq.publish("order.created", order)   # ← 여기서 서버가 죽으면?

# DB 에는 주문이 있는데 메시지는 안 나감
# 반대 순서로 하면 메시지는 나갔는데 DB 에 없음
✓ 같은 트랜잭션에 아웃박스 기록
with db.transaction():
    save_order(order)
    insert_outbox("order.created", payload)  # 같은 DB · 같은 트랜잭션

# 별도 워커(또는 CDC)가 outbox 를 읽어 발행하고 완료 표시
# → 원자성 보장. 최소 1회 전달이므로 소비 측은 멱등하게
실무의 현실적 정답 —
① 가능하면 한 트랜잭션 안에 들어가도록 경계를 다시 그리세요(같은 DB로 모으기)
② 안 되면 아웃박스 + 멱등 소비
③ 보상이 명확한 업무 흐름이면 Saga
④ 2PC 는 레거시 연동 등 정말 불가피할 때만
SECTION 12

CAP · 일관성 모델 · NewSQL

분산 시스템에서는 모든 것을 동시에 가질 수 없습니다. 무엇을 포기할지 고르는 것이 설계입니다.

CAP뜻
C 일관성어느 노드에 물어도 같은 최신 값
A 가용성일부가 죽어도 요청에 응답
P 분단 내성네트워크가 갈라져도 동작
흔한 오해 — "셋 중 둘을 고른다"는 표현이 널리 퍼져 있지만, 분산 시스템에서 네트워크 분단(P)은 선택 사항이 아닙니다 — 반드시 일어납니다. 실제 선택은 분단이 일어났을 때 C를 지킬 것인가(응답 거부), A를 지킬 것인가(옛 데이터 응답)입니다.
더 실용적인 틀은 PACELC 입니다 — 분단(P) 시에는 A/C 중, 정상(E) 시에는 지연(L)과 일관성(C) 중 무엇을 택할지.

일관성 모델

모델보장예
선형화모든 연산이 단일 시간축 위에 있는 것처럼etcd · Spanner
순차 일관성모든 노드가 같은 순서로 보지만 실시간성은 보장 안 함—
읽기-쓰기 일관성내가 쓴 것은 내가 반드시 읽음복제본 읽기에서 흔히 요구하는 수준
최종 일관성언젠가는 같아짐DNS · Cassandra 기본
실무에서 가장 자주 필요한 것은 "읽기-쓰기 일관성"입니다. 주문을 넣은 사용자가 자기 주문 목록에서 그것을 봐야 합니다. 구현은 간단합니다 — 쓰기 직후 일정 시간은 주 서버에서 읽기. (세션에 타임스탬프를 남기고 라우팅에 반영)

제품특징

NewSQL 은 만능이 아닙니다. 분산 합의 때문에 단일 노드 대비 쓰기 지연이 큽니다(수 ms → 수십 ms). 운영 복잡도도 훨씬 높습니다. 단일 PostgreSQL 로 충분한 규모라면 그것이 거의 항상 더 나은 선택입니다. "미래를 대비해서"라는 이유로 도입하면 지금의 복잡도만 늘어납니다.
SECTION 13

아카이빙 · 보관 정책

데이터는 계속 쌓입니다. 언제 어디로 치울지를 처음부터 정해야 합니다.

단계내용
핫 (Hot)최근 3~6개월. 운영 DB에 인덱스 완비
웜 (Warm)1~3년. 별도 테이블·파티션 또는 아카이브 DB
콜드 (Cold)3년 이상. S3·Glacier 등 객체 스토리지에 Parquet 등으로
파기법정 보관 기간 경과 후 반드시 삭제 — 개인정보는 보관 자체가 리스크

파티션이 있으면 아카이빙이 쉽습니다

-- PostgreSQL : 파티션을 분리해 별도 테이블로 만든 뒤 옮기고 제거
ALTER TABLE orders DETACH PARTITION orders_2023_01 CONCURRENTLY;
-- COPY orders_2023_01 TO PROGRAM 'aws s3 cp - s3://archive/orders_2023_01.csv' CSV;
DROP TABLE orders_2023_01;

-- Oracle : 파티션 교환 (즉시)
ALTER TABLE orders EXCHANGE PARTITION p_2023_01 WITH TABLE orders_archive_2023_01;

-- MySQL
ALTER TABLE orders DROP PARTITION p2023_01;
DELETE 로 대량 삭제하는 것과 비교 — 1억 행 DELETE 는 수 시간이 걸리고 로그·복제에 큰 부담을 주지만, 파티션 DROP 은 메타데이터 조작이라 즉시 끝납니다. 주기적으로 삭제할 데이터라면 처음부터 파티션으로 설계하세요.

개인정보 보관과 파기

  • 보관 기간을 컬럼으로 관리 — retention_until 을 두고 배치가 자동 처리
  • 파기는 진짜 삭제여야 — 소프트 삭제(deleted_at)는 파기가 아닙니다. 백업본까지 고려한 정책이 필요합니다
  • 가명처리·비식별화 — 통계 목적이라면 식별 정보를 지우고 남기는 방법도 있습니다
  • 삭제 요청 대응 — 사용자가 삭제를 요청했을 때 어느 테이블·백업·로그에 흩어져 있는지 미리 목록을 만들어 두세요
SECTION 14

보안 — 권한 · 암호화 · 감사

DB 유출 사고의 대부분은 정교한 공격이 아니라 권한을 너무 많이 준 것에서 시작됩니다.

① 최소 권한

  • 앱 계정에 DDL 권한 금지 — DROP TABLE 이 안 되면 인젝션이 성공해도 피해가 제한됩니다
  • 용도별 계정 분리 — 읽기 전용(분석) · 읽기쓰기(앱) · 스키마 변경(마이그레이션 전용)
  • 관리자 계정으로 앱을 붙이지 않기 — 사고 시 추적조차 불가능해집니다
  • 정기 권한 검토 — 퇴사자 계정, 임시로 준 권한이 그대로 남아 있는 경우가 매우 흔합니다

② 암호화

계층내용
전송 구간 (TLS)필수. sslmode=require 이상. 사설망이라도 켜세요
저장 암호화 (TDE)디스크·백업 파일이 유출됐을 때를 대비. DB에 접속할 수 있는 공격자에게는 무의미합니다
컬럼 암호화주민번호·카드번호 등. 암호화하면 검색·인덱스가 어려워집니다
해시 (단방향)비밀번호는 암호화가 아니라 해시. bcrypt·argon2 를 쓰고 절대 복호화 가능한 형태로 저장하지 마세요
검색이 필요한 암호화 컬럼은 설계가 까다롭습니다. 같은 값이 항상 같은 암호문이 되게 하면(결정적 암호화) 검색은 되지만 빈도 분석에 취약하고, 매번 다르게 하면 안전하지만 검색이 불가능합니다. 실무에서는 별도의 해시 컬럼(블라인드 인덱스)을 두어 동등 비교만 지원하는 방식을 씁니다.

③ 감사와 탐지

-- PostgreSQL : 접속·DDL 로깅
log_connections = on
log_disconnections = on
log_statement = 'ddl'          -- 'all' 은 부하가 큽니다
-- 세밀한 감사는 pgaudit 확장

-- MySQL : 감사 플러그인 (Percona·MariaDB 는 무료 제공)
-- Oracle : Unified Auditing
CREATE AUDIT POLICY pol_sensitive
  ACTIONS SELECT ON hr.salary, UPDATE ON hr.salary;
AUDIT POLICY pol_sensitive;
탐지해야 할 이상 징후
· 평소와 다른 시간·IP에서의 접속
· 대량 SELECT (평소 100건 조회하던 계정이 100만 건을 읽음)
· 권한 변경·계정 생성
· 스키마 변경 (배포 시간 외)
· 실패한 로그인 반복
개발·테스트 환경에 운영 데이터를 그대로 복사하지 마세요. 실무에서 가장 흔한 개인정보 유출 경로입니다. 마스킹·가명처리한 데이터셋을 만들어 쓰거나, 합성 데이터를 생성하세요.
SECTION 15

장애 대응 시나리오

실제로 일어나는 유형과 대응 순서입니다. 당황하지 않는 것이 절반입니다.

증상확인 순서 → 조치
커넥션 고갈
"too many connections"		 ① 현재 커넥션 목록에서 idle in transaction 확인 → ② 오래된 세션 종료 → ③ 원인 쿼리·누수 코드 수정 → ④ 풀 설정 재검토
디스크 가득 참 ① 로그 파일부터 정리(WAL·binlog·에러 로그) → ② 임시 테이블스페이스 → ③ 오래된 파티션 DROP → ④ VACUUM FULL 은 추가 공간이 필요하니 주의
CPU 100% ① 현재 실행 중인 쿼리 확인 → ② 가장 무거운 쿼리 종료 → ③ 실행계획 확인(통계·인덱스) → ④ 필요하면 해당 기능 일시 차단
복제 지연 폭증 ① 대량 DML 이 있었는지 확인 → ② 복제본 IO 상태 → ③ 읽기 트래픽을 주 서버로 임시 전환 → ④ 병렬 복제 설정
락으로 전면 정지 ① 블로킹 체인의 맨 위 세션 찾기 → ② 그 세션 종료 → ③ 원인(긴 트랜잭션·DDL) 파악 → ④ 재발 방지
실수로 DELETE ① 즉시 쓰기 중단(추가 변경이 복구를 어렵게 함) → ② Oracle 이면 Flashback → ③ 그 외는 백업 + 로그로 시점 복구 → ④ 복구 전 현재 상태를 먼저 백업
DB 가 안 뜸 ① 로그를 먼저 읽으세요 → ② 디스크·권한 확인 → ③ 복구 중이면 기다림(강제 종료 금지) → ④ 손상이면 백업에서 복원
장애 중에 절대 하지 말아야 할 것
· 여러 조치를 동시에 — 무엇이 효과가 있었는지 알 수 없게 됩니다
· 재시작부터 — 원인이 사라지고 다시 같은 장애가 납니다. 가능하면 상태를 먼저 수집하세요
· 백업 없이 복구 시도 — 현재 상태를 먼저 보존하세요
· 혼자 판단 — 되돌릴 수 없는 조치(파일 삭제·강제 복구)는 반드시 공유 후에
사후에 반드시 할 것 — 포스트모템을 사람이 아니라 시스템 관점으로 씁니다. "왜 이 상황이 가능했는가", "왜 더 일찍 알지 못했는가", "다음에 같은 일이 생기면 자동으로 막히는가". 비난하지 않는 회고(blameless postmortem)여야 진짜 원인이 나옵니다.
SECTION 16

DBA 없이 살아남기

전담 DBA가 없는 팀이 최소한 이것만은 해야 하는 목록입니다.

매일

  • 백업이 실제로 만들어졌는지 확인 (성공 알림이 아니라 파일 크기와 시각)
  • 디스크 사용률·커넥션 수 대시보드 확인
  • 에러 로그에 새로운 유형이 있는지

매주

  • 슬로우 쿼리 상위 10개 확인 — 새로 등장한 것이 있는지
  • 테이블·인덱스 크기 증가 추이
  • 안 쓰이는 인덱스 확인

매월 · 분기

  • 백업에서 실제로 복구해 보기 — 이것을 하지 않으면 백업은 없는 것과 같습니다
  • 권한 검토 — 퇴사자·불필요한 권한 정리
  • DB 마이너 버전 업데이트 (보안 패치)
  • 용량 계획 — 현재 증가율로 언제 한계에 닿는지
