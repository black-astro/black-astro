SECTION 01

SQL은 어떤 언어인가

SQL은 "이렇게 해라"가 아니라 "이런 결과를 달라"고 쓰는 언어입니다. 어떻게 찾을지는 DB가 알아서 정합니다 — 그래서 같은 결과라도 DB가 고르는 방법에 따라 속도가 100배 차이납니다.

명령은 네 종류뿐입니다

분류명령하는 일
DQL
조회		 SELECT 데이터를 꺼냅니다. 실무에서 쓰는 SQL의 80% 이상이 이것입니다.
DML
조작		 INSERT · UPDATE · DELETE · MERGE 데이터를 넣고 고치고 지웁니다. 트랜잭션으로 되돌릴 수 있습니다.
DDL
정의		 CREATE · ALTER · DROP · TRUNCATE 표 자체를 만들고 바꾸고 지웁니다. 대부분의 DB에서 자동 커밋되어 되돌릴 수 없습니다.
DCL/TCL
권한·거래		 GRANT · REVOKE · COMMIT · ROLLBACK 권한을 주고 뺏거나, 작업을 확정·취소합니다.
DELETE 와 TRUNCATE 는 완전히 다릅니다. DELETE 는 행을 한 줄씩 지우고 ROLLBACK 으로 되돌릴 수 있습니다. TRUNCATE 는 표를 통째로 비우는 DDL 이라 대부분 되돌릴 수 없습니다(PostgreSQL은 예외적으로 트랜잭션 안에서 롤백 가능). 운영 DB에서 TRUNCATE 를 칠 때는 반드시 두 번 확인하세요.

표준 SQL과 방언

SQL에는 ANSI/ISO 표준이 있지만, 완벽히 지키는 DB는 없습니다. 각 DB는 표준을 대부분 따르면서 자기만의 문법(방언, dialect)을 얹습니다. 이 가이드는 표준에 가까운 문법을 기본으로 쓰고, 차이가 나는 지점마다 네 DB를 나란히 보여 줍니다.

SECTION 02

SELECT — 조회의 기본

SELECT 무엇을 FROM 어디서. 이 두 단어면 시작할 수 있습니다. 

-- 전체 컬럼, 전체 행
SELECT * FROM member;

-- 필요한 컬럼만 (실무에서는 이쪽을 씁니다)
SELECT id, name, city FROM member;

-- 별칭(alias) — 결과에 보일 이름을 바꿉니다
SELECT id     AS 회원번호,
       name   AS 이름,
       city   AS 지역
FROM   member;

-- 계산해서 보여주기
SELECT name, price, price * 0.1 AS 부가세
FROM   product;

-- 중복 제거
SELECT DISTINCT city FROM member;
SELECT DISTINCT city, grade FROM member;   -- 두 컬럼 조합 기준 중복 제거
city 서울 부산 대전
SELECT * 는 연습용입니다. 실무 코드에 쓰면 ① 필요 없는 컬럼까지 네트워크로 보내 느려지고, ② 나중에 컬럼이 추가되면 앱이 예상 못 한 데이터를 받고, ③ 커버링 인덱스(⚙️ t05)를 못 타게 됩니다. 확인할 때만 쓰고, 코드에는 컬럼을 명시하세요.

별칭에 공백이나 한글을 쓰려면

-- 표준 · PostgreSQL · Oracle · SQLite : 큰따옴표
SELECT name AS "회원 이름" FROM member;

-- MySQL : 백틱도 됩니다 (큰따옴표는 설정에 따라 문자열로 해석될 수 있음)
SELECT name AS `회원 이름` FROM member;
따옴표 규칙 정리 — 작은따옴표('')는 문자열 값, 큰따옴표("")는 식별자(테이블·컬럼 이름)입니다. WHERE city = "서울" 이라고 쓰면 PostgreSQL은 "서울이라는 이름의 컬럼"을 찾다가 에러를 냅니다. 값에는 항상 작은따옴표를 쓰세요.

주석

-- 한 줄 주석 (하이픈 두 개 + 공백)

/* 여러 줄 주석
   이렇게 감쌉니다 */

SELECT name  -- 줄 끝에도 쓸 수 있습니다
FROM   member;
SECTION 03

WHERE — 조건 필터링

엑셀의 자동 필터와 같습니다. 조건에 맞는 행만 남깁니다. 

-- 비교
SELECT * FROM product WHERE price >= 50000;
SELECT * FROM member  WHERE city = '서울';
SELECT * FROM member  WHERE city <> '서울';     -- != 도 대부분 됩니다

-- 범위
SELECT * FROM product WHERE price BETWEEN 20000 AND 50000;   -- 양쪽 끝 포함

-- 목록
SELECT * FROM member WHERE city IN ('서울','부산');
SELECT * FROM member WHERE grade NOT IN ('BASIC');

-- 패턴 (문자열)
SELECT * FROM product WHERE name LIKE '%마우스%';   -- 포함
SELECT * FROM product WHERE name LIKE 'USB%';      -- 로 시작
SELECT * FROM member  WHERE email LIKE '%@example.com';

-- 빈 값
SELECT * FROM member WHERE email IS NULL;
SELECT * FROM member WHERE email IS NOT NULL;

-- 여러 조건 조합
SELECT * FROM product
WHERE  category = '주변기기'
  AND  price < 40000
  AND  stock > 0;

AND · OR 를 섞을 때는 괄호를 치세요

✗ 의도와 다르게 동작
SELECT * FROM member
WHERE  city = '서울'
   OR  city = '부산'
  AND  grade = 'GOLD';

-- AND 가 먼저 계산되므로 실제로는
-- 서울 전부  +  (부산 AND GOLD)
✓ 괄호로 의도를 명시
SELECT * FROM member
WHERE  (city = '서울' OR city = '부산')
  AND  grade = 'GOLD';

-- 서울이거나 부산이면서, GOLD 인 사람

LIKE 의 함정

패턴뜻인덱스
LIKE '서울%'서울로 시작인덱스 사용 가능
LIKE '%서울'서울로 끝인덱스 못 씀 (풀스캔)
LIKE '%서울%'포함인덱스 못 씀 (풀스캔)
_아무 글자 한 개 — '김_' 은 두 글자 이름—
앞에 % 가 붙은 검색은 인덱스를 못 씁니다. 데이터가 수백만 건이면 그대로 장애가 됩니다. 본문 검색이 필요하면 전문 검색(Full-Text Search)을 써야 합니다 → 🎓 전문가 탭 e11 · 🐘 PostgreSQL p09 · 🪶 SQLite s10.

대소문자 구분

PostgreSQL
-- 기본은 구분함
WHERE name = 'Kim'      -- 'kim' 안 걸림
WHERE name ILIKE 'kim%' -- 대소문자 무시 LIKE
WHERE LOWER(name) = 'kim'
MySQL / MariaDB
-- 기본 콜레이션이 _ci 라 구분 안 함
WHERE name = 'kim'      -- 'Kim' 도 걸림
-- 구분하려면
WHERE name = 'Kim' COLLATE utf8mb4_bin
Oracle
-- 기본은 구분함
WHERE UPPER(name) = 'KIM'
-- 세션 단위로 끄기 (12c+)
ALTER SESSION SET
  NLS_COMP=LINGUISTIC NLS_SORT=BINARY_CI;
SQLite
-- ASCII 만 대소문자 무시 지원
WHERE name = 'kim' COLLATE NOCASE
-- 한글·유니코드는 구분함
WHERE LOWER(name) = 'kim' 은 인덱스를 죽입니다. 컬럼에 함수를 씌우면 그 컬럼의 인덱스를 못 씁니다. 함수 기반 인덱스를 따로 만들거나(⚙️ t06), 저장할 때부터 소문자로 넣으세요.
SECTION 04

ORDER BY · LIMIT

정렬하고 몇 개만 자릅니다. 둘을 합치면 "매출 상위 10건" 같은 요청이 바로 처리됩니다. 

-- 오름차순 (기본값, ASC 는 생략 가능)
SELECT * FROM product ORDER BY price;

-- 내림차순
SELECT * FROM product ORDER BY price DESC;

-- 여러 기준 — 앞의 것이 같을 때 뒤의 것으로
SELECT * FROM member ORDER BY city, joined_at DESC;

-- 별칭으로 정렬 (ORDER BY 는 SELECT 다음이라 가능합니다)
SELECT name, price * 0.9 AS 할인가
FROM   product
ORDER  BY 할인가 DESC;

NULL 은 어디에 놓일까

DBASC 일 때 NULL 위치바꾸는 법
PostgreSQL맨 뒤ORDER BY x NULLS FIRST
Oracle맨 뒤ORDER BY x NULLS FIRST
MySQL / MariaDB맨 앞ORDER BY (x IS NULL), x
SQLite맨 앞NULLS LAST 지원 (3.30+)

상위 N건 — DB마다 문법이 다릅니다

PostgreSQL
SELECT * FROM product
ORDER BY price DESC
LIMIT 3 OFFSET 0;
MySQL / MariaDB
SELECT * FROM product
ORDER BY price DESC
LIMIT 3;          -- LIMIT 0, 3 도 동일
Oracle (12c 이상)
SELECT * FROM product
ORDER BY price DESC
FETCH FIRST 3 ROWS ONLY;

-- 11g 이하는 ROWNUM 을 씁니다 (o05 참고)
SQLite
SELECT * FROM product
ORDER BY price DESC
LIMIT 3;
표준 문법은 OFFSET … FETCH 입니다. PostgreSQL·Oracle·SQL Server 가 지원하고, MySQL 8.4·SQLite 는 LIMIT 만 씁니다. 이식성이 중요하면 표준을, 아니면 각 DB의 관례를 따르세요.
정렬 기준이 유일하지 않으면 페이징이 깨집니다. ORDER BY price DESC LIMIT 10 에서 같은 가격이 여러 개면 페이지를 넘길 때마다 순서가 달라져 같은 행이 두 번 나오거나 아예 빠질 수 있습니다. 마지막에 항상 유일한 컬럼(보통 id)을 붙이세요: ORDER BY price DESC, id DESC.
SECTION 05

NULL — 가장 흔한 함정

NULL은 0도, 빈 문자열도, false도 아닙니다. "모른다"는 뜻입니다. 이 한 줄을 이해하면 초보가 겪는 버그의 상당수가 사라집니다.

NULL 은 값이 아니라 "모른다"는 상태입니다. 모르는 값끼리 비교하면 답도 "모른다"가 됩니다.

모르는 값끼리는 비교할 수 없습니다

-- ✗ 절대 참이 되지 않습니다 (결과 0행)
SELECT * FROM member WHERE email = NULL;

-- ✓ 이렇게 씁니다
SELECT * FROM member WHERE email IS NULL;
SELECT * FROM member WHERE email IS NOT NULL;
왜 그럴까 — "모르는 값 = 모르는 값" 은 참일까요? 나이를 모르는 두 사람이 동갑인지 알 수 없듯, SQL은 참도 거짓도 아닌 UNKNOWN을 돌려줍니다. WHERE 는 참인 행만 남기므로 UNKNOWN 은 걸러집니다.

계산에 섞이면 전부 NULL이 됩니다

SELECT 1000 + NULL;        -- NULL  (0 이 아닙니다)
SELECT '주문-' || NULL;     -- NULL  (Oracle 은 예외적으로 '주문-')

-- 그래서 이렇게 방어합니다
SELECT COALESCE(email, '(이메일 없음)') FROM member;   -- 표준 · 어디서나
SELECT NVL(email, '(없음)')  FROM member;              -- Oracle
SELECT IFNULL(email, '(없음)') FROM member;            -- MySQL · SQLite

집계 함수는 NULL을 빼고 셉니다

-- 회원 5명 중 email 이 있는 사람은 4명 (정바람만 NULL)
SELECT COUNT(*)     AS 전체,       -- 5   ← 행의 개수 (NULL 이든 아니든)
       COUNT(email) AS 이메일있음  -- 4   ← NULL 이 아닌 값의 개수
FROM   member;

-- 평균도 마찬가지 — NULL 인 행은 분모에서도 빠집니다
SELECT COUNT(*)   AS 상품수,      -- 5
       AVG(price) AS 평균가        -- price 가 NULL 인 상품이 있다면 그 행은 제외
FROM   product;
평균이 이상하게 나온다면 여기를 의심하세요. AVG(score) 는 점수가 NULL인 사람을 분모에서도 제외합니다. "미응답을 0점으로 치고 싶다"면 AVG(COALESCE(score, 0)) 이라고 명시해야 합니다.

가장 악명 높은 함정 — NOT IN 과 NULL

✗ 결과가 통째로 0행
-- 서브쿼리 결과에 NULL 이 하나라도 있으면
SELECT * FROM member
WHERE  id NOT IN (SELECT member_id FROM orders);

-- member_id 에 NULL 이 섞이는 순간
-- 전체 결과가 0행이 됩니다
✓ NOT EXISTS 를 쓰세요
SELECT * FROM member m
WHERE  NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE  o.member_id = m.id
);

-- NULL 이 있어도 정상 동작하고
-- 보통 더 빠릅니다

빈 문자열과 NULL은 다릅니다 — 오라클만 빼고

DB'' (빈 문자열)의 취급
PostgreSQLNULL과 다릅니다. '' IS NULL 은 false
MySQL / MariaDBNULL과 다릅니다
SQLiteNULL과 다릅니다
Oracle빈 문자열을 NULL로 취급합니다. 오라클만의 특이점이며 마이그레이션에서 반드시 걸립니다
실무 원칙 — 값이 없을 수 있는 컬럼은 NULL 허용을 명시하고, 없어서는 안 되는 컬럼은 NOT NULL + DEFAULT 로 잠그세요. "일단 NULL 허용해 두자"가 나중에 집계 오류와 NPE(널 포인터)의 근원이 됩니다.

그 밖에 알아 두면 좋은 것

  • BOOLEAN — PostgreSQL·SQLite는 지원. Oracle은 23ai부터 지원(이전에는 NUMBER(1)). MySQL의 BOOLEAN 은 사실 TINYINT(1) 의 별칭입니다.
  • UUID — PostgreSQL은 전용 타입, MySQL은 BINARY(16) 권장(문자열로 넣으면 인덱스가 커집니다).
  • JSON / JSONB — 스키마가 자주 바뀌는 데이터용. PostgreSQL의 JSONB가 가장 강력합니다 → 🐘 p07.
  • ENUM — 값 목록을 타입으로 강제. 편하지만 값 추가 시 DDL이 필요해 실무에서는 코드 테이블을 선호합니다.
SECTION 07

INSERT · UPDATE · DELETE

데이터를 바꾸는 세 명령입니다. WHERE를 빠뜨리는 순간 전체가 바뀝니다. 

-- INSERT : 컬럼을 명시하는 습관을 들이세요
INSERT INTO member (id, name, email, grade, city, joined_at)
VALUES (6, '한바다', 'han@example.com', 'BASIC', '광주', '2026-08-01');

-- 여러 건 한 번에 (Oracle 제외)
INSERT INTO member (id, name, grade, city, joined_at) VALUES
 (7, '오하늘', 'BASIC', '서울', '2026-08-02'),
 (8, '유들판', 'BASIC', '대구', '2026-08-03');

-- 조회 결과를 그대로 넣기 (백업 테이블 만들 때 유용)
INSERT INTO member_archive (id, name, city)
SELECT id, name, city FROM member WHERE joined_at < '2025-01-01';
-- UPDATE : WHERE 를 반드시
UPDATE member
SET    grade = 'GOLD'
WHERE  id = 3;

-- 여러 컬럼 동시에
UPDATE product
SET    price = price * 1.1,
       stock = stock - 1
WHERE  id = 10;

-- 다른 테이블 값을 참고해 갱신 (문법이 DB마다 다릅니다)
-- PostgreSQL
UPDATE orders o
SET    status = 'VIP'
FROM   member m
WHERE  m.id = o.member_id AND m.grade = 'GOLD';

-- MySQL
UPDATE orders o
JOIN   member m ON m.id = o.member_id
SET    o.status = 'VIP'
WHERE  m.grade = 'GOLD';
-- DELETE
DELETE FROM order_item WHERE order_id = 1003;
DELETE FROM orders     WHERE id = 1003;

-- 전부 지우기 (되돌릴 수 있음)
DELETE FROM orders;

-- 표를 비우기 (빠르지만 대부분 되돌릴 수 없음)
TRUNCATE TABLE orders;
운영 DB에서 UPDATE·DELETE 를 칠 때의 3단계 안전 절차
① SELECT 로 먼저 대상을 확인합니다 — SELECT * FROM member WHERE id = 3;
② 확인이 끝나면 SELECT 부분만 UPDATE … SET 으로 바꿉니다 (WHERE 는 그대로 둡니다)
③ 자동 커밋을 끄고(BEGIN;) 실행한 뒤 영향 행 수를 확인하고 COMMIT 합니다 
-- ③ 의 실제 모습
BEGIN;

UPDATE member SET grade = 'GOLD' WHERE id = 3;
-- UPDATE 1     ← 1행. 예상과 같으면

COMMIT;
-- 예상과 다르면 ROLLBACK;
실수를 구조적으로 막는 방법 — ① 운영 DB 접속은 기본 자동 커밋을 끈 클라이언트로 합니다(DBeaver 설정에 있습니다). ② 앱 계정에는 DELETE 권한을 주지 않고 삭제 대신 deleted_at 컬럼을 채우는 소프트 삭제를 씁니다. ③ 삭제 전 백업 테이블에 INSERT … SELECT 로 옮겨 둡니다.
SECTION 08

CREATE TABLE · 제약조건

제약조건은 DB가 강제로 지켜 주는 규칙입니다. 앱 코드의 검증은 빠뜨릴 수 있지만, 제약조건은 빠져나갈 수 없습니다. 

CREATE TABLE coupon (
    id          INTEGER       PRIMARY KEY,              -- 유일 + NOT NULL
    code        VARCHAR(20)   NOT NULL UNIQUE,          -- 중복 금지
    member_id   INTEGER       NOT NULL,
    discount    DECIMAL(5,2)  NOT NULL
                CHECK (discount > 0 AND discount <= 50),-- 값 범위 강제
    used        CHAR(1)       NOT NULL DEFAULT 'N',
    expires_at  DATE          NOT NULL,
    CONSTRAINT fk_coupon_member                          -- 이름을 붙이면 에러 추적이 쉽습니다
        FOREIGN KEY (member_id) REFERENCES member(id)
        ON DELETE CASCADE
);
제약뜻없으면 생기는 일
PRIMARY KEY이 행을 유일하게 가리키는 값같은 회원이 두 번 들어가도 구분 불가
FOREIGN KEY다른 표의 키를 가리킴존재하지 않는 회원의 주문이 쌓임 (고아 데이터)
NOT NULL빈 값 금지이름 없는 회원이 생김
UNIQUE중복 금지 (NULL은 여러 개 허용)같은 이메일로 계정 두 개
CHECK값의 범위 제한수량이 −5인 주문
DEFAULT안 넣으면 이 값상태가 비어 있는 행

외래키의 ON DELETE 옵션

옵션부모(member)를 지우면
NO ACTION / RESTRICT기본값. 자식이 있으면 삭제를 막습니다 — 가장 안전합니다
CASCADE자식(주문)도 같이 지웁니다 — 편하지만 실수하면 대량 삭제입니다
SET NULL자식의 참조 컬럼을 NULL로 (컬럼이 NULL 허용이어야 함)
ON DELETE CASCADE 는 신중하게. 회원 한 명을 지웠는데 주문·결제·리뷰가 연쇄로 사라질 수 있습니다. 실무에서는 기본값(삭제 금지) + 소프트 삭제 조합을 훨씬 많이 씁니다.

JOIN 5종

두 표를 키로 이어 붙이는 것이 JOIN입니다. 엑셀 VLOOKUP이 하는 일과 같습니다. 아래 버튼을 눌러 종류별 결과를 직접 비교해 보세요.

JOIN 종류에 따라 결과가 어떻게 달라지나

member (왼쪽)

order_nomember_id

결과 — 

-- INNER JOIN : 양쪽에 다 있는 것만 (JOIN 만 써도 INNER 입니다)
SELECT m.name, o.id AS order_no
FROM   member m
JOIN   orders o ON o.member_id = m.id;

-- LEFT JOIN : 왼쪽은 전부 (실무에서 가장 많이 씁니다)
SELECT m.name, o.id AS order_no
FROM   member m
LEFT JOIN orders o ON o.member_id = m.id;

-- 주문이 한 번도 없는 회원 찾기 — LEFT JOIN 의 대표 활용
SELECT m.name
FROM   member m
LEFT JOIN orders o ON o.member_id = m.id
WHERE  o.id IS NULL;

-- 세 개 이상 붙이기
SELECT m.name, p.name AS product, oi.qty
FROM   member m
JOIN   orders o      ON o.member_id  = m.id
JOIN   order_item oi ON oi.order_id  = o.id
JOIN   product p     ON p.id         = oi.product_id
WHERE  o.status = 'PAID';
LEFT JOIN 뒤에 WHERE 를 붙이면 INNER JOIN 이 됩니다. LEFT JOIN orders o … WHERE o.status = 'PAID' 라고 쓰면 주문이 없는 회원은 o.status 가 NULL이라 조건에서 걸러집니다. 오른쪽 테이블 조건은 ON 절에 넣으세요: LEFT JOIN orders o ON o.member_id = m.id AND o.status = 'PAID'.

JOIN 하면 행이 늘어납니다

회원 1명에게 주문이 3건 있으면, 조인 결과에서 그 회원은 3번 나옵니다. 그래서 조인 후 SUM() 을 하면 값이 부풀 수 있습니다 — 실무에서 가장 흔한 집계 오류입니다.

✗ 금액이 부풀어 오름
-- 주문이 여러 건이면 회원 정보가 반복되어
-- 포인트가 주문 수만큼 더해집니다
SELECT m.name,
       SUM(m.point) AS 포인트,   -- 부풀어 오름!
       SUM(oi.qty)  AS 수량
FROM member m
JOIN orders o      ON o.member_id = m.id
JOIN order_item oi ON oi.order_id = o.id
GROUP BY m.name;
✓ 집계를 먼저 하고 붙이기
SELECT m.name, m.point, t.수량
FROM   member m
JOIN  (SELECT o.member_id, SUM(oi.qty) AS 수량
       FROM   orders o
       JOIN   order_item oi ON oi.order_id = o.id
       GROUP  BY o.member_id) t
  ON   t.member_id = m.id;
SELF JOIN — 같은 표를 자기 자신과 붙이는 것입니다. 직원과 상사가 같은 employee 표에 있을 때 FROM employee e JOIN employee b ON b.id = e.manager_id 처럼 씁니다. 별칭(e, b)을 반드시 달아야 어느 쪽인지 구분됩니다.
SECTION 10

GROUP BY · 집계 함수

엑셀 피벗테이블이 하는 일입니다. 같은 값끼리 묶어서 계산합니다.

집계 함수 다섯 개

함수하는 일NULL 취급
COUNT(*)행의 개수NULL 행도 셉니다
COUNT(컬럼)그 컬럼이 NULL이 아닌 개수NULL 제외
SUM(컬럼)합계NULL 제외

-- 전체 집계 (GROUP BY 없이)
SELECT COUNT(*) AS 상품수, AVG(price) AS 평균가, MAX(price) AS 최고가
FROM   product;

-- 카테고리별로 묶어서
SELECT category,
       COUNT(*)   AS 상품수,
       AVG(price) AS 평균가,
       SUM(stock) AS 총재고
FROM   product
GROUP  BY category
ORDER  BY 평균가 DESC;

-- 두 컬럼으로 묶기
SELECT city, grade, COUNT(*) AS 인원
FROM   member
GROUP  BY city, grade
ORDER  BY city, grade;

-- 조인 + 집계 — 회원별 총 구매액
SELECT m.name,
       COUNT(DISTINCT o.id)          AS 주문건수,
       SUM(oi.qty * oi.unit_price)   AS 총구매액
FROM   member m
JOIN   orders o      ON o.member_id = m.id
JOIN   order_item oi ON oi.order_id = o.id
WHERE  o.status <> 'CANCELED'
GROUP  BY m.name
ORDER  BY 총구매액 DESC;
name 주문건수 총구매액 최나무 2 694000 박바다 2 370000 김하늘 1 103000
GROUP BY 의 철칙 — SELECT 에 쓴 컬럼은 ① GROUP BY 에 있거나 ② 집계 함수 안에 있어야 합니다.
PostgreSQL·Oracle은 어기면 에러를 냅니다. MySQL은 설정(ONLY_FULL_GROUP_BY)에 따라 통과시키기도 하는데, 이때 나오는 값은 그룹 안 아무 행이나라서 결과를 믿을 수 없습니다.

COUNT(*) vs COUNT(컬럼) vs COUNT(DISTINCT)

SELECT COUNT(*)              AS 전체행,      -- 5
       COUNT(email)          AS 이메일보유,  -- 4  (NULL 제외)
       COUNT(DISTINCT city)  AS 지역수       -- 3  (서울·부산·대전)
FROM   member;
조인 후 COUNT(*) 는 위험합니다. 주문 3건이 붙으면 회원 1명이 3으로 세어집니다. "주문한 회원 수"를 원한다면 COUNT(DISTINCT m.id) 를 쓰세요.
SECTION 11

HAVING vs WHERE

둘 다 "거른다"지만 거르는 시점이 다릅니다. WHERE는 묶기 전에, HAVING은 묶은 다음에 거릅니다.

1
FROM · JOIN표를 읽고 붙입니다
▼
2 · WHERE
개별 행을 거릅니다아직 그룹이 없으므로 집계 함수를 쓸 수 없습니다
▼
3
GROUP BY남은 행을 묶습니다
▼
4 · HAVING
묶인 그룹을 거릅니다여기서는 집계 함수를 쓸 수 있습니다
-- "취소되지 않은 주문만 대상으로, 총 구매액 30만원 넘는 회원"
SELECT m.name, SUM(oi.qty * oi.unit_price) AS 총구매액
FROM   member m
JOIN   orders o      ON o.member_id = m.id
JOIN   order_item oi ON oi.order_id = o.id
WHERE  o.status <> 'CANCELED'          -- ← 행 단위 조건 (묶기 전)
GROUP  BY m.name
HAVING SUM(oi.qty * oi.unit_price) > 300000   -- ← 그룹 조건 (묶은 뒤)
ORDER  BY 총구매액 DESC;
✗ WHERE 에 집계 함수 — 에러
SELECT category, COUNT(*)
FROM   product
WHERE  COUNT(*) > 2      -- ✗
GROUP  BY category;
✓ HAVING 으로
SELECT category, COUNT(*)
FROM   product
GROUP  BY category
HAVING COUNT(*) > 2;     -- ✓
성능 관점 — 같은 결과를 낼 수 있다면 WHERE 를 먼저 쓰세요. WHERE 로 행을 미리 줄이면 그룹핑할 데이터 자체가 적어집니다. HAVING 은 집계 결과에만 걸 수 있는 조건에 씁니다.
SECTION 12

서브쿼리 3형태

쿼리 안의 쿼리입니다. 기준값을 먼저 구해야 할 때 씁니다. 들어가는 위치에 따라 세 가지로 나뉩니다.

서브쿼리를 고를 때 던질 질문은 하나입니다 — 내가 필요한 것이 값 하나인가, 표인가, 조건인가.

① WHERE 절 — 조건으로

-- 평균 가격보다 비싼 상품
SELECT name, price
FROM   product
WHERE  price > (SELECT AVG(price) FROM product);

-- 주문한 적 있는 회원 (IN)
SELECT name FROM member
WHERE  id IN (SELECT member_id FROM orders);

-- 같은 일을 EXISTS 로 — 보통 더 빠르고 NULL 에 안전합니다
SELECT name FROM member m
WHERE  EXISTS (SELECT 1 FROM orders o WHERE o.member_id = m.id);

② FROM 절 — 임시 표로 (인라인 뷰)

-- 회원별 구매액을 먼저 구하고, 그중 상위만
SELECT *
FROM  (SELECT m.id, m.name, SUM(oi.qty * oi.unit_price) AS 구매액
       FROM   member m
       JOIN   orders o      ON o.member_id = m.id
       JOIN   order_item oi ON oi.order_id = o.id
       GROUP  BY m.id, m.name) t
WHERE  t.구매액 > 200000
ORDER  BY t.구매액 DESC;
이렇게 중첩이 깊어지면 CTE(WITH) 로 바꾸는 편이 훨씬 읽기 좋습니다 → 🎓 전문가 탭 e04.

③ SELECT 절 — 값 하나로 (스칼라 서브쿼리)

SELECT m.name,
       (SELECT COUNT(*) FROM orders o WHERE o.member_id = m.id) AS 주문수
FROM   member m;
스칼라 서브쿼리는 행마다 실행될 수 있습니다. 회원 10만 명이면 서브쿼리가 10만 번 도는 셈입니다. 옵티마이저가 조인으로 바꿔 주기도 하지만 보장되지 않습니다. 행이 많으면 LEFT JOIN + GROUP BY 로 바꾸세요.

상관 서브쿼리 — 바깥 값을 참조하는 것

-- 카테고리 안에서 평균보다 비싼 상품
SELECT p.name, p.category, p.price
FROM   product p
WHERE  p.price > (SELECT AVG(p2.price)
                  FROM   product p2
                  WHERE  p2.category = p.category);   -- ← 바깥 p 를 참조

-- 같은 일을 윈도우 함수로 (보통 더 빠릅니다 · e01 참고)
SELECT name, category, price
FROM  (SELECT name, category, price,
              AVG(price) OVER (PARTITION BY category) AS 카테고리평균
       FROM   product) t
WHERE  price > 카테고리평균;
SECTION 13

집합 연산 UNION

JOIN이 옆으로 붙인다면, UNION은 위아래로 이어 붙입니다. 

-- UNION : 합치고 중복 제거 (정렬 비용이 듭니다)
SELECT name FROM member WHERE city = '서울'
UNION
SELECT name FROM member WHERE grade = 'GOLD';

-- UNION ALL : 합치기만 (중복 제거 안 함 · 훨씬 빠름)
SELECT id, name, '2026-01' AS 월 FROM sales_202601
UNION ALL
SELECT id, name, '2026-02'       FROM sales_202602;

-- INTERSECT : 양쪽 모두에 있는 것
SELECT name FROM member WHERE city = '서울'
INTERSECT
SELECT name FROM member WHERE grade = 'GOLD';

-- EXCEPT : 앞에는 있고 뒤에는 없는 것 (Oracle 은 MINUS)
SELECT id FROM member
EXCEPT
SELECT member_id FROM orders;

UNION 을 쓸 때 지켜야 할 것

② 같은 자리의 타입이 호환돼야 합니다
③ 결과 컬럼 이름은 첫 번째 SELECT 를 따릅니다

중복이 없다는 걸 안다면 반드시 UNION ALL 을 쓰세요. UNION 은 중복 제거를 위해 전체를 정렬하거나 해시를 만듭니다. 수백만 행에서는 이 차이가 수 초 대 수십 초로 벌어집니다.

실무 활용 — 데이터 대사

-- 마이그레이션 후 "옛 시스템에만 있는 회원" 찾기
SELECT id FROM legacy_member
EXCEPT
SELECT id FROM member;

-- 양쪽이 완전히 같은지 한 번에 확인 (두 방향 모두 0행이어야 함)
(SELECT * FROM a EXCEPT SELECT * FROM b)
UNION ALL
(SELECT * FROM b EXCEPT SELECT * FROM a);

CASE · COALESCE

SQL 안에서 조건 분기를 하는 방법입니다. 엑셀의 IF 함수와 같은 역할입니다. 

-- 조건형 CASE (가장 많이 씁니다)
SELECT name, price,
       CASE WHEN price >= 200000 THEN '고가'
            WHEN price >=  50000 THEN '중가'
            ELSE                      '저가'
       END AS 가격대
FROM   product;

-- 값 비교형 CASE (짧게 쓸 때)
SELECT name,
       CASE grade
            WHEN 'GOLD'   THEN '10% 할인'
            WHEN 'SILVER' THEN '5% 할인'
            ELSE               '할인 없음'
       END AS 혜택
FROM   member;

CASE + 집계 = 조건부 집계 (아주 유용합니다)

-- 한 번의 스캔으로 여러 조건의 개수를 동시에 셉니다
SELECT COUNT(*)                                            AS 전체주문,
       SUM(CASE WHEN status = 'PAID'     THEN 1 ELSE 0 END) AS 결제완료,
       SUM(CASE WHEN status = 'SHIPPED'  THEN 1 ELSE 0 END) AS 배송중,
       SUM(CASE WHEN status = 'CANCELED' THEN 1 ELSE 0 END) AS 취소
FROM   orders;

-- 표준 SQL 의 FILTER 절 (PostgreSQL·SQLite 지원 · 더 읽기 좋습니다)
SELECT COUNT(*)                             AS 전체주문,
       COUNT(*) FILTER (WHERE status='PAID') AS 결제완료,
       COUNT(*) FILTER (WHERE status='CANCELED') AS 취소
FROM   orders;
전체주문 결제완료 배송중 취소 6 3 2 1

SECTION 16

VIEW · 임시 테이블

복잡한 SELECT에 이름을 붙여 두고 테이블처럼 쓰는 것이 뷰입니다. 

CREATE VIEW v_member_sales AS
SELECT m.id, m.name, m.grade,
       COUNT(DISTINCT o.id)        AS 주문수,
       COALESCE(SUM(oi.qty * oi.unit_price), 0) AS 총구매액
FROM   member m
LEFT JOIN orders o      ON o.member_id = m.id AND o.status <> 'CANCELED'
LEFT JOIN order_item oi ON oi.order_id = o.id
GROUP  BY m.id, m.name, m.grade;

-- 이제 테이블처럼 씁니다
SELECT * FROM v_member_sales WHERE 총구매액 > 300000;

DROP VIEW v_member_sales;

뷰를 쓰는 세 가지 이유

  • 복잡함 감추기 — 다섯 개 테이블 조인을 팀원이 매번 쓰지 않아도 됩니다
  • 권한 통제 — 원본 테이블 접근은 막고, 필요한 컬럼만 담은 뷰만 열어 줍니다 (급여 테이블에서 주민번호를 뺀 뷰 등)
  • 호환 유지 — 테이블 구조를 바꿔도 뷰가 옛 모양을 유지해 주면 앱을 안 고쳐도 됩니다
뷰는 저장된 쿼리일 뿐 데이터를 갖고 있지 않습니다. 뷰를 조회할 때마다 안의 SELECT가 매번 실행됩니다. 무거운 뷰를 또 조인하면 성능이 급격히 나빠집니다. 뷰 위에 뷰를 얹는 구조는 특히 위험합니다.

구체화 뷰 (Materialized View) — 결과를 저장해 두는 뷰

-- PostgreSQL · Oracle 지원 (MySQL·SQLite 는 없음 → 집계 테이블로 직접 구현)
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT ordered_at, SUM(oi.qty * oi.unit_price) AS 매출
FROM   orders o JOIN order_item oi ON oi.order_id = o.id
GROUP  BY ordered_at;

-- 데이터는 갱신해 줘야 최신이 됩니다
REFRESH MATERIALIZED VIEW mv_daily_sales;                    -- PostgreSQL
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;       -- 잠금 없이 (유니크 인덱스 필요)

임시 테이블

-- 세션이 끝나면 자동으로 사라집니다
CREATE TEMPORARY TABLE tmp_target AS
SELECT id FROM member WHERE grade = 'GOLD';       -- PostgreSQL · MySQL · SQLite

-- Oracle 은 구조를 미리 만들고 데이터만 세션별로 격리합니다
CREATE GLOBAL TEMPORARY TABLE tmp_target (id NUMBER)
ON COMMIT PRESERVE ROWS;
언제 무엇을 쓸까 — 한 쿼리 안에서만 쓸 중간 결과는 CTE(WITH), 여러 쿼리에서 반복해 쓸 정의는 뷰, 배치 처리 중간 산출물은 임시 테이블, 매번 계산하기엔 무거운 집계는 구체화 뷰 또는 집계 테이블입니다.
SECTION 17

트랜잭션 입문

여러 변경을 전부 성공하거나 전부 취소로 묶는 장치입니다. 계좌 이체가 "출금만 되고 입금은 안 되는" 상태를 막습니다.

트랜잭션이 지켜 주는 것은 속도가 아니라 중간 상태가 밖으로 새지 않는다는 약속입니다.
BEGIN;                                   -- 트랜잭션 시작 (Oracle 은 자동 시작)

UPDATE account SET balance = balance - 10000 WHERE id = 1;   -- 출금
UPDATE account SET balance = balance + 10000 WHERE id = 2;   -- 입금

COMMIT;                                  -- 둘 다 확정
-- 문제가 있으면 ROLLBACK;  → 둘 다 없던 일로
DB트랜잭션 시작기본 자동 커밋
PostgreSQLBEGIN;켜짐 (문장 하나가 곧 트랜잭션)
MySQLSTART TRANSACTION; 또는 BEGIN;켜짐
OracleDML 을 치면 자동 시작꺼짐 — COMMIT 을 꼭 해야 합니다
SQLiteBEGIN;켜짐
Oracle 은 자동 커밋이 꺼져 있습니다. UPDATE 를 치고 창을 닫으면 변경이 사라집니다(롤백). 반대로 커밋하지 않은 채 두면 그 행에 락이 걸린 상태로 남아 다른 사람의 작업을 막습니다. 작업 후 COMMIT; 을 습관으로 만드세요.

SAVEPOINT — 부분 롤백

BEGIN;
INSERT INTO orders VALUES (2001, 1, '2026-08-05', 'PAID');

SAVEPOINT sp1;
INSERT INTO order_item VALUES (99, 2001, 999, 1, 1000);   -- 없는 상품 → 실패
ROLLBACK TO SAVEPOINT sp1;                                 -- 여기까지만 취소

INSERT INTO order_item VALUES (99, 2001, 10, 1, 49000);   -- 올바른 값으로 재시도
COMMIT;                                                    -- 주문 자체는 살아 있습니다

트랜잭션을 다룰 때의 세 가지 원칙

  • 짧게 유지하세요. 트랜잭션 안에서 외부 API를 호출하거나 사용자 입력을 기다리면 그동안 락이 유지되어 다른 작업이 줄줄이 막힙니다.
  • 순서를 통일하세요. A→B 순서로 잠그는 코드와 B→A 순서로 잠그는 코드가 만나면 데드락입니다(⚙️ t12).
  • 실패를 가정하세요. 커밋은 실패할 수 있습니다. 앱 코드에서 예외 처리와 재시도를 반드시 넣으세요(🔌 a11).
격리 수준·락·데드락 같은 동시성의 본론은 ⚙️ 설계 · 튜닝 탭 t10~t12 에서 다룹니다. 지금은 "COMMIT 전에는 확정이 아니다"만 확실히 해 두세요.
SECTION 18

SQL 실행 순서

SQL은 적은 순서대로 실행되지 않습니다. 이 순서를 알면 "WHERE에서 별칭을 왜 못 쓰지?" 같은 의문이 한 번에 풀립니다.

단계를 눌러 보세요
-- 우리가 쓰는 순서
SELECT   category, COUNT(*) AS 개수
FROM     product
WHERE    price >= 20000
GROUP BY category
HAVING   COUNT(*) >= 2
ORDER BY 개수 DESC
LIMIT    5;

-- DB 가 실행하는 순서
-- ① FROM     product          표를 읽고
-- ② WHERE    price >= 20000   행을 거르고
-- ③ GROUP BY category         묶고
-- ④ HAVING   COUNT(*) >= 2    그룹을 거르고
-- ⑤ SELECT   category, COUNT(*) AS 개수   ← 별칭이 여기서 생김
-- ⑥ ORDER BY 개수 DESC        정렬하고
-- ⑦ LIMIT    5                자른다

이 순서로 설명되는 것들

의문답
WHERE 에서 별칭을 못 쓰는 이유 별칭은 ⑤ SELECT 에서 생기는데 WHERE 는 ②라 아직 존재하지 않습니다
ORDER BY 에서는 별칭이 되는 이유 ⑥은 ⑤ 다음이라 이미 만들어져 있습니다
WHERE 에 집계 함수를 못 쓰는 이유 ②는 ③ GROUP BY 이전이라 그룹이 아직 없습니다
OFFSET 이 커도 안 빨라지는 이유 ⑦은 마지막이라 앞의 정렬·읽기를 전부 마친 뒤에야 자릅니다(⚙️ t09)
조인 조건을 WHERE 로 옮기면 결과가 바뀌는 이유 ①에서 붙일 때와 ②에서 거를 때의 시점이 다릅니다(q09 참고)
주의 — 이것은 논리적 순서입니다. 실제로 DB는 옵티마이저가 결과가 같음을 보장하는 선에서 순서를 마음대로 바꿉니다 (조건을 조인보다 먼저 밀어 넣는 등). 결과 해석은 논리 순서로, 성능 분석은 실행계획으로 하세요 → ⚙️ t07.
