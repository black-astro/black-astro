지금까지의 탭은 전부 OLTP였습니다 — 한 건을 정확히 넣고 한 건을 빨리 찾는 세계. 그런데 2026년 실무에서 우리를 부르는 일의 절반은 그 옆에 있습니다. OLAP 01

OLTP vs OLAP — 행 저장과 컬럼 저장

같은 SQL, 같은 데이터인데 한쪽은 40초, 한쪽은 0.3초입니다. 마법이 아니라 디스크에서 읽는 바이트 수가 100배 다르기 때문입니다.

컬럼 DB 가 빠른 첫 번째 이유는 알고리즘이 아니라 안 읽는 것입니다.

두 세계는 요구사항 자체가 다릅니다

같은 쿼리를 두 DB 에서 — 실제 숫자

🐘 PostgreSQL 18 — 1억 행

EXPLAIN (ANALYZE, BUFFERS)
SELECT country, count(*), sum(amount)
FROM   events
WHERE  ts >= '2026-01-01'
GROUP  BY country;

-- Parallel Seq Scan on events
--   Buffers: shared read=2,441,406      ← 약 19 GB
--   Workers Launched: 7
-- Execution Time: 38,512 ms             ← 38 초
병렬 워커 8개를 붙여도 19GB 를 읽는 일 자체는 사라지지 않습니다. 디스크 대역폭이 천장입니다.

📊 ClickHouse — 같은 1억 행

SELECT country, count(), sum(amount)
FROM   events
WHERE  ts >= '2026-01-01'
GROUP  BY country;

-- 3 rows in set. Elapsed: 0.221 sec.
-- Processed 100.00 million rows,
--   1.20 GB (452.49 million rows/s.)   ← 읽은 양
1.2GB 만 읽었습니다 — ts·country·amount 세 열뿐이고, 그마저 압축된 상태입니다.
"그럼 다 ClickHouse 쓰면 되는 거 아닌가요?" — 아닙니다. 같은 데이터로 SELECT * FROM events WHERE id = 91238 을 하면 PostgreSQL 은 0.2 ms, ClickHouse 는 수십~수백 ms 가 걸립니다. 컬럼 DB 는 한 행을 다시 조립하려면 모든 열 파일에서 같은 위치를 찾아 모아야 하기 때문입니다. 게다가 UPDATE·DELETE 가 사실상 없고(ClickHouse 의 ALTER … UPDATE 는 비동기 재작성 작업입니다), 외래키·트랜잭션·유니크 제약이 없습니다. 주문·결제를 여기에 넣으면 안 됩니다.

왜 이렇게까지 차이가 나나 — 세 가지 이유 🟡 중급

①
읽는 양 (I/O 삭감) 필요한 열 파일만 엽니다. 40개 열 중 3개면 읽는 양이 1/13 로 줄어듭니다.
▼
②
압축률 같은 열에는 같은 종류 값만 있습니다. 국가 코드 열은 값이 200가지뿐이라 사전 인코딩으로 10~50배, 정렬된 타임스탬프는 델타 인코딩으로 20배 이상 줄어듭니다. 행 저장에서는 int·문자열·날짜가 뒤섞여 있어 이렇게 못 줄입니다.
▼
③
벡터화 실행 (SIMD) 행 저장 엔진은 "행 하나 꺼내기 → 조건 검사 → 다음 행" 을 1억 번 반복합니다(볼케이노 모델). 컬럼 엔진은 같은 타입 값 8192개를 한 배열로 꺼내 CPU 의 SIMD 명령으로 한 번에 더합니다. 함수 호출 오버헤드가 1억 번에서 1만 2천 번으로 줄어듭니다.
PostgreSQL 도 이 방향으로 오고 있습니다. 18 버전 기준 columnar 계열 확장(Hydra·Citus 계열)과 pg_duckdb 처럼 PostgreSQL 안에서 DuckDB 엔진을 돌리는 확장이 나와 있습니다. 다만 성숙도·운영 편의를 감안하면 2026년 현재 실무의 기본 선택은 "OLTP 는 PostgreSQL, 분석은 별도 엔진" 입니다.

언제 분석 DB 를 따로 두나 🟡 중급

분석 DB 는 운영 DB 를 지키기 위해 두는 것이기도 합니다 — 무거운 집계가 OLTP 를 잡아먹지 않게.
가장 흔한 실수 두 가지.
① 운영 DB 에서 바로 집계 — 무거운 GROUP BY 가 버퍼 풀을 다 밀어내(🧬 z02) 정작 주문 조회가 느려집니다. 읽기 복제본으로 옮기는 것만으로도 대부분 해결됩니다(🐘 p15).
② 데이터 100만 행에 ClickHouse 도입 — 그 규모는 PostgreSQL 이 인덱스 하나로 이깁니다. 운영해야 할 시스템만 하나 늘어납니다.
OLAP 02

DuckDB — 분석용 SQLite

서버가 없습니다. pip install duckdb 한 줄이면 끝이고, 내 프로그램 안에서 돕니다. SQLite 가 OLTP 를 그렇게 만들었다면, DuckDB 는 OLAP 을 그렇게 만들었습니다.

"데이터를 DB 로 옮긴다"가 아니라 "DB 를 데이터가 있는 곳으로 가져간다" 입니다.

설치 — 정말 한 줄입니다

🐍 파이썬 · CLI

# 파이썬 (3.9+)
pip install duckdb

# CLI — 단일 실행 파일 하나, 의존성 없음
# macOS
brew install duckdb
# Windows (winget) / Linux
winget install DuckDB.cli
curl -fsSL https://install.duckdb.org | sh

duckdb              # 메모리 DB 로 시작
duckdb mydata.db    # 파일 DB 로 시작
# .help  .tables  .schema  .quit   ← SQLite 와 닮은 점 명령

🟨 Node · 그 밖

# Node.js (Node 24 LTS 기준)
npm install @duckdb/node-api

# Java / Go / Rust / R / C++ 바인딩 모두 있습니다
# JDBC:  org.duckdb:duckdb_jdbc
# 브라우저(WASM):  @duckdb/duckdb-wasm
#   → 서버 없이 브라우저에서 Parquet 분석이 됩니다
DuckDB 는 1.x 안정 버전대입니다. 파일 포맷 하위 호환이 보장되므로 버전을 올려도 예전 .db 를 그대로 읽습니다.

파일을 그대로 쿼리합니다 — 적재 단계가 없습니다

-- ① CSV 를 테이블처럼 (헤더·타입 자동 추론)
SELECT country, count(*) FROM 'sales_2026.csv' GROUP BY 1;

-- ② Parquet — 폴더 전체를 와일드카드로
SELECT date_trunc('month', ts) AS m, sum(amount)
FROM   read_parquet('s3://bucket/events/year=2026/**/*.parquet')
GROUP  BY 1 ORDER BY 1;

-- ③ JSON (줄바꿈 구분 JSONL 도 됩니다)
SELECT * FROM read_json_auto('logs.jsonl') WHERE level = 'ERROR';

-- ④ 여러 형식을 한 쿼리에서 조인 — 이게 DuckDB 의 진짜 매력입니다
SELECT u.name, sum(e.amount)
FROM   read_parquet('events/*.parquet') e
JOIN   'users.csv' u ON u.id = e.user_id      -- CSV 와 Parquet 를 그냥 조인
GROUP  BY 1 ORDER BY 2 DESC LIMIT 10;

-- ⑤ 원격 PostgreSQL 을 붙여 같이 조회 (확장)
INSTALL postgres; LOAD postgres;
ATTACH 'host=db.internal dbname=shop user=ro' AS pg (TYPE postgres, READ_ONLY);
SELECT * FROM pg.public.orders LIMIT 5;
파일 경로가 곧 테이블 이름입니다. FROM 'x.parquet' 처럼 따옴표 친 경로를 FROM 절에 그대로 쓸 수 있고, read_parquet·read_csv·read_json_auto 로 옵션을 줄 수도 있습니다. s3://·https:// 도 됩니다 — 필요한 행 그룹만 범위 요청(HTTP Range)으로 내려받습니다. 8GB 파일에서 100MB 만 받아 오는 일이 실제로 일어납니다.

메모리 모드와 파일 모드

🐍 파이썬 — 세 가지 쓰는 법

# ① 메모리 DB — 끝나면 사라짐 (가장 흔함)
con = duckdb.connect()          # 또는 ':memory:'

# ② 파일 DB — 테이블·뷰가 남습니다

# ③ 모듈 함수로 바로 (연결 객체 없이)

con.sql("SET memory_limit = '8GB'")

메모리보다 큰 데이터도 처리됩니다. 정렬·해시 조인·집계 모두 디스크 스필을 지원합니다. 8GB 램에서 100GB Parquet 집계가 (느리지만) 끝납니다.

분석에 쓰기 좋은 문법들 🟡 중급

-- 열 이름을 패턴으로 고르기
SELECT COLUMNS('amount_.*') FROM sales;          -- amount_ 로 시작하는 모든 열
SELECT max(COLUMNS(*)) FROM sales;               -- 모든 열의 최댓값을 한 번에

-- 일부 열만 빼기 / 바꾸기
SELECT * EXCLUDE (password_hash, ssn) FROM users;
SELECT * REPLACE (upper(country) AS country) FROM sales;

-- FROM 을 먼저 써도 됩니다 (자동완성이 편해집니다)
FROM sales SELECT country, sum(amount) GROUP BY 1;
FROM sales;                                       -- SELECT * 생략 가능

-- GROUP BY ALL / ORDER BY ALL — 열 번호 세는 일을 없앱니다
SELECT country, product, sum(amount) FROM sales GROUP BY ALL;

-- 리스트·구조체·중첩 JSON 을 그대로 다룹니다
SELECT payload.user.id, len(payload.items) FROM read_json_auto('ev.json');

-- 결과를 바로 파일로 (형식은 확장자로 판단)
COPY (SELECT * FROM sales WHERE year = 2026) TO 'out.parquet';
COPY sales TO 'part' (FORMAT parquet, PARTITION_BY (country));

언제 DuckDB 하나로 충분한가

✓ DuckDB 로 끝나는 상황
· 데이터가 파일(들)로 있고 수 GB ~ 수백 GB
· 분석하는 사람이 한 명 또는 배치 잡 하나
· 결과만 필요하고 데이터는 원본에 그대로 두고 싶다
· 노트북·CI·Lambda 안에서 돌려야 한다
· 파이썬 파이프라인 중간에 SQL 이 편한 구간이 있다
· "일단 이 CSV 좀 봐 줘" 가 하루에 세 번 온다
✗ 여기서부터는 ClickHouse 쪽
· 여러 사람이 동시에 대시보드로 조회한다
· 데이터가 실시간으로 계속 들어온다 (초당 수만 행)
· 수십 TB 이상이고 항상 떠 있어야 한다
· 권한·감사·백업 같은 운영 체계가 필요하다
· 사전 집계(머티리얼라이즈드 뷰)로 응답을 지켜야 한다
DuckDB 는 동시 쓰기에 약합니다 — SQLite 와 같은 이유입니다(✒️ s08). 한 파일 DB 에 쓰기 프로세스는 하나만 붙을 수 있습니다. 웹 서버 여러 대가 같은 .duckdb 파일을 붙잡는 구조는 만들지 마세요. 읽기 전용이면 여러 프로세스가 동시에 열 수 있습니다 (duckdb.connect(path, read_only=True)).
실무 팁 — "임시 분석"의 표준 도구가 됐습니다. 운영 DB 에서 무거운 집계를 돌리는 대신 ① COPY … TO 's3://…/dump.parquet' 로 하루치를 떨구고 ② 노트북에서 DuckDB 로 마음껏 파 보고 ③ 결론이 나면 그때 정식 파이프라인(v12)을 만듭니다. 운영 DB 를 한 번도 건드리지 않고 분석이 끝납니다.
OLAP 03

Parquet · 컬럼 포맷의 속

Parquet 는 "압축된 CSV" 가 아닙니다. 파일 안에 통계와 색인이 들어 있는 작은 데이터베이스에 가깝습니다. 구조를 알면 왜 WHERE 하나로 파일의 90%를 건너뛰는지 이해됩니다.

건너뛰기의 정체는 인덱스가 아니라 min/max 통계입니다 — 그래서 정렬해서 저장하면 극적으로 잘 듭니다.

구조를 용어로 정리하면

단위설명실무 감각
파일하나의 .parquet. 맨 끝에 푸터(메타데이터)가 붙습니다128MB ~ 1GB 가 적당
행 그룹
(Row Group)		행을 수십만 개씩 묶은 덩어리. 건너뛰기의 최소 단위기본 100만 행 · 압축 후 128MB 목표
컬럼 청크
(Column Chunk)		한 행 그룹 안에서 한 열의 값들만 모은 연속 영역여기 단위로 읽습니다
페이지
(Page)		청크를 다시 나눈 압축·인코딩 단위기본 1MB
푸터스키마 + 모든 청크의 오프셋 + 행 그룹별 min·max·null 수원격 파일도 푸터만 먼저 받습니다
왜 통계로 건너뛸 수 있나 — 논리는 단순합니다. 조건이 ts >= '2026-03-01' 인데 어떤 행 그룹의 ts 최댓값이 2026-02-28 이라면, 그 안에 조건을 만족하는 행은 있을 수가 없습니다. 그러니 읽지 않습니다. 이걸 프레디킷 푸시다운(predicate pushdown)·존 맵(zone map) 이라고 부릅니다. ClickHouse 의 스킵 인덱스(v05), PostgreSQL 의 BRIN 인덱스(🐘 p08)가 전부 같은 아이디어입니다.
정렬하지 않고 저장하면 이 최적화가 완전히 죽습니다. 타임스탬프가 뒤섞여 있으면 모든 행 그룹의 min·max 가 "전체 범위" 가 되어 어느 하나도 건너뛸 수 없습니다. COPY (SELECT * FROM t ORDER BY ts) TO 'out.parquet' — 쓰기 전에 필터로 자주 쓰는 열로 정렬하는 것, 이것 하나가 조회 속도를 몇 배 바꿉니다.

코덱보다 인코딩이 먼저 일합니다. Parquet 는 압축 전에 딕셔너리 인코딩(반복 문자열을 번호로), RLE(같은 값 반복을 "값×개수"로), 델타 인코딩(정렬된 정수의 차이만)을 적용합니다. 국가 코드 열이 100배 줄어드는 건 zstd 덕이 아니라 딕셔너리 덕입니다. 그래서 카디널리티가 낮은 열을 문자열로 둬도 크게 손해 보지 않습니다.

파티셔닝된 폴더 — 파일 이름이 곧 WHERE 절

WHERE year = 2026 AND country = 'KR' 이면

     (FORMAT parquet, PARTITION_BY (year, month, country),
      COMPRESSION zstd, ROW_GROUP_SIZE 1000000);

-- 이렇게 읽습니다 — 폴더 이름이 열로 살아납니다
SELECT country, sum(amount)
FROM   read_parquet('s3://warehouse/events/**/*.parquet', hive_partitioning = true)
WHERE  year = 2026 AND month = 3          -- ← 폴더 단위로 잘라 냅니다
GROUP  BY 1;

       sum(total_uncompressed_size) AS raw,

Arrow 와 Parquet 는 무슨 관계인가 🟡 중급

Parquet — 디스크 포맷

목적   : 저장 · 전송
최적화 : 크기 (압축·인코딩)
읽으려면 → 압축을 풀고 디코딩해야 함
수명   : 몇 년 (파일로 보관)

Arrow — 메모리 포맷

목적   : 처리 · 프로세스 간 공유
최적화 : 접근 속도 (압축 안 함, 고정 폭)
그대로  → CPU 가 바로 SIMD 로 계산
수명   : 밀리초 (메모리에만)
Parquet 를 읽으면 대개 Arrow 가 됩니다. DuckDB · Polars · pandas 2.x · Spark 가 전부 Arrow 를 메모리 표현으로 쓰기 때문에, 같은 프로세스 안에서는 서로 복사 없이 데이터를 넘깁니다. v02 에서 duckdb.sql("SELECT * FROM pldf") 가 공짜였던 이유가 이것입니다. "Parquet = 디스크의 Arrow, Arrow = 메모리의 Parquet" 정도로 외워 두면 실무에서는 충분합니다.

첫 테이블 — MergeTree

CREATE TABLE events
(
    ts          DateTime,
    user_id     UInt64,
    country     LowCardinality(String),   -- 값 종류가 적은 문자열 전용 타입
    path        String,
    status      UInt16,
    duration_ms UInt32,
    amount      Decimal(18, 2)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)                 -- 파티션: 보관·삭제의 단위
ORDER BY (country, ts, user_id)            -- ★ 정렬 키 = 사실상의 인덱스
SETTINGS index_granularity = 8192;         -- 그래뉼 하나 = 8192 행
정렬 키를 잘못 잡으면 모든 그래뉼을 읽습니다 — ClickHouse 튜닝의 90%가 ORDER BY 입니다.

ORDER BY 를 정하는 법 — 가장 중요한 결정

규칙이유
① 항상 걸리는 필터를 맨 앞에 모든 쿼리에 tenant_id 가 들어간다면 ORDER BY (tenant_id, …). 앞쪽 열만 건너뛰기가 잘 듣습니다
② 카디널리티 낮은 → 높은 순 country(200) → date → user_id(1억) 순. 반대로 두면 정렬 키가 사실상 무작위가 되어 압축률도 같이 떨어집니다
③ 3~4개를 넘기지 말 것 뒤쪽 열은 어차피 건너뛰기에 거의 기여하지 못하고, 삽입 시 정렬 비용만 늘어납니다
④ 기본키는 정렬 키의 접두사 PRIMARY KEY 를 따로 쓰면 정렬 키보다 짧게만 가능합니다. 유일성 보장이 아닙니다
⑤ 나중에 못 바꿉니다 정렬 키 변경 = 테이블 재작성. 설계 때 쿼리 목록을 먼저 적으세요
PARTITION BY 와 ORDER BY 를 헷갈리면 큰일 납니다.
· PARTITION BY 는 물리적으로 폴더를 나누는 것입니다. 목적은 통째로 지우기(DROP PARTITION)와 TTL 입니다. 보통 toYYYYMM(ts) — 월 단위가 정답이고, 일 단위로 쪼개면 파트가 폭증합니다.
· ORDER BY 가 성능을 만듭니다. 파티션은 성능 도구가 아닙니다.
파티션 개수가 수천 개를 넘기면 병합 스레드가 못 따라가고 TOO_MANY_PARTS 로 INSERT 가 막힙니다.

ClickHouse 실전 — 사전 집계 · TTL · 조인의 한계

원본 1억 행을 매번 훑는 대신 들어올 때 미리 접어 두면 대시보드가 10ms 에 뜹니다. 머티리얼라이즈드 뷰가 ClickHouse 에서는 트리거에 가깝다는 점만 이해하면 됩니다.

PostgreSQL 의 MATERIALIZED VIEW 처럼 새로고침(REFRESH)하는 스냅숏이 아닙니다 — 들어올 때마다 즉시 갱신됩니다.

AggregatingMergeTree + 머티리얼라이즈드 뷰

-- ① 결과를 담을 테이블 — 집계 "상태(State)" 를 저장합니다
CREATE TABLE events_hourly
(
    hour        DateTime,
    country     LowCardinality(String),
    cnt         AggregateFunction(count),                 -- 최종 값이 아니라 중간 상태
    revenue     AggregateFunction(sum, Decimal(18,2)),
    uniq_users  AggregateFunction(uniq, UInt64),          -- HLL 스케치가 통째로 들어갑니다
    p95_ms      AggregateFunction(quantile(0.95), UInt32)
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(hour)
ORDER BY (country, hour);

-- ② 뷰 — 원본에 INSERT 될 때마다 이 SELECT 가 그 블록에 대해 실행됩니다
CREATE MATERIALIZED VIEW events_hourly_mv TO events_hourly AS
SELECT toStartOfHour(ts)              AS hour,
       country,
       countState()                   AS cnt,            -- -State 접미사
       sumState(amount)               AS revenue,
       uniqState(user_id)             AS uniq_users,
       quantileState(0.95)(duration_ms) AS p95_ms
FROM   events
GROUP  BY hour, country;

-- ③ 조회 — -Merge 로 상태를 합쳐 최종 값을 만듭니다
SELECT country,
       toDate(hour)                   AS d,
       countMerge(cnt)                AS cnt,
       sumMerge(revenue)              AS revenue,
       uniqMerge(uniq_users)          AS dau,            -- ★ 일자별 유니크가 정확히 나옵니다
       quantileMerge(0.95)(p95_ms)    AS p95
FROM   events_hourly
WHERE  hour >= '2026-03-01'
GROUP  BY country, d
ORDER  BY d;
왜 sum 이 아니라 sumState 인가. 합계는 시간별 합을 다시 더하면 되지만, 유니크 사용자 수는 그렇게 안 됩니다 — 시간별 DAU 를 24개 더한다고 하루 DAU 가 되지 않습니다(같은 사람이 여러 시간에 옵니다). 그래서 ClickHouse 는 최종 숫자가 아니라 HyperLogLog 스케치·백분위 스케치 같은 "중간 상태" 를 통째로 저장합니다. 나중에 어떤 단위로 묶든 -Merge 로 정확히 합쳐집니다. 이게 ClickHouse 사전 집계의 핵심 아이디어이고, 다른 DB 에서 흉내 내기 가장 어려운 부분입니다.

AggregatingMergeTree집계 상태를 병합합니다 (위 예제)유니크·백분위가 필요한 사전 집계
CollapsingMergeTreesign 열 +1/−1 로 취소 처리상태가 바뀌는 엔티티 추적
ReplicatedMergeTree위 전부에 Replicated 접두사 → 다중 복제운영 클러스터의 기본
ReplacingMergeTree 는 "언젠가" 중복을 없앱니다. 병합은 백그라운드에서 임의의 시점에 일어나므로, 방금 넣은 중복이 지금 조회하면 그대로 보입니다. 확실히 하려면 조회 때 FINAL 을 붙이거나(느립니다) argMax(col, version) + GROUP BY key 로 직접 최신 행을 고릅니다. 최신 버전에는 SELECT … FINAL 을 자동으로 붙이는 final = 1 세션 설정도 있지만, 비용은 똑같습니다.

TTL — 오래된 데이터를 알아서 지우기

-- ① 행 단위 삭제 — 90일 지난 이벤트는 사라집니다
ALTER TABLE events MODIFY TTL ts + INTERVAL 90 DAY;

-- ② 계층화 — 30일 지나면 느린 디스크로, 180일 지나면 삭제
ALTER TABLE events MODIFY TTL
    ts + INTERVAL 30  DAY TO VOLUME 'cold',
    ts + INTERVAL 180 DAY DELETE;

-- ③ 열 단위 TTL — 원문은 지우고 집계에 필요한 열만 남깁니다
ALTER TABLE events MODIFY COLUMN user_agent String TTL ts + INTERVAL 14 DAY;

-- ④ 롤업 TTL — 오래된 데이터를 자동으로 접습니다 (다운샘플링)
CREATE TABLE metrics (...)
ENGINE = MergeTree ORDER BY (name, ts)
TTL ts + INTERVAL 30 DAY GROUP BY name, toStartOfHour(ts)
    SET value = avg(value);        -- 30일 지나면 시간 단위 평균만 남김
TTL 은 병합할 때 적용됩니다 — 즉시가 아닙니다. 당장 확인하려면 OPTIMIZE TABLE events FINAL 을 부르거나 merge_with_ttl_timeout 설정을 낮춥니다. 보관 정책을 SQL 한 줄로 선언할 수 있다는 건 큰 장점입니다 — PostgreSQL 이라면 파티션 드롭 배치를 직접 짜야 합니다(🧬 z13).

스킵 인덱스 — 정렬 키가 아닌 열로 거를 때 🟡 중급

-- 정렬 키에 없는 열로 필터하면 전체 그래뉼을 다 읽습니다. 그때 씁니다.
ALTER TABLE events ADD INDEX idx_status status TYPE minmax GRANULARITY 4;
ALTER TABLE events ADD INDEX idx_path   path   TYPE bloom_filter(0.01) GRANULARITY 2;
ALTER TABLE events ADD INDEX idx_tok    path   TYPE tokenbf_v1(32768, 3, 0) GRANULARITY 2;

-- 기존 데이터에도 적용하려면 한 번 물질화해야 합니다
ALTER TABLE events MATERIALIZE INDEX idx_status;

-- 잘 듣는지 확인
EXPLAIN indexes = 1 SELECT count() FROM events WHERE status = 500;
--   Skip: idx_status  Granules: 41/1250000     ← 이 비율을 봅니다
타입맞는 데이터거는 조건
minmax값이 정렬 키와 상관관계가 있는 열 (증가하는 id 등)= · 범위
set(N)그래뉼 안 값 종류가 N 개 이하= · IN
bloom_filter카디널리티가 높은 열 (경로·ID)= · IN. 범위는 안 됨
tokenbf_v1문자열 안 단어 검색hasToken() · LIKE '%tok%'

스킵 인덱스는 B-Tree 가 아닙니다. "이 그래뉼에 값이 있을 수도 있다"만 알려 줍니다(거짓 양성 허용). 값이 그래뉼 전체에 골고루 흩어져 있으면 어느 그래뉼도 못 건너뛰고 인덱스 유지 비용만 늘어납니다. 반드시 EXPLAIN indexes = 1 로 그래뉼 감소를 확인하고 남기세요.

OLAP 06

시계열 DB — 시간이 축인 데이터

메트릭·센서·주가는 "시간 + 값" 이 전부입니다. 이 모양에만 특화하면 PostgreSQL 을 그대로 쓰면서도 10배 빠르고 20배 작게 만들 수 있습니다 — TimescaleDB 가 그 길입니다.

시계열의 핵심 최적화는 "시간으로 잘라 두면 지우는 것도 읽는 것도 통째로 된다" 입니다.

TimescaleDB — PostgreSQL 확장으로 시작하기

-- 도커:  docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=pw timescale/timescaledb-ha:pg17
CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE TABLE metrics (
    ts       TIMESTAMPTZ      NOT NULL,
    device   TEXT             NOT NULL,
    metric   TEXT             NOT NULL,
    value    DOUBLE PRECISION NOT NULL,
    tags     JSONB
);

-- ① 하이퍼테이블로 승격 — 이 한 줄이 전부입니다
SELECT create_hypertable('metrics', by_range('ts', INTERVAL '7 days'));

-- ② 조회는 완전히 평범한 SQL 입니다 (여기가 큰 장점)
SELECT device, avg(value)
FROM   metrics
WHERE  ts >= now() - INTERVAL '3 hours' AND metric = 'cpu'
GROUP  BY device;

-- ③ 시계열 전용 함수들
SELECT time_bucket('5 minutes', ts) AS bucket,
       device,
       avg(value)                   AS avg_v,
       max(value)                   AS max_v,
       last(value, ts)              AS latest      -- 버킷 안 마지막 값
FROM   metrics
WHERE  ts >= now() - INTERVAL '1 day'
GROUP  BY bucket, device
ORDER  BY bucket;

-- 빈 구간 채우기 + 보간 — 그래프 그릴 때 필수입니다
SELECT time_bucket_gapfill('1 minute', ts) AS b,
       locf(avg(value))                    AS v    -- 마지막 값 유지
FROM   metrics
WHERE  ts >= now() - INTERVAL '1 hour' AND ts < now()
GROUP  BY b;

연속 집계 · 압축 · 보관 — 정책 세 줄

-- ① 연속 집계 (continuous aggregate) — 증분으로 갱신되는 머티리얼라이즈드 뷰
CREATE MATERIALIZED VIEW metrics_hourly
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 hour', ts) AS bucket,
       device, metric,
       avg(value) AS avg_v, max(value) AS max_v, count(*) AS n
FROM   metrics
GROUP  BY bucket, device, metric;

SELECT add_continuous_aggregate_policy('metrics_hourly',
    start_offset => INTERVAL '3 days',
    end_offset   => INTERVAL '1 hour',      -- 최근 1시간은 아직 안 굳힘
    schedule_interval => INTERVAL '30 minutes');

-- ② 압축 정책 — 7일 지난 청크를 컬럼 형태로 압축
ALTER TABLE metrics SET (timescaledb.compress,
    timescaledb.compress_segmentby = 'device, metric',
    timescaledb.compress_orderby   = 'ts DESC');
SELECT add_compression_policy('metrics', INTERVAL '7 days');

-- ③ 보관 정책 — 1년 지난 청크는 통째로 버림
SELECT add_retention_policy('metrics', INTERVAL '365 days');

-- 확인
SELECT * FROM timescaledb_information.chunks WHERE hypertable_name = 'metrics';
SELECT * FROM hypertable_compression_stats('metrics');
연속 집계의 진짜 강점은 "실시간 합성" 입니다. 미리 굳혀 둔 시간(end_offset 이전)은 요약 테이블에서 읽고, 아직 안 굳은 최근 구간은 원본에서 즉석 집계해 합쳐 줍니다. 그래서 뷰를 조회해도 방금 들어온 데이터가 빠지지 않습니다 — ClickHouse 의 MV(v05)나 PostgreSQL 의 REFRESH MATERIALIZED VIEW 에는 없는 성질입니다.

벡터 검색의 원리 — 뜻으로 찾기

LIKE '%환불%' 는 "돈 돌려받고 싶어요" 를 못 찾습니다. 글자가 아니라 뜻이 가까운 것을 찾으려면 문장을 숫자 목록으로 바꿔 거리를 재야 합니다.

임베딩 — 문장을 좌표로 바꾸는 일

# 임베딩 모델은 "문장 → 고정 길이 실수 배열" 함수입니다
from openai import OpenAI
client = OpenAI()

r = client.embeddings.create(
        model="text-embedding-3-small",     # 1536 차원
        input="주문한 물건을 환불하고 싶어요")
vec = r.data[0].embedding
len(vec)     # 1536
vec[:5]      # [-0.0121, 0.0338, -0.0074, 0.0512, -0.0009]

  SELECT id, embedding
  FROM   doc_chunk
  ORDER  BY binary_quantize(embedding)::bit(1536) <~> binary_quantize($1::vector)
  LIMIT  200

FROM   cand

하이브리드 검색 — 키워드 + 벡터

벡터 검색만 켜면 "ERR_CONN_4021 오류" 같은 정확한 토큰을 놓칩니다. 키워드 검색만 켜면 뜻이 같은 다른 표현을 놓칩니다. 둘 다 켜는 것이 정답입니다.

각자 잘하는 것이 정확히 다릅니다

키워드(BM25 · tsvector)가 이기는 질의
"ERR_CONN_4021"        정확한 오류 코드
"SKU-88213"            제품 번호 · 주문 번호
"김하늘 대리"            고유명사 · 사람 이름
"pg_stat_statements"   함수 · 설정 이름
"2026년 3분기"          숫자가 든 표현

→ 임베딩은 이런 토큰을 뭉개 버립니다.
  숫자 4021 과 4022 의 벡터는 거의 같습니다.
벡터가 이기는 질의
"돈 돌려받고 싶어요"     → 환불 규정 문서
"화면이 하얗게 떠요"      → 렌더링 오류 가이드
"휴가 언제까지 쓰나요"     → 연차 사용 촉진 안내
"이거 왜 이렇게 느려요"    → 성능 문제 진단 문서

→ 겹치는 글자가 없어 키워드 검색은
  결과가 0건입니다.
BM25 는 "TF-IDF 의 개량판" 이라고 보면 됩니다. ① 질의어가 문서에 몇 번 나오는가(TF), ② 그 단어가 전체 문서에서 얼마나 희귀한가(IDF), ③ 문서 길이 보정(긴 문서가 무조건 유리해지지 않게) — 이 셋을 합친 점수입니다. Elasticsearch·OpenSearch·Lucene 의 기본 랭킹이고, PostgreSQL 의 ts_rank_cd 는 BM25 그 자체는 아니지만 같은 계열의 점수입니다. 정확한 BM25 가 필요하면 PostgreSQL 에도 pg_search(ParadeDB) 같은 확장이 있습니다.
RRF 의 미덕은 정확도가 아니라 튜닝할 것이 없다는 점입니다 — 그냥 잘 됩니다.

PostgreSQL 한 쿼리로 하이브리드 검색

-- 준비: 전문 검색 열과 인덱스 (한국어는 🐘 p09 참고)
ALTER TABLE doc_chunk
  ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', body)) STORED;
CREATE INDEX ON doc_chunk USING gin (tsv);
CREATE INDEX ON doc_chunk USING hnsw (embedding vector_cosine_ops);

-- 하이브리드 검색 (RRF)
WITH params AS (
  SELECT $1::text   AS q,          -- 질문 원문
         $2::vector AS qv,         -- 질문 임베딩
         60         AS k,
         50         AS n           -- 각 목록에서 가져올 후보 수
),
kw AS (                            -- ① 키워드 후보
  SELECT c.id,
         row_number() OVER (ORDER BY ts_rank_cd(c.tsv, plainto_tsquery('simple', p.q)) DESC) AS rnk
  FROM   doc_chunk c, params p
  WHERE  c.tsv @@ plainto_tsquery('simple', p.q)
  LIMIT  (SELECT n FROM params)
),
vec AS (                           -- ② 벡터 후보
  SELECT c.id,
         row_number() OVER (ORDER BY c.embedding <=> p.qv) AS rnk
  FROM   doc_chunk c, params p
  ORDER  BY c.embedding <=> p.qv
  LIMIT  (SELECT n FROM params)
)
SELECT d.id, d.body,
       coalesce(1.0 / (p.k + kw.rnk),  0) +
       coalesce(1.0 / (p.k + vec.rnk), 0) AS rrf_score
FROM   params p
CROSS  JOIN LATERAL (
         SELECT id FROM kw UNION SELECT id FROM vec
       ) u
JOIN   doc_chunk d ON d.id = u.id
LEFT   JOIN kw  ON kw.id  = u.id
LEFT   JOIN vec ON vec.id = u.id
ORDER  BY rrf_score DESC
LIMIT  10;
후보 수(n)를 최종 개수(10)보다 훨씬 크게 잡는 것이 핵심입니다. 각 목록에서 10개씩만 뽑아 합치면 겹치는 것이 없어 융합의 의미가 없습니다. 각 50~100개를 뽑아 합치고 상위 10개를 취하세요. 비용은 거의 늘지 않습니다 — 어차피 인덱스가 상위 후보를 뽑는 비용이 지배적입니다.

# 구조 기반 + 겹침(overlap) — 실무에서 가장 자주 쓰는 조합
import hashlib, re, tiktoken

enc = tiktoken.get_encoding("cl100k_base")
TARGET, OVERLAP = 450, 80        # 토큰 기준

def chunk_markdown(md: str, title: str):
    sections, path = [], []
    for block in re.split(r"\n(?=#{1,4}\s)", md):        # 헤딩 앞에서 자름
        m = re.match(r"(#{1,4})\s+(.*)", block)
        if m:
            lv, head = len(m.group(1)), m.group(2).strip()
            path = path[:lv-1] + [head]
        body = block.strip()
        if not body:
            continue
        toks = enc.encode(body)
        # 너무 길면 겹치게 다시 자름 — 문장이 경계에서 끊기는 것을 완충합니다
        for i in range(0, len(toks), TARGET - OVERLAP):
            piece = enc.decode(toks[i:i + TARGET])
            hp = " > ".join([title] + path)
            sections.append({
                "body":        f"[{hp}]\n{piece}",       # ★ 헤딩 경로를 본문에 넣습니다
                "heading_path": hp,
                "token_count": len(enc.encode(piece)),
                "content_sha": hashlib.sha256(piece.encode()).hexdigest(),
            })
    return sections
헤딩 경로를 청크 본문 앞에 붙이는 것은 비용 대비 효과가 가장 큰 한 줄입니다. "7일 이내에 신청해야 합니다" 라는 청크만 있으면 무엇의 7일인지 알 수 없지만, [요금 정책 > 환불 > 신청 기간] 이 앞에 붙으면 임베딩에도 그 맥락이 들어가고 LLM 도 헷갈리지 않습니다. 청크 길이는 300~600 토큰, 겹침은 10~20% 에서 시작해 조정하세요.

def upsert_document(cur, src, ext_id, title, url, team_id, text):
    sha = hashlib.sha256(text.encode()).hexdigest()

    # ① 원문이 그대로면 아무것도 하지 않습니다 (임베딩 API 호출 0)
    cur.execute("""SELECT id, body_sha256 FROM doc
                   WHERE source=%s AND external_id=%s""", (src, ext_id))
    row = cur.fetchone()
    if row and row[1] == sha:
        return "unchanged"

    # ② 문서 upsert
    cur.execute("""
        INSERT INTO doc (source, external_id, title, url, team_id, body, body_sha256)
        VALUES (%s,%s,%s,%s,%s,%s,%s)
        ON CONFLICT (source, external_id) DO UPDATE
          SET title=EXCLUDED.title, body=EXCLUDED.body,
              body_sha256=EXCLUDED.body_sha256, updated_at=now()
        RETURNING id""", (src, ext_id, title, url, team_id, text, sha))
    doc_id = cur.fetchone()[0]

    # ③ 새 청크를 만들고, 내용이 같은 청크는 임베딩을 재사용합니다
    chunks = chunk_markdown(text, title)
    shas   = [c["content_sha"] for c in chunks]
    cur.execute("""SELECT content_sha, embedding FROM doc_chunk
                   WHERE doc_id=%s AND content_sha = ANY(%s)""", (doc_id, shas))
    cached = dict(cur.fetchall())          # ← 문단 하나만 고친 문서는 여기서 90% 절약됩니다

    todo = [c for c in chunks if c["content_sha"] not in cached]
    vecs = embed_batch([c["body"] for c in todo])   # 배치로 한 번에

    # ④ 트랜잭션 안에서 교체 — 검색이 빈 순간을 만들지 않습니다
    cur.execute("DELETE FROM doc_chunk WHERE doc_id=%s", (doc_id,))
    insert_chunks(cur, doc_id, chunks, cached, todo, vecs)
    return "reindexed"
"매일 밤 전부 다시 색인" 은 세 가지를 망칩니다. ① 돈 — 문서 10만 개면 임베딩 API 비용이 매일 나갑니다. ② 시간 — 몇 시간씩 걸려 그날의 변경이 반영되지 않습니다. ③ 검색 공백 — DELETE 후 INSERT 사이에 검색하면 결과가 비어 버립니다. 해시 비교 + 문서 단위 트랜잭션만 지키면 셋 다 사라집니다.

def recall_at_k(found, gold, k):
    # 정답 중 상위 k 안에 들어온 비율
    return len(set(found[:k]) & set(gold)) / len(gold)

def mrr(found, gold):
    # 첫 정답이 몇 위에 나왔는가 (1위=1.0, 5위=0.2)
    for i, d in enumerate(found, 1):
        if d in gold:
            return 1 / i
    return 0.0

def ndcg_at_k(found, gold, k):
    # 순위 가중 — 위쪽 정답에 더 큰 점수
    import math
    dcg = sum(1 / math.log2(i + 1)
              for i, d in enumerate(found[:k], 1) if d in gold)
    idl = sum(1 / math.log2(i + 1)
              for i in range(1, min(len(gold), k) + 1))
    return dcg / idl if idl else 0.0
무엇을 보나 — 목적에 따라 다릅니다. LLM 에 상위 5개를 넣는다면 recall@5 가 가장 중요합니다 (정답이 그 안에 있기만 하면 LLM 이 찾아냅니다). 사람이 검색 결과를 직접 보는 화면이라면 MRR·NDCG 가 중요합니다(1위에 있어야 합니다). 변경을 하나 할 때마다 이 숫자를 다시 재세요 — "체감상 좋아진 것 같다" 로는 청킹 파라미터 하나 못 정합니다.

-- v11 의 doc / doc_chunk 스키마를 그대로 씁니다. 권한만 덧붙입니다.
CREATE TABLE doc_acl (
    doc_id   BIGINT NOT NULL REFERENCES doc(id) ON DELETE CASCADE,
    group_id INT    NOT NULL,
    PRIMARY KEY (doc_id, group_id)
);
CREATE INDEX ON doc_acl (group_id);

-- 인덱스 3종
CREATE INDEX ON doc_chunk USING hnsw (embedding vector_cosine_ops)
       WITH (m = 16, ef_construction = 128);
CREATE INDEX ON doc_chunk USING gin (tsv);
CREATE INDEX ON doc_chunk (doc_id);

-- 실제 규모 (사내 위키 + 노션 + PDF 매뉴얼)
--   doc          42,000 건       텍스트 합계 1.9 GB
--   doc_chunk   318,000 건       평균 420 토큰
--   embedding   318,000 × 1536 × 4B = 1.9 GB
--   HNSW 인덱스                        2.7 GB   ← shared_buffers 를 8GB 로
--   GIN 인덱스                         0.4 GB
-- 검색 쿼리 (v09 의 RRF + 권한 필터 + 문서 단위 중복 제거)
WITH p AS (SELECT $1::text AS q, $2::vector AS qv, $3::int[] AS groups, 60 AS k),
allowed AS (
  SELECT DISTINCT a.doc_id FROM doc_acl a, p WHERE a.group_id = ANY(p.groups)
),
kw AS (
  SELECT c.id, row_number() OVER (
           ORDER BY ts_rank_cd(c.tsv, plainto_tsquery('simple', p.q)) DESC) AS rnk
  FROM   doc_chunk c JOIN allowed al ON al.doc_id = c.doc_id, p
  WHERE  c.tsv @@ plainto_tsquery('simple', p.q)
  LIMIT  60
),
vec AS (
  SELECT c.id, row_number() OVER (ORDER BY c.embedding <=> p.qv) AS rnk
  FROM   doc_chunk c JOIN allowed al ON al.doc_id = c.doc_id, p
  ORDER  BY c.embedding <=> p.qv
  LIMIT  60
),
fused AS (
  SELECT u.id,
         coalesce(1.0/(60 + kw.rnk), 0) + coalesce(1.0/(60 + vec.rnk), 0) AS score
  FROM   (SELECT id FROM kw UNION SELECT id FROM vec) u
  LEFT   JOIN kw ON kw.id = u.id
  LEFT   JOIN vec ON vec.id = u.id
)
SELECT DISTINCT ON (d.id)                      -- 문서당 가장 좋은 청크 하나만
       d.id AS doc_id, d.title, d.url, c.body, c.heading_path, f.score
FROM   fused f
JOIN   doc_chunk c ON c.id = f.id
JOIN   doc d       ON d.id = c.doc_id
ORDER  BY d.id, f.score DESC
LIMIT  20;
DISTINCT ON 으로 문서 단위 중복을 없애는 것이 체감 품질을 크게 올립니다(🐘 p05). 긴 문서 하나가 상위 10개를 전부 자기 청크로 채워 버리는 일이 흔한데, 사용자 입장에서는 "결과가 하나뿐" 으로 보입니다. 권한 필터를 CTE 로 먼저 좁힌 것도 중요합니다 — 사후 필터링(v09)을 피하려는 것입니다.

② ClickHouse — 접근 로그와 사전 집계

CREATE TABLE search_log
(
    ts           DateTime64(3),
    request_id   UUID,
    user_id      UInt64,
    team_id      UInt16,
    query        String,
    lang         LowCardinality(String),
    n_results    UInt16,
    top_score    Float32,
    latency_ms   UInt32,
    clicked_doc  UInt64,                        -- 0 이면 클릭 없음
    reranked     UInt8
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (team_id, ts)                          -- 대시보드가 항상 팀으로 필터합니다
TTL toDateTime(ts) + INTERVAL 90 DAY;

-- 사전 집계 (v05)
CREATE TABLE search_hourly
(
    hour       DateTime,
    team_id    UInt16,
    searches   AggregateFunction(count),
    zero_hits  AggregateFunction(countIf, UInt8),
    clicks     AggregateFunction(countIf, UInt8),
    users      AggregateFunction(uniq, UInt64),
    p95_ms     AggregateFunction(quantile(0.95), UInt32)
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(hour) ORDER BY (team_id, hour);

CREATE MATERIALIZED VIEW search_hourly_mv TO search_hourly AS
SELECT toStartOfHour(ts)                    AS hour,
       team_id,
       countState()                         AS searches,
       countIfState(n_results = 0)          AS zero_hits,
       countIfState(clicked_doc != 0)       AS clicks,
       uniqState(user_id)                   AS users,
       quantileState(0.95)(latency_ms)      AS p95_ms
FROM   search_log
GROUP  BY hour, team_id;
-- 대시보드 쿼리 ① 일별 지표
SELECT toDate(hour)                            AS d,
       countMerge(searches)                    AS searches,
       uniqMerge(users)                        AS dau,
       round(countMerge(zero_hits) * 100.0
             / countMerge(searches), 2)        AS zero_hit_pct,   -- ★ 가장 중요한 지표
       round(countMerge(clicks) * 100.0
             / countMerge(searches), 2)        AS ctr,
       quantileMerge(0.95)(p95_ms)             AS p95_ms
FROM   search_hourly
WHERE  team_id = 7 AND hour >= now() - INTERVAL 30 DAY
GROUP  BY d ORDER BY d;

-- 대시보드 쿼리 ② 답을 못 찾은 질문 (원본에서 직접)
SELECT query, count() AS n
FROM   search_log
WHERE  ts >= now() - INTERVAL 7 DAY AND n_results = 0
GROUP  BY query
HAVING n >= 3
ORDER  BY n DESC LIMIT 50;
