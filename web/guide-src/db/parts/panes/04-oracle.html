SECTION 01

오라클은 어떤 DB인가 · 에디션

기능·안정성·튜닝 도구에서 여전히 최고 수준입니다. 대신 비용이 매우 큽니다. 기술 선택 회의에서 반드시 나오는 이야기라 구조를 알아 둘 필요가 있습니다.

에디션내용
Enterprise (EE) 모든 기능. 파티셔닝·RAC·Data Guard·진단팩(AWR) 등은 대부분 별도 유료 옵션입니다. 코어 단위 라이선스라 서버 사양이 곧 비용입니다.
Standard Edition 2 (SE2) 기능이 제한됩니다(파티셔닝·병렬 쿼리 등 없음). 소켓 수 제한이 있습니다.
Free (구 XE) 무료. 사용자 데이터 12GB, CPU 2코어, 메모리 2GB 제한. 학습·개발·소규모 운영에 씁니다. 상용 사용도 허용됩니다.
Autonomous (클라우드) OCI에서 관리형으로. 항상 무료 등급(Always Free)이 있어 학습용으로 쓸 만합니다.
라이선스는 반드시 확인하세요. "EE를 깔았으니 파티셔닝을 써도 되겠지"가 수억 원짜리 감사 지적이 되는 일이 실제로 있습니다. 설치만으로 쓸 수 있게 되어 있어도, 계약한 옵션이 아니면 사용하면 안 됩니다. 가상화 환경의 코어 계산 규칙도 별도입니다 — 도입 시 반드시 영업/법무 검토를 거치세요.

버전 흐름 (2026-08 기준)

  • 11gR2 — 아직도 현장에 남아 있습니다. FETCH FIRST·IDENTITY가 없어 ROWNUM·시퀀스를 씁니다.
  • 12c / 18c / 19c — 19c가 장기 지원(LTS) 버전이라 실무 점유율이 가장 높습니다. 멀티테넌트(CDB/PDB)가 기본이 됐습니다.
  • 21c — 혁신 릴리스(단기 지원). JSON 전용 타입 등이 들어왔습니다.
  • 23ai — 현재의 장기 지원 버전. BOOLEAN 타입, IF EXISTS, 벡터 검색, SQL의 도메인·주석 개선 등 오래 기다린 기능들이 들어왔습니다.
이 탭의 기준 — 문법은 19c 이상에서 동작하는 것을 기본으로 하고, 23ai 전용 기능은 23ai 배지를, 11g 이하에서만 필요한 것은 11g 배지를 붙였습니다.
SECTION 02

설치 — Free · Docker

오라클 설치는 다른 DB보다 훨씬 무겁습니다. 학습 목적이면 도커가 정답입니다.

방법 ① Docker — 권장

# 공식 컨테이너 레지스트리 (별도 로그인 불필요)
docker run -d --name ora \
  -p 1521:1521 \
  -e ORACLE_PWD=devpass \
  -v oradata:/opt/oracle/oradata \
  container-registry.oracle.com/database/free:latest

# 기동에 2~5분 걸립니다. 아래가 보이면 준비 완료
docker logs -f ora | grep -i "DATABASE IS READY"

# 접속
docker exec -it ora sqlplus system/devpass@//localhost:1521/FREEPDB1
서비스명은 FREEPDB1 입니다(23ai Free 기준). FREE 는 컨테이너 DB(CDB)이고, 실제로 테이블을 만드는 곳은 PDB인 FREEPDB1 입니다. 이 구분을 모르면 "접속은 되는데 테이블이 안 보이는" 상황이 됩니다 → o04.

방법 ② 직접 설치 (Linux)

# Oracle Linux · RHEL 계열
sudo dnf install -y oracle-database-preinstall-23ai      # 커널 파라미터·계정 자동 설정
sudo dnf install -y oracle-database-free-23ai            # 다운로드한 RPM

# 초기 구성 (비밀번호를 물어봅니다)
sudo /etc/init.d/oracle-free-23ai configure

# 환경 변수 (~/.bashrc 에 추가)
export ORACLE_HOME=/opt/oracle/product/23ai/dbhomeFree
export ORACLE_SID=FREE
export PATH=$ORACLE_HOME/bin:$PATH

# 기동 확인
lsnrctl status
sqlplus / as sysdba

방법 ③ 접속만 필요할 때 — Instant Client

회사 서버의 오라클에 붙기만 하면 되는 경우, DB 전체를 설치할 필요가 없습니다. Oracle Instant Client(수십 MB) + SQL Developer(무료 GUI) 조합이면 충분합니다. 파이썬의 oracledb 드라이버는 Thin 모드를 지원해 Instant Client 없이도 붙습니다(🔌 a02).

설치 후 첫 확인

-- 버전
SELECT banner_full FROM v$version;

-- 지금 어디에 접속해 있나 (CDB? PDB?)
SHOW CON_NAME;
SELECT sys_context('USERENV','CON_NAME') FROM dual;

-- 사용 가능한 PDB 목록
SELECT name, open_mode FROM v$pdbs;
PDB가 MOUNTED 상태면 접속할 수 없습니다. ALTER PLUGGABLE DATABASE FREEPDB1 OPEN; 으로 열고, 재시작해도 유지되게 ALTER PLUGGABLE DATABASE FREEPDB1 SAVE STATE; 를 실행하세요. 도커 이미지는 보통 자동으로 열려 있습니다.
SECTION 03

접속 — SQL*Plus · 서비스명

오라클 접속에서 가장 많이 막히는 지점입니다. SID와 서비스명은 다릅니다 — 이것만 이해하면 대부분 풀립니다.

개념뜻
리스너 (Listener)1521 포트에서 접속 요청을 받아 DB로 넘겨주는 중개 프로세스. 이게 안 떠 있으면 ORA-12541.
SID서버에 떠 있는 인스턴스 하나의 이름. 물리적 개념.
서비스명클라이언트가 요청하는 논리적 이름. 여러 인스턴스가 한 서비스를 제공할 수 있습니다(RAC).
PDB12c 이후의 DB 안의 DB. 각 PDB가 서비스명을 가집니다.

접속 문자열 세 가지 형태

# ① Easy Connect — 가장 간단 (서비스명 앞에 슬래시)
sqlplus system/devpass@//localhost:1521/FREEPDB1

# ② SID 방식 (구형 · 콜론)
sqlplus system/devpass@localhost:1521:FREE

# ③ tnsnames.ora 별칭
sqlplus system/devpass@ORCLPDB
# $ORACLE_HOME/network/admin/tnsnames.ora
ORCLPDB =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = db.example.com)(PORT = 1521))
    (CONNECT_DATA =
      (SERVER = DEDICATED)
      (SERVICE_NAME = ORCLPDB)
    )
  )

리스너 진단

lsnrctl status          # 어떤 서비스가 등록돼 있는지 확인 ← 여기가 핵심
lsnrctl start
lsnrctl stop

# 네트워크 경로 확인
tnsping ORCLPDB
Service "FREEPDB1" has 1 instance(s). Instance "FREE", status READY, has 1 handler(s) for this service...
lsnrctl status 에 보이는 Service 이름을 그대로 쓰세요. 여기 없는 이름으로 접속하면 ORA-12514 가 납니다. 반대로 여기 보이면 접속 문자열은 맞는 것이니, 그다음은 계정·비밀번호 문제입니다.

SQL*Plus 에서 바로 쓰는 명령

SET LINESIZE 200          -- 한 줄 폭 (기본 80이라 결과가 접힙니다)
SET PAGESIZE 50           -- 헤더 반복 주기
SET SERVEROUTPUT ON       -- DBMS_OUTPUT.PUT_LINE 결과 보기
COLUMN name FORMAT A20    -- 컬럼 폭 지정

DESC member;              -- 테이블 구조
SHOW USER;                -- 지금 누구로 접속했나
SHOW CON_NAME;            -- 지금 어느 컨테이너인가

@script.sql               -- 파일 실행
SPOOL out.txt             -- 결과를 파일로
SPOOL OFF
EXIT
SQL*Plus 가 불편하다면 SQLcl 을 쓰세요. 오라클이 만든 최신 CLI로, 자동완성·히스토리·SELECT … ; 없이 실행 등 현대적인 편의 기능이 있고 JDBC만 있으면 동작합니다(Instant Client 불필요).
SECTION 04

CDB · PDB · 계정 · 권한

12c부터 오라클은 멀티테넌트 구조입니다. 계정을 어디에 만드느냐에 따라 C## 접두사가 필요해집니다 — 여기서 많이 막힙니다.

12c 이후의 오라클은 아파트 한 동(CDB)에 여러 세대(PDB)가 든 구조입니다. 접속할 때는 동이 아니라 세대 번호를 대야 합니다.
CDB
컨테이너 데이터베이스 (root) 전체를 감싸는 그릇. 여기에 만드는 계정은 공통 사용자라 이름이 C## 으로 시작해야 합니다.
▼
PDB
플러그인 데이터베이스 실제 업무 스키마가 사는 곳. 애플리케이션 계정은 여기에 만듭니다. 이름 제약이 없습니다.
-- 지금 어디인지 먼저 확인
SHOW CON_NAME;                      -- CDB$ROOT 이면 root 입니다

-- PDB 로 이동
ALTER SESSION SET CONTAINER = FREEPDB1;
SHOW CON_NAME;                      -- FREEPDB1

-- 애플리케이션 계정 만들기 (PDB 안에서)
CREATE USER app IDENTIFIED BY "Strong#Pass1"
  DEFAULT TABLESPACE users
  TEMPORARY TABLESPACE temp
  QUOTA UNLIMITED ON users;         -- ★ 이게 없으면 INSERT 시 ORA-01950

GRANT CREATE SESSION      TO app;   -- 접속 권한 (없으면 로그인 자체가 안 됨)
GRANT CREATE TABLE        TO app;
GRANT CREATE SEQUENCE     TO app;
GRANT CREATE VIEW         TO app;
GRANT CREATE PROCEDURE    TO app;
가장 흔한 두 가지 실수
① CDB$ROOT 에서 CREATE USER app → ORA-65096: 공통 사용자 이름이 부적합합니다. PDB로 이동하거나 이름을 C##app 으로 바꿔야 합니다.
② QUOTA 를 안 줌 → 테이블은 만들어지는데 INSERT 에서 ORA-01950: 테이블스페이스에 대한 권한이 없습니다.

권한 — 시스템 권한과 객체 권한

-- 시스템 권한 : "무엇을 할 수 있는가"
GRANT CREATE TABLE, CREATE VIEW TO app;

-- 객체 권한 : "어느 객체에 무엇을 할 수 있는가"
GRANT SELECT, INSERT, UPDATE ON hr.member TO app;
GRANT EXECUTE ON hr.pkg_order TO app;

-- 롤 : 권한 묶음
CREATE ROLE app_readonly;
GRANT SELECT ON hr.member TO app_readonly;
GRANT SELECT ON hr.orders TO app_readonly;
GRANT app_readonly TO analyst1, analyst2;

-- 확인
SELECT * FROM user_sys_privs;      -- 내가 가진 시스템 권한
SELECT * FROM user_tab_privs;      -- 내가 가진 객체 권한
SELECT * FROM session_privs;       -- 지금 세션에서 유효한 전체
GRANT DBA TO app; 은 절대 하지 마세요. 편하다는 이유로 실무에서 자주 벌어지는 일인데, 다른 스키마의 데이터를 전부 읽고 지울 수 있게 됩니다. SQL 인젝션 한 번이면 DB 전체가 넘어갑니다. 필요한 권한만 개별로 주세요.

스키마 = 계정

오라클에서는 계정 하나가 곧 스키마 하나입니다(PostgreSQL·MySQL과 다른 점). app 계정이 만든 테이블은 app.member 가 되고, 다른 계정이 쓰려면 스키마명을 붙이거나 시노님이 필요합니다. 

-- 시노님 : 다른 스키마 객체에 별명 붙이기
CREATE SYNONYM member FOR hr.member;              -- 내 계정에서만
CREATE PUBLIC SYNONYM member FOR hr.member;       -- 전체 공개 (남용 주의)
SECTION 05

DUAL · ROWNUM · 페이징

오라클 방언의 첫 관문입니다. 레거시 코드를 읽으려면 반드시 알아야 합니다.

ROWNUM 은 정렬보다 먼저 붙습니다. 자를 것은 언제나 정렬이 끝난 뒤여야 합니다.

DUAL — 계산 전용 가짜 테이블

-- 오라클은 SELECT 에 FROM 이 반드시 있어야 합니다
SELECT 1 + 1 FROM dual;
SELECT SYSDATE FROM dual;
SELECT seq_order.NEXTVAL FROM dual;

-- 다른 DB는 FROM 없이 됩니다
-- PostgreSQL/MySQL/SQLite:  SELECT 1 + 1;
23ai 부터는 FROM 절을 생략할 수 있습니다. SELECT 1 + 1; 이 동작합니다. 다만 현장 코드의 대부분은 여전히 FROM dual 이므로 읽을 줄 알아야 합니다.

ROWNUM — 결과에 매겨지는 임시 번호

SELECT ROWNUM, name FROM member WHERE ROWNUM <= 3;   -- 상위 3건
✗ 정렬 후 상위 N 이 아닙니다
SELECT * FROM product
WHERE  ROWNUM <= 3
ORDER  BY price DESC;

-- ROWNUM 이 ORDER BY 보다 먼저 매겨져
-- "아무 3건을 뽑아서 정렬"한 결과입니다
✓ 정렬을 먼저 하고 감싸기
SELECT * FROM (
    SELECT * FROM product ORDER BY price DESC
)
WHERE ROWNUM <= 3;
WHERE ROWNUM > 10 은 항상 0건입니다. ROWNUM은 조건을 통과한 행에만 순서대로 붙습니다. 첫 행이 1을 받는데 > 10 이면 탈락 → 다음 행도 다시 1 → 영원히 통과 못 함. 중간 페이지를 뽑으려면 반드시 서브쿼리로 감싸 별칭을 붙여야 합니다.

페이징 — 세 가지 방법

-- ① 12c 이상 (표준 문법) ★ 권장
SELECT * FROM product
ORDER  BY price DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- ② 11g 이하 : 3중 서브쿼리 (현장 레거시의 표준형)
SELECT * FROM (
    SELECT a.*, ROWNUM rn FROM (
        SELECT * FROM product ORDER BY price DESC
    ) a
    WHERE ROWNUM <= 30            -- 끝 위치
)
WHERE rn > 20;                    -- 시작 위치

-- ③ 윈도우 함수 (가장 유연 · 그룹별 페이징도 가능)
SELECT * FROM (
    SELECT p.*, ROW_NUMBER() OVER (ORDER BY price DESC) rn
    FROM   product p
)
WHERE rn BETWEEN 21 AND 30;
왜 ②는 서브쿼리를 두 번 감쌀까 — 안쪽에서 정렬하고, 중간에서 ROWNUM 을 별칭(rn)으로 고정하고, 바깥에서 그 별칭으로 범위 조건을 겁니다. ROWNUM은 매겨지는 즉시 비교할 수 없으므로 한 단계 더 감싸야 합니다.
SECTION 06

NVL · DECODE · 문자열

현장 코드에서 수천 번 만나게 되는 함수들입니다. 표준 대응 문법도 함께 정리합니다.

Oracle하는 일표준 대응
NVL(a, b)a가 NULL이면 bCOALESCE(a, b)
NVL2(a, b, c)a가 NULL이 아니면 b, NULL이면 cCASE WHEN a IS NOT NULL THEN b ELSE c END
DECODE(x, 1,'A', 2,'B', 'etc')값 비교 분기CASE x WHEN 1 THEN 'A' … END
SUBSTR(s, 1, 3)자르기 (1부터 시작)SUBSTRING(s FROM 1 FOR 3)
INSTR(s, 'x')위치 찾기 (없으면 0)POSITION('x' IN s)
LPAD(s, 5, '0')왼쪽 채우기동일
a || b문자열 결합동일 (MySQL만 CONCAT)
LISTAGG(x, ',')여러 행을 한 줄로STRING_AGG · GROUP_CONCAT
 
-- DECODE 실전 — 짧지만 가독성은 CASE 가 낫습니다
SELECT name,
       DECODE(grade, 'GOLD','10%', 'SILVER','5%', '없음') AS 혜택
FROM   member;

-- LISTAGG — 회원별 주문번호를 한 줄로
SELECT m.name,
       LISTAGG(o.id, ', ') WITHIN GROUP (ORDER BY o.id) AS 주문목록
FROM   member m JOIN orders o ON o.member_id = m.id
GROUP  BY m.name;
name 주문목록 김하늘 1001, 1003 박바다 1002, 1005
LISTAGG 는 4000바이트를 넘으면 에러(ORA-01489)가 납니다. 12cR2부터 LISTAGG(x, ',' ON OVERFLOW TRUNCATE) 로 자를 수 있습니다. 목록이 길어질 수 있으면 애플리케이션에서 조립하는 편이 안전합니다.

오라클만의 특이점 — 빈 문자열 = NULL

SELECT CASE WHEN '' IS NULL THEN 'NULL 이다' ELSE '아니다' END FROM dual;
-- 오라클: 'NULL 이다'      ← 오라클만 이렇습니다
-- 그 외 : '아니다'

-- 그래서 이런 코드가 오라클에서만 다르게 동작합니다
SELECT COUNT(*) FROM member WHERE email = '';    -- 오라클: 항상 0건
마이그레이션에서 반드시 걸리는 지점입니다. 오라클에서 PostgreSQL로 옮기면 빈 문자열이 NULL이 아니게 되어 IS NULL 조건이 걸리지 않는 행이 생깁니다. 데이터 정제 단계에서 NULLIF(col, '') 로 통일하세요.
SECTION 07

DATE · TO_DATE · INTERVAL

오라클의 DATE에는 시분초가 들어 있습니다. 이걸 모르고 날짜를 비교하다 정산이 틀어지는 사고가 정말 많습니다.

핵심 — 다른 DB의 DATE 는 "날짜만"이지만, 오라클의 DATE 는 초 단위까지 저장합니다(연·월·일·시·분·초). SYSDATE 도 지금 시각을 초까지 갖고 있습니다.
✗ 오늘 데이터가 안 나옵니다
SELECT * FROM orders
WHERE  ordered_at = SYSDATE;
-- 정확히 '지금 이 초'인 행만 걸립니다 → 0건

SELECT * FROM orders
WHERE  ordered_at BETWEEN '2026-01-01' AND '2026-01-31';
-- 1/31 00:00:00 까지만 → 하루가 통째로 빠짐
✓ 범위로 비교
SELECT * FROM orders
WHERE  ordered_at >= TRUNC(SYSDATE)
  AND  ordered_at <  TRUNC(SYSDATE) + 1;

SELECT * FROM orders
WHERE  ordered_at >= DATE '2026-01-01'
  AND  ordered_at <  DATE '2026-02-01';

날짜 함수

SELECT SYSDATE                            AS 현재시각,      -- DB 서버 시각
       SYSTIMESTAMP                       AS 타임존포함,
       TRUNC(SYSDATE)                     AS 오늘자정,
       TRUNC(SYSDATE, 'MM')               AS 이번달1일,
       LAST_DAY(SYSDATE)                  AS 이번달말일,
       ADD_MONTHS(SYSDATE, 3)             AS 삼개월후,
       SYSDATE + 7                        AS 일주일후,      -- 숫자 = 일 단위
       SYSDATE + 1/24                     AS 한시간후,      -- 1/24 = 1시간
       MONTHS_BETWEEN(SYSDATE, hire_date) AS 근무개월
FROM   dual;

-- 문자 ↔ 날짜
SELECT TO_DATE('2026-08-05 14:30', 'YYYY-MM-DD HH24:MI') FROM dual;
SELECT TO_CHAR(SYSDATE, 'YYYY-MM-DD HH24:MI:SS')          FROM dual;
SELECT TO_CHAR(SYSDATE, 'YYYY"년" MM"월" DD"일"')          FROM dual;
포맷뜻주의
YYYY4자리 연도—
MM월 (01~12)MI(분)와 헷갈리지 마세요
DD일—
HH2424시간제 시HH 만 쓰면 12시간제입니다
MI분—
SS초—

타임존이 필요하면 TIMESTAMP

CREATE TABLE event (
  id      NUMBER,
  at_utc  TIMESTAMP WITH TIME ZONE,          -- 타임존 정보 저장
  at_loc  TIMESTAMP WITH LOCAL TIME ZONE     -- 조회하는 세션 시간대로 자동 변환
);

SELECT SYSTIMESTAMP AT TIME ZONE 'UTC' FROM dual;
SELECT ordered_at + INTERVAL '3' DAY   FROM orders;
SELECT ordered_at + INTERVAL '2' MONTH FROM orders;
글로벌 서비스라면 시각은 UTC로 저장하고 표시할 때만 변환하는 것이 원칙입니다. SYSDATE 는 DB 서버의 OS 시간대를 따르므로, 서버가 옮겨가면 값의 의미가 달라집니다.
SECTION 08

시퀀스 · IDENTITY · 트리거

오라클에는 AUTO_INCREMENT 가 없습니다. 대신 시퀀스라는 독립 객체를 씁니다. 

-- 시퀀스 만들기
CREATE SEQUENCE seq_member
  START WITH 1
  INCREMENT BY 1
  NOCACHE            -- 번호 건너뜀을 막고 싶으면 (성능은 떨어집니다)
  NOCYCLE;

-- 사용
INSERT INTO member (id, name) VALUES (seq_member.NEXTVAL, '김하늘');
SELECT seq_member.CURRVAL FROM dual;    -- 방금 쓴 값 (같은 세션에서만)

-- 12c 부터는 DEFAULT 로 쓸 수 있습니다
CREATE TABLE member (
  id   NUMBER DEFAULT seq_member.NEXTVAL PRIMARY KEY,
  name VARCHAR2(50)
);

IDENTITY — 12c 이상이면 이쪽이 간단합니다 12c+

CREATE TABLE member (
  id   NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- 값을 직접 못 넣음
  name VARCHAR2(50)
);
-- 또는
  id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY  -- 직접 넣는 것도 허용
  id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY      -- NULL 넣으면 자동 채움

INSERT INTO member (name) VALUES ('김하늘');   -- id 는 자동

11g 이하 — 시퀀스 + 트리거 11g

CREATE OR REPLACE TRIGGER trg_member_id
BEFORE INSERT ON member
FOR EACH ROW
WHEN (NEW.id IS NULL)
BEGIN
  :NEW.id := seq_member.NEXTVAL;
END;
/
/ 는 SQL*Plus 에게 "PL/SQL 블록이 끝났으니 실행하라"는 뜻입니다. PL/SQL 안에는 세미콜론이 여러 번 나오므로 블록의 끝을 알리는 별도 기호가 필요합니다. 이걸 빠뜨리면 아무 일도 안 일어난 채 커서만 기다립니다.

번호가 건너뛰는 이유

시퀀스는 성능을 위해 번호를 미리 메모리에 캐시합니다(기본 20개). DB를 재시작하거나 인스턴스가 죽으면 캐시에 남아 있던 번호가 사라집니다. 또 롤백해도 이미 뽑은 번호는 돌아오지 않습니다.

번호에 의미를 부여하지 마세요. "주문번호는 빠짐없이 연속이어야 한다"는 요구는 시퀀스로 만족시킬 수 없습니다. 연속 번호가 필요하면 별도 채번 테이블 + 락이 필요하고, 이는 동시성을 크게 떨어뜨립니다. 대부분의 경우 요구사항을 재검토하는 편이 낫습니다.

트리거 — 쓸 때와 안 쓸 때

-- 감사 로그 : 트리거의 정당한 용도
CREATE OR REPLACE TRIGGER trg_member_audit
AFTER UPDATE ON member
FOR EACH ROW
BEGIN
  INSERT INTO member_hist (member_id, old_grade, new_grade, changed_at, changed_by)
  VALUES (:OLD.id, :OLD.grade, :NEW.grade, SYSTIMESTAMP, SYS_CONTEXT('USERENV','SESSION_USER'));
END;
/
트리거에 비즈니스 로직을 넣지 마세요. 코드에서 보이지 않는 곳에서 데이터가 바뀌므로 디버깅이 극도로 어려워집니다. 트리거가 다른 트리거를 부르는 연쇄가 생기면 사실상 추적이 불가능합니다. 감사 로그·타임스탬프 자동 기록 정도로 제한하세요.
SECTION 09

계층 쿼리 CONNECT BY

오라클 전용 계층 탐색 문법입니다. 재귀 CTE보다 짧고, 레거시 코드에 아주 많이 나옵니다. 

SELECT LEVEL,
       LPAD(' ', (LEVEL-1)*3) || name    AS 트리,
       SYS_CONNECT_BY_PATH(name, ' > ')  AS 경로,
       CONNECT_BY_ISLEAF                 AS 말단여부
FROM   category
START  WITH parent_id IS NULL            -- 출발점
CONNECT BY PRIOR id = parent_id          -- 부모→자식 연결 규칙
ORDER  SIBLINGS BY name;                 -- 형제끼리 정렬
LEVEL 트리 경로 1 전체 > 전체 2 의류 > 전체 > 의류 2 전자제품 > 전체 > 전자제품 3 주변기기 > 전체 > 전자제품 > 주변기기 4 마우스 > 전체 > 전자제품 > 주변기기 > 마우스
키워드뜻
START WITH탐색 출발점 조건
CONNECT BY PRIOR a = bPRIOR가 붙은 쪽이 "이전 행". PRIOR id = parent_id 는 아래로, 반대로 쓰면 위로 올라갑니다
LEVEL깊이 (출발점이 1)
SYS_CONNECT_BY_PATH루트부터의 경로 문자열
CONNECT_BY_ROOT x이 행이 속한 최상위의 x 값
CONNECT_BY_ISLEAF자식이 없으면 1
NOCYCLE순환이 있어도 멈춤 (CONNECT BY NOCYCLE PRIOR …)
ORDER SIBLINGS BY계층 구조를 유지하면서 형제만 정렬

방향 뒤집기 — 조상 찾기

-- '마우스'에서 최상위까지 거슬러 올라가기
SELECT LEVEL, name
FROM   category
START  WITH id = 5
CONNECT BY PRIOR parent_id = id;      -- PRIOR 위치가 반대

재귀 CTE 와 비교

CONNECT BY — 짧습니다
SELECT LEVEL, name
FROM   category
START  WITH parent_id IS NULL
CONNECT BY PRIOR id = parent_id;
재귀 CTE — 표준입니다
WITH tree (id, name, lvl) AS (
  SELECT id, name, 1 FROM category WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, t.lvl+1
  FROM   category c JOIN tree t ON t.id = c.parent_id
)
SELECT lvl, name FROM tree;
새로 쓴다면 재귀 CTE 를 권합니다. 다른 DB로 옮길 수 있고, 복잡한 조건을 붙이기도 쉽습니다. 다만 기존 코드를 읽고 고치려면 CONNECT BY 는 필수입니다 — 국내 SI 코드에 압도적으로 많습니다.
조직도 · 카테고리 · 댓글 — 자기 자신을 가리키는 표는 전부 이 모양입니다.
SECTION 10

오라클 분석 함수

윈도우 함수(🎓 e01)는 오라클이 원조입니다. 여기서는 오라클에만 있거나 특히 강력한 것들을 봅니다.

KEEP … DENSE_RANK FIRST/LAST — 그룹의 대표값

-- 부서별로 "가장 최근 입사자의 급여" 를 집계 한 번에
SELECT dept_id,
       MAX(salary) KEEP (DENSE_RANK FIRST ORDER BY hire_date DESC) AS 최근입사자급여,
       MIN(salary) KEEP (DENSE_RANK LAST  ORDER BY hire_date DESC) AS 최초입사자급여,
       COUNT(*) AS 인원
FROM   employee
GROUP  BY dept_id;
다른 DB에서는 ROW_NUMBER 로 서브쿼리를 만들어야 하는 일을 GROUP BY 한 번으로 끝냅니다. 오라클 정산 쿼리에서 자주 보입니다.

RATIO_TO_REPORT · 누적 분포

SELECT category, name, price,
       ROUND(RATIO_TO_REPORT(price) OVER (PARTITION BY category) * 100, 1) AS 카테고리내비중,
       ROUND(CUME_DIST() OVER (ORDER BY price) * 100, 1)                   AS 누적분포,
       PERCENT_RANK()   OVER (ORDER BY price)                              AS 백분위
FROM   product;

MODEL 절 — 스프레드시트처럼 계산

-- 전월 값을 참조해 누적 예측치를 만드는 등, 엑셀 수식 같은 계산
SELECT 월, 매출, 예측
FROM   monthly_sales
MODEL
  DIMENSION BY (월)
  MEASURES (매출, 0 AS 예측)
  RULES (
    예측[FOR 월 FROM 7 TO 12 INCREMENT 1] = 매출[CV()-1] * 1.05
  );
MODEL 절은 배우는 비용에 비해 쓸 일이 적습니다. 가독성이 매우 떨어지고 오라클 전용이라 유지보수가 어렵습니다. 대부분의 경우 윈도우 함수 + 재귀 CTE 로 충분합니다. 존재만 알아 두세요.

MATCH_RECOGNIZE — 행 패턴 인식 12c+

-- "3일 연속 매출 상승" 같은 패턴을 SQL 로 찾기
SELECT * FROM daily_sales
MATCH_RECOGNIZE (
  ORDER BY 일자
  MEASURES FIRST(UP.일자) AS 시작일, LAST(UP.일자) AS 종료일, COUNT(*) AS 일수
  ONE ROW PER MATCH
  PATTERN (UP{3,})
  DEFINE UP AS 매출 > PREV(매출)
);
이상 탐지·사용자 여정 분석에 강력합니다. 다만 문법이 낯설고 오라클 전용이라, 정말 필요할 때만 꺼내는 카드입니다.
SECTION 11

PL/SQL 기초 — 블록 · 커서

SQL에 변수·조건문·반복문·예외처리를 붙인 언어입니다. DB 안에서 도는 프로그램을 만듭니다. 

SET SERVEROUTPUT ON      -- 출력을 보려면 먼저 켜야 합니다

DECLARE
    v_name    member.name%TYPE;          -- 컬럼과 같은 타입으로 (변경에 안전)
    v_count   NUMBER := 0;
    v_row     member%ROWTYPE;            -- 행 전체를 담는 변수
BEGIN
    SELECT name INTO v_name FROM member WHERE id = 1;
    DBMS_OUTPUT.PUT_LINE('이름: ' || v_name);

    SELECT COUNT(*) INTO v_count FROM orders WHERE member_id = 1;

    IF v_count > 5 THEN
        DBMS_OUTPUT.PUT_LINE('단골');
    ELSIF v_count > 0 THEN
        DBMS_OUTPUT.PUT_LINE('일반');
    ELSE
        DBMS_OUTPUT.PUT_LINE('주문 없음');
    END IF;

EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('회원을 찾을 수 없습니다');
    WHEN TOO_MANY_ROWS THEN
        DBMS_OUTPUT.PUT_LINE('결과가 여러 건입니다');
    WHEN OTHERS THEN
        DBMS_OUTPUT.PUT_LINE('오류: ' || SQLCODE || ' ' || SQLERRM);
        RAISE;                            -- ★ 삼키지 말고 다시 던지세요
END;
/
SELECT … INTO 는 정확히 1행이어야 합니다. 0행이면 NO_DATA_FOUND, 2행 이상이면 TOO_MANY_ROWS 예외가 납니다. 이 둘을 처리하지 않으면 배치가 통째로 죽습니다.

커서 — 여러 행을 한 줄씩

-- 방법 ① 암시적 커서 FOR 루프 (가장 간결 · 권장)
BEGIN
  FOR r IN (SELECT id, name FROM member WHERE grade = 'GOLD') LOOP
      DBMS_OUTPUT.PUT_LINE(r.id || ' : ' || r.name);
  END LOOP;
END;
/

-- 방법 ② 명시적 커서 (파라미터가 필요할 때)
DECLARE
  CURSOR c_member(p_grade VARCHAR2) IS
      SELECT id, name FROM member WHERE grade = p_grade;
  v_id member.id%TYPE;  v_name member.name%TYPE;
BEGIN
  OPEN c_member('GOLD');
  LOOP
      FETCH c_member INTO v_id, v_name;
      EXIT WHEN c_member%NOTFOUND;
      DBMS_OUTPUT.PUT_LINE(v_id || ' : ' || v_name);
  END LOOP;
  CLOSE c_member;
END;
/

프로시저와 함수

CREATE OR REPLACE PROCEDURE grade_up(p_id IN NUMBER, p_result OUT VARCHAR2) IS
BEGIN
    UPDATE member SET grade = 'GOLD' WHERE id = p_id;
    IF SQL%ROWCOUNT = 0 THEN
        p_result := '대상 없음';
    ELSE
        p_result := '성공';
        COMMIT;
    END IF;
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        p_result := '실패: ' || SQLERRM;
        RAISE;
END;
/

-- 함수는 값을 돌려주고 SELECT 안에서도 쓸 수 있습니다
CREATE OR REPLACE FUNCTION total_amount(p_member_id NUMBER) RETURN NUMBER IS
    v_total NUMBER;
BEGIN
    SELECT NVL(SUM(oi.qty * oi.unit_price), 0) INTO v_total
    FROM   orders o JOIN order_item oi ON oi.order_id = o.id
    WHERE  o.member_id = p_member_id;
    RETURN v_total;
END;
/

SELECT name, total_amount(id) FROM member;
SELECT 안에서 함수를 호출하면 행마다 실행됩니다. 회원 10만 명이면 함수가 10만 번 돌고, 그 안에서 또 쿼리가 나갑니다. 조인으로 바꿀 수 있는지 먼저 검토하세요.
PL/SQL 을 쓸지 말지는 취향이 아니라 왕복 비용이 진짜 병목인가로 정합니다.
SECTION 12

패키지 · 벌크 연산

한 건씩 처리하면 SQL 엔진과 PL/SQL 엔진 사이를 계속 오갑니다(컨텍스트 스위치). 묶어서 처리하면 수십 배 빨라집니다.

패키지 — 관련 프로시저를 묶기

-- 명세 (인터페이스)
CREATE OR REPLACE PACKAGE pkg_order IS
    PROCEDURE create_order(p_member_id NUMBER, p_order_id OUT NUMBER);
    FUNCTION  total_of(p_order_id NUMBER) RETURN NUMBER;
END pkg_order;
/

-- 본문 (구현)
CREATE OR REPLACE PACKAGE BODY pkg_order IS
    PROCEDURE create_order(p_member_id NUMBER, p_order_id OUT NUMBER) IS
    BEGIN
        INSERT INTO orders (id, member_id, ordered_at, status)
        VALUES (seq_order.NEXTVAL, p_member_id, SYSDATE, 'PAID')
        RETURNING id INTO p_order_id;
    END;

    FUNCTION total_of(p_order_id NUMBER) RETURN NUMBER IS
        v NUMBER;
    BEGIN
        SELECT SUM(qty * unit_price) INTO v FROM order_item WHERE order_id = p_order_id;
        RETURN NVL(v, 0);
    END;
END pkg_order;
/
패키지의 실질적 이점 — 관련 로직이 한 곳에 모이고, 명세만 바뀌지 않으면 본문을 고쳐도 의존 객체가 무효화되지 않습니다(재컴파일 연쇄 방지). 또 패키지 안에 세션 단위 전역 변수를 둘 수 있습니다.

BULK COLLECT · FORALL — 성능의 핵심

✗ 한 건씩 — 10만 번 왕복
BEGIN
  FOR r IN (SELECT id FROM member WHERE grade='BASIC') LOOP
      UPDATE member SET grade='SILVER' WHERE id = r.id;
  END LOOP;
  COMMIT;
END;
/
-- 10만 건에 수 분
✓ 묶어서 — 한 번에
DECLARE
  TYPE t_ids IS TABLE OF member.id%TYPE;
  v_ids t_ids;
BEGIN
  SELECT id BULK COLLECT INTO v_ids
  FROM   member WHERE grade='BASIC';

  FORALL i IN 1 .. v_ids.COUNT
      UPDATE member SET grade='SILVER'
      WHERE  id = v_ids(i);
  COMMIT;
END;
/
-- 10만 건에 수 초

건수가 많으면 나눠서 담기 (LIMIT)

DECLARE
  CURSOR c IS SELECT id FROM member WHERE grade='BASIC';
  TYPE t_ids IS TABLE OF member.id%TYPE;
  v_ids t_ids;
BEGIN
  OPEN c;
  LOOP
    FETCH c BULK COLLECT INTO v_ids LIMIT 5000;   -- ★ 메모리 폭발 방지
    EXIT WHEN v_ids.COUNT = 0;

    FORALL i IN 1 .. v_ids.COUNT
        UPDATE member SET grade='SILVER' WHERE id = v_ids(i);
    COMMIT;                                        -- 청크마다 커밋
  END LOOP;
  CLOSE c;
END;
/
BULK COLLECT 를 LIMIT 없이 쓰면 위험합니다. 1억 건을 통째로 PGA 메모리에 담으려다 ORA-04030 으로 죽습니다. 항상 LIMIT 을 붙이세요 — 보통 1,000~10,000이 적당합니다. 
-- 일부가 실패해도 계속 진행하고 나중에 확인하기
BEGIN
  FORALL i IN 1 .. v_ids.COUNT SAVE EXCEPTIONS
      UPDATE member SET grade='SILVER' WHERE id = v_ids(i);
EXCEPTION
  WHEN OTHERS THEN
    FOR j IN 1 .. SQL%BULK_EXCEPTIONS.COUNT LOOP
      DBMS_OUTPUT.PUT_LINE(
        SQL%BULK_EXCEPTIONS(j).ERROR_INDEX || ' 번째 실패: ' ||
        SQLERRM(-SQL%BULK_EXCEPTIONS(j).ERROR_CODE));
    END LOOP;
END;

SECTION 13

힌트와 옵티마이저

힌트는 옵티마이저에게 주는 지시입니다. 잘 쓰면 응급처치, 잘못 쓰면 영구적인 부채가 됩니다. 

-- 힌트는 SELECT 바로 뒤 /*+ ... */ 안에 씁니다
SELECT /*+ INDEX(m idx_member_city) */ *
FROM   member m
WHERE  city = '서울';

SELECT /*+ FULL(o) PARALLEL(o, 4) */ COUNT(*)
FROM   orders o;

SELECT /*+ LEADING(m o) USE_NL(o) */ m.name, o.id
FROM   member m JOIN orders o ON o.member_id = m.id;
힌트지시 내용쓸 때
INDEX(t idx)이 인덱스를 써라통계가 틀어져 풀스캔을 탈 때
FULL(t)전체 스캔해라전체의 상당 비율을 읽을 때는 이쪽이 빠름
LEADING(a b)조인 순서를 이렇게작은 테이블부터 몰고 싶을 때
USE_NL · USE_HASH조인 방식 지정🧬 z08 참고
PARALLEL(t, n)병렬로 처리대용량 배치에만 (EE 옵션)
APPEND직접 경로 INSERT대량 적재 (로그 최소화 · 락 주의)
GATHER_PLAN_STATISTICS실제 실행 통계 수집튜닝할 때 항상 켜는 힌트
힌트를 쓰기 전에 반드시 확인하세요.
① 통계가 최신인가 — 대부분의 "이상한 계획"은 통계가 낡아서입니다
② 인덱스가 적절한가 — 힌트로 억지로 태우는 것보다 인덱스를 고치는 게 근본 해결입니다
③ 데이터가 변해도 유효한가 — 오늘 맞는 힌트가 6개월 뒤에는 최악이 될 수 있습니다
힌트는 주석이라 문법 오류가 나도 조용히 무시됩니다. 오타를 내면 아무 일도 안 일어납니다.

통계 수집

-- 특정 테이블
EXEC DBMS_STATS.GATHER_TABLE_STATS('APP', 'ORDERS');

-- 스키마 전체
EXEC DBMS_STATS.GATHER_SCHEMA_STATS('APP');

-- 마지막 수집 시각 확인 ← 느려졌을 때 여기부터 봅니다
SELECT table_name, num_rows, last_analyzed
FROM   user_tables
ORDER  BY last_analyzed;

계획을 고정하는 방법 (힌트보다 나은 선택)

  • SQL Plan Baseline — 좋은 계획을 등록해 두고 그것만 쓰게 합니다. 힌트를 코드에 박지 않아도 됩니다.
  • SQL Profile — 옵티마이저의 추정을 보정합니다. SQL Tuning Advisor 가 만들어 줍니다.
  • SQL Patch — 코드를 못 고치는 패키지 제품에 힌트를 외부에서 주입합니다.
이 기능들은 대부분 Enterprise Edition + 튜닝팩이 필요합니다. SE2 에서는 힌트와 통계 관리가 사실상 유일한 수단입니다.
SECTION 14

실행계획 · AWR · ASH

"느리다"를 숫자로 바꾸는 도구들입니다. 오라클이 다른 DB보다 확실히 앞서는 영역입니다.

① 실행계획 — 추정과 실제를 함께 보기

-- 추정 계획만 (실행하지 않음)
EXPLAIN PLAN FOR
SELECT * FROM orders WHERE member_id = 1;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- ★ 실제로 돌려 보고 추정 vs 실제 비교 (튜닝의 기본)
SELECT /*+ GATHER_PLAN_STATISTICS */ *
FROM   orders WHERE member_id = 1;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
| Id | Operation | Name | Starts | E-Rows | A-Rows | Buffers | | 0 | SELECT STATEMENT | | 1 | | 3 | 5 | | 1 | TABLE ACCESS BY INDEX ROWID| ORDERS | 1 | 3 | 3 | 5 | |* 2 | INDEX RANGE SCAN | IDX_ORD_MEM | 1 | 3 | 3 | 2 |
E-Rows(추정)와 A-Rows(실제)의 차이가 핵심입니다. 추정 3행인데 실제 300만 행이면 옵티마이저가 완전히 잘못 판단한 것이고, 그 원인은 대부분 통계 부실입니다. Buffers 는 읽은 블록 수로, 실질적 비용 지표입니다.

② 지금 뭐가 도는지 — V$ 뷰

-- 현재 활성 세션과 대기 이벤트
SELECT s.sid, s.serial#, s.username, s.status,
       s.event, s.wait_class, s.seconds_in_wait,
       q.sql_text
FROM   v$session s
LEFT   JOIN v$sql q ON q.sql_id = s.sql_id
WHERE  s.type = 'USER' AND s.status = 'ACTIVE'
ORDER  BY s.seconds_in_wait DESC;

-- 락을 기다리는 세션 (블로킹 체인)
SELECT blocking_session, sid, serial#, wait_class, seconds_in_wait
FROM   v$session
WHERE  blocking_session IS NOT NULL;

-- 문제 세션 강제 종료 (최후의 수단)
ALTER SYSTEM KILL SESSION '123,45678' IMMEDIATE;

③ AWR · ASH — 과거를 추적

# AWR 리포트 생성 (SQL*Plus 에서)

# 특정 SQL 하나만

AWR 에서 볼 것의미
DB Time세션들이 실제로 일한 총 시간. 경과 시간보다 크면 동시 부하가 높은 것
Top 10 Foreground Events무엇을 기다렸는가 — db file sequential read(인덱스 IO), enq: TX - row lock contention(락 경합) 등
SQL ordered by Elapsed Time가장 오래 걸린 쿼리 — 튜닝 대상 1순위
SQL ordered by Gets가장 많이 읽은 쿼리 — 인덱스 문제일 가능성이 높음
Buffer Hit %메모리에서 처리된 비율. 낮으면 SGA 부족 또는 잘못된 스캔
AWR·ASH·ADDM 은 Enterprise Edition + Diagnostic Pack 라이선스가 필요합니다. SE2 나 Free 에서는 무료 대안인 Statspack 을 쓰세요 (@?/rdbms/admin/spcreate.sql 로 설치). 라이선스 없이 AWR을 조회하는 것만으로도 감사 대상이 됩니다.
도구를 늘리기 전에 ①②③④ 순서를 지키는 것이 훨씬 빠릅니다.
SECTION 15

파티셔닝 · 인덱스 종류

수억 건 테이블을 조각으로 나눠 관리합니다. 조회도 빨라지고 오래된 데이터를 통째로 버릴 수도 있습니다. 

-- RANGE 파티션 + 자동 확장 (INTERVAL) ★ 실무에서 가장 많이 씁니다
CREATE TABLE orders (
    id          NUMBER,
    member_id   NUMBER,
    ordered_at  DATE NOT NULL,
    amount      NUMBER(12,2)
)
PARTITION BY RANGE (ordered_at)
INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))     -- 새 달 데이터가 오면 파티션 자동 생성
(
    PARTITION p_2025 VALUES LESS THAN (DATE '2026-01-01')
);

-- 오래된 데이터 즉시 제거 (DELETE 와 비교할 수 없이 빠릅니다)
ALTER TABLE orders DROP PARTITION p_2025;

-- 특정 파티션만 조회
SELECT * FROM orders PARTITION (p_2025);
방식기준쓰는 곳
RANGE값의 범위 (주로 날짜)★ 로그·주문·이력 — 가장 흔함
LIST값의 목록 (지역·상태)구분이 명확하고 개수가 적을 때
HASH해시 분산고르게 나누고 싶을 때 (범위 기준이 없을 때)
COMPOSITERANGE + HASH 등 조합초대용량 (월별 + 지역별)
파티셔닝은 Enterprise Edition 유료 옵션입니다. SE2 에서는 쓸 수 없습니다. 이 경우 테이블을 물리적으로 나누고 UNION ALL 뷰로 묶는 옛 방식(파티션 뷰)을 쓰거나, 아카이빙 전략을 다르게 세워야 합니다.

파티션 인덱스 — LOCAL vs GLOBAL

LOCAL — 파티션마다 별도 인덱스
CREATE INDEX idx_ord_mem ON orders(member_id) LOCAL;

-- 장점: DROP PARTITION 해도 인덱스가 안 깨짐
-- 운영 부담이 적어 대부분 이쪽을 씁니다
GLOBAL — 전체를 하나로
CREATE INDEX idx_ord_mem ON orders(member_id) GLOBAL;

-- 파티션 키가 없는 조회는 빠르지만
-- DROP PARTITION 시 인덱스가 UNUSABLE 이 됩니다
-- (UPDATE INDEXES 절로 유지 가능하나 느림)

오라클의 인덱스 종류

종류언제 쓰나
B-Tree (기본)대부분의 경우. 값의 종류가 많을수록 유리
비트맵값의 종류가 적고(성별·상태) 변경이 드문 DW 성 테이블. OLTP 에서 쓰면 락 경합이 심각해집니다
함수 기반UPPER(name) 처럼 함수를 씌워 조회할 때
역방향 키순차 증가 PK 로 인덱스 우측 블록에 경합이 심할 때 (RAC 환경)
IOT테이블 자체를 인덱스 구조로. PK 조회가 압도적일 때
도메인Oracle Text(전문 검색) 등 확장 인덱스
-- 함수 기반 인덱스 (대소문자 무시 조회를 인덱스로)
CREATE INDEX idx_member_upper_name ON member (UPPER(name));
SELECT * FROM member WHERE UPPER(name) = 'KIM';    -- 이제 인덱스를 탑니다

-- 온라인으로 만들기 (서비스 중 락 최소화)
CREATE INDEX idx_ord_dt ON orders(ordered_at) ONLINE;
파티셔닝은 인덱스의 대체품이 아닙니다 — 큰 덩어리를 안 읽게 만드는 장치입니다.
SECTION 16

RAC · Data Guard · RMAN

장애가 나도 서비스가 멈추지 않게 하는 구성입니다. 금융·통신에서는 기본 요건입니다.

가용성 설계의 첫 질문은 "무엇이 죽는 경우를 막고 싶은가"입니다 — 서버인지, 전산실 전체인지.
기술해결하는 문제주의
RAC 여러 서버가 같은 스토리지를 공유해 한 DB를 함께 처리. 한 노드가 죽어도 나머지가 계속 서비스합니다. 공유 스토리지가 단일 장애점. 유료 옵션이며 구성이 복잡합니다
Data Guard 다른 위치에 대기 DB를 두고 로그를 복제. 재해(DR) 대비와 읽기 부하 분산. Active Data Guard(대기 DB에서 조회)는 별도 옵션
RMAN 오라클 공식 백업·복구 도구. 증분 백업·블록 단위 복구·시점 복구 지원. EE·SE2 모두 사용 가능
Flashback 실수로 지운 데이터를 과거 시점으로 되살립니다. UNDO 보존 기간·플래시백 로그 설정 필요

RMAN 기본

rman target /

RMAN> BACKUP DATABASE PLUS ARCHIVELOG;          # 전체 백업 + 아카이브 로그
RMAN> BACKUP INCREMENTAL LEVEL 1 DATABASE;      # 증분 백업
RMAN> LIST BACKUP SUMMARY;                      # 백업 목록
RMAN> VALIDATE DATABASE;                        # 백업본 검증 ← 정기적으로 하세요
RMAN> DELETE OBSOLETE;                          # 보존 정책 초과분 정리

# 복구
RMAN> RESTORE DATABASE;
RMAN> RECOVER DATABASE UNTIL TIME "TO_DATE('2026-08-05 14:00','YYYY-MM-DD HH24:MI')";

Flashback — 실수 되돌리기

-- 10분 전 데이터 보기
SELECT * FROM member AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '10' MINUTE);

-- 테이블을 통째로 되돌리기 (행 이동 허용 필요)
ALTER TABLE member ENABLE ROW MOVEMENT;
FLASHBACK TABLE member TO TIMESTAMP (SYSTIMESTAMP - INTERVAL '10' MINUTE);

-- DROP 한 테이블 복구 (휴지통에서)
SELECT object_name, original_name FROM recyclebin;
FLASHBACK TABLE member TO BEFORE DROP;
Flashback Query 는 오라클의 킬러 기능입니다. "10분 전에 잘못 UPDATE 했다"는 상황에서 백업 복구 없이 즉시 확인·복원할 수 있습니다. 다만 UNDO 보존 기간(undo_retention) 안에서만 가능합니다.
백업의 진짜 요건은 "복구해 본 적이 있는가"입니다. 백업 스크립트가 매일 도는 것은 아무 의미가 없습니다. 분기마다 실제로 복구 훈련을 하세요. "백업 파일은 있는데 복구가 안 되는" 상황이 실제로 가장 흔한 재해입니다.
SECTION 17

탈오라클 마이그레이션

라이선스 비용 때문에 PostgreSQL로 옮기는 기업이 계속 늘고 있습니다. 무엇이 걸림돌인지 미리 알면 견적이 달라집니다.

난이도별 항목

🟢 쉬움 — 자동 변환
  • 기본 DDL·자료형 (VARCHAR2 → VARCHAR)
  • 표준 SELECT·JOIN·집계
  • NVL → COALESCE, DECODE → CASE
  • 시퀀스 → IDENTITY
  • FETCH FIRST 페이징 (12c 이상이면 그대로)
🔵 보통 — 손봐야 함
  • ROWNUM 페이징 → LIMIT
  • CONNECT BY → WITH RECURSIVE
  • DATE의 시분초 차이
  • LISTAGG → STRING_AGG
  • MERGE → ON CONFLICT
  • 계층·분석 함수 일부
🟣 어려움 — 재작성
  • PL/SQL 패키지 전체 → PL/pgSQL
  • 빈 문자열 = NULL 동작 차이
  • 계층적 힌트·계획 고정
  • DBMS_* 내장 패키지 의존
  • Oracle Text · Spatial
  • 운영 스크립트·모니터링 전부

반드시 확인할 동작 차이

항목Oracle → PostgreSQL 로 갈 때
빈 문자열Oracle은 '' = NULL. PG는 다름 → 데이터·조건 양쪽 점검
식별자 대소문자Oracle은 대문자로 저장, PG는 소문자 → 큰따옴표로 만든 객체가 문제
기본 격리 수준둘 다 READ COMMITTED 지만 구현이 다릅니다(⚙️ t11 · 🧬 z05)
DDL 트랜잭션Oracle은 자동 커밋, PG는 롤백 가능 → 마이그레이션 스크립트에 유리
NUMBERPG의 NUMERIC 은 정확하지만 느립니다 → 정수는 BIGINT 로
정렬 순서NLS_SORT vs COLLATE — 한글 정렬 결과가 달라질 수 있습니다

도구

  • ora2pg — 오라클 스키마·데이터·PL/SQL을 PostgreSQL로 변환. 변환 난이도 리포트를 먼저 뽑아 볼 수 있습니다
  • AWS SCT / DMS — 클라우드 이전과 함께 갈 때
  • orafce 확장 — PostgreSQL에서 오라클 함수(NVL·DECODE 등)를 흉내 내 코드 수정량을 줄입니다
현실적인 순서 — ① ora2pg 로 난이도 리포트를 뽑아 PL/SQL 양을 확인하고 ② 신규 기능부터 PostgreSQL로 만들고 ③ 읽기 전용 리포트를 옮겨 검증하고 ④ 마지막에 기간계를 옮깁니다. 한 번에 전부 옮기는 빅뱅 방식은 대부분 실패합니다.
