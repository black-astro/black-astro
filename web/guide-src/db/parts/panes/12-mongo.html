MongoDB —
표 대신
JSON 문서로

MongoDB는 데이터를 표가 아니라 JSON 문서로 저장하는 문서형 NoSQL입니다. 문서마다 구조가 달라도 되고, 관련 데이터를 한 문서에 통째로 담아 조인 없이 꺼냅니다. SQL을 아는 사람 기준으로 무엇이 어디에 대응되는지부터 시작합니다. (NoSQL 이 처음이라면 ⚡ Redis 탭 r01의 RDBMS 비교를 먼저 보세요.)

SECTION 01

MongoDB는 어떤 DB인가 — 용어 대응부터

SQL 용어와 1:1로 놓고 보면 절반은 이미 아는 것입니다. 다른 절반 — "조인 대신 내장" — 이 MongoDB의 진짜 차이입니다.

용어 대응표

RDBMSMongoDB설명
데이터베이스데이터베이스같은 개념입니다
테이블컬렉션(collection)문서들을 담는 그릇 — 구조 강제가 없습니다
행(row)문서(document)JSON 한 덩어리 (내부 저장은 BSON — 이진 JSON)
열(column)필드(field)문서마다 있어도, 없어도 됩니다
기본키(PK)_id모든 문서에 자동 생성(ObjectId) — 시간 정보 포함
JOIN내장(embed) 또는 $lookup기본 전략은 "미리 한 문서에 담기"
SQL쿼리 도큐먼트 · 집계 파이프라인{ city: "서울" } 처럼 JSON으로 조건을 씁니다

같은 데이터, 두 가지 저장 방식

RDBMS — 3개 표로 나눠서
member(id, name, city)
orders(id, member_id, ordered_at)
order_item(order_id, product, qty)
-- 조회할 때 JOIN 으로 다시 합친다
MongoDB — 문서 하나에 통째로
{
  _id: ObjectId("..."),
  name: "김하늘", city: "서울",
  orders: [
    { at: "2026-01-05",
      items: [{ p: "키보드", qty: 1 }] }
  ]
}
언제 MongoDB가 빛나나 — ① 데이터 구조가 자주 바뀌는 초기 서비스 (칸 추가에 ALTER TABLE이 없음), ② 상품 옵션·설문 응답처럼 항목마다 구조가 다른 데이터, ③ "이 화면에 필요한 것"을 문서 하나로 묶어 조인 없이 한 번에 읽는 조회 중심 워크로드. 반대로 여러 데이터에 걸친 정합성(돈·재고)이 핵심이면 RDBMS가 맞습니다 (n12).

도구 세 가지 — CLI는 mongosh, GUI는 공식 Compass(무료 — 쿼리·인덱스·실행계획까지), 클라우드는 Atlas(M0 무료 티어 — 설치 없이 시작, 백업·모니터링 포함). 학습이라면 도커 + Compass 조합을 권합니다.
MongoDB도 인증 없이 인터넷에 노출하면 몇 분 만에 털립니다. 과거 대규모 랜섬 사고의 단골이 인증 꺼진 MongoDB였습니다. 도커에서 위처럼 MONGO_INITDB_ROOT_* 를 반드시 넣고, 방화벽으로 27017을 막으세요. 라이선스는 SSPL — 서비스 백엔드로 쓰는 건 무료지만, "MongoDB 자체를 클라우드 서비스로 팔" 때만 제약이 있습니다.

CRUD — SQL과 나란히

네 가지 기본 동작을 SQL과 대조하면 문법이 바로 읽힙니다.

SQLMongoDB
INSERT INTO member VALUES (…)db.member.insertOne({ name: "김하늘" })
SELECT * FROM member WHERE city='서울'db.member.find({ city: "서울" })
SELECT name FROM memberdb.member.find({}, { name: 1, _id: 0 })
UPDATE member SET grade='GOLD' WHERE id=1db.member.updateOne({ _id: 1 }, { $set: { grade: "GOLD" } })

// 넣기 — 여러 건
db.member.insertMany([
  { name: "김하늘", grade: "GOLD",   city: "서울", joined: ISODate("2024-03-11") },
  { name: "박바다", grade: "SILVER", city: "부산", joined: ISODate("2024-07-02") },
  { name: "이구름", grade: "BASIC",  city: "서울" }   // 필드가 달라도 그냥 들어갑니다
])

// 고치기 — $set 을 빼먹으면 문서가 통째로 바뀝니다 (최대 함정!)
db.member.updateOne({ name: "이구름" }, { $set: { grade: "SILVER" } })  // ✅ 필드만 수정
db.member.updateOne({ name: "이구름" }, { grade: "SILVER" })            // ❌ 문서 전체가 {grade}만 남음(신버전은 에러)

// 갱신 연산자들
db.member.updateOne({ name: "김하늘" }, {
  $inc:  { points: 100 },          // 숫자 증가
  $push: { tags: "vip" },          // 배열에 추가
  $unset:{ tempField: "" }         // 필드 제거
})

// upsert — 있으면 수정, 없으면 삽입
db.counter.updateOne({ _id: "visits" }, { $inc: { n: 1 } }, { upsert: true })
updateOne vs updateMany — SQL의 UPDATE는 조건에 맞는 전부를 바꾸지만, MongoDB의 updateOne은 첫 한 건만 바꿉니다. "왜 하나만 바뀌지?"의 답은 대부분 이것입니다. 전부 바꾸려면 updateMany.
SECTION 04

쿼리 연산자 · 정렬 · 페이징

WHERE 절에 해당하는 연산자들입니다. $ 로 시작하는 키워드가 연산자입니다.

// 비교 — WHERE price >= 30000 AND price < 100000
db.product.find({ price: { $gte: 30000, $lt: 100000 } })

// IN — WHERE city IN ('서울','부산')
db.member.find({ city: { $in: ["서울", "부산"] } })

// OR — WHERE grade='GOLD' OR points > 1000
db.member.find({ $or: [ { grade: "GOLD" }, { points: { $gt: 1000 } } ] })

// 필드 존재 여부 · null (SQL 의 IS NULL 과 미묘하게 다릅니다)
db.member.find({ email: { $exists: false } })   // email 필드 자체가 없는 문서

// 배열 안에서 찾기 — tags 배열에 "vip" 가 들어 있는 문서
db.member.find({ tags: "vip" })

// 내장 문서 필드 — 점 표기법 (반드시 따옴표)
db.member.find({ "address.city": "서울" })

// 정렬 · 페이징 — ORDER BY joined DESC LIMIT 10 OFFSET 20
db.member.find().sort({ joined: -1 }).skip(20).limit(10)

// 세기 — SELECT COUNT(*)
db.member.countDocuments({ city: "서울" })
skip 페이징은 RDBMS의 OFFSET과 똑같은 약점이 있습니다 — skip(100000)은 10만 건을 세고 버립니다. 깊은 페이지는 find({ _id: { $gt: 마지막본_id } }).limit(10) 식의 커서 방식으로 — 원리는 ⚙️ 튜닝 탭 t09와 같습니다.
SECTION 05

문서 설계 — 내장 vs 참조

MongoDB 설계의 전부가 이 질문입니다 — "이 데이터를 문서 안에 넣을까(내장), 다른 컬렉션에 두고 id로 가리킬까(참조)?"

기준은 하나 — "같이 읽고, 개수가 유한하면 내장. 무한히 자라거나 따로도 쓰이면 참조."
상황선택
주소·옵션·설정 — 항상 부모와 같이 읽음, 몇 개 안 됨내장
주문 내역 — 계속 쌓임, 주문만 따로 조회·집계함참조 (별도 컬렉션)
댓글 — 보통 수십 개, 폭주 가능성 있음혼합 — 최근 10개는 내장 + 전체는 별도 컬렉션
작성자 이름을 게시글마다 표시참조 + 이름만 복사해 내장(비정규화) — 바뀌면 일괄 갱신
RDBMS 습관 그대로 컬렉션을 잘게 쪼개는 것이 초심자의 1번 실수입니다. 전부 참조로 만들면 조회마다 $lookup 파티가 벌어지고, MongoDB의 장점이 사라집니다. "화면(조회) 단위로 문서를 설계한다"가 문서형의 사고방식입니다.
SECTION 06

집계 파이프라인 — GROUP BY의 자리

집계는 파이프라인으로 씁니다 — 문서가 단계를 하나씩 통과하며 걸러지고($match) 묶이고($group) 정렬됩니다($sort). 

// SQL: SELECT city, COUNT(*) AS cnt, AVG(points) AS avg_pt
//      FROM member WHERE grade <> 'BASIC'
//      GROUP BY city HAVING COUNT(*) >= 2 ORDER BY cnt DESC
db.member.aggregate([
  { $match: { grade: { $ne: "BASIC" } } },     // WHERE  — 먼저 거른다 (인덱스 사용)
  { $group: {
      _id: "$city",                            // GROUP BY city
      cnt:    { $sum: 1 },                     // COUNT(*)
      avg_pt: { $avg: "$points" }              // AVG(points)
  }},
  { $match: { cnt: { $gte: 2 } } },            // HAVING
  { $sort:  { cnt: -1 } }                      // ORDER BY
])

$lookup — 그래도 조인이 필요할 때

// SQL: SELECT o.*, m.name FROM orders o JOIN member m ON m._id = o.memberId
db.orders.aggregate([
  { $lookup: {
      from: "member",            // 붙일 컬렉션
      localField: "memberId",    // orders 쪽 키
      foreignField: "_id",       // member 쪽 키
      as: "member"               // 결과가 배열로 담김
  }},
  { $unwind: "$member" }         // 배열 [ {…} ] → 객체로 펴기
])

자주 쓰는 단계 요약

단계SQL 대응
$matchWHERE — 파이프라인 맨 앞에 둬야 인덱스를 탑니다
$groupGROUP BY + 집계함수 ($sum · $avg · $min · $max · $push)
$sort / $limit / $skipORDER BY / LIMIT / OFFSET
$projectSELECT 절 — 필드 선택·계산 필드 생성
$unwind배열을 행으로 펴기 (배열 원소별 집계 전에)
$lookupLEFT JOIN
$lookup이 매 쿼리마다 나온다면 설계 신호입니다 — 그 데이터는 애초에 내장(n05)했어야 하거나, 애초에 RDBMS 일이었을 수 있습니다(n12). $lookup은 "가끔 필요한 리포트"용이지 "모든 조회의 기본"이 아닙니다.
SECTION 07

인덱스 — 원리는 RDBMS와 같다

B-Tree, 복합 인덱스의 컬럼 순서, "인덱스 안 타면 풀스캔" — ⚙️ 튜닝 탭에서 배운 원리가 그대로 적용됩니다. 문법만 다릅니다. 

db.member.createIndex({ email: 1 }, { unique: true })   // 유니크 인덱스
db.orders.createIndex({ memberId: 1, orderedAt: -1 })   // 복합 — 순서가 중요 (t05와 동일)
db.session.createIndex({ at: 1 }, { expireAfterSeconds: 1800 })  // TTL 인덱스 — 자동 삭제!
db.post.createIndex({ title: "text", body: "text" })    // 텍스트 검색용

db.member.getIndexes()          // 인덱스 목록
db.orders.find({ memberId: 1 }).explain("executionStats")   // 실행계획

explain에서 볼 것 두 가지

항목의미
stage: COLLSCAN풀스캔 — 인덱스를 못 탔습니다. RDBMS의 Seq Scan과 같은 경고
stage: IXSCAN인덱스 스캔 — 정상
totalDocsExamined vs nReturned살펴본 문서 수 vs 돌려준 수 — 차이가 크면 인덱스가 엉성한 것
TTL 인덱스는 Redis의 EXPIRE에 해당하는 기능입니다 — 세션·인증 토큰·임시 데이터를 "넣기만 하면 알아서 사라지게" 만듭니다. 배치로 지우는 코드를 짤 필요가 없습니다 (약 60초 주기로 백그라운드 삭제).
SECTION 08

트랜잭션과 일관성 — 어디까지 되나

"NoSQL은 트랜잭션이 없다"는 반쯤 옛말입니다. 핵심은 단일 문서 변경은 원래부터 원자적이라는 것 — 설계를 잘하면 트랜잭션이 거의 필요 없습니다.

  • 단일 문서 = 항상 원자적 — 문서 하나 안에서 필드 10개를 $set·$inc 로 바꾸는 것은 전부 되거나 전부 안 됩니다. 내장 설계(n05)를 잘하면 이것만으로 충분한 경우가 대부분입니다.
  • 여러 문서 트랜잭션 — 4.0+ 부터 지원합니다. 다만 성능 비용이 있고 복제 셋 구성이 필요하며, 이걸 매일 쓰고 있다면 데이터가 RDBMS 감이라는 신호입니다.
// 멀티 도큐먼트 트랜잭션 (계좌 이체 꼴)
const session = db.getMongo().startSession()
session.startTransaction()
try {
  const acc = session.getDatabase("bank").account
  acc.updateOne({ _id: "A" }, { $inc: { balance: -5000 } })
  acc.updateOne({ _id: "B" }, { $inc: { balance:  5000 } })
  session.commitTransaction()          // 둘 다 확정
} catch (e) {
  session.abortTransaction()           // 둘 다 취소
}

쓰기 확인 수준 — write concern

설정의미
w: 1프라이머리에 쓰이면 OK — 빠르지만 장애 승격 시 유실 가능

SECTION 09

복제 셋과 샤딩 — 운영 골격

운영 MongoDB는 복제 셋(replica set)이 기본 단위입니다. 한 대짜리 운영은 학습용으로만 쓰세요.

  • 복제 셋 — 프라이머리 1 + 세컨더리 2가 표준. 프라이머리가 죽으면 세컨더리들이 투표로 자동 승격합니다 (수십 초 내). 트랜잭션·majority 쓰기의 전제 조건이기도 합니다.
  • 읽기 분산 — 기본은 전부 프라이머리에서 읽습니다. readPreference=secondaryPreferred 로 세컨더리 읽기를 허용할 수 있지만 복제 지연만큼 낡은 데이터를 볼 수 있습니다 — 통계·목록처럼 낡아도 되는 조회에만.
  • 샤딩 — 컬렉션을 샤드 키 기준으로 여러 복제 셋에 분산합니다. 한 대의 디스크·쓰기 처리량을 넘어설 때의 카드이고, 샤드 키는 한번 정하면 바꾸기 어렵습니다 — 🧬 전문가 탭 z09의 샤딩 원칙이 그대로 적용됩니다.
Atlas를 쓰면 이 절이 버튼 몇 개가 됩니다 — 복제 셋 기본 제공, 백업·업그레이드·샤딩 자동화. 직접 운영과 관리형의 갈림길은 RDBMS와 같은 논리로 판단하세요: 운영 인력이 없으면 관리형이 거의 항상 쌉니다.
SECTION 10

스키마 검증과 안티패턴

"스키마가 없다"는 "아무거나 넣어도 된다"가 아닙니다. 구조는 코드와 검증 규칙으로 지켜야 하고, 안 지키면 쓰레기 데이터가 조용히 쌓입니다.

스키마 검증 — 컬렉션에 규칙 걸기

db.createCollection("member", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["name", "joined"],                  // 필수 필드
    properties: {
      name:   { bsonType: "string" },
      grade:  { enum: ["BASIC", "SILVER", "GOLD"] },
      points: { bsonType: "int", minimum: 0 }
    }
  }},
  validationAction: "error"      // 어기면 거부 ("warn" = 로그만)
})

안티패턴 4선

패턴왜 문제 · 대신
무한히 자라는 내장 배열로그·알림을 문서 안 배열에 계속 push → 16MB 한도 + 문서 이동 비용. 별도 컬렉션으로.
RDBMS처럼 전부 참조매 조회가 $lookup 잔치 — 문서형 장점 소멸. 화면 단위로 내장 설계(n05).
필드명이 데이터인 문서{ "2026-08-11": 값 } 꼴 — 인덱스·쿼리 불가. { date: …, value: … } 배열로.
검증도 버전 관리도 없음앱 코드 v1·v2가 다른 구조를 넣어 뒤죽박죽. validator + 문서에 schemaVersion 필드.

# pip install pymongo
from pymongo import MongoClient

client = MongoClient("mongodb://admin:devpass@localhost:27017/")  # 앱에서 1개만
db = client.shop

db.member.insert_one({"name": "김하늘", "grade": "GOLD"})
for m in db.member.find({"city": "서울"}).sort("joined", -1).limit(10):
    print(m["name"])

Java — Spring Data MongoDB

// implementation "org.springframework.boot:spring-boot-starter-data-mongodb"
// spring.data.mongodb.uri=mongodb://admin:devpass@localhost:27017/shop

@Document("member")
public record Member(@Id String id, String name, String grade) {}

public interface MemberRepo extends MongoRepository<Member, String> {
    List<Member> findByGrade(String grade);   // 메서드 이름이 곧 쿼리
}

SECTION 12

RDBMS와 같이 쓰기 — 무엇을 어디에

마지막 질문은 "MongoDB냐 PostgreSQL이냐"가 아니라 "이 데이터는 어느 쪽 성질인가"입니다. 한 서비스가 둘 다 쓰는 게 보통입니다.

데이터RDBMS로MongoDB로
주문 · 결제 · 재고 · 정산✓ 무조건 — 다중 행 정합성·ACID
회원 · 권한✓ 관계가 많고 정확해야 함
상품 카탈로그 (옵션이 제각각)가능 (JSONB)✓ 문서형이 자연스러움
로그 · 이벤트 · 센서 데이터✓ 대량 쓰기 + TTL + 유연 구조
사용자 생성 콘텐츠 (설문·양식)✓ 구조가 문서마다 다름
캐시 · 세션 · 순위표→ 둘 다 아님 — ⚡ Redis
"PostgreSQL JSONB로 충분한가?"를 먼저 물어보세요. 문서형 데이터가 일부라면 PostgreSQL 하나에 JSONB 컬럼(🐘 탭 p07)으로 담는 쪽이 운영할 시스템을 하나로 유지합니다. MongoDB가 이기는 지점은 대부분의 데이터가 문서형이고, 수평 확장·유연 스키마가 처음부터 요구될 때입니다.
