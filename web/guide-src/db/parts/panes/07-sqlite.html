설치도, 계정도, 포트도 없습니다. DB가 그냥 파일 하나이고 앱 안에 라이브러리로 들어갑니다. 스마트폰·브라우저·항공기 시스템까지 수조 개 규모로 배포돼 있습니다. 장난감이 아니라, 쓰임새가 다른 진짜 DB입니다.

SECTION 01

서버가 없는 DB

MySQL·PostgreSQL은 별도 프로그램(서버)이 떠 있고 앱이 네트워크로 요청합니다. SQLite는 앱 안에 들어간 라이브러리가 직접 파일을 읽고 씁니다.

SQLite 는 "가벼운 DB"라기보다 fopen 을 대신하는 저장 방식에 가깝습니다 — 경쟁 상대는 MySQL 이 아니라 직접 만든 파일 포맷입니다.
서버형 (MySQL · PostgreSQL)
[앱] --(TCP 5432)--> [DB 서버 프로세스] --> [파일]

· 서버를 설치·기동해야 함
· 계정·권한·포트·방화벽 필요
· 여러 앱이 동시에 안전하게 접근
· 네트워크 왕복 비용이 있음
임베디드 (SQLite)
[앱 + SQLite 라이브러리] --(함수 호출)--> [파일]

· 설치할 서버가 없음
· 계정·포트 개념 자체가 없음
· 접근 통제 = 파일 권한
· 네트워크 왕복이 0 (함수 호출)

어디에 이미 들어 있나

  • 모든 안드로이드·iOS 기기 — 앱 데이터 저장의 기본
  • 모든 주요 브라우저 — 내부 저장소
  • macOS · Windows 10 이상 — 시스템 곳곳에서 사용
  • 파이썬 — import sqlite3 만으로 바로 사용 (표준 라이브러리)
  • 항공기 · 자동차 · IoT 기기 — 임베디드 환경의 사실상 표준

언제 쓰고 언제 안 쓰나

판단상황
쓴다 모바일·데스크톱 앱의 로컬 저장 · CLI 도구의 설정과 캐시 · 읽기 위주 웹사이트 · 테스트 픽스처 · 데이터 분석용 임시 저장 · 엣지·IoT · 로그 수집기의 버퍼
안 쓴다 여러 서버가 동시에 쓰기 · 초당 수백 건 이상의 쓰기 · 사용자별 권한이 필요한 경우 · 네트워크 너머에서 접근해야 할 때 · 네트워크 파일시스템(NFS·SMB) 위 (락이 깨져 파일이 손상됩니다)
절대 하지 말 것 — 네트워크 드라이브 위의 SQLite. NFS·SMB·클라우드 동기화 폴더(드롭박스·원드라이브) 위에 DB 파일을 두면 파일 락이 제대로 동작하지 않아 데이터가 손상됩니다. SQLite 공식 문서가 명시적으로 경고하는 사항입니다.
SQLite 는 "MySQL 의 경쟁자"가 아닙니다. 공식 문서의 표현대로, SQLite 가 경쟁하는 대상은 fopen() 입니다. 즉 "파일에 직접 저장하는 것"의 대체재입니다. JSON·CSV 파일에 데이터를 저장하고 있다면, 그 자리가 SQLite 의 자리입니다.

.dot 명령 완전정복

점(.)으로 시작하는 명령이 sqlite3 CLI의 도구입니다. 세미콜론을 붙이지 않습니다.

명령하는 일
.tables테이블 목록
.schema memberCREATE 문 그대로 보기 (생략하면 전체)
.headers on컬럼 이름 표시 — 처음에 반드시 켜세요
.mode box표 형태 출력 (table·markdown·json·csv 등)
.import data.csv member --csvCSV 가져오기
.output result.csv결과를 파일로 (다시 화면으로는 .output stdout)
.once result.csv다음 한 번만 파일로
.backup backup.db★ 안전한 백업 (파일 복사와 다릅니다)
.dump전체를 SQL 텍스트로 (다른 DB로 옮길 때)
.read script.sqlSQL 파일 실행
.timer on실행 시간 표시
.expert인덱스 추천 (실험적 기능)

.help전체 명령 목록
.quit종료

sqlite3 shop.db
sqlite> .headers on
sqlite> .mode box
sqlite> SELECT * FROM member LIMIT 3;
┌────┬────────┬───────┬────────┐ │ id │ name │ grade │ city │ ├────┼────────┼───────┼────────┤ │ 1 │ 김하늘 │ GOLD │ 서울 │ │ 2 │ 박바다 │ SILVER│ 부산 │ └────┴────────┴───────┴────────┘

CSV 를 다루는 도구로도 훌륭합니다

# 큰 CSV 를 SQL 로 분석하기 (엑셀이 못 여는 크기도 됩니다)
sqlite3 :memory: <<'EOF'
.mode csv
.import sales.csv sales
.headers on
.mode box
SELECT region, count(*) AS 건수, sum(amount) AS 합계
FROM sales GROUP BY region ORDER BY 합계 DESC;
EOF
설정 파일로 기본값 지정 — 홈 디렉터리에 ~/.sqliterc 를 만들고 .headers on · .mode box 를 넣어 두면 매번 칠 필요가 없습니다.
SQL 이 여러 줄일 때 — 세미콜론을 칠 때까지 프롬프트가 ...> 로 바뀌며 기다립니다. 빠져나오려면 세미콜론을 치거나 Ctrl+C 를 누르세요.
SECTION 04

동적 타입 시스템

SQLite는 숫자 컬럼에 글자를 넣어도 받아 줍니다. 편리하다고 볼 수도, 위험하다고 볼 수도 있습니다 — 그리고 대개는 위험합니다. 

CREATE TABLE t (n INTEGER, s TEXT);

INSERT INTO t VALUES ('안녕', 12345);     -- 에러가 안 납니다!
SELECT n, typeof(n), s, typeof(s) FROM t;
n typeof(n) s typeof(s) 안녕 text 12345 integer
타입 친화도(Type Affinity) — SQLite는 컬럼에 선호 타입만 두고, 값이 변환 가능하면 변환하고 아니면 그대로 저장합니다. INTEGER 컬럼에 '123' 을 넣으면 숫자 123으로 바뀌지만, '안녕' 은 텍스트로 저장됩니다.
저장 클래스설명
NULL빈 값
INTEGER부호 있는 정수 (1~8바이트 가변)
REAL8바이트 부동소수점
TEXT문자열 (UTF-8/16)
BLOB바이너리 그대로

BOOLEAN·DATE·DATETIME 타입은 없습니다. BOOLEAN 은 0/1 정수로, 날짜는 TEXT('2026-08-05') 또는 숫자로 저장합니다.

STRICT 테이블 — 타입을 강제하기 3.37+

CREATE TABLE t (
    n INTEGER NOT NULL,
    s TEXT    NOT NULL
) STRICT;

INSERT INTO t VALUES ('안녕', 123);
-- Error: cannot store TEXT value in INTEGER column t.n   ← 이제 막힙니다
새로 만드는 테이블은 STRICT 를 쓰세요. 다른 DB에서 온 사람이 기대하는 동작이 되고, 데이터 오염을 예방합니다. STRICT 테이블에서 쓸 수 있는 타입은 INT · INTEGER · REAL · TEXT · BLOB · ANY 뿐입니다 (VARCHAR(50) 같은 표기는 못 씁니다).

CHECK 제약으로 방어하기

CREATE TABLE member (
    id     INTEGER PRIMARY KEY,
    name   TEXT    NOT NULL CHECK (length(name) BETWEEN 1 AND 50),
    email  TEXT    UNIQUE   CHECK (email LIKE '%_@_%'),
    age    INTEGER          CHECK (age IS NULL OR (age >= 0 AND age < 150)),
    grade  TEXT    NOT NULL DEFAULT 'BASIC'
                            CHECK (grade IN ('BASIC','SILVER','GOLD')),
    joined TEXT    NOT NULL CHECK (joined GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]')
) STRICT;
SQLite에는 ENUM 이 없으므로 CHECK (col IN (…)) 이 그 역할을 합니다. 날짜 형식도 GLOB 패턴으로 강제할 수 있습니다. 타입이 느슨한 만큼 제약으로 채우는 것이 SQLite 설계의 요령입니다.
SQLite 로 만든 데이터를 다른 DB 로 옮길 때 가장 자주 터지는 지점입니다.
SECTION 05

ROWID · AUTOINCREMENT · UPSERT

SQLite 특유의 기본키 구조를 이해하면 불필요한 설정을 안 하게 됩니다.

모든 행에는 숨은 번호가 있습니다

CREATE TABLE t (name TEXT);
INSERT INTO t VALUES ('a'), ('b');
SELECT rowid, name FROM t;         -- rowid 는 자동으로 존재합니다
rowid name 1 a 2 b
-- INTEGER PRIMARY KEY 로 선언하면 그것이 곧 rowid 가 됩니다 (별도 저장 없음)
CREATE TABLE member (
    id   INTEGER PRIMARY KEY,      -- ★ 자동 증가합니다. AUTOINCREMENT 불필요
    name TEXT NOT NULL
);
INSERT INTO member (name) VALUES ('김하늘');
SELECT last_insert_rowid();
INTEGER PRIMARY KEY 와 INT PRIMARY KEY 는 다릅니다. 정확히 INTEGER 라고 써야 rowid 별칭이 되어 자동 증가합니다. INT PRIMARY KEY 로 쓰면 일반 컬럼이 되어 값을 직접 넣어야 합니다. 다른 DB에서 온 사람이 가장 자주 걸리는 함정입니다.

AUTOINCREMENT 는 대부분 불필요합니다

구분동작
INTEGER PRIMARY KEY 사용 중인 최대값 + 1. 삭제된 번호를 재사용할 수 있습니다
INTEGER PRIMARY KEY AUTOINCREMENT 번호를 절대 재사용하지 않습니다. 대신 별도 테이블(sqlite_sequence)을 유지해 삽입이 느려집니다
번호가 재사용되면 안 되는 경우(외부 시스템이 그 번호를 기억하는 등)에만 AUTOINCREMENT 를 쓰세요. 그 외에는 성능만 손해입니다.

WITHOUT ROWID — 특수한 최적화

CREATE TABLE kv (
    k TEXT PRIMARY KEY,
    v TEXT
) WITHOUT ROWID;
-- 기본키가 문자열이고, 기본키로만 조회하는 표에서 공간·속도 이득
-- (rowid 인덱스를 따로 유지하지 않음)

UPSERT 3.24+

INSERT INTO stock (product_id, qty) VALUES (10, 5)
ON CONFLICT (product_id) DO UPDATE SET qty = qty + excluded.qty;

INSERT INTO tag (name) VALUES ('sale') ON CONFLICT DO NOTHING;

-- RETURNING 도 지원합니다 (3.35+)
INSERT INTO member (name) VALUES ('한바다') RETURNING id, name;

-- 충돌 처리 방식 지정
INSERT OR IGNORE  INTO t VALUES (...);   -- 충돌하면 건너뜀
INSERT OR REPLACE INTO t VALUES (...);   -- ⚠️ DELETE 후 INSERT — 주의
INSERT OR ABORT   INTO t VALUES (...);   -- 기본값 (에러)
INSERT OR REPLACE 는 UPSERT 가 아닙니다. 기존 행을 지우고 새로 넣습니다. 지정하지 않은 컬럼은 기본값으로 초기화되고, 외래키 CASCADE 가 걸린 자식 행이 같이 삭제될 수 있습니다. 항상 ON CONFLICT DO UPDATE 를 쓰세요.
SECTION 06

날짜 · 문자열 함수

날짜 타입이 없으므로 저장 형식을 팀에서 먼저 정하는 것이 중요합니다.

날짜 저장 — 세 가지 방식

방식예평가
ISO 문자열'2026-08-05 14:30:00' ★ 권장. 사람이 읽을 수 있고 문자열 정렬 = 시간 정렬
유닉스 초1785000000공간 절약·계산 편함. 사람이 못 읽음
율리우스일2461258.1거의 안 씁니다
SELECT date('now')                          AS 오늘,        -- 2026-08-05
       datetime('now')                      AS 현재UTC,
       datetime('now','localtime')           AS 현재로컬,
       datetime('now','+9 hours')            AS 한국시각,
       date('now','start of month')          AS 이번달1일,
       date('now','start of month','+1 month','-1 day') AS 이번달말일,
       date('now','+7 days')                 AS 일주일후,
       strftime('%Y-%m', 'now')              AS 연월,
       strftime('%s', 'now')                 AS 유닉스초,
       julianday('now') - julianday('2026-01-01') AS 올해경과일;

-- 기간 조회 (문자열 비교가 그대로 시간 비교가 됩니다)
SELECT * FROM orders
WHERE  ordered_at >= '2026-08-01' AND ordered_at < '2026-09-01';
ISO 문자열의 장점 — '2026-08-05' < '2026-08-06' 이 문자열 비교로도 정확히 동작합니다. 인덱스도 그대로 탑니다. 날짜를 문자열로 저장할 때는 반드시 YYYY-MM-DD 형식을 지키세요 (2026-8-5 처럼 자릿수를 안 맞추면 정렬이 깨집니다).

기본 컬럼값

CREATE TABLE log (
    id         INTEGER PRIMARY KEY,
    msg        TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))     -- 괄호가 필요합니다
);
-- SQLite 에는 ON UPDATE CURRENT_TIMESTAMP 가 없습니다 → 트리거로 구현
CREATE TRIGGER trg_member_updated
AFTER UPDATE ON member
BEGIN
    UPDATE member SET updated_at = datetime('now') WHERE id = NEW.id;
END;

문자열 함수

SELECT length('안녕하세요')          AS 글자수,     -- 5 (UTF-8 글자 기준)
       upper('abc'), lower('ABC'),
       substr('데이터베이스', 1, 3)   AS 앞3글자,
       replace('a-b-c', '-', '/')     AS 치환,
       trim('  x  ')                  AS 공백제거,
       'a' || 'b'                     AS 결합,
       instr('abcdef', 'cd')          AS 위치,       -- 3
       printf('%05d', 42)             AS 자리채움,   -- 00042
       hex(randomblob(16))            AS 랜덤ID,
       group_concat(name, ', ')       AS 목록
FROM   member;

-- 정규식은 기본 제공되지 않습니다 (앱에서 함수를 등록해야 동작)
-- 대신 GLOB · LIKE 를 씁니다
SELECT * FROM member WHERE name GLOB '김*';       -- 대소문자 구분
SELECT * FROM member WHERE name LIKE '김%';       -- ASCII 는 대소문자 무시
SECTION 07

PRAGMA — 설정이 곧 성능

SQLite의 설정 스위치입니다. 기본값이 안전 위주라 느립니다 — 그리고 외래키가 기본으로 꺼져 있습니다.

외래키가 기본으로 동작하지 않습니다. FOREIGN KEY 를 선언해도 연결마다 PRAGMA foreign_keys = ON; 을 실행하지 않으면 제약이 무시됩니다. 존재하지 않는 회원의 주문이 그대로 들어갑니다. (하위 호환 때문에 기본값을 못 바꾸고 있습니다) 
-- 연결할 때마다 실행해야 하는 것들 (앱 시작 코드에 넣으세요)
PRAGMA foreign_keys = ON;          -- ★ 외래키 활성화
PRAGMA journal_mode = WAL;         -- ★ 동시성 개선 (파일에 한 번만 설정되면 유지)
PRAGMA synchronous = NORMAL;       -- WAL 과 함께 쓰면 안전하면서 빠릅니다
PRAGMA busy_timeout = 5000;        -- ★ 락 대기 5초 (기본 0 = 즉시 실패)
PRAGMA cache_size = -64000;        -- 64MB (음수 = KB 단위)
PRAGMA temp_store = MEMORY;
PRAGMA설명
journal_mode DELETE(기본) → WAL 로 바꾸면 읽기·쓰기가 서로 안 막습니다 (s08)
synchronous FULL(기본·가장 안전) · NORMAL(WAL과 조합 시 권장) · OFF(빠르지만 정전 시 손상 가능)
busy_timeout 다른 연결이 잠갔을 때 몇 ms 기다릴지. 0이면 즉시 "database is locked"
foreign_keys외래키 제약 활성화 — 연결마다 필요
cache_size페이지 캐시 크기
mmap_size메모리 맵 IO 크기 — 읽기 위주에서 성능 향상
optimize연결을 닫기 전 실행하면 통계를 갱신합니다 (권장)
integrity_check파일 손상 검사
# 파이썬에서 연결할 때마다 적용하는 표준형
import sqlite3

def connect(path):
    conn = sqlite3.connect(path, timeout=5.0)
    conn.execute("PRAGMA foreign_keys = ON")
    conn.execute("PRAGMA journal_mode = WAL")
    conn.execute("PRAGMA synchronous = NORMAL")
    conn.execute("PRAGMA busy_timeout = 5000")
    conn.row_factory = sqlite3.Row        # 딕셔너리처럼 접근
    return conn
PRAGMA synchronous = OFF 는 위험합니다. 쓰기가 몇 배 빨라지지만 전원이 나가면 DB 파일이 손상될 수 있습니다. "다시 만들면 되는" 캐시나 테스트에서만 쓰세요. WAL + NORMAL 조합이면 충분히 빠르고 안전합니다.
SECTION 08

WAL 모드와 동시성

기본 저널 모드에서는 쓰는 동안 아무도 못 읽습니다. WAL로 바꾸면 읽기와 쓰기가 서로를 막지 않습니다 — 실전 앱에서는 거의 필수입니다.

SQLite 로 실제 앱을 만든다면 PRAGMA journal_mode=WAL 한 줄이 체감 성능의 절반을 결정합니다.
DELETE 모드 (기본)
· 쓰기 전에 원본을 롤백 저널에 복사
· 쓰는 동안 읽기 차단
· 읽는 동안 쓰기 차단
· 파일: shop.db + shop.db-journal
WAL 모드
· 변경분을 별도 WAL 파일에 추가
· 읽기와 쓰기가 서로 안 막음
· 쓰기는 여전히 한 번에 하나
· 파일: shop.db + shop.db-wal + shop.db-shm
PRAGMA journal_mode = WAL;      -- 한 번 설정하면 파일에 저장되어 유지됩니다
PRAGMA journal_mode;            -- 확인 → wal

-- WAL 파일이 커지면 체크포인트로 본 파일에 반영
PRAGMA wal_checkpoint(TRUNCATE);

-- 자동 체크포인트 기준 (기본 1000 페이지)
PRAGMA wal_autocheckpoint = 1000;
WAL 모드의 제약
① 네트워크 파일시스템에서 동작하지 않습니다(공유 메모리를 쓰기 때문)
② DB 파일 하나가 세 개 파일(.db, -wal, -shm)이 됩니다 — 복사할 때 셋을 함께 옮기거나, 안전하게 .backup 을 쓰세요
③ 읽기 트랜잭션이 오래 열려 있으면 체크포인트가 밀려 WAL 파일이 무한정 커집니다

쓰기는 여전히 한 번에 하나입니다

WAL이 동시성을 크게 개선하지만, 쓰기 트랜잭션은 여전히 전체에서 한 번에 하나입니다. (테이블 단위도 아니고 DB 파일 전체 기준입니다) 초당 수백 건의 쓰기가 서로 다른 프로세스에서 들어오면 대기가 발생합니다.

쓰기가 몰리는 앱의 대처
① 쓰기를 한 프로세스·스레드로 모으기(큐를 두고 직렬화)
② 트랜잭션으로 묶기 — 1000건을 개별 커밋하면 1000번 디스크 동기화가 일어납니다
③ busy_timeout 을 넉넉히 두고 재시도
④ 그래도 부족하면 서버형 DB로 이전을 검토 
# 트랜잭션으로 묶기 — 이 차이가 수백 배입니다
import sqlite3, time

conn = sqlite3.connect("bench.db")
conn.execute("CREATE TABLE IF NOT EXISTS t (v INTEGER)")

# ✗ 건별 커밋 : 10,000건에 수십 초
t0 = time.time()
for i in range(10_000):
    conn.execute("INSERT INTO t VALUES (?)", (i,))
    conn.commit()
print("건별 커밋", round(time.time() - t0, 2), "초")

# ✓ 한 트랜잭션 : 같은 건수에 0.1초 미만
t0 = time.time()
with conn:                                    # 블록이 끝나면 자동 커밋
    conn.executemany("INSERT INTO t VALUES (?)", ((i,) for i in range(10_000)))
print("일괄 커밋", round(time.time() - t0, 2), "초")

FTS5 — 전문 검색

-- 가상 테이블로 만듭니다
CREATE VIRTUAL TABLE post_fts USING fts5(
    title, body,
    tokenize = 'trigram'          -- ★ 한국어는 trigram 또는 unicode61 을 씁니다
);

INSERT INTO post_fts (title, body) VALUES
 ('SQLite 입문', 'SQLite 는 서버가 없는 데이터베이스입니다'),
 ('인덱스 이야기', 'B-Tree 인덱스는 탐색을 빠르게 합니다');

-- 검색
SELECT * FROM post_fts WHERE post_fts MATCH '데이터베이스';
SELECT * FROM post_fts WHERE post_fts MATCH 'SQLite AND 서버';

-- 랭킹 순 + 하이라이트
SELECT title, snippet(post_fts, 1, '<b>', '</b>', '…', 20) AS 발췌, rank
FROM   post_fts
WHERE  post_fts MATCH '인덱스'
ORDER  BY rank;
한국어에는 tokenize='trigram' 을 쓰세요(3.34+). 3글자 단위로 색인하므로 조사가 붙어도 부분 일치가 잘 걸립니다. 기본 unicode61 토크나이저는 공백 기준이라 한국어에 잘 맞지 않습니다. 
-- 원본 테이블과 연동 (external content 방식 — 중복 저장을 피합니다)
CREATE VIRTUAL TABLE post_fts USING fts5(
    title, body, content='post', content_rowid='id', tokenize='trigram'
);

-- 원본이 바뀔 때 색인을 따라가게 하는 트리거
CREATE TRIGGER post_ai AFTER INSERT ON post BEGIN
  INSERT INTO post_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;
CREATE TRIGGER post_ad AFTER DELETE ON post BEGIN
  INSERT INTO post_fts(post_fts, rowid, title, body) VALUES('delete', old.id, old.title, old.body);
END;
CREATE TRIGGER post_au AFTER UPDATE ON post BEGIN
  INSERT INTO post_fts(post_fts, rowid, title, body) VALUES('delete', old.id, old.title, old.body);
  INSERT INTO post_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;

SECTION 11

database is locked 해결

SQLite 질문 1위입니다. 원인은 몇 가지로 정해져 있고, 대부분 설정 두 줄로 해결됩니다.

원인해결
다른 연결이 쓰기 중 PRAGMA busy_timeout = 5000 — 기본값 0이라 즉시 실패합니다
기본 저널 모드 PRAGMA journal_mode = WAL — 읽기가 쓰기를 막지 않게
트랜잭션을 안 닫음 커밋·롤백을 빠뜨린 연결이 락을 붙들고 있습니다. with 문·try/finally 로 보장하세요
커서를 닫지 않음 결과를 끝까지 읽지 않은 커서가 읽기 락을 유지합니다
여러 스레드가 한 연결 공유 연결은 스레드마다 따로 만드세요
네트워크 드라이브 락이 동작하지 않습니다 — 로컬 디스크로 옮기세요
긴 쓰기 트랜잭션 대량 작업을 청크로 나누고 중간에 커밋하세요
"database is locked" 의 대부분은 버그가 아니라 기다릴 줄 모르는 기본 설정 때문입니다.
# 파이썬에서 안전하게 쓰는 형태
import sqlite3, threading

local = threading.local()

def conn():
    if not hasattr(local, "c"):                 # ★ 스레드마다 별도 연결
        c = sqlite3.connect("shop.db", timeout=5.0)
        c.execute("PRAGMA journal_mode=WAL")
        c.execute("PRAGMA busy_timeout=5000")
        c.execute("PRAGMA foreign_keys=ON")
        local.c = c
    return local.c

def add_order(member_id):
    c = conn()
    with c:                                     # 예외가 나면 자동 롤백, 정상이면 커밋
        c.execute("INSERT INTO orders (member_id) VALUES (?)", (member_id,))

쓰기 트랜잭션은 처음부터 BEGIN IMMEDIATE 로

-- ✗ 기본 BEGIN 은 지연 트랜잭션 :
--    읽기로 시작했다가 쓰기로 승격할 때 다른 세션과 충돌해
--    SQLITE_BUSY 가 나고 롤백해야 합니다
BEGIN;
SELECT qty FROM stock WHERE id = 1;
UPDATE stock SET qty = qty - 1 WHERE id = 1;   -- ← 여기서 실패 가능
COMMIT;

-- ✓ 쓸 것을 알면 처음부터 쓰기 락을 잡습니다
BEGIN IMMEDIATE;
SELECT qty FROM stock WHERE id = 1;
UPDATE stock SET qty = qty - 1 WHERE id = 1;
COMMIT;
이것이 실무에서 가장 효과적인 대책입니다. "읽고 나서 쓰는" 트랜잭션은 반드시 BEGIN IMMEDIATE 로 시작하세요. 파이썬 sqlite3 에서는 sqlite3.connect(..., isolation_level="IMMEDIATE") 로 지정합니다.
파이썬 3.12 이전의 sqlite3 는 자동 커밋 동작이 특이합니다. DML 앞에서 암묵적으로 트랜잭션을 열고, DDL 앞에서는 커밋해 버립니다. 혼란을 피하려면 isolation_level=None 으로 두고 트랜잭션을 직접 BEGIN/COMMIT 하는 편이 명확합니다. (3.12+ 에서는 autocommit 속성이 추가되어 표준에 가까워졌습니다)
SECTION 12

백업 · 무결성 · 암호화

쓰는 중에 파일을 그냥 복사하면 깨집니다. 안전한 방법을 씁니다. 

# ✓ 안전한 백업 (온라인 백업 API 사용 — 쓰기 중에도 일관된 사본)
sqlite3 shop.db ".backup 'backup-$(date +%F).db'"

# ✓ VACUUM INTO — 조각 모음까지 하며 새 파일로 (3.27+)
sqlite3 shop.db "VACUUM INTO 'clean.db';"

# ✓ SQL 텍스트로 (다른 DB로 옮길 때·버전 관리용)
sqlite3 shop.db .dump > shop.sql
sqlite3 new.db < shop.sql

# ✗ 위험 : 쓰기 중이면 손상된 사본이 만들어집니다
cp shop.db backup.db
# 파이썬 백업 API (진행률 표시 가능)
import sqlite3
src = sqlite3.connect("shop.db")
dst = sqlite3.connect("backup.db")
with dst:
    src.backup(dst, pages=100, progress=lambda s, r, t: print(f"{t-r}/{t}"))
dst.close(); src.close()

암호화

기본 SQLite에는 암호화 기능이 없습니다. 파일을 열면 내용이 그대로 보입니다. 필요하다면 다음 중 하나를 씁니다.

방법설명
SQLCipher가장 널리 쓰이는 오픈소스 암호화 빌드. 모바일 앱에서 표준
SEESQLite 개발사의 공식 유료 확장
OS 전체 디스크 암호화모바일·노트북이라면 이미 적용돼 있을 수 있습니다 — 먼저 확인
애플리케이션 레벨민감한 컬럼만 앱에서 암호화해 저장
모바일 앱의 SQLite 는 그냥 읽힐 수 있습니다. 루팅·탈옥된 기기나 백업 파일에서 DB를 꺼내면 내용이 그대로 보입니다. 토큰·개인정보를 SQLite 평문으로 저장하지 마세요. OS 키체인(iOS Keychain · Android Keystore)을 쓰거나 SQLCipher 를 적용하세요.
SECTION 13

어디까지 써도 되나

"SQLite는 장난감"이라는 말은 사실이 아닙니다. 다만 한계는 분명합니다.

공식 한계 (사실상 안 걸립니다)

항목한계
DB 파일 최대 크기281TB (기본 페이지 크기 기준)
테이블 행 수사실상 무제한 (2^64)
컬럼 수기본 2,000 (최대 32,767)
문자열·BLOB 크기기본 1GB
동시 읽기 연결제한 없음
동시 쓰기 연결사실상 1개 (DB 파일 단위)

현실적인 판단 기준

🟢 문제없음
  • 읽기 위주 웹사이트 (초당 수백~수천 조회)
  • 데이터 수 GB, 수천만 행
  • 단일 서버에서 동작하는 앱
  • 쓰기가 초당 수십 건 이하
🔵 설계가 필요
  • 쓰기가 초당 수백 건 — 배치·큐로 직렬화
  • 여러 프로세스가 동시에 쓰기
  • 장시간 도는 분석 쿼리와 쓰기가 공존
  • WAL + busy_timeout 필수
🟣 다른 DB로
  • 여러 서버에서 같은 DB에 쓰기
  • 네트워크 너머 접근이 필요
  • 사용자별 세밀한 권한 관리
  • 고가용성·자동 페일오버 요구
  • 쓰기가 지속적으로 초당 1,000건 이상
실제 사례 — 여러 서비스가 SQLite 로 상당한 트래픽을 처리합니다. 핵심은 "읽기는 무제한, 쓰기는 하나"라는 특성에 맞게 설계하는 것입니다. 읽기가 압도적이면 SQLite가 네트워크 왕복이 없어 오히려 더 빠릅니다.

언어·플랫폼별로 SQLite를 붙이는 실제 코드입니다.

Python — 표준 라이브러리

import sqlite3
from contextlib import closing

conn = sqlite3.connect("shop.db", timeout=5.0, isolation_level="IMMEDIATE")
conn.row_factory = sqlite3.Row                 # 컬럼명으로 접근
for p in ("journal_mode=WAL", "foreign_keys=ON", "busy_timeout=5000"):
    conn.execute(f"PRAGMA {p}")

with conn:                                     # 자동 커밋 · 예외 시 롤백
    conn.execute("INSERT INTO member (name) VALUES (?)", ("김하늘",))

with closing(conn.execute("SELECT id, name FROM member WHERE grade = ?", ("GOLD",))) as cur:
    for row in cur:
        print(row["id"], row["name"])

Node.js — better-sqlite3 (동기 · 빠름)

import Database from 'better-sqlite3';

const db = new Database('shop.db');
db.pragma('journal_mode = WAL');
db.pragma('foreign_keys = ON');

const insert = db.prepare('INSERT INTO member (name) VALUES (?)');
const many = db.transaction((names) => {       // 트랜잭션으로 묶기
  for (const n of names) insert.run(n);
});
many(['김하늘', '박바다']);

const rows = db.prepare('SELECT id, name FROM member WHERE grade = ?').all('GOLD');
console.log(rows);
Node 22+ 에는 node:sqlite 가 내장되어 별도 설치 없이 쓸 수 있습니다. 다만 아직 기능이 제한적이라, 실무에서는 better-sqlite3 가 여전히 표준입니다. 비동기 API가 필요하면 node-sqlite3 를 쓰지만, SQLite 는 로컬 파일 IO 라 동기 API 가 대개 더 빠릅니다.

Java — JDBC

// build.gradle : implementation 'org.xerial:sqlite-jdbc:3.50.x'
String url = "jdbc:sqlite:shop.db";
try (Connection c = DriverManager.getConnection(url)) {
    try (Statement s = c.createStatement()) {
        s.execute("PRAGMA journal_mode=WAL");
        s.execute("PRAGMA foreign_keys=ON");
    }
    c.setAutoCommit(false);
    try (PreparedStatement ps = c.prepareStatement("INSERT INTO member (name) VALUES (?)")) {
        ps.setString(1, "김하늘");
        ps.executeUpdate();
    }
    c.commit();
}
