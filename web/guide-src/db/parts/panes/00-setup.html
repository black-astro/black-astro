DB 를 처음 시작하는 사람이 막히는 곳은 문법이 아니라 설치와 접속입니다. "무엇을 깔아야 하나", "받은 파일을 어디까지 눌러야 하나", "깔았는데 왜 접속이 안 되나", "내 파이썬 코드에서는 무슨 패키지를 설치하나" — 이 탭 하나에 그 전부를 모았습니다. 어떤 DB 를 깔 것인가 — 7개 제품 한 장 비교

한 단계 더 — "관계형 하나 + 보조 하나"가 표준 구성 🟡 중급

고르는 게 아니라 겹쳐 쓰는 것들

초보자가 자주 하는 질문이 "PostgreSQL 이 좋아요, MongoDB 가 좋아요?"인데 둘은 경쟁 관계가 아닙니다. 실무의 표준 구성은 이렇습니다.

자리무엇을 놓나
본체관계형 하나 — 회원·주문·결제처럼 틀리면 안 되는 데이터
캐시Redis — 자주 읽지만 조금 늦어도 되는 값, 로그인 세션
로그·문서MongoDB 또는 관계형의 JSON 타입 — 모양이 자주 바뀌는 것
파일DB 가 아니라 스토리지(S3 등) — 이미지를 DB 에 넣지 않습니다
처음부터 다 깔지 마세요. 관계형 하나로 시작해서 "이 쿼리가 너무 자주 돈다"가 눈에 보일 때 Redis 를 붙이는 순서가 맞습니다. PostgreSQL 은 JSONB(p07)로 문서형 흉내도 상당 부분 냅니다.

도커가 난이도를 평평하게 만듭니다 — 이미지 제작자가 위의 "설치 후 할 일"을 환경 변수 몇 개로 미리 처리해 두었기 때문입니다. 오라클조차 docker run 한 줄이면 뜹니다(st03).
한 가지만 경고합니다 — "운영 DB 를 내 PC 에 깐다"는 생각은 하지 마세요. 이 탭에서 만드는 것은 전부 개발용 로컬 환경입니다. 실제 서비스용 DB 는 백업·이중화·모니터링·보안이 붙어야 하고(z15, z14), 요즘은 대부분 클라우드 관리형(RDS · Cloud SQL · Azure Database)을 씁니다. 로컬은 마음껏 부수고 다시 만드는 실험실로 쓰는 게 맞습니다.
SETUP 02

Docker Desktop 설치 — DB 설치의 난이도를 평평하게

DB 설치가 어려운 이유는 제품마다 마법사가 다르고, 깔고 나면 지우기도 어렵기 때문입니다. 도커는 그 전부를 명령 한 줄로 바꿉니다. DB 하나를 배우려고 도커를 배우는 게 손해 같지만, 도커를 30분 배워 두면 이 가이드의 모든 DB 를 3분 만에 띄울 수 있습니다. 정말 남는 장사입니다.

도커의 가치는 빠르기가 아니라 되돌릴 수 있음입니다 — 망쳐도 30초면 새것으로 시작합니다.

Windows — WSL2 부터 켜야 합니다

"Docker Desktop 이 시작되지 않습니다" 의 90%는 맨 아래 두 층 문제입니다 — st12 참고.

SETUP 03

도커로 DB 띄우기 — 한 줄 명령과 compose 완전판

여기가 이 탭의 핵심입니다. 아래 명령을 그대로 복사해 붙이면 DB 가 뜹니다. 다만 한 줄 명령은 컨테이너를 지우면 데이터도 사라진다는 함정이 있어서, 실제로는 볼륨을 붙이고 compose.yml 파일로 관리합니다. 둘 다 보여 드립니다.

초보자가 가장 많이 겪는 사고는 볼륨 없이 띄운 DB 를 지우고 데이터를 날리는 것입니다.

DB 별 한 줄 실행 — 복사해서 쓰세요

관계형 4종

# 🐘 PostgreSQL — 이 탭의 기본값
docker run -d --name pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_USER=app -e POSTGRES_DB=appdb \
  -v pgdata:/var/lib/postgresql/data \
  postgres:18

# 🐬 MySQL — 한글 안 깨지게 문자셋을 명령에 박습니다
docker run -d --name my -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=devpass \
  -e MYSQL_DATABASE=appdb -e MYSQL_USER=app -e MYSQL_PASSWORD=devpass \
  -v mydata:/var/lib/mysql \
  mysql:8.4 --character-set-server=utf8mb4 \
            --collation-server=utf8mb4_0900_ai_ci

# 🐬 MariaDB (MySQL 대신)
docker run -d --name maria -p 3307:3306 \
  -e MARIADB_ROOT_PASSWORD=devpass -e MARIADB_DATABASE=appdb \
  -v mariadata:/var/lib/mysql mariadb:11.8

# 🟦 SQL Server — 비밀번호 규칙이 까다롭습니다(대소문자+숫자+기호 8자+)
docker run -d --name mssql -p 1433:1433 \
  -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=DevPass!234" \
  -v mssqldata:/var/opt/mssql \

실무형 — compose.yml 한 파일로 관리

초기 SQL 자동 실행 — ./initdb 폴더

-- initdb/01-schema.sql  (파일 이름 순서대로 실행됩니다)
CREATE TABLE member (
  id         bigserial PRIMARY KEY,
  email      varchar(120) NOT NULL UNIQUE,
  name       varchar(60)  NOT NULL,
  created_at timestamptz  NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id        bigserial PRIMARY KEY,
  member_id bigint  NOT NULL REFERENCES member(id),
  amount    numeric(12,2) NOT NULL CHECK (amount >= 0),
  ordered_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_member ON orders(member_id, ordered_at DESC);
-- initdb/02-seed.sql
INSERT INTO member (email, name) VALUES
  ('kim@example.com', '김현우'),
  ('lee@example.com', '이지은');
딱 한 번만 실행됩니다 — 데이터 볼륨이 비어 있을 때에만 돕니다. SQL 을 고치고 다시 반영하려면 docker compose down -v 후 up -d 입니다. 실제 프로젝트에서는 이 폴더 대신 마이그레이션 도구를 씁니다(st11, a09).

포트 · 방화벽 · 원격 접속 — 왜 내 PC 에서만 붙나

"내 PC 에서는 잘 되는데 옆자리 동료는 접속이 안 됩니다." 설치 다음으로 흔한 벽입니다. 원인은 대부분 세 겹의 문 중 하나가 닫혀 있어서입니다 — DB 가 어느 주소로 듣는가, OS 방화벽이 통과시키는가, DB 계정이 그 IP 를 허용하는가. 순서대로 열면 됩니다.

세 문을 위에서부터 순서대로 여세요 — 아래부터 건드리면 원인이 섞여 더 오래 걸립니다.

문 ② — DB 가 "누구의 요청까지 듣는가"

# --- PostgreSQL : postgresql.conf ---
listen_addresses = '*'        # 기본은 'localhost' (내 PC 만)
port = 5432

# --- MySQL / MariaDB : my.cnf 의 [mysqld] ---
[mysqld]
bind-address = 0.0.0.0        # 기본이 127.0.0.1 인 배포판이 많습니다
port = 3306

# --- MongoDB : mongod.conf ---
net:
  port: 27017
  bindIp: 0.0.0.0             # 기본 127.0.0.1

# --- Redis : redis.conf ---
bind 0.0.0.0
protected-mode no             # 비번을 걸었을 때만 끄세요
requirepass 강한비밀번호
도커라면 이 설정을 대부분 건드릴 필요가 없습니다. 공식 이미지는 이미 0.0.0.0 으로 듣고 있고, 바깥에 노출할지는 -p 매핑이 결정하기 때문입니다. -p 5432:5432 대신 -p 127.0.0.1:5432:5432 로 쓰면 내 PC 에서만 붙게 제한할 수 있습니다.

문 ③ — "그 IP 의 그 계정"을 허용

# --- PostgreSQL : pg_hba.conf (파일 순서대로 위에서부터 검사) ---
# TYPE  DATABASE  USER  ADDRESS          METHOD
local   all       all                    scram-sha-256
host    all       all   127.0.0.1/32     scram-sha-256
host    appdb     app   192.168.0.0/24   scram-sha-256   # 사내망만
# host  all       all   0.0.0.0/0        scram-sha-256   # 전 세계 — 쓰지 마세요

# 고친 뒤 반드시 다시 읽히기
#   sudo systemctl reload postgresql
#   또는  SELECT pg_reload_conf();
-- MySQL : 계정 이름에 "어디서 오는가"가 붙어 있습니다
CREATE USER 'app'@'192.168.0.%' IDENTIFIED BY '강한비밀번호';
GRANT SELECT, INSERT, UPDATE, DELETE ON appdb.* TO 'app'@'192.168.0.%';
FLUSH PRIVILEGES;

SELECT user, host FROM mysql.user;   -- 지금 허용된 조합 확인
MySQL 의 가장 헷갈리는 지점 — 'app'@'localhost' 와 'app'@'%' 는 서로 다른 계정입니다. 비밀번호가 맞는데도 Access denied for user 'app'@'192.168.0.55' 가 뜨면 비번이 아니라 host 가 안 맞는 것입니다(st12).

타임존은 UTC 로 저장, 표시할 때 KST

-- 🐘 PostgreSQL : timestamptz 를 쓰면 알아서 해결됩니다
CREATE TABLE log (
  id bigserial PRIMARY KEY,
  msg text,
  created_at timestamptz NOT NULL DEFAULT now()   -- timestamp 가 아니라 timestamptz ★
);
SET TIME ZONE 'Asia/Seoul';       -- 세션에서 표시만 바꿉니다
SELECT created_at AT TIME ZONE 'Asia/Seoul' FROM log;

-- 🐬 MySQL : 서버 타임존을 UTC 로 두고 앱에서 변환
SET GLOBAL time_zone = '+00:00';
SELECT CONVERT_TZ(created_at, '+00:00', '+09:00') FROM log;
"9시간 차이"의 정체 — DB 서버는 UTC, 앱 서버는 KST, JDBC 는 또 자기 타임존을 붙이면서 값이 어긋납니다. 규칙은 하나 — 저장은 UTC, 변환은 화면에서 한 번만. 자세히는 m08.

테스트용 DB — Testcontainers 로 진짜 DB 를 씁니다

가짜 DB 를 쓰지 않는 이유

예전에는 테스트에 H2 같은 인메모리 DB 를 썼습니다. 빠르지만 문법과 동작이 실제 DB 와 미묘하게 달라서 테스트는 통과하는데 운영에서 터지는 일이 생겼습니다. Testcontainers 는 테스트가 시작될 때 진짜 DB 컨테이너를 띄우고 끝나면 지웁니다.

언어설치
☕ Java · 🟠 KotlintestImplementation("org.testcontainers:postgresql")
🐍 Pythonpip install testcontainers[postgres]
🟨 Nodenpm i -D testcontainers
🟣 .NETdotnet add package Testcontainers.PostgreSql
🦀 Rustcargo add --dev testcontainers
전제 조건은 도커가 돌고 있을 것 하나뿐입니다. CI(GitHub Actions 등)에서도 도커가 기본 제공되므로 그대로 돕니다.

파이썬 예 — 테스트 한 개가 DB 를 통째로 씁니다

import pytest, psycopg
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def db_url():
    # 테스트 세션 동안만 postgres:18 컨테이너가 뜹니다
    with PostgresContainer("postgres:18") as pg:
        yield pg.get_connection_url().replace(
            "postgresql+psycopg2", "postgresql")

def test_member_insert(db_url):
    with psycopg.connect(db_url) as conn, conn.cursor() as cur:
        cur.execute("CREATE TABLE member(id serial PRIMARY KEY, name text)")
        cur.execute("INSERT INTO member(name) VALUES (%s)", ("김현우",))
        cur.execute("SELECT count(*) FROM member")
        assert cur.fetchone()[0] == 1
        # 테스트가 끝나면 컨테이너째 사라집니다 — 뒷정리 코드가 필요 없습니다
느리지 않나요 — 컨테이너 기동에 2~5초가 듭니다. 그래서 scope="session" 으로 전체 테스트에 하나만 띄우고, 테스트마다 트랜잭션을 열었다 롤백하는 방식을 씁니다(a12).
여기까지가 "개발 환경"의 완성형입니다. 저장소를 받으면 compose up 으로 DB 가 뜨고, migrate 로 스키마가 맞춰지고, 테스트는 자기 컨테이너를 띄워 돕니다. 사람마다 다른 환경 때문에 생기는 문제가 거의 사라집니다.
