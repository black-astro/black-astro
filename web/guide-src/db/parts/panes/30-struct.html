애플리케이션 코드는 폴더 구조를 고민하면서, DB 는 누군가의 GUI 에서 손으로 고치는 팀이 아직 많습니다. 그러면 "운영에만 있는 컬럼", "아무도 출처를 모르는 뷰", "개발 DB 를 새로 못 만드는 저장소"가 생깁니다. 이 탭은 DB 를 코드처럼 다룰 때의 저장소 모양 — 마이그레이션 폴더 · 반복 실행 SQL · 시드 · 명명 규칙 · dbt 프로젝트 · 샤드와 환경 · CI — 을 한 장씩 보여 주고, 각 구조에서 무엇을 어디에 두는지, 무엇을 커밋하지 않는지, 언제 다음 단계로 넘어가는지를 짧게 정리합니다. 도구별 설치와 첫 명령은 🧰 설치 총정리 탭 SETUP 11, 마이그레이션 도구 비교 · 확장-축소 5단계는 🔌 앱 연동 탭 SECTION 09 에 있으니 여기서는 폴더 지도에 집중합니다.

STR 01

DB 도 코드다 — 무엇을 커밋하고 무엇을 빼나

스키마를 저장소에 두는 이유는 하나입니다. 빈 DB 에서 명령 한 번으로 지금의 운영 스키마를 똑같이 다시 만들 수 있어야 합니다. 그게 되면 신입의 개발 DB · CI 의 테스트 DB · 재해 복구용 새 서버가 모두 같은 파일에서 나옵니다. 그게 안 되면 "운영 DB 가 곧 원본"이 되고, 원본은 아무도 리뷰하지 않습니다.

앱 저장소 안의 db/ — 이 모양이 출발점

shop-api/
├─ db/
│  ├─ migration/        V__ 스키마 변경 이력 · 순서 있음 ★ (STR 02)
│  ├─ repeatable/       R__ 뷰 · 함수 · 프로시저 · 매번 최신으로 (STR 05)
│  ├─ seed/
│  │  └─ dev/           개발용 샘플 — 운영에는 안 감 (STR 06)
│  ├─ grants/           역할 · 권한 — 비밀번호는 빼고 (STR 04)
│  └─ README.md         적용 명령 · 명명 규칙 · 담당자
├─ compose.yml          로컬 DB 띄우기 (🧰 SETUP 03)
├─ .env.example         키 이름만 — 값은 비밀 저장소 (🧰 SETUP 08)
├─ .sqlfluff            SQL 린트 설정 (STR 09)
└─ src/

커밋하는 것 vs 빼는 것

✅ 커밋❌ 커밋 금지
DDL 마이그레이션 (V__)운영 데이터 덤프 — 개인정보 · 용량
뷰 · 함수 · 프로시저 정의 (R__)비밀번호 · 접속 문자열 · 키
참조 데이터 (코드표 · 국가)로컬 DB 파일 (*.db · 볼륨)
역할 구조와 GRANT생성물 (target/ · 생성 ERD)
린트 설정 · ERD 원본 · 데이터 사전개인 접속 설정 (profiles.yml)
"일단 schema.sql 을 덤프해서 커밋"은 시작으로는 괜찮지만 끝이 아닙니다. 덤프는 결과만 있고 순서가 없어서, 이미 데이터가 든 운영 DB 를 그 상태로 옮겨 가는 방법을 알려 주지 못합니다. 운영 DB 가 생기는 날 마이그레이션 폴더로 바꿉니다.

규모별 진화 — 언제 다음 단계로 넘어가나 🟢 기초

초록 점이 권장 출발점 — 운영 DB 가 생기는 날 마이그레이션 폴더로 옮깁니다.
전환신호 (하나라도 해당하면)하는 일
GUI → schema.sql두 번째 개발자 · "내 PC 에선 테이블이 없어요"현재 스키마를 덤프해 커밋, README 에 적용 명령
schema.sql → 마이그레이션운영 DB 가 생김 · dev/stg/prod 중 둘 이상덤프를 V1__baseline.sql 로 두고 이후 변경은 새 파일로
마이그레이션 → 폴더 나누기뷰 · 함수 10개+ · 시드가 마이그레이션에 섞임repeatable/ · seed/ · grants/ 분리
앱 저장소 → 별도 저장소DB 를 쓰는 앱 2개+ · DBA 가 배포를 승인 · dbtSTR 03 의 기준으로 판단 — 대부분은 앱 저장소에 남습니다
정리 — 기준은 "빈 DB 에서 명령 한 번으로 운영과 같은 스키마가 나오는가". 스키마 · 뷰 · 권한 구조는 커밋하고, 데이터 덤프와 비밀번호는 절대 커밋하지 않습니다.
STR 02

마이그레이션 디렉터리 — 파일 이름이 곧 순서입니다

도구는 달라도 원리는 같습니다. 변경 하나 = 파일 하나, 도구가 DB 안의 이력 표를 보고 아직 안 한 파일만 정해진 순서로 실행합니다. 그래서 구조에서 중요한 것은 "순서를 무엇이 정하나"와 "한 번 나간 파일은 고치지 않는다" 두 가지입니다. 도구 비교 · 체크섬 원리 · 기본 명령은 🔌 앱 연동 탭 SECTION 09 에 있으니 여기서는 폴더 모양만 봅니다.

Flyway — 파일 이름 규칙

src/main/resources/db/migration/   Spring Boot 기본 위치
├─ V1__baseline.sql                  V + 버전 + 밑줄 두 개 + 설명
├─ V2__create_orders.sql
├─ V2_1__add_orders_memo.sql         V2_1 = 버전 2.1 (사이에 끼우기)
├─ V3__ix_orders_member_id.sql
└─ R__v_sales_daily.sql              R = 반복 실행 · 버전 없음
                                     → 내용(체크섬)이 바뀔 때마다 다시 실행
                                     → 모든 V 가 끝난 뒤 설명 이름순
밑줄은 두 개(__)입니다. 하나만 쓰면 Flyway 가 마이그레이션으로 인식하지 못하고 조용히 건너뜁니다(validateMigrationNaming 을 켜면 오류로 멈춤). 버전은 숫자로 비교하므로 V10 이 V9 뒤에 옵니다 — 사람이 파일 탐색기에서 이름순으로 보면 V10 이 V1 바로 뒤에 보이니 헷갈리지 마세요.

이미 적용된 마이그레이션은 고치지 않는다 — 직접 돌려 보기 🟡 중급

Flyway 의 규칙(V 는 버전 숫자순 · R 은 체크섬이 바뀌면 다시 · 적용된 V 가 바뀌면 실패)을 파이썬 표준 라이브러리 sqlite3 로 30줄에 흉내 내 이 PC 에서 돌렸습니다. 파일은 위 트리와 같은 V1 · V2 · V10 · R__ 네 개입니다. 

# mini_migrate.py 핵심부 (Python 3.14 · 표준 라이브러리만)
def ver_key(p):          # V2_1 → (2, 1) · V10 이 V9 뒤에 오게
    return tuple(int(x) for x in
                 re.match(r"V([\d_]+)__", p.name)[1].split("_"))

versioned  = sorted(DIR.glob("V*__*.sql"), key=ver_key)
repeatable = sorted(DIR.glob("R__*.sql"))
for p in versioned + repeatable:          # V 전부 → R
    cs = sha256(p.read_bytes()).hexdigest()[:8]
    if p.name in done:
        if done[p.name] == cs: continue      # 그대로 · 건너뜀
        if p.name.startswith("V"):
            sys.exit(f"FAIL {p.name}: 적용된 파일이 바뀜 {done[p.name]} → {cs}")
    with db:                                 # 적용 + 이력을 한 트랜잭션
        db.executescript(p.read_text(encoding="utf-8"))
        db.execute("INSERT OR REPLACE INTO schema_history VALUES(?,?,?)",
                   (p.name, p.name.split("__")[0], cs))

주석 한 줄도 체크섬을 바꿉니다. 운영에 나간 V 파일은 오타라도 그대로 두고, 고칠 것은 새 V 파일로 추가합니다. 아직 아무 환경에도 적용되지 않은(머지 전) 파일만 자유롭게 고칩니다. 참고로 이름순 정렬은 ['V10__…', 'V1__…', 'V2__…'] 를 돌려줍니다 — 도구가 숫자 비교를 하는 이유입니다.

STR 03

앱 저장소 안 vs 별도 DB 저장소 — 주인이 누구인가

DB 코드를 어디에 둘지는 "편한 곳"이 아니라 "이 스키마를 바꿀 권한과 책임이 누구에게 있나"로 정합니다. 서비스 하나가 DB 하나를 가지면 답은 거의 항상 앱 저장소 안입니다. 여러 앱이 같은 테이블에 쓰기 시작하면 그때 고민이 생깁니다.

A. 앱 저장소 안 — 서비스 1 : DB 1

order-service/
├─ db/migration/          이 서비스의 sales 스키마만
├─ src/                   같은 PR 에서 스키마 + 코드
└─ .github/workflows/     배포 = 마이그레이션 → 앱 기동

장점  스키마와 코드가 한 번에 리뷰 · 한 번에 롤백
조건  다른 앱은 이 DB 에 직접 붙지 않음 (API 로)

B. 별도 DB 저장소 — 여러 앱이 공유할 때

legacy-erp-db/            여러 앱이 쓰는 DB 전용 저장소
├─ migration/
├─ repeatable/
├─ grants/
├─ CODEOWNERS             DBA + 소비 팀 리뷰 필수
├─ CHANGELOG.md           "V42 에서 orders.memo 삭제 예정"
└─ .github/workflows/     태그 v1.8.0 → 마이그레이션 배포

앱 쪽  "DB v1.8 이상 필요"를 README · 기동 검사로 명시
공유 DB 의 비용은 "스키마 변경 = 여러 팀 동시 배포"가 되는 것입니다.
상황DB 코드를 둘 곳이유
서비스 1 : DB 1앱 저장소 db/스키마와 코드가 한 PR — 같이 리뷰 · 같이 롤백
남의 앱은 읽기만 (리포트)소유 앱 저장소 + 읽기 전용 뷰계약은 뷰 · 테이블은 소유 팀이 자유롭게 바꿈
여러 앱이 같은 테이블에 씀별도 DB 저장소 + 버전 태그어느 한 앱 저장소에 두면 다른 팀이 변경을 모름
분석 웨어하우스dbt 별도 저장소 (STR 07)쓰는 사람(분석가)과 배포 주기가 다름
DBA 가 운영 DDL 을 승인어느 쪽이든 + CODEOWNERS폴더 단위로 리뷰어를 강제 — 저장소를 나눌 필요는 없음
❌ 공유 DB 를 "편해서" 고름

새 서비스가 기존 서비스의 테이블에 바로 SELECT · UPDATE 를 붙입니다. 처음 한 달은 빠르지만, 그 테이블은 이제 두 팀의 공용 API가 되어 컬럼 이름 하나 못 바꿉니다. 누가 쓰는지 아는 방법은 쿼리 로그뿐입니다.

✅ 이미 공유 중이라면 — 경계를 그어 갑니다

① 별도 DB 저장소로 모아 변경을 한 곳에서 보이게 → ② 앱마다 전용 역할 계정(STR 04)으로 누가 무엇을 쓰는지 드러냄 → ③ 남의 테이블 접근을 뷰나 API 로 하나씩 바꿈. 한 번에 쪼개려 하지 않습니다.

정리 — 서비스 하나가 DB 를 소유하면 앱 저장소 안이 정답입니다. 여러 앱이 같은 테이블에 쓰는 경우에만 별도 저장소로 빼고, 그건 목표가 아니라 경계를 긋기 위한 중간 단계입니다.
STR 04

명명 규칙 · 스키마 나누기 — 이름과 권한도 구조입니다

DB 의 "폴더"는 스키마(namespace)이고, "파일 이름"은 테이블 · 제약 · 인덱스 이름입니다. 이름 규칙이 있으면 에러 메시지 한 줄만 보고 어느 테이블의 어떤 제약인지 알고, 마이그레이션에서 DROP INDEX 할 대상을 바로 씁니다. 규칙은 무엇이 정답이냐보다 한 저장소 안에서 하나로 통일하는 것이 중요합니다(아래 접두사 체계는 흔한 관례이지 표준은 아닙니다).

접두사 + 테이블 + 컬럼 — 에러 메시지가 곧 문서가 되게 이름을 붙입니다.

이름 규칙 한 장 (README 에 그대로)

대상규칙예
테이블snake_case · 단수/복수 중 하나로 통일order_item
PK · FKpk_<테이블> · fk_<테이블>_<참조>fk_order_item_orders
유니크 · 인덱스uq_ · ix_<테이블>_<컬럼들>uq_member_email
체크ck_<테이블>_<규칙>ck_orders_amount_pos
컬럼FK 는 <대상>_id · 시각 _at · 불리언 is_member_id · paid_at
뷰 · 함수v_ · fn_ · sp_v_sales_daily
단수냐 복수냐는 취향이지만 하나만 알아 두세요. order · user 는 SQL 예약어라서 단수형을 고르면 따옴표를 달거나 피해 가야 합니다. 이 탭의 예제가 orders 만 복수인 이유입니다. 길이 한계는 PG 63바이트 · MySQL 64자 · Oracle 128바이트(12.2 이후)입니다.

├─ audit               변경 이력     — 앱은 INSERT 만
└─ public              비워 둠
"스키마"의 뜻이 DB 마다 다릅니다. PostgreSQL · SQL Server 는 DB 안의 이름공간, MySQL 은 스키마 = 데이터베이스, Oracle 은 스키마 = 사용자입니다. 그래서 MySQL 에서는 같은 구조를 데이터베이스 여러 개로, Oracle 에서는 소유 계정 여러 개로 만듭니다. search_path 와 스키마 기본은 🐘 PostgreSQL 탭 SECTION 04 참고.

권한 역할 구조 — DDL 하는 계정과 앱 계정을 나눈다 🟡 중급

앱 계정과 읽기 전용 계정을 만드는 첫 단계는 🧰 SETUP 09 에 있습니다. 저장소 구조 관점에서 한 걸음 더 가면 역할을 세 층으로 나누고 이 정의 자체를 db/grants/ 에 커밋합니다. 그러면 "운영에서 누가 테이블을 만들 수 있나"가 코드 리뷰 대상이 됩니다. 

-- db/grants/R__roles.sql — 여러 번 실행해도 같은 결과가 되게 작성
-- migrator : 스키마 소유자 · DDL 전용 · 마이그레이션 도구만 이 계정 사용
-- app_rw   : 앱 런타임 · DML 만 (CREATE · DROP 불가)
-- app_ro   : 리포트 · 분석 · 운영 조회
GRANT USAGE ON SCHEMA sales TO app_rw, app_ro;

-- migrator 가 앞으로 만들 테이블에도 자동 적용
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA sales
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA sales
  GRANT USAGE, SELECT ON SEQUENCES TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA sales
  GRANT SELECT ON TABLES TO app_ro;
-- 역할 자체는 한 번만 (DBA · 인프라 코드에서)
CREATE ROLE migrator LOGIN;
CREATE ROLE app_rw NOLOGIN;     -- 묶음 역할 · 직접 로그인 안 함
CREATE ROLE app_ro NOLOGIN;
CREATE SCHEMA sales AUTHORIZATION migrator;

-- 실제 로그인 계정은 앱마다 하나씩 → 누가 쓰는지 드러남
CREATE ROLE order_api  LOGIN IN ROLE app_rw;
CREATE ROLE report_bot LOGIN IN ROLE app_ro;
-- 비밀번호는 여기 쓰지 않음 → 비밀 저장소에서 ALTER ROLE 로
앱이 migrator 계정으로 돌면 안 됩니다. SQL 인젝션 한 번이 DROP TABLE 이 됩니다. 그리고 ALTER DEFAULT PRIVILEGES 는 FOR ROLE 로 지정한 계정이 만든 객체에만 적용되므로, 테이블을 다른 계정으로 만들면 권한이 안 붙습니다 — DDL 계정을 하나로 정하는 이유입니다.
정리 — 이름은 접두사 + 테이블 + 컬럼으로 직접 붙이고, 스키마로 도메인을, 역할로 DDL(migrator) · 앱(app_rw) · 조회(app_ro)를 나눕니다. 역할 정의도 db/grants/ 에 커밋합니다.
STR 05

SQL 파일 정리 — 뷰 · 함수 · 프로시저 · 쿼리는 어디에

테이블은 "변경 이력"이 중요하고, 뷰 · 함수 · 프로시저는 "지금의 정의"가 중요합니다. 뷰 하나 고칠 때마다 V 파일을 새로 만들면 정의 전체가 여러 파일에 흩어져 지금 모양을 아무도 모르게 됩니다. 그래서 이 둘은 폴더를 나누고, 뒤쪽은 여러 번 실행해도 같은 결과(멱등)가 되게 씁니다. 

db/
├─ migration/                 V__ 테이블 · 컬럼 · 인덱스 · 제약 — 이력이 중요
├─ repeatable/                R__ 지금의 정의가 중요 — 고치면 그 파일을 고침
│  ├─ R__10_fn_order_total.sql      함수 먼저 (번호로 순서 고정)
│  ├─ R__20_v_sales_daily.sql       뷰는 함수 뒤
│  └─ R__30_sp_close_month.sql      프로시저
└─ queries/                   자동 적용하지 않는 SQL — 리포트 · 운영 점검
   ├─ reports/monthly_sales.sql
   └─ ops/blocking_locks.sql        락 확인 (⚙️ 설계 · 튜닝 탭)

멱등하게 쓰는 법 — DB 별

-- PostgreSQL · Oracle · MySQL : 뷰는 OR REPLACE
CREATE OR REPLACE VIEW sales.v_sales_daily AS
SELECT order_date, count(*) AS orders, sum(amount) AS revenue
FROM   sales.orders
GROUP  BY order_date;

-- PG : CREATE OR REPLACE VIEW 는 컬럼을 "뒤에 추가"만 됨
--      컬럼 삭제 · 이름 변경 · 순서 변경은 DROP 후 다시
DROP VIEW IF EXISTS sales.v_sales_daily;   -- CASCADE 는 쓰지 말 것
CREATE VIEW sales.v_sales_daily AS ...;

-- SQLite : OR REPLACE 가 없어서 언제나 DROP IF EXISTS + CREATE
R__ 은 설명 이름순으로 실행됩니다. 뷰가 함수를 쓰면 함수 파일이 먼저 와야 하므로 R__10_ · R__20_ 처럼 번호를 이름 앞에 둡니다. DROP … CASCADE 는 의존하는 다른 뷰까지 지우고 그 뷰는 다시 만들어지지 않으니 피합니다.

sqlite3 로 확인 — 정의만 바꾸면 R 만 다시

-- R__v_member_contact.sql (STR 02 의 예제 저장소)
DROP VIEW IF EXISTS v_member_contact;
CREATE VIEW v_member_contact AS
  SELECT id, email, coalesce(phone, '(없음)') AS phone
  FROM member;
$ python mini_migrate.py      # '-' → '(없음)' 으로만 고친 뒤
applied R__v_member_contact.sql e89685b0
tables: ['member', 'schema_history', 'v_member_contact']
queries/ 는 도구가 실행하지 않는 폴더입니다. "이 SQL 은 어디서 돌던 거지?"를 없애려고 둡니다. 여기에도 린트(STR 09)는 걸어 두면 문법이 깨진 채로 쌓이지 않습니다.

SQL 을 앱 코드에 둘 때 — 어디에 두고 무엇이 생성되나 🟡 중급

SQL 을 직접 쓸수록 생성 코드나 테스트로 스키마와 맞춰 보는 장치가 필요합니다.
방식SQL 이 사는 곳생성물 · 주의
MyBatissrc/main/resources/mapper/<도메인>/OrderMapper.xml + 같은 이름의 자바 인터페이스mybatis.mapper-locations=classpath:mapper/**/*.xml · 생성물 없음 → 매퍼 테스트 필수
sqlc (Go 등)db/queries/*.sql · 스키마는 db/migration 을 그대로 읽음sqlc.yaml 의 out 폴더에 코드 생성 · 커밋한다면 CI 에서 sqlc diff
jOOQ자바 DSL — SQL 문자열 대신 생성된 테이블 클래스빌드 때 마이그레이션을 적용한 DB 에서 생성 → 보통 build/ 아래 · 커밋 안 함
ORM (JPA 등)엔티티 클래스 · 복잡한 쿼리만 @Query스키마는 마이그레이션이 원본 — Hibernate 의 ddl-auto=update 는 운영 금지 · ORM 선택은 🔌 SECTION 06
정리 — 테이블은 migration/(이력), 뷰 · 함수 · 프로시저는 repeatable/(지금 정의, 멱등), 손으로 돌리는 SQL 은 queries/. 앱 안의 SQL 은 스키마와 맞춰 보는 장치(생성 코드 · 테스트)와 함께 둡니다.
STR 06

시드 · 테스트 데이터 — 세 종류를 섞지 않는다

"초기 데이터"라는 말 하나에 성격이 전혀 다른 세 가지가 섞여 있습니다. 운영에도 있어야 하는 참조 데이터, 개발자 화면을 채우는 샘플, 테스트 하나가 쓰고 버리는 픽스처. 이 셋을 한 파일에 두면 언젠가 샘플 회원 "홍길동"이 운영 DB 에 들어갑니다. 

db/
├─ migration/
│  └─ V5__seed_order_status.sql     참조 데이터 — 운영에도 필요하니 마이그레이션으로
├─ seed/
│  └─ dev/                          개발용 샘플 — dev 프로필에서만 적용
│     ├─ R__dev_members.sql
│     └─ R__dev_orders.sql
└─ mask/
   └─ mask_members.sql              운영 사본을 스테이징에 넣기 전에 실행
src/test/resources/fixtures/        테스트 픽스처 — 테스트마다 만들고 지움 (🔌 SECTION 12)
적용 환경이 다르면 폴더도 달라야 합니다 — 운영 열이 진한 것만 migration/ 으로.

참조 데이터는 멱등하게 — sqlite3 로 3번 실행

INSERT INTO order_status(code, label) VALUES
  ('NEW','접수'), ('PAID','결제완료'), ('SHIPPED','배송중')
ON CONFLICT(code) DO UPDATE SET label = excluded.label;
-- 3번 실행 → count(*) = 3 (중복 없음)
-- 그냥 INSERT 였다면 2번째에
-- IntegrityError: UNIQUE constraint failed: order_status.code
# application-dev.yml — dev 프로필에서만 샘플 폴더를 더함
spring:
  flyway:
    locations: classpath:db/migration,classpath:db/seed/dev
# application.yml(운영)은 기본값 db/migration 만
ON CONFLICT … DO UPDATE 는 PostgreSQL · SQLite 문법입니다. MySQL 은 ON DUPLICATE KEY UPDATE, Oracle 은 MERGE.

운영 사본은 마스킹한 뒤에만 — mask_members.sql

-- 스테이징으로 복원한 직후, 앱을 붙이기 전에 실행
UPDATE member SET
  name  = '회원' || id,
  email = 'user' || id || '@example.com',     -- UNIQUE 유지
  phone = CASE WHEN phone IS NULL THEN NULL
               ELSE '010-0000-' || lpad((id % 10000)::text, 4, '0') END;
-- grade · 가입일은 그대로 → 분포가 살아 있어 성능 테스트에 쓸모 있음
(1, '회원1', 'user1@example.com', '010-0000-0001', 'VIP')
(2, '회원2', 'user2@example.com', None, 'BASIC')
# sqlite3 확인 결과 (sqlite 는 lpad 대신 substr('0000'||id, -4))
NULL 은 NULL 로 둡니다. 빈 값까지 가짜 번호로 채우면 "전화번호 없는 회원" 경로가 테스트에서 사라집니다. 마스킹 규칙 자체(무엇이 개인정보인가 · 가명처리)는 🧬 전문가 탭 SECTION 14 참고.
정리 — 운영에도 필요한 참조 데이터만 마이그레이션에, 개발 샘플은 seed/dev 로 프로필을 갈라, 픽스처는 테스트 코드 옆에. 운영 사본은 마스킹 전에는 어디에도 복원하지 않습니다.
STR 07

dbt 프로젝트 구조 — staging · intermediate · marts

분석 쪽 SQL 은 "변경 이력"보다 "어떤 표가 무엇에서 나왔나(계보)"가 중요합니다. dbt 는 SQL 파일과 ref() 로 그 계보를 만들고, 폴더 구조가 곧 데이터가 정제되는 단계가 됩니다. 아래는 dbt Labs 의 공식 글 "How we structure our dbt projects" 의 권장 구조를 따릅니다. dbt 가 무엇이고 run · test · 증분 모델이 어떻게 도는지는 📊 분석 · 벡터 DB 탭 OLAP 12 에 있습니다.

공식 권장 트리

jaffle_shop/
├─ dbt_project.yml        이름 · 폴더별 기본 materialized
├─ packages.yml           dbt_utils 같은 패키지
├─ models/
│  ├─ staging/            원본 표 1개 = 모델 1개 · 이름 · 형 변환만
│  │  └─ jaffle_shop/     원본 시스템별 폴더
│  │     ├─ _jaffle_shop__sources.yml
│  │     ├─ _jaffle_shop__models.yml
│  │     ├─ stg_jaffle_shop__customers.sql
│  │     └─ stg_jaffle_shop__orders.sql
│  ├─ intermediate/       stg 를 조합하는 중간 단계 · 밖에 노출 안 함
│  │  └─ finance/
│  │     └─ int_payments_pivoted_to_orders.sql
│  └─ marts/              사람이 보는 결과 · 업무 영역별
│     ├─ finance/orders.sql
│     └─ marketing/customers.sql
├─ seeds/                 작은 CSV 참조표 (국가 코드 등)
├─ snapshots/             천천히 바뀌는 값의 이력 (SCD2)
├─ macros/  tests/  analyses/

폴더별 기본값 — dbt_project.yml

name: jaffle_shop
profile: jaffle_shop      # 접속 정보는 profiles.yml (기본 ~/.dbt/) — 커밋 안 함

models:
  jaffle_shop:
    staging:
      +materialized: view        # 가볍게 · 항상 최신
    intermediate:
      +materialized: ephemeral   # 표로 안 남김 (CTE 로 끼워 넣음)

      +materialized: table       # 사람이 조회 → 미리 계산
층이름하는 일

staging 모델 — 이름 바꾸기만

  - name: jaffle_shop

    tables:
      - name: orders

# _jaffle_shop__models.yml

정리 — models/ 아래 staging(정리) → intermediate(조합) → marts(결과), 이름은 stg_ · int_ 로 층을 드러내고, ref() 는 오른쪽으로만. 접속 정보(profiles.yml)와 target/ 은 커밋하지 않습니다.
STR 08

여러 DB · 샤드 · 환경 — 파일은 하나, 설정만 여럿

dev · stg · prod, 샤드 8개, 고객사별 DB 30개 — 대상이 늘어도 마이그레이션 폴더는 하나입니다. 달라지는 것은 접속 설정과 실행 횟수뿐입니다. 환경마다 다른 SQL 파일을 두는 순간 "운영에만 있는 컬럼"이 구조적으로 생깁니다.

환경 · 샤드가 있는 저장소

db/
├─ migration/          모든 환경 · 모든 샤드가 같은 파일 ★
├─ repeatable/
├─ env/
│  ├─ dev.env          FLYWAY_URL · FLYWAY_USER (비밀번호 X)
│  ├─ stg.env
│  └─ prod.env
└─ shards.txt          샤드 접속 URL 목록 (주석 # 허용)

금지  migration-prod/ · if 환경 == prod 같은 SQL 분기
# 환경은 설정만 다르고 파일은 같습니다
set -a; . db/env/stg.env; set +a     # FLYWAY_URL · FLYWAY_USER
export FLYWAY_PASSWORD="$STG_DB_PASSWORD"   # CI 비밀 변수에서
flyway migrate

샤드마다 같은 마이그레이션

#!/usr/bin/env bash
# db/migrate-shards.sh — 하나라도 실패하면 즉시 멈춤
set -euo pipefail
for url in $(grep -v '^#' db/shards.txt); do
  echo "== $url"
  flyway -url="$url" migrate
done

# 끝나면 남은(Pending) 마이그레이션이 있는 샤드가 없는지 확인
for url in $(grep -v '^#' db/shards.txt); do
  out=$(flyway -url="$url" info)
  if grep -q Pending <<< "$out"; then echo "남음: $url"; exit 1; fi
done
샤드 1 은 V21, 샤드 7 은 아직 V20 인 시간이 반드시 있습니다. 그 사이에도 앱은 두 스키마 모두에서 돌아야 합니다. 그래서 샤드 · 멀티 DB 환경에서는 아래의 확장-축소가 선택이 아니라 필수입니다.

블루-그린 · 확장-축소 — 마이그레이션과 배포의 순서 🔴 고급

다섯 단계 각각의 내용(NULL 허용 추가 → 양쪽 쓰기 → 백필 → 읽기 전환 → 정리)은 🔌 앱 연동 탭 SECTION 09 에 있습니다. 여기서 볼 것은 배포 축 위에서 앱 버전과 마이그레이션이 어떻게 겹치는지입니다. 블루-그린 배포는 옛 버전과 새 버전이 같은 DB 를 동시에 씁니다.

v1 · v2 가 겹치는 구간(축 위 치수선) 때문에 한 배포 안에서 "추가 + 삭제"를 같이 하지 않습니다.
정리 — 환경 · 샤드가 몇 개든 마이그레이션 폴더는 하나, 다른 것은 접속 설정과 실행 횟수. 여러 버전이 같은 DB 를 쓰는 구간이 있으니 확장은 배포 전, 축소는 옛 버전이 사라진 뒤 별도 배포로 합니다.
STR 09

리뷰 · CI — 사람이 보기 전에 기계가 거른다

DB 변경 리뷰가 어려운 이유는 문법이 아니라 운영에서의 결과(잠금 시간 · 구버전 앱 호환)를 봐야 하기 때문입니다. 그래서 문법 · 형식 · 알려진 위험 패턴 · "빈 DB 에 전부 적용되는가"는 CI 가 먼저 거르고, 사람은 설계와 운영 영향만 봅니다.

붉은 칸 — "빈 DB 에 처음부터 전부"가 STR 01 의 기준을 매번 검사합니다.

CI — 빈 PostgreSQL 에 전부 적용 (GitHub Actions)

jobs:
  db:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: ci }   # CI 전용 일회용 컨테이너
        ports: ["5432:5432"]
        options: --health-cmd pg_isready --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - run: pipx install sqlfluff && sqlfluff lint db/
      - run: python db/ci/check_ddl.py $(git diff --name-only --diff-filter=A origin/main -- db/migration)
      - name: migrate on empty DB (twice = no-op)
        run: |
          for i in 1 2; do
            docker run --rm --network host -v "$PWD/db/migration:/flyway/sql" \
              flyway/flyway -url=jdbc:postgresql://localhost:5432/postgres \
              -user=postgres -password=ci migrate
          done
git diff origin/main 을 쓰려면 checkout 에 fetch-depth: 0 이 필요합니다. 되돌리기 검사(④)는 down 을 지원하는 도구에서 alembic upgrade head && alembic downgrade base && alembic upgrade head 처럼 왕복시킵니다. Flyway 무료 판처럼 down 이 없으면 ④ 대신 "고치는 V 파일을 하나 더 쓰는 법"을 PR 설명에 적게 합니다.

위험 DDL 검사 — check_ddl.py (실행 확인)

RULES = [  # PostgreSQL 기준 · 주석(--)은 지우고 검사
  (r"CREATE\s+(UNIQUE\s+)?INDEX\s+(?!CONCURRENTLY)",
   "CONCURRENTLY 없는 인덱스 생성 — 쓰기 차단"),
  (r"ALTER\s+COLUMN\s+\w+\s+(SET\s+DATA\s+)?TYPE",
   "컬럼 타입 변경 — 테이블 재작성 가능"),
  (r"SET\s+NOT\s+NULL", "SET NOT NULL — 전체 검사 동안 잠금"),
  (r"ADD\s+(CONSTRAINT\s+\w+\s+)?FOREIGN\s+KEY(?![^;]*NOT\s+VALID)",
   "FK 를 NOT VALID 없이 추가 — 전체 검증"),
  (r"DROP\s+(COLUMN|TABLE)", "DROP — 축소 단계인가?"),
]
$ python check_ddl.py V7__ix.sql V8__ix_ok.sql V9__fk_ok.sql V10__bad.sql
V7__ix.sql: CONCURRENTLY 없는 인덱스 생성 — 쓰기 차단
V10__bad.sql: 컬럼 타입 변경 — 테이블 재작성 가능
V10__bad.sql: FK 를 NOT VALID 없이 추가 — 전체 검증
# exit 1 → CI 실패 · V8(CONCURRENTLY) · V9(NOT VALID + VALIDATE) 는 통과
직접 만들기 싫다면 PostgreSQL 마이그레이션 전용 린터 squawk 가 같은 종류의 규칙을 갖고 있습니다. CREATE INDEX CONCURRENTLY 는 트랜잭션 안에서 못 돌므로 그 문장 하나만 든 파일로 분리해 두는 것이 안전합니다. 잠금이 왜 걸리는지는 ⚙️ 설계 · 튜닝 탭의 락 섹션 참고.

.sqlfluff — 저장소 루트에 하나

[sqlfluff]
dialect = postgres
templater = jinja        # dbt 프로젝트면 dbt
max_line_length = 120

[sqlfluff:rules:capitalisation.keywords]
capitalisation_policy = upper
기존 SQL 이 많은 저장소에 처음 걸면 수천 건이 나옵니다. 처음엔 CI 에서 새로 추가된 파일만 검사하고, sqlfluff fix 로 한 번에 고치는 PR 을 따로 냅니다.

STR 10

유형 · 규모별 권장 구조 한 장 — 그리고 문서화

지금까지의 구조를 한 표로 모았습니다. 대부분의 팀은 둘째 줄(서비스 하나 · 앱 저장소의 db/)에서 시작해 오래 머뭅니다. 마지막으로 ERD · 데이터 사전을 손으로 그리지 않고 스키마에서 생성하는 법과, 규칙을 사람이 아니라 도구가 지키게 하는 법을 정리합니다.

-- CI 의 ③ 직후 실행 — 규칙을 어긴 인덱스 이름 찾기 (PostgreSQL)
SELECT schemaname, tablename, indexname
FROM   pg_indexes
WHERE  schemaname IN ('core', 'sales', 'stock')
AND    indexname !~ '^(pk|uq|ix)_';
-- PK · UNIQUE 제약의 인덱스는 제약 이름을 따라가므로
-- 제약에 pk_ · uq_ 를 붙였다면 여기서 함께 걸러집니다
도구는 "확신 있는 만큼"만 고르세요. 위의 장치는 모두 DB 카탈로그 · 체크섬 · 정규식처럼 단순한 것들입니다. 여기서 시작해 규칙이 늘면 그때 전용 린터를 붙여도 늦지 않습니다.
정리 — 대부분은 앱 저장소의 db/로 충분하고, 여러 앱 · 분석 · 샤드일 때만 표의 아래 줄로 갑니다. ERD · 데이터 사전은 스키마에서 생성하고, 규칙은 체크섬 · 린트 · 카탈로그 테스트 · CODEOWNERS 로 도구가 지키게 합니다.
