SECTION 01

정규화 1~3NF

정규화는 어려운 이론이 아닙니다. 같은 정보를 두 군데 적지 않기 — 이 한 줄입니다.

정규화하지 않으면 벌어지는 일

주문번호회원명회원주소상품명수량
1001김하늘서울시 강남구키보드1
1002김하늘서울시 강남구마우스2
1003김하늘서울시 강남구모니터1
  • 갱신 이상 — 김하늘이 이사하면 주문 100건을 전부 고쳐야 합니다. 하나라도 놓치면 데이터가 서로 다릅니다
  • 삽입 이상 — 아직 주문하지 않은 회원은 등록할 방법이 없습니다
  • 삭제 이상 — 마지막 주문을 지우면 회원 정보도 함께 사라집니다

1NF → 2NF → 3NF

1NF
한 칸에는 값 하나만 "키보드, 마우스, 모니터"를 한 칸에 넣지 않습니다. 반복 그룹(취미1·취미2·취미3)도 안 됩니다.
▼
2NF
기본키 전체에 종속 복합키(주문번호+상품번호)일 때, 일부 키에만 딸린 컬럼(상품명은 상품번호에만 딸림)을 분리합니다.
▼
3NF
키가 아닌 컬럼끼리 종속되지 않게 회원번호 → 회원명 → 회원주소 처럼 이행적 종속을 분리합니다.
-- 정규화 결과 : 3개 테이블로 분리
member     (id, name, address)                  -- 회원 정보는 한 곳에만
orders     (id, member_id, ordered_at)          -- 주문 헤더
order_item (id, order_id, product_id, qty)      -- 주문 상세
product    (id, name, price)                    -- 상품 정보는 한 곳에만

-- 이제 이사하면 한 줄만 고치면 됩니다
UPDATE member SET address = '부산시 해운대구' WHERE id = 1;
실무의 판단 기준은 단순합니다. "이 값이 바뀌면 몇 군데를 고쳐야 하나?"
두 군데 이상이면 정규화가 덜 된 것입니다. 3NF까지만 하면 실무의 대부분이 해결되고, BCNF·4NF·5NF 는 이론적으로는 존재하지만 실무에서 의식적으로 적용할 일은 드뭅니다.
"중복을 없애라"가 아니라 "고칠 곳을 하나로 만들라"가 정확한 표현입니다.
SECTION 02

반정규화는 언제 하나

일부러 중복을 두는 것이 반정규화입니다. 측정해서 느릴 때만, 이유를 적어 두고 합니다.

유형예대가
집계 컬럼 post.comment_count — 매번 COUNT 하지 않으려고 댓글 추가·삭제 때 같이 갱신해야 정합성 유지
복사 컬럼 order_item.product_name — 상품명이 바뀌어도 주문 당시 이름 보존 이 경우는 오히려 정확합니다(이력 스냅숏)
계산 컬럼 orders.total_amount — 매번 합산하지 않으려고 품목 변경 시 재계산 필요
평탄화 조인 3번을 피하려고 컬럼을 합쳐 둠 갱신 지점이 늘어남
가격은 반드시 복사해야 합니다. order_item.unit_price 를 두지 않고 product.price 를 조인하면, 상품 가격이 바뀌는 순간 과거 주문 금액이 전부 바뀝니다. 이것은 반정규화가 아니라 "주문 시점의 사실을 기록"하는 올바른 설계입니다. 시간이 지나도 변하면 안 되는 값은 복사하는 것이 원칙입니다.

집계 컬럼을 안전하게 유지하기

✗ 애플리케이션에서 따로 갱신
-- 트랜잭션 밖이거나 순서가 틀리면
-- 카운트가 실제와 어긋납니다
INSERT INTO comment (...);
UPDATE post SET comment_count = comment_count + 1
WHERE id = ?;
-- 예외가 나면? 재시도하면? 중복 증가?
✓ 같은 트랜잭션 + 주기적 검증
BEGIN;
  INSERT INTO comment (...);
  UPDATE post SET comment_count = comment_count + 1
  WHERE id = ?;
COMMIT;

-- 그리고 야간 배치로 정합성 검증·보정
UPDATE post p SET comment_count =
  (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id);
반정규화 전에 반드시 확인하세요.
① 인덱스로 해결되지 않는가 — 대부분은 인덱스로 충분합니다
② 실제로 느린가 — 측정하지 않고 "느릴 것 같아서" 하는 반정규화가 가장 흔한 실수입니다
③ 캐시로 해결되지 않는가 — Redis 캐시가 더 나은 선택일 수 있습니다
④ 했다면 정합성 검증 배치를 반드시 함께 만드세요
SECTION 03

키 설계 — 대리키 · UUID

기본키 선택은 나중에 바꾸기가 거의 불가능합니다. 처음에 제대로 정해야 합니다.

✗ 자연키 — 의미 있는 값
-- 이메일·사업자번호·주민번호를 PK 로
CREATE TABLE member (
  email VARCHAR(120) PRIMARY KEY,
  ...
);

-- 문제
-- · 이메일은 바뀝니다 → 모든 FK 를 함께 변경
-- · 개인정보가 모든 자식 테이블에 복사됨
-- · 길어서 인덱스가 커짐
✓ 대리키 — 의미 없는 번호
CREATE TABLE member (
  id    BIGINT PRIMARY KEY,      -- 의미 없는 번호
  email VARCHAR(120) UNIQUE,     -- 유일성은 UNIQUE 로 보장
  ...
);

-- 이메일이 바뀌어도 FK 는 그대로
-- 개인정보가 다른 표로 퍼지지 않음

대리키의 종류

종류장점단점
순차 정수
(AUTO_INCREMENT)		 작고 빠름 · 인덱스 효율 최고 · 삽입 순서대로 저장 여러 DB 병합 시 충돌 · 총 건수가 노출됨(경쟁사가 가입자 수를 알 수 있음)
UUID v4 어디서든 독립 생성 · 추측 불가 무작위라 인덱스 성능이 나쁩니다 · 16~36바이트
UUID v7 · ULID 시간 순 정렬 + 전역 유일 — 두 장점을 모두 여전히 16바이트 · 지원 라이브러리 확인 필요
스노플레이크 시간+노드+순번 조합. 64비트로 작음 노드 ID 관리 필요
무작위 UUID 를 클러스터드 인덱스의 기본키로 쓰면 성능이 무너집니다. 특히 MySQL InnoDB 는 기본키 순서대로 디스크에 저장하므로(🐬 m09), 무작위 값이 들어올 때마다 페이지 중간에 삽입하며 페이지 분할이 계속 일어납니다. 수천만 건에서 INSERT 성능이 몇 배 차이납니다. 
-- 실무의 절충안 : 내부는 순차 정수, 외부 노출은 별도 식별자
CREATE TABLE orders (
    id         BIGINT      PRIMARY KEY,          -- 내부 조인용 (순차)
    public_id  CHAR(26)    NOT NULL UNIQUE,      -- URL·API 노출용 (ULID)
    member_id  BIGINT      NOT NULL REFERENCES member(id),
    ordered_at TIMESTAMP   NOT NULL
);
-- URL: /orders/01J2KX8PQR3M4N5T6V7W8Y9Z0A   ← 순번을 추측할 수 없습니다

복합키를 쓸 것인가

-- 연결 테이블(N:M)은 복합키가 자연스럽습니다
CREATE TABLE post_tag (
    post_id INT NOT NULL REFERENCES post(id),
    tag_id  INT NOT NULL REFERENCES tag(id),
    PRIMARY KEY (post_id, tag_id)       -- 중복 방지가 덤으로 따라옵니다
);
복합키의 트레이드오프 — 중복 방지가 자동으로 되고 인덱스도 겸합니다. 다만 이 표를 참조하는 자식이 생기면 FK 가 두 컬럼이 되어 번거로워집니다. 연결 테이블에 속성이 붙기 시작하면 단일 대리키를 추가하는 편이 낫습니다.
SECTION 04

인덱스 원리 B-Tree

인덱스는 책 뒤의 찾아보기입니다. 100만 줄에서 한 줄을 찾는 데 스무 번이면 끝납니다.

인덱스가 빠른 이유는 "미리 찾아 놨기" 때문이 아니라 한 번 볼 때마다 후보의 대부분을 버리기 때문입니다.
인덱스 없음 — 전체 스캔
100만 행을 처음부터 끝까지 비교

  1행 → 아니다
  2행 → 아니다
  ...
  1,000,000행

평균 50만 번 비교
디스크 IO 도 그만큼
B-Tree 인덱스
          [500,000]              ← 루트
        /            \
   [250,000]      [750,000]      ← 중간
    /     \        /      \
  ...    ...     ...     ...     ← 리프 (실제 위치)

log₂(1,000,000) ≈ 20번
실제 B-Tree 는 한 노드에 수백 개를 담아
3~4번의 디스크 읽기면 끝납니다

인덱스가 잘 듣는 조건 · 못 듣는 조건

조건인덱스
WHERE id = 100최적
WHERE price BETWEEN 1000 AND 5000범위 스캔 — 좋음
WHERE name LIKE '김%'전방 일치 — 사용 가능
ORDER BY created_at DESC정렬을 인덱스로 대체 — 매우 좋음
WHERE name LIKE '%김%'불가 — 풀스캔
WHERE YEAR(created_at) = 2026불가 — 컬럼에 함수
WHERE status != 'DONE'부정 조건 — 대부분 도움이 안 됨
WHERE gender = 'M'값 종류가 2개뿐 — 선택도가 낮아 무의미
선택도(selectivity)가 인덱스의 가치를 결정합니다. 조건을 걸었을 때 전체의 몇 %가 남는가입니다. 1% 만 남으면 인덱스가 큰 이득이고, 30% 이상 남으면 옵티마이저가 풀스캔을 고릅니다 — 인덱스로 찾은 뒤 테이블을 랜덤하게 읽는 비용이 순차 읽기보다 크기 때문입니다. 인덱스를 만들었는데 안 탄다면 이 때문일 수 있습니다.

인덱스의 비용

  • 쓰기가 느려집니다 — INSERT·UPDATE·DELETE 마다 모든 인덱스를 함께 갱신합니다
  • 디스크를 차지합니다 — 인덱스가 테이블보다 커지는 경우도 흔합니다
  • 옵티마이저의 선택지가 늘어납니다 — 너무 많으면 잘못된 인덱스를 고를 수도 있습니다
인덱스 설계의 출발점 — 실제로 실행되는 쿼리 목록을 먼저 적으세요. "어떤 컬럼에 인덱스를 걸까"가 아니라 "이 쿼리를 빠르게 하려면 어떤 인덱스가 필요한가"가 올바른 순서입니다.
SECTION 05

복합 인덱스 순서 · 커버링

복합 인덱스는 컬럼 순서가 성능을 결정합니다. 전화번호부를 이름으로 찾을 수 없는 것과 같은 이유입니다.

복합 인덱스는 앞 컬럼부터 차례로만 쓸 수 있습니다 — 전화번호부를 이름만 알고 펼칠 수 없는 것과 같습니다.
CREATE INDEX idx_ord ON orders (member_id, ordered_at, status);
쿼리 조건이 인덱스를 쓸 수 있나
WHERE member_id = 1✓ 선행 컬럼 — 완전 사용
WHERE member_id = 1 AND ordered_at > '2026-01-01'✓ 두 컬럼까지 사용
WHERE member_id = 1 AND status = 'PAID'△ member_id 까지만. status 는 필터로만
WHERE ordered_at > '2026-01-01'✗ 선행 컬럼이 없어 사용 불가
WHERE status = 'PAID'✗ 사용 불가
ORDER BY member_id, ordered_at✓ 정렬도 인덱스로 해결
순서를 정하는 규칙
① 등호(=) 조건 컬럼을 앞으로, 범위(>, <, BETWEEN) 조건은 뒤로
② 등호 컬럼이 여러 개면 선택도가 높은(값 종류가 많은) 것을 앞으로
③ ORDER BY 컬럼을 범위 조건 다음에 두면 정렬까지 해결됩니다
④ 범위 조건 뒤의 컬럼은 정렬에 쓸 수 없습니다 — 이것이 가장 자주 놓치는 부분입니다

커버링 인덱스 — 테이블을 아예 안 읽기

-- 이 쿼리가 필요로 하는 컬럼이 전부 인덱스에 있으면
SELECT member_id, ordered_at FROM orders WHERE member_id = 1;

-- 인덱스만 읽고 끝납니다 (테이블 접근 0)
CREATE INDEX idx_cover ON orders (member_id, ordered_at);

-- 조회 컬럼이 더 있다면 INCLUDE 로 (PostgreSQL 11+ · SQL Server)
CREATE INDEX idx_cover ON orders (member_id) INCLUDE (ordered_at, status);
-- MySQL·SQLite 는 INCLUDE 가 없으므로 인덱스 컬럼에 직접 넣습니다
실행계획에서 확인하는 법 — PostgreSQL Index Only Scan · MySQL Extra: Using index · SQLite USING COVERING INDEX · Oracle INDEX FAST FULL SCAN 또는 TABLE ACCESS 가 없는 계획. 이것이 보이면 가장 빠른 형태입니다.

인덱스는 몇 개까지

정해진 답은 없지만, 테이블당 5개 내외가 실무의 대략적 기준입니다. 그보다 많다면 중복되는 인덱스가 있을 가능성이 높습니다. 

-- 이 둘은 중복입니다 — 앞의 것을 지워도 됩니다
CREATE INDEX idx_a ON orders (member_id);
CREATE INDEX idx_b ON orders (member_id, ordered_at);   -- idx_a 의 역할을 포함

-- 반대로 이 둘은 서로 다른 쿼리를 위한 것입니다 (둘 다 필요)
CREATE INDEX idx_c ON orders (member_id, ordered_at);
CREATE INDEX idx_d ON orders (ordered_at, member_id);
SECTION 06

인덱스가 안 타는 이유 10

"인덱스를 만들었는데 여전히 느려요" — 원인은 거의 이 열 가지 안에 있습니다.

#원인해결
1컬럼에 함수·연산
WHERE YEAR(dt) = 2026		 범위 조건으로 바꾸거나 함수 기반 인덱스를 만듭니다
2앞에 % 붙은 LIKE
LIKE '%검색어%'		 전문 검색·trigram 인덱스로 (🐘 p09 · ✒️ s10)
3암묵적 형변환
WHERE varchar_col = 123		 타입을 맞춰 비교합니다. 조인 컬럼 타입 불일치도 같은 문제
4선행 컬럼 누락복합 인덱스 순서를 조정하거나 별도 인덱스
5선택도가 낮음
전체의 30% 이상이 조건에 맞음		 정상 동작입니다. 풀스캔이 실제로 더 빠릅니다
6통계가 낡음 ANALYZE 실행. 대량 적재 후에는 반드시
7OR 조건
WHERE a = 1 OR b = 2		 UNION ALL 로 분리하거나 각각 인덱스 (일부 DB는 병합 처리)
8NULL 조건
WHERE col IS NULL		 Oracle 은 단일 컬럼 B-Tree 에 NULL 을 안 넣습니다 → 부분 인덱스나 상수 결합
9부정 조건
!= · NOT IN		 대부분 인덱스가 도움이 안 됩니다. 조건을 뒤집어 표현해 보세요
10콜레이션·문자셋 불일치 조인 컬럼의 콜레이션을 통일 (🐬 m04)

가장 흔한 세 가지 실제 수정

✗ 날짜에 함수
WHERE DATE(created_at) = '2026-08-05'
WHERE YEAR(dt)=2026 AND MONTH(dt)=8
WHERE TO_CHAR(dt,'YYYYMM') = '202608'
✓ 범위로
WHERE created_at >= '2026-08-05'
  AND created_at <  '2026-08-06'

WHERE dt >= '2026-08-01'
  AND dt <  '2026-09-01'
✗ 타입이 다른 비교
-- phone 이 VARCHAR 인데
WHERE phone = 01012345678

-- 조인 컬럼 타입이 다름
JOIN t2 ON t1.code = t2.code_int
✓ 타입을 맞춤
WHERE phone = '01012345678'

-- 근본 해결은 스키마 수정
ALTER TABLE t2 MODIFY code VARCHAR(20);
✗ OR 로 묶인 다른 컬럼
SELECT * FROM member
WHERE  email = 'a@b.com'
   OR  phone = '01012345678';
✓ UNION ALL 로 분리
SELECT * FROM member WHERE email = 'a@b.com'
UNION ALL

  AND email <> 'a@b.com';   -- 중복 제거
SECTION 07

실행계획 읽는 법 (4 DB)

느린 쿼리는 추측하지 말고 계획을 보세요. 네 DB의 명령과 읽는 법을 나란히 정리합니다.

PostgreSQL
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;

-- Seq Scan / Index Scan / Index Only Scan

-- loops (크면 N+1 형태)

-- 볼 것
-- type: const > eq_ref > ref > range > index > ALL
-- rows: 읽을 것으로 추정한 행 수
-- Extra: Using index(좋음)
--        Using filesort / temporary(주의)
Oracle
SELECT /*+ GATHER_PLAN_STATISTICS */ ...;
SELECT * FROM TABLE(
  DBMS_XPLAN.DISPLAY_CURSOR(NULL,NULL,'ALLSTATS LAST'));

-- 볼 것
-- E-Rows(추정) vs A-Rows(실제)
-- Buffers (읽은 블록 수)
-- TABLE ACCESS FULL / INDEX RANGE SCAN

-- 볼 것
-- SEARCH ... USING INDEX (좋음)
-- USING COVERING INDEX (가장 좋음)
-- SCAN table (전체 스캔)

어느 DB든 확인하는 것은 같습니다

1
전체 스캔이 있는가 작은 테이블이면 정상. 큰 테이블에 풀스캔이면 인덱스를 검토합니다.
▼
2
추정 행 수와 실제가 크게 다른가 10배 이상 차이 나면 통계가 낡았거나 데이터 분포가 편향된 것입니다.
▼
3
조인 순서와 방식이 타당한가 작은 쪽을 먼저 몰고 있는지, 조인 방식(NL·Hash·Merge)이 데이터 크기에 맞는지 봅니다(🧬 z08).
▼
4
불필요한 정렬·임시 테이블이 있는가 인덱스로 정렬을 대체할 수 있는지 검토합니다.
비용(cost) 숫자끼리는 비교하지 마세요. cost 는 같은 쿼리의 다른 계획을 비교하기 위한 상대값입니다. "이 쿼리는 cost 500이라 느리다" 같은 판단은 의미가 없습니다. 실제 시간과 읽은 블록 수를 보세요.
SECTION 08

통계 정보와 카디널리티

옵티마이저는 통계를 보고 계획을 짭니다. 통계가 틀리면 멀쩡하던 쿼리가 갑자기 느려집니다.

DB는 각 테이블에 대해 행 수 · 컬럼별 값의 종류 수 · 값의 분포(히스토그램) · NULL 비율 등을 저장해 둡니다. 이를 근거로 "이 조건이면 몇 행이 남을까"를 추정하고, 그 추정에 따라 인덱스를 쓸지 · 어떤 조인 방식을 쓸지를 정합니다. 

-- PostgreSQL
ANALYZE orders;
SELECT relname, n_live_tup, last_analyze, last_autoanalyze
FROM   pg_stat_user_tables ORDER BY last_analyze NULLS FIRST;

-- MySQL
ANALYZE TABLE orders;
SELECT table_name, table_rows, update_time FROM information_schema.tables
WHERE  table_schema = 'shop';

-- Oracle
EXEC DBMS_STATS.GATHER_TABLE_STATS('APP','ORDERS');
SELECT table_name, num_rows, last_analyzed FROM user_tables;

-- SQLite
ANALYZE;
PRAGMA optimize;    -- 연결 종료 전에 실행하면 필요한 만큼만

통계가 틀어지는 순간

  • 대량 적재 직후 — 100만 건을 넣었는데 통계는 "0행"이라고 알고 있습니다
  • 대량 삭제 직후 — 반대 상황
  • 배포 직후 — 새 테이블·인덱스에 통계가 아직 없습니다
  • 데이터 분포가 급변 — 이벤트로 특정 값이 폭증한 경우
"어제까지 잘 돌던 쿼리가 오늘 갑자기 느려졌다"면 통계를 먼저 갱신해 보세요. 원인의 상당수가 이것입니다. 대량 배치 작업 후에는 ANALYZE 를 스크립트에 포함하는 것이 좋습니다.

히스토그램 — 편향된 분포

status 컬럼의 값이 DONE 99%, ERROR 1% 라면, WHERE status='ERROR' 는 인덱스가 매우 유리하고 WHERE status='DONE' 은 풀스캔이 낫습니다. 같은 컬럼인데 값에 따라 최적 계획이 다릅니다. 이를 판단하려면 단순 "값 종류 수"가 아니라 분포 히스토그램이 필요합니다. 

-- PostgreSQL : 통계 정밀도 올리기 (기본 100 → 최대 10000)
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

-- MySQL 8.0 : 히스토그램 생성
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 100 BUCKETS;

-- Oracle : 자동으로 필요한 컬럼에 생성 (METHOD_OPT 기본값)
EXEC DBMS_STATS.GATHER_TABLE_STATS('APP','ORDERS',
     method_opt => 'FOR ALL COLUMNS SIZE AUTO');
SECTION 09

페이징 — 커서 방식

OFFSET 100000 은 10만 줄을 세어서 버리고 시작합니다. 뒤 페이지가 느린 이유이자, 무한 스크롤이 갈수록 버벅이는 이유입니다.

OFFSET 이 느린 이유는 건너뛰기가 공짜가 아니기 때문입니다 — 버릴 행도 일단 읽어야 합니다.
✗ OFFSET 페이징
SELECT * FROM orders
ORDER BY id DESC
LIMIT 20 OFFSET 100000;

-- DB 가 하는 일
-- ① 조건에 맞는 행을 정렬
-- ② 앞의 100,000 행을 읽어서 버림
-- ③ 그다음 20 행을 반환
-- 페이지가 뒤로 갈수록 선형으로 느려집니다
✓ 커서(키셋) 페이징
-- 첫 페이지
SELECT * FROM orders
ORDER BY id DESC LIMIT 20;

-- 다음 페이지 : 마지막으로 본 id 를 기준으로
SELECT * FROM orders
WHERE  id < 987654         -- ← 직전 페이지의 마지막 id
ORDER  BY id DESC LIMIT 20;

-- 몇 페이지든 같은 속도 (인덱스로 바로 진입)

정렬 기준이 유일하지 않을 때

-- 생성일로 정렬하되 같은 시각이 여러 개 있을 수 있다면
-- 반드시 유일한 컬럼을 함께 넣어 순서를 확정합니다
SELECT * FROM orders
WHERE  (ordered_at, id) < ('2026-08-05', 987654)     -- 행 비교 (PostgreSQL·MySQL 지원)
ORDER  BY ordered_at DESC, id DESC
LIMIT  20;

-- 행 비교를 지원하지 않으면 풀어서
WHERE  ordered_at < '2026-08-05'
   OR (ordered_at = '2026-08-05' AND id < 987654)

-- 이 인덱스가 필요합니다
CREATE INDEX idx_ord_dt_id ON orders (ordered_at DESC, id DESC);
비교OFFSET커서
뒤 페이지 속도선형으로 느려짐일정
"5페이지로 점프"가능불가 (다음/이전만)
총 페이지 수 표시가능 (COUNT 필요)어려움
데이터가 중간에 추가·삭제되면행이 중복·누락됨안전
적합한 UI관리자 화면 (페이지 번호)무한 스크롤·모바일 피드
총 건수 표시도 비쌉니다. SELECT COUNT(*) 는 대용량에서 수 초가 걸릴 수 있습니다.
· 정확한 수가 꼭 필요한가 재검토 — "1,000+ 건" 표기로 충분한 경우가 많습니다
· 필요하면 추정치를 쓰세요 (PostgreSQL reltuples, MySQL table_rows)
· 또는 주기적으로 계산해 캐시합니다
SECTION 10

트랜잭션 ACID

돈 계산이 틀리지 않게 하는 네 가지 약속입니다.

속성뜻없으면
Atomicity
원자성		전부 되거나 전부 안 되거나출금은 됐는데 입금이 안 됨
Consistency
일관성		제약조건을 항상 만족재고가 −5개인 상태가 저장됨
Isolation
고립성		동시 트랜잭션이 서로 간섭하지 않음동시 주문에서 재고가 두 번 팔림
Durability
지속성		커밋했으면 정전에도 남음"결제 완료" 후 서버가 죽으니 기록이 없음
ACID 가 보장하지 않는 것
· 애플리케이션의 논리적 오류 — 잘못된 금액을 커밋하면 그대로 남습니다
· 여러 DB에 걸친 정합성 — 분산 트랜잭션은 별도 문제입니다(🧬 z11)
· 외부 시스템 호출 — 결제 API 호출은 롤백되지 않습니다
"트랜잭션으로 감쌌으니 안전하다"는 착각이 실무 사고의 큰 원인입니다.

트랜잭션 경계를 어디에 둘까

✗ 너무 넓음
with db.transaction():
    order = create_order(...)
    result = payment_api.charge(...)   # 외부 호출 3초
    send_email(...)                    # 또 외부 호출
    update_stock(...)
# 락을 3초 이상 붙들고 있어
# 다른 요청이 전부 대기합니다
✓ DB 작업만 짧게
with db.transaction():
    order = create_order(status='PENDING')

result = payment_api.charge(...)       # 트랜잭션 밖

with db.transaction():
    update_order_status(order.id, result)
    update_stock(...)

queue.publish('send_email', order.id)  # 비동기로
DDL 은 대부분 자동 커밋됩니다. CREATE TABLE·ALTER TABLE 은 MySQL·Oracle 에서 앞의 트랜잭션을 커밋시키고 자신도 되돌릴 수 없습니다. PostgreSQL 은 예외적으로 DDL 을 롤백할 수 있어 마이그레이션 스크립트를 안전하게 만들 수 있습니다.
SECTION 11

격리 수준 4단계

동시에 접근할 때 얼마나 엄격하게 막을지입니다. 아래 버튼으로 각 수준에서 무엇이 막히고 무엇이 뚫리는지 확인하세요.

격리 수준별 이상 현상

세 가지 이상 현상

현상무슨 일이 일어나나
더티 리드
Dirty Read		 다른 트랜잭션이 아직 커밋하지 않은 값을 읽습니다. 그 트랜잭션이 롤백하면 존재한 적 없는 값을 본 셈이 됩니다.
반복 불가 읽기
Non-repeatable Read		 같은 행을 두 번 읽었는데 값이 달라집니다. 사이에 다른 트랜잭션이 수정·커밋했기 때문입니다.
팬텀 리드
Phantom Read		 같은 조건으로 두 번 조회했는데 행 개수가 달라집니다. 사이에 새 행이 들어왔기 때문입니다.

DB별 기본값 — 여기가 핵심입니다

DB기본 격리 수준특이점
PostgreSQLREAD COMMITTEDREAD UNCOMMITTED 를 요청해도 READ COMMITTED 로 동작
OracleREAD COMMITTEDREPEATABLE READ 를 지원하지 않습니다 (SERIALIZABLE 은 지원)
MySQL InnoDBREPEATABLE READ다른 DB보다 엄격. 갭 락으로 팬텀도 대부분 방지 (🐬 m11)
SQLiteSERIALIZABLE쓰기가 하나뿐이라 자연히 직렬화됩니다
MySQL 에서 PostgreSQL 로(또는 반대로) 옮길 때 주의하세요. 기본 격리 수준이 다르므로 같은 코드가 다르게 동작할 수 있습니다. 특히 MySQL에서 REPEATABLE READ 를 전제로 짠 코드는 PostgreSQL(READ COMMITTED)에서 같은 트랜잭션 안에서 값이 바뀌는 상황을 만납니다. 
-- 격리 수준 확인·변경
SELECT @@transaction_isolation;                          -- MySQL
SHOW transaction_isolation;                              -- PostgreSQL

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;            -- 다음 트랜잭션만
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ; -- 세션 전체

-- 특정 조회만 잠그기 (격리 수준을 올리지 않고 정합성 확보)
SELECT * FROM stock WHERE id = 1 FOR UPDATE;         -- 배타 락 (쓰기 예정)
SELECT * FROM stock WHERE id = 1 FOR SHARE;          -- 공유 락 (읽기만 보장)
실무의 선택 — 대부분 기본값을 그대로 쓰고, 정합성이 꼭 필요한 지점에서만 SELECT … FOR UPDATE 로 필요한 행만 잠급니다. 격리 수준을 통째로 SERIALIZABLE 로 올리면 충돌·재시도가 급증합니다.
수준을 통째로 올리면 데드락과 대기가 함께 늘어납니다 — 자리를 좁혀 거세요.
SECTION 12

락 · 데드락 분석

데드락은 서로 상대가 잡은 것을 기다리는 상태입니다. 완전히 없앨 수는 없지만 크게 줄일 수 있습니다.

✗ 접근 순서가 다름 — 데드락
-- 트랜잭션 A
UPDATE account SET bal=bal-100 WHERE id=1;  -- 1번 잠금
UPDATE account SET bal=bal+100 WHERE id=2;  -- 2번 대기...

-- 트랜잭션 B (동시에)
UPDATE account SET bal=bal-50 WHERE id=2;   -- 2번 잠금
UPDATE account SET bal=bal+50 WHERE id=1;   -- 1번 대기...

-- 서로 영원히 기다림 → DB 가 한쪽을 롤백시킴
✓ 항상 같은 순서로
-- 두 트랜잭션 모두 id 오름차순으로 잠급니다
-- (애플리케이션에서 정렬 후 처리)

ids = sorted([from_id, to_id])
for i in ids:
    UPDATE account SET ... WHERE id = i;

-- 순서가 같으면 데드락이 원천적으로 안 생깁니다

진단 명령

PostgreSQL
-- 누가 누구를 막고 있나
SELECT blocked.pid AS 대기, blocked.query AS 대기쿼리,
       blocking.pid AS 차단, blocking.query AS 차단쿼리
FROM   pg_stat_activity blocked
JOIN   pg_stat_activity blocking
  ON   blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE  cardinality(pg_blocking_pids(blocked.pid)) > 0;

SELECT pg_terminate_backend(12345);
MySQL
SHOW ENGINE INNODB STATUS\G
-- LATEST DETECTED DEADLOCK 섹션

SELECT * FROM performance_schema.data_lock_waits;
SELECT trx_id, trx_state, trx_started, trx_query
FROM   information_schema.innodb_trx;

KILL 12345;
Oracle
SELECT blocking_session, sid, serial#,
       event, seconds_in_wait
FROM   v$session
WHERE  blocking_session IS NOT NULL;

ALTER SYSTEM KILL SESSION '123,45678' IMMEDIATE;
-- 데드락은 alert.log 와 trace 파일에 기록됩니다
SQLite
-- 락 개념이 단순합니다 (쓰기는 하나뿐)
-- database is locked 가 사실상 유일한 증상
PRAGMA busy_timeout = 5000;
BEGIN IMMEDIATE;    -- 쓰기 트랜잭션은 처음부터

-- 자세한 내용은 ✒️ SQLite 탭 s11

데드락을 줄이는 다섯 가지

  • 접근 순서 통일 — 가장 효과적입니다. 여러 행을 잠글 때 항상 같은 기준으로 정렬
  • 트랜잭션 짧게 — 외부 호출·사용자 입력을 트랜잭션 밖으로
  • 적절한 인덱스 — 인덱스가 없으면 훨씬 넓은 범위가 잠깁니다
  • 격리 수준 낮추기 — 꼭 필요한 곳만 높이세요
  • 재시도 로직 — 데드락은 정상적인 동시성 신호입니다. 1~3회 재시도하면 대부분 성공합니다(🔌 a11)
락 대기 타임아웃을 짧게 두세요. MySQL 기본 innodb_lock_wait_timeout 은 50초입니다. 그동안 커넥션이 묶여 있으면 연쇄적으로 커넥션 풀이 고갈됩니다. 5~10초 정도로 낮추고 애플리케이션에서 재시도하는 편이 낫습니다.
SECTION 13

커넥션 풀 사이징

커넥션 풀은 크게 잡을수록 빨라지지 않습니다. 오히려 느려집니다.

커넥션을 늘린다고 DB 가 빨라지지 않습니다. 줄을 어디에 세울지를 정하는 것일 뿐입니다 — 앱 앞이냐, DB 안이냐.

커넥션을 만드는 것은 비싼 작업(TCP 연결 + 인증 + 세션 초기화)이라 미리 만들어 두고 재사용하는 것이 커넥션 풀입니다. 문제는 크기입니다 — DB 서버의 CPU 코어는 정해져 있는데 커넥션을 300개 열어 두면 컨텍스트 스위칭과 락 경합만 늘어납니다.

널리 쓰이는 시작 공식
커넥션 수 = ((코어 수 × 2) + 유효 디스크 수)
8코어 + SSD 1개 → 약 17개. "고작?"이라는 생각이 들겠지만, 실측하면 이 부근에서 처리량이 최대인 경우가 많습니다. 이 값을 시작점으로 두고 부하 테스트로 조정하세요.
증상원인과 대응
커넥션 대기 타임아웃 풀이 작거나, 커넥션을 오래 붙들고 있는 쿼리가 있습니다. 느린 쿼리를 먼저 찾으세요
DB 의 max_connections 초과 앱 인스턴스 수 × 풀 크기가 DB 한계를 넘었습니다. 전체 합으로 계산해야 합니다
풀을 늘렸는데 더 느려짐 정상입니다. DB 가 병목이라면 커넥션을 늘려도 대기 위치만 바뀝니다
커넥션 누수 반납하지 않는 코드가 있습니다. 누수 감지 옵션을 켜세요
# HikariCP (Java · Spring Boot)
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=20          # max 와 같게 두는 것이 권장됩니다
spring.datasource.hikari.connection-timeout=3000  # 풀에서 못 받으면 3초 후 실패
spring.datasource.hikari.max-lifetime=1800000     # 30분 (DB 타임아웃보다 짧게)
spring.datasource.hikari.leak-detection-threshold=20000   # 누수 감지
# SQLAlchemy (Python)
engine = create_engine(
    "postgresql+psycopg://app:pw@db/shop",
    pool_size=10,          # 상시 유지
    max_overflow=10,       # 순간 초과 허용 (총 20)
    pool_timeout=3,        # 대기 최대 3초
    pool_recycle=1800,     # 30분마다 갱신
    pool_pre_ping=True,    # ★ 끊긴 커넥션 자동 감지 — 반드시 켜세요
)
여러 인스턴스를 잊지 마세요. 앱 서버 10대 × 풀 20 = DB 커넥션 200개입니다. 여기에 배치·관리자 도구·모니터링까지 더하면 금세 한계에 닿습니다. DB 의 max_connections 는 이 총합보다 여유 있게 잡되, 그 자체를 크게 늘리는 것은 해결책이 아닙니다. PostgreSQL 이라면 PgBouncer 를 두는 것이 정석입니다(🐘 p17).
서버리스 환경(Lambda 등)은 특히 주의하세요. 인스턴스가 요청마다 생겼다 사라지면 커넥션이 폭발합니다. RDS Proxy·PgBouncer 같은 외부 풀러가 사실상 필수입니다.

슬로우 쿼리 잡는 절차

감으로 찾지 마세요. 순서만 지키면 누구나 잡을 수 있습니다.

1
측정 · 수집 슬로우 쿼리 로그를 켜고 pg_stat_statements·sys.statement_analysis·AWR 로 총 소요 시간 순위를 뽑습니다.
▼
2
우선순위 결정 평균이 느린 쿼리보다 총합이 큰 쿼리를 먼저. 100ms × 100만 회 > 5초 × 10회.
▼
3
실행계획 확인 풀스캔·추정 오차·불필요한 정렬을 찾습니다(t07).
▼
4
가설 → 수정 → 재측정 인덱스 추가 · 쿼리 재작성 · 통계 갱신 중 하나씩 바꾸고 다시 잽니다.
▼
5
부작용 확인 인덱스를 추가하면 쓰기가 느려집니다. 다른 쿼리 계획이 바뀌지 않았는지 확인합니다.

개선 카드 — 효과가 큰 순서

순위카드기대 효과
1인덱스 추가·수정보통 수십~수백 배. 가장 먼저 검토

4필요한 컬럼만 조회네트워크·메모리 절감, 커버링 인덱스 가능

7비정규화·집계 테이블위로 안 되면. 정합성 비용을 감수
8서버 설정·증설마지막. 대부분 근본 원인을 가릴 뿐입니다

· 측정 없이 최적화 — 어디가 느린지 모르는 채로 코드를 고치는 것

· 운영에서 바로 인덱스 생성 — 큰 테이블은 반드시 CONCURRENTLY·온라인 DDL 로
· 서버 설정부터 만지기 — 쿼리가 원인인데 메모리를 늘려 봐야 잠깐 미룰 뿐입니다

SECTION 16

모델링 실전 — 주문 · 재고

이론을 실제 테이블로 옮겨 봅니다. 커머스의 핵심이자 면접 단골 주제입니다. 

-- 상품 : 현재 정보
CREATE TABLE product (
    id          BIGINT PRIMARY KEY,
    name        VARCHAR(200) NOT NULL,
    price       DECIMAL(12,2) NOT NULL CHECK (price >= 0),
    status      VARCHAR(20) NOT NULL DEFAULT 'ON_SALE',
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 재고 : 상품과 분리합니다 (갱신이 잦아 락 경합이 다르기 때문)
CREATE TABLE stock (
    product_id  BIGINT PRIMARY KEY REFERENCES product(id),
    qty         INT NOT NULL CHECK (qty >= 0),      -- ★ DB 가 음수를 막습니다
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 주문 헤더 : 주문 시점의 사실을 기록
CREATE TABLE orders (
    id           BIGINT PRIMARY KEY,
    public_id    CHAR(26) NOT NULL UNIQUE,          -- 외부 노출용
    member_id    BIGINT NOT NULL REFERENCES member(id),
    status       VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    total_amount DECIMAL(14,2) NOT NULL,            -- 계산 결과를 저장 (반정규화)
    ordered_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    -- 배송지도 주문 시점 값을 복사합니다 (회원 주소가 바뀌어도 유지)
    ship_name    VARCHAR(50)  NOT NULL,
    ship_addr    VARCHAR(300) NOT NULL,
    ship_phone   VARCHAR(20)  NOT NULL
);
CREATE INDEX idx_orders_member_dt ON orders (member_id, ordered_at DESC);
CREATE INDEX idx_orders_status_dt ON orders (status, ordered_at DESC);

-- 주문 상세 : 상품명·가격도 그 시점 값을 복사
CREATE TABLE order_item (
    id          BIGINT PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES orders(id),
    product_id  BIGINT NOT NULL REFERENCES product(id),
    product_name VARCHAR(200) NOT NULL,             -- ★ 스냅숏
    unit_price  DECIMAL(12,2) NOT NULL,             -- ★ 스냅숏
    qty         INT NOT NULL CHECK (qty > 0)
);
CREATE INDEX idx_item_order ON order_item (order_id);

-- 상태 변경 이력 : 언제 무엇이 바뀌었는지
CREATE TABLE order_history (
    id          BIGINT PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES orders(id),
    from_status VARCHAR(20),
    to_status   VARCHAR(20) NOT NULL,
    changed_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    changed_by  VARCHAR(50)
);

설계 판단 다섯 가지

판단이유
재고를 상품에서 분리 재고는 갱신이 잦고 락 경합이 심합니다. 같은 행에 두면 상품 조회까지 대기하게 됩니다
가격·상품명을 복사 상품 정보가 바뀌어도 과거 주문은 그대로여야 합니다. 회계·분쟁 대응의 기본
total_amount 저장 매번 SUM 하지 않기 위한 반정규화. 저장 시 검증하고 배치로 대사합니다
CHECK (qty >= 0) 애플리케이션 버그가 있어도 재고가 음수가 되는 것을 DB가 막습니다
상태 이력 테이블 "언제 배송으로 바뀌었나"는 반드시 나옵니다. 현재 상태만 두면 답할 수 없습니다

재고 차감 — 동시성이 걸리는 지점

✗ 조회 후 차감
SELECT qty FROM stock WHERE product_id = 10;
-- 애플리케이션에서 qty > 0 확인
UPDATE stock SET qty = qty - 1 WHERE product_id = 10;

-- 동시에 두 요청이 들어오면
-- 둘 다 "재고 1개 있음"을 보고 둘 다 차감 → -1
✓ 조건부 UPDATE 한 문장
UPDATE stock
SET    qty = qty - 1
WHERE  product_id = 10 AND qty >= 1;

-- 영향 행 수가 0이면 재고 부족 → 주문 실패 처리
-- DB 가 원자적으로 처리하므로 경합에서도 안전합니다
더 큰 규모라면 — 선착순 이벤트처럼 한 상품에 수만 요청이 몰리면 한 행에 락이 집중돼 DB가 병목이 됩니다. 이때는 Redis 원자 연산으로 선착순을 가리고 DB에는 확정분만 반영하거나, 재고를 여러 행으로 쪼개는 방식을 씁니다. 자세한 패턴은 ☕ 자바 가이드의 대규모 트래픽 탭에 있습니다.
