Redis는 데이터를 디스크가 아니라 메모리에 두고 마이크로초 단위로 답하는 키-값 저장소입니다. 실무에서는 RDBMS 앞에 두는 캐시, 세션 저장소, 순위표, 분산 락으로 쓰입니다. 이 탭은 NoSQL이 뭔지부터 시작해서, Redis를 실서비스에 붙일 때 필요한 것까지 다룹니다.

SECTION 01

NoSQL이란 — RDBMS와 무엇이 다른가

NoSQL은 "SQL을 안 쓴다"가 아니라 "표 구조를 강제하지 않는다(Not only SQL)"는 뜻입니다. 관계형(RDBMS)을 대체하는 게 아니라, 관계형이 불편한 자리를 보완하는 도구들의 통칭이에요.

셋의 차이는 데이터를 어떤 모양으로 저장하느냐입니다 — 표, 키-값, JSON 문서.

정면 비교 — 무엇이 다른가

항목RDBMS (PostgreSQL·MySQL…)NoSQL (Redis·MongoDB…)
데이터 모양정해진 칸의 표. 모든 행이 같은 구조키-값·JSON 문서 등 유연한 구조
스키마먼저 정하고 시작 (칸 추가 = ALTER)없거나 느슨함 — 데이터마다 칸이 달라도 됨
표끼리 연결JOIN — 정규화해 나눠 두고 붙여서 조회조인이 없거나 약함 — 한 덩어리로 미리 묶어 저장
트랜잭션ACID 완전 보장 — 돈 계산의 표준제한적 (단일 키·단일 문서 위주, 제품마다 다름)
규모 확장기본은 서버 키우기(수직) + 읽기 복제처음부터 서버 늘리기(수평 분산)를 겨냥한 설계
질의 언어SQL — 표준이 있어 어디서나 비슷제품마다 다름 (Redis 명령어, MongoDB 쿼리…)
잘 맞는 데이터회원·주문·재고 — 정확해야 하는 업무 데이터캐시·세션·로그·피드 — 빠르고 많은 데이터

NoSQL 4갈래 — 이름만 알아 두세요

갈래대표 제품데이터 모양 · 쓰는 곳
키-값Redis · Memcached키 → 값. 캐시·세션·카운터. 이 탭에서 다룹니다
문서형MongoDB · CouchDBJSON 문서. 구조가 자주 바뀌는 데이터. 🍃 MongoDB 탭
와이드 컬럼Cassandra · HBase행마다 열이 다른 거대한 표. 시계열·초대용량 쓰기
그래프Neo4j점과 선(관계). 추천·친구관계·사기 탐지
가장 중요한 결론 — 대체가 아니라 역할 분담입니다. 실무 표준 구성은 "본체는 RDBMS + 빠른 자리는 Redis + 유연한 자리는 MongoDB"처럼 각자 잘하는 곳에 두는 것입니다. "NoSQL이 신형이니 RDBMS를 버린다"가 아니에요. 돈·주문·회원처럼 틀리면 안 되는 데이터는 여전히 RDBMS가 기본입니다.
왜 NoSQL이 생겼나 — 2000년대 후반, 구글·아마존 규모의 서비스가 "한 대의 DB로는 트래픽을 못 받는" 문제를 만났습니다. 표를 여러 서버로 쪼개면 JOIN과 트랜잭션이 서버를 넘나들며 급격히 느려지기 때문에, 아예 조인·엄격한 스키마를 포기하고 분산을 쉽게 만든 저장소가 나온 것입니다. 즉 NoSQL은 "SQL보다 좋은 것"이 아니라 다른 트레이드오프를 고른 것입니다.
SECTION 02

Redis는 어떤 저장소인가

Redis가 빠른 이유는 단순합니다 — 모든 데이터가 메모리에 있고, 명령을 한 줄로 세워 순서대로 처리하기 때문입니다.

세 가지 특징이 전부입니다

  • ① 인메모리 — 데이터가 전부 RAM에 있습니다. 디스크 DB가 밀리초(ms)로 답할 때 Redis는 마이크로초(µs)로 답합니다. 대신 메모리 크기가 곧 저장 용량의 한계입니다.
  • ② 싱글 스레드 명령 처리 — 명령을 한 번에 하나씩 순서대로 실행합니다. 락 경합이 없어 단순하고, INCR 같은 연산이 저절로 원자적입니다. 뒤집어 말하면 느린 명령 하나가 전체를 막습니다 (r12에서 다룹니다).
  • ③ 자료구조 서버 — 값이 단순 문자열만이 아닙니다. 리스트·집합·정렬된 집합·해시를 서버가 직접 제공해서, "순위표"나 "최근 본 상품" 같은 기능이 명령 몇 개로 끝납니다.

체감 속도 차이

작업대략적인 시간
Redis GET (메모리)약 0.1ms 이하 — 같은 네트워크 기준
RDBMS 인덱스 조회 (캐시 적중)수 ms
RDBMS 복잡한 JOIN·집계수십 ms ~ 수 초
그래서 어디에 쓰나 — 같은 결과를 매번 다시 계산할 필요가 없는 곳입니다. "메인 페이지 인기 상품 목록"을 매 요청마다 RDBMS 집계로 만들면 수백 ms, 1분에 한 번 계산해 Redis에 올려 두면 0.1ms입니다. 이것이 캐시(r06)의 전부입니다.
Redis를 유일한 저장소로 쓰지 마세요. 기본 설정의 Redis는 서버가 죽으면 최근 데이터가 사라질 수 있습니다 (영속성은 r08). "사라져도 다시 만들 수 있는 데이터"(캐시·세션)를 두는 곳으로 시작하는 게 안전합니다.
SECTION 03

설치와 첫 접속 — Docker · redis-cli

도커 한 줄이면 뜹니다. redis-cli 로 명령을 직접 쳐 보는 것까지가 설치입니다.

# Docker — 가장 빠른 길
docker run -d --name redis -p 6379:6379 redis:7
docker exec -it redis redis-cli     # 바로 CLI 접속

# Ubuntu · Debian
sudo apt install -y redis-server
sudo systemctl enable --now redis-server

# macOS
brew install redis && brew services start redis

# Windows — 공식 지원이 없습니다. Docker 또는 WSL2 를 쓰세요

첫 명령 다섯 개

127.0.0.1:6379> PING
PONG                        # 살아 있음
127.0.0.1:6379> SET greeting "hello"
OK
127.0.0.1:6379> GET greeting
"hello"
127.0.0.1:6379> DEL greeting
(integer) 1
127.0.0.1:6379> KEYS *      # ← 학습용으로만! 운영 금지 (r12)
(empty array)
기본 Redis에는 비밀번호가 없습니다. 기본 설정은 localhost만 듣지만, bind 0.0.0.0 으로 열고 비밀번호 없이 인터넷에 노출하면 몇 분 안에 스캐너가 찾아내 데이터를 지우고 협박 메시지를 남깁니다 (실제로 흔한 사고입니다). 외부에 열어야 한다면 requirepass + 방화벽 + protected-mode yes 를 확인하세요.
포트는 6379, GUI가 필요하면 RedisInsight(공식 무료)를 쓰세요. 2024년 라이선스 논쟁으로 갈라져 나온 Valkey(리눅스재단, 완전 오픈소스)도 명령이 그대로 호환됩니다 — 회사 정책상 라이선스가 걸리면 Valkey를 검토하세요.
SECTION 04

키 설계와 TTL — 유효기간

Redis 사용법의 절반은 키 이름을 어떻게 짓고, 언제 사라지게 할 것인가입니다.

키 이름은 콜론으로 계층을 만듭니다

# 관례: 객체:아이디:속성  — 소문자, 콜론(:) 구분
SET user:1001:name "김하늘"
SET session:9f2a71 "{\"userId\":1001}"
SET cache:product:15 "{\"name\":\"무선 키보드\",\"price\":49000}"

# 나쁜 키 — 무엇인지 알 수 없고 충돌합니다
SET data1 ...
SET temp ...

TTL — 키에 수명 붙이기

SET cache:main:popular "..." EX 60      # 60초 뒤 자동 삭제
SET session:9f2a71 "..." EX 1800        # 세션 30분

TTL cache:main:popular      # 남은 초 확인 (-1 = 무기한, -2 = 없는 키)
EXPIRE user:1001:name 3600  # 이미 있는 키에 수명 부여
PERSIST session:9f2a71      # 수명 제거 (무기한으로)
캐시 키에는 반드시 TTL을 거세요. TTL 없는 캐시 키는 지워지지 않고 쌓여 메모리를 끝까지 채웁니다. "이 키는 최악의 경우 언제까지 낡은 값이어도 되는가"를 초로 적는 것이 TTL 설계입니다.

실무 키 사전 — 용도별 이름·수명 견본

키 패턴담는 것 · TTL 기준
cache:product:{id}DB 조회 결과 캐시 — TTL 30초~5분 (낡아도 되는 시간만큼)
session:{sid}로그인 세션 — TTL 30분, 요청마다 EXPIRE 로 연장
lock:{자원이름}분산 락 — TTL 수십 초 (작업 최장 시간 + 여유)
rate:{userId}:{분단위시각}처리량 카운터 — TTL 60초 (창 크기만큼)
rank:{기간}순위표 Sorted Set — 기간 끝나면 통째로 UNLINK
otp:{전화번호}인증번호 — TTL 3분, 검증 성공 시 즉시 DEL

키를 훑어야 할 때 — SCAN (KEYS 대신)

# 접두사로 순회 — 조금씩 잘라 가져와서 서버를 안 멈춥니다
SCAN 0 MATCH cache:product:* COUNT 500
# → 다음 커서 번호와 키 묶음이 옵니다. 커서가 0이 될 때까지 반복

# 접두사 일괄 삭제 (운영에서 FLUSHALL 대신 쓰는 방법)
redis-cli --scan --pattern "cache:v1:*" | xargs -L 500 redis-cli UNLINK
데이터베이스 번호 — Redis 안에는 db0~db15 라는 논리 공간이 있지만 (SELECT 1로 전환), 실무에서는 번호 구분 대신 키 접두사를 쓰고 용도가 다르면 아예 Redis 인스턴스를 분리하는 것이 표준입니다 — 클러스터 모드에서는 db0만 쓸 수 있기 때문입니다.
SECTION 05

자료구조 5종 — 값의 모양이 무기

값이 문자열 하나뿐이라면 Redis가 이렇게 쓰이지 않았을 겁니다. 어떤 기능에 어떤 자료구조를 쓰는지가 Redis 실력의 핵심입니다.

구조모양대표 명령 · 쓰는 곳
String키 → 값 하나 (문자열·숫자·JSON)SET GET INCR — 캐시 · 카운터 · 세션
Hash키 → {필드: 값, …} 작은 표 한 줄HSET HGET HGETALL — 객체 저장 (user:1001 의 이름·등급…)
List키 → 순서 있는 목록 (양끝 삽입)LPUSH RPOP LRANGE — 최근 본 상품 · 간단한 작업 큐
Set키 → 중복 없는 집합SADD SISMEMBER SINTER — 좋아요 누른 사람 · 태그 · 교집합
Sorted Set키 → (점수, 멤버) 정렬 유지ZADD ZRANGE ZRANK — 순위표 · 랭킹 · 지연 큐

직접 쳐 보기

# String — 조회수 카운터 (INCR 은 원자적: 동시에 눌러도 안 틀림)
INCR views:post:42            # 1
INCR views:post:42            # 2

# Hash — 유저 객체를 필드 단위로
HSET user:1001 name "김하늘" grade "GOLD" city "서울"
HGET user:1001 grade          # "GOLD"
HGETALL user:1001             # 전체 필드

# List — 최근 본 상품 10개 유지
LPUSH recent:1001 "p:15"      # 앞에 넣고
LTRIM recent:1001 0 9         # 10개만 남긴다
LRANGE recent:1001 0 -1       # 전체 조회

# Set — 오늘 방문한 유저 (중복 자동 제거)
SADD visit:2026-08-11 "u:1001" "u:1002" "u:1001"
SCARD visit:2026-08-11        # 2 — 유니크 방문자 수

# Sorted Set — 게임 순위표
ZADD rank:weekly 1500 "김하늘" 2100 "박바다" 1800 "이구름"
ZREVRANGE rank:weekly 0 2 WITHSCORES   # 상위 3명, 점수 포함
ZREVRANK rank:weekly "김하늘"          # 내 등수 (0부터)
ZINCRBY rank:weekly 50 "김하늘"        # 점수 가산
고르는 요령 — "이 데이터를 어떻게 꺼낼 것인가"부터 정하세요. 통째로 꺼낸다 → String(JSON), 필드 하나씩 → Hash, 최신 N개 → List, 있는지 확인·집합 연산 → Set, 순서·순위 → Sorted Set. RDBMS처럼 "일단 넣고 나중에 쿼리"가 안 되는 대신, 꺼내는 모양대로 넣어 두면 조회가 O(1)~O(logN)으로 끝납니다.

String(JSON) vs Hash — 객체는 어느 쪽에

기준String + JSONHash
꺼내는 단위항상 통째로 (직렬화/역직렬화)필드 하나씩 읽고 고칠 수 있음
부분 수정전체를 읽어 고쳐 다시 저장HSET user:1 grade GOLD 한 방
숫자 증가불가 (읽고-고치고-쓰기 경합)HINCRBY user:1 points 100 원자적
TTL키 단위 ✓키 단위만 — 필드별 TTL 없음
어울리는 곳캐시 응답처럼 통으로 쓰고 버리는 것계속 갱신되는 상태(유저 프로필·장바구니)
더 있는 것들 — 비트 단위 출석 체크(Bitmap), 오차 0.8%로 유니크 수 세기(HyperLogLog — 수억 명도 12KB), 위치 기반 반경 검색(Geo), 스트림(r10)까지 내장돼 있습니다. 
# Bitmap — 8월 출석 체크 (유저ID를 비트 위치로)
SETBIT attend:2026-08-11 1001 1     # 1001번 유저 오늘 출석
BITCOUNT attend:2026-08-11          # 오늘 출석자 수
# 한 달 개근: BITOP AND 로 31일치를 겹치면 끝

# HyperLogLog — 일간 순방문자(UV)를 12KB 로
PFADD uv:2026-08-11 "u:1001" "u:1002"
PFCOUNT uv:2026-08-11               # 오차 ±0.8% 의 유니크 수
PFMERGE uv:aug uv:2026-08-01 uv:2026-08-02   # 월간 합산
SECTION 06

캐시 전략 — Cache-Aside 패턴

Redis의 사용처 1위는 압도적으로 캐시입니다. 패턴은 사실상 하나만 알면 됩니다 — "없으면 DB에서 읽어 채우고, 있으면 바로 준다".

Cache-Aside(옆에 두는 캐시) — 원본은 언제나 RDBMS, Redis는 복사본입니다. 캐시가 통째로 날아가도 서비스는 (느려질 뿐) 돌아갑니다.

코드로는 이 열 줄입니다 (Python)

import json, redis
r = redis.Redis(decode_responses=True)

def get_product(pid: int) -> dict:
    key = f"cache:product:{pid}"
    cached = r.get(key)                    # ① 캐시 먼저
    if cached:
        return json.loads(cached)          #    히트 — DB 안 감
    row = db_query("SELECT * FROM product WHERE id = %s", pid)   # ② 미스 — 원본 조회
    r.set(key, json.dumps(row), ex=60)     # ③ 60초 캐시
    return row

캐시가 낡는 문제 — 무효화 두 가지

  • TTL로 버틴다 (기본) — "상품 정보는 60초 낡아도 된다"면 TTL만으로 충분합니다. 가장 단순하고 사고가 없습니다.
  • 변경 시 지운다 — 원본을 UPDATE 할 때 DEL cache:product:15 를 함께 실행합니다. 다음 조회가 새 값을 다시 채웁니다. "고쳐 넣기"보다 "지우기"가 정답입니다 — 고쳐 넣기는 동시 요청과 얽혀 낡은 값이 남는 경합이 생깁니다.

실무 디테일 세 가지 — 여기서 급이 갈립니다

# ① TTL 지터 — 같은 시각 대량 만료(스탬피드)를 흩뜨린다
ttl = 60 + random.randint(-10, 10)
r.set(key, val, ex=ttl)

# ② 네거티브 캐시 — "없음"도 잠깐 캐시한다
#    없는 상품 ID 로 계속 두드리는 트래픽(오타·악의적)이 DB 를 뚫는 것 방지
row = db_query(...)
if row is None:
    r.set(key, "__NONE__", ex=30)      # 짧게!
    return None

# ③ 키 버전 — 배포로 응답 구조가 바뀌면 접두사 버전을 올린다
KEY_V = "cache:v2:product:{}"          # 옛 v1 키는 TTL 로 알아서 소멸
#    구조 다른 캐시를 역직렬화하다 터지는 배포 사고를 원천 차단
캐시 스탬피드(stampede) — 인기 키의 TTL이 만료되는 순간, 수백 요청이 동시에 미스가 나서 다 같이 DB로 몰려가는 사고입니다. 대책: ① TTL에 무작위 지터(60±10초)를 줘 만료 시각을 흩뜨린다, ② 락(SET NX)으로 한 요청만 DB에 가게 한다, ③ 아주 인기 있는 키는 만료 전에 백그라운드로 미리 갱신한다.
SECTION 07

실전 레시피 — 세션 · 순위표 · 분산 락

실무에서 Redis가 실제로 맡는 일 네 가지를 그대로 옮길 수 있는 형태로 정리했습니다.

① 세션 저장소

# 로그인 시 — 세션 ID를 키로, 유저 정보를 값으로, 30분 수명
SET session:9f2a71c0 "{\"userId\":1001,\"grade\":\"GOLD\"}" EX 1800

# 매 요청 — 쿠키의 세션 ID로 조회 + 수명 연장
GET session:9f2a71c0
EXPIRE session:9f2a71c0 1800
앱 서버가 여러 대일 때 세션을 서버 메모리에 두면 다른 서버로 간 요청이 로그아웃됩니다. 세션을 Redis로 빼면 어느 서버로 가도 같은 세션을 봅니다 — 서버를 늘릴 수 있게 되는 핵심 전환입니다.

② 순위표 — Sorted Set 그대로

ZINCRBY rank:2026-08 120 "u:1001"        # 점수 올리기
ZREVRANGE rank:2026-08 0 9 WITHSCORES    # 상위 10명
ZREVRANK rank:2026-08 "u:1001"           # 내 등수 — 수백만 명이어도 O(logN)

③ 처리량 제한 (rate limit)

# 유저당 1분에 60회 — 고정 창(fixed window) 방식
INCR ratelimit:u1001:202608111024        # 분 단위 키
EXPIRE ratelimit:u1001:202608111024 60   # 처음 만들 때만 유효
# 결과가 60 을 넘으면 429 Too Many Requests 로 거절

④ 분산 락 — "동시에 한 명만"

# 락 잡기 — NX(없을 때만) + PX(수명) 를 반드시 한 명령으로
SET lock:settle:2026-08-11 "worker-a" NX PX 30000
# OK    → 락 획득, 작업 진행
# (nil) → 다른 프로세스가 작업 중, 포기하거나 대기

# 풀 때 — 내가 잡은 락인지 확인하고 지워야 안전 (Lua 로 원자 처리)
EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:settle:2026-08-11 "worker-a"
락에 수명(PX)을 빼먹으면 락을 잡은 프로세스가 죽는 순간 영원히 아무도 작업을 못 합니다. 수명은 "작업이 최악으로 걸리는 시간 + 여유"로 잡고, 더 엄밀한 보장이 필요하면 라이브러리(Redisson·redis-py 의 lock)를 쓰세요 — 직접 구현은 함정이 많습니다.
SECTION 08

영속성 — RDB · AOF, 메모리인데 왜 남는가

"메모리 저장소면 껐다 켜면 다 날아가나요?" — 설정에 따라 다릅니다. Redis는 두 가지 방식으로 디스크에 백업할 수 있습니다.

방식RDB (스냅샷)AOF (명령 로그)
원리일정 주기로 메모리 전체를 파일로 찍는다쓰기 명령을 전부 파일에 순서대로 적는다
유실 범위마지막 스냅샷 이후 전부 (수 분)기본 설정(everysec) 기준 최대 1초
재시작 속도빠름 — 파일 하나 로드느림 — 명령 재실행 (재작성으로 완화)
비용스냅샷 순간 fork 로 메모리 사용 증가쓰기마다 디스크 IO 추가
 
# redis.conf — 실무 기본형: 둘 다 켠다
save 900 1              # 900초 동안 1개 이상 바뀌면 RDB 스냅샷
save 300 10
appendonly yes          # AOF 켜기
appendfsync everysec    # 1초마다 디스크 동기화 (성능·안전의 균형점)
용도별 선택 — 순수 캐시라면 영속성을 아예 꺼도 됩니다 (죽어도 DB에서 다시 채워지니까). 세션·순위표처럼 날아가면 아픈 데이터가 있다면 RDB+AOF 둘 다 켜세요. 그리고 어느 쪽이든 원본이 Redis뿐인 돈 데이터는 두지 않는다는 원칙이 우선입니다.
SECTION 09

메모리 관리 — maxmemory와 축출

메모리가 차면 어떻게 되는가 — 이 질문의 답을 설정으로 정해 두지 않으면 Redis는 쓰기를 거부하거나(기본), OS가 프로세스를 죽입니다. 

# redis.conf
maxmemory 2gb                    # 한도를 반드시 명시하세요
maxmemory-policy allkeys-lru     # 차면 "가장 오래 안 쓴 키"부터 지운다
정책차면 하는 일 · 언제 쓰나
noeviction (기본)쓰기를 에러로 거부 — 캐시 용도에는 부적합, 데이터 보존 용도라면 이것
allkeys-lru캐시 표준 — 전체 키에서 가장 오래 안 쓴 것부터 축출
volatile-lruTTL 있는 키 중에서만 LRU 축출 — 캐시와 보존 데이터가 섞여 있을 때
allkeys-lfu사용 빈도가 낮은 것부터 — 접근 패턴이 뚜렷할 때 히트율이 더 좋음
메모리 사용량은 INFO memory 로 감시하세요. used_memory 가 maxmemory 에 붙어 다니면 축출이 상시 발생 중이라는 뜻이고 (캐시라면 정상, 세션 저장소라면 사고), mem_fragmentation_ratio 가 1.5를 넘으면 단편화가 심한 상태입니다. 재시작 또는 activedefrag 를 검토합니다.
SECTION 10

Pub/Sub과 Stream — 메시지 전달

Redis는 저장소이면서 가벼운 메시지 배달부도 됩니다. 실시간 알림은 Pub/Sub, 놓치면 안 되는 작업은 Stream입니다.

Pub/Sub — 지금 듣고 있는 사람에게만

# 터미널 A — 구독
SUBSCRIBE chat:room1

# 터미널 B — 발행
PUBLISH chat:room1 "안녕하세요"
# → A 에 즉시 도착. 단, 그 순간 듣고 있던 구독자에게만 (저장 안 됨)
휘발성입니다 — 구독자가 없거나 접속이 끊겨 있으면 메시지는 그냥 사라집니다. 채팅 브로드캐스트·실시간 갱신 알림처럼 놓쳐도 되는 신호에만 쓰세요.

Stream — 기록이 남는 큐

XADD orders:events * type "created" orderId "1001"   # 이벤트 추가 (* = 자동 ID)
XLEN orders:events                                    # 쌓인 개수
XREAD COUNT 10 STREAMS orders:events 0               # 처음부터 읽기

# 소비자 그룹 — 여러 워커가 나눠 처리 + 처리 확인(ACK)
XGROUP CREATE orders:events workers $
XREADGROUP GROUP workers w1 COUNT 10 STREAMS orders:events >
XACK orders:events workers 1691740800000-0
Kafka 가 필요해지기 전까지의 훌륭한 중간 단계입니다. 메시지가 저장되고, 워커를 늘려 나눠 먹고, 실패분을 재처리할 수 있습니다. 하루 수백만 건 수준까지는 Stream으로 충분한 경우가 많고, 그 이상의 파이프라인은 🌐 서버기술 가이드의 Kafka 탭을 보세요.
SECTION 11

복제 · Sentinel · Cluster — 죽지 않게

캐시라도 Redis가 죽으면 그 트래픽이 전부 DB로 쏟아집니다. 규모에 따라 세 단계로 고가용성을 올립니다.

단계구성 · 언제
① 복제(replica)마스터의 복사본을 1대 이상 유지. 읽기 분산 + 수동 승격이 가능해집니다. replicaof 한 줄.
② Sentinel감시 프로세스 3대가 마스터 장애를 합의로 판정하고 자동 승격. 마스터 1 + 복제 N 구조에서의 표준 HA.
③ Cluster데이터 자체를 16384 슬롯으로 나눠 여러 마스터에 분산. 메모리가 한 대에 안 담길 때. 다중 키 명령·트랜잭션에 제약이 생깁니다.
순서를 건너뛰지 마세요 — 한 대로 충분한 서비스에 Cluster를 깔면 운영 복잡도만 삽니다. 대부분의 서비스는 ①복제 + ②Sentinel(또는 클라우드 관리형: ElastiCache·Memorystore)에서 끝납니다. 복제는 비동기라 장애 승격 시 마지막 몇 초의 쓰기가 사라질 수 있다는 것만 기억해 두세요.
SECTION 12

실무 함정 — 이것만은 피하세요

Redis 장애의 대부분은 느린 명령 하나에서 시작합니다. 싱글 스레드라는 것을 잊는 순간 사고가 납니다.

하지 말 것왜 · 대신
KEYS * 운영 금지전체 키를 훑는 O(N) — 그동안 모든 요청이 멈춥니다. 대신 SCAN 으로 조금씩 순회.
빅 키 (수십만 멤버 Hash·ZSet)HGETALL·DEL 한 방이 수백 ms 블로킹. 키를 쪼개고, 지울 땐 UNLINK(백그라운드 삭제).
핫 키 (전 트래픽이 키 하나로)그 키가 있는 서버만 타죽습니다. 로컬 캐시를 앞에 한 겹 더 두거나 키를 복제해 분산.
FLUSHALL 습관전체 삭제 — 운영에서 치는 순간 캐시가 비고 DB가 무너집니다. 접두사 단위 SCAN+UNLINK 로.
트랜잭션 오해MULTI/EXEC 는 롤백이 없습니다 — 명령을 묶어 순서 보장할 뿐. 원자적 복합 연산은 Lua 스크립트가 정답.

명령을 묶는 세 가지 — 헷갈리기 쉬운 구분

방법보장하는 것 · 쓰는 곳
파이프라인왕복(RTT)만 아낀다 — 원자성 없음. 대량 쓰기 속도 수십 배 (r13 예제)
MULTI / EXEC묶음이 끼어들기 없이 순서대로 실행. 단 롤백은 없음 — 중간 명령이 실패해도 나머지는 실행됨
Lua 스크립트읽고-판단하고-쓰는 복합 로직이 통째로 원자적. 분산 락 해제(r07)·재고 차감 같은 "확인 후 변경"의 정답
# Lua 예 — "재고가 있으면 1 차감" 을 경쟁 없이
EVAL "local s = tonumber(redis.call('GET', KEYS[1]))
      if s and s > 0 then return redis.call('DECR', KEYS[1]) end
      return -1" 1 stock:p15
# GET 과 DECR 사이에 다른 요청이 못 끼어든다 — 앱에서 하면 반드시 낀다
# 느린 명령 찾기
SLOWLOG GET 10           # 최근 느린 명령 10개 (기본: 10ms 초과 기록)
LATENCY LATEST           # 지연 이벤트 요약
INFO stats               # keyspace_hits / misses → 캐시 히트율 계산
MEMORY USAGE rank:weekly # 이 키가 먹는 바이트 — 빅 키 조사
redis-cli --bigkeys      # 전체에서 큰 키 후보 훑기 (SCAN 기반이라 안전)
히트율이 성적표입니다 — hits/(hits+misses) 가 캐시 히트율. 90% 이상이면 제 몫을 하는 것이고, 낮다면 TTL이 너무 짧거나 캐시할 가치가 없는 키를 캐시하고 있는 것입니다.

앱에서 쓰기 — Python · Java · Node

언어별 표준 클라이언트와 연결 코드입니다. 풀(pool)을 재사용한다는 원칙은 RDBMS와 같습니다.

Python — redis-py

# pip install redis
import redis

# 커넥션 풀은 모듈 수준에서 한 번만
r = redis.Redis(host="localhost", port=6379,
                decode_responses=True,     # bytes 대신 str 로
                socket_timeout=2)

r.set("greeting", "hello", ex=60)
print(r.get("greeting"))                   # hello

# 파이프라인 — 왕복을 1번으로 묶어 수십 배 빠르게
with r.pipeline() as p:
    for i in range(1000):
        p.set(f"bulk:{i}", i)
    p.execute()

        String hit = redis.opsForValue().get(key);
