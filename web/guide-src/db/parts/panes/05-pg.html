SECTION 01

PostgreSQL은 어떤 DB인가

1986년 버클리에서 시작해 40년 가까이 이어온 오픈소스 DB입니다. 특정 회사 소유가 아니라 커뮤니티가 개발합니다 — 라이선스 정책이 바뀔 위험이 없다는 뜻입니다.

특징내용
라이선스PostgreSQL 라이선스(BSD 계열) — 상용 사용·수정·재배포 전부 자유
표준 준수주요 DB 중 가장 높습니다. 여기서 배운 SQL이 다른 DB로 잘 옮겨집니다
확장성타입·연산자·인덱스·언어를 사용자가 추가할 수 있는 구조. PostGIS·pgvector·TimescaleDB 가 여기서 나옵니다
프로세스 모델커넥션 하나 = OS 프로세스 하나. 그래서 커넥션 풀이 필수입니다
MVCC수정 시 새 행을 만들고 옛 행을 남깁니다 → VACUUM 필요 (p11)
릴리스 주기매년 가을 메이저 1회, 각 버전 5년 지원
버전 선택 — 새로 시작한다면 최신 안정 버전에서 하나 뒤(N-1)가 무난합니다. 확장·클라우드 서비스의 지원이 따라오는 데 시간이 걸리기 때문입니다. 2026년 8월 기준 17 또는 18이 현실적인 선택입니다.

언제 PostgreSQL이 아닌가

  • 회사가 이미 오라클/MySQL로 돌아갈 때 — 기술적 우위보다 운영 경험이 중요합니다
  • 단순 조회만 초당 수만 건 — MySQL이 더 가벼울 수 있습니다(다만 요즘은 차이가 크지 않습니다)
  • 파일 하나로 끝내야 할 때 — SQLite
  • DBA 없이 커넥션 수천 개를 다룰 때 — PgBouncer 같은 풀러를 반드시 붙여야 합니다
SECTION 02

설치 — 전 OS · Docker

설치는 쉽습니다. 중요한 것은 데이터 디렉터리와 접속 설정 파일의 위치를 아는 것입니다.

# Ubuntu · Debian — 공식 PGDG 저장소를 쓰면 최신 버전을 씁니다
sudo apt install -y postgresql-common
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh
sudo apt install -y postgresql-18

# RHEL · Rocky
sudo dnf install -y postgresql18-server
sudo /usr/pgsql-18/bin/postgresql-18-setup initdb
sudo systemctl enable --now postgresql-18

# macOS
brew install postgresql@18 && brew services start postgresql@18

# Docker
docker run -d --name pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=shop -e TZ=Asia/Seoul \
  -v pgdata:/var/lib/postgresql/data postgres:18

중요한 파일 세 개

파일역할
postgresql.conf서버 설정 전부 (메모리·로그·복제) → p17
pg_hba.conf누가 어디서 어떻게 접속할 수 있는지 — 접속 문제의 절반이 여기
PGDATA 디렉터리실제 데이터 파일. Ubuntu는 /var/lib/postgresql/18/main
-- 위치를 잊었을 때 SQL 로 확인
SHOW config_file;

pg_hba.conf — 접속 규칙

# TYPE  DATABASE  USER  ADDRESS         METHOD
local   all       all                   peer          # 유닉스 소켓: OS 계정과 DB 계정이 같아야
host    all       all   127.0.0.1/32    scram-sha-256 # 로컬 TCP
host    shop      app   10.0.1.0/24     scram-sha-256 # 사설망의 app 계정만
hostssl all       all   0.0.0.0/0       scram-sha-256 # 외부는 SSL 필수로

# 위에서부터 순서대로 검사해 처음 일치하는 규칙을 씁니다 ← 순서가 중요
# 고친 뒤: sudo systemctl reload postgresql  (재시작 불필요)
trust 는 절대 쓰지 마세요. 비밀번호 없이 누구나 접속됩니다. 또 md5 는 구식입니다 — scram-sha-256 을 쓰세요(PostgreSQL 14부터 기본값). 옛 클라이언트가 붙지 못하면 클라이언트를 올리는 것이 맞습니다.
Ubuntu에서 sudo -u postgres psql 이 되는 이유 — local … peer 규칙 때문입니다. OS 계정 postgres 로 실행하면 같은 이름의 DB 계정으로 비밀번호 없이 접속됩니다. 비밀번호로 접속하고 싶으면 psql -h 127.0.0.1 -U postgres 처럼 TCP로 붙으세요.
SECTION 03

psql 완전정복

서버에서는 GUI를 못 씁니다. psql의 역슬래시 명령 열 개만 알아도 작업 속도가 완전히 달라집니다.

명령하는 일
\l데이터베이스 목록
\c shopshop 으로 이동
\dt테이블 목록 (\dt+ 는 크기까지)
\d member테이블 구조 · 인덱스 · 제약 (가장 많이 씁니다)
\di · \dv · \df인덱스 · 뷰 · 함수 목록
\du역할(계정) 목록과 권한
\dn스키마 목록
\x세로 출력 토글 — 컬럼이 많을 때 필수
\timing쿼리 실행 시간 표시 토글
\e편집기로 쿼리 작성 (긴 쿼리에 유용)
\i file.sql파일 실행
\copy클라이언트 쪽 CSV 입출력 (서버 권한 불필요)
\watch 2직전 쿼리를 2초마다 반복 — 모니터링에 좋습니다
\? · \h SELECT명령 도움말 · SQL 문법 도움말
\q종료

CSV 입출력

# 내보내기 (클라이언트 파일로)
\copy (SELECT * FROM member WHERE grade='GOLD') TO 'gold.csv' WITH CSV HEADER

# 가져오기
\copy member FROM 'member.csv' WITH CSV HEADER

# 서버 파일 시스템을 쓰는 COPY 는 슈퍼유저 권한이 필요합니다
COPY member FROM '/tmp/member.csv' WITH (FORMAT csv, HEADER true);
COPY 는 압도적으로 빠릅니다. INSERT 를 10만 번 하는 것보다 수십~수백 배 빠르므로 대량 적재는 항상 COPY 를 쓰세요 → 🔌 a10.

셸에서 바로 실행

psql -d shop -c "SELECT count(*) FROM member;"     # 한 줄 실행
psql -d shop -f schema.sql                          # 파일 실행
psql -qtAX -d shop -c "SELECT count(*) FROM member" # 값만 (스크립트용)

# 접속 정보를 환경 변수로
export PGHOST=db.example.com PGPORT=5432 PGUSER=app PGDATABASE=shop
export PGPASSWORD=...        # 또는 ~/.pgpass 파일 (권장)
# ~/.pgpass  (권한은 반드시 600)
# host:port:database:user:password
db.example.com:5432:shop:app:strong-pass
SECTION 04

역할 · 권한 · 스키마

PostgreSQL은 사용자와 그룹을 ROLE 하나로 다룹니다. 그리고 스키마라는 폴더 개념이 있어 한 DB 안을 나눠 쓸 수 있습니다. 

-- 로그인 가능한 역할 = 사용자
CREATE ROLE app LOGIN PASSWORD 'strong-pass';
-- CREATE USER app PASSWORD '…' 와 같습니다

-- 로그인 못 하는 역할 = 그룹
CREATE ROLE readonly;
GRANT readonly TO analyst1, analyst2;

-- 권한 부여
GRANT CONNECT ON DATABASE shop TO app;
GRANT USAGE   ON SCHEMA public TO app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app;
GRANT USAGE   ON ALL SEQUENCES IN SCHEMA public TO app;   -- ★ 자동증가 컬럼에 필요

-- 앞으로 만들어질 객체에도 자동 적용 (이걸 빠뜨려서 자주 막힙니다)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO app;
PostgreSQL 15부터 public 스키마의 기본 권한이 바뀌었습니다. 이전에는 모든 사용자가 public 에 테이블을 만들 수 있었지만, 15부터는 DB 소유자만 가능합니다. 마이그레이션 시 GRANT CREATE ON SCHEMA public TO app; 이 필요할 수 있습니다.

스키마 — 한 DB 안의 네임스페이스

CREATE SCHEMA sales AUTHORIZATION app;
CREATE TABLE sales.orders (...);

-- search_path : 스키마를 안 적었을 때 찾는 순서
SHOW search_path;                    -- "$user", public
SET search_path TO sales, public;    -- 세션 단위
ALTER ROLE app SET search_path TO sales, public;   -- 계정 기본값으로
스키마를 쓰는 실전 패턴 — ① 멀티테넌트에서 고객사별 스키마 ② 한 DB에서 서비스별 분리(주문·회원·정산) ③ 마이그레이션 시 신구 버전 병행
다만 스키마가 수백 개가 되면 pg_dump·통계 관리가 급격히 무거워집니다.

행 수준 보안 (RLS) — 같은 표에서 자기 데이터만

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY own_orders ON orders
  USING (member_id = current_setting('app.member_id')::int);

-- 애플리케이션에서 세션마다 설정
SET app.member_id = '42';
SELECT * FROM orders;    -- 42번 회원의 주문만 보입니다
RLS는 강력하지만 신중히 — 정책이 모든 쿼리에 자동으로 붙으므로 실행계획과 성능에 영향을 줍니다. 또 테이블 소유자와 슈퍼유저는 기본적으로 우회합니다 (FORCE ROW LEVEL SECURITY 로 강제 가능).
SECTION 05

RETURNING · UPSERT · DISTINCT ON

PostgreSQL을 쓰면서 이 셋을 모르면 쓸데없는 왕복 쿼리를 계속 날리게 됩니다.

RETURNING — 바꾼 행을 바로 돌려받기

-- INSERT 하고 생성된 id 를 바로 받기 (SELECT 를 또 할 필요 없음)
INSERT INTO member (name, email) VALUES ('한바다','han@example.com')
RETURNING id, name, joined_at;

-- UPDATE 한 행이 무엇이었는지 확인
UPDATE product SET stock = stock - 1
WHERE  id = 10 AND stock > 0
RETURNING id, name, stock;
-- 0행이 돌아오면 재고가 없었다는 뜻 → 애플리케이션에서 바로 분기 가능

-- DELETE 한 내용을 로그로 남기기
DELETE FROM cart WHERE member_id = 1 RETURNING *;
재고 차감의 정석 — UPDATE … WHERE stock > 0 RETURNING 한 문장이면 조회 → 확인 → 차감의 경합 문제 없이 원자적으로 처리됩니다. 영향 행 수가 0이면 실패로 처리하세요.

UPSERT — ON CONFLICT

-- 있으면 누적, 없으면 삽입
INSERT INTO stock (product_id, qty) VALUES (10, 5)
ON CONFLICT (product_id)
DO UPDATE SET qty = stock.qty + EXCLUDED.qty, updated_at = now();
--                    ↑ 기존 행        ↑ 넣으려던 새 값

-- 이미 있으면 조용히 넘어가기
INSERT INTO tag (name) VALUES ('sale') ON CONFLICT DO NOTHING;

-- 조건부 업데이트
INSERT INTO price (product_id, amount, updated_at) VALUES (10, 45000, now())
ON CONFLICT (product_id) DO UPDATE
  SET amount = EXCLUDED.amount, updated_at = EXCLUDED.updated_at
  WHERE price.amount <> EXCLUDED.amount;      -- 값이 바뀔 때만 UPDATE

DISTINCT ON — 키별 최신 1건 (PostgreSQL 전용)

-- 회원별 가장 최근 주문 1건
SELECT DISTINCT ON (member_id) member_id, id, ordered_at
FROM   orders
ORDER  BY member_id, ordered_at DESC;     -- ★ DISTINCT ON 컬럼이 ORDER BY 맨 앞이어야 합니다
DISTINCT ON — 짧고 빠름
SELECT DISTINCT ON (member_id)
       member_id, id, ordered_at
FROM   orders
ORDER  BY member_id, ordered_at DESC;
표준 방식 — 다른 DB에서도 동작
SELECT member_id, id, ordered_at
FROM  (SELECT *, ROW_NUMBER() OVER
         (PARTITION BY member_id ORDER BY ordered_at DESC) rn
       FROM orders) t
WHERE  rn = 1;
그 밖의 PostgreSQL 편의 문법
· INSERT … SELECT … RETURNING 조합 가능
· UPDATE … FROM other_table 로 다른 표 참조 갱신
· DELETE … USING other_table
· GENERATED ALWAYS AS (a * b) STORED — 계산 컬럼(12+)
· MERGE — 15부터 표준 문법도 지원
SECTION 06

배열 · 범위 · ENUM 타입

한 칸에 여러 값을 담거나, 구간 자체를 값으로 다룹니다. 테이블 하나를 줄일 수 있는 도구입니다.

배열

CREATE TABLE post (
  id    SERIAL PRIMARY KEY,
  title TEXT,
  tags  TEXT[]                       -- 문자열 배열
);
INSERT INTO post (title, tags) VALUES ('DB 입문', ARRAY['db','sql','초보']);

SELECT * FROM post WHERE 'sql' = ANY(tags);        -- 포함 검색
SELECT * FROM post WHERE tags @> ARRAY['db','sql']; -- 둘 다 포함
SELECT title, unnest(tags) AS tag FROM post;        -- 행으로 펼치기
SELECT array_length(tags, 1) FROM post;

CREATE INDEX idx_post_tags ON post USING GIN (tags);   -- 배열 검색 인덱스
배열은 편하지만 관계를 대체하지 않습니다. 태그별 통계·이름 변경·태그 자체의 속성이 필요해지는 순간 별도 테이블 + 조인이 정답입니다. 기준 — 값이 그 행에 종속적이고 개수가 적으면 배열, 독립적으로 관리해야 하면 테이블.

범위 타입 — 구간을 값으로

CREATE TABLE reservation (
  id      SERIAL PRIMARY KEY,
  room_id INT NOT NULL,
  period  TSRANGE NOT NULL,          -- 시각 구간
  -- ★ 같은 방에 겹치는 예약을 DB가 막아 줍니다
  EXCLUDE USING GIST (room_id WITH =, period WITH &&)
);

INSERT INTO reservation (room_id, period)
VALUES (1, '[2026-08-05 10:00, 2026-08-05 12:00)');

-- 겹치면 여기서 에러 → 애플리케이션 검증 없이 정합성 보장
INSERT INTO reservation (room_id, period)
VALUES (1, '[2026-08-05 11:00, 2026-08-05 13:00)');   -- ✗ 충돌
예약·가격 유효기간 시스템의 정석입니다. "겹치는 예약 방지"를 애플리케이션에서 구현하면 동시 요청에서 반드시 뚫립니다. 배타 제약(EXCLUDE)은 DB가 원자적으로 보장합니다.

ENUM · 도메인

CREATE TYPE order_status AS ENUM ('PAID','SHIPPED','CANCELED');
CREATE TABLE orders (id SERIAL, status order_status NOT NULL DEFAULT 'PAID');

ALTER TYPE order_status ADD VALUE 'REFUNDED';    -- 값 추가는 가능 (삭제는 어려움)

-- 도메인 : 제약을 붙인 재사용 타입
CREATE DOMAIN email AS TEXT CHECK (VALUE ~ '^[^@]+@[^@]+\.[^@]+$');
CREATE TABLE member (id SERIAL, mail email);
ENUM 의 함정 — 값 삭제·순서 변경이 사실상 불가능합니다. 상태값이 자주 바뀌는 도메인이라면 코드 테이블 + 외래키가 유지보수에 훨씬 낫습니다. ENUM은 "절대 안 바뀔 소수의 값"에만 쓰세요.
SECTION 07

JSONB — 문서형으로 쓰기

PostgreSQL 하나로 관계형 + 문서형을 커버합니다. "MongoDB를 도입해야 하나?"라는 질문의 답이 대부분 여기입니다. 

CREATE TABLE item (
  id   SERIAL PRIMARY KEY,
  sku  TEXT UNIQUE NOT NULL,
  data JSONB NOT NULL              -- 상품마다 다른 속성들
);

INSERT INTO item (sku, data) VALUES
 ('KB-01', '{"name":"무선 키보드","brand":"LG","price":49000,
             "spec":{"switch":"적축","layout":"텐키리스"},"tags":["무선","사무용"]}');

연산자 — 이 다섯 개면 됩니다

연산자뜻예
->JSON 으로 꺼내기data->'spec'
->>텍스트로 꺼내기data->>'name'
#>>경로로 텍스트 꺼내기data#>>'{spec,switch}'
@>포함 (인덱스 사용 가능)data @> '{"brand":"LG"}'
?키 존재data ? 'discount'
SELECT data->>'name'                AS name,
       (data->>'price')::int         AS price,
       data#>>'{spec,switch}'        AS switch
FROM   item
WHERE  data @> '{"brand":"LG"}'
  AND  (data->>'price')::int < 60000;

-- 배열 펼치기
SELECT sku, jsonb_array_elements_text(data->'tags') AS tag FROM item;

-- 값 수정 (경로 지정)
UPDATE item SET data = jsonb_set(data, '{price}', '45000') WHERE sku = 'KB-01';

-- 키 추가 · 병합
UPDATE item SET data = data || '{"discount":10}'::jsonb WHERE sku = 'KB-01';

-- 키 삭제
UPDATE item SET data = data - 'discount' WHERE sku = 'KB-01';

인덱스

-- ① 범용 GIN — @> · ? 연산자 전부 지원 (인덱스가 큼)
CREATE INDEX idx_item_data ON item USING GIN (data);

-- ② jsonb_path_ops — @> 전용이지만 훨씬 작고 빠릅니다
CREATE INDEX idx_item_data ON item USING GIN (data jsonb_path_ops);

-- ③ 특정 키만 자주 쓴다면 표현식 B-tree 인덱스가 최선
CREATE INDEX idx_item_brand ON item ((data->>'brand'));
SELECT * FROM item WHERE data->>'brand' = 'LG';   -- ← 이 형태여야 인덱스를 탑니다
JSONB 를 남용하면 관계형의 장점을 전부 버리게 됩니다.
· 조건·정렬·조인에 쓰는 값 → 반드시 정식 컬럼으로 (제약·타입·인덱스를 얻습니다)
· 보관만 하는 부가 속성 → JSONB
· 중간 지점이라면 생성 컬럼으로 뽑아내는 방법도 있습니다: ALTER TABLE item ADD COLUMN brand TEXT GENERATED ALWAYS AS (data->>'brand') STORED;
JSON vs JSONB — JSON 은 원문 텍스트 그대로(입력 순서·공백 보존, 조회 때마다 파싱), JSONB 는 이진 저장(파싱 완료, 인덱스 가능, 키 중복 제거, 순서 미보존). 거의 항상 JSONB 입니다.

인덱스 점검 쿼리

-- 안 쓰이는 인덱스 찾기 (지우면 쓰기 성능이 올라갑니다)
SELECT schemaname, relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0 AND indexrelid NOT IN (SELECT conindid FROM pg_constraint)
ORDER  BY pg_relation_size(indexrelid) DESC;

-- 테이블·인덱스 크기
SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS total,
       pg_size_pretty(pg_relation_size(relid))       AS table_only
FROM   pg_catalog.pg_statio_user_tables
ORDER  BY pg_total_relation_size(relid) DESC LIMIT 20;

-- 중복 인덱스 후보 (앞부분이 같은 인덱스)
SELECT indrelid::regclass AS tbl, array_agg(indexrelid::regclass) AS idxs
FROM   pg_index GROUP BY indrelid, indkey HAVING count(*) > 1;

전문 검색 · 한국어

영어는 기본 기능으로 되지만 한국어는 그냥은 안 됩니다. 실무에서 쓰는 방법을 정리합니다.

기본 전문 검색 (영어 기준)

SELECT * FROM post
WHERE  to_tsvector('english', body) @@ to_tsquery('english', 'database & index');

-- 생성 컬럼 + GIN 인덱스 (12+)
ALTER TABLE post ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(title,'') || ' ' || coalesce(body,''))) STORED;
CREATE INDEX idx_post_tsv ON post USING GIN (tsv);

SELECT title, ts_rank(tsv, q) AS rank
FROM   post, to_tsquery('english','database') q
WHERE  tsv @@ q ORDER BY rank DESC;
한국어는 기본 설정으로 제대로 동작하지 않습니다. PostgreSQL의 기본 파서는 공백 기준으로 잘라서 "데이터베이스를"과 "데이터베이스"를 다른 단어로 봅니다. 조사가 붙는 한국어 특성상 검색이 거의 안 걸립니다.

실무에서 쓰는 세 가지 방법

방법내용평가
pg_bigm 2글자(bigram) 단위로 색인. 설치가 간단하고 부분 일치 검색이 잘 됩니다 ★ 국내에서 가장 많이 쓰입니다
pg_trgm 3글자 단위. LIKE '%…%' 를 인덱스로 처리할 수 있게 해 줍니다 유사도 검색·오타 보정에 유용
mecab-ko + textsearch_ko 형태소 분석기. 가장 정확하지만 설치·운영 부담이 큽니다 클라우드 관리형에서는 대부분 불가
-- pg_trgm : LIKE '%검색어%' 를 인덱스로
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_product_name_trgm ON product USING GIN (name gin_trgm_ops);

WHERE  name % '마우스패드'                            -- 기본 임계값 0.3
ORDER  BY sim DESC;

PL/pgSQL — 함수 · 트리거

DB 안에서 도는 로직을 만듭니다. 오라클 PL/SQL과 사고방식은 같고 문법만 다릅니다.

CREATE OR REPLACE FUNCTION total_amount(p_member_id INT)
RETURNS NUMERIC AS $$
DECLARE
    v_total NUMERIC;
BEGIN
    SELECT COALESCE(SUM(oi.qty * oi.unit_price), 0) INTO v_total
    FROM   orders o JOIN order_item oi ON oi.order_id = o.id
    WHERE  o.member_id = p_member_id AND o.status <> 'CANCELED';
    RETURN v_total;
EXCEPTION
    WHEN OTHERS THEN
        RAISE NOTICE '오류: %', SQLERRM;
        RETURN 0;
END;
$$ LANGUAGE plpgsql;

SELECT name, total_amount(id) FROM member;
$$ 는 달러 인용(dollar quoting)입니다. 함수 본문 안에 작은따옴표가 많이 나오므로, 이스케이프 지옥을 피하려고 씁니다. $func$ … $func$ 처럼 이름을 붙일 수도 있습니다(중첩할 때 필요).

여러 행 반환

CREATE OR REPLACE FUNCTION top_members(p_limit INT)
RETURNS TABLE (id INT, name TEXT, total NUMERIC) AS $$
BEGIN
    RETURN QUERY
    SELECT m.id, m.name, total_amount(m.id)
    FROM   member m
    ORDER  BY total_amount(m.id) DESC
    LIMIT  p_limit;
END;
$$ LANGUAGE plpgsql;

SELECT * FROM top_members(3);

트리거 — 갱신 시각 자동 기록

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_member_updated
BEFORE UPDATE ON member
FOR EACH ROW EXECUTE FUNCTION set_updated_at();

감사 로그 트리거

CREATE OR REPLACE FUNCTION audit_member()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO member_audit (member_id, before_data, after_data, changed_at, changed_by)
    VALUES (COALESCE(NEW.id, OLD.id), to_jsonb(OLD), to_jsonb(NEW), now(), current_user);
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_member_audit
AFTER INSERT OR UPDATE OR DELETE ON member
FOR EACH ROW EXECUTE FUNCTION audit_member();
함수 volatility 를 정확히 선언하세요. IMMUTABLE(같은 입력에 항상 같은 출력) · STABLE(한 쿼리 안에서 일정) · VOLATILE(기본값, 매번 다름). 인덱스 표현식에 쓰려면 IMMUTABLE 이어야 하고, 잘못 선언하면 옵티마이저가 잘못된 최적화를 해 결과가 틀어질 수 있습니다.

MVCC와 VACUUM

PostgreSQL 운영에서 가장 중요한 한 가지를 꼽으라면 이것입니다. 모르고 방치하면 어느 날 디스크가 가득 차거나 DB가 멈춥니다.

수정하면 새 행이 생깁니다

UPDATE
기존 행을 고치지 않습니다 새 버전 행을 추가하고, 옛 행에는 "여기까지 유효" 표시(xmax)를 남깁니다.
▼
결과
죽은 행(dead tuple)이 쌓입니다 아무도 보지 않는 옛 버전이 테이블 안에 그대로 남아 공간을 차지합니다.
▼
VACUUM
죽은 행의 공간을 재사용 가능하게 파일 크기가 줄지는 않지만, 그 자리를 새 행이 쓸 수 있게 됩니다.
-- 죽은 행이 얼마나 쌓였나 (운영에서 정기적으로 봐야 하는 쿼리)
SELECT relname,
       n_live_tup   AS 살아있는행,
       n_dead_tup   AS 죽은행,
       ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS 죽은비율,
       last_autovacuum, last_autoanalyze
FROM   pg_stat_user_tables
ORDER  BY n_dead_tup DESC LIMIT 20;
명령하는 일락
VACUUM죽은 행 공간을 재사용 가능하게서비스 중 가능
VACUUM ANALYZE+ 통계 갱신서비스 중 가능
VACUUM FULL파일을 다시 써서 실제로 축소테이블 전체 잠금 — 서비스 중단
pg_repack (확장)VACUUM FULL 과 같은 효과를 락 없이★ 운영에서는 이것
VACUUM FULL 을 운영 중에 절대 실행하지 마세요. 테이블 전체에 배타 락이 걸려 조회조차 막힙니다. 100GB 테이블이면 수십 분간 서비스가 멈춥니다. 공간을 실제로 회수해야 한다면 pg_repack 을 쓰거나 점검 시간에 하세요.

autovacuum 튜닝

# postgresql.conf — 기본값은 작은 서버 기준이라 대용량에서는 못 따라갑니다
autovacuum_vacuum_scale_factor = 0.05      # 기본 0.2 → 5% 만 죽어도 청소
autovacuum_vacuum_cost_limit   = 2000      # 기본 200 → 청소 속도 상향
autovacuum_naptime             = 30s
autovacuum_max_workers         = 5

# 특정 테이블만 더 공격적으로 (변경이 잦은 테이블)
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);

트랜잭션 ID 랩어라운드 — 서비스가 멈추는 사고

-- 남은 여유를 확인 (2억 정도면 경고, 1000만 이하면 비상)
SELECT datname, age(datfrozenxid) AS xid_age,
       2147483648 - age(datfrozenxid) AS 남은여유
FROM   pg_database ORDER BY xid_age DESC;
PostgreSQL의 트랜잭션 ID는 32비트라 약 21억에서 한 바퀴 돕니다. VACUUM이 오래된 행을 "동결(freeze)"해 주지 않으면 DB가 스스로 쓰기를 거부하고 멈춥니다(단일 사용자 모드로만 복구 가능).
원인은 거의 항상 ① 오래 열린 트랜잭션 ② 방치된 복제 슬롯 ③ autovacuum 이 못 따라감. 
-- 오래 열린 트랜잭션 찾기 (VACUUM 을 막는 주범)
SELECT pid, usename, state, now() - xact_start AS 지속시간, query
FROM   pg_stat_activity
WHERE  xact_start IS NOT NULL AND now() - xact_start > interval '5 minutes'
ORDER  BY xact_start;

-- 방치된 복제 슬롯 (WAL 이 무한정 쌓입니다)
SELECT slot_name, active, pg_size_pretty(
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS 밀린양
FROM   pg_replication_slots;

-- 필요하면 정리
SELECT pg_terminate_backend(12345);
SELECT pg_drop_replication_slot('old_slot');
운영 체크리스트 — ① n_dead_tup 비율 ② 5분 이상 열린 트랜잭션 ③ 비활성 복제 슬롯 ④ xid_age. 이 넷만 대시보드에 올려 두면 PostgreSQL 사고의 대부분을 예방합니다.
SECTION 12

EXPLAIN (ANALYZE, BUFFERS)

느린 쿼리는 추측하지 말고 계획을 보세요. PostgreSQL의 실행계획은 정보량이 매우 풍부합니다. 

-- 추정만 (실행 안 함)
EXPLAIN SELECT * FROM orders WHERE member_id = 1;

-- ★ 실제로 실행하고 시간·버퍼까지 (튜닝의 기본형)
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)
SELECT m.name, count(*)
FROM   member m JOIN orders o ON o.member_id = m.id
GROUP  BY m.name;
HashAggregate (cost=45.20..47.20 rows=200 width=40) (actual time=0.412..0.418 rows=4 loops=1) Buffers: shared hit=12 -> Hash Join (cost=15.30..40.10 rows=1020 width=32) (actual time=0.201..0.380 rows=6 loops=1) Hash Cond: (o.member_id = m.id) -> Seq Scan on orders o (actual time=0.010..0.020 rows=6 loops=1) -> Hash (actual time=0.150..0.151 rows=5 loops=1) -> Seq Scan on member m (actual time=0.008..0.012 rows=5 loops=1) Planning Time: 0.180 ms Execution Time: 0.470 ms

읽는 법 — 이 네 가지만 보세요

볼 것의미
rows 추정 vs 실제 rows=1020(추정) vs rows=6(실제) — 차이가 10배 넘으면 통계 문제
Seq Scan 이 있는가 작은 테이블이면 정상. 큰 테이블에 Seq Scan 이면 인덱스를 검토하세요
Buffers: shared hit / read hit 은 메모리, read 는 디스크. read 가 많으면 캐시 부족 또는 과도한 스캔
loops 이 노드가 몇 번 반복됐는가. loops 가 크면 N+1 형태의 중첩 루프입니다

주요 노드 이름

노드뜻
Seq Scan테이블 전체 읽기
Index Scan인덱스로 찾고 테이블에서 행을 읽음
Index Only Scan인덱스만으로 해결 — 가장 빠릅니다(커버링)
Bitmap Heap Scan인덱스로 위치를 모아 정렬해 한 번에 읽기 (중간 선택도)
Nested Loop한 쪽이 작을 때 유리한 조인
Hash Join큰 테이블끼리 등호 조인
Merge Join양쪽이 정렬돼 있을 때
Sort + external merge Disk메모리 부족으로 디스크 정렬 → work_mem 을 올리세요

슬로우 쿼리 찾기 — pg_stat_statements

-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'  (재시작 필요)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- 총 소요 시간 기준 상위 쿼리 ← 튜닝 대상 1순위
SELECT substring(query, 1, 80) AS query,
       calls,
       ROUND(total_exec_time::numeric, 1)      AS 총시간ms,
       ROUND(mean_exec_time::numeric, 2)       AS 평균ms,
       rows
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;

SELECT pg_stat_statements_reset();   -- 통계 초기화
평균이 느린 쿼리보다 "총 시간"이 큰 쿼리를 먼저 잡으세요. 100ms 쿼리가 하루 100만 번 도는 것이, 5초 쿼리가 하루 10번 도는 것보다 서버에 훨씬 큰 부담입니다.
계획을 보기 편하게 — EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) 결과를 explain.depesz.com · explain.dalibo.com 같은 시각화 도구에 붙여 넣으면 병목 노드가 색으로 표시됩니다. 큰 계획을 읽을 때 시간이 크게 절약됩니다.

파티셔닝

큰 테이블을 날짜 등으로 쪼갭니다. 조회는 필요한 조각만 보고, 오래된 데이터는 DROP 한 줄로 즉시 정리됩니다. 

-- 선언적 파티셔닝 (10+)
CREATE TABLE orders (
    id          BIGSERIAL,
    member_id   INT NOT NULL,
    ordered_at  DATE NOT NULL,
    amount      NUMERIC(12,2),
    PRIMARY KEY (id, ordered_at)          -- ★ 파티션 키가 PK 에 포함돼야 합니다
) PARTITION BY RANGE (ordered_at);

CREATE TABLE orders_2026_08 PARTITION OF orders
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE orders_2026_09 PARTITION OF orders
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- 범위 밖 데이터를 받아 줄 기본 파티션 (없으면 INSERT 에러)
CREATE TABLE orders_default PARTITION OF orders DEFAULT;

-- 인덱스는 부모에 만들면 자식에 자동 생성됩니다
CREATE INDEX idx_orders_member ON orders (member_id);

운영

-- 오래된 파티션 분리 (즉시 · 락 최소)
ALTER TABLE orders DETACH PARTITION orders_2025_01 CONCURRENTLY;
DROP TABLE orders_2025_01;

-- 기존 테이블을 파티션으로 편입
ALTER TABLE orders ATTACH PARTITION orders_2026_10
      FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 파티션 목록·크기
SELECT c.relname, pg_size_pretty(pg_relation_size(c.oid))
FROM   pg_class c JOIN pg_inherits i ON i.inhrelid = c.oid
WHERE  i.inhparent = 'orders'::regclass ORDER BY c.relname;
파티션 프루닝이 되려면 WHERE 에 파티션 키가 있어야 합니다. WHERE ordered_at >= '2026-08-01' 은 필요한 파티션만 보지만, WHERE member_id = 1 만 있으면 모든 파티션을 전부 뒤집니다. 파티션 키 선택은 조회 패턴이 결정합니다.
파티션 자동 생성 — PostgreSQL은 오라클의 INTERVAL 파티션 같은 자동 생성이 없습니다. pg_partman 확장을 쓰거나, cron 으로 다음 달 파티션을 미리 만드는 스크립트를 돌리세요. 파티션이 없으면 INSERT 가 실패하므로 반드시 자동화해야 합니다.
언제 파티셔닝을 할까 — 테이블이 수억 행 또는 수백 GB가 되거나, 오래된 데이터를 주기적으로 대량 삭제할 때입니다. 그 이하에서는 인덱스만 잘 잡아도 충분하고, 파티셔닝은 오히려 계획 수립 비용을 늘립니다.

pgvector — AI 검색을 PostgreSQL로

CREATE EXTENSION vector;

CREATE TABLE doc (
  id        SERIAL PRIMARY KEY,
  content   TEXT,
  embedding VECTOR(1536)                  -- 임베딩 모델의 차원 수
);

-- 근사 최근접 인덱스 (HNSW · 정확도와 속도의 균형)
CREATE INDEX ON doc USING hnsw (embedding vector_cosine_ops);

-- 가장 비슷한 문서 5건 (<=> 는 코사인 거리)
SELECT id, content, embedding <=> '[0.1, 0.2, …]'::vector AS distance
FROM   doc
ORDER  BY embedding <=> '[0.1, 0.2, …]'::vector
LIMIT  5;
RAG 시스템에서 별도 벡터 DB를 도입하기 전에 pgvector 를 먼저 검토하세요. 문서 수백만 건 규모까지는 충분하고, 관계형 데이터와 함께 조인할 수 있다는 큰 장점이 있습니다. (권한·메타데이터 필터링이 SQL 한 줄로 됩니다)

postgres_fdw — 다른 DB를 내 것처럼

CREATE EXTENSION postgres_fdw;
CREATE SERVER remote_db FOREIGN DATA WRAPPER postgres_fdw
  OPTIONS (host 'other.example.com', dbname 'legacy', port '5432');
CREATE USER MAPPING FOR app SERVER remote_db OPTIONS (user 'app', password '…');

IMPORT FOREIGN SCHEMA public LIMIT TO (customer)
  FROM SERVER remote_db INTO staging;

SELECT * FROM staging.customer;   -- 원격 테이블을 로컬처럼 조인 가능
클라우드 관리형(RDS·Cloud SQL)에서는 설치 가능한 확장이 제한됩니다. 도입 전에 해당 서비스의 지원 확장 목록을 반드시 확인하세요. 특히 mecab 계열 한글 형태소 확장은 대부분 사용할 수 없습니다.

논리 백업 — pg_dump

# 커스텀 포맷 (압축·병렬 복원 가능) ★ 권장
pg_dump -h localhost -U app -d shop -Fc -f shop.dump

# 병렬 덤프 (디렉터리 포맷)
pg_dump -d shop -Fd -j 4 -f shop_dir/

# 스키마만 · 데이터만
pg_dump -d shop --schema-only -f schema.sql
pg_dump -d shop --data-only   -f data.sql

# 복원
pg_restore -d shop_new -j 4 shop.dump
createdb shop_new && pg_restore -d shop_new shop.dump

# 클러스터 전체 (역할·테이블스페이스 포함)
pg_dumpall -f all.sql
pg_dumpall --globals-only -f globals.sql   # 계정 정보만
pg_dump 는 특정 시점의 일관된 스냅숏을 만들지만, 수백 GB 이상에서는 시간이 너무 오래 걸립니다. 또 덤프 중 오래 열린 트랜잭션이 VACUUM 을 막는 부작용도 있습니다. 대용량은 물리 백업 + PITR 로 가야 합니다.

물리 백업 + PITR — 원하는 시점으로 복구

# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'
# 실무에서는 pgBackRest · WAL-G · barman 같은 도구를 씁니다
# 베이스 백업
pg_basebackup -D /backup/base -Ft -z -P

# 복구 : 데이터 디렉터리를 베이스로 되돌리고
#        WAL 을 원하는 시각까지만 재생
# postgresql.conf 에
#   restore_command = 'cp /backup/wal/%f %p'
#   recovery_target_time = '2026-08-05 13:59:00'
# 그리고 recovery.signal 파일을 만든 뒤 기동
직접 구성하지 마세요. pgBackRest 나 WAL-G 를 쓰면 증분 백업·병렬·S3 업로드·검증까지 자동입니다. 수동 archive_command 는 실패를 놓치기 쉽고, 그러면 WAL 이 무한정 쌓입니다.

postgresql.conf 튜닝

기본 설정은 아주 작은 서버 기준입니다. 메모리 관련 설정 몇 개만 고쳐도 체감이 달라집니다.

설정권장 (RAM 16GB 기준)설명
shared_buffers4GB (RAM의 25%)PostgreSQL 전용 캐시. 너무 크게 잡으면 OS 캐시와 중복됩니다
effective_cache_size12GB (RAM의 75%)실제 할당이 아니라 옵티마이저에게 주는 힌트입니다
work_mem16~64MB정렬·해시마다 이만큼 씁니다. 동시 100세션 × 여러 노드면 곱해집니다
maintenance_work_mem1GBVACUUM·인덱스 생성용. 크게 잡을수록 유지보수가 빨라집니다
max_connections100~200크게 잡지 마세요 — 풀러(PgBouncer)를 쓰는 것이 정답
random_page_cost1.1 (SSD)기본 4.0은 HDD 기준. SSD면 반드시 낮추세요 — 인덱스를 더 잘 씁니다
checkpoint_timeout15min길수록 IO 스파이크가 줄지만 복구가 느려집니다
max_wal_size4GB체크포인트 간격. 작으면 체크포인트가 잦아집니다
log_min_duration_statement1000 (ms)★ 1초 넘는 쿼리를 로그로 — 반드시 켜세요
-- 지금 값 확인
SHOW shared_buffers;
SELECT name, setting, unit, source FROM pg_settings WHERE name LIKE '%mem%';

-- 재시작 없이 반영되는 항목
ALTER SYSTEM SET work_mem = '32MB';
SELECT pg_reload_conf();

-- 재시작이 필요한 항목 (pending_restart 로 확인)

work_mem 은 세션당이 아니라 "정렬·해시 노드당"입니다. 복잡한 쿼리 하나가 정렬 3개 + 해시 2개를 쓰면 work_mem × 5 를 씁니다. 여기에 동시 세션 수를 곱하면 순식간에 메모리가 넘칩니다. 전역은 작게, 무거운 배치 세션에서만 크게 잡는 것이 정석입니다: SET LOCAL work_mem = '256MB';

커넥션 풀러는 선택이 아닙니다

PostgreSQL은 커넥션 하나마다 OS 프로세스를 만듭니다. 커넥션 500개면 프로세스 500개이고, 각각 메모리를 차지합니다. PgBouncer 를 앞에 두면 앱은 수천 커넥션을 쓰더라도 실제 DB 커넥션은 수십 개로 유지됩니다. 

# pgbouncer.ini
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
listen_port = 6432
pool_mode = transaction          # ★ 대부분 이것 (커넥션을 트랜잭션 단위로 재사용)
max_client_conn = 2000
default_pool_size = 25           # 실제 DB 커넥션 수
pool_mode = transaction 에서는 세션 단위 기능을 못 씁니다. SET(세션 변수) · 준비된 문(prepared statement) · LISTEN/NOTIFY · 임시 테이블 등이 깨질 수 있습니다. 드라이버 설정에서 서버 측 prepared statement 를 끄거나, PgBouncer 1.21+ 의 준비된 문 지원을 켜세요.
설정값 계산이 막막하다면 PGTune(pgtune.leopard.in.ua) 에 서버 사양과 워크로드 유형을 넣으면 시작점을 만들어 줍니다. 그 값을 그대로 쓰지 말고, 모니터링하며 조정하세요.
