SECTION 01

MySQL과 MariaDB의 갈림길

2010년 오라클이 MySQL을 인수하자 원 개발자들이 갈라져 나와 만든 것이 MariaDB입니다. 처음엔 거의 같았지만 지금은 꽤 벌어졌습니다.

돈 문제 — "MySQL은 유료, MariaDB는 무료"가 정확히 무슨 뜻인가

  • MySQL을 그냥 서버에 설치해서 쓰는 것은 무료입니다 — Community 판이 GPL 라이선스로 공개되어 있어요. 개인 프로젝트·사내 서비스·웹 서비스 백엔드로 쓰는 데는 돈이 들지 않습니다
  • 돈이 드는 경우는 따로 있습니다 — 내 제품 안에 MySQL을 담아서 팔면서 소스 공개(GPL)를 하기 싫을 때, 또는 오라클의 공식 기술 지원·전용 관리 도구(Enterprise 판)가 필요할 때. 이때 오라클에서 상용 라이선스를 사야 합니다. 이렇게 무료 판과 유료 판이 같이 있는 것을 "이중 라이선스"라고 불러요
  • MariaDB는 유료 판이라는 것 자체가 없습니다 — 전 기능이 GPL 하나로 공개돼 있어서 어떤 상황에서도 오라클(또는 다른 회사)에 라이선스 비용을 낼 일이 없습니다. "완전 오픈소스"를 원하는 회사·공공기관이 MariaDB를 고르는 이유가 이것입니다
  • 요약 — 웹 서비스 만드는 대부분의 경우 둘 다 공짜입니다. 차이가 나는 건 "DB를 제품에 내장해 파는" 소수의 경우와 유료 기술 지원 여부예요
"드롭인 대체 가능"은 이제 옛말입니다. MariaDB 10.x 초반까지는 MySQL 5.7 과 호환됐지만, MySQL 8.0 이후로는 서로 다른 길을 갑니다. JSON 저장 방식·인증 플러그인·복제 프로토콜이 달라 MySQL 8 → MariaDB 로 그냥 옮기면 대부분 실패합니다. 옮기려면 논리 덤프(mysqldump)로 다시 적재하는 방식을 쓰세요.

어느 쪽을 고를까

  • 이미 쓰는 쪽이 있으면 그대로 — 전환 이득보다 리스크가 큽니다
  • 클라우드 관리형을 쓴다면 — AWS RDS·Aurora, GCP Cloud SQL 모두 양쪽을 지원하지만 Aurora MySQL 호환처럼 MySQL 쪽 생태계가 더 넓습니다
  • 완전 오픈소스가 중요하면 — MariaDB (GPL 단일)
  • 이 가이드의 SQL — 표시가 없으면 양쪽에서 동일하게 동작합니다. 다른 부분은 MariaDB 배지로 표시했습니다
버전 지원 상황 (2026-08 기준) — MySQL 5.7은 2023년에 지원 종료됐습니다. 아직 쓰고 있다면 보안 패치가 없는 상태입니다. 8.0도 2026년 4월에 지원이 끝났으므로 현재 기준 신규·운영 모두 8.4 LTS 로 가야 합니다.
SECTION 02

설치 — 전 OS · Docker

설치 자체는 쉽습니다. 초기 비밀번호와 문자셋만 챙기면 됩니다.

# Ubuntu · Debian
sudo apt update && sudo apt install -y mysql-server
sudo systemctl enable --now mysql
sudo mysql_secure_installation        # root 비밀번호·익명계정 제거·원격 root 차단

# RHEL · Rocky
sudo dnf install -y mysql-server
sudo systemctl enable --now mysqld
sudo grep 'temporary password' /var/log/mysqld.log   # 초기 임시 비밀번호

# MariaDB
sudo apt install -y mariadb-server
sudo systemctl enable --now mariadb
sudo mariadb-secure-installation

# macOS
brew install mysql && brew services start mysql

# Docker (문자셋을 처음부터 잡아 두세요)
docker run -d --name my -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=devpass -e MYSQL_DATABASE=shop -e TZ=Asia/Seoul \
  -v mydata:/var/lib/mysql \
  mysql:8.4 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_0900_ai_ci

우분투의 소켓 인증

# 우분투 기본 설치는 root 가 auth_socket 인증이라 sudo 로만 접속됩니다
sudo mysql

# 비밀번호 인증으로 바꾸려면
ALTER USER 'root'@'localhost'
  IDENTIFIED WITH caching_sha2_password BY 'strong-pass';
FLUSH PRIVILEGES;
운영에서는 root 를 소켓 인증으로 두는 편이 더 안전합니다. 비밀번호가 유출돼도 서버에 로그인하지 않으면 쓸 수 없기 때문입니다. 애플리케이션은 어차피 별도 계정을 씁니다.

SECTION 03

클라이언트 · 계정 · 권한

MySQL 계정은 이름@접속위치가 한 세트입니다. 이 개념을 놓치면 "접속이 안 되는" 문제가 반복됩니다. 

-- 계정 만들기 : 접속 위치가 다르면 다른 계정입니다
CREATE USER 'app'@'localhost'  IDENTIFIED BY 'strong-pass';   -- 서버 자신에서만
CREATE USER 'app'@'10.0.1.%'   IDENTIFIED BY 'strong-pass';   -- 사설망에서
CREATE USER 'app'@'%'          IDENTIFIED BY 'strong-pass';   -- 어디서나 (주의)

-- 권한
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app'@'10.0.1.%';
GRANT ALL PRIVILEGES ON shop.* TO 'admin'@'localhost';
FLUSH PRIVILEGES;

-- 확인
SELECT user, host, plugin FROM mysql.user;
SHOW GRANTS FOR 'app'@'10.0.1.%';

-- 회수·삭제
REVOKE DELETE ON shop.* FROM 'app'@'10.0.1.%';
DROP USER 'app'@'%';
가장 흔한 접속 오류
ERROR 1045 (28000): Access denied for user 'app'@'172.17.0.1'
→ 비밀번호가 아니라 그 IP에서 접속할 수 있는 계정이 없는 것입니다. 'app'@'localhost' 만 만들었는데 도커나 다른 서버에서 붙으면 이 오류가 납니다.

인증 플러그인

플러그인설명
caching_sha2_passwordMySQL 8 기본값. 안전하지만 옛 클라이언트가 못 붙습니다
mysql_native_password구식. 8.4에서 기본 비활성화, 향후 제거 예정
auth_socketOS 계정으로 인증 (로컬 전용)
"Authentication plugin 'caching_sha2_password' cannot be loaded" 오류가 나면 클라이언트 라이브러리가 오래된 것입니다. 드라이버를 올리는 것이 정답이고, 임시방편으로만 계정을 ALTER USER … IDENTIFIED WITH mysql_native_password BY '…' 로 바꾸세요. 8.4 부터는 이 플러그인을 쓰려면 서버 설정에서 명시적으로 켜야 합니다.

클라이언트 사용법

mysql -h 127.0.0.1 -P 3306 -u app -p shop     # ★ localhost 대신 IP 를 쓰면 TCP 로 붙습니다
mysql -u app -p -e "SELECT count(*) FROM member;" shop
mysql -u app -p shop < schema.sql              # 파일 실행

# 접속 정보를 파일로 (비밀번호를 명령줄에 노출하지 않기)
# ~/.my.cnf   (권한 600)
# [client]
# user=app
# password=strong-pass
# host=127.0.0.1
SHOW DATABASES;
USE shop;
SHOW TABLES;
SHOW CREATE TABLE member\G      -- \G 는 세로 출력 (읽기 편합니다)
DESC member;
SHOW PROCESSLIST;               -- 지금 도는 쿼리
STATUS;                         -- 접속 정보·문자셋 한눈에
SECTION 04

문자셋 — utf8mb4 함정

한글이 ??? 로 나오거나 이모지 저장에 실패한다면 100% 여기입니다. MySQL 국내 사용에서 가장 유명한 함정입니다.

MySQL의 utf8 은 진짜 UTF-8이 아닙니다. 최대 3바이트만 저장하는 반쪽짜리(utf8mb3)라서 4바이트가 필요한 이모지·일부 한자가 들어가지 않습니다. 항상 utf8mb4 를 쓰세요. (MySQL 8.0부터 서버 기본값이 utf8mb4 로 바뀌었지만, 옛 DB에서 마이그레이션한 경우가 문제입니다) 
-- 현재 상태 점검 (여기 있는 값이 하나라도 utf8mb3 면 손봐야 합니다)
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';

SELECT table_schema, table_name, table_collation
FROM   information_schema.tables
WHERE  table_schema = 'shop';

SELECT table_name, column_name, character_set_name, collation_name
FROM   information_schema.columns
WHERE  table_schema = 'shop' AND character_set_name IS NOT NULL;

네 곳을 모두 맞춰야 합니다

1
서버 설정character-set-server=utf8mb4 — my.cnf
2
데이터베이스 · 테이블 · 컬럼CREATE 할 때 지정하거나 ALTER 로 변경
3
커넥션드라이버의 charset=utf8mb4. JDBC URL 이나 DSN 옵션
4
애플리케이션 · 웹 페이지HTTP 헤더·HTML meta 의 인코딩
# my.cnf
[mysqld]
character-set-server = utf8mb4
collation-server     = utf8mb4_0900_ai_ci     # MariaDB 는 utf8mb4_uca1400_ai_ci 또는 _general_ci

[client]
default-character-set = utf8mb4
-- 기존 DB·테이블 변환 (테이블이 크면 시간이 오래 걸립니다)
ALTER DATABASE shop CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

ALTER TABLE member CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- ★ CONVERT TO 는 데이터를 실제로 변환합니다 (테이블 재작성)
--   DEFAULT CHARACTER SET 만 바꾸면 기존 컬럼은 그대로입니다 — 흔한 실수

콜레이션 — 정렬·비교 규칙

콜레이션동작
utf8mb4_0900_ai_ciMySQL 8 기본. 악센트·대소문자 무시. 대부분 이걸 쓰면 됩니다
utf8mb4_0900_as_cs악센트·대소문자 구분
utf8mb4_bin바이트 그대로 비교. 완전 구분
utf8mb4_general_ci구식·부정확하지만 빠름. MariaDB 에서 아직 기본값인 경우가 있습니다
테이블마다 콜레이션이 다르면 조인이 실패합니다. Illegal mix of collations 오류가 그것입니다. 또 조인 컬럼의 콜레이션이 다르면 인덱스를 못 탑니다 — 조용히 느려지는 형태라 발견이 어렵습니다. DB 전체에 하나의 콜레이션을 강제하세요.
인덱스 길이 제한 — utf8mb4 는 글자당 최대 4바이트라 VARCHAR(255) 인덱스가 1020바이트가 됩니다. InnoDB 의 기본 인덱스 키 제한은 3072바이트(DYNAMIC 행 포맷)이므로 보통 문제없지만, 옛 설정(COMPACT + 767바이트 제한)에서는 Specified key was too long 오류가 납니다. 이때는 컬럼 길이를 줄이거나 접두사 인덱스(KEY (col(191)))를 씁니다.
글자가 깨지면 코드가 아니라 다섯 군데 중 안 맞는 한 곳을 찾아야 합니다.
SECTION 05

스토리지 엔진 InnoDB

MySQL은 테이블마다 저장 엔진을 고를 수 있습니다. 하지만 현실적인 답은 하나입니다 — InnoDB.

엔진트랜잭션락 단위외래키평가
InnoDB✓행 단위✓★ 기본값 · 항상 이것
MyISAM✗테이블 전체✗쓰기 시 전체 잠김 · 크래시에 취약
MEMORY✗테이블✗재시작하면 데이터 소멸
Aria MariaDB부분테이블✗MyISAM 개선판 (크래시 안전)
MyISAM 테이블이 남아 있다면 반드시 전환하세요. ① 트랜잭션이 없어 중간에 실패하면 데이터가 반만 바뀝니다 ② 쓰기가 테이블 전체를 잠가 동시 처리가 안 됩니다 ③ 크래시 시 복구가 불완전합니다 (테이블이 깨집니다) 
-- MyISAM 테이블 찾기
SELECT table_schema, table_name, engine
FROM   information_schema.tables
WHERE  engine = 'MyISAM' AND table_schema NOT IN ('mysql','information_schema','performance_schema');

-- 전환 (테이블 재작성이므로 큰 테이블은 온라인 DDL 도구를 쓰세요 → m13)
ALTER TABLE old_table ENGINE = InnoDB;

InnoDB 의 구조

  • 클러스터드 인덱스 — 데이터가 기본키 순서대로 디스크에 저장됩니다(m09)
  • 버퍼 풀 — 메모리 캐시. 가장 중요한 설정이며 RAM의 50~70%를 줍니다(m16)
  • redo 로그 — 커밋을 보장하는 로그. ib_logfile
  • undo 로그 — MVCC와 롤백용 옛 버전 저장
  • MVCC — 읽기가 쓰기를 막지 않습니다(🧬 z05)
-- 테이블별 크기와 행 수 (근사치)
SELECT table_name,
       engine,
       table_rows,
       ROUND(data_length /1024/1024, 1) AS 데이터MB,
       ROUND(index_length/1024/1024, 1) AS 인덱스MB
FROM   information_schema.tables
WHERE  table_schema = 'shop'
ORDER  BY data_length + index_length DESC;
table_rows 는 추정치입니다. InnoDB는 정확한 행 수를 저장하지 않습니다. 정확한 값이 필요하면 SELECT COUNT(*) 를 해야 하고, 이는 큰 테이블에서 느립니다. 화면에 총 건수를 항상 표시하는 설계는 대용량에서 재검토 대상입니다.
"왜 커밋이 이렇게 빠르지"의 답은 로그에 먼저 쓰기 하나입니다.
SECTION 06

AUTO_INCREMENT · LIMIT · IFNULL

MySQL에서 특히 편한 문법들입니다. 다른 DB로 옮길 때 바뀌는 지점이기도 합니다.

-- 자동 증가
CREATE TABLE member (
  id    INT AUTO_INCREMENT PRIMARY KEY,
  name  VARCHAR(50) NOT NULL,
  email VARCHAR(120) UNIQUE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO member (name) VALUES ('김하늘');
SELECT LAST_INSERT_ID();          -- 방금 생성된 id (같은 커넥션 안에서만 유효)

-- 시작값 변경
ALTER TABLE member AUTO_INCREMENT = 1000;
AUTO_INCREMENT 값은 재시작 후 되돌아갈 수 있었습니다. MySQL 5.7 이하는 값을 메모리에만 두어 재시작 시 max(id)+1 로 리셋됐고, 삭제된 행의 번호가 재사용되는 문제가 있었습니다. 8.0부터는 redo 로그에 기록되어 이 문제가 사라졌습니다. 5.7 을 쓰고 있다면 이 동작을 반드시 알고 있어야 합니다. 
-- 페이징
SELECT * FROM product ORDER BY price DESC LIMIT 10;          -- 상위 10건
SELECT * FROM product ORDER BY price DESC LIMIT 20, 10;      -- 21번째부터 10건
SELECT * FROM product ORDER BY price DESC LIMIT 10 OFFSET 20; -- 위와 동일

-- NULL 처리
SELECT IFNULL(email, '(없음)')        FROM member;
SELECT COALESCE(email, phone, '(없음)') FROM member;   -- 여러 개면 COALESCE
SELECT NULLIF(a, b);
SELECT IF(grade='GOLD', '우수', '일반') FROM member;   -- MySQL 전용 IF 함수

-- 문자열
SELECT CONCAT(name, ' 님')            FROM member;    -- ★ || 는 OR 입니다
SELECT CONCAT_WS(' / ', city, grade)  FROM member;    -- 구분자로 연결 (NULL 무시)
SELECT GROUP_CONCAT(name ORDER BY id SEPARATOR ', ') FROM member;
MySQL의 || 는 문자열 결합이 아니라 OR 입니다. SELECT 'a' || 'b' 는 0 을 돌려줍니다. 반드시 CONCAT() 을 쓰세요. (sql_mode 에 PIPES_AS_CONCAT 을 추가하면 표준처럼 되지만, 설정에 의존하는 코드는 다른 서버에서 깨집니다)

sql_mode — 엄격 모드를 켜세요

SELECT @@sql_mode;

-- 권장 설정 (MySQL 8 기본값에 가깝습니다)

 'ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,
  ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
엄격 모드가 꺼져 있으면 MySQL이 조용히 데이터를 바꿉니다. VARCHAR(10) 에 20글자를 넣으면 경고만 내고 잘라서 저장하고, DATE 에 '0000-00-00' 이 들어갑니다. 운영 DB에서 데이터가 이상한 원인의 상당수가 이것입니다. 반드시 켜세요.

SECTION 09

클러스터드 인덱스 구조

InnoDB는 데이터를 기본키 순서대로 디스크에 저장합니다. 이 사실 하나가 기본키 설계·인덱스 성능·UUID 문제를 전부 설명합니다.

InnoDB 에서 기본키는 "행을 구분하는 번호"가 아니라 데이터가 디스크에 놓이는 순서 그 자체입니다.
기본키 인덱스
리프 노드에 데이터 전체가 들어 있습니다 기본키로 찾으면 한 번에 행 전체를 얻습니다. 가장 빠른 조회입니다.
▼
보조 인덱스
리프에 기본키 값이 들어 있습니다 보조 인덱스로 찾으면 기본키를 얻고, 그것으로 다시 기본키 인덱스를 탑니다(2단계).
이 구조의 결과
① 기본키가 크면 모든 보조 인덱스가 커집니다(전부 기본키 값을 담으므로)
② 기본키가 무작위면 INSERT 마다 디스크의 다른 위치에 써야 해 느려집니다
③ 커버링 인덱스(필요한 컬럼이 인덱스에 다 있음)면 2단계를 건너뜁니다

UUID를 기본키로 쓰면 안 되는 이유

✗ 무작위 UUID v4
id CHAR(36) PRIMARY KEY    -- '9f8b...' 무작위

-- 문제
-- · 삽입 위치가 매번 달라 페이지 분할이 빈발
-- · 36바이트가 모든 보조 인덱스에 복사됨
-- · 버퍼 풀 효율 급락
-- 수천만 건에서 INSERT 성능이 몇 배 차이납니다
✓ 순차 대리키 또는 정렬 가능한 ID
id BIGINT AUTO_INCREMENT PRIMARY KEY

-- 외부 노출용 UUID 가 필요하면 별도 컬럼
uuid BINARY(16) UNIQUE

-- 또는 시간 순 정렬되는 UUID v7 / ULID 를
-- BINARY(16) 로 저장 (문자열 X)
-- UUID 를 꼭 써야 한다면 : 문자열이 아니라 16바이트 이진으로
ALTER TABLE member ADD COLUMN uid BINARY(16) UNIQUE;
INSERT INTO member (uid) VALUES (UUID_TO_BIN(UUID(), 1));   -- 두 번째 인자 1 = 시간순 정렬
SELECT BIN_TO_UUID(uid, 1) FROM member;

기본키를 명시하지 않으면

InnoDB는 기본키가 없으면 첫 번째 NOT NULL UNIQUE 인덱스를 쓰고, 그것도 없으면 보이지 않는 6바이트 내부 키를 만듭니다. 이 경우 복제·백업·성능 모두 불리합니다. 모든 테이블에 기본키를 명시하세요. 

-- 기본키 없는 테이블 찾기
SELECT t.table_schema, t.table_name
FROM   information_schema.tables t
LEFT   JOIN information_schema.table_constraints c
       ON c.table_schema = t.table_schema AND c.table_name = t.table_name
       AND c.constraint_type = 'PRIMARY KEY'
WHERE  t.table_schema = 'shop' AND c.constraint_name IS NULL;

SECTION 11

갭 락 · 데드락

MySQL은 없는 행에도 락을 겁니다. InnoDB 데드락의 상당수가 여기서 나오며, 다른 DB에서 오면 반드시 당황하게 됩니다.

데드락은 버그가 아니라 정상 동작입니다. 없애는 게 아니라 줄이고, 재시도로 받아내는 것이 목표입니다.
락 종류범위
레코드 락인덱스의 특정 레코드에 거는 락
갭 락 (Gap Lock)레코드 사이의 빈 공간에 거는 락. 그 구간에 새 행을 못 넣게 합니다
넥스트 키 락레코드 락 + 그 앞의 갭 락. REPEATABLE READ 의 기본 동작
인텐션 락테이블 수준의 의도 표시 (행 락과 테이블 락의 충돌 감지용)
-- id 가 10, 20, 30 인 행만 있을 때
BEGIN;
SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;
-- 20 행에 레코드 락 + (10,20) (20,30) 구간에 갭 락
-- → 다른 세션이 id=17 을 INSERT 하려 하면 대기합니다 (존재하지도 않는 행인데!)
왜 이렇게 만들었나 — REPEATABLE READ 에서 팬텀 리드를 막기 위해서입니다. "조건에 맞는 행이 트랜잭션 중간에 새로 생기는" 것을 방지합니다. PostgreSQL은 같은 문제를 다른 방식(스냅숏)으로 풀기 때문에 갭 락이 없습니다.

데드락 진단

-- 마지막 데드락 상세 (가장 중요한 명령)
SHOW ENGINE INNODB STATUS\G
-- 출력의 "LATEST DETECTED DEADLOCK" 섹션을 보세요

-- 지금 대기 중인 락 (8.0+)
SELECT r.trx_id AS 대기중, r.trx_mysql_thread_id AS 대기스레드, r.trx_query AS 대기쿼리,
       b.trx_id AS 차단중, b.trx_mysql_thread_id AS 차단스레드, b.trx_query AS 차단쿼리
FROM   performance_schema.data_lock_waits w
JOIN   information_schema.innodb_trx r ON r.trx_id = w.requesting_engine_transaction_id
JOIN   information_schema.innodb_trx b ON b.trx_id = w.blocking_engine_transaction_id;

-- 오래 열린 트랜잭션
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS 지속초, trx_query
FROM   information_schema.innodb_trx
ORDER  BY trx_started;

-- 강제 종료
KILL 12345;

데드락을 줄이는 네 가지

  • 접근 순서를 통일하세요. 모든 트랜잭션이 A → B 순서로 잠그면 데드락이 원천적으로 안 생깁니다. 가장 효과적인 대책입니다.
  • 트랜잭션을 짧게. 외부 API 호출·사용자 입력 대기를 트랜잭션 안에 두지 마세요.
  • 적절한 인덱스. 인덱스가 없으면 훨씬 넓은 범위에 락이 걸립니다. WHERE status = 'X' 에 인덱스가 없으면 사실상 테이블 전체가 잠깁니다.
  • 재시도를 코드에 넣으세요. 데드락은 완전히 없앨 수 없습니다. MySQL이 한쪽을 자동으로 롤백시키므로, 애플리케이션이 1~3회 재시도하면 대부분 성공합니다(🔌 a11).
-- 락 대기 시간 설정
SELECT @@innodb_lock_wait_timeout;      -- 기본 50초 — 너무 깁니다
SET SESSION innodb_lock_wait_timeout = 5;

-- 대기하지 않고 즉시 실패 / 잠긴 행은 건너뛰기 (8.0+)
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;
SELECT * FROM job_queue WHERE status='READY' LIMIT 10 FOR UPDATE SKIP LOCKED;
FOR UPDATE SKIP LOCKED 는 작업 큐 구현의 정석입니다. 워커 여러 대가 같은 큐 테이블에서 서로 다른 작업을 집어가게 됩니다. 락 대기 없이 동시 처리량이 올라갑니다.

DELIMITER $$
-- ↑ 프로시저 안에 세미콜론이 있어서 구분자를 잠시 바꿉니다

CREATE PROCEDURE grade_up(IN p_id INT, OUT p_result VARCHAR(50))
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_result = '실패';
    END;

    START TRANSACTION;
      UPDATE member SET grade = 'GOLD' WHERE id = p_id;
      IF ROW_COUNT() = 0 THEN
          SET p_result = '대상 없음';
      ELSE

SECTION 13

파티셔닝 · 온라인 DDL

수천만 건 테이블에 컬럼을 추가하는 순간 서비스가 멈출 수 있습니다. 운영 중 스키마 변경은 별도의 기술입니다.

온라인 DDL — ALGORITHM 과 LOCK

-- 무엇이 가능한지 명시적으로 요구하고, 안 되면 에러를 받으세요
ALTER TABLE orders
  ADD COLUMN memo VARCHAR(200),
  ALGORITHM=INSTANT;              -- 즉시 (8.0+ · 메타데이터만 변경)

ALTER TABLE orders
  ADD INDEX idx_dt (ordered_at),
  ALGORITHM=INPLACE, LOCK=NONE;   -- 테이블 재작성 없이 · 읽기·쓰기 허용

-- ALGORITHM 을 안 적으면 MySQL 이 알아서 고르는데
-- COPY 가 선택되면 테이블 전체를 복사하며 오래 잠깁니다
작업가능한 알고리즘
컬럼 추가 (맨 뒤)INSTANT (8.0.12+)
컬럼 삭제INSTANT (8.0.29+) · 그 이전은 INPLACE
인덱스 추가·삭제INPLACE · LOCK=NONE
컬럼 타입 변경COPY — 테이블 재작성, 오래 걸립니다
기본키 변경COPY
문자셋 변환COPY
온라인 DDL 이라도 시작과 끝에 짧은 메타데이터 락(MDL)이 필요합니다. 그 순간 오래 도는 쿼리가 하나라도 있으면 ALTER 가 그것을 기다리고, 그 뒤의 모든 쿼리가 ALTER 를 기다리며 순식간에 커넥션이 폭발합니다. DDL 전에 긴 트랜잭션이 없는지 반드시 확인하세요.

파티셔닝

CREATE TABLE orders (
    id         BIGINT AUTO_INCREMENT,
    member_id  INT NOT NULL,
    ordered_at DATE NOT NULL,
    PRIMARY KEY (id, ordered_at)          -- ★ 파티션 키가 모든 유니크 키에 포함돼야 합니다
)
PARTITION BY RANGE (TO_DAYS(ordered_at)) (
    PARTITION p2026_07 VALUES LESS THAN (TO_DAYS('2026-08-01')),
    PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
    PARTITION pmax     VALUES LESS THAN MAXVALUE
);

ALTER TABLE orders DROP PARTITION p2026_07;      -- 즉시 삭제
ALTER TABLE orders REORGANIZE PARTITION pmax INTO (
    PARTITION p2026_09 VALUES LESS THAN (TO_DAYS('2026-10-01')),
    PARTITION pmax     VALUES LESS THAN MAXVALUE
);
MySQL 파티셔닝의 제약
① 모든 유니크 키(기본키 포함)에 파티션 키가 들어가야 합니다 — 설계를 크게 제약합니다
② 외래키를 쓸 수 없습니다
③ WHERE 에 파티션 키가 없으면 모든 파티션을 뒤집니다
이 때문에 실무에서는 파티셔닝 대신 애플리케이션 레벨 샤딩이나 아카이브 테이블 분리를 택하는 경우도 많습니다.
"개발에서는 3초였는데 운영에서 30분"이 이 표를 몰라서 생깁니다.

복제 · 이중화

MySQL 복제는 구성이 간단해 널리 쓰입니다. 복제 지연만 이해하면 됩니다. 

# 소스(Primary) my.cnf
server-id        = 1
log_bin          = mysql-bin
binlog_format    = ROW              # ★ ROW 를 쓰세요 (STATEMENT 는 비결정적 함수에서 어긋납니다)
gtid_mode        = ON
enforce_gtid_consistency = ON

# 레플리카 my.cnf
server-id        = 2
read_only        = ON
super_read_only  = ON               # 관리자도 실수로 못 쓰게
-- 소스에서 복제 계정
CREATE USER 'repl'@'10.0.1.%' IDENTIFIED BY 'repl-pass';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.0.1.%';

-- 레플리카에서 (8.0.23+ 용어)
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.1.10', SOURCE_USER='repl', SOURCE_PASSWORD='repl-pass',
  SOURCE_AUTO_POSITION=1;
START REPLICA;

-- 상태 확인 ★ 가장 중요한 명령
SHOW REPLICA STATUS\G
--   Replica_IO_Running: Yes
--   Replica_SQL_Running: Yes
--   Seconds_Behind_Source: 0      ← 이 값이 복제 지연(초)
복제는 비동기입니다. 커밋 성공 ≠ 레플리카 도착 — 이 시간차를 설계에 넣어야 합니다.
복제 지연은 반드시 생깁니다. 비동기 복제라 소스에서 커밋된 데이터가 레플리카에 수 ms ~ 수 분 뒤에 도착합니다.
· 대량 UPDATE 를 한 방에 치면 레플리카가 그것을 따라 하느라 수 분간 밀립니다
· 그동안 레플리카를 보는 화면은 옛 데이터를 보여 줍니다
· 쓰기 직후 조회는 소스로 보내야 합니다

지연 모니터링

-- Seconds_Behind_Source 는 부정확할 때가 있습니다
-- 하트비트 테이블을 두고 실제 지연을 재는 방식이 정확합니다 (pt-heartbeat)
SELECT NOW() - ts AS 실제지연 FROM heartbeat ORDER BY ts DESC LIMIT 1;

-- 병렬 복제로 지연 줄이기 (8.0+)

SECTION 15

백업 · 시점 복구

mysqldump 만 알아도 절반은 됩니다. 큰 DB는 물리 백업 + binlog가 필요합니다. 

# 논리 백업 — 반드시 --single-transaction 을 붙이세요 (InnoDB 일관성 스냅숏)
mysqldump -u root -p \
  --single-transaction --routines --triggers --events \
  --source-data=2 \                 # binlog 위치를 주석으로 기록 (시점 복구에 필요)
  shop > shop_$(date +%F).sql

# 여러 DB · 전체
mysqldump --all-databases --single-transaction > all.sql

# 압축하며
mysqldump --single-transaction shop | gzip > shop.sql.gz

# 복원
mysql -u root -p shop < shop.sql
zcat shop.sql.gz | mysql -u root -p shop
--single-transaction 없이 덤프하면 데이터가 어긋납니다. 덤프 도중에도 다른 트랜잭션이 계속 쓰기 때문에, 회원 테이블은 10시 기준, 주문 테이블은 10시 3분 기준인 백업이 만들어집니다. 복원하면 주문은 있는데 회원이 없는 상태가 됩니다.
다만 이 옵션은 InnoDB 에서만 유효합니다 — MyISAM 이 섞여 있으면 소용없습니다.

물리 백업 — XtraBackup

# 수백 GB 이상이면 mysqldump 로는 시간이 감당이 안 됩니다
xtrabackup --backup --target-dir=/backup/full --user=root --password=...
xtrabackup --prepare --target-dir=/backup/full

# 증분 백업
xtrabackup --backup --target-dir=/backup/inc1 --incremental-basedir=/backup/full

# 복원
systemctl stop mysql
xtrabackup --copy-back --target-dir=/backup/full
chown -R mysql:mysql /var/lib/mysql
systemctl start mysql

시점 복구 (PITR)

# 시나리오: 14:30 에 실수로 DELETE. 13:00 백업 + binlog 로 14:29 까지 복구

# 1) 백업 복원
mysql -u root -p < shop_backup.sql

# 2) binlog 를 그 시점까지만 재생
mysqlbinlog --start-position=1234567 \
            --stop-datetime="2026-08-05 14:29:00" \
            /var/lib/mysql/mysql-bin.00042 | mysql -u root -p

# 특정 트랜잭션만 건너뛰려면 GTID 로
mysqlbinlog --exclude-gtids='uuid:100' ... | mysql -u root -p
binlog 보존 기간을 확인하세요. binlog_expire_logs_seconds 기본값은 30일입니다. 이 기간보다 오래된 시점으로는 복구할 수 없습니다. 백업 주기와 binlog 보존 기간을 함께 설계해야 합니다.
복구 훈련을 하세요. "백업 파일은 매일 만들어지고 있다"는 사실만으로는 아무것도 보장되지 않습니다. 분기마다 실제로 다른 서버에 복원해 보고, 복구에 걸리는 시간(RTO)과 잃게 되는 데이터 범위(RPO)를 숫자로 알고 있어야 합니다.

설정권장 (RAM 16GB 전용 서버)설명

SECTION 17

MariaDB 전용 기능

MariaDB를 쓴다면 이 기능들이 코드를 상당히 줄여 줍니다.

시퀀스 — MySQL에는 없습니다

CREATE SEQUENCE seq_order START WITH 1000 INCREMENT BY 1;

SELECT NEXT VALUE FOR seq_order;
INSERT INTO orders (id) VALUES (NEXT VALUE FOR seq_order);

-- 테이블마다 별도 채번이 필요하거나, 여러 테이블이 번호를 공유해야 할 때 유용합니다

시스템 버전 테이블 — 이력이 자동으로 쌓입니다

CREATE TABLE member (
  id    INT PRIMARY KEY,
  name  VARCHAR(50),
  grade VARCHAR(10)
) WITH SYSTEM VERSIONING;

UPDATE member SET grade = 'GOLD' WHERE id = 1;

-- 과거 시점의 데이터를 그대로 조회
SELECT * FROM member FOR SYSTEM_TIME AS OF TIMESTAMP '2026-08-01 00:00:00';

-- 변경 이력 전체
SELECT *, ROW_START, ROW_END FROM member FOR SYSTEM_TIME ALL WHERE id = 1;
감사 이력 테이블을 직접 만들 필요가 없어집니다. 트리거·이력 테이블·조회 쿼리를 전부 대체합니다. 다만 데이터가 계속 쌓이므로 파티셔닝과 보존 정책을 함께 설계해야 합니다.

그 밖의 유용한 기능

기능내용
RETURNINGINSERT·DELETE 결과를 바로 반환 (10.5+) — PostgreSQL 처럼
INSERT … RETURNINGINSERT INTO t (a) VALUES (1) RETURNING id;
Galera Cluster동기식 다중 마스터 클러스터가 내장
ColumnStore컬럼 지향 엔진 — 분석 쿼리에 특화

MariaDB 전용 기능을 쓰면 MySQL 로 돌아갈 수 없습니다. 시퀀스·시스템 버전 테이블·RETURNING 을 쓴 코드는 MySQL에서 동작하지 않습니다. 이식성이 중요한 프로젝트라면 어느 쪽에서도 동작하는 문법만 쓰는 것이 장기적으로 안전할 수 있습니다.
다음으로 — 인덱스와 실행계획을 더 깊이 보려면 ⚙️ 설계 · 튜닝 탭, InnoDB의 내부 동작(MVCC·버퍼 풀·redo/undo)은 🧬 전문가 탭, 애플리케이션 연결은 🔌 앱 연동 탭으로 이어집니다.
