LOG 05

MySQL 의 로그 다섯 개 — 이름이 비슷해서 헷갈립니다

MySQL 문서에는 "로그"가 다섯 번 나옵니다. 세 개는 사람이 읽는 것이고 두 개는 엔진이 읽는 것입니다. 이 구분만 잡으면 나머지는 쉽습니다.

MySQL 로그 다섯 — 왼쪽은 스위치, 오른쪽은 엔진의 일부입니다.

슬로우 쿼리 로그 — 실무에서 제일 많이 켭니다

# my.cnf — 재시작 없이도 대부분 SET GLOBAL 로 바꿀 수 있습니다
[mysqld]
slow_query_log      = ON
slow_query_log_file = /var/log/mysql/mysql-slow.log
long_query_time     = 0.2          # 초. 소수점 가능 (0.2 = 200ms)
log_output          = FILE         # FILE | TABLE | FILE,TABLE

log_queries_not_using_indexes = ON # ★ 느리지 않아도 인덱스 안 타면 기록
log_throttle_queries_not_using_indexes = 60   # 분당 60건으로 제한
min_examined_row_limit = 100       # 100행 미만은 무시 (노이즈 제거)
log_slow_admin_statements = ON     # ALTER TABLE 같은 것도
log_slow_replica_statements = ON   # 레플리카에서 느린 적용도
-- 지금 바로 켜기 (재시작 없이)
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;
-- 주의: long_query_time 은 새 커넥션부터 적용됩니다.
--       커넥션 풀이면 풀을 비워야 반영됩니다.

SHOW GLOBAL STATUS LIKE 'Slow_queries';   -- 누적 건수
log_queries_not_using_indexes 의 함정 — 작은 마스터 테이블(코드값 20행)은 풀스캔이 정답인데도 전부 기록됩니다. min_examined_row_limit 과 log_throttle_… 을 같이 걸지 않으면 로그가 노이즈로 가득 차서 아무도 안 보게 됩니다.

슬로우 로그 한 건은 이렇게 생겼습니다

# Time: 2026-09-01T03:11:07.482913+09:00
# User@Host: app[app] @ 10.0.3.14 []  Id: 918233
# Query_time: 0.812431  Lock_time: 0.000112
#   Rows_sent: 3  Rows_examined: 1998412        ← ★ 여기가 핵심
SET timestamp=1788282667;
SELECT * FROM orders WHERE status = 'PAID';
필드읽는 법
Query_time총 소요 시간(초)
Lock_time락 대기. 이게 크면 쿼리가 아니라 동시성 문제
Rows_sent실제로 돌려준 행 수
Rows_examined훑은 행 수. sent 와 차이가 크면 인덱스 문제
한 줄 판정법 — Rows_examined / Rows_sent 가 수백~수만 배면 인덱스가 없거나 안 타는 것입니다. 이 비율 하나로 손볼 쿼리의 90%가 걸러집니다.

나머지 로그들 — 언제 쓰고 언제 끄나 🟢 기초

로그설정언제 쓰나주의
에러 로그log_error시작 실패 · 크래시 복구 · 복제 끊김항상 켜 둡니다. 끄는 옵션이 사실상 없습니다
제너럴 로그general_log"앱이 대체 무슨 쿼리를 보내나"를 볼 때운영 금지 수준. 모든 쿼리를 기록해 성능이 크게 떨어집니다
슬로우 로그slow_query_log느린 쿼리 찾기 (lg09)임계값을 0 으로 두면 제너럴 로그와 같아집니다
redoinnodb_redo_log_capacity8.0.30+크래시 복구. 사람이 읽지 않습니다작으면 체크포인트가 잦아 쓰기가 느려집니다
undoinnodb_undo_*롤백 · MVCC 스냅샷긴 트랜잭션이 있으면 undo 가 안 지워져 계속 커집니다
binloglog_bin복제 · PITR · CDC (lg06)기본 켜짐8.0+. 보존 기간을 안 정하면 디스크가 찹니다
redo 와 binlog 는 왜 둘 다 있나 — 층이 다릅니다. redo 는 InnoDB(스토리지 엔진)의 것으로 "페이지를 어떻게 바꿨나"를 물리적으로 적고, binlog 는 MySQL 서버 계층의 것으로 "무슨 변경이 있었나"를 논리적으로 적습니다. 엔진을 바꿔도(MyISAM 등) binlog 는 남고, 복제·CDC 는 binlog 만 봅니다.
커밋할 때 둘이 어긋나지 않도록 내부 2단계 커밋(redo prepare → binlog write → redo commit)을 거칩니다. 그래서 sync_binlog = 1 과 innodb_flush_log_at_trx_commit = 1 을 같이 켜야 "커밋했다고 답한 것은 절대 안 사라진다"가 성립합니다.

performance_schema 로 로그 없이 보기 🟡 중급

sys 스키마 — pg_stat_statements 의 MySQL 판

-- 총 소요 시간 상위 (파라미터를 지운 쿼리 모양별 집계)
SELECT query, exec_count, total_latency, avg_latency, rows_examined_avg
  FROM sys.statement_analysis
 ORDER BY total_latency DESC
 LIMIT 10;

-- 풀스캔을 하는 쿼리만
SELECT * FROM sys.statements_with_full_table_scans LIMIT 10;

-- 임시 테이블을 디스크에 만드는 쿼리
SELECT * FROM sys.statements_with_temp_tables LIMIT 10;

-- 초기화
CALL sys.ps_truncate_all_tables(FALSE);
파일 로그보다 이쪽이 편할 때 — 관리형 DB(RDS · Cloud SQL)는 파일에 직접 접근하기 번거롭습니다. sys 스키마는 SQL 로 바로 조회되니 대시보드를 만들기도 쉽습니다. 대신 재시작하면 초기화되고 개별 실행의 파라미터는 남지 않습니다 — 그건 슬로우 로그의 몫입니다.

MariaDB 를 쓴다면

-- MariaDB 는 슬로우 로그에 실행계획까지 붙일 수 있습니다
SET GLOBAL log_slow_verbosity = 'query_plan,explain';

-- 느린 쿼리의 일부만 샘플링 (부하가 큰 서버)
SET GLOBAL log_slow_rate_limit = 100;   -- 100건 중 1건만 기록

-- MariaDB 의 감사 플러그인 (lg10 에서 자세히)
INSTALL SONAME 'server_audit';
SET GLOBAL server_audit_logging = ON;
MySQL 과 MariaDB 는 갈라졌습니다 — 슬로우 로그 옵션 이름, 감사 플러그인, binlog 세부 동작이 버전이 올라갈수록 달라집니다. 문서를 볼 때 제품 이름부터 확인하세요. 이 탭의 예제는 특별한 표시가 없으면 MySQL 8.x 기준입니다.
LOG 06

binlog — 복제와 PITR 이 전부 여기서 나옵니다

binlog 는 "변경 이벤트를 시간 순으로 적은 파일"입니다. 그런데 이 단순한 파일 하나로 복제 · 시점 복구 · CDC · 감사가 전부 됩니다. MySQL 생태계에서 가장 많이 재활용되는 자산입니다.

복제의 실체 — 같은 로그를 두 서버가 순서대로 읽습니다.

ROW · STATEMENT · MIXED

담는 것판정
ROW
기본값 8.0		바뀐 행의 이미지(before/after)항상 같은 결과. CDC 는 이것만
STATEMENT실행한 SQL 문 그대로NOW()·UUID()·LIMIT+정렬 없음에서 어긋남
MIXED위험하면 ROW, 아니면 STATEMENT크기는 줄지만 CDC 에는 못 씀
-- 확인과 변경
SELECT @@binlog_format, @@binlog_row_image, @@log_bin;

SET GLOBAL binlog_format = 'ROW';       -- 새 커넥션부터
SET GLOBAL binlog_row_image = 'FULL';   -- CDC 라면 FULL 이 안전
-- MINIMAL 은 바뀐 컬럼만 담아 크기는 줄지만
-- 다운스트림에서 "이전 값"을 못 볼 수 있습니다
왜 STATEMENT 가 위험한가 — INSERT … VALUES (NOW()) 를 소스와 레플리카가 각각 실행하면 시각이 다릅니다. DELETE … LIMIT 10 은 정렬이 없으면 어떤 10건인지 보장이 없습니다. ROW 는 "결과 행"을 그대로 옮기므로 이런 비결정성이 사라집니다.

binlog 를 사람이 읽어 보기

# 파일 목록과 크기
mysql -e "SHOW BINARY LOGS;"

# ROW 포맷을 사람이 읽는 SQL 로 풀어서 보기
mysqlbinlog --base64-output=DECODE-ROWS -v \
            /var/lib/mysql/binlog.000123 | less

# 시간 범위로 잘라 보기 (사고 시각 주변)
mysqlbinlog --start-datetime="2026-09-01 03:30:00" \
            --stop-datetime="2026-09-01 03:45:00" \
            binlog.000123 | grep -i "delete from orders"

# 원격 서버에서 스트리밍으로 받기 (백업용)
mysqlbinlog --read-from-remote-server --host=db1 \
            --raw --stop-never binlog.000123
사고 조사에서 제일 먼저 하는 일 — "누가 그 DELETE 를 돌렸나"는 슬로우 로그가 아니라 binlog 에 답이 있습니다. ROW 포맷이면 지워진 행의 내용까지 그대로 들어 있어 복구용 INSERT 문을 만들어 낼 수도 있습니다.

binlog 로 시점 복구(PITR) 하기 🔴 실무

전체 백업 + binlog 재생

# ① 평소 : 매일 새벽 전체 백업. binlog 위치를 함께 기록합니다
mysqldump --all-databases --single-transaction \
          --source-data=2 --flush-logs \
          > /backup/full-2026-09-01.sql
# 덤프 앞부분에 이런 주석이 들어갑니다
# CHANGE REPLICATION SOURCE TO SOURCE_LOG_FILE='binlog.000124',
#                               SOURCE_LOG_POS=157;

# ② 사고 : 03:40 에 WHERE 를 빼먹은 DELETE
# ③ 백업을 복원합니다 (03:00 시점)
mysql < /backup/full-2026-09-01.sql

# ④ 백업 이후 ~ 사고 직전까지 binlog 를 재생합니다
mysqlbinlog --start-position=157 \
            --stop-datetime="2026-09-01 03:39:55" \
            binlog.000124 binlog.000125 | mysql

# GTID 를 쓰면 위치 대신 트랜잭션 ID 로 자릅니다
mysqlbinlog --exclude-gtids='3E11FA47-71CA-11E1-9E33-C80AA9429562:23' \
            binlog.000124 | mysql
GTID(Global Transaction ID) 5.6+ — 트랜잭션마다 서버 UUID + 일련번호를 붙입니다. "파일 이름 + 오프셋" 대신 트랜잭션 단위로 말할 수 있어 페일오버와 재구성이 훨씬 안전합니다. 새로 구성한다면 gtid_mode = ON 이 사실상 표준입니다.

보존 기간과 안전 설정

[mysqld]
log_bin = binlog
binlog_format = ROW
binlog_row_image = FULL

binlog_expire_logs_seconds = 604800   # 7일 (8.0+). 안 정하면 계속 쌓임
max_binlog_size = 1G

sync_binlog = 1                 # ★ 커밋마다 binlog 를 fsync
innodb_flush_log_at_trx_commit = 1   # ★ 둘을 같이 켜야 무손실
gtid_mode = ON
enforce_gtid_consistency = ON
-- 손으로 지우는 방법 (rm 쓰지 마세요)
PURGE BINARY LOGS BEFORE '2026-08-25 00:00:00';
PURGE BINARY LOGS TO 'binlog.000120';

-- 어떤 레플리카가 어디까지 읽었는지 먼저 확인
SHOW REPLICAS;
SELECT * FROM performance_schema.replication_connection_status\G
지우기 전에 반드시 확인 — 레플리카가 아직 못 읽은 binlog 를 지우면 복제가 영구히 깨져 레플리카를 처음부터 다시 만들어야 합니다. CDC(Debezium)도 마찬가지입니다 — 커넥터가 며칠 멈춰 있는 동안 binlog 가 만료되면 스냅샷부터 다시 떠야 합니다(lg11).
sync_binlog 도 다이얼입니다 — 1 은 커밋마다 fsync(가장 안전 · 가장 느림), 0 은 OS 에 맡김(가장 빠름 · 장애 시 마지막 몇 초의 binlog 유실 → 레플리카와 어긋남), N 은 N 번마다 한 번. 금융·주문처럼 복제본이 소스와 절대 달라지면 안 되는 곳은 1 고정이고, 로그성 테이블만 다루는 서버라면 낮춰서 성능을 얻습니다. lg02 의 다이얼 그림을 다시 보면 같은 이야기입니다.
