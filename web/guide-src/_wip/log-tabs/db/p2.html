LOG 03

PostgreSQL 진단 로그 — 무엇을 켜고 무엇을 끄나

PostgreSQL 은 기본 설정이 거의 아무것도 안 남기는 쪽입니다. 로그를 켜는 것이 첫 일이고, 얼마나 켜느냐가 두 번째 일입니다 — 다 켜면 디스크가 먼저 터집니다.

서식 하나를 제대로 잡으면 나중에 로그를 기계로 읽을 수 있습니다.

처음 켤 때 이 여섯 줄 PG 12+

# postgresql.conf — 운영에서 실제로 쓰는 최소 구성
logging_collector = on                 # 파일로 직접 씀 (재시작 필요)
log_directory = 'log'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_rotation_age = 1d                  # 하루마다 새 파일
log_rotation_size = 512MB              # 또는 512MB 마다
log_truncate_on_rotation = on          # 같은 이름 재사용 시 덮어씀

log_line_prefix = '%m [%p] %q%u@%d/%a '
log_min_duration_statement = 200ms     # ★ 이 한 줄이 슬로우 쿼리 로그
log_checkpoints = on                   # 체크포인트가 잦은지 보기
log_lock_waits = on                    # 락 대기 1초 넘으면 기록
log_temp_files = 10MB                  # 디스크 정렬이 터지는 쿼리 찾기
log_autovacuum_min_duration = 1s       # 오래 도는 오토배큠
재시작이 필요한 것과 아닌 것 — logging_collector 만 재시작이고 나머지는 SELECT pg_reload_conf(); 로 즉시 반영됩니다. ALTER SYSTEM SET … 로 바꾸면 postgresql.auto.conf 에 저장돼 재시작해도 유지됩니다.

절대 켜면 안 되는 조합

# ✗ 운영에서 이렇게 두면 하루 만에 디스크가 찹니다
log_statement = 'all'                  # 모든 쿼리를 전부 기록
log_min_duration_statement = 0         # 0 = 전부 (0 과 -1 을 헷갈리지 마세요)
log_duration = on                      # 위와 겹쳐서 두 줄씩 남습니다
log_connections = on
log_disconnections = on                # 커넥션 풀이면 폭증합니다

# 값의 뜻
#  -1  : 끔  ← "안 남김"
#   0  : 전부 남김  ← "다 남김" (정반대!)
# 200ms: 200ms 넘는 것만
실제 사고 — 개발 서버에서 디버깅하려고 log_min_duration_statement = 0 을 켜 두고 운영에 그대로 배포한 뒤, 몇 시간 만에 로그 파티션이 100% 가 되고 PostgreSQL 이 쓰기를 못 해 멈춘 사례가 흔합니다. 로그 디렉터리는 데이터 디렉터리와 다른 파티션에 두세요.

느린 쿼리의 실행계획까지 로그에 남기기 🟡 중급

auto_explain — 느릴 때만 EXPLAIN 을 붙여 줍니다

# postgresql.conf
shared_preload_libraries = 'auto_explain'   # 재시작 필요
auto_explain.log_min_duration = '500ms'     # 이보다 느리면 계획도 기록
auto_explain.log_analyze = on               # 실제 행 수까지 (비용 있음)
auto_explain.log_buffers = on               # 버퍼 히트/읽기
auto_explain.log_timing = off               # ★ 오버헤드가 큰 항목. 끄는 편
auto_explain.log_nested_statements = on     # 함수 안의 쿼리까지
auto_explain.log_format = 'json'            # 도구로 파싱하려면
-- 로그에 이렇게 남습니다
LOG:  duration: 1843.201 ms  plan:
  Seq Scan on orders  (cost=0.00..48120.00 rows=1 width=84)
                      (actual time=1841.9..1843.1 rows=3 loops=1)
    Filter: ((status)::text = 'PAID'::text)
    Rows Removed by Filter: 1998412        ← 200만 행을 훑고 3건
왜 유용한가 — 느린 쿼리를 나중에 재현하면 계획이 달라져 있는 경우가 많습니다 (데이터가 늘었거나 통계가 갱신됐거나). auto_explain 은 느렸던 그 순간의 계획을 남깁니다. 이게 결정적일 때가 있습니다.

pg_stat_statements — 로그가 아니라 집계입니다

-- 설치 (shared_preload_libraries 에 추가 후 재시작)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- 총 소요 시간 상위 10개 ★ 실무에서 제일 먼저 보는 쿼리
SELECT substr(query, 1, 70)             AS q,
       calls,
       round(total_exec_time::numeric, 0)  AS total_ms,
       round(mean_exec_time::numeric, 2)   AS avg_ms,
       rows
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 10;

-- 초기화 (튜닝 전후 비교할 때)
SELECT pg_stat_statements_reset();
로그 vs 집계 — 쓰는 자리가 다릅니다
· 슬로우 쿼리 로그: "그때 그 한 건"을 파라미터까지 봅니다. 사후 조사용.
· pg_stat_statements: 파라미터를 지운 쿼리 모양별 누적 통계. "무엇부터 고칠까"를 정할 때. 평균이 느린 것보다 총합이 큰 것이 먼저입니다.
둘 다 켜 두는 것이 정석입니다.

로그를 사람이 아니라 기계가 읽게 🔴 실무

CSV · JSON 으로 뽑기 PG 15+

# 셋을 동시에 켤 수 있습니다
log_destination = 'stderr,csvlog,jsonlog'   # jsonlog 는 PG 15+
logging_collector = on

# csvlog 는 테이블로 바로 읽을 수 있습니다
-- 로그를 SQL 로 조회하기
CREATE TABLE pg_log ( ... );   -- 문서의 컬럼 정의를 그대로
COPY pg_log FROM '/var/lib/pgsql/log/postgresql-2026-09-01.csv'
     WITH (FORMAT csv);

SELECT user_name, database_name, count(*), avg(...)
  FROM pg_log
 WHERE error_severity = 'LOG'
   AND message LIKE 'duration:%'
 GROUP BY 1, 2 ORDER BY 3 DESC;
컨테이너라면 — logging_collector = off 로 두고 stderr 를 그대로 표준 출력으로 흘려보낸 뒤 Fluent Bit · Loki · CloudWatch 가 받게 하는 것이 요즘 방식입니다. 파일 로테이션을 DB 가 아니라 플랫폼이 책임지게 하는 것입니다.

pgBadger — 로그를 리포트로 권장

# 설치 (배포판 패키지 또는 cpan)
sudo apt install pgbadger        # 또는 dnf install pgbadger

# 하루치 로그 → HTML 리포트 한 장
pgbadger /var/log/postgresql/postgresql-2026-09-01*.log \
         -o /tmp/report-2026-09-01.html

# 여러 날 · 여러 서버를 한 번에 (병렬 4)
pgbadger -j 4 /var/log/postgresql/postgresql-2026-08-*.log -o month.html

# 증분 모드 — 매일 돌려서 주간/월간 리포트를 자동 갱신
pgbadger --incremental --outdir /var/www/pgbadger \
         /var/log/postgresql/postgresql-*.log
리포트에서 실제로 보는 것 — ① 시간대별 쿼리 수와 지연, ② 정규화된 쿼리별 총 소요 시간 순위, ③ 락 대기 · 임시 파일 상위, ④ 체크포인트 빈도, ⑤ 에러 종류별 집계. pgBadger 가 제대로 파싱하려면 log_line_prefix 가 맞아야 합니다 — pgbadger --prefix '…' 로 알려 주거나 문서가 권장하는 서식을 쓰세요.
로그 때문에 DB 가 멈추는 두 가지 경로
· 디스크가 참 — 로그 파티션이 100% 가 되면 logging_collector 가 쓰기에 실패하고, 최악의 경우 체크포인트와 WAL 쓰기까지 막혀 DB 전체가 멈춥니다. 로그와 데이터를 다른 파티션에 두는 것이 첫 방어선입니다.
· 로그 I/O 가 쿼리를 느리게 함 — log_min_duration_statement = 0 에 log_duration = on 까지 켜면, 초당 수천 줄을 동기적으로 씁니다. 쿼리 지연 그래프가 통째로 올라갑니다. 로그를 켜고 나서 지연 지표를 다시 보세요.
LOG 04

PostgreSQL WAL 운영 — 아카이브와 PITR

WAL 은 크래시 복구만을 위한 것이 아닙니다. 같은 로그를 다른 서버에 흘리면 복제가 되고, 보관해 두면 원하는 시점으로 되감기(PITR) 가 됩니다. 백업 전략의 절반이 WAL 설정에서 결정됩니다.

세 저장소 — 원통 하나하나가 다른 규칙으로 관리됩니다.

wal_level — 무엇까지 로그에 담을지

값담는 것되는 일
minimal크래시 복구에 필요한 최소복제·PITR 불가
replica
기본값		+ 물리 복제·아카이브에 필요한 정보스트리밍 복제 · PITR
logical+ 행 단위 변경 식별 정보논리 복제 · CDC
# postgresql.conf — 복제·PITR 을 쓸 서버의 표준 구성
wal_level = replica              # CDC 를 쓸 거면 logical
archive_mode = on                # 재시작 필요
archive_command = 'test ! -f /arch/%f && cp %p /arch/%f'
archive_timeout = 300            # 쓰기가 적어도 5분마다 세그먼트를 닫음

max_wal_size = 4GB               # 체크포인트를 부르는 상한
min_wal_size = 1GB
checkpoint_timeout = 15min
checkpoint_completion_target = 0.9   # 체크포인트 I/O 를 넓게 펴서 스파이크 완화
wal_compression = on             # WAL 양을 줄임 (CPU 조금 씀)
archive_command 는 실패하면 재시도합니다 — 성공할 때까지 그 WAL 세그먼트를 지우지 않습니다. 아카이브 대상(NFS·S3)이 죽으면 pg_wal 이 계속 불어나 결국 디스크가 찹니다. 실무에서는 직접 만든 cp 대신 pgBackRest · WAL-G · barman 을 씁니다.

PITR — 30분 전으로 되감기

# ① 평소: 베이스 백업 + WAL 아카이브를 계속 쌓아 둡니다
pg_basebackup -D /backup/base-2026-09-01 -Fp -Xs -P -U repl

# ② 사고: 03:40 에 누가 DELETE 를 잘못 돌렸습니다
#    → 03:35 시점으로 되돌립니다

# ③ 새 데이터 디렉터리에 베이스 백업을 풉니다
rm -rf $PGDATA/*
cp -a /backup/base-2026-09-01/* $PGDATA/

# ④ 복구 목표를 지정합니다 (PG 12 부터 postgresql.conf 에)
cat >> $PGDATA/postgresql.conf <<'EOF'
restore_command = 'cp /arch/%f %p'
recovery_target_time = '2026-09-01 03:35:00+09'
recovery_target_action = 'promote'
EOF
touch $PGDATA/recovery.signal      # ★ 이 파일이 복구 모드 스위치

# ⑤ 시작하면 아카이브를 재생하며 그 시점까지 갑니다
pg_ctl -D $PGDATA start
PITR 이 가능한 조건 — ① 베이스 백업 하나와 ② 그 시점 이후의 WAL 이 끊김 없이 있어야 합니다. 한 세그먼트라도 빠지면 거기서 복구가 멈춥니다. 그래서 아카이브의 무결성 점검(pgbackrest check)이 백업 자체만큼 중요합니다.

pg_wal 이 계속 불어날 때 — 원인은 넷뿐입니다 🔴 실무

원인확인 쿼리조치
아카이브 실패 SELECT * FROM pg_stat_archiver;
last_failed_wal 이 최근인가		 아카이브 대상 복구. 임시로 archive_mode = off 는 PITR 사슬을 끊습니다
죽은 복제 슬롯 SELECT slot_name, active, wal_status FROM pg_replication_slots; 가장 흔합니다. 안 쓰는 슬롯은 pg_drop_replication_slot() 로 삭제
긴 트랜잭션 SELECT pid, age(backend_xid), query FROM pg_stat_activity ORDER BY 2 DESC NULLS LAST; 배치·리포트가 커넥션을 물고 있는 경우. 종료 후 체크포인트
쓰기 폭증 SELECT pg_current_wal_lsn(); 를 1분 간격으로 두 번 정상 동작입니다. max_wal_size 와 디스크를 늘리는 쪽
절대 하지 말 것 — rm pg_wal/0000…
디스크가 찼다고 WAL 세그먼트를 손으로 지우면 DB 가 다시 열리지 않습니다. 정말 급하면 순서는 이렇습니다 — ① 다른 파티션의 파일을 지워 공간을 확보(로그·임시 파일), ② 원인(슬롯·아카이브)을 제거, ③ CHECKPOINT; 를 수동 실행해 회수, ④ 그래도 안 되면 pg_archivecleanup 처럼 PostgreSQL 이 제공하는 도구로만 정리합니다.
예방 — max_slot_wal_keep_size PG 13+ 를 설정해 두면 슬롯이 그 이상 WAL 을 붙잡지 못하게 막을 수 있습니다(대신 그 복제본은 재구성해야 합니다).
복제도 결국 같은 로그입니다 — 스트리밍 복제는 스탠바이가 WAL 을 네트워크로 받아 계속 REDO 를 돌리는 것뿐입니다. 그래서 pg_stat_replication 의 write_lag · flush_lag · replay_lag 는 "로그가 어디까지 도착·기록·반영됐나"를 재는 값이고, 동기 복제(synchronous_standby_names)를 켜면 커밋이 스탠바이의 WAL 기록까지 기다립니다 — lg02 의 다이얼에서 가장 오른쪽 칸이 이것입니다.
