로그는 기록이
아니라
데이터베이스입니다

DB 에서 "로그"라는 말은 완전히 다른 두 가지를 가리킵니다 — 하나는 사람이 읽는 진단 로그(에러 · 느린 쿼리 · 누가 무엇을 조회했나), 다른 하나는 DB 자신이 읽는 트랜잭션 로그(WAL · redo · binlog)입니다. 앞의 것은 지워도 DB 가 돕니다. 뒤의 것은 지우는 순간 DB 가 열리지 않습니다. 이 탭은 그 둘을 갈라 놓고 시작해서, 커밋이 왜 로그 flush 인지, 크래시에서 어떻게 돌아오는지, 그리고 그 로그를 읽어 느린 쿼리를 잡고 · 감사에 대응하고 · 데이터 파이프라인(CDC)을 만드는 데까지 갑니다. 이 탭을 마치면 "로그 파일이 디스크를 다 먹었어요" 라는 연락에 무엇을 지워도 되는지 답할 수 있습니다.

LOG 01

DB 로그의 두 얼굴 — 사람이 읽는 것과 DB 가 읽는 것

운영 중에 가장 위험한 오해가 여기서 나옵니다. "로그 파일이 디스크를 다 먹었으니 지웁시다" — 무엇을 지우느냐에 따라 아무 일도 안 일어나거나, DB 가 두 번 다시 안 열립니다. 먼저 이 둘을 갈라 놓겠습니다.

DB 로그의 두 얼굴 — 사람이 읽는 것과 DB 가 읽는 것은 이름만 같습니다.
DB × 로그 기능 지도 — 이 탭에서 갈 곳을 한 장에 담았습니다.

① 진단 로그 — 켜고 끄는 스위치입니다

-- PostgreSQL : 200ms 넘는 쿼리만 로그로
ALTER SYSTEM SET log_min_duration_statement = '200ms';
SELECT pg_reload_conf();          -- 재시작 없이 적용

-- MySQL : 슬로우 쿼리 로그 켜기
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;  -- 초 단위 (소수 가능)

-- 끄는 것도 한 줄. 꺼도 DB 는 아무 일 없이 계속 돕니다
SET GLOBAL slow_query_log = OFF;
이 스위치의 성격 — 켜면 디스크와 CPU 를 조금 더 씁니다. 그래서 "전부 다 켜 두기"가 정답이 아니고, 무엇을 볼지 정하고 그것만 켜는 것이 운영의 기본입니다. 뒤의 lg03 · lg05 에서 제품별로 다룹니다.

② 트랜잭션 로그 — 스위치가 없습니다

# PostgreSQL 의 WAL — 여기를 지우면 DB 가 안 열립니다
$PGDATA/pg_wal/000000010000000000000023
$PGDATA/pg_wal/000000010000000000000024   # 16MB 씩

# MySQL(InnoDB) 의 redo 로그와 binlog
/var/lib/mysql/#innodb_redo/#ib_redo1234
/var/lib/mysql/binlog.000123

# Oracle 의 온라인 redo 로그
/u01/oradata/ORCL/redo01.log

# "log" 로 끝나지만 이건 데이터입니다.
# 지우려면 DB 가 시킨 방법으로만 지웁니다 (아카이브 · PURGE · 체크포인트)
실제로 자주 나는 사고 — 디스크가 차서 rm 으로 pg_wal 안의 파일을 지웠다가 DB 를 못 살린 사례가 계속 나옵니다. WAL 은 "이미 커밋했다고 응답한 데이터"가 아직 데이터 파일에 없을 수 있는 상태를 메우는 유일한 근거입니다.

왜 둘로 갈리나 — 한쪽은 관찰, 한쪽은 계약 🟢 기초

이 탭에서 실제로 쓸 명령 — 지금 확인해 보기 🟡 중급

PostgreSQL — 로그가 어디 있나
SHOW log_directory;      -- 기본 'log'
SHOW log_filename;
SHOW data_directory;     -- pg_wal 은 이 아래
SELECT pg_current_wal_lsn();   -- 지금 WAL 위치
MySQL — 다섯 로그의 현재 상태
SHOW VARIABLES LIKE 'log_error';
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'log_bin%';
SHOW BINARY LOGS;        -- binlog 목록과 크기
Oracle — alert log 위치
SELECT value FROM v$diag_info
 WHERE name = 'Diag Trace';
SELECT * FROM v$log;        -- 온라인 redo 그룹
SELECT log_mode FROM v$database;  -- ARCHIVELOG?
SQLite — 지금 어떤 모드인가
PRAGMA journal_mode;   -- delete | wal | memory ...
PRAGMA synchronous;    -- 0 OFF · 1 NORMAL · 2 FULL
-- wal 이면 파일 옆에 -wal, -shm 이 생깁니다
채택 정도를 어떻게 말해야 하나 — 이 탭에서는 정확한 점유율 숫자를 쓰지 않습니다. WAL(선행 기록)은 사실상 모든 관계형 DB 의 표준이고, binlog 기반 CDC(Debezium)는 스트리밍 파이프라인에서 널리 쓰이며, 감사 플러그인은 규제 산업에서만 켜는 편입니다. 숫자가 필요하면 DB-Engines 순위(제품 인기)와 GitHub star 추이(도구 채택)를 직접 확인하는 것이 정확합니다 — 이 두 곳이 시점이 찍힌 공개 자료입니다.
LOG 02

WAL — 데이터보다 로그를 먼저 쓰는 이유

Write-Ahead Logging 은 이름이 곧 규칙입니다. 데이터 페이지를 고치기 전에, 그 변경을 로그에 먼저 적는다. 이 한 줄에서 커밋의 의미 · 크래시 복구 · 복제 · PITR · CDC 가 전부 나옵니다.

커밋의 정체 — "로그가 디스크에 닿았다"는 확인 한 번입니다.

왜 로그가 먼저인가 — 두 가지 이유

데이터 파일에 바로 쓰면로그에 먼저 쓰면
디스크 접근여기저기 흩어진 임의 쓰기파일 끝에 순차 쓰기
쓰기 횟수페이지마다 한 번씩여러 변경을 한 번에 모아서
중간에 죽으면반쯤 고쳐진 페이지 — 복구 불가로그를 다시 읽어 재현
커밋 지연모든 페이지를 기다림로그 한 번의 fsync
핵심은 "순차" — HDD 에서는 임의 쓰기와 순차 쓰기가 수십 배 차이였습니다. NVMe SSD 에서 그 격차는 크게 줄었지만, fsync 한 번의 지연과 여러 트랜잭션을 묶어 한 번에 flush(group commit)하는 이득은 그대로 남아 있습니다.

WAL 레코드에 실제로 들어가는 것

[ LSN 0/1A2B3C48 ]                 ← 로그 안의 주소(순서)
  xid      : 51823                 ← 어느 트랜잭션인가
  rmgr     : Heap                  ← 어느 자원 관리자(테이블/인덱스)
  page     : rel 16384, blk 921    ← 어느 파일의 몇 번째 페이지
  action   : UPDATE                ← 무엇을 했나
  old/new  : (tuple 이미지 또는 차이)
  prev LSN : 0/1A2B3C10            ← 앞 레코드로 되감기용

[ LSN 0/1A2B3D02 ]
  xid      : 51823
  action   : COMMIT                ← 이 레코드가 디스크에 닿으면 커밋 확정
LSN(Log Sequence Number) — WAL 안의 바이트 오프셋입니다. "복제가 얼마나 밀렸나", "PITR 을 어디까지 복원했나"가 전부 이 숫자의 차이로 표현됩니다. MySQL 도 같은 개념을 LSN 이라 부르고, Oracle 은 SCN 이라고 부릅니다.

크래시가 나면 무슨 일이 벌어지나 — REDO 와 UNDO 🟢 기초

크래시 복구 — REDO 로 살리고 UNDO 로 되돌립니다. 근거는 로그 하나뿐입니다.

REDO / UNDO / 체크포인트 — 세 단어

단어하는 일
REDO커밋됐는데 데이터 파일에 아직 없는 변경을 다시 적용
UNDO커밋 안 됐는데 데이터 파일에 이미 반영된 변경을 되돌림
체크포인트지금까지의 더티 페이지를 데이터 파일에 밀어 넣고 "여기까지는 안전" 표시
LSN로그 안의 위치. 복제 지연·복원 지점이 전부 이 값
"커밋 안 된 변경이 왜 데이터 파일에 있나?" — 메모리가 부족하면 엔진은 커밋 여부와 무관하게 더티 페이지를 디스크로 내보냅니다(steal). 그래서 UNDO 가 필요합니다. 반대로 커밋했다고 곧바로 데이터 파일에 쓰지도 않습니다(no-force) — 그래서 REDO 가 필요합니다. steal · no-force 조합이 WAL 이 존재하는 이유입니다.

복구가 도는 것을 눈으로 보기

LOG:  database system was interrupted; last known up at 2026-08-31 03:11:07
LOG:  database system was not properly shut down; automatic recovery in progress
LOG:  redo starts at 0/1A2B3C48          ← 여기서부터 다시 적용
LOG:  invalid record length at 0/1A5F0180: wanted 24, got 0
LOG:  redo done at 0/1A5F0158            ← 로그 끝에 도달
LOG:  database system is ready to accept connections
# 직접 해 보기 (개발 환경에서만!)
pg_ctl -D $PGDATA -m immediate stop   # 전원 뽑기와 같은 종료
pg_ctl -D $PGDATA start               # 위 로그가 그대로 나옵니다

# MySQL 이면 에러 로그에 이렇게 남습니다
# [InnoDB] Starting crash recovery.
# [InnoDB] Log scan progressed past the checkpoint lsn 5238942
"복구 중"이 오래 걸린다면 — 체크포인트 간격이 너무 길거나 (max_wal_size · innodb_log_file_size 가 큼), 마지막 체크포인트 이후 쓰기가 폭증했다는 뜻입니다. 복구 시간과 평소 성능은 같은 다이얼의 양 끝입니다.

내구성 다이얼 — fsync 를 얼마나 자주 할 것인가 🔴 실무

내구성 ↔ 성능 — 한 다이얼의 양 끝입니다. 테이블마다 답이 다릅니다.
✗ 전부 최고 내구성으로 두기
-- 모든 트랜잭션이 커밋마다 fsync 를 기다립니다
SET synchronous_commit = on;   -- 기본값 (맞습니다)

-- 그런데 이런 것까지:
INSERT INTO page_view_log (path, at) VALUES ('/home', now());
-- 초당 수천 건 · 잃어도 되는 데이터인데
-- 커밋마다 디스크를 기다리며 WAL 을 밀어 냅니다

결과 — 중요한 주문 트랜잭션이 로그 뒤에서 줄을 섭니다. 전부 안전하게 만들면 정작 안전해야 할 것이 느려집니다.

✓ 트랜잭션마다 다이얼을 돌리기
-- PostgreSQL : 세션·트랜잭션 단위로 바꿀 수 있습니다
BEGIN;
SET LOCAL synchronous_commit = off;   -- 이 트랜잭션만
INSERT INTO page_view_log (path, at) VALUES ('/home', now());
COMMIT;   -- 즉시 반환. 장애 때 최근 몇백 ms 를 잃을 수 있음

-- 주문은 그대로 기본값(on)을 씁니다
BEGIN;
INSERT INTO orders (...) VALUES (...);
COMMIT;   -- fsync 를 기다립니다

같은 DB 안에서도 테이블마다 요구가 다릅니다. "잃으면 곤란한가?"를 먼저 묻고 다이얼을 돌립니다.

fsync 는 생각보다 자주 거짓말을 합니다
· 디스크 쓰기 캐시 — 소비자용 SSD 는 캐시에만 넣고 "썼다"고 답하기도 합니다. 전원이 나가면 그 구간이 사라집니다. 서버용 디스크는 PLP(전원 손실 보호) 로 이 구간을 지킵니다.
· 가상화 · 네트워크 스토리지 — 계층이 하나 늘 때마다 fsync 의 의미가 흐려집니다. 클라우드 관리형 DB 를 쓰는 이유의 절반이 여기에 있습니다.
· fsync = off 는 벤치마크 전용입니다. PostgreSQL 문서도 그렇게 씁니다. 운영에서 켜 두면 크래시 한 번에 DB 전체가 복구 불능이 될 수 있습니다. (synchronous_commit = off 는 다릅니다 — 이쪽은 최근 커밋만 잃고 DB 는 일관됩니다.)
