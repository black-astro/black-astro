LOG 07

Oracle 과 SQLite — 규모의 양 끝, 같은 원리

한쪽은 은행 코어를 돌리는 DB, 다른 쪽은 휴대폰 안에서 도는 파일 하나짜리 DB 입니다. 그런데 둘 다 "데이터보다 로그를 먼저 쓴다"는 lg02 의 규칙을 그대로 따릅니다. 다른 것은 규모와 이름뿐이라는 것을 이 섹션에서 확인합니다.

Oracle redo 순환 — 돌아가며 채우고, 복사가 끝나야 덮어씁니다. 복사가 밀리면 DB 가 기다립니다.

Oracle 의 진단 로그 — alert log 와 trace

-- 어디 있나 (ADR — Automatic Diagnostic Repository)
SELECT name, value FROM v$diag_info
 WHERE name IN ('Diag Trace', 'Diag Alert');
-- Diag Trace : .../diag/rdbms/orcl/ORCL/trace/alert_ORCL.log
-- Diag Alert : .../alert/log.xml  (같은 내용의 XML 판)

-- 온라인 redo 그룹의 상태 — 그림의 CURRENT · ACTIVE · INACTIVE
SELECT group#, sequence#, bytes/1024/1024 AS mb, members, status
  FROM v$log ORDER BY group#;

-- 아카이브 모드인가 (아니면 PITR 불가)
ARCHIVE LOG LIST;
SELECT log_mode FROM v$database;
# alert log 에서 자주 보는 두 줄 — 뜻을 알아야 합니다
Thread 1 cannot allocate new log, sequence 4812
Checkpoint not complete            ← ★ redo 그룹이 다 찼는데 아직
                                      체크포인트가 안 끝남. DB 가 멈춰 기다림
ORA-00257: archiver error           ← 아카이브 대상이 꽉 참. 즉시 조치
"Checkpoint not complete" 가 반복되면 — redo 그룹이 너무 작거나 적습니다. 그룹을 더 크게 · 더 많이(보통 3~5개) 만드는 것이 정답이고, log switch 를 15~20분에 한 번 정도로 맞추는 것이 오래된 경험칙입니다. ALTER DATABASE ADD LOGFILE GROUP 4 SIZE 1G;

AWR · ASH — 로그가 아니라 "시간 단면"

-- ASH : 1초마다 활성 세션을 찍은 사진. 최근 1시간은 메모리에
SELECT sql_id, event, count(*) AS samples
  FROM v$active_session_history
 WHERE sample_time > sysdate - 1/24
 GROUP BY sql_id, event
 ORDER BY samples DESC FETCH FIRST 10 ROWS ONLY;
-- samples 가 곧 "그 SQL 이 그 대기 상태로 보낸 초"입니다

-- AWR : 1시간마다 저장하는 성능 스냅샷. 리포트는 스크립트로
@?/rdbms/admin/awrrpt.sql        -- HTML 리포트 (구간 두 개 고름)

-- 특정 세션의 SQL 을 파일로 추적 (tkprof 로 읽음)
EXEC DBMS_MONITOR.SESSION_TRACE_ENABLE(sid => 123, serial_num => 456,
                                       waits => TRUE, binds => TRUE);
라이선스 주의 — AWR · ASH · ADDM 은 Diagnostics Pack(Enterprise Edition 의 유료 옵션)입니다. 조회만 해도 사용으로 간주됩니다. 옵션이 없으면 Statspack(무료 · 기능은 AWR 의 조상)이나 v$sql · v$session 직접 조회를 씁니다. control_management_pack_access 파라미터로 서버에서 막아 둘 수 있습니다.
다른 DB 와 대응 — ASH ≈ pg_stat_activity 를 1초마다 저장한 것, AWR ≈ pg_stat_statements + OS 지표의 시간별 스냅샷. PostgreSQL 에서 비슷한 것을 원하면 pg_stat_monitor·pgsentinel 같은 확장을 붙입니다.

SQLite — rollback journal 과 WAL 모드 🟢 기초

SQLite 두 모드 — WAL 이 읽기·쓰기 동시성과 fsync 횟수에서 이깁니다. 앱 DB 라면 거의 항상 WAL.

WAL 모드 켜기 — 한 번 켜면 파일에 남습니다

PRAGMA journal_mode = WAL;        -- 'wal' 이 돌아오면 성공. 파일에 영구 저장
PRAGMA synchronous = NORMAL;      -- WAL 에서는 NORMAL 이 권장 (커밋마다 fsync 안 함)
PRAGMA wal_autocheckpoint = 1000; -- 기본값. -wal 이 1000 페이지 넘으면 자동 체크포인트

-- 지금 상태 보기
PRAGMA journal_mode;              -- wal
PRAGMA wal_checkpoint(PASSIVE);   -- 손으로 체크포인트 (읽는 사람 방해 안 함)
PRAGMA wal_checkpoint(TRUNCATE);  -- 체크포인트 + -wal 파일을 0 으로 잘라 냄
# WAL 모드에서 생기는 파일 — 셋을 항상 같이 다룹니다
app.db          # 데이터 파일
app.db-wal      # 아직 체크포인트 안 된 변경. 지우면 최근 커밋이 사라집니다
app.db-shm      # 공유 메모리 인덱스 (프로세스 간 조정용). 지워도 다시 만듦

# 백업할 때 app.db 만 복사하면 -wal 의 내용이 빠집니다
sqlite3 app.db ".backup backup.db"     # ★ 이 방법이 안전합니다
sqlite3 app.db "VACUUM INTO 'backup.db'"
-wal 파일이 계속 커진다면 — 누군가 읽기 트랜잭션을 열어 둔 채 안 닫고 있는 것입니다. 체크포인트는 그 읽기가 보는 위치까지밖에 못 밀어 냅니다. 커서를 끝까지 소비하지 않은 ORM 코드가 흔한 원인입니다.

SQLite 에는 슬로우 로그가 없습니다 — 대신 이렇게

-- 셸에서: 명령마다 걸린 시간 표시
.timer on
SELECT count(*) FROM orders WHERE status = 'PAID';
-- Run Time: real 0.412 user 0.398 sys 0.012

-- 실행계획 — SCAN 이 보이면 인덱스가 없는 것
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE status = 'PAID';
-- QUERY PLAN
-- `--SCAN orders                       ← 전체 훑기
-- `--SEARCH orders USING INDEX ix_status (status=?)  ← 이게 목표
# 앱에서: 느린 문장을 직접 잡아 로그로 (Python 예)
import sqlite3, time, logging
con = sqlite3.connect("app.db")
con.execute("PRAGMA journal_mode=WAL")

def slow_trace(sql):                 # 모든 문장이 여기를 지나갑니다
    logging.debug("SQL %s", sql)
con.set_trace_callback(slow_trace)   # C API 의 sqlite3_trace_v2 와 같은 것

# 시간까지 재려면 실행 전후를 감싸는 얇은 래퍼를 둡니다
t = time.perf_counter()
rows = con.execute("SELECT ... ").fetchall()
if (time.perf_counter() - t) > 0.2:
    logging.warning("slow sqlite: %.3fs", time.perf_counter() - t)
SQLite 가 "로그가 없다"는 것은 결함이 아닙니다 — 서버 프로세스가 없으니 로그를 쓸 주체도 없습니다. 앱이 곧 DB 서버이므로 앱의 로거가 슬로우 로그 역할을 합니다. lg01 히트맵에서 SQLite 행이 비어 있던 이유입니다.

NoSQL 의 로그 — Redis AOF 와 MongoDB oplog

"NoSQL 은 로그가 없다"는 말은 틀렸습니다. Redis 는 명령 자체를 순서대로 적은 파일(AOF)로 복구하고, MongoDB 는 oplog 하나로 복제와 CDC 를 다 해냅니다. 관계형에서 배운 두 얼굴이 여기서도 그대로 나타납니다.

Redis 영속성 — RDB 는 사진, AOF 는 일기입니다. 둘 다 켜는 것이 운영 기본값입니다.

SLOWLOG — Redis 의 슬로우 쿼리 로그 (메모리 안에만)

# redis.conf 또는 CONFIG SET — 단위가 마이크로초입니다
CONFIG SET slowlog-log-slower-than 10000   # 10ms 넘는 명령만 (기본값)
CONFIG SET slowlog-max-len 256             # 최근 256건만 보관 (기본 128)

SLOWLOG GET 5          # 최근 5건
# 1) 1) (integer) 4812            ← 일련번호
#    2) (integer) 1788282667      ← 유닉스 시각
#    3) (integer) 31245           ← 걸린 시간 (µs) = 31ms ★
#    4) 1) "KEYS"                 ← 명령과 인자
#       2) "cache:*"
#    5) "10.0.3.14:52210"         ← 누가
#    6) "orders-api"              ← CLIENT SETNAME 으로 붙인 이름
SLOWLOG LEN
SLOWLOG RESET
Redis 에서 10ms 는 "매우 느림"입니다 — 싱글 스레드로 명령을 처리하므로 그 31ms 동안 다른 모든 클라이언트가 줄을 섭니다. SLOWLOG 에 KEYS · SMEMBERS(큰 집합) · HGETALL · FLUSHALL 이 보이면 그 명령 자체를 없애는 것이 튜닝입니다. 재시작하면 지워지므로 주기적으로 수집기에 보냅니다.

AOF — 켜기 · 되감기 · 고치기

# redis.conf — 운영 기본 조합
appendonly yes
appendfsync everysec          # lg02 다이얼의 가운데. 최대 1초 유실
# appendfsync always          # 커밋마다 fsync. 관계형 DB 수준 · 가장 느림
# appendfsync no              # OS 에 맡김. 캐시 전용이면 이것도 됨

auto-aof-rewrite-percentage 100   # 마지막 rewrite 때보다 2배 커지면
auto-aof-rewrite-min-size 64mb    # 단, 64MB 넘을 때만 다시 씀
save 3600 1 300 100 60 10000      # RDB 스냅샷 규칙 (초 · 변경 수)
# AOF 는 계속 자랍니다 — INCR 를 100만 번 하면 100만 줄.
# rewrite 는 "지금 상태를 만드는 최소 명령"으로 다시 씁니다
redis-cli BGREWRITEAOF

# 정전으로 AOF 끝이 잘렸을 때 (시작이 안 됨)
redis-check-aof --fix appendonlydir/appendonly.aof.1.incr.aof
# "잘린 마지막 명령 하나"를 버리고 살립니다
AOF 는 사람이 읽을 수 있습니다 — RESP 프로토콜 그대로라 less 로 열면 *3 $3 SET $8 user:100 … 처럼 보입니다. "누가 언제 이 키를 지웠나"를 AOF 에서 찾는 것이 Redis 판 binlog 조사입니다. 단 시각은 안 남으니 타임스탬프 주석(aof-timestamp-enabled yes 7.0+)을 켜 두면 시점 되감기(redis-check-aof --truncate-to-timestamp)까지 됩니다.

MongoDB — 프로파일러와 oplog 🟡 중급

MongoDB oplog — 복제 로그가 곧 이벤트 스트림입니다. 중심 하나, 읽는 쪽 여섯.

프로파일러 — 느린 작업을 컬렉션에 남깁니다

// 레벨 0 끔 · 1 느린 것만 · 2 전부 (운영 금지)
db.setProfilingLevel(1, { slowms: 100, sampleRate: 0.5 })
//   slowms     : 이보다 느리면 기록 (기본 100ms)
//   sampleRate : 느린 것 중 절반만 (부하 큰 서버)

// 결과는 DB 마다 system.profile (1MB capped) 에 쌓입니다
db.system.profile.find({ millis: { $gt: 100 } })
  .sort({ ts: -1 }).limit(5).pretty()
// { op: "query", ns: "shop.orders",
//   command: { find: "orders", filter: { status: "PAID" } },
//   planSummary: "COLLSCAN",        ← ★ 인덱스 없음
//   docsExamined: 1998412, nreturned: 3,   ← Rows_examined 와 같은 뜻
//   millis: 812 }

db.getProfilingStatus()
db.setProfilingLevel(0)
프로파일러를 안 켜도 mongod.log 에 남습니다 — slowms 를 넘는 작업은 레벨 0 이어도 로그 파일에 "Slow query" 로 기록됩니다(JSON 한 줄 · 4.4+). jq 'select(.msg=="Slow query") | .attr.durationMillis' 로 바로 뽑을 수 있습니다. docsExamined / nreturned 비율은 lg05 의 Rows_examined / Rows_sent 와 같은 판정법입니다.

oplog 와 journal — 둘 다 "DB 가 읽는 로그"

// oplog 창(window) — 이만큼 밀려도 세컨더리가 따라올 수 있습니다
rs.printReplicationInfo()
// configured oplog size:   2048 MB
// log length start to end: 71h  ← 이 시간 안에 복구 못 하면 재동기화
// oplog first event time / last event time

// oplog 크기 바꾸기 (재시작 없이 · 4.0+)
db.adminCommand({ replSetResizeOplog: 1, size: 16384 })   // MB

// 앱에서 oplog 를 구독 — Change Streams
const cs = db.orders.watch([{ $match: { operationType: "delete" } }])
while (await cs.hasNext()) {
  const ev = await cs.next()
  console.log(ev.documentKey, ev.clusterTime)
  // ev._id 가 resumeToken — 끊겨도 여기부터 이어받습니다
}
# mongod.conf — journal 은 WiredTiger 의 WAL 입니다 (끌 수 없음 · 6.1+)
storage:
  journal:
    commitIntervalMs: 100    # 최대 100ms 마다 fsync (기본)
# 쓰기마다 확인하려면 앱에서: { w: "majority", j: true }
oplog 가 덮이면 복제가 끊깁니다 — 세컨더리가 점검으로 oplog 창보다 오래 꺼져 있으면 RECOVERING 에 갇히고 초기 동기화를 처음부터 해야 합니다. Debezium MongoDB 커넥터도 같은 이유로 스냅샷부터 다시 뜹니다. oplog 창은 가장 긴 점검 시간의 몇 배로 잡아 두세요.
