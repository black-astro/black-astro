LOG 03

라이브러리 비교 — 내장 · Serilog · NLog · log4net · ZLogger

다섯 개를 다 알 필요는 없습니다. 다만 왜 이 중 하나를 고르는지는 말할 수 있어야 합니다. 기준은 넷입니다 — 구조적 로깅을 제대로 하는가 · 내보낼 곳(sink)이 있는가 · 설정을 바꾸기 쉬운가 · 초당 몇 줄까지 견디는가.

히트맵 — 한 줄이 전부 진한 라이브러리는 없습니다. 무엇이 급한지가 선택을 정합니다.
라이브러리한 줄 정체 장점단점채택 정도 (2026년 8월 기준)
내장 provider
Console · Debug · EventLog		 MEL 이 기본으로 들고 오는 것 의존성 0 · 컨테이너와 궁합 · JSON 포매터 내장 · OpenTelemetry 와 바로 연결 파일 sink 가 없습니다 · 롤링/보관을 직접 만들어야 함 · 필터 표현력이 낮음 모든 프로젝트의 출발점 — 안 쓰는 앱이 없습니다
Serilog 구조적 로깅을 처음부터 전제로 만든 라이브러리 sink 가 압도적으로 많음(파일·Seq·Elastic·Splunk·S3…) · enricher · Serilog.Expressions 필터 · 설정을 JSON 으로 패키지를 여러 개 붙여야 함 · 할당이 0 은 아님 · 설정을 잘못하면 종료 시 로그 유실 사실상 표준 — 신규 .NET 백엔드에서 가장 흔한 선택
NLog log4j 계보의 성숙한 로깅 프레임워크 nlog.config 하나로 재빌드 없이 대상 변경 · 대상(target)/규칙 문법이 강력 · DB·메일 target 이 기본 제공 XML 설정이 길어짐 · 구조적 로깅은 되지만 Serilog 만큼 자연스럽지 않음 널리 씀 — 특히 기존 .NET Framework 자산이 있는 조직
log4net 가장 오래된 레거시. Apache log4j 의 이식판 오래된 코드베이스에 이미 들어 있음 · 자료가 많음 구조적 로깅이 사실상 없음(문자열 위주) · 설정이 번거로움 · 생태계가 정체 신규 채택은 드묾 — 유지보수 대상으로만 만납니다
ZLogger 할당을 없애는 데 특화된 고성능 로거 (Cysharp) UTF8 로 바로 써서 문자열 할당이 거의 0 · 소스 제너레이터 기반 · Unity·게임 서버에서 강함 sink 종류가 적음 · 자료가 적음 · 문법이 조금 다름(ZLogInformation) 특정 상황에서만 — 초당 수십만 줄, 지연에 민감한 서버
채택 정도를 직접 확인하는 법 — ① NuGet 패키지 페이지의 Total downloads 와 최근 버전 날짜를 나란히 봅니다 (다운로드가 많아도 마지막 릴리스가 2년 전이면 정체된 것입니다). ② GitHub 저장소의 star 추이 · 최근 커밋 · 열린 이슈 수. ③ dotnet list package --outdated 로 우리 조직이 실제로 무엇을 쓰는지부터 세어 보세요 — 남의 통계보다 이게 정확합니다. 이 표의 "사실상 표준 / 널리 씀 / 드묾" 은 순위가 아니라 상대적 위치입니다.

고르는 기준 세 줄 🟢 기초

이렇게 정하면 거의 틀리지 않습니다

  • 컨테이너에 배포하고 로그를 수집기가 걷어 간다
    → 내장 Console(JSON 포매터) 로 충분합니다. 패키지 0개.
  • 파일로 남겨야 한다 · 여러 곳으로 동시에 보낸다 · 설정을 자주 바꾼다
    → Serilog. 가장 안전한 기본값입니다.
  • 기존 코드가 이미 NLog/log4net 이다
    → 그대로 두고 ILogger<T> 로 감쌉니다. 교체는 나중에.
  • 초당 수십만 줄 · GC 를 1ms 도 못 준다
    → ZLogger 또는 [LoggerMessage] + 내장 provider.
가장 흔한 실수 — "성능이 중요하니까 ZLogger" 로 시작하는 것. 대부분의 앱에서 로깅은 병목이 아닙니다. 측정도 안 하고 특수한 도구를 고르면 sink 가 없어서 결국 직접 만들게 됩니다.

패키지 이름만 봐도 되는 정리

# 내장만 — 아무것도 설치할 필요 없음 (WebApplication.CreateBuilder 에 포함)

# Serilog — 보통 이 조합
dotnet add package Serilog.AspNetCore          # Host 연동 + 요청 로깅
dotnet add package Serilog.Sinks.Seq           # 수집기로 보낼 때
dotnet add package Serilog.Expressions         # 조건 필터 · 표현식 템플릿

# NLog
dotnet add package NLog.Web.AspNetCore         # ASP.NET Core 연동
dotnet add package NLog.Extensions.Logging     # 콘솔 · 워커 서비스

# log4net (레거시 유지보수용)
dotnet add package Microsoft.Extensions.Logging.Log4Net.AspNetCore

# ZLogger
dotnet add package ZLogger
Serilog.AspNetCore 하나가 여러 패키지를 끌고 옵니다 — Serilog 본체 · Serilog.Extensions.Hosting · Serilog.Sinks.Console · Serilog.Sinks.File · Serilog.Settings.Configuration. 그래서 웹 앱이면 이거 하나로 시작하면 됩니다.

공존시키기 — 라이브러리를 바꾸는 중일 때 🟡 중급

// 레거시 코드가 log4net 을, 새 코드가 ILogger<T> 를 쓰는 과도기
// → 둘 다 MEL 파이프라인으로 모읍니다. 출력은 한 곳으로 나갑니다.

var builder = WebApplication.CreateBuilder(args);

builder.Logging.ClearProviders();          // ★ 기본 Console 을 먼저 지웁니다
builder.Logging.AddLog4Net("log4net.config");   // 레거시 설정 그대로
builder.Logging.AddJsonConsole();               // 새 표준 출력

// 새 코드는 그냥 ILogger<T> 를 씁니다. 레거시는 손대지 않습니다.
// 레거시 파일이 하나씩 사라질 때 AddLog4Net 줄을 지우면 이사가 끝납니다.
ClearProviders() 를 빠뜨리면 로그가 두 번 찍힙니다. Serilog 를 붙일 때도 마찬가지입니다 — UseSerilog() 는 기본 provider 를 지워 주지만, AddSerilog() 는 지우지 않습니다. "로그가 중복된다"는 신고의 대부분이 이 한 줄입니다.
정리 — 컨테이너면 내장, 파일·다중 sink 가 필요하면 Serilog가 기본 답입니다. NLog 는 설정을 XML 로 다루는 조직에서, ZLogger 는 측정해서 로깅이 병목임을 확인했을 때 고릅니다. log4net 은 새로 고르는 것이 아니라 물려받는 것입니다.
LOG 04

구조적 로깅 — 문자열을 합치지 마세요

log.LogInformation($"주문 {id} 실패") 와 log.LogInformation("주문 {OrderId} 실패", id) 는 화면에 같아 보입니다. 그런데 저장되는 것이 완전히 다릅니다 — 하나는 문장 한 덩어리, 다른 하나는 문장 + 이름 붙은 값입니다.

해부도 — 템플릿 문장 자체가 남는 것이 구조적 로깅의 핵심입니다.
문자열 보간 · 결합
log.LogInformation($"주문 {id} 실패 · 사유 {why}");
log.LogInformation("주문 " + id + " 실패");
  • 저장되는 것은 완성된 문장 하나뿐입니다
  • OrderId = 10423 으로 검색이 안 됩니다 — 문자열 부분 일치만
  • "이 오류가 몇 건" 을 세려면 정규식을 써야 합니다
  • 레벨이 꺼져 있어도 문자열을 먼저 만듭니다(비용 발생)
  • 분석 도구가 중복 이벤트를 묶지 못합니다(문장이 매번 다름)
메시지 템플릿
log.LogInformation("주문 {OrderId} 실패 · 사유 {Reason}", id, why);
log.LogError(ex, "결제 승인 실패 {OrderId} {Gateway}", id, gw);
  • OrderId:10423 로 필드 검색이 됩니다
  • @mt 로 묶어 "이 오류 상위 10건" 을 바로 냅니다
  • 레벨이 꺼져 있으면 포맷을 아예 안 합니다
  • 수집기가 OrderId 로 그래프를 그릴 수 있습니다
  • 예외는 첫 번째 인자로 — 스택트레이스가 따로 저장됩니다

템플릿 문법 — 네 가지만

// ① 이름은 PascalCase 로. 순서대로 인자와 짝지어집니다(이름이 아니라 순서!)
log.LogInformation("사용자 {UserId} 가 {ItemId} 를 구매", userId, itemId);

// ② @ — 객체를 통째로 구조화해서 저장 (Serilog 의 destructure)
log.LogInformation("주문 접수 {@Order}", order);
//   → { "Order": { "Id": 10423, "Total": 39000, "Items": 3 } }

// ③ $ — 무조건 ToString() 으로 (구조화하지 않음)
log.LogInformation("키 {$Key}", complexKey);

// ④ 포맷 지정자 — 표준 .NET 포맷과 같습니다
log.LogInformation("경과 {Elapsed:0.00} ms · 금액 {Total:N0}원", ms, total);
이름이 아니라 순서로 짝지어집니다. "{A} {B}", b, a 라고 쓰면 값이 뒤바뀐 채로 조용히 기록됩니다. 분석기 CA2017 · 로깅 분석기(Microsoft.CodeAnalysis.NetAnalyzers) 를 켜면 인자 개수 불일치를 컴파일 시점에 잡아 줍니다.

@ 를 쓸 때의 함정

// ❌ 엔티티를 통째로 구조화 — 지뢰입니다
log.LogInformation("회원 저장 {@User}", user);
//   → 이메일 · 전화번호 · 해시된 비밀번호까지 전부 로그로

// ✅ 남길 것만 골라 익명 타입으로
log.LogInformation("회원 저장 {@User}",
    new { user.Id, user.Grade, Region = user.Address?.Region });

// ✅ 또는 전용 record 를 만들어 둡니다 (재사용 · 리뷰 대상이 됨)
public sealed record UserLogView(int Id, string Grade, string? Region);
log.LogInformation("회원 저장 {@User}", UserLogView.From(user));
EF Core 엔티티에 {@} 를 붙이면 특히 위험합니다 — 내비게이션 속성을 따라가며 연관 테이블까지 직렬화하려 들 수 있고, 지연 로딩이 켜져 있으면 로그 한 줄이 쿼리 수십 개를 날립니다. 로그용 뷰 타입을 따로 두는 것이 정답입니다.

문장을 어떻게 쓸 것인가 — 사람이 아니라 검색이 읽습니다 🟡 중급

좋은 템플릿의 조건

이렇게이유
문장은 고정, 변하는 것은 전부 {}같은 사건을 묶어 셀 수 있습니다
주어 · 동사 · 결과를 넣습니다"재고 부족" 보다 "주문 접수 실패 — 재고 부족"
식별자를 반드시 하나OrderId · UserId 없이는 추적이 안 됩니다
단위를 이름에 넣습니다{ElapsedMs} · {SizeBytes}
예외는 첫 인자로LogError(ex, "...") — 문자열에 넣지 않습니다
같은 뜻이면 같은 이름OrderId / orderNo / order_id 가 섞이면 검색이 깨집니다
필드 이름을 팀 규칙으로 고정하세요. TraceId · UserId · OrderId · TenantId · ElapsedMs · StatusCode 여섯 개만 통일해도 수집기에서 대시보드를 만들 수 있게 됩니다.

수집기에서 실제로 던지는 질문

# Seq 쿼리 — 구조적 로깅이라서 되는 것들
@Level = 'Error' and OrderId = 10423

# 이 오류가 오늘 몇 건인가
select count(*) from stream
where @mt = '주문 {OrderId} 실패 · 사유 {Reason}'
group by Reason

# 느린 요청 상위
select ElapsedMs from stream
where ElapsedMs > 1000 order by ElapsedMs desc

# 문자열을 합쳐 놨다면 위 질문 전부
# "주문 10423 실패" 같은 부분 문자열 검색으로 바뀝니다 — 집계 불가
"우리는 수집기가 없어서 구조적 로깅이 필요 없다" — 가장 자주 듣는 말이고, 가장 자주 후회합니다. 수집기는 나중에 붙일 수 있지만, 그때 이미 쌓인 로그는 구조가 없어서 못 씁니다. 템플릿으로 쓰는 데 드는 추가 비용은 0 입니다.
정리 — $"..." 를 로그에 쓰지 마세요. 문장은 고정하고 값은 {이름} 으로 빼면, 같은 코드에서 사람이 읽을 문장과 기계가 셀 필드가 동시에 나옵니다. 비용은 같습니다.
