LOG 11

민감정보 — 한 번 새면 지울 수 없습니다

로그는 복제되기 위해 존재합니다 — 파일로, 수집기로, 백업으로, 감사 시스템으로. 그래서 개인정보나 비밀이 한 줄 섞이면 지워야 할 곳이 네 군데가 됩니다. 마스킹보다 애초에 안 넣는 설계가 유일하게 통합니다.

복제 트리 — 로그는 지우는 것이 아니라 안 넣는 것입니다.

실제로 자주 새는 다섯 경로

경로무엇이 새나
EF Core 쿼리 로그
Database.Command = Information		SQL 파라미터 값 전체 — 주민번호 · 이메일
기동 시 설정 덤프커넥션 문자열 · API 키
{@Object} 통째 구조화엔티티의 모든 속성
HTTP 본문 로깅비밀번호 · 카드번호 · 토큰
예외 메시지실패한 SQL · URL 의 쿼리스트링 토큰
// ❌ 이 한 줄이 사고의 시작입니다
_log.LogInformation("DB 연결 {Conn}", cfg.GetConnectionString("Main"));
//   → Server=...;User Id=sa;Password=P@ssw0rd!  가 그대로 남습니다

// ✅ 비밀을 뺀 부분만
var b = new SqlConnectionStringBuilder(cfg.GetConnectionString("Main"));
_log.LogInformation("DB 연결 {Server}/{Db}", b.DataSource, b.InitialCatalog);
EF Core 는 기본이 안전합니다 — 파라미터 값을 ? 로 가립니다. 그런데 EnableSensitiveDataLogging() 을 켜면 전부 나옵니다. 개발 편의로 켜 두고 운영에 그대로 나가는 것이 가장 흔한 유출 경로입니다. #if DEBUG 로 감싸세요.

막는 법 — 세 겹으로

// ① 타입 자체가 로그에 안 나오게 (가장 확실)
public readonly struct Secret(string value)
{
    private readonly string _v = value;
    public string Reveal() => _v;
    public override string ToString() => "***";   // 어디에 찍혀도 ***
}

// ② Serilog destructure 정책 — 특정 타입/속성을 통째로 가리기
Log.Logger = new LoggerConfiguration()
    .Destructure.ByTransforming<User>(u => new { u.Id, u.Grade })
    .Destructure.ByTransforming<PaymentRequest>(p => new
    {
        p.OrderId,
        Card = Mask(p.CardNumber),        // 1234-****-****-5678
        p.Amount
    })
    .CreateLogger();

static string Mask(string s) =>
    s.Length <= 8 ? "****" : s[..4] + new string('*', s.Length - 8) + s[^4..];
// ③ .NET 8+ 표준 — [LogProperties] + 데이터 분류 리댁션
//    dotnet add package Microsoft.Extensions.Compliance.Redaction
public sealed class Customer
{
    public int Id { get; init; }
    [PersonalData] public string Email { get; init; } = "";
    [SensitiveData] public string Ssn { get; init; } = "";
}

builder.Services.AddRedaction(r =>
    r.SetRedactor<ErasingRedactor>(new DataClassificationSet(
        DataClassifications.SensitiveData)));
①번이 가장 강합니다. 설정은 빠뜨릴 수 있지만 타입은 못 빠뜨립니다. 비밀번호·토큰·카드번호를 string 으로 들고 다니지 말고 전용 타입으로 감싸면, 실수로 로그에 넣어도 *** 만 나옵니다.

사고가 났을 때 — 대응 순서 🔴 실무

유출을 발견했다면

  1. 먼저 흘려보내는 코드를 막습니다 — 설정 한 줄이면 즉시 배포. 로그를 지우는 것보다 더 새지 않게 하는 것이 먼저입니다.
  2. 노출된 비밀을 무효화합니다 — 커넥션 문자열이 샜다면 비밀번호를 바꾸는 것이 로그를 지우는 것보다 빠르고 확실합니다. 토큰·API 키도 마찬가지로 회전시킵니다.
  3. 범위를 셉니다 — 어느 기간, 어느 파일, 어느 색인, 어느 백업. 수집기의 보관 정책을 확인하면 자동 삭제 시점이 나옵니다.
  4. 지울 수 있는 곳부터 지웁니다 — 색인은 대개 지원하지만, 백업 테이프와 외부 감사 시스템은 못 지우는 경우가 많습니다.
  5. 기록을 남깁니다 — 개인정보라면 법적 통지 의무가 걸립니다. 보안 담당자에게 즉시 알리세요. 혼자 조용히 처리하려는 것이 최악입니다.
"로그 파일만 지우면 되지 않나요" — 안 됩니다. 수집기 색인 · 백업 · 개발자 PC 로 내려받은 사본 · 이슈 트래커에 붙인 캡처까지 전부 사본입니다. 사본의 수를 모른다는 것이 로그 유출이 무서운 이유입니다.

사전에 막는 장치

// 테스트로 막기 — 금지 패턴이 로그에 나오면 실패
[Fact]
public void 로그에_비밀이_없어야_한다()
{
    var sink = new ListLoggerProvider();
    using var f = LoggerFactory.Create(b => b.AddProvider(sink));

    new PaymentService(f.CreateLogger<PaymentService>())
        .Pay(new PaymentRequest { CardNumber = "4111111111111111" });

    Assert.DoesNotContain(sink.Lines, l => l.Contains("4111111111111111"));
}
# CI 에서 소스 자체를 검사 — 위험한 호출을 금지 목록으로
grep -rn "EnableSensitiveDataLogging" --include=*.cs src/ \
  | grep -v "#if DEBUG" && exit 1

# 로그 샘플을 정규식으로 훑기 (주민번호 · 카드번호 형태)
grep -Ern "[0-9]{6}-[1-4][0-9]{6}|[0-9]{16}" logs/ && exit 1
코드 리뷰 체크리스트에 한 줄만 추가하세요 — "이 로그가 수집기 화면에 떠 있는 걸 고객이 봐도 괜찮은가". 이 질문 하나가 {@User} 와 설정 덤프의 대부분을 걸러 냅니다.
정리 — 로그는 지우기 어려운 곳으로 자동 복제됩니다. EF Core 민감 로깅 · 설정 덤프 · {@엔티티} · HTTP 본문 넷만 막아도 사고의 대부분이 사라집니다. 막는 순서는 타입 → 정책 → 리뷰이고, 새면 로그를 지우기 전에 비밀을 회전시키세요.
LOG 12

배포 환경별 — 콘솔 · 파일 · EventLog 와 로테이션

같은 앱이라도 어디에 배포하느냐에 따라 로그를 남기는 곳이 달라야 합니다. 컨테이너에 파일을 남기면 컨테이너가 죽을 때 같이 사라지고, 윈도우 서비스에서 콘솔에만 쓰면 아무 데도 안 남습니다.

간트 — 수명과 삭제 시점을 같이 그려야 보관 정책 그림이 됩니다.
배포 형태어디에 남기나 왜빠뜨리기 쉬운 것
컨테이너 · 쿠버네티스 표준 출력(stdout) JSON 한 줄 런타임이 stdout 을 걷어 수집기로 보냅니다. 파일을 쓰면 컨테이너와 함께 사라지고 레이어만 부풀립니다 여러 줄 스택트레이스가 줄마다 다른 이벤트로 쪼개짐 → JSON 한 줄로
윈도우 서비스 파일 + Error 이상만 EventLog 콘솔이 없습니다. 운영자가 이벤트 뷰어로 먼저 봅니다 retainedFileCountLimit 누락 → 디스크 100%
IIS 호스팅 파일 + stdout 로그(기동 실패용) 앱이 못 뜨는 경우는 앱 로그가 없습니다. web.config 의 stdout 로그가 유일한 단서 진단 후 stdout 로그를 끄지 않아 파일이 계속 쌓임
Linux systemd stdout → journald journalctl -u myapp -f 로 바로 봅니다. 로테이션을 OS 가 합니다 SystemdConsole 포매터를 안 써서 우선순위가 전부 info 로
설치형 데스크탑 (WPF) %LOCALAPPDATA% 아래 파일 + EventLog 사용자가 로그를 첨부해 보내야 합니다. 경로가 예측 가능해야 함 Program Files 아래에 쓰려다 권한 오류
콘솔 도구 · 배치 콘솔 + 실행별 파일 하나 스케줄러가 돌린 결과를 나중에 봐야 합니다 실행마다 파일이 늘어 수만 개가 됨

환경별로 설정을 가르는 실제 코드

var builder = Host.CreateApplicationBuilder(args);

builder.Logging.ClearProviders();

if (Environment.GetEnvironmentVariable("KUBERNETES_SERVICE_HOST") is not null
    || builder.Environment.IsProduction() && OperatingSystem.IsLinux())
{
    // 컨테이너 · 리눅스 — 한 줄 JSON 만
    builder.Logging.AddJsonConsole(o => { o.IncludeScopes = true;
                                          o.UseUtcTimestamp = true; });
}
else if (OperatingSystem.IsWindows() && !Environment.UserInteractive)
{
    // 윈도우 서비스 — 파일 + 이벤트 로그
    builder.Logging.AddEventLog(new EventLogSettings
    {
        SourceName = "OrderService",     // ★ 관리자 권한으로 미리 등록 필요
        LogName    = "Application",
        Filter     = (_, lv) => lv >= LogLevel.Error
    });
    builder.Services.AddSerilog((_, cfg) => cfg
        .ReadFrom.Configuration(builder.Configuration));
}
else
{
    // 개발 PC — 사람이 읽기 좋게
    builder.Logging.AddSimpleConsole(o => { o.SingleLine = true;
                                            o.TimestampFormat = "HH:mm:ss "; });
}
EventLog 소스는 미리 등록해야 합니다 — New-EventLog -LogName Application -Source OrderService 를 설치 스크립트에서 관리자 권한으로 한 번 실행합니다. 앱이 실행 중에 만들려 하면 권한 오류가 나고, 그 오류조차 로그로 못 남깁니다.

앱과 OS 중 한쪽만 로테이션하게 하세요. Serilog 롤링과 logrotate 를 둘 다 켜면 파일 이름이 어긋나 지워지지 않는 파일이 남습니다. 컨테이너면 아예 파일을 쓰지 않는 것이 가장 단순합니다.

로그가 안 보일 때 — 진단 순서 🔴 실무

이 순서로 확인하면 대부분 잡힙니다

  1. 레벨 — appsettings.Production.json 이 덮어쓰고 있지 않은가. 환경 변수 Logging__LogLevel__Default 도 확인.
  2. provider 가 등록됐나 — ClearProviders() 뒤에 아무것도 안 넣은 경우가 흔합니다.
  3. 설정 파일이 배포됐나 — nlog.config·appsettings.json 의 CopyToOutputDirectory.
  4. 쓸 권한이 있나 — 서비스 계정이 로그 폴더에 쓸 수 있는지. Program Files 아래는 대개 못 씁니다.
  5. flush 됐나 — 비동기 sink + CloseAndFlush() 누락.
  6. 필터에 걸렸나 — Serilog Filter.ByExcluding 표현식이 의도보다 넓게 잡는 경우.

로깅 자체를 디버깅하는 도구

// Serilog 내부 오류를 콘솔로 (sink 가 조용히 죽는 경우를 잡습니다)
Serilog.Debugging.SelfLog.Enable(Console.Error);

// 지금 적용된 필터 규칙을 찍어 보기
var opts = app.Services.GetRequiredService<IOptions<LoggerFilterOptions>>().Value;
foreach (var r in opts.Rules)
    Console.WriteLine($"{r.ProviderName} | {r.CategoryName} | {r.LogLevel}");
# 프로세스에 붙어 로깅 이벤트만 실시간으로 보기
dotnet-trace collect -p 1234 \
  --providers Microsoft-Extensions-Logging:4:5:EventSourceFilter=*

# 파일이 실제로 커지고 있는지 (윈도우)
Get-Item C:\logs\app-*.ndjson | Select Name,Length,LastWriteTime
SelfLog 는 아껴 두지 말고 개발 환경에서 항상 켜 두세요. Serilog 는 sink 가 실패해도 앱을 멈추지 않습니다(그게 맞습니다). 대신 조용히 사라지므로, "Seq 로 안 간다" 의 원인이 URL 오타 하나인 경우가 아주 많습니다.
정리 — 컨테이너는 stdout JSON, 윈도우 서비스는 파일 + EventLog, 리눅스 서비스는 journald 가 기본형입니다. 파일을 쓴다면 롤링 · 크기 한도 · 보관 개수 세 항목을 반드시 함께 주고, 로테이션은 앱과 OS 중 한쪽만 맡기세요. 로그가 안 보이면 레벨 → provider → 설정 배포 → 권한 → flush 순으로 확인합니다.
