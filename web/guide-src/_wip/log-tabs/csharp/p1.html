디버거는 내 PC 에서만 붙습니다. 운영 서버에서 새벽 3시에 벌어진 일을 다시 볼 방법은 그때 남긴 로그 하나뿐입니다. 그런데 로그는 공짜가 아닙니다 — 문자열을 만들고, 디스크를 때리고, 저장 비용을 만들고, 잘못 쓰면 개인정보까지 흘립니다. 이 탭은 .NET 의 로깅 추상화(ILogger<T>)가 왜 먼저인지부터 시작해 레벨 · 구조적 로깅 · Serilog/NLog/ZLogger 선택 · 소스 제너레이터 · 분산 추적 · 비용 · 민감정보 · 배포 환경별 설정까지 한 번에 잇습니다. 이 탭을 마치면 "로그를 어떻게 남길지"를 설계로 말할 수 있게 됩니다.

LOG 01

왜 추상화가 먼저인가 — ILogger<T> 의 구조

로깅 라이브러리를 먼저 고르면 앱 코드가 그 라이브러리에 묶입니다. .NET 은 반대로 갑니다 — 앱은 ILogger<T> 만 알고, 어디로 내보낼지는 시작 시점에 따로 정합니다. 이 순서가 로깅 설계의 전부입니다.

추상화가 먼저 — 호출부는 하나, 나가는 곳은 여럿입니다.

등장인물 셋만 외우면 됩니다

// ① ILogger<T> — 앱 코드가 보는 유일한 얼굴
public sealed class OrderService(ILogger<OrderService> log)
{
    public async Task PlaceAsync(int orderId)
    {
        log.LogInformation("주문 {OrderId} 처리 시작", orderId);
        // ...
    }
}

// ② ILoggerFactory — ILogger 를 만들어 주는 공장
//    직접 쓸 일은 드뭅니다. DI 가 알아서 ILogger<T> 를 꽂아 줍니다.
ILogger log2 = factory.CreateLogger("Batch.NightlyJob");  // 카테고리 직접 지정

// ③ ILoggerProvider — 실제로 어딘가에 쓰는 사람
//    Console · Debug · EventLog · Serilog · NLog · OpenTelemetry …
ILogger<T> 의 T 는 무엇인가 — 카테고리 이름입니다. ILogger<OrderService> 를 주입받으면 카테고리가 MyApp.Services.OrderService 가 되고, 이 문자열이 그대로 필터링의 키가 됩니다(다음 섹션). 그래서 클래스마다 자기 타입을 넣는 것이 정석입니다.

DI 로 어떻게 꽂히나 — 실제 배선

// Program.cs — .NET 10 최소 호스트
var builder = WebApplication.CreateBuilder(args);

// CreateBuilder 가 이미 다음을 해 둡니다:
//   · appsettings.json 의 "Logging" 섹션을 읽고
//   · Console / Debug / EventSource provider 를 등록
// 그래서 아무것도 안 해도 ILogger<T> 가 동작합니다.

builder.Services.AddScoped<OrderService>();   // 이게 전부입니다

var app = builder.Build();
app.Run();
// 직접 배선하고 싶다면 (콘솔 앱 · 테스트)
using var factory = LoggerFactory.Create(b =>
{
    b.SetMinimumLevel(LogLevel.Debug);
    b.AddSimpleConsole(o => { o.SingleLine = true; o.TimestampFormat = "HH:mm:ss "; });
});
ILogger<Program> log = factory.CreateLogger<Program>();
log.LogInformation("직접 만든 팩토리 {Now}", DateTime.Now);

// 테스트에서는 아무것도 안 하는 로거를 넣습니다
var svc = new OrderService(NullLogger<OrderService>.Instance);
Console.WriteLine 을 쓰지 마세요 — 레벨도, 카테고리도, 시각도, 구조도 없습니다. 컨테이너에서는 그나마 보이지만 윈도우 서비스에서는 아무 데도 안 남습니다. "빠르게 확인만" 이라도 log.LogDebug(...) 를 쓰세요 — 지우는 것도 설정 한 줄입니다.

왜 이 순서인가 — 라이브러리를 먼저 고르면 생기는 일 🟡 중급

라이브러리를 직접 부르는 코드
using Serilog;   // ← 앱 코드가 Serilog 를 압니다

public class OrderService
{
    public void Place(int id)
    {
        Log.Information("주문 {OrderId}", id);   // 전역 정적 로거
    }
}
  • 단위 테스트에서 로그를 가로챌 방법이 없습니다(전역 정적)
  • 라이브러리를 만들어 배포하면 쓰는 쪽도 Serilog 를 강제당합니다
  • NLog 로 바꾸려면 모든 파일을 고쳐야 합니다
추상화를 부르는 코드
using Microsoft.Extensions.Logging;   // ← 표준 인터페이스

public class OrderService(ILogger<OrderService> log)
{
    public void Place(int id)
    {
        log.LogInformation("주문 {OrderId}", id);
    }
}
  • 테스트에서 가짜 로거를 넣어 호출을 검증할 수 있습니다
  • Serilog·NLog·ZLogger 어느 것으로도 Program.cs 한 줄로 교체
  • NuGet 라이브러리를 만들 때 의존성이 인터페이스뿐
Serilog 를 쓰면 추상화를 버리는 것 아닌가요? — 아닙니다. Host.UseSerilog() 는 Serilog 를 ILoggerProvider 로 등록할 뿐입니다. 앱 코드는 계속 ILogger<T> 를 쓰고, 그 호출이 Serilog 의 파이프라인으로 흘러 들어갑니다. "앱은 MEL, 뒤는 Serilog" 가 2026년 현재 .NET 진영의 사실상 표준 조합입니다.

실무에선 이렇게 — 라이브러리를 만드는 쪽의 규칙 🔴 실무

내 라이브러리에 로깅을 넣을 때

<!-- MyLib.csproj — 로깅 의존성은 이 하나면 충분합니다 -->
<ItemGroup>
  <PackageReference Include="Microsoft.Extensions.Logging.Abstractions"
                    Version="10.0.0" />
</ItemGroup>
<!-- ★ .Abstractions 는 인터페이스만 들어 있습니다(구현 없음).
     Serilog·NLog 를 참조하면 쓰는 쪽에 강요하게 됩니다. -->
public sealed class RetryClient
{
    private readonly ILogger _log;

    // 로거를 안 넘겨도 동작하게 — NullLogger 가 기본값
    public RetryClient(ILogger<RetryClient>? log = null)
        => _log = (ILogger?)log ?? NullLogger.Instance;
}
왜 NullLogger.Instance 인가 — _log 가 null 이면 호출할 때마다 ?. 를 붙여야 하고, 빼먹으면 NullReferenceException 입니다. 아무 일도 안 하는 구현을 기본값으로 두면 호출부가 단순해집니다 (널 오브젝트 패턴).

테스트에서 로그를 검증하기

// 1) 가장 쉬운 방법 — 메모리에 모으는 provider 를 직접 만듭니다
public sealed class ListLoggerProvider : ILoggerProvider
{
    public List<string> Lines { get; } = new();
    public ILogger CreateLogger(string category) => new L(this, category);
    public void Dispose() { }

    private sealed class L(ListLoggerProvider p, string cat) : ILogger
    {
        public IDisposable? BeginScope<TState>(TState s) where TState : notnull => null;
        public bool IsEnabled(LogLevel level) => true;
        public void Log<TState>(LogLevel level, EventId id, TState state,
                                Exception? ex, Func<TState, Exception?, string> fmt)
            => p.Lines.Add($"{level}|{cat}|{fmt(state, ex)}");
    }
}
// 2) 테스트
var sink = new ListLoggerProvider();
using var factory = LoggerFactory.Create(b => b.AddProvider(sink));

var svc = new OrderService(factory.CreateLogger<OrderService>());
svc.Place(10423);

Assert.Contains(sink.Lines, l => l.Contains("주문 10423"));
다만 로그 문구를 단정(assert)하는 테스트는 아껴 쓰세요 — 문구를 다듬을 때마다 테스트가 깨집니다. 검증할 가치가 있는 것은 보통 "Error 가 정확히 한 번 났는가" 정도입니다.
정리 — .NET 로깅은 인터페이스(ILogger<T>) → 팩토리 → provider 세 층입니다. 앱 코드는 맨 앞만 알면 되고, 뒤의 두 층은 Program.cs 에서 갈아 끼웁니다. 라이브러리를 먼저 고르지 말고 추상화를 먼저 쓰세요 — 그래야 나중에 고를 수 있습니다.
LOG 02

레벨 6단계와 카테고리 필터 — 가장 긴 접두사가 이깁니다

로그를 다 남기면 비용과 소음이, 안 남기면 장애 때 아무것도 없습니다. 그 사이를 정하는 손잡이가 레벨과 카테고리별 규칙 둘뿐입니다. 규칙이 겹칠 때 어느 것이 이기는지만 알면 됩니다.

깔때기 — 대부분은 기록되기 전에 버려집니다. 그래서 필터가 성능의 절반입니다.

레벨 6단계 + None

레벨값언제 쓰나운영에서
Trace0루프 안 값 · 바이트 덤프. 민감정보가 섞이기 쉬움끔
Debug1분기 진입 · 중간 계산값끔
Information2업무 사건 — 주문 · 로그인 · 지급켬
Warning3이상하지만 회복됨 — 재시도 성공켬
Error4사람이 조치할 것 — 처리 실패켬
Critical5서비스가 못 뜸 · 데이터 손상켬
None6전부 끔 (필터 값으로만 씀)—
Error 의 기준은 하나입니다 — "내가 새벽에 깨어나 고쳐야 하는가". 사용자가 비밀번호를 틀린 것은 Information 입니다(시스템은 정상 동작했습니다). Error 가 하루 수천 건 찍히면 진짜 사고가 나도 아무도 못 봅니다.

Serilog 레벨과의 대응

MEL (LogLevel)Serilog (LogEventLevel)NLog
TraceVerboseTrace
DebugDebugDebug
InformationInformationInfo
WarningWarningWarn
ErrorErrorError
CriticalFatalFatal
이름만 다르고 값은 같습니다. Serilog 문서를 보다가 Verbose·Fatal 이 나오면 Trace·Critical 로 읽으면 됩니다. appsettings.json 의 Logging:LogLevel 에는 MEL 이름을, Serilog:MinimumLevel 에는 Serilog 이름을 씁니다 — 여기서 자주 헷갈립니다.
필터 규칙 — 길이가 곧 우선순위. 짧은 규칙은 넓게, 긴 규칙은 좁게 덮습니다.

실무에서 그대로 쓰는 appsettings

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.AspNetCore.Hosting.Diagnostics": "Information",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning",
      "System.Net.Http.HttpClient": "Warning",
      "MyApp.Orders": "Debug"
    },
    "Console": {
      "LogLevel": { "Default": "Warning" },
      "FormatterName": "json"
    }
  }
}
두 층입니다 — Logging:LogLevel 은 모든 provider 공통, Logging:Console:LogLevel 은 그 provider 에만 적용됩니다. "파일에는 Debug 까지, 콘솔에는 Warning 부터" 같은 조합을 이렇게 만듭니다. provider 규칙이 있으면 공통 규칙 대신 그것이 쓰입니다.

개발 · 운영을 파일로 가르기

// appsettings.Development.json — 로컬에서만 시끄럽게
{
  "Logging": {
    "LogLevel": {
      "Default": "Debug",
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}
# 어느 파일이 겹쳐 적용될지는 이 환경 변수가 정합니다
DOTNET_ENVIRONMENT=Development     # 콘솔 · 워커
ASPNETCORE_ENVIRONMENT=Production  # 웹 앱

# 환경 변수로 한 항목만 덮어쓰기 (컨테이너에서 자주 씁니다)
Logging__LogLevel__MyApp.Orders=Trace
#   __ 두 개가 JSON 의 : 한 개에 해당합니다
가장 흔한 사고 — 운영에 Development 설정이 뜨는 것. EntityFrameworkCore.Database.Command 가 Information 이면 모든 SQL 과 파라미터가 로그에 찍힙니다. 개인정보가 통째로 새는 대표 경로입니다.

코드로 거르기 — AddFilter 와 동적 변경 🔴 실무

AddFilter — 설정보다 우선하는 코드 규칙

builder.Logging
    // 카테고리 접두사 + 최소 레벨
    .AddFilter("Microsoft", LogLevel.Warning)
    .AddFilter("MyApp.Batch", LogLevel.Debug)

    // provider 를 지정해서 (Console 에만 적용)
    .AddFilter<ConsoleLoggerProvider>("MyApp", LogLevel.Information)

    // 임의 조건 — 카테고리와 레벨을 보고 직접 판단
    .AddFilter((provider, category, level) =>
        category?.StartsWith("Microsoft.AspNetCore.Mvc") == true
            ? level >= LogLevel.Warning
            : level >= LogLevel.Information);
우선순위 — ① provider 를 지정한 규칙 → ② 카테고리 접두사가 가장 긴 규칙 → ③ Default → ④ SetMinimumLevel. 같은 길이면 나중에 등록된 것이 이깁니다. 헷갈리면 규칙을 줄이는 것이 답입니다 — 실무에서 6~8줄을 넘길 일은 거의 없습니다.

재시작 없이 레벨 바꾸기

// ① appsettings.json 은 기본이 reloadOnChange: true 입니다.
//    파일을 고치면 몇 초 안에 로깅 필터가 다시 계산됩니다. 재배포 불필요.

// ② Serilog 는 스위치를 직접 들고 흔들 수 있습니다
public static class LogSwitch
{
    public static readonly LoggingLevelSwitch Level =
        new(Serilog.Events.LogEventLevel.Information);
}

Log.Logger = new LoggerConfiguration()
    .MinimumLevel.ControlledBy(LogSwitch.Level)
    .WriteTo.Console()
    .CreateLogger();

// 운영 중 관리자 엔드포인트로 30분만 Debug 를 켭니다
app.MapPost("/admin/loglevel/{lv}", (string lv) =>
{
    LogSwitch.Level.MinimumLevel = Enum.Parse<Serilog.Events.LogEventLevel>(lv, true);
    return Results.Ok($"level = {lv}");
}).RequireAuthorization("admin");
이게 실전에서 제일 값어치가 큽니다 — 재현이 안 되는 버그를 잡을 때 운영에서 잠깐 Debug 를 켤 수 있느냐가 조사 시간을 하루에서 10분으로 줄입니다. 다만 반드시 자동으로 되돌아가게 만드세요(타이머 · 만료 시각). 켜 둔 채 잊으면 다음 섹션의 비용 이야기가 그대로 현실이 됩니다.
정리 — 손잡이는 레벨과 카테고리 접두사 둘입니다. 규칙이 겹치면 가장 긴 접두사가 이기고, provider 전용 규칙이 공통 규칙보다 셉니다. Microsoft.* 를 Warning 으로 눌러 두는 것만으로 로그 양이 크게 줄어듭니다.
