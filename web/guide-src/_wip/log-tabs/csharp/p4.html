LOG 08

ASP.NET Core 연동 — 요청 로그와 스코프

웹 앱에서 로그의 90%는 요청과 함께 나옵니다. 문제는 두 가지입니다 — 기본 요청 로그가 너무 시끄럽고, 줄마다 어느 요청인지 알 수 없다는 것. 전자는 필터로, 후자는 스코프로 해결합니다.

스윔레인 — 줄을 넘는 화살표가 값이 붙는 지점입니다.

기본 요청 로그의 소음 줄이기

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.AspNetCore.Hosting.Diagnostics": "Information",
      "Microsoft.AspNetCore.Routing.EndpointMiddleware": "Warning",
      "Microsoft.AspNetCore.Mvc.Infrastructure": "Warning",
      "Microsoft.AspNetCore.StaticFiles": "Warning",
      "Microsoft.Hosting.Lifetime": "Information"
    }
  }
}
요청 하나에 기본 로그가 5~8줄 나옵니다 — "요청 시작 · 라우트 매칭 · 액션 실행 · 결과 실행 · 요청 완료". 위처럼 Microsoft.AspNetCore 를 Warning 으로 누르고 필요한 하나만 되살리는 것이 정석입니다. Serilog 를 쓴다면 UseSerilogRequestLogging() 이 이 전부를 한 줄로 대체합니다.

HTTP 로깅 미들웨어 (내장)

builder.Services.AddHttpLogging(o =>
{
    o.LoggingFields = HttpLoggingFields.RequestPath
                    | HttpLoggingFields.RequestMethod
                    | HttpLoggingFields.ResponseStatusCode
                    | HttpLoggingFields.Duration;        // ★ 본문은 빼세요

    o.RequestHeaders.Add("X-Client-Version");             // 허용 목록 방식
    o.ResponseHeaders.Add("X-Trace-Id");
    o.CombineLogs = true;                                 // 요청/응답을 한 줄로
});

var app = builder.Build();
app.UseHttpLogging();

// 특정 엔드포인트만 본문까지 (진단용 · 임시)
app.MapPost("/orders", Handler)
   .WithHttpLogging(HttpLoggingFields.RequestBody);
헤더는 기본이 마스킹입니다 — Authorization·Cookie 는 [Redacted] 로 나옵니다. 허용 목록에 직접 추가하지 마세요. RequestBody·ResponseBody 는 운영에서 켜지 마세요 — 비밀번호·카드번호가 그대로 남고, 큰 본문은 메모리도 먹습니다.

스코프 — 요청 하나를 끝까지 따라가기 🟡 중급

BeginScope 미들웨어

app.Use(async (ctx, next) =>
{
    var log = ctx.RequestServices.GetRequiredService<ILogger<Program>>();

    var traceId = Activity.Current?.TraceId.ToString()
                  ?? ctx.TraceIdentifier;

    ctx.Response.Headers["X-Trace-Id"] = traceId;   // ★ 클라이언트에도 돌려줍니다

    using (log.BeginScope(new Dictionary<string, object?>
    {
        ["TraceId"]  = traceId,
        ["UserId"]   = ctx.User.FindFirst("sub")?.Value,
        ["TenantId"] = ctx.Request.Headers["X-Tenant"].ToString()
    }))
    {
        await next(ctx);
    }
});
스코프 값을 실제로 출력하려면 provider 설정이 필요합니다 — Console 은 IncludeScopes(기본 false), JSON 포매터는 자동, Serilog 는 Enrich.FromLogContext(). "스코프를 넣었는데 안 보인다"의 원인은 대부분 여기입니다.

컨테이너에는 JSON, 개발 PC 에는 SimpleConsole 이 좋습니다. 컨테이너 로그는 사람이 아니라 수집기가 읽습니다 — 여러 줄로 예쁘게 찍으면 수집기가 한 줄씩 다른 이벤트로 오해합니다. 스택트레이스가 여러 줄로 쪼개져 검색이 안 되는 사고가 여기서 나옵니다.

감사 로그가 필요할 때 — W3CLogger 🔴 실무

// 애플리케이션 로그와 별개로, 웹 서버 형식(W3C Extended)의 접근 로그를
// 파일로 남깁니다. 보안 감사·트래픽 분석 요구가 있을 때 씁니다.
builder.Services.AddW3CLogging(o =>
{
    o.LoggingFields   = W3CLoggingFields.All & ~W3CLoggingFields.UserName;
    o.LogDirectory    = @"C:\logs\w3c";
    o.FlushInterval   = TimeSpan.FromSeconds(2);
    o.FileSizeLimit   = 50 * 1024 * 1024;
    o.RetainedFileCountLimit = 30;
    o.FileName        = "access-";
    o.AdditionalRequestHeaders.Add("X-Tenant");
});

var app = builder.Build();
app.UseW3CLogging();
언제 쓰나 — IIS 접근 로그와 같은 형식이 필요할 때, 또는 "누가 언제 어떤 URL 을 호출했는가"를 감사 목적으로 별도 보관해야 할 때입니다. 애플리케이션 로그와 보관 기간·권한이 다른 경우가 많아 파일을 분리하는 것이 맞습니다. 쿠버네티스에 배포한다면 보통 Ingress/프록시의 접근 로그가 이 역할을 대신하므로 앱에서 또 남길 이유가 없습니다.
정리 — 요청 로그는 줄이는 것과 묶는 것 두 가지입니다. Microsoft.AspNetCore 를 Warning 으로 누르고 요약 한 줄만 남기고, BeginScope 로 TraceId · UserId 를 붙여 두면 조사 시간이 열 배 줄어듭니다.
LOG 09

Activity 와 분산 추적 — TraceId 는 어떻게 자동으로 붙나

서비스가 하나면 로그만으로 충분합니다. 둘만 되어도 "이 요청이 저쪽에서 뭘 했나"를 이어 붙일 방법이 필요합니다. .NET 은 System.Diagnostics.Activity 로 표준 W3C Trace Context 를 처리하고, 로거는 그 값을 알아서 읽어 씁니다.

시퀀스 — TraceId 는 같고 SpanId 만 다릅니다. 그것이 "같은 요청"의 정의입니다.

원리 — 헤더 한 줄이 전부입니다

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └ 플래그(샘플링됨)
             │  │                                └ SpanId  — 이 구간 하나의 ID
             │  └ TraceId — 요청 전체에 하나. 서비스를 넘어가도 같습니다
             └ 버전

# .NET 은 이 헤더를 자동으로 읽고(수신), 자동으로 붙입니다(HttpClient 송신).
# 코드를 한 줄도 안 써도 이미 동작합니다 — .NET 5 부터 기본이 W3C 형식입니다.
// 지금 요청의 추적 값 읽기
var act = Activity.Current;
string? traceId = act?.TraceId.ToString();   // 32자리 hex
string? spanId  = act?.SpanId.ToString();    // 16자리 hex

// 내 코드 구간을 하나의 span 으로 만들기
private static readonly ActivitySource Source = new("MyApp.Orders", "1.0.0");

using var activity = Source.StartActivity("주문 검증");
activity?.SetTag("order.id", orderId);
activity?.SetTag("order.total", total);
// ... 작업 ...
activity?.SetStatus(ActivityStatusCode.Error, "재고 부족");
ActivitySource 는 static readonly 로 한 번만 만듭니다. 이름은 보통 어셈블리 이름을 씁니다 — 나중에 OpenTelemetry 에서 AddSource("MyApp.Orders") 로 이 이름을 지정해야 수집됩니다. StartActivity 는 아무도 안 듣고 있으면 null 을 돌려줍니다(그래서 ?.).

로그에 TraceId 를 자동으로 넣기

// ① 내장 Console — 그냥 켜면 됩니다
builder.Logging.AddJsonConsole();
builder.Services.Configure<LoggerFilterOptions>(_ => { });
// JSON 포매터는 TraceId·SpanId 를 이벤트에 넣어 줍니다.
// (ActivityTrackingOptions 기본값이 TraceId|SpanId|ParentId)

// ② 스코프에 명시적으로 넣기
builder.Logging.Configure(o => o.ActivityTrackingOptions =
      ActivityTrackingOptions.TraceId
    | ActivityTrackingOptions.SpanId
    | ActivityTrackingOptions.ParentId
    | ActivityTrackingOptions.Baggage);
// ③ Serilog — enricher 하나면 끝
//    dotnet add package Serilog.Enrichers.Span (또는 직접 작성)
Log.Logger = new LoggerConfiguration()
    .Enrich.FromLogContext()
    .Enrich.WithProperty("service.name", "order-api")
    .Enrich.With<TraceEnricher>()
    .WriteTo.Seq("http://seq:5341")
    .CreateLogger();

public sealed class TraceEnricher : ILogEventEnricher
{
    public void Enrich(LogEvent e, ILogEventPropertyFactory f)
    {
        var a = Activity.Current;
        if (a is null) return;
        e.AddPropertyIfAbsent(f.CreateProperty("TraceId", a.TraceId.ToString()));
        e.AddPropertyIfAbsent(f.CreateProperty("SpanId",  a.SpanId.ToString()));
    }
}
왜 로그에 TraceId 가 있어야 하나 — 추적(trace)은 어디서 시간이 갔는지를, 로그는 무슨 일이 있었는지를 말합니다. 둘을 잇는 열쇠가 TraceId 입니다. "느린 요청 찾기 → 그 요청의 로그 보기" 가 클릭 한 번이 되느냐, 시각으로 뒤지느냐의 차이입니다.

OpenTelemetry 로 내보내기 🔴 실무

배선 — 로그·추적·지표를 한 번에

// dotnet add package OpenTelemetry.Extensions.Hosting
// dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol
// dotnet add package OpenTelemetry.Instrumentation.AspNetCore
// dotnet add package OpenTelemetry.Instrumentation.Http

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("order-api", serviceVersion: "1.4.2"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation(o =>
            o.Filter = ctx => !ctx.Request.Path.StartsWithSegments("/health"))
        .AddHttpClientInstrumentation()
        .AddSource("MyApp.Orders")            // ★ 내 ActivitySource 이름
        .AddOtlpExporter())
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()
        .AddOtlpExporter());

// 로그도 같은 파이프라인으로
builder.Logging.AddOpenTelemetry(o =>
{
    o.IncludeScopes = true;
    o.IncludeFormattedMessage = true;
    o.ParseStateValues = true;
    o.AddOtlpExporter();
});
OTLP 로 내보내면 백엔드를 나중에 고를 수 있습니다 — Jaeger · Tempo · Honeycomb · Datadog · Application Insights 가 전부 OTLP 를 받습니다. OTEL_EXPORTER_OTLP_ENDPOINT 환경 변수만 바꾸면 목적지가 바뀝니다. 벤더 SDK 를 코드에 심지 마세요 — 그것이 OpenTelemetry 의 존재 이유입니다.

로그와 추적, 무엇을 어디에 담나

담을 것어디에
업무 사건 (주문 접수)로그 — 사람이 읽을 문장 + 필드
구간 소요 시간추적(span) — 로그로 재지 마세요
초당 처리량 · 오류율지표(metric) — 로그를 세는 것보다 훨씬 쌉니다
예외 스택로그 + span 에 SetStatus(Error)
요청 식별자양쪽 모두 — TraceId 로 잇습니다
개인정보어느 쪽에도 안 됩니다
흔한 낭비 — 처리량을 세려고 요청마다 Information 로그를 남기고 수집기에서 count(*) 를 돌리는 것. 같은 일을 Meter 카운터 하나로 하면 저장 비용이 자릿수 단위로 줄어듭니다. 로그는 세는 도구가 아니라 읽는 도구입니다.
정리 — traceparent 헤더 한 줄이 서비스 사이를 잇고, .NET 은 그것을 Activity.Current 로 들고 있습니다. 로거가 그 값을 읽어 붙이므로 우리가 할 일은 켜 두는 것뿐입니다. 시간은 span, 사건은 로그, 개수는 지표 — 담을 곳을 나누면 비용이 내려갑니다.
LOG 10

성능과 비용 — 로그는 공짜가 아닙니다

로그 한 줄에는 문자열 할당 · 직렬화 · 파일 I/O · 네트워크 · 저장 요금이 붙습니다. 대부분은 무시해도 되지만, 어디서 대가를 치르는지는 알아야 "로그를 더 남길까 말까"를 감이 아니라 선택으로 할 수 있습니다.

발산 매트릭스 — 양극이 있는 값은 한 색 명도가 아니라 두 색으로 그립니다.

비싼 자리 넷

  • 문자열 만들기 — 보간 · ToString() · JsonSerializer. 레벨이 꺼져 있어도 인자를 준비하면 이미 비용입니다.
  • 박싱 — int·DateTime 을 object[] 에 담을 때. [LoggerMessage] 로 없앱니다.
  • 동기 I/O — 파일 flush 나 네트워크 전송이 요청 스레드를 붙잡는 경우.
  • 저장 · 색인 요금 — 수집기는 수집량으로 과금합니다. 로그 한 줄이 곧 돈이 되는 구간입니다.
// 인자를 만드는 비용이 큰 경우에만 IsEnabled 로 감쌉니다
if (_log.IsEnabled(LogLevel.Debug))
{
    // 이 직렬화가 비싼 것이지, 로그 호출이 비싼 게 아닙니다
    _log.LogDebug("응답 원문 {Body}", JsonSerializer.Serialize(dto));
}

// 반대로 이런 건 감쌀 필요 없습니다 (인자 준비 비용이 0)
_log.LogDebug("주문 {OrderId} 검증 통과", orderId);
IsEnabled 를 모든 로그에 붙이지 마세요. 로거 내부가 이미 같은 검사를 합니다. 인자를 만드는 데 비용이 드는 경우에만 감쌉니다 — 직렬화 · 큰 컬렉션 순회 · 문자열 결합 같은 것들입니다.

비동기 sink 와 유실

// dotnet add package Serilog.Sinks.Async
Log.Logger = new LoggerConfiguration()
    .WriteTo.Async(a => a.File("logs/app-.ndjson",
                               rollingInterval: RollingInterval.Day),
                   bufferSize: 10_000,
                   blockWhenFull: false)   // ★ 여기가 선택 지점
    .CreateLogger();

//  blockWhenFull: false  → 큐가 차면 로그를 버립니다 (앱은 안 느려짐)
//  blockWhenFull: true   → 큐가 찰 때까지 요청 스레드가 기다립니다 (로그는 안 잃음)
//
//  ※ 어느 쪽이든 프로세스가 강제 종료되면 큐에 남은 것은 사라집니다.
//     Log.CloseAndFlush() 를 반드시 호출하세요.
// 종료 시 확실히 비우기 — 호스트 종료 훅에 연결
var app = builder.Build();
app.Lifetime.ApplicationStopped.Register(Log.CloseAndFlush);

// 컨테이너라면 종료 유예 시간도 늘려 둡니다
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(15));
가장 아픈 유실 — 앱이 죽는 순간의 로그가 바로 그 이유인데, 비동기 큐에 있다가 함께 사라지는 경우입니다. Error 이상은 동기 sink 로도 한 벌 더 남기는 구성이 안전합니다 (WriteTo.Logger(l => l.Filter.ByIncludingOnly(...).WriteTo.File(...))).

재는 법 — 감이 아니라 숫자로 🔴 실무

돌고 있는 프로세스에서 바로 보기

dotnet tool install -g dotnet-counters
dotnet tool install -g dotnet-trace

# ① 할당률·GC 를 실시간으로 — 로그를 껐다 켜며 차이를 봅니다
dotnet-counters monitor --process-id 1234 \
  --counters System.Runtime[alloc-rate,gen-0-gc-count,time-in-gc]

# ② 로깅이 실제로 얼마나 도는지 이벤트로 세기
dotnet-trace collect --process-id 1234 \
  --providers Microsoft-Extensions-Logging:4:4

# ③ 결과를 speedscope 로 열어 봅니다
dotnet-trace convert trace.nettrace --format speedscope
가장 정직한 실험 — 부하를 준 상태에서 로그 레벨만 Warning 으로 올려 보고 p99 지연과 alloc-rate 가 얼마나 떨어지는지 봅니다. 떨어지지 않으면 로깅은 병목이 아닙니다 — 다른 데를 보세요.

양을 줄이는 실제 수단

수단효과 · 주의
카테고리 필터가장 싸고 확실합니다. Microsoft.* 를 Warning 으로
헬스체크·정적파일 제외수집량이 눈에 띄게 줄어듭니다
요약 한 줄요청당 6줄 → 1줄. UseSerilogRequestLogging
샘플링성공 요청은 10%만, 오류는 100%
지표로 대체"세기"는 Meter 로. 로그보다 훨씬 쌉니다
보관 기간 단축90일 → 14일. 대부분 7일이면 충분합니다
압축 · 아카이브오래된 것은 객체 스토리지로 내리기
줄이기 전에 "이 로그로 무엇을 조사했는가"를 물어보세요. 1년 동안 아무도 열어 보지 않은 로그는 지워도 됩니다. 반대로 사고 때마다 찾게 되는 로그는 오히려 더 자세히 남길 값어치가 있습니다. 양이 아니라 쓰임으로 판단하는 것이 유일하게 통하는 기준입니다.
정리 — 비싼 자리는 문자열 만들기 · 박싱 · 동기 I/O · 저장 요금 넷입니다. 필터로 앞에서 자르고, 인자가 비쌀 때만 IsEnabled 로 감싸고, 비동기 sink 를 쓴다면 종료 시 flush 를 반드시 챙기세요. 그리고 줄이기 전에 재세요 — 대개 로깅은 병목이 아닙니다.
