LOG 05

[LoggerMessage] — 소스 제너레이터가 만드는 무할당 로깅

log.LogInformation("...", a, b) 한 줄은 실행 중에 배열을 만들고 값 타입을 박싱합니다. 초당 몇백 줄이면 아무 문제 없지만, 초당 수십만 줄이면 그것만으로 GC 가 돕니다. [LoggerMessage] 는 그 코드를 컴파일 시점에 미리 만들어 둡니다.

좌우 대조 — 같은 높이에 같은 단계를 놓으면 사라진 단계가 보입니다.
막대 — 순서만 보세요. 절대값은 런타임·인자 개수·sink 에 따라 달라집니다.

쓰는 법 — partial 메서드 선언 하나

// .NET 6 부터 들어온 소스 제너레이터입니다. 패키지 설치 없음.
public static partial class OrderLog
{
    [LoggerMessage(
        EventId    = 1001,
        Level      = LogLevel.Information,
        Message    = "주문 {OrderId} 처리 완료 · {ElapsedMs} ms")]
    public static partial void Completed(
        ILogger logger, int orderId, long elapsedMs);

    [LoggerMessage(EventId = 1002, Level = LogLevel.Error,
                   Message = "주문 {OrderId} 실패 · 사유 {Reason}")]
    public static partial void Failed(
        ILogger logger, Exception ex, int orderId, string reason);
}

// 호출
OrderLog.Completed(_log, orderId, sw.ElapsedMilliseconds);
OrderLog.Failed(_log, ex, orderId, "재고 부족");
클래스에 partial, 메서드에 partial, 본문 없음 — 이 세 가지가 조건입니다. 빌드하면 제너레이터가 나머지를 채웁니다. Exception 매개변수는 이름과 무관하게 타입으로 알아봅니다(템플릿에 안 넣어도 됩니다).

인스턴스 메서드로 더 깔끔하게

// 로거를 필드로 들고 있으면 첫 인자를 생략할 수 있습니다
public sealed partial class OrderService(ILogger<OrderService> logger)
{
    private readonly ILogger _logger = logger;   // ★ 이름이 _logger 여야 자동 인식

    [LoggerMessage(Level = LogLevel.Warning,
                   Message = "재고 부족 {Sku} — 남은 수량 {Left}")]
    private partial void LogOutOfStock(string sku, int left);

    public void Place(Order o)
    {
        if (o.Left <= 0) LogOutOfStock(o.Sku, o.Left);   // 인자 두 개뿐
    }
}
// 레벨을 호출 시점에 정하고 싶다면 Level 을 빼고 매개변수로
[LoggerMessage(Message = "외부 호출 {Url} → {Status}")]
public static partial void Called(
    ILogger logger, LogLevel level, string url, int status);

Called(_log, status >= 500 ? LogLevel.Error : LogLevel.Debug, url, status);
필드 이름 규칙이 있습니다 — _logger · logger · _log 같은 이름의 ILogger 필드를 찾습니다. 못 찾으면 컴파일 에러가 납니다(런타임 실패가 아니라서 다행입니다). 찾지 못하면 첫 인자로 ILogger 를 명시하세요.

언제 필요한가 — 전부 바꿀 필요는 없습니다 🟡 중급

측정이 먼저입니다. dotnet-counters monitor --counters System.Runtime 으로 Gen0 GC 횟수와 할당률을 보고, 로깅을 끄면 그 수치가 눈에 띄게 떨어질 때만 손을 대세요. 대부분의 앱에서는 DB 왕복 한 번이 로그 천 줄보다 비쌉니다.

직접 재는 법

[MemoryDiagnoser]          // ★ 할당량이 같이 나옵니다
public class LogBench
{
    private readonly ILogger _log =
        LoggerFactory.Create(b => b.SetMinimumLevel(LogLevel.Warning))
                     .CreateLogger("bench");
    // 최소 레벨이 Warning → Information 로그는 전부 버려집니다.
    // "꺼진 로그의 비용" 을 재는 설정입니다.

    [Benchmark(Baseline = true)]
    public void Interpolated() => _log.LogInformation($"주문 {42} 처리 {17} ms");

    [Benchmark]
    public void Template() => _log.LogInformation("주문 {Id} 처리 {Ms} ms", 42, 17);

    [Benchmark]
    public void Generated() => BenchLog.Done(_log, 42, 17);
}
보간 문자열은 레벨이 꺼져 있어도 문자열을 만듭니다. C# 10 부터 ILogger 에 보간 문자열 핸들러가 붙어 일부는 지연 평가되지만, 구조적 필드는 여전히 사라집니다. 성능 이전에 검색 가능성 때문에 템플릿을 써야 합니다.
정리 — [LoggerMessage] 는 partial 메서드 선언 하나로 박싱과 배열 할당을 없앱니다. 전부 바꿀 필요는 없고, 많이 도는 곳과 평소에 꺼 두는 로그부터 적용하세요. 이득이 있는지는 MemoryDiagnoser 로 확인하고 판단합니다.
LOG 06

Serilog 실전 — 파이프라인 · sink · enricher

Serilog 를 이해하는 가장 빠른 길은 "이벤트 하나가 지나가는 파이프라인" 으로 보는 것입니다. 만들고 → 정보를 덧붙이고 → 거르고 → 형식을 정하고 → 여러 곳으로 보냅니다. 설정 파일의 항목 이름이 전부 이 순서와 맞습니다.

파이프라인 — 셰브론 모양 자체가 방향입니다. 설정 파일 항목이 이 순서와 같습니다.

배선 — Program.cs 는 이 정도면 끝

using Serilog;

// ① 기동 중 터지는 예외도 잡으려면 부트스트랩 로거를 먼저 만듭니다
Log.Logger = new LoggerConfiguration()
    .WriteTo.Console()
    .CreateBootstrapLogger();

try
{
    var builder = WebApplication.CreateBuilder(args);

    // ② 실제 설정은 appsettings.json 에서 읽습니다
    builder.Host.UseSerilog((ctx, sp, cfg) => cfg
        .ReadFrom.Configuration(ctx.Configuration)
        .ReadFrom.Services(sp)                 // DI 로 등록한 enricher/sink
        .Enrich.FromLogContext());

    var app = builder.Build();
    app.UseSerilogRequestLogging();            // 요청 요약 한 줄
    app.Run();
}
catch (Exception ex)
{
    Log.Fatal(ex, "기동 실패");
}
finally
{
    Log.CloseAndFlush();                       // ★ 버퍼를 비우고 끝냅니다
}
Log.CloseAndFlush() 를 빼면 마지막 로그가 사라집니다. 특히 비동기 sink 를 쓰면 종료 직전 몇 초치가 통째로 유실됩니다. 컨테이너가 SIGTERM 을 보내고 몇 초 뒤 SIGKILL 하는 환경에서 가장 보고 싶은 로그(종료 원인)가 없어지는 이유가 이것입니다.

설정을 JSON 으로 — 재배포 없이 바꾸기

enricher — 모든 로그에 자동으로 붙는 값 🟡 중급

직접 만드는 enricher

public sealed class TenantEnricher(IHttpContextAccessor acc) : ILogEventEnricher
{
    public void Enrich(LogEvent e, ILogEventPropertyFactory f)
    {
        var tenant = acc.HttpContext?.User.FindFirst("tenant")?.Value;
        if (tenant is not null)
            e.AddPropertyIfAbsent(f.CreateProperty("TenantId", tenant));
    }
}

// 등록 (ReadFrom.Services(sp) 가 이걸 집어 갑니다)
builder.Services.AddHttpContextAccessor();
builder.Services.AddSingleton<ILogEventEnricher, TenantEnricher>();
// 코드 블록 범위에만 값을 붙이기 — LogContext
using (LogContext.PushProperty("BatchId", batchId))
using (LogContext.PushProperty("FileName", file.Name))
{
    await ProcessAsync(file);      // 이 안의 모든 로그에 두 값이 붙습니다
}                                   // using 을 벗어나면 자동으로 빠집니다
Enrich.FromLogContext() 를 켜야 PushProperty 가 동작합니다. 이걸 빼놓고 "값이 안 붙는다"고 하는 경우가 흔합니다. ILogger.BeginScope 로 넣은 값도 Serilog 에서는 같은 통로로 흘러갑니다.

Serilog.Expressions — 조건 필터

{
  "Serilog": {
    "Using": [ "Serilog.Expressions" ],
    "Filter": [
      { "Name": "ByExcluding",
        "Args": { "expression":
          "RequestPath like '/health%' or RequestPath like '/metrics%'" } },
      { "Name": "ByExcluding",
        "Args": { "expression":
          "SourceContext = 'Microsoft.AspNetCore.StaticFiles.StaticFileMiddleware'" } }
    ],
    "WriteTo": [
      { "Name": "Console",
        "Args": { "formatter": {
          "type": "Serilog.Templates.ExpressionTemplate, Serilog.Expressions",
          "template":
            "[{@t:HH:mm:ss} {@l:u3}] {TraceId} {@m}\n{@x}" } } }
    ]
  }
}
헬스체크를 안 거르면 로그의 대부분이 헬스체크가 됩니다. 쿠버네티스는 보통 몇 초마다 /health 를 찌릅니다. 하루 8만 6천 번이 넘고, 그게 수집기 요금이 됩니다. 필터는 성능이 아니라 비용과 가독성의 문제입니다.
정리 — Serilog 는 생성 → Enrich → Filter → Format → Sink 파이프라인입니다. 코드에는 UseSerilog + ReadFrom.Configuration 만 두고, 나머지는 전부 JSON 으로 뺍니다. Log.CloseAndFlush() 와 파일 보관 한도 두 가지는 절대 빠뜨리지 마세요.
LOG 07

NLog 실전과 고르는 순서 — 언제 Serilog 대신 쓰나

NLog 는 설정 파일 하나로 로그의 목적지와 규칙을 통째로 바꾸는 데 강합니다. 코드를 못 건드리는 운영 환경, 이미 XML 설정 문화가 있는 조직에서 여전히 좋은 선택입니다. 반대로 수집기로 구조적 이벤트를 보내는 것이 목적이면 Serilog 가 편합니다.

결정 흐름도 — 질문은 마름모, 답은 상자. 답이 없는 가지를 남기지 않습니다.

nlog.config — 이 파일이 전부입니다

<?xml version="1.0" encoding="utf-8" ?>
<nlog xmlns="http://www.nlog-project.org/schemas/NLog.xsd"
      autoReload="true" throwConfigExceptions="true">

  <targets>
    <!-- 파일 — 날짜별 롤링 + 보관 30일 -->
    <target xsi:type="File" name="file"
            fileName="logs/app-${shortdate}.log"
            archiveEvery="Day" maxArchiveDays="30"
            archiveAboveSize="104857600"
            layout="${longdate}|${level:uppercase=true}|${logger}|${message} ${exception:format=tostring}" />

    <!-- 구조적 JSON — 수집기로 보낼 때 -->
    <target xsi:type="File" name="json" fileName="logs/app.ndjson">
      <layout xsi:type="JsonLayout" includeEventProperties="true">
        <attribute name="t" layout="${date:universalTime=true:format=o}" />
        <attribute name="l" layout="${level}" />
        <attribute name="m" layout="${message}" />
      </layout>
    </target>

    <target xsi:type="ColoredConsole" name="con"
            layout="${time}|${level:uppercase=true}|${message}" />
  </targets>

  <rules>
    <logger name="Microsoft.*"          maxlevel="Info" final="true" />
    <logger name="*" minlevel="Debug"   writeTo="file" />
    <logger name="*" minlevel="Info"    writeTo="con,json" />
  </rules>
</nlog>
autoReload="true" 가 NLog 의 진짜 장점입니다 — 운영 서버에서 이 XML 만 고치면 재시작 없이 로그 레벨과 목적지가 바뀝니다. final="true" 규칙으로 여기서 처리를 끝내라고 지정할 수 있어 소음 차단이 간결합니다.

배선과 주의점

using NLog;
using NLog.Web;

var logger = NLog.LogManager.Setup()
                 .LoadConfigurationFromAppSettings()   // 또는 nlog.config
                 .GetCurrentClassLogger();
try
{
    var builder = WebApplication.CreateBuilder(args);

    builder.Logging.ClearProviders();     // ★ 중복 방지
    builder.Host.UseNLog();               // MEL → NLog 로 연결

    var app = builder.Build();
    app.Run();
}
catch (Exception ex) { logger.Error(ex, "기동 실패"); throw; }
finally { NLog.LogManager.Shutdown(); }   // ★ 버퍼 flush
nlog.config 를 출력 폴더로 복사해야 합니다. <None Update="nlog.config"><CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory></None> 를 .csproj 에 넣지 않으면 배포본에서 로그가 조용히 사라집니다. throwConfigExceptions="true" 를 켜 두면 이런 실수가 기동 시 바로 터집니다.
