로그는 글이 아니라
검색되는
데이터입니다

장애가 났을 때 우리가 가진 것은 로그뿐입니다. 그런데 대부분의 Node 프로젝트는 console.log 로 시작해서 그대로 운영에 나갑니다 — 레벨도, 시각도, 요청 ID 도 없이. 이 탭은 왜 console 로는 부족한지부터 시작해 pino · winston · debug · consola 같은 라이브러리를 무엇을 보고 고르는지, JSON 한 줄에 어떤 필드를 넣는지, 요청 ID 를 어떻게 자동으로 붙이는지, 토큰이 로그로 새지 않게 막는 법, 그리고 그 줄이 stdout 을 떠나 대시보드에 닿기까지를 잇습니다. 끝나면 “로그를 왜 그렇게 찍었냐”는 질문에 설계로 답할 수 있게 됩니다.

LOG 01

console.* 의 진실 — 어디로 나가고, 왜 부족한가

console.log 는 로거가 아닙니다. 파일 서술자에 문자열을 쓰는 편의 함수입니다. 그 사실 하나만 알아도 “왜 운영에서는 다른 걸 쓰나”가 절반은 설명됩니다.

console 은 fd 에 문자열을 쓰는 편의 함수입니다 — 목적지에 따라 동기 쓰기가 됩니다.

console 이 실제로 하는 일

// Node 의 console 은 stdout/stderr 를 감싼 얇은 껍데기입니다.
// 대략 이런 모양이라고 생각하면 정확합니다.
const { format } = require('node:util');

console.log   = (...a) => process.stdout.write(format(...a) + '\n');  // fd 1
console.error = (...a) => process.stderr.write(format(...a) + '\n');  // fd 2
console.warn  = console.error;   // ★ warn 도 stderr 입니다 (자주 놓칩니다)
console.info  = console.log;
console.debug = console.log;     // ★ 이름만 debug — 끄는 스위치가 없습니다

// 객체를 넘기면 util.inspect 가 돕니다 — 순환 참조를 따라가고,
// getter 를 호출하고, 색 코드를 붙이고, 깊이 2까지 펼칩니다.
console.log({ user: { id: 1, roles: ['admin'] } });
// → { user: { id: 1, roles: [ 'admin' ] } }   ← JSON 이 아닙니다. 파싱 못 합니다
가장 자주 물리는 것 — console.warn 과 console.error 는 stderr 로 갑니다. node app.js > app.log 로 리다이렉트하면 경고와 에러만 화면에 남고 파일에는 안 들어갑니다. 둘 다 모으려면 node app.js > app.log 2>&1 이라고 써야 합니다.

쓰기가 동기인가 비동기인가 — 목적지가 정합니다

목적지POSIX(리눅스·맥)Windows
파일동기동기
TTY(터미널)동기비동기
파이프 · 소켓리눅스 동기 / 맥 비동기동기
왜 이게 문제인가 — 동기라는 말은 write(2) 시스템 콜이 끝날 때까지 이벤트 루프가 멈춘다는 뜻입니다. 초당 수천 줄을 찍는 서버에서 console.log 는 조용한 성능 사고가 됩니다. node app.js > app.log 처럼 파일로 돌려 놓으면 더 나빠집니다.
확인해 보기 — node -e "console.log(process.stdout.isTTY)" 를 그냥 실행할 때와 | cat 을 붙였을 때 각각 돌려 보세요. 같은 코드가 환경에 따라 다르게 동작합니다.

한 단계 더 — 브라우저의 console 은 또 다릅니다 🟡 중급

브라우저에서 벌어지는 세 가지

// ① 객체는 "지연 평가"됩니다 — 펼칠 때의 값이 보입니다
const cart = { items: [] };
console.log(cart);          // devtools 에서 펼치면 items 가 3개일 수 있습니다
cart.items.push(1, 2, 3);   // 로그를 찍은 뒤에 바뀐 것인데도

// ② 콘솔에 남긴 객체는 GC 대상에서 빠집니다 (devtools 가 참조를 잡습니다)
//    루프에서 큰 객체를 찍으면 탭 메모리가 계속 오릅니다
for (const row of hugeRows) console.log(row);   // ← 개발 중에도 위험

// ③ 스냅샷이 필요하면 그 자리에서 굳힙니다
console.log(structuredClone(cart));             // 또는 JSON.parse(JSON.stringify(x))
“로그를 찍었는데 값이 이상해요” 의 90%가 ①입니다. 브라우저 콘솔은 찍는 순간의 문자열이 아니라 객체 참조를 보관합니다. Node 는 util.inspect 가 그 자리에서 문자열로 굳히므로 이 문제가 없습니다.

배포물에서 console 을 지우는 세 가지 방법

// ① 번들러가 통째로 들어내기 — 가장 확실합니다
// vite.config.ts
export default {
  esbuild: { drop: ['console', 'debugger'] },        // 프로덕션 빌드에서 제거
};

// ② terser 로 특정 함수만 남기기
// { compress: { pure_funcs: ['console.log', 'console.debug'] } }
//   → console.error 는 남기고 log/debug 만 지웁니다

// ③ 애초에 못 쓰게 막기 — eslint
// eslint.config.js
export default [{
  rules: { 'no-console': ['error', { allow: ['error', 'warn'] }] },
}];
지우는 게 늘 정답은 아닙니다 — 브라우저에서 Sentry 를 쓰면 console.* 호출이 breadcrumb(사고 직전 발자국) 으로 자동 수집됩니다(lg11). 그때는 지우지 말고 내용만 안전하게 만드는 편이 낫습니다.

실무에선 이렇게 — console 을 그냥 써도 되는 자리 🔴 실무

console 로 충분한 곳
  • 일회성 스크립트 — 마이그레이션, 데이터 보정
  • CLI 도구의 사용자 출력 — 사람에게 보여 주는 글 (이건 로그가 아니라 UI 입니다)
  • 테스트 중 임시 확인 — 커밋 전에 지우면 됩니다
  • 부팅 직전 한 줄 — 로거를 만들기 전에 죽었을 때의 최후 수단
console 이면 사고가 나는 곳
  • 요청 처리 경로 — 초당 수천 번, 동기 쓰기
  • 레벨을 끄고 싶은 곳 — console.debug 는 끌 방법이 없습니다
  • 검색해야 하는 곳 — 구조가 없으니 grep 밖에 못 씁니다
  • 여러 요청이 섞이는 곳 — 어느 줄이 어느 요청인지 알 수 없습니다
정리하면 기준은 하나입니다 — “이 줄을 나중에 누가 검색할 것인가?” 사람이 지금 눈으로 볼 뿐이면 console 로 충분하고, 나중에 누군가가 조건을 걸어 찾아야 한다면 그건 로거의 일입니다.
정리 — console 은 fd 1·2 에 문자열을 쓰는 편의 함수입니다. 목적지가 파일이면 동기 쓰기라 이벤트 루프가 멈추고, 레벨·시각·구조·요청 ID 가 없어 검색할 수 없는 글이 남습니다. 운영 로그는 처음부터 레코드로 만들어야 합니다.
LOG 02

라이브러리 지형도 — 여덟 개를 한 장에 놓고 고릅니다

JS 로깅 라이브러리는 “빠른 JSON 계열” 과 “예쁜 콘솔 계열” 로 갈립니다. 둘은 목적이 다르고, 섞어 쓰면 둘 다 손해입니다. 무엇이 어느 쪽인지부터 봅시다.

히트맵 — 빈 칸이 결론입니다. debug 의 “구조 0”, bunyan·signale 의 “유지보수 0”.

빠른 JSON 계열 — 서버가 쓰는 것

이름한 줄 요약고르는 순간
pinoJSON 을 문자열로 바로 만들고 워커 스레드로 내보냄. 사실상 표준Node 백엔드라면 기본값
winston포맷·트랜스포트 조립식. 느리지만 붙일 곳이 많음이상한 곳으로 직접 보내야 할 때
bunyan구조적 JSON 로깅의 원조. 지금은 사실상 멈춘 프로젝트신규 채택 금지 · 레거시만
roarr“항상 찍고 CLI 에서 거른다”. 라이브러리 안에서 쓰기 좋음내가 만든 패키지에 로그를 넣을 때
서버라면 고민 순서는 짧습니다 — Fastify 면 이미 pino, Express·Nest 면 pino 를 붙이고, winston 은 “pino 로 못 하는 게 있을 때”만 꺼냅니다. bunyan 은 옛 코드에서 만나면 pino 로 옮길 대상입니다(필드 이름이 거의 같습니다).

예쁜 콘솔 계열 — 사람이 읽는 것

이름한 줄 요약고르는 순간
debugDEBUG=app:* 네임스페이스 스위치. 로거가 아니라 추적 스위치라이브러리 내부 추적
consolaUnJS·Nuxt 계열. 상자·스피너·프롬프트까지CLI 도구 · 빌드 스크립트
tslogTypeScript 우선. 스택 추적과 코드 프레임이 예쁨작은 TS 서비스 · 학습용
signale예쁜 스코프 출력의 원조. 사실상 멈춤consola 로 대체하세요
섞어 쓰면 둘 다 손해입니다 — 예쁜 계열은 색 코드와 정렬이 목적이라 그대로 운영에 나가면 파싱이 안 되는 줄이 됩니다. 반대로 pino 의 JSON 을 개발 중에 눈으로 읽으면 괴롭습니다 — 그건 pino-pretty 를 파이프로 붙여 해결합니다(lg03).
