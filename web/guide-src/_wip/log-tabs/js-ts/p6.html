LOG 11

브라우저 — 로그 파일이 없는 곳에서는 사건을 보냅니다

브라우저에는 stdout 도 파일도 없습니다. 사용자 기기에서 일어난 일은 네트워크로 보내야만 우리에게 옵니다. 그래서 브라우저 로깅은 “모든 줄을 남기기”가 아니라 “사건이 났을 때 그 앞뒤를 함께 보내기”입니다.

타임라인 — 예외 하나가 아니라 그 앞의 발자국까지 함께 갑니다. 구름은 우리 프로세스 밖입니다.

Sentry 붙이기 — 다섯 줄이면 시작됩니다

npm i @sentry/browser        # React 면 @sentry/react, Next.js 면 @sentry/nextjs
// src/monitoring.ts — 앱의 가장 첫 import
import * as Sentry from '@sentry/browser';

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: `web@${import.meta.env.VITE_GIT_SHA}`,   // ★ 소스맵과 짝을 맞추는 열쇠
  environment: import.meta.env.MODE,

  sendDefaultPii: false,          // IP · 쿠키를 자동으로 붙이지 않습니다 (lg10)
  tracesSampleRate: 0.1,          // 성능 추적은 10% 만 — 비용
  replaysOnErrorSampleRate: 1.0,  // 에러가 난 세션만 화면 녹화
  replaysSessionSampleRate: 0,

  integrations: [
    Sentry.browserTracingIntegration(),
    Sentry.replayIntegration({ maskAllText: true, blockAllMedia: true }),
  ],
  tracePropagationTargets: ['https://api.example.com'],   // 이 호출에만 sentry-trace 헤더

  // 보내기 직전 마지막 검문 — 여기서 걸러진 건 네트워크를 타지 않습니다
  beforeSend(event) {
    if (event.request?.url?.includes('token=')) event.request.url = '[scrubbed]';
    return event;
  },
});

// 로그인 뒤 — 내부 ID 만. 이메일은 넣지 않습니다
Sentry.setUser({ id: user.id });
Sentry.setTag('tenant', tenantId);

// 잡은 예외를 문맥과 함께
try { await pay(order); }
catch (err) {
  Sentry.captureException(err, { tags: { flow: 'checkout' }, extra: { orderId: order.id } });
  throw err;
}
발자국은 공짜로 쌓입니다 — 클릭 · 라우팅 · fetch · console.* 호출이 SDK 안의 링 버퍼에 들어갑니다. 예외가 날 때만 마지막 100개가 딸려 갑니다. 그래서 lg01 에서 “Sentry 를 쓰면 console 을 지우지 말라”고 한 것입니다 — 그게 발자국이 됩니다.

자체 수집 — 의존성 없는 얇은 래퍼

// src/blog.ts — 브라우저용 로거. 모아서, 떠날 때, 비콘으로
type Level = 'info' | 'warn' | 'error';
const queue: object[] = [];
const ctx = { sessionId: crypto.randomUUID(), release: __GIT_SHA__ };

export function blog(level: Level, fields: Record<string, unknown>, msg: string) {
  queue.push({ level, time: Date.now(), msg, ...ctx, ...fields });
  if (import.meta.env.DEV) console[level === 'info' ? 'log' : level](msg, fields);
  if (queue.length >= 20 || level === 'error') flush();
}

function flush() {
  if (!queue.length) return;
  const body = JSON.stringify(queue.splice(0));
  // ★ 탭이 닫히는 중에도 살아남는 두 가지 방법
  if (!navigator.sendBeacon('/api/client-logs', new Blob([body], { type: 'application/json' }))) {
    fetch('/api/client-logs', { method: 'POST', body, keepalive: true }).catch(() => {});
  }
}

// 페이지를 떠날 때 남은 것을 밀어냅니다 — unload 는 모바일에서 안 옵니다
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});

// 잡히지 않은 오류 두 종류
window.addEventListener('error', (e) =>
  blog('error', { message: e.message, src: e.filename, line: e.lineno }, 'uncaught'));
window.addEventListener('unhandledrejection', (e) =>
  blog('error', { reason: String(e.reason) }, 'unhandled rejection'));
서버 쪽 /api/client-logs 는 신뢰하면 안 되는 입력입니다 — 누구나 아무 JSON 이나 보낼 수 있습니다. 크기 제한 · 속도 제한 · 스키마 검증을 걸고, 받은 값은 필드로 골라서 서버 로거에 넘기세요. 클라이언트가 보낸 문자열을 그대로 msg 에 넣으면 로그 위조(log injection) 가 됩니다.

한 단계 더 — 소스맵과 “Script error.” 🟡 중급

축소된 코드의 스택을 원래 줄로

실무에선 이렇게 — 무엇을 쓰나 · 서버와 어떻게 잇나 🔴 실무

도구주는 것고르는 순간
console 만개발자 화면에서만 보임. 사용자 기기의 일은 아무것도 모름개발 중 · 내부 도구
자체 비콘 래퍼업무 사건(checkout.step)을 우리 로그 파이프라인으로제품 분석과 합치고 싶을 때 · 데이터 반출이 안 될 때
Sentry예외 + 발자국 + 소스맵 복원 + 세션 리플레이. 사실상 표준SPA 라면 기본값
RUM (Datadog RUM · Grafana Faro)성능 지표(LCP · 지연) + 오류 + 세션. 서버 APM 과 한 화면이미 그 벤더의 서버 APM 을 쓸 때
OpenTelemetry 브라우저추적은 쓸 만하고, 로그 API 는 아직 자리 잡는 중벤더 중립이 최우선일 때 — 문서를 먼저 확인
서버 로그와 잇는 한 줄 — Sentry SDK 가 tracePropagationTargets 에 맞는 요청에 sentry-trace 헤더를 붙입니다. 서버 미들웨어에서 그 값을 읽어 lg07 의 문맥에 traceId 로 넣으면, 브라우저 오류 화면에서 클릭 한 번으로 서버 로그가 열립니다. 반대로 응답 헤더에 x-request-id 를 돌려주면(lg06) 사용자 오류 화면에 그 값을 보여 줄 수 있습니다.
브라우저에서 절대 하지 말 것 — ① 모든 클릭을 서버로 보내기(그건 로깅이 아니라 추적이고 동의가 필요합니다) ② Sentry.setUser 에 이메일 넣기 ③ 리플레이에서 maskAllText: false ④ 에러 메시지에 사용자 입력값 넣기. lg10 의 규칙이 브라우저에서는 법적 문제가 됩니다.
정리 — 브라우저에는 로그 파일이 없으니 사건이 났을 때 앞뒤를 함께 보냅니다. Sentry 는 예외 + 발자국 + 소스맵이 핵심이고 release 를 맞춰야 스택이 읽힙니다. 자체 수집은 비콘으로 모아서 보내되 서버는 그 입력을 신뢰하지 않습니다. sentry-trace 헤더 하나가 브라우저와 서버 로그를 잇습니다.
LOG 12

stdout 을 떠나서 — 수집기 · 저장소 · OpenTelemetry

앱이 할 일은 stdout 에 JSON 한 줄까지입니다. 그 줄이 대시보드에 닿기까지 서너 단계가 더 있는데, 전부 앱 바깥의 일입니다. 이 경계를 지키면 로거를 바꿔도, 저장소를 바꿔도 서로 모릅니다.

흐름 — 앱은 저장소를 모릅니다. 원통은 우리가 운영하는 것, 구름은 남이 운영하는 것.

컨테이너에서 앱이 지킬 것 — 파일을 만들지 않습니다

# Dockerfile — 로그 관련 설정은 없습니다. 그게 정답입니다
FROM node:24-alpine
WORKDIR /app
COPY dist ./dist
COPY node_modules ./node_modules
ENV NODE_ENV=production LOG_LEVEL=info
CMD ["node", "dist/main.js"]           # ★ pino-pretty 도, 파일 경로도 없습니다

# 확인 — 컨테이너 밖에서 그대로 보입니다
docker logs -f --since 5m my-api | jq -c 'select(.level=="error")'
kubectl logs deploy/checkout-api --since=10m | jq -c 'select(.reqId=="req_01J8Q")'

# 회전은 런타임이 합니다 — 앱이 winston-daily-rotate-file 을 돌리면 이중 회전이 됩니다 (lg04)
# docker: --log-opt max-size=50m --log-opt max-file=5
# kubelet: containerLogMaxSize / containerLogMaxFiles
12-factor 의 “로그는 이벤트 스트림”이 이 그림입니다 — 앱은 어디에 저장할지 모르고, 모르는 것이 장점입니다. 저장소를 Loki 에서 OpenSearch 로 바꿔도 앱은 재배포하지 않습니다. 반대로 앱이 파일을 직접 쓰기 시작하는 순간, 볼륨 · 권한 · 회전 · 디스크 가득 참이 전부 앱 문제가 됩니다.

에이전트 — Vector 로 JSON 풀어서 Loki 로

# vector.toml — 노드마다 하나 (DaemonSet)
[sources.k8s]
type = "kubernetes_logs"                  # /var/log/containers 를 읽고 pod 메타를 붙입니다

[transforms.parse]
type   = "remap"
inputs = ["k8s"]
source = '''
  parsed, err = parse_json(.message)      # pino 가 쓴 한 줄
  if err == null {
    . = merge(., parsed)                  # level · reqId · msg 가 필드가 됩니다
    del(.message)
  }                                       # JSON 이 아닌 줄(다른 도구)은 그대로 둡니다
  .level = downcase(string!(.level ?? "info"))
'''

[transforms.scrub]                        # lg10 의 셋째 겹 — 앱이 놓친 토큰을 여기서
type   = "remap"
inputs = ["parse"]
source = '''
  .msg = replace(string!(.msg ?? ""), r'eyJ[\w-]+\.[\w-]+\.[\w-]+', "[JWT]")
'''

[sinks.loki]
type     = "loki"
inputs   = ["scrub"]
endpoint = "http://loki:3100"
encoding.codec = "json"
labels.service = "{{ service }}"          # ★ 라벨은 값의 종류가 적은 것만
labels.level   = "{{ level }}"
labels.env     = "{{ env }}"              #   reqId 를 라벨로 두면 Loki 가 죽습니다
Loki 의 라벨은 인덱스 키입니다 — 값의 종류(카디널리티)가 수백을 넘는 필드 (reqId · userId · url)를 라벨로 두면 스트림이 폭발합니다. 그런 값은 본문 JSON 에 두고 | json | reqId="..." 로 거릅니다(lg07). OpenSearch 는 반대로 필드가 전부 색인되니 매핑 폭발을 조심합니다(lg05).

실무에선 이렇게 — 알림과 비용 🔴 실무

로그로 알림 걸기 — 개수가 아니라 비율로

# Grafana 알림 규칙 (Loki · LogQL) — 5분간 error 비율이 2% 를 넘으면
- alert: CheckoutErrorRate
  expr: |
    sum(rate({service="checkout-api"} | json | level="error" [5m]))
      /
    sum(rate({service="checkout-api"} | json | event="http.request" [5m]))
      > 0.02
  for: 10m                       # 10분 지속될 때만 — 순간 튀는 건 무시
  labels: { severity: page }
  annotations:
    summary: "checkout-api error ratio > 2%"
    runbook: "https://wiki/runbooks/checkout-errors"

# 조사할 때 — 어떤 사건이 늘었나 (lg05 의 event 필드가 여기서 빛납니다)
# sum by (event) (count_over_time({service="checkout-api"} | json | level="error" [1h]))
개수 알림은 트래픽이 늘면 울립니다 — 새벽 3시 에러 5건과 점심 에러 5건은 뜻이 다릅니다. 비율로 걸고 for 로 지속 시간을 두세요. 그리고 lg05 의 “400 을 error 로 찍지 않기”가 안 지켜지면 이 알림은 처음부터 소음입니다.

탭을 마치며 — 열두 절을 한 줄로 — console 은 편의 함수(lg01), 서버는 pino(lg02~03), 필드가 검색어(lg05), 요청 ID 는 저장소가 나르고(lg07), 타입으로 잠그고(lg08), 동기 쓰기를 피하고(lg09), 비밀은 애초에 안 담고(lg10), 브라우저는 사건을 보내고(lg11), 앱은 stdout 까지만, 그 뒤는 인프라(lg12). “로그를 왜 그렇게 찍었냐”에 이제 설계로 답할 수 있습니다.
정리 — 앱은 stdout 에 JSON 한 줄까지만 책임집니다. 런타임이 파일로 받고, 에이전트가 풀어서 원통(자체 운영)이나 구름(SaaS)으로 보냅니다. OpenTelemetry 는 우선 traceId 를 로그에 심는 것부터, 알림은 비율로, 비용은 재고 나서 줄입니다.
