LOG 05

구조적 로깅 — 필드 설계가 나중의 검색을 정합니다

로그를 JSON 으로 찍는 이유는 예뻐서가 아닙니다. 필드가 곧 검색어이기 때문입니다. 문장 안에 값을 숨기면 그 값으로는 영원히 검색이 안 됩니다. 무엇을 필드로 뺄지가 전부입니다.

해부도 — 필드가 곧 검색어입니다. 이름을 정하는 회의가 대시보드를 정합니다.

같은 사건을 두 가지로 찍어 보기

// ✗ 문장에 값을 녹인 로그 — 사람만 읽을 수 있습니다
log.info(`user u_8821 paid order 8821 in 37ms`);
//  · "37ms 이상 걸린 결제"를 찾으려면 정규식을 짜야 합니다
//  · 평균 소요 시간을 못 구합니다 (숫자가 아니니까)
//  · 문구를 바꾸는 순간 기존 대시보드가 전부 깨집니다

// ○ 구조적 로그 — 기계가 읽습니다
log.info({ userId: 'u_8821', orderId: 8821, durationMs: 37 }, 'order paid');
//  · durationMs > 37  같은 조건이 그대로 쿼리가 됩니다
//  · msg 는 고정 문구 — 이걸로 사건 종류를 셉니다
//  · 나중에 필드를 더해도 기존 쿼리가 안 깨집니다

// ★ 한 걸음 더 — 사건에 이름(event)을 붙이면 문구가 바뀌어도 안전합니다
log.info({ event: 'order.paid', orderId: 8821, durationMs: 37 }, 'order paid');
//    msg 는 사람용, event 는 기계용. 대시보드는 event 로 겁니다
규칙 하나만 기억하면 됩니다 — “나중에 이 값으로 필터를 걸 것 같다” 싶으면 필드로 뺍니다. 메시지는 변하지 않는 짧은 문구로 두세요. 문구를 바꾸는 건 공짜가 아닙니다.

어느 규약을 따라야 하나 — 대시보드가 정합니다. OpenSearch·Elastic 을 쓰면 ECS(@elastic/ecs-pino-format 한 줄이면 맞춰집니다), Grafana Loki 나 자체 파이프라인이면 pino 기본형으로 충분합니다. 중요한 건 일관성이지 특정 표준이 아닙니다.
절대 하지 말 것 — 같은 뜻을 userId · user_id · uid 로 섞어 쓰기. 수집기에서 서로 다른 필드가 되고, Elasticsearch 라면 매핑 폭발로 색인이 느려집니다. 필드 사전을 저장소에 파일로 두고 리뷰에서 확인하세요.

레벨 설계 — 환경마다 다른 답 🟡 중급

발산 매트릭스 — 가운데가 무채색이라 “켤까 말까”인 칸이 눈에 바로 들어옵니다.

여섯 레벨의 뜻을 팀에서 합의하기

레벨이럴 때누가 보나
fatal프로세스를 더 못 살린다 — 곧 죽는다즉시 호출(페이지)
error이 요청은 실패했고 우리 잘못일 수 있다알림 · 당번
warn지금은 넘어갔지만 곧 error 가 될 신호 (재시도 성공, 폴백)주간 리뷰
info업무상 사건 — 주문 결제됨, 배포 시작됨조사할 때
debug개발자가 흐름을 따라가려는 값버그 잡을 때만
trace한 함수 안의 시시콜콜한 값거의 안 봄
가장 흔한 오용 — 사용자 입력이 틀린 것을 error 로 찍는 것. 400·404 는 정상 동작입니다. 이걸 error 로 두면 알림이 계속 울려 진짜 error 를 아무도 안 보게 됩니다. “내가 고쳐야 할 일인가”가 error 의 기준입니다.

배포 없이 레벨 올리기 · 일부만 자세히 보기

// ① 환경변수 — 가장 기본. 재시작만으로 바뀝니다
const logger = pino({ level: process.env.LOG_LEVEL ?? 'info' });

// ② 신호로 런타임에 바꾸기 — 재시작도 없이
process.on('SIGUSR2', () => {
  logger.level = logger.level === 'debug' ? 'info' : 'debug';
  logger.warn({ level: logger.level }, 'log level toggled');
});
// $ kill -SIGUSR2 <pid>

// ③ 표본만 자세히 — 1% 요청만 debug 로 (비용을 100분의 1로)
const sampled = Math.random() < 0.01;
const reqLog = logger.child(
  { reqId, sampled },
  { level: sampled ? 'debug' : 'info' },      // 자식 로거만 레벨을 올립니다
);

// ④ 특정 사용자·테넌트만 자세히 — 재현 안 되는 버그를 잡을 때
const verbose = DEBUG_USERS.has(userId);
const userLog = logger.child({ userId }, { level: verbose ? 'trace' : 'info' });
③ 이 실무의 답입니다 — “운영에서 debug 를 켜면 비용이 터지고, 끄면 원인을 못 찾는다”는 딜레마는 표본 추출로 풉니다. sampled: true 필드를 함께 남겨 두면 대시보드에서 표본 요청만 골라 보기도 됩니다.

실무에선 이렇게 — 필드 사전을 코드로 두기 🔴 실무

이름을 파일 하나에 모으면 오타가 컴파일 에러가 됩니다

// src/log-fields.ts — 팀의 필드 사전. 리뷰는 이 파일만 보면 됩니다.
export const FIELD = {
  reqId:      'reqId',       // 요청 하나를 잇는 ID (lg07)
  traceId:    'traceId',     // 분산 추적 ID (lg12)
  userId:     'userId',      // 내부 식별자만. 이메일·전화번호 금지 (lg10)
  tenantId:   'tenantId',
  event:      'event',       // 'order.paid' 같은 사건 이름
  durationMs: 'durationMs',  // ★ 단위를 이름에 붙입니다. ms 인지 s 인지 헷갈리지 않게
  statusCode: 'statusCode',
  component:  'component',   // 'db' | 'http' | 'queue'
} as const;

// 사건 이름도 목록으로 — 대시보드가 이 목록 위에 세워집니다
export const EVENT = [
  'order.created', 'order.paid', 'order.cancelled',
  'payment.failed', 'payment.retried',
  'user.login', 'user.login_failed',
] as const;
export type Event = (typeof EVENT)[number];
왜 굳이 파일로 두나 — 로그 필드는 공개 API 와 같습니다. 대시보드·알림 규칙·데이터 분석이 전부 이 이름 위에 세워지므로, 이름을 바꾸는 것은 API 를 바꾸는 것입니다. 코드로 두면 바꿀 때 어디가 깨지는지 컴파일러가 알려 줍니다(lg08).
단위는 이름에 넣으세요 — duration 이 아니라 durationMs, size 가 아니라 sizeBytes. 6개월 뒤 대시보드를 만드는 사람은 여러분이 아닙니다.
정리 — 필드가 곧 검색어입니다. 값은 문장에 녹이지 말고 필드로 빼고, 이름은 팀에서 한 번만 정해 파일로 남깁니다. 레벨은 환경마다 다른 답이 있고, 운영에서 자세히 보고 싶으면 표본 추출로 켭니다.
LOG 06

프레임워크 연동 — 붙이는 자리는 어디나 같습니다

Express · Fastify · NestJS · Next.js — 이름은 달라도 로거를 붙이는 자리는 셋뿐입니다. 요청 진입 · 요청 스코프 로거 · 응답 완료. 프레임워크마다 그 자리의 이름만 다릅니다.

레이어 — 화살표는 한 방향. 요청 스코프 로거는 딱 한 번만 만듭니다.

Express — pino-http 한 줄

npm i pino pino-http
import express from 'express';
import pinoHttp from 'pino-http';
import { randomUUID } from 'node:crypto';
import { logger } from './logger.js';

const app = express();

app.use(pinoHttp({
  logger,

  // ① 요청 ID — 앞단(로드밸런서·게이트웨이)이 준 것을 최대한 이어받습니다
  genReqId: (req, res) => {
    const id = req.headers['x-request-id'] ?? randomUUID();
    res.setHeader('x-request-id', String(id));   // 응답에도 돌려줍니다
    return String(id);
  },

  // ② 상태코드에 따라 레벨을 다르게 — 404 를 error 로 두지 않습니다
  customLogLevel: (req, res, err) => {
    if (err || res.statusCode >= 500) return 'error';
    if (res.statusCode >= 400) return 'warn';
    if (req.url === '/healthz') return 'silent';   // ★ 헬스체크는 버립니다
    return 'info';
  },

  // ③ 남길 것만 남깁니다 (전체 req 를 찍으면 헤더가 통째로 샙니다 — lg10)
  serializers: {
    req: (req) => ({ method: req.method, url: req.url }),
    res: (res) => ({ statusCode: res.statusCode }),
  },
}));

app.get('/orders/:id', (req, res) => {
  req.log.info({ orderId: req.params.id }, 'order fetched');   // ★ req.log
  res.json({ ok: true });
});
morgan 은 접근 로그 전용입니다 — morgan('combined') 이 만드는 건 아파치 형식의 한 줄 텍스트라 JSON 이 아니고, 애플리케이션 로그와 ID 로 이어지지도 않습니다. 옛 프로젝트에서 만나면 pino-http 로 대체하는 게 맞습니다. 굳이 둘 다 쓰면 같은 요청이 두 줄로 남아 비용만 늘어납니다.

Fastify — 이미 들어 있습니다

import Fastify from 'fastify';

const app = Fastify({
  logger: {
    level: process.env.LOG_LEVEL ?? 'info',
    // 개발에서만 예쁘게
    transport: process.env.NODE_ENV !== 'production'
      ? { target: 'pino-pretty' } : undefined,
  },
  genReqId: (req) => String(req.headers['x-request-id'] ?? crypto.randomUUID()),
  disableRequestLogging: false,   // 기본 접근 로그를 끄고 직접 만들 수도 있습니다
});

app.get('/orders/:id', async (req, reply) => {
  req.log.info({ orderId: (req.params as any).id }, 'order fetched');
  //  ↑ 이미 reqId 가 붙은 자식 로거입니다. 설정할 게 없습니다
  return { ok: true };
});

// 앱 전역 로거도 같은 인스턴스입니다
app.log.warn({ port: 3000 }, 'starting');

NestJS — nestjs-pino

// app.module.ts
import { LoggerModule } from 'nestjs-pino';

@Module({
  imports: [LoggerModule.forRoot({
    pinoHttp: {
      level: process.env.LOG_LEVEL ?? 'info',
      genReqId: (req) => String(req.headers['x-request-id'] ?? randomUUID()),
      autoLogging: { ignore: (req) => req.url === '/healthz' },
    },
  })],
})
export class AppModule {}

// main.ts — Nest 기본 로거를 갈아 끼웁니다
const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useLogger(app.get(Logger));

// 서비스 어디서나 주입해서 씁니다 — reqId 가 자동으로 붙습니다
@Injectable()
export class OrderService {
  constructor(private readonly log: PinoLogger) {}
  pay(id: string) { this.log.info({ orderId: id }, 'order paid'); }
}
Nest 의 기본 Logger 는 개발용입니다 — 색이 들어간 텍스트를 찍습니다. bufferLogs: true 로 부팅 로그까지 pino 로 넘기는 것이 요령입니다. 이걸 빼면 시작 직후의 로그만 형식이 다릅니다.

엣지에서 쓸 수 있는 최소 로거

// src/edge-logger.ts — 의존성 0. 어디서나 돕니다
type Level = 'debug' | 'info' | 'warn' | 'error';
const ORDER: Record<Level, number> = { debug: 20, info: 30, warn: 40, error: 50 };
const MIN = ORDER[(process.env.LOG_LEVEL as Level) ?? 'info'];

export function elog(level: Level, fields: Record<string, unknown>, msg: string) {
  if (ORDER[level] < MIN) return;                      // 레벨 조기 반환
  const line = JSON.stringify({
    level, time: new Date().toISOString(), msg,
    service: 'web', env: process.env.VERCEL_ENV, ...fields,
  });
  // 엣지에는 stdout 이 없습니다 — 플랫폼이 console 을 수집합니다
  (level === 'error' || level === 'warn' ? console.error : console.log)(line);
}

// middleware.ts
export function middleware(req: NextRequest) {
  const reqId = req.headers.get('x-request-id') ?? crypto.randomUUID();
  elog('info', { reqId, path: req.nextUrl.pathname }, 'edge request');

  const res = NextResponse.next();
  res.headers.set('x-request-id', reqId);   // ★ 아래 런타임으로 ID 를 넘겨줍니다
  return res;
}
핵심은 “형식을 맞추는 것”입니다 — 엣지에서도 같은 필드 이름의 JSON 한 줄을 console.log 로 찍으면 수집기 입장에서는 pino 와 구별되지 않습니다. 로거 라이브러리가 아니라 출력 형식이 계약입니다.
정리 — 붙이는 자리는 요청 진입 · 요청 스코프 로거 · 응답 완료 셋뿐입니다. Express 는 pino-http, Fastify 는 내장, Nest 는 nestjs-pino, Next.js 는 런타임부터 확인하고 엣지에서는 형식만 맞춘 console 로 갑니다.
