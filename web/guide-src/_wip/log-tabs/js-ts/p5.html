LOG 09

성능 — 동기 쓰기는 이벤트 루프를 멈춥니다

Node 는 스레드가 하나입니다. 로그 한 줄을 디스크에 다 쓸 때까지 기다리는 동안 그 프로세스의 다른 요청도 전부 기다립니다. 로깅 성능 이야기는 결국 “그 기다림을 어디로 치우나”입니다.

워터폴 — 붉은 구간에서 루프가 멈춥니다. 그동안 같은 프로세스의 다른 요청도 기다립니다.

직접 재기 — 이벤트 루프 지연을 숫자로

// bench-log.ts — 같은 줄 10만 개를 세 방식으로 쓰고 루프 지연을 잽니다
import { monitorEventLoopDelay } from 'node:perf_hooks';
import pino from 'pino';

const N = 100_000;
const line = { orderId: 8821, userId: 'u_8821', durationMs: 37 };

async function run(name: string, logger: pino.Logger) {
  const h = monitorEventLoopDelay({ resolution: 5 });   // 5ms 간격으로 루프 지연 표본
  h.enable();
  const t0 = performance.now();
  for (let i = 0; i < N; i++) logger.info(line, 'order paid');
  const wall = performance.now() - t0;
  await new Promise((r) => setTimeout(r, 50));         // 표본이 잡히도록 잠깐
  h.disable();
  console.error(`${name.padEnd(16)} ${wall.toFixed(0).padStart(5)} ms  ` +
    `p99 루프지연 ${(h.percentile(99) / 1e6).toFixed(1)} ms`);
}

// ① 파일에 동기로 — 가장 느리고, 루프가 가장 오래 멈춥니다
await run('file sync', pino(pino.destination({ dest: './a.log', sync: true })));

// ② 파일에 비동기 버퍼로 — sonic-boom 이 4KB 씩 모아서 씁니다
await run('file async', pino(pino.destination({ dest: './b.log', sync: false, minLength: 4096 })));

// ③ 워커 스레드 트랜스포트 — 메인 스레드는 큐에 넣기만 합니다
await run('transport', pino({ transport: { target: 'pino/file', options: { destination: './c.log' } } }));

// $ npx tsx bench-log.ts        ← 세 줄의 숫자를 여러분 환경에서 보세요
숫자를 여기 적지 않는 이유 — SSD 냐 네트워크 디스크냐, 컨테이너냐 맥북이냐에 따라 자릿수가 바뀝니다. 확실한 것은 순서뿐입니다: 동기 파일 쓰기가 가장 느리고 루프를 가장 오래 세우며, 워커 트랜스포트가 메인 스레드 부담이 가장 적습니다. p99 루프지연 이 요청 지연에 그대로 얹히는 숫자입니다.

쓰기 방식 네 가지 — 무엇을 얻고 무엇을 잃나

방식루프 정지죽을 때 유실언제
sync: true (pino 기본)줄마다 — 목적지가 빠르면 짧게없음stdout 으로 나가는 컨테이너 · 짧은 CLI
sync: false + minLength버퍼가 찰 때만버퍼만큼 (flush 로 막음)파일에 직접 쓰는 VM 서버
transport (워커)거의 없음워커 큐만큼포맷·전송 비용이 클 때(원격·pretty)
console.log → 파일 리다이렉트줄마다 · 길게없음운영에서는 쓰지 않습니다(lg01)
pino 의 기본이 “동기”인데 왜 빠른가 — 목적지가 stdout 파이프이면 write 는 커널 버퍼(리눅스 기본 64KB)에 넣고 바로 돌아옵니다. 진짜 디스크까지 기다리는 건 파일이 목적지일 때입니다. 그래서 컨테이너에서는 기본값 그대로가 제일 단순하고 안전하며, 파일에 직접 쓸 때만 sync: false 를 고민합니다.
유실과 지연은 맞바꾸는 것입니다 — 비동기로 돌리면 빠르지만 kill -9 나 OOM 으로 죽을 때 마지막 몇 줄이 사라집니다. 그 마지막 줄이 대개 “왜 죽었는지”입니다. SIGTERM 에서 flush 하는 코드(lg03)가 그래서 필요합니다.

한 단계 더 — 뒤가 막히면 앞이 멈춥니다 (백프레셔) 🟡 중급

stdout 을 읽는 쪽이 느려지면

# 앱 → 파이프 → 컨테이너 로그 드라이버 → 파일. 이 사슬 어디가 막혀도
# 커널 버퍼(64KB)가 차는 순간 앱의 write 가 블록됩니다.
#   증상: 로그를 많이 찍는 순간 요청 지연이 톱니처럼 뜁니다

# Docker: 드라이버를 논블로킹으로 — 버퍼가 차면 앱을 막는 대신 줄을 버립니다
docker run --log-driver json-file \
  --log-opt mode=non-blocking --log-opt max-buffer-size=4m \
  --log-opt max-size=50m --log-opt max-file=5 my-api

# Kubernetes 는 kubelet 이 파일로 받습니다 — 회전은 kubelet 설정으로
#   containerLogMaxSize: 50Mi
#   containerLogMaxFiles: 5

# 확인: 동기 I/O 가 어디서 일어나는지 스택을 찍어 줍니다 (첫 tick 이후만)
node --trace-sync-io dist/main.js 2>&1 | head -n 40
mode=non-blocking 은 “유실을 택한다”는 선언입니다. “앱이 느려지느니 로그 몇 줄을 버리겠다”가 맞는 서비스가 대부분이지만, 감사 로그·결제 기록처럼 한 줄도 잃으면 안 되는 것은 로그가 아니라 DB 나 큐에 써야 합니다. 로그 파이프라인은 최선 노력(best-effort) 전달입니다.

앱 안에서 버퍼를 다루기 — sonic-boom 손잡이

import pino from 'pino';

const dest = pino.destination({
  dest: '/var/log/app/app.log',
  sync: false,
  minLength: 4096,      // 이만큼 모이면 씁니다 (그 전엔 메모리)
  maxLength: 16_777_216, // 16MB 넘게 쌓이면 새 줄을 버리고 'drop' 을 냅니다
  mkdir: true,
});

// ★ 버려지는 순간을 알아야 합니다 — 조용히 사라지면 나중에 아무도 모릅니다
let dropped = 0;
dest.on('drop', () => { dropped++; });
setInterval(() => {
  if (dropped) { logger.warn({ dropped }, 'log lines dropped'); dropped = 0; }
}, 10_000).unref();

const logger = pino(dest);

// 주기적으로 밀어내기 — 트래픽이 적을 때 마지막 줄이 버퍼에 갇히지 않게
setInterval(() => logger.flush(), 1_000).unref();
minLength 는 지연과 맞바꾸는 값입니다 — 4KB 면 초당 수십 줄짜리 서비스에서 마지막 줄이 몇 초 늦게 나타날 수 있습니다. 그래서 flush 타이머를 같이 둡니다. unref() 를 붙여야 이 타이머 때문에 프로세스가 안 끝나는 일이 없습니다.

실무에선 이렇게 — 핫 패스에서 로그를 다루는 규칙 🔴 실무

초당 만 번 도는 함수 안이라면

// ① 인자를 만들기 전에 레벨을 봅니다 — 꺼진 레벨이면 객체도 안 만듭니다
if (logger.isLevelEnabled('debug')) {
  logger.debug({ rows: rows.length, sample: rows.slice(0, 3) }, 'batch loaded');
}

// ② 루프 안에서는 세지 말고 모읍니다 — 만 줄 대신 한 줄
let retried = 0;
for (const job of jobs) {
  try { await run(job); }
  catch { retried++; }          // ✗ 여기서 logger.warn 을 찍으면 만 줄이 됩니다
}
if (retried) logger.warn({ retried, total: jobs.length }, 'jobs retried');

// ③ 큰 객체는 통째로 넘기지 않습니다 — 직렬화 비용이 곧 루프 정지 시간
logger.info({ orderId: order.id, items: order.items.length }, 'order');   // ○
logger.info({ order }, 'order');                                          // ✗ 200KB 짜리 JSON

// ④ 요청당 접근 로그는 한 줄 — 시작·끝 두 줄이면 저장 비용이 두 배
//    pino-http 의 autoLogging 이 이미 "끝날 때 한 줄" 입니다 (lg06)

// ⑤ 자주 찍는 줄은 자식 로거로 고정 필드를 미리 굳힙니다 (lg03)
const wl = logger.child({ component: 'worker', queue: 'email' });
“로깅이 병목인가”를 확인하는 가장 빠른 방법 — LOG_LEVEL=silent 로 한 번 돌려서 처리량이 얼마나 변하는지 봅니다. 10% 미만이면 로깅은 범인이 아닙니다. 로거를 바꾸기 전에 이 실험이 먼저입니다 — 실제로 원인은 대개 ③ 의 큰 객체 하나입니다.
워커 트랜스포트가 공짜는 아닙니다 — 메인 스레드에서 워커로 줄을 넘기려면 문자열을 복사해야 하고, 워커가 처리 못 하면 큐가 메모리에 쌓입니다. 운영에서 stdout 이 목적지라면 트랜스포트 없이 기본값이 가장 가볍습니다. 트랜스포트는 원격 전송·pretty 처럼 비싼 일이 있을 때만 값어치가 있습니다.
정리 — 로그 쓰기가 동기이면 그 시간만큼 이벤트 루프가 멈추고 다른 요청도 기다립니다. stdout 파이프는 커널 버퍼 덕에 빠르고, 파일이 목적지일 때 sync: false 나 워커를 고민합니다. 비동기는 유실과 맞바꾸는 것이니 flush 와 drop 을 챙기고, 핫 패스에서는 레벨 확인 · 모아서 찍기 · 큰 객체 금지 셋을 지킵니다.
LOG 10

민감정보 — redact 는 마지막 그물이 아니라 두 번째 그물입니다

로그로 새는 토큰은 수집기 · 백업 · 대시보드 캐시로 자동 복제됩니다. 지우기가 사실상 불가능합니다. 그래서 “새면 지운다”가 아니라 “애초에 안 담기게” 설계하고, redact 는 그 다음 겹으로 둡니다.

동심원 — 바깥 그물일수록 구멍이 큽니다. 안쪽 두 겹이 실제로 일하는 겹입니다.

pino redact — 경로로 가리기

import pino from 'pino';

export const logger = pino({
  redact: {
    paths: [
      // 요청 객체를 통째로 찍을 때 새는 자리 (pino-http 의 req 직렬화기)
      'req.headers.authorization',
      'req.headers.cookie',
      'req.headers["x-api-key"]',        // 하이픈이 든 키는 대괄호로

      // 응답 · 바깥 호출 에러 — axios 에러는 config.headers 를 들고 옵니다
      'err.config.headers.Authorization',
      'err.response.data.token',

      // 우리 도메인 객체
      'user.email', 'user.phone',
      'body.password', 'body.card.number', 'body.card.cvc',

      // 와일드카드 — * 는 "한 단계" 만 뜻합니다
      '*.password',                       // 최상위 아무 키 아래의 password
      'orders[*].customer.email',         // 배열 요소마다
    ],
    censor: '[REDACTED]',                 // 기본값. remove: true 면 키째 지웁니다
  },
});

logger.info({ user: { id: 'u_1', email: 'a@b.c' }, body: { password: 'x' } }, 'signup');
// {"user":{"id":"u_1","email":"[REDACTED]"},"body":{"password":"[REDACTED]"},...}
redact 는 “객체의 키”만 봅니다 — logger.info(`token=${t}`) 처럼 문자열 안에 녹인 값은 못 가립니다. 그리고 경로는 정확한 깊이여야 합니다: '*.password' 는 body.user.password 를 못 잡습니다(두 단계). 키 이름이 바뀌거나 자리가 바뀌면 조용히 새기 시작합니다 — 이게 “두 번째 겹”인 이유입니다.

실제로 새는 경로 여섯 가지와 막는 법

이렇게 찍으면무엇이 새나대신
log.info({ req })Authorization · Cookie 헤더 전부직렬화기로 method·url 만(lg06)
log.error({ err }) (axios · fetch 래퍼)err.config.headers 의 토큰 · 요청 본문redact 경로 + 우리 에러로 감싸기
log.info({ user })이메일 · 전화 · 주소 · 해시 안 된 값{ userId: user.id } 만
log.info({ url: req.originalUrl })?token= · ?code= 쿼리 문자열req.path 만, 쿼리는 키 이름만
log.debug({ sql, params })바인딩 파라미터 안의 개인정보sql 과 params.length
log.info(process.env) · 설정 덤프DB 비밀번호 · API 키 통째로키 이름 목록만, 값은 절대
여섯 줄의 공통점 — 전부 “객체를 통째로 넘긴 것”입니다. 필드로 골라 담는 습관(lg05) 하나가 여섯 사고를 동시에 막습니다. redact 목록이 길어진다면 그건 통째로 넘기는 곳이 많다는 신호입니다.
스택 트레이스도 봅니다 — 에러 메시지에 값을 넣는 습관 (new Error(`login failed for ${email}`))이 있으면 err.message 로 샙니다. 메시지는 고정 문구, 값은 에러 객체의 필드(err.userId)에 두고 그 필드를 redact 합니다.

한 단계 더 — winston 과 “값의 모양”으로 가리기 🟡 중급

winston 은 format 한 단계로

import winston from 'winston';
const { combine, timestamp, json, format } = winston.format;

const SECRET_KEYS = new Set(['password', 'authorization', 'cookie', 'token', 'cvc']);

// 키 이름으로 재귀 마스킹 — 깊이와 상관없이 잡습니다 (대신 느립니다)
function mask(v: unknown, depth = 0): unknown {
  if (depth > 6 || v === null || typeof v !== 'object') return v;
  if (Array.isArray(v)) return v.map((x) => mask(x, depth + 1));
  const out: Record<string, unknown> = {};
  for (const [k, val] of Object.entries(v as Record<string, unknown>)) {
    out[k] = SECRET_KEYS.has(k.toLowerCase()) ? '[REDACTED]' : mask(val, depth + 1);
  }
  return out;
}

const redact = format((info) => mask(info) as winston.Logform.TransformableInfo);

export const logger = winston.createLogger({
  format: combine(redact(), timestamp(), json()),   // ★ redact 가 json() 앞
  transports: [new winston.transports.Console()],
});
키 이름 기반의 값과 값어치 — 깊이를 몰라도 잡는 대신 모든 줄의 모든 키를 순회합니다. pino 의 redact 는 경로를 미리 컴파일해 두므로 훨씬 쌉니다. winston 을 쓴다면 이 비용이 lg04 의 “단계마다 객체” 위에 하나 더 얹히는 셈입니다.

모양으로 잡기 — JWT · 카드번호 · 이메일

// 키 이름을 모를 때의 마지막 수단 — 값의 "모양"으로 찾습니다
const PATTERNS: Array<[RegExp, string]> = [
  [/eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}/g, '[JWT]'],
  [/\b(?:\d[ -]?){13,19}\b/g, '[CARD]'],                       // 카드번호 후보
  [/[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}/gi, '[EMAIL]'],
  [/Bearer\s+[A-Za-z0-9._~+/-]+=*/g, 'Bearer [REDACTED]'],
];

export function scrub(s: string): string {
  let out = s;
  for (const [re, rep] of PATTERNS) out = out.replace(re, rep);
  return out;
}

// pino 에서는 msg 와 문자열 값에만 적용 — 모든 줄에 정규식 넷을 돌리는 비용을 감수하는 것
const logger = pino({
  hooks: {
    logMethod(args, method) {
      const last = args.length - 1;
      if (typeof args[last] === 'string') args[last] = scrub(args[last]);
      return method.apply(this, args);
    },
  },
});
정규식은 어림짐작입니다 — 주문번호 16자리가 [CARD] 로 바뀌고, JWT 가 아닌 base64 도 잡힙니다. 동기 정규식 넷이 모든 줄에 돌면 lg09 의 붉은 구간이 늘어납니다. 이 그물은 수집기 쪽(Vector · Fluent Bit)에 두는 편이 앱에 부담이 없습니다(lg12).

# ⑤ 코드 고치기 — redact 경로 추가가 아니라 "통째로 넘긴 곳" 을 필드로 바꿉니다
④ 가 사람들이 가장 자주 잊는 단계입니다 — 에러 알림이 Slack 으로 갔다면 로그 본문이 Slack 메시지 안에 있습니다. 백업이 S3 로 갔다면 버전 관리된 객체 안에 있습니다. 그래서 “지우기”는 늘 불완전하고, ② 의 무효화가 실제 대응입니다.
미리 해 두면 그날이 훨씬 짧아지는 것 — ① 로그 보관 기간을 필요한 만큼만(lg12) ② 브랜드 타입으로 비밀 값이 로그 함수에 못 들어가게(lg08) ③ CI 에서 eyJ · Bearer 같은 패턴을 테스트 로그 출력에서 검사하는 한 줄. 셋 다 반나절이면 됩니다.
정리 — 로그는 여러 곳으로 자동 복제되어 지우기가 거의 불가능합니다. 첫째 겹은 필드로 골라 담기, 둘째 겹이 redact(경로 기반 · 문자열 안은 못 가림), 셋째가 수집기 정규식, 넷째가 보관·권한입니다. 이미 샜다면 지우기보다 무효화가 먼저입니다.
