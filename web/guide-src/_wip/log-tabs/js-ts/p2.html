LOG 03

pino 실전 — 왜 빠르고, 무엇을 워커에게 넘기나

pino 가 빠른 이유는 마법이 아니라 안 하는 일이 많아서입니다. 메인 스레드에서는 문자열을 만들어 버퍼에 넣는 것까지만 하고, 나머지는 전부 워커 스레드로 넘깁니다.

스윔레인 — 줄을 넘어가는 화살표가 곧 스레드가 바뀌는 지점입니다.

5분 시작 — 이 설정이 대부분의 정답입니다

npm i pino
npm i -D pino-pretty          # ★ 개발 의존성입니다. 운영 번들에 넣지 마세요
// src/logger.ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',

  // ① 레벨을 숫자(30) 대신 문자열("info")로 — 수집기 쿼리가 훨씬 편합니다
  formatters: {
    level: (label) => ({ level: label }),
  },

  // ② 시각을 ISO 문자열로. 기본은 epoch 밀리초(빠르지만 사람이 못 읽습니다)
  timestamp: pino.stdTimeFunctions.isoTime,

  // ③ 모든 줄에 붙는 고정 필드 — 어느 서비스의 어느 배포인지
  base: {
    service: 'checkout-api',
    env: process.env.NODE_ENV,
    version: process.env.GIT_SHA?.slice(0, 7),
  },

  // ④ 지울 것은 처음부터 지웁니다 (lg10 에서 자세히)
  redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'],
});

logger.info({ orderId: 8821, ms: 37 }, 'order paid');
// {"level":"info","time":"2026-08-14T09:12:03.421Z","service":"checkout-api",
//  "env":"production","orderId":8821,"ms":37,"msg":"order paid"}
인자 순서를 외우세요 — logger.info(객체, 메시지) 입니다. 객체가 먼저입니다. logger.info('주문 ' + id) 처럼 문자열을 조립하면 검색할 수 있는 필드가 사라집니다. 메시지는 고정 문구로 두고 값은 객체에 넣으세요.

왜 빠른가 — 안 하는 일 다섯 가지

보통의 로거pino
util.inspect 로 예쁘게안 함 — JSON 문자열을 바로 만듭니다
중간 객체를 여러 번 변환안 함 — 한 번에 문자열로 이어 붙입니다
매 호출마다 레벨 비교레벨별 함수를 미리 만들어 둡니다. 꺼진 레벨은 빈 함수
고정 필드를 매번 직렬화자식 로거의 고정 필드는 한 번만 문자열로 굳혀 둡니다
포맷·전송을 그 자리에서워커 스레드로 넘깁니다(pino.transport)
핵심은 “문자열 조립”입니다 — pino 가 만드는 건 처음부터 끝까지 한 줄짜리 문자열입니다. 중간에 자바스크립트 객체를 만들지 않으니 GC 가 할 일도 없습니다. 이게 벤치마크에서 자릿수 차이를 만드는 부분입니다.
단, 인자는 여전히 평가됩니다 — logger.debug(`무거운 ${expensive()}`) 는 debug 가 꺼져 있어도 expensive() 가 실행됩니다. 템플릿 문자열 대신 logger.debug({ data }, '...') 로 넘기거나 if (logger.isLevelEnabled('debug')) 로 감싸세요.

자식 로거 — 문맥을 한 번만 붙이는 법 🟡 중급

logger.child() — pino 를 쓰는 진짜 이유

// 요청마다 자식 로거를 하나 만들어 두면
// 그 아래 모든 줄에 reqId 가 자동으로 붙습니다.
const reqLog = logger.child({ reqId: 'req_01J8Q', userId: 'u_8821' });

reqLog.info('handler start');
reqLog.debug({ sql: 'select ...' }, 'db query');
reqLog.info({ ms: 37 }, 'handler done');
// 세 줄 모두 reqId · userId 를 갖습니다

// 자식의 자식도 됩니다 — 계층이 쌓입니다
const dbLog = reqLog.child({ component: 'db', pool: 'primary' });

// ★ 자식 로거는 "만드는 순간" 고정 필드를 문자열로 굳혀 둡니다.
//    그래서 줄마다 다시 직렬화하지 않습니다 — 거의 공짜입니다.
//    반대로 값이 매 줄 달라지는 것은 child 가 아니라 인자로 넘기세요.
reqLog.info({ ms: Date.now() - t0 }, 'done');   // ○ 인자
logger.child({ ms: ... });                       // ✗ 매번 child 를 만들면 낭비
자식 로거를 어떻게 함수 안까지 전달하나 — 인자로 계속 넘기는 건 금방 지칩니다. AsyncLocalStorage 로 “지금 처리 중인 요청”을 들고 다니는 방법을 lg07 에서 통째로 다룹니다. 실무에서 가장 많이 쓰는 패턴입니다.

에러를 제대로 남기기 — err 라는 이름

try {
  await pay(order);
} catch (err) {
  // ★ 키 이름을 err 로 두면 pino 의 표준 직렬화기가 붙습니다
  //   → type · message · stack · code 를 펼쳐 줍니다
  reqLog.error({ err, orderId: order.id }, 'payment failed');
}

// ✗ 이렇게 하면 대부분 "{}" 만 남습니다
//   Error 는 열거 가능한 속성이 없어서 JSON.stringify 가 비웁니다
reqLog.error({ error: err });          // 키 이름이 err 가 아님
reqLog.error(JSON.stringify(err));     // → "{}"
reqLog.error(err.message);             // 스택이 사라짐

// 원인 사슬(cause)까지 남기려면
throw new Error('checkout failed', { cause: err });   // Node 16.9+
// pino 는 err.cause 도 따라 내려가며 직렬화합니다
실무에서 가장 많이 보는 로그 사고가 “에러를 찍었는데 스택이 없다”입니다. 원인은 거의 항상 위 세 가지 중 하나입니다. { err } 라는 키 이름 하나만 지켜도 절반은 해결됩니다.

트랜스포트 — 개발과 운영을 갈라 놓기 🔴 실무

개발: 파이프로 예쁘게, 운영: 그냥 stdout

# ★ 권장 — 별도 프로세스로 파이프. 앱은 JSON 만 뱉습니다
node dist/app.js | npx pino-pretty

# package.json
# "scripts": {
#   "dev":   "tsx watch src/main.ts | pino-pretty --colorize --translateTime SYS:HH:MM:ss",
#   "start": "node dist/main.js"          ← 운영은 아무것도 붙이지 않습니다
# }

# 운영에서 굳이 파일이 필요하면 (컨테이너가 아닐 때만)
node dist/app.js >> /var/log/app/app.log 2>&1
// 앱 안에서 붙여야 한다면 transport 로 — 워커 스레드에서 돕니다
const logger = pino({
  transport: process.env.NODE_ENV === 'production'
    ? undefined                                  // 운영: stdout 그대로가 가장 빠릅니다
    : { target: 'pino-pretty', options: { colorize: true } },
});

// 여러 목적지로 동시에 (각각 별도 워커)
const multi = pino({
  transport: {
    targets: [
      { target: 'pino/file',   level: 'info',  options: { destination: 1 } },  // 1 = stdout
      { target: 'pino/file',   level: 'error', options: { destination: './error.log' } },
    ],
  },
});
pino-pretty 를 운영에 절대 넣지 마세요 — 색 코드와 정렬을 만드느라 pino 의 장점을 전부 되돌립니다. 게다가 결과물이 JSON 이 아니어서 수집기가 필드를 못 읽습니다. 예쁜 출력은 사람이 보는 개발 화면에서만.

비동기 버퍼와 “죽을 때 마지막 줄”

// pino 는 기본적으로 버퍼에 모았다가 씁니다(sonic-boom).
// 빠른 대신, 프로세스가 갑자기 죽으면 버퍼가 날아갑니다.

import pino from 'pino';
const dest = pino.destination({ sync: false });   // 기본값
const logger = pino(dest);

// ★ 종료 직전에 반드시 비웁니다
const flushAndExit = (code: number) => {
  logger.flush();                 // 버퍼를 밀어냄
  dest.on('drain', () => process.exit(code));
};

process.on('SIGTERM', () => flushAndExit(0));     // k8s 가 보내는 신호
process.on('SIGINT',  () => flushAndExit(0));

// 잡히지 않은 예외 — pino.final 이 안전하게 마지막 줄을 씁니다
process.on('uncaughtException', pino.final(logger, (err, finalLogger) => {
  finalLogger.fatal({ err }, 'uncaught exception');
  process.exit(1);
}));
sync: true 는 언제 쓰나 — 짧은 CLI·배치·람다처럼 “끝나면 바로 죽는” 프로그램입니다. 이때는 버퍼가 날아가는 위험이 손해보다 큽니다. 장시간 도는 서버라면 절대 켜지 마세요 — 매 줄이 동기 write 가 됩니다(lg09).
운영 pino 체크리스트 여섯 줄 — ① level 을 환경변수로 ② base 에 service·env·version ③ redact 로 헤더·비밀번호 ④ err 키로 에러 ⑤ 요청마다 child({ reqId }) ⑥ SIGTERM 에서 flush. 여기까지가 “설정 끝”입니다. 나머지는 수집기가 합니다.
정리 — pino 는 메인 스레드에서 문자열만 만들고 나머지를 워커에 넘겨 빠릅니다. 자식 로거로 문맥을 한 번만 붙이고, 에러는 err 키로 넘기고, pino-pretty 는 개발 파이프로만 씁니다.
LOG 04

winston 실전 — 조립식의 값과 값어치

winston 은 포맷과 목적지를 레고처럼 조립하는 로거입니다. 그 유연함이 장점이자 비용입니다. pino 로 안 되는 것이 있을 때만 꺼내는 편이 좋습니다 — 그 “있을 때”가 언제인지 봅시다.

파이프라인 — 단계 수가 곧 비용. 대신 목적지를 마음대로 붙일 수 있습니다.

기본 설정 — 운영에서 쓸 만한 모양

npm i winston winston-daily-rotate-file
import winston from 'winston';
import 'winston-daily-rotate-file';

const { combine, timestamp, errors, json, colorize, printf } = winston.format;

export const logger = winston.createLogger({
  level: process.env.LOG_LEVEL ?? 'info',
  defaultMeta: { service: 'checkout-api', env: process.env.NODE_ENV },

  format: combine(
    errors({ stack: true }),          // ★ 반드시 json() 앞에. 없으면 스택이 사라집니다
    timestamp(),
    json(),
  ),

  transports: [
    new winston.transports.Console(),
    new winston.transports.DailyRotateFile({
      filename: 'logs/app-%DATE%.log',
      datePattern: 'YYYY-MM-DD',
      maxSize: '50m',
      maxFiles: '14d',                // 14일치만 남기고 지웁니다
      zippedArchive: true,
    }),
  ],

  // 죽을 때의 마지막 줄
  exceptionHandlers: [new winston.transports.File({ filename: 'logs/exceptions.log' })],
  rejectionHandlers: [new winston.transports.File({ filename: 'logs/rejections.log' })],
});

// 개발에서는 사람이 읽는 포맷으로 갈아 끼웁니다
if (process.env.NODE_ENV !== 'production') {
  logger.clear();
  logger.add(new winston.transports.Console({
    format: combine(colorize(), timestamp({ format: 'HH:mm:ss' }),
      printf(({ level, message, timestamp, ...rest }) =>
        `${timestamp} ${level} ${message} ${Object.keys(rest).length ? JSON.stringify(rest) : ''}`)),
  }));
}
순서가 결과를 바꿉니다 — errors({ stack: true }) 를 json() 뒤에 두면 이미 문자열이 된 뒤라 아무 일도 안 합니다. combine 은 위에서 아래로 순서대로 적용됩니다.

winston 의 레벨은 숫자가 반대입니다

winston 은 작을수록 심각하고 pino 는 클수록 심각합니다. 둘 다 “level 로 지정한 것과 그보다 심각한 것을 남긴다”는 뜻은 같습니다. 대시보드에서 level >= 50 같은 조건을 쓸 때 반대로 걸리기 쉬우니 레벨은 문자열로 출력해 두는 편이 안전합니다.
winston 에도 자식 로거가 있습니다 — const reqLog = logger.child({ reqId }). 다만 pino 처럼 고정 필드를 미리 굳혀 두지는 않아서 비용 절감 효과는 없고 편의 기능에 가깝습니다.

그래서 언제 winston 인가 🟡 중급

winston 이 맞는 상황
  • 수집기가 없는 환경 — 온프레미스 VM 에 직접 파일을 쓰고 회전시켜야 할 때
  • 목적지가 여럿이고 규칙이 다를 때 — error 는 Slack, 나머지는 파일, 감사 로그는 DB
  • 이미 winston 으로 돌고 있고 지금 병목이 로깅이 아닐 때 (바꾸는 게 손해)
  • 레벨을 커스텀해야 할 때 — audit · security 같은 자체 레벨 정의가 쉽습니다
winston 이면 후회하는 상황
  • 초당 수천 줄 이상 — 포맷 체인의 객체 할당이 그대로 지연이 됩니다
  • 컨테이너 · 쿠버네티스 — 파일 트랜스포트가 오히려 짐이 됩니다(lg12)
  • Fastify — 내장 pino 를 떼어 내고 winston 을 넣는 건 손해입니다
  • 원격 트랜스포트로 직접 전송 — 네트워크가 느려지면 앱이 같이 느려집니다

실무에선 이렇게 — winston 에서 pino 로 옮기기 🔴 실무

인터페이스를 먼저 좁히면 교체가 하루 일이 됩니다

// src/log.ts — 앱 코드는 이 타입만 압니다
export interface AppLogger {
  debug(fields: Record<string, unknown>, msg: string): void;
  info (fields: Record<string, unknown>, msg: string): void;
  warn (fields: Record<string, unknown>, msg: string): void;
  error(fields: Record<string, unknown>, msg: string): void;
  child(fields: Record<string, unknown>): AppLogger;
}

// winston 구현 — 인자 순서를 pino 쪽에 맞춰 뒤집어 줍니다
const wrapWinston = (w: winston.Logger): AppLogger => ({
  debug: (f, m) => w.debug(m, f),
  info:  (f, m) => w.info(m, f),
  warn:  (f, m) => w.warn(m, f),
  error: (f, m) => w.error(m, f),
  child: (f) => wrapWinston(w.child(f)),
});

// pino 는 그대로 이 모양입니다 — 나중에 한 줄만 바꾸면 됩니다
// export const log: AppLogger = pino({ ... });
이전 순서 — ① 위처럼 얇은 인터페이스를 만들어 앱 전체를 거기에 붙입니다 ② 필드 이름을 양쪽이 같게 맞춥니다(level·time·msg) ③ 스테이징에서 둘 다 켜고 대시보드 쿼리가 똑같이 나오는지 확인 ④ 운영에서 스위치. “한 번에 다 바꾸기”가 실패하는 이유는 대개 ②를 건너뛰기 때문입니다.
파일 회전을 앱이 하지 마세요 — winston-daily-rotate-file 은 편하지만 여러 프로세스가 같은 파일을 회전시키면 로그가 섞이거나 사라집니다(PM2 클러스터에서 자주 봅니다). 회전은 logrotate 나 컨테이너 런타임에 맡기는 것이 안전합니다.
정리 — winston 은 목적지를 조립하려고 씁니다. 그 유연함의 값은 단계마다 만드는 객체입니다. 수집기가 있는 환경이라면 pino + stdout 이 거의 항상 더 낫고, winston 은 수집기가 없을 때의 답입니다.
