LOG 07

요청 추적 — AsyncLocalStorage 로 ID 를 자동으로 붙입니다

요청 ID 를 함수 인자로 계속 나르는 코드는 세 번째 계층에서 무너집니다. Node 는 “지금 처리 중인 요청”을 비동기 호출을 따라 들고 다니는 저장소를 표준으로 제공합니다.

시퀀스 — 인자로 나르지 않는데 붙어 있는 것이 이 절의 전부입니다.

저장소 만들기 — 표준 모듈, 의존성 0

// src/request-context.ts
import { AsyncLocalStorage } from 'node:async_hooks';

export interface RequestContext {
  reqId: string;
  userId?: string;
  traceId?: string;
}

const als = new AsyncLocalStorage<RequestContext>();

/** 이 콜백 안에서 일어나는 모든 비동기 작업이 같은 문맥을 봅니다 */
export function runWithContext<T>(ctx: RequestContext, fn: () => T): T {
  return als.run(ctx, fn);
}

/** 어디서든 꺼내 씁니다. 문맥 밖이면 undefined */
export const getContext = () => als.getStore();

/** 처리 도중에 알게 된 값을 덧붙이기 (로그인 후 userId 등) */
export function setContext(patch: Partial<RequestContext>) {
  const cur = als.getStore();
  if (cur) Object.assign(cur, patch);   // ★ 같은 객체를 고칩니다. 새로 run 하지 않습니다
}
이게 왜 되나 — Node 는 await·setTimeout·이벤트 콜백을 만들 때 지금의 문맥을 함께 기억해 둡니다. 그래서 몇 겹을 들어가도 같은 저장소가 보입니다. Node 22~24 를 거치며 내부 구현이 바뀌어 비용이 크게 줄었습니다 — 예전에 “ALS 는 느리다”고 들은 이야기는 대부분 낡은 정보입니다.

로거에 붙이기 — mixin 한 줄

// src/logger.ts
import pino from 'pino';
import { getContext } from './request-context.js';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  base: { service: 'checkout-api', env: process.env.NODE_ENV },

  // ★ 줄을 쓸 때마다 호출됩니다 — 여기서 문맥을 꺼내 붙입니다
  mixin() {
    const ctx = getContext();
    return ctx ? { reqId: ctx.reqId, userId: ctx.userId, traceId: ctx.traceId } : {};
  },
});

// 이제 앱 어디서든 그냥 이렇게 씁니다
logger.info({ orderId: 8821 }, 'order paid');
// → { ..., reqId: "req_01J8Q", userId: "u_8821", orderId: 8821, msg: "order paid" }
// Express 에 연결
app.use((req, res, next) => {
  const reqId = String(req.headers['x-request-id'] ?? randomUUID());
  res.setHeader('x-request-id', reqId);
  runWithContext({ reqId }, () => next());   // ★ next() 를 감싸는 것이 핵심
});

// Fastify
app.addHook('onRequest', (req, reply, done) => {
  runWithContext({ reqId: req.id }, () => done());
});

// NestJS — 미들웨어로 같은 모양
export class ContextMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    runWithContext({ reqId: String(req.headers['x-request-id'] ?? randomUUID()) },
      () => next());
  }
}
mixin 과 child 중 무엇을 쓰나 — 문맥을 로거 인스턴스를 넘기지 않고 쓰고 싶으면 mixin, 로거를 명시적으로 넘길 수 있으면 child 가 더 빠릅니다(고정 필드를 미리 굳혀 두므로). 실무에서는 둘을 같이 씁니다 — 요청 로거는 child, 깊은 곳은 mixin.

문맥이 사라지는 자리 — 여기서만 조심하면 됩니다 🟡 중급

끊기는 네 가지 경우

// ① 서버 시작 시 한 번 만든 타이머·구독 — 애초에 문맥 밖입니다
setInterval(() => logger.info('heartbeat'), 60_000);   // reqId 없음. 정상입니다

// ② 요청 밖으로 "떠난" 작업 — 응답을 보내고 나서도 도는 코드
app.post('/orders', (req, res) => {
  res.json({ ok: true });
  queueMicrotask(() => heavyAudit());   // 문맥은 살아 있습니다(같은 비동기 사슬)
  setTimeout(() => heavyAudit(), 0);    // 이것도 살아 있습니다
});

// ③ ✗ 진짜로 끊기는 곳 — 다른 사슬에 등록된 콜백
const emitter = new EventEmitter();          // 앱 시작 때 만든 객체
emitter.on('done', () => logger.info('x'));  // ← 등록 시점의 문맥(=없음)을 씁니다
// 해결: 값을 미리 꺼내서 클로저에 담습니다
const { reqId } = getContext() ?? {};
emitter.on('done', () => logger.info({ reqId }, 'x'));

// ④ ✗ 워커 스레드 · 자식 프로세스 — 메모리를 공유하지 않습니다
worker.postMessage({ reqId, payload });      // 값으로 직접 넘겨야 합니다
판단 기준 한 줄 — “이 콜백은 요청 처리 중에 만들어졌는가?” 요청 처리 중에 만든 프로미스·타이머·스트림은 문맥을 물려받고, 서버 시작 때 만들어 둔 객체에 나중에 등록한 콜백은 물려받지 못합니다.

# ① 사용자에게 응답 헤더의 x-request-id 를 물어봅니다 (또는 에러 화면에 표시)

ID 를 사용자에게 보여 주세요 — 500 에러 화면에 “오류 코드: req_01J8QK4T9” 한 줄을 넣어 두면 고객센터에서 스크린샷 한 장으로 조사가 시작됩니다. 이것 하나가 장애 대응 시간을 크게 줄입니다.
ID 는 앞단에서 이어받으세요 — 로드밸런서·CDN·API 게이트웨이가 이미 x-request-id(또는 traceparent)를 붙여 보냅니다. 있으면 쓰고 없으면 만드는 것이 규칙입니다. 새로 만들어 버리면 앞단 로그와 이어지지 않습니다.

실무에선 이렇게 — 여러 서비스를 하나로 잇기 🔴 실무

우리 서비스가 다른 서비스를 부를 때 ID 를 함께 보냅니다

// src/http-client.ts — 모든 바깥 호출이 이 함수를 거치게 합니다
import { getContext } from './request-context.js';
import { logger } from './logger.js';

export async function call(url: string, init: RequestInit = {}) {
  const ctx = getContext();
  const t0 = performance.now();

  const headers = new Headers(init.headers);
  if (ctx?.reqId) headers.set('x-request-id', ctx.reqId);   // ★ 그대로 전달
  if (ctx?.traceId) headers.set('traceparent',
    `00-${ctx.traceId}-${ctx.spanId ?? '0'.repeat(16)}-01`); // W3C Trace Context

  try {
    const res = await fetch(url, { ...init, headers });
    logger.info({
      event: 'http.call', url, statusCode: res.status,
      durationMs: Math.round(performance.now() - t0),
    }, 'outbound call');
    return res;
  } catch (err) {
    logger.error({ event: 'http.call_failed', url, err }, 'outbound call failed');
    throw err;
  }
}
이 함수 하나가 세 가지를 동시에 해결합니다 — ① 다음 서비스의 로그가 같은 reqId 를 갖습니다 ② 바깥 호출의 지연이 자동으로 측정됩니다 ③ 실패가 한 곳에서만 기록되어 중복 로그가 사라집니다. 바깥으로 나가는 길을 하나로 모으는 것이 관측의 첫걸음입니다.
OpenTelemetry 를 이미 쓴다면 ID 를 직접 만들지 마세요 — @opentelemetry/api 의 trace.getActiveSpan()?.spanContext() 에서 traceId·spanId 를 꺼내 mixin 에 넣으면 로그와 트레이스가 대시보드에서 한 번에 이어집니다(lg12). OTel 도 내부적으로 같은 비동기 문맥 전파를 씁니다.
정리 — AsyncLocalStorage 로 요청 문맥을 담고 pino 의 mixin 으로 꺼내 붙이면 reqId 를 인자로 나를 필요가 없습니다. 끊기는 곳은 서버 시작 때 만든 객체의 콜백과 워커 스레드뿐입니다.
LOG 08

TypeScript — 로그도 타입으로 잠글 수 있습니다

로그 필드는 공개 API입니다. 그런데 대부분 Record<string, any> 로 열어 두고 오타를 6개월 뒤 대시보드에서 발견합니다. 컴파일러에게 시키면 될 일입니다.

좌우 대조 — 로그 필드는 공개 API입니다. API 를 any 로 두지는 않잖아요.

레벨과 사건 이름을 리터럴 유니온으로

// src/log-types.ts
export type Level = 'trace' | 'debug' | 'info' | 'warn' | 'error' | 'fatal';

// 사건 이름 목록 — 대시보드가 이 위에 세워집니다
export const EVENTS = [
  'order.created', 'order.paid', 'order.cancelled',
  'payment.failed', 'payment.retried',
  'user.login', 'user.login_failed',
  'http.call', 'http.call_failed',
] as const;
export type Event = (typeof EVENTS)[number];

// 필드 사전 — 여기 없는 키는 못 넣습니다
export interface LogFields {
  event?: Event;
  reqId?: string;
  traceId?: string;
  userId?: string;         // ★ 내부 식별자만. 이메일이 들어오면 lg10 의 사고
  orderId?: number;
  statusCode?: number;
  durationMs?: number;     // 단위를 이름에 (lg05)
  component?: 'db' | 'http' | 'queue' | 'cache';
  err?: unknown;
}

// 타입 안전한 얇은 래퍼
import { logger } from './logger.js';
export const log = {
  info : (f: LogFields, msg: string) => logger.info(f, msg),
  warn : (f: LogFields, msg: string) => logger.warn(f, msg),
  error: (f: LogFields, msg: string) => logger.error(f, msg),
  debug: (f: LogFields, msg: string) => logger.debug(f, msg),
};

log.info({ event: 'order.paid', orderId: 8821, durationMs: 37 }, 'order paid');
log.info({ userid: 1 }, 'x');   // ✗ 컴파일 에러 — 'userid' 는 LogFields 에 없습니다
log.info({ event: 'order.payed' }, 'x');   // ✗ 오타가 여기서 잡힙니다
“초과 속성 검사”가 여기서 일을 합니다 — 객체 리터럴을 바로 넘길 때만 없는 키를 잡아 줍니다. const f = { userid: 1 }; log.info(f, 'x') 는 통과합니다. 그래서 로그 필드는 변수에 담지 말고 그 자리에서 리터럴로 넘기는 습관이 유리합니다.

pino 의 타입을 제대로 쓰기

import pino from 'pino';

// ① 커스텀 레벨을 제네릭으로 알려 주면 자동완성에 나옵니다
const logger = pino<'audit' | 'security'>({
  customLevels: { audit: 35, security: 45 },
  useOnlyCustomLevels: false,
});
logger.audit({ actor: 'u_1' }, 'permission changed');   // ○ 타입이 압니다
logger.aduit({}, 'x');                                  // ✗ 컴파일 에러

// ② 자식 로거의 타입은 그대로 이어집니다
type AppLogger = pino.Logger<'audit' | 'security'>;
export function makeReqLogger(reqId: string): AppLogger {
  return logger.child({ reqId });
}

// ③ 직렬화기에도 타입을 답니다 — any 를 두면 여기가 구멍이 됩니다
const logger2 = pino({
  serializers: {
    err: pino.stdSerializers.err,
    req: (req: { method: string; url: string }) => ({ method: req.method, url: req.url }),
  },
});

// ④ 로그로 나가면 안 되는 타입을 타입 시스템으로 막기 (lg10 의 예방책)
declare const brand: unique symbol;
export type Secret<T> = T & { readonly [brand]: 'secret' };
export const asSecret = <T,>(v: T) => v as Secret<T>;

interface SafeFields { [k: string]: string | number | boolean | undefined }
function safeLog(f: SafeFields, msg: string) { logger.info(f, msg); }

const token = asSecret('eyJhbGciOi...');
safeLog({ token }, 'x');   // ✗ Secret<string> 은 SafeFields 에 안 맞습니다
④ 가 실무에서 가장 값어치가 큽니다 — 토큰·비밀번호·주민번호를 담는 값에 브랜드 타입을 씌워 두면 실수로 로그에 넣는 순간 컴파일이 막습니다. 런타임 마스킹(lg10)은 마지막 그물이고, 이건 애초에 안 담기게 하는 방법입니다.

한 단계 더 — 사건마다 필요한 필드를 강제하기 🟡 중급

“결제 실패 로그에는 orderId 가 반드시 있어야 한다”를 타입으로

// 사건별로 필요한 필드를 묶습니다 (판별 유니온)
type LogEvent =
  | { event: 'order.paid';      orderId: number; durationMs: number }
  | { event: 'payment.failed';  orderId: number; reason: string; err?: unknown }
  | { event: 'user.login';      userId: string }
  | { event: 'user.login_failed'; reason: 'bad_password' | 'locked' | 'unknown' };

// 공통 필드는 자동으로 붙으니(mixin) 여기엔 사건 고유 필드만 둡니다
export function event(e: LogEvent, msg?: string) {
  const { event, ...rest } = e;
  logger.info({ event, ...rest }, msg ?? event);
}

event({ event: 'order.paid', orderId: 8821, durationMs: 37 });         // ○
event({ event: 'payment.failed', orderId: 8821 });                     // ✗ reason 이 없습니다
event({ event: 'user.login_failed', reason: 'expired' });              // ✗ 허용된 값이 아닙니다

// 대시보드 쪽 쿼리도 같은 타입에서 만들 수 있습니다
export const EVENT_NAMES = [
  'order.paid', 'payment.failed', 'user.login', 'user.login_failed',
] as const satisfies readonly LogEvent['event'][];
// ★ satisfies — 목록에 빠진 사건이 생기면 여기서 컴파일이 막습니다
과하지 않나요? — 사건이 열 개 미만인 서비스라면 과합니다. 하지만 알림 규칙이 붙은 사건이나 매출·정산 분석의 근거가 되는 사건은 이렇게 잠가 두는 편이 좋습니다. “그 필드가 없어서 분석을 못 했다”는 지난달 로그로는 되돌릴 수 없습니다.
타입이 런타임을 지켜 주지는 않습니다 — 외부 API 응답이나 DB 행처럼 타입 주장(as)만 붙인 값은 실제로 무엇이 들었는지 컴파일러도 모릅니다. 그런 값을 통째로 로그에 넣는 순간 lg10 의 사고가 납니다. 필드로 골라 담는 습관이 결국 답입니다.
정리 — 레벨은 리터럴 유니온, 필드는 인터페이스, 사건은 판별 유니온으로 잠급니다. 타입은 컴파일 뒤 사라지므로 런타임 비용이 0이고, 브랜드 타입이면 비밀 값이 로그에 담기는 것 자체를 막을 수 있습니다.
