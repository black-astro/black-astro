LOG 07

회전과 보존 — 디스크가 차서 죽는 사고를 막기

로그로 서비스를 죽이는 가장 흔한 방법은 디스크를 채우는 것입니다. 회전은 “파일을 나눈다”가 아니라 총량에 상한을 씌운다는 뜻이고, 그 상한을 모르면 용량 계획이 없는 것입니다.

회전 — 파일 개수 × 파일 크기가 곧 상한. 이 곱을 먼저 정하고 나머지를 맞춥니다.

크기 기준과 날짜 기준

#include <spdlog/sinks/rotating_file_sink.h>
#include <spdlog/sinks/daily_file_sink.h>

// ① 크기 기준 — 상한이 확실합니다. 서버의 기본값
auto rot = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    "logs/app.log",
    50 * 1024 * 1024,   // 파일 하나 50 MB
    5);                 // app.log + app.1~5.log = 최대 300 MB
//   rotate_on_open 을 주면 프로세스가 뜰 때마다 새 파일이 됩니다
//   (4번째 인자, 기본 false)

// ② 날짜 기준 — 사람이 찾기 쉽습니다. 배치·분석 로그에
auto daily = std::make_shared<spdlog::sinks::daily_file_sink_mt>(
    "logs/app.log",
    0, 0,               // 매일 00:00 에 새 파일
    false,
    14);                // 최근 14개만 남기고 삭제
//   → logs/app_2026-09-01.log 처럼 이름이 만들어집니다

// ③ 둘 다 필요하면 싱크를 두 개 붙입니다 (lg03)
날짜 기준의 함정 — 하루치 상한이 없습니다. 장애가 나서 에러 로그가 폭주하는 날, 하루 파일 하나가 디스크를 다 먹습니다. 운영 서비스라면 크기 기준을 기본으로 하고 날짜는 부가로 두세요.

디스크가 차면 실제로 무슨 일이 나나

ENOSPC (No space left on device) 가 나면 —

  · write() 가 실패합니다
  · spdlog 는 기본적으로 예외(spdlog_ex)를 던집니다
  · 그 예외가 요청 처리 경로에서 나면? 요청이 실패합니다
  · block 정책의 비동기 큐라면? 전부 멈춥니다 (lg05)

★ 그래서 두 겹으로 막습니다
  ① 상한을 코드로   회전 크기 × 개수 = 최대치
  ② 여유를 감시로   디스크 사용률 80% 알림
                    (로그 볼륨은 데이터 볼륨과 분리하세요)

★ 그리고 로깅 실패가 서비스를 죽이지 않게
  spdlog::set_error_handler([](const std::string& msg){
      // 여기서 다시 로깅하면 무한 재귀입니다 ★
      fputs(msg.c_str(), stderr);
  });
로그 볼륨을 따로 두라는 말의 뜻 — 로그가 /var/log(별도 파티션)에 있으면 디스크가 차도 DB 와 애플리케이션은 계속 돕니다. 같은 파티션이면 로그가 서비스 데이터를 밀어냅니다. 컨테이너라면 로그를 파일로 안 쓰는 쪽이 더 낫습니다(lg10).

양쪽에서 다 도는 설정

// ① 회전은 "라이브러리에게" 맡기고 외부 도구를 섞지 않습니다
//    spdlog 의 rotating_file_sink 는 스스로 닫고 · 이름 바꾸고 · 다시 엽니다
//    → Windows 에서도 그대로 돕니다

// ② 경로는 상대경로로 두지 말고 명시적으로
//    (서비스로 등록하면 작업 디렉터리가 예상과 다릅니다)
std::filesystem::path base =
#ifdef _WIN32
    std::filesystem::path(std::getenv("PROGRAMDATA")) / "myapp" / "logs";
#else
    "/var/log/myapp";
#endif
std::filesystem::create_directories(base);

auto sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    (base / "app.log").string(), 50 * 1024 * 1024, 5);

// ③ 파일 이름에 프로세스 ID 를 넣으면 멀티프로세스에서 안전합니다 (lg09)
//    (base / std::format("app-{}.log", getpid())).string()
UTF-8 파일 이름 — Windows 에서 한글 경로를 쓰면 인코딩 문제로 열리지 않는 일이 있습니다. 로그 경로에는 ASCII 만 쓰는 것이 가장 안전하고, 메시지 안의 한글은 UTF-8 로 통일하고 콘솔에서는 chcp 65001 로 봅니다.
정리 — 회전의 목적은 총량 상한입니다 — 파일 크기 × 개수가 그 값이고, 이 곱을 먼저 정하세요. 날짜 기준은 하루 상한이 없습니다. 디스크가 차면 로깅이 예외를 던져 요청을 죽일 수 있으므로 set_error_handler 를 걸고, 로그 볼륨을 서비스 데이터와 분리하세요. POSIX 에서 rm 한 로그는 사라진 게 아니라 안 보이는 것입니다.
LOG 08

크래시 로그 — 죽는 순간에도 흔적을 남기기

가장 알고 싶은 순간은 프로세스가 죽는 순간인데, 하필 그때 로거를 부를 수 없습니다. 시그널 핸들러 안에서는 malloc 조차 금지입니다. 그래서 흔적을 남기고 빨리 죽는 전략을 따로 짭니다.

파이프라인 — 핸들러는 최소한만. 사람이 읽을 보고서는 다음 프로세스가 만듭니다.

최소한의 시그널 핸들러 (POSIX)

#include <csignal>
#include <unistd.h>

// 메시지를 "미리" 만들어 둡니다 — 핸들러 안에서는 만들 수 없습니다
static const char kMsg[] = "\n*** FATAL: signal caught, see core dump ***\n";
static int g_log_fd = -1;      // 미리 열어 둔 파일 디스크립터

extern "C" void on_fatal(int sig) {
    // ① async-signal-safe 한 write 만 씁니다
    (void)!write(g_log_fd, kMsg, sizeof(kMsg) - 1);
    (void)!write(STDERR_FILENO, kMsg, sizeof(kMsg) - 1);

    // ② 기본 동작으로 되돌리고 자기 자신에게 다시 보냅니다
    //    → 커널이 core dump 를 남깁니다 ★
    signal(sig, SIG_DFL);
    raise(sig);
}

int main() {
    g_log_fd = ::open("/var/log/myapp/crash.log",
                      O_WRONLY | O_CREAT | O_APPEND, 0644);
    struct sigaction sa{};
    sa.sa_handler = on_fatal;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESETHAND;          // 재진입 방지
    for (int s : {SIGSEGV, SIGABRT, SIGBUS, SIGFPE, SIGILL})
        sigaction(s, &sa, nullptr);
}
backtrace() 를 부르고 싶겠지만 — backtrace_symbols() 는 내부에서 malloc 을 씁니다. 힙이 망가져서 죽은 상황이라면 여기서 또 멈춥니다. backtrace()(주소만 채우기)까지는 대체로 안전하고, 주소를 심볼로 바꾸는 일은 나중에 addr2line 으로 하세요.

코어 덤프 — 사실 이게 가장 강력합니다

# ① 코어 덤프 켜기 (기본은 꺼져 있는 배포판이 많습니다)
ulimit -c unlimited
# systemd 서비스라면 유닛 파일에
#   LimitCORE=infinity

# ② 어디에 떨어지는지 확인
cat /proc/sys/kernel/core_pattern
#   |/usr/lib/systemd/systemd-coredump ...   ← systemd 가 받습니다
coredumpctl list
coredumpctl gdb 12345          # 그 프로세스의 코어로 gdb 진입

# 파일로 받고 싶다면
sudo sysctl -w kernel.core_pattern=/var/crash/core.%e.%p.%t

# ③ 심볼이 있어야 읽힙니다 — Release 라도 -g 를 켜세요
#    g++ -O2 -g          (최적화는 그대로, 디버그 정보만 추가)
#    빌드 후 분리해서 보관하면 배포 크기가 안 늘어납니다
objcopy --only-keep-debug app app.debug
objcopy --strip-debug --add-gnu-debuglink=app.debug app

# ④ 분석
gdb ./app /var/crash/core.app.12345.1756...
(gdb) bt full
(gdb) thread apply all bt

한 단계 더 — Windows 의 미니덤프 🟡 중급

SetUnhandledExceptionFilter + MiniDumpWriteDump

#include <windows.h>
#include <dbghelp.h>          // -ldbghelp / dbghelp.lib

LONG WINAPI on_crash(EXCEPTION_POINTERS* ep) {
    HANDLE h = CreateFileW(L"crash.dmp", GENERIC_WRITE, 0, nullptr,
                           CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, nullptr);
    if (h != INVALID_HANDLE_VALUE) {
        MINIDUMP_EXCEPTION_INFORMATION mei{};
        mei.ThreadId          = GetCurrentThreadId();
        mei.ExceptionPointers = ep;
        mei.ClientPointers    = FALSE;
        MiniDumpWriteDump(GetCurrentProcess(), GetCurrentProcessId(), h,
                          MiniDumpWithIndirectlyReferencedMemory,
                          &mei, nullptr, nullptr);
        CloseHandle(h);
    }
    return EXCEPTION_EXECUTE_HANDLER;   // 프로세스를 끝냅니다
}

int main() {
    SetUnhandledExceptionFilter(on_crash);
}
// ★ .dmp 는 .pdb 와 짝입니다. 빌드마다 pdb 를 반드시 보관하세요.
//   Visual Studio 나 WinDbg 에서 .dmp 를 열면 그 자리의 콜스택이 나옵니다.
같은 프로세스 안에서 덤프를 뜨는 것은 원래 위험합니다 — 이미 망가진 프로세스의 힙과 로더 락을 다시 건드리기 때문입니다. Crashpad 가 널리 쓰이는 이유가 이것입니다 — 별도의 감시 프로세스가 밖에서 덤프를 뜹니다.

C++ 쪽의 마지막 그물

#include <exception>
#include <cstdlib>

// ① 처리되지 않은 예외 — 여기는 아직 "정상" 상태입니다
//    로거를 불러도 됩니다 (시그널 핸들러가 아닙니다)
std::set_terminate([]{
    if (auto e = std::current_exception()) {
        try { std::rethrow_exception(e); }
        catch (const std::exception& x) {
            spdlog::critical("unhandled exception: {}", x.what());
        }
        catch (...) { spdlog::critical("unhandled unknown exception"); }
    }
    spdlog::shutdown();          // ★ 큐를 비웁니다
    std::abort();                // 그다음 코어 덤프로
});

// ② 정상 종료 경로에서도 반드시 flush
std::atexit([]{ spdlog::shutdown(); });

// ③ 마지막 몇 줄만이라도 살리는 값싼 방법
lg->flush_on(spdlog::level::err);          // error 이상은 즉시 디스크로
spdlog::flush_every(std::chrono::seconds(1));
이 셋의 역할이 다릅니다 — set_terminate 는 C++ 예외(아직 안전), 시그널 핸들러는 메모리 오류(아무것도 못 함), flush_on 은 둘 중 어느 쪽이든 직전 줄을 살리는 보험입니다. 세 개를 다 걸어 두세요. 셋 다 몇 줄이면 됩니다.

이때 로그가 함께 있어야 쓸모가 있습니다
  · 덤프와 같은 폴더에 마지막 로그 파일을 함께 올립니다
  · 로그에 세션 ID / 빌드 해시를 찍어 두면 덤프와 짝지을 수 있습니다 ★
데스크톱 앱이라면 거의 필수입니다 — 사용자가 “가끔 꺼져요”라고 말할 때 덤프가 없으면 할 수 있는 일이 없습니다. 서버라면 코어 덤프 + 로그로 충분한 경우가 많지만, 배포 대상이 남의 컴퓨터라면 Crashpad 를 붙이는 편이 결국 더 쌉니다.
정리 — 죽는 순간에는 로거를 부를 수 없습니다 — 시그널 핸들러에서는 write(2) 로 미리 만들어 둔 바이트만 쓰고 바로 죽입니다. 진짜 정보는 코어 덤프(POSIX) · 미니덤프(Windows)에 있고, 심볼을 빌드별로 보관해야 읽힙니다. set_terminate · 시그널 핸들러 · flush_on(err) 셋을 다 걸어 두세요.
