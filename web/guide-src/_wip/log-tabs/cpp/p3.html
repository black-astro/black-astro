LOG 05

비동기 로깅 — 큐 하나로 지연이 사라지는 이유

비동기 로깅은 일을 줄이지 않습니다. 일을 다른 스레드로 옮길 뿐입니다. 그런데도 효과가 큰 이유는, 옮겨진 일이 하필 가장 느린 부분(포맷과 시스템콜)이기 때문입니다. 대신 큐가 가득 찼을 때 무엇을 버릴지를 내가 정해야 합니다.

시퀀스 — 느린 일을 다른 코어로 밀어낸 것. 총량은 그대로지만 요청 경로에서는 사라집니다.

spdlog 비동기 — 네 줄이면 됩니다

#include <spdlog/async.h>
#include <spdlog/sinks/rotating_file_sink.h>

// ① 스레드 풀: 큐 8192칸 · 백엔드 스레드 1개
//    큐 칸 하나가 로그 한 줄입니다. 2의 거듭제곱이어야 합니다
spdlog::init_thread_pool(8192, 1);

// ② 비동기 로거 만들기 (기본 정책 = block)
auto lg = spdlog::create_async<spdlog::sinks::rotating_file_sink_mt>(
    "app", "logs/app.log", 5 * 1024 * 1024, 3);

// ②' 큐가 차면 오래된 것을 버리는 쪽 (non-blocking)
auto lg2 = spdlog::create_async_nb<spdlog::sinks::rotating_file_sink_mt>(
    "app2", "logs/app2.log", 5 * 1024 * 1024, 3);

// ③ 종료 시 반드시 — 큐에 남은 줄을 비웁니다
//    이걸 빼면 마지막 수천 줄이 그냥 사라집니다 ★
std::atexit([]{ spdlog::shutdown(); });
백엔드 스레드는 1개로 두세요 — 2개 이상이면 로그 순서가 뒤섞입니다. 시간순으로 읽을 수 없는 로그는 없는 것과 비슷합니다. 처리량이 부족하면 스레드를 늘리지 말고 큐를 키우거나 로그 양을 줄이세요.

호출부에서 실제로 일어나는 일

lg->info("주문 {} 처리 {}ms", order, elapsed);

// 동기 로거였다면 이 한 줄 안에서
//   ① 레벨 검사 → ② {fmt} 로 문자열 조립 → ③ 패턴 붙이기
//   ④ 뮤텍스 잡기 → ⑤ 버퍼 복사 → ⑥ 필요하면 write()

// 비동기 로거라면 이 한 줄 안에서
//   ① 레벨 검사 → ② 인자를 "값으로" 큐에 복사 → 끝
//   ★ 여기서 중요한 것 — 인자는 값으로 복사됩니다

const char* p = temp.c_str();
lg->info("{}", p);          // ★ 위험. temp 가 먼저 죽을 수 있습니다
lg->info("{}", temp);       // 안전 — std::string 이 복사됩니다

// 참조·포인터를 넘기면 백엔드가 읽을 때 이미 사라진 뒤일 수 있습니다.
// 비동기에서 가장 흔한 크래시 원인입니다.
“복사가 비싸지 않나요” — 대개 그 반대입니다. std::string 한 번 복사(수십 ns)가 포맷 + 시스템콜(수백 ns~수 µs)보다 훨씬 쌉니다. 정말 복사가 아까운 자리라면 quill 의 지연 포매팅을 보세요(lg06).

한 단계 더 — 큐가 가득 차면 무엇을 버릴 것인가 🟡 중급

발산 램프 — 한 줄에 초록만 있는 정책은 없습니다. 무엇을 포기할지가 선택입니다.

정책을 손으로 지정하기

#include <spdlog/async.h>

auto tp = std::make_shared<spdlog::details::thread_pool>(8192, 1);
auto sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    "logs/app.log", 5 * 1024 * 1024, 3);

auto lg = std::make_shared<spdlog::async_logger>(
    "app", sink, tp,
    spdlog::async_overflow_policy::overrun_oldest);
//   block          — 큐가 빌 때까지 호출자가 기다립니다 (기본)
//   overrun_oldest — 가장 오래된 줄을 덮어씁니다 (유실 허용)

spdlog::register_logger(lg);

// 큐가 실제로 넘치는지 재기 — 넘치는 줄을 세는 훅
//   spdlog 버전에 따라 방법이 다릅니다. 가장 확실한 방법은
//   백엔드에서 마지막으로 본 시퀀스 번호를 로그에 함께 찍는 것입니다
lg->info("seq={} {}", seq.fetch_add(1, std::memory_order_relaxed), msg);
//   나중에 로그에서 seq 가 건너뛴 자리를 세면 유실량이 나옵니다 ★

어떻게 고르나 — 상황별

상황정책
결제 · 감사 로그block — 잃으면 안 됩니다. 느려지는 편이 낫습니다
게임 서버 틱 로그overrun_oldest — 한 줄 잃어도 틱은 밀리면 안 됩니다
거래 시스템 주문 경로무한 큐 + 지연 포매팅(quill) — 메모리로 값을 냅니다
배치 · 사내 도구동기 — 단순한 것이 최고입니다
컨테이너 · stdout동기 + 수집기가 뒤를 받습니다(lg10)
block 이 위험해지는 순간 — 디스크가 느려지거나 로그 볼륨이 가득 차면 큐가 안 비고, 모든 요청 스레드가 로그 한 줄에서 멈춥니다. “로그 때문에 서비스가 죽었다”는 사고는 거의 전부 이 조합입니다. block 을 쓸 거면 디스크 여유 공간 알림을 반드시 함께 거세요(lg07).

실무에선 이렇게 — quill 의 접근 🔴 실무

quill — 호출 스레드에서 포맷을 아예 하지 않습니다

#include "quill/Backend.h"
#include "quill/Frontend.h"
#include "quill/LogMacros.h"
#include "quill/Logger.h"
#include "quill/sinks/ConsoleSink.h"

int main() {
    quill::Backend::start();                       // 백엔드 스레드 기동

    auto sink = quill::Frontend::create_or_get_sink<quill::ConsoleSink>("s1");
    quill::Logger* lg = quill::Frontend::create_or_get_logger("root", std::move(sink));

    LOG_INFO(lg, "주문 {} 처리 {}ms", 8812, 3.4);
    // 호출 스레드가 한 일 — 포맷 문자열의 "주소"와 인자의 바이트를
    // SPSC 큐에 복사한 것이 전부입니다. 문자열 조립은 백엔드가 합니다.
}
spdlog 비동기의 남은 비용
  • 인자를 큐에 넣기 전에 포맷을 미리 끝냅니다(기본 구성)
  • 즉, {fmt} 조립 비용은 여전히 호출 스레드에 남습니다
  • 메시지가 길면 문자열 할당이 호출 경로에 들어옵니다
  • 그래도 대부분의 서버에는 충분히 빠릅니다
quill 이 옮긴 것
  • 포맷 문자열은 컴파일 타임 상수로 두고 주소만 큐에
  • 인자는 바이트 그대로 큐에 — 문자열 조립은 백엔드에서
  • 그래서 호출 비용이 수 ns~수십 ns 수준까지 내려갑니다
  • 대가 — 빌드 필요 · 헤더온리 아님 · API 가 버전마다 바뀜
API 는 버전을 확인하세요 — quill 은 v4 에서 프론트엔드/백엔드 구조로 크게 바뀌었습니다. 위 코드는 v4 이후 형태입니다. 붙이기 전에 그 버전의 README 예제를 그대로 한 번 돌려 보고 시작하는 것이 가장 빠릅니다. spdlog 도 마찬가지로 1.x 안에서 async API 가 조금씩 다듬어졌습니다.
정리 — 비동기 로깅은 느린 일(포맷 · write)을 다른 코어로 옮기는 것입니다. spdlog 는 init_thread_pool + create_async 두 줄이면 되고, 백엔드 스레드는 1개 · 종료 전 shutdown() 이 규칙입니다. 큐가 차면 막을 것인가(block) 버릴 것인가(overrun_oldest)를 골라야 하고, 참조·포인터를 넘기면 백엔드가 읽을 때 이미 죽어 있을 수 있습니다.
LOG 06

로그 한 줄의 값 — 비용을 재고 줄이는 법

“로깅은 느리다”는 말은 너무 뭉뚱그린 표현입니다. 한 줄 안에서 어디에 시간이 가는지를 나누어 보면, 줄일 수 있는 곳과 없는 곳이 분명히 갈립니다. 그리고 내 기계에서 직접 재는 법까지 알아야 이야기가 끝납니다.

워터폴 — 줄일 수 있는 것은 포맷과 시스템콜. 레벨 검사는 이미 공짜에 가깝습니다.

비용을 줄이는 순서 ★

① 안 찍는다            컴파일 타임 제거 (SPDLOG_ACTIVE_LEVEL)
                        → 비용 0. 다른 어떤 최적화보다 큽니다

② 덜 찍는다            루프 안 로그를 밖으로 · 샘플링
                        → 1/1000 만 찍어도 대개 충분합니다

③ 나중에 찍는다        비동기 큐 (lg05)
                        → 호출 경로에서 포맷·시스템콜이 사라집니다

④ 늦게 포맷한다        quill 방식 · 바이너리 로깅
                        → 호출 비용이 수 ns 대로 내려갑니다

⑤ 덜 자주 내보낸다     버퍼링 · flush_every
                        → write() 를 수백 줄에 한 번으로

⑥ 짧게 찍는다          패턴에서 안 쓰는 토큰 빼기
                        → %s %! 는 생각보다 비쌉니다

★ ①②가 전체의 90% 입니다. ③부터는 재고 나서 하세요.

핫 패스에서 실제로 쓰는 기법

// ① 로거 포인터를 캐시 — spdlog::get() 은 해시 조회 + 락입니다
static auto* lg = spdlog::get("hot").get();   // 한 번만
lg->debug("tick {}", n);

// ② 무거운 인자는 레벨을 먼저 확인
if (lg->should_log(spdlog::level::debug))
    lg->debug("state {}", expensive_dump());   // 통과할 때만 계산

// ③ 아예 매크로로 — Release 에서 코드까지 사라집니다
SPDLOG_DEBUG("state {}", expensive_dump());

// ④ 샘플링 — 초당 수십만 건짜리 루프에서
if ((n & 0x3FF) == 0)                          // 1024번에 한 번
    SPDLOG_DEBUG("tick {} 진행률 {:.1f}%", n, pct);

// ⑤ 속도 제한 — 같은 에러가 초당 수천 번 날 때
//    (직접 구현하거나 spdlog 의 dup_filter_sink 를 씁니다)
#include <spdlog/sinks/dup_filter_sink.h>
auto dup = std::make_shared<spdlog::sinks::dup_filter_sink_mt>(
    std::chrono::seconds(5));                  // 5초 내 같은 메시지 묶기
dup->add_sink(file);

한 단계 더 — 직접 재는 법 🟡 중급

벤치마크 — 평균이 아니라 꼬리를 봅니다

#include <benchmark/benchmark.h>      // Google Benchmark
#include <spdlog/spdlog.h>

static void BM_log(benchmark::State& st) {
    auto lg = spdlog::get("bench");
    int i = 0;
    for (auto _ : st) lg->info("order {} amt {}", i++, 45900);
}
BENCHMARK(BM_log)->Threads(1)->Threads(4)->Threads(16);
//   ★ 스레드 수를 바꿔 가며 재세요 — 락 경합은 1스레드에서 안 보입니다

BENCHMARK_MAIN();
# 실행 — 결과를 흔들지 않게
sudo cpupower frequency-set -g performance      # 주파수 고정
taskset -c 2,3 ./bench --benchmark_repetitions=10 \
        --benchmark_report_aggregates_only=true

# 꼬리 지연은 별도로 — HdrHistogram 이나 직접 배열에 담아 정렬
#   p50 만 보면 "빠르다"가 되고 p99.9 를 보면 "가끔 30 ms" 가 됩니다

벤치가 거짓말하는 다섯 가지

함정결과
/dev/null 로 측정디스크 비용이 0 — 실제와 무관해집니다
단일 스레드락 경합이 안 보입니다. 진짜 비용은 여기 있습니다
tmpfs 에 쓰기메모리에 쓰는 셈. 회전·fsync 비용이 사라집니다
비동기인데 flush 안 함큐에 넣고 끝 — 백엔드가 못 따라오는 게 안 보입니다
평균만 보기회전이 일어난 그 한 번이 수십 ms 인데 평균에 묻힙니다
가장 정직한 측정 — 벤치마크 대신 실제 서비스에 로그를 켜고 끄면서 p99 를 비교하는 것입니다. 마이크로벤치는 “어느 쪽이 더 빠른가”에는 답하지만 “내 서비스에서 로깅이 문제인가”에는 답하지 못합니다.

한 단계 더 — 바이너리 로깅과 지연 포매팅 🧬 전문가

µs 가 돈인 곳에서 쓰는 마지막 수단

// 아이디어 — 사람이 읽을 문자열을 "실행 중에" 만들지 않습니다.
//   ① 포맷 문자열은 바이너리에 이미 들어 있습니다 → 주소(또는 ID)만 기록
//   ② 인자는 바이트 그대로 기록
//   ③ 사람이 읽는 문자열은 "나중에" 별도 도구가 만듭니다

struct Rec { const char* fmt; uint64_t ts; int32_t a0; double a1; };
// 한 줄 = 32바이트 안쪽. memcpy 한 번이 전부입니다.

// 재생기(offline decoder)가 fmt 주소를 심볼로 되돌려 문자열을 만듭니다
//   → 실행 중 비용: 수 ns
//   → 대가: 로그 파일을 그냥 cat 으로 못 봅니다. 도구가 있어야 합니다

// 이 방식을 이미 구현해 둔 것들
//   · quill        — 지연 포매팅이 기본 동작
//   · Binlog       — 바이너리 로그 + 전용 리더
//   · NanoLog      — 컴파일 타임 분해 + 후처리 (연구/실험 성격)
//   · 사내 구현    — 거래 시스템에서 흔합니다
여기까지 오기 전에 확인할 것 — 바이너리 로깅은 운영 편의성을 크게 깎습니다. 장애 한가운데에서 grep 이 안 되는 로그는 생각보다 큰 손해입니다. “p99 지연 예산에서 로깅이 실제로 몇 %인가”를 먼저 재고, 한 자릿수 %라면 여기 오지 마세요.
정리 — 동기 파일 로깅 한 줄은 포맷 · 패턴 조립 · 잠금 · 시스템콜로 나뉘고, 자릿수로는 수백 ns 규모입니다. 줄이는 순서는 ① 안 찍기 ② 덜 찍기 ③ 비동기 ④ 지연 포매팅이고, ①②에서 대부분 끝납니다. 잴 때는 스레드 수를 바꿔 가며 p99 를 보세요 — 단일 스레드 평균은 로깅에서 가장 쓸모없는 숫자입니다.
