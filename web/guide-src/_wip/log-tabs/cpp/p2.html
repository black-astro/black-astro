LOG 03

spdlog 실전 — 싱크를 조합하면 로거가 완성됩니다

spdlog 의 구조는 한 문장입니다 — 로거 하나에 싱크 여러 개를 묶고, 싱크마다 레벨과 포맷을 따로 준다. 이 한 문장만 잡으면 설치부터 운영 설정까지 30분이면 끝납니다.

허브 구조 — 로거는 하나, 목적지는 여럿. 목적지를 늘려도 호출부는 그대로입니다.

설치 — 세 가지 길

# ① vcpkg — 윈도우·리눅스 모두 이게 가장 편합니다
vcpkg add port spdlog          # vcpkg.json 매니페스트에 추가
# 또는 클래식 모드
vcpkg install spdlog

# ② Conan
conan install --requires="spdlog/[>=1.15]" --build=missing

# ③ 헤더온리 — 파일만 복사해도 돕니다
git clone --depth 1 https://github.com/gabime/spdlog.git
#   spdlog/include/ 를 인클루드 경로에 추가하면 끝입니다
#   (내부의 {fmt} 도 같이 들어 있어 별도 의존성이 없습니다)
# CMakeLists.txt — vcpkg / Conan / 시스템 설치 공통
find_package(spdlog CONFIG REQUIRED)
target_link_libraries(app PRIVATE spdlog::spdlog)

# 헤더온리로 쓰고 싶다면 (빌드는 느려지지만 링크가 없습니다)
# target_link_libraries(app PRIVATE spdlog::spdlog_header_only)
어느 길을 고르나 — 팀 프로젝트면 vcpkg 매니페스트(vcpkg.json)가 재현성이 가장 좋습니다. CI 가 없는 개인 도구라면 헤더온리 복사가 가장 빠릅니다. 둘을 섞지는 마세요 — 같은 심볼이 두 번 들어가 링크가 깨집니다.

가장 짧은 시작 — 세 줄

#include <spdlog/spdlog.h>

int main() {
    spdlog::info("서버 시작 port={}", 8080);
    spdlog::warn("커넥션 재시도 {}회", 3);
    spdlog::error("주문 {} 처리 실패: {}", 8812, "timeout");
}
// 기본 로거가 콘솔(색)로 나갑니다. 설정이 하나도 필요 없습니다.

// 레벨은 여섯 단계 + off
//   trace < debug < info < warn < error < critical
spdlog::set_level(spdlog::level::debug);   // 런타임 전역 컷오프

// 포맷은 {fmt}/std::format 과 완전히 같습니다
spdlog::info("{:>8} {:.2f} {:#x}", "쓰기", 3.14159, 255);
//        →      쓰기 3.14 0xff
파이썬과 비교하면 — logging.info(...) 와 자리가 같습니다. 다른 점은 포맷이 %s 가 아니라 {} 이고, 인자 평가가 레벨 검사보다 먼저 일어난다는 것입니다(그래서 lg04 의 매크로 이야기가 나옵니다).

한 단계 더 — 싱크 조합과 패턴 문자열 🟡 중급

실제로 쓰는 설정 한 덩어리 ★

#include <spdlog/spdlog.h>
#include <spdlog/sinks/stdout_color_sinks.h>
#include <spdlog/sinks/rotating_file_sink.h>

void init_logging(const std::string& name) {
    // ① 콘솔 — 사람이 볼 것만
    auto console = std::make_shared<spdlog::sinks::stdout_color_sink_mt>();
    console->set_level(spdlog::level::info);
    console->set_pattern("%^[%T] [%l]%$ %v");        // 짧게

    // ② 파일 — 나중에 뒤질 것까지 전부
    //    5 MB 넘으면 회전 · 파일 3개 보존
    auto file = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
        "logs/app.log", 5 * 1024 * 1024, 3);
    file->set_level(spdlog::level::debug);
    file->set_pattern("[%Y-%m-%d %H:%M:%S.%e] [%n] [%l] [%t] [%s:%#] %v");

    // ③ 둘을 한 로거에 묶습니다
    auto lg = std::make_shared<spdlog::logger>(
        name, spdlog::sinks_init_list{console, file});

    lg->set_level(spdlog::level::debug);   // ★ 로거 레벨이 먼저 걸립니다
    lg->flush_on(spdlog::level::err);      // error 이상은 즉시 디스크로
    spdlog::set_default_logger(lg);
    spdlog::flush_every(std::chrono::seconds(3));   // 나머지는 3초마다
}
레벨은 두 번 걸립니다 — 로거 레벨을 먼저 통과해야 싱크로 갑니다. 로거가 info 인데 파일 싱크만 debug 로 두면 debug 는 아무 데도 안 나옵니다. 가장 흔한 착각입니다 — 로거는 가장 낮게, 싱크에서 조입니다.

패턴 문자열 — 외울 것은 열 개뿐

토큰나오는 것
%Y-%m-%d2026-09-01
%T / %H:%M:%S14:23:41
%e / %f / %F밀리 / 마이크로 / 나노초
%l / %Linfo / I (레벨)
%n로거 이름
%t / %P스레드 ID / 프로세스 ID
%s %# %!파일 / 줄 / 함수 (매크로에서만)
%v메시지 본문 ★ 필수
%^ … %$색 입힐 구간 (콘솔 전용)
%%퍼센트 문자 자체
운영에서 쓰는 무난한 한 줄
[%Y-%m-%d %H:%M:%S.%e] [%n] [%l] [%t] [%s:%#] %v

  → [2026-09-01 14:23:41.271] [order] [info] [18244]
    [order.cpp:142] paid orderId=8812 amt=45900

★ %s %# 는 SPDLOG_INFO 같은 매크로로 부를 때만 채워집니다.
  spdlog::info(...) 로 부르면 빈칸이 됩니다 (lg04)

실무에선 이렇게 — 여러 모듈이 각자의 로거를 갖게 🔴 실무

이름 있는 로거와 레지스트리

// 모듈마다 로거를 따로 두면 "누가 시끄러운지"를 끌 수 있습니다
auto db  = std::make_shared<spdlog::logger>("db",  file);
auto net = std::make_shared<spdlog::logger>("net", file);
spdlog::register_logger(db);
spdlog::register_logger(net);

// 어디서든 이름으로 꺼냅니다 (해시 조회 — 핫 패스에서는 캐시하세요)
auto lg = spdlog::get("db");
lg->debug("쿼리 {} ms", 12);

// 환경 변수 한 줄로 레벨을 바꿀 수 있습니다
//   SPDLOG_LEVEL="info,db=trace,net=off" ./app
spdlog::cfg::load_env_levels();     // #include <spdlog/cfg/env.h>

// 종료 전에 반드시 — 비동기든 동기든 버퍼가 남아 있습니다
spdlog::shutdown();
SPDLOG_LEVEL 환경 변수는 운영에서 대단히 유용합니다 — 재빌드도 재배포도 없이 특정 모듈만 trace 로 올려 재현할 수 있습니다. 컨테이너라면 환경 변수 하나 바꿔 다시 띄우면 끝입니다.

내 타입을 그대로 찍기 — formatter

#include <spdlog/fmt/ostr.h>    // operator<< 를 쓰려면 필요

struct OrderId { long v; };

// ★ 권장 — std::formatter 특수화 (C++20 / {fmt} 공통)
template <>
struct fmt::formatter<OrderId> : fmt::formatter<std::string> {
    auto format(OrderId o, format_context& ctx) const {
        return fmt::format_to(ctx.out(), "ord#{}", o.v);
    }
};

spdlog::info("결제 {}", OrderId{8812});     // → 결제 ord#8812

// 컨테이너도 그냥 됩니다
#include <spdlog/fmt/ranges.h>
std::vector<int> v{1, 2, 3};
spdlog::info("남은 재시도 {}", v);          // → 남은 재시도 [1, 2, 3]
포맷 비용은 여기서 결정됩니다 — formatter 안에서 문자열을 새로 만들거나 락을 잡으면 그 비용이 로그 한 줄마다 붙습니다. 무거운 표현이 필요하면 레벨 검사가 통과했을 때만 만들도록 매크로를 쓰세요(lg04).
정리 — spdlog 는 로거 = 싱크의 묶음이라는 한 문장이 전부입니다. 콘솔은 info · 파일은 debug · 회전 5 MB × 3개 · error 는 즉시 flush — 이 네 줄이면 대부분의 서비스에서 그대로 씁니다. 패턴은 %v 만 필수이고, %s:%# 는 매크로로 부를 때만 채워집니다.
LOG 04

매크로냐 함수냐 — SPDLOG_INFO 가 필요한 진짜 이유

현대 C++ 는 매크로를 피하라고 가르칩니다. 그런데 로깅만은 예외입니다. 매크로만 할 수 있는 일 두 가지가 있고, 그 대가도 분명합니다.

결정 흐름도 — 지워야 하면 매크로. 그 외에는 함수가 언제나 더 안전합니다.

매크로만 할 수 있는 일 ① 소스 위치

spdlog::info("paid {}", id);
// → [info] paid 8812
//   %s:%# 는 빈칸입니다. 함수는 호출자의 위치를 모릅니다

SPDLOG_INFO("paid {}", id);
// → [info] [order.cpp:142] paid 8812
//   매크로가 __FILE__ · __LINE__ · __FUNCTION__ 을 끼워 넣습니다

// 매크로는 대략 이렇게 펼쳐집니다
#define SPDLOG_INFO(...) \
    SPDLOG_LOGGER_CALL(spdlog::default_logger_raw(), \
        spdlog::level::info, __VA_ARGS__)
//    → logger->log(spdlog::source_loc{__FILE__, __LINE__, \
//                  SPDLOG_FUNCTION}, level, __VA_ARGS__)
C++20 의 std::source_location 이 있는데? — 됩니다. 기본 인자로 std::source_location::current() 를 받으면 함수도 호출자 위치를 압니다. 다만 가변 인자 템플릿과 기본 인자를 같이 쓰려면 인자 팩을 감싸는 구조체가 하나 더 필요하고, 컴파일 타임 제거는 여전히 안 됩니다. spdlog 가 매크로를 유지하는 이유가 이 둘째 항목입니다.

매크로만 할 수 있는 일 ② 코드 삭제

// ★ spdlog.h 를 include 하기 "전에" 정의해야 합니다
#define SPDLOG_ACTIVE_LEVEL SPDLOG_LEVEL_INFO
#include <spdlog/spdlog.h>

SPDLOG_TRACE("행렬 {}", dump_matrix(m));   // ← 통째로 사라집니다
SPDLOG_DEBUG("캐시 상태 {}", cache.stats());// ← 통째로 사라집니다
SPDLOG_INFO("요청 완료 {}", id);            // ← 남습니다

// 사라진다 = dump_matrix(m) 호출 자체가 없어집니다.
// 함수 호출이었다면?
spdlog::trace("행렬 {}", dump_matrix(m));
//   레벨이 trace 가 아니어도 dump_matrix(m) 은 "먼저" 실행됩니다.
//   인자 평가가 레벨 검사보다 앞서기 때문입니다 ★

// 레벨 상수
//   SPDLOG_LEVEL_TRACE 0 · DEBUG 1 · INFO 2 · WARN 3
//   ERROR 4 · CRITICAL 5 · OFF 6
이게 성능 이야기의 절반입니다 — 운영에서 trace 를 끄면 포맷 비용만 사라지는 게 아니라 인자를 만드는 비용까지 사라집니다. dump_matrix() 가 1 ms 짜리라면, 함수 호출로 두었을 때 로그를 껐는데도 1 ms 를 계속 내는 상태가 됩니다.

한 단계 더 — 대가를 정확히 알고 쓰기 🟡 중급

매크로가 실제로 일으키는 사고

// ① 이름 충돌 — 매크로는 전처리기라 네임스페이스가 없습니다
#include <windows.h>
//   windows.h 가 ERROR 를 #define 합니다
SPDLOG_LOGGER_ERROR(lg, "...");     // 운 나쁘면 여기서 깨집니다
//   처방: #define NOMINMAX 와 #define WIN32_LEAN_AND_MEAN,
//         그리고 필요하면 #undef ERROR

// ② 인자가 두 번 평가될 수 있습니다 (매크로 구현에 따라)
SPDLOG_INFO("count={}", counter++);  // ★ 이런 코드는 절대 쓰지 마세요

// ③ 조건문에 알몸으로 넣지 않기
if (x) SPDLOG_INFO("a"); else SPDLOG_INFO("b");   // 위험
if (x) { SPDLOG_INFO("a"); } else { SPDLOG_INFO("b"); }   // ★ 항상 중괄호

// ④ 디버거에서 스텝이 이상하게 튑니다 — 한 줄이 여러 문장이라
// ⑤ 컴파일 에러 메시지가 펼쳐진 코드 기준으로 나옵니다

그래서 실무의 답은 “감싸기”

// log.h — 프로젝트 전용 얇은 헤더 하나를 둡니다
#pragma once
#define SPDLOG_ACTIVE_LEVEL SPDLOG_LEVEL_TRACE   // 빌드 타입별로 조정
#include <spdlog/spdlog.h>

// 접두사를 붙여 충돌을 줄이고, 라이브러리 교체 여지를 남깁니다
#define MYAPP_TRACE(...) SPDLOG_TRACE(__VA_ARGS__)
#define MYAPP_DEBUG(...) SPDLOG_DEBUG(__VA_ARGS__)
#define MYAPP_INFO(...)  SPDLOG_INFO(__VA_ARGS__)
#define MYAPP_WARN(...)  SPDLOG_WARN(__VA_ARGS__)
#define MYAPP_ERROR(...) SPDLOG_ERROR(__VA_ARGS__)
# 빌드 타입별로 컴파일 타임 레벨을 다르게
target_compile_definitions(app PRIVATE
  $<$<CONFIG:Debug>:SPDLOG_ACTIVE_LEVEL=SPDLOG_LEVEL_TRACE>
  $<$<CONFIG:Release>:SPDLOG_ACTIVE_LEVEL=SPDLOG_LEVEL_INFO>)
# ★ log.h 안의 #define 과 중복되면 경고가 납니다 —
#   둘 중 한 곳에서만 정의하세요. CMake 쪽을 권합니다.
감싸면 무엇이 좋은가 — 3년 뒤 spdlog 를 quill 로 바꿀 때 고칠 파일이 log.h 하나가 됩니다. 수천 곳의 호출부를 찾아 고치는 일과 비교하면 이 다섯 줄이 아주 쌉니다.
정리 — 매크로가 필요한 이유는 딱 둘입니다 — 호출자의 파일·줄 번호를 넣는 것과 Release 에서 코드를 통째로 지우는 것. 대가는 네임스페이스 없음 · 이름 충돌 · 디버깅 불편입니다. 실무의 답은 프로젝트 접두사를 붙인 얇은 log.h 하나로 감싸는 것이고, SPDLOG_ACTIVE_LEVEL 은 CMake 에서 빌드 타입별로 주는 것이 안전합니다.
