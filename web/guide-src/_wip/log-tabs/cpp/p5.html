LOG 09

멀티프로세스와 fork — 로그가 사라지는 자리 세 곳

스레드는 잘 다뤘는데 프로세스를 여러 개 띄우는 순간 로그가 조용히 없어지거나, 두 번 나오거나, 토막이 섞입니다. 원인은 셋뿐입니다 — fork 는 스레드를 복사하지 않는다 · stdio 버퍼는 복사된다 · 파일 하나에 여럿이 쓴다. 셋 다 코드가 아니라 운영체제 규칙이라, 알고 나면 처방이 한 줄입니다.

스윔레인 — 자식 레인에는 백엔드 스레드가 없습니다. 큐에 넣은 줄은 파일 레인에 닿지 못합니다.

사고 ① — fork 뒤 비동기 로그가 사라진다

#include <spdlog/spdlog.h>
#include <spdlog/async.h>
#include <spdlog/sinks/basic_file_sink.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    spdlog::init_thread_pool(8192, 1);            // 백엔드 스레드 1개
    auto lg = spdlog::create_async<spdlog::sinks::basic_file_sink_mt>(
        "app", "logs/app.log");
    lg->info("부모: 시작");

    pid_t pid = fork();
    if (pid == 0) {
        // 자식 — 메모리는 통째로 복사됐지만 스레드는 fork 를 부른 하나뿐입니다
        // 큐도 복사됐고, 큐를 비우던 백엔드 스레드는 "없습니다"
        lg->info("자식: 이 줄은 큐에 들어가고 끝입니다");   // ★ 유실
        _exit(0);   // exit() 를 쓰면 부모가 등록한 atexit 훅이 자식에서도 돕니다
    }
    waitpid(pid, nullptr, 0);
    lg->info("부모: 자식 종료");
    spdlog::shutdown();
}
POSIX 가 정한 규칙입니다 — fork() 는 호출한 스레드 하나만 자식으로 가져갑니다. 다른 스레드가 잡고 있던 뮤텍스는 잠긴 채로 복사되므로, 자식에서 그 뮤텍스를 잡으면 영원히 멈춥니다. 비동기 로거의 큐 뮤텍스가 바로 그 뮤텍스입니다 — 유실이 아니라 데드락으로 나타나기도 합니다.

처방 — 세 가지 중 하나를 고릅니다

// ① 자식에서 로거를 새로 만든다 (가장 정직한 방법)
if (pid == 0) {
    spdlog::drop_all();                       // 복사된 로거를 전부 버리고
    spdlog::init_thread_pool(1024, 1);        // 백엔드 스레드를 자식에서 새로
    auto clg = spdlog::create_async<spdlog::sinks::basic_file_sink_mt>(
        "child", std::format("logs/app-{}.log", getpid()));
    clg->info("자식: 새 로거로");
    // ...
    spdlog::shutdown(); _exit(0);
}

// ② 자식은 exec() 만 한다 — 로거를 아예 안 부릅니다
if (pid == 0) { execl("/usr/bin/worker", "worker", nullptr); _exit(127); }
//    posix_spawn() 을 쓰면 fork 와 exec 사이의 위험 구간이 없습니다 ★

// ③ pthread_atfork 로 자동화 — 자식 쪽 훅에서 로거를 재생성
pthread_atfork(
    /*prepare*/ []{ spdlog::default_logger()->flush(); },
    /*parent */ nullptr,
    /*child  */ []{ spdlog::drop_all(); /* 동기 로거로 다시 만들기 */ });
파이썬의 multiprocessing 이 겪은 것과 같은 문제입니다 — 그래서 파이썬은 3.14 부터 기본 시작 방식을 fork 에서 forkserver 로 바꿨습니다. C++ 에서도 답은 같습니다 — 스레드가 있는 프로세스에서 fork 하지 말고, 해야 한다면 곧바로 exec 하세요.

한 단계 더 — 버퍼 복사와 파일 공유 🟡 중급

사고 ② — 같은 줄이 두 번 나온다

#include <cstdio>
#include <unistd.h>

int main() {
    printf("시작\n");          // 터미널이면 줄 단위 flush → 바로 나갑니다
    // 파일이나 파이프로 리다이렉션되면? 완전 버퍼링 → 아직 메모리에만 있습니다
    fork();
    // 부모와 자식 "둘 다" 버퍼에 "시작\n" 을 갖고 있습니다
    return 0;                  // 각자 exit 하며 flush → "시작" 이 두 번 ★
}
// ./a.out            → 시작 (한 번)
// ./a.out > out.txt  → 시작 시작 (두 번)

// 처방 — fork 직전에 전부 비웁니다
fflush(nullptr);               // 열려 있는 모든 FILE* 을 flush
pid_t pid = fork();

// spdlog 도 같습니다 — 파일 싱크는 FILE* 위에 있습니다
spdlog::default_logger()->flush();   // fork 직전
// 그리고 자식에서는 _exit() — atexit 훅(shutdown → flush)을 건너뜁니다
"터미널에서는 안 나던 버그가 서비스로 올리니 난다"의 대표 사례입니다. isatty() 가 거짓이면 stdio 는 완전 버퍼링(보통 4 KB)으로 바뀝니다. systemd · 컨테이너 · nohup 전부 이 조건입니다.

사고 ③ — 파일 하나에 여러 프로세스가 쓴다

방식줄이 섞이나회전은
프로세스마다 다른 파일안 섞임각자 회전 — 가장 안전
한 파일 · O_APPENDwrite() 한 번은 통째로. 줄이 write 경계에 걸치면 섞임한 프로세스만 회전해야 함
syslog · journald안 섞임 (단일 수신자)시스템이 함
부모에게 파이프안 섞임 (부모가 한 줄씩)부모가 함
Windows 한 파일섞임 + rename 실패회전이 깨짐
// 파일 이름에 PID — 가장 싸고 확실한 처방 (lg07 에서 예고한 것)
auto path = std::format("logs/app-{}.log", getpid());     // POSIX
// Windows: GetCurrentProcessId()
auto sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    path, 50 * 1024 * 1024, 5);

// 왜 O_APPEND 만으로는 부족한가 —
//   spdlog 파일 싱크는 fwrite() 로 stdio 버퍼에 쌓았다가 write() 합니다.
//   한 줄이 버퍼 경계에 걸치면 write() 가 두 번 → 그 사이에 남이 끼어듭니다.
//   (NFS 는 O_APPEND 원자성 자체를 보장하지 않습니다)

실무에선 이렇게 — 시스템 로거에 맡기기 🔴 실무

syslog · journald · Windows 이벤트 로그

// ① syslog — 어느 유닉스에나 있습니다. 프로세스가 몇 개든 한 곳으로
#include <spdlog/sinks/syslog_sink.h>
auto sl = spdlog::syslog_logger_mt("app", "myapp", LOG_PID);
sl->warn("워커 {} 재시작", getpid());

// ③ Windows 이벤트 로그 — 서비스라면 관리자가 여기를 봅니다

prefork 서버라면 — nginx 가 하는 방식

마스터 프로세스 (스레드 없음 · 로거는 동기)
  ├─ 워커 1  ─┐
  ├─ 워커 2  ─┼─ 각자 access-<pid>.log 에 동기로 씁니다
  └─ 워커 N  ─┘   (또는 마스터가 만든 한 fd 를 공유 + O_APPEND + 한 줄 = write 한 번)

규칙
  · 마스터는 fork 하기 "전"에 스레드를 만들지 않습니다
  · 워커는 fork 직후 자기 로거를 새로 만듭니다 (필요하면 그때 비동기)
  · 회전은 마스터가 SIGUSR1 을 받아 워커에게 "파일 다시 열어라" 를 전달
    → nginx -s reopen 이 바로 이것입니다
  · 보는 쪽은 여러 파일을 합쳐서 봅니다:  tail -f logs/access-*.log
    또는 수집기가 합칩니다 (lg10)
Windows 에는 fork 가 없습니다 — CreateProcess 는 새 프로세스를 처음부터 만들므로 사고 ①②는 없지만, 사고 ③이 더 심합니다. 다른 프로세스가 열어 둔 파일은 이름을 바꿀 수 없어 회전이 조용히 실패합니다. 프로세스별 파일 이름이 선택이 아니라 필수입니다.
정리 — 멀티프로세스 로깅 사고는 셋입니다 — fork 가 스레드를 안 가져가서 비동기 큐가 멈추고, stdio 버퍼가 복사돼 줄이 두 번 나오고, 한 파일에 여럿이 써서 줄이 섞입니다. 처방은 fork 직전 flush · 자식은 exec 하거나 로거를 새로 · 프로세스별 파일 이름이고, 프로세스가 많으면 syslog · journald 에 맡기는 것이 가장 편합니다.

컨테이너와 수집기 — stdout 에 쓰고 나머지는 바깥에 맡기기

컨테이너에서는 파일 로깅의 전제가 무너집니다 — 컨테이너가 사라지면 파일도 사라지고, 노드가 100대면 파일도 100곳에 흩어집니다. 그래서 규칙이 뒤집힙니다: 앱은 stdout 에 한 줄씩 쓰고, 회전 · 수집 · 저장 · 검색은 전부 바깥의 일입니다. 이 절은 그 "바깥"이 무엇으로 이루어졌는지, 앱이 어디까지만 책임지면 되는지를 정합니다.

레이어 스택 — 앱의 책임은 맨 위 한 층뿐. 아래 다섯 층은 바꿔 끼워도 앱은 모릅니다.

컨테이너용 로거 설정 — 파일 대신 stdout

#include <spdlog/spdlog.h>
#include <spdlog/sinks/stdout_sinks.h>
#include <spdlog/sinks/stdout_color_sinks.h>
#include <unistd.h>

void init_container_logging() {
    std::shared_ptr<spdlog::sinks::sink> sink;
    if (isatty(STDOUT_FILENO)) {
        // 개발자가 docker run -it 로 볼 때 — 색 있는 사람용 포맷
        sink = std::make_shared<spdlog::sinks::stdout_color_sink_mt>();
        sink->set_pattern("%^[%T] [%l]%$ %v");
    } else {
        // 수집기가 읽을 때 — 색 없음 · 한 줄 JSON
        sink = std::make_shared<spdlog::sinks::stdout_sink_mt>();
        sink->set_pattern(
            R"({"ts":"%Y-%m-%dT%H:%M:%S.%e%z","lvl":"%l","tid":%t,"src":"%s:%#","msg":"%v"})");
    }
    auto lg = std::make_shared<spdlog::logger>("app", sink);
    lg->set_level(spdlog::level::info);
    spdlog::set_default_logger(lg);
    // stdout 싱크는 줄마다 fflush 합니다 — 따로 flush_every 가 필요 없습니다
}
위 JSON 패턴에는 구멍이 하나 있습니다 — %v 는 이스케이프되지 않습니다. 메시지에 " 나 줄바꿈이 들어가면 그 줄은 JSON 이 아니게 되고 수집기가 버립니다. 메시지에 사용자 입력이 들어갈 수 있다면 lg11 의 방법(값을 필드로 빼기)을 쓰세요.

런타임 쪽 설정 — 회전은 여기서

# docker-compose.yml — json-file 드라이버에 상한을 줍니다
services:
  app:
    image: myapp:1.4.2
    logging:
      driver: json-file
      options:
        max-size: "10m"      # 파일 하나 10 MB
        max-file: "5"        # 5개 보존 → 컨테이너당 최대 50 MB
        tag: "{{.Name}}/{{.ImageName}}"

# 확인
#   docker inspect --format '{{.LogPath}}' <container>
#   docker logs --since 10m -f app
# Kubernetes — kubelet 이 회전합니다 (노드 설정)
# /var/lib/kubelet/config.yaml
containerLogMaxSize: 10Mi
containerLogMaxFiles: 5
# 로그 파일 위치: /var/log/pods/<ns>_<pod>_<uid>/<container>/0.log
# 수집기는 이 경로를 tail 합니다
상한을 안 주면 — Docker 의 json-file 기본값은 무제한입니다. 수개월 뒤 노드 디스크가 차서 모든 컨테이너가 한꺼번에 죽는 사고의 원인이 대개 이것입니다. 데몬 전체 기본값은 /etc/docker/daemon.json 의 log-opts 에 둡니다.

실무에선 이렇게 — 앱이 지켜야 할 것과 안 해도 되는 것 🔴 실무

컨테이너에서 하지 말 것
  • 컨테이너 안에 파일로 로깅 — 재시작하면 사라지고, 수집기는 못 봅니다
  • 앱 안에서 회전 — 런타임이 이미 합니다. 두 번 하면 둘 다 꼬입니다
  • 색 코드를 stdout 에 — 수집기가 \x1b[32m 을 본문으로 저장합니다
  • 한 사건을 여러 줄로 — 스택 트레이스는 줄마다 다른 레코드가 됩니다
  • 블록 정책의 비동기 큐 — stdout 파이프가 막히면 앱 전체가 멈춥니다(lg05)
대신 이렇게
  • stdout 동기 로거 — 파이프 쓰기는 이미 충분히 빠릅니다
  • 한 줄 = 한 JSON — 스택 트레이스는 \n 을 이스케이프해 한 줄에
  • 파일이 꼭 필요하면 emptyDir 볼륨 + 사이드카 tail
  • 레벨은 환경 변수로 — SPDLOG_LEVEL 을 ConfigMap 에서(lg03)
  • SIGTERM 을 받으면 flush 하고 종료 — 마지막 줄이 살아남습니다
// SIGTERM → 정상 종료 → 마지막 로그까지 내보내기
#include <csignal>
#include <atomic>
static std::atomic<bool> g_stop{false};

int main() {
    init_container_logging();
    std::signal(SIGTERM, [](int){ g_stop = true; });   // 핸들러에서는 플래그만 (lg08)

    while (!g_stop) { serve_once(); }

    spdlog::info("SIGTERM 수신 — 정리 후 종료");
    spdlog::shutdown();      // stdout 은 즉시 flush 되지만 습관으로 둡니다
    return 0;
}
// 쿠버네티스는 SIGTERM 뒤 terminationGracePeriodSeconds(기본 30초) 를 기다리고 SIGKILL 합니다.
// 30초 안에 못 끝내면 남은 로그는 그냥 사라집니다.
사이드카는 마지막 수단입니다 — 컨테이너마다 수집기를 하나씩 붙이면 메모리와 설정이 파드 수만큼 늘어납니다. 노드당 데몬셋 하나가 기본이고, 사이드카는 파일로만 로그를 남기는 남의 바이너리를 감쌀 때만 씁니다.
정리 — 컨테이너에서 앱의 로깅 책임은 stdout 에 한 줄 JSON 을 동기로 쓰는 것까지입니다. 회전은 런타임(json-file · kubelet), 수집은 노드당 데몬셋(Fluent Bit · Vector · Alloy), 저장은 Loki 또는 Elasticsearch, 조회는 Grafana · Kibana · SaaS 가 맡습니다. 요금은 하루 용량 × 보존 일수이고, 줄이는 첫걸음은 언제나 운영에서 debug 끄기입니다.
