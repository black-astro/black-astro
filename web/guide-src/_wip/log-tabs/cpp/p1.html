파이썬은 import logging, 자바는 SLF4J, C# 은 ILogger 가 언어와 함께 옵니다. C++ 는 표준 라이브러리에 로거가 없습니다. C++23 이 std::print 를 넣었지만 그것은 출력이지 로깅이 아닙니다 — 레벨도, 싱크도, 회전도, 비동기도 없습니다. 그래서 C++ 프로젝트는 예외 없이 바깥에서 로거를 골라 붙입니다. 이 탭은 무엇을 고르고 · 어떻게 붙이고 · 얼마를 치르는지를 다룹니다. 끝나면 서비스가 죽어도 원인이 로그에 남는 상태를 만들 수 있게 됩니다.

LOG 01

표준에 로거가 없다 — std::cout 이 로거가 아닌 이유

“일단 cout 으로 찍자”는 거의 모든 C++ 프로젝트의 출발점이고, 거의 모든 프로젝트가 같은 자리에서 막힙니다. 무엇이 부족한지 정확히 알아야 어떤 라이브러리를 고를지도 정해집니다.

로그 한 줄 해부 — 여섯 칸을 자동으로 채워 주는 것이 로거의 정체입니다.

cout 으로 버티면 이렇게 됩니다

#include <iostream>
#include <chrono>
#include <thread>

void pay(int id, int amt) {
    auto now = std::chrono::system_clock::now();
    std::cout << "[" << now << "] "        // 포맷은 내 마음대로
              << "[info] "                    // 레벨? 그냥 글자입니다
              << "[tid " << std::this_thread::get_id() << "] "
              << "paid orderId=" << id
              << " amt=" << amt << "\n";
}
// 문제 ①  이 여섯 줄을 호출부마다 복사합니다
// 문제 ②  << 는 연산자 호출이 여러 번 — 그 사이에
//          다른 스레드가 끼어들어 줄이 섞입니다
// 문제 ③  운영에서 debug 를 끄려면? if 문을 손으로 답니다
// 문제 ④  파일로 보내려면? 리다이렉션 말고는 방법이 없습니다
줄이 섞인다는 게 무슨 뜻인가 — std::cout 자체는 데이터 경합을 일으키지는 않습니다(C++11 이후 표준 스트림은 동기화됩니다). 하지만 한 문장이 아니라 여러 번의 << 호출이라 [info] paid orderId=[info] paid orderId=88128813 같은 결과가 실제로 나옵니다. 버그를 쫓는 그 순간에 로그가 못 쓰게 되는 것이 가장 나쁜 실패입니다.

printf 는 나은가 — 반은 맞습니다

#include <cstdio>

printf("[info] paid orderId=%d amt=%d\n", id, amt);
// 좋은 점 : 한 번의 호출 → 줄이 통째로 나갑니다
//           (POSIX 는 FILE* 단위 잠금을 보장합니다)
// 나쁜 점 : 타입 검사가 없습니다

printf("%d\n", "여덟 글자");   // 경고만 나거나, 그냥 터집니다
printf("%s\n", 42);            // UB — 42 를 포인터로 읽습니다

// std::string 은 아예 못 넘깁니다
std::string s = "hi";
printf("%s\n", s);             // ★ UB. .c_str() 을 붙여야 합니다

// 그리고 여전히 — 레벨도, 파일 출력도, 회전도 없습니다
왜 아직도 printf 를 쓰나 — 시그널 핸들러 안(정확히는 write(2))과 커널·임베디드처럼 C++ 런타임을 못 쓰는 자리에서는 여전히 이쪽입니다. lg08 크래시 로그에서 다시 만납니다.

한 단계 더 — std::print 이 바꾼 것과 바꾸지 못한 것 🟡 중급

C++23 std::print — 출력의 정답

#include <print>      // C++23
#include <string>

int id = 8812; std::string user = "kim";

std::println("paid orderId={} user={}", id, user);
// → paid orderId=8812 user=kim

// ★ 바꾼 것 세 가지
//   ① 타입 안전   — 포맷 문자열이 컴파일 타임에 검사됩니다
//   ② std::string 을 그냥 넘깁니다 (.c_str() 불필요)
//   ③ 한 번에 만들어 한 번에 내보냅니다 — << 처럼
//      토막나 섞이는 일이 크게 줄어듭니다

std::print(stderr, "[warn] 재시도 {}회\n", n);   // 스트림 지정도 됩니다

// 컴파일러 지원(2026년 8월 기준) — GCC 14+ · Clang 18+ · MSVC 최신
//   아직 안 되면 {fmt} 를 그대로 쓰면 됩니다. API 가 같습니다
//   #include <fmt/core.h>  →  fmt::println("...{}", x);

그런데 이건 로깅이 아닙니다

필요한 것std::print로거
타입 안전 포맷있음있음
레벨 (trace~critical)없음있음
운영에서 레벨 끄기없음런타임 · 컴파일 타임
파일 · 여러 목적지없음싱크 조합
파일 회전 · 보존없음있음
시각 · 스레드 자동 첨부없음패턴 한 줄
소스 파일 · 줄 번호없음매크로가 넣어 줌
비동기 (호출 지연 분리)없음있음
정리하면 — std::print 는 로거의 재료입니다. 실제로 spdlog·quill 이 내부에서 쓰는 {fmt} 가 표준에 들어간 것이 std::format·std::print 이고, 그 위에 레벨·싱크·회전·비동기를 얹은 것이 로거입니다.

실무에선 이렇게 — 직접 만들면 어디까지 가나 🔴 실무

30줄짜리 “내 로거” — 그리고 남는 숙제

#include <print>
#include <mutex>
#include <chrono>
#include <source_location>      // C++20

enum class Lv { trace, debug, info, warn, error, critical };
inline Lv g_level = Lv::info;
inline std::mutex g_mu;

template <class... A>
void log_at(Lv lv, std::source_location loc,
            std::format_string<A...> f, A&&... a) {
    if (lv < g_level) return;                      // 레벨 필터
    auto msg = std::format(f, std::forward<A>(a)...);
    std::lock_guard lk(g_mu);                       // 줄 섞임 방지
    std::println("[{:%F %T}] [{}] [{}:{}] {}",
        std::chrono::floor<std::chrono::milliseconds>(
            std::chrono::system_clock::now()),
        int(lv), loc.file_name(), loc.line(), msg);
}

// 호출부에서 source_location 을 자동으로 잡으려면 매크로가 필요합니다
#define LOG_INFO(...) log_at(Lv::info, std::source_location::current(), __VA_ARGS__)

LOG_INFO("paid orderId={} amt={}", 8812, 45900);
여기서 멈추면 겪는 일
  • 잠금 하나로 전체 직렬화 — 스레드 16개가 로그 한 줄에서 줄을 섭니다
  • 파일에 쓰면 매번 시스템콜 — 한 줄에 수 µs 가 그냥 날아갑니다
  • 회전이 없습니다 — 새벽에 디스크가 차서 서비스가 죽습니다
  • debug 로그가 Release 에도 남습니다 — 문자열 포맷 비용은 그대로
  • 크래시 순간 버퍼에 남은 줄이 통째로 사라집니다
라이브러리가 이미 해 둔 것
  • 싱크별 잠금 · 락 프리 큐로 호출 스레드를 놓아줍니다
  • 버퍼링 + 주기적 flush — 시스템콜을 수백 줄에 한 번으로
  • 크기·날짜 기준 회전과 보존 개수가 기본 제공
  • SPDLOG_ACTIVE_LEVEL 로 코드 자체를 지웁니다(lg04)
  • 종료·시그널 시 flush 훅이 걸려 있습니다
직접 만들지 말라는 뜻은 아닙니다 — 위 30줄은 사내 툴·과제·임베디드에서는 충분합니다. 다만 여러 스레드가 초당 수만 줄을 쓰는 서버에 그대로 올리면 로깅이 병목이 되어 “로그를 끄면 빨라지는” 상태가 됩니다. 그 선을 넘는 순간이 라이브러리를 붙일 때입니다.
정리 — C++ 표준은 출력까지만 줍니다(std::print). 레벨 · 싱크 · 회전 · 비동기 · 소스 위치는 전부 바깥에서 가져와야 합니다. cout 은 줄이 섞이고, printf 는 타입이 안 맞고, 직접 만든 로거는 잠금 하나에 전부 줄을 서게 됩니다 — 이 셋이 라이브러리를 고르게 만드는 이유입니다.
LOG 02

라이브러리 여섯 개 — 무엇을 어떤 상황에 고르나

C++ 로깅 라이브러리는 많지만 실제로 후보에 오르는 것은 여섯 개쯤입니다. 성능 · 헤더온리 여부 · 비동기 · 기능 폭 · 채택 정도 · 관리 상태 여섯 축으로 한 번에 보고, 그다음 “내 상황이면 무엇인가”를 정합니다.

라이브러리 히트맵 — spdlog 는 넓게 무난하고, quill 은 지연 한 곳에 몰아넣은 모양입니다.

여섯 개, 한 줄 요약

이름이럴 때 고릅니다
spdlog기본값. 고민할 이유가 없으면 이것. {fmt} 기반 · 헤더온리도 컴파일드도 됨
quill지연이 돈인 곳. 거래·게임 서버. 호출 스레드에서 포맷을 아예 안 합니다
glog구글계 코드베이스(gRPC·Ceph·Caffe 계열)와 붙을 때. 신규 채택은 드묾
Boost.Log이미 Boost 를 크게 쓰고 필터·속성 표현식이 필요할 때
log4cplus자바 log4j 설정 파일을 그대로 옮겨야 할 때
Easylogging++헤더 하나만 떨궈야 하는 작은 도구·과제
고민을 3초로 줄이는 규칙 — 서버·게임·데스크톱이면 spdlog, p99 지연을 µs 단위로 재는 곳이면 quill, 그 밖에는 “왜 spdlog 가 아닌가”를 먼저 답해 보세요. 대부분 답이 안 나옵니다.

정리 — 후보는 여섯이지만 실질적인 선택은 spdlog(기본) 대 quill(저지연) 둘입니다. glog·Boost.Log·log4cplus 는 이미 그것을 쓰는 코드에 들어갈 때, Easylogging++ 는 헤더 하나만 떨궈야 할 때가 이유입니다. 채택 정도는 숫자를 외우지 말고 추이를 직접 확인하세요 — star-history · vcpkg · Conan Center 세 곳이면 충분합니다.
