로그는 서비스가
자기 자신에 대해
말할 수 있는 유일한 방법입니다

러스트에는 표준 로깅이 없습니다. 표준 라이브러리가 주는 것은 println! 과 eprintln! 뿐이고, 그 둘로는 운영에서 하루도 못 버팁니다. 대신 생태계가 두 겹으로 나뉜 해법을 만들었습니다 — 라이브러리가 부르는 얇은 파사드(log)와 실행 파일이 딱 한 번 고르는 구현체(env_logger·fern 등), 그리고 비동기 시대에 맞춰 “점”이 아니라 “구간”을 기록하는 tracing 입니다. 이 탭은 그 전부를 왜 이렇게 됐는지부터 설명하고, 레이어 합성 · JSON 구조적 로깅 · 파일 로테이션 · 성능 · OpenTelemetry · 패닉 · 임베디드까지 이어 갑니다. 이 탭을 마치면 새 프로젝트의 init_log() 를 남의 코드를 베끼지 않고 직접 쓸 수 있습니다.

LOG 01

println! 로 시작해서 반드시 막히는 곳 — 무엇이 없는가

누구나 println!("여기까지 왔다") 로 시작합니다. 그리고 누구나 같은 자리에서 막힙니다. 끌 수가 없고, 언제 어디서 났는지 모르고, 컨테이너에서 사라지고, 느립니다. 이 네 가지가 로깅 크레이트가 존재하는 이유 전부입니다.

둘의 차이는 편의가 아닙니다 — 끌 수 있는가, 찾을 수 있는가가 다릅니다.

① 끌 수가 없습니다

// 디버깅하다 넣은 한 줄. 지우는 걸 잊습니다
for row in &rows {
    println!("row = {row:?}");     // 100만 건이면 100만 줄
}

// 임시방편으로 이렇게들 합니다 — 그리고 이게 늘어납니다
if std::env::var("DEBUG").is_ok() {
    println!("row = {row:?}");
}
// 조건이 실행 시점마다 평가되고, {row:?} 는 조건과 무관하게
// 이미 포맷 인자로 준비됩니다(Debug 호출은 지연되지만 인자 참조는 남습니다)
// 로깅 크레이트라면 — 코드는 그대로, 끄고 켜는 건 바깥에서
log::debug!("row = {row:?}");      // 또는 tracing::debug!

// $ RUST_LOG=info  ./app     → 이 줄은 아예 실행되지 않습니다
// $ RUST_LOG=debug ./app     → 이 줄이 나옵니다
// 레벨이 안 맞으면 포맷 자체를 시작하지 않습니다 ★
핵심은 “지연 평가”입니다 — debug! 매크로는 먼저 레벨이 켜져 있는지 묻고, 꺼져 있으면 인자 포맷팅을 아예 하지 않습니다. println! 은 무조건 포맷합니다. 무거운 Debug 구현이 붙은 타입에서는 이 차이가 수십 배가 됩니다.

② stdout 은 잠금이 걸린 자원입니다

use std::io::Write;

// println! 이 실제로 하는 일 (개념적으로)
let stdout = std::io::stdout();
let mut lock = stdout.lock();      // ← 전역 뮤텍스를 잡습니다
writeln!(lock, "...").unwrap();
// 락 해제 + 줄바꿈마다 LineWriter 가 flush 합니다

// 스레드 8개가 동시에 println! 을 하면
//   8개가 같은 뮤텍스 앞에 줄을 섭니다 → 직렬화 지점이 생깁니다
// 비동기 런타임에서는 더 나쁩니다 —
//   워커 스레드가 블로킹 I/O 로 멈추면 그 위의 태스크가 전부 멈춥니다 ★
// 굳이 println! 을 써야 한다면 최소한 락을 한 번만 잡습니다
let mut out = std::io::stdout().lock();
for row in &rows {
    writeln!(out, "{row:?}")?;     // 매번 잠그지 않습니다
}
// 그래도 레벨·시각·구조는 여전히 없습니다
비동기에서 특히 위험합니다 — Tokio 워커 스레드는 보통 CPU 코어 수만큼입니다. 그 중 하나가 느린 터미널이나 파이프에 블로킹 쓰기를 하면 거기에 얹힌 태스크 전부가 대기합니다. tracing-appender 의 non_blocking 이 존재하는 이유가 이것입니다(LOG 08).

③ 컨테이너에서 로그가 사라지는 세 가지 이유 🟡 중급

버퍼링 · 종료 · 목적지

증상진짜 원인처방
마지막 몇 줄이 없다프로세스가 버퍼를 비우기 전에 죽음워커 guard 유지 · flush()
한참 뒤에 몰려 나온다파이프에 붙으면 블록 버퍼링줄 단위 flush 또는 로거 사용
아무것도 안 보인다stdout 이 아니라 stderr 로 나감수집기 설정 확인 · 목적지 통일
JSON 이 깨진다여러 스레드의 줄이 섞임줄 단위 원자적 쓰기 로거
panic 만 안 남는다패닉은 로거를 거치지 않음set_hook (LOG 11)
12-Factor 원칙 — 컨테이너 안의 앱은 파일이 아니라 stdout 한 줄기로만 씁니다. 모으고 회전시키고 보관하는 일은 도커·쿠버네티스·수집기가 합니다. 예외는 임베디드·데스크톱 앱처럼 수집기가 없는 환경뿐입니다(LOG 08).

직접 확인해 보기

# stdout 이 터미널이면 줄 단위, 파이프면 블록 버퍼링입니다
./app                 # 실시간으로 보임
./app | cat           # 뭉쳐서 나옴 ← 이게 컨테이너 상황과 같습니다

# 도커에서 로그가 늦게 보이는지 확인
docker run --rm myapp 2>&1 | ts     # moreutils 의 ts 가 시각을 붙여 줍니다

# 쿠버네티스에서는 stdout·stderr 가 같은 곳으로 모입니다
kubectl logs -f deploy/myapp --timestamps

# 종료 직전 몇 줄이 날아가는지 재현
./app & sleep 0.2; kill -TERM %1     # SIGTERM 직후 남는 줄을 봅니다
가장 억울한 사고 — “장애가 났는데 마지막 로그가 없다”. 원인은 거의 항상 비동기 쓰기 버퍼가 안 비워진 것입니다. tracing-appender 를 쓸 때 WorkerGuard 를 살려 두는 것이 그래서 중요합니다.

④ 그래도 println! 이 맞는 자리 🔴 실무

로그가 아니라 “출력”일 때

// ① CLI 의 결과물 — 이건 로그가 아니라 프로그램의 출력입니다
//    파이프로 넘겨 쓰는 값이므로 stdout 이 맞습니다
println!("{}", total);

// ② 진행 상황 · 에러 안내는 stderr 로
eprintln!("입력 파일을 찾을 수 없습니다: {path}");

// 규칙 하나만 외우면 됩니다 ★
//   stdout = 다음 프로그램이 먹을 데이터
//   stderr = 사람이 읽을 말
//   로거   = 나중에 조사할 기록
// 이 셋을 섞으면 `./app | jq` 가 깨집니다
CLI 라면 clap 의 --verbose 를 로그 레벨로 이어 붙이는 것이 관례입니다. -v 는 info, -vv 는 debug, -vvv 는 trace — clap-verbosity-flag 크레이트가 이 매핑을 그대로 해 줍니다.

테스트에서의 출력 — 이것도 함정입니다

#[test]
fn t() {
    println!("여기");        // 통과하면 안 보이고, 실패해야 보입니다
    // cargo test -- --nocapture 로 항상 보이게 할 수 있습니다
}

// 로그를 테스트에서 보고 싶다면 — 전역 로거는 한 번만 설치됩니다
static INIT: std::sync::Once = std::sync::Once::new();
fn init_test_log() {
    INIT.call_once(|| {
        let _ = tracing_subscriber::fmt()
            .with_test_writer()      // ★ 테스트 캡처로 보냅니다
            .with_env_filter("debug")
            .try_init();             // init() 은 두 번째 호출에서 패닉
    });
}
init() 과 try_init() 의 차이 — 전역 로거는 프로세스당 한 번만 설치됩니다. 테스트는 같은 프로세스에서 여러 개가 도니 init() 을 쓰면 두 번째부터 패닉합니다. 테스트 코드에서는 반드시 try_init() 을 쓰세요.
정리 — println! 의 문제는 “느리다”가 아니라 끌 수 없고 찾을 수 없다는 것입니다. 로깅 크레이트가 주는 것은 딱 넷 — 레벨(끄기) · 메타데이터(언제·어디서) · 구조(찾기) · 비동기 쓰기(안 막기). stdout 은 프로그램의 출력, stderr 는 사람에게 하는 말, 로거는 나중에 조사할 기록입니다.
LOG 02

파사드 구조 — log 크레이트가 인터페이스만 정한 이유

라이브러리는 로그를 남기고 싶지, 로그를 어디로 보낼지 정하고 싶지 않습니다. 그 두 관심사를 갈라 놓은 것이 log 크레이트입니다 — 자바의 SLF4J + Logback 과 정확히 같은 두 겹 구조입니다.

라이브러리가 구현체를 고르면 앱이 두 개의 로거를 갖게 됩니다 — 그래서 파사드가 있습니다.

라이브러리 쪽 — log 만 의존합니다

# 내가 만드는 라이브러리 크레이트의 Cargo.toml
[dependencies]
log = "0.4"          # ★ 이것만. env_logger 를 넣으면 안 됩니다

# tracing 을 쓰는 라이브러리라면
# tracing = { version = "0.1", default-features = false, features = ["std"] }
// src/lib.rs — 매크로 5종이 전부입니다
pub fn parse(input: &str) -> Result<Doc, Error> {
    log::trace!("parse 시작, {} 바이트", input.len());

    if input.is_empty() {
        log::warn!("빈 입력이 들어왔습니다");
        return Err(Error::Empty);
    }
    log::debug!(target: "mylib::parser", "토큰 {}개", n);
    log::info!("문서 하나를 읽었습니다");
    log::error!("복구 불가: {e}");
    Ok(doc)
}
target: 이 무엇인가 — 기본값은 모듈 경로(mylib::parser)입니다. 이 문자열이 나중에 RUST_LOG 필터의 왼쪽이 됩니다. 직접 지정하면 모듈 구조와 무관하게 기능 단위로 껐다 켤 수 있습니다.

실행 파일 쪽 — 구현체를 딱 한 번

# 실행 파일(bin) 의 Cargo.toml
[dependencies]
log = "0.4"
env_logger = "0.11"   # ★ 구현체는 여기에서만 고릅니다
fn main() {
    env_logger::init();          // 전역 로거를 설치합니다

    log::info!("시작");           // 이제부터 진짜로 출력됩니다
    mylib::parse("...");          // 라이브러리의 로그도 같이 나옵니다
}

// 설치하기 전에 남긴 로그는 그냥 버려집니다 —
// init 은 main 의 첫 줄에 두세요 ★
$ RUST_LOG=info cargo run
[2026-09-01T04:12:33Z INFO  myapp] 시작
[2026-09-01T04:12:33Z INFO  mylib] 문서 하나를 읽었습니다
   ↑ 시각          ↑레벨  ↑target(모듈 경로)
라이브러리가 구현체를 의존하면 생기는 일 — 앱이 fern 을 쓰는데 내가 쓴 라이브러리가 env_logger 를 끌고 들어오면, 둘 중 하나만 설치되고 나머지는 조용히 무시됩니다(set_logger 는 두 번째부터 실패). “왜 어떤 로그만 안 나오지?”의 절반이 이 문제입니다.

파사드의 속을 열어 보기 — Log 트레이트는 세 함수뿐입니다 🟡 중급

직접 구현체 만들어 보기 (30줄)

use log::{Log, Metadata, Record, LevelFilter};

struct MyLogger;

impl Log for MyLogger {
    // ① 이 레벨·target 을 받을 것인가 (빠르게 판단해야 합니다)
    fn enabled(&self, m: &Metadata) -> bool {
        m.level() <= log::Level::Info
    }
    // ② 실제로 쓰기
    fn log(&self, r: &Record) {
        if !self.enabled(r.metadata()) { return; }
        eprintln!("[{}] {} — {}", r.level(), r.target(), r.args());
        //                                     ↑ args() 는 fmt::Arguments
        //                                       여기서 처음 포맷됩니다 ★
    }
    // ③ 버퍼 비우기 (종료 직전에 불립니다)
    fn flush(&self) {}
}

static LOGGER: MyLogger = MyLogger;

fn main() {
    log::set_logger(&LOGGER).unwrap();
    log::set_max_level(LevelFilter::Info);   // ★ 이걸 빼면 아무것도 안 나옵니다
    log::info!("직접 만든 로거");
}
set_max_level 을 잊는 실수 — 기본값이 Off 입니다. 매크로는 먼저 전역 최대 레벨과 비교하고(원자적 읽기 한 번), 통과해야 enabled() 를 부릅니다. 이 2단 검사가 꺼진 로그가 거의 공짜인 이유입니다.

파사드가 하는 일은 사실 이게 전부

// log 크레이트 내부의 뼈대 (개념적으로)
static LOGGER: AtomicPtr<dyn Log> = ...;   // 전역 슬롯 하나
static MAX_LEVEL: AtomicUsize = ...;        // 전역 레벨 하나

// info!(...) 가 펼쳐지는 모양
if log::Level::Info <= log::max_level() {   // ① 원자적 비교
    let logger = log::logger();
    if logger.enabled(&metadata) {           // ② 구현체에 묻기
        logger.log(&Record::builder()        // ③ 여기서 처음 포맷
            .args(format_args!("..."))
            .level(Level::Info)
            .target(module_path!())
            .file(Some(file!()))
            .line(Some(line!()))
            .build());
    }
}
레벨언제 쓰나
error!사람이 지금 봐야 하는 것
warn!돌긴 도는데 세어 둬야 하는 것
info!운영 기본값 — 업무 사건
debug!개발자용 — 조사할 때만 켬
trace!한 줄 한 줄 — 거의 안 켬

두 세계를 잇기 — log 로그를 tracing 이 받게 하기 🔴 실무

현실 — 의존성 트리에는 둘 다 있습니다

# 내 프로젝트가 어느 쪽을 쓰는지 세어 보기
cargo tree -i log        # log 를 누가 쓰는지 (역방향)
cargo tree -i tracing

# 실제 결과는 보통 이렇습니다
#   log      ← hyper 이전 세대 · mio · 많은 오래된 크레이트
#   tracing  ← tokio · tower · axum · sqlx · reqwest(최근)
# 둘 중 하나를 버릴 수 없으니 '이어 붙이는' 것이 정답입니다
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
# tracing-log 는 tracing-subscriber 의 기본 기능에 이미 들어 있습니다
기본값이 이미 이어져 있습니다 — tracing-subscriber 는 기본 피처로 tracing-log 를 켜고, init() 이 log 의 전역 로거 자리에 브리지를 꽂습니다. 즉 log::info! 도 tracing 구독자가 받습니다.

반대 방향과, 라이브러리 설계 지침

// ① log → tracing (거의 항상 이 방향)
//    tracing-subscriber 의 init()/try_init() 이 자동으로 해 줍니다.
//    수동으로 하려면:
tracing_log::LogTracer::init().unwrap();

// ② tracing → log (구독자 대신 기존 log 구현체를 쓰고 싶을 때)
//    tracing 의 "log" 피처를 켜면 이벤트가 log 레코드로도 나갑니다
// tracing = { version = "0.1", features = ["log"] }

// ③ 라이브러리를 만든다면 — 판단 기준
//    · 동기 · 범용 유틸리티        → log 만 의존 (가장 가벼움)
//    · 비동기 · 요청 단위 문맥 필요 → tracing 만 의존
//    · 둘 다 만족시키고 싶다       → tracing + "log" 피처
브리지의 비용 — log 이벤트는 span 정보가 없습니다. 브리지를 지나온 줄에는 요청 ID 가 붙지 않습니다. “어떤 줄만 문맥이 비어 있다”면 그건 브리지를 타고 온 남의 크레이트 로그입니다.
정리 — log 는 인터페이스이고 env_logger·fern 은 구현체입니다. 규칙은 한 줄 — 라이브러리는 파사드만, 실행 파일이 구현체를 딱 한 번. 현실의 프로젝트에는 log 와 tracing 이 섞여 있고, tracing-subscriber 가 기본으로 둘을 이어 줍니다.
LOG 03

tracing 이 다른 점 — 점이 아니라 구간을 기록합니다

log 는 사건(event) 하나를 한 줄로 남깁니다. tracing 은 여기에 구간(span) 을 더합니다 — 시작과 끝이 있고, 중첩되고, 안에서 난 모든 이벤트에 자기 정보를 물려주는 것. 비동기 코드에서 “이 로그가 어느 요청 것인가”를 답할 수 있게 하는 것이 바로 이 개념입니다.

span 은 겹쳐 쌓이는 문맥입니다 — 이벤트는 자기를 감싼 모든 span 을 물려받습니다.

같은 코드를 두 방식으로

// ── log 방식 — 문맥을 손으로 나릅니다 ──────────────
fn handle(req_id: u64, user: u64) {
    log::info!("[req {req_id}] 인증 시작 user={user}");
    authenticate(req_id, user);          // ← id 를 계속 넘겨야 합니다
    log::info!("[req {req_id}] 완료");
}
fn authenticate(req_id: u64, user: u64) {   // 인자가 늘어납니다
    log::info!("[req {req_id}] 인증 성공");
}
// ── tracing 방식 — 문맥이 스택처럼 쌓입니다 ─────────
use tracing::{info, info_span};

fn handle(req_id: u64, user: u64) {
    let span = info_span!("handle", req_id, user);
    let _e = span.enter();               // ★ 이 시점부터 '안'입니다

    info!("인증 시작");                   // req_id·user 가 자동으로 붙습니다
    authenticate();                       // 인자를 안 넘겨도 됩니다
    info!("완료");
}                                         // _e 가 드롭되면 span 이 닫힙니다

fn authenticate() {
    info!("인증 성공");                   // 여기에도 req_id 가 붙습니다
}
enter() 가 돌려주는 것은 가드입니다 — 드롭되는 순간 span 이 닫히고 구간의 길이가 기록됩니다. let _ = span.enter(); 처럼 쓰면 즉시 드롭되어 아무 효과가 없습니다 — 반드시 let _e = 로 이름을 주세요.

busy 와 idle — FmtSpan::CLOSE 를 켜면 span 이 닫힐 때 실제로 CPU 를 쓴 시간(busy) 과 .await 로 기다린 시간(idle) 이 따로 찍힙니다. “느린데 CPU 는 안 쓴다”를 한눈에 구분해 줍니다.

span 을 만드는 세 가지 방법 🟡 중급

매크로 · 어트리뷰트 · 수동

use tracing::{info_span, instrument, Instrument, Level, span};

// ① 매크로 — 동기 코드에서 가장 흔합니다
let sp = info_span!("batch", file = %path.display(), rows = 0u64);
let _g = sp.enter();

// ② 어트리뷰트 — 함수 전체가 span 이 됩니다 (가장 권장)
#[instrument(level = "info", skip(pool), fields(order_id))]
async fn place_order(pool: &Pool, req: OrderReq) -> Result<Order> {
    // 인자들이 자동으로 span 필드가 됩니다 (skip 한 것 빼고)
    let o = repo::insert(pool, &req).await?;
    tracing::Span::current().record("order_id", o.id);   // 나중에 채우기
    Ok(o)
}

// ③ 수동 — 레벨을 변수로 정하고 싶을 때
let sp = span!(Level::DEBUG, "retry", attempt = 1);

// ④ 비동기에서는 enter() 대신 .instrument() ★★ (LOG 07 에서 자세히)
some_future.instrument(info_span!("job")).await;
절대 하지 말 것 — async 블록 안에서 span.enter() 가드를 .await 를 넘겨 들고 있는 것. 컴파일은 되지만 span 이 다른 태스크에 새어 나갑니다. #[instrument] 나 .instrument() 는 이 문제가 구조적으로 없습니다.

#[instrument] 의 옵션 전부

옵션하는 일
skip(a, b)그 인자를 필드에서 뺍니다
skip_all인자를 전부 뺍니다 (권장 기본)
fields(x = %v)필드를 직접 추가
fields(id)빈 칸만 만들고 나중에 record
level = "debug"span 레벨 (기본 info)
name = "..."함수명 대신 쓸 이름
ret반환값을 이벤트로 남김
errErr 일 때 error! 로 남김
target = "..."필터용 target 지정
#[instrument(
    skip_all,                       // ★ 큰 구조체를 통째로 찍지 않습니다
    fields(order_id = %req.id, amount = req.amount),
    err(Debug),                     // Err 는 Debug 로 찍어 원인 체인까지
)]
async fn pay(req: PayReq) -> Result<Receipt, PayError> { ... }
skip_all 을 기본으로 하세요 — 아무것도 안 적으면 모든 인자가 Debug 로 찍힙니다. 요청 본문·비밀번호·토큰이 여기로 새어 나가는 사고가 실제로 가장 많습니다. 필요한 필드만 골라 fields() 로 명시하세요.

span 의 수명과 “들어간다”의 정확한 뜻 🔴 실무

만들기 · 들어가기 · 닫기는 다 다릅니다

let sp = info_span!("job", id = 7);   // ① 생성 — 아직 '현재'가 아님
{
    let _g = sp.enter();              // ② 진입 — 이제부터 현재 span
    info!("안에서 남긴 로그");         // id=7 이 붙습니다
}                                     // ③ 이탈 — 가드 드롭
info!("밖에서 남긴 로그");             // id=7 이 안 붙습니다

drop(sp);                             // ④ 닫힘 — 마지막 핸들이 사라질 때

// 한 span 에 여러 번 들어갔다 나올 수 있습니다 ★
//   비동기 태스크는 실제로 이렇게 동작합니다 —
//   폴링될 때마다 enter, .await 에서 exit 를 반복합니다
수명의 세 단계를 구독자가 각각 봅니다 — on_new_span(생성) · on_enter/on_exit(진입·이탈) · on_close(닫힘). busy 시간은 enter~exit 의 합, 전체 시간은 생성~닫힘입니다. 이 둘을 빼면 .await 로 기다린 시간(idle)이 나옵니다.

span 을 얼마나 많이 만들어도 되나

// 나쁜 예 — 루프 안에서 span 을 100만 개
for row in rows {                     // ✗
    let _g = info_span!("row", id = row.id).enter();
    process(row);
}

// 좋은 예 — 바깥에 하나, 안에서는 필드만 갱신하거나 이벤트로
let sp = info_span!("rows", total = rows.len(), done = 0u64);
let _g = sp.enter();                  // ✔
for (i, row) in rows.iter().enumerate() {
    process(row);
    if i % 10_000 == 0 { sp.record("done", i as u64); }
}

// 판단 기준 ★
//   span = "나중에 이 구간의 시간을 알고 싶은 단위"
//   그게 아니면 이벤트(info!) 하나로 충분합니다
비용 감각 — 꺼진 span 은 거의 공짜(콜사이트 캐시된 정적 판단)지만, 켜진 span 은 Registry 에 등록·해제되고 필드가 저장됩니다. 요청 · 배치 · 외부 호출 정도의 단위에 두는 것이 정석이고, 내부 루프 한 바퀴마다 만드는 것은 거의 항상 과합니다.
정리 — log 는 점을, tracing 은 구간을 기록합니다. span 은 시간(길이) · 계층(부모-자식) · 문맥(상속) 세 가지를 한꺼번에 주고, 이것이 비동기에서 “이 로그가 어느 요청 것인가”에 답할 수 있는 유일한 방법입니다. 함수 단위는 #[instrument(skip_all, fields(...))] 를 기본으로 쓰세요.
