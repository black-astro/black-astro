LOG 10

분산 추적 — tracing-opentelemetry 로 span 을 서비스 밖으로 내보냅니다

서비스가 둘 이상이면 “이 요청이 어디서 느려졌나”는 한 프로세스의 로그로는 답이 안 나옵니다. OpenTelemetry(OTel) 는 그 답을 위해 trace_id 하나로 여러 서비스의 span 을 한 트리로 묶는 규격이고, tracing 의 span 은 이미 그 모양이라 레이어 하나만 끼우면 그대로 나갑니다.

서비스는 헤더로 문맥을 넘기고 span 은 각자 내보냅니다 — 트리는 저장소에서 다시 맞춰집니다.

가장 많이 막히는 곳이 버전입니다 — OpenTelemetry 러스트 SDK 는 아직 1.0 이전이라 minor 마다 API 가 바뀝니다. tracing-opentelemetry 는 OTel 보다 minor 가 하나 앞선 번호를 쓰는 관례가 있고, Cargo.lock 에 두 버전이 섞이는 순간 global::set_tracer_provider 가 서로 다른 타입을 보게 됩니다. cargo tree -d 로 중복을 먼저 지우세요.

init_telemetry() — 프로바이더 + 레이어

use opentelemetry::{global, trace::TracerProvider as _, KeyValue};
use opentelemetry_sdk::{trace::SdkTracerProvider, Resource,
                        propagation::TraceContextPropagator};
use opentelemetry_otlp::{SpanExporter, WithExportConfig};
use tracing_subscriber::{fmt, EnvFilter, prelude::*};

pub fn init_telemetry() -> anyhow::Result<SdkTracerProvider> {
    // ① W3C traceparent 를 읽고 쓰는 전파기 — 이게 없으면 헤더가 안 붙습니다
    global::set_text_map_propagator(TraceContextPropagator::new());

    // ② OTLP/gRPC exporter — Collector 의 4317 포트로
    let exporter = SpanExporter::builder()
        .with_tonic()
        .with_endpoint("http://otel-collector:4317")
        .build()?;

    // ③ 프로바이더 — 배치 전송 + 리소스(service.name 은 사실상 필수)
    let provider = SdkTracerProvider::builder()
        .with_batch_exporter(exporter)          // 전용 스레드가 모아서 보냅니다
        .with_resource(Resource::builder()
            .with_service_name("order-api")
            .with_attribute(KeyValue::new("deployment.environment", "prod"))
            .build())
        .build();
    global::set_tracer_provider(provider.clone());

    // ④ tracing 레이어 — 내 span 이 OTel span 으로 복제됩니다 ★
    let otel = tracing_opentelemetry::layer()
        .with_tracer(provider.tracer("order-api"));

    tracing_subscriber::registry()
        .with(EnvFilter::from_default_env())
        .with(fmt::layer().json())
        .with(otel)
        .init();
    Ok(provider)          // main 이 끝날 때 shutdown() 을 불러야 합니다
}
코드에서 바뀌는 것은 없습니다 — #[instrument] 로 만든 span 과 info! 이벤트가 그대로 OTel span 과 span event 가 됩니다. LOG 03·07 에서 붙인 문맥이 그대로 분산 추적의 재료입니다.

문맥을 서비스 밖으로 — 헤더 주입과 추출 🟡 중급

호출하는 쪽 — 현재 span 을 헤더에 씁니다

use opentelemetry::global;
use opentelemetry_http::HeaderInjector;
use tracing_opentelemetry::OpenTelemetrySpanExt;   // .context() 를 줍니다

#[tracing::instrument(skip_all, fields(sku))]
async fn check_stock(client: &reqwest::Client, sku: &str)
    -> anyhow::Result<Stock>
{
    let mut req = client.get(format!("http://stock/v1/{sku}")).build()?;

    // 현재 tracing span → OTel 문맥 → traceparent 헤더 ★
    let cx = tracing::Span::current().context();
    global::get_text_map_propagator(|p| {
        p.inject_context(&cx, &mut HeaderInjector(req.headers_mut()))
    });
    // 나가는 헤더: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
    //                              ↑ trace_id(16바이트)            ↑ 내 span_id   ↑ 샘플링 플래그

    Ok(client.execute(req).await?.json().await?)
}
헤더 규격은 W3C Trace Context — traceparent 와 tracestate 두 개입니다. 자바(Spring) · Go · .NET 서비스도 같은 헤더를 읽으므로 언어가 섞여도 한 트리가 됩니다. 직접 헤더를 만들지 말고 전파기에 맡기세요 — 플래그 비트와 버전 바이트를 손으로 쓰면 틀립니다.

받는 쪽 — 헤더를 부모로 삼습니다 (Axum)

use opentelemetry::global;
use opentelemetry_http::HeaderExtractor;
use tower_http::trace::TraceLayer;
use tracing_opentelemetry::OpenTelemetrySpanExt;

let app = Router::new()
    .route("/v1/{sku}", get(get_stock))
    .layer(TraceLayer::new_for_http()
        .make_span_with(|req: &http::Request<_>| {
            // ① 들어온 헤더에서 부모 문맥을 꺼냅니다 (없으면 빈 문맥)
            let parent = global::get_text_map_propagator(|p| {
                p.extract(&HeaderExtractor(req.headers()))
            });
            // ② 요청 span 을 만들고 부모를 이어 붙입니다 ★
            let span = tracing::info_span!("http",
                method = %req.method(), path = %req.uri().path(),
                trace_id = tracing::field::Empty);
            span.set_parent(parent);
            // ③ 로그 상관용 — trace_id 를 span 필드로 남깁니다
            use opentelemetry::trace::TraceContextExt;
            let id = span.context().span().span_context().trace_id();
            span.record("trace_id", id.to_string());
            span
        }));
③ 이 로그와 트레이스를 잇는 전부입니다 — span 필드는 안쪽 이벤트에 상속되므로 (LOG 05 의 with_span_list) 요청 안의 모든 JSON 로그 줄에 trace_id 가 붙습니다. Grafana 는 그 값을 클릭하면 Tempo 의 트레이스로 건너뛰게 해 줍니다.

저장소 고르기 — 시작은 Jaeger(컨테이너 하나로 UI 까지), 로그를 Loki 에 두고 있다면 Grafana Tempo (trace_id 클릭 연동), 운영 인력이 없으면 Datadog · Honeycomb · Grafana Cloud 같은 SaaS. 어느 쪽이든 앱은 Collector 만 보게 두면 저장소 교체가 YAML 한 줄입니다. 로그 자체도 OTLP 로 보내려면 opentelemetry-appender-tracing 레이어를 하나 더 끼웁니다.
정리 — 분산 추적은 새 계측이 아니라 기존 span 을 내보내는 것입니다. 필요한 것은 셋 — 전파기(헤더를 읽고 씀) · exporter + 프로바이더(OTLP 로 Collector 에) · tracing_opentelemetry::layer(). trace_id 를 span 필드로 한 번 남기면 로그와 트레이스가 이어지고, shutdown() 을 잊으면 마지막 트레이스가 사라집니다. 버전은 네 크레이트를 한 세트로 올리세요.

에러와 패닉 — 경계에서 한 번, 그리고 로거를 거치지 않는 패닉 잡기

로그가 가장 지저분해지는 곳이 에러 처리입니다. 같은 에러를 세 층에서 세 번 찍고, 정작 원인은 {e} 로 바깥 한 겹만 남습니다. 반대로 패닉은 로거를 아예 거치지 않아 파일에는 흔적이 없습니다. 이 섹션은 그 둘을 anyhow 체인과 panic::set_hook 으로 정리합니다.

에러 로그는 경계에서 한 번, 안쪽은 문맥만 붙여 올립니다 — 그래야 한 줄에 원인 체인이 다 들어갑니다.
층마다 찍고 다시 던집니다

// Axum 경계 — 에러 타입 하나가 로그와 응답을 함께 정합니다 ★
enum AppError { NotFound(String), Invalid(String), Internal(anyhow::Error) }

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, body) = match self {
            AppError::NotFound(m) => {
                tracing::info!(error = %m, "요청 거절");            // 4xx 는 info
                (StatusCode::NOT_FOUND, m)
            }
            AppError::Invalid(m) => {
                tracing::info!(error = %m, "요청 거절");
                (StatusCode::BAD_REQUEST, m)
            }
            AppError::Internal(e) => {
                tracing::error!(error = %format!("{e:#}"), "요청 실패");   // 5xx 만 error
                // 클라이언트에는 내부 사정을 보내지 않습니다 — 문구 고정
                (StatusCode::INTERNAL_SERVER_ERROR, "internal error".to_string())
            }
        };
        (status, Json(json!({ "error": body }))).into_response()
    }
}
4xx 를 error! 로 찍는 순간 알람이 무의미해집니다 — 봇이 잘못된 URL 을 긁기만 해도 에러 대시보드가 빨개집니다. “내가 고칠 수 있는 것만 error”가 기준입니다.

패닉 — 로거를 거치지 않는 유일한 출력을 붙잡기 🔴 실무

panic::set_hook — 기본 훅을 감쌉니다

pub fn install_panic_hook() {
    let default_hook = std::panic::take_hook();      // 기본 훅(stderr 출력)을 보관

    std::panic::set_hook(Box::new(move |info| {
        // 페이로드는 &str 또는 String — 둘 다 시도합니다
        //   (Rust 1.89 부터는 info.payload_as_str() 한 줄로 됩니다)
        let msg = info.payload().downcast_ref::<&str>().copied()
            .or_else(|| info.payload().downcast_ref::<String>().map(String::as_str))
            .unwrap_or("(문자열이 아닌 페이로드)");
        let location = info.location()
            .map(|l| format!("{}:{}:{}", l.file(), l.line(), l.column()));

        // ★ 로거로 — 현재 span 의 문맥(요청 ID 등)이 그대로 붙습니다
        tracing::error!(
            panic.message  = msg,
            panic.location = location.as_deref(),
            backtrace      = %std::backtrace::Backtrace::force_capture(),
            "패닉"
        );
        default_hook(info);          // 기본 훅도 불러 stderr 에는 여전히 남깁니다
    }));
}
훅은 unwinding 전에 불립니다 — 그래서 현재 span 이 아직 살아 있고 요청 ID 가 붙습니다. force_capture() 는 RUST_BACKTRACE 와 무관하게 백트레이스를 만듭니다(비용이 있으니 패닉에서만). init_log() 바로 다음 줄에서 설치하세요.

# 훅 안에서 파일에 직접 쓰거나 stderr 에 남기세요 (default_hook 이 그 역할)
panic = "abort" + non_blocking 조합의 함정 — 훅에서 tracing::error! 를 불러도 그 줄은 워커 큐에 들어갈 뿐이고, 곧바로 abort 되면 큐가 비워지지 않습니다. 파일에는 패닉 줄이 없고 stderr 에만 있습니다. 컨테이너라면 stderr 가 수집되니 괜찮지만, 파일 로깅 환경이라면 훅에서 동기 쓰기를 한 번 더 하세요.
정리 — 에러는 안쪽에서 .context() 만 붙여 올리고, 경계에서 {e:#} 로 한 번 찍습니다. anyhow 의 Display 는 바깥 한 겹뿐이니 %e 대신 {e:#} 또는 ?e. 4xx 는 info, 내가 고칠 것만 error. 패닉은 로거를 거치지 않으므로 set_hook 으로 잡아 span 문맥과 함께 남기고, panic = "abort" 면 훅에서 동기로도 씁니다.
