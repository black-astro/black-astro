러스트에는 표준 로깅이 없습니다. 표준 라이브러리가 주는 것은 println! 과 eprintln! 뿐이고, 그 둘로는 운영에서 하루도 못 버팁니다. 대신 생태계가 두 겹으로 나뉜 해법을 만들었습니다 — 라이브러리가 부르는 얇은 파사드(log)와 실행 파일이 딱 한 번 고르는 구현체(env_logger·fern 등), 그리고 비동기 시대에 맞춰 “점”이 아니라 “구간”을 기록하는 tracing 입니다. 이 탭은 그 전부를 왜 이렇게 됐는지부터 설명하고, 레이어 합성 · JSON 구조적 로깅 · 파일 로테이션 · 성능 · OpenTelemetry · 패닉 · 임베디드까지 이어 갑니다. 이 탭을 마치면 새 프로젝트의 init_log() 를 남의 코드를 베끼지 않고 직접 쓸 수 있습니다.

LOG 01

println! 로 시작해서 반드시 막히는 곳 — 무엇이 없는가

누구나 println!("여기까지 왔다") 로 시작합니다. 그리고 누구나 같은 자리에서 막힙니다. 끌 수가 없고, 언제 어디서 났는지 모르고, 컨테이너에서 사라지고, 느립니다. 이 네 가지가 로깅 크레이트가 존재하는 이유 전부입니다.

둘의 차이는 편의가 아닙니다 — 끌 수 있는가, 찾을 수 있는가가 다릅니다.

① 끌 수가 없습니다

// 디버깅하다 넣은 한 줄. 지우는 걸 잊습니다
for row in &rows {
    println!("row = {row:?}");     // 100만 건이면 100만 줄
}

// 임시방편으로 이렇게들 합니다 — 그리고 이게 늘어납니다
if std::env::var("DEBUG").is_ok() {
    println!("row = {row:?}");
}
// 조건이 실행 시점마다 평가되고, {row:?} 는 조건과 무관하게
// 이미 포맷 인자로 준비됩니다(Debug 호출은 지연되지만 인자 참조는 남습니다)
// 로깅 크레이트라면 — 코드는 그대로, 끄고 켜는 건 바깥에서
log::debug!("row = {row:?}");      // 또는 tracing::debug!

// $ RUST_LOG=info  ./app     → 이 줄은 아예 실행되지 않습니다
// $ RUST_LOG=debug ./app     → 이 줄이 나옵니다
// 레벨이 안 맞으면 포맷 자체를 시작하지 않습니다 ★
핵심은 “지연 평가”입니다 — debug! 매크로는 먼저 레벨이 켜져 있는지 묻고, 꺼져 있으면 인자 포맷팅을 아예 하지 않습니다. println! 은 무조건 포맷합니다. 무거운 Debug 구현이 붙은 타입에서는 이 차이가 수십 배가 됩니다.

② stdout 은 잠금이 걸린 자원입니다

use std::io::Write;

// println! 이 실제로 하는 일 (개념적으로)
let stdout = std::io::stdout();
let mut lock = stdout.lock();      // ← 전역 뮤텍스를 잡습니다
writeln!(lock, "...").unwrap();
// 락 해제 + 줄바꿈마다 LineWriter 가 flush 합니다

// 스레드 8개가 동시에 println! 을 하면
//   8개가 같은 뮤텍스 앞에 줄을 섭니다 → 직렬화 지점이 생깁니다
// 비동기 런타임에서는 더 나쁩니다 —
//   워커 스레드가 블로킹 I/O 로 멈추면 그 위의 태스크가 전부 멈춥니다 ★
// 굳이 println! 을 써야 한다면 최소한 락을 한 번만 잡습니다
let mut out = std::io::stdout().lock();
for row in &rows {
    writeln!(out, "{row:?}")?;     // 매번 잠그지 않습니다
}
// 그래도 레벨·시각·구조는 여전히 없습니다
비동기에서 특히 위험합니다 — Tokio 워커 스레드는 보통 CPU 코어 수만큼입니다. 그 중 하나가 느린 터미널이나 파이프에 블로킹 쓰기를 하면 거기에 얹힌 태스크 전부가 대기합니다. tracing-appender 의 non_blocking 이 존재하는 이유가 이것입니다(LOG 08).

③ 컨테이너에서 로그가 사라지는 세 가지 이유 🟡 중급

버퍼링 · 종료 · 목적지

증상진짜 원인처방
마지막 몇 줄이 없다프로세스가 버퍼를 비우기 전에 죽음워커 guard 유지 · flush()
한참 뒤에 몰려 나온다파이프에 붙으면 블록 버퍼링줄 단위 flush 또는 로거 사용
아무것도 안 보인다stdout 이 아니라 stderr 로 나감수집기 설정 확인 · 목적지 통일

12-Factor 원칙 — 컨테이너 안의 앱은 파일이 아니라 stdout 한 줄기로만 씁니다. 모으고 회전시키고 보관하는 일은 도커·쿠버네티스·수집기가 합니다. 예외는 임베디드·데스크톱 앱처럼 수집기가 없는 환경뿐입니다(LOG 08).

직접 확인해 보기

# stdout 이 터미널이면 줄 단위, 파이프면 블록 버퍼링입니다
./app                 # 실시간으로 보임
./app | cat           # 뭉쳐서 나옴 ← 이게 컨테이너 상황과 같습니다

# 도커에서 로그가 늦게 보이는지 확인
docker run --rm myapp 2>&1 | ts     # moreutils 의 ts 가 시각을 붙여 줍니다

# 쿠버네티스에서는 stdout·stderr 가 같은 곳으로 모입니다
kubectl logs -f deploy/myapp --timestamps

# 종료 직전 몇 줄이 날아가는지 재현
./app & sleep 0.2; kill -TERM %1     # SIGTERM 직후 남는 줄을 봅니다
가장 억울한 사고 — “장애가 났는데 마지막 로그가 없다”. 원인은 거의 항상 비동기 쓰기 버퍼가 안 비워진 것입니다. tracing-appender 를 쓸 때 WorkerGuard 를 살려 두는 것이 그래서 중요합니다.

④ 그래도 println! 이 맞는 자리 🔴 실무

로그가 아니라 “출력”일 때

// ① CLI 의 결과물 — 이건 로그가 아니라 프로그램의 출력입니다
//    파이프로 넘겨 쓰는 값이므로 stdout 이 맞습니다
println!("{}", total);

// ② 진행 상황 · 에러 안내는 stderr 로
eprintln!("입력 파일을 찾을 수 없습니다: {path}");

// 규칙 하나만 외우면 됩니다 ★
//   stdout = 다음 프로그램이 먹을 데이터
//   stderr = 사람이 읽을 말
//   로거   = 나중에 조사할 기록
// 이 셋을 섞으면 `./app | jq` 가 깨집니다
CLI 라면 clap 의 --verbose 를 로그 레벨로 이어 붙이는 것이 관례입니다. -v 는 info, -vv 는 debug, -vvv 는 trace — clap-verbosity-flag 크레이트가 이 매핑을 그대로 해 줍니다.

테스트에서의 출력 — 이것도 함정입니다

#[test]
fn t() {
    println!("여기");        // 통과하면 안 보이고, 실패해야 보입니다
    // cargo test -- --nocapture 로 항상 보이게 할 수 있습니다
}

// 로그를 테스트에서 보고 싶다면 — 전역 로거는 한 번만 설치됩니다
static INIT: std::sync::Once = std::sync::Once::new();
fn init_test_log() {
    INIT.call_once(|| {
        let _ = tracing_subscriber::fmt()
            .with_test_writer()      // ★ 테스트 캡처로 보냅니다
            .with_env_filter("debug")
            .try_init();             // init() 은 두 번째 호출에서 패닉
    });
}
init() 과 try_init() 의 차이 — 전역 로거는 프로세스당 한 번만 설치됩니다. 테스트는 같은 프로세스에서 여러 개가 도니 init() 을 쓰면 두 번째부터 패닉합니다. 테스트 코드에서는 반드시 try_init() 을 쓰세요.
정리 — println! 의 문제는 “느리다”가 아니라 끌 수 없고 찾을 수 없다는 것입니다. 로깅 크레이트가 주는 것은 딱 넷 — 레벨(끄기) · 메타데이터(언제·어디서) · 구조(찾기) · 비동기 쓰기(안 막기). stdout 은 프로그램의 출력, stderr 는 사람에게 하는 말, 로거는 나중에 조사할 기록입니다.
LOG 02

파사드 구조 — log 크레이트가 인터페이스만 정한 이유

라이브러리는 로그를 남기고 싶지, 로그를 어디로 보낼지 정하고 싶지 않습니다. 그 두 관심사를 갈라 놓은 것이 log 크레이트입니다 — 자바의 SLF4J + Logback 과 정확히 같은 두 겹 구조입니다.

라이브러리가 구현체를 고르면 앱이 두 개의 로거를 갖게 됩니다 — 그래서 파사드가 있습니다.

라이브러리 쪽 — log 만 의존합니다

# 내가 만드는 라이브러리 크레이트의 Cargo.toml
[dependencies]
log = "0.4"          # ★ 이것만. env_logger 를 넣으면 안 됩니다

# tracing 을 쓰는 라이브러리라면
# tracing = { version = "0.1", default-features = false, features = ["std"] }
// src/lib.rs — 매크로 5종이 전부입니다
pub fn parse(input: &str) -> Result<Doc, Error> {
    log::trace!("parse 시작, {} 바이트", input.len());

    if input.is_empty() {
        log::warn!("빈 입력이 들어왔습니다");
        return Err(Error::Empty);
    }
    log::debug!(target: "mylib::parser", "토큰 {}개", n);
    log::info!("문서 하나를 읽었습니다");
    log::error!("복구 불가: {e}");
    Ok(doc)
}
target: 이 무엇인가 — 기본값은 모듈 경로(mylib::parser)입니다. 이 문자열이 나중에 RUST_LOG 필터의 왼쪽이 됩니다. 직접 지정하면 모듈 구조와 무관하게 기능 단위로 껐다 켤 수 있습니다.

실행 파일 쪽 — 구현체를 딱 한 번

# 실행 파일(bin) 의 Cargo.toml
[dependencies]
log = "0.4"
env_logger = "0.11"   # ★ 구현체는 여기에서만 고릅니다
fn main() {
    env_logger::init();          // 전역 로거를 설치합니다

    log::info!("시작");           // 이제부터 진짜로 출력됩니다
    mylib::parse("...");          // 라이브러리의 로그도 같이 나옵니다
}

// 설치하기 전에 남긴 로그는 그냥 버려집니다 —
// init 은 main 의 첫 줄에 두세요 ★
$ RUST_LOG=info cargo run
[2026-09-01T04:12:33Z INFO  myapp] 시작
[2026-09-01T04:12:33Z INFO  mylib] 문서 하나를 읽었습니다
   ↑ 시각          ↑레벨  ↑target(모듈 경로)
라이브러리가 구현체를 의존하면 생기는 일 — 앱이 fern 을 쓰는데 내가 쓴 라이브러리가 env_logger 를 끌고 들어오면, 둘 중 하나만 설치되고 나머지는 조용히 무시됩니다(set_logger 는 두 번째부터 실패). “왜 어떤 로그만 안 나오지?”의 절반이 이 문제입니다.

파사드의 속을 열어 보기 — Log 트레이트는 세 함수뿐입니다 🟡 중급

직접 구현체 만들어 보기 (30줄)

use log::{Log, Metadata, Record, LevelFilter};

struct MyLogger;

impl Log for MyLogger {
    // ① 이 레벨·target 을 받을 것인가 (빠르게 판단해야 합니다)
    fn enabled(&self, m: &Metadata) -> bool {
        m.level() <= log::Level::Info
    }
    // ② 실제로 쓰기
    fn log(&self, r: &Record) {
        if !self.enabled(r.metadata()) { return; }
        eprintln!("[{}] {} — {}", r.level(), r.target(), r.args());
        //                                     ↑ args() 는 fmt::Arguments
        //                                       여기서 처음 포맷됩니다 ★
    }
    // ③ 버퍼 비우기 (종료 직전에 불립니다)
    fn flush(&self) {}
}

static LOGGER: MyLogger = MyLogger;

fn main() {
    log::set_logger(&LOGGER).unwrap();
    log::set_max_level(LevelFilter::Info);   // ★ 이걸 빼면 아무것도 안 나옵니다
    log::info!("직접 만든 로거");
}
set_max_level 을 잊는 실수 — 기본값이 Off 입니다. 매크로는 먼저 전역 최대 레벨과 비교하고(원자적 읽기 한 번), 통과해야 enabled() 를 부릅니다. 이 2단 검사가 꺼진 로그가 거의 공짜인 이유입니다.

파사드가 하는 일은 사실 이게 전부

// log 크레이트 내부의 뼈대 (개념적으로)
static LOGGER: AtomicPtr<dyn Log> = ...;   // 전역 슬롯 하나
static MAX_LEVEL: AtomicUsize = ...;        // 전역 레벨 하나

// info!(...) 가 펼쳐지는 모양
if log::Level::Info <= log::max_level() {   // ① 원자적 비교
    let logger = log::logger();
    if logger.enabled(&metadata) {           // ② 구현체에 묻기
        logger.log(&Record::builder()        // ③ 여기서 처음 포맷
            .args(format_args!("..."))
            .level(Level::Info)
            .target(module_path!())
            .file(Some(file!()))
            .line(Some(line!()))
            .build());
    }
}
레벨언제 쓰나
error!사람이 지금 봐야 하는 것
warn!돌긴 도는데 세어 둬야 하는 것
info!운영 기본값 — 업무 사건
debug!개발자용 — 조사할 때만 켬
trace!한 줄 한 줄 — 거의 안 켬

두 세계를 잇기 — log 로그를 tracing 이 받게 하기 🔴 실무

현실 — 의존성 트리에는 둘 다 있습니다

# 내 프로젝트가 어느 쪽을 쓰는지 세어 보기
cargo tree -i log        # log 를 누가 쓰는지 (역방향)
cargo tree -i tracing

# 실제 결과는 보통 이렇습니다
#   log      ← hyper 이전 세대 · mio · 많은 오래된 크레이트
#   tracing  ← tokio · tower · axum · sqlx · reqwest(최근)
# 둘 중 하나를 버릴 수 없으니 '이어 붙이는' 것이 정답입니다
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
# tracing-log 는 tracing-subscriber 의 기본 기능에 이미 들어 있습니다
기본값이 이미 이어져 있습니다 — tracing-subscriber 는 기본 피처로 tracing-log 를 켜고, init() 이 log 의 전역 로거 자리에 브리지를 꽂습니다. 즉 log::info! 도 tracing 구독자가 받습니다.

반대 방향과, 라이브러리 설계 지침

// ① log → tracing (거의 항상 이 방향)
//    tracing-subscriber 의 init()/try_init() 이 자동으로 해 줍니다.
//    수동으로 하려면:
tracing_log::LogTracer::init().unwrap();

// ② tracing → log (구독자 대신 기존 log 구현체를 쓰고 싶을 때)
//    tracing 의 "log" 피처를 켜면 이벤트가 log 레코드로도 나갑니다
// tracing = { version = "0.1", features = ["log"] }

// ③ 라이브러리를 만든다면 — 판단 기준
//    · 동기 · 범용 유틸리티        → log 만 의존 (가장 가벼움)
//    · 비동기 · 요청 단위 문맥 필요 → tracing 만 의존
//    · 둘 다 만족시키고 싶다       → tracing + "log" 피처
브리지의 비용 — log 이벤트는 span 정보가 없습니다. 브리지를 지나온 줄에는 요청 ID 가 붙지 않습니다. “어떤 줄만 문맥이 비어 있다”면 그건 브리지를 타고 온 남의 크레이트 로그입니다.
정리 — log 는 인터페이스이고 env_logger·fern 은 구현체입니다. 규칙은 한 줄 — 라이브러리는 파사드만, 실행 파일이 구현체를 딱 한 번. 현실의 프로젝트에는 log 와 tracing 이 섞여 있고, tracing-subscriber 가 기본으로 둘을 이어 줍니다.
LOG 03

tracing 이 다른 점 — 점이 아니라 구간을 기록합니다

log 는 사건(event) 하나를 한 줄로 남깁니다. tracing 은 여기에 구간(span) 을 더합니다 — 시작과 끝이 있고, 중첩되고, 안에서 난 모든 이벤트에 자기 정보를 물려주는 것. 비동기 코드에서 “이 로그가 어느 요청 것인가”를 답할 수 있게 하는 것이 바로 이 개념입니다.

span 은 겹쳐 쌓이는 문맥입니다 — 이벤트는 자기를 감싼 모든 span 을 물려받습니다.

같은 코드를 두 방식으로

// ── log 방식 — 문맥을 손으로 나릅니다 ──────────────
fn handle(req_id: u64, user: u64) {
    log::info!("[req {req_id}] 인증 시작 user={user}");
    authenticate(req_id, user);          // ← id 를 계속 넘겨야 합니다
    log::info!("[req {req_id}] 완료");
}
fn authenticate(req_id: u64, user: u64) {   // 인자가 늘어납니다
    log::info!("[req {req_id}] 인증 성공");
}
// ── tracing 방식 — 문맥이 스택처럼 쌓입니다 ─────────
use tracing::{info, info_span};

fn handle(req_id: u64, user: u64) {
    let span = info_span!("handle", req_id, user);
    let _e = span.enter();               // ★ 이 시점부터 '안'입니다

    info!("인증 시작");                   // req_id·user 가 자동으로 붙습니다
    authenticate();                       // 인자를 안 넘겨도 됩니다
    info!("완료");
}                                         // _e 가 드롭되면 span 이 닫힙니다

fn authenticate() {
    info!("인증 성공");                   // 여기에도 req_id 가 붙습니다
}
enter() 가 돌려주는 것은 가드입니다 — 드롭되는 순간 span 이 닫히고 구간의 길이가 기록됩니다. let _ = span.enter(); 처럼 쓰면 즉시 드롭되어 아무 효과가 없습니다 — 반드시 let _e = 로 이름을 주세요.

busy 와 idle — FmtSpan::CLOSE 를 켜면 span 이 닫힐 때 실제로 CPU 를 쓴 시간(busy) 과 .await 로 기다린 시간(idle) 이 따로 찍힙니다. “느린데 CPU 는 안 쓴다”를 한눈에 구분해 줍니다.

span 을 만드는 세 가지 방법 🟡 중급

매크로 · 어트리뷰트 · 수동

use tracing::{info_span, instrument, Instrument, Level, span};

// ① 매크로 — 동기 코드에서 가장 흔합니다
let sp = info_span!("batch", file = %path.display(), rows = 0u64);
let _g = sp.enter();

// ② 어트리뷰트 — 함수 전체가 span 이 됩니다 (가장 권장)
#[instrument(level = "info", skip(pool), fields(order_id))]
async fn place_order(pool: &Pool, req: OrderReq) -> Result<Order> {
    // 인자들이 자동으로 span 필드가 됩니다 (skip 한 것 빼고)
    let o = repo::insert(pool, &req).await?;
    tracing::Span::current().record("order_id", o.id);   // 나중에 채우기
    Ok(o)
}

// ③ 수동 — 레벨을 변수로 정하고 싶을 때
let sp = span!(Level::DEBUG, "retry", attempt = 1);

// ④ 비동기에서는 enter() 대신 .instrument() ★★ (LOG 07 에서 자세히)
some_future.instrument(info_span!("job")).await;
절대 하지 말 것 — async 블록 안에서 span.enter() 가드를 .await 를 넘겨 들고 있는 것. 컴파일은 되지만 span 이 다른 태스크에 새어 나갑니다. #[instrument] 나 .instrument() 는 이 문제가 구조적으로 없습니다.

#[instrument] 의 옵션 전부

옵션하는 일
skip(a, b)그 인자를 필드에서 뺍니다
skip_all인자를 전부 뺍니다 (권장 기본)
fields(x = %v)필드를 직접 추가

#[instrument(
    skip_all,                       // ★ 큰 구조체를 통째로 찍지 않습니다
    fields(order_id = %req.id, amount = req.amount),
    err(Debug),                     // Err 는 Debug 로 찍어 원인 체인까지
)]
async fn pay(req: PayReq) -> Result<Receipt, PayError> { ... }
skip_all 을 기본으로 하세요 — 아무것도 안 적으면 모든 인자가 Debug 로 찍힙니다. 요청 본문·비밀번호·토큰이 여기로 새어 나가는 사고가 실제로 가장 많습니다. 필요한 필드만 골라 fields() 로 명시하세요.

span 의 수명과 “들어간다”의 정확한 뜻 🔴 실무

만들기 · 들어가기 · 닫기는 다 다릅니다

let sp = info_span!("job", id = 7);   // ① 생성 — 아직 '현재'가 아님
{
    let _g = sp.enter();              // ② 진입 — 이제부터 현재 span
    info!("안에서 남긴 로그");         // id=7 이 붙습니다
}                                     // ③ 이탈 — 가드 드롭
info!("밖에서 남긴 로그");             // id=7 이 안 붙습니다

drop(sp);                             // ④ 닫힘 — 마지막 핸들이 사라질 때

// 한 span 에 여러 번 들어갔다 나올 수 있습니다 ★
//   비동기 태스크는 실제로 이렇게 동작합니다 —
//   폴링될 때마다 enter, .await 에서 exit 를 반복합니다
수명의 세 단계를 구독자가 각각 봅니다 — on_new_span(생성) · on_enter/on_exit(진입·이탈) · on_close(닫힘). busy 시간은 enter~exit 의 합, 전체 시간은 생성~닫힘입니다. 이 둘을 빼면 .await 로 기다린 시간(idle)이 나옵니다.

span 을 얼마나 많이 만들어도 되나

// 나쁜 예 — 루프 안에서 span 을 100만 개
for row in rows {                     // ✗
    let _g = info_span!("row", id = row.id).enter();
    process(row);
}

// 좋은 예 — 바깥에 하나, 안에서는 필드만 갱신하거나 이벤트로
let sp = info_span!("rows", total = rows.len(), done = 0u64);
let _g = sp.enter();                  // ✔
for (i, row) in rows.iter().enumerate() {
    process(row);
    if i % 10_000 == 0 { sp.record("done", i as u64); }
}

// 판단 기준 ★
//   span = "나중에 이 구간의 시간을 알고 싶은 단위"
//   그게 아니면 이벤트(info!) 하나로 충분합니다
비용 감각 — 꺼진 span 은 거의 공짜(콜사이트 캐시된 정적 판단)지만, 켜진 span 은 Registry 에 등록·해제되고 필드가 저장됩니다. 요청 · 배치 · 외부 호출 정도의 단위에 두는 것이 정석이고, 내부 루프 한 바퀴마다 만드는 것은 거의 항상 과합니다.
정리 — log 는 점을, tracing 은 구간을 기록합니다. span 은 시간(길이) · 계층(부모-자식) · 문맥(상속) 세 가지를 한꺼번에 주고, 이것이 비동기에서 “이 로그가 어느 요청 것인가”에 답할 수 있는 유일한 방법입니다. 함수 단위는 #[instrument(skip_all, fields(...))] 를 기본으로 쓰세요.
LOG 04

tracing-subscriber 실전 — 레이어를 겹쳐 내 구독자를 조립합니다

tracing 은 기록만 하고, 그걸 받아 처리하는 쪽이 구독자(Subscriber) 입니다. tracing-subscriber 는 구독자를 통째로 주는 대신 Registry 위에 레이어를 끼우는 방식을 씁니다 — 포맷 하나, 필터 하나, OTel 하나… 필요한 만큼 겹칩니다.

구독자는 완성품이 아니라 조립품입니다 — with() 한 번이 층 하나입니다.

가장 짧은 것부터 실무형까지

[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
# "env-filter" 없이는 EnvFilter 를 못 씁니다 ★ 가장 흔한 컴파일 에러
// ① 한 줄 — 실습·예제용
tracing_subscriber::fmt::init();

// ② 필터를 붙인 한 줄 — 작은 CLI 라면 여기까지로 충분합니다
tracing_subscriber::fmt()
    .with_env_filter("info,hyper=warn")
    .init();

// ③ 레이어 합성 — 서비스는 이 모양이 기본값입니다 ★
use tracing_subscriber::{fmt, EnvFilter, prelude::*};

pub fn init_log() {
    let filter = EnvFilter::builder()
        .with_default_directive(tracing::level_filters::LevelFilter::INFO.into())
        .from_env_lossy();          // RUST_LOG 가 이상해도 죽지 않습니다

    let json = std::env::var("LOG_FORMAT").as_deref() == Ok("json");

    tracing_subscriber::registry()
        .with(filter)
        .with(fmt::layer()
            .with_target(true)
            .with_thread_ids(!json)
            .with_ansi(!json && std::io::IsTerminal::is_terminal(&std::io::stdout())))
        .init();
    // json 이면 아래 LOG 05 의 .json() 갈래로 갑니다
}
from_env_lossy() 를 쓰세요 — from_env() 는 RUST_LOG 에 오타가 있으면 에러를 돌려주고, 그걸 unwrap() 하면 서비스가 시작도 못 합니다. lossy 는 이상한 지시자만 버리고 나머지를 살립니다.

with_ansi 는 자동이 아닙니다 — 파이프로 넘겨도 색 코드가 그대로 나갑니다. std::io::IsTerminal 로 판단하거나(Rust 1.70+), 운영에서는 무조건 끄세요. ESC[32m 같은 쓰레기가 로그 저장소에 쌓이는 것을 막습니다.

RUST_LOG 문법 전부 — 이 표 하나면 끝납니다 🟡 중급

지시자(directive) 의 문법

RUST_LOG = 지시자[,지시자,...]

지시자 = target[span{field=value}]=level
         └────┘ └──────────────┘ └───┘
          모듈 경로   span 이름·필드    레벨
         (전부 생략 가능 — 레벨만 써도 됩니다)

level = error < warn < info < debug < trace   (또는 off)
        숫자 1~5 로도 씁니다 (1=error … 5=trace)

★ 왼쪽에서 오른쪽으로 읽지 말고 "가장 구체적인 지시자가 이긴다"로 읽으세요
# ── 레벨만 ────────────────────────────────
RUST_LOG=info                    # 전부 info 이상
RUST_LOG=off                     # 전부 끄기

# ── 모듈별 ────────────────────────────────
RUST_LOG=warn,myapp=debug        # 기본 warn, 내 크레이트만 debug ★가장 흔함
RUST_LOG=myapp::db=trace         # 특정 모듈만
RUST_LOG=info,hyper=off,h2=off   # 시끄러운 크레이트 입막음
RUST_LOG=debug,sqlx::query=info  # sqlx 가 쿼리를 전부 찍는 걸 막기

# ── span 이름으로 (tracing 전용) ───────────
RUST_LOG=[request]=debug         # request 라는 span 안에서만 debug
RUST_LOG=myapp[db]=trace         # myapp 크레이트의 db span 안에서만

# ── span 필드 값으로 (tracing 전용) ★ ──────
RUST_LOG=[request{user_id=42}]=trace   # 특정 사용자 요청만 trace
RUST_LOG=[request{path}]=debug         # path 필드가 있기만 하면
필드 값 필터가 진짜 무기입니다 — 운영에서 “특정 고객만 이상하다”일 때 그 고객 요청만 trace 로 켤 수 있습니다. 전체를 trace 로 켰다가 디스크를 채우는 사고를 막아 줍니다.

use tracing_subscriber::{reload, EnvFilter, prelude::*};

let (filter, handle) = reload::Layer::new(EnvFilter::new("info"));
tracing_subscriber::registry()

    .with(tracing_subscriber::fmt::layer())
    .init();

// 나중에 (예: 관리용 HTTP 엔드포인트에서)
async fn set_level(body: String) -> StatusCode {
    match handle.modify(|f| *f = EnvFilter::new(&body)) {
        Ok(_)  => StatusCode::OK,        // 재배포 없이 debug 로 전환 ★
        Err(_) => StatusCode::BAD_REQUEST,
    }
}
이 엔드포인트는 반드시 보호하세요 — 누구나 부를 수 있으면 trace 로 올려 디스크를 채우는 공격이 됩니다. 내부망 전용 포트에 두거나 관리자 인증 뒤에 두고, 일정 시간 뒤 자동 복귀를 넣는 것이 안전합니다.

레이어별 필터와 “두 곳으로 동시에 쓰기” 🔴 실무

전역 필터 vs 레이어별 필터

use tracing_subscriber::{fmt, filter, EnvFilter, Layer, prelude::*};

// 터미널에는 사람이 읽을 것만, 파일에는 debug 까지 전부
let (file_w, _guard) = tracing_appender::non_blocking(
    tracing_appender::rolling::daily("logs", "app.log"));

tracing_subscriber::registry()
    // ① 콘솔 — info 이상만, 색 있음
    .with(fmt::layer()
        .with_ansi(true)
        .with_filter(EnvFilter::new("info")))
    // ② 파일 — debug 까지, 색 없음, JSON
    .with(fmt::layer()
        .json()
        .with_ansi(false)
        .with_writer(file_w)
        .with_filter(EnvFilter::new("debug,hyper=warn")))
    // ③ 지표용 — 특정 target 만 골라서
    .with(MetricsLayer::new()
        .with_filter(filter::filter_fn(|m| m.target().starts_with("biz::"))))
    .init();
전역 필터와 레이어 필터는 곱해집니다 — .with(EnvFilter) 는 구독자 전체에, .with_filter(...) 는 그 레이어에만 걸립니다. 전역이 info 인데 레이어가 debug 를 원하면 debug 는 안 옵니다 — 전역을 trace 로 열고 레이어별로 좁히는 것이 정석입니다.

조건부 레이어 — 타입이 안 맞을 때

// ✗ 이건 컴파일 안 됩니다 — if 의 두 갈래 타입이 다릅니다
// let layer = if json { fmt::layer().json() } else { fmt::layer() };

// ✔ 방법 1 — Boxed 로 타입을 지웁니다
use tracing_subscriber::Layer;
let layer = if json {
    fmt::layer().json().boxed()
} else {
    fmt::layer().pretty().boxed()
};

// ✔ 방법 2 — Option<Layer> 도 Layer 입니다 (None 이면 없는 셈)
let otel = if otel_on { Some(otel_layer()) } else { None };

tracing_subscriber::registry()
    .with(EnvFilter::from_default_env())
    .with(layer)
    .with(otel)                      // None 이어도 그대로 넘깁니다 ★
    .init();
// 라이브러리에서 구독자를 설치하면 안 됩니다.
// 대신 "레이어를 돌려주는 함수"를 공개하세요 ★
pub fn my_layer<S>() -> impl Layer<S>
where S: tracing::Subscriber + for<'a> tracing_subscriber::registry::LookupSpan<'a>
{ ... }
구독자도 프로세스당 하나입니다. init() 은 두 번째 호출에서 패닉하고 try_init() 은 Err 를 돌려줍니다. 라이브러리는 절대 구독자를 설치하지 마세요 — 앱의 로깅 설정을 통째로 빼앗는 셈입니다.
정리 — 구독자는 registry() + with() 반복으로 조립합니다. 필터는 앞에(뒤 레이어가 아예 안 불립니다), 색은 터미널일 때만, RUST_LOG 는 target[span{field}]=level 한 줄 문법이 전부이고 span 필드 필터가 운영에서 가장 강력한 손잡이입니다.

구조적 로깅 — 문자열이 아니라 필드로 남깁니다

구조적 로깅의 요점은 message 를 줄이고 필드를 늘리는 것입니다.

LOG 07

비동기 · Tokio — span 이 .await 를 건너 이어지는 원리

비동기 태스크는 스레드에 붙어 있지 않습니다. .await 에서 양보하고, 다음에 깨어날 때는 다른 워커 스레드일 수 있습니다. 그래서 스레드 로컬에 문맥을 담는 옛 방식은 여기서 깨지고, tracing 은 그것을 구조로 풀었습니다.

span 은 스레드가 아니라 Future 에 붙어 있습니다 — 그래서 워커를 옮겨도 안 끊깁니다.

왜 enter() 를 .await 너머로 들면 안 되나

// ✗ 컴파일은 되지만 틀린 코드입니다
async fn bad(id: u64) {
    let span = tracing::info_span!("job", id);
    let _g = span.enter();          // 가드가 .await 를 넘어 살아 있습니다
    do_io().await;                  // ← 여기서 태스크가 양보합니다
    tracing::info!("끝");
}
// 무슨 일이 나나
//   · 양보한 사이 그 스레드가 '다른 태스크'를 돌립니다
//   · 그런데 현재 span 은 여전히 job{id} 로 남아 있습니다
//   · 남의 태스크 로그에 내 id 가 붙습니다 ★ 문맥 오염
// ✔ 방법 1 — 어트리뷰트 (거의 항상 이걸 씁니다)
#[tracing::instrument(skip_all, fields(id))]
async fn good1(id: u64) {
    do_io().await;
    tracing::info!("끝");
}

// ✔ 방법 2 — Instrument 트레이트로 Future 를 감쌉니다
use tracing::Instrument;
async fn good2(id: u64) {
    async {
        do_io().await;
        tracing::info!("끝");
    }
    .instrument(tracing::info_span!("job", id))   // ★
    .await;
}

// ✔ 방법 3 — 동기 블록만 감쌀 때
span.in_scope(|| { /* .await 없는 코드만 */ });
원리 한 줄 — Instrumented<F> 는 poll() 을 감싸서 폴링 직전에 enter, 폴링이 끝나면 exit 합니다. 즉 span 이 Future 자체에 소유되므로, 어느 스레드에서 폴링되든 문맥이 정확히 그 태스크만 따릅니다.

태스크를 띄울 때 문맥 잇기

use tracing::{Instrument, Span};

// ① spawn 은 문맥을 자동으로 물려주지 않습니다
tokio::spawn(async { work().await });          // ✗ 부모 span 없음

// ② 현재 span 을 명시적으로 물려줍니다 ★
tokio::spawn(work().instrument(Span::current()));

// ③ 새 span 을 만들되 부모를 이어 붙입니다
let parent = Span::current();
tokio::spawn(async move {
    let sp = tracing::info_span!(parent: &parent, "worker", shard = 3);
    async { work().await }.instrument(sp).await;
});

// ④ 아예 부모를 끊고 싶을 때 (배경 잡업 등)
let sp = tracing::info_span!(parent: None, "cron");
// blocking 작업도 마찬가지입니다
let sp = Span::current();
tokio::task::spawn_blocking(move || {
    let _g = sp.enter();          // 여기는 .await 가 없으니 enter 가 안전합니다
    heavy_cpu_work();
}).await?;
“요청 ID 가 배경 작업 로그에 안 붙는다”는 거의 항상 ①번 실수입니다. tokio::spawn 은 완전히 독립된 태스크를 만들기 때문에 .instrument(Span::current()) 를 붙여 주지 않으면 문맥이 끊깁니다.

use tower_http::trace::TraceLayer;
use tracing::info_span;

let app = Router::new()
    .route("/orders/{id}", get(get_order))
    .layer(
        TraceLayer::new_for_http()
            // 요청마다 span 을 하나 만듭니다 ★
            .make_span_with(|req: &http::Request<_>| {
                let rid = req.headers().get("x-request-id")
                    .and_then(|v| v.to_str().ok())
                    .unwrap_or("-");
                info_span!("http",
                    method = %req.method(),
                    path   = %req.uri().path(),
                    request_id = %rid,
                    status = tracing::field::Empty,   // 나중에 채웁니다
                )
            })
            .on_response(|res: &http::Response<_>, lat: std::time::Duration, sp: &tracing::Span| {
                sp.record("status", res.status().as_u16());
                tracing::info!(duration_ms = lat.as_millis() as u64, "요청 완료");
            })
    );
레이어 순서가 중요합니다 — TraceLayer 를 가장 바깥(가장 마지막 .layer())에 두어야 인증 실패·타임아웃·패닉까지 전부 기록됩니다. 안쪽에 두면 그 앞에서 잘린 요청은 기록이 없습니다.

파일 출력과 로테이션 — WorkerGuard 를 놓치면 로그가 사라집니다

pub fn init_log() -> WorkerGuard {

        .with(EnvFilter::from_default_env())
        .with(fmt::layer().with_writer(std::io::stderr))   // 사람용

성능 — 꺼진 로그는 얼마나 싼가, 켠 로그는 얼마나 비싼가

“로그를 많이 남기면 느려진다”는 말은 절반만 맞습니다. 꺼진 로그는 거의 공짜이고(원자적 비교 한 번), 컴파일 타임에 지우면 완전히 0 입니다. 비싼 것은 켠 상태에서의 포맷·할당·쓰기이고, 그건 측정해서 다뤄야 합니다.

use opentelemetry::{global, trace::TracerProvider as _, KeyValue};
use opentelemetry_sdk::{trace::SdkTracerProvider, Resource,
                        propagation::TraceContextPropagator};
use opentelemetry_otlp::{SpanExporter, WithExportConfig};
use tracing_subscriber::{fmt, EnvFilter, prelude::*};

pub fn init_telemetry() -> anyhow::Result<SdkTracerProvider> {
    // ① W3C traceparent 를 읽고 쓰는 전파기 — 이게 없으면 헤더가 안 붙습니다
    global::set_text_map_propagator(TraceContextPropagator::new());

    // ② OTLP/gRPC exporter — Collector 의 4317 포트로
    let exporter = SpanExporter::builder()
        .with_tonic()
        .with_endpoint("http://otel-collector:4317")
        .build()?;

    // ③ 프로바이더 — 배치 전송 + 리소스(service.name 은 사실상 필수)
    let provider = SdkTracerProvider::builder()
        .with_batch_exporter(exporter)          // 전용 스레드가 모아서 보냅니다
        .with_resource(Resource::builder()
            .with_service_name("order-api")
            .with_attribute(KeyValue::new("deployment.environment", "prod"))
            .build())
        .build();
    global::set_tracer_provider(provider.clone());

    // ④ tracing 레이어 — 내 span 이 OTel span 으로 복제됩니다 ★
    let otel = tracing_opentelemetry::layer()
        .with_tracer(provider.tracer("order-api"));

    tracing_subscriber::registry()
        .with(EnvFilter::from_default_env())
        .with(fmt::layer().json())
        .with(otel)
        .init();
    Ok(provider)          // main 이 끝날 때 shutdown() 을 불러야 합니다
}

호출하는 쪽 — 현재 span 을 헤더에 씁니다

use opentelemetry::global;
use opentelemetry_http::HeaderInjector;
use tracing_opentelemetry::OpenTelemetrySpanExt;   // .context() 를 줍니다

#[tracing::instrument(skip_all, fields(sku))]
async fn check_stock(client: &reqwest::Client, sku: &str)
    -> anyhow::Result<Stock>
{
    let mut req = client.get(format!("http://stock/v1/{sku}")).build()?;

    // 현재 tracing span → OTel 문맥 → traceparent 헤더 ★
    let cx = tracing::Span::current().context();
    global::get_text_map_propagator(|p| {
        p.inject_context(&cx, &mut HeaderInjector(req.headers_mut()))
    });
    // 나가는 헤더: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
    //                              ↑ trace_id(16바이트)            ↑ 내 span_id   ↑ 샘플링 플래그

    Ok(client.execute(req).await?.json().await?)
}
헤더 규격은 W3C Trace Context — traceparent 와 tracestate 두 개입니다. 자바(Spring) · Go · .NET 서비스도 같은 헤더를 읽으므로 언어가 섞여도 한 트리가 됩니다. 직접 헤더를 만들지 말고 전파기에 맡기세요 — 플래그 비트와 버전 바이트를 손으로 쓰면 틀립니다.

            AppError::Internal(e) => {
                tracing::error!(error = %format!("{e:#}"), "요청 실패");   // 5xx 만 error
                // 클라이언트에는 내부 사정을 보내지 않습니다 — 문구 고정
                (StatusCode::INTERNAL_SERVER_ERROR, "internal error".to_string())
            }
        };
        (status, Json(json!({ "error": body }))).into_response()
    }
}
4xx 를 error! 로 찍는 순간 알람이 무의미해집니다 — 봇이 잘못된 URL 을 긁기만 해도 에러 대시보드가 빨개집니다. “내가 고칠 수 있는 것만 error”가 기준입니다.

panic::set_hook — 기본 훅을 감쌉니다

pub fn install_panic_hook() {
    let default_hook = std::panic::take_hook();      // 기본 훅(stderr 출력)을 보관

    std::panic::set_hook(Box::new(move |info| {
        // 페이로드는 &str 또는 String — 둘 다 시도합니다
        //   (Rust 1.89 부터는 info.payload_as_str() 한 줄로 됩니다)
        let msg = info.payload().downcast_ref::<&str>().copied()
            .or_else(|| info.payload().downcast_ref::<String>().map(String::as_str))
            .unwrap_or("(문자열이 아닌 페이로드)");
        let location = info.location()
            .map(|l| format!("{}:{}:{}", l.file(), l.line(), l.column()));

        // ★ 로거로 — 현재 span 의 문맥(요청 ID 등)이 그대로 붙습니다
        tracing::error!(
            panic.message  = msg,
            panic.location = location.as_deref(),
            backtrace      = %std::backtrace::Backtrace::force_capture(),
            "패닉"
        );
        default_hook(info);          // 기본 훅도 불러 stderr 에는 여전히 남깁니다
    }));
}
훅은 unwinding 전에 불립니다 — 그래서 현재 span 이 아직 살아 있고 요청 ID 가 붙습니다. force_capture() 는 RUST_BACKTRACE 와 무관하게 백트레이스를 만듭니다(비용이 있으니 패닉에서만). init_log() 바로 다음 줄에서 설치하세요.

임베디드 · no_std — defmt 는 포맷을 호스트로 미룹니다

MCU 에는 파일도 stdout 도 없고, 플래시 64KB 에 core::fmt 를 넣을 자리도 없습니다. defmt(deferred formatting) 는 발상을 뒤집습니다 — 장치는 “몇 번 문장인지”와 원시 값만 보내고, 문자열로 만드는 일은 PC 가 합니다. 그래서 빠르고, 작고, 그 대가로 호스트에 같은 ELF 가 있어야 읽힙니다.

포맷은 장치가 아니라 호스트에서 — 장치가 보내는 것은 문장 번호와 원시 값뿐입니다.

#![no_std]
#![no_main]

use defmt::{info, warn, unwrap, Format};
use defmt_rtt as _;       // ★ 링크만 하면 전역 로거가 됩니다 (use 만으로 충분)
use panic_probe as _;     // 패닉을 defmt 로 찍고 프로브를 멈춥니다

#[derive(Format)]         // Debug 대신 Format — 호스트에서 포맷됩니다
struct Reading { temp_c: f32, ok: bool }

#[cortex_m_rt::entry]
fn main() -> ! {
    let r = Reading { temp_c: 23.5, ok: true };

    info!("측정값 {:?}", r);                 // Format 구현으로 통째로
    info!("temp = {=f32} C", r.temp_c);      // ★ 타입 힌트 — 값 4바이트만 보냅니다
    warn!("배터리 {=u8}%", 12u8);
    info!("버퍼 {=[u8]:#x}", &[0xde, 0xad]); // 슬라이스 · 16진수 지정

    let v = unwrap!(sensor.read());          // Err 면 defmt 로 남기고 패닉
    //      ↑ core 의 .unwrap() 은 Debug 포맷 코드를 플래시에 끌어옵니다
    loop { cortex_m::asm::wfi(); }
}
{=u8} 같은 타입 힌트가 핵심입니다 — 힌트가 있으면 컴파일러가 정확히 그 바이트 수만 전송합니다. {:?} 는 Format 구현을 따라가므로 조금 더 큽니다. {=str} 은 문자열을 통째로 보내니 동적 문자열은 되도록 피하세요.
