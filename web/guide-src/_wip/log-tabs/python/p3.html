LOG 07

성능 — 로깅이 느려지는 지점은 세 군데뿐

로깅은 보통 공짜에 가깝습니다. 그런데 초당 수만 줄을 찍거나 네트워크로 바로 보내는 순간 갑자기 병목이 됩니다. 비싼 곳이 어디인지 알면 고치는 방법도 정해져 있습니다.

비싼 것은 언제나 입출력입니다 — 큐 하나로 요청 스레드에서 그 비용을 떼어냅니다.

① lazy 포매팅 — %s 를 쓰는 이유

# ❌ 레벨이 꺼져 있어도 문자열이 먼저 만들어집니다
logger.debug(f"주문 {order!r} 사용자 {user!r} 항목 {items!r}")
#   repr() 세 번 + 문자열 결합이 '무조건' 실행된 뒤 버려집니다

# ✅ 레벨이 켜져 있을 때만 만들어집니다
logger.debug("주문 %r 사용자 %r 항목 %r", order, user, items)

# ✅ 계산 자체가 비싸면 미리 물어봅니다
if logger.isEnabledFor(logging.DEBUG):
    logger.debug("응답 전문 %s", json.dumps(payload, ensure_ascii=False))

# ✅ structlog 는 키=값이라 이 문제가 거의 없습니다
log.debug("주문 조회", order_id=order.id, item_count=len(items))
ruff 가 잡아 줍니다 — G004(logging-f-string) 규칙을 켜면 f-string 로깅을 전부 찾아냅니다. [tool.ruff.lint] select = ["G"] 한 줄이면 됩니다. 팀 규칙으로 한 번에 정리하기 좋은 항목입니다.

② 얼마나 차이 나는지 직접 재기

# bench_log.py
import logging, timeit

logging.basicConfig(level=logging.INFO)   # DEBUG 는 꺼진 상태
log = logging.getLogger("bench")
payload = {"a": list(range(100)), "b": "x" * 200}

def lazy():   log.debug("payload %s", payload)
def eager():  log.debug(f"payload {payload}")
def guarded():
    if log.isEnabledFor(logging.DEBUG):
        log.debug("payload %s", payload)

for f in (lazy, eager, guarded):
    t = timeit.timeit(f, number=200_000)
    print(f"{f.__name__:8s} {t:.3f}s")

# 결과의 순서는 환경과 무관하게 항상 같습니다
#   guarded  < lazy  <<  eager
#   (eager 만 payload 를 20만 번 문자열로 만듭니다)
절대값을 외우지 마세요. 파이썬 버전 · CPU · 터미널 종류에 따라 몇 배씩 달라집니다. 중요한 건 순서이고, 그 순서는 어디서 재도 같습니다. “우리 서버에서 얼마인가”는 위 스크립트를 그 서버에서 돌려 보면 됩니다.

한 단계 더 — QueueHandler 로 입출력을 떼어내기 🟡 중급

구조 — 요청 스레드는 큐에 넣기만 합니다

[요청 스레드]  logger.info(...)
                 │
                 ▼  put()  ← 아주 쌉니다 (메모리 큐)
            ┌──────────┐
            │  Queue   │
            └──────────┘
                 │
                 ▼  get()   ← 별도 스레드 하나가 소비
        [QueueListener 스레드]
                 │
                 ├─ FileHandler   (디스크 대기)
                 ├─ Sentry        (네트워크 대기)
                 └─ StreamHandler

★ 느린 목적지가 요청 처리 시간에 영향을 주지 않습니다
★ 프로세스가 죽을 때 큐에 남은 로그는 사라질 수 있습니다 → 종료 시 flush 필요
Python 3.12 부터는 dictConfig 에서 바로 구성됩니다. 그 전에는 코드로 QueueListener 를 만들고 start() 를 직접 불러야 했습니다. 아래에 두 방식을 모두 적어 두었습니다.

설정 두 가지 방식

# ── Python 3.12+ : dictConfig 만으로
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {"json": {"()": "pythonjsonlogger.json.JsonFormatter"}},
    "handlers": {
        "file": {"class": "logging.handlers.RotatingFileHandler",
                 "filename": "logs/app.log", "maxBytes": 50_000_000,
                 "backupCount": 5, "encoding": "utf-8",
                 "formatter": "json"},
        "queue": {
            "class": "logging.handlers.QueueHandler",
            "handlers": ["file"],       # ★ 리스너가 뒤에서 처리할 핸들러들
            "respect_handler_level": True,
        },
    },
    "root": {"level": "INFO", "handlers": ["queue"]},
}
import logging.config, atexit
logging.config.dictConfig(LOGGING)

# 리스너를 켜고, 종료할 때 반드시 멈춥니다(남은 로그 flush)
qh = logging.getHandlerByName("queue")      # 3.12+
if qh and qh.listener:
    qh.listener.start()
    atexit.register(qh.listener.stop)
# ── 3.11 이하 : 코드로 직접
import queue, atexit, logging
from logging.handlers import QueueHandler, QueueListener

q = queue.Queue(-1)                     # 무제한 (메모리 주의)
file_h = logging.handlers.RotatingFileHandler("logs/app.log",
            maxBytes=50_000_000, backupCount=5, encoding="utf-8")

listener = QueueListener(q, file_h, respect_handler_level=True)
listener.start()
atexit.register(listener.stop)          # ★ 빠뜨리면 종료 시 로그가 날아갑니다

root = logging.getLogger()
root.handlers = [QueueHandler(q)]
root.setLevel(logging.INFO)
listener.stop() 을 빠뜨리면 프로세스가 끝날 때 큐에 남아 있던 마지막 로그가 사라집니다. 하필 죽기 직전의 로그가 가장 중요한 로그라서, 이게 빠지면 조사 자체가 불가능해집니다.

LOG 08

프레임워크 연동 — Django · Flask · FastAPI

프레임워크마다 자기 로거를 미리 설정해 둡니다. 내 설정과 그 설정이 겹치면 같은 줄이 두 번 찍히거나 포맷이 뒤섞입니다. 해결의 원칙은 하나입니다 — 핸들러는 root 한 곳에만.

중복 출력은 언제나 핸들러가 두 곳에 붙은 것입니다 — 한 곳만 남기면 끝납니다.

Django — settings.LOGGING 이 dictConfig 입니다

    "version": 1,
    "disable_existing_loggers": False,

                 "fmt": "%(asctime)s %(levelname)s %(name)s %(message)s"},
    },
    "filters": {
        "require_debug_false": {"()": "django.utils.log.RequireDebugFalse"},
    },

        "console": {"class": "logging.StreamHandler",
                    "stream": "ext://sys.stdout", "formatter": "json"},
    },
    "root": {"level": "INFO", "handlers": ["console"]},
    "loggers": {
        # 4xx/5xx 응답과 예외
        "django.request": {"level": "WARNING", "propagate": True},
        # ★ SQL 전문 — 개발에서만 켭니다. 운영에서 켜면 로그가 폭발합니다

Django 의 기본 설정을 덮어쓰고 있다는 걸 잊지 마세요. Django 는 자체 DEFAULT_LOGGING 을 가지고 있고, 내 LOGGING 은 그것과 병합됩니다. django.request 를 지정하지 않으면 500 에러가 이메일로 발송되는 기본 핸들러(mail_admins)가 살아 있을 수 있습니다.

from fastapi import FastAPI

    import uvicorn
    uvicorn.run("app.main:app", host="0.0.0.0", port=8000,
                log_config=None)     # ★ uvicorn 설정을 통째로 끄기

#   (uvicorn 액세스 로그는 필드가 고정이라 커스터마이즈가 어렵습니다)
import time
from starlette.middleware.base import BaseHTTPMiddleware

class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        t0 = time.perf_counter()
        response = await call_next(request)
        logger.info("http_request",
                    extra={"method": request.method,
                           "route": request.scope.get("route").path
                                    if request.scope.get("route") else "-",
                           "status": response.status_code,
                           "duration_ms": round((time.perf_counter()-t0)*1000, 1)})
        return response

app.add_middleware(AccessLogMiddleware)
# 그리고 uvicorn.access 는 꺼 둡니다
logging.getLogger("uvicorn.access").disabled = True

logging_tree.printout()

#     o<--"uvicorn"
#     |   Level INFO
#     |   Handler Stream <stderr>          ← ❌ 여기! 중복의 원인

for name in ("", "uvicorn", "uvicorn.access", "app", "app.billing"):
    lg = logging.getLogger(name)

증상원인과 처방
두 번 나온다자식 로거에 핸들러가 있고 propagate=True → 자식의 handlers 를 비우거나 propagate=False
안 나온다① 로거 레벨 ② 핸들러 레벨 ③ propagate=False 인데 핸들러 없음 ④ disable_existing_loggers 가 True
포맷이 섞인다프레임워크 핸들러가 살아 있음 → handlers: []
액세스 로그만 다르다uvicorn.access 를 끄고 미들웨어로 직접 남기기
gunicorn 에서만 이상워커 fork 이후 설정이 필요 → post_fork 훅에서 다시 dictConfig
gunicorn 의 post_fork 훅 — 파일 핸들러나 큐 리스너처럼 프로세스마다 따로 있어야 하는 자원은 fork 이후에 만들어야 합니다. gunicorn.conf.py 에 def post_fork(server, worker): setup() 를 두세요.
정리 — 원칙은 하나입니다 — 핸들러는 root 한 곳에만 두고, 프레임워크 로거는 {"handlers": [], "propagate": True} 로 비워서 넘겨받습니다. Django 는 settings.LOGGING, Flask 는 앱 생성 전에 dictConfig, uvicorn 은 log_config=None 입니다. 이상하면 logging_tree.printout() 한 줄로 트리를 눈으로 보세요.
LOG 09

요청 추적 — request-id 를 모든 줄에 붙이기

운영 로그에서 가장 자주 하는 일은 “이 사용자의 이 요청이 무슨 일을 겪었나”를 따라가는 것입니다. 동시에 수백 요청이 도는 서버에서 그게 가능하려면 같은 요청에서 나온 줄에 같은 표식이 있어야 합니다.

미들웨어가 만들고, 필터가 붙이고, 응답 헤더로 되돌려 줍니다 — 세 곳만 손대면 됩니다.

표준 logging 으로 — contextvars + Filter

# app/logging_filters.py
import contextvars, logging

request_id_var = contextvars.ContextVar("request_id", default="-")
user_id_var    = contextvars.ContextVar("user_id", default="-")

class RequestIdFilter(logging.Filter):
    """모든 LogRecord 에 request_id · user_id 를 채워 넣습니다."""
    def filter(self, record):
        record.request_id = request_id_var.get()
        record.user_id    = user_id_var.get()
        return True        # ★ 반드시 True — False 면 로그가 버려집니다

필터는 핸들러에 붙이세요. 로거에 붙이면 그 로거를 거치지 않는 서드파티 로그에는 안 붙습니다. 핸들러에 붙이면 그 핸들러로 나가는 모든 줄에 적용됩니다.

미들웨어 — 만들고, 헤더로 돌려주고, 비우기

# FastAPI / Starlette
import uuid
from starlette.middleware.base import BaseHTTPMiddleware
from app.logging_filters import request_id_var

class RequestIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        # 앞단(Nginx·게이트웨이)이 준 값이 있으면 그대로 이어받습니다
        rid = request.headers.get("X-Request-Id") or uuid.uuid4().hex[:12]
        token = request_id_var.set(rid)
        try:
            response = await call_next(request)
            response.headers["X-Request-Id"] = rid   # ★ 사용자에게 돌려주기
            return response
        finally:
            request_id_var.reset(token)              # ★ 반드시 원복

app.add_middleware(RequestIdMiddleware)
# Django 미들웨어
class RequestIdMiddleware:
    def __init__(self, get_response): self.get_response = get_response
    def __call__(self, request):
        rid = request.headers.get("X-Request-Id") or uuid.uuid4().hex[:12]
        token = request_id_var.set(rid)
        try:
            response = self.get_response(request)
            response["X-Request-Id"] = rid
            return response
        finally:
            request_id_var.reset(token)
reset(token) 이 왜 필요한가 — 워커 스레드는 재사용됩니다. 원복하지 않으면 다음 요청의 로그에 이전 요청의 id 가 남을 수 있습니다. try / finally 로 감싸는 것이 안전합니다.

한 단계 더 — LoggerAdapter 와 structlog 🟡 중급

LoggerAdapter — 특정 구간에만 값을 붙일 때

import logging

class OrderAdapter(logging.LoggerAdapter):
    def process(self, msg, kwargs):
        extra = kwargs.setdefault("extra", {})
        extra.update(self.extra)      # 어댑터가 들고 있는 값
        return msg, kwargs

base = logging.getLogger(__name__)

def process_order(order):
    log = OrderAdapter(base, {"order_id": order.id, "shop_id": order.shop_id})
    log.info("검증 시작")            # order_id · shop_id 자동 포함
    log.info("결제 요청")
    log.info("완료", extra={"amount": order.amount})
방법언제
Filter ★모든 줄에 붙는 값 (request_id · env · 버전)
LoggerAdapter함수 · 클래스 구간 단위 값 (order_id)
extra=그 한 줄에만 있는 값
structlog bind위 셋을 한 방식으로 처리
어댑터는 중첩할 수 있습니다 — 어댑터를 감싼 어댑터도 동작합니다. 다만 이 지점에서 코드가 지저분해지기 시작하는데, 그 때가 structlog 로 넘어갈 시점입니다.

structlog — 같은 일을 한 줄로

import structlog
from structlog.contextvars import (bind_contextvars, clear_contextvars,
                                   bound_contextvars)

log = structlog.get_logger()

# 미들웨어에서
async def dispatch(self, request, call_next):
    clear_contextvars()
    bind_contextvars(request_id=rid, path=request.url.path)
    response = await call_next(request)
    bind_contextvars(status=response.status_code)
    log.info("http_request")
    return response

# 구간 단위 — with 블록을 벗어나면 자동으로 사라집니다
with bound_contextvars(order_id=order.id):
    log.info("검증 시작")
    log.info("결제 요청")

# 특정 객체에 묶어 두기
olog = log.bind(order_id=order.id, shop_id=order.shop_id)
olog.info("완료", amount=order.amount)
asyncio 에서 특히 잘 맞습니다. contextvars 는 태스크를 만들 때 값이 복사되므로, asyncio.gather 로 동시에 도는 여러 작업이 각자의 request_id 를 유지합니다. 스레드 로컬(threading.local)로는 이게 안 됩니다.

백그라운드 작업에서 가장 자주 끊깁니다. Celery · RQ · BackgroundTasks 는 다른 프로세스·다른 컨텍스트에서 돌기 때문에 request_id 를 인자로 명시해 넘기지 않으면 추적이 그 자리에서 끊깁니다.

OpenTelemetry 를 쓴다면 trace_id 를 그대로

from opentelemetry import trace

class TraceFilter(logging.Filter):
    def filter(self, record):
        span = trace.get_current_span()
        ctx = span.get_span_context()
        if ctx and ctx.is_valid:
            record.trace_id = format(ctx.trace_id, "032x")
            record.span_id  = format(ctx.span_id, "016x")
        else:
            record.trace_id = record.span_id = "-"
        return True

직접 만들 필요가 없을 수도 있습니다 — opentelemetry-instrumentation-logging 을 설치하면 trace_id · span_id 를 자동으로 레코드에 넣어 줍니다. 이미 OTel 을 쓰고 있다면 request_id 대신 trace_id 를 표식으로 삼는 것도 좋은 선택입니다.
정리 — contextvars 에 담고, Filter 로 꺼내 붙이고, 응답 헤더로 돌려줍니다. 필터는 핸들러에 붙이고, reset(token) 으로 반드시 원복합니다. 백그라운드 작업으로 넘어갈 때는 인자로 명시해 전달해야 끊기지 않습니다. OTel 을 쓴다면 trace_id 를 그대로 쓰는 편이 낫습니다.
