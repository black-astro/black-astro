LOG 01

왜 print 를 버리는가 — logging 의 다섯 부품

print 는 끌 수가 없습니다. 어디서 났는지, 언제 났는지, 어느 요청에서 났는지도 모릅니다. 표준 logging 은 그 네 가지를 전부 해결하려고 만들어진 물건이고, 부품이 다섯 개라는 것만 알면 나머지는 설정 문제입니다.

로그 한 줄은 레벨 검사 두 번과 필터 두 번을 지나야 나옵니다 — 안 보이는 로그의 원인은 대부분 이 넷 중 하나입니다.

print 가 무너지는 지점 다섯

# 흔한 시작
def charge(order_id, amount):
    print("결제 시작", order_id)      # ① 운영에서 끌 수가 없습니다
    try:
        pg.pay(order_id, amount)
    except Exception as e:
        print("실패!", e)             # ② 스택 트레이스가 없습니다
    print("결제 끝")                   # ③ 언제 찍혔는지 모릅니다
                                      # ④ 어느 모듈·어느 요청인지 모릅니다
                                      # ⑤ 파일로 못 보냅니다 (셸 리다이렉트뿐)

print 가 느리다는 것도 사실입니다 — print 는 매번 sys.stdout 에 씁니다. 컨테이너에서 stdout 이 파이프로 물려 있으면 버퍼가 차는 순간 프로세스가 멈춰 기다립니다. 초당 수천 줄을 찍는 배치에서 실제로 겪는 사고입니다.

logging 으로 바꾸면 이렇게 됩니다

메시지 뒤에 %s 로 넘기는 이유 — logger.info("x=%s", x) 는 그 레벨이 켜져 있을 때만 문자열을 만듭니다. logger.info(f"x={x}") 는 레벨이 꺼져 있어도 f-string 이 먼저 계산됩니다. DEBUG 로그 수천 줄에서 이 차이가 그대로 CPU 로 나옵니다(LOG 07).

한 단계 더 — 부품 다섯 개의 역할 🟡 중급

Logger · Handler · Formatter · Filter · LogRecord

부품하는 일
Logger코드가 부르는 입구. 이름으로 계층을 만듭니다 (app.billing 은 app 의 자식). 레벨을 여기서 한 번 검사합니다
Handler어디로 보낼지. 콘솔 · 파일 · 소켓 · 큐 · Sentry. 로거 하나에 여러 개를 달 수 있고, 각각 자기 레벨을 가집니다
Formatter어떤 모양으로. 사람이 읽는 한 줄이냐 JSON 이냐가 여기서 갈립니다
Filter통과시킬지 · 값을 더할지. 로거에도 핸들러에도 붙일 수 있습니다. request_id 주입과 마스킹이 전부 여기서 일어납니다
LogRecord한 줄에 해당하는 객체. 시각 · 레벨 · 모듈 · 줄번호 · 스레드 · 예외 정보를 들고 다닙니다
파이썬 로깅은 Java 의 log4j 를 그대로 옮겨 온 설계입니다. 그래서 getLogger · 레벨 · 핸들러 · 어펜더(=핸들러) 개념이 자바와 똑같습니다. 자바를 해 본 적이 있다면 이름만 바꿔 읽으면 됩니다.

getLogger(__name__) 이 관례인 이유

# app/billing/pg.py  →  __name__ 은 "app.billing.pg"
logger = logging.getLogger(__name__)

# 이름이 점으로 이어지면 자동으로 부모-자식이 됩니다
#   root
#    └ app
#       └ app.billing
#          └ app.billing.pg      ← 여기서 찍은 로그가

# 부모 쪽에서 통째로 조절됩니다
logging.getLogger("app.billing").setLevel(logging.DEBUG)
#   → app.billing 아래 전부 DEBUG 로 열립니다

# 시끄러운 라이브러리 하나만 조용히
logging.getLogger("urllib3").setLevel(logging.WARNING)
logging.getLogger("botocore").setLevel(logging.WARNING)
# ❌ 하지 말 것 — 루트 로거에 바로 찍기
logging.info("주문 처리")     # 이름이 "root" 라 어디서 났는지 못 봅니다

# ❌ 모든 모듈이 같은 이름을 쓰기
logger = logging.getLogger("myapp")   # 모듈별로 못 끕니다

# ✅ 모듈마다 __name__
logger = logging.getLogger(__name__)
왜 이게 실무에서 크게 다른가 — 장애 조사 중에 “결제 모듈만 DEBUG 로 열어 주세요” 라는 요청이 옵니다. __name__ 을 썼다면 설정 한 줄로 끝나고, "myapp" 하나로 통일했다면 전체가 DEBUG 로 열려 로그가 폭발합니다.

실무에선 이렇게 — 설정은 진입점 한 곳에서만 🔴 실무

❌ 라이브러리·모듈이 설정을 건드림
# mylib/core.py  — 남의 앱에 쓰이는 코드
import logging
logging.basicConfig(level=logging.DEBUG)   # ❌ 남의 설정을 덮어씁니다

logger = logging.getLogger(__name__)
logger.addHandler(logging.StreamHandler()) # ❌ 핸들러를 스스로 답니다
                                           #    → 앱 쪽 설정과 겹쳐 두 번 찍힘

패키지를 import 한 것만으로 앱의 로그 포맷이 바뀌고 줄이 두 번 나옵니다. 실제로 유명 라이브러리들이 이 실수로 이슈를 받아 왔습니다.

✅ 라이브러리는 NullHandler 만
# mylib/__init__.py
import logging
logging.getLogger(__name__).addHandler(logging.NullHandler())
#   "핸들러가 없습니다" 경고만 막고, 아무것도 출력하지 않습니다

# mylib/core.py
logger = logging.getLogger(__name__)
logger.debug("내부 상태 %s", state)   # 앱이 켜 주면 보입니다

# app/main.py  — 설정은 애플리케이션 진입점 딱 한 곳
logging.config.dictConfig(LOGGING)   # LOG 03

“누가 설정하는가”를 한 곳으로 못 박는 것이 로깅 설계에서 가장 먼저 정할 규칙입니다.

정리 — logging 은 Logger → Filter → Handler → Formatter 네 부품이 LogRecord 하나를 넘겨 가며 처리하는 구조입니다. 모듈마다 logging.getLogger(__name__) 한 줄만 두고, 설정은 앱 진입점 한 곳에서만 합니다. 이 두 가지만 지켜도 “로그가 안 나온다 / 두 번 나온다” 사고의 대부분이 사라집니다.
LOG 02

레벨 설계 — 무엇을 언제 남기나

레벨은 “나중에 이 줄을 볼 사람이 누구인가”로 정합니다. DEBUG 는 나를 위한 것이고, WARNING 부터는 남이 새벽에 깨어나 보는 것입니다. 이 기준 하나로 대부분의 다툼이 끝납니다.

로그는 많이 남길수록 찾기 쉽고 비쌉니다 — 그 사이에서 고르는 손잡이가 레벨입니다.

다섯 레벨 — 이 기준으로 고릅니다

레벨값이 줄을 보게 될 사람
DEBUG10나(개발자). 변수 값 · 분기 · 외부 응답 원문. 운영에서는 꺼 둡니다
INFO ★20운영자. “무슨 업무가 일어났나” — 주문 접수 · 결제 승인 · 배치 시작·종료. 운영 기본값
WARNING30아침에 확인할 사람. 지금은 돌지만 이상함 — 재시도 성공 · 폴백 사용 · 사용 중단 예정 API
ERROR40지금 봐야 하는 사람. 이 요청·이 작업이 실패했음. 사용자 한 명이 피해를 봤습니다
CRITICAL50새벽에 깨울 사람. 프로세스를 더 못 이어감 — DB 접속 완전 실패 · 필수 설정 없음
가장 흔한 오용 — except 안에서 무조건 logger.error 를 부르는 것. 재시도로 복구됐다면 WARNING 이고, 사용자에게 정상 응답을 돌려줬다면 ERROR 가 아닙니다. ERROR 가 하루 5만 건 나오는 시스템은 ERROR 를 아무도 안 봅니다.

실제 코드에서의 선택

logger = logging.getLogger(__name__)

def place_order(req):
    logger.debug("요청 원문 %s", req)                    # 개발용
    order = Order.create(req)
    logger.info("주문 생성 order=%s user=%s amount=%s",   # ★ 업무 사실
                order.id, order.user_id, order.amount)

    try:
        pay(order)
    except TransientError as e:
        logger.warning("PG 일시 오류, 재시도합니다 order=%s err=%s",
                       order.id, e)                       # 복구 가능
        retry(order)
    except PgError:
        logger.exception("결제 실패 order=%s", order.id)   # 요청 실패
        raise

    return order

# 프로세스가 못 뜨는 상황
if not settings.DB_URL:
    logger.critical("DB_URL 이 없습니다. 종료합니다")
    sys.exit(1)
INFO 한 줄에 무엇을 넣나 — “누가 · 무엇을 · 얼마나 · 결과” 네 가지입니다. user=1234 order=A-991 amount=39000 status=paid 처럼 키=값 형태로 적어 두면, 나중에 JSON 으로 옮길 때 그대로 필드가 됩니다(LOG 05).

한 단계 더 — 레벨이 두 번 검사된다는 것 🟡 중급

로거 레벨과 핸들러 레벨

import logging

logger = logging.getLogger("app")
logger.setLevel(logging.DEBUG)          # ① 로거 문턱 — 여기를 먼저 통과해야

console = logging.StreamHandler()
console.setLevel(logging.INFO)          # ② 콘솔에는 INFO 이상만

filehdlr = logging.FileHandler("app.log")
filehdlr.setLevel(logging.DEBUG)        # ② 파일에는 DEBUG 까지 전부

logger.addHandler(console)
logger.addHandler(filehdlr)

logger.debug("자세한 값")   # 콘솔 ✗ / 파일 ✓
logger.info("업무 사실")     # 콘솔 ✓ / 파일 ✓

# ★ 로거 레벨이 INFO 였다면 debug 는 ①에서 죽어
#   파일 핸들러가 DEBUG 여도 절대 안 나옵니다 — 사고 1위
“DEBUG 로 켰는데 왜 안 나오죠?” 의 90%가 이것입니다. 로거는 DEBUG, 핸들러는 INFO 로 되어 있거나 그 반대입니다. 둘 다 열어야 보입니다.

레벨 상속과 NOTSET

# 특정 가지만 열기

# ── 지금 어떤 상태인지 눈으로 확인 (디버깅에 최고)

실무에선 이렇게 — 환경별 기본 레벨 🔴 실무

환경 변수 하나로 바꾸기

import os, logging

LEVEL = os.getenv("LOG_LEVEL", "INFO").upper()
#   로컬       LOG_LEVEL=DEBUG
#   스테이징   LOG_LEVEL=DEBUG  (문제 조사 중이면)
#   운영       LOG_LEVEL=INFO   ★ 기본
#   부하 시험  LOG_LEVEL=WARNING

logging.getLogger().setLevel(LEVEL)

# 시끄러운 서드파티는 항상 한 단계 올려 둡니다
for name in ("urllib3", "botocore", "asyncio", "PIL", "matplotlib"):
    logging.getLogger(name).setLevel(logging.WARNING)
재배포 없이 레벨을 바꾸고 싶다면 — 관리자 전용 엔드포인트를 하나 두고 logging.getLogger(name).setLevel(lv) 를 부르게 만듭니다. 장애 중에 결제 모듈만 3분간 DEBUG 로 열었다가 되돌리는 식으로 씁니다. (권한 검사와 자동 원복 타이머를 꼭 함께 두세요.)

로그가 많아 못 쓰겠다면 — 표본과 억제

import logging, random, time

class SampleFilter(logging.Filter):
    """DEBUG 는 1%만 남깁니다. INFO 이상은 전부 통과."""
    def __init__(self, rate=0.01):
        super().__init__(); self.rate = rate
    def filter(self, record):
        if record.levelno > logging.DEBUG:
            return True
        return random.random() < self.rate

class RateLimitFilter(logging.Filter):
    """같은 메시지는 60초에 한 번만."""
    def __init__(self, period=60):
        super().__init__(); self.period = period; self.seen = {}
    def filter(self, record):
        key = (record.name, record.levelno, record.msg)
        now = time.monotonic()
        if now - self.seen.get(key, -1e9) < self.period:
            return False
        self.seen[key] = now
        return True

logging.getLogger("app").addFilter(RateLimitFilter())
표본 추출은 마지막 수단입니다. 먼저 레벨을 정직하게 다시 나누세요 — “루프 안에서 매 건마다 INFO” 같은 것이 진짜 원인인 경우가 대부분입니다. 건별 로그는 DEBUG, 배치 단위 요약은 INFO 로 바꾸면 줄 수가 수백 배 줄어듭니다.
정리 — 레벨은 “이 줄을 볼 사람이 누구인가”로 정합니다. 운영 기본은 INFO, 시끄러운 서드파티는 WARNING 으로 올려 두고, 로거 레벨과 핸들러 레벨이 둘 다 열려 있어야 로그가 보입니다. ERROR 는 진짜 실패에만 쓰세요 — 남발하면 아무도 안 봅니다.
LOG 03

설정하는 세 가지 방법 — dictConfig 만 남습니다

basicConfig 는 연습용, fileConfig 는 레거시, dictConfig 가 실무의 답입니다. 셋의 차이와, 남들이 반드시 한 번은 밟는 함정 두 개를 짚습니다.

질문 두 개로 끝납니다 — 라이브러리면 설정하지 않고, 앱이면 dictConfig.

① basicConfig — 연습과 스크립트용

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s [%(name)s:%(lineno)d] %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
logging.getLogger(__name__).info("시작")

# ★ 함정 1 — 루트에 핸들러가 이미 있으면 '조용히 무시'됩니다
logging.basicConfig(level=logging.DEBUG)   # 두 번째 호출은 아무 일도 안 함
logging.basicConfig(level=logging.DEBUG, force=True)   # 3.8+ 강제로 재설정

# ★ 함정 2 — 누군가 먼저 logging.info() 를 부르면
#   그 순간 루트에 핸들러가 자동으로 붙어 이후 basicConfig 가 안 먹습니다
Jupyter 에서 로그가 안 보이는 이유도 이것입니다. 노트북 커널이 이미 루트 핸들러를 달아 두었기 때문에 basicConfig 가 무시됩니다. force=True 를 주세요.

한 단계 더 — dictConfig 한 벌 통째로 🟡 중급

복붙해서 바로 도는 실무 설정

# app/logging_config.py
import os, logging.config

LEVEL = os.getenv("LOG_LEVEL", "INFO").upper()

LOGGING = {
    "version": 1,                     # 항상 1 (지금까지 바뀐 적 없습니다)
    "disable_existing_loggers": False, # ★ 반드시 False — 아래 함정 설명 참고

    "formatters": {
        "plain": {
            "format": "%(asctime)s %(levelname)-8s [%(name)s:%(lineno)d] "
                      "%(message)s",
            "datefmt": "%Y-%m-%d %H:%M:%S",
        },
        "json": {                      # LOG 05 에서 자세히
            "()": "pythonjsonlogger.json.JsonFormatter",
            "fmt": "%(asctime)s %(levelname)s %(name)s %(message)s",
        },
    },

    "filters": {
        "request_id": {"()": "app.logging_filters.RequestIdFilter"},   # LOG 09
        "mask": {"()": "app.logging_filters.MaskFilter"},              # LOG 10
    },

    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "stream": "ext://sys.stdout",   # ★ stderr 가 기본이라 명시합니다
            "level": LEVEL,
            "formatter": "plain",
            "filters": ["request_id", "mask"],
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "filename": "logs/app.log",
            "maxBytes": 50 * 1024 * 1024,   # 50MB
            "backupCount": 5,
            "encoding": "utf-8",
            "level": "INFO",
            "formatter": "json",
            "filters": ["request_id", "mask"],
        },
    },

    "root": {"level": LEVEL, "handlers": ["console", "file"]},

    "loggers": {
        "app":       {"level": LEVEL, "propagate": True},
        "urllib3":   {"level": "WARNING"},
        "botocore":  {"level": "WARNING"},
        "asyncio":   {"level": "WARNING"},
    },
}

def setup():
    os.makedirs("logs", exist_ok=True)
    logging.config.dictConfig(LOGGING)
# app/main.py  — 진입점 맨 위에서 딱 한 번
from app.logging_config import setup
setup()

import logging
logging.getLogger(__name__).info("애플리케이션 시작 env=%s", os.getenv("ENV"))
"()" 키가 뭔가요 — “이 클래스를 직접 만들어 달라”는 뜻의 특수 키입니다. 값은 import 경로이고, 같은 dict 의 나머지 키가 생성자 인자로 들어갑니다. 필터 · 커스텀 포매터는 전부 이 방식으로 붙입니다.
ext:// 접두사 는 “파이썬 객체를 import 해서 넣어라”는 뜻입니다 (ext://sys.stdout). YAML 파일에 설정을 둘 때 특히 유용합니다. cfg:// 는 같은 설정 dict 안의 다른 값을 참조합니다.

실무에선 이렇게 — 두 개의 함정 🔴 실무

❌ disable_existing_loggers 를 그냥 둠
LOGGING = {
    "version": 1,
    # "disable_existing_loggers" 를 안 적으면 기본값이 True 입니다
    "root": {"level": "INFO", "handlers": ["console"]},
}
logging.config.dictConfig(LOGGING)

# 이 시점에 '이미 만들어져 있던' 모든 로거가 통째로 꺼집니다.
#   → import 순서에 따라 어떤 모듈은 로그가 나오고 어떤 모듈은 안 나옴
#   → "왜 이 파일만 로그가 없죠?" 라는 유령 버그의 정체
✅ 항상 False 로 못 박기
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,   # ★ 언제나 이렇게
    "root": {"level": "INFO", "handlers": ["console"]},
}

# 설정이 제대로 먹었는지 눈으로 확인하는 방법
import logging_tree; logging_tree.printout()
#   또는
root = logging.getLogger()
print(root.level, [h for h in root.handlers])

함정 ② — 핸들러가 두 번 붙습니다

# ❌ 모듈이 import 될 때마다 핸들러를 답니다
logger = logging.getLogger(__name__)
logger.addHandler(logging.StreamHandler())   # 재로딩·재시작마다 하나씩 추가
#   → 같은 줄이 2번, 3번, 4번 찍힙니다 (특히 Jupyter · 자동 재시작 서버)

# ✅ 방법 1 — dictConfig 만 쓰고 addHandler 를 코드에서 안 씁니다
# ✅ 방법 2 — 부득이하면 중복을 확인
if not logger.handlers:
    logger.addHandler(logging.StreamHandler())

# ✅ 방법 3 — 다시 설정하기 전에 비웁니다
for h in list(logger.handlers):
    logger.removeHandler(h); h.close()
“로그가 두 번 나온다”의 원인은 딱 두 가지입니다 — 핸들러 중복 등록이거나 propagate 로 부모까지 올라간 것입니다. logging_tree.printout() 을 찍어 보면 어느 쪽인지 3초 만에 보입니다.

YAML 로 빼 두기 — 배포 환경별 파일

# logging.prod.yaml
version: 1
disable_existing_loggers: false
formatters:
  json:
    (): pythonjsonlogger.json.JsonFormatter
    fmt: "%(asctime)s %(levelname)s %(name)s %(message)s"
handlers:
  console:
    class: logging.StreamHandler
    stream: ext://sys.stdout
    formatter: json
    level: INFO
root:
  level: INFO
  handlers: [console]
loggers:
  urllib3:
    level: WARNING
import yaml, logging.config, os

path = os.getenv("LOG_CONFIG", "logging.dev.yaml")
with open(path, encoding="utf-8") as f:
    logging.config.dictConfig(yaml.safe_load(f))
파일로 뺄지 코드에 둘지 — 환경이 2~3개면 파이썬 dict 하나에 환경 변수로 분기하는 편이 관리하기 쉽습니다. 운영팀이 재배포 없이 고쳐야 한다면 YAML 로 빼고 ConfigMap 등으로 마운트하세요.
정리 — 설정은 dictConfig 하나로 통일합니다. "disable_existing_loggers": False 를 반드시 적고, stream: ext://sys.stdout 을 명시하고(기본은 stderr), 진입점에서 딱 한 번 호출합니다. 코드 안에서 addHandler 를 부르기 시작하면 중복 출력이 따라옵니다.
