LOG 04

라이브러리 비교 — 표준 · structlog · loguru 그리고 나머지

결론부터 말하면 표준 logging 은 버리지 않습니다. 다른 라이브러리는 대부분 표준 위에 얹거나 표준으로 되돌려 보내는 물건이고, 그 이유는 여러분이 쓰는 모든 서드파티 패키지가 표준 logging 으로 로그를 남기기 때문입니다.

여섯 개를 다섯 잣대로 놓고 보면 고를 이유가 잣대마다 다르다는 것이 보입니다.

여섯 개, 한 문단씩

라이브러리어떤 물건이고 언제 고르나
logging (표준) ★사실상 표준입니다. 파이썬에 기본 포함이라 의존성이 0이고, Django · Flask · FastAPI · requests · boto3 등 거의 모든 패키지가 이걸로 로그를 냅니다. 설정이 장황한 것이 유일한 단점 — 그래서 dictConfig 한 벌을 만들어 두고 씁니다
structlog ★구조적(키=값) 로깅의 사실상 표준. 표준 logging 을 대체하지 않고 감쌉니다 — 앱 로그는 structlog 로 쓰고, 서드파티 로그는 표준 경로로 받아 같은 JSON 으로 합칩니다. 팀 서비스를 만든다면 기본 선택
logurufrom loguru import logger 한 줄이면 컬러 · 로테이션 · 트레이스백이 다 됩니다. 개인 프로젝트 · CLI · 스크립트에서 널리 씁니다. 다만 서드파티 로그를 받으려면 InterceptHandler 를 직접 붙여야 하고, 표준 dictConfig 생태계와 어긋납니다
picologgingMicrosoft 가 낸 C 확장 기반 고속 대체품. import 만 바꾸면 되는 구조라 솔깃하지만, 베타 표기가 오래 유지되고 새 파이썬 버전 대응이 느립니다. 신규 채택은 드묾 — 로깅이 진짜 병목임을 측정으로 확인한 뒤에만 검토하세요
python-json-logger포매터 하나짜리 패키지. 기존 dictConfig 에서 formatter 만 바꾸면 그날로 JSON 로그가 됩니다. 가장 적은 변경으로 구조적 로깅에 진입하는 길이라 널리 씁니다
logbook2010년대 초 표준 logging 의 대안으로 나온 물건. 지금은 신규 채택이 사실상 없습니다. 오래된 코드베이스에서 만나면 표준으로 옮기는 것을 권합니다

고르는 기준 — 이 순서로 물어보세요

① 내가 만드는 것이 라이브러리인가?
     → 표준 logging + NullHandler. 끝. 다른 선택지 없음

② 파일 하나짜리 스크립트 · 개인 도구인가?
     → loguru 도 좋습니다 (설정 0줄로 시작)
     → 표준 basicConfig 한 줄도 충분합니다

③ 팀이 운영하는 서비스인가?
     → 표준 logging(dictConfig) 이 뼈대
     → 로그를 검색·집계해야 한다 → + structlog
     → 지금 당장 JSON 만 되면 된다 → + python-json-logger

④ 로깅이 프로파일러에서 상위에 잡히는가?
     → 먼저 QueueHandler · 레벨 조정 · 표본 추출 (LOG 07)
     → 그래도 안 되면 그때 picologging 을 '측정하고' 검토
가장 흔한 실수 — loguru 를 쓰면서 서드파티 로그가 사라진 줄 모르는 것입니다. loguru 는 자기만의 통로를 쓰므로, 표준 logging 으로 남긴 SQLAlchemy · uvicorn · requests 로그가 어디에도 안 나옵니다. InterceptHandler 를 반드시 붙이세요(아래 코드).

한 단계 더 — 각각을 실제로 써 보면 🟡 중급

loguru — 시작은 가장 짧습니다

uv add loguru
from loguru import logger

logger.info("주문 생성 order={} amount={}", "A-991", 39000)
logger.bind(request_id="r-77").info("컨텍스트가 붙습니다")

# 파일 · 로테이션 · 보관 · 압축이 인자 하나씩
logger.add("logs/app.log", rotation="50 MB", retention="14 days",
           compression="zip", level="INFO", enqueue=True)   # enqueue=멀티프로세스 안전

# JSON 으로
logger.add("logs/app.jsonl", serialize=True)

@logger.catch                      # 예외를 자동으로 잡아 트레이스백까지 기록
def risky(): 1 / 0
# ★ 표준 logging 을 쓰는 서드파티 로그를 loguru 로 넘겨받기
import logging, sys
from loguru import logger

class InterceptHandler(logging.Handler):
    def emit(self, record):
        try:
            level = logger.level(record.levelname).name
        except ValueError:
            level = record.levelno
        frame, depth = logging.currentframe(), 2
        while frame and frame.f_code.co_filename == logging.__file__:
            frame = frame.f_back; depth += 1
        logger.opt(depth=depth, exception=record.exc_info) \
              .log(level, record.getMessage())

logging.basicConfig(handlers=[InterceptHandler()], level=0, force=True)
loguru 의 진짜 장점은 enqueue=True 와 @logger.catch, 그리고 예쁜 트레이스백(변수 값까지 보여 줍니다)입니다. 운영 서비스라면 이 편의를 표준 생태계와의 어긋남과 맞바꿀 값어치가 있는지 따져 보세요.

LOG 05

구조적 로깅 — 사람이 읽는 글에서 기계가 읽는 데이터로

로그가 100만 줄이 되는 순간 grep 으로는 답이 안 나옵니다. “어제 3시 이후 결제가 실패한 사용자들의 평균 금액” 같은 질문에 답하려면 로그가 문장이 아니라 필드여야 합니다.

처리기 사슬 — 도형 모양이 곧 방향이고, 중간 어디든 내 함수를 하나 끼울 수 있습니다.

왜 바꾸나 — 같은 사건, 두 가지 기록

[사람이 읽는 줄]
2026-09-01 03:14 ERROR 결제 실패 (주문 A-991, 사용자 1234, 39000원)

  · 사람은 잘 읽습니다
  · "실패한 주문의 총 금액" 을 구하려면 정규식을 짜야 합니다
  · 메시지 문구를 조금만 바꿔도 그 정규식이 깨집니다

[기계가 읽는 줄 — JSON Lines]
{"timestamp":"2026-09-01T03:14:22Z","level":"error","event":"결제 실패",
 "order":"A-991","user_id":1234,"amount":39000,"service":"billing"}

  · Loki / OpenSearch / BigQuery 에서 바로 질의됩니다
      level="error" AND event="결제 실패" | sum(amount)
  · 필드를 추가해도 기존 질의가 안 깨집니다
  · 대시보드·알림 규칙을 로그 위에 바로 세울 수 있습니다
둘 중 하나를 고르는 게 아닙니다. 로컬 개발은 사람이 읽는 컬러 출력, 운영은 JSON — 환경 변수 하나로 렌더러만 바꾸면 됩니다. structlog 는 이 전환을 위해 만들어진 물건이라고 봐도 됩니다.

가장 짧은 길 — 포매터만 바꾸기

uv add python-json-logger
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "json": {
            "()": "pythonjsonlogger.json.JsonFormatter",
            "fmt": "%(asctime)s %(levelname)s %(name)s %(message)s "

            "rename_fields": {"asctime": "timestamp", "levelname": "level"},
            "json_ensure_ascii": False,     # 한글이 \\uXXXX 로 안 깨지게
        },
    },
    "handlers": {"console": {"class": "logging.StreamHandler",
                             "stream": "ext://sys.stdout",
                             "formatter": "json"}},
    "root": {"level": "INFO", "handlers": ["console"]},
}
# extra 로 필드를 얹습니다 (표준 logging 방식)
logger.info("결제 실패", extra={"order": "A-991", "user_id": 1234,
                                "amount": 39000})
# → {"timestamp":"...","level":"ERROR","message":"결제 실패",
#    "order":"A-991","user_id":1234,"amount":39000}

# ⚠ extra 키가 LogRecord 의 기존 속성과 겹치면 KeyError 가 납니다
#   금지어: name, msg, args, levelname, module, exc_info, message ...
logger.info("x", extra={"module": "billing"})   # ❌ 터집니다
logger.info("x", extra={"app_module": "billing"})  # ✅
extra 의 한계 — 매번 dict 를 손으로 넘겨야 하고, 요청 전체에 공통으로 붙는 값(request_id 등)을 다루기가 번거롭습니다. 그래서 실무에서는 Filter 로 자동 주입(LOG 09)하거나 structlog 의 bind 를 씁니다.

한 단계 더 — structlog 실전 설정 한 벌 🟡 중급

앱 로그와 서드파티 로그를 같은 JSON 으로 합치기

uv add structlog · 표준 logging 과 함께 씁니다(대체가 아닙니다)
# app/logging_config.py
import logging.config, os, sys
import structlog

DEV = os.getenv("ENV", "dev") == "dev"

# ── ① 앱 로그와 서드파티 로그가 공통으로 지나갈 처리기들
shared_processors = [
    structlog.contextvars.merge_contextvars,       # request_id 등 컨텍스트 병합
    structlog.stdlib.add_logger_name,              # "logger": "app.billing"
    structlog.stdlib.add_log_level,                # "level": "info"
    structlog.processors.TimeStamper(fmt="iso", utc=True),
    structlog.processors.StackInfoRenderer(),
    structlog.processors.format_exc_info,          # 예외를 문자열로
    structlog.processors.UnicodeDecoder(),
]

# ── ② 개발이면 컬러 콘솔, 운영이면 JSON
renderer = (structlog.dev.ConsoleRenderer(colors=True) if DEV
            else structlog.processors.JSONRenderer(ensure_ascii=False))

logging.config.dictConfig({
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "structured": {
            "()": structlog.stdlib.ProcessorFormatter,
            # 표준 logging 으로 들어온 로그도 같은 처리기를 태웁니다
            "foreign_pre_chain": shared_processors,
            "processors": [
                structlog.stdlib.ProcessorFormatter.remove_processors_meta,
                renderer,
            ],
        },
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler",
                    "stream": "ext://sys.stdout",
                    "formatter": "structured"},
    },
    "root": {"level": os.getenv("LOG_LEVEL", "INFO"), "handlers": ["console"]},
    "loggers": {"urllib3": {"level": "WARNING"},
                "botocore": {"level": "WARNING"}},
})

# ── ③ structlog 자신의 설정 — 최종 출력은 표준 logging 에 맡깁니다
structlog.configure(
    processors=shared_processors + [
        structlog.stdlib.ProcessorFormatter.wrap_for_formatter,
    ],
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,      # ★ 성능: 로거를 한 번만 만듭니다
)
# 쓰는 쪽
import structlog
log = structlog.get_logger(__name__)

log.info("주문 생성", order_id="A-991", amount=39000)

# 요청 단위 컨텍스트 (LOG 09 에서 미들웨어로 자동화합니다)
structlog.contextvars.bind_contextvars(request_id="r-77", user_id=1234)
log.info("결제 시도")          # request_id · user_id 가 자동으로 붙습니다
structlog.contextvars.clear_contextvars()
foreign_pre_chain 이 핵심입니다. 이 한 줄 덕분에 SQLAlchemy · uvicorn · requests 처럼 표준 logging 을 쓰는 로그도 같은 타임스탬프 · 같은 필드 이름 · 같은 JSON 모양으로 나옵니다. 수집기 입장에서 로그 종류가 한 가지가 되는 것이 구조적 로깅의 절반입니다.
cache_logger_on_first_use=True 는 운영에서 반드시 켭니다. 로거 객체를 매번 만들지 않아 체감할 만큼 빨라집니다. 대신 설정을 런타임에 다시 바꿀 수 없게 되므로, 개발 중에는 꺼 두어도 됩니다.

실무에선 이렇게 — 필드 이름을 미리 못 박습니다 🔴 실무

팀 표준 필드 — 처음에 정해 두세요

필드예 · 규칙
timestampISO 8601 · UTC (2026-09-01T03:14:22.481Z)
level소문자 info / error 로 통일
event · message변수를 넣지 않은 고정 문구 ★
service · envbilling · prod
request_id요청 하나를 잇는 키 (LOG 09)
trace_id · span_idOpenTelemetry 와 맞추기 (LOG 11)
duration_ms숫자로 — 문자열 "12ms" 금지
event 에 변수를 넣지 마세요. "주문 A-991 생성" 이라고 쓰면 event 값이 주문마다 달라져 “주문 생성이 몇 번 일어났나”를 셀 수 없습니다. 문구는 고정, 변하는 값은 필드로 — 이것이 구조적 로깅의 첫 번째 규칙입니다.

카디널리티 — 로그 비용이 터지는 자리

# ❌ 값의 종류가 무한한 필드를 인덱싱 대상으로 두면
log.info("조회", sql="SELECT * FROM orders WHERE id = 9912")  # 매번 다름
log.info("요청", url="/api/orders/9912?ts=1756...")            # 매번 다름

# ✅ 변하는 부분을 빼서 묶습니다
log.info("조회", sql_template="SELECT * FROM orders WHERE id = ?",
         rows=1, duration_ms=3)
log.info("요청", route="/api/orders/{id}", status=200, duration_ms=12)
#   → route 는 값의 종류가 수십 개뿐이라 집계·알림에 쓸 수 있습니다

# ✅ 큰 본문은 통째로 넣지 말고 요약과 해시만
log.debug("응답 수신", body_bytes=len(body),
          body_sha256=hashlib.sha256(body).hexdigest()[:12])
ECS · OTel 필드 규약을 참고하면 이름 짓기로 다투지 않습니다. Elastic Common Schema 는 service.name · event.action · error.type 같은 이름을 정해 두었고, OpenTelemetry 로그 규약도 거의 같은 이름을 씁니다. 둘 중 하나를 골라 그대로 따르는 것이 가장 빠릅니다.
정리 — 구조적 로깅의 핵심은 “문구는 고정, 값은 필드로” 한 문장입니다. 최소 변경으로 시작하려면 python-json-logger 포매터 교체, 제대로 하려면 structlog + ProcessorFormatter 로 앱 로그와 서드파티 로그를 같은 JSON으로 합칩니다. 필드 이름은 ECS 나 OTel 규약을 베껴 쓰세요.
LOG 06

파일 로테이션 — 디스크를 채우지 않는 법

로그로 디스크가 100% 차면 서비스가 죽습니다. DB 도 못 쓰고, 배포도 안 되고, ssh 도 힘들어집니다. 로테이션은 있으면 좋은 기능이 아니라 안 하면 반드시 사고가 나는 항목입니다.

크기로 자르면 상한이 예측되고, 날짜로 자르면 “그날의 로그”를 찾기 쉽습니다.

RotatingFileHandler — 크기 기준

"handlers": {
    "file": {
        "class": "logging.handlers.RotatingFileHandler",
        "filename": "logs/app.log",
        "maxBytes": 50 * 1024 * 1024,   # 50MB 넘으면 회전
        "backupCount": 5,               # app.log.1 ~ app.log.5 유지
        "encoding": "utf-8",            # ★ 없으면 윈도우에서 cp949 로 깨집니다
        "delay": True,                  # 첫 로그가 날 때 파일을 엽니다
        "level": "INFO",
        "formatter": "json",
    },
}
# 디스크 상한 = maxBytes × (backupCount + 1) = 300MB
#   ★ 이 계산을 문서에 적어 두세요. 용량 산정의 근거가 됩니다
# 코드로 직접 붙일 때
from logging.handlers import RotatingFileHandler
h = RotatingFileHandler("logs/app.log", maxBytes=50_000_000,
                        backupCount=5, encoding="utf-8")

# 회전 직후 압축하고 싶다면 rotator/namer 를 갈아 끼웁니다
import gzip, shutil, os
def gzip_rotator(source, dest):
    with open(source, "rb") as fi, gzip.open(dest, "wb") as fo:
        shutil.copyfileobj(fi, fo)
    os.remove(source)
h.rotator = gzip_rotator
h.namer = lambda name: name + ".gz"
encoding="utf-8" 은 선택이 아닙니다. 윈도우에서 이걸 빼면 시스템 기본 인코딩으로 열려 한글 로그에서 UnicodeEncodeError 가 납니다. 로깅이 예외를 던지면 그 줄은 표준 에러로 밀려나고 사라집니다.

TimedRotatingFileHandler — 시간 기준

"handlers": {
    "file": {
        "class": "logging.handlers.TimedRotatingFileHandler",
        "filename": "logs/app.log",
        "when": "midnight",     # S M H D · midnight · W0~W6(요일)
        "interval": 1,
        "backupCount": 14,      # 14일치 보관
        "encoding": "utf-8",
        "utc": True,            # ★ 서버 시간대가 섞이면 조사 때 지옥입니다
        "formatter": "json",
    },
}
# 결과 파일 이름
#   logs/app.log                 ← 지금 쓰는 것
#   logs/app.log.2026-09-01
#   logs/app.log.2026-08-31 ...
고르는 기준추천
디스크 상한이 중요Rotating(크기)
“그날 로그” 를 자주 찾음Timed(날짜)
트래픽이 들쭉날쭉Rotating — 폭주해도 상한이 지켜짐
보관 기간 규정이 있음Timed + backupCount = 일수
컨테이너로 배포둘 다 안 씀 — stdout 만
Timed 는 트래픽 폭주에 무방비입니다. 하루치 파일 하나가 40GB 가 되어도 자정까지 안 자릅니다. 규정상 날짜별이 필요하면 Timed 를 쓰되, 디스크 사용률 알림을 반드시 함께 거세요.

한 단계 더 — 여러 프로세스면 파이썬 로테이션이 깨집니다 🟡 중급

무슨 일이 벌어지나

gunicorn -w 4  →  워커 프로세스 4개가 같은 app.log 를 엽니다

  워커 A: 50MB 도달 → app.log 를 app.log.1 로 rename → 새 app.log 생성
  워커 B: (아직 옛 app.log 의 파일 핸들을 쥐고 있음)
          → app.log.1 이 되어 버린 파일에 계속 씁니다
  워커 C: 동시에 회전을 시도 → app.log.1 을 app.log.2 로 밀다가 충돌
          → 파일이 통째로 사라지거나, 로그가 뒤섞입니다

증상
  · 로그 줄이 중간중간 사라진다
  · app.log 가 비어 있는데 app.log.1 만 계속 커진다
  · 윈도우에서는 PermissionError 가 나며 로그가 멈춘다
이건 버그가 아니라 설계상 한계입니다. RotatingFileHandler 문서에도 “여러 프로세스에서 한 파일에 쓰는 것은 지원하지 않는다”고 적혀 있습니다. gunicorn · uvicorn 워커 · Celery 워커가 있다면 전부 해당됩니다.

세 가지 처방

방법내용
① stdout 만 ★앱은 stdout 에만 쓰고, 파일 관리는 컨테이너 런타임 · systemd-journald · 수집기에 맡깁니다. 컨테이너 환경의 정답
② WatchedFileHandler
+ logrotate		파일 회전은 OS 의 logrotate 가 하고, 파이썬은 파일이 바뀐 것을 감지해 다시 엽니다. 리눅스 전통 방식. 윈도우에서는 못 씁니다
③ 큐로 모으기QueueHandler 로 한 프로세스에 모아 거기서만 파일에 씁니다 (LOG 07). 또는 concurrent-log-handler 패키지로 파일 잠금을 씁니다
 
# /etc/logrotate.d/myapp   ← ② 방식
/var/log/myapp/*.log {
    daily
    rotate 14
    size 100M
    compress
    delaycompress
    missingok
    notifempty
    copytruncate    # 또는 create + 앱이 WatchedFileHandler 사용
}
copytruncate vs create — copytruncate 는 파일을 복사한 뒤 0으로 자르므로 앱이 아무것도 몰라도 되지만, 복사 중에 쓰인 로그가 유실될 수 있습니다. create + WatchedFileHandler 조합이 유실 없는 정석입니다.

실무에선 이렇게 — 컨테이너면 파일을 쓰지 않습니다 🔴 실무

❌ 컨테이너 안에서 파일 로그
"handlers": {
    "file": {"class": "logging.handlers.RotatingFileHandler",
             "filename": "/app/logs/app.log", ...}
}

컨테이너가 죽으면 로그도 같이 사라집니다. 볼륨을 붙여도 여러 파드가 같은 경로에 쓰면 섞이고, 파드 이름별로 나누면 파일이 무한히 늘어납니다. 게다가 디스크가 차면 노드 전체가 영향을 받습니다.

✅ stdout 한 곳으로만
"handlers": {
    "console": {"class": "logging.StreamHandler",
                "stream": "ext://sys.stdout",
                "formatter": "json"}
},
"root": {"level": "INFO", "handlers": ["console"]}
# 파일 관리는 런타임이 합니다
docker run --log-driver json-file \
  --log-opt max-size=50m --log-opt max-file=5 myapp

12-Factor App 원칙 그대로입니다 — 앱은 이벤트 스트림을 stdout 에 흘려보낼 뿐, 어디에 저장할지는 실행 환경이 정합니다.

그럼 파일 로그는 언제 쓰나 — 온프레미스 · 윈도우 서비스 · 데스크톱 앱 · 배치 스크립트처럼 실행 환경이 로그를 걷어 가 주지 않는 곳입니다. 이 경우에도 단일 프로세스인지 먼저 확인하고, 아니라면 위의 ②·③ 처방을 쓰세요.
정리 — 컨테이너면 stdout 하나로 끝냅니다. 파일에 써야 한다면 크기 기준 RotatingFileHandler + encoding="utf-8" 이 기본이고, 디스크 상한 = maxBytes × (backupCount+1) 을 계산해 문서에 적습니다. 프로세스가 여러 개면 파이썬 로테이션은 깨집니다 — logrotate 나 큐로 넘기세요.
