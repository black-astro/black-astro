LOG 10

민감정보 — 로그로 새는 것들과 막는 법

로그는 암호화되지 않고, 오래 보관되고, 많은 사람이 봅니다. 개발자 · 운영자 · 외주 · 수집기 SaaS 까지 닿습니다. 비밀번호 한 줄이 로그에 남으면 그건 평문 저장과 같은 사고입니다.

같은 요청, 두 가지 기록 — 필터 하나가 사고와 정상 사이를 가릅니다.

실제로 새는 다섯 가지 패턴

# ① 요청 바디를 통째로
logger.debug("요청 %s", await request.json())      # 비밀번호 · 카드번호 포함

# ② 객체를 repr 로 (가장 흔합니다)
logger.info("사용자 %r", user)
#   @dataclass 나 SQLAlchemy 모델은 기본 repr 이 '모든 필드'를 찍습니다
#   → password_hash, ssn, phone 이 전부 로그로

# ③ 예외 메시지에 접속 문자열
except OperationalError as e:
    logger.exception("DB 연결 실패")
#   psycopg 등의 에러 메시지에 host/user/password 가 들어 있는 경우가 있습니다

# ④ URL 쿼리스트링에 토큰
logger.info("호출 %s", url)      # https://api/x?access_token=eyJ...

# ⑤ 서드파티 DEBUG 로그
logging.getLogger("httpx").setLevel(logging.DEBUG)
#   요청·응답 '헤더'를 그대로 찍습니다 → Authorization 노출
②번이 압도적으로 많습니다. logger.info("사용자 %r", user) 한 줄이 테이블의 모든 컬럼을 로그로 옮깁니다. 모델 클래스에 __repr__ 을 직접 정의해 두는 것만으로 절반이 막힙니다.

마스킹 필터 — 핸들러에 붙입니다

# app/logging_filters.py
import logging, re

SECRET_KEYS = {"password", "passwd", "pwd", "token", "access_token",
               "refresh_token", "secret", "api_key", "authorization",
               "cookie", "set-cookie", "ssn", "card", "card_number"}

PATTERNS = [
    (re.compile(r'(?i)("(?:%s)"\s*:\s*)"[^"]*"' % "|".join(SECRET_KEYS)),
     r'\1"***"'),                                   # JSON 형태
    (re.compile(r'(?i)\b(bearer)\s+[A-Za-z0-9._\-]+'), r'\1 ***'),
    (re.compile(r'\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?(\d{4})\b'),
     r'****-****-****-\1'),                         # 카드번호
    (re.compile(r'(?i)(access_token|api_key)=[^&\s]+'), r'\1=***'),
]

class MaskFilter(logging.Filter):
    def filter(self, record):
        msg = record.getMessage()
        for pat, repl in PATTERNS:
            msg = pat.sub(repl, msg)
        record.msg, record.args = msg, ()   # 이미 합쳤으므로 args 는 비웁니다
        # extra 로 넘어온 값도 훑습니다
        for key in list(record.__dict__):
            if key.lower() in SECRET_KEYS:
                record.__dict__[key] = "***"
        return True
왜 핸들러에 붙이나 — 로거에 붙이면 그 로거를 지나는 줄만 걸러집니다. 핸들러에 붙이면 서드파티 로그를 포함해 그 출력으로 나가는 모든 줄이 걸러집니다. dictConfig 의 handlers.console.filters 에 넣으세요.

한 단계 더 — 애초에 안 만드는 것이 제일 낫습니다 🟡 중급

모델 쪽에서 막기

from dataclasses import dataclass, field

@dataclass
class User:
    id: int
    email: str
    password_hash: str = field(repr=False)    # ★ repr 에서 제외
    ssn: str = field(repr=False)

    def __repr__(self):                        # 아예 직접 정의하는 편이 확실
        return f"User(id={self.id})"

# Pydantic v2
from pydantic import BaseModel, SecretStr, Field
class LoginIn(BaseModel):
    email: str
    password: SecretStr           # str(v) 하면 '**********' 로 나옵니다
    card: str = Field(repr=False)

# SQLAlchemy 모델도 마찬가지
class Account(Base):
    def __repr__(self):
        return f"<Account id={self.id}>"
SecretStr 은 실수를 구조적으로 막습니다. 값을 꺼내려면 .get_secret_value() 를 명시적으로 불러야 하므로, 무심코 로그에 찍히는 경로가 코드 리뷰에서 눈에 띕니다.

structlog 는 처리기 하나로

SECRET_KEYS = {"password", "token", "api_key", "authorization", "card"}

def mask_processor(logger, method_name, event_dict):
    for k in list(event_dict):
        if k.lower() in SECRET_KEYS:
            event_dict[k] = "***"
        elif k.lower() == "email" and isinstance(event_dict[k], str):
            name, _, dom = event_dict[k].partition("@")
            event_dict[k] = f"{name[:2]}***@{dom}"
    return event_dict

structlog.configure(processors=[
    structlog.contextvars.merge_contextvars,
    mask_processor,                      # ★ 렌더러 '앞'에 둡니다
    structlog.processors.TimeStamper(fmt="iso", utc=True),
    structlog.processors.JSONRenderer(ensure_ascii=False),
])
# 시끄럽고 위험한 서드파티 로거는 아예 올려 둡니다
for name in ("httpx", "httpcore", "urllib3", "requests",
             "botocore", "boto3", "sqlalchemy.engine"):
    logging.getLogger(name).setLevel(logging.WARNING)
#   특히 sqlalchemy.engine 을 INFO 로 켜면
#   바인딩된 파라미터(= 실제 값)가 전부 로그로 나옵니다
sqlalchemy.engine = INFO 는 개발용입니다. SQL 과 함께 바인드 파라미터의 실제 값이 찍히므로, 운영에서 켜면 테이블의 데이터가 그대로 로그로 복사됩니다.

실무에선 이렇게 — 사고를 전제로 설계 🔴 실무

외부로 나갈 때 한 번 더 거릅니다

import sentry_sdk

def scrub(event, hint):
    req = event.get("request", {})
    if "data" in req:
        req["data"] = "[filtered]"
    if "headers" in req:
        for h in ("Authorization", "Cookie", "X-Api-Key"):
            req["headers"].pop(h, None)
    for k in ("user",):
        event.get(k, {}).pop("ip_address", None)
    return event

sentry_sdk.init(
    dsn=os.environ["SENTRY_DSN"],
    send_default_pii=False,     # ★ 기본으로 두세요 (True 면 IP·쿠키가 전송됩니다)
    before_send=scrub,
    traces_sample_rate=0.05,
)
“기본값이 안전한가”를 항상 확인하세요. Sentry 의 send_default_pii, loguru 의 diagnose=True (예외 발생 시 지역 변수 값까지 출력), Django 의 DEBUG=True 화면 — 전부 편하려고 켜 둔 옵션이 유출 경로가 됩니다.

배포 전 점검표

항목확인 방법
마스킹 필터가 붙었나모든 handlers 의 filters 목록에 있는지
필터에 테스트가 있나caplog 로 “비밀번호가 안 나오는지” 단정

보관 기간수집기에 90일 등 상한이 걸려 있는지
접근 권한로그 대시보드가 사내 인증 뒤에 있는지
유출 시 절차이미 저장된 로그를 지우는 방법이 있는지
 
# pytest 로 못 박아 두기
def test_비밀번호가_로그에_남지_않는다(caplog):
    with caplog.at_level(logging.INFO):
        logger.info('{"password":"hunter2"}')
    assert "hunter2" not in caplog.text
    assert "***" in caplog.text
필터는 조용히 깨집니다. 정규식 하나를 고치다 실수해도 아무 에러가 안 납니다. 테스트로 못 박아 두지 않으면 몇 달 뒤에 다시 새기 시작합니다.
정리 — 순서는 ① 애초에 안 만들기(__repr__ · SecretStr) ② 나가기 전에 거르기(핸들러에 붙인 마스킹 필터) ③ 외부 전송 직전에 한 번 더(before_send) 입니다. 그리고 필터가 동작하는지 테스트로 못 박아 두세요 — 조용히 깨지는 종류의 코드입니다.
LOG 11

내보내기 — Sentry · OpenTelemetry · 수집기

서버 안의 로그는 서버가 죽으면 같이 사라집니다. 그리고 서버가 10대가 되는 순간 ssh 로 grep 하는 방식은 끝납니다. 로그를 밖으로 내보내는 길은 크게 두 갈래입니다 — 앱이 직접 보내기와 수집기가 걷어 가기.

앱은 stdout 에 흘려보낼 뿐이고, 어디로 갈지는 바깥이 정합니다 — 예외 알림만 예외적으로 직접 보냅니다.

Sentry — 예외를 사람에게 알리는 길

event_level 을 INFO 로 두지 마세요. INFO 로그 하나하나가 이슈가 되어 요금과 알림이 폭발합니다. 기본값(ERROR)이 맞습니다. 그리고 같은 예외는 자동으로 묶이지만, 메시지에 변수를 넣으면 묶이지 않고 따로따로 쌓입니다(LOG 05 의 그 규칙).

Vector — 걷어 가면서 가공까지

# vector.toml
[sources.app]
type = "file"
include = ["/var/log/app/*.log"]

[transforms.parse]
type = "remap"
inputs = ["app"]
source = '''
  . = parse_json!(string!(.message))
  .service = "billing"
  # 마지막 방어선 — 혹시 새어 나온 값을 여기서 한 번 더 지웁니다
  if exists(.password) { .password = "***" }
  if exists(.token)    { .token = "***" }
'''

[sinks.opensearch]
type = "elasticsearch"
inputs = ["parse"]
endpoints = ["http://opensearch:9200"]
bulk.index = "app-logs-%Y.%m.%d"

[sinks.archive]
type = "aws_s3"
inputs = ["parse"]
bucket = "my-log-archive"
compression = "gzip"
“뜨거운 저장소 + 차가운 저장소” 구성이 비용에서 크게 이깁니다 — 최근 7~14일은 검색 가능한 곳(Loki · OpenSearch)에, 그 이상은 S3 에 gzip 으로 던져 둡니다. 규정상 1년 보관이 필요해도 검색 인덱스를 1년치 유지할 필요는 없습니다.

규모별 최소 구성

직접 보내는 핸들러의 위험

# ❌ 로그를 HTTP 로 동기 전송
class HttpLogHandler(logging.Handler):
    def emit(self, record):
        requests.post(URL, json=self.format(record))   # 요청 스레드가 멈춥니다
#   수집기가 느려지면 → 우리 API 응답이 느려집니다
#   수집기가 죽으면   → 우리 서비스도 같이 죽습니다

# ✅ 큐를 반드시 끼웁니다 (LOG 07)
#    QueueHandler → QueueListener → HttpLogHandler
#    + 타임아웃 · 재시도 상한 · 큐 최대 크기

q = queue.Queue(maxsize=10_000)      # ★ 무제한은 메모리 사고
class DropOldestQueueHandler(logging.handlers.QueueHandler):
    def enqueue(self, record):
        try:
            self.queue.put_nowait(record)
        except queue.Full:
            try: self.queue.get_nowait()   # 가장 오래된 것을 버리고
            except queue.Empty: pass
            self.queue.put_nowait(record)
로깅 때문에 서비스가 죽는 사고는 생각보다 흔합니다. 원칙은 “로그는 절대 요청 처리 경로를 막지 않는다” 입니다 — 비동기 · 상한 있는 큐 · 짧은 타임아웃 · 실패 시 조용히 버리기.
정리 — 앱은 stdout 에 JSON 한 줄만 씁니다. 거기서부터는 수집기(Fluent Bit · Vector)가 걷어 가 Loki · OpenSearch · S3 로 보냅니다. 예외 알림만 Sentry SDK 로 직접 보내고, OTel 을 쓴다면 trace_id 로 로그와 트레이스를 잇습니다. 직접 보내는 핸들러에는 반드시 큐와 상한을 두세요.
LOG 12

예외 로깅 — 트레이스백을 잃지 않는 법

장애 조사에서 가장 아까운 순간은 “에러가 났다는 건 아는데 어디서 났는지 모를 때” 입니다. 트레이스백은 가만두면 사라집니다 — 스레드에서, asyncio 태스크에서, 그리고 except: logger.error(str(e)) 한 줄에서.

맥락마다 담당자가 다릅니다 — 네 곳에 훅을 걸어야 트레이스백이 새지 않습니다.

기본기 — exception · exc_info · stack_info

try:
    pay(order)
except PgError:
    # ✅ ① 가장 흔한 형태 — ERROR 레벨 + 트레이스백
    logger.exception("결제 실패 order=%s", order.id)

    # ② 레벨을 바꾸고 싶으면 exc_info=True
    logger.warning("결제 실패(재시도 예정) order=%s", order.id, exc_info=True)
    logger.critical("복구 불가", exc_info=True)

    # ③ 예외 객체를 직접 줄 수도 있습니다 (3.x 공통)
    logger.error("결제 실패", exc_info=err)

    # ④ 예외가 아닌데 '여기까지 어떻게 왔는지' 가 궁금할 때
    logger.warning("이상한 상태", stack_info=True)

# ❌ 하지 말 것 — 트레이스백이 통째로 사라집니다
except Exception as e:
    logger.error(f"실패: {e}")      # 메시지 한 줄만 남습니다
    logger.error(str(e))            # 어디서 났는지 영영 모릅니다
logger.exception 은 except 블록 안에서만 씁니다. 밖에서 부르면 트레이스백 자리에 NoneType: None 만 찍힙니다. 그리고 exception 은 레벨이 ERROR 로 고정이라, 다른 레벨이 필요하면 exc_info=True 를 쓰세요.

한 번만 찍기 — 계층마다 찍지 않습니다

# ✅ 안쪽은 맥락만 붙여서 다시 던지고, 경계에서 한 번만 찍습니다
def repo():
    try: db.execute(...)
    except Exception as e:
        raise RepoError(f"주문 조회 실패 id={oid}") from e   # ★ from e

def api():
    try: service()
    except Exception:
        logger.exception("요청 처리 실패")   # 경계에서 딱 한 번
        return JSONResponse({"error": "internal"}, status_code=500)
raise ... from e 를 쓰면 트레이스백에 “The above exception was the direct cause of…” 로 원인 사슬이 그대로 남습니다. from 없이 던져도 __context__ 로 이어지지만, 의도한 변환임을 코드와 로그 양쪽에 남기는 편이 낫습니다.

복붙해서 진입점에 넣는 한 벌

# app/excepthooks.py
import asyncio, logging, sys, threading

logger = logging.getLogger("uncaught")

# ── ① 메인 스레드
def _sys_hook(exc_type, exc, tb):
    if issubclass(exc_type, KeyboardInterrupt):     # Ctrl+C 는 그대로 두기
        sys.__excepthook__(exc_type, exc, tb)
        return
    logger.critical("잡히지 않은 예외", exc_info=(exc_type, exc, tb))

# ── ② 다른 스레드 (Python 3.8+)
def _thread_hook(args):
    if issubclass(args.exc_type, SystemExit):
        return
    logger.critical("스레드에서 잡히지 않은 예외 thread=%s",
                    args.thread.name if args.thread else "-",
                    exc_info=(args.exc_type, args.exc_value, args.exc_traceback))

# ── ③ asyncio 이벤트 루프
def _loop_hook(loop, context):
    exc = context.get("exception")
    if exc is not None:
        logger.critical("asyncio 예외: %s", context.get("message"), exc_info=exc)
    else:
        logger.critical("asyncio 오류: %s", context.get("message"))

# ── ④ 소멸자·GC 중에 난 예외 (드물지만 원인 찾기가 가장 어렵습니다)
def _unraisable_hook(args):
    logger.error("unraisable: %s", args.err_msg or args.object,
                 exc_info=(args.exc_type, args.exc_value, args.exc_traceback))

def install():
    sys.excepthook = _sys_hook
    threading.excepthook = _thread_hook
    sys.unraisablehook = _unraisable_hook
    try:
        asyncio.get_running_loop().set_exception_handler(_loop_hook)
    except RuntimeError:
        pass          # 아직 루프가 없으면 시작 이벤트에서 다시 부릅니다
# app/main.py
from app.logging_config import setup
from app.excepthooks import install

setup()
install()          # ★ 진입점에서 한 번

# FastAPI 라면 루프가 뜬 뒤에 한 번 더
@app.on_event("startup")
async def _hooks():
    asyncio.get_running_loop().set_exception_handler(_loop_hook)
KeyboardInterrupt 와 SystemExit 은 걸러 주세요. Ctrl+C 로 끌 때마다 CRITICAL 로그와 Sentry 알림이 날아가면 사람들이 알림을 무시하기 시작합니다. 그게 진짜 손실입니다.
Python 3.11+ 의 ExceptionGroup — asyncio.TaskGroup 이나 except* 를 쓰면 여러 예외가 한꺼번에 올라옵니다. exc_info 로 넘기면 트레이스백이 트리 모양(+---)으로 찍히므로 JSON 로그에서는 줄바꿈이 포함된 한 필드가 됩니다 — 수집기 설정에서 여러 줄 처리를 확인하세요.

import atexit, logging, signal, sys

def shutdown(*_):
    logging.getLogger(__name__).info("종료 신호 수신, 로그를 비웁니다")
    logging.shutdown()        # ★ 모든 핸들러 flush + close
    sys.exit(0)

signal.signal(signal.SIGTERM, shutdown)   # 컨테이너는 SIGTERM 으로 멈춥니다
signal.signal(signal.SIGINT, shutdown)
atexit.register(logging.shutdown)

PYTHONUNBUFFERED=1 은 컨테이너의 필수 환경 변수입니다. 없으면 stdout 이 블록 단위로 버퍼링되어 프로세스가 죽는 순간 마지막 로그가 통째로 사라집니다. 하필 가장 필요한 그 로그입니다.
정리 — except 안에서는 logger.exception, 다른 레벨이 필요하면 exc_info=True 입니다. 같은 예외를 계층마다 찍지 말고 경계에서 한 번만 찍고, 안쪽은 raise ... from e 로 맥락만 붙입니다. 그리고 메인 · 스레드 · asyncio · 자식 프로세스 네 곳에 훅을 걸어야 “죽었는데 왜 죽었는지 모르는” 상황이 없어집니다. 마지막으로 PYTHONUNBUFFERED=1 과 logging.shutdown() 을 잊지 마세요.
