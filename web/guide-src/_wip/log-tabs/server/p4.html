LOG 08

저장소 네 가지 — 색인 방식이 요금표를 정합니다

Loki · Elasticsearch · ClickHouse · 클라우드 서비스는 "무엇을 미리 색인해 두는가"가 서로 다릅니다. 그 한 가지 선택이 저장 비용 · 조회 속도 · 할 수 있는 질문을 통째로 결정합니다.

저장소 비교 — 색인을 언제 만드느냐가 비용을 저장 쪽과 조회 쪽으로 나눕니다.

고르는 기준 — 질문의 모양으로 정합니다

주로 하는 질문맞는 저장소
"이 서비스의 최근 1시간 에러 줄을 보고 싶다"Loki — 라벨로 좁히면 아주 쌉니다
"이 요청 ID 가 들어간 줄 전부"Loki(시간 범위를 좁히면) · ES
"지난 30일 중 이 문구가 나온 모든 줄"ES/OpenSearch — 전문 검색이 필요
"경로별 p95 를 지난 90일 추이로"ClickHouse — 대량 집계
"임의의 필드 조합으로 자유롭게 탐색"ES/OpenSearch · ClickHouse
"규정상 3년 보관, 조회는 가끔"오브젝트 스토리지 + 필요 시 복원
"팀에 운영할 사람이 없다"클라우드 관리형
대부분의 조직에는 Loki 로 충분합니다. 장애 조사의 90%는 "최근 몇 시간, 특정 서비스, 특정 요청 ID"이고 이건 라벨 색인만으로 충분히 빠릅니다. ES 가 필요한 순간은 "무엇을 찾을지 모른 채 넓게 훑어야 할 때"이고, ClickHouse 가 필요한 순간은 "로그를 분석 데이터로 쓸 때"입니다.

각각을 얹을 때 실제로 손대는 설정

# Loki 3.x — 뜨거운 구간과 보존, 그리고 안전벨트
limits_config:
  retention_period: 336h            # 14일
  max_query_length: 721h
  ingestion_rate_mb: 20
  ingestion_burst_size_mb: 40
  max_streams_per_user: 10000       # ★ 라벨 카디널리티 안전벨트
  max_label_names_per_series: 15
compactor:
  retention_enabled: true
  delete_request_store: s3
schema_config:
  configs:
    - from: 2026-01-01
      store: tsdb
      object_store: s3
      schema: v13
      index: { prefix: index_, period: 24h }
overrides:
  audit:
    retention_period: 8760h         # 감사 로그 테넌트만 1년
// Elasticsearch / OpenSearch — ILM 으로 단계 강등
{
  "policy": { "phases": {
    "hot":   { "actions": { "rollover": { "max_primary_shard_size": "50gb",
                                          "max_age": "1d" } } },
    "warm":  { "min_age": "3d",  "actions": {
                 "forcemerge": { "max_num_segments": 1 },
                 "shrink": { "number_of_shards": 1 } } },
    "cold":  { "min_age": "14d", "actions": { "freeze": {} } },
    "delete":{ "min_age": "90d", "actions": { "delete": {} } }
  } }
}
Loki 에서 trace_id·user_id 를 라벨로 만들지 마세요. 라벨 조합 하나가 곧 스트림 하나이고, 스트림 수가 폭발하면 Loki 가 Elasticsearch 보다 비싸집니다. 그런 값은 본문에 두고 | json 으로 검색하거나, Loki 3.x 의 structured metadata 에 담습니다.

클라우드 로그 서비스 — 요금이 세 군데에서 붙습니다 🔴 실무

과금 구조를 먼저 이해합니다

붙는 자리성격대응
수집(ingest)보낸 GB 당 — 보통 여기가 제일 큼안 보내는 게 유일한 답
저장GB·월 — 오브젝트 스토리지보다 비쌈보존 기간 · 등급 강등
조회스캔한 GB 당 (또는 쿼리 시간)시간 범위를 좁혀 조회
내보내기다른 저장소로 빼낼 때 별도애초에 이중 저장 설계
정확한 단가는 여기 적지 않겠습니다 — 리전마다 다르고 자주 바뀝니다. 2026년 8월 기준 대략, 주요 클라우드의 로그 수집 단가는 GB 당 수십 센트 수준이라고만 기억하세요. 하루 43GB 를 그대로 보내면 수집 요금만 월 수백 달러가 되는 자릿수입니다. 직접 확인하는 방법 — 각 클라우드의 요금 페이지에서 "수집 · 저장 · 분석" 세 항목을 각각 찾고, 비용 탐색기에서 로그 서비스의 지난달 실제 청구액을 열어 보세요. 추정보다 지난달 청구서가 항상 정확합니다.

현실적인 하이브리드 구성

# 흔히 쓰는 두 갈래 저장 (수집기에서 라우팅)
                     ┌─→ Loki      : 14일 · 뜨거운 조사용
  수집기(Vector) ────┤
                     └─→ S3(Parquet/JSON.gz) : 1~3년 · 감사·규정용
                            └─→ 필요할 때만 Athena·ClickHouse 로 조회

# Vector 로 두 곳에 동시에 보내기
[sinks.loki]
type = "loki"
inputs = ["sample"]           # 샘플링된 것만

[sinks.archive]
type = "aws_s3"
inputs = ["parse"]            # ★ 샘플링 전 원본 전부
bucket = "corp-log-archive"
key_prefix = "nginx/date=%Y-%m-%d/"
compression = "gzip"
  [sinks.archive.encoding]
  codec = "json"
"조사용"과 "보관용"을 분리하는 것이 비용 설계의 핵심입니다. 조사용은 비싸고 빠른 곳에 짧게, 보관용은 싸고 느린 곳에 길게 둡니다. 오브젝트 스토리지 요금은 검색 엔진 저장 요금의 한 자릿수 분의 일 수준이라, 이 분리만으로 대부분의 비용 문제가 풀립니다.
정리 — Loki 는 라벨만, ES 는 전부, ClickHouse 는 칼럼으로 색인합니다. 비용은 저장에서 내거나 조회에서 내거나 둘 중 하나이고, 클라우드는 수집 · 저장 · 조회 세 군데에서 각각 붙습니다. 대부분은 Loki(짧게) + 오브젝트 스토리지(길게) 두 갈래면 충분합니다.
LOG 09

요청 ID — 서버 다섯 대의 로그를 한 줄로 잇기

"결제가 안 됐어요"라는 신고 하나에서 프록시 · 앱 · 결제 게이트웨이의 로그를 각각 찾아 헤매는 일이 조사의 대부분입니다. 맨 앞 프록시가 ID 를 하나 만들어 끝까지 전달하면 이 일이 검색 한 번으로 끝납니다.

시퀀스 — ID 는 가장 바깥에서 한 번 태어나 안쪽으로만 흐릅니다.

Nginx — 만들거나, 이어받거나

# http 블록
# ① 앞단이 준 값이 있으면 그것을, 없으면 $request_id 로 새로 만듭니다
map $http_x_request_id $req_id {
    default $http_x_request_id;
    ""      $request_id;          # 빈 값일 때만 새로 발급
}

# ② 로그에 적고
log_format json escape=json '{"ts":"$time_iso8601","id":"$req_id",'
    '"status":$status,"rt":$request_time,"uri":"$uri",'
    '"ua":"$upstream_addr","urt":"$upstream_response_time"}';

server {
    # ③ 백엔드로 넘기고
    proxy_set_header X-Request-Id $req_id;

    # ④ 클라이언트에게도 돌려줍니다 (always = 4xx·5xx 응답에도)
    add_header X-Request-Id $req_id always;

    # ⑤ 오류 페이지에 찍어 두면 고객센터가 바로 받아 적을 수 있습니다
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        internal;
        ssi on;
        root /usr/share/nginx/html;
    }
    location /api/ { proxy_pass http://backend; }
}
인터넷에서 들어온 X-Request-Id 를 그대로 믿으면 안 됩니다. 누구든 아무 값이나 넣어 보낼 수 있고, 그러면 남의 요청과 같은 ID 로 로그가 섞입니다. 맨 바깥 프록시에서는 무조건 새로 발급하고, 내부망의 프록시에서만 이어받는 것이 안전합니다 ($http_x_request_id 대신 그냥 $request_id).

다른 앞단들은 어떻게 하나

# ── HAProxy ─────────────────────────────────────────
global
    log stdout format raw local0
defaults
    unique-id-format %{+X}o\ %ci:%cp_%fi:%fp_%Ts_%rt:%pid
    unique-id-header X-Request-Id
    log-format "%ci %ST %B %Tr %Tt %{+Q}r id=%ID hop=%si:%sp"
frontend fe
    http-request set-header X-Request-Id %[unique-id]

# ── Apache ──────────────────────────────────────────
LoadModule unique_id_module modules/mod_unique_id.so
RequestHeader set X-Request-Id "%{UNIQUE_ID}e"
LogFormat "... %{UNIQUE_ID}e ..." ext

# ── Caddy ───────────────────────────────────────────
reverse_proxy 10.0.1.5:8080 {
    header_up X-Request-Id {http.request.uuid}
}

# ── Tomcat (뒤에서 받을 때) ─────────────────────────
#   AccessLogValve pattern 에 %{X-Request-Id}i 를 넣습니다

# ── 클라우드 LB 가 이미 붙여 주는 것들 ──────────────
#   AWS ALB     : X-Amzn-Trace-Id      (Root=1-...)
#   CloudFront  : X-Amz-Cf-Id
#   Envoy · 서비스 메시 : x-request-id (자동 생성·전파)
#   → 이미 있으면 새로 만들지 말고 그 값을 로그 필드로 받으세요
이미 분산 추적을 쓰고 있다면 traceparent 가 정답입니다. W3C Trace Context 표준 헤더라 모든 언어의 계측 라이브러리가 자동으로 전파하고, trace_id 하나로 로그 · 추적 · 메트릭이 전부 이어집니다. X-Request-Id 는 추적을 아직 안 넣은 조직의 최소 장비라고 보면 됩니다 (자세한 건 🔭 관측 · 모니터링 탭).

모아 보기 — ID 하나로 전 구간 조회 🟡 중급

저장소별 질의

# Loki — 시간 범위를 반드시 좁히세요(라벨 밖 검색은 전수 훑기)
{env="prod"} |= "3f8a9c" | json | line_format "{{.host}} {{.uri}} {{.status}}"

# 서비스별로 몇 줄씩 나왔는지 한눈에
sum by (job) (count_over_time({env="prod"} |= "3f8a9c" [1h]))

# Elasticsearch / OpenSearch
GET logs-*/_search
{ "query": { "term": { "id.keyword": "3f8a9c..." } },
  "sort": [ { "@timestamp": "asc" } ], "size": 500 }

# ClickHouse
SELECT ts, host, service, status, rt, msg
FROM logs
WHERE req_id = '3f8a9c...' AND ts >= now() - INTERVAL 2 HOUR
ORDER BY ts;

# 원본 파일밖에 없을 때 (여러 서버를 한 번에)
pssh -h hosts.txt -i "grep -h 3f8a9c /var/log/nginx/access.json" \
  | jq -s 'sort_by(.ts)'

실무에서 진짜 효과가 큰 두 가지

① 오류 화면에 ID 를 작게 찍어 두기. 고객센터가 "화면 아래 코드를 불러 주세요" 한마디로 그 한 건의 요청 로그를 1초 만에 찾습니다. 재현도 필요 없고 시간대를 물어볼 필요도 없습니다. 50x 페이지에 <!--# echo var="request_id" --> 같은 SSI 한 줄이면 됩니다.
② 응답 헤더를 항상 내보내기(always). 프런트엔드가 API 오류를 잡을 때 응답 헤더의 ID 를 함께 리포팅하면, 브라우저에서 난 오류 하나가 서버 로그 한 줄과 정확히 짝지어집니다. add_header 는 always 를 안 붙이면 2xx·3xx 에만 붙습니다 — 정작 필요한 5xx 에 안 붙는 실수가 흔합니다.
ID 를 라벨이나 색인 필드로 만들지 마세요. 값의 가짓수가 요청 수만큼이라, Loki 라벨이나 ES 의 keyword 필드로 두면 색인이 폭발합니다. 본문 안의 값으로 두고 문자열 검색하는 것이 맞습니다 — 시간 범위만 좁히면 충분히 빠릅니다.
정리 — 가장 바깥 프록시에서 ID 를 하나 만들고, proxy_set_header 로 안쪽에 넘기고, add_header ... always 로 밖에도 돌려줍니다. 세 서버가 같은 값을 로그에 적으면 검색 한 번으로 전 구간이 모입니다. 인터넷에서 온 ID 는 믿지 말고 새로 발급하세요.
LOG 10

비용 · 샘플링 · 보존 — 안 남길 것을 정하는 일

로그 비용은 산수로 미리 알 수 있습니다. 초당 요청 수 × 한 줄 크기 × 86,400. 이 계산을 한 번만 해 보면 "일단 다 남기자"가 왜 안 되는지가 바로 보입니다.

막대 — 가장 큰 절감은 압축이고, 그다음이 안 보내는 것입니다.

내 서버는 얼마나 쌓이나 — 30초 계산

# ① 한 줄 평균 크기 재기
awk '{n++; s+=length($0)+1} END {print "줄수", n, "평균바이트", s/n}' \
  /var/log/nginx/access.json

# ② 지난 1시간에 몇 줄이 쌓였나
journalctl --since "1 hour ago" -u nginx | wc -l
ls -l --time-style=+%s /var/log/nginx/access.json      # 크기 변화로도 됩니다

# ③ 하루 · 한 달 환산
#    초당 요청 × 평균 바이트 × 86400 = 하루 바이트
#    1,000 × 500 × 86,400 = 43,200,000,000 ≈ 43 GB/일 ≈ 1.3 TB/월
#    여기에 서버 대수를 곱하면 그것이 수집기가 보낼 총량입니다

# ④ 압축비를 실제로 재기 (추정하지 말고)
head -c 200000000 /var/log/nginx/access.json > /tmp/s.json
gzip  -c /tmp/s.json | wc -c
zstd -19 -c /tmp/s.json | wc -c

# ⑤ 필드 하나가 차지하는 비중 — 뭘 뺄지 정할 때
jq -r 'to_entries[] | "\(.key)\t\(.value|tostring|length)"' \
  /var/log/nginx/access.json | awk -F'\t' \
  '{s[$1]+=$2} END {for (k in s) print s[k], k}' | sort -rn
⑤ 를 해 보면 대개 User-Agent 와 Referer 가 1·2등입니다. 둘이 한 줄의 40~60%를 차지하는 경우도 흔합니다. User-Agent 를 통째로 남기는 대신 "브라우저 계열"로 축약하거나(map 으로 분류) 봇 판정 결과만 남기면 용량이 눈에 띄게 떨어집니다.

보존 설계 — 세 구간으로 나눕니다

구간기간어디에 · 왜
뜨거움7~14일Loki·ES — 장애 대응은 거의 여기서 끝납니다
미지근30~90일강등된 등급 · 압축 · 느린 조회 허용
차가움1~3년오브젝트 스토리지 — 감사·규정·분쟁 대응
# 무엇을 어느 구간에 두나 — 결정 규칙
#  ERROR · 보안 이벤트 · 감사 로그  → 100% · 장기 보관 ★
#  4xx / 5xx 액세스 로그            → 100% · 뜨거움 + 장기
#  2xx 액세스 로그                  → 샘플링 · 뜨거움만
#  DEBUG                            → 운영에서는 아예 끔
#  헬스체크 · 정적 파일             → 아예 안 남김
#  요청/응답 본문                   → 남기지 않음 (사고 예방 + 용량)

# 줄이는 수단의 효과 (큰 것부터)
#  ① DEBUG 끄기               — 보통 절반 이상
#  ② 헬스체크·정적 제외        — 20~40%
#  ③ 2xx 샘플링(1/20)          — 큰 절감, 조사 손실 거의 없음
#  ④ 긴 필드 축약(UA·Referer)  — 20~40%
#  ⑤ 보존 30일 → 14일          — 선형으로 감소
#  ⑥ 중복 로깅 제거            — 10~20%

트레이드오프를 눈으로 보기 — 무엇을 잃고 무엇을 얻나 🔴 실무
