LOG 01

로그는 네 곳에서 나옵니다 — 전체 지도부터

"로그 좀 봐 주세요"라는 말은 서버에서 네 가지 서로 다른 것을 가리킬 수 있습니다. 앱이 뱉은 줄, 웹서버가 남긴 요청 기록, OS 데몬이 남긴 기록, 커널이 남긴 기록입니다. 어디를 열어야 하는지 아는 것이 로그 운영의 절반입니다.

로그 지도 — 네 원천을 한 줄기로 모으는 것이 로그 운영의 전부입니다.

리눅스 서버에서 실제로 열어 보는 자리

# ② 웹서버 — 요청 기록
/var/log/nginx/access.log        # 요청 한 건에 한 줄
/var/log/nginx/error.log         # 업스트림 끊김 · 설정 오류 · 권한 문제
/var/log/apache2/{access,error}.log
$CATALINA_BASE/logs/localhost_access_log.YYYY-MM-DD.txt
$CATALINA_BASE/logs/catalina.out          # Tomcat 은 stdout 이 여기로 갑니다

# ③ OS 데몬 — 배포판마다 이름이 다릅니다
journalctl -u nginx              # systemd 계열(요즘은 여기부터)
/var/log/syslog                  # 데비안 · 우분투
/var/log/messages                # RHEL · 로키 · 아마존리눅스
/var/log/auth.log                # 로그인 · sudo (RHEL 은 secure)

# ④ 커널 — 재부팅하면 사라집니다(영구화는 journald 몫)
dmesg -T --level=err,warn
journalctl -k -b -1              # 직전 부팅의 커널 로그 ★ OOM 추적의 시작

# 지금 이 서버에서 로그가 얼마나 쌓이고 있나
du -sh /var/log/* | sort -h | tail
journalctl --disk-usage
장애 때 여는 순서 — ② 웹서버 error_log → ① 앱 로그 → ③ OS → ④ 커널. 웹서버 error_log 한 줄이 "앱이 죽었다"인지 "앱이 느리다"인지 "설정이 틀렸다"인지를 대부분 바로 알려 줍니다. 커널까지 내려가야 하는 경우는 OOM Killer · 디스크 가득 · NIC 문제 셋 정도입니다.

네 원천의 성격이 완전히 다릅니다

원천양버리면어디로 나가나
앱중~많음사업 사고stdout(권장)
access가장 많음조사 불가파일 · syslog
error적음치명적파일 · stderr
OS 데몬적음보안 사고journald
커널아주 적음원인 미상ring buffer
양의 90%는 access 로그입니다. 그래서 비용 이야기도, 샘플링 이야기도 거의 전부 access 로그 이야기입니다(lg10). 반대로 error_log · 커널 로그는 전부 남겨도 용량이 안 됩니다 — 여기서 아끼면 손해만 봅니다.
이 탭에서 다루지 않는 것 — 메트릭(Prometheus) · 분산 추적(OpenTelemetry) · 알림 · SLO 는 🔭 관측 · 모니터링 탭에 있습니다. 앱 코드에서 구조화 로그를 찍는 법(structlog · pino · logback)도 그쪽입니다. 여기서는 이미 나온 로그를 서버가 어떻게 다루는가만 봅니다.

가장 먼저 할 일 — 디스크가 차서 서버가 멈추는 것을 막기 🟢 기초

실제로 가장 흔한 로그 장애

# 증상: 갑자기 500 이 쏟아지고, 앱은 살아 있는데 아무것도 안 됨
df -h /var                      # Use% 100% ★ 십중팔구 이것입니다
df -i /var                      # inode 가 먼저 차는 경우도 있습니다

# 누가 먹었나 — 큰 것부터
du -xh /var/log --max-depth=2 | sort -h | tail -20

# ★ 지운 파일인데 용량이 안 돌아온다면: 프로세스가 아직 붙잡고 있습니다
lsof +L1 | grep -i deleted      # (deleted) 인데 크기가 GB 인 것
#   → 그 프로세스에 로그 재오픈 신호를 주거나 재시작해야 회수됩니다

# 급할 때(주의: 이력이 사라집니다)
truncate -s 0 /var/log/nginx/access.log     # rm 말고 truncate ★
journalctl --vacuum-size=500M
rm access.log 는 용량을 되돌려 주지 않습니다. Nginx 가 그 파일의 파일 디스크립터를 붙잡고 있어서, 디렉터리에서만 사라지고 디스크는 그대로입니다. 급할 땐 truncate -s 0, 정석은 logrotate + 재오픈 신호(lg06)입니다.

새 서버를 받으면 30분 안에 해 두는 것

# ① /var/log 를 별도 파티션·볼륨으로 (루트가 차면 OS 가 멈춥니다)
lsblk; findmnt /var/log

# ② journald 상한 — 안 걸어 두면 파일시스템의 10%까지 먹습니다
sudo tee /etc/systemd/journald.conf.d/limit.conf <<'EOF'
[Journal]
Storage=persistent
SystemMaxUse=1G
SystemMaxFileSize=128M
MaxRetentionSec=14day
EOF
sudo systemctl restart systemd-journald

# ③ logrotate 가 실제로 도는지 확인 (배포판마다 cron 또는 timer)
systemctl list-timers logrotate.timer
sudo logrotate -d /etc/logrotate.conf | tail -40    # -d = 예행연습

# ④ 디스크 사용률 알림을 먼저 겁니다 (85% 에서)
#    로그 알림보다 이 알림이 먼저 필요합니다
순서가 중요합니다 — 수집기를 깔기 전에 상한부터 겁니다. 수집기를 먼저 깔면 "로그를 다 보내니 안심"하다가 전송이 막힌 날 디스크가 터집니다. 버퍼도 결국 디스크입니다.
정리 — 로그는 앱 · 웹서버 · OS · 커널 네 곳에서 나옵니다. 장애 때는 웹서버 error_log 부터 열고, 양의 90%는 access 로그라는 것을 기억하세요. 그리고 무엇보다 상한(journald SystemMaxUse · logrotate)을 먼저 걸어 둡니다 — 로그 때문에 나는 장애의 대부분은 내용이 아니라 용량입니다.
LOG 02

Nginx log_format — 기본값은 반드시 바꿔야 합니다

Nginx 가 기본으로 쓰는 combined 포맷에는 이 요청이 몇 초 걸렸는지가 없습니다. 어느 백엔드가 처리했는지도 없습니다. 장애 조사에서 막히는 이유의 절반이 여기서 옵니다 — 먼저 이 한 줄을 고칩니다.

해부도 — combined 에는 시간과 업스트림이 통째로 빠져 있습니다.

문법 — log_format 과 access_log

# log_format 이름 [escape=default|json|none] '문자열' ['이어지는 문자열'];
#   · http 블록에만 쓸 수 있습니다 (server · location 안에서는 정의 불가)
#   · 작은따옴표 문자열을 여러 줄로 이어 쓰면 그대로 붙습니다
#   · escape=json 은 값 안의 " \ 제어문자를 JSON 규칙으로 이스케이프 (1.11.8+)

log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                '"$http_referer" "$http_user_agent" '
                'rt=$request_time urt=$upstream_response_time '
                'up=$upstream_addr id=$request_id';

# access_log 경로 [포맷 [buffer=크기] [gzip[=1~9]] [flush=시간] [if=조건]];
#   · http · server · location · if · limit_except 안에서 쓸 수 있습니다
#   · 안쪽에 하나라도 쓰면 바깥 설정을 "덮어씁니다"(상속이 아니라 대체) ★
access_log /var/log/nginx/access.log main buffer=64k flush=5s;

# 여러 곳에 동시에 쓸 수도 있습니다 (파일 + 원격 syslog)
access_log /var/log/nginx/access.log main;
access_log syslog:server=10.0.0.9:514,facility=local7,tag=nginx,severity=info main;

access_log off;                       # 이 location 만 끄기
buffer= 와 flush= 를 함께 쓰세요. buffer 만 주면 버퍼가 찰 때까지 디스크에 안 내려갑니다 — 트래픽이 적은 새벽에 장애가 나면 마지막 몇 분이 안 보입니다. flush=5s 를 붙이면 5초마다 강제로 내려갑니다. 초당 수천 요청이면 버퍼링만으로 디스크 I/O 가 눈에 띄게 줄어듭니다.

시간 변수 네 개 — 차이를 보면 원인이 갈립니다 🟡 중급

워터폴 — 세 변수의 뺄셈만으로 "앱이 느린지 회선이 느린지"가 갈립니다.

주의할 함정 세 가지

# ① upstream_* 는 "요청 시작"이 아니라 "업스트림에 붙은 시점"부터 잽니다.
#    셋은 누적값이고, 재시도가 있으면 쉼표로 여러 개가 찍힙니다.
#    upstream_response_time: 0.012, 1.402   ← 첫 백엔드 실패 후 재시도
#    upstream_addr:          10.0.1.5:8080, 10.0.1.6:8080

# ② request_time 은 "클라이언트가 본문을 다 보낼 때까지"도 포함합니다.
#    느린 모바일 업로드 하나가 request_time 30초로 찍힙니다 — 앱 잘못이 아닙니다.
#    → 알림은 upstream_header_time 으로 걸고, request_time 은 참고로 봅니다.

# ③ 액세스 로그는 "응답이 끝난 뒤"에 기록됩니다.
#    앱이 응답을 못 주고 매달려 있으면 access.log 에는 아무것도 없습니다.
#    → 그 순간을 보려면 error_log 와 커넥션 상태(stub_status)를 봐야 합니다.

# 검증: 오래 걸린 요청만 뽑아 두 값을 비교
awk '$0 ~ /rt=/ {for(i=1;i<=NF;i++){if($i~/^rt=/)r=substr($i,4);
     if($i~/^urt=/)u=substr($i,5)}; if(r+0>1) print r, u, $7}' access.log \
  | sort -rn | head -20

지금 바로 복붙할 수 있는 설정

# /etc/nginx/conf.d/log.conf  — http 블록에서 include
log_format main escape=default
  '$remote_addr $http_x_forwarded_for - $remote_user [$time_iso8601] '
  '"$request" $status $body_bytes_sent $request_length '
  '"$http_referer" "$http_user_agent" '
  'host=$host rt=$request_time uct=$upstream_connect_time '
  'uht=$upstream_header_time urt=$upstream_response_time '
  'ua=$upstream_addr us=$upstream_status cs=$upstream_cache_status '
  'id=$request_id conn=$connection:$connection_requests '
  'tls=$ssl_protocol';

access_log /var/log/nginx/access.log main buffer=64k flush=5s;
error_log  /var/log/nginx/error.log warn;

# 파일 핸들 캐시 — 가상호스트가 많고 로그 파일이 수십 개일 때만 의미 있습니다
open_log_file_cache max=1000 inactive=20s valid=1m min_uses=2;

# 적용 전에 반드시 문법 검사 → 무중단 재적용
nginx -t && nginx -s reload
왜 escape=default 인가 — 사람이 읽는 텍스트 포맷에서는 기본 이스케이프가 제어문자를 \x22 형태로 바꿔 줍니다. JSON 으로 갈 거면 반드시 escape=json(다음 섹션) — 안 그러면 User-Agent 안의 따옴표 하나가 그 줄 전체를 깨뜨립니다.
access_log 는 상속이 아니라 "가장 안쪽 하나만" 적용됩니다. server 블록에 하나, location /api 에 하나를 두면 /api 요청은 server 쪽 로그에 안 남습니다. 두 곳 다 남기려면 안쪽에 두 줄을 모두 적어야 합니다.
정리 — combined 는 시간과 업스트림이 빠진 반쪽입니다. $request_time · $upstream_*_time · $upstream_addr · $request_id 네 가지를 넣는 순간 "느리다"는 신고에 앱인지 회선인지 특정 서버인지를 로그만으로 답할 수 있게 됩니다. 그리고 buffer=64k flush=5s 로 디스크 I/O 를 줄이되 마지막 몇 분을 잃지 않게 합니다.
LOG 03

JSON 로그 · error_log · 그리고 소음 지우기

로그를 기계가 읽게 만들려면 JSON 한 줄이 정답이고, 비용을 줄이려면 헬스체크와 정적 파일을 아예 안 남기는 것이 첫 수입니다. Nginx 는 두 가지를 escape=json 과 map + if= 로 해결합니다.

산키 — 밴드 두께가 곧 요금입니다. 굵은 두 갈래는 조사에 쓰이지 않습니다.

JSON 액세스 로그 — 실전 그대로

# http 블록. escape=json 이 핵심입니다 (1.11.8+)
log_format json escape=json
'{'
  '"ts":"$time_iso8601",'
  '"host":"$host",'
  '"method":"$request_method",'
  '"uri":"$uri",'
  '"args":"$args",'
  '"status":$status,'
  '"len":$body_bytes_sent,'
  '"reqlen":$request_length,'
  '"rt":$request_time,'
  '"uct":"$upstream_connect_time",'
  '"uht":"$upstream_header_time",'
  '"urt":"$upstream_response_time",'
  '"ua":"$upstream_addr",'
  '"us":"$upstream_status",'
  '"cache":"$upstream_cache_status",'
  '"cip":"$remote_addr",'
  '"xff":"$http_x_forwarded_for",'
  '"ref":"$http_referer",'
  '"agent":"$http_user_agent",'
  '"id":"$request_id",'
  '"tls":"$ssl_protocol"'
'}';

access_log /var/log/nginx/access.json json buffer=64k flush=5s;
따옴표를 붙일 자리와 안 붙일 자리가 갈립니다. $status·$body_bytes_sent·$request_time 는 항상 숫자라 따옴표 없이 두어야 저장소에서 rt > 1 같은 비교가 됩니다. 반대로 $upstream_response_time 계열은 값이 없으면 -, 재시도하면 "0.01, 1.40" 이라 반드시 문자열로 두어야 JSON 이 안 깨집니다. 이 구분을 틀리면 수집기가 하루치를 통째로 파싱 실패로 버립니다.

error_log — 레벨과 실제로 보게 될 문구

# error_log 경로 [레벨];
#   debug < info < notice < warn < error < crit < alert < emerg
#   "그 레벨 이상"이 기록됩니다. 기본은 error(빌드에 따라 warn).
error_log /var/log/nginx/error.log warn;

# 특정 서버 블록만 자세히 보고 싶을 때 (server · location 에도 쓸 수 있습니다)
server { error_log /var/log/nginx/api_debug.log info; }

# debug 는 --with-debug 로 빌드된 nginx 에서만 동작합니다

조건부 로깅 — map + if= 로 소음 지우기 🟡 중급

헬스체크·정적 파일·성공 요청 걷어 내기

# http 블록 — map 은 "변수를 만드는 표"입니다. 실행 시점에 계산됩니다.
# ① 헬스체크·메트릭 제외 (첫 매치가 이깁니다)
map $request_uri $not_probe {
    ~^/healthz    0;
    ~^/readyz     0;
    ~^/metrics    0;
    default       1;
}

# ② 성공 응답만 1/20 샘플링 — split_clients 가 해시로 균등하게 나눕니다
split_clients "$request_id" $sample_ok {
    5%      1;      # 5% = 20건 중 1건
    *       0;
}

# ③ 두 개를 합쳐 최종 판단 변수를 만듭니다
map $status $keep_by_status {
    ~^[45]  1;      # 4xx · 5xx 는 무조건 남김
    default $sample_ok;
}
map $not_probe$keep_by_status $loggable {
    "11"    1;      # 프로브가 아니고 + 남길 대상일 때만
    default 0;      # ★ if= 는 값이 0 이거나 빈 문자열이면 기록하지 않습니다
}

# server 블록
access_log /var/log/nginx/access.json json buffer=64k flush=5s if=$loggable;

location ~* \.(js|css|png|jpg|svg|woff2?)$ {
    access_log off;                 # 정적 파일은 CDN·웹서버 지표로 충분합니다
    expires 30d;
}
split_clients 의 기준 변수를 잘 고르세요. $request_id 를 쓰면 요청마다 무작위로 뽑히고, $remote_addr 를 쓰면 같은 IP 는 항상 뽑히거나 항상 안 뽑힙니다. "특정 사용자의 흐름을 통째로 보고 싶다"면 후자가, "전체 분포를 대표하게 뽑고 싶다"면 전자가 맞습니다.

더 쓸 만한 조건들

# ① 느린 요청만 따로 파일로 — 사후 분석이 훨씬 편해집니다
map $request_time $slow {
    default   0;
    ~^[1-9]   1;        # 1초 이상 (문자열 비교라 이 트릭을 씁니다)
}
access_log /var/log/nginx/slow.json json if=$slow;

# ② 사내 IP 나 모니터링 봇 제외
geo $is_internal { default 0; 10.0.0.0/8 1; 172.16.0.0/12 1; }
map $is_internal $ext_only { 1 0; default 1; }

# ③ 봇 트래픽 분리 (합치면 통계가 망가집니다)
map $http_user_agent $is_bot {
    default                       0;
    ~*(bot|crawler|spider|curl)   1;
}

# ④ 로그에 사업 구분을 직접 붙이기 — 나중에 비용 배분에 씁니다
map $host $tenant {
    hostnames;
    shop.example.com   shop;
    admin.example.com  admin;
    default            etc;
}
#   log_format 에 '"tenant":"$tenant",' 를 넣으면 그대로 필드가 됩니다

# 적용
nginx -t && systemctl reload nginx
map 은 공짜가 아닙니다 — 하지만 거의 공짜입니다. 정확 일치는 해시 조회라 사실상 비용이 없고, ~ 정규식은 요청마다 실행됩니다. 정규식 map 을 열 개씩 쌓으면 초당 수만 요청에서 체감됩니다. 정확 일치와 hostnames 를 먼저 쓰고, 정규식은 꼭 필요한 곳만 남기세요.

액세스 로그를 끄기 전에 — 잃는 것을 알고 끄기 🔴 실무

이렇게 끄면 나중에 후회합니다
server {
    access_log off;          # "용량이 커서" 통째로 끔
    ...
}
· 5xx 가 언제 시작됐는지 영영 모릅니다
· 공격 흔적(스캔·크리덴셜 스터핑)이 남지 않습니다
· 국내 개인정보 규정의 접속기록 보관 의무를 못 지킵니다
· 용량 문제는 보존 기간으로 풀 문제였습니다
이렇게 줄입니다
access_log /var/log/nginx/access.json json
           buffer=64k flush=5s if=$loggable;
# + 정적 파일 location 만 off
# + 4xx/5xx 는 100% · 2xx 는 1/20
# + 보존 14일(뜨거움) + 1년(감사용 원본)
· 조사에 필요한 줄은 전부 남습니다
· 용량은 10분의 1 이하로 떨어집니다
· 규정 대응용 원본은 따로 압축 보관합니다
샘플링한 로그로 "비율"을 계산할 때는 반드시 가중치를 되돌리세요. 2xx 를 1/20 로 남겼는데 그대로 세면 에러율이 20배로 부풀어 보입니다. 로그에 "sample_rate":20 같은 필드를 함께 넣어 두고 집계할 때 곱해 주는 것이 정석입니다. 애초에 에러율 같은 비율은 메트릭(Prometheus)으로 재는 것이 맞습니다 — 로그는 "그 한 건"을 찾는 도구입니다(🔭 관측 탭).
정리 — 액세스 로그는 escape=json 으로 JSON 한 줄, 숫자 필드에는 따옴표를 빼고 upstream_* 는 반드시 문자열로 둡니다. 소음은 map + if= 로 지우고, 성공 요청은 split_clients 로 샘플링합니다. 절대 통째로 끄지는 마세요 — 끄는 대신 줄이는 수단이 이렇게 많습니다.
LOG 04

Apache · Tomcat · Caddy — 같은 일을 다른 문법으로

네 서버가 하는 일은 같습니다 — "요청 한 건에 한 줄". 그런데 Caddy 는 처음부터 JSON이고, Tomcat 은 자기가 로그를 회전시키고, Apache 는 파이프로 외부 프로그램에 넘깁니다. 이 차이가 운영 방식을 바꿉니다.

매트릭스 — Caddy 는 기본이 JSON, Nginx 는 기본이 최소. 손댈 곳이 정반대입니다.

Apache 2.4 — LogFormat 과 ErrorLogFormat

# 액세스 로그 — %기호가 Nginx 의 $변수 자리입니다
LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\"" combined
CustomLog ${APACHE_LOG_DIR}/access.log combined

# 실무용 — 시간·업스트림·요청 ID 를 더한 버전
LogFormat "%{%Y-%m-%dT%H:%M:%S%z}t %a %{X-Forwarded-For}i %v %m %U%q \
%>s %O %I %{ms}T %{UNIQUE_ID}e \"%{User-Agent}i\"" ext
CustomLog ${APACHE_LOG_DIR}/access.log ext

#  %h 원격 호스트   %a 클라이언트 IP     %A 서버 IP
#  %t 시각          %{포맷}t strftime 지정
#  %r 요청 줄 전체  %m 메서드  %U 경로  %q 쿼리스트링  %H 프로토콜
#  %>s 최종 상태코드 (%s 는 리다이렉트 전 최초 상태) ★ 거의 항상 %>s
#  %b 본문 바이트(0이면 -)   %B 본문 바이트(0이면 0)
#  %O 보낸 총 바이트  %I 받은 총 바이트   (mod_logio 필요)
#  %D 소요 마이크로초  %T 초  %{ms}T 밀리초  %{us}T 마이크로초
#  %L 로그 ID ★ error_log 의 같은 ID 와 짝지어집니다
#  %{UNIQUE_ID}e 요청 고유 ID (mod_unique_id)
#  %v 정규 서버명   %p 포트   %X 연결 종료 상태(X=중단, +=유지, -=닫힘)
#  %{Foo}i 요청 헤더  %{Foo}o 응답 헤더  %{Foo}e 환경변수  %{Foo}C 쿠키

# 에러 로그 — 포맷도 바꿀 수 있습니다(2.4부터)
ErrorLogFormat "[%{u}t] [%-m:%l] [pid %P:tid %T] %7F: %E: [client %a] %M, referer %{Referer}i"
LogLevel warn
LogLevel info ssl:warn rewrite:trace3     # ★ 모듈별로 따로 줄 수 있습니다
%L 하나가 Apache 의 숨은 무기입니다. 액세스 로그와 에러 로그에 같은 로그 ID가 찍혀서, "이 500 응답이 남긴 에러 줄"을 정확히 짝지을 수 있습니다. Nginx 에는 이에 해당하는 기능이 없어 $request_id 를 직접 넣어야 합니다.

Apache — 조건부 로깅과 파이프 로그

# ① 조건부 — 환경변수를 세우고 env= 로 거릅니다
SetEnvIf Request_URI "^/(healthz|metrics)$"     dontlog
SetEnvIf Request_URI "\.(gif|jpg|png|css|js)$"  dontlog
SetEnvIf Remote_Addr "^10\."                    dontlog
CustomLog ${APACHE_LOG_DIR}/access.log ext env=!dontlog

# 2.4.19+ 는 표현식도 됩니다 — 훨씬 읽기 좋습니다
CustomLog ${APACHE_LOG_DIR}/slow.log ext "expr=%{TIME_MS} > 1000"

# ② 파이프 로그 — 로그를 파일이 아니라 프로그램의 stdin 으로 넘깁니다
#    Apache 가 그 프로그램을 자식으로 띄우고 죽으면 다시 띄웁니다
CustomLog "|/usr/bin/rotatelogs -l ${APACHE_LOG_DIR}/access.%Y%m%d.log 86400" ext
#    -l = 로컬시간 기준  ·  86400 = 하루마다  ·  100M 처럼 크기로도 가능
#    → logrotate 없이 회전이 끝납니다. 대신 오래된 파일 삭제는 따로 해야 합니다

# ③ syslog 로 바로 (에러 로그)
ErrorLog "syslog:local7"

# ④ 문법 검사 → 무중단 재적용 (USR1 = graceful)
apachectl configtest && apachectl graceful
파이프 로그의 대가 — 그 프로그램이 느리거나 멈추면 Apache 가 같이 멈춥니다. 파이프는 버퍼가 가득 차면 쓰기가 블록되기 때문입니다. rotatelogs 처럼 단순하고 검증된 프로그램만 물리세요. 수집기로 보내고 싶다면 파이프 대신 파일로 쓰고 수집기가 tail 하게 하는 것이 안전합니다.

Tomcat — 액세스 로그는 Valve, 앱 로그는 catalina.out 🟡 중급

AccessLogValve — server.xml

<!-- conf/server.xml 의 <Host> 안 -->
<Valve className="org.apache.catalina.valves.AccessLogValve"
       directory="logs"
       prefix="access" suffix=".log"
       fileDateFormat=".yyyy-MM-dd"
       rotatable="true"
       renameOnRotate="false"
       buffered="true"
       maxDays="14"
       requestAttributesEnabled="true"
       condition="dontlog"
       pattern="%{yyyy-MM-dd'T'HH:mm:ss.SSSXXX}t %a %{X-Forwarded-For}i %m %U%q %s %b %D %S %{X-Request-Id}i" />

<!-- Tomcat 10.1+ · 9.0.x 후반 — JSON 으로 바로 뱉는 Valve -->
<Valve className="org.apache.catalina.valves.JsonAccessLogValve"
       directory="logs" prefix="access" suffix=".json"
       maxDays="14"
       pattern="%h %l %u %t %r %s %b %D %{X-Request-Id}i" />
# 패턴 기호 (Apache 와 비슷하지만 다른 것들이 있습니다)
#  %a 클라이언트 IP   %h 호스트   %l 항상 -   %u 인증 사용자
#  %t 시각  %{포맷}t  ·  %r 요청 줄  %s 상태코드  %b 본문 바이트
#  %D 처리 시간(밀리초) ★  %T 초  %F 첫 바이트까지의 시간
#  %S 세션 ID   %I 스레드 이름 ★ 스레드 고갈 추적에 유용
#  %{헤더}i 요청 헤더  %{헤더}o 응답 헤더  %{속성}r 요청 속성
#  common · combined 는 미리 정의된 이름입니다

# requestAttributesEnabled="true" 를 켜면
#   RemoteIpValve 가 복원한 진짜 클라이언트 IP 를 %a 가 씁니다
#   (프록시 뒤에 있는 Tomcat 이라면 사실상 필수)

catalina.out 이 계속 커지는 문제

# catalina.out 은 "로그 파일"이 아니라 그냥 stdout 리다이렉트입니다.
#   bin/catalina.sh:  ... >> "$CATALINA_OUT" 2>&1 &
# 그래서 ① 회전이 없고 ② 이름을 바꿔도 Tomcat 은 옛 파일에 계속 씁니다.

# 해법 A — 애초에 안 만들기 (systemd 로 띄우고 journald 에 맡기기) ★ 권장
#   /etc/systemd/system/tomcat.service
[Service]
Environment=CATALINA_OUT=/dev/null
StandardOutput=journal
StandardError=journal
SyslogIdentifier=tomcat

# 해법 B — logrotate 에 copytruncate 를 씁니다(다음 섹션에서 왜 위험한지 설명)
/opt/tomcat/logs/catalina.out {
    daily rotate 7 compress missingok notifempty copytruncate
}

# 해법 C — conf/logging.properties 로 java.util.logging 을 파일로 분리
handlers = 1catalina.org.apache.juli.AsyncFileHandler, java.util.logging.ConsoleHandler
1catalina.org.apache.juli.AsyncFileHandler.maxDays = 14
1catalina.org.apache.juli.AsyncFileHandler.level = FINE
# Spring Boot 내장 Tomcat 이면 이 파일 자체가 없습니다 — 앱 로거(logback)가 담당
Tomcat 로그가 세 군데로 흩어지는 것이 진짜 문제입니다 — access.log(Valve) · catalina.out(stdout) · catalina.YYYY-MM-DD.log(JULI). 여기에 앱의 logback 까지 더하면 넷입니다. 전부 stdout 한 곳으로 모으고 나머지를 끄는 것이 컨테이너 시대의 정답이고, VM 이라면 최소한 수집기가 네 경로를 모두 읽게 설정해 두세요.

Caddy — 아무것도 안 해도 JSON 입니다 🟡 중급

Caddyfile — 로그 블록 전부

shop.example.com {
    reverse_proxy 10.0.1.5:8080

    log {
        output file /var/log/caddy/access.log {
            roll_size     100MiB      # 이 크기가 되면 회전 (기본 100MiB)
            roll_keep     10          # 보관 개수 (기본 10)
            roll_keep_for 720h        # 보관 기간 (기본 90일)
            roll_uncompressed         # 붙이면 gzip 안 함 (기본은 압축)
        }
        format json                   # 기본값 — 안 써도 JSON 입니다
        level  INFO
    }
}

# 사람이 볼 때만 한시적으로
log { format console }

# 전역(런타임) 로그는 따로입니다 — 액세스 로그가 아닙니다
{
    log {
        output file /var/log/caddy/caddy.log
        level ERROR
    }
}
Caddy 는 logrotate 가 필요 없습니다. 회전이 프로세스 안에 들어 있어서 파일 핸들 문제도, USR1 신호도 없습니다(lg06 의 고민이 통째로 사라집니다). 대신 회전 정책이 Caddyfile 안에 있으니 서버마다 흩어지지 않게 공통 스니펫으로 관리하세요.

Caddy 의 filter — 로그에서 값 가리기

log {
    output file /var/log/caddy/access.log
    format filter {
        wrap json
        fields {
            request>headers>Authorization delete
            request>headers>Cookie       delete
            request>remote_ip            ip_mask 16 32
            request>uri                  query {
                replace token REDACTED
                delete  sid
            }
            request>headers>User-Agent   hash
        }
    }
}
#  delete   — 필드를 통째로 제거
#  replace  — 값을 고정 문자열로 치환
#  ip_mask  — IPv4 상위 16비트만 남김 / IPv6 상위 32비트
#  hash     — 값 대신 해시(같은 값인지 비교는 되고 원본은 모름) ★
#  query / cookie — 쿼리스트링·쿼키 안의 특정 키만 골라 처리
#  regexp   — 정규식으로 부분 치환
이 filter 가 다른 서버에는 없습니다. Nginx·Apache 에서 같은 일을 하려면 수집기 단계에서 지워야 하고, 그 사이에 디스크에는 원본이 이미 적힌 상태가 됩니다. 개인정보 관점에서는 웹서버가 애초에 안 적는 것이 한 단계 앞선 방어입니다(lg11).
정리 — Apache 는 % 기호와 env=, Tomcat 은 AccessLogValve 와 흩어진 네 개의 로그 파일, Caddy 는 손대지 않아도 JSON + 자체 회전입니다. Nginx 만 회전 기능이 없어서 다음 두 섹션(syslog · logrotate)이 특히 중요해집니다.
LOG 05

syslog · journald — OS 가 관리하는 로그

웹서버 로그는 우리가 만든 것이지만, sshd · cron · sudo · systemd · 커널이 남기는 로그는 OS 가 관리합니다. 여기에는 40년 된 규칙(시설 · 심각도)과 요즘 리눅스의 journald가 겹쳐 있습니다. 둘 다 알아야 합니다.

journald 는 필드가 붙은 데이터베이스에 가깝습니다 — 그래서 조회가 쿼리처럼 됩니다.

journalctl — 실제로 치는 명령들

# ① 유닛 하나 따라가기 (가장 많이 씁니다)
journalctl -u nginx -f                    # tail -f
journalctl -u nginx -n 200 --no-pager

# ② 시간으로 좁히기 ★ 장애 조사의 시작
journalctl -u nginx --since "2026-08-31 15:00" --until "2026-08-31 15:30"
journalctl --since "1 hour ago"
journalctl --since yesterday --until today

# ③ 심각도로 좁히기 (숫자 또는 이름)
journalctl -p err -b                      # 이번 부팅에서 err 이상
journalctl -p warning..err                # 범위도 됩니다

# ④ 부팅 단위로 — 재부팅 원인을 찾을 때
journalctl --list-boots
journalctl -b -1 -p err                   # 직전 부팅의 오류만 ★
journalctl -k -b -1 | grep -i "out of memory"   # OOM Killer 추적

# ⑤ 필드로 질의 — journald 의 진짜 힘입니다
journalctl _SYSTEMD_UNIT=nginx.service _PID=1234
journalctl _COMM=sshd _UID=0
journalctl -u nginx -o json-pretty | head -40    # 붙어 있는 필드 전부 보기
journalctl -F _SYSTEMD_UNIT               # 이 서버에 있는 유닛 목록

# ⑥ 출력 형식 — 수집기에 넘길 때는 json
journalctl -u nginx -o cat                # 메시지 본문만
journalctl -u nginx -o short-iso          # 시각을 ISO8601 로
journalctl -f -o json                     # 스트리밍 JSON

# ⑦ 용량 — 이것부터 확인하세요
journalctl --disk-usage
sudo journalctl --vacuum-size=500M
sudo journalctl --vacuum-time=7d
sudo journalctl --verify                  # 손상 검사

journald 가 디스크를 먹는 문제 — 기본값이 관대합니다 🟡 중급

journald.conf — 실제로 손대는 항목

# /etc/systemd/journald.conf.d/00-limits.conf  (원본을 고치지 말고 드롭인으로)
[Journal]
Storage=persistent          # auto=디렉터리가 있을 때만 영구. persistent 로 못 박습니다
Compress=yes
SystemMaxUse=1G             # ★ 기본은 "파일시스템의 10%, 최대 4G" — 관대합니다
SystemKeepFree=2G           # 이만큼은 항상 비워 둡니다
SystemMaxFileSize=128M      # 한 조각 파일의 크기
SystemMaxFiles=100
MaxRetentionSec=14day       # 기간 상한 (용량 상한과 함께 걸립니다)
MaxFileSec=1day             # 하루마다 새 조각 파일

# 폭주 방지 — 이걸 모르면 "로그가 없어졌다"고 착각합니다 ★
RateLimitIntervalSec=30s
RateLimitBurst=10000        # 30초에 10,000줄 넘으면 그 뒤는 버립니다

ForwardToSyslog=no          # rsyslog 를 안 쓰면 꺼서 중복 저장을 막습니다
ForwardToWall=no
sudo systemctl restart systemd-journald
journalctl --disk-usage

# 폭주로 버려진 줄이 있었는지 확인 ★ 이 문구를 꼭 기억하세요
journalctl | grep -i "Suppressed .* messages"
"로그가 중간에 비었다"의 범인이 대개 RateLimitBurst 입니다. 장애 순간에는 로그가 폭발하는데, 바로 그때 journald 가 초과분을 조용히 버립니다. 유닛별로 풀 수도 있습니다 — 서비스 유닛에 LogRateLimitIntervalSec=0 을 주면 그 유닛만 제한이 풀립니다. 가장 중요한 서비스에만 예외를 주세요.

rsyslog — 원격 전송과 파일 만들기

# /etc/rsyslog.d/10-remote.conf  (RainerScript · rsyslog 8.x)

# ① 원격으로 보내기 — 디스크 큐를 반드시 함께 씁니다 ★
*.* action(type="omfwd"
           target="10.0.0.9" port="514" protocol="tcp"
           queue.type="LinkedList"
           queue.filename="fwd_q"          # 디스크로 넘칠 때 쓸 파일
           queue.maxdiskspace="1g"
           queue.saveonshutdown="on"       # 재시작해도 안 잃습니다
           action.resumeRetryCount="-1")   # 무한 재시도

# ② 시설별로 파일 나누기 (Nginx 를 local7 로 보냈다면)
local7.*   /var/log/nginx-remote.log
authpriv.* /var/log/secure

# ③ 파일을 읽어서 보내기 — 웹서버 로그를 rsyslog 로 실어 나를 때
module(load="imfile")
input(type="imfile"
      File="/var/log/nginx/access.json"
      Tag="nginx-access"
      Severity="info" Facility="local7"
      PersistStateInterval="100")         # 어디까지 읽었는지 저장

# ④ 더 확실하게 — RELP 는 응답을 받고서야 지웁니다(TCP 만으로는 유실 가능)
module(load="omrelp")
action(type="omrelp" target="10.0.0.9" port="20514")
2026년에 새로 만드는 시스템이라면 rsyslog 로 파일을 실어 나르지 않습니다. 그 일은 Fluent Bit·Vector 같은 수집기가 더 잘합니다(lg07). rsyslog 가 여전히 필요한 자리는 ① 네트워크 장비·어플라이언스가 syslog 로만 보내는 경우, ② 규정상 syslog 서버로 즉시 전송해야 하는 감사 로그(lg11), ③ 텍스트 /var/log/*.log 를 꼭 유지해야 하는 오래된 운영 절차 셋입니다.
systemd 유닛에서 로그를 어디로 보낼지 정하는 것도 설정입니다. StandardOutput=journal(기본) · append:/var/log/app.log · null 중에서 고를 수 있고, SyslogIdentifier= 로 이름을 붙이면 journalctl -t 이름 으로 바로 뽑힙니다. StandardOutput=append: 를 쓰면 systemd 가 파일을 열어 주므로 앱이 파일 경로를 몰라도 되고, logrotate 후 재오픈은 systemctl restart 또는 copytruncate 가 필요해집니다(다음 섹션).
정리 — syslog 의 시설 24칸 · 심각도 8단계는 지금도 프로토콜의 뼈대입니다. 요즘 리눅스에서는 journald 가 먼저 받고, 필요하면 rsyslog 로 넘깁니다. journalctl -u ... --since ... -p err 세 옵션이면 조사의 90%가 되고, SystemMaxUse 와 RateLimitBurst 두 개는 반드시 손대야 하는 기본값입니다.
LOG 06

logrotate — 로그를 잃는 가장 흔한 경로

로그 파일은 이름을 바꿔도 프로세스는 옛 파일에 계속 씁니다. 유닉스에서 파일의 정체는 이름이 아니라 inode 이기 때문입니다. 이 한 가지를 모르면 회전할 때마다 로그가 조용히 사라집니다.

시퀀스 — 이름과 inode 가 다른 것이 로그 회전 사고의 뿌리입니다.

설정 문법 — 실제로 쓰는 지시어 전부

# /etc/logrotate.d/nginx
/var/log/nginx/*.log /var/log/nginx/*.json {
    daily                 # hourly · daily · weekly · monthly · yearly
    rotate 14             # 몇 개를 보관할지 (14일치)
    size 100M             # 이 크기 넘으면 주기와 무관하게 회전
    maxsize 500M          # 주기 전이라도 이 크기면 회전 (size 와 조합)
    minsize 1M            # 이보다 작으면 주기가 와도 회전 안 함

    missingok             # 파일이 없어도 오류 내지 않음
    notifempty            # 비어 있으면 회전 안 함
    compress              # gzip (기본 gzip, compresscmd 로 변경 가능)
    delaycompress         # ★ 한 세대 미루고 압축 — 재오픈 전에 압축하는 사고 방지
    compresscmd /usr/bin/zstd
    compressoptions -19 --rm
    compressext .zst

    dateext               # access.log-20260831 형태로 (숫자 대신 날짜)
    dateformat -%Y%m%d
    dateyesterday         # 새벽에 도니 "어제 날짜"로 붙이는 게 자연스럽습니다

    create 0640 www-data adm      # 새 파일을 이 권한·소유자로 미리 만듦
    su root adm                   # 디렉터리 소유자가 root 가 아닐 때 필요
    olddir /var/log/nginx/old     # 회전본을 다른 디렉터리로
    sharedscripts                 # ★ 여러 파일이어도 스크립트는 한 번만
    postrotate
        [ -f /run/nginx.pid ] && kill -USR1 "$(cat /run/nginx.pid)"
    endscript
}

copytruncate 가 로그를 잃는 이유 🔴 실무

copytruncate — 신호를 못 줄 때만
/opt/tomcat/logs/catalina.out {
    daily rotate 7 compress
    copytruncate
}
① 원본을 복사하고 ② 원본을 0바이트로 자릅니다.
· ①과 ② 사이에 들어온 줄은 사라집니다 — 큰 파일일수록 그 틈이 깁니다
· 앱이 O_APPEND 없이 열었다면 오프셋이 그대로라 잘린 파일 앞부분이 널 바이트(sparse)로 채워집니다
· 복사하는 동안 디스크를 두 배로 씁니다
rename + 신호 — 정석
/var/log/nginx/*.log {
    daily rotate 14 compress delaycompress
    missingok notifempty
    create 0640 www-data adm
    sharedscripts
    postrotate
        [ -f /run/nginx.pid ] && \
          kill -USR1 "$(cat /run/nginx.pid)"
    endscript
}
· 한 줄도 잃지 않습니다 — rename 은 원자적이고, 신호 전까지의 줄은 회전본에 온전히 들어갑니다
· delaycompress 가 압축을 한 세대 미뤄 재오픈 전에 건드리지 않게 합니다
· 디스크 여유가 없어도 안전합니다
회전 뒤에 수집기가 파일을 다시 찾지 못하는 사고도 흔합니다. Fluent Bit·Vector·Filebeat 는 inode 로 파일을 추적하기 때문에 rename 방식에서는 문제가 없지만, copytruncate 를 쓰면 같은 inode 의 크기가 갑자기 줄어든 것으로 보여 처음부터 다시 읽거나 (중복!) 그 지점부터 건너뜁니다(유실!). 수집기를 쓴다면 copytruncate 를 피하는 이유가 하나 더 생기는 셈입니다. 회전 주기를 수집기의 Refresh_Interval 보다 충분히 길게 잡는 것도 중요합니다 — 회전본이 압축되어 사라지기 전에 다 읽어야 하니까요.
정리 — 파일의 정체는 이름이 아니라 inode 입니다. 그래서 정석은 rename → 재오픈 신호(USR1) → 한 세대 뒤 압축 순서이고, 설정에 delaycompress · sharedscripts · postrotate 세 줄이 반드시 들어갑니다. copytruncate 는 신호를 줄 방법이 없을 때만(catalina.out) 쓰는 최후 수단입니다.
LOG 07

수집기 다섯 개 — 무엇을 언제 고르나

로그 파일을 읽어 파싱하고 라벨을 붙여 저장소로 보내는 프로그램을 수집기라고 합니다. 다섯 개가 사실상의 후보이고, 고르는 기준은 성능이 아니라 "얼마나 변환할 것인가"와 "이미 무엇을 쓰고 있는가" 입니다.

히트맵 — Fluent Bit 은 가볍고, Vector 는 변환이 강합니다. 나머지는 "이미 쓰는 스택"이 정합니다.

이름언어성격

채택 정도를 숫자로 말하지 않는 이유 — 공개된 정확한 점유율 통계가 없습니다. 2026년 8월 기준 대략의 감으로는 쿠버네티스 노드 에이전트에서 Fluent Bit 이 가장 흔하고 Vector 가 빠르게 따라붙는 모양새인데, 직접 확인하는 방법이 있습니다 — CNCF 연례 설문(Annual Survey)의 관측 도구 문항, 각 저장소의 GitHub 스타·릴리스 빈도 추이, 그리고 주요 매니지드 쿠버네티스의 기본 로깅 애드온이 무엇인지. 이 세 가지면 시점에 맞는 판단을 스스로 내릴 수 있습니다.

Fluent Bit — 파일을 읽어 Loki 로

# /etc/fluent-bit/fluent-bit.conf
[SERVICE]
    Flush            5
    Daemon           Off
    Log_Level        info
    Parsers_File     parsers.conf
    storage.path     /var/lib/fluent-bit/storage   # ★ 디스크 버퍼
    storage.sync     normal
    storage.max_chunks_up 128

[INPUT]
    Name             tail
    Path             /var/log/nginx/access.json
    Tag              nginx.access
    Parser           json
    DB               /var/lib/fluent-bit/tail.db   # ★ 어디까지 읽었는지
    DB.locking       true
    Mem_Buf_Limit    32MB
    storage.type     filesystem                    # 메모리 넘치면 디스크로
    Skip_Long_Lines  On
    Refresh_Interval 10

[FILTER]
    Name             modify
    Match            nginx.*
    Add              env prod
    Add              host ${HOSTNAME}

[FILTER]
    Name             lua
    Match            nginx.*
    script           mask.lua
    call             mask_token

[OUTPUT]
    Name             loki
    Match            nginx.*
    host             loki.internal
    port             3100
    labels           job=nginx, env=$env, host=$host
    label_keys       $status
    line_format      json
    Retry_Limit      False                          # 무한 재시도
storage.type filesystem 을 안 켜면 메모리 버퍼가 전부입니다. 저장소가 10분만 죽어도 Mem_Buf_Limit 를 넘긴 순간부터 새 줄을 조용히 버립니다(그리고 tail 이 멈춥니다). 디스크 버퍼를 켜고, 그 디스크에도 상한과 알림을 거세요.

Vector — VRL 로 파싱 · 마스킹 · 라우팅을 한곳에서 🟡 중급

vector.toml

[sources.nginx]
type = "file"
include = ["/var/log/nginx/access.json"]
read_from = "beginning"
fingerprint.strategy = "checksum"       # inode 대신 내용으로 파일을 식별

[sources.journal]
type = "journald"
include_units = ["nginx.service", "sshd.service"]

[transforms.parse]
type = "remap"
inputs = ["nginx"]
source = '''
  . = parse_json!(.message)
  .ts       = parse_timestamp!(.ts, "%+")
  .rt       = to_float!(.rt)
  .status   = to_int!(.status)

저장소 네 가지 — 색인 방식이 요금표를 정합니다

Loki · Elasticsearch · ClickHouse · 클라우드 서비스는 "무엇을 미리 색인해 두는가"가 서로 다릅니다. 그 한 가지 선택이 저장 비용 · 조회 속도 · 할 수 있는 질문을 통째로 결정합니다.

저장소 비교 — 색인을 언제 만드느냐가 비용을 저장 쪽과 조회 쪽으로 나눕니다.

LOG 09

요청 ID — 서버 다섯 대의 로그를 한 줄로 잇기

"결제가 안 됐어요"라는 신고 하나에서 프록시 · 앱 · 결제 게이트웨이의 로그를 각각 찾아 헤매는 일이 조사의 대부분입니다. 맨 앞 프록시가 ID 를 하나 만들어 끝까지 전달하면 이 일이 검색 한 번으로 끝납니다.

시퀀스 — ID 는 가장 바깥에서 한 번 태어나 안쪽으로만 흐릅니다.

Nginx — 만들거나, 이어받거나

# http 블록
# ① 앞단이 준 값이 있으면 그것을, 없으면 $request_id 로 새로 만듭니다
map $http_x_request_id $req_id {
    default $http_x_request_id;
    ""      $request_id;          # 빈 값일 때만 새로 발급
}

# ② 로그에 적고
log_format json escape=json '{"ts":"$time_iso8601","id":"$req_id",'
    '"status":$status,"rt":$request_time,"uri":"$uri",'
    '"ua":"$upstream_addr","urt":"$upstream_response_time"}';

server {
    # ③ 백엔드로 넘기고
    proxy_set_header X-Request-Id $req_id;

    # ④ 클라이언트에게도 돌려줍니다 (always = 4xx·5xx 응답에도)
    add_header X-Request-Id $req_id always;

    # ⑤ 오류 페이지에 찍어 두면 고객센터가 바로 받아 적을 수 있습니다
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        internal;
        ssi on;
        root /usr/share/nginx/html;
    }
    location /api/ { proxy_pass http://backend; }
}
인터넷에서 들어온 X-Request-Id 를 그대로 믿으면 안 됩니다. 누구든 아무 값이나 넣어 보낼 수 있고, 그러면 남의 요청과 같은 ID 로 로그가 섞입니다. 맨 바깥 프록시에서는 무조건 새로 발급하고, 내부망의 프록시에서만 이어받는 것이 안전합니다 ($http_x_request_id 대신 그냥 $request_id).

실무에서 진짜 효과가 큰 두 가지

① 오류 화면에 ID 를 작게 찍어 두기. 고객센터가 "화면 아래 코드를 불러 주세요" 한마디로 그 한 건의 요청 로그를 1초 만에 찾습니다. 재현도 필요 없고 시간대를 물어볼 필요도 없습니다. 50x 페이지에 <!--# echo var="request_id" --> 같은 SSI 한 줄이면 됩니다.
② 응답 헤더를 항상 내보내기(always). 프런트엔드가 API 오류를 잡을 때 응답 헤더의 ID 를 함께 리포팅하면, 브라우저에서 난 오류 하나가 서버 로그 한 줄과 정확히 짝지어집니다. add_header 는 always 를 안 붙이면 2xx·3xx 에만 붙습니다 — 정작 필요한 5xx 에 안 붙는 실수가 흔합니다.
ID 를 라벨이나 색인 필드로 만들지 마세요. 값의 가짓수가 요청 수만큼이라, Loki 라벨이나 ES 의 keyword 필드로 두면 색인이 폭발합니다. 본문 안의 값으로 두고 문자열 검색하는 것이 맞습니다 — 시간 범위만 좁히면 충분히 빠릅니다.
정리 — 가장 바깥 프록시에서 ID 를 하나 만들고, proxy_set_header 로 안쪽에 넘기고, add_header ... always 로 밖에도 돌려줍니다. 세 서버가 같은 값을 로그에 적으면 검색 한 번으로 전 구간이 모입니다. 인터넷에서 온 ID 는 믿지 말고 새로 발급하세요.
LOG 10

비용 · 샘플링 · 보존 — 안 남길 것을 정하는 일

로그 비용은 산수로 미리 알 수 있습니다. 초당 요청 수 × 한 줄 크기 × 86,400. 이 계산을 한 번만 해 보면 "일단 다 남기자"가 왜 안 되는지가 바로 보입니다.

막대 — 가장 큰 절감은 압축이고, 그다음이 안 보내는 것입니다.

내 서버는 얼마나 쌓이나 — 30초 계산

#    초당 요청 × 평균 바이트 × 86400 = 하루 바이트
#    1,000 × 500 × 86,400 = 43,200,000,000 ≈ 43 GB/일 ≈ 1.3 TB/월
#    여기에 서버 대수를 곱하면 그것이 수집기가 보낼 총량입니다

# ⑤ 필드 하나가 차지하는 비중 — 뭘 뺄지 정할 때

map $request_uri $uri_log {

# ① 설정 변경 감시 — 누가 nginx.conf · logrotate 규칙을 고쳤나
-w /etc/nginx/         -p wa -k nginx-conf
-w /etc/logrotate.d/   -p wa -k rotate-conf

# ② 로그 삭제·이름 변경 감시 — 사람이 한 것만 (auid = 로그인한 실제 사용자)
-a always,exit -F arch=b64 -S unlink,unlinkat,rename,renameat \
   -F dir=/var/log -F auid>=1000 -F auid!=unset -k log-tamper

# ② 오브젝트 스토리지 — 버킷 단위 잠금 (S3 Object Lock · COMPLIANCE 모드)
aws s3api create-bucket --bucket corp-audit-logs \

    '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":400}}}'
#   COMPLIANCE = 루트 계정도 기간 안에는 삭제 불가. GOVERNANCE = 특정 권한이면 삭제 가능

# ③ 읽을 수 있는 사람 — 그룹으로 좁힙니다
ls -l /var/log/nginx/                # -rw-r----- www-data adm  ← 0640 이 정상
sudo chmod 0750 /var/log/nginx
sudo usermod -aG adm            dev-kim     # 웹서버 로그 열람
sudo usermod -aG systemd-journal dev-kim    # journalctl 전체 열람
# audit.log 는 root 만 — 그룹 열람도 열지 않습니다

# ④ 원격 저장소는 "쓰기만" 되는 자격 증명을 줍니다
#   수집기 계정: s3:PutObject 만 · Loki 테넌트: push 만 · 조회 계정은 별도
수집기 자격 증명이 "읽기·삭제"까지 되면 서버 한 대 뚫린 것으로 전체 로그가 날아갑니다. 수집기는 보내기만, 조회는 사람 계정, 삭제는 보존 정책(수명 주기 규칙)만 하게 하세요. 세 가지가 분리된 상태를 확인하는 것이 로그 접근 통제의 전부입니다.
흔한 상태 — 감사 로그가 그냥 로그인 경우
· /var/log/audit 가 서버 안에만 있고 침입자가 지우면 끝
· /var/log 가 0755 라 모든 계정이 액세스 로그를 읽음
· 수집기 IAM 이 s3:* — 한 서버가 뚫리면 아카이브 삭제 가능
· "점검"을 한 적이 없어 규정 점검에서 바로 지적
목표 상태
· auditd → rsyslog(RELP, 디스크 큐) → 중앙 서버 즉시 전송
· 중앙은 Object Lock 버킷 또는 chattr +a 파일
· 로컬 로그 0640 www-data:adm, 열람은 그룹 가입으로만
· 월 1회 aureport 요약을 티켓으로 남김 — 점검 기록도 감사 로그
정리 — 마스킹은 웹서버가 애초에 안 적는 것이 유일하게 복제본 0이고, 수집기 마스킹은 두 번째 방어선입니다. 감사 로그는 반대로 즉시 서버 밖으로 보내고 · 불변 저장하고 · 정기 점검해야 하며, 수집기는 보내기만 되는 자격 증명을 갖습니다. 접속기록 보관 의무 때문에 "안 남기기"는 답이 아니고, 식별자는 남기고 내용은 지우는 것이 답입니다.
LOG 12

컨테이너 로그와 조사 절차 — 시간 → 상태 → 경로 → 업스트림 → ID

쿠버네티스에서는 logrotate 도 파일 경로도 여러분 것이 아닙니다 — kubelet 이 회전하고 런타임이 파일을 씁니다. 그 위에서 장애가 나면 다섯 번 좁히는 절차 하나로 300만 줄에서 한 줄까지 내려갑니다. 앞의 열한 섹션이 전부 이 절차를 위해 준비한 것입니다.

트리 — 파일은 런타임이 쓰고 kubelet 이 회전하며, 읽는 쪽이 kubectl 과 수집기 둘로 갈립니다.

노드 쪽 — 회전과 파일 형식

# kubelet 설정 (KubeletConfiguration) — 노드마다 적용됩니다

kind: KubeletConfiguration
containerLogMaxSize: 50Mi      # 기본 10Mi — 시끄러운 앱은 몇 분이면 다 밀려납니다

# 2026-08-31T06:04:22.123456789Z stdout F {"level":"error","msg":"pay failed","id":"3f8a9c"}

회전 상한이 곧 "조사 가능한 시간"입니다. 초당 200줄 × 300바이트면 10Mi 는 3분도 안 돼 밀려납니다. 장애가 난 파드의 kubectl logs 가 비어 있는 이유가 대개 이것이고, 답은 상한을 키우는 것이 아니라 수집기로 밖에 내보내는 것입니다.

Fluent Bit DaemonSet — 실제로 손대는 설정

[INPUT]
    Name              tail
    Path              /var/log/containers/*.log
    Exclude_Path      /var/log/containers/*_kube-system_*.log
    multiline.parser  cri                 # ★ CRI 형식 + 잘린 줄(P) 이어 붙이기
    Tag               kube.*
    DB                /var/lib/fluent-bit/kube.db   # hostPath 볼륨에 두세요
    Mem_Buf_Limit     50MB
    Skip_Long_Lines   On
    Refresh_Interval  10

[FILTER]
    Name                kubernetes         # 파일명에서 파드를 찾아 API 로 메타데이터 조회
    Match               kube.*
    Merge_Log           On                 # 본문이 JSON 이면 필드로 펼침
    Merge_Log_Key       app
    Keep_Log            Off
    K8S-Logging.Parser  On                 # 파드 애너테이션으로 파서 지정 가능
    K8S-Logging.Exclude On                 # fluentbit.io/exclude: "true" 인 파드는 제외
    Labels              On
    Annotations         Off                # 애너테이션은 크고 카디널리티가 높습니다

[OUTPUT]
    Name   loki
    Match  kube.*
    host   loki.logging.svc
    labels job=kube, ns=$kubernetes['namespace_name'], app=$kubernetes['labels']['app']
    # ★ pod_name 을 라벨로 넣지 마세요 — 재배포마다 스트림이 늘어납니다(lg08)
# 파드 쪽에서 로그 수집 방식을 애너테이션으로 조정
metadata:
  annotations:
    fluentbit.io/parser: nginx        # 이 파드는 nginx 파서로
    fluentbit.io/exclude: "true"      # 이 파드는 아예 수집 안 함(부하 테스트 등)
인그레스 컨트롤러도 웹서버입니다 — lg02·lg03 의 이야기가 그대로 적용됩니다. ingress-nginx 는 ConfigMap 의 log-format-upstream 으로 액세스 로그 포맷을 바꾸고 log-format-escape-json: "true" 로 JSON 을 만듭니다. 기본 포맷에 이미 $req_id · $upstream_addr · $upstream_response_time 이 들어 있어서 lg09 의 요청 ID 전파가 설정 없이 시작됩니다 — 앱이 X-Request-ID 를 이어받기만 하면 됩니다. 사이드카 방식(파드마다 수집기)은 앱이 stdout 으로 못 내보내고 파일로만 쓸 때의 예외 수단이지 기본이 아닙니다.

jq -c 'select(.ts >= "2026-08-31T15:00" and .ts < "2026-08-31T15:15")' \
   /var/log/nginx/access.json > /tmp/win.json

# ② 상태코드 — 분포와 "언제 시작됐나"
jq -r '.status' /tmp/win.json | sort | uniq -c | sort -rn
jq -r 'select(.status >= 500) | .ts[0:16]' /tmp/win.json | uniq -c   # 분 단위

# ③ 경로 — 5xx 가 어디에 몰렸나
jq -r 'select(.status >= 500) | .uri' /tmp/win.json | sort | uniq -c | sort -rn | head

# ④ 업스트림 — 어느 백엔드가, 어떤 상태로, 몇 초 만에
jq -r 'select(.status >= 500) | "\(.ua) us=\(.us) urt=\(.urt)"' /tmp/win.json \
  | sort | uniq -c | sort -rn | head

# ⑤ 요청 ID — 한 건을 골라 세 서버에서 잇습니다(lg09)
jq -r 'select(.status >= 500 and .uri == "/api/pay") | .id' /tmp/win.json | head -3

Loki 에서 — 같은 다섯 단계를 LogQL 로

# ① 시간 창은 Grafana 의 시간 선택기 (또는 --since 15m)
# ② 상태코드 — 분 단위 5xx 추이 (그래프로 보면 시작점이 보입니다)
sum by (status) (count_over_time({job="nginx"} | json | status >= 500 [1m]))

# ③ 경로 상위 5개
topk(5, sum by (uri) (count_over_time({job="nginx"} | json | status >= 500 [15m])))

# ④ 업스트림 상위 5개 — ua 는 라벨이 아니라 본문 필드입니다(json 파서가 뽑음)
topk(5, sum by (ua) (count_over_time({job="nginx"} | json | status >= 500 [15m])))

# ⑤ 요청 ID 하나로 전 서비스 — 시간 범위를 좁힌 상태에서
{env="prod"} |= "3f8a9c" | json | line_format "{{.job}} {{.uri}} {{.status}} {{.urt}}"

# 보너스 — "그 시각에 새로 나타난 에러 문구" (평소엔 없던 것)
sum by (msg) (count_over_time({job="app"} | json | level="error" [15m]))
④ 에서 보이는 패턴뜻 · 다음 행동
502 + error_log connect() failed앱 프로세스 없음 — 배포 중이거나 죽음
504 + urt ≈ proxy_read_timeout앱이 매달림 — DB 락 · 풀 고갈 · 외부 API
499 + rt 큼클라이언트가 먼저 끊음 — 그쪽 타임아웃이 짧음
5xx 가 ua 한 대에 몰림그 서버 하나 — 디스크 · 메모리 · 구버전
5xx 가 모든 ua 에 동시에공통 의존 — DB · 캐시 · 방금 배포
us=200 인데 status=502Nginx 가 바꿈 — upstream sent too big header
4xx 급증 + 특정 cip스캔 · 크리덴셜 스터핑 — 보안 탭으로
이 절차가 통하려면 앞에서 만든 것들이 전부 있어야 합니다 — ①은 $time_iso8601(lg02), ②④는 $status · $upstream_addr · $upstream_response_time(lg02), JSON 이라 jq 가 도는 것은 escape=json(lg03), 4xx·5xx 가 샘플링 없이 전부 있는 것은 map + if=(lg03), ⑤는 X-Request-Id 전파(lg09), 그리고 15분 전 로그가 아직 남아 있는 것은 회전과 보존 설계(lg06 · lg10)입니다. 메트릭과 트레이스로 같은 조사를 하는 절차는 🔭 관측 탭 OBS 13 에 있습니다 — 그쪽은 "무엇이 아픈가", 이쪽은 "어느 한 건인가"입니다.
정리 — 컨테이너 로그는 런타임이 쓰고 kubelet 이 회전하며, kubectl logs 는 노드에 남은 만큼만 보여 주므로 DaemonSet 수집기가 없으면 로그가 없는 것입니다. 장애 조사는 시간 → 상태코드 → 경로 → 업스트림 → 요청 ID 다섯 번 좁히기이고, 이 순서는 jq 로도 LogQL 로도 같습니다. ③④ 에서 한곳에 몰렸는지가 "그 서버"와 "공통 의존"을 가르는 갈림길입니다.
