LOG 11

Log4Shell 의 교훈 — 로거가 공격 통로가 되던 날

2021년 12월, 로그 한 줄이 원격 코드 실행이 됐습니다. 원인은 어려운 버그가 아니라 "로그 메시지를 데이터가 아니라 명령으로 해석했다"는 설계였습니다. 이 절은 그때 무슨 일이 있었는지보다 지금 내 프로젝트에서 무엇을 확인해야 하는지에 초점을 둡니다.

해부도 — 노란 칸이 공격자가 쓴 전부입니다. 나머지는 로거가 알아서 해 줬습니다.

무슨 일이었나 — 5분 요약

항목내용
식별자CVE-2021-44228 · CVSS 10.0 (최고 등급)
영향 범위log4j-core 2.0-beta9 ~ 2.14.1
조건공격자가 넣은 문자열이 로그 메시지에 들어가기만 하면
2.15.0JNDI 를 localhost 로 제한 — 불완전
2.16.0메시지 Lookup 제거 · JNDI 기본 꺼짐
2.17.0 · 2.17.1재귀 DoS · JDBC appender 구멍까지 마감
Java 8 이하2.12.4 (Java 7) · 2.3.2 (Java 6) 별도 패치
Logback해당 없음 — 메시지에 Lookup 이 없음
Log4j 1.xJMSAppender 를 설정했을 때만 (CVE-2021-4104)
Spring Boot 기본 구성은 안전했습니다 — spring-boot-starter-logging 에는 log4j-api 와 log4j-to-slf4j 만 있고 log4j-core 가 없습니다. 취약한 건 core 뿐입니다. 그런데 다른 라이브러리가 core 를 끌고 오는 경우가 문제였습니다 — 그래서 "우리는 Logback 쓰니까 괜찮아"가 틀린 팀이 많았습니다.

String user = req.getParameter("user");
// user = "alice\n2026-09-01 10:22:41 INFO  login ok user=admin"
log.info("login fail user={}", user);

// 해결 B — Log4j2 는 인코더 변환이 있습니다
//   %enc{%m}{CRLF}
// 해결 C — JSON 인코더를 쓰면 문자열이 이스케이프되어 자동으로 막힙니다 ★

log.info("input={}", userInput);     // ✅ 인자 자리 — 포맷 해석 대상이 아님

교훈구체적으로
메시지는 데이터입력은 인자 자리에만 · JSON 인코더
전이 의존성을 안다SBOM · dependencyInsight
산출물을 스캔이미지 스캔이 빌드 스캔보다 정직
패치 경로를 미리constraints 한 줄로 올릴 수 있게
로거도 아웃바운드앱 서버의 바깥 방향 네트워크 차단
마지막 줄이 실제로 피해를 갈랐습니다 — Log4Shell 은 로거가 바깥 LDAP 서버로 접속해야 성립합니다. 앱 서버의 아웃바운드를 화이트리스트로 막아 둔 팀은 취약한 버전을 쓰고도 뚫리지 않았습니다. 로거는 네트워크를 쓰지 않는다는 가정을 버리세요 — 소켓 appender · 수집기 전송 전부 아웃바운드입니다.
왜 이런 기능이 있었나 — ${env:HOSTNAME} · ${sys:user.dir} 같은 Lookup 은 설정 파일(log4j2.xml)에서 경로나 호스트명을 끼워 넣으려고 만든 것입니다. 문제는 그 해석이 메시지 문자열에도 적용됐다는 점, 그리고 JNDI 라는 "이름으로 아무 객체나 가져오는" 표준 API 가 Lookup 목록에 있었다는 점입니다. 둘 다 각각은 합리적이었고, 합쳐지자 폭발했습니다. 보안 사고는 대개 이렇게 정상 기능 두 개의 교차점에서 납니다.
LOG 12

예외 로깅 — 한 곳에서 한 번, 스택은 필요한 만큼만

예외 로그는 장애 분석의 주식인데, 실무 로그를 열어 보면 같은 스택이 세 번 찍혀 있거나 메시지만 있고 스택이 없거나, 스택이 200줄이라 정작 원인 줄을 못 찾습니다. 규칙은 셋입니다 — 어디서 잡나 · 무엇을 남기나 · 얼마나 남기나.

트리 — 붉은 칸만 ERROR입니다. 나머지 셋을 ERROR 로 찍는 순간 알림 채널이 죽습니다.

기본기 — 스택이 사라지는 다섯 가지 방법

// ✅ 유일한 정답 — 예외를 '마지막 인자'로
log.error("order.pay.fail orderId={}", orderId, e);

// ❌ ① 메시지만 — 어디서 났는지 영원히 모릅니다
log.error("결제 실패: " + e.getMessage());

// ❌ ② toString — 첫 줄만 남고 스택은 없음
log.error("결제 실패 {}", e.toString());

// ❌ ③ printStackTrace — 로거를 안 거쳐 파일·수집기에 안 남음
e.printStackTrace();

// ❌ ④ 삼키기 — 가장 나쁨. 나중에 '왜 null 이지?' 로 돌아옵니다
try { ... } catch (Exception e) { }

// ⚠️ ⑤ {} 를 예외 자리에 쓰기 — SLF4J 는 마지막 Throwable 을 따로 뺍니다
log.error("결제 실패 {}", e);
//   출력: "결제 실패 {}" + 스택트레이스  ← {} 가 글자 그대로 남습니다
//   스택은 나오니 '틀린' 건 아니지만, 의도를 오해한 코드입니다
메시지에는 "무엇을 하다가"를, 예외에는 "왜"를 — e.getMessage() 는 라이브러리가 쓴 문장이라 내 맥락(orderId · userId)이 없습니다. 메시지 자리에 내 맥락을, 마지막 인자에 예외 객체를 두면 둘 다 남습니다.

한 곳에서 한 번 — 잡는 자리 정하기

// ❌ 레이어마다 '잡고 → 찍고 → 다시 던지기' — 같은 스택이 세 번
public Order find(Long id) {
    try { return repo.findById(id); }
    catch (DataAccessException e) {
        log.error("DB 조회 실패", e);      // 1번
        throw new OrderException(e);       // 위에서 또 찍힘
    }
}

// ✅ 잡지 말고 올려 보내기 — 필요하면 '감싸기만' 하고 로그는 안 찍음
public Order find(Long id) {
    try { return repo.findById(id); }
    catch (DataAccessException e) {
        throw new OrderException("order.find id=" + id, e);   // cause 를 반드시 넘김 ★
    }
}

// ✅ 찍는 곳은 한 곳 — 종류별로 레벨과 스택 여부를 정합니다
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)      // 4xx
    ProblemDetail badRequest(MethodArgumentNotValidException e) {
        log.warn("api.400 path={} msg={}", path(), e.getMessage());  // 스택 없음
        return ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
    }

    @ExceptionHandler(BusinessException.class)                    // 규칙 위반
    ProblemDetail business(BusinessException e) {
        log.info("api.business code={}", e.code());                   // 코드만
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.code());
    }

    @ExceptionHandler(Exception.class)                            // 5xx — 우리 잘못
    ProblemDetail unexpected(Exception e) {
        log.error("api.500 path={} traceId={}", path(), MDC.get("traceId"), e);  // 스택 전체
        return ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
    }
}
"잡고 다시 던질 때 로그를 찍지 않는다"가 규칙입니다. 예외는 그 예외를 최종적으로 처리하는 곳(응답을 만들거나 · 재시도를 포기하거나 · 스레드를 끝내는 곳)에서만 찍습니다. 중간 레이어는 맥락을 붙여 감싸기만 하고, cause 를 잃지 않게 넘깁니다.

실무에선 이렇게 — 스택트레이스를 읽을 수 있게 만들기 🔴 실무

200줄 스택을 20줄로

<!-- Logback 패턴 — %ex 의 옵션으로 길이와 제외 패키지를 정합니다 -->
<pattern>%d %-5level %logger{36} - %msg%n%ex{20, sun.reflect, java.lang.reflect,
  org.springframework.aop, org.springframework.cglib, jdk.internal}</pattern>
<!--   %ex{short}  첫 프레임만  ·  %ex{full}  전부  ·  %ex{20}  20줄
       뒤에 오는 패키지 이름이 들어간 프레임은 건너뜁니다 (Logback 1.1 이후)
       %rEx  = 원인(Caused by)을 '먼저' 찍습니다 — 진짜 원인이 맨 위로 ★
       %xEx  = 프레임마다 jar 이름·버전을 붙입니다 — 유용하지만 비쌉니다 -->

<!-- JSON 인코더 (logstash-logback-encoder) 는 더 세밀합니다 -->
<throwableConverter class="net.logstash.logback.stacktrace.ShortenedThrowableConverter">
  <maxDepthPerThrowable>20</maxDepthPerThrowable>
  <maxLength>4096</maxLength>
  <shortenedClassNameLength>30</shortenedClassNameLength>
  <rootCauseFirst>true</rootCauseFirst>          <!-- 원인부터 -->
  <inlineHash>true</inlineHash>                  <!-- 스택 해시 — 같은 오류 묶기 ★ -->
  <exclude>^sun\.reflect\..*</exclude>
  <exclude>^java\.lang\.reflect\..*</exclude>
  <exclude>^org\.springframework\.(aop|cglib|web\.filter)\..*</exclude>
  <exclude>^jakarta\.servlet\..*</exclude>

inlineHash 가 조용히 강력합니다 — 스택의 프레임 목록을 해시해서 필드로 넣어 주므로, 수집기에서 "같은 오류가 몇 번"을 셀 수 있습니다. 메시지에 orderId 가 들어가 매번 문자열이 달라도 해시는 같습니다. Sentry 같은 오류 추적 서비스가 하는 묶기(grouping)를 로그만으로 흉내 내는 방법입니다.

스택이 갑자기 비는 이유 · 예외의 비용

증상: 운영 며칠 뒤부터 NPE 로그에 스택이 없습니다
  java.lang.NullPointerException
  (at ... 줄이 하나도 없음)

원인: JIT 최적화 — OmitStackTraceInFastThrow ★
  같은 자리에서 NPE · ArrayIndexOutOfBounds · ClassCast ·
  ArithmeticException 이 '아주 많이' 나면 C2 컴파일러가
  스택 없는 미리 만든 예외 객체를 재사용합니다.

대책
  ① 로그를 거슬러 올라가 '처음' 났을 때의 스택을 찾습니다 (그때는 있음)
  ② 재현하려면  -XX:-OmitStackTraceInFastThrow  로 끕니다
     (성능 차이는 대개 무시할 수준이지만, 핫 경로에서 예외를 던지는 것 자체가 문제)
// 예외는 비쌉니다 — 생성 시점에 fillInStackTrace() 가 스택을 통째로 복사합니다
// 깊이 100 스택 한 번 ≈ 일반 로그 수만 줄에 해당하는 비용 (자릿수 수준의 감)

// 흐름 제어용 예외(재시도 신호 · 조기 종료)는 스택을 만들지 않게 합니다
public class RetrySignal extends RuntimeException {
    public RetrySignal(String msg) {
        super(msg, null, /*enableSuppression*/ false, /*writableStackTrace*/ false);
    }
}

텍스트 로그의 스택은 수집기를 깨뜨립니다 — 줄 단위로 읽는 수집기는 스택 한 줄 한 줄을 별개의 이벤트로 만듭니다. Fluent Bit 의 multiline 파서로 붙일 수도 있지만, JSON 인코더를 쓰면 스택 전체가 error.stack_trace 필드 하나로 들어가 이 문제가 사라집니다(LOG 07).
정리 — 예외는 마지막 인자로, 최종 처리하는 한 곳에서만, 4xx 는 스택 없이 · 5xx 는 원인부터 찍습니다. 이 세 줄이면 예외 로그의 사고 대부분이 사라집니다.
