LOG 08

MDC — 요청 ID 를 로그마다 자동으로

장애 분석의 첫 단계는 언제나 같습니다 — "그 요청이 남긴 줄만 모아 보기". 매번 traceId 를 인자로 넘길 수는 없으니, 스레드에 붙여 두고 패턴이 알아서 찍게 합니다. 그게 MDC 이고, 스레드가 바뀌는 순간 새 나갑니다.

스윔레인 — 레인을 넘는 화살표가 문제의 전부입니다. 넘길 때 복사하고, 끝나면 지웁니다.

필터에서 심고 finally 에서 지우기

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)          // 가장 먼저 타야 합니다
public class MdcFilter extends OncePerRequestFilter {

    private static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        String traceId = req.getHeader("X-Request-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        MDC.put("path", req.getRequestURI());
        res.setHeader("X-Request-Id", traceId);   // 클라이언트도 알 수 있게 ★
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                          // ★ 반드시 finally
        }
    }
}

// 부분만 잠깐 넣고 자동으로 빼기 — try-with-resources
try (MDC.MDCCloseable ignored = MDC.putCloseable("orderId", id.toString())) {
    log.info("order.pay.start");
    payment.pay(id);
    log.info("order.pay.done");
}   // 블록을 나가면 orderId 가 자동으로 제거됩니다
finally 를 빼먹으면 생기는 일 — 톰캣 스레드는 재사용됩니다. A 요청이 넣은 traceId 가 남아 있는 스레드로 B 요청이 들어오면 B 의 로그에 A 의 traceId 가 찍힙니다. 장애 분석 때 있지도 않은 연결을 보게 되니, 아예 없는 것보다 나쁩니다.

패턴에 꽂고 JSON 필드로 내보내기

<!-- 텍스트 패턴 — 값이 없으면 빈칸(:-) -->
<pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{20} [%X{traceId:-}] - %msg%n</pattern>

<!-- MDC 전체를 한 번에 -->
<pattern>... %mdc - %msg%n</pattern>

<!-- JSON 인코더에서는 필드로 자동 승격 -->

  <includeMdc>true</includeMdc>
  <includeMdcKeyName>traceId</includeMdcKeyName>
  <includeMdcKeyName>userId</includeMdcKeyName>
</encoder>

이미 추적 시스템이 있다면 직접 만들지 마세요 — Micrometer Tracing(Spring Boot 3.x) 을 넣으면 traceId · spanId 를 MDC 에 자동으로 넣어 줍니다. 서비스 사이를 넘어가는 전파(W3C traceparent 헤더)까지 처리됩니다. 직접 만든 X-Request-Id 는 단일 서비스일 때의 최소 구성입니다.

실무에선 이렇게 — 스레드가 바뀌는 세 자리 🔴 실무

① 스레드풀 · @Async

// 문제 — 워커 스레드에는 MDC 가 없습니다
@Async
public void sendMail(Long orderId) {
    log.info("mail.send orderId={}", orderId);   // traceId 가 빈칸 ★
}

// 해결 — 제출하는 순간의 MDC 를 복사해 주는 TaskDecorator
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> context = MDC.getCopyOfContextMap();   // 제출 스레드에서
        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            if (context != null) MDC.setContextMap(context);        // 실행 스레드에서
            try {
                runnable.run();
            } finally {
                if (previous != null) MDC.setContextMap(previous);
                else MDC.clear();                                   // ★ 되돌리기
            }
        };
    }
}

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("appExecutor")
    public Executor executor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(32);
        ex.setQueueCapacity(1000);
        ex.setThreadNamePrefix("app-");
        ex.setTaskDecorator(new MdcTaskDecorator());   // ★ 이 한 줄
        ex.initialize();
        return ex;
    }
}
CompletableFuture.supplyAsync(...) 도 같은 문제입니다 — 기본 ForkJoinPool 을 쓰면 MDC 가 비어 있습니다. executor 를 명시해서 위 decorator 가 붙은 풀을 넘기세요. @Scheduled · 메시지 리스너도 전부 같은 이야기입니다 (거기서는 새 traceId 를 발급하는 편이 맞습니다).

② 리액티브 · ③ 가상 스레드

// ② WebFlux / Reactor — MDC(ThreadLocal)는 아예 안 맞습니다
//    한 요청이 여러 스레드를 옮겨 다니기 때문입니다.
//    Reactor Context 에 담고, 로깅 시점에 MDC 로 옮깁니다.

Mono.deferContextual(ctx -> {
    String traceId = ctx.get("traceId");
    try (MDC.MDCCloseable c = MDC.putCloseable("traceId", traceId)) {
        log.info("order.start");
        return orderService.create(cmd);
    }
}).contextWrite(Context.of("traceId", newTraceId()));

// 더 나은 방법 — micrometer-context-propagation 을 넣고
//   Hooks.enableAutomaticContextPropagation();
// 을 켜면 Reactor 가 스레드 전환마다 ThreadLocal 을 복원해 줍니다.
// ③ 가상 스레드 (Java 21+ / 25 LTS)
//    MDC 는 ThreadLocal 기반이고 가상 스레드도 ThreadLocal 을 지원하므로
//    '동작은 합니다'. 재사용이 없으니 오히려 오염 위험도 없습니다.
//    문제는 개수입니다 — 가상 스레드 수십만 개 × MDC 맵 사본.

// Java 25 에서 정식이 된 ScopedValue — 값이 스코프에 묶입니다
private static final ScopedValue<String> TRACE_ID = ScopedValue.newInstance();

ScopedValue.where(TRACE_ID, traceId).run(() -> {
    handle(request);          // 이 안에서는 어디서든 TRACE_ID.get()
});                           // 스코프를 나가면 자동으로 사라집니다 ★

// 다만 로깅 라이브러리의 %X{} 는 아직 MDC 를 봅니다.
// 당장은 MDC 를 쓰고, ScopedValue 는 지원이 붙는 대로 옮기는 것이 현실적입니다.
정리하면 — 서블릿 + 스레드풀이면 필터 + TaskDecorator 로 충분하고, WebFlux 면 Reactor Context + 자동 전파를 켜고, 가상 스레드면 지금은 MDC 그대로 쓰되 스레드 수가 극단적으로 많은 구간만 ScopedValue 를 검토하세요.
LOG 09

Spring Boot 로깅 — 재시작 없이 레벨 바꾸기

운영 중에 "이 부분만 DEBUG 로 보고 싶다"가 생깁니다. 배포하고 재시작하면 그 사이 증상이 사라집니다. Actuator 의 loggers 엔드포인트는 이 문제를 한 번의 POST 로 끝냅니다.

시퀀스 — 왕복 두 번이면 끝납니다. 배포 없이 관측 수준을 바꾸는 가장 싼 도구입니다.

Actuator loggers 엔드포인트

management:
  endpoints:
    web:
      exposure:
        include: health,info,loggers,metrics   # loggers 를 열어야 합니다
  endpoint:
    loggers:
      access: unrestricted                     # 읽기+쓰기 허용
# 지금 상태 보기
curl -s localhost:8080/actuator/loggers/com.myapp | jq
# {"configuredLevel":null,"effectiveLevel":"INFO"}
#   configuredLevel = 직접 지정한 값 (없으면 null)
#   effectiveLevel  = 상속까지 계산한 실제 값 ★

# DEBUG 로 올리기
curl -s -X POST localhost:8080/actuator/loggers/com.myapp \
     -H "Content-Type: application/json" \
     -d '{"configuredLevel":"DEBUG"}'

# 특정 클래스만 (더 좁게)
curl -s -X POST localhost:8080/actuator/loggers/com.myapp.order.OrderService \
     -H "Content-Type: application/json" -d '{"configuredLevel":"TRACE"}'

# 되돌리기 — null 을 보내면 상속 상태로 복귀
curl -s -X POST localhost:8080/actuator/loggers/com.myapp \
     -H "Content-Type: application/json" -d '{"configuredLevel":null}'

# 전체 로거 목록에서 지금 DEBUG 인 것만 뽑기
curl -s localhost:8080/actuator/loggers \
  | jq -r '.loggers | to_entries[] | select(.value.effectiveLevel=="DEBUG") | .key'
이 엔드포인트는 반드시 잠가야 합니다 — 레벨을 바꿀 수 있다는 것은 디스크를 채우고 서비스를 느리게 만들 수 있다는 뜻입니다. 관리 포트를 따로 열고(management.server.port), 사내망에서만 접근하게 하거나 인증을 붙이세요. 인터넷에 열린 /actuator/loggers 는 그 자체로 사고입니다.

  1. JVM 시작
  2. Spring 이 application.yml 을 읽음

LOG 10

성능과 비용 — 얼마나 찍을지를 설계합니다

로그를 많이 찍으면 진단은 쉬워지고 지연·비용은 나빠집니다. 반대도 마찬가지입니다. 정답이 하나가 아니라 상충이므로, "어디에 놓을지"를 의식적으로 정해야 합니다.

발산 램프 — 한쪽만 진한 행은 어딘가를 크게 희생하고 있다는 뜻입니다.

먼저 재세요 — 볼륨 계산

# ① 지금 초당 몇 줄을 찍고 있나
wc -l logs/app.log
# 한 시간 치라면 / 3600

# ② 한 줄 평균 바이트
ls -l logs/app.log            # 크기 ÷ 줄 수

# ③ 하루 용량 = 초당 줄 수 × 평균 바이트 × 86400
#    예) 2,000줄/s × 300B × 86400 ≈ 51.8 GB/일 (압축 전)
#    30일 보관이면 압축해도 수백 GB — 여기서 비용이 결정됩니다

# ④ 어떤 로거가 대부분을 차지하는지
awk '{print $4}' logs/app.log | sort | uniq -c | sort -rn | head -20
#   대개 상위 3개 로거가 전체의 80% 를 차지합니다 ★

# ⑤ 같은 문구가 반복되는지 (묶어서 줄일 후보)
sed -E 's/[0-9]+/N/g' logs/app.log | sort | uniq -c | sort -rn | head
줄이는 순서 — ① 상위 3개 로거의 레벨을 올린다 → ② 루프 안 로그를 요약 한 줄로 바꾼다 → ③ 정상 흐름의 DEBUG 를 샘플링한다 → ④ 그래도 남으면 비동기. ①·② 만으로 절반 이하로 떨어지는 경우가 흔합니다.

샘플링 — 다 찍지 않고 살리기

// ① 요청 단위 샘플링 — 뽑힌 요청만 통째로 DEBUG (가장 유용) ★
public class SamplingFilter extends OncePerRequestFilter {
    private static final double RATE = 0.01;   // 1%
    protected void doFilterInternal(...) {
        boolean sampled = ThreadLocalRandom.current().nextDouble() < RATE;
        MDC.put("sampled", String.valueOf(sampled));
        try { chain.doFilter(req, res); } finally { MDC.clear(); }
    }
}
<!-- MDC 값으로 appender 를 통과시키기 -->
<appender name="DEBUG_FILE" class="...RollingFileAppender">
  <filter class="ch.qos.logback.core.filter.EvaluatorFilter">
    <evaluator class="ch.qos.logback.classic.boolex.OnMarkerEvaluator">
      <marker>SAMPLED</marker>
    </evaluator>
    <OnMismatch>DENY</OnMismatch>
    <OnMatch>ACCEPT</OnMatch>
  </filter>
  ...
</appender>

<!-- 같은 문구가 쏟아질 때 초당 개수를 제한 -->
<turboFilter class="ch.qos.logback.classic.turbo.DuplicateMessageFilter">
  <allowedRepetitions>5</allowedRepetitions>
  <cacheSize>200</cacheSize>
</turboFilter>
샘플링에서 절대 빼면 안 되는 것 — ERROR · WARN 은 100% 남깁니다. 샘플링은 정상 흐름의 상세에만 겁니다. 그리고 같은 요청은 전부 찍히거나 전부 안 찍혀야 합니다 — 줄 단위로 무작위 추출하면 이어지지 않는 조각만 남아 쓸모가 없습니다.

실무에선 이렇게 — 레벨 설계 한 장 🔴 실무

레벨 배치표

레벨운영거기 넣을 것
ERROR켬사람이 개입해야 하는 실패
WARN켬재시도 성공 · 폴백 · 임계치 근접
INFO켬요청/작업 1건당 1~3줄 요약
DEBUG끔분기·중간값 (샘플링 대상)
TRACE끔루프 안 · 프로토콜 덤프
// 요청 1건 = INFO 한 줄로 요약하는 패턴 (권장) ★
long t0 = System.nanoTime();
try {
    Result r = service.handle(cmd);
    log.info("order.create result=ok orderId={} items={} ms={}",
             r.id(), r.itemCount(), ms(t0));
    return r;
} catch (BusinessException e) {
    log.warn("order.create result=rejected reason={} ms={}", e.code(), ms(t0));
    throw e;
} catch (Exception e) {
    log.error("order.create result=error ms={}", ms(t0), e);
    throw e;
}
// 이 한 줄만으로 성공률 · 지연 분포 · 실패 사유 분포가 전부 나옵니다.
지표(metrics)와 역할을 나누세요 — "얼마나 자주·얼마나 느린가"는 메트릭(Micrometer)이 훨씬 싸게 답합니다. 로그는 "그 한 건에 무슨 일이 있었나"를 위해 남기세요. 로그로 집계하려 들면 비용이 수십 배가 됩니다.

로깅이 지연·GC 에 미치는 영향

비용이 생기는 자리 (비싼 순서)

 ① 위치 정보 (%L %M %C · includeCallerData)
    → 호출마다 스택을 만들어 훑습니다. 10배 이상 느려집니다. ★
 ② 동기 파일 쓰기 + 디스크 지연
    → p99 가 디스크 지연에 그대로 물립니다.
 ③ 문자열 조립 · 오토박싱 (GC 압력)
    → Young GC 빈도 증가 → p99 에 멈춤이 섞임
 ④ 예외 스택트레이스 생성
    → 깊은 스택 한 번이 수만 줄의 일반 로그보다 비쌉니다
 ⑤ 콘솔 출력 (터미널·컨테이너 파이프)
    → 의외로 느립니다. 운영에서 콘솔은 최소한으로.

거의 안 비싼 것
 · 꺼진 레벨의 log.debug("...{}", x)   → 레벨 검사 한 번
 · MDC.put / get                        → ThreadLocal 맵 접근
# 로깅이 원인인지 30분 안에 판별하는 절차
# 1) 레벨을 WARN 으로 내린다 → p99 를 비교
# 2) 비동기로 바꾼다        → p99 를 비교
# 3) 둘 다 안 변하면 로깅이 아닙니다 (다른 데를 보세요)

# GC 압력 확인
java -Xlog:gc*:file=gc.log:time,uptime -jar app.jar
# alloc rate 가 레벨을 내렸을 때 눈에 띄게 떨어지면 로깅이 원인입니다
①번은 정말 자주 봅니다 — 패턴에 %L(줄 번호)을 넣어 두면 로그 한 줄마다 스택 트레이스를 만듭니다. “줄 번호가 있으면 편하니까”로 넣었다가 TPS 가 절반이 된 사례가 흔합니다. 로거 이름(%logger)과 이벤트 이름이면 위치는 충분히 좁혀집니다.
