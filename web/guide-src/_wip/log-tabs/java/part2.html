LOG 04

의존성 지옥 풀기 — 바인딩 하나 · 브리지 여럿

로깅에서 가장 자주 나는 사고는 코드 문제가 아니라 클래스패스 문제입니다. "로그가 안 나온다" · "두 번 찍힌다" · "라이브러리 로그만 안 보인다" — 전부 이 절의 이야기입니다.

의존 그래프 — 들어오는 화살표는 여럿, 나가는 화살표는 하나. 이 모양이 깨지면 로그가 이상해집니다.

증상으로 원인 찾기

증상원인
로그가 하나도 안 나옴바인딩 0개 → NOP
같은 줄이 두 번appender 중복 · additivity
내 로그만 나옴브리지 없음 (JCL·JUL 유실)
설정 파일이 안 먹음다른 구현체가 이김
StackOverflowError브리지 순환 ★
기동 로그만 안 나옴JUL 브리지 초기화 시점
SLF4J(W): Class path contains multiple SLF4J providers.
SLF4J(W): Found provider [ch.qos.logback.classic.spi.LogbackServiceProvider]
SLF4J(W): Found provider [org.apache.logging.slf4j.SLF4JServiceProvider]
SLF4J(W): Actual provider is of type [...LogbackServiceProvider]

  → 경고일 뿐 실행은 됩니다. 그래서 더 위험합니다.
    개발 PC 와 운영 서버의 클래스패스 순서가 다르면
    '어느 쪽이 이기는지'가 환경마다 달라집니다. ★
NOP 이 가장 무섭습니다 — Defaulting to no-operation (NOP) logger implementation 은 예외가 아니라 경고입니다. 애플리케이션은 멀쩡히 뜨고, 로그만 조용히 사라집니다. 장애 나서야 알게 됩니다. 기동 로그의 SLF4J 줄을 CI 에서 검사하는 팀도 있습니다.

브리지 네 개 — 이름 규칙만 알면 됩니다

아티팩트하는 일
jul-to-slf4jjava.util.logging → SLF4J
jcl-over-slf4jcommons-logging → SLF4J
log4j-over-slf4jLog4j 1.x → SLF4J
log4j-to-slf4jLog4j2 API → SLF4J
이름 읽는 법
  · "A-over-B"  = A 의 API 를 흉내 내는 가짜 jar (원본은 반드시 제거)
  · "A-to-B"    = A 의 정식 어댑터 (원본 API 는 그대로 둠)
  · "B-A-impl"  = B(파사드)를 A(구현)로 잇는 바인딩

절대 같이 넣으면 안 되는 짝 ★
  log4j-over-slf4j  +  slf4j-log4j12    → 무한 재귀 (StackOverflowError)
  jcl-over-slf4j    +  slf4j-jcl        → 무한 재귀
  log4j-to-slf4j    +  log4j-slf4j2-impl → 무한 재귀

  이유: A→B 로 보내는 다리와 B→A 로 보내는 다리를
        동시에 놓으면 로그 한 줄이 영원히 왕복합니다.
Spring Boot 는 이걸 이미 해 뒀습니다 — spring-boot-starter-logging 안에 logback-classic + log4j-to-slf4j + jul-to-slf4j 가 들어 있습니다. 그래서 부트 프로젝트는 아무것도 안 해도 브리지가 다 깔려 있습니다.

실무에선 이렇게 — exclude 를 실제로 쓰는 법 🔴 실무

Gradle — 무엇이 어디서 들어왔는지부터

# ② '왜 들어왔는지' 경로 추적 — 이게 진짜 무기입니다 ★
./gradlew dependencyInsight --dependency log4j-core --configuration runtimeClasspath

# 출력 예

#  \--- com.example:legacy-client:3.1
#       \--- runtimeClasspath

# ③ 실제 실행 시점의 클래스패스에서 중복 확인
jar tf build/libs/app.jar | grep -i "SLF4JServiceProvider"
// build.gradle.kts

// ── A. 프로젝트 전체에서 특정 모듈을 빼기 (가장 확실)

    exclude(group = "commons-logging", module = "commons-logging")
    exclude(group = "log4j",           module = "log4j")           // 1.x

}

// ── B. 특정 의존성에서만 빼기

    exclude(group = "org.apache.logging.log4j", module = "log4j-core")
}

// ── C. 빠진 자리를 브리지로 메우기
implementation("org.slf4j:jcl-over-slf4j")
implementation("org.slf4j:log4j-over-slf4j")

// ── D. 중복이 다시 들어오면 빌드를 깨뜨리기 ★
configurations.all {
    resolutionStrategy {
        componentSelection {
            all {
                if (candidate.module == "slf4j-log4j12") reject("바인딩 중복 금지")
            }
        }
    }
}

LOG 05

Logback 설정 — appender · 롤링 · 프로파일

Spring Boot 는 application.yml 만으로도 꽤 갑니다. 그러다 어느 순간 패턴을 바꾸고 싶고 · 파일을 나누고 싶고 · 프로파일마다 다르게 하고 싶어집니다. 그때 필요한 것이 logback-spring.xml 한 장입니다.

원통이 저장소 — 파일은 계속 늘어납니다. 자르는 규칙과 지우는 규칙을 둘 다 정해야 끝납니다.

logback-spring.xml 한 장 (복붙용)

<!-- src/main/resources/logback-spring.xml -->
<configuration scan="true" scanPeriod="30 seconds">

  <!-- 부트가 만들어 둔 기본값을 그대로 가져다 씁니다 -->
  <include resource="org/springframework/boot/logging/logback/defaults.xml"/>

  <!-- application.yml 의 값을 XML 로 끌어오기 -->
  <springProperty scope="context" name="APP" source="spring.application.name"/>

  <property name="PATTERN"
      value="%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId:-}] - %msg%n"/>

  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder><pattern>${PATTERN}</pattern></encoder>
  </appender>

  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/${APP}.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>logs/${APP}-%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>100MB</maxFileSize>      <!-- 이 크기를 넘으면 자름 -->
      <maxHistory>30</maxHistory>            <!-- 30일치만 -->
      <totalSizeCap>10GB</totalSizeCap>      <!-- 전체 상한 ★ -->
      <cleanHistoryOnStart>true</cleanHistoryOnStart>
    </rollingPolicy>
    <encoder><pattern>${PATTERN}</pattern></encoder>
  </appender>

  <!-- 프로파일마다 다르게 -->
  <springProfile name="local">
    <root level="DEBUG"><appender-ref ref="CONSOLE"/></root>
  </springProfile>
  <springProfile name="prod">
    <logger name="com.myapp" level="INFO"/>
    <root level="WARN">
      <appender-ref ref="CONSOLE"/>
      <appender-ref ref="FILE"/>
    </root>
  </springProfile>
</configuration>
파일 이름이 logback.xml 이면 안 됩니다 — <springProfile> · <springProperty> 는 Spring 이 로깅을 초기화할 때 처리하므로, Logback 이 먼저 읽어 버리는 logback.xml 에서는 동작하지 않습니다. Spring Boot 에서는 항상 logback-spring.xml.

XML 없이 application.yml 로만

logging:
  level:
    root: INFO
    com.myapp: DEBUG
    org.hibernate.SQL: DEBUG
    org.springframework.web: WARN

  file:
    name: logs/app.log          # 경로+이름 (path 와 동시에 쓰지 않습니다)

  logback:
    rollingpolicy:
      file-name-pattern: logs/app-%d{yyyy-MM-dd}.%i.log.gz
      max-file-size: 100MB
      max-history: 30
      total-size-cap: 10GB
      clean-history-on-start: true

  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level %logger{20} - %msg%n"
    file: "%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId:-}] - %msg%n"

  charset:
    file: UTF-8                 # 윈도우에서 한글 깨짐 방지 ★
패턴 조각뜻
%d{...}시각
%thread스레드 이름
%-5level레벨 (5칸 왼쪽 정렬)
%logger{36}클래스명 (36자로 축약)
%X{traceId:-}MDC 값 (없으면 빈칸)
%msg%n메시지 + 줄바꿈
%ex{short}스택트레이스 (짧게)
%L %M %C줄번호·메서드·클래스 — 매우 느림
어디까지 yml 로 되나 — 레벨 · 파일 이름 · 롤링 · 패턴 · 인코딩까지는 yml 로 끝납니다. appender 를 여러 개 만들고 로거마다 다르게 붙이는 순간 XML 이 필요합니다. 그 전까지는 XML 을 만들지 마세요 — 관리 대상만 늘어납니다.

실무에선 이렇게 — 설정이 안 먹을 때 🔴 실무

Logback 이 설정을 찾는 순서

① logback-test.xml   (테스트 클래스패스 — 있으면 이게 이깁니다) ★
② logback.xml
③ (Spring Boot) logback-spring.xml
④ 아무것도 없으면 → 콘솔에 DEBUG 로 전부 출력

흔한 함정
  · src/test/resources/logback-test.xml 을 넣어 두고 잊어버림
    → 테스트에서만 로그가 이상하게 나옴
  · 라이브러리 jar 안에 logback.xml 이 들어 있음
    → jar tf lib.jar | grep logback  로 확인
  · -Dlogback.configurationFile=/path/logback.xml 로 강제 지정 가능

설정이 안 먹으면 우선 이걸 켭니다
  <configuration debug="true">
    → 어떤 파일을 읽었고 appender 를 어떻게 만들었는지 전부 출력
# 실행 중에 어떤 설정 파일을 읽었는지 확인
java -Dlogback.debug=true -jar app.jar 2>&1 | head -40

# 지금 유효한 레벨을 코드로 확인
# (Actuator 가 있으면 LOG 09 의 엔드포인트가 더 편합니다)

appender 를 나누고 중복을 막기

<!-- 에러만 따로 파일로 빼기 -->
<appender name="ERROR_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
  <filter class="ch.qos.logback.classic.filter.LevelFilter">
    <level>ERROR</level>
    <onMatch>ACCEPT</onMatch>
    <onMismatch>DENY</onMismatch>
  </filter>
  <file>logs/error.log</file>
  <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
    <fileNamePattern>logs/error-%d{yyyy-MM-dd}.log.gz</fileNamePattern>
    <maxHistory>90</maxHistory>
  </rollingPolicy>
  <encoder><pattern>${PATTERN}</pattern></encoder>
</appender>

<!-- 감사 로그처럼 '한 로거를 통째로 다른 파일로' -->
<logger name="AUDIT" level="INFO" additivity="false">
  <!--       additivity="false" 가 없으면 root 로도 또 나갑니다 ★ -->
  <appender-ref ref="AUDIT_FILE"/>
</logger>

<!-- 시끄러운 라이브러리 조용히 시키기 -->
<logger name="org.apache.http" level="WARN"/>
<logger name="org.hibernate.type.descriptor.sql" level="WARN"/>
“로그가 두 번 찍혀요”의 99%가 additivity 입니다. Logback 의 로거는 부모에게도 전달합니다 — com.myapp.Order 로거에 appender 를 붙이면 그 appender + root 의 appender 양쪽으로 나갑니다. 따로 빼려면 additivity="false" 를 반드시 붙이세요.
LOG 06

Log4j2 와 비동기 로깅 — Disruptor 가 뭘 바꿨나

Logback 에도 AsyncAppender 가 있습니다. 그런데 Log4j2 의 AsyncLogger 는 다른 층에서, 다른 자료구조로 비동기를 합니다. 그 차이가 처리량 차이의 정체입니다.

막대 — 동기끼리는 차이가 없습니다. 갈라지는 지점은 "누가 디스크를 기다리나"입니다.

AsyncAppender 와 AsyncLogger 는 다른 층입니다

Logback AsyncAppenderLog4j2 AsyncLogger
비동기 지점appender 앞logger 호출 직후
자료구조ArrayBlockingQueueLMAX Disruptor 링버퍼
락있음락 없음 (CAS)
포맷 시점큐에 넣기 전소비 스레드에서
가득 찼을 때버리거나 블록정책 선택 가능
설정XML 몇 줄의존성 + 설정
<!-- Logback — 이 정도로도 대부분 충분합니다 -->
<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
  <queueSize>8192</queueSize>            <!-- 기본 256 은 너무 작습니다 -->
  <discardingThreshold>0</discardingThreshold>
  <!-- 기본값 20 이면 큐가 80% 차는 순간 INFO 이하를 버립니다 ★ -->
  <neverBlock>false</neverBlock>
  <!-- true 면 큐가 꽉 찼을 때 로그를 버리고 애플리케이션은 안 멈춥니다 -->
  <includeCallerData>false</includeCallerData>
  <!-- true 로 하면 스택을 뒤져 줄번호를 붙입니다 — 10배 이상 느려집니다 -->
  <appender-ref ref="FILE"/>
</appender>
기본값이 조용히 로그를 버립니다 — Logback AsyncAppender 의 discardingThreshold 기본값은 20입니다. 큐가 80% 차면 TRACE·DEBUG·INFO 를 말없이 버립니다. “부하가 몰릴 때만 로그가 사라진다”는 신고의 원인이 대개 이것입니다. 버리기 싫으면 0, 대신 큐가 꽉 차면 애플리케이션이 기다립니다.

Log4j2 전면 비동기 켜기

// build.gradle.kts
configurations.all {
    exclude(group = "org.springframework.boot", module = "spring-boot-starter-logging")
}
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-log4j2")
    implementation("com.lmax:disruptor")   // 버전은 Log4j2 문서의 호환 표를 따르세요
}
# 방법 ① 전면 비동기 — 모든 로거가 비동기가 됩니다 (가장 빠름)
java -Dlog4j2.contextSelector=org.apache.logging.log4j.core.async.AsyncLoggerContextSelector \
     -jar app.jar

# 또는 src/main/resources/log4j2.component.properties 에
#   log4j2.contextSelector=org.apache.logging.log4j.core.async.AsyncLoggerContextSelector
#   log4j2.asyncLoggerRingBufferSize=262144
#   log4j2.asyncQueueFullPolicy=Discard        # 기본은 Default(블록)
#   log4j2.discardThreshold=INFO
<!-- 방법 ② 혼합 — 일부 로거만 비동기 -->
<Configuration status="WARN">
  <Appenders>
    <RollingFile name="FILE" fileName="logs/app.log"
                 filePattern="logs/app-%d{yyyy-MM-dd}-%i.log.gz">
      <PatternLayout pattern="%d %-5level %logger{36} [%X{traceId}] - %msg%n"/>
      <Policies>
        <TimeBasedTriggeringPolicy/>
        <SizeBasedTriggeringPolicy size="100MB"/>
      </Policies>
      <DefaultRolloverStrategy max="30"/>
    </RollingFile>
  </Appenders>
  <Loggers>
    <!-- includeLocation 은 기본 false 로 두세요 (켜면 스택을 뒤집니다) -->
    <AsyncLogger name="com.myapp" level="INFO" includeLocation="false"
                 additivity="false">
      <AppenderRef ref="FILE"/>
    </AsyncLogger>
    <Root level="WARN"><AppenderRef ref="FILE"/></Root>
  </Loggers>
</Configuration>
비동기의 대가 — ① 순서가 살짝 흔들릴 수 있고, ② 프로세스가 죽으면 큐에 남은 로그가 사라지며(그래서 종료 훅이 중요), ③ 예외 스택을 나중에 포맷하므로 가변 객체를 로그 인자로 넘기면 값이 달라집니다. 마지막 항목은 실제로 디버깅을 어렵게 만드니, 불변 값이나 문자열을 넘기세요.

한 단계 더 — 가비지 프리 모드 🧬 전문가

로그 한 줄이 만드는 쓰레기

log.info("order={} amount={}", id, amount) 한 번에 만들어지는 객체(대략)

  · Object[] 가변인자 배열              1개
  · Long / BigDecimal 오토박싱          2개
  · 포맷된 String                       1개
  · byte[] (인코딩 결과)                1개
  · LogEvent · 타임스탬프 객체 등        수 개

초당 10만 줄 = 초당 수십만 개의 단명 객체
  → Young GC 빈도가 올라가고, p99 지연에 GC 멈춤이 섞입니다.

Log4j2 의 대응 (가비지 프리 모드)
  · ThreadLocal 로 버퍼를 재사용   log4j2.enableThreadlocals=true
  · 직접 인코딩(중간 String 생략)  log4j2.enableDirectEncoders=true
  · 대부분의 Layout·Appender 가 이 모드를 지원합니다

  주의: 웹 애플리케이션(WAR)에서는 ThreadLocal 이 누수 위험이라
        기본으로 꺼집니다. 실행형 jar 에서만 켜세요.
여기까지 필요한 경우는 드뭅니다 — 초당 수십만 줄, p99 를 밀리초 단위로 관리하는 시스템에서만 의미가 있습니다. 그 전에는 로그를 덜 찍는 것이 훨씬 큰 효과를 냅니다(LOG 10).

구조적 로깅 — 문장 대신 필드로 찍기

로그를 사람이 grep 하던 시대에는 문장이 좋았습니다. 수집기에 넣고 검색·집계하는 시대에는 필드가 좋습니다. 바꾸는 데 필요한 것은 인코더 하나와 필드 이름 규약입니다.

구름이 우리 손 밖의 경계 — 거기서부터는 필드 이름이 계약입니다. 이름을 바꾸면 대시보드가 깨집니다.

Spring Boot 3.4 부터는 의존성 없이도 됩니다 — logging.structured.format.console=ecs (또는 logstash·gelf) 한 줄로 부트가 직접 JSON 을 찍습니다. 간단한 서비스라면 인코더 라이브러리를 넣지 않아도 됩니다.

코드에서 필드를 붙이는 세 가지 방법

import static net.logstash.logback.argument.StructuredArguments.*;

// ① kv — 메시지에도 보이고 JSON 필드도 됩니다 (가장 무난)
log.info("order.completed {} {}", kv("orderId", id), kv("amount", amount));
// 텍스트:  order.completed orderId=1042 amount=32000
// JSON:    {"message":"order.completed ...","orderId":1042,"amount":32000}

// ② value — 메시지에는 값만, JSON 에는 필드로
log.info("order.completed {}", value("orderId", id));

// ③ SLF4J 2.0 표준 fluent API — 라이브러리 의존이 없습니다 ★
log.atInfo()
   .setMessage("order.completed")
   .addKeyValue("orderId", id)
   .addKeyValue("amount", amount)
   .addKeyValue("elapsedMs", elapsed)
   .log();

// MDC 에 넣은 값은 자동으로 전부 필드가 됩니다 (LOG 08)
MDC.put("traceId", traceId);
log.info("order.completed");   // JSON 에 traceId 가 자동 포함

실무에선 이렇게 — 필드 설계 규칙 🔴 실무

필드 다섯 묶음이면 충분합니다

묶음필드누가 넣나
시각·레벨@timestamp log.level인코더
어디service.name host log.logger설정
누가·어떤 요청trace.id user.idMDC
무슨 일event.action + 도메인 값코드
실패error.type error.stack_trace인코더
이름 규칙 세 개
  ① 소문자 + 점(.) 계층      user.id, http.response.status_code
  ② 같은 뜻은 같은 이름       userId / user_id / uid 를 섞지 않기
  ③ 값의 타입을 고정          orderId 는 항상 숫자, 항상 문자열 중 하나

바꿀 때는 '한동안 둘 다' 를 찍습니다
  · 새 필드를 추가 → 대시보드를 옮김 → 옛 필드를 제거
  · 이름을 바로 바꾸면 그날의 대시보드가 통째로 빕니다
필드 폭발(mapping explosion) — Elasticsearch 는 새 필드마다 매핑을 만듭니다. 동적으로 만들어지는 키(예: kv(orderId, ...) 를 키 이름에 넣기)를 찍으면 인덱스가 수천 개 필드로 부풀어 클러스터가 죽습니다. 키 이름은 코드에 상수로 고정하세요 — 값만 변해야 합니다.

텍스트와 JSON 을 함께 쓰기

<!-- 개발자는 콘솔에서 사람이 읽는 형태로,
     수집기는 파일에서 JSON 으로 — 둘 다 켜 둡니다 -->
<springProfile name="local">
  <root level="DEBUG"><appender-ref ref="CONSOLE"/></root>
</springProfile>

<springProfile name="prod">
  <root level="INFO">
    <appender-ref ref="JSON"/>      <!-- 파일: 기계용 -->
    <appender-ref ref="CONSOLE"/>   <!-- 표준출력: 컨테이너 로그 -->
  </root>
</springProfile>
# 컨테이너라면 파일 대신 표준출력이 정답입니다
#   앱 → stdout(JSON) → 컨테이너 런타임 → 수집기
#   파일 롤링·디스크 관리를 앱이 안 해도 됩니다 ★

# 로컬에서 JSON 로그를 사람이 읽기
tail -f logs/app.json.log | jq -r \
  '"\(.["@timestamp"]) \(.["log.level"]) \(.message) trace=\(.["trace.id"] // "-")"'

# 특정 요청만 따라가기
grep '"trace.id":"3f9a1c0b7e2d4a55"' logs/app.json.log | jq .
둘 다 켜면 비용이 두 배 아닌가 — 맞습니다. 그래서 보통은 운영에서 콘솔은 WARN 이상, 파일 JSON 은 INFO 이상처럼 레벨을 다르게 둡니다. 컨테이너 환경이면 JSON 을 표준출력 하나로만 내보내는 쪽이 더 단순합니다.
