LOG 01

자바 로깅의 역사 — 왜 두 겹이 됐나

다른 언어는 대개 로거가 하나입니다. 파이썬은 logging, Go 는 log/slog. 자바만 파사드(SLF4J) + 구현(Logback·Log4j2) 두 겹입니다. 이유는 기술이 아니라 역사에 있습니다 — 그리고 그 역사를 알면 오늘의 의존성 문제가 전부 설명됩니다.

타임라인 — 표준이 늦게 왔기 때문에 파사드가 필요해졌습니다. 순서가 반대였다면 두 겹은 없었습니다.

System.out 은 왜 로그가 아닌가

// ❌ 이것은 로그가 아니라 '출력'입니다
System.out.println("주문 처리 시작: " + orderId);

//  · 끄고 켤 수 없습니다 (레벨이 없음)
//  · 언제 찍혔는지 모릅니다 (시각이 없음)
//  · 누가 찍었는지 모릅니다 (클래스·스레드가 없음)
//  · 파일로 못 보냅니다 (리다이렉트하면 통째로 섞임)
//  · 동기 + 락 — 초당 수만 줄이면 그 자체가 병목입니다

// ✅ 로거
private static final Logger log =
        LoggerFactory.getLogger(OrderService.class);

log.info("주문 처리 시작 orderId={}", orderId);
// 2026-09-01 10:22:41.108 [http-nio-8080-exec-3] INFO
//   c.m.order.OrderService - 주문 처리 시작 orderId=1042
System.out 이 실제로 사고를 내는 지점 — System.out 은 동기화된 PrintStream 입니다. 요청 스레드 200개가 동시에 찍으면 전부 같은 락을 기다립니다. "로그를 지웠더니 TPS 가 올랐다"는 이야기의 절반이 여기서 나옵니다.

네 세대 요약 — 지금 무엇이 남았나

세대대표지금 위치
1세대System.out테스트 코드에만
2세대Log4j 1.x2015년 수명 종료
2세대commons-logging낡은 라이브러리에 잔존
3세대java.util.loggingJDK 내장 · 도구류에서
4세대SLF4J (파사드)사실상 표준
4세대LogbackSpring Boot 기본값
4세대Log4j2대안 · 비동기가 강점
Log4j 1.x 는 왜 아직 보이나 — Apache 가 2015년에 수명 종료를 선언했지만, 그 위에 쌓인 사내 라이브러리가 너무 많았습니다. 그래서 원저자가 reload4j 라는 보안 패치 포크를 따로 냈습니다. 신규 프로젝트가 고를 이유는 전혀 없습니다.

한 단계 더 — 파사드 + 구현이라는 두 겹 🟡 중급

레이어 — 바인딩 층이 갈아 끼우는 자리입니다. 이 한 층 때문에 두 겹이 됐습니다.

라이브러리 입장에서 생각해 보기

// 내가 오픈소스 라이브러리를 만든다고 합시다.
// 로그를 남기고 싶은데, 쓰는 쪽이 어떤 로거를 쓸지 모릅니다.

// ❌ 구현을 직접 의존하면 — 사용자에게 Logback 을 강요하는 셈
implementation("ch.qos.logback:logback-classic")

// ✅ 파사드만 의존 — 사용자가 자기 구현을 고릅니다
api("org.slf4j:slf4j-api")

// 라이브러리 코드는 이것만 씁니다
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class HttpClient {
    private static final Logger log =
            LoggerFactory.getLogger(HttpClient.class);
}
한 줄 규칙 — 라이브러리는 slf4j-api 만, 애플리케이션(실행되는 쪽)만 구현체를 넣습니다. 이 규칙 하나로 이 탭에 나오는 의존성 사고의 80%가 사라집니다.

SLF4J 가 구현을 찾는 순간

// SLF4J 2.0 부터는 표준 ServiceLoader 로 찾습니다.
// logback-classic.jar 안에는 이런 파일이 들어 있습니다.
//
//   META-INF/services/org.slf4j.spi.SLF4JServiceProvider
//     → ch.qos.logback.classic.spi.LogbackServiceProvider

// 클래스패스에 provider 가 하나도 없으면
//   SLF4J(W): No SLF4J providers were found.
//   SLF4J(W): Defaulting to no-operation (NOP) logger implementation
//   → 로그가 '조용히' 전부 사라집니다 ★

// 둘 이상이면
//   SLF4J(W): Class path contains multiple SLF4J providers.
//   SLF4J(W): Actual provider is of type [...LogbackServiceProvider]
//   → 실행은 되지만 '어느 쪽이 이겼는지'는 클래스패스 순서 나름
SLF4J 1.7 과 2.x 는 찾는 방식이 다릅니다 — 1.7 은 StaticLoggerBinder 라는 클래스를 리플렉션으로 찾았고, 2.x 는 ServiceLoader 를 씁니다. 그래서 SLF4J 2.x 에 1.7용 바인딩(log4j-slf4j-impl)을 넣으면 아무 로그도 안 나옵니다. 2.x 용은 이름 끝에 2가 붙은 log4j-slf4j2-impl 입니다.
다른 언어와 비교하면 더 선명합니다 — 파이썬 logging 은 표준 라이브러리 하나라서 파사드가 필요 없었습니다. Go 는 오래 표준이 없다가 log/slog 로 표준 인터페이스를 넣었는데, 이게 사실상 자바의 SLF4J 자리입니다. 자바는 표준이 나오기 전에 생태계가 먼저 커져 버려서 파사드를 라이브러리로 만들어야 했습니다. JDK 에 들어간 java.util.logging 은 이미 Log4j 가 이긴 뒤에 나왔습니다.
LOG 02

구현체 비교 — Logback · Log4j2 그리고 나머지

고를 것은 사실상 두 개입니다. 나머지는 "이미 들어와 있어서 알아야 하는 것"에 가깝습니다. 아래 표는 절대 점수가 아니라 상대 위치입니다 — 숫자를 지어내지 않았습니다.

히트맵 — 진한 칸이 몰린 행이 그 도구의 정체입니다. Log4j2 는 성능 쪽, Logback 은 생태계 쪽에 몰려 있습니다.

채택 정도 — 숫자 대신 상대 위치로

구현체위치고르는 상황
Logback사실상 표준Spring Boot 면 그냥 기본값
Log4j2널리 씀초당 수십만 줄 · 비동기
java.util.logging내장이라 늘 있음고르는 게 아니라 만남
tinylog특정 상황에서만의존성 최소화 · 안드로이드
Log4j 1.x신규 채택 없음없음 — 걷어낼 대상
reload4j임시 방편Log4j 1.x 를 못 걷어낼 때
직접 확인하는 법 (숫자를 믿기 전에) — ① mvnrepository.com 의 “Logging Frameworks” 카테고리 usage 순위, ② GitHub 저장소의 star · 최근 릴리스 날짜, ③ 내 프로젝트는 ./gradlew dependencies · mvn dependency:tree 로 이미 뭐가 들어와 있는지부터. 2026년 8월 기준 대략의 인상은 위 표와 같지만, 시점이 지나면 바뀝니다.

고르는 기준 — 세 문장으로

✅ Logback 그대로
Spring Boot 프로젝트 · 초당 로그가 수만 줄 이하 · 설정을 application.yml 로 끝내고 싶다 · 고민하기 싫다.
→ 아무것도 안 하면 이미 Logback 입니다.
🔁 Log4j2 로 교체
초당 수십만 줄 · p99 지연에 로깅이 잡힌다 · 전면 비동기가 필요하다 · 가비지 프리 모드가 필요하다.
→ 교체 비용은 의존성 정리 + 설정 파일 다시 쓰기 정도입니다. 
고를 때 실제로 던지는 질문 세 개

① 지금 초당 몇 줄을 찍고 있나?
   → 모르면 먼저 재세요. 대부분 '생각보다 적게' 찍습니다.

② 로깅이 p99 지연에 잡히나?
   → 비동기 전환은 여기 답이 '예'일 때만 의미가 있습니다.

③ 팀이 XML 설정을 관리할 수 있나?
   → 못 하면 Logback + application.yml 이 정답입니다.
가장 흔한 오답 — “성능이 좋다니까 Log4j2 로 바꾸자”. 동기 파일 출력으로 쓰면 Log4j2 도 Logback 과 큰 차이가 없습니다. Log4j2 의 강점은 AsyncLogger 를 켰을 때 나옵니다(LOG 06).

이렇게도 쓸 수 있다 — 나머지 셋의 자리 🟡 중급

java.util.logging (JUL) — 피할 수 없는 만남

// JDK 에 내장이라 의존성이 필요 없습니다. 그게 유일한 장점입니다.
import java.util.logging.Logger;
Logger log = Logger.getLogger(MyClass.class.getName());
log.info("메시지");     // 레벨 이름부터 다름: SEVERE/WARNING/INFO/FINE

// 실무에서 JUL 을 만나는 곳
//   · Tomcat 내부 · JavaFX · JAXB · 일부 JDK 도구
//   · '표준이니까' 쓴 오래된 사내 라이브러리

// 대책 — SLF4J 로 끌어옵니다 (LOG 04 에서 자세히)
implementation("org.slf4j:jul-to-slf4j")
JUL 의 진짜 문제 — 설정 파일(logging.properties)이 JVM 전역이고, 롤링 정책이 빈약하며, 레벨 이름이 다른 로거와 안 맞습니다 (FINE ↔ DEBUG). 성능도 다른 구현체보다 떨어집니다. 직접 고르지는 말고, 들어오면 브리지로 흡수하세요.

tinylog · Log4j 1.x

// tinylog 2.x — jar 가 작고 설정이 properties 한 장이면 끝납니다

implementation("org.tinylog:tinylog-impl:2.7.0")
// SLF4J 를 통해 쓰려면
implementation("org.tinylog:slf4j-tinylog:2.7.0")

LOG 03

SLF4J 사용법 — {} 하나가 만드는 차이

log.debug("id=" + id) 와 log.debug("id={}", id) 는 결과가 같아 보입니다. 레벨이 꺼져 있을 때 완전히 달라집니다 — 그리고 운영에서 DEBUG 는 대개 꺼져 있습니다.

결정 흐름도 — 레벨 검사가 먼저냐 나중이냐가 전부입니다. {} 는 검사를 앞으로 당깁니다.

기본기 다섯 줄

private static final Logger log =
        LoggerFactory.getLogger(OrderService.class);
// static final — 클래스마다 하나. Lombok 의 @Slf4j 가 이 줄을 만들어 줍니다.

// ① 파라미터 바인딩 — 인자 개수만큼 {}
log.info("주문 생성 orderId={} userId={} amount={}", orderId, userId, amount);

// ② 예외는 '마지막 인자'로 — {} 를 하나 더 쓰지 않습니다 ★
log.error("결제 실패 orderId={}", orderId, e);
//                              ↑ {} 는 하나, 인자는 둘 — 마지막은 스택트레이스로

// ③ 중괄호를 문자로 쓰고 싶으면 백슬래시로 막습니다
log.info("literal \\{} 그대로", ignored);

// ④ 배열은 알아서 펼쳐집니다
log.debug("ids={}", (Object) new int[]{1, 2, 3});

// ⑤ 레벨은 다섯 개. 운영 기본은 INFO
log.trace(...); log.debug(...); log.info(...); log.warn(...); log.error(...);
레벨을 고르는 한 문장 기준 — ERROR: 사람이 지금 봐야 한다 · WARN: 지금은 아니지만 쌓이면 문제 · INFO: 나중에 “무슨 일이 있었나”를 재구성할 재료 · DEBUG: 개발자가 원인을 좁힐 때 켜는 것 · TRACE: 한 줄 한 줄 따라갈 때. INFO 에 “여기 지나감”을 찍기 시작하면 INFO 가 죽습니다.

isDebugEnabled 는 언제 쓰나

// ❌ 필요 없는 경우 — {} 가 이미 막아 줍니다
if (log.isDebugEnabled()) {
    log.debug("id={}", id);        // id 는 그냥 참조 전달. 비용 0
}

// ✅ 필요한 경우 ① — 인자를 만드는 것 자체가 비쌀 때
if (log.isDebugEnabled()) {
    log.debug("cart={}", cart.toDetailedString());   // ← 이 호출이 비쌉니다
}

// ✅ 필요한 경우 ② — 로그용 데이터를 모으는 반복문
if (log.isTraceEnabled()) {
    for (Item i : items) log.trace("item {}", i);    // 루프 자체를 건너뜀
}

// ✅ SLF4J 2.0 fluent API — 람다로 미루면 if 없이도 됩니다
log.atDebug()
   .addArgument(() -> cart.toDetailedString())   // 출력할 때만 호출
   .log("cart={}");

// ✅ 또는 Supplier 를 직접 넘기는 형태
log.atInfo().setMessage("무거운 계산 {}")
   .addArgument(() -> heavy())
   .addKeyValue("orderId", orderId)              // 구조적 로깅과도 이어집니다
   .log();
가장 흔한 낭비 — toString() 이 무거운 객체를 log.debug("obj={}", bigObject) 로 넘기는 것. 레벨이 꺼져 있으면 toString() 은 호출되지 않으므로 이건 안전합니다. 문제는 bigObject.toDetailedString() 처럼 내가 직접 부른 메서드입니다 — 이건 무조건 실행됩니다.

실무에선 이렇게 — 로그 문장 자체를 설계합니다 🔴 실무

나중에 검색할 수 있게 쓰기

❌ 사람만 읽는 문장
log.info("주문 " + orderId + "번이 " +
    "정상적으로 처리되었습니다");
// 검색: "정상적으로 처리" ... 몇 건인지 셀 수 없음
// 값이 문장에 녹아 있어 필드로 뽑히지 않음
✅ 기계도 읽는 문장
log.info("order.completed orderId={} amount={} ms={}",
        orderId, amount, elapsed);
// 검색: order.completed  → 건수·금액 합계·지연 분포
// 앞머리를 '이벤트 이름'으로 고정하는 것이 핵심
규칙 세 개면 충분합니다 — ① 맨 앞은 고정된 이벤트 이름(order.completed), ② 값은 key=value 로, ③ 문장은 짧게. 이렇게 쓰면 나중에 JSON 로깅(LOG 07)으로 갈 때 문장을 다시 안 써도 됩니다.

하지 말아야 할 것들

// ① 개인정보·비밀을 그대로 찍기 — 로그는 오래 남고 널리 복제됩니다
log.info("login user={} password={}", id, rawPassword);   // ❌ 절대
log.info("card={}", cardNumber);                          // ❌ 마스킹 필수
log.info("login user={}", maskEmail(email));              // ✅

// ② 루프 안에서 한 건마다 INFO
for (Order o : orders) log.info("처리 {}", o.getId());    // ❌ 10만 줄
log.info("주문 배치 처리 완료 count={}", orders.size());   // ✅ 요약 한 줄

// ③ 예외를 삼키고 메시지만 남기기
catch (IOException e) { log.error("실패: " + e.getMessage()); }  // ❌
catch (IOException e) { log.error("파일 읽기 실패 path={}", path, e); } // ✅

// ④ 로그 안에서 예외 던지기 — 로깅이 장애 원인이 됩니다
log.info("user={}", user.getName());   // user 가 null 이면 NPE ★
log.info("user={}", user);             // ✅ null 이면 "null" 이 찍힘

// ⑤ 문자열 포맷을 직접 하기
log.info(String.format("id=%d", id));  // ❌ 레벨과 무관하게 항상 포맷
④번이 실제로 장애를 냅니다 — 로그 한 줄 때문에 NullPointerException 이 나면 정상 로직이 죽습니다. SLF4J 는 인자가 null 이면 알아서 "null" 로 찍으므로, 객체를 통째로 넘기고 toString() 에 맡기는 편이 안전합니다.
