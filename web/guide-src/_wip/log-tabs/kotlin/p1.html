LOG 01

로거를 어디에 만드나 — 자바의 static final 이 코틀린에서는 셋으로 갈립니다

자바에서는 선택지가 하나였습니다. private static final Logger 를 클래스마다 한 줄 적는 것. 코틀린에는 static 이 없어서 companion object · 톱레벨 프로퍼티 · by lazy 세 갈래가 생깁니다. 셋 다 결국 같은 SLF4J Logger 를 감싸므로, 고민할 것은 성능이 아니라 어디서 보이고 언제 만들어지나 뿐입니다.

고민할 지점은 성능이 아니라 가시 범위입니다 — 톱레벨은 파일 안, companion 은 클래스 안.

세 가지를 나란히

import io.github.oshai.kotlinlogging.KotlinLogging

// ① 톱레벨 — 실무에서 가장 많이 보는 형태 ★
//    파일 맨 위에 한 줄. 같은 파일의 모든 함수가 씁니다.
private val log = KotlinLogging.logger {}

class OrderService {
    fun place(id: Long) {
        log.info { "주문 접수 id=$id" }
    }
}

// ② companion object — 자바 습관을 그대로 옮기고 싶을 때
class PayService {
    fun pay(id: Long) = log.info { "결제 id=$id" }

    companion object {
        private val log = KotlinLogging.logger {}
    }
}

// ③ 인터페이스 + 확장 — 여러 클래스에 같은 로거를 얹고 싶을 때
interface Logging
val Logging.log: KLogger
    get() = KotlinLogging.logger(javaClass.name)   // 매번 조회는 캐시됩니다
logger {} 의 빈 중괄호가 뭔가 — 람다를 하나 넘기는 겁니다. kotlin-logging 이 그 람다의 바깥 클래스 이름을 읽어 로거 이름으로 씁니다. 그래서 Foo::class.java.name 을 손으로 적을 필요가 없고, 클래스 이름을 바꿔도 로거 이름이 따라옵니다.

// 기본 — 선언한 클래스/파일 이름이 그대로 로거 이름
private val log = KotlinLogging.logger {}
//   com.example.order.OrderService

// 이름을 직접 주기 — 용도별로 묶고 싶을 때 ★

// 왜 이렇게 하나

// ⚠ 흔한 실수 — 로거를 파라미터로 받아 넘기기

// ⚠ 또 하나 — 로거를 companion 이 아닌 인스턴스 val 로
class Order {
    private val log = KotlinLogging.logger {}   // ❌ 객체마다 참조 하나
}

//   수백만 개 생기는 도메인 객체라면 필드 하나가 그냥 낭비입니다.
//   → 톱레벨이나 companion 으로 옮기세요.
정말 성능 차이가 있나 — 없습니다. LoggerFactory.getLogger(name) 는 내부 맵에서 같은 이름이면 같은 인스턴스를 돌려줍니다. 그래도 톱레벨/companion 을 권하는 이유는 성능이 아니라 객체 필드가 늘어나는 것과 이름이 예측 가능해지는 것 때문입니다.

정리 — 코틀린 로거는 파일 맨 위 private val log = KotlinLogging.logger {} 한 줄이 기본형입니다. 자바의 static final 자리를 그대로 대신하고, 이름은 자동으로 클래스/파일 이름이 됩니다. 그리고 로거 이름 = 설정 단위라는 것만 기억하면 뒤에 나오는 모든 설정이 쉬워집니다.
LOG 02

코틀린만의 함정 — 문자열 템플릿은 로그가 꺼져 있어도 먼저 계산됩니다

자바 사람들은 log.debug("id={}", id) 라는 자리표시자 문법을 씁니다. 이유가 있었습니다 — 문자열을 미리 만들지 않기 위해서입니다. 그런데 코틀린으로 오면 "id=$id" 라는 예쁜 문법이 있어서 다들 그걸 씁니다. 그리고 그 순간 자바가 20년 동안 피해 온 비용이 되돌아옵니다.

막대 길이는 단계 수입니다(측정치가 아닙니다) — 그래도 0 과 4 의 차이는 분명합니다.

무슨 일이 벌어지나 — 컴파일 결과로 보기

// 내가 쓴 코드
log.debug("주문 $id 항목 ${cart.summarize()}")

// 컴파일되면 대략 이렇게 됩니다
val s = StringBuilder()
    .append("주문 ").append(id)
    .append(" 항목 ").append(cart.summarize())   // ★ 여기서 실행!
    .toString()
log.debug(s)          // 안에서 레벨 검사 → DEBUG 꺼져 있으면 버림

//  cart.summarize() 는 DEBUG 가 꺼져 있어도 매번 돕니다.
//  그게 DB 를 한 번 더 치는 함수라면 — 로그를 껐는데도 쿼리가 나갑니다.
// 람다로 쓰면
log.debug { "주문 $id 항목 ${cart.summarize()}" }

// 대략 이렇게 됩니다

    log.debug(buildString { ... })   // 통과했을 때만 계산

얼마나 심각한가 — 판단 기준

로그 안의 내용템플릿으로 써도 되나
$id (Long)사실상 무해
$name (String)사실상 무해
${list.size}무해
$dataClass주의 — toString 전개
${list.joinToString()}❌ 위험
${json.encodeToString(x)}❌ 위험
${repo.count()}❌ 절대 금지 — I/O
진짜 문제는 속도가 아닙니다 — 부작용입니다. 로그 문자열 안에서 DB 를 치거나 lazy 컬렉션을 펼치면 로그를 끄든 켜든 그 일이 벌어지고, 최악의 경우 LazyInitializationException 같은 예외가 로그 줄에서 터집니다. “로그 한 줄 지웠더니 장애가 사라졌다”는 이야기의 대부분이 이겁니다.

이렇게도 쓸 수 있다 — SLF4J 만으로 지연 평가하기 🟡 중급

kotlin-logging 없이 버티는 방법

import org.slf4j.LoggerFactory

private val log = LoggerFactory.getLogger("com.example.Order")

// ① 자리표시자 — 가장 널리 쓰이는 형태
log.debug("주문 {} 상태 {}", id, status)
//   status.toString() 은 DEBUG 가 켜져 있을 때만 불립니다.
//   ⚠ 다만 인자를 담는 Object[] 배열은 매번 만들어집니다.

// ② 직접 검사 — 무거운 계산이 있을 때
if (log.isDebugEnabled) {
    log.debug("장바구니 {}", cart.summarize())
}

// ③ SLF4J 2.0 의 fluent API — 공급자(supplier)를 받습니다 ★
log.atDebug()
   .setMessage { "장바구니 " + cart.summarize() }
   .addKeyValue("orderId", id)
   .log()
SLF4J 2.0 fluent API 는 왜 잘 안 보이나 — 문법이 길기 때문입니다. 코틀린에서는 log.debug { } 한 줄이 같은 일을 하니 kotlin-logging 을 쓰는 편이 거의 언제나 낫습니다. fluent API 는 addKeyValue 로 구조화 로그를 만들 때만 값어치가 있습니다.

섞어 쓸 때 실제로 나오는 코드

private val log = KotlinLogging.logger {}

fun handle(order: Order) {
    // ✅ 람다 — 기본형
    log.debug { "처리 시작 ${order.id}" }

    // ✅ 예외는 첫 인자로, 메시지는 람다로
    try {
        pay(order)
    } catch (e: PayFailed) {
        log.warn(e) { "결제 실패 ${order.id} — 재시도 큐로" }
    } catch (e: Exception) {
        log.error(e) { "알 수 없는 실패 ${order.id}" }
        throw e
    }

    // ✅ 구조화 필드가 필요하면 MDC 와 함께 (LOG 06)
    log.atInfo {
        message = "주문 완료"
        payload = mapOf("orderId" to order.id, "amount" to order.amount)
    }
}
람다 안에서 예외가 나면 — kotlin-logging 은 그 예외를 삼키지 않습니다. 로그 한 줄 때문에 요청이 죽습니다. 그래서 람다 안에는 절대 실패하지 않는 표현만 넣으세요. !! 나 인덱스 접근을 넣지 마세요.

@State(Scope.Benchmark)
open class LogBench {

        log.debug("cart={}", cart)                    // toString 은 안 함

LOG 03

무엇을 고를 것인가 — 라이브러리 여섯을 한 장에

코틀린 로깅에서 이름이 나오는 것은 대략 여섯 개입니다. 문제는 이들이 같은 층에 있지 않다는 점입니다 — 어떤 것은 파사드, 어떤 것은 구현, 어떤 것은 그 위에 얹는 껍데기입니다. 먼저 어느 무대(서버·안드로이드·KMP)인지를 정하면 후보가 둘로 줄어듭니다.

한 줄로 요약하면 — 서버는 kotlin-logging + Logback, 안드로이드는 Timber, KMP 는 Kermit.

여섯 개가 각각 무엇인가

이름층한 줄 정리
kotlin-logging껍데기SLF4J 위에 람다 API만 얹음
SLF4J파사드인터페이스. 혼자선 못 찍음
Logback구현SLF4J 의 사실상 표준 구현
Log4j2구현+API비동기 로거가 강점
slf4j-simple구현표준 출력만. 테스트용
Timber껍데기안드로이드 Log 위에 얹음
Kermit · Napier전부KMP 용. 플랫폼별 백엔드 내장
왜 이름이 헷갈리나 — kotlin-logging 은 구현이 아닙니다. 이것만 넣으면 아무것도 출력되지 않습니다(SLF4J 가 “no providers” 경고를 냅니다). 반드시 구현 하나를 같이 넣어야 합니다. 반대로 Timber 는 안드로이드 Log 가 이미 있으니 그 자체로 동작합니다.

안드로이드 라이브러리에 Timber 를 넣지 마세요 — Timber 는 앱이 Timber.plant() 를 해 줘야 동작합니다. 라이브러리가 심지 않은 상태에서 Timber.d() 를 부르면 조용히 아무 일도 일어나지 않습니다. 라이브러리는 android.util.Log 를 직접 쓰거나 로그 인터페이스를 주입받으세요.

안드로이드 — Application 에서 한 번

dependencies {
    implementation("com.jakewharton.timber:timber:5.0.1")
}
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        if (BuildConfig.DEBUG) {
            Timber.plant(Timber.DebugTree())      // 디버그 빌드만 ★
        } else {
            Timber.plant(CrashReportingTree())    // 릴리스는 WARN 이상만
        }
    }
}
// 릴리스에서 DebugTree 를 안 심으면
// Timber.d(...) 호출은 '나무가 없어' 그냥 반환합니다.
// 문자열은 이미 만들어졌다는 점만 기억하세요 (LOG 09).
정리 — 여섯 개를 외울 필요는 없습니다. 무대를 먼저 정하세요. 서버면 kotlin-logging + Logback, 안드로이드면 Timber, 둘 다 공유하는 KMP 면 Kermit. 그리고 구현은 실행되는 모듈에서 딱 하나만 고릅니다 — 이 규칙 하나로 다음 섹션의 사고 대부분이 예방됩니다.
