LOG 04

SLF4J 파사드 — 로그가 안 나오거나 두 번 나오는 이유

“로그가 하나도 안 나옵니다”와 “로그가 두 줄씩 나옵니다”는 코틀린 서버에서 가장 흔한 두 가지 사고이고, 원인은 거의 항상 같습니다 — 의존성 트리에 구현이 없거나 둘 이상입니다. 이걸 이해하려면 SLF4J 의 세 층(파사드 · 바인딩 · 브리지)을 구분할 줄 알아야 합니다.

기억할 규칙 하나 — 파사드는 여러 개여도 되고, 바인딩은 정확히 하나여야 합니다.

증상으로 원인 찾기

보이는 증상원인
아무것도 안 나옴 + No SLF4J providers were found바인딩 0개
multiple SLF4J providers바인딩 2개 이상
같은 줄이 두 번 찍힘appender 중복 · additivity

내 logback.xml 이 무시됨다른 바인딩이 이김

이름이 비슷해서 헷갈리는 짝 ★

아티팩트방향
log4j-over-slf4jLog4j 1.x → SLF4J
log4j-to-slf4jLog4j 2.x API → SLF4J
log4j-slf4j2-implSLF4J → Log4j2 (바인딩)
slf4j-log4j12SLF4J → Log4j 1.x (폐기)
jcl-over-slf4jcommons-logging → SLF4J
jcl-to-slf4j이런 건 없습니다
절대 같이 넣으면 안 되는 조합 — log4j-to-slf4j(Log4j2 API 를 SLF4J 로) 와 log4j-slf4j2-impl(SLF4J 를 Log4j2 로) 를 함께 넣으면 서로를 부르며 무한 루프에 빠져 StackOverflowError 로 부팅이 죽습니다. Spring Boot 기본은 앞의 것, Log4j2 스타터는 뒤의 것을 씁니다 — 스타터를 갈아 끼울 때 앞의 것을 빼는 것이 spring-boot-starter-logging exclude 의 진짜 이유입니다.

val forbidden = listOf(
    "slf4j-simple", "slf4j-log4j12", "slf4j-jdk14", "slf4j-jcl"
)

tasks.register("checkLoggingDeps") {
    val rt = configurations.named("runtimeClasspath")
    doLast {
        val names = rt.get().resolvedConfiguration
            .resolvedArtifacts.map { it.name }
        val hits = names.filter { it in forbidden }
        val bindings = names.count {
            it == "logback-classic" || it == "log4j-slf4j2-impl"
        }
        check(hits.isEmpty()) { "금지된 SLF4J 바인딩: $hits" }
        check(bindings == 1) { "SLF4J 바인딩이 ${bindings}개입니다" }
    }
}
tasks.named("check") { dependsOn("checkLoggingDeps") }

LOG 05

Logback 설정 — 언제 자르고 언제 지우나

Logback 설정 파일은 처음 보면 어렵지만 사실 세 가지만 정하면 끝납니다 — 무엇을 적을지(encoder) · 어디에 쌓을지(appender) · 언제 자르고 지울지(rollingPolicy). 나머지는 전부 이 셋의 변주입니다. 그리고 디스크가 꽉 차서 서비스가 죽는 사고는 거의 항상 마지막 하나를 안 걸어서 납니다.

원통이 파일입니다 — 지금 쓰는 것은 하나, 나머지는 압축되어 밀려나고 결국 지워집니다.

복사해서 쓰는 logback-spring.xml

<!-- src/main/resources/logback-spring.xml
     ★ 파일 이름이 -spring 이어야 <springProfile> 이 동작합니다 -->
<configuration scan="false">
  <property name="LOG_DIR" value="${LOG_DIR:-./logs}"/>

  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} %X{callId} - %msg%n</pattern>
    </encoder>
  </appender>

  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>${LOG_DIR}/app.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>${LOG_DIR}/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>100MB</maxFileSize>     <!-- 이만큼 차면 자름 -->
      <maxHistory>30</maxHistory>          <!-- 30일 치만 -->
      <totalSizeCap>5GB</totalSizeCap>     <!-- ★ 이게 진짜 안전장치 -->
    </rollingPolicy>
    <encoder>
      <pattern>%d{ISO8601} %-5level [%X{callId}] %logger{40} - %msg%n</pattern>
    </encoder>
  </appender>

  <springProfile name="local">
    <root level="DEBUG"><appender-ref ref="CONSOLE"/></root>
  </springProfile>
  <springProfile name="prod">
    <root level="INFO"><appender-ref ref="FILE"/></root>
  </springProfile>
</configuration>

세 가지 설정이 각각 무엇을 막나

설정없으면 생기는 일
maxFileSize파일 하나가 수십 GB가 되어 열리지 않음
maxHistory파일이 영원히 쌓임
totalSizeCap트래픽이 튀는 날 디스크 full
.gz 확장자압축이 안 되어 용량 수 배
cleanHistoryOnStart재시작 잦은 배치에서 잔여물
maxHistory 만 걸면 안전하지 않습니다 — 30일을 남기라고 했는데 하루에 200GB 가 쌓이면 그대로 디스크가 찹니다. totalSizeCap 이 진짜 안전장치입니다. 컨테이너라면 여기에 볼륨 크기의 70% 정도를 넣으세요.
컨테이너에서는 파일을 안 쓰는 편이 낫습니다 — 표준 출력으로만 찍고 수집은 플랫폼(도커 로그 드라이버 · Fluent Bit · Loki)에 맡깁니다. 그러면 위 설정이 전부 필요 없어지고, 대신 JSON 인코더가 중요해집니다.

한 단계 더 — 비동기 appender 와 그 대가 🧬 전문가

AsyncAppender — 기본값이 위험합니다

<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
  <appender-ref ref="FILE"/>

  <!-- 기본값 256. 트래픽이 있으면 너무 작습니다 -->
  <queueSize>8192</queueSize>

  <!-- ★★ 기본값 20 = 큐가 80% 차면 INFO 이하를 조용히 버립니다 -->
  <discardingThreshold>0</discardingThreshold>

  <!-- 큐가 꽉 차면? false=블로킹(느려짐) true=버림(로그 손실) -->
  <neverBlock>false</neverBlock>

  <!-- 종료할 때 남은 큐를 비울 시간 -->
  <maxFlushTime>3000</maxFlushTime>
</appender>
“장애 때 로그가 없다”의 범인 — discardingThreshold 기본값입니다. 부하가 몰려 큐가 차면 바로 그 순간의 INFO 로그를 버립니다. 정작 필요한 시점의 로그가 사라지는 셈이라, 0 으로 두고 큐 크기로 조절하는 편이 낫습니다.

가상 스레드 · 코루틴 환경에서

Java 21+ 의 가상 스레드에서 로깅이 문제가 되는 이유

  Logback 의 오래된 버전은 appender 안에서 synchronized 를 썼습니다.
  가상 스레드가 synchronized 블록에서 막히면 캐리어 스레드까지
  함께 묶입니다(pinning). 로그 한 줄 때문에 처리량이 무너집니다.

  → Logback 1.5.x 는 내부 잠금을 ReentrantLock 으로 바꿨습니다.
    가상 스레드를 쓴다면 반드시 1.5 이상으로 올리세요.

  → 코루틴은 캐리어 개념이 없어 pinning 은 없지만,
    로그 I/O 가 Dispatchers.Default 스레드를 붙잡는 것은 같습니다.
    파일/네트워크 appender 는 비동기로 빼는 편이 안전합니다.

확인 방법
  java -Djdk.tracePinnedThreads=full -jar app.jar
  #  가상 스레드가 핀된 지점의 스택이 찍힙니다.
  #  거기에 ch.qos.logback 이 보이면 버전부터 올리세요.
정리 — Logback 설정은 encoder · appender · rollingPolicy 셋입니다. totalSizeCap 을 반드시 걸고, 인스턴스가 여러 대면 JSON 으로 바꾸고, AsyncAppender 를 쓴다면 discardingThreshold 를 0 으로 두세요. 컨테이너라면 표준 출력에만 찍고 수집은 플랫폼에 맡기는 것이 가장 단순합니다.
LOG 06

코루틴과 MDC — 요청 ID 가 사라지는 진짜 이유

MDC(Mapped Diagnostic Context)는 “이 요청에 붙는 꼬리표”를 담는 곳입니다. 문제는 MDC 가 ThreadLocal 로 만들어져 있다는 점입니다. 코루틴은 스레드를 옮겨 다니는 것이 존재 이유이므로, 아무 조치 없이 쓰면 launch 하나 넘어가는 순간 요청 ID 가 증발합니다.

고치는 방법은 한 줄입니다 — MDCContext() 를 코루틴 문맥에 얹기.

문제와 해법을 나란히

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-slf4j:1.10.2")
}
import kotlinx.coroutines.slf4j.MDCContext
import org.slf4j.MDC

// ❌ 사라집니다
suspend fun handleBad(id: Long) {
    MDC.put("callId", newId())
    log.info { "시작" }                 // callId 있음
    withContext(Dispatchers.IO) {
        log.info { "DB 조회" }          // callId 없음 ★
    }
}

// ✅ 이어집니다
suspend fun handleGood(id: Long) = withContext(MDCContext()) {
    log.info { "시작" }
    withContext(Dispatchers.IO) {
        log.info { "DB 조회" }          // callId 살아 있음
    }
}

// ✅ 문맥을 새로 만들면서 값을 넣기
suspend fun handleWith(id: Long) =
    withContext(MDCContext(mapOf("callId" to newId(), "orderId" to "$id"))) {
        log.info { "주문 처리" }
    }
MDCContext() 가 하는 일 — 만들어지는 그 순간의 MDC 맵을 복사해 두었다가, 코루틴이 어느 스레드에 올라갈 때마다 그 스레드의 MDC 에 넣고 · 끝나면 되돌립니다. ThreadContextElement 인터페이스의 구현체이고, 같은 방식으로 보안 컨텍스트나 트랜잭션 컨텍스트도 전파할 수 있습니다.

놓치기 쉬운 다섯 자리 ★

자리결과
launch/async 시작문맥 없으면 잃음
withContext(IO)부모 문맥은 상속됨
MDCContext 뒤에 MDC.put자식에 안 보임
GlobalScope.launch전부 잃음
콜백 · CompletableFuture전부 잃음
Flow 의 flowOn업스트림에서 잃음
// ⚠ 순서 함정 — 이건 안 됩니다
withContext(MDCContext()) {          // 이 시점의 MDC 를 스냅샷
    MDC.put("step", "2")             // 스냅샷 이후라 자식은 못 봄
    launch { log.info { "..." } }    // step 없음
}

// ✅ 값을 넣고 나서 문맥을 만듭니다
MDC.put("step", "2")
withContext(MDCContext()) {
    launch { log.info { "..." } }    // step 있음
}

// ✅ 또는 맵으로 직접 주기 (가장 명확합니다)
withContext(MDCContext(MDC.getCopyOfContextMap().orEmpty() + ("step" to "2"))) {
    launch { log.info { "..." } }
}

Spring WebFlux · 코루틴 컨트롤러

// 필터에서 한 번 심고, 컨트롤러는 아무것도 몰라도 됩니다
@Component
class CallIdFilter : WebFilter {
    override fun filter(ex: ServerWebExchange, chain: WebFilterChain): Mono<Void> {
        val id = ex.request.headers.getFirst("X-Request-Id")
            ?: UUID.randomUUID().toString().take(8)
        return chain.filter(ex)
            .contextWrite { it.put("callId", id) }      // Reactor 컨텍스트
    }
}

// 코루틴 컨트롤러에서 받아 MDC 로 옮기기
@GetMapping("/orders/{id}")
suspend fun get(@PathVariable id: Long): OrderDto {
    val callId = currentCoroutineContext()[ReactorContext]
        ?.context?.getOrDefault("callId", "-") ?: "-"
    return withContext(MDCContext(mapOf("callId" to callId))) {
        log.info { "조회 $id" }
        service.find(id)
    }
}
WebFlux 는 두 겹입니다 — Reactor 의 Context 와 MDC 를 둘 다 다뤄야 합니다. 서블릿 기반 MVC 라면 OncePerRequestFilter 에서 MDC.put 만 하면 되므로 훨씬 단순합니다. 이 복잡도가 WebFlux 를 고를 때 계산에 넣어야 할 비용입니다.

서블릿 MVC — 이쪽이 훨씬 쉽습니다

@Component
class MdcFilter : OncePerRequestFilter() {
    override fun doFilterInternal(
        req: HttpServletRequest,
        res: HttpServletResponse,
        chain: FilterChain,
    ) {
        val id = req.getHeader("X-Request-Id")
            ?: UUID.randomUUID().toString().take(8)
        MDC.put("callId", id)
        MDC.put("path", req.requestURI)
        res.setHeader("X-Request-Id", id)      // 응답에도 돌려주기 ★
        try {
            chain.doFilter(req, res)
        } finally {
            MDC.clear()                        // ★ 반드시. 스레드 풀이라 남습니다
        }
    }
}
MDC.clear() 를 finally 에 넣지 않으면 — 톰캣 스레드가 재사용되면서 다음 사용자의 로그에 앞 사람의 ID가 붙습니다. 조사할 때 완전히 잘못된 결론으로 이어지므로, 이건 버그가 아니라 사고로 취급하세요.

한 단계 더 — 직접 ThreadContextElement 만들기 🧬 전문가

MDCContext 가 실제로 하는 일

// 개념적으로는 이 정도입니다 (실제 구현은 라이브러리를 보세요)
class MyMdcContext(
    private val snapshot: Map<String, String>? = MDC.getCopyOfContextMap(),
) : ThreadContextElement<Map<String, String>?>,
    AbstractCoroutineContextElement(Key) {

    companion object Key : CoroutineContext.Key<MyMdcContext>

    // 코루틴이 이 스레드에 올라갈 때
    override fun updateThreadContext(context: CoroutineContext): Map<String, String>? {
        val old = MDC.getCopyOfContextMap()
        if (snapshot == null) MDC.clear() else MDC.setContextMap(snapshot)
        return old
    }

    // 코루틴이 이 스레드에서 내려올 때
    override fun restoreThreadContext(
        context: CoroutineContext,
        oldState: Map<String, String>?,
    ) {
        if (oldState == null) MDC.clear() else MDC.setContextMap(oldState)
    }
}

비용과 대안

MDCContext 의 비용

  · 디스패치할 때마다 맵을 두 번 바꿔 끼웁니다.
  · 코루틴 하나가 수천 번 중단/재개하면 그만큼 반복됩니다.
  · 값이 3~4개면 무시할 수준이지만,
    수십 개를 넣어 두면 눈에 띄기 시작합니다.

줄이는 법
  ① MDC 에는 '검색 키'만 넣습니다 (callId, userId, tenantId)
     — 본문 데이터는 로그 메시지나 구조화 필드로.
  ② 뜨거운 루프 안에서 코루틴을 만들지 않습니다.
  ③ 정말 많은 값이 필요하면 CoroutineContext 에 직접 담고
     로그를 찍는 지점에서만 MDC 로 옮깁니다.

대안 — OpenTelemetry
  분산 추적을 이미 쓴다면 traceId/spanId 가 자동으로 MDC 에 들어옵니다.
  (logging.pattern 에 %mdc{trace_id} 를 넣기만 하면 됩니다)
  요청 ID 를 직접 만들기 전에 이미 있는지부터 확인하세요.
정리 — MDC 는 스레드에 붙는 꼬리표라서 코루틴에서는 그냥 두면 끊깁니다. kotlinx-coroutines-slf4j 의 MDCContext() 를 코루틴 문맥에 얹으면 이어지고, 서블릿 기반이면 필터에서 MDC.put + finally { MDC.clear() } 로 끝납니다. MDC 에는 검색에 쓸 키만 넣으세요.
