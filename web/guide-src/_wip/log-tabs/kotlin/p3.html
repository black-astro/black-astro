LOG 07

Ktor 3 — CallId 와 CallLogging 두 플러그인으로 요청 한 줄을 남깁니다

Ktor 는 스프링처럼 “요청 로그가 그냥 나오는” 프레임워크가 아닙니다. 아무것도 안 하면 요청이 들어와도 한 줄도 남지 않습니다. 대신 두 플러그인이 있습니다 — 요청마다 ID 를 붙이는 CallId와 요청당 한 줄을 적는 CallLogging. 둘을 순서대로 심으면 앞 섹션의 MDC 문제까지 프레임워크가 대신 풀어 줍니다.

Ktor 의 요청 로그는 CallId → CallLogging 순서로 심는 두 플러그인이 만듭니다 — 셰브론은 되돌아가지 않습니다.

복사해서 쓰는 설치 코드 (Ktor 3.x)

// build.gradle.kts — 2026년 8월 기준 Ktor 3.x 계열
dependencies {
    implementation("io.ktor:ktor-server-core")
    implementation("io.ktor:ktor-server-call-id")       // 요청 ID
    implementation("io.ktor:ktor-server-call-logging")  // 요청 한 줄
    implementation("io.github.oshai:kotlin-logging-jvm:7.0.7")
    runtimeOnly("ch.qos.logback:logback-classic:1.5.18") // ★ 없으면 침묵
}
import io.ktor.server.plugins.callid.*
import io.ktor.server.plugins.calllogging.*   // Ktor 3 에서 패키지가 바뀌었습니다
import org.slf4j.event.Level

fun Application.module() {
    // ① 먼저 CallId
    install(CallId) {
        retrieveFromHeader("X-Request-Id")             // 게이트웨이가 준 값 우선
        generate { UUID.randomUUID().toString().take(8) }
        verify { it.isNotBlank() && it.length <= 64 }  // 이상한 값은 버리고 새로 생성
        replyToHeader("X-Request-Id")                  // 응답에도 돌려줍니다
    }
    // ② 그 다음 CallLogging
    install(CallLogging) {
        level = Level.INFO
        callIdMdc("callId")                            // MDC 키 이름 ★
        filter { call -> !call.request.path().startsWith("/health") }
        format { call ->
            val status = call.response.status()?.value ?: "-"
            val ms = call.processingTimeMillis()
            "$status ${call.request.httpMethod.value} ${call.request.path()} ${ms}ms"
        }
    }
    routing { get("/orders/{id}") { /* ... */ } }
}

각 설정이 막아 주는 사고

설정없으면
retrieveFromHeader게이트웨이·프런트가 준 ID 와 끊김
verify클라이언트가 보낸 아무 문자열이 로그에 박힘
replyToHeader고객이 “이 오류 봐 주세요” 할 때 찾을 키가 없음
callIdMdc내 log.info 줄에 ID 가 안 붙음
filter헬스체크가 초당 수십 줄을 채움
format기본 문구는 사람용 — 파싱하려면 직접 정함
MDC 문제를 Ktor 가 대신 풉니다 — callIdMdc 나 mdc { } 를 하나라도 쓰면 CallLogging 이 요청 처리를 MDCContext 로 감싸서 실행합니다. 그래서 핸들러 안에서 withContext(Dispatchers.IO) 로 넘어가도 callId 가 따라옵니다. 단, 직접 launch 한 백그라운드 작업은 여전히 LOG 06 의 규칙대로 MDCContext() 를 얹어야 합니다.
Ktor 2 → 3 에서 바뀐 것 — CallLogging 의 import 가 io.ktor.server.plugins.callloging(오타 그대로)에서 io.ktor.server.plugins.calllogging 으로 고쳐졌습니다. 옛 블로그 코드를 붙여 넣으면 import 한 줄 때문에 컴파일이 깨집니다.

이렇게도 쓸 수 있다 — MDC 에 요청 정보 더 얹기 🟡 중급

사용자 · 경로 · 테넌트를 모든 줄에

install(CallLogging) {
    callIdMdc("callId")
    // 요청에서 값을 꺼내 MDC 키로 — 검색 키만 넣습니다 (LOG 06)
    mdc("path")   { call -> call.request.path() }
    mdc("method") { call -> call.request.httpMethod.value }
    mdc("tenant") { call -> call.request.header("X-Tenant") }
    // 인증 뒤에 정해지는 값은 여기서 못 읽습니다 — 아래 참고
    mdc("userId") { call -> call.principal<UserIdPrincipal>()?.name }
}
<!-- logback.xml — 붙인 키를 패턴에서 꺼내 씁니다 -->
<pattern>%d{HH:mm:ss.SSS} %-5level [%X{callId}] [%X{tenant}] %logger{30} - %msg%n</pattern>

<!-- Ktor 가 내는 소음을 줄이는 로거 이름들 -->
<logger name="io.netty" level="INFO"/>
<logger name="io.ktor.server.engine" level="INFO"/>
<logger name="Exposed" level="WARN"/>   <!-- Exposed 를 쓴다면 SQL 로그 이름 -->
<root level="INFO"><appender-ref ref="CONSOLE"/></root>

언제 값을 읽느냐가 함정입니다

mdc { } 람다가 실행되는 시점

  CallLogging 이 MDC 를 준비하는 때는 요청 처리의 앞쪽입니다.
  그 시점에 아직 없는 값(인증 결과 · 라우트 파라미터)은 null 이 됩니다.

  값이 잡히느냐는 Authentication 플러그인과의 설치 순서에 달려 있고,
  버전마다 미묘하게 달랐습니다.
  → 확신이 없으면 로그 한 줄을 찍어 보는 것이 가장 빠릅니다.

확실한 방법 — 핸들러 안에서 직접 얹기
  get("/me") {
      val user = call.principal<UserIdPrincipal>()!!.name
      withContext(MDCContext(MDC.getCopyOfContextMap().orEmpty() + ("userId" to user))) {
          log.info { "프로필 조회" }     // userId 붙음
          call.respond(service.me(user))
      }
  }
MDC 에 개인정보를 넣지 마세요 — MDC 값은 그 요청의 모든 줄에 복제됩니다. 이메일이나 전화번호를 넣으면 로그 한 줄이 아니라 요청 하나당 수십 줄에 새어 나갑니다. userId 같은 불투명한 키만 넣습니다 (LOG 11).

실무에선 이렇게 — 예외는 한 번만 · 테스트에서 확인 🔴 실무

StatusPages 와 겹치면 두 번 찍힙니다

install(StatusPages) {
    exception<Throwable> { call, cause ->
        // ✅ 여기서 '한 번만' 스택을 남깁니다
        log.error(cause) { "처리 실패 ${call.request.path()}" }
        call.respond(HttpStatusCode.InternalServerError, ErrorBody("internal"))
    }
    exception<NotFoundException> { call, _ ->
        // ❌ 404 마다 스택을 찍지 마세요 — 로그가 아니라 소음입니다
        call.respond(HttpStatusCode.NotFound)
    }
}
// CallLogging 은 status 코드만 한 줄 적습니다.
// 핸들러 안에서 catch 해서 log.error 하고 다시 throw 하면
//   → 핸들러 1번 + StatusPages 1번 = 같은 스택이 두 번.
//   규칙: 로그는 '예외를 최종 처리하는 자리'에서만.

testApplication 으로 헤더와 로그 확인

@Test
fun `요청 ID 가 응답 헤더로 돌아온다`() = testApplication {
    application { module() }
    val res = client.get("/orders/42") {
        header("X-Request-Id", "test-7f3a")
    }
    assertEquals("test-7f3a", res.headers["X-Request-Id"])
}

@Test
fun `이상한 요청 ID 는 새로 만든다`() = testApplication {
    application { module() }
    val res = client.get("/orders/42") {
        header("X-Request-Id", "a".repeat(500))   // verify 에서 탈락
    }
    val id = res.headers["X-Request-Id"]!!
    assertEquals(8, id.length)
}
로그 내용까지 검증하려면 — Logback 의 ListAppender 를 테스트에서 ktor.application 로거에 붙이고 list 를 검사합니다(LOG 11 에 예제). 요청 로그 형식은 파싱 규칙과 짝이므로, 형식을 바꾸는 순간 수집기 설정도 같이 바꿔야 합니다.
정리 — Ktor 는 CallId → CallLogging 순서로 두 플러그인을 심어야 요청 로그가 생깁니다. callIdMdc("callId") 한 줄이 요청 ID 를 MDC 에 넣고 코루틴 너머까지 이어 주며, filter 로 헬스체크를 빼고, 예외 로그는 StatusPages 한 곳에서만 남깁니다.
LOG 08

Spring Boot + Kotlin — application.yml 여덟 줄이 로깅의 대부분입니다

스프링 부트는 Logback 을 이미 올바르게 깔아 둔 상태로 시작합니다. 여러분이 XML 을 열 일은 생각보다 적고, 대부분은 application.yml 의 logging.* 몇 줄로 끝납니다. 코틀린이라면 여기에 kotlin-logging 한 줄만 더하고, Lombok 의 @Slf4j 는 잊어도 됩니다.

스프링 부트의 로깅은 XML 이 아니라 yml 여덟 줄로 대부분 끝납니다 — XML 은 appender 를 새로 만들 때만 엽니다.

시작 — 의존성 한 줄과 로거 선언

// build.gradle.kts — Boot 3.x / 4.x 공통
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    // ↑ 이 안에 spring-boot-starter-logging = Logback + SLF4J + 브리지 3종
    implementation("io.github.oshai:kotlin-logging-jvm:7.0.7")   // ★ 이것만 추가
    // ❌ logback-classic 을 다시 적지 마세요 — 버전만 어긋납니다
}
// 코틀린에는 Lombok @Slf4j 가 없습니다 — 필요도 없습니다
private val log = KotlinLogging.logger {}

@Service
class OrderService(private val repo: OrderRepository) {
    @Transactional
    fun place(cmd: PlaceOrder): Order {
        log.info { "주문 접수 sku=${cmd.sku} qty=${cmd.qty}" }
        return repo.save(Order.from(cmd)).also {
            log.debug { "저장 완료 id=${it.id}" }
        }
    }
}

application.yml 에 두는 것 · XML 에 두는 것

하고 싶은 것어디에
패키지별 레벨yml logging.level.*
콘솔 패턴 바꾸기yml logging.pattern.console
파일 + 롤링 기본형yml logging.file.name + rollingpolicy.*
JSON 출력yml logging.structured.format.* (3.4+)
AUDIT 전용 appenderXML logback-spring.xml
AsyncAppender · 필터XML
프로파일별 분기XML <springProfile> 또는 yml 프로파일 문서
XML 을 만드는 순간 yml 의 logging.file.* · rollingpolicy.* 는 무시됩니다 — 부트의 기본 설정을 통째로 대체하기 때문입니다. 레벨(logging.level)만 살아남습니다. XML 에서 부트 기본 조각을 재사용하려면 <include resource="org/springframework/boot/logging/logback/defaults.xml"/> 를 맨 위에 넣으세요.

이렇게도 쓸 수 있다 — 재시작 없이 레벨 바꾸기 · 추적 ID 붙이기 🟡 중급

Actuator loggers — 장애 중에 DEBUG 켜기

# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,loggers   # ★ loggers 노출
  # 운영에서는 반드시 인증 뒤에 두세요 — 레벨 변경은 곧 DoS 수단입니다
# 지금 어떤 레벨인지
curl -s localhost:8080/actuator/loggers/com.example.order
# {"configuredLevel":null,"effectiveLevel":"INFO"}

# 장애 조사 중 — 그 패키지만 DEBUG 로 (재시작 없음)
curl -X POST localhost:8080/actuator/loggers/com.example.order \
  -H 'Content-Type: application/json' \
  -d '{"configuredLevel":"DEBUG"}'

# 끝나면 되돌리기 — null 이면 부모 레벨을 따릅니다
curl -X POST localhost:8080/actuator/loggers/com.example.order \
  -H 'Content-Type: application/json' -d '{"configuredLevel":null}'
# 인스턴스가 여러 대면 각 인스턴스에 따로 보내야 합니다.

실무에선 이렇게 — SQL 로그와 테스트 🔴 실무

JPA SQL 은 show-sql 이 아니라 로거로

# ❌ spring.jpa.show-sql: true
#    → System.out 으로 찍혀 레벨·패턴·파일 전부 무시됩니다

# ✅ 로거로 — 로컬 프로파일에만
spring:
  config:
    activate:
      on-profile: local
logging:
  level:
    org.hibernate.SQL: DEBUG                 # 실행되는 SQL
    org.hibernate.orm.jdbc.bind: TRACE       # 바인딩 값 (Hibernate 6+)
    org.springframework.jdbc.core: DEBUG     # JdbcTemplate 을 쓴다면
    org.springframework.transaction: DEBUG   # 트랜잭션 경계 확인
jdbc.bind: TRACE 는 운영에서 절대 켜지 마세요 — 바인딩 값에 이메일 · 비밀번호 해시 · 카드번호가 그대로 찍힙니다. “운영에서 잠깐만” 켠 TRACE 가 수집기까지 흘러가 개인정보 사고가 됩니다(LOG 11).

테스트에서 로그 검증 — OutputCaptureExtension

import org.springframework.boot.test.system.CapturedOutput
import org.springframework.boot.test.system.OutputCaptureExtension

@ExtendWith(OutputCaptureExtension::class)
@SpringBootTest
class OrderServiceLogTest(@Autowired val service: OrderService) {

    @Test
    fun `주문 접수 로그에 sku 가 남는다`(output: CapturedOutput) {
        service.place(PlaceOrder(sku = "A-1", qty = 2))
        assertThat(output.out).contains("주문 접수 sku=A-1")
    }

    @Test
    fun `로그에 카드번호가 없다`(output: CapturedOutput) {
        service.pay(card = "4111111111111111")
        assertThat(output.all).doesNotContainPattern("\\d{16}")
    }
}
로그 문구를 테스트로 고정할 것인가 — 대개는 아니오입니다. 문구는 자주 바뀌고 테스트가 깨지기만 합니다. 예외는 둘 — 수집기가 파싱하는 형식과 개인정보가 없다는 부정 검증. 이 둘만 테스트로 잠급니다.
정리 — 스프링 부트는 Logback 이 이미 들어 있으니 kotlin-logging 한 줄만 더합니다. 레벨·파일·JSON 은 application.yml 의 logging.* 로, appender 를 새로 만들 때만 logback-spring.xml 을 엽니다. Actuator loggers 로 재시작 없이 레벨을 바꾸고, SQL 은 show-sql 대신 로거로 켜세요.
