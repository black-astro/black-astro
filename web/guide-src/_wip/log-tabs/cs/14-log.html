LOG 01

로그란 무엇인가 — 추가만 되는 순서 있는 기록

우리가 매일 보는 app.log 텍스트 파일 이야기가 아닙니다. append-only ordered sequence 라는 자료구조 이야기입니다. 연산이 두 개밖에 없는데, 이 두 개로 데이터베이스와 분산 합의가 만들어집니다.

로그의 연산은 append 와 read(from offset) 둘뿐입니다 — 이 제약이 곧 힘입니다.

50줄로 만드는 로그

class Log:
    """append-only ordered sequence — 연산은 두 개뿐입니다."""
    def __init__(self):
        self._items = []            # 실제로는 디스크의 세그먼트 파일

    def append(self, record) -> int:
        self._items.append(record)  # ★ 끝에만 붙습니다
        return len(self._items) - 1 # 붙은 자리 = 오프셋(불변 식별자)

    def read(self, offset: int, limit: int = 100):
        return self._items[offset:offset + limit]

    def __len__(self):
        return len(self._items)

# 쓰기
log = Log()
log.append({"t": "deposit", "amt": 10_000})   # -> 0
log.append({"t": "withdraw", "amt": 3_000})   # -> 1

# 읽기 — 커서는 소비자가 들고 있습니다
cursor = 0
while cursor < len(log):
    for rec in log.read(cursor, 10):
        handle(rec)
        cursor += 1
없는 연산에 주목하세요 — update(i, x) 도 delete(i) 도 insert(i, x) 도 없습니다. 이 세 개를 포기했기 때문에 동시에 읽는 사람이 몇 명이든 락이 필요 없고, 어제 읽은 오프셋 3이 오늘도 같은 값입니다.

정리 — 로그는 append 와 read(offset) 두 연산만 가진 순서 있는 불변 기록입니다. 수정과 삭제를 포기한 대가로 순차 쓰기 · 락 없는 다중 독자 · 과거 재생 · 안정된 식별자를 얻습니다. 파일시스템 저널부터 Kafka 까지가 전부 같은 자료구조입니다.
LOG 02

상태와 이벤트의 이중성 — 접기와 미분

“잔액 7,000원”과 “입금 10,000 · 출금 3,000”은 같은 사실의 두 표현입니다. 상태는 이벤트를 접은 것(fold)이고, 이벤트는 상태의 차이(미분)입니다. 이 대응이 이 탭 전체의 뼈대입니다.

상태는 이벤트의 접기, 이벤트는 상태의 미분 — 어느 쪽이 원본인지가 설계를 가릅니다.

fold 를 코드로

from functools import reduce

def apply(state, ev):
    """상태 하나 + 이벤트 하나 -> 다음 상태. 순수 함수여야 합니다."""
    t = ev["t"]
    if t == "deposit":  return {**state, "bal": state["bal"] + ev["amt"]}
    if t == "withdraw": return {**state, "bal": state["bal"] - ev["amt"]}
    if t == "freeze":   return {**state, "frozen": True}
    return state                       # 모르는 이벤트는 무시(전방 호환)

initial = {"bal": 0, "frozen": False}
events  = log.read(0, 10_000)

state = reduce(apply, events, initial)   # ★ state = fold(apply, initial, events)

# 어제 자정의 잔액이 궁금하다면? 그때까지만 접으면 됩니다
as_of = [e for e in events if e["ts"] < midnight]
yesterday = reduce(apply, as_of, initial)
apply 가 순수 함수여야 하는 이유 — 재생할 때 같은 결과가 나와야 하기 때문입니다. apply 안에서 현재 시각을 읽거나 · 난수를 뽑거나 · 외부 API 를 부르면 재생한 결과가 원래와 달라집니다. 그런 값은 이벤트에 미리 박아 두는 것이 정석입니다 ({"t":"charge","amt":100,"rate":1180.5,"at":"..."}).

두 설계의 대칭 — 무엇을 원본으로 둘 것인가

상태를 원본으로 (보통의 CRUD)
UPDATE account
   SET balance = balance - 3000
 WHERE id = 7;
-- 이전 값은 그 자리에서 사라집니다
-- "왜 3,000이 빠졌나"는 어디에도 없습니다
이벤트를 원본으로 (이벤트 소싱)
INSERT INTO events(stream, seq, type, data)
VALUES ('acct-7', 12, 'withdraw',
        '{"amt":3000,"atm":"KR-118"}');
-- 잔액은 이 로그를 접어서 만듭니다
-- 과거 어느 시점이든 되살릴 수 있습니다
CRUD 가 나쁘다는 이야기가 아닙니다. CRUD 는 “지금 값만 알면 되는” 도메인에 정확히 맞습니다. 문제는 나중에 “이 값이 왜 이렇게 됐지?”를 물어야 할 때인데, 그때는 이미 정보가 없습니다. 버리는 결정은 되돌릴 수 없습니다.

실무에선 이렇게 — 스냅샷 없이는 못 삽니다 🔴 실무

접는 비용은 이벤트 수에 비례합니다

# 이벤트가 500만 개인 스트림을 매번 처음부터 접으면?
#   -> 조회 한 번에 수 초. 서비스가 못 버팁니다.

# ★ 스냅샷: "여기까지 접은 결과"를 주기적으로 저장
def load(stream_id):
    snap = snapshots.latest(stream_id)          # {seq: 4_900_000, state: {...}}
    state = snap.state if snap else initial
    start = snap.seq + 1 if snap else 0
    for ev in log.read_stream(stream_id, start): # 나머지만 접습니다
        state = apply(state, ev)
    return state

def save_snapshot(stream_id, state, seq):
    snapshots.put(stream_id, seq, state, schema_version=3)

# 규칙
#  · 스냅샷은 캐시입니다 — 지워도 로그에서 다시 만들 수 있어야 합니다
#  · apply 로직이 바뀌면 스냅샷을 전부 버리고 다시 만듭니다 ★
#  · 그래서 스냅샷에 schema_version 을 반드시 넣습니다

재생이 진짜로 어려운 지점

① 외부 부수효과
   재생 중에 다시 메일이 나가면 안 됩니다.
   -> apply 는 상태만 바꾸고, 부수효과는 별도 단계로 분리
      (읽기 모델 갱신 / 알림 발송은 '핸들러', apply 아님)

② 코드가 바뀐다
   1년 전 이벤트를 오늘 코드로 접으면 다른 값이 나올 수 있습니다.
   -> 이벤트에 version 을 넣고 apply 를 버전별로 분기
   -> 또는 업캐스터(upcaster)로 옛 이벤트를 새 형태로 승격

③ 시간·환율·세율 같은 외부 값
   -> 계산에 쓴 값을 이벤트에 함께 기록 (재현 가능성 확보)

④ 삭제 요구(GDPR 잊힐 권리)와 append-only 의 충돌
   -> 개인정보를 로그 밖 금고에 두고 로그에는 키만
      (crypto-shredding: 키를 지우면 사실상 복원 불가)
이벤트 소싱을 접는 팀이 가장 많이 걸리는 곳이 ②와 ④입니다. “로그는 영원하다”와 “법적으로 지워야 한다”가 정면으로 부딪힙니다. 🔐 보안 · 암호 탭의 키 관리가 여기서 실무 해법이 됩니다.
정리 — state = fold(apply, initial, events) 한 줄이 이 절의 전부입니다. 상태는 이벤트를 접은 결과이므로 언제든 다시 만들 수 있고, 이벤트는 상태의 차이이므로 상태만 남기면 이유가 사라집니다. 무엇을 원본으로 둘지가 시스템의 성격을 정합니다.
LOG 03

WAL 과 원자성 — 데이터보다 로그를 먼저 씁니다

“다 되거나 다 안 되거나”는 어떻게 만들까요. 답은 놀랄 만큼 단순합니다 — 진짜 데이터를 고치기 전에, 무엇을 고칠지를 로그에 먼저 적습니다. Write-Ahead Logging, 줄여서 WAL 입니다.

WAL 의 계약은 한 줄 — 로그가 페이지보다 먼저 디스크에 닿는다. 나머지는 이것의 결과입니다.

왜 이 순서가 크래시에서 살아남게 하나

크래시가 날 수 있는 지점은 세 곳입니다.

  ① 로그도 못 쓰고 죽었다
       → 아무 일도 없었던 것과 같습니다. 정상.

  ② 로그는 썼는데 페이지를 못 고치고 죽었다
       → 로그가 디스크에 있습니다.
         복구가 로그를 다시 실행(redo)해서 페이지를 만듭니다. 정상.

  ③ 페이지 일부만 고치고 죽었다 (부분 쓰기)
       → 로그에 '고치기 전 값(undo)'과 '고친 뒤 값(redo)'이 있습니다.
         커밋 레코드가 있으면 redo, 없으면 undo. 정상.

★ 반대로 했다면 (페이지 먼저, 로그 나중)
   ② 지점에서 페이지는 반쯤 바뀌었는데 무엇을 되돌려야 할지
      아무 데도 안 적혀 있습니다 → 복구 불가능
원자성이 “동시에 일어남”이 아니라는 점이 핵심입니다. 실제로는 절대 동시에 일어나지 않습니다. 다만 커밋 레코드 한 줄이 디스크에 닿는 순간을 경계로 삼아, 그 앞은 “전부 있었던 일”, 그 뒤는 “없었던 일”로 해석하는 것입니다. 원자성은 물리 현상이 아니라 로그를 읽는 규약입니다.

멱등 재실행 — 두 번 실행돼도 같아야 합니다

# 복구는 몇 번이든 중단됐다 다시 시작될 수 있습니다.
# 복구 도중 또 전원이 나갈 수 있으니까요.
# → redo 는 반드시 멱등이어야 합니다.

# ✗ 멱등이 아님: 상대적 변경
def redo_bad(page, rec):
    page.balance += rec.delta        # 두 번 적용되면 두 배

# ✓ 멱등: 절대값 + 페이지 LSN 비교 (실제 DB 방식)
def redo_ok(page, rec):
    if page.lsn >= rec.lsn:          # ★ 이미 반영된 로그다
        return                        #    건너뜁니다
    page.apply(rec.after_image)       # 고친 뒤의 값을 그대로 씀
    page.lsn = rec.lsn                # 어디까지 반영했는지 페이지에 기록

# LSN(Log Sequence Number) = 로그 안의 오프셋.
# 페이지마다 "나는 LSN 얼마까지 반영됐다"를 들고 있으면
# 재실행이 몇 번 돌아도 결과가 같습니다.
멱등성은 이 탭 전체를 관통합니다 — 복구 재실행, 메시지 재전달, 복제 로그 재적용이 전부 “두 번 와도 한 번 온 것과 같게”를 요구합니다. 🕸️ 분산 · 동시성 13 의 멱등성 키가 응용 계층에서의 같은 이야기입니다.

# DB 밖에서도 같은 패턴을 씁니다. 대표적인 것이 '아웃박스'입니다.
# 문제: DB 에 저장하고 카프카에 발행하는 두 동작은 원자적일 수 없다
#      (분산 트랜잭션 없이는)

# ✗ 위험 — 커밋은 됐는데 발행 직전에 프로세스가 죽으면 이벤트 유실
with db.transaction():
    db.insert(order)
kafka.publish(event)

# ✓ 로그를 먼저: 같은 트랜잭션 안에서 '보낼 것'을 테이블에 적습니다
with db.transaction():
    db.insert(order)
    db.insert_outbox(topic="orders", key=order.id,
                     payload=event, created_at=now())   # ★ 이게 WAL 역할

# 별도 워커가 아웃박스를 읽어 발행하고 표시합니다 (또는 CDC 가 대신)
for row in db.fetch_unsent_outbox(limit=500):
    kafka.publish(row.topic, row.key, row.payload)      # 중복 발행은 가능
    db.mark_sent(row.id)                                # 정확히 한 번은 아님

# 결과: at-least-once. 소비자가 멱등이면 실질적으로 exactly-once 처럼 동작합니다.
# 순서가 필요하면 key 를 파티션 키로 써서 같은 키는 같은 파티션으로 보냅니다.
패턴의 이름은 달라도 뼈대는 같습니다 — 파일 저장의 “임시 파일에 쓰고 rename”, 배포의 “새 심볼릭 링크로 원자 교체”, 브라우저의 IndexedDB 트랜잭션까지 전부 “진짜를 건드리기 전에 의도를 먼저 어딘가에 확정한다”는 한 가지 발상입니다.
정리 — WAL 은 데이터 페이지보다 로그를 먼저 디스크에 확정합니다. 이 순서 하나로 크래시 지점이 어디든 복구가 가능해지고, 흩어진 페이지 대신 파일 하나만 순차로 fsync 하면 되니 빠르기까지 합니다. 재실행은 반드시 멱등이어야 하고, 체크포인트가 복구 시간을 정합니다.
LOG 04

시간과 인과관계 — 벽시계로는 한 줄로 못 세웁니다

한 대에서는 “먼저 붙은 것이 먼저”라 순서가 공짜였습니다. 여러 대의 로그를 합치는 순간 그 공짜가 사라집니다. 시계는 서로 다르고, 심지어 뒤로도 갑니다.

순서의 근거는 시각이 아니라 메시지를 따라갈 수 있느냐입니다 — 그것이 happens-before.

happens-before 는 부분 순서입니다

a → b (a happens-before b) 가 성립하는 경우는 셋뿐입니다

  ① 같은 노드에서 a 가 b 보다 먼저 일어났다
  ② a 가 메시지를 보냈고 b 가 그 메시지를 받았다
  ③ a → c 이고 c → b 이다 (이행성)

그 밖에는 전부 '동시(concurrent)' — a ‖ b
  · 동시는 "같은 시각"이 아닙니다
  · "어느 쪽이 먼저인지 정할 근거가 없다"는 뜻입니다
  · 실제 벽시계로는 3시간 차이가 날 수도 있습니다

★ 그래서 분산 이벤트는 전순서(total order)가 아니라
  부분 순서(partial order)입니다.
  한 줄로 세우려면 '없는 정보를 만들어 넣는' 수밖에 없고,
  그것이 바로 합의(consensus)가 하는 일입니다.
🔢 이산수학 의 반순서 집합(poset)이 여기서 그대로 나옵니다. happens-before 는 반사·반대칭·이행을 만족하는 엄격 부분 순서이고, 전순서로 확장하는 것이 위상 정렬입니다. 다만 확장 방법이 여럿이라 어느 것을 고를지를 시스템이 정해야 합니다.

램포트 시계와 벡터 시계

# ── 램포트 논리 시계 ── 정수 하나
class Lamport:
    def __init__(self): self.t = 0
    def local(self):                 # 내 안에서 사건이 하나 일어남
        self.t += 1; return self.t
    def send(self):
        self.t += 1; return self.t   # 이 값을 메시지에 실어 보냄
    def recv(self, ts):
        self.t = max(self.t, ts) + 1 # ★ 받은 값과 비교해 앞서 감
        return self.t

# ── 벡터 시계 ── 노드마다 카운터 배열
class Vector:
    def __init__(self, me, n): self.me, self.v = me, [0] * n
    def local(self):
        self.v[self.me] += 1; return list(self.v)
    def recv(self, other):
        self.v = [max(a, b) for a, b in zip(self.v, other)]
        self.v[self.me] += 1

def compare(x, y):
    le = all(a <= b for a, b in zip(x, y))
    ge = all(a >= b for a, b in zip(x, y))
    if le and not ge: return "x → y"
    if ge and not le: return "y → x"
    if le and ge:     return "같음"
    return "동시(충돌)"                # ★ 서로 크고 작으면 concurrent

'결과가 원인보다 먼저' 나오는 줄을 보게 됩니다.

실무의 답 — 인과를 명시적으로 들고 다닙니다 (W3C Trace Context)

  traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
               ‾‾ ‾‾‾‾‾‾‾ trace-id (요청 전체) ‾‾‾   ‾ span-id ‾  플래그

  · trace_id  : 요청 하나에 하나. 서비스를 넘어가도 그대로 전파
  · span_id   : 이 구간의 ID
  · parent_id : 나를 부른 구간의 ID   ← ★ 이것이 happens-before 그 자체

정렬 규칙
  · 화면 정렬은 timestamp 로 해도 됩니다 (사람이 보기 편하니까)
  · 판단은 parent 관계로 합니다 (트리를 따라갑니다)
  · 같은 서비스 안에서는 단조 증가 시퀀스를 함께 남기면 확실합니다

로그 한 줄에 최소한 이것만은
  trace_id · span_id · service · instance · monotonic_seq
왜 이 절이 로그 탭에 있나 — 분산 시스템에서 로그의 가치는 “한 줄로 세울 수 있는가”에 달려 있기 때문입니다. 순서를 못 세우는 로그는 사건의 목록일 뿐 이야기가 되지 못합니다. 다음 절은 이 순서 문제를 정면으로 푸는 방법입니다.
정리 — 분산 로그의 순서는 시각이 아니라 happens-before 로 정의됩니다. 램포트 시계는 인과를 어기지 않는 번호를 주고, 벡터 시계는 동시까지 구분합니다. 한 줄로 세우려면 없는 정보를 만들어야 하고 — 단일 시퀀서, 합의, HLC, 동기화 시계가 그 방법입니다.
LOG 05

합의와 복제 로그 — 로그가 같으면 상태가 같습니다

여러 대가 같은 값을 갖게 하는 가장 확실한 방법은 같은 값을 복사하는 것이 아니라 같은 로그를 갖게 하는 것입니다. 상태 기계 복제(RSM)라고 부르는, 분산 시스템의 가장 오래된 아이디어입니다.

복제의 단위는 값이 아니라 로그 한 줄입니다 — 순서가 같으면 결과가 같습니다.

상태 기계 복제(RSM) 의 세 조건

복제본 N 대가 반드시 같은 상태가 되려면

  ① 같은 초기 상태에서 시작한다
  ② 같은 명령을 같은 순서로 받는다      ← 합의가 보장할 부분
  ③ 명령 적용이 결정적(deterministic)이다 ← 우리가 지킬 부분

③ 을 깨는 흔한 것들
  · 현재 시각        now()          → 명령에 시각을 실어 보냅니다
  · 난수             uuid4()        → 리더가 뽑아서 명령에 넣습니다
  · 맵 순회 순서                    → 정렬된 순회를 씁니다
  · 부동소수 연산 순서              → 같은 순서를 강제하거나 정수로
  · 로캘·타임존 의존 정렬           → 고정 로캘

★ ③ 이 깨지면 합의가 아무리 잘 돌아도 복제본이 갈라집니다.
   그리고 이 갈라짐은 몇 시간 뒤에 엉뚱한 조회 결과로 나타납니다.
“로그를 복제한다”와 “상태를 복제한다”의 차이 — 상태를 보내면 매번 전체(또는 diff)를 보내야 하고, 보내는 도중 값이 또 바뀝니다. 로그를 보내면 보낼 것이 이미 불변으로 확정돼 있고, 받는 쪽은 어디까지 받았는지 오프셋 하나로 관리하면 됩니다.

로그 매칭 성질 — 두 줄로 끝나는 귀납

Raft 가 유지하는 불변식(Log Matching Property)

  두 로그가 같은 인덱스에 같은 임기(term)의 항목을 가지면
    (1) 그 항목은 같은 명령이고
    (2) 그 앞의 모든 항목도 서로 같다

어떻게 이걸 공짜로 얻나 — 복제 요청에 '바로 앞 칸'을 같이 보냅니다

  AppendEntries(term, prevLogIndex, prevLogTerm, entries[], leaderCommit)

  팔로워:  내 로그의 prevLogIndex 자리의 임기가 prevLogTerm 인가?
           아니면 → 거절. 리더가 인덱스를 하나 낮춰 다시 시도
           맞으면 → 그 뒤를 잘라내고 entries 를 붙임

  이 검사 하나가 귀납의 기저이자 단계입니다.
  거절-후퇴를 반복하면 반드시 '갈라지기 시작한 지점'을 찾습니다.

커밋의 정의
  과반이 그 인덱스를 갖고 있고 + 그것이 현재 임기의 항목일 때
  ★ 커밋된 항목은 어떤 미래의 리더에게도 반드시 남아 있습니다

이렇게도 쓸 수 있다 — 쓰기 한 번의 진짜 비용 🟡 중급

지연은 로그가 디스크에 닿는 시간이 정합니다

합의 기반 쓰기 한 번의 지연

  리더 로그 append + fsync            0.3 ~ 5 ms   (디스크에 따라)
  + 과반 팔로워까지 왕복               0.2 ~ 2 ms   (같은 리전 기준)
  + 팔로워의 fsync                     (병렬로 진행)
  = 과반 중 '가장 느린' 쪽까지의 시간   ★ 최댓값이지 평균이 아닙니다

리전을 넘기면
  서울 ↔ 도쿄 왕복 ≈ 35ms → 쓰기 하나에 35ms 하한
  서울 ↔ 버지니아  ≈ 180ms → 초당 5회짜리 쓰기가 됩니다

그래서 실무 규칙
  · 합의 클러스터는 같은 리전(다른 AZ)에 둡니다
  · 노드는 3 또는 5 — 7 이상은 과반이 커져 느려지기만 합니다
  · 쓰기를 묶습니다(배치) — fsync 한 번에 수백 항목
  · 읽기는 리더 리스나 팔로워 읽기로 합의를 건너뜁니다

어디에 쓰이나 — 그리고 어디에 안 쓰나

쓰는 곳이유
etcd · ZooKeeper · Consul클러스터 메타데이터 — 양이 적고 정확해야 함
Kafka KRaft파티션 리더·설정 메타데이터

로그·메트릭 수집안 씁니다 — 정확히 하나일 필요가 없고 처리량이 우선입니다
합의는 비싸므로 아껴 씁니다 — “누가 리더인가 · 이 샤드는 누구 것인가” 같은 작지만 절대 틀리면 안 되는 사실에만 씁니다. 대량 데이터는 그 결정을 따라가는 방식(단일 리더 복제)으로 처리합니다. 🕸️ 분산 · 동시성 09 · 14 에 Raft 의 리더 선출과 안전성 증명이 자세히 있습니다.
정리 — 복제의 단위는 값이 아니라 로그 한 줄입니다. 같은 초기 상태 + 같은 로그 + 결정적 적용 = 같은 상태(RSM). 그래서 합의 알고리즘은 상태가 아니라 로그의 순서에 동의합니다. 쓰기 지연은 과반 중 가장 느린 노드의 fsync가 정합니다.
LOG 06

로그 기반 아키텍처 — 데이터베이스를 뒤집기

데이터베이스 안에 숨어 있던 로그를 밖으로 꺼내 시스템의 중심축으로 놓으면 아키텍처가 통째로 바뀝니다. 이벤트 소싱 · CQRS · CDC · 카프카가 전부 이 하나의 이동에서 나온 이름들입니다.

중심에 원통(로그) 하나 — 바깥의 구름들은 서로의 존재를 모른 채 같은 사실을 읽습니다.

이벤트 소싱 + CQRS — 쓰기와 읽기를 갈라 놓기

# ── 쓰기 쪽(Command): 로그에 이벤트만 붙입니다 ──
def place_order(cmd):
    stream = f"order-{cmd.order_id}"
    state  = load(stream)                     # fold 로 현재 상태 복원
    if state.status != "new":
        raise Conflict("이미 처리된 주문")     # 불변식 검사
    events = [{"t": "OrderPlaced", "items": cmd.items,
               "total": cmd.total, "at": cmd.at}]
    log.append_stream(stream, events,
                      expected_version=state.version)   # ★ 낙관적 동시성

# ── 읽기 쪽(Query): 로그를 구독해 '읽기 모델'을 만듭니다 ──
def projection_worker():
    cursor = store.get_cursor("order-list-view")
    for off, ev in log.read_from(cursor):
        if ev["t"] == "OrderPlaced":
            db.upsert_order_row(ev)           # 조회에 최적화된 평평한 표
        elif ev["t"] == "OrderShipped":
            db.set_shipped(ev)
        store.set_cursor("order-list-view", off + 1)   # 멱등하게 전진

# 읽기 모델은 언제든 지우고 오프셋 0 부터 다시 만들 수 있습니다.
# → 인덱스 설계를 바꾸고 싶으면 새 모델을 만들어 재생하면 끝입니다.
CQRS 의 진짜 이득은 “읽기 모델을 버릴 수 있다”입니다. 보통의 DB 에서는 스키마를 바꾸려면 마이그레이션이라는 위험한 수술이 필요하지만, 로그가 원본이면 새 모델을 옆에 만들어 재생하고, 다 만들어지면 스위치를 넘기면 됩니다.

Change Data Capture: DB 의 WAL 을 그대로 읽어 이벤트로 흘립니다.

  PostgreSQL   논리 복제 슬롯(pgoutput · wal2json)
  MySQL        binlog (ROW 포맷)
  MongoDB      oplog · change stream
  도구          Debezium · Maxwell · AWS DMS

애플리케이션 코드를 하나도 안 고치고 이벤트 스트림이 생깁니다.

  { "op": "u", "source": {"table": "orders", "lsn": 219383},
    "before": {"id": 9, "status": "paid"},
    "after":  {"id": 9, "status": "shipped"} }

★ 주의 — CDC 는 '행이 바뀌었다'만 알려 줍니다.
   '왜 바뀌었나'(주문 취소인지 관리자 수정인지)는 없습니다.
   그래서 CDC 이벤트는 도메인 이벤트가 아닙니다.
   · 통합·색인·데이터 웨어하우스에는 훌륭합니다
   · 도메인 로직의 근거로 쓰면 나중에 반드시 후회합니다

이중 쓰기 문제의 해법이기도 합니다 (LOG 03 의 아웃박스와 짝)
  DB 커밋 = 이벤트 발행이 되므로 둘이 어긋날 수 없습니다.

이렇게도 쓸 수 있다 — 파티션과 순서 보장의 범위 🟡 중급

순서는 파티션 안에서만 보장됩니다

토픽 orders (파티션 3개)

  P0: [주문A생성][주문A결제][주문A배송]      ← key = "A"
  P1: [주문B생성][주문B취소]                 ← key = "B"
  P2: [주문C생성][주문C결제]                 ← key = "C"

  · 같은 key → 항상 같은 파티션 → 순서 보장 ★
  · 다른 파티션 사이에는 순서가 없습니다 (전순서 아님)
  · 파티션 = 병렬성의 단위 = 소비자 최대 개수

★ 설계의 핵심은 "무엇을 key 로 둘 것인가"입니다
  · 주문 ID   → 주문 단위 순서 보장, 고르게 분산
  · 사용자 ID → 한 사용자의 사건 순서 보장
  · 상수 하나 → 전체 순서 보장, 대신 병렬성 1 (거의 안 씁니다)

핫 파티션 주의
  인기 셀러 ID 를 key 로 쓰면 그 파티션만 폭주합니다
  → key 에 접미사를 붙여 쪼개거나, 순서 보장을 포기합니다

이 구조를 고를 때와 피할 때

상황판단
“왜 이 값이 됐나”를 자주 묻는다이벤트 소싱이 맞습니다 (금융·정산·의료)
같은 사실을 여러 저장소가 필요로그를 중심에 (검색·캐시·분석)
서비스가 계속 늘어난다로그 구독이 API 호출보다 결합도가 낮습니다
레거시 DB 를 못 고친다CDC 로 밖에서 꺼냅니다
CRUD 화면 몇 개가 전부쓰지 마세요 — 복잡도만 늘어납니다
강한 즉시 일관성이 필수읽기 모델은 결국 일관입니다. 맞지 않습니다
가장 흔한 실패 — 읽기 모델이 몇 초 늦는다는 사실을 UI 가 견디지 못하는 경우입니다. “저장했는데 목록에 없어요”가 바로 그것입니다. 해법은 쓰기 응답에 필요한 값을 같이 돌려주거나, 그 화면만 쓰기 모델을 직접 읽는 것입니다. 🕸️ 분산 · 동시성 08 의 일관성 모델과 이어집니다.
정리 — DB 안에 있던 로그를 밖으로 꺼내 모든 시스템이 같은 사실을 구독하게 만드는 것이 로그 기반 아키텍처입니다. 이벤트 소싱은 쓰기를, CQRS 는 읽기를, CDC 는 레거시를 담당합니다. 순서는 파티션 안에서만 보장되고, 읽기 모델은 언제든 지우고 다시 만들 수 있는 캐시입니다.
LOG 07

정보량과 로그 — 남기지 않은 것은 복원되지 않습니다

로그를 “얼마나 남길까”는 취향 문제가 아니라 정보 이론 문제입니다. 로그는 과거에서 미래로 가는 채널이고, 채널을 통과하지 못한 정보는 어떤 똑똑한 도구로도 되살릴 수 없습니다.

카디널리티는 더하기가 아니라 곱하기로 늡니다 — 레이블 하나가 비용을 백 배로 만듭니다.

엔트로피 관점 — 한 줄이 담는 정보의 양

import math
from collections import Counter

def entropy(values):
    """이 필드가 실제로 얼마나 '구별'해 주는가 (비트)"""
    n = len(values)
    c = Counter(values)
    return -sum((k / n) * math.log2(k / n) for k in c.values())

# 하루치 로그 100만 줄에서 필드별로 재 보면
#   level      (INFO/WARN/ERROR)  →  0.3 비트   거의 다 INFO. 쓸모 적음
#   service    (12종)             →  3.1 비트
#   endpoint   (80종)             →  5.9 비트
#   status     (14종)             →  1.2 비트
#   trace_id   (100만종)          → 19.9 비트   ★ 거의 완전한 구별
#   msg 자유문자열                →  높지만 질의 불가 (구조가 없어서)

# 해석
#  · 엔트로피가 0에 가까운 필드는 남겨도 답을 못 늘립니다
#  · 엔트로피가 아주 높은 필드(trace_id)는 '연결'에는 최고지만
#    메트릭 레이블로 쓰면 카디널리티가 폭발합니다 ★
#  · 즉, 같은 필드라도 로그에서는 축복, 메트릭에서는 재앙입니다
왜 로그와 메트릭에서 답이 반대인가 — 로그는 줄마다 값을 따로 저장하므로 고유값이 많아도 비용이 선형입니다. 메트릭은 레이블 조합마다 시계열 하나를 만들어 영구히 들고 있으므로 곱셈으로 늡니다. 저장 구조가 다르니 규칙도 달라집니다.

샘플링이 정확히 무엇을 잃는가

균등 샘플링 1% (모든 요청을 1/100 확률로 남김)

  잘 보존되는 것            잃는 것
  ─────────────────         ─────────────────────────────
  평균 · 중앙값             단 한 번 일어난 사건 (99% 사라짐)
  p50 · p90 정도            p99.9 꼬리 (표본이 거의 안 남음)
  전체 비율                 특정 사용자의 전체 여정
  추세 방향                 정확한 카운트 (건수를 못 셉니다)

★ 100건 중 1건짜리 희귀 오류는 하루에 3번 났어도
  샘플에는 0.03건 → 사실상 '없던 일'이 됩니다.

그래서 실무는 균등 샘플링을 안 씁니다
  · 꼬리 우선(tail-based)  : 트레이스를 끝까지 모아 보고
                             느리거나 에러면 100% 남깁니다
  · 헤드 기반 + 강제 유지   : 에러·느린 요청은 sampled=1 로 고정
  · 계층 샘플링             : 정상 1%, 에러 100%, 신규 기능 100%
  · 카운트는 따로            : 샘플링해도 카운터는 전량 집계
                             (샘플로 곱하기 100 하면 틀립니다)

실무에선 이렇게 — 무엇을 남기면 나중에 답할 수 있나 🔴 실무

질문을 먼저 적고, 그 질문에 필요한 최소 필드를 역산합니다.

  ───────────────────────────────────      ────────────────────────────

  · 성공 경로의 DEBUG      → 평시에는 끄고 필요할 때만 동적으로 켭니다

  ★ "이 줄이 없으면 대답 못 하는 질문이 있는가?"
     없으면 그 줄은 비용일 뿐입니다.
거꾸로 가장 비싼 실수 — 장애가 터진 뒤에야 “아, 그 값을 안 남겼네”를 알게 되는 것입니다. 로그는 미래의 나에게 보내는 편지인데, 편지는 사건이 일어나기 전에 써야 합니다. 그래서 새 기능을 만들 때 “이게 실패하면 무엇을 보고 싶을까”를 설계 단계에서 정합니다.
정리 — 로그는 과거에서 미래로 가는 채널이고, 통과하지 못한 정보는 복원되지 않습니다. 카디널리티는 곱셈으로 늘어나므로 고유값이 큰 필드는 로그에는 넣되 메트릭 레이블에는 넣지 않습니다. 균등 샘플링은 정확히 희귀 사건과 꼬리를 먼저 버립니다.
LOG 08

관측 가능성의 이론 — 출력만 보고 내부를 알 수 있는가

관측 가능성(observability)은 마케팅 용어가 아니라 제어이론에서 온 정의가 있는 말입니다. “출력의 유한한 기록만으로 내부 상태를 유일하게 결정할 수 있으면 그 시스템은 관측 가능하다.” 이 정의를 소프트웨어로 옮기면 무엇을 남겨야 하는지가 자동으로 따라 나옵니다.

어떤 행도 한 칸만으로 채워지지 않습니다 — 세 신호는 대체재가 아니라 서로 다른 질문의 도구입니다.

제어이론의 정의를 그대로 옮기면

선형 시스템   x' = A x + B u ,  y = C x

  관측 가능(observable) 이란?
   → 출력 y 를 유한 시간 동안 관찰한 것만으로
     초기 상태 x(0) 을 유일하게 결정할 수 있다는 뜻

  판정: 관측 가능성 행렬 O = [C; CA; CA²; …; CAⁿ⁻¹]
        rank(O) = n 이면 관측 가능

소프트웨어로 옮기면
  x  = 프로세스·큐·캐시·커넥션 풀의 내부 상태
  y  = 우리가 밖으로 내보낸 것 (로그 · 메트릭 · 스팬)
  C  = 계측(instrumentation) — 무엇을 내보내기로 정했는가

★ 여기서 두 가지가 곧바로 따라 나옵니다
  ① 관측 가능성은 도구가 아니라 C 의 성질입니다.
     비싼 SaaS 를 붙여도 C 가 빈약하면 rank 가 안 찹니다.
  ② '모니터링'은 이미 아는 y 를 보는 것이고,
     '관측 가능성'은 새로운 y 조합으로 새 질문에 답하는 능력입니다.
➗ 선형대수 의 계수(rank)와 🤖 ML 이론 의 식별 가능성(identifiability)이 같은 뼈대입니다. 관측이 모자라면 여러 내부 상태가 같은 출력을 냅니다 — 그러면 원인을 하나로 좁힐 수 없습니다. “로그를 봐도 모르겠다”의 정확한 수학적 이름이 이것입니다.

세 신호의 저장 구조가 능력을 정합니다

결정적 차이는 “미리 집계했는가”입니다. 메트릭은 저장할 때 이미 정보를 버렸으므로 나중에 새로운 방식으로 쪼갤 수 없습니다(“이 오류가 어느 고객에게 몰렸나”에 못 답합니다). 로그·추적은 원본을 갖고 있어 질문을 나중에 정할 수 있습니다 — 대신 비쌉니다. 최근의 넓은 이벤트(wide event) 흐름은 이 셋을 한 줄에 합치자는 시도입니다.

# 계측(C 행렬)을 설계한다는 것 — 요청 하나에 '넓은 이벤트' 한 줄
# (여러 줄로 흩어 놓으면 나중에 조인해야 하고, 조인은 대부분 안 됩니다)

def handle_request(req):
    ev = {"trace_id": trace_id.get(), "route": req.route,
          "tenant": req.tenant, "version": BUILD, "region": REGION}
    t0 = time.monotonic()                    # ★ 벽시계 아님 (LOG 04)
    try:
        ev["cache_hit"]  = cache.probe(req)
        ev["db_calls"]   = 0                 # 핸들러가 늘려 갑니다
        result = do_work(req, ev)
        ev["status"] = 200
        return result
    except AppError as e:
        ev["status"], ev["error_kind"] = e.status, type(e).__name__
        raise
    finally:
        ev["duration_ms"] = round((time.monotonic() - t0) * 1000, 2)
        ev["sampled"] = ev["status"] >= 500 or ev["duration_ms"] > 1000
        emit(ev)          # 한 요청 = 한 줄. 필드가 30~100개여도 좋습니다

#   · version 1.42 배포 후 error_kind 분포가 어떻게 변했나?
#   · db_calls > 20 인 요청은 어느 tenant 에 몰려 있나?   ← 미리 계획 못 한 질문 ★
“나중에 필요하면 그때 넣지”가 안 되는 이유 — 필드를 오늘 추가해도 어제의 데이터에는 그 필드가 없습니다. 그리고 장애는 늘 어제 일어납니다. 계측은 코드처럼 리뷰하고, 필드 추가는 배포처럼 다루세요.
정리 — 관측 가능성은 출력만 보고 내부 상태를 결정할 수 있는가라는 제어이론의 성질입니다. 도구를 사서 얻는 게 아니라 무엇을 내보내기로 했는가로 정해집니다. 로그 · 메트릭 · 추적은 저장 구조가 달라 답할 수 있는 질문의 종류가 다릅니다.
LOG 09

구조적 로깅과 스키마 진화 — 한 줄은 문장이 아니라 레코드입니다

"Payment failed for order 88123 after 412ms" 는 사람에게는 친절하지만 기계에게는 파싱해야 할 숙제입니다. 로그 한 줄을 필드 이름과 값의 집합으로 보면 로그는 곧 테이블이 되고, 그 순간부터 데이터베이스가 40년 동안 풀어 온 문제 — 스키마는 어떻게 바뀌는가 — 가 그대로 따라옵니다.

로그 한 줄은 열 이름이 붙은 레코드입니다 — 문장으로 적는 순간 읽는 쪽이 파싱 비용을 냅니다.

문장과 레코드 — 같은 사실, 다른 쓸모

import json, logging, time

# ✗ 문장 — 값이 문장 속에 녹아 있어 기계가 다시 꺼내야 합니다
log.error(f"Payment failed for order {order_id} after {ms}ms")
#   "412ms 넘게 걸린 실패는 몇 건?" → 정규식으로 숫자를 뽑아 비교
#   메시지 문구를 한 글자라도 바꾸면 정규식이 깨집니다

# ✓ 레코드 — 필드가 이미 분리돼 있습니다
class JsonFormatter(logging.Formatter):
    def format(self, rec):
        base = {"ts": time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(rec.created)),
                "level": rec.levelname, "logger": rec.name,
                "event": rec.getMessage(), "schema": 3}
        base.update(getattr(rec, "fields", {}))   # extra 로 넘긴 필드
        return json.dumps(base, ensure_ascii=False)

def emit(logger, level, event, **fields):
    logger.log(level, event, extra={"fields": fields})

emit(log, logging.ERROR, "charge.failed",
     order_id=88123, reason="card_declined", duration_ms=412.7)

# 수집기에서는 곧바로 질의가 됩니다
#   event = 'charge.failed' AND duration_ms > 400
#   GROUP BY reason  → 사유별 건수가 한 줄에 나옵니다
event 는 문장이 아니라 코드로 둡니다 — charge.failed 처럼 점으로 나눈 고정 문자열이면 오타가 나지 않고, 문구를 다듬어도 질의가 안 깨집니다. 사람이 읽을 문장은 표시할 때 만들면 됩니다. Serilog 의 메시지 템플릿 {OrderId}, Go 의 slog, Java 의 Logstash 인코더가 전부 같은 생각입니다.

스키마가 없다고 생각하는 순간 스키마가 생깁니다

"우리 로그는 JSON 이라 스키마가 없어요"
  → 대시보드가 duration_ms 를 읽는 순간 그것이 스키마입니다.
    암묵적 스키마는 깨질 때까지 보이지 않을 뿐입니다.

깨지는 순간들 (전부 실제로 겪는 것들)
  · duration_ms 가 어느 날 문자열 "412.7" 로 바뀜  → 합계가 0
  · user 필드가 문자열이었다가 객체 {id, name} 로   → 색인 충돌
  · level 이 "WARN" 이었다가 "WARNING" 으로         → 필터 누락
  · 필드 이름을 orderId → order_id 로 정리          → 옛 로그 조회 불가
  · 시각을 로컬 시간에서 UTC 로 바꿈                → 9시간 어긋난 그래프

그래서 로그에도 데이터베이스와 같은 규칙이 필요합니다
  ① 스키마를 어딘가에 적어 둔다 (문서든 JSON Schema 든)
  ② 바꿀 때 호환 규칙을 따른다 (다음 표)
  ③ 줄마다 schema 버전을 싣는다 - 읽는 쪽이 어느 규칙으로 읽을지 알도록
Elasticsearch 계열 수집기의 “매핑 충돌”이 이 문제의 가장 흔한 얼굴입니다. 같은 필드 이름에 어느 날 다른 타입이 들어오면 그 줄은 조용히 버려지거나 색인이 거부됩니다. 에러가 나는 곳은 로거가 아니라 몇 단계 뒤의 수집기라서 원인을 찾는 데 시간이 걸립니다.

이렇게도 쓸 수 있다 — 호환성의 네 방향 🟡 중급

누가 먼저 바뀌는가로 규칙이 갈립니다

호환뜻허용되는 변경
후방(backward)새 코드가 옛 데이터를 읽음필드 추가(기본값 있음) · 필드 삭제
전방(forward)옛 코드가 새 데이터를 읽음필드 추가 · 기본값 있는 필드 삭제
완전(full)양쪽 다기본값 있는 필드 추가·삭제만
없음둘 다 아님이름 변경 · 타입 변경 · 뜻 변경
로그에서는 거의 항상 "후방 + 전방" 둘 다 필요합니다
  · 옛 로그를 새 대시보드가 읽는다     → 후방
  · 새 로그를 아직 안 고친 알림 규칙이 읽는다 → 전방
  · 배포는 서서히 굴러가므로 두 버전이 동시에 씁니다 ★

안전한 변경             위험한 변경 (= 새 필드 + 옛 필드 유지로 우회)
  필드 추가               필드 이름 바꾸기
  필드 삭제(읽는 쪽 확인)  타입 바꾸기 (숫자 ↔ 문자열)
  enum 값 추가            enum 값의 뜻 바꾸기
                          단위 바꾸기 (ms → s) ★ 가장 교묘함

업캐스터 — 옛 줄을 새 형태로 읽어 올리기

# 스키마 2 → 3 에서 무엇이 바뀌었나
#   · duration 이 초(float) 에서 duration_ms(밀리초) 로
#   · user(문자열) 이 user_id 로 분리
# 옛 로그는 고칠 수 없습니다(append-only). 읽을 때 올립니다.

UPCASTERS = {
    1: lambda r: {**r, "schema": 2, "level": r.get("lvl", "INFO")},
    2: lambda r: {**{k: v for k, v in r.items() if k not in ("duration", "user")},
                  "schema": 3,
                  "duration_ms": r["duration"] * 1000 if "duration" in r else None,
                  "user_id": r.get("user")},
}
CURRENT = 3

def read(rec: dict) -> dict:
    v = rec.get("schema", 1)               # 번호가 없으면 가장 옛 버전
    while v < CURRENT:
        rec = UPCASTERS[v](rec)            # 한 단계씩 올립니다
        v = rec["schema"]
    return rec

# 규칙
#  · 업캐스터는 순수 함수 - 같은 줄은 언제 읽어도 같은 결과 (LOG 02 의 apply 와 같음)
#  · 한 번에 한 단계만 - 1→3 지름길을 만들면 조합이 폭발합니다
#  · 원본은 그대로 - 저장소에는 여전히 schema 1 줄이 남아 있습니다
Avro · Protobuf 가 이 규칙을 강제해 줍니다 — Confluent Schema Registry 는 BACKWARD / FORWARD / FULL 모드로 호환되지 않는 스키마 등록을 거부하고, Protobuf 는 필드 번호를 절대 재사용하지 말라(reserved)는 규칙 하나로 전방 호환을 지킵니다. 이벤트 소싱의 이벤트 스키마에도 똑같이 적용됩니다.

실무에선 이렇게 — 공통 스키마 위에 올라타기 🔴 실무

필드 이름을 팀마다 새로 짓지 않습니다. 이미 합의된 이름이 있습니다.

OpenTelemetry 로그 데이터 모델 (필드의 뼈대)
  Timestamp · ObservedTimestamp     사건 시각 / 수집기가 본 시각 (둘이 다릅니다 ★)
  TraceId · SpanId · TraceFlags     LOG 04 의 인과 - 추적과 로그를 잇는 열쇠
  SeverityText · SeverityNumber     "ERROR" 와 17 - 숫자가 있어야 비교·정렬이 됩니다
  Body                              사람이 읽을 본문 (event 코드를 두기도 합니다)
  Resource                          누가 - service.name · service.version · host · k8s.pod
  InstrumentationScope              어느 라이브러리가
  Attributes                        나머지 전부 - order_id · reason · duration_ms …

의미 규약(semantic conventions) 이 이름을 정해 둡니다
  http.request.method · http.response.status_code · db.system · error.type …
  Elastic 의 ECS 가 2023년 OTel 규약으로 합쳐지는 쪽으로 정리됐습니다
  → 이 이름을 쓰면 대시보드·알림 템플릿을 그대로 가져다 씁니다

실무 규칙 넷
  ① Resource 는 프로세스가 시작할 때 한 번 정하고 모든 줄에 붙입니다 (코드에서 매번 쓰지 않음)
  ② 도메인 필드는 접두사로 묶습니다 - order.id · order.total · payment.method
  ③ 같은 뜻은 같은 이름 - user_id 와 userId 와 uid 가 섞이면 조인이 안 됩니다
  ④ 스키마 문서와 예제 줄을 코드 저장소에 같이 둡니다 - 리뷰 대상입니다
ObservedTimestamp 가 왜 따로 있나 — 사건이 일어난 시각과 수집기가 그 줄을 받은 시각은 다릅니다. 네트워크가 막혀 30분 뒤에 도착한 줄은 Timestamp 로 정렬하면 과거에, ObservedTimestamp 로 보면 지금 나타납니다. “왜 그래프가 뒤늦게 바뀌지?”의 답이 대개 이 둘의 차이입니다.
정리 — 로그 한 줄은 필드가 있는 레코드이고, 대시보드가 필드를 읽는 순간 스키마가 존재합니다. 변경은 데이터베이스와 같은 호환 규칙(후방·전방)을 따르고, 줄마다 schema 버전을 실어 옛 줄은 업캐스터로 읽어 올립니다. 필드 이름은 새로 짓지 말고 OTel 규약에 올라탑니다.

로그 컴팩션과 보존 — 영원히 남기지는 못합니다

로그는 append-only 지만 디스크는 유한합니다. 무엇인가는 버려야 하는데, 버리는 방법이 곧 시스템이 답할 수 있는 질문을 정합니다. 시간으로 자를지, 키마다 마지막만 남길지, 싼 저장소로 옮길지 — 셋은 서로 다른 것을 잃습니다.

보존 정책은 무엇을 잃어도 되는지를 먼저 정하는 일입니다 — 전부 유리한 행은 없습니다.

삭제와 컴팩션 — 같은 “버리기”, 다른 결과

보존(retention) - 오래된 세그먼트를 통째로 버립니다
  [seg0][seg1][seg2][seg3][seg4 활성]
   ↑ 7일 지남 → unlink                 ★ 파일 하나 지우면 끝
  남는 것: 최근 N일의 모든 사건
  잃는 것: N일 전의 모든 것 - 그때 만들어진 키의 마지막 값까지

컴팩션(compaction) - 키마다 마지막 값만 남깁니다
  전:  k1=a  k2=x  k1=b  k3=p  k2=y  k1=c  k3=∅(툼스톤)
  후:              k2=y  k1=c   (k3 는 툼스톤 뒤 삭제)
  남는 것: 모든 키의 최신 값 - 오프셋 0 부터 읽으면 현재 상태 전체
  잃는 것: k1 이 a→b→c 로 변한 과정

★ 같은 질문에 다르게 답합니다
  "k1 의 지금 값은?"         보존: 7일 전 키면 모름 / 컴팩션: 항상 답함
  "k1 이 어제 뭐였나?"       보존: 답함 / 컴팩션: 모름
  "지난주 이벤트 수는?"      보존: 답함 / 컴팩션: 모름 (사건 수가 보존 안 됨)
컴팩션은 LOG 02 의 fold 를 저장소가 대신 해 두는 것입니다. 키마다 apply 가 “마지막 값으로 덮기”라면 fold 결과는 곧 “키별 최신 값”이고, 그것만 남기면 재생 시간이 이벤트 수가 아니라 키 수에 비례합니다. Kafka Streams 의 상태 저장소 · Debezium 의 스냅샷 토픽이 이렇게 복구됩니다.

컴팩션을 직접 구현하면 (세그먼트 재작성)

TOMBSTONE = None

def compact(segments):
    """오래된 세그먼트들을 읽어 키별 마지막 값만 남긴 새 세그먼트를 만듭니다."""
    latest = {}                              # key -> (offset, value)
    for seg in segments:                     # 오래된 것부터 순서대로
        for off, key, val in seg.read():
            latest[key] = (off, val)         # 뒤에 온 것이 이깁니다
    out = Segment.new()
    for key, (off, val) in sorted(latest.items(), key=lambda kv: kv[1][0]):
        if val is TOMBSTONE:
            continue                         # 툼스톤은 유예 기간 뒤 함께 사라집니다
        out.append(off, key, val)            # ★ 오프셋은 원래 번호를 그대로 유지
    out.seal()
    for seg in segments:
        seg.unlink()                         # 옛 세그먼트는 통째로 삭제
    return out

# 지켜야 할 것
#  · 활성(쓰는 중인) 세그먼트는 건드리지 않습니다 - 읽기·쓰기와 경쟁하지 않도록
#  · 오프셋을 다시 매기지 않습니다 - 소비자의 커서가 깨집니다 (LOG 01)
#    그래서 컴팩션 뒤의 로그는 오프셋에 빈 자리가 생깁니다. 정상입니다.
#  · 툼스톤은 바로 지우지 않습니다 - 느린 소비자가 "삭제됐다"를 보고 가야 합니다

무결성 — 해시 체인 · 머클 트리 · 인증서 투명성

“append-only” 는 지금까지 약속이었습니다. 관리자가 파일을 열어 한 줄을 고치면 아무도 모릅니다. 그 약속을 수학으로 검증 가능하게 만드는 것이 이 절입니다 — 고친 것을 막지는 못해도 고쳤다는 사실은 반드시 드러나게 합니다.

루트 하나를 공개하면 몰래 고치기가 불가능해집니다 — 막는 게 아니라 반드시 드러나게 하는 것입니다.

1단계 — 해시 체인: 앞 줄의 해시를 다음 줄에 넣기

import hashlib, json

def h(data: bytes) -> str:
    return hashlib.sha256(data).hexdigest()

class ChainedLog:
    def __init__(self):
        self.items, self.prev = [], "0" * 64          # 창세기 해시

    def append(self, record: dict) -> str:
        body = json.dumps(record, sort_keys=True)     # ★ 직렬화가 결정적이어야
        entry = {"prev": self.prev, "body": body}     #   같은 입력 → 같은 해시
        entry["hash"] = h((entry["prev"] + body).encode())
        self.items.append(entry)
        self.prev = entry["hash"]                     # 다음 줄이 이 값을 품습니다
        return self.prev

    def verify(self) -> bool:
        prev = "0" * 64
        for i, e in enumerate(self.items):
            if e["prev"] != prev: return False       # 끊김 → 중간 삭제·삽입
            if h((e["prev"] + e["body"]).encode()) != e["hash"]:
                return False                          # 불일치 → 내용 변조
            prev = e["hash"]
        return True

# Git 이 정확히 이것입니다 - 커밋 해시 = H(트리 + 부모 해시 + 메시지 + …)
# 과거 커밋 하나를 고치면 그 뒤 모든 커밋의 해시가 바뀝니다 (rebase 가 그것)
# 블록체인은 여기에 "누가 다음 줄을 붙일지" 합의를 얹은 것입니다
해시 체인이 못 막는 것 — 관리자가 맨 끝을 잘라내고 그 시점의 해시부터 다시 이어 붙이면 체인은 여전히 유효합니다. 체인은 “중간이 안 바뀌었다”만 보장하고 “끝이 어디였는가”는 모릅니다. 그래서 마지막 해시를 외부에 공개해야 합니다 — 다음 단계가 그 이야기입니다.

2단계 — 머클 트리: 포함 증명을 log n 으로

def merkle_root(leaves: list[str]) -> str:
    level = [h(("\x00" + x).encode()) for x in leaves]   # 잎 접두사 0x00
    while len(level) > 1:
        if len(level) % 2: level.append(level[-1])       # 홀수면 마지막 복제
        level = [h(("\x01" + a + b).encode())            # 내부 노드 접두사 0x01
                 for a, b in zip(level[::2], level[1::2])]
    return level[0]
# 접두사를 다르게 두는 이유: 잎과 내부 노드가 같은 해시를 내는 공격(second preimage) 방지

def inclusion_proof(leaves, idx):
    """idx 번째 잎의 형제 해시 목록 - 검증자는 이것만 받습니다"""
    level = [h(("\x00" + x).encode()) for x in leaves]; proof = []
    while len(level) > 1:
        if len(level) % 2: level.append(level[-1])
        sib = idx ^ 1                                    # 이웃 인덱스
        proof.append((level[sib], sib < idx))            # (해시, 왼쪽인가)
        level = [h(("\x01" + a + b).encode()) for a, b in zip(level[::2], level[1::2])]
        idx //= 2
    return proof

def verify(leaf, proof, root) -> bool:
    cur = h(("\x00" + leaf).encode())
    for sib, is_left in proof:
        cur = h(("\x01" + (sib + cur if is_left else cur + sib)).encode())
    return cur == root         # ★ 잎 하나 + 형제 log n 개로 루트를 다시 만듭니다

# 100만 항목이면 증명 크기 ≈ 20 해시 = 640 바이트. 로그 전체를 받을 필요가 없습니다.

CT 의 답 (RFC 6962 · 2013 / 개정 RFC 9162 · 2021) - 발급을 숨길 수 없게
  ① CA 가 인증서를 발급하면 공개 CT 로그에 제출합니다
  ② 로그는 머클 트리에 추가하고 SCT(Signed Certificate Timestamp) 를 돌려줍니다
     "이 인증서를 이 시각에 받았고 곧 트리에 넣겠다"는 서명된 약속
  ③ 인증서(또는 TLS 핸드셰이크)에 SCT 를 실어 보냅니다
  ④ 브라우저는 SCT 가 없거나 부족하면 인증서를 거부합니다
     (Chrome 은 2018년 4월부터 신규 인증서에 CT 를 요구)
  ⑤ 모니터가 로그를 계속 읽으며 "내 도메인 인증서가 누가 냈나"를 감시합니다
  ⑥ 감사자는 일관성 증명으로 로그가 뒤에서 지워지지 않았는지 확인합니다

★ 핵심은 "가짜 발급을 막는다"가 아니라 "가짜 발급이 반드시 공개된다"입니다.
  가짜 인증서는 여전히 만들 수 있지만, 만들면 로그에 남고 도메인 주인이 봅니다.

④ 검증 잡              매일 처음부터 체인·루트를 다시 계산해 공개된 값과 비교

“변조 방지”와 “변조 감지”를 구분하세요 — 소프트웨어는 후자만 할 수 있습니다. 전자는 저장소의 권한과 물리 통제의 몫입니다. 감지가 확실하면 고칠 동기가 사라지므로 결과적으로 방지가 됩니다. 투명성의 힘은 막는 데 있지 않고 숨길 수 없게 하는 데 있습니다.
정리 — 해시 체인은 중간이 안 바뀌었음을, 머클 트리는 그 위에 포함과 일관성을 log n 으로 증명합니다. 루트를 외부에 공개해야 끝을 잘라내는 공격까지 드러납니다. Certificate Transparency 는 이 구조로 CA 의 발급을 숨길 수 없게 만들었고, 같은 설계가 소프트웨어 서명과 내부 감사 로그로 번졌습니다.

로그로 못 잡는 것 — 증거이지 진실이 아닙니다

열한 절 동안 로그가 얼마나 강력한지 봤으니 마지막은 한계입니다. 로그는 “적힌 것”이지 “일어난 것”이 아닙니다. 둘 사이의 틈에서 없는 줄을 없는 일로 읽고, 있는 줄을 원인으로 읽는 실수가 나옵니다.

가운데 초록만이 이해한 사건입니다 — 나머지 여섯 영역 각각에 이름이 붙는다는 것이 핵심입니다.

대응 - 부재를 신호로 바꿉니다
  · 하트비트 : "살아 있다"를 주기적으로 적고, 끊기면 알림 (dead man's switch)
  · 양쪽 계측 : 클라이언트에서도 시도·실패를 보냅니다 (RUM · 모바일 SDK)
  · 기대 카운트 : 매 시간 배치가 N 건이어야 한다 - 0 건은 "조용함"이 아니라 "장애"
  · 종료 훅 + 동기 플러시 : 정상 종료 경로에서만이라도 버퍼를 비웁니다

거짓 신호 — 있는 줄이 사실이 아닐 때

# ✗ 가장 흔한 계측 버그 - 결과가 정해지기 전에 "성공"을 적습니다
def transfer(src, dst, amt):
    log.info("transfer.ok", src=src, dst=dst, amt=amt)   # 아직 아무것도 안 했음
    with db.transaction():
        debit(src, amt)
        credit(dst, amt)          # 여기서 예외 → 롤백. 로그에는 성공이 남습니다

# ✓ 결과가 확정된 뒤에, 확정된 값으로
def transfer(src, dst, amt):
    try:
        with db.transaction():
            debit(src, amt); credit(dst, amt)
    except Exception as e:
        log.error("transfer.failed", src=src, dst=dst, amt=amt,
                  error_kind=type(e).__name__)
        raise
    log.info("transfer.ok", src=src, dst=dst, amt=amt)   # 커밋 뒤

# 그 밖의 거짓 신호
#  · 재시도 로그를 원인으로 읽기 - 재시도는 결과입니다. 첫 실패를 찾으세요
#  · 재생(replay) 중 다시 찍힌 로그 - LOG 02 의 부수효과 분리가 안 된 경우
#  · 타임스탬프가 어긋나 "결과가 원인보다 먼저" 보이는 줄 (LOG 04)
#  · 복사한 코드가 남긴 남의 이름 - log.info("cache.hit") 인데 실제로는 miss
로그는 코드가 “적기로 한 것”입니다. 코드가 틀리면 로그도 같은 방향으로 틀립니다. 그래서 로그와 독립적인 두 번째 관측(DB 의 실제 값, 상대 시스템의 기록, 고객의 화면)이 없으면 로그 하나로는 사고 조사를 끝낼 수 없습니다.

이렇게도 쓸 수 있다 — 관측자 효과와 로거 자체의 실패 🟡 중급

보는 행위가 대상을 바꿉니다

하이젠버그(Heisenbug) - 로그를 켜면 사라지는 버그
  · 로깅이 타이밍을 바꿔 경쟁 상태가 안 일어납니다
    (I/O 한 번이 마이크로초 단위 경합 창을 덮어 버립니다)
  · DEBUG 를 켜니 GC 압력이 늘어 원래 문제가 다른 문제로 바뀝니다
  · 로그 I/O 가 락 안에서 일어나 락 유지 시간이 늘어납니다 ★ 자주 봅니다

로거가 병목이 되는 순간
  · 동기 로거 + 느린 디스크 - 요청 스레드가 fsync 를 기다립니다
  · 로그 문자열을 만드는 비용 - 호출 자체가 비싼 toString() · 직렬화
    → 레벨을 먼저 확인하고 만듭니다 (isEnabled 가드 · 지연 평가)
  · 락 안의 로깅 - 임계 구역이 I/O 시간만큼 길어집니다

로거가 사고가 되는 순간
  · 로그 라이브러리의 취약점 - 2021년 12월 Log4Shell(CVE-2021-44228):
    로그에 적힌 문자열이 코드로 실행됐습니다. 로거도 입력을 받는 코드입니다
  · 시그널 핸들러 · 인터럽트 안에서의 로깅 - 락을 다시 잡아 교착
  · 로그로 디스크가 차서 DB 가 멈춤 - 로그가 서비스를 죽인 사례는 흔합니다
