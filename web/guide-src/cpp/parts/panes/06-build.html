BUILD 01

컴파일과 링크 — 실제로 무슨 일이

에러 메시지를 읽으려면 어느 단계에서 났는지부터 알아야 합니다. 네 단계만 이해하면 대부분의 빌드 문제가 풀립니다.

네 단계

# ① 전처리 — #include 를 붙여넣고 매크로를 펼칩니다
g++ -E main.cpp -o main.i
wc -l main.i          # 50줄 파일이 <iostream> 하나로 3만 줄이 됩니다

# ② 컴파일 — 어셈블리로
g++ -S main.i -o main.s

# ③ 어셈블 — 오브젝트 파일(.o)로. 아직 실행 못 합니다
g++ -c main.cpp -o main.o
nm -C main.o
#   T main            ← 내가 제공 (Text = 코드)
#   U std::printf     ← 내가 필요로 함 (Undefined) ★

# ④ 링크 — 여러 .o 와 라이브러리를 이어 붙여 실행 파일로
g++ main.o util.o -lpthread -o app
ldd app               # 실행할 때 필요한 공유 라이브러리
왜 나눠서 컴파일하나 — 파일 하나를 고쳤을 때 그 파일만 다시 번역하면 됩니다. 파일이 수백 개인 프로젝트에서 이 차이가 빌드 30초 vs 20분이 됩니다. 빌드 시스템(CMake·Ninja)이 이 의존 관계를 관리해 줍니다.

에러를 단계로 구분하기 ★

메시지단계 · 원인
No such file or directory전처리 — include 경로(-I)
'x' was not declared컴파일 — 선언 누락·오타
invalid conversion컴파일 — 타입 불일치
undefined reference to 'f()'링크 — 정의가 없음 ★
multiple definition of 'f()'링크 — 헤더에 정의를 둠
cannot find -lfoo링크 — 라이브러리 경로(-L)
version GLIBC_2.38 not found실행 — 빌드 환경이 더 최신
error while loading shared libraries실행 — .so 를 못 찾음
구분법 한 줄 — 파일명과 줄 번호가 있으면 컴파일, 없으면 링크입니다. 링크 에러는 코드가 아니라 빌드 구성의 문제라 고쳐야 할 곳이 완전히 다릅니다.

이렇게도 쓸 수 있다 — 링크 에러를 심볼로 추적 🟡 중급

undefined reference 진단 순서

# ① 그 심볼을 '제공하는' 오브젝트가 있는가
nm -C --defined-only build/*.o | grep "함수이름"

# ② 있는데도 안 되면 → 링크 순서 문제 (정적 라이브러리는 순서가 중요) ★
g++ main.o -lfoo -lbar     # foo 가 bar 를 쓰면 이 순서
g++ main.o -lbar -lfoo     # ❌ 실패할 수 있습니다
#   해결: --start-group 으로 감싸기
g++ main.o -Wl,--start-group -lfoo -lbar -Wl,--end-group

# ③ 없으면 → 그 .cpp 를 빌드에 안 넣었거나
#            extern "C" 불일치(🔗 f02)이거나
#            선언과 정의의 시그니처가 미묘하게 다름 (const 유무 등)

# ④ 맹글링된 이름 확인
c++filt _Z3fooi           # → foo(int)
nm -C app | grep foo      # -C 는 복원해서 보여 줍니다

# ⑤ 어떤 라이브러리가 그 심볼을 갖고 있나 (시스템 전체 검색)
for f in /usr/lib/x86_64-linux-gnu/*.so; do
  nm -D "$f" 2>/dev/null | grep -q " T 심볼" && echo "$f"
done

헤더와 라이브러리 찾기

# 컴파일러가 어디를 뒤지는지
g++ -E -x c++ - -v < /dev/null       # include 검색 경로
g++ -print-search-dirs                # 라이브러리 경로

# 어떤 헤더를 실제로 집었는지 (중첩 깊이가 점으로 표시됩니다)
g++ -H -fsyntax-only main.cpp 2>&1 | head -30

# pkg-config — 설치된 라이브러리의 플래그를 알려 줍니다
pkg-config --cflags --libs opencv4
g++ main.cpp $(pkg-config --cflags --libs opencv4)

# 실행 시 .so 를 어디서 찾는지
ldd app
LD_DEBUG=libs ./app 2>&1 | head -20
readelf -d app | grep -E "RPATH|RUNPATH|NEEDED"

# 윈도우
dumpbin /dependents app.exe
dumpbin /exports mylib.dll
이 명령들을 알면 달라지는 것 — 링크 에러 앞에서 추측으로 CMake 를 만지는 사람과 nm 한 번으로 “이 심볼은 어디에도 없다”를 확인하고 원인으로 직행하는 사람의 차이가 여기서 납니다.

효과가 큰 순서대로

cmake -B build -DCMAKE_EXE_LINKER_FLAGS="-fuse-ld=mold"
#   mold > lld > gold > bfd(기본)  순으로 빠릅니다

# ⑥ 헤더 의존성 줄이기 (근본 해결) ★

무엇이 느린지 측정

# 파일별 컴파일 시간
clang++ -ftime-trace -c big.cpp
#   big.json 을 ui.perfetto.dev 에 넣으면 어느 헤더·템플릿이 오래 걸리는지 그림으로

# 전처리 결과 크기로 대략 감 잡기

  echo "$(g++ -E -Iinclude $f 2>/dev/null | wc -l) $f"
done | sort -rn | head

한 단계 더 — 링커가 실제로 하는 일 🧬 전문가

심볼 해석과 재배치

링커의 작업
  ① 각 오브젝트의 심볼 테이블을 읽습니다 (제공 T · 필요 U)
  ② 필요한 심볼을 제공하는 오브젝트를 찾아 연결합니다
  ③ 섹션(.text · .data · .rodata · .bss)을 합칩니다
  ④ 주소를 확정하고 참조를 고쳐 씁니다 (relocation)
  ⑤ 실행 파일 헤더를 만듭니다

정적 라이브러리(.a)는 '오브젝트 묶음'일 뿐입니다
  · 링커는 필요한 오브젝트만 꺼내 씁니다
  · 그래서 순서가 중요합니다 (왼쪽에서 오른쪽으로 훑음)

약한 심볼(W)
  · inline 함수 · 템플릿 인스턴스는 여러 오브젝트에 중복 생성됩니다
  · 링커가 하나만 남기고 나머지를 버립니다 (중복 정의 에러가 안 나는 이유)
  · ★ 단, 모든 정의가 동일해야 합니다 (ODR — 🔬 d01)

확인
  nm -C app | awk '{print $2}' | sort | uniq -c | sort -rn
  size -A app                    # 섹션별 크기
  readelf -S app                 # 섹션 헤더

LTO 와 바이너리 크기

# 링크 시점 최적화 — 번역 단위를 넘어 인라인·제거가 가능해집니다
set(CMAKE_INTERPROCEDURAL_OPTIMIZATION_RELEASE ON)
#   또는 -flto=thin (clang, 훨씬 빠름)

# 효과: 5~20% 성능 향상 · 바이너리 축소
# 대가: 링크 시간이 크게 늘어납니다 → 릴리즈 빌드에만
# 안 쓰는 코드 제거
g++ -ffunction-sections -fdata-sections -c main.cpp
g++ -Wl,--gc-sections main.o -o app
#   함수 단위로 섹션을 나누고, 참조되지 않은 것을 버립니다

# 무엇이 크기를 차지하나
bloaty app -d compileunits,symbols | head -20
nm -C --size-sort -S app | tail -20

# 디버그 심볼 분리 (배포는 작게, 분석은 가능하게) ★
objcopy --only-keep-debug app app.debug
objcopy --strip-debug --add-gnu-debuglink=app.debug app
#   운영에는 app 만 배포하고 app.debug 는 보관 → 크래시 분석 때 사용(🔬 d11)

# 심볼 가시성 (라이브러리에서 특히 중요 — 🔗 f02)
-fvisibility=hidden -fvisibility-inlines-hidden
배포 바이너리의 기본 조합 — -O2 -DNDEBUG -fvisibility=hidden + LTO + 심볼 분리. 이렇게 하면 크기는 작고 성능은 최대이면서 크래시 분석 능력은 유지됩니다.
정리 — 빌드는 전처리 → 컴파일 → 어셈블 → 링크 네 단계입니다. 에러가 나면 줄 번호가 있으면 컴파일, 없으면 링크로 먼저 구분하고, 링크 에러는 nm -C 로 심볼을 직접 확인하세요. 빌드가 느리면 ccache · Ninja · mold 세 줄부터.
BUILD 02

CMake — 실무에 필요한 만큼만

CMake 는 거대하지만, 실제로 쓰는 것은 20줄 남짓입니다. 현대적인 방식(타깃 중심)만 익히면 나머지는 검색으로 충분합니다.

기본 골격

cmake_minimum_required(VERSION 3.20)
project(myproj VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)          # ★ -std=c++20 (gnu++20 아님)

# 라이브러리
add_library(core src/core.cpp src/algo.cpp)
target_include_directories(core
    PUBLIC  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
            $<INSTALL_INTERFACE:include>
    PRIVATE src)                        # src 는 나만 볼 수 있습니다
target_compile_features(core PUBLIC cxx_std_20)

# 실행 파일
add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE core)  # ★ include 경로가 자동으로 따라옵니다

# 경고 켜기 (컴파일러별로)
target_compile_options(core PRIVATE
    $<$<CXX_COMPILER_ID:MSVC>:/W4>
    $<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wall -Wextra -Wpedantic>)

# 테스트
enable_testing()
add_executable(test_core tests/test_core.cpp)
target_link_libraries(test_core PRIVATE core)
add_test(NAME core COMMAND test_core)
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure

PUBLIC · PRIVATE · INTERFACE ★

이 세 키워드가 현대 CMake 의 핵심입니다

  PRIVATE   : 나만 씁니다 (쓰는 쪽에 전파되지 않음)
  PUBLIC    : 나도 쓰고, 나를 링크하는 쪽에도 전파됩니다
  INTERFACE : 나는 안 쓰고, 링크하는 쪽에만 전파됩니다
              (헤더 전용 라이브러리)

예시
  target_link_libraries(core
      PUBLIC  fmt::fmt        # core 의 '헤더'가 fmt 를 쓴다 → 전파 필요
      PRIVATE zlib)           # core 의 '.cpp' 만 zlib 을 쓴다 → 감춤

  → app 은 fmt 를 자동으로 쓸 수 있지만 zlib 은 모릅니다 ★

★ 옛 방식은 쓰지 마세요 (전역 변수처럼 동작해 관리가 안 됩니다)
  include_directories()      → target_include_directories()
  link_libraries()           → target_link_libraries()
  add_definitions()          → target_compile_definitions()
  set(CMAKE_CXX_FLAGS ...)   → target_compile_options()
“타깃이 모든 것을 안다”가 현대 CMake 의 철학입니다. 타깃에 붙여 두면 링크하는 쪽이 아무것도 몰라도 include 경로·컴파일 옵션·의존성이 전부 따라옵니다.

이렇게도 쓸 수 있다 — 자주 쓰는 조각들 🟡 중급

조건 분기와 옵션

# 플랫폼별
if(WIN32)
    target_link_libraries(core PRIVATE ws2_32)
elseif(APPLE)
    target_link_libraries(core PRIVATE "-framework CoreFoundation")
else()
    target_link_libraries(core PRIVATE pthread dl)
endif()

# 제너레이터 표현식 — 빌드 타입별 (설정 시점이 아니라 빌드 시점에 평가)
target_compile_definitions(core PRIVATE
    $<$<CONFIG:Debug>:MYLIB_DEBUG>
    $<$<CONFIG:Release>:NDEBUG>)

# 사용자 옵션
option(MYLIB_BUILD_TESTS "테스트 빌드" ON)
option(MYLIB_USE_SIMD    "SIMD 사용"  ON)
if(MYLIB_BUILD_TESTS)
    add_subdirectory(tests)
endif()

# 버전 정보를 코드에 주입 ★
target_compile_definitions(core PRIVATE
    MYLIB_VERSION="${PROJECT_VERSION}"
    MYLIB_COMMIT="$ENV{GIT_COMMIT}")

# 설정 파일 생성 (더 깔끔한 방법)
configure_file(config.h.in config.h @ONLY)
target_include_directories(core PRIVATE ${CMAKE_CURRENT_BINARY_DIR})

빌드 타입

  -O2 + LTO       -O2 대비 5~20% 추가
  -Ofast          부동소수 규칙을 깨므로 결과가 달라질 수 있습니다 ⚠

// ⚠ 그래서 이런 코드는 위험합니다

    do { if (!(cond)) throw std::logic_error(msg); } while (0)

//   MSVC : Debug 빌드에서 반복자 검사가 기본으로 켜집니다 (느립니다)
//   libstdc++ : -D_GLIBCXX_DEBUG 로 켜기 ★ 개발 중에 유용
//   libc++    : -D_LIBCPP_ENABLE_ASSERTIONS=1
//   → v[100] 같은 범위 초과를 UB 대신 명확한 에러로 잡아 줍니다

        -D_FORTIFY_SOURCE=3 -fstack-protector-strong>)

# 모든 타깃에 붙이기

target_link_libraries(app  PRIVATE project_options)

# Sanitizer 도 같은 방식으로 (b10)

target_link_options(project_asan INTERFACE -fsanitize=address,undefined)
이 패턴을 쓰면 새 타깃을 추가할 때 target_link_libraries(new_target PRIVATE project_options) 한 줄이면 모든 규칙이 자동으로 적용됩니다. 플래그를 여러 곳에 복사하다 어긋나는 문제가 사라집니다.

CI — 태그를 붙이면 배포까지

C++ 프로젝트에서 CI 는 선택이 아닙니다. 세 OS · 두 컴파일러 · Sanitizer 를 사람이 매번 돌릴 수는 없습니다.

CI 가 해야 할 다섯 가지

① 빌드 — 세 OS × GCC·Clang·MSVC
   컴파일러마다 잡아 주는 경고가 다릅니다 (무료 정적 분석)

② 테스트 — ctest · 파이썬·Node 바인딩 테스트까지

⑤ 배포 — 태그가 붙으면 wheel·npm·릴리스 아티팩트 생성

★ 실행 시간이 걱정된다면
   PR 에서는 ①②(리눅스만) → 빠른 피드백

동적 · 정적 링크와 배포 의존성

“내 PC 에선 되는데 배포하면 .so 를 못 찾습니다” — C++ 배포에서 가장 흔한 문제이고, 원인은 몇 가지뿐입니다.

정적 vs 동적

정적 (.a · .lib)동적 (.so · .dll)
배포파일 하나 ★함께 배포 필요
크기큼작음(공유)
시작 시간빠름로딩·재배치 비용
보안 패치재빌드 필요 ★파일만 교체
메모리프로세스마다여러 프로세스 공유
최적화LTO 가능제한적
심볼 충돌적음가능(🔗 f02)
add_library(core STATIC ...)     # .a / .lib
add_library(core SHARED ...)     # .so / .dll / .dylib
add_library(core ...)            # BUILD_SHARED_LIBS 를 따름

# 부분적으로 정적 — C++ 런타임만 (호환성 문제 해결) ★
target_link_options(app PRIVATE -static-libstdc++ -static-libgcc)
확장 모듈·배포용 도구는 정적 링크가 대개 낫습니다 — 파일 하나로 완결되어 “의존성이 없다”는 상태가 만들어집니다. 시스템 라이브러리로 배포할 때만 동적이 유리합니다.

런타임에 라이브러리를 찾는 순서

리눅스
  ① DT_RPATH (구식)
  ② LD_LIBRARY_PATH 환경변수
  ③ DT_RUNPATH        ★ 현대적 방식
  ④ /etc/ld.so.cache  (ldconfig 로 갱신)
  ⑤ /lib · /usr/lib

맥

C++ ABI 호환성

같은 문제의 다른 형태 — libstdc++ 버전

  GCC 5 에서 std::string 의 ABI 가 바뀌었습니다 (_GLIBCXX_USE_CXX11_ABI)
  → 옛 ABI 로 빌드된 라이브러리와 새 ABI 코드를 링크하면
    undefined reference to std::__cxx11::basic_string...  ★

확인
  nm -DC libfoo.so | grep __cxx11 | head
  strings libfoo.so | grep GLIBCXX

해결
  · 모든 것을 같은 컴파일러·같은 표준 라이브러리로 빌드
  · 또는 -D_GLIBCXX_USE_CXX11_ABI=0 으로 맞추기 (옛 라이브러리에 맞춤)
  · 근본 해결: 경계를 C ABI 로 (🔗 f01) ★
    → C++ 타입을 인터페이스에 노출하지 않으면 이 문제가 사라집니다

★ 그래서 배포용 라이브러리는 C API 로 만드는 것이 정석입니다.
  파이썬·Node 확장도 각 런타임의 안정 ABI(abi3 · N-API)를 쓰는 이유가 같습니다.
이 절의 결론 — 배포 대상보다 오래된 환경에서 빌드하고, C++ 런타임은 정적으로, 공개 인터페이스는 C ABI 로. 이 셋이면 리눅스 배포 문제의 대부분이 사라집니다.

Sanitizer — 버그를 자동으로 잡습니다

플래그 하나면 메모리 오류·미정의 동작·데이터 경쟁을 정확한 줄 번호와 함께 잡아 줍니다. C++ 를 안전하게 쓰는 가장 실용적인 방법입니다.

세 가지 Sanitizer

# ① AddressSanitizer — 메모리 오류 ★ 가장 중요
g++ -fsanitize=address -g -O1 main.cpp -o app
#   잡는 것: 버퍼 오버런 · 해제 후 사용 · 이중 해제 · 누수 · 스택 오버플로
#   비용: 실행 2배 느림 · 메모리 3배

# ② UndefinedBehaviorSanitizer — UB
g++ -fsanitize=undefined -g main.cpp -o app
#   잡는 것: 정수 오버플로 · 널 역참조 · 정렬 위반 · 잘못된 형변환
#   비용: 거의 없음 (20% 내외) ★ 항상 켜도 됩니다

# ③ ThreadSanitizer — 데이터 경쟁
g++ -fsanitize=thread -g -O1 main.cpp -o app
#   잡는 것: 락 없는 동시 접근 · 교착 가능성
#   비용: 5~15배 느림 · 메모리 5~10배
#   ⚠ ASan 과 동시에 못 씁니다 (별도 빌드)

# 조합 (실무 권장)
-fsanitize=address,undefined -fno-omit-frame-pointer -g -O1
UBSan 은 비용이 거의 없습니다 — 개발 빌드에는 항상 켜 두는 것을 권합니다. 정수 오버플로처럼 조용히 잘못된 결과를 내는 문제를 바로 알려 줍니다.

    target_link_options(sanitizers INTERFACE -fsanitize=thread)

한 단계 더 — Sanitizer 는 어떻게 잡아내나 🧬 전문가

ASan 의 원리 — 그림자 메모리

① 컴파일러가 모든 메모리 접근 앞에 검사 코드를 넣습니다
② 실행 시 '그림자 메모리'를 유지합니다
   실제 메모리 8바이트 → 그림자 1바이트로 상태를 기록
   (접근 가능 / 레드존 / 해제됨 …)
③ 할당된 영역 주위에 '레드존'을 둡니다
   → 조금만 벗어나도 즉시 감지 ★
④ 해제된 메모리는 '격리 구역'에 일정 시간 보관
   → 해제 후 사용을 잡을 수 있습니다

그래서
  · 메모리 3배 사용 (그림자 + 레드존 + 격리)
  · 실행 2배 느림 (검사 코드)
  · 정확한 위치와 할당 스택까지 알려 줍니다

한계
  · 검사 코드가 들어간 부분만 감지합니다
    → 서드파티 .so 안의 버그는 못 잡습니다 (같이 빌드해야 함)
  · 레드존을 크게 넘어가는 접근은 놓칠 수 있습니다
  · 논리 오류는 대상이 아닙니다
