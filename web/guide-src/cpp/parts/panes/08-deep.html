DEEP 01

번역 단위 · ODR · 링커

진단 없이 조용히 메모리가 깨지는 유일한 규칙 위반이 ODR 입니다. 링크는 성공하는데 실행이 이상하다면 여기를 의심해야 합니다.

하나의 정의 규칙(ODR)

규칙
  · 함수·변수의 '정의'는 프로그램 전체에서 정확히 하나여야 합니다
  · 클래스·inline 함수·템플릿은 여러 번역 단위에 나와도 되지만
    ★ 모든 정의가 '완전히 동일'해야 합니다
  · 어기면 ill-formed, no diagnostic required
    → 컴파일러도 링커도 알려 주지 않고, 실행이 이상해집니다 ★

왜 중복이 허용되나
  헤더에 클래스 정의를 두면 그것을 포함한 모든 .cpp 에 생깁니다.
  링커는 '약한 심볼(W)'로 표시된 것 중 하나만 남기고 버립니다.
  → 남은 하나가 '어느 것'인지는 정해져 있지 않습니다 ★
# 심볼 종류 확인
nm -C build/core.o
#   T  텍스트(코드) — 이 파일이 정의
#   W  약한 심볼 — inline·템플릿 (중복 허용, 하나만 남김)
#   U  미정의 — 다른 곳에서 와야 함
#   t  소문자 = 내부 링키지 (static · 익명 namespace)
#   B/D  BSS/데이터 — 전역 변수

실제로 나는 사고 ★

// ① 빌드 플래그가 달라 구조체 크기가 달라지는 경우
// a.cpp 는 -DUSE_EXTRA 로, b.cpp 는 없이 컴파일
struct Cfg {
    int a;
#ifdef USE_EXTRA
    int b;                  // ★ 한쪽에만 있습니다
#endif
};
//   → 링크는 성공하고, 실행 중에 메모리가 밀려 깨집니다
//     원인 추적이 극악입니다

// ② 표준 라이브러리 디버그 모드 불일치
// a.cpp: -D_GLIBCXX_DEBUG   b.cpp: 없음
//   → std::vector 의 내부 구조가 달라집니다 → 크래시

// ③ 서로 다른 라이브러리가 같은 이름의 클래스를 정의
namespace { }               // ✅ 익명 namespace 로 격리하세요
static void helper();       // ✅ 또는 static

// ④ inline 함수를 두 헤더에 다르게 정의
// v1.h: inline int f() { return 1; }
// v2.h: inline int f() { return 2; }
//   → 어느 것이 남을지 모릅니다
파이썬·Node 확장에서 특히 위험합니다 — 같은 프로세스에 여러 확장이 로드되고, 서로 다른 버전의 같은 라이브러리를 정적 링크했다면 심볼이 섞일 수 있습니다. 가시성을 hidden 으로 두는 이유입니다(🔗 f02).

이렇게도 쓸 수 있다 — 링커가 하는 일 🟡 중급

심볼 해석 과정

① 각 오브젝트의 심볼 테이블을 읽습니다 (제공 T · 필요 U)
② 필요한 심볼을 제공하는 오브젝트를 찾아 연결합니다
③ 섹션(.text · .data · .rodata · .bss)을 합칩니다
④ 주소를 확정하고 참조를 고쳐 씁니다 (relocation)
⑤ 실행 파일 헤더를 만듭니다

★ 정적 라이브러리(.a)는 '오브젝트 묶음'일 뿐입니다
  · 링커는 필요한 오브젝트만 꺼내 씁니다
  · 왼쪽→오른쪽으로 훑으므로 순서가 중요합니다 (🛠️ b01)
  · 이미 지나간 라이브러리는 다시 안 봅니다
    → g++ main.o -lfoo -lbar (foo 가 bar 를 쓰면 이 순서)
    → 순환 의존이면 -Wl,--start-group ... --end-group

약한 심볼과 강한 심볼
  · inline·템플릿 = 약한 심볼 → 중복 허용, 하나만 채택
  · 일반 함수 = 강한 심볼 → 중복이면 multiple definition 에러
  · 강한 것이 약한 것을 이깁니다 (라이브러리 함수를 덮어쓸 때 이용)

ODR 위반 찾기

# ① LTO 를 켜면 링커가 타입 불일치를 잡아 주기도 합니다 ★
g++ -flto -O2 *.cpp
#   warning: type of 'f' does not match original declaration

# ② gold/lld 의 ODR 검사
g++ -fuse-ld=gold -Wl,--detect-odr-violations

# ③ ASan 은 전역 변수 ODR 위반을 잡습니다
g++ -fsanitize=address ...
#   ERROR: AddressSanitizer: odr-violation

# ④ 심볼 크기 비교 — 같은 심볼인데 크기가 다르면 의심
nm -S --defined-only a.o b.o | sort -k3 | awk '{print $2, $3}' | uniq -d

# ⑤ 근본 대책 ★
#   · 빌드 플래그로 구조체 내용을 바꾸지 않기
#   · 모든 번역 단위에 같은 플래그 (CMake 로 통일 — 🛠️ b04)
#   · 내부 심볼은 익명 namespace 로
#   · 공개 헤더에 서드파티 타입을 노출하지 않기 (🛠️ b03)

# 확인 — 어떤 플래그로 컴파일됐는지
readelf -p .comment build/core.o
strings build/app | grep "GCC:"

실무에선 이렇게 — 심볼 충돌 관리 🔴 실무

같은 프로세스에 여러 라이브러리

전형적인 사고

  파이썬 프로세스
    ├─ 확장 A (libfmt 10.0 정적 링크)
    └─ 확장 B (libfmt 11.0 정적 링크)

  기본 가시성이면 두 확장의 fmt 심볼이 전역에 노출됩니다.
  → 먼저 로드된 쪽이 나중 것을 가립니다 (전역 심볼 인터포지션)
  → B 가 A 의 fmt 10.0 코드를 부르게 됩니다
  → 헤더는 11.0 인데 구현은 10.0 → ODR 위반 → 조용한 손상 ★

대책
  ① 가시성을 hidden 으로 (🔗 f02) ★ 가장 중요
     CXX_VISIBILITY_PRESET hidden
  ② dlopen 시 RTLD_LOCAL (기본값)
  ③ 의존성을 동적으로 공유 (버전 통일)
  ④ 내부 namespace 로 격리
     일부 라이브러리가 제공: FMT_BEGIN_NAMESPACE 등
  ⑤ 링커 버전 스크립트로 내보낼 심볼 명시 (🔗 f02)

검증하기

# 내 확장이 무엇을 내보내는지 — 최소여야 합니다 ★
nm -D --defined-only build/_core.so | grep " T " | wc -l
#   pybind11 확장이면 PyInit_ 하나만 나와야 이상적입니다

nm -D --defined-only build/_core.so | grep " T " | head
#   fmt · nlohmann 같은 것이 보이면 가시성 설정이 안 된 것 ★

# 두 라이브러리가 같은 심볼을 내보내는지
nm -DC --defined-only libA.so libB.so | grep " T " \
  | awk '{print $3}' | sort | uniq -d | head

# 실행 시 어느 것이 선택됐는지
LD_DEBUG=bindings python -c "import mymod" 2>&1 | grep fmt

# CI 에 넣을 검사
test $(nm -D --defined-only _core.so | grep -c " T ") -le 2 \
  || { echo "내보내는 심볼이 너무 많습니다"; exit 1; }
확장 모듈의 심볼 수를 CI 로 지키세요 — PyInit_ 하나만 내보내는 것이 이상적입니다. 늘어났다면 가시성 설정이 깨졌다는 신호이고, 나중에 재현 불가능한 버그로 돌아옵니다.

한 단계 더 — 인라인과 링키지의 정확한 규칙 🧬 전문가

무엇이 어디에 있어야 하나

// 외부 링키지 (다른 번역 단위에서 보임)
void f();                    // 선언
void f() { }                 // 정의 — 한 곳에만 ★
extern int g;                // 선언
int g = 0;                   // 정의 — 한 곳에만

// 내부 링키지 (이 파일 전용)
static void h() { }          // C 스타일
namespace { void h2() { } }  // C++ 권장 ★
const int k = 1;             // ★ const 는 기본이 내부 링키지 (C++)
constexpr int m = 2;         // 마찬가지

// inline — "중복 정의를 허용하라"는 링커 지시 (탭 1 x09)
inline void i() { }          // 헤더에 정의 가능
inline int counter = 0;      // C++17 인라인 변수 ★

// 템플릿 — 암묵적으로 inline 과 같은 취급
template<class T> void t(T) { }     // 헤더에 정의

// 클래스 안에 정의한 멤버 함수는 자동으로 inline
struct S { void f() { } };   // inline

// ⚠ 헤더에 이것을 두면 multiple definition
int bad = 0;                 // ❌ 각 .cpp 에 별도 정의가 생깁니다
inline int ok = 0;           // ✅
extern int decl;             // ✅ 선언만, 정의는 .cpp 에

정적 초기화 순서 문제

// ★ 서로 다른 번역 단위의 전역 객체 초기화 순서는 정해져 있지 않습니다
// a.cpp
Logger g_logger;                     // b.cpp 의 g_config 를 씁니다
// b.cpp
Config g_config;
//   → g_config 가 아직 초기화 안 됐을 수 있습니다 (크래시 또는 쓰레기 값)

// ✅ 해법 ① 함수 안 static (첫 호출 때 초기화 · 스레드 안전) ★
Config& config() {
    static Config c;                 // C++11 부터 스레드 안전 보장
    return c;
}
Logger& logger() {
    static Logger l{config()};       // 순서가 보장됩니다
    return l;
}

// ✅ 해법 ② constinit (C++20) — 컴파일 시점 초기화를 강제
constinit static int g_count = 0;    // 동적 초기화면 컴파일 에러

// ⚠ 소멸 순서도 문제입니다 (생성의 역순, 하지만 TU 간에는 불명확)
//   → 함수 안 static 은 프로그램 종료 시 역순으로 소멸됩니다
//   → 소멸자에서 다른 전역을 쓰면 이미 파괴됐을 수 있습니다 (static destruction order fiasco)
//   → 정말 필요하면 의도적으로 누수시키는 방법도 씁니다
Logger& logger() {
    static Logger* p = new Logger{};  // 일부러 delete 안 함
    return *p;
}
확장 모듈에서 자주 겪습니다 — 라이브러리 로드 시점에 전역 생성자가 실행되는데, 그 안에서 파이썬 API 를 부르거나 다른 라이브러리를 쓰면 초기화 순서 문제가 생깁니다. 지연 초기화(함수 안 static)가 안전합니다.
정리 — ODR 위반은 진단 없이 조용히 깨지는 유일한 규칙 위반입니다. 모든 번역 단위에 같은 플래그, 내부 심볼은 익명 namespace, 가시성은 hidden — 이 셋으로 대부분 예방됩니다. 전역 객체는 함수 안 static 으로 두세요.
DEEP 02

UB — 왜 그렇게 위험한가

“동작이 정의되지 않음”은 틀린 값이 나오는 정도가 아닙니다. 코드가 통째로 사라지거나 시간 여행처럼 앞선 코드가 영향을 받습니다.

최적화와 만나면

// 컴파일러의 대전제: "이 프로그램에 UB 는 없다"
// → UB 를 일으키는 경로는 '실행되지 않는다'고 가정하고 최적화합니다

// ① 널 체크가 사라집니다 (탭 1 x05)
void f(int* p) {
    int x = *p;              // ① 역참조 → "p 는 널이 아니다"
    if (!p) return;          // ② 그러므로 항상 거짓
    use(x);                  // ③ → 검사가 통째로 삭제 ★
}

// ② 오버플로 검사가 사라집니다
if (n + 1 < n) { /* 오버플로 처리 */ }
//   부호 있는 오버플로는 UB → "일어날 리 없다" → 조건이 거짓 → 삭제

// ③ 무한 루프가 제거됩니다
while (true) { }             // 부수효과 없는 무한 루프는 UB
//   → 컴파일러가 통째로 없애고 다음 코드로 흘러갈 수 있습니다

// ④ 시간 여행 — UB 이후가 아니라 '이전' 코드도 영향받습니다 ★
printf("시작\n");            // 이 출력이 안 나올 수 있습니다
*(int*)nullptr = 1;          // UB
//   컴파일러는 UB 에 도달하는 경로 전체를 자유롭게 다룰 수 있습니다
“Release 에서만 터진다”의 정체 — 컴파일러 버그가 아니라 내 코드의 UB 입니다. Debug 에서는 최적화가 없어 우연히 의도대로 동작했을 뿐입니다.

이렇게도 쓸 수 있다 — UB 를 피하는 습관 🟡 중급

안전한 대안

// ① 정수 오버플로 — 미리 검사하거나 안전한 함수
#include <numeric>
if (a > INT_MAX - b) { /* 넘칠 상황 */ }
int r;
if (__builtin_add_overflow(a, b, &r)) { /* 오버플로 */ }   // GCC·Clang
//   C++26 에는 표준 함수가 들어옵니다

// 부호 없는 정수는 랩어라운드가 '정의'되어 있습니다 (UB 아님)
unsigned u = UINT_MAX; ++u;      // 0 — 정의된 동작

// ② 타입 재해석 — bit_cast (탭 1 x05)
float f = 1.0f;
int i = std::bit_cast<int>(f);   // ✅ C++20 · UB 아님 · 비용 0
int j = *(int*)&f;                // ❌ strict aliasing 위반
std::memcpy(&j, &f, 4);           // ✅ 예전부터 쓰던 합법적 방법

// ③ 범위 접근
v.at(i);                          // 예외를 던짐
if (i < v.size()) v[i];           // 검사 후
std::span sp{v}; sp[i];           // 디버그 빌드에서 검사되기도

// ④ 부호 비교 (탭 1 x02)
std::cmp_less(i, v.size());       // C++20 · 수학적으로 올바른 비교

// ⑤ 정렬 — memcpy 로 안전하게
Header h;
std::memcpy(&h, buf, sizeof h);   // ✅ 컴파일러가 최적화로 없애 줍니다

strict aliasing — 가장 미묘한 것

// 규칙: 객체를 '그 타입이 아닌 타입'으로 접근하면 UB
//   예외: char · unsigned char · std::byte 는 무엇이든 볼 수 있습니다

// ❌ 전형적인 위반
float f = 1.0f;
unsigned bits = *(unsigned*)&f;        // UB
//   컴파일러는 float* 와 unsigned* 가 다른 객체를 가리킨다고 가정합니다
//   → 쓰기와 읽기 순서를 자유롭게 바꿀 수 있습니다

// ❌ union 으로 타입 재해석 (C 에서는 합법, C++ 에서는 UB)
union U { float f; unsigned u; };
U x; x.f = 1.0f; use(x.u);             // ⚠ 실제로는 대부분 동작하지만 표준상 UB

// ✅ 합법적인 방법
std::bit_cast<unsigned>(f);            // C++20
std::memcpy(&bits, &f, sizeof bits);

// 진단이 어려운 이유
//   · Sanitizer 가 잘 못 잡습니다
//   · -O0 에서는 증상이 안 나옵니다
//   · -fno-strict-aliasing 을 켜면 증상이 사라집니다 ← 이것이 단서 ★

// 확인
g++ -O2 -Wstrict-aliasing=2 main.cpp
g++ -O2 -fno-strict-aliasing main.cpp   // 증상이 사라지면 위반입니다
바이너리 데이터를 다룬다면 꼭 알아야 합니다 — 네트워크 패킷·파일 포맷을 구조체로 캐스팅해 읽는 코드가 가장 흔한 위반입니다. memcpy 로 바꾸세요 — 컴파일러가 최적화로 없애 주므로 비용도 없습니다.

실무에선 이렇게 — UB 를 관리하기 🔴 실무

방어 체계 4중

  • ① 경고를 전부 켜고 에러로 — -Wall -Wextra -Werror. 컴파일러가 잡아 주는 것이 가장 쌉니다
  • ② Sanitizer 를 CI 에(🛠️ b10) — ASan·UBSan·TSan. UB 대응의 핵심입니다 ★
  • ③ 정적 분석 — clang-tidy·cppcheck. 실행하지 않고 잡히는 것들
  • ④ 표준 라이브러리 검사 모드 — -D_GLIBCXX_ASSERTIONS(가벼움, 릴리즈에도 가능), -D_GLIBCXX_DEBUG(무겁지만 철저)
  • ⑤ 퍼징 — 파서가 있다면 반드시(🛠️ b10)
# 릴리즈에도 켤 만한 가벼운 보호 (🛠️ b04)
-D_FORTIFY_SOURCE=3 -fstack-protector-strong -D_GLIBCXX_ASSERTIONS
#   비용 1% 미만으로 상당수의 오버런을 런타임에 잡습니다 ★

# 정수 오버플로를 정의된 동작으로 (표준은 아니지만 실용적)
-fwrapv          # 부호 있는 오버플로를 랩어라운드로
-ftrapv          # 오버플로 시 중단

증상의심
Debug 는 되고 Release 만 실패UB ★ UBSan 먼저
-O0 은 되고 -O2 실패UB · aliasing
-fno-strict-aliasing 으로 해결aliasing 위반

“컴파일러를 업그레이드했더니 코드가 깨졌다” — 거의 항상 원래 있던 UB 가 드러난 것입니다. 새 컴파일러가 더 공격적으로 최적화하면서 이전에는 우연히 동작하던 것이 무너집니다.

한 단계 더 — UB 를 직접 관찰하기 🧬 전문가

코드가 사라지는 것을 보기

// godbolt.org 에 붙여넣고 -O2 어셈블리를 보세요
int f(int* p) {
    int x = *p;
    if (p == nullptr) return -1;     // ★ 이 검사가 사라집니다
    return x;
}
//   -O0: cmp / je 가 보입니다
//   -O2: 검사가 통째로 없어지고 mov eax, [rdi]; ret 만 남습니다

bool overflow_check(int n) {
    return n + 1 < n;                // ★ 항상 false 로 접힙니다
}
//   -O2: xor eax, eax; ret   (그냥 0 반환)

// 반대로 부호 없는 것은 살아남습니다
bool ok(unsigned n) { return n + 1 < n; }   // 랩어라운드가 정의됨 → 검사 유지

// 무한 루프
int g() { while (true) { } }
//   부수효과가 없으면 UB → 컴파일러가 제거할 수 있습니다
//   (실제로 clang 은 함수를 비우기도 합니다)

언어가 나아가는 방향

C++ 는 UB 를 줄이는 쪽으로 움직이고 있습니다

  C++20  · 부호 있는 정수를 2의 보수로 확정
         · std::bit_cast 로 안전한 재해석
         · constinit 로 초기화 순서 문제 완화
  C++23  · 일부 UB 를 erroneous behavior 로 재분류
         · std::start_lifetime_as (버퍼를 객체로 안전하게)
  C++26  · 초기화되지 않은 읽기를 erroneous 로 (진단 가능) ★
         · 계약(contracts) — 사전·사후 조건을 언어로

erroneous behavior 란
  · 여전히 잘못됐지만 '진단 가능'하고
  · 컴파일러가 그것을 근거로 최적화하지 않습니다
  · 즉 "코드가 사라지는" 종류의 사고가 줄어듭니다 ★

그래도
  · 포인터·수명·경쟁 관련 UB 는 남습니다
  · 그래서 Rust 같은 언어가 주목받는 것이고(🦀 가이드)
  · C++ 에서는 Sanitizer 와 정적 분석이 계속 중요합니다
실무적 결론 — UB 목록을 외우는 것보다 Sanitizer 를 항상 켜 두는 습관이 훨씬 효과적입니다. 그리고 “Release 에서만 실패”를 만나면 UBSan 부터 돌리세요.
정리 — UB 는 틀린 값이 나오는 것이 아니라 코드가 사라지는 것입니다. 컴파일러는 “UB 는 없다”를 전제로 최적화하기 때문입니다. Debug 는 되고 Release 만 실패하면 컴파일러 버그가 아니라 UB 이고, -fsanitize=undefined 가 대개 그 자리를 짚어 줍니다.
DEEP 03

객체 수명과 aliasing

“메모리가 있다”와 “객체가 살아 있다”는 다른 이야기입니다. 이 구분이 바이너리 데이터를 다룰 때 미묘한 버그를 만듭니다.

객체의 수명

// 객체 수명은 '생성자가 끝날 때 시작 · 소멸자가 시작될 때 끝'
// 그 밖에서 접근하면 UB 입니다

// ① 소멸 후 접근
{
    Widget w;
    Widget* p = &w;
}   // w 소멸
// *p 접근 → UB (ASan 이 잡습니다)

// ② 생성 전 접근 — 기반 클래스 생성자에서 가상 함수
struct Base {
    Base() { init(); }               // ⚠ 파생 클래스 부분이 아직 없습니다
    virtual void init() { }
};
struct Derived : Base {
    std::vector<int> v;
    void init() override { v.push_back(1); }   // ★ v 가 아직 생성 전 → UB
};
//   생성자·소멸자 안에서 가상 함수는 '그 클래스의 버전'이 불립니다

// ③ 원시 메모리를 객체로 다루기 — placement new 가 필요합니다
alignas(Widget) std::byte buf[sizeof(Widget)];
Widget* p = new (buf) Widget{};      // ★ 여기서 객체 수명이 시작됩니다
p->~Widget();                        // 명시적 소멸

// ④ 버퍼를 구조체로 '그냥 캐스팅'하면 객체가 없습니다
Header* h = reinterpret_cast<Header*>(buf);   // ⚠ 엄밀히는 UB
h->field;                                      // 객체가 생성된 적이 없음
//   ✅ memcpy 로 복사하거나 (탭 1 x05)
Header h2; std::memcpy(&h2, buf, sizeof h2);
//   ✅ C++23 std::start_lifetime_as<Header>(buf)

실무에서 부딪히는 지점

// 네트워크 패킷·파일 포맷 파싱 — 가장 흔한 자리 ★
struct PacketHeader {
    std::uint32_t magic;
    std::uint16_t version;
    std::uint16_t length;
};
static_assert(std::is_trivially_copyable_v<PacketHeader>);
static_assert(sizeof(PacketHeader) == 8);

// ❌ 캐스팅 — aliasing 위반 + 정렬 문제 + 객체 수명
auto* h = reinterpret_cast<const PacketHeader*>(buffer);

// ✅ memcpy — 안전하고, 컴파일러가 최적화로 없애 줍니다
PacketHeader h;
if (buffer.size() < sizeof h) return error();
std::memcpy(&h, buffer.data(), sizeof h);

// ✅ 필드 단위로 읽기 (엔디언까지 처리 · 정렬 무관) ★
std::uint32_t read_u32_le(const std::byte* p) {
    return std::uint32_t(p[0]) | (std::uint32_t(p[1]) << 8)
         | (std::uint32_t(p[2]) << 16) | (std::uint32_t(p[3]) << 24);
}
//   컴파일러가 대개 단일 mov 명령으로 최적화합니다

// C++23
auto* h3 = std::start_lifetime_as<PacketHeader>(buffer.data());
실제로 대부분의 코드가 캐스팅을 씁니다 — 그리고 대개 동작합니다. 다만 정렬이 다른 아키텍처(ARM)나 공격적 최적화에서 깨집니다. memcpy 는 비용이 없으니 쓰지 않을 이유가 없습니다.

이렇게도 쓸 수 있다 — 수명을 다루는 도구 🟡 중급

placement new 와 수동 관리

// 컨테이너·optional·variant 가 내부적으로 쓰는 기법
template<class T>
class SmallOpt {
    alignas(T) std::byte storage_[sizeof(T)];
    bool has_ = false;
public:
    template<class... A>
    T& emplace(A&&... a) {
        reset();
        T* p = new (storage_) T(std::forward<A>(a)...);   // ★ 수명 시작
        has_ = true;
        return *p;
    }
    void reset() {
        if (has_) { std::launder(reinterpret_cast<T*>(storage_))->~T(); has_ = false; }
    }
    T& operator*() {
        return *std::launder(reinterpret_cast<T*>(storage_));   // ★ launder
    }
    ~SmallOpt() { reset(); }
};

// std::launder (C++17) — "여기 새 객체가 생겼다"고 컴파일러에 알림
//   객체를 파괴하고 같은 자리에 새로 만들었을 때 필요합니다
//   (컴파일러가 옛 객체의 정보를 계속 쓰는 것을 막습니다)

// 실무에서는 직접 만들지 마세요
std::optional<T> · std::variant<...> · std::vector 를 쓰면 됩니다 (탭 2 m10)

restrict — aliasing 을 알려 주기

// 컴파일러는 두 포인터가 겹칠 수 있다고 가정합니다 (⚡ e06)
void add(double* out, const double* a, const double* b, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i) out[i] = a[i] + b[i];
}
//   out 과 a 가 같을 수 있으므로 매 반복마다 다시 로드해야 합니다
//   → 벡터화 실패

// __restrict 로 "겹치지 않는다"고 약속
void add(double* __restrict out,
         const double* __restrict a,
         const double* __restrict b, std::size_t n);
//   ★ 표준은 아니지만 gcc·clang·msvc 모두 지원합니다
//   ⚠ 약속을 어기면 UB — 실제로 겹치는 포인터를 넘기면 결과가 틀립니다

// 확인 — 어셈블리에서 vaddpd 가 나오는지 (⚡ e09)
// g++ -O3 -fopt-info-vec-optimized add.cpp

// 타입이 다르면 컴파일러가 이미 겹치지 않는다고 가정합니다 (strict aliasing)
void f(int* i, float* f);      // 서로 다른 타입 → 겹칠 수 없다고 가정
//   ★ 그래서 타입 재해석이 위험한 것입니다 (d02)
파이썬 확장에서 유용합니다 — numpy 배열 두 개를 받아 하나에 쓰는 함수라면 __restrict 를 붙이는 것만으로 벡터화가 걸려 2~4배가 나올 수 있습니다. 다만 같은 배열을 입력과 출력으로 넘기지 못하게 문서에 명시하세요.

실무에선 이렇게 — 수명 버그를 구조로 막기 🔴 실무

규칙으로 예방하기

  • 소유는 unique_ptr·컨테이너, 원시 포인터는 빌려 보기만(탭 2 m02)
  • 참조·string_view·span 은 인자 전용 — 멤버로 보관하지 않기(탭 2 m11)
  • 컨테이너 재할당 후 포인터·반복자 무효 — 인덱스를 보관(탭 2 m05)
  • 생성자·소멸자에서 가상 함수 호출 금지
  • 비동기·스레드에는 값 캡처(탭 2 m07)
  • C API 경계에서는 수명을 문서화(🔗 f07)
// 도구로 잡기

//   bugprone-dangling-handle
//   bugprone-use-after-move
//   cppcoreguidelines-owning-memory

clang++ -Wlifetime -Wdangling-gsl main.cpp

// GCC

한 단계 더 — 포인터 프로버넌스 🧬 전문가

포인터는 주소만이 아닙니다

// 표준은 포인터에 '어느 객체에서 유래했는가'(provenance)를 부여합니다
int a[10], b[10];
int* p = a + 10;            // ✅ 마지막 다음까지는 합법
int* q = b;
if (p == q) {               // 주소는 같을 수 있지만
    *p;                     // ❌ p 로는 b 에 접근할 수 없습니다 (UB)
}

// 정수로 왕복하면 프로버넌스를 잃습니다
std::uintptr_t addr = reinterpret_cast<std::uintptr_t>(ptr);
int* p2 = reinterpret_cast<int*>(addr);
//   구현 정의 — 대부분 동작하지만 표준상 보장이 약합니다
//   최적화가 "이 포인터는 어디서 왔는지 모른다"고 판단해
//   보수적으로 처리하거나, 반대로 잘못 가정할 수 있습니다

// 포인터 태깅 (하위 비트에 정보 넣기) — 흔한 기법이지만 주의
std::uintptr_t tagged = addr | 1;      // 정렬 덕에 하위 비트가 비어 있음
//   ⚠ 실무에서 널리 쓰이지만 엄밀히는 회색지대입니다
//   → std::launder · memcpy 로 다루거나, 별도 필드로 분리하는 편이 안전

왜 이런 규칙이 있나

컴파일러가 '별칭 분석(alias analysis)'을 할 수 있어야
최적화가 가능하기 때문입니다

  · 두 포인터가 절대 겹치지 않는다면
    → 로드·스토어 순서를 바꾸고, 레지스터에 캐시하고, 벡터화합니다
  · 겹칠 수 있다면
    → 매번 메모리를 다시 읽어야 합니다 (느림)

프로버넌스 규칙이 없으면
  "정수로 바꿨다가 되돌린 포인터"가 무엇이든 가리킬 수 있어
  컴파일러는 모든 최적화를 포기해야 합니다.

실무 지침
  · 포인터 산술은 같은 배열 안에서만
  · 타입 재해석은 memcpy · bit_cast (d02)
  · 정수↔포인터 왕복은 최소화, 필요하면 격리된 함수에서
  · 저수준 트릭을 쓸 때는 -fno-strict-aliasing 이 필요한지 검토

★ C++26 · C 표준에서 프로버넌스를 명확히 하는 작업이 진행 중입니다
  (P2318 · TS 6010) — 지금은 '보수적으로 쓰는 것'이 답입니다
여기까지 신경 쓸 자리 — 할당자·GC·직렬화·JIT 처럼 메모리를 직접 관리하는 코드입니다. 일반 응용 코드에서는 d02 의 규칙(memcpy·bit_cast)만 지켜도 충분합니다.
정리 — “메모리가 있다”와 “객체가 살아 있다”는 다릅니다. 버퍼를 구조체로 캐스팅하지 말고 memcpy 하세요 — 비용은 0 입니다. __restrict 는 벡터화를 여는 열쇠이지만 약속을 어기면 UB 입니다. 수명 버그는 ASan 이 해제 위치까지 알려 줍니다.
DEEP 04

vtable 과 가상 호출 비용

가상 함수는 “느리다”가 아니라 “인라인을 막는다”가 정확한 표현입니다. 실제 비용을 수치로 확인하고 대안을 정리합니다.

메모리에 어떻게 놓이나

struct B { virtual void f(); virtual void g(); int x; };
struct D : B { void f() override; int y; };

sizeof(B);      // 16 = vptr(8) + int(4) + 패딩(4)
sizeof(D);      // 24 = vptr(8) + x(4) + y(4) + 패딩(8)

// 객체 배치
//   [vptr][x][패딩]          ← B
//   [vptr][x][y][패딩]       ← D (같은 vptr 자리, 다른 테이블을 가리킴)
//
// vtable (클래스마다 하나, 읽기 전용 섹션에)
//   B 의 vtable: [&B::f, &B::g, RTTI 정보, ...]
//   D 의 vtable: [&D::f, &B::g, RTTI 정보, ...]

// b.f() 가 하는 일
//   ① 객체에서 vptr 을 읽는다        (메모리 접근 1)
//   ② 테이블에서 f 의 주소를 읽는다   (메모리 접근 2)
//   ③ 그 주소로 간접 점프            (분기 예측 필요)

// 확인
// g++ -fdump-lang-class main.cpp     # vtable 레이아웃 출력
// clang++ -Xclang -fdump-record-layouts main.cpp   ★
// objdump -sj .rodata app | grep -A4 vtable
가상 함수가 하나라도 있으면 객체 앞에 vptr 8바이트가 붙고 is_standard_layout 이 깨집니다. C ABI 로 구조체를 그대로 넘길 수 없게 되는 이유입니다(🔗 f01 · 탭 1 x07).

실제 비용

직접 측정한 경향 (환경마다 다릅니다 — 직접 재세요)

  1억 회 호출, 본문이 한 줄인 함수

    직접 호출 (인라인)     0.03 ns/회   ← 사실상 사라짐
    비가상 함수 호출        1.0 ns
    가상 함수 (같은 타입)    1.5 ns      ← 예측 성공
    가상 함수 (타입 섞임)    4~8 ns      ← 예측 실패 ★
    std::function          3~10 ns

★ 진짜 비용은 '호출 자체'가 아니라 인라인 불가입니다
  · 한 줄짜리 접근자가 인라인되면 0사이클
  · 가상이면 호출이 남고, 주변 최적화(벡터화·상수 전파)도 막힙니다
  · 루프 안에서 원소마다 부르면 그 차이가 누적됩니다

언제 문제가 되나 (셋이 겹칠 때)
  ① 수백만 회 이상 호출  ② 본문이 짧음  ③ 루프 안 · 벡터화 대상
perf stat -e branch-misses,iTLB-load-misses ./app
#   간접 분기 예측 실패가 많으면 다형적 호출이 원인일 수 있습니다

이렇게도 쓸 수 있다 — 가상 호출을 없애는 방법 🟡 중급

컴파일러가 직접 호출로 바꾸게

// ① final — 더 파생될 수 없다면 대상이 확정됩니다 ★
struct D final : B { void f() override; };
D d; d.f();                  // 직접 호출 · 인라인 가능

struct B2 { virtual void f() final; };   // 함수 단위로도

// ② 정적 타입이 확실한 경로
void use(D& d) { d.f(); }    // B& 가 아니라 D& 로 받으면 직접 호출

// ③ LTO — 전체 프로그램을 보고 파생 클래스가 하나뿐이면 확정 ★
//    (speculative devirtualization)
set(CMAKE_INTERPROCEDURAL_OPTIMIZATION_RELEASE ON)

// ④ 익명 namespace — 이 파일 밖에서 상속할 수 없음을 알려 줍니다
namespace { struct Impl : Base { ... }; }

// 확인 — 어셈블리에 call *%rax (간접) 가 있는지 (⚡ e09)
// objdump -dC app | grep "call.*\*"

설계로 없애기

// ① 호출 단위를 키우기 ★ 거의 항상 최선입니다
// ❌ 원소마다 가상 호출
struct Filter { virtual double apply(double) = 0; };
for (auto& x : v) x = f->apply(x);       // 100만 번 간접 호출

// ✅ 배열 전체를 가상 함수로
struct Filter { virtual void apply(std::span<double>) = 0; };
f->apply(v);                              // 가상 호출 1번 + 내부는 순수 루프
//   → 비용이 사실상 사라지고 벡터화도 됩니다 (탭 1 x08)

// ② variant + visit — 종류가 고정이면 (탭 2 m10)
using Shape = std::variant<Circle, Rect>;
double area(const Shape& s) { return std::visit([](auto& x){ return x.area(); }, s); }
//   점프 테이블 · 인라인 가능 · 힙 할당 없음

// ③ 템플릿 (CRTP) — 컴파일 시점 다형성 (탭 2 m08)
template<class D> struct Base {
    double area() const { return static_cast<const D*>(this)->area_impl(); }
};
//   비용 0 · 대신 런타임 교체 불가

// ④ 타입별로 묶어 처리 (⚡ e05)
for (auto& c : circles) total += c.area();
for (auto& r : rects)   total += r.area();
“호출 단위를 키우기”가 핵심입니다 — 이 가이드 전체에서 반복되는 원칙과 같습니다. 파이썬 경계든 가상 함수든, 경계를 넘는 횟수를 데이터 크기와 분리하면 비용이 사라집니다.

실무에선 이렇게 — 과잉 반응하지 않기 🔴 실무

대부분은 문제가 아닙니다

가상 호출이 실제 병목인 경우는 드뭅니다

  · 초당 100만 번 불려도 1.5ns × 100만 = 1.5ms
  · 웹 요청 하나에 수십 번 부르는 정도면 무시할 수준
  · 프로파일에 나타나지 않으면 손대지 마세요 ★

과잉 반응의 대가
  · 전부 템플릿으로 바꾸면 빌드 시간·바이너리 크기 폭발 (d08)
  · CRTP 는 읽기 어렵고 에러 메시지가 나쁩니다
  · variant 는 종류를 나중에 추가하기 어렵습니다
  · 런타임 교체가 필요한 곳에서는 애초에 불가능합니다

★ 가상 함수를 그냥 쓰세요.
  프로파일러가 그 자리를 가리킬 때만 위의 기법을 꺼내면 됩니다.

가상 함수가 오히려 나은 경우
  · 플러그인 · 설정으로 구현 선택
  · 테스트용 가짜 객체 (탭 1 x08)
  · 컴파일 시간이 중요한 대형 프로젝트

그래도 지킬 것

// ① 상속할 클래스에는 virtual 소멸자 (탭 1 x08)
struct Base { virtual ~Base() = default; };
//   없으면 Base* 로 delete 할 때 파생 소멸자가 안 불립니다 (UB)

// ② 상속을 안 할 클래스는 final ★
struct Impl final : Base { ... };
//   최적화 여지 + 의도 표현

// ③ override 를 반드시
void f(int) override;        // 시그니처가 다르면 컴파일 에러

// ④ 다중 상속은 인터페이스에만
//   상태를 가진 클래스를 여럿 상속하면 vtable 이 복잡해지고
//   thunk(조정 코드)가 생겨 호출 비용이 늘어납니다

// ⑤ 가상 함수를 많이 만들지 마세요
//   vtable 이 커지면 캐시에도 부담입니다

// 검사
// clang-tidy: cppcoreguidelines-virtual-class-destructor
//             modernize-use-override
//             cppcoreguidelines-explicit-virtual-functions
가장 중요한 것은 virtual 소멸자입니다. 성능보다 정확성 문제이고, 빠뜨리면 메모리가 샙니다. -Wnon-virtual-dtor 를 켜 두세요(🛠️ b04).

한 단계 더 — vtable 의 세부 🧬 전문가

다중 상속과 thunk

struct A { virtual void f(); int a; };
struct B { virtual void g(); int b; };
struct C : A, B { void f() override; void g() override; };

// C 객체는 vptr 을 두 개 가집니다
//   [vptrA][a][vptrB][b]
//        ↑ A 로 볼 때        ↑ B 로 볼 때 (this 가 다릅니다!)

C c;
B* pb = &c;                  // ★ 주소가 조정됩니다 (+16 정도)
pb->g();                     // vptrB 의 테이블 → thunk → this 를 되돌림 → C::g

// thunk: this 포인터를 조정하고 진짜 함수로 점프하는 작은 코드
//   → 다중 상속에서 가상 호출이 조금 더 비싼 이유

// dynamic_cast 는 RTTI 를 순회합니다 (더 비쌈)
if (auto* p = dynamic_cast<C*>(pb)) { ... }     // 수십~수백 사이클
//   자주 부르면 병목이 됩니다 → 설계를 다시 보세요
//   (가상 함수로 표현할 수 있으면 그쪽이 낫습니다)

// 가상 상속 (다이아몬드 해결)은 더 복잡합니다
struct D : virtual A { };
//   vbase offset 을 통한 간접 접근 → 멤버 접근조차 느려집니다
//   ★ 꼭 필요한 경우가 아니면 피하세요

RTTI 와 예외를 끄는 선택

# 임베디드·게임 엔진에서 종종 씁니다
g++ -fno-rtti -fno-exceptions

# -fno-rtti 로 잃는 것
#   dynamic_cast · typeid
#   (vtable 의 RTTI 포인터가 사라져 바이너리가 조금 작아집니다)

# -fno-exceptions 로 잃는 것 (탭 1 x11)
#   try/catch/throw
#   std::vector::at · std::stoi 등 예외에 의존하는 표준 함수
#   → 자체 컨테이너를 쓰거나 expected 로 대체 (탭 2 m10)

# 효과
#   바이너리 5~20% 감소 · 예외 테이블 제거
#   ⚠ 성능은 대개 차이가 없습니다 (예외는 던지지 않으면 비용 0 — d05)

# 확인
size -A app | grep -E "eh_frame|gcc_except"
// RTTI 없이 타입 구분이 필요하면 — 직접 태그
struct Base {
    enum class Kind { Circle, Rect } kind;
    explicit Base(Kind k) : kind(k) {}
};
//   variant 가 이것을 타입 안전하게 해 주는 것입니다 (탭 2 m10)
확장 모듈에서는 예외를 켜 두세요 — pybind11·node-addon-api 가 예외로 에러를 전달합니다(🐍 y08 · 🟨 j02). 끄면 표준 라이브러리 일부도 못 쓰게 되어 얻는 것보다 잃는 것이 큽니다.
정리 — 가상 호출의 진짜 비용은 인라인 불가 입니다. final 을 붙이고 호출 단위를 배열 전체로 키우면 대부분 사라집니다. 다만 프로파일러가 가리킬 때만 손대세요 — 전부 템플릿으로 바꾸면 빌드 시간과 가독성을 잃습니다.
DEEP 05

예외의 실제 구현

“예외는 느리다”는 절반만 맞습니다. 던지지 않으면 비용이 0 이고, 던지면 매우 비쌉니다. 그 구조를 알면 언제 쓸지 판단할 수 있습니다.

테이블 기반(zero-cost) 방식

현대 구현(Itanium ABI · MSVC x64)은 이렇게 동작합니다

  컴파일 시점
    · try 블록에 들어가는 명령을 넣지 않습니다 ★
    · 대신 '어디서 예외가 나면 무엇을 정리할지' 표를 만들어
      바이너리의 별도 섹션에 넣습니다
        .eh_frame · .gcc_except_table (ELF)
        .pdata · .xdata (Windows)

  던져질 때
    ① __cxa_allocate_exception 으로 예외 객체 할당
    ② __cxa_throw 호출
    ③ 언와인더가 스택을 거슬러 올라가며 표를 조회
       (2단계: 먼저 핸들러를 찾고, 그다음 실제로 되감기)
    ④ 각 프레임의 소멸자를 호출
    ⑤ 핸들러로 점프

비용 구조
  · 던지지 않을 때 : 실행 비용 0 · 바이너리 +5~15% ★
  · 던질 때        : 수 μs (표 조회 + 되감기) · 시간이 일정하지 않음
  · 게다가 언와인더가 전역 락을 잡는 구현이 있어
    멀티스레드에서 동시에 던지면 직렬화됩니다 ★

그래서 나오는 결론

// ✅ 정상 흐름에는 예외를 쓰지 마세요
// ❌ 루프 안에서 흐름 제어로
for (auto& s : lines) {
    try { v.push_back(std::stoi(s)); }
    catch (...) { /* 무시 */ }        // 실패가 잦으면 수백 배 느려집니다 ★
}
// ✅ 실패가 흔하면 반환값으로 (탭 2 m10)
for (auto& s : lines)
    if (auto n = to_int(s)) v.push_back(*n);

// ✅ 진짜 예외적인 상황에는 마음껏
if (!file) throw std::runtime_error("설정 파일 없음");
//   프로그램 시작에 한 번 나는 것이라면 비용을 걱정할 이유가 없습니다

// 측정 — 던지는 비용을 직접 재 보기
auto t = bench_ms([]{
    for (int i = 0; i < 100000; ++i)
        try { throw 1; } catch (int) { }
});
//   대개 호출당 1~5μs — 함수 호출의 1000배 수준입니다
실시간 시스템에서 예외를 끄는 이유 — 느려서가 아니라 시간이 예측 불가능하기 때문입니다. 게임 프레임·오디오 콜백·거래 시스템처럼 최악 지연이 중요한 곳에서는 -fno-exceptions 를 씁니다.

이렇게도 쓸 수 있다 — 예외 안전성 다시 보기 🟡 중급

noexcept 의 의미

void f() noexcept;
//   "이 함수는 예외를 던지지 않는다"
//   어기면 std::terminate — catch 로도 못 막습니다 ★

// 얻는 것
//   ① 컴파일러가 예외 처리 코드를 생략 → 바이너리 축소
//   ② ★ 이동 생성자에 noexcept 가 있어야 vector 재할당이 '이동'을 씁니다
//      (탭 2 m03) — 없으면 복사로 후퇴해 성능이 몇 배 나빠집니다
static_assert(std::is_nothrow_move_constructible_v<MyType>);

// 반드시 noexcept 여야 하는 것
//   소멸자 (기본으로 noexcept)
//   이동 생성자 · 이동 대입
//   swap
//   해제 함수

// 조건부 noexcept
template<class T>
void g(T t) noexcept(std::is_nothrow_move_constructible_v<T>);

// 검사
noexcept(expr)               // 이 식이 noexcept 인가 (컴파일 시점)
static_assert(noexcept(a.swap(b)));

스택 되감기 관찰하기

struct Trace {
    const char* n;
    explicit Trace(const char* s) : n(s) { std::printf("+ %s\n", n); }
    ~Trace() { std::printf("- %s\n", n); }
};

void c() { Trace t{"c"}; throw std::runtime_error("실패"); }
void b() { Trace t{"b"}; c(); }
void a() { Trace t{"a"}; b(); }

int main() {
    try { a(); }
    catch (const std::exception& e) { std::printf("잡음: %s\n", e.what()); }
}
// 출력
//   + a  + b  + c
//   - c  - b  - a        ★ 소멸자가 역순으로 전부 불립니다 (RAII)
//   잡음: 실패
# 던지는 순간 멈추기 (🛠️ b09)
gdb ./app
(gdb) catch throw
(gdb) run
(gdb) bt                     # 어디서 던졌는지

# 잡히지 않은 예외로 죽었을 때
(gdb) break __cxa_throw
(gdb) break std::terminate

실무에선 이렇게 — 경계에서의 처리 🔴 실무

예외가 새면 프로세스가 죽습니다

// ① main 을 감싸기 (탭 1 x11)
int main() try { run(); return 0; }
catch (const std::exception& e) { log(e.what()); return 1; }
catch (...) { log("알 수 없는 오류"); return 2; }

// ② 스레드 함수 (탭 2 m12)
std::jthread t([]{
    try { work(); } catch (const std::exception& e) { log(e.what()); }
});

// ③ C ABI 경계 — 반드시 (🔗 f09)
extern "C" int32_t mylib_run(...) {
    try { impl(); return 0; }
    catch (const std::bad_alloc&) { return -2; }
    catch (...) { return -1; }
}
//   C++ 예외가 C 프레임을 통과하면 UB 입니다 ★

// ④ 파이썬·Node 경계 (🐍 y08 · 🟨 j02)
//   pybind11 이 자동 변환하지만, GIL 해제 구간은 직접 처리해야 합니다
std::optional<std::string> err;
{
    py::gil_scoped_release rel;
    try { compute(); } catch (const std::exception& e) { err = e.what(); }
}
if (err) throw py::value_error(*err);   // GIL 을 가진 상태에서 던지기 ★

// ⑤ 소멸자 (탭 2 m01)
~File() { try { flush(); } catch (...) { /* 로그만 */ } }

현재 구현의 문제

① 던질 때 힙 할당이 일어납니다

   그 예외 객체를 할당할 메모리가 없을 수 있습니다
   (구현은 비상용 버퍼를 둡니다)

② 언와인더가 전역 락을 잡는 구현이 있습니다
   여러 스레드가 동시에 던지면 직렬화됩니다 ★
   서버에서 예외를 흐름 제어로 쓰면 확장성이 무너집니다

③ 바이너리가 커집니다 (5~15%)
   임베디드에서 문제가 됩니다

④ 되감기 시간이 스택 깊이에 비례합니다
   최악 지연을 보장할 수 없습니다

⑤ 표(테이블)를 읽어야 해서 캐시를 오염시킵니다

DEEP 06

메모리 모델과 memory_order

멀티스레드에서 다른 CPU 가 내 쓰기를 언제 보게 되는가 를 정하는 규칙입니다. 락 프리 코드를 쓰려면 반드시 알아야 합니다.

왜 순서가 뒤바뀌나

세 곳에서 재배치가 일어납니다

  ① 컴파일러 — 최적화로 명령 순서를 바꿉니다
  ② CPU — 비순차 실행(out-of-order)
  ③ 캐시·스토어 버퍼 — 쓰기가 다른 코어에 보이는 시점이 늦어집니다

단일 스레드에서는 결과가 같도록 보장되지만
다른 스레드가 보는 순서는 다를 수 있습니다 ★

아키텍처별 강도
  x86-64 : 강한 모델 (StoreLoad 만 재배치)
           → acquire/release 가 사실상 공짜
  ARM · RISC-V : 약한 모델
           → 실제 장벽 명령이 생깁니다 ★
  ⚠ x86 에서 테스트한 락 프리 코드가 ARM(애플 실리콘·서버)에서
    깨지는 일이 실제로 있습니다
// 고전적인 실패
bool ready = false;
int  data  = 0;
// 스레드 A
data = 42;
ready = true;          // ★ 컴파일러·CPU 가 순서를 바꿀 수 있습니다
// 스레드 B
if (ready) use(data);  // data 가 아직 0일 수 있습니다

memory_order 여섯 가지

order의미
relaxed원자성만. 순서 보장 없음 — 카운터에
acquire이후 읽기·쓰기가 앞으로 못 옴 (load 에)
release이전 읽기·쓰기가 뒤로 못 감 (store 에)
acq_rel둘 다 (RMW 연산에)
seq_cst기본값. 전역 순서까지 보장 · 가장 안전
consume사실상 폐기 — 쓰지 마세요
// ✅ 생산자-소비자 — acquire/release 쌍 ★
std::atomic<bool> ready{false};
int data = 0;

// 생산자
data = 42;
ready.store(true, std::memory_order_release);   // 앞의 쓰기를 모두 공개

// 소비자
if (ready.load(std::memory_order_acquire))      // 그 이후를 모두 관찰
    use(data);                                   // ✅ 42 가 보장됩니다

// 카운터 — 순서가 필요 없으면 relaxed
counter.fetch_add(1, std::memory_order_relaxed);

이렇게도 쓸 수 있다 — 패턴으로 익히기 🟡 중급

자주 쓰는 세 가지

// ① 플래그로 종료 신호 — relaxed 로 충분한 경우가 많습니다
std::atomic<bool> stop{false};
// 워커
while (!stop.load(std::memory_order_relaxed)) { work(); }
// 메인
stop.store(true, std::memory_order_relaxed);
//   ★ 단, 종료 후 다른 데이터를 읽어야 하면 acquire/release 가 필요합니다

// ② 한 번만 초기화 — 표준 도구를 쓰세요
static std::once_flag flag;
std::call_once(flag, []{ init(); });
Logger& get() { static Logger l; return l; }    // ✅ 이것도 스레드 안전

// ③ 스핀 락 (아주 짧은 임계 구역에만)
class SpinLock {
    std::atomic_flag f_ = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (f_.test_and_set(std::memory_order_acquire))
            f_.wait(true, std::memory_order_relaxed);   // C++20 ★
    }
    void unlock() {
        f_.clear(std::memory_order_release);
        f_.notify_one();
    }
};
//   ⚠ 대기가 길면 뮤텍스가 낫습니다 (CPU 를 태우지 않으므로)

// C++20 atomic wait/notify — 스핀 없이 대기
std::atomic<int> v{0};
v.wait(0);                     // 0 이 아닐 때까지 대기 (효율적)
v.store(1); v.notify_all();

실수하기 쉬운 것들

// ① atomic 이면 안전하다는 오해 (탭 2 m12)
std::atomic<int> n{0};
n = n + 1;                     // ❌ 읽기와 쓰기가 분리 — 원자적이지 않음
n.fetch_add(1);                // ✅

// ② 두 atomic 을 함께 보는 것은 원자적이지 않습니다
if (a.load() > 0 && b.load() > 0) { }   // ❌ 그 사이에 바뀔 수 있습니다
//   → 뮤텍스나 단일 원자 구조체가 필요합니다

// ③ CAS 루프 — compare_exchange_weak 는 '가짜 실패' 가 있습니다
int expected = cur.load(std::memory_order_relaxed);
while (!cur.compare_exchange_weak(expected, expected + 1,
                                  std::memory_order_release,
                                  std::memory_order_relaxed)) {
    // expected 가 자동으로 갱신됩니다 ★
}
//   weak 는 루프 안에서, strong 은 단발 시도에

// ④ volatile 은 스레드 동기화 도구가 아닙니다 ★
volatile bool flag;            // ❌ 재배치를 막지 못합니다
std::atomic<bool> flag;        // ✅
//   volatile 은 '메모리 맵 I/O' 용입니다

// ⑤ 큰 타입의 atomic 은 락을 씁니다
std::atomic<BigStruct> a;
a.is_lock_free();              // false 면 내부적으로 뮤텍스 ★

실무에선 이렇게 — 확신이 없으면 seq_cst 🔴 실무

최적화보다 정확성

실무 지침

  ① 가능하면 공유하지 마세요 (탭 2 m12 · ⚡ e07)
  ② 공유해야 하면 뮤텍스 — 대부분 충분히 빠릅니다
  ③ 원자 변수는 단순한 카운터·플래그에
  ④ memory_order 는 기본값(seq_cst)으로 시작
  ⑤ 프로파일러가 그 자리를 가리킬 때만 relaxed·acquire/release 검토

왜 이 순서인가
  · seq_cst 와 acquire/release 의 차이는 x86 에서 거의 없습니다
  · ARM 에서도 대개 수 나노초 수준입니다
  · 반면 잘못된 relaxed 는 '재현 불가능한 버그' 를 만듭니다 ★
    · 테스트에서 안 나옵니다
    · 특정 CPU·특정 부하에서만 나타납니다
    · 디버거를 붙이면 사라집니다

★ 성능 이득은 몇 나노초, 잘못됐을 때의 대가는 며칠입니다.

한 단계 더 — happens-before 와 동기화 🧬 전문가

표준이 정의하는 것

핵심 개념

  · sequenced-before   : 같은 스레드 안의 순서
  · synchronizes-with  : release store 와 그것을 읽은 acquire load 사이
  · happens-before     : 위 둘의 이행적 폐포

데이터 경쟁의 정의
  두 접근이 (1) 같은 메모리 위치에 (2) 최소 하나가 쓰기이고
  (3) happens-before 관계가 없으면 → 데이터 경쟁 → UB ★

즉 '동시에 접근하면 안 된다'가 아니라
'순서 관계를 만들지 않고 접근하면 안 된다' 입니다.

release/acquire 가 만드는 것
  스레드 A: X 를 쓰고 → flag.store(release)
  스레드 B: flag.load(acquire) 가 true 를 보면
            → A 의 모든 이전 쓰기가 B 에게 보입니다 ★
            (X 가 atomic 이 아니어도)

seq_cst 가 추가로 주는 것
  모든 seq_cst 연산에 대한 '단일 전역 순서'
  → 여러 변수 사이의 순서까지 일관되게 보입니다
  (독립 읽기 독립 쓰기 문제를 해결)

어셈블리로 확인하기

// godbolt 에서 아키텍처를 바꿔 가며 보세요 (⚡ e09)
std::atomic<int> a;
void f() {
    a.store(1, std::memory_order_relaxed);
    a.store(1, std::memory_order_release);
    a.store(1, std::memory_order_seq_cst);
}

// x86-64 결과
//   relaxed : mov  DWORD PTR a[rip], 1
//   release : mov  DWORD PTR a[rip], 1        ★ 같습니다 (공짜)
//   seq_cst : mov  eax, 1
//             xchg DWORD PTR a[rip], eax      ★ 이것만 비쌉니다

// AArch64 결과
//   relaxed : str  w8, [x9]
//   release : stlr w8, [x9]                   ★ 장벽 명령
//   seq_cst : stlr w8, [x9]                   (load 쪽에서 차이)

// → x86 에서는 release 가 공짜이므로 굳이 relaxed 를 쓸 이유가 적고,
//   ARM 에서는 차이가 있으니 핫 경로라면 검토할 가치가 있습니다 ★
“x86 에서 잘 되니 괜찮다”는 위험합니다 — x86 의 강한 메모리 모델이 잘못된 코드를 가려 줍니다. 애플 실리콘·ARM 서버가 흔해진 지금은 ARM 에서도 반드시 테스트해야 합니다.
정리 — 멀티스레드에서 쓰기가 다른 코어에 보이는 시점을 정하는 것이 메모리 모델입니다. 생산자-소비자는 release/acquire 쌍, 단순 카운터는 relaxed, 확신이 없으면 기본값을 쓰세요. 그리고 x86 에서만 테스트하지 마세요 — ARM 에서 드러납니다.
DEEP 07

ABI 호환성 — 배포의 벽

C++ 에는 표준 ABI 가 없습니다. 컴파일러나 표준 라이브러리 버전이 다르면 같은 소스도 안 붙습니다. 라이브러리를 배포할 때 가장 자주 막히는 지점입니다.

무엇이 ABI 를 깨나

바이너리 호환을 깨는 변경 (재컴파일 없이는 못 씁니다)

  · 클래스에 멤버 변수 추가·삭제·순서 변경  ★ 크기가 바뀜
  · 가상 함수 추가·삭제·순서 변경           ★ vtable 배치가 바뀜
  · 기반 클래스 추가·변경
  · 함수 시그니처 변경 (인자 타입·개수·const)
  · 인라인 함수의 내용 변경                  ★ 이미 인라인된 코드가 남음
  · 템플릿 정의 변경
  · enum 값 변경 · 순서 변경
  · 기본 인자 변경 (호출부에 박힘)
  · 구조체 정렬·패딩 변경 (빌드 플래그 포함)

소스 호환은 되는데 ABI 는 깨지는 예
  private 멤버 하나만 추가 → 재컴파일하면 되지만
  기존 바이너리와는 못 씁니다 ★
컴파일러·표준 라이브러리 차이

  · GCC 와 Clang : 대체로 호환 (같은 Itanium ABI · libstdc++)
  · MSVC : 완전히 다릅니다 (이름 맹글링·예외·레이아웃)
  · libstdc++ vs libc++ : std:: 타입 레이아웃이 다릅니다 ★
  · GCC 5 의 _GLIBCXX_USE_CXX11_ABI 전환
      → std::string 의 ABI 가 바뀌었습니다
      undefined reference to std::__cxx11::basic_string...

해법 — 경계를 C ABI 로 ★

// ❌ C++ 타입을 공개 인터페이스에 노출
class MYLIB_API Engine {
public:
    std::vector<double> process(const std::string& input);   // ⚠
    //   쓰는 쪽이 같은 컴파일러·같은 표준 라이브러리여야 합니다
private:
    std::vector<double> buf_;      // 멤버를 추가하면 ABI 파괴
};

// ✅ C ABI 로 (🔗 f01·f03)
typedef struct mylib_engine mylib_engine;
MYLIB_EXPORT mylib_engine* mylib_engine_create(void);
MYLIB_EXPORT int32_t mylib_process(mylib_engine*, const double*, int64_t,
                                   double*, int64_t*);
//   숫자와 포인터만 → 어느 컴파일러에서든 동작합니다

// ✅ 절충 — Pimpl 로 멤버를 감추기 (탭 1 x09)
class MYLIB_API Engine {
public:
    Engine(); ~Engine();
    Engine(Engine&&) noexcept;
    void process(...);
private:
    struct Impl;
    std::unique_ptr<Impl> p_;      // ★ 크기가 항상 8바이트
};
//   내부를 바꿔도 크기가 안 변합니다

한 단계 더 — 왜 표준 ABI 가 없나 🧬 전문가

역사와 현실

· C++ 표준은 ABI 를 정의하지 않습니다
  (구현이 자유롭게 최적화할 수 있게 하려고)

· 사실상의 표준
    Itanium C++ ABI  : GCC · Clang · 대부분의 유닉스
    MSVC ABI         : 윈도우 (문서화되어 있지만 다릅니다)

· 그래서 같은 플랫폼에서도
    libstdc++ 로 빌드한 것과 libc++ 로 빌드한 것이 안 붙습니다
    std::string · std::list 등의 내부 배치가 다릅니다 ★

★ ABI 안정성이 표준 발전을 막기도 합니다
  예: std::regex 는 성능이 나쁘다고 알려져 있지만
      고치면 ABI 가 깨져서 그대로 두고 있습니다
      (std::unordered_map 도 비슷한 상황)
  → C++ 위원회에서 "ABI break" 는 오래된 논쟁 주제입니다

실무 결론
  · 라이브러리 경계에서는 std:: 타입을 노출하지 않는다
  · 필요하면 C ABI 로 감싼다
  · 사내 코드는 컴파일러를 통일한다

맹글링으로 보는 ABI

# 같은 함수가 컴파일러마다 다른 이름을 갖습니다 (🔗 f02)
void f(const std::string&);

# GCC/Clang (Itanium ABI · 새 ABI)
_Z1fRKNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE

# GCC (옛 ABI · _GLIBCXX_USE_CXX11_ABI=0)
_Z1fRKSs

# MSVC
?f@@YAXAEBV?$basic_string@DU?$char_traits@D@std@@V?$allocator@D@2@@std@@@Z

# 복원
c++filt _Z1fRKSs
undname "?f@@YAXAEBV..."

# ★ 이름이 다르다 = 링크가 안 된다
#   undefined reference to `f(std::__cxx11::basic_string<...>)'
#   → 이 메시지에 __cxx11 이 보이면 ABI 불일치입니다

# 강제로 맞추기 (옛 라이브러리와 연동할 때)
g++ -D_GLIBCXX_USE_CXX11_ABI=0 ...
에러 메시지에서 __cxx11 을 찾으세요 — undefined reference 에 이것이 보이면 ABI 불일치입니다. 라이브러리를 다시 빌드하거나 플래그를 맞춰야 합니다.
정리 — C++ 에는 표준 ABI 가 없습니다 — 컴파일러·표준 라이브러리·빌드 플래그가 다르면 안 붙습니다. 해법은 하나입니다 — 공개 경계를 C ABI 로 만들고 C++ 타입을 인터페이스에 노출하지 않는 것. ABI 변경은 abidiff 로 CI 에서 감시하세요.

class Arena {
    std::byte* buf_;
    std::size_t cap_, off_ = 0;
public:
    Arena(std::byte* b, std::size_t n) : buf_(b), cap_(n) {}

    void* alloc(std::size_t n, std::size_t align) {
        std::size_t cur = reinterpret_cast<std::uintptr_t>(buf_ + off_);
        std::size_t pad = (align - (cur % align)) % align;    // ★ 정렬 보정
        if (off_ + pad + n > cap_) throw std::bad_alloc{};
        void* p = buf_ + off_ + pad;
        off_ += pad + n;
        return p;
    }
    void reset() noexcept { off_ = 0; }      // ★ 해제는 통째로
};

// PMR 로 감싸면 표준 컨테이너에 바로 쓸 수 있습니다
class ArenaResource : public std::pmr::memory_resource {
    Arena& a_;
    void* do_allocate(std::size_t n, std::size_t align) override {
        return a_.alloc(n, align);
    }
    void do_deallocate(void*, std::size_t, std::size_t) override { }  // no-op
    bool do_is_equal(const memory_resource& o) const noexcept override {
        return this == &o;
    }
public:
    explicit ArenaResource(Arena& a) : a_(a) {}
};

// 같은 크기 객체를 아주 많이 만들고 버릴 때 (게임 엔티티·패킷)
template<std::size_t Size, std::size_t Align>
class FixedPool {
    union Slot { std::byte data[Size]; Slot* next; };
    static_assert(Size >= sizeof(Slot*));

    std::vector<std::unique_ptr<Slot[]>> blocks_;
    Slot* free_ = nullptr;
    std::size_t block_size_ = 256;

    void grow() {
        auto blk = std::make_unique<Slot[]>(block_size_);
        for (std::size_t i = 0; i < block_size_; ++i) {
            blk[i].next = free_;
            free_ = &blk[i];
        }
        blocks_.push_back(std::move(blk));
        block_size_ *= 2;
    }
public:
    void* allocate() {
        if (!free_) grow();
        Slot* s = free_;
        free_ = s->next;
        return s;                            // ★ O(1) · 포인터 하나 이동
    }
    void deallocate(void* p) noexcept {
        auto* s = static_cast<Slot*>(p);
        s->next = free_;
        free_ = s;
    }
};
//   할당·해제가 각각 몇 사이클 — malloc 대비 10배 이상 빠릅니다 ★

// C++17 이후 최소 요구사항은 간단해졌습니다
template<class T>
struct MyAlloc {
    using value_type = T;

    MyAlloc() = default;
    template<class U> constexpr MyAlloc(const MyAlloc<U>&) noexcept {}

    T* allocate(std::size_t n) {
        if (n > std::numeric_limits<std::size_t>::max() / sizeof(T))
            throw std::bad_array_new_length{};
        void* p = ::operator new(n * sizeof(T), std::align_val_t{alignof(T)});
        return static_cast<T*>(p);
    }
    void deallocate(T* p, std::size_t) noexcept {
        ::operator delete(p, std::align_val_t{alignof(T)});
    }

    template<class U> bool operator==(const MyAlloc<U>&) const noexcept
        { return true; }        // ★ 상태가 있으면 정확히 비교해야 합니다
};

  · 라이브러리 의존성을 늘릴 수 없는 환경
  · 프로파일러가 그 루프만 계속 가리킬 때

유지보수 비용

인트린식 코드를 두면 생기는 일

  · x86 과 ARM 두 벌을 유지해야 합니다 (애플 실리콘 · ARM 서버)
  · 새 명령 세트가 나오면 또 한 벌
  · 읽을 수 있는 사람이 팀에 한두 명뿐이 됩니다
  · 리팩터링 때마다 스칼라·SIMD 양쪽을 고쳐야 합니다
  · 테스트 케이스가 늘어납니다 (꼬리·정렬·경계)

그래서
  · 인트린식 코드는 '한곳에 격리'하세요
      src/kernels/ 에 모으고 인터페이스는 단순하게
  · 반드시 스칼라 기준 구현과 대조 테스트 ★
  · 주석에 '왜 이렇게 썼는지'와 측정 결과를 남기세요
      // AVX2 버전: 스칼라 대비 3.2배 (n=1M, Zen4, 2026-08 측정)

★ 성능 이득이 2배 미만이면 대개 유지보수 비용이 더 큽니다.
먼저 자동 벡터화를 노리세요(⚡ e06) — __restrict 와 단순한 루프 구조만으로 인트린식의 70~90% 성능이 나오는 경우가 많습니다. 코드는 그대로 읽히고요.

한 단계 더 — 컴파일러 내장 함수 🧬 전문가

알아 두면 유용한 __builtin_*

int r;
if (__builtin_add_overflow(a, b, &r)) { /* 오버플로 */ }

__builtin_clzll(x)        → std::countl_zero(x)

__builtin_expect(x, 0)
__builtin_unreachable()          // "여기 도달할 수 없다" ★
//   std::unreachable() (C++23)

// 함수 정보

// 프리페치 (⚡ e02)

위험한 것 — unreachable

// "여기 도달할 수 없다"고 약속하면 컴파일러가 그것을 이용합니다
int f(int x) {
    switch (x) {
        case 0: return 10;
        case 1: return 20;
        default: std::unreachable();     // ★ 다른 값이 오면 UB
    }
}
//   → 범위 검사가 사라지고 점프 테이블이 최적화됩니다
//   ⚠ 실제로 2가 들어오면 무슨 일이든 일어납니다 (d02)

// 안전한 사용
//   · 입력을 이미 검증한 뒤 내부 함수에서만
//   · 디버그 빌드에서는 assert 로 확인
#ifndef NDEBUG
    #define MYLIB_UNREACHABLE() assert(false && "도달 불가")
#else
    #define MYLIB_UNREACHABLE() std::unreachable()
#endif

// 확인 — 어셈블리에서 검사가 사라졌는지 (⚡ e09)
// godbolt 에서 unreachable 있는 버전과 없는 버전 비교
unreachable 은 컴파일러에게 주는 약속입니다 — 어기면 d02 의 모든 무서운 일이 일어납니다. 성능 이득이 확실히 측정된 자리에만, 디버그 빌드에서는 assert 로 이중 방어하세요.
정리 — 순서는 표준 함수 → __builtin_* → 인트린식 → 인라인 어셈블리 입니다. <bit> 헤더에 이미 있는 것을 인트린식으로 쓰지 마세요. 직접 쓴다면 스칼라 기준 구현과 대조 테스트를 반드시 두고, 런타임 CPU 감지로 이식성을 지키세요.

최적화 빌드의 어려움

Release 덤프에서 흔한 상황

  · 변수가 <optimized out>
      → 레지스터에만 있거나 아예 사라졌습니다
      → 주변 변수·인자로 추론하거나 RelWithDebInfo 로 재현
  · 함수가 인라인되어 스택에 없음
      → gdb 는 인라인 프레임을 보여 주기도 합니다 (DWARF 정보)
      → bt 에 "(inlined by)" 표시를 찾으세요
  · 실행 순서가 소스와 다름
      → 줄 번호가 이상해 보일 수 있습니다
  · 꼬리 호출 최적화로 프레임이 사라짐

대책
  · RelWithDebInfo 로 배포 (-O2 -g) ★
  · -fno-omit-frame-pointer
  · 중요한 상태를 전역 로그 버퍼에 남기기
      static thread_local char g_last_op[64];
      → 덤프에서 이 값을 읽으면 무엇을 하던 중이었는지 알 수 있습니다 ★
  · 크래시 직전 로그를 링 버퍼로 유지
“마지막 작업” 흔적을 남기는 기법 — thread_local 버퍼에 현재 처리 중인 요청 ID·단계를 기록해 두면, 덤프에서 그 값을 읽어 재현 범위를 즉시 좁힐 수 있습니다. 비용은 거의 없고 효과는 큽니다.
정리 — 운영 크래시는 덤프와 심볼이 있어야 분석할 수 있습니다. ulimit -c unlimited · 심볼 분리 보관 · RelWithDebInfo 배포 세 가지를 미리 준비하세요. 분석은 bt full 과 thread apply all bt 로 시작합니다.

C++ 를 쓰지 말아야 할 때

마지막 섹션은 안 쓰는 판단입니다. 기술 선택은 팀이 6개월 뒤에도 고칠 수 있는가로 결정됩니다.

C++ 가 답이 아닌 경우

  • I/O 가 병목 — 계산 언어를 바꿔도 그대로입니다(⚡ e01)
  • 이미 numpy·polars 로 충분 — 1~3배를 위해 치를 비용이 아닙니다(⚡ e10)
  • 요구가 자주 바뀌는 초기 코드 — 빌드·배포 부담이 개발 속도를 깎습니다
  • 팀에 C++ 경험자가 없음 — 버스 팩터 1 은 위험합니다
  • 크래시가 서비스를 죽이면 안 됨 — 세그폴트는 프로세스 전체를 죽입니다(🐍 y12)
  • numba·Cython 으로 충분 — 빌드 파이프라인 없이 70~90% 성능(⚡ e10)
  • 보안이 최우선 — 메모리 안전 언어가 구조적으로 유리합니다
전체에서 차지하는 비중을 먼저 보세요 — 프로파일에서 30% 미만인 함수는 100배 빠르게 해도 전체는 1.4배입니다(암달의 법칙).

## 제안: 정산 집계를 C++ 확장으로

### 현황
- 프로파일 결과 `aggregate()` 가 전체의 68% (평균 4.2초/건)
- numpy 벡터화 시도 → 원소별 분기 때문에 적용 불가
- numba 시도 → 2.1배 (객체 타입 때문에 nopython 모드 실패)

### 제안
pybind11 로 `aggregate()` 만 C++ 로. 인터페이스는 numpy 배열 in/out.

### 예상 효과 (프로토타입 실측)
| 건수    | 현행   | C++   | 배수  |
|---------|-------:|------:|------:|
| 10,000  | 4.2s   | 0.31s | 13.5× |
| 100,000 | 41s    | 2.8s  | 14.6× |
전체 배치: 6분 → 1.4분

### 비용
- 개발 2주 · CI 에 wheel 빌드 추가(3 OS × 5 버전 → abi3 로 6개)
- 유지보수: 정산팀 2명이 리뷰 가능

### 위험과 대응
- 크래시 시 프로세스 종료 → 입력 검증 + ASan CI + 순수 파이썬 폴백
- `FASTAGG_PURE=1` 로 즉시 되돌릴 수 있음
- 두 구현 결과를 대조하는 테스트를 CI 에 상시
이런 형태의 제안이 통과됩니다 — 측정 → 대안 검토 → 실측 → 비용 → 위험 대응. “C++ 로 하면 빠릅니다”만으로는 설득되지 않고, 설득되어서도 안 됩니다.
