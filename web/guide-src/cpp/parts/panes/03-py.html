왜 C++ 로 만드나 — 판단 기준이 먼저

가장 중요한 결정은 “C++ 로 안 만든다” 일 때가 많습니다. 네이티브 확장은 빌드·배포·디버깅 비용이 함께 따라오기 때문입니다.

이 네 개를 통과하고도 남는 것 — 세밀한 루프 · 기존 C/C++ 라이브러리 · 하드웨어 접근이 진짜 후보입니다.

C++ 가 실제로 이기는 자리

이럴 때 유리이럴 땐 별로
원소마다 분기·상태가 있는 루프단순 배열 연산(numpy 가 이미 C)
numpy 로 벡터화가 안 되는 계산I/O·네트워크 대기가 대부분
이미 있는 C/C++ 라이브러리를 써야 함호출이 아주 잦고 계산은 짧음
GIL 없이 여러 코어를 써야 함파이썬 객체를 많이 오가야 함
지연 시간이 일정해야 함(GC 없음)요구가 자주 바뀌는 초기 코드
메모리를 정확히 통제해야 함팀에 C++ 를 아는 사람이 없음
호출 자체의 비용을 기억하세요 — 파이썬↔C++ 경계를 한 번 넘는 데 대략 수십~수백 나노초가 듭니다. 100만 번 호출하는 짧은 함수라면 경계 비용이 계산보다 커집니다. 그래서 “한 번 불러 배열 전체를 처리” 하는 모양으로 설계해야 합니다 — 이 원칙이 이 탭 전체를 관통합니다.

현실적인 기대 배수

같은 알고리즘 기준의 대략적인 감각 (직접 재 보셔야 합니다)

  순수 파이썬 루프            1×    기준
  numpy 벡터화               10~100×   (이미 C 로 도는 것)
  numba @njit                10~100×
  C++ (단순 이식)            10~50×
  C++ (캐시·SIMD 최적화)      50~200×
  C++ + 멀티스레드            × 코어 수

  ⚠ 단, 다음이면 배수가 확 줄어듭니다
     · 파이썬 객체를 자주 오간다      → 경계 비용이 지배
     · 데이터가 작다(수천 개 이하)    → 차이가 안 보임
     · 이미 numpy 로 벡터화돼 있다    → 2~3배에 그치는 경우가 흔함

  ★ "numpy 로 이미 짜 놓은 코드를 C++ 로 옮겼는데 별로 안 빨라졌다"
     는 아주 흔한 경험입니다. numpy 는 이미 최적화된 C 코드입니다.
     C++ 가 이기려면 numpy 가 못 하는 것(분기·상태·메모리 재사용)을 해야 합니다.

실무에선 이렇게 — 도입 전에 합의할 것 🔴 실무

비용은 코드가 아니라 운영에서 옵니다

  • 빌드 환경 — 팀원 전원과 CI 에 컴파일러가 필요합니다. wheel 을 미리 만들어 배포하면 쓰는 사람은 몰라도 됩니다(y03·🛠️ b06)
  • 플랫폼 수 × 파이썬 버전 수 = 만들어야 할 wheel 수. abi3 로 묶으면 파이썬 버전별 빌드를 줄일 수 있습니다
  • 디버깅 난이도 — 파이썬에서 나던 ValueError 가 세그폴트로 인터프리터 전체가 죽는 형태로 바뀝니다
  • 버스 팩터 — 그 모듈을 고칠 수 있는 사람이 팀에 몇 명인지
  • 되돌릴 수 있게 — 순수 파이썬 구현을 같이 남겨 두고 환경변수로 전환 가능하게 해 두면 사고 시 즉시 되돌립니다 ★
가장 안전한 도입 형태 — “순수 파이썬 함수와 완전히 같은 결과를 내는 C++ 함수를 만들고, 테스트로 두 결과를 대조한다”. 그러면 언제든 되돌릴 수 있고, 정확성 검증도 자동으로 됩니다.

# 언제부터 C++ 가 이기는가
#   총시간_py   = n × t_py
#   총시간_cpp  = 경계비용 + n × t_cpp
#   → n × (t_py - t_cpp) > 경계비용  일 때만 이득

# 실제로는 이렇게 재 봅니다
import numpy as np, timeit, fastmod
for n in (100, 1_000, 10_000, 100_000, 1_000_000):
    a = np.random.rand(n)
    tp = timeit.timeit(lambda: pure_python(a), number=10) / 10
    tc = timeit.timeit(lambda: fastmod.run(a),  number=10) / 10
    print(f"{n:>9}  py {tp*1e3:8.3f}ms  cpp {tc*1e3:8.3f}ms  {tp/tc:6.1f}×")

#  전형적인 결과 — 작은 n 에서는 배수가 1 근처이거나 오히려 손해,
#  n 이 커질수록 배수가 올라가다 어느 지점에서 평평해집니다(메모리 대역폭 한계).
#  ★ 이 표를 팀에 보여 주는 것이 "빨라졌습니다"보다 100배 설득력 있습니다
이 측정이 실무에서 하는 일 — “언제 C++ 경로를 쓰고 언제 파이썬으로 두는가”를 코드에 조건으로 넣을 수 있게 됩니다. if n < 5000: return pure_python(a) 같은 분기는 과한 최적화가 아니라 측정에 근거한 설계입니다.
정리 — C++ 모듈은 마지막 카드입니다. ① 측정 → ② 알고리즘 → ③ I/O → ④ numpy·polars → ⑤ Cython·Numba 를 다 해 보고, 그래도 남는 병목 하나에만 씁니다. 그리고 설계의 핵심은 단 하나 — 경계를 최대한 적게 넘기.

파일 세 개면 됩니다. C++ 함수 하나를 파이썬에서 import 해 쓰는 것까지 처음부터 끝까지 해 보겠습니다.

① C++ 파일 하나

// src/fastmod.cpp
#include <pybind11/pybind11.h>
#include <pybind11/stl.h>      // vector ↔ list 자동 변환

namespace py = pybind11;

int add(int a, int b) {
    return a + b;
}

double mean(const std::vector<double>& v) {
    double s = 0;
    for (double x : v) s += x;
    return v.empty() ? 0.0 : s / v.size();
}

PYBIND11_MODULE(fastmod, m) {        // ★ 이름이 파이썬 모듈명과 같아야 합니다
    m.doc() = "느린 부분만 C++ 로";

    m.def("add", &add, "두 정수를 더한다",
          py::arg("a"), py::arg("b"));           // 키워드 인자 이름

    m.def("mean", &mean, "평균을 구한다",
          py::arg("values"));
}
가장 흔한 첫 실패 — PYBIND11_MODULE(fastmod, m) 의 이름과 빌드 결과 파일 이름(fastmod.cpython-312-x86_64-linux-gnu.so)이 다르면 import 가 실패합니다. 이름을 정확히 맞추세요.

타입 변환 — 어디서 복사가 일어나는가

        if (t.size() != 2) return false;
        value = MyPoint{t[0].cast<double>(), t[1].cast<double>()};
        return true;
    }
    static handle cast(const MyPoint& p, return_value_policy, handle) {
        return py::make_tuple(p.x, p.y).release(); // C++ → 파이썬
    }
};

class Engine:

double mean(Arr a) {
    py::buffer_info buf = a.request();          // 복사 없이 정보만
    if (buf.ndim != 1)
        throw std::runtime_error("1차원 배열이어야 합니다");

    const double* p = static_cast<const double*>(buf.ptr);
    const std::size_t n = static_cast<std::size_t>(buf.shape[0]);

    double s = 0;
    for (std::size_t i = 0; i < n; ++i) s += p[i];
    return n ? s / n : 0.0;
}

// 더 간단한 접근자 (경계 검사 포함 — 개발 중에 유용)
double mean2(Arr a) {

    double s = 0;
    for (py::ssize_t i = 0; i < r.shape(0); ++i) s += r(i);
    return s / r.shape(0);
}

  ③ 선언하지 않으면 free-threaded 인터프리터가 그 모듈을 위해
     GIL 을 다시 켭니다 (동작은 하지만 병렬 이점이 사라집니다)
  ④ TSan(ThreadSanitizer) 으로 데이터 경쟁을 미리 잡기 (🛠️ b10)

  ⚠ 검증 없이 mod_gil_not_used() 를 선언하면
    조용한 데이터 손상으로 이어집니다. 선언은 '약속'입니다.
지금 할 일 — 새로 만드는 확장은 전역 가변 상태를 두지 않는 설계로 가세요. 함수가 인자로 받은 데이터만 만지면 free-threading 전환이 그냥 됩니다.

왜 코어 수만큼 안 빨라지나

스레드를 8개 썼는데 3배밖에 안 빨라지는 흔한 이유들

  ① 메모리 대역폭 한계 ★ 가장 흔함
     단순한 배열 연산은 CPU 가 아니라 '메모리에서 읽는 속도'가 한계입니다.
     코어를 늘려도 대역폭은 그대로라 4~5코어에서 평평해집니다.
     → 계산 밀도(원소당 연산 수)를 높이거나 캐시에 맞게 쪼개세요(⚡ e02)

  ② false sharing
     스레드들이 같은 캐시 라인(64바이트)에 쓰면 서로를 무효화합니다.
     → 스레드별 결과를 64바이트 간격으로 떨어뜨리거나 지역 변수에 누적(⚡ e08)

  ③ 작업 분배 불균형
     원소마다 계산량이 다르면 한 스레드만 오래 돕니다.
     → schedule(dynamic) 이나 작업 큐

  ④ 하이퍼스레딩
     논리 코어 16개여도 물리 코어는 8개인 경우가 많습니다.

  ⑤ 다른 프로세스와의 경합
     이미 멀티프로세싱으로 8개 워커가 돌고 있다면 코어는 남아 있지 않습니다.

측정

  htop 으로 실제 코어 사용률 확인 (전부 100% 인지)
실무에서 보고할 때 — “8스레드로 3.2배”는 실패가 아닙니다. 메모리 대역폭이 한계라면 그게 물리적 상한입니다. 상한이 무엇인지 근거를 대는 것이 배수 자체보다 중요합니다.
정리 — py::gil_scoped_release 한 줄이면 파이썬 스레드로 여러 코어를 실제로 쓸 수 있습니다 — 파이썬만으로는 불가능했던 지점입니다. 규칙은 하나 — GIL 을 놓은 구간에서는 파이썬 객체를 절대 만지지 않기. 그리고 계산이 짧으면 놓지 않는 편이 빠릅니다.

C++ 예외와 파이썬 에러의 차이

C++ 예외      : 스택 되감기(unwinding) 로 전파. 소멸자가 불립니다.
파이썬 에러   : 함수가 NULL 을 반환하고 '스레드 에러 상태'에 기록합니다.
                되감기가 아니라 '반환값 검사'로 전파됩니다.

pybind11 이 하는 일
  ① C++ → 파이썬 : catch 로 잡아 PyErr_SetString 등으로 상태를 설정하고
                    NULL 을 반환합니다.
  ② 파이썬 → C++ : 반환값이 NULL 이면 py::error_already_set 을 던집니다.

★ 그래서 이 규칙이 나옵니다
  · C++ 예외를 파이썬 경계 너머로 그대로 보내면 안 됩니다
    (되감기 정보가 없는 곳으로 넘어가면 UB)
  · 파이썬 에러 상태를 지우지 않고 두면 다음 API 호출이 실패합니다
  · GIL 없이 파이썬 에러 상태를 만지면 손상됩니다

워커 스레드에서 콜백 부르기

// C++ 스레드에서 파이썬을 부르려면 반드시 GIL 을 획득해야 합니다
void run_async(py::function cb) {
    // ★ 콜백 객체를 스레드로 넘기기 전에 GIL 을 가진 상태에서 복사
    std::thread([cb = std::move(cb)]() mutable {
        auto result = compute();               // GIL 없이 계산

        py::gil_scoped_acquire acq;            // 부를 때만 획득
        cb(result);
    }).detach();
}

// ⚠ detach 된 스레드는 인터프리터 종료 시 문제가 됩니다.
//   가능하면 join 하거나, 스레드 풀 + 명시적 종료를 쓰세요.

// ✅ 더 파이썬다운 방법 — Future 를 돌려주기
py::object run_future(py::array_t<double> a) {
    py::object fut = py::module_::import("concurrent.futures")
                        .attr("Future")();
    std::thread([a, fut]() mutable {
        double r;
        { py::gil_scoped_release rel; r = compute(a); }
        py::gil_scoped_acquire acq;
        fut.attr("set_result")(r);
    }).detach();
    return fut;
}
//   파이썬: f = fastmod.run_future(arr); f.result()
더 간단한 대안 — 비동기가 필요하면 C++ 에서 스레드를 만들지 말고, GIL 을 놓는 동기 함수를 만든 뒤 파이썬 쪽에서 ThreadPoolExecutor 로 감싸는 편이 훨씬 안전하고 디버깅도 쉽습니다(y07).

한 단계 더 — 콜백 비용을 재 보기 🧬 전문가

호출 하나에 드는 것

C++ → 파이썬 콜백 한 번에 일어나는 일

  ① GIL 획득            (경합이 없으면 수백 ns, 있으면 수 μs)
  ② 인자를 파이썬 객체로 변환  (int·float 도 객체 할당이 필요)
  ③ 파이썬 함수 호출     (프레임 생성 · 바이트코드 실행)
  ④ 반환값을 C++ 로 변환
  ⑤ GIL 해제

  합계 대략 1μs 안팎 — 계산이 그보다 짧으면 콜백이 지배합니다.

비교 감각
  · C++ 함수 호출          ~1ns
  · 가상 함수 호출          ~2ns
  · 파이썬 함수 호출        ~50ns  (파이썬 안에서)
  · C++ → 파이썬 콜백      ~1000ns ★ 1000배 차이

  → "원소마다 콜백"이 왜 안 되는지가 숫자로 설명됩니다.
