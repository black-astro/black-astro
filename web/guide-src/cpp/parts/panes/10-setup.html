SETUP 01

컴파일러 고르기 — MSVC · GCC · Clang 무엇을 언제

파이썬은 “파이썬을 깐다”가 끝입니다. C++ 는 컴파일러가 여러 종류이고, 어느 것을 깔았느냐에 따라 명령어도 에러 메시지도 만들어지는 파일도 달라집니다. 그래서 가장 먼저 결정할 것은 컴파일러입니다. 5분이면 정해집니다.

“무엇을 깔까”는 무엇을 만들 것인가로 정해집니다 — 성능 차이로 고르는 것이 아닙니다.

“Visual Studio 를 깔아야 하나요” — 아닙니다. 컴파일러만 필요하면 Build Tools(편집기 없는 버전)로 충분하고 용량도 훨씬 작습니다. IDE 를 쓰고 싶으면 Community 를 깔면 됩니다 — 컴파일러는 같은 것이 들어갑니다. s02 에서 둘 다 다룹니다.

같은 코드, 다른 명령 — 첫 인상

# 같은 hello.cpp 를 셋으로 빌드하면

# ① MSVC — 개발자 명령 프롬프트에서
cl /std:c++20 /EHsc /O2 hello.cpp
# → hello.obj · hello.exe 가 나옵니다

# ② GCC (MSYS2 UCRT64 · 리눅스 · 맥)
g++ -std=c++20 -O2 hello.cpp -o hello

# ③ Clang
clang++ -std=c++20 -O2 hello.cpp -o hello

# ④ Clang 을 MSVC 처럼 쓰기 (윈도우 전용 · 플래그가 cl 과 같음)
clang-cl /std:c++20 /EHsc /O2 hello.cpp
플래그 모양이 다릅니다 — MSVC 는 / 로 시작하고 GCC·Clang 은 - 로 시작합니다. 인터넷에서 복사한 명령이 안 먹는다면 대부분 이 차이입니다. 그래서 실무에서는 손으로 치지 않고 CMake 에 맡깁니다(s06).

한 단계 더 — 진짜 차이는 “런타임”입니다 🟡 중급

왜 섞어 쓰면 안 되나 — ABI

컴파일러가 다르면 만들어 낸 .lib/.a 파일을 서로 못 씁니다. std::string 이 메모리에 놓이는 모양, 예외를 던지는 방식, 이름을 붙이는 규칙(맹글링)이 컴파일러마다 다르기 때문입니다. 이것을 ABI(Application Binary Interface)라고 합니다.

표준 라이브러리C 런타임
MSVCMS STLUCRT (msvcp140.dll)
MinGW UCRT64libstdc++UCRT
MinGW MINGW64libstdc++msvcrt.dll (옛것)
리눅스 GCClibstdc++glibc
맥 Clanglibc++libSystem
실전 규칙 — 하나의 실행 파일 안에서는 컴파일러를 하나만 씁니다. MSVC 로 만든 .lib 를 g++ 로 링크하면 undefined reference 폭탄을 맞습니다. 꼭 섞어야 하면 경계를 C 함수(extern "C")로 만들어야 합니다.

파이썬·Node 확장을 만들 거라면 ★

여기에는 선택의 여지가 거의 없습니다. 확장 모듈은 그 파이썬(또는 Node)을 빌드한 컴파일러와 같은 계열로 빌드해야 합니다.

대상써야 하는 컴파일러

윈도우 · Node LTSMSVC (node-gyp) ★
리눅스 휠(manylinux)GCC (도커 안)
맥 휠Apple Clang
MSYS2 파이썬MSYS2 GCC (짝이 맞을 때만)
가장 흔한 함정 — 윈도우에서 MSYS2 의 g++ 로 python.org 파이썬용 .pyd 를 만들려다 실패합니다. 둘의 런타임이 다르기 때문입니다. 윈도우에서 파이썬 확장을 만들 계획이라면 s02 의 MSVC 는 선택이 아니라 필수입니다.

실무에선 이렇게 — 셋 다 깔고 CMake 로 고릅니다 🔴 실무

같은 소스, 컴파일러만 바꿔 빌드

# 빌드 폴더를 컴파일러마다 따로 두는 것이 핵심입니다
# (한 폴더에서 컴파일러를 바꾸면 CMakeCache 가 꼬입니다 — s12)

cmake -S . -B build-msvc  -G "Visual Studio 17 2022" -A x64
cmake -S . -B build-gcc   -G Ninja -DCMAKE_CXX_COMPILER=g++
cmake -S . -B build-clang -G Ninja -DCMAKE_CXX_COMPILER=clang++

cmake --build build-msvc  --config Release
cmake --build build-gcc
cmake --build build-clang

# 셋 다 통과하면 "이식성이 있다"고 말할 수 있습니다.
# 실제로 CI 는 이걸 매 커밋마다 돌립니다.
왜 셋 다 돌려 보나 — 컴파일러마다 잡아내는 실수가 다릅니다. GCC 만 잡는 경고, Clang 만 잡는 경고, MSVC 에서만 나는 링크 에러가 각각 있습니다. 공짜 코드 리뷰어 세 명이라고 생각하면 됩니다.

지금 뭐가 깔려 있는지부터 확인

# 윈도우 PowerShell — 셋 다 물어봅니다
g++ --version
clang++ --version
cl                       # 버전만 뱉고 끝나면 정상

# 어디에 있는 것을 쓰고 있나 (★ 이게 더 중요합니다 — s11)
where.exe g++
where.exe cl

# 맥 · 리눅스
g++ --version ; clang++ --version
which -a g++ clang++

# 아무 것도 안 나오면 → 아직 아무것도 안 깔린 상태입니다.
# s02(윈도우) 또는 s05(맥·리눅스)로 가세요.
당장 깔기 싫다면 — godbolt.org(Compiler Explorer)에서 브라우저로 MSVC·GCC·Clang 전부를 바로 돌려 볼 수 있습니다. 문법을 익히는 동안은 이걸로 충분하지만, 라이브러리를 쓰고 파일을 읽는 순간부터는 로컬 환경이 필요합니다.
정리 — 컴파일러는 MSVC · GCC · Clang 셋입니다. 윈도우에서 파이썬·Node 확장이나 윈도우 전용 앱을 만들면 MSVC, 리눅스 서버에 올릴 코드면 GCC, 진단 도구가 필요하면 Clang. 하나의 실행 파일 안에서는 섞지 않습니다.
SETUP 02

윈도우 ① — Visual Studio Build Tools 설치

윈도우에서 C++ 를 한다면 여기서 시작합니다. 파이썬 확장도, Node 애드온도, 대부분의 윈도우용 라이브러리도 전부 이 컴파일러를 전제로 합니다. 화면에 뭐가 뜨는지, 어디를 체크해야 하는지 하나씩 따라가겠습니다.

  --override "--quiet --wait --norestart --nocache ^
    --add Microsoft.VisualStudio.Workload.VCTools ^
    --add Microsoft.VisualStudio.Component.VC.CMake.Project ^

④ PowerShell 에서 개발 환경 켜기 ★

# (자식 프로세스에서 설정되고 끝나기 때문입니다 — s12)

        -latest -property installationPath

cl          # ← 이제 같은 창에서 됩니다

무엇이 좋은가
  · MSVC 버전이 올라가도 그대로 동작
  · 32/64비트를 창마다 다르게 쓸 수 있음
  · 다른 툴체인(GCC)과 PATH 가 충돌하지 않음  ← ★
C 언어만 쓸 거라도 같습니다 — MSVC 는 cl.exe 하나가 C 와 C++ 를 모두 컴파일합니다. 확장자가 .c 면 C 로, .cpp 면 C++ 로 처리합니다. 강제하려면 /TC(C) · /TP(C++) 를 씁니다. 참고로 MSVC 의 C 지원은 C11 · C17 이며(/std:c11, /std:c17), C23 지원은 아직 부분적입니다 — 최신 C 표준이 필요하면 s03 의 GCC 를 쓰세요.

clang-cl — MSVC 인 척하는 Clang 🟡 중급

왜 clang-cl 인가

clang-cl.exe 는 플래그와 ABI 를 MSVC 와 똑같이 맞춘 Clang 입니다. MSVC 로 빌드한 .lib 와 섞어 쓸 수 있으면서, 진단 메시지와 sanitizer 는 Clang 것을 씁니다. 

# 개발자 명령 프롬프트(s02)에서 — cl 대신 clang-cl 만 바꿔 치기
clang-cl /std:c++20 /EHsc /W4 /O2 hello.cpp

# CMake 에서 통째로 바꾸기
cmake -S . -B build-clangcl -G Ninja ^
  -DCMAKE_C_COMPILER=clang-cl ^
  -DCMAKE_CXX_COMPILER=clang-cl ^
  -DCMAKE_LINKER=lld-link

# Visual Studio 프로젝트에서도 고를 수 있습니다
#   프로젝트 속성 → 일반 → 플랫폼 도구 집합 → "LLVM (clang-cl)"
#   (VS 설치기에서 "Windows용 C++ Clang 도구" 를 체크했을 때만 보입니다)
실무에서 언제 쓰나 — ① MSVC 가 못 잡는 버그를 ASan 으로 잡을 때, ② 링크가 너무 느려 lld-link 로 바꿀 때, ③ 팀 전체가 clang-tidy 규칙을 쓸 때.

SETUP 05

macOS 와 Linux — 명령 한두 줄이면 끝납니다

윈도우에 비하면 허무할 정도로 간단합니다. 컴파일러가 OS 에 이미 있거나 패키지 관리자 한 줄이면 들어옵니다. 대신 “기본 컴파일러가 너무 낡았다”는 다른 종류의 문제가 생기는데, 그 해결까지 같이 봅니다.

맥·리눅스의 어려움은 설치가 아니라 버전이 낡은 것입니다 — 그 해결이 이 섹션의 핵심.

macOS — 명령줄 도구부터

# ① Xcode Command Line Tools (컴파일러 · make · git · 헤더)
xcode-select --install
#   → 팝업이 뜹니다. "설치"를 누르고 몇 분 기다립니다 (약 1~2GB)
#   Xcode 앱 전체(15GB)는 필요 없습니다. iOS 앱을 만들 때만 받으세요.

# ② 확인
clang --version         # Apple clang version 1x.x.x
xcode-select -p         # /Library/Developer/CommandLineTools
xcrun --show-sdk-path   # SDK 위치 — 헤더를 못 찾을 때 확인
make --version
git --version

# ③ 문제가 생겼을 때 (업데이트 후 헤더를 못 찾는 경우)
sudo rm -rf /Library/Developer/CommandLineTools
sudo xcode-select --install

# Xcode 앱도 깔려 있다면 어느 쪽을 쓸지 정합니다
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
sudo xcode-select -s /Library/Developer/CommandLineTools   # 되돌리기

SETUP 06

CMake 와 Ninja — 첫 프로젝트를 만들어 봅니다

컴파일러를 깔았으니 이제 손으로 g++ 를 치지 않는 법을 배웁니다. CMake 는 “어떤 OS·어떤 컴파일러든 같은 두 줄로 빌드되게” 해 주는 도구이고, C++ 세계의 사실상 표준입니다. vcpkg·IDE·CI 가 전부 CMake 를 전제로 돌아갑니다.

외울 명령은 구성 한 줄 · 빌드 한 줄입니다 — 나머지는 CMake 가 알아서 합니다.

① CMake 설치 — 윈도우

https://cmake.org/download/

  ▸ "Binary distributions" 표에서
      Windows x64 Installer:  cmake-4.x.x-windows-x86_64.msi   ← ★
      (ARM 노트북이면 windows-arm64.msi)

  ▸ 설치 마법사 두 번째 화면 — 반드시 고르세요
      ○ Do not add CMake to the system PATH
      ◉ Add CMake to the system PATH for all users     ← ★ 이것
      ○ Add CMake to the system PATH for current user
      ☐ Create CMake Desktop Icon

또는 명령 한 줄:
  winget install --id Kitware.CMake

MSYS2 를 쓴다면 (UCRT64 셸에서):
  pacman -S mingw-w64-ucrt-x86_64-cmake

확인:

  where.exe cmake
“Add to PATH” 를 놓쳤다면 다시 깔 필요 없습니다 — 제어판에서 지우고 다시 설치하거나, s03 의 PATH 등록 방법으로 C:\Program Files\CMake\bin 을 직접 넣으면 됩니다.

② Ninja 설치 — 왜 필요한가

# Ninja 는 "실제로 컴파일을 실행하는" 도구입니다.
# CMake 는 지시서를 만들고, Ninja 가 그걸 최대 속도로 수행합니다.
# make 보다 빠르고, 윈도우에서도 잘 돕니다.

# 윈도우
winget install --id Ninja-build.Ninja
#   수동: https://github.com/ninja-build/ninja/releases
#         ninja-win.zip → ninja.exe 하나뿐입니다.
#         C:\tools\ninja\ 에 풀고 그 폴더를 PATH 에 추가

# MSYS2
pacman -S mingw-w64-ucrt-x86_64-ninja

# 맥 / 리눅스
brew install ninja
sudo apt install ninja-build

# 확인
ninja --version          # 1.1x.x

# ★ Visual Studio Build Tools 를 깔았다면 이미 들어 있습니다
#   ...\BuildTools\Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\ninja.exe
얼마나 빨라지나 — 파일 200개 프로젝트에서 make 대비 체감 1.5~3배, 특히 “바뀐 것이 없을 때 다시 빌드”가 거의 즉시 끝납니다. 개발 중에는 이 차이가 가장 크게 느껴집니다.

첫 프로젝트 — 파일 두 개 🟢 기초

③ 폴더와 파일 만들기

hello/
├── CMakeLists.txt      ← 빌드 설명서 (내가 쓰는 파일)
├── src/
│   └── main.cpp        ← 소스
└── build/              ← ★ CMake 가 만드는 폴더. 손대지 않습니다
    ├── CMakeCache.txt      탐지 결과
    ├── build.ninja         실제 빌드 지시서
    ├── compile_commands.json   편집기가 읽는 파일 (s08)
    └── hello.exe           결과물

── 규칙 두 가지 ──
 ① 소스 폴더와 빌드 폴더를 분리합니다 (out-of-source build)
    소스 폴더에서 cmake . 를 치면 산출물이 소스에 섞여 지옥이 됩니다
 ② build/ 는 .gitignore 에 넣습니다
    언제든 지우고 다시 만들 수 있어야 정상입니다
// src/main.cpp
#include <iostream>
#include <string>

int main() {
    std::string who = "world";
    std::cout << "hello, " << who << "!\n";
    return 0;
}

④ 최소 CMakeLists.txt — 이 12줄이면 충분

cmake_minimum_required(VERSION 3.25)

project(hello VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)          # -std=gnu++20 대신 -std=c++20

# 편집기 자동완성용 파일을 만들게 합니다 (s08 에서 씁니다) ★
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

add_executable(hello src/main.cpp)

# 경고를 컴파일러별로 켜기
target_compile_options(hello PRIVATE
  $<$<CXX_COMPILER_ID:MSVC>:/W4>
  $<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wall;-Wextra;-Wpedantic>)
$<...> 는 뭔가요 — 제너레이터 표현식입니다. “MSVC 일 때만 /W4” 처럼 구성 시점이 아니라 빌드 시점에 결정되는 값을 씁니다. 지금은 복사해 쓰는 관용구로 생각하면 됩니다.

빌드하고 실행 — 명령 두 줄 🟢 기초

⑤ 실제로 돌려 보기

# ① 구성 — 한 번만 (컴파일러 탐지 · 빌드 폴더 생성)
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release

#   -S .        소스 폴더 (CMakeLists.txt 가 있는 곳)
#   -B build    빌드 폴더 (없으면 만듭니다)
#   -G Ninja    생성기. 안 주면 OS 기본값(윈도우=VS, 리눅스=Make)
#   -DCMAKE_BUILD_TYPE=Release   최적화 켜기 (Ninja/Make 에서 필수 ★)

# ② 빌드 — 고칠 때마다 이것만
cmake --build build

# 병렬 · 자세히 보기
cmake --build build -j 8
cmake --build build --verbose        # 실제 컴파일 명령을 보여 줍니다

# ③ 실행
./build/hello              # 윈도우: .\build\hello.exe

# 청소
cmake --build build --target clean
rm -rf build               # 완전 초기화 (윈도우: Remove-Item -Recurse build)
Visual Studio 생성기는 다릅니다 — -G "Visual Studio 17 2022" 는 멀티 구성이라 CMAKE_BUILD_TYPE 이 무시됩니다. 대신 빌드할 때 --config Release 를 줍니다. 결과물도 build\Release\hello.exe 처럼 한 층 더 들어갑니다.

자주 쓰는 CMake 명령 모음

명령하는 일
cmake -S . -B build구성
cmake --build build빌드
cmake --build build -t clean산출물 지우기
cmake --install build --prefix out설치
ctest --test-dir build테스트 실행
cmake -L build설정된 옵션 보기
cmake --fresh -S . -B build캐시 버리고 재구성 ★
cmake --help-module FindZLIB내장 문서
cmake -G쓸 수 있는 생성기 목록
--fresh 를 기억하세요(CMake 3.24+) — “컴파일러를 바꿨는데 안 먹는다”, “옵션이 반영이 안 된다” 의 90%는 낡은 CMakeCache.txt 때문입니다. 이 옵션이 그걸 버리고 다시 구성합니다.

라이브러리를 여러 개로 나눌 때 — 규모가 커지면 add_library(core STATIC src/a.cpp src/b.cpp) 로 묶고 target_include_directories(core PUBLIC include), target_link_libraries(hello PRIVATE core) 로 연결합니다. 핵심 규칙 하나 — include_directories() 같은 전역 명령을 쓰지 말고 target_* 명령만 쓰세요. 이것이 “현대 CMake” 의 전부라고 해도 과언이 아닙니다.
정리 — CMake 는 설치 시 PATH 체크박스가 중요하고, 프로젝트는 CMakeLists.txt 12줄이면 시작됩니다. 명령은 cmake -S . -B build -G Ninja 와 cmake --build build 두 줄. 안 될 때는 --fresh 를 떠올리세요.

코드 품질 도구 — format · tidy · sanitizer 를 켭니다

C++ 는 틀린 코드도 잘 컴파일됩니다. 배열 밖을 읽어도, 해제한 메모리를 써도 컴파일러는 아무 말 없이 .exe 를 만들어 줍니다. 그래서 도구를 켜는 것이 문법을 배우는 것만큼 중요합니다. 설치는 대부분 이미 끝났고, 여기서는 설정 파일을 두는 것이 전부입니다.

단계마다 잡히는 버그의 종류가 다릅니다 — 하나로 다 잡을 수 있다는 도구는 없습니다.

if (MSVC)
  add_compile_options(/W4 /permissive- /Zc:__cplusplus /utf-8)
  # /WX  = 경고를 에러로 (CI 에서만 켜는 것을 권합니다)
else()
  add_compile_options(
    -Wall -Wextra -Wpedantic
    -Wshadow            # 안쪽 변수가 바깥 변수를 가림
    -Wconversion        # 값이 잘리는 암묵 변환
    -Wsign-conversion
    -Wnon-virtual-dtor  # 다형 기반 클래스인데 소멸자가 virtual 아님
    -Wold-style-cast    # C 스타일 캐스트
    -Wnull-dereference
    -Wdouble-promotion
    -Wformat=2)
  # -Werror  ← CI 에서만

/utf-8 은 한국어 개발자에게 특히 중요합니다 — MSVC 는 소스 인코딩을 시스템 코드 페이지(CP949)로 가정합니다. UTF-8 로 저장한 파일에 한글 문자열이 있으면 C4819 경고가 뜨거나 글자가 깨집니다. 이 플래그 하나로 해결됩니다.

설치가 안 된 게 아니라 못 찾는 것인 경우가 압도적으로 많습니다. “왜 g++ 가 안 되지”, “왜 다른 버전이 잡히지”, “왜 VS Code 에서만 안 되지” — 전부 PATH 이야기입니다. 이 섹션만 이해하면 설치 문제의 절반이 사라집니다.

왜 터미널을 다시 열어야 하나 ★

프로세스는 시작할 때 환경 변수를 한 번 복사해 갖고 있습니다. 나중에 레지스트리를 고쳐도 이미 떠 있는 프로그램은 모릅니다. 그래서 PATH 를 바꾸면 터미널을, 때로는 VS Code 나 탐색기까지 다시 열어야 합니다. 

# 새 창을 열지 않고 현재 세션에만 반영 (임시)

# 레지스트리에서 다시 읽어 현재 세션을 갱신 (반영구적으로 편함)
function Update-Env {
  $m = [Environment]::GetEnvironmentVariable('Path','Machine')
  $u = [Environment]::GetEnvironmentVariable('Path','User')
  $env:Path = "$m;$u"
}
Update-Env

VS Code 가 유독 안 될 때 — VS Code 는 시작될 때의 환경을 그대로 씁니다. 탐색기에서 아이콘으로 실행했다면 탐색기(explorer.exe)의 환경을 물려받습니다. PATH 를 고친 뒤에는 VS Code 를 완전히 종료(모든 창)하고 다시 여세요. 가장 확실한 것은 로그아웃 후 다시 로그인입니다.

정리 — PATH 는 앞에서부터 찾다가 처음 만난 것을 씁니다. 그래서 순서가 곧 결과입니다. 바꿨으면 터미널(그리고 VS Code)을 새로 여세요. 확인은 where.exe / which -a, 추가는 setx 대신 PowerShell 스크립트로.
