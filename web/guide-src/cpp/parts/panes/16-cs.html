다섯 갈래 중 어디로 갈 것인가 — 2026년의 기본값

C++ 를 C# 에서 부르는 방법은 다섯 가지입니다. 그런데 실제로 고민할 가치가 있는 건 두 개뿐이고, 나머지 셋은 “이런 조건일 때만” 이라는 꼬리표가 붙습니다. 먼저 그 지도를 그려 놓고 시작합니다.

고민의 90%는 첫 줄에서 끝납니다 — C ABI 함수 + LibraryImport가 2026년의 기본값입니다.

표를 한 줄로 요약하면 — 크로스 플랫폼이 필요하면 선택지는 P/Invoke 계열뿐입니다. C++/CLI 와 COM 은 윈도우에 못 박히고, 자동 생성은 결국 P/Invoke 코드를 대신 써 주는 도구입니다. 즉 다섯 갈래가 아니라 “P/Invoke 를 손으로 쓰느냐, 생성기에 맡기느냐, 윈도우 전용을 감수하느냐” 셋입니다.

가장 짧은 길 — 이 정도면 끝입니다

// native/mylib.cpp  — C++ 쪽은 이 한 겹만 얹으면 됩니다
#include <cstdint>

extern "C" {                       // 이름 맹글링을 끕니다 (🔗 C ABI 탭 참고)

#if defined(_WIN32)
  #define API __declspec(dllexport)
#else
  #define API __attribute__((visibility("default")))
#endif

API int32_t mylib_add(int32_t a, int32_t b) { return a + b; }

}   // extern "C"
// Program.cs — C# 쪽은 선언 한 개, 호출 한 줄
using System.Runtime.InteropServices;

internal static partial class Native
{
    [LibraryImport("mylib")]          // mylib.dll · libmylib.so · libmylib.dylib
    internal static partial int mylib_add(int a, int b);
}

Console.WriteLine(Native.mylib_add(2, 40));   // 42
이게 전부입니다 — 중간에 어떤 런타임도, 브리지 라이브러리도 없습니다. C# 이 OS 의 동적 로더로 .dll/.so 를 열고, 심볼 주소를 찾아, 그대로 점프합니다. 파이썬의 ctypes, 자바의 FFM 과 정확히 같은 원리입니다.

P/Invoke — 구방식과 새 방식

// ① 구방식 DllImport — .NET Framework 시절부터 쓰던 것
//    런타임이 실행 중에 마샬링 코드(IL 스텁)를 만들어 냅니다
[DllImport("mylib", CharSet = CharSet.Ansi,
           CallingConvention = CallingConvention.Cdecl,
           SetLastError = true)]
static extern int mylib_greet(string name, byte[] buf, int cap);


// ② 새 방식 LibraryImport — .NET 7 부터. 컴파일 시점에 코드 생성 ★
//    생성된 C# 소스를 눈으로 볼 수 있고, NativeAOT 에서도 그대로 돕니다
[LibraryImport("mylib", StringMarshalling = StringMarshalling.Utf8,
               SetLastError = true)]
[UnmanagedCallConv(CallConvs = [typeof(CallConvCdecl)])]
internal static partial int mylib_greet(string name, Span<byte> buf, int cap);
//              ^^^^^^^ partial 필수 · 담는 class 도 partial 이어야 합니다
둘의 진짜 차이 — 문법이 아니라 마샬링 코드가 언제 만들어지느냐입니다. DllImport 는 실행 중에 런타임이 IL 을 짜냅니다(그래서 NativeAOT·트리밍에서 삐걱거립니다). LibraryImport 는 빌드할 때 평범한 C# 코드를 생성합니다 — 디버거로 한 줄씩 밟을 수 있고, 무엇이 복사되는지 눈으로 보입니다.

C++/CLI 와 자동 생성은 이런 모양

// ③ C++/CLI — 한 파일 안에서 관리 코드와 네이티브 코드를 섞습니다
//    (Wrapper.cpp · /clr 로 컴파일 · 윈도우 전용)
public ref class Engine {                 // ref class = .NET 클래스
    NativeEngine* impl_;                  // 네이티브 객체를 그대로 소유
public:
    Engine(int w)  { impl_ = new NativeEngine(w); }
    ~Engine()      { delete impl_; }      // → C# 의 Dispose()
    !Engine()      { delete impl_; }      // → 종료자(finalizer)
    double Score(System::String^ s);      // C# 이 그냥 호출합니다
};

swig -csharp -c++ -namespace MyLib -outdir gen/ mylib.i

#    CppSharp / ClangSharp 는 .NET 프로그램으로 실행합니다

ClangSharpPInvokeGenerator @generate.rsp     # 설정 파일로 옵션을 넘깁니다

# 결과물은 결국 [DllImport]/[LibraryImport] 가 잔뜩 붙은 .cs 파일입니다
자동 생성의 위치 — “바인딩을 대신 타이핑해 주는 도구”지, 새로운 연결 방식이 아닙니다. 그래서 생성기가 만든 코드를 읽을 줄 알아야 쓸 수 있고, 그건 결국 이 탭의 k02~k07 을 아는 것과 같습니다.

언제 P/Invoke 를 “쓰지 않는” 게 맞나

상황더 나은 선택
단순 수치 루프C# 으로 Span+SIMD — 경계 비용이 이득을 먹습니다
호출이 초당 수백만 번C++ 쪽에서 배치로 묶어 한 번에
서로 다른 프로세스여도 됨gRPC · 파이프 — 크래시가 격리됩니다
C++ 코드가 아직 없음먼저 C# 으로 만들고 측정한 뒤 결정
GPU 를 쓰고 싶다ComputeSharp · ILGPU · CUDA 래퍼
가장 흔한 실수 — “C++ 가 빠르니까”로 시작해서, 정작 경계를 1억 번 넘나드는 설계를 만드는 것입니다. P/Invoke 한 번의 비용은 대략 1~5ns(빈 함수 기준)로 아주 작지만, 마샬링이 붙으면 수십~수백 ns가 됩니다. 이득은 한 번의 호출이 하는 일의 크기에서 나옵니다.

.NET 10 프로젝트 기본 설정

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>

    <!-- ★ LibraryImport 가 생성하는 코드는 unsafe 를 씁니다 -->

EmitCompilerGeneratedFiles 를 꼭 켜 보세요 — obj/Debug/net10.0/generated/…/LibraryImportGenerator/… 에 실제로 실행될 마샬링 코드가 평범한 C# 으로 떨어집니다. “어디서 복사가 일어나는가”를 추측하지 않고 읽어서 알 수 있게 됩니다.

한 단계 더 — 왜 소스 생성기가 이겼나 🧬 전문가

런타임 IL 스텁 vs 컴파일 시점 생성

[DllImport] — 실행 중에 벌어지는 일
  ① 처음 호출되는 순간 런타임이 시그니처를 읽습니다
  ② 마샬링 규칙을 해석해 IL 스텁을 '즉석에서' 만듭니다
  ③ 그 IL 을 JIT 가 기계어로 번역합니다
  ④ 이후 호출은 그 기계어로 직행 (그래서 두 번째부터는 빠릅니다)

  문제 : ①~③ 이 '실행 중 코드 생성'입니다
     → NativeAOT 는 실행 중 코드 생성을 못 합니다
     → 트리머는 어떤 타입이 마샬링에 쓰이는지 알 수 없어 못 지웁니다
     → 무엇이 복사되는지 소스로 확인할 방법이 없습니다

[LibraryImport] — 빌드할 때 벌어지는 일
  ① Roslyn 생성기가 partial 선언을 봅니다
  ② 평범한 C# 파일을 만들어 컴파일에 끼워 넣습니다
       fixed / GCHandle / Utf8 인코딩이 전부 소스로 보입니다
  ③ 남는 것은 순수한 unsafe 호출 하나 (extern 그대로)

  결과 : NativeAOT 완전 호환 · 트리밍 안전 · 디버거로 밟기 가능

경계 비용을 실제로 재 보기

// dotnet add package BenchmarkDotNet

using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class Boundary
{
    [Benchmark(Baseline = true)]
    public int Managed() => 2 + 40;                  // 순수 C#

    [Benchmark]

    [Benchmark]
    public int PInvokeString() => Native.mylib_len("hello world");
}
BenchmarkRunner.Run<Boundary>();

/* 참고용 결과의 '모양' (수치는 기계마다 다릅니다)
   Managed              0.3 ns   1.00x
   PInvokeBlittable     2~4 ns   약 10x        ← blittable 만이면 거의 공짜
   PInvokeString      60~150 ns  수백 x        ← UTF-8 인코딩 + 할당이 붙음
*/
여기서 얻을 결론 — blittable 인자만 쓰는 호출은 사실상 공짜이고, 비싼 것은 P/Invoke 자체가 아니라 문자열·배열·구조체 변환입니다. 그래서 이 탭의 절반(k03·k04)이 “변환을 없애는 법”에 쓰입니다.
정리 — 새 프로젝트라면 고민하지 말고 extern "C" 함수 + [LibraryImport] 입니다. C++/CLI 는 “윈도우 전용 + 기존 C++ 클래스가 산더미”일 때만, 자동 생성은 “헤더가 수천 줄”일 때만, COM 은 “이미 있어서 어쩔 수 없을 때만” 꺼냅니다.
C# 02

첫 P/Invoke — 10분이면 호출됩니다

설명은 뒤로 미루고 실제로 도는 것을 먼저 만듭니다. C++ 파일 하나, C# 파일 하나, 그리고 DLL 을 어떻게 실행 폴더까지 데려가느냐 — 초보가 막히는 지점은 사실 마지막 하나뿐입니다.

막히는 지점은 대부분 ①②가 아니라 “DLL 이 출력 폴더에 없다” 하나입니다.

C++ 쪽 — 공유 라이브러리 한 개

// native/mylib.cpp
#include <cstdint>
#include <cmath>

#if defined(_WIN32)
  #define MYLIB_API __declspec(dllexport)
#else
  #define MYLIB_API __attribute__((visibility("default")))
#endif

extern "C" {

MYLIB_API int32_t mylib_add(int32_t a, int32_t b) {
    return a + b;
}

// 배열을 제자리에서 처리 — C# 이 넘겨준 메모리를 그대로 씁니다
MYLIB_API void mylib_scale(double* data, int64_t n, double k) {
    for (int64_t i = 0; i < n; ++i) data[i] *= k;
}

// 버전 확인용 — 붙었는지 가장 먼저 확인하는 함수를 하나 두면 편합니다
MYLIB_API int32_t mylib_version(void) { return 1; }

}   // extern "C"
# native/CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(mylib LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 20)

add_library(mylib SHARED mylib.cpp)          # ★ SHARED — .dll / .so / .dylib

# 내보내기를 명시한 것만 밖으로 (리눅스·맥에서 심볼 노출을 줄입니다)
set_target_properties(mylib PROPERTIES
    CXX_VISIBILITY_PRESET hidden
    VISIBILITY_INLINES_HIDDEN ON
    WINDOWS_EXPORT_ALL_SYMBOLS OFF)

// App/Native.cs
using System.Runtime.InteropServices;

internal static partial class Native
{
    private const string Lib = "mylib";   // 확장자·lib 접두사는 붙이지 않습니다

    [LibraryImport(Lib)]
    internal static partial int mylib_add(int a, int b);

    [LibraryImport(Lib)]
    internal static partial int mylib_version();

    // double[] 은 blittable → 핀 고정만 하고 그대로 넘어갑니다 (복사 없음)
    [LibraryImport(Lib)]
    internal static partial void mylib_scale(Span<double> data, long n, double k);
}
// App/Program.cs
Console.WriteLine($"lib v{Native.mylib_version()}");     // v1
Console.WriteLine(Native.mylib_add(2, 40));              // 42

double[] xs = [1, 2, 3];
Native.mylib_scale(xs, xs.Length, 10);
Console.WriteLine(string.Join(", ", xs));                // 10, 20, 30

가장 단순한 방법 — csproj 에 복사 규칙 ★

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <AllowUnsafeBlocks>true</AllowUnsafeBlocks>
  </PropertyGroup>

  <!-- ① 프로젝트 폴더 안에 있는 파일이라면 None Update 로 충분합니다 -->
  <ItemGroup>
    <None Update="mylib.dll">
      <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
    </None>
  </ItemGroup>

  <!-- ② 다른 폴더에서 끌어올 때는 Content Include + Link ★ -->
  <ItemGroup>
    <Content Include="..\native\build\Release\mylib.dll"
             Condition="$([MSBuild]::IsOSPlatform('Windows'))">
      <Link>mylib.dll</Link>
      <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
    </Content>
    <Content Include="..\native\build\libmylib.so"
             Condition="$([MSBuild]::IsOSPlatform('Linux'))">
      <Link>libmylib.so</Link>
      <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
    </Content>
  </ItemGroup>
</Project>
PreserveNewest vs Always — PreserveNewest 는 원본이 더 새로울 때만 복사합니다(빠름). C++ 를 자주 다시 빌드하는 개발 중에는 이게 정답이고, “고쳤는데 반영이 안 된다” 싶으면 bin/ 을 지우고 다시 돌려 보세요.

이름 규칙 — 왜 “mylib” 만 쓰나

[LibraryImport("mylib")] 이라고 쓰면 런타임이 이렇게 찾습니다

  윈도우   mylib.dll  →  mylib
  리눅스   libmylib.so  →  mylib.so  →  libmylib  →  mylib
  맥      libmylib.dylib → mylib.dylib → libmylib → mylib

  ★ 즉 "mylib" 한 이름으로 세 OS 가 전부 해결됩니다

생성기가 만든 코드는 이렇게 생겼습니다

// obj/Debug/net10.0/generated/.../Native.g.cs (의미만 옮긴 것)
internal static partial class Native
{
    internal static unsafe partial void mylib_scale(
        Span<double> data, long n, double k)
    {

        {                       // ★ GC 가 못 옮기게 고정 — 복사가 아닙니다
            __PInvoke(__data, n, k);
        }

        // 진짜 진입점 — 여기서부터는 순수한 네이티브 호출입니다

                   ExactSpelling = true)]
        static extern unsafe void __PInvoke(double* d, long n, double k);

}
읽는 요령 — 생성된 코드에 fixed 만 있으면 “복사 없음”, Marshal.AllocCoTaskMem · Encoding.UTF8.GetBytes · new byte[] 가 보이면 “복사 있음”입니다. 성능이 걱정될 때 프로파일러를 켜기 전에 이 파일부터 열어 보세요. 답이 5초 만에 나옵니다.

마샬링 규칙 — 무엇이 그냥 통과하고 무엇이 변환되나

P/Invoke 의 거의 모든 버그와 거의 모든 비용이 “타입이 경계에서 어떻게 변환되는가” 한 곳에 몰려 있습니다. 규칙은 의외로 짧습니다 — 메모리 모양이 같으면 그냥 통과하고, 다르면 변환기가 낍니다.

왼쪽만 쓰도록 API 를 설계하면 마샬링 버그가 구조적으로 사라집니다.

bool 함정 — 왜 값이 뒤집히나

// C++ 쪽
extern "C" MYLIB_API bool mylib_is_ready(void);   // sizeof(bool) == 1
extern "C" MYLIB_API void mylib_set_flag(bool on);
// ✗ 이렇게 두면 LibraryImport 가 컴파일 에러를 냅니다
//    bool 은 blittable 이 아니라 폭을 알 수 없기 때문입니다
[LibraryImport("mylib")]
internal static partial bool mylib_is_ready();      // SYSLIB1051 계열 오류

// ✓ 폭을 명시합니다 — C++ 의 bool 은 1바이트
[LibraryImport("mylib")]
[return: MarshalAs(UnmanagedType.U1)]
internal static partial bool mylib_is_ready();

[LibraryImport("mylib")]
internal static partial void mylib_set_flag(
    [MarshalAs(UnmanagedType.U1)] bool on);

// ✓ 아예 오해가 불가능하게 — C++ 쪽을 int32_t 로 바꾸는 편이 낫습니다
//    extern "C" int32_t mylib_is_ready(void);
[LibraryImport("mylib")]
internal static partial int mylib_is_ready();       // 0 / 1 로만 약속
왜 이게 사고가 되나 — 구방식 [DllImport] 의 bool 기본값은 Win32 의 4바이트 BOOL 입니다. C++ 의 1바이트 bool 을 받으면 나머지 3바이트의 쓰레기값까지 읽습니다. 값이 “가끔” 틀리는, 최악의 종류의 버그입니다. LibraryImport 가 컴파일 에러로 막아 주는 것이 큰 장점 중 하나입니다.

이렇게도 쓸 수 있다 — 문자열을 주고받는 세 가지 모양 🟡 중급

① 넘기기 · ② 받아오기

// C++ — UTF-8 을 기준으로 삼습니다 (세 OS 공통)
extern "C" {
// ① 받기만 — 소유권은 C# 에 있고 C++ 는 읽기만
MYLIB_API int32_t mylib_len(const char* utf8);

// ② 돌려주기 — C# 이 버퍼를 주고 C++ 가 채웁니다 ★ 가장 안전
//    반환값 = 필요한 바이트 수 (buf 가 작으면 -1)
MYLIB_API int32_t mylib_greet(const char* name, char* buf, int32_t cap);
}
internal static partial class Native
{
    // ① string → const char* : 생성기가 UTF-8 로 인코딩합니다
    [LibraryImport("mylib", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial int mylib_len(string utf8);

    // ② 버퍼는 Span<byte> 로 — 핀 고정만 되고 복사가 없습니다
    [LibraryImport("mylib", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial int mylib_greet(string name, Span<byte> buf, int cap);
}

public static string Greet(string name)
{
    Span<byte> buf = stackalloc byte[256];        // 작은 건 스택에서
    int n = Native.mylib_greet(name, buf, buf.Length);
    if (n < 0) throw new InvalidOperationException("버퍼가 작습니다");
    return Encoding.UTF8.GetString(buf[..n]);     // 여기서 한 번만 복사
}
이 “버퍼를 주고 채워 받는” 모양이 표준입니다 — C++ 가 malloc 한 문자열을 돌려주면 누가 free 하느냐가 매번 문제가 됩니다. C# 이 버퍼를 소유하면 그 질문 자체가 사라집니다. Win32 API 도 대부분 이 모양입니다.

③ C++ 가 할당한 문자열을 받아야 할 때

// C++ 가 소유하는 두 가지 방식
extern "C" {
// (a) 수명이 긴 정적 문자열 — 해제하지 않습니다 (에러 메시지에 적합)
MYLIB_API const char* mylib_last_error(void);

// (b) 새로 할당해 돌려주고 전용 해제 함수를 함께 제공 ★
MYLIB_API char* mylib_render(const char* tpl);
MYLIB_API void  mylib_free_string(char* p);
}
// (a) 해제 불필요 — IntPtr 로 받아 직접 읽습니다
[LibraryImport("mylib")]
private static partial IntPtr mylib_last_error();

public static string LastError() =>
    Marshal.PtrToStringUTF8(mylib_last_error()) ?? "";

// (b) 반드시 같은 라이브러리의 해제 함수로 돌려줍니다
[LibraryImport("mylib", StringMarshalling = StringMarshalling.Utf8)]
private static partial IntPtr mylib_render(string tpl);

[LibraryImport("mylib")]
private static partial void mylib_free_string(IntPtr p);

public static string Render(string tpl)
{
    IntPtr p = mylib_render(tpl);
    if (p == IntPtr.Zero) throw new OutOfMemoryException();
    try { return Marshal.PtrToStringUTF8(p)!; }   // 여기서 C# 이 복사
    finally { mylib_free_string(p); }             // ★ finally 필수
}
절대 Marshal.FreeHGlobal 로 해제하지 마세요 — C++ 가 new[]/malloc 으로 잡은 메모리를 C# 의 할당자로 풀면 힙이 깨집니다. 윈도우에서는 DLL 마다 CRT 힙이 다를 수도 있어 더 위험합니다. “할당한 쪽이 해제한다”가 유일한 안전 규칙입니다.

CallingConvention — 언제 신경 쓰나

// 64비트에서는 호출 규약이 사실상 하나뿐이라 신경 쓸 일이 거의 없습니다.
// 문제가 되는 곳은 딱 둘입니다 — 32비트 윈도우, 그리고 Win32 API.

// ① 명시하는 법 (LibraryImport 방식)
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;

[LibraryImport("mylib")]
[UnmanagedCallConv(CallConvs = [typeof(CallConvCdecl)])]   // 기본값
internal static partial int mylib_add(int a, int b);

[LibraryImport("user32")]
[UnmanagedCallConv(CallConvs = [typeof(CallConvStdcall)])] // Win32 API
internal static partial int MessageBoxW(IntPtr h, string t, string c, uint ty);

// ② 구방식이라면
[DllImport("mylib", CallingConvention = CallingConvention.Cdecl)]
static extern int mylib_add(int a, int b);
32비트에서 규약이 틀리면 — 값은 맞게 돌아오는데 스택이 조금씩 어긋납니다. 몇백 번 호출한 뒤 엉뚱한 곳에서 죽습니다. 증상이 “호출 직후”가 아니라 “한참 뒤에 랜덤하게”라서 원인을 찾기가 최악입니다. 64비트만 지원한다고 못 박는 것이 실무에서 가장 큰 절약입니다.

DisableRuntimeMarshalling

// AssemblyInfo.cs — 어셈블리 전체에 한 번
using System.Runtime.CompilerServices;
[assembly: DisableRuntimeMarshalling]

// 이걸 켜면 어셈블리 안의 모든 P/Invoke 에서
//   · 자동 문자열 변환    → 금지 (직접 byte* 로 다뤄야 함)
//   · 자동 bool 변환      → 금지
//   · 자동 구조체 변환    → 금지 (blittable 만 허용)
//   · [MarshalAs]         → 무시
// 대신
//   · 호출이 '순수한 점프'가 되어 오버헤드가 최소가 됩니다
//   · NativeAOT 와 완전히 일치하는 동작을 보장합니다
//   · 무엇이 복사되는지 실수할 여지가 사라집니다
누가 쓰나 — 그래픽·오디오·게임 엔진 바인딩처럼 초당 수만~수백만 번 호출하고, 타입이 이미 전부 blittable 인 라이브러리입니다(Silk.NET · Vortice 등이 이 방식). 일반 업무 앱에서는 얻는 것보다 잃는 편의가 큽니다 — 필요할 때만 꺼내세요.

    Assert.Equal(16, Native.mylib_sizeof_mystruct());
}
Unsafe.SizeOf 와 Marshal.SizeOf 가 다르면 위험 신호입니다 — 그 타입은 blittable 이 아니라 변환이 일어나고 있다는 뜻입니다. 그리고 C++ 에 크기를 물어보는 함수를 하나 노출해 두는 습관은 “빌드 설정이 달라 패딩이 어긋났다”는 종류의 사고를 테스트에서 잡아 줍니다.
정리 — 메모리 모양이 같으면 공짜, 다르면 변환입니다. 경계에는 고정폭 정수 · 실수 · 포인터만 노출하고, long · bool · size_t 는 피하고, 문자열은 UTF-8 + 버퍼 채우기로 통일하세요.
C# 04

구조체 · 배열 — 복사 없이 넘기는 법

C++ 로 넘어가는 이유가 “빠르게”라면, 경계에서 데이터를 복사하는 순간 그 이유가 절반 사라집니다. 구조체 배치를 C++ 와 똑같이 맞추고 배열을 핀 고정해서 넘기면, 8천만 바이트도 0바이트 복사로 건네집니다.

복사가 있는지 없는지는 생성된 스텁에 fixed 가 보이는지로 확인합니다.

패딩이 어긋나면 어떤 일이 벌어지나

C++ 가 #pragma pack(1) 로 빌드되었는데
C# 은 기본 정렬을 쓰는 경우

  C++  [ id(4) ][ score(8) ]                    = 12바이트
  C#   [ id(4) ][ pad(4) ][ score(8) ]          = 16바이트

  → C# 이 만든 배열의 1번 원소는 오프셋 16
    C++ 는 오프셋 12 를 1번 원소로 읽습니다
  → 값이 '조금씩 밀려서' 나옵니다. 크래시도 안 납니다 ★

C# 05

핸들과 수명 — SafeHandle 로 누수를 구조적으로 막기

C++ 객체는 경계를 넘지 못합니다. 대신 불투명 포인터(핸들)를 건네고, C# 은 그것을 객체처럼 보이게 감쌉니다. 이때 IntPtr 로 들고 있으면 해제를 잊는 순간 그냥 누수이고, SafeHandle 로 감싸면 런타임이 뒤를 봐 줍니다.

누수를 규율이 아니라 타입으로 막는 것이 핵심입니다.

C++ 쪽 — 불투명 핸들 세 함수

// mylib.h — 내부 구조를 절대 노출하지 않습니다
typedef struct MylibEngine MylibEngine;    // 정의 없이 이름만 ★

extern "C" {

// mylib.cpp — 진짜 구현은 평범한 C++ 클래스입니다
struct MylibEngine {
    std::deque<double> buf;

    explicit MylibEngine(int w) : window(w) {}
};

}

C# 06

콜백 — C++ 가 C# 을 부르게 만들기

진행률 보고, 이벤트 알림, 정렬 비교 함수 — 네이티브가 관리 코드를 되부르는 상황은 생각보다 자주 옵니다. 원리는 간단합니다. C# 메서드의 주소를 함수 포인터로 만들어 넘기는 것. 함정은 하나뿐입니다 — GC 가 그 대상을 치워 버릴 수 있다는 것.

“등록은 됐는데 나중에 죽는다”면 열에 아홉은 델리게이트가 수거된 것입니다.

C++ 쪽 — 표준형은 함수 포인터 + user 포인터

// mylib.h
extern "C" {

// ★ 반드시 void* user 를 함께 받습니다 — 이게 없으면
//   "어느 객체에 대한 콜백인지" 를 표현할 방법이 사라집니다
typedef void (*mylib_progress_fn)(int32_t percent, void* user);

MYLIB_API int32_t mylib_run(const double* data, int64_t n,
                            mylib_progress_fn cb, void* user);
}
// mylib.cpp
extern "C" int32_t mylib_run(const double* data, int64_t n,
                             mylib_progress_fn cb, void* user)
{
    const int64_t step = n / 10 > 0 ? n / 10 : 1;
    for (int64_t i = 0; i < n; ++i) {
        ... 무거운 계산 ...
        if (cb && i % step == 0)
            cb(static_cast<int32_t>(i * 100 / n), user);   // 되부르기
    }
    if (cb) cb(100, user);
    return 0;
}
void* user 는 선택이 아니라 필수입니다 — C# 쪽에서 [UnmanagedCallersOnly] 메서드는 정적 메서드여야 합니다. 인스턴스 상태를 되찾을 유일한 통로가 이 user 포인터입니다. C API 를 설계할 때 콜백 인자에 user 를 빠뜨리면 나중에 못 고칩니다(ABI 변경).

C# 쪽 ① — 함수 포인터 방식 (권장) ★

using System.Runtime.InteropServices;

internal static unsafe partial class Native
{
    [LibraryImport("mylib")]
    internal static partial int mylib_run(
        double* data, long n,
        delegate* unmanaged<int, void*, void> cb,   // ★ C# 9+ 함수 포인터
        void* user);
}

public sealed class Runner
{
    public event Action<int>? Progress;

    // 네이티브에서만 부를 수 있는 정적 진입점
    [UnmanagedCallersOnly]
    private static void OnProgress(int percent, void* user)
    {
        // user 로 넘겨 둔 GCHandle 을 되살려 인스턴스를 찾습니다
        var self = (Runner)GCHandle.FromIntPtr((IntPtr)user).Target!;
        self.Progress?.Invoke(percent);
    }

    public unsafe void Run(double[] data)
    {
        var gch = GCHandle.Alloc(this);            // 약한 참조가 아닌 보통 핸들
        try
        {
            fixed (double* p = data)
                Native.mylib_run(p, data.LongLength,
                                 &OnProgress,      // 주소를 그대로
                                 (void*)GCHandle.ToIntPtr(gch));
        }
        finally { gch.Free(); }
    }
}

델리게이트 방식 — 편하지만 규율이 필요합니다

// 인스턴스 메서드와 람다를 쓸 수 있어 편합니다
[UnmanagedFunctionPointer(CallingConvention.Cdecl)]
internal delegate void ProgressDelegate(int percent, IntPtr user);

[DllImport("mylib")]

// ✗ 이렇게 쓰면 언젠가 죽습니다
public void RunBad(double[] data)
{
    mylib_run(data, data.LongLength,
              (p, _) => Console.WriteLine(p),    // 지역 델리게이트 ★
              IntPtr.Zero);
}   // 호출이 진행되는 동안 GC 가 이 델리게이트를 수거할 수 있습니다

// ✓ 필드로 붙잡아 둡니다 — 등록이 살아 있는 동안 계속
private ProgressDelegate? _cb;

public void RunGood(double[] data)
{
    _cb = (p, _) => Progress?.Invoke(p);         // 필드에 보관 ★
    mylib_run(data, data.LongLength, _cb, IntPtr.Zero);
    GC.KeepAlive(_cb);                           // 확실히 하기 위해
}
왜 이런 일이 생기나 — 델리게이트를 네이티브로 넘길 때 런타임은 그 델리게이트를 부르는 작은 네이티브 스텁을 만들어 그 주소를 넘깁니다. C++ 는 그 스텁 주소만 보관하는데, GC 는 “관리 코드에서 아무도 이 델리게이트를 참조하지 않는다”고 판단합니다. 수거되면 스텁도 사라지고, C++ 는 없어진 주소로 점프합니다.

// 런타임은 첫 콜백 때 그 스레드를 자동으로 등록(attach)합니다.
//   → 첫 호출만 수백 마이크로초 걸릴 수 있습니다
//   → 이후는 정상 속도

// 진단 : 콜백이 어느 스레드에서 오는지 확인
[UnmanagedCallersOnly]
private static void OnEvent(int code, void* user)
{
    Debug.WriteLine($"tid={Environment.CurrentManagedThreadId} " +
                    $"pool={Thread.CurrentThread.IsThreadPoolThread}");
}

// 주의 : 그 스레드에서 async/await 를 쓰면 컨텍스트가 없어
//        재개가 스레드풀로 넘어갑니다. 콜백 안에서는 동기 코드만.
프로세스 종료 중에 오는 콜백이 가장 위험합니다 — 런타임이 이미 정리를 시작했는데 C++ 스레드가 살아서 콜백을 부르면 진단조차 어려운 크래시가 납니다. C API 에 mylib_shutdown() 을 반드시 두고, C# 쪽에서 등록을 해제한 뒤 스레드가 멎을 때까지 기다린 다음 종료하세요.
정리 — 콜백은 [UnmanagedCallersOnly] 정적 메서드 + delegate* unmanaged 가 기본형이고, 인스턴스는 void* user 에 실어 둔 GCHandle 로 되찾습니다. 콜백 안에서는 값만 저장하고 즉시 반환, 예외는 절대 밖으로 내보내지 않습니다.
C# 07

예외와 에러 — 경계는 넘지 못합니다

C++ 예외와 .NET 예외는 완전히 다른 메커니즘입니다. 서로를 알지 못하고, 서로를 잡지 못합니다. 경계를 넘으려 하는 순간 스택 트레이스도 로그도 없이 프로세스가 사라집니다. 해결은 단순합니다 — 경계에서 전부 잡아 에러 코드로 바꾸는 것.

경계 함수 하나하나가 “절대 예외를 내보내지 않는다”는 계약을 지켜야 합니다.

C++ 쪽 — 경계를 봉인하는 매크로

// mylib_error.h
#include <string>

enum : int32_t {
    MYLIB_OK          =  0,
    MYLIB_EINVAL      = -1,   // 인자가 잘못됨
    MYLIB_ENOMEM      = -2,   // 메모리 부족
    MYLIB_EIO         = -3,   // 입출력 실패
    MYLIB_EINTERNAL   = -99   // 알 수 없는 예외
};

// 스레드마다 따로 — 멀티스레드에서 메시지가 섞이지 않습니다 ★
inline thread_local std::string g_last_error;

extern "C" MYLIB_API const char* mylib_last_error(void) {
    return g_last_error.c_str();
}
// 모든 경계 함수를 이 매크로로 감쌉니다
#define MYLIB_GUARD(body)                               \
    try { g_last_error.clear(); body }                  \
    catch (const std::bad_alloc&) {                     \
        g_last_error = "메모리 부족"; return MYLIB_ENOMEM; } \
    catch (const std::exception& e) {                   \
        g_last_error = e.what();     return MYLIB_EIO; } \
    catch (...) {                                       \
        g_last_error = "알 수 없는 예외"; return MYLIB_EINTERNAL; }

extern "C" MYLIB_API int32_t mylib_load(const char* path) {
    MYLIB_GUARD({
        if (!path) { g_last_error = "path 가 null"; return MYLIB_EINVAL; }
        do_load(path);                 // 여기서 무엇을 던지든 안전합니다
        return MYLIB_OK;
    })
}
thread_local 이 핵심입니다 — 전역 하나로 두면 스레드 A 의 에러 메시지를 스레드 B 가 읽는 사고가 납니다. ASP.NET Core 처럼 요청마다 스레드가 다른 환경에서는 반드시 스레드 지역이어야 합니다.

public sealed class MylibException : Exception
{
    public int Code { get; }
    public MylibException(int code, string message)
        : base($"{message} (code={code})") => Code = code;
}

internal static class Check
{
    // 모든 호출을 이 한 줄로 감쌉니다 ★
    public static int Ok(int rc)
    {
        if (rc == 0) return rc;

        string msg = Marshal.PtrToStringUTF8(Native.mylib_last_error()) ?? "";
        throw rc switch
        {
            -1 => new ArgumentException(msg),
            -2 => new OutOfMemoryException(msg),
            -3 => new IOException(msg),
            _  => new MylibException(rc, msg),
        };
    }
}

// 사용하는 쪽 — C# 답게 보입니다
public void Load(string path) => Check.Ok(Native.mylib_load(path));
에러 코드를 .NET 표준 예외로 매핑하세요 — 인자 오류는 ArgumentException, 파일은 IOException 처럼. 전부 MylibException 하나로 던지면 쓰는 쪽이 catch 를 세밀하게 쓸 수 없습니다. 코드 값은 Code 프로퍼티로 남겨 두면 필요할 때 꺼내 쓸 수 있습니다.

한 페이지짜리 규약 문서

mylib C API 규약 (버전 1)

  1. 모든 함수는 int32_t 를 반환한다. 0 = 성공, 음수 = 실패.
     · 값을 돌려줘야 하면 출력 포인터로 받는다
         int32_t mylib_sum(const double* d, int64_t n, double* out);

  2. 실패했을 때만 mylib_last_error() 가 의미 있는 문구를 준다.
     · 스레드 지역이며 다음 호출까지만 유효하다
     · 반환된 포인터를 해제하지 않는다

  3. 어떤 함수도 예외를 밖으로 내보내지 않는다.

  4. 어떤 함수도 nullptr 인자에 대해 크래시하지 않는다.
     · nullptr 이면 MYLIB_EINVAL 을 돌려준다

  5. 에러 코드 값은 절대 재사용·재정의하지 않는다.
     · 새 에러는 새 번호를 받는다 (호환성)

  6. mylib_version() 은 언제나 호출 가능하며 실패하지 않는다.
이 여섯 줄이 팀을 구합니다 — 바인딩을 쓰는 사람(C#·파이썬·Node) 모두가 같은 방식으로 코드를 짜게 되고, 새 함수를 추가할 때 무엇을 지켜야 하는지가 명확해집니다. 규약 없는 C API 는 함수마다 다른 규칙을 갖게 되고, 결국 아무도 안 쓰게 됩니다.

C# 08

C++/CLI — 클래스를 통째로 감싸는 길

P/Invoke 는 함수 단위라, C++ 클래스가 수백 개인 코드베이스를 감싸려면 손이 너무 많이 갑니다. C++/CLI 는 한 소스 파일 안에서 .NET 클래스와 C++ 클래스를 같이 쓸 수 있게 해 줍니다. 대가는 분명합니다 — 윈도우 전용.

C++/CLI 의 값은 속도가 아니라 손으로 쓸 바인딩 코드의 양입니다.

감쌀 C++ 클래스

#include <vector>

P/Invoke 로 감싸려면 필요한 것
  · extern "C" 래퍼 함수 5개 (create/destroy/push/value/report)
  · 문자열 반환 규약 · 해제 함수
  · C# 쪽 SafeHandle + 공개 클래스
  → 클래스 하나에 대략 100줄

클래스가 200개라면
  → 20,000줄. 손으로 쓸 양이 아닙니다 ★

C++/CLI 로 감싸면
  · 헤더를 include 하고 ref class 를 하나 쓴다
  · 메서드마다 한두 줄
  → 클래스 하나에 대략 25줄, 그리고 C# 쪽 코드는 0줄

C++/CLI 래퍼 — 이게 전부입니다

// wrapper/EngineWrapper.cpp   (/clr 로 컴파일)
#include "../native/Engine.h"
#include <msclr/marshal_cppstd.h>

using namespace System;

namespace MyLib {

public ref class Engine          // ref class = .NET 클래스입니다
{
    ::Engine* impl_;             // 네이티브 객체를 그대로 소유 (raw 포인터)

public:
    Engine(int window) : impl_(new ::Engine(window)) {}

    ~Engine() { this->!Engine(); }          // → C# 의 Dispose()
    !Engine() { delete impl_; impl_ = nullptr; }   // → 종료자

    void Push(double v) { impl_->Push(v); }

    property double Value {                 // C# 의 프로퍼티가 됩니다
        double get() { return impl_->Value(); }
    }

    String^ Report() {                      // std::string → System::String
        return msclr::interop::marshal_as<String^>(impl_->Report());
    }
};

}   // namespace MyLib
~Engine() 과 !Engine() 의 뜻 — C++/CLI 에서 소멸자(~)는 IDisposable.Dispose() 로, 종료자(!)는 finalizer 로 컴파일됩니다. 즉 ref class 를 하나 쓰면 using 문이 그냥 동작합니다 — SafeHandle 을 직접 쓸 필요가 없습니다.

    impl_->ProcessRaw(p, xs->Length);

    auto out = gcnew List<double>((int)v.size());
    for (double x : v) out->Add(x);
    return out;
}

C++/CLI 의 진짜 장점이 여기 있습니다 — P/Invoke 에서는 불가능했던 “예외를 예외로 변환”이 그냥 됩니다. 같은 프레임 안에서 두 런타임이 함께 살아 있기 때문입니다. std::vector, std::map, 템플릿, 상속까지 그대로 다룰 수 있습니다.

실무에선 이렇게 — 언제 이 길을 고르나 🔴 실무

C++/CLI 가 맞지 않는 경우
✗ 리눅스 컨테이너에 배포할 계획이 조금이라도 있다
    → /clr 는 윈도우에서만 빌드됩니다. 대안이 없습니다.

✗ NativeAOT · 단일 파일 · 트리밍을 쓰고 싶다
    → 혼합 어셈블리는 전부 불가입니다.

✗ 감쌀 것이 함수 몇 개뿐이다
    → 빌드 복잡도만 늘어납니다. P/Invoke 20줄이면 끝납니다.

✗ Unity 에서 쓰려고 한다
    → IL2CPP 와 혼합 어셈블리는 함께 갈 수 없습니다.

✗ 팀에 C++ 를 아는 사람이 없다
    → C++/CLI 는 C++ 와 C# 을 '둘 다' 알아야 읽힙니다.
      배우는 사람이 가장 적은 문법이기도 합니다.
C++/CLI 가 압도적으로 이기는 경우
✓ 윈도우 데스크톱 앱(WPF·WinForms)이 확정이다

✓ 기존 C++ 코드베이스가 수십만 줄이고 클래스가 수백 개
    → 손으로 쓸 P/Invoke 양이 현실적이지 않습니다.

✓ 객체 그래프를 오가야 한다
    → 컬렉션 · 상속 · 콜백이 얽힌 API 를 함수 목록으로
      납작하게 펴는 일 자체가 큰 설계 작업입니다.

✓ C++ 쪽 소스를 고칠 수 없다 (다른 팀 · 서드파티)
    → include 만 하면 되므로 원본을 건드리지 않습니다.

✓ 예외 · 이벤트를 자연스럽게 이어 주고 싶다
    → 같은 프레임에서 변환되므로 코드가 짧습니다.

실무 요령 — 계층을 반드시 세 개로 나눕니다
    Native(순수 C++) / Wrapper(/clr) / App(C#)
    Wrapper 에는 로직을 절대 넣지 않습니다 — 변환만.

성능 — 어디서 비용이 나나

C++/CLI 의 호출 비용은 P/Invoke 와 거의 같습니다
  관리 → 네이티브 전환마다 스택 프레임 표시 · GC 모드 전환

그래서 실수하기 쉬운 패턴
  ✗ ref class 의 메서드를 루프 안에서 100만 번 부른다
      for (int i = 0; i < n; i++) wrapper->Push(xs[i]);
      → 전환이 100만 번. 순수 C++ 대비 몇 배 느려집니다

  ✓ 배열째로 한 번 넘긴다
      wrapper->PushRange(xs);      // 안에서 pin_ptr 로 고정 후 루프

측정 요령
  · Visual Studio 프로파일러에서 'Interop' 프레임을 세어 봅니다
  · 전환 횟수 자체를 로그로 세는 것이 가장 확실합니다

정리하면 P/Invoke 든 C++/CLI 든 규칙은 같습니다 —
  "경계는 굵고 드물게, 안쪽 루프는 한쪽 세계에서만" ★
C++/CLI 를 “점진적 이주”의 도구로 쓰는 팀도 많습니다 — 기존 MFC/WinForms 앱에서 UI 만 WPF·C# 로 새로 쓰고 엔진은 그대로 두는 식입니다. 이때 C++/CLI 계층은 영구 설계가 아니라 다리이므로, 나중에 P/Invoke 로 갈아탈 수 있게 인터페이스를 얇게 유지해 두면 좋습니다.
정리 — C++/CLI 는 “윈도우 전용 + 기존 C++ 클래스가 산더미” 라는 조건에서만 이깁니다. ref class 하나로 Dispose · 프로퍼티 · 예외 변환이 전부 따라오지만, 리눅스 · NativeAOT · Unity 와는 함께 갈 수 없습니다.

자동 바인딩 — 헤더에서 생성하고 손으로 다듬기

// gen/Native.cs 는 건드리지 않습니다 (다음 생성에 덮어써집니다)
// 대신 partial 로 확장하거나 별도 파일에 얇게 씁니다

// MyLib/Engine.cs — 사람이 쓰는 유일한 층
namespace MyLib;

public sealed class Engine : IDisposable
{
    private readonly EngineHandle _h;      // 생성물의 포인터를 감쌉니다

    public Engine(int window)
    {
        unsafe
        {
            var p = Native.Native.mylib_engine_create(window);
            if (p is null) throw new ArgumentOutOfRangeException(nameof(window));
            _h = new EngineHandle((IntPtr)p);
        }
    }

    public void Push(double v) => Check.Ok(
        Native.Native.mylib_engine_push(_h, v));

    public string Report()
    {
        IntPtr p = Native.Native.mylib_engine_report(_h);
        try { return Marshal.PtrToStringUTF8(p) ?? ""; }
        finally { Native.Native.mylib_free_string(p); }   // ★ 생성기가 모르는 규약
    }

    public void Dispose() => _h.Dispose();
}
Report() 가 이 층이 필요한 이유를 그대로 보여 줍니다 — 생성기는 char* 반환값을 봤을 뿐, 그것을 해제해야 하는지 모릅니다. “누가 해제하나”를 아는 사람은 헤더 주석을 읽은 사람뿐이고, 그 지식이 들어가는 자리가 바로 이 손으로 쓴 얇은 층입니다.

이름 규칙 하나로 후처리가 가능해집니다 — xxx 와 xxx_len 이 나란히 오면 Span<T> 로, out_ 접두사면 out 매개변수로 바꾸는 작은 후처리 스크립트를 한 번 써 두면 이후 모든 생성에 적용됩니다. 생성기를 바꾸는 것보다 헤더 규칙을 정하는 편이 훨씬 값쌉니다.
정리 — 헤더가 크면 ClangSharp(C ABI) · SWIG(다언어) · CppSharp(C++ 클래스) 중에 고르되, 생성물은 원시 층으로만 쓰고 공개 API 는 손으로 얇게 얹습니다. 생성물을 커밋해 두면 ABI 변화가 diff 로 보입니다.

Unity 에서 NativeArray 를 쓰는 것이 정답인 이유 — 관리 배열은 GC 대상이라 핀을 잡아야 하고, 오래 잡으면 GC 를 방해합니다. NativeArray 는 처음부터 네이티브 메모리라 그 문제가 없고, Burst · Job System 과도 그대로 이어집니다. 단 Dispose() 를 잊으면 에디터가 누수를 경고합니다.

using AOT;    // ★ MonoPInvokeCallback 이 여기 있습니다

public static class MyLib
{

    public delegate void LogFn(int level, IntPtr utf8Message);

    [DllImport(Lib, CallingConvention = CallingConvention.Cdecl)]
    public static extern void mylib_set_logger(LogFn fn);

    [MonoPInvokeCallback(typeof(LogFn))]
    private static void OnLog(int level, IntPtr msg)
    {
        try
        {
            string s = Marshal.PtrToStringUTF8(msg) ?? "";
            if (level >= 2) Debug.LogError(s); else Debug.Log(s);
        }
        catch { /* 콜백에서 예외를 내보내면 그대로 크래시입니다 */ }
    }

    // ★ 델리게이트를 static 필드로 붙잡아 둡니다 — GC 수거 방지
    private static readonly LogFn s_log = OnLog;

    public static void Init() => mylib_set_logger(s_log);
}

#if UNITY_EDITOR && UNITY_EDITOR_WIN
using System;
using System.Runtime.InteropServices;

public static class NativeLoader
{
    [DllImport("kernel32")] static extern IntPtr LoadLibrary(string p);
    [DllImport("kernel32")] static extern bool   FreeLibrary(IntPtr h);
    [DllImport("kernel32")] static extern IntPtr GetProcAddress(IntPtr h, string n);

    static IntPtr _h;

    public static void Load(string path)
    {
        Unload();
        // 원본을 잠그지 않도록 임시 복사본을 로드합니다 ★
        var tmp = $"{path}.{Guid.NewGuid():N}.dll";
        System.IO.File.Copy(path, tmp, true);
        _h = LoadLibrary(tmp);
        if (_h == IntPtr.Zero) throw new Exception($"로드 실패: {tmp}");
    }

    public static T Get<T>(string name) where T : Delegate =>
        Marshal.GetDelegateForFunctionPointer<T>(GetProcAddress(_h, name));

    public static void Unload()
    {
        if (_h != IntPtr.Zero) { FreeLibrary(_h); _h = IntPtr.Zero; }
    }
}
#endif
임시 복사본을 로드하는 것이 요령입니다 — 원본 파일이 잠기지 않으므로 에디터를 켜 둔 채로 C++ 를 다시 빌드할 수 있습니다. 플레이 모드에 들어갈 때 Load, 나올 때 Unload 를 걸어 두면 재시작 없이 반복 개발이 됩니다. 배포 빌드에는 이 코드가 들어가지 않게 #if UNITY_EDITOR 로 확실히 감싸세요.

SetDllImportResolver — 만능 열쇠 ★

using System.Reflection;
using System.Runtime.InteropServices;

internal static class NativeResolver
{
    // 이 어셈블리의 P/Invoke 가 처음 라이브러리를 찾을 때 불립니다
    [ModuleInitializer]                       // 어셈블리 로드 시 자동 실행
    internal static void Init() =>
        NativeLibrary.SetDllImportResolver(typeof(NativeResolver).Assembly, Resolve);

    private static IntPtr Resolve(string name, Assembly asm, DllImportSearchPath? path)
    {
        if (name != "mylib") return IntPtr.Zero;   // 다른 건 기본 동작에 맡깁니다

        // ① 환경 변수로 지정된 경로를 최우선으로 (배포 후 진단에 유용)
        var env = Environment.GetEnvironmentVariable("MYLIB_PATH");
        if (!string.IsNullOrEmpty(env) && NativeLibrary.TryLoad(env, out var h1))
            return h1;

        // ② 내가 정한 폴더 구조에서 찾기
        string rid = RuntimeInformation.RuntimeIdentifier;      // "linux-x64" 등
        string file = OperatingSystem.IsWindows() ? "mylib.dll"
                    : OperatingSystem.IsMacOS()   ? "libmylib.dylib"
                    :                               "libmylib.so";
        string p = Path.Combine(AppContext.BaseDirectory, "native", rid, file);
        if (File.Exists(p) && NativeLibrary.TryLoad(p, out var h2)) return h2;

        return IntPtr.Zero;                     // 기본 탐색으로 넘깁니다
    }
}
언제 필요한가 — NuGet 규약을 못 쓰는 상황들입니다. 플러그인 폴더에서 로드해야 하거나, 고객이 라이브러리 경로를 지정해야 하거나, CPU 기능(AVX-512 유무)에 따라 다른 바이너리를 고르는 경우입니다. [ModuleInitializer] 와 짝지으면 사용자가 아무것도 호출하지 않아도 걸립니다.

CPU 기능에 따라 골라 싣기

using System.Runtime.Intrinsics.X86;

private static string PickVariant()
{
    if (Avx512F.IsSupported) return "mylib_avx512";
    if (Avx2.IsSupported)    return "mylib_avx2";
    return "mylib_sse2";               // 안전한 기본값
}

// Resolver 안에서 이 이름으로 로드합니다
if (NativeLibrary.TryLoad(Path.Combine(dir, PickVariant() + ext), out var h))
    return h;
# 같은 소스를 세 번 빌드합니다
for v in sse2 avx2 avx512; do
  case $v in
    sse2)   FLAGS="-msse2" ;;
    avx2)   FLAGS="-mavx2 -mfma" ;;
    avx512) FLAGS="-mavx512f -mavx512dq" ;;
  esac
  cmake -S native -B build/$v -DCMAKE_CXX_FLAGS="$FLAGS -O3"
  cmake --build build/$v -j
  cp build/$v/libmylib.so artifacts/linux-x64/libmylib_$v.so
done
왜 하나로 못 만드나 — -mavx512f 로 빌드한 바이너리를 AVX-512 가 없는 CPU 에서 로드하면 첫 명령에서 즉시 죽습니다(illegal instruction). C++ 안에서 런타임 디스패치(__builtin_cpu_supports)를 하는 방법도 있지만, 파일을 나누는 편이 빌드 플래그를 단순하게 유지해 줍니다.

// native/resize.cpp — 바이리니어 축소. 메모리를 할당하지 않습니다
#include <cstdint>
#include <algorithm>
#include <thread>
#include <vector>

static void resize_rows(const uint8_t* src, int sw, int sh, int sstride,
                        uint8_t* dst, int dw, int dh, int dstride,
                        int ch, int y0, int y1)
{
    const float fx = static_cast<float>(sw) / dw;
    const float fy = static_cast<float>(sh) / dh;
    for (int y = y0; y < y1; ++y) {
        const float sy = (y + 0.5f) * fy - 0.5f;
        const int   y1i = std::clamp(static_cast<int>(sy), 0, sh - 1);
        const int   y2i = std::min(y1i + 1, sh - 1);
        const float wy = sy - y1i;
        for (int x = 0; x < dw; ++x) {
            const float sx = (x + 0.5f) * fx - 0.5f;
            const int   x1i = std::clamp(static_cast<int>(sx), 0, sw - 1);
            const int   x2i = std::min(x1i + 1, sw - 1);
            const float wx = sx - x1i;
            for (int c = 0; c < ch; ++c) {
                const float a = src[y1i*sstride + x1i*ch + c] * (1-wx)
                              + src[y1i*sstride + x2i*ch + c] * wx;
                const float b = src[y2i*sstride + x1i*ch + c] * (1-wx)
                              + src[y2i*sstride + x2i*ch + c] * wx;
                dst[y*dstride + x*ch + c] =
                    static_cast<uint8_t>(a * (1-wy) + b * wy + 0.5f);
            }
        }
    }
}
// 경계 함수 — 검증 · 스레드 분할 · 예외 봉인이 전부입니다
extern "C" MYLIB_API int32_t mylib_resize(
    const uint8_t* src, int32_t sw, int32_t sh, int32_t sstride,
    uint8_t*       dst, int32_t dw, int32_t dh, int32_t dstride,
    int32_t ch, int32_t threads)
{
    MYLIB_GUARD({
        if (!src || !dst)                  return MYLIB_EINVAL;
        if (sw <= 0 || sh <= 0)            return MYLIB_EINVAL;
        if (dw <= 0 || dh <= 0)            return MYLIB_EINVAL;
        if (ch != 1 && ch != 3 && ch != 4) return MYLIB_EINVAL;
        if (sstride < sw * ch || dstride < dw * ch) return MYLIB_EINVAL;

        int n = threads > 0 ? threads
              : std::max(1u, std::thread::hardware_concurrency());
        n = std::min(n, dh);

        std::vector<std::thread> ts;
        const int chunk = (dh + n - 1) / n;
        for (int i = 0; i < n; ++i)
            ts.emplace_back(resize_rows, src, sw, sh, sstride,
                            dst, dw, dh, dstride, ch,
                            i * chunk, std::min((i + 1) * chunk, dh));
        for (auto& t : ts) t.join();
        return MYLIB_OK;
    })
}

namespace MyCompany.MyLib;

internal static partial class Native
{
    [LibraryImport("mylib")]
    internal static partial int mylib_resize(
        ReadOnlySpan<byte> src, int sw, int sh, int sstride,
        Span<byte>         dst, int dw, int dh, int dstride,
        int ch, int threads);

    [LibraryImport("mylib")]
    internal static partial IntPtr mylib_last_error();

    [LibraryImport("mylib")]
    internal static partial int mylib_version();
}
// MyLib/Resizer.cs — 공개 층 (사람이 쓰는 유일한 API)
namespace MyCompany.MyLib;

public static class Resizer
{
    public static int Version => Native.mylib_version();

    /// <summary>RGBA/RGB/그레이 이미지를 축소·확대합니다.</summary>
    public static void Resize(
        ReadOnlySpan<byte> src, int srcW, int srcH,
        Span<byte> dst, int dstW, int dstH,
        int channels = 4, int threads = 0)
    {
        int need = dstW * dstH * channels;
        if (dst.Length < need)
            throw new ArgumentException($"dst 버퍼가 작습니다 ({need} 필요)");

        int rc = Native.mylib_resize(
            src, srcW, srcH, srcW * channels,
            dst, dstW, dstH, dstW * channels,
            channels, threads);

        if (rc != 0) Throw(rc);
    }

    // 배열을 새로 만들어 돌려주는 편의 오버로드
    public static byte[] Resize(byte[] src, int sw, int sh,
                                int dw, int dh, int ch = 4)
    {
        var dst = new byte[dw * dh * ch];
        Resize(src, sw, sh, dst, dw, dh, ch);
        return dst;
    }

    private static void Throw(int rc)
    {
        string msg = Marshal.PtrToStringUTF8(Native.mylib_last_error()) ?? "";
        throw rc switch
        {
            -1 => new ArgumentException(msg),
            -2 => new OutOfMemoryException(msg),
            _  => new InvalidOperationException($"{msg} (rc={rc})")
        };
    }
}
공개 API 가 Span 버전과 배열 버전 둘 다 있는 이유 — 성능이 중요한 호출자는 버퍼를 재사용하고, 편하게 쓰고 싶은 호출자는 배열을 받아 갑니다. 둘 다 제공하되 내부 구현은 Span 하나로 모읍니다.

// Assets/Scripts/TextureResizer.cs
using Unity.Collections;
using Unity.Collections.LowLevel.Unsafe;
using UnityEngine;
using System.Runtime.InteropServices;

public static class TextureResizer
{
    const string Lib =
#if UNITY_IOS && !UNITY_EDITOR
        "__Internal";
#else
        "mylib";
#endif

    [DllImport(Lib, CallingConvention = CallingConvention.Cdecl)]
    static extern int mylib_resize(IntPtr src, int sw, int sh, int sstride,
                                   IntPtr dst, int dw, int dh, int dstride,
                                   int ch, int threads);

    public static unsafe Texture2D Resize(Texture2D src, int dw, int dh)
    {
        var dstTex = new Texture2D(dw, dh, TextureFormat.RGBA32, false);

        NativeArray<byte> s = src.GetRawTextureData<byte>();
        NativeArray<byte> d = dstTex.GetRawTextureData<byte>();

        int rc = mylib_resize(
            (IntPtr)s.GetUnsafeReadOnlyPtr(), src.width, src.height, src.width * 4,
            (IntPtr)d.GetUnsafePtr(),         dw,        dh,         dw * 4,
            4, 0);

        if (rc != 0) { Object.Destroy(dstTex); throw new Exception($"resize {rc}"); }

        dstTex.Apply(false);      // GPU 로 업로드
        return dstTex;
    }
}
여기서 복사가 몇 번 일어나나 — 0번입니다. GetRawTextureData 는 텍스처의 CPU 쪽 메모리를 그대로 가리키고, C++ 는 그 주소를 직접 읽고 씁니다. Apply() 만이 실제 전송(CPU→GPU)입니다. 같은 일을 GetPixels()/SetPixels() 로 하면 Color 배열 변환 때문에 수십 배 느립니다.

BenchmarkDotNet 설정

// Bench/ResizeBench.cs
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;
using MyCompany.MyLib;

[MemoryDiagnoser]
[SimpleJob(warmupCount: 3, iterationCount: 10)]
public class ResizeBench
{
    private byte[] _src = null!, _dst = null!;
    private const int SW = 4096, SH = 4096, DW = 1024, DH = 1024;

    [GlobalSetup]
    public void Setup()
    {
        _src = new byte[SW * SH * 4];
        Random.Shared.NextBytes(_src);
        _dst = new byte[DW * DH * 4];
    }

    [Benchmark(Baseline = true)]                 // 순수 C# 구현
    public void ManagedBilinear() => ManagedResize.Run(_src, SW, SH, _dst, DW, DH);

    [Benchmark]                                  // C++ · 단일 스레드
    public void NativeSingle() =>
        Resizer.Resize(_src, SW, SH, _dst, DW, DH, 4, threads: 1);

    [Benchmark]                                  // C++ · 전 코어
    public void NativeMulti() =>
        Resizer.Resize(_src, SW, SH, _dst, DW, DH, 4, threads: 0);

    [Benchmark]                                  // 경계 자체의 비용
    public int EmptyCall() => Resizer.Version;
}

BenchmarkRunner.Run<ResizeBench>();
dotnet run -c Release --project Bench

여기서 읽어야 할 것 네 가지

  ① 실제 이득    210ms → 6.9ms = 약 30배. 옮길 가치가 있었습니다.
  ② 경계 비용    EmptyCall 2.7ns 는 6.9ms 의 0.00004%.
                 즉 P/Invoke 오버헤드는 '없는 것과 같습니다'.
  ③ 할당 0 B     Span 경로가 살아 있다는 증거입니다 ★
                 여기가 0 이 아니면 어딘가에서 복사가 부활한 것입니다.
  ④ 병렬 효율    38.2 / 6.9 = 5.5배 (8코어 기준) — 메모리 대역폭 한계

반대로 이런 결과가 나왔다면 되돌아봐야 합니다
  · Ratio 가 0.7 정도  → 이득이 적습니다. 복잡도를 감수할 값이 있나?
  · Allocated 가 큼    → 마샬링에서 복사가 일어나고 있습니다 (k03·k04)
  · EmptyCall 이 수백 ns → 문자열·구조체 마샬링이 끼어 있습니다
