STR 01

C++ 프로젝트의 공통 바탕 — Pitchfork 레이아웃과 규모별 진화

C++ 에는 Maven 같은 공식 표준 레이아웃이 없습니다. 대신 CMake 생태계에서 사실상 표준으로 굳은 것이 Pitchfork 레이아웃(PFL) — include/ · src/ · tests/ · external/ · docs/ 로 나누는 규칙입니다. fmt · spdlog · Catch2 같은 유명 라이브러리 대부분이 이 모양이라, 처음 보는 저장소에서도 길을 잃지 않습니다.

라이브러리 + 실행 파일 하나 — 출발점

shop/                      # 저장소 이름 = 프로젝트 이름
├─ CMakeLists.txt          # 최상위 — project() · 옵션 · add_subdirectory
├─ CMakePresets.json       # dev · release · asan 프리셋 (커밋)
├─ include/
│  └─ shop/                # ★ 공개 헤더 — 쓰는 쪽이 <shop/…> 로 포함
│     ├─ order.hpp
│     └─ money.hpp
├─ src/                    # 구현 .cpp + 비공개 헤더 (밖에서 안 보임)
│  ├─ CMakeLists.txt
│  ├─ order.cpp
│  ├─ money.cpp
│  └─ detail/db_row.hpp    # 내부 전용 헤더
├─ tests/                  # 테스트 — 별도 실행 파일 타깃
├─ external/               # 소스째 들고 온 서드파티 (되도록 비움)
├─ docs/
├─ tools/                  # 스크립트 · 코드 생성기
└─ build/                  # 산출물 — .gitignore

공개 헤더를 왜 include/shop/ 로 한 번 더 감싸나

// ❌ include/order.hpp 에 바로 두면
#include "order.hpp"        // 어느 라이브러리의 order.hpp ?
                            // 의존성 둘이 같은 이름을 쓰면 먼저 찾은 쪽이 이김

// ✅ include/shop/order.hpp
#include <shop/order.hpp>   // 이름 공간이 경로에 박혀 충돌이 없음
                            // 빌드 트리에서도, 설치 후
                            // (/usr/include/shop/order.hpp)에도 같은 한 줄 ★

// 같은 라이브러리 안의 비공개 헤더는 따옴표 + 상대 경로
#include "detail/db_row.hpp"
세 가지가 한 번에 풀립니다 — ① 헤더 이름 충돌, ② 소스 트리와 설치 트리의 #include 줄이 같아짐, ③ "include/ 아래 = 공개 API, src/ 아래 = 구현"이라는 경계가 폴더로 보임. ③ 이 STR 06 의 ABI 관리와 STR 10 의 규칙 강제의 출발점입니다.
폴더 (PFL)무엇을 두나흔한 실수
include/<proj>/설치되어 남에게 나가는 헤더만구현용 헬퍼 헤더까지 여기 둠
src/.cpp 와 비공개 헤더. PFL 은 실행 파일 진입점도 여기공개 헤더를 src 에서 직접 include 경로로 노출
libs/저장소 안의 하위 라이브러리 여럿 (각자 include/src 를 가짐)처음부터 만들기 — 하나일 땐 불필요
tests/ · examples/테스트 타깃 · 사용 예제테스트를 라이브러리 타깃에 섞음
external/패키지 관리자로 못 받는 서드파티 원본 (STR 05)고쳐 쓰고 출처를 안 남김
tools/ · docs/ · data/스크립트 · 문서 · 테스트 데이터빌드 산출물을 data 에 커밋
합친 배치도 PFL 이 허용합니다 — 헤더와 .cpp 를 src/shop/order.hpp · src/shop/order.cpp 처럼 한 폴더에 두는 "merged" 방식. 설치할 일이 없는 앱이나 헤더 전용 라이브러리에 편합니다. 분리냐 합침이냐는 공개 API 를 남에게 주느냐로 고르고, 한 저장소 안에서 섞지만 마세요. C 프로젝트의 같은 이야기는 🅲 C 언어 탭 c25 에 있습니다.

규모별 진화 — 언제 다음 단계로 넘어가나 🟢 기초

구조는 신호가 올 때 한 칸씩 키웁니다. 단, C++ 은 라이브러리 + 앱 분리(2단계)만큼은 테스트 때문에 거의 처음부터 필요합니다.
신호 (경험치)무엇이 아픈가다음 단계
테스트를 쓰고 싶다main() 이 들어 있는 실행 파일은 테스트가 링크할 수 없음로직을 라이브러리 타깃으로 (STR 02)
헤더 하나 고치면 수백 개 재컴파일공개 헤더에 무거운 include 가 몰림전방 선언 · pimpl (STR 03)
파일 수십 개 · 사람 2~3명"이 기능은 어디 소속?" · 타깃 하나가 다 끌어옴libs/ 로 타깃 분리 (STR 08)
다른 저장소가 가져다 씀복사·붙여넣기로 퍼진 코드가 버전마다 다름설치 규칙 · 패키지 (STR 06)
팀이 여럿엔진이 게임 코드를 include 하는 식의 역방향 의존규칙 자동 검사 (STR 10)
정리 — 바탕은 include/<proj>/ · src/ · tests/ 세 폴더와 최상위 CMakeLists 하나입니다. 공개 헤더는 항상 프로젝트 이름 폴더로 감싸 <proj/x.hpp> 로 포함하고, 나머지는 위 표의 신호가 올 때만 키웁니다.
STR 02

모던 CMake 타깃 구조 — 폴더마다 CMakeLists, 의존은 타깃으로

C++ 프로젝트의 "모듈 경계"는 폴더가 아니라 CMake 타깃입니다. 폴더를 나눠도 전역 include_directories() 하나면 모두가 모두를 봅니다. 반대로 타깃을 나누고 PUBLIC/PRIVATE 를 정확히 붙이면 빌드가 의존 방향을 검사해 줍니다. 키워드의 뜻과 프리셋 문법은 🛠️ 빌드 탭 b02 에 있으니, 여기서는 파일을 어떻게 나눠 배치하나만 봅니다.

트리 — CMakeLists 가 폴더마다 하나

shop/
├─ CMakeLists.txt          # project · find_package · add_subdirectory 만
├─ CMakePresets.json       # 팀 공용 (커밋)
├─ CMakeUserPresets.json   # 개인용 — .gitignore
├─ cmake/                  # 직접 만든 .cmake 모듈 · Config.cmake.in
├─ include/shop/…          # 공개 헤더
├─ src/
│  └─ CMakeLists.txt       # shop::core 라이브러리 타깃
├─ apps/
│  └─ shop-cli/
│     ├─ CMakeLists.txt    # 실행 파일 타깃 — 얇게
│     └─ main.cpp
└─ tests/
   └─ CMakeLists.txt       # 테스트 실행 파일 (STR 09)
PFL 은 실행 파일도 src/ 에 두지만, 실행 파일이 둘 이상이면 apps/ 로 빼는 관례가 흔합니다(규칙이 아니라 관례). 핵심은 main() 이 있는 파일을 라이브러리 타깃에 넣지 않는 것입니다.

최상위 CMakeLists.txt — 조립만 합니다

cmake_minimum_required(VERSION 3.25)
project(shop VERSION 1.4.0 LANGUAGES CXX)

find_package(fmt CONFIG REQUIRED)
find_package(SQLite3 REQUIRED)        # SQLite::SQLite3 타깃 제공

if(PROJECT_IS_TOP_LEVEL)              # (3.21+) 남이 add_subdirectory 하면 건너뜀
    set(CMAKE_CXX_EXTENSIONS OFF)
    include(CTest)                    # BUILD_TESTING 옵션 (기본 ON)
endif()

add_subdirectory(src)
add_subdirectory(apps/shop-cli)
if(PROJECT_IS_TOP_LEVEL AND BUILD_TESTING)
    add_subdirectory(tests)
endif()

src/CMakeLists.txt — 라이브러리가 자기 사정을 다 압니다

add_library(shop_core)
add_library(shop::core ALIAS shop_core)  # 쓰는 쪽은 언제나 shop::core

target_sources(shop_core
    PRIVATE order.cpp money.cpp
    PUBLIC FILE_SET HEADERS              # (3.23+) 공개 헤더 목록
        BASE_DIRS ${PROJECT_SOURCE_DIR}/include
        FILES ${PROJECT_SOURCE_DIR}/include/shop/order.hpp
              ${PROJECT_SOURCE_DIR}/include/shop/money.hpp)

    PRIVATE ${CMAKE_CURRENT_SOURCE_DIR})  # "detail/db_row.hpp" 용 — 나만 봄

target_link_libraries(shop_core
    PUBLIC  fmt::fmt            # order.hpp 가 fmt 타입을 드러냄
    PRIVATE SQLite::SQLite3)    # .cpp 안에서만 씀

apps/shop-cli/CMakeLists.txt — 두 줄

add_executable(shop-cli main.cpp)
target_link_libraries(shop-cli PRIVATE shop::core)
# include/ 경로 · fmt 헤더 · C++23 설정이 자동으로 따라옵니다
# SQLite 는 링크만 되고 헤더 경로는 안 옵니다 (PRIVATE)
ALIAS 를 왜 만드나 — 설치된 패키지를 find_package 로 받으면 이름이 shop::core 입니다(STR 06). 저장소 안에서도 같은 이름을 쓰면 나중에 소스 포함 ↔ 패키지 사용을 바꿔도 링크 줄이 그대로이고, :: 가 들어간 이름은 오타가 나면 CMake 가 "그런 타깃 없음"으로 바로 멈춥니다.
타깃 그래프 — 공개 헤더가 드러내는 의존만 PUBLIC. 그러면 앱은 core 의 내부 사정을 알 방법이 없습니다.
❌ 폴더는 나눴지만 경계가 없음

최상위에 include_directories(include src libs) · link_libraries(fmt sqlite3) 를 둡니다. 모든 타깃이 모든 헤더를 보므로 앱이 src/detail/ 을 include 해도 아무도 모르고, 나중에 라이브러리를 떼어 내려 하면 그제야 수백 곳이 깨집니다.

✅ 타깃마다 필요한 것만

각 폴더의 CMakeLists 가 자기 타깃의 소스 · 헤더 · 의존만 선언합니다. 최상위는 add_subdirectory 로 조립만 합니다. 전역 명령(include_directories · add_definitions · CMAKE_CXX_FLAGS 덧붙이기)은 쓰지 않습니다.

파일여기에 둔다여기에 두지 않는다
최상위 CMakeListsproject() · find_package · 옵션 · add_subdirectory소스 목록 · 타깃별 플래그
폴더별 CMakeLists그 폴더의 타깃 하나(또는 몇 개)와 그 의존다른 폴더의 소스
cmake/*.cmake경고 묶음 함수 · sanitizer 함수 · Config.cmake.in타깃 정의
CMakePresets.json제너레이터 · 빌드 폴더 · 툴체인 · 캐시 변수개인 경로 (→ CMakeUserPresets)
정리 — C++ 의 모듈 경계는 CMake 타깃입니다. 폴더마다 CMakeLists 하나, 최상위는 조립만, 라이브러리는 proj::name ALIAS 로 부르고, 공개 헤더가 드러내는 의존만 PUBLIC 으로 둡니다.
STR 03

헤더/소스 분리와 컴파일 시간 — 공개 헤더를 가볍게

#include 는 파일을 그 자리에 붙여넣는 것이라, 공개 헤더가 끌어온 모든 것은 그 헤더를 쓰는 모든 .cpp 가 다시 읽습니다. 그래서 C++ 의 구조 설계는 결국 "공개 헤더에 무엇을 남기나"입니다. 분리의 기초는 🔵 C++ 기초 탭 x09, 템플릿 인스턴스화 비용은 🔬 전문가 탭 d08, PCH · 유니티 빌드 측정은 🚀 고성능 탭 h12 에 있으니, 여기서는 배치 규칙만 봅니다.

무엇을 어디에 — 헤더 무게로 나눈 트리

include/shop/
├─ fwd.hpp            # 전방 선언만 — class Order; class Money;
├─ order.hpp          # 공개 클래스 — 표준 헤더 몇 개만 include
├─ logger.hpp         # pimpl — 무거운 의존이 하나도 안 보임
├─ algo.hpp           # 템플릿 공개 API (헤더에 둘 수밖에 없음)
└─ detail/
   └─ algo_impl.hpp   # 템플릿 내부 — namespace shop::detail
src/
├─ order.cpp          # 첫 줄은 #include <shop/order.hpp> ★
├─ logger.cpp         # <fstream> · <mutex> 는 여기서만
├─ algo_inst.cpp      # 자주 쓰는 타입의 명시적 인스턴스화
└─ detail/
   └─ db_row.hpp      # 비공개 헤더 — 같은 타깃의 .cpp 만 봄
.cpp 첫 줄에 자기 헤더 — 헤더가 다른 include 에 얹혀 가면 첫 줄에서 바로 컴파일 오류가 나므로, 모든 공개 헤더가 혼자서도 컴파일되는지 자동으로 검사됩니다.

pimpl — 구현을 .cpp 로 숨기기

// include/shop/logger.hpp — 쓰는 쪽이 보는 전부
#pragma once
#include <memory>
#include <string>
#include <string_view>

namespace shop {
class Logger {
public:
    explicit Logger(const std::string& path);
    ~Logger();                          // ★ 선언만 — 정의는 .cpp
    Logger(Logger&&) noexcept;
    Logger& operator=(Logger&&) noexcept;
    void write(std::string_view line);
private:
    struct Impl;                        // 전방 선언
    std::unique_ptr<Impl> impl_;
};
}  // namespace shop
// src/logger.cpp — 무거운 헤더는 여기에만
#include <shop/logger.hpp>
#include <fstream>
#include <mutex>

namespace shop {
struct Logger::Impl {
    std::ofstream out;
    std::mutex m;
    explicit Impl(const std::string& p) : out(p, std::ios::app) {}
};
Logger::Logger(const std::string& p) : impl_(std::make_unique<Impl>(p)) {}
Logger::~Logger() = default;            // 여기서는 Impl 이 완전한 타입
Logger::Logger(Logger&&) noexcept = default;
Logger& Logger::operator=(Logger&&) noexcept = default;

void Logger::write(std::string_view line) {
    std::lock_guard lk(impl_->m);       // 이동된 뒤의 객체에는 부르지 않는 전제
    impl_->out << line << '\n';
}
}  // namespace shop
소멸자를 헤더에서 = default 로 두면 컴파일 오류입니다 — unique_ptr<Impl> 의 삭제자가 불완전한 타입 Impl 을 지우려 하기 때문입니다. 소멸자 · 이동 연산은 선언은 헤더, 정의는 .cpp 가 공식입니다.
재컴파일 범위 = 그 헤더를 include 하는 .cpp 수. pimpl 과 비공개 헤더는 이 숫자를 줄이는 구조 장치입니다.
기법무엇을 줄이나대가 · 주의
전방 선언 (fwd.hpp)포인터 · 참조 · 함수 선언만 쓰는 곳의 include값 멤버 · 상속 · 인라인 호출에는 못 씀
pimplprivate 멤버의 의존이 공개 헤더에 드러나는 것힙 할당 1회 + 간접 호출 — 핫패스 값 타입엔 쓰지 않음
템플릿 + detail/사용자가 내부 이름을 쓰는 것 (컴파일 시간은 그대로)타입이 정해져 있으면 extern template + 명시적 인스턴스화
PCH표준 · 서드파티 헤더 반복 파싱PCH 에 넣은 헤더를 고치면 전부 재컴파일 — 내 헤더는 넣지 않음
유니티 빌드CI 의 전체 빌드 시간익명 namespace 이름 충돌 · 증분 빌드는 오히려 느림

STR 04

C++20 모듈 — 파일 배치와 헤더와의 공존

모듈은 "헤더를 붙여넣지 않고 컴파일된 인터페이스를 가져오는" 방식입니다. 구조 관점에서 바뀌는 점은 두 가지 — 공개 범위가 폴더가 아니라 export 키워드로 정해지고, 빌드 시스템이 파일 사이 의존 순서를 알아야 한다는 것입니다. 문법 소개와 컴파일러별 지원 표는 🚀 고성능 탭 h12 에 있습니다.

모듈 하나 = 폴더 하나 = 타깃 하나

src/money/
├─ CMakeLists.txt
├─ money.cppm          # 기본 인터페이스 단위  export module shop.money;
├─ money-format.cppm   # 인터페이스 파티션     export module shop.money:format;
└─ money.cpp           # 구현 단위             module shop.money;
include/shop/
└─ legacy.hpp          # 아직 헤더로 남은 부분 — 함께 써도 됩니다
파일 종류밖에서 보이나CMake 에서
기본 인터페이스export 한 것만FILE_SET CXX_MODULES
인터페이스 파티션기본 인터페이스가 다시 export 할 때FILE_SET CXX_MODULES
구현 단위안 보임 (.cpp 와 같음)일반 소스 (PRIVATE)
확장자는 관례입니다 — Clang 쪽은 .cppm, MSVC 기본은 .ixx. CMake 는 FILE_SET 으로 종류를 알려 주므로 어느 쪽이든 됩니다. 모듈 이름(shop.money)과 폴더 이름을 맞추는 것도 컴파일러가 강제하지 않는 팀 규칙입니다.

세 파일의 실제 모양

// money.cppm — 기본 인터페이스
module;                          // 전역 모듈 조각: 기존 헤더는 여기서 include
#include <cstdint>
export module shop.money;
export import :format;           // 파티션을 바깥에도 보이게

export namespace shop {
class Money {
public:
    explicit Money(std::int64_t cents) : cents_(cents) {}
    std::int64_t cents() const { return cents_; }
    Money operator+(Money o) const;          // 정의는 money.cpp
private:
    std::int64_t cents_;
};
}
// money-format.cppm — 파티션
module;
#include <cstdint>
#include <string>
export module shop.money:format;
export namespace shop { std::string format_cents(std::int64_t cents); }

// money.cpp — 구현 단위 (인터페이스를 자동으로 가져옴)
module;
#include <cstdint>
#include <format>
#include <string>
module shop.money;
namespace shop {
Money Money::operator+(Money o) const { return Money{cents_ + o.cents_}; }
std::string format_cents(std::int64_t c) {   // 0 이상만 가정 (음수 처리 생략)
    return std::format("{}.{:02}", c / 100, c % 100);
}
}
모듈의 구현 단위는 pimpl 의 .cpp 와 같은 역할 — 인터페이스만 BMI 로 나가고, 구현 변경은 쓰는 쪽을 건드리지 않습니다.

❌ 저장소 전체를 한 번에 모듈로

✅ 잎 모듈부터, 타깃 단위로

정리 — 모듈은 폴더 하나 · 타깃 하나 · 모듈 하나로 맞추고, 인터페이스는 FILE_SET CXX_MODULES, 구현 단위는 일반 소스로 둡니다. 툴체인 지원이 고르지 않으니 헤더와 공존시키며 잎 타깃부터 옮깁니다.
STR 05

STR 06

라이브러리 · ABI — 공개 헤더가 곧 계약서

남이 가져다 쓰는 라이브러리는 구조가 곧 계약입니다. include/<proj>/ 에 있는 모든 것이 공개 API이고, 공유 라이브러리라면 그 헤더의 클래스 레이아웃까지 ABI로 굳습니다. ABI 가 깨지는 원리는 🔬 전문가 탭 d07, 설치 명령 전체는 🛠️ 빌드 탭 b02 에 있으니, 여기서는 소스 트리와 설치 트리를 어떻게 맞추나를 봅니다.

PFL 의 include/shop/ 가 설치 트리와 같은 모양이라서, 빌드 중에도 설치 후에도 #include 줄이 같습니다.

        endif()
    endforeach()
endfunction()

한계를 알고 쓰세요 — LINK_LIBRARIES 는 직접 적은 이름 그대로입니다. 팀이 언제나 ALIAS 이름(engine::render)으로 링크한다는 전제가 필요하고, 다른 타깃의 PUBLIC 으로 건너온 헤더 경로는 못 잡습니다. 그래서 STR 02 의 "공개 헤더가 드러내는 것만 PUBLIC" 규칙이 먼저입니다. 전체 그래프는 cmake --graphviz=deps.dot 로 눈으로 확인합니다.

❌ 규칙이 위키에만

"core 는 render 를 모른다"가 문서에만 있고 최상위에 include_directories(engine game) 가 있습니다. 반년 뒤 누군가 급하게 #include <engine/render/mesh.hpp> 를 core 에 넣고, 서버 빌드가 GPU 라이브러리를 요구하기 시작합니다.

✅ 규칙이 빌드에

타깃마다 필요한 것만 링크하므로 그 include 는 컴파일 오류이고, 링크 줄로 우회하면 forbid_link 가 구성 단계에서 멈춥니다. OS 헤더는 폴더별 tidy 가, 남은 판단은 CODEOWNERS 리뷰가 맡습니다.

정리 — 시작은 PFL + 라이브러리/앱 타깃, 커지면 libs/ · apps/, 남에게 주면 install · ABI, 엔진이면 동심원 의존. 그리고 규칙은 문서가 아니라 CMake 타깃 → 링크 검사 → 폴더별 clang-tidy → CODEOWNERS 순서로 도구에 맡깁니다.
