FFI 01

C ABI 가 공용어인 이유

C++ 의 클래스도, 템플릿도, 예외도 다른 언어는 이해하지 못합니다. 모든 언어가 공통으로 아는 것은 “C 함수를 부르는 방법” 하나뿐입니다.

그래서 공개하는 함수만 extern "C" 로 감쌉니다 — 안은 마음껏 C++ 를 써도 됩니다.

ABI 란 무엇인가

API : 소스 코드 수준의 약속 — "이 함수는 이런 인자를 받는다"
ABI : 기계어 수준의 약속 — 실제로 어떻게 부르는가

  · 인자를 어느 레지스터·스택 위치에 놓는가
  · 반환값은 어디로 받는가
  · 스택 정리는 누가 하는가
  · 구조체는 메모리에 어떻게 배치되는가
  · 함수 이름이 심볼로 어떻게 기록되는가

C ABI 는 이 규칙이 OS·아키텍처마다 '문서로 고정'되어 있습니다.
그래서 어떤 언어로 만들었든 이 규칙만 지키면 서로 부를 수 있습니다.

★ C++ 는 표준 ABI 가 없습니다
  같은 리눅스에서도 GCC 와 Clang 의 이름 맹글링·예외 구현이 다를 수 있고,
  MSVC 는 아예 다릅니다. 그래서 C++ 클래스를 그대로 노출하면
  '같은 컴파일러로 빌드한 경우에만' 동작합니다(🔬 d07).

C++ 구현을 C API 로 감싸기

// ── 내부는 자유롭게 현대 C++ 로
namespace impl {
std::vector<double> smooth(std::span<const double> in, int window);
}

// ── 밖으로는 C 함수 하나만
extern "C" int32_t mylib_smooth(const double* in, int64_t n,
                                double* out, int32_t window) {
    if (!in || !out || n < 0)      return MYLIB_ERR_INVALID;
    if (window <= 0 || window > n) return MYLIB_ERR_INVALID;

    try {                                        // ★ 예외를 여기서 전부 잡기
        auto r = impl::smooth({in, static_cast<std::size_t>(n)}, window);
        std::memcpy(out, r.data(), r.size() * sizeof(double));
        return MYLIB_OK;
    } catch (const std::bad_alloc&) {
        return MYLIB_ERR_NOMEM;
    } catch (...) {
        return MYLIB_ERR_UNKNOWN;                // 절대 밖으로 안 나가게
    }
}
이 형태가 규칙입니다 — 얇은 C 껍질 + 풍부한 C++ 내부. 껍질에서 하는 일은 셋뿐입니다 — 인자 검증 · 예외를 에러 코드로 변환 · 메모리 복사.

인자가 실제로 어디로 가나

x86-64 System V (리눅스 · 맥)
  정수·포인터 인자 : RDI, RSI, RDX, RCX, R8, R9  순서대로
  실수 인자        : XMM0~XMM7
  나머지           : 스택
  반환             : RAX (정수) · XMM0 (실수)
  큰 구조체        : 호출자가 공간을 잡고 그 주소를 숨은 첫 인자로

Windows x64
  정수 인자 : RCX, RDX, R8, R9  (4개만!)
  실수 인자 : XMM0~XMM3
  ★ 레지스터 순서가 다릅니다 — 그래서 규약이 안 맞으면 인자가 뒤섞입니다

32비트 시절의 유산 (윈도우 DLL 에서 아직 보입니다)
  __cdecl    : 호출자가 스택 정리 (C 기본)
  __stdcall  : 피호출자가 정리 (Win32 API)
  → 안 맞으면 스택이 망가져 호출 직후 크래시합니다
  → 64비트에서는 규약이 하나로 통일돼 이 문제가 거의 사라졌습니다

왜 알아야 하나 — FFI 에서 인자 타입을 잘못 선언하면 컴파일러도 인터프리터도 잡아 주지 못하고 실행 중에 이상한 값이나 크래시로 나타납니다. 규약을 알면 “왜 세 번째 인자만 쓰레기 값이 오는가” 같은 증상을 추론할 수 있게 됩니다.
정리 — C ABI 는 언어 사이의 유일한 공용어입니다. C++ 클래스·템플릿·예외는 넘길 수 없고, 숫자 · 포인터 · 함수 포인터 · 표준 배치 구조체만 넘어갑니다. 구조는 항상 같습니다 — 얇은 extern "C" 껍질 + 자유로운 C++ 내부.
FFI 02

extern "C" 와 이름 맹글링

C++ 컴파일러는 함수 이름을 내부적으로 바꿔 버립니다. 오버로딩 때문에 그래야 하는데, 그러면 다른 언어가 찾지 못합니다.

이름이 어떻게 바뀌나

void f(int);
void f(double);
void f(int, char*);
//  세 함수의 이름이 전부 "f" 라면 링커가 구분할 수 없습니다.
//  그래서 컴파일러가 인자 타입을 이름에 인코딩합니다.

//   _Z1fi          ← f(int)          (GCC/Clang · Itanium ABI)
//   _Z1fd          ← f(double)
//   _Z1fiPc        ← f(int, char*)
//   ?f@@YAXH@Z     ← MSVC 는 형식이 완전히 다릅니다

// extern "C" 를 붙이면 맹글링하지 않습니다
extern "C" void g(int);      // 심볼 이름이 그냥 "g" (또는 "_g")
//   → 대신 오버로딩을 쓸 수 없습니다 (이름이 하나여야 하므로)

// 헤더 전체에 적용하는 관용구
#ifdef __cplusplus
extern "C" {
#endif

int32_t mylib_smooth(const double*, int64_t, double*, int32_t);

#ifdef __cplusplus
}
#endif
//   ★ 이 헤더를 C 에서 include 하면 extern "C" 가 없고,
//     C++ 에서 include 하면 적용됩니다 — 양쪽에서 쓸 수 있게 됩니다

확인하고 진단하기

# 심볼 목록 (-C 는 사람이 읽을 수 있게 복원)
nm -D --defined-only mylib.so | grep mylib
nm -DC --defined-only mylib.so | grep mylib     # 복원된 이름

# 맹글링된 이름을 원래대로
echo "_Z1fi" | c++filt          # → f(int)

# 윈도우
dumpbin /exports mylib.dll
undname "?f@@YAXH@Z"

# ★ FFI 에서 "심볼을 못 찾음" 이 나오면 첫 번째로 이걸 확인합니다
python -c "
import ctypes
lib = ctypes.CDLL('./mylib.so')
lib.mylib_smooth           # AttributeError 면 심볼 이름 문제
"
가장 흔한 실수 — 헤더에는 extern "C" 를 썼는데 .cpp 에서 그 헤더를 include 하지 않고 함수를 정의한 경우입니다. 그러면 정의 쪽은 맹글링되어 선언과 정의가 서로 다른 심볼이 됩니다. 구현 파일에서 반드시 자기 헤더를 include 하세요.

세 OS 를 하나의 매크로로

// mylib_export.h
#pragma once

#if defined(_WIN32)
  #ifdef MYLIB_BUILDING              // 라이브러리를 빌드할 때 정의
    #define MYLIB_API __declspec(dllexport)
  #else                              // 쓰는 쪽에서 include 할 때
    #define MYLIB_API __declspec(dllimport)
  #endif
#else
  #define MYLIB_API __attribute__((visibility("default")))
#endif

#ifdef __cplusplus
  #define MYLIB_EXTERN extern "C"
#else
  #define MYLIB_EXTERN
#endif

#define MYLIB_EXPORT MYLIB_EXTERN MYLIB_API

// 사용
MYLIB_EXPORT int32_t mylib_smooth(const double*, int64_t, double*, int32_t);
add_library(mylib SHARED src/api.cpp)
target_compile_definitions(mylib PRIVATE MYLIB_BUILDING)
set_target_properties(mylib PROPERTIES
    CXX_VISIBILITY_PRESET hidden        # ★ 기본은 숨기고
    VISIBILITY_INLINES_HIDDEN ON)       #   표시한 것만 내보내기

내보낼 것을 명시적으로 통제하기

# 리눅스 — 버전 스크립트로 심볼 목록을 고정
# mylib.map
MYLIB_1.0 {
  global:
    mylib_*;          # 이것만 내보냅니다
  local:
    *;                # 나머지는 전부 숨김
};
target_link_options(mylib PRIVATE
    "-Wl,--version-script=${CMAKE_CURRENT_SOURCE_DIR}/mylib.map")
왜 숨기는가

  ① 심볼이 적을수록 로딩이 빠릅니다 (동적 링커의 재배치 작업 감소)
  ② 내부 심볼이 다른 라이브러리와 충돌하지 않습니다 ★
     — 같은 프로세스에 두 확장 모듈이 같은 이름을 내보내면
       나중에 로드된 쪽이 앞의 것을 가릴 수 있습니다
  ③ 컴파일러가 더 공격적으로 최적화할 수 있습니다
     (밖에서 부를 수 없다면 인라인·제거가 자유로워집니다)
  ④ API 표면이 문서와 일치하게 유지됩니다

C 와 C++ 를 함께 쓰는 프로젝트

// C 라이브러리 헤더를 C++ 에서 include 할 때
// (헤더에 extern "C" 가드가 없는 옛 라이브러리라면 직접 감쌉니다)
extern "C" {
#include "old_c_lib.h"
}

// 반대로, C++ 로 만든 것을 C 에서 쓰게 하려면
// ① 헤더에는 C 문법만 (클래스·네임스페이스·기본 인자 금지)
// ② 불투명 포인터로 객체를 감춤 (f03)
// ③ C++ 표준 라이브러리를 정적 링크하거나 의존성 명시

// C 링커로 링크할 때는 C++ 런타임을 직접 붙여야 합니다
//   gcc main.c -lmylib -lstdc++      ← C++ 표준 라이브러리 명시
//   또는 라이브러리를 g++ 로 링크해 런타임을 안에 포함

// 전역 객체 초기화에 주의 ★
//   C++ 전역 객체의 생성자는 라이브러리 로드 시점에 불립니다.
//   그 안에서 예외가 나거나 다른 라이브러리를 쓰면
//   초기화 순서 문제로 crash 가 납니다.
//   → 지연 초기화(함수 안 static)로 피하세요
Engine& instance() {

}

FFI 03

헤더 설계 — 불투명 포인터

C++ 객체를 다른 언어에 노출하는 표준 방법입니다. 내부는 감추고 포인터 하나만 넘깁니다 — 라이브러리 배포의 정석입니다.

라이브러리를 버전을 올려도 안 깨지게 만드는 가장 확실한 방법입니다.

핸들 패턴

/* ── mylib.h — 쓰는 쪽이 보는 전부 ─────────────── */
#ifndef MYLIB_H
#define MYLIB_H
#include <stdint.h>
#include "mylib_export.h"

typedef struct mylib_engine mylib_engine;   /* ★ 정의 없이 이름만 */

MYLIB_EXPORT mylib_engine* mylib_engine_create(int32_t window);
MYLIB_EXPORT void          mylib_engine_destroy(mylib_engine* e);

MYLIB_EXPORT int32_t mylib_engine_feed(mylib_engine* e,
                                       const double* data, int64_t n);
MYLIB_EXPORT int32_t mylib_engine_result(const mylib_engine* e,
                                         double* out, int64_t* out_n);
#endif
// ── api.cpp — 구현 ────────────────────────────
#include "mylib.h"
#include "engine.hpp"          // 진짜 C++ 클래스

// 불완전 타입 mylib_engine 을 실제 클래스로 정의
struct mylib_engine {
    impl::Engine e;            // 안에 무엇이 있든 밖에서는 모릅니다
};

extern "C" mylib_engine* mylib_engine_create(int32_t window) {
    if (window <= 0) return nullptr;
    try { return new mylib_engine{impl::Engine(window)}; }
    catch (...) { return nullptr; }
}

extern "C" void mylib_engine_destroy(mylib_engine* e) {
    delete e;                  // nullptr 도 안전합니다
}

왜 이 구조인가

  • 내부를 바꿔도 쓰는 쪽이 다시 컴파일할 필요가 없습니다 — 구조체 크기가 헤더에 없으므로 ABI 가 안 깨집니다(🔬 d07)
  • C++ 표준 라이브러리가 헤더에 새어 나가지 않습니다 — std::vector 를 헤더에 쓰면 C 에서 못 씁니다
  • 수명 관리가 명확합니다 — create/destroy 쌍
  • 모든 언어에서 같은 모양으로 감쌀 수 있습니다
/* 타입 안전성을 조금 더 — void* 대신 이름 있는 구조체 포인터 */
typedef struct mylib_engine  mylib_engine;
typedef struct mylib_session mylib_session;
/*  둘을 바꿔 넣으면 C 컴파일러가 경고를 줍니다.
    void* 로 하면 아무것도 못 잡습니다. ★                */
SQLite 가 정확히 이 형태입니다 — sqlite3*, sqlite3_stmt* 가 불투명 핸들이고, sqlite3_open/sqlite3_close 가 수명을 관리합니다. 20년 넘게 ABI 를 유지할 수 있었던 이유이기도 합니다.

실무에선 이렇게 — 쓰기 좋은 C API 의 조건 🔴 실무

체크리스트

  • 모든 함수에 접두어 — mylib_
  • create/destroy 쌍이 명확하고, destroy(NULL) 이 안전한가
  • 에러는 반환값으로, 값은 출력 인자로(f09)
  • 포인터 + 길이를 항상 쌍으로 (배열만 넘기지 않기)
  • const 를 정확히 — 입력은 const T*
  • 예외가 절대 새지 않게 — 모든 extern "C" 함수에 try/catch
  • 스레드 안전성 문서화 — 핸들 공유 가능 여부
  • 버전 함수 — mylib_version()
  • 재진입 가능 — 전역 상태를 두지 않기
전역 상태는 특히 위험합니다 — 파이썬에서 여러 스레드가 부르거나, 같은 프로세스에 여러 사용자가 있으면 서로 간섭합니다. 상태는 전부 핸들 안에 두세요.

불투명 핸들을 파이썬 클래스로

import ctypes
from ctypes import c_void_p, c_int32, c_int64, c_double, POINTER

lib.mylib_engine_create.argtypes  = [c_int32]
lib.mylib_engine_create.restype   = c_void_p        # ★ 불투명 핸들
lib.mylib_engine_destroy.argtypes = [c_void_p]
lib.mylib_engine_destroy.restype  = None
lib.mylib_engine_feed.argtypes    = [c_void_p, POINTER(c_double), c_int64]
lib.mylib_engine_feed.restype     = c_int32

class Engine:
    """C 핸들을 파이썬 객체로 감쌉니다."""

    def __init__(self, window: int = 3):
        self._h = lib.mylib_engine_create(window)
        if not self._h:
            raise ValueError(f"엔진 생성 실패 (window={window})")

    def feed(self, data) -> None:
        a = np.ascontiguousarray(data, dtype=np.float64)
        rc = lib.mylib_engine_feed(
            self._h, a.ctypes.data_as(POINTER(c_double)), a.size)
        if rc != 0:
            raise RuntimeError(_msg(rc))

    def close(self) -> None:
        if getattr(self, "_h", None):
            lib.mylib_engine_destroy(self._h)
            self._h = None                    # ★ 이중 해제 방지

    __del__ = close                            # GC 될 때도 정리
    def __enter__(self):  return self
    def __exit__(self, *e): self.close(); return False

FFI 버그의 절반이 여기서 납니다 — “이 메모리는 누가 해제하는가”를 정하지 않으면 반드시 새거나 두 번 해제됩니다.

문자열 다루기

// C++ std::string 은 넘길 수 없습니다. 세 가지 방법이 있습니다.

// ① 호출자 버퍼 (권장) — 크기 조회 후 채우기
extern "C" int32_t mylib_name(const mylib_engine* h,
                              char* buf, int32_t* size) {
    const std::string& s = h->e.name();
    const int32_t need = static_cast<int32_t>(s.size()) + 1;   // +1 = '\0'
    if (!buf) { *size = need; return MYLIB_OK; }               // 크기만
    if (*size < need) { *size = need; return MYLIB_ERR_BUFFER; }
    std::memcpy(buf, s.c_str(), need);
    *size = need;
    return MYLIB_OK;
}

// ② 라이브러리 할당 + 전용 해제
extern "C" char* mylib_name_alloc(const mylib_engine* h) {
    const std::string& s = h->e.name();
    auto* p = static_cast<char*>(std::malloc(s.size() + 1));
    if (p) std::memcpy(p, s.c_str(), s.size() + 1);
    return p;                       // NULL 이면 실패
}
extern "C" void mylib_string_free(char* p) { std::free(p); }

// ③ 정적 문자열 빌려주기 (버전 등 변하지 않는 것만)
extern "C" const char* mylib_version_string(void) {
    return "1.2.3";                 // 정적 저장 기간 → 항상 유효
}

지켜야 할 다섯 가지

  ① 할당한 쪽이 해제한다
     라이브러리가 준 것은 라이브러리 함수로, 내가 준 것은 내가.

  ② 포인터는 항상 길이와 함께

  ③ 빌려준 포인터의 유효 기간을 명시

  ④ 라이브러리는 받은 포인터를 보관하지 않는다
     보관해야 하면 반드시 복사하고, 그 사실을 문서에 적습니다.

  ⑤ NULL 을 언제나 허용하거나, 언제나 거부하거나
     함수마다 다르면 사용자가 반드시 틀립니다.
     → destroy(NULL) 은 안전하게, 나머지는 에러 코드로.

/* C 콜백의 표준 형태 — 반드시 void* user 를 함께 받습니다 */
typedef int32_t (*mylib_progress_fn)(double frac, void* user);
/*   반환 0 = 계속, 그 외 = 중단                                  */

                               mylib_progress_fn cb, void* user);

/* ★ void* user 가 없으면 콜백이 '전역 상태'에만 접근할 수 있어
     여러 인스턴스를 동시에 쓸 수 없습니다. C API 설계의 기본 관용구입니다. */
// 구현 — C++ 쪽
extern "C" int32_t mylib_run(mylib_engine* h,
                             mylib_progress_fn cb, void* user) {
    if (!h) return MYLIB_ERR_INVALID;
    try {
        return h->e.run([&](double f) -> bool {
            if (!cb) return true;
            return cb(f, user) == 0;          // 0 이면 계속
        }) ? MYLIB_OK : MYLIB_ERR_CANCELED;
    } catch (...) {
        return MYLIB_ERR_UNKNOWN;             // ★ 예외를 절대 밖으로
    }
}
//  ⚠ 콜백이 예외를 던질 수 있다는 것도 고려해야 합니다
//    (다른 언어의 예외가 C 프레임을 통과하면 UB)

import ctypes
from ctypes import c_double, c_int32, c_void_p, CFUNCTYPE

# 시그니처 정의 — C 선언과 정확히 일치해야 합니다
PROGRESS = CFUNCTYPE(c_int32, c_double, c_void_p)

lib.mylib_run.argtypes = [c_void_p, PROGRESS, c_void_p]
lib.mylib_run.restype  = c_int32

class Engine:
    def run(self, on_progress=None):
        def _cb(frac, _user):
            try:
                if on_progress:
                    on_progress(frac)
                return 0                      # 계속
            except KeyboardInterrupt:
                return 1                      # 중단 ★
            except Exception:
                return 1                      # 예외를 C 로 넘기지 않습니다

        self._cb = PROGRESS(_cb)              # ★ 인스턴스에 보관 (GC 방지)
        rc = lib.mylib_run(self._h, self._cb, None)
        if rc != 0:
            raise RuntimeError(f"실행 실패 {rc}")

C → 파이썬 콜백 한 번 (ctypes CFUNCTYPE)

  ② libffi 로 인자 변환 (C 값 → 파이썬 객체)
  ③ 파이썬 함수 호출
  ④ 반환값 변환
  ⑤ GIL 해제
  합계 대략 1~3 μs — 정방향 호출보다 오히려 비쌉니다 ★

C → JS 콜백 (koffi register)
  ① V8 컨텍스트 진입 · 인자 변환 · 호출
  대략 0.5~2 μs

numba @cfunc 은 강력한 우회로입니다 — 파이썬 코드를 C ABI 함수 포인터로 컴파일해 주므로, 원소마다 불려도 GIL 도 인터프리터도 거치지 않습니다. 사용자 정의 규칙이 꼭 필요한 라이브러리에서 고려할 만합니다.
정리 — C 콜백은 함수 포인터 + void* user 가 표준형입니다. 파이썬에서는 콜백 객체를 반드시 살려 두고, 예외를 콜백 밖으로 내보내지 마세요(에러 코드로 변환). 그리고 가능하면 콜백 대신 폴링이 훨씬 안전합니다.
C ABI 는 함수 포인터와 void* 한 쌍이 전부입니다 — 이 관용구를 그대로 따르세요.

    """모든 mylib 오류의 부모."""
    def __init__(self, code: int, detail: str = ""):
        self.code = code
        super().__init__(f"[{code}] {detail}" if detail else f"코드 {code}")

class MylibValueError(MylibError, ValueError): pass
class MylibMemoryError(MylibError, MemoryError): pass
class MylibIOError(MylibError, OSError): pass

_MAP = {
    -1: MylibValueError,
    -2: MylibMemoryError,
    -3: MylibIOError,
    -4: MylibValueError,
    -5: KeyboardInterrupt,
}

def _check(rc: int) -> None:
    if rc == 0:
        return
    detail = lib.mylib_last_error().decode("utf-8", "replace")
    exc = _MAP.get(rc, MylibError)
    if exc is KeyboardInterrupt:
        raise KeyboardInterrupt(detail)
    raise exc(rc, detail)

# 사용
_check(lib.mylib_parse(text.encode()))

package mylib

/*
#cgo LDFLAGS: -L${SRCDIR}/lib -lmylib
#cgo CFLAGS: -I${SRCDIR}/include
#include "mylib.h"
#include <stdlib.h>
*/
import "C"
import (
    "errors"
    "unsafe"
)

func Smooth(in []float64, window int) ([]float64, error) {
    out := make([]float64, len(in))
    rc := C.mylib_smooth(
        (*C.double)(unsafe.Pointer(&in[0])),
        C.int64_t(len(in)),
        (*C.double)(unsafe.Pointer(&out[0])),
        C.int32_t(window),
    )
    if rc != 0 {
        return nil, errors.New(C.GoString(C.mylib_last_error()))
    }
    return out, nil
}

GC 언어와의 메모리 경계

GC 가 있는 언어(Java · C# · Go · JS)의 공통 함정

  ① 객체 이동(compaction)
     GC 가 메모리를 정리하며 객체를 옮길 수 있습니다.
     C 에 넘긴 포인터가 그 사이 무효가 됩니다.
     → 고정(pinning) 하거나, 네이티브 메모리를 따로 할당

     C#  : fixed 블록 · GCHandle.Alloc(pinned)
     Java: Arena 로 할당한 MemorySegment (힙 밖) ★
     Go  : cgo 호출 중에는 고정되지만 보관은 금지
     JS  : 큰 TypedArray 는 외부 메모리라 비교적 안전

  ② 콜백 수명
     콜백 객체가 GC 되면 C 쪽 함수 포인터가 죽습니다.
     → 전역 참조로 유지 (C# GCHandle · Java Arena · Python 멤버)

  ③ 예외·패닉
     각 언어의 예외가 C 프레임을 통과하면 UB 입니다.
     → 콜백 안에서 전부 잡아 에러 코드로 변환
