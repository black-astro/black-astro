HPC 02

저지연 설계 — 핫패스에서 아무것도 하지 않기

고빈도 거래 코드의 원칙은 놀랍도록 단순합니다. 핫패스에서 할당하지 않고, 던지지 않고, 시스템콜을 부르지 않는다. 셋 다 “평균은 빠른데 가끔 100배 느린” 원인이기 때문입니다. 평균이 아니라 p99.9 를 지키는 코드가 어떻게 생겼는지 봅니다.

최적화 순서는 큰 막대부터 — 내 코드는 마지막입니다.

핫패스 3대 금기

// ❌ 핫패스에 이런 것들이 있으면 p99.9 가 무너집니다
void on_tick(const Tick& t) {
    std::string sym = t.symbol();          // 할당 (malloc, 최악 수십 µs)
    std::vector<Order> orders;             // 할당
    if (bad) throw std::runtime_error(""); // 예외 (수 µs + 언와인딩)
    log_ << "tick " << sym << "\n";        // 시스템콜 + 락
    auto now = std::chrono::system_clock::now(); // vDSO 지만 수십 ns
}

// ✅ 같은 일을, 아무것도 새로 만들지 않고
struct Engine {
    std::array<Order, 64> pool_;           // 미리 잡아 둔 저장소
    RingBuffer<LogRec, 4096> logq_;        // 로그는 큐에만 넣고 끝

    void on_tick(const Tick& t) noexcept { // noexcept ★
        std::string_view sym = t.symbol(); // 복사 없음
        Order& o = pool_[n_++ & 63];       // 재사용
        o.set(sym, t.px, t.qty);
        logq_.try_push({t.seq, t.px});     // 실제 기록은 다른 스레드가
    }
};
왜 평균이 아니라 p99.9 인가 — malloc 은 대개 100ns 지만 새 페이지가 필요하면 mmap 을 부르고 수십 µs 가 됩니다. 평균만 보면 안 보이고, 1000번에 한 번 손해가 하루 손익을 결정합니다.

지연을 재는 법 — rdtsc 와 히스토그램

#include <x86intrin.h>
#include <array>
#include <cstdint>
#include <algorithm>

// TSC 는 요즘 CPU 에서 '고정 주파수'(invariant TSC)라 시계로 쓸 수 있습니다
static inline uint64_t rdtsc_start() {
    _mm_lfence();                    // 앞의 명령이 끝난 뒤 읽기
    return __rdtsc();
}
static inline uint64_t rdtsc_end() {
    unsigned aux; uint64_t t = __rdtscp(&aux);  // 자기 앞은 순서 보장
    _mm_lfence();
    return t;
}

// 히스토그램 — 평균 대신 분포를 봅니다 (버킷당 16 사이클)
struct Hist {
    std::array<uint32_t, 4096> b{};
    void add(uint64_t cyc) noexcept { b[std::min<uint64_t>(cyc >> 4, 4095)]++; }
    uint64_t pct(double p) const {                // p = 0.999 처럼
        uint64_t tot = 0; for (auto v : b) tot += v;
        uint64_t want = (uint64_t)(tot * p), acc = 0;
        for (size_t i = 0; i < b.size(); ++i)
            if ((acc += b[i]) >= want) return i << 4;
        return 4095 << 4;
    }
};
사이클을 ns 로 — /sys/devices/system/cpu/cpu0/cpufreq/base_frequency 또는 dmesg | grep tsc 로 TSC 주파수를 얻어 나눕니다. 3.0GHz 면 1 사이클 = 0.333ns.

스레드를 특정 코어에 고정 (affinity)

#include <pthread.h>
#include <sched.h>

void pin_to_core(int core) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(core, &set);
    // 지금 스레드를 core 번 논리 CPU 에만 돌게 묶습니다
    pthread_setaffinity_np(pthread_self(), sizeof(set), &set);
}

// 실시간 우선순위까지 (권한 필요: setcap 또는 root)
#include <sys/resource.h>
void make_realtime() {
    sched_param sp{};
    sp.sched_priority = 80;                 // 1~99
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp);
}

int main() {
    std::thread t([]{ pin_to_core(5); make_realtime(); hot_loop(); });
    t.join();
}
SCHED_FIFO 는 위험합니다 — 무한 루프를 돌면 그 코어에서 커널조차 못 끼어들어 머신이 멈춘 것처럼 보입니다. 반드시 isolcpus 로 분리된 코어에서만 쓰고, watchdog 을 켜 두세요.

실무에선 이렇게 — 바쁜 대기와 커널 바이패스 🔴 실무

잠들지 않는 수신 루프

// epoll_wait 는 '깨어나는 데' 수 µs 가 듭니다.
// 저지연에서는 자지 않고 계속 물어봅니다 (busy poll).
void rx_loop(int fd, Engine& eng) noexcept {
    alignas(64) static char buf[2048];       // 캐시라인 정렬
    for (;;) {
        ssize_t n = ::recv(fd, buf, sizeof(buf), MSG_DONTWAIT);
        if (n > 0) { eng.on_packet(buf, (size_t)n); continue; }
        _mm_pause();                          // SMT 형제에게 양보 (약 30사이클)
    }
}

// 커널에 '소켓 폴링을 커널 안에서 돌려 달라' 요청 (SO_BUSY_POLL)
int usec = 50;
setsockopt(fd, SOL_SOCKET, SO_BUSY_POLL, &usec, sizeof(usec));
// → 인터럽트·문맥 전환을 건너뛰어 수신 지연이 절반 이하로

HPC 03

락프리 자료구조 — SPSC 링 큐부터 손으로

뮤텍스는 잠기는 순간 커널로 들어가 다른 스레드를 재웁니다. 그 왕복이 수 µs 입니다. 생산자 하나 · 소비자 하나(SPSC)라면 락 없이, 원자 변수 두 개로 큐를 만들 수 있습니다. 전체 구현을 한 줄씩 보고, 언제 그냥 뮤텍스가 나은지까지 정리합니다.

락프리 큐의 정체는 인덱스 두 개 + 캐시라인 분리입니다.

SPSC 링 큐 — 전체 구현

#include <atomic>
#include <cstddef>
#include <new>
#include <type_traits>

template <class T, size_t N>   // N 은 2의 거듭제곱
class SpscQueue {
    static_assert((N & (N - 1)) == 0, "N must be a power of two");
    static constexpr size_t MASK = N - 1;

    alignas(64) std::atomic<size_t> head_{0};   // 소비자가 씀
    size_t cached_tail_ = 0;                    // 소비자 전용 사본
    alignas(64) std::atomic<size_t> tail_{0};   // 생산자가 씀
    size_t cached_head_ = 0;                    // 생산자 전용 사본
    alignas(64) T buf_[N];

public:
    // 생산자 스레드만 호출
    bool try_push(const T& v) noexcept {
        const size_t t = tail_.load(std::memory_order_relaxed);
        const size_t next = t + 1;
        if (next - cached_head_ > N) {                     // 꽉 찼나?
            cached_head_ = head_.load(std::memory_order_acquire);
            if (next - cached_head_ > N) return false;
        }
        buf_[t & MASK] = v;                                // 데이터 먼저
        tail_.store(next, std::memory_order_release);      // 그 다음 공개 ★
        return true;
    }

    // 소비자 스레드만 호출
    bool try_pop(T& out) noexcept {
        const size_t h = head_.load(std::memory_order_relaxed);
        if (h == cached_tail_) {                           // 비었나?
            cached_tail_ = tail_.load(std::memory_order_acquire);
            if (h == cached_tail_) return false;
        }
        out = buf_[h & MASK];
        head_.store(h + 1, std::memory_order_release);
        return true;
    }
};
cached_ 사본이 핵심입니다 — 상대편 인덱스를 매번 load 하면 매번 상대 코어의 캐시라인을 끌어옵니다. 사본을 두고 필요할 때만 갱신하면 처리량이 2~3배 올라갑니다. (이 기법을 쓴 대표 구현이 Folly ProducerConsumerQueue 와 rigtorp/SPSCQueue 입니다.)

memory_order 를 실전 기준으로

쓰는 곳무엇을 보장하나
relaxed원자성만. 순서 보장 없음
acquire(load)이 뒤의 읽기가 앞으로 못 옴
release(store)이 앞의 쓰기가 뒤로 못 감
acq_relRMW 연산용(둘 다)
seq_cst전역 순서. 기본값이자 제일 비쌈
// 짝을 외우면 끝입니다 — release 로 쓰고 acquire 로 읽는다
// 생산자                        소비자
buf_[t] = v;               //  ┐
tail_.store(t+1, release); //  │ 이 짝이 성립하면
                           //  │ 소비자는 buf_[t] 를
size_t x = tail_.load(acquire); // ┘ 반드시 볼 수 있습니다
if (h < x) use(buf_[h]);

// x86 에서는 acquire/release 가 '공짜'입니다 (기계어가 같음).
// 그래도 반드시 적어야 합니다 — 컴파일러 재배치를 막는 것이
// 절반의 목적이고, ARM(애플 실리콘 · Graviton)에서는 진짜 명령이 됩니다.
x86 에서 잘 도는 코드가 ARM 에서 깨집니다 — relaxed 로 대충 써도 x86 은 강한 메모리 모델이라 우연히 맞습니다. M 시리즈 맥이나 Graviton 에서 처음 터집니다. CI 에 ARM 러너를 하나 넣어 두는 것이 가장 싼 보험입니다.

이렇게도 쓸 수 있다 — 여러 생산자(MPMC)와 ABA 🟡 중급

MPMC — 칸마다 순번을 붙입니다

// Dmitry Vyukov 의 bounded MPMC 큐 — 사실상 업계 표준 설계
template <class T, size_t N>
class MpmcQueue {
    struct Cell { std::atomic<size_t> seq; T data; };
    static constexpr size_t MASK = N - 1;
    alignas(64) Cell buf_[N];
    alignas(64) std::atomic<size_t> enq_{0};
    alignas(64) std::atomic<size_t> deq_{0};
public:
    MpmcQueue() { for (size_t i = 0; i < N; ++i) buf_[i].seq.store(i, std::memory_order_relaxed); }

    bool try_push(const T& v) noexcept {
        Cell* c; size_t pos = enq_.load(std::memory_order_relaxed);
        for (;;) {
            c = &buf_[pos & MASK];
            size_t s = c->seq.load(std::memory_order_acquire);
            intptr_t diff = (intptr_t)s - (intptr_t)pos;
            if (diff == 0) {                       // 내 차례다
                if (enq_.compare_exchange_weak(pos, pos + 1,
                        std::memory_order_relaxed)) break;
            } else if (diff < 0) return false;     // 가득 참
            else pos = enq_.load(std::memory_order_relaxed);  // 남이 채감
        }
        c->data = v;
        c->seq.store(pos + 1, std::memory_order_release);   // 소비자에게 공개
        return true;
    }
};
순번(seq)이 하는 일 — “이 칸이 지금 몇 바퀴째의 누구 차례인지”를 담아 칸 단위로 순서를 강제합니다. 덕분에 포인터 CAS 가 필요 없고, 그래서 ABA 문제 자체가 생기지 않습니다.

new 는 범용 할당자입니다. “아무 크기나, 아무 때나, 아무 스레드에서나”를 감당하느라 탐색 · 락 · 단편화를 안고 있습니다. 그런데 우리 프로그램은 대개 패턴이 뻔합니다. 그 패턴을 알면 할당을 덧셈 한 번으로 줄일 수 있습니다.

아레나 — 전체 구현 (40줄)

#include <cstddef>
#include <cstdint>
#include <memory>
#include <new>

class Arena {
    std::byte* base_;
    size_t     cap_;
    size_t     cur_ = 0;
public:
    explicit Arena(size_t bytes)
        : base_(static_cast<std::byte*>(::operator new(bytes))), cap_(bytes) {}
    ~Arena() { ::operator delete(base_); }
    Arena(const Arena&) = delete;
    Arena& operator=(const Arena&) = delete;

    void* alloc(size_t n, size_t align = alignof(std::max_align_t)) noexcept {
        size_t p = (cur_ + align - 1) & ~(align - 1);   // 정렬 올림
        if (p + n > cap_) return nullptr;               // 넘치면 실패 (던지지 않음)
        cur_ = p + n;
        return base_ + p;
    }

    template <class T, class... A>
    T* make(A&&... a) noexcept {
        void* m = alloc(sizeof(T), alignof(T));
        return m ? ::new (m) T(std::forward<A>(a)...) : nullptr;
    }

    void reset() noexcept { cur_ = 0; }   // 전부 해제 — 이게 전부입니다 ★
    size_t used() const noexcept { return cur_; }
};

    arena.reset();          // 소멸자 호출 없음! 아래 경고 참고
}

    // ① 스택에 1MB 를 잡고
    std::byte buf[1 << 20];
    // ② 그 안에서만 할당하는 리소스를 만듭니다 (다 쓰면 upstream 으로)
    std::pmr::monotonic_buffer_resource pool{buf, sizeof(buf),
                                             std::pmr::new_delete_resource()};

    // ③ 표준 컨테이너를 그대로 쓰되 저장소만 바꿉니다
    std::pmr::vector<int>    v{&pool};
    std::pmr::string         s{&pool};
    std::pmr::unordered_map<int, std::pmr::string> m{&pool};

    v.reserve(10000);        // malloc 안 부릅니다 — buf 안에서 해결
    s = "요청 아이디: ";
    /* ... */
}   // pool 소멸 = 전부 해제. 개별 free 없음 ★

// 재사용 풀 — 같은 크기 블록을 반복해 쓸 때
std::pmr::unsynchronized_pool_resource up;   // 단일 스레드용 (락 없음)
std::pmr::synchronized_pool_resource   sp;   // 멀티 스레드용
리소스쓰는 자리
monotonic_buffer_resource요청·프레임 단위
unsynchronized_pool_resource같은 크기 반복
synchronized_pool_resource위 + 스레드 공유
new_delete_resource()기본(=malloc)
null_memory_resource()할당 금지 강제
실측 — 요청당 vector 를 3개 만드는 서버 핸들러에서 pmr 로 바꾸자 p99 지연 340µs → 91µs. 코드는 타입 이름만 바뀌었습니다. 핫패스에 null_memory_resource() 를 물려 두면 할당이 일어나는 순간 bad_alloc 이라 “몰래 할당”을 테스트로 잡을 수 있습니다.

4KB 대신 2MB 페이지

#include <sys/mman.h>

// 16GB 를 다루는데 페이지가 4KB 면 페이지가 400만 개 —
// TLB(주소 변환 캐시)는 보통 1500~3000개뿐이라 계속 미스가 납니다.
// 2MB 페이지로 바꾸면 페이지 수가 512분의 1이 됩니다.

void* alloc_huge(size_t bytes) {
    // 2MB 배수로 올림
    bytes = (bytes + (2u<<20) - 1) & ~((size_t)(2u<<20) - 1);
    void* p = mmap(nullptr, bytes, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB, -1, 0);
    if (p == MAP_FAILED) {                       // hugetlbfs 미설정이면
        p = mmap(nullptr, bytes, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        madvise(p, bytes, MADV_HUGEPAGE);        // THP 에 힌트만 주기
    }
    return p;
}

// 저지연이라면 여기에 두 줄 더
#include <sys/resource.h>
mlockall(MCL_CURRENT | MCL_FUTURE);   // 스왑 아웃 금지 ★
madvise(p, bytes, MADV_WILLNEED);     // 미리 페이지 폴트 일으켜 두기
std::memset(p, 0, bytes);             // 실제로 만져야 물리 페이지가 붙습니다
왜 memset 까지 하나 — 리눅스는 mmap 시점에 주소만 주고 처음 만질 때 물리 페이지를 붙입니다(demand paging). 핫패스에서 그 첫 접근이 일어나면 수 µs 짜리 페이지 폴트가 됩니다. 시작할 때 전부 만져 두는 것이 저지연의 기본 준비입니다.

병렬 계산 — OpenMP · oneTBB · std::execution

코어가 16개인데 하나만 쓰고 있다면 15배를 버리는 중입니다. 그런데 스레드를 16개 만든다고 16배가 되지는 않습니다. 어디까지 빨라지는지 미리 계산하고, 실제로 그만큼 나오는지 재는 법까지 봅니다. C++ 에서 병렬을 쓰는 세 가지 길을 실제 코드로 비교합니다.

스레드를 늘리기 전에 상한을 먼저 계산합니다 — 안 그러면 헛수고입니다.

OpenMP — 한 줄로 시작하기

// 컴파일: g++ -std=c++23 -O2 -fopenmp a.cpp   (MSVC: /openmp:llvm)
#include <omp.h>
#include <vector>

double sum_of_squares(const std::vector<double>& v) {
    double s = 0.0;
    // reduction 이 스레드별 부분합을 만들고 마지막에 합칩니다 ★
    #pragma omp parallel for reduction(+:s) schedule(static)
    for (size_t i = 0; i < v.size(); ++i) s += v[i] * v[i];
    return s;
}

#pragma omp parallel for schedule(dynamic, 64)

// 중첩 루프를 하나로 펴서 나누기
#pragma omp parallel for collapse(2)

  for (int x = 0; x < W; ++x) img[y][x] = f(x, y);

#pragma omp single

std::execution — 표준 병렬 알고리즘

#include <algorithm>
#include <execution>
#include <numeric>
#include <vector>

std::vector<double> v(100'000'000);

// ① 병렬 정렬 — 이것 하나로도 도입 가치가 있습니다
std::sort(std::execution::par, v.begin(), v.end());

// ② 병렬 + 벡터화(SIMD) 허용
std::transform(std::execution::par_unseq, v.begin(), v.end(), v.begin(),
               [](double x) { return std::sqrt(x) * 2.0; });

// ③ 리듀스 — accumulate 대신 reduce (결합 순서가 바뀔 수 있음에 주의)
double s = std::reduce(std::execution::par, v.begin(), v.end(), 0.0);

// ④ 변환 + 리듀스를 한 번에 (메모리를 한 번만 읽습니다) ★
double dot = std::transform_reduce(std::execution::par_unseq,
                a.begin(), a.end(), b.begin(), 0.0,
                std::plus<>{}, std::multiplies<>{});
# GCC/Clang 은 내부적으로 oneTBB 를 씁니다 — 링크가 필요합니다
sudo apt install libtbb-dev
g++ -std=c++23 -O2 par.cpp -ltbb -o par
# MSVC 는 추가 링크 없이 그대로 됩니다
par 정책의 두 함정 — ① 실행 순서 보장이 사라집니다. par_unseq 안에서 락을 잡거나 메모리를 할당하면 UB입니다. ② 부동소수 덧셈은 결합 법칙이 안 성립해서 reduce 결과가 accumulate 와 미세하게 다릅니다. 재현성이 필요한 계산(회계·검증)에서는 문제가 됩니다.

parallel_for 와 parallel_reduce

#include <tbb/parallel_for.h>
#include <tbb/parallel_reduce.h>
#include <tbb/blocked_range.h>

// 범위를 트리처럼 쪼개고, 논 스레드가 남의 작업을 훔쳐 갑니다(work stealing)
tbb::parallel_for(tbb::blocked_range<size_t>(0, n, /*grain=*/1024),
    [&](const tbb::blocked_range<size_t>& r) {
        for (size_t i = r.begin(); i != r.end(); ++i) out[i] = f(in[i]);
    });

// 리듀스 — 부분 결과를 어떻게 합칠지까지 지정
double total = tbb::parallel_reduce(
    tbb::blocked_range<size_t>(0, n), 0.0,
    [&](const auto& r, double init) {
        for (size_t i = r.begin(); i != r.end(); ++i) init += v[i];
        return init;
    },
    std::plus<double>{});

// 2차원 범위도 그대로
tbb::parallel_for(tbb::blocked_range2d<int>(0, H, 32, 0, W, 32),
    [&](const auto& r) { /* r.rows() · r.cols() */ });
grain size 감각 — 한 덩어리가 최소 수 µs 어치는 되어야 합니다. 너무 잘게 쪼개면 스케줄링 비용이 계산보다 커집니다. 모르겠으면 생략하세요 — TBB 의 auto_partitioner 가 대개 잘 맞춥니다.

실무에선 이렇게 — 스레드 수를 어떻게 정하나 🔴 실무

hardware_concurrency 를 그대로 믿지 않기

#include <thread>
#include <fstream>
#include <sched.h>

unsigned usable_threads() {
    // ① 컨테이너 CPU 제한 (cgroup v2) — 쿠버네티스에서 필수 ★
    std::ifstream f("/sys/fs/cgroup/cpu.max");
    long quota, period;
    if (f >> quota >> period && quota > 0)
        return std::max<long>(1, quota / period);

    // ② affinity 로 묶여 있으면 그만큼만
    cpu_set_t set;
    if (sched_getaffinity(0, sizeof(set), &set) == 0)
        return (unsigned)CPU_COUNT(&set);

    return std::thread::hardware_concurrency();   // ③ 최후의 수단
}
// hardware_concurrency() 는 '논리 코어'를 셉니다.
// 8코어 16스레드 머신에서 16을 돌려주는데,
// 메모리 대역폭이 병목인 작업이라면 8이 더 빠릅니다.

한 단계 더 — 대역폭 한계와 루프라인 🧬 전문가

연산 강도로 상한을 계산합니다

연산 강도(AI) = 부동소수 연산 수 ÷ 메모리에서 읽은 바이트 수

예) c[i] = a[i] + b[i]  (double)
    연산 1회 · 메모리 24바이트(a 읽기 8 + b 읽기 8 + c 쓰기 8)
    AI = 1/24 ≈ 0.042 FLOP/byte

머신 성능:
    최대 연산  ~1,500 GFLOP/s  (16코어 · AVX-512 · FMA)
    최대 대역폭   ~200 GB/s

    대역폭이 결정하는 상한 = 0.042 × 200 = 8.4 GFLOP/s
    → 최대 연산 성능의 0.6% 밖에 못 씁니다 ★
    → 이런 루프는 코어를 늘려도 소용없습니다. 메모리가 병목입니다.

    AI 가 10 을 넘어야(예: 행렬 곱) 연산이 병목이 되고,
    그때부터 SIMD · 코어 수가 의미를 갖습니다.
이 계산이 하는 일 — “병렬화해도 소용없는 루프”를 코드를 짜기 전에 걸러 줍니다. 대역폭 한계 루프에서 할 일은 병렬화가 아니라 메모리를 덜 읽게 만드는 것(융합 · 타일링 · 자료형 축소)입니다.

// vecadd.cu
#include <cstdio>
#include <vector>

__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];      // 범위 검사 필수 (남는 스레드가 생김)
}

int main() {
    const int n = 1 << 24;              // 1600만 개
    std::vector<float> ha(n, 1.0f), hb(n, 2.0f), hc(n);

    float *da, *db, *dc;
    cudaMalloc(&da, n * sizeof(float));
    cudaMalloc(&db, n * sizeof(float));
    cudaMalloc(&dc, n * sizeof(float));

    cudaMemcpy(da, ha.data(), n * sizeof(float), cudaMemcpyHostToDevice);
    cudaMemcpy(db, hb.data(), n * sizeof(float), cudaMemcpyHostToDevice);

    int threads = 256;                              // 보통 128~512
    int blocks  = (n + threads - 1) / threads;      // 올림 나눗셈
    add<<<blocks, threads>>>(da, db, dc, n);

    cudaMemcpy(hc.data(), dc, n * sizeof(float), cudaMemcpyDeviceToHost);
    cudaDeviceSynchronize();                        // 커널 에러는 여기서 드러납니다

    printf("%f\n", hc[0]);                          // 3.000000
    cudaFree(da); cudaFree(db); cudaFree(dc);
}

손익분기 계산

[ 벡터 덧셈 1600만 개 (float) — 위의 예제 ]
  데이터 전송   192MB (a, b 보내고 c 받기)
  PCIe 4.0     25GB/s  →  전송 시간 약 7.7ms
  커널 자체     약 0.4ms
  ─────────────────────────────────
  GPU 총합      약 8.1ms
  CPU (16스레드 AVX)  약 3.5ms
  → GPU 가 2배 느립니다 ★ 전송이 전부를 먹었습니다

[ 같은 데이터로 반복 계산을 100번 한다면 ]
  전송 7.7ms + 커널 0.4 × 100 = 47.7ms
  CPU 3.5 × 100 = 350ms
  → GPU 가 7배 빠릅니다

결론 — GPU 는 '한 번 올린 데이터로 얼마나 오래 계산하느냐'가 전부입니다.
       연산 강도(h05) 를 GPU 에도 똑같이 적용하면 됩니다.
GPU 가 안 맞는 일 — ① 데이터가 작을 때(수 MB 이하), ② 분기가 데이터마다 다를 때(warp divergence), ③ 임의 접근이 심할 때, ④ 매 호출마다 새 데이터를 올려야 할 때. 넷 중 하나라도 해당되면 CPU + SIMD 가 대개 낫습니다.

// 공유 메모리 타일링 — GPU 최적화의 대표 기법
__global__ void matmul(const float* A, const float* B, float* C, int N) {
    __shared__ float sA[16][16], sB[16][16];   // 블록 안에서 공유 (아주 빠름)
    int r = blockIdx.y * 16 + threadIdx.y;
    int c = blockIdx.x * 16 + threadIdx.x;
    float acc = 0.f;
    for (int t = 0; t < N / 16; ++t) {
        sA[threadIdx.y][threadIdx.x] = A[r * N + t * 16 + threadIdx.x];
        sB[threadIdx.y][threadIdx.x] = B[(t * 16 + threadIdx.y) * N + c];
        __syncthreads();
        for (int k = 0; k < 16; ++k) acc += sA[threadIdx.y][k] * sB[k][threadIdx.x];
        __syncthreads();
    }
    C[r * N + c] = acc;
}

int main(int argc, char** argv) {

    avformat_open_input(&fmt, argv[1], nullptr, nullptr);
    avformat_find_stream_info(fmt, nullptr);

    // 비디오 스트림 찾기
    const AVCodec* dec = nullptr;
    int vs = av_find_best_stream(fmt, AVMEDIA_TYPE_VIDEO, -1, -1, &dec, 0);

    AVCodecContext* ctx = avcodec_alloc_context3(dec);
    avcodec_parameters_to_context(ctx, fmt->streams[vs]->codecpar);
    ctx->thread_count = 0;              // 0 = 코어 수만큼 자동 ★
    avcodec_open2(ctx, dec, nullptr);

    AVPacket* pkt = av_packet_alloc();
    AVFrame*  frm = av_frame_alloc();

    while (av_read_frame(fmt, pkt) >= 0) {
        if (pkt->stream_index == vs) {
            if (avcodec_send_packet(ctx, pkt) == 0) {
                // 한 패킷에서 프레임이 0개일 수도, 여러 개일 수도 있습니다 ★
                while (avcodec_receive_frame(ctx, frm) == 0) {
                    // frm->data[0..2] = Y, U, V 평면
                    // frm->linesize[0] = 한 줄 바이트 수 (폭과 다릅니다!)
                    process(frm);
                }
            }
        }
        av_packet_unref(pkt);           // 참조를 놓아 줍니다 (안 하면 누수)
    }
    avcodec_send_packet(ctx, nullptr);  // 플러시 — 남은 프레임 뽑기
    while (avcodec_receive_frame(ctx, frm) == 0) process(frm);

    av_frame_free(&frm); av_packet_free(&pkt);
    avcodec_free_context(&ctx); avformat_close_input(&fmt);
}
초보가 반드시 틀리는 두 가지 — ① linesize 는 폭과 다릅니다 (정렬 때문에 패딩이 붙습니다). 폭으로 계산하면 화면이 비스듬히 밀립니다. ② send 한 번에 receive 는 여러 번 — B프레임 때문에 디코더가 프레임을 모았다가 한꺼번에 내놓습니다.

// 카메라 8대를 동시에 처리하는 구조 — 단계마다 스레드를 분리합니다
struct Pipeline {
    SpscQueue<AVFrame*, 8>  decoded_;    // h03 의 큐
    SpscQueue<Result,   64> results_;

    void decode_thread(int cam) {        // 카메라당 하나
        while (running_) {
            AVFrame* f = decode_next(cam);
            if (!decoded_.try_push(f)) { av_frame_free(&f); drops_++; }
            // ★ 큐가 차면 '기다리지 않고 버립니다' —
            //   실시간 영상에서는 늦은 프레임이 없는 프레임보다 나쁩니다
        }
    }
    void infer_thread() {                // GPU 한 장을 공유
        std::vector<AVFrame*> batch;
        while (running_) {
            AVFrame* f;
            while (batch.size() < 8 && decoded_.try_pop(f)) batch.push_back(f);
            if (!batch.empty()) { results_.try_push(infer(batch)); batch.clear(); }
        }
    }
};
실시간 영상의 철칙 — 큐를 무한정 키우지 마세요. 처리가 못 따라가면 지연이 계속 쌓여 “10초 전 화면”을 보게 됩니다. 고정 크기 큐 + 오래된 프레임 버리기가 정답이고, 버린 수(drops_)를 지표로 내보내야 합니다.

#include <cmath>
#include <atomic>

struct State {
    double phase = 0.0;
    std::atomic<float> freq{440.0f};   // UI 가 바꾸는 값 ★
};

// 이 함수는 '실시간 스레드'에서 불립니다 — 규칙이 적용됩니다
static int cb(const void*, void* out, unsigned long n,
              const PaStreamCallbackTimeInfo*, PaStreamCallbackFlags, void* ud) {
    auto* s = static_cast<State*>(ud);
    float* o = static_cast<float*>(out);
    const double f  = s->freq.load(std::memory_order_relaxed);
    const double dp = 2.0 * M_PI * f / 48000.0;
    for (unsigned long i = 0; i < n; ++i) {
        float v = (float)std::sin(s->phase);
        *o++ = v; *o++ = v;              // 스테레오
        s->phase += dp;
        if (s->phase > 2 * M_PI) s->phase -= 2 * M_PI;
    }
    return paContinue;
}

int main() {
    State st;
    Pa_Initialize();
    PaStream* stream;
    Pa_OpenDefaultStream(&stream, 0, 2, paFloat32, 48000, 128, cb, &st);
    Pa_StartStream(stream);
    std::getchar();                      // UI 스레드에서 st.freq 를 바꿔도 안전
    Pa_StopStream(stream); Pa_CloseStream(stream); Pa_Terminate();
}

    }

// 콜백 소요 시간을 직접 재서 '예산 대비 비율'을 기록합니다
struct RtWatch {
    std::atomic<uint32_t> overruns{0};
    std::atomic<uint32_t> worst_pct{0};
    void measure(uint64_t cycles, double budget_ns, double ghz) {
        double used = cycles / ghz;               // ns
        uint32_t pct = (uint32_t)(used / budget_ns * 100);
        uint32_t w = worst_pct.load(std::memory_order_relaxed);
        while (pct > w && !worst_pct.compare_exchange_weak(w, pct)) {}
        if (pct >= 100) overruns.fetch_add(1, std::memory_order_relaxed);
    }
};

// 링 버퍼 하나로 딜레이·에코·코러스가 전부 됩니다
class Delay {
    std::vector<float> buf_;     // prepareToPlay 에서만 크기 결정
    size_t w_ = 0, mask_ = 0;
public:
    void prepare(double sr, double maxSec) {
        size_t n = 1; while (n < (size_t)(sr * maxSec)) n <<= 1;  // 2의 거듭제곱
        buf_.assign(n, 0.0f);
        mask_ = n - 1;
    }
    // 실시간 스레드 — 할당 없음, 분기 없음
    float process(float x, float delaySamples, float fb, float mix) noexcept {
        float rp = (float)w_ - delaySamples;
        while (rp < 0) rp += (float)buf_.size();
        size_t i0 = (size_t)rp & mask_;
        size_t i1 = (i0 + 1) & mask_;
        float  fr = rp - std::floor(rp);
        float  d  = buf_[i0] + fr * (buf_[i1] - buf_[i0]);   // 선형 보간
        buf_[w_ & mask_] = x + d * fb;
        w_ = (w_ + 1) & mask_;
        return x * (1.0f - mix) + d * mix;
    }
};
왜 보간이 필요한가 — 딜레이 시간을 부드럽게 바꾸려면 정수가 아닌 위치를 읽어야 합니다. 정수로 반올림하면 노브를 돌릴 때 지지직 소리가 납니다.

// ② 채널 처리를 SIMD 로 — 4샘플씩
#include <immintrin.h>
void gain_simd(float* p, size_t n, float g) noexcept {
    __m128 gv = _mm_set1_ps(g);
    size_t i = 0;
    for (; i + 4 <= n; i += 4)
        _mm_storeu_ps(p + i, _mm_mul_ps(_mm_loadu_ps(p + i), gv));
    for (; i < n; ++i) p[i] *= g;
}

고속 I/O — mmap · io_uring · O_DIRECT

read() 한 번은 시스템콜 한 번입니다. 초당 100만 건을 읽어야 하면 시스템콜만으로 CPU 한 코어가 날아갑니다. 리눅스는 이 문제를 위해 io_uring 이라는 완전히 새로운 인터페이스를 만들었습니다. 실제 코드와 실측 수치로 봅니다.

I/O 는 “빨리 하는” 것이 아니라 여러 건을 동시에 걸어 두는 것입니다.

io_uring — liburing 으로 실제 읽기

#include <liburing.h>
#include <fcntl.h>
#include <vector>

constexpr int QD = 128;                 // 큐 깊이 — 동시에 걸어 둘 요청 수

int main() {
    io_uring ring;
    io_uring_queue_init(QD, &ring, 0);  // SQ/CQ 를 만들고 mmap 합니다

    int fd = ::open("big.bin", O_RDONLY);
    std::vector<std::vector<char>> bufs(QD, std::vector<char>(4096));

    size_t submitted = 0, done = 0, total = 1'000'000;
    while (done < total) {
        // ① 빈 슬롯만큼 요청을 채웁니다
        int n = 0;
        while (submitted - done < QD && submitted < total) {
            io_uring_sqe* sqe = io_uring_get_sqe(&ring);
            if (!sqe) break;
            size_t i = submitted % QD;
            off_t off = (off_t)(rand() % 100000) * 4096;
            io_uring_prep_read(sqe, fd, bufs[i].data(), 4096, off);
            io_uring_sqe_set_data64(sqe, submitted);   // 나중에 누구 결과인지
            ++submitted; ++n;
        }
        if (n) io_uring_submit(&ring);   // ② 시스템콜 한 번 — n 건을 한꺼번에 ★

        // ③ 완료된 것들을 한꺼번에 수확
        io_uring_cqe* cqe;
        unsigned head; unsigned count = 0;
        io_uring_wait_cqe(&ring, &cqe);
        io_uring_for_each_cqe(&ring, head, cqe) {
            if (cqe->res < 0) { /* 에러: -errno */ }
            ++done; ++count;
        }
        io_uring_cq_advance(&ring, count);
    }
    io_uring_queue_exit(&ring);
}
핵심은 큐 깊이입니다 — NVMe SSD 는 내부적으로 수십 개를 동시에 처리합니다. 요청을 하나씩 보내면 장치가 놀고, 128개를 걸어 두면 그제야 제 성능이 납니다. read() 가 느린 진짜 이유는 시스템콜이 아니라 큐 깊이 1 입니다.

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

class MappedFile {
    void*  p_ = nullptr;
    size_t n_ = 0;
public:
    explicit MappedFile(const char* path) {
        int fd = ::open(path, O_RDONLY);
        struct stat st{}; fstat(fd, &st);
        n_ = (size_t)st.st_size;
        p_ = mmap(nullptr, n_, PROT_READ, MAP_PRIVATE, fd, 0);
        ::close(fd);                       // 매핑은 fd 없이도 살아 있습니다 ★
        madvise(p_, n_, MADV_SEQUENTIAL);  // 순차로 읽을 거라고 알려 줍니다
    }
    ~MappedFile() { if (p_) munmap(p_, n_); }
    const char* data() const { return (const char*)p_; }
    size_t size() const { return n_; }
};

AF_XDP · DPDK 개요

[ 일반 소켓 ]
  NIC → 드라이버 → 커널 네트워크 스택 → 소켓 버퍼 → 내 버퍼
        (인터럽트 · 복사 2회 · 프로토콜 처리 전부 커널)

[ AF_XDP ]  커널 5.4+ · 일반 NIC · 무료
  NIC → 드라이버 → (eBPF 프로그램이 골라냄) → UMEM(내 메모리) 직행
        · 커널 스택을 건너뛰지만 커널 드라이버는 그대로 씁니다
        · NIC 를 통째로 뺏지 않아 같은 카드로 SSH 도 됩니다 ★
        · 왕복 ~2µs · 초당 1400만 패킷(단일 코어)

[ DPDK ]  전용 드라이버 · NIC 를 통째로 점유
  NIC → (유저 공간 드라이버) → 내 메모리
        · 폴링 모드 · 커널 전혀 안 씀 · 왕복 ~1.5µs
        · 그 NIC 로는 다른 통신을 못 합니다 (관리 포트 별도 필요)
        · TCP 를 직접 구현해야 합니다 (또는 f-stack · VPP)

[ RDMA / RoCE ]  상대 서버 메모리에 직접 쓰기
        · CPU 개입 없이 원격 메모리 접근 · 왕복 ~1µs
        · HPC · 분산 스토리지 · GPU 클러스터에서 표준
2026년의 실용적 선택 — 대부분의 팀에게는 AF_XDP 가 정답입니다. DPDK 는 성능이 조금 더 좋지만 운영 비용이 훨씬 큽니다 (NIC 전용화 · 드라이버 바인딩 · huge page 필수 · 디버깅 어려움).

// DuckDB · ClickHouse 가 쓰는 실행 모델이기도 합니다
constexpr size_t VEC = 2048;              // 캐시에 들어가는 크기

double sum_filtered(const double* px, const int32_t* qty, size_t n) {
    double acc = 0.0;
    for (size_t base = 0; base < n; base += VEC) {
        size_t m = std::min(VEC, n - base);
        // ① 필터를 먼저 '선택 벡터'로 만들고
        alignas(64) uint16_t sel[VEC]; size_t k = 0;
        for (size_t i = 0; i < m; ++i) if (qty[base+i] > 0) sel[k++] = (uint16_t)i;
        // ② 통과한 것만 계산 — 분기 없는 연속 루프가 됩니다
        for (size_t j = 0; j < k; ++j) acc += px[base + sel[j]];
    }
    return acc;
}

#include <immintrin.h>

// AVX2 — double 4개씩. 누산기를 4개 두어 의존 사슬을 끊습니다 ★
double simd_sum(const double* p, size_t n) {
    __m256d a0 = _mm256_setzero_pd(), a1 = a0, a2 = a0, a3 = a0;
    size_t i = 0;
    for (; i + 16 <= n; i += 16) {
        a0 = _mm256_add_pd(a0, _mm256_loadu_pd(p + i));
        a1 = _mm256_add_pd(a1, _mm256_loadu_pd(p + i + 4));
        a2 = _mm256_add_pd(a2, _mm256_loadu_pd(p + i + 8));
        a3 = _mm256_add_pd(a3, _mm256_loadu_pd(p + i + 12));
    }
    __m256d s = _mm256_add_pd(_mm256_add_pd(a0, a1), _mm256_add_pd(a2, a3));
    alignas(32) double t[4]; _mm256_store_pd(t, s);
    double acc = t[0] + t[1] + t[2] + t[3];
    for (; i < n; ++i) acc += p[i];       // 남는 것
    return acc;
}
// 누산기 하나만 쓰면 add 의 지연(4사이클)에 묶여 성능이 4분의 1이 됩니다.

// 조건부 합계 — 분기 대신 마스크
double simd_sum_gt(const double* p, size_t n, double thr) {
    __m256d th = _mm256_set1_pd(thr), acc = _mm256_setzero_pd();
    size_t i = 0;
    for (; i + 4 <= n; i += 4) {
        __m256d v = _mm256_loadu_pd(p + i);
        __m256d m = _mm256_cmp_pd(v, th, _CMP_GT_OQ);   // 조건 → 마스크
        acc = _mm256_add_pd(acc, _mm256_and_pd(v, m));  // 통과한 것만 더함
    }
    alignas(32) double t[4]; _mm256_store_pd(t, acc);
    double r = t[0] + t[1] + t[2] + t[3];
    for (; i < n; ++i) if (p[i] > thr) r += p[i];
    return r;
}

// std::simd 는 C++26 에 들어갑니다.
// 지금은 experimental 로 GCC 11+ · Clang 에서 쓸 수 있습니다.
#include <experimental/simd>
namespace stdx = std::experimental;

double portable_sum(const double* p, size_t n) {
    using V = stdx::native_simd<double>;   // AVX2 면 4개, AVX-512 면 8개
    V acc = 0.0;
    size_t i = 0, W = V::size();
    for (; i + W <= n; i += W) {
        V v; v.copy_from(p + i, stdx::element_aligned);
        acc += v;
    }
    double r = stdx::reduce(acc);
    for (; i < n; ++i) r += p[i];
    return r;
}

ML 추론 런타임 — 파이썬 없이 배포하기

모델 학습은 파이썬이 압도적입니다. 그런데 배포는 사정이 다릅니다. 파이썬 인터프리터 · 수 GB 짜리 의존성 · GIL 없이 실행 파일 하나로 끝내고 싶을 때 C++ 추론 런타임을 씁니다. ONNX Runtime 으로 일반 모델을, llama.cpp 로 LLM 을 돌려 봅니다.

로컬 추론의 병목은 연산이 아니라 메모리 대역폭입니다.

#include <vector>

int main() {
    Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "app");

    Ort::SessionOptions so;
    so.SetIntraOpNumThreads(8);                    // 연산 하나 안의 병렬
    so.SetGraphOptimizationLevel(ORT_ENABLE_ALL);  // 그래프 융합 ★
    // GPU 를 쓰려면 (CUDA 프로바이더)
    // OrtSessionOptionsAppendExecutionProvider_CUDA(so, 0);

    Ort::Session session(env, "model.onnx", so);

    // 입력 텐서 만들기 — 우리 벡터를 '감싸기만' 합니다 (복사 없음)
    std::vector<float>   input(1 * 3 * 224 * 224);
    std::vector<int64_t> shape{1, 3, 224, 224};
    auto mem = Ort::MemoryInfo::CreateCpu(OrtArenaAllocator, OrtMemTypeDefault);
    Ort::Value in = Ort::Value::CreateTensor<float>(
        mem, input.data(), input.size(), shape.data(), shape.size());

    const char* in_names[]  = {"input"};
    const char* out_names[] = {"output"};

    auto outs = session.Run(Ort::RunOptions{nullptr},
                            in_names, &in, 1, out_names, 1);

    float* p = outs[0].GetTensorMutableData<float>();
    auto info = outs[0].GetTensorTypeAndShapeInfo();
    size_t n = info.GetElementCount();
    // p[0..n) 가 결과입니다
}

속도를 결정하는 것

[ 토큰 생성 속도의 이론적 상한 ]
  decode 단계는 토큰마다 '가중치 전체'를 한 번 읽습니다.
  → 초당 토큰 수 ≈ 메모리 대역폭 ÷ 모델 크기

  예) Q4 7B 모델(4.1GB)
      · DDR5 데스크톱   ~60GB/s  →  약 14 tok/s
      · M4 Max 통합메모리 ~410GB/s →  약 100 tok/s
      · RTX 4090 VRAM   ~1000GB/s →  약 240 tok/s

  ★ 연산 능력(TFLOPS)이 아니라 대역폭이 답을 정합니다.
     그래서 애플 실리콘이 로컬 LLM 에 유독 강합니다.

[ prefill 은 반대입니다 ]
  프롬프트 전체를 한 번에 행렬 곱으로 처리 → 연산 병목
  → 긴 프롬프트는 GPU 가 압도적으로 유리합니다

[ 그래서 지표를 두 개로 봅니다 ]
  · TTFT (첫 토큰까지) — prefill 성능
  · TPS  (초당 토큰)   — decode 성능
배치가 판을 바꿉니다 — 요청 하나만 처리하면 대역폭에 묶이지만, 여러 요청을 함께 decode 하면 같은 가중치 읽기를 나눠 쓰므로 총 처리량이 몇 배가 됩니다. vLLM · TensorRT-LLM 이 하는 일이 이것입니다.

추론 서버 뼈대

// 요청을 모아 배치로 처리하는 구조 — GPU 활용률이 몇 배가 됩니다
class BatchServer {
    SpscQueue<Req*, 1024> inbox_;              // h03
    Ort::Session& sess_;
    static constexpr int MAX_B = 16;
    static constexpr auto MAX_WAIT = std::chrono::milliseconds(5);

    void worker() {
        std::vector<Req*> batch;
        auto deadline = Clock::now() + MAX_WAIT;
        while (running_) {
            Req* r;
            // ★ 배치가 차거나 마감 시간이 되면 실행 — 지연과 처리량의 타협
            while (batch.size() < MAX_B && Clock::now() < deadline)
                if (inbox_.try_pop(r)) batch.push_back(r);
            if (batch.empty()) { deadline = Clock::now() + MAX_WAIT; continue; }

            run_batch(batch);                   // 한 번의 Run 으로 전부
            for (auto* q : batch) q->done.set_value();
            batch.clear();
            deadline = Clock::now() + MAX_WAIT;
        }
    }
};
동적 배치의 효과 — 이미지 분류 서버에서 배치 없이 초당 320건, 마감 5ms 동적 배치로 초당 2,100건. p99 지연은 3.1ms → 7.4ms 로 늘었지만 장비 수는 6분의 1이 됩니다. 요구 지연이 허락하면 거의 항상 옳은 거래입니다.

직접 짜 보면 이해가 달라집니다

// 추론 엔진의 핵심은 결국 행렬 곱 하나입니다.
// 양자화된 가중치(4비트)를 풀면서 곱하는 것이 GGML 이 하는 일입니다.

// Q4 블록 — 32개 값을 16바이트 + 스케일 하나로 저장 (2.5배 압축)
struct BlockQ4 {
    uint16_t d;         // FP16 스케일
    uint8_t  qs[16];    // 4비트 × 32개
};

// 한 블록을 풀어 float 32개로 (실제로는 SIMD 로 처리합니다)
inline void dequant_q4(const BlockQ4& b, float* out) {
    const float d = fp16_to_fp32(b.d);
    for (int i = 0; i < 16; ++i) {
        int lo = (b.qs[i] & 0x0F) - 8;      // 하위 4비트
        int hi = (b.qs[i] >>   4) - 8;      // 상위 4비트
        out[i]      = lo * d;
        out[i + 16] = hi * d;
    }
}
// 실제 커널은 '풀어서 저장'하지 않고 곱셈에 바로 넣습니다 —
// 메모리를 한 번만 읽는 것이 전부이기 때문입니다(위 대역폭 계산 참고).
직접 짜는 것을 권하지는 않습니다 — 다만 이 구조를 알면 “왜 Q4 가 2.5배 작은데 품질은 별로 안 떨어지나”, “왜 대역폭이 속도를 정하나”, “왜 배치가 이득인가”가 전부 설명됩니다. 수치를 해석할 수 있게 되는 것이 목적입니다.
정리 — 추론을 C++ 로 옮기는 값어치는 속도보다 배포에 있습니다 — 실행 파일 하나, 의존성 없음, 지연 편차 없음. 병목은 대개 메모리 대역폭입니다.

컴파일 · 바이너리 최적화 — LTO · PGO · 빌드 시간

코드를 한 줄도 안 고치고 10~30% 빨라지는 방법이 있습니다. 컴파일러에게 더 넓게 보게 하고(LTO), 실제로 어떻게 도는지 알려 주는(PGO) 것입니다. 동시에 C++ 의 가장 큰 불편인 빌드 시간을 줄이는 실전 처방도 함께 봅니다.

코드를 안 고치고 얻는 성능은 여기까지입니다 — 대신 확실합니다.

PGO 가 실제로 하는 일 — ① 자주 도는 분기를 예측 힌트로, ② 뜨거운 함수만 인라인(차가운 함수는 크기 우선), ③ 코드 배치 재정렬로 명령어 캐시 적중률 향상. 분기가 많은 코드(파서 · 인터프리터 · 컴파일러)에서 효과가 가장 큽니다.

연속 프로파일링을 권합니다 — 성능 문제는 대개 재현이 안 됩니다. “어제 새벽 3시에 느렸다”를 조사하려면 그때의 플레임그래프가 이미 저장돼 있어야 합니다. 오버헤드는 1% 미만이고, 얻는 것은 비교가 안 됩니다.

[ 배운 것 ]
  · 범인은 '파싱'이 아니라 '할당'이었습니다
  · 평균(1.2ms)은 처음부터 끝까지 거의 안 변했습니다
  · 코드 변경량은 200줄 미만, 알고리즘은 하나도 안 바꿨습니다
이 사례의 교훈 — p99 문제의 원인은 거의 항상 “가끔 비싼 것”입니다. 할당 · 페이지 폴트 · 락 대기 · GC · 리해싱 · 로그 플러시. 평균을 보면 절대 안 보입니다 — 그래서 h02 의 히스토그램이 필요합니다.
정리 — 프로파일링은 도구가 아니라 순서입니다 — 지표 정의 → CPU 사용률 → 플레임그래프 → IPC → 하나만 고치고 다시 재기.
