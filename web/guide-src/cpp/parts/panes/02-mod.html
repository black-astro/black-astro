RAII — C++ 의 심장

“가진 것은 사라질 때 알아서 반납한다”는 한 문장이 전부입니다. 파이썬의 with 가 모든 객체에 항상 걸려 있는 셈입니다.

"닫는 것을 잊었다"는 버그가 C++ 에서 드문 이유입니다 — 잊을 코드 자체가 없습니다.

문제 — 손으로 정리하면 반드시 빠뜨립니다

void process(const char* path) {
    FILE* f = std::fopen(path, "r");
    std::mutex& m = get_mutex();
    m.lock();
    int* buf = new int[1024];

    if (!validate()) return;          // ❌ 셋 다 안 풀림
    if (parse(f) < 0) { m.unlock(); return; }   // ❌ 두 개 빠짐
    risky();                          // ❌ 예외가 나면 전부 샘

    delete[] buf;
    m.unlock();
    std::fclose(f);
}
//  경로가 늘어날수록 정리 코드가 곱하기로 늘어납니다.
//  예외까지 고려하면 사람이 지킬 수 없습니다.
다른 언어는 어떻게 했나 — 자바는 try-finally, 파이썬은 with, C# 은 using. 전부 “블록을 벗어날 때 정리” 를 문법으로 만든 것입니다. C++ 는 그걸 객체의 소멸자로 해결했고, 그래서 블록을 따로 쓸 필요가 없습니다.

class Socket {
    int fd_ = -1;
public:
    explicit Socket(int fd) noexcept : fd_(fd) {}
    ~Socket() { if (fd_ >= 0) ::close(fd_); }

    Socket(const Socket&)            = delete;     // 복사 금지 ★
    Socket& operator=(const Socket&) = delete;
    Socket(Socket&& o) noexcept : fd_(std::exchange(o.fd_, -1)) {}
    Socket& operator=(Socket&& o) noexcept {
        if (this != &o) { if (fd_ >= 0) ::close(fd_); fd_ = std::exchange(o.fd_, -1); }
        return *this;
    }
    int get() const noexcept { return fd_; }
};

임시 상태 되돌리기 — scope guard

// "블록을 벗어날 때 이걸 실행해" 를 즉석에서 만드는 관용구
template<class F>
class ScopeExit {
    F f_;
    bool active_ = true;
public:
    explicit ScopeExit(F f) : f_(std::move(f)) {}
    ~ScopeExit() { if (active_) f_(); }
    void dismiss() noexcept { active_ = false; }   // 취소
    ScopeExit(const ScopeExit&) = delete;
};
template<class F> ScopeExit(F) -> ScopeExit<F>;   // 추론 가이드 (C++17)

// 사용 — 원래 값으로 되돌리기
void render() {
    auto old = get_state();
    set_state(temp);
    ScopeExit restore([&]{ set_state(old); });     // ★ 어떤 경로로 나가도 복원

    draw();                    // 예외가 나도 복원됩니다
}

// 트랜잭션 패턴 — 성공하면 취소
void insert(Db& db, const Row& r) {
    db.begin();
    ScopeExit rollback([&]{ db.rollback(); });
    db.exec(r);
    db.commit();
    rollback.dismiss();        // ★ 여기까지 왔으면 롤백하지 않음
}

MOD 02

스마트 포인터 — new·delete 를 지웁니다

이것만 써도 메모리 누수의 90%가 사라집니다. 핵심은 “누가 소유하는가”를 타입으로 표현하는 것입니다.

고르는 순서는 값 → unique_ptr → shared_ptr 입니다. 마지막까지 오는 경우는 생각보다 드뭅니다.

unique_ptr — 기본값

#include <memory>

auto p = std::make_unique<Widget>(arg1, arg2);   // ★ new 대신 이것
p->draw();
(*p).draw();
p.get();          // 원본 포인터 (C API 에 넘길 때)
p.reset();        // 지금 해제
p = nullptr;      // 같은 뜻

// 복사 불가 · 이동만 가능 — "소유자는 하나"를 타입이 강제합니다
auto q = p;              // ❌ 컴파일 에러
auto q = std::move(p);   // ✅ 소유권 이전 (p 는 이제 nullptr)

// 함수 인터페이스로 의도를 표현
std::unique_ptr<Widget> create();          // "받는 쪽이 소유합니다"
void consume(std::unique_ptr<Widget> w);   // "넘기면 내 것이 됩니다"
void use(const Widget& w);                 // "잠깐 빌려 봅니다" ★
void use(Widget* w);                       // "빌려 보되 없을 수도"

// 배열도 됩니다 (대개 vector 가 낫습니다)
auto arr = std::make_unique<double[]>(1000);
arr[0] = 1.0;

// 비용 — 원시 포인터와 완전히 같습니다 (크기 8바이트, 오버헤드 0) ★

shared_ptr — 정말 필요할 때만

auto s = std::make_shared<Widget>(args);   // 참조 카운트 방식
auto s2 = s;                                // 카운트 +1
s.use_count();                              // 현재 소유자 수
//  마지막 shared_ptr 이 사라질 때 해제됩니다

// weak_ptr — 보기만 하고 수명에 관여하지 않습니다
std::weak_ptr<Widget> w = s;
if (auto locked = w.lock()) {               // 살아 있으면 shared_ptr 획득
    locked->draw();
}

// ⚠ 순환 참조 — 서로 shared_ptr 이면 영원히 해제되지 않습니다 ★
struct Node {
    std::shared_ptr<Node> child;
    std::weak_ptr<Node>   parent;    // ★ 부모는 weak 로 끊습니다
};

// 비용 — 원시 포인터의 두 배 크기 + 원자적 카운트 연산
sizeof(std::unique_ptr<int>);   // 8
sizeof(std::shared_ptr<int>);   // 16 (포인터 + 제어 블록 포인터)
//   복사할 때마다 원자 연산이 일어나 멀티스레드에서 경합이 생깁니다
shared_ptr 을 기본값으로 쓰지 마세요 — “누가 소유하는지 생각하기 귀찮아서” 쓰는 경우가 많은데, 그러면 수명이 언제 끝나는지 아무도 모르는 코드가 됩니다. 정말로 소유자가 여럿일 때만(캐시·그래프·비동기 완료 대기) 쓰세요.

한 단계 더 — 제어 블록과 실제 비용 🧬 전문가

shared_ptr 내부

shared_ptr 은 두 개의 포인터입니다
  ① 객체 포인터
  ② 제어 블록 포인터 → { 강한 카운트, 약한 카운트, 삭제자, 할당자 }

make_shared<T>(args)
  객체와 제어 블록을 한 번에 할당 (할당 1회) ★
  → 캐시 지역성이 좋고 빠릅니다
  ⚠ 대신 weak_ptr 이 하나라도 살아 있으면
    객체 메모리 전체가 해제되지 않습니다 (제어 블록과 붙어 있으므로)

shared_ptr<T>(new T(args))
  할당 2회 (객체 + 제어 블록)
  → weak_ptr 이 남아도 객체 메모리는 즉시 해제됩니다

카운트 연산 비용
  · 복사·소멸마다 원자적 증감 (lock 접두 명령)
  · 여러 스레드가 같은 shared_ptr 을 복사하면 캐시 라인 경합 ★
  · 그래서 핫 루프에서 shared_ptr 을 값으로 넘기면 눈에 띄게 느려집니다
    → const shared_ptr& 또는 원시 참조로 넘기세요

MOD 03

이동 시맨틱 — 복사하지 않고 옮기기

100MB 짜리 벡터를 함수에서 돌려줄 때 복사가 일어나지 않는 이유입니다. 개념은 하나 — “어차피 사라질 것이라면 내용을 훔쳐 오면 된다.”

함수에서 큰 객체를 그냥 return 하면 컴파일러가 알아서 이동하거나 아예 생략합니다 — std::move 를 붙이지 마세요.

복사와 이동의 차이

std::vector<int> a(1'000'000);

// 복사 — 100만 개를 새 메모리에 전부 옮겨 적습니다 (느림)
std::vector<int> b = a;              // a 는 그대로 살아 있습니다

// 이동 — 내부 포인터만 넘겨받습니다 (거의 공짜) ★
std::vector<int> c = std::move(a);   // a 는 '비어 있지만 유효한' 상태가 됩니다
a.size();                            // 0 (읽어도 UB 는 아닙니다)
a.push_back(1);                      // 다시 써도 됩니다

// vector 내부를 그림으로 보면
//   복사: [ptr|size|cap] → 새 버퍼를 잡고 100만 개 memcpy
//   이동: [ptr|size|cap] 세 값만 옮기고 원본은 nullptr 로  ★ 8바이트 3개

// std::move 는 '옮기는 함수'가 아닙니다 ★
//   그냥 "이건 훔쳐 가도 된다"고 표시하는 캐스트일 뿐입니다.
//   실제 이동은 이동 생성자·이동 대입이 합니다.
이동 후의 객체는 “유효하지만 값이 정해지지 않은 상태”입니다. size()·clear()·재대입은 안전하지만, 내용이 무엇인지 가정하면 안 됩니다. 표준 컨테이너는 대개 비어 있게 되지만 표준이 보장하는 것은 아닙니다.

언제 자동으로 이동되나

// ① 임시 객체(rvalue)를 대입할 때 — 자동으로 이동

v = make_vector();                       // 이동 대입

std::vector<int> f() {
    std::vector<int> local(1000);
    return local;                        // ✅ 이동 (사실 대개 RVO 로 복사·이동 둘 다 생략)
    // return std::move(local);          // ❌ 오히려 RVO 를 막습니다
}

//   → 이동시킬 값에 const 를 붙이지 마세요

이렇게도 쓸 수 있다 — 직접 구현하기 🟡 중급

이동 생성자·이동 대입

class Buffer {
    std::size_t n_ = 0;
    double*     p_ = nullptr;
public:
    explicit Buffer(std::size_t n) : n_(n), p_(new double[n]{}) {}
    ~Buffer() { delete[] p_; }

    // 복사 — 새로 할당하고 내용을 옮겨 적습니다
    Buffer(const Buffer& o) : n_(o.n_), p_(new double[o.n_]) {
        std::copy_n(o.p_, n_, p_);
    }

    // 이동 — 포인터를 훔치고 원본을 비웁니다 ★ noexcept 필수
    Buffer(Buffer&& o) noexcept
        : n_(std::exchange(o.n_, 0)),
          p_(std::exchange(o.p_, nullptr)) {}

    // 이동 대입 — 내 것을 버리고 훔쳐 옵니다
    Buffer& operator=(Buffer&& o) noexcept {
        if (this != &o) {                    // ★ 자기 대입 방어
            delete[] p_;
            n_ = std::exchange(o.n_, 0);
            p_ = std::exchange(o.p_, nullptr);
        }
        return *this;
    }
    Buffer& operator=(const Buffer& o) {      // copy and swap 관용구
        Buffer tmp(o);
        std::swap(n_, tmp.n_);
        std::swap(p_, tmp.p_);
        return *this;
    }
};
사실 이 클래스는 만들 필요가 없습니다 — std::vector<double> 를 멤버로 두면 여섯 개 특수 멤버가 전부 공짜로 올바르게 만들어집니다(0의 법칙). 직접 구현은 진짜로 원시 자원을 감쌀 때만 하세요.

lvalue · rvalue · xvalue

C++ 의 모든 식은 값 카테고리를 가집니다

            expression
            /        \
        glvalue      rvalue
        /     \      /     \
    lvalue    xvalue      prvalue

  lvalue  : 이름이 있고 주소를 얻을 수 있음      int x;  x
  prvalue : 순수한 임시값                        42,  f()
  xvalue  : 곧 사라질 것 (eXpiring)              std::move(x)
  rvalue  : prvalue + xvalue → '훔쳐 가도 되는 것'

  T&   (lvalue 참조)  : lvalue 에만 바인딩
  const T&            : 둘 다 바인딩 (그래서 예전엔 이것만 썼습니다)
  T&&  (rvalue 참조)  : rvalue 에만 바인딩 → 이동의 근거 ★

  ★ 핵심 혼동: 'T&& 인 변수 자체는 lvalue 입니다'
    void f(Widget&& w) { g(w); }              // 복사됩니다!
    void f(Widget&& w) { g(std::move(w)); }   // ✅ 이동
    (이름이 있으면 lvalue — 예외 없는 규칙입니다)

template<class T>
void wrapper(T&& arg) {                 // T 가 추론될 때만 전달 참조
    inner(std::forward<T>(arg));        // lvalue 면 lvalue 로, rvalue 면 rvalue 로
}
//   forward 는 '조건부 move' 입니다 — 원래 카테고리를 복원합니다

// 참조 접힘 규칙 (왜 이게 되는지)
//   T = Widget&   → Widget& &&  → Widget&    (lvalue 를 넘긴 경우)
//   T = Widget    → Widget&&               (rvalue 를 넘긴 경우)

// 실제 쓰임 — make_unique 의 구현이 이것입니다
template<class T, class... Args>
std::unique_ptr<T> make_unique(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}

const 와 constexpr

const 는 “안 바꾸겠다는 약속”, constexpr 은 “실행 전에 미리 계산해 두기”입니다. 둘 다 비용 없이 안전과 속도를 얻는 도구입니다.

const 정확성

class Report {
    std::vector<double> data_;
    mutable std::optional<double> cache_;   // ★ const 함수에서도 바꿀 수 있음
public:
    // 읽기만 하는 함수에는 반드시 const
    std::size_t size() const noexcept { return data_.size(); }

    double mean() const {                   // const 함수인데 캐시는 갱신
        if (!cache_) cache_ = compute();
        return *cache_;
    }

    // const 버전과 비const 버전을 함께 제공하는 관용구
    double&       at(std::size_t i)       { return data_[i]; }
    const double& at(std::size_t i) const { return data_[i]; }
};

const Report r = load();
r.size();      // ✅ const 함수만 부를 수 있습니다

  + 좌·우·부모 포인터 24바이트
  + 색상(레드블랙) + 패딩 8바이트
  + 할당자 오버헤드 ~16바이트
  = 원소당 약 56바이트 ★ 데이터의 7배

std::unordered_map<int,int>
  노드 (키+값+next 포인터) + 버킷 배열
  = 원소당 약 40~50바이트

std::vector<std::pair<int,int>>
  = 원소당 8바이트 (+ 여유 용량) ★

→ 100만 개면 56MB vs 8MB.
  게다가 map 은 원소가 메모리에 흩어져 있어
  순회할 때마다 캐시 미스가 납니다.

★ 그래서 실무 결론:
  '정렬된 vector + binary_search' 가
  map 보다 빠른 경우가 매우 흔합니다 (읽기 위주라면 거의 항상).

        std::shared_lock lk(mx_);      // 여러 스레드가 동시에 읽기 ★
        return data_[i];
    }
    void set(int i, double v) {
        std::unique_lock lk(mx_);      // 쓸 때만 배타적
        data_[i] = v;
    }
};

왜 순서가 뒤바뀌나

// 컴파일러와 CPU 는 성능을 위해 명령 순서를 바꿉니다.
// 단일 스레드에서는 결과가 같지만, 다른 스레드가 보는 순서는 다를 수 있습니다.

// ❌ 고전적인 실패
bool ready = false;
int  data  = 0;
// 스레드 A
data = 42;
ready = true;          // ★ 컴파일러가 이 둘의 순서를 바꿀 수 있습니다
// 스레드 B
if (ready) use(data);  // data 가 아직 0일 수 있습니다

// ✅ atomic 으로 순서를 강제
std::atomic<bool> ready{false};
int data = 0;
// A
data = 42;
ready.store(true, std::memory_order_release);    // 앞의 쓰기를 모두 공개
// B
if (ready.load(std::memory_order_acquire))       // 그 이후를 모두 관찰
    use(data);                                    // ✅ 42 가 보장됩니다

// memory_order 요약
//   seq_cst  기본값 · 가장 안전 · 가장 느림 (전역 순서)
//   acquire/release  생산자-소비자 쌍 ★ 실무에서 쓰는 대부분
//   relaxed  순서 보장 없음 · 카운터처럼 값만 정확하면 될 때
//   → 확신이 없으면 기본값(seq_cst)을 쓰세요. 대개 충분히 빠릅니다.
