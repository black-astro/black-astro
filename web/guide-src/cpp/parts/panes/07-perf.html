PERF 01

측정 먼저 — 벤치마크를 신뢰할 수 있게

“빨라진 것 같다”는 증거가 아닙니다. 제대로 재는 법부터 잡지 않으면 나머지 아홉 섹션은 의미가 없습니다.

최적화의 순서 ★

이 순서를 지키면 대부분 ①②에서 끝납니다

  ① 알고리즘 · 자료구조     O(n²) → O(n)        수십~수백 배
  ② I/O · 쿼리 횟수         N+1 제거 · 배치      수십 배
  ③ 메모리 접근 패턴        캐시 친화적 배치     2~10배   ★ C++ 의 영역
  ④ 복사 · 할당 제거        이동 · reserve       1.5~3배
  ⑤ 벡터화 · 병렬           SIMD · 멀티스레드    2~수십 배
  ⑥ 마이크로 최적화         분기 · 인라인        수 %

★ ③부터가 C++ 를 쓰는 진짜 이유입니다.
  ①②는 파이썬에서도 할 수 있고, 거기서 못 얻은 이득을
  C++ 로 옮긴다고 얻어지지 않습니다.

⚠ 순서를 건너뛰면
  · O(n²) 알고리즘을 SIMD 로 최적화 → 여전히 O(n²)
  · 쿼리가 1만 번인데 루프를 튜닝 → 아무 변화 없음

제대로 재기

#include <chrono>

// ★ 최소한의 규칙
//   ① Release 빌드로 (b04)
//   ② steady_clock 이나 perf_counter 를 쓸 것 (system_clock ❌)
//   ③ 여러 번 재고 '최솟값'을 볼 것 (평균은 노이즈에 흔들립니다)
//   ④ 결과를 실제로 쓸 것 (안 쓰면 컴파일러가 통째로 지웁니다) ★

template<class F>
double bench_ms(F&& f, int reps = 10) {
    double best = 1e300;
    for (int i = 0; i < reps; ++i) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        auto t1 = std::chrono::steady_clock::now();
        best = std::min(best,
            std::chrono::duration<double, std::milli>(t1 - t0).count());
    }
    return best;
}

// 컴파일러가 코드를 지우지 못하게 (최적화 방지 장벽)
template<class T>
inline void do_not_optimize(T const& v) {
    asm volatile("" : : "r,m"(v) : "memory");
}
//   또는 benchmark::DoNotOptimize (Google Benchmark)

// 사용
auto t = bench_ms([&]{ auto r = compute(data); do_not_optimize(r); });
가장 흔한 벤치마크 실수 — 결과를 안 써서 컴파일러가 계산 자체를 삭제한 것을 “0.001ms 로 빨라졌다”고 보고하는 것입니다. 결과가 비현실적으로 빠르면 먼저 이것을 의심하세요.

static void BM_Smooth(benchmark::State& state) {
    const std::size_t n = state.range(0);
    std::vector<double> in(n, 1.0), out(n);

    for (auto _ : state) {                    // ★ 이 루프가 자동 반복
        core::smooth(in.data(), n, out.data(), 3);
        benchmark::DoNotOptimize(out.data());
        benchmark::ClobberMemory();

    state.SetItemsProcessed(state.iterations() * n);
    state.SetBytesProcessed(state.iterations() * n * sizeof(double));
}

숫자를 해석하기

perf stat 결과 읽는 법

  IPC (instructions per cycle)
    > 2.0  : 좋음 — CPU 를 잘 쓰고 있습니다
    < 1.0  : 뭔가 기다리고 있습니다 (메모리·분기) ★
    < 0.5  : 심각 — 캐시 미스나 의존성 사슬을 의심

  cache-misses / cache-references
    > 10%  : 메모리 레이아웃 문제 (e02)

  branch-misses / branches
    > 5%   : 예측 불가능한 분기 (e05)

  page-faults 가 많다
    → 할당이 잦거나 메모리가 부족

★ 프로파일 1위가 memcpy · operator new 면 → e03·e04
  1위가 read · recv · execute 면 → I/O 문제 (C++ 최적화 무의미)
  1위가 내 계산 함수인데 IPC 가 낮으면 → e02 (캐시)
  IPC 도 높은데 느리면 → 알고리즘 자체 (①로 돌아가기)
프로파일 결과의 맨 위가 대개 내 코드가 아닙니다 — memcpy·operator new·__memmove_avx 같은 것이 1위라면 복사와 할당이 진짜 문제입니다(e03·e04). 그 자리를 “라이브러리가 느리다”고 해석하면 안 됩니다.

PERF 02

메모리 레이아웃과 캐시

같은 알고리즘도 데이터가 어떻게 놓여 있느냐에 따라 수 배가 갈립니다. C++ 를 쓰는 진짜 이유가 여기 있습니다.

"알고리즘 복잡도는 같은데 왜 10배 차이가 나지"의 답은 거의 항상 이 그림입니다.

메모리는 계층입니다

대략적인 지연 시간 (현대 x86 · 사이클)

  레지스터        0
  L1 캐시         ~4      (32~48KB)
  L2 캐시         ~14     (512KB~2MB)
  L3 캐시         ~40     (8~32MB, 코어 공유)
  메인 메모리     ~200    ★ L1 의 50배
  SSD             ~100,000
  네트워크        ~수백만

핵심
  · CPU 는 메모리에서 '64바이트 단위(캐시 라인)'로 가져옵니다
  · double 하나(8바이트)를 읽어도 64바이트가 올라옵니다
  · 그래서 '연속으로 붙어 있으면' 공짜로 따라옵니다 ★
  · 흩어져 있으면 매번 200 사이클을 기다립니다

→ 200 사이클이면 덧셈 수십 개를 할 수 있습니다.
  즉 대부분의 프로그램은 '계산이 느린' 게 아니라 '기다리는' 중입니다.

눈으로 보이는 차이

// ① 순차 접근 vs 무작위 접근
std::vector<int> v(64 * 1024 * 1024);      // 256MB

for (std::size_t i = 0; i < v.size(); ++i) sum += v[i];        // 순차
for (std::size_t i : random_indices)        sum += v[i];        // 무작위
//   같은 횟수인데 무작위가 5~20배 느립니다 ★

// ② 2차원 배열 순회 순서
double m[N][N];
for (int i = 0; i < N; ++i)
    for (int j = 0; j < N; ++j) sum += m[i][j];   // ✅ 행 우선 (연속)
for (int j = 0; j < N; ++j)
    for (int i = 0; i < N; ++i) sum += m[i][j];   // ❌ 열 우선 (건너뜀)
//   N=2048 이면 5~10배 차이 — 코드는 두 글자만 다릅니다 ★

// ③ 포인터 추적 (연결 리스트가 느린 이유)
for (Node* p = head; p; p = p->next) sum += p->value;
//   매 노드마다 캐시 미스 가능 → vector 대비 10배 이상 느릴 수 있습니다
//   (탭 2 m05 에서 "list 는 거의 답이 아니다"라고 한 이유)
numpy 가 빠른 이유도 같습니다 — 파이썬 list 는 포인터 배열이라 값이 흩어져 있고, numpy 배열은 연속된 숫자 블록입니다. C++ 로 옮겨도 vector<shared_ptr<T>> 를 쓰면 같은 문제가 생깁니다.

이렇게도 쓸 수 있다 — AoS 와 SoA 🟡 중급

구조체 배열 vs 배열 구조체 ★

// AoS (Array of Structs) — 직관적이지만 일부 필드만 쓸 때 손해
struct Particle { float x, y, z, vx, vy, vz; float mass; bool alive; };
std::vector<Particle> ps(1'000'000);        // 32바이트 × 100만

for (auto& p : ps) p.x += p.vx;             // x, vx 만 쓰는데
//   캐시 라인 64바이트에 Particle 2개 → 필요한 건 8바이트, 나머지는 낭비 ★

// SoA (Struct of Arrays) — 쓰는 것만 연속으로
struct Particles {
    std::vector<float> x, y, z, vx, vy, vz, mass;
    std::vector<uint8_t> alive;
};
Particles ps;

for (std::size_t i = 0; i < n; ++i) ps.x[i] += ps.vx[i];
//   ✅ x 와 vx 만 캐시에 올라옵니다 → 미스가 크게 줄고
//   ✅ 벡터화도 훨씬 잘 됩니다 (e06)
//   보통 2~5배, 많으면 10배까지 차이 납니다

// ⚠ 대신 '한 입자의 모든 필드'를 쓰는 코드는 AoS 가 낫습니다
//   → 접근 패턴을 보고 정하세요
파이썬 모듈을 만들 때 자연스럽게 SoA 가 됩니다 — numpy 배열을 열 단위로 받으면(xs, ys, zs) 그것이 곧 SoA 입니다(🐍 y01 · 🟨 j04). JS 객체 배열을 그대로 넘기는 것보다 훨씬 빠른 이유이기도 합니다.

실무에선 이렇게 — 접근 패턴 설계 🔴 실무

블로킹 — 캐시에 맞게 쪼개기

// 행렬 곱 — 고전적인 예
// ❌ 단순 구현 — B 를 열 방향으로 읽어 캐시 미스가 많습니다
for (int i = 0; i < N; ++i)
  for (int j = 0; j < N; ++j) {
    double s = 0;
    for (int k = 0; k < N; ++k) s += A[i][k] * B[k][j];
    C[i][j] = s;
  }

// ✅ 타일링 — 캐시에 들어가는 블록 단위로
constexpr int T = 64;                       // L1 에 맞게 조정
for (int ii = 0; ii < N; ii += T)
 for (int jj = 0; jj < N; jj += T)
  for (int kk = 0; kk < N; kk += T)
   for (int i = ii; i < std::min(ii+T, N); ++i)
    for (int j = jj; j < std::min(jj+T, N); ++j) {
      double s = C[i][j];
      for (int k = kk; k < std::min(kk+T, N); ++k) s += A[i][k] * B[k][j];
      C[i][j] = s;
    }
//   N=1024 에서 3~5배 빨라집니다 ★

// ⚠ 실무에서는 직접 짜지 말고 BLAS 를 쓰세요

TLB 와 huge page

가상 주소 → 물리 주소 변환도 캐시됩니다 (TLB)

  · 기본 페이지 4KB · TLB 엔트리 수백~수천 개
  · 즉 TLB 로 커버되는 메모리는 수 MB 수준 ★
  · 그보다 큰 데이터를 무작위로 접근하면 TLB 미스가 추가로 발생
    (캐시 미스와 별개로 페이지 테이블을 걸어야 함)

할당 줄이기 — reserve · 재사용 · 풀

메모리를 새로 얻는 일은 비쌉니다. 게다가 시간이 일정하지 않아 p99 지연을 망칩니다. 미리 잡아 두고 재사용하는 것이 답입니다.

할당 비용은 얼마나

대략적인 감각 (glibc malloc 기준)

  스택 할당            ~0 사이클   (포인터만 이동)
  작은 힙 할당 (캐시됨) ~20~50 사이클
  큰 힙 할당           ~100~수천 사이클
  새 페이지가 필요할 때  수 μs      ★ 커널 진입 (mmap)

★ 문제는 평균이 아니라 '가끔 아주 느린 것' 입니다
  · 페이지 폴트 · 아레나 확장 · 락 경합(멀티스레드)
  · p50 은 1μs 인데 p99 가 500μs 인 경우가 흔합니다

그리고 할당은 캐시도 망칩니다
  · 새 메모리는 캐시에 없습니다 (콜드)

객체 풀

// 같은 타입을 자주 만들고 버린다면 — 재사용 풀
template<class T>
class Pool {
    std::vector<std::unique_ptr<T>> free_;
public:
    struct Deleter {
        Pool* p;
        void operator()(T* t) const {
            t->reset();                       // 상태 초기화
            p->free_.emplace_back(t);         // 풀로 반납 ★
        }
    };
    using Handle = std::unique_ptr<T, Deleter>;

    Handle acquire() {
        if (free_.empty()) return Handle{new T{}, Deleter{this}};
        auto* t = free_.back().release();
        free_.pop_back();
        return Handle{t, Deleter{this}};
    }
};

Pool<Buffer> pool;
{
    auto b = pool.acquire();      // 할당 없이 재사용
    use(*b);
}                                  // 자동으로 반납 (RAII)

PERF 04

복사 제거 — 값 vs 참조

자기도 모르게 큰 객체를 복사하고 있는 자리를 찾아 없앱니다. 코드는 그대로인데 수 배가 빨라지는 경우가 흔합니다.

복사가 숨어 있는 다섯 자리 ★

// ① 범위 for 에서 & 누락 — 가장 흔합니다
for (auto s : names)          // ❌ 문자열마다 복사
for (const auto& s : names)   // ✅

// ② 함수 인자를 값으로
void f(std::vector<int> v);        // ❌ 통째로 복사
void f(const std::vector<int>& v); // ✅ (탭 1 x03)

// ③ map 순회에서 타입을 잘못 적기
std::map<std::string, Big> m;
for (const std::pair<std::string, Big>& p : m)   // ❌ 실제 타입은
                                                  //   pair<const string, Big>
                                                  //   → 변환 복사 발생
for (const auto& p : m)                           // ✅

// ④ auto 가 참조를 떼어 버림 (탭 1 x02)
auto v = obj.data();          // ❌ 복사
const auto& v = obj.data();   // ✅

// ⑤ 반환값을 참조에 안 받기 · 임시를 여러 번 만들기
std::string s = a + "-" + b + "-" + c;   // 중간 임시 여러 개
std::string s = std::format("{}-{}-{}", a, b, c);   // ✅ (탭 2 m11)

RVO 는 언제 보장되나

// 이름 있는 지역 변수(NRVO)는 '허용'이지 '의무'가 아닙니다
std::vector<int> make2() {
    std::vector<int> v(1000);
    return v;        // 대개 생략되지만 표준이 강제하지 않습니다
}

// NRVO 가 안 되는 경우
std::vector<int> f(bool c) {

}
std::vector<int> g(std::vector<int> param) {
    return param;          // ❌ 매개변수는 NRVO 대상이 아님 → 이동

반환값이 실제로 어떻게 전달되나

ABI 규칙 (x86-64 System V)

  · 작고 trivially copyable 한 타입 → 레지스터로 반환 (공짜)
      struct P { double x, y; };        // XMM0, XMM1
  · 크거나 non-trivial 한 타입 → 호출자가 공간을 잡고
    그 주소를 숨은 첫 인자로 전달 (RVO 의 실체) ★
      std::vector<int>                   // 호출자 스택에 직접 구성

  → 그래서 "큰 객체 반환은 느리다"는 옛말입니다.
    C++17 이후로는 반환이 대개 공짜입니다.

trivially copyable 여부가 갈림길
  static_assert(std::is_trivially_copyable_v<P>);
  · memcpy 로 옮길 수 있는 타입 → 레지스터·memcpy 최적화 가능
  · 소멸자나 복사 생성자를 직접 쓰면 이 성질이 깨집니다 ★

확인
  g++ -O2 -S -masm=intel -o - test.cpp | grep -A20 "make"
  godbolt.org 에서 반환 방식 비교
실무 함의 — 값으로 반환하는 것을 두려워하지 마세요. C++17 이후로는 대개 비용이 없습니다. 오히려 출력 인자(void f(T& out))가 코드를 읽기 어렵게 만드는 대가만 치르는 경우가 많습니다 (버퍼 재사용이 목적일 때는 예외 — e03).
정리 — 복사는 다섯 자리에 숨어 있습니다 — 범위 for 의 & 누락, 값 인자, map 순회 타입, auto, 문자열 조립. clang-tidy performance-* 가 전부 자동으로 잡아 줍니다. 그리고 값 반환은 이제 공짜이니 두려워하지 마세요.
PERF 05

분기 예측과 브랜치리스

if 하나가 예측을 빗나가면 15~20 사이클이 날아갑니다. 예측 불가능한 분기가 루프 안에 있으면 그것이 병목이 됩니다.

여기까지 신경 쓸 코드는 정말 뜨거운 루프뿐입니다 — 나머지는 가독성이 이깁니다.

왜 비싼가

현대 CPU 는 파이프라인이 깊습니다 (15~20 단계)

  · 분기를 만나면 결과를 기다리지 않고 '예측'해서 계속 실행합니다
  · 맞으면 손해 없음 (예측 정확도는 보통 95% 이상)
  · 틀리면 파이프라인을 비우고 다시 시작 → 15~20 사이클 손실 ★

예측이 잘 되는 것
  · 항상 참/거짓인 조건
  · 규칙적인 패턴 (참참거참참거…)
  · 루프 종료 조건 (마지막 한 번만 틀림)

예측이 안 되는 것
  · 무작위 데이터에 의존하는 조건 ★
  · 가상 함수 호출 대상이 매번 바뀔 때

유명한 실험
  정렬된 배열에 if (v[i] > 128) 를 도는 것이
  정렬 안 된 배열보다 3~6배 빠릅니다.
  같은 코드, 같은 데이터 개수인데 '순서'만 다릅니다 ★

perf stat -e branches,branch-misses ./app

  · 2비트 포화 카운터 — 최근 결과를 기억 (강한참·약한참·약한거짓·강한거짓)
  · 전역 이력 레지스터 — 최근 N개 분기의 패턴
  · TAGE 등 하이브리드 — 여러 길이의 이력을 조합해 예측
  · 간접 분기 예측기 (BTB) — 가상 호출·함수 포인터 대상

그래서
  · 규칙적인 패턴(ABABAB)은 잘 예측합니다 ★
  · 무작위는 원리상 50% 밖에 못 맞춥니다
  · 분기가 아주 많으면 예측기 자원이 부족해집니다 (aliasing)
  · 함수가 커지면 명령 캐시(L1i)와 BTB 압박이 생깁니다
    → 인라인을 무조건 늘리는 것이 답이 아닌 이유 ★

Spectre 이후
  · 투기 실행 완화 옵션이 간접 분기 비용을 크게 올렸습니다
    (retpoline 등) → 가상 호출이 예전보다 비싸졌습니다
  · -mindirect-branch=thunk 같은 옵션의 영향을 재 보세요

PERF 06

SIMD — 한 번에 여러 개

CPU 는 double 4~8개를 한 명령으로 계산할 수 있습니다. 먼저 컴파일러가 자동으로 하게 유도하고, 그래도 안 되면 직접 씁니다.

자동 벡터화를 막는 것은 대개 포인터가 겹칠 수 있다는 가능성입니다 — 그래서 __restrict 가 효과를 냅니다.

자동 벡터화가 먼저입니다

// 이런 루프는 컴파일러가 알아서 벡터화합니다
void add(double* __restrict out,
         const double* __restrict a,
         const double* __restrict b, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i)
        out[i] = a[i] + b[i];
}
//   -O3 로 컴파일하면 addpd(SSE) · vaddpd(AVX) 명령이 나옵니다
//   → 한 번에 2~8개씩 처리 ★

// ★ __restrict 가 핵심입니다
//   없으면 out 과 a 가 겹칠 수 있다고 가정해 벡터화를 포기합니다 (탭 1 x04)
//   표준은 아니지만 gcc·clang·msvc 모두 지원합니다

// 확인
// g++ -O3 -fopt-info-vec-optimized add.cpp
//   add.cpp:5:24: optimized: loop vectorized using 32 byte vectors ★
// clang++ -O3 -Rpass=loop-vectorize add.cpp
순서를 지키세요 — ① 자동 벡터화가 되게 코드를 정리, ② 컴파일러 리포트로 확인, ③ 그래도 안 되면 인트린식. 바로 인트린식으로 가면 이식성과 유지보수를 잃고 컴파일러가 더 잘하는 경우도 많습니다.

인트린식

#include <immintrin.h>

// AVX2 — double 4개씩
void add_avx2(double* out, const double* a, const double* b, std::size_t n) {
    std::size_t i = 0;
    for (; i + 4 <= n; i += 4) {
        __m256d va = _mm256_loadu_pd(a + i);      // 4개 로드
        __m256d vb = _mm256_loadu_pd(b + i);
        __m256d vs = _mm256_add_pd(va, vb);       // 4개 동시 덧셈 ★
        _mm256_storeu_pd(out + i, vs);
    }
    for (; i < n; ++i) out[i] = a[i] + b[i];      // 꼬리 처리
}

// 수평 합 (reduction)
double sum_avx2(const double* a, std::size_t n) {
    __m256d acc = _mm256_setzero_pd();
    std::size_t i = 0;
    for (; i + 4 <= n; i += 4)
        acc = _mm256_add_pd(acc, _mm256_loadu_pd(a + i));
    alignas(32) double tmp[4];
    _mm256_store_pd(tmp, acc);
    double s = tmp[0] + tmp[1] + tmp[2] + tmp[3];
    for (; i < n; ++i) s += a[i];
    return s;
}
//   ⚠ 합산 순서가 달라져 결과가 미세하게 다를 수 있습니다

// ① std::experimental::simd (C++26 표준화 예정)
#include <experimental/simd>
namespace stdx = std::experimental;

void add(double* out, const double* a, const double* b, std::size_t n) {
    using V = stdx::native_simd<double>;       // 플랫폼에 맞는 폭
    std::size_t i = 0;
    for (; i + V::size() <= n; i += V::size()) {
        V va(a + i, stdx::element_aligned);
        V vb(b + i, stdx::element_aligned);
        (va + vb).copy_to(out + i, stdx::element_aligned);
    }
    for (; i < n; ++i) out[i] = a[i] + b[i];
}
//   x86 · ARM 어디서나 같은 코드 ★

PERF 07

병렬 — 여러 코어를 실제로

파이썬 혼자서는 불가능한 지점입니다. 다만 코어를 8개 써도 8배가 되지는 않습니다 — 왜 그런지가 이 섹션의 핵심입니다.

가장 쉬운 방법부터

// ① 표준 병렬 알고리즘 (탭 2 m06) — 스레드를 직접 안 만듭니다 ★
#include <execution>
std::sort(std::execution::par, v.begin(), v.end());
std::transform(std::execution::par_unseq,
               a.begin(), a.end(), out.begin(), f);
double s = std::reduce(std::execution::par, v.begin(), v.end());
//   GCC 는 TBB 링크 필요: target_link_libraries(app PRIVATE TBB::tbb)

// ② OpenMP — 지시문 한 줄
#pragma omp parallel for schedule(static) reduction(+:total)
for (std::ptrdiff_t i = 0; i < n; ++i)
    total += heavy(data[i]);

// 작업량이 불균등하면
#pragma omp parallel for schedule(dynamic, 64)

// ③ 직접 청크 나누기 — 의존성이 없을 때 가장 단순합니다
const unsigned T = std::thread::hardware_concurrency();
std::vector<std::jthread> ths;
for (unsigned k = 0; k < T; ++k)
    ths.emplace_back([&, k] {
        const std::size_t lo = n * k / T, hi = n * (k+1) / T;
        for (std::size_t i = lo; i < hi; ++i) out[i] = f(in[i]);
    });
//   jthread 는 소멸자에서 join 합니다 (C++20)

왜 코어 수만큼 안 빨라지나 ★

8스레드인데 3배밖에 안 나오는 흔한 이유

  ① 메모리 대역폭 한계 ★ 가장 흔함
     단순 배열 연산은 CPU 가 아니라 '메모리에서 읽는 속도'가 한계입니다.
     코어를 늘려도 대역폭은 그대로라 4~5코어에서 평평해집니다.
     → 원소당 계산량을 늘리거나 캐시에 맞게 쪼개세요 (e02)

  ② false sharing — 다음 섹션(e08)

  ③ 작업 분배 불균등
     원소마다 계산량이 다르면 한 스레드만 오래 돕니다.
     → schedule(dynamic) · 작업 큐

  ④ 하이퍼스레딩
     논리 16코어여도 물리는 8개인 경우가 많습니다.

  ⑤ 동기화·할당 경합
     공유 뮤텍스 · malloc 아레나 락 (e03)

  ⑥ 암달의 법칙
     10%가 순차라면 아무리 코어를 늘려도 최대 10배입니다.

측정
  htop 으로 코어 사용률 확인 (전부 100% 인지)
  perf stat -e cache-misses,LLC-load-misses ./app

이렇게도 쓸 수 있다 — 잘 나누는 법 🟡 중급

공유를 없애는 것이 최선

// ❌ 공유 결과 + 락 — 스레드를 늘려도 안 빨라집니다
std::mutex m; std::vector<double> results;
parallel_for(n, [&](std::size_t i) {
    auto r = compute(i);
    std::lock_guard lk(m);
    results.push_back(r);        // ★ 전부 여기서 줄을 섭니다
});

// ✅ ① 자리를 미리 잡고 각자 자기 칸에
std::vector<double> results(n);
parallel_for(n, [&](std::size_t i) { results[i] = compute(i); });

// ✅ ② 스레드별로 모았다가 마지막에 합치기 ★
std::vector<std::vector<double>> per_thread(T);
parallel_chunks(T, [&](unsigned t, std::size_t lo, std::size_t hi) {
    auto& local = per_thread[t];
    local.reserve(hi - lo);
    for (std::size_t i = lo; i < hi; ++i)
        if (keep(i)) local.push_back(compute(i));

PERF 08

false sharing 과 원자 연산 비용

스레드를 늘렸는데 오히려 느려지는 대표적 원인입니다. 서로 다른 변수를 쓰는데도 같은 캐시 라인에 있으면 충돌합니다.

무슨 일이 일어나나

// ❌ 스레드마다 다른 인덱스에 쓰는데도 느립니다
struct Counters { std::int64_t c[8]; };      // 64바이트 = 캐시 라인 하나 ★
Counters counters;

// 스레드 k 가 counters.c[k] 만 건드립니다 — 겹치지 않는데도
for (...) counters.c[k]++;
//   ★ 8개가 전부 같은 캐시 라인에 있어
//     한 스레드가 쓸 때마다 다른 코어의 캐시가 무효화됩니다
//     → 매번 캐시 라인을 주고받으며 수십~수백 사이클 낭비
//     8스레드가 1스레드보다 느려지기도 합니다

// ✅ 방법 ① 캐시 라인만큼 떼어 놓기
struct alignas(64) PaddedCounter {
    std::int64_t v = 0;
};
std::vector<PaddedCounter> counters(T);      // 각자 다른 라인 ★

// C++17 표준 상수
#include <new>
alignas(std::hardware_destructive_interference_size) std::int64_t v;

// ✅ 방법 ② 지역 변수에 누적하고 마지막에 한 번만 (더 좋습니다) ★
std::int64_t local = 0;
for (...) local++;                           // 레지스터에서 돕니다
counters[k].v = local;                       // 끝나고 한 번

// ✅ 지역 누적 + 최종 합산
parallel_chunks(T, [&](unsigned t, auto lo, auto hi) {
    std::int64_t local = 0;
    for (auto i = lo; i < hi; ++i) local += data[i];
    total.fetch_add(local, std::memory_order_relaxed);   // 스레드당 1회 ★
});

// 샤딩 예 — 락 하나를 16개로
struct ShardedMap {
    static constexpr int N = 16;
    struct alignas(64) Shard {            // ★ 패딩 필수
        std::mutex m;
        std::unordered_map<Key, Val> data;
    };
    std::array<Shard, N> shards;

    Val get(const Key& k) {
        auto& s = shards[std::hash<Key>{}(k) % N];
        std::lock_guard lk(s.m);
        return s.data.at(k);
    }
};

한 단계 더 — 캐시 일관성 프로토콜 🧬 전문가

MESI — 왜 그렇게 비싼가

각 캐시 라인은 상태를 가집니다 (MESI)

  M (Modified)  : 내가 수정했고 나만 가짐
  E (Exclusive) : 나만 가짐 (수정 안 함)
  S (Shared)    : 여럿이 가짐 (읽기 전용)
  I (Invalid)   : 무효

쓰기가 일어나면
  ① 다른 코어에 "무효화(invalidate)" 메시지를 보냅니다
  ② 그 코어들이 응답할 때까지 기다립니다
  ③ 내 캐시를 M 으로 바꾸고 씁니다

★ 두 코어가 번갈아 같은 라인에 쓰면
  라인이 코어 사이를 계속 오갑니다 (cache line ping-pong)
  → 각 쓰기가 100~300 사이클로 늘어납니다

false sharing 이 치명적인 이유가 이것입니다.
논리적으로 무관한 변수인데 물리적으로 같은 라인이면
하드웨어는 구분하지 못합니다.

// ③ 읽기 전용으로 만들기 — S 상태는 여럿이 가져도 무료 ★
const std::vector<double> table = build();     // 만들고 안 바꿈
//   여러 스레드가 동시에 읽어도 아무 비용이 없습니다

// ④ 인접한 인덱스를 다른 스레드에 주지 않기
//    ❌ 스레드 k 가 i % T == k 인 원소를 처리 (인터리브)
//    ✅ 스레드 k 가 [n*k/T, n*(k+1)/T) 를 처리 (블록) ★

// ⑤ 원자 변수를 배열로 둘 때
std::vector<std::atomic<int>> counters(T);      // ❌ 붙어 있음
struct alignas(64) AtomicCounter { std::atomic<int> v{0}; };
std::vector<AtomicCounter> counters(T);          // ✅
읽기 전용 데이터는 공유해도 공짜입니다 — 여러 코어가 S 상태로 각자 캐시에 갖고 있으면 됩니다. “쓰기만 분리하면 된다”는 것이 이 섹션의 결론입니다.
정리 — 스레드를 늘렸는데 느려지면 false sharing 을 의심하세요. 서로 다른 변수라도 같은 64바이트 라인에 있으면 충돌합니다. 해법은 지역 변수에 누적하고 마지막에 한 번만 합치기, 그래도 공유해야 하면 alignas(64) 패딩입니다.
"코어를 늘렸는데 그대로다" 의 흔한 정체가 거짓 공유입니다.

import numpy as np, timeit, fastmod

def compare(n):
    a = np.random.rand(n)
    L = a.tolist()

    # ① 순수 파이썬
    def py():
        out = [0.0] * len(L)
        for i in range(1, len(L)-1):
            out[i] = (L[i-1] + L[i] + L[i+1]) / 3
        return out

    # ② numpy 벡터화
    def np_():
        return np.convolve(a, np.ones(3)/3, mode="same")

    # ③ C++ 확장
    def cpp():
        return fastmod.smooth(a, 3)

    for name, f in (("python", py), ("numpy", np_), ("cpp", cpp)):
        t = min(timeit.repeat(f, number=1, repeat=5))
        print(f"{name:8} {t*1e3:9.3f}ms")

for n in (1_000, 100_000, 10_000_000):
    print(f"\n=== n={n:,}")
    compare(n)
세 가지를 다 재세요 — 순수 파이썬만 비교하면 부풀려진 배수가 나옵니다. 의사결정에 필요한 것은 “지금 쓰는 방법(대개 numpy) 대비 몇 배인가” 입니다.
