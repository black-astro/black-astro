C++ 를 실행하는 법 — 컴파일이 전부의 시작

파이썬은 파일을 그냥 실행합니다. C++ 는 기계어로 번역한 뒤 그 결과물을 실행합니다. 이 한 단계가 속도의 이유이자, 앞으로 만날 모든 번거로움의 이유입니다.

첫 프로그램 — 파이썬과 나란히

// hello.cpp
#include <iostream>          // 파이썬의 import 에 해당

int main() {                  // 시작 지점이 반드시 있어야 합니다
    std::cout << "안녕\n";     // print("안녕")
    return 0;                 // 0 = 정상 종료 (셸이 이 값을 봅니다)
}
# ① 번역(컴파일) → ② 실행  — 두 단계입니다
g++ -std=c++20 -O2 hello.cpp -o hello
./hello                       # 윈도우면 hello.exe

# 파이썬은 이 한 줄이 전부였습니다
python hello.py
컴파일러는 뭘 쓰나 — 리눅스·맥은 g++ 또는 clang++, 윈도우는 Visual Studio Build Tools(cl.exe)를 깔면 됩니다. 어느 쪽이든 이 가이드의 코드는 그대로 돕니다. 지금 아무것도 깔기 싫다면 godbolt.org 에서 브라우저로 바로 돌려 볼 수 있습니다.

왜 이 귀찮음을 감수하나

파이썬C++

타입 검사실행 중에컴파일할 때
에러를 보는 시점그 줄에 도달할 때실행 전
속도기준수십~수백 배

오해 하나 — “C++ 가 빠르다”가 내가 쓴 C++ 코드가 빠르다는 뜻은 아닙니다. 생각 없이 쓴 C++ 는 numpy 보다 느립니다. 빠른 이유는 메모리 배치와 복사를 내가 직접 정할 수 있기 때문이고, 그건 ⚡ 성능 탭에서 다룹니다.

이렇게도 쓸 수 있다 — 컴파일 옵션이 결과를 바꿉니다 🟡 중급

외우면 좋은 플래그 다섯 개

g++ -std=c++20 -O2 -Wall -Wextra -g main.cpp -o app

#  -std=c++20   어느 표준으로 볼지 (안 주면 컴파일러 기본값 — 낡을 수 있음)
#  -O2          최적화 ★ 이거 하나로 10배 차이가 납니다
#  -Wall -Wextra 경고를 켜기 ★ C++ 경고는 대부분 진짜 버그입니다
#  -g           디버그 정보 (디버거로 붙을 때 필요)

# 경고를 에러로 승격 — 팀 프로젝트의 기본 설정
g++ -std=c++20 -O2 -Wall -Wextra -Werror main.cpp

# 여러 파일이면 전부 나열하거나, 나눠서 컴파일합니다
g++ -std=c++20 -c a.cpp -o a.o     # 번역만 (오브젝트 파일)
g++ -std=c++20 -c b.cpp -o b.o
g++ a.o b.o -o app                 # 링크 (합치기)
왜 나눠서 컴파일하나 — 파일 하나를 고쳤을 때 그 파일만 다시 번역하면 되기 때문입니다. 파일이 수백 개인 프로젝트에서 이 차이가 빌드 30초 vs 20분이 됩니다. CMake 가 이걸 자동으로 관리해 줍니다(🛠️ 빌드 탭).

두 종류의 에러를 구분하기 ★

① 컴파일 에러 — 문법·타입이 틀렸다
error: 'cout' was not declared in this scope
   → #include <iostream> 을 빠뜨렸거나 std:: 를 안 붙였습니다

error: invalid conversion from 'const char*' to 'int'
   → 타입이 안 맞습니다. 그 줄만 보면 됩니다

② 링크 에러 — 문법은 맞는데 '실체'가 없다
undefined reference to `foo()'
   → 선언만 있고 정의가 없거나, 그 .cpp 를 컴파일에 안 넣었습니다
   → 라이브러리를 안 붙였을 때도 납니다 (-lpthread 등)

multiple definition of `foo()'
   → 같은 함수가 두 번 정의됐습니다 (헤더에 정의를 넣은 경우)
이 구분이 왜 중요한가 — 에러 메시지에 error: 와 파일·줄 번호가 있으면 컴파일, undefined reference·LNK2019 처럼 줄 번호가 없으면 링크입니다. 고쳐야 할 곳이 완전히 다릅니다 — 링크 에러는 코드가 아니라 빌드 구성의 문제입니다.

실무에선 이렇게 — 손으로 g++ 를 치지 않습니다 🔴 실무

CMake — 지금은 이 20줄이면 충분합니다

# CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(myproj LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app main.cpp util.cpp)     # 실행 파일
# add_library(mylib STATIC util.cpp)      # 라이브러리라면

target_compile_options(app PRIVATE
  $<$<CXX_COMPILER_ID:MSVC>:/W4>
  $<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wall -Wextra>)
# 빌드는 어느 OS 에서나 같은 두 줄
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

./build/app        # 윈도우: build\Release\app.exe
왜 CMake 인가 — 윈도우·리눅스·맥에서 같은 파일 하나로 빌드되고, pybind11·vcpkg·CI 가 전부 CMake 를 전제로 돌아갑니다. “C++ 프로젝트를 받았다” = “CMakeLists.txt 부터 연다”가 됩니다.

개발 중에 실제로 쓰는 것들

# ① 빌드 캐시 — 두 번째부터 몇 배 빨라집니다
sudo apt install ccache          # 또는 brew install ccache
cmake -B build -DCMAKE_CXX_COMPILER_LAUNCHER=ccache

# ② 편집기 자동완성이 되게 — compile_commands.json ★
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
ln -s build/compile_commands.json .        # clangd·VSCode 가 이걸 읽습니다

# ③ 빌드 시스템은 Ninja 가 make 보다 빠릅니다
cmake -B build -G Ninja

# ④ 포맷·정적 분석 (파이썬의 ruff 자리)
clang-format -i src/*.cpp        # .clang-format 파일로 팀 규칙 고정
clang-tidy src/*.cpp -- -std=c++20
처음 세팅에서 가장 많이 막히는 것 — 편집기에 빨간 줄이 잔뜩 뜨는데 빌드는 되는 경우. 거의 전부 compile_commands.json 이 없거나 편집기가 못 찾아서입니다. 이 파일 하나로 자동완성·정의로 이동이 전부 살아납니다.

한 단계 더 — 번역 과정을 눈으로 보기 🧬 전문가

소스가 실행 파일이 되기까지 네 단계

# ① 전처리 — #include 를 통째로 붙여넣고 매크로를 펼칩니다
g++ -E hello.cpp | wc -l
#   40줄짜리 파일이 <iostream> 하나 때문에 수만 줄이 됩니다
#   → 헤더를 함부로 include 하면 '빌드가 느려지는' 이유가 이것입니다

# ② 컴파일 — 어셈블리로
g++ -S -O2 hello.cpp -o -   | head -40

# ③ 어셈블 — 오브젝트 파일(.o)로. 아직 실행 못 합니다
g++ -c hello.cpp -o hello.o
nm -C hello.o                 # 이 파일이 가진/필요한 심볼 목록
#   T main            ← 내가 제공 (Text = 코드)
#   U std::cout       ← 내가 필요로 함 (Undefined) ★

# ④ 링크 — 여러 .o 와 라이브러리를 이어 붙여 실행 파일로
g++ hello.o -o hello
ldd hello                     # 실행할 때 필요한 공유 라이브러리 (맥은 otool -L)

빌드가 느릴 때 어디를 보나

# 파일별 컴파일 시간 재기 (clang)
clang++ -ftime-trace -c big.cpp
#   big.json 을 chrome://tracing 이나 ui.perfetto.dev 에 넣으면
#   어느 헤더·어느 템플릿이 시간을 먹는지 그림으로 보입니다

# 전처리 결과 크기로 대략 감 잡기
for f in src/*.cpp; do echo "$(g++ -E $f 2>/dev/null | wc -l) $f"; done | sort -rn | head

# 자주 쓰는 처방
#   · 헤더에서 다른 헤더 include 를 줄이고 '전방 선언'으로 대체
#       class Foo;              // 정의 없이 이름만 알려 주기
#   · 무거운 표준 헤더는 .cpp 안으로 내리기
#   · 미리 컴파일된 헤더 (CMake 3.16+)
#       target_precompile_headers(app PRIVATE <vector> <string>)
#   · Unity build(파일 합쳐 컴파일) — CMAKE_UNITY_BUILD ON
이걸 알면 달라지는 것 — “빌드가 느리다”를 체감이 아니라 수치로 말할 수 있게 됩니다. C++ 프로젝트에서 빌드 시간은 곧 팀 전체의 생산성이라, 이걸 줄이는 사람이 실제로 대접받습니다.
정리 — C++ 는 컴파일 → 실행 두 단계입니다. g++ -std=c++20 -O2 -Wall a.cpp -o a 이 한 줄만 외우면 시작할 수 있고, 실무에서는 이걸 CMake 가 대신 해 줍니다. 에러가 나면 먼저 컴파일 에러인지 링크 에러인지부터 구분하세요 — 고칠 곳이 다릅니다.
CPP 02

변수 · 타입 · auto

파이썬은 값이 타입을 정했습니다. C++ 는 내가 미리 정합니다. 귀찮은 대신, 실행 중에 타입을 확인하는 비용이 사라집니다.

기본 타입

int    n = 10;            // 정수 (보통 32비트)
double d = 3.14;          // 실수 (파이썬 float 와 같음)
bool   b = true;          // 참/거짓 (소문자!)
char   c = 'A';           // 글자 하나 (작은따옴표)

std::string s = "안녕";   // 문자열 — #include <string>

// auto — 오른쪽을 보고 타입을 알아서 정합니다
auto x = 10;              // int
auto y = 3.14;            // double
auto z = "글자";           // ⚠ std::string 이 아니라 const char*
auto w = std::string("글자");   // 이렇게 해야 string

// 변수는 반드시 초기화하세요 ★
int a;                    // ❌ 쓰레기 값이 들어 있습니다 (UB)
int a2{};                 // ✅ 0 으로 초기화
std::string s2;           // string 은 안 적어도 빈 문자열
파이썬에서 온 사람이 가장 놀라는 것 — 초기화하지 않은 변수는 0이 아닙니다. 그 자리에 남아 있던 아무 값이 들어 있고, 그걸 읽는 건 정식으로 미정의 동작(UB)입니다. 선언과 동시에 값을 주는 습관이 C++ 안전의 절반입니다.

파이썬 타입과의 대응

파이썬C++메모

floatdouble같은 IEEE 754

파이썬 int 와 결정적으로 다른 점 — 파이썬 정수는 자릿수 제한이 없었습니다. C++ int 는 대개 ±21억이고, 넘치면 조용히 이상한 값이 되거나 컴파일러가 “넘칠 리 없다”고 가정해 코드를 지워 버립니다(🔬 전문가 탭 UB).

이렇게도 쓸 수 있다 — 크기를 정확히 정하는 타입 🟡 중급

고정폭 정수 — 다른 언어와 데이터를 주고받을 때 필수

#include <cstdint>

int32_t  a;     // 정확히 32비트 부호 있음
uint32_t b;     // 정확히 32비트 부호 없음
int64_t  c;     // 64비트
uint8_t  byte;  // 1바이트 (바이너리 데이터에)

//  int · long 의 크기는 플랫폼마다 다릅니다
//    윈도우 64비트: long = 4바이트
//    리눅스 64비트: long = 8바이트   ← 같은 코드가 다르게 동작
//  → 파일 포맷 · 네트워크 패킷 · 다른 언어와의 인터페이스에는
//    반드시 int32_t 처럼 크기가 박힌 타입을 쓰세요 ★

// 크기 · 정렬 확인
sizeof(int)        // 4
sizeof(void*)      // 8 (64비트)
alignof(double)    // 8

// 컨테이너 크기·인덱스는 size_t (부호 없음)
std::size_t n = v.size();

부호 있는 것과 없는 것을 섞으면 ★

std::vector<int> v;                  // 비어 있음

for (int i = 0; i < v.size() - 1; ++i)   // ❌ 무한 루프에 가까운 폭주
    ...
//  v.size() 는 부호 없는 0.  0 - 1 은 -1 이 아니라
//  18446744073709551615 (엄청나게 큰 수)가 됩니다.

// ✅ 방법 1 — 크기를 먼저 검사
if (!v.empty())
    for (std::size_t i = 0; i + 1 < v.size(); ++i) ...

// ✅ 방법 2 — 범위 for (인덱스를 아예 쓰지 않기) ★ 가장 좋습니다
for (int x : v) ...

// ✅ 방법 3 — C++20 부터는 안전한 비교 함수가 있습니다
#include <utility>
if (std::cmp_less(i, v.size())) ...    // 부호가 달라도 수학적으로 비교

// 변환은 반드시 명시적으로
double d = 3.9;
int    n = static_cast<int>(d);       // 3 (버림) — 의도를 코드에 남깁니다
-Wall -Wextra 를 켜야 하는 이유 — 위 비교는 comparison of integer expressions of different signedness 경고로 잡힙니다. C++ 에서 경고는 거의 다 진짜 버그입니다. 경고를 켜지 않으면 이런 게 조용히 배포됩니다.

실무에선 이렇게 — 타입으로 실수를 막습니다 🔴 실무

auto 를 언제 쓰고 언제 안 쓰나

// ✅ 타입 이름이 길고, 오른쪽만 봐도 뻔할 때
auto it = m.find(key);                     // 반복자 타입을 적을 이유가 없습니다
auto p  = std::make_unique<Node>();
for (const auto& [key, val] : dict) { ... } // 구조적 바인딩 (C++17)

// ❌ 읽는 사람이 타입을 알아야 판단할 수 있을 때
auto   total = compute();    // int 인지 double 인지 모르면 리뷰가 안 됩니다
double total = compute();

// ⚠ auto 는 참조·const 를 '떼어 버립니다' — 복사가 몰래 생깁니다 ★
auto        s = obj.name();  // 복사!
auto&       s = obj.name();  // 참조 (원본을 봄)
const auto& s = obj.name();  // 읽기 전용 참조 ← 함수 인자·범위 for 의 기본형

for (auto x : big_vec)         // ❌ 원소마다 복사
for (const auto& x : big_vec)  // ✅ 복사 없음

숫자 하나를 그냥 넘기지 않기

// ❌ 인자를 바꿔 넣어도 컴파일이 됩니다
void reserve_room(int user_id, int room_no);
reserve_room(room_no, user_id);        // 아무도 못 잡습니다

// ✅ 타입을 따로 만들면 컴파일러가 잡아 줍니다 (강한 타입)
struct UserId { int v; };
struct RoomNo { int v; };
void reserve_room(UserId, RoomNo);
reserve_room(RoomNo{3}, UserId{7});    // ❌ 컴파일 에러 — 여기서 막힙니다

// 상수는 이름을 붙입니다
constexpr int    kMaxRetry = 3;        // 매크로(#define) 대신 ★
constexpr double kTaxRate  = 0.1;

// 타입 별칭 — 의미를 이름으로

               | std::views::transform([](int x){ return x * x; });
for (int x : evens) ...        // 여기서야 실제로 계산됩니다 (지연 평가)
왜 알고리즘을 쓰나 — 짧아서가 아니라 이름이 의도를 말해 주기 때문입니다. std::any_of 는 “하나라도 있으면”이라고 읽히고, 손으로 쓴 for 문은 읽는 사람이 루프를 따라가며 해석해야 합니다. 버그도 대개 손으로 쓴 쪽에서 납니다.

std::vector<int> v{1,2,3,4,5};

// ❌ 순회 중에 추가·삭제 — 파이썬은 에러라도 났지만 C++ 는 그냥 죽습니다
for (auto& x : v) {
    if (x == 3) v.push_back(99);   // 재할당되면 x 가 가리키던 메모리가 사라짐

// ✅ ① 지울 때 — erase-remove 관용구 (C++20 은 std::erase)
std::erase_if(v, [](int x){ return x % 2 == 0; });   // 짝수 전부 삭제

// ✅ ② 반복자 루프에서 지우기 — erase 가 '다음 반복자'를 돌려줍니다
for (auto it = v.begin(); it != v.end(); ) {
    if (*it < 0) it = v.erase(it);   // ★ ++it 을 하면 안 됩니다
    else         ++it;
}

// ✅ ③ 추가할 것은 따로 모았다가 루프가 끝난 뒤에
std::vector<int> to_add;
for (const auto& x : v) if (need(x)) to_add.push_back(make(x));
v.insert(v.end(), to_add.begin(), to_add.end());

for (int x : v) if (cond(x)) s += x;    // 조건부 이동으로 바뀌기도 하지만 대개 손해

// ③ 포인터가 겹칠 수 있다는 가능성 (aliasing) ★
void add(int* out, const int* a, const int* b, int n) {
    for (int i = 0; i < n; ++i) out[i] = a[i] + b[i];
}
//   컴파일러는 out 과 a 가 같은 메모리일 수 있다고 가정해 보수적으로 컴파일합니다
//   → 겹치지 않는다고 알려 주면 벡터화됩니다
void add(int* __restrict out, const int* a, const int* b, int n);

// ④ 데이터 의존성

// ⑤ float 연산 순서 — 결합법칙이 성립하지 않아 기본적으로 재배치 금지
//    -ffast-math 로 허용할 수 있지만 정확도를 포기하는 것이라 신중하게
순서를 지키세요 — 이런 것들은 프로파일러가 그 루프를 가리킨 뒤에 볼 내용입니다. 대부분의 실제 병목은 알고리즘과 메모리 접근 패턴이지 벡터화 여부가 아닙니다.
정리 — 조건·반복은 파이썬과 거의 같습니다. for (const auto& x : v) 하나만 손에 익히면 인덱스 실수가 사라지고, 순회 중에 컨테이너를 건드리지 않는 것이 C++ 에서 가장 중요한 규칙입니다 — 파이썬은 에러를 냈지만 C++ 는 그냥 죽거나 이상한 값이 됩니다.

포인터와 참조 — 여기가 진짜 관문

파이썬 변수는 전부 포인터였습니다. 다만 그 사실이 감춰져 있었을 뿐입니다. C++ 는 값을 직접 다룰지, 주소를 다룰지 내가 고릅니다. 그게 속도의 대가로 치르는 값입니다.

값 · 포인터 · 참조 세 가지

p = nullptr;      // ✅ 비어 있음을 표현 가능
int& r2;          // ❌ 참조는 반드시 만들 때 대상이 있어야 합니다

기본 클래스

class Counter {
public:                              // 밖에서 쓸 수 있는 것
    Counter() = default;             // 기본 생성자
    explicit Counter(int start)      // 생성자 (파이썬 __init__)
        : n_(start) {}               // ★ 초기화 리스트 — 본문보다 이쪽

    ~Counter() {                     // 소멸자 — 사라질 때 자동 호출
        std::cout << "정리됨\n";
    }

    void add(int d)       { n_ += d; }
    int  value() const    { return n_; }   // 안 바꾸는 함수엔 const

private:                             // 밖에서 못 건드림 (기본값)
    int n_ = 0;                      // 멤버는 뒤에 _ 를 붙이는 관례가 흔합니다
};

Counter c{10};        // 스택에 생성
c.add(5);
c.value();            // 15
// } 를 만나면 여기서 ~Counter() 가 자동으로 불립니다 ★

    std::vector<int>        data_;    // 알아서 정리됨
    std::unique_ptr<Impl>   impl_;    // 알아서 정리됨
    std::string             name_;
    // 아무것도 안 써도 완벽하게 동작합니다 ★
};

// 5 의 법칙 — 하나라도 직접 쓰면 나머지도 정의해야 합니다
//   소멸자 / 복사 생성 / 복사 대입 / 이동 생성 / 이동 대입
class Raw {
    int* p_;
public:
    ~Raw() { delete p_; }        // 소멸자만 썼더니
};
Raw a, b = a;                    // 복사되면 같은 포인터를 둘이 delete → 크래시 ★

// 그래서 실무 규칙은 이것입니다
//   ① 자원은 unique_ptr·vector·string 같은 '이미 관리되는 타입'에 맡긴다
//   ② 정말 직접 관리해야 하면 그 클래스는 '자원 하나만' 감싸고
//      다섯 개를 모두 명시한다 (또는 복사를 delete 한다)
이 규칙 하나로 C++ 메모리 버그의 대부분이 사라집니다. “delete 를 어디서 부르지?”라는 고민이 나온다면 이미 잘못된 길에 들어선 것입니다 — 그 자원을 감쌀 타입을 먼저 만드세요(탭 2).

객체 레이아웃과 특수 멤버 자동 생성 규칙

// ① 이동 생성자는 '복사 생성자나 소멸자를 직접 쓰면' 자동 생성이 막힙니다
class A { ~A() {} };            // 소멸자를 썼더니
A a; A b = std::move(a);        // → 이동이 아니라 '복사'가 불립니다 (조용히)
//   대형 컨테이너에서 성능이 몇 배 나빠지는 흔한 원인 ★
//   해결: 필요한 것을 = default 로 명시
class B { ~B() = default; B(B&&) = default; B& operator=(B&&) = default; };

// ② 클래스 크기 — 빈 클래스도 1바이트입니다 (주소가 있어야 하므로)
struct Empty {};                 sizeof(Empty);        // 1
struct Derived : Empty { int x; }; sizeof(Derived);    // 4 (빈 기반 최적화)
struct HasMember { Empty e; int x; }; sizeof(HasMember); // 8 (패딩 발생)
//   → C++20 [[no_unique_address]] 로 멤버에도 같은 최적화를 적용할 수 있습니다
struct Better { [[no_unique_address]] Empty e; int x; };  // 4

// ③ 컴파일 시점에 성질 확인 — 라이브러리 인터페이스에 못 박아 두기
static_assert(std::is_trivially_copyable_v<Point>);   // memcpy 해도 되는 타입인가
static_assert(std::is_standard_layout_v<Point>);      // C 와 호환되는 배치인가 ★
//   이 두 개가 참이어야 C ABI 로 구조체를 그대로 넘길 수 있습니다(🔗 탭)
모듈을 만들 때 직결됩니다 — 파이썬·Node 에 넘길 구조체는 is_standard_layout 이 참이어야 바이트 단위로 그대로 주고받을 수 있습니다. 가상 함수가 하나라도 있으면 이 성질이 깨집니다(vtable 포인터가 앞에 붙습니다).
정리 — C++ 클래스의 핵심은 소멸자입니다. 객체가 사라지는 그 자리에서 반드시 불리기 때문에, “열었으면 닫기”를 사람이 아니라 타입이 책임지게 만들 수 있습니다. 그리고 가장 좋은 클래스는 소멸자를 안 쓰는 클래스입니다 — vector·string·unique_ptr 이 대신해 주니까요.
CPP 08

상속과 가상 함수

파이썬은 항상 자식 메서드가 불렸습니다. C++ 는 virtual 을 붙여야 그렇게 됩니다. 안 붙이면 조용히 부모 것이 불립니다.

인터페이스와 구현

class Storage {                       // 파이썬 ABC 자리
public:
    virtual ~Storage() = default;     // ★ 반드시 virtual 소멸자
    virtual void save(std::string_view key,
                      std::span<const std::byte> data) = 0;   // = 0 → 순수 가상
    virtual bool exists(std::string_view key) const = 0;
};

class FileStorage : public Storage {
public:
    void save(std::string_view key,
              std::span<const std::byte> data) override {     // ★ override 필수
        ...
    }
    bool exists(std::string_view key) const override { ... }
};

// 쓰는 쪽은 인터페이스만 압니다
void backup(Storage& s) { s.save("k", data); }

FileStorage fs;
backup(fs);                            // 실행 시점에 FileStorage 것이 불립니다

// 다형적으로 보관하려면 포인터로
std::vector<std::unique_ptr<Storage>> all;
all.push_back(std::make_unique<FileStorage>());
virtual ~Storage() 를 빠뜨리면 — Storage* 로 delete 할 때 자식 소멸자가 안 불립니다(UB). 자식이 들고 있던 메모리·파일이 그대로 샙니다. “상속할 클래스에는 virtual 소멸자” 는 예외 없는 규칙입니다.

virtual 을 안 붙이면

struct Base    { void f() { std::puts("Base"); } };        // virtual 없음
struct Derived : Base { void f() { std::puts("Derived"); } };

Derived d;
Base& b = d;
b.f();          // "Base" ★ 파이썬이라면 "Derived" 였을 자리

// virtual 을 붙이면 기대대로 동작합니다
struct Base2    { virtual void f() { std::puts("Base"); } };
struct Derived2 : Base2 { void f() override { std::puts("Derived"); } };
Base2& b2 = d2;
b2.f();         // "Derived"

// ⚠ 객체 잘림(slicing) — 값으로 복사하면 자식 부분이 잘려 나갑니다
void take(Base2 b);      // ❌ 값으로 받으면
take(d2);                //    Base2 부분만 복사됩니다 (자식이 사라짐)
void take(Base2& b);     // ✅ 참조나 포인터로 받으세요

std::vector<Base2> v;    // ❌ 다형적 컨테이너로 쓸 수 없습니다
std::vector<std::unique_ptr<Base2>> v2;   // ✅

이렇게도 쓸 수 있다 — 상속 말고 다른 방법 🟡 중급

void process(const Data& d, std::function<void(Result)> on_done);
process(d, [](Result r){ save(r); });

using Shape = std::variant<Circle, Rect, Triangle>;

상속을 쓸 때의 규칙

// ① override 를 반드시 적으세요 — 오타를 컴파일러가 잡아 줍니다
struct D : B {
    void run(int) override;    // 부모에 run(int) 이 없으면 컴파일 에러 ★
    void run(long);            // override 없으면 '새 함수'가 조용히 생깁니다
};

// ② 더 못 물려받게 막기
struct Final final : B { ... };            // 이 클래스는 상속 불가
void f() final;                            // 이 함수는 더 재정의 불가
//   final 은 컴파일러가 가상 호출을 직접 호출로 바꿀 수 있게 해 성능에도 도움

// ③ protected 는 최소한으로 — 자식이 부모 내부에 의존하기 시작합니다

// ④ 다중 상속은 '인터페이스(순수 가상만 있는 클래스)' 에만
struct Readable  { virtual ~Readable() = default;  virtual Data read() = 0; };
struct Writable  { virtual ~Writable() = default;  virtual void write(Data) = 0; };
struct File : Readable, Writable { ... };   // ✅ 이 정도는 안전합니다
//   상태를 가진 클래스를 여럿 상속하면 다이아몬드 문제와 virtual 상속으로 이어집니다
파이썬 습관과의 차이 — 파이썬은 믹스인 상속이 흔했지만, C++ 에서는 상속이 가장 강한 결합입니다. “기능을 재사용하고 싶다”면 멤버로 가지는 것(컴포지션)이 거의 항상 낫습니다.

한 단계 더 — 가상 호출은 실제로 얼마나 비싼가 🧬 전문가

vtable 의 구조

struct B { virtual void f(); virtual void g(); int x; };
sizeof(B);      // 16 — vptr(8) + int(4) + 패딩(4)
//   가상 함수가 하나라도 있으면 객체 앞에 '표 주소' 8바이트가 붙습니다

// b.f() 가 실제로 하는 일
//   ① 객체에서 vptr 을 읽는다        (메모리 접근 1)
//   ② 표에서 f 의 주소를 읽는다      (메모리 접근 2)
//   ③ 그 주소로 간접 점프            (분기 예측 실패 가능)
//
//   직접 호출 대비 대략 몇 사이클 — 그 자체는 크지 않습니다.
//   진짜 비용은 ★ 인라인이 불가능해진다는 것입니다.
//   한 줄짜리 접근자가 인라인되면 0사이클인데, 가상이면 호출이 남습니다.

// 컴파일러가 대상을 확신하면 직접 호출로 바꿉니다 (devirtualization)
struct D final : B { void f() override; };
D d; d.f();          // 정적 타입이 확실 → 직접 호출 · 인라인 가능
//   final 을 붙이는 것만으로 최적화 여지가 생깁니다

언제 문제가 되나 — 그리고 대안

//   ① 아주 자주 불린다(수백만 회)  ② 함수 본문이 아주 짧다
//   ③ 루프 안에서 불린다 → 벡터화가 막힌다

// ❌ 원소마다 가상 호출 — 캐시도, 벡터화도 놓칩니다

// ✅ 대안 ③ 함수 단위를 키우기 — 원소 하나가 아니라 '배열 전체'를 가상 함수로

//   가상 호출 1번 + 내부는 순수 루프 → 비용이 사실상 사라집니다 ★

// 측정 없이 판단하지 마세요
//   perf stat -e branch-misses,cache-misses ./app
//   대부분의 프로그램에서 가상 호출은 병목 근처에도 못 갑니다
흔한 과잉 반응 — “가상 함수는 느리다”며 전부 템플릿으로 바꾸면 빌드 시간과 바이너리 크기가 폭발하고 코드가 읽기 어려워집니다. 위 대안 ③(호출 단위를 키우기) 이 거의 항상 가장 좋은 답입니다.
정리 — 자식 것이 불리게 하려면 virtual, 재정의할 때는 override, 상속할 클래스에는 virtual 소멸자. 이 세 개가 규칙의 전부입니다. 그리고 상속은 마지막에 고려하세요 — C++ 에서는 variant·템플릿·함수 객체로 해결되는 경우가 훨씬 많습니다.

예외와 에러 처리

문법은 파이썬과 거의 같습니다. 다른 건 문화 — C++ 에는 예외를 아예 쓰지 않는 코드베이스가 많습니다. 두 방식을 다 알아야 남의 코드를 읽을 수 있습니다.

예외 기본

#include <stdexcept>

double divide(double a, double b) {
    if (b == 0)
        throw std::invalid_argument("0으로 나눌 수 없습니다");
    return a / b;
}

try {
    auto r = divide(1, 0);
} catch (const std::invalid_argument& e) {   // ★ const 참조로 받으세요
    std::cerr << e.what() << "\n";
} catch (const std::exception& e) {          // 좁은 것 → 넓은 것 순서
    std::cerr << "그 외: " << e.what() << "\n";
}
// catch (...) 는 모든 것을 잡습니다 (마지막 수단)

// 표준 예외 계층
//   std::exception
//     ├─ logic_error   → invalid_argument · out_of_range · domain_error
//     ├─ runtime_error → range_error · system_error(errno·OS 에러)
//     └─ bad_alloc(메모리 부족) · bad_cast

// 내 예외 만들기
class ParseError : public std::runtime_error {
public:
    ParseError(int line, const std::string& msg)
        : std::runtime_error("행 " + std::to_string(line) + ": " + msg),
          line_(line) {}
    int line() const noexcept { return line_; }
private:
    int line_;
};

현대 구현은 '테이블 기반(zero-cost)' 방식입니다.

  · 대신 컴파일러가 '어디서 예외가 나면 무엇을 정리할지' 표를 만들어

  · 실제로 던져지면 그 표를 '읽어 가며' 스택을 되감습니다

  · 던지지 않을 때 : 실행 비용 0 · 바이너리 크기 +5~15%
  · 던질 때        : 매우 비쌈 (수 마이크로초 — 표 조회 + 되감기)
                     ★ 게다가 시간이 일정하지 않습니다
