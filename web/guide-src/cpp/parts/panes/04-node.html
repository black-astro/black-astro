NODE 01

애드온 · WASM · 별도 프로세스 — 무엇을 고를까

네이티브 애드온이 항상 답은 아닙니다. 배포와 유지보수 비용까지 보면 다른 선택이 나은 경우가 많습니다.

속도최고0.7~0.9배IPC 비용
배포OS별 바이너리파일 하나 ★실행 파일
격리없음(크래시=전체)샌드박스완전 격리 ★

고르는 기준 — 큰 데이터를 자주 주고받으면 애드온, 배포 편의와 안전이 우선이면 WASM, 크래시가 서버를 죽이면 안 되거나 GPL 라이브러리를 쓴다면 별도 프로세스입니다.

FFI 와도 비교해야 합니다

같은 C++ 코드를 Node 에서 쓰는 네 가지 길

  ① 네이티브 애드온 (N-API)     ← 이 탭
     · 가장 빠름 · JS 객체를 자유롭게 다룸
     · 빌드 필요 · prebuild 배포 · 이 탭의 주제

  ② FFI (koffi · Deno.dlopen)   ← 🔗 f06
     · 빌드 불필요 · 여러 언어가 같은 .so 공유
     · 호출 비용이 조금 큼 · JS 객체를 다루기 어려움

  ③ WASM (Emscripten)
     · 파일 하나로 배포 · 브라우저에서도 동작
     · 메모리 경계를 넘을 때 복사 · 시스템 호출 제한

  ④ 별도 프로세스 + IPC
     · 크래시 격리 · 라이선스 분리 · 언어 자유
     · 직렬화 비용 · 프로세스 관리 부담

★ 실무 조언
  먼저 ②(FFI)로 만들어 동작을 검증하고,
  호출 비용이 문제가 되면 ①(애드온)으로 옮기는 순서가 안전합니다.
  C API 를 잘 만들어 두면 둘 사이 이동이 쉽습니다(🔗 f03).

이렇게도 쓸 수 있다 — 언제 애드온이 정답인가 🟡 중급

실제로 쓰이는 곳

  • 이미지·영상 처리 — sharp(libvips), ffmpeg 바인딩. Buffer 를 복사 없이 넘길 수 있는 것이 결정적입니다
  • 암호·해시 — bcrypt, argon2. CPU 를 오래 쓰므로 워커 스레드로 빼는 것이 필수입니다
  • DB 드라이버 — better-sqlite3, node-oracledb. 기존 C 라이브러리를 그대로 씁니다
  • 직렬화 — protobuf, msgpack 가속
  • OS 통합 — 트레이 아이콘, 전역 단축키, 화면 캡처(Electron)
  • ML 추론 — onnxruntime-node, node-llama-cpp
애드온이 답이 아닌 경우 — JSON 파싱·문자열 처리 같은 것은 V8 이 이미 매우 빠릅니다. 경계 비용 때문에 C++ 로 옮기면 오히려 느려지는 경우가 흔합니다. 반드시 먼저 측정하세요.

N-API 를 써야 하는 이유 ★

Node 애드온 API 의 역사

  ① V8 API 직접 사용 (옛 방식 · nan)
     · V8 버전이 바뀔 때마다 코드가 깨집니다
     · Node 메이저 버전마다 재빌드 필요
     · Electron 은 또 다른 V8 버전 → 별도 빌드

  ② N-API / Node-API (Node 8.6+, 안정화 10+)  ★ 현재 표준
     · C 로 된 ABI 안정 인터페이스
     · 한 번 빌드하면 Node 여러 메이저 버전에서 동작
     · Electron·Bun·Deno 도 일부 지원
     · node-addon-api 는 이것의 C++ 래퍼(헤더 전용)

★ 지금 새로 만든다면 선택지는 하나입니다 — node-addon-api
  nan(Native Abstractions for Node) 은 레거시입니다.

버전 확인
  napi_version 3 → Node 10+
  napi_version 8 → Node 16+   (대부분 여기면 충분)
  napi_version 9 → Node 18.17+

실무에선 이렇게 — 도입 전에 계산할 것 🔴 실무

진짜 비용은 배포입니다

지원해야 할 조합
  OS      : linux · darwin · win32
  아키텍처 : x64 · arm64
  libc    : glibc · musl(alpine) ★ 도커에서 자주 문제
  런타임   : Node · Electron · Bun

  → 최소 6~12개 바이너리. prebuild 로 자동화하지 않으면 감당 못 합니다(j09)

사용자 쪽에서 나는 문제
  · 컴파일러가 없어 설치 실패 (윈도우가 특히)
  · node-gyp 이 Python 을 요구 (예전 버전)
  · 알파인 리눅스에서 musl 불일치
  · Electron 버전이 다르면 재빌드 필요
  · CI 캐시에 안 맞는 바이너리가 남아 있음

★ 그래서 prebuildify + node-gyp-build 조합이 사실상 표준입니다
  (모든 바이너리를 패키지에 넣고 런타임에 골라 로드)

한 단계 더 — Node 아키텍처와의 관계 🧬 전문가

이벤트 루프와 스레드 풀

Node 의 구조
  · 메인 스레드 하나가 JS 를 실행합니다 (이벤트 루프)
  · libuv 스레드 풀(기본 4개)이 파일 I/O·DNS·zlib 을 처리합니다
  · 네이티브 애드온의 AsyncWorker 도 이 풀을 씁니다 ★

★ 그래서 생기는 일
  ① 동기 애드온 호출은 이벤트 루프를 통째로 멈춥니다
     500ms 걸리면 그동안 모든 HTTP 요청이 대기합니다
  ② AsyncWorker 를 많이 쓰면 스레드 풀이 고갈됩니다
     → 파일 I/O 까지 느려집니다
     UV_THREADPOOL_SIZE 로 늘릴 수 있습니다 (최대 1024)
  ③ 자체 스레드를 쓰면 풀과 무관하지만
     JS 를 부를 때 ThreadSafeFunction 이 필요합니다(j07)

측정
  node --cpu-prof app.js          # CPU 프로파일
  process.env.UV_THREADPOOL_SIZE  # 현재 설정
  perf_hooks.monitorEventLoopDelay()   # 이벤트 루프 지연 ★

이벤트 루프 지연 측정하기

import { monitorEventLoopDelay } from 'node:perf_hooks'

const h = monitorEventLoopDelay({ resolution: 10 })
h.enable()

// 동기 애드온 호출
for (let i = 0; i < 100; i++) addon.heavySync(data)

h.disable()
console.log(`평균 ${(h.mean/1e6).toFixed(1)}ms  최대 ${(h.max/1e6).toFixed(1)}ms`)
//   ★ 최대값이 수백 ms 면 사용자가 체감하는 응답 지연입니다

// 비동기 버전과 비교
h.reset(); h.enable()
await Promise.all(Array.from({length:100}, () => addon.heavyAsync(data)))
h.disable()
console.log(`비동기: 최대 ${(h.max/1e6).toFixed(1)}ms`)   // 훨씬 작아야 정상
기준선 — 웹 서버라면 이벤트 루프 지연이 10ms 를 넘으면 문제로 봅니다. 1ms 이상 걸리는 애드온 함수는 비동기로 만드세요(j06).
정리 — 애드온은 큰 데이터를 복사 없이 다뤄야 할 때 가장 강력합니다. 배포가 부담이면 WASM, 크래시 격리가 필요하면 별도 프로세스, 빠르게 검증하려면 FFI 를 먼저 보세요. 그리고 무엇을 고르든 이벤트 루프를 막지 않는 것이 첫 번째 원칙입니다.

① C++ 파일

// src/addon.cpp
#include <napi.h>
#include <vector>

// 모든 함수는 CallbackInfo 를 받고 Napi::Value 를 돌려줍니다
Napi::Value Add(const Napi::CallbackInfo& info) {
    Napi::Env env = info.Env();

    // ★ 인자 검증을 반드시 하세요 (안 하면 크래시)
    if (info.Length() < 2 || !info[0].IsNumber() || !info[1].IsNumber()) {
        Napi::TypeError::New(env, "숫자 두 개가 필요합니다")
            .ThrowAsJavaScriptException();
        return env.Null();
    }

    double a = info[0].As<Napi::Number>().DoubleValue();
    double b = info[1].As<Napi::Number>().DoubleValue();
    return Napi::Number::New(env, a + b);
}

// 모듈 등록
Napi::Object Init(Napi::Env env, Napi::Object exports) {
    exports.Set("add", Napi::Function::New(env, Add));
    return exports;
}
NODE_API_MODULE(addon, Init)      // ★ 첫 인자는 binding.gyp 의 target_name

// 매번 쓰는 검증 코드를 줄이는 관용구
namespace {
double RequireNumber(const Napi::CallbackInfo& info, std::size_t i,
                     const char* name) {
    if (info.Length() <= i || !info[i].IsNumber())
        throw Napi::TypeError::New(info.Env(),
            std::string(name) + " 는 숫자여야 합니다");
    return info[i].As<Napi::Number>().DoubleValue();
}
int RequireInt(const Napi::CallbackInfo& info, std::size_t i,
               const char* name, int def) {
    if (info.Length() <= i || info[i].IsUndefined()) return def;
    return RequireNumber(info, i, name);
}
}  // namespace

// index.js — 얇은 JS 래퍼로 검증·기본값을 처리 ★
const native = require('node-gyp-build')(__dirname)

export function smooth(data, { window = 3, mode = 'nearest' } = {}) {
  if (!(data instanceof Float64Array))
    data = Float64Array.from(data)          // 정규화
  if (!Number.isInteger(window) || window < 1)
    throw new RangeError(`window 는 1 이상 정수여야 합니다 (받음: ${window})`)
  return native.smooth(data, window, mode === 'reflect' ? 1 : 0)
}

function toF64(data) {
  if (data instanceof Float64Array) return data
  if (ArrayBuffer.isView(data))
    return Float64Array.from(data)          // 다른 TypedArray → 변환
  if (Array.isArray(data)) return Float64Array.from(data)
  throw new TypeError('배열 또는 TypedArray 가 필요합니다')
}

export function smooth(data, window = 3) {
  const a = toF64(data)
  if (a.length === 0) return new Float64Array(0)      // ★ 빈 입력 처리
  if (!Number.isInteger(window) || window < 1 || window > a.length)
    throw new RangeError(`window 는 1~${a.length} 여야 합니다 (받음: ${window})`)
  return native.smooth(a, window)
}

Napi::Value Grayscale(const Napi::CallbackInfo& info) {

    const int h = info[2].ToNumber().Int32Value();

            0.299 * p[i*4] + 0.587 * p[i*4+1] + 0.114 * p[i*4+2]);
        p[i*4] = p[i*4+1] = p[i*4+2] = g;

class SmoothWorker : public Napi::AsyncWorker {
public:
    SmoothWorker(Napi::Function& cb, Napi::Float64Array input, int window)
        : Napi::AsyncWorker(cb),
          window_(window),
          n_(input.ElementLength()),
          ref_(Napi::Persistent(input))          // ★ GC 방지
    {
        src_ = input.Data();
        out_.resize(n_);
    }

    // ⚠ 워커 스레드에서 실행 — 여기서 JS 를 만지면 절대 안 됩니다 ★
    void Execute() override {

    }

    // 메인 스레드로 돌아와서 실행 — 여기서만 JS 를 다룹니다
    void OnOK() override {
        Napi::HandleScope scope(Env());
        auto arr = Napi::Float64Array::New(Env(), n_);
        std::copy(out_.begin(), out_.end(), arr.Data());
        Callback().Call({ Env().Null(), arr });   // (err, result)
    }

    void OnError(const Napi::Error& e) override {
        Napi::HandleScope scope(Env());
        Callback().Call({ e.Value(), Env().Undefined() });
    }

private:

    std::vector<double> out_;
    Napi::Reference<Napi::Float64Array> ref_;

        : AsyncProgressWorker(cb), prog_(Napi::Persistent(onProgress)) {}

        const std::size_t step = std::max<std::size_t>(n_ / 100, 1);

// 취소 가능한 작업 — AbortSignal 과 연결 ★
export function smoothAsync(data, { window = 3, signal, onProgress } = {}) {
  return new Promise((resolve, reject) => {
    const task = native.smoothAsync(
      toF64(data), window,
      (err, result) => err ? reject(err) : resolve(result),
      onProgress
    )
    if (signal) {
      if (signal.aborted) { task.cancel(); return reject(signal.reason) }
      signal.addEventListener('abort', () => task.cancel(), { once: true })
    }
  })
}

// libuv 풀을 피하고 싶을 때 — 직접 스레드에서 돌리고 TSFN 으로 알림
#include <thread>

Napi::Value RunOwnThread(const Napi::CallbackInfo& info) {
    auto env = info.Env();
    auto deferred = Napi::Promise::Deferred::New(env);
    auto input = info[0].As<Napi::Float64Array>();

    // 데이터를 C++ 로 복사 (스레드가 안전하게 소유)
    auto data = std::make_shared<std::vector<double>>(
        input.Data(), input.Data() + input.ElementLength());

    auto tsfn = Napi::ThreadSafeFunction::New(
        env, Napi::Function::New(env, [](const Napi::CallbackInfo&){}),
        "worker", 0, 1);

    std::thread([data, tsfn, deferred]() mutable {
        auto result = std::make_shared<std::vector<double>>(core::run(*data));
        tsfn.BlockingCall([deferred, result](Napi::Env env, Napi::Function) {
            auto arr = Napi::Float64Array::New(env, result->size());
            std::copy(result->begin(), result->end(), arr.Data());
            deferred.Resolve(arr);            // ★ 메인 스레드에서 resolve
        });
        tsfn.Release();
    }).detach();

    return deferred.Promise();
}

class BatchWorker : public Napi::AsyncWorker {

    std::vector<std::vector<double>> outputs_;

    void Execute() override {
        outputs_.resize(inputs_.size());
        // 내부에서 병렬화까지 (⚡ e07)
        std::transform(std::execution::par,
                       inputs_.begin(), inputs_.end(), outputs_.begin(),
                       [](const auto& in){ return core::run(in); });

        auto arr = Napi::Array::New(Env(), outputs_.size());
        for (std::size_t i = 0; i < outputs_.size(); ++i) {
            auto ta = Napi::Float64Array::New(Env(), outputs_[i].size());
            std::copy(outputs_[i].begin(), outputs_[i].end(), ta.Data());
            arr.Set(i, ta);
        }
        Callback().Call({ Env().Null(), arr });
    }
};

Napi::Value Watch(const Napi::CallbackInfo& info) {

    auto jsCallback = info[0].As<Napi::Function>();

        jsCallback,          // 부를 JS 함수

        0,                   // 큐 최대 크기 (0 = 무제한)
        1,                   // 초기 스레드 수
        [](Napi::Env) { /* 마지막 Release 후 정리 */ });

    std::thread([tsfn]() mutable {
        while (running) {
            auto ev = wait_for_event();           // 블로킹 (JS 무관)

            // 메인 스레드에서 실행될 람다를 큐에 넣습니다
            tsfn.BlockingCall([ev](Napi::Env env, Napi::Function cb) {
                cb.Call({ Napi::String::New(env, ev.name) });
            });
        }
        tsfn.Release();       // ★ 반드시 해제 (안 하면 프로세스가 안 끝납니다)
    }).detach();

async function* events(path) {
  const queue = []
  let resolve
  const w = native.watch(path, (t, f) => {
    queue.push({ t, f })
    resolve?.()
  })
  try {
    while (true) {
      if (!queue.length) await new Promise(r => { resolve = r })
      yield queue.shift()
    }
  } finally { native.unwatch(w) }
}

        Napi::Function func = DefineClass(env, "Engine", {
            InstanceMethod("feed",   &Engine::Feed),
            InstanceMethod("result", &Engine::Result),
            InstanceMethod("close",  &Engine::Close),
            InstanceAccessor("size", &Engine::GetSize, nullptr),   // 읽기 전용
            StaticMethod("version",  &Engine::Version),
        });

        auto* ctor = new Napi::FunctionReference();
        *ctor = Napi::Persistent(func);
        env.SetInstanceData(ctor);

        exports.Set("Engine", func);
        return exports;
    }

    explicit Engine(const Napi::CallbackInfo& info)
        : Napi::ObjectWrap<Engine>(info)
    {
        int window = 3;
        if (info.Length() > 0 && info[0].IsObject())
            window = info[0].As<Napi::Object>()
                        .Get("window").ToNumber().Int32Value();
        if (window <= 0)
            throw Napi::RangeError::New(info.Env(), "window 는 1 이상");
        impl_ = std::make_unique<core::Engine>(window);
    }

private:
    std::unique_ptr<core::Engine> impl_;

    Napi::Value Feed(const Napi::CallbackInfo& info) {
        auto a = info[0].As<Napi::Float64Array>();
        impl_->feed(a.Data(), a.ElementLength());
        return info.Env().Undefined();
    }
    Napi::Value GetSize(const Napi::CallbackInfo& info) {
        return Napi::Number::New(info.Env(),
                                 static_cast<double>(impl_->size()));
    }
    Napi::Value Close(const Napi::CallbackInfo& info) {
        impl_.reset();                     // ★ 명시적 해제
        return info.Env().Undefined();
    }
};

한 단계 더 — ObjectWrap 의 내부 🧬 전문가

JS 객체와 C++ 객체의 연결

new addon.Engine() 이 하는 일

  ① V8 이 JS 객체를 만듭니다
  ② napi_wrap 으로 그 객체에 C++ 포인터를 붙입니다
     (내부 필드 또는 숨은 속성에 저장)
  ③ finalizer 를 등록합니다 — GC 될 때 C++ 소멸자를 부르도록
  ④ 메서드 호출 시 napi_unwrap 으로 포인터를 꺼내 씁니다

★ 그래서 생기는 특성
  · JS 객체가 살아 있는 동안 C++ 객체도 살아 있습니다
  · JS 참조가 사라지면 GC 시점에 C++ 소멸자가 불립니다
  · GC 가 안 돌면 소멸자도 안 불립니다 (프로세스 종료 시 보장 없음) ★
  · 그래서 close()/dispose 패턴이 필요합니다

메서드 호출 비용
  ① unwrap (포인터 조회)  ② 인자 변환  ③ C++ 호출  ④ 반환값 변환
  → 대략 100~300ns. 초당 수백만 회는 무리입니다.
    핫 루프라면 배열 단위 API 로 바꾸세요.

애드온이 로드되지 않는 대표 메시지

  using NODE_MODULE_VERSION 108. This version requires 115.

NODE_MODULE_VERSION (ABI)
  Node 18 → 108
  Node 20 → 115
  Node 22 → 127
  Electron 28 → 119   ← 같은 Node 버전이어도 다릅니다

N-API 를 쓰면
  · napi_version 만 맞으면 됩니다 (하위 호환 보장)
  · Electron 도 N-API 를 지원합니다
  · 재빌드 없이 그대로 로드됩니다 ★

이렇게도 쓸 수 있다 — 다른 런타임 지원 🟡 중급

Bun · Deno

Bun
  · N-API 를 상당 부분 지원합니다 (완전하지는 않습니다)
  · 대부분의 애드온이 그대로 동작하지만 검증이 필요합니다
  · Bun 자체 FFI(bun:ffi)가 더 빠르므로, C API 도 함께 제공하면 좋습니다

Deno
  · N-API 지원 (Deno 2.x 에서 npm 패키지와 함께)
  · 권한 모델 때문에 --allow-ffi 등이 필요할 수 있습니다
  · Deno.dlopen(FFI)가 더 자연스러운 경로입니다(🔗 f06)

★ 실무 조언
  하나의 C++ 코어를 두 가지로 노출하면 모든 런타임을 덮습니다
    ① N-API 애드온  → Node · Electron (성능 최우선)
    ② C ABI 공유 라이브러리 → Deno · Bun · 파이썬 · 그 외 (🔗 탭)
  코어 로직을 순수 C++ 로 분리해 두면 어렵지 않습니다 (j02 구조)
