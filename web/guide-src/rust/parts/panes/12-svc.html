Rust 가 이기는 자리 — 어디에 쓰면 남는 장사인가

Rust 를 “빠른 언어”로만 소개하면 절반만 맞습니다. C 도 빠르고 C++ 도 빠릅니다. Rust 의 진짜 값어치는 그 속도를 유지하면서 메모리 사고와 데이터 레이스를 컴파일 단계에서 지운다는 데 있습니다. 이 섹션은 “그래서 어떤 일을 Rust 로 다시 써야 이득인가”를 실제 사례와 함께 정리합니다.

Rust 가 들어간 자리는 전부 “빠르면서 절대 죽으면 안 되는” 곳입니다 — 그게 이 언어의 시장입니다.

제로 비용 추상화 — 예쁘게 써도 안 느려집니다

// 읽기 좋은 이터레이터 체인
pub fn sum_even(v: &[u32]) -> u64 {
    v.iter()
     .filter(|&&x| x % 2 == 0)
     .map(|&x| x as u64)
     .sum()
}

// --release 로 빌드하면 컴파일러가 이걸로 바꿉니다:
//   루프 하나 + SIMD 벡터화. 클로저 호출도, 중간 Vec 도 없습니다.
//   godbolt.org 에 붙여 보면 어셈블리가 20줄 남짓입니다.

// 파이썬이라면 sum(x for x in v if x % 2 == 0) — 편하지만
//   제너레이터 프레임 · 정수 객체 할당 · 참조 카운트가 매 원소마다 돕니다.
// 자바라면 IntStream — JIT 가 잘 풀어 주지만 워밍업이 필요하고
//   객체 헤더 · 카드 마킹 같은 비용이 남습니다.
“제로 비용”의 정확한 뜻 — “쓰지 않으면 비용이 없고, 쓰더라도 손으로 짠 것보다 느리지 않다”(비야네 스트롭스트룹의 정의)입니다. 추상화가 컴파일 시점에 사라지기 때문이고, 그 근거는 제네릭이 단형화(monomorphization)되고 트레이트 호출 대부분이 정적으로 결정되기 때문입니다(🔬 d03).

데이터 레이스 — 다른 언어에선 런타임, 여기선 빌드 에러

use std::collections::HashMap;
use std::thread;

fn main() {
    let mut map = HashMap::new();
    map.insert("hits", 0u64);

    // ❌ 두 스레드가 같은 HashMap 을 동시에 건드리려 함
    thread::scope(|s| {
        s.spawn(|| { map.insert("a", 1); });   // error[E0499]:
        s.spawn(|| { map.insert("b", 2); });   //   cannot borrow `map` as mutable
    });                                        //   more than once at a time
}

// ✅ 공유하려면 '어떻게 공유할지'를 타입으로 적어야 통과합니다
use std::sync::{Arc, Mutex};
let map = Arc::new(Mutex::new(HashMap::new()));
// 또는 아예 공유하지 않는 설계 — 액터 (h03) ★ 이 탭이 미는 방향
Go 와 결정적으로 갈리는 지점 — Go 에서 같은 map 을 두 고루틴이 건드리면 컴파일은 되고 운영에서 concurrent map writes 로 프로세스가 죽습니다. Java 라면 조용히 값이 깨집니다. Rust 는 그 코드가 애초에 빌드되지 않습니다(⚡ e06 의 Send·Sync).

“메모리 누수가 안전이라니?” — Rust 의 안전 정의는 “미정의 동작(UB)이 없다”이지 “버그가 없다”가 아닙니다. 누수는 UB 가 아니라 그냥 메모리를 안 돌려준 상태입니다. Arc 순환 참조가 대표적이고, 잡는 법은 h10 에 있습니다.

unsafe 는 “검사를 끄는” 게 아닙니다

// unsafe 블록 안에서도 소유권·빌림·타입 검사는 그대로 돕니다.
// 추가로 '다섯 가지'가 허용될 뿐입니다:
//   ① 원시 포인터 역참조   ② unsafe fn 호출
//   ③ static mut 접근      ④ union 필드 읽기
//   ⑤ unsafe trait 구현 (Send/Sync 를 손으로 붙이기)

// 실무 원칙: unsafe 를 안전한 API 로 '포장'해서 밖으로는 안 보이게 합니다.
pub fn split_at_mut(v: &mut [u32], mid: usize)
    -> (&mut [u32], &mut [u32])
{
    assert!(mid <= v.len());              // ← 여기서 조건을 보장하고
    let ptr = v.as_mut_ptr();
    unsafe {                               // ← 좁은 범위에서만
        (std::slice::from_raw_parts_mut(ptr, mid),
         std::slice::from_raw_parts_mut(ptr.add(mid), v.len() - mid))
    }
}
// 표준 라이브러리가 통째로 이 패턴입니다 — Vec · HashMap 내부는 unsafe 투성이고,
// 밖으로는 안전한 인터페이스만 나옵니다. (🔬 d01)
서비스 코드에서 unsafe 비율 — 실측 조사(cargo-geiger 등)에서 애플리케이션 크레이트의 99% 이상이 unsafe 를 한 줄도 안 씁니다. 쓰는 곳은 FFI 경계(🔗 f03)와 자료구조 내부뿐입니다.
정리 — Rust 를 고르는 이유는 “빠르다”가 아니라 “빠른데 안 죽는다”입니다. CPU 를 태우거나 · 메모리를 아끼거나 · p99 를 잡아야 하는 조각에 넣으면 남는 장사이고, I/O 대기가 대부분인 코드에 넣으면 빌드 시간만 늘어납니다. 전환은 가장 뜨거운 함수 하나부터, 그리고 반드시 수치를 재서 하세요.

Tokio 내부 — work-stealing 스케줄러가 태스크를 굴리는 법

tokio::spawn 한 태스크는 그다음에 무슨 일을 겪을까요. 이 그림이 머릿속에 있으면 “왜 서버가 갑자기 멈추는지” · “워커 수를 몇으로 둘지” · “어디에 spawn_blocking 을 쓸지”가 추측이 아니라 계산이 됩니다. 🧰 t04 가 사용법이라면 여기는 구조입니다.

태스크는 스레드가 아니라 폴링 단위입니다 — 폴링 한 번이 길어지면 그 워커가 통째로 멈춥니다.

런타임을 손으로 만들어 설정하기

use tokio::runtime::Builder;

fn main() -> anyhow::Result<()> {
    let rt = Builder::new_multi_thread()
        .worker_threads(8)                 // 기본값 = 논리 코어 수
        .max_blocking_threads(256)         // spawn_blocking 풀 상한 (기본 512)
        .thread_name("svc-worker")         // 스레드 이름 ★ 프로파일에서 바로 보입니다
        .thread_stack_size(2 * 1024 * 1024)// 기본 2MB — 재귀가 깊으면 늘림
        .enable_all()                      // 타이머 + I/O 드라이버 켜기
        .build()?;

    rt.block_on(async {
        // 여기부터 async 세계
        server().await
    })
}

// 매크로 버전 — 위와 같은 일을 합니다
#[tokio::main(worker_threads = 8)]
async fn main() { /* … */ }

// 스레드 하나짜리 — 테스트 · CLI · 임베디드에 ★
#[tokio::main(flavor = "current_thread")]
async fn main() { /* … */ }
워커 수를 몇으로? — 기본값(코어 수)에서 시작하고, 컨테이너에서는 반드시 명시하세요. 쿠버네티스에서 CPU limit 이 2코어여도 Tokio 는 호스트의 64코어를 보고 워커를 64개 만듭니다 — 컨텍스트 스위칭만 늘어납니다. std::thread::available_parallelism() 도 cgroup 을 못 보는 경우가 있어 환경변수로 주입하는 편이 안전합니다.

격리하는 세 가지 방법

use tokio::task;

// ① spawn_blocking — 짧고 가끔인 블로킹 (파일 · 레거시 라이브러리)
let text = task::spawn_blocking(move || {
    std::fs::read_to_string("big.log")     // 블로킹 풀에서 실행
}).await??;                                 // JoinError + io::Error

// ② block_in_place — 지금 이 워커를 '블로킹 전용'으로 잠시 전환
//    (multi_thread 전용. 지역 큐를 다른 워커에게 넘기고 실행합니다)
let sum = task::block_in_place(|| heavy_cpu(&data));

// ③ rayon 으로 넘기고 결과만 async 로 받기 ★ CPU 작업의 정석 (⚡ e05)
let (tx, rx) = tokio::sync::oneshot::channel();
rayon::spawn(move || {
    let out = data.par_iter().map(expensive).sum::<f64>();
    let _ = tx.send(out);
});
let out = rx.await?;   // 워커는 그동안 다른 요청을 처리합니다
①과 ②의 차이 — spawn_blocking 은 다른 스레드로 보내므로 클로저가 Send + 'static 이어야 합니다. block_in_place 는 현재 스레드에서 그대로 돌기 때문에 빌린 참조를 그대로 쓸 수 있지만, current_thread 런타임에선 패닉합니다.

채널 · 액터 — Arc<Mutex> 를 안 쓰는 설계

상태를 여럿이 공유해야 할 때 대부분 Arc<Mutex<T>> 부터 꺼냅니다. 동작은 합니다. 그런데 락 경합 · 데드락 · “누가 언제 잠그는지 모르겠음”이 따라옵니다. Rust 에서 더 잘 통하는 답은 “상태를 한 태스크가 독점하고 메시지로만 말을 건다” — 액터입니다.

락은 “같은 자리를 나눠 쓰는” 설계고 액터는 “주인에게 부탁하는” 설계입니다 — 후자가 훨씬 디버깅하기 쉽습니다.

액터 — 실제로 쓰는 형태 (핸들 + 루프)

use tokio::sync::{mpsc, oneshot};
use std::collections::HashMap;

// ① 메시지 타입 — 응답이 필요하면 oneshot 을 같이 싣습니다
enum Msg {
    Incr { key: String },
    Get  { key: String, reply: oneshot::Sender<u64> },
    Snapshot { reply: oneshot::Sender<HashMap<String, u64>> },
}

// ② 액터 본체 — 상태가 그냥 지역 변수입니다 (락 없음!)
async fn run(mut rx: mpsc::Receiver<Msg>) {
    let mut counts: HashMap<String, u64> = HashMap::new();
    while let Some(msg) = rx.recv().await {
        match msg {
            Msg::Incr { key } => *counts.entry(key).or_default() += 1,
            Msg::Get { key, reply } => {
                let _ = reply.send(counts.get(&key).copied().unwrap_or(0));
            }
            Msg::Snapshot { reply } => { let _ = reply.send(counts.clone()); }
        }
    }
    // rx.recv() 가 None → 모든 송신자가 사라짐 → 여기서 정리하고 종료 ★
    tracing::info!(keys = counts.len(), "counter actor stopped");
}

// ③ 핸들 — 밖에서는 이것만 보입니다. Clone 해서 마음껏 나눠 줍니다
#[derive(Clone)]
pub struct Counter(mpsc::Sender<Msg>);

impl Counter {
    pub fn spawn() -> Self {
        let (tx, rx) = mpsc::channel(1024);
        tokio::spawn(run(rx));
        Counter(tx)
    }
    pub async fn incr(&self, key: &str) {
        let _ = self.0.send(Msg::Incr { key: key.into() }).await;
    }
    pub async fn get(&self, key: &str) -> u64 {
        let (tx, rx) = oneshot::channel();
        if self.0.send(Msg::Get { key: key.into(), reply: tx }).await.is_err() {
            return 0;                      // 액터가 죽었음
        }
        rx.await.unwrap_or(0)
    }
}
이 패턴의 진짜 이득 — Counter 를 쓰는 쪽은 락도 Arc 도 모릅니다. 나중에 “액터를 16개로 샤딩”하거나 “다른 프로세스로 분리”해도 호출부 코드가 그대로입니다. Arc<Mutex> 로 짜면 그 변경이 전부 호출부까지 번집니다.

pub struct ShardedCounter {
    shards: Vec<Counter>,        // 위에서 만든 액터 핸들 N개
}

impl ShardedCounter {
    pub fn new(n: usize) -> Self {
        Self { shards: (0..n).map(|_| Counter::spawn()).collect() }
    }
    fn pick(&self, key: &str) -> &Counter {
        let mut h = std::collections::hash_map::DefaultHasher::new();
        key.hash(&mut h);
        &self.shards[(h.finish() as usize) % self.shards.len()]
    }
    pub async fn incr(&self, key: &str) { self.pick(key).incr(key).await }
    pub async fn get(&self, key: &str) -> u64 { self.pick(key).get(key).await }
}

fn spawn_supervised(name: &'static str) -> Counter {
    let (tx, rx) = mpsc::channel(1024);
    let mut rx = Some(rx);
    tokio::spawn(async move {
        loop {
            let r = rx.take().expect("rx");
            let h = tokio::spawn(run_returning(r));
            match h.await {
                Ok(returned_rx) => { rx = Some(returned_rx); }   // 정상 종료
                Err(e) if e.is_panic() => {
                    tracing::error!(actor = name, "패닉 — 재시작");

                    break;
                }
                Err(_) => break,
            }
        }
    });
    Counter(tx)
}

규칙 하나로 요약 — select! 의 갈래에는 “중간에 버려도 아무 상태가 안 남는 것”만 두세요. 애매하면 tokio::spawn 으로 떼어 내고 JoinHandle 을 select 하면 됩니다. 이 함정은 테스트에서 거의 안 잡히고 부하가 걸릴 때만 나타나서 특히 고약합니다.
정리 — 공유 상태가 보이면 먼저 “이걸 한 태스크가 독점할 수 있나”를 물어보세요. 답이 예면 액터 + mpsc + oneshot 이고, 그 편이 락보다 읽기도 고치기도 쉽습니다. 채널은 반드시 bounded 로 만들어 백프레셔를 얻고, 큐 길이는 지연 예산으로 계산하세요. select! 에는 취소 안전한 것만 넣습니다.

동기화 고급 — 락을 고르는 기준과 락을 없애는 법

액터로 다 풀리지는 않습니다. 읽기가 압도적으로 많은 설정, 수십만 키의 캐시, 초당 수백만 번 올라가는 카운터 — 각각 정답이 다릅니다. 이 섹션은 std::sync · tokio::sync · parking_lot · DashMap · ArcSwap · 원자 연산을 “언제 무엇을”로 정리합니다.

락을 고르기 전에 “락이 정말 필요한가”를 네 번 묻습니다 — 넷 중 하나에서 대개 걸립니다.

std::sync::Mutex 와 tokio::sync::Mutex — 언제 무엇

use std::sync::Mutex as StdMutex;

// ❌ 잠근 채 await — 컴파일은 되지만 재앙입니다 (Send 에러로 막힐 때가 많음)
// let g = cache.lock().unwrap();
// let row = db.query(&g.sql).await?;   // 이 몇 ms 동안 모두가 대기

“읽기가 많으니 RwLock” 은 절반만 맞습니다

RwLock 의 숨은 비용
  ① 읽기 잠금도 '원자 연산'입니다 — 독자 수를 세야 하니까.
     여러 코어가 같은 캐시 라인을 두드립니다 (false sharing 과 같은 문제)
  ② 그래서 읽기가 짧으면 Mutex 보다 느립니다.
     경험칙 — 임계 구역이 100ns 미만이면 Mutex 가 낫습니다.
  ③ 쓰기 기아(writer starvation) 또는 그 반대가 생깁니다.
     std::RwLock 은 OS 구현에 맡기므로 플랫폼마다 다르게 굶습니다.

실측 감각 (8코어, 초당 연산 백만 단위)
  임계구역 20ns  · 읽기 99%   Mutex 승     (RwLock 은 -20~30%)
  임계구역 500ns · 읽기 99%   RwLock 승    (2~4배)
  임계구역 500ns · 읽기 80%   비슷하거나 Mutex 승
  임계구역이 길다  → 애초에 설계를 바꿀 것 (액터 · 샤딩)
실무 순서 — ① 먼저 Mutex 로 짜고 ② 재 보고 ③ 정말 읽기가 길고 많을 때만 RwLock. “읽기가 많다”는 직관만으로 RwLock 을 쓰면 대개 손해입니다.

Atomic — 메모리 순서를 고르는 법

use std::sync::atomic::{AtomicU64, AtomicBool, Ordering};

static REQS: AtomicU64 = AtomicU64::new(0);

// ① 통계 카운터 — Relaxed 로 충분합니다 (순서 보장이 필요 없음)
REQS.fetch_add(1, Ordering::Relaxed);
let n = REQS.load(Ordering::Relaxed);

// ② 플래그로 다른 데이터를 '공개'할 때 — Release/Acquire 짝 ★
static READY: AtomicBool = AtomicBool::new(false);
// 쓰는 쪽
unsafe { DATA = compute(); }
READY.store(true, Ordering::Release);      // 이 앞의 쓰기가 전부 보이게 됨
// 읽는 쪽
if READY.load(Ordering::Acquire) {         // 보이면 DATA 도 반드시 보임
    unsafe { use_data(&DATA); }
}

// ③ 확신이 없으면 SeqCst — 가장 강하고 조금 느립니다
REQS.fetch_add(1, Ordering::SeqCst);

// ④ compare_exchange — 낙관적 갱신 루프
let mut cur = REQS.load(Ordering::Relaxed);
loop {
    let next = cur.max(new_value);
    match REQS.compare_exchange_weak(cur, next,
              Ordering::Relaxed, Ordering::Relaxed) {
        Ok(_) => break,
        Err(actual) => cur = actual,       // 누가 먼저 바꿨음 → 재시도
    }
}

제로카피 — 바이트를 옮기지 않고 넘기기

네트워크 서비스가 느린 이유의 상당 부분은 계산이 아니라 같은 바이트를 서너 번 복사하는 것입니다. 소켓 버퍼 → Vec<u8> → 파싱 결과 String → 다시 직렬화 버퍼. Rust 는 소유권 덕분에 “복사 안 하고 넘기기”가 안전하게 가능한 드문 언어입니다.

fn normalize(s: &str) -> Cow<'_, str> {

use tokio::net::{TcpListener, TcpStream};
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let listener = TcpListener::bind("0.0.0.0:9000").await?;
    let token = CancellationToken::new();
    tracing::info!(addr = %listener.local_addr()?, "listening");

    loop {
        tokio::select! {
            res = listener.accept() => {
                let (sock, peer) = match res {
                    Ok(v) => v,
                    // ★ accept 실패로 루프를 끝내면 안 됩니다 (EMFILE 등)
                    Err(e) => { tracing::warn!(%e, "accept"); continue; }
                };
                sock.set_nodelay(true)?;      // 작은 응답의 지연을 없앰 ★
                let t = token.clone();
                tokio::spawn(async move {
                    if let Err(e) = serve(sock, t).await {
                        tracing::warn!(%peer, %e, "conn");
                    }
                });
            }
            _ = tokio::signal::ctrl_c() => { token.cancel(); break; }
        }
    }
    Ok(())
}
set_nodelay(true) 를 잊지 마세요 — 기본은 Nagle 알고리즘이 켜져 있어 작은 패킷을 모아 보냅니다. 요청-응답형 프로토콜에서는 응답마다 최대 40ms 가 붙습니다. “왜 로컬에서 40ms 씩 걸리지?”의 단골 원인입니다.

커스텀 코덱 — 길이 머리 + 본문

use tokio_util::codec::{Decoder, Encoder, Framed};
use bytes::{Bytes, BytesMut, Buf, BufMut};

pub struct LenCodec { max: usize }

impl Decoder for LenCodec {
    type Item = Bytes;
    type Error = std::io::Error;

    fn decode(&mut self, src: &mut BytesMut)
        -> Result<Option<Bytes>, Self::Error>
    {
        if src.len() < 4 { return Ok(None); }              // ① 길이도 안 옴
        let len = u32::from_be_bytes(src[..4].try_into().unwrap()) as usize;
        if len > self.max {                                 // ★ 반드시 상한 검사
            return Err(std::io::Error::new(
                std::io::ErrorKind::InvalidData, "frame too large"));
        }
        if src.len() < 4 + len {
            src.reserve(4 + len - src.len());               // 미리 확보(재할당 감소)
            return Ok(None);                                // ② 본문이 덜 옴
        }
        src.advance(4);                                     // 머리 버리고
        Ok(Some(src.split_to(len).freeze()))                // 본문만 떼어 냄 ★
    }
}

impl Encoder<Bytes> for LenCodec {
    type Error = std::io::Error;
    fn encode(&mut self, item: Bytes, dst: &mut BytesMut) -> Result<(), Self::Error> {
        dst.reserve(4 + item.len());
        dst.put_u32(item.len() as u32);
        dst.put_slice(&item);
        Ok(())
    }
}

while let Some(incoming) = endpoint.accept().await {
    tokio::spawn(async move {
        let conn = incoming.await?;
        // 한 연결 안에서 스트림을 여러 개 — 서로 막지 않습니다 ★
        while let Ok((mut send, mut recv)) = conn.accept_bi().await {
            tokio::spawn(async move {
                let req = recv.read_to_end(64 * 1024).await?;
                send.write_all(&handle(req)).await?;
                send.finish()?;
                anyhow::Ok(())
            });
        }
        anyhow::Ok(())
    });
}

            // ★ 버퍼의 '소유권'을 커널에 넘기고 돌려받는 방식 (완료 기반 I/O)
            let (res, buf) = stream.read(buf).await;
            let n = res?;
            let (res, _) = stream.write_all(buf.slice(..n)).await;
            res?;
            std::io::Result::Ok(())
        });
    }
}
io_uring 을 지금 도입할 것인가 — 벤치에서는 tokio 대비 작은 요청 위주일 때 20~40% 가 나오지만, 생태계가 전부 tokio 기준입니다(sqlx·reqwest·axum 전부). 실무 권고는 “프록시·캐시처럼 의존성이 거의 없는 단일 목적 서비스”에만 검토하는 것입니다.

이렇게도 쓸 수 있다 — “정확히 한 번”의 진실 🟡 중급

분산 시스템에 진짜 exactly-once 는 없습니다

가능한 것은 둘뿐입니다
  at-most-once   유실 가능 · 중복 없음      (커밋을 먼저)
  at-least-once  유실 없음 · 중복 가능      (처리를 먼저) ★ 기본값

"exactly-once" 로 불리는 것들의 정체
  ① Kafka 트랜잭션        — 같은 클러스터 안에서 읽고 쓸 때만 성립
  ② 멱등 소비 (idempotent) — 중복이 와도 결과가 같게 만드는 것 ★ 실무 정답
  ③ 결과 저장소의 트랜잭션 — 오프셋과 결과를 '같은 트랜잭션'에 쓰기

즉 현실의 답은 거의 항상 ②입니다 —
  "중복을 막는다"가 아니라 "중복이 와도 괜찮게 만든다"
멱등성 만드는 세 가지 수단 — ① 고유 키 + UPSERT(INSERT … ON CONFLICT DO UPDATE), ② 결과가 집합·최대값처럼 “다시 해도 같은 것”이 되게 설계, ③ 처리한 메시지 id 를 Redis SETNX + TTL 로 기억. ③은 TTL 안쪽의 중복만 막는다는 걸 잊지 마세요.

// [dependencies] async-stream = "0.3"
use async_stream::try_stream;
use futures::Stream;

// 페이지네이션 API 를 하나의 스트림처럼 보이게 만들기
fn all_users(client: Client) -> impl Stream<Item = anyhow::Result<User>> {
    try_stream! {
        let mut cursor: Option<String> = None;
        loop {
            let page = client.list_users(cursor.clone()).await?;
            for u in page.items {
                yield u;                       // ★ 제너레이터처럼
            }
            match page.next_cursor {
                Some(c) => cursor = Some(c),
                None => break,
            }
        }
    }
}

// 쓰는 쪽은 그냥 스트림입니다 — 페이지 개념이 사라집니다
let mut s = std::pin::pin!(all_users(client));

}

데이터 엔진 — Polars · DataFusion · Arrow

Rust 가 파이썬 세계를 가장 크게 흔든 곳이 여기입니다. Polars(DataFrame)와 DataFusion(SQL 엔진)은 둘 다 Rust 로 쓰였고, Apache Arrow 라는 공통 메모리 형식 위에 서 있습니다. 이 섹션은 “왜 Pandas 보다 빠른가”를 구조로 설명하고 실제로 돌려 봅니다.

빠른 이유는 마법이 아니라 메모리 배치 · 캐시 · SIMD · 지연 실행 네 가지입니다.

DataFusion — 내 데이터에 SQL 을 얹기

// [dependencies] datafusion = "43"
use datafusion::prelude::*;

let ctx = SessionContext::new();

// ① 파일을 테이블로 등록
ctx.register_parquet("logs", "data/**/*.parquet",
                     ParquetReadOptions::default()).await?;

// ② 그냥 SQL 을 씁니다
let df = ctx.sql("
    SELECT service,
           COUNT(*)                                  AS n,
           APPROX_PERCENTILE_CONT(latency, 0.99)     AS p99
    FROM logs
    WHERE level = 'ERROR' AND ts >= 1756000000
    GROUP BY service
    ORDER BY n DESC
    LIMIT 10
").await?;

df.show().await?;

// ③ 내 함수를 SQL 에서 부르게 만들기 (UDF)
use datafusion::logical_expr::{create_udf, Volatility};
let mask = create_udf("mask_ip", vec![DataType::Utf8], DataType::Utf8,
                      Volatility::Immutable, Arc::new(mask_impl));
ctx.register_udf(mask);
ctx.sql("SELECT mask_ip(client_ip) FROM logs LIMIT 5").await?.show().await?;

// ④ 결과를 스트림으로 받기 — 메모리 상수 유지
let mut stream = df.execute_stream().await?;
while let Some(batch) = stream.next().await {
    let batch = batch?;      // RecordBatch (Arrow)
    handle(batch);
}
Polars vs DataFusion — Polars 는 “DataFrame API 가 편한” 쪽, DataFusion 은 “SQL 과 확장이 필요한” 쪽입니다. 내 서비스에 쿼리 엔진을 내장하고 싶다면(사용자가 SQL 을 입력) DataFusion, 데이터 변환 파이프라인이면 Polars 가 보통 더 간결합니다.

CLI · 시스템 도구 — ripgrep 이 빠른 이유를 내 도구에

Rust 가 가장 조용히, 그러나 가장 널리 퍼진 곳은 커맨드라인 도구입니다. ripgrep · fd · bat · eza · zoxide · uv · ruff — 전부 Rust 입니다. 이 섹션은 그들이 빠른 구체적인 이유와, 같은 기법으로 내 도구를 만드는 법을 다룹니다.

빠른 CLI 의 비밀은 알고리즘이 아니라 할당을 안 하고 · 병렬로 · 먼저 거르는 것입니다.

clap — 서브커맨드까지 derive 로

[dependencies]
clap = { version = "4", features = ["derive", "env", "wrap_help"] }
clap_complete = "4"
use clap::{Parser, Subcommand, ValueEnum, ArgAction};
use std::path::PathBuf;

#[derive(Parser)]
#[command(name = "logtool", version, about = "로그를 훑고 집계합니다")]
struct Cli {
    /// 자세히 (-v, -vv, -vvv)
    #[arg(short, long, action = ArgAction::Count, global = true)]
    verbose: u8,

    /// 설정 파일 — 환경변수 LOGTOOL_CONFIG 로도 받습니다
    #[arg(short, long, env = "LOGTOOL_CONFIG", global = true)]
    config: Option<PathBuf>,

    #[command(subcommand)]
    cmd: Cmd,
}

#[derive(Subcommand)]
enum Cmd {
    /// 패턴을 찾습니다
    Grep {
        pattern: String,
        #[arg(default_value = ".")]
        paths: Vec<PathBuf>,
        /// 동시 처리 수 (기본: 코어 수)
        #[arg(short = 'j', long)]
        jobs: Option<usize>,
        #[arg(long, value_enum, default_value_t = Fmt::Text)]
        format: Fmt,
    },
    /// 집계합니다
    Agg {
        #[arg(long)] since: Option<String>,
        #[arg(long, num_args = 1.., value_delimiter = ',')]
        group_by: Vec<String>,
    },
}

#[derive(Copy, Clone, ValueEnum)]
enum Fmt { Text, Json, Csv }

fn main() -> anyhow::Result<()> {
    let cli = Cli::parse();
    match cli.cmd {
        Cmd::Grep { pattern, paths, jobs, format } => grep(&pattern, &paths, jobs, format),
        Cmd::Agg { since, group_by } => agg(since, &group_by),
    }
}

병렬 파일 처리 — ignore + rayon

// [dependencies] ignore = "0.4"  rayon = "1"  memchr = "2"  grep-regex/regex = "1"
use ignore::WalkBuilder;
use std::sync::mpsc;

fn grep(pattern: &str, paths: &[PathBuf], jobs: Option<usize>) -> anyhow::Result<()> {
    let re = regex::bytes::Regex::new(pattern)?;   // ★ bytes 버전 — UTF-8 검증 생략
    let (tx, rx) = mpsc::channel::<String>();
    let n = jobs.unwrap_or_else(|| std::thread::available_parallelism()
                                      .map(|v| v.get()).unwrap_or(4));

    // 출력 전담 스레드 하나 — 여기서만 stdout 을 잠급니다
    let printer = std::thread::spawn(move || {
        let stdout = std::io::stdout();
        let mut out = std::io::BufWriter::new(stdout.lock());   // ★ 버퍼링 필수
        use std::io::Write;
        for line in rx { let _ = writeln!(out, "{line}"); }
        let _ = out.flush();
    });

    // 병렬 순회 — .gitignore · 숨김 파일 규칙을 알아서 지킵니다
    WalkBuilder::new(&paths[0])
        .threads(n)
        .hidden(true).git_ignore(true).git_global(true)
        .build_parallel()
        .run(|| {
            let re = re.clone();
            let tx = tx.clone();
            Box::new(move |res| {
                let Ok(entry) = res else { return ignore::WalkState::Continue };
                if !entry.file_type().is_some_and(|t| t.is_file()) {
                    return ignore::WalkState::Continue;
                }
                if let Ok(buf) = std::fs::read(entry.path()) {
                    for m in re.find_iter(&buf) {
                        let _ = tx.send(format!("{}:{}", entry.path().display(), m.start()));
                    }
                }
                ignore::WalkState::Continue
            })
        });

    drop(tx);              // ★ 이걸 빠뜨리면 printer 가 영원히 안 끝납니다
    printer.join().unwrap();
    Ok(())
}

  Node 도구          80~200ms  (V8 부팅)
  Java 도구         200~800ms  (JVM 부팅)

  Rust 에서도 느려지는 원인
    · 큰 static 테이블을 시작할 때 초기화 → LazyLock 으로 미루기
    · 설정 파일·네트워크를 무조건 읽기 → 필요할 때만
    · 정규식을 매번 컴파일     → LazyLock<Regex> 로 한 번만 ★

use regex::Regex;

fn is_id2(s: &str) -> bool { ID.is_match(s) }

use std::sync::{Arc, Weak, Mutex};

// ❌ 부모 → 자식 → 부모 를 전부 Arc 로 하면 카운트가 0이 되지 않습니다
struct Node {
    parent: Option<Arc<Node>>,          // ★ 여기가 문제
    children: Mutex<Vec<Arc<Node>>>,
}
// 부모가 자식을 1 잡고, 자식이 부모를 1 잡음 → 서로 붙잡고 안 죽음

// ✅ 한쪽을 Weak 로 — '소유하지 않는 참조'
struct Node2 {
    parent: Option<Weak<Node2>>,        // 카운트를 올리지 않습니다
    children: Mutex<Vec<Arc<Node2>>>,
}
// 쓸 때 승격
if let Some(p) = node.parent.as_ref().and_then(|w| w.upgrade()) { /* … */ }

// 규칙: '소유 방향'을 정하고 반대 방향은 전부 Weak
//   부모가 자식을 소유 · 자식은 부모를 Weak
//   캐시가 값을 소유 · 값이 캐시를 가리키면 Weak
//   옵저버 목록은 Weak (구독자가 사라지면 자동으로 무효)

// 살아 있는 개수 확인 — 누수 감시에 유용합니다
println!("strong={} weak={}", Arc::strong_count(&a), Arc::weak_count(&a));

// ① 프로세스 RSS — 리눅스
fn rss_bytes() -> Option<u64> {
    let s = std::fs::read_to_string("/proc/self/statm").ok()?;
    let pages: u64 = s.split_whitespace().nth(1)?.parse().ok()?;
    Some(pages * 4096)
}

// ② 컨테이너 한도 안에서 얼마나 쓰는지 (cgroup v2)

임베디드 · WASM · 엣지 — 런타임이 없는 곳에서도 돕니다

Rust 에는 가비지 컬렉터도 런타임도 없습니다. 그래서 운영체제가 없는 마이크로컨트롤러, 브라우저·서버리스 WASM, 엣지 함수 처럼 다른 언어가 못 들어가는 곳에 그대로 들어갑니다. 이 섹션은 그 세 갈래의 현재 실제 상태와 시작하는 법을 정리합니다.

차이는 “무엇이 없느냐”일 뿐 언어·소유권·크레이트 대부분은 그대로입니다.

#![no_main]                 // OS 가 주는 main 진입점 없음

use panic_probe as _;       // 패닉 처리기 (필수 — 없으면 링크 에러)

use alloc::vec::Vec;

    let p = embassy_rp::init(Default::default());
    let mut led = embassy_rp::gpio::Output::new(p.PIN_25, Level::Low);

//   있음: Option Result Iterator 슬라이스 정수 연산 fmt(일부)

왜 임베디드에서 Rust 인가 — C 에서 가장 흔한 사고가 버퍼 넘침 · 널 포인터 · 인터럽트와 메인 루프의 데이터 레이스인데 셋 다 컴파일 단계에서 막힙니다. 특히 Send/Sync 와 critical-section 크레이트 조합으로 인터럽트 공유 데이터가 타입으로 강제됩니다.

// src/ingest.rs
use tokio_util::codec::{FramedRead, LinesCodec};
use tokio::net::{TcpListener, UdpSocket};
use futures::StreamExt;

pub async fn tcp(addr: &str, tx: mpsc::Sender<RawLine>) -> anyhow::Result<()> {
    let l = TcpListener::bind(addr).await?;
    loop {
        let (sock, peer) = match l.accept().await {
            Ok(v) => v,
            Err(e) => { tracing::warn!(%e, "accept"); continue; }   // h06
        };
        sock.set_nodelay(true).ok();
        let tx = tx.clone();
        tokio::spawn(async move {
            // 한 줄 = 한 로그. 최대 길이를 반드시 제한합니다
            let mut fr = FramedRead::new(sock, LinesCodec::new_with_max_length(64 * 1024));
            while let Some(line) = fr.next().await {
                match line {
                    Ok(s) => {
                        // ★ 가득 차면 기다리지 않고 버립니다 — 수신이 막히면 안 됩니다
                        if tx.try_send(RawLine::from(s)).is_err() {
                            metrics::counter!("ingest_dropped", "proto" => "tcp").increment(1);
                        }
                    }
                    Err(e) => { tracing::debug!(%peer, %e, "line"); break; }
                }
            }
        });
    }
}

pub async fn udp(addr: &str, tx: mpsc::Sender<RawLine>) -> anyhow::Result<()> {
    let sock = UdpSocket::bind(addr).await?;
    let mut buf = vec![0u8; 65_535];
    loop {
        let (n, _peer) = sock.recv_from(&mut buf).await?;
        // 이 루프에서는 절대 파싱하지 않습니다 (h06 의 철칙)
        if tx.try_send(RawLine::from_slice(&buf[..n])).is_err() {
            metrics::counter!("ingest_dropped", "proto" => "udp").increment(1);
        }
    }
}

// src/agg.rs — h03 의 액터 패턴 그대로
use std::collections::HashMap;

#[derive(Default)]
struct Bucket { count: u64, err: u64, lat: Vec<u32> }

pub async fn run(mut rx: mpsc::Receiver<Event>, redis: ConnectionManager) {
    // (분 단위 타임스탬프, 서비스명) → 버킷
    let mut buckets: HashMap<(i64, String), Bucket> = HashMap::new();
    let mut flush = tokio::time::interval(Duration::from_secs(10));

    loop {
        tokio::select! {
            Some(e) = rx.recv() => {                    // ★ 취소 안전
                let minute = e.ts - (e.ts % 60);
                let b = buckets.entry((minute, e.service.clone())).or_default();
                b.count += 1;
                if e.level >= Level::Error { b.err += 1; }
                b.lat.push(e.latency_ms);
            }
            _ = flush.tick() => {
                if buckets.is_empty() { continue; }
                // 파이프라인으로 한 번에 (h07) — 왕복이 1회
                let mut pipe = redis::pipe();
                for ((min, svc), b) in buckets.drain() {
                    let key = format!("agg:{min}");
                    pipe.hincr(&key, format!("{svc}:n"), b.count).ignore();
                    pipe.hincr(&key, format!("{svc}:e"), b.err).ignore();
                    let mut lat = b.lat; lat.sort_unstable();
                    let p99 = lat[lat.len() * 99 / 100.min(lat.len() - 1)];
                    pipe.hset(&key, format!("{svc}:p99"), p99).ignore();
                    pipe.expire(&key, 7200).ignore();       // 2시간만 보관
                }
                let mut con = redis.clone();
                if let Err(e) = pipe.query_async::<()>(&mut con).await {
                    tracing::error!(%e, "redis flush");     // 실패해도 서비스는 계속
                }
            }
            else => break,
        }
    }
}

// src/sink.rs
use tokio_stream::StreamExt;
use polars::prelude::*;

pub async fn parquet_sink(rx: mpsc::Receiver<Event>) -> anyhow::Result<()> {
    let stream = tokio_stream::wrappers::ReceiverStream::new(rx);
    // ★ "5만 건 또는 30초 중 먼저" (h07) — 둘 중 하나만 쓰면 반드시 문제가 납니다
    let mut chunks = stream.chunks_timeout(50_000, Duration::from_secs(30));

    while let Some(batch) = chunks.next().await {
        let n = batch.len();
        let t0 = std::time::Instant::now();

        // 열 단위로 뒤집습니다 (h08 의 Arrow 형식에 맞게)
        let mut ts = Vec::with_capacity(n);
        let mut svc = Vec::with_capacity(n);
        let mut lvl = Vec::with_capacity(n);
        let mut lat = Vec::with_capacity(n);
        for e in batch {
            ts.push(e.ts); svc.push(e.service); lvl.push(e.level as u8); lat.push(e.latency_ms);
        }
        let mut df = df!["ts" => ts, "service" => svc, "level" => lvl, "latency" => lat]?;

        // ★ Parquet 쓰기는 CPU 를 씁니다 → 워커를 막지 않게 격리 (h02)
        let path = partition_path(&df)?;
        tokio::task::spawn_blocking(move || -> PolarsResult<()> {
            std::fs::create_dir_all(std::path::Path::new(&path).parent().unwrap()).ok();
            ParquetWriter::new(std::fs::File::create(&path)?)
                .with_compression(ParquetCompression::Zstd(None))
                .with_statistics(StatisticsOptions::full())
                .finish(&mut df)?;
            Ok(())
        }).await??;

        metrics::histogram!("sink_batch_ms").record(t0.elapsed().as_millis() as f64);
        metrics::counter!("sink_rows").increment(n as u64);
    }
    Ok(())
}

// src/api.rs
use axum::{Router, routing::get, extract::{Query, State}, Json};

#[derive(serde::Deserialize)]
struct Q { service: String, from: i64, to: i64 }

async fn stats(State(st): State<AppState>, Query(q): Query<Q>)
    -> Result<Json<Vec<Point>>, ApiError>
{
    let now = chrono::Utc::now().timestamp();
    let hot_from = (now - 7200).max(q.from);          // 최근 2시간은 Redis

    // ① 뜨거운 구간 — Redis (밀리초)
    let mut out = redis_points(&st.redis, &q.service, hot_from, q.to).await?;

    // ② 찬 구간 — Parquet 스캔 (수백 ms) · 블로킹이므로 격리 (h02)
    if q.from < hot_from {
        let (svc, from, to) = (q.service.clone(), q.from, hot_from);
        let cold = tokio::task::spawn_blocking(move || -> PolarsResult<Vec<Point>> {
            let lf = LazyFrame::scan_parquet("data/**/*.parquet", Default::default())?
                .filter(col("service").eq(lit(svc)))
                .filter(col("ts").gt_eq(lit(from)).and(col("ts").lt(lit(to))))
                .group_by([(col("ts") / lit(60)).alias("m")])
                .agg([len().alias("n"), col("latency").mean().alias("avg")]);
            to_points(lf.collect()?)
        }).await??;
        out.splice(0..0, cold);                        // 앞에 붙입니다
    }
    Ok(Json(out))
}

pub fn router(st: AppState) -> Router {
    Router::new()
        .route("/stats", get(stats))
        .route("/healthz", get(|| async { "ok" }))
        .route("/metrics", get(|State(s): State<AppState>| async move { s.prom.render() }))
        .layer(tower_http::trace::TraceLayer::new_for_http())
        .layer(tower::limit::ConcurrencyLimitLayer::new(64))   // h03
        .layer(tower::load_shed::LoadShedLayer::new())
        .with_state(st)
}
