폴더가 아니라
크레이트와 가시성이
구조를 지킵니다

Rust 는 다른 언어보다 구조를 지키기가 쉽습니다. 모듈은 mod 로 직접 선언해야 생기고, 기본이 비공개이며, 크레이트끼리는 Cargo.toml 에 적은 방향으로만 use 할 수 있기 때문입니다. 대신 "어디서 나눌지"는 아무도 정해 주지 않습니다. 이 탭은 웹 서비스 · CLI · 데스크톱 · 라이브러리 · 워크스페이스의 권장 구조를 한 장씩 보여 주고, 각 구조에서 무엇을 어디에 두는지, 무엇을 공개하는지, 언제 다음 단계로 넘어가는지를 짧게 정리합니다. 모듈 문법 자체는 🦀 기초 탭 r09, 워크스페이스 설정은 🛠️ 빌드 탭 b05 에 있으니 여기서는 판단에 집중합니다.

STR 01

Rust 프로젝트의 공통 바탕 — 패키지 하나, 뿌리 파일 둘

유형이 달라도 바닥은 같습니다. Cargo.toml 하나가 패키지이고, 그 안의 src/lib.rs 와 src/main.rs 가 각각 크레이트의 뿌리입니다. Cargo 는 정해진 자리에 놓인 파일을 설정 없이 찾아내므로, 자리를 지키는 것만으로 빌드 · 테스트 · 예제 · 벤치가 따라옵니다.

모든 유형의 공통 골격 — Cargo 가 자동으로 찾는 자리

myapp/
├─ Cargo.toml          이름 · 의존성 · [lints]
├─ Cargo.lock          실행 파일이면 커밋 (🧰 s04)
├─ src/
│  ├─ lib.rs           라이브러리 크레이트의 뿌리 — 로직은 여기
│  ├─ main.rs          바이너리 크레이트의 뿌리 — 얇게
│  ├─ bin/
│  │  └─ migrate.rs    두 번째 실행 파일 (--bin migrate)
│  ├─ config.rs        모듈 = 파일 하나 (mod config;)
│  ├─ storage.rs       storage 모듈 본문 · 하위 모듈 선언
│  └─ storage/
│     ├─ disk.rs       storage::disk
│     └─ memory.rs     storage::memory
├─ tests/              통합 테스트 — 공개 API 만 (STR 08)
├─ examples/           cargo run --example 이름 (STR 07)
├─ benches/            cargo bench (STR 08)
└─ build.rs            있을 때만 — 컴파일 전에 실행 (STR 09)
lib.rs + main.rs 를 같이 두는 것이 기본값입니다. 패키지 이름이 myapp 이면 main.rs 는 myapp::run() 처럼 라이브러리를 남처럼 부릅니다. tests/ 의 통합 테스트도 라이브러리만 볼 수 있으므로, 로직이 main.rs 에 있으면 통합 테스트를 쓸 수 없습니다.

모듈 파일 규칙 — foo.rs + foo/ vs foo/mod.rs

// src/lib.rs — 모듈 트리는 여기서 선언해야 생깁니다
pub mod storage;   // src/storage.rs 또는 src/storage/mod.rs
mod config;        // src/config.rs

// src/storage.rs — 2018 이후 방식 ★
pub mod disk;      // src/storage/disk.rs
pub mod memory;    // src/storage/memory.rs
pub use disk::DiskStore;   // 자주 쓰는 이름은 한 층 위로 (STR 02)

// 옛 방식이라면 위 내용이 src/storage/mod.rs 에 들어갑니다.
// 컴파일러에게는 둘이 완전히 같습니다.
방식장점단점
storage.rs + storage/에디터 탭에 파일 이름이 그대로 보임 · The Book 이 먼저 소개파일과 폴더가 떨어져 정렬됨
storage/mod.rs모듈 하나가 폴더 하나에 다 들어감탭마다 mod.rs — 어느 것인지 헷갈림
둘 다 두면 빌드가 막힙니다 — storage.rs 와 storage/mod.rs 가 함께 있으면 E0761(모듈 파일이 두 곳에 있음). 어느 쪽이 "정답"이라기보다 한 크레이트 안에서 섞지 않는 것이 규칙입니다. 새 프로젝트는 2018 방식을 권하고, clippy 로 강제할 수 있습니다(STR 10). mod · use 문법과 첫 에러는 🦀 r09 참고.

규모별 진화 — 언제 다음 단계로 넘어가나 🟡 중급

초록 점이 권장 출발점 — 첫 테스트나 두 번째 실행 파일이 생기는 순간 로직을 lib.rs 로 옮깁니다.
전환신호 (하나라도 해당하면)하는 일
main.rs → 모듈 파일한 파일 500줄+ · user_ · order_ 같은 접두사 함수 묶음이 보임접두사를 모듈 이름으로: mod user;
모듈 → lib + maintests/ 에서 검증하고 싶음 · 두 번째 실행 파일 · 바인딩 계획로직을 lib.rs 로, main.rs 는 10~30줄
lib → 기능 모듈 트리모듈 15개+ · "주문 쪽 · 회원 쪽" 대화가 나옴orders.rs + orders/ · pub(crate) 경계 (STR 02)
→ 워크스페이스한 줄 고쳐도 cargo check 가 수십 초 · 배포 단위 2+ · proc-macro · 무거운 의존성 격리crates/* 로 분리 (STR 03)
숫자는 경험칙입니다 — 500줄 · 15개는 공식 기준이 아니라 "이쯤에서 대개 불편해진다"는 감각입니다. 공식으로 정해진 것은 자리(Cargo 의 자동 탐색 규칙)와 모듈 파일 규칙뿐이고, 나머지는 팀이 정해 STR 10 의 도구로 지킵니다.
정리 — 패키지 하나에 lib.rs(로직)와 main.rs(얇은 입구), 테스트 · 예제 · 벤치는 Cargo 가 찾는 자리에. 모듈 파일은 foo.rs + foo/ 로 통일하고, 테스트 · 진입점 · 빌드 시간 · 배포 단위가 늘 때마다 한 단계씩 나눕니다.
STR 02

모듈 가시성으로 경계 만들기 — 폴더 대신 pub 의 범위

다른 언어에서 "이 폴더는 건드리지 마세요"는 문서나 리뷰로 지킵니다. Rust 는 가시성 한정자가 그 일을 합니다. 한 크레이트 안의 기능 모듈 사이 경계는 pub(crate) 와 pub(super) 로, 크레이트 밖과의 경계는 pub use 재노출로 긋습니다.

동심원 — pub 은 약속입니다. 바깥 원에 올린 이름만 바꿀 때 사용자 코드가 깨집니다.

구조 — 공개 얼굴은 lib.rs 한 곳

netkit/src/
├─ lib.rs          공개 API 목록 (pub use) + prelude
├─ client.rs       pub struct Client — 공개 타입의 정의
├─ config.rs       pub struct Config
├─ error.rs        pub enum Error · pub type Result
├─ wire.rs         pub(crate) — 크레이트 내부 프로토콜
└─ wire/
   └─ crc.rs       pub(super) — wire 만 쓰는 도우미
// src/lib.rs
mod client;            // 모듈 자체는 비공개 —
mod config;            //   경로(netkit::client::…)를 약속하지 않음
mod error;
mod wire;

pub use client::Client;           // 사용자는 netkit::Client 로 씀
pub use config::Config;
pub use error::{Error, Result};

/// `use netkit::prelude::*;` 한 줄로 자주 쓰는 것 전부
pub mod prelude {
    pub use crate::{Client, Config, Error, Result};
}

안쪽 경계 — pub(crate) · pub(super)

// src/wire.rs
mod crc;                               // wire/crc.rs

pub(crate) struct Frame(Vec<u8>);     // client.rs 에서는 보이고, 밖에선 안 보임

impl Frame {
    pub(crate) fn encode(msg: &str) -> Frame {
        let mut buf = msg.as_bytes().to_vec();
        buf.extend_from_slice(&crc::crc16(&buf).to_be_bytes());
        Frame(buf)
    }
}

// src/wire/crc.rs
pub(super) fn crc16(data: &[u8]) -> u16 {  // wire 와 그 자식만
    data.iter().fold(0u16, |acc, &b| acc.rotate_left(5) ^ b as u16)  // 예시용
}

// src/client.rs
use crate::wire::Frame;                // OK — 같은 크레이트
// use crate::wire::crc::crc16;        // ❌ E0603: crc 모듈이 비공개
pub(crate) 가 몰리는 곳이 다음 크레이트 경계 후보입니다. 기능 모듈 둘이 서로의 pub(crate) 를 잔뜩 쓰면 경계가 틀린 것이고, 한 모듈이 다른 모두에게 pub(crate) 를 제공하면 그 모듈은 따로 떼어 낼 만한 바닥(core)입니다.
❌ 내부 폴더가 곧 공개 경로
// lib.rs
pub mod client;
pub mod wire;          // 내부 프로토콜까지 공개

// 사용자 코드
use netkit::client::Client;
use netkit::wire::Frame;   // 이제 Frame 을 못 바꿈
// → client.rs 를 쪼개는 순간 모든 사용자가 깨짐
✅ 모듈은 비공개, 이름만 평평하게
// lib.rs
mod client;
mod wire;
pub use client::Client;

// 사용자 코드
use netkit::Client;
// → client.rs 를 client/ 폴더로 쪼개도
//   lib.rs 의 pub use 한 줄만 고치면 됨
한정자보이는 범위구조에서의 쓰임
(없음)선언한 모듈과 그 자식모든 것의 기본값 — 일단 여기서 시작
pub(super)부모 모듈까지orders/ 안 파일끼리만 쓰는 도우미
pub(in crate::orders)지정한 조상 모듈까지깊은 트리에서 경계를 정확히 — 드물게
pub(crate)크레이트 전체기능 모듈 사이의 내부 API · 공용 타입
pub (+ pub use)크레이트 밖라이브러리의 약속 · 워크스페이스의 다른 크레이트
prelude 는 관례이지 의무가 아닙니다 — std 의 std::prelude 를 흉내 낸 것으로, 트레이트를 많이 가져와야 쓸 수 있는 크레이트 (예: diesel::prelude · bevy::prelude)에서 빛납니다. 공개 이름이 열 개 남짓이면 pub use 만으로 충분합니다. 비공개 모듈 안의 pub 이 실제로 밖에 닿는지는 rustc 의 unreachable_pub 린트가 짚어 줍니다(STR 10).
정리 — 모듈은 비공개로 선언하고 공개 이름은 lib.rs 의 pub use 로 평평하게. 기능 모듈 사이는 pub(crate), 폴더 안 도우미는 pub(super). 가시성이 곧 경계라서, 경계를 어기면 리뷰가 아니라 컴파일러가 막습니다.
STR 03

Cargo 워크스페이스 — crates/* 와 의존 방향

워크스페이스 명령 · xtask · "언제 나눌 것인가"의 기본은 🛠️ b05 와 🧰 s04 에 있습니다. 여기서는 그 위에 폴더를 어떻게 배치하고, 버전 · 메타데이터 · 린트를 루트에서 어떻게 물려주고, 크레이트 사이 화살표를 어느 쪽으로 둘지만 봅니다. Rust 에서는 크레이트 경계가 곧 컴파일러가 지키는 경계입니다 — Cargo.toml 에 적지 않은 크레이트는 use 자체가 안 됩니다.

평평한 crates/ — 폴더 이름 = 패키지 이름

shop/
├─ Cargo.toml             가상 매니페스트 — [workspace] 만, [package] 없음
├─ Cargo.lock             워크스페이스에 하나 (전원이 같은 버전)
├─ target/                하나 — 빌드 캐시 공유
├─ deny.toml              의존 규칙 (STR 10)
├─ crates/
│  ├─ shop-domain/        규칙 · 타입 — 의존성 최소
│  ├─ shop-infra/         sqlx · reqwest 구현
│  ├─ shop-api/           axum 라우터 · 핸들러
│  ├─ shop-server/        bin — main.rs 30줄
│  └─ shop-cli/           bin — 운영 도구
└─ xtask/                 빌드 자동화 (🛠️ b05)
한 단계 깊이로 평평하게 — crates/backend/db/ 처럼 중첩하면 members 글롭과 경로가 복잡해지고 찾기도 어렵습니다. rust-analyzer 저장소가 이 방식(crates/* 한 층, 폴더 이름 = 패키지 이름)으로 크레이트 수십 개를 운영합니다. 규칙이라기보다 널리 따르는 관례입니다.

루트에서 물려주기 — 버전 · 메타 · 린트

# shop/Cargo.toml
[workspace]
resolver = "3"           # edition 2024 짝 — 가상 매니페스트는 직접 적어야 합니다
members  = ["crates/*", "xtask"]

[workspace.package]
version      = "0.4.0"
edition      = "2024"
rust-version = "1.85"
license      = "MIT OR Apache-2.0"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
sqlx  = { version = "0.8", default-features = false, features = ["runtime-tokio", "postgres"] }
shop-domain = { path = "crates/shop-domain" }   # 내부 크레이트도 이름 하나로
shop-infra  = { path = "crates/shop-infra" }

[workspace.lints.rust]
unsafe_code     = "deny"
unreachable_pub = "warn"            # STR 02 — 밖에 안 닿는 pub 찾기

[workspace.lints.clippy]
all         = { level = "warn", priority = -1 }   # 묶음은 priority 를 낮춰야
unwrap_used = "warn"                               #   개별 설정이 이깁니다
# crates/shop-infra/Cargo.toml
[package]
name = "shop-infra"
version.workspace      = true
edition.workspace      = true
rust-version.workspace = true
license.workspace      = true

[dependencies]
shop-domain.workspace = true
sqlx = { workspace = true, features = ["uuid"] }  # 기능은 더할 수만 · 버전은 못 바꿈
tokio.workspace = true

[lints]
workspace = true      # ★ 이 줄이 없으면 [workspace.lints] 가 적용되지 않습니다
의존 그래프 — 화살표가 한쪽(domain)으로만 흐르면 바닥을 바꾸지 않고 위를 갈아 끼울 수 있습니다.

크레이트를 쪼개는 기준 🟡 중급

기준이럴 때 쪼갭니다주의
컴파일 시간크레이트가 병렬 · 증분 컴파일의 단위입니다. 자주 바뀌는 코드와 무거운 의존성(sqlx 매크로 · 거대한 생성 코드)을 떼면 한 줄 수정에 다시 도는 범위가 줄어듭니다쪼개기 전에 cargo build --timings 로 실제 병목 확인 (🛠️ b10)
재사용실행 파일이 둘 이상(server · cli · worker), 파이썬 · Node 바인딩이 같은 로직을 씀"언젠가 쓸지도"는 신호가 아닙니다
경계"domain 은 sqlx 를 몰라야 한다"를 리뷰가 아니라 빌드로 지키고 싶음한 크레이트 안의 모듈로는 방향을 강제할 수 없음 — 그래서 쪼갬
강제 사항절차 매크로(proc-macro = true)는 반드시 별도 크레이트 (🔬 d09)매크로 크레이트는 shop-macros 처럼 이름으로 드러냄
❌ 버전이 멤버마다 흩어짐
# crates/shop-api/Cargo.toml
serde = "1.0.190"
# crates/shop-infra/Cargo.toml
serde = { version = "1", features = ["derive"] }
# → 올릴 때 파일 다섯 개를 고치고 하나는 빠뜨림
# → 린트도 멤버마다 달라 경고 기준이 제각각
✅ 루트에 한 번, 멤버는 workspace = true
# 루트 [workspace.dependencies] 에 serde 한 줄
# 멤버는
serde.workspace = true
[lints]
workspace = true
# → 버전 · 기능 · 린트 정책이 한 파일에서 보임
멤버의 [lints] 는 전부 아니면 전무 — workspace = true 와 개별 린트를 같은 표에 섞으면 Cargo 가 거부합니다. 한 크레이트만 예외가 필요하면 코드에 #![allow(...)] 를 이유와 함께 붙이세요. [workspace.lints] 는 Rust 1.74 부터, resolver = "3" 은 1.84 부터 씁니다.
정리 — crates/* 한 층에 폴더 이름 = 패키지 이름, 버전 · 메타 · 린트는 루트에서 물려줍니다. 화살표는 전부 domain 쪽으로 — 쪼개는 이유는 컴파일 시간 · 재사용 · 경계 셋 중 하나여야 합니다.
STR 04

Axum 웹 서비스 — 한 크레이트 안의 routes · handlers · domain · repo

Router · 추출기 · 레이어가 맞물리는 원리는 🌐 w02, 워크스페이스로 나눈 큰 서비스의 골격 · AppState · 설정은 🌐 w03 에 있습니다. 이 섹션은 그 앞 단계 — 크레이트 하나로 시작하는 서비스에서 파일을 어떻게 나누고, 기능별 Router 를 어떻게 합치고, AppState 를 어디에 둘지입니다. 대부분의 서비스는 여기서 시작해 한참을 이 모양으로 삽니다.

AppState 는 크레이트 뿌리의 state.rs — main.rs 가 만들고, lib.rs 의 app() 이 with_state 로 딱 한 번 주입합니다. 하위 라우터는 전부 Router<AppState> 를 돌려주기만 합니다. 필드 구성(풀은 Arc 없이, 큰 설정은 Arc)은 🌐 w03 참고.

기능별 Router 합치기 — nest · merge

// src/lib.rs
pub mod config;
pub mod error;
pub mod state;
mod domain;
mod handlers;
mod repo;
mod routes;

pub use state::AppState;

pub fn app(state: AppState) -> axum::Router {
    routes::router().with_state(state)   // Router<AppState> → Router
}

// src/routes.rs
use axum::{routing::get, Router};
use crate::{handlers, state::AppState};

pub(crate) fn router() -> Router<AppState> {
    Router::new()
        .route("/health", get(handlers::health))
        .nest("/api/users", users())      // 접두사를 붙여 끼움
        .merge(admin())                   // 접두사 없이 합침
}

fn users() -> Router<AppState> {
    use handlers::users::*;
    Router::new()
        .route("/", get(list).post(create))
        .route("/{id}", get(get_one))     // 0.8 경로 문법 {id}
}

fn admin() -> Router<AppState> {
    Router::new().route("/admin/stats", get(handlers::admin_stats))
}
// src/handlers/users.rs — 얇게: 꺼내고, 부르고, 돌려준다
use axum::{extract::{Path, State}, Json};
use crate::{domain::user::User, error::AppError, repo, state::AppState};

pub(crate) async fn get_one(
    State(st): State<AppState>,
    Path(id): Path<i64>,
) -> Result<Json<User>, AppError> {
    let user = repo::users::find(&st.db, id).await?   // sqlx::Error → AppError (From)
        .ok_or(AppError::NotFound)?;
    Ok(Json(user))
}
// list · create 와 handlers.rs 의 health · admin_stats 는 같은 모양이라 생략

규모구조넘어가는 신호
엔드포인트 ~10개위의 계층 폴더 (routes · handlers · domain · repo)한 폴더에 파일 10개+ · 기능 하나 고치는데 폴더 셋
기능 5개 이상기능 모듈 (coupons.rs + coupons/) · 기능 안은 pub(super)domain 에 sqlx 가 새어 들어옴 · 두 번째 실행 파일
여러 실행 파일 · 팀워크스페이스 domain · infra · api · bin (🌐 w03 · STR 03)—
Axum 0.8 의 nest — 루트("/")나 빈 경로에 nest 하면 패닉합니다. 접두사 없이 합칠 때는 merge 를 쓰세요. 합치는 라우터들은 같은 상태 타입(Router<AppState>)이어야 하고, with_state 는 맨 바깥에서 한 번만 부릅니다.
정리 — lib.rs 의 app(state) 가 입구, routes.rs 가 지도, 핸들러는 얇게, 규칙은 domain, SQL 은 repo. 기능이 늘면 기능 모듈로, 방향을 빌드로 지켜야 하면 크레이트로 넘어갑니다.
STR 05

CLI 도구 — main 은 얇게, 로직은 lib 에

clap 사용법은 🧰 t03, 빠른 CLI 의 요령과 배포는 🚀 h09 에 있습니다. 여기서는 파일 배치만 봅니다 — #[derive(Parser)] 구조체를 어디에 두고, 서브커맨드를 어떻게 모듈로 나누고, 왜 main.rs 를 열 줄로 줄이는지. 이유는 하나입니다: 로직이 라이브러리에 있어야 함수로 바로 테스트하고, 나중에 GUI · 서버에서도 재사용할 수 있습니다.

서브커맨드가 있는 CLI

mytool/
├─ Cargo.toml
├─ src/
│  ├─ main.rs          10줄 — parse → run → 종료 코드
│  ├─ lib.rs           pub fn run(cli: Cli) -> anyhow::Result<()>
│  ├─ cli.rs           #[derive(Parser)] Cli · Command · 각 Args
│  ├─ commands.rs      pub(crate) mod init; pub(crate) mod sync;
│  ├─ commands/
│  │  ├─ init.rs       pub(crate) fn run(args: &InitArgs)
│  │  └─ sync.rs
│  ├─ config.rs        설정 파일 읽기 (🧰 t09)
│  └─ output.rs        사람용 텍스트 / --json 출력을 한곳에
└─ tests/
   └─ cli.rs           실제 바이너리 실행 (assert_cmd)
// src/main.rs — 하는 일은 셋: 파싱 · 위임 · 종료 코드
use clap::Parser;
use mytool::cli::Cli;
use std::process::ExitCode;

fn main() -> ExitCode {
    match mytool::run(Cli::parse()) {
        Ok(()) => ExitCode::SUCCESS,
        Err(e) => {
            eprintln!("오류: {e:#}");     // anyhow 의 원인 사슬까지 한 줄로
            ExitCode::FAILURE
        }
    }
}

clap 구조체는 cli.rs, 실행은 commands/

// src/cli.rs — 명령행 스펙만. 로직 없음
use clap::{Args, Parser, Subcommand};
use std::path::PathBuf;

#[derive(Debug, Parser)]
#[command(name = "mytool", version, about = "저장소 동기화 도구")]
pub struct Cli {
    /// 자세히 출력
    #[arg(short, long, global = true)]
    pub verbose: bool,
    #[command(subcommand)]
    pub command: Command,
}

#[derive(Debug, Subcommand)]
pub enum Command {
    /// 설정 파일 만들기
    Init(InitArgs),
    /// 원격과 동기화
    Sync(SyncArgs),
}

#[derive(Debug, Args)]
pub struct InitArgs {
    #[arg(long, default_value = "mytool.toml")]
    pub path: PathBuf,
}

#[derive(Debug, Args)]
pub struct SyncArgs {
    #[arg(long)]
    pub dry_run: bool,
}

// src/lib.rs
pub mod cli;
mod commands;
mod config;
mod output;

use cli::{Cli, Command};

pub fn run(cli: Cli) -> anyhow::Result<()> {
    match cli.command {
        Command::Init(args) => commands::init::run(&args),
        Command::Sync(args) => commands::sync::run(&args, cli.verbose),
    }
}

#[cfg(test)]
mod tests {
    use super::cli::Cli;
    use clap::{CommandFactory, Parser};

    #[test]
    fn cli_spec_is_valid() {
        Cli::command().debug_assert();   // 인자 정의 충돌을 테스트에서 잡음
    }

    #[test]
    fn parses_sync() {
        let cli = Cli::try_parse_from(["mytool", "sync", "--dry-run"]).unwrap();
        assert!(matches!(cli.command, super::Command::Sync(ref a) if a.dry_run));
    }
}
좌우 대조 — main.rs 를 얇게 두면 로직이 라이브러리가 되고, 테스트와 재사용이 공짜로 따라옵니다.
무엇을어디에이유
clap derive 구조체cli.rs (pub mod cli)main · 테스트 · 셸 자동완성 생성(build.rs 나 xtask)이 함께 씀
서브커맨드 실행commands/이름.rs 의 run(&Args)명령 하나 = 파일 하나 · 추가 · 삭제가 파일 단위
출력 형식output.rsprintln! 이 흩어지면 --json 을 붙일 수 없음
종료 코드 · 에러 표시main.rs 만라이브러리는 Result 를 돌려줄 뿐 exit 하지 않음
바이너리 자체를 검사하고 싶을 때 — 통합 테스트(tests/)에는 Cargo 가 CARGO_BIN_EXE_mytool 환경 변수로 빌드된 실행 파일 경로를 넘겨 줍니다. assert_cmd 가 이를 감싸 종료 코드 · 표준 출력을 검사합니다. 로직 테스트는 lib 에서, 바이너리 테스트는 "인자가 제대로 이어지나" 정도만. 도구가 커져 GUI 나 서버가 같은 로직을 쓰게 되면 lib 을 crates/mytool-core 로 떼어 워크스페이스로 넘어갑니다(STR 03).
정리 — cli.rs 에 clap 구조체, commands/ 에 명령마다 파일 하나, main.rs 는 파싱 · 위임 · 종료 코드 세 가지만. exit 는 main 에서만 하고, 로직은 라이브러리 함수로 테스트합니다.
STR 06

Tauri 데스크톱 — src-tauri 와 프런트 분리, commands 모듈

만들어진 폴더 하나하나의 뜻은 🖥️ u02, 커맨드 · IPC 는 u03, 권한은 u06, 실전 앱의 전체 구조는 u13 에 있습니다. 여기서는 앱이 커질 때 Rust 쪽 파일을 어떻게 나누고, 로직을 언제 UI 없는 크레이트로 떼는지만 짧게 봅니다.

트리 — 프런트와 Rust 는 invoke 로만 만나고, 무거운 로직은 UI 를 모르는 core 로 내려갑니다.

src-tauri/src — 커맨드는 모듈로

src-tauri/src/
├─ main.rs            my_app_lib::run() 만 (데스크톱 진입점)
├─ lib.rs             Builder · 플러그인 · invoke_handler 등록
├─ commands.rs        pub mod files; pub mod settings;
├─ commands/
│  ├─ files.rs        #[tauri::command] pub async fn …
│  └─ settings.rs
├─ state.rs           AppState (.manage)
└─ error.rs           Serialize 되는 에러 — 프런트가 받음
// src-tauri/src/lib.rs
mod commands;
mod error;
mod state;

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .manage(state::AppState::default())
        .invoke_handler(tauri::generate_handler![
            commands::files::list_dir,        // 모듈 경로 그대로
            commands::settings::get_settings,
        ])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

# src-tauri/Cargo.toml

커맨드를 lib.rs 에 두고 pub 을 붙이면 매크로가 만드는 글루 코드 이름이 겹쳐 빌드가 깨집니다(Tauri 공식 문서의 제약). 커맨드는 별도 모듈에 pub fn 으로 두고 generate_handler! 에 경로로 등록하세요 — 위 구조가 그 모양입니다.
core 로 떼는 신호 — 커맨드 함수 안에 수백 줄이 생김 · 같은 로직을 CLI 나 서버에서도 쓰고 싶음 · Tauri 없이 단위 테스트하고 싶음. 커맨드는 "core 를 부르고 에러를 프런트용으로 바꾸는" 얇은 어댑터로 남깁니다. 권한(capabilities/*.json)은 창 단위로 쪼개 u06 처럼 관리합니다.
정리 — 프런트는 src/, Rust 는 src-tauri/, 실제 구성은 lib.rs 의 run(). 커맨드는 commands/ 모듈에 pub fn 으로, 로직이 커지면 UI 없는 core 크레이트로 내립니다.
STR 07

라이브러리 크레이트 — 공개 API · feature · semver

앱은 내가 쓰고 내가 고칩니다. 라이브러리는 남이 쓰고, 내가 바꾸면 남의 빌드가 깨집니다. 그래서 라이브러리 구조의 핵심은 폴더가 아니라 "무엇을 약속했나"를 한눈에 보이게 하는 것입니다. feature 문법과 cargo-hack 은 🛠️ b04, 문서 테스트 문법은 🦀 r11 에 있습니다.

공개 라이브러리 한 벌

fastparse/

├─ README.md           첫 예제 = examples/basic.rs 와 같게
├─ CHANGELOG.md        semver 약속의 기록
├─ src/

feature 는 더하기만 — additive 원칙

# fastparse/Cargo.toml
[features]
default    = ["json"]
json       = ["dep:serde_json"]          # dep: — 의존성 이름이 feature 로 새지 않게
serde      = ["dep:serde"]
tls-rustls = ["dep:rustls"]
tls-native = ["dep:native-tls"]

[dependencies]
serde_json = { version = "1", optional = true }
serde      = { version = "1", optional = true, features = ["derive"] }
rustls     = { version = "0.23", optional = true }
native-tls = { version = "0.2", optional = true }

[package.metadata.docs.rs]
all-features = true                      # docs.rs 에 모든 API 를 보이게
// src/lib.rs — feature 가 켜지면 "생기기만" 합니다
#[cfg(feature = "json")]
mod json;
#[cfg(feature = "json")]
pub use json::to_json;

// 둘 다 켜져도 빌드는 되어야 합니다 — 우선순위로 고르기
// (rustls_backend · native_backend 모듈은 각 feature 게이트 아래에 있다고 가정)
#[cfg(feature = "tls-rustls")]
type Tls = rustls_backend::Backend;
#[cfg(all(feature = "tls-native", not(feature = "tls-rustls")))]
type Tls = native_backend::Backend;
feature 는 의존 그래프 전체에서 합쳐집니다 — 내 크레이트를 쓰는 A 가 tls-rustls, B 가 tls-native 를 켜면 한 빌드에 둘 다 켜집니다. 그래서 "켜면 기능이 사라지는" feature 나 compile_error! 로 막는 상호 배타 feature 는 남의 빌드를 깨뜨립니다. no_std 도 같은 이유로 std feature 를 켜는 쪽으로 설계합니다.
해부도 — 공개 이름은 lib.rs 한 파일에서 전부 보여야 합니다. 그래야 리뷰에서 "약속이 늘었나"를 바로 압니다.
규칙왜도구 · 표기
확장할 enum · 구조체에 #[non_exhaustive]나중에 변형 · 필드를 더해도 메이저 버전이 아님 (밖에서는 _ 갈래 필수 · 리터럴 생성 불가)pub enum Error 에 거의 항상
공개 구조체 필드는 신중히pub 필드는 이름 · 타입 모두 약속. 생성자 + 게터가 바꾸기 쉬움설정류는 빌더 패턴
예제는 실행되게/// 예제는 cargo test 가 컴파일 · 실행 — 문서가 낡으면 빌드가 깨짐네트워크 예제는 no_run
feature 조합 검사기본값에서만 빌드되는 조합 함정cargo hack check --feature-powerset (🛠️ b04)
게시 전 semver 검사"패치 버전인데 함수를 지웠다"를 사람이 놓침cargo semver-checks — crates.io 의 직전 버전과 공개 API 비교
정리 — 구현 모듈은 비공개, 공개 이름은 lib.rs 의 pub use 목차로, 확장할 타입엔 #[non_exhaustive]. feature 는 켜면 생기기만 하게, 게시 전에는 cargo semver-checks 로 약속이 깨졌는지 기계에게 묻습니다.
STR 08

테스트 위치 — 같은 파일 · tests/ · 벤치가 보는 범위

Rust 는 테스트를 어디에 두느냐가 무엇을 볼 수 있느냐를 정합니다. 같은 파일의 mod tests 는 비공개 함수까지, tests/ 의 파일은 남의 크레이트처럼 공개 API 만 봅니다. 문법과 하네스 내부는 🦀 r11, 서버 테스트는 🌐 w11 에 있습니다.

단위 테스트 — 같은 파일 맨 아래

// src/billing.rs
fn split(total: i64, n: i64) -> (i64, i64) {   // 비공개 — 몫 · 나머지
    (total / n, total % n)
}

pub fn per_person(total: i64, n: i64) -> i64 {
    let (q, r) = split(total, n);
    if r > 0 { q + 1 } else { q }                // 남는 돈은 올림
}

#[cfg(test)]                    // cargo test 때만 컴파일
mod tests {
    use super::*;               // 부모의 비공개 항목까지 보입니다

    #[test]
    fn split_keeps_remainder() {
        assert_eq!(split(10_000, 3), (3333, 1));
    }

    #[test]
    fn rounds_up() {
        assert_eq!(per_person(10_000, 3), 3334);
    }
}
테스트가 길어져 본문이 안 보이면 #[cfg(test)] mod tests; 로 선언만 남기고 src/billing/tests.rs 로 옮깁니다 — 여전히 자식 모듈이라 비공개 항목이 보입니다.

통합 테스트 — tests/ 는 파일마다 별도 크레이트

tests/
├─ common/
│  └─ mod.rs        공용 헬퍼 — tests/common.rs 로 두면
│                   "테스트 0개" 크레이트가 하나 더 생김
├─ checkout.rs      → 테스트 실행 파일 1
└─ refund.rs        → 테스트 실행 파일 2 (링크도 따로)

# 파일이 많아져 링크 시간이 길면 하나로 묶기
tests/
└─ it/
   ├─ main.rs       mod common; mod checkout; mod refund;
   ├─ common.rs
   ├─ checkout.rs
   └─ refund.rs     → 실행 파일 1개
// tests/common/mod.rs
#![allow(dead_code)]        // 헬퍼를 안 쓰는 테스트 파일에서 경고 방지
pub fn sample_total() -> i64 { 10_000 }

// tests/checkout.rs
mod common;
use shop::per_person;       // lib.rs 의 pub use billing::per_person; 덕분
                            // shop::billing::split 은 불가 — 비공개

#[test]
fn split_bill_three_ways() {
    assert_eq!(per_person(common::sample_total(), 3), 3334);
}
매트릭스 — 아래 세 줄은 별도 크레이트로 컴파일되므로 공개 API 만 봅니다. 이것이 lib.rs 를 두는 가장 실용적인 이유입니다.

문서/// · //! 코드 블록README · 문서 예제가 지금도 컴파일되나
바이너리tests/cli.rs + CARGO_BIN_EXE_이름인자 · 종료 코드 (STR 05)
벤치benches/*.rs + [[bench]] harness = false성능 회귀 — criterion (⚡ e01)
워크스페이스 전체 시나리오테스트 전용 크레이트 crates/shop-e2e여러 크레이트를 엮는 흐름 — 각 크레이트의 tests/ 에 흩지 않음
정리 — 비공개 로직은 같은 파일의 mod tests, 공개 API 시나리오는 tests/, 공용 헬퍼는 tests/common/mod.rs. 통합 테스트 파일이 많아 느리면 tests/it/main.rs 하나로 묶습니다.
STR 09

빌드 스크립트 · FFI · 생성 코드 — build.rs · OUT_DIR · *-sys

C 라이브러리를 붙이거나, 프로토콜 정의 · 표에서 코드를 만들어야 하면 컴파일 전에 도는 코드가 필요합니다. Rust 에서 그 자리는 패키지 루트의 build.rs 하나이고, 생성물은 OUT_DIR 에만 씁니다. bindgen · cbindgen 의 사용법은 🔗 f08 · f04 에 있으니, 여기서는 파일을 어디에 두는지만 봅니다.

파이프라인 — build.rs 는 앞칸에서 한 번 돌고, 본체는 OUT_DIR 의 결과만 끌어옵니다.

표에서 코드 만들기 — OUT_DIR 로

errcodes/
├─ Cargo.toml
├─ build.rs              패키지 루트 (src/ 안이 아님)
├─ schema/codes.txt      NOT_FOUND=404 처럼 한 줄씩
└─ src/
   ├─ lib.rs
   └─ codes.rs           include!(…/codes.rs) 한 줄
// build.rs — 작업 디렉터리는 패키지 루트입니다
use std::{env, fs, path::Path};

fn main() {
    println!("cargo::rerun-if-changed=schema/codes.txt");   // 이 파일이 바뀔 때만 재실행

    let src = fs::read_to_string("schema/codes.txt").unwrap();
    let mut out = String::from("pub const CODES: &[(&str, u16)] = &[\n");
    for line in src.lines().filter(|l| !l.trim().is_empty()) {
        let (name, code) = line.split_once('=').expect("NAME=CODE 형식");
        out.push_str(&format!("    ({:?}, {}),\n", name.trim(), code.trim()));
    }
    out.push_str("];\n");

    let dest = Path::new(&env::var("OUT_DIR").unwrap()).join("codes.rs");
    fs::write(dest, out).unwrap();
}

// src/codes.rs
include!(concat!(env!("OUT_DIR"), "/codes.rs"));
cargo:: 두 콜론 문법은 Rust 1.77 부터입니다. MSRV 가 그보다 낮으면 옛 문법 cargo:rerun-if-changed= 를 씁니다. build.rs 가 쓰는 크레이트는 [build-dependencies] 에 따로 적습니다.

*-sys 관례 — 원시 FFI 와 안전한 래퍼를 둘로

fastlz/                    워크스페이스 (예시 이름)
├─ fastlz-sys/
│  ├─ Cargo.toml           links = "fastlz" · [build-dependencies] cc
│  ├─ build.rs             C 소스 컴파일 또는 시스템 라이브러리 찾기
│  ├─ vendor/fastlz.c      번들한 C 소스 (git submodule 이 흔함)
│  └─ src/lib.rs           extern "C" 선언만 — 전부 unsafe
└─ fastlz/
   ├─ Cargo.toml           fastlz-sys 에 의존
   └─ src/lib.rs           안전한 API — Result · 소유권 · Drop
// fastlz-sys/build.rs
fn main() {
    println!("cargo::rerun-if-changed=vendor/fastlz.c");
    cc::Build::new()
        .file("vendor/fastlz.c")
        .compile("fastlz");       // 정적 라이브러리를 만들고 링크 지시까지 출력
}
왜 둘로 나누나 — links = "fastlz" 는 "이 네이티브 라이브러리를 링크하는 크레이트는 그래프 전체에 하나"를 Cargo 가 보장하게 합니다. 다른 안전한 래퍼를 쓰고 싶은 사람도 같은 -sys 를 공유하면 링크 충돌이 없습니다. 이름 끝의 -sys 는 crates.io 의 관례입니다.
생성 코드를 어디에언제주의
OUT_DIR (커밋 안 함)입력이 저장소 안에 있고 생성 도구가 가벼움 · prost-build 같은 코드 생성기 (🌐 w09)사용자 PC 에도 생성 도구가 필요 (bindgen 이면 libclang)
src/generated/ (커밋)생성 도구가 무겁거나 드물게 바뀜 · 사용자에게 도구를 요구하고 싶지 않음xtask 로 재생성 · CI 에서 "다시 생성해도 diff 0" 검사
생성 전용 크레이트워크스페이스에서 생성 코드가 큼 (shop-proto)그 크레이트만 다시 돌아 증분 빌드가 빨라짐
정리 — build.rs 는 패키지 루트에, 결과는 OUT_DIR 에, 재실행 조건은 rerun-if-changed 로. 네이티브 라이브러리는 foo-sys(원시) + foo(안전) 둘로 나눕니다.
STR 10

한 장 요약 — 유형 · 규모별 권장 구조와 규칙 강제

앞의 아홉 섹션을 표 한 장과 질문 세 개로 줄입니다. 그리고 정한 규칙을 문서가 아니라 Cargo · 린트 · cargo-deny 가 지키게 만드는 법으로 끝냅니다. Rust 는 크레이트 경계 자체가 강제 수단이라 다른 언어보다 도구가 적게 듭니다.

질문 셋이면 시작 구조가 정해집니다 — 대부분의 답은 "lib.rs + 얇은 main.rs"입니다.

구조 규칙을 도구로 강제하기 🟡 중급

린트 — 루트에 한 번 (STR 03 의 [workspace.lints])

[workspace.lints.rust]
unsafe_code     = "deny"       # 필요한 모듈만 #![allow(unsafe_code)] — forbid 면 아무도 못 풂 (🔬 d01)
unreachable_pub = "warn"       # 밖에 안 닿는 pub → pub(crate) 로 (STR 02)

[workspace.lints.clippy]
all              = { level = "warn", priority = -1 }
mod_module_files = "warn"      # mod.rs 를 쓰면 경고 — foo.rs + foo/ 로 통일 (STR 01)
unwrap_used      = "warn"      # 테스트는 clippy.toml 의 allow-unwrap-in-tests = true 로 예외

cargo-deny — "이 크레이트는 저 의존성을 직접 쓰지 마"

# deny.toml (워크스페이스 루트)
[bans]
multiple-versions = "warn"           # 같은 크레이트 두 버전 = 빌드 시간 · 크기 낭비
deny = [
    # sqlx 는 infra 크레이트만 직접 의존할 수 있습니다
    { crate = "sqlx", wrappers = ["shop-infra"] },
    { crate = "openssl" },           # rustls 로 통일
]

[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause", "Unicode-3.0"]
wrappers 는 "금지된 크레이트를 직접 의존해도 되는 크레이트 목록"입니다 — domain 이나 api 가 sqlx 를 끌어오면 cargo deny check bans 가 실패합니다. 최근 cargo-deny 문법 기준이며, 오래된 버전은 crate 대신 name 을 씁니다. 실행 전 cargo deny init 으로 만든 기본 파일과 맞춰 보세요.

CI 한 단계 — 구조 검사 묶음

강제 수단무엇을 막나비용
가시성 (pub(crate) 등)모듈 경계 밖 접근 — 컴파일 에러0
크레이트 의존 선언선언 안 한 방향 · 순환 — 빌드 거부크레이트 분리 비용
[workspace.lints]unsafe · unwrap · 모듈 파일 방식 · 불필요한 pub설정 몇 줄
cargo-deny금지 의존 · 직접 의존 제한 · 라이선스 · 취약점deny.toml 유지
cargo-machete안 쓰는 의존성 (빌드 시간)가끔 오탐 — 메타데이터로 무시 지정
cargo-machete 는 소스를 문자열로 훑는 방식이라 매크로 안에서만 쓰는 의존성을 "안 쓴다"고 볼 수 있습니다. 그런 크레이트는 [package.metadata.cargo-machete] ignored = ["이름"] 으로 빼고, 더 정확한 검사가 필요하면 nightly 의 cargo-udeps 를 씁니다(🛠️ b10).
정리 — 시작은 대부분 lib.rs + 얇은 main.rs, 실행 파일이 둘이 되면 워크스페이스. 경계는 가시성과 크레이트 의존 선언이 먼저 지키고, 나머지는 [workspace.lints] · cargo-deny · cargo-machete 를 CI 에 걸어 리뷰가 아니라 빌드가 지키게 합니다.
