왜 Rust 로 만드나 — 판단 기준이 먼저

가장 중요한 결정은 “Rust 로 안 만든다”일 때가 많습니다. 네이티브 확장은 빌드·배포·디버깅 비용이 함께 따라옵니다. 측정으로 시작하고, 대안을 먼저 세어 본 뒤 그래도 남는 경우에만 만드세요.

손익분기점 계산

모델 (직접 재서 값을 채우세요 · ⚡ e01)

  파이썬 실행 시간      T_py
  Rust 실행 시간        T_rs        (보통 T_py / 10 ~ / 200)
  경계 통과 비용        C ≈ 0.1 ~ 1 μs / 호출
  변환 비용             V ∝ 데이터 크기 (제로카피면 ≈ 0 · y06)

  호출 n 번, 데이터 m 개일 때
    파이썬:  n · T_py(m)
    Rust  :  n · (C + V(m) + T_rs(m))

  → n 이 크고 m 이 작으면 C 가 지배합니다 (배치로 묶으세요)
  → m 이 크면 V 가 지배합니다 (제로카피가 필수 · y06)

실측 감각 (환경마다 다릅니다 — 반드시 직접 재세요)
  빈 함수 호출 왕복        약 0.1~0.3 μs
  리스트 100만 개 → Vec    수십 ms (복사 발생)
  numpy 배열 제로카피      약 0.001 ms (뷰만 만듦) ★

// src/lib.rs
use pyo3::prelude::*;

/// 1..n 의 제곱합을 구합니다.
#[pyfunction]
fn sum_squares(n: u64) -> u64 {
    (1..=n).map(|x| x * x).sum()
}

#[pyfunction]
fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}

/// 파이썬 모듈 정의 — 이름이 Cargo.toml 의 lib.name 과 같아야 합니다 ★
#[pymodule]
fn fastmod(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(sum_squares, m)?)?;
    m.add_function(wrap_pyfunction!(count_words, m)?)?;
    m.add("__version__", env!("CARGO_PKG_VERSION"))?;
    Ok(())
}

fn tokenize(text: &str, lowercase: bool, min_len: usize) -> Vec<String> {

from ._native import sum_squares as _sum_squares

def sum_squares(n: int) -> int:
    """1..n 의 제곱합."""
    if n < 0:
        raise ValueError("n 은 0 이상이어야 합니다")   # 검증은 파이썬에서 ★
    return _sum_squares(n)

#[pyfunction]
fn inspect(py: Python<'_>, obj: &Bound<'_, PyAny>) -> PyResult<String> {
    //      ^^^^^^^^^^^^ GIL 토큰       ^^^^^^^^^^^^^^^ GIL 에 묶인 참조
    let t = obj.get_type().name()?;
    Ok(format!("{t}"))
}

// 세 가지 형태
//   Python<'py>      GIL 을 잡고 있다는 증거 (토큰)
//   Bound<'py, T>    GIL 에 묶인 파이썬 객체 참조 ★ 대부분 이것
//   Py<T>            GIL 과 무관하게 보관 가능 (쓰려면 다시 GIL 필요)

// GIL 없이 보관하기 (구조체 필드 · 스레드 간 전달 · y09)
struct Holder { callback: Py<PyAny> }
impl Holder {
    fn call(&self, py: Python<'_>) -> PyResult<()> {
        self.callback.bind(py).call0()?;      // ★ GIL 을 다시 잡아 bind
        Ok(())
    }
}

//   컴파일 에러가 됩니다. C API 를 직접 쓸 때의 대표적 사고를 막습니다.

기본 형태

use pyo3::prelude::*;

#[pyclass]
struct Counter {
    #[pyo3(get)]                 // 읽기 전용 속성
    total: u64,
    #[pyo3(get, set)]            // 읽고 쓰기
    step: u64,
    history: Vec<u64>,           // 표시 안 함 (내부용)
}

#[pymethods]
impl Counter {
    #[new]                       // __init__
    #[pyo3(signature = (step = 1))]
    fn new(step: u64) -> Self {
        Counter { total: 0, step, history: Vec::new() }
    }

    fn increment(&mut self) -> u64 {
        self.total += self.step;
        self.history.push(self.total);
        self.total
    }

    fn reset(&mut self) { self.total = 0; self.history.clear(); }

    #[getter]                    // 계산되는 속성
    fn count(&self) -> usize { self.history.len() }

    fn __repr__(&self) -> String { format!("Counter(total={})", self.total) }
    fn __len__(&self) -> usize { self.history.len() }
}

// 모듈에 등록
#[pymodule]
fn fastmod(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_class::<Counter>()?;
    Ok(())
}

    let a = img.as_array();                       // ArrayView3<u8>
    let (h, w, _) = a.dim();
    let mut out = Array2::<u8>::zeros((h, w));

    for y in 0..h {
        for x in 0..w {
            let r = a[[y, x, 0]] as u32;
            let g = a[[y, x, 1]] as u32;
            let b = a[[y, x, 2]] as u32;
            out[[y, x]] = ((r * 299 + g * 587 + b * 114) / 1000) as u8;
        }
    }
    out.into_pyarray(py)
}

#        ↑        ↑    ↑   ↑     ↑
#      임시4    임시1 임시2 임시3  임시5    (각각 8MB 씩이면 40MB 순회)
// Rust — 한 번의 순회, 임시 배열 0
#[pyfunction]
fn fused<'py>(py: Python<'py>,
              a: PyReadonlyArray1<f64>,
              b: PyReadonlyArray1<f64>,
              c: PyReadonlyArray1<f64>) -> PyResult<Bound<'py, PyArray1<f64>>>
{
    let (a, b, c) = (a.as_slice()?, b.as_slice()?, c.as_slice()?);
    let out: Vec<f64> = (0..a.len())
        .map(|i| (a[i]*a[i] + b[i]*b[i]).sqrt() / (c[i] + 1e-9))
        .collect();
    Ok(out.into_pyarray(py))
}

  · 파이썬 쪽이 그 사이에 배열을 바꾸지 않는다는 전제가 필요합니다 ★

파이썬 스레드는 GIL 때문에 CPU 작업을 동시에 못 합니다. 그런데 Rust 코드는 GIL 을 놓고 돌 수 있습니다 — 그 순간 다른 파이썬 스레드가 움직이고, rayon 으로 전 코어를 쓸 수 있습니다. 파이썬으로는 물리적으로 불가능한 지점입니다.

use std::sync::atomic::{AtomicUsize, AtomicBool, Ordering};
use std::sync::Arc;

#[pyclass]
struct Job {
    done: Arc<AtomicUsize>,
    cancel: Arc<AtomicBool>,
}

#[pymethods]
impl Job {
    fn run(&self, py: Python<'_>, data: Vec<f64>) -> PyResult<Vec<f64>> {
        let (done, cancel) = (self.done.clone(), self.cancel.clone());
        let out = py.allow_threads(move || {
            data.par_iter().map(|x| {
                done.fetch_add(1, Ordering::Relaxed);
                f(*x)
            }).collect::<Vec<_>>()
        });
        Ok(out)
    }
    #[getter] fn progress(&self) -> usize { self.done.load(Ordering::Relaxed) }
    fn cancel(&self) { self.cancel.store(true, Ordering::Relaxed); }
}

use thiserror::Error;                      // (🔐 o09)

#[derive(Error, Debug)]
pub enum CoreError {
    #[error("입력이 비었습니다")]                Empty,
    #[error("길이 초과: {got} > {max}")]         TooLong { got: usize, max: usize },
    #[error("잘못된 형식: {0}")]                 BadFormat(String),
    #[error("파일 오류")]                       Io(#[from] std::io::Error),
}

// ★ From 을 구현하면 ? 하나로 변환됩니다
impl From<CoreError> for PyErr {
    fn from(e: CoreError) -> PyErr {
        match e {
            CoreError::Empty          => PyValueError::new_err(e.to_string()),
            CoreError::TooLong { .. } => PyOverflowError::new_err(e.to_string()),
            CoreError::BadFormat(_)   => PyValueError::new_err(e.to_string()),
            CoreError::Io(io)         => PyIOError::new_err(io.to_string()),
        }
    }
}

#[pyfunction]
fn process(text: &str) -> PyResult<String> {
    Ok(core_process(text)?)                // CoreError → PyErr 자동
}

비용을 알고 쓰세요 ★

파이썬 콜백 1회의 비용
  · 인자를 파이썬 객체로 변환
  · 파이썬 함수 호출 (인터프리터 진입)
  · 반환값을 Rust 타입으로 변환
  → 보통 수백 나노초 ~ 수 마이크로초

★ 100만 개 원소마다 콜백을 부르면
  콜백만으로 0.5~5초입니다. Rust 로 바꾼 의미가 사라집니다.

★ 설계 대안
  ① 콜백 없이 — 결과를 돌려주고 파이썬이 처리하게

       for r in results: handle(r)          ← 파이썬 루프지만 한 번뿐

  ② 배치 콜백 — n개 처리할 때마다 한 번

  ③ 규칙을 데이터로 받기 — 콜백 대신 설정
       fastmod.filter(data, min=0, max=100)  ← Rust 안에서 전부 처리

  ④ 정말 필요하면 표현식을 문자열로 받아 Rust 가 해석

#[pyfunction]
fn par_with_cb(py: Python<'_>, data: Vec<f64>, f: Py<PyAny>) -> Vec<f64> {
    py.allow_threads(|| {
        data.par_iter().map(|x| {
            Python::with_gil(|py| {           // ★ 여기서 전부 줄을 섭니다
                f.bind(py).call1((*x,)).unwrap().extract().unwrap()
            })
        }).collect()
    })
}

// ✅ 두 단계로 나누기 — 무거운 계산은 병렬, 콜백은 나중에 한 번
#[pyfunction]
fn par_then_cb(py: Python<'_>, data: Vec<f64>, f: &Bound<'_, PyAny>)
    -> PyResult<Vec<f64>>
{
    let mid: Vec<f64> = py.allow_threads(|| {
        data.par_iter().map(|x| heavy(*x)).collect()      // 병렬 ✅
    });
    f.call1((mid.clone(),))?;                             // 콜백 1회 ✅
    Ok(mid)
}

            Err(e) => {
                // ★ 어디서 실패했는지 맥락을 더해 다시 던집니다
                let msg = format!("콜백이 {i} 번째 원소({x})에서 실패");
                let new = PyRuntimeError::new_err(msg);
                new.set_cause(py, Some(e));       // 원인 보존 (y08)
                return Err(new);
            }
        }
    }
    Ok(out)
}

락 순서가 만드는 데드락 ★

// ❗ 위험: Rust 락을 잡은 채 파이썬 콜백을 부르기
#[pymethods]
impl Registry {
    fn notify(&self, py: Python<'_>) -> PyResult<()> {
        let g = self.state.lock().unwrap();        // ① Rust 락
        for h in &self.handlers {
            h.bind(py).call0()?;                   // ② 파이썬 코드 실행
        }                                          //    → 이 안에서 다시
        Ok(())                                     //      notify() 를 부르면 데드락
    }
}

// ✅ 락을 놓고 부르세요 (🔐 o10 의 원칙)
fn notify(&self, py: Python<'_>) -> PyResult<()> {
    let handlers: Vec<Py<PyAny>> = {
        let g = self.state.lock().unwrap();
        g.handlers.clone()                          // 복사해서 락 해제 ★
    };
    for h in &handlers { h.bind(py).call0()?; }
    Ok(())
}

// 같은 원리로: GIL 을 놓은 스레드가 Rust 락을 기다리고,
// GIL 을 든 스레드가 그 락을 들고 있으면 전체가 멈춥니다.
// → GIL 과 Rust 락을 동시에 잡는 구간을 최소화하세요

Python::with_gil 의 비용과 재진입

// 이미 GIL 을 잡고 있을 때 with_gil 을 다시 불러도 됩니다 (재진입 안전)
Python::with_gil(|py| {
    Python::with_gil(|py2| { })      // ✅ 문제없음 (참조 카운트처럼 동작)
});

// 다만 GIL 이 없는 스레드에서 부르면 '획득 대기' 가 발생합니다

    Python::with_gil(|py| {          // ★ 여기서 GIL 을 기다립니다
        // 파이썬 메인 스레드가 바쁘면 오래 걸릴 수 있습니다
    });
});

// 비용 측정 (직접 재 보세요 · ⚡ e01)
//   경합 없을 때 with_gil 왕복: 수십~수백 ns
//   경합 있을 때: 스케줄러에 달렸습니다 (밀리초까지)

// ★ 실무 패턴: 결과를 모아 두었다가 한 번에 GIL 을 잡으세요
let results: Vec<f64> = compute_without_gil();
Python::with_gil(|py| { report(py, &results) })?;     // GIL 획득 1회
비동기 파이썬과 섞을 때 — asyncio 이벤트 루프를 콜백에서 건드리면 루프가 다른 스레드에 있어 예외가 납니다. pyo3-async-runtimes 크레이트를 쓰거나, 결과만 돌려주고 스케줄링은 파이썬이 하게 두세요.
정리 — 파이썬 콜백은 호출당 수백 ns~수 μs 이고, 병렬 안에서는 GIL 때문에 줄을 섭니다. 먼저 콜백 없는 설계(결과 반환 · 배치 진행률 · 설정으로 규칙 전달 · 이터레이터)를 검토하세요. 보관은 Py<PyAny>, 호출은 bind(py), 그리고 락을 잡은 채 콜백을 부르지 마세요.

한 단계 더 — Limited API 의 안쪽 🧬 전문가

무엇이 '안정' 인가

CPython 의 두 층
  ① 전체 C API — 버전마다 바뀔 수 있습니다 (구조체 필드 포함)
  ② Limited API — 버전 간 유지를 약속한 부분집합 (PEP 384)

abi3 = Limited API 만 쓰고, 그것을 지킨 바이너리 인터페이스

★ 왜 일반 빌드는 버전마다 달라지나
  PyObject 구조체의 내부 배치, 매크로로 인라인된 접근이
  버전마다 바뀝니다. 그래서 3.11 용 .so 를 3.12 에서 로드하면
  "undefined symbol" 이나 크래시가 납니다.

★ abi3 가 하는 일
  구조체를 직접 만지는 대신 함수를 호출합니다.
  그래서 약간 느리지만, 배치가 바뀌어도 동작합니다.

흔한 실패 12가지 — 처음 만들 때 반드시 밟는 것들

여기 모은 것들은 전부 실제로 겪게 되는 문제입니다. 대부분 원인을 알면 1분이면 해결되는데, 모르면 반나절이 갑니다. 막혔을 때 이 목록부터 훑어보세요.

① ~ ⑥ 빌드와 import ★

① ImportError: dynamic module does not define module export function
   원인  Cargo.toml 의 [lib] name 과 #[pymodule] 함수 이름이 다름
   해결  둘을 맞추거나 pyproject 의 module-name 을 확인 (y02)

② ModuleNotFoundError: No module named 'fastmod'
   원인  maturin develop 을 다른 가상환경에서 실행
   해결  which python / pip show fastmod 로 확인 후 재설치

③ 링크 에러: undefined reference to `PyList_New' (cargo test 할 때)
   원인  extension-module feature 때문에 파이썬 심볼을 안 링크함
   해결  crate-type = ["cdylib", "rlib"] + feature 를 optional 로
         [features] extension-module = ["pyo3/extension-module"]
         cargo test --no-default-features

④ 윈도우에서 링크 실패
   원인  python3xx.lib 를 못 찾음 · 32/64비트 불일치
   해결  같은 비트의 파이썬 사용 · maturin 이 자동 처리하므로
         cargo build 대신 maturin 을 쓰세요 ★

⑤ 바꿨는데 반영이 안 됨
   원인  .so 가 이미 로드된 프로세스 / 캐시
   해결  파이썬 프로세스를 새로 띄우세요 (주피터는 커널 재시작)

⑥ ImportError: ... GLIBC_2.34 not found
   원인  빌드 환경의 glibc 가 실행 환경보다 새로움
   해결  manylinux 컨테이너에서 빌드 (maturin-action 이 처리) (🛠️ b08)

⑦ ~ ⑫ 동작과 성능 ★

⑦ Rust 로 바꿨는데 안 빨라졌다
   원인 1  --release 를 안 붙임 ★ 가장 흔합니다
   원인 2  경계 통과 횟수가 많음 (요소마다 호출) → 배치로 (y01)
   원인 3  list → Vec 변환 비용이 지배적 → numpy 로 (y06)
   원인 4  .clone() 이 루프 안에 있음 (⚡ e02)
   확인    py-spy 로 어디에 시간이 가는지 보세요

⑧ RuntimeError: Already borrowed
   원인  같은 #[pyclass] 인스턴스를 두 번 빌림 (자기 자신을 인자로)
   해결  frozen + Mutex 로 바꾸기 (y05)

⑨ pickle 실패 — cannot pickle 'X' object
   원인  __getstate__/__setstate__ 미구현
   해결  y05 참고 · multiprocessing 을 쓰면 반드시 필요

⑩ Ctrl+C 가 안 먹는다
   원인  GIL 을 놓은 채 오래 도는 중
   해결  주기적으로 py.check_signals() (y07)

⑪ numpy 배열인데 as_slice() 가 None
   원인  연속 배열이 아님 (슬라이스 뷰 · 전치)
   해결  파이썬 래퍼에서 np.ascontiguousarray (y06)

⑫ 세그폴트 — 파이썬이 그냥 죽는다
   원인  unsafe 코드 · FFI · 스레드에서 GIL 없이 파이썬 객체 접근
   해결  아래 진단 절차로

import random, os
_RATIO = float(os.getenv("MYPKG_NATIVE_RATIO", "1.0"))
def process(x):
    if random.random() < _RATIO:
        return _native.process(x)
    return _pure.process(x)
