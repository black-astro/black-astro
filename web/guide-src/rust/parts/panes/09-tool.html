TOOL 01

생태계 지도 — 무엇을 고를 것인가

crates.io 에는 비슷한 크레이트가 열 개씩 있습니다. 대부분의 경우 사실상 표준이 정해져 있고, 그것을 아는 것만으로 선택 시간이 사라집니다.

고민이 되면 의존하는 크레이트가 많은 쪽을 고르세요 — 생태계가 붙어 있다는 뜻입니다.

크레이트를 고를 때 실제로 보는 것

항목확인하는 법
최근 릴리스1년 넘게 없으면 이유를 확인하세요 (완성된 것일 수도 있습니다)
역의존성 수crates.io 의 "Dependents" — 가장 믿을 만한 신호입니다
버전이 0.x 인가0.x 는 마이너 올림도 깨질 수 있습니다
unsafe 사용량cargo geiger 로 확인
취약점cargo audit — CI 에 넣으세요
라이선스cargo deny 로 허용 목록을 강제

표준 라이브러리에 없어서 놀라는 것들

  • 난수 — rand 크레이트가 필요합니다
  • 정규식 — regex
  • 날짜와 시간 — std::time 은 시각 계산만, 달력은 chrono
  • JSON · HTTP · 로깅 — 전부 외부
  • 비동기 런타임 — async 문법은 언어에, 실행기는 크레이트에
표준을 작게 유지하는 것은 의도된 선택입니다 — 표준에 들어가면 영원히 못 바꾸기 때문입니다.
TOOL 02

serde — 직렬화의 사실상 표준

JSON · YAML · TOML · MessagePack · CBOR 이 전부 같은 하나의 인터페이스 위에 있습니다. 구조체에 표기 한 줄을 붙이면 형식은 나중에 갈아 끼울 수 있습니다.

기본 — 표기 한 줄

use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
struct User {
    id: u64,
    name: String,
    email: Option<String>,     // 없어도 되는 필드
}

// 문자열 ↔ 구조체
let json = serde_json::to_string(&user)?;
let user: User = serde_json::from_str(&json)?;

// 형식을 바꾸려면 크레이트만 바꿉니다
let yaml = serde_yaml::to_string(&user)?;
let toml = toml::to_string(&user)?;

실무에서 반드시 쓰게 되는 속성

#[derive(Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]     // 자바스크립트 쪽 관례에 맞춤
#[serde(deny_unknown_fields)]          // 오타 난 필드를 에러로
struct Order {
    #[serde(rename = "orderId")]
    id: u64,

    #[serde(default)]                  // 없으면 기본값
    memo: String,

    #[serde(skip_serializing_if = "Option::is_none")]
    coupon: Option<String>,            // None 이면 아예 안 내보냄

    #[serde(skip)]                     // 직렬화 대상에서 제외
    cache: Vec<u8>,

    #[serde(with = "chrono::serde::ts_seconds")]
    created_at: DateTime<Utc>,         // 커스텀 변환
}

태그가 붙은 enum — API 설계의 핵심

#[derive(Serialize, Deserialize)]
#[serde(tag = "type", rename_all = "snake_case")]
enum Event {
    Created { id: u64 },
    Updated { id: u64, field: String },
    Deleted { id: u64 },
}

// {"type":"created","id":7}
// {"type":"updated","id":7,"field":"name"}

// match 로 받으면 빠뜨린 경우를 컴파일러가 잡아 줍니다
이벤트 · 메시지 · 상태를 태그 enum 으로 정의하면 새 종류를 추가할 때 고쳐야 할 자리를 컴파일러가 전부 알려 줍니다.

성능과 함정

  • 제로카피 역직렬화 — &'a str 로 받으면 문자열을 복사하지 않습니다(입력이 살아 있어야 함)
  • serde_json::Value 는 느립니다 — 구조를 아는 데이터는 구조체로 받으세요
  • u64 정밀도 — 자바스크립트는 53비트까지만 정확합니다. 큰 ID 는 문자열로 내보내세요
  • 빌드 시간 — derive 매크로가 많으면 컴파일이 느려집니다
  • 스키마 진화 — 필드를 지우기 전에 #[serde(default)] 로 한 버전 살려 두세요
형식을 바꾸는 일이 의존성 한 줄 교체로 끝납니다 — 타입은 손대지 않습니다.
TOOL 03

CLI 만들기 — clap 으로 30분이면 됩니다

러스트가 가장 자주 쓰이는 자리 중 하나가 커맨드라인 도구입니다 — 의존성 없는 단일 바이너리, 빠른 시작, 크로스 컴파일이 전부 맞아떨어집니다.

구조체 하나가 곧 명령행 스펙

use clap::{Parser, Subcommand};

#[derive(Parser)]
#[command(name = "mytool", version, about = "파일을 정리합니다")]
struct Cli {
    /// 자세한 로그를 출력합니다
    #[arg(short, long)]
    verbose: bool,

    /// 설정 파일 경로
    #[arg(short, long, default_value = "config.toml")]
    config: PathBuf,

    #[command(subcommand)]
    command: Commands,
}

#[derive(Subcommand)]
enum Commands {
    /// 대상을 훑기만 합니다
    Scan { path: PathBuf },
    /// 실제로 정리합니다
    Clean {
        path: PathBuf,
        #[arg(long)] dry_run: bool,
    },
}

fn main() {
    let cli = Cli::parse();          // 파싱 · 검증 · --help 생성이 전부 여기서
    match cli.command { /* ... */ }
}

공짜로 따라오는 것들

  • --help · --version 을 자동 생성 — 주석이 곧 도움말입니다
  • 타입 검증 — PathBuf, u16, enum 이 자동으로 파싱·검증됩니다
  • 필수 인자 누락 시 친절한 에러 메시지
  • 셸 자동완성 스크립트 생성 (clap_complete)
  • 환경변수 대체 — #[arg(env = "MYTOOL_CONFIG")]

CLI 를 제대로 만드는 규칙

규칙이유
결과는 stdout파이프로 넘길 수 있어야 합니다
로그는 stderr결과와 섞이면 자동화가 깨집니다
종료 코드성공 0 · 실패 1 이상 — 셸 스크립트가 읽습니다
--json 옵션사람용과 기계용 출력을 분리
파괴적 작업--dry-run 을 기본으로 두는 것도 방법입니다

진행률과 색

indicatif(진행 바) · owo-colors(색) 을 씁니다. 출력이 터미널이 아닐 때는 색을 끄세요 — 파이프로 넘긴 로그에 제어 문자가 섞입니다.

에러를 사람이 읽게

anyhow 로 문맥을 쌓고, main 이 anyhow::Result 를 반환하게 하면 실패 경로가 자동으로 출력됩니다.

배포

cargo-dist 로 플랫폼별 바이너리와 설치 스크립트를 한 번에 만듭니다. cargo install 은 쓰는 사람이 컴파일해야 해서 느립니다.

TOOL 04

tokio — async 런타임 실전

러스트의 async 는 문법만 언어에 있고 실행기는 없습니다. 그 실행기가 tokio 이고, 서버 코드의 사실상 전부가 이 위에서 돕니다.

태스크는 스레드가 아닙니다 — 수만 개를 만들어도 되지만, 하나가 막히면 워커 하나가 통째로 멈춥니다.

가장 자주 쓰는 도구 다섯

// ① 동시에 여러 개 — 전부 기다림
let (a, b) = tokio::join!(fetch_user(1), fetch_order(2));

// ② 먼저 끝나는 것만 — 나머지는 취소됩니다
tokio::select! {
    res = fetch() => handle(res),
    _   = tokio::time::sleep(Duration::from_secs(3)) => timeout(),
}

// ③ 타임아웃
let res = tokio::time::timeout(Duration::from_secs(2), fetch()).await??;

// ④ 백그라운드로 던지기 (JoinHandle 을 버리면 결과·패닉을 놓칩니다)
let h = tokio::spawn(async move { work().await });
let out = h.await?;

// ⑤ 블로킹 격리
let rows = tokio::task::spawn_blocking(|| heavy_cpu()).await?;

자주 밟는 함정

함정결과
await 를 안 붙임아무 일도 안 일어납니다 — Future 는 폴링돼야 돕니다(경고가 나옵니다)
std::sync::Mutex 를 await 너머로워커가 막힙니다 — tokio::sync::Mutex 를 쓰세요
select! 취소 안전성중간에 취소되면 상태가 어중간하게 남을 수 있습니다
런타임 안에서 block_on즉시 패닉하거나 데드락
태스크 누수spawn 한 것을 아무도 안 기다리면 패닉이 조용히 묻힙니다
런타임을 하나만 쓰세요. tokio 위에 async-std 용 크레이트를 섞으면 런타임이 두 개 뜨거나 패닉합니다. 크레이트를 고를 때 "tokio 호환"인지부터 확인하는 것이 러스트 비동기 생태계의 현실입니다.
TOOL 05

axum — 웹 서버 한 파일로

tokio 팀이 만든 웹 프레임워크입니다. 매크로가 거의 없고 평범한 함수와 타입으로 라우트를 씁니다 — 그래서 에러 메시지가 읽히고, IDE 자동완성도 제대로 됩니다.

돌아가는 최소 서버

use axum::{Router, routing::get, Json, extract::{State, Path}};
use std::sync::Arc;

#[derive(Clone)]
struct AppState { db: Pool }

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let state = AppState { db: pool };

    let app = Router::new()
        .route("/health", get(|| async { "ok" }))
        .route("/users/{id}", get(get_user))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    axum::serve(listener, app).await?;
    Ok(())
}

async fn get_user(
    State(st): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<User>, AppError> {
    let user = repo::find(&st.db, id).await?;
    Ok(Json(user))
}

추출기(extractor) — 인자가 곧 명세

타입무엇을 꺼내나
Path<T>경로 변수 — /users/{id}
Query<T>쿼리 문자열 — serde 로 구조체에 매핑
Json<T>본문 JSON — 파싱 실패는 자동으로 400
State<T>DB 풀 · 설정 같은 공유 상태
HeaderMap헤더 전체
직접 만든 타입FromRequestParts 구현 — 인증 토큰 검증이 여기
순서가 중요합니다 — 본문을 소비하는 추출기(Json 등)는 인자 목록의 마지막에 와야 합니다.
매크로가 아니라 타입 시스템으로 조립되기 때문에, 잘못 쓰면 컴파일 단계에서 걸립니다.

에러 타입 하나로 응답을 통일

#[derive(thiserror::Error, Debug)]
enum AppError {
    #[error("찾을 수 없습니다")]        NotFound,
    #[error("권한이 없습니다")]          Forbidden,
    #[error(transparent)]               Other(#[from] anyhow::Error),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (code, msg) = match self {
            AppError::NotFound  => (StatusCode::NOT_FOUND, self.to_string()),
            AppError::Forbidden => (StatusCode::FORBIDDEN, self.to_string()),
            AppError::Other(e)  => {
                tracing::error!("{e:?}");        // 내부 정보는 로그로만
                (StatusCode::INTERNAL_SERVER_ERROR, "서버 오류".into())
            }
        };
        (code, Json(serde_json::json!({ "error": msg }))).into_response()
    }
}

tower 미들웨어 — 실서비스에 필요한 것

use tower_http::{trace::TraceLayer, cors::CorsLayer,
                 compression::CompressionLayer, timeout::TimeoutLayer};

let app = Router::new()
    .route("/users/{id}", get(get_user))
    .layer(TimeoutLayer::new(Duration::from_secs(10)))
    .layer(CompressionLayer::new())
    .layer(CorsLayer::permissive())      // 운영에서는 출처를 좁히세요
    .layer(TraceLayer::new_for_http())   // 요청 로그
    .with_state(state);
.layer() 는 아래에서 위로 감쌉니다. 나중에 붙인 것이 바깥쪽이 되므로, 로깅은 가장 마지막에 붙여야 모든 요청을 기록합니다.
TOOL 06

데이터베이스 — sqlx 와 그 대안들

러스트에는 JPA 같은 지배적 ORM 이 없습니다. 대신 쿼리를 직접 쓰되 컴파일 때 검증하는 방식이 가장 널리 쓰입니다.

sqlx — 쿼리를 컴파일 때 검증

SQL 을 그대로 쓰고, 빌드할 때 실제 DB 스키마에 대고 검사합니다. 컬럼 이름 오타나 타입 불일치가 컴파일 에러가 됩니다.

고르는 경우 — SQL 을 직접 통제하고 싶고, 쿼리가 복잡할 때. 가장 많이 쓰입니다.

SeaORM · Diesel

SeaORM 은 async 기반 ORM 으로 엔티티와 관계를 다룹니다. Diesel 은 타입 안전한 쿼리 빌더로 역사가 길고 성능이 좋습니다(동기 기반).

고르는 경우 — CRUD 가 대부분이고 관계 매핑을 자동화하고 싶을 때.

드라이버 직접

tokio-postgres · rusqlite 를 바로 씁니다. 가장 얇고 빠르지만 매핑을 전부 손으로 합니다.

고르는 경우 — 쿼리 몇 개뿐이거나, 극한 성능이 필요할 때.

sqlx 실제 사용

// 풀은 앱 시작에 한 번만 만들고 State 로 공유합니다
let pool = sqlx::postgres::PgPoolOptions::new()
    .max_connections(20)
    .acquire_timeout(Duration::from_secs(3))
    .connect(&db_url).await?;

// query_as! 는 컴파일 때 스키마와 대조합니다
let user = sqlx::query_as!(
    User,
    "SELECT id, name, email FROM users WHERE id = $1",
    id
).fetch_optional(&pool).await?;

// 트랜잭션
let mut tx = pool.begin().await?;
sqlx::query!("UPDATE accounts SET bal = bal - $1 WHERE id = $2", amt, from)
    .execute(&mut *tx).await?;
sqlx::query!("UPDATE accounts SET bal = bal + $1 WHERE id = $2", amt, to)
    .execute(&mut *tx).await?;
tx.commit().await?;      // 드롭되면 자동 롤백됩니다

실무에서 챙길 것

항목내용
오프라인 빌드cargo sqlx prepare 로 .sqlx 를 커밋 — CI 에 DB 가 없어도 빌드됩니다
마이그레이션sqlx migrate — 파일로 버전 관리하고 앱 시작 때 적용
풀 크기기본값을 그대로 쓰지 마세요. DB 최대 연결 수 ÷ 인스턴스 수
N+1ORM 이 없으니 자동으로 생기지는 않지만, 루프 안 쿼리는 여전히 문제입니다
타입 매핑NUMERIC 은 rust_decimal, 시간은 chrono 기능을 켜야 합니다
트랜잭션 누락commit() 을 안 부르고 드롭하면 조용히 롤백됩니다 — 반환값을 꼭 확인
Drop 이 롤백을 해 준다는 점이 러스트의 이득입니다. 예외가 나든, ? 로 일찍 반환하든, 패닉이 나든 커밋하지 않은 트랜잭션은 반드시 롤백됩니다 — 잊을 수가 없습니다.
쿼리를 감추지 않으면서 오타와 타입만 컴파일러가 봐 줍니다 — 이 조합이 Rust 쪽 주류입니다.
TOOL 07

reqwest — 외부 API 부르기

HTTP 클라이언트는 reqwest 하나가 사실상 표준입니다. 쓰는 법보다 중요한 것은 타임아웃 · 재시도 · 클라이언트 재사용 세 가지입니다.

클라이언트는 한 번 만들어 재사용합니다

// ❌ 요청마다 만들면 커넥션 풀과 TLS 세션을 매번 새로 만듭니다
// let res = reqwest::get(url).await?;

// ✅ 앱 시작에 한 번 만들어 공유합니다 (내부가 Arc 라 clone 이 쌉니다)
let client = reqwest::Client::builder()
    .timeout(Duration::from_secs(5))          // 전체 시간 상한
    .connect_timeout(Duration::from_secs(2))  // 연결까지의 상한
    .pool_max_idle_per_host(16)
    .user_agent("mytool/1.0")
    .build()?;

let res: ApiResponse = client
    .post("https://api.example.com/orders")
    .header("Authorization", format!("Bearer {token}"))
    .json(&body)
    .send().await?
    .error_for_status()?      // 4xx · 5xx 를 에러로 바꿉니다
    .json().await?;

놓치기 쉬운 것들

  • send() 는 상태 코드를 보지 않습니다 — 404 도 성공으로 옵니다. error_for_status() 를 꼭 붙이세요
  • 타임아웃 기본값이 없습니다 — 안 걸면 영원히 기다립니다
  • 재시도는 직접 — backoff 나 tower 재시도 레이어를 씁니다. POST 는 멱등키 없이 재시도 금지
  • 큰 응답은 스트리밍 — bytes_stream() 으로 받아야 메모리가 안 터집니다
  • TLS 백엔드 — rustls 를 쓰면 시스템 OpenSSL 의존이 사라져 배포가 쉬워집니다
순서를 지키세요 — 타임아웃 없이 재시도를 붙이면 장애가 배로 증폭됩니다.
TOOL 08

tracing — 로그와 관측

println! 로 시작한 로그는 반드시 한계에 부딪힙니다. 러스트의 표준은 log 가 아니라 tracing 입니다 — 구간(span) 개념이 있어 비동기 코드에서도 문맥이 유지됩니다.

기본 설정

use tracing_subscriber::{EnvFilter, fmt, prelude::*};

fn init_log() {
    tracing_subscriber::registry()
        .with(EnvFilter::try_from_default_env()
                  .unwrap_or_else(|_| "info,sqlx=warn".into()))
        .with(fmt::layer().json())      // 운영은 JSON, 개발은 기본 포맷
        .init();
}

// 쓰는 쪽 — 구조화된 필드로 남깁니다
tracing::info!(user_id = %id, amount, "결제를 시작합니다");
tracing::error!(error = ?e, "결제 실패");

// %  = Display 로 출력  ·  ?  = Debug 로 출력

RUST_LOG=debug,hyper=info 처럼 환경변수로 레벨을 모듈별로 조절합니다 — 재빌드 없이 바꿀 수 있습니다.

span — 비동기에서 문맥이 유지되는 이유

#[tracing::instrument(skip(pool), fields(order_id))]
async fn place_order(pool: &Pool, req: OrderReq) -> Result<Order> {
    // 이 함수 안에서 나오는 모든 로그에 함수 이름과 인자가 붙습니다
    let order = repo::insert(pool, &req).await?;

    tracing::Span::current().record("order_id", order.id);
    tracing::info!("주문 생성 완료");
    Ok(order)
}
태스크가 워커 스레드를 옮겨 다녀도 span 이 따라갑니다. 스레드 로컬에 기대는 기존 로깅 방식이 async 에서 깨지는 문제를 구조적으로 해결한 것이 tracing 입니다.

로그에 담아야 할 것

  • 요청 ID · 추적 ID (분산 추적)
  • 사용자·주문 같은 식별자
  • 걸린 시간과 결과 코드
  • 재시도 횟수 · 폴백 발동 여부

절대 담으면 안 되는 것

  • 토큰 · 비밀번호 · API 키
  • 주민번호 · 카드번호 전체
  • 요청 본문 통째로 (개인정보가 섞입니다)
  • #[instrument(skip(...))] 로 민감 인자를 빼세요

한 단계 더

  • tracing-opentelemetry — 분산 추적 연동
  • metrics · prometheus — 지표
  • tokio-console — 태스크가 막힌 곳을 실시간으로
  • 패닉도 로그로 — std::panic::set_hook
TOOL 09

설정 · 환경변수 · 시크릿

설정을 코드에 박아 두면 환경마다 빌드를 새로 해야 합니다. 러스트에는 스프링의 application.yml 같은 표준이 없으니, 규칙을 직접 정해야 합니다.

구조체 하나로 받아 검증까지

use serde::Deserialize;

#[derive(Deserialize, Debug)]
struct Config {
    #[serde(default = "default_port")]
    port: u16,
    database_url: String,
    #[serde(default)]
    log_level: String,
    max_connections: u32,
}
fn default_port() -> u16 { 3000 }

fn load() -> anyhow::Result<Config> {
    // 우선순위 — 기본값 → 파일 → 환경변수
    let cfg = config::Config::builder()
        .add_source(config::File::with_name("config").required(false))
        .add_source(config::Environment::with_prefix("APP").separator("__"))
        .build()?
        .try_deserialize()?;
    Ok(cfg)
}

// APP__DATABASE_URL · APP__PORT 로 덮어씁니다

설계 규칙

규칙이유
시작할 때 한 번에 읽고 검증잘못된 설정으로 뜨느니 안 뜨는 편이 낫습니다
필수 항목에 기본값 금지DB 주소에 기본값을 두면 운영에서 개발 DB 를 봅니다
우선순위를 문서로"왜 이 값이 적용됐지"를 추적할 수 있어야 합니다
Debug 에 시크릿 금지secrecy 크레이트나 직접 Debug 구현으로 마스킹
.env 는 개발에서만dotenvy. 운영은 오케스트레이터의 시크릿을 씁니다
기능 플래그설정으로 껐다 켜면 롤백이 배포보다 빠릅니다
시크릿을 저장소에 커밋했다면 히스토리에서 지우는 것으로 끝나지 않습니다. 이미 노출된 것이므로 즉시 폐기하고 새로 발급해야 합니다. gitleaks 를 pre-commit 훅과 CI 양쪽에 걸어 두세요.
TOOL 10

테스트 전략 — 언어가 도와주는 만큼

러스트는 타입 시스템이 많은 버그를 미리 잡아 줍니다. 그래서 테스트의 초점이 "널일까 아닐까"가 아니라 로직 · 경계 · 통합으로 옮겨 갑니다.

타입으로 표현할 수 있는 것은 테스트가 아니라 타입으로 막는 것이 러스트다운 방식입니다.

기본 형태

// src/parser.rs 안에 그대로 둡니다
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn 빈_입력은_에러다() {
        assert!(parse("").is_err());
    }

    #[test]
    fn 정상_입력을_파싱한다() {
        let r = parse("a=1").unwrap();
        assert_eq!(r.get("a"), Some(&1));
    }

    #[tokio::test]           // async 테스트
    async fn 저장하고_다시_읽는다() {
        let repo = Repo::in_memory();
        repo.save(&item).await.unwrap();
        assert_eq!(repo.find(1).await.unwrap(), Some(item));
    }
}

테스트 이름을 한글로 써도 됩니다 — 실패했을 때 무엇이 깨졌는지 바로 읽힙니다.

TOOL 11

배포 — 바이너리 하나로 끝내기

러스트의 가장 실용적인 장점 중 하나가 런타임이 필요 없다는 것입니다. JVM 도, 파이썬 인터프리터도, node_modules 도 없이 파일 하나를 옮기면 됩니다.

컨테이너 — 다단계 빌드

# 1단계 — 빌드
FROM rust:1-slim AS builder
WORKDIR /app

# 의존성만 먼저 빌드해 캐시를 살립니다
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo "fn main(){}" > src/main.rs && \
    cargo build --release && rm -rf src

COPY . .
RUN touch src/main.rs && cargo build --release

# 2단계 — 실행 (수십 MB)
FROM gcr.io/distroless/cc-debian12
COPY --from=builder /app/target/release/myapp /myapp
USER nonroot
ENTRYPOINT ["/myapp"]
cargo-chef 를 쓰면 위 캐시 트릭을 더 정확하게 합니다. CI 빌드 시간이 크게 줄어듭니다.

정적 링크 — 이미지를 몇 MB 로

# musl 타깃으로 빌드하면 libc 의존이 사라집니다
rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl

# scratch 이미지에 바이너리만 넣을 수 있습니다
# FROM scratch
# COPY myapp /myapp
musl 은 기본 할당자가 느립니다. 할당이 잦은 서버라면 jemallocator 나 mimalloc 을 함께 쓰세요 — 그냥 바꾸면 처리량이 눈에 띄게 떨어질 수 있습니다.
항목내용
헬스체크 엔드포인트/health(살아 있나) 와 /ready(트래픽 받을 준비) 를 분리하세요
정상 종료SIGTERM 을 받으면 새 요청은 거절하고 진행 중인 것만 끝냅니다 — axum::serve(...).with_graceful_shutdown()
패닉 처리기본은 그 태스크만 죽습니다. 프로세스를 죽이고 재시작하는 편이 안전한 경우가 많습니다
메모리 상한컨테이너 제한을 걸고 실제 사용량을 지표로 보세요 — 러스트도 누수가 없지는 않습니다
바이너리 크기strip = true · opt-level = "z" · panic = "abort" 로 크게 줄어듭니다
크로스 컴파일cross 또는 cargo-zigbuild — 맥에서 리눅스 바이너리를 만들 때 편합니다
CI 캐시Swatinem/rust-cache 액션 — 빌드 시간이 절반 이하가 됩니다

러스트를 실무에 쓰는 이유는 결국 두 가지로 모입니다 — 런타임 없이 배포되는 단일 바이너리, 그리고 메모리·동시성 버그가 빌드에서 막힌다는 것. 배우는 비용은 분명히 있지만, 그 비용은 처음 한 번이고 얻는 것은 서비스가 사는 내내 돌아옵니다. 막힐 때는 Ctrl K 검색으로 필요한 섹션을 바로 찾아 쓰세요.
