SETUP 01

시작과 끝은 rustup 하나입니다 — 다른 방법은 쓰지 마세요

파이썬은 설치 방법이 열 가지쯤 됩니다(공식 설치본 · 배포판 패키지 · pyenv · conda · uv…). 그래서 “내 파이썬이 어디 있는지” 를 평생 헷갈립니다. Rust 는 그 문제를 처음부터 없앴습니다 — 공식 설치 방법은 rustup 하나이고, 컴파일러 · 패키지 매니저 · 문서 · 포매터가 전부 그 안에 들어 있습니다. 이 섹션에서 받는 곳 · 설치 화면 · 확인 명령까지 끝냅니다.

rustup 은 버전 관리자입니다 — 파이썬의 pyenv, Node 의 nvm 자리를 공식 도구가 차지하고 있습니다.

한 단계 더 — rustup 이 디스크에 실제로 만드는 것 🧬 전문가

폴더 두 개가 전부입니다

~/.rustup/                     (윈도우: %USERPROFILE%\.rustup)
├─ toolchains/
│  ├─ stable-x86_64-pc-windows-msvc/
│  │  ├─ bin/  rustc.exe cargo.exe rustdoc.exe   ← 진짜 실행 파일
│  │  └─ lib/rustlib/  표준 라이브러리 · 타깃별 .rlib
│  └─ nightly-x86_64-pc-windows-msvc/
├─ downloads/                  받다 만 파일 (지워도 됩니다)
└─ settings.toml               기본 툴체인 · 디렉터리별 override 기록

~/.cargo/                      (윈도우: %USERPROFILE%\.cargo)
├─ bin/     rustc cargo rustup clippy-driver rustfmt …  ← shim ★ PATH 에 넣는 건 여기
│           + cargo install 로 깐 도구들도 여기로 들어옵니다 (s06)
├─ registry/  crates.io 에서 받은 크레이트 소스 캐시 (수 GB 까지 큽니다)
├─ git/       git 의존성 체크아웃
└─ config.toml  레지스트리 · 링커 · 프록시 설정 (s07 · s09)

# 크기가 궁금할 때
du -sh ~/.cargo ~/.rustup      # 보통 합쳐서 2~6 GB

shim — 이름은 같지만 진짜가 아닌 파일

# ~/.cargo/bin/rustc 는 컴파일러가 아닙니다.
# "지금 이 폴더에서 어떤 툴체인을 써야 하지?" 를 판단해서
# ~/.rustup/toolchains/<선택된 것>/bin/rustc 로 넘기는 대리인입니다.

# 진짜가 어디 있는지 보기
rustup which rustc
#   C:\Users\me\.rustup\toolchains\stable-…\bin\rustc.exe
rustup which --toolchain nightly cargo

# 그래서 이런 일이 가능합니다
cd ~/projA && rustc --version    # 1.89.0   (rust-toolchain.toml 없음 → 기본값)
cd ~/projB && rustc --version    # 1.75.0   (rust-toolchain.toml 이 고정)

# 디렉터리별 강제 지정 (파일을 안 만들고)
rustup override set nightly       # 이 폴더는 앞으로 nightly
rustup override list
rustup override unset
왜 이 구조를 아는 것이 중요한가 — “왜 내 PC 에서만 버전이 다르지?” 의 답이 거의 항상 이 세 곳 중 하나이기 때문입니다: ① rustup default ② 폴더 override ③ rust-toolchain.toml. 순서대로 우선순위가 거꾸로입니다 (③ 이 가장 셈). 자세한 우선순위 표는 s08 에 있습니다.
정리 — rustup.rs 에서 받아 실행하고, cargo new hello && cargo run 이 “Hello, world!” 를 찍을 때까지가 설치입니다. rustc --version 만 보고 끝내지 마세요 — 그건 링커를 확인하지 않은 상태입니다. 채널은 고민할 것 없이 stable, 버전 고정이 필요하면 채널이 아니라 rust-toolchain.toml 을 씁니다.
SETUP 02

Windows — 링커 하나 때문에 첫날이 날아갑니다

Rust 는 윈도우에서 마이크로소프트의 링커(link.exe) 를 빌려 씁니다. 직접 만들지 않고 빌려 쓰는 이유는 윈도우 시스템 라이브러리(kernel32 · user32 …)와 정확히 같은 규약으로 이어 붙여야 하기 때문입니다. 그래서 “Rust 만 깔면 되는 거 아니었나” 라는 기대가 여기서 깨집니다. 이 섹션은 무엇을 · 어디서 · 얼마나 받아야 하는지를 화면 단위로 짚습니다.

넷째 칸이 비어 있으면 컴파일은 성공하고 링크만 실패합니다 — 그래서 rustc --version 은 멀쩡합니다.

cargo — 빌드 · 의존성 · 테스트 · 문서가 한 명령에

파이썬은 pip + venv + pytest + black + build 를 따로 배웁니다. C++ 는 CMake 와 vcpkg 를 따로 배웁니다. Rust 는 전부 cargo 하나이고, 그래서 배울 명령이 열 개 남짓입니다. 이 섹션에서 그 열 개와 Cargo.toml 의 모든 칸, 그리고 왜 첫 빌드만 오래 걸리는지를 구조로 이해합니다.

첫 빌드가 느린 이유는 ③ 다운로드 + ④ 의존성 전체 컴파일 때문입니다 — 두 번째부터는 내 코드만 다시 합니다.

cargo init                   # 이미 있는 폴더를 프로젝트로

cargo check                  # 타입만 검사 ★ 편집 중엔 이것만

cargo test                   # 테스트 (문서 안 예제까지 같이)

Cargo.lock — 커밋하나, 안 하나

프로젝트 종류Cargo.lock이유
실행 파일 · 서비스커밋합니다 ★어제 통과한 CI 가 오늘도 통과해야 합니다
라이브러리 (crates.io 배포)커밋해도 됩니다배포물에는 안 들어갑니다. CI 재현용으로 두는 편이 요즘 권장
워크스페이스루트에 하나만멤버별로 생기지 않습니다
# Cargo.lock 이 하는 일
#   Cargo.toml 은 "1.x 면 아무거나"  ← 범위
#   Cargo.lock 은 "1.2.7 · 해시 abc" ← 확정

cargo build                # lock 이 있으면 그대로 씁니다 (네트워크 최소)
cargo update               # 범위 안에서 전부 최신으로 → lock 갱신
cargo update -p serde      # serde 만
cargo update -p serde --precise 1.0.210   # 특정 버전으로 못 박기

# CI 에서 lock 이 바뀌면 실패시키기 (재현성 보증) ★
cargo build --locked
cargo test --locked --offline

target/ — 왜 이렇게 커지나

myapp/target/
├─ debug/
│  ├─ myapp(.exe)         내 실행 파일
│  ├─ deps/               의존성 · 내 코드의 중간 산출물 (.rlib .rmeta)
│  ├─ build/              build.rs 를 컴파일·실행한 결과
│  ├─ incremental/        증분 컴파일 캐시 ★ 여기가 제일 큽니다
│  └─ .fingerprint/       "뭐가 바뀌었나" 판단용 지문
├─ release/               --release 결과 (debug 와 완전히 별도)
└─ CACHEDIR.TAG           백업 도구가 건너뛰라는 표시

target/ 은 절대 커밋하지 않습니다. cargo new 가 만든 .gitignore 에 이미 들어 있습니다. 실수로 올라갔다면 git rm -r --cached target 로 빼세요. 디스크가 부족할 때 가장 먼저 지울 곳도 여기입니다.

SETUP 05

에디터 — rust-analyzer 하나가 체감의 90%

Rust 는 에디터 지원의 질이 학습 속도를 그대로 결정하는 언어입니다. 타입을 안 적어도 되지만 타입이 무엇인지는 알아야 하고, 소유권 에러는 줄 위에서 즉시 보여야 의미가 있습니다. 그 일을 하는 것이 rust-analyzer 입니다. 이 섹션은 VS Code 설정 파일 실제 내용 · 디버깅 launch.json · 대안 에디터까지 다룹니다.

빨간 줄은 에디터가 아니라 cargo check 가 그린 것입니다 — 그래서 컴파일 결과와 항상 일치합니다.

필수 도구 — clippy · rustfmt 부터 감사 도구까지

Rust 생태계의 도구는 대부분 cargo- 로 시작하는 서브커맨드 형태입니다. 설치하면 cargo 이름 으로 그냥 불립니다. 다만 깔리는 위치가 두 종류여서, 그걸 모르면 “깔았는데 없다”가 반복됩니다. 여기서 어디에 · 어떻게 · 왜를 정리하고 실무에서 실제로 쓰는 여덟 개를 한 줄 사용법과 함께 익힙니다.

“깔았는데 없다” 의 원인은 대부분 ① 로 깔아야 할 것을 ② 로 찾거나 그 반대입니다.

clippy — 코드 리뷰를 대신해 줍니다

# 설치 — default 프로필이면 이미 있습니다
rustup component add clippy
cargo clippy --version

# 기본 사용
cargo clippy                            # 기본 타깃
cargo clippy --all-targets              # 테스트 · 예제 · 벤치까지 ★
cargo clippy --workspace --all-targets --all-features

# CI 에서 — 경고 하나라도 있으면 실패시키기 ★★
cargo clippy --all-targets -- -D warnings

# 자동으로 고칠 수 있는 것은 고쳐 버리기
cargo clippy --fix                      # git 이 깨끗해야 실행됩니다
cargo clippy --fix --allow-dirty --allow-staged
# Cargo.toml — 프로젝트 전체 린트 정책 (팀 규칙을 코드로)
[lints.rust]
unsafe_code = "forbid"
missing_docs = "warn"

[lints.clippy]
all       = { level = "warn", priority = -1 }
pedantic  = { level = "warn", priority = -1 }
unwrap_used   = "warn"      # unwrap 을 쓰면 경고 ★ 서비스 코드에 유용
expect_used   = "allow"
module_name_repetitions = "allow"   # pedantic 중 성가신 것만 끄기
clippy 는 “문법 검사”가 아니라 “관용구 교사”입니다 — if x == true, 불필요한 clone(), len() == 0, match 로 쓸 수 있는 if let 사슬 같은 것을 잡아 줍니다. 초보일수록 얻는 게 많습니다. 반드시 켜 두세요.

rustfmt — 포맷 논쟁을 없앱니다

rustup component add rustfmt

cargo fmt -p core            # 특정 크레이트만
rustfmt src/main.rs          # 파일 하나만
# 프로젝트 루트의 rustfmt.toml — 안정 채널에서 되는 것들
edition        = "2024"
max_width      = 100         # 기본 100. 팀에 따라 120 도 씁니다
tab_spaces     = 4
newline_style  = "Unix"      # 윈도우 팀원과 섞여도 CRLF 가 안 생깁니다 ★
use_field_init_shorthand = true
use_try_shorthand        = true    # r#try 대신 ? 를 씁니다
reorder_imports          = true

# ── 아래는 nightly 에서만 동작합니다 ──
#   cargo +nightly fmt 로 돌려야 적용됩니다
group_imports        = "StdExternalCrate"   # std / 외부 / crate 순으로 묶기 ★
imports_granularity  = "Crate"
wrap_comments        = true
comment_width        = 100
“왜 내 rustfmt.toml 이 무시되지?” — 위 표시처럼 일부 옵션은 nightly 전용입니다. stable 로 cargo fmt 를 돌리면 조용히 무시됩니다(에러도 안 납니다). 팀이 그 옵션을 쓰기로 했다면 rustup toolchain install nightly 후 cargo +nightly fmt 를 CI 와 에디터 양쪽에 맞춰 두세요.

집에서는 cargo build 가 알아서 다 받아 옵니다. 그런데 회사 망에 들어가는 순간 같은 명령이 failed to get response 로 죽습니다. 프록시 · 사내 CA 인증서 · 차단된 도메인 · 폐쇄망… 이 섹션은 ~/.cargo/config.toml 파일 하나로 그 상황들을 전부 다루는 법입니다. 개인 PC 만 쓰더라도 “캐시가 어디 있고 얼마나 큰지”는 알아 두는 편이 좋습니다.

캐시가 있으면 네트워크를 아예 안 탑니다 — CI 가 느리다면 ~/.cargo/registry 캐싱부터 확인하세요.

config.toml — 어디에 두느냐로 범위가 정해집니다

적용 범위가 좁은 쪽이 이깁니다 (아래로 갈수록 셈)

① $CARGO_HOME/config.toml         ← 내 계정 전체
     리눅스·mac : ~/.cargo/config.toml
     윈도우     : %USERPROFILE%\.cargo\config.toml

② 상위 폴더들의 .cargo/config.toml  ← 루트까지 올라가며 전부 합쳐집니다
     /work/.cargo/config.toml

③ 프로젝트의 .cargo/config.toml    ← 이 프로젝트만 ★ 팀에 공유할 것은 여기
     myproj/.cargo/config.toml

④ 환경 변수                        ← 가장 셈
     CARGO_HTTP_PROXY · CARGO_NET_OFFLINE · CARGO_BUILD_JOBS …
     (설정 키 a.b.c → 환경 변수 CARGO_A_B_C 규칙)

※ 옛 이름 "config" (확장자 없음) 도 여전히 읽힙니다. 새로 만들 땐 config.toml.
※ Cargo.toml 과 헷갈리지 마세요 — 이쪽은 "도구 설정", 저쪽은 "프로젝트 정의".
지금 무엇이 적용 중인지 보는 법 — cargo config get (안정화된 하위 명령) 또는 cargo -Zunstable-options config get --show-origin (nightly) 로 값이 어느 파일에서 왔는지까지 확인할 수 있습니다.

sparse 인덱스 — 예전에는 crates.io 의 전체 목록 git 저장소를 통째로 받았습니다 (첫 빌드가 몇 분씩 걸리던 이유). 지금은 HTTP 로 필요한 항목만 가져오는 sparse+https://index.crates.io/ 가 기본입니다. 그래서 사내 프록시는 “git 을 통과시키는 것”이 아니라 “HTTPS GET 을 통과시키는 것”이면 됩니다.

툴체인 · 타깃 — “왜 내 PC 에서만 다르지” 를 없애는 법

Rust 는 컴파일러가 여러 개 깔려 있는 것이 정상인 언어입니다. stable 로 개발하다 nightly 로 매크로를 펼쳐 보고, wasm 을 빌드하고, 서버용 musl 을 만듭니다. 그래서 “지금 이 폴더에서 어떤 rustc 가 쓰이는가” 를 판단하는 규칙이 있고, 그 규칙을 알면 버전 문제의 90%가 사라집니다. 타깃 추가와 크로스 컴파일도 여기서 함께 봅니다.

③ 이 유일하게 저장소에 남는 것입니다 — 나머지는 내 PC 에서만 유효합니다.

    strategy:
      fail-fast: false

        os: [ubuntu-latest, windows-latest, macos-latest]

정리 — 컴파일러 선택은 +툴체인 → 환경 변수 → rust-toolchain.toml → override → default 순으로 이깁니다. 팀에서 공유해야 하는 것은 rust-toolchain.toml 하나뿐입니다. 다른 CPU·OS 용으로 빌드하려면 rustup target add + 그 타깃용 링커가 둘 다 필요하고, 링커 준비가 귀찮으면 cross 나 cargo-zigbuild 를 쓰세요.
SETUP 09

빌드가 느립니다 — 어디에 시간이 가는지 부터 봅니다

Rust 를 처음 쓰는 사람이 가장 자주 하는 불평이 “빌드가 느리다” 입니다. 그런데 느린 이유가 매번 다릅니다 — 첫 빌드는 의존성 컴파일, 두 번째부터는 링크, CI 는 캐시 없음, 윈도우는 백신 검사. 원인이 다르면 처방도 다릅니다. 이 섹션은 측정하는 법 → 링커 교체 → 캐시 → 프로파일 조정 순으로, 가장 효과가 큰 순서대로 정리합니다.

첫 빌드와 두 번째 빌드는 느린 이유가 다릅니다 — 처방도 달라야 합니다.

왜 첫 빌드가 그렇게 오래 걸리나

① 의존성을 "소스로" 받아 전부 직접 컴파일합니다
   파이썬의 pip 는 미리 빌드된 wheel 을 받습니다.
   Java 는 jar(바이트코드)를 그대로 씁니다.
   Rust 는 crates.io 에서 소스만 받아 내 PC 에서 컴파일합니다.
   → 왜? 제네릭·인라인·기능 플래그(feature)에 따라 결과가 달라지므로
     "미리 만들어 둘 수" 가 없습니다.

② 제네릭이 타입마다 코드를 새로 만듭니다 (단형화)
   Vec<u8> 과 Vec<String> 은 서로 다른 기계어가 생깁니다.

③ 파생 매크로가 코드를 불려 놓습니다
