FFI 01

C ABI 가 공용어인 이유

언어마다 문법도 런타임도 다르지만 “C 함수를 부르는 법”은 모두 압니다. 그래서 언어 간 연동은 대부분 C 인터페이스를 경유합니다. Rust 는 런타임이 없어 이 역할에 특히 잘 맞습니다.

ABI 란 무엇인가

API — 소스 코드 수준의 약속 (함수 이름 · 인자 타입)
ABI — 기계어 수준의 약속 ★
        · 인자를 어느 레지스터·스택에 놓는가
        · 반환값은 어디로 오는가
        · 구조체 필드가 메모리에 어떻게 배치되는가
        · 함수 이름이 심볼로 어떻게 적히는가
        · 누가 스택을 정리하는가

C ABI 는 이것들이 '플랫폼마다 고정' 돼 있습니다.
  x86-64 SysV (리눅스·맥)  ·  Win64 (윈도우)  ·  AAPCS64 (ARM)

★ 그래서 C 로 컴파일된 라이브러리는
  어떤 언어에서도 부를 수 있습니다.
  Rust 는 "C 처럼 보이는 함수"를 만들 수 있습니다.
Rust ABI 는 불안정합니다 — 컴파일러 버전이 다르면 같은 Rust 끼리도 안 맞을 수 있습니다(🔬 d11). 그래서 경계는 반드시 C ABI 여야 합니다.

인터페이스 설계 5원칙 ★

① 좁게 — 함수 10개 이하를 목표로
   내부 타입을 노출하지 말고 '핸들 + 동작' 으로 (f03 의 불투명 포인터)

② 안정되게 — 한 번 배포한 시그니처는 바꾸지 않는다
   기능 추가는 새 함수로. 구조체는 버전 필드나 크기 필드를 넣어 확장 (f09)

③ 소유권을 명시 — 누가 할당하고 누가 해제하는가 (f06)
   이름으로 드러내세요: mylib_string_free · mylib_buffer_free

④ 실패를 코드로 — 예외도 Result 도 없습니다 (f09)
   0 = 성공, 음수 = 실패. 마지막 에러 메시지를 얻는 함수를 따로 제공

⑤ 패닉을 가두어라 — 경계 밖으로 나가면 UB (f09)
   모든 extern "C" 함수를 catch_unwind 로 감싸세요

★ 이 다섯 가지가 이 탭 전체의 목차이기도 합니다.

런타임이 없다는 이점

Rust 가 C ABI 라이브러리로 특히 좋은 이유

  · GC 가 없습니다 — 초기화·정지 시간이 없습니다
  · 런타임 초기화가 필요 없습니다 (Go 는 런타임을 띄워야 합니다)
  · 예외 테이블 외에는 숨은 비용이 없습니다
  · 정적 링크가 자연스럽습니다 (musl 로 완전 정적도 가능 · 🛠️ b07)

★ 비교
  C/C++   같은 수준. 대신 메모리 안전은 사람이 책임
  Go      cgo 경계 비용이 크고 런타임이 따라옵니다
  C#/자바 런타임(CLR/JVM)을 임베드해야 합니다
  Rust    C 와 같은 비용 + 안전한 내부 ★

★ 남는 의존성 확인
  ldd target/release/libmylib.so
    linux-vdso · libgcc_s · libc · libm 정도

  완전 정적으로 (musl)
    rustup target add x86_64-unknown-linux-musl
    cargo build --release --target x86_64-unknown-linux-musl
정리 — C ABI 는 언어 간 공용어이고, Rust 는 런타임이 없어 이 역할에 잘 맞습니다. 대신 Option·Result·String 을 못 쓰고, 안전장치가 사라집니다. 좁게 · 안정되게 · 소유권 명시 · 에러는 코드로 · 패닉은 가두기 — 이 다섯 원칙이 이 탭의 전부입니다.
FFI 02

#[no_mangle] · extern "C" — 내보내기

Rust 함수를 C 가 부를 수 있게 만드는 데 필요한 것은 두 줄입니다. extern "C" 로 호출 규약을, #[no_mangle] 로 이름을 지정합니다. 나머지는 어떤 타입을 주고받을 수 있는가의 문제입니다.

최소 예제

// src/lib.rs
#[no_mangle]
pub extern "C" fn mylib_add(a: i32, b: i32) -> i32 {
    a + b
}

// #[no_mangle]  이름을 그대로 심볼로 (안 붙이면 _ZN5mylib3add17h... 가 됩니다)
// extern "C"    C 호출 규약
// pub           크레이트 밖으로

// 2024 에디션부터는 unsafe 표기를 씁니다
// #[unsafe(no_mangle)]
// pub unsafe extern "C" fn mylib_add(a: i32, b: i32) -> i32 { a + b }
cargo build --release

# 심볼 확인 ★ 문제가 생기면 항상 여기부터
nm -D target/release/libmylib.so | grep mylib
#   0000000000007a10 T mylib_add        ← T = 텍스트(코드), 전역

# 윈도우
dumpbin /exports target\release\mylib.dll

# 맥
nm -gU target/release/libmylib.dylib | grep mylib
#[no_mangle] 이름은 전역입니다 — 다른 라이브러리와 겹치면 어느 것이 불릴지 알 수 없습니다. 반드시 mylib_ 같은 접두사를 붙이세요.

슬라이스와 문자열 받기

use std::ffi::{c_char, CStr};
use std::slice;

#[no_mangle]
pub unsafe extern "C" fn mylib_checksum(data: *const u8, len: usize) -> u32 {
    if data.is_null() || len == 0 { return 0; }          // ★ 널 검사 먼저
    let bytes = slice::from_raw_parts(data, len);        // unsafe (🔬 d03)
    bytes.iter().fold(0u32, |a, b| a.wrapping_add(*b as u32))
}

#[no_mangle]
pub unsafe extern "C" fn mylib_count_words(s: *const c_char) -> usize {
    if s.is_null() { return 0; }
    match CStr::from_ptr(s).to_str() {                   // UTF-8 검증
        Ok(text) => text.split_whitespace().count(),
        Err(_) => 0,                                     // 잘못된 UTF-8
    }
}

// ★ 안전한 래퍼로 감싸는 습관 (🔬 d08)
#[no_mangle]
pub unsafe extern "C" fn mylib_process(data: *const u8, len: usize) -> i32 {
    let Some(bytes) = to_slice(data, len) else { return -1 };
    core_process(bytes)                                   // 여기부터는 안전한 Rust
}
unsafe fn to_slice<'a>(p: *const u8, len: usize) -> Option<&'a [u8]> {
    if p.is_null() { return None; }
    if len == 0 { return Some(&[]); }
    Some(slice::from_raw_parts(p, len))
}
len == 0 일 때 널 포인터가 올 수 있습니다 — slice::from_raw_parts(null, 0) 은 UB 입니다(정렬된 비널 포인터를 요구). 길이 0 을 먼저 처리하는 습관을 들이세요.

출력을 돌려주는 방법 세 가지

// ① 호출자가 버퍼를 준다 ★ 가장 안전하고 흔합니다
#[no_mangle]
pub unsafe extern "C" fn mylib_encode(
    input: *const u8, in_len: usize,
    out: *mut u8, out_cap: usize, out_len: *mut usize,
) -> i32 {
    let Some(src) = to_slice(input, in_len) else { return -1 };
    let result = encode(src);
    if out.is_null() || out_cap < result.len() {
        *out_len = result.len();     // ★ 필요한 크기를 알려 줍니다
        return -2;                   // 버퍼 부족
    }
    std::ptr::copy_nonoverlapping(result.as_ptr(), out, result.len());
    *out_len = result.len();
    0
}
// 호출 패턴: 크기를 먼저 물어보고(out=NULL) → 할당 → 다시 호출

// ② 라이브러리가 할당하고 해제 함수를 제공 (f06)
#[no_mangle]
pub extern "C" fn mylib_encode_alloc(input: *const u8, len: usize,

#[no_mangle]
pub extern "C" fn mylib_free(ptr: *mut u8, len: usize);

// ③ 콜백으로 흘려보내기 (f07)
#[no_mangle]

FFI 03

#[repr(C)] — Rust 는 필드 순서를 바꿉니다

Rust 는 메모리를 아끼려고 구조체 필드를 마음대로 재배치합니다. 그래서 C 와 구조체를 주고받으려면 #[repr(C)] 로 “건드리지 마”라고 해야 합니다. 이걸 빠뜨리면 값이 조용히 깨집니다 — 크래시도 안 나서 더 위험합니다.

헤더는 손으로 쓰지 말고 cbindgen 으로 생성하세요 — 표기와 헤더가 어긋나는 사고를 막습니다.

무슨 일이 일어나나

struct Bad { a: u8, b: u64, c: u8 }
#[repr(C)]
struct Good { a: u8, b: u64, c: u8 }

println!("{} {}", size_of::<Bad>(), size_of::<Good>());   // 16  24

// Bad 의 실제 배치 (컴파일러가 재배치)
//   [b: 8바이트][a: 1][c: 1][패딩 6]  = 16
// Good 의 배치 (C 규칙 그대로)
//   [a: 1][패딩 7][b: 8][c: 1][패딩 7] = 24

// ★ C 쪽에서 Bad 를 { uint8_t a; uint64_t b; uint8_t c; } 로 선언하면
//   a 를 읽었는데 b 의 하위 바이트가 나옵니다 — 크래시 없이 값만 틀립니다

#[repr(C)]
#[derive(Debug, Clone, Copy)]
pub struct Point { pub x: f64, pub y: f64 }

#[no_mangle]
pub extern "C" fn mylib_distance(a: Point, b: Point) -> f64 {
    ((a.x - b.x).powi(2) + (a.y - b.y).powi(2)).sqrt()
}
/* C 쪽 */
typedef struct { double x, y; } Point;
double mylib_distance(Point a, Point b);

repr 의 종류 ★

표기뜻
#[repr(C)]C 배치 규칙 ★ FFI 기본
#[repr(transparent)]필드 하나와 동일 배치
#[repr(u8)]enum 판별자 크기 지정
#[repr(C, packed)]패딩 없음 ★ 위험
#[repr(align(64))]정렬 강제 (캐시라인)
(없음)Rust 마음대로
// transparent — 뉴타입을 C 에 그대로 (r07)
#[repr(transparent)]
pub struct Handle(*mut c_void);      // C 에서는 그냥 void*

// C 스타일 enum
#[repr(i32)]
pub enum Status { Ok = 0, NotFound = 1, Error = 2 }

// packed — 네트워크 프로토콜 등
#[repr(C, packed)]
struct Header { kind: u8, len: u32 }   // 5바이트 (패딩 없음)
// ❗ packed 필드의 참조를 만들면 UB 입니다 (정렬 위반 · 🔬 d03)
//    let r = &h.len;                  // ❌ 컴파일러가 막습니다
let len = h.len;                        // ✅ 복사해서 쓰기
let len = std::ptr::addr_of!(h.len);    // ✅ 주소만 필요하면

// 정렬 강제 — false sharing 방지 (⚡ e06)
#[repr(align(64))]
struct CacheAligned(AtomicU64);

★ 플랫폼마다 다른 것들

FFI 04

cbindgen — 헤더를 손으로 쓰지 마세요

.h 헤더를 손으로 쓰면 반드시 코드와 어긋납니다. 필드 하나 추가했는데 헤더를 안 고치면 조용히 값이 깨집니다(f03). cbindgen 을 빌드에 붙여 헤더가 항상 코드에서 생성되게 하세요.

붙이는 방법

# Cargo.toml
[build-dependencies]
cbindgen = "0.27"
// build.rs
fn main() {
    let crate_dir = std::env::var("CARGO_MANIFEST_DIR").unwrap();

    std::fs::create_dir_all(out.parent().unwrap()).unwrap();

    cbindgen::generate(&crate_dir)
        .expect("cbindgen 실패")
        .write_to_file(&out);

    println!("cargo:rerun-if-changed=src/ffi.rs");   // ★ 바뀔 때만 재생성
}

    ctypes.POINTER(ctypes.c_ubyte), ctypes.c_size_t,   # 출력 버퍼
    ctypes.POINTER(ctypes.c_size_t),                   # 실제 길이
]
lib.mylib_encode.restype = ctypes.c_int32

def encode(data: bytes) -> bytes:
    src = (ctypes.c_ubyte * len(data)).from_buffer_copy(data)
    need = ctypes.c_size_t(0)

    # ① 필요한 크기 물어보기 (out=NULL)
    rc = lib.mylib_encode(src, len(data), None, 0, ctypes.byref(need))
    if rc not in (0, -2):
        raise RuntimeError(last_error())

    # ② 버퍼를 만들어 다시 호출
    out = (ctypes.c_ubyte * need.value)()
    rc = lib.mylib_encode(src, len(data), out, need.value, ctypes.byref(need))
    if rc != 0:
        raise RuntimeError(last_error())
    return bytes(out[:need.value])

FFI 06

문자열 · 메모리 소유권 규약

FFI 에서 가장 사고가 잦은 자리입니다. “이 메모리는 누가 해제하나”를 정하지 않으면 반드시 새거나 두 번 해제됩니다. 규칙은 단순합니다 — 할당한 쪽이 해제한다.

문자열을 돌려주는 정석 ★

use std::ffi::{CString, CStr, c_char};

#[no_mangle]
pub extern "C" fn mylib_greet(name: *const c_char) -> *mut c_char {
    let name = unsafe {
        if name.is_null() { return std::ptr::null_mut(); }
        match CStr::from_ptr(name).to_str() {
            Ok(s) => s,
            Err(_) => return std::ptr::null_mut(),
        }
    };
    let msg = format!("안녕 {name}");
    match CString::new(msg) {                    // 내부 널이 있으면 실패
        Ok(c) => c.into_raw(),                   // ★ 소유권을 C 로 넘김
        Err(_) => std::ptr::null_mut(),
    }
}

// ★ 반드시 짝이 되는 해제 함수를 제공하세요
#[no_mangle]
pub unsafe extern "C" fn mylib_string_free(s: *mut c_char) {
    if s.is_null() { return; }
    drop(CString::from_raw(s));                  // 다시 받아 해제
}
char *msg = mylib_greet("현우");
if (msg) { printf("%s\n", msg); mylib_string_free(msg); }   /* ★ 반드시 */
free() 로 해제하면 안 됩니다 — Rust 의 할당자와 C 의 malloc 은 다를 수 있습니다. 반드시 라이브러리가 제공한 해제 함수를 쓰게 하고, 헤더 주석에 명시하세요(f04).

규약을 이름으로 드러내기 ★

★ 네 가지 패턴과 이름 규칙

① 호출자가 버퍼를 준다 — 해제 불필요 (가장 안전) ★
   int32_t mylib_encode(const uint8_t *in, size_t in_len,
                        uint8_t *out, size_t out_cap, size_t *out_len);

② 라이브러리가 할당 — 짝이 되는 free 를 제공
   char *mylib_greet(const char *name);
   void  mylib_string_free(char *s);          ← 이름에 free 를 넣으세요

③ 정적 문자열 반환 — 해제 금지
   const char *mylib_version_string(void);    ← const 로 표시 + 문서에 명시

pub extern "C" fn mylib_encode_alloc(input: *const u8, len: usize) -> Buf {
    let Some(src) = (unsafe { to_slice(input, len) }) else {
        return Buf { ptr: std::ptr::null_mut(), len: 0, cap: 0 };
    };
    let mut v = encode(src);
    let b = Buf { ptr: v.as_mut_ptr(), len: v.len(), cap: v.capacity() };
    std::mem::forget(v);            // ★ Rust 가 해제하지 않게 (🔐 o01)
    b
}

#[no_mangle]
pub unsafe extern "C" fn mylib_buf_free(b: Buf) {
    if b.ptr.is_null() { return; }
    drop(Vec::from_raw_parts(b.ptr, b.len, b.cap));   // ★ cap 이 반드시 필요
}

// ❗ cap 을 안 돌려주면 Vec 을 복원할 수 없습니다.
//   len 만 알고 from_raw_parts(ptr, len, len) 하면
//   할당 크기가 달라 UB 입니다 ★

왜 free() 로 못 푸나

Rust 의 기본 할당자는 시스템 malloc 을 씁니다.
그래서 대부분의 플랫폼에서 free() 로도 '우연히' 동작합니다.

★ 하지만 의존하면 안 되는 이유
  · #[global_allocator] 를 바꾸면 즉시 깨집니다 (jemalloc · mimalloc)
  · 윈도우에서 MSVC CRT 가 다르면 힙이 다릅니다 ★
    (라이브러리는 /MD, 앱은 /MT 로 빌드된 경우 등)
  · Vec 은 크기·정렬 정보를 요구합니다 (dealloc(ptr, layout))
  · 미래에 Rust 가 할당 전략을 바꿀 수 있습니다

★ 결론
  반드시 짝이 되는 해제 함수를 제공하고,
  헤더 주석과 문서에 "free() 를 쓰지 마세요" 를 명시하세요.

use std::ffi::c_void;

pub type ProgressFn = extern "C" fn(progress: f32, user: *mut c_void);

#[no_mangle]
pub unsafe extern "C" fn mylib_process(
    data: *const u8, len: usize,
    cb: Option<ProgressFn>,        // ★ Option 으로 널 가능 (f03)
    user: *mut c_void,             // 호출자의 컨텍스트를 그대로 돌려줌
) -> i32 {
    let Some(src) = to_slice(data, len) else { return -1 };

    for (i, chunk) in src.chunks(4096).enumerate() {
        process_chunk(chunk);
        if let Some(f) = cb {
            f(i as f32 / (src.len() / 4096) as f32, user);    // ★ 호출
        }
    }
    0
}

// ★ user 포인터가 왜 필요한가
//   C 함수 포인터는 상태를 담을 수 없습니다 (클로저가 아님).
//   그래서 호출자가 자기 객체 주소를 user 로 주고,
//   콜백 안에서 그것을 다시 캐스팅해 씁니다.
typedef struct { int count; FILE *log; } Ctx;

static void on_progress(float p, void *user) {
    Ctx *c = (Ctx *)user;                    /* ★ 되돌리기 */
    c->count++;
    fprintf(c->log, "%.0f%%\n", p * 100);
}

Ctx ctx = { 0, stdout };
mylib_process(data, len, on_progress, &ctx);

Rust 안에서 클로저를 넘기려면

// Rust 클로저를 C 콜백으로 변환하는 관용구 (🔐 o11)
extern "C" fn trampoline<F: FnMut(f32)>(p: f32, user: *mut c_void) {
    let f = unsafe { &mut *(user as *mut F) };    // ★ 되돌리기
    f(p);
}

pub fn process_with<F: FnMut(f32)>(data: &[u8], mut f: F) -> i32 {
    unsafe {
        mylib_process(
            data.as_ptr(), data.len(),
            Some(trampoline::<F>),
            &mut f as *mut F as *mut c_void,      // 클로저 주소를 user 로
        )
    }
}

// 쓰는 쪽 — 안전한 Rust API 가 됩니다 ★
process_with(&data, |p| println!("{:.0}%", p * 100.0));

// 콜백 대신 상태를 조회하게 하기
use std::sync::atomic::{AtomicU64, Ordering};

pub struct Job { done: AtomicU64, total: u64 }

#[no_mangle]
pub unsafe extern "C" fn mylib_job_progress(j: *const Job) -> f32 {
    let Some(j) = j.as_ref() else { return 0.0 };
    j.done.load(Ordering::Relaxed) as f32 / j.total as f32
}

//   · 콜백 수명·GC 문제가 없습니다
//   · 스레드 안전을 원자 연산 하나로 해결
//   · 호출자가 원하는 주기로 확인 (UI 프레임에 맞춰서)
//   · 모든 언어에서 바인딩이 단순합니다

//   · 데이터를 스트리밍으로 흘려보낼 때 (전체를 메모리에 못 올림)
//   · 이벤트 발생 시점이 중요할 때
//   · 호출자가 흐름을 제어해야 할 때 (중단·필터)

콜백에서 지켜야 할 규칙

□ 콜백 안에서 패닉이 나면? (f09)
    Rust → 다른 언어 → Rust 로 되감기면 UB 입니다.
    → 콜백을 부르는 쪽(Rust)에서 catch_unwind 로 감쌀 수는 없습니다
      (콜백은 남의 코드입니다)
    → 각 언어 바인딩에서 예외를 잡아 에러 코드로 바꾸도록 문서화 ★

□ 콜백이 오래 걸리면?
    Rust 쪽 락을 잡은 채 콜백을 부르지 마세요 (데드락 · 🔐 o10)
    반드시 락을 놓고 부르세요

□ 콜백이 다시 라이브러리를 부르면? (재진입)
    허용할지 문서에 명시하세요. 대개 금지하는 편이 안전합니다.

□ 콜백이 반환값으로 중단을 표현할 수 있게
    typedef int (*ProgressFn)(float, void*);   /* 0 = 계속, 그 외 = 중단 */
    → 사용자가 취소할 수 있습니다 ★

□ 어느 스레드에서 불리는가
    메인 스레드 보장인지, 워커에서도 불리는지 명시하세요
    (UI 프레임워크는 대개 메인 스레드에서만 UI 를 만질 수 있습니다)
중단 신호를 반환값으로 두는 것은 비용이 0 이면서 매우 유용합니다. void 대신 int 를 반환하게 설계해 두면 나중에 취소 기능을 넣을 때 ABI 를 안 깨고 추가할 수 있습니다(f09).

// Rust 가 스레드를 만들어 콜백을 부르는 경우
#[no_mangle]
pub unsafe extern "C" fn mylib_start_async(
    cb: ProgressFn, user: *mut c_void,
) -> i32 {
    // ❗ 원시 포인터는 Send 가 아닙니다 — 래퍼가 필요합니다
    struct SendPtr(*mut c_void);
    unsafe impl Send for SendPtr {}          // ★ 안전성은 호출자와의 규약에 의존

    let u = SendPtr(user);
    std::thread::spawn(move || {
        let u = u;                            // 이동
        for i in 0..100 {
            cb(i as f32 / 100.0, u.0);        // 워커 스레드에서 호출 ★
        }
    });
    0
}

//   "콜백은 임의의 스레드에서 호출됩니다. 스레드 안전하게 작성하세요."
//
// ★ 언어별 함정
//   파이썬: GIL 이 필요합니다 — ctypes 콜백은 자동으로 잡아 줍니다
//   C#: UI 스레드가 아니면 Invoke 가 필요합니다

#[repr(C)]
pub struct Event { pub kind: i32, pub value: f64 }

#[no_mangle]
pub unsafe extern "C" fn mylib_poll_event(
    h: *mut Session, out: *mut Event,
) -> i32 {
    let Some(s) = h.as_mut() else { return -1 };
    match s.queue.pop() {                     // 논블로킹
        Some(ev) => { *out = ev; 1 }          // 1 = 이벤트 있음
        None => 0,                            // 0 = 없음
    }
}

// ★ 장점
//   · 콜백 수명·GC·스레드 문제가 전부 사라집니다

//   · 게임 엔진·UI 프레임워크와 궁합이 좋습니다 ★

// ★ 단점
//   · 폴링 주기만큼 지연이 생깁니다
//   · 큐가 넘칠 때의 정책이 필요합니다 (드롭 · 블로킹 · 확장)
여러 언어를 지원할수록 큐 방식이 유리합니다 — 콜백은 언어마다 다른 함정(GC · GIL · UI 스레드)이 있지만, 폴링은 어디서나 똑같이 동작합니다.
정리 — C ABI 콜백은 함수 포인터 + void* user data 가 공통 관용구입니다. 콜백 객체의 수명은 호출자 책임이고 GC 함정이 언어마다 있으니 문서에 경고하세요. 중단 신호를 반환값으로 두면 나중에 취소 기능을 ABI 를 깨지 않고 추가할 수 있고, 여러 언어를 지원한다면 폴링·큐 방식이 훨씬 단순합니다.

use foo_sys as ffi;
use std::ptr::NonNull;

pub struct Context {
    raw: NonNull<ffi::FooContext>,      // ★ 널이 아님을 타입으로 (r08)
}

impl Context {
    pub fn new() -> Result<Self, Error> {
        let raw = unsafe { ffi::foo_create() };
        NonNull::new(raw)
            .map(|raw| Context { raw })
            .ok_or(Error::AllocFailed)
    }

    pub fn process(&mut self, input: &[u8]) -> Result<Vec<u8>, Error> {
        let mut out_len: usize = 0;
        let rc = unsafe {
            ffi::foo_process(self.raw.as_ptr(),
                             input.as_ptr(), input.len(),
                             std::ptr::null_mut(), 0, &mut out_len)
        };
        if rc != 0 && rc != ffi::FOO_BUFFER_TOO_SMALL { return Err(Error::from(rc)); }

        let mut buf = vec![0u8; out_len];
        let rc = unsafe {
            ffi::foo_process(self.raw.as_ptr(),
                             input.as_ptr(), input.len(),
                             buf.as_mut_ptr(), buf.len(), &mut out_len)
        };
        if rc != 0 { return Err(Error::from(rc)); }
        buf.truncate(out_len);
        Ok(buf)
    }
}

impl Drop for Context {
    fn drop(&mut self) { unsafe { ffi::foo_destroy(self.raw.as_ptr()) } }
}

문서를 읽고 확인할 것 ★

□ 스레드 안전한가
    · 전역 상태를 쓰는가 (errno 같은 것)
    · 초기화 함수가 한 번만 불려야 하는가 → OnceLock (r02)
    · 컨텍스트별로는 안전한가 → Send 만 붙이고 Sync 는 금지

□ 재진입 가능한가 (콜백 안에서 다시 부를 수 있나)

□ 반환된 포인터의 수명은
    · 정적인가 (해제 금지)
    · 다음 호출까지만 유효한가 ★ (strtok 같은 것)
    · 호출자가 해제하는가 → Drop 으로

□ 에러를 어떻게 알리나
    · 반환값 · errno · 별도 함수 (f09)
    · errno 는 스레드 로컬입니다 — 호출 직후에 읽어야 합니다

□ 시그널·longjmp 를 쓰는가 ★
    · setjmp/longjmp 가 Rust 스택을 건너뛰면 Drop 이 안 불립니다
    · libpng · libjpeg 이 이 방식을 씁니다 — 주의가 필요합니다

□ 할당자를 교체할 수 있나
    · 그렇다면 Rust 할당자와 맞춰 둘 수 있습니다

FFI 09

패닉이 경계를 넘으면 — 그리고 에러 코드

Rust 패닉이 C 코드를 가로질러 되감기면 정의되지 않은 동작입니다. 그래서 모든 extern "C" 함수는 패닉을 가두고 에러 코드로 바꿔야 합니다. 이 섹션은 FFI 에서 가장 중요한 안전 규칙입니다.

라이브러리로 배포한다면 ①번을 반드시 하세요 — ②는 쓰는 쪽의 선택이라 강제할 수 없습니다.

catch_unwind 로 가두기 ★

use std::panic::{catch_unwind, AssertUnwindSafe};

#[no_mangle]
pub unsafe extern "C" fn mylib_process(data: *const u8, len: usize) -> i32 {
    let result = catch_unwind(AssertUnwindSafe(|| {
        let Some(src) = to_slice(data, len) else { return -1 };
        match core_process(src) {
            Ok(_) => 0,
            Err(e) => { set_last_error(e.to_string()); code_of(&e) }
        }
    }));

    match result {
        Ok(code) => code,
        Err(_) => {                                  // ★ 패닉을 잡았습니다
            set_last_error("내부 오류 (패닉)".into());
            -99
        }
    }
}

// 매크로로 반복을 줄이기
macro_rules! ffi_guard {
    ($body:expr) => {
        match std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| $body)) {
            Ok(v) => v,
            Err(_) => { set_last_error("내부 오류 (패닉)".into()); -99 }
        }
    };
}

#[no_mangle]
pub unsafe extern "C" fn mylib_encode(...) -> i32 {
    ffi_guard!({ /* 본문 */ })
}
Rust 2024 에디션부터 extern "C" 함수는 패닉 시 기본적으로 abort 합니다. UB 는 피하지만 프로세스가 죽습니다 — 파이썬 인터프리터나 Node 서버가 통째로 종료되는 것은 여전히 최악이므로, 잡아서 에러 코드로 바꾸는 것이 정답입니다.

use std::cell::RefCell;
thread_local! {
    static LAST_ERROR: RefCell<String> = RefCell::new(String::new());
}

fn set_last_error(msg: String) {
    LAST_ERROR.with(|e| *e.borrow_mut() = msg);
}

#[no_mangle]
pub unsafe extern "C" fn mylib_last_error(buf: *mut c_char, cap: usize) -> usize {
    LAST_ERROR.with(|e| {
        let s = e.borrow();
        let bytes = s.as_bytes();
        let n = bytes.len().min(cap.saturating_sub(1));
        if !buf.is_null() && cap > 0 {
            std::ptr::copy_nonoverlapping(bytes.as_ptr(), buf as *mut u8, n);
            *buf.add(n) = 0;                      // 널 종단 ★
        }
        bytes.len()                                // 전체 길이를 반환 (버퍼 크기 판단용)
    })
}

pub unsafe extern "C" fn mylib_init(opts: *const Options) -> i32 {
    let size = if opts.is_null() { 0 } else { (*opts).size as usize };

    let threads = if size >= offset_of!(Options, threads) + 4 {
        (*opts).threads
    } else { 0 };

    let retries = if size >= offset_of!(Options, retries) + 4 {
        (*opts).retries                          // ★ v2 이상만
    } else { 3 };                                // v1 이면 기본값

    // …
    0
}

// 호출자 (C)
//   Options o = {0};
//   o.size = sizeof(o);       ← 자기가 아는 크기를 알려 줍니다
//   o.threads = 4;
//   mylib_init(&o);
//
// → 옛 헤더로 컴파일된 앱도, 새 헤더로 컴파일된 앱도 모두 동작합니다 ★

왜 UB 인가

Rust 패닉은 기본적으로 '스택 되감기(unwinding)' 입니다.
C++ 예외와 같은 메커니즘(DWARF/SEH)을 씁니다.

  Rust 함수 → C 함수 → Rust 콜백에서 패닉
                ↑
            여기를 되감으려면 C 프레임의 정리 정보가 필요한데,
            C 는 그런 정보를 갖고 있지 않습니다.
            → 정의되지 않은 동작 (대개 abort 또는 힙 손상) ★

★ 대응
  ① 모든 extern "C" 함수를 catch_unwind 로 감싸기 (이 섹션)
  ② panic = "abort" 프로파일 — 되감기 자체가 없어집니다
     · 바이너리가 작아지고 약간 빨라집니다 (🛠️ b10)
     · 하지만 패닉 = 프로세스 종료입니다
     · PyO3 에서는 쓰지 마세요 (예외로 못 바꿈 · 🐍 y03)
  ③ extern "C-unwind" — 되감기를 명시적으로 허용하는 ABI
     C++ 예외와 상호 운용해야 할 때만 (Rust 1.71+)

# 확인
cargo rustc --release -- --print cfg | grep panic
RUST_BACKTRACE=1 ./app

패닉을 아예 줄이기 ★

// catch_unwind 는 안전망이지, 설계가 아닙니다.
// FFI 층에서는 패닉이 날 일 자체를 없애세요.

// ❌ 패닉하는 코드
v[i]                        // 범위 초과 → panic
s.unwrap()                  // None → panic
a / b                       // b == 0 → panic (정수)
x as usize                  // 음수 → 릴리즈에선 거대한 수 (r02)

// ✅
v.get(i).ok_or(Code::InvalidArg)?
s.ok_or(Code::NotFound)?
a.checked_div(b).ok_or(Code::InvalidArg)?
usize::try_from(x).map_err(|_| Code::InvalidArg)?

// clippy 로 강제하기
//   #![deny(clippy::unwrap_used, clippy::expect_used,
//           clippy::indexing_slicing, clippy::panic)]
//   FFI 모듈에만 붙이면 실용적입니다 ★

// 할당 실패는 잡을 수 없습니다
//   Rust 는 OOM 시 abort 합니다 (catch_unwind 로 못 잡습니다)
//   큰 할당은 try_reserve 로 미리 확인하세요
let mut v = Vec::new();
v.try_reserve(n).map_err(|_| Code::Internal)?;
FFI 모듈에 #![deny(clippy::unwrap_used)] 를 붙이세요 — 패닉 가능성을 컴파일 타임에 제거하는 것이 catch_unwind 로 잡는 것보다 훨씬 낫습니다.
정리 — 모든 extern "C" 함수는 catch_unwind 로 패닉을 가두고 에러 코드 + last_error 함수로 실패를 알립니다. 에러 코드 숫자는 한 번 배포하면 절대 바꾸지 마세요. 확장은 새 함수 · 새 코드 · 크기 필드가 든 구조체로 하고, FFI 층에는 unwrap·인덱싱을 clippy 로 금지하세요.

C# — P/Invoke

using System;
using System.Runtime.InteropServices;

internal static partial class Native
{
    private const string Lib = "mylib";      // libmylib.so / mylib.dll

    // .NET 7+ 의 소스 생성 방식 (더 빠릅니다) ★
    [LibraryImport(Lib)]
    internal static partial int mylib_add(int a, int b);

    [LibraryImport(Lib, StringMarshalling = StringMarshalling.Utf8)]
    internal static partial IntPtr mylib_greet(string name);

    [LibraryImport(Lib)]
    internal static partial void mylib_string_free(IntPtr s);

    // 예전 방식
    [DllImport(Lib, CallingConvention = CallingConvention.Cdecl)]
    internal static extern double mylib_distance(Point a, Point b);
}

[StructLayout(LayoutKind.Sequential)]        // ★ #[repr(C)] 에 대응 (f03)
internal struct Point { public double X, Y; }

// 안전한 래퍼
public static string Greet(string name)
{
    IntPtr p = Native.mylib_greet(name);
    if (p == IntPtr.Zero) throw new InvalidOperationException(LastError());
    try { return Marshal.PtrToStringUTF8(p)!; }
    finally { Native.mylib_string_free(p); }  // ★ 반드시 해제 (f06)
}

Go — cgo

package mylib

/*
#cgo LDFLAGS: -L${SRCDIR}/lib -lmylib
#cgo CFLAGS: -I${SRCDIR}/include
#include "mylib.h"
#include <stdlib.h>
*/
import "C"
import (
    "errors"
    "unsafe"
)

func Add(a, b int32) int32 {
    return int32(C.mylib_add(C.int32_t(a), C.int32_t(b)))
}

func Greet(name string) (string, error) {
    cname := C.CString(name)               // Go → C 문자열 (복사)
    defer C.free(unsafe.Pointer(cname))    // ★ C 힙이므로 free

    p := C.mylib_greet(cname)
    if p == nil { return "", errors.New(lastError()) }
    defer C.mylib_string_free(p)           // ★ 라이브러리 해제 함수 (f06)
    return C.GoString(p), nil
}

// 슬라이스 넘기기 — 복사 없음
func Checksum(data []byte) uint32 {
    if len(data) == 0 { return 0 }
    return uint32(C.mylib_checksum(
        (*C.uint8_t)(unsafe.Pointer(&data[0])), C.size_t(len(data))))
}
// ❗ Go 의 GC 가 데이터를 옮길 수 있습니다.
//    호출 중에는 안전하지만, C 쪽이 포인터를 보관하면 안 됩니다 ★

#[no_mangle] pub extern "C" fn mylib_noop() {}
#[no_mangle] pub extern "C" fn mylib_add_bench(a: i32, b: i32) -> i32 { a + b }
#[no_mangle] pub unsafe extern "C" fn mylib_sum_bench(p: *const f64, n: usize) -> f64 {
    if p.is_null() || n == 0 { return 0.0 }
    std::slice::from_raw_parts(p, n).iter().sum()
}
# 파이썬 쪽 측정
import timeit
print(timeit.timeit(lambda: lib.mylib_noop(), number=1_000_000))
# 이 값이 '호출 하나의 하한선' 입니다 ★

# 데이터 크기별로 재서 손익분기점을 찾으세요
for n in (10, 100, 1_000, 100_000):
    a = np.random.random(n)
    p = a.ctypes.data_as(ctypes.POINTER(ctypes.c_double))
    t_rust = timeit.timeit(lambda: lib.mylib_sum_bench(p, n), number=10_000)
    t_np   = timeit.timeit(lambda: a.sum(), number=10_000)
    print(n, t_rust, t_np)
# ★ 작은 n 에서는 numpy 가 이기고, 큰 n 에서 역전되는 지점이 보입니다

정리 — C ABI 하나면 C# · 자바 · Go · Ruby · Swift 어디서나 부를 수 있고, 패턴은 로드 → 시그니처 선언 → 호출 → 해제로 같습니다. 각 언어 바인딩에 스모크 테스트를 두고 CI 에서 돌리고, 런타임 버전 확인으로 불일치를 즉시 드러내세요. 언어를 늘리는 비용은 실제로 크니 필요한 것만 지원하는 편이 낫습니다. 다음은 🛠️ 빌드 · 배포 탭입니다.
언어를 넘나드는 코드의 가치는 성능보다 같은 로직을 한 번만 관리한다는 데 있습니다.
