PERF 01

측정 먼저 — criterion 과 프로파일러

최적화에서 가장 흔한 실패는 엉뚱한 곳을 고치는 것입니다. --release 로 빌드했는지, 워밍업을 했는지, 컴파일러가 코드를 지우지는 않았는지 — 측정이 틀리면 그다음 판단이 전부 틀립니다.

criterion 으로 재기 ★

# Cargo.toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "my_bench"
harness = false              # ★ 필수 (b02)
// benches/my_bench.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion, BenchmarkId};

fn bench_sum(c: &mut Criterion) {
    let data: Vec<f64> = (0..10_000).map(|x| x as f64).collect();

    c.bench_function("sum_iter", |b| {
        b.iter(|| black_box(&data).iter().sum::<f64>())
        //     ^^^^^^^^^^ ★ 컴파일러가 계산을 지우지 못하게 막습니다
    });

    // 크기별 비교 — 손익분기점을 찾을 때 (⚡ e05)
    let mut g = c.benchmark_group("sum");
    for n in [100, 1_000, 100_000] {
        let v: Vec<f64> = (0..n).map(|x| x as f64).collect();
        g.bench_with_input(BenchmarkId::new("seq", n), &v, |b, v| {
            b.iter(|| v.iter().sum::<f64>())
        });
    }
    g.finish();
}

criterion_group!(benches, bench_sum);
criterion_main!(benches);
cargo bench
#   target/criterion/report/index.html  ← 그래프 · 이전 실행과 비교 ★
cargo bench -- sum_iter          # 이름으로 필터
cargo bench -- --save-baseline before
cargo bench -- --baseline before # 개선 전후 비교 ★

측정이 틀리는 다섯 가지 ★

① --release 를 안 씀
     디버그 빌드는 10~100배 느립니다 (b06)
     cargo bench 는 자동으로 릴리즈이지만,
     직접 잰다면 반드시 --release ★

② 컴파일러가 계산을 지움
     결과를 안 쓰면 통째로 삭제됩니다 (⚡ e03)
     → black_box() 로 막으세요

③ 워밍업 없음
     첫 실행은 캐시가 비어 있어 느립니다
     criterion 이 자동으로 처리합니다

④ 입력이 비현실적
     정렬된 배열 · 전부 같은 값 · 너무 작은 데이터
     → 실제 데이터를 쓰거나 비슷하게 생성하세요 ★

⑤ 환경 노이즈
     다른 프로세스 · CPU 주파수 변동 · 서멀 스로틀링
     → 여러 번 재고 중앙값을 보세요 (criterion 이 통계를 냅니다)
     → CI 에서 잰 절대값은 믿지 마세요 (b08)

★ 상대 비교를 하세요
  "2.3ms" 보다 "이전 대비 40% 빠름" 이 훨씬 신뢰할 수 있습니다.

★ 실제 워크로드와 벤치마크가 갈리는 지점

① 캐시 상태
   벤치마크는 같은 데이터를 반복해 L1/L2 에 다 들어가 있습니다.
   실제로는 캐시 미스가 훨씬 많습니다 (e04)
   → 데이터 크기를 캐시보다 크게 잡아 보세요

② 분기 예측
   같은 입력을 반복하면 분기가 100% 예측됩니다.
   실제 데이터는 예측이 자주 빗나갑니다
   → 무작위 입력도 함께 재세요

③ 할당자 상태
   반복하면 할당자가 워밍업되어 빨라집니다 (e02)

④ 단일 스레드 가정
   실제 서버는 여러 요청이 동시에 돕니다.
   메모리 대역폭·캐시를 공유하므로 코어 수만큼 빨라지지 않습니다 (e05)

⑤ 전체 시스템에서의 비중
   함수를 100배 빠르게 해도 전체의 2% 면 전체는 2% 만 빨라집니다
   → 엔드투엔드 측정을 반드시 함께 하세요 ★

★ 결론: 마이크로 벤치마크로 '방향'을 잡고,
  엔드투엔드 측정으로 '결정'하세요.

PERF 02

할당 줄이기 — 느린 Rust 의 90%

Rust 코드가 기대만큼 안 빠른 이유는 대부분 하나입니다 — 불필요한 .clone() 과 to_string(). 소유권 에러를 clone 으로 넘긴 코드가 루프 안에 있으면 C++ 보다 느려집니다. 여기가 가장 먼저 볼 곳입니다.

전형적인 패턴 ★

// ❌ 루프 안의 clone
for row in &rows {
    process(row.clone());              // 매번 힙 할당 + 복사
}
// ✅
for row in &rows {
    process(row);                      // 빌려 주기 (🔐 o02)
}

// ❌ 문자열을 매번 만들기
for u in &users {
    let key = format!("{}:{}", u.id, u.name);   // 할당 1회씩
    map.insert(key, u);
}
// ✅ 버퍼 재사용
let mut key = String::with_capacity(64);
for u in &users {
    key.clear();                       // ★ 용량은 유지됩니다
    use std::fmt::Write;
    write!(key, "{}:{}", u.id, u.name).unwrap();
    map.insert(key.clone(), u);        // 여기선 어쩔 수 없이 1회
}

use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering};

static ALLOCS: AtomicUsize = AtomicUsize::new(0);
struct Counting;
unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, l: Layout) -> *mut u8 {
        ALLOCS.fetch_add(1, Ordering::Relaxed);
        System.alloc(l)
    }
    unsafe fn dealloc(&self, p: *mut u8, l: Layout) { System.dealloc(p, l) }
}
#[global_allocator] static A: Counting = Counting;

PERF 03

이터레이터가 for 만큼 빠른 이유

.iter().map().filter().sum() 이 손으로 쓴 for 문과 같은 기계어가 됩니다. “추상화에는 비용이 없다(zero-cost)”는 말의 실체를 어셈블리로 직접 확인하고, 그 최적화가 깨지는 조건도 함께 봅니다.

# 결과에서 확인할 것

  · SIMD 명령이 있는가 (vpaddq · paddd 등 · e09)
  · 함수 호출이 남아 있는가 (인라인이 안 된 것)

왜 사라지나

① 어댑터는 전부 구조체입니다
     Map<Filter<slice::Iter<u64>>>
     각자 next() 를 구현합니다

② 전부 제네릭이라 단형화됩니다 (r10)
     타입이 정확히 정해지므로 동적 호출이 없습니다

③ next() 가 인라인됩니다
     #[inline] 이 붙어 있고, 본체가 작습니다

④ 인라인 후 LLVM 이 루프 하나로 합칩니다
     중간 구조체는 레지스터로 사라집니다

⑤ 범위 검사 제거
     슬라이스 이터레이터는 포인터를 직접 전진시키므로
     인덱싱과 달리 검사가 아예 없습니다 ★

★ 그래서 오히려 이터레이터가 빠를 수 있습니다.
  v[i] 는 매번 i < len 을 확인해야 합니다.

fn dot(a: &[f64], b: &[f64]) -> f64 {

    for i in 0..n { s += a[i] * b[i]; }
    s
}

주요 최적화 패스

인라인 확장 (inlining)
  작은 함수 본체를 호출부에 펼칩니다. 다른 모든 최적화의 전제입니다.

  map 과 filter 가 각각 루프를 만들지 않고 하나로 합쳐집니다.

스칼라 치환 (SROA)

벡터화 (SLP / loop vectorization)

PERF 04

메모리 레이아웃과 캐시

같은 알고리즘도 데이터가 메모리에 어떻게 놓여 있느냐에 따라 수 배가 갈립니다. CPU 는 이미 충분히 빠르고, 대부분의 시간을 메모리를 기다리며 보냅니다. 네이티브 언어를 쓰는 진짜 이유가 여기 있습니다 — 배치를 내가 정할 수 있습니다.

비용의 크기 ★

메모리 계층 (대략적인 지연 · CPU 마다 다릅니다)
  레지스터        0 사이클
  L1 캐시         ~4 사이클
  L2 캐시         ~12 사이클
  L3 캐시         ~40 사이클
  RAM             ~200~300 사이클 ★ L1 의 50배 이상
  SSD             ~수만 사이클

★ 의미
  덧셈 하나가 1 사이클인데 RAM 접근이 200 사이클입니다.
  → "계산을 줄이는 것" 보다 "메모리 접근을 줄이는 것" 이 대개 큽니다.

캐시 라인 = 64바이트 ★
  메모리는 64바이트 단위로 읽힙니다.
  u64 하나를 읽어도 그 주변 8개가 함께 옵니다.
  → 연속으로 접근하면 공짜, 흩어져 접근하면 매번 비용

lscpu | grep -i cache

//   나머지 60바이트는 낭비입니다 ★

작업 훔치기(work stealing)

rayon 은 작업을 재귀적으로 반으로 쪼개고,
놀고 있는 스레드가 남의 작업을 훔쳐 갑니다.

  · 스레드 수를 신경 쓸 필요가 없습니다
  · 다만 쪼개는 것 자체에 비용이 있습니다

병렬화 전에 e02(할당)와 e04(배치)를 먼저 하세요. 느린 코드를 8배 빠르게 하는 것보다, 먼저 100배 빠르게 만든 뒤 병렬화하는 편이 훨씬 큽니다.
정리 — .iter() → .par_iter() 여섯 글자면 전 코어를 씁니다. 작은 데이터에는 손해이니 임계값을 측정으로 정하고, 결과는 collect/sum/fold+reduce 로 모으세요(Mutex 로 모으면 이득이 사라집니다). 스케일이 안 나오면 메모리 대역폭을 먼저 의심하세요.
PERF 06

Send · Sync — 데이터 경쟁이 빌드 에러

다른 언어에서 동시성 버그는 운영에서 가끔 터지는 재현 불가능한 문제였습니다. Rust 에서는 컴파일 에러입니다. 그 장치가 Send 와 Sync 두 트레이트입니다 — 이 탭에서 가장 중요한 개념입니다.

두 트레이트의 뜻 ★

Send  — "이 값을 다른 스레드로 '보내도' 안전하다"
        소유권을 옮기는 것

Sync  — "이 값을 여러 스레드가 '동시에 참조해도' 안전하다"
        &T 가 Send 인 것과 같습니다

★ 대부분의 타입은 둘 다 자동으로 구현됩니다 (auto trait)
  구성 요소가 전부 Send/Sync 면 자동으로 Send/Sync 입니다.

★ 아닌 것들
  Rc<T>        !Send, !Sync   카운터가 원자적이지 않음 (🔐 o10)
  RefCell<T>   Send,  !Sync   빌림 검사가 원자적이지 않음
  Cell<T>      Send,  !Sync
  *const T     !Send, !Sync   원시 포인터 (🔬 d03)
  MutexGuard   !Send          락을 잡은 스레드가 풀어야 함

★ 조합
  Arc<T>       T: Send+Sync 면 Send+Sync ★
  Mutex<T>     T: Send 면 Send+Sync ★ (락이 보호하므로)
  RwLock<T>    T: Send+Sync 면 Send+Sync

컴파일러가 막는 모습

use std::rc::Rc;
use std::sync::Arc;

let data = Rc::new(vec![1, 2, 3]);
// std::thread::spawn(move || { println!("{:?}", data); });
//   error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely ★
//   help: within this `{closure}`, the trait `Send` is not implemented

// ✅ Arc 로 (🔐 o10)
let data = Arc::new(vec![1, 2, 3]);
let d = Arc::clone(&data);
std::thread::spawn(move || { println!("{:?}", d); });

// 공유 가변 상태
// let counter = Rc::new(RefCell::new(0));       // ❌ 스레드 불가
let counter = Arc::new(Mutex::new(0));           // ✅
let c = Arc::clone(&counter);
std::thread::spawn(move || { *c.lock().unwrap() += 1; });

// ★ 핵심: "실수로 스레드 간 공유" 가 불가능합니다.
//   C++ 에서는 그냥 컴파일되고, 가끔 값이 깨집니다.
//   Rust 에서는 빌드가 안 됩니다.
이것이 “fearless concurrency”의 실체입니다 — 용감해서가 아니라 컴파일러가 검사해 주기 때문에 겁내지 않아도 됩니다. rayon 을 마음 놓고 쓸 수 있는 이유이기도 합니다(e05).

이렇게도 쓸 수 있다 — 에러를 읽고 푸는 법 🟡 중급

자주 만나는 에러와 처방 ★

① `Rc<T>` cannot be sent between threads safely
     → Arc 로 바꾸세요

② `RefCell<T>` cannot be shared between threads safely
     → Mutex 나 RwLock 으로

③ `*mut T` cannot be sent between threads safely
     → 래퍼 타입을 만들고 unsafe impl Send (🔗 f07 · 🔬 d08)
       단, 정말 안전한지 스스로 증명해야 합니다 ★

④ closure may outlive the current function
     → move 를 붙이거나 thread::scope 를 쓰세요 (🔐 o03 · e07)

⑤ borrowed value does not live long enough
     → 'static 이 필요합니다 → 소유 값으로 넘기기

⑥ `MutexGuard` cannot be sent between threads safely (async)
     → await 를 넘어 락을 들고 있습니다 → 범위를 좁히세요 (e08)

★ 대부분의 처방이 정해져 있습니다.
  에러 메시지의 `help:` 를 읽으면 대개 답이 있습니다 (r01).

타입이 Send/Sync 인지 확인하기

// 컴파일 타임 검사 — 테스트로 두면 회귀를 막습니다 ★
fn assert_send<T: Send>() {}
fn assert_sync<T: Sync>() {}

#[test]
fn types_are_thread_safe() {
    assert_send::<MyHandle>();
    assert_sync::<MyHandle>();
    assert_send::<MyError>();          // 에러도 Send 여야 유용합니다 (🔐 o09)
}

// 또는 상수로
const _: () = {
    fn check<T: Send + Sync>() {}
    fn assert_all() { check::<MyHandle>(); }
};

// ★ 라이브러리를 만든다면 이 테스트를 반드시 두세요.
//   나중에 필드에 Rc 를 하나 추가하면 조용히 !Send 가 되고,
//   사용자의 멀티스레드 코드가 깨집니다.

// 왜 Send 가 아닌지 알아내기
// let _: &dyn Send = &my_value;
//   → 에러 메시지가 어느 필드 때문인지 알려 줍니다 ★

실무에선 이렇게 — FFI 에서의 Send/Sync 🔴 실무

직접 붙여야 할 때 ★

// C 라이브러리 핸들을 감쌀 때 (🔗 f08)
pub struct Decoder { raw: *mut ffi::Decoder }

// 원시 포인터가 있어 자동으로 !Send, !Sync 입니다.
// C 문서를 읽고 판단해 직접 붙입니다.

// ★ 판단 기준
//   "이 핸들을 다른 스레드로 옮겨도 되나?"        → Send
//   "여러 스레드가 동시에 써도 되나?"             → Sync

// 대부분의 C 라이브러리는
unsafe impl Send for Decoder {}      // 컨텍스트별로는 안전한 경우가 많음
// unsafe impl Sync for Decoder {}   // ❌ 동시 접근은 대개 불가

// Sync 가 필요하면 락으로 감싸세요
pub struct SharedDecoder(Mutex<Decoder>);
// → Mutex<T> 는 T: Send 면 Sync 입니다 ★

// ❗ unsafe impl 은 '컴파일러에게 하는 약속' 입니다.
//   틀리면 데이터 경쟁이 나고, 그건 UB 입니다 (🔬 d02).
//   반드시 근거를 주석으로 남기세요
// SAFETY: libfoo 문서에 따르면 Decoder 는 한 번에 한 스레드에서만
//         사용하면 안전하며, 스레드 간 이동은 허용됩니다.
//         (docs: https://... section 3.2)

파이썬·Node 바인딩에서

// 🐍 PyO3 (y05 · y07)
//   Py<T> 는 Send 입니다 (GIL 로 보호되므로)
//   Bound<'py, T> 는 !Send (GIL 에 묶여 있음)
//   → allow_threads 클로저에 Bound 를 넣으면 컴파일 에러 ★ 안전합니다

#[pyclass]
struct Handle { inner: Mutex<Decoder> }   // frozen + Mutex 가 안전 (y05)

// 🟨 napi-rs (j05·j07)
//   AsyncTask 의 compute 는 워커 스레드에서 돕니다
//   → Task 구조체가 Send 여야 합니다
//   JsObject · Env 는 !Send — 워커로 못 넘깁니다 (설계상 안전)

// 🔗 C ABI 콜백 (f07)
//   *mut c_void user data 를 스레드로 넘기려면 래퍼가 필요합니다
struct SendPtr(*mut c_void);
unsafe impl Send for SendPtr {}
// SAFETY: 호출자가 스레드 안전한 포인터를 준다고 문서에 명시함

// ★ 공통 원칙
//   각 바인딩 프레임워크가 !Send 로 막아 주는 것들은
//   전부 '이유가 있어서' 막는 것입니다. 우회하기 전에 왜인지 이해하세요.
unsafe impl Send/Sync 는 신중하게 — 이것이 틀리면 Rust 의 동시성 보장이 통째로 무너집니다. SAFETY 주석에 근거(문서 링크·조건)를 반드시 남기세요(🔬 d08).

한 단계 더 — auto trait 의 동작 🧬 전문가

자동 구현과 부정 구현

// Send/Sync 는 'auto trait' 입니다
//   구성 요소가 전부 만족하면 자동으로 구현됩니다
struct A { x: u32, y: String }        // 자동으로 Send + Sync
struct B { x: u32, y: Rc<u32> }       // Rc 때문에 !Send, !Sync

// 명시적으로 막기 (nightly 에서만 negative impl)
// impl !Send for MyType {}

// 안정 버전에서 !Send 로 만드는 방법 ★
use std::marker::PhantomData;
use std::rc::Rc;

pub struct NotSend {
    data: u32,
    _marker: PhantomData<Rc<()>>,      // ★ Rc 를 담은 척 → !Send
}

// PhantomData 의 다른 용도
//   PhantomData<T>           T 를 소유한 것처럼 (드롭 검사)
//   PhantomData<&'a T>       라이프타임을 붙들기 (🔐 o03 의 변성)
//   PhantomData<*const T>    !Send + !Sync

// 제네릭에서 전파
struct Wrapper<T>(T);
// Wrapper<u32> 는 Send, Wrapper<Rc<u32>> 는 !Send — 자동으로 따라갑니다 ★

Rust 가 막지 못하는 것

★ Send/Sync 가 보장하는 것
  · 데이터 경쟁 없음 (data race)
    = 두 스레드가 동기화 없이 같은 메모리를 쓰는 일

★ 보장하지 않는 것
  · 데드락 ★
      두 락을 다른 순서로 잡으면 여전히 멈춥니다 (🔐 o10)
  · 경쟁 조건 (race condition)
      논리적 순서 문제는 타입으로 못 막습니다
      예: 잔액을 읽고 → 검사하고 → 쓰는 사이에 다른 스레드가 바꿈
      → 트랜잭션이나 CAS 로 해결해야 합니다 (🔬 d06)
  · 메모리 누수
      Rc 순환은 안전한 코드로도 샙니다 (🔐 o10)
  · 성능 문제
      락 경합·false sharing 은 컴파일러가 모릅니다 (e04)

★ 그래도 큰 차이입니다
  데이터 경쟁은 '재현 불가능한 버그' 의 주범이었습니다.
  그것 하나가 사라진 것만으로 디버깅 시간이 크게 줍니다.

# 데드락 진단
#   parking_lot 의 deadlock_detection feature
#   gdb: thread apply all bt
#   tokio-console (async · e08)
정리 — Send=다른 스레드로 보내도 됨, Sync=동시에 참조해도 됨입니다. 대부분 자동으로 구현되고, Rc·RefCell·원시 포인터가 예외입니다. 데이터 경쟁이 컴파일 에러가 되지만 데드락은 못 막습니다. FFI 핸들에 unsafe impl Send 를 붙일 때는 SAFETY 주석에 근거를 남기세요.

□ Mutex 안에 Mutex 를 두지 마세요

★ 진단
  · parking_lot 의 deadlock_detection feature
  · gdb -p PID → thread apply all bt
  · 스레드 이름을 붙여 두면 덤프가 읽힙니다

  · 타임아웃 있는 락 (try_lock_for) 으로 조기 발견

★ 락 오염 (poisoning)

PERF 08

async — 언제 쓰고 언제 쓰지 않나

async 는 기다림이 많을 때만 이득입니다. 계산이 많으면 오히려 손해이고, 코드도 복잡해집니다. 네이티브 모듈에서는 대개 필요 없습니다 — 그럼에도 알아야 하는 이유와, 필요할 때 쓰는 법을 봅니다.

CPU 는 한 명령으로 여러 값을 동시에 계산할 수 있습니다. 대부분은 컴파일러가 알아서 해 줍니다 — 우리가 할 일은 그렇게 되도록 코드를 정리하는 것이고, 직접 쓰는 것은 마지막 수단입니다.

자동 벡터화를 유도하기 ★

// ✅ 벡터화되기 쉬운 코드
pub fn scale(v: &mut [f32], k: f32) {
    for x in v.iter_mut() { *x *= k; }      // ★ 단순 · 분기 없음 · 연속
}

pub fn dot(a: &[f32], b: &[f32]) -> f32 {
    let n = a.len().min(b.len());
    a[..n].iter().zip(&b[..n]).map(|(x, y)| x * y).sum()
}

// ❌ 벡터화를 막는 것들
//   · 분기 (if 가 원소마다 다르게 갈림)
//   · 조기 종료 (break · ?)
//   · 함수 호출 (인라인 안 되면)
//   · 원소 간 의존 (앞 결과를 다음에 씀)
//   · 범위 검사 (e03)
//   · f64 합의 순서 문제 (e03) ★

// ✅ 분기를 산술로 바꾸기
// for x in v { if *x < 0.0 { *x = 0.0 } }        // 분기
for x in v.iter_mut() { *x = x.max(0.0); }        // ★ 벡터화됩니다

// ✅ 청크로 나누어 힌트 주기
for c in v.chunks_exact_mut(8) {

// ① wide · simba 크레이트 (안정 버전에서 쓸 수 있습니다)
use wide::f32x8;
pub fn scale(v: &mut [f32], k: f32) {
    let kv = f32x8::splat(k);
    for c in v.chunks_exact_mut(8) {
        let x = f32x8::from(&c[..8]) * kv;
        c.copy_from_slice(x.as_array_ref());
    }
    // 나머지 처리
    let rem = v.len() % 8;
    for x in &mut v[v.len() - rem..] { *x *= k; }
}

한 단계 더 — 벡터화의 안쪽 🧬 전문가

LLVM 이 하는 두 가지

① 루프 벡터화 (loop vectorization)
   for i in 0..n { c[i] = a[i] + b[i] }
   → 4개씩(또는 8개씩) 묶어 한 명령으로

   조건
   · 반복 횟수를 알거나 런타임에 확인 가능
   · 메모리 접근이 겹치지 않음 (aliasing · 🔬 d03) ★
     → Rust 의 &mut 는 배타적이라 aliasing 정보가 정확합니다
       C 의 restrict 를 항상 붙인 것과 같은 효과입니다 ★
   · 원소 간 의존이 없음

② SLP 벡터화 (superword level parallelism)
   독립적인 연산 여러 개를 묶습니다
   let (x, y, z) = (a.0 * k, a.1 * k, a.2 * k);   // 한 명령으로

★ Rust 가 C 보다 유리한 지점
  &mut T 는 "이 참조로만 접근한다" 는 보장입니다 (🔐 o02).
  LLVM 이 noalias 를 붙일 수 있어 더 공격적으로 최적화합니다.
  → 같은 코드에서 Rust 가 C 보다 빠른 경우가 여기서 나옵니다.

// 길이를 맞춰 힌트 주기
pub fn add_hint(a: &[f32], b: &[f32], c: &mut [f32]) {
    let n = c.len().min(a.len()).min(b.len());
    let (a, b, c) = (&a[..n], &b[..n], &mut c[..n]);
    for i in 0..n { c[i] = a[i] + b[i]; }
}

import numpy as np, timeit, fastmod

N = 1_000_000
data = np.random.random(N)

def pure_python(a):
    return sum(x * x for x in a if x > 0.5)

def numpy_way(a):
    return float((a[a > 0.5] ** 2).sum())

def rust_way(a):
    return fastmod.sum_squares_above(a, 0.5)     # 🐍 y06 제로카피

    print(f"{name:8} {t*1000:8.3f} ms")
