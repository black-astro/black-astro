네 가지 길 — 무엇을 고를지부터 정합니다

왜 자바에서 Rust 를 부르나

★ 실제로 이득이 확인되는 자리

  · 이미지 · 영상 · 오디오 처리 (리사이즈 · 인코딩 · 필터)
  · 압축 · 암호 (zstd · brotli · AEAD) — 자바 구현이 느린 영역
  · 파서 — 대용량 CSV · 로그 · 바이너리 프로토콜
  · 지오메트리 · 물리 · 매칭 엔진 — 객체 할당이 많아 GC 가 힘든 코드
  · 이미 Rust 로 잘 만들어진 크레이트가 있는 경우 ★
      image · regex · zstd · ring · rustls · polars · tantivy
  · 안드로이드 · iOS 에 같은 로직을 얹어야 하는 경우 (v10 · v11)

★ 이득이 작은 자리 — 굳이 하지 마세요
  · JIT 가 이미 잘 하는 순수 정수 루프 (C2 는 상당히 잘 합니다)
  · DB·HTTP 대기가 대부분인 코드 — 언어를 바꿔도 그대로 기다립니다
  · 초당 수백만 번 부르며 매번 작은 일을 시키는 설계
      → 경계 비용이 계산보다 커집니다. 배치로 묶으세요(v08)

★ GC 관점에서의 진짜 이유
  큰 byte[] 를 계속 만들고 버리는 코드는 GC 를 흔듭니다.
  네이티브 쪽 메모리(DirectByteBuffer · Arena)로 옮기면
  힙 밖에서 처리되어 p99 지연이 눈에 띄게 안정됩니다 (v08)

한 단계 더 — JNI 는 왜 불편하고 FFM 은 왜 나왔나 🧬 전문가

JNI 의 설계와 그 대가

JNI 는 1997년(Java 1.1) 설계입니다. 전제가 이랬습니다.

  · 네이티브 코드는 '자바를 다시 부르는' 일이 잦다  → JNIEnv 함수표 240여 개
  · 객체는 GC 가 옮길 수 있다                      → 직접 포인터 금지, 핸들(jobject)만
  · 네이티브 안에서 만든 참조는 자동 정리돼야 한다  → 지역 참조 프레임 (v04)

이 전제 때문에 생긴 대가
  · 배열 하나 읽는 데도 Get/Release 짝이 필요합니다 (v03)
  · 참조 수명 규칙을 사람이 지켜야 합니다 (v04)
  · 자바 쪽에 native 메서드 선언 + 심볼 이름 규칙이 필요합니다 (v02)
  · JVM 이 JNI 경계에서 최적화를 포기합니다 (인라인 불가)

★ 그럼에도 JNI 는 여전히 가장 빠릅니다
  자바 → 네이티브 방향 '단순 호출'만 놓고 보면
  스터브가 짧아 오버헤드가 수 나노초 수준입니다 (v08)

Panama 가 바꾼 것

FFM(Foreign Function & Memory) API 연혁

  JEP 412/419/424/434/442  인큐베이터 · 프리뷰 반복 (Java 17~21)
  JEP 454  Java 22 에서 정식 API 로 확정 ★
  JEP 472  Java 24~25 — 네이티브 접근을 '제한된 연산'으로 정리
           --enable-native-access 없이 쓰면 경고가 납니다 (v05)

무엇이 달라졌나
  · 자바 쪽에서 함수를 '찾아서' 부릅니다 — 네이티브에 자바 전용 심볼이 필요 없음
      → Rust 는 그냥 extern "C" 함수 하나면 끝 ★
  · 메모리는 Arena 가 소유합니다 — try-with-resources 로 해제 시점이 명확
  · MethodHandle 이라 JIT 가 상수 폴딩·인라인을 할 수 있습니다
  · jextract 로 헤더(.h) → 자바 바인딩을 생성합니다

★ 한계
  · 안드로이드에는 없습니다 (ART 는 FFM 미구현) → v10 은 JNI/UniFFI
  · 네이티브 → 자바 콜백(업콜)은 JNI 보다 비쌉니다
  · Java 22 미만에서는 아예 못 씁니다
한 줄 요약 — JNI 는 “네이티브가 JVM 을 부른다”는 전제로, FFM 은 “JVM 이 네이티브를 부른다”는 전제로 설계됐습니다. Rust 모듈은 대부분 후자이므로 FFM 쪽이 자연스럽습니다.
정리 — 서버 JVM 이면 Panama FFM, 안드로이드·KMP 면 UniFFI, Java 21 이하에 묶였고 호출이 잦으면 jni 크레이트, 프로토타입이면 JNA 가 2026년의 기본값입니다. 무엇을 고르든 로직은 순수 Rust 한 벌, 어댑터만 여럿으로 두고, 재고 나서 도입하세요.
JVM 02

jni 크레이트 — 첫 모듈이 도는 데까지

JNI 는 이름 규칙만 맞으면 도는 단순한 규약입니다. 자바에 native 메서드를 선언하고, 그 이름에 대응하는 심볼을 Rust 가 내보내고, System.loadLibrary 로 .so/.dll 을 올리면 끝입니다. 여기서는 파일 세 개로 첫 호출을 성공시키고, Gradle 이 cargo 를 부르게 만듭니다.

JNI 는 이름으로 찾는 규약입니다 — 첫 사고의 90%가 심볼 이름 오타입니다.

파일 세 개로 시작 ★

# Cargo.toml
[package]
name = "mylib"
version = "0.1.0"
edition = "2021"

[lib]
name = "mylib"                # → libmylib.so / mylib.dll / libmylib.dylib
crate-type = ["cdylib"]       # ★ 동적 라이브러리 (🔗 f02)

[dependencies]
jni = "0.21"

[profile.release]
lto = true
codegen-units = 1
panic = "abort"               # ★ 주의 — v04 를 읽고 결정하세요
// src/lib.rs
use jni::JNIEnv;
use jni::objects::JClass;
use jni::sys::jint;

// 자바 : package com.example;  class Native { static native int addNumbers(int,int); }
// 심볼 : Java_com_example_Native_addNumbers
#[no_mangle]
pub extern "system" fn Java_com_example_Native_addNumbers(
    _env: JNIEnv,          // ① JVM 을 다시 부르는 창구
    _class: JClass,        // ② static 이면 클래스, 인스턴스면 JObject(this)
    a: jint,               // ③ 여기서부터 실제 인자
    b: jint,
) -> jint {
    a + b                  // jint 는 i32 의 별칭입니다
}
extern "system" 을 쓰세요 — 32비트 윈도우에서 JNI 는 stdcall 입니다. extern "C" 로 적으면 그 플랫폼에서만 스택이 깨집니다. 64비트에서는 같지만 습관을 그렇게 들이는 편이 안전합니다.

자바 쪽과 실행

// src/main/java/com/example/Native.java
package com.example;

public final class Native {
    static {
        // ① java.library.path 에서 libmylib.so 를 찾습니다
        System.loadLibrary("mylib");
        // 개발 중에는 절대 경로가 편합니다
        // System.load("/abs/path/target/release/libmylib.so");
    }
    private Native() {}

    public static native int addNumbers(int a, int b);
}
# ① Rust 빌드
cargo build --release
ls target/release/            # libmylib.so | mylib.dll | libmylib.dylib

# ② 심볼 확인 ★ 문제가 나면 항상 여기부터
nm -D target/release/libmylib.so | grep Java_
#   0000000000008a10 T Java_com_example_Native_addNumbers
dumpbin /exports target\release\mylib.dll | findstr Java_     # 윈도우
nm -gU target/release/libmylib.dylib | grep Java_             # 맥

# ③ 자바 실행 — 라이브러리 경로를 알려 줍니다
javac -d out src/main/java/com/example/Native.java
java -Djava.library.path=target/release -cp out com.example.Main
-Xcheck:jni 를 개발 내내 켜 두세요 — 잘못된 참조 사용·예외 미처리를 죽기 전에 알려 줍니다. 운영에서는 느려지므로 끕니다(v04).

이렇게도 쓸 수 있다 — 이름 규칙과 파일 이름 규칙 🟡 중급

심볼 이름 만드는 법 ★

규칙
  Java_ + 패키지경로(. → _) + _ + 클래스명 + _ + 메서드명

예시
  com.example.Native#addNumbers
    → Java_com_example_Native_addNumbers

  com.my_app.Codec#encode          ← 패키지에 밑줄이 있음 ★
    → Java_com_my_1app_Codec_encode      (_ 는 _1 로)

  com.example.Outer$Inner#run      ← 중첩 클래스
    → Java_com_example_Outer_00024Inner_run   ($ 는 _00024)

  오버로드가 있으면 시그니처까지 붙습니다 ★
  encode(byte[]) 와 encode(String) 이 함께 있으면
    → Java_com_example_Codec_encode___3B          (byte[])
    → Java_com_example_Codec_encode__Ljava_lang_String_2

무엇이 다른가 ★

JNI 의 GetStringUTFChars 가 주는 것은 표준 UTF-8 이 아닙니다.

  ① NUL(U+0000) 을 0xC0 0x80 두 바이트로 씁니다
       → C 문자열로 다뤄도 중간에 끊기지 않게 하려는 설계
  ② BMP 밖 문자(이모지 · 일부 한자)를 서로게이트 쌍 두 개로 나눠
     각각 3바이트로 인코딩합니다 (표준 UTF-8 이면 4바이트 하나)
       "🦀" → 표준 UTF-8 : F0 9F A6 80        (4바이트)
             → Modified   : ED A0 BD ED B6 80 (6바이트) ★

무엇이 문제인가
  · Rust 의 String 은 표준 UTF-8 만 허용합니다
  · 이모지가 든 문자열을 그대로 from_utf8 하면 실패하거나 깨집니다

jni 0.21 은 이것을 알아서 처리합니다
  · env.get_string(&s)  → 내부에서 Modified UTF-8 을 표준으로 변환 ★
  · env.new_string(s)   → 표준을 Modified 로 변환해 자바에 전달
  → 크레이트를 쓰는 한 신경 쓸 일이 거의 없습니다.

★ 직접 JNI C API 를 부르거나 다른 언어(C++)와 섞을 때만 문제가 됩니다.
  그때는 GetStringChars(UTF-16) 를 받아 직접 변환하는 편이 안전합니다.

use jni::JNIEnv;
use jni::objects::{JByteArray, JClass, JIntArray, ReleaseMode};

// ① 복사 — 가장 단순합니다
#[no_mangle]
pub extern "system" fn Java_com_example_Native_sumBytes(
    mut env: JNIEnv, _c: JClass, arr: JByteArray,
) -> jni::sys::jlong {
    // jbyte(i8) 배열을 Vec<u8> 로 복사해서 줍니다 ★
    let data: Vec<u8> = match env.convert_byte_array(&arr) {
        Ok(v) => v,
        Err(_) => return -1,
    };
    data.iter().map(|&b| b as i64).sum()
}

// ② 핀 — 복사를 피하고 결과를 되씁니다
#[no_mangle]
pub extern "system" fn Java_com_example_Native_doubleInPlace(
    mut env: JNIEnv, _c: JClass, arr: JIntArray,
) {
    // CopyBack : 끝날 때 자바 배열로 값을 되돌려 씁니다
    // NoCopyBack : 읽기만 할 때 (되쓰기 비용을 아낍니다) ★
    let mut elems = match unsafe { env.get_array_elements(&arr, ReleaseMode::CopyBack) } {
        Ok(e) => e,
        Err(_) => return,
    };
    for v in elems.iter_mut() { *v *= 2; }
    // elems 가 drop 될 때 Release 가 호출됩니다 (자동) ★
}

Rust 쪽 — 버퍼를 그대로 보기

use jni::objects::{JByteBuffer, JClass};
use jni::sys::jint;
use jni::JNIEnv;

#[no_mangle]
pub extern "system" fn Java_com_example_Native_grayscale(
    mut env: JNIEnv, _c: JClass,
    buf: JByteBuffer,        // ByteBuffer.allocateDirect 로 만든 것이어야 합니다 ★
    width: jint, height: jint,
) -> jint {
    // ① 주소와 용량을 얻습니다 — 둘 다 실패할 수 있습니다
    let ptr = match unsafe { env.get_direct_buffer_address(&buf) } {
        Ok(p) if !p.is_null() => p,
        _ => return -1,      // Direct 가 아니면 여기서 걸립니다
    };
    let cap = match env.get_direct_buffer_capacity(&buf) {
        Ok(c) => c,
        Err(_) => return -2,
    };

    // ② 크기 검증을 반드시 합니다 ★ (여기서 안 막으면 힙 밖을 밟습니다)
    let need = (width as usize) * (height as usize) * 4;
    if cap < need { return -3; }

    // ③ 슬라이스로 보고 순수 Rust 로 처리
    let px = unsafe { std::slice::from_raw_parts_mut(ptr, need) };
    for chunk in px.chunks_exact_mut(4) {
        let g = ((chunk[0] as u32 * 299 + chunk[1] as u32 * 587
                  + chunk[2] as u32 * 114) / 1000) as u8;
        chunk[0] = g; chunk[1] = g; chunk[2] = g;   // 알파는 그대로
    }
    0
}

public final class Frames implements AutoCloseable {
    // Direct 버퍼는 만들고 버리는 비용이 큽니다 → 재사용합니다 ★
    private static final ThreadLocal<ByteBuffer> POOL =
        ThreadLocal.withInitial(() -> ByteBuffer.allocateDirect(4 * 1024 * 1024));

    public static ByteBuffer borrow(int need) {
        ByteBuffer b = POOL.get();
        if (b.capacity() < need) {              // 모자라면 키워서 교체
            b = ByteBuffer.allocateDirect(need);
            POOL.set(b);
        }
        b.clear();
        return b;
    }

    public static void grayscale(ByteBuffer rgba, int w, int h) {
        if (!rgba.isDirect()) throw new IllegalArgumentException("direct 만 됩니다");
        int rc = Native.grayscale(rgba, w, h);   // ★ 여기서 복사가 없습니다
        if (rc != 0) throw new IllegalStateException("native rc=" + rc);
    }
    @Override public void close() { POOL.remove(); }
}
★ Direct 버퍼 운영 주의점

  · 회수는 GC 가 Cleaner 로 처리합니다 — 즉시가 아닙니다
  · 총량 상한 : -XX:MaxDirectMemorySize=512m (기본은 -Xmx 와 같음)
  · 넘치면 OutOfMemoryError: Direct buffer memory
  · 모니터링 : jcmd <pid> VM.native_memory summary
              (미리 -XX:NativeMemoryTracking=summary 로 띄워야 합니다)

★ 대안 — 네이티브가 할당하고 자바가 감싸기
  Rust 에서 malloc 한 메모리를 env.new_direct_byte_buffer(ptr, len) 로
  감싸 자바에 돌려줄 수 있습니다. 이때 해제 책임은 Rust 에 있으므로
  자바 쪽에 close() 를 반드시 만들어 두세요 (v04 의 핸들 패턴).
정리 — 숫자는 그냥 넘어가고, 문자열은 크레이트가 Modified UTF-8 을 처리해 줍니다. 배열은 수 KB 면 복사(convert_byte_array) · 되쓰기가 필요하면 핀(get_array_elements) · 1MB 이상이면 DirectByteBuffer 입니다. Critical 영역은 수 마이크로초짜리에만 쓰고, Direct 버퍼는 풀에 두고 재사용하세요.

객체 · 콜백 · 예외 — 참조 수명이 핵심입니다

JNI 에서 받은 JObject 는 포인터가 아니라 핸들입니다. 네이티브 메서드가 반환하는 순간 자동으로 무효가 되고, 다른 스레드로 가져갈 수도 없습니다. 이 규칙 하나를 모르면 재현되지 않는 크래시가 납니다. 여기서 지역/전역 참조 · ID 캐싱 · 예외 · 패닉 · 스레드 attach 를 전부 정리합니다.

JNI 사고의 대부분은 지역 참조를 오래 들고 있거나 스레드를 안 붙인 것입니다.

자바 객체의 메서드 부르기

use jni::JNIEnv;

        }

    };

ID 캐싱 — 매번 찾지 않습니다 ★

use std::sync::OnceLock;
use jni::objects::{GlobalRef, JMethodID};
use jni::signature::{Primitive, ReturnType};

// find_class · get_method_id 는 문자열 검색이라 비쌉니다.
// 한 번만 찾고 재사용합니다 ★
static CB_CLASS: OnceLock<GlobalRef> = OnceLock::new();
static CB_ON_PROGRESS: OnceLock<JMethodID> = OnceLock::new();

fn init_ids(env: &mut JNIEnv) -> jni::errors::Result<()> {
    if CB_CLASS.get().is_some() { return Ok(()); }
    let class = env.find_class("com/example/ProgressListener")?;
    let mid = env.get_method_id(&class, "onProgress", "(I)V")?;
    // ★ 클래스는 GlobalRef 로 살려 둬야 합니다.
    //   클래스가 언로드되면 JMethodID 가 무효가 되기 때문입니다.
    let _ = CB_CLASS.set(env.new_global_ref(class)?);
    let _ = CB_ON_PROGRESS.set(mid);
    Ok(())
}

fn notify(env: &mut JNIEnv, listener: &JObject, pct: i32) {
    let Some(&mid) = CB_ON_PROGRESS.get() else { return };
    // 캐싱한 ID 로 부르는 빠른 경로 — 이름 검색이 사라집니다
    let r = unsafe {
        env.call_method_unchecked(listener, mid,
            ReturnType::Primitive(Primitive::Void),
            &[jni::objects::JValue::Int(pct).as_jni()])
    };
    if r.is_err() { let _ = env.exception_clear(); }
}
효과 — call_method(이름 검색 포함)는 캐싱한 call_method_unchecked 대비 몇 배 느립니다. 콜백을 초당 수천 번 이상 부른다면 캐싱이 필수입니다. 한 번씩 부르는 곳이라면 읽기 쉬운 call_method 그대로 두세요.

패닉이 경계를 넘으면 안 됩니다 ★

use std::panic::{catch_unwind, AssertUnwindSafe};

#[no_mangle]
pub extern "system" fn Java_com_example_Native_resize(
    mut env: JNIEnv, _c: JClass, src: JByteArray, w: jint, h: jint,
) -> JByteArray {
    // ★ 모든 extern 함수를 이 틀로 감쌉니다
    let result = catch_unwind(AssertUnwindSafe(|| {
        let data = env.convert_byte_array(&src)?;
        let out = core::resize(&data, w as u32, h as u32)?;   // 순수 Rust
        env.byte_array_from_slice(&out).map_err(Into::into)
    }));

    match result {
        Ok(Ok(arr)) => arr,
        Ok(Err(e)) => { report(&mut env, e); JByteArray::default() }
        Err(payload) => {
            // 패닉 메시지를 최대한 살려서 자바 예외로
            let msg = payload.downcast_ref::<&str>().map(|s| s.to_string())
                .or_else(|| payload.downcast_ref::<String>().cloned())
                .unwrap_or_else(|| "네이티브 패닉".into());
            throw(&mut env, "java/lang/RuntimeException", &msg);
            JByteArray::default()
        }
    }
}
panic = "abort" 를 켜면 catch_unwind 가 아무것도 못 잡습니다 — 패닉이 곧 프로세스 종료입니다. JNI 라이브러리라면 panic = "unwind"(기본값)를 유지하고 경계에서 잡는 편이 낫습니다. 바이너리 크기 때문에 abort 를 쓰고 싶다면 패닉이 절대 안 나도록 unwrap 을 전부 없애야 합니다.

use jni::objects::{GlobalRef, JObject, JValue};
use jni::{JNIEnv, JavaVM};

#[no_mangle]
pub extern "system" fn Java_com_example_Native_processAsync(
    mut env: JNIEnv, _c: JClass, listener: JObject,
) {
    // ① 스레드로 넘길 수 있는 것만 챙깁니다 ★
    let vm: JavaVM = match env.get_java_vm() { Ok(v) => v, Err(_) => return };
    let cb: GlobalRef = match env.new_global_ref(&listener) { Ok(g) => g, Err(_) => return };

    std::thread::spawn(move || {
        // ② 이 스레드를 JVM 에 붙입니다 — 안 붙이면 즉시 크래시
        //    as_daemon 은 JVM 종료를 막지 않습니다 (백그라운드 작업에 적합)
        let mut env = match vm.attach_current_thread_as_daemon() {
            Ok(e) => e,
            Err(_) => return,
        };

        for pct in (0..=100).step_by(10) {
            std::thread::sleep(std::time::Duration::from_millis(100));

            // ③ 반복문 안에서 객체를 만들면 프레임을 열어 줍니다 ★
            let r = env.with_local_frame::<_, _, jni::errors::Error>(8, |env| {
                env.call_method(cb.as_obj(), "onProgress", "(I)V",
                                &[JValue::Int(pct)])?;
                Ok(())
            });
            if r.is_err() { let _ = env.exception_clear(); break; }
        }
        // ④ AttachGuard 가 drop 되면서 detach 됩니다 (자동)
    });
}

지켜야 할 규칙 · 진단

★ 스레드 규칙 5가지

  ① JNIEnv 는 절대 스레드로 넘기지 않습니다 (Send 가 아닙니다)
  ② JavaVM · GlobalRef 만 넘깁니다
  ③ 스레드마다 attach 하고, 끝나면 detach 합니다 (Guard 가 자동)
  ④ attach 는 싸지 않습니다 — 스레드 풀을 쓰고 반복 attach 를 피하세요
  ⑤ 자주 붙였다 떼면 JVM 이 스레드 목록을 계속 고칩니다 → 오버헤드

★ 콜백 자체를 피하는 설계가 더 낫습니다
  · 진행률은 AtomicLong 에 써 두고 자바가 폴링
  · 결과는 반환값으로 (콜백 없이)
  · 이벤트가 많으면 배치로 모아 한 번에 전달
  → 네이티브 → 자바 방향(업콜)이 반대 방향보다 훨씬 비쌉니다 (v08)

★ 진단 도구

  -XX:+CreateCoredumpOnCrash    크래시 시 코어 덤프

public final class Engine implements AutoCloseable {
    private long handle;                       // 0 = 이미 닫힘

    public Engine() { handle = nativeNew(); }

    public float score(int x) {
        long h = handle;
        if (h == 0) throw new IllegalStateException("이미 닫힌 Engine 입니다");
        return nativeScore(h, x);
    }

    @Override public synchronized void close() {
        if (handle != 0) { nativeFree(handle); handle = 0; }   // ★ 두 번 해제 방지
    }

    private static native long  nativeNew();
    private static native float nativeScore(long h, int x);
    private static native void  nativeFree(long h);
}

// 쓰는 쪽 — try-with-resources 로 해제를 강제합니다
try (Engine e = new Engine()) {
    System.out.println(e.score(42));
}
finalize 는 쓰지 마세요(제거됐습니다). 깜빡한 close() 를 잡고 싶다면 java.lang.ref.Cleaner 를 보조 안전망으로만 붙이고, 정상 경로는 반드시 try-with-resources 로 두세요. handle 을 0 으로 만드는 것이 double free 를 막는 유일한 장치입니다.
정리 — 지역 참조는 메서드가 끝나면 사라지고 스레드를 넘지 못합니다. 오래 들고 있어야 하면 GlobalRef, 다른 스레드에서 쓰려면 JavaVM + attach_current_thread 입니다. 클래스·메서드 ID 는 OnceLock 에 캐싱하고, 모든 extern 함수는 catch_unwind 로 감싸 패닉을 자바 예외로 번역하세요. Rust 객체는 long 핸들 + AutoCloseable 로 쥐어 줍니다.

FFM 은 자바가 네이티브 함수를 찾아서 부르는 방식입니다. Rust 쪽에는 자바 전용 코드가 한 줄도 없습니다 — 평범한 extern "C" 함수면 됩니다. 그래서 같은 .so 를 파이썬·Node·C# 이 함께 씁니다(🔗 f01). 대신 변환 코드를 자바 쪽에서 써야 하는데, 그건 jextract 가 만들어 줍니다.

Rust 쪽 — C ABI 설계 ★

// src/ffi.rs — 얇게. 로직은 lib.rs 에 (🔗 f01)
use std::ffi::{c_char, CString};
use std::ptr;

#[repr(C)]
pub struct Buf { pub ptr: *mut u8, pub len: usize }   // 소유권은 Rust 에 있습니다

/// 성공 0 · 실패 음수. 결과는 out 으로 돌려줍니다.
#[no_mangle]
pub extern "C" fn mylib_resize(
    src: *const u8, src_len: usize,
    w: u32, h: u32,
    out: *mut Buf,                 // ★ 출력 인자
) -> i32 {
    if src.is_null() || out.is_null() || w == 0 || h == 0 { return -1; }
    let data = unsafe { std::slice::from_raw_parts(src, src_len) };

    let r = std::panic::catch_unwind(|| crate::resize(data, w, h));
    match r {
        Ok(Ok(mut v)) => {
            v.shrink_to_fit();
            let b = Buf { ptr: v.as_mut_ptr(), len: v.len() };
            std::mem::forget(v);                 // ★ 해제는 mylib_buf_free 가
            unsafe { ptr::write(out, b) };
            0
        }
        Ok(Err(e)) => { set_last_error(e.to_string()); -2 }
        Err(_)      => { set_last_error("네이티브 패닉".into()); -99 }
    }
}

#[no_mangle]
pub extern "C" fn mylib_buf_free(b: Buf) {
    if b.ptr.is_null() { return; }
    unsafe { drop(Vec::from_raw_parts(b.ptr, b.len, b.len)) };
}

/// 마지막 에러 메시지를 버퍼에 복사하고 길이를 반환합니다.
#[no_mangle]
pub extern "C" fn mylib_last_error(buf: *mut c_char, cap: usize) -> usize { /* … */ 0 }

#[no_mangle]
pub extern "C" fn mylib_version() -> u32 { 1 }
설계 규칙 세 가지 — ① 불투명 포인터로 내부를 숨기고, ② 에러는 정수 코드로, ③ 할당한 쪽이 해제합니다. 이 셋만 지키면 자바·파이썬·C# 바인딩이 전부 기계적으로 나옵니다(🔗 f06).

자바 쪽 — 전체 코드 ★

import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;
import java.nio.file.Path;

public final class MyLib {
    // ① 라이브러리 수명 = 프로세스 수명 → 공유 Arena
    private static final Arena LIB_ARENA = Arena.ofShared();
    private static final SymbolLookup LOOKUP =
        SymbolLookup.libraryLookup(Path.of(NativeLoader.extract()), LIB_ARENA);
    private static final Linker LINKER = Linker.nativeLinker();

    // ② Buf { void* ptr; size_t len; } 의 메모리 배치를 자바로 적습니다
    private static final MemoryLayout BUF = MemoryLayout.structLayout(
        ValueLayout.ADDRESS.withName("ptr"),
        ValueLayout.JAVA_LONG.withName("len")).withName("Buf");

    // ③ int mylib_resize(const uint8_t*, size_t, uint32_t, uint32_t, Buf*)
    private static final MethodHandle RESIZE = LINKER.downcallHandle(
        LOOKUP.find("mylib_resize").orElseThrow(),
        FunctionDescriptor.of(ValueLayout.JAVA_INT,
            ValueLayout.ADDRESS, ValueLayout.JAVA_LONG,
            ValueLayout.JAVA_INT, ValueLayout.JAVA_INT,
            ValueLayout.ADDRESS));

    private static final MethodHandle BUF_FREE = LINKER.downcallHandle(
        LOOKUP.find("mylib_buf_free").orElseThrow(),
        FunctionDescriptor.ofVoid(BUF));

    public static byte[] resize(byte[] src, int w, int h) {
        // ④ 이 블록을 벗어나면 할당한 메모리가 전부 해제됩니다 ★
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment in = arena.allocateFrom(ValueLayout.JAVA_BYTE, src);
            MemorySegment out = arena.allocate(BUF);

            int rc = (int) RESIZE.invokeExact(in, (long) src.length, w, h, out);
            if (rc != 0) throw new IllegalStateException("native rc=" + rc);

            MemorySegment ptr = out.get(ValueLayout.ADDRESS, 0);
            long len = out.get(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS.byteSize());

            // ⑤ 주소만 온 상태 — 길이를 붙여야 읽을 수 있습니다 ★
            byte[] result = ptr.reinterpret(len)
                               .toArray(ValueLayout.JAVA_BYTE);
            BUF_FREE.invokeExact(out);       // ⑥ 네이티브 메모리 해제
            return result;
        } catch (Throwable t) {
            throw new RuntimeException(t);
        }
    }
}

// 기본 downcall 은 자바 배열을 그대로 못 넘깁니다 (GC 가 옮기므로).
// Linker.Option.critical(true) 를 주면 힙 세그먼트를 그대로 넘길 수 있습니다.
private static final MethodHandle SUM = LINKER.downcallHandle(
    LOOKUP.find("mylib_sum").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG,
        ValueLayout.ADDRESS, ValueLayout.JAVA_LONG),
    Linker.Option.critical(true));      // ★ 힙 접근 허용

public static long sum(byte[] data) throws Throwable {
    MemorySegment heap = MemorySegment.ofArray(data);   // 복사 없음 ★
    return (long) SUM.invokeExact(heap, (long) data.length);
}
critical 의 대가 — JNI 의 Critical 영역과 같습니다. 그 함수가 도는 동안 GC 가 방해받을 수 있습니다. 짧고 빠른 함수에만 쓰고, 그 안에서 다시 자바를 부르거나 블로킹하면 안 됩니다. 오래 걸리는 작업은 Arena 로 네이티브 메모리에 복사하는 편이 전체적으로 낫습니다.

FFM 을 감싸는 실무 규칙

① 원시 바인딩(raw)과 공개 API 를 나눕니다

     매번 downcallHandle 하면 JIT 가 상수로 접지 못해 느려집니다

③ invokeExact 만 씁니다 (invoke 는 느립니다)

④ Arena.ofConfined() 를 기본으로, try-with-resources 를 벗어나지 않게
     세그먼트를 밖으로 반환하지 마세요 (자바 배열로 복사해서 반환)

⑤ 스레드 규칙
     ofConfined 세그먼트는 만든 스레드에서만 씁니다.
     가상 스레드에서 네이티브를 부르면 캐리어가 붙잡힙니다(pinning) ★
     오래 걸리는 네이티브 호출은 플랫폼 스레드 풀로 보내세요

⑥ 되돌릴 스위치
     -Dmylib.native=false 로 순수 자바 구현으로 돌아가게 (v12)

★ 성능 감각 (v08 에서 측정합니다)
     빈 downcall           수 나노초 — JNI 와 사실상 동급
     critical downcall     더 낮음 (인라인 가능)
     업콜(upcall)          downcall 의 수십 배
     Arena 할당/해제       할당 크기에 비례 — 재사용하세요
정리 — FFM 은 Rust 쪽을 언어 중립으로 남겨 두는 방식입니다. SymbolLookup 으로 찾고 downcallHandle 로 핸들을 만들어 invokeExact 로 부르며, 메모리는 Arena 가 소유합니다. 핸들은 static final, Arena 는 ofConfined, 바인딩은 cbindgen → jextract 로 자동 생성하고, 실행에는 --enable-native-access 를 잊지 마세요.

       함수 이름 · 인자 타입 · 반환 타입 · 체크섬
       → uniffi-bindgen 이 .so 를 읽어 이 표를 복원합니다 ★

  ③ 언어별 바인딩
       코틀린 : JNA Library 인터페이스 + 변환 코드 + 예외 클래스
       스위프트 : @_cdecl 없이 직접 심볼 호출

JNA · JNR — 선언만으로 부르기

JNA 는 자바 인터페이스를 하나 적으면 그게 곧 바인딩인 라이브러리입니다. 빌드 설정도 코드 생성도 없어서 “되는지만 30분 안에 확인” 하는 데 가장 좋습니다. 대신 호출마다 리플렉션과 변환이 들어가 넷 중 가장 느립니다 — 그 대가가 어느 정도인지 알고 쓰면 훌륭한 도구입니다.

JNA 인터페이스 매핑 — 30분 프로토타입 ★

import com.sun.jna.*;

// v05 에서 만든 것과 같은 C ABI 라이브러리를 그대로 씁니다.
public interface MyLib extends Library {

    Pointer mylib_open(String path);              // const char* → String 자동 변환

// ③ 바로 씁니다 — 빌드 설정도 코드 생성도 없습니다
public class Demo {

JNA 가 자동으로 해 주는 것 — 플랫폼별 파일 이름 결정, String ↔ char* 변환, jar 안의 네이티브 자동 추출(jna.boot.library.path), 구조체 정렬 계산. v09 에서 직접 만들 로더를 JNA 는 이미 갖고 있습니다.

구조체 · 포인터 · 메모리

import com.sun.jna.*;
import java.util.List;

// Rust: #[repr(C)] pub struct Buf { ptr: *mut u8, len: usize }
public class Buf extends Structure {
    public Pointer ptr;
    public long    len;

    @Override protected List<String> getFieldOrder() {
        return List.of("ptr", "len");      // ★ 필드 순서를 반드시 알려 줘야 합니다
    }
    public static class ByValue extends Buf implements Structure.ByValue {}
}

public interface MyLib extends Library {
    MyLib INSTANCE = Native.load("mylib", MyLib.class);
    int  mylib_resize(byte[] src, long len, int w, int h, Buf out);
    void mylib_buf_free(Buf.ByValue b);        // 값으로 넘기는 구조체
}

// 결과 읽기
Buf out = new Buf();
int rc = MyLib.INSTANCE.mylib_resize(src, src.length, 800, 600, out);
if (rc != 0) throw new IllegalStateException("rc=" + rc);
out.read();                                    // ★ 네이티브 → 자바 필드 동기화
byte[] result = out.ptr.getByteArray(0, (int) out.len);

// 직접 메모리를 잡을 때
Memory buf = new Memory(1024 * 1024);          // 네이티브 힙에 1MB
buf.clear();
// … 넘겨서 채운 뒤 …
byte[] copied = buf.getByteArray(0, 4096);
getFieldOrder() 를 빠뜨리거나 순서가 틀리면 필드가 엉뚱한 오프셋으로 읽힙니다. 예외가 아니라 이상한 값이 나옵니다. 구조체가 많다면 구조체를 아예 안 쓰는 API 설계(🔗 f01 의 JSON 트릭)가 훨씬 안전합니다.

이렇게도 쓸 수 있다 — Direct 매핑과 JNR 🟡 중급

JNA Direct 매핑 — 같은 JNA 인데 훨씬 빠릅니다 ★

import com.sun.jna.Native;

public final class MyLibDirect {
    static {
        Native.register("mylib");     // ★ 이 클래스의 native 메서드를 직접 연결
    }
    private MyLibDirect() {}

    // JNI 처럼 native 로 선언하지만, 심볼 이름은 메서드 이름 그대로입니다
    public static native int mylib_add(int a, int b);
    public static native int mylib_sum(java.nio.ByteBuffer buf, int len);
}
★ 인터페이스 매핑 vs Direct 매핑

  인터페이스 매핑 (extends Library)
    · 호출마다 동적 프록시 → 리플렉션 → 인자 변환
    · 가장 쓰기 쉽고 가장 느립니다
    · 프로토타입 · 호출이 드문 초기화 함수에 적합

  Direct 매핑 (Native.register)
    · 로드 시점에 심볼을 메서드에 직접 붙입니다
    · 호출 비용이 JNI 에 가까워집니다 (수 배 빨라집니다) ★
    · 대신 쓸 수 있는 타입이 제한됩니다
        원시 타입 · Pointer · Structure · 직접 버퍼(ByteBuffer)
        String 자동 변환은 안 됩니다 → byte[] 로 직접

★ 실무 요령
  · 초기화·설정 함수는 인터페이스 매핑으로 편하게
  · 뜨거운 함수 몇 개만 Direct 매핑으로 옮깁니다
  · 두 방식을 한 프로젝트에서 함께 써도 됩니다

JVM 08

성능 비교 — 경계 비용을 숫자로

“어느 게 빠른가”는 호출당 얼마인가와 몇 번 부르는가를 함께 봐야 답이 나옵니다. 여기서는 네 방식의 빈 호출 비용을 JMH 로 재고, 큰 배열을 넘길 때의 전략과 GC 와의 상호작용까지 정리합니다. 결론부터 말하면 대부분의 프로젝트에서 경계 비용은 문제가 아닙니다.

숫자보다 중요한 것은 호출 횟수입니다 — 배치로 묶으면 이 표 전체가 무의미해집니다.

JMH 로 직접 재기 ★

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)
@Fork(value = 1, jvmArgs = {"--enable-native-access=ALL-UNNAMED"})
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
public class BoundaryBench {

    private byte[] small;      // 1KB
    private ByteBuffer direct; // 1KB direct

    @Setup public void setup() {
        small = new byte[1024];
        new Random(42).nextBytes(small);
        direct = ByteBuffer.allocateDirect(1024);
        direct.put(small).flip();
    }

    // ① 기준선 — 순수 자바
    @Benchmark public int javaAdd() { return 2 + 3; }

    // ② JNI 원시 인자
    @Benchmark public int jniAdd() { return Native.addNumbers(2, 3); }

    // ③ JNI + 배열 복사
    @Benchmark public long jniSumArray() { return Native.sumBytes(small); }

    // ④ JNI + Direct 버퍼 (복사 없음)
    @Benchmark public long jniSumDirect() { return Native.sumDirect(direct, 1024); }

    // ⑤ FFM
    @Benchmark public int ffmAdd() throws Throwable { return MyLib.add(2, 3); }

    // ⑥ JNA
    @Benchmark public int jnaAdd() { return MyLib.INSTANCE.mylib_add(2, 3); }
}
반드시 지킬 것 — ① --release 로 빌드된 .so 인가, ② JIT 워밍업을 충분히 했는가(-wi 5 이상), ③ 결과를 블랙홀에 넣거나 반환했는가. 셋 중 하나만 빠져도 숫자가 통째로 거짓이 됩니다. 특히 ③ 이 빠지면 JIT 가 호출 자체를 지워 버립니다.

읽는 법 · 흔한 착시

★ 착시 ① "Rust 로 바꿨는데 안 빨라졌다"
   · 디버그 빌드였습니다 (--release 확인)
   · JIT 가 이미 그 자바 코드를 잘 최적화하고 있었습니다
   · 병목이 GC 나 I/O 였습니다 → 프로파일러부터 (⚡ e01)

★ 착시 ② "JNI 가 FFM 보다 열 배 빠르다"
   · FFM 을 invoke 로 불렀거나 MethodHandle 을 매번 만들었습니다
   · static final + invokeExact 로 고치면 차이가 사라집니다 (v05)

★ 착시 ③ "UniFFI 는 느려서 못 쓴다"
   · 초당 수십만 번 부를 때만 그렇습니다
   · 이미지 한 장에 10ms 짜리 일이면 0.006% 입니다

★ 착시 ④ 마이크로벤치가 좋은데 실서비스가 안 좋다
   · 벤치는 캐시가 뜨겁고 분기 예측이 완벽합니다
   · 실제로는 데이터가 캐시에 없고 다른 스레드와 경쟁합니다
   · 반드시 실부하(부하 테스트)로 다시 확인하세요 ★

★ 함께 봐야 하는 지표
   -Xlog:gc*                    GC 횟수 · 정지 시간
   jcmd <pid> VM.native_memory  네이티브 메모리 증가
   p50 / p95 / p99              평균이 아니라 꼬리를 보세요

    ~ 4 KB     복사가 가장 단순하고 충분합니다

  입력 복사 + 출력 복사 = 두 번입니다.
  4K 이미지(약 24MB)를 UniFFI 로 왕복시키면 48MB 복사가 생깁니다.
  이 경로만 JNI + Direct 로 빼는 것이 v12 의 설계입니다.

GC 와의 상호작용

★ 네이티브 모듈이 GC 에 주는 영향 세 가지

  ① 큰 byte[] 를 계속 만들면 → 젊은 세대가 빨리 차고 승격이 늘어납니다
       해결 : 결과를 Direct 버퍼에 쓰고 재사용

  ② 핀·Critical 이 길면 → GC 가 그 구간을 기다립니다
       해결 : Critical 영역은 마이크로초 단위로만

  ③ 네이티브 메모리는 힙에 안 보입니다 ★
       -Xmx 로는 제어되지 않습니다. 컨테이너 메모리 한도를 넘겨
       OOMKilled 가 나는 대표적 원인입니다.
       해결 : -XX:MaxDirectMemorySize · Rust 쪽 할당량 상한 · NMT 로 감시

★ 어떤 GC 가 유리한가
  · G1 (기본)     대부분의 경우 그대로 두면 됩니다
  · ZGC          p99 가 중요하고 힙이 크면 유리합니다
  · 어떤 GC 든 네이티브로 옮긴 데이터는 GC 대상이 아니므로
    "옮기는 것" 자체가 이미 GC 압력을 줄입니다 ★

★ 가상 스레드 주의 (Java 21+)

package com.example.mylib;

import java.io.*;
import java.nio.file.*;
import java.util.Locale;

public final class NativeLoader {
    private static volatile boolean loaded = false;

    public static synchronized void load() {
        if (loaded) return;
        // ① 개발·운영 오버라이드를 먼저 봅니다 (되돌릴 수 있게)
        String override = System.getProperty("mylib.native.path");
        if (override != null) { System.load(override); loaded = true; return; }

        String dir  = platformDir();                  // linux-x86_64 …
        String file = System.mapLibraryName("mylib"); // libmylib.so …
        String res  = "/native/" + dir + "/" + file;

        try (InputStream in = NativeLoader.class.getResourceAsStream(res)) {
            if (in == null)
                throw new UnsatisfiedLinkError("지원하지 않는 플랫폼입니다: " + dir);

            // ② 임시 파일로 꺼냅니다. 경로는 -Dmylib.tmpdir 로 바꿀 수 있게 ★
            Path tmpDir = Path.of(System.getProperty("mylib.tmpdir",
                                  System.getProperty("java.io.tmpdir")));
            Files.createDirectories(tmpDir);
            Path out = Files.createTempFile(tmpDir, "mylib-", suffix(file));
            Files.copy(in, out, StandardCopyOption.REPLACE_EXISTING);
            out.toFile().setExecutable(true, true);

            // ③ 절대 경로로 올립니다 (loadLibrary 가 아니라 load)
            System.load(out.toAbsolutePath().toString());
            loaded = true;

            // ④ 종료 시 정리 — 윈도우는 올린 파일을 못 지웁니다(무시됩니다)
            out.toFile().deleteOnExit();
        } catch (IOException e) {
            throw new UnsatisfiedLinkError("네이티브 추출 실패: " + e.getMessage());
        }
    }

    private static String platformDir() {
        String os = System.getProperty("os.name").toLowerCase(Locale.ROOT);
        String arch = System.getProperty("os.arch").toLowerCase(Locale.ROOT);
        String o = os.contains("win") ? "windows"
                 : os.contains("mac") ? "macos"
                 : os.contains("linux") ? "linux" : "unknown";
        String a = switch (arch) {
            case "amd64", "x86_64" -> "x86_64";
            case "aarch64", "arm64" -> "aarch64";
            default -> arch;
        };
        return o + "-" + a;
    }
    private static String suffix(String f) {
        int i = f.lastIndexOf('.');
        return i < 0 ? ".bin" : f.substring(i);
    }
}

private static Path extractCached(String res, String file) throws IOException {

        bytes = in.readAllBytes();
    }
    String hash = HexFormat.of().formatHex(
        MessageDigest.getInstance("SHA-256").digest(bytes)).substring(0, 16);

    Path dir = Path.of(System.getProperty("mylib.tmpdir",
                       System.getProperty("java.io.tmpdir")), "mylib-" + hash);
    Files.createDirectories(dir);
    Path target = dir.resolve(file);

    if (!Files.exists(target) || Files.size(target) != bytes.length) {
        // 같은 폴더 안에 임시로 쓴 뒤 원자적으로 옮깁니다 ★
        Path tmp = Files.createTempFile(dir, "part-", ".tmp");
        Files.write(tmp, bytes);
        try { Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE); }
        catch (FileAlreadyExistsException ignored) { Files.deleteIfExists(tmp); }
    }
    return target;
}
버전 확인은 로드 직후에 — mylib_version() 을 불러 자바 쪽 상수와 다르면 즉시 예외를 던지세요. “새 jar 인데 옛 .so 가 올라간” 상태는 조용히 틀린 결과를 냅니다.
정리 — 네이티브를 native/<os>-<arch>/ 규약으로 jar 안에 넣고, 런타임에 추출 → System.load(절대경로) 로 올립니다. 다중 타깃은 cross · cargo-zigbuild 와 Actions 매트릭스로 굽고, 배포 전에는 ldd·GLIBC 요구 버전·심볼·컨테이너 스모크를 확인하세요. 로더에는 임시 경로 오버라이드와 버전 검사를 반드시 넣습니다.

안드로이드 — cargo-ndk 와 jniLibs

안드로이드에는 Panama FFM 이 없습니다. 그래서 길은 JNI 또는 UniFFI 둘 뿐입니다. 다행히 안드로이드는 네이티브를 담는 규약이 아주 명확합니다 — jniLibs/<ABI>/lib*.so 에 넣으면 APK 설치 시 알아서 골라 들어갑니다. cargo-ndk · Gradle 플러그인 · 코루틴 연동 · 16KB 페이지까지 한 번에 정리합니다.

안드로이드는 배치 규약이 명확합니다 — ABI 폴더에 넣으면 나머지는 시스템이 합니다.

코틀린 쪽 — external fun

package com.example.myapp

object NativeCore {
    init {
        System.loadLibrary("myapp")     // libmyapp.so
    }

    // ★ 심볼 : Java_com_example_myapp_NativeCore_resize
    //   object 는 자바로 보면 NativeCore 클래스입니다
    external fun resize(src: ByteArray, w: Int, h: Int): ByteArray

    external fun grayscale(buf: java.nio.ByteBuffer, w: Int, h: Int): Int

    external fun version(): Int
}
// 코루틴에서 부르기 — 메인 스레드를 절대 막지 않습니다 ★
class ImageRepository {
    suspend fun resize(bytes: ByteArray, w: Int, h: Int): ByteArray =
        withContext(Dispatchers.Default) {          // CPU 작업 → Default
            NativeCore.resize(bytes, w, h)
        }
}

// ViewModel
viewModelScope.launch {
    _state.value = UiState.Loading
    val out = runCatching { repo.resize(bytes, 800, 600) }
    _state.value = out.fold(
        onSuccess = { UiState.Done(it) },
        onFailure = { UiState.Error(it.message ?: "실패") }
    )
}
Dispatchers.IO 가 아니라 Dispatchers.Default 입니다 — 네이티브 계산은 CPU 작업입니다. IO 디스패처는 스레드를 많이 만들어 CPU 를 과하게 경쟁시킵니다. 파일을 읽는 부분만 IO 로 감싸세요.

Kotlin Multiplatform · iOS — 한 벌로 두 스토어

KMP 는 화면은 각자, 로직은 한 벌로 만드는 방식입니다. 그 “로직 한 벌”을 코틀린 대신 Rust 로 두면 안드로이드·iOS 는 물론 데스크톱과 서버까지 같은 코어를 씁니다. Kotlin/Native 의 cinterop 을 직접 쓰는 대신 UniFFI 를 쓰는 이유도 여기서 정리합니다.

KMP 의 값어치는 고칠 곳이 한 군데라는 데 있습니다 — 코어가 Rust 여도 똑같습니다.

왜 cinterop 대신 UniFFI 인가 ★

cinteropUniFFI
얻는 것C 헤더 그대로코틀린다운 API
포인터직접 관리객체로 감싸 줌

  cinterop 은 Kotlin/Native(iOS·macOS·리눅스) 전용입니다.
  안드로이드는 Kotlin/JVM 이라 cinterop 이 아예 안 됩니다 ★

  UniFFI 는 그 두 벌을 한 정의에서 생성합니다.
  이것이 Mozilla 가 UniFFI 를 만든 이유이기도 합니다.

  · iOS 만 지원하고 앞으로도 그렇다
  · 기존 C 라이브러리를 그대로 쓰고 싶다 (Rust 가 아니라)

#[derive(Debug, thiserror::Error)]
pub enum ImgError {
    #[error("이미지를 읽지 못했습니다: {0}")]
    Decode(String),
    #[error("인코딩에 실패했습니다: {0}")]
    Encode(String),
    #[error("크기가 잘못됐습니다: {w}x{h}")]
    BadSize { w: u32, h: u32 },
}

pub fn resize_jpeg(src: &[u8], w: u32, h: u32, quality: u8)
    -> Result<Vec<u8>, ImgError>
{
    if w == 0 || h == 0 || w > 20_000 || h > 20_000 {
        return Err(ImgError::BadSize { w, h });      // ★ 상한을 코어에서 막습니다
    }
    let img = image::load_from_memory(src)
        .map_err(|e| ImgError::Decode(e.to_string()))?;

    // Lanczos3 는 품질이 좋고 Triangle 은 빠릅니다 — 요구에 맞춰 고르세요
    let out = img.resize_to_fill(w, h, FilterType::Lanczos3);

    let mut buf = std::io::Cursor::new(Vec::with_capacity(src.len() / 4));
    out.to_rgb8()
       .write_to(&mut buf, ImageFormat::Jpeg)
       .map_err(|e| ImgError::Encode(e.to_string()))?;
    let _ = quality;                                  // 필요하면 인코더 설정으로
    Ok(buf.into_inner())
}

use jni::objects::{JByteArray, JByteBuffer, JClass};
use jni::sys::{jint, jlong};
use jni::JNIEnv;
use std::panic::{catch_unwind, AssertUnwindSafe};

/// 입력은 Direct 버퍼, 출력도 Direct 버퍼에 씁니다 → 복사 0
/// 반환 : 0 이상이면 출력 바이트 수, 음수면 에러 코드
#[no_mangle]
pub extern "system" fn Java_com_example_img_NativeImg_resizeDirect(
    mut env: JNIEnv, _c: JClass,
    input: JByteBuffer, in_len: jint,
    output: JByteBuffer,
    w: jint, h: jint,
) -> jint {
    let r = catch_unwind(AssertUnwindSafe(|| -> Result<i32, i32> {
        let ip = unsafe { env.get_direct_buffer_address(&input) }.map_err(|_| -1)?;
        let icap = env.get_direct_buffer_capacity(&input).map_err(|_| -1)?;
        let op = unsafe { env.get_direct_buffer_address(&output) }.map_err(|_| -2)?;
        let ocap = env.get_direct_buffer_capacity(&output).map_err(|_| -2)?;

        let n = in_len as usize;
        if n > icap { return Err(-3); }                    // ★ 경계 검사

        let src = unsafe { std::slice::from_raw_parts(ip, n) };
        let out = imgcore::resize_jpeg(src, w as u32, h as u32, 85)
            .map_err(|_| -4)?;
        if out.len() > ocap { return Err(-5); }            // 출력 버퍼 부족

        let dst = unsafe { std::slice::from_raw_parts_mut(op, out.len()) };
        dst.copy_from_slice(&out);
        Ok(out.len() as i32)
    }));
    match r { Ok(Ok(n)) => n, Ok(Err(c)) => c, Err(_) => -99 }
}

/// 작은 이미지용 — byte[] 를 그대로 받는 단순 경로
#[no_mangle]
pub extern "system" fn Java_com_example_img_NativeImg_resizeBytes<'l>(
    mut env: JNIEnv<'l>, _c: JClass<'l>, src: JByteArray<'l>, w: jint, h: jint,
) -> JByteArray<'l> {
    let data = match env.convert_byte_array(&src) { Ok(v) => v, Err(_) => return JByteArray::default() };
    match imgcore::resize_jpeg(&data, w as u32, h as u32, 85) {
        Ok(out) => env.byte_array_from_slice(&out).unwrap_or_default(),
        Err(e) => {
            let _ = env.throw_new("java/lang/IllegalArgumentException", e.to_string());
            JByteArray::default()
        }
    }
}

@Component
@ConditionalOnProperty(name = "img.impl", havingValue = "jni")
class JniResizer implements Resizer {
    private static final ThreadLocal<ByteBuffer> IN  =
        ThreadLocal.withInitial(() -> ByteBuffer.allocateDirect(32 << 20));
    private static final ThreadLocal<ByteBuffer> OUT =
        ThreadLocal.withInitial(() -> ByteBuffer.allocateDirect(8 << 20));

    @PostConstruct void init() { NativeLoader.load(); }

    @Override public byte[] resize(byte[] src, int w, int h) {
        ByteBuffer in = IN.get(), out = OUT.get();
        if (in.capacity() < src.length) throw new IllegalArgumentException("입력이 너무 큽니다");
        in.clear(); in.put(src); in.flip();
        int n = NativeImg.resizeDirect(in, src.length, out, w, h);
        if (n < 0) throw new IllegalStateException("native rc=" + n);
        byte[] result = new byte[n];
        out.position(0).get(result, 0, n);
        return result;
    }
}

@RestController
@RequestMapping("/resize")
class ResizeController {
    private final Resizer resizer;
    // ★ 네이티브 작업은 전용 풀로 격리합니다.
    //   가상 스레드에서 부르면 캐리어가 붙잡힙니다 (v08)
    private final ExecutorService pool =
        Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());

    ResizeController(Resizer resizer) { this.resizer = resizer; }

    @PostMapping(consumes = MediaType.APPLICATION_OCTET_STREAM_VALUE,
                 produces = MediaType.IMAGE_JPEG_VALUE)
    CompletableFuture<ResponseEntity<byte[]>> resize(
            @RequestBody byte[] body,
            @RequestParam int w, @RequestParam int h) {

        if (body.length > 32 * 1024 * 1024)          // ★ 상한을 앞에서 막습니다
            return CompletableFuture.completedFuture(
                ResponseEntity.status(413).build());

        return CompletableFuture.supplyAsync(
            () -> ResponseEntity.ok(resizer.resize(body, w, h)), pool);
    }

    @PreDestroy void shutdown() { pool.shutdown(); }
}
