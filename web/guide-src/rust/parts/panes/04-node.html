애드온 vs WASM — 무엇을 고르나

둘 다 “Rust 코드를 JS 에서 부른다”지만 돌아가는 곳이 다릅니다. 애드온은 OS 위에서 네이티브로, WASM 은 샌드박스 안에서 돕니다. 이 차이가 성능·배포·할 수 있는 일 전부를 가릅니다.

비교표 ★

★ 한 줄 판단
  브라우저에서 돌아야 한다        → WASM (선택지가 없습니다)
  Node 서버에서 최고 성능이 필요   → 애드온
  Node 인데 배포를 단순하게        → WASM 도 좋은 선택 ★
  파일·네트워크·스레드를 써야 함   → 애드온
  플러그인처럼 신뢰할 수 없는 코드 → WASM (샌드박스)

세 번째 선택지도 있습니다

③ 별도 프로세스 + IPC
   Rust 로 CLI 나 서버를 만들고 JS 가 프로세스를 띄워 통신

   장점
     · 크래시가 Node 를 죽이지 않습니다 ★
     · 언어 경계 문제가 없습니다 (표준 입출력 · HTTP · 유닉스 소켓)
     · 배포가 단순합니다 (실행 파일 하나)
     · 다른 언어에서도 그대로 씁니다
   단점
     · 왕복 지연 (수십 μs ~ 수 ms)
     · 데이터 직렬화 비용
     · 프로세스 관리가 필요합니다

   ★ 이게 정답인 경우가 생각보다 많습니다
     · 호출 빈도가 낮고 데이터가 큰 작업 (이미지 변환 · 빌드 도구)
     · 오래 도는 작업 (인덱싱 · 컴파일)
     · CLI 로도 쓸모가 있는 기능

④ 그냥 JS 로 두기
   Node 는 생각보다 빠릅니다. V8 의 JIT 는 뜨거운 루프를 잘 최적화합니다.
   측정 없이 네이티브로 옮기지 마세요 (🐍 y01 과 같은 원칙 · ⚡ e01)
파이썬과 다른 점 — 파이썬은 인터프리터라 루프 자체가 느립니다. JS 는 JIT 가 있어 단순 수치 루프는 이미 빠릅니다. 그래서 Node 에서 네이티브가 이기는 지점은 SIMD · 병렬 · 특수 알고리즘 · 기존 Rust 크레이트 활용 쪽입니다.

WASM 이 애드온보다 나은 경우 ★

① 배포 단순성이 성능보다 중요할 때
   애드온: linux-x64 · linux-arm64 · musl · darwin-x64 · darwin-arm64 ·
           win32-x64 … 6개 이상의 바이너리를 CI 로 만들어야 합니다 (j10)
   WASM:   .wasm 파일 하나. 어디서나 돕니다. ★

② 라이브러리를 npm 에 공개할 때
   설치 실패 문의가 압도적으로 줄어듭니다.
   (node-gyp 컴파일 실패는 npm 생태계의 오랜 골칫거리입니다)

③ 서버리스·엣지 (Cloudflare Workers · Deno Deploy · Vercel Edge)
   네이티브 애드온을 아예 못 씁니다. WASM 만 가능합니다. ★

④ 신뢰할 수 없는 코드를 실행할 때
   샌드박스가 기본입니다.

★ 성능 차이는 생각보다 작습니다
  순수 계산은 네이티브의 70~95% 정도 나옵니다 (직접 재 보세요 · ⚡ e10).
  대신 큰 데이터를 주고받으면 복사 비용이 생깁니다 (j09).

실무에선 이렇게 — 경계를 설계한다 🔴 실무

호출 횟수를 먼저 봅니다 ★

// ❌ 요소마다 경계를 넘음
const results = rows.map(r => native.process(r));   // 100만 번

// ✅ 배치
const results = native.processBatch(rows);          // 1번

// ✅✅ 이미 메모리에 있는 버퍼를 그대로 (j04)
const out = native.processBuffer(inputBuffer);      // 복사도 없음
경계 통과 비용 감각 (직접 재 보세요 · ⚡ e01)
  napi-rs 빈 함수 호출     대략 수십~수백 ns
  WASM 빈 함수 호출        더 쌉니다 (같은 프로세스·같은 VM)
  숫자 전달                거의 공짜
  문자열 전달              길이에 비례해 복사 (UTF-16 ↔ UTF-8 변환 ★)
  Buffer 전달              제로카피 가능 (j04)

★ 문자열이 의외의 함정입니다
  JS 문자열은 UTF-16, Rust 는 UTF-8 이라 매번 변환됩니다.
  대량 텍스트는 Buffer(바이트)로 주고받는 편이 훨씬 빠릅니다.

이벤트 루프를 막지 않기

★ Node 에서 가장 중요한 제약

  동기 함수가 100ms 걸리면
  그동안 서버는 아무 요청도 처리하지 못합니다.

  판단 기준
    < 1ms     동기로 두세요 (비동기 오버헤드가 더 큽니다)
    1~10ms    상황에 따라 (요청당 한 번이면 동기도 가능)
    > 10ms    반드시 비동기로 (j05) ★

  비동기로 만드는 방법
    · napi-rs 의 AsyncTask — 스레드 풀에서 실행
    · #[napi] async fn — tokio 런타임 사용
    · 둘 다 Promise 를 반환합니다

  WASM 은?
    WASM 도 동기로 돌면 메인 스레드를 막습니다.
    브라우저에서는 Web Worker 로, Node 에서는 worker_threads 로 옮기세요.
파이썬과 가장 다른 점 — 파이썬은 GIL 을 놓으면 되지만(🐍 y07), Node 는 싱글 스레드 이벤트 루프라 막는 순간 서버 전체가 멈춥니다. 네이티브 애드온을 만들 때 비동기 설계가 성능보다 먼저입니다.

napi-rs 가 그 위에서 하는 일

N-API 는 C 인터페이스라 그대로 쓰면 장황합니다.
napi-rs 는 매크로로 그것을 감춥니다.

  #[napi]
  fn add(a: i32, b: i32) -> i32 { a + b }

  ↓ 매크로가 생성하는 것 (개념)

  · napi_value 인자를 i32 로 변환하는 코드
  · 타입이 안 맞으면 TypeError 를 던지는 코드
  · 결과를 napi_value 로 변환
  · 모듈 등록 코드
  · TypeScript 타입 정의(.d.ts) 생성 ★  ← 이게 큰 이점입니다

# 생성된 코드 보기
cargo expand --lib

★ .d.ts 자동 생성은 파이썬 쪽(.pyi 를 손으로 · 🐍 y10)보다 나은 점입니다.
  타입이 코드와 어긋날 수 없습니다.
정리 — 브라우저·엣지면 WASM, Node 서버에서 최고 성능이면 애드온, 크래시 격리·CLI 겸용이면 별도 프로세스입니다. 애드온은 N-API 덕분에 Node 버전이 바뀌어도 재빌드가 필요 없지만, 플랫폼별 바이너리를 CI 로 만들어야 합니다(j10). 무엇을 고르든 10ms 이상 걸리면 비동기로 만드세요.
고르는 기준은 성능이 아니라 어디서 돌아야 하는가입니다.

// src/lib.rs
#![deny(clippy::all)]

use napi_derive::napi;

/// 1..n 의 제곱합
#[napi]
pub fn sum_squares(n: u32) -> u32 {
    (1..=n).map(|x| x * x).sum()
}

#[napi]
pub fn count_words(text: String) -> u32 {
    text.split_whitespace().count() as u32
}

#[napi(object)] 은 '복사' 입니다
  JS 객체의 각 필드를 읽어 Rust 구조체를 만듭니다.

  ② Buffer 로 직렬화 (j04)
  ③ 객체 대신 개별 인자

숫자 타입 함정 ★

JS 의 number 는 f64 입니다 — 정수는 2^53 까지만 정확합니다.

  #[napi] fn f(n: i64) -> i64      → TS 에서 bigint
  #[napi] fn g(n: i32) -> i32      → TS 에서 number ✅
  #[napi] fn h(n: f64) -> f64      → number ✅

★ 실무 권장
  · 카운트·인덱스는 u32/i32 로 (40억까지면 대부분 충분)
  · 진짜 큰 수는 bigint 를 받아들이거나 문자열로
  · 타임스탬프(ms)는 f64 로 두면 2^53ms ≈ 28만년까지 안전합니다

오버플로 동작
  u32 자리에 -1 을 주면?          → 변환 에러 (napi 가 검사)
  u32 자리에 2^40 을 주면?        → 변환 에러
  f64 자리에 NaN 을?              → NaN 그대로 들어옵니다 ★ 직접 검사하세요

napi_value 는 핸들입니다

napi_value 는 V8 객체를 가리키는 '핸들' 입니다.
GC 가 객체를 옮겨도 핸들은 유효합니다 (간접 참조).

★ 중요한 제약
  핸들은 '핸들 스코프' 안에서만 유효합니다.
  함수가 반환되면 그 스코프가 닫히고 핸들이 무효가 됩니다.
  → JS 값을 Rust 구조체에 저장하려면 Reference 를 만들어야 합니다.

  use napi::bindgen_prelude::*;
  let r: Ref<JsObject> = obj.create_ref()?;    // GC 로부터 보호
  // 나중에
  let obj = r.get_value(&env)?;
  r.unref(env)?;                                // ★ 반드시 해제

  napi-rs 의 고수준 타입(String · Vec · #[napi(object)])은
  전부 '값을 Rust 로 복사' 하므로 이 문제가 없습니다.
  그래서 대부분의 코드에서는 신경 쓸 일이 없습니다. ★

Buffer · TypedArray — 제로카피

이미지·오디오·대용량 파일을 다룬다면 여기가 성능의 전부입니다. Node 의 Buffer 는 연속된 바이트 덩어리라 Rust 슬라이스로 그대로 볼 수 있습니다. 파이썬의 numpy 제로카피와 같은 자리입니다(🐍 y06).

읽기 · 쓰기

use napi::bindgen_prelude::*;
use napi_derive::napi;

// 읽기 — 복사 없음 ★
#[napi]
pub fn checksum(data: Buffer) -> u32 {
    let bytes: &[u8] = &data;            // Deref 로 슬라이스 (🔐 o07)
    bytes.iter().fold(0u32, |a, b| a.wrapping_add(*b as u32))
}

// 제자리 수정 — 할당조차 없습니다
#[napi]
pub fn invert(mut data: Buffer) {
    let bytes: &mut [u8] = &mut data;
    for b in bytes.iter_mut() { *b = !*b; }
}

// 새 Buffer 반환 (Vec 을 그대로 넘김 — 복사 1회)
#[napi]
pub fn compress(data: Buffer) -> Result<Buffer> {
    let out: Vec<u8> = do_compress(&data)?;
    Ok(out.into())                        // ★ Vec<u8> → Buffer
}

// TypedArray
#[napi]
pub fn scale(mut a: Float64Array, k: f64) {
    for x in a.iter_mut() { *x *= k; }
}
#[napi]
pub fn sum_i32(a: Int32Array) -> i64 {
    a.iter().map(|x| *x as i64).sum()
}

외부 메모리와 finalizer

// C 라이브러리가 할당한 메모리를 복사 없이 JS 에 노출 (🔗 f08)
use napi::bindgen_prelude::*;

#[napi]
pub fn decode(env: Env, input: Buffer) -> Result<Buffer> {
    let (ptr, len) = unsafe { ffi::decode(input.as_ptr(), input.len()) };
    unsafe {
        Ok(Buffer::from_external(
            &env,
            ptr,
            len,
            (),                             // finalizer 에 넘길 값
            |_env, _hint| { ffi::free(ptr) }, // ★ GC 될 때 해제
        )?)
    }
}

// ★ 이 패턴의 요점
//   · JS 가 그 메모리를 다 쓰면 finalizer 가 불립니다
//   · 그때까지 C 쪽이 해제하면 안 됩니다 (소유권 규약 · 🔗 f06)
//   · finalizer 는 임의의 시점에 임의의 스레드에서 불릴 수 있습니다

// 메모리 압력 알리기 — GC 가 더 적극적으로 돌게
env.adjust_external_memory(len as i64)?;

#[napi]
pub fn process_into(input: Buffer, mut output: Buffer) -> Result<u32> {
    let src: &[u8] = &input;
    let dst: &mut [u8] = &mut output;
    if dst.len() < src.len() {
        return Err(Error::new(Status::InvalidArg, "출력 버퍼가 작습니다"));
    }
    for (d, s) in dst.iter_mut().zip(src) { *d = s.wrapping_add(1); }
    Ok(src.len() as u32)
}

Promise · 스레드 안전 콜백

워커 스레드에서 JS 함수를 부르려면 반드시 메인 스레드로 넘겨야 합니다. V8 은 스레드 안전하지 않기 때문입니다. 그 다리 역할을 하는 것이 ThreadsafeFunction 입니다 — 진행률·이벤트·스트림에 씁니다.

use napi::bindgen_prelude::*;
use napi::{Env, JsObject, Result};

// ② 직접 deferred 로 (외부 이벤트를 기다릴 때)
#[napi(ts_return_type = "Promise<number>")]
pub fn manual(env: Env) -> Result<JsObject> {
    let (deferred, promise) = env.create_deferred()?;

    std::thread::spawn(move || {
        std::thread::sleep(std::time::Duration::from_millis(100));
        match compute() {
            Ok(v) => deferred.resolve(move |_env| Ok(v)),   // ★ 메인 스레드에서 실행
            Err(e) => deferred.reject(Error::from_reason(e.to_string())),
        }
    });

}

ThreadsafeFunction — 콜백 ★

use napi::threadsafe_function::{
    ThreadsafeFunction, ThreadsafeFunctionCallMode, ErrorStrategy,
};

#[napi]
pub fn watch(
    #[napi(ts_arg_type = "(progress: number) => void")]
    callback: JsFunction,
) -> Result<()> {
    let tsfn: ThreadsafeFunction<f64, ErrorStrategy::Fatal> =
        callback.create_threadsafe_function(0, |ctx| {
            ctx.env.create_double(ctx.value).map(|v| vec![v])
        })?;

    std::thread::spawn(move || {
        for i in 0..=100 {
            std::thread::sleep(std::time::Duration::from_millis(50));
            tsfn.call(i as f64 / 100.0, ThreadsafeFunctionCallMode::NonBlocking);
        }
        // 마지막에 반드시 해제 — 안 하면 프로세스가 안 끝납니다 ★
        tsfn.abort().ok();
    });

    Ok(())
}

Blocking vs NonBlocking

// NonBlocking — 큐가 차면 버립니다 (진행률에 적합) ★
tsfn.call(value, ThreadsafeFunctionCallMode::NonBlocking);

// Blocking — 큐가 빌 때까지 기다립니다 (데이터 손실 불가일 때)
tsfn.call(value, ThreadsafeFunctionCallMode::Blocking);

// 큐 크기는 create 할 때 정합니다
callback.create_threadsafe_function(
    1024,        // 0 = 무제한 ★ 메모리 폭증 위험
    |ctx| { }
)?;

// ★ 실무 선택
//   진행률·로그        → NonBlocking + 작은 큐 (최신 값만 중요)
//   이벤트·데이터      → Blocking 또는 충분한 큐
//   무제한 큐(0)       → 생산이 소비보다 빠르면 메모리가 터집니다

// 에러 전략
//   ErrorStrategy::Fatal     — 콜백이 (value) 를 받음
//   ErrorStrategy::CalleeHandled — 콜백이 (err, value) 를 받음 (Node 관례)
let tsfn: ThreadsafeFunction<f64, ErrorStrategy::CalleeHandled> = ...;
tsfn.call(Ok(value), mode);
tsfn.call(Err(Error::from_reason("실패")), mode);

#[napi]
pub struct Watcher { tsfn: Option<ThreadsafeFunction<Event, ErrorStrategy::Fatal>> }

#[napi(object)]
pub struct Event { pub kind: String, pub path: String }

#[napi]
impl Watcher {
    #[napi(constructor)]
    pub fn new() -> Self { Watcher { tsfn: None } }

    #[napi]
    pub fn on_change(&mut self, callback: JsFunction) -> Result<()> {
        let tsfn = callback.create_threadsafe_function(64, |ctx| {
            Ok(vec![ctx.value])
        })?;
        self.tsfn = Some(tsfn);
        Ok(())
    }

    #[napi]
    pub fn close(&mut self) -> Result<()> {
        if let Some(t) = self.tsfn.take() { t.abort()?; }    // ★ 정리
        Ok(())
    }
}

  ④ 정말 스트림이 필요하면 Node 스트림 API 로 감싸기

  const queue = []
  let notify
  const w = new native.Watcher()
  w.onChange(ev => { queue.push(ev); notify?.() })
  try {
    while (true) {
      if (queue.length === 0) await new Promise(r => { notify = r })
      yield queue.shift()
    }
  } finally { w.close() }         // ★ 정리를 보장
}

use napi_derive::napi;
use regex::Regex;

#[napi]
pub struct Matcher {
    re: Regex,                       // 내부 필드 (JS 에 안 보임)
    pub count: u32,                  // pub 이면 속성으로 노출 ★
}

#[napi]
impl Matcher {
    #[napi(constructor)]
    pub fn new(pattern: String) -> Result<Self> {
        let re = Regex::new(&pattern)
            .map_err(|e| Error::new(Status::InvalidArg, e.to_string()))?;
        Ok(Matcher { re, count: 0 })
    }

    #[napi]
    pub fn find_all(&mut self, text: String) -> Vec<String> {
        self.count += 1;
        self.re.find_iter(&text).map(|m| m.as_str().to_string()).collect()
    }

    #[napi(getter)]
    pub fn pattern(&self) -> String { self.re.as_str().to_string() }

    #[napi(setter)]
    pub fn set_count(&mut self, v: u32) { self.count = v; }

    #[napi(factory)]                 // static 생성자
    pub fn from_words(words: Vec<String>) -> Result<Self> { }

    #[napi]
    pub fn to_string(&self) -> String { format!("Matcher({})", self.re) }
}

#[napi]
pub struct Db { conn: Option<Connection> }

#[napi]
impl Db {
    #[napi(constructor)]
    pub fn new(path: String) -> Result<Self> { }

    #[napi]
    pub fn close(&mut self) -> Result<()> {
        if let Some(c) = self.conn.take() { c.close()?; }   // ★ 명시적 정리
        Ok(())
    }

    #[napi]
    pub fn query(&self, sql: String) -> Result<Vec<Row>> {
        let c = self.conn.as_ref()
            .ok_or_else(|| Error::from_reason("이미 닫혔습니다"))?;
        c.query(&sql)
    }
}

impl Drop for Db {
    fn drop(&mut self) { let _ = self.conn.take(); }   // GC 될 때 안전망
}

// ★ GC 시점은 예측할 수 없습니다 (🔐 o07)
//   파일 핸들·연결처럼 한정된 자원은 반드시 close() 를 제공하세요.
//   JS 쪽에서 try/finally 나 using(TC39 명시적 자원 관리)으로 쓰게 합니다.

이렇게도 쓸 수 있다 — 설치 실패를 줄이기 🟡 중급

폴백 경로 만들기 ★

// index.js — 순서대로 시도
function loadNative() {
  // ① 플랫폼 서브 패키지
  try { return require('fastmod-linux-x64-gnu') } catch {}
  // ② 로컬 빌드 (개발 중 · 소스에서 설치)
  try { return require('./fastmod.node') } catch {}
  // ③ WASM 폴백 ★ 어떤 플랫폼에서도 동작
  try { return require('./wasm/fastmod.js') } catch {}
  // ④ 순수 JS 폴백
  return require('./js-fallback.js')
}
module.exports = loadNative()
★ WASM 폴백이 특히 좋은 전략입니다 (j01)
  같은 Rust 코드를 WASM 으로도 빌드해 두면
  지원하지 않는 플랫폼에서도 '느리지만 동작' 합니다.
  napi-rs 는 wasm32-wasi 타깃도 지원합니다.

★ 파이썬 쪽과 같은 원칙입니다 (🐍 y01 · y11)
  "되돌릴 수 있게 · 없어도 동작하게"
// package.json — 소스 빌드 폴백
{
  "scripts": {
    "install": "napi-postinstall || node scripts/build-from-source.js"
  }
}
// ❗ 다만 postinstall 빌드는 사용자에게 Rust 를 요구합니다.
//    최후의 수단으로만 두고, README 에 명시하세요.

사용자가 겪는 오류와 원인

"Cannot find module 'fastmod-linux-x64-gnu'"
  · 그 플랫폼 패키지를 배포 안 했거나
  · npm i --no-optional 로 설치했거나
  · lockfile 이 다른 플랫폼에서 만들어졌거나 ★
      → npm 은 optionalDependencies 를 lock 에 기록합니다.
        CI(linux)에서 만든 lock 을 맥에서 쓰면 문제가 됩니다.
        npm 8.6+ 는 개선됐지만, yarn/pnpm 은 설정을 확인하세요.

"Error relocating ...: symbol not found" (Alpine)
  · musl 빌드가 없어 glibc 빌드를 로드한 것

"was compiled against a different Node.js version"
  · N-API 를 안 쓰고 V8 API 를 쓴 애드온 (j01)
  · napi-rs 를 쓰면 이 오류는 나지 않습니다 ★

"invalid ELF header"
  · 아키텍처 불일치 (arm64 에서 x64 바이너리)
  · 애플 실리콘 맥에서 Rosetta 로 도는 Node 를 쓸 때도

★ 진단 명령
  node -p "process.platform + '-' + process.arch"
  node -p "process.report.getReport().header.glibcVersionRuntime"
  ldd $(node -p "require.resolve('fastmod-linux-x64-gnu')")

실무에선 이렇게 — 배포 체크리스트 🔴 실무

배포 전 확인 ★

□ 필요한 플랫폼을 전부 빌드했는가
    최소: linux-x64-gnu · linux-x64-musl · darwin-arm64 · win32-x64
□ 실제로 설치해 봤는가 (각 플랫폼에서)
    docker run --rm -it node:20-alpine sh -c "npm i fastmod && node -e '...'"
□ index.d.ts 가 패키지에 들어갔는가
    npm pack --dry-run 으로 파일 목록 확인 ★
□ files 필드에 필요한 것만 있는가 (src/ · target/ 제외)
□ 버전이 서브 패키지와 일치하는가
□ engines.node 가 N-API 버전과 맞는가
□ 바이너리 크기가 합리적인가 (🛠️ b10)
    strip = "symbols" · lto = true
□ 라이선스 파일이 포함됐는가
□ 첫 배포는 npm publish --tag next 로 미리 검증 ★

설치 검증 스크립트

#!/usr/bin/env bash
# scripts/verify-install.sh — 여러 환경에서 실제 설치 테스트
set -e

for img in node:20 node:20-alpine node:18; do
  echo "=== $img ==="
  docker run --rm "$img" sh -c "
    npm i -g fastmod@latest &&
    node -e \"const f=require('fastmod'); console.log(f.sumSquares(10))\"
  "
done

# arm64 도 (도커 buildx / QEMU)
docker run --rm --platform linux/arm64 node:20 sh -c "npm i fastmod && ..."
★ CI 에 넣으세요 (🛠️ b08)
  배포 job 다음에 '설치 검증' job 을 두고,
  실패하면 npm dist-tag 로 되돌립니다
    npm dist-tag add fastmod@0.9.0 latest

★ 되돌릴 수 있게
  · npm unpublish 는 24시간 제한이 있고 권장되지 않습니다
  · 대신 패치 버전을 올려 다시 배포하는 것이 정석입니다
  · deprecate 로 경고를 남길 수 있습니다
      npm deprecate fastmod@1.0.1 "설치 문제가 있습니다. 1.0.2 를 쓰세요"

크기 줄이기 (🛠️ b10 과 같은 기법)

ls -lh *.node
cargo bloat --release --crates          # 어느 크레이트가 큰지 ★

npm pack --dry-run
npx package-size fastmod

공급망 신뢰 ★

네이티브 바이너리를 배포한다는 것은
사용자 머신에서 임의 코드를 실행한다는 뜻입니다.
그래서 신뢰 장치가 중요합니다.

□ CI 에서만 배포 (로컬에서 npm publish 금지)
    npm 의 Trusted Publishing / provenance 를 켜세요
      npm publish --provenance
    → npm 페이지에 '어느 워크플로에서 빌드됐는지' 가 표시됩니다 ★

□ 2FA 를 켜기 (npm 계정 · 자동화 토큰은 최소 권한)

□ 재현 가능한 빌드에 가깝게
    rust-toolchain.toml 로 컴파일러 고정 (r01)
    Cargo.lock 커밋 (🛠️ b03)

□ 의존성 감사
    cargo audit · cargo deny (🛠️ b09)
    npm audit

□ 서브 패키지도 같은 조직/계정에서 배포
    이름 선점(typosquatting) 방지를 위해 미리 확보해 두세요

★ 사용자 입장의 검증
  npm 페이지의 provenance 배지 확인
  또는 소스에서 직접 빌드 (cargo build --release)
파이썬 wheel 과 같은 문제입니다(🐍 y11) — 바이너리를 배포하는 순간 신뢰가 핵심이 됩니다. CI 에서만 배포 + provenance 두 가지는 반드시 갖추세요.
정리 — 플랫폼별 서브 패키지 + optionalDependencies 가 요즘 표준이고, napi-rs 의 CI 템플릿이 이걸 전부 만들어 줍니다. musl(Alpine)을 빠뜨리지 마세요 — 문의의 대부분이 여기서 옵니다. WASM 폴백을 두면 어떤 플랫폼에서도 동작하고, CI 에서만 배포 + provenance 로 신뢰를 확보하세요. 다음은 🔗 C ABI · FFI 탭입니다.
네이티브 패키지의 성패는 성능이 아니라 설치가 조용히 끝나는가에서 갈립니다.
