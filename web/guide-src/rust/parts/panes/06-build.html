cargo 가 하는 일 — 한 도구로 전부

cargo 는 빌드 도구이자 패키지 관리자이자 테스트 러너이자 문서 생성기입니다. 이 하나가 C++ 의 도구 대여섯 개를 대신합니다 — 그리고 그것이 Rust 로 네이티브 모듈을 만들 때 가장 크게 체감되는 이점입니다.

실무에선 이렇게 — build.rs 로 빌드에 끼어들기 🔴 실무

언제 쓰나

// build.rs — 크레이트 컴파일 '전에' 실행됩니다
fn main() {
    // ① C 코드 함께 컴파일 (🔗 f08)
    cc::Build::new().file("src/fast.c").compile("fast");

    // ② 바인딩 생성 (bindgen · cbindgen · 🔗 f04·f08)
    // ③ 코드 생성 (프로토콜 정의 → Rust 소스)
    let out = std::env::var("OUT_DIR").unwrap();
    std::fs::write(format!("{out}/generated.rs"), gen_code()).unwrap();

    // ④ 빌드 시각 · git 해시를 상수로 ★
    let hash = std::process::Command::new("git")
        .args(["rev-parse", "--short", "HEAD"]).output()
        .map(|o| String::from_utf8_lossy(&o.stdout).trim().to_string())
        .unwrap_or_default();
    println!("cargo:rustc-env=GIT_HASH={hash}");

    // ⑤ 조건부 컴파일 플래그
    if std::env::var("CARGO_CFG_TARGET_OS").unwrap() == "windows" {
        println!("cargo:rustc-cfg=feature=\"win\"");
    }

    // ★ 언제 다시 실행할지 반드시 지정하세요
    println!("cargo:rerun-if-changed=src/fast.c");
    println!("cargo:rerun-if-env-changed=MYLIB_PATH");
}
// 생성된 코드 쓰기
include!(concat!(env!("OUT_DIR"), "/generated.rs"));
const GIT_HASH: &str = env!("GIT_HASH");

build.rs 의 주의점

□ rerun-if 를 지정하지 않으면
    소스가 하나라도 바뀔 때마다 build.rs 가 다시 돕니다 ★
    → 빌드가 눈에 띄게 느려집니다

□ 빌드 머신에 도구를 요구합니다
    cc → C 컴파일러 · bindgen → libclang
    → 사용자가 sdist 로 설치할 때 실패의 원인 (🐍 y12)
    → 가능하면 생성물을 커밋하고 feature 로 선택 (🔗 f08)

□ 크로스 컴파일에서 헷갈립니다 (b07)
    build.rs 는 '호스트' 에서 컴파일·실행됩니다
    HOST vs TARGET 환경 변수를 구분하세요

□ 네트워크를 쓰지 마세요
    빌드 재현성이 깨지고, 오프라인 빌드가 불가능해집니다

□ 출력은 OUT_DIR 에만
    소스 디렉터리에 쓰면 crates.io 게시가 실패합니다

★ 대안을 먼저 검토하세요
    · 상수 → 그냥 코드에 쓰기
    · 코드 생성 → 절차 매크로 (🔬 d09)
    · 플랫폼 분기 → #[cfg(target_os = "...")]
build.rs 는 임의 코드를 실행합니다 — 의존성을 추가할 때 그 크레이트의 build.rs 도 내 머신에서 돕니다. 공급망 보안 관점에서 cargo-deny 로 감사하세요(b09).

한 단계 더 — cargo 가 rustc 를 부르는 방식 🧬 전문가

지문(fingerprint)과 증분 빌드

cargo 는 크레이트마다 '지문' 을 계산해 저장합니다
  · 소스 파일 내용(mtime + 해시)
  · 컴파일 플래그 · feature 조합
  · 의존 크레이트의 지문
  · rustc 버전 · 타깃

하나라도 바뀌면 그 크레이트와 '그것에 의존하는 전부' 를 다시 빌드합니다.

★ 그래서 이런 일이 생깁니다
  · RUSTFLAGS 를 바꾸면 → 전체 재빌드
  · feature 를 켜고 끄면 → 그 크레이트 이하 전부
  · --release 와 debug 를 오가면 → 각각 별도 (둘 다 캐시됩니다)
  · CI 에서 캐시가 안 먹으면 → 매번 전체 빌드 (b08)

# 왜 다시 빌드하는지 보기
CARGO_LOG=cargo::core::compiler::fingerprint=info cargo build 2>&1 | head -30

# 무엇이 오래 걸리는지
cargo build --timings
#   → target/cargo-timings/cargo-timing.html ★ 병렬화 상태까지 보입니다

직접 rustc 를 부를 때

# cargo 없이 (의존성이 없다면)
rustc --edition 2021 -O src/lib.rs --crate-type cdylib

# cargo 가 넘기는 인자 보기
cargo build -v 2>&1 | grep rustc | head -3

# 특정 크레이트에만 플래그 주기
cargo rustc --release -p mycrate -- -C target-cpu=native

# 어셈블리·LLVM IR 보기 (⚡ e03 · 🔬 d10)
cargo rustc --release -- --emit asm
cargo rustc --release -- --emit llvm-ir
cargo asm --lib my_function          # cargo-show-asm (더 편합니다)

# 타입 크기 (r07 · 🔗 f03)
cargo +nightly rustc -- -Zprint-type-sizes

# 컴파일 단계별 시간 (🔬 d10)
cargo +nightly rustc -- -Ztime-passes
정리 — cargo 하나가 빌드·의존성·테스트·문서·린트를 전부 합니다. 편집 중엔 cargo check, 성능은 --release, 느려지면 cargo build --timings 로 원인을 보세요. build.rs 는 강력하지만 rerun-if-changed 를 반드시 지정하고, 가능하면 안 쓰는 편이 배포가 단순해집니다.

Cargo.toml — 읽는 법만 알면 됩니다

프로젝트가 무엇을 쓰는지 적어 두는 파일입니다. CMakeLists 처럼 로직이 들어가지 않고, 선언만 있습니다. 실무에서 실제로 만나는 항목만 정리합니다.

전체 구조

실무에선 이렇게 — 공개 API 를 관리한다 🔴 실무

semver 를 지키는 도구

# 공개 API 가 깨졌는지 자동 검사 ★
cargo install cargo-semver-checks
cargo semver-checks check-release

# 출력 예
#   --- failure enum_variant_added: pub enum variant added ---
#   Description: A publicly-visible enum has a new variant.
#   → #[non_exhaustive] 가 없으면 major 를 올려야 합니다 (r08)

# 공개 API 목록 뽑아 보기
cargo install cargo-public-api
cargo public-api
cargo public-api diff v0.1.0        # 이전 버전과 비교 ★

# CI 에 넣으면 실수로 API 를 깨는 것을 막습니다 (b08)
★ API 를 깨는 변경 (major 올림)
  · pub 함수·타입 제거·이름 변경
  · 함수 시그니처 변경
  · struct 에 pub 필드 추가 (non_exhaustive 없이)
  · enum 에 배리언트 추가 (non_exhaustive 없이)
  · trait 에 기본 구현 없는 메서드 추가 (🔐 o05)
  · 공개 타입의 트레이트 구현 제거
  · 최소 rust-version 올림 (논쟁적이지만 minor 로 보는 편)

의존성을 API 에 노출하지 않기 ★

// ❌ serde_json::Value 를 공개 API 에 두면
pub fn parse(s: &str) -> serde_json::Value;
// → serde_json 을 major 업데이트할 때 내 API 도 깨집니다
//   사용자도 같은 버전을 써야 합니다 (r09 의 중복 크레이트 문제)

// ✅ 내 타입으로 감싸기
pub struct Value(serde_json::Value);
pub fn parse(s: &str) -> Result<Value, Error>;

// ✅ 또는 재수출해서 버전을 명확히
pub use serde_json;                    // 사용자가 mylib::serde_json 으로 씁니다

// ★ 예외: 사실상 표준인 타입은 노출해도 됩니다
//   std 타입 · serde 트레이트 · http 크레이트의 타입 등

BUILD 03

의존성 · 버전 · Cargo.lock

"1.0" 이 정확히 무슨 뜻인지, Cargo.lock 을 커밋해야 하는지 — 이 둘만 알면 의존성 관리는 끝납니다. 재현 가능한 빌드가 목표입니다.

버전 표기의 뜻 ★

표기허용 범위
"1.2.3"≥1.2.3, <2.0.0 ★ 기본
"^1.2.3"위와 같음
"~1.2.3"≥1.2.3, <1.3.0
"=1.2.3"정확히 이것만
"1.2"≥1.2.0, <2.0.0
"1"≥1.0.0, <2.0.0
"0.2.3"≥0.2.3, <0.3.0 ★
"*"아무거나 (게시 금지)
★ 0.x 는 특별합니다
  semver 에서 0.x 는 "아직 안정되지 않음" 이라
  0.2 → 0.3 이 호환을 깰 수 있는 변경으로 취급됩니다.
  → Rust 생태계에는 0.x 크레이트가 아주 많습니다 (rand 0.8, pyo3 0.23)
  → 그래서 마이너 업데이트가 실제로 코드를 깨뜨립니다 ★

★ 실무 권장
  · 라이브러리를 만든다   → 넓게 ("1", "0.23")
  · 애플리케이션·서비스   → 넓게 쓰되 Cargo.lock 을 커밋 ★
  · "=1.2.3" 고정은 피하세요 — 보안 패치도 못 받습니다

Cargo.lock 을 커밋할까 ★

★ 공식 권장
  · 실행 파일 · 서비스 · 네이티브 모듈  →  커밋 ★
  · 라이브러리(crates.io 게시)          →  커밋해도 됩니다
      (게시할 때는 무시되고, CI 재현성에는 도움이 됩니다)

★ 커밋하면
  · 팀·CI·내 노트북이 정확히 같은 버전을 씁니다
  · "어제는 됐는데 오늘 CI 가 깨졌다" 가 사라집니다 ★
  · 의존성 업데이트가 명시적인 커밋이 됩니다 (리뷰 가능)

★ 커밋하지 않으면
  · 매번 최신 호환 버전을 씁니다
  · 새 버전의 버그를 바로 만납니다

# 갱신 명령
cargo update                    # 전부 (lock 범위 안에서)
cargo update -p serde           # 하나만
cargo update -p serde --precise 1.0.195
cargo upgrade                   # cargo-edit — Cargo.toml 의 범위 자체를 올림

# 무엇이 바뀌는지 미리 보기

★ 그래서 생기는 문제 (r09)
  · 타입이 달라 서로 못 주고받습니다
  · 바이너리가 커지고 빌드가 느려집니다
  · 전역 상태를 쓰는 크레이트는 두 벌이 각자 상태를 갖습니다 ★
      (log · tracing · rayon 스레드 풀 등에서 미묘한 버그)

# 해결

# 최소 버전으로 테스트 (라이브러리 저자용) ★
cargo +nightly build -Z minimal-versions

feature 통합의 함정 ★

같은 크레이트를 여러 곳이 쓰면 feature 가 '합쳐집니다'.

  내 크레이트: serde = { version = "1", default-features = false }
  의존성 X:    serde = { version = "1", features = ["std"] }
  → 결과: std 가 켜집니다 ★ 내가 끈 것이 무시된 셈

★ 이것이 no_std · WASM 빌드에서 자주 문제가 됩니다 (🟨 j09)

# 어떤 feature 가 최종적으로 켜졌는지 확인
cargo tree -f "{p} {f}"
cargo tree -e features -i serde

# resolver 2 (edition 2021 기본) 가 일부 개선했습니다
#   · build-dependencies 와 일반 의존성의 feature 를 분리
#   · 타깃별 의존성의 feature 를 분리
[workspace]
resolver = "2"

# 그래도 통합은 일어납니다 — 근본 해결은
#   ① 그 feature 를 켜는 의존성을 빼거나
#   ② 그 크레이트를 안 쓰거나
#   ③ 포크해서 feature 를 끄거나 ([patch])
정리 — "1.0" 은 1.x 중 최신, "0.2" 는 0.2.x 만 입니다. Cargo.lock 은 커밋하세요 — 재현 가능한 빌드의 출발점입니다. 컴파일러 · 의존성 · 컨테이너 이미지 · 빌드 플래그 네 가지를 고정하고, cargo audit·cargo deny 를 CI 에 넣으세요. cargo tree -d 로 중복 크레이트를 주기적으로 확인하는 습관도 유용합니다.
BUILD 04

feature 플래그 — 안 쓰는 건 빌드에서 빼기

기능을 켜고 끌 수 있게 만드는 장치입니다. 끈 기능은 코드도 의존성도 통째로 빠집니다 — 빌드 시간·바이너리 크기·공격 표면이 함께 줄어듭니다. 네이티브 모듈에서는 파이썬용·Node용 바인딩을 나누는 데 특히 유용합니다.

빌드가 느리다고 느껴지면 먼저 cargo tree 를 보세요 — 대개 안 쓰는 기능이 딸려 왔습니다.

정의와 사용

[features]
default = ["std", "compression"]      # 기본으로 켜지는 것 ★
std = []                              # 기능 이름만 (조건부 컴파일용)
compression = ["dep:zstd"]            # 선택적 의존성을 켬
python = ["dep:pyo3"]
node = ["dep:napi", "dep:napi-derive"]
full = ["compression", "python"]      # 여러 개를 묶기

[dependencies]
zstd = { version = "0.13", optional = true }     # ★ optional 이면 dep: 로 켬
pyo3 = { version = "0.23", optional = true }
napi = { version = "2", optional = true }
// 코드에서 분기
#[cfg(feature = "compression")]
pub fn compress(data: &[u8]) -> Vec<u8> { zstd::encode_all(data, 3).unwrap() }

#[cfg(not(feature = "compression"))]
pub fn compress(data: &[u8]) -> Vec<u8> { data.to_vec() }

#[cfg(feature = "python")]
pub mod python_bindings;              // 🐍 y02 · r09

// 조건 조합
#[cfg(all(feature = "std", not(target_arch = "wasm32")))]
#[cfg(any(feature = "a", feature = "b"))]

// 컴파일 타임 검사
#[cfg(all(feature = "python", feature = "node"))]
compile_error!("python 과 node 를 함께 켤 수 없습니다");
cargo build --features compression
cargo build --no-default-features
cargo build --no-default-features --features std
cargo build --all-features                # ★ CI 에서 전부 켜고 테스트

네이티브 모듈의 전형적 구성 ★

# 하나의 크레이트로 Rust 라이브러리 · 파이썬 모듈 · C ABI 를 전부
[features]
default = []
python = ["dep:pyo3"]                 # 🐍 PyO3 바인딩
capi = []                             # 🔗 C ABI 내보내기
extension-module = ["pyo3/extension-module"]

[lib]
crate-type = ["cdylib", "rlib"]       # rlib 도 두면 cargo test 가 됩니다
src/
├─ lib.rs          pub 로직 (feature 무관) ★
├─ core/           순수 Rust — 여기가 본체
├─ python.rs       #[cfg(feature = "python")]
└─ capi.rs         #[cfg(feature = "capi")]

빌드 방법
  cargo test                              # 순수 로직만 테스트 (빠름)
  maturin develop --features python       # 파이썬 모듈 (🐍 y03)
  cargo build --features capi --release   # C ABI (🔗 f02)

★ 이 구성의 이점
  · 핵심 로직을 한 번만 쓰고 여러 대상에 재사용
  · cargo test 가 파이썬 없이 돕니다 (🐍 y12 의 링크 에러 회피)
  · 각 바인딩은 얇은 변환 층만 담당

이렇게도 쓸 수 있다 — feature 설계 원칙 🟡 중급

더하기만 되어야 합니다 (additive) ★

★ 규칙: feature 를 켜면 '기능이 늘기만' 해야 합니다.

  ❌ 나쁜 예 — 켜면 동작이 바뀜
     [features]
     use-fast-hash = []      # 켜면 해시 알고리즘이 바뀜 → 결과가 달라짐
     no-std = []             # 켜면 기능이 줄어듦 ★ 이름부터 잘못

  ✅ 좋은 예
     [features]
     default = ["std"]
     std = []                # 켜면 기능이 늘어남
     fast-hash = []          # 켜면 대안이 '추가' 되고 API 로 선택

★ 왜 중요한가 (b03 의 feature 통합)
  내 크레이트를 쓰는 A 가 no-std 를 켜면
  같은 빌드 안의 B 도 no-std 로 동작하게 됩니다 —
  B 는 그걸 원하지 않았는데도요.

★ 그래서 관례
  · no_std 지원은 default = ["std"] + --no-default-features 로
  · 기능 제거가 아니라 기능 추가로 표현
  · 상호 배타적 feature 는 compile_error! 로 막기

no_std 지원하기

// src/lib.rs
#![cfg_attr(not(feature = "std"), no_std)]

#[cfg(feature = "std")]
extern crate std;

extern crate alloc;                    // Vec · String 은 alloc 에 있습니다
use alloc::{vec::Vec, string::String};

    }
}

#   코드 레이아웃을 실행 프로파일에 맞춰 재배열
#   i-cache 미스를 줄입니다 (큰 바이너리에서 효과)

clippy 는 “이렇게 쓰는 게 낫다”를 알려 주는 선배입니다. 잔소리가 아니라 대부분 진짜 개선이고, 초심자에게는 가장 좋은 학습 도구입니다. 프로젝트 초기에 켜 두세요 — 나중에 켜면 경고 수백 개를 한꺼번에 마주합니다.

# 실제로 자주 나오는 지적들
  · needless_range_loop
      for i in 0..v.len() { v[i] }  →  for x in &v { }        (r04)
  · redundant_clone
      불필요한 .clone() ★                                      (⚡ e02)
  · single_char_pattern
      s.split("a")  →  s.split('a')
  · manual_map / option_if_let_else
      match 를 .map() 으로                                     (r08)
  · large_enum_variant
      배리언트 하나가 너무 큼 → Box 로                          (r08)
  · too_many_arguments
      인자 8개 이상 → 구조체로                                  (r07)
  · missing_safety_doc
      unsafe fn 에 # Safety 주석이 없음 ★                      (🔬 d08)
초심자에게 가장 좋은 학습 도구입니다 — clippy 가 지적하는 것을 이유까지 읽으면 “Rust 답게 쓰는 법”이 자연스럽게 익혀집니다. cargo clippy --fix 로 자동 수정된 diff 를 읽어 보세요.

근본 원인

빌드가 느린 이유
  ① 단형화 — 제네릭을 타입마다 복제합니다 (r10 · 🔬 d10)
     타입 10개 × 함수 20개 = 코드 200벌을 LLVM 이 최적화
  ② 크레이트가 컴파일 단위 — 크레이트 하나가 통째로 다시 빌드됩니다
     (C++ 는 .cpp 파일 단위라 더 잘게 나뉩니다)
  ③ 절차 매크로 — syn/quote 를 빌드해야 하고, 확장 비용도 큽니다 (🔬 d09)
  ④ LLVM 최적화 — opt-level 3 · LTO 는 본질적으로 느립니다
  ⑤ 링크 — 큰 바이너리 하나를 만드는 데 시간이 듭니다

바이너리가 큰 이유
  ① 정적 링크가 기본 — 의존성이 전부 들어갑니다 ★
     (C 는 libc 를 동적 링크하므로 hello world 가 수십 KB)
  ② 단형화로 코드가 복제됩니다
  ③ 패닉 메시지·포맷 코드 (core::fmt 가 수십 KB · 🟨 j09)
  ④ 디버그 정보 (strip 하면 사라집니다)
  ⑤ 백트레이스 지원 코드

★ 그래서 근본 대책은
  · 의존성 줄이기
  · 제네릭 사용을 절제하기 (🔐 o06 의 dyn 전환)
  · 안 쓰는 feature 끄기 (b04)
  이 셋이 대부분입니다.
