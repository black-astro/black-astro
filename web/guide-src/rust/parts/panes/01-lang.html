RUST 01

Rust 를 실행하는 법 — cargo 하나면 됩니다

파이썬은 파일을 그냥 실행합니다. Rust 는 기계어로 번역한 뒤 그 결과물을 실행합니다. C++ 와 같은 구조지만 결정적인 차이가 하나 있습니다 — 빌드·의존성·테스트·문서를 cargo 하나가 전부 맡습니다.

첫 프로그램 — 파이썬과 나란히

// src/main.rs
fn main() {                       // 시작 지점이 반드시 있어야 합니다
    println!("안녕");             // print("안녕")
}
# ① 설치 — 이 한 줄이 컴파일러 + cargo + 문서를 전부 깝니다
#   https://rustup.rs  (윈도우는 rustup-init.exe)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

# ② 프로젝트 만들기 → ③ 실행
cargo new hello        # 폴더 · Cargo.toml · src/main.rs · git 저장소까지 한 번에
cd hello
cargo run              # 빌드하고 바로 실행 ★ 이 한 줄이 대부분입니다

# 파이썬은 이 한 줄이 전부였습니다
python hello.py
C++ 와 가장 크게 갈리는 지점 — C++ 는 컴파일러를 고르고, CMake 를 배우고, 패키지 매니저를 따로 깔아야 첫 줄이 돕니다. Rust 는 rustup 한 번, cargo run 한 번입니다. 이 차이가 🐍 파이썬 모듈 탭에서 그대로 이어집니다 (maturin develop 한 줄, 🐍 y03).

왜 이 귀찮음을 감수하나

파이썬Rust
실행 방식한 줄씩 해석미리 기계어로
타입 검사실행 중에컴파일할 때
에러를 보는 시점그 줄에 도달할 때실행 전
속도기준수십~수백 배
메모리 관리자동(GC)컴파일러가 검사
널 오류실행 중 터짐존재하지 않음
고치고 확인즉시빌드 기다림
오해 하나 — “Rust 가 빠르다”가 내가 쓴 Rust 코드가 빠르다는 뜻은 아닙니다. .clone() 을 남발한 Rust 는 numpy 보다 느립니다. 빠른 이유는 메모리 배치와 복사를 내가 직접 정할 수 있기 때문이고, 그건 ⚡ 성능 탭에서 다룹니다 (⚡ e02).

이렇게도 쓸 수 있다 — cargo 명령 지도와 에러 읽는 법 🟡 중급

실무에서 실제로 쓰는 명령 여덟 개

cargo new 이름          # 실행 파일 프로젝트
cargo new 이름 --lib    # 라이브러리 프로젝트 ★ 모듈을 만들 땐 이쪽

cargo check             # 타입만 검사 (코드 생성 안 함) ★ 가장 자주 씁니다
                        #   build 보다 3~5배 빠릅니다. 편집 중엔 이것만
cargo build             # 디버그 빌드 → target/debug/
cargo build --release   # 최적화 빌드 → target/release/  ★ 성능 측정은 반드시 이걸로
cargo run               # 빌드 + 실행
cargo test              # 테스트 전부 실행 (문서 안 예제까지)
cargo doc --open        # 내 코드 + 의존성 문서를 만들어 브라우저로 열기 ★

cargo add rand          # 의존성 추가 (Cargo.toml 을 직접 안 고쳐도 됩니다)
cargo clippy            # 린트 — "이렇게 쓰는 게 낫다"를 알려 줍니다 (🛠️ b09)
cargo fmt               # 자동 정렬 — 팀에서 포맷 논쟁이 사라집니다
가장 큰 생산성 차이 — cargo check 를 에디터에 붙여 두면 (rust-analyzer 가 자동으로 합니다) 저장하는 순간 타입 에러가 뜹니다. Rust 개발 시간의 대부분은 “빌드 기다리기”가 아니라 “빨간 줄 지우기”입니다.

실무에선 이렇게 — 툴체인을 고정하고 팀에서 같은 결과를 낸다 🔴 실무

rust-toolchain.toml — 버전을 저장소에 박아 둡니다 ★

# 프로젝트 루트에 두면 이 폴더에서는 항상 이 버전이 쓰입니다.
# 팀원·CI·내 노트북이 전부 같은 컴파일러를 쓰게 됩니다.
[toolchain]
channel = "1.83.0"                    # 정확한 버전 고정 ★ 실무 권장
components = ["rustfmt", "clippy"]    # 없으면 자동으로 깔립니다
targets = ["x86_64-unknown-linux-musl"]   # 크로스 빌드용 (🛠️ b07)
# 버전 관리 명령
rustup update                 # 최신 안정판으로
rustup toolchain list         # 깔린 것들
rustup default 1.83.0         # 전역 기본값
rustup component add clippy rustfmt rust-src

# "왜 내 PC 에서만 빌드가 깨지지?" 의 90%는 버전 차이입니다.
# rust-toolchain.toml 을 커밋하면 이 질문 자체가 사라집니다. ★
고정 vs 최신 — channel = "stable" 로 두면 항상 최신을 쓰지만, 새 clippy 린트가 추가되면 어제까지 통과하던 CI 가 깨집니다. 라이브러리는 stable, 서비스·배포용은 정확한 버전 고정이 무난합니다.

증분 컴파일 — target/ 에는 크레이트별 결과물과 지문(fingerprint)이 있습니다. 소스·플래그·의존성 중 하나라도 바뀌면 그 크레이트만 다시 빌드합니다. 플래그를 바꾸면(예: RUSTFLAGS) 전체가 다시 빌드되므로, 릴리즈와 디버그를 오가면 느려지는 것이 정상입니다.

에디션 — 언어가 바뀌어도 옛 코드가 돕니다 ★

# Cargo.toml
[package]

# 에디션은 '언어 방언'입니다. 크레이트마다 다른 에디션을 써도
# 서로 링크됩니다 — 이것이 Rust 가 하위 호환을 깨지 않고
# 언어를 개선해 온 방법입니다. ★
에디션이 실제로 바꾼 것들 (자주 만나는 것만)

        · async/await 도입
  2021  · 클로저가 구조체 필드 단위로 캡처 (🔐 o11)

에디션 ≠ 버전 — 에디션은 3년에 한 번, 컴파일러 버전은 6주마다 나옵니다. 새 문법 대부분은 에디션과 무관하게 최신 컴파일러면 그냥 쓸 수 있습니다. 에디션은 “기존 코드의 의미를 바꾸는 변경”만 담습니다.
정리 — rustup 으로 깔고 cargo new · cargo run 두 줄이면 시작입니다. 편집 중엔 cargo check, 성능을 볼 땐 반드시 --release. 막히면 help: 줄을 먼저 읽으세요 — Rust 에러 메시지는 대부분 답까지 적어 줍니다. 팀 프로젝트라면 rust-toolchain.toml 을 커밋하는 것으로 시작하세요.
RUST 02

변수 · 타입 — 기본이 “못 바꿈”입니다

파이썬·C++ 는 변수를 만들면 당연히 바꿀 수 있습니다. Rust 는 반대입니다. let 은 못 바꾸고, let mut 이라야 바꿉니다. 귀찮아 보이지만, 이 기본값 하나가 나중에 동시성 버그를 통째로 막아 줍니다(⚡ e06).

선언 — 세 가지 형태만 알면 됩니다

fn main() {
    let x = 5;              // 못 바꿈 (기본)
    // x = 6;               // ❌ error: cannot assign twice to immutable variable

    let mut y = 5;          // 바꿀 수 있음
    y = 6;                  // ✅

    let z: i64 = 5;         // 타입을 직접 적기 (필요할 때만)

    // 섀도잉 — 같은 이름으로 '새 변수'를 만듭니다 ★ 파이썬엔 없는 개념
    let s = "42";           // &str
    let s: i32 = s.parse().unwrap();   // 같은 이름, 다른 타입
    println!("{s}");        // 42

    // 왜 유용한가: 변환 과정에서 이름을 새로 짓지 않아도 됩니다
    // (s_str, s_num 같은 이름이 사라집니다)
}
mut 을 언제 붙이나 — 붙이지 않고 쓰다가, 컴파일러가 붙이라고 할 때 붙이면 됩니다. 에러 메시지가 정확히 그렇게 알려 줍니다(help: consider making this binding mutable). “일단 mut 부터 붙이고 보자”는 Rust 의 이점을 스스로 버리는 습관입니다.

디버그와 릴리즈가 다르게 동작합니다 ★

let x: u8 = 255;
let y = x + 1;

// 디버그 빌드  → panic: attempt to add with overflow ★ 즉시 멈춤
// 릴리즈 빌드  → 0 (한 바퀴 돌아감, wrapping)

// ❗ 이 차이 때문에 "테스트는 통과했는데 운영에서 값이 이상하다"가 생깁니다.
// 의도를 코드에 적으면 두 빌드가 같아집니다 ↓

let a = x.checked_add(1);      // Option<u8>  → None (넘치면 없음) ★ 가장 안전
let b = x.saturating_add(1);   // 255         → 최대값에서 멈춤
let c = x.wrapping_add(1);     // 0           → 한 바퀴 (의도적일 때만)
let (d, over) = x.overflowing_add(1);  // (0, true) → 값 + 넘쳤는지

// 실무 기본값: checked_* 를 쓰고 ? 로 전파 (🔐 o08)
fn safe_index(n: usize, off: usize) -> Option<usize> {
    n.checked_add(off)
}
릴리즈에서도 패닉시키고 싶다면 — Cargo.toml 에 [profile.release] overflow-checks = true 를 넣습니다. 비용은 보통 몇 % 수준이고, 금액·인덱스 계산이 있는 서비스라면 켜 두는 편이 낫습니다(🛠️ b06).

as 변환은 조용히 잘라 냅니다

let big: i64 = 300;
let small = big as u8;         // 44  ★ 경고도 없이 잘립니다

let f = 3.9_f64;
let i = f as i64;              // 3   (버림)
let neg = -1_i32 as u32;       // 4294967295

// ✅ 안전한 변환 — 실패를 값으로 받습니다
use std::convert::TryFrom;
let ok  = u8::try_from(big);           // Result<u8, _> → Err
let ok2: Result<u8, _> = big.try_into();

// ✅ 넓히는 변환은 From 으로 (절대 실패하지 않음)
let wide: i64 = i64::from(42_i32);     // ✅ 명확
let wide2 = 42_i32 as i64;             // 동작은 같지만 의도가 덜 드러남

// clippy 가 잡아 줍니다
//   cargo clippy -- -W clippy::cast_possible_truncation
실무 규칙 — 넓힐 때는 From/into(), 좁힐 때는 try_into(). as 는 “잘려도 괜찮다는 걸 내가 알고 있다”는 표시로만 쓰세요. FFI 경계(🔗 f03)에서 특히 자주 사고가 납니다.

실무에선 이렇게 — usize · 상수 · 타입 별칭 🔴 실무

usize 는 “이 기계에서 인덱스로 쓸 수 있는 크기” ★

let v = vec![1, 2, 3];
let i: usize = 0;          // 인덱스는 항상 usize
let x = v[i];

// 64비트에서는 u64, 32비트(wasm32 등)에서는 u32 크기입니다.
// → WASM 으로 빌드할 때 값이 안 맞는 사고가 여기서 납니다 (🟨 j08)

// ❌ 뺄셈이 위험합니다 — usize 는 음수가 없습니다
let n: usize = 3;
// let d = n - 5;          // 디버그: panic / 릴리즈: 거대한 수

// ✅
let d = n.checked_sub(5).unwrap_or(0);
let d2 = n.saturating_sub(5);          // 0

// 길이 비교는 뺄셈 말고 비교로
if v.len() > 5 { /* … */ }             // ✅

RUST 03

함수와 표현식 — 세미콜론 하나가 반환을 바꿉니다

Rust 에서는 거의 모든 것이 값을 내놓는 식(expression)입니다. if 도 match 도 블록 {} 도 값입니다. 그래서 마지막 줄에 세미콜론을 빼면 그게 반환값이 됩니다.

함수 — 파이썬과 나란히

fn add(a: i32, b: i32) -> i32 {
    a + b                 // ★ 세미콜론 없음 = 이것이 반환값
}

fn add2(a: i32, b: i32) -> i32 {
    return a + b;         // 이렇게 써도 됩니다 (조기 반환엔 필수)
}

fn shout(msg: &str) {     // 반환 타입이 없으면 () = 아무것도 안 돌려줌
    println!("{}!", msg);
}

// 인자 타입과 반환 타입은 '반드시' 적어야 합니다 (추론 안 함)
// 함수 안의 지역 변수만 추론합니다 ★
# 파이썬
def add(a, b):
    return a + b
가장 흔한 첫 실수 — a + b; 처럼 세미콜론을 붙이면 그 줄은 “값을 버리는 문장”이 되어 함수가 () 를 반환합니다. 에러: expected `i32`, found `()` → 세미콜론을 지우세요.

모든 것이 값입니다 ★

let area = {
    let w = 3.0;
    let h = 4.0;
    w * h                    // ★ 세미콜론 없음
};

// match 도 값입니다 (r04)
let kind = match n {
    0 => "영",
    1..=9 => "한 자리",
    _ => "여러 자리",

// loop 도 값을 낼 수 있습니다 (break 에 값을 실어서)
let found = loop {
    let x = next();
    if x > 100 { break x; }
};

// ❗ if 의 두 갈래는 타입이 같아야 합니다
// let x = if c { 1 } else { "하나" };   // ❌ 타입 불일치

이렇게도 쓸 수 있다 — 여러 값 반환과 구조 분해 🟡 중급

튜플 · 구조체 · 구조 분해

// 값 두 개를 돌려주기 — 파이썬의 return a, b 와 같습니다
fn min_max(v: &[i32]) -> (i32, i32) {
    (*v.iter().min().unwrap(), *v.iter().max().unwrap())
}
let (lo, hi) = min_max(&data);        // 구조 분해

struct Stats { min: i32, max: i32, mean: f64 }
fn stats(v: &[i32]) -> Stats { /* … */ }

let Stats { min, mean, .. } = stats(&data);   // 필요한 것만 꺼내기

let ((a, b), c) = ((1, 2), 3);

실무 기준 — 튜플은 둘까지. 셋부터는 struct 로 이름을 붙이세요. fn f() -> (bool, u32, String) 를 받는 쪽은 순서를 매번 문서에서 확인해야 합니다.

인자를 어떤 타입으로 받을 것인가 ★

// ❌ String 을 받으면 호출자가 소유권을 넘겨야 합니다 (r05)
fn greet_bad(name: String) { println!("안녕 {name}"); }
// greet_bad(s);  → 이후 s 를 못 씁니다

// ✅ 읽기만 한다면 &str 로 받으세요 — 가장 넓게 받아집니다
fn greet(name: &str) { println!("안녕 {name}"); }
greet("리터럴");          // ✅
greet(&owned_string);     // ✅ String → &str 자동 변환 (Deref, 🔐 o07)

// 슬라이스도 마찬가지
fn sum(v: &[i32]) -> i32 { v.iter().sum() }   // Vec 도 배열도 받습니다
sum(&vec);  sum(&[1,2,3]);

// 인자 타입 고르는 표
//   읽기만       → &str, &[T], &T
//   고칠 것       → &mut T
//   가져가 보관   → String, Vec<T>, T   ★ 소유권을 받는다는 신호
이 표 하나가 초반의 절반입니다 — Rust 초심자가 컴파일 에러에 갇히는 이유의 대부분은 “읽기만 하면 되는데 소유권을 받는 함수”를 만들었기 때문입니다. 자세한 건 🔐 o02 에서 봅니다.

실무에선 이렇게 — 유연한 시그니처와 impl Trait 🔴 실무

호출부를 편하게 만드는 관용구

use std::path::Path;

// ① 문자열·경로를 아무 형태로나 받기
fn open(p: impl AsRef<Path>) -> std::io::Result<File> {
    File::open(p.as_ref())
}
open("a.txt");  open(String::from("b.txt"));  open(&path_buf);   // 전부 ✅

// ② 어떤 이터레이터든 받기
fn total(xs: impl IntoIterator<Item = i32>) -> i32 {
    xs.into_iter().sum()
}
total(vec![1,2,3]);  total(1..=10);   // 전부 ✅

// ③ 반환 타입을 감추기 — 이름 없는 이터레이터·클로저를 돌려줄 때
fn evens(n: u32) -> impl Iterator<Item = u32> {
    (0..n).filter(|x| x % 2 == 0)
}

// ④ 기본값이 없으므로 Option 이나 빌더로 표현합니다 ★
fn connect(host: &str, port: Option<u16>) { let port = port.unwrap_or(8080); }
Rust 에는 기본 인자도, 오버로딩도 없습니다. 이름이 다른 함수(new/with_capacity)나 빌더 패턴으로 표현합니다. 이 제약 덕분에 “어느 오버로드가 불렸는지” 헷갈릴 일이 없습니다.

실패할 수 있는 함수의 모양

// Rust 에는 예외가 없습니다. 실패는 '반환값'입니다 (🔐 o08)
fn parse_port(s: &str) -> Result<u16, std::num::ParseIntError> {
    s.parse::<u16>()
}

// 없을 수도 있다 → Option
fn first_word(s: &str) -> Option<&str> {
    s.split_whitespace().next()
}

// 함수 시그니처만 봐도 알 수 있는 것 ★
//   -> T            반드시 성공
//   -> Option<T>    없을 수 있음
//   -> Result<T,E>  실패할 수 있고, 이유(E)가 있음
//
// 파이썬은 이걸 docstring 에 적었지만 Rust 는 '타입'에 적습니다.
// 그래서 호출자가 처리를 빠뜨리면 컴파일이 되지 않습니다.

한 단계 더 — never 타입 · const fn · 인라인 🧬 전문가

! — 절대 돌아오지 않는 타입

fn die(msg: &str) -> ! {        // 반환하지 않는다는 타입
    panic!("{msg}");
}

// ! 는 '어떤 타입으로도 강제 변환'됩니다. 그래서 이게 컴파일됩니다 ↓
let x: i32 = match opt {
    Some(v) => v,
    None => return,             // return 의 타입은 !
};
let y: u32 = if ok { 1 } else { panic!("실패") };   // panic! 의 타입도 !

// continue · break · std::process::exit 도 전부 ! 입니다.
// 이 규칙 덕분에 match 의 한 갈래에서 탈출해도 타입이 맞습니다. ★

const fn 과 인라인 힌트

// const fn — 컴파일 타임에도 계산할 수 있는 함수
const fn kib(n: usize) -> usize { n * 1024 }
const BUF: usize = kib(64);        // 컴파일 타임에 계산되어 상수로 박힘
let runtime = kib(x);              // 런타임 호출도 됩니다 (제약 없음)

// 인라인 힌트 — 대부분 필요 없습니다 (컴파일러가 더 잘 압니다)
#[inline]                 // 크레이트 경계를 넘어 인라인 가능하게
pub fn tiny(x: u32) -> u32 { x + 1 }

#[inline(always)]         // 강제 — 측정 없이 쓰면 대개 손해입니다 ★
#[inline(never)]          // 프로파일링에서 함수 이름을 남기고 싶을 때

// ★ 실무 규칙: 제네릭이 아닌 '작은 pub 함수'에만 #[inline] 을 답니다.
//   제네릭 함수는 어차피 호출 크레이트에서 코드가 생성됩니다 (🔬 d10)
측정이 먼저입니다 — 인라인 힌트로 얻는 이득은 대부분 오차 범위이고, always 를 남발하면 코드가 커져 캐시가 밀려 오히려 느려집니다(⚡ e01·e04).
정리 — 마지막 줄에 세미콜론이 없으면 그게 반환값입니다. if·match·블록이 전부 값이라 임시 변수가 크게 줄어듭니다. 인자는 읽기만 하면 &str/&[T], 보관하면 String/Vec<T>. 실패는 예외가 아니라 Option·Result 라는 반환 타입으로 표현합니다.
RUST 04

조건 · 반복 · match — 빠뜨리면 빌드가 막힙니다

if 와 for 는 파이썬과 거의 같습니다. 새로 배울 것은 match 하나입니다. match 는 “모든 경우를 적었는지” 컴파일러가 세어 줍니다. 이 성질이 나중에 코드를 고칠 때 빠뜨린 곳을 전부 찾아 주는 안전망이 됩니다.

조건과 반복 — 파이썬과 나란히

// 조건 — 괄호 없음, 중괄호 필수, bool 만 받습니다
if n > 0 {
    println!("양수");
} else if n == 0 {
    println!("영");
} else {
    println!("음수");
}
// ❗ if n { } 처럼 정수를 조건에 못 씁니다 (파이썬·C 와 다름)

// 반복 — 세 가지
for x in &v { println!("{x}"); }        // 파이썬 for x in v
for i in 0..v.len() { }                 // range(len(v))
for (i, x) in v.iter().enumerate() { }  // enumerate(v)
for (k, val) in &map { }                // dict.items()

while n > 0 { n -= 1; }

loop {                                   // while True
    if done() { break; }
}

// 라벨 — 중첩 루프를 한 번에 빠져나오기
'outer: for a in 0..10 {
    for b in 0..10 {
        if a * b > 50 { break 'outer; }
    }
}

match — switch 의 상위 호환 ★

let msg = match code {
    200 => "성공",
    301 | 302 => "리다이렉트",        // 여러 값
    400..=499 => "요청 오류",          // 범위
    n if n >= 500 => "서버 오류",      // 가드 (조건 추가)
    _ => "알 수 없음",                 // 나머지 전부
};

// ★ 결정적 차이: 빠짐없이 적지 않으면 컴파일이 안 됩니다
enum State { Idle, Running, Done }

fn label(s: State) -> &'static str {
    match s {
        State::Idle => "대기",
        State::Running => "실행 중",
        // State::Done 을 빠뜨리면 ↓
        // error[E0004]: non-exhaustive patterns: `State::Done` not covered
        State::Done => "완료",
    }
}
이게 왜 중요한가 — 나중에 State::Failed 를 추가하면, 처리하지 않은 모든 match 가 컴파일 에러로 뜹니다. “고쳐야 할 곳을 컴파일러가 전부 찾아 주는” 경험이 Rust 의 가장 큰 실무 이점입니다.

이렇게도 쓸 수 있다 — if let · let else · while let 🟡 중급

if let Some(v) = maybe {
    println!("값 {v}");

// ★ let else — "아니면 나간다" (Rust 1.65+) · 실무에서 매우 자주 씁니다
fn handle(input: &str) -> Result<u32, MyError> {

// 중첩 Option 풀기
if let Some(Some(inner)) = nested { }

상태 전이를 타입으로 적기

#[derive(Debug, Clone, Copy, PartialEq)]
enum Conn { Idle, Connecting { retries: u8 }, Ready, Failed }

fn step(state: Conn, ev: Event) -> Conn {
    use Conn::*;
    match (state, ev) {
        (Idle, Event::Start) => Connecting { retries: 0 },
        (Connecting { retries }, Event::Timeout) if retries < 3
            => Connecting { retries: retries + 1 },
        (Connecting { .. }, Event::Timeout) => Failed,
        (Connecting { .. }, Event::Ok) => Ready,
        (Ready, Event::Close) => Idle,
        (s, _) => s,                    // 그 외 이벤트는 무시
    }
}

RUST 05

소유권 첫 만남 — 값을 넘기면 원래 것을 못 씁니다

Rust 를 배우다 처음 벽에 부딪히는 자리입니다. 겁먹을 필요는 없습니다 — “값의 주인은 항상 한 명” 이 한 줄이 전부입니다. 여기서는 에러 메시지를 알아보는 수준까지만 하고, 깊은 규칙은 🔐 소유권 탭에서 봅니다.

이동(move) — 처음 만나는 에러

let s1 = String::from("안녕");
let s2 = s1;                 // ★ 복사가 아니라 '이동' — 주인이 s2 로 바뀝니다
// println!("{s1}");         // ❌ error[E0382]: borrow of moved value: `s1`

// 함수에 넘겨도 이동입니다
fn consume(s: String) { }
let s = String::from("안녕");
consume(s);
// println!("{s}");          // ❌ 같은 에러

// ✅ 해결 세 가지
let s = String::from("안녕");
consume(s.clone());          // ① 복사본을 준다 (비용 있음)
println!("{s}");             // s 는 그대로

fn peek(s: &String) { }      // ② 빌려 준다 ★ 대부분 이게 정답
peek(&s);
println!("{s}");

let s = consume_and_return(s);   // ③ 돌려받는다 (드묾)
파이썬과 비교 — 파이썬은 s2 = s1 이면 같은 객체를 둘이 가리킵니다. Rust 는 주인이 옮겨 가고 앞의 이름은 무효가 됩니다. 이 규칙 덕분에 “누가 언제 해제하나”가 항상 명확해서 GC 가 필요 없습니다.

이동하지 않는 타입도 있습니다 (Copy)

let a = 5;
let b = a;              // 복사 (i32 는 Copy)
println!("{a} {b}");    // ✅ 둘 다 멀쩡

// Copy 인 것들 — '스택에 통째로 들어가는 작고 단순한 값'
//   i32 u8 f64 bool char
//   &T (불변 참조)
//   위 타입들로만 이루어진 튜플·배열·구조체 (#[derive(Copy, Clone)] 필요)

// Copy 가 아닌 것들 — '힙을 가지고 있거나 해제가 필요한 값'
//   String  Vec<T>  Box<T>  File  HashMap  대부분의 구조체

#[derive(Clone, Copy)]         // 이렇게 하면 내 타입도 Copy 가 됩니다
struct Point { x: f64, y: f64 }

// ★ 판단 기준: "이걸 통째로 memcpy 해도 문제없나?" 가 Copy 의 조건입니다.
//   힙 포인터가 들어 있으면 두 주인이 같은 메모리를 해제하게 되므로 불가합니다.
왜 Copy 에 Clone 이 따라오나 — Copy 는 “비트 복사로 충분”, Clone 은 “복사하는 방법이 있다”입니다. 전자는 후자의 특수한 경우라 Copy 를 붙이려면 Clone 도 있어야 합니다.

    fn drop(&mut self) { println!("{} 해제", self.0); }
}

fn main() {
    let _a = Noisy("A");
    let _b = Noisy("B");
    {
        let _c = Noisy("C");
    }                       // C 해제

}                           // B 해제 → A 해제  ★ 선언의 역순

// 출력: C 해제 / 끝 / B 해제 / A 해제

// ★ 실무에서 이게 중요한 순간
//   락 가드(MutexGuard)와 파일 핸들의 해제 순서가 데드락·플러시 문제를 만듭니다.
//   일찍 놓고 싶으면 명시적으로:

Vec · String · 슬라이스 — 파이썬 list·str 의 자리

Vec<T> 가 파이썬 list, String 이 str 입니다. 다만 문자열이 두 종류(String 과 &str)라는 것, 그리고 인덱싱이 바이트 단위라는 것이 처음엔 걸립니다. 이 둘만 넘으면 됩니다.

Vec — 파이썬 list 와 나란히

let mut v: Vec<i32> = Vec::new();
let mut v = vec![1, 2, 3];          // 리터럴 매크로
let mut v = vec![0u8; 1024];        // 0 을 1024개 (파이썬 [0]*1024)

v.push(4);                          // append
v.pop();                            // pop() → Option<i32>
v.len();  v.is_empty();
v.insert(0, 9);   v.remove(0);
v.extend([7, 8]);                   // extend
v.sort();  v.reverse();  v.dedup(); // 정렬·뒤집기·중복 제거(인접)
v.contains(&3);

// 인덱싱 — 두 가지
let x = v[0];                       // 범위를 벗어나면 panic
let x = v.get(0);                   // Option<&i32> ★ 안전한 쪽
let x = v.get(0).copied().unwrap_or(0);

// 순회 세 가지 — 이 구분이 중요합니다 ★
for x in &v { }        // &i32     빌려 보기
for x in &mut v { }    // &mut i32 고치기
for x in v { }         // i32      가져가기 (이후 v 를 못 씀)
크기를 알면 미리 잡으세요 — Vec::with_capacity(n) 은 재할당을 없애 큰 루프에서 눈에 띄게 빨라집니다(⚡ e02). push 는 용량이 차면 2배로 늘리며 전체를 복사합니다.

String 과 &str — 왜 둘인가 ★

let owned: String = String::from("안녕");   // 힙에 내 것 (늘어날 수 있음)
let borrowed: &str = "안녕";                // 어딘가를 가리키는 창 (고정)

// 관계는 Vec<T> ↔ &[T] 와 정확히 같습니다
//   String  ↔ &str      (소유 ↔ 빌림)
//   Vec<T>  ↔ &[T]

// 서로 오가기
let s: String = borrowed.to_string();      // 복사 (비용 있음)
let s: String = borrowed.to_owned();       // 같은 것
let r: &str = &owned;                      // 공짜 (Deref)
let r: &str = owned.as_str();              // 같은 것

// ★ 실무 규칙 하나로 요약
//   함수 인자   → &str      (가장 넓게 받힘)
//   구조체 필드 → String    (수명 고민이 사라짐)
//   반환값      → String    (빌린 것을 돌려주려면 라이프타임이 필요 · 🔐 o03)

let mut s = String::new();
s.push_str("안");  s.push('녕');
s += " 세상";

구조체와 impl — 클래스를 반으로 갈라 둔 형태

Rust 에는 class 가 없습니다. 데이터는 struct, 동작은 impl 로 나눠 씁니다. 상속도 없습니다 — 공통 동작은 트레이트(🔐 o05)로 표현합니다. 처음엔 낯설지만, “이 타입이 무슨 데이터를 갖는가”가 한눈에 보입니다.

열거형과 Option — 널 오류가 존재하지 않는 이유

Rust 의 enum 은 다른 언어의 열거형보다 훨씬 강력합니다 — 각 배리언트가 값을 담을 수 있습니다. 그래서 “없을 수도 있음”을 None 이 아니라 Option<T> 라는 타입으로 표현하고, 그 결과 널 참조 오류가 언어에서 사라집니다.

값을 담는 열거형

enum Message {
    Quit,                          // 값 없음
    Move { x: i32, y: i32 },       // 이름 있는 필드
    Write(String),                 // 값 하나
    Color(u8, u8, u8),             // 여러 값
}

fn handle(m: Message) {
    match m {
        Message::Quit => println!("종료"),
        Message::Move { x, y } => println!("이동 {x},{y}"),
        Message::Write(s) => println!("쓰기 {s}"),
        Message::Color(r, g, b) => println!("색 {r}{g}{b}"),
    }
}

// ★ 다른 언어라면 이걸 '클래스 4개 + 공통 인터페이스'로 표현합니다.
//   Rust 는 한 타입으로 두고, 컴파일러가 모든 경우를 검사합니다.
//   이 조합(enum + match)이 Rust 코드가 안전한 가장 큰 이유입니다.

Option — 널이 없는 세계 ★

// 표준 라이브러리에 이렇게 정의돼 있습니다
// enum Option<T> { Some(T), None }

let a: Option<i32> = Some(5);
let b: Option<i32> = None;

// ★ 핵심: Option<i32> 와 i32 는 '다른 타입'입니다.
//   그래서 값을 꺼내지 않고는 계산에 쓸 수 없습니다.
// let sum = a + 1;         // ❌ 컴파일 에러

// 꺼내는 방법들
match a { Some(v) => v, None => 0 };
a.unwrap_or(0);                  // 없으면 0
a.unwrap_or_default();           // 없으면 기본값
a.unwrap_or_else(|| compute());  // 없으면 계산
a.unwrap();                      // 없으면 panic ★ 프로토타입·테스트에서만
a.expect("설정이 없습니다");      // panic 하되 이유를 남김

// 변환 — 꺼내지 않고 그대로 다루기 (자주 씁니다)
a.map(|v| v * 2);                // Some(10)
a.filter(|v| *v > 3);            // 조건에 맞으면 유지
a.and_then(|v| lookup(v));       // Option 을 반환하는 함수 연결
a.is_some();  a.is_none();
a.ok_or("없음")?;                // Option → Result (🔐 o08)
unwrap() 을 언제 써도 되나 — 테스트, 예제, 그리고 “여기서 None 이면 프로그램 논리가 깨진 것”이 확실할 때입니다. 라이브러리 코드에서는 expect("이유") 로 왜 그렇게 확신하는지를 남기세요.

이렇게도 쓸 수 있다 — 널 대신 Option 이 만든 차이 🟡 중급

실무에선 이렇게 — enum 으로 도메인을 표현한다 🔴 실무

불가능한 상태를 표현할 수 없게 만들기 ★

// ❌ 이 구조체는 '말이 안 되는 상태'를 만들 수 있습니다
struct Conn {
    connected: bool,
    socket: Option<TcpStream>,      // connected=true 인데 None 일 수 있음
    error: Option<String>,          // 셋 다 동시에 채워질 수도
}

// ✅ enum 으로 바꾸면 잘못된 조합이 '표현 불가능'해집니다
enum Conn {
    Disconnected,
    Connected(TcpStream),
    Failed(String),
}

// ★ "make illegal states unrepresentable" — Rust 설계의 핵심 관용구입니다.
//   검사 코드를 줄이는 게 아니라, 검사할 필요 자체를 없앱니다.

// 배리언트에 메서드 달기
impl Conn {

}

// 판별자 값을 직접 지정 (FFI·프로토콜에서 씁니다 · 🔗 f03)
#[derive(Debug, Clone, Copy, PartialEq)]
#[repr(u8)]
enum Status { Ok = 0, NotFound = 4, Error = 5 }

let code = Status::NotFound as u8;      // 4  ★ enum → 정수는 as 로

// 정수 → enum 은 자동이 아닙니다 (아무 값이나 올 수 있으니 당연)
impl TryFrom<u8> for Status {
    type Error = ();
    fn try_from(v: u8) -> Result<Self, ()> {
        match v {
            0 => Ok(Status::Ok),
            4 => Ok(Status::NotFound),
            5 => Ok(Status::Error),
            _ => Err(()),
        }
    }
}
// 이 보일러플레이트는 num_enum · strum 크레이트가 derive 로 만들어 줍니다

// 나중에 배리언트를 추가해도 사용자 코드가 안 깨지게 하려면
#[non_exhaustive]
pub enum ApiError { NotFound, Timeout }
//  → 외부 크레이트는 반드시 _ 갈래를 써야 합니다 (라이브러리 설계 · 🛠️ b02)

한 단계 더 — enum 은 메모리에서 어떻게 생겼나 🧬 전문가

널 포인터 최적화 ★

use std::mem::size_of;

size_of::<Option<u8>>();          // 2  (태그 1 + 값 1)
size_of::<Option<&u8>>();         // 8  ★ 태그가 없습니다!
size_of::<Option<Box<u8>>>();     // 8
size_of::<Option<String>>();      // 24 (String 과 동일)

// 왜? 참조·Box 는 '절대 널이 될 수 없다'는 것이 타입의 보장입니다.
// 그래서 컴파일러가 0 이라는 값을 None 표현으로 재활용합니다.
// → Option 을 써도 비용이 0 인 경우가 아주 많습니다.

// ★ FFI 에서 결정적으로 유용합니다 (🔗 f07)
//   Option<extern "C" fn(i32)> 는 C 의 '널 가능 함수 포인터'와
//   메모리 배치가 정확히 같습니다. 그대로 주고받을 수 있습니다.

// NonZero 타입도 같은 원리
size_of::<Option<std::num::NonZeroU32>>();   // 4

// enum 의 실제 배치를 보고 싶을 때
//   cargo +nightly rustc -- -Zprint-type-sizes

// print-type-sizes 출력 예
//   type: `Message`: 32 bytes, alignment: 8 bytes
//       variant `Write`: 24 bytes
//           field `.0`: 24 bytes        (String)
//       variant `Move`: 8 bytes
//           field `.x`: 4 bytes
//           field `.y`: 4 bytes
//       variant `Quit`: 0 bytes

// ★ 실무 함정: 배리언트 하나가 크면 enum 전체가 그 크기가 됩니다.
//   Result<(), BigError> 를 반환하면 성공 경로도 그 크기를 냅니다.
//   → 에러를 Box<dyn Error> 나 Box<BigError> 로 감싸면 8바이트가 됩니다 (🔐 o09)

// 판별자 값 읽기 (안정화된 방법)
let d = std::mem::discriminant(&msg);
// 값 비교 없이 '어느 배리언트인지'만 비교할 때 씁니다
성능 감각 — Result<T, E> 를 반환하는 함수가 느린 이유는 거의 항상 E 가 커서입니다. 에러 타입은 작게 유지하거나 Box 로 감싸세요. 측정 방법은 ⚡ e01 에서 봅니다.
정리 — Rust 의 enum 은 값을 담는 “이것 아니면 저것”입니다. Option<T> 가 널을 대체하고, 꺼내지 않으면 쓸 수 없어서 널 오류가 사라집니다. 설계할 때는 “불가능한 상태를 표현할 수 없게” enum 으로 묶으세요. Option<&T>·Option<Box<T>> 는 추가 비용이 0 입니다.
RUST 09

모듈 · 크레이트 — 파일이 자동으로 모듈이 되지 않습니다

파이썬은 파일을 만들면 그대로 모듈입니다. Rust 는 mod 로 “이 파일도 내 식구”라고 선언해야 합니다. 한 번만 이해하면 되는 규칙이지만, 처음 파일을 나눌 때 반드시 걸리는 자리라 여기서 정리합니다.

파일을 나누는 최소 규칙

src/
├─ lib.rs            ← 크레이트의 뿌리 (라이브러리)
├─ main.rs           ← 크레이트의 뿌리 (실행 파일)
├─ math.rs           ← 모듈 하나
└─ shapes/
   ├─ mod.rs         ← 옛 방식
   └─ circle.rs
또는
├─ shapes.rs         ← 새 방식 (2018+) ★ 이쪽을 권장
└─ shapes/
   └─ circle.rs
// src/lib.rs
mod math;              // ★ src/math.rs 를 읽어 들입니다 (이게 없으면 파일이 없는 것)
pub mod shapes;        // 밖에서도 쓸 수 있게

pub use shapes::Circle;   // 재수출 — 사용자는 crate::Circle 로 씁니다 ★

// src/math.rs

// src/shapes.rs

pub struct Circle { pub r: f64 }

제네릭 입문 — 타입을 나중에 채우는 틀

같은 코드를 i32 용·f64 용으로 두 번 쓰지 않게 해 주는 장치입니다. C++ 템플릿과 비슷하지만 훨씬 친절합니다 — 제약을 미리 적으므로 에러가 “수백 줄”이 아니라 “한 줄”로 나옵니다.

함수와 구조체의 제네릭

// fn largest<T>(v: &[T]) -> &T {
//     let mut m = &v[0];
//     for x in v { if x > m { m = x; } }    // ❌ T 를 비교할 수 있나?
//     m
// }

// ✅ '비교할 수 있는 타입만' 이라고 제약을 적습니다 (트레이트 바운드)
fn largest<T: PartialOrd>(v: &[T]) -> &T {

    for x in v { if x > m { m = x; } }
    m

C++ 템플릿과의 차이 — C++ 는 쓰다가 안 되면 에러가 납니다(수백 줄). Rust 는 정의할 때 제약을 적어야 하고, 안 맞으면 the trait bound `T: PartialOrd` is not satisfied 한 줄로 끝납니다.

// Rust
use std::collections::HashMap;
use std::fs;

fn word_count(path: &str) -> std::io::Result<Vec<(String, usize)>> {
    let text = fs::read_to_string(path)?;          // with open + read
    let mut counts: HashMap<&str, usize> = HashMap::new();

    for w in text.split_whitespace() {
        *counts.entry(w).or_insert(0) += 1;        // Counter
    }

    let mut v: Vec<_> = counts.into_iter()
        .map(|(k, n)| (k.to_string(), n))
        .collect();
    v.sort_by(|a, b| b.1.cmp(&a.1));               // most_common
    v.truncate(10);
    Ok(v)
}
