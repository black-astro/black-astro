OWN 01

소유권 규칙 — 세 줄이 전부입니다

Rust 에는 GC 가 없고, free() 도 직접 부르지 않습니다. 그런데도 메모리가 새지 않고 이중 해제도 없습니다. 비밀은 세 줄짜리 규칙과, 그것을 컴파일 타임에 검사하는 것뿐입니다.

규칙 세 줄 ★

① 모든 값에는 주인(owner)이 있다.
② 주인은 한 번에 한 명이다.
③ 주인이 스코프를 벗어나면 값은 해제된다.
{
    let s = String::from("안녕");   // ① s 가 주인
    // s 를 쓴다
}                                   // ③ 스코프 끝 → 힙 메모리 해제 (drop 호출)

let a = String::from("안녕");
let b = a;                          // ② 주인이 b 로 이동 (a 는 무효)

// 그래서 다음이 전부 자동으로 보장됩니다
//   · 해제를 빠뜨릴 수 없다      (주인이 사라지면 반드시 해제)
//   · 두 번 해제할 수 없다        (주인은 한 명)
//   · 해제 후 접근할 수 없다      (무효가 된 이름은 컴파일 에러)
//
// ★ C++ 의 RAII 와 같은 아이디어인데, C++ 는 '지키면 좋은 관례'이고
//   Rust 는 '어기면 컴파일이 안 되는 규칙'입니다. 이 차이가 전부입니다.

언제 해제되는지 눈으로 보기

struct Res(&'static str);
impl Drop for Res {
    fn drop(&mut self) { println!("[{}] 해제", self.0); }
}

fn take(r: Res) { println!("[{}] 받음", r.0); }   // r 이 주인이 됨

fn main() {
    let a = Res("A");
    let b = Res("B");
    take(b);                     // ★ 여기서 B 가 해제됩니다 (함수 끝에서)
    println!("함수 뒤");
}                                // A 해제

// 출력
//   [B] 받음
//   [B] 해제        ← take 가 끝나는 시점
//   함수 뒤
//   [A] 해제

// ★ "값을 함수에 넘기면 그 함수가 주인이 되고, 함수가 끝나면 해제된다"
//   이 감각이 잡히면 소유권 에러의 90%가 이해됩니다.
파이썬과 비교 — 파이썬은 참조 카운트가 0이 될 때 해제되므로 “언제 해제되는지 코드만 봐서는 모릅니다”. Rust 는 스코프를 보면 정확히 알 수 있습니다 — 그래서 파일·소켓·락 같은 자원도 메모리와 똑같이 다룰 수 있습니다.

Drop 안에서 패닉하지 마세요 — 이미 패닉 중에 drop 이 또 패닉하면 프로세스가 즉시 abort 합니다. Drop 구현은 실패할 수 없는 일만 하고, 실패할 수 있는 정리는 close() 같은 명시적 메서드로 두세요.

Drop 을 구현하면 잃는 것들

struct Guard { data: Vec<u8> }
impl Drop for Guard { fn drop(&mut self) { } }

// ★ Drop 을 구현하면 '부분 이동'이 금지됩니다
// fn take(g: Guard) -> Vec<u8> { g.data }
//   error[E0509]: cannot move out of type `Guard`,
//                 which implements the `Drop` trait
//   (필드를 빼가면 drop 이 무엇을 정리해야 할지 모호해지기 때문)

// 해법 — Option 으로 감싸고 take
struct Guard2 { data: Option<Vec<u8>> }
impl Guard2 {
    fn take(mut self) -> Vec<u8> { self.data.take().unwrap() }
}
impl Drop for Guard2 {
    fn drop(&mut self) { if let Some(d) = self.data.take() { /* 정리 */ } }
}

// Copy 와 Drop 은 함께 못 씁니다 (해제할 것이 있는데 비트 복사는 모순)
// ManuallyDrop 으로 우회하는 패턴은 FFI 에서 나옵니다 (🔗 f06 · 🔬 d04)
Drop 순서의 미묘한 함정 — 구조체 필드는 선언 순서대로 해제됩니다. runtime 필드와 그것을 쓰는 handle 필드가 있다면 선언 순서가 곧 종료 순서가 되어, tokio 런타임 종료 시 행이 걸리는 원인이 되곤 합니다(⚡ e08).
정리 — 주인은 한 명, 주인이 사라지면 값도 사라진다 — 이게 전부입니다. 그래서 메모리뿐 아니라 파일·락·연결도 똑같이 자동 정리됩니다. 설계할 때는 “이 데이터의 주인은 누구인가”를 먼저 정하세요. 검사는 컴파일 타임에 끝나므로 런타임 비용은 0 입니다.
주인은 언제나 한 명이라 누가 언제 해제하는지 코드만 보고 알 수 있습니다.
OWN 02

빌림 — 읽기는 여럿, 쓰기는 하나

값을 넘길 때마다 소유권이 옮겨 가면 아무것도 못 합니다. 그래서 잠깐 빌려 보는 참조(&)가 있습니다. 규칙은 딱 하나 — “읽기 참조는 여러 개, 쓰기 참조는 하나, 둘은 공존 못 함”. 이 한 줄이 데이터 경쟁을 언어 차원에서 없앱니다.

이 한 규칙이 데이터 경쟁 · 이터레이터 무효화 · 해제 후 사용을 한꺼번에 없앱니다.

빌림 규칙

let mut s = String::from("안녕");

// ✅ 불변 참조는 여러 개
let r1 = &s;
let r2 = &s;
println!("{r1} {r2}");

// ✅ 가변 참조는 하나
let m = &mut s;
m.push_str(" 세상");

// ❌ 불변과 가변은 함께 못 씁니다
// let r = &s;
// let m = &mut s;      // error[E0502]: cannot borrow `s` as mutable
// println!("{r}");     //   because it is also borrowed as immutable

// ★ 왜 이 규칙인가
//   "읽는 동안 아무도 못 바꾼다" 가 보장되면
//   · 이터레이터 무효화가 없고 (r06)
//   · 데이터 경쟁이 없고 (⚡ e06)
//   · 컴파일러가 값을 레지스터에 캐시해도 안전합니다 (최적화 이득)

참조는 언제까지 살아 있나 (NLL)

let mut s = String::from("안녕");

let r = &s;
println!("{r}");        // ★ r 의 '마지막 사용'이 여기
let m = &mut s;         // ✅ 통과합니다! r 은 이미 끝났으니까
m.push('!');

// 이것을 NLL (non-lexical lifetimes) 이라고 합니다.
// 참조의 수명은 스코프 끝이 아니라 '마지막으로 쓰인 곳'까지입니다.
// → 2018 이전 Rust 의 악명 높은 답답함이 대부분 여기서 사라졌습니다. ★

// 그래서 이런 코드도 됩니다
let mut v = vec![1, 2, 3];
let first = v[0];        // 값을 복사 (참조가 아님)
v.push(4);               // ✅ 문제없음

// 이건 여전히 안 됩니다 (참조를 계속 쓰니까)
// let first = &v[0];
// v.push(4);
// println!("{first}");  // ❌
에러가 났을 때 첫 번째 시도 — 참조를 쓰는 위치를 앞으로 당기거나, 값을 복사(copied()·clone())해 보세요. NLL 덕분에 순서만 바꿔도 통과하는 경우가 아주 많습니다.

// ① 순회하면서 수정
// for x in &v { if bad(x) { v.remove(0); } }     // ❌
v.retain(|x| !bad(x));                            // ✅
let to_remove: Vec<usize> = /* 인덱스 수집 */;    // ✅ 두 단계로

// ② self 의 두 필드를 동시에 (메서드 안에서)
// fn f(&mut self) { self.update(&self.data); }   // ❌ self 를 두 번 빌림
fn f(&mut self) {
    let data = std::mem::take(&mut self.data);    // ✅ 꺼냈다가

    self.data = data;                              //    돌려놓기
}
// 또는 필드를 분리해 함수로 빼기 (구조체 분해)
fn f2(&mut self) {
    let Self { data, cache, .. } = self;           // ✅ 필드 단위로 빌림
    cache.update(data);                            //    컴파일러가 구분해 줍니다
}

// ③ HashMap 에서 꺼내 쓰면서 다른 키 넣기
// if let Some(v) = m.get("a") { m.insert("b", v+1); }   // ❌
let v = m.get("a").copied();                       // ✅ 값을 복사해 끊기
if let Some(v) = v { m.insert("b".into(), v + 1); }

// ④ 클로저가 캡처를 오래 붙잡기 → o11 에서
// ⑤ 반환값이 인자를 빌리는 경우 → o03 (라이프타임)

에러 메시지를 해석하기

error[E0502]: cannot borrow `v` as mutable because it is also
              borrowed as immutable
  --> src/main.rs:4:5
   |
3  |     let first = &v[0];
   |                  - immutable borrow occurs here   ← ① 빌린 곳
4  |     v.push(4);
   |     ^^^^^^^^^ mutable borrow occurs here          ← ② 충돌한 곳
5  |     println!("{first}");
   |               ------- immutable borrow later used here  ← ③ 왜 아직 사나

# 읽는 순서: ③ → ① → ②
#   "③ 에서 아직 쓰고 있으니 ① 의 빌림이 살아 있고,
#    그래서 ② 의 가변 빌림이 안 된다"
#
# ★ 고치는 방법은 셋 중 하나입니다
#   · ③ 을 ② 앞으로 옮긴다        (순서 바꾸기 — 가장 흔한 답)
#   · ① 에서 값을 복사한다          (&v[0] → v[0])
#   · 구조를 나눈다                (필드 분해 · 함수 추출)
세 줄이 항상 있습니다 — 빌린 곳 · 충돌한 곳 · 나중에 쓴 곳. 이 세 곳 중 어느 하나를 옮기면 대부분 해결됩니다. “왜 안 되지”가 아니라 “셋 중 뭘 옮길까”로 생각하면 훨씬 빠릅니다.

MIR 위의 흐름 분석

빌림 검사(borrowck)는 소스가 아니라 MIR(중간 표현) 위에서 돕니다 (🔬 d10).

  ① 각 참조가 '살아 있는 지점들'의 집합을 계산 (liveness)
  ② 각 지점에서 어떤 빌림이 활성인지 추적
  ③ 충돌(같은 자리에서 가변+불변, 또는 가변 둘)을 찾으면 에러

RUSTC_LOG=rustc_borrowck cargo +nightly build

★ 중요한 성질: borrowck 는 '함수 하나 안에서만' 봅니다.
  함수 경계는 시그니처(라이프타임)만 보고 판단합니다 (o03).
  그래서 시그니처가 정확하면 구현을 바꿔도 호출자가 안 깨집니다.

// ★ 유명한 한계: 조건부로 빌림을 반환하는 패턴 (NLL 문제 사례 #3)
// fn get_or_insert<'a>(m: &'a mut HashMap<K,V>, k: K) -> &'a mut V {
//     if let Some(v) = m.get_mut(&k) { return v; }   // ❌ 여기서 빌림이
//     m.insert(k, V::default());                    //    끝나지 않은 것으로 봄
//     m.get_mut(&k).unwrap()
// }

// ✅ 우회 ① entry API (표준 라이브러리가 이걸 위해 존재합니다)
fn get_or_insert<'a>(m: &'a mut HashMap<String, V>, k: String) -> &'a mut V {
    m.entry(k).or_default()
}

// ✅ 우회 ③ polonius (차세대 borrowck) 를 기다리기 — 이 패턴을 허용합니다

// ★ 실무 감각: borrowck 가 막는 것의 대부분은 '진짜 문제'입니다.
//   위 사례처럼 '안전한데 못 통과하는' 경우는 손에 꼽을 정도이고,
//   전부 표준 라이브러리에 우회 API 가 마련돼 있습니다.
정리 — 읽기 참조는 여럿, 쓰기 참조는 하나, 둘은 공존 불가. 참조의 수명은 마지막 사용까지(NLL)라 순서만 바꿔도 풀리는 경우가 많습니다. 에러 메시지의 빌린 곳 · 충돌한 곳 · 나중에 쓴 곳 세 줄 중 하나를 옮기세요. 설계에서는 &self/&mut self 구분이 곧 동시성 계약입니다.

라이프타임 — 'a 는 무엇을 말하는가

'a 를 보면 겁이 나지만, 뜻은 단순합니다 — “이 참조는 저것보다 오래 살면 안 된다”는 표시일 뿐입니다. 대부분은 컴파일러가 알아서 붙여 줍니다. 우리가 적어야 하는 경우는 몇 가지로 정해져 있습니다.

"라이프타임을 붙였더니 컴파일된다"가 아니라 "이미 있던 관계를 적었을 뿐"입니다.

왜 필요한가 — 댕글링을 막습니다

// ❌ 컴파일러가 이걸 막아야 합니다
// fn longest(a: &str, b: &str) -> &str {
//     if a.len() > b.len() { a } else { b }
// }
//   error[E0106]: missing lifetime specifier
//   help: this function's return type contains a borrowed value, but
//         the signature does not say whether it is borrowed from `a` or `b`

// ✅ "반환값은 a, b 둘 다보다 오래 살지 않는다" 고 적어 줍니다
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

// 이 표시 덕분에 호출자 쪽에서 이런 코드가 막힙니다
let r;
{
    let tmp = String::from("짧다");
    r = longest(&long, &tmp);      // ❌ tmp 가 곧 죽는데 r 은 밖에 있음
}

중요한 오해 하나 — 'a 는 수명을 “정하는” 것이 아니라 “관계를 적는” 것입니다. 값이 더 오래 살게 만들지 않습니다. 컴파일러에게 검사 기준을 알려 줄 뿐입니다.

생략 규칙 — 안 적어도 되는 경우 ★

//   ① 각 참조 인자에 서로 다른 라이프타임을 준다
//   ② 인자가 참조 하나뿐이면, 반환값도 그것으로 정한다
//   ③ 메서드에 &self 가 있으면, 반환값은 self 로 정한다

//   적어야 하는 경우는 사실상 둘뿐입니다
//     · 참조 인자가 둘 이상이고 반환값이 참조일 때 (longest)
//     · 구조체가 참조를 필드로 가질 때 (아래)

// 구조체가 참조를 담을 때
struct Parser<'a> {
    input: &'a str,        // "Parser 는 input 보다 오래 못 산다"
    pos: usize,
}
impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self { Self { input, pos: 0 } }
    fn rest(&self) -> &'a str { &self.input[self.pos..] }
}

struct Owned { data: Vec<u8> }

// ★ 실무 판단 기준
//   · 수명이 짧고 성능이 중요한 파서·이터레이터 → 참조 (①)
//   · 오래 보관하는 설정·상태·핸들            → 소유 (②)
//   · 애매하면 소유로 시작                      ← 초심자 권장 ★
//
// 파싱 라이브러리(serde, nom)가 ① 을 쓰는 이유는
// "입력 버퍼가 살아 있는 동안만 쓰인다"가 명확하기 때문입니다.

// 둘 다 지원하기 — Cow (Clone on Write)
use std::borrow::Cow;
fn normalize(s: &str) -> Cow<'_, str> {
    if s.contains(' ') { Cow::Owned(s.replace(' ', "_")) }   // 고칠 때만 복사
    else { Cow::Borrowed(s) }                                // 아니면 빌린 채로
}

처방을 순서대로 시도합니다 ★

① 소유 값으로 바꿔 본다
     &str → String,  &[T] → Vec<T>
     → 90% 는 여기서 끝납니다. 복사 비용은 대개 무시할 수준입니다.

② 참조를 반환하지 말고 인덱스·범위를 반환한다
     fn find(&self) -> &str        →  fn find(&self) -> Range<usize>

③ 콜백으로 뒤집는다 (내부 이터레이션)
     fn items(&self) -> Vec<&T>    →  fn for_each(&self, f: impl FnMut(&T))

④ Rc/Arc 로 공유 소유권을 만든다 (o10)
     여러 곳이 진짜로 같은 값을 오래 봐야 할 때만

⑤ 그래도 안 되면 구조를 바꾼다
     아레나 · 인덱스 기반 (o01)

★ 순서를 지키는 게 중요합니다. ①을 건너뛰고 ④부터 가면
  Rc<RefCell<T>> 로 뒤덮인, 런타임에 패닉하는 코드가 됩니다.

변성(variance) — 왜 어떤 건 되고 어떤 건 안 되나

// &'long T 를 &'short T 가 필요한 자리에 넣을 수 있습니다 (공변)
fn takes_short<'s>(x: &'s str) { }
let long: &'static str = "리터럴";
takes_short(long);            // ✅ 더 오래 사는 건 언제나 OK

// 하지만 &mut T 는 T 에 대해 '불변(invariant)' 입니다
// fn f<'a>(x: &mut &'a str, y: &'a str) { *x = y; }
//   → &mut 안의 라이프타임은 늘리지도 줄이지도 못합니다.
//   이걸 허용하면 짧은 참조를 긴 자리에 심을 수 있게 됩니다.

// 정리
//   &'a T          'a 에 공변, T 에 공변
//   &'a mut T      'a 에 공변, T 에 불변  ★ 여기가 에러의 근원
//   fn(T) -> U     T 에 반변, U 에 공변
//   Cell<T>        T 에 불변
//
// PhantomData 로 변성을 직접 지정하는 일은 unsafe 추상화에서 나옵니다 (🔬 d08)

OWN 04

슬라이스 — 복사 없이 들여다보는 창

슬라이스는 “어디서부터 몇 개”만 담은 두 워드짜리 값입니다. 복사가 없어 빠르지만, 원본이 바뀌면 창이 무효가 됩니다 — 그 위험을 컴파일러가 막아 주는 것이 핵심입니다.

슬라이스의 정체

let v = vec![10, 20, 30, 40, 50];
let s: &[i32] = &v[1..4];        // [20, 30, 40]

// 메모리에는 이것뿐입니다 — 데이터 복사 없음
//   { ptr: v.as_ptr() + 1*4,  len: 3 }
assert_eq!(std::mem::size_of::<&[i32]>(), 16);   // 포인터 8 + 길이 8

// 문자열도 같습니다
let text = String::from("안녕 세상");
let word: &str = &text[0..6];    // "안녕"  (바이트 인덱스 · r06)
assert_eq!(std::mem::size_of::<&str>(), 16);

// 소유 ↔ 빌림 대응표
//   String  → &str
//   Vec<T>  → &[T]
//   Box<[T]> → &[T]
//   [T; N]  → &[T]
// ★ 함수 인자는 항상 오른쪽(빌림)으로 받으세요 — 왼쪽 전부를 받을 수 있습니다

가변 슬라이스와 분할

정리 — 트레이트는 “이런 일을 할 수 있다”는 자격증이고, 상속을 대신합니다. 남의 타입에도 붙일 수 있고(고아 규칙 안에서), 기본 구현을 담을 수 있습니다. 실무에서는 Display·From·FromStr 를 구현할 일이 가장 많습니다. 구현이 하나뿐인 트레이트는 만들지 마세요 — 간접 층만 늘어납니다.
OWN 06

트레이트 객체 vs 제네릭 — 빠르게냐 유연하게냐

같은 트레이트를 쓰는 두 가지 방법이 있습니다. 제네릭(<T: Trait>)은 타입별로 코드를 만들어 빠르고, 트레이트 객체(dyn Trait)는 하나의 코드로 여러 타입을 담습니다. 고르는 기준은 명확합니다.

C++ 의 템플릿과 가상 함수의 관계와 정확히 같은 트레이드오프입니다.

두 방식을 나란히

trait Draw { fn draw(&self); }

// ① 제네릭 — 정적 디스패치
fn render_static<T: Draw>(x: &T) { x.draw(); }
//  컴파일러가 타입별로 함수를 복사해 만듭니다 (단형화 · r10)
//  → 호출이 인라인될 수 있고, 비용이 0 입니다

// ② 트레이트 객체 — 동적 디스패치
fn render_dyn(x: &dyn Draw) { x.draw(); }
//  실행 중에 vtable 을 보고 어느 draw 인지 찾습니다
//  → 함수 포인터 한 번 경유 (인라인 불가)

// ★ 결정적 차이: 여러 타입을 한 컬렉션에 담기
let shapes: Vec<Box<dyn Draw>> = vec![
    Box::new(Circle { r: 1.0 }),
    Box::new(Square { s: 2.0 }),        // ✅ 서로 다른 타입이 한 Vec 에
];
for s in &shapes { s.draw(); }

// let v: Vec<impl Draw> = vec![circle, square];   // ❌ 불가능

코드 크기타입만큼 ↑하나

//   · 안쪽 루프에서 초당 수백만 번 호출  → 제네릭
//   · 플러그인·핸들러 목록                → dyn
//   · 설정에 따라 구현이 바뀜             → dyn

//   dyn 호출 오버헤드는 보통 나노초 단위입니다.
//   함수 본문이 조금이라도 하는 일이 있으면 차이가 묻힙니다.
//   "dyn 은 느리다"는 대부분 측정 없이 하는 말입니다.

이렇게도 쓸 수 있다 — dyn 이 안 되는 경우 🟡 중급

객체 안전성 (object safety)

// 이 트레이트는 dyn 으로 못 씁니다
trait Bad {
    fn new() -> Self;                    // ❌ Self 를 반환
    fn compare<T>(&self, x: T);          // ❌ 제네릭 메서드
    fn clone_me(&self) -> Self;          // ❌ Self 반환
}
// let x: &dyn Bad = ..;
//   error[E0038]: the trait `Bad` cannot be made into an object

// 왜? vtable 에는 '함수 포인터'만 들어갑니다.
//   · Self 를 반환하면 크기를 모릅니다 (타입마다 다름)
//   · 제네릭 메서드는 함수가 여러 개라 포인터 하나로 못 담습니다

// ✅ 우회법
trait Good {
    fn clone_box(&self) -> Box<dyn Good>;      // Self 대신 Box<dyn>
    fn compare(&self, x: &dyn std::any::Any);  // 제네릭 대신 dyn
    fn new_default() -> Self where Self: Sized; // where Self: Sized 로
    //   → 이 메서드만 dyn 에서 제외됩니다 ★
}

// ① 실패할 수 있는 정리는 명시 메서드로도 제공하세요
impl Writer {
    pub fn finish(mut self) -> io::Result<()> {     // 에러를 받을 수 있음
        self.flush()?;
        self.done = true;
        Ok(())
    }
}
impl Drop for Writer {
    fn drop(&mut self) {
        if !self.done { let _ = self.flush(); }      // ★ 에러를 삼킬 수밖에 없음
    }
}

impl fmt::Display for MyError {

}

impl std::error::Error for MyError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        self.source.as_ref().map(|b| &**b as _)

}

//   ✅ write!(f, "{}", self.msg)   + source() 구현

★ 실무에서 알아야 할 것

  · 블록 자체가 해제되는 시점: strong == 0 && weak == 0
