unsafe 는 “아무거나 해도 된다”가 아니라 다섯 가지를 추가로 허용하는 것입니다. 대신 컴파일러가 검사하던 불변식을 사람이 지켜야 합니다. 이 탭은 FFI 를 다루다 보면 반드시 만나는 영역이고, 안전한 껍데기로 감싸 남에게 내놓는 법까지 봅니다.

DEEP 01

unsafe 가 실제로 푸는 것 — 다섯 가지

가장 큰 오해는 “unsafe 를 쓰면 검사가 꺼진다”는 것입니다. 타입 검사도, 빌림 검사도 그대로 돕니다. 딱 다섯 가지 동작이 추가로 허용될 뿐입니다.

unsafe 블록은 가능한 한 작게 하고, 바깥에 안전한 함수로 감싸 내보내는 것이 표준 관행입니다.

허용되는 다섯 가지 ★

unsafe {
    // ① 원시 포인터 역참조
    let x = *raw_ptr;                       // d03

    // ② unsafe 함수 호출 (FFI 포함)
    let n = ffi::c_function(arg);           // 🔗 f08

    // ③ 가변 static 접근 (2024 에디션에서 금지 방향)
    // COUNTER += 1;

    // ④ union 필드 읽기
    let v = my_union.as_int;                // 🔗 f03

    // ⑤ unsafe 트레이트 구현
    // unsafe impl Send for MyType {}       // ⚡ e06
}

// ★ 여전히 검사되는 것
//   · 타입 검사        (i32 를 String 에 못 넣습니다)
//   · 빌림 검사        (&mut 두 개를 동시에 못 만듭니다)
//   · 수명 검사
//   · 소유권 · Drop
//
// unsafe 는 '검사 해제' 가 아니라 '추가 권한' 입니다.
그래서 unsafe 블록은 짧을 수 있습니다 — 위험한 연산 한 줄만 감싸면 되고, 나머지 코드는 여전히 안전합니다. 블록을 최대한 좁게 유지하는 것이 첫 번째 원칙입니다.

두 종류의 unsafe

// ① unsafe 블록 — "내가 규칙을 지켰다"
fn safe_wrapper(v: &[u8], i: usize) -> u8 {
    assert!(i < v.len());
    unsafe { *v.get_unchecked(i) }      // 검사를 했으므로 안전
}

// ② unsafe fn — "부르는 쪽이 규칙을 지켜야 한다"
/// # Safety
/// `p` 는 `len` 바이트만큼 읽을 수 있는 유효한 포인터여야 합니다.
pub unsafe fn read_raw(p: *const u8, len: usize) -> Vec<u8> {
    std::slice::from_raw_parts(p, len).to_vec()
}

// ★ unsafe fn 에는 반드시 # Safety 문서를 쓰세요 (d08)
//   clippy::missing_safety_doc 이 강제해 줍니다 (🛠️ b09)

// 2024 에디션 — unsafe fn 안이 자동으로 unsafe 블록이 아닙니다
pub unsafe fn f(p: *const u8) {
    unsafe { *p };                      // ★ 명시적으로 감싸야 합니다
}
// → "이 함수의 어느 부분이 위험한지" 가 드러납니다

// 어트리뷰트도 unsafe 표기 (2024)
#[unsafe(no_mangle)]
pub extern "C" fn exported() { }        // 🔗 f02

이렇게도 쓸 수 있다 — 언제 정말 필요한가 🟡 중급

실무에서 unsafe 가 나오는 자리 ★

① FFI — 이 가이드의 주 무대입니다
     · C 함수 호출 (🔗 f08)
     · 포인터를 슬라이스로 (🔗 f02)
     · Box::into_raw / from_raw (🔗 f06)
     → 대부분의 네이티브 모듈에서 unsafe 는 여기뿐입니다

② 성능 — 검사 제거
     get_unchecked · from_utf8_unchecked
     → 측정으로 이득이 확인될 때만 (⚡ e03) ★
       대개 이터레이터로 해결됩니다

③ 자료구조 구현
     Vec · HashMap 같은 것을 직접 만들 때
     → 표준 라이브러리나 크레이트를 먼저 찾으세요

④ Send/Sync 를 손으로 붙일 때 (⚡ e06)

⑤ 초기화되지 않은 메모리 (d04)
     큰 버퍼를 0 으로 채우지 않고 쓰기

★ 실무 감각
  일반 애플리케이션 코드에서 unsafe 가 필요한 경우는 거의 없습니다.
  필요하다고 느끼면 대개 설계를 다시 볼 신호입니다 (🔐 o01).

쓰기 전에 확인할 것

□ 안전한 대안이 정말 없는가
    · get_unchecked → 슬라이싱으로 검사 제거 (⚡ e03)
    · from_utf8_unchecked → 한 번만 검증하고 재사용
    · transmute → bytemuck · zerocopy 크레이트 (🔗 f03)
    · 자기 참조 → 인덱스 기반 (🔐 o01)

□ 이득이 측정으로 확인됐는가 (⚡ e01) ★
    "빠를 것 같아서" 는 이유가 아닙니다

□ 불변식을 문서로 적을 수 있는가 (d08)
    적을 수 없다면 아직 이해하지 못한 것입니다

□ Miri 로 검증할 수 있는가 (d07)

□ 안전한 API 로 감쌀 수 있는가 (d08)
    사용자가 unsafe 를 쓰지 않게 하는 것이 목표입니다

★ 크레이트 전체에서 금지하기 (🛠️ b09)
  #![forbid(unsafe_code)]              // 아예 못 쓰게
  #![deny(unsafe_code)]                // allow 로 예외 가능
  → FFI 모듈만 예외로 두는 구성이 흔합니다

SAFETY 주석 쓰기

// 관례: unsafe 블록 바로 위에 SAFETY 주석 ★
let s = unsafe {
    // SAFETY: `ptr` 은 위에서 널을 검사했고, `len` 은 호출자가
    //         보장하는 유효 길이입니다. 이 함수가 반환되기 전까지
    //         해당 메모리는 해제되지 않습니다 (호출자 계약, f06 참조).
    std::slice::from_raw_parts(ptr, len)
};

// unsafe fn 에는 # Safety 섹션
/// 버퍼를 처리합니다.
///
/// # Safety
///
/// - `ptr` 은 `len` 바이트에 대해 유효하고 정렬돼 있어야 합니다.
/// - `len == 0` 이면 `ptr` 은 널이어도 됩니다.
/// - 호출 중 다른 스레드가 이 메모리를 수정하면 안 됩니다.
pub unsafe fn process(ptr: *const u8, len: usize) -> u32 { }

// clippy 로 강제 (🛠️ b09)
// #![warn(clippy::undocumented_unsafe_blocks)]
// #![warn(clippy::missing_safety_doc)]

// ★ 주석의 목적
//   6개월 뒤의 내가, 그리고 리뷰어가
//   "이게 왜 안전한가" 를 재확인할 수 있어야 합니다.
//   "안전함" 한 줄은 주석이 아닙니다.
SAFETY 주석을 쓸 수 없다면 그 unsafe 는 아직 안전하지 않은 것입니다. 조건을 명확히 적을 수 있을 때까지 안전한 대안을 찾으세요.

한 단계 더 — 안전성의 경계 🧬 전문가

건전성(soundness)이란

★ 핵심 원칙
  "안전한 코드만 써서는 UB 를 일으킬 수 없어야 한다"
  이것을 만족하면 그 API 는 '건전(sound)' 합니다.

★ 불건전한 API 의 예
  pub fn get(&self, i: usize) -> &T {
      unsafe { self.data.get_unchecked(i) }     // ❌ 검사 없이 노출
  }
  → 사용자가 안전한 코드로 out-of-bounds 를 일으킬 수 있습니다
  → 이 함수는 unsafe fn 이거나, 검사를 해야 합니다

★ 유명한 사례
  · 초기 std::mem::uninitialized (지금은 deprecated · d04)
  · Rc 를 Send 로 만든 크레이트들 (RUSTSEC 권고가 나왔습니다)
  · 라이프타임을 늘리는 transmute

★ 건전성 버그는 보안 취약점입니다
  RustSec 데이터베이스에 등록되고, cargo audit 가 잡습니다 (🛠️ b03)

★ 판단 기준
  "악의적인 사용자가 안전한 코드만으로 이 API 를 오용해
   메모리 안전성을 깨뜨릴 수 있는가?"
  → 그렇다면 설계를 고쳐야 합니다 (d08)

unsafe 를 줄여 온 역사

★ 표준 라이브러리와 생태계가 unsafe 를 대체해 온 것들

  mem::uninitialized      → MaybeUninit (d04)
  transmute (바이트 변환)  → bytemuck · zerocopy (🔗 f03)
  수동 포인터 산술         → 슬라이스 메서드 (chunks · windows)
  자기 참조 구조체         → 인덱스 · ouroboros · Pin (d05)
  수동 락프리 구현         → crossbeam (⚡ e07)
  C 문자열 처리            → CStr · CString (🔗 f06)
  정렬 안 된 읽기          → read_unaligned · bytemuck

★ 교훈
  "unsafe 가 필요하다" 고 느끼면
  먼저 crates.io 에서 검증된 대안을 찾아보세요.
  누군가 이미 그 문제를 안전하게 풀어 두었을 가능성이 높습니다. ★

# 검증된 크레이트인지 확인
#   다운로드 수 · 최근 커밋 · unsafe 사용량 (cargo geiger)
#   RustSec 권고 이력 (cargo audit)
정리 — unsafe 는 다섯 가지를 추가 허용할 뿐, 검사를 끄지 않습니다. 실무에서는 FFI 경계에서만 만나는 것이 정상이고, 블록을 좁게 · 한 모듈에 모아 · SAFETY 주석을 반드시 남기세요. 안전한 코드만으로 UB 를 만들 수 없어야 그 API 가 건전합니다.
DEEP 02

UB 목록 — 무엇이 금지인가

“정의되지 않은 동작(UB)”은 틀린 값이 나오는 정도가 아닙니다 — 컴파일러가 “일어날 리 없다”고 가정하고 코드를 지워 버립니다. 다행히 Rust 는 UB 조건이 목록으로 정리돼 있습니다. 이 목록 밖은 안전합니다.

UB 목록 ★

① 널·정렬 안 됨·해제된 포인터 역참조 (d03)
② 데이터 경쟁 — 동기화 없이 동시 접근 (⚡ e06)
③ 유효하지 않은 값 만들기
     · bool 에 0/1 이 아닌 값
     · char 에 유효하지 않은 코드포인트
     · enum 에 없는 판별자 ★
     · NonNull 에 0
     · &T 에 널이나 댕글링
     · 초기화되지 않은 메모리를 값으로 읽기 (d04)
④ 잘못된 aliasing
     · &mut T 가 살아 있는 동안 다른 경로로 접근
     · &T 가 살아 있는 동안 수정 ★
⑤ 할당 범위를 벗어난 포인터 산술
⑥ str 에 유효하지 않은 UTF-8
⑦ 언와인딩이 extern "C" 경계를 넘음 (🔗 f09)
⑧ 잘못된 인라인 어셈블리 (d10)
⑨ 무한 루프에 부수 효과가 없음 (일부 조건)

★ 이 목록에 없으면 UB 가 아닙니다
  · 정수 오버플로 → UB 아님 (랩어라운드 · r02) ★ C++ 와 다릅니다
  · 널 참조 생성 → 만들 수 없습니다 (Option 이 있으니)
  · 메모리 누수 → UB 아님 (안전합니다 · 🔐 o10)

UB 가 코드를 지우는 예

// ❌ 널일 수 있는 포인터를 먼저 역참조
unsafe fn bad(p: *const i32) -> i32 {
    let x = *p;                   // ① 역참조 → "p 는 널이 아니다" 가정
    if p.is_null() { return 0; }  // ② 그러므로 항상 거짓
    x                             // ③ → 검사가 통째로 삭제됩니다 ★
}
// 결과: 널을 넘겨도 크래시가 아니라 '검사 없이 진행'
//   → 디버그에서는 멀쩡하고 릴리즈에서만 터지는 대표 패턴

// ✅ 검사를 먼저
unsafe fn good(p: *const i32) -> i32 {
    if p.is_null() { return 0; }
    *p
}

// ❌ 유효하지 않은 enum 값 만들기
#[repr(u8)]
enum Status { Ok = 0, Err = 1 }
let s: Status = unsafe { std::mem::transmute(7u8) };   // ★ UB
// match 가 어느 갈래도 안 타거나, 엉뚱하게 동작합니다
// ✅ TryFrom 으로 검증 (r08)

// ❌ 안전한 코드에서도 UB 를 부를 수 있는 unsafe API
//    → 그것이 '불건전' 입니다 (d01)
UB 는 “그 줄에서 터진다”가 아닙니다 — 프로그램 전체에 대한 가정이 깨져 전혀 다른 곳에서 이상하게 동작합니다. 디버깅이 극도로 어려운 이유입니다.

이렇게도 쓸 수 있다 — C++ 와 비교 🟡 중급

여전히 조심할 것

// ① 정수 오버플로는 UB 는 아니지만 버그입니다 (r02)
let x: u8 = 255;
let y = x + 1;      // 디버그: 패닉 / 릴리즈: 0
// → checked_add · overflow-checks = true (🛠️ b06)

// ② 부동소수점
0.0 / 0.0           // NaN (UB 아님)
f64::INFINITY       // 정의됨
(1e308 * 10.0)      // inf
let n = f64::NAN as i32;    // 0 (Rust 는 saturating cast · 정의됨) ★

// ③ 패닉은 UB 가 아닙니다 — 정의된 동작입니다
//    다만 FFI 경계를 넘으면 UB (🔗 f09)

// ④ 무한 재귀 → 스택 오버플로 → abort (UB 아님, 프로세스 종료)

// ⑤ 메모리 누수 → 안전합니다 (🔐 o10)
std::mem::forget(value);        // 완전히 안전한 함수입니다

// ★ 그러니 "Rust 는 안전하다" 는 정확히는
//   "메모리 안전성과 데이터 경쟁 없음을 보장한다" 입니다.
//   논리 버그 · 데드락 · 누수 · 패닉은 여전히 사람의 몫입니다.

실무에선 이렇게 — UB 를 예방하는 습관 🔴 실무

FFI 에서 특히 조심할 것 ★

// ① 널·길이 0 을 먼저 처리 (🔗 f02)
unsafe fn to_slice<'a>(p: *const u8, len: usize) -> Option<&'a [u8]> {
    if len == 0 { return Some(&[]); }       // ★ from_raw_parts(null, 0) 은 UB
    if p.is_null() { return None; }
    Some(std::slice::from_raw_parts(p, len))
}

// ② 정렬 확인 (d03)
assert_eq!(p as usize % std::mem::align_of::<T>(), 0);

// ③ 수명 — 반환 참조의 수명을 함부로 늘리지 마세요
unsafe fn bad<'a>(p: *const u8) -> &'a str { }   // ★ 'a 를 호출자가 정합니다
// → 문서에 유효 범위를 명시하고, 가능하면 소유 값을 반환하세요 (🔗 f06)

// ④ 값 검증
let s = std::str::from_utf8(bytes)?;            // ✅ 검증
// let s = unsafe { std::str::from_utf8_unchecked(bytes) };  // ❌ 검증 없이

catch_unwind(AssertUnwindSafe(|| { }))

//    문서에 명시 (🐍 y06 의 numpy 제로카피)

DEEP 03

원시 포인터 — NonNull · 정렬 · 프로버넌스

참조(&T)와 달리 원시 포인터(*const T)에는 보장이 없습니다 — 널일 수도, 정렬이 안 됐을 수도, 이미 해제됐을 수도 있습니다. FFI 에서 매일 만나는 타입이므로 규칙을 정확히 알아야 합니다.

종류와 기본

let x = 42i32;
let p: *const i32 = &x;            // 불변 원시 포인터
let mut y = 42i32;
let q: *mut i32 = &mut y;          // 가변

// 만드는 것은 안전, 역참조가 unsafe ★
unsafe { println!("{}", *p); }

// 널
let n: *const i32 = std::ptr::null();
p.is_null();

// NonNull — 널이 아님을 타입으로 (r08 의 최적화도 받습니다)
use std::ptr::NonNull;
let nn: NonNull<i32> = NonNull::new(q).expect("널");
unsafe { *nn.as_ptr() }
// size_of::<Option<NonNull<T>>>() == size_of::<*mut T>()  ★

// 산술
unsafe {
    let p2 = p.add(1);             // T 크기 단위로 이동
    let p3 = p.offset(-1);
    let d = p2.offset_from(p);     // 거리
}
// ★ 할당 범위를 벗어나면 '계산만 해도' UB 입니다 (d02)
//   배열의 '마지막 다음 자리' 까지는 합법 (end 포인터)

// 안전한 변환
let s: &[i32] = unsafe { std::slice::from_raw_parts(p, len) };
let p = v.as_ptr();
let p = v.as_mut_ptr();

정렬이 중요한 이유 ★

use std::mem::{align_of, size_of};

// u64 는 8바이트 정렬이 필요합니다
let buf: [u8; 16] = [0; 16];
let p = buf.as_ptr().wrapping_add(1) as *const u64;   // ★ 정렬 안 됨
// unsafe { *p }                    // ❌ UB (일부 CPU 에서는 크래시)

// ✅ 정렬 안 된 읽기 전용 함수
let v = unsafe { p.read_unaligned() };
unsafe { q.write_unaligned(v) };

// ✅ memcpy 로 복사 (컴파일러가 최적화해 줍니다)
let mut v = 0u64;
unsafe {
    std::ptr::copy_nonoverlapping(
        buf.as_ptr().add(1), &mut v as *mut u64 as *mut u8, 8);
}

// ✅ 가장 좋은 방법 — bytemuck / zerocopy (🔗 f03)
// let v: u64 = u64::from_le_bytes(buf[1..9].try_into().unwrap());

// 정렬 확인
assert_eq!(p as usize % align_of::<u64>(), 0);
p.is_aligned();                     // 1.79+

// ★ 네트워크 버퍼·파일 데이터를 구조체로 캐스팅하는 코드가
//   이 함정에 가장 자주 빠집니다. from_le_bytes 를 쓰세요.
x86 은 정렬 안 된 접근을 허용하지만 ARM 일부에서는 크래시합니다. “내 PC 에서는 되는데 라즈베리파이·애플 실리콘에서 죽는다”의 원인이 정렬 위반인 경우가 많습니다.

이렇게도 쓸 수 있다 — 참조와 포인터 사이 🟡 중급

변환할 때의 규칙

// 참조 → 포인터: 항상 안전
let p = &x as *const i32;
let p = std::ptr::addr_of!(s.field);       // ★ 참조를 만들지 않고 주소만
let p = std::ptr::addr_of_mut!(s.field);
// → packed 구조체나 초기화되지 않은 필드에 필요합니다 (🔗 f03 · d04)

// 포인터 → 참조: unsafe (조건이 많습니다)
unsafe {
    let r: &i32 = &*p;                     // 다음을 전부 만족해야 합니다:
    //   · 널이 아님
    //   · 정렬됨
    //   · 유효한 값이 들어 있음 (초기화됨)
    //   · 'a 동안 해제되지 않음
    //   · &mut 라면 다른 접근이 없음 (aliasing)
    let r = p.as_ref();                    // Option<&T> — 널 검사 포함 ★
    let r = q.as_mut();                    // Option<&mut T>
}

// 읽기·쓰기 (참조를 만들지 않고)
unsafe {
    let v = p.read();                      // 복사해 옴 (Copy 아니어도 가능)
    q.write(value);                        // 기존 값의 Drop 없이 덮어씀 ★
    let old = q.replace(value);            // 기존 값을 돌려받음
    std::ptr::drop_in_place(q);            // Drop 만 실행
}
// ★ write 는 Drop 을 부르지 않습니다 — 초기화되지 않은 자리에 쓸 때 씁니다 (d04)

aliasing 규칙 ★

// ❌ &mut 가 살아 있는 동안 다른 경로로 접근
let mut x = 5;
let r = &mut x;
let p = &x as *const i32;      // ★ r 이 살아 있는데 다른 참조 생성
unsafe { println!("{}", *p); } // → UB (Miri 가 잡습니다 · d07)

// ✅ 포인터를 먼저 만들고 그것만 쓰기
let mut x = 5;
let p = &mut x as *mut i32;
unsafe { *p = 6; println!("{}", *p); }

// ★ Rust 의 &mut 는 "이 참조로만 접근한다" 는 강한 보장입니다.
//   그래서 LLVM 에 noalias 를 붙일 수 있고, 최적화가 공격적입니다 (⚡ e09).
//   이 보장을 깨면 컴파일러의 가정이 틀려 코드가 이상해집니다.

// 두 개의 &mut 가 필요한 경우 — 겹치지 않음을 증명하세요
let (a, b) = v.split_at_mut(mid);         // ✅ 안전 API (🔐 o02)

// 정말 필요하면 원시 포인터로 유지하고 참조를 만들지 마세요
unsafe {
    let p1 = v.as_mut_ptr();
    let p2 = p1.add(mid);
    // p1 과 p2 로만 접근 — 참조를 만들지 않음
}

실무에선 이렇게 — FFI 포인터 다루기 🔴 실무

방어적인 헬퍼 만들기 ★

// FFI 진입점마다 반복하지 말고 헬퍼로 (🔗 f02)
/// # Safety
/// `p` 가 널이 아니면 `len` 원소만큼 유효해야 합니다.
unsafe fn as_slice<'a, T>(p: *const T, len: usize) -> Option<&'a [T]> {
    if len == 0 { return Some(&[]); }
    if p.is_null() { return None; }
    debug_assert_eq!(p as usize % std::mem::align_of::<T>(), 0, "정렬 위반");
    Some(std::slice::from_raw_parts(p, len))
}

/// C 문자열 → &str
unsafe fn as_str<'a>(p: *const c_char) -> Option<&'a str> {
    if p.is_null() { return None; }
    std::ffi::CStr::from_ptr(p).to_str().ok()
}

/// 핸들 → &mut
unsafe fn as_handle<'a, T>(p: *mut T) -> Option<&'a mut T> {
    p.as_mut()
}

// 진입점은 이렇게 짧아집니다
#[no_mangle]
pub unsafe extern "C" fn mylib_process(p: *const u8, len: usize) -> i32 {
    let Some(data) = as_slice(p, len) else { return -1 };
    core_process(data)                     // 여기부터는 안전한 Rust ★
}

한 단계 더 — 프로버넌스 🧬 전문가

포인터는 주소만이 아닙니다

// ★ 포인터에는 '출처(provenance)' 가 함께 붙어 있습니다
//   어느 할당에서 왔는지, 어느 범위에 접근할 수 있는지

let a = [1u8, 2, 3];
let b = [4u8, 5, 6];
let pa = a.as_ptr();
let pb = b.as_ptr();

// 주소가 우연히 인접해도, pa 로 b 에 접근하면 UB 입니다 ★
// unsafe { *pa.add(3) }        // ❌ a 의 범위를 벗어남

// 정수로 갔다 오면 프로버넌스가 흐려집니다
let addr = pa as usize;
let p2 = addr as *const u8;     // ★ 어느 할당의 것인지 모호해집니다
// → 되도록 피하고, 꼭 필요하면 with_addr 를 쓰세요 (1.84+ 안정화)

let p3 = pa.with_addr(addr);    // ✅ pa 의 프로버넌스를 유지하며 주소만 바꿈
let addr = pa.addr();           // ✅ 주소만 꺼내기 (프로버넌스 없이)
let p4 = std::ptr::without_provenance(addr);   // 명시적으로 프로버넌스 없음

// ★ 왜 중요한가
//   컴파일러는 "이 포인터가 저 할당을 건드릴 리 없다" 고 가정합니다.
//   정수 왕복으로 그 가정을 깨면 최적화가 코드를 망가뜨립니다.
//   Miri 의 -Zmiri-strict-provenance 로 검사할 수 있습니다 (d07)

태그드 포인터와 실무

// 포인터 하위 비트에 플래그를 넣는 기법 (정렬 덕분에 비어 있습니다)
// u64 는 8바이트 정렬 → 하위 3비트가 항상 0

let p: *mut u64 = ...;
let tagged = p.map_addr(|a| a | 1);        // ★ 프로버넌스 유지
let flag = tagged.addr() & 1;
let clean = tagged.map_addr(|a| a & !1);

// ★ 실무에서 쓰이는 곳
//   · GC · 인터프리터의 값 표현
//   · 락프리 자료구조의 버전 태그 (d06)
//   · 인덱스와 플래그를 한 워드에

// ❗ 주의
//   · 이식성 (정렬 가정이 플랫폼마다 다를 수 있습니다)
//   · 디버깅이 어려워집니다
//   · Miri 로 반드시 검증하세요

// 대안: 별도 필드나 enum 을 쓰는 것이 대개 낫습니다.
//   메모리를 아끼는 이득이 정말 큰지 측정하세요 (⚡ e01)
정리 — 원시 포인터는 널·정렬·유효성·수명·aliasing 다섯 가지를 사람이 책임집니다. FFI 에서는 널 검사 → 길이 0 처리 → 정렬 확인 → 안전한 슬라이스로 넘기는 헬퍼 함수를 만들어 재사용하세요. 정렬 위반은 ARM 에서 크래시하고, 정수 왕복은 프로버넌스를 흐립니다.
DEEP 04

MaybeUninit — 초기화되지 않은 메모리

큰 버퍼를 0 으로 채우는 비용이 아까울 때가 있습니다. 하지만 초기화되지 않은 메모리를 값으로 읽는 것은 UB입니다(d02). MaybeUninit 이 그것을 합법적으로 다루는 유일한 방법입니다.

왜 필요한가

use std::mem::MaybeUninit;

// ❌ 예전 방식 — deprecated, UB 입니다
// let x: u32 = unsafe { std::mem::uninitialized() };

// ★ 왜 UB 인가
//   · bool 에 2 가 들어 있으면 match 가 이상해집니다 (d02)
//   · 컴파일러가 "초기화됐다" 고 가정해 최적화합니다
//   · Drop 이 쓰레기 값에 대해 실행될 수 있습니다

// ✅ MaybeUninit — "아직 값이 없을 수 있다" 를 타입으로
let mut x: MaybeUninit<u32> = MaybeUninit::uninit();
x.write(42);
let v = unsafe { x.assume_init() };     // ★ 쓴 뒤에만 호출

// 0 으로 채우기 (안전)
let z: MaybeUninit<u32> = MaybeUninit::zeroed();

// 배열
let mut arr: [MaybeUninit<u8>; 1024] = unsafe { MaybeUninit::uninit().assume_init() };
//   ★ MaybeUninit 배열 자체는 초기화가 필요 없으므로 이 assume_init 은 합법
for (i, slot) in arr.iter_mut().enumerate() { slot.write(i as u8); }
let arr: [u8; 1024] = unsafe { std::mem::transmute(arr) };

실무에서는 대개 필요 없습니다 ★

// ★ 먼저 안전한 대안을 확인하세요

// ① vec![0; n] — 0 으로 채우기
let mut buf = vec![0u8; 1024 * 1024];
//   OS 가 0 페이지를 주므로 큰 할당에서는 사실상 공짜입니다 ★
//   (calloc 이 페이지를 lazy 하게 매핑합니다)

// ② Vec::with_capacity + extend (r06 · ⚡ e02)
let mut v = Vec::with_capacity(n);
v.extend(iter);

// ③ 읽어서 채우기 — 표준 API 를 쓰세요
let mut buf = vec![0u8; 8192];
let n = reader.read(&mut buf)?;
buf.truncate(n);

// ④ spare_capacity_mut — Vec 의 미사용 영역을 MaybeUninit 로
let mut v: Vec<u8> = Vec::with_capacity(1024);
let spare = v.spare_capacity_mut();          // &mut [MaybeUninit<u8>]
// … 채운 뒤 …
unsafe { v.set_len(written); }               // ★ 실제로 쓴 만큼만

// ★ 측정 없이 MaybeUninit 를 쓰지 마세요 (⚡ e01)
//   memset 비용은 대개 무시할 수준이고,
//   틀리면 재현 불가능한 버그가 됩니다.
큰 버퍼의 vec![0; n] 은 생각보다 쌉니다 — OS 가 0 으로 채워진 페이지를 지연 할당하기 때문입니다. 실제로 memset 이 병목인지 프로파일러로 확인한 뒤에 MaybeUninit 를 고려하세요.

use std::ptr::addr_of_mut;

#[repr(C)]
struct Header { magic: u32, len: u32, name: [u8; 32] }

    let p = h.as_mut_ptr();
    unsafe {
        // ★ addr_of_mut! 로 참조를 만들지 않고 주소만 (d03)

        addr_of_mut!((*p).len).write(0);
        addr_of_mut!((*p).name).write([0; 32]);
        h.assume_init()                       // 전부 채운 뒤에만 ★
    }
}

//   그래서 실무에서는 그냥 이렇게 쓰는 것이 낫습니다
fn build_safe() -> Header {
    Header { magic: 0x4D59_4C42, len: 0, name: [0; 32] }
}

// C 함수가 구조체를 채워 주는 흔한 패턴 (🔗 f08)
// int foo_get_info(FooInfo *out);

#[repr(C)]
pub struct FooInfo { version: u32, flags: u32, name: *const c_char }

pub fn get_info() -> Result<FooInfo, Error> {
    let mut info = MaybeUninit::<FooInfo>::uninit();
    let rc = unsafe { ffi::foo_get_info(info.as_mut_ptr()) };
    if rc != 0 { return Err(Error::from(rc)); }
    // SAFETY: foo_get_info 가 0 을 반환하면 out 을 완전히 채웠다고
    //         문서에 명시돼 있습니다 (libfoo docs §4.1)
    Ok(unsafe { info.assume_init() })
}

// ★ 이것이 MaybeUninit 의 가장 정당한 용도입니다.
//   C 가 채워 줄 자리를 미리 0 으로 채울 필요가 없습니다.

// 배열도 마찬가지
let mut buf: Vec<MaybeUninit<u8>> = Vec::with_capacity(n);
unsafe {
    let written = ffi::foo_read(buf.as_mut_ptr() as *mut u8, n);
    buf.set_len(written);
}
// → 안전한 Vec<u8> 로 변환하려면 transmute 또는 재구성이 필요합니다

// ★ 원칙: MaybeUninit 를 API 밖으로 내보내지 마세요
//   내부에서만 쓰고, 밖에는 완성된 타입을 돌려줍니다 (d08)

pub struct Decoder { /* … */ }

impl Decoder {
    /// 디코딩 결과를 반환합니다.
    pub fn decode(&mut self, input: &[u8]) -> Result<Vec<u8>, Error> {
        let need = self.output_size(input);
        let mut out = Vec::with_capacity(need);

        // SAFETY: ffi::decode 는 반환값만큼의 바이트를 채웁니다.
        //         capacity 는 need 이상이 보장됩니다.
        let written = unsafe {
            let n = ffi::decode(self.raw, input.as_ptr(), input.len(),
                                out.as_mut_ptr(), need);
            if n < 0 { return Err(Error::from(n)); }
            n as usize
        };
        unsafe { out.set_len(written) };       // ★ 실제로 쓴 만큼
        Ok(out)
    }
}

// ★ set_len 의 조건
//   · len <= capacity
//   · 0..len 범위가 전부 초기화됐음
//   → 이 둘을 보장하지 못하면 UB 입니다

초기화되지 않은 값의 정체

★ "쓰레기 값이 들어 있다" 가 아닙니다
  LLVM 에서 초기화되지 않은 메모리는 'poison/undef' 값입니다.
  이것은 '아직 정해지지 않은 값' 이고,
  읽을 때마다 다른 값일 수 있습니다.

  let x: u8 = uninit();
  if x == x { }            // ★ 거짓일 수 있습니다
  if x < 128 && x >= 128 { }  // 둘 다 참일 수 있습니다

★ 그래서 컴파일러가 이상한 최적화를 합니다
  · 분기를 양쪽 다 지우거나
  · 값을 임의로 고정하거나
  · 그 코드 경로를 통째로 도달 불가로 판단

★ MaybeUninit<T> 는
  "이 메모리는 T 의 유효한 값이 아닐 수 있다" 를 타입으로 표현합니다.
  컴파일러가 그 가정을 하지 않으므로 안전하게 다룰 수 있습니다.

  size_of::<MaybeUninit<T>>() == size_of::<T>()    ★ 비용 0
  align_of 도 같습니다

DEEP 05

Pin — 움직이면 깨지는 것들

Rust 에서 값은 언제든 메모리 안에서 옮겨질 수 있습니다(이동은 memcpy · r05). 그런데 자기 자신을 가리키는 구조체는 옮겨지면 포인터가 무효가 됩니다. Pin 은 그것을 타입으로 막는 장치입니다 — async 의 기반이기도 합니다.

문제 상황

struct SelfRef {
    data: String,
    ptr: *const String,        // data 를 가리킴
}

let mut s = SelfRef { data: "안녕".into(), ptr: std::ptr::null() };
s.ptr = &s.data;

let moved = s;                 // ★ 구조체가 이동하면
// moved.ptr 은 '이전 위치의 data' 를 가리킵니다 → 댕글링

// ★ Rust 는 이동이 자유롭기 때문에 이 문제가 생깁니다.
//   C++ 는 이동 생성자에서 포인터를 고칠 수 있지만,
//   Rust 의 이동은 memcpy 이고 후크가 없습니다.

// 그래서 Pin 이 필요합니다
use std::pin::Pin;
let mut boxed = Box::pin(SelfRef { data: "안녕".into(), ptr: std::ptr::null() });
// Pin<Box<T>> 는 T 를 밖으로 꺼낼 수 없게 합니다 (T: !Unpin 일 때)
실무에서 Pin 을 직접 쓸 일은 드뭅니다 — async 를 쓰면 뒤에서 자동으로 쓰이고, 자기 참조가 필요하면 인덱스 기반(🔐 o01)이나 ouroboros·self_cell 크레이트가 더 실용적입니다.

Unpin — 대부분의 타입은 상관없습니다 ★

// 거의 모든 타입이 Unpin 입니다: u32 · String · Vec<T> · &T …

fn f<T: Unpin>(p: Pin<&mut T>) {
    let r: &mut T = p.get_mut();       // ★ Unpin 이면 그냥 꺼낼 수 있습니다
}

//   · async 블록이 만든 Future ★

// ★ 그래서 실무 감각은

//   struct FFuture { s: String, r: *const String, state: u8 }
//   → r 이 s 를 가리킵니다 = 자기 참조 ★
//   → 이 Future 가 이동하면 r 이 무효가 됩니다
//   → 그래서 !Unpin 이고, poll 은 Pin<&mut Self> 를 받습니다

let fut: Pin<Box<dyn Future<Output = u32> + Send>> = Box::pin(async { 42 });

fn recurse(n: u32) -> Pin<Box<dyn Future<Output = u32> + Send>> {

pin_project! {

    }

impl<F: Future> Future for Wrapper<F> {
    type Output = F::Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<F::Output> {

        *this.count += 1;

FFI 에서의 고정

// C 라이브러리가 우리 구조체의 주소를 보관하는 경우 (🔗 f07)
//   → 그 구조체가 이동하면 C 쪽 포인터가 무효가 됩니다

// ✅ Box 로 힙에 고정하고 주소를 넘기기
pub struct Callback { handler: Box<dyn Fn(i32)> }

pub struct Registration {
    inner: Box<Callback>,           // ★ Box 안의 주소는 이동해도 안 바뀝니다
}

impl Registration {
    pub fn new(f: impl Fn(i32) + 'static) -> Self {
        let inner = Box::new(Callback { handler: Box::new(f) });
        let ptr = &*inner as *const Callback as *mut c_void;
        unsafe { ffi::register(trampoline, ptr) };
        Registration { inner }
    }
}
impl Drop for Registration {
    fn drop(&mut self) { unsafe { ffi::unregister() } }   // ★ 반드시
}

// ★ Box<T> 를 이동해도 T 의 주소는 그대로입니다.
//   그래서 대부분의 FFI 시나리오에서는 Pin 없이 Box 로 충분합니다.
//   (Pin 이 필요한 것은 '스택에 있는 자기 참조' 같은 경우입니다)
Box<T> 안의 T 는 이동하지 않습니다 — Box 자체(포인터)만 이동합니다. 그래서 FFI 로 주소를 넘길 때는 Box 로 충분하고, Pin 까지 필요한 경우는 드뭅니다.

한 단계 더 — Pin 의 계약 🧬 전문가

정확히 무엇을 보장하나

Pin<P> 의 계약 (P 는 포인터 타입)

  T: Unpin 이면    → 아무 보장도 없습니다 (그냥 P 처럼 동작)
  T: !Unpin 이면   → "이 값은 drop 될 때까지 이 주소에 머문다" ★

  더 정확히
  · Pin<&mut T> 를 만든 이후로 T 는 이동하지 않습니다
  · T 의 메모리는 drop 이 호출될 때까지 무효화되지 않습니다
  · drop 이 반드시 호출됩니다 (mem::forget 으로 건너뛰면 안 됨) ★

★ 마지막 조건이 미묘합니다
  Pin 된 값을 mem::forget 하면 메모리가 재사용될 수 있는데,
  C 쪽이 그 주소를 여전히 보고 있으면 UB 입니다.
  → 이것을 'Drop 보장(drop guarantee)' 이라고 합니다.

★ 직접 구현할 때 지켜야 할 것
  · Pin<&mut Self> 를 받는 메서드에서 Self 를 이동하지 않기
  · get_unchecked_mut 로 꺼낸 참조로 mem::swap · mem::replace 금지
  · 필드 투영은 pin-project 를 쓰세요 (손으로 하면 실수하기 쉽습니다)

언제 !Unpin 을 만드나

use std::marker::PhantomPinned;

// 자기 참조나 외부에 주소를 등록한 타입
pub struct Registered {
    data: [u8; 1024],
    // C 쪽이 &self.data 를 보관 중
    _pin: PhantomPinned,           // ★ !Unpin 으로 만듭니다
}

impl Registered {
    pub fn new() -> Pin<Box<Self>> {
        let mut b = Box::pin(Registered { data: [0; 1024], _pin: PhantomPinned });
        let ptr = b.data.as_ptr();

        b
    }

    fn drop(&mut self) { unsafe { ffi::unregister_buffer() } }
}

//   훨씬 단순하고 다른 언어에서 쓰기도 좋습니다 (🔗 f06 의 불투명 핸들).
//   Pin 은 async 런타임·스트림 라이브러리를 만들 때 주로 필요합니다.
정리 — Rust 의 값은 언제든 memcpy 로 이동하므로 자기 참조가 깨집니다. Pin 이 그것을 타입으로 막지만, 대부분의 타입은 Unpin 이라 상관없습니다. 실무에서는 async 에서만 만나고, Box::pin·pin!·pin-project-lite 로 해결됩니다. 자기 참조가 필요하면 인덱스 · 라이프타임 분리 · self_cell 을 먼저 검토하세요.
DEEP 06

메모리 모델 · Ordering

멀티스레드에서 “다른 CPU 가 이 값을 언제 보게 되는가”를 정하는 규칙입니다. CPU 와 컴파일러가 명령 순서를 바꾸기 때문에, 필요한 순서를 명시해야 합니다. 락 프리 자료구조의 기반입니다.

다섯 가지 Ordering ★

Ordering뜻
Relaxed원자성만 · 순서 보장 없음
Acquire읽기 — 이후 연산이 앞으로 못 감
Release쓰기 — 이전 연산이 뒤로 못 감
AcqRel읽고 쓰기 (fetch_* 에)
SeqCst전역 순서 보장 · 가장 강함
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};

// ★ 실무 지침
//   · 단순 카운터 · 통계  → Relaxed (가장 쌉니다)
//   · 플래그로 데이터 전달 → Release/Acquire 짝 ★
//   · 헷갈리면            → SeqCst (느리지만 안전)

// 카운터
static COUNT: AtomicU64 = AtomicU64::new(0);
COUNT.fetch_add(1, Ordering::Relaxed);
COUNT.load(Ordering::Relaxed);

// 데이터 전달 — 이 짝이 핵심입니다 ★
static READY: AtomicBool = AtomicBool::new(false);
static mut DATA: u64 = 0;

// 생산자
unsafe { DATA = 42; }
READY.store(true, Ordering::Release);      // ★ 이전 쓰기가 먼저 보임을 보장

// 소비자
if READY.load(Ordering::Acquire) {         // ★ 이후 읽기가 뒤에 일어남을 보장
    unsafe { println!("{}", DATA); }       // 42 가 보장됩니다
}

왜 필요한가

★ 순서가 바뀌는 두 가지 이유

① 컴파일러 최적화
   독립적인 명령을 재배치합니다.
   단일 스레드에서는 결과가 같으므로 합법입니다.

② CPU
   · 저장 버퍼 (쓰기가 지연되어 다른 코어에 늦게 보임)
   · 비순차 실행 (out-of-order)
   · x86 은 비교적 강한 순서를 보장하지만
     ARM · RISC-V 는 훨씬 약합니다 ★

★ 그래서 x86 에서만 테스트하면 버그가 안 보입니다.
  애플 실리콘·ARM 서버에서 처음 터지는 경우가 실제로 있습니다.

★ Relaxed 로 충분한 경우
  · 값 자체만 필요할 때 (카운터 · 통계 · ID 생성)
  · 다른 데이터와의 순서가 상관없을 때

★ Release/Acquire 가 필요한 경우
  · "데이터를 다 썼다" 를 플래그로 알릴 때
  · 락 · 큐 · 참조 카운터의 해제 시점 ★
x86 에서는 Relaxed 와 Acquire 가 같은 코드로 컴파일되는 경우가 많습니다 — 버그가 있어도 드러나지 않습니다. ARM 기기에서도 테스트하고, Miri 와 loom 으로 검증하세요.

이렇게도 쓸 수 있다 — 실전 패턴 🟡 중급

CAS 와 fetch 연산

use std::sync::atomic::{AtomicU64, Ordering};

let a = AtomicU64::new(0);

// 산술
a.fetch_add(1, Ordering::Relaxed);
a.fetch_sub(1, Ordering::Relaxed);
a.fetch_max(5, Ordering::Relaxed);
a.fetch_or(0b1, Ordering::Relaxed);

// 교환
let old = a.swap(10, Ordering::AcqRel);

// CAS — 조건부 교환 ★
match a.compare_exchange(10, 20, Ordering::AcqRel, Ordering::Acquire) {
    Ok(prev) => { /* 10 이었고 20 으로 바꿈 */ }
    Err(actual) => { /* 10 이 아니었음, 실제 값은 actual */ }
}
// weak 버전 — 루프 안에서 (가짜 실패가 가능하지만 더 빠릅니다)
let mut cur = a.load(Ordering::Relaxed);
loop {
    let new = cur * 2;
    match a.compare_exchange_weak(cur, new, Ordering::AcqRel, Ordering::Relaxed) {
        Ok(_) => break,
        Err(v) => cur = v,          // 다른 스레드가 바꿨으므로 재시도
    }
}

// fetch_update — 위 루프를 간단히
a.fetch_update(Ordering::AcqRel, Ordering::Relaxed, |v| Some(v * 2)).ok();

Arc 가 쓰는 패턴 ★

// Arc 의 clone / drop 이 실제로 하는 일 (🔐 o10)

// clone — 카운터만 올리면 됩니다
self.count.fetch_add(1, Ordering::Relaxed);
//   ★ Relaxed 로 충분합니다. 이미 참조를 갖고 있으니
//     다른 데이터와의 순서가 필요 없습니다.

// drop — 여기가 중요합니다
if self.count.fetch_sub(1, Ordering::Release) != 1 { return; }
//   ★ Release: 내가 이 데이터에 한 쓰기가
//     마지막 스레드에게 보이도록 보장

std::sync::atomic::fence(Ordering::Acquire);
//   ★ Acquire 펜스: 다른 스레드의 쓰기를 전부 보고 나서 해제

unsafe { drop_data() };

// ★ 이 패턴이 Release/Acquire 의 교과서적 사용입니다.
//   "마지막 사람이 뒷정리한다" 를 안전하게 구현합니다.

// 펜스 (개별 원자 연산과 별개로 순서를 강제)
use std::sync::atomic::fence;
fence(Ordering::SeqCst);
std::sync::atomic::compiler_fence(Ordering::SeqCst);   // 컴파일러만

이미 만들어진 것을 쓰세요 ★

★ 락 프리 자료구조를 직접 만들면 만나는 문제들
  · ABA 문제 — 값이 A→B→A 로 바뀌면 CAS 가 속습니다
  · 메모리 회수 — 다른 스레드가 아직 보고 있는 노드를 언제 해제하나
      → epoch 기반 · hazard pointer 가 필요합니다
  · 메모리 순서 — 이 섹션의 내용을 전부 정확히
  · 검증이 어렵습니다 — 재현 불가능한 버그

★ 검증된 크레이트 (⚡ e07)
  crossbeam        큐 · 스택 · epoch 기반 회수 ★
  dashmap          동시 해시맵
  arc-swap         Arc 를 원자적으로 교체
  flume            채널
  parking_lot      더 빠른 Mutex/RwLock

★ 직접 구현이 정당한 경우
  · 표준·크레이트에 없는 특수한 자료구조
  · 그것이 제품의 핵심 가치
  · loom 으로 검증할 수 있고, 리뷰할 사람이 있음
  → 그렇지 않다면 Mutex 로 시작하고 측정하세요 (⚡ e07)
    경합이 없으면 Mutex 는 충분히 빠릅니다.

검증 도구 — loom ★

    use loom::sync::atomic::{AtomicUsize, Ordering};
    use loom::sync::Arc;

            assert_eq!(c.load(Ordering::Relaxed), 2);

    }
}

한 단계 더 — 하드웨어와의 관계 🧬 전문가

어떤 명령으로 컴파일되나

x86-64 (강한 메모리 모델 · TSO)
  load(Relaxed/Acquire/SeqCst)   →  mov          (전부 같습니다) ★
  store(Relaxed/Release)          →  mov
  store(SeqCst)                   →  xchg (또는 mov + mfence)
  fetch_add                       →  lock xadd
  compare_exchange                →  lock cmpxchg

AArch64 (약한 메모리 모델)
  load(Relaxed)                   →  ldr
  load(Acquire)                   →  ldar         ★ 다릅니다
  store(Release)                  →  stlr
  fetch_add                       →  ldaddal (또는 ldxr/stxr 루프)

★ 그래서
  · x86 에서는 Relaxed 와 Acquire 의 차이가 코드에 안 나타납니다
    → 버그가 숨습니다
  · ARM 에서는 실제로 다른 명령이 나옵니다
    → 애플 실리콘·Graviton 에서 처음 터집니다 ★

cargo asm --lib my_atomic_fn    (⚡ e03)

SeqCst 를 기본으로 쓸까

★ 찬성
  · 가장 이해하기 쉽습니다 (전역 순서가 있는 것처럼)
  · 틀릴 여지가 적습니다
  · x86 에서는 load 비용이 거의 같습니다

★ 반대
  · store 와 RMW 에서 비용이 큽니다 (특히 ARM)
  · "왜 SeqCst 인지" 생각하지 않게 됩니다
  · 성능이 중요한 핫 패스에서는 손해

★ 실무 권장
  ① 먼저 SeqCst 로 정확하게 만드세요
  ② 프로파일러가 그 지점을 가리키면 (⚡ e01)
  ③ 무엇이 필요한지 분석해 Relaxed/Acquire/Release 로 낮추세요
  ④ loom 으로 검증하세요

  → "성능을 위해 처음부터 Relaxed" 는 대부분 잘못된 최적화입니다.
    카운터처럼 명백한 경우만 예외입니다.

★ 참고 자료
  · Rust Atomics and Locks (Mara Bos) — 이 주제의 결정판 ★
  · std::sync::atomic 문서
  · C++ 메모리 모델 자료 (Rust 가 그것을 따릅니다)
정리 — 카운터는 Relaxed, 데이터 전달은 Release/Acquire 짝, 헷갈리면 SeqCst 입니다. x86 에서는 버그가 안 보이므로 ARM 에서도 테스트하고 loom 으로 검증하세요. 락 프리 자료구조는 직접 만들지 말고 crossbeam 을 쓰는 것이 실무적입니다.
DEEP 07

Miri — unsafe 를 검증하는 도구

unsafe 코드의 버그는 대부분 테스트를 통과합니다 — 그러다 운영에서 터집니다. Miri 는 Rust 코드를 해석기로 실행하며 UB 를 검출합니다. unsafe 를 쓴다면 CI 에 넣지 않을 이유가 없습니다.

    fn null_and_empty() {

Miri 는 “테스트가 지나간 길만” 봅니다 — unsafe 함수마다 정상 · 널 · 길이 0 · 해제 네 가지 테스트를 두면 대부분의 UB 를 잡아냅니다.

한 단계 더 — Stacked Borrows 와 Tree Borrows 🧬 전문가

aliasing 모델이란

Rust 의 참조 규칙(🔐 o02)을 unsafe 코드까지 확장하려면
'정확히 무엇이 허용되는가' 를 정의해야 합니다.
그 후보가 두 가지입니다.

Stacked Borrows (기본)
  · 각 메모리 위치마다 '빌림 스택' 을 유지
  · &mut 를 만들면 그 위에 태그를 push
  · 다른 경로로 접근하면 그 위의 태그를 pop (무효화) ★
  · 엄격합니다 — 실제로는 안전한 코드도 거부하는 경우가 있습니다

Tree Borrows (실험적)
  · 스택 대신 트리로 관리
  · 더 관대하면서도 필요한 최적화는 유지
  · 실제 코드에서 오탐이 적습니다

DEEP 08

안전 추상화 설계 — 불변식을 문서로

이 탭에서 가장 중요한 섹션입니다. unsafe 를 쓰는 목적은 안전한 껍데기를 만들어 남에게 내놓는 것이지, unsafe 를 퍼뜨리는 것이 아닙니다. 사용자가 unsafe 를 한 줄도 쓰지 않게 만드는 것이 목표입니다.

기본 형태 ★

use std::ptr::NonNull;

/// C 디코더를 감싼 안전한 핸들.
///
/// # 불변식
/// - `raw` 는 항상 유효한 디코더를 가리킵니다 (생성자가 널을 거부).
/// - 이 타입이 살아 있는 동안 `raw` 는 해제되지 않습니다.
/// - `raw` 는 이 인스턴스만 소유합니다 (Clone 을 구현하지 않음).
pub struct Decoder {
    raw: NonNull<ffi::Decoder>,
}

impl Decoder {
    pub fn new() -> Result<Self, Error> {
        // SAFETY: decoder_create 는 실패 시 널을 반환합니다.
        let raw = unsafe { ffi::decoder_create() };
        NonNull::new(raw).map(|raw| Decoder { raw }).ok_or(Error::Alloc)
    }

    pub fn decode(&mut self, input: &[u8]) -> Result<Vec<u8>, Error> {
        // SAFETY: 불변식에 의해 raw 는 유효하고, input 은 Rust 슬라이스라
        //         ptr/len 이 정확합니다. &mut self 이므로 동시 호출이 없습니다.
        let n = unsafe {
            ffi::decode(self.raw.as_ptr(), input.as_ptr(), input.len())
        };
        if n < 0 { return Err(Error::from(n)); }
        Ok(self.take_output(n as usize))
    }
}

impl Drop for Decoder {
    fn drop(&mut self) {
        // SAFETY: 불변식에 의해 raw 는 유효하고, 여기서 한 번만 해제됩니다.
        unsafe { ffi::decoder_destroy(self.raw.as_ptr()) }
    }
}

설계 체크리스트 ★

□ 불변식을 문장으로 쓸 수 있는가
    쓸 수 없으면 아직 설계가 안 된 것입니다

□ 생성자가 불변식을 보장하는가
    널 검사 · 범위 검사 · 초기화 (r07 의 Percent 패턴)

□ 모든 공개 메서드가 불변식을 유지하는가
    &mut self 메서드가 중간 상태를 남기지 않는지

□ 필드가 비공개인가
    pub 필드가 있으면 사용자가 불변식을 깰 수 있습니다 ★

□ Drop 이 정확히 한 번 해제하는가
    Clone 을 구현했다면 이중 해제가 되지 않는지

□ Send/Sync 가 올바른가 (⚡ e06)
    자동으로 붙었다면 정말 맞는지 확인하세요

□ 안전한 코드만으로 UB 를 만들 수 없는가 (d01 의 건전성)
    "악의적인 사용자" 를 가정해 보세요

□ 패닉 안전한가
    중간에 패닉해도 불변식이 유지되는가 (🔐 o07)

이렇게도 쓸 수 있다 — 불건전해지기 쉬운 자리 🟡 중급

use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

// ① derive 매크로 — #[derive(MyTrait)]
#[proc_macro_derive(Summary, attributes(summary))]
pub fn derive_summary(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;
    quote! {
        impl Summary for #name {
            fn summary(&self) -> String { format!("{}", stringify!(#name)) }
        }
    }.into()
}

DEEP 10

컴파일 과정 — MIR · 단형화 · LLVM

소스가 실행 파일이 되기까지 컴파일러 안에서 무슨 일이 일어나는지 봅니다. 빌드가 왜 느린지(🛠️ b10), 왜 이터레이터가 빠른지(⚡ e03), 왜 제네릭에 비용이 없는지(r10)가 여기서 설명됩니다.

빌드를 줄이려면 4·5단계를 건드려야 합니다 — 제네릭을 dyn 으로 바꾸거나 크레이트를 쪼개는 것이 효과적입니다.

단계 ★

소스 (.rs)
  │  어휘 분석 · 파싱
  ▼
AST
  │  매크로 확장 (d09)
  ▼
AST (확장됨)
  │  이름 해석 · 모듈 구성 (r09)
  ▼
HIR (High-level IR)
  │  타입 검사 · 트레이트 해석 (🔐 o05·o06)
  ▼
THIR → MIR (Mid-level IR)          ★ Rust 고유의 표현
  │  · 빌림 검사 (borrowck) ← 여기서 소유권 검사 (🔐 o02)
  │  · MIR 최적화 (인라인 · 상수 전파)
  │  · 단형화 (monomorphization) ← 제네릭을 타입별로 복제 (r10)
  ▼

  │  LLVM 최적화 (인라인 · 벡터화 · ⚡ e03·e09)
  ▼

MIR 이 하는 일

MIR 은 '제어 흐름 그래프' 형태의 단순한 표현입니다.

  fn add(a: i32, b: i32) -> i32 { a + b }

  MIR (개념)
    bb0: {
        _3 = CheckedAdd(_1, _2);
        assert(!move (_3.1: bool), "overflow") -> bb1;   ★ 디버그 빌드만
    }
    bb1: { _0 = move (_3.0: i32); return; }

★ MIR 에서 일어나는 중요한 일들
  · 빌림 검사 — 소스가 아니라 MIR 위에서 (🔐 o02)
      그래서 NLL 처럼 '마지막 사용까지' 를 정확히 계산합니다
  · Drop 삽입 — 스코프 끝에 drop 호출을 끼워 넣습니다 (🔐 o01)
      조건부 이동이 있으면 drop flag(숨은 bool)도
  · 오버플로 검사 삽입 (debug_assertions · r02)
  · MIR 최적화 — 간단한 인라인·상수 전파
      -Zmir-opt-level 로 조절

DEEP 11

ABI 안정성 — Rust 는 자기 자신과도 안 맞습니다

C++ 에서 “컴파일러 버전이 다르면 링크가 안 된다”가 문제였습니다. Rust 는 한 발 더 나갑니다 — 공식적으로 ABI 를 보장하지 않습니다. 그래서 경계는 항상 C ABI(🔗 f01)여야 하고, 이 제약이 배포 설계를 결정합니다.

무엇이 보장되지 않나 ★

★ 보장되지 않는 것 (repr(Rust) · 기본값)
  · 구조체 필드 순서와 패딩 (r07 · 🔗 f03)
  · enum 판별자의 크기와 값
  · 함수 호출 규약 (extern "Rust")
  · 이름 맹글링 형식 (🔗 f02)
  · 트레이트 객체 vtable 배치 (🔐 o06)
  · Vec · String 의 내부 표현

★ 언제 달라지나
  · 컴파일러 버전이 다르면
  · 최적화 설정이 다르면 (이론상)
  · 같은 코드라도 재컴파일하면 (이론상)

★ 실제로는
  같은 컴파일러 버전 · 같은 설정이면 잘 맞습니다.
  하지만 '보장' 이 없으므로 의존하면 안 됩니다.

★ 그래서 Rust 라이브러리는
  · 소스로 배포합니다 (crates.io · 🛠️ b02)
  · 매번 함께 컴파일됩니다 (정적 링크)
  · 동적 링크한 Rust .so 를 다른 Rust 앱이 쓰는 방식은 쓰지 않습니다 ★

보장되는 것

// ① #[repr(C)] — C 배치 규칙 (🔗 f03)
#[repr(C)] pub struct Point { pub x: f64, pub y: f64 }

// ② extern "C" — C 호출 규약 (🔗 f02)
#[no_mangle] pub extern "C" fn f(a: i32) -> i32 { a }

// ③ #[repr(transparent)] — 필드 하나와 동일
#[repr(transparent)] pub struct Handle(*mut c_void);

// ④ 원시 포인터 · 정수 · 부동소수점 — 플랫폼 ABI 그대로

// ⑤ 널 포인터 최적화 (r08) — 문서화된 보장 ★
//    Option<&T> · Option<Box<T>> · Option<NonNull<T>>
//    Option<extern "C" fn()> 는 C 의 널 가능 포인터와 동일

// ★ 이 다섯 가지만 경계에서 쓰면 안전합니다.
//   그것이 🔗 C ABI 탭의 규칙이 그렇게 생긴 이유입니다.

// 확인
const _: () = assert!(std::mem::size_of::<Point>() == 16);
const _: () = assert!(
    std::mem::size_of::<Option<&u8>>() == std::mem::size_of::<*const u8>()
);

파이썬·Node 확장에서 ★

★ 다행히 대부분 문제가 안 됩니다
  · 확장 모듈은 하나의 .so/.pyd 로 통째로 빌드됩니다
  · 안에서 쓰는 Rust 크레이트는 전부 정적 링크됩니다
  · 밖으로 나가는 경계는 파이썬 C API / N-API (둘 다 C ABI) ★

★ 그래도 조심할 것
  ① 여러 확장이 같은 Rust 크레이트를 각자 정적 링크
       → 각자 자기 사본을 갖습니다 (전역 상태가 공유되지 않음)
       예: 두 확장이 rayon 을 쓰면 스레드 풀이 두 개 (⚡ e05)
       예: log 크레이트의 전역 로거가 각자 따로 (r09 의 중복 문제)

  ② 심볼 충돌 (🔗 f02)
       두 확장이 같은 C 라이브러리를 정적 링크하면
       심볼이 겹쳐 엉뚱한 버전이 불릴 수 있습니다
       → 버전 스크립트로 심볼을 가리세요

  ③ 파이썬 ABI (🐍 y11)
       abi3 를 쓰면 파이썬 버전 축이 사라집니다

  ④ Node ABI (🟨 j01)
       N-API 덕분에 Node 버전 축이 사라집니다

언제 C ABI 를 쓸까 ★

✅ C ABI 가 필요한 경우
  · 다른 언어에서 부를 때 (🔗 f01)
  · 플러그인 시스템 (동적 로딩)
  · 시스템 라이브러리로 배포
  · 컴파일러 버전이 다른 코드와 링크

❌ 필요 없는 경우
  · 순수 Rust 프로젝트 (cargo 가 전부 함께 빌드)
  · PyO3 · napi-rs 확장 (프레임워크가 경계를 처리)
  · WASM (🟨 j08)

★ 플러그인을 만든다면
  · C ABI 로 인터페이스를 정의하고 (🔗 f01·f09)
  · 버전 확인 함수를 두고 (🔗 f09)
  · abi_stable 크레이트를 검토하세요
      Rust 타입을 안정적으로 주고받게 해 주는 크레이트입니다
      (제약이 많으므로 정말 필요할 때만)

★ 가장 단순한 대안
  플러그인을 '별도 프로세스' 로 두고 IPC (🟨 j01)
  → ABI 문제가 통째로 사라집니다

ABI 불안정이라는 하나의 제약이
이 가이드의 여러 결정을 만들었습니다.

  🔗 f01  경계는 C ABI — 다른 선택지가 없습니다
  🔗 f02  #[no_mangle] extern "C" — 맹글링·규약을 고정
  🔗 f03  #[repr(C)] — 배치를 고정
  🔗 f06  소유권 규약 — Vec 을 그대로 못 넘기므로
  🔗 f09  에러 코드 — Result 를 그대로 못 넘기므로
  🐍 y11  abi3 — 파이썬 쪽 ABI 축을 없애기
  🟨 j01  N-API — Node 쪽 ABI 축을 없애기
  🛠️ b10  바이너리 크기 — 정적 링크의 대가

★ 정리하면
  "Rust 안에서는 마음껏, 경계에서는 C 로"
  이 한 줄이 네이티브 모듈 설계의 핵심 원칙입니다.
정리 — Rust 는 ABI 를 보장하지 않습니다 — 자기 자신과도. 그래서 정적 링크가 기본이고, 경계는 반드시 #[repr(C)] + extern "C" 입니다. 확장 모듈은 통째로 빌드되므로 대개 문제가 없지만, 여러 확장이 같은 크레이트를 각자 링크하면 전역 상태가 공유되지 않는다는 점은 기억하세요.

Rust 를 쓰지 말아야 할 때

마지막 섹션입니다. 안 쓰는 판단도 실력입니다. Rust 가 좋은 언어라는 것과, 지금 이 프로젝트에 맞는다는 것은 다른 이야기입니다. 솔직한 기준을 정리합니다.

쓰지 말아야 할 신호 ★

① 팀에 Rust 를 읽을 수 있는 사람이 나뿐이다 ★
     · 내가 없으면 아무도 못 고칩니다
     · 코드 리뷰가 형식적이 됩니다

     그것들도 이미 C · Rust 입니다

④ 요구사항이 자주 바뀐다
     Rust 는 리팩터링이 안전하지만 '처음 쓰기' 는 느립니다
     프로토타입 단계라면 파이썬이 낫습니다

⑥ 실행 시간이 이미 충분히 빠르다
     "빨라서 나쁠 건 없다" 는 이유가 아닙니다

⑦ 기존 C++ 자산이 크고 잘 관리되고 있다
     경계를 새로 만드는 비용이 이득보다 클 수 있습니다 (🔵 C++ 가이드)

⑧ 컴파일 시간이 개발 흐름의 병목이 될 규모다 (🛠️ b10)

# ADR-012: 로그 파서를 Rust 확장으로 교체

## 배경
일일 배치의 로그 파싱이 전체 42초 중 31초를 차지.
py-spy 프로파일 결과 `parse_line` 이 74% (측정: 2026-08-01, 2.3GB 로그).

## 검토한 대안
| 방안 | 예상 개선 | 비용 | 판단 |
|---|---|---|---|
| 정규식 최적화 | 1.3배 | 낮음 | 시도함, 부족 |
| numpy 벡터화 | 불가 | — | 문자열이라 부적합 |
| Cython | 5~10배 | 중간 | 유지보수자 1명 |
| **Rust + PyO3** | **20~60배** | 중간 | **채택** |

## 결정
`parse_line` 만 Rust 로 이전. 순수 파이썬 폴백 유지.
`LOGPARSE_NATIVE=0` 으로 즉시 되돌릴 수 있음.

## 결과 (2026-08-15 측정)
전체 42초 → 6.1초 (6.9배). p99 지연 편차도 감소.
CI 시간 +4분 (플랫폼 3종 빌드).

- 유지보수자 2명 확보 (○○, □□) ← 조건이었음
