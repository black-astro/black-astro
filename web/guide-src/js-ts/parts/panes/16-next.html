Next.js 가 푸는 문제 — SPA 로는 못 넘는 벽

리액트만으로도 화면은 잘 만들었습니다. 그런데 서비스를 열자마자 검색에 안 잡히고, 첫 화면이 늦고, DB 비밀번호를 브라우저에 둘 수 없다는 세 개의 벽이 나타납니다. Next.js 는 이 셋을 전부 "HTML 을 언제 어디서 만드는가" 를 바꿔서 풉니다.

이 표가 이 탭 전체의 지도입니다 — 남은 섹션은 전부 어느 칸을 쓸지 고르고 그 칸을 관리하는 법입니다.

CSR 만으로 안 되는 세 가지

<!-- Vite + React 로 만든 앱을 '소스 보기' 하면 이게 전부입니다 -->
<div id="root"></div>
<script type="module" src="/assets/index-a3f1.js"></script>
  • ① 검색·공유 — 크롤러와 카카오톡·슬랙 미리보기 봇은 대체로 JS 를 실행하지 않거나 아주 늦게 실행합니다. 위 HTML 에는 제목도 본문도 없으니 빈 페이지로 수집됩니다
  • ② 첫 화면 — JS 번들 내려받기 → 실행 → API 호출 → 응답 → 그제서야 화면. 흰 화면 구간이 네트워크가 느릴수록 길어집니다
  • ③ 데이터 접근 — 브라우저 코드에는 DB 접속 정보나 API 키를 둘 수 없습니다. 그래서 결국 API 서버를 따로 만들게 됩니다 — 화면 저장소 하나, 서버 저장소 하나, 타입은 손으로 맞추는 생활이 시작됩니다
흔한 오해 — "구글은 이제 JS 를 실행하니 괜찮다". 구글은 실행하지만 지연 큐에 넣습니다. 그리고 네이버·다음·빙· 각종 미리보기 봇·AI 크롤러는 대부분 실행하지 않습니다. 커머스·미디어·랜딩 페이지라면 이건 매출 문제입니다.

Next.js 가 바꾸는 지점

// app/posts/[slug]/page.tsx  —  파일 하나가 곧 페이지입니다
// ★ 이 함수는 '서버에서' 실행됩니다. 브라우저 번들에 안 들어갑니다.
import { db } from "@/lib/db";

export default async function PostPage(
  { params }: { params: Promise<{ slug: string }> }   // Next 15+ 는 Promise
) {
  const { slug } = await params;
  const post = await db.post.findUnique({ where: { slug } });  // DB 직접

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.body}</p>
    </article>
  );
}

// 결과: 사용자와 크롤러가 받는 HTML 안에 제목·본문이 '이미' 들어 있습니다.
// API 서버도, fetch 도, 로딩 스피너도 없습니다.
이 코드가 이 탭의 전부를 압축합니다 — 컴포넌트가 서버에서 돈다는 한 가지 사실에서 SEO · 첫 화면 · DB 직접 접근 · 번들 축소가 동시에 해결됩니다. 나머지는 "그럼 클릭은 어떻게 하나(f03)", "매번 DB 를 때리면 느리지 않나(f04)" 같은 뒤따르는 질문들입니다.

용어 정리 — SSG · ISR · SSR · PPR 을 한 표로 🟡 중급

전략HTML 을 만드는 시점쓰는 자리 · 대가
SSG
정적 생성		빌드할 때 한 번 문서 · 블로그 글 · 이용약관. 가장 빠르고 가장 쌉니다. 대가 — 내용을 바꾸려면 다시 빌드·배포해야 합니다
ISR
증분 재생성		빌드 때 + 이후 revalidate 주기마다 상품 목록 · 기사 · 순위표. SSG 의 속도에 갱신을 얹은 것이라 2026년 콘텐츠 페이지의 기본값입니다. 대가 — 최대 N초 낡은 화면을 볼 수 있습니다
SSR
요청 렌더		요청이 올 때마다 사람마다 다른 화면(장바구니 · 대시보드 · 내 주문). 대가 — 서버 비용과 지연이 요청 수에 비례합니다
PPR
부분 사전 렌더		껍데기는 빌드 때, 구멍은 요청 때 "헤더·상품 정보는 모두 같고, 재고·추천만 다르다" 같은 섞인 페이지. SSG 의 첫 바이트에 SSR 의 개인화를 얹습니다
CSR
클라이언트		브라우저에서 (Next 안에서도 씁니다) 차트 · 에디터 · 지도처럼 서버가 그려 봤자 의미 없는 것. Next 에서는 "use client" 컴포넌트가 이 자리입니다
이름에 겁먹지 마세요 — App Router 에서 이것들은 따로 고르는 모드가 아닙니다. 코드에 cookies() 를 쓰면 SSR 이 되고, revalidate 를 적으면 ISR 이 되고, 아무것도 안 쓰면 SSG 가 됩니다. 내가 쓴 코드가 전략을 결정합니다(f06 에서 자세히).

App Router 구조 — 폴더가 곧 URL, 파일 이름이 곧 역할

라우터 설정 파일이 없습니다. app/ 아래의 폴더 이름이 주소가 되고, 파일 이름이 그 자리의 역할을 정합니다. 규약을 여덟 개만 외우면 구조가 전부 읽힙니다.

파일 이름 여덟 개가 곧 프레임워크입니다 — 설정 파일 대신 폴더 구조로 말합니다.

서버 컴포넌트 — "use client" 가 진짜로 바꾸는 것

App Router 에서 모든 컴포넌트는 기본이 서버 컴포넌트입니다. 리액트 탭에서 배운 훅과 이벤트 핸들러가 여기서는 안 됩니다. 왜 안 되는지, 그리고 "use client" 한 줄이 무엇을 뒤집는지가 Next 를 쓸 때 가장 자주 헷갈리는 지점입니다.

"use client" 는 "이 파일부터 아래로 전부 브라우저에도 보낸다"는 선언입니다.

서버 컴포넌트 — 기본값

// app/posts/page.tsx  —  아무 표시도 없으면 '서버'입니다
import { db } from "@/lib/db";
import { marked } from "marked";          // 250KB, 브라우저로 안 감

export default async function Posts() {   // ★ async 가 됩니다
  const posts = await db.post.findMany({ orderBy: { id: "desc" } });

  return (
    <ul>
      {posts.map((p) => (
        <li key={p.id} dangerouslySetInnerHTML={{ __html: marked(p.body) }} />
      ))}
    </ul>
  );
}

// 여기서 되는 것
//   await · DB 접근 · 파일 시스템 · process.env.SECRET · 무거운 라이브러리
// 여기서 안 되는 것
//   useState · useEffect · onClick · window · localStorage
왜 async 가 되나 — 서버 컴포넌트는 한 번 실행하고 끝입니다. 다시 렌더될 일이 없으니 기다렸다가 결과를 반환해도 됩니다. 리액트 탭의 useEffect + fetch + 로딩 상태 세 줄이 await 한 줄로 줄어드는 이유가 이것입니다.

데이터 가져오기와 캐싱 — Next 15 에서 기본값이 뒤집혔습니다

서버 컴포넌트에서는 await fetch() 가 전부입니다. 어려운 건 가져오기가 아니라 언제까지 그 결과를 재사용할 것인가입니다. Next 14 까지는 자동으로 캐시했고, Next 15 부터는 기본이 캐시 안 함으로 바뀌었습니다 — 인터넷 예제의 절반이 옛 기준입니다.

"왜 데이터가 안 바뀌죠?" 의 답은 이 다섯 칸 중 어디에 남아 있나를 순서대로 확인하는 것입니다.

기본 — 서버 컴포넌트에서 그냥 await

Server Actions — API 라우트 없이 서버 함수를 부르기

리액트 탭에서 저장 버튼을 만들려면 API 라우트 · fetch · 로딩 상태 · 에러 상태가 필요했습니다. Server Action 은 서버 함수를 그대로 <form action=> 에 넘겨 그 전부를 없앱니다. 대신 "이 함수는 인터넷에 공개된 엔드포인트" 라는 사실을 잊으면 그대로 보안 사고가 됩니다.

API 라우트 · fetch · 상태 관리 세 가지가 함수 하나로 접힙니다 — 대신 권한 검사가 그 함수의 책임이 됩니다.

검증과 에러 되돌려 주기 — useActionState

// actions.ts
"use server";
import { z } from "zod";

const Schema = z.object({
  title: z.string().min(2, "제목은 2자 이상"),
  body:  z.string().min(10, "본문이 너무 짧습니다"),
});

export type State = { errors?: Record<string, string[]>; message?: string };

export async function createPost(prev: State, formData: FormData): Promise<State> {
  const parsed = Schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success)
    return { errors: parsed.error.flatten().fieldErrors };

  try {
    await db.post.create({ data: parsed.data });
  } catch {
    return { message: "저장에 실패했습니다. 잠시 후 다시 시도해 주세요." };
  }
  revalidatePath("/posts");
  redirect("/posts");                  // ★ try 밖
}
redirect() 와 notFound() 는 내부적으로 예외를 던집니다. try … catch 블록 안에서 부르면 catch 가 삼켜 버려 이동이 일어나지 않고 message 만 돌아옵니다. "저장은 됐는데 페이지가 안 넘어간다"의 원인 1위입니다.

// src/middleware.ts   (프로젝트 루트 또는 src/ 바로 아래)
import { NextResponse, type NextRequest } from "next/server";

const PROTECTED = ["/dashboard", "/settings", "/admin"];

export function middleware(req: NextRequest) {
  const { pathname } = req.nextUrl;
  const token = req.cookies.get("session")?.value;

  if (PROTECTED.some((p) => pathname.startsWith(p)) && !token) {
    const url = req.nextUrl.clone();
    url.pathname = "/login";
    url.searchParams.set("next", pathname);   // 로그인 후 돌아올 곳
    return NextResponse.redirect(url);
  }

  // 헤더를 덧붙여 아래로 흘려보내기
  const res = NextResponse.next();
  res.headers.set("x-request-id", crypto.randomUUID());
  return res;
}

import GitHub from "next-auth/providers/github";
import Credentials from "next-auth/providers/credentials";
import { compare } from "bcryptjs";
import { db } from "@/lib/db";

export const { handlers, auth, signIn, signOut } = NextAuth({
  session: { strategy: "jwt", maxAge: 60 * 60 * 24 * 30 },   // 30일
  pages: { signIn: "/login", error: "/login" },

  providers: [
    GitHub,                                    // 환경변수만 있으면 설정 끝
    Credentials({
      credentials: { email: {}, password: {} },
      authorize: async (c) => {
        const user = await db.user.findUnique({
          where: { email: String(c.email) },

        if (!user) return null;                 // ★ null = 로그인 실패

export const listPublished = unstable_cache(

      .where(eq(posts.published, true))
      .orderBy(desc(posts.createdAt)).limit(50),

  { revalidate: 3600, tags: ["posts"] },

  ["post-by-slug"],
  { revalidate: 3600, tags: ["posts"] },
);

// src/features/posts/actions.ts
"use server";
import { revalidateTag } from "next/cache";
import { redirect } from "next/navigation";
import { auth } from "@/auth";
import { db } from "@/db";
import { posts } from "@/db/schema";
import { eq } from "drizzle-orm";
import { PostInput } from "./schema";

export type State = { errors?: Record<string, string[]>; message?: string };

async function requireAdmin() {
  const session = await auth();                       // ★ 액션마다
  if (session?.user?.role !== "admin") throw new Error("권한이 없습니다");
  return session.user;
}

export async function createPost(prev: State, fd: FormData): Promise<State> {
  const user = await requireAdmin();

  const parsed = PostInput.safeParse(Object.fromEntries(fd));
  if (!parsed.success)
    return { errors: parsed.error.flatten().fieldErrors };

  try {
    await db.insert(posts).values({ ...parsed.data, authorId: user.id });
  } catch (e: any) {
    if (String(e?.message).includes("unique"))
      return { errors: { slug: ["이미 쓰인 주소입니다"] } };
    return { message: "저장에 실패했습니다" };
  }

  revalidateTag("posts");                             // ★ 캐시 무효화
  redirect("/admin");                                 // ★ try 밖
}

export async function deletePost(id: number) {
  await requireAdmin();
  await db.delete(posts).where(eq(posts.id, id));
  revalidateTag("posts");
}

마지막 한마디 — Next.js 를 어렵게 만드는 것은 문법이 아니라 "이 코드가 어디서 도는가" 한 가지입니다. 새 코드를 쓸 때마다 서버인가 브라우저인가, 캐시되나 매번인가 두 질문만 스스로에게 던지면, 나머지는 전부 따라옵니다.
정리 — 블로그(ISR)와 관리자(동적)를 한 앱에 담고, 읽기는 unstable_cache + 태그로 CDN 에서 끝내고, 쓰기는 Server Action 안에서 권한 검사 → 검증 → 저장 → revalidateTag 로 마칩니다. 배포는 output: "standalone" 도커 이미지 하나이고, 확인은 빌드 출력표의 기호와 curl 로 받아 본 HTML 두 가지로 합니다. 이 한 벌을 직접 만들어 보면 App Router 는 더 이상 낯설지 않습니다.
