DEEP 01

V8 이 코드를 실행하는 과정

자바스크립트는 인터프리터 언어일까요? 절반만 맞습니다.

파이프라인

소스 코드
   ↓  파서 (Parser)
추상 구문 트리 (AST)
   ↓  Ignition — 바이트코드 인터프리터
바이트코드 실행 시작  ← ★ 여기서 바로 돌기 시작합니다 (빠른 시작)
   ↓  실행하면서 프로파일링 ("이 함수가 자주 불린다")
Sparkplug (베이스라인 컴파일러) — 간단한 기계어
   ↓  더 자주 불리면
Maglev / TurboFan — ★ 최적화된 기계어
   ↓  가정이 깨지면
Deoptimization — 다시 바이트코드로 ★ 성능 급락
핵심 개념: JIT(Just-In-Time) 컴파일
미리 다 컴파일하지 않고, 실행하면서 뜨거운 코드만 기계어로 만듭니다. 그래서 시작은 빠르고, 반복 실행되는 코드는 C 에 근접한 속도가 나옵니다. 대신 “최적화 가정”이 깨지면 되돌아갑니다(d02). 
# 실제로 확인해 보기
node --trace-opt --trace-deopt app.js       # 최적화·해제 로그
node --print-bytecode app.js                # 바이트코드 출력
node --allow-natives-syntax                 # %OptimizeFunctionOnNextCall 사용 가능

Hermes · 다른 엔진

엔진특징

HermesReact Native 기본. 미리 바이트코드로 컴파일(AOT) → 앱 시작이 빠르고 메모리가 적음
JavaScriptCoreSafari · Bun
SpiderMonkeyFirefox
“이 최적화가 항상 통한다”고 믿지 마세요. V8 은 계속 바뀝니다. 예전에 유명했던 최적화 팁(예: for 가 forEach 보다 항상 빠르다)이 지금은 차이가 없거나 역전된 경우가 많습니다. 항상 측정하세요(d06·d14).

그래도 변하지 않는 원칙

  • 객체 모양을 일정하게 유지 (d02)
  • 같은 자리에는 같은 타입을 넣기
  • 불필요한 객체 생성을 줄이기 (GC 부담)
  • 알고리즘 복잡도가 미시 최적화보다 백 배 중요
  • 이벤트 루프를 막지 않기 (🚀 대규모 k02)
실무에서 이 지식이 쓰이는 순간 — “왜 이 함수만 유독 느리지?”를 프로파일러로 봤는데 deopt 가 반복되고 있을 때. 원인은 대개 d02 에 있습니다.
DEEP 02

히든 클래스 · 최적화 해제

같은 코드가 10배 느려지는 이유입니다.

히든 클래스 (Shape / Map)

// V8 은 객체마다 "내부 구조 정보"를 만들어 재사용합니다
const a = { x: 1, y: 2 };     // 히든클래스 C0 → C1(x) → C2(x,y)
const b = { x: 3, y: 4 };     // ★ 같은 C2 를 공유 → 빠른 접근

const c = { y: 5, x: 6 };     // ❌ 순서가 다르면 다른 히든클래스
const d = { x: 7 };
d.y = 8;                       // ❌ 나중에 추가해도 경로가 달라짐

// ★ 규칙
//   ① 속성을 "생성자에서 전부" 초기화
//   ② 항상 "같은 순서"로
//   ③ delete 를 쓰지 말 것 (사전 모드로 전락 → 크게 느려짐)
느린 패턴
class P {
  constructor(x, y) {
    this.x = x;
    if (y) this.y = y;   // 조건부
  }
}
delete obj.cache;        // 사전 모드
obj[key] = v;            // 동적 키 남발
빠른 패턴
class P {
  constructor(x, y) {
    this.x = x;
    this.y = y ?? null;  // 항상 정의
    this.cache = null;
  }
}
obj.cache = null;        // delete 대신
// 동적 키가 많으면 Map 사용

인라인 캐시 (IC)

function getX(obj) { return obj.x; }

// 모노모픽 — 한 종류만 들어옴 → ★ 가장 빠름
getX({ x: 1, y: 2 });
getX({ x: 3, y: 4 });

// 폴리모픽 — 2~4 종류 → 조금 느림
getX({ x: 1, y: 2 });
getX({ x: 1, z: 3 });

// 메가모픽 — 5종류 이상 → ★ 최적화 포기, 매번 조회
// 실무에서 이렇게 되는 경우:
//   · 여러 API 응답을 같은 함수로 처리
//   · JSON.parse 결과를 그대로 여기저기 넘김
// 배열도 "요소 종류"에 따라 내부 표현이 다릅니다
const nums = [1, 2, 3];        // PACKED_SMI — 가장 빠름
const dbl  = [1.1, 2.2];       // PACKED_DOUBLE
const mix  = [1, "a", {}];     // PACKED_ELEMENTS — 느림
const holey = [1, , 3];        // ★ HOLEY — 구멍이 있으면 크게 느려집니다

// 구멍을 만드는 코드
const arr = new Array(100);          // ❌ 전부 구멍
arr[500] = 1;                        // ❌ 중간이 비어 버림
delete arr[0];                       // ❌

// ✅
const arr2 = new Array(100).fill(0);
const arr3 = Array.from({ length: 100 }, (_, i) => i);
이 최적화를 “먼저” 하지 마세요. 대부분의 성능 문제는 DB·네트워크·알고리즘에 있습니다. 이 절의 내용은 프로파일러가 특정 함수를 지목했을 때 원인을 이해하기 위한 지식입니다. 측정 없는 미시 최적화는 시간 낭비입니다.
DEEP 03

메모리 구조 · GC

자바의 GC 와 개념이 거의 같습니다. 세대별 수집이 핵심입니다.

힙 구조

[Young Generation]  새로 만든 객체 (작음, 수 MB)
  ├ Nursery / From
  └ Intermediate / To
  → Scavenger 로 자주·빠르게 수집 (1~2ms)
  → 대부분의 객체는 여기서 바로 사라집니다 ("대부분 금방 죽는다")

[Old Generation]   두 번 살아남은 객체 (큼)
  → Mark-Sweep-Compact 로 가끔 수집
  → ★ Major GC 는 수십~수백 ms 걸릴 수 있습니다

[그 외]
  Large Object Space  큰 객체
  Code Space          컴파일된 코드
  ※ Buffer 는 힙 밖(외부 메모리) — --max-old-space-size 와 무관
import v8 from "node:v8";
console.log(v8.getHeapStatistics());
// heap_size_limit, used_heap_size, external_memory …

process.memoryUsage();
// rss(전체) · heapTotal · heapUsed · external · arrayBuffers
Node 는 컨테이너 메모리 한도를 자동으로 못 봅니다. --max-old-space-size 를 지정하지 않으면 기본 힙 한도(~4GB, 시스템에 따라 다름)까지 늘리다 커널에 OOMKilled(137) 당합니다 — 로그도 안 남습니다. 컨테이너 메모리의 75% 정도로 지정하세요(🚀 대규모 k14).

GC 를 덜 일하게 하기

// ① 반복문 안에서 객체를 계속 만들지 않기
// ❌ 100만 개의 임시 객체
for (const row of rows) {
  results.push({ ...row, computed: calc(row) });
}
// ✅ 필요한 필드만
for (const row of rows) {
  results.push({ id: row.id, value: calc(row) });
}

// ② 큰 문자열 연결은 배열 + join
// ❌ 반복마다 새 문자열
let s = ""; for (const x of arr) s += x;
// ✅
const parts = []; for (const x of arr) parts.push(x); parts.join("");

// ③ 스트리밍으로 — 전체를 메모리에 올리지 않기 (🟩 Node n05)
// ❌ JSON.parse(hugeString)
// ✅ 스트리밍 파서 또는 청크 처리
# GC 관찰
node --trace-gc app.js
# [12345:0x...] 1234 ms: Scavenge 45.2 (52.1) -> 12.3 (52.1) MB, 1.2 ms
#                        ↑ 종류    ↑ 전    ↑ 후            ↑ 걸린 시간

# Major GC(Mark-Sweep)가 자주·오래 걸린다면
#   → Old Generation 에 객체가 계속 쌓이고 있다는 뜻 (d04 누수 의심)
GC 옵션을 만지는 건 거의 마지막 수단입니다. --max-semi-space-size 같은 값을 조정하기 전에 객체를 덜 만드는 코드로 바꾸는 것이 훨씬 효과가 큽니다. p99 가 튄다면 GC 정지를 의심하되, 먼저 측정하세요.

// 코드에서 직접 스냅샷 (운영 중 조사)
import { writeHeapSnapshot } from "node:v8";

process.on("SIGUSR2", () => {           // ★ 신호로 트리거
  const f = writeHeapSnapshot(`/tmp/heap-${Date.now()}.heapsnapshot`);
  logger.info({ f }, "힙 스냅샷 저장");
});
// kill -SIGUSR2 <pid> 로 원하는 순간에 찍을 수 있습니다
스냅샷을 찍으면 프로세스가 잠깐 멈춥니다. 힙이 1GB 면 수 초간 정지할 수 있습니다. 운영에서는 로드밸런서에서 뺀 인스턴스에서 찍으세요.
지속 모니터링 — heapUsed 를 메트릭으로 내보내고 재시작 후 우상향하는지 보세요. 정상이라면 톱니 모양(늘었다 GC 로 줄었다)이 반복되고, 누수면 바닥선이 계속 올라갑니다(🚀 대규모 k12).
DEEP 05

마이크로태스크 심화

🟨 JS j10 의 확장판. 정확한 우선순위를 정리합니다.

Node 의 전체 우선순위

1. 동기 코드 (현재 스택)
2. process.nextTick 큐        ← ★ Node 전용, 가장 먼저
3. 마이크로태스크 큐 (Promise, queueMicrotask)
4. 매크로태스크 — 이벤트 루프 페이즈 순서로
     timers → pending → poll → check(setImmediate) → close

★ 2·3 은 "각 단계 사이마다" 전부 비워집니다.
console.log("1: 동기");

setTimeout(() => console.log("6: timeout"), 0);
setImmediate(() => console.log("7: immediate"));

process.nextTick(() => console.log("3: nextTick"));
Promise.resolve().then(() => console.log("4: promise"));
queueMicrotask(() => console.log("5: microtask"));

console.log("2: 동기");

// 1 → 2 → 3 → 4 → 5 → 6 → 7
process.nextTick 을 남용하면 이벤트 루프가 굶습니다. nextTick 안에서 또 nextTick 을 부르면 큐가 비지 않아 타이머·I/O 가 영원히 실행되지 않습니다(starvation). 라이브러리 내부용이라고 생각하고, 앱 코드에서는 쓰지 마세요.

실무에서 문제가 되는 경우

// ① 마이크로태스크 무한 루프 — 서버가 응답을 멈춥니다
function loop() { Promise.resolve().then(loop); }
loop();     // ❌ CPU 100%, 다른 요청 전부 대기

// ② 재귀 Promise 로 큐 처리
async function drain() {
  while (queue.length) {
    await process(queue.shift());
    // ★ await 뒤가 마이크로태스크라 I/O 에 양보되지 않을 수 있습니다
  }
}
// ✅ 주기적으로 매크로태스크에 양보
if (++n % 100 === 0) await new Promise(r => setImmediate(r));

// ③ await 이 없는 async 함수는 "동기처럼" 시작합니다
async function f() {
  console.log("A");        // 즉시 실행
  await null;
  console.log("B");        // 마이크로태스크
}
f(); console.log("C");     // A → C → B
// ④ 브라우저 전용 — 렌더링과의 관계
element.style.width = "100px";
requestAnimationFrame(() => { /* 다음 프레임 직전 */ });
// 마이크로태스크는 "렌더링 전에" 전부 실행됩니다
// → 여기서 무거운 일을 하면 프레임이 밀립니다
면접에서 이 주제가 나오면 — “마이크로태스크는 현재 작업이 끝난 직후 전부, 매크로태스크는 한 번에 하나씩”이라는 한 문장으로 시작하고, starvation 위험까지 언급하면 이해도가 확실히 전달됩니다.
DEEP 06

프로파일링

느린 곳은 추측하지 말고 측정하세요. 도구가 답을 알려 줍니다.

CPU 프로파일

# 종료 시 .cpuprofile 생성 → Chrome DevTools 에 드래그

npx clinic flame -- node dist/index.js
npx clinic doctor -- node dist/index.js    # ★ 자동 진단 (이벤트 루프·GC·I/O)

# ④ 0x — 가벼운 플레임 그래프
npx 0x dist/index.js
플레임 그래프 읽는 법
  · 가로 폭 = 그 함수가 CPU 를 쓴 시간 비율 ★
  · 세로 = 호출 스택 깊이
  · "넓고 평평한 것"을 찾으세요 — 그게 병목입니다
  · 내 코드가 아니라 라이브러리가 넓다면
    → 어떻게 호출하고 있는지를 보세요 (대개 호출 횟수 문제)

// 동시 실행 수 제한 — 직접 구현 (🟩 Node n11 의 원리)
class Semaphore {
  private queue: (() => void)[] = [];
  private active = 0;
  constructor(private readonly limit: number) {}

  async acquire(): Promise<() => void> {
    if (this.active >= this.limit) {
      await new Promise<void>(r => this.queue.push(r));
    }
    this.active++;
    return () => {                       // release
      this.active--;
      this.queue.shift()?.();
    };
  }
}

const sem = new Semaphore(5);
const release = await sem.acquire();
try { await heavyTask(); } finally { release(); }
// 같은 요청이 동시에 오면 하나만 실행 (in-flight 중복 제거)
const inFlight = new Map<string, Promise<unknown>>();

function dedupe<T>(key: string, fn: () => Promise<T>): Promise<T> {
  const existing = inFlight.get(key);
  if (existing) return existing as Promise<T>;

  const p = fn().finally(() => inFlight.delete(key));
  inFlight.set(key, p);
  return p;
}

// ★ 캐시 스탬피드를 한 프로세스 안에서 막는 간단한 방법 (🚀 k04)

    return Reflect.set(obj, prop, value, receiver);

function instrument<T extends object>(obj: T, name: string): T {

    get(t, k, r) {
      const v = Reflect.get(t, k, r);
      if (typeof v !== "function") return v;
      return async (...args: unknown[]) => {
        const start = performance.now();

        finally { metrics.timing(`${name}.${String(k)}`, performance.now() - start); }
      };
    },
  });
}

  "user.login": { userId: number; ip: string };

class TypedEmitter<T extends Record<string, unknown>> {
  private handlers = new Map<keyof T, Set<(p: never) => void>>();

  on<K extends keyof T>(event: K, fn: (payload: T[K]) => void) {
    if (!this.handlers.has(event)) this.handlers.set(event, new Set());
    this.handlers.get(event)!.add(fn as never);
    return () => this.handlers.get(event)!.delete(fn as never);
  }

  emit<K extends keyof T>(event: K, payload: T[K]) {
    this.handlers.get(event)?.forEach(fn => (fn as (p: T[K]) => void)(payload));
  }
}

      merge(target[key], source[key]);      // ❌ __proto__ 를 그대로 따라감
    } else target[key] = source[key];
  }
}

// 도메인 — 규칙이 여기 모입니다
export class Order {
  private constructor(
    readonly id: OrderId,
    private status: OrderStatus,
    private readonly items: OrderItem[],
  ) {}

  static create(items: OrderItem[]): Order {
    if (items.length === 0) throw new EmptyOrderError();
    return new Order(OrderId.generate(), "PENDING", items);
  }

  cancel(): void {
    if (this.status === "SHIPPED") throw new CannotCancelError();
    this.status = "CANCELLED";           // ★ 규칙이 엔티티 안에
  }

  get total(): number {
    return this.items.reduce((s, i) => s + i.subtotal, 0);
  }
}
