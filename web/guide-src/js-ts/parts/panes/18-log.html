장애가 났을 때 우리가 가진 것은 로그뿐입니다. 그런데 대부분의 Node 프로젝트는 console.log 로 시작해서 그대로 운영에 나갑니다 — 레벨도, 시각도, 요청 ID 도 없이. 이 탭은 왜 console 로는 부족한지부터 시작해 pino · winston · debug · consola 같은 라이브러리를 무엇을 보고 고르는지, JSON 한 줄에 어떤 필드를 넣는지, 요청 ID 를 어떻게 자동으로 붙이는지, 토큰이 로그로 새지 않게 막는 법, 그리고 그 줄이 stdout 을 떠나 대시보드에 닿기까지를 잇습니다. 끝나면 “로그를 왜 그렇게 찍었냐”는 질문에 설계로 답할 수 있게 됩니다.

LOG 01

console.* 의 진실 — 어디로 나가고, 왜 부족한가

console.log 는 로거가 아닙니다. 파일 서술자에 문자열을 쓰는 편의 함수입니다. 그 사실 하나만 알아도 “왜 운영에서는 다른 걸 쓰나”가 절반은 설명됩니다.

console 은 fd 에 문자열을 쓰는 편의 함수입니다 — 목적지에 따라 동기 쓰기가 됩니다.

console 이 실제로 하는 일

// Node 의 console 은 stdout/stderr 를 감싼 얇은 껍데기입니다.
// 대략 이런 모양이라고 생각하면 정확합니다.
const { format } = require('node:util');

console.log   = (...a) => process.stdout.write(format(...a) + '\n');  // fd 1
console.error = (...a) => process.stderr.write(format(...a) + '\n');  // fd 2
console.warn  = console.error;   // ★ warn 도 stderr 입니다 (자주 놓칩니다)
console.info  = console.log;
console.debug = console.log;     // ★ 이름만 debug — 끄는 스위치가 없습니다

// 객체를 넘기면 util.inspect 가 돕니다 — 순환 참조를 따라가고,
// getter 를 호출하고, 색 코드를 붙이고, 깊이 2까지 펼칩니다.
console.log({ user: { id: 1, roles: ['admin'] } });
// → { user: { id: 1, roles: [ 'admin' ] } }   ← JSON 이 아닙니다. 파싱 못 합니다
가장 자주 물리는 것 — console.warn 과 console.error 는 stderr 로 갑니다. node app.js > app.log 로 리다이렉트하면 경고와 에러만 화면에 남고 파일에는 안 들어갑니다. 둘 다 모으려면 node app.js > app.log 2>&1 이라고 써야 합니다.

쓰기가 동기인가 비동기인가 — 목적지가 정합니다

목적지POSIX(리눅스·맥)Windows
파일동기동기
TTY(터미널)동기비동기
파이프 · 소켓리눅스 동기 / 맥 비동기동기
왜 이게 문제인가 — 동기라는 말은 write(2) 시스템 콜이 끝날 때까지 이벤트 루프가 멈춘다는 뜻입니다. 초당 수천 줄을 찍는 서버에서 console.log 는 조용한 성능 사고가 됩니다. node app.js > app.log 처럼 파일로 돌려 놓으면 더 나빠집니다.
확인해 보기 — node -e "console.log(process.stdout.isTTY)" 를 그냥 실행할 때와 | cat 을 붙였을 때 각각 돌려 보세요. 같은 코드가 환경에 따라 다르게 동작합니다.

한 단계 더 — 브라우저의 console 은 또 다릅니다 🟡 중급

브라우저에서 벌어지는 세 가지

// ① 객체는 "지연 평가"됩니다 — 펼칠 때의 값이 보입니다
const cart = { items: [] };
console.log(cart);          // devtools 에서 펼치면 items 가 3개일 수 있습니다
cart.items.push(1, 2, 3);   // 로그를 찍은 뒤에 바뀐 것인데도

// ② 콘솔에 남긴 객체는 GC 대상에서 빠집니다 (devtools 가 참조를 잡습니다)
//    루프에서 큰 객체를 찍으면 탭 메모리가 계속 오릅니다
for (const row of hugeRows) console.log(row);   // ← 개발 중에도 위험

// ③ 스냅샷이 필요하면 그 자리에서 굳힙니다
console.log(structuredClone(cart));             // 또는 JSON.parse(JSON.stringify(x))
“로그를 찍었는데 값이 이상해요” 의 90%가 ①입니다. 브라우저 콘솔은 찍는 순간의 문자열이 아니라 객체 참조를 보관합니다. Node 는 util.inspect 가 그 자리에서 문자열로 굳히므로 이 문제가 없습니다.

실무에선 이렇게 — console 을 그냥 써도 되는 자리 🔴 실무

console 로 충분한 곳
  • 일회성 스크립트 — 마이그레이션, 데이터 보정
  • CLI 도구의 사용자 출력 — 사람에게 보여 주는 글 (이건 로그가 아니라 UI 입니다)
  • 테스트 중 임시 확인 — 커밋 전에 지우면 됩니다
  • 부팅 직전 한 줄 — 로거를 만들기 전에 죽었을 때의 최후 수단
console 이면 사고가 나는 곳
  • 요청 처리 경로 — 초당 수천 번, 동기 쓰기
  • 레벨을 끄고 싶은 곳 — console.debug 는 끌 방법이 없습니다
  • 검색해야 하는 곳 — 구조가 없으니 grep 밖에 못 씁니다
  • 여러 요청이 섞이는 곳 — 어느 줄이 어느 요청인지 알 수 없습니다
정리하면 기준은 하나입니다 — “이 줄을 나중에 누가 검색할 것인가?” 사람이 지금 눈으로 볼 뿐이면 console 로 충분하고, 나중에 누군가가 조건을 걸어 찾아야 한다면 그건 로거의 일입니다.
정리 — console 은 fd 1·2 에 문자열을 쓰는 편의 함수입니다. 목적지가 파일이면 동기 쓰기라 이벤트 루프가 멈추고, 레벨·시각·구조·요청 ID 가 없어 검색할 수 없는 글이 남습니다. 운영 로그는 처음부터 레코드로 만들어야 합니다.

라이브러리 지형도 — 여덟 개를 한 장에 놓고 고릅니다

LOG 03

pino 실전 — 왜 빠르고, 무엇을 워커에게 넘기나

pino 가 빠른 이유는 마법이 아니라 안 하는 일이 많아서입니다. 메인 스레드에서는 문자열을 만들어 버퍼에 넣는 것까지만 하고, 나머지는 전부 워커 스레드로 넘깁니다.

스윔레인 — 줄을 넘어가는 화살표가 곧 스레드가 바뀌는 지점입니다.

5분 시작 — 이 설정이 대부분의 정답입니다

npm i pino
npm i -D pino-pretty          # ★ 개발 의존성입니다. 운영 번들에 넣지 마세요
// src/logger.ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',

  // ① 레벨을 숫자(30) 대신 문자열("info")로 — 수집기 쿼리가 훨씬 편합니다
  formatters: {
    level: (label) => ({ level: label }),
  },

  // ② 시각을 ISO 문자열로. 기본은 epoch 밀리초(빠르지만 사람이 못 읽습니다)
  timestamp: pino.stdTimeFunctions.isoTime,

  // ③ 모든 줄에 붙는 고정 필드 — 어느 서비스의 어느 배포인지
  base: {
    service: 'checkout-api',
    env: process.env.NODE_ENV,
    version: process.env.GIT_SHA?.slice(0, 7),
  },

  // ④ 지울 것은 처음부터 지웁니다 (lg10 에서 자세히)
  redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'],
});

logger.info({ orderId: 8821, ms: 37 }, 'order paid');
// {"level":"info","time":"2026-08-14T09:12:03.421Z","service":"checkout-api",
//  "env":"production","orderId":8821,"ms":37,"msg":"order paid"}
인자 순서를 외우세요 — logger.info(객체, 메시지) 입니다. 객체가 먼저입니다. logger.info('주문 ' + id) 처럼 문자열을 조립하면 검색할 수 있는 필드가 사라집니다. 메시지는 고정 문구로 두고 값은 객체에 넣으세요.

왜 빠른가 — 안 하는 일 다섯 가지

보통의 로거pino
util.inspect 로 예쁘게안 함 — JSON 문자열을 바로 만듭니다
중간 객체를 여러 번 변환안 함 — 한 번에 문자열로 이어 붙입니다
매 호출마다 레벨 비교레벨별 함수를 미리 만들어 둡니다. 꺼진 레벨은 빈 함수
고정 필드를 매번 직렬화자식 로거의 고정 필드는 한 번만 문자열로 굳혀 둡니다
포맷·전송을 그 자리에서워커 스레드로 넘깁니다(pino.transport)
핵심은 “문자열 조립”입니다 — pino 가 만드는 건 처음부터 끝까지 한 줄짜리 문자열입니다. 중간에 자바스크립트 객체를 만들지 않으니 GC 가 할 일도 없습니다. 이게 벤치마크에서 자릿수 차이를 만드는 부분입니다.
단, 인자는 여전히 평가됩니다 — logger.debug(`무거운 ${expensive()}`) 는 debug 가 꺼져 있어도 expensive() 가 실행됩니다. 템플릿 문자열 대신 logger.debug({ data }, '...') 로 넘기거나 if (logger.isLevelEnabled('debug')) 로 감싸세요.

import pino from 'pino';
const dest = pino.destination({ sync: false });   // 기본값
const logger = pino(dest);

// ★ 종료 직전에 반드시 비웁니다
const flushAndExit = (code: number) => {
  logger.flush();                 // 버퍼를 밀어냄
  dest.on('drain', () => process.exit(code));
};

process.on('SIGTERM', () => flushAndExit(0));     // k8s 가 보내는 신호
process.on('SIGINT',  () => flushAndExit(0));

// 잡히지 않은 예외 — pino.final 이 안전하게 마지막 줄을 씁니다
process.on('uncaughtException', pino.final(logger, (err, finalLogger) => {
  finalLogger.fatal({ err }, 'uncaught exception');
  process.exit(1);
}));
sync: true 는 언제 쓰나 — 짧은 CLI·배치·람다처럼 “끝나면 바로 죽는” 프로그램입니다. 이때는 버퍼가 날아가는 위험이 손해보다 큽니다. 장시간 도는 서버라면 절대 켜지 마세요 — 매 줄이 동기 write 가 됩니다(lg09).

정리 — pino 는 메인 스레드에서 문자열만 만들고 나머지를 워커에 넘겨 빠릅니다. 자식 로거로 문맥을 한 번만 붙이고, 에러는 err 키로 넘기고, pino-pretty 는 개발 파이프로만 씁니다.

winston 실전 — 조립식의 값과 값어치

winston 은 포맷과 목적지를 레고처럼 조립하는 로거입니다. 그 유연함이 장점이자 비용입니다. pino 로 안 되는 것이 있을 때만 꺼내는 편이 좋습니다 — 그 “있을 때”가 언제인지 봅시다.

파이프라인 — 단계 수가 곧 비용. 대신 목적지를 마음대로 붙일 수 있습니다.

기본 설정 — 운영에서 쓸 만한 모양

실무에선 이렇게 — winston 에서 pino 로 옮기기 🔴 실무

인터페이스를 먼저 좁히면 교체가 하루 일이 됩니다

// src/log.ts — 앱 코드는 이 타입만 압니다
export interface AppLogger {
  debug(fields: Record<string, unknown>, msg: string): void;
  info (fields: Record<string, unknown>, msg: string): void;
  warn (fields: Record<string, unknown>, msg: string): void;
  error(fields: Record<string, unknown>, msg: string): void;
  child(fields: Record<string, unknown>): AppLogger;
}

// winston 구현 — 인자 순서를 pino 쪽에 맞춰 뒤집어 줍니다
const wrapWinston = (w: winston.Logger): AppLogger => ({
  debug: (f, m) => w.debug(m, f),
  info:  (f, m) => w.info(m, f),
  warn:  (f, m) => w.warn(m, f),
  error: (f, m) => w.error(m, f),
  child: (f) => wrapWinston(w.child(f)),
});

// pino 는 그대로 이 모양입니다 — 나중에 한 줄만 바꾸면 됩니다
// export const log: AppLogger = pino({ ... });
이전 순서 — ① 위처럼 얇은 인터페이스를 만들어 앱 전체를 거기에 붙입니다 ② 필드 이름을 양쪽이 같게 맞춥니다(level·time·msg) ③ 스테이징에서 둘 다 켜고 대시보드 쿼리가 똑같이 나오는지 확인 ④ 운영에서 스위치. “한 번에 다 바꾸기”가 실패하는 이유는 대개 ②를 건너뛰기 때문입니다.
파일 회전을 앱이 하지 마세요 — winston-daily-rotate-file 은 편하지만 여러 프로세스가 같은 파일을 회전시키면 로그가 섞이거나 사라집니다(PM2 클러스터에서 자주 봅니다). 회전은 logrotate 나 컨테이너 런타임에 맡기는 것이 안전합니다.
정리 — winston 은 목적지를 조립하려고 씁니다. 그 유연함의 값은 단계마다 만드는 객체입니다. 수집기가 있는 환경이라면 pino + stdout 이 거의 항상 더 낫고, winston 은 수집기가 없을 때의 답입니다.

구조적 로깅 — 필드 설계가 나중의 검색을 정합니다

로그를 JSON 으로 찍는 이유는 예뻐서가 아닙니다. 필드가 곧 검색어이기 때문입니다. 문장 안에 값을 숨기면 그 값으로는 영원히 검색이 안 됩니다. 무엇을 필드로 뺄지가 전부입니다.

해부도 — 필드가 곧 검색어입니다. 이름을 정하는 회의가 대시보드를 정합니다.

같은 사건을 두 가지로 찍어 보기

// ✗ 문장에 값을 녹인 로그 — 사람만 읽을 수 있습니다
log.info(`user u_8821 paid order 8821 in 37ms`);
//  · "37ms 이상 걸린 결제"를 찾으려면 정규식을 짜야 합니다
//  · 평균 소요 시간을 못 구합니다 (숫자가 아니니까)
//  · 문구를 바꾸는 순간 기존 대시보드가 전부 깨집니다

// ○ 구조적 로그 — 기계가 읽습니다
log.info({ userId: 'u_8821', orderId: 8821, durationMs: 37 }, 'order paid');
//  · durationMs > 37  같은 조건이 그대로 쿼리가 됩니다
//  · msg 는 고정 문구 — 이걸로 사건 종류를 셉니다
//  · 나중에 필드를 더해도 기존 쿼리가 안 깨집니다

// ★ 한 걸음 더 — 사건에 이름(event)을 붙이면 문구가 바뀌어도 안전합니다
log.info({ event: 'order.paid', orderId: 8821, durationMs: 37 }, 'order paid');
//    msg 는 사람용, event 는 기계용. 대시보드는 event 로 겁니다
규칙 하나만 기억하면 됩니다 — “나중에 이 값으로 필터를 걸 것 같다” 싶으면 필드로 뺍니다. 메시지는 변하지 않는 짧은 문구로 두세요. 문구를 바꾸는 건 공짜가 아닙니다.

발산 매트릭스 — 가운데가 무채색이라 “켤까 말까”인 칸이 눈에 바로 들어옵니다.

// src/edge-logger.ts — 의존성 0. 어디서나 돕니다
type Level = 'debug' | 'info' | 'warn' | 'error';
const ORDER: Record<Level, number> = { debug: 20, info: 30, warn: 40, error: 50 };
const MIN = ORDER[(process.env.LOG_LEVEL as Level) ?? 'info'];

export function elog(level: Level, fields: Record<string, unknown>, msg: string) {
  if (ORDER[level] < MIN) return;                      // 레벨 조기 반환
  const line = JSON.stringify({
    level, time: new Date().toISOString(), msg,
    service: 'web', env: process.env.VERCEL_ENV, ...fields,
  });
  // 엣지에는 stdout 이 없습니다 — 플랫폼이 console 을 수집합니다
  (level === 'error' || level === 'warn' ? console.error : console.log)(line);
}

// middleware.ts
export function middleware(req: NextRequest) {
  const reqId = req.headers.get('x-request-id') ?? crypto.randomUUID();
  elog('info', { reqId, path: req.nextUrl.pathname }, 'edge request');

  const res = NextResponse.next();
  res.headers.set('x-request-id', reqId);   // ★ 아래 런타임으로 ID 를 넘겨줍니다
  return res;
}

// src/request-context.ts
import { AsyncLocalStorage } from 'node:async_hooks';

export interface RequestContext {
  reqId: string;
  userId?: string;
  traceId?: string;
}

const als = new AsyncLocalStorage<RequestContext>();

/** 이 콜백 안에서 일어나는 모든 비동기 작업이 같은 문맥을 봅니다 */
export function runWithContext<T>(ctx: RequestContext, fn: () => T): T {
  return als.run(ctx, fn);
}

/** 어디서든 꺼내 씁니다. 문맥 밖이면 undefined */
export const getContext = () => als.getStore();

/** 처리 도중에 알게 된 값을 덧붙이기 (로그인 후 userId 등) */
export function setContext(patch: Partial<RequestContext>) {
  const cur = als.getStore();
  if (cur) Object.assign(cur, patch);   // ★ 같은 객체를 고칩니다. 새로 run 하지 않습니다
}

// src/http-client.ts — 모든 바깥 호출이 이 함수를 거치게 합니다
import { getContext } from './request-context.js';
import { logger } from './logger.js';

export async function call(url: string, init: RequestInit = {}) {
  const ctx = getContext();
  const t0 = performance.now();

  const headers = new Headers(init.headers);
  if (ctx?.reqId) headers.set('x-request-id', ctx.reqId);   // ★ 그대로 전달
  if (ctx?.traceId) headers.set('traceparent',
    `00-${ctx.traceId}-${ctx.spanId ?? '0'.repeat(16)}-01`); // W3C Trace Context

  try {
    const res = await fetch(url, { ...init, headers });
    logger.info({
      event: 'http.call', url, statusCode: res.status,
      durationMs: Math.round(performance.now() - t0),
    }, 'outbound call');
    return res;
  } catch (err) {
    logger.error({ event: 'http.call_failed', url, err }, 'outbound call failed');
    throw err;
  }
}
이 함수 하나가 세 가지를 동시에 해결합니다 — ① 다음 서비스의 로그가 같은 reqId 를 갖습니다 ② 바깥 호출의 지연이 자동으로 측정됩니다 ③ 실패가 한 곳에서만 기록되어 중복 로그가 사라집니다. 바깥으로 나가는 길을 하나로 모으는 것이 관측의 첫걸음입니다.
OpenTelemetry 를 이미 쓴다면 ID 를 직접 만들지 마세요 — @opentelemetry/api 의 trace.getActiveSpan()?.spanContext() 에서 traceId·spanId 를 꺼내 mixin 에 넣으면 로그와 트레이스가 대시보드에서 한 번에 이어집니다(lg12). OTel 도 내부적으로 같은 비동기 문맥 전파를 씁니다.
정리 — AsyncLocalStorage 로 요청 문맥을 담고 pino 의 mixin 으로 꺼내 붙이면 reqId 를 인자로 나를 필요가 없습니다. 끊기는 곳은 서버 시작 때 만든 객체의 콜백과 워커 스레드뿐입니다.

정리 — 레벨은 리터럴 유니온, 필드는 인터페이스, 사건은 판별 유니온으로 잠급니다. 타입은 컴파일 뒤 사라지므로 런타임 비용이 0이고, 브랜드 타입이면 비밀 값이 로그에 담기는 것 자체를 막을 수 있습니다.

성능 — 동기 쓰기는 이벤트 루프를 멈춥니다

Node 는 스레드가 하나입니다. 로그 한 줄을 디스크에 다 쓸 때까지 기다리는 동안 그 프로세스의 다른 요청도 전부 기다립니다. 로깅 성능 이야기는 결국 “그 기다림을 어디로 치우나”입니다.

워터폴 — 붉은 구간에서 루프가 멈춥니다. 그동안 같은 프로세스의 다른 요청도 기다립니다.

직접 재기 — 이벤트 루프 지연을 숫자로

// bench-log.ts — 같은 줄 10만 개를 세 방식으로 쓰고 루프 지연을 잽니다
import { monitorEventLoopDelay } from 'node:perf_hooks';
import pino from 'pino';

const N = 100_000;
const line = { orderId: 8821, userId: 'u_8821', durationMs: 37 };

async function run(name: string, logger: pino.Logger) {
  const h = monitorEventLoopDelay({ resolution: 5 });   // 5ms 간격으로 루프 지연 표본
  h.enable();
  const t0 = performance.now();
  for (let i = 0; i < N; i++) logger.info(line, 'order paid');
  const wall = performance.now() - t0;
  await new Promise((r) => setTimeout(r, 50));         // 표본이 잡히도록 잠깐
  h.disable();
  console.error(`${name.padEnd(16)} ${wall.toFixed(0).padStart(5)} ms  ` +
    `p99 루프지연 ${(h.percentile(99) / 1e6).toFixed(1)} ms`);
}

// ① 파일에 동기로 — 가장 느리고, 루프가 가장 오래 멈춥니다
await run('file sync', pino(pino.destination({ dest: './a.log', sync: true })));

// ② 파일에 비동기 버퍼로 — sonic-boom 이 4KB 씩 모아서 씁니다
await run('file async', pino(pino.destination({ dest: './b.log', sync: false, minLength: 4096 })));

// ③ 워커 스레드 트랜스포트 — 메인 스레드는 큐에 넣기만 합니다
await run('transport', pino({ transport: { target: 'pino/file', options: { destination: './c.log' } } }));

// $ npx tsx bench-log.ts        ← 세 줄의 숫자를 여러분 환경에서 보세요
숫자를 여기 적지 않는 이유 — SSD 냐 네트워크 디스크냐, 컨테이너냐 맥북이냐에 따라 자릿수가 바뀝니다. 확실한 것은 순서뿐입니다: 동기 파일 쓰기가 가장 느리고 루프를 가장 오래 세우며, 워커 트랜스포트가 메인 스레드 부담이 가장 적습니다. p99 루프지연 이 요청 지연에 그대로 얹히는 숫자입니다.

쓰기 방식 네 가지 — 무엇을 얻고 무엇을 잃나

방식루프 정지죽을 때 유실언제
sync: true (pino 기본)줄마다 — 목적지가 빠르면 짧게없음stdout 으로 나가는 컨테이너 · 짧은 CLI
sync: false + minLength버퍼가 찰 때만버퍼만큼 (flush 로 막음)파일에 직접 쓰는 VM 서버
transport (워커)거의 없음워커 큐만큼포맷·전송 비용이 클 때(원격·pretty)
console.log → 파일 리다이렉트줄마다 · 길게없음운영에서는 쓰지 않습니다(lg01)
pino 의 기본이 “동기”인데 왜 빠른가 — 목적지가 stdout 파이프이면 write 는 커널 버퍼(리눅스 기본 64KB)에 넣고 바로 돌아옵니다. 진짜 디스크까지 기다리는 건 파일이 목적지일 때입니다. 그래서 컨테이너에서는 기본값 그대로가 제일 단순하고 안전하며, 파일에 직접 쓸 때만 sync: false 를 고민합니다.
유실과 지연은 맞바꾸는 것입니다 — 비동기로 돌리면 빠르지만 kill -9 나 OOM 으로 죽을 때 마지막 몇 줄이 사라집니다. 그 마지막 줄이 대개 “왜 죽었는지”입니다. SIGTERM 에서 flush 하는 코드(lg03)가 그래서 필요합니다.

한 단계 더 — 뒤가 막히면 앞이 멈춥니다 (백프레셔) 🟡 중급

stdout 을 읽는 쪽이 느려지면

#   증상: 로그를 많이 찍는 순간 요청 지연이 톱니처럼 뜁니다

docker run --log-driver json-file \

앱 안에서 버퍼를 다루기 — sonic-boom 손잡이

import pino from 'pino';

const dest = pino.destination({
  dest: '/var/log/app/app.log',
  sync: false,
  minLength: 4096,      // 이만큼 모이면 씁니다 (그 전엔 메모리)
  maxLength: 16_777_216, // 16MB 넘게 쌓이면 새 줄을 버리고 'drop' 을 냅니다
  mkdir: true,
});

// ★ 버려지는 순간을 알아야 합니다 — 조용히 사라지면 나중에 아무도 모릅니다
let dropped = 0;
dest.on('drop', () => { dropped++; });
setInterval(() => {
  if (dropped) { logger.warn({ dropped }, 'log lines dropped'); dropped = 0; }
}, 10_000).unref();

const logger = pino(dest);

// 주기적으로 밀어내기 — 트래픽이 적을 때 마지막 줄이 버퍼에 갇히지 않게
setInterval(() => logger.flush(), 1_000).unref();
minLength 는 지연과 맞바꾸는 값입니다 — 4KB 면 초당 수십 줄짜리 서비스에서 마지막 줄이 몇 초 늦게 나타날 수 있습니다. 그래서 flush 타이머를 같이 둡니다. unref() 를 붙여야 이 타이머 때문에 프로세스가 안 끝나는 일이 없습니다.

정리 — 로그 쓰기가 동기이면 그 시간만큼 이벤트 루프가 멈추고 다른 요청도 기다립니다. stdout 파이프는 커널 버퍼 덕에 빠르고, 파일이 목적지일 때 sync: false 나 워커를 고민합니다. 비동기는 유실과 맞바꾸는 것이니 flush 와 drop 을 챙기고, 핫 패스에서는 레벨 확인 · 모아서 찍기 · 큰 객체 금지 셋을 지킵니다.

민감정보 — redact 는 마지막 그물이 아니라 두 번째 그물입니다

로그로 새는 토큰은 수집기 · 백업 · 대시보드 캐시로 자동 복제됩니다. 지우기가 사실상 불가능합니다. 그래서 “새면 지운다”가 아니라 “애초에 안 담기게” 설계하고, redact 는 그 다음 겹으로 둡니다.

동심원 — 바깥 그물일수록 구멍이 큽니다. 안쪽 두 겹이 실제로 일하는 겹입니다.

pino redact — 경로로 가리기

import pino from 'pino';

export const logger = pino({
  redact: {
    paths: [
      // 요청 객체를 통째로 찍을 때 새는 자리 (pino-http 의 req 직렬화기)
      'req.headers.authorization',
      'req.headers.cookie',
      'req.headers["x-api-key"]',        // 하이픈이 든 키는 대괄호로

      // 응답 · 바깥 호출 에러 — axios 에러는 config.headers 를 들고 옵니다
      'err.config.headers.Authorization',
      'err.response.data.token',

      // 우리 도메인 객체
      'user.email', 'user.phone',
      'body.password', 'body.card.number', 'body.card.cvc',

      '*.password',                       // 최상위 아무 키 아래의 password
      'orders[*].customer.email',         // 배열 요소마다
    ],
    censor: '[REDACTED]',                 // 기본값. remove: true 면 키째 지웁니다
  },
});

redact 는 “객체의 키”만 봅니다 — logger.info(`token=${t}`) 처럼 문자열 안에 녹인 값은 못 가립니다. 그리고 경로는 정확한 깊이여야 합니다: '*.password' 는 body.user.password 를 못 잡습니다(두 단계). 키 이름이 바뀌거나 자리가 바뀌면 조용히 새기 시작합니다 — 이게 “두 번째 겹”인 이유입니다.

실제로 새는 경로 여섯 가지와 막는 법

이렇게 찍으면무엇이 새나대신
log.info({ req })Authorization · Cookie 헤더 전부직렬화기로 method·url 만(lg06)
log.error({ err }) (axios · fetch 래퍼)err.config.headers 의 토큰 · 요청 본문redact 경로 + 우리 에러로 감싸기
log.info({ user })이메일 · 전화 · 주소 · 해시 안 된 값{ userId: user.id } 만
log.info({ url: req.originalUrl })?token= · ?code= 쿼리 문자열req.path 만, 쿼리는 키 이름만
log.debug({ sql, params })바인딩 파라미터 안의 개인정보sql 과 params.length
log.info(process.env) · 설정 덤프DB 비밀번호 · API 키 통째로키 이름 목록만, 값은 절대
여섯 줄의 공통점 — 전부 “객체를 통째로 넘긴 것”입니다. 필드로 골라 담는 습관(lg05) 하나가 여섯 사고를 동시에 막습니다. redact 목록이 길어진다면 그건 통째로 넘기는 곳이 많다는 신호입니다.
스택 트레이스도 봅니다 — 에러 메시지에 값을 넣는 습관 (new Error(`login failed for ${email}`))이 있으면 err.message 로 샙니다. 메시지는 고정 문구, 값은 에러 객체의 필드(err.userId)에 두고 그 필드를 redact 합니다.

한 단계 더 — winston 과 “값의 모양”으로 가리기 🟡 중급

winston 은 format 한 단계로

import winston from 'winston';
const { combine, timestamp, json, format } = winston.format;

const SECRET_KEYS = new Set(['password', 'authorization', 'cookie', 'token', 'cvc']);

// 키 이름으로 재귀 마스킹 — 깊이와 상관없이 잡습니다 (대신 느립니다)
function mask(v: unknown, depth = 0): unknown {
  if (depth > 6 || v === null || typeof v !== 'object') return v;
  if (Array.isArray(v)) return v.map((x) => mask(x, depth + 1));
  const out: Record<string, unknown> = {};
  for (const [k, val] of Object.entries(v as Record<string, unknown>)) {
    out[k] = SECRET_KEYS.has(k.toLowerCase()) ? '[REDACTED]' : mask(val, depth + 1);
  }
  return out;
}

const redact = format((info) => mask(info) as winston.Logform.TransformableInfo);

export const logger = winston.createLogger({
  format: combine(redact(), timestamp(), json()),   // ★ redact 가 json() 앞
  transports: [new winston.transports.Console()],
});
키 이름 기반의 값과 값어치 — 깊이를 몰라도 잡는 대신 모든 줄의 모든 키를 순회합니다. pino 의 redact 는 경로를 미리 컴파일해 두므로 훨씬 쌉니다. winston 을 쓴다면 이 비용이 lg04 의 “단계마다 객체” 위에 하나 더 얹히는 셈입니다.

모양으로 잡기 — JWT · 카드번호 · 이메일

// 키 이름을 모를 때의 마지막 수단 — 값의 "모양"으로 찾습니다
const PATTERNS: Array<[RegExp, string]> = [
  [/eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}/g, '[JWT]'],
  [/\b(?:\d[ -]?){13,19}\b/g, '[CARD]'],                       // 카드번호 후보
  [/[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}/gi, '[EMAIL]'],
  [/Bearer\s+[A-Za-z0-9._~+/-]+=*/g, 'Bearer [REDACTED]'],
];

export function scrub(s: string): string {
  let out = s;
  for (const [re, rep] of PATTERNS) out = out.replace(re, rep);
  return out;
}

// pino 에서는 msg 와 문자열 값에만 적용 — 모든 줄에 정규식 넷을 돌리는 비용을 감수하는 것
const logger = pino({
  hooks: {
    logMethod(args, method) {
      const last = args.length - 1;
      if (typeof args[last] === 'string') args[last] = scrub(args[last]);
      return method.apply(this, args);
    },
  },
});
정규식은 어림짐작입니다 — 주문번호 16자리가 [CARD] 로 바뀌고, JWT 가 아닌 base64 도 잡힙니다. 동기 정규식 넷이 모든 줄에 돌면 lg09 의 붉은 구간이 늘어납니다. 이 그물은 수집기 쪽(Vector · Fluent Bit)에 두는 편이 앱에 부담이 없습니다(lg12).

정리 — 로그는 여러 곳으로 자동 복제되어 지우기가 거의 불가능합니다. 첫째 겹은 필드로 골라 담기, 둘째 겹이 redact(경로 기반 · 문자열 안은 못 가림), 셋째가 수집기 정규식, 넷째가 보관·권한입니다. 이미 샜다면 지우기보다 무효화가 먼저입니다.

브라우저 — 로그 파일이 없는 곳에서는 사건을 보냅니다

브라우저에는 stdout 도 파일도 없습니다. 사용자 기기에서 일어난 일은 네트워크로 보내야만 우리에게 옵니다. 그래서 브라우저 로깅은 “모든 줄을 남기기”가 아니라 “사건이 났을 때 그 앞뒤를 함께 보내기”입니다.

자체 수집 — 의존성 없는 얇은 래퍼

// src/blog.ts — 브라우저용 로거. 모아서, 떠날 때, 비콘으로
type Level = 'info' | 'warn' | 'error';
const queue: object[] = [];
const ctx = { sessionId: crypto.randomUUID(), release: __GIT_SHA__ };

export function blog(level: Level, fields: Record<string, unknown>, msg: string) {
  queue.push({ level, time: Date.now(), msg, ...ctx, ...fields });
  if (import.meta.env.DEV) console[level === 'info' ? 'log' : level](msg, fields);
  if (queue.length >= 20 || level === 'error') flush();
}

function flush() {
  if (!queue.length) return;
  const body = JSON.stringify(queue.splice(0));
  // ★ 탭이 닫히는 중에도 살아남는 두 가지 방법
  if (!navigator.sendBeacon('/api/client-logs', new Blob([body], { type: 'application/json' }))) {
    fetch('/api/client-logs', { method: 'POST', body, keepalive: true }).catch(() => {});
  }
}

// 페이지를 떠날 때 남은 것을 밀어냅니다 — unload 는 모바일에서 안 옵니다
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});

// 잡히지 않은 오류 두 종류
window.addEventListener('error', (e) =>
  blog('error', { message: e.message, src: e.filename, line: e.lineno }, 'uncaught'));
window.addEventListener('unhandledrejection', (e) =>
  blog('error', { reason: String(e.reason) }, 'unhandled rejection'));
서버 쪽 /api/client-logs 는 신뢰하면 안 되는 입력입니다 — 누구나 아무 JSON 이나 보낼 수 있습니다. 크기 제한 · 속도 제한 · 스키마 검증을 걸고, 받은 값은 필드로 골라서 서버 로거에 넘기세요. 클라이언트가 보낸 문자열을 그대로 msg 에 넣으면 로그 위조(log injection) 가 됩니다.

OpenTelemetry 브라우저추적은 쓸 만하고, 로그 API 는 아직 자리 잡는 중벤더 중립이 최우선일 때 — 문서를 먼저 확인
서버 로그와 잇는 한 줄 — Sentry SDK 가 tracePropagationTargets 에 맞는 요청에 sentry-trace 헤더를 붙입니다. 서버 미들웨어에서 그 값을 읽어 lg07 의 문맥에 traceId 로 넣으면, 브라우저 오류 화면에서 클릭 한 번으로 서버 로그가 열립니다. 반대로 응답 헤더에 x-request-id 를 돌려주면(lg06) 사용자 오류 화면에 그 값을 보여 줄 수 있습니다.
브라우저에서 절대 하지 말 것 — ① 모든 클릭을 서버로 보내기(그건 로깅이 아니라 추적이고 동의가 필요합니다) ② Sentry.setUser 에 이메일 넣기 ③ 리플레이에서 maskAllText: false ④ 에러 메시지에 사용자 입력값 넣기. lg10 의 규칙이 브라우저에서는 법적 문제가 됩니다.
정리 — 브라우저에는 로그 파일이 없으니 사건이 났을 때 앞뒤를 함께 보냅니다. Sentry 는 예외 + 발자국 + 소스맵이 핵심이고 release 를 맞춰야 스택이 읽힙니다. 자체 수집은 비콘으로 모아서 보내되 서버는 그 입력을 신뢰하지 않습니다. sentry-trace 헤더 하나가 브라우저와 서버 로그를 잇습니다.
LOG 12

stdout 을 떠나서 — 수집기 · 저장소 · OpenTelemetry

앱이 할 일은 stdout 에 JSON 한 줄까지입니다. 그 줄이 대시보드에 닿기까지 서너 단계가 더 있는데, 전부 앱 바깥의 일입니다. 이 경계를 지키면 로거를 바꿔도, 저장소를 바꿔도 서로 모릅니다.

흐름 — 앱은 저장소를 모릅니다. 원통은 우리가 운영하는 것, 구름은 남이 운영하는 것.

컨테이너에서 앱이 지킬 것 — 파일을 만들지 않습니다

12-factor 의 “로그는 이벤트 스트림”이 이 그림입니다 — 앱은 어디에 저장할지 모르고, 모르는 것이 장점입니다. 저장소를 Loki 에서 OpenSearch 로 바꿔도 앱은 재배포하지 않습니다. 반대로 앱이 파일을 직접 쓰기 시작하는 순간, 볼륨 · 권한 · 회전 · 디스크 가득 참이 전부 앱 문제가 됩니다.

에이전트 — Vector 로 JSON 풀어서 Loki 로

# vector.toml — 노드마다 하나 (DaemonSet)
[sources.k8s]
type = "kubernetes_logs"                  # /var/log/containers 를 읽고 pod 메타를 붙입니다

[transforms.parse]
type   = "remap"
inputs = ["k8s"]
source = '''
  parsed, err = parse_json(.message)      # pino 가 쓴 한 줄
  if err == null {
    . = merge(., parsed)                  # level · reqId · msg 가 필드가 됩니다
    del(.message)
  }                                       # JSON 이 아닌 줄(다른 도구)은 그대로 둡니다
  .level = downcase(string!(.level ?? "info"))
'''

[transforms.scrub]                        # lg10 의 셋째 겹 — 앱이 놓친 토큰을 여기서
type   = "remap"
inputs = ["parse"]
source = '''
  .msg = replace(string!(.msg ?? ""), r'eyJ[\w-]+\.[\w-]+\.[\w-]+', "[JWT]")
'''

[sinks.loki]
type     = "loki"
inputs   = ["scrub"]
endpoint = "http://loki:3100"
encoding.codec = "json"
labels.service = "{{ service }}"          # ★ 라벨은 값의 종류가 적은 것만
labels.level   = "{{ level }}"
labels.env     = "{{ env }}"              #   reqId 를 라벨로 두면 Loki 가 죽습니다
Loki 의 라벨은 인덱스 키입니다 — 값의 종류(카디널리티)가 수백을 넘는 필드 (reqId · userId · url)를 라벨로 두면 스트림이 폭발합니다. 그런 값은 본문 JSON 에 두고 | json | reqId="..." 로 거릅니다(lg07). OpenSearch 는 반대로 필드가 전부 색인되니 매핑 폭발을 조심합니다(lg05).

실무에선 이렇게 — 알림과 비용 🔴 실무

로그로 알림 걸기 — 개수가 아니라 비율로

# Grafana 알림 규칙 (Loki · LogQL) — 5분간 error 비율이 2% 를 넘으면
- alert: CheckoutErrorRate
  expr: |
    sum(rate({service="checkout-api"} | json | level="error" [5m]))
      /
    sum(rate({service="checkout-api"} | json | event="http.request" [5m]))
      > 0.02
  for: 10m                       # 10분 지속될 때만 — 순간 튀는 건 무시
  labels: { severity: page }
  annotations:
    summary: "checkout-api error ratio > 2%"
    runbook: "https://wiki/runbooks/checkout-errors"

# 조사할 때 — 어떤 사건이 늘었나 (lg05 의 event 필드가 여기서 빛납니다)
# sum by (event) (count_over_time({service="checkout-api"} | json | level="error" [1h]))
개수 알림은 트래픽이 늘면 울립니다 — 새벽 3시 에러 5건과 점심 에러 5건은 뜻이 다릅니다. 비율로 걸고 for 로 지속 시간을 두세요. 그리고 lg05 의 “400 을 error 로 찍지 않기”가 안 지켜지면 이 알림은 처음부터 소음입니다.

탭을 마치며 — 열두 절을 한 줄로 — console 은 편의 함수(lg01), 서버는 pino(lg02~03), 필드가 검색어(lg05), 요청 ID 는 저장소가 나르고(lg07), 타입으로 잠그고(lg08), 동기 쓰기를 피하고(lg09), 비밀은 애초에 안 담고(lg10), 브라우저는 사건을 보내고(lg11), 앱은 stdout 까지만, 그 뒤는 인프라(lg12). “로그를 왜 그렇게 찍었냐”에 이제 설계로 답할 수 있습니다.
정리 — 앱은 stdout 에 JSON 한 줄까지만 책임집니다. 런타임이 파일로 받고, 에이전트가 풀어서 원통(자체 운영)이나 구름(SaaS)으로 보냅니다. OpenTelemetry 는 우선 traceId 를 로그에 심는 것부터, 알림은 비율로, 비용은 재고 나서 줄입니다.
