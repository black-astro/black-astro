자바스크립트에는 Maven 같은 정해진 표준 레이아웃이 없습니다. 그래서 같은 React 앱도 팀마다 폴더가 다르고, 파일이 삼백 개쯤 되면 "그 코드 어디 있어요?"가 하루에 몇 번씩 나옵니다. 이 탭은 React SPA · Vue · Next.js · Node 백엔드 · Electron · 모노레포 · 라이브러리의 권장 구조를 한 장씩 놓고, 언제 다음 단계로 넘어가는지를 비교합니다. 프레임워크별 깊은 내용은 각 탭으로 링크하고, 여기서는 고르는 기준만 다룹니다. tsconfig paths · package.json exports · 프로젝트 참조 · workspace:* 동작은 Node 24.14 · TypeScript 5.7 · pnpm 10.33 으로 직접 돌려 본 결과를 옮겼습니다.

STR 01

공통 바탕 — package.json · tsconfig · src/ 와 규모별 진화

프레임워크가 달라도 바닥은 같습니다. 루트에는 설정, 코드는 src/, 모듈은 ESM, 별칭은 런타임도 아는 방식으로. tsconfig 옵션 하나하나는 🔷 TS 탭 t14 에 있으니, 여기서는 파일이 어디에 놓이고 왜 그런지, 그리고 커지면 어떻게 바뀌는지만 봅니다.

모든 유형의 출발점

my-app/
├─ package.json        # 이름 · 스크립트 · 의존성 · "type": "module"
├─ pnpm-lock.yaml      # 커밋 필수 · 매니저 하나만 (🧰 도구 o01)
├─ tsconfig.json       # 컴파일 옵션 · paths 별칭
├─ eslint.config.js    # 설정 파일은 루트에 평평하게 (STR 09)
├─ .env.example        # 변수 이름만 커밋 — 값은 .env (커밋 금지)
├─ src/                # ★ 손으로 쓰는 코드는 전부 여기
│  └─ main.ts          # 진입점은 하나
├─ public/             # (웹) 가공 없이 복사되는 정적 파일
├─ dist/               # 빌드 산출물 — .gitignore
└─ node_modules/       # .gitignore

규칙 다섯 가지

규칙이유
코드는 src/ 아래만tsconfig include · 린트 · 커버리지가 "src 만 보면 된다"로 단순해집니다
"type": "module"새 프로젝트는 ESM 이 기본입니다 (🟨 JS 탭 j09)
별칭은 하나, 런타임도 알게tsconfig paths 는 타입 검사기만 압니다 — 아래 실험
tsconfig 는 용도별로Vite 템플릿처럼 앱용 · 설정 파일용(node)을 나누고 references 로 묶습니다
private: true배포하지 않을 앱이 실수로 npm 에 올라가는 것을 막습니다

실험 — paths 만 쓰면 실행이 깨집니다

# tsconfig: "paths": { "@/*": ["./src/*"] }  · module NodeNext
$ tsc -p .              # 오류 없음 — 타입 검사기는 별칭을 압니다
$ cat dist/main.js
import { hello } from "@/utils/greet.js";   # ← 별칭이 그대로 남음
$ node dist/main.js
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/utils'
  imported from ...\dist\main.js

# package.json 의 "imports" 로 바꾸면 (아래 오른쪽)
$ tsc -p .              # 오류 없음 — TS 가 dist/* 를 src/*.ts 로 되짚음
$ node dist/main.js
hi imports
"개발 서버는 되는데 빌드하면 모듈을 못 찾는다"의 대부분이 이것입니다. 번들러(Vite · Next)를 쓰는 프런트는 번들러가 별칭을 풀어 주므로 paths 로 충분하고, tsc 로 컴파일해 node 로 돌리는 서버는 imports 를 씁니다.

서버 · 스크립트의 별칭 — imports

// package.json — Node 가 직접 이해하는 별칭 (# 으로 시작)
{
  "name": "shop-api",
  "private": true,
  "type": "module",
  "imports": { "#app/*": "./dist/*" }
}
// src/main.ts
// import { hello } from "#app/utils/greet.js";

한 저장소 안 tsconfig 여러 개 — references

# packages/core 는 composite: true, apps/api 가 references 로 참조
$ tsc -p apps/api        # core 를 아직 안 빌드했으면
error TS6305: Output file '.../packages/core/dist/index.d.ts'
  has not been built from source file '.../packages/core/src/index.ts'.
$ tsc -b apps/api        # ★ -b 는 참조를 따라 core → api 순서로 빌드
Projects in this build:
    * packages/core/tsconfig.json
    * apps/api/tsconfig.json
references 는 모노레포에서 빌드가 필요한 패키지에 씁니다. 설정 공유와 함께 🚑 프론트 실무 탭 pf12 에 자세히 있습니다.
구조는 처음에 정하는 것이 아니라 신호가 올 때 한 칸씩 옮기는 것입니다.
❌ 첫날부터 3단계
shop/
├─ apps/web/            # 앱은 하나뿐인데
├─ packages/ui/         # 버튼 세 개짜리 패키지
├─ packages/utils/      # 함수 다섯 개
└─ turbo.json           # 캐시할 것이 없는 캐시 설정
✅ 지금 크기에 맞게
shop/
└─ src/
   ├─ features/cart/    # 기능별 폴더 (2단계)
   ├─ features/auth/
   └─ shared/ui/        # 두 번째 앱이 생기면
                        # 그때 packages/ui 로 옮깁니다
정리 — 코드는 src/, 설정은 루트, 별칭은 런타임이 아는 방식으로. 구조는 폴더 → 기능 → 워크스페이스 순서로 신호가 올 때만 넘어갑니다.
STR 02

React SPA — 종류별 vs 기능별 vs Feature-Sliced Design

React 는 폴더에 대해 아무 말도 하지 않습니다. 그래서 세 가지 방식이 실무에 공존합니다. 작을 때는 종류별, 커지면 기능별, 팀이 여럿이면 FSD — 각각 어디서 무너지는지를 알면 고르기 쉽습니다.

① 종류별 (by type)

src/
├─ components/   # 화면 조각 전부 — 60개가 한 폴더에
├─ hooks/        # useCart · useAuth · useDebounce …
├─ pages/        # 라우트 화면
├─ api/          # fetch 함수
├─ store/
└─ utils/        # 잡동사니가 쌓이는 곳

② 기능별 (by feature)

src/
├─ app/                 # 라우터 · 프로바이더 · 전역 CSS
├─ features/
│  ├─ cart/
│  │  ├─ CartPanel.tsx
│  │  ├─ useCart.ts
│  │  ├─ cart.api.ts
│  │  └─ index.ts       # ★ 밖에 보여 줄 것만 export
│  └─ auth/
└─ shared/              # 업무를 모르는 것만 (Button · http · 날짜)

③ Feature-Sliced Design (FSD)

src/
├─ app/         # 초기화 · 라우터 · 프로바이더
├─ pages/       # 라우트 하나 = 슬라이스 하나
├─ widgets/     # 헤더 · 상품 목록처럼 큰 화면 조각
├─ features/    # 사용자 행동 — add-to-cart · login
├─ entities/    # 업무 개념 — user · product · cart
└─ shared/      # ui · api · lib · config (업무 모름)

features/add-to-cart/
├─ ui/          # 세그먼트: ui · model · api · lib · config
├─ model/
└─ index.ts     # 공개 API — 밖에서는 이것만 import
FSD 는 공식 문서(feature-sliced.design)가 있는 방법론이라 "우리 팀 규칙"을 따로 쓰지 않아도 됩니다. 예전 문서의 processes 층은 지금은 쓰지 않는 것으로 정리됐습니다.
FSD 의 전부는 "아래로만, 옆으로는 안 됨" 한 줄입니다 — 옆이 필요하면 위층에서 둘을 조립합니다.
방식맞는 규모무너지는 지점넘어갈 때
종류별화면 10개 안팎 · 1~2명 · 학습 · 프로토타입components/ 에 50개+ · 기능 하나 지우려면 5개 폴더를 뒤짐기능 단위로 PR 이 나기 시작하면
기능별대부분의 사내 SPA · 2~8명shared/ 가 비대해지고 feature 끼리 서로 import팀이 둘 이상 · 경계 다툼이 리뷰마다
FSD여러 팀 · 수명이 긴 제품작은 앱에선 층 고민이 코드보다 오래 걸림— (린터 Steiger 로 강제, STR 10)

기능의 공개 API — index.ts

// src/features/cart/index.ts — 밖에서 써도 되는 것만
export { CartPanel } from "./CartPanel";
export { useCart } from "./useCart";
export type { CartItem } from "./cart.types";
// cart.api.ts · 내부 컴포넌트는 내보내지 않습니다

// 다른 곳에서
import { CartPanel } from "@/features/cart";            // ✅
import { fetchCart } from "@/features/cart/cart.api";   // ❌ 내부 직접 접근

규칙 네 가지

  • 기능 폴더 안은 평평하게 — 파일 10개 넘을 때만 ui/ · model/ 로 나눕니다
  • feature → feature import 금지 — 둘이 필요하면 page(또는 widget)에서 조립
  • shared 는 업무를 모릅니다 — "cart" 라는 단어가 나오면 shared 가 아닙니다
  • index.ts 는 기능마다 하나 — 루트 전체 배럴(src/index.ts)은 순환 참조와 번들 크기 문제를 만듭니다(🟨 j09)
"기능"의 단위가 애매하면 지울 때 같이 지워지는 파일들이 한 기능입니다.
정리 — 작을 때는 종류별로 시작해도 되지만, 화면이 스무 개를 넘으면 features/ 로 묶고 index.ts 로 입구를 하나만 냅니다. 팀이 여럿이면 FSD 의 층 규칙을 빌려 옵니다.
STR 03

Vue 3 앱 — views · composables · stores

Vue 는 공식 템플릿(npm create vue@latest)이 만든 폴더가 사실상 표준입니다. React 의 기능별 원칙이 그대로 적용되고, 이름만 다릅니다. 컴포넌트 나누는 기준과 폴더 예는 💚 Vue 탭 u12, 컴포저블은 u09, Pinia 는 u10 에 있습니다.

기본형 — create-vue 구조 + composables · api

src/
├─ main.ts           # createApp · 플러그인 등록
├─ App.vue
├─ router/index.ts   # 라우트 정의 (views 를 지연 로드)
├─ views/            # 라우트 화면 — URL 하나에 파일 하나
├─ components/       # 재사용 UI · BaseButton.vue 처럼 Base 접두사
├─ composables/      # useXxx() — 상태 있는 로직 재사용
├─ stores/           # Pinia — 스토어 하나 = 업무 개념 하나
├─ api/              # 서버 호출 함수
└─ assets/

커지면 — 기능별 모듈

src/
├─ app/              # main.ts · router · 전역 플러그인
├─ modules/
│  ├─ order/
│  │  ├─ views/OrderListView.vue
│  │  ├─ components/OrderRow.vue
│  │  ├─ composables/useOrderFilter.ts
│  │  ├─ order.store.ts      # defineStore("order", …)
│  │  ├─ order.api.ts
│  │  └─ routes.ts          # 이 기능의 라우트만 → app/router 가 합침
│  └─ member/
└─ shared/           # BaseButton · http · 포맷터
Nuxt 는 components/ · composables/ · pages/ 폴더 이름 자체가 자동 import 와 라우팅 규약입니다(Nuxt 4 는 app/ 아래). 폴더 이름을 바꾸면 기능이 꺼지니 위 구조를 그대로 옮기지 마세요.
Vue 와 React 의 구조 원칙은 같습니다 — 다른 것은 이름과 상태 관리의 공식 여부뿐입니다.
무엇을어디에왜
라우트 화면views/ 또는 modules/*/views/"URL 하나 = 파일 하나"가 보이면 길을 잃지 않습니다
두 화면이 쓰는 로직composables/useXxx.ts믹스인 대신 — 출처가 보이는 재사용
여러 화면이 쓰는 데이터stores/ 또는 modules/*/x.store.ts컴포넌트 트리와 무관하게 공유 (💚 u10)
한 화면에서만 쓰는 조각그 view 옆 (modules/*/components/)전역 components/ 를 비대하게 만들지 않기
정리 — 작을 때는 create-vue 의 views · components · composables · stores 그대로, 커지면 modules/기능/ 안에 같은 이름의 폴더를 한 벌씩 둡니다.
STR 04

Next.js App Router — app/ 은 라우트만, 코드는 밖으로

Next.js 는 이 탭에서 유일하게 폴더 구조가 곧 기능인 프레임워크입니다. 폴더가 URL 이 되고 파일 이름이 역할이 됩니다(▲ Next.js 탭 f02). 그래서 오히려 app/ 에 모든 것을 넣고 싶어지는데, 커지면 라우트 트리와 업무 코드가 뒤엉킵니다. 공식 문서도 두 방식을 모두 허용하니, 규모로 고르면 됩니다.

권장형 — 라우트는 얇게, 기능은 features/

src/
├─ app/                           # ★ 라우트만 — 조립하는 곳
│  ├─ layout.tsx
│  ├─ (marketing)/                # 라우트 그룹 — URL 에 안 나옴
│  │  ├─ layout.tsx               # 마케팅 전용 레이아웃
│  │  └─ pricing/page.tsx         → /pricing
│  ├─ (app)/dashboard/
│  │  ├─ page.tsx                 → /dashboard
│  │  └─ _components/             # 비공개 폴더 — 라우트 아님
│  └─ api/webhooks/route.ts       → POST /api/webhooks
├─ features/
│  └─ posts/
│     ├─ PostList.tsx             # 서버 컴포넌트 (기본)
│     ├─ LikeButton.tsx           # "use client" — 잎에만
│     ├─ queries.ts               # import "server-only"
│     └─ actions.ts               # "use server"
├─ components/ui/                 # 버튼 · 모달 — 업무 모름
└─ lib/                           # db · auth · env — 서버 전용

폴더 규약 세 가지

표기뜻 · 언제
(group)/URL 에 안 나오는 묶음. 레이아웃을 나눌 때(마케팅 vs 로그인 후 화면)
_folder/라우팅에서 빠지는 비공개 폴더. 그 라우트만 쓰는 조각을 옆에 둘 때
src/src/app 을 지원합니다. 설정 파일(next.config.ts · .env)은 루트에 남습니다
// src/app/(app)/posts/page.tsx — 라우트는 조립만
import { PostList } from "@/features/posts/PostList";
import { getPosts } from "@/features/posts/queries";

export default async function PostsPage() {
  const posts = await getPosts();
  return <PostList posts={posts} />;
}
// src/features/posts/queries.ts
import "server-only";       // 클라이언트 컴포넌트가 import 하면 빌드 실패
import { db } from "@/lib/db";
export const getPosts = () => db.post.findMany({ take: 20 });
app/ 은 URL 과 레이아웃의 지도로만 두고, 실제 일은 features/ 가 합니다.
❌ app/ 안에 전부
app/dashboard/page.tsx      # DB 쿼리 · 폼 · 차트가 한 파일
app/dashboard/utils.ts      # 다른 라우트가 여기서 import
app/settings/page.tsx       # → import "../dashboard/utils"
# 라우트를 옮기면 import 가 줄줄이 깨집니다
✅ 경계 파일은 작게
"use client" 는 버튼 · 폼 같은 잎 컴포넌트에만
  → 위에 붙이면 아래 트리 전체가 클라이언트 번들로
서버 전용 모듈 첫 줄에 import "server-only"
  → 비밀이 번들로 새는 사고를 빌드가 막음 (▲ f03)
언제 features/ 로 빼나 — 라우트가 10개 안팎이고 혼자라면 app/ 안에 _components/ 를 두는 공식 "라우트 옆 배치"로 충분합니다. 두 라우트가 같은 조각을 쓰기 시작하면 그때 src/features/ 로 옮기세요.
정리 — app/ 은 page · layout · route 만 두는 라우트 지도, 쿼리 · 액션 · 화면 조각은 src/features/. 클라이언트 경계는 잎으로, 서버 전용은 server-only 로 표시합니다.
STR 05

Node 백엔드 — Express · Hono 는 기능별, NestJS 는 모듈 단위

Express 와 Hono 는 구조를 정해 주지 않고, NestJS 는 모듈이라는 단위를 강제합니다. 결론은 같습니다 — 기능별로 묶고, 기능 안에서 routes → service → repository 로 층을 나눕니다. Express 실무 구조 전체는 🚂 Express 탭 x12, Nest CLI 가 만드는 구조는 🐈 NestJS 탭 s02 에 있습니다.

Express · Hono — 기능 폴더 + 세 층

src/
├─ index.ts               # 런타임 진입점 (serve · listen)
├─ app.ts                 # 미들웨어 · 기능 라우터 연결
├─ modules/
│  ├─ users/

Nest 모듈의 exports 는 기능의 공개 API 입니다. React 기능 폴더의 index.ts(STR 02)와 같은 역할을 프레임워크가 강제해 줍니다.
방식맞는 때
계층별

기능별 + 도메인 층규칙이 service 에 넘칠 때만 (🧬 전문가 탭 d15)
기능별 구조의 숙제는 기능 사이 화살표입니다 — 한 방향으로만 흐르게, 순환은 이벤트로 끊습니다.

}
✅ 값만 주고받음

  // 규칙만 — HTTP · 큐 · CLI 어디서든 호출

정리 — 백엔드도 기능 폴더 + routes · service · repository 세 층이 기본입니다. Nest 는 모듈 exports 로 경계를 강제하고, 기능 사이 순환은 새 모듈이나 이벤트로 끊습니다.
STR 06

Electron · 데스크톱 — main · preload · renderer 는 폴더가 아니라 보안 경계

Electron 의 폴더 셋은 취향이 아니라 서로 다른 런타임과 권한입니다. 그래서 다른 유형과 달리 폴더 사이의 import 가 원천적으로 막혀야 합니다. 프로세스 구조는 🖥️ Electron 탭 e01, 대규모 앱의 프로세스 격리는 ⚙️ 네이티브 탭 v01 에 있으니 여기서는 폴더 배치만 봅니다.

electron-vite 템플릿 + shared/

my-app/
├─ electron.vite.config.ts    # main · preload · renderer 세 번 빌드
├─ electron-builder.yml       # 패키징
├─ resources/                 # 아이콘 등
└─ src/
   ├─ main/                   # Node 권한 — 창 · 파일 · DB · OS
   │  ├─ index.ts
   │  └─ ipc/                 # 채널별 핸들러 · 입력 검증은 여기서
   ├─ preload/index.ts        # contextBridge — 허용 목록만 노출
   ├─ renderer/               # 브라우저 — React/Vue 앱
   │  └─ src/                 #   (STR 02 · 03 구조 그대로)
   └─ shared/                 # ★ 타입 · 채널 이름 상수만
shared/ 는 템플릿에 없는 권장 추가입니다. 여기엔 타입과 상수만 둡니다 — fs 를 쓰는 함수를 넣는 순간 renderer 번들이 깨지거나, 더 나쁘게는 권한이 새어 나갑니다.

세 곳이 같은 계약을 보게

// src/shared/ipc.ts — 이름과 타입만
export type Settings = { theme: "dark" | "light" };
export const IPC = {
  readFile: "file:read",
  saveSettings: "settings:save",
} as const;
export interface Api {
  readFile(path: string): Promise<string>;
  saveSettings(s: Settings): Promise<void>;
}

// src/preload/index.ts — 함수 단위로만 노출
import { contextBridge, ipcRenderer } from "electron";
import { IPC, type Api } from "../shared/ipc";
const api: Api = {
  readFile: (p) => ipcRenderer.invoke(IPC.readFile, p),
  saveSettings: (s) => ipcRenderer.invoke(IPC.saveSettings, s),
};
contextBridge.exposeInMainWorld("api", api);
// ❌ exposeInMainWorld("ipc", ipcRenderer) — 모든 채널이 열립니다
폴더 경계 = 권한 경계입니다 — 바깥 폴더가 안쪽 코드를 import 하는 순간 보안 모델이 무너집니다.
무엇을어디에왜
파일 · DB · 네이티브 모듈main/Node 가 있는 유일한 곳. renderer 에서 sqlite 를 부르면 안 됩니다
IPC 핸들러main/ipc/기능.ts채널이 50개를 넘어도 기능별로 찾을 수 있게. 인자 검증은 여기서
채널 이름 · 타입shared/오타 하나로 조용히 응답이 없는 버그를 타입이 막습니다
화면 · 상태renderer/src/일반 SPA 와 같습니다 — 기능별 폴더
정리 — main · preload · renderer 는 런타임과 권한이 다른 세 앱입니다. 공유는 shared/ 의 타입과 상수만, 나머지는 IPC 로 건넵니다. Tauri 는 같은 구조를 src/ 와 src-tauri/ 로 나눕니다.
STR 07

모노레포 — pnpm workspace + Turborepo, apps/ 와 packages/

두 번째 앱이 생기고 타입을 복사해 붙이기 시작하면 워크스페이스로 넘어갈 때입니다. 도구 소개와 turbo.json 은 🧰 도구 탭 o02, 의존 연결 · tsconfig 공유 · 환경 변수는 🚑 프론트 실무 탭 pf12 에 있으니, 여기서는 폴더를 어떻게 가르고 무엇이 무엇을 참조하는지만 정리합니다.

기본 배치

acme/

STR 08

라이브러리 패키지 — 진입점 하나, exports 가 곧 공개 API

앱은 아무 파일이나 import 해도 되지만, 라이브러리는 사용자가 import 할 수 있는 경로가 곧 약속입니다. 내부 파일 이름을 바꿨다가 누군가의 빌드가 깨지면 그건 메이저 버전 변경입니다. exports 필드가 그 약속을 런타임과 타입 검사 양쪽에서 강제합니다. tsup 설정은 🧰 도구 탭 o03, 하위 경로 노출과 트리셰이킹은 🧬 전문가 탭 d18 에 있습니다.

구조

date-kit/
├─ package.json       # ★ exports · type · files · sideEffects
├─ tsconfig.json
├─ tsup.config.ts     # dist 와 .d.ts 생성 (번들러는 도구 탭 o03)
├─ src/
│  ├─ index.ts        # ★ 공개 API — 여기서 export 한 것만 약속
│  ├─ format.ts
│  ├─ format.test.ts
│  └─ internal/       # exports 에 없으니 밖에서 import 불가
│     └─ parse.ts
├─ dist/              # 배포물 — 커밋 안 함, files 로 포함
└─ README.md · CHANGELOG.md · LICENSE
{
  "name": "@acme/date-kit",
  "version": "1.4.0",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "engines": { "node": ">=20.19" }
}

CJS 전용새로 만들지 않습니다
라이브러리 구조의 핵심은 폴더가 아니라 exports 에 무엇을 적느냐입니다.
배포 전 검사 두 줄 — npx publint 는 exports · files 가 실제 파일과 맞는지, npx attw --pack .(@arethetypeswrong/cli)는 각 해석 방식(node16 · bundler 등)에서 타입이 제대로 잡히는지 봅니다. 이중 배포를 한다면 둘 다 CI 에 넣으세요. 번들러는 tsup(🧰 o03) 외에 후속으로 거론되는 tsdown 도 있으니 시작할 때 저장소 상태를 확인하세요.
정리 — 라이브러리는 src/index.ts 하나가 공개 API, 나머지는 internal/ 에. exports 로 그 약속을 강제하고, 2026 신규 패키지는 ESM 전용이 기본입니다.
STR 09

테스트 · 설정 파일 위치 — 단위는 옆에, E2E 는 따로, 설정은 루트에

테스트와 설정 파일은 "어디 둬도 돌아가니까" 가장 빨리 흩어지는 것들입니다. 규칙은 단순합니다 — 코드와 함께 바뀌는 테스트는 코드 옆, 앱 전체를 보는 테스트는 따로, 도구 설정은 루트에 한 벌. 도구 자체는 🧰 도구 탭 o04(ESLint) · o05(Vitest) · o06(Playwright), 환경 변수 검증은 o09 에 있습니다.

STR 10

한 장 요약 — 유형 · 규모별 권장 구조와 규칙을 도구로 강제하기

규칙을 도구로 강제하기 🟡 중급

① ESLint 기본 규칙만으로 — 기능 내부 접근 금지

// eslint.config.js — 플러그인 없이
export default [
  {
    files: ["src/**/*.{ts,tsx}"],
    rules: {
      "no-restricted-imports": ["error", {
        patterns: [{
          group: ["@/features/*/*"],
          message: "기능은 index.ts 로만 import 하세요 (STR 02)",
        }],
      }],
    },
  },
];
# ESLint Linter API 로 확인한 결과
import { CartPanel } from "@/features/cart";            → OK
import { fetchCart } from "@/features/cart/cart.api";
  → '@/features/cart/cart.api' import is restricted from being
    used by a pattern. 기능은 index.ts 로만 import 하세요
import x from "./cart.api";   (기능 안의 상대 경로)      → OK
층 규칙이 여럿이면 eslint-plugin-boundaries 처럼 "요소 종류 → 허용 대상"을 선언하는 플러그인이 낫습니다. Nx 를 쓴다면 태그 기반 @nx/enforce-module-boundaries 가 같은 일을 합니다.

② dependency-cruiser — 순환 · 방향을 CI 에서

// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    { name: "no-circular", severity: "error",
      from: {}, to: { circular: true } },
    { name: "no-feature-to-feature", severity: "error",
      from: { path: "^src/features/([^/]+)/" },
      to:   { path: "^src/features/([^/]+)/",
              pathNot: "^src/features/$1/" } },
    { name: "packages-dont-know-apps", severity: "error",
      from: { path: "^packages/" }, to: { path: "^apps/" } },
  ],
};
// CI: npx depcruise src --config .dependency-cruiser.cjs

③ FSD — Steiger

# steiger.config.ts 에 FSD 플러그인(@feature-sliced/steiger-plugin)을 등록한 뒤
npx steiger ./src     # FSD 공식 린터 — 층 · 슬라이스 · 공개 API 규칙
dependency-cruiser · Steiger · boundaries 플러그인은 이 PC 에 설치하지 않아 실행하지 않았고, 설정은 각 공식 문서 기준입니다. 이미 위반이 많은 프로젝트는 처음부터 error 로 걸지 말고 새 위반만 막는 것부터 시작하세요.
정리 — 시작은 대부분 기능별 폴더, 앱이 둘이면 워크스페이스. 정한 규칙은 no-restricted-imports 한 줄부터 린트와 CI 에 넣어 사람 대신 도구가 지키게 합니다.
