TOOL 01

패키지 매니저

팀에서 하나만 정해서 쓰세요. 섞이면 lock 파일이 충돌합니다.

비교

도구특징
npm기본 내장. 무난. 팀에 특별한 요구가 없으면 이걸로 충분
pnpm디스크 절약 + 빠름. 하드링크로 중복 제거. 모노레포에 강함 — 신규 프로젝트 추천
yarn (berry)PnP 등 고급 기능. 설정이 까다로워 호불호가 갈립니다
bun매우 빠르지만 런타임까지 바꾸는 선택. 아직 신중히
# pnpm — 요즘 신규 프로젝트의 기본
corepack enable                        # Node 내장 (별도 설치 불필요)
pnpm install
pnpm add express
pnpm add -D typescript
pnpm dlx create-vite                   # npx 에 해당

# ★ 팀에 패키지 매니저를 강제하기
# package.json
{ "packageManager": "pnpm@10.30.2" }   # corepack 이 버전까지 맞춰 줍니다
lock 파일은 반드시 커밋하세요. 없으면 사람마다·서버마다 다른 버전이 설치되어 “내 PC 에서는 되는데” 문제가 생깁니다. package-lock.json·pnpm-lock.yaml 중 쓰는 것 하나만 남기세요.

install vs ci

npm install     # lock 을 "고칠 수 있음" — 개발용
npm ci          # ★ lock 그대로, node_modules 삭제 후 재설치
                #   CI·Docker 는 반드시 이것 (재현성 + 속도)

pnpm install --frozen-lockfile         # pnpm 의 ci 에 해당

npm outdated                           # 오래된 패키지
npm audit                              # ★ 취약점 검사 (CI 에 포함)
npm ls some-pkg                        # 왜 설치됐는지 추적
npm why some-pkg                       # (pnpm) 의존 경로

의존성을 늘리기 전에

  • 내장 기능으로 되는가? — UUID·날짜 포맷·깊은 복사·fetch 는 이제 전부 내장(🟩 Node n14)
  • 마지막 업데이트가 1년 이상 전이면 재검토
  • 이 패키지가 또 몇 개를 끌고 오는지 확인
  • 번들 크기가 중요한 프런트엔드라면 bundlephobia 로 확인
  • postinstall 스크립트가 있는지 — 공급망 공격의 주요 통로(🧬 d13)
버전 고정 전략 — 애플리케이션은 ^ 로 두고 lock 으로 고정, 라이브러리는 범위를 넓게 두어 사용자와 충돌하지 않게 합니다. renovate·dependabot 으로 자동 PR 을 받으면 업데이트를 미루다 한꺼번에 터지는 일을 막습니다.
lock 파일은 빌드 재현성의 전부입니다 — .gitignore 에 넣으면 안 됩니다.
TOOL 02

모노레포

프런트·백엔드·공통 타입을 한 저장소에서 관리합니다.

언제 쓰나

모노레포가 유리
  • 프런트·백엔드가 타입·스키마를 공유
  • 같은 팀이 여러 앱을 함께 배포
  • 공통 UI·유틸 패키지가 있음
  • 한 번에 걸친 변경이 잦음
분리가 나은 경우
  • 팀·배포 주기가 완전히 다름
  • 저장소 권한을 나눠야 함
  • CI 시간이 길어져 감당 안 됨
  • 구성원이 도구에 익숙하지 않음
my-repo/
  pnpm-workspace.yaml
  package.json                 루트 (공통 devDependencies)
  apps/
    api/                       NestJS 서버
    web/                       React 프런트
    mobile/                    React Native
  packages/
    schema/                    ★ Zod 스키마 + 타입 (양쪽에서 import)
    ui/                        공통 컴포넌트
    config/                    eslint · tsconfig 공유 설정
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

Turborepo — 빌드 캐시

pnpm add -Dw turbo
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],        // ★ 의존 패키지를 먼저 빌드
      "outputs": ["dist/**"]
    },
    "test":      { "dependsOn": ["build"] },
    "typecheck": { "dependsOn": ["^build"] },
    "dev":       { "cache": false, "persistent": true }
  }
}
turbo build                    # 바뀐 것만 빌드 (캐시 활용)
turbo build --filter=api       # 특정 앱만
turbo build --filter=...[HEAD^]  # 변경된 것과 그 의존만 ★ CI 에서 유용

# 효과: 안 바뀐 패키지는 캐시에서 즉시 복원 → CI 시간이 크게 줄어듭니다
// apps/api/package.json — 내부 패키지 참조
{
  "dependencies": {
    "@repo/schema": "workspace:*"     // ★ pnpm 워크스페이스 프로토콜
  }
}
// 이렇게 쓰면 프런트·백엔드가 같은 타입을 봅니다
import { CreateUserSchema, type CreateUser } from "@repo/schema";

// 서버: 검증
const dto = CreateUserSchema.parse(req.body);
// 프런트: 폼 검증 + 타입
const form = useForm<CreateUser>({ resolver: zodResolver(CreateUserSchema) });
모노레포의 진짜 가치가 여기 있습니다. API 응답 형태를 바꾸면 프런트엔드가 컴파일 에러로 알려 줍니다. “배포하고 나서야 깨진 걸 아는” 상황이 사라집니다.
모노레포의 기준은 규모가 아니라 같이 바뀌는 코드인가입니다.
TOOL 03

번들러 · 빌드

목적에 따라 도구가 다릅니다. 고민 시간을 줄이는 표부터.

무엇을 언제

도구용도
Vite프런트엔드 앱 — 개발 서버가 매우 빠름. 사실상 표준. Vite 8 부터 Rolldown(Rust)이 기본 번들러, oxlint 가 기본 린터입니다
tsup라이브러리 — ESM+CJS+d.ts 를 한 번에. 설정이 거의 없음
tscNode 서버 — 그냥 컴파일만 하면 될 때
esbuild매우 빠른 저수준 번들러 (위 도구들의 내부 엔진)
Rollup / Rolldown라이브러리 번들의 전통 강자 / Rolldown 이 Vite 8 의 기본이며 Rollup 플러그인과 대체로 호환됩니다
webpack레거시 유지보수 외에는 신규 채택 이유가 줄었습니다

서버는 번들이 필요할까

대부분 필요 없습니다 — tsc 로 컴파일만 하면 충분합니다.

번들이 유용한 경우
  · 서버리스(Lambda) — 콜드 스타트를 줄여야 할 때
  · 단일 파일 배포가 필요할 때
  · 컨테이너 이미지를 극단적으로 줄일 때

주의: 네이티브 모듈(bcrypt·sharp·better-sqlite3)은
      번들에 포함되지 않습니다 → external 로 빼야 합니다
빌드가 느려졌다면 원인은 대개 타입 검사입니다. esbuild·swc 는 타입을 검사하지 않고 지우기만 합니다. tsc --noEmit 을 별도 스크립트로 분리해 빌드와 병렬로 돌리는 것이 실무 표준입니다.
번들 최적화의 핵심은 압축률이 아니라 지금 필요한 것만 먼저 보내는 것입니다.

ESLint · Prettier · Biome

코드 스타일 논쟁을 도구에게 넘기세요.

ESLint 10 — flat config 단독

npm i -D eslint typescript-eslint eslint-config-prettier
// eslint.config.js  (ESLint 10 부터 이 형식만 됩니다 — .eslintrc 는 제거됐습니다)
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import prettier from "eslint-config-prettier";

export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,   // ★ 타입 정보를 쓰는 규칙
  {
    languageOptions: {
      parserOptions: { projectService: true },
    },
    rules: {
      "@typescript-eslint/no-floating-promises": "error",   // ★ await 빠뜨림 방지
      "@typescript-eslint/no-misused-promises": "error",
      "@typescript-eslint/no-unused-vars": ["warn", { argsIgnorePattern: "^_" }],
      "no-console": ["warn", { allow: ["warn", "error"] }],
      eqeqeq: ["error", "always"],
    },
  },
  { ignores: ["dist/**", "coverage/**"] },
  prettier,                                      // ★ 항상 마지막 (포맷 규칙 끄기)
);
no-floating-promises 는 켤 가치가 큽니다. await 를 빠뜨린 Promise 는 조용히 실패하고 Node 프로세스를 죽일 수도 있습니다(🟨 JS j11). 이 규칙 하나가 실제 버그를 여러 개 잡아 줍니다.
ESLint 10(2026-02)에서 .eslintrc.* 와 .eslintignore 가 완전히 제거됐습니다. 9 에서는 ESLINT_USE_FLAT_CONFIG=false 로 옛 형식을 계속 쓸 수 있었지만 10 에는 그 탈출구가 없습니다. npx @eslint/migrate-config .eslintrc.json 으로 변환하고, .eslintignore 에 있던 항목은 config 배열 안의 ignores 로 옮기세요 (위 예시의 { ignores: [...] } 블록).

둘을 동시에 쓰지 마세요. ESLint 의 포맷 규칙과 Prettier 가 충돌하면 저장할 때마다 코드가 왔다 갔다 합니다. eslint-config-prettier 를 맨 마지막에 두어 겹치는 규칙을 꺼야 합니다. 
// .vscode/settings.json — 팀에 공유 (커밋하세요)
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": { "source.fixAll.eslint": "explicit" },
  "typescript.tsdk": "node_modules/typescript/lib"   // ★ 버전 통일
}
규칙은 적게 시작하세요. 경고가 500개 뜨는 설정은 아무도 안 봅니다. recommended 로 시작해 실제로 버그를 잡은 규칙만 추가하는 편이 훨씬 오래갑니다.

oxlint — 세 번째 선택지 2026

Rust 로 쓴 린터입니다. 같은 코드베이스에서 ESLint 대비 50~100배 빠르고, 멀티코어를 전부 씁니다 — 큰 저장소에서 “린트가 몇 분”이던 것이 몇 초가 됩니다. 오랫동안 “빠르지만 타입을 모른다”가 약점이었는데, 2026 년에 tsgo(TypeScript 7 의 Go 컴파일러)를 붙여 타입 인지 린팅이 들어왔고 규칙도 787개까지 늘었습니다. Vite 8 의 기본 린터이고 NestJS 12 의 기본 툴체인에도 들어갑니다. 

npx oxlint                       # 설정 없이 바로 (권장 규칙이 기본)
npx oxlint --fix
npm i -D oxlint

# ESLint 와 같이 쓰기 — 가장 현실적인 조합입니다
#   oxlint 가 잡을 수 있는 규칙은 ESLint 에서 꺼 버립니다
npm i -D eslint-plugin-oxlint
// eslint.config.js — oxlint 와 겹치는 규칙을 자동으로 끕니다
import oxlint from "eslint-plugin-oxlint";

export default [
  // …기존 설정…
  ...oxlint.configs["flat/recommended"],   // ★ 맨 마지막
];
// package.json
//   "lint": "oxlint && eslint ."
//     → 빠른 oxlint 가 먼저 걸러 내고, 남은 것만 ESLint 가 봅니다

// fetch 를 감싸는 얇은 클라이언트 — 실무에서 이 정도면 충분합니다
async function api<T>(path: string, init?: RequestInit & { schema?: ZodType<T> }) {
  const res = await fetch(`${BASE}${path}`, {
    ...init,
    headers: { "Content-Type": "application/json", ...init?.headers },
    signal: init?.signal ?? AbortSignal.timeout(10_000),   // ★ 타임아웃 기본값
  });

  if (!res.ok) {
    const body = await res.text();
    throw new HttpError(res.status, body);
  }
  const json = await res.json();
  return init?.schema ? init.schema.parse(json) : (json as T);   // ★ 검증까지
}

  • 빠른 것부터 — 타입 검사·린트를 먼저, 무거운 E2E 는 나중에
  • PR 에서는 검사만, 배포는 main 병합 후
  • 모노레포라면 바뀐 것만 (turbo --filter=...[HEAD^])
  • 비밀 값은 OIDC 로 — 장기 액세스 키를 저장하지 마세요
  • 배포 후 헬스체크 확인까지 파이프라인에 포함
CI 가 10분을 넘으면 사람들이 기다리지 않습니다. 캐시·병렬화·변경분만 실행으로 5분 이내를 목표로 하세요. 느린 CI 는 결국 “일단 머지하고 나중에 고치자”로 이어집니다.
CI 의 값은 자동화가 아니라 사람이 확인하지 않아도 되는 범위가 늘어나는 데 있습니다.

TOOL 14

테스트 심화 — 예제를 넘어서

o05 가 “어떻게 쓰는가”였다면, 여기는 “내 테스트가 무엇을 못 잡고 있는가” 입니다.

① 속성 기반 테스트 — fast-check

보통의 테스트는 내가 생각해 낸 입력만 검증합니다. 문제는 버그가 사는 곳이 대개 내가 생각 못 한 입력이라는 점입니다 — 빈 문자열, 이모지, 음수 0, 아주 큰 수, 서머타임 경계. 속성 기반 테스트는 입력을 라이브러리가 수백 개 만들어 던집니다.

npm i -D fast-check @fast-check/vitest
import { test } from "@fast-check/vitest";
import fc from "fast-check";
import { expect } from "vitest";

// "예제"가 아니라 "항상 참이어야 하는 성질(property)" 을 적습니다
test.prop([fc.array(fc.integer())])("정렬은 길이를 바꾸지 않는다", (arr) => {
  expect(mySort(arr).length).toBe(arr.length);
});

test.prop([fc.string()])("인코딩 → 디코딩은 원본이다", (s) => {
  expect(decode(encode(s))).toBe(s);          // ★ 왕복(round-trip) 속성
});

test.prop([fc.nat(), fc.integer({ min: 0, max: 100 })])(
  "할인가는 0 이상 원가 이하다",              // 불변식(invariant)
  (price, pct) => {
    const r = applyDiscount(price, pct);
    expect(r).toBeGreaterThanOrEqual(0);
    expect(r).toBeLessThanOrEqual(price);
  });

반례 축소(shrinking) — 이게 진짜 값어치

Property failed after 37 tests
{ seed: 1739..., path: "12:3:0:1" }
Counterexample: [ 0, -0 ]        ← ★ 이 두 줄이 전부

처음 실패한 입력은 [ 8391, -4, 0, 77, -0, 12, ... ] 였습니다.
fast-check 는 실패를 유지하는 선에서 입력을 계속 줄여
"가장 작은 반례" 만 남겨 줍니다.
→ 디버깅 시작점이 "배열 200개" 가 아니라 "[0, -0]" 이 됩니다.
   (Object.is(0, -0) === false 라서 중복 제거가 깨지던 실제 버그)
도입할 가치가 있는 곳 — 파서·직렬화·정렬·금액 계산·날짜 변환·권한 계산처럼 입력 공간이 넓고 규칙이 명확한 순수 함수.
가치가 없는 곳 — CRUD 컨트롤러, 화면 조립 코드. “항상 참인 성질”이 안 떠오르면 그 코드는 대상이 아닙니다.

② 뮤테이션 테스트 — Stryker

커버리지 100% 는 “그 줄이 실행됐다”는 뜻일 뿐, “그 줄이 틀렸을 때 테스트가 빨개진다”는 뜻이 아닙니다. expect 가 하나도 없는 테스트도 커버리지는 올라갑니다. Stryker 는 소스를 일부러 고쳐 놓고(mutant) 테스트가 잡아내는지 셉니다.

npm i -D @stryker-mutator/core @stryker-mutator/vitest-runner
// stryker.config.json
{ "testRunner": "vitest", "coverageAnalysis": "perTest",
  "mutate": ["src/domain/**/*.ts", "!src/**/*.spec.ts"],
  "thresholds": { "high": 80, "low": 60, "break": 50 } }
$ npx stryker run

src/domain/discount.ts
  #12  Survived   if (percent > 100)  →  if (percent >= 100)
  #19  Survived   return price * r    →  return price / r
  #24  Killed     ConditionalExpression

Mutation score: 61.5%   ← ★ 커버리지는 98% 였습니다

"Survived" = 코드를 망가뜨렸는데 테스트가 전부 통과했다
           = 그 분기를 지켜 주는 테스트가 사실상 없다
느립니다 — 전체 코드에 돌리지 마세요. 변이 하나마다 테스트를 다시 돌리므로 시간이 수십 배가 됩니다. 도메인 로직 폴더에만 범위를 좁히고, PR 마다가 아니라 야간 스케줄 CI에서 돌리는 것이 현실적인 운용입니다. 도입할 가치 — 돈·재고·권한 계산 모듈, 그리고 “커버리지는 높은데 왜 자꾸 버그가 나지?”라는 질문이 나왔을 때.

③ 계약 테스트 — Pact

MSA 에서 가장 흔한 사고는 “서버 팀이 필드 이름을 바꿨는데 아무도 몰랐다” 입니다. 각 서비스의 단위 테스트는 전부 초록색이고, E2E 는 느려서 자주 못 돌립니다. 계약 테스트는 소비자가 기대하는 응답 모양을 파일(pact)로 못 박고 제공자 CI 가 그것으로 자신을 검증합니다.

npm i -D @pact-foundation/pact
// ── 소비자(주문 서비스) 쪽 테스트 ──
import { PactV3, MatchersV3 as M } from "@pact-foundation/pact";

const provider = new PactV3({ consumer: "order-api", provider: "user-api" });

it("사용자 조회 계약", async () => {
  provider
    .given("id 1 사용자가 존재한다")
    .uponReceiving("사용자 조회 요청")
    .withRequest({ method: "GET", path: "/users/1" })
    .willRespondWith({
      status: 200,
      body: {                              // ★ 값이 아니라 "모양"을 고정
        id: M.integer(1), email: M.email("a@b.c"),
        grade: M.regex(/GOLD|SILVER/, "GOLD"),
      },
    });

  await provider.executeTest(async (mock) => {
    const u = await new UserClient(mock.url).find(1);
    expect(u.email).toBe("a@b.c");
  });
});
// → pacts/order-api-user-api.json 생성 → Pact Broker 로 발행
# ── 제공자(user-api) CI ──
# 발행된 모든 소비자 계약을 실제 서버에 재생해 봅니다
npx pact-provider-verifier --provider-base-url=http://localhost:3000

# ★ email 을 mail 로 바꾸면 "제공자 CI 가" 빨개집니다.
#   소비자 팀이 운영에서 발견하기 전에.
도입할 가치 — 서비스가 3개 이상이고 팀이 나뉘어 배포 주기가 서로 다를 때. 소비자와 제공자를 같은 저장소에서 같은 사람이 같이 배포한다면 타입 공유(공용 패키지)로 충분합니다. 계약 테스트는 Broker 운영·버전 태깅이라는 관리 비용이 따라옵니다.

④ 스냅샷 테스트의 함정

it("응답 형태", () => {
  expect(render(order)).toMatchSnapshot();   // ⚠️ 편하지만 위험
});
  • 실패해도 무엇이 잘못인지 모릅니다 — “달라졌다”만 알려 줍니다
  • -u 반사 신경 — 깨지면 다들 vitest -u 로 덮어씁니다. 그 순간 버그가 정답으로 승격됩니다 ★
  • 날짜·UUID·정렬 순서가 섞이면 깜빡이는 테스트가 되고, 거대한 .snap 은 아무도 리뷰하지 않습니다
// ✅ 인라인 스냅샷 — 코드 옆에 있어 리뷰가 됩니다
expect(fmt(1234567)).toMatchInlineSnapshot(`"1,234,567원"`);

// ✅ 흔들리는 값은 고정하고, 검증할 필드만 명시
vi.setSystemTime(new Date("2026-08-04"));
expect(res.body).toMatchObject({ status: "PAID", amount: 10_000 });

⑤ 피라미드와 “테스트하지 않을 것”

        ▲  E2E (Playwright)        5%   결제·로그인 등 핵심 흐름만
       ███ 통합 (DB·HTTP 실물)     25%   ★ 가성비가 가장 높은 층
     ███████ 단위 (순수 로직)      70%   빠르고 많아도 부담 없음

느리고 잘 깨지는 층이 위로 갈수록 얇아야 합니다.
E2E 200개짜리 프로젝트는 예외 없이 "아무도 안 보는 빨간 CI" 가 됩니다.
테스트하지 말 것이유
getter · setter · DTO 매핑깨질 수가 없습니다. 리팩터링만 방해합니다
라이브러리 동작 (Zod·Prisma 자체)남의 테스트를 다시 짜는 일입니다
mock 만 검증하는 테스트내가 짠 mock 이 잘 도는지를 볼 뿐입니다 (o05)
화면 픽셀·문구가장 자주 바뀌고 가장 자주 깨집니다
private 메서드공개 동작으로 검증되지 않는다면 설계가 잘못된 것입니다
도입 순서를 지키세요. ① 통합 테스트(Testcontainers)로 진짜 DB부터 → ② 도메인 로직에 fast-check → ③ 커버리지가 의심스러우면 Stryker(야간) → ④ 서비스가 갈라지면 Pact. ①이 없는데 ③부터 하는 팀이 의외로 많습니다 — 측정 도구를 늘려도 안 짠 테스트는 생기지 않습니다.
