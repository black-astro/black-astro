TS 01

왜 TypeScript 인가

“타입을 적는 귀찮음”보다 얻는 것이 훨씬 큰 지점이 분명히 있습니다.

실제로 막아 주는 버그

JS — 런타임에 터짐
function total(order) {
  return order.items
    .reduce((s,i) => s + i.price, 0);
}

total({ item: [] });
// TypeError: Cannot read
// properties of undefined
// ★ 배포 후 사용자가 발견
TS — 저장하는 순간 빨간 줄
type Order = {
  items: { price: number }[];
};
function total(order: Order) {
  return order.items
    .reduce((s,i) => s + i.price, 0);
}

total({ item: [] });
// ★ 'item' 은 'items' 여야 합니다

타입이 주는 실질적 이득

  • 자동완성 — 객체에 뭐가 들었는지 외울 필요가 없습니다. 실무에서 이게 제일 큽니다
  • 안전한 리팩터링 — 필드 이름을 바꾸면 고쳐야 할 곳이 전부 빨갛게 뜹니다
  • 문서 역할 — 함수 시그니처만 봐도 무엇을 넣고 무엇이 나오는지 압니다
  • 팀 확장 — 새 사람이 코드를 읽는 속도가 확연히 다릅니다
TypeScript 가 막아 주지 못하는 것 — API 응답이 타입과 다를 때, JSON.parse 결과, any 로 뚫린 곳, 잘못된 타입 단언(as). 바깥에서 들어오는 값은 런타임에 검증해야 합니다(t11 · 🧰 도구 o07 Zod).

시작하기

npx tsc --init                   # tsconfig.json 생성

# 빌드
npx tsc                          # dist/ 로 컴파일
npx tsc --noEmit                 # ★ 타입 검사만 (CI 에서 쓰는 형태)

# 개발 중 바로 실행
npx tsx src/index.ts             # tsx — 가장 편함

# TypeScript 를 그대로 실행 (Node 24+ 기본 · Node 26 에서 정식)
node src/index.ts
#  · 타입 "지우기"만 합니다 — 타입 검사는 tsc --noEmit 로 따로
#  · enum · 구 데코레이터 · namespace 같은 "코드를 만들어 내는" 문법은 안 됩니다
#    → tsconfig 에 "erasableSyntaxOnly": true 를 켜 두면 미리 막아 줍니다
// tsconfig.json — 처음엔 이 정도면 충분합니다
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,                    // ★ TS 7 부터는 기본값입니다
    "skipLibCheck": true,              // 라이브러리 타입은 검사 생략 (빌드 속도)
    "types": ["node"],                 // ★ TS 7 기본값이 [] — 필요한 것만 적습니다
    "outDir": "dist",
    "rootDir": "src",                  // ★ TS 7 기본값이 "./" — src 라면 꼭 적으세요
    "erasableSyntaxOnly": true,        // node src/index.ts 로 돌릴 거라면
    "paths": { "@/*": ["./src/*"] }    // ★ tsconfig 위치 기준 상대경로 (baseUrl 없음)
  },
  "include": ["src/**/*"]
}
TS 7 로 오면서 tsconfig 가 실제로 바뀝니다. 아래 옵션은 경고가 아니라 하드 에러입니다 — baseUrl · target: "es5" · downlevelIteration · moduleResolution: node/node10/classic/amd · module: amd/umd/systemjs · esModuleInterop: false. baseUrl 을 지우고 paths 를 tsconfig 파일 위치 기준 상대경로로 바꾸는 것이 가장 흔한 작업입니다. 반대로 experimentalDecorators·emitDecoratorMetadata 는 계속 지원됩니다(Nest·TypeORM 에 필수) — 다만 데코레이터는 코드를 만들어 내는 문법이라 erasableSyntaxOnly 와 같이 쓸 수 없습니다.
기존 JS 프로젝트에 점진 도입하기 — allowJs: true 로 켜 두고 파일 하나씩 .ts 로 바꾸세요. 전부 한 번에 바꾸려다 실패하는 팀이 많습니다. 급하면 JSDoc 주석만으로도 타입 검사를 받을 수 있습니다(checkJs).
⚠️ TS 7.0 은 아직 programmatic API 가 없습니다(7.1 예정). 그래서 컴파일러를 라이브러리로 불러 쓰는 도구들 — typescript-eslint · ts-jest · ts-morph, 그리고 Vue·Svelte·Astro 의 템플릿 타입 검사기 — 가 tsgo 위에서 돌지 않습니다. 이 도구를 쓰고 있다면 tsc(6.x)를 병행하거나 7.1 을 기다리세요.
타입스크립트가 막아 주는 것은 버그가 아니라 버그가 배포되는 일입니다.
TS 02

기본 타입 · 추론

타입은 웬만하면 안 적는 게 좋습니다. TS 가 알아서 알아냅니다.

타입 표기

// 기본
let name: string = "김현우";
let age: number = 30;
let ok: boolean = true;
let big: bigint = 10n;
let sym: symbol = Symbol();

// 배열 · 튜플
let tags: string[] = ["a", "b"];
let pair: [number, string] = [1, "a"];      // 길이·순서 고정
let named: [x: number, y: number] = [1, 2];  // 이름 붙은 튜플

// 객체
let user: { id: number; name?: string } = { id: 1 };  // ? = 선택

// 함수
const add = (a: number, b: number): number => a + b;
const log = (msg: string): void => console.log(msg);

// 특수 타입
let anything: any;        // ❌ 타입 검사 포기 — 쓰지 마세요
let safe: unknown;       // ✅ 확인 후에만 쓸 수 있음
function fail(): never { throw new Error(); }   // 절대 반환 안 함
any 는 전염됩니다. 하나가 any 면 그것을 쓰는 코드가 전부 검사에서 빠집니다. 타입을 모를 때는 unknown 을 쓰고 확인 후 사용하세요. noImplicitAny(strict 에 포함)를 켜 두면 실수로 생기는 any 를 막아 줍니다.

추론 — 적지 않아도 되는 곳

// ❌ 불필요한 표기 (오히려 읽기 나쁨)
const name: string = "김현우";
const nums: number[] = [1, 2, 3];
const user: { id: number } = { id: 1 };

// ✅ 추론에 맡기기
const name = "김현우";          // "김현우" (리터럴 타입!)
const nums = [1, 2, 3];         // number[]
const user = { id: 1 };         // { id: number }

// ★ 타입을 꼭 적어야 하는 곳은 두 군데뿐입니다
function f(a: number) { }       // ① 함수 매개변수
let result: string | null = null;  // ② 나중에 채울 변수

const 와 리터럴 타입

let  a = "hello";     // string       (재할당 가능하므로 넓게)
const b = "hello";    // "hello"      ★ 리터럴 타입으로 좁게

// 객체는 안쪽까지 좁혀지지 않습니다
const conf = { mode: "dark" };          // { mode: string }
const conf2 = { mode: "dark" } as const; // { readonly mode: "dark" } ✅

// as const 의 진짜 쓸모 — 상수에서 타입 만들기
const ROLES = ["admin", "user", "guest"] as const;
type Role = typeof ROLES[number];       // "admin" | "user" | "guest"
// ★ 배열만 고치면 타입이 따라옵니다 (t08 에서 더)

// satisfies — 타입 검사는 받되 좁은 추론은 유지 (TS 4.9+)
const config = {
  port: 3000,
  host: "localhost",
} satisfies Record<string, string | number>;
config.port.toFixed();   // ✅ number 로 정확히 추론됨
satisfies 는 “검사는 받고 싶지만 타입은 넓히기 싫을 때” 씁니다. : Type 으로 적으면 타입이 넓어지고, 아무것도 안 적으면 검사를 못 받습니다. 그 사이를 메워 주는 문법입니다.
TS 03

interface vs type

면접 단골 질문이지만, 실무에서는 큰 차이가 없습니다. 기준만 정하면 됩니다.

차이점 정리

항목interface / type
객체 모양둘 다 가능
유니온 · 튜플type 만 가능
선언 병합interface 만 — 같은 이름을 여러 번 선언하면 합쳐짐
확장extends / & (교차 타입)
계산된 타입type 만 — 조건부·매핑드 타입
에러 메시지interface 쪽이 조금 더 읽기 쉽습니다
// interface — 확장 가능하고 선언 병합됨
interface User { id: number; name: string; }
interface User { email: string; }        // ★ 자동으로 합쳐짐
interface Admin extends User { level: number; }

// type — 무엇이든 이름 붙일 수 있음
type ID = string | number;                       // 유니온
type Point = [number, number];                   // 튜플
type Handler = (e: Event) => void;               // 함수
type Admin2 = User & { level: number };          // 교차
type Keys = keyof User;                          // 계산된 타입
실무 기준 — ① 라이브러리를 만든다면 interface(사용자가 확장할 수 있게), ② 앱을 만든다면 type 으로 통일해도 아무 문제 없습니다. 중요한 건 팀에서 하나로 정하는 것입니다. 선언 병합은 서드파티 타입 확장(t13) 외에는 오히려 위험합니다.

실무에서 자주 쓰는 형태

// 인덱스 시그니처 — 키를 미리 모를 때
type Dict = { [key: string]: number };
type Dict2 = Record<string, number>;      // 같은 뜻, 이쪽이 읽기 좋음

// 읽기 전용
type ReadonlyUser = {
  readonly id: number;
  readonly tags: readonly string[];       // 배열도 따로 표시
};

// 함수 속성이 있는 객체 (콜러블)
type Logger = {
  (msg: string): void;                     // 함수로도 호출 가능
  level: "info" | "error";                 // 속성도 있음
};

// 생성자 타입 (DI 컨테이너 만들 때)
type Ctor<T> = new (...args: any[]) => T;

// 중첩 객체
interface ApiResponse<T> {
  data: T;
  meta: { page: number; total: number };
  error?: { code: string; message: string };
}

교차 타입의 함정

type A = { x: string };
type B = { x: number };
type C = A & B;          // x: string & number = never (만들 수 없는 타입)

const c: C = { x: ??? };  // ★ 어떤 값도 넣을 수 없습니다

// interface extends 였다면 에러로 즉시 알려 줍니다
interface D extends A { x: number }   // ❌ 컴파일 에러 ✅ 더 안전
같은 이름의 속성을 다른 타입으로 교차하면 never 가 되어 런타임이 아니라 나중에 이상한 에러로 나타납니다. 확장 관계가 명확한 곳에서는 interface extends 쪽이 사고를 빨리 잡아 줍니다.
성능 차이나 옳고 그름의 문제가 아닙니다 — 확장 가능성만 보면 됩니다.
TS 04

유니온 · 내로잉

TypeScript 를 제대로 쓰기 시작하는 지점입니다. 여기가 핵심입니다.

타입 좁히기 — TS 는 흐름을 읽습니다

function format(value: string | number | Date | null) {
  if (value === null) return "-";
  // 여기부터 value: string | number | Date

  if (typeof value === "string") return value.trim();     // string
  if (typeof value === "number") return value.toFixed(2); // number
  return value.toISOString();                             // Date ★ 자동 추론
}

// 좁히는 방법들
typeof x === "string"          // 원시 타입
x instanceof Date              // 클래스
"name" in obj                  // 속성 존재
Array.isArray(x)               // 배열
x === null / x != null         // null 체크
x.kind === "circle"            // ★ 판별 유니온 (아래)

판별 유니온 — 실무에서 가장 강력한 패턴

type Result<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

function render(res: Result<User>) {
  switch (res.status) {
    case "loading": return "불러오는 중…";
    case "success": return res.data.name;    // ★ data 가 여기서만 존재
    case "error":   return res.error.message;
  }
}

// ★ 이 패턴의 진짜 가치:
//   "로딩 중인데 data 를 읽는" 버그가 컴파일 단계에서 막힙니다.
//   isLoading·data·error 를 각각 boolean 으로 두는 설계보다 훨씬 안전합니다.

빠짐없이 처리했는지 검사하기

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number }
  | { kind: "tri"; b: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "rect":   return s.w * s.h;
    case "tri":    return (s.b * s.h) / 2;
    default: {
      // ★ 모든 경우를 처리했다면 s 는 never 가 됩니다
      const _exhaustive: never = s;
      throw new Error(`알 수 없는 도형: ${JSON.stringify(s)}`);
    }
  }
}

// Shape 에 새 종류를 추가하면 → 이 줄에서 컴파일 에러
// "처리를 빼먹었다"를 배포 전에 알 수 있습니다 ★
이 never 트릭은 실무에서 정말 자주 씁니다. 결제 수단·주문 상태·알림 종류처럼 종류가 늘어나는 것에 걸어 두면, 새 종류를 추가할 때 고쳐야 할 곳을 컴파일러가 전부 찾아 줍니다.

좁히기가 풀리는 순간 — 함정

function f(user: { name?: string }) {
  if (user.name) {
    // 여기서는 string
    doSomething();          // ★ 이 함수가 name 을 지울 수도 있다고 TS 는 봅니다
    user.name.trim();       // ❌ 에러? — 콜백 안이면 좁히기가 풀립니다
  }
}

// ✅ 지역 변수로 뽑아 두면 안전합니다
const name = user.name;
if (name) {
  setTimeout(() => name.trim(), 100);    // ✅ 클로저 안에서도 유지
}
“분명 체크했는데 빨간 줄이 뜬다” 면 대개 이 경우입니다. 콜백·비동기 안에서는 값이 바뀌었을 수 있으므로 TS 가 보수적으로 봅니다. 지역 상수로 복사하는 것이 가장 깔끔한 해법입니다.
유니온을 만나면 먼저 좁히고 그다음 쓴다 — 이 순서가 타입스크립트 코드의 기본 리듬입니다.
TS 05

함수 타입 · 오버로드

함수의 입력과 출력만 잘 타이핑해도 절반은 끝납니다.

기본형

// 매개변수 · 반환
function add(a: number, b: number): number { return a + b; }

// 선택 · 기본값 · 나머지
function greet(name: string, title?: string, ...rest: string[]) { }

// 함수 타입을 이름 붙여 재사용
type Middleware = (req: Request, res: Response, next: () => void) => void;
const auth: Middleware = (req, res, next) => { next(); };
// ★ 이렇게 하면 매개변수 타입을 다시 안 적어도 됩니다 (문맥 추론)

// 콜백 타입
function retry<T>(fn: () => Promise<T>, times: number): Promise<T> { ... }

// this 타입 명시 (첫 매개변수 자리, 실제 인자는 아님)
function handler(this: HTMLButtonElement, e: MouseEvent) {
  this.disabled = true;
}

반환 타입은 적을까 말까

// 내부 함수 — 추론에 맡기세요
const double = (n: number) => n * 2;

// ★ 공개 API·라이브러리는 명시하세요
export function getUser(id: number): Promise<User> { ... }
// 이유: 구현을 고쳤을 때 "반환 타입이 조용히 바뀌는 것"을 막습니다
void 와 undefined 는 다릅니다. () => void 타입 자리에는 무엇을 반환하는 함수든 넣을 수 있습니다 (반환값을 무시하겠다는 뜻). 그래서 arr.forEach(x => list.push(x)) 가 에러가 아닌 것입니다.

오버로드 — 입력에 따라 출력이 다를 때

// 선언 (호출부에서 보이는 시그니처)
function parse(input: string): object;
function parse(input: string, raw: true): string;
// 구현 (밖에서는 안 보임)
function parse(input: string, raw?: boolean): object | string {
  return raw ? input : JSON.parse(input);
}

parse("{}");            // object
parse("{}", true);      // string  ★ 정확히 좁혀짐
// ★ 대부분은 오버로드보다 제네릭·유니온이 낫습니다
// 오버로드 (장황함)
function first(a: string[]): string;
function first(a: number[]): number;

// 제네릭 (한 줄)
function first<T>(a: T[]): T | undefined { return a[0]; }

// 조건부 반환이 필요하면 (t09)
function get<T extends boolean>(raw: T): T extends true ? string : object;

실무 패턴 — 함수 시그니처로 API 설계하기

// 옵션 객체 — 인자가 3개를 넘으면 이렇게 바꾸세요
type FetchOptions = {
  method?: "GET" | "POST" | "PUT" | "DELETE";
  headers?: Record<string, string>;
  timeout?: number;
  retry?: number;
};
async function request<T>(url: string, opts: FetchOptions = {}): Promise<T> { ... }

// 호출부가 읽기 좋아집니다

불리언 매개변수를 늘어놓지 마세요. save(data, true, false, true) 는 읽을 수 없는 코드입니다. 옵션 객체로 바꾸면 이름이 곧 설명이 되고, 나중에 옵션을 추가하기도 쉽습니다.
TS 06

제네릭

“쓸 때 정해지는 타입”. 같은 코드를 타입만 바꿔 재사용하기 위한 문법입니다.

왜 필요한가

// ❌ any — 타입 정보가 사라집니다
function firstAny(arr: any[]): any { return arr[0]; }
const a = firstAny(["x"]);      // any — 자동완성 없음, 오타 못 잡음

// ✅ 제네릭 — 넣은 타입이 그대로 나옵니다
function first<T>(arr: T[]): T | undefined { return arr[0]; }
const b = first(["x"]);         // string ★
const c = first([1, 2]);        // number

// 여러 개도 가능
function pair<K, V>(k: K, v: V): [K, V] { return [k, v]; }

// 제약 — "이런 성질은 있어야 한다"
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
longest("abc", "de");        // ✅ string 에는 length 가 있음
longest([1,2], [3]);         // ✅ 배열도
longest(1, 2);               // ❌ number 에는 length 가 없음

기본값과 키 제약

// 기본 타입 인자
type ApiResult<T = unknown> = { data: T; ok: boolean };

// 키를 제약 — 실무에서 매우 자주 쓰는 형태
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const k of keys) out[k] = obj[k];
  return out;
}

const user = { id: 1, name: "김", pw: "secret" };
pick(user, ["id", "name"]);      // { id: number; name: string } ★
pick(user, ["nope"]);            // ❌ 없는 키는 컴파일 에러

실무에서 만나는 제네릭

// ① API 클라이언트
async function api<T>(path: string): Promise<T> {
  const res = await fetch(path);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<T>;
}
const user = await api<User>("/api/users/1");     // user: User

// ② 저장소 인터페이스 (Nest·계층 설계에서 그대로 씁니다)
interface Repository<T, ID = number> {
  findById(id: ID): Promise<T | null>;
  findAll(): Promise<T[]>;
  save(entity: T): Promise<T>;
  delete(id: ID): Promise<void>;
}
class UserRepository implements Repository<User> { ... }

// ③ 이벤트 맵 — 타입 안전한 이벤트 버스
type Events = {
  "order.created": { orderId: string; amount: number };
  "user.login":    { userId: number };
};
function emit<K extends keyof Events>(name: K, payload: Events[K]) { ... }

emit("order.created", { orderId: "A1", amount: 1000 });   // ✅

제네릭을 남용하지 마세요. 타입 파라미터가 한 곳에서만 쓰인다면 제네릭일 이유가 없습니다. function f<T>(x: T): void 는 그냥 unknown 이면 됩니다. “들어온 타입이 나가는 타입에 영향을 줄 때”만 제네릭입니다.
이름 규칙 — T(Type) · K(Key) · V(Value) · E(Element) · R(Return) 이 관례지만, 의미가 있으면 <TUser, TOrder> 처럼 이름을 붙이는 편이 읽기 좋습니다.
제네릭을 쓸지 말지의 기준은 하나입니다 — 들어온 타입이 결과에 영향을 주는가.
TS 07

유틸리티 타입 총정리

이미 있는 타입을 조금씩 바꿔 쓰는 내장 도구들. 실무 사용 빈도 최상위입니다.

객체 다루기

유틸리티하는 일
Partial<T>모든 속성을 선택으로 — 수정 API 의 body
Required<T>모든 속성을 필수로
Readonly<T>모든 속성을 읽기 전용으로
Pick<T, K>지정한 키만 골라내기
Omit<T, K>지정한 키만 빼기 — 비밀번호 제외 등
Record<K, V>키-값 사전 만들기
interface User {
  id: number; name: string; email: string;
  password: string; createdAt: Date;
}

// 응답에서 비밀번호 빼기 — ★ 실무 최다 사용
type UserResponse = Omit<User, "password">;

// 생성 요청 — 서버가 만드는 필드 제외
type CreateUser = Omit<User, "id" | "createdAt">;

// 수정 요청 — 일부만 보낼 수 있게
type UpdateUser = Partial<CreateUser>;

// 목록용 — 필요한 것만
type UserSummary = Pick<User, "id" | "name">;

// 상태별 색상 사전
type Status = "active" | "inactive" | "banned";
const COLOR: Record<Status, string> = {
  active: "green", inactive: "gray", banned: "red",
};   // ★ 상태를 추가하면 여기서 컴파일 에러가 납니다

유니온 · 함수 다루기

유틸리티하는 일
Exclude<T, U>유니온에서 빼기
Extract<T, U>유니온에서 고르기
NonNullable<T>null·undefined 제거
ReturnType<F>함수의 반환 타입
Parameters<F>함수의 매개변수 튜플
Awaited<P>Promise 를 벗긴 타입
InstanceType<C>클래스의 인스턴스 타입
type Status = "loading" | "success" | "error";
type Done = Exclude<Status, "loading">;      // "success" | "error"

// ★ 함수에서 타입을 역으로 뽑아내기 — 매우 실용적
function createUser(name: string, age: number) {
  return { id: 1, name, age, createdAt: new Date() };
}
type User = ReturnType<typeof createUser>;   // 반환 객체 타입
type Args = Parameters<typeof createUser>;   // [string, number]

// async 함수라면 Awaited 로 벗기기
async function fetchUser() { return { id: 1, name: "김" }; }
type FetchedUser = Awaited<ReturnType<typeof fetchUser>>;

// 실무: Prisma·zod 처럼 "값에서 타입이 나오는" 라이브러리와 궁합이 좋습니다
const userSchema = z.object({ name: z.string(), age: z.number() });
type UserInput = z.infer<typeof userSchema>;   // ★ 스키마 하나로 타입까지
타입을 두 번 적지 마세요. “스키마 · 상수 · 함수”에서 타입을 뽑아내는 방향으로 설계하면, 고칠 곳이 한 군데로 줄어듭니다. 이것이 유틸리티 타입의 진짜 목적입니다.
타입을 복사하지 않고 파생시키는 것이 유지보수의 전부입니다.
TS 08

keyof · typeof · 인덱스드 액세스

값에서 타입을 뽑아내는 세 가지 도구. 타입 중복을 없애는 열쇠입니다.

세 가지 연산자

interface User { id: number; name: string; tags: string[]; }

// ① keyof — 키들의 유니온
type UserKey = keyof User;              // "id" | "name" | "tags"

// ② typeof — 값에서 타입 얻기 (타입 자리에서 씀)
const defaults = { retry: 3, timeout: 5000 };
type Config = typeof defaults;          // { retry: number; timeout: number }

// ③ 인덱스드 액세스 — 속성의 타입 꺼내기
type Name = User["name"];               // string
type Tag  = User["tags"][number];       // string ★ 배열 요소 타입
type Some = User["id" | "name"];        // number | string

// 조합 — 배열 상수에서 유니온 타입 만들기
const ROLES = ["admin", "user", "guest"] as const;
type Role = (typeof ROLES)[number];     // "admin" | "user" | "guest"
// ★ 배열만 고치면 타입이 자동으로 따라옵니다
“상수를 하나만 두는” 패턴이 이 절의 핵심입니다. 상수 배열·객체를 as const 로 선언하고 타입은 거기서 파생시키면, 값과 타입이 어긋날 일이 없습니다. 드롭다운 옵션·상태 코드·권한 목록에 그대로 쓰입니다.

실무 활용

// ① 타입 안전한 속성 접근기
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const name = get(user, "name");     // string ★
get(user, "nope");                  // ❌ 컴파일 에러

// ② 정렬 키를 실제 필드로 제한
function sortBy<T>(list: T[], key: keyof T, dir: "asc" | "desc" = "asc") {
  return list.toSorted((a, b) =>
    (a[key] > b[key] ? 1 : -1) * (dir === "asc" ? 1 : -1));
}
sortBy(users, "createdAt");         // ✅
sortBy(users, "typo");              // ❌ 잡힘

// ③ 설정 객체에서 환경 변수 타입 만들기
const ENV_KEYS = ["DB_HOST", "DB_PORT", "REDIS_URL"] as const;
type EnvKey = (typeof ENV_KEYS)[number];
const env = {} as Record<EnvKey, string>;
env.DB_HOST;      // ✅ 자동완성됨
env.DB_HOSTT;     // ❌ 오타를 잡아 줍니다
// ④ 라우트 경로 타입화 (템플릿 리터럴과 조합 — t10)
const routes = {
  home: "/",
  user: "/users/:id",
  order: "/orders/:orderId/items/:itemId",
} as const;

type RouteName = keyof typeof routes;       // "home" | "user" | "order"

keyof any 는 string | number | symbol 입니다. 객체 키를 문자열로만 다루고 싶다면 Extract<keyof T, string> 또는 K extends string & keyof T 로 좁혀야 합니다. Object.keys() 가 string[] 을 반환하는 것도 이 때문입니다.
TS 09

조건부 타입 · infer

타입에도 if 문이 있습니다. 라이브러리 타입이 똑똑해 보이는 이유입니다.

기본 문법

// A extends B ? 참일때 : 거짓일때
type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">;      // true
type B = IsString<42>;        // false

// 실용 예 — null 을 제외한 타입
type NonNull<T> = T extends null | undefined ? never : T;

// 유니온에 적용하면 각각에 분배됩니다 (분배 조건부 타입)
type ToArray<T> = T extends any ? T[] : never;
type R = ToArray<string | number>;    // string[] | number[]  ★ 각각 적용

// 분배를 막고 싶으면 대괄호로 감쌉니다
type NoDist<T> = [T] extends [any] ? T[] : never;
type R2 = NoDist<string | number>;    // (string | number)[]

infer — 타입 안에서 꺼내 오기

// 배열의 요소 타입 꺼내기
type ElementOf<T> = T extends (infer U)[] ? U : never;
type E = ElementOf<string[]>;              // string

// Promise 벗기기 (Awaited 의 원리)
type Unwrap<T> = T extends Promise<infer U> ? U : T;

// 함수 반환 타입 (ReturnType 의 원리)
type Ret<F> = F extends (...args: any[]) => infer R ? R : never;

// 첫 번째 매개변수만
type FirstArg<F> = F extends (a: infer A, ...rest: any[]) => any ? A : never;

// 재귀 — 깊이 중첩된 Promise 도 전부 벗기기
type DeepAwait<T> = T extends Promise<infer U> ? DeepAwait<U> : T;
type X = DeepAwait<Promise<Promise<string>>>;   // string

실무에서 쓰는 조건부 타입

// ① API 응답 형태를 요청에 따라 바꾸기
type ApiResult<T, Raw extends boolean = false> =
  Raw extends true ? string : { data: T; ok: boolean };

declare function call<T, R extends boolean = false>(
  url: string, raw?: R): Promise<ApiResult<T, R>>;

const a = await call<User>("/u");          // { data: User; ok: boolean }
const b = await call<User>("/u", true);    // string ★

// ② 옵션에 따라 필수 필드가 달라지는 함수
type Options =
  | { mode: "file"; path: string }
  | { mode: "memory" };            // path 를 받으면 컴파일 에러

// ③ 깊은 Partial (중첩 객체 전부 선택적으로)
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

// ④ null 가능한 필드만 골라내기
type NullableKeys<T> = {
  [K in keyof T]: null extends T[K] ? K : never
}[keyof T];
여기서부터는 “필요할 때만” 쓰세요. 조건부 타입은 강력하지만 에러 메시지가 급격히 난해해집니다. 업무 코드에서 세 줄 넘는 타입 연산이 나오면, 타입을 단순화하거나 코드를 나누는 편이 대개 더 낫습니다. (라이브러리를 만든다면 이야기가 다릅니다 — t17)
디버깅 요령 — 복잡한 타입은 type _Check = MyType<Sample>; 처럼 중간 결과에 이름을 붙여 두고 에디터에서 호버해 보세요. 어디서 never 가 되는지 바로 보입니다.
직접 만들 일은 드물지만 라이브러리 타입을 읽으려면 이 모양을 알아야 합니다.

타입 가드 · unknown

TypeScript 와 현실이 만나는 경계. 여기를 어떻게 다루느냐가 실력입니다.

사용자 정의 타입 가드

// x is T — "이 함수가 true 면 x 는 T 다" 라고 컴파일러에 알림
function isUser(x: unknown): x is User {
  return typeof x === "object" && x !== null
      && "id" in x && typeof (x as User).id === "number";
}

const data: unknown = await res.json();
if (isUser(data)) {
  data.name;          // ✅ 여기서는 User
}

// asserts — 아니면 던지는 형태
function assertUser(x: unknown): asserts x is User {
  if (!isUser(x)) throw new TypeError("User 가 아닙니다");
}
assertUser(data);
data.name;            // ✅ 이후 전부 User

// 배열 필터에서 타입 좁히기 (아주 자주 쓰입니다)
const items: (string | null)[] = ["a", null, "b"];
const clean = items.filter((x): x is string => x !== null);   // string[] ★
// ★ 이 표기가 없으면 (string | null)[] 로 남습니다
타입 가드는 “약속”이지 “검증”이 아닙니다. x is T 라고 적어 놓고 내부 검사가 허술하면 컴파일러는 그대로 믿습니다. 복잡한 형태라면 손으로 짜지 말고 Zod 를 쓰세요(🧰 도구 o07).

타입의미
any“검사하지 마” — 타입 시스템을 끄는 것. 쓰지 마세요
unknown“뭔지 모름” — 확인 후에만 쓸 수 있음. any 의 안전한 대체
never“있을 수 없음” — 빠짐없음 검사(t04), 절대 반환 안 하는 함수

if (typeof u === "string") u.trim(); // ✅ 확인 후 사용

// catch 절은 unknown 으로 받으세요 (tsconfig: useUnknownInCatchVariables)

}

데코레이터 — 실제로 무슨 일이 일어나나

// 데코레이터는 "클래스·메서드를 감싸는 함수"입니다
function Log(target: any, key: string, desc: PropertyDescriptor) {
  const original = desc.value;
  desc.value = function (...args: any[]) {
    console.log(`→ ${key}(${JSON.stringify(args)})`);
    const result = original.apply(this, args);
    console.log(`← ${key} =`, result);
    return result;
  };
}

class Calc {
  @Log
  add(a: number, b: number) { return a + b; }
}
new Calc().add(1, 2);
// → add([1,2])
// ← add = 3

//   "메타데이터를 붙여 두고 프레임워크가 나중에 읽는" 구조입니다.

타입 레벨 프로그래밍

타입만으로 계산하는 세계. 라이브러리를 만들 때 쓰입니다.

타입으로 하는 재귀

// 문자열 뒤집기
type Reverse<S extends string> =
  S extends `${infer H}${infer R}` ? `${Reverse<R>}${H}` : "";
type A = Reverse<"hello">;      // "olleh"

// 유니온을 튜플로
type Split<S extends string, D extends string> =
  S extends `${infer H}${D}${infer R}` ? [H, ...Split<R, D>] : [S];
type B = Split<"a,b,c", ",">;   // ["a", "b", "c"]

// 깊은 readonly
type DeepReadonly<T> = T extends (infer U)[]
  ? readonly DeepReadonly<U>[]
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

// 중첩 객체의 경로 문자열 만들기 (i18n·폼 라이브러리가 쓰는 기법)
type Paths<T, P extends string = ""> = T extends object
  ? { [K in keyof T & string]:
      | (P extends "" ? K : `${P}.${K}`)
      | Paths<T[K], P extends "" ? K : `${P}.${K}`>
    }[keyof T & string]
  : never;

type C = Paths<{ user: { name: string; addr: { city: string } } }>;
// "user" | "user.name" | "user.addr" | "user.addr.city" ★

한계와 주의

제약
  · 재귀 깊이 제한 (기본 약 50, 꼬리 재귀 최적화 시 1000)
  · "Type instantiation is excessively deep" 에러를 만나게 됨
  · 타입 계산이 느려지면 에디터 자동완성이 눈에 띄게 느려짐
  · 유니온 조합이 커지면 폭발 (10 × 10 × 10 = 1000 가지)

측정
  tsc --diagnostics            # 타입 검사 시간·인스턴스 수
  tsc --generateTrace trace    # 어느 타입이 느린지 추적
업무 코드에서는 거의 필요 없습니다. 이 절의 기법은 tRPC · Prisma · react-hook-form 같은 “타입으로 개발자 경험을 만드는 라이브러리”의 영역입니다. 서비스 코드에 이런 타입이 등장하면 대개 설계를 단순화할 여지가 있다는 신호입니다.
