RN 01

RN 이 동작하는 원리

여기를 이해하면 성능 문제의 원인이 전부 보입니다.

옛 아키텍처 — 브리지

[JS 스레드]        [브리지]        [네이티브 UI 스레드]
  React 로직   ──JSON 직렬화──>   실제 화면 그리기
              <──비동기·배치───

문제
  · 모든 통신이 JSON 직렬화 → 비용이 큼
  · 완전 비동기 → 스크롤 중 흰 화면이 보이는 원인
  · JS 스레드가 막히면 → 터치·애니메이션이 전부 멈춤

새 아키텍처 (0.68+, 0.76 부터 기본)

[JS]  ←── JSI (직접 호출) ──→  [C++ / 네이티브]
                                  ↓
        Fabric (새 렌더러) · TurboModules (지연 로딩)

달라진 점
  · JSI — JS 가 네이티브 함수를 직접 호출 (직렬화 없음)
  · Fabric — 동기 레이아웃 가능 → 흰 화면 감소
  · TurboModules — 쓰는 모듈만 로딩 → 시작 속도 개선
  · Hermes — RN 전용 JS 엔진, 시작 속도·메모리 우수 (기본값)
실무에서 알아야 할 결론 — ① JS 스레드를 막으면 앱 전체가 버벅입니다(무거운 계산 금지), ② 애니메이션은 네이티브 스레드에서 돌려야 60fps 가 나옵니다(r11), ③ 리스트는 화면에 보이는 것만 그려야 합니다(r06).

Expo vs Bare 선택

처음 시작할 때 가장 중요한 결정입니다. 결론부터: Expo 로 시작하세요.

비교

항목Expo / Bare(순수 RN)
시작1분 / Xcode·Android Studio 설정 필요
네이티브 코드가능(prebuild) / 자유
빌드EAS 클라우드 빌드 / 로컬 빌드 환경 필요
업데이트OTA 지원(EAS Update) / 직접 구축
맥 없이 iOS가능 (EAS) / 불가
라이브러리대부분 호환 / 전부 가능
2024년 이후로는 Expo 가 사실상 기본입니다. 예전에 “Expo 는 제약이 많다”던 문제는 Config Plugin·prebuild 로 대부분 해결됐습니다. RN 공식 문서도 Expo 를 권장합니다.

      disabled={disabled}

      <Text style={styles.title}>{title}</Text>
      {subtitle && <Text style={styles.sub}>{subtitle}</Text>}
    </Pressable>
  );
}

Zustand — 전역 상태

npm i zustand
import { create } from "zustand";
import { persist, createJSONStorage } from "zustand/middleware";
import AsyncStorage from "@react-native-async-storage/async-storage";

type AuthState = {
  user: User | null;
  login: (u: User) => void;
  logout: () => void;
};

export const useAuth = create<AuthState>()(
  persist(
    (set) => ({
      user: null,
      login: (user) => set({ user }),
      logout: () => set({ user: null }),
    }),
    {
      name: "auth",
      storage: createJSONStorage(() => AsyncStorage),
      partialize: (s) => ({ user: s.user }),      // ★ 저장할 것만
    },
  ),
);

// 사용 — ★ 필요한 조각만 구독해야 불필요한 리렌더가 없습니다
const user = useAuth(s => s.user);
const logout = useAuth(s => s.logout);

// ❌ 전체를 구독하면 아무 값이나 바뀔 때마다 리렌더됩니다
const { user, logout } = useAuth();
Context 로 전역 상태를 만들 때 주의 — 값이 바뀌면 그 Context 를 쓰는 모든 컴포넌트가 리렌더됩니다. 자주 바뀌는 값(입력값·스크롤 위치)에는 Context 를 쓰지 마세요. Zustand 는 구독한 조각만 리렌더합니다.
RN 05

스타일 · Flexbox

웹 CSS 와 비슷하지만 기본값이 다릅니다.

웹 CSS 와 다른 점

· 기본 flexDirection 이 column  (웹은 row)
· 모든 View 가 이미 display:flex
· 단위가 없습니다 — 숫자는 dp (밀도 독립 픽셀)
· 상속이 없습니다 — 부모의 fontSize 가 자식에 안 내려감
  (단, Text 안의 Text 는 예외)
· 축약형이 제한적 — margin: "0 auto" 같은 문자열 불가
· % 는 일부만 지원, calc() 없음
· position: fixed 없음 (absolute 만)
· z-index 대신 렌더 순서 + elevation(안드로이드)
const styles = StyleSheet.create({
  container: {
    flex: 1,                        // ★ 남은 공간 다 쓰기
    flexDirection: "row",
    justifyContent: "space-between",// 주축 정렬
    alignItems: "center",           // 교차축 정렬
    gap: 12,                        // 0.71+ 지원
    padding: 16,
  },
  card: {
    flex: 1,                        // 형제끼리 균등 분할
    aspectRatio: 16 / 9,            // 비율 고정
    borderRadius: 12,
    overflow: "hidden",             // ★ iOS 는 이게 있어야 자식이 잘림
  },
  // 그림자는 플랫폼마다 다릅니다
  shadow: Platform.select({
    ios: { shadowColor: "#000", shadowOffset: { width: 0, height: 2 },
           shadowOpacity: 0.1, shadowRadius: 8 },
    android: { elevation: 4 },
  }),

RN 06

리스트 — FlatList

앱 성능 문제의 절반이 여기서 나옵니다.

ScrollView 를 쓰면 안 되는 이유

ScrollView  — 자식을 "전부" 렌더링하고 메모리에 유지
FlatList    — 화면에 보이는 것 + 약간의 여유분만 (가상화)

항목 1,000개일 때
  ScrollView  → 1,000개 컴포넌트 생성 → 수 초간 멈춤 → 메모리 폭발
  FlatList    → 약 15개만 → 즉시 렌더링

기준: 항목이 20개를 넘거나 개수를 모르면 → FlatList
<FlatList
  data={orders}
  keyExtractor={(item) => item.id}            // ★ 안정적인 고유 키
  renderItem={({ item }) => <OrderRow order={item} />}

  // 성능 옵션
  initialNumToRender={10}
  maxToRenderPerBatch={10}
  windowSize={5}                               // 화면 단위 (기본 21)
  removeClippedSubviews                        // 안드로이드에서 효과 큼

  // 높이가 고정이면 ★ 이게 가장 큰 최적화입니다
  getItemLayout={(_, index) => ({
    length: ROW_HEIGHT, offset: ROW_HEIGHT * index, index,
  })}

  // 무한 스크롤
  onEndReached={fetchNextPage}
  onEndReachedThreshold={0.5}
  ListFooterComponent={isFetching ? <ActivityIndicator /> : null}

  // 당겨서 새로고침
  refreshControl={<RefreshControl refreshing={isRefetching} onRefresh={refetch} />}

  // 빈 상태 · 구분선
  ListEmptyComponent={<Empty message="주문이 없습니다" />}
  ItemSeparatorComponent={() => <View style={styles.sep} />}
/>

RN 11

애니메이션 · 제스처

60fps 의 비결은 하나입니다 — JS 스레드를 거치지 않는 것.

왜 Reanimated 인가

[내장 Animated]  JS 스레드에서 값 계산 → 네이티브로 전달
   → JS 가 바쁘면 애니메이션이 끊깁니다
   → useNativeDriver: true 로 일부만 개선 가능
      (transform·opacity 만 지원, width·색상 불가)

[Reanimated]  worklet 이 UI 스레드에서 직접 실행
   → JS 스레드가 아무리 바빠도 60fps 유지 ★
   → 모든 속성 애니메이션 가능
npx expo install react-native-reanimated react-native-gesture-handler
import Animated, {
  useSharedValue, useAnimatedStyle, withSpring, withTiming,
} from "react-native-reanimated";

function Box() {
  const offset = useSharedValue(0);        // ★ UI 스레드에 사는 값

  const style = useAnimatedStyle(() => ({
    transform: [{ translateX: offset.value }],
  }));                                      // ★ 이 함수는 UI 스레드에서 실행됩니다

  return (
    <>
      <Animated.View style={[styles.box, style]} />
      <Button title="이동" onPress={() => {
        offset.value = withSpring(100, { damping: 15 });
      }} />
    </>
  );
}

제스처 — 스와이프 삭제

import { Gesture, GestureDetector } from "react-native-gesture-handler";
import { runOnJS } from "react-native-reanimated";

function SwipeRow({ onDelete }: { onDelete: () => void }) {
  const x = useSharedValue(0);

  const pan = Gesture.Pan()
    .onUpdate((e) => { x.value = Math.min(0, e.translationX); })
    .onEnd(() => {
      if (x.value < -120) {
        x.value = withTiming(-400);
        runOnJS(onDelete)();          // ★ UI 스레드 → JS 함수 호출
      } else {
        x.value = withSpring(0);
      }
    });

  const style = useAnimatedStyle(() => ({ transform: [{ translateX: x.value }] }));

  return (
    <GestureDetector gesture={pan}>
      <Animated.View style={style}>{/* 내용 */}</Animated.View>
    </GestureDetector>
  );
}
worklet 안에서 일반 JS 함수를 직접 부르면 크래시합니다. setState·console.log·API 호출은 모두 runOnJS(fn)() 로 감싸야 합니다. 반대로 JS 에서 worklet 값을 읽으려면 runOnUI 를 씁니다.

    Events("onSensorChange")               // 이벤트 발행
  }
}

# OTA 업데이트 — ★ JS 만 바뀌었다면 심사 없이 즉시 반영
eas update --branch production --message "버그 수정"
OTA 로 되는 것과 안 되는 것 — JS·이미지·스타일 변경은 OTA 로 즉시 가능합니다. 네이티브 모듈 추가·권한 변경·SDK 업그레이드는 반드시 새 빌드와 심사가 필요합니다. (스토어 정책상 기능을 통째로 바꾸는 OTA 는 금지입니다)

심사에서 자주 반려되는 이유

  • 권한 설명 문구 누락·불충분 — “왜 필요한지” 구체적으로 (r10)
  • 테스트 계정 미제공 — 로그인이 필요한 앱은 심사자용 계정 필수
  • 결제 우회 — 디지털 재화를 외부 결제로 유도하면 즉시 반려
  • 계정 삭제 기능 없음 — 회원가입이 있으면 앱 내 삭제가 의무입니다
  • 크래시 — 심사자 기기에서 죽으면 바로 반려
  • 개인정보 처리방침 URL 누락
  • 미완성 기능·플레이스홀더 화면
