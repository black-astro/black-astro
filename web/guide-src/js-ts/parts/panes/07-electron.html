ELECTRON 01

메인 · 렌더러 구조

이 구분 하나만 이해하면 Electron 의 80%는 끝납니다.

두 개의 세계

Main
메인 프로세스 — Node.js 환경 앱당 하나. 창을 만들고, 파일·DB·OS 기능에 접근합니다. fs·child_process 를 쓸 수 있습니다.
▲ IPC ▼
Renderer
렌더러 프로세스 — 브라우저 환경 창마다 하나씩. React·Vue 로 화면을 그립니다. 기본적으로 Node 를 쓸 수 없습니다(그래야 안전합니다).
▲
Preload
프리로드 — 둘 사이의 다리 렌더러가 로드되기 전에 실행되며, 허용된 기능만 화면에 노출합니다.
규칙 하나 — 화면(렌더러)은 파일을 직접 읽을 수 없습니다. “메인에게 부탁 → 메인이 처리 → 결과를 돌려받기”가 모든 기능의 기본 흐름입니다(e03 IPC).

# 옛 방식(electron-forge + webpack)보다 빌드가 훨씬 빠릅니다
Electron 버전 = Chromium + V8 + Node 의 묶음입니다. Electron 42 는 Chromium 148 · V8 14.8 · Node 24.15 를 담고 있습니다. 그래서 “이 웹 API 를 쓸 수 있나”는 Chromium 버전이, “이 node: 모듈이 있나”는 내장 Node 버전이 결정합니다 — 내 PC 에 설치된 Node 버전과는 무관합니다. Electron 은 Chromium 을 따라 8주마다 메이저가 올라가므로, 보안 패치를 받으려면 정기적으로 올리는 것을 전제로 개발하세요.
Electron 은 가볍지 않습니다. 빈 앱도 설치 파일이 80~150MB, 메모리 100MB+ 입니다 (Chromium 을 통째로 포함하기 때문). 가벼움이 중요하면 Tauri(Rust) 를 검토하세요 — 대신 웹뷰가 OS 마다 달라 호환성 이슈가 생깁니다.
일렉트론 구조의 한 문장 요약 — 권한은 메인에, 화면은 렌더러에.

메인 프로세스

import { app, BrowserWindow, shell } from "electron";
import path from "node:path";

let mainWindow: BrowserWindow | null = null;

function createWindow() {
  mainWindow = new BrowserWindow({
    width: 1200, height: 800,
    minWidth: 940, minHeight: 600,
    show: false,                              // ★ 준비될 때까지 숨김
    titleBarStyle: process.platform === "darwin" ? "hiddenInset" : "default",
    webPreferences: {
      preload: path.join(__dirname, "../preload/index.js"),
      contextIsolation: true,                 // ★ 반드시 true (e04)
      nodeIntegration: false,                 // ★ 반드시 false
      sandbox: true,
    },
  });

  // ★ 흰 화면 깜빡임 방지
  mainWindow.once("ready-to-show", () => mainWindow?.show());

  // 외부 링크는 기본 브라우저로 (앱 안에서 열면 보안 위험)
  mainWindow.webContents.setWindowOpenHandler(({ url }) => {
    shell.openExternal(url);
    return { action: "deny" };
  });

  if (process.env.NODE_ENV === "development") {
    mainWindow.loadURL("http://localhost:5173");
    mainWindow.webContents.openDevTools();
  } else {
    mainWindow.loadFile(path.join(__dirname, "../renderer/index.html"));
  }
}

요청-응답 (가장 많이 씁니다)

// ① 메인 — 핸들러 등록
import { ipcMain, dialog } from "electron";

ipcMain.handle("file:read", async (event, filePath: string) => {
  // ★ 반드시 검증하세요 (e04)
  const safe = path.resolve(DATA_DIR, filePath);
  if (!safe.startsWith(path.resolve(DATA_DIR) + path.sep)) {
    throw new Error("잘못된 경로입니다");
  }
  return fs.readFile(safe, "utf8");
});

ipcMain.handle("dialog:openFile", async () => {
  const { canceled, filePaths } = await dialog.showOpenDialog({
    properties: ["openFile"],
    filters: [{ name: "엑셀", extensions: ["xlsx", "csv"] }],
  });
  return canceled ? null : filePaths[0];
});
// ② 프리로드 — 화면에 노출할 API 만 정의
import { contextBridge, ipcRenderer } from "electron";

const api = {
  readFile: (p: string) => ipcRenderer.invoke("file:read", p),
  openFile: () => ipcRenderer.invoke("dialog:openFile"),
};
contextBridge.exposeInMainWorld("api", api);
export type Api = typeof api;                 // ★ 타입을 렌더러에서 재사용

// ③ 렌더러 — 그냥 함수처럼 씁니다
const path = await window.api.openFile();
if (path) {
  const text = await window.api.readFile(path);

IPC 로 큰 데이터를 자주 주고받지 마세요. 구조화 복제(structured clone)로 직렬화 비용이 듭니다. 100MB 파일 내용을 통째로 넘기는 대신 메인에서 처리하고 결과만 보내거나, 파일 경로만 주고받으세요.

ELECTRON 04

preload · 보안

이 절을 대충 넘기면 사용자 PC 를 공격자에게 내주게 됩니다.

왜 위험한가

nodeIntegration: true 로 두면
  화면(웹 페이지)에서 require("child_process") 가 됩니다.
  → 표시하는 콘텐츠에 XSS 가 하나라도 있으면
  → 공격자가 사용자 PC 에서 "무슨 명령이든" 실행합니다

위험이 들어오는 경로
  · 외부 웹사이트를 iframe·webview 로 표시
  · 서버에서 받은 HTML 을 innerHTML 로 넣기
  · 사용자가 입력한 마크다운 렌더링
  · 취약한 npm 패키지 (🧬 전문가 d13)
// ★ 안전한 기본 설정 — 이대로 두세요
webPreferences: {
  contextIsolation: true,       // 프리로드와 페이지의 컨텍스트 분리
  nodeIntegration: false,       // 페이지에서 Node 사용 불가
  sandbox: true,                // 렌더러를 샌드박스에
  webSecurity: true,            // ★ 개발 편의로도 끄지 마세요
  allowRunningInsecureContent: false,
  preload: path.join(__dirname, "preload.js"),
}
인터넷에서 “해결책”으로 nodeIntegration: true 를 권하는 글이 많습니다. 대부분 오래된 튜토리얼입니다. 지금은 contextBridge 로 필요한 기능만 노출하는 것이 유일한 정답입니다.

보안 체크리스트

  • ☐ contextIsolation: true · nodeIntegration: false
  • ☐ CSP 헤더 설정 (인라인 스크립트 차단)
  • ☐ 외부 링크는 shell.openExternal 로만
  • ☐ will-navigate 로 예상 밖 이동 차단
  • ☐ 원격 콘텐츠를 로드한다면 반드시 HTTPS
  • ☐ DB 접속 정보·API 키를 앱에 넣지 않기 — 디컴파일하면 다 보입니다
  • ☐ npm audit · Electron 최신 버전 유지 (Chromium 취약점 패치)
Electron 버전을 오래 방치하지 마세요. Chromium 취약점이 그대로 남아 있게 됩니다. 보안 패치를 받으려면 최신 3개 메이저 버전 안에 머물러야 합니다.
여기에 더해 배포된 앱이 공격 도구로 악용되는 것을 막는 Fuses·asar 무결성은 ⚙️ 네이티브 v15 에서 다룹니다.
"XSS 하나가 파일 삭제로 이어지는 것"을 막는 구조입니다.

import { app, BrowserWindow } from 'electron';
import path from 'node:path';

// 1) 내 앱이 myapp:// 를 담당한다고 OS 에 등록
if (process.defaultApp) {
  // 개발 중(electron . 로 띄울 때)은 실행 인자까지 함께 등록해야 한다
  if (process.argv.length >= 2)
    app.setAsDefaultProtocolClient('myapp', process.execPath,
                                   [path.resolve(process.argv[1])]);
} else {
  app.setAsDefaultProtocolClient('myapp');
}

// 2) 두 번째 실행을 막는다 — 실패하면 '내가 두 번째'라는 뜻
const primary = app.requestSingleInstanceLock();
if (!primary) {
  app.quit();                 // 인자는 이미 첫 번째 프로세스로 전달됐다
} else {
  app.on('second-instance', (_e, argv) => {
    // Windows · Linux: 두 번째 실행의 argv 가 여기로 넘어온다
    const url = argv.find(a => a.startsWith('myapp://'));
    focusMain();
    if (url) route(url);
  });

  // macOS: argv 가 아니라 open-url 이벤트로 온다
  app.on('open-url', (e, url) => { e.preventDefault(); focusMain(); route(url); });

  app.whenReady().then(() => {
    createWindow();
    // Windows · Linux 첫 실행: 시작 인자에 딥링크가 섞여 있다
    const url = process.argv.find(a => a.startsWith('myapp://'));
    if (url) route(url);
  });
}
플랫폼마다 들어오는 통로가 다릅니다. macOS 는 open-url, Windows·Linux 는 argv 입니다. 세 경로(첫 실행 argv · second-instance argv · open-url)를 모두 처리하지 않으면 “어떤 때는 되고 어떤 때는 안 되는” 버그가 됩니다 — 딥링크 문의의 대부분이 여기서 나옵니다.
단일 인스턴스 락은 딥링크만을 위한 게 아닙니다. SQLite 파일·로그 파일·설정 파일을 두 프로세스가 동시에 쓰는 사고를 막아 줍니다. 데이터를 파일로 들고 있는 앱이라면 거의 항상 켜야 합니다.

function focusMain() {
  const win = BrowserWindow.getAllWindows()[0];
  if (!win) return createWindow();
  if (win.isMinimized()) win.restore();
  win.show();
  win.focus();
}

// 딥링크는 '외부에서 들어온 입력'이다 — 화이트리스트로 받는다
const ROUTES = {
  room:    (id: string) => `/rooms/${encodeURIComponent(id)}`,
  ticket:  (id: string) => `/tickets/${encodeURIComponent(id)}`,
} as const;

function route(raw: string) {
  let u: URL;
  try { u = new URL(raw); } catch { return; }
  if (u.protocol !== 'myapp:') return;

  const kind = u.hostname;                       // myapp://room/42 → 'room'
  const id   = u.pathname.replace(/^\//, '');
  const make = ROUTES[kind as keyof typeof ROUTES];
  if (!make) return;                             // 모르는 경로는 조용히 버린다

  BrowserWindow.getAllWindows()[0]
    ?.webContents.send('deeplink:navigate', make(id));
}
딥링크는 공격 표면입니다. 악성 웹페이지가 myapp:// 링크를 심어 사용자를 클릭하게 만들 수 있습니다. URL 을 그대로 loadURL·shell.openPath·exec 에 넘기면 안 됩니다. 위처럼 허용한 경로만 화이트리스트로 매핑하고, 결제·삭제처럼 되돌릴 수 없는 동작은 딥링크로 바로 실행하지 말고 확인 화면을 거치세요.
패키징 쪽 설정도 함께 필요합니다 — electron-builder.yml 의 protocols:(name·schemes) 항목을 적어야 설치 시 OS 에 등록됩니다. macOS 는 CFBundleURLTypes 로 들어갑니다.

통합 터미널 · 자식 프로세스 붙이기

VS Code 의 터미널 패널을 만드는 부품은 두 개입니다 — node-pty(가짜 터미널)와 xterm.js(화면). 빌드 로그·배포 스크립트를 앱 안에서 돌리는 사내 도구의 핵심 부품이기도 합니다.

왜 spawn 이 아니라 pty 인가

child_process.spawn
  • 파이프라 TTY 가 아니다 → 색이 안 나오고 진행바가 깨집니다
  • npm·docker 가 “터미널이 아님”으로 판단해 출력 형식을 바꿉니다
  • 창 크기 개념이 없어 줄바꿈이 엉킵니다
  • 대화형 입력(비밀번호 프롬프트)이 동작하지 않습니다
node-pty
  • OS 에게 진짜 터미널을 하나 만들어 달라고 요청합니다
  • 색·커서 제어·진행바가 그대로 옵니다
  • resize(cols, rows) 로 창 크기를 알려 줄 수 있습니다
  • Windows 는 ConPTY, 유닉스는 forkpty 를 씁니다
npm i node-pty @xterm/xterm @xterm/addon-fit
# node-pty 는 네이티브 모듈 → Electron ABI 로 다시 빌드해야 한다
npm i -D @electron/rebuild && npx electron-rebuild
네이티브 모듈이라 “내 PC 에선 되는데”가 자주 납니다. electron-rebuild 를 postinstall 에 걸고, CI 에서 배포 대상 OS 별로 각각 빌드하세요 (⚙️ 네이티브 · 미디어 탭 07 네이티브 모듈 운영에서 이어집니다).

메인 프로세스 — 세션 관리

import * as pty from 'node-pty';
import { ipcMain, BrowserWindow } from 'electron';
import os from 'node:os';

const shell = process.platform === 'win32'
  ? (process.env.COMSPEC ?? 'powershell.exe')
  : (process.env.SHELL   ?? '/bin/bash');

const sessions = new Map<string, pty.IPty>();

ipcMain.handle('term:create', (e, { cols, rows, cwd }) => {
  const id = crypto.randomUUID();
  const p = pty.spawn(shell, [], {
    name: 'xterm-color', cols, rows,
    cwd: cwd ?? os.homedir(),
    env: { ...process.env, TERM: 'xterm-256color' },
  });

  // ── 흐름 제어: 출력을 모아서 보낸다 ──────────────────
  // 빌드 로그는 초당 수천 줄이 나온다. 한 줄마다 IPC 를 태우면
  // 렌더러가 먼저 죽는다. 16ms(한 프레임) 단위로 묶어 보낸다.
  let buf = '', timer: NodeJS.Timeout | null = null;
  const wc = BrowserWindow.fromWebContents(e.sender)!.webContents;
  p.onData(chunk => {
    buf += chunk;
    if (buf.length > 512 * 1024) buf = buf.slice(-512 * 1024);  // 폭주 방어
    timer ??= setTimeout(() => {
      wc.send(`term:data:${id}`, buf); buf = ''; timer = null;
    }, 16);
  });

  p.onExit(({ exitCode }) => {
    wc.send(`term:exit:${id}`, exitCode);
    sessions.delete(id);
  });

  sessions.set(id, p);
  return id;
});

ipcMain.on('term:input',  (_e, id, data)       => sessions.get(id)?.write(data));
ipcMain.on('term:resize', (_e, id, cols, rows) => sessions.get(id)?.resize(cols, rows));
ipcMain.on('term:kill',   (_e, id)             => sessions.get(id)?.kill());

// 창이 닫히면 자식 프로세스도 정리한다 — 안 하면 유령 셸이 남는다
app.on('before-quit', () => { for (const p of sessions.values()) p.kill(); });
16ms 배칭이 이 섹션의 핵심입니다. npm run build 한 번이 3만 줄을 뱉는 일은 흔합니다. 줄마다 IPC 를 보내면 초당 수천 번의 직렬화가 일어나 UI 가 멈춥니다. 모아 보내기 + 상한(512KB) 두 줄이 터미널 패널의 체감 품질을 결정합니다.

터미널을 열어 준다는 것의 무게

터미널 = 사용자 PC 에서 임의 명령 실행입니다. “버튼을 누르면 배포 스크립트가 도는” 사내 도구를 만들 때, 렌더러가 보낸 문자열을 그대로 셸에 넘기면 XSS 하나가 곧바로 원격 코드 실행이 됩니다.
위험 — 문자열을 셸에 통째로
ipcMain.handle('run', (_e, cmd) =>
  exec(cmd));            // 렌더러가 시키는 대로 다 한다
안전 — 명령은 메인이 정한다
const TASKS = {
  build:  ['npm', ['run', 'build']],
  deploy: ['node', ['scripts/deploy.js']],
} as const;

ipcMain.handle('run', (_e, key: keyof typeof TASKS) => {
  const t = TASKS[key];
  if (!t) throw new Error('unknown task');
  return execFile(t[0], t[1], { shell: false });
});
  • 셸을 통하지 않기 — execFile + shell:false
  • 작업 목록은 메인에 상수로 — 렌더러는 키만 보냅니다
  • 자유 터미널이 꼭 필요하면 기능 자체를 설정으로 잠글 수 있게 두세요
  • cwd 는 앱이 정한 작업 폴더로 고정 — 사용자 입력 경로는 검증
사내 도구 현실 조언 — 대부분의 요구는 “터미널”이 아니라 “정해진 스크립트 3개를 버튼으로” 입니다. 먼저 execFile + 로그 뷰로 만들고, 진짜 대화형이 필요할 때만 pty 를 붙이세요.

확장 시스템 — VS Code 가 안 죽는 이유

확장 5만 개가 도는데도 편집기가 멈추지 않는 것은 성능이 아니라 격리 설계 때문입니다. 남의 코드를 내 프로세스 밖에 두는 구조를 그대로 따라 만듭니다.

확장은 같은 프로세스에 들이지 않습니다. 남의 코드가 무한 루프를 돌아도 사용자가 잃는 건 “확장 기능”뿐입니다.

① 확장 호스트 띄우기

import { utilityProcess, MessageChannelMain } from 'electron';
import path from 'node:path';

let host: Electron.UtilityProcess | null = null;

function startHost() {
  const { port1, port2 } = new MessageChannelMain();

  host = utilityProcess.fork(path.join(__dirname, 'ext-host.js'), [], {
    serviceName: 'extension-host',
    // 확장은 앱 권한을 그대로 물려받으면 안 된다 — 환경 변수부터 줄인다
    env: { NODE_ENV: process.env.NODE_ENV ?? 'production' },
  });

  host.postMessage({ type: 'init' }, [port1]);   // 포트를 넘겨 직접 통신
  wireRenderer(port2);

  host.on('exit', (code) => {
    log.warn('extension host exited', code);
    if (code !== 0) setTimeout(startHost, 1000);  // 죽으면 되살린다
  });
}
utilityProcess 는 Chromium 이 관리하는 Node 프로세스입니다. child_process.fork 와 달리 앱이 죽으면 같이 정리되고 MessagePort 를 직접 주고받을 수 있어, 메인을 거치지 않는 렌더러 ↔ 확장 직통 채널을 만들 수 있습니다.

③ 확장에게 주는 API — 좁게, 검사하며

// ext-host.js — 확장이 import 하는 것은 '내가 만든 객체' 하나뿐
function makeApi(manifest: Manifest) {
  const can = (p: string) => manifest.permissions?.includes(p) ?? false;

  return Object.freeze({
    commands: {
      register(id: string, fn: () => void) {
        if (!id.startsWith(manifest.name + '.'))     // 남의 이름표 도용 금지
          throw new Error('command id must be prefixed');
        registry.set(id, guard(manifest, fn));
      },
    },
    workspace: {
      readFile: (p: string) => {
        if (!can('workspace.read')) throw new Error('permission denied');
        return rpc('workspace.readFile', p);          // 실제 IO 는 메인이 한다
      },
    },
    window: { showMessage: (m: string) => rpc('window.showMessage', m) },
  });
}

// 오래 잡아먹는 확장은 표시해 둔다 (VS Code 의 '확장 성능' 화면과 같은 원리)
function guard(m: Manifest, fn: Function) {
  return async (...a: unknown[]) => {
    const t = performance.now();
    try { return await fn(...a); }
    finally {
      const ms = performance.now() - t;
      if (ms > 100) telemetry.slowExtension(m.name, ms);
    }
  };
}

④ 설계할 때 미리 정해 둘 것

  • API 는 한 번 공개하면 못 지웁니다. 처음엔 다섯 개로 시작하세요 — 늘리는 건 쉽고 줄이는 건 불가능합니다
  • 버전 범위를 매니페스트에 강제(engines) — 안 맞으면 로드 거부하고 이유를 보여 줍니다
  • 확장 전용 저장소를 주세요(ctx.storagePath). 아니면 남의 설정 파일을 건드립니다
  • UI 는 직접 그리게 하지 마세요. DOM 접근을 열면 격리가 무의미해집니다 — 선언(메뉴·명령·뷰 타입)만 받고 그리는 것은 앱이 합니다
  • 느린 확장·죽은 확장 목록을 사용자에게 보여 주세요. “앱이 느리다”의 원인을 사용자가 스스로 찾습니다
사내 도구에서도 쓸모가 있습니다. 팀마다 다른 요구를 본체에 다 넣으면 앱이 무너집니다. “팀별 스크립트를 확장으로” 두면 본체는 안정적으로 두고 각 팀이 자기 속도로 붙일 수 있습니다.
남의 코드를 로드한다면 공급망 검토가 따라옵니다. 확장 설치 시 서명·해시 검증, 버전 고정, 사내 레지스트리를 함께 설계하세요 (🧬 전문가 탭 13 공급망 보안).

껐다 켰을 때 어제 그 자리, 그 문서가 그대로 있는 것 — 기능 목록에는 안 적히지만 “완성도”라고 부르는 것의 절반입니다.

창 위치 복원 — 모니터 검증이 핵심

import { screen, BrowserWindow } from 'electron';
import Store from 'electron-store';

const store = new Store<{ win: Rect & { max: boolean } }>();

function restoreBounds() {
  const s = store.get('win');
  const def = { width: 1280, height: 800 };
  if (!s) return def;

  // ★ 저장된 좌표가 '지금도 존재하는 화면' 안인지 확인한다.
  //   노트북에서 외부 모니터를 빼면 창이 화면 밖에 놓여 영영 안 보인다.
  const visible = screen.getAllDisplays().some(d => {
    const w = d.workArea;
    return s.x >= w.x - 40 && s.y >= w.y - 40 &&
           s.x + 80 <= w.x + w.width && s.y + 40 <= w.y + w.height;
  });
  return visible ? s : def;                 // 안 보이면 기본 위치로
}

const win = new BrowserWindow({ ...restoreBounds(), show: false });
if (store.get('win')?.max) win.maximize();
win.once('ready-to-show', () => win.show());   // 흰 화면 깜빡임 방지

// 저장은 몰아서 — resize 이벤트는 드래그 중 초당 수십 번 옵니다
let t: NodeJS.Timeout;
const save = () => {
  clearTimeout(t);
  t = setTimeout(() => {
    if (win.isDestroyed()) return;
    store.set('win', { ...win.getNormalBounds(), max: win.isMaximized() });
  }, 400);
};
win.on('resize', save);
win.on('move', save);
win.on('close', save);
getBounds() 가 아니라 getNormalBounds() 입니다. 최대화 상태에서 getBounds() 를 저장하면 “복원”을 눌렀을 때 크기가 화면 전체가 되어 원래 크기를 영영 잃습니다. 모니터 해제 검증과 함께, 버그 리포트가 가장 많이 오는 두 지점입니다.

import { safeStorage } from 'electron';

// OS 가 제공하는 암호화 (Keychain · DPAPI · libsecret)
function saveToken(t: string) {
  if (!safeStorage.isEncryptionAvailable()) return;   // 리눅스는 없을 수 있다
  store.set('tok', safeStorage.encryptString(t).toString('base64'));
}
function loadToken(): string | null {
  const b = store.get('tok');
  if (!b) return null;
  try { return safeStorage.decryptString(Buffer.from(b, 'base64')); }
  catch { store.delete('tok'); return null; }   // 다른 PC 로 복사된 경우
}
복원은 “실패해도 앱은 떠야” 합니다. 상태 파일이 깨졌을 때 시작 자체가 막히면 사용자는 재설치밖에 못 합니다. 복원 코드 전체를 try/catch 로 감싸고, 실패하면 파일을 .bak 으로 밀어내고 기본값으로 시작하세요.

오프라인 우선 · 동기화 설계

Slack·Notion 을 지하철에서 열어도 어제 대화가 보이고 글이 써집니다. 데스크탑 앱이 웹앱과 갈라지는 지점이자, 가장 자주 틀리는 설계입니다.

핵심은 순서입니다 — 로컬에 먼저 쓰고, 화면을 먼저 바꾸고, 네트워크는 나중에.

아웃박스 패턴 — 보낼 것을 DB 에 적는다

-- 로컬 SQLite (better-sqlite3 · node:sqlite)
CREATE TABLE messages (
  id          TEXT PRIMARY KEY,     -- 클라이언트가 만든 UUID
  room_id     TEXT NOT NULL,
  body        TEXT NOT NULL,
  created_at  INTEGER NOT NULL,
  server_seq  INTEGER,              -- NULL 이면 아직 서버가 모르는 것
  state       TEXT NOT NULL         -- pending | sent | failed
);
CREATE INDEX idx_msg_room ON messages(room_id, created_at);

CREATE TABLE outbox (
  id        TEXT PRIMARY KEY,
  op        TEXT NOT NULL,          -- create.message · update.doc ...
  payload   TEXT NOT NULL,          -- JSON
  tries     INTEGER NOT NULL DEFAULT 0,
  next_at   INTEGER NOT NULL        -- 지수 백오프용 시각
);
// 전송 = '로컬에 쓰기' 한 트랜잭션. 네트워크는 나중 일이다
const send = db.transaction((roomId: string, body: string) => {
  const id = crypto.randomUUID();
  db.prepare(`INSERT INTO messages
      (id,room_id,body,created_at,state) VALUES (?,?,?,?,'pending')`)
    .run(id, roomId, body, Date.now());
  db.prepare(`INSERT INTO outbox (id,op,payload,next_at) VALUES (?,?,?,?)`)
    .run(id, 'create.message', JSON.stringify({ id, roomId, body }), Date.now());
  return id;
});

// 화면은 로컬 DB 만 봅니다 — 네트워크 상태와 무관하게 항상 그려집니다
id 를 클라이언트가 만드는 것이 포인트입니다. 서버가 id 를 준다면 오프라인에서 글을 쓸 수 없습니다. UUID 를 클라이언트가 만들면 같은 요청을 두 번 보내도 서버가 중복을 걸러 낼 수 있어 (멱등성) 재시도가 안전해집니다.

플러시 루프 · 재연결

const BACKOFF = [1_000, 2_000, 5_000, 15_000, 60_000];

async function flush() {
  const now = Date.now();
  const rows = db.prepare(
    `SELECT * FROM outbox WHERE next_at <= ? ORDER BY next_at LIMIT 20`).all(now);

  for (const r of rows) {
    try {
      await api(r.op, JSON.parse(r.payload));       // 서버는 id 로 멱등 처리
      db.prepare(`DELETE FROM outbox WHERE id = ?`).run(r.id);
      db.prepare(`UPDATE messages SET state='sent' WHERE id = ?`).run(r.id);
    } catch (e) {
      const tries = r.tries + 1;
      const wait  = BACKOFF[Math.min(tries - 1, BACKOFF.length - 1)];
      // 4xx 는 재시도해도 소용없다 — 실패로 확정하고 사용자에게 알린다
      const fatal = e instanceof HttpError && e.status >= 400 && e.status < 500;
      if (fatal || tries > 12) {
        db.prepare(`DELETE FROM outbox WHERE id=?`).run(r.id);
        db.prepare(`UPDATE messages SET state='failed' WHERE id=?`).run(r.id);
      } else {
        db.prepare(`UPDATE outbox SET tries=?, next_at=? WHERE id=?`)
          .run(tries, now + wait, r.id);
      }
    }
  }
}

// 네트워크가 돌아오면 즉시 한 번 — 이벤트는 렌더러에서 받아 메인으로 넘긴다
setInterval(flush, 3_000);
ipcMain.on('net:online', () => flush());

// 서버는 단조 증가하는 seq(또는 커서)를 준다
async function pull() {
  const since = db.prepare(`SELECT COALESCE(MAX(server_seq),0) s FROM messages`)
                  .get().s;
  const { changes, nextSeq, reset } = await api('sync.pull', { since });

  if (reset) return fullResync();     // 서버가 '너무 오래됐다'고 하면 전체 재동기화

  db.transaction(() => {
    for (const c of changes) {
      if (c.deleted) db.prepare(`DELETE FROM messages WHERE id=?`).run(c.id);
      else db.prepare(`INSERT INTO messages (id,room_id,body,created_at,server_seq,state)
             VALUES (@id,@roomId,@body,@createdAt,@seq,'sent')
             ON CONFLICT(id) DO UPDATE SET
               body=excluded.body, server_seq=excluded.server_seq`).run(c);
    }
    db.prepare(`UPDATE meta SET cursor=?`).run(nextSeq);
  })();
}
