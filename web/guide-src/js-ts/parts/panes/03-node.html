NODE 01

Node 런타임 구조

“싱글 스레드”라는 말은 절반만 맞습니다. 실제 구조를 봅시다.

무엇으로 이루어져 있나

JS
내 코드 (자바스크립트) 메인 스레드 하나에서만 실행됩니다. 여기가 막히면 전부 멈춥니다.
▼
V8
V8 엔진 — 자바스크립트 실행 구글이 만든 엔진. 파싱·JIT 컴파일·GC 를 담당합니다(🧬 전문가 d01).
▼
libuv
libuv — 비동기 I/O 파일·DNS·압축 같은 작업을 스레드 풀(기본 4개)에서 대신 처리합니다. 네트워크는 OS 의 비동기 기능을 그대로 씁니다.
▼
OS
운영체제 epoll(Linux)·kqueue(macOS)·IOCP(Windows) — 실제 대기를 맡습니다.
정확히 말하면 — “내 자바스크립트 코드가 도는 스레드가 하나”입니다. 파일 읽기·압축·암호화는 libuv 스레드 풀에서 병렬로 처리됩니다. UV_THREADPOOL_SIZE 환경 변수로 늘릴 수 있습니다(기본 4).

언제 Node 를 고르나

잘 맞는 일
  • API 서버 (DB 조회가 대부분)
  • 여러 API 를 모아 주는 서버 (BFF)
  • 실시간 (WebSocket·SSE·채팅)
  • 프런트와 언어를 통일하고 싶을 때
  • 빠른 프로토타이핑
안 맞는 일
  • 이미지·영상 변환 (CPU 집약)
  • 대규모 수치 계산·머신러닝
  • 수십 GB 데이터 일괄 처리
  • 정밀한 소수 계산 (금융 코어)
  • 멀티코어를 다 써야 하는 작업
“안 맞는 일”도 방법은 있습니다. worker_threads(n09)로 별도 스레드에 넘기거나, 네이티브 애드온(sharp 는 C++ 로 이미지 처리)을 쓰거나, 아예 다른 서비스로 분리하면 됩니다. 문제는 모르고 메인 스레드에서 돌릴 때 생깁니다.

이벤트 루프 심화

🟨 JS j10 의 확장판. Node 만의 페이즈와 실무 측정법을 다룹니다.

libuv 의 6단계 페이즈

   ┌───────────────────────────┐
┌─>│  timers                   │  setTimeout · setInterval
│  ├───────────────────────────┤
│  │  pending callbacks        │  일부 시스템 에러 콜백
│  ├───────────────────────────┤
│  │  idle, prepare            │  내부용
│  ├───────────────────────────┤     ┌────────────────┐
│  │  poll                     │<────│  들어오는 I/O   │
│  ├───────────────────────────┤     └────────────────┘
│  │  check                    │  setImmediate
│  ├───────────────────────────┤
└──┤  close callbacks          │  socket.on("close")
   └───────────────────────────┘

★ 매크로태스크 콜백이 하나 끝날 때마다 마이크로태스크 큐를

NODE 05

스트림 · 버퍼

Node 의 가장 강력한 기능이자 가장 안 쓰이는 기능입니다.

왜 스트림인가

[통째로 읽기]  10GB 파일 → 메모리 10GB 필요 → 즉시 OOM
[스트림]       10GB 파일 → 64KB 씩 흘려보냄 → 메모리 수 MB

게다가 "첫 바이트가 도착하는 즉시" 처리를 시작할 수 있습니다.
파일 업로드·다운로드·CSV 처리·응답 압축이 전부 스트림입니다.

네 가지 종류

종류예
Readable파일 읽기, HTTP 요청 본문, process.stdin
Writable파일 쓰기, HTTP 응답, process.stdout
Duplex양방향 — TCP 소켓
Transform변환하며 통과 — gzip, 암호화, CSV 파싱

프레임워크 없이

import { createServer } from "node:http";

const server = createServer(async (req, res) => {
  // 라우팅을 직접 해야 합니다
  const url = new URL(req.url, `http://${req.headers.host}`);

  if (req.method === "GET" && url.pathname === "/health") {
    res.writeHead(200, { "Content-Type": "application/json" });
    return res.end(JSON.stringify({ ok: true }));
  }

  if (req.method === "POST" && url.pathname === "/api/users") {
    // ★ 본문도 직접 모아야 합니다 (스트림으로 옵니다)
    const chunks = [];
    for await (const c of req) chunks.push(c);
    const body = JSON.parse(Buffer.concat(chunks).toString());
    res.writeHead(201, { "Content-Type": "application/json" });
    return res.end(JSON.stringify({ id: 1, ...body }));
  }

  res.writeHead(404).end("Not Found");

비동기 동시 실행 제어

Promise.all 에 1,000개를 넣는 순간 상대 서버가 죽습니다.

문제 상황

// ❌ 10,000개 요청을 동시에 발사
await Promise.all(users.map(u => sendEmail(u)));

// 무슨 일이 일어나나
//   · 소켓 10,000개 동시 오픈 → EMFILE (파일 디스크립터 고갈)
//   · 메일 서버가 429/503 으로 차단
//   · 메모리에 10,000개의 Promise + 응답 버퍼
//   · DB 라면 커넥션 풀이 즉시 고갈
// ★ "동시에 몇 개까지" 를 반드시 정해야 합니다

직접 구현 — 개념 이해용

async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let index = 0;

  async function worker() {
    while (index < items.length) {
      const i = index++;                    // ★ 원자적으로 하나씩 가져감
      results[i] = await fn(items[i], i);
    }
  }

  await Promise.all(
    Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

await mapLimit(users, 10, sendEmail);       // 동시에 10개씩

// ② 처리되지 않은 Promise 거부 (Node 15+ 부터 기본이 crash)

f();                       // await 도 catch 도 없음 → 프로세스 종료

// ③ EventEmitter 의 error 이벤트에 리스너 없음
socket.emit("error", err);

// ④ 메모리 초과 (OOM)
// ⑤ 스택 오버플로 (무한 재귀)
// 최상위 안전망 — 로그를 남기고 "깨끗하게" 종료
process.on("uncaughtException", (err, origin) => {
  logger.fatal({ err, origin }, "처리되지 않은 예외");
  // 여기서 계속 돌리면 안 됩니다 — 상태를 신뢰할 수 없습니다
  gracefulExit(1);
});

process.on("unhandledRejection", (reason) => {
  logger.fatal({ reason }, "처리되지 않은 Promise 거부");
  gracefulExit(1);
});

function gracefulExit(code) {
  server.close(() => process.exit(code));
  setTimeout(() => process.exit(code), 5000).unref();
}
“죽지 않게 막는 것”이 목표가 아닙니다. 목표는 ① 원인을 로그로 남기고 ② 빠르게 재시작하는 것입니다. 예외가 새어 나온 프로세스는 메모리·커넥션 상태를 신뢰할 수 없습니다. PM2·K8s 가 즉시 다시 띄워 줍니다.

  • 무한히 커지는 Map/배열 — 캐시에 TTL·최대 크기가 없음
  • 해제 안 된 이벤트 리스너 — 요청마다 등록만 함

  • 클로저가 큰 객체를 붙잡음 — 응답 전체를 캡처한 콜백
  • 전역 변수 누적 — 요청 정보를 모듈 스코프에 저장

같은 서버, 세 가지 방식

// ① Node — server.mjs   $ node server.mjs
import { createServer } from "node:http";

createServer((req, res) => {
  res.writeHead(200, { "content-type": "application/json" });
  res.end(JSON.stringify({ runtime: "node", v: process.version }));
}).listen(3000);
// ② Deno — server.ts   $ deno run --allow-net server.ts
Deno.serve({ port: 3000 }, (_req: Request) =>
  Response.json({ runtime: "deno", v: Deno.version.deno }));
// ★ TS 를 그대로 실행합니다. 빌드 단계가 없습니다.
// ③ Bun — server.ts   $ bun server.ts
Bun.serve({
  port: 3000,
  fetch: (_req: Request) => Response.json({ runtime: "bun", v: Bun.version }),
});
// ★ Deno·Bun 은 둘 다 "요청 → Response 반환" 이라는
//   표준 Fetch 모델을 씁니다. Hono 같은 프레임워크가
//   세 런타임에서 같은 코드로 도는 이유입니다.

Bun — 진짜 강점과 아직 조심할 점

실제로 체감되는 것
  • 설치 속도 — bun install 이 npm 대비 몇 배. CI 캐시 미스 때 차이가 가장 큽니다
  • 번들러·테스트러너 내장 — tsup·vitest·tsx 를 한꺼번에 걷어냅니다
  • 기동 시간 — 짧은 CLI·스크립트·서버리스에서 유리
  • bun --hot — 프로세스 재시작 없는 리로드
아직 걸리는 것
  • 네이티브 애드온(N-API) 호환 — sharp·bcrypt·node-gyp 계열이 버전에 따라 깨집니다 ★
  • Node 내부 API 를 파고드는 라이브러리(APM 에이전트·일부 ORM)
  • 프로파일링·힙 스냅샷 도구가 V8 생태계만큼 성숙하지 않음
  • 사내 표준·클라우드 런타임이 Node 만 지원하는 경우
가장 안전한 Bun 도입법 — 런타임은 Node 로 두고 패키지 매니저·테스트러너만 Bun 으로 바꾸는 것입니다(bun install + bun test). 위험은 거의 없고 CI 시간은 바로 줄어듭니다.

Deno 2 — 권한 모델이 핵심

# Deno 는 "기본값이 아무것도 못 함" 입니다
deno run server.ts                    # ❌ 네트워크 접근에서 즉시 거부
deno run --allow-net=:3000 server.ts  # 포트만 열어 줌
deno run --allow-read=./data \
         --allow-env=PORT,DATABASE_URL \
         --allow-net=api.example.com server.ts   # ★ 화이트리스트

deno run -A server.ts                 # 전부 허용 — 편하지만 의미가 사라집니다

# npm 패키지를 그대로 (Deno 2)
import express from "npm:express@5";
deno install                          # package.json · node_modules 인식
권한 모델은 “공급망 방어”가 목적입니다. 악성 postinstall 이나 오염된 트랜지티브 의존성이 토큰을 읽어 외부로 보내는 시나리오를 런타임이 막아 줍니다(🧬 전문가 d13). -A 로 시작해 놓고 끝까지 안 좁히면 Node 와 다를 게 없습니다.
