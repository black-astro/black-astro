SETUP 01

무엇을 깔아야 하나 — 사실 처음엔 아무것도

자바스크립트는 이미 여러분 PC 에 깔려 있습니다. 크롬·엣지·사파리 안에 엔진이 들어 있으니까요. 그런데도 node 를 까는 이유가 분명히 있습니다. 그 경계선부터 그어 두면 나머지 설치가 전부 “왜”가 붙은 채로 이해됩니다.

설치는 필요가 생겼을 때 하면 됩니다 — 처음부터 다 깔아 두는 것이 오히려 혼란의 원인입니다.

① 설치 0 단계 — 브라우저 콘솔

크롬·엣지에서 F12(맥은 Cmd+Option+I)를 누르고 Console 탭을 열면 그 자리가 자바스크립트 실행기입니다. 파이썬의 python REPL 과 같은 것이 이미 깔려 있는 셈입니다. 

// 콘솔에 그대로 붙여 넣어 보세요
1 + 1                       // 2
[1,2,3].map(n => n * 2)     // [2, 4, 6]
await fetch("/").then(r => r.status)   // ★ 콘솔은 최상위 await 이 됩니다

// 여러 줄을 쓸 때는 Shift+Enter 로 줄바꿈
function hello(name) {
  return `안녕하세요 ${name}`;
}
hello("김현우")
콘솔보다 편한 자리 — Sources ▸ Snippets
개발자도구 Sources 탭 왼쪽의 Snippets 에 코드를 저장해 두면 Ctrl+Enter 로 몇 번이고 다시 실행할 수 있습니다. 파일을 만들지 않고 수십 줄짜리 연습을 하기에 딱 좋습니다.
브라우저에서 절대 안 되는 것 — fs.readFile 로 내 PC 파일 읽기, 서버 열기(listen), npm install 로 받은 패키지 쓰기, DB 접속. 전부 보안상 막혀 있습니다. 이 중 하나가 필요해지는 순간이 Node 를 깔 때입니다.

npm패키지 관리자. Node 설치에 같이 들어옵니다
npx설치하지 않고 한 번만 실행. npm 에 딸려 옴
corepackpnpm·yarn 을 켜 주는 중개자. Node 에 동봉
# 설치 후 이 네 줄이 다 대답하면 성공입니다
node -v          # v24.x.x
npm -v           # 11.x.x
npx -v           # 11.x.x
corepack -v      # 0.3x.x

“npm 도 따로 깔아야 하나요” — 아닙니다. Node 설치 프로그램 하나에 node · npm · npx · corepack 이 전부 들어 있습니다. 파이썬에서 python 과 pip 가 같이 오는 것과 같습니다.

런타임 셋 비교 — Node · Bun · Deno 🟢 기초

Node 24 LTS ★ Bun 1.x Deno 2
한 줄 정체 사실상의 표준. 2009년부터 속도로 승부하는 신형 Node 만든 사람이 만든 재설계판
패키지 npm (+pnpm·yarn 선택) bun install 내장 · 매우 빠름 npm 호환 + JSR
TypeScript 타입 지우기는 기본 지원(st07) 그냥 bun a.ts 로 실행 그냥 deno run a.ts
내장 도구 --test · --watch · --env-file 테스트 · 번들러 · 실행기 전부 테스트 · 포맷 · 린트 · 컴파일
권한 제한 없음 (실험적 권한 모델 있음) 제한 없음 기본 차단 · --allow-net 로 허용
회사에서 쓰나 거의 전부 — 배포·모니터링 생태계 완비 늘고 있지만 아직 소수 소수 · 사내 도구 위주

2026년의 정답은 여전히 Node 입니다. Bun 과 Deno 는 훌륭하지만, 회사 코드베이스 · CI · 도커 이미지 · 배포 플랫폼 · 채용 공고가 전부 Node 를 전제로 움직입니다. Bun 은 “빠른 npm install 대체”나 “tsx 없이 TS 스크립트 실행” 용도로 Node 와 같이 깔아 두는 것이 실용적입니다. 둘을 동시에 깔아도 서로 방해하지 않습니다.

Windows 설치 — .msi 마법사 를 한 화면씩

화면에 무엇이 뜨는지, 어느 체크박스를 켜고 어느 것을 끄는지, 설치가 끝난 뒤 무엇으로 확인하는지까지 그대로 따라갈 수 있게 적었습니다. 5분이면 끝납니다.

설치 확인 — 여기까지 되면 성공입니다 🟢 기초

확인 스크립트 — 그대로 복사

# PowerShell 을 "새로" 열고 (기존 창 말고)
node -v            # v24.9.0
npm -v             # 11.6.0
npx -v             # 11.6.0
corepack -v        # 0.34.0

# 실제로 코드가 도는지
node -e "console.log('설치 완료:', process.version, process.platform)"
# → 설치 완료: v24.9.0 win32

# 어느 파일이 실행되고 있는지 (★ 문제 생겼을 때 제일 먼저 볼 것)
where.exe node
# C:\Program Files\nodejs\node.exe

# 첫 파일 실행
"console.log('hello')" | Out-File -Encoding utf8 hello.js
node hello.js      # hello
PowerShell 에서 where 는 쓰지 마세요. PowerShell 의 where 는 Where-Object 의 별칭이라 전혀 다른 동작을 합니다. where.exe node 처럼 확장자를 붙이거나 Get-Command node 를 쓰세요.

첫 프로젝트를 30초 만에

mkdir hello-node
cd hello-node

npm init -y                    # package.json 생성
npm pkg set type=module        # ★ import 문법을 쓰겠다는 선언

# src/index.js 를 만들고 아래 내용을 넣습니다
node --watch src/index.js      # 저장할 때마다 자동 재시작
// src/index.js
import os from "node:os";
import { readFile } from "node:fs/promises";

console.log("Node", process.version);
console.log("CPU", os.cpus().length, "코어");

const pkg = JSON.parse(
  await readFile("./package.json", "utf8")   // ★ 브라우저에서는 불가능한 일
);
console.log("프로젝트 이름:", pkg.name);
이 코드가 브라우저와 다른 점 — node:fs 로 내 PC 파일을 읽고, node:os 로 CPU 개수를 봅니다. 이것 하나로 Node 를 깐 값은 다 했습니다. 나머지 섹션은 이 환경을 여럿이 · 오래 · 여러 프로젝트로 쓰기 위한 정비입니다.
설치 직후 가장 흔한 사고 세 가지
① 'node'은(는) 내부 또는 외부 명령이 아닙니다 — 열려 있던 터미널을 닫고 새로 여세요. 그래도 안 되면 PATH 문제입니다(st05).
② npx : 이 시스템에서 스크립트를 실행할 수 없으므로 — PowerShell 실행 정책입니다(st05). 명령 한 줄로 해결됩니다.
③ VS Code 내장 터미널에서만 안 됨 — VS Code 를 완전히 종료했다가 다시 켜세요. 편집기가 켜질 때의 PATH 를 그대로 물고 있습니다.

   C:\Users\사용자\.npmrc          ← 프록시·토큰 설정. 필요하면 백업

③ 환경 변수에서 위 경로가 남아 있으면 제거 (st05)

④ 새 터미널에서 node -v 가 "명령이 아닙니다" 를 내면
   완전히 지워진 것입니다

정리 — nodejs.org 왼쪽 LTS 버튼 → .msi 실행 → Add to PATH 켜 두고 Tools for Native Modules 는 끄고 다음 → 새 터미널에서 node -v. 안 되면 대부분 터미널을 새로 안 연 것입니다.
SETUP 03

버전 관리자 — fnm · nvm · Volta 로 갈아 끼우기

프로젝트 A 는 Node 20 을 요구하고 B 는 24 를 요구합니다. 시스템에 하나만 깔려 있으면 지울 때마다 다시 깔아야 합니다. 버전 관리자는 이 문제를 폴더 단위로 해결합니다.

핵심은 PATH 맨 앞자리를 차지하는 것입니다 — 원리를 알면 “왜 안 바뀌지”도 스스로 풀 수 있습니다.

SETUP 04

macOS · Linux — Homebrew · apt · fnm 중 무엇으로

유닉스 계열에서는 선택지가 더 많고, 그래서 잘못 고르면 sudo 지옥에 빠집니다. 실제로 초보가 가장 많이 하는 실수인 sudo npm install -g 가 왜 위험한지도 여기서 정리합니다.

설치 위치가 시스템이냐 홈이냐가 갈림길입니다 — sudo 문제의 90%가 여기서 결정됩니다.

macOS — 세 가지 방법

# ── ① Homebrew (가장 흔함) ──
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install node@24            # 메이저 고정 ★ (그냥 node 면 최신 Current)
brew link --overwrite node@24   # PATH 에 연결

# Apple Silicon 은 /opt/homebrew, 인텔 맥은 /usr/local 입니다
brew --prefix                   # 내 맥이 어느 쪽인지

# ── ② fnm (권장) ──
brew install fnm
echo 'eval "$(fnm env --use-on-cd --shell zsh)"' >> ~/.zshrc
exec zsh                        # 셸 다시 읽기
fnm install 24 && fnm default 24

# ── ③ 공식 .pkg ──
# nodejs.org 에서 node-v24.x.x.pkg 를 받아 실행
# → /usr/local/bin/node 에 깔립니다. 지우기가 번거로우니 권하지 않습니다
맥에서 zsh: command not found: node — Apple Silicon 에서 Homebrew 경로가 ~/.zprofile 에 안 들어간 경우입니다. echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile 을 실행하고 터미널을 새로 여세요.

node -v      # v18.x — 우분투 22.04 기준. 이미 EOL 입니다

WSL2 를 쓴다면 — 윈도우 쪽 Node 와 완전히 별개로 리눅스용 Node 를 깔아야 합니다. WSL 터미널에서 /mnt/c/Program Files/nodejs/node.exe 가 잡히면 속도가 수십 배 느려지고 경로 문제가 끝없이 납니다. WSL 안에서는 위의 fnm 방법으로 따로 깔고, 프로젝트도 /home/… 안에 두세요.

★ sudo npm install -g 는 왜 금지인가 🟢 기초

❌ 이렇게 하면 벌어지는 일
sudo npm install -g typescript

# 그 결과
#  · /usr/local/lib/node_modules 안의 파일 소유자가 root 가 됩니다
#  · 다음번에 sudo 없이 설치하면 EACCES 로 실패
#  · 그래서 또 sudo 를 붙이는 악순환
#  · 패키지의 postinstall 스크립트가 root 권한으로 실행됩니다
#    → 악성 패키지 하나면 시스템 전체가 넘어갑니다 ★
#  · 캐시(~/.npm)도 root 소유로 바뀌어
#    이후 모든 npm 명령이 권한 오류를 냅니다
✅ 대신 이렇게
# 방법 ① 버전 관리자를 씁니다 — 문제 자체가 사라집니다
fnm install 24
npm i -g typescript          # sudo 없이 됩니다 (홈 디렉터리)

# 방법 ② 전역 설치 경로를 홈으로 옮깁니다
mkdir -p ~/.npm-global
npm config set prefix ~/.npm-global
echo 'export PATH="$HOME/.npm-global/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

# 방법 ③ 애초에 전역 설치를 안 합니다 ★ 가장 좋음
npx tsc --version
pnpm add -D typescript && pnpm exec tsc --version

이미 sudo 로 망가뜨렸다면 — 복구 절차

# ① 캐시 소유권을 나에게 돌려놓기
sudo chown -R $(id -u):$(id -g) ~/.npm

# ② 홈 안의 프로젝트 폴더도 확인
sudo chown -R $(id -u):$(id -g) ~/work/my-app/node_modules

# ③ root 소유가 된 전역 폴더는 통째로 지우고 다시 시작
sudo rm -rf /usr/local/lib/node_modules
npm config set prefix ~/.npm-global

# ④ 어떤 것이 root 소유인지 미리 보기
ls -la $(npm root -g)
ls -la ~/.npm | head

# ★ 정리 후에는 npm config get prefix 가
#   홈 디렉터리 아래를 가리켜야 정상입니다
판별법 — npm config get prefix 결과가 /usr 나 /usr/local 로 시작하면 언젠가는 sudo 를 요구합니다. /home/… 나 ~/.local/… 이면 안전합니다.

리눅스 서버에 올릴 때의 정석

개발 머신          → fnm (홈 · 여러 버전)
CI (GitHub Actions) → actions/setup-node@v4
운영 서버          → 도커 이미지 node:24-alpine
                     또는 NodeSource + systemd
# .github/workflows/ci.yml — CI 에서 버전 맞추기
- uses: actions/setup-node@v4
  with:
    node-version-file: '.node-version'   # ★ 파일을 그대로 읽습니다
    cache: 'pnpm'

# Dockerfile — 멀티스테이지의 기본형
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:24-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
세 곳의 버전을 한 파일로 묶는 것이 핵심입니다. .node-version 하나만 고치면 개발 머신(fnm) · CI(setup-node) 가 동시에 따라옵니다. 도커 태그만 수동이므로 Dockerfile 도 같이 바꾸는 것을 체크리스트에 넣어 두세요.
정리 — 맥·리눅스에서는 어디에 깔리느냐가 전부입니다. 홈 디렉터리에 깔리는 fnm 을 쓰면 sudo 문제가 원천적으로 사라집니다. sudo npm i -g 는 절대 쓰지 마세요 — 권한이 꼬이고 보안 구멍이 됩니다. 서버는 NodeSource 또는 도커 이미지로 메이저 버전을 고정합니다.
SETUP 05

PATH · 환경 변수 — “명령을 찾을 수 없습니다” 의 정체

설치 관련 질문의 절반은 PATH 입니다. 원리는 세 줄이면 끝나고, 알고 나면 다시는 같은 문제로 검색하지 않게 됩니다. 화면 경로까지 그대로 적었습니다.

PATH 는 우선순위가 있는 폴더 목록일 뿐입니다 — 앞에 있는 것이 이깁니다.

윈도우 — 환경 변수 화면까지 가는 길

방법 A — 검색으로 (가장 빠름)
  시작 버튼 → "환경 변수" 입력
  → "시스템 환경 변수 편집" 또는
    "계정의 환경 변수 편집" 클릭

방법 B — 손으로
  Win + R → sysdm.cpl → Enter
  → [고급] 탭 → 아래쪽 [환경 변수(N)...] 버튼

들어가면 창이 위아래 둘로 나뉩니다
  ┌ 사용자 변수 (내 계정에만 적용) ★ 여기를 씁니다
  └ 시스템 변수 (모든 계정 · 관리자 권한 필요)

  위쪽 목록에서 Path 를 고르고 [편집(E)...]
  → [새로 만들기(N)] → 경로를 붙여 넣기
  → [위로 이동(U)] 으로 순서 조정
  → 확인 · 확인 · 확인 (창 세 개를 다 확인으로 닫아야 저장됩니다) ★
가장 흔한 실수 두 가지
① 창을 X 로 닫으면 저장이 안 됩니다 — 반드시 [확인]으로.
② 저장해도 이미 열린 터미널·VS Code 에는 반영되지 않습니다. 새 창을 열거나, 심하면 로그아웃 후 다시 로그인 해야 합니다.

PowerShell 로 확인하고 고치기

"express": "~5.1.0"

"express": "5.1.0"
   정확히 그 버전만

"express": "*"        아무거나 — 절대 쓰지 마세요
"express": "next"     태그 지정

   "^0.3.1" → 0.3.1 이상 0.4.0 미만 (마이너도 안 올림)

    "module": "NodeNext",          // Node 의 ESM/CJS 규칙을 따름
    "moduleResolution": "NodeNext",// import 경로를 어떻게 찾을까
    "lib": ["ES2023"],             // 쓸 수 있는 내장 API 목록

    "strict": true,                // ★ 이것 하나가 TS 의 절반입니다
    "noUncheckedIndexedAccess": true, // arr[0] 이 undefined 일 수 있음
    "verbatimModuleSyntax": true,  // import type 을 명시하게 강제

    "outDir": "dist",
    "rootDir": "src",
    "sourceMap": true,             // 디버거가 .ts 줄을 보여 줍니다
    "skipLibCheck": true,          // node_modules 타입은 검사 생략 (빠름)
    "esModuleInterop": true
  },
  "include": ["src"],
  "exclude": ["node_modules", "dist"]
}
strict: true 는 절대 끄지 마세요. 끄면 null·undefined 검사가 사라져서 “타입스크립트를 쓰는데도 Cannot read properties of undefined” 가 계속 납니다. 기존 코드가 너무 많아 부담되면 strict 를 켜고 "strictNullChecks": false 부터 하나씩 되돌리는 편이 낫습니다.

  • 설정 파일 개수를 줄이고 싶다
  • 린트가 느려서 아무도 안 돌린다 (Rust 라 수십 배 빠릅니다)

import path from "node:path";

  resolve: {
    alias: {

    },
  },

      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true,
      },
    },
  },

  build: {
    outDir: "dist",
    sourcemap: true,     // 배포 후 에러 추적용
  },
});
