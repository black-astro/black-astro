TOOL 01

패키지 매니저

팀에서 하나만 정해서 쓰세요. 섞이면 lock 파일이 충돌합니다.

비교

도구특징
npm기본 내장. 무난. 팀에 특별한 요구가 없으면 이걸로 충분
pnpm디스크 절약 + 빠름. 하드링크로 중복 제거. 모노레포에 강함 — 신규 프로젝트 추천
yarn (berry)PnP 등 고급 기능. 설정이 까다로워 호불호가 갈립니다
bun매우 빠르지만 런타임까지 바꾸는 선택. 아직 신중히
# pnpm — 요즘 신규 프로젝트의 기본
corepack enable                        # Node 내장 (별도 설치 불필요)
pnpm install
pnpm add express
pnpm add -D typescript
pnpm dlx create-vite                   # npx 에 해당

# ★ 팀에 패키지 매니저를 강제하기
# package.json
{ "packageManager": "pnpm@9.12.0" }    # corepack 이 버전까지 맞춰 줍니다
lock 파일은 반드시 커밋하세요. 없으면 사람마다·서버마다 다른 버전이 설치되어 “내 PC 에서는 되는데” 문제가 생깁니다. package-lock.json·pnpm-lock.yaml 중 쓰는 것 하나만 남기세요.

install vs ci

npm install     # lock 을 "고칠 수 있음" — 개발용
npm ci          # ★ lock 그대로, node_modules 삭제 후 재설치
                #   CI·Docker 는 반드시 이것 (재현성 + 속도)

pnpm install --frozen-lockfile         # pnpm 의 ci 에 해당

npm outdated                           # 오래된 패키지
npm audit                              # ★ 취약점 검사 (CI 에 포함)
npm ls some-pkg                        # 왜 설치됐는지 추적
npm why some-pkg                       # (pnpm) 의존 경로

의존성을 늘리기 전에

  • 내장 기능으로 되는가? — UUID·날짜 포맷·깊은 복사·fetch 는 이제 전부 내장(🟩 Node n14)
  • 마지막 업데이트가 1년 이상 전이면 재검토
  • 이 패키지가 또 몇 개를 끌고 오는지 확인
  • 번들 크기가 중요한 프런트엔드라면 bundlephobia 로 확인
  • postinstall 스크립트가 있는지 — 공급망 공격의 주요 통로(🧬 d13)
버전 고정 전략 — 애플리케이션은 ^ 로 두고 lock 으로 고정, 라이브러리는 범위를 넓게 두어 사용자와 충돌하지 않게 합니다. renovate·dependabot 으로 자동 PR 을 받으면 업데이트를 미루다 한꺼번에 터지는 일을 막습니다.
TOOL 02

모노레포

프런트·백엔드·공통 타입을 한 저장소에서 관리합니다.

언제 쓰나

모노레포가 유리
  • 프런트·백엔드가 타입·스키마를 공유
  • 같은 팀이 여러 앱을 함께 배포
  • 공통 UI·유틸 패키지가 있음
  • 한 번에 걸친 변경이 잦음
분리가 나은 경우
  • 팀·배포 주기가 완전히 다름
  • 저장소 권한을 나눠야 함
  • CI 시간이 길어져 감당 안 됨
  • 구성원이 도구에 익숙하지 않음
my-repo/
  pnpm-workspace.yaml
  package.json                 루트 (공통 devDependencies)
  apps/
    api/                       NestJS 서버
    web/                       React 프런트
    mobile/                    React Native
  packages/
    schema/                    ★ Zod 스키마 + 타입 (양쪽에서 import)
    ui/                        공통 컴포넌트
    config/                    eslint · tsconfig 공유 설정
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

Turborepo — 빌드 캐시

pnpm add -Dw turbo
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],        // ★ 의존 패키지를 먼저 빌드
      "outputs": ["dist/**"]
    },
    "test":      { "dependsOn": ["build"] },
    "typecheck": { "dependsOn": ["^build"] },
    "dev":       { "cache": false, "persistent": true }
  }
}
turbo build                    # 바뀐 것만 빌드 (캐시 활용)
turbo build --filter=api       # 특정 앱만
turbo build --filter=...[HEAD^]  # 변경된 것과 그 의존만 ★ CI 에서 유용

# 효과: 안 바뀐 패키지는 캐시에서 즉시 복원 → CI 시간이 크게 줄어듭니다
// apps/api/package.json — 내부 패키지 참조
{
  "dependencies": {
    "@repo/schema": "workspace:*"     // ★ pnpm 워크스페이스 프로토콜
  }
}
// 이렇게 쓰면 프런트·백엔드가 같은 타입을 봅니다
import { CreateUserSchema, type CreateUser } from "@repo/schema";

// 서버: 검증
const dto = CreateUserSchema.parse(req.body);
// 프런트: 폼 검증 + 타입
const form = useForm<CreateUser>({ resolver: zodResolver(CreateUserSchema) });
모노레포의 진짜 가치가 여기 있습니다. API 응답 형태를 바꾸면 프런트엔드가 컴파일 에러로 알려 줍니다. “배포하고 나서야 깨진 걸 아는” 상황이 사라집니다.
TOOL 03

번들러 · 빌드

목적에 따라 도구가 다릅니다. 고민 시간을 줄이는 표부터.

무엇을 언제

도구용도
Vite프런트엔드 앱 — 개발 서버가 매우 빠름. 사실상 표준
tsup라이브러리 — ESM+CJS+d.ts 를 한 번에. 설정이 거의 없음
tscNode 서버 — 그냥 컴파일만 하면 될 때
esbuild매우 빠른 저수준 번들러 (위 도구들의 내부 엔진)
Rollup / Rolldown라이브러리 번들의 전통 강자 / 차세대 (Vite 가 채택 중)
webpack레거시 유지보수 외에는 신규 채택 이유가 줄었습니다
// vite.config.ts — 프런트엔드
export default defineConfig({
  plugins: [react()],
  resolve: { alias: { "@": path.resolve(__dirname, "src") } },
  server: {
    port: 5173,
    proxy: { "/api": { target: "http://localhost:3000", changeOrigin: true } },
  },
  build: {
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks: {                 // ★ 자주 안 바뀌는 것을 분리 → 캐시 효율
          vendor: ["react", "react-dom"],
        },
      },
    },
  },
});

라이브러리 빌드 — tsup

// tsup.config.ts
export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm", "cjs"],       // ★ 양쪽 지원 (🟨 JS j09)
  dts: true,                     // 타입 선언 자동 생성
  sourcemap: true,
  clean: true,
  treeshake: true,
  external: ["react"],           // ★ peer 의존성은 번들에 넣지 않기
});
// package.json — 진입점 정의
{
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"],             // ★ 배포에 포함할 것만
  "sideEffects": false           // 트리셰이킹 허용 신호
}

서버는 번들이 필요할까

대부분 필요 없습니다 — tsc 로 컴파일만 하면 충분합니다.

번들이 유용한 경우
  · 서버리스(Lambda) — 콜드 스타트를 줄여야 할 때
  · 단일 파일 배포가 필요할 때
  · 컨테이너 이미지를 극단적으로 줄일 때

주의: 네이티브 모듈(bcrypt·sharp·better-sqlite3)은
      번들에 포함되지 않습니다 → external 로 빼야 합니다
빌드가 느려졌다면 원인은 대개 타입 검사입니다. esbuild·swc 는 타입을 검사하지 않고 지우기만 합니다. tsc --noEmit 을 별도 스크립트로 분리해 빌드와 병렬로 돌리는 것이 실무 표준입니다.

ESLint · Prettier · Biome

코드 스타일 논쟁을 도구에게 넘기세요.

ESLint 9 — flat config

npm i -D eslint typescript-eslint eslint-config-prettier
// eslint.config.js  (ESLint 9 부터 이 형식입니다)
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import prettier from "eslint-config-prettier";

export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,   // ★ 타입 정보를 쓰는 규칙
  {
    languageOptions: {
      parserOptions: { projectService: true },
    },
    rules: {
      "@typescript-eslint/no-floating-promises": "error",   // ★ await 빠뜨림 방지
      "@typescript-eslint/no-misused-promises": "error",
      "@typescript-eslint/no-unused-vars": ["warn", { argsIgnorePattern: "^_" }],
      "no-console": ["warn", { allow: ["warn", "error"] }],
      eqeqeq: ["error", "always"],
    },
  },
  { ignores: ["dist/**", "coverage/**"] },

no-floating-promises 는 켤 가치가 큽니다. await 를 빠뜨린 Promise 는 조용히 실패하고 Node 프로세스를 죽일 수도 있습니다(🟨 JS j11). 이 규칙 하나가 실제 버그를 여러 개 잡아 줍니다.

테스트 — Vitest

테스트가 빨라야 사람들이 돌립니다.

설정

npm i -D vitest @vitest/coverage-v8
// vitest.config.ts
export default defineConfig({
  test: {
    globals: true,                    // describe·it 을 import 없이
    environment: "node",              // 프런트엔드면 "jsdom"
    setupFiles: ["./test/setup.ts"],
    coverage: {
      provider: "v8",
      reporter: ["text", "lcov"],
      exclude: ["**/*.config.*", "**/dist/**"],
    },
    // 통합 테스트는 순차로 (DB 충돌 방지)
    poolOptions: { threads: { singleThread: false } },
  },
});
import { describe, it, expect, vi, beforeEach } from "vitest";

describe("OrderService", () => {
  const repo = { save: vi.fn(), findById: vi.fn() };
  const service = new OrderService(repo as any);

  beforeEach(() => vi.clearAllMocks());

  it("재고가 부족하면 주문이 실패한다", async () => {
    repo.findById.mockResolvedValue({ stock: 0 });
    await expect(service.create({ productId: 1, qty: 1 }))
      .rejects.toThrow(OutOfStockError);
    expect(repo.save).not.toHaveBeenCalled();
  });

  it("시간에 의존하는 로직", () => {
    vi.useFakeTimers();
    vi.setSystemTime(new Date("2026-08-04"));
    expect(isExpired(order)).toBe(true);
    vi.useRealTimers();
  });
});

모킹을 너무 많이 하면 테스트가 의미를 잃습니다. 전부 가짜로 바꾸면 “내가 짠 mock 이 잘 도는지” 를 검증할 뿐입니다. DB 는 Testcontainers 로 진짜를 쓰고, 외부 API 만 모킹하는 것이 균형점입니다.

무엇을 테스트할까

  • 돈·권한·재고 관련 로직 — 반드시
  • 버그가 났던 곳 — 재발 방지 테스트를 먼저
  • 복잡한 분기·계산 — 할인·정산·유효기간
  • 단순 CRUD·getter — 안 해도 됩니다
커버리지 숫자를 목표로 삼지 마세요. 80% 를 맞추려고 의미 없는 테스트를 양산하게 됩니다. “이 코드가 깨지면 서비스에 무슨 일이 생기나”를 기준으로 고르세요.

E2E — Playwright

진짜 브라우저로 사람이 하듯 클릭해 봅니다.

기본

npm init playwright@latest
import { test, expect } from "@playwright/test";

test("로그인 후 주문을 생성한다", async ({ page }) => {
  await page.goto("/login");

  // ★ 접근성 기준으로 찾으세요 (CSS 선택자보다 훨씬 안 깨집니다)
  await page.getByLabel("이메일").fill("test@example.com");
  await page.getByLabel("비밀번호").fill("password123");
  await page.getByRole("button", { name: "로그인" }).click();

  await expect(page).toHaveURL("/dashboard");
  await expect(page.getByText("환영합니다")).toBeVisible();

  await page.getByRole("link", { name: "주문하기" }).click();
  await page.getByRole("button", { name: "결제" }).click();

  await expect(page.getByRole("alert")).toContainText("주문이 완료");
});
// playwright.config.ts
export default defineConfig({
  testDir: "./e2e",
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,          // ★ CI 에서만 재시도
  use: {
    baseURL: "http://localhost:5173",
    trace: "on-first-retry",                // ★ 실패 시 재현 자료
    screenshot: "only-on-failure",
    video: "retain-on-failure",
  },
  webServer: {                               // 테스트 전 서버 자동 실행
    command: "npm run dev",
    port: 5173,
    reuseExistingServer: !process.env.CI,
  },
  projects: [
    { name: "chromium", use: devices["Desktop Chrome"] },
    { name: "mobile", use: devices["iPhone 14"] },
  ],

E2E 테스트를 너무 많이 만들지 마세요. 느리고, 깨지기 쉽고(flaky), 유지보수 비용이 큽니다. 핵심 흐름 5~10개만 — 로그인·결제·주문 같은 “이게 깨지면 서비스가 죽는” 경로에 집중하세요. 
npx playwright test                    # 실행
npx playwright test --ui               # ★ UI 모드 — 단계별로 보며 디버깅
npx playwright codegen localhost:5173  # ★ 조작을 코드로 기록
npx playwright show-report
codegen 으로 시작하세요. 브라우저에서 직접 클릭하면 테스트 코드가 자동으로 만들어집니다. 거기서 다듬는 편이 처음부터 손으로 쓰는 것보다 훨씬 빠릅니다.

Zod — 런타임 검증

타입은 실행 중에는 사라집니다. 바깥에서 오는 값은 다시 확인해야 합니다.

어디에 쓰나

  • API 요청 본문·쿼리 (🚂 Express x05)
  • 환경 변수 — 부팅 시 검증 (🟩 Node n08)
  • 외부 API 응답 — 상대가 형태를 바꿔도 즉시 발견
  • localStorage·설정 파일 — 옛 버전 데이터가 남아 있을 수 있음
  • 폼 입력 — react-hook-form 과 연동
import { z } from "zod";

export const OrderSchema = z.object({
  id: z.string().uuid(),
  amount: z.number().int().positive(),
  status: z.enum(["PENDING", "PAID", "CANCELLED"]),
  items: z.array(z.object({
    productId: z.number(),
    qty: z.number().int().min(1).max(99),
  })).min(1, "상품을 하나 이상 선택하세요"),
  memo: z.string().max(500).optional(),
  createdAt: z.coerce.date(),          // ★ 문자열 → Date 자동 변환
});

export type Order = z.infer<typeof OrderSchema>;   // ★ 타입 자동 생성

// 사용
const result = OrderSchema.safeParse(input);
if (!result.success) {

  return;
}
result.data.amount;                     // number 로 확정

// fetch 를 감싸는 얇은 클라이언트 — 실무에서 이 정도면 충분합니다
async function api<T>(path: string, init?: RequestInit & { schema?: ZodType<T> }) {
  const res = await fetch(`${BASE}${path}`, {
    ...init,
    headers: { "Content-Type": "application/json", ...init?.headers },
    signal: init?.signal ?? AbortSignal.timeout(10_000),   // ★ 타임아웃 기본값
  });

  if (!res.ok) {
    const body = await res.text();
    throw new HttpError(res.status, body);
  }
  const json = await res.json();
  return init?.schema ? init.schema.parse(json) : (json as T);   // ★ 검증까지
}

pino — 구조화 로그

import pino from "pino";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  // ★ 비밀 값 마스킹 — 실수로 토큰을 남기는 사고를 막습니다
  redact: {
    paths: ["req.headers.authorization", "req.headers.cookie",
            "*.password", "*.passwordHash", "*.cardNumber"],
    censor: "[REDACTED]",
  },
  base: { service: "order-api", env: process.env.NODE_ENV },
  transport: process.env.NODE_ENV !== "production"
    ? { target: "pino-pretty", options: { colorize: true } }
    : undefined,                       // ★ 운영은 JSON 그대로
});

// 자식 로거로 문맥 고정
const reqLog = logger.child({ requestId, userId });
reqLog.info({ orderId }, "주문 생성 완료");

TOOL 11

CI/CD

테스트 → 빌드 → 배포를 사람 손 없이.

GitHub Actions — 기본형

name: CI
on:
  pull_request:
  push: { branches: [main] }

jobs:
  check:
    runs-on: ubuntu-latest
    services:                          # ★ 테스트용 DB 를 띄웁니다
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        options: >-
          --health-cmd pg_isready --health-interval 10s
        ports: ["5432:5432"]
      redis:
        image: redis:7
        ports: ["6379:6379"]

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm                   # ★ 의존성 캐시 (시간 크게 절약)

      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm test
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/test
          REDIS_URL: redis://localhost:6379

      - run: npm audit --audit-level=high    # 취약점 검사
      - uses: codecov/codecov-action@v4      # 커버리지 리포트

배포 워크플로

  deploy:
    needs: check
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production            # ★ 승인 게이트를 걸 수 있습니다
    permissions: { id-token: write, contents: read }

    steps:
      - uses: actions/checkout@v4

      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha         # ★ 레이어 캐시
          cache-to: type=gha,mode=max

      - name: 배포
        run: |
          kubectl set image deployment/api \
            api=ghcr.io/${{ github.repository }}:${{ github.sha }}
          kubectl rollout status deployment/api --timeout=5m   # ★ 실패 시 감지
이미지 태그에 latest 만 쓰지 마세요. 커밋 SHA 로 태그하면 “지금 도는 게 어느 코드인지”가 명확하고, 문제가 생겼을 때 이전 태그로 즉시 롤백할 수 있습니다.

파이프라인 설계 원칙

  • 빠른 것부터 — 타입 검사·린트를 먼저, 무거운 E2E 는 나중에
  • PR 에서는 검사만, 배포는 main 병합 후
  • 모노레포라면 바뀐 것만 (turbo --filter=...[HEAD^])
  • 비밀 값은 OIDC 로 — 장기 액세스 키를 저장하지 마세요
  • 배포 후 헬스체크 확인까지 파이프라인에 포함
CI 가 10분을 넘으면 사람들이 기다리지 않습니다. 캐시·병렬화·변경분만 실행으로 5분 이내를 목표로 하세요. 느린 CI 는 결국 “일단 머지하고 나중에 고치자”로 이어집니다.
