SCALE 01

Node 로 트래픽 받기

“싱글 스레드라 느리다”는 오해부터 풀고 시작합니다.

왜 스레드 하나로 버티나

[스레드 기반 서버]  요청 1개 = 스레드 1개
  요청 10,000개 → 스레드 10,000개
  → 스레드당 1MB 스택 = 10GB
  → 컨텍스트 스위칭 비용 폭발

[Node]  요청 10,000개 = 대기 중인 콜백 10,000개
  → 실제로 CPU 를 쓰는 건 "응답이 도착한 것"뿐
  → 메모리는 수백 MB, 스위칭 없음

핵심: 웹 서버 작업의 대부분은 "기다리는 시간"입니다.
      DB 응답 50ms 동안 CPU 는 놀고 있습니다.
      Node 는 그 시간에 다른 요청을 처리합니다.
단, 계산이 들어오는 순간 무너집니다. 요청 하나가 CPU 를 200ms 점유하면 그동안 다른 모든 요청이 대기합니다. 초당 5개만 들어와도 서버가 마비됩니다. 이것이 Node 운영의 유일하고 가장 큰 위험입니다.

용량 산정 — 면접에서 시키는 계산

1) DAU × 1인당 요청 수 = 하루 총 요청
2) ÷ 86,400 = 평균 RPS
3) × 피크 배수(3~10) = 피크 RPS
4) 리틀의 법칙: 동시 처리 수 = RPS × 평균 처리시간(초)
5) ÷ 서버 1대 처리량 = 필요 대수

예) DAU 100만 · 1인 20요청 · 피크 5배
    = 2,000만 ÷ 86,400 × 5 ≈ 1,160 RPS
    평균 응답 100ms → 동시 116건
    → 커넥션 풀·외부 API 동시 호출 수를 이 기준으로 설계

Node 서버 1대의 감각

작업 성격대략의 처리량 (2vCPU)
메모리 캐시 응답10,000+ RPS
Redis 조회 1회수천 RPS
DB 조회 1~2회500 ~ 2,000 RPS
DB 쓰기 + 트랜잭션수백 RPS
JSON 1MB 파싱초당 수십 건 — CPU 바운드 ★
이미지 리사이즈워커 필수
정확한 수치가 목적이 아닙니다. 자릿수가 맞는지 보는 겁니다. “200 RPS 인데 서버 20대”면 뭔가 잘못 설계된 것이고, “3,000 RPS 를 2대로” 라면 부하 테스트(k13) 없이는 믿을 수 없습니다.

캐시 전략 · Redis

가장 저렴하고 효과가 큰 수단. 대신 정합성을 내줍니다.

기본 패턴 — Cache Aside

import { Redis } from "ioredis";
const redis = new Redis(env.REDIS_URL, {
  maxRetriesPerRequest: 3,
  enableReadyCheck: true,
  // ★ Redis 가 죽어도 서비스는 살아야 합니다
  reconnectOnError: (err) => err.message.includes("READONLY"),
});

async function getProduct(id: number): Promise<Product | null> {
  const key = `product:${id}`;

  try {
    const hit = await redis.get(key);
    if (hit) return JSON.parse(hit);
  } catch (e) {
    logger.warn({ e }, "캐시 조회 실패 — DB 로 우회");   // ★ 캐시 장애가 서비스 장애가 되면 안 됩니다
  }

  const product = await db.product.findUnique({ where: { id } });
  if (!product) return null;

  // ★ TTL 에 랜덤을 섞습니다 (k04 스탬피드 방지)
  const ttl = 300 + Math.floor(Math.random() * 60);
  redis.setex(key, ttl, JSON.stringify(product)).catch(() => {});
  return product;
}

// 갱신할 때는 "고치지 말고 지우세요"
async function updateProduct(id: number, dto: UpdateDto) {
  const updated = await db.product.update({ where: { id }, data: dto });
  await redis.del(`product:${id}`);          // ★ set 이 아니라 del
  return updated;
}
캐시를 새 값으로 덮어쓰면 안 되는 이유 — 동시에 두 요청이 수정하면 느린 쪽이 나중에 덮어써서 옛 값이 캐시에 남습니다. 지워 두면 다음 조회가 DB 에서 최신을 가져옵니다.

SCALE 04

캐시가 서비스를 죽일 때

캐시 때문에 생긴 장애는 캐시가 없었을 때보다 큽니다.

① 캐시 스탬피드

인기 상품 캐시가 만료되는 그 순간
  → 동시에 들어온 요청 3,000개가 전부 MISS
  → 3,000개가 같은 DB 쿼리를 동시에 실행
  → DB CPU 100% → 커넥션 고갈 → 전 서비스 마비

막는 법 세 가지
  ① TTL 에 랜덤 섞기 (가장 쉽고 효과 큼)
  ② 재계산은 한 명만 (분산 락)
  ③ 만료 전에 미리 갱신 (백그라운드 리프레시)
// ② 락으로 한 명만 DB 에 보내기
async function getWithLock(id: number) {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const lockKey = `lock:${key}`;
  const got = await redis.set(lockKey, "1", "EX", 5, "NX");

  if (got) {
    try {
      const data = await db.product.findUnique({ where: { id } });
      await redis.setex(key, 300 + Math.random() * 60, JSON.stringify(data));
      return data;
    } finally { await redis.del(lockKey); }
  }

  // 락을 못 얻은 요청은 짧게 기다렸다 캐시를 다시 봅니다
  await new Promise(r => setTimeout(r, 50));
  const retry = await redis.get(key);
  return retry ? JSON.parse(retry) : db.product.findUnique({ where: { id } });
}

② 캐시 관통 · ③ 핫키

// ② 존재하지 않는 id 를 계속 조회 (봇·버그·공격)
//    → "없음"도 캐시합니다
const cached = await redis.get(key);
if (cached === "__NULL__") return null;
if (cached) return JSON.parse(cached);

const data = await db.product.findUnique({ where: { id } });
if (!data) {
  await redis.setex(key, 30, "__NULL__");     // 짧은 TTL
  return null;
}
// ③ 핫키 — 특정 키에 요청이 몰려 Redis 노드 하나가 터짐
//    → 로컬 캐시를 한 겹 더 (2단 캐시)
import { LRUCache } from "lru-cache";

const local = new LRUCache<string, Product>({
  max: 1000,
  ttl: 5_000,                     // ★ 아주 짧게 — 정합성 손실 최소화
});

async function get2Tier(id: number) {
  const key = `product:${id}`;
  const l1 = local.get(key);
  if (l1) return l1;                       // 왕복 0회

  const l2 = await redis.get(key);
  if (l2) { const v = JSON.parse(l2); local.set(key, v); return v; }

  const data = await db.product.findUnique({ where: { id } });
  local.set(key, data);
  await redis.setex(key, 300, JSON.stringify(data));
  return data;
}
로컬 캐시는 서버마다 값이 다릅니다. 10대라면 최대 5초 동안 10가지 답이 나갈 수 있습니다. 재고·잔액에는 쓰지 마세요.
④ 배포 직후 눈사태 — 재시작으로 로컬 캐시가 전부 비면 모든 요청이 MISS 가 됩니다. 인기 데이터를 기동 시 미리 채우는 워밍업과, 롤링 배포(한 번에 전부 재시작하지 않기)로 완화합니다.
SCALE 05

동시성 · 분산 락

서버가 여러 대가 되는 순간 메모리 락은 아무 의미가 없습니다.

재고가 마이너스가 되는 이유

재고 1개 · 동시에 100명이 주문

서버A: SELECT 재고 → 1
서버B: SELECT 재고 → 1      ← 아직 아무도 안 줄임
서버A: 1 > 0 → 주문 생성, UPDATE 재고 = 0
서버B: 1 > 0 → 주문 생성, UPDATE 재고 = 0

→ 1개를 2명에게 판매, 100명이면 재고 -37 같은 숫자가 남습니다

★ Node 는 싱글 스레드지만 await 사이에 다른 요청이 끼어듭니다.
  "한 프로세스 안에서도" 이 문제가 생깁니다.

해법 1 — 락 없이 (가장 먼저 검토)

// ★ 조건을 UPDATE 문 안으로 밀어 넣습니다
const r = await prisma.stock.updateMany({
  where: { productId, quantity: { gte: qty } },   // 조건
  data: { quantity: { decrement: qty } },
});
if (r.count === 0) throw new OutOfStockError(productId);

// Redis 원자 연산 — 선착순 쿠폰에 잘 맞습니다
const left = await redis.decrby(`stock:${productId}`, qty);
if (left < 0) {
  await redis.incrby(`stock:${productId}`, qty);   // 되돌리기
  throw new OutOfStockError(productId);
}
“읽고 → 판단하고 → 쓰기”를 하지 마세요. 그 세 단계 사이가 전부 사고 구간입니다. 판단을 쿼리 안으로 옮기면 락이 아예 필요 없어집니다.

해법 2 — 분산 락 (Redlock)

npm i redlock 또는 ioredis + Lua
// 직접 만들 때 빠뜨리기 쉬운 것들
// ① TTL (프로세스가 죽으면 락이 영원히 남음)
// ② 소유자 확인 (남의 락을 지우면 안 됨)
// ③ 작업이 TTL 보다 길어질 때의 연장

const token = crypto.randomUUID();

// 획득 — NX(없을 때만) + PX(만료)
const ok = await redis.set(lockKey, token, "PX", 5000, "NX");
if (!ok) throw new BusyError("잠시 후 다시 시도해 주세요");

try {
  await doWork();
} finally {
  // ★ 해제는 반드시 Lua 로 (내 락인지 확인 후 삭제 — 원자적)
  await redis.eval(`
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else return 0 end
  `, 1, lockKey, token);
}
// 라이브러리를 쓰는 편이 안전합니다
import Redlock from "redlock";
const redlock = new Redlock([redis], { retryCount: 3, retryDelay: 200 });

await redlock.using([`lock:stock:${productId}`], 5000, async (signal) => {
  const stock = await getStock(productId);
  if (stock < qty) throw new OutOfStockError(productId);
  await decreaseStock(productId, qty);

  if (signal.aborted) throw signal.error;   // ★ 락이 만료됐는지 확인
});
분산 락은 완벽하지 않습니다. 네트워크 지연·GC 정지로 락이 만료됐는데 작업이 계속되는 상황이 생길 수 있습니다. 돈이 걸린 곳은 락에만 의존하지 말고 DB 유니크 제약·원자적 UPDATE 를 최후 방어선으로 두세요.
SCALE 06

멱등성 — 두 번 눌러도 한 번만

대규모에서는 같은 요청이 두 번 오는 게 정상입니다.

중복은 왜 생기나

  • 사용자가 결제 버튼을 두 번 눌렀다
  • 응답이 늦어 클라이언트가 재시도했다 (서버는 이미 처리 완료)
  • 로드밸런서·게이트웨이가 자동 재시도했다
  • 큐 워커가 재시도로 같은 작업을 다시 받았다 (k07)
  • 모바일 앱이 네트워크 복구 후 대기 큐를 전송했다 (⚛️ RN r09)
재시도 로직(k08)을 넣는 순간 멱등성은 필수가 됩니다. 둘은 항상 같이 설계해야 합니다. “재시도하면 되지”가 곧 “중복 결제”입니다. 
// Idempotency-Key 패턴 — 업계 표준 (Stripe·Toss 등)
app.post("/api/payments", async (req, res) => {
  const key = req.header("Idempotency-Key");
  if (!key) throw new ValidationError("Idempotency-Key 헤더가 필요합니다");

  const k = `idem:pay:${key}`;
  const first = await redis.set(k, "PROCESSING", "EX", 86400, "NX");

  if (!first) {
    const saved = await redis.get(k);
    if (saved === "PROCESSING")
      return res.status(409).json({ code: "IN_PROGRESS" });
    return res.json(JSON.parse(saved!));      // ★ 저장된 결과 재사용
  }

  try {
    const result = await paymentService.pay(req.body);
    await redis.setex(k, 86400, JSON.stringify(result));
    res.json(result);
  } catch (e) {
    await redis.del(k);                        // ★ 실패는 지워 재시도 허용
    throw e;
  }
});

  created_at     timestamptz default now()
);

}

재시도 — 잘못하면 불난 데 기름

// ❌ 나쁜 재시도 — 서버가 힘든데 3배로 때립니다

  try { return await call(); } catch { /* 즉시 재시도 */ }
}

// ✅ 지수 백오프 + 지터
async function retry<T>(fn: () => Promise<T>, max = 3): Promise<T> {
  let lastErr: unknown;
  for (let i = 0; i < max; i++) {
    try { return await fn(); }
    catch (e) {
      lastErr = e;
      if (!isRetryable(e)) throw e;          // ★ 4xx 는 재시도해도 소용없습니다
      const base = 200 * 2 ** i;             // 200 → 400 → 800
      const jitter = Math.random() * base;   // ★ 지터 — 동시 재시도 방지
      await new Promise(r => setTimeout(r, base + jitter));
    }
  }
  throw lastErr;
}

const isRetryable = (e: any) =>
  e.name === "TimeoutError" ||
  ["ECONNRESET", "ETIMEDOUT", "ECONNREFUSED"].includes(e.code) ||
  [429, 502, 503, 504].includes(e.status);

// Lua 는 Redis 안에서 한 덩어리로 실행됩니다 (경쟁 조건 없음)
const LUA = `
  local key      = KEYS[1]
  local capacity = tonumber(ARGV[1])
  local rate     = tonumber(ARGV[2])
  local now      = tonumber(ARGV[3])

  local b = redis.call('HMGET', key, 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now

  tokens = math.min(capacity, tokens + (now - ts) * rate)
  local allowed = tokens >= 1
  if allowed then tokens = tokens - 1 end

  redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', key, 120)
  return allowed and 1 or 0
`;

const allowed = await redis.eval(LUA, 1, `rate:${userId}`,
  "60", "1", String(Date.now() / 1000));

     .end(await client.register.metrics()));
라벨에 사용자ID·주문번호를 넣지 마세요. Prometheus 는 라벨 조합마다 시계열을 만듭니다. 고유값을 넣으면 시계열이 수백만 개가 되어(카디널리티 폭발) 모니터링 서버가 먼저 죽습니다. 그건 로그에 남기세요.

메모리 한도를 반드시 지정하세요. Node 는 컨테이너 한도를 자동으로 못 봅니다(자바와 다릅니다). --max-old-space-size 를 컨테이너 메모리의 75% 정도로 주지 않으면 계속 늘리다 OOMKilled(exit 137) 당합니다 — 로그도 안 남습니다. 
CMD ["node", "--max-old-space-size=1536", "dist/index.js"]   # 2GB 컨테이너

무중단 배포 — 끊기는 진짜 이유

파드 종료 시 실제로 일어나는 일
  1. 종료 중으로 표시
  2. 서비스 엔드포인트에서 제거   ┐ 이 둘은 동시에
  3. 컨테이너에 SIGTERM 전달      ┘ (순서 보장 없음)

  → 3번이 먼저 오면, 아직 라우팅되는 상태에서 종료가 시작
  → 그 사이 요청이 502 로 떨어집니다

해결: 종료 신호를 받고 몇 초 버틴 뒤 실제 종료
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 5"] }   # ★ 제거를 기다림
terminationGracePeriodSeconds: 60

livenessProbe:                       # ★ 의존성 검사 넣지 말 것
  httpGet: { path: /health/live, port: 3000 }
  initialDelaySeconds: 10
readinessProbe:                      # ★ DB·Redis 는 여기서
  httpGet: { path: /health/ready, port: 3000 }
  periodSeconds: 5

strategy:
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 무중단

resources:
  requests: { cpu: "250m", memory: "512Mi" }
  limits:   { cpu: "1",    memory: "2Gi" }
// 애플리케이션 쪽 — 우아한 종료 (🟩 Node n08)
process.on("SIGTERM", async () => {
  server.close();                                  // 새 요청 차단
  await new Promise(r => setTimeout(r, 5000));     // 진행 중 요청 완료
  await worker.close();                            // ★ 큐 워커도 정리
  await prisma.$disconnect();
  await redis.quit();
  process.exit(0);
});
단일 VM 이라면 PM2 로도 무중단이 됩니다 — pm2 reload app 이 하나씩 순차 재시작합니다. K8s 를 쓸 여건이 아니면 PM2 클러스터 모드가 현실적인 선택입니다.

Node 기반 대규모 서비스의 표준 구성

                     [CDN]  정적 파일 · 이미지
                       │
                  [로드밸런서]  TLS 종료 · 헬스체크
                       │
                  [API 게이트웨이]  인증 · Rate Limit · 라우팅
                       │
       ┌───────────────┼───────────────┐
  [주문 API]      [상품 API]      [회원 API]      ← 각각 여러 파드, 오토스케일
       │               │               │
       │          [Redis]  캐시 · 세션 · 분산락 · 큐(BullMQ)
       │               │
  [Primary DB] ──복제──→ [Read Replica ×N]
       │
  [워커 프로세스]  메일 · 이미지 · 정산 (API 와 분리 배포) ★
       │

배포 전 체크리스트

  • ☐ 모든 외부 호출에 타임아웃이 있는가
  • ☐ 이벤트 루프 지연을 측정·알람하고 있는가
  • ☐ 커넥션 풀 × 서버 대수가 DB 한도 안인가
  • ☐ 캐시 TTL 에 랜덤을 섞었는가
  • ☐ 재시도하는 API 가 멱등한가
  • ☐ 재고·포인트 차감이 원자적인가
  • ☐ 큐 작업이 두 번 실행돼도 괜찮은가
  • ☐ DLQ·백로그에 알람이 있는가
  • ☐ liveness / readiness 를 분리했는가
  • ☐ SIGTERM 처리 + preStop 이 있는가
  • ☐ --max-old-space-size 를 지정했는가
  • ☐ 로그가 JSON + traceId 인가
  • ☐ Redis 가 죽어도 서비스가 동작하는가
  • ☐ 부하 테스트로 한계 RPS 를 아는가

면접에서 이렇게 답하면 됩니다

질문답의 뼈대
Node 는 싱글 스레드인데
어떻게 트래픽을 받나?		 I/O 대기 중에 다른 요청을 처리 → 대신 CPU 작업이 들어오면 즉시 무너짐 → 워커·별도 서비스로 분리 (k01·k02)
트래픽이 10배가 되면? 측정(k13) → 이벤트 루프·쿼리 개선 → 캐시 → 읽기 복제본 → 파드 확장 → 비동기화
선착순 쿠폰 10만 요청 Redis DECR 로 수량 판정 → 통과분만 큐로 → 워커가 DB 저장. DB 에 10만 요청을 보내지 않습니다
중복 결제를 어떻게 막나? Idempotency-Key + Redis 선점 + DB 유니크 제약(최후 방어선)
외부 결제사가 느려지면? 타임아웃 → 재시도(백오프+지터) → 서킷 브레이커 → 폴백
서버를 늘렸는데
세션이 풀립니다		 메모리 세션 → Redis 세션 또는 JWT. 무상태가 확장의 전제(k11)
가장 좋은 답은 “저희는 이렇게 겪었습니다”입니다. 수치(전 800ms → 후 90ms), 원인(N+1 + 동기 JSON 파싱), 조치(include + 워커 분리), 확인 방법(k6 p99)까지 한 세트로 말하면 지식 나열보다 훨씬 강한 인상을 줍니다.

순서를 지키세요

1단계 — 측정 이벤트 루프 지연·슬로우 쿼리·p99 를 먼저 보세요(k02·k12). 여기서 끝나는 문제가 대부분입니다.
2단계 — 없애기 인덱스·N+1·동기 코드 제거. 코드를 고치는 게 가장 싸고 효과가 큽니다.
3단계 — 걷어내기 캐시로 DB 부하를 덜고(k03), 급하지 않은 일은 큐로(k07).
4단계 — 늘리기 무상태로 만들고(k11) 파드를 늘립니다. 이때부터 동시성(k05)과 멱등성(k06)이 필수가 됩니다.
5단계 — 지키기 타임아웃·서킷·Rate Limit(k08·k09)으로 과부하에서 무너지지 않게.
6단계 — 확인하기 부하 테스트로 한계를 재고(k13) 알람을 걸어 둡니다.
1·2단계를 건너뛰고 4단계로 가는 것이 가장 흔한 실수입니다. 동기 함수 하나만 고치면 될 일에 파드를 10개 늘리면 비용은 10배가 되고 문제는 그대로입니다. 그리고 다음 달에 다시 옵니다.
