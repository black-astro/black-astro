.NET 이 뭔지부터 — 이름 정리가 절반입니다

파이썬은 “파이썬을 깐다”가 끝입니다. C# 은 언어(C#)와 실행 판(.NET)이 따로이고, 그 .NET 이 역사적으로 세 갈래로 갈라져 있었습니다. 검색 결과가 서로 모순돼 보이는 이유가 여기 있습니다. 15년 치 이름의 지도를 먼저 그려 두면 나머지 설치는 순식간입니다.

짝수가 LTS(3년), 홀수가 STS(18개월) 입니다. 11월에 새 버전이 나오는 것도 고정입니다. 고민되면 짝수 = 회사, 홀수 = 취미 로 외우면 실무에서 틀리지 않습니다.

지원 종료(EOL)는 “못 쓴다”가 아니라 “보안 패치가 안 온다”입니다. 인터넷에 노출된 서버라면 이건 사실상 못 쓰는 것과 같습니다. 클라우드(Azure App Service · AWS Lambda)는 EOL 런타임의 배포 자체를 거부하기 시작합니다.

파이썬의 venv 나 Node 의 nvm 같은 게 필요 없습니다. .NET 은 런타임이 버전별로 나란히 설치(side-by-side) 되고, 어떤 버전으로 돌릴지는 프로젝트 파일이 직접 지정하기 때문입니다. 이건 .NET 환경 관리가 다른 생태계보다 편한 결정적인 이유입니다.

SETUP 05

dotnet CLI 기본기 — IDE 없이도 전부 됩니다

dotnet 명령 하나가 프로젝트 생성 · 빌드 · 실행 · 테스트 · 배포 · 패키지 관리를 전부 합니다. Visual Studio 의 버튼들도 결국 이 명령을 부릅니다. CLI 를 알면 IDE 가 왜 그렇게 동작하는지도 알게 됩니다 — 그래서 여기가 이 탭의 중심입니다.

솔루션은 목록, 프로젝트(.csproj)가 실제 설정입니다 — 이 구분이 빌드 문제 해결의 출발점입니다.

① 만들기 — dotnet new

# 어떤 템플릿이 있나 (설치된 것 전부)
dotnet new list

# 자주 쓰는 것
dotnet new console   -o src/MyShop.Cli     # 콘솔 앱
dotnet new classlib  -o src/MyShop.Core    # 클래스 라이브러리
dotnet new webapi    -o src/MyShop.Api     # 웹 API (최소 API)
dotnet new mvc       -o src/MyShop.Web     # MVC 웹앱
dotnet new blazor    -o src/MyShop.Ui      # Blazor
dotnet new xunit     -o tests/MyShop.Tests # 테스트
dotnet new worker    -o src/MyShop.Job     # 백그라운드 서비스
dotnet new wpf       -o src/MyShop.Desktop # WPF (윈도우 전용)

# 부가 파일 템플릿 — 의외로 많이 씁니다
dotnet new gitignore          # .NET 용 .gitignore
dotnet new editorconfig       # 기본 .editorconfig
dotnet new globaljson --sdk-version 10.0.100
dotnet new nugetconfig        # NuGet.Config

# 옵션 보기 (템플릿마다 다릅니다)
dotnet new webapi --help
dotnet new console -f net8.0 -o old   # 대상 프레임워크 지정
-o 를 안 주면 현재 폴더에 만들고 폴더 이름을 프로젝트 이름으로 씁니다. 그래서 mkdir MyShop && cd MyShop && dotnet new console 이 가장 흔한 시작 방식입니다. 이름에 공백·한글은 피하세요 (st12).

② 묶기 — 솔루션과 참조

# 솔루션 만들기 (.slnx — 새 XML 형식, .NET 9+ · VS 2022 17.13+ 지원)
dotnet new sln -n MyShop --format slnx
#   옛 형식이 필요하면: dotnet new sln -n MyShop   (MyShop.sln)

# 프로젝트를 솔루션에 등록
dotnet sln add src/MyShop.Api/MyShop.Api.csproj
dotnet sln add src/MyShop.Core/MyShop.Core.csproj
dotnet sln add tests/MyShop.Tests/MyShop.Tests.csproj

# 한 번에 (glob)
dotnet sln add (ls -r src/*.csproj)          # PowerShell
dotnet sln add $(find . -name "*.csproj")    # bash

# 등록된 것 보기 · 빼기
dotnet sln list
dotnet sln remove src/MyShop.Old/MyShop.Old.csproj

# 프로젝트끼리 참조 — Api 가 Core 를 쓴다
dotnet add src/MyShop.Api reference src/MyShop.Core
dotnet add tests/MyShop.Tests reference src/MyShop.Core

# 참조 목록 확인
dotnet list src/MyShop.Api reference
솔루션이 꼭 필요한가 — 프로젝트가 하나면 필요 없습니다. 두 개 이상이 되는 순간 dotnet build 한 번으로 전부 빌드하고, IDE 가 한 창에 열어 주기 위해 필요해집니다. .slnx 는 옛 .sln 의 난해한 GUID 덩어리를 걷어낸 새 형식으로, 깃 충돌이 훨씬 덜 납니다.

③ 돌리기 — 매일 치는 명령

# 복원 → 빌드 → 실행. build/run 이 복원을 자동으로 합니다
dotnet restore                       # 보통 따로 칠 일이 없습니다
dotnet build                         # Debug 로 빌드
dotnet build -c Release              # Release
dotnet run --project src/MyShop.Api  # 빌드 + 실행

# 코드가 바뀌면 자동 재시작 (웹 개발 필수)
dotnet watch run --project src/MyShop.Api

# 테스트
dotnet test                          # 솔루션 전체
dotnet test --filter "FullyQualifiedName~Cart"   # 이름으로 골라
dotnet test --collect:"XPlat Code Coverage"      # 커버리지

# 인자 넘기기 — -- 뒤는 프로그램에게 갑니다
dotnet run --project src/MyShop.Cli -- --input data.csv --verbose

# 청소
dotnet clean
dotnet build-server shutdown         # 백그라운드 컴파일러 종료
dotnet run 은 개발용입니다. 매번 빌드 검사를 하고 SDK 를 요구합니다. 서버에서는 절대 dotnet run 으로 서비스를 띄우지 마세요 — dotnet publish 결과의 dotnet MyApi.dll 을 실행합니다.

④ 내보내기 — dotnet publish

# 기본 — 런타임이 서버에 있다는 전제 (가장 가볍습니다)
dotnet publish -c Release -o out
#   out/MyApi.dll · MyApi.exe · 의존 dll · appsettings.json

# 런타임까지 통째로 담기 (서버에 .NET 이 없어도 됨)
dotnet publish -c Release -r linux-x64 --self-contained true -o out
#   약 70MB. 안 쓰는 코드를 잘라내려면
dotnet publish -c Release -r linux-x64 --self-contained true \
  -p:PublishTrimmed=true -o out

# 단일 실행 파일 하나로
dotnet publish -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true -o out

# 네이티브 AOT — 시작이 수 ms, 메모리 최소 (제약 있음)
dotnet publish -c Release -r linux-x64 -p:PublishAot=true -o out

# RID 값: win-x64 · win-arm64 · linux-x64 · linux-musl-x64 · osx-arm64
RID(Runtime Identifier) 는 “어느 OS·CPU 용인가”를 나타내는 이름표입니다. 알파인 리눅스 도커 이미지에 올릴 때는 linux-x64 가 아니라 linux-musl-x64 여야 합니다 — C 라이브러리가 다르기 때문이고, 이걸 틀리면 컨테이너가 실행 즉시 죽습니다.

한 단계 더 — global.json 으로 SDK 를 고정합니다 🟡 중급

왜 필요한가

SDK 는 기본적으로 PC 에 깔린 가장 높은 버전이 선택됩니다. 그래서 내 PC 에서는 되는데 동료 PC 나 CI 에서 빌드 결과가 미묘하게 다른 일이 생깁니다. global.json 은 이 폴더 아래에서는 이 SDK 를 써라 라고 못을 박습니다. 

{
  "sdk": {
    "version": "10.0.100",
    "rollForward": "latestFeature",
    "allowPrerelease": false
  }
}
# 만들기
dotnet new globaljson --sdk-version 10.0.100

# 지금 어느 SDK 가 선택됐는지 (global.json 반영된 결과)
dotnet --version

# rollForward 값이 하는 일
#   disable        정확히 그 버전만. 없으면 에러
#   patch          10.0.100 → 10.0.1xx 중 가장 높은 패치 허용
#   latestFeature  10.0.1xx → 10.0.4xx 까지 허용  ★ 실무 기본
#   latestMajor    11.x 까지도 허용 (사실상 고정 해제)
rollForward: "disable" 은 함정입니다. 팀원이 SDK 를 업데이트하는 순간 NETSDK1141 로 빌드가 막힙니다. latestFeature 가 “버전은 고정하되 패치는 따라간다”는 실무의 균형점입니다. 증상별 대처는 st12 에 있습니다.

<Project Sdk="Microsoft.NET.Sdk">

  </ItemGroup>

  <ItemGroup>
    <None Update="config\rules.json" CopyToOutputDirectory="PreserveNewest" />
  </ItemGroup>

</Project>
SDK 스타일 프로젝트는 소스 파일을 일일이 나열하지 않습니다 — 폴더 안의 .cs 를 전부 자동 포함합니다. 옛 .NET Framework 프로젝트 파일에는 <Compile Include="..." /> 가 수백 줄 있었는데, 그게 사라진 것이 지금 형식의 가장 큰 변화입니다.

SETUP 06

NuGet — 패키지가 오는 길을 알아야 안 막힙니다

파이썬의 pip, Node 의 npm 에 해당하는 것이 NuGet 입니다. 평소에는 dotnet add package 한 줄이면 끝나지만, 회사 네트워크에 들어가는 순간 복원이 막히고 에러 코드(NU1101)가 쏟아집니다. 패키지가 어디서 어떻게 오는지를 그림 한 장으로 잡아 두면 그때 5분이면 해결됩니다.

복원이 실패하면 빌드는 시작조차 하지 않습니다 — 그래서 에러 메시지가 NU 로 시작하면 네트워크·피드부터 봅니다.

① 매일 쓰는 명령

# 추가 — 버전을 안 적으면 최신 안정판
dotnet add package Serilog.AspNetCore
dotnet add package Newtonsoft.Json --version 13.0.3
dotnet add src/MyShop.Api package Dapper       # 프로젝트 지정

# 프리릴리즈까지 허용
dotnet add package Some.Lib --prerelease

# 목록 보기
dotnet list package                    # 이 프로젝트가 쓰는 것
dotnet list package --include-transitive  # 딸려 온 것까지 전부
dotnet list package --outdated         # 새 버전이 나온 것 ★
dotnet list package --vulnerable       # 알려진 취약점이 있는 것 ★★

# 제거
dotnet remove package Newtonsoft.Json

# 복원 · 캐시
dotnet restore
dotnet restore --force --no-cache      # 강제로 다시
dotnet nuget locals all --list         # 캐시 위치 확인
dotnet nuget locals all --clear        # 캐시 통째로 비우기
--vulnerable 은 분기에 한 번씩 꼭 돌려 보세요. 직접 넣은 패키지는 멀쩡한데 그 패키지가 끌고 온 하위 의존성에 취약점이 있는 경우가 대부분이라 --include-transitive 를 함께 붙입니다. CI 에 넣어 두면(st11) 사람이 기억할 필요가 없어집니다.

② nuget.org 에서 고르는 법

검색은 nuget.org 에서 합니다. 이름이 비슷한 가짜·방치된 패키지가 많아 고르는 눈이 필요합니다. 페이지에서 이 다섯 가지만 보면 거의 틀리지 않습니다.

볼 것기준
총 다운로드수백만이면 사실상 표준
마지막 배포일2년 이상 멈췄으면 다시 생각
Frameworks 목록net10.0 또는 netstandard2.0 이 있어야
Source repository깃허브 링크가 있고 이슈에 답이 달리는지
소유자 배지Microsoft · dotnetfoundation 이면 안심
이름 한 글자 다른 가짜 패키지(타이포스쿼팅)가 실제로 있습니다. Newtonsoft.Json 과 Newtonsoft.Json.Net 같은 식입니다. 검색 결과의 첫 줄을 반사적으로 누르지 말고 다운로드 수와 소유자를 한 번 보세요. 회사라면 아예 사내 피드만 허용하고 승인된 패키지만 통과시킵니다.

사내 네트워크 — NuGet.Config 와 프록시 🟡 중급

설정 파일은 위로 올라가며 합쳐집니다

NuGet 은 아래에서 위로 올라가며 설정을 겹칩니다 (아래쪽이 이깁니다)

  C:\Users\나\AppData\Roaming\NuGet\NuGet.Config   ← 사용자 전역
  D:\work\NuGet.Config                             ← 상위 폴더
  D:\work\MyShop\NuGet.Config                      ← 저장소 루트 ★ 여기에 둡니다
  D:\work\MyShop\src\NuGet.Config                  ← 프로젝트별(드묾)

지금 어떤 설정이 적용됐는지 확인
  dotnet nuget list source
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <!-- ★ 부모 설정을 지우고 여기 적은 것만 씁니다 -->
  <packageSources>
    <clear />
    <add key="company" value="https://nexus.mycorp.com/repository/nuget/index.json" />
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" />
  </packageSources>

  <!-- 사내 피드 인증 -->
  <packageSourceCredentials>
    <company>
      <add key="Username" value="%NUGET_USER%" />
      <add key="ClearTextPassword" value="%NUGET_TOKEN%" />
    </company>
  </packageSourceCredentials>

  <!-- 회사 프록시를 타야 한다면 -->
  <config>
    <add key="http_proxy" value="http://proxy.mycorp.com:8080" />
    <add key="globalPackagesFolder" value="D:\nuget-cache" />
  </config>
</configuration>
비밀번호를 파일에 그대로 적어 깃에 올리는 사고가 정말 자주 납니다. 위처럼 %환경변수% 를 쓰거나, 명령으로 등록해 사용자 전역 설정에만 저장하세요 — 저장소에 커밋되는 NuGet.Config 에는 주소만 둡니다.

피드를 명령으로 관리하기

# 등록된 피드 보기
dotnet nuget list source

# 사내 피드 추가 (자격 증명은 사용자 전역에 저장)
dotnet nuget add source https://nexus.mycorp.com/repository/nuget/index.json \
  --name company --username myid --password $env:NUGET_TOKEN \
  --store-password-in-clear-text

# 잠시 끄기 · 켜기 · 지우기
dotnet nuget disable source nuget.org
dotnet nuget enable  source nuget.org
dotnet nuget remove  source company

# 특정 피드만 써서 복원 (진단할 때 유용)
dotnet restore --source https://api.nuget.org/v3/index.json

# 오프라인 · 폐쇄망 — 폴더를 피드처럼 씁니다
dotnet nuget add source D:\offline-packages --name local
#   .nupkg 파일들을 그 폴더에 넣어 두면 그대로 복원됩니다

# 내가 만든 라이브러리를 올릴 때
dotnet pack -c Release
dotnet nuget push bin/Release/MyLib.1.0.0.nupkg \

프록시가 있는 회사에서 가장 빨리 확인하는 방법 — dotnet restore --interactive 를 한 번 돌려 보세요. 인증이 필요하면 브라우저 로그인 창을 띄워 줍니다. 그래도 NU1301(피드에 접근 불가)이 나면 네트워크 차단이고, NU1101(패키지를 못 찾음)이면 피드 목록 문제입니다.

실무 표준 — 중앙 패키지 관리(CPM) 🔴 실무

버전을 한 파일에 모읍니다

프로젝트가 열 개면 Serilog 버전이 열 군데 흩어집니다. 하나만 안 올려 두면 런타임에 어셈블리 버전 충돌이 나고, 원인 찾기가 아주 고약합니다. 중앙 패키지 관리는 버전을 저장소 루트 한 파일로 모읍니다. 

<!-- 저장소 루트 · Directory.Packages.props -->
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
    <CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>
  </PropertyGroup>

  <ItemGroup>
    <PackageVersion Include="Serilog.AspNetCore" Version="9.0.0" />
    <PackageVersion Include="Dapper" Version="2.1.66" />
    <PackageVersion Include="xunit" Version="2.9.3" />
  </ItemGroup>
</Project>
<!-- 각 프로젝트의 .csproj — 버전을 적지 않습니다 -->
<ItemGroup>
  <PackageReference Include="Serilog.AspNetCore" />
  <PackageReference Include="Dapper" />
</ItemGroup>
업그레이드가 파일 한 줄 수정으로 끝납니다. 게다가 PR 에서 “무엇이 올라갔는지”가 한눈에 보입니다 — 열 개 .csproj 에 흩어진 변경보다 리뷰가 훨씬 쉽습니다.

버전을 재현 가능하게 못 박기

<!-- 버전 표기법 -->
<PackageReference Include="Dapper" Version="2.1.66" />
<!-- ↑ "2.1.66 이상 중 가장 낮은 것" 이라는 뜻입니다. 정확히 이 버전이 아닙니다 -->

<PackageReference Include="Dapper" Version="[2.1.66]" />
<!-- ↑ 대괄호 = 정확히 이 버전만 -->

<PackageReference Include="Dapper" Version="[2.1.0,3.0.0)" />
<!-- ↑ 2.1.0 이상 3.0.0 미만 -->
# 잠금 파일 — npm 의 package-lock.json 에 해당합니다
# csproj 에 이 한 줄을 넣으면 packages.lock.json 이 생깁니다
#   <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>

# CI 에서는 잠금 파일과 다르면 실패하게 만듭니다 (★ 재현성)

# 잠금 파일을 갱신할 때만
dotnet restore --force-evaluate
“내 PC 에서는 되는데 CI 에서만 깨진다”의 단골 원인이 버전 표기입니다. Version="2.1.66" 은 상한이 없어서, 어느 날 새 버전이 나오면 아무도 아무것도 안 바꿨는데 빌드가 달라집니다. 잠금 파일 + --locked-mode 조합이 이걸 완전히 막아 줍니다.
정리 — 복원은 캐시 → 피드 목록 → project.assets.json 순서로 흐릅니다. 회사에서는 NuGet.Config 를 저장소 루트에 두되 비밀번호는 환경 변수로, 프로젝트가 여러 개면 Directory.Packages.props 로 버전을 한곳에 모읍니다.

SETUP 08

Rider · VS Code — 언제 무엇을 쓰나

SETUP 09

콘솔과 웹은 SDK 하나로 끝납니다. 그런데 창이 뜨는 프로그램과 게임은 각자 추가 부품을 요구합니다 — 워크로드, 안드로이드 SDK, 엔진 본체. 여기서는 무엇이 더 필요한지와 설치가 됐는지 확인하는 법만 정확히 짚습니다.

SETUP 10

웹 · DB 준비 — API 하나가 뜨기까지

웹 API 는 dotnet new webapi 로 5초 만에 만들어집니다. 그런데 브라우저에서 열면 인증서 경고가 뜨고, DB 를 붙이려면 서버가 필요하고, 마이그레이션 명령은 설치가 안 되어 있습니다. 이 세 가지 걸림돌을 한 번에 치워 두면 다시는 막히지 않습니다.

막히는 지점은 늘 셋입니다 — 인증서 · dotnet ef 설치 · DB 서버.

코드 품질 · 빌드 — 사람 대신 컴파일러가 잔소리하게

코드 리뷰에서 “여기 들여쓰기가”, “null 체크 빠졌는데요”를 사람이 말하고 있다면 설정이 부족한 것입니다. .NET 은 분석기가 컴파일러에 내장되어 있어서, 설정 몇 줄로 스타일 · 잠재적 버그 · 취약점을 빌드 단계에서 잡을 수 있습니다. 새 프로젝트를 만든 첫날 해 두는 것이 열 배 쉽습니다.

같은 실수를 0초에 잡느냐 리뷰에서 잡느냐의 차이입니다 — 설정 20줄이 그 차이를 만듭니다.

① nullable 켜기 — 가장 값싼 버그 예방

<PropertyGroup>
  <Nullable>enable</Nullable>
  <!-- string? 처럼 물음표를 붙인 것만 null 이 될 수 있게 됩니다 -->
</PropertyGroup>
// nullable 을 켜면 컴파일러가 이렇게 말합니다
string name = null;        // CS8600 경고 — null 을 넣을 수 없는 타입
string? maybe = null;      // OK — 물음표가 "없을 수 있다"는 선언

void Print(string? s)
{
    Console.WriteLine(s.Length);   // CS8602 경고 — null 일 수 있는데 접근
    if (s is null) return;
    Console.WriteLine(s.Length);   // 여기서는 경고 없음. 컴파일러가 압니다
}

// 기존 코드가 경고 폭탄이라면 단계적으로
//   <Nullable>warnings</Nullable>     경고만 (에러 아님)
//   파일 맨 위에  #nullable enable      파일 단위로 켜기
//   당장 어쩔 수 없는 곳은  value!      null 아님을 단언 (남발 금지)
NullReferenceException 은 .NET 에서 가장 흔한 런타임 예외입니다. nullable 참조 형식은 그걸 실행 전에 대부분 잡아 줍니다. 새 프로젝트 템플릿에는 이미 켜져 있습니다 — 끄지 마세요. 경고가 많다고 끄는 순간, 그 경고가 말하던 버그는 전부 그대로 남습니다.

② 분석기와 경고 정책

<!-- 저장소 루트 · Directory.Build.props → 모든 프로젝트에 자동 적용 -->
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- 분석기 -->
    <EnableNETAnalyzers>true</EnableNETAnalyzers>

TreatWarningsAsErrors 를 기존 프로젝트에 갑자기 켜면 빌드가 죽습니다. 새 프로젝트에서는 첫날 켜고, 기존 프로젝트라면 <WarningsAsErrors>CS8600;CS8602</WarningsAsErrors> 처럼 중요한 것 몇 개만 골라 시작한 뒤 범위를 넓히세요.

④ CI — GitHub Actions

# .github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.0.x'
          # global.json 이 있으면 그 버전을 우선합니다
          cache: true
          cache-dependency-path: '**/packages.lock.json'

      - run: dotnet restore --locked-mode
      - run: dotnet format --verify-no-changes
      - run: dotnet build --no-restore -c Release
      - run: dotnet test --no-build -c Release --logger trx
      - run: dotnet list package --vulnerable --include-transitive

      - name: 배포 산출물
        run: dotnet publish src/MyShop.Api -c Release -o out --no-build
      - uses: actions/upload-artifact@v4
        with: { name: api, path: out }
--no-restore · --no-build 를 붙이는 이유 — 안 붙이면 단계마다 복원과 빌드를 다시 합니다. CI 시간이 두세 배가 되고, 더 나쁜 것은 test 가 방금 빌드한 것과 다른 결과물을 테스트할 수도 있다는 점입니다.
파일두는 곳하는 일
.editorconfig저장소 루트서식 · 스타일 · 규칙 심각도. IDE 세 개가 모두 읽습니다
Directory.Build.props저장소 루트모든 .csproj 에 공통 속성 주입 (앞에서 적용)
Directory.Build.targets저장소 루트공통 빌드 단계 (뒤에서 적용)
Directory.Packages.props저장소 루트패키지 버전 중앙 관리 (st06)
global.json저장소 루트SDK 버전 고정 (st05)
NuGet.Config저장소 루트피드 목록 (st06)
packages.lock.json프로젝트별복원 결과 잠금. 커밋합니다
bin/ · obj/프로젝트별커밋하지 않습니다 — dotnet new gitignore
정리 — nullable 켜기 · 분석기 켜기 · dotnet format · CI 네 가지입니다. 공통 설정은 Directory.Build.props 한 파일에 모으고, 경고를 에러로 만드는 것은 새 프로젝트에서는 첫날, 기존 프로젝트에서는 골라서 적용하세요.

# ④ 이 폴더에 SDK 를 강제하는 파일이 있나
Get-ChildItem -Recurse -Filter global.json .. | Select-Object FullName

dotnet build-server shutdown
dotnet nuget locals all --clear
Get-ChildItem -Recurse -Include bin,obj -Directory | Remove-Item -Recurse -Force
dotnet restore --force

스택오버플로나 팀 채널에 물어볼 때, 아래 네 가지를 함께 올리면 답이 오는 속도가 완전히 달라집니다. 반대로 이게 없으면 “dotnet --info 결과 좀 주세요”라는 답만 돌아옵니다.

  • dotnet --info 전체 출력 — SDK·런타임·RID 가 한 번에 보입니다
  • 에러 메시지 원문 — 번역하지 말고 코드(NU1101 등)까지 그대로
  • 재현 명령 — 어느 폴더에서 무엇을 쳤는지
  • .csproj 와 global.json 내용
이 목록을 만드는 과정에서 원인을 스스로 찾는 경우가 절반쯤 됩니다. “어느 폴더에서 무엇을 쳤는지”를 적다 보면 global.json 이 있는 폴더 밖에서 실행하고 있었다거나 다른 SDK 가 선택되어 있었다는 사실이 드러나기 때문입니다.
정리 — 막히면 dotnet --info → where dotnet → 에러 코드 앞 글자 순서로 좁힙니다. NETSDK는 버전, NU는 패키지, CS는 코드입니다. 마지막 수단은 재설치가 아니라 캐시 정리(nuget locals --clear + bin/obj 삭제) 입니다.
