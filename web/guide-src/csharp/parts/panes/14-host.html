서블릿 컨테이너는 왜 사라졌나

톰캣의 존재 이유는 "여러 개의 WAR 을 한 프로세스에 얹어 함께 운영" 하는 것이었습니다. 2000년대에는 서버 한 대가 비쌌으니 합리적이었습니다. 지금은 컨테이너와 프로세스 격리가 싸졌기 때문에, 앱 하나 = 프로세스 하나 가 기본이 되었습니다. 그러면 컨테이너가 할 일이 없습니다 — 그 자리에 라이브러리 한 개만 남습니다.

Spring Boot 를 이미 쓰고 있다면 낯설지 않습니다. java -jar app.jar 로 임베디드 톰캣을 띄우는 그 방식이 .NET 에서는 선택이 아니라 유일한 방식이라고 보면 정확합니다.

그래서 서버에 실제로 까는 것

# 확인

self-contained 로 게시하면 이것조차 필요 없습니다. 런타임을 앱 폴더에 통째로 담아 가는 방식입니다 — 서버에 아무 권한도 없고 아무것도 못 깔 때 쓰는 탈출구입니다 (h09).

HOST 02

Kestrel 파고들기

톰캣의 server.xml 에서 하던 일 — 포트 열기, 스레드 수, 커넥션 제한, 타임아웃 — 을 .NET 에서는 어디서 하는지 정확히 짚습니다. Kestrel 은 톰캣보다 설정 항목이 적습니다. 적은 이유도 함께 봅니다.

해부도 — Kestrel 설정은 Endpoints(어디서 받나) 와 Limits(얼마나 받나) 두 덩어리뿐입니다.

코드로 여는 방법 — 우선순위가 더 높습니다

var builder = WebApplication.CreateBuilder(args);

builder.WebHost.ConfigureKestrel(o =>
{
    // ① 평문 HTTP — 리버스 프록시 뒤라면 이것만 열면 됩니다
    o.ListenAnyIP(5000);

    // ② TLS 직접 종료 — 프록시 없이 단독 노출할 때
    o.ListenAnyIP(5001, l =>
    {
        l.UseHttps("/etc/ssl/payroll.pfx", "비밀번호");
        l.Protocols = HttpProtocols.Http1AndHttp2;
    });

    // ③ 유닉스 도메인 소켓 — Nginx 와 같은 서버에 있을 때 가장 빠름
    o.ListenUnixSocket("/var/run/payroll.sock");

    // ④ 루프백만 — 외부에서 직접 못 들어오게 잠급니다
    o.ListenLocalhost(5002);

    o.Limits.MaxConcurrentConnections   = 20_000;
    o.Limits.MaxRequestBodySize         = 300L * 1024 * 1024;
    o.Limits.KeepAliveTimeout           = TimeSpan.FromMinutes(2);
    o.Limits.RequestHeadersTimeout      = TimeSpan.FromSeconds(30);
    o.Limits.MinRequestBodyDataRate     =
        new MinDataRate(bytesPerSecond: 100, gracePeriod: TimeSpan.FromSeconds(10));

    o.AddServerHeader = false;          // Server: Kestrel 헤더를 숨깁니다
});

var app = builder.Build();
app.MapGet("/healthz", () => Results.Ok("ok"));
app.Run();

설정이 겹칠 때 누가 이기나

순위어디서예
1 (최강)ConfigureKestrel 코드ListenAnyIP(5000)
2ASPNETCORE_URLS 환경 변수http://0.0.0.0:5000
3--urls 명령행 인자dotnet app.dll --urls ...
4appsettings 의 Kestrel:EndpointsJSON 블록
5launchSettings.json개발 전용 — 서버에는 배포조차 안 됩니다
"로컬에선 5000 인데 서버에선 5000 이 아니에요" 사고의 90%가 이 표에서 나옵니다. launchSettings.json 은 Visual Studio 와 dotnet run 전용이고 publish 폴더에 들어가지 않습니다. 운영 포트는 환경 변수나 appsettings 로 정하세요.

HTTP/2 · HTTP/3 🟡 중급

프로토콜 켜기

builder.WebHost.ConfigureKestrel(o =>
{
    o.ListenAnyIP(443, l =>
    {
        l.UseHttps();
        // HTTP/3 는 QUIC(UDP 443) 위에서 돕니다.
        // Http1AndHttp2AndHttp3 로 켜면 브라우저가 알아서 협상합니다.
        l.Protocols = HttpProtocols.Http1AndHttp2AndHttp3;
    });
});
{
  "Kestrel": {
    "EndpointDefaults": { "Protocols": "Http1AndHttp2" }
  }
}
gRPC 를 쓴다면 HTTP/2 가 필수입니다 (🔷 w13 참고). 평문 HTTP/2(h2c)는 Protocols = Http2 로 TLS 없이도 열 수 있는데, Nginx 뒤에서 gRPC 를 중계할 때 이 조합을 씁니다.

HTTP/3 를 켜기 전 확인할 것

# 1) Linux 는 libmsquic 패키지가 필요합니다
sudo apt install -y libmsquic

# 2) 방화벽에 UDP 443 을 열어야 합니다 (TCP 만 열면 조용히 HTTP/2 로 떨어집니다)
sudo ufw allow 443/udp

# 3) 응답에 알림 헤더가 나가야 브라우저가 다음 요청부터 QUIC 을 씁니다
#    alt-svc: h3=":443"; ma=86400

# 4) 확인
curl --http3 -I https://payroll.corp.local/healthz
사내망에서 HTTP/3 는 대개 이득이 없습니다. QUIC 의 장점은 패킷 손실이 있는 모바일 회선에서 나옵니다. LAN 안이면 HTTP/2 로 충분하고, UDP 를 막는 사내 방화벽 때문에 문제만 늘어납니다.

Kestrel 을 단독으로 노출해도 되나 🔴 고급

단독 노출이 괜찮은 경우
  • 클라이언트가 사내 시스템뿐이고, 앞에 이미 L4/L7 로드밸런서(F5 · ALB)가 있는 경우
  • 컨테이너로 띄우고 Ingress 컨트롤러가 앞을 지키는 경우
  • Microsoft 공식 입장도 "인터넷 직접 노출도 지원한다" 입니다 — 보안 검토를 마쳤다면 문제 없습니다
앞에 무언가를 두는 편이 나은 경우
  • 한 포트에 여러 앱을 호스트명으로 나눠야 할 때 (Kestrel 도 SNI 로 되지만 관리가 번거롭습니다)
  • 정적 파일이 많을 때 — Nginx 가 훨씬 잘합니다
  • 인증서 갱신 · WAF · 접근 로그 · IP 차단을 앱 밖에서 하고 싶을 때
  • 느린 클라이언트 공격(Slowloris)을 앱 프로세스 앞에서 흡수하고 싶을 때
실무 답 — 사내 업무 시스템이라면 거의 항상 앞에 프록시를 둡니다. 기술적 필요보다 운영 편의 때문입니다 — 인증서를 한 곳에서 갱신하고, 점검 페이지를 앱과 무관하게 띄우고, 접근 로그를 통합할 수 있습니다. 자바에서 톰캣을 Nginx 뒤에 두던 그 이유와 정확히 같습니다.

스레드 모델 — 톰캣과 결정적으로 다른 점

톰캣은 maxThreads="200" 처럼 요청 하나에 스레드 하나를 배정했습니다 (가상 스레드가 나오기 전까지는). Kestrel 은 비동기 I/O 완성 포트 위에서 돌기 때문에 동시 요청 수와 스레드 수가 연결되어 있지 않습니다. 그래서 Kestrel 에는 maxThreads 에 해당하는 설정이 없습니다. 

// ❌ 이런 코드 한 줄이 그 장점을 통째로 날립니다
app.MapGet("/report", () =>
{
    var data = _http.GetStringAsync(url).Result;   // 스레드를 붙잡고 대기
    Thread.Sleep(2000);                            // 스레드풀 고갈의 시작
    return data;
});

// ✅ 끝까지 async
app.MapGet("/report", async (CancellationToken ct) =>
    await _http.GetStringAsync(url, ct));
.Result · .Wait() · Thread.Sleep 세 개가 .NET 서버 장애 원인 1위입니다. 자바의 Future.get() 남용과 같은 문제인데, Kestrel 은 스레드가 훨씬 적기 때문에 훨씬 빨리 터집니다 (h12 · h13).

요청 상한 세 곳 — 하나만 고치면 안 됩니다

// ① Kestrel 전역
builder.WebHost.ConfigureKestrel(o =>
    o.Limits.MaxRequestBodySize = 300L * 1024 * 1024);

// ② 엔드포인트 개별 (전역보다 우선)
app.MapPost("/upload", Upload)
   .WithMetadata(new RequestSizeLimitAttribute(300 * 1024 * 1024));

// ③ 폼 데이터는 별도 상한이 또 있습니다
builder.Services.Configure<FormOptions>(o =>
{
    o.MultipartBodyLengthLimit = 300L * 1024 * 1024;
    o.ValueLengthLimit         = int.MaxValue;
});
<!-- ④ IIS 뒤라면 web.config 에 하나 더 (바이트 단위, 기본 30 MB) -->
<security>
  <requestFiltering>
    <requestLimits maxAllowedContentLength="314572800" />
  </requestFiltering>
</security>
Nginx 를 앞에 두면 다섯 번째 상한이 생깁니다 — client_max_body_size (h06). 업로드가 실패하는데 앱 로그에 아무것도 안 남으면 가장 앞단에서 잘린 것입니다.
정리 — Kestrel 설정은 어디서 받나(Endpoints) 와 얼마나 받나(Limits) 두 덩어리이고, 톰캣의 maxThreads 에 해당하는 항목은 존재하지 않습니다. 대신 코드가 끝까지 async 인지가 그 자리를 대신합니다.

Windows ① — IIS 에 올리기

사내 시스템에서 가장 흔한 구성입니다. 이미 IIS 로 다른 사이트를 서비스하고 있고, 거기에 .NET 앱 하나를 얹는 그림입니다. 화면 단계와 web.config 전문까지 갑니다.

설치 순서가 중요합니다. IIS 를 먼저 켠 뒤 Hosting Bundle 을 설치하세요. 반대로 하면 모듈이 등록되지 않아 500.19 가 납니다. 이미 그랬다면 Hosting Bundle 을 복구(Repair) 로 다시 돌리면 됩니다.

자바 개발자를 위한 한 줄 요약

IIS 는 톰캣이 아닙니다. Apache 입니다. IIS 는 내 코드를 실행하지 않습니다 — 별도 프로세스로 앱을 띄우고 요청을 넘겨줄 뿐입니다. Apache 앞단 + mod_jk 조합에 가깝고, 차이는 Apache 는 톰캣을 직접 켜지 않지만 IIS 는 앱 프로세스를 직접 띄우고 감시한다는 점입니다.

좌우 대조 — in-process 는 프로세스가 하나, out-of-process 는 둘이고 그 사이에 HTTP 왕복이 있습니다.

그래도 out-of-process 를 고르는 경우

  • x86 / x64 가 섞일 때 — 앱 풀 비트와 앱 비트가 달라야 하는 레거시 상황
  • 같은 앱 풀에 여러 앱을 넣어야 할 때 (in-process 는 앱 풀 하나에 앱 하나가 원칙입니다)
  • Kestrel 고유 기능이 필요할 때 — HTTP/3 · 유닉스 소켓 · 커스텀 전송
  • 앱이 죽어도 IIS 작업자는 살아 있어야 할 때
<aspNetCore ... hostingModel="OutOfProcess" />
in-process 에서는 UseKestrel 설정이 대부분 무시됩니다. 웹 서버가 Kestrel 이 아니라 IIS HTTP 서버(IISHttpServer) 로 바뀌기 때문입니다. 포트 · 인증서 · 프로토콜은 전부 IIS 바인딩 에서 정합니다.

    throw "헬스체크 실패 — 롤백했습니다"
}
Write-Host "배포 완료"
정리 — Windows 서비스는 systemd 의 Windows 판입니다. 코드는 UseWindowsService() 한 줄, 등록은 sc.exe create 한 줄이고, 진짜 중요한 것은 ContentRootPath 지정(작업 디렉터리가 System32 라서)과 복구 옵션입니다.

여기는 자바와 거의 아무것도 바뀌지 않는 구간입니다. 다만 .NET 에는 반드시 켜야 하는 스위치가 하나 있습니다 — 안 켜면 접속자 IP 가 전부 127.0.0.1 로 찍힙니다.

/etc/nginx/sites-available/payroll.conf — 전문과 줄별 주석

# ── 업스트림: 앱 서버 목록 ─────────────────────────────────
upstream payroll_app {
    # keepalive 를 쓰려면 server 뒤에 포트, 그리고 아래 keepalive 지시자가 필요합니다.
    server 127.0.0.1:5000 max_fails=3 fail_timeout=10s;
    # 2대로 늘릴 때는 여기에 줄을 추가합니다 (h10 롤링 배포)
    # server 127.0.0.1:5001 max_fails=3 fail_timeout=10s;

    # 유닉스 소켓이 가장 빠릅니다 (같은 서버일 때)
    # server unix:/var/run/payroll.sock;

    # 커넥션 재사용 — 없으면 요청마다 TCP 핸드셰이크가 일어납니다
    keepalive 64;
    keepalive_timeout 60s;
}

# ── http → https 강제 ─────────────────────────────────────
server {
    listen 80;
    listen [::]:80;
    server_name payroll.corp.local;

    # Let's Encrypt 갱신용 경로만 예외로 둡니다 (h08)
    location /.well-known/acme-challenge/ { root /var/www/certbot; }

    location / { return 308 https://$host$request_uri; }
}

# ── 본 서버 ───────────────────────────────────────────────
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                                  # nginx 1.25+ 문법
    server_name payroll.corp.local;

    ssl_certificate     /etc/letsencrypt/live/payroll.corp.local/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/payroll.corp.local/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    # 업로드 상한 — 앱 설정(h02)보다 이쪽이 먼저 자릅니다
    client_max_body_size 300m;
    # 느린 클라이언트가 헤더를 질질 끄는 공격을 여기서 막습니다
    client_body_timeout  60s;
    client_header_timeout 20s;

    # 접근 로그에 응답 시간과 업스트림 시간을 같이 남깁니다
    access_log /var/log/nginx/payroll.access.log combined;
    error_log  /var/log/nginx/payroll.error.log warn;

    # ── 정적 파일은 Nginx 가 직접 (앱까지 안 갑니다) ───────
    location /static/ {
        alias /opt/payroll/wwwroot/;
        expires 30d;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # ── 나머지는 전부 앱으로 ───────────────────────────────
    location / {
        proxy_pass http://payroll_app;

        # keepalive 를 쓰려면 이 두 줄이 필수입니다 (기본은 HTTP/1.0)
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        # ★ 앱이 진짜 요청을 알 수 있게 알려 주는 네 줄 ★
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;

        # WebSocket / SignalR 업그레이드 (🔷 w06 참고)
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # 타임아웃 — 리포트 생성이 오래 걸리면 여기서 504 가 납니다
        proxy_connect_timeout 5s;
        proxy_send_timeout    300s;
        proxy_read_timeout    300s;

        # 버퍼링 — 스트리밍(SSE · 대용량 다운로드)에서는 꺼야 합니다
        proxy_buffering  on;
        proxy_buffers    16 16k;
        proxy_busy_buffers_size 64k;
    }

    # 서버가 보내는 이벤트 스트림은 버퍼링을 끕니다
    location /events {
        proxy_pass http://payroll_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }

    # 압축 — 앱에서 하지 말고 여기서 합니다 (CPU 절약)
    gzip on;
    gzip_types text/plain text/css application/json application/javascript;
    gzip_min_length 1024;

    # 보안 헤더
    add_header X-Content-Type-Options nosniff always;
    add_header X-Frame-Options SAMEORIGIN always;
    add_header Strict-Transport-Security "max-age=31536000" always;
}
# WebSocket 업그레이드용 map 은 http 블록(nginx.conf)에 한 번만 둡니다
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor
                       | ForwardedHeaders.XForwardedProto
                       | ForwardedHeaders.XForwardedHost;

    // ★ 신뢰할 프록시를 반드시 지정합니다.
    //   기본값은 루프백만 신뢰인데, 도커·쿠버네티스에서는 프록시가 다른 IP 라
    //   조용히 무시됩니다 — "켰는데 안 돼요"의 원인 1위.
    o.KnownProxies.Clear();
    o.KnownNetworks.Clear();
    o.KnownProxies.Add(IPAddress.Parse("10.10.0.5"));          // Nginx 서버
    o.KnownNetworks.Add(new IPNetwork(IPAddress.Parse("10.42.0.0"), 16)); // 파드 대역

    // 프록시가 몇 겹인지 (LB → Nginx → 앱 이면 2)
    o.ForwardLimit = 2;
});

app.UseAuthorization();

YARP — C# 으로 만드는 게이트웨이

Spring Cloud Gateway 자리에 오는 것이 YARP(Yet Another Reverse Proxy) 입니다. Nginx 와 달리 설정이 아니라 C# 코드로 라우팅을 바꿀 수 있습니다. 언제 Nginx 대신 이걸 고르는지가 이 섹션의 핵심입니다.

허브 — 게이트웨이의 값어치는 라우팅이 아니라 공통 관심사를 한 곳에 모으는 것입니다.

dotnet new web -o Gateway

언제 Nginx 대신 YARP 인가 🟡 중급

YARP 이 나은 경우
  • 라우팅 규칙이 C# 로직일 때 — 사번·부서·권한으로 목적지가 갈립니다
  • 인증을 게이트웨이에서 끝내고 싶을 때 — 사내 Entra ID / AD 를 그대로 씁니다
  • 레거시를 점진적으로 교체할 때 — 경로 하나씩 새 서비스로 넘깁니다 (Strangler Fig)
  • 운영팀이 Nginx 설정을 못 만지는 조직일 때 — 배포 파이프라인 안에서 관리됩니다
  • Windows 서버뿐이고 Nginx 를 깔 수 없을 때
Nginx 를 그대로 두는 편이 나은 경우
  • 하는 일이 단순 프록시 + TLS 종료 뿐일 때 — 프로세스를 하나 더 둘 이유가 없습니다
  • 정적 파일이 많을 때 — Nginx 가 압도적으로 빠릅니다
  • 이미 운영팀이 Nginx 로 표준화되어 있을 때
  • 앱과 게이트웨이가 같이 죽으면 안 될 때 — 런타임이 같으면 같은 사고에 함께 넘어집니다
실무에서 가장 흔한 조합 — Nginx(맨 앞, TLS·정적) → YARP(인증·라우팅) → 각 서비스. 두 개를 대립시킬 필요가 없습니다. Nginx 는 인프라 층, YARP 는 애플리케이션 층 게이트웨이입니다. Spring 쓰던 팀이 Nginx + Spring Cloud Gateway 를 함께 두던 것과 같은 그림입니다.
정리 — YARP 은 Spring Cloud Gateway 자리입니다. 설정만으로 되는 라우팅은 Nginx 로 충분하고, C# 로직이 필요한 라우팅·인증 통합·레거시 점진 교체가 YARP 을 고를 이유입니다.

sudo update-ca-certificates

#!/usr/bin/env bash
set -euo pipefail
SRC=$1
PORTS=(5000 5001)

for p in "${PORTS[@]}"; do
  echo "── 포트 $p 교체 ──"

  curl -fsS -X POST "http://127.0.0.1:$p/admin/drain" \
       -H "X-Admin-Key: $ADMIN_KEY"

  # 2) Nginx 가 이 인스턴스를 뺄 때까지 대기 (fail_timeout 만큼)
  sleep 12

  # 3) 교체 · 재시작
  sudo rsync -a --delete "$SRC"/ "/opt/payroll-$p"/
  sudo systemctl restart "payroll@$p"

  # 4) 살아날 때까지 대기 (최대 60초)
  for i in $(seq 1 60); do
    if curl -fsS "http://127.0.0.1:$p/healthz" >/dev/null 2>&1; then
      echo "포트 $p 정상 (${i}초)"; break
    fi
    [ "$i" -eq 60 ] && { echo "기동 실패 — 중단"; exit 1; }
    sleep 1
  done
done
echo "롤링 배포 완료"

// 준비 상태를 뒤집을 수 있는 플래그

    // liveness — 프로세스가 살아 있나 (재시작 판단용)

    // readiness — 트래픽을 받아도 되나 (LB 판단용)
    .AddCheck<ReadyCheck>("ready", tags: ["ready"])

    new() { Predicate = c => c.Tags.Contains("live") });

life.ApplicationStopping.Register(() =>
    app.Services.GetRequiredService<ReadinessState>().Ready = false);
liveness 와 readiness 를 반드시 나누세요. 하나로 합치면 DB 가 잠깐 끊겼을 때 앱이 재시작되는 사고가 납니다 — DB 는 곧 돌아오는데 앱만 계속 죽었다 살아납니다. liveness 는 프로세스 자체만 보고, 외부 의존성은 readiness 에만 넣습니다.

DB 마이그레이션과 배포 순서 🔴 고급

확장-축소(Expand–Contract) — 두 번에 나눠 배포

-- ❌ 한 번에 하면 무중단이 불가능합니다
ALTER TABLE Employee RENAME COLUMN Name TO FullName;
-- 구버전 앱은 Name 을, 신버전은 FullName 을 찾습니다.
-- 롤링 중에는 두 버전이 동시에 살아 있으므로 반드시 한쪽이 깨집니다.

-- ✅ 1차 배포 (확장) — 새 컬럼을 추가만 합니다
ALTER TABLE Employee ADD FullName NVARCHAR(100) NULL;
UPDATE Employee SET FullName = Name WHERE FullName IS NULL;
-- 앱 v2: 쓸 때는 둘 다, 읽을 때는 FullName 우선

-- ✅ 2차 배포 (축소) — v2 가 전부 뜬 뒤 다음 배포에서
ALTER TABLE Employee DROP COLUMN Name;
-- 앱 v3: FullName 만 사용
운영 DB 에 dotnet ef database update 를 앱 기동 중에 돌리지 마세요. 롤링 중이면 여러 인스턴스가 동시에 마이그레이션을 시도합니다. SQL 스크립트를 뽑아 배포 파이프라인에서 한 번만 실행하는 것이 정석입니다.

배포 순서 (하위 호환 스키마 원칙)

 2. 앱 롤링 배포 (v2)
 3. 확인 · 관찰 (하루~일주일)

블루그린 — 서버 두 벌(blue · green)을 통째로 두고 LB 를 한 번에 전환하는 방식입니다. 롤링보다 롤백이 압도적으로 빠릅니다(LB 를 되돌리면 끝). 대신 서버가 두 배 필요하고, DB 는 한 벌을 공유하므로 스키마 호환 문제는 그대로 남습니다. 사내 시스템에서는 가상 머신 스냅샷 + 롤링 조합이 비용 대비 효과가 좋습니다.
정리 — 무중단의 조건은 서버 2대 이상 + readiness 헬스체크 + 하위 호환 스키마 세 가지입니다. 1대뿐이면 app_offline.htm(IIS) 또는 소켓 활성화(systemd)로 중단 시간을 초 단위로 줄이는 것이 현실적인 목표입니다.

.NET 은 cgroup 제한을 읽습니다

자바에서 -XX:MaxRAMPercentage 를 안 주면 컨테이너 밖의 물리 메모리를 보고 힙을 잡아 OOMKill 이 나던 문제가 있었습니다. .NET Core 3.0 부터는 cgroup 제한을 자동으로 읽습니다 — 기본 동작이 안전합니다. 

# 컨테이너 안에서 런타임이 인식한 값 확인
docker exec payroll dotnet-counters monitor \
  --counters System.Runtime --process-id 1

# GCHeapHardLimit 은 기본적으로 컨테이너 제한의 75% 로 잡힙니다
# 예: limits.memory = 2G → 힙 상한 약 1.5G
# 필요하면 명시적으로 조정
DOTNET_GCHeapHardLimitPercent=50        # 16진수가 아닌 새 방식(.NET 8+)
DOTNET_GCConserveMemory=5               # 0~9 · 높을수록 메모리를 아낍니다
DOTNET_gcServer=1                       # 서버 GC (h12)
DOTNET_GCHeapCount=2                    # 서버 GC 힙 개수 = CPU 제한과 맞춤

CPU 제한과 서버 GC — 가장 흔한 함정

CPU 를 0.5 코어로 제한하고 서버 GC 를 켜면 성능이 크게 떨어집니다. 서버 GC 는 코어마다 힙과 GC 스레드를 만듭니다. 물리 코어가 32개인 호스트에서 컨테이너에 0.5 코어만 줬는데 GC 스레드가 32개 생기면 서로 CPU 를 뺏습니다. 
판단 기준

  CPU 제한 < 1 코어  → 워크스테이션 GC (DOTNET_gcServer=0)
  CPU 제한 1~2 코어  → 재 보고 결정. 대개 워크스테이션이 유리
  CPU 제한 ≥ 2 코어  → 서버 GC + DOTNET_GCHeapCount 를 코어 수에 맞춤

  참고: .NET 은 cgroup 의 cpu.max 를 읽어 Environment.ProcessorCount 를
        보정하지만, 소수점 코어(0.5)는 1로 올림됩니다.
사내 업무 시스템의 현실적 권고 — 컨테이너에 CPU 2코어 · 메모리 2GB 이상을 주고 서버 GC 를 켭니다. 그보다 작게 쪼갤 이유가 있다면 워크스테이션 GC 로 바꾸세요 (h12 에서 곡선으로 비교합니다).
