DEEP 01

CLR 구조 · JIT

C# 코드가 CPU 명령이 되기까지. 두 번 컴파일된다는 사실이 출발점입니다.

벤치마크에서 첫 실행을 버리는 이유가 여기 있습니다.

JIT 이 해 주는 일

  • 인라이닝 — 작은 메서드 호출을 본문으로 펼칩니다(속성 접근이 공짜인 이유)
  • 경계 검사 제거 — for (i = 0; i < arr.Length; i++) 형태를 알아보고 검사 제거
  • 죽은 코드 제거 — 상수 조건 분기를 통째로 삭제
  • 계층형 컴파일 — 자주 실행되면 더 좋은 코드로 교체(OSR)
  • 제네릭 특수화 — 값 타입은 타입마다 전용 코드를 만듭니다
arr.Length 를 변수에 담는 최적화는 이제 손해입니다. JIT 이 패턴을 인식해 경계 검사를 지우는데, 변수에 담으면 그 패턴이 깨져 오히려 검사가 남습니다.

직접 확인하기

# IL 보기
dotnet tool install -g ilspycmd
ilspycmd -il bin/Release/net10.0/App.dll

# JIT 이 실제로 만든 기계어 보기
DOTNET_JitDisasm="MyClass:Compute*" dotnet run -c Release
// 인라이닝 제어 (거의 쓸 일이 없지만 알아 두면 유용)
[MethodImpl(MethodImplOptions.AggressiveInlining)]
public static int Fast(int a, int b) => a + b;

[MethodImpl(MethodImplOptions.NoInlining)]      // 벤치마크에서 최적화 방지
public static void Measured() { }
Unity 는 이야기가 다릅니다. IL2CPP 는 IL 을 C++ 로 변환해 미리 컴파일합니다 — JIT 이 없어 워밍업도 없지만 런타임 최적화도 없습니다. 모바일에서 Mono(JIT) 보다 IL2CPP 가 빠른 이유이자, 리플렉션이 잘리는 이유이기도 합니다.
DEEP 02

메모리 배치 — 스택 · 힙 · 참조

"값 타입은 스택"은 절반만 맞습니다. 정확한 그림을 잡습니다.

실제 규칙

void M()
{
    int a = 1;              // 스택 (지역 변수)
    var p = new Point();    // 스택 (struct 지역 변수)
    var n = new Node();     // 참조는 스택, 객체 본체는 힙

    var list = new List<Point>();
    list.Add(p);            // ★ 이 Point 는 힙에 있습니다 (배열 안)
}

class Holder
{
    Point _p;               // ★ 이 struct 는 힙에 있습니다 (객체의 일부)
}
정확한 규칙 — 값 타입은 "자신이 놓인 곳"에 있습니다. 지역 변수면 스택, 객체의 필드면 힙, 배열 원소면 힙. "복사되는가"(값 의미)가 struct 의 본질이고, 스택/힙은 그 결과일 뿐입니다.

객체 하나의 비용

64비트에서 class 인스턴스
  객체 헤더(동기화 블록)   8 바이트
  메서드 테이블 포인터     8 바이트
  ─────────────────────── 최소 24 바이트 (정렬 포함)

즉 int 하나만 든 class 도 24바이트,
같은 내용의 struct 는 4바이트.
→ 작고 많은 데이터일수록 struct 가 유리한 이유
// 메모리 레이아웃 확인 (ObjectLayoutInspector)
TypeLayout.PrintLayout<Player>();

// 필드 순서만 바꿔도 크기가 줄어듭니다 (패딩)
struct Bad  { byte A; long B; byte C; }   // 24바이트
struct Good { long B; byte A; byte C; }   // 16바이트
struct 라고 항상 빠른 것은 아닙니다. 16~24바이트를 넘으면 복사 비용이 커져 오히려 class 가 낫습니다. 큰 struct 를 넘길 때는 in 매개변수로 복사를 막으세요.
GC 를 줄이는 것은 "스택에 올리기"가 아니라 "객체 수를 줄이기" 입니다 — 값 100만 개를 배열 하나에 담으면 힙 객체는 1개입니다.

struct 냐 class 냐 — 판단표

조건structclass이유
크기 16바이트 이하✓—복사가 참조보다 싸거나 비슷
크기 24바이트 초과—✓복사 비용이 커집니다(in 으로 완화 가능)
불변(만들고 안 바꿈)✓—readonly struct 로 방어 복사도 방지
수백만 개를 배열로✓✓—연속 메모리 · 객체 헤더 없음 · GC 부담 0
상속·다형성이 필요—✓struct 는 상속 불가
null 이 의미 있음—✓Nullable<T> 는 크기가 늘고 박싱 위험
인터페이스로 다룸주의✓박싱됩니다 — 제네릭 제약(where T : IFoo)으로 회피
컬렉션에 자주 넣고 뺌주의✓복사가 반복됩니다

눈에 안 보이는 할당 — 이것들을 찾아야 합니다

// ① 박싱 — struct 를 object·인터페이스로 다루는 순간
int n = 42;
object o = n;                       // 힙에 24바이트
Console.WriteLine("값 " + n);       // n.ToString() → 문자열 할당
list.Add(n);                        // List<object> 면 박싱, List<int> 면 안 함

// 인터페이스 호출도 박싱
IComparable c = n;                  // ✗ 박싱
static int Cmp<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b);  // ✓ 안 함

// ② 클로저 — 람다가 바깥 변수를 잡으면 클래스가 하나 생깁니다
for (var i = 0; i < 1000; i++)
    items.Where(x => x.Id == i);    // ✗ i 를 캡처 → 반복마다 클로저 객체

// 캡처를 없애면 할당이 사라집니다
items.Where(static x => x.Id > 0);  // ✓ static 람다 (C# 9+)

// ③ params · LINQ · foreach 의 숨은 할당
void Log(params object[] a) { }     // 호출마다 배열 할당
Log("a", 1, true);                  //   + int·bool 박싱 2회

foreach (var x in (IEnumerable<int>)array)  // ✗ 열거자가 박싱됨
foreach (var x in array)                     // ✓ 배열은 구조체 열거자

// ④ 문자열 — 게임 루프에서 가장 흔한 범인
label.Text = "HP: " + hp;                    // ✗ 매 프레임 문자열 할당
label.Text = string.Create(...)              // ✓ 또는 값이 바뀔 때만 갱신

// ⑤ async 상태 기계 — 완료된 경우가 많으면 ValueTask
public async ValueTask<int> GetAsync(int id)   // 캐시 적중이 잦으면 할당 회피
{
    if (_cache.TryGetValue(id, out var v)) return v;   // 동기 완료 → 할당 없음
    return await LoadAsync(id);
}
이 최적화들은 "게임 루프·초당 수만 번" 자리에서만 의미가 있습니다. 웹 요청 처리에서 클로저 하나를 없애는 것은 DB 쿼리 한 번 앞에서 아무 의미가 없습니다. 먼저 측정하고(BenchmarkDotNet · dotnet-counters), 할당이 실제로 병목인 자리에만 적용하세요.

레이아웃을 직접 확인하고 줄이기

// 패딩 때문에 필드 순서가 크기를 바꿉니다 (64비트, 8바이트 정렬)
struct Bad                          // 24바이트
{
    byte A;    // 1 + 패딩 7
    long B;    // 8
    byte C;    // 1 + 패딩 7
}

struct Good                         // 16바이트
{
    long B;    // 8
    byte A;    // 1
    byte C;    // 1 + 패딩 6
}

// 확인: dotnet add package ObjectLayoutInspector
TypeLayout.PrintLayout<Bad>();
// Size: 24 bytes. Paddings: 14 bytes (%58 of empty space)

// 큰 struct 를 복사 없이 넘기기
static float Dist(in Matrix4x4 a, in Matrix4x4 b) { ... }   // 64바이트 × 2 복사 방지

// readonly struct — 방어 복사(defensive copy)까지 없앱니다
public readonly struct Vec3(float x, float y, float z)
{
    public readonly float X = x, Y = y, Z = z;
    public float Length => MathF.Sqrt(X * X + Y * Y + Z * Z);
}
// readonly 가 아니면 in 매개변수에서 메서드를 부를 때마다 복사본이 생깁니다

// ref struct — 스택에만 존재하도록 컴파일러가 강제
ref struct Reader
{
    ReadOnlySpan<byte> _buf;        // 힙에 올라갈 수 없으니 안전
}
기법없애는 것대가
readonly struct방어 복사불변이어야 함
in 매개변수인자 복사readonly 아니면 역효과
ref struct힙 승격 가능성필드·async·컬렉션에 못 넣음
Span<T>배열 복사·슬라이스 할당수명 제약
ArrayPool<T>큰 배열 반복 할당반드시 Return · 내용 초기화 안 됨
stackalloc작은 임시 버퍼 할당크기 상한 필수(스택 오버플로)
85KB 를 넘는 배열은 LOH(대형 객체 힙)로 갑니다. LOH 는 기본적으로 압축하지 않아 단편화가 쌓이고, 수집이 Gen2 와 함께 일어나 멈칫하는 시간이 깁니다. 큰 버퍼는 ArrayPool<byte>.Shared 로 재사용하는 것이 AOT·GC 튜닝 어느 쪽보다 효과가 큽니다.
DEEP 03

GC 내부 — 세대 · LOH · 서버 GC

언제 멈추고 얼마나 멈추는지. 게임의 프레임 튐과 서버의 p99가 여기서 결정됩니다.

세대 가설

Gen 0
갓 만들어진 객체 — 대부분 금방 죽는다 수집이 매우 쌉니다(밀리초 이하). 자주 일어납니다.
Gen 1
Gen0 을 한 번 살아남은 것 완충 지대. 여전히 쌉니다.
Gen 2
오래 사는 객체 — 캐시·싱글턴 수집이 비쌉니다. 여기가 자주 돌면 문제입니다.
LOH
85KB 이상 — 큰 배열·버퍼 Gen2 와 함께 수집되고 기본적으로 압축하지 않습니다(단편화).
// 수집 횟수 확인 — Gen2 가 자주 늘면 설계를 봐야 합니다
Console.WriteLine($"G0={GC.CollectionCount(0)} G1={GC.CollectionCount(1)} G2={GC.CollectionCount(2)}");
Console.WriteLine($"할당 총량 {GC.GetTotalAllocatedBytes() / 1024 / 1024} MB");

설정과 대책

<PropertyGroup>
  <!-- 서버: 코어마다 힙과 스레드 → 처리량 ↑ (메모리 사용 ↑) -->
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
  <!-- 컨테이너에서는 힙 상한을 명시 -->
  <GCHeapHardLimitPercent>75</GCHeapHardLimitPercent>
</PropertyGroup>
  • 서버 GC — 처리량 우선. API·게임 서버에 권장
  • 워크스테이션 GC — 지연 우선. 데스크탑 앱에 적합
  • LOH 압축은 필요할 때만 GCSettings.LargeObjectHeapCompactionMode
  • 큰 버퍼는 ArrayPool 로 재사용 — LOH 단편화의 근본 대책
GC.Collect() 를 코드에 넣지 마세요. 런타임의 판단을 방해해 대개 더 느려집니다. 예외는 게임의 씬 전환 직후처럼 "지금 멈춰도 되는 순간"이 명확한 경우뿐입니다.
GC 를 끄거나 부르는 것이 아니라 세대 구조에 맞게 쓰는 것이 튜닝입니다.
DEEP 04

메모리 누수 추적

.NET 에도 누수가 있습니다. "아무도 안 쓰는데 누군가 붙잡고 있는" 상태입니다.

범인 다섯

  • 이벤트 미해지 — += 하고 -= 안 함 (1순위)
  • static 컬렉션 — 캐시에 넣고 안 지움
  • 타이머·구독 — Timer·IDisposable 미해제
  • 클로저 — 람다가 큰 객체를 잡고 있음
  • Task 누적 — 완료되지 않는 작업이 쌓임
// 약한 참조로 캐시 (필요하면 GC 가 회수)
private readonly ConditionalWeakTable<Player, Stats> _stats = new();

// 이벤트를 안전하게 — 구독 해제를 IDisposable 로 반환
public IDisposable Subscribe(Action<int> h)
{
    Changed += h;
    return new Unsubscriber(() => Changed -= h);
}

찾는 절차

# ① 메모리가 실제로 느는지 확인
dotnet-counters monitor -p <PID> \
  System.Runtime[dotnet.gc.heap.size,dotnet.gc.collections]

# ② 시점을 달리해 덤프 두 개
dotnet-dump collect -p <PID> -o before.dmp
# ... 부하를 준 뒤 ...
dotnet-dump collect -p <PID> -o after.dmp

# ③ 무엇이 늘었는지 비교
dotnet-dump analyze after.dmp
> dumpheap -stat                 # 타입별 개수·크기
> gcroot <주소>                   # 누가 붙잡고 있는지 ★
> dumpobj <주소>
gcroot 가 핵심입니다. "이 객체를 누가 참조하고 있는가"를 루트까지 거슬러 보여 줍니다. 대부분 여기서 이벤트 핸들러나 static 필드가 나옵니다.
Unity 는 별도 도구가 필요합니다. Memory Profiler 패키지로 스냅샷을 두 개 찍어 비교하세요. 씬을 다시 로드해도 옛 오브젝트가 남아 있으면 누수입니다.
DEEP 05

async 의 정체 — 상태 기계

await 는 컴파일러가 메서드를 잘게 쪼개 상태 기계로 다시 씁니다.

무슨 코드로 바뀌는가

// 내가 쓴 코드
async Task<int> GetAsync()
{
    var a = await LoadAsync();     // ← 여기서 잘린다
    return a + 1;
}

// 컴파일러가 만드는 것 (개념)
struct StateMachine : IAsyncStateMachine
{
    int _state;
    TaskAwaiter<int> _awaiter;

    public void MoveNext()
    {
        switch (_state)
        {
            case -1:
                _awaiter = LoadAsync().GetAwaiter();
                if (!_awaiter.IsCompleted)      // ★ 이미 끝났으면 그냥 진행
                {
                    _state = 0;
                    _builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);
                    return;                     // 스레드를 놓는다
                }
                goto case 0;
            case 0:
                var a = _awaiter.GetResult();
                _builder.SetResult(a + 1);
                return;
        }
    }
}

여기서 나오는 실무 결론

  • 이미 완료된 작업은 상태 기계를 타지 않습니다 — 캐시 히트가 많으면 ValueTask 가 유효합니다
  • async 메서드마다 상태 기계 객체가 생깁니다 — 아주 뜨거운 경로에서는 이것도 비용입니다
  • await 이후는 다른 스레드일 수 있습니다 — ThreadStatic·UI 접근에 주의
  • SynchronizationContext 가 있으면 원래 컨텍스트로 돌아옵니다 (UI·Unity). 서버(ASP.NET Core)에는 없습니다
// 라이브러리 코드라면 컨텍스트 복귀를 끄는 것이 표준
await SomethingAsync().ConfigureAwait(false);

// 앱 코드(ASP.NET Core)에서는 컨텍스트가 없어 붙일 필요가 없습니다
"async 를 쓰면 스레드가 늘어난다"는 오해입니다. 오히려 스레드를 덜 쓰기 위해 쓰는 것입니다. 대기 중에는 어떤 스레드도 그 작업을 붙잡고 있지 않습니다.
async 는 스레드를 만드는 것이 아닙니다 — 기다리는 동안 자리를 비켜 주는 것입니다.
DEEP 06

스레드 풀 · 기아 현상

서버가 갑자기 전부 느려지는 현상의 대표적인 원인입니다.

무슨 일이 일어나는가

스레드 풀 기아(starvation) — .Result 로 비동기를 기다리는 코드가 여럿이면 스레드가 전부 대기 상태로 묶입니다. 풀은 1초에 1~2개씩만 스레드를 늘리므로 회복이 매우 느리고, 그동안 모든 요청이 지연됩니다. 
// 증상 확인
ThreadPool.GetAvailableThreads(out var worker, out var io);
Console.WriteLine($"여유 스레드 {worker}");

// 지표로 감시 (급증하면 기아)
dotnet-counters monitor -p <PID> \
  System.Runtime[dotnet.threadpool.queue.length,dotnet.threadpool.thread.count]

고치는 법

  • 동기 차단 제거 — .Result·.Wait()·lock 안의 IO
  • 동기 API 는 동기 스레드로 — 레거시 라이브러리는 전용 큐로 분리
  • 최소 스레드 상향은 임시방편 — 근본 원인을 고치세요
  • CPU 작업을 요청 스레드에서 하지 말고 Task.Run 으로
// 임시 완화 (진짜 해결이 아님을 알고 쓰세요)
ThreadPool.SetMinThreads(workerThreads: 200, completionPortThreads: 200);
게임 서버에서는 다른 각도로도 옵니다. 룸 루프를 Task.Run 으로 수백 개 띄우면 풀 스레드를 전부 점유합니다. 장시간 도는 루프는 전용 스레드 (new Thread { IsBackground = true })로 만드세요.
"CPU 는 놀고 있는데 응답이 느리다" — 이 조합을 보면 가장 먼저 스레드 풀 기아를 의심하세요.

기아를 만드는 코드 — 실제로 자주 보는 것들

// ① 가장 흔함 — 동기 메서드 안에서 비동기 호출
public User Get(int id) => _repo.GetAsync(id).Result;          // ✗
public Task<User> GetAsync(int id) => _repo.GetAsync(id);      // ✓ 끝까지 async

// ② 생성자·프로퍼티에서 — async 를 못 쓰니 여기서 막습니다
public class Service
{
    private readonly Config _cfg;
    public Service(IConfigLoader l) => _cfg = l.LoadAsync().GetAwaiter().GetResult();  // ✗
}
// ✓ 팩토리 메서드나 IHostedService 로 시작할 때 한 번 로드

// ③ 이벤트 핸들러 — 인터페이스가 동기라서
public void OnMessage(Message m) => HandleAsync(m).Wait();     // ✗
public void OnMessage(Message m) => _channel.Writer.TryWrite(m); // ✓ 큐에 넣고 반환

// ④ lock 안에서 IO — 스레드가 묶이고 다른 스레드도 막힙니다
lock (_gate) { var r = _http.GetStringAsync(url).Result; }      // ✗
await _semaphore.WaitAsync(ct);                                 // ✓ SemaphoreSlim
try { var r = await _http.GetStringAsync(url, ct); }
finally { _semaphore.Release(); }

// ⑤ 동기 IO 를 요청 스레드에서
var text = File.ReadAllText(path);                              // ✗ 디스크가 느리면 묶임
var text = await File.ReadAllTextAsync(path, ct);               // ✓

// ⑥ 병렬 처리에 Parallel.For 로 비동기를 섞기
Parallel.For(0, 100, i => DoAsync(i).Wait());                   // ✗ 최악
await Parallel.ForEachAsync(items, ct, async (x, t) => await DoAsync(x, t)); // ✓
레거시 라이브러리가 동기 API 만 제공한다면 .Result 로 감싸지 말고 전용 스레드나 별도 큐로 격리하세요. Task.Run(() => SyncCall()) 도 스레드풀을 쓰므로 동시 호출 수를 SemaphoreSlim 으로 제한해야 풀 전체로 번지지 않습니다.

foreach (var room in rooms) _ = Task.Run(() => room.LoopForever());

DEEP 07

메모리 모델 · 락 프리

CPU 와 컴파일러는 순서를 바꿉니다. 멀티스레드 버그의 근원입니다.

재배치와 가시성

// 이 코드는 '영원히 끝나지 않을 수' 있습니다
private bool _stop;              // ✗
public void Run() { while (!_stop) { } }     // JIT 이 레지스터에 캐시
public void Stop() => _stop = true;

// ① volatile — 항상 메모리에서 읽고 쓴다
private volatile bool _stop;     // ✓

// ② Interlocked — 원자적 연산
Interlocked.Increment(ref _count);
Interlocked.Exchange(ref _state, 1);
var prev = Interlocked.CompareExchange(ref _state, 1, 0);   // 0이면 1로

// ③ lock — 가장 쉽고 안전 (진입·탈출 시 메모리 장벽)
lock (_gate) { _count++; }
volatile 은 원자성을 주지 않습니다. _count++ 는 읽기+더하기+쓰기 세 단계라 volatile 을 붙여도 경쟁이 그대로 남습니다. 수치 연산은 Interlocked, 복합 로직은 lock 입니다.

락 프리는 최후에

// CAS 루프 — 성공할 때까지 재시도
public void AddMax(ref long field, long value)
{
    long cur;
    do
    {
        cur = Volatile.Read(ref field);
        if (value <= cur) return;
    }
    while (Interlocked.CompareExchange(ref field, value, cur) != cur);
}

// 카운터는 전용 타입이 훨씬 빠릅니다 (경합이 심할 때)
private readonly PaddedCounter _hits;   // false sharing 방지 패딩
락 프리 코드는 검증이 매우 어렵습니다. ABA 문제·false sharing·메모리 장벽을 모두 고려해야 하고, 틀려도 대부분의 실행에서는 잘 동작합니다. 측정으로 락이 병목임을 확인한 뒤에만 손대세요.
더 나은 방법은 공유를 없애는 것입니다. 게임 서버의 룸 하나 = 스레드 하나 구조처럼 데이터를 나눠 가지면 동기화 자체가 필요 없어집니다.
DEEP 08

캐시 라인 · 데이터 지역성

요즘 CPU 에서 느린 것은 계산이 아니라 메모리에서 값을 가져오는 시간입니다.

배열 vs 객체 배열

// 객체 배열 — 메모리에 흩어져 있다 (캐시 미스)
class Enemy { public float X, Y; public int Hp; /* ... 그 밖에 많은 필드 */ }
Enemy[] enemies;                       // 참조 배열 → 실제 객체는 여기저기

foreach (var e in enemies) e.X += 1;   // 매번 다른 메모리로 점프

// 구조 배열(SoA) — 붙어 있다
float[] xs, ys;                        // 좌표만 연속으로
for (int i = 0; i < xs.Length; i++) xs[i] += 1;   // 순차 접근 · 캐시 적중
Unity 의 DOTS/ECS 가 빠른 이유가 정확히 이것입니다. 같은 종류의 데이터를 연속된 메모리에 모아 캐시 미스를 없애고 SIMD 를 쓸 수 있게 합니다 (🕹️ Unity 실전 탭 06).

false sharing

// 서로 다른 스레드가 '같은 캐시 라인(64B)'의 값을 만지면
// 실제로는 관계없는 데이터인데도 캐시가 계속 무효화됩니다
class Counters
{
    public long A;     // 스레드 1이 증가
    public long B;     // 스레드 2가 증가  ← 같은 라인에 있으면 서로 방해
}

// 패딩으로 떼어 놓기
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedLong { [FieldOffset(64)] public long Value; }
  • 증상 — 코어를 늘렸는데 오히려 느려짐
  • 확인 — 스레드별 카운터를 따로 두고 마지막에 합치기로 바꿔 비교
  • 대안 — ThreadLocal<T> · 파티션별 집계
이 최적화는 마지막에 하세요. 알고리즘·할당·IO 를 먼저 잡고, 프로파일러가 메모리 대기(stall)를 가리킬 때만 의미가 있습니다.
"메모리는 다 똑같이 빠르다"는 전제가 성능 오해의 절반을 만듭니다.
DEEP 09

JIT 없이 미리 기계어로. 시작이 즉시이고 메모리가 적습니다 — 대신 제약이 있습니다.

쓰는 법과 효과

→ 서버리스 · CLI 도구 · 컨테이너 밀집 배치에서 큰 이득

포기해야 하는 것

  • 런타임 리플렉션이 제한됩니다 — 타입을 문자열로 찾는 코드가 깨집니다

  • 플러그인 로딩(Assembly.LoadFrom) 불가
  • 빌드 시간이 길어집니다

누수의 전형왜 안 죽나고치는 법
정적 컬렉션루트에서 계속 참조만료·크기 제한 · MemoryCache
이벤트 핸들러발행자가 구독자를 붙잡음-= 로 해제 · 약한 참조
타이머콜백이 객체를 캡처Dispose · PeriodicTimer
취소 토큰 등록장수 토큰에 계속 등록등록 반환값을 Dispose
캐시 무제한—SizeLimit + 만료
HttpClient 매번 생성소켓·핸들러 누적IHttpClientFactory
LOH 단편화큰 배열이 흩어짐ArrayPool · 압축 모드
이벤트 핸들러 누수는 데스크탑·Unity 에서 압도적으로 흔합니다. _service.DataChanged += OnChanged; 만 하고 해제하지 않으면 서비스가 살아 있는 한 창(ViewModel)도 못 죽습니다. 창을 100번 열었다 닫으면 100개가 메모리에 남습니다. 구독한 자리마다 해제할 자리를 함께 만드는 습관이 유일한 예방책입니다.

// 코드로 진단 정보를 노출 — 운영 도구에서 바로 볼 수 있게
app.MapGet("/admin/diag", () =>
{
    ThreadPool.GetAvailableThreads(out var w, out var io);
    ThreadPool.GetMaxThreads(out var mw, out var mio);
    var gc = GC.GetGCMemoryInfo();

    return Results.Ok(new
    {
        threadPool = new { busyWorker = mw - w, busyIo = mio - io,
                           pending = ThreadPool.PendingWorkItemCount },
        gc = new
        {
            heapMb  = GC.GetTotalMemory(false) / 1_048_576,
            gen0 = GC.CollectionCount(0), gen1 = GC.CollectionCount(1),
            gen2 = GC.CollectionCount(2),
            pauseTimePercent = gc.PauseTimePercentage,
            fragmentedMb = gc.FragmentedBytes / 1_048_576
        },
        uptime = Environment.TickCount64 / 1000,
        version = Environment.GetEnvironmentVariable("APP_VERSION")
    });
}).RequireAuthorization("admin");
사고가 난 뒤에 도구를 설치하려 하면 이미 늦습니다. 프로세스는 대개 재시작되었거나 곧 재시작됩니다. DOTNET_DbgEnableMiniDump 를 지금 켜 두면 다음 크래시의 원인을 단번에 알 수 있습니다. 덤프 저장 경로는 컨테이너 밖(볼륨)으로 잡으세요 — 컨테이너와 함께 사라지면 아무 소용이 없습니다.
DEEP 11

보안 — 역직렬화 · 공급망

내가 쓴 코드보다 가져다 쓴 패키지와 남이 보낸 데이터가 더 위험합니다.

역직렬화

타입 정보를 데이터가 정하게 하면 원격 코드 실행이 됩니다. BinaryFormatter 는 .NET 9 에서 제거되었고, TypeNameHandling.All(Newtonsoft) 도 같은 위험을 만듭니다. 
// ✗ 절대 금지
var obj = new BinaryFormatter().Deserialize(stream);
JsonConvert.DeserializeObject(json,
    new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.All });

// ✓ 받을 타입을 코드가 정한다
var dto = JsonSerializer.Deserialize<PlayerDto>(json, _opt);

// 크기·깊이 상한도 두세요
var opt = new JsonSerializerOptions { MaxDepth = 16 };
  • 게임 패킷도 같은 원칙 — 패킷 id 로 서버가 타입을 정합니다
  • 세이브 파일도 남이 수정할 수 있는 입력으로 취급

DEEP 12

최적화의 순서

여기까지 온 도구를 어떤 순서로 쓸 것인가. 순서를 틀리면 시간을 버립니다.

단계

1
측정 — 어디가 느린가 프로파일러 없이 시작하지 마세요. 체감 문제부터 정의합니다(프레임 튐? p99? 시작 시간?).
2
없애기 — 아예 안 하기 불필요한 호출·중복 계산·과한 로그. 가장 큰 효과가 여기서 나옵니다.
3
줄이기 — 덜 하기 캐시 · 배칭 · 페이징 · AOI. 알고리즘과 데이터 양의 문제입니다.
4
빠르게 — 같은 일을 싸게 Span · 풀링 · struct · SIMD. 여기까지 와야 미시 최적화가 의미가 있습니다.
4번부터 시작하는 것이 가장 흔한 실수입니다. 전체의 0.1% 를 5배 빠르게 만들어도 체감은 0 입니다.
