SQ 01

한 장 지도 — C# 은 무엇으로 쓰나

스택 · 큐 · 덱 · 우선순위 큐 · 스레드 안전 큐 · 비동기 채널 — 여섯 가지 일을 .NET 이 각각 어떤 타입으로 하는지, 그리고 무엇을 새 코드에서 쓰면 안 되는지를 먼저 한 장으로 정리합니다. 이 표 하나만 외워 두면 나머지 섹션은 "왜 그런가"를 확인하는 과정입니다.

SQ 02

스택 — Stack<T> 하나면 됩니다

Stack<T> 의 속은 배열 _array 와 개수 _size 두 필드가 전부입니다. 그래서 빠르고 단순하지만, 열거 순서가 꼭대기부터라는 점과 빈 스택에서 Pop 하면 예외라는 점은 꼭 알고 써야 합니다.

기본 사용 — 출력까지

// Program.cs (.NET 10 · top-level)
var s = new Stack<int>();
s.Push(10);
s.Push(20);
s.Push(30);

Console.WriteLine(s.Peek());               // 30 (꺼내지 않고 보기)
Console.WriteLine(s.Count);                // 3
Console.WriteLine(string.Join(",", s));    // 30,20,10  ← 꼭대기부터!

Console.WriteLine(s.Pop());                // 30
Console.WriteLine(s.Contains(10));         // True  (O(n) 선형 탐색)

// ★ 비울 때까지 꺼내기 — Count 확인 + Pop 대신 TryPop 한 번
while (s.TryPop(out var top))
    Console.Write($"{top} ");              // 20 10
Console.WriteLine();

// 빈 스택에서 Pop / Peek → 예외
try { s.Pop(); }
catch (InvalidOperationException e)
{
    Console.WriteLine(e.Message);          // Stack empty.
}
Try 패턴이 기본입니다. TryPop(out T) · TryPeek(out T) 는 비어 있으면 false 를 돌려줍니다. "비어 있을 수 있다"가 정상 흐름이면 Try, "비어 있으면 버그다"면 Pop 으로 예외를 내게 둡니다 — 예외를 흐름 제어에 쓰지 않는다는 .NET 의 규칙 그대로입니다.

인덱서가 없습니다. s[0] 은 컴파일되지 않습니다. 중간 요소를 봐야 한다면 그건 스택이 아니라 List<T> 를 스택처럼 쓰는 상황입니다 (list.Add = Push, list[^1] = Peek, list.RemoveAt(list.Count - 1) = Pop — 셋 다 O(1)). 자바 Stack 이 비판받은 "중간 삽입이 된다"는 문제가 C# 에는 애초에 없습니다.
Stack<T> 은 끝에만 붙이는 배열입니다. 꼭대기가 배열 끝이라 열거는 끝에서 앞으로 돕니다.

비제네릭 System.Collections.Stack 이 레거시가 된 이유 🟡 중급

System.Collections.Stack (.NET 1.0)
using System.Collections;

var s = new Stack();          // 요소 타입이 object
s.Push(1);                    // int → object 박싱 (힙 할당 24바이트)
s.Push("문자열");             // 아무거나 들어감 — 컴파일러가 못 막음

int n = (int)s.Pop();         // 💥 InvalidCastException (런타임!)
                              //    꺼낸 건 "문자열" 이었음
Stack<T> (.NET 2.0~)
var s = new Stack<int>();     // T 가 int 로 고정
s.Push(1);                    // int 배열에 그대로 — 박싱 없음
// s.Push("문자열");          // ❌ 컴파일 에러 CS1503

int n = s.Pop();              // 캐스트 불필요 · 실패할 일 없음

무엇이 다른가

  • 박싱 — 비제네릭은 내부가 object[] 라 값 타입을 넣을 때마다 힙에 상자를 만듭니다. 100만 번 Push 면 100만 번 할당입니다.
  • 타입 안전 — 잘못된 타입이 섞여도 꺼낼 때 런타임에야 터집니다.
  • Stack.Synchronized(s) — 메서드마다 락을 거는 래퍼인데, "Count 확인 후 Pop" 같은 두 동작 사이는 보호하지 못해 실제로는 안전하지 않았습니다. 지금은 ConcurrentStack<T> 가 그 자리를 대신합니다.
  • 타입은 지금도 남아 있고 [Obsolete] 도 아닙니다 — 옛 코드 호환용일 뿐입니다.
레거시 코드를 고칠 때 순서를 조심하세요. new Stack(collection) · new Stack<T>(collection) 모두 컬렉션을 앞에서부터 차례로 Push 합니다. 그래서 스택을 스택으로 복사하면 순서가 뒤집힙니다 — 바로 아래에서 봅니다.

열거 순서와 복사 — 꼭대기부터가 만드는 함정 🟡 중급

var s = new Stack<int>([1, 2, 3]);   // 1,2,3 차례로 Push → 꼭대기 3
// 컬렉션 식을 생성자 인자로 넘김 (C# 12+)
// Stack<int> t = [1, 2, 3];          // ❌ Stack 에는 Add 가 없어 안 됨

Console.WriteLine(string.Join(",", s));           // 3,2,1
Console.WriteLine(string.Join(",", s.ToArray())); // 3,2,1 (ToArray 도 꼭대기부터)

var copy = new Stack<int>(s);           // ⚠ 3,2,1 순서로 Push → 꼭대기 1
Console.WriteLine(copy.Peek());          // 1   ← 뒤집혔다!

var same = new Stack<int>(s.Reverse());  // LINQ Reverse: 1,2,3 → 꼭대기 3
Console.WriteLine(same.Peek());          // 3   ← 원본과 같음

왜 이렇게 설계됐나

열거를 Pop 할 순서와 맞춘 것입니다. foreach 로 훑은 순서가 그대로 앞으로 꺼낼 순서라 "다음에 처리될 것부터 보여 주기"에는 자연스럽습니다. 문제는 생성자는 앞에서부터 Push 한다는 점이 겹칠 때입니다.

스택을 복제할 일이 잦다면 그 자체가 신호입니다. undo 이력처럼 "이전 상태를 보존"해야 한다면 복사 대신 ImmutableStack<T>(SQ 08)를 쓰세요 — Push 가 새 스택을 돌려주고 꼬리를 공유하므로 복사 비용이 0 이고 순서 함정도 없습니다.

Unity — 오브젝트 풀은 Stack<T> 🟡 중급

using UnityEngine;

public sealed class BulletPool : MonoBehaviour
{
    [SerializeField] private Bullet prefab;
    private readonly Stack<Bullet> _idle = new(64);  // 미리 64칸

    public Bullet Rent(Vector3 pos)
    {
        // 남은 게 있으면 재사용, 없으면 새로 — Try 패턴으로 한 번에
        var b = _idle.TryPop(out var cached) ? cached : Instantiate(prefab);
        b.transform.position = pos;
        b.gameObject.SetActive(true);
        return b;
    }

    public void Return(Bullet b)
    {
        b.gameObject.SetActive(false);
        _idle.Push(b);           // 방금 쓴 것이 다음에 먼저 나감 (LIFO)
    }
}

왜 큐가 아니라 스택인가

  • 방금 반납한 객체가 CPU 캐시에 아직 남아 있을 확률이 높습니다 — LIFO 가 FIFO 보다 유리합니다.
  • 스택은 꼭대기 하나만 만지므로 인덱스 계산이 가장 단순합니다.
  • Unity 2021.1+ 의 UnityEngine.Pool.ObjectPool<T> 도 같은 LIFO 방식으로 재사용합니다 — 직접 짜기 싫으면 그것을 쓰세요.
같은 객체를 두 번 Return 하면 스택에 두 번 들어가 두 곳에서 동시에 쓰입니다. Stack.Contains 로 막으면 O(n) 이니, 객체에 bool InPool 플래그를 두고 검사하세요. (ObjectPool<T> 는 collectionCheck 옵션이 에디터에서 이를 잡습니다.)
정리 — 스택은 Stack<T> + TryPop. 열거와 ToArray 는 꼭대기부터, 생성자는 앞에서부터 Push — 둘이 만나면 뒤집힙니다.
SQ 03

큐 (FIFO) — Queue<T> 와 원형 배열

Queue<T> 는 배열 하나를 원형으로 돌려 쓰는 구조입니다. 앞에서 꺼내도 뒤 요소를 당기지 않으므로 Enqueue · Dequeue 가 모두 O(1) 입니다. 이 점이 List<T>.RemoveAt(0) 과의 결정적 차이입니다.

기본 사용 — 예외형과 Try 형

var q = new Queue<string>();
q.Enqueue("1번 손님");
q.Enqueue("2번 손님");
q.Enqueue("3번 손님");

Console.WriteLine(q.Peek());      // 1번 손님 (꺼내지 않음)
Console.WriteLine(q.Dequeue());   // 1번 손님
Console.WriteLine(q.Count);       // 2
Console.WriteLine(string.Join(" / ", q));   // 2번 손님 / 3번 손님 (앞부터)

// 처리 루프 — 표준 관용구
while (q.TryDequeue(out var who))
    Console.WriteLine($"처리: {who}");
// 처리: 2번 손님
// 처리: 3번 손님

Console.WriteLine(q.TryPeek(out _));   // False
// q.Dequeue();   // 💥 InvalidOperationException: Queue empty.

"실패하면 예외" vs "실패하면 false"

동작예외형Try 형자바 Queue 대응
넣기Enqueue(x)— (실패 안 함)add / offer
꺼내기Dequeue()TryDequeue(out x)remove / poll
앞 보기Peek()TryPeek(out x)element / peek

자바는 "특수값"으로 null 을 돌려주므로 null 을 넣을 수 없지만, C# 의 Try 형은 bool + out 이라 Queue<string?> 에 null 도 정상 요소로 넣고 뺄 수 있습니다. 반환값과 "없음"이 섞이지 않습니다.

Queue<T> 의 Enqueue 는 실패하지 않습니다 — 크기 제한이 없기 때문입니다. "꽉 차면 거절 / 기다림" 이 필요하면 그건 유한(bounded) 큐이고, C# 에서는 Channel.CreateBounded(SQ 07)가 그 역할입니다.
Queue<T> 는 요소를 움직이지 않고 두 인덱스만 움직입니다 — 그래서 앞에서 꺼내도 O(1) 입니다.

큐로 쓰면 안 되는 것 — List.RemoveAt(0) 🟡 중급

List 를 큐처럼 — 매번 전체를 당김
var jobs = new List<Job>();
jobs.Add(job);                  // 뒤에 추가 O(1)

var next = jobs[0];
jobs.RemoveAt(0);               // ⚠ 나머지 n-1 개를 한 칸씩 앞으로 복사 O(n)
// 10만 건을 이렇게 비우면 약 50억 번의 요소 이동 (n²/2)

// LINQ 로 흉내 — 더 나쁨
jobs = jobs.Skip(1).ToList();   // 매번 새 리스트 할당 + 전체 복사
Queue<T> — 인덱스만 한 칸
var jobs = new Queue<Job>();
jobs.Enqueue(job);              // O(1) 분할 상환

if (jobs.TryDequeue(out var next))   // _head 만 +1 → O(1)
    Run(next);

// 10만 건을 비워도 요소 이동 0번
다른 언어의 같은 함정 — 파이썬 list.pop(0), 자바스크립트 Array.prototype.shift() 도 O(n) 입니다. 셋 다 "배열의 앞을 지우면 뒤를 당긴다"는 같은 이유입니다. 원형 배열(Queue<T> · collections.deque · ArrayDeque)이 정답인 것도 같습니다.

용량 관리 — EnsureCapacity · TrimExcess 🟡 중급

var q = new Queue<int>();          // 처음엔 길이 0 배열 (할당 없음)
q.Enqueue(1);                       // 길이 4 로 할당
// 이후 4 → 8 → 16 → 32 … 로 2배씩 (최소 +4)

어떻게 감지하나

Stack<T> · Queue<T> 는 변경할 때마다 _version 정수를 1 올립니다. 열거자는 시작할 때 그 값을 복사해 두고, MoveNext 때마다 비교해 다르면 예외를 던집니다. 잘못된 결과를 조용히 내는 대신 즉시 실패(fail-fast) 하는 설계입니다.

BFS 가 바로 이 모양입니다 — 꺼낸 노드의 이웃을 다시 넣는 일. while (q.TryDequeue(...)) 는 열거자를 쓰지 않으므로 안전하고, 이것이 C# BFS 의 표준 형태입니다(SQ 08). 반면 ConcurrentQueue<T> 의 열거는 스냅숏이라 예외가 나지 않습니다(SQ 06).
정리 — FIFO 는 Queue<T> + TryDequeue. 원형 배열이라 앞에서 꺼내도 O(1) 이고, 크기 제한이 없으며 저절로 줄지 않는다는 두 가지를 기억하세요.

덱 — .NET 에는 표준 Deque 가 없다

자바는 ArrayDeque, 파이썬은 collections.deque, C++ 은 std::deque 가 있지만 .NET 10 의 BCL 에는 양쪽 끝 O(1) 덱이 없습니다. 그래서 현업 코드는 LinkedList<T> 로 때우거나, 원형 버퍼 덱을 직접 한 파일로 들고 다닙니다. 이 섹션은 둘의 비용을 비교하고 완전한 구현을 드립니다.

  • RemoveFirst 가 값을 돌려주지 않아 var x = d.First.Value; d.RemoveFirst(); 두 줄이 됩니다.
  • 노드가 힙에 흩어져 순회가 느립니다(아래 그림).
요소는 제자리에 두고 _head 와 Count 만 움직입니다 — 앞으로 감으면 PushFront, 뒤로 늘리면 PushBack.

복사해서 쓰는 Deque<T> — 완전한 구현 🔴 고급

// Deque.cs — .NET 10 과 Unity(C# 9 · .NET Standard 2.1) 양쪽에서 컴파일되도록 작성
using System;
using System.Collections;
using System.Collections.Generic;
using System.Diagnostics.CodeAnalysis;

/// <summary>원형 버퍼 덱. 양 끝 넣기 · 빼기 분할 상환 O(1), 인덱스 접근 O(1). 스레드 안전하지 않음.</summary>
public sealed class Deque<T> : IReadOnlyList<T>
{
    private T[] _buf;
    private int _head;      // 맨 앞 요소가 있는 실제 칸
    private int _count;
    private int _version;   // 열거 중 변경 감지 — Queue<T> 와 같은 방식

    public Deque() : this(4) { }
    public Deque(int capacity)
    {
        if (capacity < 0) throw new ArgumentOutOfRangeException(nameof(capacity));
        _buf = capacity == 0 ? Array.Empty<T>() : new T[capacity];
    }

    public int Count => _count;
    public int Capacity => _buf.Length;

    // 논리 위치(0 = 맨 앞) → 실제 칸. 나머지 연산(%) 대신 비교 한 번 (Queue<T> 와 같음)
    private int Phys(int i)
    {
        int p = _head + i;
        return p >= _buf.Length ? p - _buf.Length : p;
    }

    public T this[int index]
    {
        get
        {
            if ((uint)index >= (uint)_count) throw new ArgumentOutOfRangeException(nameof(index));
            return _buf[Phys(index)];
        }
    }

    public void PushBack(T item)
    {
        if (_count == _buf.Length) Grow();
        _buf[Phys(_count)] = item;
        _count++; _version++;
    }

    public void PushFront(T item)
    {
        if (_count == _buf.Length) Grow();
        _head = _head == 0 ? _buf.Length - 1 : _head - 1;   // 한 칸 뒤로 감기
        _buf[_head] = item;
        _count++; _version++;
    }

    public bool TryPopFront([MaybeNullWhen(false)] out T item)
    {
        if (_count == 0) { item = default!; return false; }
        item = _buf[_head];
        _buf[_head] = default!;                              // 참조를 끊어 GC 가 회수하게
        _head = _head + 1 == _buf.Length ? 0 : _head + 1;
        _count--; _version++;
        return true;
    }

    public bool TryPopBack([MaybeNullWhen(false)] out T item)
    {
        if (_count == 0) { item = default!; return false; }
        int last = Phys(_count - 1);
        item = _buf[last];
        _buf[last] = default!;
        _count--; _version++;
        return true;
    }

    public bool TryPeekFront([MaybeNullWhen(false)] out T item)
    {
        if (_count == 0) { item = default!; return false; }
        item = _buf[_head];
        return true;
    }

    public bool TryPeekBack([MaybeNullWhen(false)] out T item)
    {
        if (_count == 0) { item = default!; return false; }
        item = _buf[Phys(_count - 1)];
        return true;
    }

    public T PopFront()  => TryPopFront(out var x) ? x : throw Empty();
    public T PopBack()   => TryPopBack(out var x)  ? x : throw Empty();
    public T PeekFront() => TryPeekFront(out var x) ? x : throw Empty();
    public T PeekBack()  => TryPeekBack(out var x)  ? x : throw Empty();
    private static InvalidOperationException Empty() => new("Deque empty.");

    public void Clear()
    {
        Array.Clear(_buf, 0, _buf.Length);
        _head = 0; _count = 0; _version++;
    }

    private void Grow()
    {
        int newCap = _buf.Length == 0 ? 4 : _buf.Length * 2;
        var next = new T[newCap];
        int first = Math.Min(_count, _buf.Length - _head);     // [_head .. 끝]
        Array.Copy(_buf, _head, next, 0, first);
        Array.Copy(_buf, 0, next, first, _count - first);      // [0 .. 나머지]
        _buf = next;
        _head = 0;
    }

    public IEnumerator<T> GetEnumerator()
    {
        int version = _version;
        for (int i = 0; i < _count; i++)
        {
            if (version != _version)
                throw new InvalidOperationException("Collection was modified.");
            yield return _buf[Phys(i)];
        }
    }
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
}

설계 메모

  • 용량을 2의 거듭제곱으로 강제하지 않았습니다. 자바 ArrayDeque 는 & (n - 1) 마스크를 쓰지만, .NET 의 Queue<T> 는 비교 한 번으로 감습니다. 분기 예측이 잘 맞아 차이가 거의 없습니다.
  • 빈 칸을 default 로 지웁니다. 안 지우면 꺼낸 객체를 배열이 계속 붙잡아 GC 가 못 치웁니다(BCL 은 RuntimeHelpers.IsReferenceOrContainsReferences<T>() 로 값 타입일 때 이 대입을 건너뜁니다).
  • IReadOnlyList<T> 를 구현해 LINQ · foreach · 인덱서가 다 됩니다.
  • 스레드 안전하지 않습니다 — Stack<T> · Queue<T> 와 같은 계약입니다.

SQ 05

우선순위 큐 — PriorityQueue<TElement, TPriority>

.NET 6 에서야 들어온 표준 힙입니다. 요소와 우선순위를 따로 받는 설계라 요소 타입을 고치지 않고도 쓸 수 있지만, 같은 우선순위끼리의 순서 비보장 · 우선순위 변경 불가 · 정렬되지 않은 열거 세 가지 함정이 있습니다.

기본 — 작은 값이 먼저 (최소 힙)

var pq = new PriorityQueue<string, int>();
pq.Enqueue("설거지", 3);
pq.Enqueue("서버 장애", 1);
pq.Enqueue("메일 답장", 2);

Console.WriteLine(pq.Peek());     // 서버 장애
Console.WriteLine(pq.Count);      // 3

// 요소와 우선순위를 함께 꺼내기 — TryDequeue 는 out 이 두 개
while (pq.TryDequeue(out var job, out var pri))
    Console.WriteLine($"{pri} {job}");
// 1 서버 장애
// 2 메일 답장
// 3 설거지

// 한꺼번에 넣기
pq.EnqueueRange([("a", 2), ("b", 1)]);
Console.WriteLine(pq.Dequeue());  // b
Dequeue() 는 요소만 돌려줍니다. 우선순위(예: 다익스트라의 거리)도 필요하면 TryDequeue(out e, out p) 를 쓰세요 — 그래서 실무 코드에서는 TryDequeue 가 훨씬 자주 보입니다.

함정 ① — 같은 우선순위는 넣은 순서대로 나오지 않는다 🔴 고급

var pq = new PriorityQueue<string, int>();
foreach (var name in new[] { "첫째", "둘째", "셋째", "넷째", "다섯째", "여섯째" })
    pq.Enqueue(name, 1);           // 전부 우선순위 1

while (pq.TryDequeue(out var n, out _))
    Console.Write($"{n} ");
// 첫째 여섯째 다섯째 넷째 셋째 둘째   ← FIFO 가 아님!

Dequeue 는 마지막 칸 요소를 루트로 옮긴 뒤 아래로 내립니다. 동점이면 내려가지 않으므로 맨 뒤에 넣은 "여섯째"가 루트로 올라와 두 번째로 나옵니다. 이것은 버그가 아니라 힙의 성질이고, 문서에도 순서를 보장하지 않는다고 적혀 있습니다.

해결 — 순번을 두 번째 키로

// 우선순위를 (등급, 순번) 튜플로 — ValueTuple 은 앞 항목부터 비교
var pq = new PriorityQueue<string, (int Level, long Seq)>();
long seq = 0;
foreach (var name in new[] { "첫째", "둘째", "셋째", "넷째", "다섯째", "여섯째" })
    pq.Enqueue(name, (1, seq++));

while (pq.TryDequeue(out var n, out _))
    Console.Write($"{n} ");
// 첫째 둘째 셋째 넷째 다섯째 여섯째   ← 안정적(FIFO)
작업 스케줄러 · 메시지 처리처럼 "같은 등급이면 먼저 온 것부터"가 요구사항이면 반드시 순번을 붙이세요. long 순번은 초당 10억 건을 넣어도 수백 년간 넘치지 않습니다.

    }
}

var todo = new PriorityQueue<string, TaskKey>();   // Comparer 생략 → IComparable 사용
var d = new DateTime(2026, 10, 1);
todo.Enqueue("보고서", new(d, 1));
todo.Enqueue("장애 회고", new(d, 5));
Console.WriteLine(todo.Dequeue());   // 장애 회고 (마감 같고 중요도 높음)

함정 ② — 우선순위를 바꾸는 API 가 없다 → 지연 삭제 🔴 고급

다익스트라 — "낡은 항목은 꺼낼 때 버린다"

var graph = new Dictionary<char, (char To, int W)[]>
{
    ['A'] = [('B', 4), ('C', 1)],
    ['C'] = [('B', 2), ('D', 5)],
    ['B'] = [('D', 1)],
    ['D'] = [],
};

var dist = new Dictionary<char, int> { ['A'] = 0 };
var pq = new PriorityQueue<char, int>();
pq.Enqueue('A', 0);
int stale = 0;

while (pq.TryDequeue(out var u, out var d))
{
    if (d > dist[u]) { stale++; continue; }   // ★ 이미 더 짧은 길로 처리됨 → 버림
    foreach (var (v, w) in graph[u])
    {
        int nd = d + w;
        if (nd < dist.GetValueOrDefault(v, int.MaxValue))
        {
            dist[v] = nd;
            pq.Enqueue(v, nd);                  // decrease-key 대신 "새로 하나 더"
        }
    }
}
Console.WriteLine(string.Join(" ", dist.OrderBy(kv => kv.Key)
    .Select(kv => $"{kv.Key}={kv.Value}")));   // A=0 B=3 C=1 D=4
Console.WriteLine($"버린 낡은 항목 {stale}개");   // 버린 낡은 항목 2개

왜 이렇게 하나

PriorityQueue 는 요소의 위치를 기억하지 않으므로 "B 의 우선순위를 4 → 3 으로" 같은 decrease-key 가 불가능합니다. 대신 새 우선순위로 한 번 더 넣고, 꺼낼 때 dist 와 비교해 낡은 것을 버립니다. 힙에 최대 간선 수만큼 항목이 쌓이지만 복잡도는 O(E log E) = O(E log V) 로 같습니다.

Remove .NET 9+ — pq.Remove(element, out var removed, out var priority) 로 특정 요소를 지울 수 있게 되었지만 배열을 처음부터 훑는 O(n) 입니다. 지우고 다시 넣어 우선순위를 바꾸는 방식은 항목이 많으면 지연 삭제보다 느립니다. 가끔 취소하는 용도로만 쓰세요.
요소 객체의 필드를 고쳐도 힙은 모릅니다. 우선순위는 Enqueue 순간 값으로 복사돼 저장되므로, job.Priority = 0 처럼 바꿔도 위치가 그대로입니다. 바꿔야 한다면 "다시 넣고 낡은 것은 무시" 하세요.

top-k — EnqueueDequeue 로 크기 k 힙 유지 🟡 중급

// 큰 수 k 개 — "최소 힙에 k 개만 남긴다"
int[] nums = [5, 1, 9, 3, 7, 8, 2];
const int k = 3;
var heap = new PriorityQueue<int, int>(k);

foreach (var x in nums)
{
    if (heap.Count < k) heap.Enqueue(x, x);
    else heap.EnqueueDequeue(x, x);   // x 가 최소보다 작으면 x 를 그대로 돌려주고 끝
}

// UnorderedItems — 힙 배열 순서 그대로 (정렬 아님)
Console.WriteLine(string.Join(",", heap.UnorderedItems.Select(t => t.Element)));  // 7,8,9

var top = new List<int>();
while (heap.TryDequeue(out var v, out _)) top.Add(v);   // 작은 것부터 나옴
top.Reverse();
Console.WriteLine(string.Join(",", top));   // 9,8,7

비용과 함정

  • n 개를 다 정렬하면 O(n log n), k 크기 힙은 O(n log k) 에 메모리 O(k) — 스트림에도 됩니다.
  • EnqueueDequeue 는 새 값이 루트 이하면 힙을 건드리지 않고 그대로 돌려줍니다. Enqueue 후 Dequeue 를 따로 부르는 것보다 sift 가 한 번 적습니다.
  • 위 예에서 UnorderedItems 가 7,8,9 로 정렬돼 보이는 것은 우연입니다. 개수가 늘면 바로 흐트러집니다 — 정렬이 필요하면 꼭 Dequeue 로 꺼내세요.
Unity 에는 이 타입이 없습니다(SQ 01). A* 의 open 리스트를 List 에 넣고 매번 Sort 하는 코드가 흔한데 프레임마다 O(n log n) 입니다. 위 4-ary 힙의 부모 · 자식 공식으로 50줄짜리 이진 힙을 만들어 두면 해결됩니다.
정리 — PriorityQueue 는 최소 힙 · 동점 순서 없음 · 우선순위 변경 없음. 동점에는 순번 키, 변경에는 지연 삭제, 방향 반전에는 Comparer.Create 가 정답입니다.
SQ 06

스레드 안전 큐 — Concurrent* 와 BlockingCollection

Queue<T> 를 두 스레드가 동시에 만지면 예외 없이 데이터가 사라지거나 중복됩니다. ConcurrentQueue<T> 는 락 없이 그 문제를 풀지만 "비었을 때 기다리기"는 하지 않습니다. 기다림과 상한(배압)이 필요해지는 순간 BlockingCollection 이나 Channel 로 넘어갑니다.

ConcurrentQueue<T> — Try 만 있는 큐

using System.Collections.Concurrent;

var q = new ConcurrentQueue<int>();

// 8개 스레드가 동시에 1만 개씩 넣기
Parallel.For(0, 8, t =>
{
    for (int i = 0; i < 10_000; i++) q.Enqueue(i);
});
Console.WriteLine(q.Count);              // 80000 (Queue<T> 였다면 들쭉날쭉)

// 꺼내기는 Try 하나뿐 — Dequeue() 메서드 자체가 없음
long sum = 0;
Parallel.For(0, 4, _ =>
{
    long local = 0;
    while (q.TryDequeue(out var x)) local += x;   // 비면 false → 루프 종료
    Interlocked.Add(ref sum, local);
});
Console.WriteLine(sum);                  // 399960000 (= 8 × 0~9999 합)
Console.WriteLine(q.IsEmpty);            // True
if (q.Count > 0) q.TryDequeue(...) 는 의미가 없습니다. 확인과 꺼내기 사이에 다른 스레드가 가져갈 수 있습니다. TryDequeue 의 반환값만 믿으세요. 비었는지 볼 때는 Count == 0 대신 IsEmpty — Count 는 세그먼트를 훑는 더 비싼 연산입니다.

BlockingCollection — 생산자 · 소비자 완전한 예제 🟡 중급

using System.Collections.Concurrent;

// 내부 저장소는 기본이 ConcurrentQueue → FIFO. 3개 차면 Add 가 멈춤 (배압)
using var bc = new BlockingCollection<int>(boundedCapacity: 3);

var producer = Task.Run(() =>
{
    for (int i = 1; i <= 10; i++)
        bc.Add(i);              // 꽉 차면 이 스레드가 블록
    bc.CompleteAdding();        // ★ "더 없음" — poison pill 대신 쓰는 종료 신호
});

var consumers = Enumerable.Range(1, 2).Select(id => Task.Run(() =>
{
    int sum = 0;
    // 비면 블록, CompleteAdding 후 다 비면 foreach 가 자연히 끝남
    foreach (var x in bc.GetConsumingEnumerable())
        sum += x;
    return sum;
})).ToArray();

await producer;
int[] sums = await Task.WhenAll(consumers);
Console.WriteLine($"합계 {sums.Sum()}");   // 합계 55 (두 소비자의 몫은 실행마다 다름)
Console.WriteLine(bc.IsCompleted);         // True

종료 처리 — poison pill vs 완료 신호

고전적인 방법은 특수값(poison pill)을 넣어 "이걸 받으면 끝내라"고 하는 것입니다. 소비자가 N 명이면 알약도 N 개 넣어야 하고, 정상 데이터와 구분되는 값이 필요합니다. CompleteAdding() 은 그 일을 컬렉션 상태로 대신합니다 — 이후 Add 는 InvalidOperationException, 모든 GetConsumingEnumerable 은 남은 것을 다 꺼낸 뒤 끝납니다.

왜 "레거시 쪽"인가 — Take · Add 가 스레드를 막고 기다립니다. ASP.NET Core 처럼 스레드 풀을 공유하는 곳에서 소비자 여럿이 막혀 있으면 스레드 풀 고갈로 이어집니다. 같은 구조를 await 로 하는 것이 Channel<T>(SQ 07)이고, 새 코드는 그쪽입니다. 콘솔 · 전용 스레드 배치처럼 막아도 되는 곳에서는 여전히 간단하고 좋은 도구입니다.
생성자에 다른 저장소를 넘기면 순서가 바뀝니다 — new BlockingCollection<int>(new ConcurrentStack<int>(), 3) 이면 LIFO 입니다.

Unity — 메인 스레드 디스패치 큐 🟡 중급

using System;
using System.Collections.Concurrent;
using UnityEngine;

// 다른 스레드(소켓 수신 · Task.Run)에서 Unity API 를 부르면 예외 →
// 할 일을 큐에 넣고, 메인 스레드의 Update 가 꺼내 실행
public sealed class MainThread : MonoBehaviour
{
    private static readonly ConcurrentQueue<Action> _q = new();
    private const int BudgetPerFrame = 64;     // 한 프레임에 너무 많이 하지 않게

    public static void Post(Action work) => _q.Enqueue(work);   // 아무 스레드에서나

    private void Update()
    {
        for (int i = 0; i < BudgetPerFrame && _q.TryDequeue(out var work); i++)
        {
            try { work(); }
            catch (Exception e) { Debug.LogException(e); }   // 하나가 터져도 나머지는 계속
        }
    }
}

왜 ConcurrentQueue 인가

  • 생산자는 여러 스레드, 소비자는 메인 스레드 하나 — 기다릴 필요가 없습니다. Update 가 어차피 매 프레임 옵니다.
  • Unity 메인 스레드에서 BlockingCollection.Take 를 부르면 게임이 멈춥니다. 절대 금지입니다.
  • 프레임 예산을 두어 한 프레임에 큐가 몰려도 프레임이 튀지 않게 합니다. 남은 것은 다음 프레임에 처리됩니다.
Unity 6 은 await Awaitable.MainThreadAsync() 로 메인 스레드에 돌아오는 방법도 제공합니다. 콜백이 많고 순서가 중요하면 위 큐, async 흐름 안에서 잠깐 돌아올 때는 Awaitable 이 편합니다.
정리 — 여러 스레드가 넣고 빼기만 하면 ConcurrentQueue + TryDequeue, 비었을 때 기다리고 상한이 필요하면 Channel(새 코드) 또는 BlockingCollection(스레드를 막아도 되는 곳). Count 로 확인하고 꺼내는 코드는 전부 경쟁 상태입니다.
SQ 07

비동기 큐 — System.Threading.Channels

Channel<T> 는 async 세계의 BlockingCollection 입니다. 비었으면 await 로 기다리고, 꽉 차면 await 로 생산자를 늦추며(배압), Writer.Complete() 로 끝을 알립니다. 그 사이 스레드는 막히지 않고 풀로 돌아갑니다. 🧬 고급 탭 A 03 에서 한 장으로 소개한 것을 여기서 옵션 · 종료 · 함정까지 뜯어 봅니다.

생산자 2 · 소비자 1 — 완전한 예제

using System.Threading.Channels;

var channel = Channel.CreateBounded<Order>(new BoundedChannelOptions(capacity: 4)
{
    FullMode = BoundedChannelFullMode.Wait,  // 꽉 차면 WriteAsync 가 대기 (기본값)
    SingleReader = true,                     // 소비자 1명 → 내부 동기화를 줄인 구현 선택
    SingleWriter = false,                    // 생산자는 여럿
});

async Task ProduceAsync(string source, int count, CancellationToken ct)
{
    for (int i = 1; i <= count; i++)
    {
        // 자리가 없으면 여기서 await — 소비자가 느리면 생산자도 느려짐 (배압)
        await channel.Writer.WriteAsync(new Order(source, i), ct);
        await Task.Delay(5, ct);
    }
}

async Task<int> ConsumeAsync(CancellationToken ct)
{
    int handled = 0;
    // Complete() 된 뒤 남은 것까지 다 읽으면 foreach 가 끝남
    await foreach (var order in channel.Reader.ReadAllAsync(ct))
    {
        await Task.Delay(10, ct);            // 처리가 생산보다 느림
        handled++;
    }
    return handled;
}

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
var consumer = ConsumeAsync(cts.Token);                  // 소비자 먼저 시작
await Task.WhenAll(ProduceAsync("웹", 10, cts.Token),
                   ProduceAsync("앱", 10, cts.Token));
channel.Writer.Complete();                               // ★ 모든 생산자가 끝난 뒤 딱 한 번
Console.WriteLine($"처리 {await consumer}건");            // 처리 20건

record Order(string Source, int No);

꽉 찼을 때 — Wait 와 DropOldest 를 눈으로 🟡 중급

using System.Threading.Channels;

// ① Wait (기본) — TryWrite 는 자리가 없으면 false
var w = Channel.CreateBounded<int>(2);
Console.WriteLine(w.Writer.TryWrite(1));   // True
Console.WriteLine(w.Writer.TryWrite(2));   // True
Console.WriteLine(w.Writer.TryWrite(3));   // False  ← WriteAsync 였다면 await 대기

// ② DropOldest — 항상 들어가고, 밀려난 것은 콜백으로 (.NET 6+)
var dropped = new List<int>();
var d = Channel.CreateBounded<int>(
    new BoundedChannelOptions(3) { FullMode = BoundedChannelFullMode.DropOldest },
    itemDropped: x => dropped.Add(x));

for (int i = 1; i <= 5; i++)
    d.Writer.TryWrite(i);                  // 5번 모두 true
d.Writer.Complete();

await foreach (var x in d.Reader.ReadAllAsync())
    Console.Write($"{x} ");                // 3 4 5
Console.WriteLine($"| 버림 {string.Join(",", dropped)}");   // | 버림 1,2

무엇을 고를까

  • 잃으면 안 되는 데이터(주문 · 이메일 발송 · 결제 이벤트) → Wait. 생산자가 느려지는 것을 받아들입니다.
  • 최신 값만 의미 있는 데이터(플레이어 위치 · 센서 값 · 시세) → DropOldest. 오래된 위치를 처리하는 것은 낭비입니다.
  • HTTP 요청에서 바로 쓰는 경우 → TryWrite 로 시도하고 false 면 503 / 429 로 거절. 요청 스레드를 붙잡고 기다리게 하지 않습니다(SQ 12).
itemDropped 콜백으로 버린 개수를 메트릭으로 내보내세요. "조용히 버려지는" 데이터는 장애 분석 때 가장 찾기 어렵습니다.

규칙 네 가지

  1. Complete 는 "마지막 생산자"가 한 번만. 두 번 부르면 ChannelClosedException(InvalidOperationException 의 파생) — 확실하지 않으면 TryComplete().
  2. 생산자가 여럿이면 Task.WhenAll(producers) 뒤에 Complete 합니다(위 예제 패턴). 각 생산자가 Complete 하면 첫 번째가 나머지를 막습니다.
  3. 오류는 Complete(ex) 로 넘기면 소비자의 await foreach 가 남은 항목을 다 받은 뒤 같은 예외를 던지고, Reader.Completion 도 실패 상태가 됩니다.
  4. 취소(CancellationToken)는 "그만 기다리기"일 뿐 채널을 닫지 않습니다. 종료 절차는 Complete, 강제 중단은 토큰 — 둘을 구분하세요.

소비자 여럿 — 나눠 갖기이지 방송이 아니다 🟡 중급

var jobs = Channel.CreateBounded<int>(new BoundedChannelOptions(100)
{
    SingleReader = false,      // ★ 소비자가 여럿이면 반드시 false
});

// 워커 4개가 같은 Reader 를 읽음 → 항목 하나는 워커 하나에게만
var workers = Enumerable.Range(1, 4).Select(id => Task.Run(async () =>
{
    int mine = 0;
    await foreach (var job in jobs.Reader.ReadAllAsync())
        mine++;
    return mine;
})).ToArray();

for (int i = 0; i < 1_000; i++) await jobs.Writer.WriteAsync(i);
jobs.Writer.Complete();

int[] counts = await Task.WhenAll(workers);
Console.WriteLine(counts.Sum());   // 1000 (각 워커 몫은 실행마다 다름)
  • Channel 은 작업 분배(competing consumers) 구조입니다. 모든 구독자에게 같은 메시지를 뿌리는 pub/sub 이 필요하면 구독자마다 채널을 하나씩 두고 복사해 넣어야 합니다.
  • SingleReader = true 인데 실제로 둘이 읽으면 예외 없이 항목이 꼬일 수 있습니다. 성능 옵션이 아니라 계약입니다.
  • 순서: 소비자가 하나면 FIFO 가 보장되지만, 여럿이면 처리 완료 순서는 보장되지 않습니다.
우선순위가 있는 채널 — .NET 9 의 System.Threading.Channels 에 Channel.CreateUnboundedPrioritized<T>() 가 추가되었습니다 .NET 9+. 이름처럼 Unbounded 뿐이므로 상한은 따로 관리해야 합니다. Unity 에는 Channels 가 기본으로 없어 DLL 을 직접 넣거나 SQ 06 의 ConcurrentQueue 방식을 씁니다.
정리 — async 생산자 · 소비자는 Channel.CreateBounded + ReadAllAsync + Writer.Complete() 세 줄이 뼈대입니다. 꽉 찼을 때의 정책(Wait · Drop)을 정하는 것이 배압 설계입니다.

① 괄호 검사 — Stack<char>

static bool IsBalanced(string s)
{
    var st = new Stack<char>();
    foreach (var c in s)
    {
        switch (c)
        {
            case '(' or '[' or '{':
                st.Push(c);
                break;
            case ')' or ']' or '}':
            {
                char open = c switch { ')' => '(', ']' => '[', _ => '{' };
                // 비어 있으면 TryPop 이 false → 짝 없는 닫는 괄호
                if (!st.TryPop(out var top) || top != open) return false;
                break;
            }
        }
    }
    return st.Count == 0;              // 남은 여는 괄호가 있으면 실패
}

foreach (var s in new[] { "{[()]}", "([)]", "((", "a[b]{c}" })
    Console.WriteLine($"{s} {IsBalanced(s)}");
// {[()]} True
// ([)] False
// (( False
// a[b]{c} True

② 단조 스택 — 다음 큰 수

static int[] NextGreater(int[] a)
{
    var res = new int[a.Length];
    Array.Fill(res, -1);
    var st = new Stack<int>();      // 아직 답을 못 찾은 '인덱스'
    for (int i = 0; i < a.Length; i++)
    {
        // 나보다 작은 값들은 지금 답을 찾았다
        while (st.TryPeek(out var j) && a[j] < a[i])
            res[st.Pop()] = a[i];
        st.Push(i);
    }
    return res;                       // 스택에 남은 것은 답 없음(-1)
}

Console.WriteLine(string.Join(",", NextGreater([2, 7, 3, 5, 4, 6, 8])));
// 7,8,5,6,6,8,-1
while (st.TryPeek(out var j) && …) — "비어 있지 않고, 꼭대기가 조건을 만족하는 동안"을 한 줄로 씁니다. st.Count > 0 && a[st.Peek()] < a[i] 보다 짧고 Peek 를 두 번 하지 않습니다. 주식 가격 span · 히스토그램 최대 직사각형도 같은 뼈대입니다.
붉은 칸이 방금 Push 된 값, 아래 줄이 그 단계에서 Pop 되며 답을 얻은 값 — 8 만 끝까지 남아 -1 입니다.

③ BFS 최단 거리 — Queue<(int R, int C)>

string[] grid = ["S.#.", "..#.", "#...", ".#.G"];
int H = grid.Length, W = grid[0].Length;
var dist = new int[H, W];
for (int r = 0; r < H; r++)
    for (int c = 0; c < W; c++) dist[r, c] = -1;

(int dr, int dc)[] dirs = [(1, 0), (-1, 0), (0, 1), (0, -1)];
var q = new Queue<(int R, int C)>();     // 값 튜플 → 박싱 · 할당 없음
q.Enqueue((0, 0));
dist[0, 0] = 0;

while (q.TryDequeue(out var cur))         // ★ foreach 가 아니라 while
{
    foreach (var (dr, dc) in dirs)
    {
        int nr = cur.R + dr, nc = cur.C + dc;
        if (nr < 0 || nc < 0 || nr >= H || nc >= W) continue;
        if (grid[nr][nc] == '#' || dist[nr, nc] != -1) continue;
        dist[nr, nc] = dist[cur.R, cur.C] + 1;   // 넣을 때 방문 표시
        q.Enqueue((nr, nc));
    }
}
Console.WriteLine(dist[3, 3]);   // 6  (S → G 최단 칸 수)
방문 표시는 "넣을 때" 합니다. 꺼낼 때 표시하면 같은 칸이 큐에 여러 번 들어가 최악의 경우 큐가 폭증합니다.

④ 슬라이딩 윈도우 최댓값 — 단조 덱

// SQ 04 의 Deque<T> 사용
static List<int> MaxSliding(int[] a, int k)
{
    var dq = new Deque<int>();   // 인덱스 — 값이 앞에서 뒤로 내림차순
    var res = new List<int>();
    for (int i = 0; i < a.Length; i++)
    {
        if (dq.TryPeekFront(out var f) && f <= i - k)
            dq.PopFront();                       // 창 밖으로 나간 인덱스
        while (dq.TryPeekBack(out var b) && a[b] <= a[i])
            dq.PopBack();                        // 나보다 작으면 다시는 최대가 못 됨
        dq.PushBack(i);
        if (i >= k - 1) res.Add(a[dq.PeekFront()]);
    }
    return res;
}

Console.WriteLine(string.Join(",", MaxSliding([1, 3, -1, -3, 5, 3, 6, 7], 3)));
// 3,3,5,5,6,7
코딩 테스트에서 Deque 클래스가 없다면 — 각 인덱스는 한 번만 들어가므로 int[] buf = new int[n]; int head = 0, tail = 0; 배열 하나에 두 포인터로 충분합니다(감을 필요가 없음). 앞에서 빼기는 head++, 뒤에서 빼기는 tail--.

⑤ 0-1 BFS — 비용 0 은 앞에, 1 은 뒤에

var adj = new List<(int To, int W)>[5];
for (int i = 0; i < 5; i++) adj[i] = [];
foreach (var (u, v, w) in new[] { (0, 1, 1), (0, 2, 0), (2, 1, 0),
                                  (1, 3, 1), (2, 3, 1), (3, 4, 0) })
    adj[u].Add((v, w));

var dist = Enumerable.Repeat(int.MaxValue, 5).ToArray();
dist[0] = 0;
var dq = new Deque<int>();
dq.PushBack(0);

while (dq.TryPopFront(out var u))
{
    foreach (var (v, w) in adj[u])
    {
        if (dist[u] + w >= dist[v]) continue;
        dist[v] = dist[u] + w;
        if (w == 0) dq.PushFront(v);    // 같은 거리 → 지금 바로 처리
        else        dq.PushBack(v);     // 거리 +1 → 다음 차례
    }
}
Console.WriteLine(string.Join(",", dist));   // 0,0,0,1,1

가중치가 0 과 1 뿐이면 다익스트라의 O(E log V) 대신 덱으로 O(V + E) 입니다. 덱이 없는 .NET 에서 SQ 04 구현이 필요한 대표적 이유입니다.

⑥ undo / redo — 스택 두 개

var ed = new Editor();
ed.Type("안녕");
ed.Type("하세요");
ed.Undo();  Console.WriteLine(ed.Text);   // 안녕
ed.Redo();  Console.WriteLine(ed.Text);   // 안녕하세요
ed.Undo();  ed.Type("!");
Console.WriteLine(ed.Text);               // 안녕!
Console.WriteLine(ed.CanRedo);            // False (새 입력이 redo 를 지움)

sealed class Editor
{
    private readonly Stack<string> _undo = new();
    private readonly Stack<string> _redo = new();
    public string Text { get; private set; } = "";
    public bool CanRedo => _redo.Count > 0;

    public void Type(string s)
    {
        _undo.Push(Text);
        Text += s;
        _redo.Clear();                    // 새 편집은 '미래'를 무효화
    }
    public void Undo()
    {
        if (!_undo.TryPop(out var prev)) return;
        _redo.Push(Text);
        Text = prev;
    }
    public void Redo()
    {
        if (!_redo.TryPop(out var next)) return;
        _undo.Push(Text);
        Text = next;
    }
}

불변 스택 · 큐 — ImmutableStack · ImmutableQueue 로 스냅숏 🔴 고급

using System.Collections.Immutable;

var h0 = ImmutableStack<string>.Empty;
var h1 = h0.Push("v1");
var h2 = h1.Push("v2");                 // h1 은 그대로 — 새 노드 하나만 생김
var h3 = h2.Pop(out var top);

Console.WriteLine(top);                        // v2
Console.WriteLine(string.Join(",", h2));       // v2,v1  (h2 는 안 바뀜)
Console.WriteLine(ReferenceEquals(h3, h1));    // True — Pop 은 꼬리를 그대로 돌려줌

var q1 = ImmutableQueue<int>.Empty.Enqueue(1).Enqueue(2);
var q2 = q1.Dequeue(out var first);
Console.WriteLine($"{first} | {string.Join(",", q1)} | {string.Join(",", q2)}");
// 1 | 1,2 | 2

언제 쓰나

  • ImmutableStack 은 단일 연결 리스트입니다. Push 는 새 머리 노드 하나, Pop 은 꼬리를 돌려줄 뿐 — 버전마다 전체를 복사하지 않고 꼬리를 공유합니다.
  • 상태 이력 · 시간 여행 디버깅 · Redux 식 상태처럼 "모든 과거 버전을 들고 있어야" 할 때, 버전 하나당 비용이 O(1) 입니다.
  • 여러 스레드에 락 없이 넘기기 — 바뀌지 않으므로 그냥 공유하면 됩니다. 갱신은 ImmutableInterlocked.Push(ref stack, x) 로 원자적으로.
  • ImmutableQueue 는 내부적으로 불변 스택 두 개(앞 · 뒤)로 만든 큐입니다.
빠른 큐 · 스택이 아닙니다. 노드마다 할당이 있어 단순 처리 루프에서는 Stack<T> 보다 몇 배 느립니다. "과거 버전을 공유해야 한다"는 요구가 있을 때만 고르세요.
정리 — 괄호 · 다음 큰 수는 Stack + TryPeek 루프, 최단 거리는 Queue + while TryDequeue, 윈도우 최댓값 · 0-1 BFS 는 덱, undo 는 스택 두 개(이력 공유가 필요하면 ImmutableStack).

  • 자바 → C#: ArrayDeque 를 찾다가 없어서 LinkedList 로 가기 쉽습니다. 스택 · 큐로만 쓰던 것이면 Stack<T> · Queue<T> 로 나눠 옮기세요. 진짜 양쪽이 필요하면 SQ 04.

public sealed class BackgroundTaskQueue
{
    private readonly Channel<Func<CancellationToken, ValueTask>> _ch;

    public BackgroundTaskQueue(int capacity) =>
        _ch = Channel.CreateBounded<Func<CancellationToken, ValueTask>>(
            new BoundedChannelOptions(capacity)
            {
                FullMode = BoundedChannelFullMode.Wait,   // 꽉 차면 TryWrite 가 false
                SingleReader = true,                      // 워커 하나
            });

    // HTTP 요청처럼 기다리면 안 되는 쪽
    public bool TryEnqueue(Func<CancellationToken, ValueTask> work) => _ch.Writer.TryWrite(work);

    // 배치 · 내부 호출처럼 기다려도 되는 쪽
    public ValueTask EnqueueAsync(Func<CancellationToken, ValueTask> work, CancellationToken ct) =>
        _ch.Writer.WriteAsync(work, ct);

    public IAsyncEnumerable<Func<CancellationToken, ValueTask>> ReadAllAsync(CancellationToken ct) =>
        _ch.Reader.ReadAllAsync(ct);
}

public sealed class QueuedWorker(BackgroundTaskQueue queue, ILogger<QueuedWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await foreach (var work in queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                await work(stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;                                   // 종료 중 — 조용히 빠져나감
            }
            catch (Exception ex)
            {
                log.LogError(ex, "백그라운드 작업 실패");  // ★ 하나가 실패해도 워커는 계속
            }
        }
    }
}
try/catch 가 꼭 필요한 이유 — .NET 6 부터 BackgroundService 에서 처리되지 않은 예외가 나면 호스트 전체가 종료됩니다 (BackgroundServiceExceptionBehavior.StopHost 가 기본). 작업 하나의 실패가 서버를 내리지 않도록 항목 단위로 감쌉니다.
병렬로 처리하려면 워커를 여러 개 띄우고 SingleReader = false 로 바꿉니다. 또는 워커 안에서 Parallel.ForEachAsync(queue.ReadAllAsync(ct), new ParallelOptions { MaxDegreeOfParallelism = 4 }, …) 처럼 동시 실행 수를 제한합니다.

public sealed class RecentLog<T>(int capacity)
{
    private readonly Queue<T> _q = new(capacity);   // 미리 N칸 → 재할당 0

    public void Add(T item)
    {
        if (_q.Count == capacity) _q.Dequeue();      // 파이썬 deque(maxlen) 과 같은 동작

    }

    public IReadOnlyCollection<T> Items => _q;      // 오래된 것 → 최신 순
}

public sealed class SlidingWindowLog(int limit, long windowMs)
{
    private readonly Queue<long> _hits = new();    // 허용된 요청의 시각
    private readonly Lock _gate = new();           // .NET 9+ 전용 락 타입

    public bool TryAcquire() => TryAcquire(Environment.TickCount64);

    public bool TryAcquire(long nowMs)             // 테스트용으로 시각을 주입
    {
        lock (_gate)
        {
            // 창 밖으로 나간 기록을 앞에서부터 버림 — 큐가 시간순이라 가능
            while (_hits.TryPeek(out var t) && nowMs - t >= windowMs)
                _hits.Dequeue();
            if (_hits.Count >= limit) return false;
            _hits.Enqueue(nowMs);
            return true;
        }
    }
}

var rl = new SlidingWindowLog(limit: 3, windowMs: 1000);
foreach (var t in new long[] { 0, 100, 200, 300, 1050, 1150, 1200, 1300 })
    Console.Write($"{t}:{(rl.TryAcquire(t) ? "허용" : "거절")} ");
// 0:허용 100:허용 200:허용 300:거절 1050:허용 1150:허용 1200:허용 1300:거절
운영에서는 내장 기능을 — ASP.NET Core 7+ 의 AddRateLimiter 와 System.Threading.RateLimiting 의 SlidingWindowRateLimiter · TokenBucketRateLimiter 가 있습니다. 서버가 여러 대면 Redis 같은 공유 저장소가 필요합니다. 위 코드는 원리 이해 · 단일 프로세스 내부 보호용입니다.

using System.Runtime.CompilerServices;
using System.Threading.Channels;

static async IAsyncEnumerable<List<T>> ReadBatchesAsync<T>(
    ChannelReader<T> reader, int maxBatch,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    // 하나라도 생길 때까지 기다린 뒤, 지금 쌓인 것을 최대 maxBatch 개까지 한꺼번에
    while (await reader.WaitToReadAsync(ct))
    {
        var batch = new List<T>(maxBatch);
        while (batch.Count < maxBatch && reader.TryRead(out var item))
            batch.Add(item);
        if (batch.Count > 0) yield return batch;
    }
}

var events = Channel.CreateBounded<int>(1_000);
for (int i = 1; i <= 7; i++) await events.Writer.WriteAsync(i);
events.Writer.Complete();

await foreach (var batch in ReadBatchesAsync(events.Reader, maxBatch: 3))
    Console.WriteLine(string.Join(",", batch));
// 1,2,3
// 4,5,6
// 7

using System.Collections.Generic;
using UnityEngine;

public readonly struct GameEvent
{
    public readonly int Type, EntityId;
    public GameEvent(int type, int entityId) { Type = type; EntityId = entityId; }
}

public sealed class EventBus : MonoBehaviour
{
    // 큐 두 개를 번갈아 씀 — 처리 중에 생긴 이벤트는 다음 프레임으로
    private Queue<GameEvent> _current = new Queue<GameEvent>(256);
    private Queue<GameEvent> _next    = new Queue<GameEvent>(256);

    public void Raise(GameEvent e) => _next.Enqueue(e);   // 메인 스레드 전용

    private void LateUpdate()
    {
        (_current, _next) = (_next, _current);             // 교체 — 할당 없음
        while (_current.TryDequeue(out var e))
            Dispatch(e);                                   // 여기서 Raise 해도 _next 로
    }

    private void Dispatch(in GameEvent e) { /* 구독자에게 전달 */ }
}

왜 이렇게 하나

  • 이벤트 처리 중에 새 이벤트가 생기는 연쇄(피격 → 사망 → 드롭)를 한 큐로 돌리면 한 프레임이 끝나지 않을 수 있습니다. 두 큐를 번갈아 쓰면 프레임마다 끝이 보장됩니다.
  • GameEvent 를 readonly struct 로 두면 Queue<GameEvent> 안에 값으로 들어가 이벤트마다 할당이 0 입니다. class 이벤트는 프레임마다 쓰레기를 만듭니다.
  • 용량 256 으로 미리 잡고 계속 재사용 — 큐는 비워도 배열을 유지하므로 GC 스파이크가 없습니다.
  • 다른 스레드에서 올리는 이벤트는 SQ 06 의 MainThread.Post 를 거쳐 들어오게 하세요.
Unity 는 C# 9 수준이라 record struct · 컬렉션 식 [] · 기본 생성자(primary constructor)를 쓸 수 없습니다. 그래서 이 카드의 코드는 일부러 옛 문법으로 적었습니다. TryDequeue 는 .NET Standard 2.1 에 있어 그대로 됩니다.
