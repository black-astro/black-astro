STR 01

.NET 의 공통 바탕 — 솔루션 · 프로젝트 · 루트 설정 파일

.NET 은 어떤 앱을 만들든 바탕이 같습니다. 솔루션(.sln / .slnx)은 프로젝트 목록이고, 실제 설정은 .csproj 에 있으며, 저장소 루트의 파일 몇 개가 모든 프로젝트에 공통으로 적용됩니다. 각 명령과 파일의 상세는 설치 탭 SETUP 05 · 06 · 11 에 있으니, 여기서는 어디에 무엇을 두는지와 커지면 어떻게 바뀌는지만 봅니다.

STR 02

ASP.NET Core — Controllers 계층형 vs 기능별(Vertical Slice)

dotnet new webapi 가 만드는 폴더는 시작점일 뿐입니다. 엔드포인트가 스무 개를 넘으면 Controllers · Services · Models 를 오가는 시간이 늘어납니다. 이 섹션은 두 배치를 나란히 놓고, Minimal API 에서 엔드포인트를 기능 폴더 안 확장 메서드로 모으는 법을 봅니다. 앱이 뜨는 순서와 DI 는 엔터프라이즈 탭 ENT 02 · 03.

계층형 (Controllers 템플릿 그대로)

Shop.Api/
├─ Program.cs
├─ Controllers/  OrdersController · MembersController · …
├─ Services/     OrderService · IOrderService · …
├─ Models/       주문 · 회원 DTO 가 한 폴더에 섞임
├─ Data/         AppDbContext · Migrations/
└─ appsettings.json
# 기능 하나를 고치려면 폴더 4개를 오갑니다

Shop.Api/
├─ Program.cs                # 조립만 — 기능마다 Map 한 줄
├─ Features/

└─ Common/                   # 정말 공통인 것만 (에러 응답 · 필터)
함께 바뀌는 것을 함께 둡니다 — 변경 하나가 폴더 하나에서 끝나는 쪽이 기능별입니다.

엔드포인트 그룹 확장 메서드는 기능 폴더 안에 🟡 중급

// Features/Orders/OrderEndpoints.cs
namespace Shop.Api.Features.Orders;

public static class OrderEndpoints
{
    public static IEndpointRouteBuilder MapOrders(this IEndpointRouteBuilder app)
    {
        var g = app.MapGroup("/orders").WithTags("Orders");

        g.MapPost("/", PlaceOrder.Handle);
        g.MapPost("/{id:long}/cancel", CancelOrder.Handle);
        return app;
    }
}

// Program.cs — 기능이 늘어도 한 줄씩만 늘어납니다
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddInfrastructure(builder.Configuration); // Infrastructure/ 의 확장 메서드
var app = builder.Build();
app.MapOrders();
app.MapMembers();
app.Run();
// Features/Orders/PlaceOrder.cs — 요청 · 응답 · 처리가 한 파일
using Microsoft.AspNetCore.Http.HttpResults;
using Shop.Api.Infrastructure;

namespace Shop.Api.Features.Orders;

public static class PlaceOrder
{
    public sealed record Request(string Item, int Quantity);
    public sealed record Response(long Id);

    public static async Task<Results<Created<Response>, ValidationProblem>> Handle(
        Request req, AppDbContext db, CancellationToken ct)
    {
        if (req.Quantity <= 0)
            return TypedResults.ValidationProblem(new Dictionary<string, string[]>
            {
                ["quantity"] = ["수량은 1 이상이어야 합니다"]
            });

        var order = new Order { Item = req.Item, Quantity = req.Quantity };
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);
        return TypedResults.Created($"/orders/{order.Id}", new Response(order.Id));
    }
}
Controllers 도 기능별로 둘 수 있습니다 — MVC 는 폴더가 아니라 타입으로 컨트롤러를 찾으므로 Features/Orders/OrdersController.cs 로 옮겨도 그대로 동작합니다. 계층형 vs 기능별은 Minimal API 냐 Controllers 냐와 별개의 선택입니다.
무엇을어디에금지
라우트 묶음Features/<기능>/<기능>Endpoints.cs 의 Map<기능>()Program.cs 에 MapPost 수십 줄
DI 등록그 계층 · 기능의 Add<무엇>() 확장 메서드Program.cs 200줄
기능끼리 공유Common/ 또는 도메인 프로젝트(STR 03)Orders 가 Members 내부 클래스를 직접 사용
DbContextInfrastructure/ 하나 — 기능마다 DbSet기능마다 DbContext (트랜잭션이 갈라짐)
정리 — 엔드포인트 20개 이하면 템플릿 그대로도 괜찮고, 넘으면 Features/<기능>/ 로 묶어 라우트는 그 폴더의 Map<기능>() 에, Program.cs 는 조립만 하게 둡니다.
STR 03

Clean Architecture 솔루션 — 네 프로젝트와 참조 방향, 그리고 비용

업무 규칙이 복잡하고 오래 살아남을 시스템이면 규칙을 프레임워크와 DB 로부터 떼어 두는 값어치가 있습니다. .NET 에서는 이것을 프로젝트 분리 + 참조 방향으로 컴파일러가 지키게 합니다. 만드는 명령 · 각 층의 책임표 · MediatR 은 엔터프라이즈 탭 ENT 04, 짧은 개요는 고급 탭 ADV 11 에 있으니 여기서는 모양과 비용 판단만 봅니다.

네 프로젝트 + 테스트

src/
├─ Shop.Domain/            # 엔티티 · 값 객체 · 규칙 — 참조 0개
│  └─ Orders/Order.cs
├─ Shop.Application/       # 유스케이스 · 포트(인터페이스) → Domain
│  └─ Orders/

│     └─ IOrderRepository.cs

│  ├─ Persistence/AppDbContext.cs
│  └─ DependencyInjection.cs

조립은 각 층의 확장 메서드로

// Shop.Infrastructure/DependencyInjection.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using Shop.Application.Orders;
using Shop.Infrastructure.Persistence;

namespace Shop.Infrastructure;

public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services, IConfiguration config)
    {
        services.AddDbContext<AppDbContext>(o =>
            o.UseNpgsql(config.GetConnectionString("Shop")));
        // 인터페이스는 Application 에, 구현은 여기에
        services.AddScoped<IOrderRepository, EfOrderRepository>();
        return services;
    }
}
Api 가 Infrastructure 를 참조하는 이유는 DI 조립 한 곳뿐입니다. 엔드포인트 코드에서 AppDbContext 를 직접 쓰기 시작하면 이 구조의 이점이 사라지니, 그것을 막는 테스트를 STR 10 에서 겁니다.
참조 그래프 — Domain 은 나가는 화살표가 0개. 하나라도 생기면 이 구조를 택한 이유가 사라집니다.

이점과 비용 — 작은 서비스엔 과합니다 🟡 중급

항목얻는 것내는 것
참조 방향Domain 이 EF · HTTP 를 쓰면 컴파일 오류 — 리뷰 대신 빌드가 지킴프로젝트 4개 + 테스트 3개, 솔루션 관리 비용
테스트규칙 테스트가 DB · 웹 서버 없이 수 초 안에인터페이스와 가짜 구현이 늘어남
교체DB · 메일 · 외부 API 를 바꿔도 Domain · Application 은 그대로실제로 바꾸는 일은 드묾 — "언젠가"를 위한 비용
새 기능 하나어디에 무엇을 둘지 팀 전체가 같은 답DTO → 커맨드 → 엔티티 매핑 2~3번, 파일 4~6개
❌ 엔드포인트 8개짜리 CRUD 에 네 프로젝트
Shop.Domain/          Order.cs          # 속성만 있는 클래스
Shop.Application/     OrderService.cs   # 리포지토리를 그대로 전달
Shop.Infrastructure/  OrderRepository.cs
Shop.Api/             OrdersController.cs
# 규칙이 없으니 층마다 같은 필드를 옮겨 적기만 합니다
✅ 프로젝트 하나 + 기능별 폴더로 시작
Shop.Api/
└─ Features/Orders/   PlaceOrder.cs · Order.cs
# 규칙이 자라는 기능이 생기면 그때
#   Shop.Domain 을 떼어 내고 (1단계)
#   외부 연동이 늘면 Infrastructure 를 뗍니다 (2단계)
정리 — Clean Architecture 는 참조 방향을 컴파일러가 지키게 하는 솔루션 모양입니다. 업무 규칙이 복잡하고 오래 사는 시스템에만 쓰고, CRUD 서비스는 STR 02 의 기능별 폴더로 충분합니다.
STR 04

테스트 프로젝트 — 미러링 · 단위/통합 분리 · 공유 픽스처

자바는 src/test/java 가 같은 모듈 안에 있지만, .NET 은 테스트도 별도 프로젝트입니다. 그래서 "어느 테스트 프로젝트가 어느 운영 프로젝트를 보느냐"가 곧 구조입니다. xUnit 사용법은 도구 탭 TOOL 04 · 05, Spring 테스트와의 대응은 엔터프라이즈 탭 ENT 12 에 있으니 여기서는 배치와 경계만 봅니다.

운영 프로젝트마다 거울 하나

tests/
├─ Directory.Build.props          # 테스트 공통 (아래)
├─ Shop.Domain.Tests/             # src/Shop.Domain 의 거울
│  └─ Orders/OrderTests.cs        #   ↔ src/Shop.Domain/Orders/Order.cs
├─ Shop.Application.Tests/        # 가짜 리포지토리로 유스케이스
├─ Shop.Api.IntegrationTests/     # 앱을 메모리에 띄워 HTTP 로
│  ├─ ShopApiFactory.cs           # 공유 픽스처 — WebApplicationFactory
│  └─ Orders/PlaceOrderTests.cs
└─ Shop.Testing/                  # (선택) 빌더 · 가짜 시계 — 테스트끼리 공유
# 이름 규칙: 단위 = <대상>.Tests · 통합 = <대상>.IntegrationTests
폴더 구조까지 거울로 두면 "이 클래스의 테스트 어디 있지?"를 묻지 않습니다. 단위와 통합을 프로젝트로 나누면 PR 마다 단위만, 야간에 통합까지처럼 CI 에서 골라 돌리기 쉽습니다.

// App.xaml.cs — App.xaml 의 StartupUri 는 지웁니다
using System.Windows;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

public partial class App : Application
{
    private IHost? _host;

    protected override void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);
        var builder = Host.CreateApplicationBuilder(e.Args);
        builder.Services.AddSingleton<IOrderService, OrderService>();
        builder.Services.AddTransient<MainViewModel>();
        builder.Services.AddTransient<MainWindow>();   // 생성자에서 MainViewModel 을 받음

    }

    protected override void OnExit(ExitEventArgs e)
    {
        _host?.Dispose();          // 싱글턴 서비스의 Dispose 호출
        base.OnExit(e);
    }
}

asmdef 어셈블리는 기본 어셈블리(Assembly-CSharp)를 참조할 수 없습니다. asmdef 가 없는 서드파티 스크립트는 Assembly-CSharp(Plugins/ 안이면 firstpass)로 컴파일되므로 우리 asmdef 에서 안 보입니다. 그 폴더에 asmdef 를 하나 만들어 주거나 업체가 asmdef 를 제공하는 버전을 쓰세요.
재컴파일 범위 = 고친 어셈블리 + 그것을 참조하는 어셈블리. 자주 고치는 코드를 잎(UI · Editor)에 둘수록 저장 후 대기가 짧아집니다.

언제 솔루션을 나누나

상황구조
같은 팀 · 같은 DB · 같이 배포해도 됨한 솔루션에 실행 프로젝트 여럿 (이 섹션)
배포 주기만 다름한 솔루션 유지, CI 에서 바뀐 실행 프로젝트만 빌드 · 배포
팀이 다르고 DB 도 따로솔루션 · 저장소 분리 — 공유 코드는 사내 NuGet (STR 09)
공유 코드가 계속 같이 바뀜나누지 마세요 — 패키지 버전 맞추기가 일이 됩니다
배치를 API 안의 백그라운드 서비스로 넣는 유혹 — 처음엔 편하지만, API 를 3대로 늘리는 순간 배치도 3번 돕니다. "몇 대로 늘릴지가 다르면 실행 프로젝트를 나눈다"가 기준입니다(대규모 트래픽 탭 · BATCH 12).
정리 — 실행 파일이 늘면 실행 프로젝트를 늘리고 업무 코드는 classlib 으로 뺍니다. 실행 프로젝트끼리는 참조하지 않고, DI 등록 확장 메서드를 같이 써서 등록이 갈라지지 않게 합니다.
STR 09

라이브러리 · NuGet — 공개 API · internal · 다중 타깃

앱은 아무 클래스나 public 이어도 사고가 작지만, 라이브러리는 public 이 곧 약속입니다. 한 번 내보낸 public 멤버는 쓰는 쪽을 깨지 않고는 지울 수 없습니다. 패키지 만들기 · 올리기 · SemVer 는 도구 탭 TOOL 09 에 있으니 여기서는 무엇을 공개하고 그 경계를 어떻게 지키는지를 봅니다.
