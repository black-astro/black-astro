ADV 01

async / await 완전정복

"스레드를 하나 더 쓰는 것"이 아닙니다. 기다리는 동안 스레드를 반납하는 것 — 서버 처리량이 여기서 갈립니다.

같은 서버가 동시에 몇 명을 받느냐는 대기 구간에서 스레드를 놓느냐로 결정됩니다.

기본형과 규칙

public async Task<Player> LoadAsync(int id, CancellationToken ct)
{
    var row  = await _db.FindAsync(id, ct);        // 대기 = 스레드 반납
    var meta = await _http.GetAsync(url, ct);      // 순차로 필요하면 이렇게
    return Map(row, meta);
}

// 서로 관계없는 작업은 동시에
var (profile, items) = (LoadProfileAsync(id), LoadItemsAsync(id));
await Task.WhenAll(profile, items);
return new View(profile.Result, items.Result);

// 타임아웃
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(3));
await CallAsync(cts.Token);
  • async 는 위로 전파됩니다 — 중간에서 끊지 말고 진입점까지 이어 주세요
  • 반환은 Task·Task<T>. async void 는 이벤트 핸들러에서만
  • 취소 토큰은 맨 아래까지 전달 — 안 그러면 취소해도 일이 계속 돕니다

터지는 세 가지 패턴

.Result · .Wait()
var user = GetAsync().Result;
// UI·구형 ASP.NET 에서 데드락
// 서버에서는 스레드 고갈
끝까지 await
var user = await GetAsync();
// ② async void — 예외를 잡을 수 없어 프로세스가 죽습니다
async void Save() { await ...; }          // ✗
async Task SaveAsync() { await ...; }     // ✓

// ③ 루프 안에서 await — N번 왕복합니다
foreach (var id in ids) await LoadAsync(id);            // ✗ 느림

var tasks = ids.Select(LoadAsync);                       // ✓ 동시에
var all   = await Task.WhenAll(tasks);

// 단, 동시 수를 제한해야 상대 서버가 죽지 않습니다
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (id, token) => await LoadAsync(id, token));
Unity 에서는 이야기가 다릅니다. 유니티의 API 는 메인 스레드에서만 호출할 수 있어 await 뒤에 다른 스레드로 넘어가면 터집니다. 게임 코드에서는 코루틴이나 UniTask(할당 없는 async)를 쓰세요.
await 의 질문은 "몇 초 걸리나"가 아니라 "기다리는 동안 이 스레드가 무엇을 하는가"입니다.
ADV 02

Task · ValueTask · 취소와 재시도

비동기의 나머지 절반 — 언제 멈추고, 실패하면 어떻게 하는가.

Task 와 ValueTask

// Task — 힙에 객체 하나. 기본은 이걸로 충분합니다.
public Task<int> GetAsync() => _db.CountAsync();

// ValueTask — '대부분 이미 값이 있는' 경우의 할당 제거
public ValueTask<Item> GetItemAsync(int id)
{
    if (_cache.TryGetValue(id, out var hit))
        return new ValueTask<Item>(hit);        // 할당 0
    return new ValueTask<Item>(LoadSlowAsync(id));
}
ValueTask 는 두 번 await 하면 안 됩니다. 결과를 재사용하려면 .AsTask() 로 바꾸세요. 애매하면 Task 를 쓰는 것이 안전하고, ValueTask 는 측정해서 병목으로 확인된 뒤 도입하세요. 
// 오래 걸리는 CPU 작업은 스레드풀로 (서버에서만)
var result = await Task.Run(() => HeavyCompute(data), ct);

// 진행률 보고
var progress = new Progress<int>(p => bar.Value = p);
await DownloadAsync(url, progress, ct);

취소 · 재시도 · 타임아웃

// 취소는 '요청'입니다 — 받은 쪽이 확인해야 멈춥니다
public async Task WorkAsync(CancellationToken ct)
{
    while (true)
    {
        ct.ThrowIfCancellationRequested();       // 협조 지점
        await StepAsync(ct);
    }
}

// 재시도 — 지수 백오프 + 지터
static async Task<T> RetryAsync<T>(Func<Task<T>> act, int max = 3)
{
    for (int i = 0; ; i++)
    {
        try { return await act(); }
        catch (Exception e) when (i < max && IsTransient(e))
        {
            var wait = TimeSpan.FromMilliseconds(
                Math.Pow(2, i) * 200 + Random.Shared.Next(100));
            await Task.Delay(wait);
        }
    }
}
직접 만들기 전에 Polly 를 보세요. 재시도·서킷 브레이커·타임아웃·벌크헤드가 한 줄 설정으로 붙습니다 (🧰 실전 도구 탭). 여기 코드는 안에서 무슨 일이 일어나는지 알기 위한 것입니다.
재시도해서는 안 되는 것도 있습니다. 결제·아이템 지급처럼 두 번 실행되면 안 되는 작업은 멱등 키를 함께 보내야 안전합니다(🔷 ASP.NET Core 탭).
ADV 03

스레드 · 동기화 · Channel

게임 서버는 여러 스레드가 같은 데이터를 만집니다. 여기서 나는 버그는 재현이 안 됩니다.

경쟁 상태와 lock

private int _count;
public void Add() => _count++;      // ✗ 원자적이지 않다 (읽기→더하기→쓰기)

// ① lock — 가장 쉽고 대부분 충분
private readonly object _gate = new();
public void Add() { lock (_gate) { _count++; } }

// ② Interlocked — 단순 연산은 락 없이
Interlocked.Increment(ref _count);
Interlocked.CompareExchange(ref _state, 1, 0);   // 0이면 1로

// ③ 동시 컬렉션
private readonly ConcurrentDictionary<int, Session> _sessions = new();
_sessions.TryAdd(id, s);
_sessions.AddOrUpdate(id, s, (_, old) => old.Merge(s));
lock 안에서 await 는 불가능합니다. 비동기 구간을 보호해야 하면 SemaphoreSlim(1,1) 을 쓰세요. 그리고 락을 잡은 채 외부 호출(DB·HTTP)을 하지 마세요 — 전체가 그 속도에 묶입니다.

Channel — 생산자·소비자의 표준

// 게임 서버에서 '패킷 수신 → 처리' 를 잇는 가장 깔끔한 방법
var ch = Channel.CreateBounded<Packet>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // 밀리면 오래된 것부터 버림
    SingleReader = true,
});

// 생산자 — 네트워크 스레드
await ch.Writer.WriteAsync(packet, ct);

// 소비자 — 로직 스레드 하나 (락이 필요 없어집니다)
await foreach (var p in ch.Reader.ReadAllAsync(ct))
    Handle(p);
락을 줄이는 가장 좋은 방법은 "공유하지 않는 것"입니다. 게임 룸마다 스레드(또는 액터) 하나가 그 룸만 처리하게 만들면 룸 안의 데이터에는 락이 필요 없습니다 — 상용 게임 서버가 널리 쓰는 구조입니다(🌐 게임 서버 탭).
ADV 04

Span<T> · Memory<T> — 복사 없는 처리

배열을 자르지 않고 들여다보는 방법. 패킷 파싱·문자열 처리에서 할당을 0으로 만듭니다.

쓰는 법

// Substring 은 새 문자열을 만든다 → 할당
var head = text.Substring(0, 4);          // ✗ 힙 할당

// Span 은 '창'만 만든다 → 할당 0
ReadOnlySpan<char> span = text.AsSpan(0, 4);   // ✓

// 패킷 파싱 (게임 서버의 핵심 경로)
static bool TryParse(ReadOnlySpan<byte> buf, out Header h)
{
    if (buf.Length < 8) { h = default; return false; }
    h = new Header(
        Id:   BinaryPrimitives.ReadInt32LittleEndian(buf),
        Size: BinaryPrimitives.ReadInt32LittleEndian(buf[4..]));
    return true;
}

// 스택에 임시 버퍼 (작은 크기만!)
Span<byte> tmp = stackalloc byte[128];

규칙과 한계

  • Span<T> 는 필드에 저장할 수 없습니다 — 스택 전용(ref struct)
  • async 메서드에서 쓸 수 없습니다 — 그때는 Memory<T>
  • stackalloc 은 루프 안에서 금지 — 스택이 넘칩니다
  • 큰 버퍼는 ArrayPool<T>.Shared 에서 빌려 쓰고 돌려주세요
var buf = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var n = await stream.ReadAsync(buf.AsMemory(), ct);
    Process(buf.AsSpan(0, n));
}
finally { ArrayPool<byte>.Shared.Return(buf); }   // ★ 반드시 반납
모든 코드에 Span 을 바를 필요는 없습니다. 효과가 큰 곳은 초당 수천 번 도는 경로(패킷 수신·직렬화·로그 파싱)입니다. 나머지는 가독성이 더 중요합니다.
ADV 05

GC 와 할당 줄이기

"게임이 가끔 뚝뚝 끊긴다"의 범인은 대개 GC 입니다. 메모리를 아끼는 게 아니라 새로 만드는 횟수를 줄이는 것이 핵심입니다.

어디서 몰래 할당되는가

void Update()
{
    // ① 문자열 — 매 프레임 새 객체
    label.text = "HP " + hp;                     // ✗

    // ② 박싱 — 값 타입이 object 로 변할 때
    object o = 3;                                // ✗
    Debug.Log(string.Format("{0}", hp));         // ✗ 박싱

    // ③ 람다가 바깥 변수를 잡을 때(클로저)
    list.ForEach(x => x.Add(offset));            // ✗ offset 캡처

    // ④ LINQ · foreach on interface
    var alive = enemies.Where(e => e.Hp > 0);    // ✗ 반복자 객체

    // ⑤ params · 배열
    Log("a", "b");                               // params → 배열 생성
}
이 다섯 개만 잡아도 프레임 튐의 대부분이 사라집니다. Unity 라면 Profiler 의 GC Alloc 열을 켜고 0 B 가 아닌 줄을 위에서부터 지워 나가세요.

고치는 법

// ① 값이 바뀔 때만 갱신 + 캐시
private int _shownHp = -1;
void Update()
{
    if (_shownHp == hp) return;
    _shownHp = hp;
    label.SetText("HP {0}", hp);      // TMP 의 할당 없는 API
}

// ② 재사용 버퍼
private readonly List<Collider> _hits = new(32);
_hits.Clear();
Physics.OverlapSphereNonAlloc(pos, r, _buffer);   // NonAlloc 계열

// ③ 구조체 + 정적 람다
list.ForEach(static x => x.Reset());   // 캡처 없음을 컴파일러가 보장

// ④ 오브젝트 풀
var bullet = _pool.Rent();
_pool.Return(bullet);
서버에서는 관점이 다릅니다. 게임 클라이언트는 순간 멈춤(프레임 튐)이 문제고, 서버는 처리량과 p99 지연이 문제입니다. 서버 GC(<ServerGarbageCollection>true</>)를 켜는 것만으로 처리량이 크게 오르는 경우가 많습니다(🔬 전문가 탭).
ADV 06

의존성 주입 · 설정

new 를 코드 안에 흩뿌리지 않고 한 곳에서 조립합니다. 테스트가 쉬워집니다.

기본형

var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddSingleton<IClock, SystemClock>();      // 앱 전체 1개
builder.Services.AddScoped<IUserRepository, UserRepo>();   // 요청마다 1개
builder.Services.AddTransient<IMailer, Mailer>();          // 쓸 때마다 새로
builder.Services.AddHttpClient<IPayApi, PayApi>();

// 설정을 타입으로 받기
builder.Services.Configure<GameOptions>(
    builder.Configuration.GetSection("Game"));

var app = builder.Build();

// 생성자로 받기만 하면 됩니다
public sealed class MatchService(
    IUserRepository users,
    IOptions<GameOptions> opt,
    ILogger<MatchService> log)
{
    private readonly int _maxParty = opt.Value.MaxParty;
}

수명을 틀리면 생기는 일

수명쓸 곳주의
Singleton캐시 · 설정 · 커넥션 풀상태를 넣으면 경쟁
Scoped요청 단위 작업 · DbContext싱글턴이 주입받으면 오류
Transient가벼운 도우미많이 만들면 할당
싱글턴이 Scoped 를 주입받으면 안 됩니다. 요청이 끝나도 붙잡고 있어 DbContext 가 망가집니다. 꼭 필요하면 IServiceScopeFactory 로 그때그때 범위를 만드세요.
Unity 에는 이 컨테이너가 없습니다. 대신 VContainer·Zenject 를 쓰거나, 간단하면 ScriptableObject 에 설정을 담아 주입하는 방식이 흔합니다.

수명(Lifetime) 세 가지 — 잘못 고르면 버그가 됩니다

등록만들어지는 횟수맞는 것
Singleton앱 전체에 1개설정 · 캐시 · HttpClient 팩토리
Scoped요청마다 1개DbContext · 현재 사용자 정보
Transient주입할 때마다 새로가벼운 무상태 서비스
1순위 사고 — Singleton 이 Scoped 를 물고 있는 것. 싱글턴 서비스에 DbContext 를 주입하면 모든 요청이 하나의 DbContext 를 공유해 동시성 예외와 데이터 오염이 납니다. .NET 이 기본으로 이 조합을 감지해 던지는 예외가 "Cannot consume scoped service from singleton" 입니다.

DI 가 있으면 테스트가 이렇게 됩니다

// 결제 서비스 — 외부 PG 사를 인터페이스 뒤로
public class OrderService(IPayGateway pay, IClock clock)
{
    public async Task<Order> Checkout(Cart cart)
    {
        var paid = await pay.ChargeAsync(cart.Total);
        return new Order(cart, paid.TxId, clock.Now);
    }
}

// 테스트 — 진짜 결제 없이 실패 상황까지 재현
var fakePay  = new FakeGateway { FailWith = "한도 초과" };
var fixedNow = new FixedClock(new DateTime(2026, 1, 1));
var svc = new OrderService(fakePay, fixedNow);

await Assert.ThrowsAsync<PaymentException>(
    () => svc.Checkout(cart));
new 를 직접 쓰는 순간 그 클래스는 테스트에서 바꿔치기할 수 없습니다. "밖에서 받는다"는 규칙 하나가 시간(IClock)·랜덤·외부 API 를 전부 가짜로 갈아 끼울 수 있게 만듭니다 — DI 의 진짜 값어치입니다.

ADV 08

리플렉션 · 소스 제너레이터

"코드가 코드를 다루는" 영역. 편하지만 느립니다 — 빌드 시점으로 옮기는 것이 요즘 방식입니다.

리플렉션

// 타입 정보를 런타임에 읽는다
var t = typeof(Player);
foreach (var p in t.GetProperties())
    Console.WriteLine($"{p.Name} : {p.PropertyType.Name}");

// 속성(Attribute) 으로 표시하고 찾아 쓰기
[AttributeUsage(AttributeTargets.Method)]
public sealed class CommandAttribute(string name) : Attribute
{
    public string Name { get; } = name;
}

var handlers = typeof(Program).Assembly.GetTypes()
    .SelectMany(t => t.GetMethods())
    .Where(m => m.GetCustomAttribute<CommandAttribute>() is not null);
리플렉션은 느리고, AOT 에서 잘립니다. Unity 의 IL2CPP 나 .NET Native AOT 에서는 쓰지 않는 코드로 판단해 지워질 수 있습니다. 시작할 때 한 번만 훑고 결과를 캐시하거나, 아래 소스 제너레이터로 옮기세요.

소스 제너레이터 — 빌드 때 코드를 만든다

// 쓰는 쪽은 partial 하나면 됩니다
public partial class Player
{
    [GeneratedRegex(@"^[a-zA-Z0-9_]{3,16}$")]
    private static partial Regex NameRule();     // 컴파일 시점 생성

    public bool IsValidName(string n) => NameRule().IsMatch(n);
}

// 로깅도 같은 방식 — 문자열 포맷을 미리 만들어 둡니다
public static partial class Log
{
    [LoggerMessage(Level = LogLevel.Warning,
                   Message = "매칭 실패 {RoomId} 사유={Reason}")]
    public static partial void MatchFailed(ILogger l, int roomId, string reason);
}
효과가 확실한 세 곳 — 정규식·로깅·JSON. 전부 런타임 리플렉션을 빌드 시점으로 옮겨 시작 속도와 AOT 호환성을 함께 얻습니다.
ADV 09

네이티브 상호운용 — P/Invoke

C·C++ 로 된 기존 자산을 그대로 씁니다. 게임의 물리·오디오·플랫폼 SDK 연동에 필요합니다.

DllImport

using System.Runtime.InteropServices;

internal static partial class Native
{
    // C# 12+ — 소스 제너레이터 방식(빠르고 AOT 안전)
    [LibraryImport("user32.dll", StringMarshalling = StringMarshalling.Utf16)]
    [return: MarshalAs(UnmanagedType.Bool)]
    internal static partial bool MessageBeep(uint type);

    [LibraryImport("mylib", EntryPoint = "compute")]
    internal static partial int Compute(
        ReadOnlySpan<float> input, Span<float> output, int len);
}
경계를 넘는 비용은 공짜가 아닙니다. 한 번에 큰 덩어리를 넘기세요 — 루프 안에서 한 값씩 부르면 네이티브가 아무리 빨라도 전체는 느려집니다.

지켜야 할 것

  • 구조체 레이아웃을 [StructLayout(LayoutKind.Sequential)] 로 고정
  • 포인터로 넘길 배열은 고정(fixed)하거나 Span 사용 — GC 가 옮기면 터집니다
  • 네이티브가 준 메모리는 누가 해제하는지 문서로 남기세요
  • 플랫폼별 바이너리(.dll·.so·.dylib)를 전부 배포해야 합니다
Unity 에서는 더 조심해야 합니다. 네이티브 플러그인은 에디터에서 한 번 로드되면 안 내려갑니다 — DLL 을 교체하려면 에디터를 재시작해야 하고, 플러그인이 죽으면 에디터가 통째로 죽습니다.
ADV 10

성능 측정 — BenchmarkDotNet

추측하지 말고 재세요. "이게 더 빠를 것 같다"는 대부분 틀립니다.

벤치마크 작성

dotnet add package BenchmarkDotNet
dotnet run -c Release          # ★ 반드시 Release
[MemoryDiagnoser]                       // 할당량도 함께 측정
[SimpleJob(RuntimeMoniker.Net100)]
public class ParseBench
{
    private string _line = "12,34,56";

    [Benchmark(Baseline = true)]
    public int[] Split() => _line.Split(',').Select(int.Parse).ToArray();

    [Benchmark]
    public int SpanParse()
    {
        var s = _line.AsSpan(); int sum = 0;
        foreach (var range in s.Split(','))
            sum += int.Parse(s[range]);
        return sum;
    }
}

읽는 법 · 함정

| Method    |      Mean | Ratio | Allocated |
|---------- |----------:|------:|----------:|
| Split     | 210.4 ns  |  1.00 |     264 B |
| SpanParse |  38.7 ns  |  0.18 |       0 B |   ← 5배 · 할당 0
  • Allocated 열을 먼저 보세요 — 게임에서는 이게 프레임 튐입니다
  • Mean 차이가 20% 이내면 의미 없는 경우가 많습니다(측정 오차·환경)
  • 실제 데이터 크기로 재세요. 10개와 10만 개는 결과가 뒤집힙니다
  • Debug 빌드 측정은 전부 무효입니다
먼저 프로파일러로 병목을 찾고, 그다음 벤치마크로 대안을 비교하세요. 순서를 바꾸면 전체의 0.1% 를 5배 빠르게 만드는 헛수고를 하게 됩니다 (🔬 전문가 탭 프로파일링).

복사해 쓰는 벤치마크 — "어느 쪽이 빠른가" 논쟁을 끝내는 법

// dotnet add package BenchmarkDotNet
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]                      // ★ 할당량까지 측정
public class StringJoinBench
{
    private readonly int[] _nums = Enumerable.Range(0, 1_000).ToArray();

    [Benchmark(Baseline = true)]
    public string Concat()
    {
        var s = "";
        foreach (var n in _nums) s += n + ",";
        return s;
    }

    [Benchmark]
    public string Builder()
    {
        var sb = new StringBuilder();
        foreach (var n in _nums) sb.Append(n).Append(',');
        return sb.ToString();
    }

    [Benchmark]
    public string Join() => string.Join(',', _nums);
}

BenchmarkRunner.Run<StringJoinBench>();   // ★ Release 로 실행!
| Method  |        Mean |   Ratio |  Allocated |
|---------|------------:|--------:|-----------:|
| Concat  | 1,213.42 us |    1.00 | 11,265 KB  |  ← 기준
| Builder |    12.87 us |    0.01 |     33 KB  |  94배 빠르고
| Join    |     9.21 us |    0.008|     15 KB  |  할당은 1/750
Stopwatch 로 한 번 돌려 보는 것은 측정이 아닙니다. JIT 워밍업·GC 타이밍·CPU 부스트에 따라 결과가 매번 다릅니다. BenchmarkDotNet 은 워밍업 후 수백 번 반복해 통계를 내고, Debug 빌드로 돌리면 실행을 거부합니다 — 그것이 정답인 이유입니다.

ADV 12

자주 하는 실수 모음

코드 리뷰에서 반복해서 지적하게 되는 것들을 모았습니다.

언어 · 런타임

  • DateTime.Now 대신 DateTimeOffset.UtcNow — 서버는 UTC 로 저장하고 표시할 때만 변환
  • new Random() 을 반복 생성 — 같은 값이 나옵니다. Random.Shared
  • IDisposable 을 안 닫음 — using 을 습관으로
  • 예외를 흐름 제어로 사용 — 느리고 의도가 흐려집니다
  • == 로 문자열 비교 시 문화권 이슈 — StringComparison 명시
  • float 비교를 == 로 — 오차 범위로 비교하세요

서버 · 게임

  • 클라이언트를 믿는 것 — 좌표·데미지·재화는 서버가 계산합니다(🌐 게임 서버 탭)
  • 동기 API 를 서버에서 호출 — .Result 하나로 처리량이 무너집니다
  • Update 안의 GetComponent·Find — Awake 에서 캐시
  • 로그를 문자열로 조립 — 구조적 로깅(log.Info("x {A}", a))
  • 설정을 코드에 하드코딩 — 환경별로 갈라지는 순간 사고가 납니다
  • 테스트 없는 리팩터링 — 성능 개선일수록 동작 보장이 먼저입니다
다음 단계 — 게임이라면 🎮 Unity 기초, 서버라면 🌐 게임 서버 또는 🔷 ASP.NET Core, 런타임 내부가 궁금하면 🔬 전문가 · CLR 내부로 이어집니다.
