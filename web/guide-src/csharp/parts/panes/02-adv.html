ADV 01

async / await 완전정복

"스레드를 하나 더 쓰는 것"이 아닙니다. 기다리는 동안 스레드를 반납하는 것 — 서버 처리량이 여기서 갈립니다.

같은 서버가 동시에 몇 명을 받느냐는 대기 구간에서 스레드를 놓느냐로 결정됩니다.

기본형과 규칙

public async Task<Player> LoadAsync(int id, CancellationToken ct)
{
    var row  = await _db.FindAsync(id, ct);        // 대기 = 스레드 반납
    var meta = await _http.GetAsync(url, ct);      // 순차로 필요하면 이렇게
    return Map(row, meta);
}

// 서로 관계없는 작업은 동시에
var (profile, items) = (LoadProfileAsync(id), LoadItemsAsync(id));
await Task.WhenAll(profile, items);
return new View(profile.Result, items.Result);

// 타임아웃
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(3));
await CallAsync(cts.Token);
  • async 는 위로 전파됩니다 — 중간에서 끊지 말고 진입점까지 이어 주세요
  • 반환은 Task·Task<T>. async void 는 이벤트 핸들러에서만
  • 취소 토큰은 맨 아래까지 전달 — 안 그러면 취소해도 일이 계속 돕니다

터지는 세 가지 패턴

.Result · .Wait()
var user = GetAsync().Result;
// UI·구형 ASP.NET 에서 데드락
// 서버에서는 스레드 고갈
끝까지 await
var user = await GetAsync();
// ② async void — 예외를 잡을 수 없어 프로세스가 죽습니다
async void Save() { await ...; }          // ✗
async Task SaveAsync() { await ...; }     // ✓

// ③ 루프 안에서 await — N번 왕복합니다
foreach (var id in ids) await LoadAsync(id);            // ✗ 느림

var tasks = ids.Select(LoadAsync);                       // ✓ 동시에
var all   = await Task.WhenAll(tasks);

// 단, 동시 수를 제한해야 상대 서버가 죽지 않습니다
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (id, token) => await LoadAsync(id, token));
Unity 에서는 이야기가 다릅니다. 유니티의 API 는 메인 스레드에서만 호출할 수 있어 await 뒤에 다른 스레드로 넘어가면 터집니다. 게임 코드에서는 코루틴이나 UniTask(할당 없는 async)를 쓰세요.
await 의 질문은 "몇 초 걸리나"가 아니라 "기다리는 동안 이 스레드가 무엇을 하는가"입니다.
ADV 02

Task · ValueTask · 취소와 재시도

비동기의 나머지 절반 — 언제 멈추고, 실패하면 어떻게 하는가.

Task 와 ValueTask

// Task — 힙에 객체 하나. 기본은 이걸로 충분합니다.
public Task<int> GetAsync() => _db.CountAsync();

// ValueTask — '대부분 이미 값이 있는' 경우의 할당 제거
public ValueTask<Item> GetItemAsync(int id)
{
    if (_cache.TryGetValue(id, out var hit))
        return new ValueTask<Item>(hit);        // 할당 0
    return new ValueTask<Item>(LoadSlowAsync(id));
}
ValueTask 는 두 번 await 하면 안 됩니다. 결과를 재사용하려면 .AsTask() 로 바꾸세요. 애매하면 Task 를 쓰는 것이 안전하고, ValueTask 는 측정해서 병목으로 확인된 뒤 도입하세요. 
// 오래 걸리는 CPU 작업은 스레드풀로 (서버에서만)
var result = await Task.Run(() => HeavyCompute(data), ct);

// 진행률 보고
var progress = new Progress<int>(p => bar.Value = p);
await DownloadAsync(url, progress, ct);

취소 · 재시도 · 타임아웃

// 취소는 '요청'입니다 — 받은 쪽이 확인해야 멈춥니다
public async Task WorkAsync(CancellationToken ct)
{
    while (true)
    {
        ct.ThrowIfCancellationRequested();       // 협조 지점
        await StepAsync(ct);
    }
}

// 재시도 — 지수 백오프 + 지터
static async Task<T> RetryAsync<T>(Func<Task<T>> act, int max = 3)
{
    for (int i = 0; ; i++)
    {
        try { return await act(); }
        catch (Exception e) when (i < max && IsTransient(e))
        {
            var wait = TimeSpan.FromMilliseconds(
                Math.Pow(2, i) * 200 + Random.Shared.Next(100));
            await Task.Delay(wait);
        }
    }
}
직접 만들기 전에 Polly 를 보세요. 재시도·서킷 브레이커·타임아웃·벌크헤드가 한 줄 설정으로 붙습니다 (🧰 실전 도구 탭). 여기 코드는 안에서 무슨 일이 일어나는지 알기 위한 것입니다.
재시도해서는 안 되는 것도 있습니다. 결제·아이템 지급처럼 두 번 실행되면 안 되는 작업은 멱등 키를 함께 보내야 안전합니다(🔷 ASP.NET Core 탭).
ADV 03

스레드 · 동기화 · Channel

게임 서버는 여러 스레드가 같은 데이터를 만집니다. 여기서 나는 버그는 재현이 안 됩니다.

경쟁 상태와 lock

private int _count;
public void Add() => _count++;      // ✗ 원자적이지 않다 (읽기→더하기→쓰기)

// ① lock — 가장 쉽고 대부분 충분
private readonly object _gate = new();
public void Add() { lock (_gate) { _count++; } }

// ② Interlocked — 단순 연산은 락 없이
Interlocked.Increment(ref _count);
Interlocked.CompareExchange(ref _state, 1, 0);   // 0이면 1로

// ③ 동시 컬렉션
private readonly ConcurrentDictionary<int, Session> _sessions = new();
_sessions.TryAdd(id, s);
_sessions.AddOrUpdate(id, s, (_, old) => old.Merge(s));
lock 안에서 await 는 불가능합니다. 비동기 구간을 보호해야 하면 SemaphoreSlim(1,1) 을 쓰세요. 그리고 락을 잡은 채 외부 호출(DB·HTTP)을 하지 마세요 — 전체가 그 속도에 묶입니다.

Channel — 생산자·소비자의 표준

// 게임 서버에서 '패킷 수신 → 처리' 를 잇는 가장 깔끔한 방법
var ch = Channel.CreateBounded<Packet>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // 밀리면 오래된 것부터 버림
    SingleReader = true,
});

// 생산자 — 네트워크 스레드
await ch.Writer.WriteAsync(packet, ct);

// 소비자 — 로직 스레드 하나 (락이 필요 없어집니다)
await foreach (var p in ch.Reader.ReadAllAsync(ct))
    Handle(p);
락을 줄이는 가장 좋은 방법은 "공유하지 않는 것"입니다. 게임 룸마다 스레드(또는 액터) 하나가 그 룸만 처리하게 만들면 룸 안의 데이터에는 락이 필요 없습니다 — 상용 게임 서버가 널리 쓰는 구조입니다(🌐 게임 서버 탭).
ADV 04

Span<T> · Memory<T> — 복사 없는 처리

배열을 자르지 않고 들여다보는 방법. 패킷 파싱·문자열 처리에서 할당을 0으로 만듭니다.

쓰는 법

// Substring 은 새 문자열을 만든다 → 할당
var head = text.Substring(0, 4);          // ✗ 힙 할당

// Span 은 '창'만 만든다 → 할당 0
ReadOnlySpan<char> span = text.AsSpan(0, 4);   // ✓

// 패킷 파싱 (게임 서버의 핵심 경로)
static bool TryParse(ReadOnlySpan<byte> buf, out Header h)
{
    if (buf.Length < 8) { h = default; return false; }
    h = new Header(
        Id:   BinaryPrimitives.ReadInt32LittleEndian(buf),
        Size: BinaryPrimitives.ReadInt32LittleEndian(buf[4..]));
    return true;
}

// 스택에 임시 버퍼 (작은 크기만!)
Span<byte> tmp = stackalloc byte[128];

규칙과 한계

  • Span<T> 는 필드에 저장할 수 없습니다 — 스택 전용(ref struct)
  • async 메서드에서 쓸 수 없습니다 — 그때는 Memory<T>
  • stackalloc 은 루프 안에서 금지 — 스택이 넘칩니다
  • 큰 버퍼는 ArrayPool<T>.Shared 에서 빌려 쓰고 돌려주세요
var buf = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var n = await stream.ReadAsync(buf.AsMemory(), ct);
    Process(buf.AsSpan(0, n));
}
finally { ArrayPool<byte>.Shared.Return(buf); }   // ★ 반드시 반납
모든 코드에 Span 을 바를 필요는 없습니다. 효과가 큰 곳은 초당 수천 번 도는 경로(패킷 수신·직렬화·로그 파싱)입니다. 나머지는 가독성이 더 중요합니다.
자르기·찾기·파싱이 반복되는 경로에서만 의미가 있습니다 — 그 밖에서는 Substring 이 읽기 좋고 충분히 빠릅니다.

Span · Memory · 배열 — 언제 무엇을

타입어디에 살 수 있나쓸 곳못 하는 것
Span<T>스택만(ref struct)동기 메서드 안의 파싱·슬라이스필드 저장 · async · 컬렉션에 넣기

할당 없이 파싱하기 — 실전 형태

// CSV 한 줄을 문자열 하나도 안 만들고 읽기
static bool TryParseRow(ReadOnlySpan<char> line, out Row row)
{
    row = default;

    var i1 = line.IndexOf(',');
    if (i1 < 0) return false;
    var i2 = line[(i1 + 1)..].IndexOf(',');
    if (i2 < 0) return false;
    i2 += i1 + 1;

    if (!int.TryParse(line[..i1], out var id)) return false;              // 할당 0
    var name = line[(i1 + 1)..i2];                                        // 창만
    if (!decimal.TryParse(line[(i2 + 1)..], out var amount)) return false;

    row = new Row(id, name.ToString(), amount);   // 필요한 것만 문자열로
    return true;
}

// 구분자로 나누기 — Split 은 배열 + 문자열들을 만듭니다
foreach (var part in line.Split(','))            // ✗ 할당 여러 개
{ }

foreach (var range in line.AsSpan().Split(','))  // ✓ .NET 9+ — 할당 0
{
    var part = line.AsSpan()[range];
}

// 문자열 조립도 할당 없이 (길이를 아는 경우)
var key = string.Create(16, (roomId, slot), static (dst, s) =>
{
    s.roomId.TryFormat(dst, out var w);
    dst[w] = ':';
    s.slot.TryFormat(dst[(w + 1)..], out _);
});
int.TryParse·decimal.TryParse·DateTime.TryParse 는 전부 ReadOnlySpan<char> 오버로드가 있습니다. 그래서 문자열로 만들지 않고 바로 숫자로 갈 수 있습니다. 반대 방향인 TryFormat 도 마찬가지여서, 파싱과 출력 양쪽 모두 할당 0 이 가능합니다.

여기서 실수합니다

// ✗ ① stackalloc 을 루프 안에서 — 스택이 쌓여 넘칩니다
for (var i = 0; i < 10000; i++)
{
    Span<byte> buf = stackalloc byte[1024];   // 스택 오버플로
}
// ✓ 루프 밖에서 한 번, 또는 ArrayPool 로
Span<byte> buf = stackalloc byte[1024];
for (var i = 0; i < 10000; i++) { buf.Clear(); /* ... */ }

// ✗ ② 크기를 입력에서 받아 stackalloc — 공격 지점이 됩니다
Span<byte> b = stackalloc byte[header.Length];       // 위험
// ✓ 상한을 두고 넘으면 풀에서
byte[]? rented = null;
Span<byte> b2 = header.Length <= 256
    ? stackalloc byte[256]
    : (rented = ArrayPool<byte>.Shared.Rent(header.Length));
try { /* 사용 */ }
finally { if (rented is not null) ArrayPool<byte>.Shared.Return(rented); }

// ✗ ③ 반납한 배열을 계속 씀 — 다른 곳이 그 배열을 빌려 갑니다
var arr = ArrayPool<byte>.Shared.Rent(1024);
ArrayPool<byte>.Shared.Return(arr);
Process(arr);                                  // 내용이 이미 바뀌었을 수 있습니다

// ✗ ④ Rent 는 "요청한 크기 이상"을 줍니다 — Length 를 믿지 마세요
var a = ArrayPool<byte>.Shared.Rent(100);
// a.Length 는 128 일 수 있습니다
Process(a.AsSpan(0, 100));                     // ✓ 실제 크기를 직접 잘라 쓰기

// ✗ ⑤ 민감 데이터를 담았다면 반납 전에 지우기
ArrayPool<byte>.Shared.Return(a, clearArray: true);
ArrayPool 은 "빌린 것을 반드시 돌려주는" 규칙 위에서만 안전합니다. 예외가 나서 Return 을 건너뛰면 풀이 말라 이후 Rent 가 매번 새로 할당하게 됩니다 — 최적화하려다 오히려 더 많이 할당하는 상태가 됩니다. 반드시 try/finally 로 감싸세요.
ADV 05

GC 와 할당 줄이기

"게임이 가끔 뚝뚝 끊긴다"의 범인은 대개 GC 입니다. 메모리를 아끼는 게 아니라 새로 만드는 횟수를 줄이는 것이 핵심입니다.

어디서 몰래 할당되는가

void Update()
{
    // ① 문자열 — 매 프레임 새 객체
    label.text = "HP " + hp;                     // ✗

    // ② 박싱 — 값 타입이 object 로 변할 때
    object o = 3;                                // ✗
    Debug.Log(string.Format("{0}", hp));         // ✗ 박싱

    // ③ 람다가 바깥 변수를 잡을 때(클로저)
    list.ForEach(x => x.Add(offset));            // ✗ offset 캡처

    // ④ LINQ · foreach on interface
    var alive = enemies.Where(e => e.Hp > 0);    // ✗ 반복자 객체

    // ⑤ params · 배열
    Log("a", "b");                               // params → 배열 생성
}
이 다섯 개만 잡아도 프레임 튐의 대부분이 사라집니다. Unity 라면 Profiler 의 GC Alloc 열을 켜고 0 B 가 아닌 줄을 위에서부터 지워 나가세요.

고치는 법

// ① 값이 바뀔 때만 갱신 + 캐시
private int _shownHp = -1;
void Update()
{
    if (_shownHp == hp) return;
    _shownHp = hp;
    label.SetText("HP {0}", hp);      // TMP 의 할당 없는 API
}

// ② 재사용 버퍼
private readonly List<Collider> _hits = new(32);
_hits.Clear();
Physics.OverlapSphereNonAlloc(pos, r, _buffer);   // NonAlloc 계열

// ③ 구조체 + 정적 람다
list.ForEach(static x => x.Reset());   // 캡처 없음을 컴파일러가 보장

// ④ 오브젝트 풀
var bullet = _pool.Rent();
_pool.Return(bullet);
서버에서는 관점이 다릅니다. 게임 클라이언트는 순간 멈춤(프레임 튐)이 문제고, 서버는 처리량과 p99 지연이 문제입니다. 서버 GC(<ServerGarbageCollection>true</>)를 켜는 것만으로 처리량이 크게 오르는 경우가 많습니다(🔬 전문가 탭).

public static class CommandRegistry
{
    private static readonly FrozenDictionary<string, Action<string[]>> Map =
        BuildMap();

    private static FrozenDictionary<string, Action<string[]>> BuildMap()
    {
        var d = new Dictionary<string, Action<string[]>>(StringComparer.OrdinalIgnoreCase);
        foreach (var m in typeof(Commands).GetMethods(
                     BindingFlags.Public | BindingFlags.Static))
        {
            if (m.GetCustomAttribute<CommandAttribute>() is not { } attr) continue;
            // ★ 델리게이트로 만들어 두면 이후 호출은 리플렉션이 아닙니다
            var fn = m.CreateDelegate<Action<string[]>>();
            d[attr.Name] = fn;
        }
        return d.ToFrozenDictionary();     // .NET 8+ — 읽기 전용에 최적화
    }

    public static bool TryRun(string name, string[] args)
    {
        if (!Map.TryGetValue(name, out var fn)) return false;
        fn(args);                          // 일반 델리게이트 호출 속도
        return true;
    }
}

지켜야 할 것

  • 구조체 레이아웃을 [StructLayout(LayoutKind.Sequential)] 로 고정

  • 플랫폼별 바이너리(.dll·.so·.dylib)를 전부 배포해야 합니다
Unity 에서는 더 조심해야 합니다. 네이티브 플러그인은 에디터에서 한 번 로드되면 안 내려갑니다 — DLL 을 교체하려면 에디터를 재시작해야 하고, 플러그인이 죽으면 에디터가 통째로 죽습니다.

타임아웃 — ReDoS 를 막는 한 줄

ADV 15

암호화 · 해시 실전

직접 발명하지 않는 것이 제 1 원칙입니다. 표준 라이브러리의 검증된 조합을 올바른 자리에 꽂는 법만 다룹니다.

해시(SHA-256) · HMAC 서명

using System.Security.Cryptography;
using System.Text;

// 해시 — 내용의 지문. 파일 무결성·중복 검사·캐시 키
byte[] hash = SHA256.HashData(File.ReadAllBytes(path));   // static 한 줄
string hex  = Convert.ToHexString(hash);                  // "A3F2…"

// 대용량 파일은 스트림으로
await using var fs = File.OpenRead(path);
var h2 = await SHA256.HashDataAsync(fs, ct);

// HMAC — "비밀 키를 아는 쪽이 만들었다"는 서명.
// 웹훅 검증·클라이언트 요청 위조 방지의 표준입니다
static bool VerifyWebhook(string body, string signatureHex, byte[] secret)
{
    var expected = HMACSHA256.HashData(secret, Encoding.UTF8.GetBytes(body));
    var actual   = Convert.FromHexString(signatureHex);
    // ★ 일반 비교(SequenceEqual)는 틀린 위치에서 일찍 끝나
    //   시간 차이로 서명이 새는 타이밍 공격에 노출됩니다
    return CryptographicOperations.FixedTimeEquals(expected, actual);
}

// 게임 예: 결제 영수증·랭킹 제출에 서버 발급 HMAC 를 붙여
// 클라이언트가 값을 조작했는지 서버에서 검증합니다
해시는 비밀이 아니라 지문입니다. 같은 입력은 언제나 같은 해시가 나오므로 숨기는 용도가 아니고, HMAC 는 해시에 비밀 키를 섞어 "누가 만들었나"를 보증합니다. 비밀번호 저장은 둘 다 아닙니다 — 오른쪽에서 따로 다룹니다.

// 암호화 + 변조 감지를 한 번에 하는 인증 암호화(AEAD)
public static byte[] Encrypt(byte[] plain, byte[] key)
{
    var nonce = RandomNumberGenerator.GetBytes(AesGcm.NonceByteSizes.MaxSize);
    var cipher = new byte[plain.Length];
    var tag    = new byte[AesGcm.TagByteSizes.MaxSize];

    using var aes = new AesGcm(key, tag.Length);
    aes.Encrypt(nonce, plain, cipher, tag);

    // nonce ‖ tag ‖ cipher 를 붙여 저장 — 셋 다 비밀이 아닙니다
    return [.. nonce, .. tag, .. cipher];
}

public static byte[] Decrypt(byte[] blob, byte[] key)
{
    var nonce  = blob.AsSpan(0, 12);
    var tag    = blob.AsSpan(12, 16);
    var cipher = blob.AsSpan(28);
    var plain  = new byte[cipher.Length];
    using var aes = new AesGcm(key, tag.Length);
    aes.Decrypt(nonce, cipher, tag, plain);   // 변조됐으면 여기서 예외
    return plain;
}
키는 코드·리포지토리에 두지 않습니다. 환경 변수·Secret Manager·클라우드 Key Vault 에서 읽어 오세요. 그리고 nonce 를 같은 키로 재사용하면 GCM 보안이 통째로 무너집니다 — 위처럼 암호화할 때마다 새로 뽑는 것이 규칙입니다. 클라이언트 배포 파일 안의 키는 이미 공개된 키라는 점도 기억하세요.

비밀번호 — 해시가 아니라 KDF

// 비밀번호는 "느리게" 해시해야 합니다 — 무차별 대입을 비싸게
// SHA256 은 초당 수십억 번 계산되므로 자격이 없습니다

// 표준 라이브러리만으로: PBKDF2
const int Iterations = 600_000;              // OWASP 권고 수준
public static (byte[] Salt, byte[] Hash) HashPassword(string pw)
{
    var salt = RandomNumberGenerator.GetBytes(16);   // 사용자마다 다르게
    var hash = Rfc2898DeriveBytes.Pbkdf2(
        pw, salt, Iterations, HashAlgorithmName.SHA256, outputLength: 32);
    return (salt, hash);
}

public static bool Verify(string pw, byte[] salt, byte[] stored)
{
    var hash = Rfc2898DeriveBytes.Pbkdf2(
        pw, salt, Iterations, HashAlgorithmName.SHA256, 32);
    return CryptographicOperations.FixedTimeEquals(hash, stored);
}
