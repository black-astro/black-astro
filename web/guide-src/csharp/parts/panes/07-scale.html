SCALE 01

규모의 감각 잡기

"동시접속 10만"이 실제로 초당 몇 요청이고 서버 몇 대인지 계산해 봅니다.

숫자로 환산하기

동시접속(CCU) 10,000 인 모바일 RPG 가정

일반 API (로비·상점·인벤토리)
  사용자당 분당 6요청 → 10,000 × 6 / 60 = 1,000 RPS
  한 요청 20ms → 서버 1대(4코어)가 대략 500~1,000 RPS
  → 앱 서버 2~4대 + 여유

실시간 전투 (20Hz 동기화)
  방당 4명 · 초당 20틱 · 인당 200B
  4 × 20 × 200 = 16 KB/s per room
  방 2,500개(1만 명) → 40 MB/s = 320 Mbps ★ 대역폭이 먼저 한계

DB
  쓰기 초당 200건 · 읽기 800건
  → 읽기는 캐시로 90% 흡수, 쓰기는 단일 인스턴스로도 가능
병목은 대개 순서가 정해져 있습니다. ① DB 커넥션 → ② 캐시 없는 반복 조회 → ③ 대역폭 → ④ CPU. 먼저 무너질 곳부터 대비하세요.

먼저 정할 것

  • 목표 지표(SLO) — 예: "API p99 200ms · 가용성 99.5%"
  • 예상 CCU 의 3배로 부하 테스트 — 오픈 첫날은 항상 예상을 넘습니다
  • 비용 한도 — 무한 확장은 가능하지만 돈이 듭니다
  • 줄일 수 있는 기능 — 부하가 폭주하면 무엇을 끌 것인가(랭킹·상세 통계)
"일단 만들고 나중에 확장"은 절반만 맞습니다. 무상태(stateless)·멱등성·수평 확장 가능한 세션 — 이 셋은 처음부터 지켜야 합니다. 나중에 바꾸려면 사실상 다시 만들게 됩니다.
증설이 듣지 않는다면 병목을 잘못 짚은 것입니다 — 대수를 늘리기 전에 무엇이 먼저 마르는지부터 재세요.

직접 계산해 보기 — 우리 서비스의 숫자

[1] RPS 구하기
    RPS = CCU × (사용자당 분당 요청 수) / 60
    예) CCU 30,000 · 분당 6요청 → 3,000 RPS

[2] 서버 대수
    한 대가 감당하는 RPS ≈ 코어수 × 1000 / 평균응답ms
    예) 4코어 · 평균 20ms → 4 × 1000 / 20 = 200... 이 아니라
        비동기 IO 라 실제로는 500~1,500 RPS (CPU 를 안 씀)
    ※ 반드시 부하 테스트로 실측하세요. 계산은 자릿수 확인용입니다.
    3,000 RPS ÷ 800 = 4대 → 여유 포함 6대

[3] DB 커넥션
    필요 커넥션 = 앱 대수 × 풀 크기
    6대 × 20 = 120 개 → Postgres max_connections 확인
    ※ 풀 크기는 (코어수 × 2 + 디스크수) 정도가 출발점.
       크게 잡을수록 좋은 것이 절대 아닙니다.

[4] 대역폭 (실시간이면 여기가 먼저)
    초당 바이트 = 인원 × 틱레이트 × 패킷크기
    30,000 × 20 × 200B = 120 MB/s = 960 Mbps
    → 1Gbps 회선을 이미 넘습니다. 패킷을 줄이거나 서버를 나눠야 합니다.

[5] 저장 용량
    일일 로그 = RPS × 86,400 × 로그당 바이트
    3,000 × 86,400 × 500B ≈ 130 GB/일 → 보관 14일이면 1.8TB
    ※ 로그 비용이 서버 비용을 넘는 경우가 실제로 흔합니다.
계산 결과는 자릿수 확인용입니다. "5대냐 6대냐"를 계산으로 정하려 하지 마세요 — "5대냐 50대냐"를 틀리지 않는 것이 이 계산의 목적입니다. 정확한 수는 부하 테스트로만 나옵니다.

// 여러 서버 중 하나만 실행해야 할 때 (일일 정산 · 스케줄)
public async Task<bool> TryRunOnceAsync(string key, TimeSpan ttl, Func<Task> work)
{
    var token = Guid.NewGuid().ToString();
    if (!await db.StringSetAsync(key, token, ttl, When.NotExists))
        return false;                     // 다른 서버가 잡았다

    try { await work(); return true; }
    finally
    {
        // ★ 내가 잡은 락만 푼다 (TTL 만료 후 남의 락을 푸는 사고 방지)
        const string lua = @"
            if redis.call('get', KEYS[1]) == ARGV[1]
            then return redis.call('del', KEYS[1]) else return 0 end";
        await db.ScriptEvaluateAsync(lua, [key], [token]);
    }
}
락 TTL 보다 작업이 오래 걸리면 두 대가 동시에 돕니다. TTL 을 넉넉히 잡고, 작업 자체를 멱등하게 만들어 두 번 실행돼도 결과가 같게 설계하세요 — 이것이 더 근본적인 해법입니다.
Redis 도 단일 장애점입니다. 세션을 Redis 에만 두면 Redis 가 죽을 때 전원 로그아웃됩니다. 영속화 설정·복제·클러스터를 검토하고, 죽었을 때 어떻게 동작할지를 정해 두세요.
SCALE 04

캐시 전략 · 스탬피드

캐시는 없앨 때가 어렵습니다. 그리고 만료되는 순간이 가장 위험합니다.

캐시 스탬피드

인기 있는 키가 만료되는 순간, 그 키를 기다리던 수천 요청이 동시에 DB 로 몰립니다. 평소에는 캐시가 막아 주던 부하가 한꺼번에 터지는 것입니다. 
// ① 하나만 계산하게 만든다 (나머지는 기다렸다 결과를 공유)
private static readonly SemaphoreSlim _gate = new(1, 1);

async Task<T> GetAsync<T>(string key, Func<Task<T>> load, TimeSpan ttl)
{
    if (_cache.TryGetValue(key, out T? hit)) return hit!;

    await _gate.WaitAsync();
    try
    {
        if (_cache.TryGetValue(key, out hit)) return hit!;   // 이중 확인
        var v = await load();
        // ② 만료 시각을 흩뿌린다 (한꺼번에 만료되지 않게)
        var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
        _cache.Set(key, v, ttl + jitter);
        return v;
    }
    finally { _gate.Release(); }
}

무효화 전략

방식설명주의
TTL시간이 지나면 자동 삭제가장 단순 · 잠깐 옛 값
쓰기 시 삭제변경하면 키를 지움지울 키를 빠뜨리기 쉬움
버전 키shop:v12 처럼 번호를 올림옛 키는 TTL 로 정리
핫키 문제 — 랭킹 1페이지처럼 모두가 보는 키는 Redis 노드 하나에 부하가 몰립니다. 앱 메모리에 1초짜리 로컬 캐시를 한 겹 더 두면 Redis 호출이 수천 분의 일로 줄어듭니다.
재화·인벤토리는 캐시하지 마세요. "골드가 잘못 보인다"는 신뢰를 잃는 버그입니다. 읽기 성능이 필요하면 캐시 대신 읽기 전용 복제본을 쓰세요.

이 순서대로 시도하세요 — 위로 갈수록 싸고 효과가 큽니다

순서수단효과드는 노력언제 한계
1인덱스 · N+1 제거수십 배수 시간거의 항상 여기서 큰 몫이 나옵니다
2캐시(Redis)읽기 90% 흡수1~2일무효화 설계가 어려워질 때
3커넥션 풀러(PgBouncer)커넥션 한계 해소반나절—
4인스턴스 스케일업2~4배재시작 한 번가장 큰 인스턴스에 닿을 때
5읽기 복제본읽기 부하 분산2~3일쓰기가 병목일 때
6아카이빙(옛 데이터 분리)인덱스·백업이 빨라짐1주—
7기능별 DB 분리쓰기 분산2~4주한 기능이 여전히 넘칠 때
8샤딩사실상 무한수개월 · 설계 변경—
1번을 건너뛰고 8번을 하는 팀이 실제로 있습니다. 인덱스 하나로 끝날 문제를 샤딩으로 해결하려다 서비스를 다시 쓰게 됩니다. "DB 가 느리다" 는 진단이 아닙니다 — 느린 쿼리 로그를 켜고 상위 10개를 보는 것이 진단입니다. 거기서 대부분 답이 나옵니다.

// 발행 워커 — SKIP LOCKED 로 여러 워커가 안전하게 나눠 처리
public class OutboxPublisher(IServiceScopeFactory f, ILogger<OutboxPublisher> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(1));
        while (await timer.WaitForNextTickAsync(ct))
        {
            try
            {
                using var scope = f.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<GameDb>();

                var batch = await db.Database.SqlQuery<OutboxRow>($"""
                    SELECT * FROM outbox
                     WHERE processed_at IS NULL AND next_try_at <= now()
                     ORDER BY id
                     LIMIT 100
                     FOR UPDATE SKIP LOCKED
                    """).ToListAsync(ct);

                foreach (var m in batch)
                {
                    try
                    {
                        await _bus.PublishAsync(m.Type, m.Payload, ct);
                        await db.Database.ExecuteSqlAsync(
                            $"UPDATE outbox SET processed_at = now() WHERE id = {m.Id}", ct);
                    }
                    catch (Exception ex)
                    {
                        // 지수 백오프로 다시 시도 — 8회 넘으면 사람이 봐야 합니다
                        var delay = TimeSpan.FromSeconds(Math.Pow(2, m.Attempts));
                        await db.Database.ExecuteSqlAsync($"""
                            UPDATE outbox
                               SET attempts = attempts + 1,
                                   next_try_at = now() + {delay}
                             WHERE id = {m.Id}
                            """, ct);
                        if (m.Attempts >= 8)
                            log.LogError(ex, "outbox 배달 실패 {Id} {Type}", m.Id, m.Type);
                    }
                }
            }
            catch (Exception ex) { log.LogError(ex, "outbox 루프 오류"); }
        }
    }
}
FOR UPDATE SKIP LOCKED 가 이 패턴의 핵심입니다 — 워커를 여러 대 띄워도 같은 행을 두 번 집지 않고, 느린 행 때문에 다른 워커가 막히지도 않습니다. 처리 끝난 행은 주기적으로 지우거나 파티션을 잘라 내세요 — 안 그러면 이 테이블이 DB 에서 가장 커집니다.
