출시 첫날 동시접속이 예상의 10배로 오면 서버는 반드시 무너집니다. 어디가 먼저 무너지는지, 그때 무엇을 늘려야 하는지를 미리 알아 둡니다. 여기까지 마치면 수만 동시접속을 견디는 구조를 설계하고 장애를 침착하게 처리할 수 있습니다.

SCALE 01

규모의 감각 잡기

"동시접속 10만"이 실제로 초당 몇 요청이고 서버 몇 대인지 계산해 봅니다.

숫자로 환산하기

동시접속(CCU) 10,000 인 모바일 RPG 가정

일반 API (로비·상점·인벤토리)
  사용자당 분당 6요청 → 10,000 × 6 / 60 = 1,000 RPS
  한 요청 20ms → 서버 1대(4코어)가 대략 500~1,000 RPS
  → 앱 서버 2~4대 + 여유

실시간 전투 (20Hz 동기화)
  방당 4명 · 초당 20틱 · 인당 200B
  4 × 20 × 200 = 16 KB/s per room
  방 2,500개(1만 명) → 40 MB/s = 320 Mbps ★ 대역폭이 먼저 한계

DB
  쓰기 초당 200건 · 읽기 800건
  → 읽기는 캐시로 90% 흡수, 쓰기는 단일 인스턴스로도 가능
병목은 대개 순서가 정해져 있습니다. ① DB 커넥션 → ② 캐시 없는 반복 조회 → ③ 대역폭 → ④ CPU. 먼저 무너질 곳부터 대비하세요.

먼저 정할 것

  • 목표 지표(SLO) — 예: "API p99 200ms · 가용성 99.5%"
  • 예상 CCU 의 3배로 부하 테스트 — 오픈 첫날은 항상 예상을 넘습니다
  • 비용 한도 — 무한 확장은 가능하지만 돈이 듭니다
  • 줄일 수 있는 기능 — 부하가 폭주하면 무엇을 끌 것인가(랭킹·상세 통계)
"일단 만들고 나중에 확장"은 절반만 맞습니다. 무상태(stateless)·멱등성·수평 확장 가능한 세션 — 이 셋은 처음부터 지켜야 합니다. 나중에 바꾸려면 사실상 다시 만들게 됩니다.
SCALE 02

수평 확장 — 서버를 늘릴 수 있는 상태

한 대를 키우는 것(수직)에는 한계가 있습니다. 여러 대로 나누려면 조건이 있습니다.

앱 서버는 얼마든지 늘릴 수 있지만, 상태를 들고 있으면 그 순간 못 늘립니다.

무상태로 만들기

메모리에 상태

// A 서버에 로그인 → B 서버로 요청
// → "로그인이 풀렸어요"
바깥에 상태

  • 업로드 파일은 오브젝트 스토리지로(로컬 디스크 금지)
  • 스케줄 작업은 한 대만 실행되게 락으로 보호
  • 메모리 캐시는 써도 되지만 서버마다 다를 수 있음을 전제로

게임 서버는 사정이 다릅니다

실시간 게임 서버는 무상태가 될 수 없습니다. 방의 상태를 메모리에 들고 20Hz 로 돌려야 하기 때문입니다. 대신 "방 단위로 나누는" 방식으로 확장합니다.
  • 방 배정 서버(매치메이커)가 어느 게임 서버로 갈지 정합니다
  • 게임 서버는 자기 방만 책임집니다 — 서로 통신하지 않습니다
  • 서버가 죽으면 그 방만 영향받습니다(스냅샷으로 복구)
  • 방 수요에 따라 인스턴스를 늘렸다 줄입니다(Agones 등)
// 매치메이커가 여유 있는 서버를 골라 배정
var node = _nodes.Where(n => n.Rooms < n.Capacity)
                 .OrderBy(n => n.Rooms)
                 .FirstOrDefault()
           ?? await ScaleOutAsync();          // 없으면 새 인스턴스 요청
return new MatchResult(node.Host, node.Port, roomToken);

분산 락

// 여러 서버 중 하나만 실행해야 할 때 (일일 정산 · 스케줄)
public async Task<bool> TryRunOnceAsync(string key, TimeSpan ttl, Func<Task> work)
{
    var token = Guid.NewGuid().ToString();
    if (!await db.StringSetAsync(key, token, ttl, When.NotExists))
        return false;                     // 다른 서버가 잡았다

    try { await work(); return true; }
    finally
    {
        // ★ 내가 잡은 락만 푼다 (TTL 만료 후 남의 락을 푸는 사고 방지)
        const string lua = @"
            if redis.call('get', KEYS[1]) == ARGV[1]
            then return redis.call('del', KEYS[1]) else return 0 end";
        await db.ScriptEvaluateAsync(lua, [key], [token]);
    }
}
락 TTL 보다 작업이 오래 걸리면 두 대가 동시에 돕니다. TTL 을 넉넉히 잡고, 작업 자체를 멱등하게 만들어 두 번 실행돼도 결과가 같게 설계하세요 — 이것이 더 근본적인 해법입니다.
Redis 도 단일 장애점입니다. 세션을 Redis 에만 두면 Redis 가 죽을 때 전원 로그아웃됩니다. 영속화 설정·복제·클러스터를 검토하고, 죽었을 때 어떻게 동작할지를 정해 두세요.
SCALE 04

캐시 전략 · 스탬피드

캐시는 없앨 때가 어렵습니다. 그리고 만료되는 순간이 가장 위험합니다.

캐시 스탬피드

인기 있는 키가 만료되는 순간, 그 키를 기다리던 수천 요청이 동시에 DB 로 몰립니다. 평소에는 캐시가 막아 주던 부하가 한꺼번에 터지는 것입니다. 
// ① 하나만 계산하게 만든다 (나머지는 기다렸다 결과를 공유)
private static readonly SemaphoreSlim _gate = new(1, 1);

async Task<T> GetAsync<T>(string key, Func<Task<T>> load, TimeSpan ttl)
{
    if (_cache.TryGetValue(key, out T? hit)) return hit!;

    await _gate.WaitAsync();
    try
    {
        if (_cache.TryGetValue(key, out hit)) return hit!;   // 이중 확인
        var v = await load();
        // ② 만료 시각을 흩뿌린다 (한꺼번에 만료되지 않게)
        var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
        _cache.Set(key, v, ttl + jitter);
        return v;
    }
    finally { _gate.Release(); }
}

무효화 전략

방식설명주의
TTL시간이 지나면 자동 삭제가장 단순 · 잠깐 옛 값
쓰기 시 삭제변경하면 키를 지움지울 키를 빠뜨리기 쉬움
버전 키shop:v12 처럼 번호를 올림옛 키는 TTL 로 정리
핫키 문제 — 랭킹 1페이지처럼 모두가 보는 키는 Redis 노드 하나에 부하가 몰립니다. 앱 메모리에 1초짜리 로컬 캐시를 한 겹 더 두면 Redis 호출이 수천 분의 일로 줄어듭니다.
재화·인벤토리는 캐시하지 마세요. "골드가 잘못 보인다"는 신뢰를 잃는 버그입니다. 읽기 성능이 필요하면 캐시 대신 읽기 전용 복제본을 쓰세요.

② 샤딩 — 마지막 수단

// 플레이어 id 로 DB 를 나눈다

요청 안에서 다 하려고 하면 느려집니다. 급하지 않은 일은 미룹니다.

소비자 쪽 규칙

  • 같은 메시지를 두 번 받을 수 있습니다 — 처리를 멱등하게 (처리한 id 기록)
  • 순서 보장은 파티션 안에서만 — 플레이어 id 로 파티션을 나누세요
  • 실패 메시지는 DLQ(죽은 편지 큐)로 — 무한 재시도로 큐를 막지 않게
  • 소비 지연을 모니터링 — 밀리기 시작하면 소비자를 늘립니다
규모에 맞게 고르세요. 작으면 DB 테이블 큐로도 충분하고, 중간 규모는 Redis Stream·RabbitMQ, 초당 수만 건이면 Kafka. 처음부터 Kafka 를 도입하면 운영 부담이 이득보다 큽니다.
SCALE 07

부하 제어 — 거절도 전략입니다

전부 받아 주다 전부 느려지는 것보다, 일부를 빨리 돌려보내는 편이 낫습니다.

속도 제한

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    o.AddPolicy("per-user", ctx =>
        RateLimitPartition.GetTokenBucketLimiter(
            ctx.User.Identity?.Name ?? ctx.Connection.RemoteIpAddress!.ToString(),
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 20,               // 순간 버스트 허용
                TokensPerPeriod = 10,          // 초당 10개 회복
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                QueueLimit = 0,                // 대기 없이 즉시 거절
            }));
});

app.MapPost("/shop/buy", BuyAsync).RequireRateLimiting("per-user");
429 응답에는 Retry-After 를 넣으세요. 클라이언트가 언제 다시 시도할지 알 수 있어야 재시도 폭풍이 생기지 않습니다.

대기열 · 점진 오픈

  • 대기열 — 오픈 첫날 접속을 순서대로 받습니다. "몇 번째, 예상 몇 분"을 보여 주는 것이 중요합니다
  • 기능 차단 — 부하가 높으면 랭킹·통계 같은 부가 기능부터 끕니다
  • 서킷 브레이커 — 외부 API 가 죽으면 빠르게 실패시키고 폴백
  • 재시도 지터 — 클라이언트가 동시에 재접속하지 않게
// Polly — 서킷 브레이커 + 타임아웃
builder.Services.AddHttpClient<IPayApi, PayApi>()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 2;
        o.CircuitBreaker.FailureRatio = 0.5;
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(3);
    });
재시도는 장애를 키웁니다. 서버가 느려서 실패하는데 3번씩 재시도하면 부하가 3배가 되어 회복을 막습니다. 서킷 브레이커와 반드시 함께 쓰세요.
SCALE 08

게임 서버 스케일링 — 방 단위로

웹 서버와 달리 연결이 오래 유지되고 상태가 있습니다. 그래서 방식이 다릅니다.

인스턴스 관리

// 게임 서버가 자기 상태를 주기적으로 보고
public sealed class NodeReporter(IRedis redis) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await redis.Db.HashSetAsync($"node:{NodeId}",
            [
                new("rooms", RoomManager.Count),
                new("cpu",   Cpu.Percent()),
                new("state", _draining ? "draining" : "ready"),
            ]);
            await redis.Db.KeyExpireAsync($"node:{NodeId}", TimeSpan.FromSeconds(15));
            await Task.Delay(5000, ct);
        }
    }
}
  • TTL 로 죽은 노드를 자동 제거 — 보고가 끊기면 목록에서 사라집니다
  • draining 상태 — 새 방은 안 받고 기존 방이 끝나면 종료
  • 여유분을 미리 — 새 인스턴스가 뜨는 데 30초~2분이 걸립니다

축소가 더 어렵습니다

사람이 붙어 있는 서버를 끌 수 없습니다. 웹은 요청이 끝나면 그만이지만, 게임은 30분짜리 판이 돌고 있습니다. 축소는 항상 draining → 자연 종료 순서여야 합니다.
  • 축소는 천천히 — 트래픽이 줄어도 여유를 두고 줄이세요
  • 방 이전(마이그레이션)은 매우 어렵습니다. 대개 하지 않습니다
  • 점검 공지 — 예정된 종료는 게임 안에서 미리 알립니다
  • 스팟 인스턴스는 게임 서버에 위험합니다(갑자기 회수)
Agones · Unity Game Server Hosting 같은 전용 오케스트레이터는 위 과정(할당·드레인·스케일)을 표준화해 줍니다. 직접 만들기 전에 검토할 가치가 있습니다.

DB 스키마 변경은 두 단계로 나누세요. ① 컬럼 추가(구버전도 동작) → 배포 → ② 다음 배포에서 옛 컬럼 제거. 한 번에 바꾸면 배포 중 두 버전이 공존하는 순간 터집니다.

점검을 해야 한다면

  • 사전 공지 — 게임 내 배너 + 커뮤니티. 최소 하루 전
  • 점검 모드 스위치 — 새 접속 차단, 진행 중인 판은 마무리
  • 롤백 계획 — 언제까지 안 되면 되돌린다를 미리 정하세요
  • 점검 후 보상 — 우편 일괄 지급 도구를 준비
  • 재접속 폭주 대비 — 점검이 끝나면 전원이 동시에 붙습니다
점검 종료 시각을 정확히 지키세요. 연장은 신뢰를 크게 깎습니다. 예상보다 넉넉히 잡고 일찍 끝내는 것이 항상 낫습니다.

SCALE 12

비용 · 글로벌 서비스

기술적으로 가능한 것과 지속 가능한 것은 다릅니다.

비용이 새는 곳

  • 대역폭 — 게임 서버에서 가장 큰 비용. 패킷 크기가 곧 요금입니다
  • 과도한 인스턴스 — 새벽에도 최대치로 켜 두는 경우
  • 로그·메트릭 보관 — 전부 무기한 보관하면 저장 비용이 서버를 넘습니다
  • 리전 간 전송 — 같은 리전 안에서 처리하도록 배치
  • 안 쓰는 리소스 — 테스트용 인스턴스·스냅샷이 남아 있습니다
패킷 20% 줄이기 = 대역폭 비용 20% 절감입니다. AOI·델타 압축·전송 주기 조정은 성능 개선이자 비용 절감입니다 (🌐 게임 서버 탭 04).

글로벌 서비스

  • 지연은 물리 법칙 — 서울↔미국 서부 왕복 130ms 는 줄일 수 없습니다. 실시간 대전이면 지역별 서버가 유일한 답입니다
  • 계정은 글로벌, 전투는 지역 으로 나누는 구조가 일반적입니다
  • 시간대·명절 — 이벤트 시각을 UTC 로 저장하고 표시할 때 변환
  • 법규 — 개인정보 이전·연령 등급·확률 공시는 국가마다 다릅니다
