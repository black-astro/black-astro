게임 서버의 어려움은 성능이 아니라 "모두가 같은 것을 보게 만드는 일" 입니다. 지연은 반드시 있고, 패킷은 사라지며, 누군가는 반드시 조작을 시도합니다. 여기까지 마치면 실시간 대전이 가능한 서버를 설계하고 치트를 막을 수 있습니다.

구조 총정리 — 무엇을 만들 것인가

장르에 따라 필요한 서버가 완전히 다릅니다. 여기서 잘못 고르면 전부 다시 만들게 됩니다.

세 가지 구조

P2P
플레이어끼리 직접 연결 서버 비용 0. 하지만 방장이 나가면 끝이고 치트를 막을 수 없습니다. 협동 게임·파티 게임 정도.

SERVER 02

TCP · UDP · 신뢰성 UDP

실시간 게임이 UDP 를 쓰는 이유는 속도가 아니라 "기다리지 않기 위해서" 입니다.

위치 정보는 0.05초 전 좌표를 굳이 다시 받을 이유가 없습니다. 그래서 UDP 입니다.

무엇을 어디로 보낼 것인가

데이터전송이유
이동 좌표 · 회전UDP 비신뢰다음 것이 곧 온다
발사 · 스킬 사용UDP 신뢰빠뜨리면 안 됨
채팅 · 아이템 획득TCP 또는 신뢰 UDP순서·보장 필요
로그인 · 결제TCP(HTTPS)정확성 최우선
실무에서는 둘을 함께 씁니다. 로그인·상점·인벤토리는 HTTP API(TCP), 전투 중 실시간 동기화만 UDP. 하나로 통일하려다 둘 다 어중간해지는 경우가 많습니다.

신뢰성 UDP 의 최소 구성

// 헤더에 번호와 확인용 비트를 실어 보낸다 (라이브러리가 해 주는 일)
[StructLayout(LayoutKind.Sequential, Pack = 1)]
struct Header
{
    public ushort Seq;        // 이 패킷의 번호
    public ushort Ack;        // 내가 마지막으로 받은 번호
    public uint   AckBits;    // 그 앞 32개를 받았는지 비트로
    public byte   Channel;    // 0=비신뢰 1=신뢰 2=순서보장
}
  • 재전송 — Ack 가 안 오면 다시 보냅니다(신뢰 채널만)
  • 순서 — 필요할 때만 (전부 순서를 지키면 TCP 와 같아집니다)
  • 조각화 — MTU(약 1200바이트)를 넘으면 나눠 보냅니다
  • 혼잡 제어 — 손실률이 높으면 전송 주기를 낮춥니다
직접 구현하지 마세요. 위 네 가지를 제대로 만드는 데 몇 달이 걸리고 미묘한 버그가 남습니다. LiteNetLib·ENet·Netcode 의 UnityTransport 같은 검증된 라이브러리를 쓰고, 이 구조를 이해한 상태로 튜닝하는 것이 목표입니다.

소켓 서버 — .NET 으로 직접

수천 명을 한 프로세스에서 받는 서버의 뼈대. 할당 없는 수신 루프가 핵심입니다.

TCP 수신 루프

var listener = new TcpListener(IPAddress.Any, 7777);
listener.Start(backlog: 512);

while (!ct.IsCancellationRequested)
{
    var client = await listener.AcceptTcpClientAsync(ct);
    client.NoDelay = true;                 // ★ Nagle 끄기 (지연 40ms 제거)
    _ = HandleAsync(client, ct);           // 세션마다 독립 처리
}

static async Task HandleAsync(TcpClient c, CancellationToken ct)
{
    var buf = ArrayPool<byte>.Shared.Rent(16 * 1024);
    try
    {
        var stream = c.GetStream();
        var filled = 0;
        while (true)
        {
            var n = await stream.ReadAsync(buf.AsMemory(filled), ct);
            if (n == 0) break;             // 연결 종료
            filled += n;

            // ★ TCP 는 '메시지 경계'가 없다 — 길이 헤더로 잘라야 한다
            var offset = 0;
            while (filled - offset >= 4)
            {
                var len = BinaryPrimitives.ReadInt32LittleEndian(
                              buf.AsSpan(offset));
                if (len <= 0 || len > 64 * 1024) throw new InvalidDataException();
                if (filled - offset - 4 < len) break;      // 아직 덜 왔다
                Dispatch(buf.AsSpan(offset + 4, len));
                offset += 4 + len;
            }
            Buffer.BlockCopy(buf, offset, buf, 0, filled - offset);
            filled -= offset;
        }
    }
    finally { ArrayPool<byte>.Shared.Return(buf); c.Dispose(); }
}

반드시 챙길 것

  • 메시지 경계 — TCP 는 스트림입니다. 길이 헤더로 직접 자르세요. 이걸 빼먹으면 "가끔 패킷이 깨진다" 가 됩니다
  • 길이 상한 — 헤더의 길이를 그대로 믿고 버퍼를 잡으면 메모리 폭탄 공격에 당합니다
  • NoDelay = true — 안 켜면 작은 패킷이 40ms 씩 지연됩니다
  • 연결 상한 · 유휴 타임아웃 — 접속만 하고 아무것도 안 하는 연결을 끊으세요
  • ArrayPool — 세션마다 버퍼를 새로 잡으면 GC 가 무너집니다
더 높은 성능이 필요하면 System.IO.Pipelines 를 보세요. 버퍼 관리·역압(backpressure)을 대신 해 주어 위 코드의 복잡한 부분이 사라지고 할당도 거의 0 이 됩니다.

패킷 설계 · 직렬화

초당 수만 개가 오갑니다. 1바이트를 줄이는 것이 대역폭 비용으로 돌아옵니다.

패킷 정의

// 공용 프로젝트에 두고 클라이언트·서버가 함께 참조합니다
public enum PacketId : ushort
{
    None = 0,
    C_Move = 1, C_Fire = 2, C_Chat = 3,
    S_Spawn = 100, S_State = 101, S_Hit = 102,
}

[MessagePackObject]
public struct MovePacket
{
    [Key(0)] public uint  Tick;      // ★ 시간 기준 (뒤에서 씁니다)
    [Key(1)] public short X, Y;      // 좌표를 정수로 압축 (cm 단위)
    [Key(2)] public byte  YawDeg;    // 회전은 1바이트로 충분
    [Key(3)] public byte  Flags;     // 점프·달리기 등을 비트로
}
  • float 대신 정수 — 위치를 cm 단위 short 로 담으면 4바이트→2바이트
  • 불리언은 비트로 — 8개를 1바이트에
  • 변하지 않는 값은 보내지 않기 — 처음 한 번만
  • 델타 압축 — 직전과 같으면 생략

SERVER 05

룸 · 세션 · 게임 루프

서버도 게임처럼 일정 주기로 도는 루프가 있습니다. 락을 없애는 구조가 여기서 나옵니다.

룸 하나 = 스레드 하나

public sealed class GameRoom
{
    private readonly Channel<IPacket> _inbox =
        Channel.CreateUnbounded<IPacket>(new() { SingleReader = true });

    public ValueTask PushAsync(IPacket p) => _inbox.Writer.WriteAsync(p);

    public async Task RunAsync(CancellationToken ct)
    {
        var tick = TimeSpan.FromMilliseconds(50);      // 20Hz
        var next = DateTime.UtcNow;

        while (!ct.IsCancellationRequested)
        {
            // ① 들어온 입력을 전부 처리 (이 룸의 데이터는 나만 만진다 → 락 불필요)
            while (_inbox.Reader.TryRead(out var p)) Handle(p);

            // ② 게임 로직 한 틱
            Simulate((float)tick.TotalSeconds);

            // ③ 상태 방송
            Broadcast();

            next += tick;
            var wait = next - DateTime.UtcNow;
            if (wait > TimeSpan.Zero) await Task.Delay(wait, ct);
            else next = DateTime.UtcNow;               // 밀렸으면 따라잡지 않는다
        }
    }
}

이 구조의 장점

  • 락이 사라집니다 — 룸 데이터는 그 루프만 만집니다
  • 재현이 쉽습니다 — 입력 순서가 정해져 있어 버그 재현이 가능합니다
  • 수평 확장이 자연스럽습니다 — 룸을 다른 서버로 옮기면 됩니다
  • 틱 시간을 측정해 룸당 부하를 바로 알 수 있습니다
루프 안에서 DB·HTTP 를 기다리지 마세요. 한 룸의 20Hz 가 무너지고 그 방 전원이 렉을 느낍니다. 저장은 큐에 넣고 다른 곳에서 처리하세요. 
// 저장은 비동기로 흘려보낸다
_saveQueue.Enqueue(new SaveJob(playerId, snapshot));

// 세션 정리 — 끊긴 연결을 방치하면 룸이 안 닫힙니다
if (now - p.LastPacketAt > TimeSpan.FromSeconds(20)) Kick(p, "timeout");
틱 시간 모니터링이 게임 서버의 핵심 지표입니다. 20Hz 라면 한 틱 50ms 안에 끝나야 합니다. 평균이 아니라 최대값을 보세요 — 한 번의 100ms 가 렉으로 체감됩니다.
SERVER 06

권위 서버 — 클라이언트를 믿지 않기

멀티플레이 보안의 전부입니다. 이 원칙 하나로 대부분의 치트가 막힙니다.

무엇을 보내야 하는가

클라이언트가 결과를 보낸다
// "나 (100, 50)으로 이동했어"
Send(new Move { X = 100, Y = 50 });
// "적에게 9999 데미지 줬어"
Send(new Hit { Dmg = 9999 });
// → 메모리 수정 한 번이면 끝
클라이언트는 의도만
// "앞으로 가려고 함"
Send(new Input { Dir = 1, Tick = t });
// "이 방향으로 쐈음"
Send(new Fire { Dir = d, Tick = t });
// → 결과는 서버가 계산
// 서버: 입력을 받아 직접 계산하고 검증한다
void OnInput(Player p, InputPacket input)
{
    // ① 시간 검증 — 미래·과거 입력은 버린다
    if (input.Tick > _tick + 2 || input.Tick < _tick - 20) return;

    // ② 이동은 서버가 계산 (속도 상한 적용)
    var move = Clamp(input.Dir, p.MaxSpeed) * DeltaTime;
    var next = p.Pos + move;

    // ③ 지형 충돌도 서버가 판정
    if (!_map.IsWalkable(next)) return;

    p.Pos = next;
}

검증 항목

  • 이동 속도 — 두 틱 사이 이동 거리가 상한을 넘으면 거부
  • 쿨타임 — 스킬 사용 간격을 서버가 기록
  • 사거리·시야 — 벽 너머의 적을 맞힐 수 없게
  • 데미지 — 공식은 서버에만. 클라이언트는 표시만
  • 인벤토리 — 가진 적 없는 아이템 사용 차단
  • 입력 빈도 — 초당 입력 수 상한 (자동 연사 매크로)
"서버가 계산하면 느려지지 않나요?" 이동·충돌 계산은 생각보다 싸고, 진짜 비용은 네트워크입니다. 그리고 대안이 없습니다 — 경쟁 게임에서 클라이언트를 믿는 순간 핵 하나로 서비스가 무너집니다.
서버 계산의 부작용은 "반응이 굼뜨다" 입니다. 키를 눌러도 서버 응답(왕복 100ms) 뒤에 움직이면 조작감이 나쁩니다. 이를 해결하는 것이 다음 섹션의 클라이언트 예측입니다.
SERVER 07

클라이언트 예측 · 보간 · 지연 보상

서버가 진실을 갖되 조작은 즉각 반응해야 합니다. 상용 슈터가 쓰는 세 가지 기법입니다.

내 캐릭터는 미래를 예측하고, 남의 캐릭터는 과거를 보간합니다.

예측과 재조정

// 클라이언트 — 보낸 입력을 기억해 둔다
private readonly Queue<PendingInput> _pending = new();

void SendInput(InputPacket input)
{
    _pending.Enqueue(new PendingInput(input, _tick));
    ApplyLocally(input);                 // ★ 서버를 기다리지 않고 바로 움직임
    net.Send(input);
}

// 서버 상태가 도착하면
void OnServerState(StatePacket s)
{
    // 서버가 확인해 준 입력까지는 버린다
    while (_pending.Count > 0 && _pending.Peek().Tick <= s.LastProcessedTick)
        _pending.Dequeue();

    if (Vector3.Distance(transform.position, s.Pos) > 0.05f)
    {
        transform.position = s.Pos;                 // 서버 위치로 되돌리고
        foreach (var p in _pending) ApplyLocally(p.Input);   // 남은 입력을 다시 적용
    }
}

보간과 지연 보상

// ① 다른 플레이어 — 받은 상태 두 개 사이를 보간
const float InterpDelay = 0.1f;          // 100ms 뒤처져 그린다

var renderTime = Now - InterpDelay;
var (a, b) = _buffer.Around(renderTime);
transform.position = Vector3.Lerp(a.Pos, b.Pos,
    (renderTime - a.Time) / (b.Time - a.Time));

// ② 지연 보상 — 쏜 시점의 과거로 되돌려 판정 (히트스캔)
bool Hit(Player shooter, Ray ray, uint clientTick)
{
    var rewind = _history.Snapshot(clientTick);       // 그때의 모든 위치
    return rewind.Raycast(ray, out var target);
}
지연 보상에는 대가가 있습니다. "엄폐물 뒤로 숨었는데 맞았다"가 발생합니다. 되돌리는 시간에 상한(예: 200ms)을 두고, 과도한 지연 사용자는 보상 대상에서 제외하는 것이 일반적입니다.
셋 다 필요한 것은 아닙니다. 캐주얼 게임은 보간만 해도 충분하고, 예측·지연 보상은 FPS·격투처럼 반응이 승패를 가르는 장르에서 필요합니다. 복잡도가 크게 올라가므로 필요할 때만 도입하세요.

매치메이킹 · 방 배정

"비슷한 실력끼리, 빠르게" — 두 목표는 서로 충돌합니다.

기본 구조

public sealed class MatchMaker
{
    private readonly List<Ticket> _queue = new();

    public void Enqueue(Ticket t) { lock (_queue) _queue.Add(t); }

    // 주기적으로 돌며 짝을 맞춘다
    public void Tick()
    {
        lock (_queue)
        {
            _queue.Sort((a, b) => a.Rating.CompareTo(b.Rating));

            for (int i = 0; i + 1 < _queue.Count; )
            {
                var (a, b) = (_queue[i], _queue[i + 1]);
                // ★ 기다린 시간만큼 실력 허용 범위를 넓힌다
                var band = 50 + a.WaitSeconds * 20;

                if (Math.Abs(a.Rating - b.Rating) <= band)
                {
                    CreateRoom(a, b);
                    _queue.RemoveRange(i, 2);
                }
                else i++;
            }
        }
    }
}

현실에서 고려할 것

  • 지역(핑) — 실력보다 지연이 경험을 더 망칩니다. 지역별 큐가 기본
  • 대기 시간 상한 — 오래 기다리면 조건을 풀어 주세요. 3분은 이탈입니다
  • 파티 — 인원이 다른 그룹을 섞는 규칙이 필요합니다
  • 재접속 — 끊긴 사람이 돌아올 자리를 남겨 둘지
  • 봇 투입 — 새벽처럼 사람이 적을 때
  • 신규 보호 — 초반 몇 판은 쉬운 상대와
실력 점수는 Elo 보다 Glicko·TrueSkill 이 낫습니다. 불확실성을 함께 다뤄 신규 유저의 점수가 빨리 수렴합니다. 다만 초기에는 단순 Elo 로 시작하고 데이터가 쌓인 뒤 교체해도 늦지 않습니다.
큐 대기 화면에서 이탈이 가장 많이 일어납니다. 예상 대기 시간을 보여 주고, 기다리는 동안 할 것(상점·꾸미기)을 주세요.

SERVER 11

부하 테스트 — 봇으로 미리 겪기

출시 당일에 알게 되면 늦습니다. 봇 1만 개를 붙여 미리 무너뜨려 보세요.

봇 클라이언트

// 실제 프로토콜을 그대로 쓰는 가짜 클라이언트
static async Task RunBotAsync(int id, CancellationToken ct)
{
    using var cli = new GameClient();
    await cli.ConnectAsync(host, port, ct);
    await cli.LoginAsync($"bot{id}", ct);
    await cli.JoinRandomRoomAsync(ct);

    var rnd = new Random(id);
    while (!ct.IsCancellationRequested)
    {
        await cli.SendInputAsync(new Input {
            Dir = rnd.Next(0, 8), Fire = rnd.Next(10) == 0 }, ct);
        await Task.Delay(50, ct);                 // 20Hz
    }
}

// 동시에 띄우기 — 한 프로세스에서 수천 개도 가능합니다
await Parallel.ForEachAsync(Enumerable.Range(0, 5000),
    new ParallelOptions { MaxDegreeOfParallelism = 200 },
    async (i, t) => await RunBotAsync(i, t));

무엇을 볼 것인가

  • 틱 시간 — 20Hz 라면 50ms 를 넘는 순간이 언제부터인지
  • CPU · GC — Gen2 수집이 잦아지면 설계 문제입니다
  • 대역폭 — 인당 KB/s × CCU = 월 트래픽 비용
  • 접속 폭주 — 오픈 직후 동시에 몰리는 상황을 따로 테스트
  • 재접속 폭풍 — 서버를 껐다 켰을 때 전원이 동시에 붙습니다
평균이 아니라 꼬리를 보세요. 평균 틱 20ms 라도 p99 가 200ms 면 100명 중 1명은 매번 렉을 겪습니다. 지표는 p95 · p99 로 관리하세요.
봇은 개발 내내 쓸모가 있습니다. 빈 서버에서 기능을 시험하고, 회귀 테스트로도 씁니다. 일반 API 부하는 k6 로, 게임 프로토콜은 직접 만든 봇이 정답입니다.
