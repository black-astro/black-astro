운영 규칙

  • 레벨 — Error 는 사람이 조치할 것만. 나머지는 Warning 이하
  • 보관 기간을 반드시 설정 — 디스크가 차서 서버가 죽는 사고가 흔합니다
  • 민감정보 금지 — 비밀번호·토큰·카드번호·주민번호
  • 운영에서 Debug 를 켜 두지 마세요 — I/O 가 응답을 느리게 합니다
  • 수집기(Seq·Loki·CloudWatch)로 보내면 검색이 됩니다
로그에 개인정보가 들어가면 삭제가 어렵습니다. 여러 곳에 복제되고 백업에도 남습니다. 애초에 남기지 않는 것이 유일한 방법입니다.

레벨을 고르는 기준 — "누가 언제 보는가"

레벨뜻예운영에서알람
Fatal서비스가 못 뜬다DB 접속 실패로 기동 중단켬즉시 호출
Error사람이 조치해야 함결제 승인 API 가 계속 실패켬비율로 알람
Warning이상하지만 서비스는 됨재시도로 회복 · 캐시 미스 급증켬대시보드만
Information비즈니스 사건구매 · 로그인 · 아이템 지급켬—
Debug개발자 추적용분기 진입 · 중간 값끔—
Verbose전부루프 안 값끔—
Error 를 남발하면 Error 가 의미를 잃습니다. "사용자가 잘못된 비밀번호를 넣었다"는 Information 입니다 — 시스템이 정상 동작한 것이니까요. 내가 새벽 3시에 깨어나 고쳐야 하는가를 기준으로 삼으면 거의 틀리지 않습니다. Error 가 하루 수천 건 찍히는 서비스는, 진짜 사고가 나도 아무도 눈치채지 못합니다.

요청 하나를 끝까지 따라가기 — 상관관계 ID

// 요청마다 TraceId 를 심고, 모든 로그에 자동으로 붙게 합니다
app.Use(async (ctx, next) =>
{
    var traceId = ctx.Request.Headers["X-Trace-Id"].FirstOrDefault()
                  ?? Activity.Current?.TraceId.ToString()
                  ?? Guid.NewGuid().ToString("N");

    ctx.Response.Headers["X-Trace-Id"] = traceId;   // ★ 클라에도 돌려준다

    using (LogContext.PushProperty("TraceId", traceId))
    using (LogContext.PushProperty("PlayerId",
        ctx.User.FindFirst("sub")?.Value ?? "-"))
    {
        await next(ctx);
    }
});

// 요청 요약 한 줄 — 수백 줄의 개별 로그보다 이게 더 유용합니다
builder.Host.UseSerilog((ctx, cfg) => cfg.ReadFrom.Configuration(ctx.Configuration));
app.UseSerilogRequestLogging(o =>
{
    o.MessageTemplate =
        "{RequestMethod} {RequestPath} → {StatusCode} in {Elapsed:0}ms";
    o.GetLevel = (http, elapsed, ex) =>
        ex is not null                      ? LogEventLevel.Error :
        http.Response.StatusCode >= 500     ? LogEventLevel.Error :
        elapsed > 1000                      ? LogEventLevel.Warning :
        http.Request.Path.StartsWithSegments("/health")
                                            ? LogEventLevel.Verbose   // 헬스체크는 묻기
                                            : LogEventLevel.Information;
    o.EnrichDiagnosticContext = (diag, http) =>
    {
        diag.Set("ClientVer", http.Request.Headers["X-Client-Ver"].ToString());
        diag.Set("Ip", http.Connection.RemoteIpAddress?.ToString());
    };
});
사용자가 캡처한 오류 화면에 TraceId 를 띄우세요. "12시쯤 구매가 안 됐어요" 로 로그를 뒤지는 것과 TraceId 로 한 번에 찾는 것은 대응 시간이 열 배 차이 납니다. 헬스체크를 Verbose 로 내리는 것도 중요합니다 — 안 그러면 로그의 90%가 헬스체크가 됩니다.

public sealed record LoginRequest(string Email, string Password)
{
    // ToString 을 막아 실수로 통째로 찍히는 것을 방지
    public override string ToString() => $"LoginRequest({Mask(Email)})";
    private static string Mask(string s) =>
        s.Length <= 3 ? "***" : s[..2] + new string('*', s.Length - 3) + s[^1];
}

// ③ 마지막 안전망 — 나가는 로그에서 패턴을 지웁니다
public class RedactEnricher : ILogEventEnricher
{
    private static readonly Regex Jwt =
        new(@"eyJ[\w-]+\.[\w-]+\.[\w-]+", RegexOptions.Compiled);

    public void Enrich(LogEvent e, ILogEventPropertyFactory f)
    {
        if (e.MessageTemplate.Text.Length > 0 &&
            e.Properties.TryGetValue("Body", out var v) &&
            v is ScalarValue { Value: string s } && Jwt.IsMatch(s))
            e.AddOrUpdateProperty(f.CreateProperty("Body", Jwt.Replace(s, "[jwt]")));
    }
}

복원력 정책

.AddResilienceHandler("pay", b => b
    .AddTimeout(TimeSpan.FromSeconds(3))
    .AddRetry(new HttpRetryStrategyOptions
    {
        MaxRetryAttempts = 2,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,                       // ★ 동시 재시도 방지
        ShouldHandle = args => ValueTask.FromResult(
            args.Outcome.Result?.StatusCode is HttpStatusCode.ServiceUnavailable
              or HttpStatusCode.RequestTimeout),
    })
    .AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5, MinimumThroughput = 20,
        BreakDuration = TimeSpan.FromSeconds(15),
    }));
재시도해서는 안 되는 요청을 구분하세요. 결제 승인처럼 두 번 실행되면 안 되는 것은 멱등 키를 함께 보내거나 재시도를 끄고, 조회로 결과를 확인하는 방식이 안전합니다.
AddStandardResilienceHandler() 는 이 순서를 이미 맞춰 둔 것입니다 — 직접 조립할 때만 순서를 신경 쓰면 됩니다.

재시도해도 되는가 — 판단표

상황재시도이유대신
연결 실패 · DNS · 408 · 429 · 502 · 503 · 504해도 됨서버에 아직 안 닿았거나 일시적—
GET 조회가 타임아웃해도 됨읽기는 몇 번 해도 안전(멱등)—
400 · 401 · 403 · 404 · 422하면 안 됨같은 요청은 몇 번을 보내도 같은 결과즉시 실패로 처리
결제 승인이 타임아웃절대 금지이미 승인됐을 수 있음 → 이중 결제멱등 키 · 조회 API 로 결과 확인
아이템 지급 POST조건부멱등 키가 있으면 안전Idempotency-Key 헤더
500 (서버 내부 오류)조건부부분 처리됐을 수 있음멱등이면 재시도, 아니면 조회 확인

결제처럼 되돌릴 수 없는 호출 — 안전한 패턴

public async Task<PayResult> ConfirmAsync(string orderId, CancellationToken ct)
{
    var key = $"pay:{orderId}";              // 우리가 만든 멱등 키

    try
    {
        // 재시도를 끈 클라이언트로 호출 (한 번만)
        return await _payNoRetry.ConfirmAsync(key,
            new ConfirmReq(orderId, _amount), ct);
    }
    catch (Exception ex) when (ex is TaskCanceledException or HttpRequestException)
    {
        // ★ 여기가 핵심 — 실패한 것이 아니라 "결과를 모르는" 상태입니다
        _log.LogWarning(ex, "결제 응답 미확인 {OrderId} — 조회로 확인합니다", orderId);

        for (var i = 0; i < 5; i++)
        {
            await Task.Delay(TimeSpan.FromSeconds(2 * (i + 1)), ct);
            try
            {
                var actual = await _pay.GetAsync(key, ct);   // 조회는 재시도 안전
                if (actual.Status is "DONE" or "CANCELED") return actual;
            }
            catch (ApiException e) when (e.StatusCode == HttpStatusCode.NotFound)
            {
                return PayResult.NotStarted;   // 서버에 안 닿았음 → 안전하게 실패 처리
            }
        }

        // 끝까지 모르면 사람이 봐야 합니다 — 자동으로 결정하지 마세요
        await _alert.RaiseAsync($"결제 상태 불명 orderId={orderId}");
        return PayResult.Pending;
    }
}
"타임아웃 = 실패"가 아닙니다. 이중 결제 사고의 대부분이 이 오해에서 나옵니다 — 응답을 못 받았을 뿐 저쪽에서는 성공했을 수 있습니다. 되돌릴 수 없는 호출은 재시도가 아니라 조회로 확인하세요.

  • Refit 의 ApiException 에는 응답 본문이 들어 있습니다(Content) — 잡을 때 반드시 로그에 남기세요

목을 너무 많이 쓰면 "통과하는데 안 돌아가는" 테스트가 됩니다. DB 는 진짜로, 외부 결제·메일은 가짜로 가 실무에서 가장 잘 통하는 경계입니다.

파이프라인은 이 순서로 — 싼 검사부터

단계명령걸리는 시간실패하면
1. 포맷dotnet format --verify-no-changes수 초즉시 중단 — 리뷰 시간 낭비 방지
2. 빌드 + 경고dotnet build -warnaserror1~2분중단
3. 단위 테스트dotnet test --filter Category!=Slow1분중단
4. 통합 테스트dotnet test --filter Category=Integration3~5분중단
5. 취약점dotnet list package --vulnerable수 초경고만(막으면 배포가 마비)
6. 이미지 빌드docker build2~3분중단
7. 배포main 브랜치만1~2분자동 롤백
순서의 원칙은 "싸고 자주 실패하는 것을 앞으로" 입니다. 포맷 오류 때문에 10분짜리 통합 테스트를 다 돌리고 나서 실패하면 개발자는 파이프라인을 미워하게 되고, 결국 빨간 CI 를 무시하기 시작합니다. 피드백은 3분 안에 오는 것이 목표입니다.

  • 심볼 포함 — 디버깅 시 소스로 들어갈 수 있습니다
  • 게임이라면 클라이언트·서버 공용 프로토콜이 가장 좋은 후보입니다
Unity 에서 쓸 패키지는 제약이 있습니다. Unity 는 NuGet 을 기본 지원하지 않아 DLL 을 직접 넣거나 NuGetForUnity 를 씁니다. .NET Standard 2.1 을 타깃으로 만들어야 호환됩니다.
