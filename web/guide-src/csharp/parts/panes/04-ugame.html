GAME 01

프로젝트 구조 · 어셈블리 분리

스크립트가 300개를 넘으면 저장할 때마다 20초씩 기다리게 됩니다. 구조가 곧 개발 속도입니다.

Assembly Definition — 컴파일 시간을 줄인다

// Scripts/Gameplay/Gameplay.asmdef
{
  "name": "Game.Gameplay",
  "references": ["Game.Core", "Unity.InputSystem"],
  "autoReferenced": false
}
  • 고친 어셈블리만 다시 컴파일됩니다 — 저장 후 대기 시간이 몇 배 줄어듭니다
  • 의존 방향을 강제할 수 있습니다 (Core 가 UI 를 참조하면 컴파일 에러)
  • 테스트 어셈블리를 따로 두면 빌드에서 자동 제외됩니다
asmdef 를 나눈 뒤 "왜 클래스를 못 찾지"가 나오면 참조(references)를 안 넣은 것입니다. 순환 참조는 불가능하므로, 서로가 필요하면 인터페이스를 Core 에 두고 양쪽이 그것을 보게 만드세요.
"UI 가 전투 코드를 직접 부른다"가 편해 보여도, 화살표가 양방향이 되는 순간 컴파일 시간과 테스트 가능성을 잃습니다.
GAME 02

오브젝트 풀링 — 프레임 튐의 1순위 대책

Instantiate/Destroy 를 반복하면 GC 가 돌고, 그때 화면이 멈칫합니다.

총알·이펙트·적·데미지 텍스트 — 반복해서 나타났다 사라지는 것은 전부 풀 대상입니다.

직접 만들기 (원리)

public class BulletPool : MonoBehaviour
{
    [SerializeField] private Bullet prefab;
    [SerializeField] private int prewarm = 50;

    private readonly Stack<Bullet> _idle = new();

    void Awake()
    {
        for (int i = 0; i < prewarm; i++)     // ★ 로딩 때 미리 만든다
        {
            var b = Instantiate(prefab, transform);
            b.gameObject.SetActive(false);
            _idle.Push(b);
        }
    }

    public Bullet Get(Vector3 pos, Quaternion rot)
    {
        var b = _idle.Count > 0 ? _idle.Pop() : Instantiate(prefab, transform);
        b.transform.SetPositionAndRotation(pos, rot);
        b.gameObject.SetActive(true);
        return b;
    }

    public void Release(Bullet b)
    {
        b.gameObject.SetActive(false);
        b.ResetState();                        // ★ 상태 초기화를 잊지 마세요
        _idle.Push(b);
    }
}

놓치기 쉬운 것

  • 상태 초기화 — 속도·남은 시간·트레일이 남아 있으면 "이상하게 동작하는 총알"이 됩니다
  • 파티클은 Stop(true, ClearBehaviour.Clear) 로 잔상 제거
  • 코루틴은 비활성화되면 멈춥니다 — 재활성화 시 다시 시작해야 합니다
  • 이벤트 구독은 OnEnable/OnDisable 짝으로
  • 최대 개수 상한을 두세요 — 무한히 늘면 그냥 메모리 누수입니다
씬 로딩 때 미리 채워 두는 것(prewarm)이 핵심입니다. 전투 중에 처음 50개를 만들면 바로 그 순간 멈칫합니다. 로딩 화면에서 미리 만들어 두면 사용자는 알아채지 못합니다.
풀이 만능은 아닙니다. 가끔 한 번 나오는 오브젝트까지 풀에 넣으면 메모리만 잡아먹습니다. 기준은 "초당 여러 번 생성되는가" 입니다.

풀 매니저 — 프리팹별 풀을 하나로

public class PoolHub : MonoBehaviour
{
    static readonly Dictionary<GameObject, ObjectPool<GameObject>> s_pools = new();

    public static GameObject Spawn(GameObject prefab, Vector3 pos, Quaternion rot)
    {
        if (!s_pools.TryGetValue(prefab, out var pool))
        {
            pool = new ObjectPool<GameObject>(
                () => { var g = Instantiate(prefab); g.AddComponent<PoolTag>().Origin = prefab; return g; },
                g => g.SetActive(true),
                g => g.SetActive(false),
                Destroy, defaultCapacity: 32, maxSize: 256);
            s_pools[prefab] = pool;
        }
        var go = pool.Get();
        go.transform.SetPositionAndRotation(pos, rot);
        return go;
    }

    public static void Despawn(GameObject go) =>
        s_pools[go.GetComponent<PoolTag>().Origin].Release(go);
}
// 사용처는 Instantiate/Destroy 를 Spawn/Despawn 으로 바꾸기만
이펙트 자동 반납 — 파티클에 Stop Action: Callback 을 걸고 OnParticleSystemStopped 에서 Despawn 하면 수명 관리 코드가 사라집니다.
GAME 03

프로파일링 — 추측 대신 측정

"느린 것 같다"로 고치면 엉뚱한 곳을 만집니다. 어디서 몇 ms 를 먼저 확인하세요.

최적화는 가장 큰 칸부터 줄이는 게임입니다 — 어디가 큰지는 측정 없이 알 수 없습니다.

Profiler 읽는 순서

  • ① 실제 기기에 연결 — 에디터 수치는 참고용일 뿐입니다(Development Build 체크)
  • ② CPU 그래프에서 튀는 구간을 클릭 → Timeline 으로 원인 함수 확인
  • ③ GC Alloc 열을 정렬 — 0 B 가 아닌 것부터 없앱니다
  • ④ Rendering — Batches · SetPass Calls · Tris 를 봅니다
  • ⑤ Memory — 텍스처가 대부분입니다. Memory Profiler 패키지로 상세 분석

GAME 04

그래픽 최적화 — 드로우콜 · 배칭

GPU 가 아니라 "몇 번 그리라고 시켰는가" 가 병목인 경우가 대부분입니다.

드로우콜 최적화의 본질은 GPU 가 아니라 CPU 가 명령을 준비하는 횟수를 줄이는 것입니다.

배칭 — 여러 개를 한 번에

  • Static Batching — 안 움직이는 물체에 Static 체크. 메모리를 쓰지만 효과가 큽니다
  • SRP Batcher — URP 기본. 같은 셰이더면 재질이 달라도 묶입니다
  • GPU Instancing — 같은 메시·재질을 수백 개 (풀·나무·적)
  • 텍스처 아틀라스 — 여러 이미지를 한 장으로 합쳐 재질 수를 줄입니다
배칭을 깨는 것들 — 런타임에 material.color = ... 로 재질을 건드리면 그 오브젝트만 별도 재질(인스턴스)이 되어 배칭에서 빠집니다. 색을 바꾸려면 MaterialPropertyBlock 을 쓰세요. 
private static readonly int ColorId = Shader.PropertyToID("_BaseColor");
private MaterialPropertyBlock _mpb;

void Awake() => _mpb = new MaterialPropertyBlock();

void SetColor(Color c)
{
    _renderer.GetPropertyBlock(_mpb);
    _mpb.SetColor(ColorId, c);
    _renderer.SetPropertyBlock(_mpb);   // 재질 복제 없이 색만 변경
}

그 밖의 큰 것들

  • 실시간 그림자를 줄이세요 — 모바일에서 가장 비쌉니다. 라이트맵 굽기로 대체
  • 라이트는 굽고(Baked), 움직이는 것만 실시간
  • Overdraw — 반투명(파티클·UI)이 겹치면 픽셀을 여러 번 그립니다
  • LOD — 멀리 있는 모델은 저해상도로 교체
  • 오클루전 컬링 — 벽 뒤 물체를 아예 안 그림
  • 텍스처 압축 — Android ASTC, iOS ASTC, PC DXT
모바일에서 가장 효과가 큰 순서 — ① 텍스처 크기·압축 ② 실시간 그림자 제거 ③ 파티클 Overdraw ④ SetPass Calls. 이 넷만 정리해도 발열과 배터리가 눈에 띄게 좋아집니다.
GAME 05

Addressables — 메모리와 다운로드 관리

모든 에셋을 앱에 넣으면 설치 용량이 폭발합니다. 필요할 때 받아서 쓰는 구조로 바꿉니다.

기본 사용

using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

private AsyncOperationHandle<GameObject> _handle;

async void LoadBoss()
{
    _handle = Addressables.LoadAssetAsync<GameObject>("Boss_Dragon");
    var prefab = await _handle.Task;
    Instantiate(prefab);
}

void OnDestroy()
{
    // ★ 반드시 해제 — 안 하면 메모리에 계속 남습니다
    if (_handle.IsValid()) Addressables.Release(_handle);
}

// 인스턴스까지 한 번에 (해제도 함께)
var go = await Addressables.InstantiateAsync("Boss_Dragon").Task;
Addressables.ReleaseInstance(go);

운영 관점

  • 초기 설치 용량을 줄입니다 — 스토어 상한(구글 150MB 등)을 넘기지 않게
  • 콘텐츠만 갱신 가능 — 앱 심사 없이 이벤트 에셋 교체(원격 카탈로그)
  • 중복 제거 — 여러 번들이 같은 텍스처를 물면 메모리가 두 배가 됩니다
  • 다운로드 진행률을 사용자에게 보여 주세요
// 다운로드 크기 확인 후 진행
var size = await Addressables.GetDownloadSizeAsync(label).Task;
if (size > 0)
{
    var dl = Addressables.DownloadDependenciesAsync(label);
    while (!dl.IsDone) { bar.value = dl.PercentComplete; await Task.Yield(); }
    Addressables.Release(dl);
}
해제를 빠뜨리면 조용히 메모리가 찹니다. Addressables 는 참조 카운트로 관리되므로 Load 와 Release 를 짝으로 맞춰야 합니다. Memory Profiler 로 씬 전환 후 남은 번들을 확인하세요.

씬 전환과 메모리 수명

// 스테이지 진입 — 라벨 단위로 미리 받고, 나갈 때 통째로 해제
public class StageLoader
{
    readonly List<AsyncOperationHandle> _held = new();

    public async Task EnterAsync(string label)
    {
        var locs = await Addressables.LoadResourceLocationsAsync(label).Task;
        foreach (var loc in locs)
        {
            var h = Addressables.LoadAssetAsync<Object>(loc);
            _held.Add(h);
            await h.Task;
        }
    }

    public void Exit()
    {
        foreach (var h in _held) Addressables.Release(h);
        _held.Clear();
        // 씬 언로드 후 남은 것 정리
        Resources.UnloadUnusedAssets();
    }
}
"스테이지를 나가면 그 스테이지의 메모리가 0이 되는가" — Memory Profiler 스냅샷을 진입 전·후로 찍어 비교하는 것이 Addressables 도입의 완료 조건입니다.
GAME 06

DOTS · Job System · Burst

수천 개를 동시에 움직여야 할 때. 멀티코어를 실제로 쓰는 유일한 길입니다.

Job + Burst 부터

using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;
using Unity.Mathematics;

[BurstCompile]                                  // ★ 네이티브 수준으로 컴파일
public struct MoveJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Dir;
    public NativeArray<float3> Pos;
    public float Dt;

    public void Execute(int i) => Pos[i] += Dir[i] * Dt;
}

// 실행
var job = new MoveJob { Pos = _pos, Dir = _dir, Dt = Time.deltaTime };
var handle = job.Schedule(_pos.Length, innerloopBatchCount: 64);
handle.Complete();                              // 결과가 필요한 시점에
Job 안에서는 Unity 오브젝트를 못 씁니다. Transform·GameObject·Debug.Log 전부 불가. 순수한 숫자 계산만 가능하며, 데이터는 NativeArray 로 넘기고 반드시 Dispose 해야 합니다.

언제 도입할 것인가

효과가 큰 경우
  • 같은 계산을 수천 개에 반복 (군중·탄막·파티클)
  • 경로 탐색·시야 판정 대량 처리
  • 절차적 생성 · 지형 계산
도입하면 손해
  • 오브젝트가 수십 개뿐
  • UI · 게임 로직 대부분
  • 팀이 ECS 를 처음 접함 (학습 비용이 큽니다)
전면 ECS 전환은 신중하게. 기존 MonoBehaviour 게임에 무거운 계산만 Job + Burst 로 떼어내는 하이브리드가 현실적입니다. Unity.Mathematics 의 float3 을 쓰면 Burst 최적화(SIMD)가 훨씬 잘 먹습니다.

Transform 수천 개도 Job 으로 — TransformAccessArray

using UnityEngine.Jobs;

[BurstCompile]
struct SwarmJob : IJobParallelForTransform
{
    [ReadOnly] public NativeArray<float3> Vel;
    public float Dt;

    public void Execute(int i, TransformAccess t) =>
        t.position += (Vector3)(Vel[i] * Dt);
}

TransformAccessArray _tfs;    // 스폰 시 Add, 파괴 시 RemoveAtSwapBack

void Update()
{
    var job = new SwarmJob { Vel = _vel, Dt = Time.deltaTime };
    _handle = job.Schedule(_tfs);   // Transform 인데도 워커 스레드에서 돈다
}
void LateUpdate() => _handle.Complete();

"Job 은 Transform 을 못 쓴다"의 예외 통로입니다 — 군중 이동·총알 수천 발이 메인 스레드를 떠납니다.

Complete() 를 어디서 부를 것인가

Schedule 직후 Complete
var h = job.Schedule(n, 64);
h.Complete();   // 메인이 그냥 기다림
// = 멀티코어 효과 없음
한 프레임 벌려 주기
// Update 에서 Schedule
_h = job.Schedule(n, 64);
// LateUpdate 에서 회수
_h.Complete();
// 그 사이 워커가 일한다
NativeArray 는 GC 가 안 치워 줍니다. OnDestroy 에서 Dispose() 를 빠뜨리면 메모리 누수 경고가 콘솔을 덮습니다. Allocator.TempJob 은 4프레임 안에, Persistent 는 수동으로 — 수명 규칙을 정해 두세요.

// 대책 1 — Pending 큐를 로컬에 남긴다
void OnPurchaseConfirmedByStore(string txId, string receipt)
{
    PendingQueue.Add(txId, receipt);     // ① 디스크에 먼저 기록
    TryDeliver(txId);                    // ② 서버 검증 시도
}

// 대책 2 — 앱 시작 때마다 미처리분 재시도
async void Start()
{
    foreach (var p in PendingQueue.All())
    {

        if (ok) PendingQueue.Remove(p.TxId);   // 서버가 중복은 걸러 준다
    }
}

// 값 하나를 두 벌로 들고 대조 (간단하지만 효과가 있습니다)
public struct SecureInt
{
    private int _value, _check;
    public int Value
    {
        get { if ((_value ^ Key) != _check) OnTamper(); return _value; }
        set { _value = value; _check = value ^ Key; }
    }
    private const int Key = 0x5F3E;
}

현실적인 기준

클라이언트는 절대 신뢰할 수 없습니다. 해커가 기기를 완전히 통제하므로 클라이언트만의 방어는 시간 벌기일 뿐입니다. 돈·랭킹·경쟁에 영향을 주는 값은 서버가 계산하는 것이 유일한 해법입니다.
  • 싱글 · 비경쟁 — 최소한의 난독화면 충분합니다. 과투자하지 마세요
  • 랭킹 있음 — 점수 계산 근거(플레이 로그)를 서버가 검증
  • 실시간 대전 — 서버 권위 필수(🌐 게임 서버 탭 06)
  • 이상 탐지 — 통계적으로 불가능한 기록을 자동 플래그
차단보다 탐지가 실용적입니다. 즉시 밴하면 우회 방법을 찾아냅니다. 조용히 기록해 두었다가 주기적으로 일괄 처리하는 것이 상용 게임의 일반적인 운영 방식입니다.
치트 방지의 분수령은 암호화 기술이 아니라 "결과를 누가 계산하는가"입니다.
