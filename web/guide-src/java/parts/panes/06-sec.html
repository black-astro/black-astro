SEC 01

전체 그림 — 필터 체인

스프링 시큐리티는 결국 서블릿 필터 묶음입니다. 요청은 컨트롤러에 닿기 전에 이 체인을 통과합니다.

요청
HTTP 요청 도착Authorization 헤더나 세션 쿠키를 달고 옵니다.
▼
1
SecurityContextHolderFilter세션에 저장된 인증 정보를 꺼내 SecurityContext 에 복원합니다. (Spring Security 6부터 — 5의 SecurityContextPersistenceFilter 를 대체)
▼
2
인증 필터 (UsernamePassword · JWT · OAuth2)자격 증명을 검사해 Authentication 객체를 만듭니다. 커스텀 JWT 필터가 들어가는 자리입니다.
▼
3
ExceptionTranslationFilter뒤에서 터진 인증·인가 예외를 잡아 401/403 으로 바꿉니다.
▼
4
AuthorizationFilter“이 사용자가 이 URL 에 접근해도 되는가”를 최종 판단합니다.
▼
5
DispatcherServlet → Controller여기까지 왔다면 인증·인가를 통과한 것입니다.

SEC 02

설정 기본형

Spring Security 7(Boot 4.0 = 7.0 · Boot 4.1 = 7.1)은 람다 DSL만 씁니다. 옛 자료를 복붙하면 컴파일부터 안 됩니다.

Security 7 에서 완전히 없어진 것 — 6 시절 “deprecated” 였던 것들이 이제 제거됐습니다.
· WebSecurityConfigurerAdapter — SecurityFilterChain 빈으로 대체
· authorizeRequests() — authorizeHttpRequests() 로
· 체이닝용 .and() — 람다 중첩으로만 작성
· AccessDecisionManager·AccessDecisionVoter — AuthorizationManager 로
· OAuth2 password grant — 사양 자체가 폐기돼 제거 (authorization code + PKCE 로)
또 URL 매칭 기본이 AntPathRequestMatcher·MvcRequestMatcher 에서 PathPatternRequestMatcher 로 바뀌었습니다. 문자열만 넘기는 requestMatchers("/api/**") 는 그대로 동작하지만, 매처를 직접 만들어 넘기던 코드는 고쳐야 합니다. 
@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtFilter;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            // REST API 는 세션을 안 쓰므로 CSRF 불필요
            .csrf(AbstractHttpConfigurer::disable)
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))

            // 세션을 만들지 않는다 (JWT 방식)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

            // URL 별 권한 — 위에서부터 순서대로 매칭됩니다 ★
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**", "/api/public/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers("/actuator/health").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers("/api/orders/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()          // 나머지는 인증 필요
            )

            // JWT 필터를 인증 필터 앞에 끼운다
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)

            // 인증·인가 실패 시 JSON 으로 응답 (기본은 로그인 페이지로 리다이렉트)
            .exceptionHandling(e -> e
                .authenticationEntryPoint(new JwtAuthenticationEntryPoint())  // 401
                .accessDeniedHandler(new JwtAccessDeniedHandler())            // 403
            )

            .formLogin(AbstractHttpConfigurer::disable)
            .httpBasic(AbstractHttpConfigurer::disable)
            .build();
    }

    // 정적 리소스는 시큐리티를 아예 태우지 않는다 (성능)
    @Bean
    public WebSecurityCustomizer webSecurityCustomizer() {
        return web -> web.ignoring().requestMatchers("/css/**", "/js/**", "/images/**");
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();  // bcrypt
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
    }
}
requestMatchers 는 순서가 중요합니다. 위에서부터 처음 매칭되는 규칙이 적용되므로, .anyRequest() 를 위에 두면 아래 규칙이 전부 무시됩니다. 구체적인 것 → 넓은 것 순서로 쓰세요.
SEC 03

폼 로그인 · 세션

서버가 화면까지 그리는 전통적인 웹이라면 이 방식이 여전히 가장 단순하고 안전합니다.

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/", "/login", "/signup").permitAll()
            .anyRequest().authenticated())

        .formLogin(form -> form
            .loginPage("/login")                    // 내 로그인 화면
            .loginProcessingUrl("/login")           // 폼 action (필터가 가로챔)
            .usernameParameter("email")             // input name
            .passwordParameter("password")
            .defaultSuccessUrl("/", true)
            .failureUrl("/login?error")
        )

        .logout(out -> out
            .logoutUrl("/logout")
            .logoutSuccessUrl("/login?logout")
            .invalidateHttpSession(true)
            .deleteCookies("JSESSIONID")
        )

        .rememberMe(r -> r
            .key("고유한-비밀-키")
            .tokenValiditySeconds(60 * 60 * 24 * 14))   // 2주

        // Security 7 은 람다 중첩만 씁니다 — .and() 체이닝은 제거됐습니다
        .sessionManagement(s -> s
            .sessionFixation(f -> f.changeSessionId())   // 로그인 시 세션 ID 교체 ★
            .maximumSessions(1)                          // 동시 접속 1개
            .maxSessionsPreventsLogin(false))            // 새 로그인이 이전 것을 밀어냄
        .build();
}

UserDetailsService 구현

@Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String email) {
        User user = userRepository.findByEmail(email)
                .orElseThrow(() -> new UsernameNotFoundException("사용자 없음"));
        return new CustomUserDetails(user);
    }
}

@RequiredArgsConstructor
public class CustomUserDetails implements UserDetails {

    @Getter private final User user;

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return user.getRoles().stream()
                .map(r -> new SimpleGrantedAuthority("ROLE_" + r.name()))  // 접두사 ★
                .toList();
    }

    @Override public String getPassword() { return user.getPassword(); }
    @Override public String getUsername() { return user.getEmail(); }
    @Override public boolean isEnabled() { return user.isActive(); }
    @Override public boolean isAccountNonLocked() { return !user.isLocked(); }
}
ROLE_ 접두사 규칙 — hasRole("ADMIN") 은 내부적으로 ROLE_ADMIN 을 찾습니다. 권한을 만들 때 접두사를 붙여 저장하고, hasAuthority() 를 쓸 때는 전체 문자열을 씁니다.

JWT 인증 — 전체 구현

SPA·모바일 앱의 표준 방식입니다. 필요한 조각을 전부 담았습니다.

implementation("io.jsonwebtoken:jjwt-api:0.13.0") · runtimeOnly("io.jsonwebtoken:jjwt-impl:0.13.0") · runtimeOnly("io.jsonwebtoken:jjwt-jackson:0.13.0")

① 토큰 발급·검증 컴포넌트

@Component
public class JwtTokenProvider {

    private final SecretKey key;
    private final long accessExpMs;
    private final long refreshExpMs;

    public JwtTokenProvider(
            @Value("${jwt.secret}") String secret,          // 최소 32바이트 ★
            @Value("${jwt.access-exp-ms:1800000}") long accessExpMs,   // 30분
            @Value("${jwt.refresh-exp-ms:1209600000}") long refreshExpMs) { // 14일
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.accessExpMs = accessExpMs;
        this.refreshExpMs = refreshExpMs;
    }

    public String createAccessToken(Long userId, String email, List<String> roles) {
        Instant now = Instant.now();
        return Jwts.builder()
                .subject(String.valueOf(userId))
                .claim("email", email)
                .claim("roles", roles)
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plusMillis(accessExpMs)))
                .signWith(key)
                .compact();
    }

    public String createRefreshToken(Long userId) {
        Instant now = Instant.now();
        return Jwts.builder()
                .subject(String.valueOf(userId))
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plusMillis(refreshExpMs)))
                .signWith(key)
                .compact();
    }

    public Claims parse(String token) {          // 만료·위조면 예외
        return Jwts.parser().verifyWith(key).build()
                   .parseSignedClaims(token).getPayload();
    }

    public boolean validate(String token) {
        try {
            parse(token);
            return true;
        } catch (ExpiredJwtException e) {
            log.debug("만료된 토큰");
        } catch (JwtException | IllegalArgumentException e) {
            log.warn("잘못된 토큰: {}", e.getMessage());
        }
        return false;
    }
}

② 요청마다 토큰을 검사하는 필터

@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String token = resolveToken(req);

        if (token != null && tokenProvider.validate(token)) {
            Claims claims = tokenProvider.parse(token);

            List<SimpleGrantedAuthority> authorities =
                    ((List<?>) claims.get("roles")).stream()
                            .map(r -> new SimpleGrantedAuthority(r.toString()))
                            .toList();

            var auth = new UsernamePasswordAuthenticationToken(
                    Long.valueOf(claims.getSubject()), null, authorities);
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));

            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res);      // ★ 실패해도 여기서 막지 말고 넘긴다
    }                                  //   최종 판단은 AuthorizationFilter 가 함

    private String resolveToken(HttpServletRequest req) {
        String bearer = req.getHeader(HttpHeaders.AUTHORIZATION);
        return (bearer != null && bearer.startsWith("Bearer "))
                ? bearer.substring(7) : null;
    }
}

③ 로그인·재발급 API

@RestController
@RequestMapping("/api/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthService authService;

    @PostMapping("/login")
    public TokenRes login(@Valid @RequestBody LoginReq req) {
        return authService.login(req);
    }

    @PostMapping("/reissue")
    public TokenRes reissue(@RequestBody ReissueReq req) {
        return authService.reissue(req.refreshToken());
    }

    @PostMapping("/logout")
    public void logout(@AuthenticationPrincipal Long userId) {
        authService.logout(userId);      // Redis 에서 refresh 토큰 삭제
    }
}

@Service
@RequiredArgsConstructor
public class AuthService {

    private final AuthenticationManager authManager;
    private final JwtTokenProvider tokenProvider;
    private final RefreshTokenStore store;         // Redis

    public TokenRes login(LoginReq req) {
        // 여기서 UserDetailsService + PasswordEncoder 가 동작합니다
        Authentication auth = authManager.authenticate(
                new UsernamePasswordAuthenticationToken(req.email(), req.password()));

        var user = (CustomUserDetails) auth.getPrincipal();
        List<String> roles = auth.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority).toList();

        String access = tokenProvider.createAccessToken(
                user.getUser().getId(), user.getUsername(), roles);
        String refresh = tokenProvider.createRefreshToken(user.getUser().getId());

        store.save(user.getUser().getId(), refresh);   // 재발급·강제 로그아웃용
        return new TokenRes(access, refresh, "Bearer", 1800);
    }
}

④ 실패 응답을 JSON 으로

// 필터에서 터진 예외는 @RestControllerAdvice 로 안 갑니다 ★
@Component
public class JwtAuthenticationEntryPoint implements AuthenticationEntryPoint {
    @Override
    public void commence(HttpServletRequest req, HttpServletResponse res,
                         AuthenticationException e) throws IOException {
        write(res, HttpStatus.UNAUTHORIZED, "A001", "인증이 필요합니다");
    }
}

@Component
public class JwtAccessDeniedHandler implements AccessDeniedHandler {
    @Override
    public void handle(HttpServletRequest req, HttpServletResponse res,
                       AccessDeniedException e) throws IOException {
        write(res, HttpStatus.FORBIDDEN, "A002", "권한이 없습니다");
    }
}

private static void write(HttpServletResponse res, HttpStatus status,
                          String code, String message) throws IOException {
    res.setStatus(status.value());
    res.setContentType(MediaType.APPLICATION_JSON_VALUE);
    res.setCharacterEncoding("UTF-8");
    res.getWriter().write("""
        {"code":"%s","message":"%s"}
        """.formatted(code, message));
}
JWT 운영 체크리스트
· 시크릿은 32바이트 이상 + 환경 변수로
· Access 토큰은 짧게(15~30분), Refresh 는 길게
· 민감 정보를 페이로드에 넣지 마세요 — 누구나 디코딩할 수 있습니다(암호화 아님)
· 강제 로그아웃이 필요하면 Refresh 토큰을 서버에 저장하고 삭제
· 토큰 저장은 httpOnly 쿠키가 localStorage 보다 XSS 에 안전합니다

구글·카카오·네이버 로그인. 스프링이 대부분을 대신해 줍니다.

implementation("org.springframework.boot:spring-boot-starter-security-oauth2-client")
Boot 3 의 spring-boot-starter-oauth2-client 가 개명된 이름입니다. 
spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ${GOOGLE_CLIENT_ID}
            client-secret: ${GOOGLE_CLIENT_SECRET}
            scope: profile, email
          kakao:                              # 국내 서비스는 직접 정의
            client-id: ${KAKAO_CLIENT_ID}
            client-authentication-method: client_secret_post
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope: profile_nickname, account_email
        provider:
          kakao:
            authorization-uri: https://kauth.kakao.com/oauth/authorize
            token-uri: https://kauth.kakao.com/oauth/token
            user-info-uri: https://kapi.kakao.com/v2/user/me
            user-name-attribute: id
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .oauth2Login(oauth -> oauth
            .userInfoEndpoint(u -> u.userService(customOAuth2UserService))
            .successHandler(oauth2SuccessHandler))   // JWT 발급 후 리다이렉트
        .build();
}

@Service
@RequiredArgsConstructor
public class CustomOAuth2UserService extends DefaultOAuth2UserService {

    private final UserRepository userRepository;

    @Override
    public OAuth2User loadUser(OAuth2UserRequest req) {
        OAuth2User oAuth2User = super.loadUser(req);
        String provider = req.getClientRegistration().getRegistrationId();

        OAuthAttributes attrs = OAuthAttributes.of(provider, oAuth2User.getAttributes());

        // 있으면 갱신, 없으면 가입 (자동 회원가입)
        User user = userRepository.findByEmail(attrs.email())
                .map(u -> u.updateOAuthInfo(attrs.name()))
                .orElseGet(() -> userRepository.save(attrs.toEntity()));

        return new CustomOAuth2User(user, oAuth2User.getAttributes());
    }
}
SPA 와 함께 쓸 때 — 소셜 로그인 성공 후 successHandler 에서 JWT 를 만들어 프론트엔드 URL 로 리다이렉트하면서 토큰을 전달하는 방식이 일반적입니다.
기존 계정과 이메일이 같을 때 어떻게 합칠지를 미리 정해 두지 않으면 나중에 데이터가 꼬입니다.

URL 단위로 막을 수 없는 것들 — “자기 글만 수정 가능” 같은 규칙을 다룹니다.

@Configuration

@Service

    @PostAuthorize("returnObject.userId == authentication.principal")

    @PreAuthorize("hasRole('ADMIN') or #order.userId == authentication.principal")
    public void update(OrderUpdateReq order) { }

    @PreAuthorize("@orderPermission.canEdit(#id, authentication)")
    public void edit(Long id) { }
}

@Component("orderPermission")
@RequiredArgsConstructor
public class OrderPermissionEvaluator {
    private final OrderRepository repository;

    public boolean canEdit(Long orderId, Authentication auth) {
        return repository.findById(orderId)
                .map(o -> o.getUserId().equals(auth.getPrincipal()))
                .orElse(false);
    }
}

권한 설계 — Role vs Authority

// Role — 역할 (굵은 단위)
ROLE_USER, ROLE_ADMIN, ROLE_MANAGER
hasRole("ADMIN")            // ROLE_ 자동 부착

// Authority — 세부 권한 (권장 ★)
order:read, order:write, order:delete
hasAuthority("order:write")

// 실무에서는 Role 에 Authority 를 묶습니다
//   ROLE_ADMIN   -> order:*, user:*
//   ROLE_MANAGER -> order:read, order:write
//   ROLE_USER    -> order:read
// 계층 구조 — ADMIN 이면 USER 권한도 자동으로
@Bean
public RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.withDefaultRolePrefix()
            .role("ADMIN").implies("MANAGER")
            .role("MANAGER").implies("USER")
            .build();
}
가장 흔한 보안 구멍 — “URL 은 막았는데 남의 데이터에 접근할 수 있는 경우”입니다. GET /api/orders/1 이 인증만 확인하고 그 주문이 내 것인지 확인하지 않으면 아무나 남의 주문을 볼 수 있습니다. 조회 쿼리에 userId 조건을 넣는 것이 가장 확실합니다.

SSRF 방어 — InetAddressFilter Boot 4.1

SSRF(Server-Side Request Forgery)는 “사용자가 준 URL 로 서버가 대신 요청하게” 만드는 공격입니다. 썸네일 생성·웹훅 등록·이미지 프록시처럼 URL 을 입력으로 받는 기능이 있으면 노출됩니다. 공격자는 http://169.254.169.254/…(클라우드 메타데이터)나 http://127.0.0.1:8500 같은 내부 주소를 넣습니다 — 방화벽 바깥에서는 못 닿지만 내 서버는 닿기 때문에 뚫립니다.

WebFlux 시큐리티

개념은 같고 클래스 이름 앞에 Server·Reactive 가 붙습니다.

@Configuration
@EnableWebFluxSecurity                       // @EnableWebSecurity 가 아님
@RequiredArgsConstructor
public class ReactiveSecurityConfig {

    private final JwtTokenProvider tokenProvider;

    @Bean
    public SecurityWebFilterChain filterChain(ServerHttpSecurity http) {
        return http
            .csrf(ServerHttpSecurity.CsrfSpec::disable)
            .authorizeExchange(ex -> ex                     // authorizeHttpRequests 아님
                .pathMatchers("/api/auth/**").permitAll()
                .pathMatchers("/api/admin/**").hasRole("ADMIN")
                .anyExchange().authenticated())
            .addFilterAt(jwtWebFilter(), SecurityWebFiltersOrder.AUTHENTICATION)
            .exceptionHandling(e -> e
                .authenticationEntryPoint((exchange, ex) -> {
                    exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
                    return exchange.getResponse().setComplete();
                }))
            .build();
    }

    private WebFilter jwtWebFilter() {
        return (exchange, chain) -> {
            String token = resolve(exchange.getRequest());
            if (token == null || !tokenProvider.validate(token)) {
                return chain.filter(exchange);
            }
            Claims claims = tokenProvider.parse(token);
            var auth = new UsernamePasswordAuthenticationToken(
                    claims.getSubject(), null, authorities(claims));

            return chain.filter(exchange)
                    .contextWrite(ReactiveSecurityContextHolder
                            .withAuthentication(auth));      // ThreadLocal 이 아니라 컨텍스트 ★
        };
    }
}

// 현재 사용자 꺼내기 — 리액티브 방식
public Mono<UserRes> me() {
    return ReactiveSecurityContextHolder.getContext()
            .map(ctx -> ctx.getAuthentication().getName())
            .flatMap(userService::findByName);
}
핵심 차이 — MVC 는 SecurityContextHolder(ThreadLocal)를 쓰지만 WebFlux 는 스레드가 계속 바뀌므로 리액티브 컨텍스트에 담습니다. SecurityContextHolder.getContext() 를 그대로 쓰면 null 이 나옵니다.

로그인 유지 — 리프레시 토큰 · 다중 기기

“로그인 상태가 왜 자꾸 풀려요?” 와 “토큰이 털렸는데 못 막아요” 는 같은 설계에서 나옵니다. 실서비스가 쓰는 로테이션 + 기기별 세션 구조를 만듭니다.

리프레시 토큰은 한 번만 쓸 수 있는 표입니다. 같은 표가 두 번 오면 둘 중 하나는 도둑입니다.

토큰 계열(family) 저장

@Entity @Table(name = "refresh_token",
       indexes = @Index(columnList = "familyId"))
public class RefreshToken {
    @Id private String id;              // jti
    private String familyId;            // 기기 하나 = 계열 하나
    private Long   userId;

    private String tokenHash;           // ★ 원문을 저장하지 않는다
    private Instant expiresAt;
    private Instant usedAt;             // 사용되면 시각을 남긴다
    private boolean revoked;

    // 관리 화면 · '내 기기 목록'에 쓰인다
    private String deviceLabel;         // "Chrome · Windows"
    private String ip;
    private Instant lastSeenAt;
}
@Transactional
public TokenPair refresh(String raw) {
    String hash = sha256(raw);
    RefreshToken t = repo.findByTokenHash(hash)
        .orElseThrow(() -> new BadCredentialsException("unknown token"));

    // ① 이미 쓴 토큰이 다시 왔다 = 어딘가에서 복제됐다
    if (t.getUsedAt() != null || t.isRevoked()) {
        repo.revokeFamily(t.getFamilyId());          // 그 기기 전체를 끊는다
        alarm.suspiciousReuse(t.getUserId(), t.getFamilyId());
        throw new BadCredentialsException("token reuse detected");
    }
    if (t.getExpiresAt().isBefore(Instant.now()))
        throw new CredentialsExpiredException("expired");

    // ② 정상 — 쓴 것으로 표시하고 같은 계열로 새로 발급
    t.setUsedAt(Instant.now());
    String next = issueRefresh(t.getUserId(), t.getFamilyId());
    return new TokenPair(issueAccess(t.getUserId()), next);
}
리프레시 토큰을 DB 에 원문으로 저장하지 마세요. DB 가 유출되면 전 사용자 계정이 그대로 열립니다. 비밀번호와 똑같이 해시를 저장하고 비교하세요 (수명이 짧고 엔트로피가 충분하므로 SHA-256 으로 충분합니다).

SECURITY 12

2단계 인증 · 계정 보호

비밀번호만으로는 못 막습니다. 이미 다른 사이트에서 유출된 비밀번호로 로그인을 시도하는 공격(크리덴셜 스터핑)이 대부분이기 때문입니다.

TOTP — 라이브러리 없이 이해하기

// 인증 앱(Google Authenticator 등)은 표준 알고리즘입니다.
// 서버와 앱이 '같은 비밀 + 현재 시각'으로 같은 숫자를 만듭니다.
public boolean verify(String base32Secret, String code) {
    byte[] key = new Base32().decode(base32Secret);
    long   now = Instant.now().getEpochSecond() / 30;   // 30초 창

    // 시계 오차를 감안해 앞뒤 한 칸씩 허용한다
    for (long w = now - 1; w <= now + 1; w++) {
        if (constantTimeEquals(code, totp(key, w))) return true;
    }
    return false;
}

private String totp(byte[] key, long counter) {
    byte[] data = ByteBuffer.allocate(8).putLong(counter).array();
    Mac mac = Mac.getInstance("HmacSHA1");
    mac.init(new SecretKeySpec(key, "HmacSHA1"));
    byte[] h = mac.doFinal(data);

    int off = h[h.length - 1] & 0xF;                    // 동적 절단
    int bin = ((h[off] & 0x7F) << 24) | ((h[off+1] & 0xFF) << 16)
            | ((h[off+2] & 0xFF) << 8) | (h[off+3] & 0xFF);
    return String.format("%06d", bin % 1_000_000);
}
같은 코드를 두 번 받아 주면 안 됩니다. 30초 창 안에 중간자가 코드를 가로채 재사용할 수 있습니다. 사용한 (userId, counter) 를 기록해 두고 재사용을 거부하세요.

막는 것보다 중요한 것 — 잠금과 관측

// 로그인 실패를 사용자 기준 + IP 기준 두 축으로 센다
@Component @RequiredArgsConstructor
public class LoginGuard {
    private final StringRedisTemplate redis;

    public void check(String userKey, String ip) {
        if (count("u:" + userKey) >= 10 || count("i:" + ip) >= 50)
            throw new LockedException("too many attempts");
    }
    public void fail(String userKey, String ip) {
        bump("u:" + userKey, Duration.ofMinutes(15));
        bump("i:" + ip,      Duration.ofMinutes(15));
    }
    public void success(String userKey) { redis.delete("u:" + userKey); }
}
  • 계정 잠금은 그 자체가 공격 수단입니다 — 남의 계정을 일부러 잠글 수 있으니 영구 잠금은 피하고 시간 제한으로
  • “아이디가 없습니다”와 “비밀번호가 틀렸습니다”를 구분하지 마세요 — 가입 여부가 새어 나갑니다
  • 유출된 비밀번호 목록(k-anonymity API)과 대조해 가입·변경 시 거부
  • 새 기기·새 지역 로그인은 메일로 알림 — 사용자가 먼저 알아챕니다
다음 단계는 패스키(WebAuthn)입니다. 비밀번호와 OTP 를 둘 다 없애는 방향이고, Spring Security 6.4+ 는 webAuthn() 설정을 기본 제공합니다. 신규 서비스라면 처음부터 패스키를 함께 열어 두는 것을 권합니다.
SECURITY 13

권한 모델 — 역할로는 부족할 때

ROLE_ADMIN 하나로 시작한 프로젝트는 반드시 “이 팀 매니저는 자기 팀 문서만 수정 가능” 앞에서 무너집니다. 처음부터 자원 소유권을 넣어 설계하는 방법입니다.

역할(RBAC) → 속성(ABAC) 으로 넘어가는 지점

RBAC
“관리자면 다 된다” 권한이 사람에 붙습니다. 규칙이 단순해 빠르고, 역할이 10개를 넘지 않으면 충분합니다.
ABAC

// Spring Security 의 방식 — 표현식에 도메인 판단을 위임한다
@PreAuthorize("hasRole('ADMIN') or @docAuth.canEdit(#id, authentication)")
@PutMapping("/docs/{id}")
public DocView update(@PathVariable Long id, @RequestBody DocForm f) { ... }

@Component("docAuth")
@RequiredArgsConstructor
public class DocAuthorizer {
    private final DocRepository docs;

    public boolean canEdit(Long docId, Authentication auth) {
        Long me = ((AppUser) auth.getPrincipal()).id();
        return docs.findOwnerAndTeam(docId)
            .map(d -> d.ownerId().equals(me) || d.editorIds().contains(me))
            .orElse(false);
    }
}

멀티테넌시 — 남의 회사 데이터가 보이는 사고

// 요청마다 테넌트를 확정하고, 그 밖으로는 아예 못 나가게 만든다
@Component
public class TenantFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain) throws IOException, ServletException {
        try {
            AppUser u = current();                     // 토큰에서 꺼낸다
            TenantContext.set(u.tenantId());           // ★ 헤더로 받지 않는다
            chain.doFilter(req, res);
        } finally {
            TenantContext.clear();                     // 스레드 재사용 주의
        }
    }
}

@FilterDef(name = "tenant", parameters = @ParamDef(name = "tid", type = Long.class))

  • 테넌트 id 를 요청 파라미터·헤더로 받지 마세요 — 값 하나 바꾸면 남의 데이터가 열립니다. 토큰에서만 꺼냅니다
  • where 절을 개발자가 매번 쓰게 두면 언젠가 빠집니다. Hibernate 필터·RLS(PostgreSQL) 처럼 기본이 차단인 장치를 쓰세요
  • ThreadLocal 은 반드시 finally 에서 정리 — 스레드 풀이 재사용하면 다음 요청이 남의 테넌트로 동작합니다
  • 비동기·@Async·가상 스레드로 넘길 때 컨텍스트 전파를 확인하세요
DB 차원 격리(PostgreSQL Row Level Security)는 🗄️ 데이터베이스 가이드에서 다룹니다 — 애플리케이션 버그가 나도 DB 가 마지막으로 한 번 더 막아 주는 구조입니다.
