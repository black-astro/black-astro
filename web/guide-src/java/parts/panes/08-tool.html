Lombok — 보일러플레이트 제거

자바의 “장황함” 절반을 없애 줍니다. 다만 아무 데나 쓰면 사고가 납니다.

Lombok 사고 3대장
① 엔티티에 @Data·@ToString 금지 — 연관 엔티티를 따라가며 무한 순환과 N+1이 납니다. 꼭 쓰려면 @ToString(exclude = "orders").
② 엔티티에 @Setter 금지 — 아무 데서나 상태가 바뀌면 도메인 규칙을 지킬 수 없습니다.
③ @EqualsAndHashCode 전체 필드 사용 금지 — 엔티티는 ID 기준으로만. @EqualsAndHashCode(of = "id")

생성자 3종 — 누구를 인자로 가져가나 🟢 기초

이름이 길어서 헷갈리지만 읽어 보면 뜻이 그대로 들어 있습니다. @NoArgsConstructor(노 아그스 컨스트럭터)는 “인자 없는 생성자”, @RequiredArgsConstructor(리콰이어드 아그스 컨스트럭터)는 “꼭 필요한 인자만 받는 생성자”, @AllArgsConstructor(올 아그스 컨스트럭터)는 “모든 필드를 받는 생성자”입니다. 현업에서는 줄여서 노아그 · 리콰이어드 · 올아그라고 부릅니다. 핵심은 “꼭 필요한”의 기준이 final 과 @NonNull이라는 점입니다.

생성자 3종 — 리콰이어드는 final·@NonNull 만, 올아그는 static·초기화된 final 을 뺀 전부를 받습니다.

긴 옵션들 — 괄호 안의 한 줄마다 이유가 있다 🟡 중급

실무 코드에서 보는 롬복 어노테이션은 대부분 괄호가 붙어 있습니다. 하나씩 무엇을 만들어 주나 → 생성되는 코드 → 언제 쓰고 언제 피하나 순서로 봅니다.

① @NoArgsConstructor(access = AccessLevel.PROTECTED)

읽는 법: “노아그 컨스트럭터, 액세스 레벨 프로텍티드”. JPA 엔티티의 표준 관례입니다.

@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Order { ... }

// ↓ 생성되는 코드
protected Order() {
}
왜 protected 인가 — ① JPA 명세가 엔티티에 public 또는 protected 기본 생성자를 요구합니다(리플렉션으로 빈 객체를 만든 뒤 값을 채움). ② 하이버네이트의 지연 로딩 프록시는 엔티티를 상속한 클래스라서 부모 생성자를 부를 수 있어야 합니다 — private 이면 막힙니다. ③ public 이면 아무 데서나 new Order() 로 빈 껍데기 엔티티를 만들 수 있습니다. protected 는 이 둘 사이의 타협점입니다.

② @AllArgsConstructor(staticName = "of")

읽는 법: “올아그 컨스트럭터, 스태틱 네임 오브”. 생성자를 private 으로 숨기고 정적 팩토리를 만듭니다.

@Getter
@AllArgsConstructor(staticName = "of")
public class Money {
    private final long amount;
    private final String currency;
}

// ↓ 생성되는 코드
private Money(long amount, String currency) { ... }

public static Money of(long amount, String currency) {
    return new Money(amount, currency);
}

Money m = Money.of(1000, "KRW");   // List.of 와 같은 읽기 감각
쓸 때 — 값 객체(Money, Point)처럼 인자가 2~3개이고 순서가 분명할 때. 피할 때 — 인자가 4개를 넘거나 같은 타입이 연달아 나오면 @Builder 가 낫습니다. @RequiredArgsConstructor(staticName = "of") 도 똑같이 동작합니다.

③ @RequiredArgsConstructor(onConstructor_ = @Autowired)

읽는 법: “온 컨스트럭터 언더바”. 생성된 생성자에 어노테이션을 붙여 달라는 옵션입니다. 이름 끝의 _ 는 javac 8 이상에서 쓰는 문법 우회용 표기입니다.

// 옛날 코드에서 자주 보임
@Service
@RequiredArgsConstructor(onConstructor_ = @Autowired)
public class PayService {
    private final PayClient client;
}

// ↓ 생성되는 코드
@Autowired
public PayService(PayClient client) {
    this.client = client;
}
이제는 필요 없습니다 — 스프링 4.3 부터 생성자가 하나뿐이면 @Autowired 없이도 자동 주입합니다. 새 코드에서는 그냥 @RequiredArgsConstructor 만 쓰세요. 생성자가 둘 이상인 클래스에서만 의미가 있는데, 그런 빈은 설계부터 다시 보는 게 맞습니다.

④ @Builder(toBuilder = true) · @Builder.Default

읽는 법: “빌더 투빌더 트루”, “빌더 닷 디폴트”. toBuilder 는 기존 객체를 복사한 빌더를, Default 는 빌더에서 안 부른 필드의 기본값을 살려 줍니다.

@Builder(toBuilder = true)
public class Coupon {
    private final String code;
    @Builder.Default
    private final int rate = 10;
}

// ↓ 생성되는 코드 (요약)

    private String code;
    private boolean rate$set;     // 불렀는지 기억
    private int rate$value;
    public CouponBuilder rate(int rate) {
        this.rate$value = rate; this.rate$set = true; return this;
    }
    public Coupon build() {
        int rate = this.rate$value;
        if (!this.rate$set) rate = Coupon.$default$rate();  // ← 기본값 10

빌더 파이프라인 — build() 가 유일한 생성 지점이라 기본값 처리도 여기서 일어납니다.

⑤ @Builder + @NoArgsConstructor + @AllArgsConstructor — 왜 셋을 같이 붙이나

@Builder 를 클래스에 붙이면 롬복은 “다른 생성자가 하나도 없을 때만” 올아그 생성자를 몰래 만들어 씁니다. 그런데 JPA·Jackson 때문에 @NoArgsConstructor 를 붙이는 순간 생성자가 생겼으니 올아그 생성자를 만들지 않고, 빌더의 build() 가 부를 생성자가 없어 컴파일 오류가 납니다. 그래서 @AllArgsConstructor 를 명시해 빌더 전용 생성자를 돌려놓는 것이고, 바깥에서 못 쓰게 access = AccessLevel.PRIVATE 로 숨깁니다.

컴파일 오류
@Builder
@NoArgsConstructor
public class OrderDto {
    private Long id;
    private String name;
}
// error: constructor OrderDto in class OrderDto
//        cannot be applied to given types;
//   required: no arguments

세 개를 같이 — 또는 생성자에 @Builder
// DTO: 셋을 같이
@Getter
@Builder
@NoArgsConstructor
@AllArgsConstructor(access = AccessLevel.PRIVATE)
public class OrderDto { ... }

// 엔티티: 빌더가 받을 필드를 직접 고른다 (권장)
@Entity @Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Order {
    @Id @GeneratedValue private Long id;
    private String name;
    private int qty;

    @Builder
    private Order(String name, int qty) {   // id 는 빌더에 안 나옴
        this.name = name;
        this.qty = qty;
    }
}
엔티티는 생성자에 @Builder — 클래스에 붙이면 id·createdAt·연관 컬렉션까지 빌더에 열려 Order.builder().id(99L) 같은 위험한 코드가 가능해집니다. 생성자 레벨 @Builder 는 받을 값을 직접 고르는 방법입니다.

스프링 생성자 주입 — @RequiredArgsConstructor + private final 🟡 중급

스프링 빈은 필드를 전부 private final 로 두고 클래스에 @RequiredArgsConstructor 하나만 붙이는 것이 현업 표준입니다. final 이라 주입 후 바뀌지 않고, 생성자가 하나라 @Autowired 가 필요 없고, 테스트에서 new OrderService(fakeRepo, fakeNotifier) 로 바로 만들 수 있습니다. 필드 주입(@Autowired private ...)은 final 을 못 쓰고 순환 참조를 늦게 발견하게 만듭니다.

함정 — @Qualifier 가 생성자로 안 넘어간다

@Service
@RequiredArgsConstructor
public class PayService {
    @Qualifier("tossClient")              // 필드에만 붙어 있음
    private final PayClient payClient;    // PayClient 빈이 둘이라면?
}

// ↓ 롬복이 만든 생성자 — @Qualifier 가 없다
public PayService(PayClient payClient) {
    this.payClient = payClient;
}
// 기동 실패:
// NoUniqueBeanDefinitionException: expected single matching bean
//   but found 2: tossClient,kakaoClient

해결 — lombok.config 에 복사 대상 등록

# 프로젝트 루트(또는 src/main/java)의 lombok.config
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Value
// ↓ 등록 후 생성되는 코드
public PayService(@Qualifier("tossClient") PayClient payClient) {
    this.payClient = payClient;
}
copyableAnnotations(카피어블 어노테이션스) — 필드에 붙은 어노테이션을 생성자 파라미터·세터로 복사해 줄 목록입니다. 롬복 기본 목록은 null 관련 어노테이션 위주라 스프링 @Qualifier·@Value 는 직접 넣어야 합니다. 설정을 바꾼 뒤에는 클린 빌드(./gradlew clean build)를 해야 반영됩니다.
config 없이 넘어가는 방법 — 생성자를 직접 쓰고 파라미터에 @Qualifier 를 붙이거나, 필드 이름을 빈 이름과 같게(private final PayClient tossClient;) 지어 스프링의 이름 매칭에 기대는 방법도 있습니다. 다만 이름 매칭은 리네임 한 번에 조용히 깨지므로 config 등록이 가장 안전합니다.

엔티티에서 피할 것 — @Data · @Setter · @EqualsAndHashCode · @ToString 🟡 중급

어노테이션 (읽는 법)엔티티에서 무슨 일이대신 이렇게
@Data
데이터		Getter·Setter·RequiredArgs·ToString·EqualsAndHashCode 를 한꺼번에 — 아래 문제가 전부 따라옴@Getter 만 + 필요한 것만 골라 붙임
@Setter
세터		어디서든 order.setStatus(PAID) — 결제 검증 같은 도메인 규칙 우회, 변경 지점 추적 불가order.pay() 같은 의도가 드러나는 메서드
@EqualsAndHashCode
이퀄스 앤 해시코드		전체 필드 비교 → 연관 필드 접근 시 지연 로딩 발동·LazyInitializationException, 값이 바뀌면 hashCode 가 바뀌어 HashSet 에서 못 찾음onlyExplicitlyIncluded = true + id 에만 @EqualsAndHashCode.Include
@ToString
투스트링		Order → items → Order → … 순환 참조로 StackOverflowError, 로그 한 줄에 쿼리 수십 개연관 필드에 @ToString.Exclude
@Data 엔티티
@Entity
@Data                      // 💥 전부 열림
public class Order {
    @Id @GeneratedValue
    private Long id;
    private OrderStatus status;

    @OneToMany(mappedBy = "order")
    private List<OrderItem> items;   // toString·equals 가 여기까지 따라감
}

log.info("주문 {}", order);
// → items 지연 로딩 쿼리 → OrderItem.toString → order.toString → ...
// → StackOverflowError
필요한 것만 골라서
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@ToString
public class Order {
    @Id @GeneratedValue
    @EqualsAndHashCode.Include         // id 만 비교
    private Long id;
    private OrderStatus status;

    @OneToMany(mappedBy = "order")
    @ToString.Exclude                  // 순환 차단
    private List<OrderItem> items = new ArrayList<>();

    public void pay() {                // setter 대신 의도 메서드
        if (status != OrderStatus.CREATED) throw new IllegalStateException();
        this.status = OrderStatus.PAID;
    }
}
id 기준 equals 의 남은 함정 — 저장 전 엔티티는 id == null 이라 새 엔티티 두 개가 서로 같다고 판정됩니다. 저장 전 엔티티를 Set 에 담지 않는 규칙을 두거나, 엄밀함이 필요하면 equals/hashCode 를 직접 작성합니다(id 가 null 이면 false, hashCode 는 getClass().hashCode() 고정). 기존 코드의 @EqualsAndHashCode(of = "id") 도 같은 뜻이지만, 롬복 문서는 onlyExplicitlyIncluded 방식을 권장합니다.

@Value vs record — 언제 무엇을 🟡 중급

롬복의 @Value(밸류 — 스프링의 @Value("${...}") 와 이름만 같고 전혀 다른 것)는 클래스를 final, 필드를 private final 로 만들고 getter·equals·hashCode·toString·올아그 생성자를 붙입니다. 자바 16 부터 언어에 들어온 record(레코드)가 같은 일을 문법으로 합니다.

검증직접 생성자를 써야 함콤팩트 생성자로 짧게

@Service
@Slf4j
public class ExcelReader {

    public List<OrderRow> read(InputStream in) throws IOException {
        List<OrderRow> rows = new ArrayList<>();

        try (Workbook wb = WorkbookFactory.create(in)) {     // xls/xlsx 자동 판별
            Sheet sheet = wb.getSheetAt(0);                   // 또는 wb.getSheet("주문")
            DataFormatter fmt = new DataFormatter();          // 셀을 '보이는 대로' 문자열화

            for (int r = 1; r <= sheet.getLastRowNum(); r++) {   // 1행부터 (0은 헤더)
                Row row = sheet.getRow(r);
                if (row == null || isEmpty(row, fmt)) continue;   // 빈 행 건너뛰기

                try {
                    rows.add(new OrderRow(
                            getString(row, 0, fmt),
                            getInt(row, 1),
                            getDate(row, 2)
                    ));
                } catch (Exception e) {
                    log.warn("{}행 파싱 실패: {}", r + 1, e.getMessage());
                    // 실패한 행 번호를 모아 사용자에게 돌려주면 훨씬 친절합니다
                }
            }
        }
        return rows;
    }

    // ── 셀 읽기 유틸 — 이게 실무의 8할입니다 ──────────────────
    private String getString(Row row, int idx, DataFormatter fmt) {
        Cell cell = row.getCell(idx, Row.MissingCellPolicy.RETURN_BLANK_AS_NULL);
        return cell == null ? null : fmt.formatCellValue(cell).trim();
    }

    private Integer getInt(Row row, int idx) {
        Cell cell = row.getCell(idx);
        if (cell == null) return null;
        return switch (cell.getCellType()) {
            case NUMERIC -> (int) cell.getNumericCellValue();
            case STRING  -> {
                String s = cell.getStringCellValue().replaceAll("[^0-9-]", "");
                yield s.isBlank() ? null : Integer.parseInt(s);
            }
            case FORMULA -> (int) cell.getNumericCellValue();
            default      -> null;
        };
    }

    private LocalDate getDate(Row row, int idx) {
        Cell cell = row.getCell(idx);
        if (cell == null) return null;
        // 엑셀 날짜는 내부적으로 '숫자'입니다
        if (cell.getCellType() == CellType.NUMERIC && DateUtil.isCellDateFormatted(cell)) {
            return cell.getLocalDateTimeCellValue().toLocalDate();
        }
        String s = cell.getStringCellValue().trim();
        return s.isBlank() ? null : LocalDate.parse(s.replace("/", "-"));
    }

    private boolean isEmpty(Row row, DataFormatter fmt) {
        for (int c = row.getFirstCellNum(); c < row.getLastCellNum(); c++) {
            Cell cell = row.getCell(c);
            if (cell != null && !fmt.formatCellValue(cell).isBlank()) return false;
        }
        return true;
    }
}

        throw new BadRequestException("엑셀 파일만 업로드할 수 있습니다");
    }
    try (InputStream in = file.getInputStream()) {
        List<OrderRow> rows = excelReader.read(in);
        return orderService.bulkCreate(rows);
    }
}

                row.createCell(1).setCellValue(o.customerName());

            sheet.createFreezePane(0, 1);                     // 헤더 고정

        CellStyle s = wb.createCellStyle();

        f.setColor(IndexedColors.WHITE.getIndex());
        s.setFont(f);
        s.setFillForegroundColor(IndexedColors.DARK_BLUE.getIndex());
        s.setFillPattern(FillPatternType.SOLID_FOREGROUND);
        s.setAlignment(HorizontalAlignment.CENTER);
        s.setBorderBottom(BorderStyle.THIN);
        return s;

        CellStyle s = wb.createCellStyle();

                new XSSFSheetXMLHandler.SheetContentsHandler() {
                    private final List<String> row = new ArrayList<>();

        while (sheets.hasNext()) {
            try (InputStream sheet = sheets.next()) {
                parser.parse(new InputSource(sheet));
            }
        }
    }
}

TOOL 18

JSpecify — null을 타입 계약으로

자바에는 @Nullable이 스무 종류 넘게 있었습니다. 패키지가 다르면 도구가 다르게 해석했고, 그래서 아무도 믿지 않았습니다. JSpecify 는 구글·젯브레인스·오라클·우버·스프링이 함께 만든 표준입니다.

Spring Framework 7 은 자체 @Nullable을 버리고 JSpecify 로 전환했습니다.
의존성 — implementation("org.jspecify:jspecify:1.0.0") · 런타임 의존성이 거의 없습니다(애너테이션만 · 약 3KB). Maven 도 동일

애너테이션 네 개가 전부입니다

@NullMarked — 기본을 뒤집는다

// package-info.java — 이 패키지 전체에 적용
@NullMarked
package com.example.order;

import org.jspecify.annotations.NullMarked;

// 이제 이 패키지 안에서는
public class OrderService {
    // 아무 표시가 없으면 = null 이 아니다 (계약)
    public Order findById(Long id) { ... }

    // null 이 올 수 있으면 명시한다
    public @Nullable Order findByNo(String orderNo) { ... }

    // 인자도 마찬가지
    public void update(Order order, @Nullable String memo) { ... }
}
이 방향이 핵심입니다. 예전에는 “null 일 수 있는 곳에 표시”했는데, 실제로는 대부분이 non-null입니다. @NullMarked로 기본을 non-null 로 뒤집으면 표시할 곳이 훨씬 적어집니다.

네 애너테이션의 역할

애너테이션뜻
@NullMarked이 범위의 기본은 non-null (모듈·패키지·클래스·메서드)
@Nullable이 타입은 null 일 수 있다
@NonNull이 타입은 null 이 아니다 — @NullMarked 안에서는 거의 쓸 일이 없다
@NullUnmarked이 범위만 다시 “모름” 상태로 — 마이그레이션 중 임시 탈출구
// 아직 정리 못 한 레거시 클래스만 예외 처리
@NullUnmarked
public class LegacyImportService {
    // 여기 안에서는 null 여부를 검사하지 않는다
}

타입 사용 위치 애너테이션 — 붙는 자리가 의미를 바꾼다

// JSpecify 의 @Nullable 은 TYPE_USE 애너테이션이다.
// 그래서 '어디에 붙느냐'로 뜻이 정확히 갈린다.

List<@Nullable String> a;    // 리스트는 있다. 원소가 null 일 수 있다
@Nullable List<String> b;    // 리스트 자체가 null 일 수 있다. 원소는 non-null
@Nullable List<@Nullable String> c;   // 둘 다

// 배열도 마찬가지
String @Nullable [] d;        // 배열이 null 일 수 있다
@Nullable String[] e;         // 원소가 null 일 수 있다

// 예전 애너테이션들은 이 구분을 못 했다 — JSpecify 가 해결한 대표적인 지점

// 메서드 체인에서도 정확하다
Map<String, @Nullable User> cache;
User u = cache.get("a");          // ⚠️ 도구가 "null 일 수 있음"을 안다

// 제네릭 타입 변수
class Box<T extends @Nullable Object> {   // T 가 nullable 일 수도 있다
    private T value;
    public T get() { return value; }
}
class NonNullBox<T> {                      // @NullMarked 안이면 T 는 non-null
    private T value;
}

실제 코드에 적용한 모습

// package-info.java
@NullMarked
package com.example.order.service;

// OrderService.java
public class OrderService {

    private final OrderRepository repository;      // non-null (기본)

    public OrderService(OrderRepository repository) {
        this.repository = repository;              // 검사 불필요
    }

    // 반환이 null 일 수 있으면 반드시 표시
    public @Nullable Order findByOrderNo(String orderNo) {
        return repository.findByOrderNo(orderNo).orElse(null);
    }

    // 선택적 인자
    public Order place(PlaceOrderCommand cmd, @Nullable String couponCode) {
        Order order = Order.of(cmd);
        if (couponCode != null) {                  // 도구가 이 검사를 요구한다
            order.applyCoupon(couponCode);
        }
        return repository.save(order);
    }

    // 컬렉션 — 리스트는 항상 있고 원소도 non-null (빈 리스트를 돌려준다)
    public List<Order> findByUser(Long userId) {
        return repository.findByUserId(userId);
    }
}

규칙과 관례

  • @NullMarked는 패키지 단위로 — package-info.java에 한 번 쓰면 그 패키지 전체에 적용됩니다
  • 모듈 전체에 적용도 가능합니다 — module-info.java에 @NullMarked
  • 컬렉션은 null 대신 빈 컬렉션을 돌려주세요 — @Nullable List는 호출부에 이중 검사를 강요합니다
  • 필드보다 생성자 주입 — 초기화 시점이 명확해집니다
  • 기존 Optional과 병행 가능 — Optional 은 반환 타입에, JSpecify 는 모든 위치에
Optional 을 대체하지 않습니다. 서로 다른 도구입니다 — Optional 은 “값이 없을 수 있음”을 런타임 객체로, JSpecify 는 정적 분석용 계약으로 표현합니다. 인자·필드·제네릭 파라미터에는 Optional 을 쓰지 않으므로 JSpecify 가 그 자리를 채웁니다.

JSpecify 실전 — 검사 도구와 도입

애너테이션만 붙이면 아무 일도 일어나지 않습니다. 검사기(NullAway·IntelliJ)를 붙여야 빌드가 막아 주고, 코틀린 상호운용에서 진가가 드러납니다.

NullAway — 빌드에서 막는다

// build.gradle.kts
plugins {
    id("net.ltgt.errorprone") version "4.1.0"
}

dependencies {
    implementation("org.jspecify:jspecify:1.0.0")
    errorprone("com.google.errorprone:error_prone_core:2.36.0")
    errorprone("com.uber.nullaway:nullaway:0.12.3")
}

tasks.withType<JavaCompile>().configureEach {
    options.errorprone {
        // JSpecify 모드 — @NullMarked 를 인식한다
        option("NullAway:JSpecifyMode", "true")
        option("NullAway:AnnotatedPackages", "com.example")
        error("NullAway")                     // 위반 시 컴파일 실패
        // 점진 도입 중이라면 warn 으로 시작
        // warn("NullAway")
    }
}
NullAway 는 우버가 만든 검사기로, 안드로이드·서버 양쪽에서 널리 쓰입니다. 컴파일 시간에 거의 영향이 없어서(수 %) 상시 켜 둘 수 있는 것이 장점입니다.

검사기가 잡아 주는 것

@NullMarked
public class OrderService {

    public @Nullable Order find(Long id) { ... }

    public void bad(Long id) {
        Order order = find(id);
        order.getTotal();          // ❌ 컴파일 에러
        // dereferenced expression is @Nullable
    }

    public void good(Long id) {
        Order order = find(id);
        if (order == null) return;
        order.getTotal();          // ✅ 검사 후에는 통과
    }

    public void alsoGood(Long id) {
        Optional.ofNullable(find(id))
            .map(Order::getTotal)
            .ifPresent(System.out::println);
    }

    Order returnNull() {
        return null;               // ❌ non-null 로 선언한 메서드가 null 반환
    }
}

코틀린과의 상호운용 — 여기서 진가가 드러난다

애너테이션이 없을 때
// 자바: public String getName() { return null; }

// 코틀린에서 보면
val name = javaObj.name        // String! (플랫폼 타입)
println(name.length)            // 컴파일 통과 → 런타임 NPE 💥

// 코틀린의 null 안전성이 자바 경계에서 무력화된다
JSpecify 를 붙이면
// 자바(@NullMarked): public @Nullable String getName()

// 코틀린이 정확한 타입으로 읽는다
val name: String? = javaObj.name     // String? 로 인식
// println(name.length)               // ❌ 컴파일 에러
println(name?.length ?: 0)            // ✅

// non-null 로 선언된 것은 String 으로 온다
val id: Long = javaObj.id             // 검사 불필요

// 코틀린 컴파일러 옵션
// -Xjspecify-annotations=strict  (버전에 따라 기본 활성)
자바·코틀린 혼용 프로젝트라면 JSpecify 는 사실상 필수입니다. 자바 모듈에 @NullMarked를 붙이는 것만으로 코틀린 쪽 플랫폼 타입이 사라지고 null 안전성이 경계를 넘어 이어집니다. 코틀린 가이드의 자바와 섞어 쓰기 섹션과 함께 보면 그림이 완성됩니다.

점진적 도입 — 한 번에 다 하지 않는다

권장 순서

  1. 의존성 추가 — 애너테이션만이라 위험이 없습니다
  2. 새 패키지부터 @NullMarked — 새로 만드는 코드에만 적용
  3. NullAway 를 warn 으로 켜서 현황 파악
  4. 도메인·API 경계 패키지부터 정리 (효과가 가장 큽니다)
  5. 정리가 끝난 패키지를 AnnotatedPackages에 추가하고 error 로 승격
  6. 손대기 어려운 레거시는 @NullUnmarked로 격리
