JPA+ 01

상속 매핑 3전략

객체는 상속이 되는데 테이블은 안 됩니다. JPA 는 이 간극을 세 가지 방식으로 메우고, 어느 것을 고르느냐로 쿼리 성능과 제약 조건이 갈립니다.

고민되면 SINGLE_TABLE 로 시작하세요 — 자식이 늘어 컬럼이 지저분해지면 그때 JOINED 로 옮깁니다.

SINGLE_TABLE · JOINED 코드

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type")     // 기본 컬럼명은 DTYPE
public abstract class Payment {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private Long amount;
    @Enumerated(EnumType.STRING)
    private PaymentStatus status;
}

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    private String cardNo;          // ⚠️ NOT NULL 을 걸 수 없다 (다른 타입 행은 null)
    private int installment;
}

@Entity
@DiscriminatorValue("BANK")
public class BankTransfer extends Payment {
    private String bankCode;
    private String accountNo;
}

// JOINED 로 바꾸려면 애너테이션 한 줄
@Inheritance(strategy = InheritanceType.JOINED)
@DiscriminatorColumn(name = "payment_type")     // JOINED 에서는 선택 (있으면 조회가 빨라진다)

@MappedSuperclass — 상속이 아니라 '재사용'

// 테이블 상속이 아니라 '필드만 물려주는' 용도
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;
}

@Entity
public class Order extends BaseEntity { ... }    // 컬럼만 물려받는다

// 차이
// · @Inheritance   : 부모도 엔티티. 부모 타입으로 조회 가능 (다형 쿼리)
// · @MappedSuperclass : 부모는 엔티티가 아니다. 조회 불가. 순수 재사용
//
// 감사 필드·공통 id 는 대부분 @MappedSuperclass 가 정답이다
고를 때 질문답
자식이 2~4개, 필드도 적다SINGLE_TABLE — 단순하고 빠르다
자식마다 필드가 많고 NOT NULL 이 필요JOINED
부모 타입으로 조회할 일이 없다상속을 쓰지 말고 별도 엔티티로
공통 필드만 재사용하고 싶다@MappedSuperclass
구분 컬럼 없이 타입을 알고 싶다JOINED + @DiscriminatorColumn (조회 성능 개선)
JPA+ 02

복합키와 식별 관계

레거시 DB 를 만나면 반드시 나오는 주제입니다. @IdClass와 @EmbeddedId 두 방식이 있고, 연관관계까지 키에 포함되면(식별 관계) 난이도가 한 단계 올라갑니다.

@IdClass — 관계형에 가까운 방식
// 키 클래스 — equals/hashCode 필수, 기본 생성자 필수
public class OrderItemId implements Serializable {
    private Long order;      // 필드명이 엔티티와 같아야 한다
    private Long product;

    public OrderItemId() {}
    public OrderItemId(Long order, Long product) { ... }

    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
}

@Entity
@IdClass(OrderItemId.class)
public class OrderItem {
    @Id @ManyToOne
    @JoinColumn(name = "order_id")
    private Order order;

    @Id @ManyToOne
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
}

// 조회
em.find(OrderItem.class, new OrderItemId(1L, 100L));
@EmbeddedId — 객체지향에 가까운 방식
@Embeddable
public class OrderItemId implements Serializable {
    @Column(name = "order_id")
    private Long orderId;

    @Column(name = "product_id")
    private Long productId;

    protected OrderItemId() {}
    public OrderItemId(Long orderId, Long productId) { ... }

    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
}

@Entity
public class OrderItem {
    @EmbeddedId
    private OrderItemId id;

    @MapsId("orderId")                    // 키의 어느 필드와 연결되는지
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    private Order order;

    @MapsId("productId")
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
}

둘 중 무엇을 쓰나

항목@IdClass / @EmbeddedId
스타일관계형 / 객체지향
JPQLo.order.id / o.id.orderId (조금 길다)
키 클래스 재사용어렵다 / 쉽다(@Embeddable)
Spring Data둘 다 지원 / @EmbeddedId 가 더 자연스럽다
권장레거시 호환 / 새로 만든다면 이쪽
키 클래스에는 반드시 — Serializable 구현, 기본 생성자, equals/hashCode. 하나라도 빠지면 조회가 안 되거나 조용히 중복 저장됩니다.

식별 관계 vs 비식별 관계

// 식별 관계 — 부모 키가 자식 기본키의 일부 (위 예시)
// · 키가 계속 늘어난다 (손자 세대는 3개 컬럼)
// · 조인이 늘고 인덱스가 커진다

// 비식별 관계 — 자식은 자기 대리키를 가진다 (권장)
@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                        // 대리키

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;                    // 그냥 외래키

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id", nullable = false)
    private Product product;

    // 논리적 유일성은 유니크 제약으로
    // @Table(uniqueConstraints = @UniqueConstraint(columnNames = {"order_id","product_id"}))
}
새로 설계한다면 비식별 관계 + 대리키가 정석입니다. JPA 와 궁합이 좋고, 나중에 키 구조가 바뀌어도 파급이 작습니다. 식별 관계는 레거시 DB 를 그대로 매핑해야 할 때만 쓰세요.
JPA+ 03

임베디드 · 값 타입

주소·기간·금액처럼 여러 컬럼이 한 덩어리로 의미를 갖는 것들입니다. 값 타입으로 묶으면 도메인이 읽히고, 검증이 한 곳에 모입니다. 

@Embeddable
public class Address {
    @Column(name = "zip_code", length = 10)
    private String zipCode;

    @Column(name = "address1", length = 200)
    private String address1;

    @Column(name = "address2", length = 200)
    private String address2;

    protected Address() {}                       // JPA 용

    public Address(String zipCode, String address1, String address2) {
        if (zipCode == null || !zipCode.matches("\\d{5}"))
            throw new IllegalArgumentException("우편번호 형식 오류: " + zipCode);
        this.zipCode = zipCode;
        this.address1 = address1;
        this.address2 = address2;
    }

    public String full() { return address1 + " " + address2 + " (" + zipCode + ")"; }

    // ★ 값 타입은 equals/hashCode 를 '모든 필드'로 구현해야 한다
    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
}

@Entity
public class Member {
    @Id @GeneratedValue private Long id;

    @Embedded
    private Address homeAddress;

    // 같은 타입을 두 번 쓰면 컬럼명을 재정의한다
    @Embedded
    @AttributeOverrides({
        @AttributeOverride(name = "zipCode",  column = @Column(name = "work_zip")),
        @AttributeOverride(name = "address1", column = @Column(name = "work_addr1")),
        @AttributeOverride(name = "address2", column = @Column(name = "work_addr2")),
    })
    private Address workAddress;
}

값 타입은 공유하면 안 된다

memberB.setHomeAddress(addr);      // 같은 객체!

memberA.changeAddress(new Address("54321", "부산", "2층"));

// 복사가 필요하면 명시적으로
Address copy = new Address(addr.getZipCode(), addr.getAddress1(), addr.getAddress2());
임베디드 타입은 반드시 불변으로 설계하세요. 세터가 있으면 공유 참조 부작용이 언젠가 반드시 발생하고, 재현이 매우 어렵습니다.

JPA+ 04

컨버터 · JSON 컬럼 매핑

DB 컬럼 타입과 자바 타입이 다를 때 다리를 놓습니다 — 암호화 컬럼, enum 코드값, JSON 컬럼이 대표적인 쓰임입니다.

AttributeConverter 기본

// enum 을 코드값으로 저장 (ORDINAL 도 STRING 도 싫을 때)
@Converter(autoApply = true)      // 이 타입 전체에 자동 적용
public class OrderStatusConverter implements AttributeConverter<OrderStatus, String> {

    @Override
    public String convertToDatabaseColumn(OrderStatus attr) {
        return attr == null ? null : attr.getCode();      // "01", "02" …
    }

    @Override
    public OrderStatus convertToEntityAttribute(String dbData) {
        return dbData == null ? null : OrderStatus.fromCode(dbData);
    }
}

// 암호화 컬럼 — 주민번호·계좌번호
@Converter
public class CryptoConverter implements AttributeConverter<String, String> {
    @Override public String convertToDatabaseColumn(String plain) {
        return plain == null ? null : AesUtil.encrypt(plain);
    }
    @Override public String convertToEntityAttribute(String cipher) {
        return cipher == null ? null : AesUtil.decrypt(cipher);
    }
}

@Entity
public class Member {
    @Convert(converter = CryptoConverter.class)
    private String ssn;               // DB 에는 암호문으로 저장된다
}
암호화 컬럼은 검색이 안 됩니다. where ssn = ?가 동작하려면 결정적 암호화(같은 값→같은 암호문)여야 하고, 그러면 보안이 약해집니다. 검색이 필요하면 해시 컬럼을 따로 두세요.

JSON 컬럼 다루기

// Hibernate 6 는 JSON 을 기본 지원한다
@Entity
public class Product {
    @Id @GeneratedValue private Long id;

    @JdbcTypeCode(SqlTypes.JSON)
    @Column(columnDefinition = "jsonb")        // PostgreSQL
    private ProductOptions options;            // 그냥 객체로 매핑된다

    @JdbcTypeCode(SqlTypes.JSON)
    private List<String> keywords;
}

public record ProductOptions(
    String color, String size, Map<String, String> extra) {}

// 컨버터로 직접 만들 수도 있다 (MySQL 등)
@Converter
public class JsonConverter implements AttributeConverter<ProductOptions, String> {
    private static final ObjectMapper MAPPER = new ObjectMapper();

    @Override public String convertToDatabaseColumn(ProductOptions attr) {
        try { return MAPPER.writeValueAsString(attr); }
        catch (JsonProcessingException e) { throw new IllegalStateException(e); }
    }
    @Override public ProductOptions convertToEntityAttribute(String db) {
        try { return db == null ? null : MAPPER.readValue(db, ProductOptions.class); }
        catch (JsonProcessingException e) { throw new IllegalStateException(e); }
    }
}
JSON 컬럼은 “스키마가 자주 바뀌는 부가 정보”에 적합합니다. 검색·집계가 필요한 값은 정식 컬럼으로 빼세요 — JSON 안의 값으로 조건을 걸면 인덱스를 타기 어렵습니다 (PostgreSQL 의 GIN 인덱스 같은 예외는 있습니다).
컨버터가 적용되지 않는 곳 — @Id(기본키), @Version, 그리고 enum 에 @Enumerated가 이미 붙어 있으면 그쪽이 우선합니다. 또 컨버터를 통과한 값은 JPQL 에서 DB 값 기준으로 비교되므로, where status = :status 같은 쿼리에 주의가 필요합니다.
JPA+ 05

식별자 생성 전략

@GeneratedValue 한 줄이 배치 INSERT 가능 여부를 결정합니다. IDENTITY 를 쓰면 Hibernate 의 배치 기능이 통째로 꺼집니다.

전략DB특징
IDENTITYMySQL·MariaDBAUTO_INCREMENT. INSERT 를 즉시 실행해야 키를 안다 → 배치 불가
SEQUENCEPostgreSQL·Oracle시퀀스에서 미리 받아 온다 → 배치 가능 · allocationSize 로 왕복 절감
TABLE모든 DB키 테이블을 직접 관리. 락 경합 때문에 거의 안 쓴다
AUTO—DB 방언에 따라 자동 선택. 명시하는 편이 낫다
UUID모든 DB분산 생성 가능. 인덱스 단편화 주의 → UUIDv7·ULID 권장

SEQUENCE + 배치 INSERT

@Entity
@SequenceGenerator(
    name = "order_seq_gen",
    sequenceName = "order_seq",
    allocationSize = 50            // ★ 50개씩 미리 받아 온다 (DB 왕복 1/50)
)
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq_gen")
    private Long id;
}

IDENTITY 를 쓰는 MySQL 이라면

// 배치가 안 되므로 대량 저장은 JDBC 로 직접
@Repository
@RequiredArgsConstructor
public class OrderBulkRepository {
    private final JdbcTemplate jdbcTemplate;

    public void bulkInsert(List<Order> orders) {
        jdbcTemplate.batchUpdate(
            "insert into orders(user_id, amount, status, created_at) values (?,?,?,?)",
            orders, 1000,
            (ps, o) -> {
                ps.setLong(1, o.getUserId());
                ps.setLong(2, o.getAmount());
                ps.setString(3, o.getStatus().name());
                ps.setTimestamp(4, Timestamp.valueOf(o.getCreatedAt()));
            });
    }
}
// 10만 건 기준: JPA 한 건씩 수십 초 → JDBC 배치 1~2초
“배치를 켰는데 안 빨라진다”의 90%가 IDENTITY 입니다. 하이버네이트 로그(generate_statistics)에서 JDBC batches 수를 확인하세요 — 0이면 배치가 동작하지 않는 것입니다.
UUID 를 쓸 거라면 v7 을 쓰세요. 무작위 UUIDv4 는 인덱스 페이지가 흩어져 INSERT 성능이 크게 떨어집니다. 시간 순서가 앞에 오는 UUIDv7·ULID는 B-Tree 에 순차적으로 쌓여 이 문제가 없습니다. (Hibernate 6.5+ 는 @UuidGenerator(style = TIME) 지원)
JPA+ 06

영속성 컨텍스트 심화

데이터 · JPA 탭에서 더티 체킹까지 봤다면, 여기서는 플러시 시점, 준영속 처리, merge의 함정을 다룹니다.

준영속 객체를 다룰 때는 merge 보다 “조회 후 필요한 필드만 옮기기”가 안전합니다.

merge 의 위험

// 컨트롤러에서 받은 DTO 를 엔티티로 만들어 merge 하면?
@PutMapping("/orders/{id}")
public void update(@PathVariable Long id, @RequestBody OrderRequest req) {
    Order detached = new Order();
    detached.setId(id);
    detached.setStatus(req.getStatus());
    // memo, amount 등은 세팅하지 않았다 → null

    em.merge(detached);      // ❌ null 필드가 DB 를 덮어쓴다!
}

// ✅ 조회 후 필요한 필드만 변경 (더티 체킹)
@Transactional
public void update(Long id, OrderRequest req) {
    Order order = orderRepository.findById(id)
        .orElseThrow(() -> new NotFoundException(id));
    order.changeStatus(req.getStatus());       // 도메인 메서드로
    // save() 불필요
}

플러시 시점과 제어

// 플러시가 일어나는 때
// ① 트랜잭션 커밋 직전
// ② JPQL·네이티브 쿼리 실행 직전 (결과 정합성을 위해)
// ③ em.flush() 명시 호출

@Transactional
public void demo() {
    Order o = new Order(...);
    em.persist(o);                       // 아직 INSERT 안 됨

    // JPQL 실행 → 자동 플러시 (방금 넣은 것도 조회된다)
    List<Order> list = em.createQuery("select o from Order o", Order.class)
                          .getResultList();

    // 대량 처리에서는 주기적으로 flush + clear
    for (int i = 0; i < 100_000; i++) {
        em.persist(new Order(...));
        if (i % 500 == 0) { em.flush(); em.clear(); }   // ★ 메모리 관리
    }
}

// 플러시 모드 — 조회 성능이 중요한 구간에서만 신중히
em.setFlushMode(FlushModeType.COMMIT);   // JPQL 전에 플러시하지 않는다
                                          // (정합성 위험이 있으니 기본은 AUTO)
같은 트랜잭션에서 조회한 객체는 항상 같은 인스턴스입니다(1차 캐시). 그래서 findById(1) == findById(1)이 true입니다. 반대로 트랜잭션이 다르면 다른 인스턴스이므로, 엔티티를 ==로 비교하는 코드는 언젠가 반드시 틀립니다 — id 로 비교하세요.

지연 로딩 내부 — 프록시

LAZY가 어떻게 동작하는지 알면 LazyInitializationException·instanceof 실패· equals 오작동의 원인이 한 번에 풀립니다.

JPA+ 08

페치 전략 총정리

N+1 을 없애는 방법은 여럿인데 각각 한계가 다릅니다. 특히 컬렉션 fetch join + 페이징은 반드시 알아야 하는 함정입니다.

이 경고 로그가 보이면 이미 메모리 위험입니다 — 데이터가 커지면 OOM 으로 이어집니다.
// ✅ 방법 1 — ToOne 은 fetch join, 컬렉션은 batch size 에 맡긴다
@Query("select o from Order o join fetch o.user join fetch o.delivery where o.status = :status")
List<Order> findWithUserAndDelivery(@Param("status") OrderStatus status, Pageable pageable);
// application.yml: default_batch_fetch_size: 100
//  → 항목 컬렉션은 IN (…) 으로 한 번에 가져온다

// ✅ 방법 2 — 2단계 조회 (가장 안전하고 예측 가능)
public Page<OrderDto> search(OrderCondition cond, Pageable pageable) {
    // 1단계: id 만 페이징 (조인 없음 → 정확한 LIMIT)
    Page<Long> ids = orderRepository.findIdsByCondition(cond, pageable);

    // 2단계: 그 id 들로 상세 조회 (fetch join 자유롭게)
    List<Order> orders = orderRepository.findAllWithDetailsByIdIn(ids.getContent());

    return new PageImpl<>(toDto(orders), pageable, ids.getTotalElements());
}

JPA+ 09

락 — 동시 수정 제어

두 사용자가 같은 행을 동시에 고치면 나중 것이 앞의 것을 덮어씁니다(lost update). JPA 는 낙관적 락과 비관적 락 두 가지를 제공하고, 거의 항상 낙관적 락이 정답입니다.

낙관적 락은 락을 걸지 않습니다 — 충돌을 감지할 뿐이라 성능 부담이 거의 없습니다.

낙관적 락 + 재시도

@Entity
public class Product {
    @Id @GeneratedValue private Long id;
    private int stock;

    @Version                       // ★ 이 한 줄이 전부
    private Long version;

    public void decrease(int qty) {
        if (stock < qty) throw new OutOfStockException(id, stock);
        this.stock -= qty;
    }
}

// 충돌은 '재시도'가 정석
@Service
@RequiredArgsConstructor
public class StockService {

    @Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2))
    @Transactional
    public void decrease(Long productId, int qty) {
        Product p = productRepository.findById(productId).orElseThrow();
        p.decrease(qty);
    }

    @Recover
    public void recover(ObjectOptimisticLockingFailureException e, Long id, int qty) {
        throw new ConflictException("주문이 몰리고 있습니다. 다시 시도해 주세요.");
    }
}

비관적 락 — 정말 필요할 때만

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)          // select ... for update
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}

// 락 모드
// · PESSIMISTIC_READ  : 공유 락 (다른 트랜잭션도 읽을 수 있다)
// · PESSIMISTIC_WRITE : 배타 락 (가장 많이 쓴다)
// · OPTIMISTIC        : 읽은 것도 버전 검사에 포함
// · OPTIMISTIC_FORCE_INCREMENT : 연관 엔티티 변경 시 부모 버전 올리기

// ⚠️ 비관적 락의 대가
// · 락을 잡은 채 트랜잭션이 길어지면 대기가 폭증한다
// · 락 순서가 엇갈리면 데드락 (항상 같은 순서로 잠글 것)
// · 락 타임아웃을 반드시 설정 (기본은 무한 대기인 DB 도 있다)
더 나은 선택지 — 재고 차감처럼 단순한 경우는 원자적 UPDATE(set stock = stock - :qty where stock >= :qty)가 락도 재시도도 없이 가장 빠릅니다.

2차 캐시

1차 캐시는 트랜잭션 안에서만 삽니다. 2차 캐시는 애플리케이션 전체가 공유하지만, 쓸 수 있는 조건이 까다롭습니다. 잘못 쓰면 오래된 데이터를 보게 됩니다.

전략언제
READ_ONLY절대 안 바뀌는 데이터 — 가장 빠르고 안전
NONSTRICT_READ_WRITE가끔 바뀌고 잠깐 오래된 값을 봐도 되는 경우
READ_WRITE자주 바뀌는 데이터 (소프트 락 사용 · 비용 있음)
TRANSACTIONALJTA 환경 — 거의 안 쓴다
2차 캐시를 권하지 않는 경우가 더 많습니다 — ① 서버가 여러 대면 서버마다 캐시가 다릅니다(분산 캐시 설정이 별도로 필요), ② 벌크 연산·네이티브 쿼리는 캐시를 무효화하지 않습니다, ③ 디버깅이 어렵습니다. Redis 를 애플리케이션 레벨 캐시로 쓰는 편이 통제하기 쉽습니다.
2차 캐시가 정말 잘 맞는 자리 — 코드 테이블·설정·카테고리처럼 거의 안 바뀌고 자주 읽는 데이터입니다. 이 경우 READ_ONLY로 두면 DB 왕복이 사라지고 부작용도 없습니다.

  • 콜백 안에서 다른 엔티티를 저장하지 마세요 — 플러시 중에 또 플러시가 일어나 예측 불가한 동작을 합니다

  • @PostLoad 에서 무거운 작업 금지 — 조회 건수만큼 실행됩니다

JPA+ 12

벌크 연산 · 대용량 처리

수만 건을 다루기 시작하면 JPA 를 쓰는 방식 자체를 바꿔야 합니다. 영속성 컨텍스트가 도움이 아니라 짐이 되는 구간입니다.

public interface OrderRepository extends JpaRepository<Order, Long> {

public void exportAll(Consumer<OrderRow> sink) {

JPA+ 13

멀티 데이터소스 · 읽기 분리

조회 부하를 읽기 복제본으로 넘기거나, 여러 DB를 함께 쓰는 구성입니다. 트랜잭션 경계와 라우팅 규칙을 정확히 잡는 것이 핵심입니다. 

// ① 읽기/쓰기 라우팅 — @Transactional(readOnly) 로 판단
public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                ? "reader" : "writer";
    }
}

@Configuration
public class DataSourceConfig {

    @Bean @ConfigurationProperties("spring.datasource.writer")
    public DataSource writerDataSource() { return DataSourceBuilder.create().build(); }

    @Bean @ConfigurationProperties("spring.datasource.reader")
    public DataSource readerDataSource() { return DataSourceBuilder.create().build(); }

    @Bean
    public DataSource routingDataSource(
            @Qualifier("writerDataSource") DataSource writer,
            @Qualifier("readerDataSource") DataSource reader) {
        RoutingDataSource ds = new RoutingDataSource();
        ds.setTargetDataSources(Map.of("writer", writer, "reader", reader));
        ds.setDefaultTargetDataSource(writer);
        return ds;
    }

    @Bean
    @Primary
    public DataSource dataSource(@Qualifier("routingDataSource") DataSource routing) {
        // ★ 지연 프록시 — 커넥션을 '실제로 쓸 때' 결정한다 (readOnly 판단이 먼저 끝나도록)
        return new LazyConnectionDataSourceProxy(routing);
    }
}

    return findById(id);                       // @Transactional(readOnly) → reader! 아직 없을 수 있다
}

// ✅ 같은 트랜잭션 안에서 처리하거나, 저장 결과를 그대로 반환
@Transactional
public OrderDto create(OrderRequest req) {
    Order saved = orderRepository.save(new Order(req));
    return OrderDto.from(saved);               // 다시 조회하지 않는다
}

// ✅ 꼭 다시 읽어야 하면 강제로 writer 로
@Transactional     // readOnly = false → writer
public OrderDto findFresh(Long id) { ... }

JPA+ 14

소프트 삭제 · 동적 필터

실무 대부분의 시스템은 데이터를 진짜로 지우지 않습니다. 그 순간 “모든 조회에 deleted = false 를 붙이는” 문제가 생기고, 하이버네이트는 그것을 자동화하는 장치를 제공합니다.

@SQLDelete + @SQLRestriction

@Entity
@SQLDelete(sql = "update orders set deleted = true, deleted_at = now() where id = ?")
@SQLRestriction("deleted = false")      // Hibernate 6.3+ (구 @Where)
public class Order {
    @Id @GeneratedValue private Long id;
    private boolean deleted = false;
    private LocalDateTime deletedAt;
}

// repository.delete(order) → UPDATE 가 나간다
// 모든 조회에 자동으로 "and deleted = false" 가 붙는다

// ⚠️ 주의
// · 네이티브 쿼리에는 적용되지 않는다
// · 삭제된 것도 봐야 할 때(관리자 화면) 방법이 없다 → 아래 @FilterDef 사용
// · 유니크 제약과 충돌한다 (삭제된 행이 남아 있으므로)
//   → 부분 인덱스: create unique index ... where deleted = false (PostgreSQL)

@FilterDef — 켜고 끌 수 있는 조건

@Entity
@FilterDef(name = "deletedFilter",
           parameters = @ParamDef(name = "isDeleted", type = Boolean.class))
@Filter(name = "deletedFilter", condition = "deleted = :isDeleted")
public class Order { ... }

// 필요할 때만 켠다
@Transactional(readOnly = true)
public List<Order> findActive() {
    Session session = em.unwrap(Session.class);
    session.enableFilter("deletedFilter").setParameter("isDeleted", false);
    return orderRepository.findAll();
}

// 관리자 화면 — 필터를 켜지 않으면 전부 보인다
public List<Order> findAllIncludingDeleted() {
    return orderRepository.findAll();
}

// 멀티테넌시에도 같은 방식이 쓰인다
@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")
소프트 삭제는 생각보다 비쌉니다. ① 유니크 제약이 무력화되고, ② 인덱스에 안 쓰는 행이 계속 쌓이며, ③ 통계·집계 쿼리마다 조건을 기억해야 합니다. 정말 복구 요구가 있는 테이블만 소프트 삭제로 하고, 나머지는 이력 테이블로 옮기고 삭제하는 편이 깨끗합니다.
