QDSL 01

왜 QueryDSL인가 · 설정

Spring Data 의 쿼리 메서드는 조건이 늘면 이름이 감당 못 하게 길어지고, @Query 문자열은 동적 조건에 취약합니다. 그 사이를 메우는 도구입니다.

문자열로 동적 쿼리를 만들면
public List<Order> search(OrderCondition cond) {
    StringBuilder jpql = new StringBuilder("select o from Order o where 1=1");
    Map<String, Object> params = new HashMap<>();

    if (cond.getStatus() != null) {
        jpql.append(" and o.status = :status");   // 앞 공백 빠지면 런타임 에러
        params.put("status", cond.getStatus());
    }
    if (cond.getMinAmount() != null) {
        jpql.append(" and o.totalAmount >= :minAmount");
        params.put("minAmount", cond.getMinAmount());
    }
    // 조건이 늘수록 감당이 안 된다
    // · 컬럼명을 바꾸면? → 컴파일은 통과, 운영에서 터진다
    // · 타입이 틀리면?   → 마찬가지
    // · IDE 자동완성 없음, 리팩터링 추적 안 됨
    TypedQuery<Order> query = em.createQuery(jpql.toString(), Order.class);
    params.forEach(query::setParameter);
    return query.getResultList();
}
QueryDSL
public List<Order> search(OrderCondition cond) {
    return queryFactory
        .selectFrom(order)
        .where(
            statusEq(cond.getStatus()),        // null 이면 조건에서 자동 제외
            amountGoe(cond.getMinAmount()),
            createdBetween(cond.getFrom(), cond.getTo())
        )
        .orderBy(order.createdAt.desc())
        .fetch();
}

private BooleanExpression statusEq(OrderStatus status) {
    return status != null ? order.status.eq(status) : null;
}
private BooleanExpression amountGoe(Long amount) {
    return amount != null ? order.totalAmount.goe(amount) : null;
}
// 필드명이 바뀌면 컴파일 에러 · IDE 자동완성 · 조건 재사용 가능

QDSL 02

기본 문법

SQL 을 아는 사람이라면 거의 그대로 읽힙니다. select · from · where · orderBy · fetch 다섯 개면 시작할 수 있습니다.

import static com.example.domain.QMember.member;

List<Order> orders = queryFactory
        .selectFrom(order)                          // select(order).from(order) 축약
        .where(order.status.eq(OrderStatus.PAID))
        .orderBy(order.createdAt.desc())
        .fetch();

QDSL 03

동적 조건 — null 이 곧 “조건 없음”

QueryDSL 의 가장 강력한 성질입니다. where() 에 null을 넘기면 그 조건은 무시됩니다. 이 규칙 하나로 동적 쿼리가 if 없이 표현됩니다.

이 성질 덕분에 검색 API 한 개로 수십 가지 조합을 처리할 수 있습니다.

BooleanExpression — 권장 방식

public List<Order> search(OrderCondition cond) {
    return queryFactory
        .selectFrom(order)
        .leftJoin(order.member, member).fetchJoin()
        .where(
            statusEq(cond.getStatus()),
            amountGoe(cond.getMinAmount()),
            memberNameContains(cond.getKeyword()),
            createdBetween(cond.getFrom(), cond.getTo())
        )
        .fetch();
}

private BooleanExpression statusEq(OrderStatus status) {
    return status == null ? null : order.status.eq(status);
}
private BooleanExpression amountGoe(Long amount) {
    return amount == null ? null : order.totalAmount.goe(amount);
}
private BooleanExpression memberNameContains(String keyword) {
    return !StringUtils.hasText(keyword) ? null : member.name.contains(keyword);
}
private BooleanExpression createdBetween(LocalDateTime from, LocalDateTime to) {
    if (from == null && to == null) return null;
    if (from == null) return order.createdAt.loe(to);
    if (to == null) return order.createdAt.goe(from);
    return order.createdAt.between(from, to);
}

// ★ 장점 — 이 메서드들을 '다른 쿼리에서도 재사용'할 수 있다
// ★ 조합도 된다: statusEq(s).and(amountGoe(a))

BooleanBuilder — 조건이 복잡할 때

public List<Order> search(OrderCondition cond) {
    BooleanBuilder builder = new BooleanBuilder();

    if (cond.getStatus() != null) builder.and(order.status.eq(cond.getStatus()));
    if (cond.getMinAmount() != null) builder.and(order.totalAmount.goe(cond.getMinAmount()));

    // OR 그룹이 섞이면 Builder 가 읽기 좋다
    if (StringUtils.hasText(cond.getKeyword())) {
        builder.and(
            member.name.contains(cond.getKeyword())
                .or(order.orderNo.contains(cond.getKeyword()))
        );
    }

    // 권한에 따른 강제 조건 (절대 빠지면 안 되는 것)
    builder.and(order.deleted.isFalse());

    return queryFactory.selectFrom(order)
            .leftJoin(order.member, member)
            .where(builder)
            .fetch();
}
모든 조건이 null 이면 전체 조회가 됩니다. 기간 필수나 최대 조회 건수 제한 같은 안전장치를 반드시 넣으세요 — 실수로 수백만 건을 읽는 사고가 흔합니다.
QDSL 04

조인 총정리

QueryDSL 의 조인은 JPQL 조인 그대로입니다. 연관 기반 조인과 연관 없는 조인(theta·on), 그리고 fetch join을 구분해서 씁니다.

조건을 어디에 두느냐가 결과 행 수를 바꿉니다 — left join 을 썼는데 행이 줄었다면 where 절을 보세요.
// ① 연관 기반 조인 — 가장 흔하다
queryFactory.selectFrom(order)
    .join(order.member, member)              // inner join
    .leftJoin(order.delivery, delivery)      // left outer join
    .where(member.name.eq("김현우"))
    .fetch();

// ② fetch join — 연관 엔티티를 함께 로딩 (N+1 해결)
queryFactory.selectFrom(order)
    .join(order.member, member).fetchJoin()
    .leftJoin(order.delivery, delivery).fetchJoin()
    .where(order.status.eq(PAID))
    .fetch();
// ⚠️ 컬렉션 fetchJoin + 페이징은 금지 (JPA 심화 08 참고)

// ③ on 절 — 조인 대상 필터링 (left join 에서 의미가 크다)
queryFactory.select(order, coupon)
    .from(order)
    .leftJoin(coupon).on(
        coupon.orderId.eq(order.id),
        coupon.status.eq(CouponStatus.USED)   // 이 조건에 맞는 쿠폰만 붙인다
    )
    .fetch();
// inner join 이면 on 과 where 가 결과적으로 같지만,
// left join 에서는 완전히 다르다 (on 은 붙일지 말지, where 는 행을 남길지)

// ④ 연관관계 없는 조인 (theta join)
queryFactory.select(order, product)
    .from(order, product)                     // 카티션 곱 + where
    .where(order.productName.eq(product.name))
    .fetch();
// left join 이 필요하면 on 을 쓴다
queryFactory.select(order, product)
    .from(order)
    .leftJoin(product).on(order.productName.eq(product.name))
    .fetch();

// ⑤ 컬렉션 조인
queryFactory.selectFrom(order)
    .join(order.items, orderItem)             // 일대다
    .where(orderItem.quantity.gt(5))
    .distinct()                                // 중복 제거
    .fetch();

on 과 where 의 차이 — left join 에서

위치결과
on 절 조건조건에 안 맞으면 연관만 null. 왼쪽 행은 남는다
where 절 조건조건에 안 맞으면 행 자체가 사라진다 (left join 의미가 없어짐)
// 주문 전체 + 사용된 쿠폰(있으면)
.leftJoin(coupon).on(coupon.orderId.eq(order.id), coupon.used.isTrue())
// → 쿠폰 없는 주문도 나온다 (coupon 은 null)

// 쿠폰을 쓴 주문만
.leftJoin(coupon).on(coupon.orderId.eq(order.id))
.where(coupon.used.isTrue())
// → 쿠폰 없는 주문은 사라진다 (사실상 inner join)

조인 성능 감각

  • fetch join 은 ToOne 위주로 — 컬렉션은 하나만, 페이징과 함께 쓰지 않기
  • 조인 순서와 인덱스 — 결국 SQL 이므로 실행 계획을 봐야 합니다
  • distinct 는 애플리케이션 레벨에서도 동작합니다(Hibernate 6+ 는 엔티티 중복을 자동 제거)
  • 조인 대신 두 번 조회가 빠른 경우도 많습니다 — 특히 대용량 일대다
  • 표시용 데이터는 DTO 프로젝션으로 (엔티티를 안 만든다)
QDSL 05

서브쿼리

JPAExpressions 로 작성합니다. 다만 JPQL 의 제약을 그대로 물려받아 from 절 서브쿼리(인라인 뷰)는 불가능합니다 — 그 우회 방법까지 함께 봅니다. 

import static com.querydsl.jpa.JPAExpressions.select;
import static com.querydsl.jpa.JPAExpressions.selectFrom;

// ① where 절 서브쿼리 — 최고 금액 주문
QOrder sub = new QOrder("sub");             // ★ 별칭이 겹치면 안 된다

queryFactory.selectFrom(order)
    .where(order.totalAmount.eq(
        select(sub.totalAmount.max()).from(sub)
    ))
    .fetch();

// ② in 서브쿼리 — VIP 회원의 주문
QMember subM = new QMember("subM");

queryFactory.selectFrom(order)
    .where(order.member.id.in(
        select(subM.id).from(subM).where(subM.grade.eq(Grade.VIP))
    ))
    .fetch();

// ③ exists — in 보다 빠른 경우가 많다
queryFactory.selectFrom(order)
    .where(selectFrom(orderItem)
        .where(orderItem.order.eq(order), orderItem.quantity.gt(10))
        .exists())
    .fetch();

// ④ select 절 서브쿼리 — 회원별 주문 수
queryFactory
    .select(member.name,
            select(sub.count()).from(sub).where(sub.member.eq(member)))
    .from(member)
    .fetch();

// ⑤ 상관 서브쿼리 + 최신 1건 (자주 쓰는 패턴)
QOrder o2 = new QOrder("o2");
queryFactory.selectFrom(order)
    .where(order.createdAt.eq(
        select(o2.createdAt.max()).from(o2).where(o2.member.eq(order.member))
    ))
    .fetch();

from 절 서브쿼리가 안 될 때

  1. 조인으로 바꿔 본다 — 대부분의 인라인 뷰는 조인으로 표현됩니다
  2. 쿼리를 두 번 나눈다 — 서브쿼리 결과(id 목록)를 먼저 받고 그것으로 본 쿼리
  3. 네이티브 쿼리 — 통계·리포트처럼 복잡하면 이쪽이 정직합니다
  4. DB 뷰를 만든다 — 재사용되는 복잡한 집계라면 좋은 선택
Hibernate 6 부터는 일부 from 절 서브쿼리를 지원합니다. 다만 QueryDSL 5.x 의 API 가 이를 온전히 노출하지 않으므로, 복잡한 통계는 jOOQ 나 네이티브 쿼리 병행이 현실적입니다.

서브쿼리 성능 감각

// ❌ 상관 서브쿼리가 행마다 실행되면 느리다
.where(order.totalAmount.gt(
    select(sub.totalAmount.avg()).from(sub).where(sub.member.eq(order.member))
))

// ✅ 조인 + 그룹핑으로 바꾸면 한 번에 계산된다
// (평균을 미리 구해 조인)

// exists vs in
// · exists : 첫 행을 찾으면 멈춘다 → 보통 더 빠르다
// · in     : 서브쿼리 결과를 전부 만든 뒤 비교 (옵티마이저가 바꿔 주기도 한다)

QDSL 06

프로젝션 — DTO 로 받기

조회 전용 API 에서 엔티티를 통째로 읽는 것은 낭비입니다. QueryDSL 은 필요한 컬럼만 DTO 로 받는 방법을 네 가지 제공합니다.

방식특징
Projections.constructor생성자 호출. 순서·타입이 맞아야 하고 틀리면 런타임 에러
Projections.fields필드에 직접 주입 (기본 생성자 필요). 이름이 맞아야 한다
Projections.bean세터로 주입. DTO 에 세터가 필요
@QueryProjection컴파일 타임 검증 — 가장 안전. 단 DTO 가 QueryDSL 에 의존
Tuple임시 조회용. 서비스 밖으로 내보내지 말 것
// ① @QueryProjection — 권장 (컴파일 시점에 검증된다)
public record OrderSummary(Long id, String orderNo, String memberName, Long totalAmount) {
    @QueryProjection
    public OrderSummary { }        // record 의 compact 생성자에 붙인다
}
// → QOrderSummary 가 생성된다

List<OrderSummary> result = queryFactory
    .select(new QOrderSummary(order.id, order.orderNo, member.name, order.totalAmount))
    .from(order)
    .join(order.member, member)
    .fetch();
// 필드를 하나 추가하면 컴파일 에러 → 빠뜨릴 수 없다

// ② Projections.constructor — DTO 가 QueryDSL 을 몰라도 된다
List<OrderSummary> result2 = queryFactory
    .select(Projections.constructor(OrderSummary.class,
            order.id, order.orderNo, member.name, order.totalAmount))
    .from(order).join(order.member, member)
    .fetch();

// ③ 이름이 다를 때 — as() 로 별칭
List<OrderView> result3 = queryFactory
    .select(Projections.fields(OrderView.class,
            order.id,
            order.orderNo.as("no"),                    // 필드명이 no 인 경우
            ExpressionUtils.as(
                select(sub.count()).from(sub).where(sub.member.eq(member)), "orderCount")))
    .from(order).join(order.member, member)
    .fetch();

// ④ 중첩 DTO
List<OrderDetail> details = queryFactory
    .select(Projections.constructor(OrderDetail.class,
            order.id,
            Projections.constructor(MemberDto.class, member.id, member.name)))
    .from(order).join(order.member, member)
    .fetch();

// ⑤ Tuple — 임시로 여러 값
List<Tuple> tuples = queryFactory
    .select(order.status, order.totalAmount.sum(), order.count())
    .from(order).groupBy(order.status)
    .fetch();
for (Tuple t : tuples) {
    OrderStatus status = t.get(order.status);
    Long sum = t.get(order.totalAmount.sum());
}
Tuple을 컨트롤러까지 내보내지 마세요. QueryDSL 타입이 프레젠테이션 계층까지 새어 나가고, 어떤 값이 들어 있는지 코드만 봐서는 알 수 없습니다. 리포지터리 안에서 DTO 로 변환해 반환하세요.
QDSL 07

집계 · 그룹핑 · CASE

통계 API 를 만들 때 쓰는 문법들입니다. SQL 의 집계 함수가 거의 그대로 대응되고, 표현식을 조합할 수 있습니다.

QDSL 08

페이징 · 카운트 최적화

목록 API 의 절반은 페이징입니다. 카운트 쿼리를 어떻게 만드느냐로 응답 시간이 크게 달라집니다.

기본 페이징

public Page<OrderSummary> search(OrderCondition cond, Pageable pageable) {
    List<OrderSummary> content = queryFactory
        .select(new QOrderSummary(order.id, order.orderNo, member.name, order.totalAmount))
        .from(order)
        .join(order.member, member)
        .where(statusEq(cond.getStatus()), amountGoe(cond.getMinAmount()))
        .orderBy(order.createdAt.desc())
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

    // 카운트는 별도 쿼리 — 조인·정렬을 뺀다
    JPAQuery<Long> countQuery = queryFactory
        .select(order.count())
        .from(order)
        .join(order.member, member)      // 조건에 필요한 조인만 남긴다
        .where(statusEq(cond.getStatus()), amountGoe(cond.getMinAmount()));

    // ★ 카운트를 '필요할 때만' 실행한다
    return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
}
PageableExecutionUtils는 ① 첫 페이지이고 결과가 페이지 크기보다 작거나 ② 마지막 페이지인 경우 카운트 쿼리를 아예 실행하지 않습니다. 간단하지만 효과가 큽니다.

QDSL 09

벌크 연산 · 수정 · 삭제

한 건씩 더티 체킹으로 고치면 수만 건에서는 답이 없습니다. QueryDSL 로 UPDATE·DELETE 를 한 방에 날릴 수 있지만, 영속성 컨텍스트를 우회한다는 점을 반드시 기억해야 합니다. 

@Transactional
public long expireOldOrders(LocalDateTime before) {
    long updated = queryFactory
        .update(order)
        .set(order.status, OrderStatus.EXPIRED)
        .set(order.updatedAt, LocalDateTime.now())
        .set(order.version, order.version.add(1))     // ★ 버전을 직접 올려야 한다
        .where(order.status.eq(OrderStatus.NEW),
               order.createdAt.lt(before))
        .execute();

    em.flush();
    em.clear();          // ★ 1차 캐시를 비운다 — 안 하면 옛 값을 보게 된다
    return updated;
}

// 계산식으로 수정
queryFactory.update(product)
    .set(product.stock, product.stock.subtract(1))
    .where(product.id.eq(id), product.stock.gt(0))
    .execute();          // 반환값이 0이면 재고 부족 — 원자적 차감

// 조건부 수정 (CASE)
queryFactory.update(member)
    .set(member.grade, new CaseBuilder()
        .when(member.totalPurchase.goe(1_000_000)).then(Grade.VIP)
        .when(member.totalPurchase.goe(100_000)).then(Grade.GOLD)
        .otherwise(Grade.NORMAL))
    .execute();

// 삭제
queryFactory.delete(orderLog)
    .where(orderLog.createdAt.lt(LocalDateTime.now().minusYears(1)))
    .execute();

벌크 연산의 성질 — 반드시 알아야 할 것

  • 영속성 컨텍스트를 거치지 않습니다 → 1차 캐시가 옛 값을 들고 있음
  • @PreUpdate·@LastModifiedDate 가 동작하지 않습니다 → 직접 set
  • @Version 이 자동으로 오르지 않습니다 → 직접 add(1)
  • 2차 캐시도 갱신되지 않습니다
  • cascade 가 동작하지 않습니다 → 자식은 따로 처리
  • 그 대신 압도적으로 빠릅니다 — 10만 건이 쿼리 한 방

// 페이징 헬퍼를 매번 쓰기 번거롭다면 공통 추상 클래스를 만든다
public abstract class QuerydslSupport {

    protected final JPAQueryFactory queryFactory;

    protected QuerydslSupport(JPAQueryFactory queryFactory) {
        this.queryFactory = queryFactory;
    }

    protected <T> Page<T> applyPagination(
            Pageable pageable,
            Function<JPAQueryFactory, JPAQuery<T>> contentQuery,
            Function<JPAQueryFactory, JPAQuery<Long>> countQuery) {

        JPAQuery<T> query = contentQuery.apply(queryFactory);
        List<T> content = query
                .offset(pageable.getOffset())
                .limit(pageable.getPageSize())
                .fetch();

        return PageableExecutionUtils.getPage(content, pageable,
                () -> countQuery.apply(queryFactory).fetchOne());
    }
}

QDSL 11

재사용 · 표현식 조합

QueryDSL 의 진짜 힘은 조건을 값처럼 다룰 수 있다는 데 있습니다. 메서드로 뽑아 두면 여러 쿼리에서 재사용되고, 조합도 됩니다. 

// 조건을 모아 두는 클래스 — 도메인 언어가 된다
public final class OrderPredicates {

    private OrderPredicates() {}

    public static BooleanExpression isActive() {
        return order.deleted.isFalse().and(order.status.ne(OrderStatus.CANCELED));
    }

    public static BooleanExpression paidBetween(LocalDateTime from, LocalDateTime to) {
        if (from == null && to == null) return null;
        BooleanExpression base = order.status.eq(OrderStatus.PAID);
        if (from != null) base = base.and(order.paidAt.goe(from));
        if (to != null) base = base.and(order.paidAt.loe(to));
        return base;
    }

    public static BooleanExpression bigOrder() {
        return order.totalAmount.goe(100_000);
    }

    public static BooleanExpression ownedBy(Long memberId) {
        return memberId == null ? null : order.member.id.eq(memberId);
    }
}

// 쓰는 쪽 — 읽으면 뜻이 그대로 보인다
queryFactory.selectFrom(order)
    .where(isActive(), paidBetween(from, to), bigOrder())
    .fetch();

// 조합도 자유롭다
BooleanExpression cond = isActive().and(bigOrder().or(ownedBy(vipId)));

// 표현식도 재사용한다
public static NumberExpression<Long> finalAmount() {
    return order.totalAmount.subtract(order.discountAmount).add(order.shippingFee);
}
queryFactory.select(order.orderNo, finalAmount().as("finalAmount"))
    .from(order)
    .where(finalAmount().goe(50_000))          // select 와 where 에 같은 식을 쓴다
    .orderBy(finalAmount().desc())
    .fetch();

// 동적 정렬 (Pageable.getSort() 를 QueryDSL 로)
private OrderSpecifier<?>[] toOrderSpecifiers(Sort sort) {
    return sort.stream().map(o -> {
        com.querydsl.core.types.Order dir =
            o.isAscending() ? ASC : DESC;
        PathBuilder<Order> path = new PathBuilder<>(Order.class, "order");
        return new OrderSpecifier(dir, path.get(o.getProperty()));
    }).toArray(OrderSpecifier[]::new);
}

성능 — 무엇을 조심하나

QueryDSL 은 결국 JPQL 을 만드는 도구입니다. 느린 이유는 QueryDSL 이 아니라 만들어진 SQL에 있습니다.

문제해결
목록 조회에서 N+1fetchJoin() · default_batch_fetch_size · DTO 프로젝션
카운트 쿼리가 느리다조인·정렬 제거 · PageableExecutionUtils · 근사 카운트

        Long totalAmount, OrderStatus status, LocalDateTime createdAt, Long itemCount) {
    @QueryProjection public OrderSummary {}
}

// ── 구현 ────────────────────────────────────────────────
@Repository
@RequiredArgsConstructor
public class OrderRepositoryImpl implements OrderRepositoryCustom {

    private final JPAQueryFactory queryFactory;

    @Override
    public Page<OrderSummary> search(OrderSearchCondition cond, Pageable pageable) {

        List<OrderSummary> content = queryFactory
            .select(new QOrderSummary(
                    order.id, order.orderNo, member.name, member.grade,
                    order.totalAmount, order.status, order.createdAt,
                    JPAExpressions.select(orderItem.count())
                            .from(orderItem).where(orderItem.order.eq(order))))
            .from(order)
            .join(order.member, member)
            .where(
                order.deleted.isFalse(),                 // 항상 붙는 조건
                statusEq(cond.status()),
                amountBetween(cond.minAmount(), cond.maxAmount()),
                keywordContains(cond.keyword()),
                createdBetween(cond.from(), cond.to()),
                vipOnly(cond.onlyVip())
            )
            .orderBy(toOrderSpecifiers(pageable.getSort()))
            .offset(pageable.getOffset())
            .limit(pageable.getPageSize())
            .fetch();

        JPAQuery<Long> countQuery = queryFactory
            .select(order.count())
            .from(order)
            .join(order.member, member)                  // 조건에 필요한 조인만
            .where(
                order.deleted.isFalse(),
                statusEq(cond.status()),
                amountBetween(cond.minAmount(), cond.maxAmount()),
                keywordContains(cond.keyword()),
                createdBetween(cond.from(), cond.to()),
                vipOnly(cond.onlyVip())
            );

        return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
    }

    // ── 조건 메서드 (재사용 가능) ──
    private BooleanExpression statusEq(OrderStatus status) {
        return status == null ? null : order.status.eq(status);
    }

    private BooleanExpression amountBetween(Long min, Long max) {
        if (min == null && max == null) return null;
        if (min == null) return order.totalAmount.loe(max);
        if (max == null) return order.totalAmount.goe(min);
        return order.totalAmount.between(min, max);
    }

    private BooleanExpression keywordContains(String keyword) {
        if (!StringUtils.hasText(keyword)) return null;
        return order.orderNo.contains(keyword)
                .or(member.name.contains(keyword));
    }

    private BooleanExpression createdBetween(LocalDate from, LocalDate to) {
        if (from == null && to == null) return null;
        LocalDateTime start = from == null ? null : from.atStartOfDay();
        LocalDateTime end = to == null ? null : to.plusDays(1).atStartOfDay();
        if (start == null) return order.createdAt.lt(end);
        if (end == null) return order.createdAt.goe(start);
        return order.createdAt.goe(start).and(order.createdAt.lt(end));
    }

    private BooleanExpression vipOnly(Boolean onlyVip) {
        return Boolean.TRUE.equals(onlyVip) ? member.grade.eq(Grade.VIP) : null;
    }

    // ── 정렬 화이트리스트 ──
    private static final Map<String, ComparableExpressionBase<?>> SORTABLE = Map.of(
            "createdAt", order.createdAt,
            "totalAmount", order.totalAmount,
            "orderNo", order.orderNo);

    private OrderSpecifier<?>[] toOrderSpecifiers(Sort sort) {
        List<OrderSpecifier<?>> specs = new ArrayList<>();
        for (Sort.Order o : sort) {
            ComparableExpressionBase<?> path = SORTABLE.get(o.getProperty());
            if (path == null) continue;                    // 허용되지 않은 컬럼은 무시
            specs.add(o.isAscending() ? path.asc() : path.desc());
        }
        specs.add(order.id.desc());                        // ★ 안정 정렬을 위한 타이브레이커
        return specs.toArray(OrderSpecifier[]::new);
    }
}
이 코드에서 눈여겨볼 세 가지 — ① 항상 붙는 조건(deleted.isFalse())을 맨 앞에 고정, ② 정렬 화이트리스트로 임의 컬럼 정렬 차단, ③ id 타이브레이커로 페이지가 흔들리지 않게. 세 가지 모두 실무에서 사고가 났던 자리입니다.

public record DailySales(String day, long orderCount,
                         long totalAmount, long avgAmount, long maxAmount) {
    @QueryProjection public DailySales {}
}

public List<DailySales> dailySales(LocalDate from, LocalDate to) {
    StringTemplate day = Expressions.stringTemplate(
            "function('to_char', {0}, {1})", order.paidAt, "YYYY-MM-DD");

    return queryFactory
        .select(new QDailySales(
                day,
                order.count(),
                order.totalAmount.sum().coalesce(0L),
                order.totalAmount.avg().castToNum(Long.class).coalesce(0L),
                order.totalAmount.max().coalesce(0L)))
        .from(order)
        .where(order.status.eq(OrderStatus.PAID),
               order.paidAt.goe(from.atStartOfDay()),
               order.paidAt.lt(to.plusDays(1).atStartOfDay()))
        .groupBy(day)
        .orderBy(day.desc())
        .fetch();
}

// 상품별 판매 순위 + 비중
public List<ProductRank> topProducts(LocalDate from, int limit) {
    NumberExpression<Long> sales = orderItem.price.multiply(orderItem.quantity).sum();

    return queryFactory
        .select(new QProductRank(product.id, product.name, sales, orderItem.count()))
        .from(orderItem)
        .join(orderItem.product, product)
        .join(orderItem.order, order)
        .where(order.status.eq(PAID), order.paidAt.goe(from.atStartOfDay()))
        .groupBy(product.id, product.name)
        .orderBy(sales.desc())
        .limit(limit)
        .fetch();
}

            .select(new QOrderSummary(...))
            .from(order).join(order.member, member)
            .where(order.status.eq(PAID))
            .stream()) {                       // ★ fetch() 대신 stream()
        stream.forEach(sink);
    }

// ② 커서 청크 — 배치에서 가장 안전한 방식
public void processAll(Consumer<List<Order>> handler) {
    Long lastId = null;
    while (true) {
        List<Order> chunk = queryFactory
            .selectFrom(order)
            .where(order.status.eq(NEW),
                   lastId == null ? null : order.id.gt(lastId))
            .orderBy(order.id.asc())
            .limit(1000)
            .fetch();

        if (chunk.isEmpty()) break;
        handler.accept(chunk);
        lastId = chunk.get(chunk.size() - 1).getId();
        em.clear();                            // ★ 영속성 컨텍스트 비우기
    }
}
통계 쿼리는 운영 DB 를 오래 잡습니다. 조회 범위를 기간으로 강제하고, 무거운 리포트는 읽기 복제본이나 미리 계산한 집계 테이블로 옮기세요. 실시간이 아니어도 되는 지표를 실시간으로 만들다 DB 가 마비되는 일이 흔합니다.

버전 상황과 대안

QueryDSL 은 원 저장소의 릴리스가 느려진 상태입니다. 그래서 포크·대안이 등장했습니다 — 새 프로젝트라면 알고 고르는 편이 좋습니다.

선택지상황과 특징
querydsl 5.1.x (원본)여전히 가장 널리 쓰인다. jakarta 분류자 제공. 릴리스 주기가 길다
OpenFeign 포크io.github.openfeign.querydsl — 최신 JDK·Hibernate 대응이 빠르다
Spring Data JPA + Specification추가 의존성 없음. 표현력이 떨어지고 코드가 장황하다
jOOQSQL 그 자체를 타입 안전하게. 통계·복잡 쿼리에 강하다. 상용 DB 는 유료
Kotlin JDSL코틀린 프로젝트라면 코드 생성 없이 동적 쿼리 (라인 오픈소스)
Blaze-PersistenceJPA 확장 — CTE·윈도 함수·엔티티 뷰까지. 학습 곡선이 있다

Specification 과 비교

// Spring Data 의 Specification — 추가 의존성 없이 동적 쿼리
public static Specification<Order> statusEq(OrderStatus status) {
    return (root, query, cb) ->
        status == null ? null : cb.equal(root.get("status"), status);
}

orderRepository.findAll(
    Specification.where(statusEq(status)).and(amountGoe(min)), pageable);

// · 조인·프로젝션이 장황하다
// · 가독성이 떨어진다
