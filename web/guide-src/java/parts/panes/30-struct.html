파일이 스무 개일 때는 아무렇게나 둬도 찾을 수 있습니다. 문제는 파일이 삼백 개, 사람이 다섯 명, 실행 파일이 세 개가 될 때입니다. 이 탭은 자바 프로젝트를 어떤 폴더·패키지·모듈로 나누는지, 그리고 언제 다음 단계로 넘어가야 하는지를 짧게 정리합니다. Maven 표준 레이아웃에서 시작해 Spring Boot 기능별 패키지, Gradle 멀티 모듈과 build-logic, 테스트 픽스처 공유, JavaFX 앱과 라이브러리 구조까지 보고, 마지막에 구조 규칙을 ArchUnit 테스트로 강제하는 법으로 끝냅니다. 순수 자바 예제(package-private 경계, JPMS exports)는 JDK 25.0.1 에서 직접 컴파일해 오류 메시지를 옮겼습니다.

STR 01

왜 구조인가 — 표준 레이아웃과 규모별 진화

구조는 "그 코드 어디 있어요?"를 아무도 묻지 않게 만드는 약속입니다. 자바는 Maven 이 정한 표준 디렉터리 레이아웃을 Gradle 도 그대로 따르기 때문에, 처음 보는 저장소도 같은 자리에서 시작합니다. Initializr 가 만든 폴더 하나하나의 뜻은 설치 탭 ST 09 에 있으니, 여기서는 왜 그렇게 나뉘는지와 커지면 어떻게 바뀌는지만 봅니다.

표준 레이아웃 — 모듈 하나일 때

shop/
├─ settings.gradle.kts         # 프로젝트 이름 · (나중에) 모듈 목록
├─ build.gradle.kts            # 플러그인 · 의존성
├─ gradle/libs.versions.toml   # 버전을 한곳에 (STR 04)
├─ src/
│  ├─ main/
│  │  ├─ java/com/example/shop/   # 운영 코드 — 폴더 = 패키지
│  │  └─ resources/               # yml · 로그 설정 · SQL · 정적 파일
│  └─ test/
│     ├─ java/com/example/shop/   # 같은 패키지 이름으로 테스트
│     └─ resources/               # 테스트 전용 설정
└─ build/                      # 산출물 (Maven 은 target/) — 커밋 금지

규칙 네 가지

규칙이유
패키지 = 역도메인
com.example.shop		전 세계에서 이름이 겹치지 않게 하는 자바 관례(JLS §6.1). 소문자만, 하이픈은 못 씁니다
폴더 경로 = 패키지javac 는 강제하지 않지만 Gradle·Maven·IDE 가 전부 이걸 전제로 찾습니다
테스트도 같은 패키지폴더는 달라도 패키지가 같으면 package-private 클래스를 테스트할 수 있습니다
resources 는 jar 루트로src/main/resources/application.yml → jar 안 /application.yml → classpath: 로 읽힘
레이아웃을 바꾸지 마세요 — sourceSets { main { java.srcDirs("src") } } 처럼 바꿀 수는 있지만, 새로 온 사람·플러그인·CI 스크립트가 전부 표준 경로를 가정합니다. 얻는 것이 없습니다.
구조는 처음에 정하는 것이 아니라 신호가 올 때 한 칸씩 옮기는 것입니다.

다음 단계로 넘어가는 신호 🟢 기초

지금이런 일이 생기면다음 단계
단일 패키지한 폴더에 파일 30개 이상 · 같은 이름 접두사(Order…)가 10개 넘게 몰림기능별 패키지 (STR 02)
기능별 패키지배치·워커 같은 두 번째 실행 파일이 필요 · 빌드 3분 이상 · "이 패키지는 저 패키지를 쓰면 안 된다"는 말이 리뷰마다 나옴멀티 모듈 (STR 04 · 07)
멀티 모듈팀 둘이 같은 배포 열차를 기다림 · 한 기능만 10배로 늘려야 함 · DB 를 나눠야 함서비스 분리 (확장 탭)
❌ 첫날부터 4단계
shop-order-service/     # 저장소 1
shop-member-service/    # 저장소 2
shop-common-lib/        # 저장소 3 — 버전 맞추기 지옥
# 엔티티 6개짜리 서비스에 저장소 3개 · 배포 파이프라인 3개
✅ 지금 크기에 맞게
shop/                   # 저장소 1 · 모듈 1
└─ src/main/java/com/example/shop/
   ├─ order/            # 기능별 패키지 (2단계)
   └─ member/
# 배치가 생기면 그때 멀티 모듈로 쪼갭니다
정리 — 표준 레이아웃은 바꾸지 말고, 패키지 → 모듈 → 서비스 순서로 신호가 왔을 때만 한 칸씩 넘어갑니다.
STR 02

Spring Boot — 계층별 패키지 vs 기능별 패키지

부트 탭 BOOT 02 에서 "도메인(기능)으로 묶으라"고 권했습니다. 이 섹션은 그 이유와, 기능별로 묶은 뒤 package-private 으로 경계를 만드는 법을 실제 컴파일 결과로 보여 줍니다.

계층별 (package by layer)

com/example/shop/
├─ controller/   OrderController · MemberController · …
├─ service/      OrderService · MemberService · …
├─ repository/   OrderRepository · MemberRepository · …
├─ dto/          주문·회원 DTO 가 한 폴더에 섞임
└─ entity/       Order · Member · …
# 모든 클래스가 public 이어야 서로 부를 수 있음

기능별 (package by feature)

com/example/shop/
├─ ShopApplication.java   # 최상위 — 컴포넌트 스캔 기준점
├─ order/                 # 주문에 관한 것은 전부 여기
│  ├─ OrderController.java      (package-private)
│  ├─ OrderService.java         (public — 다른 기능의 입구)
│  ├─ OrderRepository.java      (package-private)
│  ├─ Order.java · OrderStatus.java
│  └─ CancelOrderRequest.java
├─ member/
└─ common/                # 정말 공통인 것만 (예외 · 설정)
함께 바뀌는 것을 함께 둡니다 — 변경 하나가 폴더 하나에서 끝나는 쪽이 기능별입니다.

package-private 으로 경계 만들기 🟡 중급

입구만 public, 나머지는 숨김

// order/OrderService.java
package com.shop.order;

public class OrderService {                 // 공개 — 다른 기능이 부르는 입구
    private final OrderRepository repo = new OrderRepository();

    public long place(String item) {
        return repo.save(item);
    }
}

// order/OrderRepository.java
package com.shop.order;

class OrderRepository {                     // public 없음 = 같은 패키지만
    private long seq = 0;
    long save(String item) { return ++seq; }
}

// member/MemberService.java — 다른 기능의 내부를 쓰려 하면
package com.shop.member;

import com.shop.order.OrderRepository;      // 3행

public class MemberService {
    void cheat() { new OrderRepository(); }
}
$ javac -d out $(find src -name '*.java')     # JDK 25.0.1 실측
...MemberService.java:3: error: OrderRepository is not public in
  com.shop.order; cannot be accessed from outside package
...MemberService.java:6: error: (같은 오류 — new 하는 줄)
2 errors

스프링에서도 그대로 됩니다

  • 컴포넌트 스캔은 public 을 요구하지 않습니다 — @Controller·@Component 클래스를 package-private 으로 둬도 빈이 됩니다.
  • Spring Data 리포지토리 인터페이스도 package-private 으로 둘 수 있습니다 — 다른 기능이 남의 테이블을 직접 조회하는 길이 닫힙니다.
  • 예제처럼 new 로 만든 것은 설명용이고, 실제로는 생성자 주입입니다(BOOT 03).
하위 패키지를 만들면 경계가 사라집니다 — 자바의 package-private 은 정확히 같은 패키지만 봅니다. order/web/, order/domain/ 으로 쪼개는 순간 서로 부르려면 public 이 필요하고, 그때부터 경계는 컴파일러가 아니라 ArchUnit(STR 10) 이 지켜야 합니다.
언제권장
엔티티 5개 이하 · 학습용계층별도 괜찮습니다 — 한눈에 다 보입니다
기능이 늘어나는 서비스기능별 — 기능 안에서는 평평하게(하위 폴더 없이)
한 기능이 파일 15개 넘음그 기능만 하위 패키지 + ArchUnit, 또는 STR 03
❌ 기능별처럼 보이지만 전부 public + 잡동사니 폴더
order/   (모든 클래스 public — member 가 OrderRepository 를 직접 씀)
common/util/  OrderUtils · MemberHelper · DateUtil2 …
# common 이 모든 기능에 의존하는 순간 순환이 생깁니다
✅ 입구 하나 + 진짜 공통만
order/   public 은 OrderService · 이벤트 · DTO 뿐
member/  order 가 필요하면 OrderService 로만
common/  예외 · 설정 · 기능 이름이 안 들어간 것만
# 규칙: common 은 기능 패키지를 import 하지 않는다
정리 — 기능별로 묶고 기능 안은 평평하게, 다른 기능이 쓸 입구만 public 으로 둡니다. package-private 은 공짜 경계입니다.
STR 03

헥사고날 · 클린을 과하지 않게

포트·어댑터의 원리, 도메인과 JPA 엔티티를 나누는 코드, 도메인이 스프링을 모르게 하는 ArchUnit 규칙은 깊이 탭 DEEP 16 에 있습니다. 여기서는 폴더 모양과 어디까지만 적용할지만 다룹니다.

복잡한 기능만 포트 · 어댑터로

com/example/shop/
├─ order/                       # 결제 · 재고 · 외부 PG 가 얽힌 기능
│  ├─ domain/                   # Order · Money · 규칙 — 스프링 import 0
│  ├─ application/              # PlaceOrderService (유스케이스 · 트랜잭션)
│  │  └─ port/out/              # PaymentPort · StockPort (인터페이스)
│  └─ adapter/
│     ├─ in/web/                # OrderController
│     └─ out/
│        ├─ persistence/        # JPA 엔티티 · 리포지토리 구현
│        └─ pg/                 # PgPaymentAdapter (외부 HTTP)
├─ member/                      # 단순 CRUD — STR 02 처럼 평평하게
└─ notice/                      # 단순 CRUD

포트는 "바깥 시스템"에만

// order/application/port/out/PaymentPort.java
// 외부 PG 는 바뀔 수 있고 테스트에서 가짜가 필요 → 포트를 둡니다
public interface PaymentPort {
    PaymentResult pay(long orderId, long amount);
}

// order/adapter/out/pg/PgPaymentAdapter.java
@Component
class PgPaymentAdapter implements PaymentPort {   // 어댑터는 숨김
    private final RestClient pg;
    PgPaymentAdapter(RestClient.Builder builder) {
        this.pg = builder.baseUrl("https://pg.example.com").build();
    }
    @Override
    public PaymentResult pay(long orderId, long amount) {
        return pg.post().uri("/payments")
                 .body(new PayRequest(orderId, amount))
                 .retrieve().body(PaymentResult.class);
    }
}
DB 리포지토리에까지 포트를 둘지는 팀의 선택입니다. Spring Data 인터페이스가 이미 추상화라서, 작은 팀은 OrderRepository extends JpaRepository 를 응용 계층이 직접 쓰는 타협을 많이 합니다.
헥사고날의 값은 안쪽 원이 두꺼울 때만 나옵니다. 규칙이 없는 기능엔 원이 필요 없습니다.
비교기능별 평평 (STR 02)포트 · 어댑터
기능 하나의 파일 수3~5개 (컨트롤러 · 서비스 · 리포지토리 · 엔티티 · DTO)7~10개 (+ 포트 · 어댑터 · JPA 엔티티 · 매퍼)
도메인 단위 테스트엔티티에 JPA 애너테이션이 붙어 있어도 가능은 함순수 자바 — 스프링 컨텍스트 없이 밀리초
입구가 여러 개 (REST · Kafka · 배치)서비스를 그대로 재사용 — 대개 충분유스케이스 재사용이 명시적
외부 시스템 교체서비스 코드 여기저기를 고침어댑터 하나만 교체
어울리는 곳CRUD · 관리자 화면 · 작은 서비스결제 · 정산 · 주문처럼 규칙과 외부 연동이 많은 핵심 기능
과해지는 신호 — ① 구현이 하나뿐이고 바뀔 계획도 없는 인터페이스가 절반 이상 ② OrderUseCase 인터페이스와 OrderService 구현이 1:1 로만 존재 ③ 매퍼가 필드를 그대로 옮기기만 함. 셋 다면 그 기능은 STR 02 의 평평한 구조로 되돌려도 잃는 것이 없습니다.
정리 — 헥사고날은 프로젝트 전체가 아니라 기능 단위로 고릅니다. 포트는 바깥 시스템에만, 나머지는 기능별 평평 구조로 둡니다.
STR 04

멀티 모듈 Gradle — settings · 의존 방향 · build-logic · 버전 카탈로그

패키지 경계는 사람이 지키지만 모듈 경계는 컴파일러가 지킵니다. 의존을 선언하지 않은 모듈의 클래스는 import 자체가 안 되기 때문입니다. Gradle 기본 문법(스코프 · 의존성 충돌)은 도구 탭 TOOL 10 에 있고, 여기서는 모듈을 어떻게 나누고 어떻게 묶어 관리하는지를 봅니다.

폴더 모양

shop/
├─ settings.gradle.kts          # 모듈 목록 · build-logic 연결
├─ build.gradle.kts             # 거의 비어 있음
├─ gradle/libs.versions.toml    # 버전 카탈로그 — 버전은 여기에만
├─ build-logic/                 # 공통 빌드 설정 (convention plugin)
│  ├─ settings.gradle.kts
│  ├─ build.gradle.kts          # plugins { `kotlin-dsl` }
│  └─ src/main/kotlin/
│     └─ shop.java-conventions.gradle.kts
├─ common/          # 예외 · 시간 · ID — 아무것도 의존하지 않음
├─ core-domain/     # 엔티티 · 규칙 · 포트 인터페이스
├─ infra-db/        # JPA 구현 — core-domain 의 포트를 구현
├─ app-api/         # 실행 jar ① REST
└─ app-batch/       # 실행 jar ② 배치
// settings.gradle.kts

    includeBuild("build-logic")          // convention plugin 을 플러그인처럼 씀
}
dependencyResolutionManagement {
    repositories { mavenCentral() }      // 저장소는 여기 한 곳에서만
}
rootProject.name = "shop"
include("common", "core-domain", "infra-db", "app-api", "app-batch")

// build.gradle.kts (루트) — 플러그인 버전만 한 번 등록

    alias(libs.plugins.spring.boot) apply false

build-logic — 모든 모듈의 공통 설정을 플러그인 하나로

// build-logic/settings.gradle.kts
dependencyResolutionManagement {
    repositories { gradlePluginPortal(); mavenCentral() }
    versionCatalogs { create("libs") { from(files("../gradle/libs.versions.toml")) } }
}
rootProject.name = "build-logic"

// build-logic/src/main/kotlin/shop.java-conventions.gradle.kts
plugins { java }

java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }

val libs = the<VersionCatalogsExtension>().named("libs")
dependencies {
    // 모든 모듈이 같은 Boot BOM 으로 버전을 맞춥니다 (Boot 플러그인이 없는 모듈도)
    implementation(platform(libs.findLibrary("spring-boot-dependencies").get()))
    testImplementation(libs.findLibrary("spring-boot-starter-test").get())
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}
tasks.withType<JavaCompile>().configureEach {
    options.compilerArgs.add("-parameters")   // Boot 플러그인 없는 모듈도 파라미터 이름 유지
}
tasks.withType<Test>().configureEach { useJUnitPlatform() }
모듈 그래프의 규칙은 하나 — 안정적인 쪽(core-domain)으로만 화살표가 향한다.

실행 모듈 — app-api/build.gradle.kts

plugins {
    id("shop.java-conventions")          // build-logic 의 공통 설정

}
dependencies {
    implementation(project(":core-domain"))

    implementation(libs.spring.boot.starter.webmvc)
}

// infra-db/build.gradle.kts — Boot 플러그인 없음 (일반 jar)
plugins { id("shop.java-conventions") }
dependencies {
    implementation(project(":core-domain"))
    implementation(libs.spring.boot.starter.data.jpa)
}

자주 걸리는 함정 세 가지

① Application 클래스 위치 — 부트는 @SpringBootApplication 이 있는 패키지 아래만 스캔하고 JPA 리포지토리·엔티티도 그 기준으로 찾습니다. com.shop.api.ApiApplication 이면 com.shop.infra 의 리포지토리를 못 찾습니다. → 실행 모듈의 Application 은 공통 최상위 패키지 com.shop 에 둡니다.
② 라이브러리 모듈에 Boot 플러그인 — bootJar 가 생기고 일반 jar 가 꺼져 다른 모듈이 의존할 수 없게 됩니다. Boot 플러그인은 실행 모듈에만.
③ 루트 build.gradle.kts 의 subprojects { } — 예전 방식입니다. 모듈이 무엇을 받는지 그 모듈 파일만 봐서는 알 수 없고 구성 캐시와도 잘 안 맞습니다. Gradle 공식 문서도 convention plugin(build-logic) 을 권합니다.
모듈의존해도 되는 것금지
commonJDK 만다른 모든 모듈 — 아래로 가장 많이 깔리는 모듈이라 바뀌면 전부 다시 빌드
core-domaincommoninfra-* · app-* · spring-boot-starter-webmvc
infra-dbcore-domain · common · JPAapp-* · 다른 infra-*
app-*core-domain · common · infra-* (가능하면 runtimeOnly)다른 app-* — 공유할 것이 있으면 core 로 내립니다
정리 — 모듈은 의존 화살표가 core-domain 으로만 모이게 나누고, 공통 설정은 build-logic 의 convention plugin, 버전은 libs.versions.toml 한 곳에 둡니다. (Maven 이면 부모 POM 의 <modules> 와 <dependencyManagement> 가 같은 역할입니다.)
STR 05

설정 · 리소스 구조 — 프로필 · 프로퍼티 클래스 · 시크릿

설정 파일은 코드보다 환경마다 다르게 바뀌는 것을 담습니다. 그래서 "공통 기본값 + 환경별 차이"로 나누고, 비밀번호는 저장소 밖에서 들어오게 하는 것이 구조의 전부입니다.

리소스 폴더

app-api/src/main/resources/
├─ application.yml            # 모든 환경 공통 기본값
├─ application-local.yml      # 내 PC — H2 · SQL 로그
├─ application-prod.yml       # 운영과의 "차이"만 · 비밀번호 없음
├─ log4j2-spring.xml          # 로그 설정 (TOOL 02) — -spring 접미사
├─ db/migration/V1__init.sql  # Flyway 마이그레이션
├─ static/ · templates/       # 정적 파일 · 서버 렌더링 템플릿
└─ META-INF/additional-spring-configuration-metadata.json
app-api/src/test/resources/
└─ application-test.yml       # 테스트 전용
config/                       # 운영 서버의 jar 옆 — 저장소에 없음
└─ application-prod.yml       # 운영자가 재빌드 없이 덮어씀
라이브러리 모듈에 application.yml 을 두지 마세요 — 클래스패스에 같은 이름이 둘이면 하나만 읽히고 나머지는 조용히 무시됩니다. 모듈 기본값은 infra-db.yml 처럼 다른 이름으로 두고 실행 모듈에서 spring.config.import: classpath:infra-db.yml 로 가져옵니다.

@ConfigurationProperties 는 쓰는 기능 옆에

// order/PaymentProperties.java — 주문 기능만 쓰므로 order 패키지에
@ConfigurationProperties("shop.payment")
public record PaymentProperties(URI baseUrl, Duration timeout, int maxRetries) {}

// ShopApplication.java — 최상위에서 한 번만 스캔 등록
@SpringBootApplication
@ConfigurationPropertiesScan
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}
# application.yml — 공통 기본값
shop:
  payment:
    base-url: https://pg-sandbox.example.com
    timeout: 3s
    max-retries: 2
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shop
    username: shop
    password: ${DB_PASSWORD}        # 값은 환경 변수로 — 저장소엔 이름만

# application-prod.yml — 운영 차이만
shop:
  payment:
    base-url: https://pg.example.com
여러 기능이 같이 쓰는 설정(예: 공통 HTTP 타임아웃)만 common/config/ 로 올립니다. config/ 패키지에 프로퍼티 클래스 50개를 모아 두면 계층별 패키지와 같은 문제가 생깁니다.
저장소에는 아래 두 칸만 들어갑니다. 위 세 칸은 배포 환경이 채웁니다.
❌ 비밀번호가 저장소에
# application-prod.yml (커밋됨)
spring:
  datasource:
    password: Sh0p!2026      # git 히스토리에 영원히 남습니다
✅ 이름만 저장소에, 값은 밖에서
spring:
  config:
    import: "optional:configtree:/run/secrets/"   # K8s · Docker 시크릿 파일
  datasource:
    password: ${DB_PASSWORD}                      # 또는 환경 변수
정리 — application.yml 은 공통 기본값, application-{profile}.yml 은 차이만, 비밀은 환경 변수·시크릿 파일로. 프로퍼티 클래스는 쓰는 기능 패키지 옆에 둡니다.
STR 06

테스트 구조 — 단위 · 슬라이스 · 통합과 testFixtures

테스트 폴더는 운영 코드의 패키지를 거울처럼 따라갑니다. 멀티 모듈이 되면 새 문제가 하나 생깁니다 — 테스트용 데이터 빌더와 Testcontainers 설정을 모듈끼리 어떻게 나눠 쓰나. 답은 Gradle 의 java-test-fixtures 플러그인입니다. 도구 자체(JUnit · Mockito · Testcontainers 코드)는 도구 탭 TOOL 09 · TOOL 12 에 있습니다.

어떤 테스트를 어느 모듈에

core-domain/src/test/java/com/shop/order/
└─ OrderTest.java               # 단위 — 스프링 없음 · 가장 많이
infra-db/
├─ src/test/java/com/shop/infra/
│  └─ OrderJpaRepositoryTest.java   # @DataJpaTest + 진짜 DB

└─ OrderFlowIT.java             # @SpringBootTest — 앱 전체 (적게)

단위없음 — new 로 만듦그 클래스가 있는 모듈 · 같은 패키지

    testFixturesApi(libs.spring.boot.testcontainers)
    testFixturesApi(libs.testcontainers.mysql)
}

// app-api/build.gradle.kts — 가져다 쓰는 쪽

    testImplementation(testFixtures(project(":infra-db")))
}

// app-api 의 통합 테스트 — 컨테이너 설정을 복사하지 않고 가져옴
@SpringBootTest

카탈로그의 libs.spring.boot.testcontainers · libs.testcontainers.mysql 는 별칭입니다. Testcontainers 1.x 와 2.x 는 모듈 artifact 이름이 다르니, 실제 좌표는 카탈로그 한 곳에서만 관리합니다.
모듈 구조가 좋으면 테스트 피라미드가 저절로 아래가 넓어집니다.

통합 테스트를 따로 돌리기 🟡 중급

// app-api/build.gradle.kts — JVM Test Suite 로 src/integrationTest/java 를 분리
testing {
    suites {
        register<JvmTestSuite>("integrationTest") {
            dependencies {
                implementation(project())
                implementation(platform(libs.spring.boot.dependencies))
                implementation(libs.spring.boot.starter.test)
                implementation(testFixtures(project(":infra-db")))
            }
            targets.all {
                testTask.configure { shouldRunAfter(tasks.named("test")) }
            }
        }
    }
}
tasks.named("check") { dependsOn(testing.suites.named("integrationTest")) }
  • ./gradlew test — 단위 · 슬라이스만, 개발 중 수시로 (수 초)
  • ./gradlew integrationTest — 컨테이너가 뜨는 것만
  • ./gradlew check — 둘 다, CI 에서
작은 프로젝트는 분리하지 않고 src/test 하나에 두고, 통합 테스트 이름을 *IT 로 끝내는 것만으로도 충분합니다. 분리는 통합 테스트 때문에 test 가 1분을 넘을 때 합니다. Boot 4 부터는 슬라이스 애너테이션이 기술별 테스트 스타터(예: spring-boot-starter-webmvc-test)로 나뉘었으니 모듈마다 필요한 것만 넣습니다.
정리 — 테스트는 운영 패키지를 거울처럼, 그 코드가 사는 모듈에 둡니다. 모듈 사이에 나눠 쓸 빌더·컨테이너 설정은 testFixtures 로 한 번만 만듭니다.
STR 07

한 저장소에 API · 배치 · 워커

실무 자바 서비스는 HTTP API 하나로 끝나지 않습니다. 밤에 도는 정산 배치, Kafka 메시지를 처리하는 워커가 붙습니다. 셋이 같은 도메인 규칙을 쓰면 한 저장소의 실행 모듈 셋으로, 규칙이 다르면 저장소를 나눕니다. 서비스를 나눌지 말지(MSA)는 확장 탭의 몫이고 여기서는 한 저장소 안의 모양만 봅니다.

실행 모듈 셋 + 공유 모듈

shop/
├─ settings.gradle.kts
├─ build-logic/
├─ apps/                         # 실행 모듈 = bootJar = 배포 단위
│  ├─ api/      → shop-api.jar      HTTP · 상시 3대
│  ├─ batch/    → shop-batch.jar    스케줄러가 밤에 1회 실행
│  └─ worker/   → shop-worker.jar   Kafka 컨슈머 · 2대
└─ modules/                      # 공유 모듈 = 일반 jar
   ├─ core-domain/
   ├─ infra-db/
   ├─ infra-kafka/
   └─ common/
// settings.gradle.kts — 폴더가 깊어도 경로 그대로
include(":apps:api", ":apps:batch", ":apps:worker")
include(":modules:core-domain", ":modules:infra-db",
        ":modules:infra-kafka", ":modules:common")

// apps/batch/build.gradle.kts
plugins {
    id("shop.java-conventions")
    alias(libs.plugins.spring.boot)
}
dependencies {
    implementation(project(":modules:core-domain"))
    runtimeOnly(project(":modules:infra-db"))
}
tasks.bootJar { archiveFileName = "shop-batch.jar" }

웹 서버가 필요 없는 앱

# apps/worker/src/main/resources/application.yml
spring:
  main:
    web-application-type: none   # 톰캣을 띄우지 않음 — 포트 충돌 · 메모리 절약
  application:
    name: shop-worker
규칙이유
실행 모듈 1개 = jar 1개 = 배포 단위 1개"무엇을 배포하나"가 폴더 이름으로 보입니다
실행 모듈끼리 의존 금지api 가 batch 를 의존하면 배치 클래스가 API 서버에 실려 갑니다
스키마 마이그레이션은 한 곳Flyway 는 하나의 앱(보통 api)이나 별도 migration 작업이 소유 — 셋이 동시에 돌리면 경합
CI 는 바뀐 앱만./gradlew :apps:api:bootJar — 다만 core 가 바뀌면 셋 다 대상
초록 셋이 배포 단위, 붉은 가운데가 공유 비용입니다.

모노레포냐 멀티 레포냐 🟡 중급

STR 08

JavaFX 데스크톱 앱 — MVVM 패키지와 리소스 자리

JavaFX 화면 · FXML · 백그라운드 작업 · jpackage 배포는 JavaFX 탭(FXML 섹션 · 배포 섹션)에 있습니다. 여기서는 화면이 스무 개가 넘어도 길을 잃지 않는 폴더 모양만 봅니다. 원칙은 웹과 같습니다 — 기능별로 묶고, 화면은 바깥에.

기능별 + MVVM

desk-app/
├─ build.gradle.kts                 # javafx 플러그인 · jlink/jpackage 설정
├─ src/main/java/
│  ├─ module-info.java              # 패키지 없이 소스 루트에
│  └─ com/example/desk/
│     ├─ App.java                   # Application — 창 · 화면 전환만
│     ├─ order/
│     │  ├─ OrderController.java    # FXML 컨트롤러 = View (얇게)
│     │  └─ OrderViewModel.java     # 상태 · 명령 — Property 만, Node 없음
│     ├─ settings/
│     ├─ core/                      # 도메인 · 서비스 — JavaFX import 0
│     └─ infra/                     # HTTP 클라이언트 · 로컬 DB · 설정 파일
├─ src/main/resources/com/example/desk/
│  ├─ order/OrderView.fxml          # 컨트롤러와 같은 패키지 경로
│  ├─ order/order.css
│  └─ app.css · icons/
└─ build/                           # jlink 이미지 · jpackage 설치본 (커밋 금지)

module-info.java — FXML 이 리플렉션을 쓰는 자리만 열기

module com.example.desk {
    requires javafx.controls;
    requires javafx.fxml;
    requires java.net.http;

    opens com.example.desk.order to javafx.fxml;       // @FXML 필드 주입
    opens com.example.desk.settings to javafx.fxml;    // 화면 패키지마다 한 줄
    exports com.example.desk to javafx.graphics;       // App 을 런처가 생성
}
// order/OrderViewModel.java — 화면 없이 JUnit 으로 테스트할 수 있음
public final class OrderViewModel {
    private final StringProperty keyword = new SimpleStringProperty("");
    private final ObservableList<OrderRow> rows = FXCollections.observableArrayList();
    private final OrderService service;          // core 의 서비스

    public OrderViewModel(OrderService service) { this.service = service; }

    public StringProperty keywordProperty() { return keyword; }
    public ObservableList<OrderRow> rows() { return rows; }

    public void search() {                       // 느린 호출이면 Task 로 (JavaFX 탭)
        rows.setAll(service.search(keyword.get()));
    }
}
getClass().getResource("OrderView.fxml") 는 클래스와 같은 패키지 경로에서 찾습니다. FXML 을 resources/fxml/ 한 폴더에 몰아 두면 경로 문자열이 화면마다 늘고, 모듈 캡슐화에도 걸리기 쉽습니다.
데스크톱도 화면은 가장 바깥. 화면 코드가 얇을수록 테스트가 쉬워집니다.
무엇어디에
FXML · 화면별 CSSsrc/main/resources/ 아래 컨트롤러와 같은 패키지 경로
앱 전체 CSS · 아이콘 · 폰트최상위 패키지 경로 (com/example/desk/app.css)
사용자 설정 · 로컬 DB 파일jar 안이 아니라 사용자 홈 (%APPDATA% · ~/.config) — 설치 폴더는 쓰기 금지일 수 있음
설치본 아이콘 · 라이선스src/main/packaging/ 같은 별도 폴더 — 런타임 리소스와 섞지 않음
정리 — 데스크톱 앱도 기능별 패키지 + View/ViewModel 분리, FXML 은 컨트롤러와 같은 경로, 화면 패키지마다 opens … to javafx.fxml 한 줄입니다.
STR 09

라이브러리 구조 — 공개 API · internal · exports · BOM

앱은 내가 고치면 끝이지만 라이브러리는 남이 이미 쓰고 있는 것을 고칩니다. 그래서 구조의 목적이 바뀝니다 — "어디까지가 약속이냐"를 패키지로 보이게 하는 것. JPMS 문법 전체는 깊이 탭 DEEP 17 에 있습니다.

약속하는 곳과 안 하는 곳

acme-pay/                          # 라이브러리 저장소
├─ settings.gradle.kts
├─ acme-pay-bom/                   # java-platform — 버전 묶음
├─ acme-pay-core/
│  └─ src/main/java/
│     ├─ module-info.java          # exports com.acme.pay.api
│     └─ com/acme/pay/
│        ├─ api/                   # 공개 — 하위 호환을 약속
│        ├─ spi/                   # 확장 지점 — 사용자가 구현
│        └─ internal/              # 비공개 — 언제든 바뀜
├─ acme-pay-spring-boot-starter/   # 자동 설정 (선택)
└─ acme-pay-test/                  # 사용자용 테스트 도우미 · 가짜 구현
// acme-pay-core/src/main/java/module-info.java
module com.acme.pay {
    exports com.acme.pay.api;
    exports com.acme.pay.spi;
    // com.acme.pay.internal 은 exports 하지 않음
}

실측 — internal 을 쓰려 하면 (JDK 25.0.1)

# ① 모듈패스로 컴파일 — 막힘
$ javac -p pay/out -d app/out ...
Main.java:3: error: package com.acme.pay.internal is not visible
  (package com.acme.pay.internal is declared in module com.acme.pay,
   which does not export it)

# ② 같은 jar 를 클래스패스로 — 그냥 됨
$ javac -cp pay/out -d app/out Main.java
$ java -cp "pay/out;app/out" com.shop.Main
300
exports 는 모듈패스에서만 지켜집니다. 스프링 부트 앱을 포함한 대부분의 사용자는 클래스패스로 쓰므로, 패키지 이름 internal 자체가 경고판이 되어야 합니다. 문서에도 "internal 은 호환 대상 아님"을 적습니다.
module-info 를 아직 못 넣는다면 최소한 jar 매니페스트에 자동 모듈 이름을 고정하세요 — tasks.jar { manifest { attributes("Automatic-Module-Name" to "com.acme.pay") } }. 안 넣으면 jar 파일 이름에서 추측한 이름이 사용자 module-info 에 박힙니다.
자바의 가시성은 세 겹(접근 제어자 · 패키지 · 모듈) — 사용자가 어떻게 싣느냐에 따라 마지막 겹이 사라집니다.

멀티 모듈 라이브러리의 BOM

정리 — 라이브러리는 api · spi · internal 세 패키지로 약속의 범위를 드러내고, module-info 의 exports 와 이름 둘 다로 막습니다. 모듈이 여럿이면 BOM 으로 버전을 묶습니다.
STR 10

한 장 요약 — 규모 · 유형별 권장 구조와 ArchUnit 으로 강제하기

ArchUnit — 구조 규칙을 테스트로 🟡 중급

// app-api/src/test/java/com/shop/ArchitectureTest.java
package com.shop;

import com.tngtech.archunit.core.importer.ImportOption;
import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;
import static com.tngtech.archunit.library.Architectures.layeredArchitecture;
import static com.tngtech.archunit.library.dependencies.SlicesRuleDefinition.slices;

@AnalyzeClasses(packages = "com.shop",
                importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {

    // ① 기능 패키지끼리 순환 금지 — order → member → order 면 실패
    @ArchTest
    static final ArchRule 기능_사이_순환_금지 =
        slices().matching("com.shop.(*)..").should().beFreeOfCycles();

    // ② 계층 방향 — web → application → domain 만 허용
    @ArchTest
    static final ArchRule 계층_방향 = layeredArchitecture()
        .consideringOnlyDependenciesInLayers()
        .layer("Web").definedBy("..web..")
        .layer("Application").definedBy("..application..")
        .layer("Domain").definedBy("..domain..")
        .whereLayer("Web").mayNotBeAccessedByAnyLayer()
        .whereLayer("Application").mayOnlyBeAccessedByLayers("Web")
        .whereLayer("Domain").mayOnlyBeAccessedByLayers("Application", "Web");

    // ③ 컨트롤러가 리포지토리를 직접 부르지 않기 (기능별 평평 구조에도 적용)
    @ArchTest
    static final ArchRule 컨트롤러는_리포지토리_직접_금지 =
        noClasses().that().haveSimpleNameEndingWith("Controller")
            .should().dependOnClassesThat().haveSimpleNameEndingWith("Repository");

    // ④ 다른 기능의 internal 패키지 금지 — 기능마다 한 줄
    @ArchTest
    static final ArchRule 주문_internal_은_주문만 =
        noClasses().that().resideOutsideOfPackage("com.shop.order..")
            .should().dependOnClassesThat().resideInAPackage("com.shop.order.internal..");
}

어디에 두고 어떻게 돌리나

// app-api/build.gradle.kts — 실행 모듈의 테스트에 (모든 모듈 클래스가 보이는 곳)
dependencies {
    testImplementation(libs.archunit.junit5)
}

  • 이미 위반이 많은 기존 프로젝트는 FreezingArchRule.freeze(규칙) 로 현재 위반을 기록해 두고 새 위반만 막습니다.
ArchUnit 은 외부 의존성이라 실행하지 않았고 API 는 1.4 사용자 가이드 기준입니다. 도메인이 스프링을 모르게 하는 규칙은 DEEP 16 에 있습니다.
