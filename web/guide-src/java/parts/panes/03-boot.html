BOOT 01

스프링 부트가 하는 일

“왜 이렇게 편한가”를 먼저 알면 나중에 안 될 때 어디를 봐야 할지 알게 됩니다.

① 객체를 대신 만들고 연결한다 (DI)

❌ 직접 만들면
var repo = new OrderRepository(dataSource);
var mailer = new EmailNotifier(smtpConfig);
var service = new OrderService(repo, mailer);
var controller = new OrderController(service);
// 하나 바뀌면 줄줄이 고쳐야 한다
✅ 스프링이 하면
@Service
public class OrderService {
    private final OrderRepository repo;
    private final Notifier notifier;

    // 생성자만 만들어 두면 스프링이 알아서 넣어 준다
    public OrderService(OrderRepository repo, Notifier notifier) {
        this.repo = repo;
        this.notifier = notifier;
    }
}

② 흔한 설정을 미리 해 둔다 (자동 설정)

spring-boot-starter-web 하나를 넣으면 톰캣 서버 · JSON 변환기 · 에러 페이지 · 정적 리소스 처리가 전부 딸려옵니다. spring-boot-starter-data-jpa를 넣으면 DataSource · 커넥션 풀 · 트랜잭션 매니저 · EntityManager가 자동으로 준비됩니다.

스타터의 뜻 — “이 기능에 필요한 라이브러리 묶음 + 자동 설정”. 버전도 서로 맞는 조합으로 고정돼 있어서 버전 충돌을 신경 쓸 필요가 없습니다.

③ 서버를 내장한다

@SpringBootApplication          // 이 한 줄이 아래 셋을 합친 것
// = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

WAR 를 만들어 톰캣에 올리던 시절과 달리, jar 하나에 서버가 들어 있어 java -jar app.jar 로 끝납니다.

요청이 흘러가는 길

▼

BOOT 03

DI · Bean · 스코프

스프링의 심장입니다. “내가 new 하지 않는다”는 것 하나만 이해하면 됩니다.

빈으로 등록하는 방법

// 1) 스테레오타입 애너테이션 — 가장 흔함
@Component      // 일반적인 빈
@Service        // 비즈니스 로직 (의미만 다름)
@Repository     // DB 접근 (예외 변환 기능이 덤으로)
@Controller     // 웹 (뷰 반환)
@RestController // 웹 (JSON 반환) = @Controller + @ResponseBody

// 2) @Configuration + @Bean — 외부 라이브러리 객체를 등록할 때
@Configuration
public class AppConfig {

    @Bean
    public RestClient restClient() {
        return RestClient.builder()
                .baseUrl("https://api.example.com")
                .build();
    }

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
                .registerModule(new JavaTimeModule())
                .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
    }
}

주입 방법 — 생성자 주입만 쓰세요

❌ 필드 주입 — 편하지만 문제가 많다
@Service
public class OrderService {
    @Autowired private OrderRepository repo;   // ❌
}
// · 테스트에서 가짜 객체를 넣기 어렵다
// · final 을 못 써서 나중에 바뀔 수 있다
// · 순환 참조가 있어도 실행될 때까지 모른다
✅ 생성자 주입
@Service
@RequiredArgsConstructor          // Lombok — final 필드로 생성자 자동 생성
public class OrderService {
    private final OrderRepository repo;
    private final Notifier notifier;
}
// · final 보장 (불변)
// · 테스트에서 new OrderService(mockRepo, mockNotifier)
// · 순환 참조는 시작할 때 바로 에러 ✅
// · 생성자가 하나면 @Autowired 도 생략 가능

같은 타입 빈이 여러 개일 때

public interface Notifier { void send(String to, String msg); }

@Component("email") class EmailNotifier implements Notifier { }
@Component("sms")   class SmsNotifier implements Notifier { }

// 1) 이름으로 지정
public OrderService(@Qualifier("email") Notifier notifier) { }

// 2) 기본값 지정
@Component @Primary
class EmailNotifier implements Notifier { }

// 3) 전부 받기 — 전략 패턴에서 유용
@Service
public class NotifyService {
    private final List<Notifier> all;              // 전부 주입
    private final Map<String, Notifier> byName;    // 빈 이름이 키

    public void broadcast(String msg) {
        all.forEach(n -> n.send("all", msg));
    }
}

BOOT 04

자동 설정의 원리

“마법”이 아니라 조건부 설정입니다. 원리를 알면 “왜 내 설정이 안 먹지?”를 스스로 풀 수 있습니다.

동작 방식

// 스프링 부트 내부의 자동 설정 클래스는 대략 이렇게 생겼습니다
@AutoConfiguration
@ConditionalOnClass(DataSource.class)         // 이 클래스가 클래스패스에 있고
@ConditionalOnMissingBean(DataSource.class)   // 내가 직접 만든 게 없으면
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}

핵심은 @ConditionalOnMissingBean 입니다 — 내가 직접 빈을 등록하면 자동 설정은 물러납니다. “설정을 바꾸고 싶으면 그냥 만들어라”가 스프링 부트의 방식입니다.

무엇이 적용됐는지 확인하기

# application.yml — 시작할 때 리포트 출력
debug: true
============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:            ← 적용된 것
-----------------
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found 'javax.sql.DataSource'

Negative matches:            ← 적용 안 된 것 + 이유 ★
-----------------
   RedisAutoConfiguration:
      Did not match:
      - @ConditionalOnClass did not find 'RedisOperations'
“왜 안 되지?”의 90%는 이 리포트의 Negative matches 에 답이 있습니다. 의존성이 없거나, 내가 만든 빈이 이미 있거나, 프로퍼티 조건이 안 맞는 것입니다.
특정 자동 설정을 끄려면: @SpringBootApplication(exclude = SecurityAutoConfiguration.class)

BOOT 06

REST 컨트롤러

컨트롤러가 할 일은 셋뿐입니다 — 요청 받기 · 서비스 호출 · 응답 만들기. 로직은 절대 두지 마세요.

@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    // 목록 — GET /api/orders?status=PAID&page=0&size=20
    @GetMapping
    public Page<OrderRes> list(
            @RequestParam(required = false) OrderStatus status,
            @PageableDefault(size = 20, sort = "createdAt",
                             direction = Sort.Direction.DESC) Pageable pageable) {
        return orderService.search(status, pageable);
    }

    // 단건 — GET /api/orders/1
    @GetMapping("/{id}")
    public OrderRes get(@PathVariable Long id) {
        return orderService.get(id);
    }

    // 생성 — POST /api/orders
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)               // 201
    public OrderRes create(@Valid @RequestBody OrderCreateReq req) {
        return orderService.create(req);
    }

    // 수정 — PATCH /api/orders/1
    @PatchMapping("/{id}")
    public OrderRes update(@PathVariable Long id,
                           @Valid @RequestBody OrderUpdateReq req) {
        return orderService.update(id, req);
    }

    // 삭제 — DELETE /api/orders/1
    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)            // 204
    public void delete(@PathVariable Long id) {
        orderService.delete(id);
    }

    // 헤더 · 쿠키도 받을 수 있다
    @PostMapping("/{id}/pay")
    public ResponseEntity<OrderRes> pay(
            @PathVariable Long id,
            @RequestHeader("X-Idempotency-Key") String key,
            @CookieValue(required = false) String sessionId) {

        OrderRes res = orderService.pay(id, key);
        return ResponseEntity.ok()
                .header("X-Processed-At", Instant.now().toString())
                .body(res);
    }
}

요청 · 응답 · DTO

엔티티를 그대로 주고받지 마세요. 이 한 가지 원칙이 나중에 생길 사고의 절반을 막습니다.

❌ 엔티티를 그대로 노출
@GetMapping("/{id}")
public User get(@PathVariable Long id) {
    return userRepository.findById(id).orElseThrow();
}

public record UserRes(Long id, String name, String email) {
    public static UserRes from(User u) {
        return new UserRes(u.getId(), u.getName(), u.getEmail());

}

@GetMapping("/{id}")
public UserRes get(@PathVariable Long id) {
    return UserRes.from(userService.get(id));

public record UserRes(
        Long id,

        @JsonProperty("user_name")          // JSON 키 이름 바꾸기
        String name,

        @JsonIgnore                          // 응답에서 제외
        String password,

  jackson:

    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};

public class DateRangeValidator
        implements ConstraintValidator<ValidDateRange, SearchReq> {
    @Override
    public boolean isValid(SearchReq r, ConstraintValidatorContext ctx) {
        if (r.from() == null || r.to() == null) return true;
        return !r.to().isBefore(r.from());
    }
}

전역 예외 처리

컨트롤러마다 try/catch 를 쓰지 마세요. 한 곳에서 전부 받아 일관된 형식으로 응답하는 것이 정석입니다.

전체 구성 — 이대로 복사해서 쓰면 됩니다

// 1) 에러 응답 형식 — 프론트엔드와 약속
public record ErrorResponse(
        String code,
        String message,
        List<FieldError> errors,
        String path,
        Instant timestamp
) {
    public record FieldError(String field, String reason) { }

    public static ErrorResponse of(ErrorCode c, String path) {
        return new ErrorResponse(c.getCode(), c.getMessage(), List.of(), path, Instant.now());
    }
}

// 2) 전역 핸들러
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    // 우리가 정의한 비즈니스 예외
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(
            BusinessException e, HttpServletRequest req) {
        ErrorCode c = e.getCode();
        log.warn("비즈니스 예외: {} - {}", c.getCode(), e.getMessage());
        return ResponseEntity.status(c.getStatus())
                .body(ErrorResponse.of(c, req.getRequestURI()));
    }

    // @Valid 실패 — 어느 필드가 왜 틀렸는지 담아 준다 ★
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(
            MethodArgumentNotValidException e, HttpServletRequest req) {

        List<ErrorResponse.FieldError> fields = e.getBindingResult()
                .getFieldErrors().stream()
                .map(f -> new ErrorResponse.FieldError(f.getField(), f.getDefaultMessage()))
                .toList();

        return ResponseEntity.badRequest().body(new ErrorResponse(
                "V001", "입력값이 올바르지 않습니다", fields,
                req.getRequestURI(), Instant.now()));
    }

    // 타입이 안 맞을 때 (예: /orders/abc)
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public ResponseEntity<ErrorResponse> handleTypeMismatch(
            MethodArgumentTypeMismatchException e, HttpServletRequest req) {
        return ResponseEntity.badRequest().body(new ErrorResponse(
                "V002", "'%s' 값의 형식이 올바르지 않습니다".formatted(e.getName()),
                List.of(), req.getRequestURI(), Instant.now()));
    }

    // 마지막 방어선 — 예상 못 한 모든 것
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAll(Exception e, HttpServletRequest req) {
        log.error("처리되지 않은 예외", e);            // ★ 스택 트레이스는 반드시 로그로
        return ResponseEntity.internalServerError().body(new ErrorResponse(
                "E999", "서버 오류가 발생했습니다",   // ★ 내부 정보는 노출하지 않는다
                List.of(), req.getRequestURI(), Instant.now()));
    }
}

BOOT 10

계층 설계

각 층이 무엇을 하고 무엇을 하지 않는지가 명확해야 프로젝트가 커져도 안 무너집니다.

계층해야 할 일하면 안 되는 일
Controller HTTP 매핑, 요청 검증, DTO ↔ 서비스 호출, 상태 코드 결정 비즈니스 로직, DB 접근, 트랜잭션
Service 비즈니스 규칙, 트랜잭션 경계, 여러 리포지토리 조합 HTTP 관련 코드(HttpServletRequest), SQL 직접 작성
Repository DB 접근, 쿼리 비즈니스 판단(“이 주문은 취소 가능한가”)
Domain 상태와 그 상태를 바꾸는 규칙 프레임워크 의존

전체 흐름 예시

// ── Controller — 얇게 ──────────────────────────────
@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;

    @PostMapping("/{id}/pay")
    public OrderRes pay(@PathVariable Long id) {
        return orderService.pay(id);          // 그냥 넘긴다
    }
}

// ── Service — 규칙과 트랜잭션 ───────────────────────
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)               // 클래스 기본은 읽기 전용
public class OrderService {

    private final OrderRepository orderRepository;
    private final StockService stockService;
    private final Notifier notifier;

    @Transactional                             // 쓰기 메서드만 재정의
    public OrderRes pay(Long id) {
        Order order = orderRepository.findById(id)
                .orElseThrow(() -> new OrderNotFoundException(id));

        stockService.decrease(order.getProductId(), order.getQuantity());
        order.pay();                           // ← 상태 변경 규칙은 '도메인'에

        // 트랜잭션이 커밋된 뒤에 알림 (실패해도 주문은 유지)
        notifier.sendAfterCommit(order.getEmail(), "결제 완료");
        return OrderRes.from(order);           // 더티 체킹으로 자동 UPDATE
    }
}

// ── Domain — 규칙의 주인 ────────────────────────────
@Entity
public class Order {
    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    public void pay() {
        if (status != OrderStatus.CREATED) {
            throw new AlreadyPaidException(id);    // 규칙이 여기 있다
        }
        this.status = OrderStatus.PAID;
        this.paidAt = LocalDateTime.now();
    }

    public boolean isCancelable() {
        return status.cancelable();
    }
}
“서비스가 비대해진다”는 신호 — 한 서비스가 500줄이 넘거나 리포지토리를 5개 이상 주입받고 있다면 도메인이 나눠질 때입니다. 상태를 바꾸는 규칙을 엔티티 안으로 옮기면 서비스가 눈에 띄게 얇아집니다.

AOP · 트랜잭션 경계

“모든 메서드에 로그 남기기” 같은 가로지르는 관심사를 한 곳에 모으는 방법입니다.

AOP — 실행 시간 로깅 예제

@Aspect
@Component
@Slf4j
public class LoggingAspect {

    // 이 패키지 아래 모든 서비스 메서드
    @Around("execution(* com.myapp..*Service.*(..))")
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();                  // 원래 메서드 실행
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            if (ms > 500) {
                log.warn("느린 메서드: {} {}ms", pjp.getSignature().toShortString(), ms);
            }
        }
    }

    // 특정 애너테이션이 붙은 것만
    @Around("@annotation(com.myapp.common.LogExecutionTime)")
    public Object logAnnotated(ProceedingJoinPoint pjp) throws Throwable { ... }
}
애너테이션시점
@Before메서드 실행 전
@AfterReturning정상 반환 후
@AfterThrowing예외 발생 시
@After무조건 (finally)
@Around전후 모두 — 가장 많이 씁니다

⚠️ 프록시의 한계 — 자기 호출은 안 먹는다

❌ 트랜잭션이 안 걸립니다

public class OrderService {

    public void process() {
        save();          // ← this.save() 라서 프록시를 안 거침!

    @Transactional

✅ 해결책
// 1) 클래스를 분리한다 (권장)
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderSaver saver;      // 다른 빈이므로 프록시를 거침
    public void process() { saver.save(); }
}

// 2) 호출하는 쪽 메서드에 붙인다
@Transactional
public void process() { save(); }

// 3) 자기 자신을 주입 (임시방편)
// ⚠️ @RequiredArgsConstructor 는 필드의 @Lazy 를 생성자 파라미터로
//    복사하지 않아 그냥은 순환 참조로 실패합니다. lombok.config 에
//    lombok.copyableAnnotations += org.springframework.context.annotation.Lazy
//    를 넣거나, 생성자를 직접 작성해 파라미터에 @Lazy 를 붙이세요.
@Lazy private final OrderService self;
public void process() { self.save(); }

@PostMapping(value = "/upload",
             consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public UploadRes upload(@RequestPart("file") MultipartFile file,
                        @RequestPart("meta") @Valid MetaReq meta) {

    if (file.isEmpty()) throw new BadRequestException("파일이 비어 있습니다");

    // 확장자 검증 — 파일명만 믿지 말 것
    String name = StringUtils.cleanPath(
            Objects.requireNonNull(file.getOriginalFilename()));
    if (name.contains("..")) throw new BadRequestException("잘못된 경로");

    String ext = StringUtils.getFilenameExtension(name);
    if (!List.of("xlsx", "csv", "png", "jpg").contains(ext)) {
        throw new BadRequestException("허용되지 않는 형식입니다");
    }

    // 저장 — 원본 이름을 그대로 쓰지 말 것 (덮어쓰기·경로 조작 방지)
    String saved = UUID.randomUUID() + "." + ext;
    Path target = uploadDir.resolve(saved);
    file.transferTo(target);

    return new UploadRes(saved, file.getSize());
}

@GetMapping("/download/{id}")
public ResponseEntity<Resource> download(@PathVariable Long id) {
    FileMeta meta = fileService.get(id);

@Service
@RequiredArgsConstructor
public class OrderService {
    private final MeterRegistry registry;

    public void pay(Long id) {
        Timer.Sample sample = Timer.start(registry);
        try {
            doPay(id);
            registry.counter("order.pay", "result", "success").increment();
        } catch (Exception e) {
            registry.counter("order.pay", "result", "fail").increment();
            throw e;
        } finally {
            sample.stop(registry.timer("order.pay.time"));
        }
    }
}

배포 전 체크리스트

  • ✅ ddl-auto: validate — update·create 는 절대 금지
  • ✅ 비밀번호·키가 환경 변수로 빠져 있나
  • ✅ server.shutdown: graceful — 처리 중 요청 보호
  • ✅ Actuator 가 외부에 열려 있지 않은지
  • ✅ 로그 레벨이 운영은 INFO (DEBUG 는 디스크를 태웁니다)
  • ✅ 타임존 -Duser.timezone=Asia/Seoul
  • ✅ 헬스 체크 경로를 LB 에 등록
  • ✅ 힙 덤프 경로 설정 (OOM 원인 분석용)
  • ✅ DB 커넥션 풀 크기 ↔ 서버 대수 확인
무중단 배포는 graceful 종료 + readiness 프로브 조합이 기본입니다. 새 인스턴스가 /actuator/health/readiness 에서 UP 을 반환한 뒤에 트래픽을 옮기고, 옛 인스턴스는 처리 중인 요청을 마치고 내려가게 합니다.
BOOT 17

쿠버네티스 · 무중단 배포

대기업 배포는 거의 다 K8s 입니다. 애플리케이션이 지켜야 할 약속이 몇 가지 있습니다.

두 가지 프로브 — 역할이 다릅니다

프로브실패하면
liveness
살아 있나?		파드를 죽이고 재시작합니다. 여기에 DB 검사를 넣으면 DB 가 잠깐 흔들릴 때 전 파드가 재시작합니다 — 넣지 마세요
readiness
받을 준비 됐나?		트래픽만 끊고 재시작은 안 합니다. DB·Redis 의존성은 여기에 넣습니다
startup기동이 느린 앱을 위해 초기에만 여유를 줍니다
# application.yml — 부트가 두 엔드포인트를 만들어 줍니다
management:
  endpoint:
    health:
      probes:
        enabled: true          # /actuator/health/liveness, /readiness
  health:
    livenessstate:  { enabled: true }
    readinessstate: { enabled: true }

server:
  shutdown: graceful           # ★ 처리 중인 요청을 끝내고 종료
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
# deployment.yaml
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 5
resources:
  requests: { cpu: "500m", memory: "1Gi" }    # 스케줄링 기준
  limits:   { cpu: "2",    memory: "2Gi" }    # 넘으면 OOMKilled

무중단 배포 — 끊기는 진짜 이유

파드 종료 순간 실제로 일어나는 일

  1. K8s 가 파드를 "종료 중"으로 표시
  2. 서비스 엔드포인트에서 제거   ┐ 이 둘은
  3. 컨테이너에 SIGTERM 전달      ┘ 동시에 일어납니다 (순서 보장 없음)

  → 3번이 먼저 오면, 아직 라우팅되는 상태에서 앱이 종료를 시작
  → 그 사이에 들어온 요청이 502 로 떨어집니다

해결: 종료 신호를 받고 몇 초 버틴 뒤에 실제 종료를 시작
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 5"] }   # ★ 엔드포인트 제거를 기다림
terminationGracePeriodSeconds: 60                 # graceful shutdown 보다 길게

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # 새 파드를 1개 더 띄우고
    maxUnavailable: 0    # ★ 기존 파드는 하나도 안 줄인다 = 무중단
배포할 때마다 잠깐 502 가 뜬다면 열에 아홉은 preStop 이 없거나 server.shutdown: graceful 이 빠진 것입니다. 스케일 인·노드 교체 때도 똑같이 일어나므로 반드시 넣으세요.

오토스케일 · 설정 주입

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 3          # ★ 2 이상 — 1이면 재시작 때 서비스가 멈춥니다
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300    # 급하게 줄이지 않기 (플래핑 방지)
설정과 비밀값은 이미지에 넣지 마세요. ConfigMap·Secret 을 환경 변수로 주입하면 스프링이 SPRING_DATASOURCE_PASSWORD 같은 이름을 자동으로 매핑합니다. 같은 이미지를 개발·스테이징·운영에 그대로 쓰는 게 원칙입니다. 서버가 여러 대가 된 뒤의 이야기는 ⚡ 대규모 트래픽 탭에서 이어집니다.
