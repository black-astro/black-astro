기술강점약점언제

MyBatis SQL 을 그대로 씀. 복잡한 통계·레거시 DB 에 강함 매핑을 전부 손으로. 컴파일 검사 없음 레거시 DB, 튜닝된 SQL 이 필요한 곳

R2DBC 논블로킹 연관관계·더티 체킹 없음 WebFlux 프로젝트 — 🌊 09번
실무에서 가장 흔한 조합 — Spring Data JPA (단순 CRUD) + QueryDSL (복잡한 조회) 입니다. 통계 리포트처럼 SQL 을 손으로 튜닝해야 하는 화면만 MyBatis 나 JdbcClient 로 따로 빼는 식으로 섞어 씁니다. 한 프로젝트에서 여러 개를 같이 쓰는 건 전혀 이상하지 않습니다.
DATA 02

DataSource · 커넥션 풀

DB 커넥션은 비싸고 개수가 정해진 자원입니다. 여기 설정이 잘못되면 서버가 통째로 멈춥니다.

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb?
         useSSL=false&serverTimezone=Asia/Seoul&
         characterEncoding=UTF-8&rewriteBatchedStatements=true
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 20        # 핵심 설정 ★
      minimum-idle: 10
      connection-timeout: 3000     # 커넥션을 못 얻으면 3초 후 실패
      idle-timeout: 600000         # 10분
      max-lifetime: 1740000        # 29분 (DB wait_timeout 보다 짧게!)
      leak-detection-threshold: 60000   # 60초 넘게 안 돌려주면 경고
      pool-name: HikariPool-main
max-lifetime 은 DB 의 wait_timeout 보다 짧아야 합니다. 안 그러면 DB 가 이미 끊은 커넥션을 풀이 계속 들고 있다가 Communications link failure 가 간헐적으로 터집니다.

풀 크기는 몇으로?

직관과 반대로 크게 잡을수록 느려집니다. DB 의 CPU·디스크가 병목이라 커넥션이 많으면 경합만 늘어납니다. 

권장 공식 (HikariCP 문서)
   pool_size = (코어 수 × 2) + 유효 디스크 수

예) 4코어 + SSD 1개 → 약 10
    대부분의 웹 서비스는 10~30 사이면 충분

⚠️ 서버 5대 × 풀 30 = DB 커넥션 150개
   DB 의 max_connections 를 넘으면 전체 장애
“커넥션 고갈”의 진짜 원인은 풀이 작아서가 아니라 커넥션을 오래 붙잡고 있어서입니다. 트랜잭션 안에서 외부 API 를 호출하고 있다면 그게 범인입니다 — 트랜잭션 밖으로 빼세요.

JPA 엔티티 매핑

엔티티는 DB 테이블과 이어진 객체입니다. 여기 설계가 나중을 좌우합니다.

@Entity
@Table(name = "orders",
       indexes = {
           @Index(name = "idx_order_no", columnList = "order_no", unique = true),
           @Index(name = "idx_user_status", columnList = "user_id, status")
       })
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)   // JPA 는 기본 생성자 필요
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // MySQL AUTO_INCREMENT
    private Long id;

    @Column(name = "order_no", nullable = false, unique = true, length = 30)
    private String orderNo;

    @Enumerated(EnumType.STRING)          // ★ ORDINAL 은 절대 금지
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Column(nullable = false)
    private int amount;

    @Column(columnDefinition = "TEXT")
    private String memo;

    @CreatedDate                          // Auditing
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @Version                              // 낙관적 락
    private Long version;

    // 생성은 정적 팩토리로 — 유효하지 않은 엔티티가 존재할 수 없게
    public static Order create(String orderNo, int amount) {
        Order o = new Order();
        o.orderNo = orderNo;
        o.amount = amount;
        o.status = OrderStatus.CREATED;
        return o;
    }

    // 상태 변경은 의미 있는 메서드로 (setter 를 열지 않는다)
    public void pay() {
        if (status != OrderStatus.CREATED) throw new AlreadyPaidException(id);
        this.status = OrderStatus.PAID;
    }
}

Auditing 켜기 — 생성·수정 시각 자동

엔티티 설계 원칙

  • ❌ @Setter를 열지 마세요 — 아무 데서나 상태가 바뀌면 규칙을 지킬 수 없습니다
  • ❌ @Data·@ToString 전체 적용 금지 — 연관 엔티티를 타고 가며 무한 순환·N+1이 납니다
  • ✅ @Enumerated(EnumType.STRING) — ORDINAL 은 enum 순서가 바뀌면 기존 데이터가 전부 틀어집니다
  • ✅ 기본 생성자는 PROTECTED — 아무나 빈 객체를 못 만들게
  • ✅ equals/hashCode 는 ID 기준으로만 (또는 아예 안 만들기)
  • ✅ 엔티티를 API 응답으로 쓰지 마세요 — DTO 로 변환
ddl-auto 는 운영에서 반드시 validate. update 는 컬럼을 지우지 못하고, create 는 테이블을 통째로 날립니다. 스키마 변경은 Flyway(15번)로 관리하세요.
DATA 05

연관관계 매핑

JPA 에서 가장 헷갈리는 부분입니다. 규칙 세 가지만 지키면 대부분 해결됩니다.

연관관계 3원칙
① 모든 연관관계는 LAZY — @ManyToOne 의 기본값이 EAGER 라서 반드시 바꿔야 합니다
② 연관관계의 주인은 외래 키를 가진 쪽(보통 @ManyToOne)
③ @OneToMany 는 꼭 필요할 때만 — 없어도 대부분 돌아갑니다

N:1 — 가장 많이 씁니다

@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)       // ★ 반드시 LAZY
    @JoinColumn(name = "user_id", nullable = false,
                foreignKey = @ForeignKey(name = "fk_order_user"))
    private User user;                        // orders 테이블에 user_id 컬럼
}

// 반대편(1:N)은 필요할 때만 추가
@Entity
public class User {
    @OneToMany(mappedBy = "user")             // mappedBy = 주인이 아님을 표시
    private List<Order> orders = new ArrayList<>();
}

1:N — 부모가 자식을 관리할 때

@Entity
public class Order {
    @OneToMany(mappedBy = "order",
               cascade = CascadeType.ALL,     // 부모 저장 시 자식도
               orphanRemoval = true)          // 목록에서 빼면 삭제
    private List<OrderItem> items = new ArrayList<>();

    // 양방향은 편의 메서드로 양쪽을 함께 세팅
    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);      // ★ 이걸 빠뜨리면 FK 가 null 로 저장됨
    }
}

1:1 과 N:M

// 1:1 — FK 를 가진 쪽이 주인
@Entity
public class User {
    @OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    @JoinColumn(name = "profile_id")
    private Profile profile;
}

// ⚠️ 1:1 의 '반대편'은 LAZY 가 안 먹습니다 (프록시를 못 만듦)
//    → 조회 시 항상 추가 쿼리가 나갑니다. 단방향으로 두는 게 안전합니다.

// N:M — @ManyToMany 는 쓰지 마세요 ★
// ❌ 중간 테이블에 컬럼을 못 넣고, 쿼리가 예측 불가
@ManyToMany
private List<Tag> tags;

// ✅ 중간 엔티티를 직접 만듭니다
@Entity
public class PostTag {
    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = LAZY) @JoinColumn(name = "post_id")
    private Post post;

    @ManyToOne(fetch = LAZY) @JoinColumn(name = "tag_id")
    private Tag tag;

    private LocalDateTime taggedAt;      // 추가 정보를 넣을 수 있다 ✅
}
양방향이 정말 필요한가? — user.getOrders() 를 실제로 쓰지 않는다면 단방향(@ManyToOne만)으로 두세요. 양방향은 동기화 실수·순환 참조·N+1 의 원천입니다. 목록이 필요하면 orderRepository.findByUserId(id) 로 충분합니다.
DATA 06

영속성 컨텍스트 — JPA 의 심장

“왜 save() 를 안 했는데 UPDATE 가 나가지?”의 답이 여기 있습니다.

엔티티의 4가지 상태

비영속
new 로 막 만든 상태JPA 가 모르는 객체. new Order()
영속
영속성 컨텍스트가 관리 중save() 했거나 findById() 로 꺼낸 것. 변경이 자동 추적됩니다
준영속
관리에서 떨어진 상태트랜잭션이 끝난 뒤. 변경해도 DB 에 안 반영됩니다
삭제
삭제 예약remove() 호출. 커밋 시 DELETE
@Transactional
public void changeName(Long id, String newName) {
    Order order = orderRepository.findById(id).orElseThrow();  // 영속 상태
    order.changeName(newName);
    // save() 를 부르지 않아도 커밋 시점에 UPDATE 가 나갑니다 ★ (더티 체킹)
}

@Transactional(readOnly = true)
public OrderRes get(Long id) {
    Order o = orderRepository.findById(id).orElseThrow();
    o.changeName("바꿔도");     // readOnly 라 UPDATE 안 나감
    return OrderRes.from(o);
}

영속성 컨텍스트가 해 주는 일

  • 1차 캐시 — 같은 트랜잭션에서 같은 ID 를 두 번 조회하면 쿼리가 한 번만 나갑니다
  • 동일성 보장 — 같은 ID 로 꺼낸 두 객체는 == 가 true
  • 변경 감지(더티 체킹) — 필드를 바꾸면 커밋 때 자동 UPDATE
  • 쓰기 지연 — INSERT 를 모았다가 커밋 시 한 번에
@Transactional
void demo() {
    Order a = repo.findById(1L).get();   // SELECT 발생
    Order b = repo.findById(1L).get();   // 쿼리 없음 (1차 캐시)
    System.out.println(a == b);          // true ✅
}

가장 흔한 사고 — LazyInitializationException

// ❌ 트랜잭션 밖에서 지연 로딩
public OrderRes get(Long id) {              // @Transactional 없음
    Order o = repo.findById(id).orElseThrow();
    return new OrderRes(o.getUser().getName());  // 💥 LazyInitializationException
}

// ✅ 해결 1 — 트랜잭션 안에서 DTO 로 변환
@Transactional(readOnly = true)
public OrderRes get(Long id) {
    Order o = repo.findById(id).orElseThrow();
    return OrderRes.from(o);       // 여기서 필요한 값을 다 꺼냄
}

// ✅ 해결 2 — 페치 조인으로 한 번에 (08번 참고)
@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE o.id = :id")
Optional<Order> findWithUser(Long id);
spring.jpa.open-in-view 는 false 로 두세요. 기본값 true 는 이 예외를 감춰 주지만, 대신 요청이 끝날 때까지 DB 커넥션을 붙잡습니다. 트래픽이 늘면 커넥션 고갈로 이어집니다.
DATA 07

쿼리 메서드 · JPQL

메서드 이름으로 안 되는 것은 직접 씁니다. JPQL 은 테이블이 아니라 엔티티를 대상으로 합니다.

public interface OrderRepository extends JpaRepository<Order, Long> {

    // JPQL — 엔티티 이름과 필드명을 씁니다 (테이블/컬럼 아님)
    @Query("""
        SELECT o FROM Order o
         WHERE o.status = :status
           AND o.amount >= :minAmount
         ORDER BY o.createdAt DESC
        """)
    List<Order> search(@Param("status") OrderStatus status,
                       @Param("minAmount") int minAmount);

    // DTO 로 바로 받기 (필요한 컬럼만 SELECT — 성능에 유리) ★
    @Query("""
        SELECT new com.myapp.order.dto.OrderSummary(o.id, o.orderNo, u.name, o.amount)
          FROM Order o JOIN o.user u
         WHERE o.createdAt >= :from
        """)
    List<OrderSummary> findSummaries(LocalDateTime from);

    // 네이티브 SQL — DB 고유 기능이 필요할 때
    @Query(value = """
        SELECT * FROM orders
         WHERE MATCH(memo) AGAINST(:kw IN BOOLEAN MODE)
        """, nativeQuery = true)
    List<Order> fullTextSearch(String kw);

    // 벌크 연산 — 한 번에 UPDATE/DELETE
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("UPDATE Order o SET o.status = :to WHERE o.status = :from")
    int bulkUpdateStatus(OrderStatus from, OrderStatus to);
}

프로젝션 — 필요한 것만 가져오기

N+1 문제 — 가장 많이 만나는 성능 사고

개발할 땐 멀쩡하다가 데이터가 쌓이면 갑자기 느려지는 문제의 1순위입니다.

❌ 쿼리가 101번 나갑니다
List<Order> orders = orderRepository.findAll();   // 쿼리 1번

for (Order o : orders) {
    System.out.println(o.getUser().getName());    // 주문마다 1번씩! (100번)
}
// 총 1 + 100 = 101번
SELECT * FROM orders;                    -- 1번
SELECT * FROM users WHERE id = 1;        -- N번
SELECT * FROM users WHERE id = 2;
SELECT * FROM users WHERE id = 3;
...
✅ 페치 조인 — 1번
@Query("SELECT o FROM Order o JOIN FETCH o.user")
List<Order> findAllWithUser();
SELECT o.*, u.*
  FROM orders o
  JOIN users u ON u.id = o.user_id;      -- 1번 ✅

JOIN 과 JOIN FETCH 는 다릅니다 — 그냥 JOIN 은 조건에만 쓰이고 데이터를 안 가져옵니다. JOIN FETCH 라야 함께 조회됩니다.

해결 방법 4가지

// 1) 페치 조인 — 가장 확실
@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE o.status = :s")
List<Order> findWithUser(OrderStatus s);

// 2) @EntityGraph — 메서드 이름 방식에도 붙일 수 있다
@EntityGraph(attributePaths = {"user", "items"})
List<Order> findByStatus(OrderStatus status);

// 3) batch size — 컬렉션에 특히 유용 ★
//    IN (1,2,3,...) 로 묶어서 조회 → 1 + (N/100) 번
//    application.yml:
//    spring.jpa.properties.hibernate.default_batch_fetch_size: 100

// 4) DTO 직접 조회 — 애초에 필요한 것만
@Query("""
    SELECT new com.myapp.dto.OrderSummary(o.id, u.name, o.amount)
      FROM Order o JOIN o.user u
    """)
List<OrderSummary> findSummaries();

⚠️ 컬렉션 페치 조인의 함정

// ❌ 1:N 을 페치 조인하면 행이 뻥튀기됩니다
@Query("SELECT o FROM Order o JOIN FETCH o.items")
List<Order> findAll();
// 주문 1개에 상품 3개 → 같은 주문이 3번 나옴

// ✅ 해결 1 — DISTINCT (Hibernate 6+ 는 자동)
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")

// ❌ 페이징이 안 됩니다! (메모리에서 페이징 → OOM 위험)
//    "firstResult/maxResults specified with collection fetch; applying in memory"

// ✅ 해결 2 — batch fetch size 를 쓰면 페이징이 됩니다 ★
//    ToOne 만 페치 조인하고, 컬렉션은 batch size 로
@Query("SELECT o FROM Order o JOIN FETCH o.user")
Page<Order> findAllWithUser(Pageable pageable);
// + default_batch_fetch_size: 100

// ⚠️ 컬렉션 페치 조인은 '하나만' 가능합니다
//    둘 이상이면 MultipleBagFetchException → Set 으로 바꾸거나 batch size

쿼리가 몇 번 나가는지 눈으로 보기

spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
        default_batch_fetch_size: 100      # ★ 이 한 줄이 N+1 의 대부분을 해결합니다
logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE     # 파라미터 값까지

# 더 편한 방법 — 쿼리 개수를 세어 주는 라이브러리
# implementation("com.github.gavlyukovskiy:datasource-proxy-spring-boot-starter:1.9.2")
실무 기본 세팅 — default_batch_fetch_size: 100 을 켜 두고, ToOne 연관은 페치 조인, 컬렉션은 batch size로 가는 조합이 페이징까지 되면서 N+1 도 막는 가장 무난한 방법입니다.

QueryDSL 동적 쿼리

검색 조건이 있을 수도 없을 수도 있을 때, 이만한 도구가 없습니다.

❌ 문자열로 조립하면
StringBuilder sql = new StringBuilder("SELECT o FROM Order o WHERE 1=1");
if (status != null)  sql.append(" AND o.status = :status");
if (from != null)    sql.append(" AND o.createdAt >= :from");
if (keyword != null) sql.append(" AND o.memo LIKE :kw");
// · 오타가 나도 컴파일은 통과, 실행할 때 터짐
// · 파라미터 바인딩도 따로 관리해야 함
// · 조건이 늘수록 손댈 수 없어짐
✅ QueryDSL
query.selectFrom(order)
     .where(statusEq(cond.status()),        // null 이면 자동으로 무시됨 ★
            createdAfter(cond.from()),
            memoContains(cond.keyword()))
     .fetch();

where() 에 넘긴 조건이 null 이면 그냥 빠집니다. 이 성질 하나로 동적 쿼리가 아주 깔끔해집니다.

전체 구현 — 검색 + 페이징

import static com.myapp.order.QOrder.order;
import static com.myapp.user.QUser.user;

@Repository
@RequiredArgsConstructor
public class OrderRepositoryImpl implements OrderRepositoryCustom {

    private final JPAQueryFactory query;

    @Override
    public Page<OrderSummary> search(OrderSearchCond cond, Pageable pageable) {

        // 1) 내용 조회
        List<OrderSummary> content = query
                .select(Projections.constructor(OrderSummary.class,   // DTO 로 바로
                        order.id, order.orderNo, user.name, order.amount, order.createdAt))
                .from(order)
                .join(order.user, user)                    // 페치 조인 아님 (DTO 라서 불필요)
                .where(
                        statusEq(cond.status()),
                        userNameContains(cond.userName()),
                        amountGoe(cond.minAmount()),
                        createdBetween(cond.from(), cond.to())
                )
                .orderBy(orderSpec(pageable))
                .offset(pageable.getOffset())
                .limit(pageable.getPageSize())
                .fetch();

        // 2) 카운트 — 별도 쿼리로 분리하면 정렬·조인을 줄일 수 있다
        JPAQuery<Long> countQuery = query
                .select(order.count())
                .from(order)
                .join(order.user, user)
                .where(
                        statusEq(cond.status()),
                        userNameContains(cond.userName()),
                        amountGoe(cond.minAmount()),
                        createdBetween(cond.from(), cond.to())
                );

        // 마지막 페이지이거나 첫 페이지에 다 들어가면 카운트 쿼리를 생략한다 ★
        return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
    }

    // ── 조건 메서드: null 이면 null 을 반환 → where 에서 무시됨 ──────
    private BooleanExpression statusEq(OrderStatus s) {
        return s != null ? order.status.eq(s) : null;
    }

    private BooleanExpression userNameContains(String name) {
        return StringUtils.hasText(name) ? user.name.contains(name) : null;
    }

    private BooleanExpression amountGoe(Integer min) {
        return min != null ? order.amount.goe(min) : null;
    }

    private BooleanExpression createdBetween(LocalDate from, LocalDate to) {
        if (from == null && to == null) return null;
        if (from == null) return order.createdAt.loe(to.atTime(23, 59, 59));
        if (to == null)   return order.createdAt.goe(from.atStartOfDay());
        return order.createdAt.between(from.atStartOfDay(), to.atTime(23, 59, 59));
    }

    // 조건을 조합해서 재사용할 수도 있습니다
    private BooleanExpression isActive() {
        return order.status.in(OrderStatus.CREATED, OrderStatus.PAID)
                .and(order.deletedAt.isNull());
    }

    private OrderSpecifier<?>[] orderSpec(Pageable pageable) {
        if (pageable.getSort().isEmpty()) {
            return new OrderSpecifier[]{ order.createdAt.desc() };
        }
        return pageable.getSort().stream()
                .map(o -> new OrderSpecifier<>(
                        o.isAscending() ? Order.ASC : Order.DESC,
                        Expressions.stringPath(order, o.getProperty())))
                .toArray(OrderSpecifier[]::new);
    }
}

페이징 · 정렬 · 프로젝션

목록 화면은 거의 전부 페이징입니다. 잘못 만들면 데이터가 늘수록 급격히 느려집니다.

기본 페이징

// 컨트롤러 — Pageable 을 그대로 받으면 됩니다
@GetMapping
public Page<OrderRes> list(
        @PageableDefault(size = 20, sort = "createdAt",
                         direction = Sort.Direction.DESC) Pageable pageable) {
    return orderService.list(pageable);
}
// 요청: /api/orders?page=0&size=20&sort=createdAt,desc

// 리포지토리 — 반환 타입만 다르고 시그니처가 같으므로 둘 중 하나만 선언
Page<Order> findByStatus(OrderStatus status, Pageable pageable);
// Slice<Order> findByStatus(OrderStatus status, Pageable pageable);  // 카운트 없음

// Page 가 주는 정보
page.getContent();        page.getTotalElements();
page.getTotalPages();     page.hasNext();
page.map(OrderRes::from); // 내용만 변환 (메타는 유지) ★
Slice 를 쓰면 카운트 쿼리가 안 나갑니다. “더 보기” 방식의 무한 스크롤이면 전체 개수가 필요 없으니 Slice 가 훨씬 빠릅니다.

깊은 페이지가 느린 이유와 해결

-- 100만 번째 페이지
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000;
-- DB 가 100만 20건을 읽고 100만 건을 버립니다 💥
// ✅ 커서(무한 스크롤) 방식 — 마지막 본 ID 부터
@Query("""
    SELECT o FROM Order o
     WHERE (:lastId IS NULL OR o.id < :lastId)
     ORDER BY o.id DESC
    """)
List<Order> findNext(Long lastId, Pageable pageable);
// 항상 인덱스로 바로 찾아가므로 페이지가 깊어져도 일정한 속도 ✅

// QueryDSL 로도
query.selectFrom(order)
     .where(lastId != null ? order.id.lt(lastId) : null)
     .orderBy(order.id.desc())
     .limit(size)
     .fetch();
정렬 컬럼에 인덱스가 없으면 페이징은 무조건 느립니다. ORDER BY created_at DESC 를 쓴다면 created_at 에 인덱스가 있어야 합니다.

@Mapper                                     // 또는 @MapperScan 을 설정에
public interface OrderMapper {

    // 애너테이션 방식 — 짧은 쿼리에
    @Select("SELECT * FROM orders WHERE id = #{id}")
    OrderDto findById(Long id);

    @Insert("""
        INSERT INTO orders (order_no, amount, status, created_at)
        VALUES (#{orderNo}, #{amount}, #{status}, NOW())
        """)
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(OrderDto dto);

    // XML 방식 — 복잡한 쿼리는 이쪽
    List<OrderSummary> search(OrderSearchCond cond);
}

</mapper>
#{} 와 ${} 는 완전히 다릅니다
· #{value} → PreparedStatement 바인딩 (안전) ✅
· ${value} → 문자열을 그대로 붙임 → SQL 인젝션 💥
${} 는 정렬 컬럼명처럼 어쩔 수 없을 때만, 그리고 반드시 화이트리스트 검증 후에 쓰세요.

MyBatis 동적 SQL · 결과 매핑

MyBatis 의 진짜 강점입니다. 조건에 따라 SQL 자체가 달라집니다.

동적 SQL

<select id="search" resultType="OrderSummary">
  SELECT o.*, u.name AS userName
    FROM orders o
    JOIN users u ON u.id = o.user_id
  <where>                          <!-- 조건이 하나도 없으면 WHERE 자체를 안 붙임 -->
    <if test="status != null">
      AND o.status = #{status}
    </if>
    <if test="userName != null and userName != ''">
      AND u.name LIKE CONCAT('%', #{userName}, '%')
    </if>
    <if test="from != null and to != null">
      AND o.created_at BETWEEN #{from} AND #{to}
    </if>
    <if test="statuses != null and statuses.size() > 0">
      AND o.status IN
      <foreach collection="statuses" item="s" open="(" separator="," close=")">
        #{s}
      </foreach>
    </if>
  </where>
  <choose>
    <when test="sort == 'amount'">ORDER BY o.amount DESC</when>
    <otherwise>ORDER BY o.created_at DESC</otherwise>
  </choose>
</select>

<!-- UPDATE 에는 set -->
<update id="update">
  UPDATE orders
  <set>                            <!-- 마지막 콤마를 알아서 제거 -->
    <if test="status != null">status = #{status},</if>
    <if test="memo != null">memo = #{memo},</if>
    updated_at = NOW()
  </set>
  WHERE id = #{id}
</update>

결과 매핑 · 대량 처리

<!-- 1:N 을 한 번에 매핑 -->
<resultMap id="orderDetail" type="OrderDetail">
  <id property="id" column="o_id"/>
  <result property="orderNo" column="order_no"/>
  <association property="user" javaType="UserDto">
    <id property="id" column="u_id"/>
    <result property="name" column="u_name"/>
  </association>
  <collection property="items" ofType="ItemDto">
    <id property="id" column="i_id"/>
    <result property="name" column="i_name"/>
  </collection>
</resultMap>

<!-- 대량 INSERT — 한 번의 쿼리로 ★ -->
<insert id="insertAll">
  INSERT INTO orders (order_no, amount, status) VALUES
  <foreach collection="list" item="o" separator=",">
    (#{o.orderNo}, #{o.amount}, #{o.status})
  </foreach>
</insert>

트랜잭션 완전정복

“왜 롤백이 안 되지?”의 원인은 거의 정해져 있습니다. 여기서 전부 정리합니다.

기본 사용

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)        // 클래스 기본값 = 읽기 전용
public class OrderService {

    @Transactional                      // 쓰기 메서드만 재정의
    public Order create(OrderCreateReq req) { ... }

    // 옵션
    @Transactional(
        timeout = 5,                              // 5초 넘으면 롤백
        isolation = Isolation.READ_COMMITTED,     // 격리 수준
        propagation = Propagation.REQUIRED,       // 전파 방식
        rollbackFor = Exception.class             // ★ 체크 예외도 롤백
    )
    public void process() { ... }
}
readOnly = true 의 효과 — 하이버네이트가 스냅샷을 안 만들어 메모리를 아끼고 더티 체킹을 건너뜁니다. DB 에 따라 읽기 전용 커넥션으로 라우팅할 수도 있습니다. 조회 메서드에는 꼭 붙이세요.

전파(Propagation)

옵션동작
REQUIRED (기본)있으면 참여, 없으면 새로 시작
REQUIRES_NEW항상 새 트랜잭션. 바깥이 롤백돼도 얘는 커밋됨
NESTED중첩 (세이브포인트)
SUPPORTS있으면 참여, 없으면 없이 실행
NOT_SUPPORTED트랜잭션 없이 실행
MANDATORY없으면 예외
// 실전 예: 주문이 실패해도 로그는 반드시 남긴다
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(String message) {
    auditRepository.save(new AuditLog(message));
}

⚠️ 롤백이 안 되는 5가지 이유

① 체크 예외는 기본적으로 롤백되지 않습니다
@Transactional
public void process() throws IOException {
    repository.save(entity);
    throw new IOException("실패");     // ❌ 커밋됩니다!
}
// ✅ @Transactional(rollbackFor = Exception.class)
② 예외를 잡아 버리면 롤백 신호가 안 갑니다
@Transactional
public void process() {
    try {
        repository.save(entity);
        risky();
    } catch (Exception e) {
        log.error("실패", e);          // ❌ 삼켜서 커밋됨
    }
}
// ✅ 다시 던지거나, TransactionAspectSupport
//    .currentTransactionStatus().setRollbackOnly();
③ 자기 자신을 호출하면 프록시를 안 거칩니다
public void outer() {
    inner();          // ❌ this.inner() — 트랜잭션 없음
}
@Transactional
public void inner() { ... }
// ✅ 클래스 분리 (🍃 Boot 11번 참고)
④ private / final 메서드에는 안 걸립니다
@Transactional
private void save() { }      // ❌ 프록시가 오버라이드 불가
⑤ 다른 스레드는 트랜잭션을 공유하지 않습니다
@Transactional
public void process() {
    executor.submit(() -> repository.save(e));  // ❌ 별개 트랜잭션
}
// @Async 메서드도 마찬가지 — 새 트랜잭션이 필요합니다

트랜잭션 설계 원칙

  • 짧게 유지하세요 — 트랜잭션이 길면 커넥션을 오래 붙잡아 풀이 고갈됩니다
  • 외부 API 호출을 트랜잭션 안에 넣지 마세요 — 상대가 느려지면 우리 DB 커넥션이 전부 묶입니다
  • 커밋 후 처리는 이벤트로

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)

    notifier.send(event.email(), "결제 완료");
    // 트랜잭션이 롤백되면 이 코드는 아예 실행되지 않습니다 ✅
}

// 발행하는 쪽
@Transactional
public void pay(Long id) {
    Order o = ...;
    o.pay();

Spring Batch — 수천만 건을 다루는 법

정산·집계·마이그레이션처럼 밤에 도는 일은 웹과 완전히 다른 도구가 필요합니다.

직접 짜면 반드시 부딪히는 것들

@Scheduled 로 만든 자체 배치의 최후

  · 500만 건을 findAll() → 즉시 OOM
  · 3시간 돌다가 240만 건에서 실패 → 처음부터 다시
  · 어디까지 처리했는지 아무도 모름
  · 서버가 2대라 같은 배치가 동시에 두 번 돎
  · 실패했는데 아무도 몰랐고, 다음 날 정산이 틀림

Spring Batch 가 기본으로 해결해 주는 것
  ✓ 청크 단위 처리 (메모리 일정하게 유지)
  ✓ 실패 지점부터 재시작
  ✓ 실행 이력을 메타 테이블에 기록
  ✓ 같은 파라미터의 Job 중복 실행 차단
  ✓ 건너뛰기(skip)·재시도(retry) 정책
implementation("org.springframework.boot:spring-boot-starter-batch")
Boot 4 부터 Job 저장소의 기본이 in-memory 입니다 — 재시작·중복 실행 차단을 쓰려면 DB 모드가 필요합니다.
implementation("org.springframework.boot:spring-boot-starter-batch-jdbc")
⚠️ 그리고 메타 테이블(BATCH_JOB_*) 이 필요합니다 — spring.batch.jdbc.initialize-schema=always 또는 Flyway 로 생성(d15).

청크 처리 — 핵심 개념 하나

read → read → … → read  (chunk size 만큼 = 1,000건)
                    ↓
                 process  (한 건씩 변환·필터)
                    ↓
                  write   (1,000건을 한 번에 저장 · 커밋)
                    ↓
              메모리 비우고 다음 청크로

→ 500만 건이어도 메모리에는 항상 1,000건만 있습니다
→ 커밋도 1,000건마다 — 롤백 범위가 작습니다

실전 Job — Spring Boot 4 기준

@Configuration
@RequiredArgsConstructor
public class SettlementJobConfig {

    private final JobRepository jobRepository;
    private final PlatformTransactionManager txManager;
    private final DataSource dataSource;

    @Bean
    public Job settlementJob(Step settlementStep) {
        return new JobBuilder("settlementJob", jobRepository)
                .start(settlementStep)
                .build();
    }

    @Bean
    public Step settlementStep(ItemReader<Order> reader,
                               ItemProcessor<Order, Settlement> processor,
                               ItemWriter<Settlement> writer) {
        return new StepBuilder("settlementStep", jobRepository)
                .<Order, Settlement>chunk(1000, txManager)   // ★ 청크 크기
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .faultTolerant()
                .skip(InvalidDataException.class).skipLimit(100)  // 100건까지는 건너뜀
                .retry(DeadlockLoserDataAccessException.class).retryLimit(3)
                .build();
    }

    // ★ 커서 방식 — 500만 건이어도 메모리는 일정
    @Bean
    @StepScope                                  // 실행 시점 파라미터를 받으려면 필수
    public JdbcCursorItemReader<Order> reader(
            @Value("#{jobParameters['targetDate']}") String targetDate) {
        return new JdbcCursorItemReaderBuilder<Order>()
                .name("orderReader")
                .dataSource(dataSource)
                .sql("select id, user_id, amount from orders where order_date = ?")
                .queryArguments(targetDate)
                .rowMapper(new DataClassRowMapper<>(Order.class))
                .fetchSize(1000)
                .build();
    }

    @Bean
    public JdbcBatchItemWriter<Settlement> writer() {
        return new JdbcBatchItemWriterBuilder<Settlement>()
                .dataSource(dataSource)
                .sql("insert into settlement (order_id, amount, fee) " +
                     "values (:orderId, :amount, :fee)")
                .beanMapped()
                .build();                       // 내부적으로 JDBC 배치 = 가장 빠름
    }
}
Reader 를 JPA 로 만들 때는 조심하세요. JpaPagingItemReader 는 페이지가 뒤로 갈수록 느려지고(OFFSET 문제), 처리 중 데이터가 바뀌면 건너뛰는 행이 생깁니다. 대량이면 JdbcCursorItemReader 나 id 기준 커서 페이징(where id > :lastId)을 쓰세요.

// 파티셔닝 — id 범위를 10등분해 동시에 처리
@Bean
public Step partitionedStep(Step workerStep, TaskExecutor executor) {
    return new StepBuilder("partitionedStep", jobRepository)
            .partitioner("workerStep", new ColumnRangePartitioner())
            .step(workerStep)
