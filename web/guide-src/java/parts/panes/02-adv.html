ADV 01

JVM 구조와 메모리

“어디에 무엇이 저장되는가”만 알면 OOM·성능 문제의 절반은 짐작이 갑니다.

스택
스레드마다 하나씩메서드 호출 정보, 지역 변수, 기본형 값. 메서드가 끝나면 즉시 사라집니다.
힙
모든 스레드가 공유new 로 만든 모든 객체. GC 가 청소하는 곳. OOM 의 주 무대입니다.
메타스페이스
클래스 정보클래스 구조, static 필드. Java 8부터 힙 밖(네이티브 메모리)에 있습니다.
기타
코드 캐시 · 다이렉트 버퍼JIT 이 만든 기계어, NIO 버퍼. 힙 통계에 안 잡혀서 놓치기 쉽습니다.
void example() {
    int a = 10;                    // 스택 — 값 자체
    String s = "hello";            // 스택엔 '주소', 실제 객체는 힙
    List<String> list = new ArrayList<>();   // 힙
}   // 메서드 끝 -> 스택은 즉시 정리, 힙 객체는 GC 가 나중에

“대부분의 객체는 금방 죽는다”는 가정 위에 설계돼 있습니다. 그래서 짧게 쓰고 버리는 객체는 사실상 공짜에 가깝고, 오래 붙잡고 있는 객체(캐시·static 컬렉션)가 문제를 만듭니다.

실무에서 쓰는 옵션

# 힙 크기 — 컨테이너에선 비율 지정이 안전

# GC 로그

① static 컬렉션에 계속 담기 — 절대 안 지워집니다. 캐시는 반드시 크기 제한을 두세요.
② DB 결과를 전부 메모리로 — findAll() 이 100만 건이면 그대로 힙에 올라옵니다. 페이징·스트리밍을 쓰세요.
③ 파일·스트림을 안 닫음 — try-with-resources를 쓰면 구조적으로 막힙니다.
메모리 문제를 볼 때 첫 질문은 힙 안인가 밖인가입니다.
ADV 02

GC — 쓰레기 수집

자바가 메모리를 대신 정리해 주는 대신, 정리하는 동안 잠깐 멈춥니다(Stop-The-World). 이 멈춤을 줄이는 게 튜닝의 전부입니다.

ADV 03

equals · hashCode · 불변 설계

이 규약을 어기면 Set 에 넣었는데 못 찾는, 재현도 어려운 버그가 납니다.

규약 — 둘은 항상 같이 구현

public final class Money {
    private final String currency;
    private final long amount;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;      // 패턴 매칭
        return amount == m.amount && currency.equals(m.currency);
    }

    @Override
    public int hashCode() {
        return Objects.hash(currency, amount);          // 필드 조합
    }
}

// 규약
//   1) a.equals(b) 가 true 면 -> hashCode() 도 반드시 같아야 한다
//   2) hashCode 가 같다고 equals 가 true 일 필요는 없다 (해시 충돌 허용)
//   3) equals 에 쓴 필드만 hashCode 에도 쓴다
왜 중요한가 — HashMap·HashSet은 먼저 hashCode 로 자리를 찾고 그 안에서 equals 로 비교합니다. hashCode 를 빼먹으면 같은 값이라도 다른 자리에 들어가서 영원히 못 찾습니다.

불변 객체 — 가장 값싼 안전장치

// 불변 만들기 5원칙
public final class Period {              // 1) final class — 상속 차단
    private final LocalDate start;       // 2) 모든 필드 final + private
    private final List<String> tags;

    public Period(LocalDate start, List<String> tags) {
        this.start = start;
        this.tags = List.copyOf(tags);   // 3) 방어적 복사 (들어올 때)
    }

    public List<String> getTags() {
        return tags;                     // 4) 이미 불변이라 그대로 OK
    }                                    //    가변이면 복사해서 반환

    public Period withStart(LocalDate s) {
        return new Period(s, tags);      // 5) 변경은 '새 객체'로
    }
}

// record 를 쓰면 1·2는 자동. 3만 신경 쓰면 됩니다
public record Period(LocalDate start, List<String> tags) {
    public Period {
        tags = List.copyOf(tags);        // 압축 생성자에서 복사
    }
}

불변 객체는 여러 스레드가 동시에 읽어도 안전합니다. 동시성 문제의 상당수가 “공유되는 가변 상태”에서 나오므로, 불변으로 만들 수 있으면 락 자체가 필요 없어집니다.

ADV 04

스레드 기초

웹 서버는 이미 스레드 위에서 돌고 있습니다. 직접 만들 일은 적어도 무슨 일이 벌어지는지는 알아야 합니다.

만들고 실행하기

// 1) 가장 단순한 방법
Thread t = new Thread(() -> System.out.println("다른 스레드"));
t.start();          // ⚠️ run() 을 직접 부르면 그냥 메서드 호출입니다
t.join();           // 끝날 때까지 기다림

// 2) 이름을 붙이면 로그·덤프에서 찾기 쉽다
Thread t2 = new Thread(task, "order-worker-1");

// 3) 데몬 스레드 — 메인이 끝나면 같이 종료
t2.setDaemon(true);

// 현재 스레드
Thread.currentThread().getName();     // "main", "http-nio-8080-exec-1" …
Thread.sleep(1000);                   // 1초 대기 (InterruptedException 처리 필요)

// 인터럽트 — '멈춰 달라'는 신호 (강제 종료가 아님)
t.interrupt();
// 받는 쪽
while (!Thread.currentThread().isInterrupted()) { ... }

스레드 상태

상태의미
NEW만들어졌지만 start() 전
RUNNABLE실행 중이거나 CPU 를 기다리는 중
BLOCKED락을 기다리는 중 — 덤프에 많으면 경합 의심
WAITING다른 스레드를 무기한 대기 (join, wait)

서버가 멈춘 것 같을 때 — jcmd <pid> Thread.print 로 덤프를 뜨고 BLOCKED 가 몰려 있는 지점을 찾으세요. 같은 락을 여러 스레드가 기다리고 있으면 그게 병목입니다.
"스레드 풀 크기를 얼마로 할까"라는 오래된 고민이 가상 스레드에서는 대체로 사라집니다 — 대신 다른 자원의 상한이 병목이 됩니다.

스레드를 직접 만들지 않는 법 — 실무에서 쓰는 형태

ExecutorService — 이것이 기본입니다

// ✗ new Thread() 를 직접 쓰는 코드는 거의 항상 잘못된 코드입니다
new Thread(() -> doWork()).start();     // 개수 제어 없음 · 예외 유실 · 종료 불가

// ✓ 풀에 맡깁니다 (try-with-resources — Java 19+)
try (var pool = Executors.newFixedThreadPool(8)) {
    List<Future<Report>> futures = ids.stream()
        .map(id -> pool.submit(() -> buildReport(id)))
        .toList();

    for (var f : futures) {
        Report r = f.get(10, TimeUnit.SECONDS);   // ★ 타임아웃을 반드시
        save(r);
    }
}   // 블록을 벗어나면 알아서 close + 완료 대기

// ✓✓ 가상 스레드 (Java 21+) — IO 대기가 많으면 이쪽
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    ids.forEach(id -> pool.submit(() -> callExternalApi(id)));
}   // 1만 개를 던져도 됩니다

// 주기 작업
try (var sched = Executors.newScheduledThreadPool(1)) {
    sched.scheduleAtFixedRate(this::cleanup, 0, 1, TimeUnit.HOURS);
}
Future.get() 을 타임아웃 없이 부르지 마세요. 상대가 응답을 안 주면 영원히 기다립니다 — 요청을 처리하던 스레드가 통째로 묶이고, 같은 일이 반복되면 톰캣 스레드 풀이 말라 서비스가 멈춥니다. "서버가 살아 있는데 아무 응답이 없다"의 대표적 원인입니다.

// 큐가 무한이면 메모리가 터집니다 — 상한과 거절 정책을 함께

    8, 16,                                   // core, max
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),          // ★ 큐 상한

        .setNameFormat("report-%d").build(), // ★ 이름 — 덤프에서 결정적입니다

// 종료는 반드시 (스프링이면 @PreDestroy · @Bean(destroyMethod))
pool.shutdown();

ADV 05

동기화 · 락 · 원자성

“가끔만 틀리는 버그”의 원인은 대부분 여기 있습니다. 여러 스레드가 같은 값을 동시에 건드릴 때 무슨 일이 일어나는지 봅시다.

❌ count++ 는 원자적이지 않다
class Counter {
    private int count = 0;
    public void inc() { count++; }     // 읽기 → +1 → 쓰기, 3단계!
}

// 스레드 1000개가 각각 1000번 증가시키면
// 기대: 1,000,000  실제: 973,412 처럼 매번 다름 💥
✅ 세 가지 해법
// 1) synchronized — 가장 단순
private int count = 0;
public synchronized void inc() { count++; }

// 2) AtomicInteger — 락 없이 (CAS), 더 빠름
private final AtomicInteger count = new AtomicInteger();
public void inc() { count.incrementAndGet(); }

// 3) LongAdder — 경합이 심할 때 최강
private final LongAdder count = new LongAdder();
public void inc() { count.increment(); }

// 메서드 전체 — this 를 락으로 사용
public synchronized void transfer() { ... }

// 필요한 부분만 (권장) — 락 구간이 짧을수록 좋다
private final Object lock = new Object();
public void transfer() {
    prepare();                    // 락 밖
    synchronized (lock) {
        balance -= amount;        // 꼭 필요한 부분만
    }
    notifyUser();                 // 락 밖
}

// ReentrantLock — 타임아웃·시도가 필요할 때
private final ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }   // finally 필수!
} else {
    throw new BusyException();
}

// 읽기가 압도적으로 많으면 ReadWriteLock
private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();  // var는 지역 변수 전용 — 필드에는 못 씀
rw.readLock().lock();     // 읽기끼리는 서로 안 막음
rw.writeLock().lock();    // 쓰기는 전부 배타

volatile — 가시성만 보장

// ❌ 다른 스레드에서 바꾼 값이 안 보일 수 있다 (CPU 캐시)
private boolean running = true;
public void stop() { running = false; }
public void run() { while (running) { ... } }   // 영원히 안 멈출 수 있음

// ✅ volatile — 항상 메인 메모리에서 읽고 쓴다
private volatile boolean running = true;
volatile 은 원자성을 보장하지 않습니다. volatile int count; count++; 는 여전히 깨집니다.
· 플래그(true/false) → volatile
· 증감·누적 → Atomic 계열
· 여러 값을 함께 → synchronized / Lock
데드락 — 서로가 서로를 기다림
스레드 A가 락1을 쥐고 락2를 기다리고, B가 락2를 쥐고 락1을 기다리면 둘 다 영원히 멈춥니다. 예방법은 하나 — 락을 항상 같은 순서로 잡기(예: ID 가 작은 계좌부터). 그리고 가능하면 tryLock(타임아웃)을 써서 영원히 기다리지 않게 하세요.
동시성 코드를 쓸 때 첫 선택지는 이미 만들어진 것입니다.

//   CPU 작업  : 코어 수 (그 이상은 컨텍스트 스위칭 손해)
//   I/O 작업  : 코어 수 × (1 + 대기시간/계산시간)
//   예) 계산 5ms + DB 대기 45ms, 8코어 → 8 × (1+9) = 80
// 공식은 출발점일 뿐 — 부하 테스트로 큐 길이·지연을 보고 조정합니다

// 읽기 95% 인 자료에는 StampedLock 낙관적 읽기
private final StampedLock sl = new StampedLock();

double read() {
    long stamp = sl.tryOptimisticRead();     // 락 없이 일단 읽고
    double x = this.value;
    if (!sl.validate(stamp)) {               // 그 사이 쓰기가 있었나?
        stamp = sl.readLock();               // 있었다면 그때만 진짜 락
        try { x = this.value; }
        finally { sl.unlockRead(stamp); }
    }
    return x;
}
// ReadWriteLock 보다 읽기 처리량이 크게 높습니다.
// 단, 재진입 불가 · Condition 없음 — 용도를 좁게 잡으세요.

// 단계별 합류가 필요하면 Phaser (CountDownLatch 의 재사용 버전)
var phaser = new Phaser(3);                  // 참가자 3

phaser.arriveAndAwaitAdvance();              // 라운드 2 — 재사용 ✅

CompletableFuture — 비동기 조합

“여러 API 를 동시에 호출해서 합치기” 같은 작업을 콜백 지옥 없이 쓰는 방법입니다.

// 1) 비동기 실행
CompletableFuture<User> userF =
        CompletableFuture.supplyAsync(() -> userClient.find(id), pool);

// 2) 결과를 변환 (스레드 유지)
CompletableFuture<String> nameF = userF.thenApply(User::getName);

// 3) 또 다른 비동기 호출을 이어붙이기 (평탄화)
CompletableFuture<Profile> profileF =
        userF.thenCompose(u -> CompletableFuture.supplyAsync(() -> profileClient.find(u.getId())));

// 4) 둘을 동시에 실행하고 합치기 ★ 가장 많이 쓰는 패턴
CompletableFuture<Order> orderF = CompletableFuture.supplyAsync(() -> orderClient.find(id), pool);
CompletableFuture<OrderView> viewF =
        userF.thenCombine(orderF, (user, order) -> new OrderView(user, order));

// 5) 전부 끝날 때까지
CompletableFuture.allOf(f1, f2, f3).join();
List<String> results = Stream.of(f1, f2, f3).map(CompletableFuture::join).toList();

// 6) 가장 먼저 끝난 하나
CompletableFuture.anyOf(f1, f2).join();

// 7) 예외 처리
userF.exceptionally(e -> {                       // 실패하면 대체값
        log.error("조회 실패", e);
        return User.unknown();
     })
     .orTimeout(3, TimeUnit.SECONDS)             // 타임아웃 (Java 9+)
     .whenComplete((result, err) -> {            // 성공·실패 모두
        if (err != null) log.error("실패", err);
     });
기본 풀을 쓰지 마세요 — supplyAsync(task)에 풀을 안 주면 공용 ForkJoinPool을 씁니다. 여기서 DB·HTTP 같은 블로킹 작업을 하면 애플리케이션 전체의 병렬 스트림까지 함께 굶습니다. 반드시 전용 풀을 두 번째 인자로 넘기세요.

여기서 실력이 갈립니다 — 5년차가 놓치는 네 가지

① 실행 스레드의 진실 · ② 예외의 정체

// ① thenApply 는 "어느 스레드에서" 도는가? — 답: 그때그때 다릅니다
f.thenApply(x -> heavy(x));
//   future 가 '아직 미완료'  → 완료시키는 스레드(풀 스레드)가 실행
//   future 가 '이미 완료'    → thenApply 를 '부른 스레드'가 실행 ★
// 톰캣 요청 스레드에서 완료된 future 에 무거운 변환을 붙이면
// 그 변환이 '요청 스레드에서' 돕니다 — 지연의 단골 원인.
// 실행 위치를 보장하려면 항상 thenApplyAsync(fn, pool).

// ② 꺼낼 때 예외 타입이 바뀝니다
f.get()    // ExecutionException 로 감싸서 (checked)
f.join()   // CompletionException 로 감싸서 (unchecked)
// 원인 판정은 반드시 e.getCause() 로:
.exceptionally(e -> {
    Throwable cause = (e instanceof CompletionException) ? e.getCause() : e;
    if (cause instanceof TimeoutException) return fallback();
    throw new CompletionException(cause);       // 모르는 건 다시 던지기
})

// handle vs whenComplete — 자주 헷갈리는 차이
.handle((val, err) -> err == null ? val : fallback())  // 결과를 '바꿈'
.whenComplete((val, err) -> log(val, err))             // 관찰만, 예외는 그대로 흐름

③ allOf 부분 실패 수집 · ④ 취소와 타임아웃의 배신

// ③ allOf 는 하나만 실패해도 통째로 실패합니다.
//    "성공한 것만 모으고 실패는 따로" 가 실무 요구 — 이렇게 만듭니다
List<CompletableFuture<Item>> fs = ids.stream()
        .map(id -> fetch(id).handle((v, e) ->
                e == null ? Result.ok(v) : Result.fail(id, e)))  // 실패를 값으로
        .toList();
CompletableFuture.allOf(fs.toArray(CompletableFuture[]::new)).join();
Map<Boolean, List<Result>> byOk = fs.stream()
        .map(CompletableFuture::join)
        .collect(Collectors.partitioningBy(Result::isOk));

// ④ cancel() 은 '체인 아래로만' 알려집니다
CompletableFuture<A> up = supplyAsync(...);
CompletableFuture<B> down = up.thenApply(...);
down.cancel(true);
//   up 은 계속 돕니다! 실행 중인 스레드에 인터럽트도 안 갑니다 ★
//   orTimeout(3, SECONDS) 도 같습니다 — future 만 실패시키고
//   뒤에서 원래 작업은 끝까지 돕니다 (자원은 계속 소모)
//   → 진짜 취소가 필요하면: Future.cancel(true)(ExecutorService 제출분)
//     또는 구조적 동시성(다음 섹션)으로 스코프째 취소

// 보너스: MDC·SecurityContext 는 풀 스레드로 안 따라갑니다
Supplier<Map<String,String>> ctx = MDC::getCopyOfContextMap;
var saved = ctx.get();
supplyAsync(() -> { MDC.setContextMap(saved); return work(); }, pool);

⚠️ 켜기 전에 확인할 것

  • synchronized 안에서 블로킹하면 고정(pinning)됩니다 — 가상 스레드가 캐리어 스레드를 반납하지 못해 이점이 사라집니다. ReentrantLock 으로 바꾸세요. Java 24+ 에서 대부분 해소
  • ThreadLocal 을 캐시로 쓰면 안 됩니다 — 스레드가 수백만 개가 되면 메모리를 그만큼 먹습니다. ScopedValue(다음 섹션)로 대체하세요.
  • DB 커넥션 풀이 새 병목이 됩니다 — 스레드는 100만 개여도 커넥션은 20개뿐입니다. 풀 크기를 함께 조정하세요.
  • CPU 집약 작업에는 이점이 없습니다 — 가상 스레드는 기다리는 작업(I/O)에 효과가 있습니다.

    return () -> {
        limit.acquire();                 // 101번째부터는 여기서 대기
        try { return task.call(); }      //   (가상 스레드라 대기가 공짜)
        finally { limit.release(); }
    };
}
“무제한 생성”이 진짜 함정입니다 — 가상 스레드 100만 개는 공짜지만, 그 100만 개가 동시에 때리는 DB·외부 API 는 공짜가 아닙니다. 스레드를 아끼는 시대에서 다운스트림을 보호하는 시대로 바뀐 것뿐입니다. 경계마다 세마포어 하나 — 이게 가상 스레드 시대의 스레드 풀 크기 튜닝입니다.

알아두면 자유로워지는 것들

// 지금 가상 스레드 위인가? (라이브러리 분기 작성 시)
Thread.currentThread().isVirtual()

// 인터럽트·취소·타임아웃 — 전부 '그대로' 동작합니다
Future<String> f = ex.submit(() -> slowCall());
f.get(3, TimeUnit.SECONDS);        // 타임아웃
f.cancel(true);                    // 인터럽트로 취소

// 데몬 여부·우선순위는 못 바꿉니다 (항상 데몬 · NORM 고정)
// → main 이 끝나면 가상 스레드도 끝 — 배치라면 join 을 잊지 마세요

// CompletableFuture 와 조합 — 실행자만 갈아끼우면 됩니다
var vex = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture.supplyAsync(() -> userClient.find(id), vex)
                 .orTimeout(2, TimeUnit.SECONDS);

// 관측 — 개수가 수십만이라 jstack 은 못 씁니다
// JFR 이벤트: jdk.VirtualThreadStart / End / Pinned / SubmitFailed
// jcmd <pid> Thread.dump_to_file -format=json dump.json  (전체 덤프)

요약 — 이름 · 예외 핸들러 · 세마포어 · JFR 네 가지를 챙기면 가상 스레드는 “켜 보는 기능”에서 “설계에 쓰는 도구”가 됩니다.

DB가 가상 스레드와 안 친할 때 — 고정(pinning) 진단과 우회 4단계

가상 스레드의 마법은 “블로킹하면 캐리어(OS 스레드)를 반납한다”입니다. 그런데 반납하지 못하는 자리가 있습니다 — 이것이 고정(pinning)이고, 옛날 JDBC 드라이버가 대표적인 범인입니다. 고정된 만큼 캐리어가 잠기면 스레드 풀 시절보다 오히려 느려질 수도 있습니다.

어디서 나고, 어떻게 찾나

// 고정이 생기는 자리 (Java 21~23 기준)
// ① synchronized 블록 '안에서' 블로킹      ← 옛 JDBC 드라이버의 주범
// ② Object.wait() · 네이티브 코드(JNI) 안에서 블로킹
// ③ 파일 I/O 일부 (OS 에 논블로킹 API 가 없어 내부 오프로딩)

// 오래된 드라이버 내부가 대략 이렇습니다
synchronized (connectionMutex) {          // ← 락을 쥔 채
    sendQueryPacket(sql);
    readResultPacket();                   // ← 소켓 대기 = 캐리어 고정 ❌
}

// 진단 ① 실행 플래그 — 고정될 때마다 스택을 찍어 줍니다
java -Djdk.tracePinnedThreads=full -jar app.jar

// 진단 ② JFR — 운영에서는 이쪽 (오버헤드 낮음)
jcmd <pid> JFR.start settings=profile
// 이벤트 jdk.VirtualThreadPinned 를 Mission Control 로 확인
// '20ms 이상 고정' 이 반복되는 스택이 수리 대상입니다
Java 24 부터 (JEP 491) — synchronized 안에서 블로킹해도 캐리어를 반납하도록 JVM 자체가 바뀌었습니다. ①번 고정은 런타임 업그레이드로 사라집니다. 남는 것은 ② 네이티브 경계뿐 — 그래서 아래 우회는 “Java 24 로 못 올리는 동안”과 “JNI 드라이버”를 위한 기술입니다.

우회 — 위에서부터 차례로 시도하세요

// ① 드라이버·런타임 업그레이드 (제일 싸고 확실)
//    MySQL Connector/J 9.x · PostgreSQL 42.6+ 는 synchronized 를
//    ReentrantLock 으로 바꿨습니다. Java 24+ 면 그것만으로도 해결.

// ② 업그레이드 불가 → 블로킹 구간만 '플랫폼 스레드 섬'으로 격리 ★
//    고정될 코드는 어차피 고정되니, 전용 풀에 가두고
//    가상 스레드는 결과만 기다리게 합니다 (기다림은 반납 가능)
private static final ExecutorService JDBC_ISLAND =
        Executors.newFixedThreadPool(20);        // = 커넥션 풀 크기

Order findOrder(long id) throws Exception {
    return JDBC_ISLAND.submit(() -> jdbc.query(...)).get();
    //     ↑ 플랫폼 스레드가 고정을 대신 떠안고
    //     ↑ .get() 대기 중인 가상 스레드는 캐리어를 반납합니다 ✅
}

// ③ 커넥션 수 = 진짜 동시성 한계 — 입구에서 미리 자르기
//    (커넥션 20개에 가상 스레드 1만 개가 몰리면 대기 폭주 + 타임아웃)
private final Semaphore db = new Semaphore(20);  // HikariCP max 와 동일
// + HikariCP: maximumPoolSize=20, connectionTimeout 은 짧게(1~3s)

// ④ 그래도 부족하면 논블로킹 드라이버로 (R2DBC · Vert.x SQL)
//    단, 코드 스타일이 리액티브로 바뀝니다 — 🌊 WebFlux 탭 09번
순서가 중요합니다 — ②의 “섬 패턴”은 코드 전체가 아니라 고정이 실측된 경계 하나에만 씁니다. JFR 로 찾기 전에 여기저기 submit().get() 을 감으면 스레드 풀 시절로 되돌아갈 뿐입니다. 그리고 섬의 크기는 반드시 커넥션 풀 크기와 같게 — 더 크면 의미가 없고 더 작으면 커넥션을 놀립니다.
WebFlux 대신 가상 스레드를 쓸 수 있을까? — 상당수의 경우 그렇습니다. “동시 요청은 많지만 로직은 단순한 I/O 대기”라면 익숙한 동기 코드 + 가상 스레드가 WebFlux 보다 훨씬 유지보수하기 쉽습니다. WebFlux 가 여전히 유리한 경우는 스트리밍·백프레셔가 필요할 때입니다 — 🌊 WebFlux 탭 01번에서 판단 기준을 정리했습니다.
가상 스레드가 바꾼 것은 성능보다 비동기 코드를 안 써도 된다는 점입니다.

구조적 동시성 · 스코프 값 Java 21~26

여러 비동기 작업을 하나의 단위로 묶어 “다 성공하거나 다 취소되거나”를 보장하는 방법입니다.

구조적 동시성

// 문제: 하나가 실패해도 나머지는 계속 돌아 자원을 낭비한다
// 해결: 스코프로 묶어 생명주기를 함께 관리

// ⚠️ 아래 open()/Joiner API 는 2026-08 현재도 여전히 preview 입니다.
//    Java 25 = JEP 505(5차 preview) · Java 26 = JEP 525(6차 preview).
//    컴파일·실행에 --enable-preview 플래그가 필요합니다.
//    Java 26 에서 Joiner.onTimeout() 이 추가돼 스코프 단위 타임아웃을 걸 수 있습니다.
//    Java 21~24 의 preview API 는 형태가 다릅니다:
//    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) { ... }

try (var scope = StructuredTaskScope.open()) {
    // 두 작업을 동시에 시작
    var userTask  = scope.fork(() -> userClient.find(id));
    var orderTask = scope.fork(() -> orderClient.findByUser(id));

    scope.join();                     // 둘 다 끝날 때까지 대기
                                      // 하나가 실패하면 나머지는 자동 취소 ✅
    return new Dashboard(userTask.get(), orderTask.get());
}   // 스코프를 벗어나면 남은 작업은 반드시 정리된다

// 가장 먼저 성공한 것만 쓰기 (여러 공급자 중 빠른 것)
try (var scope = StructuredTaskScope.open(
        StructuredTaskScope.Joiner.<String>anySuccessfulResultOrThrow())) {
    scope.fork(() -> providerA.fetch());
    scope.fork(() -> providerB.fetch());
    return scope.join();
}
CompletableFuture 와 뭐가 다른가 — CompletableFuture 는 작업들이 서로 남남이라 하나가 실패해도 나머지를 손으로 취소해야 합니다. 구조적 동시성은 try 블록처럼 범위를 벗어나면 반드시 정리됩니다.

ScopedValue — ThreadLocal 의 후계

// ThreadLocal 의 문제: 언제 지워야 할지 모르고, 가상 스레드에선 메모리 폭증
private static final ThreadLocal<User> CURRENT = new ThreadLocal<>();
CURRENT.set(user);
try { ... } finally { CURRENT.remove(); }   // 빼먹으면 누수

// ScopedValue — 범위가 끝나면 자동으로 사라진다 (불변)
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, loginUser)
           .run(() -> {
               service.process();          // 이 안에서는 어디서든 읽을 수 있다
           });                             // 끝나면 자동 해제 ✅

// 읽는 쪽
void deepInside() {
    User u = CURRENT_USER.get();
}

요청 단위의 로그인 사용자·추적 ID·테넌트 정보를 넘길 때 씁니다. 메서드 파라미터로 계속 넘기지 않아도 되면서, ThreadLocal 처럼 새지 않습니다.

리플렉션 — 실행 중에 클래스를 들여다보기

컨테이너에서 제일 먼저 하는 설정

# ❌ 흔한 실수 — 컨테이너 메모리를 무시하고 고정
java -Xmx2g -jar app.jar
   → 컨테이너 한도가 1GB 면 힙만으로 초과 → OOMKilled(exit 137)
   → 애플리케이션 로그에는 아무것도 안 남습니다 (커널이 죽인 것)

# ✅ 컨테이너 한도의 비율로 지정 (Java 10+ 기본으로 컨테이너를 인식)
java -XX:MaxRAMPercentage=75.0 \
     -XX:InitialRAMPercentage=75.0 \
     -jar app.jar
JVM 이 쓰는 메모리 = 힙만이 아닙니다. 메타스페이스·스레드 스택(스레드당 1MB)·코드 캐시·다이렉트 버퍼가 힙 밖에 더 붙습니다. 그래서 힙을 컨테이너 한도의 100% 로 주면 반드시 죽습니다. 70~75% 가 안전한 출발점입니다.

운영에서 늘 넣는 옵션

-XX:MaxRAMPercentage=75.0
-XX:+HeapDumpOnOutOfMemoryError          # ★ OOM 순간을 파일로 남긴다
-XX:HeapDumpPath=/dump/heap.hprof        #   (영속 볼륨이어야 재시작 후에도 남음)
-XX:+ExitOnOutOfMemoryError              # 반쯤 죽은 채 서비스하지 말고 재시작
-Xlog:gc*:file=/log/gc.log:time,uptime:filecount=5,filesize=10M
-Dfile.encoding=UTF-8
-Duser.timezone=Asia/Seoul               # ★ 컨테이너 기본은 UTC 입니다
OOM 은 “증상”이지 원인이 아닙니다. 힙 덤프를 받아 MAT 나 IntelliJ 프로파일러로 열면 “어떤 객체가 몇 개, 누가 붙잡고 있는지”가 바로 보입니다. 범인은 대부분 무한히 커지는 캐시이거나 정리 안 된 ThreadLocal 입니다.

GC 고르기 — Java 21 기준

GC이럴 때
G1 (기본)대부분의 웹 서비스. 힙 4~32GB 에서 무난합니다. 고민되면 그냥 G1
ZGC정지 시간이 중요할 때. 힙이 커도 1ms 미만 정지. -XX:+UseZGC Java 25 기준 (세대형은 23부터 기본, ZGenerational 플래그는 24부터 폐기)
Parallel배치처럼 처리량만 중요하고 멈춰도 되는 작업
Serial컨테이너가 아주 작을 때(1 vCPU). 사이드카·작은 유틸
# p99 가 GC 때문에 튄다면 (gc.log 에서 200ms+ 정지가 보임)
-XX:+UseZGC     # 세대형 ZGC 는 Java 23부터 기본 (ZGenerational 플래그는 24부터 폐기)

# G1 을 계속 쓰면서 정지 시간만 낮추고 싶다면
-XX:MaxGCPauseMillis=100     # 목표치일 뿐, 보장은 아닙니다
GC 옵션부터 만지는 것은 거의 항상 잘못된 순서입니다. GC 가 자주 도는 진짜 이유는 대개 객체를 너무 많이 만드는 코드입니다. (한 번에 100만 건 조회, 문자열 반복 연결, 불필요한 DTO 변환) 코드를 고치면 GC 는 저절로 조용해집니다.

기동 시간 — 오토스케일에 직결됩니다

  • 트래픽이 몰려 서버를 늘릴 때 부팅이 60초면 이미 늦습니다
  • CDS(클래스 데이터 공유)로 기동 20~30% 단축 — -XX:ArchiveClassesAtExit Spring Boot 3.3+
  • 스프링의 지연 초기화는 첫 요청이 느려지므로 운영에서는 권하지 않습니다
  • 기동 직후 느린 것(JIT 워밍업)은 정상 — readiness 프로브로 트래픽 투입을 늦추세요
더 나아가려면 ⚡ 대규모 트래픽 탭의 k02(병목 지도)·k14(관측)·k15(부하 테스트) 를 이어서 보세요. JVM 튜닝은 측정한 뒤에 하는 마지막 단계입니다.
