ADV 01

JVM 구조와 메모리

“어디에 무엇이 저장되는가”만 알면 OOM·성능 문제의 절반은 짐작이 갑니다.

스택
스레드마다 하나씩메서드 호출 정보, 지역 변수, 기본형 값. 메서드가 끝나면 즉시 사라집니다.
힙
모든 스레드가 공유new 로 만든 모든 객체. GC 가 청소하는 곳. OOM 의 주 무대입니다.
메타스페이스
클래스 정보클래스 구조, static 필드. Java 8부터 힙 밖(네이티브 메모리)에 있습니다.
기타
코드 캐시 · 다이렉트 버퍼JIT 이 만든 기계어, NIO 버퍼. 힙 통계에 안 잡혀서 놓치기 쉽습니다.
void example() {
    int a = 10;                    // 스택 — 값 자체
    String s = "hello";            // 스택엔 '주소', 실제 객체는 힙
    List<String> list = new ArrayList<>();   // 힙
}   // 메서드 끝 -> 스택은 즉시 정리, 힙 객체는 GC 가 나중에

힙은 다시 세대로 나뉩니다

영역내용
Eden새 객체가 처음 놓이는 곳. 대부분 여기서 바로 죽습니다
Survivor 0/1Eden 에서 살아남은 것이 잠시 머무는 곳
Old(Tenured)오래 살아남은 객체. 여기가 차면 Full GC — 느립니다

“대부분의 객체는 금방 죽는다”는 가정 위에 설계돼 있습니다. 그래서 짧게 쓰고 버리는 객체는 사실상 공짜에 가깝고, 오래 붙잡고 있는 객체(캐시·static 컬렉션)가 문제를 만듭니다.

실무에서 쓰는 옵션

# 힙 크기 — 컨테이너에선 비율 지정이 안전
java -Xms512m -Xmx2g -jar app.jar
java -XX:MaxRAMPercentage=75 -jar app.jar   # 컨테이너 메모리의 75%

# OOM 나면 힙 덤프 남기기 (원인 분석의 핵심)
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/log/dump.hprof -jar app.jar

# GC 로그
java -Xlog:gc*:file=/var/log/gc.log:time -jar app.jar

# 현재 상태 확인
jps -l                  # 실행 중인 자바 프로세스
jcmd <pid> GC.heap_info  # 힙 사용량
jcmd <pid> Thread.print  # 스레드 덤프 (멈춤 현상 분석)
jmap -histo <pid> | head -20   # 어떤 객체가 많은지
OOM 이 나는 진짜 이유 Top 3
① static 컬렉션에 계속 담기 — 절대 안 지워집니다. 캐시는 반드시 크기 제한을 두세요.
② DB 결과를 전부 메모리로 — findAll() 이 100만 건이면 그대로 힙에 올라옵니다. 페이징·스트리밍을 쓰세요.
③ 파일·스트림을 안 닫음 — try-with-resources를 쓰면 구조적으로 막힙니다.
ADV 02

GC — 쓰레기 수집

자바가 메모리를 대신 정리해 주는 대신, 정리하는 동안 잠깐 멈춥니다(Stop-The-World). 이 멈춤을 줄이는 게 튜닝의 전부입니다.

어떤 객체가 청소되나

// GC 는 "루트에서 도달할 수 없는" 객체를 지운다
//   루트 = 스택의 지역변수, static 필드, 실행 중인 스레드 …

List<byte[]> cache = new ArrayList<>();

void leak() {
    cache.add(new byte[10_000_000]);   // cache 가 살아있는 한 절대 안 지워짐
}

void ok() {
    byte[] tmp = new byte[10_000_000];
    process(tmp);
}   // 메서드 끝 -> 참조가 끊김 -> 다음 GC 때 회수 ✅

// System.gc() 는 '요청'일 뿐이고, 오히려 Full GC 를 유발합니다.
// 실무에서 호출할 이유가 없습니다.

GC 종류 — 뭘 쓸까

GC특징 · 언제

ADV 03

equals · hashCode · 불변 설계

이 규약을 어기면 Set 에 넣었는데 못 찾는, 재현도 어려운 버그가 납니다.

규약 — 둘은 항상 같이 구현

public final class Money {
    private final String currency;
    private final long amount;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;      // 패턴 매칭
        return amount == m.amount && currency.equals(m.currency);
    }

    @Override
    public int hashCode() {
        return Objects.hash(currency, amount);          // 필드 조합
    }
}

// 규약
//   1) a.equals(b) 가 true 면 -> hashCode() 도 반드시 같아야 한다
//   2) hashCode 가 같다고 equals 가 true 일 필요는 없다 (해시 충돌 허용)
//   3) equals 에 쓴 필드만 hashCode 에도 쓴다
왜 중요한가 — HashMap·HashSet은 먼저 hashCode 로 자리를 찾고 그 안에서 equals 로 비교합니다. hashCode 를 빼먹으면 같은 값이라도 다른 자리에 들어가서 영원히 못 찾습니다.

불변 객체 — 가장 값싼 안전장치

// 불변 만들기 5원칙
public final class Period {              // 1) final class — 상속 차단
    private final LocalDate start;       // 2) 모든 필드 final + private
    private final List<String> tags;

    public Period(LocalDate start, List<String> tags) {
        this.start = start;
        this.tags = List.copyOf(tags);   // 3) 방어적 복사 (들어올 때)
    }

    public List<String> getTags() {
        return tags;                     // 4) 이미 불변이라 그대로 OK
    }                                    //    가변이면 복사해서 반환

    public Period withStart(LocalDate s) {
        return new Period(s, tags);      // 5) 변경은 '새 객체'로
    }
}

// record 를 쓰면 1·2는 자동. 3만 신경 쓰면 됩니다
public record Period(LocalDate start, List<String> tags) {
    public Period {
        tags = List.copyOf(tags);        // 압축 생성자에서 복사
    }
}

불변 객체는 여러 스레드가 동시에 읽어도 안전합니다. 동시성 문제의 상당수가 “공유되는 가변 상태”에서 나오므로, 불변으로 만들 수 있으면 락 자체가 필요 없어집니다.

ADV 04

스레드 기초

웹 서버는 이미 스레드 위에서 돌고 있습니다. 직접 만들 일은 적어도 무슨 일이 벌어지는지는 알아야 합니다.

만들고 실행하기

// 1) 가장 단순한 방법
Thread t = new Thread(() -> System.out.println("다른 스레드"));
t.start();          // ⚠️ run() 을 직접 부르면 그냥 메서드 호출입니다
t.join();           // 끝날 때까지 기다림

// 2) 이름을 붙이면 로그·덤프에서 찾기 쉽다
Thread t2 = new Thread(task, "order-worker-1");

// 3) 데몬 스레드 — 메인이 끝나면 같이 종료
t2.setDaemon(true);

// 현재 스레드
Thread.currentThread().getName();     // "main", "http-nio-8080-exec-1" …
Thread.sleep(1000);                   // 1초 대기 (InterruptedException 처리 필요)

// 인터럽트 — '멈춰 달라'는 신호 (강제 종료가 아님)
t.interrupt();
// 받는 쪽
while (!Thread.currentThread().isInterrupted()) { ... }

스레드 상태

상태의미
NEW만들어졌지만 start() 전
RUNNABLE실행 중이거나 CPU 를 기다리는 중
BLOCKED락을 기다리는 중 — 덤프에 많으면 경합 의심
WAITING다른 스레드를 무기한 대기 (join, wait)
TIMED_WAITING시간 제한 대기 (sleep, await(t))
TERMINATED종료
서버가 멈춘 것 같을 때 — jcmd <pid> Thread.print 로 덤프를 뜨고 BLOCKED 가 몰려 있는 지점을 찾으세요. 같은 락을 여러 스레드가 기다리고 있으면 그게 병목입니다.
ADV 05

동기화 · 락 · 원자성

“가끔만 틀리는 버그”의 원인은 대부분 여기 있습니다. 여러 스레드가 같은 값을 동시에 건드릴 때 무슨 일이 일어나는지 봅시다.

❌ count++ 는 원자적이지 않다
class Counter {
    private int count = 0;
    public void inc() { count++; }     // 읽기 → +1 → 쓰기, 3단계!
}

// 스레드 1000개가 각각 1000번 증가시키면
// 기대: 1,000,000  실제: 973,412 처럼 매번 다름 💥
✅ 세 가지 해법
// 1) synchronized — 가장 단순
private int count = 0;
public synchronized void inc() { count++; }

// 2) AtomicInteger — 락 없이 (CAS), 더 빠름
private final AtomicInteger count = new AtomicInteger();
public void inc() { count.incrementAndGet(); }

// 3) LongAdder — 경합이 심할 때 최강
private final LongAdder count = new LongAdder();
public void inc() { count.increment(); }
public long get() { return count.sum(); }

synchronized 와 락

// 메서드 전체 — this 를 락으로 사용
public synchronized void transfer() { ... }

// 필요한 부분만 (권장) — 락 구간이 짧을수록 좋다
private final Object lock = new Object();
public void transfer() {
    prepare();                    // 락 밖
    synchronized (lock) {
        balance -= amount;        // 꼭 필요한 부분만
    }
    notifyUser();                 // 락 밖
}

// ReentrantLock — 타임아웃·시도가 필요할 때
private final ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }   // finally 필수!
} else {
    throw new BusyException();
}

// 읽기가 압도적으로 많으면 ReadWriteLock
private final var rw = new ReentrantReadWriteLock();
rw.readLock().lock();     // 읽기끼리는 서로 안 막음
rw.writeLock().lock();    // 쓰기는 전부 배타

volatile — 가시성만 보장

// ❌ 다른 스레드에서 바꾼 값이 안 보일 수 있다 (CPU 캐시)
private boolean running = true;
public void stop() { running = false; }
public void run() { while (running) { ... } }   // 영원히 안 멈출 수 있음

// ✅ volatile — 항상 메인 메모리에서 읽고 쓴다
private volatile boolean running = true;
volatile 은 원자성을 보장하지 않습니다. volatile int count; count++; 는 여전히 깨집니다.
· 플래그(true/false) → volatile
· 증감·누적 → Atomic 계열
· 여러 값을 함께 → synchronized / Lock
데드락 — 서로가 서로를 기다림
스레드 A가 락1을 쥐고 락2를 기다리고, B가 락2를 쥐고 락1을 기다리면 둘 다 영원히 멈춥니다. 예방법은 하나 — 락을 항상 같은 순서로 잡기(예: ID 가 작은 계좌부터). 그리고 가능하면 tryLock(타임아웃)을 써서 영원히 기다리지 않게 하세요.
ADV 06

java.util.concurrent — 직접 만들지 마세요

스레드를 손으로 만들고 관리하는 코드는 대부분 이미 표준 라이브러리에 더 잘 만들어져 있습니다.

ExecutorService — 스레드 풀

// 고정 크기 풀
try (var pool = Executors.newFixedThreadPool(10)) {   // Java 19+ AutoCloseable
    Future<Integer> f = pool.submit(() -> compute());
    Integer result = f.get();          // 결과를 기다림 (블로킹)
}   // 자동으로 shutdown + 대기

// 예전 방식 (여전히 많이 봅니다)
ExecutorService pool = Executors.newFixedThreadPool(10);
try {
    pool.submit(task);
} finally {
    pool.shutdown();                   // 새 작업 거부, 진행 중인 건 마침
    pool.awaitTermination(30, TimeUnit.SECONDS);
    pool.shutdownNow();                // 강제 종료
}

// 여러 작업을 한 번에
List<Callable<String>> tasks = List.of(t1, t2, t3);
List<Future<String>> futures = pool.invokeAll(tasks);   // 전부 끝날 때까지
String first = pool.invokeAny(tasks);                    // 가장 먼저 끝난 하나

// 주기 실행
var sched = Executors.newScheduledThreadPool(2);
sched.scheduleAtFixedRate(job, 0, 10, TimeUnit.SECONDS);

동시성 컬렉션

클래스용도
ConcurrentHashMap스레드 안전한 Map. HashMap 대신
CopyOnWriteArrayList읽기 위주 · 쓰기가 드문 목록(리스너 등)
BlockingQueue생산자-소비자 큐. 비면 대기
ConcurrentLinkedQueue락 없는 큐
var map = new ConcurrentHashMap<String, Integer>();
map.merge("key", 1, Integer::sum);        // 원자적 증가 ✅
map.computeIfAbsent("k", k -> expensive());  // 한 번만 계산

// 생산자-소비자
BlockingQueue<Order> queue = new LinkedBlockingQueue<>(1000);
queue.put(order);        // 가득 차면 대기
Order o = queue.take();  // 비어 있으면 대기

// 동기화 보조 도구
var latch = new CountDownLatch(3);    // 3개가 끝날 때까지 대기
latch.countDown();  latch.await();
var sem = new Semaphore(5);           // 동시 5개만 허용
sem.acquire();  try { ... } finally { sem.release(); }
Collections.synchronizedMap()은 쓰지 마세요 — 맵 전체에 락을 걸어 사실상 직렬화됩니다. ConcurrentHashMap은 구역별로만 잠가서 훨씬 빠릅니다.
ADV 07

CompletableFuture — 비동기 조합

“여러 API 를 동시에 호출해서 합치기” 같은 작업을 콜백 지옥 없이 쓰는 방법입니다.

// 1) 비동기 실행
CompletableFuture<User> userF =
        CompletableFuture.supplyAsync(() -> userClient.find(id), pool);

// 2) 결과를 변환 (스레드 유지)
CompletableFuture<String> nameF = userF.thenApply(User::getName);

// 3) 또 다른 비동기 호출을 이어붙이기 (평탄화)
CompletableFuture<Profile> profileF =
        userF.thenCompose(u -> CompletableFuture.supplyAsync(() -> profileClient.find(u.getId())));

// 4) 둘을 동시에 실행하고 합치기 ★ 가장 많이 쓰는 패턴
CompletableFuture<Order> orderF = CompletableFuture.supplyAsync(() -> orderClient.find(id), pool);
CompletableFuture<OrderView> viewF =
        userF.thenCombine(orderF, (user, order) -> new OrderView(user, order));

// 5) 전부 끝날 때까지
CompletableFuture.allOf(f1, f2, f3).join();
List<String> results = Stream.of(f1, f2, f3).map(CompletableFuture::join).toList();

// 6) 가장 먼저 끝난 하나
CompletableFuture.anyOf(f1, f2).join();

// 7) 예외 처리
userF.exceptionally(e -> {                       // 실패하면 대체값
        log.error("조회 실패", e);
        return User.unknown();
     })
     .orTimeout(3, TimeUnit.SECONDS)             // 타임아웃 (Java 9+)
     .whenComplete((result, err) -> {            // 성공·실패 모두
        if (err != null) log.error("실패", err);
     });
기본 풀을 쓰지 마세요 — supplyAsync(task)에 풀을 안 주면 공용 ForkJoinPool을 씁니다. 여기서 DB·HTTP 같은 블로킹 작업을 하면 애플리케이션 전체의 병렬 스트림까지 함께 굶습니다. 반드시 전용 풀을 두 번째 인자로 넘기세요.
ADV 08

가상 스레드 — 판이 바뀐 지점 Java 21+

“동시 접속 1만 명을 처리하려고 WebFlux 로 갈아탈까” 고민했다면, 먼저 이걸 보세요. 기존 코드를 거의 그대로 두고 처리량을 올릴 수 있습니다.

무엇이 문제였나

기존 플랫폼 스레드는 OS 스레드와 1:1입니다. 하나에 스택 메모리 약 1MB가 필요해서 수천 개가 한계이고, DB 조회·API 호출 같은 기다리는 시간 동안 그 비싼 스레드가 아무것도 안 하고 묶여 있습니다.

플랫폼 스레드가상 스레드
1개 비용약 1MB약 1KB
동시 개수수천수백만
생성 비용비쌈 (풀 필요)거의 공짜
블로킹 시OS 스레드가 묶임바로 반납, 다른 일 처리

쓰는 법 — 놀랄 만큼 단순합니다

// 1) 하나 띄우기
Thread.startVirtualThread(() -> {
    var result = restClient.get("/api/orders");   // 블로킹해도 괜찮다
    log.info("{}", result);
});

// 2) 실행자 — 작업마다 새 가상 스레드 (풀이 필요 없음!)
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Order>> futures = ids.stream()
            .map(id -> executor.submit(() -> orderClient.find(id)))
            .toList();
    for (var f : futures) process(f.get());
}   // 자동으로 전부 대기 후 종료

// 3) 10,000개 동시 실행 — 예전엔 상상도 못 했던 코드
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
        ex.submit(() -> {
            Thread.sleep(1000);      // 1초 대기하는 작업 1만 개
            return i;
        }));
}   // 전체 소요 시간: 약 1초 (플랫폼 스레드였다면 메모리 부족)

스프링 부트에서 켜기 — 설정 한 줄

# application.yml  (Spring Boot 3.2+)
spring:
  threads:
    virtual:
      enabled: true

이 한 줄이면 톰캣의 요청 처리 스레드, @Async, 스케줄러가 전부 가상 스레드로 바뀝니다. 컨트롤러·서비스 코드는 한 글자도 안 고칩니다. 

// 직접 지정하고 싶다면
@Bean
public AsyncTaskExecutor applicationTaskExecutor() {
    return new TaskExecutorAdapter(
            Executors.newVirtualThreadPerTaskExecutor());
}

⚠️ 켜기 전에 확인할 것

  • synchronized 안에서 블로킹하면 고정(pinning)됩니다 — 가상 스레드가 캐리어 스레드를 반납하지 못해 이점이 사라집니다. ReentrantLock 으로 바꾸세요. Java 24+ 에서 대부분 해소
  • ThreadLocal 을 캐시로 쓰면 안 됩니다 — 스레드가 수백만 개가 되면 메모리를 그만큼 먹습니다. ScopedValue(다음 섹션)로 대체하세요.
  • DB 커넥션 풀이 새 병목이 됩니다 — 스레드는 100만 개여도 커넥션은 20개뿐입니다. 풀 크기를 함께 조정하세요.
  • CPU 집약 작업에는 이점이 없습니다 — 가상 스레드는 기다리는 작업(I/O)에 효과가 있습니다.
# 고정(pinning) 발생 지점 찾기
java -Djdk.tracePinnedThreads=full -jar app.jar
WebFlux 대신 가상 스레드를 쓸 수 있을까? — 상당수의 경우 그렇습니다. “동시 요청은 많지만 로직은 단순한 I/O 대기”라면 익숙한 동기 코드 + 가상 스레드가 WebFlux 보다 훨씬 유지보수하기 쉽습니다. WebFlux 가 여전히 유리한 경우는 스트리밍·백프레셔가 필요할 때입니다 — 🌊 WebFlux 탭 01번에서 판단 기준을 정리했습니다.
ADV 09

구조적 동시성 · 스코프 값 Java 21~25

여러 비동기 작업을 하나의 단위로 묶어 “다 성공하거나 다 취소되거나”를 보장하는 방법입니다.

구조적 동시성

// 문제: 하나가 실패해도 나머지는 계속 돌아 자원을 낭비한다
// 해결: 스코프로 묶어 생명주기를 함께 관리

try (var scope = StructuredTaskScope.open()) {
    // 두 작업을 동시에 시작
    var userTask  = scope.fork(() -> userClient.find(id));
    var orderTask = scope.fork(() -> orderClient.findByUser(id));

    scope.join();                     // 둘 다 끝날 때까지 대기
                                      // 하나가 실패하면 나머지는 자동 취소 ✅
    return new Dashboard(userTask.get(), orderTask.get());
}   // 스코프를 벗어나면 남은 작업은 반드시 정리된다

// 가장 먼저 성공한 것만 쓰기 (여러 공급자 중 빠른 것)
try (var scope = StructuredTaskScope.open(
        StructuredTaskScope.Joiner.<String>anySuccessfulResultOrThrow())) {
    scope.fork(() -> providerA.fetch());
    scope.fork(() -> providerB.fetch());
    return scope.join();
}
CompletableFuture 와 뭐가 다른가 — CompletableFuture 는 작업들이 서로 남남이라 하나가 실패해도 나머지를 손으로 취소해야 합니다. 구조적 동시성은 try 블록처럼 범위를 벗어나면 반드시 정리됩니다.

ScopedValue — ThreadLocal 의 후계

// ThreadLocal 의 문제: 언제 지워야 할지 모르고, 가상 스레드에선 메모리 폭증
private static final ThreadLocal<User> CURRENT = new ThreadLocal<>();
CURRENT.set(user);
try { ... } finally { CURRENT.remove(); }   // 빼먹으면 누수

// ScopedValue — 범위가 끝나면 자동으로 사라진다 (불변)
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, loginUser)
           .run(() -> {
               service.process();          // 이 안에서는 어디서든 읽을 수 있다
           });                             // 끝나면 자동 해제 ✅

// 읽는 쪽
void deepInside() {
    User u = CURRENT_USER.get();
}

요청 단위의 로그인 사용자·추적 ID·테넌트 정보를 넘길 때 씁니다. 메서드 파라미터로 계속 넘기지 않아도 되면서, ThreadLocal 처럼 새지 않습니다.

ADV 11

리플렉션 · 애너테이션 · 프록시

스프링이 “마법처럼” 동작하는 원리가 여기 있습니다. 직접 쓸 일은 드물어도 알면 스프링이 안 무섭습니다.

리플렉션 — 실행 중에 클래스를 들여다보기

Class<?> clazz = order.getClass();
clazz.getSimpleName();                      // "Order"
clazz.getDeclaredFields();                  // 필드 목록
clazz.getDeclaredMethods();                 // 메서드 목록

// 애너테이션이 붙었는지 확인
if (clazz.isAnnotationPresent(Service.class)) { ... }

// 값 읽기·쓰기 (private 도 가능)
Field f = clazz.getDeclaredField("amount");
f.setAccessible(true);
int amount = (int) f.get(order);

// 메서드 호출
Method m = clazz.getMethod("pay");
m.invoke(order);

// 객체 생성
Object o = clazz.getDeclaredConstructor().newInstance();
느리고 위험합니다. 컴파일러의 타입 검사를 우회하므로 오타가 런타임 예외로 나옵니다. 프레임워크를 만들 때가 아니면 직접 쓸 일이 거의 없습니다.

직접 만드는 애너테이션

@Target(ElementType.METHOD)          // 어디에 붙일 수 있나
@Retention(RetentionPolicy.RUNTIME)  // 언제까지 살아있나 (리플렉션엔 RUNTIME 필수)
public @interface LogExecutionTime {
    String value() default "";
}

// 사용
@LogExecutionTime("주문 처리")
public void process(Order o) { ... }

// 읽는 쪽 (보통은 AOP 가 대신 해 줍니다)
Method m = ...;
if (m.isAnnotationPresent(LogExecutionTime.class)) {
    String label = m.getAnnotation(LogExecutionTime.class).value();
}

프록시 — 스프링 AOP 의 정체

// 원본 객체를 감싼 '대역'을 만들어 앞뒤에 코드를 끼운다
Object proxy = Proxy.newProxyInstance(
    loader, new Class[]{Notifier.class},
    (p, method, args) -> {
        long t = System.nanoTime();
        Object result = method.invoke(target, args);   // 원본 호출
        log.info("{} took {}ms", method.getName(),
                 (System.nanoTime() - t) / 1_000_000);
        return result;
    });
이게 @Transactional이 동작하는 방식입니다. 스프링이 프록시를 만들어 메서드 앞에서 트랜잭션을 시작하고 뒤에서 커밋합니다. 그래서 같은 클래스 안에서 자기 메서드를 호출하면 프록시를 안 거쳐서 안 먹습니다 — 🗄️ 데이터 탭 14번에서 자세히 다룹니다.
