GW 01

게이트웨이가 필요한 이유

서비스가 하나뿐이라면 필요 없습니다. 여러 개가 되는 순간 이야기가 달라집니다.

게이트웨이 없이

브라우저 ──→ order-service   (인증 코드 복사)
        ──→ user-service    (인증 코드 복사)
        ──→ payment-service (인증 코드 복사)

문제
· 서비스마다 인증·로깅·CORS 를 중복 구현
· 프론트엔드가 주소를 전부 알아야 함
· 서비스 주소가 바뀌면 클라이언트도 배포
· 서비스가 전부 외부에 노출

게이트웨이가 있으면

브라우저 ──→ [Gateway] ──→ order-service
                       ──→ user-service
                       ──→ payment-service

· 인증·로깅·Rate Limit 을 한 곳에서
· 클라이언트는 게이트웨이 주소 하나만
· 내부 서비스는 외부에 노출되지 않음
· 서킷 브레이커로 장애 전파 차단

게이트웨이가 하는 일

  • 라우팅 — 경로·헤더를 보고 어느 서비스로 보낼지 결정
  • 인증·인가 — 토큰을 여기서 한 번만 검증
  • Rate Limit — 과도한 요청 차단
  • 서킷 브레이커 — 죽은 서비스로 계속 보내지 않기
  • 로깅·추적 — 요청 ID 를 심어 전 구간 추적
  • 응답 변환 — 헤더 추가·제거
implementation("org.springframework.cloud:spring-cloud-starter-gateway")
⚠️ WebFlux 기반이라 spring-boot-starter-web 과 함께 쓰면 안 됩니다.
서비스가 1~2개라면 도입하지 마세요. 운영할 컴포넌트가 하나 늘고, 여기가 단일 장애점이 됩니다. Nginx 로 충분한 경우도 많습니다.
GW 02

라우팅 설정

YAML 로도, 자바 코드로도 정의할 수 있습니다.

YAML 방식

spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: http://localhost:8081          # 고정 주소
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1                    # /api/orders/1 -> /orders/1
            - AddRequestHeader=X-Gateway, true

        - id: user-service
          uri: lb://user-service               # 서비스 디스커버리 사용
          predicates:
            - Path=/api/users/**
            - Method=GET,POST
          filters:
            - name: CircuitBreaker
              args:
                name: userCB
                fallbackUri: forward:/fallback/user

        - id: legacy
          uri: http://legacy.internal:9090
          predicates:
            - Path=/legacy/**
            - Header=X-Legacy, true

      default-filters:                          # 모든 라우트에 적용
        - AddResponseHeader=X-Powered-By, gateway
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "https://myapp.com"
            allowedMethods: "*"

자바 코드 방식 — 조건이 복잡할 때

@Configuration
public class GatewayConfig {

    @Bean
    public RouteLocator routes(RouteLocatorBuilder builder) {
        return builder.routes()

            .route("order", r -> r
                .path("/api/orders/**")
                .filters(f -> f
                    .stripPrefix(1)
                    .addRequestHeader("X-Source", "gateway")
                    .retry(c -> c.setRetries(3)
                                 .setMethods(HttpMethod.GET))
                    .circuitBreaker(c -> c.setName("orderCB")
                                          .setFallbackUri("forward:/fallback")))
                .uri("lb://order-service"))

            // 카나리 — 헤더가 있으면 새 버전으로
            .route("order-canary", r -> r
                .path("/api/orders/**")
                .and().header("X-Canary", "true")
                .uri("lb://order-service-v2"))

            // 가중치 기반 분배 (90:10)
            .route("v1", r -> r.path("/api/**")
                .and().weight("group", 90).uri("lb://svc-v1"))
            .route("v2", r -> r.path("/api/**")
                .and().weight("group", 10).uri("lb://svc-v2"))

            .build();
    }
}
라우트는 위에서부터 매칭됩니다. 구체적인 조건(카나리 등)을 위에 두세요. /actuator/gateway/routes 로 현재 등록된 라우트를 확인할 수 있습니다.

@Component
public class TenantRoutePredicateFactory
        extends AbstractRoutePredicateFactory<TenantRoutePredicateFactory.Config> {

    public TenantRoutePredicateFactory() { super(Config.class); }

    @Override
    public Predicate<ServerWebExchange> apply(Config config) {
        return exchange -> {
            String tenant = exchange.getRequest().getHeaders().getFirst("X-Tenant");
            return config.getTenant().equals(tenant);
        };
    }

    @Data public static class Config { private String tenant; }
}

GW 05

커스텀 필터

실무에서 가장 많이 만드는 것 — 인증 검사와 요청 추적입니다.

글로벌 필터 — 모든 요청에

@Component
@Slf4j
public class TraceGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String traceId = UUID.randomUUID().toString().substring(0, 8);
        long start = System.currentTimeMillis();

        // 백엔드로 추적 ID 를 넘긴다
        ServerHttpRequest request = exchange.getRequest().mutate()
                .header("X-Trace-Id", traceId)
                .build();

        log.info("[{}] → {} {}", traceId,
                request.getMethod(), request.getURI().getPath());

        return chain.filter(exchange.mutate().request(request).build())
                .then(Mono.fromRunnable(() -> {
                    long took = System.currentTimeMillis() - start;
                    log.info("[{}] ← {} ({}ms)", traceId,
                            exchange.getResponse().getStatusCode(), took);
                }));
    }

    @Override
    public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }   // 가장 먼저
}

라우트별 필터 — JWT 검사 ★

@Component
public class AuthGatewayFilterFactory
        extends AbstractGatewayFilterFactory<AuthGatewayFilterFactory.Config> {

    private final JwtTokenProvider tokenProvider;

    public AuthGatewayFilterFactory(JwtTokenProvider p) {
        super(Config.class);
        this.tokenProvider = p;
    }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {
            String token = resolve(exchange.getRequest());

            if (token == null || !tokenProvider.validate(token)) {
                return unauthorized(exchange);
            }

            Claims claims = tokenProvider.parse(token);

            // 검증된 사용자 정보를 헤더로 백엔드에 전달 ★
            // → 각 서비스는 토큰을 다시 파싱할 필요가 없다
            var request = exchange.getRequest().mutate()
                    .header("X-User-Id", claims.getSubject())
                    .header("X-User-Roles", String.join(",", roles(claims)))
                    .build();

            return chain.filter(exchange.mutate().request(request).build());
        };
    }

    private Mono<Void> unauthorized(ServerWebExchange exchange) {
        var res = exchange.getResponse();
        res.setStatusCode(HttpStatus.UNAUTHORIZED);
        res.getHeaders().setContentType(MediaType.APPLICATION_JSON);
        byte[] body = """
            {"code":"A001","message":"인증이 필요합니다"}
            """.getBytes(StandardCharsets.UTF_8);
        return res.writeWith(Mono.just(res.bufferFactory().wrap(body)));
    }

    public static class Config { }
}
filters:
  - Auth                # 클래스명에서 GatewayFilterFactory 를 뗀 이름
백엔드 서비스는 게이트웨이만 신뢰해야 합니다. X-User-Id 헤더를 그대로 믿는데 서비스가 외부에 노출돼 있으면 누구나 위조할 수 있습니다. 내부망에만 두고, 게이트웨이에서 클라이언트가 보낸 X-User-* 헤더는 제거하세요.
GW 06

서킷 브레이커

한 서비스가 죽었을 때 전체가 같이 죽는 것을 막습니다.

3가지 상태

CLOSED
정상요청을 그대로 전달하며 실패율을 셉니다.
▼ 실패율이 임계치를 넘으면
OPEN
차단호출 자체를 하지 않고 즉시 폴백. 죽은 서비스를 더 때리지 않습니다.
▼ 일정 시간 후
HALF_OPEN
탐색몇 개만 보내 봅니다. 성공하면 CLOSED, 실패하면 다시 OPEN.
implementation("org.springframework.cloud:spring-cloud-starter-circuitbreaker-reactor-resilience4j") 
resilience4j:
  circuitbreaker:
    configs:
      default:
        slidingWindowSize: 20              # 최근 20건으로 판단
        minimumNumberOfCalls: 10           # 10건은 모여야 판단 시작
        failureRateThreshold: 50           # 실패 50% 넘으면 OPEN
        slowCallDurationThreshold: 2s
        slowCallRateThreshold: 60
        waitDurationInOpenState: 10s       # 10초 후 HALF_OPEN
        permittedNumberOfCallsInHalfOpenState: 3
    instances:
      orderCB:
        baseConfig: default
      userCB:
        baseConfig: default
        failureRateThreshold: 30           # 더 민감하게

  timelimiter:
    configs:
      default:
        timeoutDuration: 3s
// 폴백 컨트롤러
@RestController
public class FallbackController {

    @GetMapping("/fallback/order")
    public ResponseEntity<Map<String, Object>> orderFallback() {
        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
                .body(Map.of(
                    "code", "S001",
                    "message", "주문 서비스가 일시적으로 응답하지 않습니다",

    }
}

Rate Limit · 로드밸런싱

과도한 요청을 막고, 여러 인스턴스에 골고루 분배합니다.

Rate Limit — 토큰 버킷

implementation("org.springframework.boot:spring-boot-starter-data-redis-reactive") 
- id: api
  uri: lb://api-service
  predicates:
    - Path=/api/**
  filters:
    - name: RequestRateLimiter
      args:
        redis-rate-limiter.replenishRate: 10    # 초당 10개 채움
        redis-rate-limiter.burstCapacity: 20    # 순간 최대 20개
        redis-rate-limiter.requestedTokens: 1
        key-resolver: "#{@userKeyResolver}"
// 무엇을 기준으로 셀 것인가
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> {
        String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
        return Mono.just(userId != null ? userId : ipOf(exchange));
    };
}

@Bean
public KeyResolver ipKeyResolver() {
    return exchange -> Mono.just(
            exchange.getRequest().getRemoteAddress().getAddress().getHostAddress());
}
// 한도를 넘으면 429 Too Many Requests

게이트웨이 운영 주의
① 단일 장애점입니다 — 반드시 2대 이상 띄우세요.
② 블로킹 코드를 넣지 마세요 — WebFlux 기반이라 한 요청이 막으면 전체가 멈춥니다. DB 조회가 필요하면 R2DBC 나 Redis 리액티브 클라이언트를 쓰세요.
③ 타임아웃을 반드시 설정하세요 — 백엔드가 느려지면 게이트웨이 커넥션이 고갈됩니다.
④ 응답 본문을 통째로 읽는 필터는 메모리를 먹습니다. 꼭 필요할 때만.
GW 09

MSA 인프라 — 디스커버리 · 설정 · 추적

서비스가 열 개가 되면 주소·설정·로그를 사람이 관리할 수 없습니다.

① 서비스 디스커버리 — 주소를 이름으로

주소를 고정으로 적으면

  uri: http://10.0.1.24:8081
  → 서버가 늘거나 IP 가 바뀌면 게이트웨이를 다시 배포해야 합니다
  → 오토스케일과 근본적으로 맞지 않습니다

이름으로 부르면

  uri: lb://order-service
  → 레지스트리에 등록된 인스턴스 목록을 받아 알아서 분산
  → 죽은 인스턴스는 목록에서 빠집니다
선택지언제 씁니다
Kubernetes ServiceK8s 를 쓴다면 이미 있습니다. 별도 레지스트리 없이 DNS 이름으로 부르면 끝 — 요즘 기본
EurekaK8s 가 아닌 환경(온프레미스 VM). 국내 SI·금융권에 여전히 많습니다

@Bean
GlobalFilter requestIdFilter() {
    return (exchange, chain) -> {
        String rid = exchange.getRequest().getHeaders()
                .getFirst("X-Request-Id");
        if (rid == null) rid = UUID.randomUUID().toString();

        var mutated = exchange.getRequest().mutate()
                .header("X-Request-Id", rid).build();

        exchange.getResponse().getHeaders().add("X-Request-Id", rid);  // 응답에도
        return chain.filter(exchange.mutate().request(mutated).build());
    };
}

gRPC — MSA 내부 통신

외부 공개는 REST, 서비스끼리는 gRPC. 그 경계선을 정합니다.

REST 와 무엇이 다른가

항목REST + JSONgRPC
전송HTTP/1.1 (보통)HTTP/2 — 멀티플렉싱·헤더 압축
페이로드텍스트 JSONprotobuf 바이너리 — 보통 3~10배 작음
계약문서·OpenAPI (선택).proto 가 곧 계약 ★ 코드가 생성됨
스트리밍SSE·WebSocket 별도양방향이 기본 기능
브라우저그냥 됨직접 안 됨 — grpc-web + 프록시 필요
디버깅curl 로 즉시grpcurl 필요 · 눈으로 못 읽음
HTTP/1.1  커넥션 하나에 요청 하나 — 키프얼라이브를 써도
          "앞 요청이 끝나야 다음"(head-of-line blocking)
HTTP/2    ★ 커넥션 하나 위에 스트림 수백 개를 동시에
          → 커넥션 풀 압박이 줄고, 헤더도 HPACK 으로 압축됩니다
          → 내부 홉이 많은 MSA 일수록 이득이 커집니다
“무조건 빠르다”가 아닙니다. 페이로드가 작고 호출이 드물면 체감 차이가 거의 없습니다. gRPC 의 실제 이득은 ① 스키마가 강제되어 필드 오타·타입 사고가 사라지는 것, ② 클라이언트 코드를 직접 안 짜도 되는 것, ③ 그다음이 성능입니다. 순서를 착각하면 도입 근거가 약해집니다.

.proto — 계약을 먼저 씁니다

syntax = "proto3";

package order.v1;                       // ★ 버전을 패키지에 넣습니다
option java_package = "com.company.grpc.order.v1";
option java_multiple_files = true;

import "google/protobuf/timestamp.proto";

service OrderService {
  rpc GetOrder     (GetOrderRequest)  returns (OrderResponse);              // 단항
  rpc ListOrders   (ListOrdersRequest) returns (stream OrderResponse);      // 서버 스트리밍
  rpc UploadEvents (stream OrderEvent) returns (UploadSummary);             // 클라 스트리밍
  rpc Sync         (stream OrderEvent) returns (stream OrderResponse);      // 양방향
}

message GetOrderRequest {
  int64 order_id = 1;                   // ★ 숫자는 "필드 번호" — 이름이 아니라 이걸로 인코딩
}

message OrderResponse {
  int64  order_id = 1;
  Status status   = 2;
  google.protobuf.Timestamp created_at = 3;
  repeated OrderItem items = 4;         // 리스트
  optional string memo = 5;             // "없음"과 "빈 문자열"을 구분하려면 optional
}

enum Status {
  STATUS_UNSPECIFIED = 0;               // ★ 0번은 반드시 비워 둡니다 (기본값 자리)
  STATUS_PAID = 1;
  STATUS_SHIPPED = 2;
}

@GrpcService                                   // net.devh 스타터
public class OrderGrpcService
        extends OrderServiceGrpc.OrderServiceImplBase {

    private final OrderQuery query;

    // ① 단항 — 요청 1 : 응답 1 (REST 와 같은 모양)
    @Override
    public void getOrder(GetOrderRequest req,
                         StreamObserver<OrderResponse> res) {
        var order = query.find(req.getOrderId())
            .orElseThrow(() -> Status.NOT_FOUND
                .withDescription("주문을 찾을 수 없습니다: " + req.getOrderId())
                .asRuntimeException());

        res.onNext(toProto(order));            // 값 전달
        res.onCompleted();                     // ★ 반드시 호출 — 빼먹으면 클라가 영원히 대기
    }

    // ② 서버 스트리밍 — 대량 조회를 나눠 보냅니다 (메모리 폭발 방지)
    @Override
    public void listOrders(ListOrdersRequest req,
                           StreamObserver<OrderResponse> res) {
        try (var stream = query.streamByUser(req.getUserId())) {
            stream.forEach(o -> res.onNext(toProto(o)));
        }
        res.onCompleted();
    }

    // ③ 클라이언트 스트리밍 — 받는 쪽 Observer 를 "반환"합니다
    @Override
    public StreamObserver<OrderEvent> uploadEvents(StreamObserver<UploadSummary> res) {
        var n = new AtomicInteger();
        return new StreamObserver<>() {
            public void onNext(OrderEvent e) { ingest(e); n.incrementAndGet(); }
            public void onError(Throwable t) { log.warn("업로드 중단", t); }
            public void onCompleted() {
                res.onNext(UploadSummary.newBuilder().setAccepted(n.get()).build());
                res.onCompleted();
            }
        };
    }
    // ④ 양방향 — ③과 같은 모양에서 onNext 안에서 곧바로 res.onNext() 로 밀어 줍니다
}

왜 번호를 재사용하면 안 되는가
  protobuf 는 이름이 아니라 "번호 + 타입"으로 인코딩합니다.
  3번을 string 에서 int64 로 바꿔 재사용하면,
  아직 옛 스키마를 쓰는 서비스는 그 바이트를 ★ 조용히 잘못 해석합니다.
  예외도 안 나고 로그도 안 남습니다 — 값만 틀립니다.
  (배포는 절대 동시에 끝나지 않으므로 구·신 버전은 반드시 공존합니다)

안전한 변경 ✅                      깨지는 변경 ❌
  · 새 필드 추가 (새 번호)             · 필드 번호 변경·재사용
  · 필드 삭제 후 reserved              · 타입 변경 (string ↔ int64)
  · 새 rpc 추가                        · rpc 이름·시그니처 변경
  · enum 값 추가 (끝에)                · required ↔ optional (proto2 잔재)
  · 필드 이름만 변경(권장 안 함)        · 패키지·서비스 이름 변경

★ proto3 는 "모르는 필드는 무시"가 기본이라
  신규 필드를 추가해도 구버전 클라이언트가 죽지 않습니다.
.proto 는 별도 저장소에서 버전 관리하세요. 서비스마다 복사해 두면 세 곳의 스키마가 미묘하게 달라집니다. Buf(buf lint·buf breaking)를 CI 에 넣으면 호환성을 깨는 PR 자체를 막을 수 있습니다. 큰 변경은 파일을 order/v2 로 새로 파고 두 버전을 한동안 함께 서빙하는 것이 정석입니다.

// REST 의 필터(g05)에 해당합니다 — 로깅·인증·추적을 여기 한 곳에
@GrpcGlobalServerInterceptor
public class TraceServerInterceptor implements ServerInterceptor {

    static final Metadata.Key<String> TRACE =
        Metadata.Key.of("x-trace-id", Metadata.ASCII_STRING_MARSHALLER);

    @Override
    public <Q, R> ServerCall.Listener<Q> interceptCall(
            ServerCall<Q, R> call, Metadata headers, ServerCallHandler<Q, R> next) {

        MDC.put("traceId", Optional.ofNullable(headers.get(TRACE))
                                   .orElseGet(() -> UUID.randomUUID().toString()));
        long start = System.nanoTime();

        return next.startCall(new SimpleForwardingServerCall<Q, R>(call) {
            @Override public void close(Status status, Metadata trailers) {
                log.info("{} {} {}ms", call.getMethodDescriptor().getFullMethodName(),
                         status.getCode(), (System.nanoTime() - start) / 1_000_000);
                MDC.clear();
                super.close(status, trailers);
            }
        }, headers);
    }
}
// 인증도 같은 자리 — Metadata 의 authorization 을 읽어 Context 에 넣습니다.
// 게이트웨이가 검증한 X-User-Id 를 메타데이터로 넘기는 구성이 흔합니다(g05).

경계선 — 외부는 REST, 내부는 gRPC
✅ 내부 서비스 간 동기 호출이 많고 스키마를 강제하고 싶을 때
✅ 대량·실시간 스트리밍(시세·로그·진행률)
✅ 팀·언어가 갈려 있을 때 — .proto 하나로 클라이언트가 생성됩니다
❌ 브라우저·외부 파트너 공개 API — REST + OpenAPI 가 압도적으로 편합니다
❌ 서비스가 2~3개뿐 — 도구·학습 비용이 이득보다 큽니다
❌ 비동기로 풀어야 할 일 — 그건 gRPC 가 아니라 Kafka 입니다(⚡ k08). 동기 호출 체인이 길어지면 장애가 그대로 전파됩니다.
