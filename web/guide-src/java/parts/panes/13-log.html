LOG 01

자바 로깅의 역사 — 왜 두 겹이 됐나

다른 언어는 대개 로거가 하나입니다. 파이썬은 logging, Go 는 log/slog. 자바만 파사드(SLF4J) + 구현(Logback·Log4j2) 두 겹입니다. 이유는 기술이 아니라 역사에 있습니다 — 그리고 그 역사를 알면 오늘의 의존성 문제가 전부 설명됩니다.

타임라인 — 표준이 늦게 왔기 때문에 파사드가 필요해졌습니다. 순서가 반대였다면 두 겹은 없었습니다.

System.out 은 왜 로그가 아닌가

// ❌ 이것은 로그가 아니라 '출력'입니다
System.out.println("주문 처리 시작: " + orderId);

//  · 끄고 켤 수 없습니다 (레벨이 없음)
//  · 언제 찍혔는지 모릅니다 (시각이 없음)
//  · 누가 찍었는지 모릅니다 (클래스·스레드가 없음)
//  · 파일로 못 보냅니다 (리다이렉트하면 통째로 섞임)
//  · 동기 + 락 — 초당 수만 줄이면 그 자체가 병목입니다

// ✅ 로거
private static final Logger log =
        LoggerFactory.getLogger(OrderService.class);

log.info("주문 처리 시작 orderId={}", orderId);
// 2026-09-01 10:22:41.108 [http-nio-8080-exec-3] INFO
//   c.m.order.OrderService - 주문 처리 시작 orderId=1042
System.out 이 실제로 사고를 내는 지점 — System.out 은 동기화된 PrintStream 입니다. 요청 스레드 200개가 동시에 찍으면 전부 같은 락을 기다립니다. "로그를 지웠더니 TPS 가 올랐다"는 이야기의 절반이 여기서 나옵니다.

한 단계 더 — 파사드 + 구현이라는 두 겹 🟡 중급

레이어 — 바인딩 층이 갈아 끼우는 자리입니다. 이 한 층 때문에 두 겹이 됐습니다.

라이브러리 입장에서 생각해 보기

// 내가 오픈소스 라이브러리를 만든다고 합시다.
// 로그를 남기고 싶은데, 쓰는 쪽이 어떤 로거를 쓸지 모릅니다.

// ❌ 구현을 직접 의존하면 — 사용자에게 Logback 을 강요하는 셈
implementation("ch.qos.logback:logback-classic")

// ✅ 파사드만 의존 — 사용자가 자기 구현을 고릅니다
api("org.slf4j:slf4j-api")

// 라이브러리 코드는 이것만 씁니다
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class HttpClient {
    private static final Logger log =
            LoggerFactory.getLogger(HttpClient.class);
}
한 줄 규칙 — 라이브러리는 slf4j-api 만, 애플리케이션(실행되는 쪽)만 구현체를 넣습니다. 이 규칙 하나로 이 탭에 나오는 의존성 사고의 80%가 사라집니다.

SLF4J 가 구현을 찾는 순간

// SLF4J 2.0 부터는 표준 ServiceLoader 로 찾습니다.
// logback-classic.jar 안에는 이런 파일이 들어 있습니다.
//
//   META-INF/services/org.slf4j.spi.SLF4JServiceProvider
//     → ch.qos.logback.classic.spi.LogbackServiceProvider

// 클래스패스에 provider 가 하나도 없으면
//   SLF4J(W): No SLF4J providers were found.
//   SLF4J(W): Defaulting to no-operation (NOP) logger implementation
//   → 로그가 '조용히' 전부 사라집니다 ★

// 둘 이상이면
//   SLF4J(W): Class path contains multiple SLF4J providers.
//   SLF4J(W): Actual provider is of type [...LogbackServiceProvider]
//   → 실행은 되지만 '어느 쪽이 이겼는지'는 클래스패스 순서 나름
SLF4J 1.7 과 2.x 는 찾는 방식이 다릅니다 — 1.7 은 StaticLoggerBinder 라는 클래스를 리플렉션으로 찾았고, 2.x 는 ServiceLoader 를 씁니다. 그래서 SLF4J 2.x 에 1.7용 바인딩(log4j-slf4j-impl)을 넣으면 아무 로그도 안 나옵니다. 2.x 용은 이름 끝에 2가 붙은 log4j-slf4j2-impl 입니다.
다른 언어와 비교하면 더 선명합니다 — 파이썬 logging 은 표준 라이브러리 하나라서 파사드가 필요 없었습니다. Go 는 오래 표준이 없다가 log/slog 로 표준 인터페이스를 넣었는데, 이게 사실상 자바의 SLF4J 자리입니다. 자바는 표준이 나오기 전에 생태계가 먼저 커져 버려서 파사드를 라이브러리로 만들어야 했습니다. JDK 에 들어간 java.util.logging 은 이미 Log4j 가 이긴 뒤에 나왔습니다.
LOG 02

구현체 비교 — Logback · Log4j2 그리고 나머지

고를 것은 사실상 두 개입니다. 나머지는 "이미 들어와 있어서 알아야 하는 것"에 가깝습니다. 아래 표는 절대 점수가 아니라 상대 위치입니다 — 숫자를 지어내지 않았습니다.

히트맵 — 진한 칸이 몰린 행이 그 도구의 정체입니다. Log4j2 는 성능 쪽, Logback 은 생태계 쪽에 몰려 있습니다.

→ 교체 비용은 의존성 정리 + 설정 파일 다시 쓰기 정도입니다. 
고를 때 실제로 던지는 질문 세 개

① 지금 초당 몇 줄을 찍고 있나?
   → 모르면 먼저 재세요. 대부분 '생각보다 적게' 찍습니다.

② 로깅이 p99 지연에 잡히나?
   → 비동기 전환은 여기 답이 '예'일 때만 의미가 있습니다.

가장 흔한 오답 — “성능이 좋다니까 Log4j2 로 바꾸자”. 동기 파일 출력으로 쓰면 Log4j2 도 Logback 과 큰 차이가 없습니다. Log4j2 의 강점은 AsyncLogger 를 켰을 때 나옵니다(LOG 06).

LOG 03

SLF4J 사용법 — {} 하나가 만드는 차이

log.debug("id=" + id) 와 log.debug("id={}", id) 는 결과가 같아 보입니다. 레벨이 꺼져 있을 때 완전히 달라집니다 — 그리고 운영에서 DEBUG 는 대개 꺼져 있습니다.

결정 흐름도 — 레벨 검사가 먼저냐 나중이냐가 전부입니다. {} 는 검사를 앞으로 당깁니다.

기본기 다섯 줄

private static final Logger log =
        LoggerFactory.getLogger(OrderService.class);
// static final — 클래스마다 하나. Lombok 의 @Slf4j 가 이 줄을 만들어 줍니다.

// ① 파라미터 바인딩 — 인자 개수만큼 {}
log.info("주문 생성 orderId={} userId={} amount={}", orderId, userId, amount);

// ② 예외는 '마지막 인자'로 — {} 를 하나 더 쓰지 않습니다 ★
log.error("결제 실패 orderId={}", orderId, e);
//                              ↑ {} 는 하나, 인자는 둘 — 마지막은 스택트레이스로

// ③ 중괄호를 문자로 쓰고 싶으면 백슬래시로 막습니다
log.info("literal \\{} 그대로", ignored);

// ④ 배열은 알아서 펼쳐집니다
log.debug("ids={}", (Object) new int[]{1, 2, 3});

// ⑤ 레벨은 다섯 개. 운영 기본은 INFO
log.trace(...); log.debug(...); log.info(...); log.warn(...); log.error(...);
레벨을 고르는 한 문장 기준 — ERROR: 사람이 지금 봐야 한다 · WARN: 지금은 아니지만 쌓이면 문제 · INFO: 나중에 “무슨 일이 있었나”를 재구성할 재료 · DEBUG: 개발자가 원인을 좁힐 때 켜는 것 · TRACE: 한 줄 한 줄 따라갈 때. INFO 에 “여기 지나감”을 찍기 시작하면 INFO 가 죽습니다.

isDebugEnabled 는 언제 쓰나

// ❌ 필요 없는 경우 — {} 가 이미 막아 줍니다
if (log.isDebugEnabled()) {
    log.debug("id={}", id);        // id 는 그냥 참조 전달. 비용 0
}

// ✅ 필요한 경우 ① — 인자를 만드는 것 자체가 비쌀 때
if (log.isDebugEnabled()) {
    log.debug("cart={}", cart.toDetailedString());   // ← 이 호출이 비쌉니다
}

// ✅ 필요한 경우 ② — 로그용 데이터를 모으는 반복문
if (log.isTraceEnabled()) {
    for (Item i : items) log.trace("item {}", i);    // 루프 자체를 건너뜀
}

// ✅ SLF4J 2.0 fluent API — 람다로 미루면 if 없이도 됩니다
log.atDebug()
   .addArgument(() -> cart.toDetailedString())   // 출력할 때만 호출
   .log("cart={}");

// ✅ 또는 Supplier 를 직접 넘기는 형태
log.atInfo().setMessage("무거운 계산 {}")
   .addArgument(() -> heavy())
   .addKeyValue("orderId", orderId)              // 구조적 로깅과도 이어집니다
   .log();
가장 흔한 낭비 — toString() 이 무거운 객체를 log.debug("obj={}", bigObject) 로 넘기는 것. 레벨이 꺼져 있으면 toString() 은 호출되지 않으므로 이건 안전합니다. 문제는 bigObject.toDetailedString() 처럼 내가 직접 부른 메서드입니다 — 이건 무조건 실행됩니다.

실무에선 이렇게 — 로그 문장 자체를 설계합니다 🔴 실무

나중에 검색할 수 있게 쓰기

❌ 사람만 읽는 문장
log.info("주문 " + orderId + "번이 " +
    "정상적으로 처리되었습니다");
// 검색: "정상적으로 처리" ... 몇 건인지 셀 수 없음
// 값이 문장에 녹아 있어 필드로 뽑히지 않음
✅ 기계도 읽는 문장
log.info("order.completed orderId={} amount={} ms={}",
        orderId, amount, elapsed);
// 검색: order.completed  → 건수·금액 합계·지연 분포
// 앞머리를 '이벤트 이름'으로 고정하는 것이 핵심
규칙 세 개면 충분합니다 — ① 맨 앞은 고정된 이벤트 이름(order.completed), ② 값은 key=value 로, ③ 문장은 짧게. 이렇게 쓰면 나중에 JSON 로깅(LOG 07)으로 갈 때 문장을 다시 안 써도 됩니다.

catch (IOException e) { log.error("실패: " + e.getMessage()); }  // ❌
catch (IOException e) { log.error("파일 읽기 실패 path={}", path, e); } // ✅

// ④ 로그 안에서 예외 던지기 — 로깅이 장애 원인이 됩니다
log.info("user={}", user.getName());   // user 가 null 이면 NPE ★
log.info("user={}", user);             // ✅ null 이면 "null" 이 찍힘

// ⑤ 문자열 포맷을 직접 하기
log.info(String.format("id=%d", id));  // ❌ 레벨과 무관하게 항상 포맷
④번이 실제로 장애를 냅니다 — 로그 한 줄 때문에 NullPointerException 이 나면 정상 로직이 죽습니다. SLF4J 는 인자가 null 이면 알아서 "null" 로 찍으므로, 객체를 통째로 넘기고 toString() 에 맡기는 편이 안전합니다.
LOG 04

의존성 지옥 풀기 — 바인딩 하나 · 브리지 여럿

로깅에서 가장 자주 나는 사고는 코드 문제가 아니라 클래스패스 문제입니다. "로그가 안 나온다" · "두 번 찍힌다" · "라이브러리 로그만 안 보인다" — 전부 이 절의 이야기입니다.

의존 그래프 — 들어오는 화살표는 여럿, 나가는 화살표는 하나. 이 모양이 깨지면 로그가 이상해집니다.

증상으로 원인 찾기

증상원인
로그가 하나도 안 나옴바인딩 0개 → NOP
같은 줄이 두 번appender 중복 · additivity
내 로그만 나옴브리지 없음 (JCL·JUL 유실)
설정 파일이 안 먹음다른 구현체가 이김
StackOverflowError브리지 순환 ★
기동 로그만 안 나옴JUL 브리지 초기화 시점

SLF4J(W): Found provider [ch.qos.logback.classic.spi.LogbackServiceProvider]
SLF4J(W): Found provider [org.apache.logging.slf4j.SLF4JServiceProvider]

  → 경고일 뿐 실행은 됩니다. 그래서 더 위험합니다.
    개발 PC 와 운영 서버의 클래스패스 순서가 다르면
    '어느 쪽이 이기는지'가 환경마다 달라집니다. ★
NOP 이 가장 무섭습니다 — Defaulting to no-operation (NOP) logger implementation 은 예외가 아니라 경고입니다. 애플리케이션은 멀쩡히 뜨고, 로그만 조용히 사라집니다. 장애 나서야 알게 됩니다. 기동 로그의 SLF4J 줄을 CI 에서 검사하는 팀도 있습니다.

브리지 네 개 — 이름 규칙만 알면 됩니다

아티팩트하는 일
jul-to-slf4jjava.util.logging → SLF4J
jcl-over-slf4jcommons-logging → SLF4J
log4j-over-slf4jLog4j 1.x → SLF4J
log4j-to-slf4jLog4j2 API → SLF4J
이름 읽는 법
  · "A-over-B"  = A 의 API 를 흉내 내는 가짜 jar (원본은 반드시 제거)
  · "A-to-B"    = A 의 정식 어댑터 (원본 API 는 그대로 둠)
  · "B-A-impl"  = B(파사드)를 A(구현)로 잇는 바인딩

절대 같이 넣으면 안 되는 짝 ★
  log4j-over-slf4j  +  slf4j-log4j12    → 무한 재귀 (StackOverflowError)
  jcl-over-slf4j    +  slf4j-jcl        → 무한 재귀
  log4j-to-slf4j    +  log4j-slf4j2-impl → 무한 재귀

  이유: A→B 로 보내는 다리와 B→A 로 보내는 다리를
        동시에 놓으면 로그 한 줄이 영원히 왕복합니다.
Spring Boot 는 이걸 이미 해 뒀습니다 — spring-boot-starter-logging 안에 logback-classic + log4j-to-slf4j + jul-to-slf4j 가 들어 있습니다. 그래서 부트 프로젝트는 아무것도 안 해도 브리지가 다 깔려 있습니다.

LOG 05

Logback 설정 — appender · 롤링 · 프로파일

Spring Boot 는 application.yml 만으로도 꽤 갑니다. 그러다 어느 순간 패턴을 바꾸고 싶고 · 파일을 나누고 싶고 · 프로파일마다 다르게 하고 싶어집니다. 그때 필요한 것이 logback-spring.xml 한 장입니다.

원통이 저장소 — 파일은 계속 늘어납니다. 자르는 규칙과 지우는 규칙을 둘 다 정해야 끝납니다.

logback-spring.xml 한 장 (복붙용)

<!-- src/main/resources/logback-spring.xml -->
<configuration scan="true" scanPeriod="30 seconds">

  <!-- 부트가 만들어 둔 기본값을 그대로 가져다 씁니다 -->
  <include resource="org/springframework/boot/logging/logback/defaults.xml"/>

  <!-- application.yml 의 값을 XML 로 끌어오기 -->
  <springProperty scope="context" name="APP" source="spring.application.name"/>

  <property name="PATTERN"
      value="%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId:-}] - %msg%n"/>

  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder><pattern>${PATTERN}</pattern></encoder>
  </appender>

  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/${APP}.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>logs/${APP}-%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>100MB</maxFileSize>      <!-- 이 크기를 넘으면 자름 -->
      <maxHistory>30</maxHistory>            <!-- 30일치만 -->
      <totalSizeCap>10GB</totalSizeCap>      <!-- 전체 상한 ★ -->
      <cleanHistoryOnStart>true</cleanHistoryOnStart>
    </rollingPolicy>
    <encoder><pattern>${PATTERN}</pattern></encoder>
  </appender>

  <!-- 프로파일마다 다르게 -->
  <springProfile name="local">
    <root level="DEBUG"><appender-ref ref="CONSOLE"/></root>
  </springProfile>
  <springProfile name="prod">
    <logger name="com.myapp" level="INFO"/>
    <root level="WARN">
      <appender-ref ref="CONSOLE"/>
      <appender-ref ref="FILE"/>
    </root>
  </springProfile>
</configuration>
파일 이름이 logback.xml 이면 안 됩니다 — <springProfile> · <springProperty> 는 Spring 이 로깅을 초기화할 때 처리하므로, Logback 이 먼저 읽어 버리는 logback.xml 에서는 동작하지 않습니다. Spring Boot 에서는 항상 logback-spring.xml.

XML 없이 application.yml 로만

logging:
  level:
    root: INFO
    com.myapp: DEBUG
    org.hibernate.SQL: DEBUG
    org.springframework.web: WARN

  file:
    name: logs/app.log          # 경로+이름 (path 와 동시에 쓰지 않습니다)

  logback:

      file-name-pattern: logs/app-%d{yyyy-MM-dd}.%i.log.gz

      clean-history-on-start: true

  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level %logger{20} - %msg%n"
    file: "%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId:-}] - %msg%n"

  charset:

어디까지 yml 로 되나 — 레벨 · 파일 이름 · 롤링 · 패턴 · 인코딩까지는 yml 로 끝납니다. appender 를 여러 개 만들고 로거마다 다르게 붙이는 순간 XML 이 필요합니다. 그 전까지는 XML 을 만들지 마세요 — 관리 대상만 늘어납니다.

LOG 06

Log4j2 와 비동기 로깅 — Disruptor 가 뭘 바꿨나

Logback 에도 AsyncAppender 가 있습니다. 그런데 Log4j2 의 AsyncLogger 는 다른 층에서, 다른 자료구조로 비동기를 합니다. 그 차이가 처리량 차이의 정체입니다.

막대 — 동기끼리는 차이가 없습니다. 갈라지는 지점은 "누가 디스크를 기다리나"입니다.

AsyncAppender 와 AsyncLogger 는 다른 층입니다

Logback AsyncAppenderLog4j2 AsyncLogger
비동기 지점appender 앞logger 호출 직후
자료구조ArrayBlockingQueueLMAX Disruptor 링버퍼
락있음락 없음 (CAS)
포맷 시점큐에 넣기 전소비 스레드에서
가득 찼을 때버리거나 블록정책 선택 가능
설정XML 몇 줄의존성 + 설정
<!-- Logback — 이 정도로도 대부분 충분합니다 -->
<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
  <queueSize>8192</queueSize>            <!-- 기본 256 은 너무 작습니다 -->
  <discardingThreshold>0</discardingThreshold>
  <!-- 기본값 20 이면 큐가 80% 차는 순간 INFO 이하를 버립니다 ★ -->
  <neverBlock>false</neverBlock>
  <!-- true 면 큐가 꽉 찼을 때 로그를 버리고 애플리케이션은 안 멈춥니다 -->
  <includeCallerData>false</includeCallerData>
  <!-- true 로 하면 스택을 뒤져 줄번호를 붙입니다 — 10배 이상 느려집니다 -->
  <appender-ref ref="FILE"/>
</appender>
기본값이 조용히 로그를 버립니다 — Logback AsyncAppender 의 discardingThreshold 기본값은 20입니다. 큐가 80% 차면 TRACE·DEBUG·INFO 를 말없이 버립니다. “부하가 몰릴 때만 로그가 사라진다”는 신고의 원인이 대개 이것입니다. 버리기 싫으면 0, 대신 큐가 꽉 차면 애플리케이션이 기다립니다.

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)          // 가장 먼저 타야 합니다
public class MdcFilter extends OncePerRequestFilter {

    private static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        String traceId = req.getHeader("X-Request-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }
        MDC.put(TRACE_ID, traceId);
        MDC.put("path", req.getRequestURI());
        res.setHeader("X-Request-Id", traceId);   // 클라이언트도 알 수 있게 ★
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();                          // ★ 반드시 finally
        }
    }
}

// 부분만 잠깐 넣고 자동으로 빼기 — try-with-resources

① 스레드풀 · @Async

// 해결 — 제출하는 순간의 MDC 를 복사해 주는 TaskDecorator
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> context = MDC.getCopyOfContextMap();   // 제출 스레드에서
        return () -> {
            Map<String, String> previous = MDC.getCopyOfContextMap();
            if (context != null) MDC.setContextMap(context);        // 실행 스레드에서
            try {
                runnable.run();
            } finally {
                if (previous != null) MDC.setContextMap(previous);
                else MDC.clear();                                   // ★ 되돌리기
            }
        };
    }
}

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("appExecutor")
    public Executor executor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(32);
        ex.setQueueCapacity(1000);
        ex.setThreadNamePrefix("app-");
        ex.setTaskDecorator(new MdcTaskDecorator());   // ★ 이 한 줄
        ex.initialize();
        return ex;
    }
}
CompletableFuture.supplyAsync(...) 도 같은 문제입니다 — 기본 ForkJoinPool 을 쓰면 MDC 가 비어 있습니다. executor 를 명시해서 위 decorator 가 붙은 풀을 넘기세요. @Scheduled · 메시지 리스너도 전부 같은 이야기입니다 (거기서는 새 traceId 를 발급하는 편이 맞습니다).

public class SamplingFilter extends OncePerRequestFilter {
    private static final double RATE = 0.01;   // 1%

             r.id(), r.itemCount(), ms(t0));
    return r;

    throw e;
} catch (Exception e) {

로깅이 지연·GC 에 미치는 영향

비용이 생기는 자리 (비싼 순서)

 ① 위치 정보 (%L %M %C · includeCallerData)
    → 호출마다 스택을 만들어 훑습니다. 10배 이상 느려집니다. ★
 ② 동기 파일 쓰기 + 디스크 지연
    → p99 가 디스크 지연에 그대로 물립니다.
 ③ 문자열 조립 · 오토박싱 (GC 압력)
    → Young GC 빈도 증가 → p99 에 멈춤이 섞임
 ④ 예외 스택트레이스 생성
    → 깊은 스택 한 번이 수만 줄의 일반 로그보다 비쌉니다
 ⑤ 콘솔 출력 (터미널·컨테이너 파이프)
    → 의외로 느립니다. 운영에서 콘솔은 최소한으로.

거의 안 비싼 것
 · 꺼진 레벨의 log.debug("...{}", x)   → 레벨 검사 한 번
 · MDC.put / get                        → ThreadLocal 맵 접근
# 로깅이 원인인지 30분 안에 판별하는 절차
# 1) 레벨을 WARN 으로 내린다 → p99 를 비교
# 2) 비동기로 바꾼다        → p99 를 비교
# 3) 둘 다 안 변하면 로깅이 아닙니다 (다른 데를 보세요)

# GC 압력 확인
java -Xlog:gc*:file=gc.log:time,uptime -jar app.jar

예외 로깅 — 한 곳에서 한 번, 스택은 필요한 만큼만

예외 로그는 장애 분석의 주식인데, 실무 로그를 열어 보면 같은 스택이 세 번 찍혀 있거나 메시지만 있고 스택이 없거나, 스택이 200줄이라 정작 원인 줄을 못 찾습니다. 규칙은 셋입니다 — 어디서 잡나 · 무엇을 남기나 · 얼마나 남기나.

트리 — 붉은 칸만 ERROR입니다. 나머지 셋을 ERROR 로 찍는 순간 알림 채널이 죽습니다.

기본기 — 스택이 사라지는 다섯 가지 방법

// ✅ 유일한 정답 — 예외를 '마지막 인자'로
log.error("order.pay.fail orderId={}", orderId, e);

// ❌ ① 메시지만 — 어디서 났는지 영원히 모릅니다
log.error("결제 실패: " + e.getMessage());

// ❌ ② toString — 첫 줄만 남고 스택은 없음
log.error("결제 실패 {}", e.toString());

// ❌ ③ printStackTrace — 로거를 안 거쳐 파일·수집기에 안 남음
e.printStackTrace();

// ❌ ④ 삼키기 — 가장 나쁨. 나중에 '왜 null 이지?' 로 돌아옵니다
try { ... } catch (Exception e) { }

// ⚠️ ⑤ {} 를 예외 자리에 쓰기 — SLF4J 는 마지막 Throwable 을 따로 뺍니다
log.error("결제 실패 {}", e);
//   출력: "결제 실패 {}" + 스택트레이스  ← {} 가 글자 그대로 남습니다
//   스택은 나오니 '틀린' 건 아니지만, 의도를 오해한 코드입니다
메시지에는 "무엇을 하다가"를, 예외에는 "왜"를 — e.getMessage() 는 라이브러리가 쓴 문장이라 내 맥락(orderId · userId)이 없습니다. 메시지 자리에 내 맥락을, 마지막 인자에 예외 객체를 두면 둘 다 남습니다.

        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.code());
    }

    @ExceptionHandler(Exception.class)                            // 5xx — 우리 잘못
    ProblemDetail unexpected(Exception e) {
        log.error("api.500 path={} traceId={}", path(), MDC.get("traceId"), e);  // 스택 전체
        return ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);
    }
}
