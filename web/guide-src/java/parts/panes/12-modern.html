MODERN 01

왜 지금 자바가 다시 빨라졌나 — 8 → 17 → 21 → 25

“자바는 느리고 장황하다”는 인상은 대부분 Java 8 시절의 기억입니다. 그 사이 자바는 6개월마다 새 버전을 내면서 문법·런타임·기동 시간을 전부 갈아엎었습니다. 먼저 무엇이 언제 들어왔는지 지도를 그리고, 그다음 내 프로젝트를 어디에 놓을지 정합니다.

운영은 LTS, 실험은 중간 버전 + --enable-preview — 이 두 줄이 버전 전략의 전부입니다.

버전이 오를 때마다 사라진 “관용구”

// ── Java 8 시절 ──────────────────────────────
List<String> names = new ArrayList<String>();
for (User u : users) {
    if (u.getAge() >= 20) names.add(u.getName());
}
Collections.sort(names);
String joined = String.join(",", names);

// ── 지금 (Java 21+) ──────────────────────────
var names = users.stream()
        .filter(u -> u.age() >= 20)   // record 라 getter 가 age()
        .map(User::name)
        .sorted()
        .toList();                    // Java 16+ : 불변 리스트 한 방에
var joined = String.join(",", names);

// ── 타입 분기: Java 8 ────────────────────────
if (shape instanceof Circle) {
    Circle c = (Circle) shape;        // 형변환을 또 씁니다
    return Math.PI * c.getR() * c.getR();
} else if (shape instanceof Rect) { ... }

// ── 지금 (Java 21+) ──────────────────────────
return switch (shape) {               // sealed 라 default 가 필요 없습니다
    case Circle(double r)        -> Math.PI * r * r;
    case Rect(double w, double h) -> w * h;
};
여기서 중요한 것 — 줄 수가 준 게 아니라 틀릴 수 있는 자리가 줄었습니다. 형변환·널 검사·break 누락·가변 리스트 노출이 전부 문법 차원에서 사라집니다. “최신 문법을 쓰자”가 취향 문제가 아닌 이유입니다.

MODERN 02

가상 스레드 — 스레드를 아끼지 않아도 되는 시대

가상 스레드는 “빨라지는 기능”이 아니라 스레드를 자원으로 취급하지 않아도 되게 만드는 기능입니다. 그 차이를 이해하려면 스레드가 블로킹될 때 실제로 무슨 일이 벌어지는지부터 봐야 합니다. 여기서는 마운트·언마운트·캐리어라는 세 단어만 확실히 잡습니다.

가상 스레드의 정체는 블로킹 지점에서 스택을 힙으로 옮길 수 있는 스레드입니다 — 나머지는 전부 여기서 나옵니다.

만드는 법 네 가지 — 그리고 각각 언제

// ① 딱 하나 띄우고 잊기 (fire and forget)
Thread.startVirtualThread(() -> sendMail(order));

// ② 이름·예외 처리를 붙여서 (★ 운영 코드는 이쪽)
Thread t = Thread.ofVirtual()
        .name("settle-", 0)                     // settle-0, settle-1 …
        .uncaughtExceptionHandler((th, e) ->
                log.error("[{}] 실패", th.getName(), e))
        .start(() -> settle(id));
t.join();                                       // 기다릴 수 있습니다

// ③ 작업 단위로 뿌리고 결과를 모으기 (가장 흔한 형태)
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Item>> fs = ids.stream()
            .map(id -> ex.submit(() -> client.fetch(id)))
            .toList();
    for (var f : fs) collect(f.get());
}   // close() 가 전부 끝날 때까지 기다립니다 (try-with-resources)

// ④ 팩토리만 넘겨 기존 API 에 꽂기
ThreadFactory tf = Thread.ofVirtual().name("api-", 0).factory();
var ex = Executors.newThreadPerTaskExecutor(tf);

// 지금 가상 스레드 위인지 확인 (라이브러리에서 분기할 때)
boolean v = Thread.currentThread().isVirtual();
newVirtualThreadPerTaskExecutor() 는 “풀”이 아닙니다 — 이름 그대로 작업마다 새 가상 스레드를 만들고 끝나면 버립니다. 재사용하지 않으므로 ThreadLocal 오염도, 풀 크기 튜닝도 없습니다. ExecutorService 인터페이스를 그대로 쓰는 건 기존 코드를 안 고치기 위해서일 뿐입니다.

캐리어와 스케줄러 — 손잡이는 두 개뿐

# 가상 스레드를 실제로 굴리는 것은 전용 ForkJoinPool 입니다.
# 손잡이는 시스템 프로퍼티 두 개가 전부입니다.

# ① 동시에 '실행 중'일 수 있는 가상 스레드 수 (기본 = CPU 코어 수)
-Djdk.virtualThreadScheduler.parallelism=8

언제 이득이고 언제 아닌가 — 리틀의 법칙 한 줄 🟡 중급

숫자로 판단하기

리틀의 법칙:   필요한 동시 스레드 수 = 처리량(TPS) × 평균 응답시간(초)

[사례 A] 외부 API 를 부르는 조회 API
   목표 500 TPS, 외부 API 평균 400ms
   → 필요한 동시 실행 = 500 × 0.4 = 200 개
   플랫폼 스레드 200개 = 스택만 200MB, 컨텍스트 스위치 폭증
   가상 스레드 200개  = 사실상 공짜.  ✅ 이득이 큽니다

[사례 B] 느린 협력사 API (평균 3초) 를 100 TPS 로
   → 필요한 동시 실행 = 100 × 3 = 300 개
   기존엔 톰캣 maxThreads=200 에서 큐가 밀려 타임아웃
   ✅ 가상 스레드로 바꾸면 그냥 흘러갑니다

[사례 C] 이미지 리사이즈 · 암호화 · 압축 (CPU 를 계속 씀)
   → 동시에 진짜로 일할 수 있는 것은 '코어 수'뿐
   가상 스레드 1000개를 만들어도 캐리어가 8개면 8개만 돕니다
   ❌ 이득 없음. 오히려 컨텍스트가 늘어 미세하게 손해입니다

[사례 D] 이미 WebFlux·Netty 로 논블로킹인 코드
   → 이미 스레드를 안 붙잡고 있습니다
   ❌ 갈아탈 이유가 성능에는 없습니다 (가독성이라면 이유가 됩니다)

CPU 바운드에는 왜 소용없나

// ❌ 흔한 오해 — "가상 스레드니까 1만 개 돌리면 빠르겠지"
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var img : images) ex.submit(() -> resize(img));   // 순수 CPU 작업
}
//  캐리어는 코어 수(예: 8)뿐입니다.
//  가상 스레드 1만 개가 8자리를 두고 줄을 설 뿐,
//  총 CPU 시간은 1도 줄지 않습니다. 오히려 스택 청크 1만 개가 힙을 먹습니다.

// ✅ CPU 작업은 예전 그대로 — 코어 수만큼의 플랫폼 스레드 풀
private static final ExecutorService CPU =
        Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());

// ✅ 섞여 있으면 나눕니다 — I/O 는 가상, 계산은 고정 풀
try (var io = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = urls.stream()
        .map(u -> io.submit(() -> {
            byte[] raw = download(u);                 // I/O → 가상 스레드가 유리
            return CPU.submit(() -> resize(raw)).get(); // 계산 → 고정 풀로 위임
        })).toList();
}
한 줄 판단법 — “이 스레드는 대부분의 시간 동안 무엇을 하고 있나?” 기다리고 있다면 가상 스레드가 정답이고, 계산하고 있다면 코어 수만큼의 플랫폼 스레드 풀이 정답입니다. 이 질문 하나면 사례 A~D 를 전부 분류할 수 있습니다.

한 단계 더 — 컨티뉴에이션, 마법의 정체 🔴 고급

언마운트가 실제로 하는 일

가상 스레드가 socket.read() 를 부르면 대략 이런 일이 벌어집니다.

 1. JDK 내부의 소켓 구현이 "지금 읽을 게 없다"를 확인
 2. 파크(park) 요청 → Continuation.yield() 호출
 3. 지금까지 쌓인 스택 프레임을 힙의 StackChunk 객체로 복사
 4. 캐리어(ForkJoinPool worker)의 스택은 텅 비고 → 다음 작업을 집음
 5. 데이터가 도착하면 셀렉터가 이 가상 스레드를 다시 스케줄에 올림
 6. 아무 캐리어에나 마운트 — StackChunk 를 캐리어 스택으로 되돌림
 7. socket.read() 다음 줄부터 아무 일 없었다는 듯 계속 실행

핵심은 3번과 6번입니다.
  · 스택이 '옮길 수 있는 데이터'라서 가능한 일입니다
  · 옮기는 양은 '지금 쌓인 프레임'만큼이라 대개 아주 작습니다
  · 그래서 깊은 재귀 상태로 블로킹하면 언마운트 비용이 커집니다 ★

되돌아올 때 '같은 캐리어'라는 보장이 없습니다.
  → 캐리어 스레드에 묶인 상태(ThreadLocal 을 캐리어 기준으로 캐싱 등)를
    가정하는 코드는 전부 깨집니다. v03 에서 다룹니다.

가상 스레드 실전 함정 — 켜고 나서 만나는 것들

가상 스레드를 켠 뒤 “오히려 느려졌다”는 신고는 거의 항상 같은 네 가지입니다 — 핀닝 · ThreadLocal 폭증 · 커넥션 풀 · 다운스트림 과부하. 네 가지 전부 증상이 아니라 원인을 재는 법이 있습니다. 그걸 먼저 손에 넣습니다.

핀닝의 정의는 “캐리어를 붙잡은 채 블로킹하는 것” — Java 24 부터 원인의 90%가 런타임 업그레이드만으로 사라집니다.

① 핀닝 — 재는 법과 고치는 법

# ── Java 21~23 (플래그가 살아 있는 버전) ──────────────
java -Djdk.tracePinnedThreads=full -jar app.jar
#   핀닝될 때마다 스택을 통째로 찍습니다. 운영에는 부담이 큽니다.

# ── Java 24+ (★ 위 플래그는 제거됐습니다) ────────────
jcmd <pid> JFR.start name=pin settings=profile duration=120s \
     filename=/tmp/pin.jfr
jfr summary /tmp/pin.jfr | grep -i pinned
jfr print --events jdk.VirtualThreadPinned /tmp/pin.jfr | head -60
#   기본 임계값은 20ms — 그보다 오래 고정된 것만 기록됩니다

# 상시 관측: 애플리케이션 기동 시 JFR 을 얇게 켜 둡니다
java -XX:StartFlightRecording=settings=default,maxsize=200M,dumponexit=true \

Java 24 이후 jdk.tracePinnedThreads 는 없습니다 — 예전 블로그를 보고 이 플래그를 넣으면 조용히 무시되거나 경고만 뜹니다. “켰는데 아무것도 안 나온다”의 절반이 이 경우입니다. 24 부터는 JFR 이 유일한 창구라고 외우세요.

// ④ 마지막 카드: 논블로킹 드라이버(R2DBC 등) — 코드 스타일이 바뀝니다

방파제 다시 세우기 — 경계마다 세마포어

@Component
public class PartnerApiClient {

    // 협력사 API 는 동시 50건까지만 — 스레드 풀의 자리를 세마포어가 대신합니다
    private final Semaphore limit = new Semaphore(50);
    private final RestClient rest;

    public Quote quote(Req req) {
        boolean got;
        try {
            // ★ 무한 대기 금지 — 대기에도 상한을 둡니다
            got = limit.tryAcquire(300, TimeUnit.MILLISECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        }
        if (!got) throw new TooManyRequestsException("협력사 호출 포화");

        try {
            return rest.post().uri("/quote").body(req)
                       .retrieve().body(Quote.class);
        } finally {
            limit.release();
        }
    }
}

// 관측 — 대기 길이를 지표로 뽑아 두면 사고 때 바로 보입니다
Gauge.builder("partner.permits.available", limit, Semaphore::availablePermits)
     .register(registry);
세마포어는 “요청당 하나”가 아니라 “자원당 하나”입니다 — DB · 협력사 A · 협력사 B · 파일 저장소마다 따로 둡니다. 하나로 묶으면 느린 협력사 하나가 전부를 막는, 스레드 풀 시절과 똑같은 문제로 되돌아갑니다.
정리 — 가상 스레드를 켠 뒤 할 일은 네 가지입니다. 런타임을 24+ 로 올려 핀닝을 없애고, ThreadLocal 캐시를 걷어내고, 커넥션 풀과 타임아웃을 다시 잡고, 자원마다 세마포어로 방파제를 세우는 것. 진단은 전부 JFR + jcmd Thread.dump_to_file -format=json 두 도구면 됩니다.

직접 지정할 때 — 그리고 남는 손잡이

@Configuration
public class VirtualThreadConfig {

    // ① 톰캣 요청 처리 실행자를 직접 갈아끼우기
    @Bean
    TomcatProtocolHandlerCustomizer<?> protocolHandlerVirtualThreads() {
        return handler -> handler.setExecutor(
                Executors.newVirtualThreadPerTaskExecutor());
    }

    // ② @Async 용 실행자 — 이름을 붙여 두면 로그 추적이 삽니다
    @Bean(name = "applicationTaskExecutor")
    AsyncTaskExecutor applicationTaskExecutor() {
        var ex = new SimpleAsyncTaskExecutor("async-");
        ex.setVirtualThreads(true);
        ex.setConcurrencyLimit(500);   // ★ 무제한 생성 방지 (기본은 무제한)
        return ex;
    }

    // ③ CPU 작업 전용 — 여기는 절대 가상 스레드로 두지 않습니다
    @Bean("cpuExecutor")
    ExecutorService cpuExecutor() {
        return Executors.newFixedThreadPool(
                Runtime.getRuntime().availableProcessors());
    }
}

MODERN 05

구조적 동시성 — 동시 작업을 try 블록처럼 묶기

ExecutorService 로 세 개를 동시에 던지면, 그 셋은 서로 남남이고 부모와도 남남입니다. 하나가 터져도 나머지는 계속 돌고, 요청이 취소돼도 아무도 모릅니다. 구조적 동시성은 그 셋을 하나의 단위로 묶어 다 성공하거나 다 정리되거나를 보장합니다.

구조적 동시성의 약속은 성능이 아니라 “새는 작업이 없다”입니다 — 취소와 타임아웃이 공짜로 따라옵니다.
버전 상태를 먼저 확인하세요 (2026-08 기준) — StructuredTaskScope 는 Java 21 에서 인큐베이터로 나와 24 에서 프리뷰(JEP 499), 25 에서 5차 프리뷰(JEP 505), 26 에서 6차 프리뷰(JEP 525)로 이어졌습니다. 아직 정식 API 가 아니며 --enable-preview 가 필요하고, 21~24 와 25+ 의 API 모양이 다릅니다. 아래 코드는 Java 25 기준이며, 옛 형태도 함께 적어 둡니다. 공용 라이브러리에는 아직 넣지 마세요.

기본형 — 다 성공해야 한다

// Java 25 (JEP 505, preview)
import java.util.concurrent.StructuredTaskScope;

Dashboard load(long userId) throws Exception {
    try (var scope = StructuredTaskScope.open()) {   // 기본 = 전부 성공해야 함
        var user   = scope.fork(() -> userClient.find(userId));
        var orders = scope.fork(() -> orderClient.recent(userId));
        var point  = scope.fork(() -> pointClient.balance(userId));

        scope.join();          // 셋 다 끝날 때까지 — 하나라도 실패하면
                               // 나머지를 취소하고 여기서 예외를 던집니다
        return new Dashboard(user.get(), orders.get(), point.get());
    }   // 블록을 벗어나면 자식이 하나도 안 남습니다 (보장)
}

// ── Java 21~24 의 옛 형태 (블로그에서 이 모양을 자주 봅니다) ──
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> userClient.find(id));
    var order = scope.fork(() -> orderClient.recent(id));
    scope.join();
    scope.throwIfFailed();                 // 25 에서는 join() 이 대신합니다
    return new Dashboard(user.get(), order.get());
}
fork() 가 돌려주는 것은 Future 가 아니라 Subtask 입니다 — get() 은 join() 이후에만 부를 수 있습니다. join() 전에 부르면 IllegalStateException 입니다. “끝난 다음에 결과를 읽는다”를 타입이 강제하는 설계입니다.

조이너 — 언제 join 을 끝낼지 정하기

import java.util.concurrent.StructuredTaskScope.Joiner;

// ① 가장 먼저 성공한 하나만 (여러 공급자 중 빠른 쪽)
try (var scope = StructuredTaskScope.open(
        Joiner.<Quote>anySuccessfulResultOrThrow())) {
    scope.fork(() -> providerA.quote(req));
    scope.fork(() -> providerB.quote(req));
    return scope.join();          // 먼저 성공한 값. 나머지는 자동 취소
}

// ② 전부 성공해야 하고, 결과를 스트림으로 받기
try (var scope = StructuredTaskScope.open(
        Joiner.<Item, Stream<Subtask<Item>>>allSuccessfulOrThrow())) {
    ids.forEach(id -> scope.fork(() -> itemClient.find(id)));
    return scope.join().map(Subtask::get).toList();
}

// ③ 실패해도 끝까지 모으기 (부분 성공 허용 — 대시보드 위젯 같은 것)
try (var scope = StructuredTaskScope.open(Joiner.<Widget>awaitAll())) {
    var a = scope.fork(() -> widgetA());
    var b = scope.fork(() -> widgetB());
    scope.join();                                 // 예외를 던지지 않습니다
    return List.of(
        a.state() == Subtask.State.SUCCESS ? a.get() : Widget.empty(),
        b.state() == Subtask.State.SUCCESS ? b.get() : Widget.empty());
}

MODERN 06

스코프 값 — ThreadLocal 을 대신할 것 Java 25 정식

로그인 사용자·추적 ID·테넌트처럼 요청 하나 동안 어디서든 읽고 싶은 값을 메서드 인자로 계속 넘기는 것은 고통스럽습니다. 그래서 ThreadLocal 을 썼는데, ThreadLocal 은 언제 지워야 할지 아무도 모르고 가상 스레드에서는 개수만큼 늘어납니다. ScopedValue 는 그 자리를 불변 + 범위 한정으로 대신합니다.

ScopedValue 는 값을 스레드가 아니라 호출 범위에 매답니다 — 그래서 누수라는 개념이 없습니다.

기본 사용 — 세 줄이면 끝납니다

public final class RequestContext {
    // ① 상수로 하나 선언 (보통 static final)
    public static final ScopedValue<User>   USER  = ScopedValue.newInstance();
    public static final ScopedValue<String> TRACE = ScopedValue.newInstance();
}

// ② 경계에서 바인딩 — 이 안에서만 값이 보입니다
ScopedValue.where(RequestContext.USER, loginUser)
           .where(RequestContext.TRACE, traceId)      // 여러 개 체이닝 가능
           .run(() -> orderService.place(cmd));       // 값을 안 돌려줄 때

// 값을 돌려받고 싶으면 call (체크 예외도 던질 수 있습니다)
Receipt r = ScopedValue.where(RequestContext.USER, loginUser)
                       .call(() -> orderService.place(cmd));

// ③ 깊은 곳에서 읽기 — 인자로 안 넘겨도 됩니다
class OrderService {
    void place(Cmd cmd) {
        User u = RequestContext.USER.get();           // 그냥 읽습니다
        if (RequestContext.TRACE.isBound())           // 바인딩 여부 확인
            log.info("[{}] 주문", RequestContext.TRACE.get());
    }
}

// 바인딩 없이 get() 하면 NoSuchElementException 입니다 ★
// 선택적으로 쓰려면 isBound() 로 감싸거나 orElse 를 씁니다
User u = RequestContext.USER.orElse(User.anonymous());
API 이름이 몇 번 바뀌었습니다 — 예전 예제의 ScopedValue.runWhere(K, v, op)·callWhere(...) 정적 메서드는 지금은 없습니다. Java 25 정식 API 는 ScopedValue.where(K, v).run(...) / .call(...) 한 가지 형태입니다.

누수remove 누락 시구조적으로 불가

});

// ❌ 이런 건 안 됩니다 — 값을 바꿀 방법이 없습니다
// TENANT.set("other");                 // 그런 메서드가 없습니다

// → 가변 상태가 필요하면 '가변 객체'를 바인딩합니다 (권장하진 않습니다)
static final ScopedValue<Map<String,Object>> BAG = ScopedValue.newInstance();

실무 배선 — 필터에서 한 번만 묶습니다 🟡 중급

서블릿 필터에서 요청 전체를 감싸기

@Component
public class RequestContextFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        var traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
                              .orElseGet(() -> UUID.randomUUID().toString());
        var tenant  = resolveTenant(req);

        try {
            // ★ 핵심 — chain.doFilter 를 통째로 run 안에 넣습니다
            //    이 아래의 컨트롤러·서비스·리포지토리 전부가 범위 안입니다
            ScopedValue.where(RequestContext.TRACE, traceId)
                       .where(RequestContext.TENANT, tenant)
                       .call(() -> { chain.doFilter(req, res); return null; });
        } catch (IOException | ServletException | RuntimeException e) {
            throw e;
        } catch (Exception e) {
            throw new ServletException(e);
        }
    }
}

// MDC 도 같이 채워 두면 기존 로그 설정을 안 고쳐도 됩니다
// MDC.put("traceId", traceId);  ... finally { MDC.remove("traceId"); }
왜 필터여야 하나 — ScopedValue 는 호출 스택을 감싸야 값이 보입니다. 인터셉터의 preHandle 처럼 “들어올 때 한 번, 나갈 때 한 번” 구조에서는 감쌀 수가 없습니다. 그래서 필터(또는 AOP 어라운드)가 유일한 자리입니다.

MODERN 07

패턴 매칭 완전판 — if-instanceof 사슬의 끝

패턴 매칭은 “이 값이 이런 모양인지 확인하고, 맞으면 그 안을 꺼내는” 문법입니다. 확인과 꺼내기가 한 번에 일어나기 때문에 형변환이 사라지고, sealed 와 합치면 빠뜨린 경우를 컴파일러가 잡아 줍니다. 여기까지 오면 자바에서도 대수적 데이터 타입을 쓸 수 있습니다.

패턴 매칭의 진짜 가치는 짧아지는 것이 아니라 빠뜨린 경우를 컴파일러가 잡아 주는 것입니다.

패턴의 네 종류 — 한눈에

Object o = ...;

// ① 타입 패턴 — instanceof 안에서 (Java 16+)
if (o instanceof String s && s.length() > 3) {
    System.out.println(s.toUpperCase());   // 형변환 없이 바로
}
//  s 의 유효 범위(scope)가 '조건이 참인 곳'으로 자동 한정됩니다
if (!(o instanceof String s)) return;      // ★ 이 관용구가 아주 유용합니다
System.out.println(s.length());            // 여기서도 s 를 씁니다

// ② record 패턴 — 안을 분해 (Java 21+)
record Point(int x, int y) {}
if (o instanceof Point(int x, int y)) {    // x, y 가 바로 나옵니다
    System.out.println(x + y);
}

// ③ 중첩 패턴 — 분해 안에서 또 분해
record Line(Point from, Point to) {}
if (o instanceof Line(Point(var x1, var y1), Point p2)) {
    System.out.println(x1 + " → " + p2.x());
}

// ④ var 패턴 · 무시 패턴 (Java 21+)
if (o instanceof Line(var a, var _)) {     // _ = 안 쓰는 값
    System.out.println(a);
}
if (!(o instanceof X x)) return; 를 기억하세요 — “아니면 빠져나간다”를 먼저 쓰고 그 아래를 전부 평평하게 만드는 관용구입니다. 중첩된 if 로 오른쪽으로 밀리던 코드가 한 겹으로 펴집니다.

switch 패턴 — null 과 default 의 규칙

String describe(Object o) {
    return switch (o) {
        case null            -> "없음";          // ★ null 을 케이스로 쓸 수 있습니다
        case Integer i when i < 0 -> "음수 " + i;  // 가드(when)는 패턴 뒤에
        case Integer i       -> "정수 " + i;
        case String s        -> "문자열 " + s.length();
        case int[] arr       -> "배열 " + arr.length;
        default              -> "기타";
    };
}
//  · case null 을 안 쓰면 switch(null) 은 NullPointerException 입니다
//    (기존 switch 와 같은 동작 — 실수하기 쉬우니 명시하는 습관을)
//  · "case null, default ->" 로 묶을 수도 있습니다

// ❌ 순서를 잘못 쓰면 컴파일 에러가 납니다 (도미넌스)
switch (o) {
    case Object obj -> "아무거나";
    case String s   -> "문자열";   // error: this case label is dominated
}

// ❌ 가드가 있어도 '가려짐' 판정은 패턴 기준입니다
switch (n) {
    case Integer i       -> "정수";
    case Integer i when i > 0 -> "양수";   // ❌ 이미 위에서 다 잡힙니다
}
가드(when)는 “같은 타입 안에서 더 좁히는 조건”입니다 — 따라서 가드가 붙은 케이스를 먼저 쓰고 가드 없는 같은 타입을 뒤에 씁니다. “좁은 것 → 넓은 것” 순서만 지키면 컴파일러가 나머지를 확인해 줍니다.

sealed 와 합치기 — 자바의 대수적 데이터 타입 🟡 중급

결과 타입을 예외 대신 값으로

// 한 파일 안에 계층을 다 적는 것이 관례입니다
public sealed interface PayResult {
    record Approved(String txId, long amount)        implements PayResult {}
    record Declined(String code, String message)     implements PayResult {}
    record Pending (String txId, Instant retryAfter) implements PayResult {}
}
//  permits 를 생략하면 '같은 파일 안의 구현체'로 자동 한정됩니다

// 쓰는 쪽 — default 가 없다는 점이 핵심입니다
String render(PayResult r) {
    return switch (r) {                 // 전부 적지 않으면 컴파일 에러 ★
        case Approved(String tx, long amt) -> "승인 " + amt + "원 (" + tx + ")";
        case Declined(String code, var msg) -> "거절 [" + code + "] " + msg;
        case Pending(var tx, var after)     -> "대기 — " + after + " 이후 재시도";
    };
}

// 나중에 Refunded 를 추가하면?
//   → render() 가 곧바로 컴파일 에러가 납니다.
//   → "처리해야 할 곳"이 빌드 시점에 전부 드러납니다 ★★
//   → 이것이 예외나 enum + if 사슬로는 절대 못 얻는 안전망입니다

방문자 패턴을 대체하는 법

❌ 예전 — 방문자 패턴(Visitor)
interface Node { <R> R accept(Visitor<R> v); }
interface Visitor<R> {
    R visitNum(Num n);
    R visitAdd(Add a);
    R visitMul(Mul m);
}
final class Num implements Node {
    final int v;
    public <R> R accept(Visitor<R> vi) { return vi.visitNum(this); }
}
// 새 노드를 추가하면 Visitor 인터페이스와
// 모든 구현체를 전부 고쳐야 합니다 (그래도 컴파일러가 잡아 주긴 합니다)
// 대신 accept/visit 보일러플레이트가 노드 수 × 방문자 수만큼 늘어납니다
✅ 지금 — sealed + switch
sealed interface Node {
    record Num(int v)              implements Node {}
    record Add(Node l, Node r)     implements Node {}
    record Mul(Node l, Node r)     implements Node {}
}

int eval(Node n) {
    return switch (n) {
        case Num(int v)        -> v;
        case Add(var l, var r) -> eval(l) + eval(r);
        case Mul(var l, var r) -> eval(l) * eval(r);
    };
}
// 노드 정의 5줄, 연산 하나당 함수 하나.
// 새 노드를 추가하면 모든 switch 가 컴파일 에러로 알려 줍니다.
어느 쪽이 유리한가 — 타입이 자주 늘어나면 방문자(구현체만 추가), 연산이 자주 늘어나면 sealed + switch(함수만 추가)가 유리합니다. 도메인 모델은 대개 타입은 안정적이고 연산이 계속 늘어나므로 실무에서는 후자가 압도적으로 잘 맞습니다.

record · sealed · 값 지향 설계 — 무엇을 어디에 쓸까

record 문법 자체는 ☕ Java 기초 탭에서 다뤘습니다. 여기서는 설계 판단만 봅니다 — 어디까지 record 로 만들고 어디서 클래스로 돌아가야 하는지, sealed 계층을 어떻게 자르는지, DTO 를 경계마다 몇 개 둘 것인지. 그리고 앞으로 올 값 클래스(Valhalla)가 이 판단을 어떻게 바꾸는지.

sealed 계층의 값어치는 “빠뜨린 곳이 컴파일 에러로 드러난다” 한 줄에 전부 있습니다.

record 를 “제대로” 만드는 법

public record Money(String currency, long minor) implements Comparable<Money> {

    // ① 컴팩트 생성자 — 검증과 '정규화'를 여기서 합니다
    public Money {
        Objects.requireNonNull(currency, "currency");
        if (currency.length() != 3)
            throw new IllegalArgumentException("통화 코드는 3자리: " + currency);
        currency = currency.toUpperCase();   // ★ 파라미터에 재대입 = 정규화
        if (minor < 0) throw new IllegalArgumentException("음수 금액");
    }

    // ② 정적 팩토리 — 읽기 좋은 이름을 줍니다
    public static Money krw(long won) { return new Money("KRW", won); }
    public static Money zero(String cur) { return new Money(cur, 0); }

    // ③ 연산은 새 값을 돌려줍니다 (with 관례)
    public Money plus(Money other) {
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("통화 불일치");
        return new Money(currency, Math.addExact(minor, other.minor));
    }

    @Override public int compareTo(Money o) { return Long.compare(minor, o.minor); }
    @Override public String toString() { return minor + " " + currency; }
}
표준 생성자를 private 으로 숨길 수는 없습니다 ★ — record 의 표준 생성자는 record 자체보다 덜 공개적일 수 없습니다. public record 면 new Money(...) 를 막을 방법이 없습니다. 정말 팩토리만 허용하고 싶다면 record 를 패키지 전용으로 두고 인터페이스를 공개하는 구성을 쓰세요.

static OrderEvent upgrade(OrderEventV1 old) {
    return switch (old) {
        case OrderEventV1.Placed(var id, var at, var oid, var amt)

        case OrderEventV1.Canceled(var id, var at, var oid, var r)

// ① permits 를 명시하면 다른 파일에도 둘 수 있습니다 (같은 패키지/모듈 안)
public sealed interface Shape permits Circle, Rect, Triangle {}
public record Circle(double r)            implements Shape {}
public record Rect(double w, double h)    implements Shape {}
public record Triangle(double b, double h) implements Shape {}

// ② 하위 타입은 셋 중 하나여야 합니다
//    final      — 더 못 늘어남 (record 는 자동으로 final)
//    sealed     — 또 한 겹 제한 (트리 구조)
//    non-sealed — 여기서부터는 자유롭게 상속 허용 ★
public sealed interface Payment permits Card, Bank, Wallet {}
public non-sealed interface Wallet extends Payment {}   // 외부 확장 지점

// ③ 같은 모듈(모듈이 없으면 같은 패키지) 안에 있어야 합니다
//    → 라이브러리 사용자가 내 계층을 못 늘리게 막는 효과가 있습니다
언제 sealed 를 쓰나 — 한 줄 판단
“경우의 수가 정해져 있고, 그걸 빠짐없이 다뤄야 한다” → sealed.
“누구든 새 구현을 추가할 수 있어야 한다” → 그냥 인터페이스.
결제 결과·주문 상태·파싱 결과·명령은 전자이고, 플러그인·전략·리포지토리는 후자입니다.

값 클래스(Valhalla) — 무엇이 바뀔까

지금 record 의 한계는 '여전히 객체'라는 점입니다.

  record Point(int x, int y)
    → 힙에 객체 하나 + 헤더 + 참조.  배열이면 Point[] 는
      '포인터의 배열'이라 값들이 메모리에 흩어집니다.
    → 100만 개를 순회하면 캐시 미스가 지배적입니다.

Valhalla 프로젝트의 '값 클래스'는 여기에 답을 줍니다.
  · 정체성(identity)이 없는 클래스 — == 가 필드 비교와 같아집니다
  · JVM 이 힙 할당을 생략하고 필드를 '펼쳐서' 배치할 수 있습니다
  · 배열이 진짜 '값의 배열'이 되어 C 구조체 배열처럼 촘촘해집니다
  · 동기화(synchronized)와 정체성 해시가 금지됩니다

★ 지금 할 수 있는 준비는 이것뿐입니다 —
  ① 값 타입은 record 로, 불변으로 만들어 두기
  ② 값 객체에 synchronized 를 걸지 않기
  ③ == 대신 equals 로 비교하기 (지금도 옳은 습관입니다)
  ④ 정체성에 의존하지 않기 (IdentityHashMap 등)
  → 이렇게 짜 두면 값 클래스가 나왔을 때
    선언 한 줄만 바꿔서 성능을 얻습니다.
정리 — 값은 record, 정해진 경우의 수는 sealed, 상태가 변하는 것은 클래스입니다. record 는 컴팩트 생성자에서 검증·정규화하고 정적 팩토리로 이름을 주는 것까지가 한 세트이고, DTO 는 API · 유스케이스 · 영속 세 겹으로 나누는 것이 기본형입니다. 이렇게 불변·무정체성으로 짜 두면 나중에 값 클래스가 나왔을 때 그대로 이득을 봅니다.

FFM API — JNI 없이 C 라이브러리 부르기 Java 22 정식

예전에는 자바에서 C 함수를 부르려면 C 로 브리지 코드를 짜서 컴파일해야 했습니다(JNI). java.lang.foreign 은 그 과정을 통째로 없앴습니다 — 자바 코드만으로 네이티브 함수를 부르고 네이티브 메모리를 다룹니다. 게다가 메모리 수명과 경계를 JVM 이 검사해 줍니다.

FFM 은 “C 를 안 짜고 C 를 부르는 법”입니다 — 메모리 수명은 Arena, 안전은 MemorySegment 가 맡습니다.

가장 짧은 예제 — strlen 부르기

import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

public class Ffm {
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();
        SymbolLookup libc = linker.defaultLookup();      // 표준 C 라이브러리

        // size_t strlen(const char *s)
        MethodHandle strlen = linker.downcallHandle(
                libc.find("strlen").orElseThrow(),
                FunctionDescriptor.of(ValueLayout.JAVA_LONG,   // 반환
                                      ValueLayout.ADDRESS));  // 인자

        try (Arena arena = Arena.ofConfined()) {          // ★ 수명 = 이 블록
            MemorySegment cs = arena.allocateFrom("안녕 java");  // 널 종료 문자열
            long len = (long) strlen.invokeExact(cs);
            System.out.println(len);                      // 바이트 길이
        }   // 여기서 네이티브 메모리가 전부 해제됩니다
    }
}

invokeExact 를 쓰세요 — invoke 는 타입이 안 맞으면 실행 중에 변환을 시도해 느리고, invokeExact 는 시그니처가 정확히 일치해야 하는 대신 직접 호출만큼 빠릅니다. 캐스팅((long))을 빼먹으면 WrongMethodTypeException 이 납니다.

    · 수 초면 충분 → AOT 캐시로 끝. 가장 값싼 선택입니다.
    · 수십 ms 여야 함 → native-image 나 CRaC 를 검토합니다.
      (함수형 워크로드 · 스케일 투 제로)

Q2. 오래 떠 있는 서버인가?
    · 예 → native-image 는 손해일 수 있습니다.
           JIT 이 없어서 '오래 돌수록 빨라지는' 이점을 못 얻습니다.
    · 아니오(짧게 뜨고 사라짐) → native-image 가 유리합니다.

★ 대부분의 웹 서비스는 Q1=수 초, Q2=예 입니다.
  → 답은 AOT 캐시입니다. native-image 는 필요할 때만.

@Service
@RequiredArgsConstructor
public class IndexService {

    private final VectorStore vectorStore;

    public void index(Resource pdf) {
        // ① 읽기
        var reader = new TikaDocumentReader(pdf);
        List<Document> docs = reader.get();

        // ② 조각내기 — 너무 크면 근거가 흐려지고, 너무 작으면 맥락이 끊깁니다
        var splitter = new TokenTextSplitter(800, 350, 5, 10000, true);
        List<Document> chunks = splitter.apply(docs);

        // ③ 메타데이터를 붙여 두면 나중에 필터로 좁힐 수 있습니다 ★
        chunks.forEach(d -> {
            d.getMetadata().put("source", pdf.getFilename());
            d.getMetadata().put("dept", "cs");
            d.getMetadata().put("indexedAt", Instant.now().toString());
        });

        // ④ 임베딩 + 저장 (한 번에)
        vectorStore.add(chunks);
    }
}
조각 크기가 RAG 품질의 절반입니다 — 너무 크면 근거 안에 잡음이 섞여 모델이 헷갈리고, 너무 작으면 문장이 끊겨 의미가 사라집니다. 600~1000 토큰 + 겹침 100~300 부터 시작해 실제 질문 20개로 검색 결과를 눈으로 확인하며 조정하세요.

@Bean
ChatClient ragClient(ChatClient.Builder b, VectorStore store) {
    return b.defaultAdvisors(
                QuestionAnswerAdvisor.builder(store)
                    .searchRequest(SearchRequest.builder()
                            .topK(4)
                            .similarityThreshold(0.6)   // 너무 먼 것은 버립니다
                            .build())
                    .build(),
                new SimpleLoggerAdvisor())              // 프롬프트 로깅
            .build();
}

// 방법 B — 직접 조립 (근거를 화면에 같이 보여 줘야 할 때 ★)
public Answer ask(String question) {
    List<Document> found = vectorStore.similaritySearch(
            SearchRequest.builder()
                .query(question).topK(4).similarityThreshold(0.6)
                .filterExpression("dept == 'cs'")       // 메타데이터 필터
                .build());

    String context = found.stream().map(Document::getText)
                          .collect(Collectors.joining("\n---\n"));

    String answer = chat.prompt()
            .system("아래 [근거]만 사용해 답하라. 없으면 모른다고 답하라.")
            .user(u -> u.text("""
                    [근거]
                    {ctx}

                    [질문]
                    {q}
                    """).param("ctx", context).param("q", question))
            .call().content();

    // 출처를 함께 돌려주면 사용자가 검증할 수 있습니다 — 신뢰도가 크게 오릅니다
    var sources = found.stream()
            .map(d -> (String) d.getMetadata().get("source")).distinct().toList();
    return new Answer(answer, sources);
}

    rewrite("org.openrewrite.recipe:rewrite-migrate-java:latest.release")
    rewrite("org.openrewrite.recipe:rewrite-spring:latest.release")
}

rewrite {
    activeRecipe(
        "org.openrewrite.java.migrate.UpgradeToJava21",
        // Spring Boot 3 로 올릴 때 javax → jakarta 까지 함께
        "org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_5"
    )
}
# 먼저 '무엇을 바꿀지'만 봅니다 — 절대 바로 적용하지 마세요
./gradlew rewriteDryRun
#   build/reports/rewrite/rewrite.patch 에 diff 가 나옵니다

# 확인한 뒤 적용
./gradlew rewriteRun
git diff --stat            # 변경량을 먼저 보고, 커밋을 잘게 나눕니다

잘 먹히는 것: 불필요한 final·다이아몬드 연산자·List.of· String.format → 텍스트 블록·@Deprecated API 치환·javax→jakarta. 잘 안 먹히는 것: record 로의 변환, 패턴 매칭 도입 — 설계 판단이 필요해서 사람이 해야 합니다.

기계 변환 PR 은 반드시 따로 — 500 파일이 바뀐 PR 에 기능 수정이 섞이면 아무도 리뷰할 수 없습니다. “레시피 하나 = 커밋 하나”로 나누면 문제가 생겼을 때 그 커밋만 되돌리면 됩니다.
