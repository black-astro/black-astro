장애 첫 5분 런북 — 분류하고, 보고, 멈춘다

장애 대응에서 가장 비싼 실수는 원인부터 찾으려는 것입니다. 첫 5분의 목표는 원인이 아니라 증상 분류 → 최근 변경 확인 → 출혈을 멈출지 결정입니다. 이 순서를 몸에 익혀 두면 알람이 울렸을 때 손이 먼저 움직입니다.

OPS 02

스레드 덤프 읽기 — "지금 다들 뭐 하고 있나"를 찍은 사진

"서버가 느리다"의 절반 이상은 스레드 덤프 세 장이면 원인이 보입니다. 덤프는 모든 스레드가 그 순간 서 있는 코드 줄을 찍은 사진입니다. 한 장은 우연일 수 있으니 5초 간격으로 세 장 떠서, 계속 같은 곳에 몰려 있는 스레드를 찾습니다. 스레드 상태와 락의 원리는 🧬 고급 탭 ADV 04~05에 있고, 여기서는 읽는 법만 다룹니다.

해부도 — waiting to lock 의 주소로 locked 를 검색하면 범인 스레드가 나옵니다. 덤프 읽기의 절반이 이 검색입니다.

덤프 뜨기 — 5초 간격 3장

# 자바 프로세스 찾기 (JDK 의 jps 또는 ps)
jps -l
#   1 /app/app.jar          ← 컨테이너 안에서는 보통 PID 1

# 권장: jcmd (-l 은 jstack 과 같은 락 정보 포함)
for i in 1 2 3; do
  jcmd 1 Thread.print -l > /tmp/td-$(date +%H%M%S).txt
  sleep 5
done

# 쿠버네티스 — 파드 안에서 떠서 로컬로 가져오기
kubectl -n shop exec order-api-7d9f8-x2k4p -- \
  sh -c 'for i in 1 2 3; do jcmd 1 Thread.print -l > /tmp/td-$i.txt; sleep 5; done'
kubectl -n shop cp order-api-7d9f8-x2k4p:/tmp/td-1.txt ./td-1.txt

# JDK 가 없는 이미지(JRE 만)라면 — 표준 출력으로 덤프가 찍힙니다
kill -3 1          # SIGQUIT. 프로세스는 죽지 않습니다
kubectl -n shop logs order-api-7d9f8-x2k4p --since=1m > td.txt
JRE 이미지에는 jcmd 가 없습니다 — eclipse-temurin:25-jre 같은 이미지라면 kill -3 이 유일한 길입니다. 운영 이미지를 만들 때 jcmd 를 쓸 수 있게 할지 미리 정해 두세요(JDK 이미지 또는 jlink 에 jdk.jcmd 모듈 포함).

상태덤프에서의 뜻많으면

OPS 03

힙 덤프와 OOM — 메시지가 이미 칸 이름을 알려 줍니다

OutOfMemoryError 는 한 종류가 아닙니다. 어느 메모리 칸이 찼는지가 메시지에 그대로 찍히고, 칸마다 원인과 처방이 완전히 다릅니다. 그리고 힙이 원인이라면 죽는 순간의 힙 덤프가 유일한 증거입니다 — 그래서 덤프 옵션은 장애 전에 켜 둬야 합니다. 힙 구조와 MAT 의 원리는 🔬 전문가 탭 DEEP 07에 있습니다.

메모리 배치 — 힙만 메모리가 아닙니다. Xmx 를 컨테이너 한도와 같게 잡으면 나머지 칸이 들어갈 자리가 없어 OOMKilled 가 납니다.

OOM 다섯 종류 — 메시지별 첫 조치

OOMKilled 에는 힙 덤프가 없습니다 — 운영체제가 SIGKILL 로 죽였기 때문에 JVM 은 덤프를 쓸 기회가 없습니다. "OOM 인데 덤프가 안 남았다"면 거의 이것입니다. kubectl describe pod 의 Reason: OOMKilled 로 확인합니다.

장애 전에 켜 둘 JVM 옵션 — 그대로 복사

# Dockerfile 또는 Deployment 의 JAVA_TOOL_OPTIONS
JAVA_TOOL_OPTIONS="\
 -XX:MaxRAMPercentage=70.0 \
 -XX:+HeapDumpOnOutOfMemoryError \
 -XX:HeapDumpPath=/dumps \
 -XX:+ExitOnOutOfMemoryError \
 -XX:MaxMetaspaceSize=512m \
 -XX:MaxDirectMemorySize=256m \
 -XX:NativeMemoryTracking=summary \
 -Xlog:gc*:file=/dumps/gc-%p.log:time,uptime,level,tags:filecount=5,filesize=20m"

# HeapDumpPath 가 디렉터리면 java_pid<PID>.hprof 로 저장됩니다
# /dumps 는 반드시 '파드가 죽어도 남는' 볼륨이어야 합니다
옵션왜
HeapDumpOnOutOfMemoryError죽는 순간 증거 확보
ExitOnOutOfMemoryError반쯤 죽은 채 살아 있지 않게 — 재시작이 낫다
MaxMetaspaceSize기본은 무제한 — 누수가 컨테이너를 죽임
NativeMemoryTracking힙 밖 메모리를 칸별로 보기(약간의 비용)

OPS 04

GC 로그 해석과 튜닝 — 플래그보다 로그 한 줄이 먼저

GC 튜닝의 90%는 힙 크기를 맞게 주는 것이고, 나머지 10%를 판단하려면 GC 로그가 있어야 합니다. 로그 없이 플래그를 바꾸는 것은 증상 없이 약을 바꾸는 것과 같습니다. G1 · ZGC 의 내부 동작은 🔬 전문가 탭 DEEP 06, 운영 JVM 튜닝 전반은 🧬 고급 탭 ADV 13을 보세요.

산점도 — 튀는 점 하나가 장애입니다. GC 로그를 보는 목적은 평균이 아니라 최댓값과 그 이유를 찾는 것입니다.

컨테이너에서 자주 당하는 것

❌ 아무것도 안 줌
기본 MaxRAMPercentage 는 25%입니다. 2 GiB 컨테이너에 힙 512 MiB — 메모리는 남는데 Java heap space 로 죽습니다.
❌ -Xmx 를 한도와 같게
-Xmx2g + 한도 2Gi — 힙 밖 칸이 들어갈 자리가 없어 OOMKilled.

정리 — GC 로그는 항상 켜 둡니다(비용 거의 없음). 볼 것은 Pause Full · GC 후 힙 추세 · 멈춤 최댓값 세 가지. 대부분 G1 + 맞는 힙 크기로 끝나고, 컨테이너에서는 MaxRAMPercentage 를 65~75%로, CPU 는 2개 이상을 주거나 GC 를 명시하세요.
OPS 05

커넥션 풀 고갈 — 풀을 늘리기 전에 '쥔 시간'을 보세요

자바 웹 서비스 장애에서 가장 자주 보는 로그 한 줄이 Connection is not available, request timed out 입니다. DB 는 한가한데 서비스가 멈춘다면 거의 이것입니다. 원인은 대개 풀이 작아서가 아니라 커넥션을 쥐고 다른 일을 하는 코드입니다. 풀 크기 계산 · 설정값 · 안티패턴 순서로 봅니다.

게이지 — 세 값을 나란히 놓아야 진단이 됩니다. 왼쪽 둘만 보면 "풀을 늘리자"가 되고, 셋을 보면 "누가 쥐고 있나"가 됩니다.

풀 크기 계산 — 리틀의 법칙

필요한 커넥션 수 = 초당 트랜잭션 × 커넥션을 쥐는 평균 시간(초)

예) 인스턴스 하나에 초당 200 트랜잭션, 쥐는 시간 평균 25 ms
    200 × 0.025 = 5개   →  여유 2배  →  maximumPoolSize = 10

같은 트래픽인데 쥐는 시간이 1.8 s 라면?
    200 × 1.8   = 360개  →  풀로 해결할 수 없는 숫자
                            (DB max_connections 를 먼저 넘습니다)

슬로우 쿼리 실전 추적 — 가장 느린 것 말고 '총합이 큰 것'

"느린 쿼리 찾아 주세요"라는 말을 들으면 보통 한 번에 4초 걸리는 리포트 쿼리를 찾습니다. 그런데 서비스를 실제로 무겁게 만드는 것은 대개 3ms 짜리가 5만 번 도는 쿼리입니다. 이 섹션은 DB · 앱 · 테스트 세 곳에서 쿼리를 잡는 법을 다룹니다. N+1 을 고치는 JPA 기법(fetch join · batch size)은 🧩 JPA 심화 탭에 있습니다.

막대 — 총합으로 정렬하면 N+1 이 맨 위로 올라옵니다. 평균으로 정렬하면 영영 안 보입니다.

DB 에서 잡기 — 총합 상위 10개

-- PostgreSQL (pg_stat_statements 확장, PG 13+ 컬럼명)
SELECT calls,
       round(total_exec_time)       AS total_ms,
       round(mean_exec_time::numeric, 1) AS mean_ms,
       rows,
       left(query, 80)              AS query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  10;

-- MySQL 8 (performance_schema — 타이머 단위는 피코초)
SELECT LEFT(DIGEST_TEXT, 80)              AS query,
       COUNT_STAR                         AS calls,
       ROUND(SUM_TIMER_WAIT / 1e12, 1)    AS total_s,
       ROUND(AVG_TIMER_WAIT / 1e9, 1)     AS avg_ms
FROM   performance_schema.events_statements_summary_by_digest
ORDER  BY SUM_TIMER_WAIT DESC
LIMIT  10;

소켓 타임아웃은 '최후의 안전망' — 쿼리 타임아웃보다 길게 둡니다. 쿼리 타임아웃은 DB 가 쿼리를 정상 취소하지만, 소켓 타임아웃은 커넥션을 끊어 버리기 때문입니다.

무중단 배포 — 끄는 순서와 DB 호환이 전부

배포할 때마다 5xx 가 몇십 건씩 튄다면 원인은 둘 중 하나입니다. 파드를 끄는 순서가 틀렸거나, 새 코드와 옛 코드가 같은 DB 를 동시에 쓰는 몇 분을 생각하지 않은 것입니다. 쿠버네티스 · Docker 배포 기초는 🍃 Spring Boot 탭 BOOT 16~17에 있고, 여기서는 그 두 가지만 정확히 맞춥니다.

시퀀스 — 1번과 2번이 같은 순간이라는 것이 핵심입니다. preStop 의 sleep 은 버그 회피가 아니라 이 경쟁을 흡수하는 장치입니다.

실무에선 이렇게 — DB 마이그레이션은 expand-contract 🔴 실무

파이프라인 — 되돌릴 수 없는 단계는 맨 끝 하나뿐이게 쪼갭니다. 그래서 롤백이 늘 가능합니다.

Flyway 로 나눠 쓰기 — user_name → display_name

-- V41__add_display_name.sql        (① 확장 — 앱 v1 과도 호환)
ALTER TABLE member ADD COLUMN display_name VARCHAR(100) NULL;

-- 앱 v2: 저장할 때 user_name · display_name 둘 다 씀

-- V42__backfill_display_name.sql    (③ 백필 — 큰 테이블은 배치로 나눠서)
UPDATE member SET display_name = user_name
WHERE  display_name IS NULL AND id BETWEEN 1 AND 100000;

-- 앱 v3: display_name 을 읽음 · v4: user_name 쓰기 중단

-- V45__drop_user_name.sql           (⑥ 수축 — 최소 한 번의 배포 주기 뒤)
ALTER TABLE member DROP COLUMN user_name;

호환되지 않는 변경 · 안전한 대체

한 번에 하면 깨지는 것안전한 대체
컬럼 이름 변경위의 6단계
NOT NULL 컬럼 추가NULL 허용 + 기본값 → 백필 → 제약 추가
컬럼 삭제코드에서 먼저 제거 → 다음 배포에 DROP
타입 변경새 컬럼 추가 후 이전
큰 테이블 인덱스PG CONCURRENTLY · MySQL 온라인 DDL
JPA 엔티티의 함정 — 옛 앱 v1 의 엔티티에 없는 NOT NULL 컬럼이 생기면 v1 의 INSERT 가 전부 실패합니다. 그리고 spring.jpa.hibernate.ddl-auto 는 운영에서 반드시 validate 또는 none 입니다 — 스키마는 Flyway 만 바꿉니다.
정리 — 끌 때는 preStop sleep → SIGTERM → 새 요청 거부 → 진행 중 완료 → 종료, grace period 는 그 합보다 길게. liveness 에는 외부 의존성을 넣지 않고, DB 변경은 expand-contract 로 쪼개서 "지금 앱과 이전 앱이 같은 스키마에서 돈다"를 늘 지킵니다.

설정 · 비밀 관리 — "어느 값이 이겼나"와 "어디에 남았나"

CPU 프로파일링 — JFR 과 플레임 그래프로 핫스팟 찾기
