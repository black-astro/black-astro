DEEP 03

Java Memory Model — happens-before

“가끔만 틀리는” 버그의 근원. 동시성의 이론적 기반입니다.

왜 필요한가 — 가시성과 재배치

// 이 코드는 "영원히 끝나지 않을 수" 있습니다
class Worker {
    private boolean running = true;         // ❌ volatile 없음

    public void run() {
        while (running) { doWork(); }        // 컴파일러가 이렇게 바꿀 수 있습니다:
                                             //   if (running) while(true) doWork();
    }
    public void stop() { running = false; }  // 다른 스레드에서 호출
}

// 원인 두 가지
//  ① 가시성 — 각 코어의 캐시에 값이 따로 있어 변경이 안 보임
//  ② 재배치 — 컴파일러·CPU 가 순서를 바꿈 (단일 스레드 결과만 보장)
// ✅ volatile — 가시성 + 재배치 금지
private volatile boolean running = true;

// volatile 이 보장하는 것
//  · 쓰기는 즉시 메인 메모리에, 읽기는 항상 메인 메모리에서
//  · 이 변수 앞뒤의 명령이 넘나들지 못함 (메모리 배리어)
// ★ 보장하지 않는 것: 원자성
volatile int count;
count++;        // ❌ 여전히 안전하지 않습니다 (읽기+더하기+쓰기 = 3단계)
                //    → AtomicInteger 를 쓰세요 (z04)
“테스트에서는 잘 되던데요” — 이런 버그는 코어 수·JIT 최적화 시점·부하에 따라 나타납니다. 개발 PC 에서는 안 나고 운영에서만 재현되는 전형적인 유형이며, 재현이 안 되므로 코드로 판단해야 합니다.

happens-before 규칙

A happens-before B의미
같은 스레드의 앞 문장 → 뒤 문장프로그램 순서
volatile 쓰기 → 그 변수 읽기가장 많이 쓰는 규칙
unlock → 같은 락의 locksynchronized
Thread.start() → 그 스레드의 첫 문장시작 규칙
스레드 종료 → join() 반환종료 규칙
final 필드 초기화 → 생성자 반환불변 객체가 안전한 이유
// 안전 발행(safe publication) — 이 규칙들이 실제로 쓰이는 자리
class Config {
    private final Map<String, String> values;   // ★ final

    Config(Map<String, String> v) {
        this.values = Map.copyOf(v);             // 불변 복사
    }
}
// final 필드는 생성자가 끝나는 시점에 "완전히 초기화된 상태"가
// 다른 스레드에도 보이는 것이 보장됩니다.
// → 불변 객체는 어떤 동기화 없이도 여러 스레드가 공유할 수 있습니다 ★

// 이중 검사 잠금 — volatile 이 없으면 깨집니다
class Holder {
    private static volatile Holder instance;     // ★ volatile 필수
    static Holder get() {
        if (instance == null) {
            synchronized (Holder.class) {
                if (instance == null) instance = new Holder();
            }
        }
        return instance;
    }
}
// ★ 사실 이럴 필요 없습니다 — 정적 홀더나 enum 을 쓰세요 (z14)
실무 결론 — ① 불변 객체를 기본으로 (record · final 필드), ② 공유 상태가 꼭 필요하면 java.util.concurrent 를 쓰고, ③ volatile 은 플래그 하나 정도에만, ④ 직접 락을 설계하기 전에 이미 있는 자료구조를 먼저 찾으세요.
동시성에서 어려운 것은 원자성보다 언제 보이는가입니다.
DEEP 04

CAS · 락프리 자료구조

락 없이 원자성을 만드는 방법. ConcurrentHashMap 의 내부입니다.

CAS — Compare And Swap

CPU 명령 하나로 다음을 원자적으로 수행합니다.

  if (메모리의 값 == 기대값) { 메모리 = 새값; return true; }
  else                       { return false; }

낙관적 접근
  1. 현재 값을 읽는다
  2. 새 값을 계산한다
  3. CAS 로 바꾼다 → 실패하면 1부터 다시 (스핀)

장점: 락 없음 → 컨텍스트 스위칭·데드락 없음
단점: 경쟁이 심하면 재시도가 늘어 오히려 느려짐
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();               // 내부적으로 CAS 루프

// CAS 를 직접 쓰는 형태
AtomicReference<State> ref = new AtomicReference<>(initial);
State cur, next;
do {
    cur = ref.get();
    next = cur.withUpdated(value);        // ★ 불변 객체로 새 상태 계산
} while (!ref.compareAndSet(cur, next));

// 함수형 갱신 (위 루프를 대신해 줍니다)
ref.updateAndGet(s -> s.withUpdated(value));
map.compute(key, (k, v) -> v == null ? 1 : v + 1);
ABA 문제 — 값이 A → B → A 로 돌아오면 CAS 는 변하지 않았다고 착각합니다. AtomicStampedReference(버전 태그)로 해결하지만, 불변 객체를 새로 만들어 교체하면 애초에 발생하지 않습니다.

고경쟁에서는 LongAdder

// AtomicLong — 스레드 수가 많으면 CAS 실패가 폭증합니다
AtomicLong hits = new AtomicLong();
hits.incrementAndGet();       // 32 스레드에서 경쟁 → 처리량 급락

// ★ LongAdder — 셀을 여러 개 두고 나눠 더한 뒤 합칩니다
LongAdder hits = new LongAdder();
hits.increment();             // 경쟁 시 수 배 빠름
hits.sum();                   // 읽을 때 합산 (약간 느림)

// 기준
//   읽기가 잦고 정확한 순간값이 필요 → AtomicLong
//   쓰기가 압도적 (카운터·메트릭)     → LongAdder ★
// VarHandle — Unsafe 를 대체하는 공식 API (Java 9+)
class Node {
    private volatile Object value;
    private static final VarHandle VALUE;
    static {
        try {
            VALUE = MethodHandles.lookup()
                .findVarHandle(Node.class, "value", Object.class);
        } catch (ReflectiveOperationException e) { throw new Error(e); }
    }

    boolean cas(Object expect, Object update) {
        return VALUE.compareAndSet(this, expect, update);
    }
    Object getAcquire()          { return VALUE.getAcquire(this); }
    void setRelease(Object v)    { VALUE.setRelease(this, v); }
    // ★ acquire/release 는 volatile 보다 약한(=빠른) 메모리 순서 보장
}

DEEP 05

false sharing · 캐시 라인

코드는 완벽한데 느린 이유. 하드웨어를 알아야 보입니다.

공유하지 않는데 공유한 것처럼 느려집니다 — 그래서 이름이 거짓 공유입니다.

캐시 라인이란

CPU 는 메모리를 바이트가 아니라 "캐시 라인" 단위로 읽습니다.
  일반적으로 64바이트

문제: 서로 다른 변수가 같은 라인에 있으면
      한쪽만 바꿔도 다른 코어의 캐시가 통째로 무효화됩니다
      → 실제로는 공유하지 않는데 공유하는 것처럼 느려짐
      → 이것이 false sharing (거짓 공유)

        코어1이 a 를 수정 ─┐
                          ├→ 같은 캐시 라인 → 서로의 캐시를 계속 무효화
        코어2가 b 를 수정 ─┘   → 수 배 느려질 수 있습니다
// ❌ false sharing 이 일어나는 구조
class Counters {
    volatile long a;     // 같은 캐시 라인에 나란히 배치됨
    volatile long b;
}
// 스레드1이 a 를, 스레드2가 b 를 계속 증가시키면
// 논리적으로는 독립인데 실제로는 서로를 방해합니다

// ⚠️ @Contended 는 공식 API 가 아니라 JDK 내부 애노테이션입니다
//    (jdk.internal.vm.annotation — 컴파일에 --add-exports 로
//     java.base/jdk.internal.vm.annotation 을 열어야 하고,
//     실행 시 -XX:-RestrictContended 도 필요합니다)
import jdk.internal.vm.annotation.Contended;   // JDK 내부용

@Contended
static class PaddedCounter { volatile long value; }

// ✅ 실무 해법 — LongAdder 를 쓰거나 수동 패딩(더미 long 필드)으로 분리
LongAdder counter = new LongAdder();   // ★ 내부가 이미 패딩되어 있습니다

DEEP 06

GC 심화 — G1 · ZGC 내부

🧬 고급 a02 의 확장판. 어떤 원리로 멈춤을 줄이는지 봅니다.

멈춤이 짧은 이유는 알고리즘이 빨라서가 아니라 한 번에 조금만 건드리기 때문입니다.

G1 — 리전 기반

힙을 2,048개 정도의 "리전"으로 쪼갭니다.
각 리전은 상황에 따라 Eden · Survivor · Old · Humongous 역할을 맡습니다.

Young GC
  · Eden 리전을 비우고 살아남은 것을 Survivor 로 (STW, 보통 수~수십 ms)

Mixed GC
  · 동시 마킹으로 "쓰레기가 많은 Old 리전"을 골라
  · 그 리전만 정리 → ★ 전체를 훑지 않아 멈춤이 짧습니다
    (Garbage-First = 쓰레기 많은 것부터)

핵심 옵션
  -XX:MaxGCPauseMillis=200      목표 정지 시간 (보장 아님 · 힌트)
  -XX:G1HeapRegionSize=8m       리전 크기
  -XX:InitiatingHeapOccupancyPercent=45   동시 마킹 시작 시점
Humongous 객체 주의 — 리전 크기의 절반을 넘는 객체는 특별 취급되어 연속 리전을 차지하고 수거가 늦어집니다. 큰 배열·큰 바이트 버퍼를 자주 만들면 “힙에 여유가 있는데 Full GC 가 도는” 현상이 생깁니다.

ZGC — 컬러 포인터와 로드 배리어

목표: 힙 크기와 무관하게 정지 시간 1ms 미만

방법
  · 포인터의 사용하지 않는 비트에 "색"을 심어 상태를 표시
  · 애플리케이션이 참조를 읽을 때마다 로드 배리어가 끼어들어
    필요하면 그 자리에서 포인터를 고침 (동시 이동)
  · 그래서 "객체를 옮기는 동안에도" 앱이 계속 돕니다

대가
  · 로드 배리어 때문에 처리량이 약간 (수 %) 낮습니다
  · 메모리를 조금 더 씁니다

세대별 ZGC — 대부분의 워크로드에서 비세대형보다 낫습니다
  -XX:+UseZGC
  ※ Java 23부터 세대형이 기본. 21~22에서만 -XX:+ZGenerational 을
    추가로 켜야 하고, 24부터는 이 플래그 자체가 폐기됐습니다

ZGCp99 지연이 중요하거나 힙이 큼(32GB+)
Parallel배치 — 처리량만 중요하고 멈춰도 될 때
Serial1 vCPU 컨테이너 · 사이드카
ShenandoahZGC 와 유사한 저지연 GC (Red Hat)

GC 튜닝 전에 확인할 것 — 객체를 너무 많이 만들고 있지 않은지. 한 번에 100만 건 조회, 불필요한 DTO 변환, 문자열 연결이 GC 를 바쁘게 만드는 진짜 원인인 경우가 대부분입니다. 코드를 고치면 GC 는 저절로 조용해집니다.

Compact Object Headers — 플래그 하나로 힙 20% 절감

자바 객체는 데이터 앞에 "헤더"를 달고 다닙니다.
64비트 JVM 의 기본 헤더는 12바이트 (mark word 8 + 압축 클래스 포인터 4)
→ 8바이트 정렬까지 감안하면 필드가 하나뿐인 객체도 16바이트를 씁니다.

Compact Object Headers 는 이걸 8바이트로 줄입니다.

  class Point { int x, y; }        헤더 12B + 필드 8B → 정렬 24B
  같은 클래스, 압축 헤더 켰을 때    헤더  8B + 필드 8B → 정렬 16B   ★ 33% 감소

★ JDK 25 에서 정식 제품 기능이 됐습니다 (JEP 519 · 그 전에는 JDK 24 실험 기능)
  다만 기본값은 여전히 "꺼짐" 입니다 — 직접 켜야 합니다.
  기본값으로 만들자는 JEP 534 는 아직 초안 단계입니다.
# 켜기 (JDK 25+ 에서는 실험 기능 플래그 없이 그냥 켜집니다)
java -XX:+UseCompactObjectHeaders -jar app.jar

# 얼마나 줄었는지 확인 — JOL 로 실제 레이아웃을 찍어 봅니다 (z05)
java -XX:+UseCompactObjectHeaders \
     -cp app.jar:jol-cli.jar org.openjdk.jol.Main internals com.myapp.Point

# 켜기 전/후 힙 사용량 비교 (같은 부하를 준 뒤)
jcmd <pid> GC.heap_info
효과는 “객체 하나가 얼마나 작은가”에 달려 있습니다. 실측으로 힙 사용량 10~20%, 작은 객체를 대량으로 만드는 워크로드에서는 그 이상 줄어듭니다.
✅ 잘 먹히는 곳 — 수백만 건 엔티티·DTO 를 메모리에 올리는 서비스, 대형 캐시, 노드가 많은 그래프·트리, 작은 객체가 쏟아지는 스트림 처리
❌ 별 차이 없는 곳 — 객체 하나가 이미 큰 경우(긴 문자열·큰 배열 중심). 헤더 4바이트는 전체 대비 비율로만 의미가 있습니다.
힙이 줄면 GC 도 덩달아 조용해집니다. 할당량 자체가 줄어 Young GC 주기가 길어지고 승격도 덜 일어납니다. 다만 Unsafe·JOL·에이전트처럼 헤더 레이아웃을 직접 가정하는 코드는 깨질 수 있으니 ★ 부하 테스트를 한 번 돌린 뒤에 운영에 넣으세요.

오프힙 · 네이티브 메모리

“힙은 여유 있는데 컨테이너가 죽는” 이유.

JVM 이 쓰는 메모리 전부

컨테이너 메모리 한도 (예: 2GB)
├─ 힙 (-Xmx)                    ← 우리가 아는 그것
├─ 메타스페이스                  클래스 정보 (기본 무제한 ★)
├─ 코드 캐시                     JIT 결과 (기본 240MB)
├─ 스레드 스택                   스레드당 1MB × 개수 ★
├─ 다이렉트 버퍼                 NIO · Netty
├─ GC 구조체                     힙의 5~10%
└─ 네이티브 라이브러리           JNI · 압축 · 암호화

★ -Xmx2g 로 두고 컨테이너를 2GB 로 잡으면 반드시 OOMKilled 됩니다.
  힙은 컨테이너의 70~75% 가 안전선입니다 (🧬 고급 a13)

DirectByteBuffer — 힙 밖의 메모리

// 힙 안 — GC 가 관리, 복사 비용 있음
ByteBuffer heap = ByteBuffer.allocate(1024);

// ★ 힙 밖 — I/O 시 복사가 없어 빠르지만 GC 가 늦게 회수합니다
ByteBuffer direct = ByteBuffer.allocateDirect(1024);

// 한도 설정 (기본은 -Xmx 와 같습니다 — 즉 두 배를 쓸 수 있습니다!)
// -XX:MaxDirectMemorySize=256m

// ★ 다이렉트 버퍼는 참조가 사라진 뒤 GC 가 돌아야 해제됩니다
//   → 힙에 여유가 있으면 GC 가 안 돌고 → 네이티브 메모리만 계속 증가
//   → OutOfMemoryError: Direct buffer memory
// 해결: 풀링(Netty 가 하는 일)하거나 MaxDirectMemorySize 를 명시
// Java 21+ — Foreign Function & Memory API (Unsafe 의 공식 후계)
try (Arena arena = Arena.ofConfined()) {          // ★ 명시적 수명 관리
    MemorySegment seg = arena.allocate(1024);
    seg.set(ValueLayout.JAVA_INT, 0, 42);
    int v = seg.get(ValueLayout.JAVA_INT, 0);
}   // 여기서 즉시 해제 — GC 를 기다리지 않습니다

// 네이티브 함수 호출도 JNI 없이 가능해졌습니다
Linker linker = Linker.nativeLinker();
MethodHandle strlen = linker.downcallHandle(
    linker.defaultLookup().find("strlen").orElseThrow(),
    FunctionDescriptor.of(JAVA_LONG, ADDRESS));
메타스페이스 누수를 조심하세요. 기본값이 무제한이라, 동적 프록시·CGLIB·스크립팅을 요청마다 생성하면 클래스가 계속 쌓입니다. -XX:MaxMetaspaceSize=256m 로 상한을 두면 OOM 으로 빨리 드러나 원인을 찾기 쉬워집니다.
DEEP 09

NIO · Netty 이벤트 루프

WebFlux · Spring Cloud Gateway 아래에서 실제로 도는 것.

블로킹 I/O 와 무엇이 다른가

[블로킹 — 전통적 톰캣]
  연결 1개 = 스레드 1개
  10,000 연결 → 스레드 10,000개 → 스택만 10GB · 스위칭 폭발

[NIO — 셀렉터]
  스레드 1개가 Selector 로 "준비된 채널"만 골라 처리
  10,000 연결 → 스레드 몇 개
  ★ 대신 콜백 기반이라 코드가 어려워집니다

[가상 스레드 — Java 21]
  블로킹처럼 쓰되 내부적으로는 논블로킹
  ★ 대부분의 웹 서버는 이제 이쪽이 정답입니다 (🧬 고급 a08)
// NIO 셀렉터 — 원리를 보여 주는 최소 코드
Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.bind(new InetSocketAddress(8080));
server.configureBlocking(false);                     // ★ 논블로킹
server.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();                               // 준비될 때까지 대기
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) { /* 새 연결 */ }
        else if (key.isReadable()) { /* 읽기 가능 */ }
    }
    selector.selectedKeys().clear();                 // ★ 안 지우면 무한 반복
}

Netty 의 구조

[Boss 그룹]   연결 수락만 담당 (보통 1개 스레드)
     ↓
[Worker 그룹]  EventLoop N개 (기본 = CPU × 2)
     ↓         ★ 하나의 연결은 "항상 같은 EventLoop" 에 묶입니다
[ChannelPipeline]
   inbound  →  디코더 → 비즈니스 핸들러 → …
   outbound ←  인코더 ←

핵심 규칙

    한 핸들러에서 DB 를 동기로 호출하면
    그 EventLoop 에 묶인 "수천 개 연결이 전부" 멈춥니다

pipeline.addLast(new HttpServerCodec());
pipeline.addLast(new HttpObjectAggregator(1_048_576));   // ★ 크기 제한

MethodHandle — 리플렉션의 대안

MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodHandle mh = lookup.findVirtual(
    User.class, "getName", MethodType.methodType(String.class));

// ★ static final 로 두어야 최적화됩니다
private static final MethodHandle GET_NAME;

// LambdaMetafactory — 함수형 인터페이스로 변환 (가장 빠름)
Function<User, String> getter = (Function<User, String>) LambdaMetafactory
    .metafactory(lookup, "apply",
        MethodType.methodType(Function.class),
        MethodType.methodType(Object.class, Object.class),
        mh, MethodType.methodType(String.class, User.class))
    .getTarget().invokeExact();

// ★ Jackson·MapStruct 같은 라이브러리가 내부에서 쓰는 기법입니다

public record Err<T>(String message) implements Result<T> {}

키워드의미
exports컴파일·런타임 모두 접근 허용. public 이어도 exports 안 하면 밖에서 못 씁니다 ★
opens컴파일은 막고 리플렉션만 허용. setAccessible(true) 가 통하는 유일한 통로

JDKJEP무엇이 좋아졌나
24JEP 483 AOT 클래스 로딩·링킹 — 클래스를 미리 읽고 링크해 캐시에 담습니다 (시작점)
25JEP 514 명령이 한 줄로 — -XX:AOTCacheOutput 하나로 훈련 실행과 캐시 생성이 합쳐졌습니다 (전에는 record → create → use 3단계)
25JEP 515 메서드 프로파일까지 캐시 — JIT 이 워밍업을 처음부터 다시 하지 않아 기동 직후의 피크 성능 도달이 빨라집니다
26JEP 516 어떤 GC 에서도 동작 — 캐시를 만들 때와 쓸 때의 GC 가 달라도 됩니다. ★ ZGC 를 쓰면 AOT 캐시를 못 쓰던 제약이 풀렸습니다
# JDK 24 — 3단계 (JEP 483)
java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -jar app.jar   # ① 훈련
java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf \
     -XX:AOTCache=app.aot -jar app.jar                                  # ② 캐시 생성
java -XX:AOTCache=app.aot -jar app.jar                                  # ③ 사용

# JDK 25+ — 한 줄로 끝 (JEP 514) · 프로파일까지 담깁니다 (JEP 515)
java -XX:AOTCacheOutput=app.aot -jar app.jar    # 훈련 실행 한 번 → 종료하면 캐시가 나옴
java -XX:AOTCache=app.aot -jar app.jar          # 이후 실행
