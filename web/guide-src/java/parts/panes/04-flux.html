왜 WebFlux인가 — 그리고 언제 쓰지 말아야 하나

가상 스레드가 나온 지금, 이 판단이 예전보다 훨씬 중요해졌습니다.

MVC — 요청 하나에 스레드 하나

요청 1 → [스레드 1] ──DB 대기 2초── 응답

FLUX 02

Mono와 Flux

리액티브의 모든 것이 이 둘로 표현됩니다. “값이 나중에 온다”를 담는 상자라고 보면 정확합니다.

둘의 차이는 개수뿐

타입의미MVC 대응
Mono<T>0 또는 1개T · Optional<T>
Flux<T>0 ~ N개 (무한 가능)List<T> · Stream<T>
// 만들기
Mono<String> m1 = Mono.just("값");
Mono<String> m2 = Mono.empty();                 // 값 없음
Mono<String> m3 = Mono.error(new RuntimeException());
Mono<String> m4 = Mono.fromCallable(() -> compute());   // 지연 실행
Mono<String> m5 = Mono.defer(() -> Mono.just(now()));   // 구독할 때마다 새로

Flux<Integer> f1 = Flux.just(1, 2, 3);
Flux<Integer> f2 = Flux.range(1, 100);
Flux<String> f3 = Flux.fromIterable(list);
Flux<Long> f4 = Flux.interval(Duration.ofSeconds(1));   // 1초마다 무한

// 변환
Mono<List<T>> list = flux.collectList();
Flux<T> flux2 = mono.flux();
Mono<T> first = flux.next();

⚠️ 구독하지 않으면 아무 일도 안 일어난다

❌ 실행되지 않습니다
public void save(Order o) {
    repository.save(o);        // Mono 를 만들기만 하고 버림
}                              // DB 에 아무것도 안 들어감 💥
✅ 반환해서 프레임워크가 구독하게
public Mono<Order> save(Order o) {
    return repository.save(o);    // 컨트롤러가 반환하면 스프링이 구독
}

Mono·Flux 는 “무엇을 할지 적어 둔 설계도”일 뿐입니다. 누군가 subscribe() 해야 비로소 흐르기 시작합니다. 웹 컨트롤러에서는 반환만 하면 스프링이 대신 구독합니다 — 직접 subscribe()를 호출하는 코드는 대개 잘못된 신호입니다.

"로그가 안 찍혀요"의 대부분은 구독하지 않은 것입니다.
FLUX 03

연산자 지도

수백 개가 있지만 실무에서 쓰는 건 20개 남짓입니다. 목적별로 묶어 두면 찾기 쉽습니다.

연산자하는 일메모
■ 변환
map(v -> f(v))값을 바꿈 (동기)Stream 의 map 과 동일
flatMap(v -> mono)또 다른 비동기 호출을 이어붙임가장 많이 씁니다. 순서 보장 안 됨
concatMapflatMap + 순서 보장순서가 중요하면 이걸로
flatMapSequential동시 실행 + 결과는 순서대로성능과 순서 둘 다
switchMap새 값이 오면 이전 것 취소검색어 자동완성
■ 거르기
filter조건에 맞는 것만
take(n) / skip(n)앞 n개 / n개 건너뛰기무한 스트림 자르기
distinct()중복 제거
takeUntil / takeWhile조건까지만
■ 합치기
zip(a, b)둘을 동시 실행 후 짝지음API 병렬 호출의 핵심 ★
merge여러 개를 뒤섞어 하나로도착 순서대로
concat앞의 것이 끝나면 다음순차
then / thenReturn앞의 결과를 버리고 다음저장 후 완료 신호
■ 없을 때 · 에러
defaultIfEmpty(v)비었으면 기본값
switchIfEmpty(mono)비었으면 다른 흐름으로404 처리에 자주
onErrorReturn(v)에러면 대체값
onErrorResume(e -> mono)에러면 다른 흐름폴백
retry / retryWhen재시도백오프 설정 가능
timeout(d)제한 시간외부 호출엔 필수
■ 부수 효과 · 디버깅
doOnNext / doOnError흐름을 안 바꾸고 관찰로깅에 사용
log()모든 신호를 로그로디버깅 1순위

map vs flatMap — 가장 헷갈리는 지점

// map — 동기 변환. 결과가 그냥 값일 때
Mono<String> name = userMono.map(User::getName);

// flatMap — 반환값이 또 Mono/Flux 일 때
// ❌ map 을 쓰면 Mono<Mono<Order>> 가 되어 버린다
Mono<Mono<Order>> wrong = userMono.map(u -> orderRepo.findByUser(u.getId()));

// ✅ flatMap 이 한 겹 벗겨 준다
Mono<Order> right = userMono.flatMap(u -> orderRepo.findByUser(u.getId()));

// 실전 — 조회 → 검증 → 저장 체인
public Mono<OrderRes> pay(Long id) {
    return orderRepository.findById(id)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(id)))
            .flatMap(order -> {
                order.pay();
                return orderRepository.save(order);
            })
            .map(OrderRes::from)
            .doOnSuccess(r -> log.info("결제 완료 {}", r.id()));
}

FLUX 04

스레드 모델 · 스케줄러

여기가 WebFlux 에서 사고가 가장 많이 나는 곳입니다. 이벤트 루프를 막으면 서버 전체가 멈춥니다.

절대 규칙 — 이벤트 루프 스레드(reactor-http-nio-*)에서 블로킹 호출을 하면 안 됩니다. 스레드가 CPU 코어 수만큼(보통 4~8개)뿐이라 한 요청이 막히면 다른 수천 개 요청이 전부 멈춥니다.
블로킹의 예: JDBC · RestTemplate · Thread.sleep() · .block() · 파일 I/O · 무거운 CPU 연산
subscribeOn 은 소스부터, publishOn 은 그 지점부터 — 이 두 연산자 밖에서는 스레드가 저절로 바뀌지 않습니다.

스케줄러 종류

스케줄러용도
Schedulers.parallel()CPU 연산 (코어 수만큼)
Schedulers.boundedElastic()블로킹 작업 격리용 ★
Schedulers.immediate()현재 스레드 유지
Schedulers.single()전용 스레드 하나
Schedulers.fromExecutor(e)내 실행자 사용
// 어쩔 수 없이 블로킹 코드를 써야 한다면 반드시 격리
public Mono<Report> legacyReport(Long id) {
    return Mono.fromCallable(() -> legacyJdbcDao.find(id))   // 블로킹
               .subscribeOn(Schedulers.boundedElastic());     // 별도 스레드로 ★

// publishOn — 이 지점 '이후'의 스레드를 바꾼다
flux.publishOn(Schedulers.parallel())
    .map(this::heavyCompute);

// subscribeOn — 소스가 실행될 스레드를 바꾼다 (위치 무관, 한 번만 적용)
mono.subscribeOn(Schedulers.boundedElastic());

FLUX 05

컨트롤러 · 라우터 함수

MVC 와 똑같이 애너테이션으로 쓸 수도 있고, 함수형으로 쓸 수도 있습니다.

애너테이션 방식 — MVC 와 거의 같습니다

@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService service;

    @GetMapping
    public Flux<OrderRes> list() {              // List 대신 Flux
        return service.findAll();
    }

    @GetMapping("/{id}")
    public Mono<OrderRes> get(@PathVariable Long id) {   // 단건은 Mono
        return service.get(id);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<OrderRes> create(@Valid @RequestBody Mono<OrderCreateReq> req) {
        return req.flatMap(service::create);
    }

    @DeleteMapping("/{id}")
    public Mono<Void> delete(@PathVariable Long id) {
        return service.delete(id);
    }
}

반환 타입만 바뀌었을 뿐 구조는 MVC 와 동일합니다. 기존 MVC 경험을 그대로 살릴 수 있어 처음엔 이 방식을 권합니다.

함수형 방식 — 라우터

@Configuration
public class OrderRouter {

    @Bean
    public RouterFunction<ServerResponse> routes(OrderHandler handler) {
        return RouterFunctions.route()
                .path("/api/orders", builder -> builder
                        .GET("", handler::list)
                        .GET("/{id}", handler::get)
                        .POST("", handler::create)
                        .DELETE("/{id}", handler::delete))
                .filter((req, next) -> {           // 라우터 단위 필터
                    log.info("{} {}", req.method(), req.path());
                    return next.handle(req);
                })
                .build();
    }
}

@Component
@RequiredArgsConstructor
public class OrderHandler {
    private final OrderService service;

    public Mono<ServerResponse> get(ServerRequest req) {
        Long id = Long.valueOf(req.pathVariable("id"));
        return service.get(id)
                .flatMap(o -> ServerResponse.ok().bodyValue(o))
                .switchIfEmpty(ServerResponse.notFound().build());
    }

    public Mono<ServerResponse> create(ServerRequest req) {
        return req.bodyToMono(OrderCreateReq.class)
                .flatMap(service::create)
                .flatMap(o -> ServerResponse
                        .created(URI.create("/api/orders/" + o.id()))
                        .bodyValue(o));
    }
}

WebClient — 논블로킹 HTTP 호출

RestTemplate의 후계입니다. MVC 프로젝트에서도 쓸 수 있습니다.

설정 — 타임아웃은 반드시

@Bean
public WebClient orderApiClient(WebClient.Builder builder) {
    HttpClient httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000)
            .responseTimeout(Duration.ofSeconds(5))
            .doOnConnected(conn -> conn
                    .addHandlerLast(new ReadTimeoutHandler(5))
                    .addHandlerLast(new WriteTimeoutHandler(5)));

    return builder
            .baseUrl("https://api.example.com")
            .clientConnector(new ReactorClientHttpConnector(httpClient))
            .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
            .filter(logRequest())            // 요청 로깅
            .codecs(c -> c.defaultCodecs()
                    .maxInMemorySize(5 * 1024 * 1024))   // 응답 크기 제한 (기본 256KB)
            .build();
}

private ExchangeFilterFunction logRequest() {
    return ExchangeFilterFunction.ofRequestProcessor(req -> {
        log.debug("{} {}", req.method(), req.url());
        return Mono.just(req);
    });
}

FLUX 07

백프레셔 — 감당할 만큼만 받기

생산자가 소비자보다 빠를 때 “천천히 주세요”라고 말할 수 있는 능력입니다. 리액티브의 진짜 차별점입니다.

백프레셔 = 소비자가 올려 보내는 request(n). 이 신호를 못 받는 소스만 onBackpressure* 로 완충합니다.

왜 필요한가

DB 가 초당 10만 건을 뿜는데
소비자는 초당 1천 건만 처리 가능하다면?

백프레셔 없음 → 메모리에 쌓임 → OOM 💥
백프레셔 있음 → "1천 개만 주세요" → 안정 ✅
// 전략 선택 — 넷 중 하나만 골라 씁니다 (체인으로 연결하는 게 아님)
flux.onBackpressureBuffer(1000);        // ① 1000개까지 버퍼
flux.onBackpressureDrop(v -> log.warn("버림: {}", v));  // ② 넘치면 버림
flux.onBackpressureLatest();            // ③ 최신 것만 유지
flux.onBackpressureError();             // ④ 넘치면 에러

// 속도 제한
flux.limitRate(100)                     // 한 번에 100개씩 요청
    .delayElements(Duration.ofMillis(10));

// 묶어서 처리 — DB 배치 저장에 유용 ★
flux.buffer(500)                        // 500개씩 묶음
    .flatMap(batch -> repository.saveAll(batch))
    .subscribe();

// 시간 기준으로 묶기
flux.bufferTimeout(500, Duration.ofSeconds(1));

동시 실행 개수 제한

// ❌ flatMap 기본 동시성은 256 — 외부 API 를 순식간에 때립니다
Flux.fromIterable(ids)
    .flatMap(id -> apiClient.get(id))
    .subscribe();

// ✅ 동시 실행 수를 제한
Flux.fromIterable(ids)
    .flatMap(id -> apiClient.get(id), 10)   // 최대 10개 동시
    .subscribe();

// 순서까지 지키려면
    .flatMapSequential(id -> apiClient.get(id), 10)

// 완전 순차 (가장 느리지만 안전)
    .concatMap(id -> apiClient.get(id))
실전에서 가장 자주 쓰는 조합 — .flatMap(fn, 동시개수) + .timeout() + .retryWhen(). 외부 API 를 대량 호출할 때 이 셋이 없으면 상대 서버를 다운시키거나 우리가 먼저 죽습니다.

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final StockRepository stockRepository;

    @Transactional                       // 리액티브에서도 그대로 동작
    public Mono<Order> create(OrderCreateReq req) {
        return stockRepository.findByProductId(req.productId())
                .switchIfEmpty(Mono.error(new StockNotFoundException()))
                .flatMap(stock -> {
                    if (stock.getQuantity() < req.quantity())
                        return Mono.error(new InsufficientStockException());
                    stock.decrease(req.quantity());
                    return stockRepository.save(stock);
                })
                .then(orderRepository.save(Order.from(req)));
                // 어느 단계에서 에러가 나도 전체 롤백 ✅
    }
}

FLUX 13

Netty 구조 — 왜 WebFlux가 빠른가

WebFlux 아래에는 항상 Netty가 깔려 있습니다. 여기를 모르면 튜닝도 장애 분석도 추측이 됩니다.

Netty 의 속도 비결 = 스레드 수를 소켓 수에서 분리한 것. 1만 연결도 코어 수만큼의 스레드로 감당합니다.

Reactor 패턴 — 스레드 하나가 수천 소켓을 본다

[ 톰캣 · 블로킹 ]
소켓 1  → 스레드 1  (read() 에서 멈춰 있음)
소켓 2  → 스레드 2  (read() 에서 멈춰 있음)
소켓 N  → 스레드 N   … 스레드 = 소켓 개수

[ Netty · Reactor 패턴 ]
소켓 1 ┐
소켓 2 ├→ [ Selector / epoll ] → 이벤트 루프 스레드 1개
  …    │      "읽을 게 생긴 소켓만 알려 줘"
소켓 N ┘
      → 이벤트가 온 소켓만 골라서 처리 → 다음 소켓
      스레드는 '기다리지' 않고 '깨워질 때만' 일한다

핵심은 스레드 수를 소켓 수에서 분리한 것입니다. 연결 1만 개가 있어도 실제로 데이터가 오가는 건 그중 수백 개뿐이므로, CPU 코어 수만큼의 스레드로 전부 감당할 수 있습니다. 컨텍스트 스위칭과 스레드 스택(기본 1MB × N)이 통째로 사라지는 것이 WebFlux 가 메모리를 적게 먹는 진짜 이유입니다.

EventLoopGroup — boss와 worker

// boss   : accept() 만 담당 (연결 수락) — 보통 1개면 충분
// worker : 수락된 연결의 read/write 를 전담 — 코어 수만큼
EventLoopGroup boss   = new MultiThreadIoEventLoopGroup(1, NioIoHandler.newFactory());
EventLoopGroup worker = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());

// ★ 한 Channel 은 평생 같은 EventLoop 에 묶인다 (스레드 어피니티)
//    → 그 채널의 핸들러 안에서는 동기화가 필요 없다
//    → 대신 그 스레드를 막으면 '그 채널에 붙은 다른 수천 연결'도 같이 멈춘다

ChannelPipeline — 요청이 지나가는 컨베이어

소켓에서 바이트 도착
   ↓  Inbound (아래 → 위)
[ SslHandler ] → [ HttpServerCodec ] → [ 집계 ] → [ 내 핸들러 ]
   ↑  Outbound (위 → 아래)
소켓으로 바이트 전송

· ChannelHandler = 컨베이어 위의 작업자 하나
· ChannelPipeline = 작업자들의 줄 (연결마다 1개)
· ChannelHandlerContext = 작업자가 앞뒤 사람에게 말 거는 창구

ByteBuf — 참조 카운팅이 붙은 버퍼 ★

종류특징
힙 ByteBufJVM 힙에 할당. GC 가 치워 줌. 소켓에 쓸 때 복사 1회 발생

할당자(Allocator) — 4.2 에서 기본값이 바뀌었습니다 ★

할당자특징
AdaptiveNetty 4.2 기본값. 실제 워크로드를 관찰해 버퍼 크기·전략을 자동 조정. pooled 보다 메모리를 적게 쓰고 가상 스레드와도 잘 맞습니다 ★
Pooled버퍼를 재사용해 GC 압력을 줄임. 4.1 까지의 기본값. 지금은 -Dio.netty.allocator.type=pooled 로 명시해야 씁니다
Unpooled매번 새로 할당. 느리지만 진단용으로 유용
4.1 시절 블로그를 그대로 믿지 마세요 — “Netty 기본은 PooledByteBufAllocator” 는 4.2 부터 사실이 아닙니다. 기본은 AdaptiveByteBufAllocator 입니다. 풀 기준으로 튜닝하던 io.netty.allocator.numDirectArenas 같은 옵션은 adaptive 에서는 의미가 없습니다.

public class EchoServer {

    public static void main(String[] args) throws Exception {
        EventLoopGroup boss   = new MultiThreadIoEventLoopGroup(1, NioIoHandler.newFactory());
        EventLoopGroup worker = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());
        try {
            ServerBootstrap b = new ServerBootstrap()
                .group(boss, worker)
                .channel(NioServerSocketChannel.class)
                .option(ChannelOption.SO_BACKLOG, 1024)              // 서버 소켓용
                .childOption(ChannelOption.TCP_NODELAY, true)        // 연결마다
                .childOption(ChannelOption.SO_KEEPALIVE, true)
                .childHandler(new ChannelInitializer<SocketChannel>() {
                    @Override protected void initChannel(SocketChannel ch) {
                        ch.pipeline()
                          .addLast(new LoggingHandler(LogLevel.DEBUG))
                          .addLast(new LengthFieldBasedFrameDecoder(
                                       65536, 0, 4, 0, 4))           // 길이 헤더 4바이트
                          .addLast(new LengthFieldPrepender(4))
                          .addLast(new StringDecoder(UTF_8))
                          .addLast(new StringEncoder(UTF_8))
                          .addLast(new EchoHandler());
                    }
                });

            ChannelFuture f = b.bind(9090).sync();
            f.channel().closeFuture().sync();          // 종료까지 대기
        } finally {
            boss.shutdownGracefully();
            worker.shutdownGracefully();
        }
    }
}

TCP 경계 문제 — 하프 패킷 · 스티키 패킷 ★

보낸 쪽:   [ 주문A ][ 주문B ][ 주문C ]

받는 쪽에 실제로 도착하는 모습(둘 다 정상):
  ① 스티키   [ 주문A주문B주문 ][ C ]     ← 뭉쳐서 옴
  ② 하프     [ 주문 ][ A주문B ][ 주문C ] ← 잘려서 옴

TCP 는 '바이트 스트림'이라 메시지 경계를 보장하지 않는다.
경계는 '내가' 만들어야 한다.
디코더경계를 정하는 방법
LengthFieldBasedFrameDecoder길이 헤더를 읽어 그만큼 자름 — 실무 표준 ★
DelimiterBasedFrameDecoder구분자(\n, \0)로 자름
LineBasedFrameDecoder줄바꿈으로 자름 (텍스트 프로토콜)
FixedLengthFrameDecoder항상 N바이트 고정
// 프레임 형식:  [ 길이(4바이트) ][ 본문 ]
new LengthFieldBasedFrameDecoder(
        1024 * 1024,  // maxFrameLength — 넘으면 TooLongFrameException (DoS 방어)
        0,            // lengthFieldOffset  : 길이 필드 시작 위치
        4,            // lengthFieldLength  : 길이 필드 크기
        0,            // lengthAdjustment   : 길이값 보정
        4);           // initialBytesToStrip: 앞 4바이트(헤더)는 버리고 넘김

// ⚠️ 디코더는 상태를 가집니다 → @Sharable 금지, 연결마다 새로 만들 것

ChannelOption — 자주 만지는 것만

옵션의미 · 실전값
SO_BACKLOGaccept 대기 큐. 리눅스 somaxconn과 둘 중 작은 값이 적용됩니다. 4096 권장
TCP_NODELAYNagle 끄기. 작은 패킷의 40ms 지연 제거 — 켜 두세요(true) ★
SO_KEEPALIVE죽은 연결 감지. 다만 기본 2시간이라 앱 레벨 하트비트가 더 실용적
SO_REUSEADDR재기동 시 Address already in use 방지

언제 Netty 를 직접 쓰나
① 사설 바이너리 프로토콜 — 금융 FIX·POS·IoT 장비 연동처럼 HTTP 가 아닌 경우
② 게임 서버 — 지연에 민감하고 연결이 오래 유지되는 경우
③ 프록시·중계 서버 — 바이트를 그대로 흘려보내야 할 때(zero-copy)
④ 수십만 동시 연결 — HTTP 서버 추상화의 오버헤드조차 아까울 때
그 외 웹 API 라면 직접 쓸 이유가 없습니다. WebFlux 가 이미 잘 감싸 놨습니다.

public class HeartbeatHandler extends ChannelDuplexHandler {
    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
        if (evt instanceof IdleStateEvent e) {
            switch (e.state()) {
                case WRITER_IDLE -> ctx.writeAndFlush(PING);  // 30초 조용하면 핑
                case READER_IDLE -> ctx.close();              // 60초 무응답 = 사망 판정
                default -> {}
            }
        }
    }
}

ConnectionProvider provider = ConnectionProvider.builder("order-api")
    .maxConnections(200)                            // 호스트당 최대 커넥션 ★
    .pendingAcquireMaxCount(1000)                   // 대기 큐 (기본: max × 2)
    .pendingAcquireTimeout(Duration.ofSeconds(3))   // 대기 한계 (기본 45초 — 너무 김) ★
    .maxIdleTime(Duration.ofSeconds(20))            // 놀고 있는 커넥션 폐기 ★★
    .maxLifeTime(Duration.ofMinutes(5))             // 오래된 커넥션 강제 교체
    .evictInBackground(Duration.ofSeconds(30))      // 유휴 커넥션 청소 주기
    .lifo()                                         // 최근 쓴 것부터 재사용 (기본)
    .metrics(true)                                  // ★ 마이크로미터 연동
    .build();

HttpClient httpClient = HttpClient.create(provider)
    .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000)
    .responseTimeout(Duration.ofSeconds(5))         // 응답 전체 한계 ★
    .doOnConnected(c -> c
        .addHandlerLast(new ReadTimeoutHandler(5))  // 5초간 수신 없음
        .addHandlerLast(new WriteTimeoutHandler(5)))
    .compress(true)
    .keepAlive(true)
    .metrics(true, Function.identity());            // URI 태그 (카디널리티 주의)

@Bean
WebClient orderClient(WebClient.Builder b) {
    return b.baseUrl("https://order.internal")
            .clientConnector(new ReactorClientHttpConnector(httpClient))
            .build();
}

pendingAcquireTimeout기본 45초 → 3초 이하로 낮추세요 ★
maxIdleTime기본 없음(무한) → 반드시 설정 ★★
maxLifeTime기본 없음 → 5~10분 (LB 뒤 IP 변경 대응)

가장 흔한 사고 — keep-alive 타임아웃 불일치 ★★

우리 쪽 풀:   maxIdleTime = 무한 (기본값)
상대 서버:    keepAliveTimeout = 5초  (nginx 기본)

t=0    요청 → 커넥션 A 사용 → 풀에 반납
t=5s   상대 서버가 A 를 조용히 닫음 (FIN)

t=6s   요청 → 풀에서 A 를 꺼내 전송

    }
    protected void handleTextMessage(WebSocketSession s, TextMessage m)
            throws IOException {
        for (WebSocketSession peer : sessions)          // 브로드캐스트
            if (peer.isOpen()) peer.sendMessage(m);
    }
    public void afterConnectionClosed(WebSocketSession s, CloseStatus st) {
        sessions.remove(s);                             // ★ 정리 안 하면 누수
    }
}
WebSocketSession.sendMessage 는 동시 호출에 안전하지 않습니다. 여러 스레드가 같은 세션에 보내면 IllegalStateException 이 납니다 — ConcurrentWebSocketSessionDecorator 로 감싸거나(전송 버퍼·타임아웃 지정), 세션마다 전송 큐를 하나 두는 것이 실무 패턴입니다.

하트비트STOMP 기본 10초. 프록시(Nginx) proxy_read_timeout 보다 짧게 — 안 그러면 조용히 끊깁니다
재접속클라이언트 책임 — stompjs 는 내장, 순수 WS 는 지수 백오프로 직접. 끊긴 동안 메시지는 재접속 후 REST 로 따라잡기
메시지 크기·버퍼setMessageSizeLimit·setSendBufferSizeLimit 명시 — 느린 클라이언트 하나가 메모리를 먹는 사고 방지
수평 확장세션은 서버에 붙박이 — LB 는 그대로 두고 브로커 릴레이로 메시지만 공유가 정석
WebFlux 에서는 WebSocketHandler 가 Flux<WebSocketMessage> 를 주고받는 리액티브 API 입니다 — 백프레셔(f07)가 소켓까지 이어져 수만 동시 접속에 유리합니다. STOMP 편의 기능은 MVC 쪽이 성숙하니, 접속 수가 수천 이하라면 MVC + STOMP 조합이 개발 속도 면에서 낫습니다.
SSE 로 충분한지 먼저 물어보세요 — 알림·시세·진행률처럼 서버가 밀기만 하면 되는 기능은 SSE(f08)가 훨씬 단순합니다(HTTP 그대로 · 자동 재접속 내장). WebSocket 은 클라이언트도 초당 여러 번 말을 걸 때(채팅 입력·커서 공유·게임 조작) 꺼내는 카드입니다.
