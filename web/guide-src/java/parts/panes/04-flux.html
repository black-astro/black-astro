FLUX 01

왜 WebFlux인가 — 그리고 언제 쓰지 말아야 하나

가상 스레드가 나온 지금, 이 판단이 예전보다 훨씬 중요해졌습니다.

MVC — 요청 하나에 스레드 하나

요청 1 → [스레드 1] ──DB 대기 2초── 응답
요청 2 → [스레드 2] ──DB 대기 2초── 응답
   …
요청 201 → 대기 (톰캣 기본 풀 200개 소진)

스레드는 '기다리는 동안'에도 메모리를 붙잡고 있다

WebFlux — 적은 스레드가 돌려막기

요청 1~10000 → [이벤트 루프 스레드 8개]
   DB 요청을 던져 놓고 → 즉시 다른 요청 처리
   결과가 오면 → 콜백으로 이어서 처리

기다리는 동안 스레드가 놀지 않는다

셋 중 무엇을 고를까 2026 기준

상황선택
일반적인 CRUD APIMVC — 고민할 필요 없습니다
동시 접속은 많은데 로직은 I/O 대기 위주MVC + 가상 스레드 ★ 코드는 그대로, 처리량만 올라갑니다

FLUX 02

Mono와 Flux

리액티브의 모든 것이 이 둘로 표현됩니다. “값이 나중에 온다”를 담는 상자라고 보면 정확합니다.

둘의 차이는 개수뿐

타입의미MVC 대응
Mono<T>0 또는 1개T · Optional<T>
Flux<T>0 ~ N개 (무한 가능)List<T> · Stream<T>
// 만들기
Mono<String> m1 = Mono.just("값");
Mono<String> m2 = Mono.empty();                 // 값 없음
Mono<String> m3 = Mono.error(new RuntimeException());
Mono<String> m4 = Mono.fromCallable(() -> compute());   // 지연 실행
Mono<String> m5 = Mono.defer(() -> Mono.just(now()));   // 구독할 때마다 새로

Flux<Integer> f1 = Flux.just(1, 2, 3);
Flux<Integer> f2 = Flux.range(1, 100);
Flux<String> f3 = Flux.fromIterable(list);
Flux<Long> f4 = Flux.interval(Duration.ofSeconds(1));   // 1초마다 무한

// 변환
Mono<List<T>> list = flux.collectList();
Flux<T> flux2 = mono.flux();
Mono<T> first = flux.next();

⚠️ 구독하지 않으면 아무 일도 안 일어난다

❌ 실행되지 않습니다
public void save(Order o) {
    repository.save(o);        // Mono 를 만들기만 하고 버림
}                              // DB 에 아무것도 안 들어감 💥
✅ 반환해서 프레임워크가 구독하게
public Mono<Order> save(Order o) {
    return repository.save(o);    // 컨트롤러가 반환하면 스프링이 구독
}

Mono·Flux 는 “무엇을 할지 적어 둔 설계도”일 뿐입니다. 누군가 subscribe() 해야 비로소 흐르기 시작합니다. 웹 컨트롤러에서는 반환만 하면 스프링이 대신 구독합니다 — 직접 subscribe()를 호출하는 코드는 대개 잘못된 신호입니다.

FLUX 03

연산자 지도

수백 개가 있지만 실무에서 쓰는 건 20개 남짓입니다. 목적별로 묶어 두면 찾기 쉽습니다.

연산자하는 일메모
■ 변환
map(v -> f(v))값을 바꿈 (동기)Stream 의 map 과 동일
flatMap(v -> mono)또 다른 비동기 호출을 이어붙임가장 많이 씁니다. 순서 보장 안 됨
concatMapflatMap + 순서 보장순서가 중요하면 이걸로
flatMapSequential동시 실행 + 결과는 순서대로성능과 순서 둘 다
switchMap새 값이 오면 이전 것 취소검색어 자동완성
■ 거르기
filter조건에 맞는 것만
take(n) / skip(n)앞 n개 / n개 건너뛰기무한 스트림 자르기
distinct()중복 제거
takeUntil / takeWhile조건까지만
■ 합치기
zip(a, b)둘을 동시 실행 후 짝지음API 병렬 호출의 핵심 ★
merge여러 개를 뒤섞어 하나로도착 순서대로
concat앞의 것이 끝나면 다음순차
then / thenReturn앞의 결과를 버리고 다음저장 후 완료 신호
■ 없을 때 · 에러
defaultIfEmpty(v)비었으면 기본값
switchIfEmpty(mono)비었으면 다른 흐름으로404 처리에 자주
onErrorReturn(v)에러면 대체값
onErrorResume(e -> mono)에러면 다른 흐름폴백
retry / retryWhen재시도백오프 설정 가능
timeout(d)제한 시간외부 호출엔 필수
■ 부수 효과 · 디버깅
doOnNext / doOnError흐름을 안 바꾸고 관찰로깅에 사용
log()모든 신호를 로그로디버깅 1순위

map vs flatMap — 가장 헷갈리는 지점

// map — 동기 변환. 결과가 그냥 값일 때
Mono<String> name = userMono.map(User::getName);

// flatMap — 반환값이 또 Mono/Flux 일 때
// ❌ map 을 쓰면 Mono<Mono<Order>> 가 되어 버린다
Mono<Mono<Order>> wrong = userMono.map(u -> orderRepo.findByUser(u.getId()));

// ✅ flatMap 이 한 겹 벗겨 준다
Mono<Order> right = userMono.flatMap(u -> orderRepo.findByUser(u.getId()));

// 실전 — 조회 → 검증 → 저장 체인
public Mono<OrderRes> pay(Long id) {
    return orderRepository.findById(id)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(id)))
            .flatMap(order -> {
                order.pay();
                return orderRepository.save(order);
            })
            .map(OrderRes::from)
            .doOnSuccess(r -> log.info("결제 완료 {}", r.id()));
}

zip — 병렬 호출의 핵심 ★

// ❌ 순차 실행 — 300ms + 400ms = 700ms
public Mono<Dashboard> slow(Long id) {
    return userClient.get(id)
            .flatMap(user -> orderClient.get(id)
                    .map(orders -> new Dashboard(user, orders)));
}

// ✅ 동시 실행 — max(300, 400) = 400ms
public Mono<Dashboard> fast(Long id) {
    return Mono.zip(
            userClient.get(id),
            orderClient.get(id),
            couponClient.get(id)
    ).map(t -> new Dashboard(t.getT1(), t.getT2(), t.getT3()));
}

// 개수가 많으면 Tuple 대신 조합 함수
Mono.zip(list, arr -> combine(arr));

// 하나가 실패해도 나머지는 살리고 싶다면
Mono.zip(
    userClient.get(id).onErrorReturn(User.unknown()),
    orderClient.get(id).onErrorReturn(List.of())
)
FLUX 04

스레드 모델 · 스케줄러

여기가 WebFlux 에서 사고가 가장 많이 나는 곳입니다. 이벤트 루프를 막으면 서버 전체가 멈춥니다.

절대 규칙 — 이벤트 루프 스레드(reactor-http-nio-*)에서 블로킹 호출을 하면 안 됩니다. 스레드가 CPU 코어 수만큼(보통 4~8개)뿐이라 한 요청이 막히면 다른 수천 개 요청이 전부 멈춥니다.
블로킹의 예: JDBC · RestTemplate · Thread.sleep() · .block() · 파일 I/O · 무거운 CPU 연산

스케줄러 종류

스케줄러용도
Schedulers.parallel()CPU 연산 (코어 수만큼)
Schedulers.boundedElastic()블로킹 작업 격리용 ★
Schedulers.immediate()현재 스레드 유지
Schedulers.single()전용 스레드 하나
Schedulers.fromExecutor(e)내 실행자 사용
// 어쩔 수 없이 블로킹 코드를 써야 한다면 반드시 격리
public Mono<Report> legacyReport(Long id) {
    return Mono.fromCallable(() -> legacyJdbcDao.find(id))   // 블로킹
               .subscribeOn(Schedulers.boundedElastic());     // 별도 스레드로 ★
}

// publishOn — 이 지점 '이후'의 스레드를 바꾼다
flux.publishOn(Schedulers.parallel())
    .map(this::heavyCompute);

// subscribeOn — 소스가 실행될 스레드를 바꾼다 (위치 무관, 한 번만 적용)
mono.subscribeOn(Schedulers.boundedElastic());

FLUX 05

컨트롤러 · 라우터 함수

MVC 와 똑같이 애너테이션으로 쓸 수도 있고, 함수형으로 쓸 수도 있습니다.

애너테이션 방식 — MVC 와 거의 같습니다

@RestController
@RequestMapping("/api/orders")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService service;

    @GetMapping
    public Flux<OrderRes> list() {              // List 대신 Flux
        return service.findAll();
    }

    @GetMapping("/{id}")
    public Mono<OrderRes> get(@PathVariable Long id) {   // 단건은 Mono
        return service.get(id);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public Mono<OrderRes> create(@Valid @RequestBody Mono<OrderCreateReq> req) {
        return req.flatMap(service::create);
    }

    @DeleteMapping("/{id}")
    public Mono<Void> delete(@PathVariable Long id) {
        return service.delete(id);
    }
}

반환 타입만 바뀌었을 뿐 구조는 MVC 와 동일합니다. 기존 MVC 경험을 그대로 살릴 수 있어 처음엔 이 방식을 권합니다.

함수형 방식 — 라우터

@Configuration
public class OrderRouter {

    @Bean
    public RouterFunction<ServerResponse> routes(OrderHandler handler) {
        return RouterFunctions.route()
                .path("/api/orders", builder -> builder
                        .GET("", handler::list)
                        .GET("/{id}", handler::get)
                        .POST("", handler::create)
                        .DELETE("/{id}", handler::delete))
                .filter((req, next) -> {           // 라우터 단위 필터
                    log.info("{} {}", req.method(), req.path());
                    return next.handle(req);
                })
                .build();
    }
}

@Component
@RequiredArgsConstructor
public class OrderHandler {
    private final OrderService service;

    public Mono<ServerResponse> get(ServerRequest req) {
        Long id = Long.valueOf(req.pathVariable("id"));
        return service.get(id)
                .flatMap(o -> ServerResponse.ok().bodyValue(o))
                .switchIfEmpty(ServerResponse.notFound().build());
    }

    public Mono<ServerResponse> create(ServerRequest req) {
        return req.bodyToMono(OrderCreateReq.class)
                .flatMap(service::create)
                .flatMap(o -> ServerResponse
                        .created(URI.create("/api/orders/" + o.id()))
                        .bodyValue(o));
    }
}
FLUX 06

WebClient — 논블로킹 HTTP 호출

RestTemplate의 후계입니다. MVC 프로젝트에서도 쓸 수 있습니다.

설정 — 타임아웃은 반드시

@Bean
public WebClient orderApiClient(WebClient.Builder builder) {
    HttpClient httpClient = HttpClient.create()
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000)
            .responseTimeout(Duration.ofSeconds(5))
            .doOnConnected(conn -> conn
                    .addHandlerLast(new ReadTimeoutHandler(5))
                    .addHandlerLast(new WriteTimeoutHandler(5)));

    return builder
            .baseUrl("https://api.example.com")
            .clientConnector(new ReactorClientHttpConnector(httpClient))
            .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
            .filter(logRequest())            // 요청 로깅
            .codecs(c -> c.defaultCodecs()
                    .maxInMemorySize(5 * 1024 * 1024))   // 응답 크기 제한 (기본 256KB)
            .build();
}

private ExchangeFilterFunction logRequest() {
    return ExchangeFilterFunction.ofRequestProcessor(req -> {
        log.debug("{} {}", req.method(), req.url());
        return Mono.just(req);
    });
}

FLUX 07

백프레셔 — 감당할 만큼만 받기

생산자가 소비자보다 빠를 때 “천천히 주세요”라고 말할 수 있는 능력입니다. 리액티브의 진짜 차별점입니다.

왜 필요한가

DB 가 초당 10만 건을 뿜는데
소비자는 초당 1천 건만 처리 가능하다면?

백프레셔 없음 → 메모리에 쌓임 → OOM 💥
백프레셔 있음 → "1천 개만 주세요" → 안정 ✅
// 전략 선택
flux.onBackpressureBuffer(1000)         // 1000개까지 버퍼
    .onBackpressureDrop(v -> log.warn("버림: {}", v))
    .onBackpressureLatest()             // 최신 것만 유지
    .onBackpressureError();             // 넘치면 에러

// 속도 제한
flux.limitRate(100)                     // 한 번에 100개씩 요청
    .delayElements(Duration.ofMillis(10));

// 묶어서 처리 — DB 배치 저장에 유용 ★
flux.buffer(500)                        // 500개씩 묶음
    .flatMap(batch -> repository.saveAll(batch))
    .subscribe();

// 시간 기준으로 묶기
flux.bufferTimeout(500, Duration.ofSeconds(1));

동시 실행 개수 제한

// ❌ flatMap 기본 동시성은 256 — 외부 API 를 순식간에 때립니다
Flux.fromIterable(ids)
    .flatMap(id -> apiClient.get(id))
    .subscribe();

// ✅ 동시 실행 수를 제한
Flux.fromIterable(ids)
    .flatMap(id -> apiClient.get(id), 10)   // 최대 10개 동시
    .subscribe();

// 순서까지 지키려면
    .flatMapSequential(id -> apiClient.get(id), 10)

// 완전 순차 (가장 느리지만 안전)
    .concatMap(id -> apiClient.get(id))
실전에서 가장 자주 쓰는 조합 — .flatMap(fn, 동시개수) + .timeout() + .retryWhen(). 외부 API 를 대량 호출할 때 이 셋이 없으면 상대 서버를 다운시키거나 우리가 먼저 죽습니다.
FLUX 08

SSE · 스트리밍

WebFlux 가 가장 빛나는 영역입니다. 연결을 열어 두고 계속 흘려보내는 기능이 자연스럽게 됩니다.

Server-Sent Events

// 서버 → 클라이언트 단방향 실시간 푸시
@GetMapping(value = "/stream",
            produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<OrderEvent> stream() {
    return orderEventPublisher.flux()
            .map(OrderEvent::from);
}

// 이벤트 메타데이터까지 담기
@GetMapping(value = "/sse", produces = TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> sse() {
    return Flux.interval(Duration.ofSeconds(1))
            .map(i -> ServerSentEvent.<String>builder()
                    .id(String.valueOf(i))
                    .event("tick")
                    .data("현재 시각 " + LocalTime.now())
                    .retry(Duration.ofSeconds(3))   // 끊기면 재연결 간격
                    .build());
}

// 연결이 끊겼을 때 정리
.doOnCancel(() -> log.info("클라이언트 연결 종료"))
.doFinally(sig -> cleanup());
// 브라우저 쪽

// JPA 의 @OneToMany 가 없으므로 이렇게 씁니다
public Mono<OrderDetail> getDetail(Long orderId) {
    return orderRepository.findById(orderId)
            .flatMap(order -> Mono.zip(
                    Mono.just(order),
                    itemRepository.findByOrderId(orderId).collectList(),
                    userRepository.findById(order.getUserId())
            ))
            .map(t -> new OrderDetail(t.getT1(), t.getT2(), t.getT3()));
}

// 목록 + 각각의 상세 — N+1 이 되지 않게 한 번에 모아 조회 ★
public Flux<OrderDetail> listWithItems(List<Long> orderIds) {
    Mono<Map<Long, List<Item>>> itemMap = itemRepository
            .findByOrderIdIn(orderIds)
            .collectMultimap(Item::getOrderId)
            .map(m -> m.entrySet().stream().collect(
                    Collectors.toMap(Map.Entry::getKey, e -> List.copyOf(e.getValue()))));

    return itemMap.flatMapMany(map ->
            orderRepository.findAllById(orderIds)
                    .map(o -> new OrderDetail(o, map.getOrDefault(o.getId(), List.of()))));
}

@Repository
@RequiredArgsConstructor
public class OrderQueryRepository {

    private final DatabaseClient client;

    public Flux<OrderSummary> summarize(LocalDate from, LocalDate to) {
        return client.sql("""
                SELECT u.name         AS user_name,
                       COUNT(*)       AS order_count,
                       SUM(o.amount)  AS total_amount
                  FROM orders o
                  JOIN users u ON u.id = o.user_id
                 WHERE o.created_at BETWEEN :from AND :to
                 GROUP BY u.name
                 ORDER BY total_amount DESC
                """)
                .bind("from", from.atStartOfDay())
                .bind("to", to.atTime(23, 59, 59))
                .map((row, meta) -> new OrderSummary(
                        row.get("user_name", String.class),
                        row.get("order_count", Long.class),
                        row.get("total_amount", Long.class)))
                .all();
    }
}
R2DBC 를 쓰기 전에 알아야 할 것
① 연관관계 매핑·지연 로딩·더티 체킹이 없습니다 — JPA 의 편의 기능 대부분이 없습니다. 직접 조합해야 합니다.
② QueryDSL 을 못 씁니다 — 동적 쿼리는 문자열을 조립하거나 Criteria API 를 씁니다.
③ 지원 DB 가 제한적입니다 — MySQL·PostgreSQL·MSSQL·H2·Oracle. 그 외는 확인이 필요합니다.
④ 그래서 “단순 조회가 대량으로 일어나는 서비스”에 잘 맞고, 복잡한 도메인 모델이 있다면 MVC + JPA + 가상 스레드가 나은 선택인 경우가 많습니다.

리액티브 트랜잭션

@Transactional 이 그대로 동작하지만, 스레드가 아니라 리액티브 컨텍스트를 타고 흐른다는 점이 다릅니다.

@Configuration
public class R2dbcConfig {
    @Bean
    public ReactiveTransactionManager transactionManager(ConnectionFactory cf) {
        return new R2dbcTransactionManager(cf);
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final StockRepository stockRepository;

    @Transactional                       // 리액티브에서도 그대로 동작
    public Mono<Order> create(OrderCreateReq req) {
        return stockRepository.findByProductId(req.productId())
                .switchIfEmpty(Mono.error(new StockNotFoundException()))
                .flatMap(stock -> {
                    if (stock.getQuantity() < req.quantity())
                        return Mono.error(new InsufficientStockException());
                    stock.decrease(req.quantity());
                    return stockRepository.save(stock);
                })
                .then(orderRepository.save(Order.from(req)));
                // 어느 단계에서 에러가 나도 전체 롤백 ✅
    }
}

직접 제어하기

@RequiredArgsConstructor
public class OrderService {
    private final TransactionalOperator tx;

    public Mono<Order> create(OrderCreateReq req) {
        return doWork(req)
                .as(tx::transactional);      // 이 체인 전체가 한 트랜잭션
    }
}
주의할 점
① 체인 밖에서 실행되는 코드는 트랜잭션에 안 들어갑니다. 반드시 flatMap·then 으로 이어 붙이세요.
② JDBC 트랜잭션과 섞이지 않습니다 — 한 메서드에서 JPA 와 R2DBC 를 같이 쓰면 롤백이 따로 놉니다.
③ publishOn 으로 스레드를 바꿔도 컨텍스트는 따라가지만, Mono.fromCallable 안의 블로킹 JDBC 호출은 별개입니다.
FLUX 11

에러 처리 · 재시도

리액티브에서는 예외가 신호로 흐르기 때문에 try/catch 로는 못 잡습니다.

// ❌ 이렇게는 안 잡힙니다
try {
    return service.find(id);     // Mono 를 만들 뿐, 에러는 나중에 흐름
} catch (Exception e) { }        // 절대 안 걸림

// ✅ 연산자로 처리
service.find(id)
    // 1) 대체값
    .onErrorReturn(Order.empty())

    // 2) 특정 예외만
    .onErrorReturn(TimeoutException.class, Order.empty())

    // 3) 다른 흐름으로 (폴백)
    .onErrorResume(e -> {
        log.warn("주 저장소 실패, 캐시 조회", e);
        return cacheRepository.find(id);
    })

    // 4) 예외를 바꿔서 다시 던지기
    .onErrorMap(DataAccessException.class,
                e -> new ServiceException("DB 오류", e))

    // 5) 비어 있을 때
    .switchIfEmpty(Mono.error(new OrderNotFoundException(id)))

    // 6) 성공·실패 관계없이
    .doFinally(sig -> meter.increment(sig.name()));

재시도 — 지수 백오프

apiClient.call()
    .timeout(Duration.ofSeconds(3))
    .retryWhen(
        Retry.backoff(3, Duration.ofMillis(200))   // 200ms, 400ms, 800ms
             .maxBackoff(Duration.ofSeconds(5))
             .jitter(0.5)                          // 동시 재시도 분산
             .filter(e -> e instanceof TimeoutException
                       || e instanceof WebClientRequestException)
             .onRetryExhaustedThrow((spec, signal) ->
                     new ExternalApiException("재시도 초과", signal.failure()))
    )
    .onErrorResume(e -> Mono.just(fallbackValue()));
재시도하면 안 되는 것 — 결제·주문 생성처럼 중복이 치명적인 요청은 멱등키(Idempotency-Key) 없이 재시도하면 이중 결제가 납니다. 400 번대 에러도 재시도해 봐야 결과가 같습니다 — filter 로 일시적 오류만 골라내세요.

디버깅 · 테스트 · 함정

리액티브의 가장 큰 비용은 디버깅 난이도입니다. 도구를 알아 두면 훨씬 수월합니다.

디버깅

// 1) log() — 모든 신호를 찍는다
flux.log("order-flow")
    .filter(...)
    .log("after-filter");
// onSubscribe / request(N) / onNext(v) / onComplete

// 2) checkpoint() — 스택 트레이스에 위치 표시
mono.checkpoint("주문 조회 단계")
    .flatMap(...)
    .checkpoint("결제 단계");

// 3) 전역 디버그 모드 (개발 환경만! 성능 비용이 큽니다)
@PostConstruct
void init() { Hooks.onOperatorDebug(); }

// 4) doOn* 으로 관찰 (흐름을 바꾸지 않음)
.doOnSubscribe(s -> log.info("시작"))
.doOnNext(v -> log.debug("값: {}", v))
.doOnError(e -> log.error("실패", e))
.doOnCancel(() -> log.warn("취소됨"))

@Test
