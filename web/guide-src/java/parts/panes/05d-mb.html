JPA 가 “객체로 생각하고 SQL 은 맡긴다”면, MyBatis 는 “SQL 을 내가 쓰고 매핑만 맡긴다”입니다. 복잡한 조회·통계·레거시 DB에서는 이쪽이 훨씬 정직하고 빠릅니다. 이 탭은 설정부터 동적 SQL · 배치 · 인터셉터 · 성능까지 실무 전 범위를 다룹니다.

MYB 01

언제 MyBatis인가 · 설정

JPA 와 우열을 가리는 문제가 아닙니다. “이 시스템에서 SQL 을 누가 통제해야 하는가”에 대한 답이 다를 뿐입니다.

SQL 을 보고 튜닝해야 하는 시스템에서는 MyBatis 가 훨씬 직관적입니다.

MyBatis 가 유리한 경우

  • 통계·리포트가 주 업무 — 윈도 함수·CTE·힌트를 자유롭게
  • 레거시 DB 스키마 — 정규화가 안 됐거나 복합키·트리거가 많다
  • DBA 가 SQL 을 검토하는 조직 — SQL 이 파일로 남는다
  • 튜닝이 잦다 — 실행 계획을 보고 SQL 을 바로 고칠 수 있다
  • 대량 배치 — 벌크·머지·프로시저 호출이 자연스럽다

JPA 가 유리한 경우

  • 도메인 규칙이 복잡 — 객체로 상태를 관리해야 한다
  • CRUD 가 대부분 — 반복 SQL 을 쓰지 않아도 된다
  • DB 를 바꿀 가능성 — 방언 차이를 프레임워크가 흡수
  • 변경 감지·낙관적 락 같은 기능이 필요
  • 스키마를 우리가 설계한다
실무에서 흔한 답 — 쓰기는 JPA, 복잡한 조회는 MyBatis. 둘 다 같은 트랜잭션 안에서 동작하므로 함께 쓰는 데 기술적 문제가 없습니다.

MYB 02

매퍼 — 인터페이스와 XML

MyBatis 의 기본 단위는 인터페이스 + SQL 한 쌍입니다. SQL 은 XML 또는 애너테이션에 쓸 수 있고, 실무에서는 대부분 XML 을 씁니다.

인터페이스

@Mapper
public interface OrderMapper {

    // 단건
    OrderDto findById(Long id);

    // 목록
    List<OrderDto> findByStatus(String status);

    // 파라미터가 여럿이면 @Param 으로 이름을 준다
    List<OrderDto> search(@Param("cond") OrderCondition cond,
                          @Param("offset") int offset,
                          @Param("limit") int limit);

    // 저장 — 생성된 키를 객체에 다시 넣는다
    void insert(OrderDto order);

    int update(OrderDto order);

    int deleteById(Long id);

    // 대량 조회 — 커서 방식
    void streamAll(ResultHandler<OrderDto> handler);
}

XML 매퍼

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
  "https://mybatis.org/dtd/mybatis-3-mapper.dtd">

<mapper namespace="com.example.mapper.OrderMapper">   <!-- ★ 인터페이스 전체 경로 -->

  <select id="findById" parameterType="long" resultType="OrderDto">
    SELECT id, order_no, member_id, total_amount, status, created_at
      FROM orders
     WHERE id = #{id}
  </select>

  <select id="findByStatus" resultType="OrderDto">
    SELECT id, order_no, total_amount, status
      FROM orders
     WHERE status = #{status}
     ORDER BY created_at DESC
  </select>

  <insert id="insert" useGeneratedKeys="true" keyProperty="id">
    INSERT INTO orders (order_no, member_id, total_amount, status, created_at)
    VALUES (#{orderNo}, #{memberId}, #{totalAmount}, #{status}, NOW())
  </insert>

  <update id="update">
    UPDATE orders
       SET status = #{status}, updated_at = NOW()
     WHERE id = #{id}
  </update>

  <delete id="deleteById">
    DELETE FROM orders WHERE id = #{id}
  </delete>
</mapper>

애너테이션 방식

@Mapper
public interface CodeMapper {

    @Select("SELECT code, name FROM code_group WHERE type = #{type}")
    List<CodeDto> findByType(String type);

    @Insert("INSERT INTO code_group(code, name, type) VALUES(#{code}, #{name}, #{type})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    void insert(CodeDto dto);

    @Update("UPDATE code_group SET name = #{name} WHERE code = #{code}")
    int updateName(@Param("code") String code, @Param("name") String name);
}

// 언제 애너테이션을 쓰나
// · SQL 이 짧고 동적 조건이 없을 때 (코드 테이블·단순 조회)
// · 동적 SQL 이 들어가면 <script> 로 감싸야 해서 오히려 지저분해진다
// → 실무 대부분은 XML 이 낫다

기본 규칙

  • namespace = 인터페이스 전체 경로 — 틀리면 BindingException
  • id = 메서드명 — 오버로딩은 불가(같은 id 두 개 금지)
  • resultType 은 반환 원소 타입 — List<OrderDto>여도 OrderDto
  • map-underscore-to-camel-case를 켜면 별칭을 대부분 생략할 수 있다
  • XML 은 src/main/resources 아래에 — 자바 폴더에 두면 빌드에서 빠진다
XML 에서 < 를 쓸 수 없습니다. &lt; 로 이스케이프하거나 <![CDATA[ ... ]]> 로 감싸세요 — WHERE created_at < #{to} 에서 자주 겪는 문제입니다.
MYB 03

파라미터 — #{} 와 ${}

MyBatis 에서 가장 중요한 한 가지입니다. #{}는 바인딩, ${}는 문자열 치환이고, ${}는 SQL 인젝션의 통로입니다.

외울 것은 한 문장 — 값은 #{}, 그 밖에는 쓰지 않는다.
${} — 문자열이 그대로 박힌다
<select id="search" resultType="OrderDto">
  SELECT * FROM orders
   WHERE order_no = '${orderNo}'
</select>

<!-- 실제로 만들어지는 SQL -->
SELECT * FROM orders WHERE order_no = 'ORD-1'

<!-- 사용자가 이렇게 보내면? -->
orderNo = "' OR '1'='1"
SELECT * FROM orders WHERE order_no = '' OR '1'='1'
<!-- 💥 전체 조회. 여기에 UNION 을 붙이면 다른 테이블도 털린다 -->
#{} — 바인딩 파라미터
<select id="search" resultType="OrderDto">
  SELECT * FROM orders
   WHERE order_no = #{orderNo}
</select>

<!-- 실제 SQL -->
SELECT * FROM orders WHERE order_no = ?
<!-- 값은 JDBC 가 바인딩 → 인젝션 불가능 -->
<!-- 실행 계획도 재사용된다 (성능 이점) -->
기본은 언제나 #{}입니다. ${}는 컬럼명·테이블명·정렬 방향처럼 바인딩이 불가능한 자리에서만 쓰고, 반드시 화이트리스트 검증을 거치세요. 
<!-- ${} 를 안전하게 쓰는 유일한 방법 — 화이트리스트 -->
<select id="searchSorted" resultType="OrderDto">
  SELECT * FROM orders
   WHERE status = #{status}
   ORDER BY ${sortColumn} ${sortDirection}
</select>
// 자바 쪽에서 반드시 검증한다
private static final Set<String> SORTABLE =
        Set.of("created_at", "total_amount", "order_no");

public List<OrderDto> searchSorted(String status, String sortColumn, boolean asc) {
    String column = SORTABLE.contains(sortColumn) ? sortColumn : "created_at";
    String direction = asc ? "ASC" : "DESC";        // 문자열을 직접 만들지 않는다
    return orderMapper.searchSorted(status, column, direction);
}

파라미터 여러 개 넘기기

// ① @Param — 가장 명확 (권장)
List<OrderDto> find(@Param("status") String status,
                    @Param("from") LocalDateTime from);
// XML: #{status}, #{from}

// ② DTO 하나로 묶기
List<OrderDto> search(OrderCondition cond);
// XML: #{status}, #{minAmount}  (DTO 필드명)

// ③ Map (권장하지 않음 — 키 오타를 못 잡는다)
List<OrderDto> search(Map<String, Object> params);

// ④ 섞어 쓰기
List<OrderDto> search(@Param("cond") OrderCondition cond,
                      @Param("pageable") PageRequest pageable);
// XML: #{cond.status}, #{pageable.offset}

타입 지정이 필요할 때

<!-- null 을 넘길 때 JDBC 타입을 몰라 에러가 나는 경우 (특히 오라클) -->
WHERE memo = #{memo, jdbcType=VARCHAR}

<!-- 타입 핸들러 지정 -->
WHERE status = #{status, typeHandler=com.example.StatusTypeHandler}

<!-- 숫자 정밀도 -->
#{amount, javaType=java.math.BigDecimal, jdbcType=DECIMAL}

<!-- LIKE 는 바인딩과 함께 쓴다 (문자열 결합 금지) -->
WHERE name LIKE CONCAT('%', #{keyword}, '%')     <!-- MySQL -->
WHERE name LIKE '%' || #{keyword} || '%'          <!-- PostgreSQL·Oracle -->
<!-- 또는 자바에서 "%" + keyword + "%" 를 만들어 #{keyword} 로 -->
MYB 04

resultMap — 결과 매핑

컬럼과 필드 이름이 다르거나, 한 쿼리 결과를 객체 그래프로 만들어야 할 때 씁니다. MyBatis 의 매핑 능력이 드러나는 지점입니다. 

<!-- 기본 resultMap -->
<resultMap id="orderMap" type="OrderDto">
  <id     property="id"          column="order_id"/>      <!-- 식별자 (중요) -->
  <result property="orderNo"     column="order_no"/>
  <result property="totalAmount" column="total_amount"/>
  <result property="status"      column="status"
          typeHandler="org.apache.ibatis.type.EnumTypeHandler"/>
  <result property="createdAt"   column="created_at"/>
</resultMap>

<select id="findById" resultMap="orderMap">
  SELECT id AS order_id, order_no, total_amount, status, created_at
    FROM orders WHERE id = #{id}
</select>

<!-- 상속으로 재사용 -->
<resultMap id="orderDetailMap" type="OrderDetailDto" extends="orderMap">
  <result property="memberName" column="member_name"/>
  <result property="memo"       column="memo"/>
</resultMap>

<!-- 생성자 매핑 (불변 DTO·record) -->
<resultMap id="summaryMap" type="OrderSummary">
  <constructor>
    <idArg column="id"           javaType="java.lang.Long"/>
    <arg   column="order_no"     javaType="java.lang.String"/>
    <arg   column="total_amount" javaType="java.lang.Long"/>
  </constructor>
</resultMap>

언제 resultMap 이 필요한가

  • 컬럼명과 필드명이 다르다 — map-underscore-to-camel-case로 안 되는 경우
  • 연관 객체를 채워야 한다 (association·collection — 다음 섹션)
  • 생성자로만 만들 수 있는 DTO (record·불변 객체)
  • 타입 핸들러를 지정해야 한다
  • 같은 매핑을 여러 쿼리에서 재사용한다
단순 조회는 resultType으로 충분합니다. 카멜 케이스 자동 변환만 켜 두면 대부분의 CRUD 는 resultMap 없이 됩니다 — 필요할 때만 쓰세요.

자주 만나는 매핑 문제

증상원인
필드가 전부 null컬럼명 불일치 → 별칭 또는 resultMap
enum 매핑 실패DB 값과 enum 이름 불일치 → 타입 핸들러 (10 참고)
날짜가 안 들어온다LocalDateTime 지원 확인 · 드라이버 버전
중복 행이 하나로 합쳐짐<id> 태그로 식별자를 지정했는지
0/false 가 null 로call-setters-on-nulls 설정 확인
record 매핑 실패생성자 매핑(<constructor>) 사용
설정 한 줄로 대부분의 매핑이 사라집니다 — resultMap 은 예외 상황에만.
MYB 05

연관 매핑 — association · collection

한 번의 조인 결과를 객체 그래프로 만듭니다. JPA 의 연관관계와 비슷해 보이지만, MyBatis 는 매핑만 할 뿐 지연 로딩·변경 감지 같은 것은 없습니다.

1:1 · N:1 — association

<resultMap id="orderWithMember" type="OrderDto">
  <id     property="id"      column="o_id"/>
  <result property="orderNo" column="o_order_no"/>

  <association property="member" javaType="MemberDto">
    <id     property="id"    column="m_id"/>
    <result property="name"  column="m_name"/>
    <result property="grade" column="m_grade"/>
  </association>
</resultMap>

<select id="findWithMember" resultMap="orderWithMember">
  SELECT o.id        AS o_id,
         o.order_no  AS o_order_no,
         m.id        AS m_id,
         m.name      AS m_name,
         m.grade     AS m_grade
    FROM orders o
    JOIN members m ON m.id = o.member_id
   WHERE o.id = #{id}
</select>

<!-- ★ 별칭 접두사를 쓰면 컬럼 충돌을 피할 수 있다 (o_ / m_) -->

1:N — collection

<resultMap id="orderDetail" type="OrderDetailDto">
  <id     property="id"          column="o_id"/>
  <result property="orderNo"     column="o_order_no"/>
  <result property="totalAmount" column="o_total"/>

  <collection property="items" ofType="OrderItemDto">
    <id     property="id"          column="i_id"/>
    <result property="productName" column="i_product_name"/>
    <result property="quantity"    column="i_quantity"/>
    <result property="price"       column="i_price"/>
  </collection>
</resultMap>

<select id="findDetail" resultMap="orderDetail">
  SELECT o.id AS o_id, o.order_no AS o_order_no, o.total_amount AS o_total,
         i.id AS i_id, i.product_name AS i_product_name,
         i.quantity AS i_quantity, i.price AS i_price
    FROM orders o
    LEFT JOIN order_items i ON i.order_id = o.id
   WHERE o.id = #{id}
</select>

<!-- 조인 결과가 여러 행이어도 MyBatis 가 <id> 기준으로 하나의 객체로 합친다 -->

별도 쿼리로 채우기 (select 속성)

<resultMap id="orderLazy" type="OrderDto">
  <id property="id" column="id"/>
  <collection property="items"
              column="id"                        <!-- 이 값을 인자로 넘긴다 -->
              select="findItemsByOrderId"        <!-- 별도 쿼리 실행 -->
              fetchType="lazy"/>                 <!-- 지연 로딩 -->
</resultMap>

<select id="findItemsByOrderId" resultType="OrderItemDto">
  SELECT * FROM order_items WHERE order_id = #{id}
</select>
이 방식은 N+1 을 만듭니다. 주문 100건을 조회하면 항목 쿼리가 100번 나갑니다. 목록에서는 조인 매핑을, 상세 화면처럼 단건일 때만 이 방식을 고려하세요. 지연 로딩을 쓰려면 lazy-loading-enabled: true 설정도 필요합니다.

JPA 연관관계와의 차이

항목MyBatis
매핑 시점쿼리 결과를 읽을 때만 — 연결이 유지되지 않는다
지연 로딩select 속성으로 가능하지만 N+1 주의
변경 감지없다 — 바꾸면 update 를 직접 호출
영속성 컨텍스트없다 — 같은 행을 두 번 조회하면 다른 객체
cascade없다 — 자식 저장·삭제를 직접
이 “없음”이 단점만은 아닙니다. 예측 가능성이 높아 어떤 SQL 이 언제 나가는지가 코드에 그대로 보입니다.
MYB 06

동적 SQL

MyBatis 를 쓰는 가장 큰 이유입니다. 조건에 따라 SQL 을 조립하면서도 SQL 의 모양이 그대로 보입니다. 

<select id="search" resultType="OrderDto">
  SELECT o.id, o.order_no, o.total_amount, o.status, m.name AS member_name
    FROM orders o
    JOIN members m ON m.id = o.member_id

  <where>                                    <!-- ★ 앞의 AND/OR 를 자동 제거 -->
    o.deleted = false
    <if test="status != null">
      AND o.status = #{status}
    </if>
    <if test="minAmount != null">
      AND o.total_amount >= #{minAmount}
    </if>
    <if test="keyword != null and keyword != ''">
      AND (o.order_no LIKE CONCAT('%', #{keyword}, '%')
           OR m.name LIKE CONCAT('%', #{keyword}, '%'))
    </if>
    <if test="from != null and to != null">
      AND o.created_at >= #{from}
      AND o.created_at < #{to}
    </if>
    <if test="statuses != null and !statuses.isEmpty()">
      AND o.status IN
      <foreach collection="statuses" item="s" open="(" separator="," close=")">
        #{s}
      </foreach>
    </if>
  </where>

  <choose>                                   <!-- if/else if/else -->
    <when test="sort == 'amount'">ORDER BY o.total_amount DESC, o.id DESC</when>
    <when test="sort == 'oldest'">ORDER BY o.created_at ASC, o.id ASC</when>
    <otherwise>ORDER BY o.created_at DESC, o.id DESC</otherwise>
  </choose>

  LIMIT #{limit} OFFSET #{offset}
</select>

<!-- UPDATE 는 <set> 이 쉼표를 정리해 준다 -->
<update id="updateSelective">
  UPDATE orders
  <set>
    <if test="status != null">status = #{status},</if>
    <if test="memo != null">memo = #{memo},</if>
    updated_at = NOW()
  </set>
  WHERE id = #{id}
</update>

<!-- trim 으로 직접 제어 -->
<trim prefix="WHERE" prefixOverrides="AND |OR ">
  ...
</trim>

foreach 활용

<!-- IN 절 -->
WHERE id IN
<foreach collection="ids" item="id" open="(" separator="," close=")">
  #{id}
</foreach>

<!-- 대량 INSERT (한 문장으로) -->
<insert id="insertAll">
  INSERT INTO order_items (order_id, product_id, quantity, price)
  VALUES
  <foreach collection="items" item="i" separator=",">
    (#{i.orderId}, #{i.productId}, #{i.quantity}, #{i.price})
  </foreach>
</insert>

<!-- Map 순회 -->
<foreach collection="params" index="key" item="value" separator=" AND ">
  ${key} = #{value}
</foreach>
IN 절에 값이 1,000개를 넘으면 오라클은 에러가 나고, 다른 DB 도 실행 계획이 나빠집니다. 청크로 나누거나 임시 테이블·조인으로 바꾸세요. 빈 리스트를 넘기면 IN () 이 되어 문법 오류가 나므로 빈 검사도 필수입니다.

bind · OGNL 표현식

<select id="searchByName" resultType="MemberDto">
  <bind name="pattern" value="'%' + keyword + '%'"/>
  SELECT * FROM members WHERE name LIKE #{pattern}
</select>

<!-- test 에 쓰는 OGNL 표현식 -->
<if test="status != null">
<if test="keyword != null and keyword != ''">
<if test="list != null and list.size() > 0">

<if test="flag">                          <!-- Boolean -->

MYB 07

SQL 재사용

같은 컬럼 목록과 조건을 여러 쿼리에 복사하다 보면 한 곳만 고치고 다른 곳을 놓치는 사고가 납니다. <sql> 조각으로 묶습니다. 

<!-- 컬럼 목록을 한 곳에서 관리 -->
<sql id="orderColumns">
  o.id, o.order_no, o.member_id, o.total_amount, o.status, o.created_at
</sql>

<!-- 공통 검색 조건 -->
<sql id="searchConditions">
  <where>
    o.deleted = false
    <if test="status != null">AND o.status = #{status}</if>
    <if test="from != null">AND o.created_at >= #{from}</if>
    <if test="to != null">AND o.created_at < #{to}</if>
  </where>
</sql>

<select id="search" resultType="OrderDto">
  SELECT <include refid="orderColumns"/>
    FROM orders o
  <include refid="searchConditions"/>
   ORDER BY o.created_at DESC
   LIMIT #{limit} OFFSET #{offset}
</select>

<select id="countSearch" resultType="long">
  SELECT COUNT(*)
    FROM orders o
  <include refid="searchConditions"/>      <!-- 조건을 그대로 재사용 -->
</select>

<!-- 다른 매퍼의 조각도 가져올 수 있다 (namespace 로) -->
<include refid="com.example.mapper.CommonMapper.paging"/>

<!-- 파라미터를 받는 조각 -->
<sql id="tableName">
  orders_${yearMonth}                       <!-- 파티션 테이블 -->
</sql>
<select id="findPartitioned" resultType="OrderDto">
  SELECT * FROM <include refid="tableName">
    <property name="yearMonth" value="#{ym}"/>
  </include>
</select>
목록 쿼리와 카운트 쿼리의 조건을 <sql> 로 공유하는 것이 가장 실용적인 활용입니다. 조건이 어긋나 총 건수와 실제 목록이 안 맞는 버그를 막습니다.
MYB 08

페이징

MyBatis 는 페이징을 프레임워크가 대신 해 주지 않습니다. 직접 LIMIT 을 쓰거나, PageHelper 같은 플러그인을 붙이거나, 커서 방식을 씁니다.

① 직접 작성 — 가장 명확

public record PageRequest(int page, int size) {
    public int offset() { return (page - 1) * size; }
}

@Mapper
public interface OrderMapper {
    List<OrderDto> search(@Param("cond") OrderCondition cond,
                          @Param("offset") int offset,
                          @Param("limit") int limit);
    long countSearch(@Param("cond") OrderCondition cond);
}

@Service
public class OrderQueryService {
    public Page<OrderDto> search(OrderCondition cond, PageRequest req) {
        List<OrderDto> content = mapper.search(cond, req.offset(), req.size());
        long total = mapper.countSearch(cond);
        return new PageImpl<>(content, org.springframework.data.domain
                .PageRequest.of(req.page() - 1, req.size()), total);
    }
}
DB 별 문법 차이 — MySQL·PostgreSQL 은 LIMIT ? OFFSET ?, 오라클 12c+ 는 OFFSET ? ROWS FETCH NEXT ? ROWS ONLY, 그 이전 오라클은 ROWNUM 서브쿼리입니다.

② PageHelper — 자동 변환

// implementation("com.github.pagehelper:pagehelper-spring-boot-starter:2.1.0")

public PageInfo<OrderDto> search(OrderCondition cond, int page, int size) {
    PageHelper.startPage(page, size);                // ★ 바로 다음 쿼리에만 적용
    List<OrderDto> list = mapper.search(cond);       // LIMIT 이 자동으로 붙는다
    return new PageInfo<>(list);                     // 총 건수도 자동 계산
}

// 장점 — SQL 을 건드리지 않고 페이징. DB 방언도 자동
// 단점
// · startPage 직후의 쿼리에만 적용된다 (사이에 다른 쿼리가 오면 오작동)
// · 카운트 쿼리를 자동 생성하므로 복잡한 쿼리에서 비효율적일 수 있다
// · 인터셉터로 SQL 을 조작하므로 디버깅이 어려워진다
<!-- ③ 커서(키셋) 페이징 — 대용량에서 유일하게 일정한 성능 -->
<select id="scroll" resultType="OrderDto">
  SELECT <include refid="orderColumns"/>
    FROM orders o
   WHERE o.deleted = false
  <if test="lastId != null">
     AND o.id < #{lastId}
  </if>
   ORDER BY o.id DESC
   LIMIT #{size}
</select>

<!-- ④ 커버링 인덱스 응용 — 깊은 페이지 대응 (MySQL) -->
<select id="deepPage" resultType="OrderDto">
  SELECT o.*
    FROM orders o
    JOIN (SELECT id FROM orders
           WHERE deleted = false
           ORDER BY created_at DESC
           LIMIT #{limit} OFFSET #{offset}) t ON t.id = o.id
   ORDER BY o.created_at DESC
</select>
정렬 기준에 유일 컬럼을 반드시 포함하세요. ORDER BY created_at DESC만으로는 같은 시각의 행 순서가 매번 달라져 페이지 사이에서 데이터가 중복되거나 빠집니다. ORDER BY created_at DESC, id DESC 처럼 타이브레이커를 두세요.
MYB 09

배치 · 대량 처리

MyBatis 의 강점이 가장 잘 드러나는 영역입니다. 수만 건 INSERT와 수백만 건 조회를 메모리 안전하게 처리하는 방법입니다.

대량 INSERT — 두 가지 방법

// ① foreach 다중 VALUES — 가장 간단하고 빠르다
// <insert id="insertAll">
//   INSERT INTO order_items(order_id, product_id, quantity)
//   VALUES <foreach collection="items" item="i" separator=",">
//            (#{i.orderId}, #{i.productId}, #{i.quantity})
//          </foreach>
// </insert>

public void bulkInsert(List<OrderItem> items) {
    // ⚠️ 한 번에 너무 많이 넣으면 SQL 길이 제한에 걸린다 → 청크로
    Lists.partition(items, 500).forEach(mapper::insertAll);
}

// ② ExecutorType.BATCH — JDBC 배치 사용
@Service
@RequiredArgsConstructor
public class BulkService {
    private final SqlSessionFactory sqlSessionFactory;

    public void bulkInsert(List<OrderItem> items) {
        try (SqlSession session = sqlSessionFactory.openSession(ExecutorType.BATCH)) {
            OrderItemMapper mapper = session.getMapper(OrderItemMapper.class);
            for (int i = 0; i < items.size(); i++) {
                mapper.insert(items.get(i));
                if (i % 1000 == 0) session.flushStatements();   // 주기적으로 전송
            }
            session.flushStatements();
            session.commit();
        }
    }
}

MySQL 에서 fetchSize 가 안 먹는 이유 — 커넥터가 기본적으로 전체 결과를 메모리로 가져옵니다. useCursorFetch=true 를 URL 에 넣거나 fetchSize = Integer.MIN_VALUE 로 스트리밍 모드를 켜야 합니다.
작업권장 방법
수백 건 INSERTforeach 다중 VALUES
수만~수십만 건 INSERTExecutorType.BATCH + 청크 flush
대량 UPDATE (조건 기반)단일 UPDATE 문 하나로 (WHERE 조건으로)
행마다 다른 값으로 UPDATEBATCH 실행 또는 CASE WHEN · 임시 테이블 조인
UPSERTDB 문법 그대로 — ON DUPLICATE KEY·ON CONFLICT·MERGE
수백만 건 조회ResultHandler·Cursor + fetchSize
대량 처리에서 고칠 것은 SQL 이 아니라 몇 번 왕복하는가입니다.
MYB 10

타입 핸들러

자바 타입과 JDBC 타입 사이의 변환기입니다. enum 코드값, JSON 컬럼, 암호화, 커스텀 값 객체에 씁니다. 

// ① enum 을 코드값으로 저장 — 가장 흔한 쓰임
public interface CodeEnum {
    String getCode();
}

public enum OrderStatus implements CodeEnum {
    NEW("01"), PAID("02"), SHIPPED("03"), DONE("04"), CANCELED("99");

    private final String code;
    OrderStatus(String code) { this.code = code; }
    @Override public String getCode() { return code; }

    public static OrderStatus fromCode(String code) {
        return Arrays.stream(values())
                .filter(v -> v.code.equals(code))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("알 수 없는 코드: " + code));
    }
}

@MappedTypes(OrderStatus.class)
public class OrderStatusTypeHandler extends BaseTypeHandler<OrderStatus> {

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    OrderStatus param, JdbcType jdbcType) throws SQLException {
        ps.setString(i, param.getCode());
    }

    @Override
    public OrderStatus getNullableResult(ResultSet rs, String columnName) throws SQLException {
        String code = rs.getString(columnName);
        return code == null ? null : OrderStatus.fromCode(code);
    }

    @Override
    public OrderStatus getNullableResult(ResultSet rs, int columnIndex) throws SQLException {
        String code = rs.getString(columnIndex);
        return code == null ? null : OrderStatus.fromCode(code);
    }

    @Override
    public OrderStatus getNullableResult(CallableStatement cs, int columnIndex) throws SQLException {
        String code = cs.getString(columnIndex);
        return code == null ? null : OrderStatus.fromCode(code);
    }
}

@MappedTypes(ProductOptions.class)
@MappedJdbcTypes(JdbcType.VARCHAR)
public class JsonTypeHandler extends BaseTypeHandler<ProductOptions> {

    private static final ObjectMapper MAPPER = new ObjectMapper();

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i,
                                    ProductOptions param, JdbcType jt) throws SQLException {
        try { ps.setString(i, MAPPER.writeValueAsString(param)); }
        catch (JsonProcessingException e) { throw new SQLException(e); }
    }

    @Override
    public ProductOptions getNullableResult(ResultSet rs, String col) throws SQLException {
        return parse(rs.getString(col));
    }
    // 나머지 오버라이드 생략

    private ProductOptions parse(String json) throws SQLException {
        if (json == null) return null;
        try { return MAPPER.readValue(json, ProductOptions.class); }
        catch (JsonProcessingException e) { throw new SQLException(e); }
    }
}

MyBatis 에도 1차·2차 캐시가 있습니다. 그런데 2차 캐시는 대부분의 실무에서 위험합니다 — 왜 그런지 알고 판단해야 합니다.

MYB 12

인터셉터(플러그인)

MyBatis 실행 과정에 끼어드는 확장점입니다. 쿼리 로깅·실행 시간 측정·공통 컬럼 자동 채우기·멀티테넌시에 씁니다. 

// 슬로우 쿼리 로깅 + 실행 시간 측정
@Intercepts({
    @Signature(type = Executor.class, method = "query",
               args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class}),
    @Signature(type = Executor.class, method = "update",
               args = {MappedStatement.class, Object.class}),
})
@Component
public class SlowQueryInterceptor implements Interceptor {

    private static final Logger log = LoggerFactory.getLogger(SlowQueryInterceptor.class);
    private static final long THRESHOLD_MS = 1000;

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();
        } finally {
            long elapsed = System.currentTimeMillis() - start;
            if (elapsed >= THRESHOLD_MS) {
                log.warn("슬로우 쿼리 {}ms — {}", elapsed, ms.getId());
            }
        }
    }
}

// 공통 컬럼 자동 채우기 (created_by · updated_at 등)
@Intercepts(@Signature(type = Executor.class, method = "update",
                       args = {MappedStatement.class, Object.class}))
@Component
public class AuditInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        Object param = invocation.getArgs()[1];
        if (param instanceof Auditable auditable) {
            auditable.setUpdatedAt(LocalDateTime.now());
            auditable.setUpdatedBy(currentUser());
        }
        return invocation.proceed();
    }
}

끼어들 수 있는 지점

대상할 수 있는 일
Executor쿼리 실행 전후 — 로깅·시간 측정·캐시
StatementHandlerSQL 문자열 조작 — 페이징·힌트 추가·테넌트 조건
ParameterHandler파라미터 가공 — 암호화
ResultSetHandler결과 가공 — 복호화·마스킹
인터셉터는 강력하지만 위험합니다. SQL 을 몰래 바꾸면 “분명히 이렇게 썼는데 다른 쿼리가 나간다”는 상황이 생겨 디버깅이 매우 어려워집니다. 정말 전역적으로 필요한 것에만 쓰세요.

등록과 순서

// Spring Boot 에서는 @Component 만 붙이면 자동 등록된다

// 순서를 제어하려면 SqlSessionFactory 를 직접 구성
@Bean
public SqlSessionFactory sqlSessionFactory(DataSource ds) throws Exception {
    SqlSessionFactoryBean bean = new SqlSessionFactoryBean();
    bean.setDataSource(ds);

MYB 13

Spring 통합 · 다중 데이터소스

트랜잭션은 스프링이 관리하고 MyBatis 는 그 위에서 돕니다. 여러 DB를 쓰거나 읽기 복제본으로 나눌 때의 구성도 함께 봅니다. 

// 기본 — 스프링 트랜잭션이 SqlSession 을 관리한다
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderMapper orderMapper;
    private final OrderItemMapper itemMapper;

    @Transactional                       // 두 매퍼가 같은 커넥션·트랜잭션을 쓴다
    public Long place(OrderCreateRequest req) {
        OrderDto order = OrderDto.from(req);
        orderMapper.insert(order);                    // useGeneratedKeys 로 id 채워짐

        List<OrderItemDto> items = req.items().stream()
                .map(i -> OrderItemDto.of(order.getId(), i))
                .toList();
        itemMapper.insertAll(items);

        return order.getId();
    }

    @Transactional(readOnly = true)      // 읽기 전용 힌트 (읽기 복제본 라우팅에 사용)
    public OrderDetailDto get(Long id) {
        return orderMapper.findDetail(id);
    }
}

@Configuration

public class OrderDataSourceConfig {

    @Bean @Primary
    @ConfigurationProperties("spring.datasource.order")
    public DataSource orderDataSource() {
        return DataSourceBuilder.create().type(HikariDataSource.class).build();
    }

    @Bean
    public SqlSessionFactory orderSqlSessionFactory(
            @Qualifier("orderDataSource") DataSource ds) throws Exception {
        SqlSessionFactoryBean bean = new SqlSessionFactoryBean();
        bean.setDataSource(ds);
        bean.setMapperLocations(new PathMatchingResourcePatternResolver()
                .getResources("classpath:mapper/order/*.xml"));
        org.apache.ibatis.session.Configuration cfg =
                new org.apache.ibatis.session.Configuration();
        cfg.setMapUnderscoreToCamelCase(true);
        bean.setConfiguration(cfg);
        return bean.getObject();
    }

    @Bean
    public SqlSessionTemplate orderSqlSessionTemplate(
            @Qualifier("orderSqlSessionFactory") SqlSessionFactory factory) {
        return new SqlSessionTemplate(factory);
    }

    @Bean @Primary
    public PlatformTransactionManager orderTransactionManager(
            @Qualifier("orderDataSource") DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }
}

// · @Transactional 없이 매퍼를 부르면 매번 새 세션·커넥션이다
//   → readOnly 판단이 안 되어 항상 writer 로 간다
// · 조회 메서드에도 @Transactional(readOnly = true) 를 붙이는 습관이 필요하다
조회에 readOnly = true 를 붙이는 것은 라우팅뿐 아니라 플러시 생략·DB 힌트 측면에서도 이득입니다. 팀 컨벤션으로 정해 두세요.
MYB 14

JPA 와 함께 쓰기

실무에서 가장 현실적인 구성입니다. 쓰기·도메인 규칙은 JPA, 복잡한 조회·통계·배치는 MyBatis. 같은 트랜잭션에서 함께 동작하지만 주의할 점이 있습니다.

둘은 같은 커넥션을 쓰므로 한 트랜잭션 안에서 원자성이 보장됩니다.

함께 쓸 때 주의점

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository orderRepository;   // JPA
    private final OrderQueryMapper orderQueryMapper; // MyBatis

    @Transactional
    public void payAndReport(Long id) {
        Order order = orderRepository.findById(id).orElseThrow();
        order.markPaid();                            // 더티 체킹 — 아직 flush 안 됨

        // ⚠️ MyBatis 는 영속성 컨텍스트를 모른다 → 옛 값을 읽는다!
        OrderStat stat = orderQueryMapper.findStat(id);

        // ✅ 명시적으로 flush 한 뒤 조회
        orderRepository.flush();
        OrderStat stat2 = orderQueryMapper.findStat(id);
    }

    @Transactional
    public void bulkUpdate(List<Long> ids) {
        orderQueryMapper.bulkUpdateStatus(ids, "EXPIRED");   // MyBatis 로 대량 수정
        entityManager.clear();                                // ✅ JPA 캐시 비우기
    }
}

하나만 고르라면 — 도메인이 복잡한 서비스는 JPA + QueryDSL, 데이터 가공·통계가 중심이면 MyBatis. 규모가 커지면 대부분 둘 다 쓰게 됩니다.
세 탭을 모두 보셨다면 — 데이터 · JPA(기초) → JPA 심화(상속·락·대용량) → QueryDSL(타입 안전 동적 쿼리) → MyBatis(SQL 직접 작성)까지가 자바 데이터 계층의 전 범위입니다. 이제 어떤 요구에 어떤 도구를 쓸지를 근거를 갖고 정할 수 있습니다.
