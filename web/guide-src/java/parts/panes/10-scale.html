SCALE 01

트래픽을 숫자로 읽는 법

“많다·느리다”로는 아무것도 못 고칩니다. 먼저 단위를 손에 익히세요.

알아야 하는 단위 네 개

단위뜻과 감각
RPS / TPS초당 요청 수. “DAU 100만·1인당 20요청·피크가 평균의 5배”면 100만×20÷86400×5 ≈ 1,150 RPS
지연(Latency)요청 하나가 끝나기까지 걸린 시간. 평균이 아니라 p95·p99를 봅니다
동시성같은 순간 처리 중인 요청 수. 스레드·커넥션이 여기에 묶입니다
처리량(Throughput)시간당 실제로 끝낸 일의 양. RPS 를 버텨 낸 결과
평균 응답시간은 거짓말을 합니다. 100명 중 99명이 50ms, 1명이 5초여도 평균은 100ms 입니다. 그 1명이 매일 1만 명이면 민원은 그쪽에서 옵니다. 지표는 p99 로 합의하세요.

리틀의 법칙 — 딱 하나만 외운다면

동시 처리 건수 = 도착률(RPS) × 평균 처리시간(초)

예) 500 RPS · 평균 200ms
    → 500 × 0.2 = 100 건이 항상 서버 안에 떠 있다
    → 스레드(또는 커넥션)가 100개는 있어야 밀리지 않는다

예) 같은 500 RPS 인데 외부 API 가 느려져 2초가 됐다
    → 500 × 2 = 1,000 건
    → 톰캣 기본 스레드 200개로는 즉시 대기열 폭발
    → 요청은 큐에 쌓이고, 응답시간은 눈덩이처럼 커진다
장애의 90%는 이 식 하나로 설명됩니다. “왜 갑자기 전부 느려졌지?” → 대개 처리시간이 늘어 동시 건수가 한도를 넘은 것입니다. 트래픽이 늘지 않아도 의존하는 쪽이 느려지면 똑같이 무너집니다.

용량 산정 — 면접에서 자주 시키는 계산

순서대로 따라가면 됩니다

1) DAU 와 1인당 요청 수 → 하루 총 요청
2) ÷ 86,400 → 평균 RPS
3) × 피크 배수(보통 3~10) → 피크 RPS
4) 리틀의 법칙 → 필요한 동시 처리 수
5) 서버 1대가 감당하는 RPS 로 나눔 → 필요한 대수
6) 저장량 = 하루 데이터량 × 보관 기간 × 복제본 수

체크: 읽기:쓰기 비율은? (보통 읽기가 9배 이상)
      → 읽기가 압도적이면 캐시·읽기 복제본이 먼저다

서버 1대의 감각 (JVM · 8vCPU 기준)

작업 성격대략의 한 대 처리량
메모리 캐시 응답 (DB 안 감)수천 ~ 수만 RPS
Redis 조회 1회 포함수천 RPS
단순 DB 조회 1~2회수백 ~ 1천 RPS
DB 쓰기 + 트랜잭션수백 RPS
외부 API 대기 포함(블로킹)스레드 수에 갇힘 — 가상 스레드 검토
정확한 값이 목적이 아닙니다. 자릿수가 맞는지 보는 겁니다. “100 RPS 인데 서버 20대”면 뭔가 잘못 짜인 것이고, “5,000 RPS 인데 2대”면 부하 테스트 없이는 못 믿습니다.

SCALE 03

캐시 전략 총정리

트래픽 대응의 가장 저렴하고 효과 큰 수단입니다. 대신 정합성을 내줍니다.

읽기 패턴 — 실무는 사실상 이것 하나

[Cache-Aside / Look-aside]  ★ 90% 는 이걸 씁니다

  1. 캐시 확인 → 있으면 그대로 반환 (HIT)
  2. 없으면 DB 조회                    (MISS)
  3. 캐시에 넣고 반환

장점  캐시가 죽어도 서비스는 산다 (DB 로 흐름)
단점  MISS 시 한 번은 느리다, 정합성은 TTL 에 맡긴다

쓰기 패턴

방식동작과 쓰임
Write-AroundDB 만 쓰고 캐시는 지운다. 가장 안전 — 기본값으로 삼으세요
Write-ThroughDB·캐시 동시 갱신. 일관되지만 쓰기가 느려짐
Write-Back캐시에 먼저 쓰고 나중에 DB 반영. 빠르지만 유실 위험 — 조회수 같은 데만
갱신할 때는 “고치지 말고 지우세요”(evict). 캐시를 새 값으로 덮어쓰면 동시 수정 시 오래된 값이 나중에 덮는 사고가 납니다. 지워 두면 다음 조회가 DB 에서 최신을 가져옵니다.

스프링 캐시 추상화 — 코드는 이게 끝

@EnableCaching            // 부트 클래스에 한 번
@Configuration
class CacheConfig {
    @Bean
    CacheManager cacheManager(RedisConnectionFactory cf) {
        var json = new GenericJackson2JsonRedisSerializer();
        var base = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .disableCachingNullValues()      // null 저장 금지
            .serializeValuesWith(SerializationPair.fromSerializer(json));

        return RedisCacheManager.builder(cf)
            .cacheDefaults(base)
            .withCacheConfiguration("product",         // 캐시별 TTL 따로
                base.entryTtl(Duration.ofMinutes(30)))
            .build();
    }
}

@Service
class ProductService {

    @Cacheable(value = "product", key = "#id")
    public ProductDto find(Long id) { ... }        // 결과를 캐싱

    @CacheEvict(value = "product", key = "#dto.id")
    public void update(ProductDto dto) { ... }     // 바뀌면 지운다

    @CacheEvict(value = "product", allEntries = true)
    public void reloadAll() { ... }                // 통째로 비우기
}
같은 클래스 안에서 부르면 캐시가 안 먹습니다. @Cacheable 은 프록시로 동작해서 내부 호출은 프록시를 안 거칩니다 (@Transactional 과 똑같은 함정 — 🧬 고급 탭 a11 참고).

무엇을 캐시할지 · 하지 말지

캐시하면 효과가 큰 것
  • 읽기가 압도적으로 많고 잘 안 바뀌는 것 — 상품 상세, 카테고리, 설정
  • 계산이 비싼 것 — 집계·랭킹·추천 결과
  • 외부 API 응답 — 환율, 날씨, 배송사 코드
  • 권한·회원 정보처럼 매 요청마다 조회되는 것
캐시하면 사고 나는 것
  • 돈·재고 같은 정합성이 생명인 값 — 캐시된 재고로 판매 결정 금지
  • 사용자마다 다르고 한 번만 보는 데이터 — 적중률 0, 메모리만 먹음
  • 개인정보 — 넣는다면 TTL 짧게·암호화. Redis 는 평문 저장입니다
  • 이미 1ms 인 쿼리 — 네트워크 왕복이 더 비쌉니다

캐시로만 쓰기엔 아깝습니다. 자료구조를 고르는 게 절반입니다.

키 이름 규칙 · TTL

서비스:도메인:식별자[:버전]

  user:session:ab12cd

규칙
· TTL 없는 키를 만들지 마세요 → 언젠가 메모리가 찹니다
· 값 하나가 100KB 를 넘으면 설계를 다시 보세요 (Big Key)

파이프라인 — 왕복을 줄이는 법

// 나쁨: 1,000번 네트워크 왕복 (1ms × 1000 = 1초)
for (var id : ids) redis.opsForValue().get("p:" + id);

// 좋음: 한 번에 보내기
List<String> keys = ids.stream().map(id -> "p:" + id).toList();
List<Object> values = redis.opsForValue().multiGet(keys);   // MGET

// 서로 다른 명령을 묶을 때는 파이프라인
redis.executePipelined((RedisCallback<Object>) conn -> {
    for (var id : ids) conn.stringCommands().get(("p:" + id).getBytes());
    return null;

SCALE 05

캐시가 서비스를 죽이는 세 가지

캐시를 넣어서 생긴 장애는 캐시를 안 넣었을 때보다 큽니다. 이름을 알아 두세요.

셋 다 「캐시가 비는 순간」이 원인입니다 — 언제 비는지를 흩뿌리는 것이 공통 해법입니다.

① 캐시 스탬피드 (Thundering Herd)

인기 상품 캐시가 만료되는 그 순간
  → 동시에 들어온 요청 3,000개가 전부 MISS
  → 3,000개가 동시에 같은 DB 쿼리를 날림
  → DB CPU 100% · 커넥션 고갈 · 전 서비스 마비

막는 법 세 가지

  • TTL 을 흩뿌리기 — 10분 + random(0~60초). 한 줄이면 되고 효과가 큽니다
  • 재계산은 한 명만 — 분산 락을 잡은 요청만 DB 로, 나머지는 잠깐 기다리거나 옛 값을 씁니다
  • 미리 갱신 — 남은 TTL 이 10% 미만이면 백그라운드로 먼저 새로 채웁니다
public ProductDto find(Long id) {
    String key = "product:" + id;
    var hit = redis.opsForValue().get(key);
    if (hit != null) return (ProductDto) hit;

    // MISS — 락을 얻은 하나만 DB 로 간다
    String lockKey = "lock:" + key;
    Boolean got = redis.opsForValue()
        .setIfAbsent(lockKey, "1", Duration.ofSeconds(3));

    if (Boolean.TRUE.equals(got)) {
        try {
            var dto = repository.findDto(id);
            long ttl = 600 + ThreadLocalRandom.current().nextInt(60);   // ★ 흩뿌리기
            redis.opsForValue().set(key, dto, Duration.ofSeconds(ttl));
            return dto;
        } finally { redis.delete(lockKey); }
    }
    // 못 얻은 요청은 짧게 기다렸다가 캐시를 다시 본다
    try { Thread.sleep(50); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    var retry = redis.opsForValue().get(key);
    return retry != null ? (ProductDto) retry : repository.findDto(id);
}

② 캐시 관통 (Penetration)

존재하지 않는 id 를 계속 조회 (봇·공격·버그)
  → 캐시에는 영원히 없음 → 매번 DB 로 통과
  → 캐시를 넣은 의미가 사라짐

· "없음"도 캐시한다 (짧은 TTL, 예: 30초)

동시성 제어 — 재고가 마이너스가 되는 이유

서버가 여러 대가 되는 순간 synchronized 는 아무 의미가 없습니다.

사고는 읽기와 쓰기 사이의 틈에서 납니다 — 그 틈을 없애는 것이 가장 싼 해법입니다.

무슨 일이 벌어지나

재고 1개 · 동시에 100명이 주문

서버A 스레드1: SELECT 재고 → 1
서버B 스레드7: SELECT 재고 → 1     ← 아직 아무도 안 줄임
서버A: 1 > 0 이므로 주문 생성, UPDATE 재고 = 0
서버B: 1 > 0 이므로 주문 생성, UPDATE 재고 = 0

→ 1개를 2명에게 팔았고, 재고는 0
→ 100명이면 재고 -37 같은 숫자가 실제로 남습니다
synchronized 는 JVM 하나 안에서만 유효합니다. 서버가 2대면 이미 못 막습니다. 게다가 @Transactional 안에서 락을 걸면 커밋 전에 락이 풀려 그 틈에 다른 요청이 옛 값을 읽습니다.

@Service
@RequiredArgsConstructor
public class OrderService {
    private final RedissonClient redisson;
    private final StockService stockService;      // ★ 별도 빈

    public void order(Long productId, int qty) {
        RLock lock = redisson.getLock("lock:stock:" + productId);
        boolean got = false;
        try {
            // 최대 3초 기다리고, 잡으면 자동 연장(watchdog)
            got = lock.tryLock(3, TimeUnit.SECONDS);
            if (!got) throw new BusyException("잠시 후 다시 시도해 주세요");

            stockService.decreaseInTx(productId, qty);   // 트랜잭션은 안쪽에

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (got && lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}
락 획득 → 트랜잭션 시작 → 커밋 → 락 해제 순서를 지키세요. @Transactional 메서드 안에서 락을 잡으면 커밋보다 락 해제가 먼저 일어나 그 사이에 다른 요청이 옛 값을 읽습니다. 위 코드처럼 락은 바깥, 트랜잭션은 안쪽 별도 빈이 정석입니다.

멱등성 — 두 번 눌러도 한 번만

대규모에서는 같은 요청이 두 번 오는 게 정상입니다. 그걸 전제로 설계하세요.

중복은 왜 생기나

  • 사용자가 결제 버튼을 두 번 눌렀다
  • 응답이 늦어 클라이언트가 타임아웃으로 재시도했다 (서버는 이미 처리 완료)
  • 게이트웨이·로드밸런서가 자동 재시도했다
  • Kafka 컨슈머가 리밸런싱으로 같은 메시지를 다시 받았다 (at-least-once)
  • 배치가 실패해 재실행됐다
“재시도하면 되지”가 곧 “중복 결제”입니다. 재시도 로직(k11)을 넣는 순간 멱등성은 선택이 아니라 필수 조건이 됩니다. 둘은 항상 같이 설계해야 합니다.

클라이언트가 요청마다 UUID 를 헤더에 담아 보냅니다.

서버

  2. 키가 이미 있고 완료 상태면 → 저장된 결과를 그대로 반환
  3. 키가 있고 처리 중이면 → 409 Conflict (또는 잠깐 대기)
@RestController
@RequiredArgsConstructor
class PaymentController {
    private final StringRedisTemplate redis;
    private final PaymentService service;

    @PostMapping("/api/payments")
    public ResponseEntity<?> pay(
            @RequestHeader("Idempotency-Key") String key,
            @RequestBody @Valid PayRequest req) {

        String k = "idem:pay:" + key;
        // 선점: 처음 온 요청만 true
        Boolean first = redis.opsForValue()
            .setIfAbsent(k, "PROCESSING", Duration.ofHours(24));

        if (!Boolean.TRUE.equals(first)) {
            String saved = redis.opsForValue().get(k);
            if ("PROCESSING".equals(saved))            // 아직 처리 중
                return ResponseEntity.status(409).body("처리 중입니다");
            return ResponseEntity.ok(read(saved));      // 저장된 결과 재사용
        }

        try {
            PayResult r = service.pay(req);
            redis.opsForValue().set(k, write(r), Duration.ofHours(24));
            return ResponseEntity.ok(r);
        } catch (Exception e) {
            redis.delete(k);                            // ★ 실패는 지워 재시도 허용
            throw e;
        }
    }
}

Kafka — 왜 큐를 넣는가

동기 호출을 줄이면 응답은 빨라지고 장애는 번지지 않습니다.

동기 호출의 한계

[동기] 주문 API 하나에 전부 매달린 경우
  주문 저장 120ms + 쿠폰 80ms + 포인트 90ms
  + 알림톡 300ms + 정산 150ms  =  740ms
  → 알림톡 업체가 죽으면 "주문 자체가" 실패한다

[비동기] 이벤트를 던지고 끝
  주문 저장 120ms + 발행 3ms  =  123ms
  쿠폰·포인트·알림·정산은 각자 구독해서 처리
  → 알림톡이 죽어도 주문은 정상, 복구되면 밀린 것부터 처리

Kafka 용어 — 이 다섯 개면 됩니다

용어뜻
토픽메시지가 쌓이는 이름 (예: order.created)
파티션토픽을 쪼갠 단위. 병렬 처리의 최소 단위이자 순서 보장의 범위
컨슈머 그룹같은 그룹은 일을 나눠 갖고, 다른 그룹은 같은 걸 각자 다 받습니다
오프셋어디까지 읽었는지 표시. 커밋해야 다음부터 안 읽습니다
키같은 키 = 같은 파티션 = 순서 보장. 주문번호·사용자ID 를 씁니다
컨슈머 수는 파티션 수를 넘을 수 없습니다. 파티션 3개에 컨슈머 5개를 띄우면 2개는 놉니다. 처리량을 늘리려면 파티션부터 늘려야 하고, 파티션은 줄일 수 없으니 넉넉히(예: 예상 컨슈머 수의 2배) 잡습니다.

Kafka 운영 — 유실 · 중복 · 순서

면접에서 가장 자주 파고드는 세 가지입니다. 보장 수준의 이름부터 외우세요.

전달 보장 세 가지

수준의미와 현실
at-most-once먼저 커밋하고 처리 → 유실 가능. 로그 수집 정도에만
at-least-once처리하고 커밋 → 중복 가능. 실무 기본값. 중복은 k07 멱등성으로 흡수합니다
exactly-once트랜잭션으로 정확히 한 번. Kafka 안에서만 성립하고 성능 대가가 큽니다. 외부 DB 까지는 보장 못 합니다
실무의 정답은 “at-least-once + 멱등 컨슈머”입니다. exactly-once 를 설정으로 사려 하지 말고, 중복이 와도 결과가 같게 만드는 쪽이 훨씬 싸고 튼튼합니다.

유실을 막는 설정

브로커
  min.insync.replicas = 2        # 최소 2대에 써져야 성공 처리
  replication.factor  = 3

프로듀서
  acks = all                     # 위 조건을 실제로 기다림
  enable.idempotence = true      # 재시도로 인한 중복 발행 방지

컨슈머
  enable.auto.commit = false     # ★ 처리 성공 후 수동 커밋
  ack-mode: manual

→ acks=1 이면 리더가 죽는 순간 그 메시지는 사라집니다.
→ auto-commit 은 "받자마자 커밋"이라 처리 중 죽으면 유실입니다.

재시도 · DLQ — 죽은 메시지 보관소

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
    // 3회 실패하면 order.created.DLT 토픽으로 보낸다
    var recoverer = new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", -1));

    var backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1000);
    backoff.setMultiplier(2.0);                     // 1s → 2s → 4s

    var handler = new DefaultErrorHandler(recoverer, backoff);
    // 재시도해도 소용없는 예외는 즉시 DLQ 로
    handler.addNotRetryableExceptions(
        IllegalArgumentException.class, JsonProcessingException.class);
    return handler;
}
DLQ 를 만들고 안 보면 없는 것과 같습니다. DLT 토픽의 메시지 수에 알람을 걸어 두세요. “조용해서 잘 돌아가는 줄 알았는데 3주치 정산이 DLQ 에 쌓여 있었다”는 실제로 자주 일어나는 사고입니다.

순서 · 리밸런싱 · 컨슈머 랙

  • 순서는 파티션 안에서만 보장됩니다. 순서가 중요한 단위(주문번호·계좌번호)를 키로 주면 같은 파티션으로 갑니다
  • 리밸런싱 — 컨슈머가 들어오고 나갈 때 파티션이 재배분되며 잠깐 멈춥니다. 처리가 max.poll.interval.ms 를 넘으면 쫓겨나 무한 리밸런싱에 빠집니다
  • 한 건이 오래 걸린다면 max-poll-records 를 줄이거나 무거운 일은 별도 스레드 풀로 넘기세요
  • 컨슈머 랙(lag) = 쌓인 양 − 읽은 양. 운영에서 제일 중요한 단일 지표입니다. 계속 커지면 소비가 생산을 못 따라가는 것 — 파티션·컨슈머를 늘립니다
Kafka 가 과한 경우도 많습니다. 단순한 작업 큐라면 Redis Stream·RabbitMQ·심지어 DB 테이블 큐로 충분합니다. Kafka 는 대용량·다중 구독·재처리가 필요할 때 값을 합니다. 운영 인력이 없다면 관리형(MSK·Confluent)을 쓰세요.

분산 트랜잭션 — 아웃박스와 사가

DB 커밋과 메시지 발행 사이에 서버가 죽으면? 그 틈이 실제로 사고가 됩니다.

이중 쓰기 문제 (Dual Write)

@Transactional
public void order(OrderRequest req) {
    orderRepository.save(order);        // ① DB 커밋
    kafka.send("order.created", event); // ② 메시지 발행
}

문제 1: ① 성공 후 ② 직전에 서버가 죽으면
        → 주문은 있는데 포인트·알림이 영원히 안 감

문제 2: ② 를 먼저 하면
        → 발행됐는데 ① 이 롤백 → 있지도 않은 주문의 이벤트가 돌아다님

문제 3: @Transactional 안에서 send() 를 해도
        → 커밋 전에 이미 나가서, 롤백돼도 되돌릴 수 없음
DB 와 메시지 브로커를 하나의 트랜잭션으로 묶을 수는 없습니다. (XA 2PC 는 가능하지만 느리고 잠기기 쉬워 현대 시스템에선 거의 안 씁니다.) 그래서 나온 게 아웃박스 패턴입니다.

아웃박스 패턴 — 같은 DB 에 같이 쓴다

create table outbox (
  id          bigint       primary key auto_increment,
  aggregate   varchar(50)  not null,     -- order
  event_type  varchar(50)  not null,     -- order.created
  payload     json         not null,
  created_at  timestamp    not null default now(),
  published_at timestamp   null          -- null 이면 아직 안 보냄
);
create index idx_outbox_pending on outbox (published_at, id);
// ① 업무 데이터와 이벤트를 "한 트랜잭션에" 저장 — 원자적
@Transactional

    outboxRepository.save(Outbox.of("order", "order.created", order));

// ② 별도 스케줄러가 안 보낸 것만 골라 발행
@Scheduled(fixedDelay = 1000)
@Transactional
public void relay() {
    for (var box : outboxRepository.findTop100Pending()) {

        box.markPublished();               // 더티 체킹으로 UPDATE
    }
}
발행이 두 번 될 수는 있습니다(보내고 표시 직전에 죽으면). 그래서 아웃박스 + 멱등 컨슈머(k07) 는 항상 한 세트입니다. 규모가 커지면 스케줄러 대신 Debezium(CDC) 으로 DB 로그를 읽어 자동 발행하게 바꿉니다.

사가(Saga) — 롤백 대신 보상

서비스가 나뉘면 롤백이 없습니다

주문 → 결제 → 재고 차감 → 배송 요청
                   ↑ 여기서 실패하면?

이미 끝난 "결제"를 DB 롤백으로 되돌릴 수 없습니다.
대신 반대 동작(보상 트랜잭션)을 실행합니다.

  재고 차감 실패
    → 결제 취소(환불) 이벤트 발행
    → 주문 상태를 CANCELLED 로

핵심: 모든 단계마다 "그것을 되돌리는 동작"이 짝으로 있어야 합니다.

코레오그래피

Redis + Lua — 원자적 토큰 버킷

// Lua 스크립트는 Redis 안에서 "한 덩어리로" 실행됩니다 (경쟁 조건 없음)
private static final String LUA = """
  local key      = KEYS[1]
  local capacity = tonumber(ARGV[1])   -- 버킷 크기
  local rate     = tonumber(ARGV[2])   -- 초당 채워지는 토큰
  local now      = tonumber(ARGV[3])

  local b = redis.call('HMGET', key, 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now

  tokens = math.min(capacity, tokens + (now - ts) * rate)   -- 시간만큼 리필
  local allowed = tokens >= 1
  if allowed then tokens = tokens - 1 end

  redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
  redis.call('EXPIRE', key, 120)
  return allowed and 1 or 0
""";

public boolean allow(String userId) {
    Long ok = redis.execute(RedisScript.of(LUA, Long.class),
        List.of("rate:" + userId),
        "60", "1", String.valueOf(System.currentTimeMillis() / 1000));
    return ok != null && ok == 1L;
}
// 인터셉터에서 걸고, 표준 헤더로 알려 준다
@Component
class RateLimitInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object h) {
        String key = userIdOr(req.getRemoteAddr());
        if (limiter.allow(key)) return true;

        res.setStatus(429);                             // Too Many Requests
        res.setHeader("Retry-After", "10");             // ★ 언제 다시 오라고 알려 주기
        res.setHeader("X-RateLimit-Limit", "60");
        return false;
    }
}
429 는 “거절”이 아니라 “안내”여야 합니다. Retry-After 를 주면 정상 클라이언트는 얌전히 기다립니다. 아무 안내 없이 막으면 즉시 재시도해서 부하가 더 늘어납니다.

    res.setHeader("Retry-After", String.valueOf(waitNanos / 1_000_000_000 + 1));
}

    .expireAfterAccess(Duration.ofMinutes(10))
    .build(k -> newBucket());

대용량 테이블의 흔한 함정

깊은 페이징 — 100만 페이지
select * from orders
 order by id desc
 limit 20 offset 1000000;

-- 뒤로 갈수록 선형으로 느려짐

select * from orders
 where id < :lastId          -- 직전 페이지 마지막 id
 order by id desc
 limit 20;
-- 인덱스로 바로 진입. offset 무관
-- COUNT 도 문제입니다: "전체 12,847,392건" 을 매번 세면 느립니다
-- ① 총 개수를 안 보여 주거나 (무한 스크롤)
-- ② "1000+" 처럼 근사치로 (limit 1001 로 세기)
-- ③ 통계 테이블에 주기적으로 저장

그 밖의 실무 규칙

  • 대량 업데이트는 쪼개서 — 한 번에 100만 건 UPDATE 는 락과 복제 지연을 만듭니다. 1,000건씩 나눠 커밋하세요
  • 파티셔닝 — 로그·주문처럼 기간으로 나뉘는 테이블은 월 단위 파티션이 효과적입니다. 오래된 파티션은 DROP 한 번으로 지웁니다 (DELETE 보다 압도적으로 빠름)
  • 인덱스는 공짜가 아닙니다 — 조회는 빨라지고 쓰기는 느려집니다. 안 쓰는 인덱스를 찾아 지우는 것도 튜닝입니다
  • 긴 트랜잭션 금지 — 트랜잭션 안에서 외부 API 를 호출하면 그동안 커넥션과 락을 붙잡고 있습니다 (🗄️ 데이터 탭 d14)
샤딩을 정말 해야 한다면 — 샤드 키를 바꿀 수 없다는 것부터 기억하세요. 키를 잘못 고르면 특정 샤드만 뜨거워지고(핫스팟), 샤드를 넘는 조인·트랜잭션은 애플리케이션이 직접 해야 합니다. 도입 전에 수직 분할·아카이빙으로 미룰 수 있는지 먼저 보세요.

  • ☐ 커넥션 풀 크기 × 서버 대수가 DB 최대 접속 수 안에 들어오는가
  • ☐ 캐시 TTL 에 랜덤을 섞었는가 (스탬피드 방지)
  • ☐ 재시도하는 API 는 멱등한가
  • ☐ 재고·포인트 차감이 원자적인가 (읽고→판단→쓰기 아닌가)
  • ☐ 컨슈머가 같은 메시지를 두 번 받아도 괜찮은가

  • ☐ readiness 프로브(/actuator/health/readiness)가 DB 상태까지 보는가 (liveness 에 DB 를 넣으면 안 됩니다)
