선언은 인터페이스, 생성은 ArrayDeque

import java.util.*;

public class Map01 {
    public static void main(String[] args) {
        Deque<Integer> stack = new ArrayDeque<>();   // 스택
        Queue<String>  queue = new ArrayDeque<>();   // 큐 (같은 클래스!)
        Deque<String>  deque = new ArrayDeque<>();   // 덱

        stack.push(1); stack.push(2);
        queue.offer("a"); queue.offer("b");
        deque.offerFirst("x"); deque.offerLast("y");

        System.out.println(stack.pop());     // 2
        System.out.println(queue.poll());    // a
        System.out.println(deque.pollLast()); // y
    }
}
왜 Queue 로 선언하나 — 큐로 쓸 변수를 Queue<E> 로 받으면 push·pollLast 같은 "큐답지 않은" 메서드가 자동완성에서 사라집니다. 타입으로 용도를 좁히는 것이 이 탭 전체의 습관입니다.

SQ 02

스택 — Stack 이 사장된 진짜 이유와 ArrayDeque 관용구

"Stack 은 synchronized 라서 느리다"가 흔한 설명이지만, 실제로 더 큰 이유는 설계입니다. Stack 은 Vector 를 상속한 탓에 스택이 아닌 일(중간 삽입·인덱스 수정)을 허락하고, 순회 순서가 바닥→꼭대기라 디버깅 출력부터 헷갈립니다. 실제 출력으로 확인합니다.

좌우 대조 — ArrayDeque 는 꺼낼 순서대로 보여 주고, Stack 은 쌓은 순서대로 보여 줍니다.

실제 출력으로 확인 — StackOrder.java

import java.util.*;

public class StackOrder {
    public static void main(String[] args) {
        Stack<Integer> legacy = new Stack<>();
        Deque<Integer> st = new ArrayDeque<>();
        for (int i = 1; i <= 3; i++) {   // 1, 2, 3 순서로 쌓는다
            legacy.push(i);
            st.push(i);
        }
        System.out.println(legacy.peek() + " " + st.peek()); // 3 3
        System.out.println(legacy);                    // [1, 2, 3]  바닥→꼭대기
        System.out.println(st);                        // [3, 2, 1]  꼭대기→바닥
        System.out.println(legacy.stream().toList());  // [1, 2, 3]
        System.out.println(st.stream().toList());      // [3, 2, 1]
        System.out.println(new ArrayList<>(legacy).getFirst()); // 1 (바닥)
        System.out.println(new ArrayList<>(st).getFirst());     // 3 (꼭대기)

        // Stack 은 List 이기도 해서 '중간'을 건드릴 수 있다
        legacy.add(0, 99);                  // 바닥 밑에 끼워 넣기
        legacy.set(2, -1);                  // 중간 값 바꾸기
        legacy.remove(Integer.valueOf(3));  // 꼭대기를 pop 없이 지우기
        System.out.println(legacy);              // [99, 1, -1]
        System.out.println(legacy.search(99));   // 3 (꼭대기에서 1부터 센 거리)
    }
}

SQ 03

큐(FIFO) — 예외형과 특수값형, 그리고 큐가 아닌 큐

Queue 인터페이스는 같은 일을 하는 메서드를 두 벌 가지고 있습니다. 실패를 예외로 알리는 add·remove·element 와, 특수값(false·null)으로 알리는 offer·poll·peek 입니다. 어느 쪽을 쓰느냐가 코드의 의도를 드러냅니다. 그리고 ArrayDeque 가 null 을 거부하는 이유도 바로 여기에 있습니다.

행렬 — 같은 동작이 네 가지 실패 방식으로 나뉩니다. 평소엔 offer · poll · peek.

두 벌의 차이 — QueueApi.java

import java.util.*;
import java.util.concurrent.*;

public class QueueApi {
    public static void main(String[] args) {
        Queue<String> q = new ArrayDeque<>();
        q.offer("A"); q.offer("B"); q.offer("C");
        System.out.println(q.peek());   // A
        System.out.println(q.poll());   // A
        System.out.println(q);          // [B, C]
        q.clear();
        System.out.println(q.poll());   // null — 비었음을 null 로 알림
        try { q.remove(); }
        catch (NoSuchElementException e) { System.out.println("remove -> NoSuchElementException"); }

        // 용량이 정해진 큐에서 add/offer 의 차이가 드러난다
        Queue<String> bounded = new ArrayBlockingQueue<>(2);
        System.out.println(bounded.offer("x"));  // true
        System.out.println(bounded.offer("y"));  // true
        System.out.println(bounded.offer("z"));  // false — 가득 참
        try { bounded.add("z"); }
        catch (IllegalStateException e) { System.out.println("add -> " + e.getMessage()); } // add -> Queue full
    }
}
ArrayDeque 는 용량 제한이 없어서 add 와 offer 의 차이가 보이지 않습니다. 용량 있는 큐로 바꿔 끼울 수도 있는 코드라면 처음부터 offer 를 쓰고 반환값을 확인하세요.

ArrayDeque 는 왜 null 을 거부하나

Queue<String> q = new ArrayDeque<>();
q.offer(null);                // NullPointerException — 넣는 순간 막는다

Queue<String> ll = new LinkedList<>();
ll.offer(null);               // LinkedList 는 받아 준다
System.out.println(ll.size() + " " + ll.poll()); // 1 null  ← 값이 null
System.out.println(ll.poll());                   // null    ← 비어서 null
// 두 null 을 구분할 방법이 없다!
poll()·peek() 의 null 은 "비었음"이라는 신호입니다. 원소로 null 을 허락하면 그 신호가 깨집니다. 그래서 ArrayDeque·PriorityQueue·모든 concurrent 큐는 null 을 넣는 순간 NPE 를 던집니다. 내부 구현도 "빈 칸 = null" 을 전제로 짜여 있습니다(SQ 04).
"값이 없음"을 넣어야 한다면 Optional<T> 를 원소로 하거나, 레코드 센티널(record Empty() implements Msg)을 만드세요.

덱의 속 — ArrayDeque 원형 배열을 JDK 25 소스로 뜯어 보기

ArrayDeque 는 배열 한 장 + 인덱스 두 개(head, tail)가 전부입니다. 원소를 옮기지 않고 인덱스만 돌리기 때문에 앞뒤 어느 쪽 연산도 O(1) 입니다. 아래 그림의 상태값은 상상이 아니라 JDK 25.0.1 에서 리플렉션으로 내부 필드를 직접 찍은 값입니다.

메모리 레이아웃 — tail 칸은 항상 비어 있습니다. 그 빈 칸이 "비었음"과 "꽉 참"을 구분하는 장치입니다.

JDK 25 소스 — addFirst · addLast 의 전부

// java.util.ArrayDeque (JDK 25) — 주석만 줄임
transient Object[] elements;  // 원소가 없는 칸은 항상 null
transient int head;           // 다음에 poll/pop 될 칸
transient int tail;           // 다음에 addLast 될 칸 (항상 null)

public void addFirst(E e) {
    if (e == null) throw new NullPointerException();
    final Object[] es = elements;
    es[head = dec(head, es.length)] = e;   // head 를 한 칸 뒤로(원형)
    if (head == tail) grow(1);             // 따라잡았으면 = 꽉 찼으면 키운다
}

public void addLast(E e) {
    if (e == null) throw new NullPointerException();
    final Object[] es = elements;
    es[tail] = e;
    if (head == (tail = inc(tail, es.length))) grow(1);
}

static final int inc(int i, int modulus) { if (++i >= modulus) i = 0; return i; }
static final int dec(int i, int modulus) { if (--i < 0) i = modulus - 1; return i; }

SQ 05

우선순위 큐 — PriorityQueue 는 정렬된 목록이 아니다

PriorityQueue 는 배열에 저장한 이진 최소 힙입니다. poll() 은 항상 가장 작은 것을 꺼내지만, 배열 자체는 정렬돼 있지 않습니다. 그래서 출력해 보면 엉뚱한 순서가 나오고, 원소를 넣은 뒤에 바꾸면 힙이 조용히 깨집니다. 힙 이론은 CS 가이드에 맡기고, 여기서는 자바 API 가 어떻게 동작하고 어디서 사고가 나는지만 봅니다.

배열 ↔ 트리 — 맨 앞(0번)만 확실히 최솟값입니다. 나머지 순서는 힙 규칙만 지킬 뿐 정렬이 아닙니다.

기본 사용 · 최대 힙 · 다중 키 — Pq.java

import java.util.*;

public class Pq {
    record Task(String name, int priority, long createdAt) {}

    public static void main(String[] args) {
        var min = new PriorityQueue<Integer>(List.of(5, 1, 4, 2, 3));
        System.out.println(min);              // [1, 2, 4, 5, 3]  ← 힙 배열 순서
        StringBuilder sb = new StringBuilder();
        while (!min.isEmpty()) sb.append(min.poll()).append(' ');
        System.out.println(sb.toString().trim()); // 1 2 3 4 5  ← poll 해야 정렬 순

        var max = new PriorityQueue<Integer>(Comparator.reverseOrder()); // 최대 힙
        max.addAll(List.of(5, 1, 4, 2, 3));
        System.out.println(max.poll() + " " + max.poll());   // 5 4

        var tasks = new PriorityQueue<Task>(
            Comparator.comparingInt(Task::priority)          // ① 우선순위 작은 것 먼저
                      .thenComparingLong(Task::createdAt));  // ② 같으면 먼저 온 것 먼저
        tasks.add(new Task("배포", 2, 30));
        tasks.add(new Task("장애", 1, 20));
        tasks.add(new Task("문서", 3, 10));
        tasks.add(new Task("보안패치", 1, 25));
        while (!tasks.isEmpty()) System.out.print(tasks.poll().name() + " ");
        System.out.println();   // 장애 보안패치 배포 문서
    }
}

같은 우선순위는 순서를 보장하지 않는다

PriorityQueue 는 안정(stable)하지 않습니다. 비교 결과가 0 인 두 원소는 넣은 순서와 관계없이 아무 순서로 나올 수 있습니다. "같은 우선순위면 먼저 온 것부터"가 필요하면 위처럼 두 번째 키(생성 시각·일련번호)를 비교자에 붙여야 합니다.

// 가장 큰 3개: 전체 정렬 O(n log n) 대신 O(n log k)
int[] data = {7, 42, 3, 19, 88, 5, 61, 23};
var heap = new PriorityQueue<Integer>();     // 최소 힙!
for (int x : data) {
    heap.offer(x);
    if (heap.size() > 3) heap.poll();        // 가장 작은 것을 버린다
}
List<Integer> top = new ArrayList<>(heap);
top.sort(Comparator.reverseOrder());

다익스트라 — 지연 삭제 관용구

record Edge(int to, int w) {}
record State(int node, long dist) {}

static long[] dijkstra(List<List<Edge>> g, int src) {
    long[] dist = new long[g.size()];
    Arrays.fill(dist, Long.MAX_VALUE);
    dist[src] = 0;
    var pq = new PriorityQueue<State>(Comparator.comparingLong(State::dist));
    pq.add(new State(src, 0));
    while (!pq.isEmpty()) {
        State s = pq.poll();
        if (s.dist() > dist[s.node()]) continue;   // 낡은 항목 → 건너뜀
        for (Edge e : g.get(s.node())) {
            long nd = s.dist() + e.w();
            if (nd < dist[e.to()]) {
                dist[e.to()] = nd;
                pq.add(new State(e.to(), nd));     // 고치지 않고 새로 넣는다
            }
        }
    }
    return dist;
}

// [0, 3, 1, 4] — 낡은 항목 2개는 건너뜀

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;

public class ProdCons {
    sealed interface Msg permits Order, Stop {}
    record Order(int id, long amount) implements Msg {}
    enum Stop implements Msg { PILL }         // 독약 — 싱글턴이면 충분

    public static void main(String[] args) throws Exception {
        final int PRODUCERS = 3, CONSUMERS = 4, PER_PRODUCER = 1_000;
        BlockingQueue<Msg> queue = new ArrayBlockingQueue<>(100); // ★ 유한
        LongAdder handled = new LongAdder(), total = new LongAdder();

        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int c = 0; c < CONSUMERS; c++) {
                exec.submit(() -> {
                    while (true) {
                        switch (queue.take()) {             // 비면 가상 스레드만 잠든다
                            case Stop s -> { return null; }   // 독약 → 종료
                            case Order(var _, long amount) -> {   // Java 22+ 이름 없는 패턴
                                total.add(amount); handled.increment();
                            }
                        }
                    }
                });
            }
            List<Future<?>> producers = new ArrayList<>();
            for (int p = 0; p < PRODUCERS; p++) {
                final int base = p * PER_PRODUCER;
                producers.add(exec.submit(() -> {
                    for (int i = 0; i < PER_PRODUCER; i++)
                        queue.put(new Order(base + i, 10));  // 꽉 차면 대기
                    return null;
                }));
            }
            for (Future<?> f : producers) f.get();              // ① 생산 완료 확인
            for (int c = 0; c < CONSUMERS; c++) queue.put(Stop.PILL); // ② 소비자 수만큼
        }   // ③ close() 가 모든 가상 스레드 종료를 기다린다

        System.out.println("처리 " + handled.sum() + "건 · 합계 " + total.sum());
        // 처리 3000건 · 합계 30000
        System.out.println("남은 것 " + queue.size());   // 남은 것 0
    }
}

작업 큐 하나가 스레드 풀 동작을 바꾼다 — ThreadPoolExecutor 실측 🔴 고급

막대 — 무한 큐를 쓰면 maximumPoolSize 는 장식입니다. 큐 종류가 풀의 성격을 정합니다.

실측 코드 — PoolQueue.java

import java.util.concurrent.*;

public class PoolQueue {
    static void run(String name, BlockingQueue<Runnable> q) throws Exception {
        var pool = new ThreadPoolExecutor(2, 10, 30, TimeUnit.SECONDS, q,
                new ThreadPoolExecutor.CallerRunsPolicy());
        var latch = new CountDownLatch(1);       // 작업이 안 끝나게 붙잡아 둔다
        for (int i = 0; i < 50; i++) {
            pool.execute(() -> {
                try { latch.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
            // 다음 작업이 CallerRuns 로 main 을 막기 전에 멈춘다
            if (pool.getPoolSize() == 10 && q.remainingCapacity() == 0) break;
        }
        System.out.printf("%-24s 스레드 %2d개 · 대기 %2d개%n", name, pool.getPoolSize(), q.size());
        latch.countDown();
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
    public static void main(String[] args) throws Exception {
        run("LinkedBlockingQueue()", new LinkedBlockingQueue<>());
        run("ArrayBlockingQueue(20)", new ArrayBlockingQueue<>(20));
        run("SynchronousQueue", new SynchronousQueue<>());
    }
}
// LinkedBlockingQueue()    스레드  2개 · 대기 48개
// ArrayBlockingQueue(20)   스레드 10개 · 대기 20개
// SynchronousQueue         스레드 10개 · 대기  0개

SQ 07

비동기 · 스트림 — 버퍼에 상한을 두는 큐들

비동기 코드에서도 큐는 사라지지 않습니다. 이름이 버퍼로 바뀔 뿐입니다. 빠른 생산자와 느린 소비자 사이에는 반드시 어딘가에 쌓이는 곳이 생기고, 그 크기를 정하지 않으면 메모리가 정합니다(OOM). JDK 표준 Flow API, Reactor 의 Sinks, Spring 의 작업 큐를 차례로 봅니다.

파이프라인 — 비동기 버퍼도 결국 유한 큐입니다. 가득 찼을 때 멈출지, 버릴지를 먼저 정해야 합니다.

JDK 만으로 — Pub.java (의존성 0)

import java.util.concurrent.*;

public class Pub {
    public static void main(String[] args) throws Exception {
        try (var pub = new SubmissionPublisher<Integer>(
                Executors.newVirtualThreadPerTaskExecutor(), 4)) {  // 버퍼 상한 4
            var done = new CountDownLatch(1);
            pub.subscribe(new Flow.Subscriber<>() {
                Flow.Subscription sub; int sum;
                public void onSubscribe(Flow.Subscription s) { sub = s; s.request(1); }
                public void onNext(Integer v) {
                    try { Thread.sleep(5); } catch (InterruptedException e) { }  // 느린 소비자
                    sum += v;
                    sub.request(1);                    // 하나 처리했으니 하나 더
                }
                public void onError(Throwable t) { t.printStackTrace(); }
                public void onComplete() { System.out.println("합계 " + sum); done.countDown(); }
            });
            int dropped = 0;
            for (int i = 1; i <= 20; i++) {
                // 반환값이 음수면 '버려진 개수'
                int lag = pub.offer(i, (s, v) -> false);   // false = 다시 시도하지 말고 버려라
                if (lag < 0) dropped++;
            }
            System.out.println("버린 것 > 0 : " + (dropped > 0));  // 버린 것 > 0 : true
            pub.close();       // 남은 버퍼를 다 보낸 뒤 onComplete
            done.await();      // 합계 10 (실행마다 달라질 수 있음 — 무엇이 버려졌는지에 따라)
        }
    }
}

알고리즘 패턴 — 자바다운 코드로 쓰는 여섯 가지

코딩 테스트와 실무에서 스택·큐·덱이 나오는 패턴은 거의 정해져 있습니다. 개념 설명은 CS 가이드에 있으니 여기서는 자바에서 어떤 타입·메서드로 쓰는 게 관용구인지, 그리고 자주 틀리는 한 줄에 집중합니다. 모든 결과는 실제 실행값입니다.

단계별 상태 — 덱의 앞이 곧 답입니다. 뒤에서는 "앞으로 답이 될 수 없는 것"을, 앞에서는 "창 밖"을 버립니다.

① 괄호 검사 — Deque<Character> 스택

static boolean balanced(String s) {
    Deque<Character> st = new ArrayDeque<>();
    for (char ch : s.toCharArray()) {
        switch (ch) {
            case '(', '[', '{' -> st.push(ch);
            case ')', ']', '}' -> {
                if (st.isEmpty()) return false;          // 닫는 게 먼저 옴
                char open = st.pop();
                if ("([{".indexOf(open) != ")]}".indexOf(ch)) return false;
            }
            default -> { }
        }
    }
    return st.isEmpty();                                 // 안 닫힌 게 남음
}
// balanced("{[()()]}") true · balanced("([)]") false · balanced("((") false

static int[] nextGreater(int[] a) {
    int[] ans = new int[a.length];
    Arrays.fill(ans, -1);
    Deque<Integer> st = new ArrayDeque<>();   // ★ 값이 아니라 '인덱스'를 담는다
    for (int i = 0; i < a.length; i++) {
        while (!st.isEmpty() && a[st.peek()] < a[i])
            ans[st.pop()] = a[i];              // 기다리던 것들의 답이 나왔다
        st.push(i);
    }
    return ans;
}

③ BFS — Deque<int[]> 큐, 넣을 때 방문 표시

static int shortest(char[][] g, int sr, int sc, int tr, int tc) {
    int R = g.length, C = g[0].length;
    int[][] dist = new int[R][C];
    for (int[] row : dist) Arrays.fill(row, -1);
    Deque<int[]> q = new ArrayDeque<>();
    q.offer(new int[]{sr, sc});
    dist[sr][sc] = 0;
    int[][] dirs = {{1,0},{-1,0},{0,1},{0,-1}};
    while (!q.isEmpty()) {
        int[] cur = q.poll();
        for (int[] d : dirs) {
            int r = cur[0] + d[0], c = cur[1] + d[1];
            if (r < 0 || c < 0 || r >= R || c >= C) continue;
            if (g[r][c] == '#' || dist[r][c] != -1) continue;
            dist[r][c] = dist[cur[0]][cur[1]] + 1;   // ★ 넣을 때 표시
            q.offer(new int[]{r, c});
        }
    }
    return dist[tr][tc];
}
// "S..#" / ".#.." / "...T" 에서 S→T = 5
꺼낼 때 방문 표시를 하면 같은 칸이 큐에 여러 번 들어가 큐가 폭발합니다. 답은 맞게 나와서 더 위험합니다. 좌표를 record Pos(int r, int c) 로 담아도 되지만, 수백만 칸이면 int[] 나 r * C + c 정수 하나가 가볍습니다.

static int[] windowMax(int[] a, int k) {
    int[] out = new int[a.length - k + 1];
    Deque<Integer> dq = new ArrayDeque<>();       // 인덱스. 값은 앞→뒤 감소
    for (int i = 0; i < a.length; i++) {
        if (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();     // 창 밖
        while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) dq.pollLast();  // 가망 없음
        dq.offerLast(i);
        if (i >= k - 1) out[i - k + 1] = a[dq.peekFirst()];
    }
    return out;
}
// windowMax({1, 3, -1, -3, 5, 3, 6, 7}, 3) → [3, 3, 5, 5, 6, 7]
// 데이터가 작고 한 번만 볼 거라면 Java 24+ Gatherers 도 됩니다 (O(n·k))

⑤ 0-1 BFS — 비용 0 은 앞에, 1 은 뒤에

static int zeroOneBfs(List<List<int[]>> adj, int src, int dst) {
    int[] dist = new int[adj.size()];
    Arrays.fill(dist, Integer.MAX_VALUE);
    dist[src] = 0;
    Deque<Integer> dq = new ArrayDeque<>();
    dq.offerFirst(src);
    while (!dq.isEmpty()) {
        int u = dq.pollFirst();
        for (int[] e : adj.get(u)) {
            int v = e[0], w = e[1];
            if (dist[u] + w < dist[v]) {
                dist[v] = dist[u] + w;
                if (w == 0) dq.offerFirst(v);   // 덱이라서 가능한 한 줄
                else        dq.offerLast(v);
            }
        }
    }
    return dist[dst];
}
// 0→1(1) 0→2(0) 2→1(0) 1→3(1) 2→3(1) 이면 0→3 = 1
간선 비용이 0/1 뿐이면 다익스트라의 PriorityQueue(O(log n)) 대신 덱의 양끝(O(1))으로 같은 답을 냅니다. "벽 부수기 횟수 최소" 같은 격자 문제가 이 모양입니다.

⑥ undo / redo — 스택 두 개

public class Editor {
    interface Command { void apply(StringBuilder d); void revert(StringBuilder d); }
    record Append(String text) implements Command {
        public void apply(StringBuilder d)  { d.append(text); }
        public void revert(StringBuilder d) { d.setLength(d.length() - text.length()); }
    }
    static final int LIMIT = 100;
    final StringBuilder doc = new StringBuilder();
    final Deque<Command> undo = new ArrayDeque<>();
    final Deque<Command> redo = new ArrayDeque<>();

    void exec(Command c) {
        c.apply(doc);
        undo.push(c);
        if (undo.size() > LIMIT) undo.removeLast();  // 가장 오래된 기록(바닥) 버리기
        redo.clear();                                // 새 작업 → redo 갈래 소멸
    }
    void undo() { Command c = undo.poll(); if (c != null) { c.revert(doc); redo.push(c); } }
    void redo() { Command c = redo.poll(); if (c != null) { c.apply(doc);  undo.push(c); } }
}
// exec "Hello", ", ", "World" → undo → "Hello, " → undo → "Hello"
// → redo → "Hello, " → exec "Java" → "Hello, Java" → redo 해도 그대로
Stack 으로는 이 한 줄이 어색합니다 — 바닥을 버리는 removeLast(). 덱이라서 "깊이 제한 있는 스택"이 자연스럽게 됩니다.

성능과 메모리 — 박싱, 노드, 그리고 믿을 수 없는 벤치마크

"ArrayDeque 가 LinkedList 보다 빠르다"는 맞습니다. 그런데 얼마나, 왜인지는 측정해야 압니다. 이 섹션의 수치는 이 PC(12 스레드)·JDK 25·단일 스레드에서 간이 측정한 예시입니다(JMH 아님). 크기보다 순서와 이유를 보세요.

막대 — 단일 스레드 큐는 ArrayDeque 가 압도적입니다. 같은 O(1) 이라도 노드 할당·락·CAS 가 상수를 몇 배로 만듭니다.

측정 코드 — Bench2.java (요지)

// 큐 정상 상태: 1,000개가 든 큐에서 offer 1 + poll 1 을 2천만 번
static final Integer[] VALS = new Integer[1024];
static { for (int i = 0; i < 1024; i++) VALS[i] = 100_000 + i; } // 박싱은 미리

static long time(Queue<Integer> q) {
    long best = Long.MAX_VALUE;
    for (int round = 0; round < 7; round++) {          // 앞 2회는 워밍업
        q.clear();
        for (int i = 0; i < 1000; i++) q.offer(VALS[i & 1023]);
        long t = System.nanoTime(), x = 0;
        for (int i = 0; i < 20_000_000; i++) { q.offer(VALS[i & 1023]); x += q.poll(); }
        long e = System.nanoTime() - t;
        sink += x;                                     // 죽은 코드 제거 방지
        if (round >= 2) best = Math.min(best, e);
    }
    return best / 1_000_000;
}

원시 타입 스택 — 수백만 개면 직접 만든다

/** int 전용 스택 — 박싱 없음, 원소당 4바이트 */
public final class IntStack {
    private int[] a = new int[16];
    private int size;

    public void push(int v) {
        if (size == a.length) a = java.util.Arrays.copyOf(a, size * 2);
        a[size++] = v;
    }
    public int pop() {
        if (size == 0) throw new java.util.NoSuchElementException();
        return a[--size];
    }
    public int peek() {
        if (size == 0) throw new java.util.NoSuchElementException();
        return a[size - 1];
    }
    public boolean isEmpty() { return size == 0; }
    public int size() { return size; }
}

실무 코드에서 스택·큐는 "자료구조 문제"가 아니라 작은 부품으로 나옵니다. 여섯 가지 자주 쓰는 모양을, 각각 어떤 타입을 왜 고르는지와 함께 돌아가는 코드로 정리합니다. 모든 출력은 실제 실행값입니다.

① 최근 N개 보관 — 크기 고정 덱

import java.util.*;

/** 최근 N개 — 넘치면 가장 오래된 것을 버린다. 스레드 안전 */
final class Recent<T> {
    private final int cap;
    private final ArrayDeque<T> buf;

    Recent(int cap) { this.cap = cap; this.buf = new ArrayDeque<>(cap); }

    synchronized void add(T t) {
        if (buf.size() == cap) buf.pollFirst();   // 가장 오래된 것 버리기
        buf.addLast(t);
    }
    synchronized List<T> newestFirst() {
        return List.copyOf(buf.reversed());      // Java 21 — 복사해서 내보내기
    }
}

// var r = new Recent<String>(3);
// for (String s : List.of("a", "b", "c", "d", "e")) r.add(s);
// r.newestFirst() → [e, d, c]
내부 덱을 그대로 반환하지 마세요. 받은 쪽이 순회하는 동안 다른 스레드가 add 하면 SQ 10 ③ 이 일어납니다. List.copyOf 로 스냅숏을 넘기면 락 밖에서 안전하게 읽힙니다. 최근 에러 100건, 최근 요청 지연 1,000개(백분위 계산용)에 그대로 씁니다.

BlockingQueue<Event> buf = new ArrayBlockingQueue<>(10_000);

// 배치 쓰기 — 가상 스레드 하나
void writerLoop() throws InterruptedException {
    List<Event> batch = new ArrayList<>(500);
    while (running) {
        Event first = buf.poll(1, TimeUnit.SECONDS);   // 최대 1초 대기
        if (first == null) continue;
        batch.add(first);

offer + 버림 카운터는 "로그·지표처럼 잃어도 되는 것"에, put(대기) 은 "주문처럼 잃으면 안 되는 것"에 씁니다. drainTo 는 원소를 하나씩 poll 하는 것보다 락을 덜 잡습니다.

③ 슬라이딩 윈도우 레이트 리미터 — 타임스탬프 덱 🟡 중급

타임라인 — 덱의 앞은 가장 오래된 기록, 뒤는 가장 최근입니다. 그래서 양끝만 쓰는 ArrayDeque 가 딱 맞습니다.
import java.util.*;
import java.util.concurrent.*;

final class SlidingWindowLimiter {
    private final int limit;
    private final long windowNanos;
    private final ArrayDeque<Long> hits = new ArrayDeque<>();

    SlidingWindowLimiter(int limit, long windowMillis) {
        this.limit = limit;
        this.windowNanos = windowMillis * 1_000_000;
    }

    synchronized boolean tryAcquire(long now) {        // now = System.nanoTime()
        while (!hits.isEmpty() && now - hits.peekFirst() >= windowNanos)
            hits.pollFirst();                          // 창 밖 기록 제거
        if (hits.size() >= limit) return false;        // 거절 — 기록하지 않음
        hits.addLast(now);
        return true;
    }
}

// 키(사용자·IP)별로
final ConcurrentHashMap<String, SlidingWindowLimiter> limiters = new ConcurrentHashMap<>();
boolean allow(String key) {
    return limiters.computeIfAbsent(key, k -> new SlidingWindowLimiter(3, 1000))
                   .tryAcquire(System.nanoTime());
}
// 0,100,200,300,900,1050,1150,1250ms 에 호출 → OOOXXOOO

④ 재시도 큐 — DelayQueue 와 지수 백오프 🟡 중급

순환 — 재시도는 실행 → 지연 → 대기 → 실행의 반복이고, 빠져나가는 길은 성공과 횟수 초과 둘뿐입니다.
import java.util.concurrent.*;

record Retry(String job, int attempt, long readyAt) implements Delayed {
    public long getDelay(TimeUnit u) {
        return u.convert(readyAt - System.nanoTime(), TimeUnit.NANOSECONDS);
    }
    public int compareTo(Delayed o) {
        return Long.compare(readyAt, ((Retry) o).readyAt);
    }
    static Retry after(String job, int attempt, long millis) {
        return new Retry(job, attempt, System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(millis));
    }
    static long backoffMillis(int attempt) {          // 100, 200, 400, 800 ... 최대 30초
        return Math.min(30_000, 100L << Math.min(attempt, 20));
    }
}

var dq = new DelayQueue<Retry>();
dq.put(Retry.after("메일", 2, 200));
dq.put(Retry.after("결제", 1, 50));
System.out.println(dq.poll());          // null — 아직 시각이 안 됨
System.out.println(dq.take().job());    // 결제 (약 50ms 뒤)
System.out.println(dq.take().job());    // 메일 (약 200ms 뒤)
선택지언제
DelayQueue + 워커재시도 대상이 큐 형태로 모일 때, 꺼내는 쪽을 직접 제어할 때
ScheduledExecutorService.schedule작업 하나하나를 "n 초 뒤에 실행"으로 던질 때 — 내부도 지연 힙 큐
Spring Retry · Resilience4j Retry메서드 호출 단위 재시도. 대기 중 스레드를 붙잡는지 확인
메시지 브로커의 지연 큐 · DLQ재시작해도 재시도가 살아남아야 할 때 (메모리 큐는 사라짐)
DelayQueue 는 메모리 안에만 있습니다. 프로세스가 죽으면 기다리던 재시도가 모두 사라집니다. 결제처럼 잃으면 안 되는 재시도는 DB 테이블(다음 실행 시각 컬럼)이나 브로커에 두고, DelayQueue 는 "잃어도 다시 생기는" 일에 쓰세요. 백오프에 무작위 흔들림(jitter)을 더하면 여러 인스턴스가 동시에 재시도하는 몰림을 막을 수 있습니다.

⑤ 재귀를 명시적 스택으로 — StackOverflowError 피하기 🔴 고급

import java.util.*;

public class Deep {
    static final class Node {
        final int val; final List<Node> children = new ArrayList<>();
        Node(int v) { val = v; }
    }

    static long sumRec(Node n) {               // 깊이만큼 호출 프레임이 쌓인다
        long s = n.val;
        for (Node c : n.children) s += sumRec(c);
        return s;
    }

    static long sumIter(Node root) {           // 프레임 대신 힙의 덱에 쌓는다
        long s = 0;
        Deque<Node> st = new ArrayDeque<>();
        st.push(root);
        while (!st.isEmpty()) {
            Node n = st.pop();
            s += n.val;
            for (Node c : n.children.reversed()) st.push(c);  // 거꾸로 넣어야 왼쪽부터
        }
        return s;
    }

    public static void main(String[] args) {
        Node root = new Node(1), cur = root;      // 깊이 1,000,000 짜리 한 줄 트리
        for (int i = 2; i <= 1_000_000; i++) { Node n = new Node(1); cur.children.add(n); cur = n; }

        try { System.out.println(sumRec(root)); }
        catch (StackOverflowError e) { System.out.println("재귀: StackOverflowError"); }
        System.out.println("반복: " + sumIter(root));
    }
}
// 재귀: StackOverflowError
// 반복: 1000000

언제 바꾸나 · 무엇을 조심하나

상황판단
균형 트리 · 깊이 수십재귀 그대로. 읽기 쉬운 쪽이 이깁니다
사용자가 만든 트리 (조직도 · 댓글 · JSON)명시적 스택. 깊이를 내가 정할 수 없습니다
그래프 DFS · 연결 리스트 모양명시적 스택 — 깊이 = 노드 수가 될 수 있음
-Xss 로 스택 늘리기임시방편. 스레드마다 늘어나고, 입력이 더 커지면 또 터짐
후위 순회(자식 먼저)상태 플래그를 같이 넣거나 스택 두 개 — 전위보다 까다롭습니다
방문 순서를 재귀와 똑같이 맞추려면 자식을 거꾸로 push 해야 합니다(스택은 마지막에 넣은 것이 먼저 나오니까). Java 21 의 children.reversed() 뷰가 인덱스 루프를 대신합니다. 작은 트리로 두 결과가 [1, 2, 4, 5, 3] 으로 같은지 확인했습니다.
가상 스레드도 스택 깊이 한계가 있습니다. 깊은 재귀는 가상 스레드에서도 StackOverflowError 입니다.
