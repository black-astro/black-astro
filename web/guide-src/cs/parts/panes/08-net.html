NET 01

OSI 7계층 · TCP/IP — 문제를 층으로 나누기

계층 모델의 진짜 가치는 암기가 아니라 문제 위치를 좁히는 도구라는 데 있습니다. “안 된다”는 신고를 받았을 때 어느 층인지부터 정하면 절반이 끝납니다.

L7 응용
HTTP · gRPC · DNS · TLS진단: curl -v · 브라우저 개발자 도구 · 앱 로그
▼ 캡슐화 (헤더가 하나씩 붙는다)
L4 전송
TCP · UDP · QUIC진단: ss · telnet · nc · 재전송률
▼
L3 네트워크
IP · ICMP · 라우팅진단: ping · traceroute · ip route
▼
L2 데이터링크
이더넷 · MAC · ARP · 스위치진단: ip neigh · arping
▼
L1 물리
케이블 · 광 · 무선진단: ethtool · 링크 상태 · 에러 카운터

캡슐화 — 헤더가 겹겹이

애플리케이션 데이터
  [HTTP 헤더][본문]
      ↓ TCP 가 감싼다
  [TCP 헤더][HTTP 헤더][본문]        ← 세그먼트
      ↓ IP 가 감싼다
  [IP 헤더][TCP 헤더][...]           ← 패킷
      ↓ 이더넷이 감싼다
  [이더넷 헤더][IP 헤더][...][FCS]    ← 프레임

받는 쪽은 반대로 하나씩 벗긴다

오버헤드
  이더넷 14B + IP 20B + TCP 20B = 54B
  MTU 1500B 기준 → 실제 데이터 최대 1460B (MSS)
  → 작은 요청이 많으면 헤더 비중이 커진다

“안 된다”를 층으로 가르기

  1. 물리 · 링크 — ip link 로 UP 인지, ethtool 로 에러가 있는지
  2. 네트워크(L3) — ping 이 가나? 라우팅 테이블이 맞나?
  3. 전송(L4) — nc -zv host port 로 포트가 열려 있나?
  4. 이름 — dig 로 DNS 가 맞게 나오나?
  5. 보안 — 방화벽 · 보안 그룹 · SELinux
  6. 응용(L7) — curl -v 로 응답이 오나? 상태 코드는?
순서가 핵심입니다 — 아래층이 안 되는데 위층을 봐야 시간만 갑니다. 반대로 ping 은 되는데 포트가 안 열린다면 L3 는 정상이고 L4/방화벽 문제로 즉시 좁혀집니다.

MTU 문제 — 계층이 새는 대표 사례

  MTU 1500 인 구간을 지나야 하는데
  VPN·터널이 헤더를 추가해 실제 여유가 1400 이라면

  · 작은 요청은 잘 된다
  · 큰 응답에서만 멈춘다 ★ "가끔 안 된다" 의 원인
  · Path MTU Discovery 가 ICMP 로 알려 주는데
    방화벽이 ICMP 를 막으면 → 블랙홀

확인
  ping -M do -s 1472 target        # 1472 + 28 = 1500
  ip link show                      # MTU 값
  tracepath target                  # 경로상 MTU
“ICMP 는 위험하니 다 막자”가 만드는 사고입니다 — Path MTU Discovery 가 ICMP 를 쓰기 때문에 전면 차단하면 큰 패킷만 조용히 사라집니다. 최소한 fragmentation-needed 타입은 허용해야 합니다.

실무에선 이렇게 — 한 번의 요청에서 벌어지는 일 🔴 실무

브라우저에 주소를 치면

  1. DNS 조회 — 캐시 → 리졸버 → 루트 → TLD → 권한 서버 (07절)
  2. TCP 연결 — 3-way 핸드셰이크 (1 RTT) (04절)
  3. TLS 핸드셰이크 — 인증서 검증 · 키 교환 (1~2 RTT) (09절)
  4. HTTP 요청 · 응답 — 서버 처리 시간 + 1 RTT (08절)
  5. 렌더링 — HTML 파싱 · 추가 리소스 요청 (반복)
# 각 단계의 시간을 직접 재기
curl -w '
  DNS 조회       %{time_namelookup}s
  TCP 연결       %{time_connect}s
  TLS 핸드셰이크  %{time_appconnect}s
  첫 바이트까지   %{time_starttransfer}s
  전체           %{time_total}s
' -o /dev/null -s https://example.com

# 출력 예 (서울에서 미국 서버)
#   DNS 조회       0.025s
#   TCP 연결       0.180s     ← 1 RTT
#   TLS 핸드셰이크  0.520s     ← 2 RTT 더
#   첫 바이트까지   0.720s     ← 서버 처리 + 1 RTT
#   전체           0.850s

# ★ 실제 콘텐츠 전송보다 '왕복'이 대부분을 차지한다 → 12절
이 curl -w 한 줄이 성능 진단의 시작점입니다 — 느린 원인이 DNS 인지 · 연결인지 · 서버 처리인지가 즉시 갈립니다. 대시보드에도 이 분해를 넣어 두면 좋습니다.

서브넷 마스크는 “어디까지가 같은 동네인가”를 정합니다. 아래 계산기에 CIDR 을 넣어 보면 범위와 호스트 수가 바로 나옵니다.

NET 03

이더넷 · ARP — 같은 동네 안에서는 MAC 으로

IP 는 “최종 목적지”이고 MAC 은 “다음 한 홉”입니다. 이 구분을 알면 같은 서브넷 안에서만 안 되는 문제를 바로 좁힐 수 있습니다.

패킷이 실제로 가는 길

내 PC(192.168.0.5) → 8.8.8.8 로 보낼 때

 ① 목적지가 내 서브넷 안인가?
    192.168.0.0/24 안이 아니다 → 게이트웨이로 보낸다
 ② 게이트웨이(192.168.0.1)의 MAC 주소를 안다?
    모르면 ARP 로 물어본다 — "192.168.0.1 누구세요?" (브로드캐스트)
 ③ 게이트웨이가 응답 — "저요, MAC 은 aa:bb:cc:dd:ee:ff"
 ④ 프레임을 만든다
    [목적지 MAC = 게이트웨이][출발 MAC = 내 것][IP 헤더: 8.8.8.8][...]
 ⑤ 게이트웨이가 받아서 다음 홉의 MAC 으로 갈아 끼우고 전달

★ IP 는 끝까지 그대로, MAC 은 홉마다 바뀐다

확인 명령

ip addr                 # 내 IP · MAC
ip route                # 라우팅 테이블 (기본 게이트웨이)
ip neigh                # ARP 캐시 ★
#  192.168.0.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE

arping -I eth0 192.168.0.1     # 특정 IP 의 MAC 확인
ip neigh flush all             # ARP 캐시 비우기

# 스위치 포트 · 링크 상태
ethtool eth0            # Speed · Duplex · Link detected
ip -s link show eth0    # 에러 · 드롭 카운터

# 프레임을 직접 보기
sudo tcpdump -i eth0 -n arp
ip neigh 에 FAILED 나 INCOMPLETE 가 보이면 L2 문제입니다 — 상대가 꺼져 있거나, VLAN 이 다르거나, 스위치 포트 설정이 잘못된 것입니다.

ethtool eth0 | grep -E "Speed|Duplex|Link"

NET 04

TCP — 신뢰성을 만드는 방법

IP 는 “보내기만” 합니다 — 순서도 도착도 보장하지 않습니다. 그 위에 확인 응답과 재전송을 얹어 신뢰성을 만든 것이 TCP 이고, 그 대가가 왕복 시간입니다.

TLS 까지 하면 추가로 1~2 RTT — 서울-미국이면 그것만으로 300~450ms 입니다.

TCP 가 보장하는 것

TCP 가 보장하지 않는 것 — 애플리케이션이 처리했다는 보장입니다. send() 가 성공해도 상대 앱이 읽기 전에 죽으면 사라집니다. 그래서 애플리케이션 레벨 ACK 가 필요합니다 → 🕸️ 분산 13.

연결 종료와 TIME_WAIT

4-way 핸드셰이크
  A → FIN      "나는 다 보냈다"
  B → ACK
  B → FIN      "나도 다 보냈다"
  A → ACK      → A 는 TIME_WAIT 로 (2×MSL, 보통 60초)

왜 TIME_WAIT 이 필요한가
 ① 마지막 ACK 가 유실되면 상대가 FIN 을 재전송 → 응답해야 함
 ② 옛 연결의 지연된 패킷이 새 연결에 섞이는 것 방지

문제
 · 클라이언트가 많은 연결을 짧게 열고 닫으면 TIME_WAIT 이 쌓임
 · 로컬 포트 고갈 (기본 약 28,000개)

대응
 · ★ Keep-Alive 로 연결 재사용 (가장 좋은 답)
 · 커넥션 풀 사용
 · net.ipv4.tcp_tw_reuse=1 (클라이언트 측)
 · 포트 범위 확대: net.ipv4.ip_local_port_range

TIME_WAIT 을 정확히 이해하기

왜 60초나 남아 있나?

  ① 늦게 도착한 패킷이 '같은 포트를 쓰는 다음 연결'에
     섞여 들어가는 것을 막기 위해
  ② 마지막 ACK 가 유실되면 상대가 FIN 을 재전송하는데,
     그때 응답해 줄 누군가가 남아 있어야 하기 때문

즉 버그가 아니라 '정확성을 위한 설계'입니다.

문제가 되는 경우
  · 서버가 먼저 끊는 구조 → TIME_WAIT 이 서버에 쌓임
  · 아웃바운드 연결이 많음 → 로컬 포트 고갈

해결 순서
  ① keepalive 로 연결 재사용 (근본)
  ② net.ipv4.tcp_tw_reuse = 1 (아웃바운드에 안전)
  ③ 포트 범위 확대 ip_local_port_range
  ✗ tcp_tw_recycle — NAT 환경을 깨뜨려 커널에서 제거됐습니다
연결 수 한계 = 포트 범위 ÷ TIME_WAIT 시간 포트 28,000개 ÷ 60초 = 초당 약 466 연결
범위를 55,000개로 넓히면 초당 약 916 연결

그 이상이 필요하면 연결을 재사용하는 수밖에 없습니다 — 이것이 HTTP keepalive · 커넥션 풀이 존재하는 이유입니다
“누가 먼저 끊는가”를 설계로 정하세요. 클라이언트가 먼저 끊게 하면 TIME_WAIT 이 클라이언트에 흩어져 서버에는 부담이 없습니다. HTTP 에서 서버가 Connection: close 를 보내면 반대가 됩니다 — 서버 쪽 keepalive 를 켜 두는 것이 이 문제를 함께 해결합니다.

흐름 제어 · 혼잡 제어 — 얼마나 빨리 보낼까

받는 쪽이 감당할 만큼(흐름 제어), 그리고 길이 막히지 않을 만큼(혼잡 제어) 속도를 조절합니다. 대역폭이 충분한데도 느린 이유가 대개 여기 있습니다.

두 개의 윈도우

실제 전송량 = min(수신 윈도우, 혼잡 윈도우)
흐름 제어혼잡 제어
보호 대상수신자네트워크
신호수신 윈도우 광고패킷 손실 · 지연
제어 주체수신자가 알려 줌송신자가 추정
혼잡 제어의 기본 흐름 (Reno 계열)

  슬로우 스타트: 1 → 2 → 4 → 8 ... (RTT 마다 2배)
       ↓ 임계값 도달
  혼잡 회피:    1씩 증가 (선형)
       ↓ 손실 감지
  빠른 회복:    윈도우를 절반으로 → 다시 선형 증가

★ 슬로우 스타트가 '느리게 시작' 이라는 뜻이다
  → 짧은 연결은 최대 속도에 도달하기 전에 끝난다
  → 연결 재사용이 중요한 이유

대역폭 지연 곱 (BDP)

BDP = 대역폭 × RTT “전송 중인 데이터”가 얼마나 될 수 있는가 = 필요한 윈도우 크기 
1Gbps · RTT 100ms (서울-미국)
  BDP = 1,000,000,000 / 8 × 0.1 = 12.5 MB

★ 윈도우가 12.5MB 보다 작으면
  대역폭이 1Gbps 여도 그만큼 못 쓴다

  윈도우 64KB 라면 최대 처리량
   = 65536 / 0.1 = 655 KB/s ≈ 5 Mbps    ← 1Gbps 회선인데!

 · ★ 근본적으로: CDN 으로 RTT 를 줄인다

# 게임 서버의 전형적인 패턴 — 신뢰성을 선택적으로
#
# 신뢰 필요 없음 (매 틱 갱신)      → 그냥 UDP, 최신 것만 쓰기
#   플레이어 위치 · 회전
# 신뢰 필요 (놓치면 안 됨)         → 직접 ACK/재전송 구현
#   아이템 획득 · 채팅 · 상태 변경
# 순서 필요 (신뢰는 불필요)        → 시퀀스 번호로 오래된 것 버리기

import struct, time

HEADER = struct.Struct("!IIB")     # seq, ack, flags

class Channel:
    def __init__(self):
        self.seq = 0
        self.pending = {}          # seq -> (payload, sent_at)

    def send_reliable(self, sock, addr, payload):
        self.seq += 1
        pkt = HEADER.pack(self.seq, 0, 1) + payload
        sock.sendto(pkt, addr)
        self.pending[self.seq] = (pkt, time.monotonic())

    def tick(self, sock, addr, rto=0.2):
        now = time.monotonic()
        for seq, (pkt, sent) in list(self.pending.items()):
            if now - sent > rto:
                sock.sendto(pkt, addr)          # 재전송
                self.pending[seq] = (pkt, now)

    def on_ack(self, seq):
        self.pending.pop(seq, None)

TLS 핸드셰이크 — 상대가 진짜인지 확인하고 열쇠 만들기

HTTPS 의 s 가 하는 일을 단계별로 봅니다. 인증서 오류를 해석하고 왜 이렇게 여러 왕복이 필요한지를 알면 성능과 보안 판단을 함께 할 수 있습니다.

TLS 1.3 핸드셰이크 (1 RTT)

  1. ClientHello — 지원하는 암호 목록 + 키 공유 후보 + SNI(어느 도메인인지)
  2. ServerHello — 고른 암호 + 서버 키 공유 + 인증서 + 서명
  3. 클라이언트 검증 — 인증서 체인 · 유효기간 · 도메인 일치 · 폐기 여부
  4. 양쪽이 같은 세션 키 를 계산 (디피-헬만) — 키 자체는 오간 적이 없음
  5. Finished — 이후 모든 데이터는 대칭키로 암호화
TLS 1.2 는 2 RTT, 1.3 은 1 RTT 입니다. 재연결 시 0-RTT 도 가능하지만 재전송 공격 위험이 있어 멱등한 요청에만 써야 합니다.

직접 보기

# 전체 핸드셰이크 과정
openssl s_client -connect example.com:443 -servername example.com

# 인증서 정보만
echo | openssl s_client -connect example.com:443 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# 체인 확인
openssl s_client -connect example.com:443 -showcerts

# 지원 프로토콜 확인
for v in tls1_2 tls1_3; do
  echo -n "$v: "
  echo | openssl s_client -$v -connect example.com:443 >/dev/null 2>&1 \
    && echo OK || echo NO
done

# 만료일 감시 (모니터링에 넣을 것)
echo | openssl s_client -connect example.com:443 2>/dev/null \
  | openssl x509 -noout -enddate

소켓 · 포트 — 커널이 만든 두 개의 대기 줄

listen() 뒤에는 SYN 큐와 accept 큐 두 개가 있습니다. 연결이 간헐적으로 거절되거나 지연되는 문제의 원인이 대개 이 큐들입니다.

서버 소켓의 흐름

socket()  → 소켓 생성
bind()    → 주소·포트 할당
listen(backlog) → 두 개의 큐 생성
  · SYN 큐    (반쯤 열린 연결) — 핸드셰이크 진행 중
  · accept 큐 (완성된 연결)    — accept() 를 기다림
accept()  → accept 큐에서 하나 꺼내 연결 소켓 반환

★ 앱이 accept 를 충분히 빨리 안 하면
  accept 큐가 차고 → 새 연결이 버려진다 (또는 SYN 을 무시)
  → 클라이언트는 타임아웃 · 연결 거부를 겪는다

크기 결정
  accept 큐 = min(listen 의 backlog, net.core.somaxconn)

확인과 튜닝

# 리슨 소켓의 큐 상태
ss -lnt
# State  Recv-Q  Send-Q  Local Address:Port
# LISTEN 0       511     0.0.0.0:80
#        ↑        ↑
#   현재 대기 중  backlog 크기
# Recv-Q 가 계속 0 이 아니면 accept 가 밀리고 있다

# 넘침 카운터

#   nginx: listen 80 backlog=4096;
#   gunicorn: --backlog 2048
큐를 늘리는 것은 임시방편입니다 — 근본 원인은 앱이 요청을 충분히 빨리 처리 못 하는 것입니다. 큐만 늘리면 대기 시간이 길어질 뿐이고, 타임아웃된 요청을 처리하느라 자원을 낭비하게 됩니다.

실무에선 이렇게 — SYN 플러드와 방어 🔴 실무

SYN 플러드 공격
  · 위조한 출발지로 SYN 만 대량 전송
  · 서버는 SYN 큐에 항목을 만들고 SYN-ACK 를 보내고 대기
  · 큐가 차면 정상 연결도 못 받는다

방어: SYN 쿠키
  · SYN 큐를 쓰지 않고, 필요한 정보를 시퀀스 번호에 인코딩
  · ACK 가 오면 그 번호로 상태를 복원
  · 상태를 저장하지 않으므로 큐가 차지 않는다

  sysctl net.ipv4.tcp_syncookies=1     # 기본 활성

한계
  · 일부 TCP 옵션(윈도우 스케일 등)이 손실될 수 있다
  · 큐가 찼을 때만 발동하므로 평상시에는 영향 없음

# 출발지 IP 분포 (정상 트래픽이면 다양하다)

#  ① 앞단에 CDN/DDoS 방어 (Cloudflare · AWS Shield)
#  ② 레이트 리밋 (nginx limit_req · iptables)
#  ③ SYN 쿠키 확인
#  ④ 큐 크기 조정
#  ★ 서버 하나로 대규모 공격을 막을 수는 없다
대부분의 DDoS 방어는 앞단에서 합니다 — 대역폭을 채우는 공격은 서버에 도착하기 전에 막아야 하기 때문입니다. 서버 설정은 소규모 공격과 오작동 클라이언트에 대한 방어선입니다.

“호출 그래프의 깊이”가 지연을 결정합니다 — 넓게(병렬) 부르는 것은 괜찮지만 깊게(순차) 부르면 RTT 가 곱해집니다. 마이크로서비스 설계에서 호출 사슬을 3단계 이하로 유지하는 것이 일반적인 지침입니다.

# 데드라인 전파 — 남은 예산 안에서만 호출
import time, asyncio

class Deadline:
    def __init__(self, budget_s): self.end = time.monotonic() + budget_s
    def remaining(self): return max(0.0, self.end - time.monotonic())

async def handler(dl: Deadline):
    if dl.remaining() < 0.02:
        return cached_fallback()               # 시간이 없으면 즉시 폴백
    try:
        return await asyncio.wait_for(call_api(), timeout=dl.remaining())
    except asyncio.TimeoutError:
        return cached_fallback()

네트워크 진단 — 명령 순서

“접속이 안 된다”는 신고를 받았을 때 아래에서 위로 올라가며 확인합니다. 각 단계에서 성공하면 그 아래층은 정상입니다.

단계별 확인

  1. 이름이 풀리나 — dig +short example.com
  2. IP 에 도달하나 — ping -c 3 1.2.3.4 (ICMP 차단 가능성 유의)
  3. 경로는 어디까지 — mtr -n -c 20 1.2.3.4
  4. 포트가 열렸나 — nc -zv 1.2.3.4 443
  5. TLS 가 되나 — openssl s_client -connect 1.2.3.4:443
  6. 응답이 오나 — curl -v https://example.com
  7. 어디가 느린가 — curl -w 로 단계별 시간 (01절)
  8. 패킷을 직접 — tcpdump · Wireshark
2번에서 실패해도 포기하지 마세요 — 많은 서버가 ICMP 를 막습니다. ping 이 안 돼도 포트는 열릴 수 있으니 4번을 반드시 해 보세요.
