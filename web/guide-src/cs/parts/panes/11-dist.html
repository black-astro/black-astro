동시성 vs 병렬성 — 다른 문제입니다

동시성은 여러 일을 번갈아 잘 다루는 것이고, 병렬성은 진짜 동시에 하는 것입니다. 해결책과 병목이 완전히 다릅니다.

경쟁 상태 · 원자성 — count += 1 은 세 단계입니다

한 줄처럼 보이는 연산이 사실 읽기 · 계산 · 쓰기 세 단계입니다. 그 사이에 다른 스레드가 끼어들면 값이 사라집니다. 재현이 안 되는 버그의 대표적인 원인입니다.

겹치는 구간이 아주 짧아 대부분의 실행에서는 문제가 안 보입니다 — 그래서 위험합니다.

직접 재현해 보기

import threading

counter = 0
def worker():
    global counter
    for _ in range(100_000):
        counter += 1          # ★ 원자적이지 않다

ts = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
print(counter)                # 400000 이 아니다 (실행마다 다름)

# ✓ 락으로
lock = threading.Lock()
def worker_safe():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

# ✓ 더 나은 방법: 각자 세고 마지막에 합친다 (경합 제거)
def worker_local(results, idx):
    local = 0
    for _ in range(100_000): local += 1
    results[idx] = local
# → 락이 아예 필요 없다

DIST 03

메모리 모델 — 내가 쓴 값을 상대가 못 볼 수 있습니다

락 없이 변수를 공유하면 값이 안 보이거나 순서가 뒤집혀 보일 수 있습니다. 컴파일러와 CPU 가 단일 스레드 기준으로 최적화하기 때문입니다.

가시성 문제

// ✗ 영원히 안 끝날 수 있다
class Worker {
    boolean running = true;          // volatile 없음

    void run() {
        while (running) { /* 일 */ }  // 컴파일러가 레지스터에 캐시
    }                                 // → 다른 스레드의 변경을 못 봄
    void stop() { running = false; }
}

// ✓ volatile — 항상 메모리에서 읽고 쓴다
volatile boolean running = true;

// ✓ 또는 원자 타입
AtomicBoolean running = new AtomicBoolean(true);
이 버그는 최적화 수준과 CPU 에 따라 나타납니다 — 디버그 빌드나 x86 에서는 우연히 동작하다가 릴리즈 빌드나 ARM 에서 멈춥니다. “맥북에서만 안 된다”의 원인이 되기도 합니다.

재정렬 문제

스레드 A            스레드 B
  data = 42;          if (ready)
  ready = true;           use(data);

★ 컴파일러나 CPU 가 A 의 두 줄 순서를 바꿀 수 있다
  (단일 스레드 관점에서는 결과가 같으므로 허용된다)
  → B 가 ready=true 를 보고 data 는 아직 0 일 수 있다

메모리 순서 강도
  x86 : 비교적 강함 (스토어-로드 재정렬만)
  ARM : 약함 — 더 많은 재정렬 허용
  → ★ x86 에서 잘 되던 코드가 ARM 에서 깨지는 이유
Apple Silicon 도입 이후 실제로 많이 드러난 문제입니다. 해결은 적절한 동기화 원시(락 · 원자 연산 · 채널)를 쓰는 것이고, 그러면 언어가 순서를 보장해 줍니다.

이렇게도 쓸 수 있다 — happens-before 와 메모리 순서 🟡 중급

happens-before 관계가 성립하면 가시성이 보장된다

자바에서 happens-before 를 만드는 것들
  · 같은 스레드의 프로그램 순서
  · 락 해제 → 이후의 같은 락 획득
  · volatile 쓰기 → 이후의 같은 volatile 읽기
  · Thread.start() → 그 스레드의 첫 동작
  · 그 스레드의 마지막 동작 → join() 반환
  · 동시성 컬렉션 · CountDownLatch 등의 연산

★ 즉 "락을 제대로 쓰면 재정렬을 걱정할 필요가 없다"
  락 없이 공유하려 할 때만 이 이론이 필요해진다
// Rust · C++ 의 메모리 순서 (약한 것부터)
use std::sync::atomic::Ordering;

Ordering::Relaxed  // 원자성만 보장 · 순서 보장 없음 (카운터)
Ordering::Acquire  // 이 읽기 이후의 연산이 앞으로 못 옴 (락 획득)
Ordering::Release  // 이 쓰기 이전의 연산이 뒤로 못 감 (락 해제)
Ordering::AcqRel   // 둘 다 (읽고-수정하고-쓰기)
Ordering::SeqCst   // 전역 순서 보장 · 가장 강하고 가장 느림 ★ 기본 선택

// 전형적인 Release/Acquire 쌍
// 생산자
data.store(42, Ordering::Relaxed);
ready.store(true, Ordering::Release);     // 이 앞의 쓰기가 모두 보인다

// 소비자
if ready.load(Ordering::Acquire) {        // 이 뒤의 읽기가 뒤로 안 밀린다
    assert_eq!(data.load(Ordering::Relaxed), 42);   // 보장됨
}
확신이 없으면 SeqCst 를 쓰세요 — 약한 순서로 성능을 얻는 것은 측정으로 필요성이 증명된 뒤에만 의미가 있고, 틀렸을 때 재현이 거의 불가능합니다.

DIST 04

락 프리 · CAS — “바뀌지 않았으면 바꿔라”

락 없이 동기화하는 핵심 도구가 Compare-And-Swap 입니다. 빠르지만 함정이 많고 구현이 어렵습니다 — 왜 그런지, 언제 락이 더 나은지를 봅니다.

CAS 의 원리

CAS(주소, 기대값, 새값)
  if (*주소 == 기대값) { *주소 = 새값; return true; }
  else                 { return false; }

ABA 문제

스레드 A: old = X 를 읽음
스레드 B: X → Y → X 로 두 번 바꿈
스레드 A: CAS 성공! (값은 X 로 같으니까)
          ★ 그런데 그 사이에 상태가 달라졌다

포인터를 다루는 락프리 스택에서 특히 위험
  · A 가 노드를 읽음
  · B 가 그 노드를 꺼내 해제하고, 같은 주소에 새 노드 할당
  · A 의 CAS 가 성공 → 해제된 메모리를 참조

해결
  · 태그된 포인터 (값 + 버전 카운터를 함께 CAS)
  · 해저드 포인터 · epoch 기반 회수
  · GC 언어에서는 메모리 재사용이 없어 덜 심각하다

// ✗ 채널을 읽는 사람이 없으면 영원히 블로킹
func leak() {
    ch := make(chan int)          // 버퍼 없음
    go func() { ch <- 1 }()       // 아무도 안 읽으면 이 고루틴은 영원히 남는다
}

// ✓ context 로 취소 가능하게
func noLeak(ctx context.Context) {
    ch := make(chan int, 1)       // 버퍼를 두거나
    go func() {
        select {
        case ch <- compute():
        case <-ctx.Done():        // 취소되면 빠져나온다
        }
    }()
}

CAP 정리 · PACELC — 자주 오해되는 정리

“일관성과 가용성 중 하나를 고르라”가 아닙니다. 정확히는 “망이 갈라졌을 때 무엇을 포기할지 정하라”이고, 평소에는 다른 선택(PACELC)이 더 중요합니다.

정확한 진술

네트워크 분단(P)이 일어났을 때, 일관성(C) 과 가용성(A) 을 동시에 만족할 수 없다 
분단이 일어났을 때의 선택

이렇게도 쓸 수 있다 — 쿼럼 — R + W > N 🟡 중급

N 개의 복제본, 쓰기에 W 개 응답, 읽기에 R 개 조회

  R + W > N  이면 읽기와 쓰기 집합이 반드시 겹친다
  → 최신 값을 최소 하나는 읽게 된다

예 (N=3)
  W=3, R=1 → 쓰기 느림 · 읽기 빠름 · 쓰기 가용성 낮음
  W=2, R=2 → ★ 균형 (한 노드 장애 허용)
  W=1, R=1 → 둘 다 빠름 · 일관성 없음 (최종 일관성)
  W=1, R=3 → 쓰기 빠름 · 읽기 느림

★ 주의: 쿼럼만으로 선형화가 보장되지는 않는다
  · 동시 쓰기 충돌 · 부분 실패 · 롤백 없음
  · 진짜 선형화가 필요하면 합의 프로토콜 (09절)

DIST 09

합의 — 여러 대가 같은 값에 동의하는 법

리더 선출 · 분산 락 · 설정 저장이 전부 합의 위에 있습니다. Raft 를 직접 구현할 일은 없어도, 왜 느리고 무엇을 보장하는지는 알아야 잘 쓸 수 있습니다.

Raft 의 세 요소

  1. 리더 선출 — 임기(term)마다 하나의 리더. 하트비트가 끊기면 후보가 되어 투표를 요청하고, 과반 득표로 리더가 됩니다.
  2. 로그 복제 — 모든 쓰기는 리더를 거칩니다. 리더가 팔로워에게 로그를 보내고 과반이 기록하면 커밋합니다.
  3. 안전성 — 커밋된 항목은 절대 사라지지 않고 순서가 바뀌지 않습니다.
노드 상태
  Follower  → 타임아웃 → Candidate → 과반 득표 → Leader
                              ↓ 실패
                          다시 Follower

★ 무작위 선거 타임아웃으로 동시 후보를 줄인다
★ 쓰기 한 번에 최소 1 RTT × (리더 → 과반 팔로워)
  → 지연이 있는 다중 리전에서는 비싸다

분산 락은 생각보다 위험하다

  ① 클라이언트 A 가 락을 얻는다 (TTL 30초)
  ② A 가 GC 정지나 네트워크 지연으로 40초간 멈춘다
  ③ TTL 만료 → B 가 락을 얻는다
  ④ A 가 깨어나서 "나는 락을 갖고 있다" 며 작업을 계속한다
  ★ 두 클라이언트가 동시에 임계 구역에 있다

해결: 펜싱 토큰
  · 락을 줄 때마다 증가하는 번호를 함께 준다
  · 자원(스토리지)이 그 번호를 확인해 오래된 것을 거부한다
    A: 토큰 33 으로 쓰기 → 성공
    B: 토큰 34 로 쓰기   → 성공 (저장소가 34 를 기억)
    A: 토큰 33 으로 쓰기 → ★ 거부

★ 자원 쪽이 토큰을 검사해 주지 않으면 완전한 해결이 안 된다
# Redis 단일 인스턴스 락 (Redlock 은 논쟁이 있으니 신중히)
import uuid, redis

def acquire(r, key, ttl_ms=30000):
    token = str(uuid.uuid4())
    ok = r.set(key, token, nx=True, px=ttl_ms)      # 원자적
    return token if ok else None

RELEASE = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""   # ★ 내 토큰일 때만 해제 (남의 락을 지우면 안 된다)

def release(r, key, token):
    r.eval(RELEASE, 1, key, token)

# ★ 더 중요한 질문: 락이 정말 필요한가?
#   · 효율 목적(중복 작업 방지)이면 → 가끔 중복돼도 괜찮게 설계
#   · 정확성 목적(중복이 치명적)이면 → 락이 아니라 DB 제약·멱등성으로
“정확성을 위한 분산 락”은 거의 항상 잘못된 선택입니다 — DB 유니크 제약 · 조건부 UPDATE · 멱등성 키가 훨씬 단순하고 확실합니다. 락은 “중복 작업을 줄이면 좋겠다” 수준의 효율 목적에만 쓰세요.

분산 트랜잭션 — “다 되거나 다 안 되게”

여러 서비스에 걸친 작업을 원자적으로 만드는 문제입니다. 2PC 는 이론적으로 맞지만 실무에서는 위험하고, 대부분 사가 패턴으로 풉니다.

2단계 커밋 (2PC)

1단계 — 준비
  코디네이터 → 모든 참여자: "커밋할 수 있나?"
  참여자 → "예" (이 시점부터 자원을 잠근 채 대기)

2단계 — 커밋
  코디네이터 → 모든 참여자: "커밋해"
  참여자 → 커밋 완료

★ 치명적 문제
  · 코디네이터가 1단계 뒤에 죽으면
    참여자들은 락을 쥔 채 영원히 대기 (블로킹)
  · 참여자 하나가 느리면 전체가 대기
  · 가용성이 모든 참여자의 곱이 된다
    99% × 99% × 99% = 97%

→ 그래서 마이크로서비스에서는 거의 안 쓴다

사가 패턴

긴 트랜잭션을 여러 로컬 트랜잭션으로 쪼개고
실패하면 ★ 보상 트랜잭션으로 되돌린다

  주문 생성  → 결제 승인  → 재고 차감  → 배송 요청
     ↓ 실패      ↓ 실패       ↓ 실패
  주문 취소  ← 결제 취소  ← 재고 복구

두 가지 방식
  오케스트레이션 — 중앙 조정자가 순서를 관리
    + 흐름이 한눈에 보임 · 디버깅 쉬움
    - 조정자가 단일 지점

  코레오그래피 — 각 서비스가 이벤트를 듣고 반응
    + 결합도 낮음
    - 전체 흐름을 파악하기 어려움
사가는 격리성이 없습니다 — 중간 상태가 다른 트랜잭션에 보입니다. “결제는 됐는데 재고는 아직”인 상태를 사용자와 다른 서비스가 볼 수 있다는 전제로 설계해야 합니다.

문제: DB 저장과 이벤트 발행을 원자적으로 할 수 없다

  db.save(order)          ← 성공
  kafka.publish(event)    ← 실패!  → 이벤트가 유실된다

  순서를 바꿔도 마찬가지 (이벤트만 나가고 저장 실패)

해결: 아웃박스 테이블
  ① 같은 DB 트랜잭션 안에서 데이터와 이벤트를 함께 저장
  ② 별도 프로세스가 아웃박스를 읽어 메시지 브로커로 발행
  ③ 발행 성공하면 아웃박스에서 삭제(또는 표시)

  → 원자성이 DB 트랜잭션 하나로 보장된다
  → 최소 한 번 전달 (중복 가능 → 소비자가 멱등해야 함)
CREATE TABLE outbox (
  id          BIGSERIAL PRIMARY KEY,
  aggregate   TEXT NOT NULL,
  event_type  TEXT NOT NULL,
  payload     JSONB NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT now(),
  published_at TIMESTAMPTZ
);
CREATE INDEX ON outbox (published_at) WHERE published_at IS NULL;

-- 애플리케이션
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (aggregate, event_type, payload)
       VALUES ('order', 'OrderCreated', '{"id":123}');
COMMIT;   -- ★ 둘 다 되거나 둘 다 안 된다

-- 발행 워커 (여러 대여도 안전하게)
BEGIN;
  SELECT * FROM outbox
   WHERE published_at IS NULL
   ORDER BY id LIMIT 100
     FOR UPDATE SKIP LOCKED;     -- ★ 다른 워커와 겹치지 않는다
  -- 발행 후
  UPDATE outbox SET published_at = now() WHERE id = ANY(...);
COMMIT;
FOR UPDATE SKIP LOCKED 가 큐 구현의 핵심입니다 — 여러 워커가 같은 행을 잡지 않고 각자 다른 행을 가져갑니다. DB 를 간단한 작업 큐로 쓸 때도 같은 패턴을 씁니다.

# 스노우플레이크 직접 구현
class Snowflake:
    EPOCH = 1700000000000        # 기준 시각 (ms)
    def __init__(self, node_id):
        self.node = node_id & 0x3FF        # 10비트
        self.seq = 0
        self.last = -1
    def next_id(self):
        now = int(time.time() * 1000)
        if now < self.last:                 # ★ 시계가 뒤로 갔다
            raise RuntimeError("클럭 역행 — ID 발급 중단")
        if now == self.last:
            self.seq = (self.seq + 1) & 0xFFF        # 12비트
            if self.seq == 0:
                while now <= self.last: now = int(time.time()*1000)
        else:
            self.seq = 0
        self.last = now
        return ((now - self.EPOCH) << 22) | (self.node << 12) | self.seq
정렬 가능한 ID 를 쓰면 B+트리 인덱스가 훨씬 효율적입니다 — 순차 삽입이 되어 페이지 분할과 랜덤 I/O 가 줄어듭니다 (🗂️ 자료구조 08). 새 프로젝트라면 UUID v7 또는 ULID 를 기본으로 두세요.

import random, time

def retry(fn, attempts=5, base=0.1, cap=10.0):
    for i in range(attempts):
        try:
            return fn()
        except RetryableError as e:
            if i == attempts - 1: raise
            # ★ full jitter — 동시 재시도를 흩뜨린다
            delay = random.uniform(0, min(cap, base * (2 ** i)))
            time.sleep(delay)

import time, threading

class CircuitBreaker:
    """closed(정상) → open(차단) → half-open(탐색) → closed"""
    def __init__(self, threshold=5, timeout=30, half_open_max=3):
        self.threshold, self.timeout = threshold, timeout
        self.half_open_max = half_open_max
        self.failures = 0
        self.state = "closed"
        self.opened_at = 0
        self.half_open_calls = 0
        self.lock = threading.Lock()

    def call(self, fn, fallback=None):
        with self.lock:
            if self.state == "open":
                if time.monotonic() - self.opened_at < self.timeout:
                    if fallback: return fallback()
                    raise CircuitOpenError()
                self.state, self.half_open_calls = "half-open", 0
            if self.state == "half-open" and self.half_open_calls >= self.half_open_max:
                if fallback: return fallback()
                raise CircuitOpenError()
            if self.state == "half-open": self.half_open_calls += 1

        try:
            result = fn()
        except Exception:
            with self.lock:
                self.failures += 1
                if self.failures >= self.threshold:
                    self.state, self.opened_at = "open", time.monotonic()
            raise
        else:
            with self.lock:
                self.failures, self.state = 0, "closed"
            return result

Raft 를 단계별로 — 리더 선출 · 로그 복제 · 안전성

09 절에서 “합의가 왜 필요한가”를 봤다면, 여기서는 실제로 어떻게 도는지를 봅니다. etcd · Consul · TiKV · CockroachDB 가 전부 Raft 로 돌고, 쿠버네티스의 상태도 그 위에 얹혀 있습니다. Paxos 보다 이해하기 쉽게 설계된 것이 Raft 의 목표였고, 그 설계를 따라가 봅니다.

합의(consensus) — 여러 서버가 같은 값의 같은 순서에 동의하는 것. 과반(quorum)이 살아 있으면 동작하고, 과반이 깨지면 멈춥니다(틀린 답을 내지 않습니다). 5대 클러스터는 2대까지, 3대 클러스터는 1대까지 장애를 견딥니다 — f 대를 견디려면 2f+1 대가 필요합니다.
과반이 반드시 겹친다는 성질 하나가 Raft 안전성의 뿌리입니다 — 두 과반은 최소 한 서버를 공유합니다.

로그 복제 — 쓰기 하나가 커밋되기까지

쓰기 지연 = 과반 중 가장 느린 서버까지의 왕복 + 디스크 fsync — 이 식이 Raft 기반 시스템 성능의 상한입니다.

  ① 마지막 항목의 임기가 더 크면 더 최신
  ② 임기가 같으면 로그가 더 길수록 더 최신

  → 커밋된 항목은 반드시 과반에 있고,
    당선되려면 과반의 표가 필요하므로,
    새 리더는 커밋된 항목을 '반드시' 갖고 있습니다.

  이것이 "커밋된 것은 절대 사라지지 않는다" 의 증명입니다.
가장 미묘한 규칙은 네 번째입니다. 새 리더가 이전 임기의 항목을 과반에 복제했다고 해서 곧바로 커밋으로 셀 수는 없습니다 — 그 상태에서 리더가 죽으면 뒤집힐 수 있는 시나리오가 존재합니다. 그래서 Raft 는 자기 임기의 항목이 하나 커밋될 때 이전 것들을 함께 커밋합니다. 논문에서 가장 많이 오해되는 부분이고, 실제 구현 버그도 여기서 자주 나옵니다.
