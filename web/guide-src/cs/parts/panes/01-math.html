        out.append(x); out.append(y)
    return out

# 반례를 한 줄만 찾으면 이 주장은 끝난다

# 올바른 병합: 매 순간 '더 작은 쪽'을 고른다
def merge(a, b):
    i = j = 0; out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]: out.append(a[i]); i += 1
        else:            out.append(b[j]); j += 1
    return out + a[i:] + b[j:]

명제논리 · 진리표 — 조건문 버그의 절반이 여기서 납니다

if (!(a && b)) 를 if (!a && !b) 로 바꿔 쓴 적이 있다면, 그건 오타가 아니라 드모르간 법칙을 틀린 것입니다. 진리표는 그런 실수를 기계적으로 잡아 주는 도구입니다.

기본 연산 네 개

이름기호코드참이 되는 때
부정¬p!pp 가 거짓일 때
논리곱p ∧ qp && q둘 다 참
논리합p ∨ qp || q하나라도 참
함의p → q!p || qp 가 참인데 q 가 거짓일 때만 거짓
함의가 가장 헷갈립니다 — “비가 오면 우산을 쓴다”는 명제는 비가 안 오는 날에는 무조건 참입니다. 우산을 썼든 안 썼든 상관없습니다. 이 성질이 계약·검증 조건에서 자주 함정이 됩니다.

진리표 — 모든 경우를 나열해 확인

p   q  │ p∧q  p∨q  p→q  p⊕q(XOR)
───────┼──────────────────────────
T   T  │  T    T    T     F
T   F  │  F    T    F     T
F   T  │  F    T    T     T
F   F  │  F    F    T     F

변수가 n 개면 행은 2ⁿ 개.
변수 3개면 8줄이라 손으로 다 적을 수 있다.
실전 사용법 — 조건문이 의심스러우면 변수 2~3개짜리 진리표를 그려 기대값 열을 하나 더 만들어 비교하세요. 5분이면 끝나고, 확실합니다.

이렇게도 쓸 수 있다 — 드모르간 · 조건문 뒤집기 🟡 중급

드모르간 법칙

¬(p ∧ q) ≡ ¬p ∨ ¬q
¬(p ∨ q) ≡ ¬p ∧ ¬q 부정을 안으로 넣으면 ∧ 와 ∨ 가 뒤집힌다 — 이 한 줄이 전부입니다.
✗ 자주 하는 실수
// "유효하지 않은 사용자"
if (!(isActive && hasEmail)) { ... }
// 를 이렇게 바꿔 쓴다 ↓ (틀림)
if (!isActive && !hasEmail) { ... }
✓ 드모르간 적용
if (!isActive || !hasEmail) { ... }
// ∧ 이 ∨ 로 바뀐다는 것이 핵심

단락 평가 — 순서가 의미를 바꾼다

// && 는 왼쪽이 거짓이면 오른쪽을 아예 실행하지 않는다
if (user && user.name.length > 0) { }   // 안전
if (user.name.length > 0 && user) { }   // user 가 null 이면 터짐

// 논리적으로 p∧q ≡ q∧p 지만, 코드에서는 다르다.
// 수학의 교환법칙은 '부수효과가 없을 때'만 성립한다.

// 이 성질을 의도적으로 쓰는 관용구
const name = user && user.name;        // 가드
const port = env.PORT || 3000;         // 기본값
const port2 = env.PORT ?? 3000;        // 0 도 허용하려면 ??
|| 와 ?? 의 차이 — || 는 0 · "" · false 도 “없는 것”으로 봅니다. 0 이 유효한 값이면 반드시 ?? 를 쓰세요. 타임아웃·수량 설정에서 자주 사고가 납니다.

실무에선 이렇게 — 복잡한 조건을 줄이는 법 🔴 실무

조건문 정리 4단계

  1. 이름을 붙인다 — if (a > 3 && b !== null && !c) 대신 const canPublish = .... 조건에 이름이 붙는 순간 리뷰가 가능해집니다.
  2. 부정을 밖으로 뺀다 — 드모르간으로 ! 를 최상위 하나로 모읍니다.
  3. 조기 반환으로 평탄화 — 중첩 if 를 가드 절로 바꾸면 진리표를 그릴 필요 자체가 줄어듭니다.
  4. 진리표로 검증 — 그래도 3변수 이상이면 표를 그려 기대값과 대조합니다.
✗ 읽을 수 없는 조건
if (!(u.age >= 19 && u.verified) ||
    (u.banned && !u.appealed)) {
  deny();
}
✓ 이름 + 드모르간
const isAdult    = u.age >= 19;
const isEligible = isAdult && u.verified;
const isBlocked  = u.banned && !u.appealed;

if (!isEligible || isBlocked) deny();
SQL 에서는 한 가지가 더 있습니다 — NULL 이 섞이면 참·거짓 말고 “알 수 없음”이라는 세 번째 값이 생깁니다(3치 논리). NOT (x = 1) 이 x 가 NULL 일 때 참이 아닌 이유입니다 → 🗄️ Database 가이드에서 이어집니다.
조건문이 이해되지 않을 때는 경우를 다 적어 보는 것이 언제나 가장 빠릅니다.
MATH 03

술어논리 — “모든”과 “어떤”을 정확히 말하기

요구사항에 “모든 주문은 결제 정보를 가진다”와 “어떤 주문은 쿠폰이 있다”가 섞여 있습니다. 이 둘을 뒤집을 때 규칙을 모르면 테스트 케이스가 통째로 비게 됩니다.

한정자 두 개

∀x P(x) — 모든 x 에 대해 P 가 참
∃x P(x) — 어떤 x 가 존재해 P 가 참 ∀ 는 All 의 A 를, ∃ 는 Exists 의 E 를 뒤집은 것입니다. 
# 코드에서는 이미 매일 쓰고 있다
all(o.paid for o in orders)    # ∀o  paid(o)
any(o.coupon for o in orders)  # ∃o  coupon(o)

# 빈 리스트일 때가 함정이다
all([])   # True   ← "모든"은 공허하게 참 (vacuous truth)
any([])   # False
빈 집합의 함정 — “모든 항목이 검증됐다”는 항목이 하나도 없을 때도 참입니다. 검증 로직에서 데이터가 비었을 때 통과해 버리는 사고가 여기서 납니다.

부정하면 서로 바뀐다

¬∀x P(x) ≡ ∃x ¬P(x)
¬∃x P(x) ≡ ∀x ¬P(x) “모두 안전하다”의 반대는 “안전하지 않은 게 하나라도 있다”입니다. 
# "모든 파일이 스캔됐다"의 부정
not all(f.scanned for f in files)
# ≡ 스캔 안 된 파일이 하나라도 있다
any(not f.scanned for f in files)

# 실전: 반례를 바로 찾아 로그에 남기는 형태가 좋다
bad = next((f for f in files if not f.scanned), None)
if bad:
    raise ValueError(f"스캔 안 됨: {bad.name}")   # 어떤 것인지까지 알려 준다
실무 팁 — all(...) 로 검사하고 실패하면 “무엇이 실패했는지” 모릅니다. 위처럼 반례를 찾는 형태로 쓰면 에러 메시지가 훨씬 쓸모 있어집니다.

이렇게도 쓸 수 있다 — 순서가 바뀌면 뜻이 달라진다 🟡 중급

∀∃ 와 ∃∀ 는 완전히 다른 말

∀u ∃s 담당(s, u)
모든 사용자에게 각자의 담당자가 있다

∃s ∀u 담당(s, u)
한 사람이 모든 사용자를 담당한다
요구사항 회의에서 실제로 갈리는 지점입니다. “담당자가 있어야 한다”는 문장 하나가 N명 배정인지 1명 전담인지 정해 주지 않습니다. 여기서 스키마가 갈립니다.

SQL 이 사실 술어논리다

-- ∃ : 주문이 있는 고객
SELECT * FROM customer c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.cid = c.id);

-- ∀ : 모든 주문이 결제된 고객
-- ∀ 는 SQL 에 직접 없다. ¬∃¬ 로 바꿔 쓴다
SELECT * FROM customer c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.cid = c.id AND o.paid = false      -- 결제 안 된 게 없다
);
“전부 ~한” 조건은 SQL 에서 늘 NOT EXISTS 로 씁니다. 위 부정 규칙(¬∀ ≡ ∃¬)을 알면 이 패턴이 외울 것이 아니라 유도되는 것이 됩니다.

실무에선 이렇게 — 명세 · 불변식 · 계약 🔴 실무

불변식을 코드에 박아 두기

class Cart:
    """불변식(어느 시점에나 항상 참이어야 하는 것):
       ∀ item ∈ items : item.qty > 0
       total == Σ item.price * item.qty
    """
    def _check(self):
        assert all(i.qty > 0 for i in self.items), "수량 0 이하 항목 존재"
        assert self.total == sum(i.price * i.qty for i in self.items)

    def add(self, item):
        self.items.append(item)
        self.total += item.price * item.qty
        self._check()          # 상태를 바꾼 직후마다 확인

# 사전조건 / 사후조건 (계약에 의한 설계)
def withdraw(balance: int, amount: int) -> int:
    assert amount > 0                 # 사전조건: 호출하는 쪽 책임
    assert balance >= amount
    result = balance - amount
    assert result >= 0                # 사후조건: 이 함수의 약속
    return result
테스트와 무엇이 다른가 — 테스트는 고른 입력 몇 개를 확인하고, 불변식은 모든 실행에서 항상 확인합니다. 재현이 어려운 버그는 불변식 검사를 넣어 두면 터지는 순간에 잡힙니다. 운영에서는 로그로 낮춰 두는 것이 보통입니다.

두 단계면 끝

  1. 기본 단계 — 첫 번째 도미노가 넘어진다 (n = 0 또는 1 에서 참)
  2. 귀납 단계 — k 번째가 넘어지면 k+1 번째도 넘어진다
P(0) ∧ (∀k: P(k) → P(k+1)) ⟹ ∀n P(n) 이 둘만 보이면 무한히 많은 n 에 대해 한 번에 증명이 끝납니다.

def total(items):

        return 0
    return items[0] + total(items[1:])   # ← 귀납 단계

# 이 함수가 맞다고 믿는 근거:
#  ① 빈 리스트의 합은 0 이다                    (기본)

def merge_sort(a):
    if len(a) <= 1: return a                # 기본
    mid = len(a) // 2
    left  = merge_sort(a[:mid])             # 나보다 작은 모든 크기를
    right = merge_sort(a[mid:])             # 이미 안다고 가정 (강한 귀납)
    return merge(left, right)

def find_max(a: list[int]) -> int:
    m = a[0]
    i = 1
    # 불변식: m == max(a[0..i-1])
    while i < len(a):
        if a[i] > m:
            m = a[i]
        i += 1
    return m

# ① 초기 : i=1 일 때 m = a[0] = max(a[0..0])       ✓
# ② 유지 : 불변식이 참이고 한 바퀴 돌면
#          m' = max(m, a[i]) = max(a[0..i])       ✓
#          i' = i+1 이므로 max(a[0..i'-1]) 과 일치
# ③ 종료 : i == len(a) 이므로 m = max(a[0..n-1])  ✓
#
# 변형 함수: len(a) - i  (매번 1씩 감소, 0 에서 멈춤)
확인할 것질문
초기루프에 들어가기 직전에 참인가
유지참인 상태로 한 바퀴 돌면 여전히 참인가
종료루프를 빠져나온 시점에 원하는 결과가 되는가
변형매 반복마다 줄어드는 값이 있는가
불변식은 시험 문제가 아니라 실전 도구입니다. 이진 탐색·투 포인터·슬라이딩 윈도우처럼 경계 조건이 헷갈리는 코드를 쓸 때 “지금 이 시점에 무엇이 참인가”를 주석으로 한 줄 적어 두면 off-by-one 이 거의 사라집니다. 주석으로 남기면 다음 사람도 안전하게 고칠 수 있습니다.

def birthday(n, days=365):
    p = 1.0
    for i in range(n):
        p *= (days - i) / days
    return 1 - p          # 충돌이 하나라도 있을 확률

WHITE, GRAY, BLACK = 0, 1, 2      # 안 봄 / 보는 중 / 다 봄

def find_cycle(graph):
    color = {v: WHITE for v in graph}
    stack = []                     # 지금 내려온 경로

    def dfs(v):
        color[v] = GRAY
        stack.append(v)
        for nxt in graph.get(v, []):
            if color.get(nxt, WHITE) == GRAY:        # ★ 회색을 다시 만나면 사이클
                i = stack.index(nxt)
                return stack[i:] + [nxt]             # 사이클 경로를 그대로 반환
            if color.get(nxt, WHITE) == WHITE:
                found = dfs(nxt)
                if found: return found
        color[v] = BLACK
        stack.pop()
        return None

    for v in graph:
        if color[v] == WHITE:
            found = dfs(v)
            if found: return found
    return None

g = {"a": ["b"], "b": ["c"], "c": ["a"]}
print(find_cycle(g))    # ['a', 'b', 'c', 'a']  ← 어디가 문제인지까지 알려 준다
회색(GRAY)이 핵심입니다 — “다 본 것(검정)”을 다시 만나는 건 사이클이 아닙니다. 지금 내려오고 있는 경로 위의 정점을 다시 만났을 때만 사이클입니다. 이 구분을 놓치면 멀쩡한 다이아몬드 의존성을 사이클로 잘못 신고합니다.

트리의 정의와 성질

정점 n 개인 트리 ⟺ 간선이 정확히 n−1 개 ⟺ 모든 두 정점 사이 경로가 정확히 하나 ⟺ 연결됐고 사이클 없음

네 조건이 전부 같은 말입니다. 그래서 “간선이 n−1 개인데 연결됐다”만 확인하면 트리임이 보장됩니다. 이 성질이 MST 알고리즘의 종료 조건이 됩니다.

경로가 유일하다는 것이 실무에서 가장 유용합니다 — 파일 경로가 하나뿐이고, 조직도에서 상급자가 명확하고, DOM 에서 부모 체인이 유일한 이유가 전부 이것입니다.

def kruskal(n, edges):        # edges: (비용, u, v)
    parent = list(range(n))
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]   # 경로 압축
            x = parent[x]
        return x

    mst, cost = [], 0
    for w, u, v in sorted(edges):           # ① 싼 것부터
        ru, rv = find(u), find(v)
        if ru == rv:                        # ② 이미 연결됨 → 사이클
            continue
        parent[ru] = rv                     # ③ 합친다
        mst.append((u, v, w)); cost += w
        if len(mst) == n - 1: break         # ④ n-1 개면 끝
    return mst, cost
“싼 것부터 고르되 사이클만 피한다”가 전부입니다 — 대표적인 탐욕 알고리즘이고, 그게 정말 최소임이 증명돼 있습니다. 사이클 판정에 쓰인 find/union 이 🗂️ 자료구조 11 유니온 파인드입니다.

def sieve(n):
    is_p = [True] * (n + 1)
    is_p[0] = is_p[1] = False
    i = 2
    while i * i <= n:              # √n 까지만 보면 된다
        if is_p[i]:
            for j in range(i * i, n + 1, i):   # i*i 부터 시작 (그 앞은 이미 지워짐)
                is_p[j] = False
        i += 1
    return [i for i, p in enumerate(is_p) if p]

len(sieve(1_000_000))    # 78,498 개 · 0.1초 정도

# 하나만 판정할 때
def is_prime(n):
    if n < 2: return False
    if n % 2 == 0: return n == 2
    f = 3
    while f * f <= n:
        if n % f == 0: return False
        f += 2
    return True

def pow_mod(base, exp, mod):
    result = 1
    base %= mod
    while exp > 0:
        if exp & 1:                 # 지수의 비트가 1이면 곱한다
            result = result * base % mod
        base = base * base % mod    # 제곱해서 올라간다
        exp >>= 1
    return result

# 2^1000 을 1000번 곱하지 않고 10번만에 (log₂1000 ≈ 10)

# 안전한 이유: n = p×q 에서 p·q 를 알아내는 것(소인수분해)이
#              현재 알려진 방법으로는 현실적인 시간 안에 불가능하기 때문
# 아주 작은 수로 직접 확인해 보기 (실제로는 2048비트 이상을 쓴다)
p, q = 61, 53
n = p * q                    # 3233
phi = (p - 1) * (q - 1)      # 3120
e = 17                       # phi 와 서로소인 공개 지수
d = modinv(e, phi)           # 2753  ← 09 의 확장 유클리드

m = 65                                   # 평문

def find_single(nums):

점화식과 마스터 정리 — 재귀 복잡도를 3초에

“병합 정렬은 O(n log n)”을 외우는 대신 유도하는 법입니다. 마스터 정리는 분할 정복 알고리즘의 복잡도를 표 한 번 보고 답하게 해 줍니다.

점화식 세우기

def merge_sort(a):
    if len(a) <= 1: return a            # T(1) = O(1)
    mid = len(a) // 2
    l = merge_sort(a[:mid])             # T(n/2)
    r = merge_sort(a[mid:])             # T(n/2)
    return merge(l, r)                  # O(n)

# 코드를 그대로 식으로 옮기면
#   T(n) = 2·T(n/2) + O(n)
#          ↑    ↑       ↑
#        몇 번  얼마로  나머지 일
#        부르나  줄여서
T(n) = a · T(n/b) + f(n) — a: 재귀 호출 수 · b: 줄어드는 비율 · f(n): 나머지 작업

마스터 정리 — 세 경우만 보면 됩니다

② f 가 nc 와 같다 → Θ(nc log n)
③ f 가 nc 보다 크다 → Θ(f(n))

이렇게도 쓸 수 있다 — 재귀 트리로 직관 얻기 🟡 중급

왜 log n 층인가

T(n) = 2T(n/2) + n

층      호출 수    각 호출의 일     그 층의 총합
────────────────────────────────────────────
0          1           n                n
1          2          n/2               n
2          4          n/4               n
...
log n     n           1                 n
────────────────────────────────────────────
                              총합 = n × log n

★ 핵심은 두 가지
  · n 을 2로 계속 나눠 1이 될 때까지 → log₂n 층
  · 각 층의 총합이 항상 n → 층 수 × n

한 개만 재귀하면 (이진 탐색)

T(n) = T(n/2) + 1

각 층에 호출이 1개뿐 → 총 log n 번
→ Θ(log n)

10억 개에서도 30번이면 끝난다

1씩 줄이면 (순진한 피보나치)

T(n) = T(n-1) + T(n-2) + 1

층마다 호출이 2배씩 → 2ⁿ
→ Θ(1.618ⁿ)   황금비

n=50 이면 이미 몇 분,
n=100 이면 우주가 끝난다
차이를 만드는 것은 “나누기냐 빼기냐”입니다. n/2 로 줄이면 log 층, n-1 로 줄이면 n 층입니다. 알고리즘을 설계할 때 이 하나만 봐도 될지 안 될지가 갈립니다.

실무에선 이렇게 — 마스터 정리로 안 되는 경우 🔴 실무

적용할 수 없는 형태

① 부분 문제 크기가 다를 때
   T(n) = T(n/3) + T(2n/3) + n
   → 재귀 트리를 직접 그린다 (결과: Θ(n log n))

② 재귀 호출 수가 n 에 의존
   T(n) = n·T(n/2) + n
   → 마스터 정리 밖

③ f(n) 이 다항식이 아닐 때
   T(n) = 2T(n/2) + n/log n
   → 아카라-바자이 정리 또는 직접 계산

④ 뺄셈형
   T(n) = T(n-1) + n     → Θ(n²)
   T(n) = 2T(n-1) + 1    → Θ(2ⁿ)

실무에서 진짜로 쓰는 순서

  1. 점화식을 세운다 — 코드에서 “몇 번 부르나 / 얼마로 줄이나 / 나머지 일”만 읽습니다.
  2. 표에서 찾는다 — 위 다섯 개 안에 대부분 들어갑니다.
  3. 안 맞으면 재귀 트리 — 3층만 그려도 패턴이 보입니다.
  4. 실측으로 확인 — n 을 10배 늘려 시간이 몇 배가 되는지 봅니다. 10배 → 10배면 O(n), 100배면 O(n²), 12배쯤이면 O(n log n).
④ 가 가장 실용적입니다 — 이론이 애매하면 n=1000, 10000, 100000 으로 재 보는 것이 가장 빠른 답입니다. 🧮 계산이론 탭 07·08에 측정 방법이 있습니다.
