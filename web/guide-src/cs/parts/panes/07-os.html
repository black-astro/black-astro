OS 01

운영체제가 하는 일 — 자원을 나눠 쓰게 하는 심판

OS 가 없으면 프로그램 하나가 메모리 전체를 덮어쓰고 CPU 를 독점할 수 있습니다. 그래서 OS 는 하드웨어를 감추고, 대신 추상화를 제공합니다 — 프로세스 · 파일 · 소켓이 전부 그 추상화입니다.

네 가지 핵심 역할

역할추상화없으면
CPU 관리프로세스 · 스레드하나가 독점
메모리 관리가상 주소 공간서로 덮어씀
저장 관리파일 · 디렉터리블록을 직접 다뤄야
장치 관리디바이스 파일 · 소켓하드웨어별 코드 필요
“모든 것은 파일”이 유닉스의 설계 철학입니다 — 디스크 · 터미널 · 소켓 · 프로세스 정보(/proc)가 전부 같은 read/write 인터페이스로 다뤄집니다. 인터페이스를 하나로 줄이는 것의 위력을 보여 주는 예입니다.

사용자 모드와 커널 모드

CPU 에는 특권 레벨이 있다 (x86: 링 0 ~ 3)

  링 0 — 커널      모든 명령 실행 가능
  링 3 — 사용자    특권 명령 금지 · 자기 주소 공간만

사용자 모드에서 금지된 것
  · 임의의 물리 메모리 접근
  · I/O 포트 직접 제어
  · 인터럽트 활성/비활성
  · 페이지 테이블 변경

그래서 파일을 읽으려면 커널에게 부탁해야 한다
  → 시스템 콜 (11절)

  read() 호출
    → 트랩 명령 (syscall)
    → CPU 가 링 0 으로 전환 + 커널 코드로 점프
    → 커널이 작업 수행
    → 다시 링 3 으로 복귀

  - 드라이버 하나의 버그가 시스템 전체를 죽인다

마이크로커널의 장단점
  + 드라이버가 죽어도 재시작 가능 (자동차·의료기기)
  - 메시지 전달 비용

  · 모놀리식이지만 모듈을 동적 로드 (lsmod)

  · eBPF — 검증된 코드를 커널에 안전하게 주입 ★

프로세스와 스레드 — 무엇을 공유하는가

프로세스는 따로 사는 집, 스레드는 한 집에 사는 식구입니다. 이 차이가 성능 · 안정성 · 동시성 버그의 성격을 전부 결정합니다.

import os, sys

pid = os.fork()          # ★ 한 번 호출되고 두 번 반환된다
if pid == 0:
    print("자식", os.getpid())
    os._exit(0)          # 자식은 반드시 _exit (버퍼 중복 플러시 방지)
else:
    print("부모", os.getpid(), "자식", pid)
    os.waitpid(pid, 0)   # ★ 안 하면 좀비가 남는다

# fork 는 copy-on-write
#  · 주소 공간을 '복사한 척' 만 한다
#  · 쓰는 순간에만 실제 복사
#  · 그래서 큰 프로세스도 fork 가 빠르다
#  ★ 단, 파이썬은 참조 카운트 때문에 읽기만 해도 페이지가 복사된다

# 프로세스 상태
#  R 실행/대기  S 인터럽트 가능 슬립  D 인터럽트 불가 슬립(I/O)
#  Z 좀비 — 끝났는데 부모가 회수 안 함
#  T 정지
문제원인대응
좀비 프로세스부모가 wait 안 함wait · SIGCHLD 처리 · init 에 위임
고아 프로세스부모가 먼저 죽음init(PID 1)이 입양
컨테이너에 좀비 쌓임PID 1 이 앱이라 회수 안 함tini · --init 사용
D 상태에서 안 죽음I/O 대기 (kill -9 도 안 통함)디스크·NFS 문제 확인
도커에서 --init 을 쓰라는 이유가 이것입니다 — 컨테이너 안의 PID 1 은 보통 애플리케이션인데, 좀비를 회수하는 코드가 없어서 프로세스 테이블이 찹니다. docker run --init 또는 tini 를 엔트리포인트로 두세요.

실무에선 이렇게 — 스레드 수를 정하는 법 🔴 실무

스레드 수 ≈ 코어 수 × (1 + 대기 시간 / 계산 시간) 순수 CPU 작업이면 코어 수, I/O 가 90% 면 코어 수 × 10 
import os
cores = os.cpu_count()

# CPU 바운드 → 코어 수 (컨텍스트 스위치 낭비를 피함)
cpu_pool = ProcessPoolExecutor(max_workers=cores)

# I/O 바운드 → 훨씬 크게, 다만 상한을 둔다
io_pool = ThreadPoolExecutor(max_workers=min(32, cores * 8))

# ★ 컨테이너에서는 os.cpu_count() 가 호스트 코어를 반환할 수 있다
def container_cpus():
    try:                        # cgroup v2
        with open("/sys/fs/cgroup/cpu.max") as f:
            quota, period = f.read().split()
            if quota != "max": return max(1, int(int(quota) / int(period)))
    except FileNotFoundError: pass
    return os.cpu_count()

# 자바도 같은 문제 — JDK 10+ 는 자동 인식
#   -XX:ActiveProcessorCount=4 로 강제 가능

스레드를 늘렸는데 느려짐컨텍스트 스위치 · 락 경합 · 캐시 오염

컨텍스트 스위치 — 공짜가 아닙니다

스레드를 바꿔 끼우는 데도 비용이 듭니다. 그것도 직접 비용보다 간접 비용(캐시 오염)이 훨씬 큽니다. “스레드를 늘렸는데 느려졌다”의 답이 여기 있습니다.

무슨 일이 벌어지나

직접 비용 (1~5µs)
  ① 현재 레지스터를 저장
  ② 스케줄러가 다음 태스크 선택
  ③ 새 태스크의 레지스터 복원
  ④ 프로세스가 다르면 페이지 테이블 전환 (+ TLB 플러시)

간접 비용 (훨씬 큼 · 수십~수백 µs)
  ⑤ ★ 캐시가 새 태스크의 데이터로 채워져야 한다
     내 데이터가 L1/L2 에서 밀려나 있다
     → 돌아왔을 때 전부 미스

  ⑥ TLB 도 마찬가지 (프로세스 전환 시)
  ⑦ 분기 예측기도 새로 학습해야 함
그래서 코루틴이 빠릅니다 — 같은 스레드 안에서 스택 포인터만 바꾸므로 커널 진입도, TLB 플러시도, 캐시 오염도 최소입니다(수십~수백 ns).

class BatchWriter:
    def __init__(self, flush_size=1000, flush_ms=100):
        self.buf, self.size, self.ms = [], flush_size, flush_ms
        self.last = time.monotonic()

    def add(self, item):
        self.buf.append(item)
        now = time.monotonic()
        if len(self.buf) >= self.size or (now - self.last) * 1000 >= self.ms:
            self.flush()

    def flush(self):
        if not self.buf: return
        db.bulk_insert(self.buf)        # 한 번의 왕복
        self.buf.clear(); self.last = time.monotonic()

스왑과 스래싱

메모리가 부족하면 OS 는 잘 안 쓰는 페이지를 디스크로 내린다

  정상: 진짜 안 쓰는 페이지만 나감 → 문제 없음
  스래싱: 내리자마자 다시 필요해짐 → 계속 왕복
          → CPU 는 노는데 아무 일도 진행이 안 됨
          → 응답 시간이 수십 초로

판단
  vmstat 1 에서 si/so 가 지속적으로 0 이 아니면 위험

대응 (순서대로)
  ① 메모리를 실제로 쓰는 프로세스를 줄인다
  ② 힙 크기 · 캐시 크기 설정을 낮춘다
  ③ 메모리를 늘린다
  ④ swappiness 조정 (0 이 아니라 1~10 권장)
     sysctl vm.swappiness=10
스왑을 완전히 끄는 것이 항상 정답은 아닙니다 — 끄면 스래싱 대신 OOM Killer 가 바로 동작합니다. DB 서버는 보통 swappiness=1, 쿠버네티스 노드는 전통적으로 스왑을 껐지만 최근에는 제한적으로 허용하는 방향입니다.

class ShardedCounter:
    def __init__(self, shards=16):
        self.locks = [threading.Lock() for _ in range(shards)]
        self.counts = [0] * shards
        self.n = shards

    def incr(self, key):
        i = hash(key) % self.n
        with self.locks[i]:            # 다른 샤드는 서로 안 막는다
            self.counts[i] += 1

    def total(self):
        return sum(self.counts)        # 근사치 (정확하려면 전부 잠금)

# 안전하게 파일 저장하는 관용구 (원자적 교체)
import os, tempfile

def atomic_write(path, data):
    d = os.path.dirname(path)
    fd, tmp = tempfile.mkstemp(dir=d)         # 같은 파일 시스템에
    try:
        with os.fdopen(fd, "wb") as f:
            f.write(data)
            f.flush()
            os.fsync(f.fileno())              # ① 내용을 디스크로
        os.replace(tmp, path)                 # ② 원자적 교체
        dirfd = os.open(d, os.O_DIRECTORY)
        try: os.fsync(dirfd)                  # ③ 디렉터리도 fsync
        finally: os.close(dirfd)
    except BaseException:
        os.unlink(tmp); raise

import selectors, socket

sel = selectors.DefaultSelector()      # 플랫폼별 최적 (리눅스=epoll)

srv = socket.socket()
srv.bind(("0.0.0.0", 8080)); srv.listen(1024)
srv.setblocking(False)
sel.register(srv, selectors.EVENT_READ, data=None)

while True:
    for key, mask in sel.select(timeout=1.0):     # 준비된 것만 반환
        if key.data is None:                       # 새 연결
            conn, addr = key.fileobj.accept()
            conn.setblocking(False)
            sel.register(conn, selectors.EVENT_READ, data=addr)
        else:                                      # 데이터 도착
            conn = key.fileobj
            data = conn.recv(4096)
            if not data:
                sel.unregister(conn); conn.close()
            else:
                conn.sendall(process(data))

스케줄러 내부 — CFS 의 vruntime 에서 EEVDF 까지

03절이 “무엇을 먼저 실행할까”라는 개념이었다면, 여기서는 리눅스가 실제로 쓰는 방식을 봅니다. CFS 는 “누가 가장 적게 썼나”만 보고 고르며, 그 판단 기준이 vruntime 입니다. 6.6 부터 기본이 된 EEVDF 는 여기에 “언제까지 줘야 하나”를 더했습니다. 이 절의 실질적인 목적은 하나입니다 — 컨테이너의 CPU 스로틀링이 평균 사용률이 낮은데도 왜 p99 를 망가뜨리는지 설명할 수 있게 되는 것.

“공평하다”를 정의하는 문제입니다. 모두에게 같은 시간을 주는 것이 공평일까요, 아니면 중요도(nice · cpu.weight)에 비례해서 주는 것이 공평일까요. CFS 는 후자를 택했고, “비례해서 주고 있는가”를 재는 자가 vruntime 입니다.
우선순위는 “먼저 실행”이 아니라 “시간이 천천히 흐른다”로 구현되어 있습니다 — 굶는 태스크가 생기지 않는 이유입니다.

지금 이 서버에서 직접 확인하기

# 이 프로세스가 어떤 정책으로 도는가
chrt -p $$                 # SCHED_OTHER = CFS/EEVDF

# 태스크 하나의 스케줄링 통계 — 진단의 출발점
grep -E 'vruntime|sum_exec|wait_sum|nr_switches' /proc/$$/sched
#  se.vruntime       가상 실행 시간
#  se.sum_exec_runtime  실제로 CPU 를 쓴 누적 시간
#  se.statistics.wait_sum   ★ 큐에서 기다린 총 시간
#  nr_involuntary_switches  ★ 강제로 뺏긴 횟수

# ★ wait_sum 이 sum_exec_runtime 에 근접하면
#   "일하는 시간만큼 기다리고 있다" = CPU 경합입니다

# 런큐에 몇 개나 밀려 있나
vmstat 1 5                 # r 열 = 실행 대기 중 태스크 수
#   r 이 코어 수보다 꾸준히 크면 CPU 부족입니다

# 커널이 노출하는 노브 (6.6+ 는 이름이 바뀌었습니다)
ls /sys/kernel/debug/sched/
#  base_slice_ns              ← EEVDF (6.6+)
#  latency_ns, min_granularity_ns  ← 그 이전 CFS

# 몫 조정 — 절대 시간이 아니라 '가중치 비율' 로 작동합니다
nice -n 10 ./batch_job &   # 가중치 110 → 약 1/9 몫
taskset -c 0-3 ./worker    # 특정 코어에 고정 (캐시 지역성)
“CPU 사용률 60%인데 왜 느리죠” 에 답하는 자리입니다. 사용률이 아니라 wait_sum 과 vmstat 의 r 을 보세요 — 전자는 “기다린 시간”, 후자는 “줄 서 있는 수”라 평균 사용률이 숨기는 지연을 그대로 드러냅니다.

vruntime 계산과 몫의 관계

vruntime += Δ실행시간 × (1024 ÷ 가중치) nice 0 → 가중치 1024 → 실제 시간 그대로
nice −5 → 3121 → 1/3 속도로 늘어남 → 3배 자주 뽑힘
nice +5 → 335 → 3배 속도로 늘어남 → 1/3

가중치 표는 공비 1.25 의 등비수열입니다 — 한 단계 = 약 10% 몫 차이, 다섯 단계 = 약 3배

몫i = wi ÷ Σwj — 절대 시간이 아니라 비율이라 경쟁자가 없으면 nice 19 도 CPU 를 다 씁니다
궁금한 것답
새 태스크의 vruntime큐의 최솟값 근처로 맞춤 (안 그러면 독점)
잠에서 깬 태스크약간 깎아 줌 → 대화형이 빠릿함
한 번에 얼마나슬라이스 = 목표지연 × 내 가중치 비율
너무 잘게 쪼개면컨텍스트 스위치 비용 폭증(04절)
그래서 하한이min_granularity / base_slice
코어 간 이동부하 분산 — 캐시를 잃어 비쌈
실시간 정책은 이 계산 밖에 있습니다. SCHED_FIFO · SCHED_RR 은 CFS 태스크보다 무조건 먼저 실행됩니다. 그래서 실시간 우선순위를 잘못 주면 시스템 전체가 멈춘 것처럼 보입니다 — 커널이 rt_runtime_us 로 95% 상한을 두는 이유입니다.

EEVDF — “얼마나”에 “언제까지”를 더하기

CFS 는 “덜 쓴 사람”만 봤고, EEVDF 는 “덜 썼고 급한 사람”을 봅니다 — 처리량을 지키면서 꼬리 지연을 줄이는 방향입니다.

컨테이너에서 실제로 만나는 형태

# cgroup v2 — 쿠버네티스의 requests/limits 가 여기로 내려옵니다
cat /sys/fs/cgroup/cpu.max
#  "200000 100000"  = 100ms 주기마다 200ms → 2코어 (limits)
#  "max 100000"     = 상한 없음

cat /sys/fs/cgroup/cpu.weight
#  100 이 기본 (nice 0). requests 가 이 값으로 바뀝니다
#  → 경합할 때만 의미가 있는 '비율' 입니다

# ★ 스로틀링이 걸리고 있는가 — 지연 장애의 1순위 원인
cat /sys/fs/cgroup/cpu.stat
#  nr_periods      전체 주기 수
#  nr_throttled    ★ 쿼터를 다 써서 멈춘 주기 수
#  throttled_usec  ★ 멈춰 있던 총 시간

# 비율로 보기 — 5% 를 넘으면 p99 에서 보입니다
awk '/nr_periods/{p=$2} /nr_throttled/{t=$2}
     END{printf "throttled %.1f%%\n", t*100/p}' /sys/fs/cgroup/cpu.stat

# 프로메테우스에서는 같은 값이 이 이름으로 옵니다
#   container_cpu_cfs_throttled_periods_total
#   container_cpu_cfs_periods_total
“CPU 평균 40%인데 p99 가 튄다”의 진범이 대개 이것입니다. 쿼터는 100ms 주기 단위로 정산합니다. 스레드 8개가 첫 20ms 에 쿼터를 다 쓰면 남은 80ms 를 통째로 멈춰 있습니다 — 평균 사용률은 낮게 나오지만 그 요청은 80ms 를 그냥 잃습니다.

스로틀링을 없애는 순서

할 일이유
① 런타임에 한도 알리기스레드 수가 코어 수를 안 넘게
② limit 을 올리기버스트가 정상 패턴이면 한도가 잘못된 것
③ 주기 줄이기정산 단위가 짧아져 멈추는 덩어리가 작아짐
④ limit 을 없애기requests 만 두고 weight 로 경쟁시키기
피할 것replica 만 늘리기 — 스로틀은 그대로입니다
# ① 런타임이 '호스트의 코어 수' 를 보는 문제를 먼저 막습니다

# ② 쿠버네티스에서 확인
kubectl get pod api-0 -o jsonpath='{.spec.containers[0].resources}'

# ③ 노드 전체에서 스로틀 상위 컨테이너 찾기
for d in /sys/fs/cgroup/kubepods.slice/*/*/cpu.stat; do
  awk -v n="$d" '/nr_periods/{p=$2} /nr_throttled/{t=$2}
    END{if(p>0 && t*100/p>5) printf "%5.1f%%  %s\n", t*100/p, n}' "$d"
done | sort -rn | head
