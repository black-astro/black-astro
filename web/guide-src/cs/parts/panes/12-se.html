SE 01

추상화 · 결합도 · 응집도 — 설계를 재는 자

좋은 설계의 기준은 “이 요구가 바뀌면 어디를 고쳐야 하나”입니다. 한 군데면 좋은 설계이고, 열 군데면 나쁜 설계입니다. 나머지는 전부 이 문장의 파생입니다.

결합도 — 낮을수록 좋다

종류내용평가
내용 결합남의 내부를 직접 건드림최악
공통 결합전역 변수 공유나쁨
제어 결합플래그로 상대 동작을 조종나쁨
스탬프 결합필요 없는 것까지 통째로 전달보통
데이터 결합필요한 값만 인자로좋음
메시지 결합메시지·이벤트로만가장 낮음
# 제어 결합 — 플래그가 함수 안에서 갈라진다
def save(data, is_draft):        # ✗
    if is_draft: ...
    else: ...

# ✓ 함수를 나눈다
def save_draft(data): ...
def publish(data): ...

# 스탬프 결합 — 필요한 것만 받는다
def send_mail(user): ...          # ✗ user 전체
def send_mail(email, name): ...   # ✓ 필요한 것만
# → 테스트가 쉬워지고 의존성이 줄어든다

응집도 — 높을수록 좋다

한 모듈 안의 것들이 얼마나 '한 가지 일' 을 하는가

  기능적 응집 (최고) — 하나의 명확한 목적
  순차적 응집       — 출력이 다음의 입력
  통신적 응집       — 같은 데이터를 다룸
  절차적 응집       — 순서만 같음
  시간적 응집       — 같은 시점에 실행 (초기화 묶음)
  논리적 응집       — 비슷해 보여서 묶음 (플래그로 분기)
  우연적 응집 (최악) — 이유 없이 한 파일에

★ utils.py · common.py · helpers.py 는
  대개 우연적 응집의 신호다 — 갈 곳 없는 것들의 창고
“변경 이유가 같은 것끼리 모으라”가 응집의 실용적 정의입니다. 같은 시점에 같은 이유로 바뀌는 코드가 한곳에 있으면 변경이 국소적으로 끝납니다.

이렇게도 쓸 수 있다 — 추상화가 새는 지점 🟡 중급

모든 추상화는 어느 정도 샌다 (Leaky Abstraction)

  · ORM 은 SQL 을 감추지만 N+1 은 그대로 드러난다
  · 네트워크 파일 시스템은 로컬처럼 보이지만 지연이 다르다
  · 가비지 컬렉션은 메모리를 감추지만 정지 시간이 보인다
  · 컨테이너는 격리를 주지만 커널은 공유된다

★ 그래서 '추상화 아래를 알아야' 한다 — 이 가이드 전체의 이유다

나쁜 추상화의 신호
  · 쓰려면 내부를 알아야 한다
  · 예외 상황에서 원래 계층이 튀어나온다
  · 파라미터가 계속 늘어난다
  · "이 경우에만" 이 반복된다
추상화 판단기준
지금 만들 것인가같은 패턴을 3번 봤을 때 (Rule of Three)
얼마나 일반화할 것인가실제로 있는 경우만 · 미래를 상상하지 말 것
좋은 추상화인가이름을 붙일 수 있는가 · 설명이 한 문장인가
제거해야 하나구현체가 하나뿐이고 앞으로도 하나면
“나중에 필요할까 봐” 만든 추상화가 가장 비쌉니다 — 추측한 확장점은 대개 틀리고, 잘못된 추상화는 중복보다 나쁩니다. 중복은 나중에 합치면 되지만 잘못된 추상화는 되돌리기 어렵습니다.

실무에선 이렇게 — 변경 비용으로 판단하기 🔴 실무

질문확인 방법
이 필드를 추가하면?고쳐야 할 파일 수를 센다
이 외부 API 를 바꾸면?직접 참조하는 곳을 grep
이 규칙이 바뀌면?같은 로직이 몇 군데 있나
이 모듈을 지우면?얼마나 많은 것이 깨지나
새 사람이 이해하려면?몇 개 파일을 읽어야 하나
# 실제로 측정할 수 있다
# 함께 바뀌는 파일 (변경 결합도)
git log --format="%H" --since="6 months ago" | while read c; do
  git show --name-only --format="" $c
done | sort | uniq -c | sort -rn | head -20

# 두 파일이 항상 함께 바뀐다면
#  → 같은 모듈에 있어야 하거나, 결합이 과한 것

# 자주 바뀌는 파일 = 리팩터링 우선순위
git log --format="" --name-only --since="1 year ago" \
  | sort | uniq -c | sort -rn | head -20

# 복잡도 + 변경 빈도 = 핫스팟 (Code Maat · CodeScene 의 아이디어)
“자주 바뀌면서 복잡한 파일”이 리팩터링 1순위입니다 — 복잡하지만 안 바뀌는 코드는 건드릴 이유가 없습니다. git 히스토리가 이 판단의 데이터가 됩니다.
두 지표는 독립이 아닙니다 — 응집도를 올리면(관련된 것끼리 모으면) 결합도는 대개 저절로 내려갑니다.

등급으로 보기 — 어디까지가 위험한가

결합도 — 나쁜 것부터

종류무엇을 공유하나
내용 결합남의 내부를 직접 건드림 — private 필드·리플렉션
공통 결합전역 변수를 함께 씀 — 누가 언제 바꿨는지 추적 불가
외부 결합외부 포맷·프로토콜에 함께 묶임
제어 결합플래그를 넘겨 상대의 흐름을 조종 — save(data, true)
스탬프 결합큰 객체를 통째로 넘기고 일부만 씀
데이터 결합필요한 값만 인자로 — 목표 지점
# ✗ 제어 결합 — 불리언 인자가 상대의 흐름을 나눕니다
def save(order, send_mail: bool, is_draft: bool): ...
save(o, True, False)      # 호출부만 봐서는 무슨 뜻인지 모릅니다

# ✓ 흐름을 나누지 말고 함수를 나눕니다
def save_draft(order): ...
def publish(order): ...   # 메일 발송은 이벤트로 분리

# ✗ 스탬프 결합 — User 전체를 넘기지만 실제로는 email 만 씀
def notify(user: User): send(user.email)
# ✓ 필요한 것만 (테스트도 쉬워집니다)
def notify(email: str): send(email)
불리언 인자는 대개 설계 신호입니다. f(x, True) 를 읽고 무슨 뜻인지 바로 모르겠다면 그 함수는 두 가지 일을 하고 있습니다. 나누면 이름이 설명을 대신하고, 조건 분기가 사라집니다.

응집도 — 좋은 것부터

종류무엇으로 묶였나
기능적 응집하나의 일만 함 — 목표 지점
순차적 응집앞의 출력이 뒤의 입력
통신적 응집같은 데이터를 다룸
절차적 응집실행 순서만 같음
시간적 응집"시작할 때 하는 일들" — init() 에 잡다한 것
우연적 응집utils.py — 아무 관계 없는 것들
실측하는 법 — git 이 데이터를 갖고 있습니다

# 같이 자주 바뀌는 파일 쌍 = 숨은 결합
git log --name-only --pretty=format: --since=1.year |
  awk 'NF' | sort | uniq -c | sort -rn | head -20

# 한 커밋에 들어간 파일 수의 분포
#   평균 10개 이상이면 결합도가 높다는 신호

# 자주 바뀌면서 큰 파일 = 리팩터링 1순위
git log --format= --name-only --since=6.months |
  sort | uniq -c | sort -rn | head
utils · common · helper 는 응집도가 0 인 이름입니다. "여기에 뭘 넣어야 하지?"의 답이 "딱히 갈 곳 없는 것 전부" 가 되기 때문입니다. 결국 모든 모듈이 그 파일에 의존하게 되어 결합도까지 함께 나빠집니다. 무슨 일을 하는지로 이름을 짓고(money_format·retry_policy), 이름이 안 지어지면 아직 그 추상화가 없다는 뜻입니다.

SOLID — 어길 때 뭐가 아픈가로 이해하기

다섯 원칙을 외우는 것보다 어겼을 때 생기는 증상을 아는 것이 유용합니다. 그리고 과하게 적용하면 오히려 나빠진다는 것도 함께 봅니다.

원칙어기면
S단일 책임 — 변경 이유가 하나한 클래스를 여러 팀이 동시에 수정 · 충돌
O개방-폐쇄 — 확장에 열리고 수정에 닫힘기능 추가마다 기존 코드 수정 · 회귀
L리스코프 치환 — 자식이 부모를 대체 가능isinstance 분기가 늘어남
I인터페이스 분리 — 안 쓰는 메서드 강요 금지NotImplementedError 가 늘어남
D의존 역전 — 구현이 아니라 추상에 의존테스트에 실제 DB · 외부 API 가 필요

D — 가장 실용적인 원칙

✗ 구현에 직접 의존
class OrderService:
    def __init__(self):
        self.db = PostgresClient(...)     # 고정
        self.mailer = SmtpMailer(...)     # 고정

    def create(self, req):
        self.db.insert(...)
        self.mailer.send(...)

# 테스트하려면 실제 DB 와 SMTP 가 필요하다
✓ 추상에 의존 + 주입
class OrderService:
    def __init__(self, repo: OrderRepo, mailer: Mailer):
        self.repo, self.mailer = repo, mailer

    def create(self, req):
        self.repo.save(...)
        self.mailer.send(...)

# 테스트
svc = OrderService(InMemoryRepo(), FakeMailer())
# 빠르고 · 격리되고 · 검증하기 쉽다
파이썬 · Go 에서는 인터페이스를 명시하지 않아도 됩니다 — Protocol(파이썬) · 암묵적 인터페이스(Go)로 선언 없이 같은 효과를 얻습니다. 중요한 것은 주입이지 인터페이스 선언이 아닙니다.

과하게 적용하면

증상원인
구현이 하나뿐인 인터페이스가 가득D 를 기계적으로 적용
클래스가 수십 개인데 각 3줄S 를 과하게
추적하려면 5단계를 타고 가야추상화 계층 과다
팩토리의 팩토리패턴 남용
설정으로 모든 것을 조절O 를 오해
“Enterprise FizzBuzz” 라는 유명한 농담이 있습니다 — FizzBuzz 를 SOLID·패턴으로 구현하면 수십 개 파일이 됩니다. 원칙은 문제를 해결할 때만 가치가 있습니다.

이렇게도 쓸 수 있다 — 다른 유용한 원칙들 🟡 중급

원칙내용
YAGNI필요해질 때까지 만들지 마라 — 가장 자주 어겨진다
KISS단순하게 — 영리한 코드보다 지루한 코드
DRY지식의 중복을 피하라 — 코드 모양의 중복이 아니다
최소 놀람이름과 동작이 예상과 일치할 것
데메테르 법칙a.b().c().d() 를 피하라 (친구의 친구)
합성 > 상속상속은 가장 강한 결합
실패는 빨리잘못된 상태로 진행하지 말 것
포아송 원칙입력에는 관대하게, 출력에는 엄격하게 (지금은 논쟁적)
# DRY 의 오해 — 우연히 같아 보이는 코드를 합치면 나중에 아프다
# ✗ 지금 모양이 같다고 합침
def validate(data, kind):
    if kind == "user":  ...
    elif kind == "order": ...
    # 둘의 규칙이 나중에 갈라지면 이 함수가 지옥이 된다

# ✓ 지식이 같은 것만 합친다
#   "이메일 형식 검증" 은 하나 — 규칙이 진짜 같다
#   "사용자 검증" 과 "주문 검증" 은 다른 지식 — 따로 둔다

# 판단 기준: "이 규칙이 바뀔 때 둘 다 바뀌어야 하는가?"
#   예 → 합친다 (같은 지식)
#   아니오 → 따로 둔다 (우연한 유사성)
“성급한 추상화보다 중복이 낫다”(Sandi Metz)는 실무에서 반복적으로 확인되는 조언입니다. 중복은 눈에 보이고 나중에 합칠 수 있지만, 잘못된 추상화는 모두를 그 안에서 일하게 만듭니다.

실무에선 이렇게 — 상속을 피하는 이유 🔴 실무

✗ 상속으로 재사용
class Bird:
    def fly(self): ...

class Penguin(Bird):        # 리스코프 위반
    def fly(self):
        raise NotImplementedError

# 부모의 계약을 자식이 못 지킨다
# → 쓰는 쪽이 isinstance 로 분기하게 된다

class Stack(list):          # 더 나쁜 예
    ...                     # list 의 모든 메서드가 노출된다
                            # stack.insert(0, x) 가 가능해진다
✓ 합성으로
class Stack:
    def __init__(self):
        self._items = []            # 감춘다
    def push(self, x): self._items.append(x)
    def pop(self):     return self._items.pop()

# 능력을 인터페이스로 분리
class Flyable(Protocol):
    def fly(self) -> None: ...

class Eagle:
    def fly(self): ...
class Penguin:
    def swim(self): ...
# 펭귄은 Flyable 이 아니다 — 타입으로 표현된다
상속이 적절한 경우이유
진짜 is-a 관계이고 계약이 지켜짐치환 가능
프레임워크가 요구할 때선택지가 없음
템플릿 메서드 (제한적)알고리즘 골격 공유
봉인된 계층 (sealed)모든 하위 타입을 아는 경우
“코드 재사용을 위한 상속”이 문제입니다 — 재사용이 목적이면 합성이나 함수 추출이 맞습니다. 상속은 다형성이 필요할 때만 쓰고, 그마저도 인터페이스로 충분한 경우가 많습니다.
다섯 개를 다 지키는 것이 목표가 아닙니다 — 고치기 무서운 코드를 줄이는 것이 목표입니다.
SE 03

생성 패턴 — 객체를 어떻게 만들까

객체 생성 책임을 분리하면 테스트와 교체가 쉬워집니다. 다만 현대 언어와 DI 컨테이너가 많은 부분을 대신하므로 여전히 쓸모 있는 것만 봅니다.

여전히 유용한 것

패턴쓰는 자리
팩토리 메서드타입에 따라 다른 구현 생성 (파서 · 핸들러)
빌더선택 인자가 많은 객체 · 불변 객체 조립
의존성 주입가장 널리 쓰임 — 테스트 가능성
프로토타입복제가 생성보다 쌀 때 (게임 오브젝트)
오브젝트 풀생성 비용이 큰 자원 (커넥션 · 버퍼)
싱글턴주의 필요 — 아래 참고
# 팩토리 — 등록 기반이 확장에 좋다
HANDLERS = {}

def register(kind):
    def deco(cls):

from functools import wraps

def with_retry(attempts=3):
    def deco(fn):
        @wraps(fn)
        def wrapper(*a, **kw):
            for i in range(attempts):
                try: return fn(*a, **kw)
                except RetryableError:
                    if i == attempts - 1: raise
                    time.sleep(0.1 * 2 ** i)
        return wrapper
    return deco

def with_cache(ttl=60):
    def deco(fn):
        store = {}
        @wraps(fn)
        def wrapper(*a):
            now = time.monotonic()
            if a in store and now < store[a][1]: return store[a][0]
            v = fn(*a); store[a] = (v, now + ttl)
            return v
        return wrapper
    return deco

@with_cache(ttl=300)
@with_retry(attempts=3)

TRANSITIONS = {

    ("review", "approve"): lambda doc: notify_subscribers(doc),
    ("review", "reject"):  lambda doc: notify_author(doc),

def transition(doc, action):
    key = (doc.status, action)
    nxt = TRANSITIONS.get(key)
    if nxt is None:
        raise InvalidTransition(f"{doc.status} 에서 {action} 불가")

# ADR-014: 주문 이벤트 발행에 아웃박스 패턴 사용

## 상태
채택됨 (2026-03-12)

## 맥락
주문 생성 시 DB 저장과 Kafka 발행을 함께 해야 한다.
현재는 저장 후 발행하는데, 발행 실패 시 이벤트가 유실되고 있다.
지난 분기에 3건의 정합성 불일치가 발생했다.

## 결정
아웃박스 테이블을 도입하고 별도 릴레이가 발행한다.

## 근거
- 원자성을 DB 트랜잭션 하나로 확보할 수 있다
- 2PC 는 가용성 저하와 운영 복잡도가 크다
- Debezium CDC 는 인프라 추가 부담이 있어 다음 단계로 미룬다

## 결과
- 최소 한 번 전달 → 소비자를 멱등하게 만들어야 한다
- 릴레이 지연을 모니터링해야 한다 (목표 p99 < 2초)
- 아웃박스 테이블 정리 배치가 필요하다

## 대안
- 2PC: 가용성 저하로 기각
- 발행 후 저장: 유실 방향만 바뀔 뿐
- CDC: 인프라 준비 후 재검토 (ADR-020 예정)
ADR 의 가치는 “왜”를 남기는 것입니다 — 코드는 무엇을 하는지 보여 주지만 왜 그렇게 했는지는 안 보여 줍니다. 1년 뒤에 “이걸 왜 이렇게 했지?”라는 질문에 답할 수 있게 됩니다. 파일로 저장소에 함께 두는 것이 위키보다 오래갑니다.
아키텍처 논쟁의 대부분은 화살표를 그려 보면 정리됩니다.

class Order:                       # 애그리거트 루트
    def __init__(self, id, lines):

        self.status = "draft"

애그리거트 = "한 트랜잭션 안에서 함께 일관성을 지켜야 하는 것들"

규칙
 ① 애그리거트 하나 = 트랜잭션 하나
 ② 다른 애그리거트는 ★ ID 로만 참조 (객체 참조 금지)
 ③ 애그리거트 간 일관성은 최종 일관성으로 (이벤트)
 ④ ★ 작게 유지한다 — 크면 락 경합과 로딩 비용이 커진다

예: 주문
  Order (루트)
    └ OrderLine[]        ← 함께 저장·검증 (같은 애그리거트)
    · customer_id        ← ID 로만 (Customer 는 다른 애그리거트)
    · payment_id         ← ID 로만

✗ 나쁜 예: Customer 안에 모든 Order 를 담기
  · 주문이 1만 개면 고객 하나 로딩에 1만 행
  · 주문 하나 추가에 고객 전체를 잠근다
경계를 정하는 질문
이 규칙이 즉시 지켜져야 하는가예 → 같은 애그리거트
잠깐 어긋나도 되는가예 → 다른 애그리거트 + 이벤트
함께 수정되는 일이 잦은가예 → 같은 애그리거트 후보
크기가 무한히 커질 수 있는가예 → 분리해야 함
“즉시 일관성이 필요한가”가 유일한 기준입니다 — 재고 차감과 주문 확정이 반드시 함께여야 하면 같은 애그리거트이거나 같은 트랜잭션이어야 하고, 몇 초 늦어도 되면 이벤트로 나눌 수 있습니다 (🕸️ 분산 11).

    raise AssertionError("조건이 만족되지 않음")

def get_price(order, feature_flags):
    old = legacy_price(order)
    if not feature_flags.get("new_pricing_shadow"): return old

    try:
        new = new_price(order)
        if abs(new - old) > 0.01:
            log.warning("가격 불일치 order=%s old=%s new=%s", order.id, old, new)
            metrics.inc("pricing_mismatch")
    except Exception:
        log.exception("새 구현 실패")
        metrics.inc("pricing_new_error")

    return new if feature_flags.get("new_pricing_enabled") else old

배포가 두려우면 배포를 미루게 되고, 미루면 한 번에 나가는 변경이 커져 더 위험해집니다. 작게 자주 · 되돌릴 수 있게가 핵심입니다.

  3. 보안 · 품질 — 의존성 스캔 · 시크릿 스캔 · 커버리지 (🔐 12)
  4. 빌드 · 서명 — 이미지 생성 · SBOM · 서명 (🔐 06)
  5. 스테이징 배포 · 스모크 테스트
  6. 프로덕션 배포 — 카나리 → 전체
  7. 배포 후 검증 — 지표 확인 · 자동 롤백 조건
순서가 중요합니다 — 싸고 빠른 검사를 앞에 두면 대부분의 실패를 몇 분 안에 알 수 있습니다. 느린 E2E 를 먼저 돌리면 개발 흐름이 끊깁니다.

SLI · SLO · 에러 버짓

SLI — 측정하는 지표
  "성공한 요청 / 전체 요청"
  "500ms 이내 응답 비율"

SLO — 목표
  "30일 동안 가용성 99.9%"
  = 허용 다운타임 43분

에러 버짓 — 남은 여유
  99.9% 목표에서 현재 99.95% 라면
  버짓의 절반이 남았다

★ 에러 버짓의 쓸모
  · 남으면 → 위험한 변경을 시도해도 된다
  · 소진되면 → 신규 배포를 멈추고 안정화에 집중
  → "속도 vs 안정성" 논쟁을 데이터로 해결한다
SLO 는 사용자 관점으로 정하세요 — “CPU 80% 이하”가 아니라 “주문이 3초 안에 완료된다”. 내부 지표는 원인 분석용이고, SLO 는 사용자가 겪는 것이어야 합니다.
