구조는
무엇이 함께
바뀌는가로 나눈다

언어마다 폴더 이름은 다르지만 왜 그렇게 나누는지는 같습니다. 바꿀 때 덜 건드리고, 처음 보는 사람이 덜 헤매고, 여러 사람이 서로를 덜 기다리게 하려는 것입니다. 이 탭은 특정 언어가 아니라 구조의 원리를 봅니다 — 응집과 결합, 의존 방향의 원칙, 계층형과 기능별, 헥사고날 · 클린, UI 패턴, 모듈러 모놀리스와 마이크로서비스, 이벤트 · 파이프라인 · 플러그인. 그리고 앱 유형마다 무엇이 권장되는지 한 장으로 정리한 뒤 자바 · 코틀린 · 파이썬 · TS · C# · C++ · Rust · C · DB · 서버 가이드의 구조 탭으로 연결합니다. 마지막은 규칙을 기계로 지키는 법과, 결정을 기록하며 구조를 조금씩 옮기는 법입니다.

STR 01

구조는 왜 필요한가 — "무엇이 함께 바뀌나"로 나누기

구조가 없어도 프로그램은 돕니다. 구조가 줄여 주는 것은 실행 비용이 아니라 사람의 비용 세 가지입니다 — 변경 비용(하나 고칠 때 몇 군데를 건드리나), 이해 비용(새 사람이 몇 파일을 읽어야 하나), 조율 비용(여러 사람이 서로를 얼마나 기다리나). 응집도와 결합도의 정의는 SE 01 에 있으니, 여기서는 그 자를 폴더와 모듈을 자르는 칼로 씁니다.

같은 앱 — 함께 바뀌는 것끼리 모은 모양

shop/
├─ orders/          # 주문이 바뀌면 여기만 — 화면·규칙·저장이 한 폴더
│  ├─ api            #   요청을 받는 입구
│  ├─ rules          #   할인 · 취소 가능 여부 같은 업무 규칙
│  └─ store          #   저장 방식
├─ members/         # 회원 기능 — orders 와는 공개 입구로만 대화
├─ billing/         # 결제 — 외부 PG 가 바뀌면 여기만
├─ shared/          # 진짜 공통만: 금액 · 시간 · 에러 타입
└─ main             # 조립 — 무엇을 무엇에 꽂을지 정하는 한 곳
공통 폐쇄 원칙(CCP) — "같은 이유로, 같은 때에 바뀌는 것을 한 묶음에". 클래스 수준의 단일 책임 원칙(SRP)을 패키지 크기로 키운 것입니다.

자를 때 쓰는 질문 다섯

질문답이 "예"면
이 둘은 항상 같이 커밋되나?같은 폴더로 — 떨어져 있으면 변경이 흩어집니다
이 둘은 바뀌는 이유가 다른가?나눕니다 — 규칙(업무)과 기술(DB · HTTP)이 대표적
이걸 쓰는 쪽이 전부 다 필요한가?아니면 쪼갭니다 — 공통 재사용 원칙(CRP)
다른 팀이 이걸 자주 고치나?경계를 그어 소유자를 정합니다
이름이 utils · common 인가?"갈 곳 없는 것들의 창고" — 원래 주인에게 돌려보냅니다
규모별 진화 — 신호가 왔을 때만 한 칸씩. 숫자는 경험칙이지 규격이 아닙니다.

STR 02

의존 방향의 원칙 — 안정된 쪽으로 기대고, 고리는 만들지 않는다

나누기만 하면 끝이 아닙니다. 나눈 덩어리 사이의 화살표 방향이 구조의 품질을 정합니다. 로버트 C. 마틴이 정리한 패키지 원칙 셋 — ADP(순환 금지) · SDP(안정된 쪽으로 의존) · SAP(안정할수록 추상적으로) — 과 의존성 역전(DIP) 하나면 대부분의 구조 논쟁을 화살표로 정리할 수 있습니다.

의존 그래프 — 모든 화살표가 안정된 쪽을 향하면 고리는 생길 수 없습니다.

원칙 넷 — 실무 언어로

원칙실무 문장어기면
ADP
비순환 의존		패키지 사이에 고리가 없어야 합니다하나 고치면 고리 전체를 다시 빌드 · 배포
SDP
안정 의존		자주 바뀌는 쪽이 잘 안 바뀌는 쪽에 기댑니다공용 코드가 화면 때문에 매주 바뀜
SAP
안정 추상		많이 기대지는 곳일수록 인터페이스 · 값 타입 위주로굳은 구체 코드 = 고칠 수 없는 코드
DIP
의존성 역전		업무 규칙이 약속(인터페이스)을 정의하고 기술 코드가 그걸 구현규칙이 DB 드라이버를 import

I 와 순환을 직접 세어 보기 (파이썬 3.13)

deps = {
    "web":     ["orders", "billing"],
    "batch":   ["billing"],
    "orders":  ["billing", "core"],
    "billing": ["core"],
    "core":    [],
}
def instability(deps):
    ca = {p: 0 for p in deps}            # 들어오는 의존
    for targets in deps.values():
        for t in targets:
            ca[t] += 1
    return {p: round(len(deps[p]) / (ca[p] + len(deps[p])), 2)
            if ca[p] + len(deps[p]) else 0.0 for p in deps}

print(instability(deps))
# {'web': 1.0, 'batch': 1.0, 'orders': 0.67,
#  'billing': 0.25, 'core': 0.0}
# core 에 "web" 을 추가하면 DFS 가 고리를 찾습니다:
# ['web', 'orders', 'billing', 'core', 'web']

정리 — 화살표는 안정된 쪽으로만(SDP), 고리 없이(ADP), 많이 기대지는 곳은 추상적으로(SAP). 방향이 틀리면 인터페이스를 쓰는 쪽으로 옮겨 뒤집습니다(DIP).
STR 03

계층형 vs 기능별 — 가로로 자를까, 세로로 자를까

같은 앱도 두 방식으로 자를 수 있습니다. 계층형(package by layer)은 기술 역할로 가로로 — controllers · services · repositories. 기능별(package by feature · vertical slice)은 업무 기능으로 세로로 — orders · members · billing. 처음엔 계층형이 깔끔해 보이지만, 기능이 늘수록 기능 하나 고치는 데 폴더 네 개를 오가게 됩니다.

계층형 — 기술 역할로 가로 분할

src/
├─ controllers/   # 모든 기능의 HTTP 입구
│  ├─ OrderController
│  └─ MemberController
├─ services/      # 모든 기능의 업무 로직
│  ├─ OrderService
│  └─ MemberService
├─ repositories/  # 모든 기능의 저장
└─ models/        # 모든 엔티티 · DTO 가 한곳에
# 장점: 처음 보는 사람도 "역할"로 찾음
# 단점: 기능이 20개면 각 폴더에 파일 20개+

기능별 — 업무 기능으로 세로 분할

src/
├─ orders/        # 주문의 모든 것
│  ├─ order-controller
│  ├─ order-service
│  ├─ order-repo
│  └─ index       # 밖에 공개하는 것만 (입구)
├─ members/
├─ billing/
└─ shared/        # 기능 이름이 안 들어간 것만
# 장점: 변경이 한 폴더 · 지우기도 폴더째
# 단점: 공통 코드 위치를 정하는 규칙이 필요
좌우 대조 — 변경이 닿는 폴더 수가 두 방식의 차이 전부입니다.

실무 기본값 — 기능이 1차, 계층이 2차 🟡 중급

상황권장
CRUD 위주 · 기능 몇 개계층형도 충분 — 단순함이 이김
기능 5개 이상 · 사람 2명 이상기능별, 기능 폴더 안에서 필요하면 계층
기능 안의 규칙이 두꺼움기능 폴더 안을 domain · application · infra 로 (STR 04)
프런트엔드기능별(features/) + 공용 UI(components/) 조합이 흔함
기능별의 함정은 기능끼리 내부를 직접 import 하는 것입니다. 기능마다 공개 입구 하나(index · 공개 서비스 · internal 가시성)를 두고 그것만 쓰게 합니다. 
// orders/index.ts — 이 기능이 밖에 내보내는 것의 전부
export { placeOrder, cancelOrder } from "./order-service";
export type { OrderSummary } from "./types";
// order-repo, 할인 계산 같은 내부는 내보내지 않음

// members/… 에서
import { placeOrder } from "../orders";            // ✓ 입구로
import { applyDiscount } from "../orders/discount"; // ✗ 내부 직접
// ✗ 줄은 린트 규칙으로 막습니다 (STR 09)
언어별 "입구" 도구: 자바 package-private · 코틀린/C# internal · Rust pub(crate) · TS index.ts + 린트 · 파이썬 __all__ 과 밑줄 관례.
정리 — 작은 앱은 계층형도 괜찮지만, 기능이 늘면 기능별로 1차 분할하고 기능 안에서 필요할 때만 계층을 둡니다. 기능 사이는 공개 입구로만.
STR 04

헥사고날 · 클린 · 어니언 — 도메인을 가운데, 의존은 안쪽으로

세 이름의 공통 핵심 — 업무 규칙이 프레임워크 · DB 를 모르게 하고 의존은 안쪽으로만 흐르게 한다 — 과 "흔한 구조 vs 뒤집은 구조" 그림은 SE 06 에 있습니다. 여기서는 셋이 어디가 다른지, 폴더로 옮기면 어떤 모양인지, 그리고 언제 과설계가 되는지만 봅니다.

동심원 — 반지름이 변경 빈도. 바깥은 갈아 끼우고 안쪽은 오래 삽니다.

셋의 차이 — 강조점이 다를 뿐

이름처음 낸 사람강조하는 것
헥사고날
(포트와 어댑터)		앨리스터 코번 · 2005안과 밖의 대칭 — 들어오는 쪽(HTTP · CLI · 테스트)도 나가는 쪽(DB · 메일)도 전부 어댑터
어니언제프리 팔레르모 · 2008겹 — 도메인 모델 · 도메인 서비스 · 앱 서비스 · 인프라
클린로버트 C. 마틴 · 2012의존성 규칙이라는 한 문장 + 유스케이스 단위의 경계
포트는 안쪽이 정의한 인터페이스, 어댑터는 그걸 바깥 기술로 구현하거나 호출하는 코드입니다. "들어오는(driving) 포트"는 유스케이스 자체, "나가는(driven) 포트"는 저장 · 알림 같은 약속입니다.

폴더로 옮기면 — 기능 하나 안에서

orders/
├─ domain/            # Order · Money · 취소 규칙 — 순수 코드
├─ application/       # cancel_order() 유스케이스
│  └─ ports.py        #   OrderStore (나가는 포트) — 안쪽 소유
├─ adapters/
│  ├─ inbound/        # HTTP 라우터 · CLI · 메시지 소비자
│  └─ outbound/       # PostgresOrderStore · SmtpNotifier
└─ wiring.py          # 어떤 어댑터를 꽂을지 — 조립은 한 곳
# import 방향: adapters → application → domain (반대 금지)

포트 하나, 어댑터 둘 — 테스트가 쉬워지는 이유 🟡 중급

from dataclasses import dataclass
from typing import Protocol

@dataclass
class Order:                          # domain — 아무것도 import 안 함
    id: str
    amount: int
    status: str = "NEW"
    def cancel(self) -> None:
        if self.status == "SHIPPED":
            raise ValueError("배송된 주문은 취소할 수 없습니다")
        self.status = "CANCELLED"

class OrderStore(Protocol):           # 나가는 포트 — 안쪽이 정의
    def get(self, order_id: str) -> Order: ...
    def put(self, order: Order) -> None: ...

def cancel_order(store: OrderStore, order_id: str) -> Order:
    order = store.get(order_id)       # 유스케이스 — DB 를 모름
    order.cancel()
    store.put(order)
    return order
class MemoryStore:                    # 어댑터 ① — 테스트용
    def __init__(self, *orders: Order):
        self.rows = {o.id: o for o in orders}
    def get(self, order_id: str) -> Order:
        return self.rows[order_id]
    def put(self, order: Order) -> None:
        self.rows[order.id] = order

store = MemoryStore(Order("A1", 12000),
                    Order("B2", 5000, "SHIPPED"))
print(cancel_order(store, "A1").status)   # CANCELLED
cancel_order(store, "B2")

STR 05

UI 패턴 — MVC · MVP · MVVM · 단방향 데이터 흐름

화면이 있는 앱의 어려움은 상태가 여러 곳에서 바뀐다는 데 있습니다. 클릭 · 서버 응답 · 타이머가 같은 화면을 동시에 건드립니다. UI 패턴들은 전부 "화면(View)에서 로직과 상태를 빼내서 어디에 둘까"에 대한 답이고, 최근의 답은 상태는 한곳, 흐름은 한 방향입니다.

단방향
(Flux · Redux · Elm)		상태는 스토어 하나, 바꾸는 길은 액션 → 리듀서 하나상태 → 렌더 (항상 같은 방향)

같은 생각, 두 언어 — 리듀서와 StateFlow 🟡 중급

// TS — 순수 함수 리듀서 (Redux · useReducer 공통)
type State = { items: string[]; filter: "all" | "done" };
type Action =
  | { type: "added"; item: string }
  | { type: "filtered"; filter: State["filter"] };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "added":
      return { ...state, items: [...state.items, action.item] };
    case "filtered":
      return { ...state, filter: action.filter };
  }
}
// 화면: dispatch({ type: "added", item: "우유" })
// Kotlin — ViewModel 이 상태 하나를 노출 (Compose 가 구독)
data class CartState(val items: List<String> = emptyList())

class CartViewModel(private val repo: CartRepository) : ViewModel() {
    private val _state = MutableStateFlow(CartState())
    val state: StateFlow<CartState> = _state.asStateFlow()

    fun onAdd(item: String) {                 // 이벤트는 위로
        _state.update { it.copy(items = it.items + item) }
        viewModelScope.launch { repo.save(item) }
    }
}
// 화면: val s by vm.state.collectAsStateWithLifecycle()

STR 06

모듈러 모놀리스 → 마이크로서비스 — 경계를 먼저, 분리는 나중에

모놀리스와 마이크로서비스의 비교표와 "분산 모놀리스가 최악"이라는 조언은 SE 06 에 있습니다. 여기서는 그 사이의 실무 경로 — 경계는 어떻게 찾나(바운디드 컨텍스트), 언제 쪼개나(조직 · 배포 · 확장 신호), 분산은 무엇을 비용으로 내나, 그리고 다시 합친 사례를 봅니다.

사분면 — 위로 먼저(경계), 오른쪽은 나중(배포). 오른쪽 아래가 분산 모놀리스입니다.

경계 찾기 — 같은 단어가 다른 뜻이 되는 곳

"상품"이뜻하는 것
카탈로그에서이름 · 설명 · 사진 · 카테고리
주문에서주문 시점의 가격 · 수량 (나중에 값이 바뀌어도 고정)
배송에서무게 · 부피 · 위험물 여부
DDD(에릭 에번스, 2003)의 바운디드 컨텍스트는 "한 단어가 한 뜻으로만 쓰이는 범위"입니다. 거대한 Product 클래스 하나 대신 컨텍스트마다 자기 모델을 두고, 경계에서는 ID 와 이벤트로만 주고받습니다. 남의 모델이 내 안으로 새지 않게 막는 번역층을 부패 방지 계층(ACL)이라고 부릅니다.

STR 07

이벤트 기반 · 파이프라인 · 플러그인 — 호출 대신 다른 연결 방식

계층과 동심원은 "누가 누구를 부르나"의 구조입니다. 어떤 문제는 아예 부르지 않는 구조가 더 맞습니다 — 일이 일어났다고 알리기만 하거나(이벤트), 앞 단계의 결과를 흘려보내기만 하거나(파이프라인), 본체가 모르는 기능을 꽂아 넣거나(플러그인). 로그를 시스템의 중심축으로 두는 이벤트 소싱 · CQRS · CDC 는 LOG 06 에서 다룹니다.

허브 — 발행자와 구독자가 서로를 모르는 것이 이 구조의 이득이자 디버깅의 어려움입니다.

STR 09

구조 규칙을 기계로 지키기 — 리뷰가 아니라 빌드가 막게

"domain 은 infra 를 import 하지 않는다"는 규칙은 문서에 적어 두면 석 달 안에 깨집니다. 급한 날 한 줄이면 되니까요. 규칙은 어기면 빌드가 실패하게 만들어야 지켜집니다. 파이썬 import-linter 예는 SE 06 에 있으니, 여기서는 강제 수단의 사다리와 언어별 도구 이름을 정리합니다.

사다리 — 싼 것부터 기계에 맡기고, 정말 중요한 경계는 빌드 모듈로 굳힙니다.

자바 — ArchUnit (JUnit 5)

@AnalyzeClasses(packages = "com.example.shop")
class ArchitectureTest {

    @ArchTest
    static final ArchRule layers = layeredArchitecture()
        .consideringAllDependencies()
        .layer("Web").definedBy("..web..")
        .layer("Application").definedBy("..application..")
        .layer("Domain").definedBy("..domain..")
        .whereLayer("Web").mayNotBeAccessedByAnyLayer()
        .whereLayer("Application").mayOnlyBeAccessedByLayers("Web")
        .whereLayer("Domain").mayOnlyBeAccessedByLayers("Application", "Web");

    @ArchTest   // 기능 패키지 사이 고리 금지 (ADP)
    static final ArchRule noCycles =
        slices().matching("com.example.shop.(*)..").should().beFreeOfCycles();
}

TS — dependency-cruiser

// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    { name: "no-circular", severity: "error",
      from: {}, to: { circular: true } },
    { name: "domain-is-pure", severity: "error",
      from: { path: "^src/domain" },
      to:   { path: "^src/(infra|ui)" } },
    { name: "no-feature-internals", severity: "error",
      from: { path: "^src/features/([^/]+)/" },
      to:   { path: "^src/features/([^/]+)/internal/",
              pathNot: "^src/features/$1/" } },
  ],
};
// npx depcruise src --config .dependency-cruiser.cjs
세 번째 규칙은 "다른 기능의 internal 폴더 import 금지" — $1 은 from 쪽에서 잡은 기능 이름입니다. CI 에서 돌리면 PR 단계에서 막힙니다.

STR 10

결정 기록과 진화 — ADR · 스트랭글러 · 처음엔 단순하게

구조는 한 번 정하고 끝나는 것이 아니라 계속 옮겨 가는 것입니다. 옮기려면 두 가지가 필요합니다 — 왜 지금 모양이 됐는지의 기록(ADR), 그리고 서비스를 멈추지 않고 조금씩 옮기는 방법(스트랭글러). ADR 실제 예(아웃박스 도입)는 SE 06 에 있으니, 여기서는 운영 규칙과 템플릿만 봅니다.

ADR 은 저장소 안에, 번호 순으로

docs/adr/
├─ 0001-record-architecture-decisions.md   # "ADR 을 쓰기로 함" 부터
├─ 0002-modular-monolith.md                # 채택
├─ 0003-orders-hexagonal.md                # 채택
├─ 0007-use-graphql.md                     # 대체됨 → 0012
├─ 0012-back-to-rest-for-public-api.md     # 채택 (0007 을 대체)
└─ template.md
# 규칙
#  · 채택된 ADR 은 고치지 않는다 — 바뀌면 새 ADR 이 대체
#  · 코드와 같은 PR 로 — 리뷰에서 "왜"까지 같이 본다
형식은 마이클 나이가드(2011)의 제목 · 상태 · 맥락 · 결정 · 결과 다섯 칸이 출발점입니다. 선택지 비교를 더 자세히 쓰는 MADR 같은 변형도 있습니다.

스트랭글러 — 새 구조로 조금씩 옮기기 🟡 중급

마틴 파울러가 이름 붙인 "교살자 무화과" 패턴
(숙주 나무를 감싸며 자라 결국 대신 서는 덩굴)

① 앞에 입구(프록시 · 라우터 · 파사드)를 세운다
② 기능 하나를 새 구조로 다시 만든다
③ 입구에서 그 기능의 요청만 새 쪽으로 보낸다
④ 문제없으면 옛 코드를 지운다 — 다음 기능으로
⑤ 옛 시스템이 빈 껍데기가 되면 입구째 정리

★ 코드 안에서도 같습니다
   옛 OrderService 앞에 인터페이스를 세우고
   새 구현으로 하나씩 옮긴 뒤 옛 클래스를 지운다
# nginx — 입구에서 경로별로 나눈다
location /api/orders/ {
    proxy_pass http://orders_new;    # 옮긴 기능
}
location / {
    proxy_pass http://legacy_app;    # 나머지는 그대로
}
빅뱅 재작성은 거의 항상 늦고 기능이 빠집니다 — 옛 시스템의 숨은 규칙(버그처럼 보이는 정상 동작)까지 다시 찾아야 하기 때문입니다. 스트랭글러는 매 단계가 배포 가능하고 되돌릴 수 있다는 것이 핵심입니다.
결정 흐름도 — 질문은 셋, 기본 답은 "유지". 바꿀 이유가 신호로 확인될 때만 움직입니다.

"처음엔 단순하게" — 한 장 요약 🟢 기초

원칙실무 문장
필요할 때 만든다 (YAGNI)"나중에 쪼갤 수도 있으니" 지금 서비스 · 모듈 · 포트를 미리 만들지 않습니다
경계가 먼저, 분리는 나중폴더 · 공개 입구로 경계를 긋고 → 검증되면 빌드 모듈 → 신호가 오면 서비스
방향은 처음부터 지킨다폴더 수는 적어도 의존 방향(업무 규칙 → 기술 금지)은 첫날부터 — 나중에 뒤집기가 가장 비쌉니다
되돌릴 수 있게쪼개는 결정은 합칠 수 있게, 기술 선택은 어댑터 뒤에
규칙은 기계에, 이유는 ADR 에무엇을 지킬지는 테스트가, 왜 그런지는 기록이 기억합니다
정리 — 결정은 ADR 로 저장소에, 큰 이동은 스트랭글러로 조금씩, 기본값은 단순하게 시작해 신호가 올 때만 한 칸씩. 의존 방향만은 첫날부터 지킵니다.
