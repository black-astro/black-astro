RTOS 는 그 문제를 태스크 · 우선순위 · 블로킹 큐로 풉니다 — 서버 개발자에게 익숙한 스레드 · 락 · BlockingQueue 를 메모리 128KB, MMU 없는 칩에 맞게 줄여 놓은 것이라고 보면 됩니다. 이 탭은 FreeRTOS 커널을 STM32F446RE 에서 실무로 쓰는 법을 다룹니다: 태스크와 스케줄러, 큐 · 세마포어 · 뮤텍스, 인터럽트와의 연결, 메모리 설계, 동시성 버그 잡기, 저전력, 그리고 센서 → 처리 → 통신 3태스크 시스템 설계까지. 이 탭을 마치면 우선순위 역전과 ISR 우선순위 설정을 틀리지 않는 RTOS 펌웨어를 설계할 수 있습니다.

RTOS 01

왜 RTOS 인가 — 슈퍼루프가 무너지는 순간

RTOS 는 "빠르게" 만드는 도구가 아닙니다. 정해진 시간 안에 반드시 반응하게 만드는 도구입니다. CPU 는 하나인데 할 일은 여럿일 때, 무엇을 먼저 할지 규칙으로 정해 두는 것 — 그게 실시간 운영체제의 전부입니다.

슈퍼루프는 모든 일이 같은 우선순위입니다 — RTOS 는 급한 일이 덜 급한 일을 밀어내게(선점) 해 줍니다.

슈퍼루프 — 처음엔 이걸로 충분합니다

int main(void) {
    HAL_Init();
    SystemClock_Config();          // 180 MHz
    MX_GPIO_Init(); MX_I2C1_Init(); MX_USART2_UART_Init();

    for (;;) {
        read_sensor_blocking();    // I2C 폴링 8 ms — CPU 는 기다리기만
        update_display();          // 12 ms
        uart_send_status();        // HAL_UART_Transmit 폴링 6 ms
        if (HAL_GPIO_ReadPin(B1_GPIO_Port, B1_Pin) == GPIO_PIN_RESET) {
            on_button();           // ★ 한 바퀴(26 ms)에 한 번만 봅니다
        }
    }
}
무너지는 신호 세 가지 — ① 함수 하나가 길어지면 나머지 전부가 같이 늦어집니다. ② "UART 는 5ms 마다, 화면은 50ms 마다"처럼 주기가 다른 일이 섞이면 카운터와 플래그가 폭발합니다. ③ 기다리는 동안(I2C·UART 폴링) CPU 가 다른 일을 못 합니다. 이걸 인터럽트 + 상태 머신으로 끝까지 버티는 방법도 있지만(C 실전 탭 c22), 코드가 읽기 어려워집니다.

RTOS — 일마다 태스크 하나, 급한 순서는 숫자로

#include "FreeRTOS.h"
#include "task.h"

static void ButtonTask(void *arg);    // 우선순위 3 (가장 급함)
static void SensorTask(void *arg);    // 우선순위 2
static void DisplayTask(void *arg);   // 우선순위 1
static TaskHandle_t s_btnTask;        // ISR 이 깨울 때 쓸 핸들

int main(void) {
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init(); MX_I2C1_Init(); MX_USART2_UART_Init();

    //          함수         이름    스택(워드) 인자  우선순위 핸들
    xTaskCreate(ButtonTask,  "btn",  256,  NULL, 3, &s_btnTask);
    xTaskCreate(SensorTask,  "sens", 384,  NULL, 2, NULL);
    xTaskCreate(DisplayTask, "disp", 512,  NULL, 1, NULL);

    vTaskStartScheduler();            // ★ 정상이면 여기서 돌아오지 않습니다
    for (;;) { }                      // 힙이 모자라 Idle 태스크를 못 만들 때만 도달
}

static void ButtonTask(void *arg) {
    (void)arg;
    for (;;) {
        // EXTI 인터럽트가 vTaskNotifyGiveFromISR 로 깨울 때까지 잠듭니다 (r07)
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        on_button();                  // 눌린 뒤 수 µs 안에 실행
    }
}
서버 개발에 빗대면 — 태스크는 스레드, ulTaskNotifyTake 는 BlockingQueue.take() 처럼 깨울 때까지 CPU 를 0% 쓰며 잠드는 호출입니다. 차이는 하나 — 자바 스레드 스케줄러는 "공평"하려 애쓰지만 RTOS 는 무조건 우선순위가 높은 쪽을 돌립니다. 공평함 대신 예측 가능성을 삽니다.

실시간의 뜻 — 하드 · 펌 · 소프트 🟡 중급

한 시스템 안에 세 등급이 섞여 있습니다 — 우선순위는 이 등급 순서로 매깁니다.

"실시간" 에 대한 흔한 오해

오해사실
실시간 = 빠르다최악의 경우가 보장된다. 평균 1µs·가끔 50ms 보다 항상 5ms 가 낫습니다
RTOS 를 쓰면 실시간이 된다우선순위 설계가 틀리면 RTOS 위에서도 마감을 놓칩니다(r06 · r11)
CPU 가 빠르면 해결된다바쁜 대기(while 폴링)는 클럭을 올려도 남의 시간을 계속 먹습니다
리눅스는 실시간이 안 된다PREEMPT_RT 가 6.12 커널에 들어가 수십 µs 지터까지 가능 — 다만 MMU 있는 큰 칩이 필요
지터(jitter) — 같은 일이 매번 시작되는 시각의 흔들림입니다. 서버의 p99 지연과 같은 감각입니다. RTOS 의 가치는 평균이 아니라 p100(최악값)을 작고 일정하게 만드는 데 있습니다.

실무에선 이렇게 — RTOS 도입을 결정하는 질문 🔴 실무

체크리스트 — 셋 이상이면 RTOS

□ 주기가 서로 다른 일이 3개 이상이다     (1ms 제어 · 10ms 센서 · 1s 로그)
□ 기다리는 동안 다른 일을 해야 한다       (Wi-Fi 응답 대기 중에도 모터 제어)
□ 마감이 다른 일이 섞여 있다             (하드 + 소프트)
□ 통신 스택을 붙인다                     (lwIP · USB · BLE — 대부분 RTOS 를 전제)
□ 여러 사람이 모듈을 나눠 개발한다        (태스크 = 소유권 경계)
□ RAM 이 32KB 이상 남는다               (태스크당 스택 0.5~2KB)
통신 스택이 결정타인 경우가 많습니다 — lwIP 의 sys_arch, ST 의 USB 미들웨어, Wi-Fi 모듈 SDK 는 대부분 FreeRTOS 위에서 도는 것을 기본으로 씁니다. 베어메탈 모드도 있지만 기능이 제한됩니다.

RTOS 02

FreeRTOS 구조와 도입 — C 파일 몇 개와 설정 헤더 하나

FreeRTOS 는 라이브러리입니다. 별도의 OS 이미지가 아니라 내 펌웨어에 같이 컴파일되는 C 파일 몇 개이고, 동작은 FreeRTOSConfig.h 한 파일로 정합니다. 어디가 칩마다 바뀌고 어디가 고정인지 알면 도입이 무섭지 않습니다.

FreeRTOS 의 이식성은 포트 계층 두 파일에 몰려 있습니다 — 나머지는 어느 칩에서나 같은 C 코드입니다.

FreeRTOSConfig.h — F446RE 에 맞춘 핵심 항목 🟡 중급

#define FREERTOS_CONFIG_H
#include <stdint.h>
extern uint32_t SystemCoreClock;              // CMSIS 가 180000000 으로 갱신

#define configUSE_MUTEXES                 1
#define configUSE_RECURSIVE_MUTEXES       1

#define configSUPPORT_STATIC_ALLOCATION   1

#define configCHECK_FOR_STACK_OVERFLOW    2
#define configUSE_MALLOC_FAILED_HOOK      1
#define configASSERT(x) do { if ((x) == 0) { taskDISABLE_INTERRUPTS(); for (;;) { } } } while (0)

  #define configPRIO_BITS  __NVIC_PRIO_BITS     // = 4
#else

#endif

#define configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY  5

    (configLIBRARY_LOWEST_INTERRUPT_PRIORITY << (8 - configPRIO_BITS))        // 0xF0

#define xPortPendSVHandler  PendSV_Handler
#define xPortSysTickHandler SysTick_Handler   // 직접 이식할 때만 (CubeMX + CMSIS v2 는
                                              //  cmsis_os2.c 가 SysTick_Handler 를 제공)

/* ── 선택적 API 포함 ── */
#define INCLUDE_vTaskDelay                    1
#define INCLUDE_vTaskDelete                   1   // vTaskDelete(NULL) (r03) — 기본값 0
#define INCLUDE_xTaskDelayUntil               1
#define INCLUDE_vTaskSuspend                  1   // portMAX_DELAY 무한 대기에 필요
#define INCLUDE_uxTaskGetStackHighWaterMark   1

각 항목을 고르는 기준

항목기준
configTICK_RATE_HZ1000 이 무난. 높이면 tick 인터럽트 부담 ↑, 낮추면 지연 해상도 ↓
configMAX_PRIORITIES실제로 쓰는 수준만큼(5~8). 클수록 RAM 조금 ↑
configMINIMAL_STACK_SIZEIdle 태스크 스택. 워드 단위(Cortex-M 에서 ×4 바이트)
configTOTAL_HEAP_SIZEF446RE SRAM 128KB 중 동적 객체 몫. 정적 할당만 쓰면 0 가능(r10)
configCHECK_FOR_STACK_OVERFLOW개발 중 2. 문맥 전환 때 검사 — 비용은 작습니다
configASSERT절대 빼지 마세요. ISR 우선순위 실수를 잡는 유일한 장치
configMAX_SYSCALL_…이 값보다 숫자가 작은(더 급한) ISR 은 FreeRTOS API 금지
왜 시프트(<< 4)를 하나 — Cortex-M 의 우선순위 레지스터는 8비트인데 STM32F4 는 위쪽 4비트만 씁니다. HAL 함수(HAL_NVIC_SetPriority(irq, 5, 0))는 0~15 를 받아 알아서 시프트하지만, 커널은 BASEPRI 레지스터에 날값을 쓰므로 미리 시프트한 0x50 이 필요합니다.
NVIC 우선순위 그룹 — 4비트를 전부 선점 우선순위로 써야 합니다(NVIC_PRIORITYGROUP_4, 서브 우선순위 0비트). HAL_Init() 이 기본으로 이렇게 설정하니 바꾸지 마세요. 커널이 configASSERT 로 검사합니다.

CubeMX 로 켤 때 — HAL 타임베이스를 TIM6 으로 옮기는 이유 🔴 실무

CubeMX 설정 순서

1) System Core → SYS → Timebase Source : SysTick → TIM6   ★
2) Middleware → FREERTOS → Interface : CMSIS_V2
   · Config parameters : TICK_RATE 1000, MAX_PRIORITIES 56(CMSIS 기본)
   · USE_PREEMPTION Enabled, CHECK_FOR_STACK_OVERFLOW Option2
   · Memory Management scheme : heap_4
3) Tasks and Queues 탭에서 태스크 · 큐를 만들거나, 코드로 직접 생성
4) NVIC 탭 : FreeRTOS API 를 부르는 IRQ 는 Preemption Priority 5 이상
   (CubeMX 가 "Uses FreeRTOS functions" 체크 시 5 미만을 막아 줍니다)
/* CubeMX 가 main.c 에 생성 — HAL 의 1 ms 시계는 이제 TIM6 이 돌립니다 */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
    if (htim->Instance == TIM6) {
        HAL_IncTick();
    }
}

SysTick 하나를 둘이 쓰면 생기는 일

주인SysTick 에 바라는 것
FreeRTOStick 인터럽트를 가장 낮은 우선순위(15)로 · 스케줄러가 멈추면 같이 멈춰도 됨 · tickless 때 재설정

요구가 충돌합니다 — 커널이 SysTick 을 최저 우선순위로 낮추면, 그보다 급한 ISR 안에서 HAL 타임아웃을 기다릴 때 tick 이 영영 안 올라 멈춥니다. tickless idle(r12)은 SysTick 을 멈추고 다시 프로그램하므로 HAL 시계도 같이 어긋납니다. 그래서 SysTick 은 커널에 주고, HAL 은 남는 기본 타이머 TIM6/TIM7 로 보냅니다. CubeMX 도 그대로 두면 경고를 띄웁니다.
CMSIS-RTOS v2 래퍼는 무엇인가 — cmsis_os2.c 가 osThreadNew 같은 Arm 표준 이름을 FreeRTOS 함수로 옮겨 주는 얇은 층입니다. 이 탭은 네이티브 API 를 기본으로 하고 각 섹션에 대응표를 둡니다. 두 API 는 한 프로젝트에서 섞어 써도 됩니다 — 결국 같은 커널 객체입니다.
정리 — 커널 C 파일 + 포트(ARM_CM4F) + 힙 하나 + FreeRTOSConfig.h. CubeMX 를 쓰면 HAL 타임베이스를 TIM6 으로 옮기는 것부터 합니다.
RTOS 03

태스크 — 끝나지 않는 함수 하나와 그 스택

태스크는 자기 스택과 우선순위를 가진 무한 루프 함수입니다. 스레드와 거의 같지만 세 가지가 다릅니다 — 스택 크기를 내가 정확히 정해야 하고, 절대 return 하지 않으며, 우선순위 숫자가 클수록 급합니다.

대부분의 태스크는 대부분의 시간을 Blocked 로 보냅니다 — 그래야 낮은 우선순위에게 차례가 갑니다.

xTaskCreate — 인자 하나하나

BaseType_t xTaskCreate(
    TaskFunction_t        pxTaskCode,    // void f(void *)
    const char * const    pcName,        // 디버거 · 트레이스용 이름
    const configSTACK_DEPTH_TYPE uxStackDepth, // ★ 워드 수 (바이트 아님)
    void * const          pvParameters,  // 태스크에 넘길 포인터
    UBaseType_t           uxPriority,    // 0 ~ configMAX_PRIORITIES-1
    TaskHandle_t * const  pxCreatedTask  // 핸들을 받을 곳 (NULL 가능)
);   // 반환: pdPASS 또는 errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY

static TaskHandle_t s_sensor;

void app_start(void) {
    BaseType_t ok = xTaskCreate(SensorTask, "sensor",
                                384,          // 384 워드 = 1536 바이트
                                NULL, 2, &s_sensor);
    configASSERT(ok == pdPASS);               // 힙 부족을 조용히 넘기지 않기
}
워드 vs 바이트 — Cortex-M 에서 StackType_t 는 uint32_t 이므로 256 = 1024 바이트입니다. ESP-IDF 의 FreeRTOS 는 이 인자를 바이트로 받고, CMSIS v2 의 osThreadAttr_t.stack_size 도 바이트입니다. 코드를 옮길 때 4배 차이로 스택이 넘치거나 RAM 이 바닥납니다.

태스크 함수의 모양 — 절대 return 하지 않습니다

static void SensorTask(void *arg) {
    (void)arg;
    sensor_init();                        // ① 한 번만 하는 준비

    for (;;) {                            // ② 영원히
        int16_t t = sensor_read_temp();
        publish(t);
        vTaskDelay(pdMS_TO_TICKS(100));   // ③ 반드시 어딘가에서 Blocked
    }

}

/* 일을 마치고 사라져야 하는 태스크라면 — return 대신 */
static void OneShotTask(void *arg) {
    (void)arg;
    do_calibration();
    vTaskDelete(NULL);                    // 자기 자신 삭제 (TCB · 스택은 Idle 이 회수)

return 하면 어떻게 되나 — 태스크 함수의 복귀 주소는 포트가 넣어 둔 prvTaskExitError() 입니다. 여기서 configASSERT 에 걸려 멈춥니다. 자바의 run() 이 끝나면 스레드가 정리되는 것과 달리, FreeRTOS 는 "실수로 끝났다"고 봅니다.

RTOS 04

스케줄러 — 가장 높은 Ready 태스크가 돈다, 규칙은 이것 하나

FreeRTOS 스케줄러의 규칙은 놀랄 만큼 단순합니다. Ready 중 우선순위가 가장 높은 태스크가 Running, 같은 우선순위끼리는 tick 마다 번갈아. 이 두 줄과 "언제 다시 고르나"만 알면 모든 타이밍 그림을 손으로 그릴 수 있습니다.

스케줄러는 tick · 블로킹 해제 · ISR 의 양보 요청 때 다시 고릅니다 — 고르는 기준은 언제나 우선순위 숫자 하나입니다.

tick — 커널의 심장 박동

// SysTick 이 1 ms 마다 xPortSysTickHandler() 를 부릅니다
//   → xTaskIncrementTick(): tick 카운트 +1,
//     깨어날 시각이 된 Blocked 태스크를 Ready 로
//   → 바꿔야 하면 PendSV 를 걸어 둠 → 모든 ISR 이 끝난 뒤 문맥 전환

TickType_t now = xTaskGetTickCount();        // 태스크에서
TickType_t t2  = xTaskGetTickCountFromISR(); // ISR 에서

// ms ↔ tick 변환은 반드시 매크로로 — tick 주기를 바꿔도 코드가 맞습니다
vTaskDelay(pdMS_TO_TICKS(250));              // 1000 Hz 면 250 tick
uint32_t ms = now * portTICK_PERIOD_MS;      // 거꾸로 (정수 나눗셈 주의)

// 32 비트 tick 은 1 kHz 에서 약 49.7 일 만에 0 으로 되감깁니다
// 경과 시간은 뺄셈으로 — 되감겨도 부호 없는 산술이라 맞습니다
if ((TickType_t)(xTaskGetTickCount() - start) >= pdMS_TO_TICKS(500)) {
    on_timeout();
}
PendSV 가 왜 필요한가 — 문맥 전환을 ISR 한가운데서 하면 다른 ISR 의 레지스터가 섞입니다. 그래서 커널은 PendSV 를 가장 낮은 우선순위로 두고 "전환 예약"만 합니다. 다른 인터럽트가 다 끝난 순간 PendSV 가 돌아 태스크를 바꿉니다. Cortex-M4 @180MHz 에서 전환 자체는 1µs 안팎입니다.

스케줄러가 다시 고르는 순간

사건결과
tick 인터럽트지연이 끝난 태스크가 Ready 로. 같은 우선순위면 타임슬라이스 교대
태스크가 대기 API 호출자신이 Blocked → 다음으로 높은 Ready 가 Running
xQueueSend 등이 더 높은 태스크를 깨움그 API 안에서 즉시 전환 (다음 tick 을 기다리지 않음)
ISR 이 portYIELD_FROM_ISR(pdTRUE)ISR 이 끝나자마자 전환 (r07)
taskYIELD()같은 우선순위에게 자발적으로 양보
굶주림(starvation) — 높은 우선순위 태스크가 Blocked 되지 않고 계속 돌면 낮은 태스크는 영원히 못 돕니다. 리눅스 일반 스케줄러(CFS · EEVDF)처럼 "오래 기다린 쪽을 봐주는" 장치가 없습니다. 높은 우선순위일수록 짧게 일하고 빨리 잠들어야 합니다.

vTaskDelay vs xTaskDelayUntil — 주기가 밀리는 이유 🟡 중급

vTaskDelay 는 "지금부터 N", xTaskDelayUntil 은 "지난번 기상 + N" — 주기 작업에는 언제나 후자입니다.

주기 태스크의 정석

static volatile uint32_t s_overruns;

static void ControlTask(void *arg) {
    (void)arg;
    const TickType_t period = pdMS_TO_TICKS(10);
    TickType_t last = xTaskGetTickCount();      // ★ 루프 밖에서 한 번만

    for (;;) {
        // last 를 period 만큼 전진시키고 그 시각까지 잠듭니다
        BaseType_t slept = xTaskDelayUntil(&last, period);
        if (slept == pdFALSE) {
            s_overruns++;      // 이미 마감을 넘김 — 잠들지 않고 바로 반환
        }
        control_step();        // 3 ms 걸려도 다음 기상은 정확히 +10 ms
    }
}
V10.4 이전 이름 — vTaskDelayUntil(&last, period) (반환값 없음, INCLUDE_vTaskDelayUntil). V11 에도 호환 매크로로 남아 있지만 마감 초과를 알 수 없으니 새 이름을 쓰세요.

vTaskDelay(1) 은 1 ms 가 아닙니다

tick:   |-------|-------|-------|
                ^ 여기서 vTaskDelay(1) 호출 (tick 직전)
                 ^ 다음 tick 에 바로 깨어남 → 실제 대기 ≈ 0.1 ms

vTaskDelay(n) 의 실제 대기 = (n-1) ~ n tick 사이
→ "최소 2 ms" 가 필요하면 vTaskDelay(pdMS_TO_TICKS(2) + 1)
→ µs 단위 지연은 RTOS 가 아니라 하드웨어 타이머로
HAL_Delay 는 태스크에서 쓰지 마세요 — HAL_Delay 는 HAL_GetTick() 을 while 로 돌며 기다리는 바쁜 대기라 그동안 낮은 우선순위 태스크가 하나도 못 돕니다. 태스크 안에서는 언제나 vTaskDelay 입니다.

RTOS 05

큐 — 태스크 사이의 BlockingQueue, 단 값을 복사합니다

태스크끼리 데이터를 주고받는 기본 수단은 큐입니다. 전역 변수 + 플래그로 주고받으면 레이스가 생기지만, 큐는 넣고 빼는 순간이 원자적이고 비면 잠들고 차면 기다립니다. 자바의 ArrayBlockingQueue 와 같은데, 결정적인 차이가 하나 — 참조가 아니라 바이트를 복사합니다.

큐는 복사로 소유권 문제를 없앱니다 — 대신 큰 데이터는 복사 비용과 큐 RAM 이 커집니다.

기본형 — 구조체를 값으로

#include "queue.h"

typedef struct {
    uint32_t tick;        // 4

RTOS 펌웨어가 처음 멈추는 곳은 십중팔구 여기입니다. ISR 에서 일반 API 를 부르거나, NVIC 우선순위를 기본값 0 으로 둔 채 FromISR API 를 부르면 configASSERT 에 걸려 그대로 섭니다. 규칙은 세 가지 — FromISR 만 부른다 · 우선순위 숫자는 5 이상 · 깨운 태스크가 더 급하면 양보한다.

경계선 하나 — 5 보다 작은 숫자의 ISR 에서는 FreeRTOS 함수를 하나도 부르지 않습니다.

HAL 콜백의 함정 — HAL_UART_RxCpltCallback 은 DMA 스트림 IRQ 안에서 불릴 수 있습니다. USART2 IRQ 를 6 으로 올려 놓고 DMA1_Stream5_IRQn 은 기본 0 으로 두면 DMA 완료 때만 assert 가 납니다. 콜백에서 FreeRTOS 를 부르는 모든 IRQ 소스(UART · DMA · EXTI · TIM)를 5 이상으로 맞추세요.

지연 처리(deferred interrupt) — ISR 의 길이는 짧게 고정하고, 무거운 일은 우선순위로 제어되는 태스크가 합니다.

    (void)p1;
    log_warn("UART overrun, SR=0x%08lx", (unsigned long)ul2);
}

void USART2_IRQHandler(void) {
    uint32_t sr = USART2->SR;
    if (sr & USART_SR_ORE) {
        (void)USART2->DR;                      // SR → DR 순서로 읽어 ORE 해제
        BaseType_t woken = pdFALSE;

태스크 알림 · 이벤트 그룹 · 스트림/메시지 버퍼 — 언제 무엇을

큐와 세마포어만으로 모든 걸 할 수 있지만, FreeRTOS 에는 더 가볍거나 더 잘 맞는 도구가 세 가지 더 있습니다. 고르는 기준은 "받는 쪽이 몇인가 · 무엇을 보내는가"입니다.

/* ③ 이벤트 비트처럼 — 무엇이 일어났는지 비트로 */

#define EV_TX    (1u << 1)

소프트웨어 타이머 — 태스크 하나가 모든 콜백을 돌립니다

"500 ms 뒤에 LED 끄기", "2 초 동안 응답 없으면 재전송" 같은 일마다 태스크를 만들면 스택이 아깝습니다. 소프트웨어 타이머는 타이머 서비스 태스크(데몬) 하나가 모든 타이머의 콜백을 차례로 실행해 줍니다. 그래서 규칙도 하나 — 콜백에서 절대 기다리지 않는다.

소프트웨어 타이머는 하드웨어 타이머가 아니라 "tick 을 세는 태스크 하나"입니다 — 정밀도는 tick, 지연은 그 태스크의 우선순위가 정합니다.

/* 운영 중 감시 — 셸 명령이나 주기 로그로 */
void heap_report(void) {
    size_t now = xPortGetFreeHeapSize();             // 지금 남은 양
    size_t low = xPortGetMinimumEverFreeHeapSize();  // 부팅 후 최저 기록 ★
    log_info("heap free=%u min=%u", (unsigned)now, (unsigned)low);
}
최저 기록이 핵심 — 지금 남은 양은 순간값이라 의미가 적습니다. 부하 시험을 충분히 돌린 뒤 xPortGetMinimumEverFreeHeapSize() 가 전체의 20~30% 이상 남으면 안전권, 그 아래면 늘리거나 객체를 줄입니다. 서버의 "최대 힙 사용량" 지표와 같은 감각입니다.

동시성 버그와 디버깅 — 데드락 · 레이스 · 크리티컬 섹션 남용, 그리고 트레이스

RTOS 버그는 "가끔, 부하가 높을 때만, 디버거를 붙이면 사라지는" 모양으로 옵니다. 서버의 동시성 버그와 똑같은 종류지만 스레드 덤프도 로그 수집기도 없습니다. 대신 런타임 통계와 트레이스 도구로 시간 축을 눈으로 보는 것이 가장 빠른 길입니다.

데드락은 순환입니다 — 잠금 순서를 하나로 정하면 그래프에 고리가 생길 수 없습니다.

RTOS 12

저전력 — tickless idle, 그리고 Stop 모드와 묶을 때

배터리 기기에서 RTOS 의 tick 은 골칫거리입니다. 할 일이 없어도 1 ms 마다 깨어나 tick 을 세기 때문입니다. tickless idle 은 "다음 할 일이 40 ms 뒤라면 40 ms 동안 tick 을 끄고 한 번에 잔다"는 기능입니다. 켜는 건 한 줄이지만, 더 깊은 Stop 모드와 묶으려면 클럭 · 타이머 · 디버거를 같이 다뤄야 합니다.

깨어날 때마다 클럭이 돌고 플래시를 읽습니다 — 깨어나는 횟수 자체가 전력입니다.

켜기 — 포트 기본 구현 (Sleep 모드 + WFI)

한 번에 몇 ms 까지 잘 수 있나 — 직접 계산

SysTick 은 24비트 카운터 → 최대 0xFFFFFF = 16,777,215 클럭

SysTick 클럭 = 코어 180 MHz 일 때
  1 tick(1 ms) = 180,000 클럭
  최대 연속 수면 = 16,777,215 / 180,000 = 93 tick (≈ 93.2 ms)

SysTick 클럭 = HCLK/8 = 22.5 MHz 로 두면  (configSYSTICK_CLOCK_HZ)
  1 tick = 22,500 클럭
  최대 연속 수면 = 16,777,215 / 22,500 = 745 tick (≈ 0.75 s)

→ 그보다 긴 대기는 중간에 한 번 깨어 다시 잠듭니다 (기능상 문제는 없음)
기상 지연 — tickless 는 "인터럽트 하나에 깨어나 → 클럭 · tick 보정 → 스케줄"을 거치므로 첫 태스크 실행이 일반 모드보다 조금 늦습니다. Sleep 모드(WFI)는 수 µs 수준이라 대개 무시해도 되지만, 아래 Stop 모드는 다릅니다.

Stop 모드 tickless — 직접 구현하는 뼈대 🔴 실무

Stop 모드 tickless 는 "자고, 깨고, 클럭을 되살리고, 잔 만큼 시간을 맞추는" 여섯 단계입니다.
/* FreeRTOSConfig.h : configUSE_TICKLESS_IDLE 2  (포트 기본 구현 대신 내 함수)
   #define portSUPPRESS_TICKS_AND_SLEEP(x) vPortSuppressTicksAndSleep(x)
   ※ 뼈대입니다 — RTC 클럭 · 보정 오차 처리는 제품마다 다듬어야 합니다 */
extern RTC_HandleTypeDef hrtc;               // LSE 32.768 kHz
#define WUT_HZ  2048u                        // RTCCLK / 16
uint32_t rtc_now_wut_units(void);            // RTC 시각을 1/2048 s 단위로 (구현 생략)

void vPortSuppressTicksAndSleep(TickType_t xExpectedIdleTime) {
    if (xExpectedIdleTime > 30000u) xExpectedIdleTime = 30000u;  // WUT 16비트 한계 안
    SysTick->CTRL &= ~SysTick_CTRL_ENABLE_Msk;                // ① tick 정지
    __disable_irq();                                          // PRIMASK — WFI 깨움은 유지
    __DSB(); __ISB();

    if (eTaskConfirmSleepModeStatus() == eAbortSleep) {       // ② 그사이 일이 생김
        SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
        __enable_irq();
        return;
    }

    uint32_t wut = (xExpectedIdleTime * WUT_HZ) / configTICK_RATE_HZ;   // ③ 40 tick → 81
    if (wut < 2u) { SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk; __enable_irq(); return; }
    uint32_t t0 = rtc_now_wut_units();
    HAL_RTCEx_SetWakeUpTimer_IT(&hrtc, wut - 1u, RTC_WAKEUPCLOCK_RTCCLK_DIV16);

    HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI);  // ④

    SystemClock_Config();                                     // ⑤ HSI → PLL 180 MHz
    HAL_RTCEx_DeactivateWakeUpTimer(&hrtc);
    uint32_t slept = ((rtc_now_wut_units() - t0) * configTICK_RATE_HZ) / WUT_HZ;
    if (slept > xExpectedIdleTime) slept = xExpectedIdleTime;
    vTaskStepTick(slept);                                     // ⑥ tick 보정

    SysTick->VAL = 0;
    SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
    __enable_irq();                                           // 깨운 인터럽트가 여기서 처리됨
}

숫자로 보는 함정

WUT 해상도 = 1/2048 s ≈ 0.488 ms  (tick 1 ms 보다 거침)

40 tick 자려고 하면 → 40 × 2048 / 1000 = 81.92 → 81 카운트
실제 수면 = 81 / 2048 = 39.55 ms → 0.45 ms 일찍 깸
→ 잔 시간을 RTC 로 다시 재서 보정하므로 tick 은 틀어지지 않지만
  나머지(0.92 카운트)를 버리는 오차가 매번 누적되지 않게 하려면
  rtc_now_wut_units() 처럼 '절대 시각'으로 계산해야 합니다

WUT 16비트 · RTCCLK/16 → 최대 65,536 / 2,048 = 32 s
Stop 에서 깨는 데 걸리는 시간 — 레귤레이터를 저전력 모드로 두면 복귀가 더 느리고, 거기에 PLL 재잠금 시간이 더해집니다. 데이터시트의 tWUSTOP 값과 실제 측정(GPIO + 스코프)으로 확인하고, 그만큼 N 을 줄여 잡습니다. 1 ms 안에 반응해야 하는 태스크가 있는 동안에는 Stop 대신 Sleep 에 머무는 것이 맞습니다.
더 쉬운 길 — STM32L4 · U5 · WB 처럼 LPTIM 이 있는 저전력 계열은 ST 가 FreeRTOS tickless 예제를 제공합니다. 배터리 수명이 핵심인 제품이라면 칩 선택 단계에서 F4 대신 그쪽을 검토하세요(🔩 하드웨어 기초 탭의 배터리 계산 참고).
정리 — configUSE_TICKLESS_IDLE 1 한 줄로 Sleep 모드 tickless 를 얻습니다. Stop 모드까지 가려면 RTC 기상 · 클럭 복구 · tick 보정을 직접 짜고, 기상 지연을 재서 반영합니다.

/* app.c — FreeRTOS V11 · STM32F446RE · CubeMX 가 hi2c1 · huart2 · hiwdg 를 생성했다고 가정 */
#include "main.h"
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "event_groups.h"
#include <stdio.h>
#include <stdlib.h>

extern I2C_HandleTypeDef  hi2c1;           /* CubeMX 가 main.c 에 정의 — main.h 는 선언해 주지 않음 */
extern UART_HandleTypeDef huart2;
extern IWDG_HandleTypeDef hiwdg;

#define TMP_ADDR  0x48u                    /* 예: 온도 센서 7비트 주소 */
#define TMP_REG   0x00u

typedef struct { uint32_t tick; int16_t temp_x10; } Sample;                 /* 8 B */
typedef struct { uint32_t tick; int16_t avg_x10; uint8_t alarm; } Report;  /* 8 B */

enum { PRIO_COMM = 1, PRIO_PROC = 2, PRIO_SENSOR = 3, PRIO_WDG = 4 };
#define CHK_SENSOR (1u << 0)
#define CHK_PROC   (1u << 1)
#define CHK_COMM   (1u << 2)
#define CHK_ALL    (CHK_SENSOR | CHK_PROC | CHK_COMM)

static QueueHandle_t      q_raw, q_out;
static EventGroupHandle_t eg_alive;
static TaskHandle_t       h_sensor, h_comm;

int16_t tmp_to_x10(const uint8_t raw[2]);  /* 센서 데이터시트 변환식 (생략) */
void    log_missing(EventBits_t got);      /* 빠진 체크인 기록 (생략) */

static void must(BaseType_t r) { configASSERT(r == pdPASS); (void)r; }  /* assert 가 꺼져도 호출은 남음 */

/* ── Sensor: 10 ms 주기 · I2C 는 DMA, 완료는 알림으로 ── */
static void SensorTask(void *arg) {
    (void)arg;
    static uint8_t raw[2];                 /* DMA 가 쓰는 버퍼 — 스택 말고 static */
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        xTaskDelayUntil(&last, pdMS_TO_TICKS(10));
        (void)ulTaskNotifyTake(pdTRUE, 0); /* 지난번 늦게 온 알림 비우기 */
        if (HAL_I2C_Mem_Read_DMA(&hi2c1, TMP_ADDR << 1, TMP_REG,
                                 I2C_MEMADD_SIZE_8BIT, raw, 2) == HAL_OK &&
            ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(5)) != 0) {
            Sample s = { .tick = last, .temp_x10 = tmp_to_x10(raw) };
            (void)xQueueSend(q_raw, &s, 0); /* 가득 차면 버림 — 센서는 기다리지 않음 */
        }
        xEventGroupSetBits(eg_alive, CHK_SENSOR);
    }
}

void HAL_I2C_MemRxCpltCallback(I2C_HandleTypeDef *hi2c) {   /* DMA IRQ — NVIC 5 이상 */
    if (hi2c == &hi2c1) {
        BaseType_t woken = pdFALSE;
        vTaskNotifyGiveFromISR(h_sensor, &woken);
        portYIELD_FROM_ISR(woken);
    }
}

/* ── Proc: 10 개 평균 · 60.0 ℃ 초과면 경보 ── */
static void ProcTask(void *arg) {
    (void)arg;
    int32_t acc = 0;
    int n = 0;
    for (;;) {
        Sample s;
        if (xQueueReceive(q_raw, &s, pdMS_TO_TICKS(100)) == pdPASS) {
            acc += s.temp_x10;
            if (++n == 10) {
                int32_t avg = acc / 10;
                Report r = { .tick = s.tick, .avg_x10 = (int16_t)avg,
                             .alarm = (uint8_t)(avg > 600) };
                (void)xQueueSend(q_out, &r, 0);
                acc = 0;
                n = 0;
            }
        }
        xEventGroupSetBits(eg_alive, CHK_PROC);   /* 데이터가 끊겨도 100 ms 마다 체크인 */
    }
}

/* ── Comm: 문자열로 만들어 UART DMA 송신, 완료 알림까지 버퍼 보호 ── */
static void CommTask(void *arg) {
    (void)arg;
    static char line[48];                  /* DMA 가 읽는 동안 살아 있어야 함 */
    for (;;) {
        Report r;
        if (xQueueReceive(q_out, &r, pdMS_TO_TICKS(500)) == pdPASS) {
            int m = abs(r.avg_x10);
            int len = snprintf(line, sizeof line, "T=%lu AVG=%s%d.%d%s\r\n",
                               (unsigned long)r.tick, r.avg_x10 < 0 ? "-" : "",
                               m / 10, m % 10, r.alarm ? " ALARM" : "");
            if (len > 0 && len < (int)sizeof line &&
                HAL_UART_Transmit_DMA(&huart2, (uint8_t *)line, (uint16_t)len) == HAL_OK) {
                (void)ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(50));
            }
        }
        xEventGroupSetBits(eg_alive, CHK_COMM);
    }
}

void HAL_UART_TxCpltCallback(UART_HandleTypeDef *huart) {
    if (huart == &huart2) {
        BaseType_t woken = pdFALSE;
        vTaskNotifyGiveFromISR(h_comm, &woken);
        portYIELD_FROM_ISR(woken);
    }
}

/* ── Wdg: 1 s 안에 셋 다 체크인했을 때만 IWDG 갱신 ── */
static void WdgTask(void *arg) {
    (void)arg;
    for (;;) {
        EventBits_t b = xEventGroupWaitBits(eg_alive, CHK_ALL,
                                            pdTRUE,    /* 셋 다 왔으면 지움 → 다음 창에서 다시 받아야 */
                                            pdTRUE,    /* AND */
                                            pdMS_TO_TICKS(1000));
        if ((b & CHK_ALL) == CHK_ALL) {
            HAL_IWDG_Refresh(&hiwdg);
        } else {
            log_missing(b);                /* 갱신하지 않음 → 계속 빠지면 IWDG 가 리셋 */
        }
    }
}

void app_start(void) {                     /* main() 에서 MX_*_Init() 다음에 호출 */
    q_raw    = xQueueCreate(8, sizeof(Sample));
    q_out    = xQueueCreate(4, sizeof(Report));
    eg_alive = xEventGroupCreate();
    configASSERT(q_raw && q_out && eg_alive);

    must(xTaskCreate(WdgTask,    "wdg",    192, NULL, PRIO_WDG,    NULL));
    must(xTaskCreate(SensorTask, "sensor", 256, NULL, PRIO_SENSOR, &h_sensor));
    must(xTaskCreate(ProcTask,   "proc",   256, NULL, PRIO_PROC,   NULL));
    must(xTaskCreate(CommTask,   "comm",   512, NULL, PRIO_COMM,   &h_comm));

    __HAL_DBGMCU_FREEZE_IWDG();            /* 디버거로 멈춰 있는 동안 리셋 방지 (개발용) */
    vTaskStartScheduler();
}

typedef struct ActiveObject ActiveObject;
struct ActiveObject {
    TaskHandle_t  task;
    QueueHandle_t queue;                                  /* 이 객체만의 수신함 */
    void (*dispatch)(ActiveObject *me, const Event *e);   /* 상태 머신 */
};

static void ao_thread(void *arg) {
    ActiveObject *me = arg;
    Event e;
    for (;;) {
        xQueueReceive(me->queue, &e, portMAX_DELAY);       /* 기다리는 곳은 여기 하나 */
        me->dispatch(me, &e);                             /* 끝까지 실행 — 안에서 블로킹 금지 */
    }
}

void ao_start(ActiveObject *me, const char *name, UBaseType_t prio,
              UBaseType_t qlen, configSTACK_DEPTH_TYPE stackWords) {
    me->queue = xQueueCreate(qlen, sizeof(Event));
    configASSERT(me->queue);
    must(xTaskCreate(ao_thread, name, stackWords, me, prio, &me->task));
}

BaseType_t ao_post(ActiveObject *me, const Event *e) {
    return xQueueSend(me->queue, e, 0);                   /* 보내는 쪽도 기다리지 않음 */
}
BaseType_t ao_post_from_isr(ActiveObject *me, const Event *e, BaseType_t *woken) {
    return xQueueSendFromISR(me->queue, e, woken);
}
