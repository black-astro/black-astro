개발 보드에서 제품까지 — EVT · DVT · PVT, 단계마다 펌웨어가 할 일

하드웨어 제품은 한 번에 만들어지지 않습니다. 업계는 보통 EVT → DVT → PVT → 양산(MP) 네 관문을 거치고, 관문마다 보드가 새로 나옵니다. 서버 개발에 빗대면 dev → staging → canary → prod 와 같지만 결정적인 차이가 하나 있습니다 — 배포된 뒤에는 서버처럼 SSH 로 들어갈 수 없습니다. 그래서 펌웨어는 출하 전에 "현장에서 혼자 살아남는 장치"를 다 갖춰야 합니다.

타임라인 — 하드웨어는 관문마다 무엇을 증명하나가 바뀌고, 펌웨어 일은 DVT 에 가장 많이 몰립니다.

PROD 02

부트로더 설계 — Flash 를 나누고, 앱으로 깨끗하게 점프하기

부트로더는 리셋 직후 가장 먼저 도는 작은 두 번째 프로그램입니다. 할 일은 셋뿐입니다 — 앱이 멀쩡한지 확인하고, 필요하면 새 앱을 받고, 앱으로 넘어간다. 서버로 치면 GRUB 이나 컨테이너의 init 과 같은 자리입니다. 리셋에서 main 까지의 기본 줄거리(벡터 테이블 [0] · [4], Reset_Handler)는 하드웨어 기초 탭 h11 · 링커 스크립트는 h12 를 참고하고, 여기서는 두 프로그램이 한 Flash 를 나눠 쓰는 법에 집중합니다.

메모리 배치 — 부트로더를 넣는 순간 앱이 쓸 Flash 가 줄어듭니다. A/B 를 하면 절반 이하로.

부트로더의 main — 판단은 이것뿐

/* bootloader/main.c — 0x0800 0000, 32 KB 안에 들어가야 함 */
#define APP_BASE   0x08010000u
#define APP_MAX    (192u * 1024u)

int main(void)
{
    HAL_Init();                    /* 클럭은 HSI 16 MHz 그대로 — 단순할수록 안전 */

    if (boot_request_pending())    /* 앱이 "업데이트 받을래" 하고 리셋했나 */
        recovery_mode();           /* UART · USB 로 새 이미지 받기 (돌아오지 않음) */

    if (!app_valid(APP_BASE, APP_MAX))
        recovery_mode();           /* 앱이 없거나 깨졌으면 앱으로 가지 않는다 */

    jump_to_app(APP_BASE);         /* 돌아오지 않음 */
}
부트로더는 거의 고치지 않는 코드입니다. 현장에 나간 부트로더는 업데이트하지 않는 것이 원칙이라(업데이트 도중 꺼지면 복구 수단이 없음) 기능을 최소로, 클럭 설정도 최소로 둡니다. 32 KB 를 넘으면 HAL 대신 LL 을 쓰거나 -Os 로 줄이세요.

앱 유효성 검사 — 점프하기 전에 반드시

static bool app_valid(uint32_t base, uint32_t max)
{
    const uint32_t sp = *(const volatile uint32_t *)base;          /* 벡터 [0] */
    const uint32_t pc = *(const volatile uint32_t *)(base + 4u);   /* 벡터 [1] */

    /* 지워진 Flash 는 0xFFFFFFFF — 이 검사 하나로 "앱 없음"이 걸린다 */
    if (sp < 0x20000000u || sp > 0x20020000u) return false;  /* SRAM 128 KB, 끝 포함 */
    if ((sp & 0x3u) != 0u)                    return false;  /* 스택은 워드 정렬 */
    if ((pc & 0x1u) == 0u)                    return false;  /* Thumb 비트가 없으면 가짜 */
    if (pc < base || pc >= base + max)        return false;  /* 앱 영역 밖을 가리킴 */

    return image_digest_ok(base);   /* 내용 전체 확인 — CRC 또는 SHA-256 (PROD 04) */
}
SP · PC 검사만으로는 부족합니다 — 업데이트가 앞 1 KB 만 쓰고 끊기면 벡터 테이블은 멀쩡한데 나머지가 0xFF 입니다. 점프는 성공하고 몇 초 뒤 HardFault 가 납니다. 이미지 전체의 해시를 함께 봐야 합니다.

앱으로 점프 — 순서가 곧 정답 🟡 중급

단계 — 핵심은 "앱이 리셋 직후의 칩을 만나게" 하는 것입니다. 하나라도 빠지면 증상이 몇 초 뒤에 엉뚱한 곳에서 납니다.

jump_to_app — 위 일곱 단계 그대로

/* MSP 를 바꾼 뒤엔 C 지역 변수(스택)를 믿을 수 없다 → 어셈블리 두 줄 */
__attribute__((naked, noreturn))
static void start_app(uint32_t sp, uint32_t pc)
{
    __asm volatile("msr msp, r0 \n"    /* r0 = sp (AAPCS 첫 인자) */
                   "bx  r1      \n");  /* r1 = pc, Thumb 비트 1 그대로 */
}

void jump_to_app(uint32_t base)
{
    const uint32_t sp = *(const volatile uint32_t *)base;
    const uint32_t pc = *(const volatile uint32_t *)(base + 4u);

    __disable_irq();                                  /* ② */
    HAL_DeInit();                                     /* ③ 주변장치 RCC 리셋 */
    HAL_RCC_DeInit();                                 /*   HSI 로 복귀 (안에서 SysTick 재설정) */
    SysTick->CTRL = 0; SysTick->LOAD = 0; SysTick->VAL = 0;  /* 그래서 맨 마지막에 정지 */

    for (uint32_t i = 0; i < 8u; i++) {               /* ④ F446 IRQ 97개 — 넉넉히 8워드 */
        NVIC->ICER[i] = 0xFFFFFFFFu;
        NVIC->ICPR[i] = 0xFFFFFFFFu;
    }
    SCB->ICSR = SCB_ICSR_PENDSTCLR_Msk;               /*   SysTick 펜딩도 */

    SCB->VTOR = base;                                 /* ⑤ 0x200 정렬 필수 */
    __DSB(); __ISB();

    __set_CONTROL(0u);                                /* ⑥ PSP · FPU 문맥 흔적 제거 */
    __ISB();
    __enable_irq();                                   /*   NVIC 를 다 껐으니 안전 */
    start_app(sp, pc);                                /* ⑥ MSP ⑦ 분기 */
}

왜 이 순서인가

결정이유
SysTick 정지를 맨 뒤에F4 HAL 의 HAL_RCC_DeInit() 은 끝에서 HAL_InitTick() 으로 SysTick 을 다시 켭니다
__enable_irq()점프는 리셋이 아니라 PRIMASK=1 이 그대로 넘어갑니다. CubeMX 앱은 이걸 풀지 않으므로 SysTick 이 안 돌고 HAL_Delay 에서 멈춤
CONTROL = 0부트로더가 RTOS 를 썼다면 PSP 사용 · 비특권 상태일 수 있음. 앱의 스타트업은 MSP 특권을 가정
naked 함수C 로 __set_MSP(sp) 뒤 ((void(*)(void))pc)() 를 쓰면 최적화 수준에 따라 pc 를 바뀐 스택에서 읽음
DSB · ISBVTOR 쓰기가 끝나기 전에 인터럽트가 들어오지 않게
VTOR 정렬 — Cortex-M4 의 벡터 테이블은 "벡터 개수 × 4 를 2 의 거듭제곱으로 올린 값"에 정렬돼야 합니다. F446 은 113개 × 4 = 452 B → 512 B(0x200) 정렬. CMSIS 의 system_stm32f4xx.c 주석이 "0x200 의 배수"라고 적어 둔 이유입니다.

    NVIC_SystemReset();            /* 칩 전체를 진짜 리셋 상태로 */
}

/* 부트로더: 맨 처음, HAL_Init 보다 먼저 */

{
    if (g_boot_req != BOOT_REQ_MAGIC) return false;
    g_boot_req = 0u;               /* 한 번만 — 안 지우면 영원히 복구 모드 */
    return true;
}
전원 투입(POR) 직후의 SRAM 은 쓰레기 값입니다. 매직 값이 우연히 맞을 확률은 2-32 이지만, 더 확실히 하려면 매직과 그 비트 반전 값을 함께 써 두고 둘 다 맞을 때만 인정합니다. 반대 방향(부트로더 → 앱)도 이렇게 리셋 후 점프하면 위 일곱 단계 중 ②~④가 저절로 해결됩니다.
정리 — F446 에서 부트로더는 S0~S1(32 KB), 앱은 0x0801 0000 부터가 흔한 배치입니다. 점프 전에 SP · PC · 해시로 앱을 검사하고, 인터럽트 · 클럭 · NVIC 를 리셋 직후 상태로 돌린 뒤 VTOR → MSP → Reset_Handler 순서로 넘깁니다.

typedef struct {
    uint32_t active;     /* 확정된 슬롯 0=A 1=B */
    uint32_t pending;    /* 시험할 슬롯 */
    uint32_t state;      /* 0=IDLE 1=PENDING 2=TRIAL */
    uint32_t tries;      /* TRIAL 부팅 횟수 */
} boot_ctrl_t;           /* PROD 07 의 정전 안전 저장으로 보관 */

#define MAX_TRIES 3u

uint32_t choose_slot(void)
{
    boot_ctrl_t bc;
    ctrl_load(&bc);
    if (bc.state == 1u) { bc.state = 2u; bc.tries = 0u; }    /* PENDING → TRIAL */
    if (bc.state == 2u) {
        if (bc.tries >= MAX_TRIES || !app_valid(slot_base(bc.pending), SLOT_MAX)) {
            bc.state = 0u;                         /* 롤백 — active 는 그대로 */
            ctrl_save(&bc);
            evt_log(EV_ROLLBACK);
            return bc.active;
        }
        bc.tries++;                                /* 점프 "전에" 먼저 기록 */
        ctrl_save(&bc);
        return bc.pending;
    }
    return bc.active;
}
tries 를 점프 전에 저장하는 것이 핵심입니다. 점프 뒤에 세면 새 펌웨어가 부팅하자마자 죽을 때 카운트가 영원히 오르지 않아 무한 리셋 루프가 됩니다.

/* 슬롯 B 에 오프셋 순서대로만 쓴다 — 섹터 첫 청크에서 그 섹터를 지움 */
int ota_write_chunk(uint32_t off, const uint8_t *buf, uint32_t len)
{
    if (off != g_ota.next_off)      return OTA_E_ORDER;  /* 서버에 next_off 재요청 */
    if (off + len > SLOT_MAX)       return OTA_E_SIZE;
    if (len % 4u != 0u)             return OTA_E_ALIGN;  /* 워드 쓰기 */

    uint32_t addr = slot_base(other_slot()) + off;
    if (is_sector_start(addr) && flash_erase_sector_at(addr) != 0)
        return OTA_E_FLASH;
    if (flash_write(addr, buf, len) != 0) return OTA_E_FLASH;

    sha256_update(&g_ota.sha, buf, len);  /* 받으면서 해시 — 다시 읽을 필요 없음 */

PROD 04

이미지 무결성 · 서명 — "깨지지 않았나"와 "우리가 만든 것인가"는 다른 질문

부트로더가 앱을 실행하기 전에 묻는 질문은 두 가지입니다. 전송 중에 비트가 깨지지 않았나(무결성), 그리고 우리 회사가 만든 이미지가 맞나(진본성). CRC 는 앞의 질문만, 서명은 둘 다 답합니다. 웹 개발에 빗대면 CRC 는 TCP 체크섬, 서명은 HTTPS 인증서 검증입니다 — 체크섬이 맞는다고 그 서버를 믿지는 않습니다.

매트릭스 — CRC · SHA-256 은 사고를, 서명은 공격을 막습니다. 서명 검증에 기기 쪽 비밀은 필요 없습니다.

CRC-32 — 스트리밍으로 계산

/* IEEE 802.3 CRC-32 (zlib 과 같은 값). 표 없이 비트 단위 — 부트로더용으로 작게 */
uint32_t crc32_update(uint32_t crc, const uint8_t *p, size_t n)
{
    crc = ~crc;
    while (n--) {
        crc ^= *p++;
        for (int k = 0; k < 8; k++)
            crc = (crc & 1u) ? (crc >> 1) ^ 0xEDB88320u : (crc >> 1);
    }
    return ~crc;
}
/* 검산: crc32_update(0, "123456789", 9) == 0xCBF43926
   나눠 넣어도 같음: crc = crc32_update(0, a, 4); crc = crc32_update(crc, a + 4, 5); */
STM32 의 하드웨어 CRC 유닛은 F4 에서 다항식 0x04C11DB7 고정 · 비트 반전 없음이라 위 값(zlib)과 다르게 나옵니다. PC 쪽 도구와 맞추려면 입력 · 출력 반전을 소프트웨어로 해 주거나, 반전 설정이 있는 F7 · L4 · G4 등의 CRC 유닛을 씁니다.

/* TinyCrypt (MCUboot 도 쓰는 작은 암호 라이브러리) */
#include "tinycrypt/sha256.h"
#include "tinycrypt/ecc_dsa.h"
extern const uint8_t g_pubkey[64];          /* X‖Y — 부트로더에 상수로 */

bool image_signature_ok(const fw_hdr_t *h)
{
    uint8_t d[32];
    struct tc_sha256_state_struct s;

    /* ① 본문 해시가 헤더에 적힌 값과 같은가 */
    tc_sha256_init(&s);
    tc_sha256_update(&s, (const uint8_t *)h + h->hdr_size, h->img_size);
    tc_sha256_final(d, &s);
    if (memcmp(d, h->sha256, 32) != 0) return false;

    /* ② 헤더 앞 60 바이트(해시 포함)에 대한 서명이 맞는가 */
    tc_sha256_init(&s);
    tc_sha256_update(&s, (const uint8_t *)h, offsetof(fw_hdr_t, sig));
    tc_sha256_final(d, &s);
    return uECC_verify(g_pubkey, d, sizeof d, h->sig, uECC_secp256r1()) == 1;
}
OpenSSL 서명은 DER 형식(가변 길이 70~72 B)입니다. uECC 는 r‖s 64 B 원시 형식을 받으므로 서명 서버에서 변환해야 합니다 (예: 파이썬 cryptography 의 decode_dss_signature). 이걸 놓치면 "서명이 맞는데 검증이 실패"합니다. h->img_size 를 믿기 전에 슬롯 크기 안인지부터 확인하세요.

개인키는 서명 서버 하나에만 — CI 가 빌드한 산출물을 서명 서버(클라우드 KMS · HSM)에 보내 서명만 받아 옵니다. 개발 중엔 별도의 개발용 키를 쓰고, 개발 키로 서명된 이미지는 양산 부트로더가 거부하게 합니다.
키 교체 계획을 처음부터 넣어 두세요 — 부트로더에 공개키 슬롯을 2~3개 두고 "폐기된 키 목록"을 업데이트로 보낼 수 있게 하면, 키가 유출됐을 때 현장 장비를 버리지 않아도 됩니다. 새 시리즈(STM32 H5 · U5 등)는 칩 자체의 불변 부트 영역과 TrustZone 으로 이 사슬의 첫 고리를 하드웨어가 맡습니다(PROD 11).
정리 — CRC 는 사고, 서명은 공격을 막습니다. 이미지에 0x200 헤더(버전 · 크기 · 해시 · 서명)를 붙이고, 부트로더는 공개키만 품습니다. 사슬의 첫 고리인 부트로더를 WRP · RDP 로 굳히지 않으면 나머지는 장식입니다 — 처음이라면 MCUboot 부터 검토하세요.
PROD 05

워치독 — "살아 있다"가 아니라 "일하고 있다"를 확인하는 타이머

워치독은 정해진 시간 안에 "갱신(킥)"하지 않으면 칩을 리셋하는 하드웨어 타이머입니다. 쿠버네티스의 liveness probe 와 같은 역할이지만, probe 가 HTTP 200 만 확인하면 의미가 없듯이 아무 데서나 킥하는 워치독도 아무것도 지키지 못합니다. F446 에는 성격이 다른 두 개 — IWDG(독립 · 끌 수 없음)와 WWDG(창 · 너무 일찍 킥해도 리셋)가 있습니다. RTOS 에서의 감시 태스크 패턴은 FreeRTOS 탭 r13 에 있고, 여기서는 타이밍 계산과 제품 운영 관점을 봅니다.

라인 — 킥이 끊긴 순간부터 타임아웃만큼 뒤에 리셋됩니다. 그 타임아웃은 LSI 오차 때문에 3배 가까이 흔들립니다.

IWDG 타임아웃 계산

타임아웃 = (4 × 2^PR) × (RLR + 1) / f_LSI
           └ 분주 4·8·…·256  └ 12비트 0~4095

예) 분주 64 (PR=4), RLR = 999
  f_LSI = 32 kHz (전형) → 64 × 1000 / 32000 = 2.00 s
  f_LSI = 17 kHz (최소) → 64 000 / 17 000  = 3.76 s
  f_LSI = 47 kHz (최대) → 64 000 / 47 000  = 1.36 s

최대: 분주 256, RLR 4095 → 256 × 4096 / 32000 = 32.8 s
최소: 분주 4,   RLR 0    → 4 / 32000       = 0.125 ms

PROD 06

리셋 원인 · 브라운아웃 — "가끔 재부팅된다"를 숫자로 바꾸기

현장에서 가장 흔한 불만은 "가끔 꺼졌다 켜진다"입니다. 원인은 워치독일 수도, 폴트일 수도, 전원이 잠깐 처진 것일 수도 있습니다. 다행히 STM32 는 왜 리셋됐는지를 RCC_CSR 레지스터에 남깁니다. 이 값을 부팅마다 읽어 기록하고 서버로 올리는 것만으로 서버의 종료 코드(exit code) 대시보드 같은 것이 생깁니다. 플래그 읽기의 기본은 하드웨어 기초 탭 h11 에 있고, 여기서는 판정 순서 · 브라운아웃 설정 · 리셋 루프 대응을 다룹니다.

결정 흐름도 — 내부 리셋도 NRST 핀을 끌어내리므로 PIN 은 맨 마지막, 전원 투입 때 같이 켜지는 BOR 때문에 POR 을 BOR 보다 먼저 봅니다.

플래그를 비트마스크로 남기기

typedef enum {
    RST_LPWR = 1u << 0, RST_WWDG = 1u << 1, RST_IWDG = 1u << 2,
    RST_SFT  = 1u << 3, RST_POR  = 1u << 4, RST_BOR  = 1u << 5,
    RST_PIN  = 1u << 6,
} rst_flag_t;

/* 맨 처음 한 번 — 문자열 하나가 아니라 "켜진 것 전부"를 남긴다 */
uint32_t reset_flags_take(void)
{
    const uint32_t csr = RCC->CSR;
    uint32_t f = 0u;
    if (csr & RCC_CSR_LPWRRSTF) f |= RST_LPWR;
    if (csr & RCC_CSR_WWDGRSTF) f |= RST_WWDG;
    if (csr & RCC_CSR_IWDGRSTF) f |= RST_IWDG;
    if (csr & RCC_CSR_SFTRSTF)  f |= RST_SFT;
    if (csr & RCC_CSR_PORRSTF)  f |= RST_POR;
    if (csr & RCC_CSR_BORRSTF)  f |= RST_BOR;
    if (csr & RCC_CSR_PINRSTF)  f |= RST_PIN;
    RCC->CSR |= RCC_CSR_RMVF;   /* 지우지 않으면 다음 부팅에 섞임 */
    return f;
}
원본 비트를 다 남기고 해석은 서버에서 — 펌웨어에서 문자열 하나로 줄이면 판정 규칙을 고칠 때마다 업데이트가 필요합니다. 비트마스크 1 바이트와 부팅 번호를 올리면 대시보드에서 "IWDG 비율이 v1.5.0 부터 3배" 같은 걸 바로 봅니다.

#define BI_MAGIC 0x5AFEB007u
typedef struct {
    uint32_t magic, magic_inv;   /* 둘 다 맞아야 유효 — POR 직후 쓰레기 걸러 냄 */
    uint32_t bad_boots;          /* 연속 비정상 부팅 수 */
    uint32_t sw_reason;          /* NVIC_SystemReset 직전에 적은 이유 */
} boot_info_t;
__attribute__((section(".noinit"))) boot_info_t g_bi;

void boot_info_update(uint32_t rst)
{
    if (g_bi.magic != BI_MAGIC || g_bi.magic_inv != ~BI_MAGIC || (rst & RST_POR)) {
        g_bi = (boot_info_t){ .magic = BI_MAGIC, .magic_inv = ~BI_MAGIC };
    }
    const bool bad = (rst & (RST_IWDG | RST_WWDG)) ||
                     ((rst & RST_BOR) && !(rst & RST_POR)) ||   /* 전원 투입 때의 BOR 은 정상 */
                     ((rst & RST_SFT) && g_bi.sw_reason == SWR_FAULT);
    g_bi.bad_boots = bad ? g_bi.bad_boots + 1u : 0u;
    g_bi.sw_reason = SWR_NONE;

    if (g_bi.bad_boots >= 5u) safe_mode();     /* 돌아오지 않음 */
}

/* 60 s 동안 문제없이 돌면 "건강함"으로 */
void boot_info_mark_healthy(void) { g_bi.bad_boots = 0u; }

안전 모드는 "고쳐 받을 수 있는 최소 상태"입니다. 리셋 루프의 원인은 보통 특정 주변장치 드라이버나 깨진 설정이므로, 그것들을 건너뛰고 통신만 살리면 서버가 원인 로그를 받고 수정 펌웨어를 보낼 수 있습니다. 안드로이드의 복구 모드와 같은 발상입니다.
.noinit 카운터는 전원을 껐다 켜면 사라집니다. 전원이 반복해서 끊기는 루프(브라운아웃이 POR 까지 내려가는 경우)까지 세려면 PROD 07 의 Flash 저장이나 F446 의 백업 레지스터 · 4 KB 백업 SRAM(VBAT 로 유지)을 씁니다. PROD 03 의 A/B 롤백(TRIAL 3회)과 이 카운터는 서로 다른 층입니다 — 롤백이 먼저, 그래도 안 되면 안전 모드.
정리 — 부팅마다 RCC_CSR 을 읽고 지우고, 비트 전부를 부팅 번호와 함께 기록합니다. 판정은 워치독 → 소프트웨어 → POR → BOR → PIN 순. 양산품은 BOR 레벨 3을 공정에서 설정하고, 연속 비정상 부팅이 쌓이면 안전 모드로 들어가 고쳐 받을 수 있게 합니다.

설정 · 데이터 저장 — 어느 순간 꺼져도 이전 값이나 새 값, 둘 중 하나

F446 내부 Flash 에 쓰는 기본(섹터 지우기 · 워드 쓰기 · 지우는 동안 CPU 정지 · A/B 두 섹터 교대)은 STM32 탭 m11 에서 다뤘습니다. 제품에서는 두 가지가 더 문제가 됩니다. 수명 — 섹터당 약 1만 번 지우면 끝이고, 전원 차단 — 쓰는 도중 꺼진 반쪽 기록을 믿으면 안 됩니다. 데이터베이스의 WAL(로그 선행 기록) + 커밋 레코드와 같은 원리로 둘을 함께 풉니다.

상태 기계 — 본문을 다 쓴 뒤 완료 워드를 마지막에 씁니다. 0xFF 는 쓰기로만 0 이 되므로 완료 표시는 되돌아가지 않습니다.

덧붙여 쓰는 기록 — 지우기를 수백 분의 1 로

#define REC_COMMIT 0x600DC0DEu
typedef struct {
    uint32_t seq;        /* 쓸 때마다 +1 — 가장 큰 확정 기록이 현재 값 */
    uint16_t len;
    uint16_t ver;        /* 설정 구조체 형식 버전 — 업데이트 뒤 변환용 */
    uint8_t  data[48];
    uint32_t crc;        /* seq ~ data 의 CRC32 (PROD 04) */
    uint32_t commit;     /* ② 맨 마지막에 쓰는 완료 표시 */
} rec_t;
_Static_assert(sizeof(rec_t) == 64, "16 KB 섹터에 256 칸");

int cfg_append(const void *d, uint16_t len)
{
    if (len > sizeof(((rec_t *)0)->data)) return -1;
    rec_t r;
    memset(&r, 0, sizeof r);
    r.seq = g_last_seq + 1u;  r.len = len;  r.ver = CFG_VER;
    memcpy(r.data, d, len);
    r.crc = crc32_update(0u, (const uint8_t *)&r, offsetof(rec_t, crc));

    uint32_t a = next_blank_slot();         /* 64 B 전부 0xFF 인 칸 */
    if (a == 0u) a = switch_sector();       /* 다른 섹터를 지우고 첫 칸 */
    if (flash_write(a, &r, offsetof(rec_t, commit)) != 0) return -2;   /* ① */
    const uint32_t c = REC_COMMIT;
    if (flash_write(a + offsetof(rec_t, commit), &c, 4u) != 0) return -3;  /* ② */
    g_last_seq = r.seq;
    return 0;
}

읽을 때의 규칙

/* 두 섹터(S2 · S3)의 모든 칸을 훑어 가장 큰 seq 의 확정 기록 */
const rec_t *cfg_latest(void)
{
    const rec_t *best = NULL;
    for (int s = 0; s < 2; s++) {
        const rec_t *p = (const rec_t *)sector_base(s);
        for (uint32_t i = 0; i < 256u; i++, p++) {
            if (p->commit != REC_COMMIT) continue;          /* 반쪽 · 빈칸 */
            if (crc32_update(0u, (const uint8_t *)p, offsetof(rec_t, crc)) != p->crc)
                continue;                                    /* 비트 손상 */
            if (best == NULL || p->seq > best->seq) best = p;
        }
    }
    return best;   /* NULL 이면 공장 기본값 */
}
빈칸 판정은 64 B 전부를 봐야 합니다. 첫 워드만 보고 0xFF 라서 "비었다"고 하면, 본문 중간까지 쓰다 꺼진 칸에 다시 쓰게 되고 F4 는 이미 0 인 비트를 1 로 못 되돌리므로 엉뚱한 값이 섞입니다.
섹터 교대 순서 — 다른 섹터를 지우고, 최신 기록을 거기 첫 칸에 쓴 다음에야 옛 섹터를 버립니다. 지우는 도중 꺼져도 옛 섹터에 최신 값이 남아 있습니다. 부팅 때 g_last_seq 는 cfg_latest()->seq 로 복원합니다.

수명 계산 — 1분에 한 번 저장하면 언제 닳나 🟡 중급

EEPROM 에뮬레이션 — ST 응용 노트 방식

페이지(섹터) 두 개, 각 페이지 맨 앞에 상태: ERASED · RECEIVE_DATA · VALID_PAGE

VALID 페이지에 (가상 주소 16비트, 값 16비트) 4 B 쌍을 뒤에 덧붙임
  [VALID][0x0001=25][0x0002=300][0x0001=26][0x0001=27] ...
                                          └ 같은 주소면 뒤의 것이 최신

페이지가 차면: 다른 페이지를 RECEIVE_DATA 로 → 각 주소의 최신 값만 복사
              → 옛 페이지 지움 → 새 페이지를 VALID 로
(F4 는 AN3969, 시리즈마다 응용 노트 · X-CUBE-EEPROM 이 따로 있음)

수명: 16 KB 페이지 ≈ 4 095 칸 − 변수 10개 복사분 = 4 085 회 / 지우기
      × 2 페이지 × 1만 회 ≈ 8 170만 회 → 1분에 1회면 약 155 년
위의 64 B 덧붙이기와 원리가 같고, 기록 단위를 변수 하나(4 B)로 쪼갠 것이 차이입니다. 값이 자주 바뀌는 카운터 몇 개에 강하고, 큰 구조체를 통째로 저장하는 데는 64 B 기록이 단순합니다.

littlefs 는 쓰기 시 복사(copy-on-write)와 메타데이터 쌍으로 정전 안전 · 마모 분산을 파일 시스템 수준에서 해 줍니다. RAM 은 캐시 몇 개 분량(위 설정이면 1 KB 안팎)이면 됩니다. FAT 는 정전에 약하므로 SD 카드처럼 PC 와 주고받을 때만 씁니다.
"마운트 실패 → 포맷" 은 개발용 코드입니다. 현장에서 SPI 배선 접촉 불량 한 번으로 마운트가 실패하면 사용자 데이터가 전부 지워집니다. 포맷은 공장 공정(PROD 10)에서만, 현장에선 오류를 기록하고 읽기 전용으로 버팁니다. F446 내부 Flash(128 KB 섹터)는 블록이 너무 커서 littlefs 와 잘 맞지 않습니다.
정리 — 정전 안전은 본문 → 완료 표시 순서와 순번 + CRC로, 수명은 지우기 한 번에 여러 번 쓰는 덧붙이기로 해결합니다. 작은 설정은 내부 Flash 기록, 자주 바뀌는 값은 EEPROM 에뮬레이션, 대용량은 외부 Flash + littlefs. 현장에서 자동 포맷은 금지입니다.

저전력 제품 설계 — 전력 예산표로 배터리 수명을 먼저 계산한다

Sleep · Stop · Standby 모드에 들어가는 법은 STM32 탭 m13 · AVR 탭 a12 · FreeRTOS 탭 r12 에 있습니다. 제품에서 묻는 것은 다른 질문입니다 — "이 배터리로 몇 년 가나?" 답은 평균 전류 하나로 정해지고, 평균 전류는 모드별 전류 × 그 모드에 머무는 시간 비율의 합입니다. 클라우드 비용을 "인스턴스 단가 × 가동 시간"으로 미리 계산하듯, 배터리도 설계 단계에서 예산표를 먼저 씁니다.

파형 — 짧고 높은 펄스와 길고 낮은 바닥, 둘의 넓이(전하)를 더한 것이 배터리를 씁니다.

states = [  # (이름, 전류 A, 시간 s)
    ("measure",  3e-3, 0.050),
    ("radio_tx", 8e-3, 0.004),
]
PERIOD  = 60.0
SLEEP_I = 4e-6                      # MCU Stop + LDO Iq + 센서 대기 합계

awake = sum(t for _, _, t in states)
q = sum(i * t for _, i, t in states) + SLEEP_I * (PERIOD - awake)
avg = q / PERIOD
print(f"평균 {avg * 1e6:.2f} uA")
for name, mah in [("CR2032", 220), ("2xAA", 2500)]:
    h = mah / 1000 / avg
    print(f"{name}: 이론 {h / 8760:.1f} 년, 80% 가정 {0.8 * h / 8760:.1f} 년")

정리 — 배터리 수명 = 용량 ÷ 평균 전류, 평균 전류 = Σ(전류 × 시간) ÷ 주기. 예산표를 먼저 쓰고, PPK2 같은 프로파일러로 실측해 맞춥니다. 떠 있는 핀 · 풀업 · LED · 레귤레이터 Iq 같은 누설 하나가 수명을 년에서 일 단위로 바꿉니다.

덧붙이기 — 섹터를 넘으면 다음 섹터를 지움

#define LOG_SECT   4096u
#define LOG_NSECT  16u
static uint32_t g_wr;          /* 다음에 쓸 오프셋 (0 ~ 64 KB) */

int log_append(const log_hdr_t *h, const void *args)
{
    const uint32_t n = sizeof *h + h->len;
    if (n > LOG_SECT) return -1;

    /* 섹터 끝을 넘으면 다음 섹터 처음으로 (기록이 섹터를 걸치지 않게) */
    if ((g_wr % LOG_SECT) + n > LOG_SECT)
        g_wr = ((g_wr / LOG_SECT + 1u) % LOG_NSECT) * LOG_SECT;
    if (g_wr % LOG_SECT == 0u)
        w25q_erase_4k(LOG_BASE + g_wr);       /* 가장 오래된 4 KB 를 버림 */

    /* w25q_program 은 256 B 페이지 경계에서 나눠 써야 함 (넘으면 같은 페이지 앞을 덮음) */
    w25q_program(LOG_BASE + g_wr, h, sizeof *h);
    w25q_program(LOG_BASE + g_wr + sizeof *h, args, h->len);
    g_wr += n;
    if (g_wr >= LOG_NSECT * LOG_SECT) g_wr = 0u;   /* 링 끝에 딱 맞게 찼으면 처음으로 */
    return 0;
}
부팅 때는 각 섹터의 첫 기록 seq 를 읽어 가장 큰 섹터를 찾고, 그 안을 끝까지 훑어 g_wr 를 복원합니다. CRC 가 깨진 마지막 기록(쓰다 꺼짐)은 건너뜁니다 — PROD 07 의 "확정만 믿는다"와 같은 규칙입니다.

생산 테스트 펌웨어의 OTP 기록

#define OTP_BASE  0x1FFF7800u
#define OTP_LOCK  0x1FFF7A00u
typedef struct {
    uint32_t magic;        /* 0x1D0B10C0 */
    char     serial[16];   /* MES 가 발급 — 라벨과 같은 값 */
    uint8_t  mac[6];
    uint8_t  hw_rev;
    uint8_t  _rsv;
    uint32_t crc;          /* 앞 28 B 의 CRC32 */
} otp_ident_t;
_Static_assert(sizeof(otp_ident_t) == 32, "OTP 블록 하나");

HAL_StatusTypeDef otp_write_block(uint32_t blk, const void *src)
{
    if (blk >= 16u) return HAL_ERROR;
    const uint32_t a = OTP_BASE + 32u * blk;
    const uint32_t *w = src;
    for (uint32_t i = 0; i < 8u; i++)            /* 이미 쓰인 블록이면 거부 */
        if (((const volatile uint32_t *)a)[i] != 0xFFFFFFFFu) return HAL_ERROR;

    HAL_StatusTypeDef st = HAL_OK;
    HAL_FLASH_Unlock();
    for (uint32_t i = 0; st == HAL_OK && i < 8u; i++)
        st = HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, a + 4u * i, w[i]);
    if (st == HAL_OK && memcmp((const void *)a, src, 32u) != 0) st = HAL_ERROR;
    if (st == HAL_OK)                               /* 읽어서 맞을 때만 잠금 */
        st = HAL_FLASH_Program(FLASH_TYPEPROGRAM_BYTE, OTP_LOCK + blk, 0x00u);
    HAL_FLASH_Lock();
    return st;
}

#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>

/* 핀 번호가 코드에 없다 — 보드의 디바이스트리가 led0 을 PA5 로 정의 */
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios);

int main(void)
{
    if (!gpio_is_ready_dt(&led)) return 0;
    gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);
    while (1) {
        gpio_pin_toggle_dt(&led);
        k_msleep(500);
    }
}
Zephyr 는 리눅스 재단 산하의 RTOS 로, 하드웨어 기술을 디바이스트리에, 기능 선택을 Kconfig 에 둡니다(리눅스 커널과 같은 방식). 이 탭의 MCUboot(PROD 04) · 로그 · 셸 · 설정 저장 · 네트워크가 서브시스템으로 들어 있어 "직접 만들던 것"을 고르는 일로 바뀝니다.

Rust + embassy — 같은 LED 를 async 로

#![no_std]
#![no_main]
use embassy_executor::Spawner;
use embassy_stm32::gpio::{Level, Output, Speed};
use embassy_time::Timer;
use {defmt_rtt as _, panic_probe as _};

#[embassy_executor::main]
async fn main(_spawner: Spawner) {
    let p = embassy_stm32::init(Default::default());
    let mut led = Output::new(p.PA5, Level::High, Speed::Low);  // Nucleo LD2
    loop {
        led.toggle();
        Timer::after_millis(500).await;   // 기다리는 동안 다른 태스크가 돎
    }
}
embassy 는 RTOS 태스크 대신 async/await 로 동시성을 표현하고, 소유권 시스템이 "주변장치 하나를 두 곳에서 잡는" 실수를 컴파일 단계에서 막습니다. 로그 크레이트 defmt 는 PROD 09 의 토큰 로깅을 언어 차원에서 한 것이고, probe-rs 가 굽기 · 디버깅을 맡습니다.
