SET 01

전체 지도 — 여섯 가지 도구가 각각 하는 일

설치 안내서를 따라 하다 막히는 이유의 대부분은 지금 깔고 있는 것이 무슨 역할인지 모르기 때문입니다. 도구 이름이 수십 개로 보여도 역할로 묶으면 여섯 칸뿐입니다. 이 지도를 먼저 머리에 넣고 나머지 절을 읽으세요.

펌웨어 개발 = 빌드(PC) → 굽기(PC → 프로브) → 실행(칩). 막히면 먼저 "몇째 줄에서 막혔나"를 봅니다.

여섯 칸 — 이름이 아니라 역할로 외웁니다

역할하는 일이 탭의 대표
호스트 컴파일러내 PC(x86-64)에서 도는 프로그램을 만듭니다MSYS2 GCC · MSVC cl.exe
크로스 컴파일러PC 에서 돌면서 다른 CPU(AVR · ARM)용 기계어를 만듭니다avr-gcc · arm-none-eabi-gcc
빌드 도구어떤 파일을 어떤 옵션으로 다시 컴파일할지 정합니다make · CMake + Ninja
플래셔산출물(.hex/.bin)을 칩의 플래시 메모리에 씁니다avrdude · STM32CubeProgrammer · OpenOCD
디버그 프로브USB ↔ 칩의 디버그 핀(SWD)을 이어 주는 하드웨어ST-LINK(Nucleo 내장) · J-Link
IDE위 다섯 개를 버튼 하나로 묶어 줍니다VS Code · STM32CubeIDE
서버 개발에 빗대면 — 크로스 컴파일러는 맥에서 리눅스용 도커 이미지를 빌드하는 것과 같습니다 (--platform linux/arm64). 플래셔는 배포 스크립트, 디버그 프로브는 원격 서버에 붙는 SSH + 원격 디버거의 하드웨어판입니다.

"크로스"라는 이름이 붙는 이유

# 같은 소스, 두 가지 컴파일러 — 결과물의 CPU 가 다릅니다
gcc               -c blink.c -o pc.o     # x86-64 기계어 (이 PC 에서 실행 가능)
arm-none-eabi-gcc -c blink.c -o mcu.o    # ARM Thumb 기계어 (PC 에서 실행 불가)
avr-gcc           -c blink.c -o avr.o    # AVR 기계어

# 파일 형식을 보면 차이가 그대로 보입니다 (MSYS2 · 리눅스에 file 명령이 있음)
file pc.o mcu.o avr.o
#  pc.o : ELF 64-bit LSB relocatable, x86-64            (윈도우 GCC 라면 COFF 형식)
#  mcu.o: ELF 32-bit LSB relocatable, ARM, EABI5
#  avr.o: ELF 32-bit LSB relocatable, Atmel AVR 8-bit

# 컴파일러 이름 읽는 법:  <CPU>-<벤더>-<OS>-<ABI>-gcc
#   arm - none - eabi           → ARM 용 · 운영체제 없음(none) · 임베디드 ABI
#   x86_64-w64-mingw32-gcc       → x86-64 용 · 윈도우(mingw) 대상
none 이 핵심입니다 — 운영체제가 없으니 printf 가 화면에 찍힐 곳도, malloc 이 메모리를 달라고 할 커널도 없습니다. 그래서 크로스 툴체인은 컴파일러와 함께 OS 없는 환경용 C 라이브러리(AVR 은 avr-libc, ARM 은 newlib)를 같이 들고 옵니다.

빌드 산출물 세 가지 — 무엇을 칩에 굽나

app.elf   ← 컴파일·링크의 진짜 결과물
          기계어 + 각 조각이 놓일 주소 + 디버그 정보(심볼 · 줄 번호)
          gdb 와 OpenOCD · CubeProgrammer 는 이걸 바로 먹습니다 ★

app.hex   ← elf 에서 '굽기에 필요한 바이트 + 주소'만 텍스트로 뽑은 것
          :100000000C9434000C943E000C943E000C943E0082
          avrdude · 아두이노 업로드가 쓰는 형식 (Intel HEX)

app.bin   ← 주소 정보도 없는 날 바이트 덩어리
          굽는 쪽이 시작 주소를 알아야 합니다 (STM32 는 0x08000000)
          Nucleo 의 USB 드라이브에 끌어다 놓기 · OTA 업데이트 파일

# elf → hex / bin 변환은 objcopy 가 합니다 (u06 · u07)
디버깅은 반드시 .elf 로 — hex 와 bin 에는 함수 이름도 줄 번호도 없습니다. "굽기는 bin, 디버그 심볼은 같은 빌드의 elf" 가 원칙이고, 다른 빌드의 elf 를 붙이면 디버거가 엉뚱한 줄을 가리킵니다.
이 탭과 다른 탭의 경계 — C 문법과 PC 용 빌드의 깊은 내용(분할 컴파일 · Makefile 완전판)은 🅲 C 기초 탭 c10 · ⚙️ C 실전 탭 c25 에, 링커 스크립트 · 스타트업 코드의 속은 🟦 STM32 탭에 있습니다. 여기서는 깔고, 이어 붙이고, 첫 결과를 칩에서 보는 것까지만 합니다.
정리 — 도구는 호스트 컴파일러 · 크로스 컴파일러 · 빌드 도구 · 플래셔 · 디버그 프로브 · IDE 여섯 칸입니다. PC 프로그램은 앞의 셋으로 끝나고, 펌웨어는 결과물(.elf → .hex/.bin)을 USB 너머 칩으로 옮기는 뒤의 셋이 더 붙습니다. 문제가 생기면 "빌드 · 굽기 · 실행" 중 어느 줄인지부터 가립니다.
SET 02

윈도우 PC 용 C — MSYS2 GCC 와 MSVC

펌웨어를 짜더라도 PC 용 C 컴파일러는 따로 있어야 합니다 — 링 버퍼 · CRC · 파서 같은 순수 로직은 칩에 굽기 전에 PC 에서 테스트하는 것이 훨씬 빠르기 때문입니다(🐞 디버깅 · 테스트 탭). 윈도우에는 선택지가 둘입니다. 이 절은 둘 다 깔고 차이를 봅니다.

기본은 MSYS2 UCRT64 GCC. 윈도우 전용 앱이면 MSVC, 리눅스 API 가 필요하면 WSL2 입니다.

① MSYS2 설치 — 10분

# 1) 설치 (msys2.org 의 설치 파일을 받아도 같습니다)
winget install MSYS2.MSYS2          # 기본 경로 C:\msys64

# 2) 시작 메뉴에서 'MSYS2 UCRT64' 터미널을 엽니다 ★ (MSYS · MINGW64 아님)
#    아래부터는 그 터미널 안에서 칩니다
# 3) 패키지 DB 갱신 — 창이 닫히면 다시 열고 한 번 더
pacman -Syu

# 4) GCC · GDB · make · CMake · Ninja · clangd 를 한 번에
pacman -S --needed mingw-w64-ucrt-x86_64-toolchain \
                   mingw-w64-ucrt-x86_64-cmake \
                   mingw-w64-ucrt-x86_64-ninja \
                   mingw-w64-ucrt-x86_64-clang-tools-extra
#   toolchain 그룹에서 '전부 설치?' 물으면 엔터(=all)

gcc --version     # gcc.exe (Rev?, Built by MSYS2 project) 15.x 처럼 나오면 성공
왜 UCRT64 인가 — MSYS2 에는 환경이 여럿(MSYS · MINGW64 · UCRT64 · CLANG64) 있습니다. UCRT64 는 윈도우 10 에 기본으로 들어 있는 새 C 런타임(UCRT)에 링크해서, 만든 exe 가 다른 PC 에서도 문제없이 돌고 MSVC 로 만든 라이브러리와도 잘 섞입니다. 패키지 이름 앞의 mingw-w64-ucrt-x86_64- 가 그 표시입니다.

② PowerShell · VS Code 에서도 gcc 가 보이게 (PATH)

[Environment]::SetEnvironmentVariable('Path', "$p;C:\msys64\ucrt64\bin", 'User')

# ⚠ 이미 열려 있는 터미널 · VS Code 는 옛 PATH 를 기억합니다 → 전부 닫고 새로 엽니다
where.exe gcc       # C:\msys64\ucrt64\bin\gcc.exe 가 '첫 줄'이어야 합니다
gcc --version
mingw32-make --version   # UCRT64 의 make 는 이 이름입니다 (make.exe 아님)
C:\msys64\usr\bin 은 PATH 에 넣지 마세요 — 그 폴더에는 리눅스 흉내용 find · sort · link 가 들어 있어서 윈도우 기본 명령과 MSVC 의 link.exe 를 가로챕니다. 필요한 건 ucrt64\bin 하나뿐입니다. GUI 로 하려면 Win+R → sysdm.cpl → 고급 → 환경 변수.

첫 컴파일 — 표준 버전을 눈으로 확인 🟢 기초

stdver.c — 지금 어느 C 표준으로 컴파일됐나

#include <stdio.h>

int main(void) {
#ifdef __STDC_VERSION__
    printf("__STDC_VERSION__ = %ldL\n", (long)__STDC_VERSION__);
#else
    puts("__STDC_VERSION__ 미정의 (MSVC 에 /std 를 안 준 경우)");
#endif
    return 0;
}
gcc -std=c17 -Wall -Wextra stdver.c -o stdver && ./stdver
#  __STDC_VERSION__ = 201710L

gcc -std=c23 -Wall -Wextra stdver.c -o stdver && ./stdver
#  __STDC_VERSION__ = 202311L      (GCC 14 이상)
#  GCC 13 이하는 -std=c2x 로 쓰고 202000L 이 나옵니다

gcc stdver.c -o stdver && ./stdver     # 플래그 없음
#  GCC 15 이상: 202311L (기본이 gnu23) · GCC 8~14: 201710L (gnu17)

경고 플래그 — 처음부터 이 조합으로

# 학습 · 개발용 기본 세트 (GCC · Clang 공통)
gcc -std=c17 -O0 -g3 \
    -Wall -Wextra -Wpedantic \
    -Wshadow -Wconversion -Wsign-conversion \
    -Wstrict-prototypes -Wmissing-prototypes \
    -Werror=implicit-function-declaration \
    main.c -o app

#  -Wpedantic              GNU 확장을 쓰면 알려 줌 (이식성)
#  -Wconversion            int → uint8_t 같은 '조용한 잘림' ★ 임베디드 필수
#  -Wstrict-prototypes     int f() 처럼 인자 목록 없는 선언 경고
#  -Werror=implicit-...    선언 없이 함수 호출 → 에러 (C99 부터 이미 금지)
#  -g3                     매크로까지 디버그 정보에 (gdb 에서 매크로 값 보기)
왜 -Wconversion 을 굳이 켜나 — 펌웨어는 uint8_t · uint16_t 를 끝없이 섞습니다. uint8_t x = adc_read(); 처럼 10비트 값이 8비트로 잘려도 C 는 아무 말을 안 합니다. 경고가 많이 나와 귀찮지만 그 하나하나가 실제 칩에서 값이 틀어지는 자리입니다(C 기초 탭 c02).
플래그를 안 적으면 컴파일러 버전이 C 버전을 정합니다 — -std=c17 이든 -std=c23 이든 직접 적는 것이 규칙입니다.

MSVC 에서만 막히는 C 코드

// ① 가변 길이 배열(VLA) — MSVC 는 지원하지 않습니다 (C11 부터 선택 기능)
void f(int n) { int buf[n]; }        // MSVC: error C2057

// ② GCC 확장 문법 — __attribute__ 는 MSVC 에 없습니다
__attribute__((packed)) struct S { char a; int b; };
//   MSVC 는 #pragma pack(push, 1) ... #pragma pack(pop)

// ③ 이식 가능하게 — 매크로로 감쌉니다
#if defined(_MSC_VER)
  #define PACKED_BEGIN __pragma(pack(push, 1))
  #define PACKED_END   __pragma(pack(pop))
#else
  #define PACKED_BEGIN
  #define PACKED_END   __attribute__((packed))
#endif
펌웨어 로직을 PC 에서 테스트할 거라면 GCC 쪽이 유리합니다 — 칩용 컴파일러가 전부 GCC 계열이라 __attribute__ · 확장 문법이 그대로 통하기 때문입니다. MSVC 는 윈도우 GUI · DLL 을 만들 때 고르세요. Clang(winget install LLVM.LLVM)도 있지만 윈도우에서는 MSVC 의 헤더 · 링커를 빌려 쓰므로 Build Tools 가 같이 필요합니다.
정리 — 윈도우 PC 용 C 는 MSYS2 UCRT64 GCC 를 기본으로(pacman -S mingw-w64-ucrt-x86_64-toolchain + PATH 에 C:\msys64\ucrt64\bin), 윈도우 전용 앱이면 MSVC(cl /std:c17 /W4 /utf-8)입니다. 어느 쪽이든 표준 버전(-std=c17)과 경고(-Wall -Wextra -Wconversion)를 직접 적습니다 — GCC 15 부터 기본값이 C23 으로 바뀌었습니다.

Make · CMake · Ninja — C 전용 최소 프로젝트와 크로스 빌드

빌드 도구 자체의 문법은 C 기초 탭 c10(분할 컴파일)과 C 실전 탭 c25(Makefile · CMake 완전판)에 있습니다. 여기서는 같은 프로젝트를 Makefile 과 CMakeLists.txt 로 나란히 세운 뒤, 임베디드에서만 필요한 툴체인 파일 · 프리셋 · 빌드 후 처리(objcopy)를 붙입니다.

CMake = 계획(구성 · 생성), Ninja = 실행. 툴체인을 바꾸려면 build 폴더를 지우고 다시 구성합니다.

같은 프로젝트 — Makefile 판

# 폴더:  src/main.c  src/ring.c  include/ring.h
CC      ?= gcc
CFLAGS  := -std=c17 -Wall -Wextra -Wconversion -O2 -g -Iinclude -MMD -MP
SRCS    := $(wildcard src/*.c)
OBJS    := $(SRCS:src/%.c=build/%.o)

build/app: $(OBJS)
	$(CC) $^ -o $@

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build

clean:
	rm -rf build

-include $(OBJS:.o=.d)      # 헤더 의존성 (-MMD 가 만든 .d)
.PHONY: clean

blink.c — 레지스터로 직접 (PB5 = 보드의 D13 · L LED)

#include <avr/io.h>        // DDRB · PORTB · PB5 정의 (-mmcu 로 칩이 골라짐)
#include <util/delay.h>     // _delay_ms — F_CPU 가 정의돼 있어야 함

int main(void) {
    DDRB |= (1 << DDB5);        // PB5 를 출력으로 (Data Direction Register)
    for (;;) {
        PORTB ^= (1 << PORTB5); // 켜고 끄기 뒤집기
        _delay_ms(500);
    }
}
아두이노 코드와 같은 일 — pinMode(13, OUTPUT) = DDRB |= 1<<DDB5, digitalWrite = PORTB 비트 조작입니다. 레지스터의 뜻은 🔷 AVR 탭에서 하나씩 뜯고, 여기서는 빌드해서 굽는 길만 봅니다.

세 명령으로 굽기 — 컴파일 · 변환 · 업로드 🟢 기초

#     176       0       0     176      b0 blink.elf

플래그와 avrdude 옵션 해부

조각뜻
-mmcu=atmega328p칩 종류. 명령어 세트 · 레지스터 주소 · 메모리 크기 · 시작 코드가 정해짐 ★
-DF_CPU=16000000UL"이 칩은 16 MHz 로 돈다"는 약속. 칩 클럭을 바꾸지는 않음
-Os크기 최적화. _delay_ms 는 최적화가 꺼지면 시간이 틀어짐
-c arduino프로그래머 종류 = Uno 의 부트로더(STK500 v1 프로토콜)
-p m328p대상 칩 (서명 0x1E950F 로 대조)
-P COM5 -b 115200포트와 속도. Uno 의 Optiboot 은 115200
-U flash:w:blink.hex:i메모리:동작(w 쓰기 · r 읽기 · v 검증):파일:형식(i = Intel HEX)
F_CPU 를 틀리게 주면 — -DF_CPU=8000000UL 로 빌드해 16 MHz 칩에 구우면 지연 루프가 절반만 돌아 500 ms 가 250 ms 가 됩니다. 시리얼 보레이트 계산도 같은 값을 쓰므로 UART 글자가 깨지는 원인이 되기도 합니다(📡 통신 탭).
.hex 에 담기는 것은 칠한 칸뿐입니다. 부트로더 512 B 를 빼면 내 프로그램 한도는 32,256 B 입니다.

업로드 버튼 뒤에서 — 부트로더와 avrdude 의 대화 🟡 중급

아두이노가 프로그래머 없이 USB 로 구워지는 이유가 부트로더입니다. 대신 그 512 B 와 리셋 타이밍을 대가로 냅니다.

Makefile — 매번 치지 않게

MCU     := atmega328p

# make flash PORT=COM7 처럼 바꿔 쓰기 (같은 줄에 주석을 달면 값 뒤에 공백이 붙습니다)
PORT    ?= COM5

OBJCOPY := avr-objcopy

           -ffunction-sections -fdata-sections
LDFLAGS := -mmcu=$(MCU) -Wl,--gc-sections

blink.hex: blink.elf
	$(OBJCOPY) -O ihex -R .eeprom $< $@
	avr-size $<

blink.elf: blink.c
	$(CC) $(CFLAGS) $(LDFLAGS) $^ -o $@

flash: blink.hex
	avrdude -c arduino -p m328p -P $(PORT) -b 115200 -U flash:w:$<:i

.PHONY: flash

.hex 한 줄 읽기 (Intel HEX)

:10 0000 00 0C9434000C943E000C943E000C943E00 82
 │   │   │   │                                │
 │   │   │   └ 데이터 16 B                     └ 체크섬
 │   │   └ 레코드 종류 00 = 데이터 (01 = 파일 끝)
 │   └ 주소 0x0000
 └ 바이트 수 0x10 = 16

데이터 앞 4 B  0C 94 34 00  = jmp 0x0068   ← 리셋 벡터 (워드 주소 0x34 × 2)
다음 4 B       0C 94 3E 00  = jmp 0x007C   ← 안 쓰는 인터럽트 → __bad_interrupt

체크섬 = (모든 바이트 합의 하위 8비트)의 2의 보수
  0x10+0x00+0x00+0x00+0x0C+0x94+... 합의 하위 바이트 0x7E → 0x100-0x7E = 0x82

마지막 줄은 항상   :00000001FF   (파일 끝)
업로드 전 백업 — -U flash:r:backup.hex:i 로 지금 칩 내용을 먼저 읽어 두면, 통신이 되는지 확인도 되고 원래 프로그램으로 되돌릴 수도 있습니다.

avrdude -c usbasp -p m328p -U lfuse:r:-:h -U hfuse:r:-:h -U efuse:r:-:h
#   Uno 공장값: lfuse 0xFF · hfuse 0xDE · efuse 0xFD (0xFD 는 0x05 로 보이기도 함)

벽돌을 만드는 두 가지 실수

① 클럭 퓨즈(CKSEL)를 '외부 클럭'으로 잘못 씀
   → 크리스털이 있어도 칩이 안 깨어남 → ISP 응답 없음
   → 복구: 다른 보드의 핀으로 클럭을 넣어 주거나 고전압 프로그래머

② hfuse 의 SPIEN 을 끄거나 RSTDISBL 을 켬
   → ISP 자체가 막힘 → 고전압(HV) 프로그래밍만 가능

예방
   · 퓨즈 계산은 웹 계산기(AVR fuse calculator)로 두 번 확인
   · avrdude -n (dry-run, 실제 쓰기 없음)으로 명령부터 확인
   · 학습용 Uno 는 퓨즈를 건드릴 일이 거의 없습니다
-c arduino 로는 퓨즈를 바꿀 수 없습니다 — 부트로더는 자기 자신과 퓨즈를 못 고칩니다. 그래서 USB 업로드만 하는 동안에는 칩을 벽돌로 만들 위험이 거의 없고, ISP 를 쓰기 시작할 때부터 조심하면 됩니다.
정리 — AVR 은 avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL -Os → avr-objcopy -O ihex -R .eeprom → avrdude -c arduino -p m328p -P COM5 -b 115200 -U flash:w:blink.hex:i 세 줄입니다. -mmcu 는 칩을, F_CPU 는 클럭 약속을 정하고, Uno 는 부트로더 512 B 덕분에 프로그래머 없이 USB 로 구워집니다.

손으로 빌드 — Nucleo-F446RE LED(PA5) 깜빡이기 🟢 기초

필요한 파일 다섯 개와 main.c

blink/
├─ Src/main.c                     ← 내가 쓰는 것
├─ Src/system_stm32f4xx.c         ← SystemInit (클럭 · FPU 켜기)
├─ Startup/startup_stm32f446xx.s  ← 벡터 표 · Reset_Handler
├─ STM32F446RETX_FLASH.ld         ← 링커 스크립트
└─ Drivers/CMSIS/...              ← 레지스터 정의 헤더
   (뒤의 넷은 STM32CubeMX 가 만든 프로젝트에서 그대로 가져옵니다 — u08)
#include "stm32f4xx.h"     // -DSTM32F446xx 로 F446 정의가 골라짐

static void delay(volatile uint32_t n) { while (n--) { } }

int main(void) {
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;   // GPIOA 에 클럭 공급
    (void)RCC->AHB1ENR;                    // 클럭이 실제로 켜질 때까지 한 번 읽기
    GPIOA->MODER = (GPIOA->MODER & ~GPIO_MODER_MODER5)
                 | GPIO_MODER_MODER5_0;    // PA5 = 범용 출력(01)
    for (;;) {
        GPIOA->ODR ^= GPIO_ODR_OD5;        // LD2 켜고 끄기
        delay(1000000);                    // 대략 0.5~1초 (클럭 · 최적화에 따라 다름)
    }
}

디버그 프로브 — ST-LINK · J-Link · CMSIS-DAP 와 SWD 배선

SVD 파일 — 레지스터를 이름으로 보기

SVD 는 칩 회사가 주는 "레지스터 지도" XML입니다. Cortex-Debug 에 넣어 두면 디버그 중에 GPIOA → ODR → OD5 처럼 주변장치 레지스터를 이름과 비트 단위로 보고 고칠 수 있습니다. F446 용은 CubeCLT 설치 폴더의 STMicroelectronics_CMSIS_SVD 안이나 ST 웹의 칩 페이지(CAD Resources)에 있습니다.

디버거로 멈춘 동안에도 주변장치는 돕니다 — 브레이크포인트에 걸려도 타이머 · UART 수신은 계속돼서 "디버깅할 때만 데이터가 깨지는" 일이 생깁니다. STM32 는 DBGMCU 설정으로 디버그 정지 중 타이머를 멈출 수 있습니다(🐞 디버깅 탭).
정리 — 프로브는 USB 를 SWD(SWCLK · SWDIO · GND + VTref, 권장 NRST) 로 바꾸는 하드웨어입니다. Nucleo 는 ST-LINK 가 내장이라 케이블 하나면 되고, 외부 보드는 CN2 점퍼를 빼고 CN4 에서 선을 땁니다. PC 쪽은 OpenOCD(또는 pyOCD · ST-LINK 서버) 가 GDB 서버가 되고, VS Code 는 Cortex-Debug 로 F5 디버그를 합니다.
SET 10

PlatformIO — 여러 보드를 한 프로젝트 형식으로

지금까지는 칩마다 툴체인을 손으로 깔았습니다. PlatformIO 는 그것을 패키지 관리자처럼 처리합니다 — platformio.ini 에 "Uno, 아두이노 프레임워크"라고 적으면 맞는 컴파일러 · 라이브러리 · 업로더를 알아서 받아 옵니다. 서버 개발자에게는 Gradle · npm 과 같은 경험이라 진입이 가장 쉽습니다.

PlatformIO 의 단위는 환경(env) 입니다. 보드를 바꾸는 일이 ini 의 한 블록을 추가하는 일이 됩니다.

설치 — 둘 중 하나

# ① VS Code 확장 'PlatformIO IDE' (platformio.platformio-ide)
#    설치하면 PlatformIO Core 와 전용 파이썬 환경을 스스로 받습니다
#    왼쪽 막대의 개미 머리 아이콘 → New Project

# ② 명령줄만 (CI · 다른 편집기)
pip install -U platformio        # 또는 pipx install platformio
pio --version

# 새 프로젝트
mkdir blink-pio; cd blink-pio
pio project init --board uno --board nucleo_f446re
이미 설치한 툴체인과는 별개입니다 — PlatformIO 는 %USERPROFILE%\.platformio\packages 에 자기 avr-gcc · arm-none-eabi-gcc 를 따로 받습니다. 버전이 Arm 공식 최신보다 늦을 수 있으니, 특정 버전이 필요하면 platform_packages 로 바꿔 끼웁니다.

board = uno

[env:nucleo_f446re]

upload_protocol = stlink
debug_tool = stlink

[env:native]                    ; PC 에서 로직 단위 테스트 (보드 불필요 · PC 의 gcc 사용 — u02)

SET 11

하드웨어 없이 연습 — 시뮬레이터로 어디까지 되나

보드가 오기 전에도, 출장 중에도, CI 서버에서도 펌웨어를 돌려 볼 수 있습니다. 다만 시뮬레이터마다 잘하는 칸이 전혀 다릅니다 — 브라우저에서 LED 를 보는 것, 회로의 전압을 보는 것, CPU 명령을 정확히 돌리는 것은 서로 다른 도구의 몫입니다. 그리고 시뮬레이터에서 된다고 실제 보드에서 되는 것은 아닙니다.

위 두 줄은 "보는" 도구, 아래 세 줄은 "돌리는" 도구입니다. 학습엔 Wokwi, 회귀 테스트엔 Renode · QEMU.

#   UART0 출력이 터미널에 찍힘. -s -S 를 붙이면 gdb(:1234) 대기

# QEMU — Cortex-M4 순수 로직 (보드 주변장치 없이 CPU 만)
#   mps2-an386 용 벡터 표(startup.c)와 링커 스크립트(mps2.ld)를 함께 넣습니다
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb --specs=rdimon.specs \

qemu-system-arm -M mps2-an386 -nographic -semihosting -kernel test.elf

세미호스팅 = 칩(또는 에뮬레이터)이 디버거를 통해 PC 의 printf · 파일을 빌려 쓰는 방식입니다. 실제 보드에서도 OpenOCD 의 arm semihosting enable 로 되지만 아주 느리고 디버거 없이는 멈추므로 테스트 전용입니다.

SimulIDE — 회로를 그리고 hex 를 넣기

SimulIDE 는 회로 시뮬레이터 + MCU 시뮬레이터입니다. 브레드보드처럼 저항 · LED · 포텐셔미터 · 오실로스코프를 놓고 ATmega328P 에 내가 만든 .hex 를 올리면 핀 전압이 실제로 오르내리는 것을 봅니다. "풀업 저항이 없으면 버튼 입력이 왜 떠다니나" 같은 전기 쪽 직관을 기르기에 가장 좋습니다(🔩 하드웨어 기초 탭).

처음 2주 추천 루트 — Wokwi 로 아두이노 예제 → u06 의 blink.hex 를 Wokwi(VS Code)로 → SimulIDE 로 풀업 · 분압 회로 → 보드 도착 후 같은 hex 를 실제로 굽기.

실무에선 이렇게 — 시뮬레이터가 거짓말하는 곳 🔴 실무

항목시뮬레이터실제 보드
타이밍대개 '대략' — 사이클 정확한 건 simavr 정도클럭 오차(내부 RC 는 ±1~2 %), 인터럽트 지연이 섞임
전기이상적인 전압 · 노이즈 없음버튼 채터링 · 긴 선의 노이즈 · 전원 강하
주변장치모델이 있는 것만, 에러 플래그는 거의 안 남오버런 · 프레이밍 에러 · DMA 경합이 실제로 남
초기값RAM 이 0 으로 시작하는 경우가 많음RAM 은 쓰레기 값 — 초기화 안 한 변수가 여기서 드러남
USB · 무선대부분 없음열거 · 드라이버 · 전파 환경
전력안 봄슬립 전류 · 배터리 수명 (🚀 양산 탭)
시뮬레이터 통과 = 로직이 맞다는 뜻까지만 — "시뮬레이터에서는 되는데 보드에서는 안 된다"의 대부분은 초기화하지 않은 변수 · volatile 누락 · 타이밍 가정입니다. 시뮬레이터는 순수 로직 회귀 테스트에 쓰고, 하드웨어 의존 부분은 반드시 실제 보드(가능하면 로직 분석기와 함께 — u12)로 확인합니다.
정리 — 눈으로 배우는 건 Wokwi(브라우저 · VS Code) 와 SimulIDE(회로), 자동으로 돌리는 건 simavr(AVR) · QEMU(uno · mps2-an386 세미호스팅) · Renode(STM32 · 다중 칩) 입니다. 시뮬레이터는 로직까지만 보증합니다 — 타이밍 · 전기 · 초기값 문제는 실제 보드에서만 드러납니다.

첫 구매 가이드 — 보드 두 장과 측정 도구 둘

LED 저항값 — 직접 계산해 보기

옴의 법칙  I = (전원 전압 − LED 순방향 전압) ÷ R
  (순방향 전압 Vf = LED 가 켜지려면 먹는 전압. 빨강 약 2.0 V)

Uno (5 V 핀), R = 220 Ω
  I = (5.0 − 2.0) ÷ 220 = 0.0136 A ≈ 13.6 mA      ✓ 핀 권장 20 mA 이하

STM32 (3.3 V 핀), R = 220 Ω
  I = (3.3 − 2.0) ÷ 220 = 0.0059 A ≈ 5.9 mA       ✓ 충분히 보임

저항 없이 바로 연결하면?
  I = (5.0 − 2.0) ÷ (거의 0) → 핀의 한계까지 흐름
  ATmega328P 핀 절대 최대 40 mA · STM32F4 핀 절대 최대 25 mA
  → LED 나 핀이 상합니다 ✗
서버 개발에 빗대면 — 저항은 rate limiter 입니다. 없으면 요청(전류)이 상한 없이 몰려 서버(핀)가 죽습니다. 전압 · 전류 · 저항의 기초는 🔩 하드웨어 기초 탭에서 처음부터 다룹니다.

24 MHz · 8 채널 저가형 (Cypress FX2 칩 기반 '호환품')

샘플링 정리
  24 MHz 로 샘플 → 신호 주파수의 4배 이상이면 모양이 보임
  UART 115200 bps, I²C 400 kHz, SPI 수 MHz 까지는 충분
  아날로그 파형(전압 크기)은 못 봄 → 오실로스코프의 일
입력 전압 확인 — 저가형은 대개 5 V 까지만 견딥니다. 12 V · 24 V 신호(산업용 센서, RS-232 원 신호)에 바로 물리면 망가집니다. GND 를 반드시 대상 보드 GND 에 함께 물려야 파형이 제대로 나옵니다.

  ③ D0(RX) · D1(TX) 에 무언가 연결됨     → 업로드 동안 선을 뽑기
  ④ 자동 리셋이 안 됨 (DTR 미연결 클론)  → 업로드 직전 리셋 버튼을 눌렀다 떼기

  ⑥ 칩이 Uno 가 아니다 (Uno R4 등)        → u12
