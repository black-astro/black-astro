UV · 파이썬 환경 관리의 최신 표준

venv도 pip도
더 이상
따로 쓰지 않는다

uv는 Rust로 만든 파이썬 패키지·프로젝트 관리자입니다. 가상환경 생성, 파이썬 버전 설치, 의존성 해결, 락파일 관리를 하나의 명령어로 처리하고, pip보다 10~100배 빠릅니다.

UV 01

왜 uv인가

기존 방식의 고통을 먼저 정리하면 uv가 무엇을 해결했는지 명확해집니다.

패키지 설치 속도 (pandas + numpy + opencv + pyside6 기준)
pip install
poetry install
uv sync

캐시가 있으면 uv는 하드링크로 파일을 연결해 사실상 즉시 끝납니다. 실제 값은 환경에 따라 다릅니다.

기존 방식 (도구가 4개)

pyenv install 3.12.0        # 파이썬 버전 관리
python -m venv .venv        # 가상환경 생성
.venv\Scripts\activate      # 활성화 (까먹기 쉬움)
pip install pandas          # 설치
pip freeze > requirements.txt   # 수동 기록 (부정확!)
  • activate를 잊으면 전역에 설치되어 환경이 오염됨
  • requirements.txt는 직접 설치한 것과 딸려온 것이 구분 안 됨
  • 의존성 재현이 불완전 — “내 PC에선 되는데요”
  • 파이썬 버전 관리는 또 다른 도구(pyenv)가 필요

uv 방식 (도구가 1개)

uv init myapp               # 프로젝트 + pyproject.toml 생성
cd myapp
uv add pandas               # 설치 + 기록 + 락파일 갱신 (한 번에)
uv run main.py              # 가상환경 자동 인식 후 실행
  • activate 불필요 — uv run이 알아서 .venv를 씁니다
  • pyproject.toml = 내가 선언한 의존성 (사람이 관리)
  • uv.lock = 실제 설치된 전체 트리 (기계가 관리, 커밋 대상)
  • 파이썬 버전까지 uv python install로 해결
Spring 비유 — pyproject.toml은 pom.xml / build.gradle, uv.lock은 정확한 버전이 고정된 의존성 트리 (Gradle의 lockfile)입니다. uv sync는 mvn install에 해당합니다.

비교 — 파이썬 환경 도구 4파전

도구장점단점선택 기준
uv가장 빠름, 버전관리+패키지+락파일 통합, activate 불필요비교적 신생 (그러나 급속히 표준화 중)★ 새 프로젝트 기본값

UV 02

설치와 첫 프로젝트

아래 터미널에서 재생을 누르면 실제 명령 흐름이 순서대로 타이핑됩니다.

프로젝트 생성 시나리오
PowerShell — D:\work
PS D:\work>

설치 (Windows)

# PowerShell — 공식 설치 스크립트
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 또는 이미 쓰는 도구가 있다면
winget install --id=astral-sh.uv
pip install uv
scoop install uv

# 확인
uv --version

# 업데이트
uv self update
설치 후 터미널을 다시 켜세요 — PATH가 갱신되지 않아 uv를 찾을 수 없습니다가 뜨는 경우가 대부분입니다. PyCharm을 쓴다면 IDE도 재시작해야 인식합니다.

프로젝트 만들기

# 새 폴더로 시작
uv init myapp
cd myapp

# 이미 있는 폴더에서 시작
cd 기존폴더
uv init

# 앱 형태(기본) vs 라이브러리 형태
uv init --app myapp
uv init --lib mylib        # src/ 레이아웃 + 빌드 설정

# 파이썬 버전 지정해서 생성
uv init --python 3.12 myapp
myapp/ pyproject.toml # 프로젝트 설정 + 의존성 선언 uv.lock # 정확한 버전 고정 (커밋 O) .python-version # 사용할 파이썬 버전 main.py README.md .venv/ # 가상환경 (커밋 X)
UV 03

파이썬 버전 관리

pyenv 없이 uv 하나로 여러 파이썬 버전을 깔고 프로젝트별로 고정합니다.

# 설치 가능한 버전 목록
uv python list

# 특정 버전 설치 (시스템 파이썬을 건드리지 않음)
uv python install 3.12
uv python install 3.11 3.12 3.13     # 여러 개 동시에

# 현재 프로젝트가 쓸 버전 고정 -> .python-version 파일 생성
uv python pin 3.12

# 설치된 파이썬 위치 확인
uv python find

# 특정 버전으로 가상환경 만들기
uv venv --python 3.12
왜 프로젝트마다 버전을 고정하나 — PyWinAuto·OpenCV 같은 라이브러리는 특정 파이썬 버전에서만 휠(wheel)이 제공되는 경우가 있습니다. .python-version을 커밋해 두면 팀원 모두 같은 버전에서 돌아갑니다.
PySide6 주의 — 최신 파이썬이 나온 직후에는 PySide6 휠이 아직 없을 수 있습니다. GUI 프로젝트라면 3.11~3.12 같은 안정 버전으로 pin 해 두는 편이 안전합니다.
UV 04

패키지 add · sync · lock

이 세 명령의 관계만 이해하면 uv는 끝입니다.

3단계 흐름
1. 선언
uv add pandas
pyproject.toml 에
"pandas>=2.2" 기록
→
2. 해결
uv lock
의존성 트리 전체를
uv.lock 에 고정
→
3. 반영
uv sync
.venv 를 lock 과
정확히 일치시킴

uv add는 이 3단계를 자동으로 다 수행합니다. lock/sync를 따로 칠 일은 드뭅니다.

uv add 한 줄의 여정 uv add pandas
자동 3단선언 → 잠금 → 설치가
순서대로 일어남

패키지 다루기

uv add pandas                    # 최신 버전
uv add "pandas>=2.2,<3"          # 범위 지정
uv add pandas numpy matplotlib   # 여러 개
uv add --dev pytest ruff         # 개발 전용 (배포엔 미포함)
uv add git+https://github.com/user/repo
uv add ./local_package           # 로컬 경로

uv remove pandas                 # 삭제

uv sync                          # lock 대로 환경 맞추기 (팀원 최초 1회)
uv sync --frozen                 # lock 갱신 없이 (CI 권장)
uv lock --upgrade                # 전체 최신으로 갱신
uv lock --upgrade-package pandas # 특정 패키지만 갱신

uv tree                          # 의존성 트리 보기
uv pip list                      # 설치 목록

커밋 규칙 (.gitignore)

# 반드시 커밋
pyproject.toml      # 무엇을 원하는지
uv.lock             # 정확히 무엇이 깔렸는지
.python-version     # 어떤 파이썬으로

# 커밋 금지 (.gitignore)
.venv/
__pycache__/
*.pyc
.env
uv.lock을 꼭 커밋하세요 — 이게 없으면 팀원마다 다른 버전이 깔려 “제 컴퓨터에선 되는데요” 문제가 그대로 재발합니다. Gradle lockfile을 커밋하는 것과 같은 이유입니다.
새 팀원 온보딩 — git clone 후 uv sync 한 번이면 파이썬 설치부터 패키지까지 끝납니다.
UV 05

uv run — activate를 잊어도 되는 이유

uv run은 실행 직전에 환경을 자동으로 맞춰줍니다.

실행하기

uv run main.py                 # 스크립트 실행
uv run python                  # REPL 진입
uv run python -m pytest        # 모듈 실행
uv run pytest                  # 설치된 명령 실행
uv run --with rich python      # 임시로 패키지 추가해 실행

# 매번 uv run 이 귀찮다면 (기존 방식도 가능)
.venv\Scripts\activate         # Windows
source .venv/bin/activate      # Mac/Linux
uv run이 하는 일 — ① lock 확인 → ② 환경이 다르면 자동 동기화 → ③ .venv의 파이썬으로 실행. 즉 항상 최신 상태에서 실행되는 것이 보장됩니다.

단일 파일 스크립트 (PEP 723)

# analyze.py — 파일 안에 의존성을 직접 적습니다
# /// script
# requires-python = ">=3.12"
# dependencies = ["pandas", "matplotlib"]
# ///

import pandas as pd
df = pd.read_csv("sales.csv")
print(df.describe())
# 프로젝트 없이 바로 실행 — uv가 임시 환경을 만들어 줌
uv run analyze.py

# 의존성 블록을 명령으로 추가
uv add --script analyze.py pandas matplotlib
실무에서 아주 유용 — 동료에게 .py 파일 하나만 보내도 uv run 한 줄로 돌아갑니다. 설치 안내 문서가 필요 없습니다.
UV 06

pyproject.toml 해부

프로젝트의 모든 설정이 이 파일 하나에 모입니다.

[project]
name = "myapp"
version = "0.1.0"
description = "업무 자동화 도구"
requires-python = ">=3.12"
dependencies = [                 # ← uv add 가 여기에 씁니다
    "pandas>=2.2.0",
    "numpy>=2.0",
    "opencv-python>=4.10",
    "pyside6>=6.7",
]

[project.scripts]                # 실행 명령 등록
myapp = "myapp.main:run"         # -> uv run myapp

[dependency-groups]              # uv add --dev 가 여기에
dev = ["pytest>=8.0", "ruff>=0.6"]

[tool.uv]
package = false                  # 앱이면 false, 라이브러리면 true

[tool.ruff]                      # 린터 설정도 같은 파일에
line-length = 100
target-version = "py312"

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

버전 표기법

표기의미
pandas아무 버전이나 (권장하지 않음)
pandas>=2.22.2 이상 (가장 흔함)
pandas==2.2.3정확히 이 버전
pandas~=2.2.02.2.x 안에서만 (패치만 허용)
pandas>=2.2,<3메이저 업그레이드 차단

개발 도구 세팅 (권장)

uv add --dev ruff pytest

uv run ruff check .        # 린트 검사
uv run ruff check --fix .  # 자동 수정
uv run ruff format .       # 포매팅 (black 대체)
uv run pytest -v           # 테스트
Spring 비유 — ruff는 Checkstyle + SpotBugs + 포매터를 하나로 합친 도구입니다. Rust로 짜여 있어 수천 개 파일도 1초 안에 끝납니다. [tool.ruff] 설정이 pyproject.toml에 같이 들어가는 것도 Gradle 설정이 build.gradle에 모이는 것과 같습니다.
UV 07

uvx · 기존 프로젝트 마이그레이션

설치하지 않고 실행하기, 그리고 requirements.txt에서 넘어오기.

uvx — 일회용 실행

# 설치 없이 바로 실행 (npx 와 같은 개념)
uvx ruff check .
uvx black .
uvx httpie GET example.com
uvx --from pyinstaller pyinstaller main.py

# 자주 쓰는 도구는 전역 설치
uv tool install ruff
uv tool install pyinstaller
uv tool list
uv tool upgrade --all
프로젝트를 오염시키지 않습니다 — 도구는 격리된 환경에 깔리므로 프로젝트 의존성에 섞이지 않습니다. 린터·포매터·빌드도구가 여기 해당합니다.

기존 프로젝트 옮기기

# requirements.txt 가 있는 프로젝트에서
uv init                                  # pyproject.toml 생성
uv add -r requirements.txt               # 통째로 가져오기
uv lock                                  # 락파일 생성
del requirements.txt                     # 이제 불필요

# 반대로 내보내야 할 때 (배포 환경이 pip만 지원)
uv export --format requirements-txt > requirements.txt
uv export --no-dev > requirements.txt

# pip 호환 명령도 그대로 제공 (더 빠름)
uv pip install pandas
uv pip freeze
uv pip sync requirements.txt
Docker/CI 팁 — 빌드 단계에서는 uv sync --frozen --no-dev를 쓰세요. 락파일을 갱신하지 않아 재현성이 보장되고 개발 도구도 빠집니다.

고급 — 워크스페이스와 패키지 발행

워크스페이스 — 한 저장소, 여러 패키지

# 루트 pyproject.toml
[tool.uv.workspace]
members = ["apps/*", "libs/*"]

# 구조
# repo/
#   pyproject.toml        <- workspace 선언
#   uv.lock               <- ★ 전체가 락파일 하나 공유
#   apps/gui/             <- PySide6 앱
#   apps/batch/           <- 배치 스크립트
#   libs/core/            <- 공용 로직 (분석·DB)

# apps/gui/pyproject.toml 에서 내부 패키지 참조
[project]
dependencies = ["core"]
[tool.uv.sources]
core = { workspace = true }
uv run --package gui python -m gui    # 특정 멤버 실행
uv sync --all-packages                # 전부 동기화
Spring 비유 — Gradle 멀티모듈과 동일합니다. GUI·배치·공용 로직을 한 repo에서 관리하면서 버전 충돌은 락파일 하나로 원천 차단됩니다.

라이브러리 빌드·사내 배포

# --lib 로 시작한 프로젝트는 빌드 가능
uv build                     # dist/*.whl + *.tar.gz 생성

# 팀에 나눠주기 (PyPI 없이)
# 방법 1: 파일로 직접
uv add ../core-0.2.0-py3-none-any.whl
# 방법 2: git 으로
uv add git+https://github.com/우리팀/core --tag v0.2.0
# 방법 3: 사내 인덱스 (pypiserver/devpi/Nexus)
uv publish --index-url http://pypi.내부주소/simple/

# 버전 규칙 (SemVer): 깨지는 변경=메이저,
# 기능 추가=마이너, 버그픽스=패치
언제 라이브러리로 쪼개나 — 같은 함수(전처리·DB 접근)를 두 번째 프로젝트에서 복사하게 되는 순간입니다. 그 전까지는 한 프로젝트 안의 모듈이면 충분합니다.
UV 08
