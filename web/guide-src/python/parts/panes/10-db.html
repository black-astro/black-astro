SECTION 02

테이블 · 행 · 열 · 키(Key)

관계형 DB는 결국 엑셀 시트 여러 장입니다. 다른 점은 시트끼리 키로 연결되어 있고, 그 규칙을 DB가 강제로 지켜 준다는 것입니다.

두 테이블과 키의 관계

member (회원)

orders (주문)

-- 테이블 만들기 (PostgreSQL / MySQL 기준)
CREATE TABLE member (
    id        INT PRIMARY KEY,          -- 기본키: 중복 불가 + NULL 불가
    name      VARCHAR(50) NOT NULL,     -- 반드시 값이 있어야 함
    email     VARCHAR(120) UNIQUE,      -- 중복 불가 (NULL 은 허용)
    joined_at DATE DEFAULT CURRENT_DATE
);

CREATE TABLE orders (
    id        INT PRIMARY KEY,
    member_id INT NOT NULL,
    amount    DECIMAL(12,2) NOT NULL CHECK (amount >= 0),
    ordered_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- 외래키: member 에 없는 회원의 주문은 아예 저장이 안 된다
    FOREIGN KEY (member_id) REFERENCES member(id)
);
제약(Constraint)뜻없으면 생기는 일
PRIMARY KEY이 행을 유일하게 가리키는 값같은 사람이 두 번 들어가도 구분 불가
FOREIGN KEY다른 표의 PK 를 가리킴존재하지 않는 회원의 주문이 쌓임(고아 데이터)
NOT NULL빈 값 금지이름 없는 회원이 생김
UNIQUE중복 금지같은 이메일로 계정 2개
CHECK값의 범위 제한금액이 −5000원인 주문
DEFAULT안 넣으면 이 값가입일이 비는 행
PK는 무엇으로 잡나 — 주민번호·이메일 같은 의미 있는 값은 피하세요(바뀔 수 있고 개인정보). 자동 증가 정수가 표준입니다: Oracle GENERATED AS IDENTITY · MySQL AUTO_INCREMENT · PostgreSQL GENERATED ALWAYS AS IDENTITY(구버전 SERIAL).
SECTION 03

SQL 실행 순서 — 적힌 순서대로 실행되지 않는다

SQL을 배울 때 가장 먼저 무너지는 지점입니다. SELECT는 거의 마지막에 실행됩니다 — 그래서 WHERE에서는 SELECT에서 만든 별칭을 못 씁니다.

쿼리 한 개가 실행되는 진짜 순서
속도 
SELECT   team, SUM(amount) AS total
FROM     orders
JOIN     member ON member.id = orders.member_id
WHERE    ordered_at >= '2026-01-01'
GROUP BY team
HAVING   SUM(amount) > 1000
ORDER BY total DESC
LIMIT    5;
여기서 오는 대표 에러 2가지
① WHERE total > 1000 → 에러. total은 SELECT에서 만든 별칭인데 WHERE가 먼저 실행되므로 아직 존재하지 않습니다. 집계 조건은 HAVING에 씁니다.
② WHERE SUM(amount) > 1000 → 에러. 집계는 GROUP BY 이후에 만들어집니다.

WHERE — 조건에 맞는 행만 남기기

엑셀의 자동 필터와 완전히 같습니다. 조건을 바꾸면 행이 실제로 걸러집니다.

조건을 눌러 보세요
0남은 행
0전체 행

-- 비교           =  <>(또는 !=)  <  >  <=  >=
-- 범위           BETWEEN 100 AND 500          -- 양 끝 포함
-- 목록           IN ('A','B','C')             -- = 를 OR 로 늘어놓은 것
-- 패턴           LIKE '김%'     -- % = 아무 글자 여러 개, _ = 아무 글자 하나
-- 없음(NULL)     IS NULL / IS NOT NULL        -- ★ = NULL 은 절대 안 됨!
-- 조합           AND(그리고)  OR(또는)  NOT(아님)

SELECT * FROM orders
WHERE  team = 'A'
  AND  amount >= 300
  AND  ordered_at BETWEEN '2026-01-01' AND '2026-03-31';
NULL은 “값이 없음”이지 0이나 빈 문자열이 아닙니다. WHERE grade = NULL은 에러가 아니라 조용히 0건을 돌려줍니다. NULL 비교는 반드시 IS NULL / IS NOT NULL.
※ Oracle은 예외적으로 빈 문자열('')을 NULL로 취급합니다 — 다른 DB에서 옮겨올 때 대표적인 함정입니다.

JOIN — 두 표를 키로 이어붙이기

엑셀 VLOOKUP이 하는 일입니다. 다만 SQL은 못 찾았을 때 어떻게 할지를 4가지 방식으로 고를 수 있습니다. 버튼을 눌러 결과 행이 어떻게 달라지는지 보세요.

JOIN 4종 — 결과 행이 바뀝니다

member (왼쪽)

orders (오른쪽)

memberorders

결과

-- 기본형: ON 에 "이어 붙일 기준"을 쓴다
SELECT m.name, o.amount
FROM   member m
JOIN   orders o ON o.member_id = m.id;      -- JOIN = INNER JOIN

-- 주문이 없는 회원도 보고 싶다 -> LEFT
SELECT m.name, o.amount
FROM   member m
LEFT JOIN orders o ON o.member_id = m.id;   -- 없으면 NULL 로 채워짐

-- "주문이 한 번도 없는 회원만" (안티 조인) — 자주 쓰는 패턴
SELECT m.name
FROM   member m
LEFT JOIN orders o ON o.member_id = m.id
WHERE  o.id IS NULL;                        -- ★ 이 한 줄이 핵심
LEFT JOIN 을 WHERE 로 죽이는 실수 — LEFT JOIN orders o ... WHERE o.amount > 100 이라고 쓰면 짝이 없어 NULL이 된 행이 WHERE에서 전부 탈락해 결국 INNER JOIN이 됩니다. 조건을 ON 절로 옮기거나 OR o.id IS NULL을 붙이세요.

GROUP BY — 묶어서 한 줄로 요약하기

엑셀 피벗테이블입니다. 행들이 팀별로 모였다가 한 줄로 접히는 과정을 보세요. Pandas의 groupby와 완전히 같은 개념입니다.

Split → Apply → Combine
속도

원본 행

결과

SELECT team,
       COUNT(*)      AS 건수,
       SUM(amount)   AS 합계,
       AVG(amount)   AS 평균,
       MAX(amount)   AS 최대,
       MIN(amount)   AS 최소
FROM   orders
WHERE  ordered_at >= '2026-01-01'    -- ① 먼저 행을 거르고
GROUP BY team                         -- ② 팀별로 묶어서
HAVING COUNT(*) >= 2                  -- ③ 묶은 결과를 다시 거르고
ORDER BY 합계 DESC;                   -- ④ 정렬

-- COUNT 의 3가지 얼굴
COUNT(*)          -- 행 개수 (NULL 포함)
COUNT(grade)      -- grade 가 NULL 이 아닌 행의 개수   ★ 자주 헷갈림
COUNT(DISTINCT team)  -- 서로 다른 team 의 개수
규칙 하나만 기억하세요 — GROUP BY를 쓰면 SELECT에는 ① GROUP BY에 적은 컬럼과 ② 집계 함수만 올 수 있습니다. (MySQL은 기본 설정에 따라 이를 눈감아 주기도 하는데, 그때 나오는 값은 아무 행에서나 하나 집어온 값이라 신뢰하면 안 됩니다.)
SECTION 07

서브쿼리와 윈도우 함수

“팀별 1등만”, “전체 평균보다 큰 주문만”, “누적 합계” 같은 요구는 GROUP BY만으로는 안 됩니다. 여기서 윈도우 함수가 등장합니다.

서브쿼리 — 쿼리 안의 쿼리

-- ① WHERE 안에서 (스칼라)
SELECT * FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

-- ② FROM 안에서 (인라인 뷰)
SELECT t.team, t.합계
FROM (SELECT team, SUM(amount) AS 합계
      FROM orders GROUP BY team) t
WHERE t.합계 > 1000;

-- ③ EXISTS — "있기만 하면" (IN 보다 빠른 경우가 많음)
SELECT * FROM member m
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.member_id = m.id);

CTE (WITH) — 서브쿼리에 이름 붙이기

WITH team_total AS (
    SELECT team, SUM(amount) AS 합계
    FROM   orders
    GROUP BY team
)
SELECT *
FROM   team_total
WHERE  합계 > 1000
ORDER BY 합계 DESC;

-- 읽는 순서 = 쓴 순서라 훨씬 이해하기 쉽다.
-- Oracle 9i+, MySQL 8.0+, PostgreSQL 8.4+ 모두 지원.

윈도우 함수 — 그룹으로 접지 않고 계산하기

GROUP BY는 여러 행을 한 줄로 접습니다. 윈도우 함수는 행을 그대로 둔 채 옆에 계산 결과를 한 칸 더 붙입니다 — 순위·누적·이전 값 비교가 전부 가능해집니다.

1A32022840

RANK는 동점에 같은 순위를 주고 다음 순위를 건너뜁니다(2,2,4). DENSE_RANK는 건너뛰지 않습니다(2,2,3). ROW_NUMBER는 무조건 1,2,3. 누적 합에 ROWS BETWEEN …을 명시한 이유 — 기본 프레임은 RANGE라서 동점 행을 한꺼번에 더해 위 표의 320 두 건이 둘 다 1160이 돼 버립니다. 

SELECT id, team, amount,
       ROW_NUMBER() OVER (PARTITION BY team ORDER BY amount DESC) AS 팀내순번,
       RANK()       OVER (PARTITION BY team ORDER BY amount DESC) AS 팀내순위,
       SUM(amount)  OVER (PARTITION BY team ORDER BY amount DESC
                          ROWS BETWEEN UNBOUNDED PRECEDING
                               AND CURRENT ROW)                    AS 누적,
       LAG(amount)  OVER (PARTITION BY team ORDER BY id)          AS 이전주문금액,
       AVG(amount)  OVER (PARTITION BY team)                      AS 팀평균
FROM   orders;

-- "팀별 1등만 뽑기" 정석
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY team ORDER BY amount DESC) AS rn
  FROM   orders
)
SELECT * FROM ranked WHERE rn = 1;
지원 버전 주의 — 윈도우 함수는 Oracle은 오래전부터, PostgreSQL은 8.4부터 되지만 MySQL은 8.0부터입니다. MySQL 5.7 이하에서는 사용자 변수 트릭이나 자기 조인으로 우회해야 합니다 — 버전부터 확인하세요.

SECTION 10

트랜잭션 — 전부 되든가, 전부 취소되든가

A가 B에게 1만 원을 보냅니다. A에서 빠지고 B에 들어가기 중간에 서버가 죽으면? 트랜잭션이 없으면 돈이 증발합니다. 재생해 보세요.

계좌 이체 — 중간에 오류가 나면
속도

ACID — 네 글자로 정리

A — Atomicity (원자성)

전부 성공하거나 전부 취소. 절반만 반영되는 상태는 없다.

C — Consistency (일관성)

제약(PK·FK·CHECK)을 깨는 상태로는 끝나지 않는다.

I — Isolation (격리성)

동시에 실행돼도 혼자 실행한 것처럼 보인다 (§11).

D — Durability (지속성)

COMMIT 했으면 정전이 나도 남아 있다.

-- 표준
BEGIN;                                            -- PostgreSQL / MySQL
    UPDATE account SET balance = balance - 10000 WHERE id = 'A';
    UPDATE account SET balance = balance + 10000 WHERE id = 'B';
COMMIT;                                           -- 확정
-- ROLLBACK;                                      -- 취소

-- Oracle 은 BEGIN 이 필요 없다 (DML 을 만나면 자동 시작)
UPDATE account SET balance = balance - 10000 WHERE id = 'A';
UPDATE account SET balance = balance + 10000 WHERE id = 'B';
COMMIT;

-- 중간 지점 되돌리기
SAVEPOINT sp1;
    ...
ROLLBACK TO sp1;
# 파이썬에서는 with 문이 COMMIT/ROLLBACK 을 대신해 준다
import psycopg

with psycopg.connect(DSN) as conn:       # 블록을 정상 탈출 -> COMMIT
    with conn.cursor() as cur:           # 예외 발생     -> ROLLBACK
        cur.execute("UPDATE account SET balance = balance - %s WHERE id = %s", (10000, "A"))
        cur.execute("UPDATE account SET balance = balance + %s WHERE id = %s", (10000, "B"))
DDL은 롤백되지 않는 경우가 많습니다 — Oracle·MySQL은 CREATE TABLE·ALTER TABLE을 만나면 진행 중인 트랜잭션을 자동 COMMIT합니다. PostgreSQL은 DDL도 트랜잭션에 넣을 수 있어(롤백 가능) 마이그레이션에 강합니다.

SECTION 14

Redis — 표가 아닌 DB, 메모리 위의 자료구조

Redis는 SQL도 테이블도 없습니다. 키 하나에 자료구조 하나를 메모리에 얹어 둡니다. 그래서 μs 단위로 빠르고, 대신 메모리가 곧 한계입니다.

Redis 자료구조 5종 — 명령을 눌러 보세요

TTL — 시간이 지나면 스스로 사라집니다
TTL SET session:abc "..." EX 30 — 30초 뒤 자동 삭제됩니다. 세션·인증코드·캐시가 알아서 정리되는 이유입니다. 
# 문자열 — 캐시·카운터
SET user:1:name "김민준"
GET user:1:name
SET page:views 0
INCR page:views              # 원자적 증가 (동시성 안전)
SET code:0413 "123456" EX 180   # 3분 뒤 자동 삭제

# 리스트 — 큐 / 최근 목록
LPUSH queue:job "task-1"     # 왼쪽에 넣고
RPOP  queue:job              # 오른쪽에서 꺼내면 FIFO
BRPOP queue:job 0            # 값이 생길 때까지 대기 (블로킹)
LRANGE recent:view 0 9       # 최근 10개

# 해시 — 객체 하나를 필드별로
HSET user:1 name "김민준" grade "VIP" point 320
HGETALL user:1
HINCRBY user:1 point 50

# 셋 — 중복 없는 집합
SADD post:1:likes "u7"
SISMEMBER post:1:likes "u7"  # 좋아요 눌렀나? O(1)
SCARD post:1:likes           # 좋아요 수

# 소트 셋 — 점수로 정렬된 집합 (실시간 순위표의 표준)
ZADD rank 320 "김민준"
ZADD rank 510 "이서연"
ZREVRANGE rank 0 9 WITHSCORES   # 상위 10명
ZREVRANK rank "김민준"           # 내 등수
운영에서 절대 하면 안 되는 명령 — KEYS * 는 전체 키를 훑으며 서버를 멈춥니다. 반드시 SCAN을 쓰세요. FLUSHALL 은 전부 삭제입니다.
또한 Redis는 단일 스레드라 무거운 명령 하나가 모든 요청을 막습니다.
영속성(데이터가 남는가) — Redis는 기본이 메모리지만 RDB(주기적 스냅샷)와 AOF(명령 로그)로 디스크에 남길 수 있습니다. 그래도 “없어지면 곤란한 데이터”의 원본은 RDBMS에 두고, Redis는 다시 만들 수 있는 데이터(캐시·세션·랭킹)에 쓰는 것이 원칙입니다.

import json, redis, psycopg

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def get_orders(team: str):
    key = f"orders:team:{team}"

    cached = r.get(key)               # ① 캐시부터 확인
    if cached:
        return json.loads(cached)     #    있으면 끝 (DB 안 감)

    with psycopg.connect(DSN) as conn:            # ② 없으면 DB 조회
        rows = conn.execute(
            "SELECT id, amount FROM orders WHERE team = %s", (team,)
        ).fetchall()

    r.setex(key, 300, json.dumps(rows))           # ③ 캐시에 저장 (5분)
    return rows

def update_order(order_id: int, amount: int, team: str):
    with psycopg.connect(DSN) as conn:
        conn.execute("UPDATE orders SET amount = %s WHERE id = %s", (amount, order_id))
    r.delete(f"orders:team:{team}")               # ④ ★ 캐시 무효화 (지우기)
문제무엇인가대응
캐시 스탬피드인기 키가 만료되는 순간 수천 요청이 동시에 DB로 몰림TTL에 랜덤 편차 부여, 갱신 시 락(단일 갱신)
캐시 관통없는 데이터를 계속 조회 → 매번 DB행“없음”도 짧게 캐싱, 블룸 필터
오래된 데이터DB는 바뀌었는데 캐시는 옛날 값쓰기 시 삭제(갱신보다 안전), TTL 짧게
메모리 초과키가 무한히 쌓임maxmemory + allkeys-lru 정책
캐시 무효화는 “갱신”이 아니라 “삭제” — 캐시를 새 값으로 덮어쓰면 동시성 상황에서 옛 값이 나중에 덮어쓰는 사고가 납니다. 그냥 DELETE 하고 다음 요청이 새로 채우게 두세요.

r.set("user:1:name", "김민준", ex=300)
print(r.get("user:1:name"))

pipe = r.pipeline()                    # 여러 명령을 한 번에 (왕복 1회)
pipe.incr("page:views")
pipe.zadd("rank", {"김민준": 320})
pipe.execute()
redis-py 8 부터 기본 프로토콜이 RESP2 → RESP3 로 바뀌었습니다. 그에 맞춰 약 84개 명령의 반환 타입이 통일되었습니다 — 리스트로 오던 것이 dict 로, 평평하던 응답이 구조화된 형태로 바뀐 식입니다. 기존 코드가 응답 모양에 의존하고 있다면 업그레이드 후 조용히 깨질 수 있습니다. 급하면 redis.Redis(..., protocol=2) 로 예전 동작을 유지하고, 시간을 두고 RESP3 기준으로 고치세요.

ORM 모델 정의 — 타입 힌트가 곧 컬럼 (SQLAlchemy 2.0 스타일)

위까지가 Core(SQL 문자열을 그대로 쓰는 쪽)였다면, 여기서부터가 ORM입니다. 2.0 스타일은 클래스에 타입 힌트만 적으면 그게 곧 컬럼 정의입니다. 

from datetime import datetime
from sqlalchemy import ForeignKey, String, func, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, Session

class Base(DeclarativeBase):
    pass

class Customer(Base):
    __tablename__ = "customers"
    id:   Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    orders: Mapped[list["Order"]] = relationship(back_populates="customer")

class Order(Base):
    __tablename__ = "orders"
    id:          Mapped[int] = mapped_column(primary_key=True)
    customer_id: Mapped[int] = mapped_column(ForeignKey("customers.id"))
    amount:      Mapped[int]
    memo:        Mapped[str | None]          # Optional -> NULL 허용
    created_at:  Mapped[datetime] = mapped_column(server_default=func.now())
    customer: Mapped["Customer"] = relationship(back_populates="orders")

Base.metadata.create_all(engine)             # 테이블이 없으면 만든다
타입 힌트가 곧 컬럼 정의입니다 — Mapped[int] 는 INTEGER NOT NULL, Mapped[str | None] 은 VARCHAR NULL 이 됩니다. 별도 선언이 없으니 mypy·IDE 자동완성이 그대로 먹습니다. 길이·제약·기본값처럼 더 적을 게 있을 때만 mapped_column(...) 을 붙이면 됩니다.

조회 — select() 하나로 통일

with Session(engine) as s:
    # 여러 건
    rows = s.scalars(select(Order).where(Order.amount >= 1000)).all()

    # 한 건 (없으면 None)
    one = s.scalar(select(Order).where(Order.id == 1))

    # 개수
    n = s.scalar(select(func.count()).select_from(Order))

    # 조인
    q = (select(Customer.name, func.sum(Order.amount))
         .join(Order)
         .group_by(Customer.name))
    for name, total in s.execute(q):
        print(name, total)

scalars() 와 execute()

  • s.scalars(...) → ORM 객체 자체를 줍니다(Order 인스턴스)
  • s.execute(...) → 튜플 행을 줍니다(위 조인처럼 열을 골라 뽑을 때)
  • 한 건만 필요하면 s.scalar(...) — 없으면 None

session.query() 는 레거시

  • session.query(...) 는 1.x 시절 API입니다
  • 2.0 에서도 아직 동작하지만, 새 코드는 쓰지 마세요
  • ✅ select() + session.scalars() / session.execute()
  • 검색하다 나온 옛날 예제가 대부분 query() 라 헷갈리기 쉽습니다

SQL 인젝션 — 문자열을 이어 붙이면 벌어지는 일

❌ 이렇게 쓰면 뚫립니다

name = input("이름: ")
cur.execute(
    f"SELECT * FROM member WHERE name = '{name}'"

사용자가 이름 칸에 ' OR '1'='1 을 넣으면 쿼리는 이렇게 완성됩니다: 

SELECT * FROM member WHERE name = '' OR '1'='1'
-- 조건이 항상 참 -> 전체 회원 정보 유출

'; DROP TABLE member; -- 이면 테이블이 사라집니다.

✅ 파라미터 바인딩

name = input("이름: ")

# PostgreSQL / MySQL
cur.execute(
    "SELECT * FROM member WHERE name = %s",
    (name,),          # ★ 값은 따로 넘긴다
)

# Oracle
cur.execute(
    "SELECT * FROM member WHERE name = :n",
    n=name,
)

# SQLAlchemy
conn.execute(
    text("SELECT * FROM member WHERE name = :n"),
    {"n": name},
)
값을 따로 넘기면 DB가 그것을 “코드”가 아니라 “값”으로만 취급합니다. 무슨 문자를 넣어도 그냥 이름일 뿐입니다.
