CPython 말고 다른 파이썬들

우리가 “파이썬”이라고 부르는 것의 정식 이름은 CPython 입니다. python.org 가 배포하는 것도, uv 가 받아 오는 것도 전부 CPython 입니다. 나머지는 특수 목적이라 처음에는 몰라도 됩니다.

구현정체언제
CPythonC 로 짠 표준 구현. 사실상 “파이썬”거의 항상 ★
PyPyJIT 로 순수 파이썬 루프가 몇 배 빠름C 확장 없는 계산 루프
Anaconda 배포CPython + 과학 패키지 묶음연구실 관행
MicroPython마이크로컨트롤러용 초경량ESP32 등 임베디드
Pyodide브라우저(WASM)에서 도는 파이썬웹 데모
Jython · IronPythonJVM · .NET 위의 파이썬 2/3 계열레거시 연동
지금 뭘 쓰고 있는지 확인 — python -VV 를 치면 구현 이름과 빌드 정보까지 나옵니다. Python 3.14.2 (main, …) [MSC v.19… 64 bit (AMD64)] 처럼요. 64 bit 인지도 여기서 확인합니다 — 32비트를 깔면 나중에 라이브러리가 안 깔립니다.
32비트를 깔지 마세요 — python.org 다운로드 페이지에는 아직 Windows installer (32-bit) 가 남아 있습니다. 이걸 받으면 메모리를 2GB 남짓밖에 못 쓰고, NumPy·PyTorch 같은 주요 라이브러리의 최신 휠이 아예 제공되지 않습니다. 반드시 Windows installer (64-bit) 를 받으세요. ARM 노트북(Snapdragon X 등)이라면 ARM64 를 받습니다.

윈도우 설치는 화면이 딱 세 장입니다. 그런데 첫 화면 아래쪽의 작은 체크박스 하나를 놓치면 그 뒤 모든 명령이 안 먹습니다. 이 절은 그 화면을 버튼 이름 그대로 따라갑니다.

PATH 완전 정복 — “명령을 못 찾겠다”의 정체

설치 문제의 8할은 여기서 끝납니다. PATH 는 “실행 파일을 찾을 폴더 목록”이고, 셸은 그 목록을 위에서부터 훑다가 처음 만난 것을 실행합니다. 이 두 문장만 정확히 알면 대부분의 증상을 스스로 진단할 수 있습니다.

“설치했는데 안 잡힌다”는 없는 게 아니라 순서가 뒤인 경우가 대부분입니다.

최종 PATH 는 시스템 변수 + 사용자 변수를 이어 붙인 값입니다. 즉 시스템 쪽이 언제나 앞이라, 사용자 변수에 아무리 위로 올려 놔도 시스템 변수에 있는 다른 파이썬을 못 이깁니다. 회사 PC 에서 “PATH 를 고쳤는데 안 바뀐다”면 이 경우입니다. 

# 지금 PATH 를 한 줄에 하나씩 — 순서가 그대로 보입니다
$env:Path -split ';' | Where-Object { $_ }

# 사용자 PATH 만 / 시스템 PATH 만 따로 보기
[Environment]::GetEnvironmentVariable('Path','User') -split ';'
[Environment]::GetEnvironmentVariable('Path','Machine') -split ';'

# 이 터미널에서만 임시로 맨 앞에 추가 (창을 닫으면 사라집니다 — 실험용)
$env:Path = "C:\Python314;C:\Python314\Scripts;" + $env:Path

# 영구히 사용자 PATH 에 추가 (관리자 권한 불필요)
$old = [Environment]::GetEnvironmentVariable('Path','User')
[Environment]::SetEnvironmentVariable(
    'Path', "C:\Python314;C:\Python314\Scripts;$old", 'User')
#   → 새 터미널부터 적용됩니다
PATH 는 터미널이 켜질 때 한 번만 읽힙니다 — 창을 열어 둔 채로 환경 변수를 고쳐도 그 창에는 반영되지 않습니다. 새 창을 여세요. VS Code·PyCharm 도 마찬가지라 IDE 자체를 재시작해야 합니다.

pip 완전 정복 — 설치가 실패하는 진짜 이유

pip install 한 줄 뒤에서 벌어지는 일을 알면, 실패 메시지를 보고 원인을 짚을 수 있습니다. 특히 “휠(wheel)이 있느냐 없느냐” 하나가 3초 설치와 컴파일러를 깔아야 하는 30분을 가릅니다.

설치가 느리거나 실패하는 지점은 거의 언제나 휠이 없어서입니다.

매일 쓰는 명령 열 개

# 설치 — 항상 python -m pip 로 쓰는 습관 ★
python -m pip install requests
python -m pip install "requests==2.32.3"      # 정확히
python -m pip install "requests>=2.32,<3"     # 범위
python -m pip install --upgrade requests      # 올리기
python -m pip install -r requirements.txt     # 파일로 한꺼번에

# 지우기 · 보기
python -m pip uninstall requests
python -m pip list                    # 깔린 것 전부
python -m pip list --outdated         # 새 버전이 나온 것만
python -m pip show -f requests        # 버전·위치·의존성·파일 목록 ★
python -m pip freeze                  # requirements 형태로

# 진단
python -m pip check                   # 의존성이 깨졌는지 검사 ★
python -m pip debug --verbose         # 이 환경이 받을 수 있는 휠 태그 목록
python -m pip download requests -d ./wheels   # 받기만 (설치는 안 함)
pip show -f 가 의외로 유용합니다 — “이 패키지가 어디에 깔렸고, 무엇을 요구하고, 누가 이걸 요구하는지”가 한 번에 나옵니다. Required-by: 줄을 보면 지워도 되는 패키지인지 바로 판단됩니다.

휠(wheel)이란 무엇인가

휠은 “미리 빌드해 둔 설치 파일”입니다. 파일 이름 자체가 어느 환경용인지 말해 줍니다.

 │      └────────────────────── 버전

      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-toml
      - id: check-added-large-files      # 큰 파일 실수 방지 ★
        args: [--maxkb=1000]
      - id: check-merge-conflict
      - id: detect-private-key           # 개인키 커밋 차단 ★

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.14.0
    hooks:
      - id: mypy
        additional_dependencies: [types-requests]
# 설치 — 이 한 줄이 .git/hooks 에 훅을 심습니다
pre-commit install

# 처음 한 번은 전체 파일에 돌려 보세요 (대량 수정이 생깁니다)
pre-commit run --all-files

# 훅 버전 자동 갱신
pre-commit autoupdate

# 급할 때 건너뛰기 (자주 쓰면 의미가 없습니다)
git commit --no-verify -m "wip"
기존 프로젝트에 도입할 때 — --all-files 로 전체 포맷을 하면 거대한 커밋 하나가 생겨 git blame 이 망가집니다. 그 커밋 해시를 .git-blame-ignore-revs 에 적고 git config blame.ignoreRevsFile .git-blame-ignore-revs 를 걸어 두세요. 이걸 모르고 도입했다가 원망을 삽니다.

CI — GitHub Actions 최소 한 벌

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.13", "3.14"]
    steps:
      - uses: actions/checkout@v4

      - name: uv 설치
        uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true

      - name: 파이썬 준비
        run: uv python install ${{ matrix.python-version }}

      - name: 의존성 설치
        run: uv sync --all-extras

      - name: lint
        run: uv run ruff check --output-format=github .

      - name: format 확인
        run: uv run ruff format --check .

      - name: 타입 검사
        run: uv run mypy src

      - name: 테스트
        run: uv run pytest --cov --cov-report=xml
--output-format=github 를 붙이면 ruff 의 지적이 PR 화면의 해당 줄에 바로 표시됩니다. 로그를 뒤질 필요가 없어져서 실제로 고쳐지는 비율이 눈에 띄게 올라갑니다. matrix 로 두 버전을 함께 돌리면 “3.14 에서만 깨지는 코드”를 미리 잡습니다.
도구를 “깔기만” 하면 아무도 안 씁니다 — 실제로 정착하는 순서는 ① 에디터 저장 시 자동 포맷(고통 없음) → ② pre-commit(커밋할 때 자동) → ③ CI 에서 실패 시 머지 차단(강제) 입니다. ③부터 시작하면 “CI 가 자꾸 빨간불”이라는 불만만 남습니다. ①을 먼저 깔아 두면 ③에서 걸릴 일이 거의 없어집니다.

막혔을 때의 순서 — 이 다섯 단계

① 터미널을 새로 연다
     PATH 는 창이 켜질 때 한 번만 읽힙니다.
     설치·환경 변수 변경 뒤에는 무조건 새 창.

② 지금 어느 파이썬인지 확인한다
     python -c "import sys; print(sys.executable)"
     where.exe python        (리눅스·맥: which -a python3)
     py -0p

③ 가상환경 안인지 확인한다
     python -c "import sys; print(sys.prefix != sys.base_prefix)"
     True 가 아니면 activate 부터.

④ 에러 메시지의 '첫 줄'과 '마지막 줄'을 읽는다
     파이썬 트레이스백은 마지막 줄이 결론이고,
     pip 는 첫 줄에 진짜 원인이 있는 경우가 많습니다.

⑤ 그래도 모르겠으면 환경을 버린다
     rmdir /s /q .venv   (리눅스: rm -rf .venv)
     py -3.14 -m venv .venv
     pip install -r requirements.txt
     → 1분이면 깨끗한 상태로 돌아옵니다. 이게 가상환경의 값입니다.
파이썬을 다시 까는 것은 마지막 수단입니다 — 초보자가 가장 자주 하는 실수가 “안 되니까 지우고 다시 설치”인데, 지우면 그 파이썬을 쓰던 가상환경이 전부 죽어서 상황이 더 나빠집니다. 위 ①~⑤ 로 90%는 해결됩니다.
빈 PC 를 30분 만에 세우는 최종 순서 — ① python.org 3.14 설치(Add to PATH 체크) → ② 새 터미널에서 py -0p 확인 → ③ Store 별칭 끄기 → ④ Set-ExecutionPolicy RemoteSigned -Scope CurrentUser → ⑤ VS Code + Python·Pylance·Ruff 확장 → ⑥ 프로젝트 폴더에서 py -3.14 -m venv .venv → Select Interpreter → ⑦ python -m pip install -r requirements.txt → ⑧ 익숙해지면 uv 로 갈아타기(uv 세팅 탭). 이 여덟 줄이 이 탭 전체의 요약입니다.
