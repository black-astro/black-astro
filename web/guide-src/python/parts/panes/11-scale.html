SCALE 01

파이썬으로 서버를 만든다는 것

가장 먼저 GIL 과 WSGI/ASGI 를 이해해야 합니다.

GIL — 파이썬의 전제

GIL (Global Interpreter Lock)
  = 한 프로세스 안에서 "파이썬 바이트코드는 한 번에 하나만" 실행

결과
  · 스레드를 100개 만들어도 CPU 계산은 1코어만 씁니다
  · 단, I/O 대기(DB·네트워크·파일) 중에는 GIL 을 놓습니다
    → I/O 작업은 스레드로도 동시성이 나옵니다 ★

정리
  I/O 바운드  →  async 또는 스레드    (동시성 OK)
  CPU 바운드  →  멀티프로세싱 필수     (스레드는 무의미)

※ free-threaded 빌드(GIL 없음)는 3.13 에서 실험적으로 들어왔고
  3.14 에서 PEP 779 로 "공식 지원" 단계가 됐습니다 (실행: python3.14t)
“파이썬은 느리다”는 말의 실체 — 순수 계산은 실제로 느립니다(C 의 수십~수백 배). 하지만 웹 서버 작업의 대부분은 대기 시간이라 제대로 만들면 트래픽 처리에는 충분합니다. 인스타그램·드롭박스가 파이썬으로 돌아갑니다.
free-threading — 3.14 에서 “공식 지원”이 됐습니다. 3.13 에서 실험적으로 들어왔고, 3.14 에서 PEP 779 로 공식 지원 단계에 올라 실험 딱지를 뗐습니다. 전용 실행 파일 python3.14t 로 돌립니다 (uv 라면 uv python install 3.14t). 대신 단일 스레드 성능은 5~10% 느립니다 — GIL 을 없애는 대가입니다. 2026-08 기준 상위 네이티브 패키지 360개 중 183개가 free-threading 휠을 냅니다. 돌아가는 서비스를 갈아엎기보다 새 워크로드부터 검토하는 편이 안전합니다.

WSGI vs ASGI

구분설명
WSGI동기 표준. Django(전통)·Flask. 요청 하나당 워커/스레드 하나를 점유
ASGI비동기 표준. FastAPI·Starlette·Django 3.0+. 하나의 워커가 수천 연결을 다룸
[WSGI · 동기]  워커 4개 × 스레드 8 = 동시 32 요청
   DB 응답 100ms 를 기다리는 동안 그 스레드는 놀고 있습니다

[ASGI · 비동기]  워커 4개, 각각 수천 개의 대기 중 요청
   기다리는 동안 다른 요청을 처리 → 같은 자원으로 훨씬 많이

★ 단, async 함수 안에서 "동기 블로킹 코드"를 부르면
  이벤트 루프 전체가 멈춥니다 (k03 — 가장 흔한 사고)

무엇을 고를까

  • 신규 API 서버 → FastAPI(ASGI). 타입 힌트 기반 검증·문서 자동 생성
  • 관리자·풀스택 → Django. ORM·어드민·인증이 전부 들어 있습니다
  • 간단한 내부 도구 → Flask 로 충분
  • 데이터 API(모델 서빙·집계) → FastAPI + 백그라운드 워커(k08)
HTTP·REST·FastAPI 기본기가 아직이라면 🌐 웹 기초 탭을 먼저 보세요. 요청·응답 한 바퀴부터 첫 서버 · 로그인(JWT) · CORS 까지 정리돼 있습니다. 여기서 만든 것을 검증하는 방법은 🧪 테스트 탭에 있습니다.
기존 분석 코드를 서비스로 올릴 때 — pandas·numpy 연산은 CPU 바운드입니다. API 핸들러 안에서 직접 돌리면 서버 전체가 멈춥니다. 큐(k08)나 별도 프로세스(k04)로 반드시 분리하세요.

    email: EmailStr
    name: str = Field(min_length=1, max_length=50)
    age: int | None = Field(default=None, ge=0, le=150)

class UserOut(BaseModel):
    id: int
    email: EmailStr
    name: str
    # ★ password 는 아예 넣지 않습니다 (응답 모델로 노출 차단)

@asynccontextmanager
async def lifespan(app: FastAPI):
    await db.connect()            # 시작 시
    yield
    await db.disconnect()         # ★ 종료 시 정리 (k11 무중단 배포)

#   기본값 자리를 비워 두므로 재사용·테스트·타입 검사가 모두 편합니다
@app.post("/users", response_model=UserOut, status_code=201)
async def create_user(dto: UserCreate,
                      svc: Annotated[UserService, Depends(get_service)]):
    if await svc.exists(dto.email):
        raise HTTPException(status.HTTP_409_CONFLICT, "이미 가입된 이메일입니다")
    return await svc.create(dto)

InterpreterPoolExecutor — Python 3.14 신설

from concurrent.futures import InterpreterPoolExecutor

# 워커 하나하나가 "독립 서브인터프리터"입니다 (PEP 734)
#   · GIL 을 공유하지 않으므로 CPU 바운드가 진짜 병렬로 돕니다
#   · 프로세스보다 가볍습니다 — fork/spawn 없이 인터프리터만 새로 뜹니다

with InterpreterPoolExecutor(max_workers=4) as ex:
    totals = list(ex.map(heavy_calc, chunks))

#     사실상 pickle 왕복입니다 (전역 변수·DB 커넥션 공유 불가)
#   · 인터프리터 시작 비용이 스레드보다 큽니다
#   · C 확장이 서브인터프리터를 지원해야 합니다

# 컨테이너의 실제 CPU 한도 읽기 (os.cpu_count() 는 호스트 값을 줍니다)
import os

def container_cpus() -> int:
    try:  # cgroup v2
        with open("/sys/fs/cgroup/cpu.max") as f:
            quota, period = f.read().split()
            if quota != "max":
                return max(1, int(int(quota) / int(period)))
    except FileNotFoundError:
        pass
    return os.cpu_count() or 1

DB 접근 · 커넥션 풀

SQLAlchemy 2.0 비동기 기준. 진짜 한도는 대부분 여기입니다.

비동기 세션 구성

uv add sqlalchemy[asyncio] asyncpg
from typing import Annotated

from sqlalchemy.ext.asyncio import (
    create_async_engine, async_sessionmaker, AsyncSession)

engine = create_async_engine(
    settings.database_url,           # postgresql+asyncpg://...
    pool_size=10,                    # ★ 워커당 커넥션 수
    max_overflow=5,                  # 순간 초과 허용
    pool_timeout=3,                  # ★ 못 얻으면 3초 만에 실패 (무한 대기 금지)
    pool_recycle=1800,               # 30분마다 재연결 (DB 쪽 타임아웃 회피)
    pool_pre_ping=True,              # 죽은 커넥션 자동 감지
    echo=False,
)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

async def get_db():
    async with SessionLocal() as session:
        yield session                # ★ FastAPI 의존성으로 주입

@app.get("/users/{user_id}")
async def get_user(user_id: int,
                   db: Annotated[AsyncSession, Depends(get_db)]):
    user = await db.get(User, user_id)
    if not user:
        raise HTTPException(404, "없습니다")
    return user

# 분산 락 — 여러 서버·워커에 걸쳐야 할 때
import contextlib
import uuid

UNLOCK_LUA = """
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else return 0 end
"""

@contextlib.asynccontextmanager
async def with_lock(key: str, ttl: int = 5):
    token = str(uuid.uuid4())
    got = await r.set(f"lock:{key}", token, ex=ttl, nx=True)
    if not got:
        raise BusyError("잠시 후 다시 시도해 주세요")
    try:
        yield
    finally:
        await r.eval(UNLOCK_LUA, 1, f"lock:{key}", token)  # ★ 내 락만 삭제
# 멱등성 — 같은 요청이 두 번 와도 결과는 한 번
from typing import Annotated

from fastapi import Header

@app.post("/payments")
async def pay(dto: PayRequest,
              idempotency_key: Annotated[str, Header(alias="Idempotency-Key")]):
    k = f"idem:pay:{idempotency_key}"
    first = await r.set(k, "PROCESSING", ex=86400, nx=True)

    if not first:
        saved = await r.get(k)
        if saved == b"PROCESSING":
            raise HTTPException(409, "처리 중입니다")
        return json.loads(saved)             # ★ 저장된 결과 재사용

    try:
        result = await payment_service.pay(dto)
        await r.setex(k, 86400, json.dumps(result))
        return result
    except Exception:
        await r.delete(k)                     # ★ 실패는 지워 재시도 허용
        raise

왜 필요한가

[동기] 주문 API 하나에 전부 매달림
  주문 저장 120ms + 메일 300 + 정산 150 + 리포트 2,000

async def settle_daily(target_date: date):
    # ① 중복 실행 차단
    lock = await r.set(f"batch:settle:{target_date}", "1", ex=7200, nx=True)
    if not lock:

        return

        # ② 진행 상태 기록 (재시작 지점)
        last_id = int(await r.get(f"batch:settle:{target_date}:cursor") or 0)

        while True:
            rows = await fetch_chunk(target_date, last_id, size=1000)
            if not rows:
                break
            await process_chunk(rows)                # ③ 청크 단위 커밋
            last_id = rows[-1].id
            await r.set(f"batch:settle:{target_date}:cursor", last_id)

        logger.info("정산 완료 date=%s", target_date)
    except Exception:
        logger.exception("정산 실패 date=%s", target_date)   # ④ 알람
        raise
    finally:
        await r.delete(f"batch:settle:{target_date}")

from locust import HttpUser, task, between

class ApiUser(HttpUser):
    wait_time = between(1, 3)          # ★ 실제 사용자처럼 생각하는 시간

    def on_start(self):
        r = self.client.post("/auth/login",
                             json={"email": "test@a.com", "password": "pw"})
        self.client.headers["Authorization"] = f"Bearer {r.json()['token']}"

    @task(5)                        # 가중치 — 5배 자주
    def list_products(self):
        with self.client.get("/api/products?page=1",
                             name="/api/products",   # ★ URL 을 묶어서 집계
                             catch_response=True) as r:
            if r.elapsed.total_seconds() > 0.5:
                r.failure("500ms 초과")

    @task(1)
    def create_order(self):
        self.client.post("/api/orders", json={"product_id": 1, "qty": 1})

배포 전 체크리스트

  • ☐ async def 안에 동기 블로킹 코드가 없는가 (k03)
  • ☐ 모든 외부 호출에 타임아웃이 있는가
  • ☐ 이벤트 루프 지연을 측정·알람하는가
  • ☐ 커넥션 수 = 서버 × 워커 × 풀 이 DB 한도 안인가 (k05)
  • ☐ 캐시 TTL 에 랜덤을 섞었는가 (k06)
  • ☐ 재고·포인트 차감이 원자적인가 (k07)
  • ☐ Celery 작업이 두 번 실행돼도 괜찮은가 (k08)
  • ☐ 배치가 중복 실행되지 않는가 (k10)
  • ☐ PYTHONUNBUFFERED=1 이 설정됐는가 (k11)
  • ☐ liveness / readiness 를 분리했는가
  • ☐ --graceful-timeout + preStop 이 있는가
  • ☐ 로그가 JSON + request_id 인가 (k12)
  • ☐ 운영에서 /docs 가 닫혀 있는가 (k02)
  • ☐ 부하 테스트로 한계 RPS 를 아는가 (k13)

면접에서 자주 묻는 것

질문답의 뼈대
GIL 이 뭐고 왜 문제인가? 한 번에 하나의 바이트코드만 실행 → CPU 작업은 스레드로 못 늘림, I/O 는 GIL 을 놓으므로 async·스레드가 유효 (k01)
FastAPI 가 빠른 이유는? ASGI 비동기로 대기 시간에 다른 요청 처리. 단 동기 코드를 섞으면 그대로 무너짐 (k03)
트래픽이 10배가 되면? 측정(k13) → 쿼리·블로킹 개선 → 캐시 → 워커·파드 확장 → 무거운 일은 Celery 로
선착순 이벤트 설계 Redis DECR 로 수량 판정 → 통과분만 Celery 로 → DB 저장. DB 에 전량을 보내지 않습니다
중복 결제를 어떻게 막나? Idempotency-Key + Redis 선점 + DB 유니크 제약 (k07)
수천만 행을 처리하려면? 청크·Parquet → Polars/DuckDB → 그래도 크면 분산 (k09)
가장 좋은 답은 “저희는 이렇게 겪었습니다”입니다. 수치(전 1.2s → 후 120ms), 원인(async 안의 requests 호출), 조치(httpx 전환 + 커넥션 재사용), 확인 방법(Locust p99)까지 한 세트로 말하면 지식 나열보다 훨씬 강한 인상을 줍니다.
