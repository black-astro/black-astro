왜 print 를 버리는가 — logging 의 다섯 부품

print 는 끌 수가 없습니다. 어디서 났는지, 언제 났는지, 어느 요청에서 났는지도 모릅니다. 표준 logging 은 그 네 가지를 전부 해결하려고 만들어진 물건이고, 부품이 다섯 개라는 것만 알면 나머지는 설정 문제입니다.

로그 한 줄은 레벨 검사 두 번과 필터 두 번을 지나야 나옵니다 — 안 보이는 로그의 원인은 대부분 이 넷 중 하나입니다.

한 단계 더 — 부품 다섯 개의 역할 🟡 중급

Logger · Handler · Formatter · Filter · LogRecord

부품하는 일
Logger코드가 부르는 입구. 이름으로 계층을 만듭니다 (app.billing 은 app 의 자식). 레벨을 여기서 한 번 검사합니다
Handler어디로 보낼지. 콘솔 · 파일 · 소켓 · 큐 · Sentry. 로거 하나에 여러 개를 달 수 있고, 각각 자기 레벨을 가집니다
Formatter어떤 모양으로. 사람이 읽는 한 줄이냐 JSON 이냐가 여기서 갈립니다
Filter통과시킬지 · 값을 더할지. 로거에도 핸들러에도 붙일 수 있습니다. request_id 주입과 마스킹이 전부 여기서 일어납니다
LogRecord한 줄에 해당하는 객체. 시각 · 레벨 · 모듈 · 줄번호 · 스레드 · 예외 정보를 들고 다닙니다
파이썬 로깅은 Java 의 log4j 를 그대로 옮겨 온 설계입니다. 그래서 getLogger · 레벨 · 핸들러 · 어펜더(=핸들러) 개념이 자바와 똑같습니다. 자바를 해 본 적이 있다면 이름만 바꿔 읽으면 됩니다.

getLogger(__name__) 이 관례인 이유

# app/billing/pg.py  →  __name__ 은 "app.billing.pg"

# 이름이 점으로 이어지면 자동으로 부모-자식이 됩니다
#   root
#    └ app
#       └ app.billing
#          └ app.billing.pg      ← 여기서 찍은 로그가

logging.getLogger("app.billing").setLevel(logging.DEBUG)
#   → app.billing 아래 전부 DEBUG 로 열립니다

# 시끄러운 라이브러리 하나만 조용히
logging.getLogger("urllib3").setLevel(logging.WARNING)
logging.getLogger("botocore").setLevel(logging.WARNING)
# ❌ 하지 말 것 — 루트 로거에 바로 찍기
logging.info("주문 처리")     # 이름이 "root" 라 어디서 났는지 못 봅니다

# ❌ 모든 모듈이 같은 이름을 쓰기
logger = logging.getLogger("myapp")   # 모듈별로 못 끕니다

# ✅ 모듈마다 __name__

왜 이게 실무에서 크게 다른가 — 장애 조사 중에 “결제 모듈만 DEBUG 로 열어 주세요” 라는 요청이 옵니다. __name__ 을 썼다면 설정 한 줄로 끝나고, "myapp" 하나로 통일했다면 전체가 DEBUG 로 열려 로그가 폭발합니다.

실무에선 이렇게 — 설정은 진입점 한 곳에서만 🔴 실무

❌ 라이브러리·모듈이 설정을 건드림
# mylib/core.py  — 남의 앱에 쓰이는 코드

logging.basicConfig(level=logging.DEBUG)   # ❌ 남의 설정을 덮어씁니다

logger = logging.getLogger(__name__)
logger.addHandler(logging.StreamHandler()) # ❌ 핸들러를 스스로 답니다

패키지를 import 한 것만으로 앱의 로그 포맷이 바뀌고 줄이 두 번 나옵니다. 실제로 유명 라이브러리들이 이 실수로 이슈를 받아 왔습니다.

✅ 라이브러리는 NullHandler 만

logging.getLogger(__name__).addHandler(logging.NullHandler())
#   "핸들러가 없습니다" 경고만 막고, 아무것도 출력하지 않습니다

logger.debug("내부 상태 %s", state)   # 앱이 켜 주면 보입니다

# app/main.py  — 설정은 애플리케이션 진입점 딱 한 곳
logging.config.dictConfig(LOGGING)   # LOG 03

“누가 설정하는가”를 한 곳으로 못 박는 것이 로깅 설계에서 가장 먼저 정할 규칙입니다.

정리 — logging 은 Logger → Filter → Handler → Formatter 네 부품이 LogRecord 하나를 넘겨 가며 처리하는 구조입니다. 모듈마다 logging.getLogger(__name__) 한 줄만 두고, 설정은 앱 진입점 한 곳에서만 합니다. 이 두 가지만 지켜도 “로그가 안 나온다 / 두 번 나온다” 사고의 대부분이 사라집니다.
LOG 02

레벨 설계 — 무엇을 언제 남기나

레벨은 “나중에 이 줄을 볼 사람이 누구인가”로 정합니다. DEBUG 는 나를 위한 것이고, WARNING 부터는 남이 새벽에 깨어나 보는 것입니다. 이 기준 하나로 대부분의 다툼이 끝납니다.

로그는 많이 남길수록 찾기 쉽고 비쌉니다 — 그 사이에서 고르는 손잡이가 레벨입니다.

다섯 레벨 — 이 기준으로 고릅니다

레벨값이 줄을 보게 될 사람
DEBUG10나(개발자). 변수 값 · 분기 · 외부 응답 원문. 운영에서는 꺼 둡니다
INFO ★20운영자. “무슨 업무가 일어났나” — 주문 접수 · 결제 승인 · 배치 시작·종료. 운영 기본값
WARNING30아침에 확인할 사람. 지금은 돌지만 이상함 — 재시도 성공 · 폴백 사용 · 사용 중단 예정 API
ERROR40지금 봐야 하는 사람. 이 요청·이 작업이 실패했음. 사용자 한 명이 피해를 봤습니다
CRITICAL50새벽에 깨울 사람. 프로세스를 더 못 이어감 — DB 접속 완전 실패 · 필수 설정 없음
가장 흔한 오용 — except 안에서 무조건 logger.error 를 부르는 것. 재시도로 복구됐다면 WARNING 이고, 사용자에게 정상 응답을 돌려줬다면 ERROR 가 아닙니다. ERROR 가 하루 5만 건 나오는 시스템은 ERROR 를 아무도 안 봅니다.

로그가 많아 못 쓰겠다면 — 표본과 억제

import logging, random, time

class SampleFilter(logging.Filter):
    """DEBUG 는 1%만 남깁니다. INFO 이상은 전부 통과."""
    def __init__(self, rate=0.01):
        super().__init__(); self.rate = rate
    def filter(self, record):
        if record.levelno > logging.DEBUG:
            return True
        return random.random() < self.rate

class RateLimitFilter(logging.Filter):
    """같은 메시지는 60초에 한 번만."""
    def __init__(self, period=60):
        super().__init__(); self.period = period; self.seen = {}
    def filter(self, record):
        key = (record.name, record.levelno, record.msg)
        now = time.monotonic()
        if now - self.seen.get(key, -1e9) < self.period:
            return False
        self.seen[key] = now
        return True

logging.getLogger("app").addFilter(RateLimitFilter())
표본 추출은 마지막 수단입니다. 먼저 레벨을 정직하게 다시 나누세요 — “루프 안에서 매 건마다 INFO” 같은 것이 진짜 원인인 경우가 대부분입니다. 건별 로그는 DEBUG, 배치 단위 요약은 INFO 로 바꾸면 줄 수가 수백 배 줄어듭니다.
정리 — 레벨은 “이 줄을 볼 사람이 누구인가”로 정합니다. 운영 기본은 INFO, 시끄러운 서드파티는 WARNING 으로 올려 두고, 로거 레벨과 핸들러 레벨이 둘 다 열려 있어야 로그가 보입니다. ERROR 는 진짜 실패에만 쓰세요 — 남발하면 아무도 안 봅니다.
LOG 03

설정하는 세 가지 방법 — dictConfig 만 남습니다

basicConfig 는 연습용, fileConfig 는 레거시, dictConfig 가 실무의 답입니다. 셋의 차이와, 남들이 반드시 한 번은 밟는 함정 두 개를 짚습니다.

질문 두 개로 끝납니다 — 라이브러리면 설정하지 않고, 앱이면 dictConfig.

① basicConfig — 연습과 스크립트용

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s [%(name)s:%(lineno)d] %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
logging.getLogger(__name__).info("시작")

# ★ 함정 1 — 루트에 핸들러가 이미 있으면 '조용히 무시'됩니다
logging.basicConfig(level=logging.DEBUG)   # 두 번째 호출은 아무 일도 안 함
logging.basicConfig(level=logging.DEBUG, force=True)   # 3.8+ 강제로 재설정

라이브러리 비교 — 표준 · structlog · loguru 그리고 나머지

결론부터 말하면 표준 logging 은 버리지 않습니다. 다른 라이브러리는 대부분 표준 위에 얹거나 표준으로 되돌려 보내는 물건이고, 그 이유는 여러분이 쓰는 모든 서드파티 패키지가 표준 logging 으로 로그를 남기기 때문입니다.

여섯 개를 다섯 잣대로 놓고 보면 고를 이유가 잣대마다 다르다는 것이 보입니다.

여섯 개, 한 문단씩

라이브러리어떤 물건이고 언제 고르나
logging (표준) ★사실상 표준입니다. 파이썬에 기본 포함이라 의존성이 0이고, Django · Flask · FastAPI · requests · boto3 등 거의 모든 패키지가 이걸로 로그를 냅니다. 설정이 장황한 것이 유일한 단점 — 그래서 dictConfig 한 벌을 만들어 두고 씁니다
structlog ★구조적(키=값) 로깅의 사실상 표준. 표준 logging 을 대체하지 않고 감쌉니다 — 앱 로그는 structlog 로 쓰고, 서드파티 로그는 표준 경로로 받아 같은 JSON 으로 합칩니다. 팀 서비스를 만든다면 기본 선택

import logging, sys
from loguru import logger

class InterceptHandler(logging.Handler):
    def emit(self, record):
        try:
            level = logger.level(record.levelname).name
        except ValueError:
            level = record.levelno
        frame, depth = logging.currentframe(), 2
        while frame and frame.f_code.co_filename == logging.__file__:
            frame = frame.f_back; depth += 1
        logger.opt(depth=depth, exception=record.exc_info) \
              .log(level, record.getMessage())

logging.basicConfig(handlers=[InterceptHandler()], level=0, force=True)
loguru 의 진짜 장점은 enqueue=True 와 @logger.catch, 그리고 예쁜 트레이스백(변수 값까지 보여 줍니다)입니다. 운영 서비스라면 이 편의를 표준 생태계와의 어긋남과 맞바꿀 값어치가 있는지 따져 보세요.

# app/logging_config.py
import logging.config, os, sys
import structlog

DEV = os.getenv("ENV", "dev") == "dev"

# ── ① 앱 로그와 서드파티 로그가 공통으로 지나갈 처리기들
shared_processors = [
    structlog.contextvars.merge_contextvars,       # request_id 등 컨텍스트 병합
    structlog.stdlib.add_logger_name,              # "logger": "app.billing"
    structlog.stdlib.add_log_level,                # "level": "info"
    structlog.processors.TimeStamper(fmt="iso", utc=True),
    structlog.processors.StackInfoRenderer(),
    structlog.processors.format_exc_info,          # 예외를 문자열로
    structlog.processors.UnicodeDecoder(),
]

# ── ② 개발이면 컬러 콘솔, 운영이면 JSON
renderer = (structlog.dev.ConsoleRenderer(colors=True) if DEV
            else structlog.processors.JSONRenderer(ensure_ascii=False))

logging.config.dictConfig({
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "structured": {
            "()": structlog.stdlib.ProcessorFormatter,
            # 표준 logging 으로 들어온 로그도 같은 처리기를 태웁니다
            "foreign_pre_chain": shared_processors,
            "processors": [
                structlog.stdlib.ProcessorFormatter.remove_processors_meta,
                renderer,
            ],
        },
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler",
                    "stream": "ext://sys.stdout",
                    "formatter": "structured"},
    },
    "root": {"level": os.getenv("LOG_LEVEL", "INFO"), "handlers": ["console"]},
    "loggers": {"urllib3": {"level": "WARNING"},
                "botocore": {"level": "WARNING"}},
})

# ── ③ structlog 자신의 설정 — 최종 출력은 표준 logging 에 맡깁니다
structlog.configure(
    processors=shared_processors + [
        structlog.stdlib.ProcessorFormatter.wrap_for_formatter,
    ],
    logger_factory=structlog.stdlib.LoggerFactory(),
    wrapper_class=structlog.stdlib.BoundLogger,
    cache_logger_on_first_use=True,      # ★ 성능: 로거를 한 번만 만듭니다
)
# 쓰는 쪽
import structlog
log = structlog.get_logger(__name__)

log.info("주문 생성", order_id="A-991", amount=39000)

# 요청 단위 컨텍스트 (LOG 09 에서 미들웨어로 자동화합니다)
structlog.contextvars.bind_contextvars(request_id="r-77", user_id=1234)
log.info("결제 시도")          # request_id · user_id 가 자동으로 붙습니다
structlog.contextvars.clear_contextvars()
foreign_pre_chain 이 핵심입니다. 이 한 줄 덕분에 SQLAlchemy · uvicorn · requests 처럼 표준 logging 을 쓰는 로그도 같은 타임스탬프 · 같은 필드 이름 · 같은 JSON 모양으로 나옵니다. 수집기 입장에서 로그 종류가 한 가지가 되는 것이 구조적 로깅의 절반입니다.
cache_logger_on_first_use=True 는 운영에서 반드시 켭니다. 로거 객체를 매번 만들지 않아 체감할 만큼 빨라집니다. 대신 설정을 런타임에 다시 바꿀 수 없게 되므로, 개발 중에는 꺼 두어도 됩니다.

ECS · OTel 필드 규약을 참고하면 이름 짓기로 다투지 않습니다. Elastic Common Schema 는 service.name · event.action · error.type 같은 이름을 정해 두었고, OpenTelemetry 로그 규약도 거의 같은 이름을 씁니다. 둘 중 하나를 골라 그대로 따르는 것이 가장 빠릅니다.
정리 — 구조적 로깅의 핵심은 “문구는 고정, 값은 필드로” 한 문장입니다. 최소 변경으로 시작하려면 python-json-logger 포매터 교체, 제대로 하려면 structlog + ProcessorFormatter 로 앱 로그와 서드파티 로그를 같은 JSON으로 합칩니다. 필드 이름은 ECS 나 OTel 규약을 베껴 쓰세요.
LOG 06

파일 로테이션 — 디스크를 채우지 않는 법

로그로 디스크가 100% 차면 서비스가 죽습니다. DB 도 못 쓰고, 배포도 안 되고, ssh 도 힘들어집니다. 로테이션은 있으면 좋은 기능이 아니라 안 하면 반드시 사고가 나는 항목입니다.

크기로 자르면 상한이 예측되고, 날짜로 자르면 “그날의 로그”를 찾기 쉽습니다.

RotatingFileHandler — 크기 기준

"handlers": {
    "file": {
        "class": "logging.handlers.RotatingFileHandler",
        "filename": "logs/app.log",
        "maxBytes": 50 * 1024 * 1024,   # 50MB 넘으면 회전
        "backupCount": 5,               # app.log.1 ~ app.log.5 유지
        "encoding": "utf-8",            # ★ 없으면 윈도우에서 cp949 로 깨집니다
        "delay": True,                  # 첫 로그가 날 때 파일을 엽니다
        "level": "INFO",
        "formatter": "json",
    },
}
# 디스크 상한 = maxBytes × (backupCount + 1) = 300MB
#   ★ 이 계산을 문서에 적어 두세요. 용량 산정의 근거가 됩니다
# 코드로 직접 붙일 때
from logging.handlers import RotatingFileHandler
h = RotatingFileHandler("logs/app.log", maxBytes=50_000_000,
                        backupCount=5, encoding="utf-8")

# 회전 직후 압축하고 싶다면 rotator/namer 를 갈아 끼웁니다
import gzip, shutil, os
def gzip_rotator(source, dest):
    with open(source, "rb") as fi, gzip.open(dest, "wb") as fo:
        shutil.copyfileobj(fi, fo)
    os.remove(source)
h.rotator = gzip_rotator
h.namer = lambda name: name + ".gz"
encoding="utf-8" 은 선택이 아닙니다. 윈도우에서 이걸 빼면 시스템 기본 인코딩으로 열려 한글 로그에서 UnicodeEncodeError 가 납니다. 로깅이 예외를 던지면 그 줄은 표준 에러로 밀려나고 사라집니다.

TimedRotatingFileHandler — 시간 기준

"handlers": {
    "file": {
        "class": "logging.handlers.TimedRotatingFileHandler",
        "filename": "logs/app.log",
        "when": "midnight",     # S M H D · midnight · W0~W6(요일)
        "interval": 1,
        "backupCount": 14,      # 14일치 보관
        "encoding": "utf-8",
        "utc": True,            # ★ 서버 시간대가 섞이면 조사 때 지옥입니다
        "formatter": "json",
    },
}
# 결과 파일 이름
#   logs/app.log                 ← 지금 쓰는 것
#   logs/app.log.2026-09-01
#   logs/app.log.2026-08-31 ...
고르는 기준추천
디스크 상한이 중요Rotating(크기)
“그날 로그” 를 자주 찾음Timed(날짜)
트래픽이 들쭉날쭉Rotating — 폭주해도 상한이 지켜짐
보관 기간 규정이 있음Timed + backupCount = 일수
컨테이너로 배포둘 다 안 씀 — stdout 만
Timed 는 트래픽 폭주에 무방비입니다. 하루치 파일 하나가 40GB 가 되어도 자정까지 안 자릅니다. 규정상 날짜별이 필요하면 Timed 를 쓰되, 디스크 사용률 알림을 반드시 함께 거세요.

한 단계 더 — 여러 프로세스면 파이썬 로테이션이 깨집니다 🟡 중급

무슨 일이 벌어지나

gunicorn -w 4  →  워커 프로세스 4개가 같은 app.log 를 엽니다

  워커 A: 50MB 도달 → app.log 를 app.log.1 로 rename → 새 app.log 생성
  워커 B: (아직 옛 app.log 의 파일 핸들을 쥐고 있음)
          → app.log.1 이 되어 버린 파일에 계속 씁니다
  워커 C: 동시에 회전을 시도 → app.log.1 을 app.log.2 로 밀다가 충돌
          → 파일이 통째로 사라지거나, 로그가 뒤섞입니다

증상
  · 로그 줄이 중간중간 사라진다
  · app.log 가 비어 있는데 app.log.1 만 계속 커진다
  · 윈도우에서는 PermissionError 가 나며 로그가 멈춘다
이건 버그가 아니라 설계상 한계입니다. RotatingFileHandler 문서에도 “여러 프로세스에서 한 파일에 쓰는 것은 지원하지 않는다”고 적혀 있습니다. gunicorn · uvicorn 워커 · Celery 워커가 있다면 전부 해당됩니다.

def eager():  log.debug(f"payload {payload}")
def guarded():
    if log.isEnabledFor(logging.DEBUG):
        log.debug("payload %s", payload)

for f in (lazy, eager, guarded):
    t = timeit.timeit(f, number=200_000)
    print(f"{f.__name__:8s} {t:.3f}s")

#   guarded  < lazy  <<  eager
#   (eager 만 payload 를 20만 번 문자열로 만듭니다)
절대값을 외우지 마세요. 파이썬 버전 · CPU · 터미널 종류에 따라 몇 배씩 달라집니다. 중요한 건 순서이고, 그 순서는 어디서 재도 같습니다. “우리 서버에서 얼마인가”는 위 스크립트를 그 서버에서 돌려 보면 됩니다.

운영 로그에서 가장 자주 하는 일은 “이 사용자의 이 요청이 무슨 일을 겪었나”를 따라가는 것입니다. 동시에 수백 요청이 도는 서버에서 그게 가능하려면 같은 요청에서 나온 줄에 같은 표식이 있어야 합니다.

import contextvars, logging

request_id_var = contextvars.ContextVar("request_id", default="-")
user_id_var    = contextvars.ContextVar("user_id", default="-")

class RequestIdFilter(logging.Filter):

# FastAPI / Starlette
import uuid
from starlette.middleware.base import BaseHTTPMiddleware
from app.logging_filters import request_id_var

class RequestIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        # 앞단(Nginx·게이트웨이)이 준 값이 있으면 그대로 이어받습니다
        rid = request.headers.get("X-Request-Id") or uuid.uuid4().hex[:12]
        token = request_id_var.set(rid)
        try:
            response = await call_next(request)
            response.headers["X-Request-Id"] = rid   # ★ 사용자에게 돌려주기
            return response
        finally:
            request_id_var.reset(token)              # ★ 반드시 원복

import logging

class OrderAdapter(logging.LoggerAdapter):
    def process(self, msg, kwargs):
        extra = kwargs.setdefault("extra", {})
        extra.update(self.extra)      # 어댑터가 들고 있는 값
        return msg, kwargs

def process_order(order):

마스킹 필터 — 핸들러에 붙입니다

# app/logging_filters.py
import logging, re

SECRET_KEYS = {"password", "passwd", "pwd", "token", "access_token",
               "refresh_token", "secret", "api_key", "authorization",
               "cookie", "set-cookie", "ssn", "card", "card_number"}

PATTERNS = [
    (re.compile(r'(?i)("(?:%s)"\s*:\s*)"[^"]*"' % "|".join(SECRET_KEYS)),
     r'\1"***"'),                                   # JSON 형태
    (re.compile(r'(?i)\b(bearer)\s+[A-Za-z0-9._\-]+'), r'\1 ***'),
    (re.compile(r'\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?(\d{4})\b'),
     r'****-****-****-\1'),                         # 카드번호
    (re.compile(r'(?i)(access_token|api_key)=[^&\s]+'), r'\1=***'),
]

class MaskFilter(logging.Filter):
    def filter(self, record):
        msg = record.getMessage()
        for pat, repl in PATTERNS:
            msg = pat.sub(repl, msg)
        record.msg, record.args = msg, ()   # 이미 합쳤으므로 args 는 비웁니다
        # extra 로 넘어온 값도 훑습니다
        for key in list(record.__dict__):
            if key.lower() in SECRET_KEYS:
                record.__dict__[key] = "***"
        return True
왜 핸들러에 붙이나 — 로거에 붙이면 그 로거를 지나는 줄만 걸러집니다. 핸들러에 붙이면 서드파티 로그를 포함해 그 출력으로 나가는 모든 줄이 걸러집니다. dictConfig 의 handlers.console.filters 에 넣으세요.

장애 조사에서 가장 아까운 순간은 “에러가 났다는 건 아는데 어디서 났는지 모를 때” 입니다. 트레이스백은 가만두면 사라집니다 — 스레드에서, asyncio 태스크에서, 그리고 except: logger.error(str(e)) 한 줄에서.

# app/excepthooks.py
import asyncio, logging, sys, threading

logger = logging.getLogger("uncaught")

# ── ① 메인 스레드
def _sys_hook(exc_type, exc, tb):
    if issubclass(exc_type, KeyboardInterrupt):     # Ctrl+C 는 그대로 두기
        sys.__excepthook__(exc_type, exc, tb)
        return
    logger.critical("잡히지 않은 예외", exc_info=(exc_type, exc, tb))

# ── ② 다른 스레드 (Python 3.8+)
def _thread_hook(args):
    if issubclass(args.exc_type, SystemExit):
        return
    logger.critical("스레드에서 잡히지 않은 예외 thread=%s",
                    args.thread.name if args.thread else "-",
                    exc_info=(args.exc_type, args.exc_value, args.exc_traceback))

# ── ③ asyncio 이벤트 루프
def _loop_hook(loop, context):
    exc = context.get("exception")
    if exc is not None:
        logger.critical("asyncio 예외: %s", context.get("message"), exc_info=exc)
    else:
        logger.critical("asyncio 오류: %s", context.get("message"))

# ── ④ 소멸자·GC 중에 난 예외 (드물지만 원인 찾기가 가장 어렵습니다)
def _unraisable_hook(args):
    logger.error("unraisable: %s", args.err_msg or args.object,
                 exc_info=(args.exc_type, args.exc_value, args.exc_traceback))

def install():
    sys.excepthook = _sys_hook
    threading.excepthook = _thread_hook
    sys.unraisablehook = _unraisable_hook
    try:
        asyncio.get_running_loop().set_exception_handler(_loop_hook)
    except RuntimeError:
        pass          # 아직 루프가 없으면 시작 이벤트에서 다시 부릅니다
# app/main.py
from app.logging_config import setup
from app.excepthooks import install

setup()
install()          # ★ 진입점에서 한 번

# FastAPI 라면 루프가 뜬 뒤에 한 번 더
@app.on_event("startup")
async def _hooks():
    asyncio.get_running_loop().set_exception_handler(_loop_hook)
