UV · 파이썬 환경 관리의 최신 표준

venv도 pip도
더 이상
따로 쓰지 않는다

uv는 Rust로 만든 파이썬 패키지·프로젝트 관리자입니다. 가상환경 생성, 파이썬 버전 설치, 의존성 해결, 락파일 관리를 하나의 명령어로 처리하고, pip보다 10~100배 빠릅니다. 여기까지 하면 팀원과 CI가 똑같이 재현되는 개발 환경을 만들어 두고 유지할 수 있습니다.

UV 01

왜 uv인가

기존 방식의 고통을 먼저 정리하면 uv가 무엇을 해결했는지 명확해집니다.

패키지 설치 속도 (pandas + numpy + opencv + pyside6 기준)
pip install
poetry install
uv sync

캐시가 있으면 uv는 하드링크로 파일을 연결해 사실상 즉시 끝납니다. 실제 값은 환경에 따라 다릅니다.

기존 방식 (도구가 4개)

pyenv install 3.14.0        # 파이썬 버전 관리
python -m venv .venv        # 가상환경 생성
.venv\Scripts\activate      # 활성화 (까먹기 쉬움)
pip install pandas          # 설치
pip freeze > requirements.txt   # 수동 기록 (부정확!)
  • activate를 잊으면 전역에 설치되어 환경이 오염됨
  • requirements.txt는 직접 설치한 것과 딸려온 것이 구분 안 됨
  • 의존성 재현이 불완전 — “내 PC에선 되는데요”
  • 파이썬 버전 관리는 또 다른 도구(pyenv)가 필요

uv 방식 (도구가 1개)

uv init myapp               # 프로젝트 + pyproject.toml 생성
cd myapp
uv add pandas               # 설치 + 기록 + 락파일 갱신 (한 번에)
uv run myapp                # 가상환경 자동 인식 후 실행
  • activate 불필요 — uv run이 알아서 .venv를 씁니다
  • pyproject.toml = 내가 선언한 의존성 (사람이 관리)
  • uv.lock = 실제 설치된 전체 트리 (기계가 관리, 커밋 대상)
  • 파이썬 버전까지 uv python install로 해결
Spring 비유 — pyproject.toml은 pom.xml / build.gradle, uv.lock은 정확한 버전이 고정된 의존성 트리 (Gradle의 lockfile)입니다. uv sync는 mvn install에 해당합니다.

비교 — 파이썬 환경 도구 4파전

도구장점단점선택 기준
uv가장 빠름, 버전관리+패키지+락파일 통합, activate 불필요비교적 신생 (그러나 급속히 표준화 중)★ 새 프로젝트 기본값
pip + venv파이썬 내장, 어디서나 동작, 자료 최다느림, 락파일 없음, 전부 수동, 버전관리 별도(pyenv)추가 도구 설치가 불가능한 환경
Poetry락파일·빌드·배포 통합, 성숙한 생태계uv보다 훨씬 느림, 파이썬 버전 관리는 없음이미 Poetry 쓰는 팀 합류 시
Conda컴파일 필요한 과학 패키지에 강함, 비파이썬 의존성도 관리무겁고 느림, pip 혼용 시 꼬임, 상용 채널 라이선스 주의GPU·과학 스택이 pip로 안 깔릴 때
uv 의 값은 빠르다는 것보다 정해야 할 것이 줄어든다는 데 있습니다.
UV 02

설치와 첫 프로젝트

아래 터미널에서 재생을 누르면 실제 명령 흐름이 순서대로 타이핑됩니다.

프로젝트 생성 시나리오
PowerShell — D:\work
PS D:\work>

설치 (Windows)

# PowerShell — 공식 설치 스크립트
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 또는 이미 쓰는 도구가 있다면
winget install --id=astral-sh.uv
pip install uv
scoop install uv

# 확인
uv --version

# 업데이트
uv self update
설치 후 터미널을 다시 켜세요 — PATH가 갱신되지 않아 uv를 찾을 수 없습니다가 뜨는 경우가 대부분입니다. PyCharm을 쓴다면 IDE도 재시작해야 인식합니다.

프로젝트 만들기

# 새 폴더로 시작
uv init myapp
cd myapp

# 이미 있는 폴더에서 시작
cd 기존폴더
uv init

# 0.12 부터 uv init 기본값 = "패키지 프로젝트" (src/ 레이아웃 + 빌드 설정)
uv init --app myapp          # 앱 (기본값)
uv init --lib mylib          # 배포용 라이브러리
uv init --script run.py      # 단일 파일 스크립트 (PEP 723 헤더만 생성)
uv init --no-package myapp   # 예전 방식: 루트에 main.py, build-system 없음

# 파이썬 버전 지정해서 생성
uv init --python 3.14 myapp
myapp/ pyproject.toml # 프로젝트 설정 + 의존성 + build-system .python-version # 사용할 파이썬 버전 README.md .gitignore src/myapp/ __init__.py # 진입점 함수가 여기에 uv.lock # uv sync/add 시 생성 (커밋 O) .venv/ # 가상환경 (커밋 X)
0.12 에서 바뀐 점 — 이제 uv init이 기본으로 src/<이름>/ 레이아웃과 [build-system], [project.scripts]까지 만들어 줍니다. 루트에 main.py 하나만 있던 예전 형태가 필요하면 --no-package를 붙이세요.
UV 03

파이썬 버전 관리

pyenv 없이 uv 하나로 여러 파이썬 버전을 깔고 프로젝트별로 고정합니다.

# 설치 가능한 버전 목록
uv python list

# 특정 버전 설치 (시스템 파이썬을 건드리지 않음)
uv python install 3.14
uv python install 3.11 3.13 3.14     # 여러 개 동시에
uv python install 3.14t              # free-threaded(GIL 없는) 빌드

# uv 가 관리하는 파이썬을 패치 버전까지 올리기
uv python upgrade 3.14

# 현재 프로젝트가 쓸 버전 고정 -> .python-version 파일 생성
uv python pin 3.14

# 설치된 파이썬 위치 확인
uv python find

# 특정 버전으로 가상환경 만들기
uv venv --python 3.14
왜 프로젝트마다 버전을 고정하나 — PyWinAuto·OpenCV 같은 라이브러리는 특정 파이썬 버전에서만 휠(wheel)이 제공되는 경우가 있습니다. .python-version을 커밋해 두면 팀원 모두 같은 버전에서 돌아갑니다.
지금 몇을 쓰나 — 현행 stable 은 3.14(3.14.2)입니다. 3.12 는 이미 security-only 단계로 들어가 버그픽스 릴리스가 끝났으니 새 프로젝트는 3.14, 늦어도 3.13 에서 시작하세요.
free-threading 빌드 (3.14t) — 3.14 에서 PEP 779로 GIL 없는 빌드가 실험 단계를 벗어나 공식 지원 단계가 됐습니다. 끝의 t가 그 표시입니다. 다만 단일 스레드 성능은 5~10% 느리고, 2026-08 기준 상위 네이티브 패키지 360개 중 183개만 free-threading 휠을 냅니다. 기본은 여전히 일반 빌드로 두고, CPU 병렬이 실제로 병목일 때만 골라 쓰세요.
PySide6 주의 — 최신 파이썬이 나온 직후에는 PySide6 휠이 아직 없을 수 있습니다. PySide6 6.11 은 파이썬 3.10~3.14 를 지원하고 3.15 는 아직 미지원입니다. GUI 프로젝트라면 지원 범위 안쪽 버전으로 pin 해 두는 편이 안전합니다.
"파이썬을 잘못 건드려 시스템이 망가졌다" 는 사고가 구조적으로 안 생깁니다.
UV 04

패키지 add · sync · lock

이 세 명령의 관계만 이해하면 uv는 끝입니다.

3단계 흐름
1. 선언
uv add pandas
pyproject.toml 에
"pandas>=2.2" 기록
→
2. 해결
uv lock
의존성 트리 전체를
uv.lock 에 고정
→
3. 반영
uv sync
.venv 를 lock 과
정확히 일치시킴

uv add는 이 3단계를 자동으로 다 수행합니다. lock/sync를 따로 칠 일은 드뭅니다.

uv add 한 줄의 여정 uv add pandas
자동 3단선언 → 잠금 → 설치가
순서대로 일어남

패키지 다루기

uv add pandas                    # 최신 버전
uv add "pandas>=2.2,<3"          # 범위 지정
uv add pandas numpy matplotlib   # 여러 개
uv add --dev pytest ruff         # 개발 전용 (배포엔 미포함)
uv add git+https://github.com/user/repo
uv add ./local_package           # 로컬 경로

uv remove pandas                 # 삭제

uv sync                          # lock 대로 환경 맞추기 (팀원 최초 1회)
uv sync --frozen                 # lock 갱신 없이 (CI 권장)
uv lock --upgrade                # 전체 최신으로 갱신
uv lock --upgrade-package pandas # 특정 패키지만 갱신

uv tree                          # 의존성 트리 보기
uv pip list                      # 설치 목록

커밋 규칙 (.gitignore)

# 반드시 커밋
pyproject.toml      # 무엇을 원하는지
uv.lock             # 정확히 무엇이 깔렸는지
.python-version     # 어떤 파이썬으로

# 커밋 금지 (.gitignore)
.venv/
__pycache__/
*.pyc
.env
uv.lock을 꼭 커밋하세요 — 이게 없으면 팀원마다 다른 버전이 깔려 “제 컴퓨터에선 되는데요” 문제가 그대로 재발합니다. Gradle lockfile을 커밋하는 것과 같은 이유입니다.
새 팀원 온보딩 — git clone 후 uv sync 한 번이면 파이썬 설치부터 패키지까지 끝납니다.
기억할 것은 하나입니다 — toml 은 의도, lock 은 결과.
UV 05

uv run — activate를 잊어도 되는 이유

uv run은 실행 직전에 환경을 자동으로 맞춰줍니다.

uv run 이 없애는 것은 명령어 몇 줄이 아니라 "환경이 어긋난 채로 실행될 가능성" 자체입니다.

실행하기

uv run main.py                 # 스크립트 실행
uv run python                  # REPL 진입
uv run python -m pytest        # 모듈 실행
uv run pytest                  # 설치된 명령 실행
uv run --with rich python      # 임시로 패키지 추가해 실행

# 매번 uv run 이 귀찮다면 (기존 방식도 가능)
.venv\Scripts\activate         # Windows
source .venv/bin/activate      # Mac/Linux
uv run이 하는 일 — ① lock 확인 → ② 환경이 다르면 자동 동기화 → ③ .venv의 파이썬으로 실행. 즉 항상 최신 상태에서 실행되는 것이 보장됩니다.

단일 파일 스크립트 (PEP 723)

# analyze.py — 파일 안에 의존성을 직접 적습니다
# /// script
# requires-python = ">=3.14"
# dependencies = ["pandas", "matplotlib"]
# ///

import pandas as pd
df = pd.read_csv("sales.csv")
print(df.describe())
# 프로젝트 없이 바로 실행 — uv가 임시 환경을 만들어 줌
uv run analyze.py

# 의존성 블록을 명령으로 추가
uv add --script analyze.py pandas matplotlib
실무에서 아주 유용 — 동료에게 .py 파일 하나만 보내도 uv run 한 줄로 돌아갑니다. 설치 안내 문서가 필요 없습니다.
UV 06

pyproject.toml 해부

프로젝트의 모든 설정이 이 파일 하나에 모입니다.

[project]
name = "myapp"
version = "0.1.0"
description = "업무 자동화 도구"
requires-python = ">=3.14"
dependencies = [                 # ← uv add 가 여기에 씁니다
    "pandas>=2.2.0",
    "numpy>=2.0",
    "opencv-python>=4.14,<5",    # OpenCV 5 는 당분간 회피
    "pyside6>=6.11",
]

[project.scripts]                # 실행 명령 등록
myapp = "myapp.main:run"         # -> uv run myapp

[dependency-groups]              # uv add --dev 가 여기에
dev = ["pytest>=9.0", "ruff>=0.16", "mypy>=2.0"]

[tool.uv]
package = true                   # 0.12 기본값 (--no-package 로 만들면 false)

[tool.ruff]                      # 린터 설정도 같은 파일에
line-length = 100
target-version = "py314"

[build-system]                   # uv init 0.12 의 기본 백엔드
requires = ["uv_build>=0.12,<0.13"]
build-backend = "uv_build"
opencv-python 은 4.x 로 묶어 두세요 — OpenCV 5가 2026-07 에 나왔지만 일부 API 가 opencv-contrib-python 쪽으로 옮겨가서 기존 코드가 조용히 깨질 수 있습니다. 당장 5 의 기능이 필요한 게 아니라면 opencv-python>=4.14,<5로 메이저 업그레이드를 막아 두는 편이 안전합니다.
build-backend 는 골라 쓸 수 있습니다 — 위의 uv_build는 uv 가 직접 만든 기본 백엔드로, 별도 설치 없이 가장 빠릅니다. hatchling·setuptools·flit도 그대로 쓸 수 있으니 이미 쓰던 게 있으면 굳이 바꾸지 않아도 됩니다. uv init --build-backend hatch 처럼 생성 시점에 지정할 수도 있습니다.

버전 표기법

표기의미
pandas아무 버전이나 (권장하지 않음)
pandas>=2.22.2 이상 (가장 흔함)
pandas==2.2.3정확히 이 버전
pandas~=2.2.02.2.x 안에서만 (패치만 허용)
pandas>=2.2,<3메이저 업그레이드 차단

개발 도구 세팅 (권장)

uv add --dev ruff pytest mypy

uv run ruff check .        # 린트 검사
uv run ruff check --fix .  # 자동 수정
uv run ruff format .       # 포매팅 (black 대체)
uv run mypy src            # 타입 검사
uv run pytest -v           # 테스트
Spring 비유 — ruff는 Checkstyle + SpotBugs + 포매터를 하나로 합친 도구입니다. Rust로 짜여 있어 수천 개 파일도 1초 안에 끝납니다. [tool.ruff] 설정이 pyproject.toml에 같이 들어가는 것도 Gradle 설정이 build.gradle에 모이는 것과 같습니다.

린터·타입체커 설정 채워 넣기

ruff — 어떤 규칙을 켤지 고르기

[tool.ruff]
line-length = 100
target-version = "py314"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
코드무엇을 잡나
Epycodestyle — 들여쓰기·공백 등 스타일 (기본)
Fpyflakes — 안 쓰는 import, 정의 안 된 이름 (기본)
Iisort — import 순서 정렬
UPpyupgrade — 낡은 문법을 최신 문법으로
Bbugbear — 흔한 버그 패턴 (가변 기본 인자 등)
SIMflake8-simplify — 장황한 코드를 단순하게
대부분 자동으로 고쳐집니다 — uv run ruff check --fix . 한 번이면 import 정렬(I)과 문법 현대화(UP)를 포함해 상당수가 그 자리에서 수정됩니다. 남는 건 사람이 판단해야 하는 것들뿐입니다.

mypy — 타입 검사 (설정이 비어 있기 쉬운 자리)

[tool.mypy]
python_version = "3.14"
strict = true
warn_unreachable = true
uv add --dev mypy
uv run mypy src

# 큰 코드베이스는 병렬로
uv run mypy -n8 src              # = --num-processes 8
mypy 2.0 부터 기본값이 엄격해졌습니다 — --strict-bytes와 --local-partial-types가 기본 ON이라, 1.x 에서 조용히 통과하던 코드에 새 에러가 뜰 수 있습니다. 기존 프로젝트를 올릴 때는 strict = true부터 켜지 말고 에러를 하나씩 정리한 뒤 단계적으로 조이세요.
"이 프로젝트를 돌리려면 뭐가 필요한가"의 답이 한 곳에 있습니다.
UV 07

uvx · 기존 프로젝트 마이그레이션

설치하지 않고 실행하기, 그리고 requirements.txt에서 넘어오기.

uvx — 일회용 실행

# 설치 없이 바로 실행 (npx 와 같은 개념)
uvx ruff check .
uvx black .
uvx httpie GET example.com
uvx --from pyinstaller pyinstaller main.py

# 자주 쓰는 도구는 전역 설치
uv tool install ruff
uv tool install pyinstaller
uv tool list
uv tool upgrade --all
프로젝트를 오염시키지 않습니다 — 도구는 격리된 환경에 깔리므로 프로젝트 의존성에 섞이지 않습니다. 린터·포매터·빌드도구가 여기 해당합니다.

기존 프로젝트 옮기기

# requirements.txt 가 있는 프로젝트에서
uv init                                  # pyproject.toml 생성
uv add -r requirements.txt               # 통째로 가져오기
uv lock                                  # 락파일 생성
rm requirements.txt                      # 이제 불필요

# 반대로 내보내야 할 때 (배포 환경이 pip만 지원)
uv export --format requirements-txt > requirements.txt
uv export --no-dev > requirements.txt

# pip 호환 명령도 그대로 제공 (더 빠름)
uv pip install pandas
uv pip freeze
uv pip sync requirements.txt
Docker/CI 팁 — 빌드 단계에서는 uv sync --frozen --no-dev를 쓰세요. 락파일을 갱신하지 않아 재현성이 보장되고 개발 도구도 빠집니다.

고급 — 워크스페이스와 패키지 발행

워크스페이스 — 한 저장소, 여러 패키지

# 루트 pyproject.toml
[tool.uv.workspace]
members = ["apps/*", "libs/*"]

# 구조
# repo/
#   pyproject.toml        <- workspace 선언
#   uv.lock               <- ★ 전체가 락파일 하나 공유
#   apps/gui/             <- PySide6 앱
#   apps/batch/           <- 배치 스크립트
#   libs/core/            <- 공용 로직 (분석·DB)

# apps/gui/pyproject.toml 에서 내부 패키지 참조
[project]
dependencies = ["core"]
[tool.uv.sources]
core = { workspace = true }
uv run --package gui python -m gui    # 특정 멤버 실행
uv sync --all-packages                # 전부 동기화
Spring 비유 — Gradle 멀티모듈과 동일합니다. GUI·배치·공용 로직을 한 repo에서 관리하면서 버전 충돌은 락파일 하나로 원천 차단됩니다.

라이브러리 빌드·사내 배포

# [build-system] 이 있는 프로젝트는 빌드 가능
# (0.12 부터 uv init 기본, --no-package 로 만들었다면 불가)
uv build                     # dist/*.whl + *.tar.gz 생성

# 팀에 나눠주기 (PyPI 없이)
# 방법 1: 파일로 직접
uv add ../core-0.2.0-py3-none-any.whl
# 방법 2: git 으로
uv add git+https://github.com/우리팀/core --tag v0.2.0
# 방법 3: 사내 인덱스 (pypiserver/devpi/Nexus)
uv publish --publish-url https://pypi.내부주소/legacy/

# 버전 규칙 (SemVer): 깨지는 변경=메이저,
# 기능 추가=마이너, 버그픽스=패치
--index-url 이 아니라 --publish-url — --index-url은 내려받을 때 쓰는 pip 호환 플래그라 uv publish에는 없습니다. 발행에는 업로드 엔드포인트 주소를 --publish-url로 줘야 합니다. pyproject.toml에 미리 적어 두면 이름으로 부를 수 있습니다. 
[[tool.uv.index]]
name = "사내"
url = "https://pypi.내부주소/simple/"
publish-url = "https://pypi.내부주소/legacy/"
uv publish --index 사내      # 위 publish-url 을 그대로 사용
언제 라이브러리로 쪼개나 — 같은 함수(전처리·DB 접근)를 두 번째 프로젝트에서 복사하게 되는 순간입니다. 그 전까지는 한 프로젝트 안의 모듈이면 충분합니다.
가상환경을 직접 만들고 켜는 단계가 통째로 사라집니다.

UV 09

팀으로 쓰기 — 워크스페이스 · CI · 도커

혼자 쓸 때는 uv add 만 알면 됩니다. 여러 명 · 여러 서버가 되면 “내 PC 에선 되는데”가 시작되고, 그때 필요한 것이 락파일을 신뢰하는 습관입니다.

워크스페이스 — 한 저장소에 여러 패키지

# 루트 pyproject.toml
[project]
name = "acme"
requires-python = ">=3.12"

[tool.uv.workspace]
members = ["packages/*", "apps/*"]

# apps/api/pyproject.toml — 사내 공용 패키지를 경로로 참조
[project]
name = "api"
dependencies = ["acme-core", "fastapi>=0.115"]

[tool.uv.sources]
acme-core = { workspace = true }        # PyPI 가 아니라 이 저장소의 것
uv sync                 # 워크스페이스 전체를 한 번에
uv run --package api uvicorn app:api --reload
uv add --package api httpx      # 특정 패키지에만 의존성 추가
락파일은 저장소에 하나입니다. 패키지가 10개여도 uv.lock 은 루트에 한 개 — 패키지끼리 다른 버전을 쓰는 사고가 구조적으로 막힙니다. 반드시 커밋하세요.

CI · 도커 — 재현 가능한 설치

# GitHub Actions
- uses: astral-sh/setup-uv@v5
  with:
    enable-cache: true                  # ~/.cache/uv 를 캐시
    cache-dependency-glob: "uv.lock"
- run: uv sync --locked --all-extras --dev   # ★ 락파일과 다르면 실패
- run: uv run pytest -q
# 멀티스테이지 — 의존성 레이어를 코드와 분리해 캐시를 살린다
FROM ghcr.io/astral-sh/uv:python3.12-bookworm-slim AS build
WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy

# 1) 의존성만 먼저 (코드가 바뀌어도 이 레이어는 재사용된다)
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-install-project --no-dev

# 2) 코드
COPY . .
RUN --mount=type=cache,target=/root/.cache/uv uv sync --locked --no-dev

FROM python:3.12-slim-bookworm
WORKDIR /app
COPY --from=build /app /app
ENV PATH="/app/.venv/bin:$PATH"
CMD ["uvicorn", "app:api", "--host", "0.0.0.0", "--port", "8000"]
uv sync --locked 와 그냥 uv sync 는 다릅니다. --locked 는 락파일이 최신인지 확인만 하고 다르면 실패합니다. CI 에서 이걸 빼면 빌드할 때마다 다른 버전이 설치될 수 있어 “어제는 됐는데”가 생깁니다.
팀 환경 문제의 대부분은 도구가 아니라 기준이 되는 파일이 없어서 생깁니다.
