TEST 01

왜 테스트를 쓰는가

“동작 확인”을 사람이 하느냐 코드가 하느냐의 차이입니다.

손으로 확인하는 것과 무엇이 다른가

[손으로]
  코드 수정 → 서버 켜기 → 브라우저 열기 → 로그인 →
  화면 이동 → 값 입력 → 결과 눈으로 확인       ... 매번 2분

  · 기능이 20개면 전부 다시 볼 수 없습니다 → ★ 방금 고친 것만 봅니다
  · 그래서 "엉뚱한 데가 깨지는" 사고가 납니다
  · 확인한 사람만 알고, 기록도 남지 않습니다

[테스트 코드로]
  pytest                                        ... 3초

  · 20개를 전부, 매번 확인합니다
  · 무엇이 왜 깨졌는지 이름과 함께 나옵니다
  · ★ 다른 사람이 고쳐도 똑같이 지켜집니다
얻는 것설명
회귀 방지 ★고친 곳이 다른 데를 깨뜨렸는지 즉시 알려 줍니다. 테스트의 가장 큰 값어치입니다
리팩터링 자신감구조를 바꿔도 동작이 같음을 증명할 수 있습니다. 테스트가 없으면 아무도 손대지 못하는 코드가 됩니다
살아 있는 문서테스트 이름이 이 함수가 무엇을 보장하는지를 말해 줍니다
설계 압력테스트가 어려운 코드 = 의존이 뒤엉킨 코드. 테스트를 쓰다 보면 구조가 정리됩니다
버그 재발 차단버그를 고칠 때 그 상황을 테스트로 먼저 남기면 같은 버그가 두 번 나지 않습니다

테스트의 층 — 무엇을 얼마나

        ▲  느림 · 비쌈 · 진짜에 가까움
       ╱E2E╲        브라우저까지 (Playwright)      ... 아주 적게
     ╱───────╲
   ╱  통합 테스트 ╲   API + DB 실제로 (x07·x08)    ... 적당히
 ╱───────────────╲
╱   단위 테스트     ╲ 함수 하나 (x02~x06)         ... ★ 가장 많이
─────────────────────
        ▼  빠름 · 쌈 · 좁은 범위

실무 감각
  · 단위 테스트가 대부분을 차지해야 전체가 빨라집니다
  · ★ 하지만 "핵심 시나리오 한 줄짜리 통합 테스트"의
    가성비가 단위 테스트 20개보다 클 때도 많습니다
  · 어디부터? → 돈·권한·계산이 걸린 곳부터
처음이라면 “회귀 방지” 하나만 노리세요. 커버리지 100%, TDD 같은 이야기는 나중입니다. 방금 만든 함수 하나에 대해 “정상 1개 + 예외 1개” 테스트를 쓰는 것부터 시작하면 충분합니다.
테스트가 있다고 버그가 없어지지는 않습니다. 테스트는 “내가 생각한 경우”만 확인합니다. 생각하지 못한 입력은 여전히 뚫립니다 — 그래서 버그가 나면 그 케이스를 테스트로 추가하는 습관이 중요합니다.
“테스트 쓸 시간이 없다” 는 말의 실체는 보통 “디버깅에 쓸 시간은 이미 쓰고 있다” 입니다. 같은 버그를 두 번 이상 고쳐 봤다면 그 시점이 테스트를 도입할 시점입니다.

def apply_discount(price: int, rate: float) -> int:
    """할인율을 적용한 최종 가격(원 단위 내림)."""
    if not 0 <= rate < 1:
        raise ValueError("할인율은 0 이상 1 미만이어야 합니다")
    return int(price * (1 - rate))

scope — 얼마나 자주 다시 만드나

scope생성 주기쓰는 곳
function (기본)테스트 함수마다 대부분. 서로 영향이 없어야 하므로 기본값이 안전합니다
class테스트 클래스마다클래스로 묶어 놓았을 때
module파일마다파일 안에서만 공유할 무거운 자원
package패키지(폴더)마다드묾
session전체 실행에 한 번 DB 컨테이너 · 테스트 엔진 생성처럼 비싼 준비 ★
 
# tests/conftest.py
import pytest
from sqlalchemy import create_engine

@pytest.fixture(scope="session")
def engine():
    """DB 엔진은 전체에서 한 번만 — 비쌉니다."""
    eng = create_engine("postgresql+psycopg://test:test@localhost:5433/test")
    Base.metadata.create_all(eng)
    yield eng
    Base.metadata.drop_all(eng)
    eng.dispose()

@pytest.fixture                       # ★ function scope — 테스트마다 새로
def session(engine):
    """각 테스트는 독립된 트랜잭션에서 (x08)."""
    conn = engine.connect()
    tx = conn.begin()
    s = Session(bind=conn)
    yield s
    s.close()
    tx.rollback()                    # ★ 흔적을 남기지 않습니다
    conn.close()
scope 를 넓히면 테스트가 서로에게 영향을 줍니다. session 스코프 fixture 를 테스트 안에서 수정하면 실행 순서에 따라 결과가 달라집니다. “혼자 돌리면 통과하는데 전체로 돌리면 실패”의 1순위 원인입니다 — 공유하려면 읽기 전용으로 두세요.

테이블로 정리하면 좋은 것들

  • 계산·변환 함수 — 입력 → 기대 출력이 명확한 것
  • 검증 규칙 — 이메일·전화번호·비밀번호 정책
  • 상태 전이 — (현재상태, 이벤트) → 다음상태
  • 버그 케이스 모음 — 실제로 터졌던 입력값을 계속 추가
  • 경계값 — 0, 1, 최댓값, 최댓값+1 (x05)
# 상태 전이표 — 이런 것이 parametrize 의 진가입니다
@pytest.mark.parametrize("current, event, expected", [
    ("PENDING", "pay",    "PAID"),
    ("PENDING", "cancel", "CANCELED"),
    ("PAID",    "ship",   "SHIPPED"),
    ("PAID",    "cancel", "REFUNDING"),
    ("SHIPPED", "cancel", None),          # ★ 불가능한 전이
])
def test_주문_상태_전이(current, event, expected):
    if expected is None:
        with pytest.raises(InvalidTransition):
            transition(current, event)
    else:
        assert transition(current, event) == expected
기대값을 코드로 계산하지 마세요. assert discount(p, r) == int(p * (1 - r)) 처럼 쓰면 구현과 똑같은 식을 두 번 쓴 것이라 버그를 절대 못 잡습니다. 기대값은 사람이 손으로 계산한 상수로 적으세요.

소수점 — == 를 쓰면 안 됩니다

>>> 0.1 + 0.2 == 0.3
False                              # ★ 부동소수점의 숙명
>>> 0.1 + 0.2
0.30000000000000004

# ✅ pytest.approx
def test_부가세_계산():
    assert calc_vat(10_000) == pytest.approx(1000.0)
    assert 0.1 + 0.2 == pytest.approx(0.3)

    # 허용 오차를 직접 지정
    assert measure() == pytest.approx(3.14159, abs=1e-3)   # 절대 오차
    assert price() == pytest.approx(1_000_000, rel=1e-4)   # 상대 오차

    # 리스트·딕셔너리·numpy 배열에도 그대로 적용됩니다 ★
    assert [0.1 + 0.2, 1.0] == pytest.approx([0.3, 1.0])
    assert {"a": 0.1 + 0.2} == pytest.approx({"a": 0.3})
돈은 애초에 float 로 다루지 마세요. int(원 단위) 또는 decimal.Decimal 을 쓰면 approx 가 필요 없어집니다. 정확히 맞아야 하는 값에 근사 비교를 쓰기 시작하면 진짜 1원 오차 버그를 놓칩니다.
TEST 06

mock — 외부를 가짜로

외부 API · 시간 · 랜덤처럼 내가 통제할 수 없는 것을 고정합니다.

왜 필요한가

테스트 안에서 진짜로 부르면 생기는 일

  결제 API      → ★ 실제로 돈이 나갑니다
  이메일 발송   → 사용자에게 진짜 메일이 갑니다
  외부 시세 API → 값이 매번 달라져 assert 를 못 씁니다
  datetime.now  → 내일 돌리면 실패합니다
  random        → 실행할 때마다 결과가 다릅니다
  time.sleep(5) → 테스트 하나가 5초를 잡아먹습니다

→ 이런 것들을 "가짜"로 바꿔치기하는 것이 mock 입니다.
# app/notify.py
import httpx

def send_slack(message: str) -> bool:
    r = httpx.post("https://hooks.slack.com/xxx", json={"text": message},
                   timeout=3.0)
    return r.status_code == 200

def notify_order(order_id: int) -> bool:
    return send_slack(f"주문 {order_id} 접수")
# tests/test_notify.py
from unittest.mock import patch, MagicMock
from app import notify

@patch("app.notify.httpx.post")          # ★ "쓰이는 곳" 기준으로 경로를 씁니다
def test_슬랙_전송_성공(mock_post):
    mock_post.return_value = MagicMock(status_code=200)

    assert notify.notify_order(42) is True

    # 호출됐는지 · 무엇으로 불렸는지까지 검증 ★
    mock_post.assert_called_once()
    kwargs = mock_post.call_args.kwargs
    assert "주문 42" in kwargs["json"]["text"]
    assert kwargs["timeout"] == 3.0

@patch("app.notify.httpx.post")

    mock_post.return_value = MagicMock(status_code=500)
    assert notify.notify_order(42) is False

@patch("app.notify.httpx.post", side_effect=httpx.TimeoutException("timeout"))
def test_타임아웃은_예외로_올라온다(mock_post):

patch 경로는 “정의된 곳”이 아니라 “쓰이는 곳”입니다. app/notify.py 안에서 쓰는 httpx.post 를 바꾸려면 "httpx.post" 가 아니라 "app.notify.httpx.post" 를 patch 해야 합니다. mock 이 “안 먹는” 경우의 대부분이 이 실수입니다.

TEST 08

DB 테스트

핵심은 하나 — 테스트가 끝나면 흔적이 남지 않아야 합니다.

세 가지 방법

방법속도특징
트랜잭션 롤백 ★가장 빠름 테스트마다 트랜잭션을 열고 끝나면 롤백. 데이터가 남지 않습니다. 1순위 선택
매번 초기화느림 drop_all + create_all. 단순하지만 테이블이 많으면 답답합니다
SQLite 메모리매우 빠름 설치가 필요 없지만 방언이 다릅니다. JSONB·윈도우 함수 등에서 갈립니다 ⚠️
Testcontainers느림(첫 실행) 운영과 같은 DB를 도커로 띄웁니다. 가장 신뢰도 높음
운영 DB 와 다른 DB 로 테스트하지 마세요. PostgreSQL 로 서비스하면서 SQLite 로 테스트하면 테스트는 통과하는데 운영에서 터지는 상황이 생깁니다 (대소문자 구분 · 트랜잭션 격리 · 타입 · 인덱스 동작이 다릅니다).

services:

def test_재고가_부족하면_주문할_수_없다(session):
    # ── Arrange (준비) ─────────────────────────
    product = make_product(session, stock=1)
    user = make_user(session)

    # ── Act (실행) ─────────────────────────────  ★ 딱 한 줄이어야 좋습니다
    with pytest.raises(OutOfStock) as e:
        place_order(session, user.id, product.id, qty=5)

    # ── Assert (검증) ──────────────────────────
    assert e.value.detail["available"] == 1
    assert session.query(Order).count() == 0        # 부작용도 확인
Act 가 여러 줄이면 테스트가 두 개일 가능성이 높습니다. “A 하고 B 하면 C 가 된다”를 검증하고 싶다면 A 는 Arrange 로 옮기고 B 만 Act 에 두세요. 실패했을 때 어디가 문제인지 즉시 보입니다.

증상문제 · 해결
깜빡이는 테스트
(flaky)		 가끔 실패합니다. 원인은 대개 시간 · 랜덤 · 순서 · 실제 네트워크. 고정(x06) 하거나 지우세요. ★ 가끔 실패하는 테스트는 아무도 안 믿게 됩니다
순서 의존혼자 돌리면 되는데 전체로 돌리면 실패. pytest -p no:randomly 없이도 통과해야 합니다. 공유 상태를 제거(x03·x08)
sleep 이 박힌 테스트 time.sleep(3) 대신 조건 대기나 mock 으로. 테스트 전체 시간이 분 단위가 되면 아무도 안 돌립니다
assert 없는 테스트 “에러만 안 나면 통과”. 커버리지는 오르는데 아무것도 보장하지 않습니다
거대한 테스트 200줄에 assert 30개. 실패하면 원인을 못 찾습니다. 쪼개세요
구현 복사 기대값을 구현과 같은 식으로 계산 (x04). 상수로 적으세요
mock 범벅 전부 가짜라 실제 연동이 깨져도 통과 (x06)
주석 처리된 테스트 # def test_... 로 남겨 두지 마세요. @pytest.mark.skip(reason=...) 로 이유와 함께

FIRST — 좋은 테스트의 다섯 글자

F  Fast          빠르다        전체가 몇 초 안에 끝나야 자주 돌립니다
I  Independent   독립적이다     순서·다른 테스트에 영향받지 않습니다
R  Repeatable    반복 가능하다   몇 번을 돌려도 같은 결과 (시간·랜덤 고정)
S  Self-validating 자가 검증한다 통과/실패가 자동으로 판정됩니다
                               ★ "출력을 눈으로 보는" 테스트는 테스트가 아닙니다
T  Timely        제때 쓴다      기능과 함께. 나중에 몰아 쓰면 영영 안 씁니다

오늘부터 할 수 있는 것

  • ☐ uv add --dev pytest 하고 테스트 파일 하나를 만든다
  • ☐ 가장 계산이 복잡한 함수 하나에 정상 1개 + 예외 1개
  • ☐ 다음에 버그를 고칠 때, 고치기 전에 실패하는 테스트부터 쓴다
  • ☐ --cov 를 붙여 0% 인 파일이 뭔지 본다
  • ☐ GitHub Actions 워크플로 하나(x09)를 붙이고 Required check 로 건다
  • ☐ API 를 만들었다면 핵심 시나리오 하나를 TestClient 로 (x07)
