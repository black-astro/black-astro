파이썬은 프로젝트 구조를 강제하지 않습니다. 그래서 같은 회사 안에서도 저장소마다 모양이 다르고, 규모가 커지면 "이 코드는 어디에 두지?"를 매번 회의로 정하게 됩니다. 이 탭은 라이브러리 · CLI · 웹 API · Django · 데이터/ML · 데스크톱 · 모노레포의 권장 구조를 한 장씩 보여 주고, 각 구조에서 무엇을 어디에 두는지, 무엇이 무엇을 import 해도 되는지, 언제 다음 단계로 넘어가는지를 짧게 정리합니다. src 레이아웃의 원리 · 도메인 경계 · 순환 import 를 깊게 다룬 내용은 🏭 실무 탭 PROD 01 에 있으니, 여기서는 유형별 지도에 집중합니다.

STR 01

파이썬 프로젝트의 공통 바탕 — pyproject 하나와 src 레이아웃

유형이 달라도 바닥은 같습니다. 설정은 pyproject.toml 한 파일, 코드는 src/<패키지>/ 아래, 테스트는 그 옆. 이 바닥을 먼저 깔아 두면 뒤의 일곱 유형은 src/<패키지>/ 안을 어떻게 나누느냐의 차이일 뿐입니다.

모든 유형의 공통 골격

myproj/
├─ pyproject.toml        이름 · 의존성 · 진입점 · 도구 설정 전부
├─ uv.lock               정확한 버전 (커밋 O)
├─ .python-version       파이썬 버전 고정
├─ README.md
├─ src/
│  └─ myproj/            import myproj 가 가리키는 곳
│     ├─ __init__.py     "여기부터 패키지" 표시 · 가볍게
│     └─ core.py         모듈 = .py 파일 하나
├─ tests/                src/myproj 와 같은 모양 (STR 08)
├─ scripts/              일회성 스크립트 — 패키지 밖
└─ .gitignore            .venv/ · .env · __pycache__/

용어 세 개만 정확히

이름실체import 모양
모듈.py 파일 하나myproj.core
패키지__init__.py 가 있는 폴더myproj
배포 패키지pip/uv 로 설치하는 단위 — [project] name이름이 달라도 됨
(my-proj → my_proj)
__init__.py 를 빠뜨려도 import 는 됩니다 — 파이썬이 "네임스페이스 패키지"로 취급하기 때문입니다. 그래서 실수를 늦게 알아챕니다. 여러 배포 패키지가 한 이름공간을 나눠 쓰는 경우가 아니면 항상 둡니다 (ruff 의 INP001 규칙이 빠진 곳을 찾아 줍니다).

src 레이아웃 vs 평평한 레이아웃 — 테스트가 무엇을 import 하나 🟢 기초

Python Packaging User Guide 는 두 방식을 모두 소개하면서 src 레이아웃의 장점으로 "설치하지 않은 코드를 실수로 import 하는 일을 막는다"를 꼽습니다. 평평한 레이아웃(./myproj/)에서는 저장소 루트가 곧 import 경로라서 테스트가 현재 폴더의 소스를 집어 오고, 패키지 데이터 누락 같은 실수가 배포 뒤에야 드러납니다. 이 PC 에서 확인해 보면 src 레이아웃은 설치 전에는 루트에서조차 import 가 안 됩니다. 

# src 레이아웃 — 저장소 루트에서 (설치 전)
python -c "import shop2"
# ModuleNotFoundError: No module named 'shop2'

# uv sync 가 프로젝트를 .venv 에 편집 가능 설치한 뒤
uv run python -c "import shop2"   # OK — 어디서 실행해도 같은 코드
더 깊게는 — 평평한 레이아웃에서 실제로 나는 사고(템플릿 파일 누락), --import-mode=importlib, 도메인 · 어댑터 경계는 🏭 실무 탭 PROD 01 에 있습니다. 여기서 기억할 것은 하나 — "새로 만든다면 src, 이미 평평한 저장소는 굳이 옮기지 않는다"입니다. uv 의 uv init --package · --lib 가 처음부터 src 레이아웃을 만들어 줍니다(📦 uv 탭 UV 02).

규모별 진화 — 언제 다음 단계로 넘어가나 🟡 중급

초록 점이 권장 출발점 — 두 번째 사람이나 첫 테스트가 생기는 순간 src 패키지로 옮깁니다.
전환신호 (하나라도 해당하면)하는 일
파일 → 모듈 몇 개한 파일이 300줄을 넘김 · 같은 함수를 두 스크립트가 복사해 씀공용 함수를 utils 가 아니라 이름 있는 모듈로
모듈 → src 패키지테스트를 붙임 · 두 번째 사람 · 서버/PC 에 배포 · 진입점 2개uv init --package 로 옮기고 tests/ 신설
패키지 → 하위 패키지모듈 20개+ · "이건 주문 쪽, 이건 회원 쪽" 대화가 나옴기능(도메인)별 폴더 + 의존 방향 규칙 (STR 10)
하위 패키지 → 워크스페이스배포 단위 2개+ (API · 배치 · 라이브러리) · 팀이 둘로 갈림packages/* · apps/* 로 분리 (STR 09)
정리 — 설정은 pyproject.toml 하나, 코드는 src/<패키지>/, 테스트는 tests/. 이 바닥 위에서 사람 · 진입점 · 배포 단위가 늘 때마다 한 단계씩 나눕니다.
STR 02

라이브러리 · CLI 도구 — 문은 여러 개, 공개 API 는 하나

라이브러리는 남이 import 하고, CLI 는 남이 명령으로 칩니다. 둘 다 "바깥에 약속한 이름"이 있어서, 그 약속과 내부 구현을 파일 수준에서 갈라 두는 것이 구조의 핵심입니다. 내부 파일을 옮겨도 사용자 코드가 안 깨지게 만드는 것이 목표입니다. 

textkit/                     라이브러리 + CLI 를 한 배포 패키지로
├─ pyproject.toml            [project.scripts] textkit = "textkit.cli:main"
├─ src/textkit/
│  ├─ __init__.py            공개 API 재노출 · __all__ · __version__
│  ├─ __main__.py            python -m textkit → cli.main()
│  ├─ cli.py                 인자 파싱 · 출력 · 종료 코드만
│  ├─ core.py                공개 함수 (slugify · wrap …)
│  ├─ _normalize.py          밑줄 = 내부 구현 · 언제든 바뀜
│  └─ py.typed               빈 파일 — "타입 힌트 있음" 표시 (PEP 561)
├─ tests/
└─ README.md
문(진입점)은 셋이어도 약속(공개 API)은 __init__.py 한 곳입니다.

pyproject — 진입점과 타입 표시

[project]
name = "textkit"
version = "0.3.0"
requires-python = ">=3.12"
dependencies = []            # 라이브러리는 범위로 (==고정 금지)

[project.scripts]
textkit = "textkit.cli:main" # 설치하면 textkit 명령이 생김

[build-system]               # uv init --lib 가 적어 줍니다 (버전 범위 생략)
requires = ["uv_build"]
build-backend = "uv_build"
py.typed 는 내용 없는 빈 파일입니다. 이게 있어야 mypy · pyright 가 사용자 쪽에서 이 패키지의 타입 힌트를 읽습니다(PEP 561). 빌드 백엔드가 패키지 폴더 안 파일을 함께 담으니 따로 등록할 필요는 보통 없습니다.

__init__ · cli · __main__

# src/textkit/__init__.py — 바깥에 약속하는 이름
from textkit.core import slugify, wrap

__all__ = ["slugify", "wrap"]
__version__ = "0.3.0"

# src/textkit/cli.py — 얇게: 파싱 → core 호출 → 종료 코드
import argparse
from textkit import slugify

def main(argv: list[str] | None = None) -> int:
    p = argparse.ArgumentParser(prog="textkit")
    p.add_argument("text")
    args = p.parse_args(argv)
    print(slugify(args.text))
    return 0

# src/textkit/__main__.py
from textkit.cli import main
raise SystemExit(main())
❌ 내부 경로가 곧 공개 API
# 사용자 코드
from textkit.core.utils.text import slugify
# → utils 를 정리하는 순간 모든 사용자가 깨짐

# __init__.py 에서 무거운 것을 import
import pandas            # textkit --help 도 1초
✅ 한 층 위에서 재노출, 내부는 밑줄
# 사용자 코드
from textkit import slugify
# → core.py 를 쪼개도 __init__ 만 고치면 됨

# 무거운 의존은 쓰는 함수 안에서
def to_frame(rows):
    import pandas as pd  # 필요할 때만 로드
    return pd.DataFrame(rows)
밑줄은 약속일 뿐 잠금이 아닙니다 — textkit._normalize 도 import 는 됩니다. 파이썬의 관례는 "밑줄로 시작하는 모듈 · 이름 · __all__ 에 없는 이름은 바뀌어도 불평하지 않기"입니다. 시작이 느린 CLI 는 python -X importtime -m textkit --help 로 어느 import 가 시간을 먹는지 바로 보입니다.
정리 — 진입점은 [project.scripts] 와 __main__.py, 공개 API 는 __init__.py 의 __all__, 구현은 _밑줄 모듈. CLI 파일은 얇게, __init__ 은 가볍게.
STR 03

FastAPI 서비스 — 층으로 나누다가 기능으로 나눈다

FastAPI 는 폴더 구조를 정해 주지 않습니다. 공식 문서의 "Bigger Applications" 는 routers/ 와 공용 의존성 파일 정도만 보여 주고, 공식 템플릿(full-stack-fastapi-template)은 api/routes · core · models · crud 로 나눕니다. 그 사이의 실무 관례를 정리하면 처음엔 층(api · services · repositories)으로, 업무 영역이 늘면 기능(orders · users)으로 갑니다.

① 계층별 — 업무 영역 4개 이하

src/app/
├─ main.py           FastAPI() · include_router
├─ api/
│  ├─ deps.py        get_db · current_user (Depends)
│  └─ routes/        orders.py · users.py
├─ services/         업무 규칙 — FastAPI 모름
├─ repositories/     SQL · 세션 다루기
├─ schemas/          pydantic — 요청/응답 모양
├─ models/           SQLAlchemy ORM — 테이블
└─ core/             config · security · db

② 기능별 — 영역 5개+ · 팀이 나뉨

src/app/
├─ main.py
├─ core/             config · security · db (모두가 씀)
├─ orders/
│  ├─ router.py      APIRouter · Depends
│  ├─ service.py
│  ├─ repository.py
│  ├─ schemas.py
│  └─ models.py
├─ users/            같은 다섯 파일
└─ payments/
services 가 FastAPI 를 import 하지 않으면 같은 함수를 배치 · CLI · 테스트에서 그대로 부를 수 있습니다.

api 층 — Depends 는 여기에만

# src/app/api/deps.py
from typing import Annotated
from fastapi import Depends
from sqlalchemy.orm import Session
from app.core.db import SessionLocal

def get_db():
    with SessionLocal() as db:
        yield db

DbDep = Annotated[Session, Depends(get_db)]

# src/app/api/routes/orders.py
from fastapi import APIRouter, HTTPException
from app.api.deps import DbDep
from app.schemas.order import OrderCreate, OrderOut
from app.services import orders as svc

router = APIRouter(prefix="/orders", tags=["orders"])

@router.post("", response_model=OrderOut, status_code=201)  # OrderOut: from_attributes=True
def create_order(body: OrderCreate, db: DbDep):
    try:
        return svc.create_order(db, body)
    except svc.OutOfStock as e:          # 업무 예외 → HTTP 로 번역
        raise HTTPException(409, str(e))

services 층 — 웹을 모르는 함수

# src/app/services/orders.py
from sqlalchemy.orm import Session
from app.repositories import orders as repo
from app.schemas.order import OrderCreate

class OutOfStock(Exception):
    pass

def create_order(db: Session, body: OrderCreate):
    if repo.stock_of(db, body.item_id) < body.qty:
        raise OutOfStock(f"item={body.item_id}")
    order = repo.add(db, body)
    db.commit()                       # 트랜잭션 경계는 서비스가
    return order
도메인과 DB 를 더 떼고 싶다면 — 서비스가 Session 대신 Protocol 로 선언한 저장소를 받게 하는 방식은 🏭 실무 탭 PROD 01(도메인 · 어댑터), 계층 · DDD 의 원리는 🧬 전문가 탭 DEEP 16 에 있습니다. 처음 서버를 세우는 단계는 🌐 웹 탭 WEB 05 "파일이 늘어나면".
기준① 계층별② 기능별
새 기능 하나 추가폴더 5곳에 파일 하나씩폴더 하나 안에서 끝
처음 보는 사람"요청이 어떻게 흐르나"가 잘 보임"이 서비스가 무엇을 하나"가 잘 보임
잘 맞는 규모영역 4개 이하 · 1팀영역 5개+ · 기능별 담당자
지켜야 할 규칙위층 → 아래층만다른 기능은 그쪽 service 로만 (repository 직접 금지)
나눌 때 가장 흔한 실수 — schemas.OrderOut(응답 모양)과 models.Order(테이블)를 하나로 합치는 것. 컬럼을 하나 추가했을 뿐인데 API 응답에 비밀 필드가 나가는 사고가 여기서 납니다. 둘은 이름이 같아도 다른 파일에 둡니다.
정리 — api → services → repositories → models 한 방향, Depends · HTTPException 은 api 층에만. 영역이 다섯을 넘으면 같은 다섯 파일을 기능 폴더 안으로 옮깁니다.
STR 04

Django 프로젝트 — 설정 패키지 하나와 앱 여러 개

Django 는 구조를 꽤 정해 줍니다. startproject 가 만드는 것은 설정 패키지(settings · urls · asgi)이고, startapp 이 만드는 것이 앱(models · views · admin · migrations)입니다. 남는 질문은 둘 — 앱을 어떻게 나누나, 앱이 커지면 로직을 어디에 두나. 

shop/
├─ pyproject.toml
├─ manage.py                 기본 DJANGO_SETTINGS_MODULE 지정
├─ config/                   django-admin startproject config .  (이름은 관례)
│  ├─ settings/              settings.py 를 패키지로 쪼갬 (직접)
│  │  ├─ __init__.py
│  │  ├─ base.py             공통
│  │  ├─ dev.py              from .base import * · DEBUG = True
│  │  └─ prod.py             비밀은 환경변수에서
│  ├─ urls.py                각 앱의 urls 를 include 만
│  └─ asgi.py · wsgi.py
├─ accounts/                 python manage.py startapp accounts
├─ orders/
│  ├─ models.py · admin.py · apps.py · urls.py · views.py
│  ├─ services.py            쓰기 로직 (커뮤니티 관례)
│  ├─ selectors.py           읽기 쿼리 (커뮤니티 관례)
│  ├─ migrations/
│  └─ tests/
├─ payments/
├─ templates/ · static/      여러 앱이 같이 쓰는 것
└─ tests/                    (선택) 앱을 가로지르는 통합 테스트
Django 앱은 업무 개념 하나 — 기반 앱(accounts)은 아무도 import 하지 않게 둡니다.

settings 를 base · dev · prod 로

# config/settings/base.py
from pathlib import Path
# settings/ 로 한 층 깊어졌으니 parent 가 하나 더
BASE_DIR = Path(__file__).resolve().parent.parent.parent
INSTALLED_APPS = [
    "django.contrib.admin", "django.contrib.auth",
    "django.contrib.contenttypes", "django.contrib.sessions",
    "django.contrib.messages", "django.contrib.staticfiles",
    "accounts", "orders", "payments",
]

# config/settings/dev.py
from .base import *          # noqa: F403
DEBUG = True
ALLOWED_HOSTS = ["localhost", "127.0.0.1"]

# config/settings/prod.py
import os
from .base import *          # noqa: F403
DEBUG = False
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]  # 없으면 기동 실패
ALLOWED_HOSTS = os.environ["ALLOWED_HOSTS"].split(",")
기본값을 고치는 곳이 두 군데 — manage.py 와 asgi.py(wsgi.py) 모두 os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings") 를 갖고 있습니다. "config.settings.dev" 로 바꾸고, 운영 서버는 환경변수로 config.settings.prod 를 줍니다.

앱이 커지면 — services · selectors

# orders/services.py — 쓰기: 규칙 + 트랜잭션
from django.db import transaction
from orders.models import Order

@transaction.atomic
def order_place(*, user, item_ids: list[int]) -> Order:
    order = Order.objects.create(user=user)
    order.items.set(item_ids)
    return order

# orders/selectors.py — 읽기: 쿼리만
def order_list_for(*, user):
    return (Order.objects.filter(user=user)
            .prefetch_related("items"))

# orders/views.py — 얇게: 입력 검증 → 서비스 호출 → 응답
공식 규칙이 아닙니다 — services.py / selectors.py 는 HackSoft 의 Django Styleguide 에서 퍼진 커뮤니티 관례입니다. Django 공식 문서는 로직을 모델 메서드 · 매니저에 두는 예를 더 많이 보여 줍니다. 뷰 · 시리얼라이저 · 시그널에 로직이 흩어지기 시작했다면 그때 도입하세요.

def build() -> Path:

STR 06

데스크톱 앱 (PySide6) — 화면과 로직을 다른 폴더에

GUI 앱은 main_window.py 하나에 버튼 처리 · pandas 집계 · 파일 저장이 다 들어가기 쉽습니다. 그러면 로직 하나를 테스트하려 해도 창을 띄워야 합니다. 구조의 원칙은 단순합니다 — Qt 를 import 하는 파일은 ui/ 에만, 리소스는 패키지 안에, 진입점은 하나.

STR 07

설정 · 비밀 · 환경 — 한 모듈로 모으고 .env 는 커밋하지 않는다

# src/app/core/config.py
from functools import lru_cache
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env", env_prefix="APP_", extra="ignore")

    env: str = "dev"
    database_url: str            # 기본값 없음 = 필수 → 없으면 기동 실패
    api_key: SecretStr           # 출력해도 '**********'
    debug: bool = False

@lru_cache
def get_settings() -> Settings:
    return Settings()
바깥 모듈은 get_settings() 만 부릅니다 — 필요한 값의 목록이 곧 Settings 클래스입니다.

import-linter — 기능 폴더는 서로 모른다

# uv add --dev import-linter → uv run lint-imports
[tool.importlinter]
root_packages = ["app"]

[[tool.importlinter.contracts]]
name = "기능 폴더끼리는 서로 모른다"
type = "independence"
modules = ["app.orders", "app.users", "app.payments"]
ignore_imports = [
    # 예외는 이름을 붙여서: service 끼리만 허용
    "app.orders.service -> app.users.service",
]

[[tool.importlinter.contracts]]
name = "기능 폴더 안의 층"
type = "layers"
containers = ["app.orders", "app.users", "app.payments"]
layers = ["router", "service", "repository"]
layers · forbidden 계약의 기본형(api → services → domain, 도메인이 httpx 를 모르게)과 실패 출력은 🏭 실무 탭 PROD 01 에 있습니다.

# tests/test_imports.py — 모듈마다 새 인터프리터에서 단독 import
import pkgutil, subprocess, sys
import pytest
import app

MODULES = [m.name for m in pkgutil.walk_packages(app.__path__, "app.")
           if not m.name.endswith("__main__")]

@pytest.mark.parametrize("mod", MODULES)
def test_import_alone(mod):
    r = subprocess.run([sys.executable, "-c", f"import {mod}"],
                       capture_output=True, text=True)
    assert r.returncode == 0, r.stderr
왜 단독으로 — 순환은 import 순서에 따라 숨습니다. 테스트 한 프로세스 안에서는 다른 테스트가 먼저 import 해 둔 덕에 통과하기도 합니다. 이 PC 에서 STR 09 의 shop 패키지에 같은 루프를 돌리면 shop.orders · shop.users 둘 다 FAIL, 고친 shop2 는 전부 OK 였습니다. pylint 로 보려면 uv run --with pylint pylint --disable=all --enable=cyclic-import src/app.
정리 — 만드는 것(라이브러리 · 웹 · GUI · 데이터)이 출발 구조를 정하고, 사람 · 진입점 · 배포 단위가 다음 단계를 정합니다. 정한 import 방향은 import-linter · ruff · 단독 import 테스트로 CI 에 걸어 둡니다.
