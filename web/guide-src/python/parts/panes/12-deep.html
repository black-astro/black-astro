DEEP 01

CPython 이 코드를 실행하는 과정

파이썬은 인터프리터 언어일까요? 바이트코드로 컴파일된 뒤 실행됩니다.

파이썬이 느리다고 할 때 느린 것은 평가 루프가 명령 하나마다 치르는 비용입니다 — 루프를 줄이는 최적화가 통하는 이유입니다.

파이프라인

소스 코드 (.py)
   ↓  토크나이저 · 파서
추상 구문 트리 (AST)
   ↓  컴파일러
바이트코드 (.pyc 로 캐시 — __pycache__)
   ↓  평가 루프 (ceval.c) ★ 여기서 한 줄씩 실행
결과

★ 컴파일 단계가 있으므로 "순수 인터프리터"는 아닙니다.
  다만 기계어가 아니라 "바이트코드"까지만 만듭니다.
  (자바의 JVM 바이트코드와 같은 개념 · 기본 빌드에서 JIT 는 꺼져 있음,
   3.14 공식 바이너리에는 실험적 JIT 가 포함돼 있어 켜 볼 수 있습니다)
import dis

def add(a, b):
    return a + b

dis.dis(add)
# 3.14.2 실측
#   RESUME          0
#   LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)
#   BINARY_OP       0 (+)
#   RETURN_VALUE
#
# ★ 3.14 에서 달라진 점
#   · LOAD_FAST_BORROW — 참조 카운트를 올리지 않고 지역 변수를 빌려 옵니다
#   · 지역 변수를 연달아 읽으면 LOAD_FAST_BORROW_LOAD_FAST_BORROW 로 융합됩니다
#   · BINARY_OP 는 oparg 로 연산자를 구분합니다 (0 = +, 13 = +=)
#     BINARY_SUBSCR(a[i]) 도 BINARY_OP 의 NB_SUBSCR 로 통합됐습니다
#   · 전역 접근은 여전히 LOAD_GLOBAL (3.14 는 "LOAD_GLOBAL 1 (range + NULL)" 로 표시)

# ★ 왜 이걸 보나
#   "왜 이 코드가 더 빠른가"를 눈으로 확인할 수 있습니다
dis.dis("a = [1,2,3]")        # BUILD_LIST
dis.dis("a = (1,2,3)")        # LOAD_CONST — ★ 튜플은 상수로 미리 만들어집니다

# ⚠ 바이트코드는 마이너 버전마다 바뀝니다.
#   명령 이름을 외우지 말고 쓰는 버전에서 직접 dis 로 확인하세요.
3.11 부터 “Specializing Adaptive Interpreter” 가 들어왔습니다. 같은 타입이 반복되면 전용 명령으로 바꿔 실행합니다 (BINARY_OP → BINARY_OP_ADD_INT). 3.10 대비 10~60% 빨라진 이유입니다. JIT(PEP 744)는 3.13 부터 실험적으로 들어왔고, 3.14 부터는 Windows·macOS 공식 바이너리에 포함되어 켜 볼 수 있습니다. 다만 여전히 기본은 꺼져 있는 실험 단계입니다.

알아 두면 유용한 사실들

# ① 작은 정수·짧은 문자열은 캐시됩니다 (인터닝)
a, b = 256, 256
a is b            # True  (-5 ~ 256 은 미리 만들어 둔 객체)
c, d = 257, 257
c is d            # False (별도 객체)  ★ 그래서 is 로 값 비교를 하면 안 됩니다

# ② .pyc 는 소스가 안 바뀌면 재사용됩니다
#    (셸에서) python -X importtime app.py   # ★ 임포트가 느린 모듈 찾기

# ③ 지역 변수가 전역보다 빠릅니다 (3.14 기준 LOAD_FAST_BORROW vs LOAD_GLOBAL)
def slow():
    for i in range(1000): len(data)      # 매번 전역 조회
def fast():
    _len = len                            # ★ 지역으로 끌어오기
    for i in range(1000): _len(data)

# ④ 문자열 연결
"".join(parts)                # ★ O(n)
s += x  (반복문 안)            # O(n²) 가 될 수 있음
이 지식으로 미시 최적화부터 하지 마세요. 파이썬에서 성능 문제의 원인은 대부분 쿼리 · 알고리즘 복잡도 · 불필요한 I/O 입니다. 바이트코드 수준 최적화는 프로파일러가 특정 함수를 지목한 뒤에 하는 일입니다 (⚡ 대규모 트래픽 탭 k14).

버전 로드맵 — 알아 둘 PEP 3.14 / 3.15

  • PEP 649/749 — 어노테이션 지연 평가가 3.14 부터 기본. from __future__ import annotations 가 더 이상 필요 없고, 전방 참조를 문자열로 감쌀 필요도 없습니다. 런타임에 어노테이션을 읽어야 하면 새 표준 모듈 annotationlib 을 씁니다.
  • PEP 750 — t-string(3.14). t"…" 은 문자열이 아니라 Template 객체를 만듭니다. f-string 과 달리 조립되기 전 구조(정적 문자열 조각 + 보간값)를 라이브러리에 그대로 넘길 수 있어, SQL 인젝션·XSS 를 라이브러리가 원천 차단할 수 있습니다 (z15).
  • PEP 779 — free-threading 공식 지원(3.14). 실험 딱지를 뗐습니다 (z10).
  • PEP 744 — JIT. 3.14 부터 공식 바이너리에 포함되지만 기본은 꺼짐 · 실험 단계.
# PEP 649 — 3.14 에서는 아래 import 없이도 전방 참조가 그냥 됩니다
# from __future__ import annotations      ← 더 이상 필요 없음
import annotationlib
from dataclasses import dataclass

@dataclass
class Node:
    parent: Node | None = None            # ★ 따옴표로 감쌀 필요가 없습니다

annotationlib.get_annotations(Node)       # 필요할 때만 평가됩니다
# {'parent': __main__.Node | None}

# PEP 750 — t-string 은 str 이 아니라 Template
name = "Robert'); DROP TABLE users;--"
query = t"SELECT * FROM users WHERE name = {name}"
type(query)          # <class 'string.templatelib.Template'>
# ★ 라이브러리가 "정적 조각"과 "보간값"을 구분해서 받습니다
#   → name 을 반드시 파라미터 바인딩으로 처리하도록 강제할 수 있습니다
# ❌ f"SELECT ... {name}" 은 이미 합쳐진 문자열이라 구분이 불가능합니다
3.15 (2026-10 예정) 확정분 — PEP 810 lazy import(lazy import 문. 무거운 모듈을 실제로 쓸 때 로드해 CLI 시작 시간을 줄입니다), PEP 814 frozendict 내장, PEP 799 표준 프로파일러(stdlib 에 통합되는 샘플링 프로파일러), 그리고 JIT 의 x86-64 성능 8~9% 개선.
DEEP 02

객체 모델 · 참조 카운팅

파이썬의 모든 것은 객체입니다. 그 객체가 어떻게 관리되는지 봅니다.

모든 객체가 가진 것

PyObject (C 구조체)
  ├ ob_refcnt   참조 카운트  ★ 0 이 되면 즉시 해제
  └ ob_type     타입 포인터

즉 파이썬 변수는 "값"이 아니라 "객체를 가리키는 이름표"입니다.
  a = [1, 2, 3]
  b = a            # 같은 객체를 가리키는 이름표가 하나 더
  b.append(4)      # a 도 바뀝니다 (🐍 Python 탭 p08)
import sys

x = [1, 2, 3]
sys.getrefcount(x)          # 2 (변수 + getrefcount 인자)

# 객체 크기
sys.getsizeof([])           # 56 bytes
sys.getsizeof({})           # 64
sys.getsizeof(0)            # 28  ★ 정수 하나가 28바이트

# ★ 그래서 파이썬은 메모리를 많이 씁니다
#   1,000만 개의 정수를 리스트에 담으면 400MB+
#   → numpy 배열이면 80MB (🔢 NumPy 탭)
참조 카운팅의 장단점 — 장점: 참조가 0 이 되는 즉시 해제되어 메모리 예측이 쉽습니다. 단점: 모든 객체에 카운터를 두는 비용, 순환 참조를 못 잡습니다(z03), 그리고 카운터 갱신 때문에 GIL 이 필요해졌습니다(z10).

__slots__ — 메모리를 줄이는 법

# 일반 클래스는 인스턴스마다 __dict__ 를 가집니다
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

# ★ __slots__ 를 쓰면 dict 없이 고정 슬롯만
class SlotPoint:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

sys.getsizeof(Point(1,2).__dict__)   # 104 bytes (dict 만)
# 100만 개 생성 시
#   Point      → 약 180MB
#   SlotPoint  → 약  56MB   ★ 3배 차이

# 제약: 동적 속성 추가 불가, 다중 상속 시 주의
p = SlotPoint(1, 2)
p.z = 3          # AttributeError
# dataclass 와 조합 (Python 3.10+)
from dataclasses import dataclass

@dataclass(slots=True, frozen=True)
class Point:
    x: float
    y: float
# ★ slots=True 로 메모리 절약 + frozen=True 로 불변 + 해시 가능
언제 쓰나 — 같은 객체를 수십만 개 이상 만들 때만 의미가 있습니다. 수백 개 만드는 클래스에 __slots__ 를 붙이는 것은 복잡도만 늘리는 일입니다. 대량 데이터라면 애초에 numpy·pandas·Polars 를 쓰는 편이 낫습니다.
DEEP 03

메모리 관리 · GC

참조 카운팅이 못 잡는 것을 세대별 GC 가 정리합니다.

파이썬의 메모리 해제는 대부분 GC 가 아니라 참조 카운팅이 즉시 처리합니다. GC 는 순환 참조만 뒤처리합니다.

순환 참조 — 참조 카운팅의 구멍

class Node:
    def __init__(self):
        self.parent = None
        self.children = []

parent = Node()
child = Node()
parent.children.append(child)
child.parent = parent            # ★ 서로를 가리킴

del parent, child
# 참조 카운트가 0 이 되지 않습니다 → 메모리에 남음
# → 세대별 GC 가 나중에 수거합니다

import gc
gc.collect()                     # 수동 수거
print(gc.get_stats())            # 세대별 통계
세대별 GC (generational)
  0세대  새 객체 — 자주 검사 (임계치 700)
  1세대  0세대에서 살아남은 것
  2세대  오래 산 것 — 드물게 검사

이유: "대부분의 객체는 금방 죽는다"는 경험칙
      (자바·V8 의 GC 와 같은 원리)
순환 참조를 만드는 흔한 코드 — 부모↔자식 양방향 참조, 콜백에 self 를 담은 클로저, __del__ 이 있는 객체의 순환(옛 버전에서는 아예 수거 불가였습니다). weakref 로 한쪽을 약한 참조로 바꾸면 순환이 끊깁니다.

weakref — 참조를 붙잡지 않는 참조

import weakref

class Node:
    def __init__(self):
        self.children = []
        self._parent = None

    @property
    def parent(self):
        return self._parent() if self._parent else None

    @parent.setter
    def parent(self, node):
        self._parent = weakref.ref(node) if node else None
        # ★ 부모를 약한 참조로 → 순환이 생기지 않습니다

# 캐시에 쓸 때 (값이 다른 데서 안 쓰이면 자동으로 사라짐)
cache = weakref.WeakValueDictionary()
cache["key"] = obj

# 객체가 사라질 때 알림
weakref.finalize(obj, lambda: print("정리됨"))
# GC 튜닝 — 대량 객체를 만드는 배치에서 효과가 있습니다
import gc

gc.disable()                     # ★ 순환 참조가 없다고 확신할 때만
try:
    build_millions_of_objects()
finally:
    gc.enable()
    gc.collect()

# 임계치 조정 (기본 700, 10, 10)
gc.set_threshold(2000, 20, 20)   # GC 를 덜 자주 → CPU 절약, 메모리 더 씀

# 디버깅 — 수거되지 않는 객체 추적
gc.set_debug(gc.DEBUG_LEAK)
print(gc.garbage)                # 수거 불가 객체 목록
실무에서 GC 를 끄는 경우 — Instagram 은 웹 워커에서 GC 를 끄고 요청 처리 후 프로세스를 재활용해 메모리·CPU 를 크게 아꼈습니다. 다만 메모리 사용량을 반드시 모니터링해야 하는 고급 기법입니다.

DEEP 05

디스크립터 프로토콜

@property·ORM 필드·__slots__ 가 전부 이것으로 만들어집니다.

동작 원리

# __get__ · __set__ · __delete__ 중 하나라도 있으면 디스크립터
class Validated:
    def __set_name__(self, owner, name):     # ★ 3.6+ 자동 호출
        self.name = f"_{name}"

    def __get__(self, obj, objtype=None):
        if obj is None: return self          # 클래스에서 접근
        return getattr(obj, self.name)

    def __set__(self, obj, value):
        if not isinstance(value, (int, float)):
            raise TypeError(f"{self.name} 은 숫자여야 합니다")
        if value < 0:
            raise ValueError(f"{self.name} 은 음수일 수 없습니다")
        setattr(obj, self.name, value)

class Product:
    price = Validated()
    stock = Validated()

    def __init__(self, price, stock):
        self.price = price        # ★ __set__ 이 호출됩니다
        self.stock = stock

p = Product(1000, 5)
p.price = -1                      # ValueError
속성 조회 순서 — ① 데이터 디스크립터(__set__ 있음) → ② 인스턴스 __dict__ → ③ 비데이터 디스크립터·클래스 속성 → ④ __getattr__. @property 가 인스턴스 속성보다 우선인 이유가 이것입니다.

실무에서 만나는 디스크립터

# ① @property — 가장 익숙한 디스크립터

class Proxy:

메타클래스 · 클래스 생성 가로채기

“클래스를 만드는 클래스”. 프레임워크가 마법을 부리는 자리입니다.

클래스도 객체입니다

class Foo: pass

type(Foo)              # <class 'type'>   ★ 클래스의 타입은 type
type(Foo())            # <class 'Foo'>

# type 으로 클래스를 동적으로 만들 수 있습니다
Bar = type("Bar", (object,), {"x": 1, "hello": lambda self: "hi"})
Bar().hello()          # "hi"

# 메타클래스 = type 을 상속해 "클래스 생성 과정"에 끼어드는 것
class RegistryMeta(type):
    registry = {}

    def __new__(mcls, name, bases, ns, **kwargs):
        cls = super().__new__(mcls, name, bases, ns)
        if bases:                              # 추상 베이스는 제외
            mcls.registry[ns.get("key", name)] = cls   # ★ 자동 등록
        return cls

class Handler(metaclass=RegistryMeta): pass

class OrderHandler(Handler): key = "order"
class UserHandler(Handler):  key = "user"

RegistryMeta.registry     # {'order': OrderHandler, 'user': UserHandler}
# ★ 플러그인 자동 등록 — 사람이 목록을 관리하지 않아도 됩니다

대부분은 메타클래스가 필요 없습니다

# ★ __init_subclass__ 로 충분한 경우가 많습니다 (3.6+, 훨씬 간단)
class Handler:
    registry = {}

    def __init_subclass__(cls, key=None, **kwargs):
        super().__init_subclass__(**kwargs)
        if key:
            Handler.registry[key] = cls

class OrderHandler(Handler, key="order"): pass
# 메타클래스 없이 같은 일을 합니다

# ★ 클래스 데코레이터로도 됩니다
def register(key):
    def deco(cls):
        Handler.registry[key] = cls
        return cls
    return deco

@register("order")
class OrderHandler: pass
메타클래스 사용 기준 — 파이썬 코어 개발자 Tim Peters 의 말이 유명합니다: “메타클래스가 필요한지 고민하고 있다면 필요 없는 것”. 실제로 필요한 곳은 ORM·직렬화·DI 컨테이너 같은 프레임워크이고, 업무 코드에서는 __init_subclass__·데코레이터로 거의 다 됩니다.

실무에서 쓰이는 예

  • ABCMeta — 추상 클래스(abc.ABC)의 구현체
  • Django ORM — models.Model 이 필드를 수집·검증
  • Pydantic — 타입 힌트를 읽어 검증기를 생성
  • Enum — 멤버를 고유 객체로 만들고 재할당을 막음
읽을 줄만 알아도 충분합니다. 직접 만들 일은 드물지만, 라이브러리가 왜 그렇게 동작하는지 이해하려면 이 개념이 필요합니다.

제너레이터는 “멈출 수 있는 함수”

def gen():
    print("시작")
    x = yield 1          # ★ 여기서 멈추고 값을 반환, 나중에 값을 받음
    print("받은 값:", x)
    yield 2

g = gen()

def outer():

    return result

#   @asyncio.coroutine + yield from  →  async def + await

DEEP 10

GIL 심화 · free-threading

왜 GIL 이 생겼고, 파이썬 3.14 에서 무엇이 바뀌었는지.

GIL 이 막는 것은 파이썬 바이트코드의 동시 실행뿐입니다 — 기다리는 시간까지 막지는 않습니다.

GIL 이 존재하는 이유

참조 카운팅(z02) 때문입니다.

  a = [1,2,3]     ob_refcnt = 1
  b = a           ob_refcnt = 2   ← 이 증감이 원자적이어야 함

여러 스레드가 동시에 카운터를 건드리면
  → 카운트가 틀어짐 → 살아 있는 객체를 해제 → 크래시

해결책 두 가지
  ① 객체마다 락 → 락이 너무 많아 느려짐 (실제로 시도했다 실패)
  ② 인터프리터 전체에 락 하나 → ★ GIL (구현이 단순하고 단일 스레드가 빠름)

결과
  · 단일 스레드 성능이 좋습니다
  · C 확장을 만들기 쉽습니다 (numpy 가 흥한 이유)
  · 대신 멀티코어 CPU 를 못 씁니다
# GIL 은 5ms 마다 다른 스레드에 넘어갑니다
import sys
sys.getswitchinterval()          # 0.005
sys.setswitchinterval(0.001)     # 조정 가능 (거의 쓸 일 없음)

# ★ C 확장은 GIL 을 놓을 수 있습니다
#   numpy 의 큰 배열 연산, zlib 압축, hashlib,
#   그리고 모든 I/O 는 GIL 을 놓습니다
#   → 그래서 이런 작업은 "스레드로도" 병렬이 됩니다

free-threading (PEP 703) 3.14 공식

# GIL 없는 빌드
python3.14t                       # 't' = free-threaded
python -VV                        # "free-threading build" 표시 확인

# 3.13 에서는 실험적 별도 빌드였고,
# 3.14 부터 PEP 779 로 "공식 지원(officially supported)" 으로 승격됐습니다.
# (2025-10 릴리스 이후 stable 로 굴러가고 있습니다 — 더 이상 미래 이야기가 아닙니다)
기대 효과
  · 스레드로 CPU 작업 병렬화 가능 → 멀티프로세싱 불필요
  · 프로세스 간 데이터 복사(pickle) 비용 제거

현실적 제약 (2026-08 기준)
  · 단일 스레드 성능이 약 5~10% 느립니다
  · C 확장이 free-threading 대응을 해야 합니다
    numpy·pandas 등 주요 패키지는 대응 완료 —
    상위 네이티브 패키지 360개 중 183개가 free-threading 휠을 냅니다
    (나머지 절반은 아직이므로 의존성부터 확인하세요)
  · 기존 "GIL 덕분에 안전했던" 코드가 깨질 수 있습니다
    → 진짜 락이 필요해집니다

★ "곧 온다"가 아니라 이미 와 있습니다. 다만 도입 전에
  ① 내 의존성이 free-threading 휠을 내는지 ② 5~10% 손해를 감수할 만큼

# 워커마다 독립된 인터프리터 = 독립된 GIL → CPU 작업이 실제로 병렬화됩니다

#       인터프리터를 새로 만드는 시작 비용도 있습니다 — 짧은 작업에는 손해입니다

@njit(cache=True)                       # ★ 기계어로 컴파일
def monte_carlo(n: int) -> float:
    inside = 0
    for _ in range(n):
        x, y = random.random(), random.random()
        if x*x + y*y <= 1.0: inside += 1
    return 4.0 * inside / n

Protocol — 덕 타이핑에 타입을 붙이기

from typing import Protocol, runtime_checkable

class Storage(Protocol):
    def put(self, key: str, data: bytes) -> str: ...
    def get(self, key: str) -> bytes: ...

from typing import ParamSpec, TypeVar, Callable

from typing import Self, assert_never

불변 자료구조

    tags: tuple[str, ...] = ()       # ★ list 가 아니라 tuple (불변)

@dataclass
class Bad:

    # ValueError: mutable default <class 'list'> for field items is not allowed
    # ★ 클래스를 정의하는 순간 터집니다 (인스턴스를 만들기도 전에)

@dataclass
class Good:

가변 기본 인자는 파이썬의 대표적 함정입니다. def f(items=[]) 의 리스트는 함수 정의 시 한 번만 만들어져 모든 호출이 같은 리스트를 공유합니다. 기본값은 None 으로 두고 함수 안에서 만드세요. dataclass 와는 다른 얘기입니다 — dataclass 는 같은 실수를 정의 시점에 ValueError 로 막아 주지만, 일반 함수는 아무 경고 없이 조용히 공유됩니다.

result = pipe(raw,
              str.strip,

              lambda s: s.replace(" ", "-"))

# 타입별 분기 — if isinstance 사슬을 없앱니다
@singledispatch
def render(value) -> str:
    return str(value)

@render.register
def _(value: datetime) -> str:
    return value.strftime("%Y-%m-%d")

@render.register
def _(value: Decimal) -> str:
    return f"{value:,.0f}원"
# Result 패턴 — 예외 대신 값으로 (타입으로 강제)
from dataclasses import dataclass

@dataclass(frozen=True)
class Ok[T]:
    value: T
@dataclass(frozen=True)
class Err[E]:
    error: E

type Result[T, E] = Ok[T] | Err[E]

def parse_amount(s: str) -> Result[int, str]:
    try:
        return Ok(int(s))
    except ValueError:
        return Err(f"숫자가 아닙니다: {s}")

match parse_amount(user_input):
    case Ok(value):  process(value)
    case Err(msg):   show_error(msg)     # ★ 처리를 빼먹으면 타입 검사가 잡아 줍니다
순수 함수형을 강요하지 마세요. 파이썬은 reduce 보다 명시적인 for 문을 선호하는 언어입니다. 불변성과 순수 함수 두 가지만 지켜도 실무에서 얻을 이득의 대부분을 가져갑니다.

# 도메인 — 규칙이 여기 모입니다
@dataclass(frozen=True)
class Order:
    id: OrderId
    items: tuple[OrderItem, ...]
    status: OrderStatus = OrderStatus.PENDING

    def __post_init__(self):
        if not self.items:
            raise EmptyOrderError()

    def cancel(self) -> None:
        if self.status is OrderStatus.SHIPPED:
            raise CannotCancelError()      # ★ 규칙이 엔티티 안에
        object.__setattr__(self, "status", OrderStatus.CANCELLED)

    @property
    def total(self) -> int:
        return sum(i.price * i.qty for i in self.items)
