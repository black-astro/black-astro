WEB 01

웹은 어떻게 동작하나

요청 하나가 왕복하는 한 바퀴를 먼저 그려 두면 나머지가 전부 쉬워집니다.

웹 개발에서 배우는 거의 모든 것은 이 한 바퀴의 어느 지점을 손보는가로 정리됩니다.

엔터를 친 순간부터 화면이 뜰 때까지

https://api.example.com/users/7 을 열었다

① 주소 해석    api.example.com  →  DNS 조회  →  93.184.216.34
                  "이름"을 "IP 주소"로 바꾸는 전화번호부입니다
② 연결         그 IP 의 443 번 포트로 TCP 연결
                  http = 80,  https = 443 (생략하면 이 값)
③ 암호화 협상   TLS 핸드셰이크 — 이때부터 오가는 내용이 암호화됩니다
④ 요청 전송     GET /users/7 HTTP/1.1  +  헤더들
⑤ 서버 처리     라우팅 → 인증 → DB 조회 → JSON 만들기
⑥ 응답 수신     200 OK  +  헤더  +  본문(JSON)
⑦ 연결 재사용   keep-alive — 다음 요청은 ①~③ 을 건너뜁니다 ★

★ 서버 처리(⑤)는 보통 전체의 일부입니다.
  "느리다"는 신고의 상당수가 실은 ①·③ 이나 네트워크 구간입니다.
내 손으로 한 번 확인해 보세요. 브라우저에서 F12 → Network 탭을 열고 아무 사이트나 새로고침하면 요청 하나하나의 메서드 · 상태 코드 · 소요 시간이 그대로 보입니다. 이 탭에서 배우는 모든 용어가 그 화면에 이미 다 적혀 있습니다.

서버 쪽 한 줄 세우기

[브라우저 · 앱 · 다른 서버]      ← 클라이언트 (요청하는 쪽)
        │  HTTP
[로드밸런서 / Nginx]              TLS 종료 · 정적 파일 · 라우팅
        │
[내 파이썬 앱]  ★ 여기를 만듭니다   FastAPI · Django · Flask
        │
[DB · Redis · 외부 API]           데이터가 실제로 있는 곳

먼저 정리하고 갈 단어

용어뜻
클라이언트요청하는 쪽. 브라우저·모바일 앱·다른 서버
서버요청을 받아 응답을 만드는 계속 켜져 있는 프로그램
IP · 포트건물 주소(IP) + 몇 호(포트). 한 서버에서 8000·5432 처럼 포트로 프로그램을 구분합니다
HTTP클라이언트와 서버가 쓰는 대화 규칙. 글자로 된 약속일 뿐입니다
무상태(stateless)서버는 지난 요청을 기억하지 않습니다. 그래서 요청마다 “나 누구다”를 다시 말해야 합니다 (w08)
API사람이 보는 화면이 아니라 프로그램이 쓰라고 만든 창구. 보통 JSON 을 주고받습니다
“무상태”가 이 탭의 숨은 주인공입니다. 서버가 아무것도 기억하지 않기 때문에 로그인(w08~w10) 이 필요하고, 그래서 서버를 몇 대로 늘려도 됩니다. 확장이 쉬운 이유가 여기서 나옵니다 — 이야기가 ⚡ 대규모 트래픽 탭으로 이어집니다.
WEB 02

HTTP 메서드와 상태 코드

외울 것은 많지 않습니다. 자주 쓰는 것부터 정확히 쓰면 됩니다.

메서드 — “무엇을 하려는지”를 동사로

메서드하는 일 본문멱등성예
GET조회. 아무것도 바꾸지 않습니다 없음✅ 있음GET /users/7
POST생성. 서버가 새 자원을 만듭니다 있음❌ 없음POST /users
PUT전체 교체. 보낸 것으로 통째로 덮어씁니다 있음✅ 있음PUT /users/7
PATCH일부 수정. 보낸 필드만 바꿉니다 있음△ 설계 나름PATCH /users/7
DELETE삭제 보통 없음✅ 있음DELETE /users/7
멱등성(idempotent) = 같은 요청을 10번 보내도 결과가 1번과 같다. 네트워크가 끊겨 재시도할 때 안전한지를 가르는 성질입니다. POST /orders 를 두 번 보내면 주문이 두 건 생깁니다 — 그래서 결제·주문에는 별도의 장치가 필요합니다(⚡ 대규모 트래픽 k07).
❌ 메서드를 동사 대신 URL 로
GET  /getUser?id=7
POST /deleteUser?id=7
GET  /updateUserName?id=7&name=김
POST /user/7/delete

→ GET 으로 데이터를 지우면
  브라우저·프록시가 "안전하다"고 믿고
  미리 당겨 오다가 실제로 삭제됩니다 ★
✅ 동사는 메서드, URL 은 명사
GET    /users/7
DELETE /users/7
PATCH  /users/7
POST   /users

→ URL 만 봐도 "무엇"인지,
  메서드만 봐도 "무슨 일"인지
  즉시 읽힙니다

상태 코드 — 세 자리 숫자의 첫 자리

2xx  성공        내가 시킨 대로 됐다
3xx  리다이렉트   다른 데로 가라
4xx  ★ 클라이언트 잘못   보낸 쪽이 고쳐야 한다
5xx  ★ 서버 잘못         서버가 고쳐야 한다

첫 자리 4 와 5 를 나누는 기준이 가장 중요합니다.
"누가 고쳐야 하는가" — 이게 4xx / 5xx 의 전부입니다.
코드이름언제 쓰나
200OK조회·수정 성공. 본문에 결과
201Created생성 성공. Location 헤더에 새 자원 주소
204No Content성공했고 돌려줄 본문이 없음. 삭제에 흔함
301 / 308Moved Permanently주소가 영구히 바뀜. 브라우저가 캐시합니다
302 / 307Found임시 이동
304Not Modified안 바뀌었으니 캐시 쓰라는 뜻

4xx · 5xx — 실무에서 자주 틀리는 것

코드이름언제 쓰나
400Bad Request형식이 틀림. 필수 필드 누락·타입 오류
401Unauthorized“너 누구야” — 토큰이 없거나 만료 (w10)
403Forbidden“누군지는 알겠는데 권한 없어”
404Not Found그 자원이 없음
405Method Not AllowedURL 은 맞는데 메서드가 틀림
409Conflict이미 있는 이메일·중복 신청 등 상태 충돌
422Unprocessable Entity형식은 맞는데 값이 규칙 위반. FastAPI 의 검증 실패 기본값
429Too Many Requests속도 제한에 걸림
500Internal Server Error서버 코드가 터짐. 버그입니다
502 / 504Bad Gateway / Timeout앞단은 살았는데 뒤가 죽었거나 느림
503Service Unavailable일시적으로 못 받음. 점검·과부하
401 과 403 을 바꿔 쓰는 실수가 가장 흔합니다. 401 = 인증(누구인가), 403 = 인가(할 수 있는가). 클라이언트는 401 을 받으면 로그인 화면으로 보내고, 403 을 받으면 “권한이 없습니다”를 띄웁니다 — 동작이 완전히 다릅니다.
200 에 {"success": false} 를 담지 마세요. 모니터링·로드밸런서·클라이언트 라이브러리가 전부 상태 코드로 성공/실패를 판단합니다. 200 으로 실패를 감추면 장애가 지표에 안 잡힙니다.
상태 코드는 장식이 아니라 상대가 다음에 무엇을 할지 정하는 신호입니다.
WEB 03

요청 · 응답 해부

HTTP 메시지는 사실 그냥 글자입니다. 한 번 뜯어보면 신비함이 사라집니다.

요청은 이렇게 생겼습니다

POST /api/orders?draft=true HTTP/1.1     ← ① 시작 줄
Host: api.example.com                    ← ② 헤더 (여기부터)
Content-Type: application/json
Content-Length: 46
Authorization: Bearer eyJhbGciOi...
Accept: application/json
User-Agent: Mozilla/5.0 ...
                                         ← ③ 빈 줄 (헤더 끝 표시)
{"product_id": 7, "qty": 2}              ← ④ 본문(body)

① 메서드 + 경로 + 쿼리스트링 + 버전
② 부가 정보. "내용물 설명서"라고 보면 정확합니다
③ 이 빈 줄 하나가 헤더와 본문을 가릅니다
④ 실제 데이터. GET 에는 보통 없습니다

쿼리스트링 — ? 뒤에 붙는 것

/products?category=book&page=2&sort=price&q=%ED%8C%8C%EC%9D%B4%EC%8D%AC
          └─ key=value 를 & 로 이어 붙입니다

· 전부 "문자열"입니다 — page=2 도 서버에는 "2" 로 옵니다
· 한글·공백·특수문자는 %XX 로 인코딩됩니다 (URL 인코딩)
· ★ 주소창·로그·브라우저 기록에 그대로 남습니다
  → 비밀번호·토큰을 쿼리스트링에 넣으면 절대 안 됩니다

용도: 필터 · 정렬 · 페이지 번호 처럼 "조회 조건"
헤더 이름은 대소문자를 가리지 않습니다. Content-Type 과 content-type 은 같습니다. 직접 비교하는 코드를 쓸 땐 소문자로 맞춰 비교하세요 — 프록시를 거치며 표기가 바뀝니다.

응답과 Content-Type

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/orders/1042
Cache-Control: no-store
Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Lax

{"id": 1042, "status": "PENDING"}
Content-Type본문 형태
application/jsonAPI 의 기본. {"a": 1}
application/x-www-form-urlencodeda=1&b=2. HTML <form> 기본값 · OAuth2 로그인 폼
multipart/form-data파일 업로드. 여러 조각으로 나눠 보냄
text/html브라우저가 그리는 화면 (Django 템플릿 등)
text/plain그냥 글자
text/event-stream서버가 계속 흘려보냄 (SSE · 스트리밍 응답)

자주 쓰는 헤더

헤더의미
Authorization인증 정보. Bearer <토큰> (w10)
Accept클라이언트가 받고 싶은 형식
Content-Type지금 보내는 본문의 형식
Cache-Control얼마나 캐시해도 되는가
Set-Cookie / Cookie세션 방식의 뼈대 (w08)
X-Request-Id요청 추적용 식별자. 로그를 이어 붙일 때 필수
# 직접 눈으로 보기 — curl -v 는 헤더를 전부 보여 줍니다
curl -v https://httpbin.org/get

# JSON 을 POST 로 보내기
curl -X POST https://httpbin.org/post \
  -H "Content-Type: application/json" \
  -d '{"name":"김현우","qty":2}'

# 상태 코드만 확인
curl -o /dev/null -s -w "%{http_code}\n" https://example.com
Content-Type 을 안 맞추면 400·422 가 납니다. “JSON 을 보냈는데 서버가 못 알아듣는다”의 90% 는 헤더를 빠뜨렸거나 form 으로 보낸 경우입니다. 보낸 것과 선언한 것이 같은지부터 확인하세요.

그런데 HTTP/1.1 옆의 숫자 — 2 와 3 은 무엇이 다른가

HTTP/1.1        연결 하나에 요청 하나씩, 앞의 응답이 와야 다음을 보냅니다
                → 브라우저가 도메인당 6개쯤 연결을 열어 억지로 우회
                → 헤더(쿠키·User-Agent…)가 요청마다 평문으로 통째로 반복

HTTP/2  (2015)  ★ 연결 하나에서 스트림 여러 개를 동시에 (멀티플렉싱)
                ★ HPACK 헤더 압축 — 반복되는 헤더를 표로 줄임
                · 서버 푸시는 사실상 폐기되었습니다
                남은 문제: TCP 레벨 HOL 블로킹 —
                  패킷 하나가 유실되면 무관한 스트림까지 전부 멈춥니다

HTTP/3  (2022, RFC 9114)   ★ QUIC over UDP
                ★ 스트림이 서로 독립 → TCP HOL 블로킹이 사라짐
                ★ TLS 가 전송 계층에 통합 → 핸드셰이크 1-RTT (재접속은 0-RTT)
                ★ 모바일에서 IP 가 바뀌어도 연결 유지 (connection migration)

메시지의 의미(메서드·상태 코드·헤더)는 셋 다 같습니다.
바뀐 것은 "그것을 선으로 어떻게 실어 나르는가" 뿐입니다.
앱 서버가 직접 할 일은 거의 없습니다. CDN · Nginx · ALB 같은 앞단이 브라우저와 2/3 로 이야기하고, uvicorn 은 그 뒤에서 HTTP/1.1 로 받습니다 (uvicorn 자체는 HTTP/2 를 지원하지 않습니다). “HTTP/3 를 켜라”는 요구는 대개 인프라 설정이지 코드 변경이 아닙니다.

REST API 설계

URL 은 자원(명사), 동작은 메서드. 이 한 줄이 규칙의 90%입니다.

URL 짓는 규칙

① 명사 · 복수형으로
   /users        /orders        /products
   ✗ /user  ✗ /getUsers  ✗ /userList

② 계층은 슬래시로 — "누구의 무엇"
   /users/7/orders          7번 사용자의 주문 목록
   /users/7/orders/1042     그중 1042번 주문
   ★ 2단계까지만. 3단계를 넘으면 읽기 어려워집니다

③ 조회 조건은 쿼리스트링으로
   /orders?status=PAID&from=2026-01-01&page=2&size=20

④ 소문자 · 하이픈
   /order-items      ✗ /orderItems   ✗ /order_items

⑤ 버전은 앞에
   /api/v1/users     깨지는 변경이 생기면 v2 를 새로 냅니다

⑥ 끝에 슬래시를 붙일지 말지 — ★ 하나로 통일
   /users 와 /users/ 를 섞으면 리다이렉트가 끼어듭니다
요청의미
GET /orders목록 조회 (필터·페이징은 쿼리로)
POST /orders새 주문 생성 → 201 + Location
GET /orders/1042단건 조회 → 없으면 404
PATCH /orders/1042일부 수정
DELETE /orders/1042삭제 → 204

code 는 기계가, message 는 사람이 읽습니다. 클라이언트가 메시지 문자열로 분기하기 시작하면 문구 한 글자만 고쳐도 앱이 깨집니다. 분기는 반드시 code 로 하게 만드세요.
REST 로 억지로 욱여넣지 마세요. “로그인”·“결제 취소”·“이메일 재발송” 같은 행위는 자원으로 표현하기 어렵습니다. POST /auth/login, POST /orders/1042/cancel 처럼 동작을 하위 경로로 두는 것이 실무의 관행입니다 — 팀 안에서 일관되기만 하면 됩니다.
일관성이 목적입니다 — 다음 API 주소를 짐작할 수 있으면 잘 설계된 것입니다.

인증 ① — 세션 vs JWT

서버는 지난 요청을 기억하지 않습니다. 그래서 매번 “나 누구다”가 필요합니다.

둘의 차이는 보안 강도가 아니라 상태를 어디에 둘 것인가입니다 — 서버에 두면 회수가 쉽고, 클라이언트에 두면 확장이 쉽습니다.

세션 — 서버가 기억한다

① 로그인 성공
   서버: 임의의 문자열(세션 ID) 생성
         저장소에 {abc123: user_id=7} 기록
   응답: Set-Cookie: session=abc123; HttpOnly; Secure

② 이후 모든 요청
   브라우저가 쿠키를 ★ 자동으로 ★ 붙여 보냄
   서버: abc123 을 저장소에서 찾아 → user_id=7 확인

③ 로그아웃
   저장소에서 abc123 삭제 → ★ 즉시 무효화

특징
  · 서버에 상태가 있습니다 (그래서 "세션 저장소"가 필요)
  · 서버가 2대면 저장소를 공유해야 함 → 보통 Redis
  · 쿠키 = 브라우저 자동 전송 → CSRF 방어가 별도로 필요 (w11)
쿠키 옵션의미
HttpOnly자바스크립트가 못 읽음 → XSS 로 탈취 불가 ★
SecureHTTPS 에서만 전송
SameSite=Lax다른 사이트에서 온 요청엔 안 붙음 → CSRF 완화
SameSite=Strict외부 사이트에서 온 요청엔 아예 안 실림 — CSRF 로는 가장 강하지만 메일·검색 결과 링크로 들어오면 로그아웃된 것처럼 보입니다
SameSite=None; Secure크로스 사이트로 보내겠다는 선언. ★ Secure 를 같이 안 주면 브라우저가 쿠키를 버립니다
__Host- prefix__Host-session 처럼 이름 앞에 붙이면 브라우저가 Secure + Path=/ + Domain 없음을 강제합니다. 서브도메인이 쿠키를 덮어쓰는 공격(cookie tossing)을 가장 싸게 막는 방법 ★
Max-Age / Expires유효 기간. 빼면 세션 쿠키가 되어 브라우저를 닫을 때 사라집니다
Domain / Path어느 주소에 붙일지
브라우저만 상대한다면 세션이 더 안전하고 더 단순합니다. HttpOnly 쿠키는 자바스크립트가 읽을 수 없어 토큰을 localStorage 에 두는 방식보다 탈취에 강합니다. “요즘은 JWT”라는 말만 듣고 고르지 마세요.

JWT — 토큰 자체가 신분증

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI3IiwiZXhwIjoxNzY... . 4pQ8v...
└──── 헤더 ────┘   └──────── 페이로드 ────────┘  └ 서명 ┘
      알고리즘            내용(sub·exp·역할)      위조 검사용

★ 페이로드는 암호화가 아니라 Base64 인코딩입니다.
  누구나 디코드해서 읽을 수 있습니다 → 비밀을 담으면 안 됩니다.
  서명은 "내용이 바뀌지 않았음"만 보장합니다.

① 로그인 → 서버가 토큰 발급 (서버는 아무것도 저장 안 함)
② 요청마다  Authorization: Bearer <토큰>   ← ★ 직접 붙여야 함
③ 서버는 서명만 검증 → 통과하면 sub 에서 user_id 를 꺼냄
④ 로그아웃? ★ 서버가 모르므로 만료 전까지 유효합니다
기준세션 + 쿠키JWT
서버 저장소필요 (Redis 등)불필요
즉시 로그아웃✅ 쉬움❌ 어려움 (블랙리스트 필요)
서버 여러 대저장소 공유 필요✅ 그냥 됨
모바일 앱 · 서버 간쿠키가 불편✅ 자연스러움
XSS 위험낮음(HttpOnly)높음(JS 가 읽을 수 있으면)
CSRF 위험있음 → SameSite 필요낮음(자동 전송 아님)
권한 변경 반영즉시만료까지 지연 ★

무엇을 고를까

  • 웹만 · 사내 서비스 → 세션 + HttpOnly 쿠키. 가장 단순하고 안전합니다
  • 모바일 앱 · 외부 API 를 함께 → JWT
  • MSA — 여러 서비스가 각자 검증 → JWT(공개키 방식 RS256)
  • 둘 다 필요하면 → 웹은 쿠키, 앱은 토큰 으로 나눠도 됩니다
JWT 의 최대 약점은 “취소할 수 없다”입니다. 탈퇴·강제 로그아웃·권한 회수가 만료 전까지 반영되지 않습니다. 그래서 실무에서는 액세스 토큰을 짧게(15~30분) 두고 리프레시 토큰은 서버에 저장합니다 — 결국 반쯤 세션이 됩니다(w10).
WEB 09

인증 ② — 비밀번호 저장

여기서 실수하면 서비스가 아니라 회사가 위험해집니다.

절대 하면 안 되는 것

# ❌ ① 평문 저장 — 설명이 필요 없습니다
user.password = "mypassword123"

# ❌ ② 양방향 암호화 — 키가 새면 전부 복호화됩니다
user.password = aes_encrypt(pw, KEY)

# ❌ ③ MD5 · SHA-1 · SHA-256 단독
#      ★ 이들은 "빠르라고" 만든 함수입니다
#      GPU 로 초당 수십억 번 시도 → 무차별 대입에 무력
user.password = hashlib.sha256(pw.encode()).hexdigest()

# ❌ ④ 소금(salt) 없음
#      같은 비밀번호 → 같은 해시 → 레인보우 테이블 한 방
#      "1234 를 쓴 사람 전부"가 한 번에 뚫립니다

# ❌ ⑤ 비밀번호를 로그에 남기기
logger.info("login attempt: %s / %s", email, password)   # ★ 사고

# ❌ ⑥ 로그인 실패 사유를 자세히
#      "없는 이메일입니다" → 가입 여부를 알려 주는 것
#      → "이메일 또는 비밀번호가 올바르지 않습니다" 로 통일
“해시했으니 안전하다”가 아닙니다. 중요한 건 느린 해시인가입니다. 비밀번호 해시는 일부러 느리게 설계된 알고리즘 (bcrypt · argon2 · scrypt · PBKDF2)만 써야 합니다.
알고리즘평가비고
Argon2id✅ 1순위현재 권장 표준. 메모리도 많이 쓰게 해 GPU 에 강함
bcrypt✅ 안전오래 검증됨. 입력 72바이트 제한에 주의
scrypt✅ 안전표준 라이브러리 hashlib.scrypt 로도 가능
PBKDF2△ 허용Django 기본값. 반복 횟수를 크게
SHA-256 · MD5❌ 금지너무 빠릅니다

WEB 10

인증 ③ — JWT 로그인 전 과정

발급 → 검증 → 갱신. 그대로 복사해 쓸 수 있는 최소 구현입니다.

접근 토큰을 짧게 두는 이유는 하나입니다 — 탈취돼도 오래 못 쓰게 하려고. 대신 갱신 토큰은 반드시 서버가 회수할 수 있어야 합니다.

전체 흐름

[가입]   POST /auth/signup   비밀번호 → Argon2 해시로 저장 (w09)

[로그인] POST /auth/login    email + password
           └→ 200  { access_token(30분), token_type: "bearer" }
              + Set-Cookie: refresh_token=...; HttpOnly; Secure  ★

[사용]   GET /users/me       Authorization: Bearer <access>
           └→ 서명·만료 검증 → sub 에서 user_id

[만료]   401 을 받으면
         POST /auth/refresh  (쿠키의 refresh_token 사용)
           └→ 새 access_token + ★ 새 refresh_token (회전)

[로그아웃] POST /auth/logout  저장된 refresh_token 삭제
           ★ access_token 은 만료까지 살아 있습니다 — 그래서 짧게 둡니다

# app/security.py
import uuid
from datetime import datetime, timedelta, timezone
import jwt                                   # PyJWT
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    jwt_secret: str                          # ★ 32자 이상 · .env 로 관리
    access_ttl_min: int = 30
    refresh_ttl_days: int = 14
    model_config = {"env_file": ".env"}

settings = Settings()
ALGO = "HS256"

def _now() -> datetime:
    return datetime.now(timezone.utc)        # ★ 항상 UTC

def create_access_token(user_id: int, role: str = "user") -> str:
    payload = {
        "sub": str(user_id),                 # ★ sub 는 문자열이어야 합니다
        "role": role,
        "type": "access",
        "iat": _now(),
        "exp": _now() + timedelta(minutes=settings.access_ttl_min),
    }
    return jwt.encode(payload, settings.jwt_secret, algorithm=ALGO)

def create_refresh_token(user_id: int) -> tuple[str, str]:
    jti = str(uuid.uuid4())                  # ★ 토큰 고유 id (회수용)
    payload = {
        "sub": str(user_id), "type": "refresh", "jti": jti,
        "iat": _now(),
        "exp": _now() + timedelta(days=settings.refresh_ttl_days),
    }
    return jwt.encode(payload, settings.jwt_secret, algorithm=ALGO), jti

from typing import Annotated
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")

CRED_ERR = HTTPException(
    status.HTTP_401_UNAUTHORIZED,
    detail="인증이 필요합니다",
    headers={"WWW-Authenticate": "Bearer"},
)

async def get_current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
) -> User:
    try:
        payload = jwt.decode(token, settings.jwt_secret, algorithms=[ALGO])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "토큰이 만료되었습니다")
    except jwt.InvalidTokenError:            # ★ 서명 위조·형식 오류
        raise CRED_ERR

    if payload.get("type") != "access":      # ★ 리프레시 토큰으로 API 호출 차단
        raise CRED_ERR

    user = await repo.get(int(payload["sub"]))
    if user is None or not user.is_active:
        raise CRED_ERR
    return user

@router.post("/refresh")
async def refresh(response: Response,
                  refresh_token: Annotated[str | None, Cookie()] = None):
    if not refresh_token:
        raise CRED_ERR
    try:
        p = jwt.decode(refresh_token, settings.jwt_secret, algorithms=[ALGO])
    except jwt.InvalidTokenError:
        raise CRED_ERR
    if p.get("type") != "refresh":
        raise CRED_ERR

    uid, jti = int(p["sub"]), p["jti"]
    # ★ 저장소에 없으면 이미 쓰였거나 회수된 토큰입니다
    if not await redis.delete(f"rt:{uid}:{jti}"):
        await revoke_all(uid)                                  # 재사용 감지 → 전부 무효화
        raise CRED_ERR

    new_refresh, new_jti = create_refresh_token(uid)           # ★ 회전(rotation)
    await redis.setex(f"rt:{uid}:{new_jti}", 60 * 60 * 24 * 14, "1")
    response.set_cookie(
        "refresh_token", new_refresh,
        httponly=True, secure=True, samesite="lax",
        max_age=60 * 60 * 24 * 14, path="/auth",   # ★ 로그인 때와 똑같이
    )
    return {"access_token": create_access_token(uid), "token_type": "bearer"}

async def revoke_all(user_id: int) -> None:
    # ★ KEYS 가 아니라 SCAN — 블로킹 없이 조금씩 훑습니다
    keys = [k async for k in redis.scan_iter(match=f"rt:{user_id}:*", count=100)]
    if keys:                                   # ★ 빈 리스트면 delete() 인자가 0개 → 에러
        await redis.delete(*keys)

@router.post("/logout", status_code=204)
async def logout(user: CurrentUser, response: Response):
    await revoke_all(user.id)
    response.delete_cookie("refresh_token", path="/auth")

KEYS 는 운영 DB 를 멈춥니다. Redis 는 단일 스레드라 KEYS 하나가 전체 키를 훑는 동안 다른 모든 명령이 대기합니다 — SCAN(scan_iter)을 쓰세요.
체크리스트 — 하나라도 빠지면 구멍입니다. ① algorithms=["HS256"] 를 반드시 명시 (안 하면 alg: none 공격에 노출) ② jwt_secret 은 코드에 넣지 말고 환경변수로 ③ 액세스 토큰은 짧게, 리프레시는 회전 ④ 페이로드에 개인정보를 넣지 마세요 — 누구나 읽습니다 ⑤ type 을 확인해 토큰 종류를 섞어 쓰지 못하게
액세스 토큰을 localStorage 에 두지 마세요. XSS 하나로 전부 털립니다. 메모리(변수)에 보관하고 새로고침 때는 /auth/refresh 로 다시 받는 방식이 현재의 표준 절충안입니다.

CORS — 브라우저가 왜 막는가

Access to fetch at 'http://localhost:8000/api/users'
from origin 'http://localhost:5173' has been blocked by CORS policy

무슨 일인가
  브라우저에는 "동일 출처 정책(Same-Origin Policy)"이 있습니다.
  출처(origin) = 프로토콜 + 도메인 + 포트  ★ 셋 중 하나만 달라도 다른 출처

    http://localhost:5173   ←→  http://localhost:8000   포트 다름 → 다른 출처
    https://a.com           ←→  http://a.com            프로토콜 다름 → 다른 출처

왜 막는가
  막지 않으면, 내가 evil.com 에 접속한 순간
  그 페이지의 스크립트가 내 쿠키를 달고 bank.com 에 요청을 보낼 수 있습니다.

★ 서버가 막는 게 아닙니다. 요청은 서버에 도착했고 응답도 왔습니다.
  브라우저가 "허용 헤더가 없다"며 JS 에게 안 넘겨준 것뿐입니다.
  그래서 curl · Postman 에서는 잘 됩니다 — 이것이 가장 헷갈리는 지점입니다.
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(

    allow_credentials=True,         # 쿠키를 주고받을 때

allow_origins=["*"] 와 allow_credentials=True 는 함께 못 씁니다. 브라우저가 거부합니다 — 그렇게 되면 아무 사이트나 내 쿠키로 요청할 수 있으니까요. 운영에서 * 를 쓰는 것은 공개 읽기 전용 API 가 아니라면 피하세요.
preflight(사전 요청) — PUT·DELETE 나 커스텀 헤더가 있으면 브라우저가 본 요청 전에 OPTIONS 를 먼저 보냅니다. 네트워크 탭에 OPTIONS 가 보이는 건 정상입니다. 여기서 401 이 나면 인증 미들웨어가 OPTIONS 를 막고 있는 것입니다.

HTTPS — 왜 반드시인가

HTTP 로 보내면
  카페 와이파이의 누구나 비밀번호·토큰을 그대로 볼 수 있습니다.
  중간에서 내용을 바꿔치기할 수도 있습니다.

HTTPS = HTTP + TLS
  ① 암호화   내용이 안 보임
  ② 무결성   중간에서 못 바꿈
  ③ 신원확인 인증서로 "진짜 그 서버"임을 증명

실무 구성
  [브라우저] ──HTTPS──→ [Nginx / ALB]  ★ 여기서 TLS 종료
                              │  HTTP (내부망)
                        [FastAPI 앱]
  → 인증서는 앞단이 관리합니다. 앱 코드는 손댈 것이 없습니다.
  → 무료 인증서: Let's Encrypt (certbot 이 자동 갱신)

앱에서 챙길 것
  · 앞단이 TLS 를 끝냈으므로 앱은 X-Forwarded-Proto 로 원래 스킴을 봅니다
    uvicorn --proxy-headers --forwarded-allow-ips="*"
  · HTTP 로 온 요청은 301 로 HTTPS 에 넘깁니다 (보통 앞단이 처리)

    r.headers["X-Frame-Options"] = "DENY"
    r.headers["Referrer-Policy"] = "no-referrer"
    r.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"
    return r

from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()

class ConnectionManager:
    """접속 목록 관리 + 브로드캐스트 — 실무의 기본 뼈대"""
    def __init__(self):
        self.active: list[WebSocket] = []

    async def connect(self, ws: WebSocket):
        await ws.accept()                  # ★ 핸드셰이크 수락 (빠뜨리면 무한 대기)
        self.active.append(ws)

    def disconnect(self, ws: WebSocket):
        self.active.remove(ws)             # ★ 정리 안 하면 죽은 소켓에 계속 전송

    async def broadcast(self, data: dict):
        for ws in self.active:
            await ws.send_json(data)

manager = ConnectionManager()

@app.websocket("/ws/chat")
async def chat(ws: WebSocket):
    await manager.connect(ws)
    try:
        while True:
            msg = await ws.receive_json()          # 클라이언트 → 서버
            await manager.broadcast(msg)           # 전원에게 중계
    except WebSocketDisconnect:
        manager.disconnect(ws)
