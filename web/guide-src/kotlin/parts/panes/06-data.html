DATA 01

기술 고르기 지도

코틀린에서는 선택지가 자바보다 넓습니다. 도메인 복잡도와 쿼리 복잡도, 그리고 팀 경험이 결정 요소입니다.

비동기 스택(WebFlux)이라면 R2DBC가 추가 축입니다 — 이 표의 “쿼리 복잡” 쪽에 가깝습니다.
기술코틀린 궁합특징
JPA + Spring Data보통 (플러그인 필요)생태계 최강. 코틀린 함정이 많아 규칙이 필요

Kotlin JDSL매우 좋음코틀린 전용 JPA 동적 쿼리 — kapt 불필요
Exposed매우 좋음젯브레인스 제작 SQL DSL. 가볍고 명시적
jOOQ좋음DB 스키마에서 코드 생성 — SQL 을 타입 안전하게
Spring Data JDBC좋음지연 로딩 없는 단순 매핑 — 애그리거트 단위

MyBatis보통SQL 을 직접 쓰는 팀. 코틀린에서도 무리 없이 동작
가장 실용적인 조합 — 쓰기는 JPA(도메인 규칙·트랜잭션), 복잡한 조회는 jOOQ 또는 Kotlin JDSL. 둘을 억지로 하나로 통일하려다 JPQL 로 불가능한 쿼리를 억지로 만드는 것이 더 큰 비용입니다.
DATA 02

코틀린 엔티티 설계 — 함정 총정리

이 섹션 하나가 이 탭에서 가장 중요합니다. data class 로 엔티티를 만들면 지연 로딩·동등성·컬렉션 관리가 전부 어긋납니다.

흔히 쓰는 잘못된 엔티티
@Entity
data class Order(                      // ❌ data class
    @Id @GeneratedValue
    val id: Long = 0,                  // ❌ val — JPA 가 값을 넣지 못한다

    @ManyToOne(fetch = FetchType.LAZY)
    val user: User,                    // ❌ toString 이 프록시를 건드린다

    @OneToMany(mappedBy = "order", cascade = [CascadeType.ALL])
    val items: MutableList<OrderItem> = mutableListOf(),
)

// 무엇이 문제인가
// ① equals/hashCode 가 '모든 필드'로 만들어진다
//    → 지연 로딩 프록시를 강제로 초기화하고, 값이 바뀌면 Set 에서 사라진다
// ② toString() 이 연관 엔티티를 전부 찍는다 → 무한 재귀 · N+1 폭발
// ③ copy() 로 만든 객체는 같은 id 를 가진 '다른 엔티티'가 된다 (매우 위험)
// ④ val 은 Hibernate 가 리플렉션으로 채우긴 하지만 의도가 어긋난다
권장 형태
@Entity
@Table(name = "orders")
class Order(                            // 일반 class
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long = 0,                   // 식별자만 val (읽기 전용)

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    var user: User,

    @Enumerated(EnumType.STRING)        // ★ ORDINAL 금지
    var status: OrderStatus = OrderStatus.NEW,
) {
    @OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true)
    private val _items: MutableList<OrderItem> = mutableListOf()
    val items: List<OrderItem> get() = _items.toList()   // 밖에는 읽기 전용으로

    fun addItem(item: OrderItem) {
        check(status == OrderStatus.NEW) { "확정된 주문은 수정 불가" }
        _items += item
        item.order = this                                  // 양방향 동기화
    }

    // id 기반 동등성 (Hibernate 권장 형태)
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Order) return false
        return id != 0L && id == other.id
    }
    override fun hashCode(): Int = javaClass.hashCode()    // 상수 — 프록시에도 안전
    override fun toString(): String = "Order(id=$id, status=$status)"  // 연관 제외
}
함정이유와 해결
data class 사용equals/hashCode/copy 가 전부 문제 → 일반 class
모든 필드 valJPA 는 상태를 바꾼다 → 식별자만 val, 나머지 var
hashCode()를 id 로저장 전 id=0 → 저장 후 값이 바뀌어 Set 에서 사라진다 → 클래스 상수
기본 toString()연관을 전부 로딩 → id·기본 필드만 출력
클래스가 final지연 로딩 프록시 불가 → plugin.jpa/allopen이 열어 준다
기본 생성자 없음JPA 요구 → plugin.jpa(no-arg)
@Enumerated 기본값ORDINAL 은 순서가 바뀌면 데이터가 밀린다 → STRING
가변 컬렉션 노출밖에서 마음대로 추가 → private + 읽기 전용 getter
allopen 플러그인을 엔티티까지 확장하기 — 기본 설정은 @Entity도 열어 주지만, 직접 만든 애너테이션이나 추상 클래스를 쓴다면 build.gradle.kts에 추가하세요. 
allOpen {
    annotation("jakarta.persistence.Entity")
    annotation("jakarta.persistence.MappedSuperclass")
    annotation("jakarta.persistence.Embeddable")
}
noArg {
    annotation("jakarta.persistence.Entity")
    invokeInitializers = true      // init 블록도 실행 (검증 로직이 있다면)
}
엔티티는 JPA 의 규칙을 따르는 객체입니다 — 값 객체와 다릅니다.
DATA 03

연관관계 매핑

연관관계는 “어느 쪽이 외래키를 갖는가”와 “언제 로딩할 것인가” 두 가지 결정입니다. 코틀린에서는 여기에 컬렉션 캡슐화가 더해집니다.

헷갈릴 때는 "DB 테이블에 외래 키가 어디 있나"만 보면 됩니다 — 거기가 주인입니다.
@Entity
class Order(
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long = 0,

    // 다대일 — 외래키를 가진 쪽(주인). 기본이 EAGER 이므로 반드시 LAZY 로!
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_id", nullable = false)
    var user: User,
) {
    // 일대다 — mappedBy 로 주인을 가리킨다 (여기는 거울)
    @OneToMany(mappedBy = "order", cascade = [CascadeType.ALL], orphanRemoval = true)
    private val _items: MutableList<OrderItem> = mutableListOf()
    val items: List<OrderItem> get() = _items

    // 일대일 — 주인 쪽에 외래키
    @OneToOne(fetch = FetchType.LAZY, cascade = [CascadeType.ALL])
    @JoinColumn(name = "delivery_id")
    var delivery: Delivery? = null

    // 값 타입 컬렉션 — 별도 엔티티가 필요 없는 값들
    @ElementCollection
    @CollectionTable(name = "order_tags", joinColumns = [JoinColumn(name = "order_id")])
    @Column(name = "tag")
    private val _tags: MutableSet<String> = mutableSetOf()
    val tags: Set<String> get() = _tags

    // 편의 메서드 — 양방향을 항상 함께 맞춘다
    fun addItem(item: OrderItem) {
        _items += item
        item.order = this
    }
    fun removeItem(item: OrderItem) {
        _items -= item
        item.order = null        // orphanRemoval 이 켜져 있으면 DELETE 된다
    }
}

@Entity
class OrderItem(
    @Id @GeneratedValue val id: Long = 0,
    var productId: Long,
    var quantity: Int,
    var price: Long,
) {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    var order: Order? = null

    fun subtotal(): Long = price * quantity
}

기본 규칙

  • 모든 연관은 LAZY — @ManyToOne·@OneToOne의 기본값이 EAGER 라 반드시 명시해야 합니다 (N+1 의 최대 원인)
  • 양방향은 꼭 필요할 때만 — 단방향으로 충분한 경우가 많습니다
  • 편의 메서드로 양쪽을 동기화 — 한쪽만 바꾸면 DB 와 메모리가 어긋납니다
  • cascade = ALL은 애그리거트 안에서만 — 주문→주문항목은 OK, 주문→사용자는 절대 안 됩니다
  • 컬렉션은 Set 보다 List가 실무에서 편하지만, 중복 방지가 필요하면 Set + 올바른 equals

코틀린 특유의 주의점

// ① nullable 연관은 타입에 ? 를 붙인다
@ManyToOne(fetch = FetchType.LAZY)
var coupon: Coupon? = null          // optional = true 와 짝을 맞춘다

// ② non-null 연관은 optional = false 로 DB 제약까지

var user: User                       // ? 없음

// ③ 지연 로딩 프록시를 == 로 비교하지 말 것
if (order.user.id == userId) { }     // 프록시가 초기화된다
if (order.user.id == userId) { }     // id 만 쓰면 초기화 없이도 가능(설정에 따라)

// ④ 컬렉션 초기화는 프로퍼티 선언에서

영속성 컨텍스트 · 더티 체킹

JPA 를 쓰면서 “왜 save()를 안 불렀는데 UPDATE 가 나가지?”를 겪습니다. 영속성 컨텍스트가 스냅숏을 들고 있다가 트랜잭션 끝에 비교하기 때문입니다.

이 메커니즘 덕분에 도메인 메서드로 상태를 바꾸는 설계가 자연스러워집니다.
@Service
@Transactional
class OrderService(private val repo: OrderRepository) {

    fun pay(id: Long, amount: Long) {
        val order = repo.findByIdOrNull(id) ?: throw NotFound(id)
        order.markPaid(amount)          // 도메인 메서드가 상태를 바꾼다
        // repo.save(order)  ← 필요 없다. 커밋 시점에 자동으로 UPDATE
    }

    // 읽기 전용 — 스냅숏을 안 만들어 메모리·성능 이득
    @Transactional(readOnly = true)
    fun get(id: Long): OrderResponse =
        repo.findByIdOrNull(id)?.toResponse() ?: throw NotFound(id)

    // 준영속 — 트랜잭션 밖에서 받은 객체는 merge 가 필요하다
    @Transactional
    fun update(detached: Order) {
        val managed = repo.findByIdOrNull(detached.id) ?: throw NotFound(detached.id)
        managed.applyFrom(detached)     // merge 보다 '필요한 필드만 옮기기'가 안전
    }
}

Spring Data 리포지터리

코틀린에서 Spring Data 를 쓸 때 알아야 할 것은 Optional 을 쓰지 않는다는 점과 nullable 반환 타입을 정확히 적는 것입니다.

기본 형태

interface OrderRepository : JpaRepository<Order, Long> {

    // 없을 수 있으면 ? 를 붙인다 — Optional 은 쓰지 않는다
    fun findByOrderNo(orderNo: String): Order?

    // 목록은 non-null (빈 리스트가 온다)
    fun findByUserIdOrderByCreatedAtDesc(userId: Long): List<Order>

    // 페이징
    fun findByStatus(status: OrderStatus, pageable: Pageable): Page<Order>

    // 존재 여부 · 개수
    fun existsByOrderNo(orderNo: String): Boolean
    fun countByUserIdAndStatus(userId: Long, status: OrderStatus): Long

    // 삭제 (반환은 삭제된 건수)
    fun deleteByCreatedAtBefore(t: LocalDateTime): Long

    // 스트리밍 — 대용량 처리 (트랜잭션 안에서 써야 한다)
    @QueryHints(QueryHint(name = HINT_FETCH_SIZE, value = "1000"))
    fun findAllByStatus(status: OrderStatus): Stream<Order>
}

DATA 06

쿼리 — JPQL · 프로젝션

엔티티를 통째로 가져오는 대신 필요한 컬럼만 뽑으면 성능이 크게 달라집니다. 코틀린에서는 data class 생성자 표현식이 특히 잘 맞습니다. 

interface OrderRepository : JpaRepository<Order, Long> {

    // JPQL — 엔티티 이름과 필드 이름을 쓴다 (테이블 이름이 아니다)
    @Query("select o from Order o where o.status = :status and o.totalAmount >= :min")
    fun search(status: OrderStatus, min: Long): List<Order>

    // DTO 프로젝션 — data class 생성자를 그대로 부른다
    @Query("""
        select new com.example.dto.OrderSummary(o.id, o.orderNo, u.name, o.totalAmount)
        from Order o join o.user u
        where o.createdAt >= :from
    """)
    fun summaries(from: LocalDateTime): List<OrderSummary>

    // 인터페이스 프로젝션 — 더 가볍다 (프록시가 만들어진다)
    @Query("select o.id as id, o.orderNo as orderNo from Order o where o.userId = :userId")
    fun findProjections(userId: Long): List<OrderIdAndNo>

    // 네이티브 쿼리 — DB 함수·힌트가 필요할 때
    @Query(
        value = "select * from orders where created_at >= :from and status = :status",
        nativeQuery = true,
    )
    fun findNative(from: LocalDateTime, status: String): List<Order>

    // 벌크 업데이트 — 영속성 컨텍스트를 우회하므로 주의
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("update Order o set o.status = :to where o.status = :from")
    fun bulkUpdateStatus(from: OrderStatus, to: OrderStatus): Int
}

data class OrderSummary(val id: Long, val orderNo: String, val userName: String, val total: Long)

interface OrderIdAndNo {
    val id: Long
    val orderNo: String
}

방식특징

벌크 연산의 함정

N+1 문제와 해결

JPA 성능 문제의 8할입니다. 목록 10건을 조회했는데 쿼리가 11번 나가는 현상이고, 해결책은 fetch join · EntityGraph · batch size 세 가지입니다.

일대다 컬렉션은 fetch join 을 하나만 쓸 수 있습니다 — 나머지는 batch size 로 해결합니다.
// ① fetch join — JPQL 에 명시
@Query("select o from Order o join fetch o.user where o.status = :status")
fun findWithUser(status: OrderStatus): List<Order>

// 컬렉션 fetch join 은 중복이 생기므로 distinct (Hibernate 6+ 는 자동)
@Query("select distinct o from Order o join fetch o.items where o.id in :ids")
fun findWithItems(ids: List<Long>): List<Order>

// ⚠️ 컬렉션 fetch join + 페이징은 위험하다
//    → Hibernate 가 전체를 메모리로 읽고 자바에서 자른다 (경고 로그가 뜬다)

// ② @EntityGraph — 쿼리를 안 고치고 로딩 계획만 지정
@EntityGraph(attributePaths = ["user", "delivery"])
fun findByStatus(status: OrderStatus): List<Order>

// ③ batch size — 전역 설정이 가장 실용적
// application.yml
// spring.jpa.properties.hibernate.default_batch_fetch_size: 100
//   → 지연 로딩이 필요할 때 IN (…) 으로 100개씩 묶어서 가져온다

실무 조합 — 이렇게 씁니다

  1. 기본값으로 default_batch_fetch_size: 100을 켜 둔다 — 대부분의 N+1 이 2번 쿼리로 줄어듭니다
  2. ~ToOne 연관은 fetch join 으로 함께 조회
  3. 컬렉션은 batch size 에 맡기거나, 페이징이 필요하면 id 만 페이징 → 그 id 로 상세 조회 2단계로
  4. 조회 전용은 DTO 프로젝션으로 아예 연관을 안 탄다

발견하는 법

spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
        generate_statistics: true      # 쿼리 수를 로그로
logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace   # 바인딩 값까지
테스트로 잡는 것이 가장 확실합니다. Statistics.queryExecutionCount를 검증하는 테스트를 두면 누군가 연관을 추가해 N+1 을 만들었을 때 CI 에서 실패합니다.

동적 쿼리 작성

@Repository
class OrderQueryRepository(private val query: JPAQueryFactory) {

    fun search(cond: OrderSearchCondition, pageable: Pageable): Page<OrderSummary> {
        val o = QOrder.order
        val u = QUser.user

        val where = BooleanBuilder().apply {
            cond.status?.let { and(o.status.eq(it)) }
            cond.userId?.let { and(o.user.id.eq(it)) }
            cond.minAmount?.let { and(o.totalAmount.goe(it)) }
            cond.keyword?.takeIf { it.isNotBlank() }?.let { and(u.name.contains(it)) }
        }

        val content = query
            .select(QOrderSummary(o.id, o.orderNo, u.name, o.totalAmount))
            .from(o).join(o.user, u)
            .where(where)
            .orderBy(o.createdAt.desc())
            .offset(pageable.offset)
            .limit(pageable.pageSize.toLong())
            .fetch()

        val total = query.select(o.count()).from(o).where(where).fetchOne() ?: 0L
        return PageImpl(content, pageable, total)
    }
}
코틀린에서 QueryDSL 을 더 편하게 — BooleanBuilder 대신 nullable 을 그대로 넘기는 방식이 코틀린과 잘 맞습니다. where(...)에 null을 넘기면 그 조건은 무시되므로, cond.status?.let { o.status.eq(it) } 처럼 만든 값을 그대로 나열하면 됩니다.

동적 쿼리 ② — Kotlin JDSL

라인의 오픈소스로, 코드 생성 없이 JPA 동적 쿼리를 타입 안전하게 씁니다. kapt 가 필요 없다는 점만으로도 코틀린 프로젝트에서 큰 장점입니다.

의존성 — implementation("com.linecorp.kotlin-jdsl:jpql-dsl:3.5.5") · implementation("com.linecorp.kotlin-jdsl:jpql-render:3.5.5") · 스프링 연동은 spring-data-jpa-support
@Repository
class OrderQueryRepository(private val em: EntityManager) {

    private val context = JpqlRenderContext()

    fun search(cond: OrderSearchCondition, pageable: Pageable): List<OrderSummary> {
        val query = jpql {
            selectNew<OrderSummary>(
                path(Order::id),
                path(Order::orderNo),
                path(Order::user).path(User::name),
                path(Order::totalAmount),
            ).from(
                entity(Order::class),
                join(Order::user),
            ).whereAnd(
                cond.status?.let { path(Order::status).eq(it) },        // null 이면 조건 제외
                cond.minAmount?.let { path(Order::totalAmount).ge(it) },
                cond.keyword?.takeIf { it.isNotBlank() }
                    ?.let { path(Order::user).path(User::name).like("%$it%") },
            ).orderBy(path(Order::createdAt).desc())
        }

        return em.createQuery(query, context)
            .setFirstResult(pageable.offset.toInt())
            .setMaxResults(pageable.pageSize)
            .resultList
    }
}

jOOQ — 스키마에서 코드를 만든다

실제 DB 스키마를 읽어 테이블·컬럼 타입을 코드로 생성합니다. 컬럼 이름 오타가 컴파일 에러가 되고, 복잡한 SQL 을 그대로 표현할 수 있습니다. 

// 복잡한 통계 쿼리 — JPQL 로는 표현하기 어려운 것들이 자연스럽다
@Repository
class SalesQueryRepository(private val dsl: DSLContext) {

    fun dailySales(from: LocalDate, to: LocalDate): List<DailySales> =
        dsl.select(
                ORDERS.CREATED_AT.cast(SQLDataType.LOCALDATE).`as`("day"),
                DSL.count().`as`("cnt"),
                DSL.sum(ORDERS.TOTAL_AMOUNT).`as`("total"),
                DSL.avg(ORDERS.TOTAL_AMOUNT).`as`("avg"),
            )
            .from(ORDERS)
            .where(ORDERS.STATUS.eq("PAID"))
            .and(ORDERS.CREATED_AT.between(from.atStartOfDay(), to.atTime(23, 59, 59)))
            .groupBy(DSL.field("day"))
            .orderBy(DSL.field("day").desc())
            .fetchInto(DailySales::class.java)

    // 윈도 함수 — 사용자별 최근 주문 3건
    fun recentPerUser(): List<OrderRow> {
        val rn = DSL.rowNumber().over()
            .partitionBy(ORDERS.USER_ID)
            .orderBy(ORDERS.CREATED_AT.desc()).`as`("rn")

        val t = dsl.select(ORDERS.asterisk(), rn).from(ORDERS).asTable("t")
        return dsl.selectFrom(t).where(t.field("rn", Int::class.java)!!.le(3))
            .fetchInto(OrderRow::class.java)
    }

    // CTE · UPSERT · 벌크 — SQL 이 되는 것은 대부분 된다
    fun upsertStock(productId: Long, delta: Int) =
        dsl.insertInto(STOCKS).columns(STOCKS.PRODUCT_ID, STOCKS.QTY)
            .values(productId, delta)
            .onConflict(STOCKS.PRODUCT_ID)
            .doUpdate().set(STOCKS.QTY, STOCKS.QTY.plus(delta))
            .execute()
}

트랜잭션 심화

전파(propagation)·격리 수준·락은 동시성 사고가 났을 때 비로소 필요해지는 지식입니다. 코틀린 코드로 실제 상황과 함께 정리합니다.

"감사 로그만은 남기고 싶다"가 REQUIRES_NEW 의 거의 유일한 정답 용례입니다 — 나머지는 기본값으로 두세요.
전파 속성동작 · 쓰는 곳
REQUIRED(기본)있으면 참여, 없으면 시작. 대부분 이걸로 충분
REQUIRES_NEW항상 새 트랜잭션 — 감사 로그·이력처럼 본 작업이 실패해도 남겨야 할 때
NESTED세이브포인트 — 부분 롤백 (JPA 에서는 제약이 있다)
SUPPORTS · NOT_SUPPORTED있으면 참여 / 트랜잭션 없이 실행
MANDATORY · NEVER반드시 있어야 / 있으면 예외 — 실수 방지용
@Service
class OrderService(
    private val repo: OrderRepository,
    private val auditService: AuditService,
) {
    @Transactional
    fun place(cmd: PlaceOrderCommand): Order {
        val order = repo.save(Order(cmd))
        auditService.log("ORDER_PLACED", order.id)   // 별도 빈이라 프록시를 탄다
        return order
    }
}

@Service
class AuditService(private val auditRepo: AuditRepository) {
    // 본 트랜잭션이 롤백돼도 감사 로그는 남긴다
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    fun log(action: String, targetId: Long) {
        auditRepo.save(AuditLog(action, targetId))
    }
}

    withContext(Dispatchers.IO) { tx.execute { doDecrease(id, qty) } }
}
격리 수준은 함부로 올리지 마세요. SERIALIZABLE은 정확하지만 처리량이 급감하고 데드락이 늘어납니다. 대부분의 문제는 낙관적 락 + 재시도나 원자적 UPDATE(update ... set stock = stock - :qty where stock >= :qty)로 더 싸게 해결됩니다.
DATA 13

대용량 · 성능

수십만 건을 다루기 시작하면 JPA 를 쓰는 방식 자체를 바꿔야 합니다. 영속성 컨텍스트가 도움이 아니라 부담이 되는 구간입니다.

기준은 단순합니다 — 수천 건까지는 JPA, 수만 건부터는 배치, 수백만 건은 DB 도구.

배치 INSERT — 한 건씩 넣지 않기

spring:
  jpa:
    properties:
      hibernate:
        jdbc.batch_size: 500          # 묶어서 보낸다
        order_inserts: true
        order_updates: true
  datasource:
    url: jdbc:postgresql://.../app?reWriteBatchedInserts=true   # PG 는 이 옵션까지
@Transactional
fun bulkInsert(rows: List<OrderRow>) {
    rows.chunked(500).forEach { chunk ->
        chunk.forEach { em.persist(it.toEntity()) }
        em.flush()
        em.clear()          // ★ 1차 캐시를 비우지 않으면 메모리가 계속 찬다
    }
}

// ⚠️ @GeneratedValue(strategy = IDENTITY) 면 배치가 동작하지 않는다
//    (INSERT 마다 키를 받아야 하므로) → SEQUENCE + allocationSize 사용

대량 조회 — 페이징의 함정

// ❌ OFFSET 페이징 — 뒤로 갈수록 느려진다 (100만 번째 페이지는 재앙)
repo.findAll(PageRequest.of(10_000, 20))

// ✅ 커서(키셋) 페이징 — 항상 같은 속도
@Query("""
    select o from Order o
    where (:lastId is null or o.id < :lastId)
    order by o.id desc
""")
fun findPage(lastId: Long?, pageable: Pageable): List<Order>

// ✅ 전체 스캔이 필요하면 스트리밍 + clear
@Transactional(readOnly = true)
fun exportAll(sink: (OrderRow) -> Unit) {
    repo.streamAll().use { stream ->
        stream.forEachIndexed { i, o ->
            sink(o.toRow())
            if (i % 1000 == 0) em.clear()
        }
    }
}
증상원인 · 대응
목록 API 가 느리다N+1 → batch size · fetch join · DTO 프로젝션
메모리가 계속 오른다1차 캐시 누적 → clear() · 읽기 전용 트랜잭션
INSERT 가 느리다배치 미적용 · IDENTITY 전략 → SEQUENCE + batch_size
뒤쪽 페이지가 느리다OFFSET → 커서 페이징
가끔 타임아웃락 경합 · 인덱스 부재 → 실행 계획 확인
커넥션 풀 고갈open-in-view · 트랜잭션 안 외부 호출 → 경계 재설계
업데이트가 전 컬럼을 쓴다Hibernate 기본 동작 → @DynamicUpdate(신중히)
대량 배치는 JPA 를 쓰지 않는 선택도 좋습니다. JdbcTemplate.batchUpdate나 jOOQ 로 순수 SQL을 쓰면 수십 배 빠른 경우가 많습니다. 도메인 규칙이 필요 없는 데이터 이관·집계라면 굳이 엔티티를 만들 이유가 없습니다.
DATA 14

스키마 관리 — Flyway

ddl-auto: update는 운영에서 절대 쓰면 안 됩니다. 스키마는 버전이 붙은 SQL 파일로 관리하고, 애플리케이션이 뜰 때 적용합니다.

기본 설정

spring:
  jpa:
    hibernate:
      ddl-auto: validate       # 운영: validate 또는 none
    open-in-view: false
  flyway:
    enabled: true
    baseline-on-migrate: true  # 기존 DB 에 처음 도입할 때
    locations: classpath:db/migration
src/main/resources/db/migration/
  V1__init.sql
  V2__add_order_status_index.sql
  V3__create_settlement_table.sql
  R__view_daily_sales.sql        # R = 반복 실행 (뷰·함수)

규칙
· 이미 적용된 파일은 절대 수정하지 않는다 (체크섬이 어긋난다)
· 되돌릴 SQL 도 함께 준비 (Flyway 커뮤니티 판에는 undo 가 없다)
· 파괴적 변경은 2단계로: 새 컬럼 추가 → 코드 배포 → 옛 컬럼 제거

무중단 배포와 스키마

작업안전한 순서
컬럼 추가nullable 로 추가 → 코드 배포 → 백필 → NOT NULL
컬럼 삭제코드에서 사용 제거 → 배포 → 다음 배포에서 DROP
컬럼 이름 변경새 컬럼 추가 → 양쪽 쓰기 → 백필 → 옛 컬럼 제거
인덱스 추가PG 는 CREATE INDEX CONCURRENTLY
대용량 백필배치로 나눠서 (한 트랜잭션에 몰지 않기)
ddl-auto: update가 위험한 이유 — 컬럼 삭제·타입 변경을 감지하지 못하고, 예측할 수 없는 순서로 DDL 을 날립니다. 로컬 개발에서만 쓰고, 그마저도 Testcontainers + Flyway 로 통일하는 편이 낫습니다.
DATA 15

데이터 계층 테스트

H2 로 테스트하고 운영은 PostgreSQL 이면, 테스트가 통과해도 운영에서 깨집니다. Testcontainers 로 같은 DB를 쓰는 것이 지금의 표준입니다. 

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)  // H2 로 바꾸지 않기
@Testcontainers
class OrderRepositoryTest(
    @Autowired val repo: OrderRepository,
    @Autowired val em: TestEntityManager,
) {
    companion object {
        @Container @ServiceConnection
        val postgres = PostgreSQLContainer("postgres:16-alpine")
    }

    @Test
    fun `주문번호로 조회한다`() {
        val saved = em.persistAndFlush(order(orderNo = "ORD-1"))
        em.clear()                                   // 1차 캐시를 비워야 진짜 쿼리가 나간다

        val found = repo.findByOrderNo("ORD-1")
        assertEquals(saved.id, found?.id)
    }

    @Test
    fun `N+1 이 발생하지 않는다`() {
        repeat(10) { em.persist(order(orderNo = "ORD-$it")) }
        em.flush(); em.clear()

        val stats = em.entityManager.entityManagerFactory
            .unwrap(SessionFactory::class.java).statistics
        stats.clear()

        repo.findAllWithUser().forEach { it.user.name }      // 연관 접근

        assertEquals(1, stats.prepareStatementCount)         // 쿼리 1번이어야 한다
    }
}

fun order(
    orderNo: String = "ORD-${UUID.randomUUID().toString().take(6)}",
    user: User = user(),
    status: OrderStatus = OrderStatus.NEW,
    items: List<OrderItem> = listOf(orderItem()),

    .apply { items.forEach(::addItem) }

  • 식별자만 val, 나머지 var
  • equals는 id 기반, hashCode는 클래스 상수
  • toString에 연관 필드 제외
  • 모든 연관은 LAZY 명시
  • @Enumerated(STRING) 고정
  • 컬렉션은 private + 읽기 전용 getter
  • open-in-view: false · ddl-auto: validate
  • default_batch_fetch_size: 100 기본 적용
  • 조회 전용 API 는 DTO 프로젝션
