코틀린 환경의 세 갈래 — 무엇을 만들지부터 정합니다

파이썬은 “파이썬을 깐다”가 끝이고, 자바는 “JDK 를 깐다”가 끝입니다. 코틀린은 어디로 컴파일할지에 따라 깔 것이 달라집니다. 서버는 JDK 하나면 되지만, 안드로이드는 SDK 수 기가가 더 필요하고, iOS 까지 노리는 KMP 는 맥과 Xcode가 사실상 필수입니다. 여기서 자기 갈래를 정하고 나면 뒤 섹션에서 읽을 것과 건너뛸 것이 갈립니다.

코틀린 컴파일러는 따로 안 깔아도 됩니다 🟢 기초

왜 “코틀린 설치”가 검색해도 안 나오나

코틀린 컴파일러는 Gradle 의존성 하나일 뿐입니다. build.gradle.kts 에 kotlin("jvm") version "2.2.0" 이라고 적으면 Gradle 이 그 버전의 컴파일러를 인터넷에서 받아 캐시합니다. 그래서 팀원 열 명이 각자 다른 코틀린을 깔아 두어도 빌드 결과는 똑같습니다.

파이썬의 python 이나 Node 의 node 처럼 PATH 에 있어야 하는 실행 파일이 아닙니다. kotlinc 를 깔면 편한 순간이 있긴 한데(st03), 없어도 개발에 아무 지장이 없습니다.

그래서 실제 설치 순서

① JDK 21 (또는 25)          ← 반드시 손으로   st02
② IntelliJ IDEA             ← 손으로          st04
   (안드로이드면 Android Studio)                st06
③ Gradle                    ← 안 깝니다.
   프로젝트의 ./gradlew 가 알아서 받습니다      st05
④ Kotlin 컴파일러           ← 안 깝니다.
   Gradle 이 의존성으로 받습니다
⑤ kotlinc CLI (선택)        ← 스크립트·실험용   st03
⑥ Android SDK (안드로이드)  ← Studio 안에서    st06
⑦ Xcode (iOS)              ← 맥 앱스토어      st07
손으로 깔아야 하는 것은 사실상 두 개(JDK · IDE)입니다. “설치가 복잡하다”는 인상은 대개 안드로이드 SDK 때문인데, 그것도 Android Studio 첫 실행 마법사가 대신 해 줍니다.

SETUP 02

JDK 설치 — Temurin 21 / 25 LTS 와 JAVA_HOME

코틀린 코드가 도는 자리는 JVM 입니다. 그래서 코틀린을 시작하는 첫 단계는 JDK 설치입니다. 여기서 JAVA_HOME 과 PATH 두 개만 제대로 잡아 두면 뒤에 나올 Gradle · IDE 문제의 절반이 사라집니다. 반대로 이 둘이 어긋나면 “Gradle 이 자꾸 옛날 자바로 빌드한다” 같은 이해 못 할 증상이 계속 따라다닙니다.

JAVA_HOME 은 bin 의 부모입니다. ...\jdk-21\bin 까지 넣으면 도구들이 JDK 를 못 찾습니다.

# C:\Program Files\Common Files\Oracle\Java\javapath\java.exe 가

한 단계 더 — 여러 JDK 를 오가며 쓰기 🟡 중급

macOS · Linux — SDKMAN!

# 설치 (curl 한 줄)
curl -s "https://get.sdkman.io" | bash
source "$HOME/.sdkman/bin/sdkman-init.sh"

# 받을 수 있는 JDK 목록
sdk list java | head -40

# 설치 — 이름 규칙: <버전>-<벤더>
sdk install java 21.0.5-tem     # Temurin 21
sdk install java 25-tem         # Temurin 25

# 지금 셸에서만 바꾸기 (프로젝트마다 다를 때)
sdk use java 21.0.5-tem

# 기본값으로 고정
sdk default java 21.0.5-tem

# 폴더에 .sdkmanrc 를 두면 cd 할 때 자동 전환됩니다
echo "java=21.0.5-tem" > .sdkmanrc
sdk env install && sdk env

# 보너스 — 코틀린 CLI 도 여기서 (st03)
sdk install kotlin
sdk install gradle
SDKMAN! 이 하는 일은 심볼릭 링크 하나를 옮기는 것뿐입니다. ~/.sdkman/candidates/java/current 가 실제 JDK 폴더를 가리키고, JAVA_HOME 은 그 링크를 가리킵니다. 마법이 아니라서 고장 나도 원인이 보입니다.

윈도우 — 굳이 도구를 안 써도 됩니다

function j25 {

사실 코틀린 개발에서는 이게 거의 필요 없습니다. Gradle 의 jvmToolchain(21)(st05)이 프로젝트별 JDK 를 빌드 파일 안에서 정해 주고, 없으면 자동으로 받아 오기 때문입니다. 손으로 전환하는 일은 터미널에서 java -jar 로 직접 돌릴 때 정도입니다.
안드로이드 개발자를 위한 예외 — Android Studio 는 자체 내장 JDK(JBR, JetBrains Runtime)를 들고 다닙니다. 그래서 PC 에 JDK 가 없어도 안드로이드 빌드는 됩니다. 다만 터미널에서 ./gradlew 를 직접 칠 때는 시스템 JDK 가 쓰이므로, Studio 에서는 되는데 터미널에서만 실패하는 현상이 생깁니다 — 이때는 File → Settings → Build Tools → Gradle → Gradle JDK 에서 Studio 가 쓰는 JDK 를 확인해 시스템 JAVA_HOME 과 맞추면 됩니다(st11).
정리 — adoptium.net 에서 Temurin 21(또는 25) .msi, 마법사에서 JAVA_HOME · Add to PATH 두 체크박스, 설치 후 터미널 새로 열기. 확인은 java -version · javac -version · echo $env:JAVA_HOME · where.exe java 네 줄. JAVA_HOME 은 언제나 bin 의 부모 폴더입니다.
SETUP 03

코틀린 컴파일러 · kotlinc — 없어도 되지만 알면 좋은 것

실무 프로젝트에서 kotlinc 를 직접 치는 일은 거의 없습니다 — Gradle 과 IDE 가 대신 부릅니다. 그런데도 이 섹션이 있는 이유는 두 가지입니다. 첫째, “코틀린이 어떻게 실행되는가”를 한 번 눈으로 보면 뒤에 나오는 Gradle 설정이 전부 이해되기 때문이고, 둘째 REPL 과 .kts 스크립트는 프로젝트를 만들지 않고 문법을 실험할 때 정말 편하기 때문입니다.

Gradle 은 결국 경로 ①을 자동으로 해 주는 것입니다 — 원리는 이 한 줄이 전부입니다.

kotlinc 옵션 — 알아 둘 만한 것만 🟢 기초

자주 쓰는 옵션

옵션뜻
-d <경로>결과물 위치. .jar 로 끝나면 jar, 폴더면 .class 들
-include-runtime코틀린 표준 라이브러리를 jar 안에 넣습니다. 이게 없으면 실행 시 NoClassDefFoundError ★
-cp / -classpath쓰는 라이브러리 jar 경로
-jvm-target 21어느 JVM 버전용 바이트코드를 뽑을지
-script.kts 파일을 스크립트로 실행
-Werror경고를 에러로 — CI 에서 씁니다
-verbose무슨 파일을 읽는지 전부 출력(문제 추적용)
-version버전 확인. K2 여부도 여기서
-include-runtime 을 기억하세요. 자바와 달리 코틀린은 kotlin-stdlib 가 런타임에 반드시 필요합니다. String?.let · listOf 같은 것이 전부 거기 있습니다.

.main.kts — 의존성까지 쓰는 단일 파일 스크립트

#!/usr/bin/env kotlin
// tidy.main.kts — 파일 이름이 반드시 .main.kts 여야 합니다

@file:DependsOn("com.squareup.okhttp3:okhttp:4.12.0")   // 의존성을 코드 안에서!

import okhttp3.OkHttpClient
import okhttp3.Request
import java.io.File

val target = File(args.getOrNull(0) ?: ".")     // args 가 바로 쓰입니다
println("정리할 폴더: ${target.absolutePath}")

target.walkTopDown()
    .filter { it.isFile && it.extension == "tmp" }
    .forEach { println("삭제 대상: ${it.name}") }

val client = OkHttpClient()
val res = client.newCall(Request.Builder().url("https://example.com").build()).execute()
println("응답 코드: ${res.code}")
kotlin tidy.main.kts ./build
# 첫 실행은 의존성을 받느라 느리고, 두 번째부터는 캐시됩니다

.kts 를 어디에 쓰나

쓰임설명
build.gradle.kts가장 많이 만나는 .kts. Gradle 이 이 파일을 스크립트로 컴파일해 실행합니다(st05)
운영 잡일 스크립트배포 전 점검 · 로그 파싱 — bash 보다 타입이 안전
단발성 실험라이브러리 API 를 한 번 눌러 볼 때. 프로젝트를 안 만들어도 됩니다
NotebookKotlin Kernel for Jupyter — 데이터 실험
테스트 픽스처테스트 데이터 생성 스크립트
.kts 는 느립니다 — 실행할 때마다 컴파일이 먼저 일어납니다. 수백 번 도는 자동화라면 차라리 jar 로 만들어 두는 편이 낫습니다. “가끔 손으로 부르는 잡일”에 어울립니다.
IntelliJ 에서 .kts 를 열면 자동완성이 됩니다 — @file:DependsOn 을 쓰면 IDE 가 그 라이브러리를 인덱싱해 줍니다. bash 스크립트에는 없는 경험이라, 팀 스크립트를 코틀린으로 옮기는 회사가 늘고 있습니다.

K2 모드 — 켜져 있는지 확인

K2 는 코틀린 2.0 부터 들어온 새 컴파일러 프론트엔드입니다. 타입 추론이 정확해지고 컴파일이 눈에 띄게 빨라졌습니다. Kotlin 2.x 를 쓰면 빌드는 자동으로 K2 이고, IDE 의 코드 분석기도 최신 IntelliJ 에서는 K2 모드가 기본입니다. 

확인 위치

    ▸ "Enable K2 mode" 체크 상태

증상으로 알아채기
  ▸ 큰 파일에서 자동완성이 확 빨라졌다   → K2 켜짐
  ▸ 빌드는 되는데 에디터만 빨간 줄       → 캐시 문제일 가능성
     File → Invalidate Caches → Invalidate and Restart
“빌드는 되는데 IDE 만 빨갛다”는 거의 항상 캐시입니다. 순서대로 시도하세요 — ① Gradle 창의 새로고침(⟳) → ② ./gradlew --stop → ③ Invalidate Caches and Restart. ①에서 90% 가 해결됩니다.
메모리를 늘려 두면 체감이 달라집니다 — 기본 힙이 부족하면 큰 프로젝트에서 인덱싱이 느리고 자동완성이 끊깁니다. Help → Change Memory Settings 에서 -Xmx 를 4096MB 이상으로 올리세요 (RAM 16GB 이상이면 6144MB). Toolbox 를 쓰면 톱니바퀴 → Settings 에서도 바꿀 수 있습니다. 안드로이드 프로젝트라면 여기에 Gradle 데몬 메모리도 따로 올려야 합니다(st10).

SETUP 05

Gradle Kotlin DSL — build.gradle.kts 완전 기초

코틀린 개발에서 가장 많이 헤매는 파일이 이것입니다. 문법은 코틀린인데 하는 일은 빌드 설정이라 “이게 왜 되는지” 감이 안 잡히기 때문입니다. 여기서는 ./gradlew build 를 치면 실제로 무슨 일이 일어나는지부터 보고, settings.gradle.kts · build.gradle.kts · libs.versions.toml 세 파일이 각각 무엇을 맡는지 나눠 설명합니다.

4단계(구성)와 6단계(실행)를 구분하는 것이 Gradle 을 이해하는 첫걸음입니다.

settings.gradle.kts — 프로젝트의 지도

// settings.gradle.kts — 빌드에서 가장 먼저 읽히는 파일
rootProject.name = "hello-kotlin"

// 플러그인을 어디서 받을지 (플러그인 전용 저장소 설정)
pluginManagement {
    repositories {
        gradlePluginPortal()
        mavenCentral()
        google()                 // 안드로이드 플러그인은 여기에
    }
}

// 라이브러리를 어디서 받을지 — 모듈마다 안 적고 여기 한 번에
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        mavenCentral()
        google()
    }
}

// 멀티모듈 — 폴더 이름을 적습니다
include(":app")
include(":core:domain")          // core/domain 폴더
include(":core:data")
FAIL_ON_PROJECT_REPOS 를 켜 두세요. 모듈마다 repositories { } 를 제각각 적는 것을 빌드가 막아 줍니다. 저장소가 흩어지면 “어떤 모듈만 사내 넥서스를 못 본다” 같은 문제가 생깁니다.

jvmToolchain — 가장 중요한 한 줄 🟢 기초

이 한 줄이 하는 일

kotlin {
    jvmToolchain(21)
}

// 위 한 줄이 아래 전부를 대신합니다
//   ▸ 코틀린 컴파일러가 21 용 바이트코드를 만든다
//   ▸ javac 도 21 로 컴파일한다
//   ▸ 테스트도 21 JVM 에서 돈다
//   ▸ 내 PC 에 21 이 없으면? Gradle 이 자동으로 받아 옵니다  ★

// 세밀하게 지정하고 싶으면
kotlin {
    jvmToolchain {
        languageVersion.set(JavaLanguageVersion.of(21))
        vendor.set(JvmVendorSpec.ADOPTIUM)     // Temurin 만 쓰겠다
    }
}
“내 PC 에 없으면 받아 온다”가 핵심입니다. 새 팀원이 JDK 17 만 깔고 들어와도 ./gradlew build 한 번이면 21 을 자동으로 내려받아 같은 결과를 냅니다. “나는 되는데 너는 안 되네”가 사라지는 지점입니다.

ANDROID_HOME 과 adb 🟢 기초

환경 변수 잡기

# ── Windows (시스템 환경 변수 편집 — st02 와 같은 화면) ──
# 새 시스템 변수
#   ANDROID_HOME = C:\Users\내이름\AppData\Local\Android\Sdk
# Path 에 두 줄 추가
#   %ANDROID_HOME%\platform-tools

정리 — developer.android.com/studio 에서 Studio 를 받고 첫 마법사에 맡기면 SDK 가 따라옵니다. 기억할 것은 SDK 폴더의 네 덩어리, PATH 에 넣는 platform-tools, local.properties 의 sdk.dir, 그리고 adb devices 가 모든 기기 문제의 출발점이라는 것입니다.

한글이 ??? 로 나오는 문제와 빌드가 느린 문제는 성격이 달라 보이지만, 둘 다 “Gradle 이 JVM 을 어떤 옵션으로 띄우는가” 한 파일에서 해결됩니다. 이 섹션은 gradle.properties 한 장을 통째로 읽고 각 줄이 무엇을 바꾸는지 설명합니다. 안드로이드 빌드가 유난히 느릴 때의 체크리스트도 함께 정리합니다.

# 데몬 힙. 안드로이드/멀티모듈이면 4g 이상, 서버 단일 모듈은 2g 로 충분

org.gradle.caching=true                  # 빌드 캐시

kotlin.incremental.useClasspathSnapshot=true

누가 누구를 제약하나

  • Gradle 이 JDK 를 제약합니다 — 오래된 Gradle 은 새 JDK 에서 아예 안 뜹니다

최후의 수단 — 단계별 초기화 🟡 중급

약한 것부터 강한 것 순서로

# 1단계 — 데몬만 (가장 자주 듣습니다)
./gradlew --stop

# 2단계 — 이 프로젝트의 빌드 산출물
./gradlew clean

# 3단계 — IDE 인덱스
#   File → Invalidate Caches... → [Invalidate and Restart]

# 4단계 — 이 프로젝트의 로컬 Gradle 상태
rm -rf .gradle build
#   윈도우: Remove-Item -Recurse -Force .gradle, build

# 5단계 — 의존성을 새로 받기
./gradlew build --refresh-dependencies

# 6단계 — 전역 캐시 (수 GB 를 다시 받습니다. 신중히)
rm -rf ~/.gradle/caches
#   래퍼 배포판까지 지우려면 ~/.gradle/wrapper/dists

# 7단계 — 코틀린/네이티브(KMP) 캐시
rm -rf ~/.konan

# 8단계 — 안드로이드 빌드 캐시
rm -rf ~/.android/build-cache
6단계부터는 정말 마지막에 하세요. 전역 캐시를 지우면 다음 빌드가 수십 분 걸립니다. 그리고 대부분의 문제는 1~3단계에서 끝납니다 — 순서를 건너뛰고 6단계부터 하는 것이 가장 흔한 시간 낭비입니다.

에러를 제대로 읽는 법

# Gradle 이 요약해 버린 진짜 예외를 보고 싶을 때
./gradlew build --stacktrace     # 스택 전체
./gradlew build --info           # 태스크별 상세
./gradlew build --debug          # 너무 많습니다 (최후)

# 실패한 태스크만 다시
./gradlew build --continue       # 실패해도 끝까지 돌려 전체 문제 파악

# 코틀린 컴파일러가 왜 실패했는지
./gradlew compileKotlin --info | grep -i "error\|warning"

# 안드로이드 — 어떤 병합 단계에서 깨졌는지
./gradlew assembleDebug --stacktrace 2>&1 | head -60
에러 메시지의 마지막 줄이 아니라 Caused by: 를 찾으세요. Gradle 은 예외를 여러 겹 감싸기 때문에 맨 위의 Execution failed for task ':app:compileDebugKotlin' 은 아무 정보가 없습니다. 아래로 내려가 가장 마지막 Caused by 가 진짜 원인입니다.
검색할 때는 버전을 빼고 검색하세요 — "Unsupported class file major version 69" kotlin gradle 보다 Unsupported class file major version gradle jdk 가 훨씬 좋은 결과를 줍니다. 버전 숫자는 내 상황에만 있는 값입니다.
새 PC 를 받았을 때의 30분 체크리스트 — ① java -version · javac -version 이 같은 버전인가 · ② echo $env:JAVA_HOME 이 bin 의 부모를 가리키는가 · ③ where.exe java 첫 줄이 그 JDK 인가 · ④ 프로젝트 경로에 한글·공백이 없는가 · ⑤ ./gradlew --version 이 정상 출력되는가 · ⑥ (안드로이드) adb devices 가 도는가 · ⑦ ./gradlew build 가 통과하는가. 이 일곱 줄이 전부 통과하면 환경 문제는 없습니다.
정리 — 진단은 “터미널에서도 실패하나” 로 시작합니다. 버전 에러는 major − 44 = 자바 버전 으로 읽고 jvmToolchain 으로 통일, 다운로드가 멈추면 프록시·인증서, 이상한 실패는 경로에 한글·공백, 나머지는 ./gradlew --stop → clean → Invalidate Caches 순서입니다. 그리고 언제나 마지막 Caused by 를 읽으세요.
