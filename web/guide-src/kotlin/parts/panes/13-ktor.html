Ktor 는 자바를 거치지 않고 코틀린만 보고 설계된 서버 프레임워크입니다. 모든 핸들러가 suspend 이고, 프레임워크가 기본으로 켜 두는 것이 하나도 없습니다. 그래서 기동이 0.3초, 힙이 50MB 대에서 시작하고, 켠 기능만 정확히 돕니다. 이 탭은 스프링 부트를 아는 독자를 가정하고 끝까지 스프링과 대조하면서 갑니다 — 라우팅 · 플러그인 파이프라인 · 직렬화 · 코루틴 동시성 · Exposed · 인증 · WebSocket · Koin · 테스트 · 관측 · 배포, 그리고 마지막에 짧은 URL 서비스 하나를 처음부터 끝까지 만듭니다. 이 탭을 마치면 Ktor 서비스를 혼자 설계해서 운영에 올릴 수 있게 됩니다.

KTOR 01

Ktor 는 무엇이고 왜 쓰나 — 스프링과 나란히

Ktor 를 "가벼운 스프링"으로 이해하면 계속 헤맵니다. 두 프레임워크는 철학이 반대입니다 — 스프링은 다 켜 두고 끄는 쪽, Ktor 는 다 꺼 두고 켜는 쪽입니다. 이 한 문장이 기동 시간부터 디버깅 방식까지 전부를 설명합니다.

Ktor 가 빠른 이유는 마법이 아니라 안 하는 일이 많기 때문입니다 — 그 대신 내가 해야 할 일이 늘어납니다.

Ktor 를 한 화면으로

// Main.kt — 이 파일 하나가 돌아가는 웹 서버 전부입니다
fun main() {
    embeddedServer(Netty, port = 8080) {
        install(ContentNegotiation) { json() }   // 켜야 JSON 이 됩니다

        routing {
            get("/hello") {                       // 이 람다는 suspend 입니다
                call.respond(mapOf("msg" to "안녕"))
            }
        }
    }.start(wait = true)
}
여기에 없는 것들을 보세요 — 애너테이션이 없고, 컴포넌트 스캔이 없고, @RestController 같은 클래스가 아예 없습니다. Ktor 의 라우트는 클래스가 아니라 함수 호출이라, IDE 에서 정의로 이동이 그대로 통합니다. 스프링에서 "이 URL 이 어느 메서드로 가지?"를 찾느라 헤매던 시간이 사라집니다.

현실의 대부분은 세 번째 질문에서 멈춥니다 — 그래도 나머지 한 줌을 위해 Ktor 를 알아 둘 값어치가 있습니다.

Ktor 가 실제로 잘 하는 자리

  • 게이트웨이 · BFF — 여러 내부 API 를 코루틴으로 동시에 호출해 합칩니다. Ktor 의 최적 서식지입니다.
  • KMP 백엔드 — commonMain 의 @Serializable DTO 를 서버와 iOS·안드로이드가 그대로 공유합니다.
  • 서버리스 · 짧은 수명 컨테이너 — 콜드 스타트가 과금이 되는 자리.
  • 사이드카 · 내부 툴 — 메트릭 수집기, 웹훅 수신기처럼 기능은 적고 개수는 많은 서비스.
  • 스트리밍 · 실시간 — WebSocket · SSE 가 코루틴 위에서 자연스럽습니다.
실무에서 가장 흔한 조합 — 핵심 도메인 서비스는 스프링 부트로 두고, 그 앞의 게이트웨이 한 대만 Ktor 로 두는 형태입니다. 전면 교체를 설득할 필요가 없어 도입이 쉽습니다.

기동 시간과 메모리 재기

# ① 기동 시간 — 로그의 "Responding at" 까지 걸린 시간을 열 번 재서 중앙값을 씁니다
for i in $(seq 1 10); do
  /usr/bin/time -f "%e" java -jar app-all.jar & PID=$!
  until curl -sf localhost:8080/healthz >/dev/null 2>&1; do sleep 0.01; done
  kill $PID
done

# ② 실제로 쓰는 메모리는 힙이 아니라 RSS 입니다 (컨테이너가 죽이는 기준)
ps -o rss= -p $PID          # KB 단위
cat /sys/fs/cgroup/memory.current    # 컨테이너 안에서라면 이쪽

# ③ 부하를 주면서 재기 — 기동 직후 숫자는 절반의 진실입니다
oha -z 60s -c 50 http://localhost:8080/api/links
#   또는  wrk -t4 -c50 -d60s http://localhost:8080/api/links
왜 직접 재야 하나 — 인터넷의 비교표는 스프링 쪽에 자동 설정이 얼마나 켜져 있었는지를 대부분 밝히지 않습니다. spring-boot-starter-web 하나만 넣은 앱과 시큐리티 · JPA · 액추에이터가 붙은 앱은 기동 시간이 두 배 차이납니다. 내 프로젝트의 의존성 목록으로 잰 숫자만 의사결정에 쓸 수 있습니다.

③ Gradle 수동

가장 흔한 첫 실패 — ktor-server-content-negotiation 만 넣고 ktor-serialization-kotlinx-json 을 빠뜨리면 install(ContentNegotiation) { json() } 의 json() 이 컴파일되지 않습니다. Ktor 는 "협상하는 기능"과 "JSON 으로 협상하는 구현"을 다른 아티팩트로 나눠 뒀습니다. 이 분리가 Ktor 의존성 전체의 규칙입니다 — 기능 하나에 아티팩트 하나, 구현 하나에 아티팩트 하나.
두 방식은 섞어 쓸 수 있습니다 — 운영은 EngineMain, 테스트는 embeddedServer 가 흔한 조합입니다.

① embeddedServer — 코드가 주인

// Application.kt
fun main() {
    embeddedServer(
        factory = Netty,
        port = System.getenv("PORT")?.toInt() ?: 8080,
        host = "0.0.0.0",
        module = Application::module,          // 함수 참조로 넘기면 재사용이 쉽습니다
    ).start(wait = true)
}

// 설정을 더 주려면 configure 블록을 씁니다
fun main() {
    embeddedServer(Netty, configure = {
        connectionGroupSize = 2
        workerGroupSize = 4
        callGroupSize = 8                      // 핸들러를 실행할 스레드 수
        shutdownGracePeriod = 3_000
        shutdownTimeout = 10_000
    }) { module() }.start(wait = true)
}

fun Application.module() {                     // ★ Application 의 확장 함수 = "모듈"
    configureSerialization()
    configureLogging()
    configureRouting()
}
Application.module() 이라는 이름 규칙 — Ktor 에서 "모듈"은 Application 의 확장 함수일 뿐입니다. 특별한 타입도, 애너테이션도 아닙니다. 그래서 여러 개로 쪼개서 조합할 수 있고, 테스트에서 일부만 켜서 돌릴 수 있습니다.

fun Application.configureRouting() = routing {

            }

            delete { call.respond(HttpStatusCode.NoContent) }
        }
    }

// routes/HealthRoutes.kt
fun Route.healthRoutes(db: Database) {
    get("/healthz") { call.respondText("OK") }               // 살아 있나 (liveness)
    get("/readyz") {                                          // 받을 준비가 됐나 (readiness)
        val ok = runCatching { db.ping() }.isSuccess
        if (ok) call.respondText("READY")
        else call.respond(HttpStatusCode.ServiceUnavailable, "DB")
    }
}

플러그인 파이프라인 — Ktor 의 심장

Ktor 를 진짜로 이해했는지는 파이프라인을 설명할 수 있는가로 갈립니다. 스프링의 필터 · 인터셉터 · AOP · @ControllerAdvice 가 하던 일을 Ktor 는 페이즈 다섯 개짜리 파이프라인 하나로 전부 처리합니다.

fun Application.configureDefaults(cfg: AppConfig) {

    install(DefaultHeaders) {
        header("X-Engine", "Ktor")
        // Server 헤더는 기본으로 붙습니다. 숨기려면 아래를 씁니다
        // header(HttpHeaders.Server, "")
    }

    install(ContentNegotiation) {
        json(Json {
            ignoreUnknownKeys = true     // ★ 모르는 필드가 와도 터지지 않게 (호환성)
            encodeDefaults = true        // 기본값도 응답에 실어 보냅니다
            explicitNulls = false        // null 필드는 아예 빼서 응답을 가볍게
            prettyPrint = cfg.isDev
        })
    }

    install(CORS) {
        cfg.allowedOrigins.forEach { allowHost(it, schemes = listOf("https")) }
        allowMethod(HttpMethod.Put); allowMethod(HttpMethod.Delete); allowMethod(HttpMethod.Patch)
        allowHeader(HttpHeaders.Authorization)
        allowHeader(HttpHeaders.ContentType)
        allowCredentials = true
        maxAgeInSeconds = 3600           // 프리플라이트 캐시 — 없으면 OPTIONS 가 두 배로 옵니다
    }

    install(Compression) {
        gzip  { priority = 1.0; minimumSize(1024) }
        deflate { priority = 0.9 }
        // 이미 압축된 것은 다시 압축하지 않습니다
        matchContentType(ContentType.Text.Any, ContentType.Application.Json)
    }

    install(CallLogging) {
        level = Level.INFO
        filter { it.request.path().startsWith("/api") }      // 헬스체크 로그로 도배되는 것 방지
        format { call ->
            val t = call.processingTimeMillis()
            "${call.response.status()?.value} ${call.request.httpMethod.value} ${call.request.path()} ${t}ms"
        }
    }

    install(StatusPages) { /* kt05 에서 자세히 */ }
}

val SimpleRateLimit = createApplicationPlugin(
    name = "SimpleRateLimit",
    createConfiguration = ::RateLimitConfig,
) {
    val counters = ConcurrentHashMap<String, AtomicInteger>()
    val limit = pluginConfig.limitPerMinute
    val keyOf = pluginConfig.keyExtractor

    // 플러그인이 자기 코루틴을 띄울 수 있습니다 (앱이 죽으면 같이 죽습니다)
    application.launch {
        while (true) { delay(60_000); counters.clear() }
    }

    onCall { call ->                       // ① 핸들러 전
        val n = counters.computeIfAbsent(keyOf(call)) { AtomicInteger() }.incrementAndGet()
        if (n > limit) {
            call.respond(HttpStatusCode.TooManyRequests, mapOf("retryAfter" to 60))
        }
    }

    onCallReceive { call -> }              // ② 본문을 읽기 직전
    onCallRespond { call, body -> }        // ③ 응답을 내보내기 직전
    on(CallFailed) { call, cause ->        // ④ 예외가 났을 때
        application.log.warn("실패: {} {}", call.request.path(), cause.message)
    }
}

install(SimpleRateLimit) { limitPerMinute = 120 }

직렬화 · 검증 — JSON 을 도메인 객체로

스프링은 잭슨이 리플렉션으로 필드를 뒤집니다. Ktor 는 kotlinx.serialization 이 컴파일 타임에 직렬화 코드를 생성합니다 — 리플렉션이 없어서 빠르고, 널 가능성이 타입 그대로 지켜집니다.

// validation/Validate.kt — 확장 함수 하나로 감싸 둡니다
class ValidationException(val fields: Map<String, List<String>>) :
    RuntimeException("검증 실패")

fun <T> T.validated(rule: Validation<T>): T {
    val result = rule(this)
    if (result is Invalid) {
        throw ValidationException(
            result.errors.groupBy(
                keySelector = { it.dataPath.removePrefix(".") },
                valueTransform = { it.message },
            )
        )
    }
    return this
}

// ── 에러 응답의 표준형 ──────────────────────────────────────────
@Serializable
data class ErrorResponse(
    val code: String,
    val message: String,
    val fields: Map<String, List<String>>? = null,
    val traceId: String? = null,
)

fun Application.configureStatusPages() = install(StatusPages) {

    exception<ValidationException> { call, e ->
        call.respond(HttpStatusCode.UnprocessableEntity,
            ErrorResponse("VALIDATION_FAILED", "입력값을 확인해 주세요", e.fields, call.callId))
    }

    exception<BadRequestException> { call, e ->
        call.respond(HttpStatusCode.BadRequest,
            ErrorResponse("MALFORMED_BODY", e.message ?: "본문을 읽을 수 없습니다", traceId = call.callId))
    }

    // 도메인 예외 — 계층을 sealed 로 두면 when 이 빠짐없이 검사됩니다
    exception<DomainException> { call, e ->
        val (status, code) = when (e) {
            is DomainException.NotFound  -> HttpStatusCode.NotFound to "NOT_FOUND"
            is DomainException.Conflict  -> HttpStatusCode.Conflict to "CONFLICT"
            is DomainException.Forbidden -> HttpStatusCode.Forbidden to "FORBIDDEN"
        }
        call.respond(status, ErrorResponse(code, e.message ?: code, traceId = call.callId))
    }

    // 마지막 그물 — 여기까지 오면 우리 잘못입니다
    exception<Throwable> { call, e ->
        call.application.log.error("처리되지 않은 예외 traceId={}", call.callId, e)
        call.respond(HttpStatusCode.InternalServerError,
            ErrorResponse("INTERNAL", "잠시 후 다시 시도해 주세요", traceId = call.callId))
    }

    // 상태 코드 자체를 가로채기 (404 · 405 등)
    status(HttpStatusCode.NotFound) { call, status ->
        call.respond(status, ErrorResponse("NOT_FOUND", "그런 경로가 없습니다"))
    }
}

}

KTOR 06

코루틴이 그대로 서버가 됩니다

Ktor 의 모든 핸들러 람다는 suspend 입니다. 어댑터도, Mono 도, CompletableFuture 도 없습니다. 코틀린에서 배운 코루틴 지식이 100% 그대로 서버에서 통합니다 — 이 탭에서 Ktor 를 쓰는 가장 큰 이유가 여기 있습니다.

게이트웨이 · BFF 에서 Ktor 가 가장 크게 이기는 그림입니다 — 코드 세 줄로 세 배가 빨라집니다.

병렬 호출 — coroutineScope + async

// 게이트웨이 라우트 — 내부 API 셋을 동시에 부르고 합칩니다
get("/api/dashboard/{userId}") {
    val userId = call.parameters["userId"]!!

    val dashboard = withTimeout(2.seconds) {          // 전체 상한 2초
        coroutineScope {                              // ★ 구조적 동시성의 경계
            val user   = async { userClient.get(userId) }
            val orders = async { orderClient.recent(userId, limit = 5) }
            val coupon = async { couponClient.available(userId) }

            Dashboard(
                user   = user.await(),                // 여기서 비로소 기다립니다
                orders = orders.await(),
                coupon = coupon.await(),
            )
        }
    }
    call.respond(dashboard)
}
coroutineScope 가 하는 세 가지 — ① 안쪽 async 가 전부 끝날 때까지 기다리고, ② 하나라도 예외가 나면 나머지를 취소하고, ③ 그 예외를 밖으로 던집니다. 이걸 손으로 짜면 CompletableFuture.allOf + 취소 처리로 30줄이 됩니다.

부분 실패를 허용하고 싶을 때

// 쿠폰 조회가 실패해도 대시보드는 보여 줘야 한다면
get("/api/dashboard/{userId}") {

    coroutineScope {
        val user   = async { userClient.get(userId) }          // 필수
        val orders = async { orderClient.recent(userId, 5) }   // 필수
        val coupon = async {                                    // 선택
            runCatching {
                withTimeout(300.milliseconds) { couponClient.available(userId) }

        }

}
runCatching 은 CancellationException 도 삼킵니다. 코루틴에서 취소는 예외로 전파되므로, 이걸 삼키면 취소가 안 먹는 코루틴이 됩니다. 안전한 형태는 이렇게 다시 던지는 것입니다 — catch (e: CancellationException) { throw e }. withTimeout 의 TimeoutCancellationException 은 예외라서 위 코드에서는 의도대로 잡히지만, 바깥 취소까지 삼키지 않게 주의해야 합니다.

    return Report(rows)
}

// plugins/Security.kt
fun Application.configureSecurity(cfg: JwtConfig, users: UserService) {

    val verifier = JWT.require(Algorithm.HMAC256(cfg.secret))
        .withIssuer(cfg.issuer)
        .withAudience(cfg.audience)
        .build()

    install(Authentication) {

        jwt("auth-jwt") {
            realm = cfg.realm
            verifier(verifier)

            validate { credential ->                       // 토큰이 유효한 뒤에 부릅니다
                val uid = credential.payload.getClaim("uid").asLong() ?: return@validate null
                val roles = credential.payload.getClaim("roles").asList(String::class.java).orEmpty()
                UserPrincipal(uid, roles.toSet())          // null 을 돌려주면 401 입니다
            }

            challenge { _, _ ->                            // 실패했을 때 무엇을 돌려줄지
                call.respond(HttpStatusCode.Unauthorized,
                    ErrorResponse("UNAUTHORIZED", "토큰이 없거나 만료됐습니다"))
            }
        }

        // 서버 사이 통신용 — 정적 API 키
        bearer("service-token") {
            authenticate { token ->
                if (MessageDigest.isEqual(token.token.toByteArray(), cfg.serviceToken.toByteArray()))
                    ServicePrincipal("internal") else null
            }
        }
    }
}

fun Route.authRoutes(cfg: JwtConfig, users: UserService, tokens: RefreshTokenStore) {

    post("/auth/login") {
        val req = call.receive<LoginRequest>()
        val user = users.verify(req.email, req.password)
            ?: throw DomainException.Forbidden("이메일 또는 비밀번호가 틀렸습니다")

        val refresh = tokens.issue(user.id)                 // 랜덤 문자열 + DB 저장
        call.response.cookies.append(
            Cookie(
                name = "refresh", value = refresh,
                httpOnly = true, secure = true,
                path = "/auth", maxAge = 14 * 24 * 3600,
                extensions = mapOf("SameSite" to "Strict"),
            )
        )
        call.respond(TokenResponse(issueAccessToken(cfg, user), expiresIn = 900))
    }

    post("/auth/refresh") {
        val presented = call.request.cookies["refresh"]
            ?: throw DomainException.Forbidden("리프레시 토큰이 없습니다")

        // ★ 회전 — 쓴 토큰은 즉시 폐기하고 새로 발급합니다
        val userId = tokens.consumeAndRotate(presented)
            ?: throw DomainException.Forbidden("리프레시 토큰이 유효하지 않습니다")

        val user = users.get(userId)
        call.respond(TokenResponse(issueAccessToken(cfg, user), expiresIn = 900))
    }

    authenticate("auth-jwt") {
        post("/auth/logout") {
            tokens.revokeAll(call.principal<UserPrincipal>()!!.userId)
            call.respond(HttpStatusCode.NoContent)
        }
    }
}

// ── 방 관리자 — 동시성 안전이 전부입니다 ──────────────────────────
@Serializable
sealed interface ChatEvent {
    @Serializable @SerialName("msg")   data class Message(val from: String, val text: String) : ChatEvent
    @Serializable @SerialName("join")  data class Joined(val who: String, val count: Int) : ChatEvent
    @Serializable @SerialName("leave") data class Left(val who: String, val count: Int) : ChatEvent
}

class ChatRoom {
    private val mutex = Mutex()
    private val sessions = mutableMapOf<String, DefaultWebSocketServerSession>()

    suspend fun join(name: String, s: DefaultWebSocketServerSession) {
        mutex.withLock { sessions[name] = s }
        broadcast(ChatEvent.Joined(name, size()))
    }

    suspend fun leave(name: String) {
        mutex.withLock { sessions.remove(name) }
        broadcast(ChatEvent.Left(name, size()))
    }

    suspend fun size() = mutex.withLock { sessions.size }

    suspend fun broadcast(event: ChatEvent) {
        // ★ 락을 쥔 채로 전송하지 않습니다 — 스냅샷만 뜨고 락을 놓습니다
        val targets = mutex.withLock { sessions.toMap() }
        val dead = mutableListOf<String>()

        coroutineScope {
            targets.forEach { (name, session) ->
                launch {
                    try {
                        withTimeout(2.seconds) { session.sendSerialized<ChatEvent>(event) }
                    } catch (e: Exception) {
                        dead += name             // 느리거나 끊긴 세션은 버립니다
                    }
                }
            }
        }
        if (dead.isNotEmpty()) mutex.withLock { dead.forEach(sessions::remove) }
    }
}

라우트 — finally 가 핵심

fun Route.chatRoutes(room: ChatRoom) {
    authenticate("auth-jwt") {
        webSocket("/ws/chat") {
            val name = call.principal<UserPrincipal>()!!.userId.toString()

            room.join(name, this)
            try {
                for (frame in incoming) {              // 연결이 끊기면 루프가 끝납니다
                    when (frame) {
                        is Frame.Text -> {
                            val text = frame.readText().take(500)
                            if (text.isNotBlank()) room.broadcast(ChatEvent.Message(name, text))
                        }
                        is Frame.Binary -> { /* 무시 */ }
                        else -> {}
                    }
                }
            } catch (e: ClosedReceiveChannelException) {
                // 정상 종료 — 로그 남길 필요 없습니다
            } catch (e: Throwable) {
                application.log.warn("소켓 오류 user={}", name, e)
            } finally {
                room.leave(name)                       // ★ 무슨 일이 있어도 여기는 실행됩니다
            }
        }
    }
}
webSocket { } 블록 안은 연결이 사는 동안 계속 실행됩니다. 일반 라우트처럼 "응답하고 끝"이 아닙니다. 여기서 만든 코루틴 · 타이머 · 구독은 전부 finally 에서 정리해야 합니다. 세션 1만 개짜리 서비스에서 정리를 빠뜨리면 몇 시간 만에 OOM 이 납니다.

// 브로드캐스트가 느린 세션에서 막히지 않게, 세션마다 발신 코루틴을 둡니다
class BufferedSession(
    private val session: DefaultWebSocketServerSession,
    scope: CoroutineScope,
) {
    // 용량을 넘으면 가장 오래된 것을 버립니다 (알림은 최신이 중요)
    private val outbox = Channel<ChatEvent>(capacity = 64, onBufferOverflow = BufferOverflow.DROP_OLDEST)

    private val pump = scope.launch {
        for (event in outbox) {
            runCatching { session.sendSerialized(event) }
                .onFailure { outbox.close(); session.close() }
        }
    }

    fun offer(event: ChatEvent) = outbox.trySend(event).isSuccess   // 절대 블로킹하지 않습니다
    fun stop() { outbox.close(); pump.cancel() }
}
왜 trySend 인가 — 브로드캐스트 루프가 단 한 세션의 네트워크 속도에 묶이면 안 됩니다. trySend 는 버퍼가 차 있으면 즉시 false 를 돌려주고 지나갑니다. "느린 사람은 메시지를 좀 놓친다"가 "모두가 느려진다"보다 낫습니다.

fun Application.configureMonitoring(registry: PrometheusMeterRegistry) {

    install(CallId) {
        header(HttpHeaders.XRequestId)                  // 앞단이 준 값이 있으면 그것을 씁니다
        generate { UUID.randomUUID().toString() }       // 없으면 만듭니다

        replyToHeader(HttpHeaders.XRequestId)           // 응답에도 실어 보냅니다
    }

    install(CallLogging) {
        level = Level.INFO
        callIdMdc("callId")                             // ★ MDC 에 넣으면 모든 로그 줄에 붙습니다
        mdc("userId") { it.principal<UserPrincipal>()?.userId?.toString() }
        filter { !it.request.path().startsWith("/healthz") }   // 헬스체크 소음 제거
        format { call ->
            "${call.response.status()?.value} ${call.request.httpMethod.value} " +
            "${call.request.path()} ${call.processingTimeMillis()}ms"
        }
    }

    install(MicrometerMetrics) {
        this.registry = registry
        meterBinders = listOf(
            JvmMemoryMetrics(), JvmGcMetrics(), JvmThreadMetrics(),
            ProcessorMetrics(), FileDescriptorMetrics(),
        )
        distributionStatisticConfig = DistributionStatisticConfig.Builder()
            .percentiles(0.5, 0.95, 0.99)               // p99 를 보려면 이걸 켜야 합니다
            .build()
    }

    routing {
        get("/metrics") { call.respond(registry.scrape()) }   // Prometheus 가 긁어 갑니다

        get("/healthz") { call.respondText("OK") }             // liveness — 절대 DB 를 보지 마세요
        get("/readyz") {                                        // readiness — 여기서 의존성을 봅니다
            val checks = mapOf(
                "db" to runCatching { withTimeout(1.seconds) { deps.ping() } }.isSuccess,
                "redis" to runCatching { withTimeout(500.milliseconds) { deps.cache.ping() } }.isSuccess,
            )
            if (checks.values.all { it }) call.respond(checks)
            else call.respond(HttpStatusCode.ServiceUnavailable, checks)
        }
    }
}

// 비즈니스 지표는 도메인 서비스에서 직접 올립니다
class LinkService(
    private val repo: LinkRepository,
    private val cache: CacheClient,
    private val metrics: MeterRegistry,
) {
    private val created = metrics.counter("links.created")
    private val cacheHit = metrics.counter("links.resolve", "source", "cache")
    private val cacheMiss = metrics.counter("links.resolve", "source", "db")

    suspend fun resolve(slug: String): String? {
        cache.get("u:$slug")?.let { cacheHit.increment(); return it }
        cacheMiss.increment()
        return repo.findBySlug(slug)?.url?.also { cache.set("u:$slug", it, 1.hours) }
    }

    // 처리 시간을 재는 표준형
    suspend fun <T> timed(name: String, block: suspend () -> T): T {
        val sample = Timer.start(metrics)
        try { return block() } finally { sample.stop(metrics.timer(name)) }
    }
}
태그에 카디널리티가 높은 값을 넣지 마세요 — counter("x", "slug", slug) 처럼 사용자 id · URL · slug 를 태그로 넣으면 시계열이 수백만 개가 되어 프로메테우스가 먼저 죽습니다. 태그는 값의 종류가 수십 개 이하인 것만(상태 코드 · 메서드 · 결과 구분).

// domain/LinkService.kt
class LinkService(
    private val repo: LinkRepository,
    private val cache: CacheClient,
    private val clock: Clock = Clock.System,     // ★ 테스트에서 시간을 고정하려고
) {
    private val alphabet = "abcdefghijkmnpqrstuvwxyz23456789"   // 헷갈리는 글자 제외

    suspend fun create(req: CreateLinkRequest, ownerId: Long): Link {
        req.validated(validateCreateLink)
        // 사용자가 원하는 슬러그가 있으면 그것으로, 없으면 뽑아서 충돌 시 재시도
        repeat(5) {
            val slug = req.slug ?: randomSlug()
            runCatching { return repo.create(slug, req.url, ownerId) }
                .onFailure { if (req.slug != null) throw DomainException.Conflict("슬러그 $slug") }
        }
        error("슬러그를 5번 시도해도 못 만들었습니다")
    }

    // ★ 리다이렉트는 서비스에서 가장 뜨거운 경로입니다 — 캐시 우선
    suspend fun resolve(slug: String): String? {
        cache.get("u:$slug")?.let { return it }
        val link = repo.findBySlug(slug) ?: return null
        cache.set("u:$slug", link.url, ttl = 1.hours)
        return link.url
    }

    // 클릭은 Redis 에서만 셉니다 (DB 쓰기를 요청 경로에서 뺍니다)
    suspend fun recordClick(slug: String) { cache.incr("c:$slug") }

    suspend fun stats(slug: String): LinkStats {
        val link = repo.findBySlug(slug) ?: throw DomainException.NotFound("링크 $slug")
        val pending = cache.getLong("c:$slug") ?: 0
        return LinkStats(slug, link.url, link.clicks + pending, link.createdAt)
    }

    private fun randomSlug(len: Int = 7) =
        (1..len).map { alphabet.random() }.joinToString("")
}

// routes/RedirectRoutes.kt — 초당 수천 건이 오는 경로. 가장 짧게 유지합니다
fun Route.redirectRoutes(service: LinkService, counters: CounterBus) {
    get("/{slug}") {
        val slug = call.parameters["slug"]!!
        val url = service.resolve(slug)
            ?: return@get call.respond(HttpStatusCode.NotFound, ErrorResponse("NOT_FOUND", "없는 링크입니다"))

        // ★ 응답을 먼저 보내고, 집계는 응답 경로에서 뺍니다
        call.respondRedirect(url, permanent = false)      // 302 (301 은 브라우저가 캐시해 통계가 끊깁니다)

        application.launch {                               // 요청 코루틴과 분리
            runCatching {
                service.recordClick(slug)
                counters.publish(slug)                     // 대시보드로 흘려보냅니다
            }.onFailure { application.log.warn("클릭 집계 실패 slug={}", slug, it) }
        }
    }
}

fun Route.adminSocketRoutes(counters: CounterBus) {
    authenticate("auth-jwt") {
        webSocket("/ws/admin") {
            val principal = call.principal<UserPrincipal>()!!
            if ("ADMIN" !in principal.roles) {
                close(CloseReason(CloseReason.Codes.VIOLATED_POLICY, "권한 없음")); return@webSocket
            }

            val job = launch {
                counters.stream()                          // Flow<ClickEvent>
                    .sample(500.milliseconds)              // ★ 초당 수천 건을 초당 2회로 줄입니다
                    .collect { sendSerialized(it) }
            }
            try {
                for (frame in incoming) { /* 클라이언트는 보낼 게 없습니다 */ }
            } finally {
                job.cancel()                               // ★ 반드시 정리
            }
        }
    }
}

// infra/ClickFlusher.kt — Redis 의 카운터를 주기적으로 DB 에 반영합니다
class ClickFlusher(
    private val cache: CacheClient,
    private val repo: LinkRepository,
    scope: CoroutineScope,
) {
    private val job = scope.launch {
        while (isActive) {
            delay(30.seconds)
            runCatching { flushOnce() }
                .onFailure { logger.error("클릭 반영 실패", it) }   // ★ 실패해도 루프는 계속
        }
    }

    private suspend fun flushOnce() {
        val pending = cache.scanAndReset("c:*")            // { slug -> 증가량 }
        if (pending.isEmpty()) return
        repo.bulkIncrement(pending)                        // 한 트랜잭션에 몰아서
        logger.info("클릭 {}건 반영", pending.values.sum())
    }

    fun stop() = job.cancel()
}

// infra/RedisCache.kt
class RedisCache(cfg: RedisConfig) : CacheClient {
    private val client = RedisClient.create(cfg.url)
    private val conn = client.connect()
    private val cmd = conn.coroutines()          // ★ suspend 로 쓰는 명령 인터페이스

    override suspend fun get(key: String): String? = cmd.get(key)

    override suspend fun set(key: String, value: String, ttl: Duration) {
        cmd.set(key, value, SetArgs.Builder.ex(ttl.inWholeSeconds))
    }

    override suspend fun incr(key: String): Long = cmd.incr(key) ?: 0

    override suspend fun getLong(key: String): Long? = cmd.get(key)?.toLongOrNull()

    override fun close() { conn.close(); client.shutdown() }
}

    monitor.subscribe(ApplicationStopped) {
        appScope.cancel(); cache.close(); ds.close()
    }
}

가장 크게 벌어진 둘은 p99 와 테스트 시간입니다. p99 차이는 스레드 풀 대기에서 옵니다 — 리다이렉트처럼 짧은 요청이 많이 몰릴 때 스레드 모델이 먼저 한계를 만납니다. 테스트 시간은 컨텍스트 기동이 없다는 것 하나 때문입니다. 처리량 차이(33%)는 생각보다 크지 않습니다 — 대부분의 서비스에서 병목은 프레임워크가 아니라 DB 와 외부 호출입니다.

그래서 무엇을 배웠나 — 체크리스트

  • 도메인에 io.ktor.* 를 들이지 않기 — 이 한 줄이 테스트 속도와 이식성을 만듭니다.
  • 트랜잭션은 짧게, 외부 호출은 밖으로 — 커넥션 점유가 처리량의 상한입니다.
  • 뜨거운 경로는 캐시 우선 · 쓰기는 비동기 — 리다이렉트에 DB 쓰기를 넣지 않습니다.
  • 에러 모양을 처음에 한 번 정하기 — StatusPages + sealed 예외.
  • WebSocket 은 finally 부터 — 정리 누락이 유일하고도 확실한 사고 원인입니다.
  • liveness 와 readiness 를 구분 — 연쇄 장애를 막는 가장 싼 방법.
  • CallId 를 첫날에 — 나중에 넣으면 이미 늦습니다.
마지막으로 정직하게 — 이 표의 숫자만 보고 사내 표준을 갈아엎지 마세요. Ktor 의 진짜 비용은 벤치마크에 안 나옵니다 — 배치 · 스케줄러 · 사내 스타터 · 신입 온보딩 · 검색 가능한 답변의 양. 새로 만드는 작은 서비스 하나부터 시작해서 팀이 코루틴에 익숙해진 뒤에 넓히는 것이 실패하지 않는 순서입니다.
