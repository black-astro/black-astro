AND 01

프로젝트 구조와 시작

안드로이드 프로젝트는 Gradle 멀티모듈 + 매니페스트 + 리소스로 이루어집니다. 서버 프로젝트와 다른 부분만 짚고 넘어갑니다.

minSdk 를 정하는 법

낮출수록 더 많은 기기를 지원하지만 옛 API 대응 코드가 늘어납니다. Android Studio 의 마법사가 버전별 점유율을 보여 주므로 그걸 기준으로 정합니다. 26(Oreo) 이상이면 자바 8 API·알림 채널 등 대부분의 현대적 기능을 쓸 수 있습니다.

서버 개발자가 낯설어하는 것

  • 매니페스트 — 화면·서비스·권한을 XML 로 선언해야 시스템이 안다
  • 리소스 — 문자열·색·크기를 코드가 아니라 res/에 두고 참조
  • R8/ProGuard — 릴리스 빌드에서 코드가 난독화·축소된다 (리플렉션 주의)
  • 기기 파편화 — 화면 크기·OS 버전·제조사 변형까지 고려
AND 02

생명주기 — 화면은 사라진다

안드로이드에서 버그의 가장 큰 원천입니다. 화면 회전 · 백그라운드 전환 · 프로세스 종료 세 가지가 각각 다르게 동작하고, 각각 다른 복구 수단이 있습니다.

개발자 옵션의 “활동 유지 안 함”을 켜면 ②를 항상 재현할 수 있습니다 — 출시 전 필수 점검입니다.

Activity 생명주기 콜백

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent { AppTheme { AppNavHost() } }     // Compose 진입점
    }
    // onStart  — 화면에 보이기 시작
    // onResume — 사용자와 상호작용 가능 (포커스)
    // onPause  — 다른 화면이 위로 (일부 가림)
    // onStop   — 완전히 안 보임 → 여기서 무거운 작업 중단
    // onDestroy— 끝 (회전 시에도 불린다!)
}

// Compose 에서 생명주기 이벤트를 관찰
@Composable
fun ObserveLifecycle(onResume: () -> Unit) {
    val owner = LocalLifecycleOwner.current
    DisposableEffect(owner) {
        val observer = LifecycleEventObserver { _, event ->
            if (event == Lifecycle.Event.ON_RESUME) onResume()
        }
        owner.lifecycle.addObserver(observer)
        onDispose { owner.lifecycle.removeObserver(observer) }
    }
}

상태 복구 — SavedStateHandle

@HiltViewModel
class SearchViewModel @Inject constructor(
    private val savedState: SavedStateHandle,   // 프로세스 종료도 견딘다
    private val repo: SearchRepository,
) : ViewModel() {

    // 화면 인자 (Navigation 에서 전달된 값)
    private val categoryId: Long = checkNotNull(savedState["categoryId"])

    // 사용자 입력 — 프로세스가 죽어도 복구된다
    val query: StateFlow<String> = savedState.getStateFlow("query", "")

    fun onQueryChange(q: String) { savedState["query"] = q }

    val results: StateFlow<List<Item>> = query
        .debounce(300)
        .flatMapLatest { repo.search(it, categoryId) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())
}
SavedStateHandle 에는 작은 값만 넣으세요(수백 KB 이하). Bundle 크기를 넘기면 TransactionTooLargeException으로 앱이 죽습니다. 목록 데이터는 DB 에 두고 id 만 저장하는 것이 정석입니다.
AND 03

Compose — 선언형 UI

XML 로 화면을 만들고 findViewById로 값을 바꾸던 방식이, “상태를 주면 화면이 그려진다”는 함수 하나로 바뀝니다.

Compose 를 배울 때 외울 문장은 하나입니다 — 화면 = f(상태). 화면을 고치려 하지 말고 상태를 고치세요.
기존 View 방식 — 명령형
// activity_main.xml 에 뷰를 선언하고
val textView = findViewById<TextView>(R.id.text)
val button = findViewById<Button>(R.id.button)

var count = 0
button.setOnClickListener {
    count++
    textView.text = "클릭 $count"       // 직접 바꾼다
    if (count > 5) {
        button.isEnabled = false          // 상태가 여러 곳에 흩어진다
        textView.setTextColor(Color.RED)
    }
}
// 화면이 복잡해질수록 '지금 화면 상태'를 아무도 모른다
Compose — 선언형
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }

    Column(
        modifier = Modifier.fillMaxWidth().padding(16.dp),
        horizontalAlignment = Alignment.CenterHorizontally,
    ) {
        Text(
            text = "클릭 $count",
            color = if (count > 5) Color.Red else Color.Unspecified,
            style = MaterialTheme.typography.headlineMedium,
        )
        Button(onClick = { count++ }, enabled = count <= 5) {
            Text("누르기")
        }
    }
}
// 상태(count)만 바뀌면 화면은 알아서 다시 그려진다

핵심 개념 넷

개념뜻
@ComposableUI 를 그리는 함수. 반환값이 아니라 화면을 방출한다
Recomposition상태가 바뀌면 그 부분만 다시 실행된다
State<T>Compose 가 관찰하는 값. 바뀌면 recomposition 을 유발
Modifier크기·여백·클릭·배경을 체인으로 붙이는 방식
Composable 함수의 규칙 — ① 이름은 대문자로 시작, ② 반환값이 없다(Unit), ③ 부수 효과를 직접 쓰지 않는다(다음 섹션), ④ 여러 번·순서 없이 실행될 수 있다.

Modifier — 순서가 의미를 바꾼다

// 패딩 → 배경 : 패딩 바깥은 배경이 없다
Text("A", Modifier.padding(16.dp).background(Color.Blue))

// 배경 → 패딩 : 배경이 패딩 영역까지 칠해진다
Text("A", Modifier.background(Color.Blue).padding(16.dp))

// 자주 쓰는 것들
Modifier
    .fillMaxWidth()                 // 가로 꽉
    .height(48.dp)
    .padding(horizontal = 16.dp)
    .clip(RoundedCornerShape(8.dp))
    .background(MaterialTheme.colorScheme.surface)
    .clickable { onClick() }        // 클릭 영역은 여기까지
    .semantics { contentDescription = "주문 항목" }   // 접근성
미리보기(@Preview)를 적극 쓰세요. 기기를 띄우지 않고 IDE 안에서 화면을 확인합니다. 상태별 미리보기(로딩·에러·빈 목록)를 만들어 두면 UI 회귀를 눈으로 즉시 잡습니다.

레이아웃 · 리스트

Compose 의 레이아웃은 Column · Row · Box 셋으로 거의 다 됩니다. 목록은 LazyColumn — 화면에 보이는 것만 만들어 성능을 지킵니다.

기본 레이아웃

// 세로 배치
Column(

    horizontalAlignment = Alignment.CenterHorizontally,

    Text("제목")
    Text("설명")

Row(verticalAlignment = Alignment.CenterVertically) {

    Text("12,000원")

// 겹치기
Box(contentAlignment = Alignment.Center) {
    Image(painter, contentDescription = null)
    CircularProgressIndicator()                          // 이미지 위에
}

// 스크롤이 필요한 짧은 화면
Column(Modifier.verticalScroll(rememberScrollState())) { /* ... */ }

LazyColumn — 목록의 기본

@Composable
fun OrderList(orders: List<Order>, onClick: (Long) -> Unit) {
    LazyColumn(
        contentPadding = PaddingValues(16.dp),
        verticalArrangement = Arrangement.spacedBy(12.dp),
    ) {
        item { ListHeader() }                      // 단일 항목

        items(
            items = orders,
            key = { it.id },                        // ★ 안정적인 key 는 필수
        ) { order ->
            OrderCard(order, onClick = { onClick(order.id) })
        }

        if (orders.isEmpty()) {
            item { EmptyView() }
        }
    }
}

// 그리드는 LazyVerticalGrid
LazyVerticalGrid(columns = GridCells.Fixed(2)) { items(products) { ProductCard(it) } }
key를 주지 않으면 항목이 추가·삭제될 때 인덱스 기준으로 재사용되어 상태가 엉뚱한 항목에 붙습니다(체크박스가 다른 줄로 옮겨 가는 버그).

화면 골격 — Scaffold

@OptIn(ExperimentalMaterial3Api::class)
@Composable
fun OrderScreen(
    state: OrderUiState,
    onRefresh: () -> Unit,
    onItemClick: (Long) -> Unit,
) {
    val snackbarHostState = remember { SnackbarHostState() }

    Scaffold(
        topBar = {
            TopAppBar(
                title = { Text("주문 내역") },
                actions = { IconButton(onRefresh) { Icon(Icons.Default.Refresh, "새로고침") } },
            )
        },
        snackbarHost = { SnackbarHost(snackbarHostState) },
        floatingActionButton = {
            FloatingActionButton(onClick = { /* ... */ }) { Icon(Icons.Default.Add, "추가") }
        },
    ) { padding ->
        Box(Modifier.padding(padding).fillMaxSize()) {      // ★ padding 을 반드시 적용
            when (state) {
                OrderUiState.Loading -> CircularProgressIndicator(Modifier.align(Alignment.Center))
                is OrderUiState.Error -> ErrorView(state.message, onRetry = onRefresh)
                is OrderUiState.Success -> OrderList(state.orders, onItemClick)

        }
    }
}
화면 상태를 sealed 로 만들고 when으로 분기하는 이 형태가 Compose 화면의 표준 골격입니다. 로딩·에러·성공·빈 목록 네 가지를 빠뜨리지 않게 컴파일러가 도와줍니다(Kotlin 기초 11 · sealed).
AND 05

상태와 재구성(recomposition)

Compose 를 제대로 쓰는 것은 상태를 어디에 둘지를 정하는 일입니다. 잘못 두면 화면이 안 바뀌거나, 반대로 필요 없이 계속 다시 그려집니다.

다시 그려지는 범위는 값을 읽는 곳이 정합니다 — 넘기는 곳이 아닙니다.
// ① remember — 재구성 사이에 값을 기억한다 (화면 회전에는 사라진다)
var text by remember { mutableStateOf("") }

// ② rememberSaveable — 화면 회전·프로세스 종료도 견딘다 (작은 값만)
var query by rememberSaveable { mutableStateOf("") }

// ③ 계산 결과 캐싱 — key 가 바뀔 때만 다시 계산
val formatted = remember(order.total) { formatCurrency(order.total) }

// ④ 리스트 상태
val listState = rememberLazyListState()
val scope = rememberCoroutineScope()
Button(onClick = { scope.launch { listState.animateScrollToItem(0) } }) { Text("맨 위로") }

// ⑤ 파생 상태 — 자주 바뀌는 값에서 '가끔 바뀌는 값'을 뽑을 때
val showScrollToTop by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 5 }
}
// listState 는 스크롤마다 바뀌지만 showScrollToTop 은 true/false 가 바뀔 때만 재구성

상태 호이스팅 — 위로 끌어올리기

// ❌ 상태를 안에 가둔 컴포저블 — 테스트·재사용이 어렵다
@Composable
fun SearchBar() {
    var query by remember { mutableStateOf("") }
    TextField(query, { query = it })
}

// ✅ 상태를 밖으로, 이벤트를 위로 (stateless)
@Composable
fun SearchBar(
    query: String,
    onQueryChange: (String) -> Unit,
    modifier: Modifier = Modifier,
) {
    TextField(value = query, onValueChange = onQueryChange, modifier = modifier)
}

// 쓰는 쪽에서 상태를 소유한다
@Composable
fun SearchScreen(vm: SearchViewModel = hiltViewModel()) {
    val query by vm.query.collectAsStateWithLifecycle()
    SearchBar(query = query, onQueryChange = vm::onQueryChange)
}
규칙 — 상태는 그것을 읽는 모든 컴포저블의 공통 조상에 둡니다. UI 컴포넌트는 상태를 받고 이벤트를 올려보내는 형태(stateless)로 만들면 미리보기·테스트·재사용이 전부 쉬워집니다.

재구성을 줄이는 기술

  • 상태를 읽는 범위를 좁힌다 — 값을 그대로 넘기지 말고 람다로 넘기면 그 자식만 재구성됩니다 (text = { count })
  • 안정적인(stable) 타입을 쓴다 — List는 불안정으로 취급됩니다. ImmutableList(kotlinx.collections.immutable)나 @Immutable 표시
  • key를 준다 — 목록 항목의 정체성
  • 무거운 계산은 remember(key) 로 캐싱
  • 람다를 매번 새로 만들지 않기 — 메서드 참조(vm::onClick) 사용
@Immutable
data class OrderUi(val id: Long, val title: String, val total: String)

// 컴파일러 지표 켜기 — 어떤 함수가 불안정한지 보고서로 나온다
// kotlin { compilerOptions { freeCompilerArgs.addAll(
//   "-P", "plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=..." ) } }
Composable 안에서 값을 직접 바꾸지 마세요. @Composable fun A() { count++ } 같은 코드는 재구성마다 실행되어 무한 루프가 됩니다. 상태 변경은 이벤트 콜백이나 부수 효과 API(다음 섹션)에서만.
AND 06

부수 효과 — Effect API

“화면이 뜨면 데이터를 불러온다”, “에러가 생기면 스낵바를 띄운다” 같은 UI 그리기가 아닌 일은 정해진 API 안에서 해야 합니다. 아무 데서나 하면 재구성마다 반복 실행됩니다.

API언제 쓰나
LaunchedEffect(key)진입 시 한 번 · key 가 바뀔 때 코루틴 실행 (가장 많이 씀)
rememberCoroutineScope()이벤트 콜백에서 코루틴을 시작할 때 (클릭 → 스크롤)
DisposableEffect(key)등록/해제가 짝인 것 (리스너·브로드캐스트 리시버)
rememberUpdatedState오래 도는 effect 안에서 최신 람다를 참조해야 할 때
SideEffect재구성이 성공할 때마다 비-Compose 객체에 값 전달
produceState비-Compose 소스를 State 로 변환
snapshotFlowCompose State 를 Flow 로 (스크롤 위치 관찰 등)
@Composable
fun OrderScreen(vm: OrderViewModel = hiltViewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()
    val snackbar = remember { SnackbarHostState() }

    // ① 진입 시 한 번 로드 (id 가 바뀌면 다시)
    LaunchedEffect(vm.orderId) { vm.load() }

    // ② 일회성 이벤트 수신 — SharedFlow
    LaunchedEffect(Unit) {
        vm.events.collect { event ->
            when (event) {
                is Event.ShowMessage -> snackbar.showSnackbar(event.text)
                is Event.NavigateBack -> onBack()
            }
        }
    }

    // ③ 이벤트 콜백에서 코루틴 — rememberCoroutineScope
    val scope = rememberCoroutineScope()
    val listState = rememberLazyListState()
    Button(onClick = { scope.launch { listState.animateScrollToItem(0) } }) { Text("맨 위로") }

    // ④ 등록/해제 짝
    DisposableEffect(Unit) {
        val receiver = NetworkReceiver { vm.onNetworkChange(it) }
        context.registerReceiver(receiver, filter)
        onDispose { context.unregisterReceiver(receiver) }
    }

    // ⑤ 스크롤 끝 감지 → 다음 페이지 (Compose State → Flow)
    LaunchedEffect(listState) {
        snapshotFlow { listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index }
            .distinctUntilChanged()
            .collect { last -> if (last != null && last >= state.items.size - 3) vm.loadMore() }
    }
}

  • Composable 본문에서 API 호출 — 재구성마다 호출됩니다
  • 스낵바를 상태로 표현 — 회전하면 다시 뜹니다. 이벤트(SharedFlow)로
  • rememberCoroutineScope 를 진입 로직에 — 그건 LaunchedEffect 자리

ViewModel · 화면 상태 설계

안드로이드 아키텍처의 중심입니다. 화면이 재생성돼도 살아남고, viewModelScope로 화면이 사라지면 코루틴이 자동 취소됩니다.

"화면이 이상하다"의 원인은 대개 상태가 두 군데에 있는 것입니다 — 출처를 하나로 만드세요.
// 화면 상태 — sealed 로 모든 경우를 덮는다
sealed interface OrderUiState {
    data object Loading : OrderUiState
    data class Success(
        val orders: List<OrderUi>,
        val isRefreshing: Boolean = false,
    ) : OrderUiState
    data class Error(val message: String) : OrderUiState
}

// 일회성 이벤트 — 상태가 아니다
sealed interface OrderEvent {
    data class ShowMessage(val text: String) : OrderEvent
    data class NavigateToDetail(val id: Long) : OrderEvent
}

@HiltViewModel
class OrderViewModel @Inject constructor(
    private val repo: OrderRepository,
    savedState: SavedStateHandle,
) : ViewModel() {

    private val _state = MutableStateFlow<OrderUiState>(OrderUiState.Loading)
    val state: StateFlow<OrderUiState> = _state.asStateFlow()

    private val _events = MutableSharedFlow<OrderEvent>()
    val events: SharedFlow<OrderEvent> = _events.asSharedFlow()

    init { load() }

    fun load() {
        viewModelScope.launch {                     // 화면이 사라지면 자동 취소
            _state.value = OrderUiState.Loading
            _state.value = runCatching { repo.list() }
                .fold(
                    onSuccess = { OrderUiState.Success(it.map(Order::toUi)) },
                    onFailure = { OrderUiState.Error(it.toUserMessage()) },
                )
        }
    }

    fun refresh() = viewModelScope.launch {
        _state.update { if (it is OrderUiState.Success) it.copy(isRefreshing = true) else it }
        runCatching { repo.list() }
            .onSuccess { _state.value = OrderUiState.Success(it.map(Order::toUi)) }
            .onFailure { _events.emit(OrderEvent.ShowMessage("새로고침 실패")) }
    }

    fun onItemClick(id: Long) = viewModelScope.launch {
        _events.emit(OrderEvent.NavigateToDetail(id))
    }
}

DB·네트워크를 Flow 로 잇기

@HiltViewModel
class FeedViewModel @Inject constructor(repo: FeedRepository) : ViewModel() {

    // Room 이 Flow 를 주면 데이터가 바뀔 때마다 화면이 자동 갱신된다
    val state: StateFlow<FeedUiState> = repo.observeFeed()
        .map { FeedUiState.Success(it.map(Post::toUi)) }
        .catch { emit(FeedUiState.Error(it.message ?: "오류")) }

            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = FeedUiState.Loading,
        )
}
단일 소스 원칙(SSOT) — 화면은 DB 를 보고, 네트워크는 DB 를 갱신합니다. 이렇게 하면 오프라인에서도 동작하고, 갱신 로직이 화면과 분리됩니다.

ViewModel 규칙

  • Context·View·Activity 를 들고 있지 않기 — 메모리 누수의 정석 (필요하면 AndroidViewModel의 application)
  • UI 모델로 변환해서 내보내기 — 화면이 도메인 객체를 직접 다루지 않게
  • 상태는 하나의 StateFlow — 여러 개면 조합 상태가 어긋납니다
  • 이벤트와 상태를 구분 — 토스트·이동은 이벤트
  • init에서 무거운 로딩을 하면 테스트가 어려워집니다 — 화면에서 LaunchedEffect로 부르는 방식도 좋습니다

class OrderRepository @Inject constructor(
    private val api: OrderApi,
    private val dao: OrderDao,
    private val io: CoroutineDispatcher = Dispatchers.IO,
) {
    // 화면은 DB 만 본다 (단일 소스)
    fun observe(): Flow<List<Order>> = dao.observeAll().map { it.map(OrderEntity::toDomain) }

    // 네트워크는 DB 를 갱신한다
    suspend fun refresh(): Result<Unit> = withContext(io) {
        runCatching {
            val remote = api.list()
            dao.replaceAll(remote.map(OrderDto::toEntity))
        }.onFailure { e ->
            if (e is CancellationException) throw e
            Log.w(TAG, "동기화 실패", e)
        }.map { }
    }
}

// 에러를 사용자 메시지로 바꾸는 자리도 여기
fun Throwable.toUserMessage(): String = when (this) {
    is UnknownHostException, is ConnectException -> "인터넷 연결을 확인해 주세요"
    is SocketTimeoutException -> "응답이 지연되고 있어요. 잠시 후 다시 시도해 주세요"
    is HttpException -> when (code()) {
        401 -> "다시 로그인해 주세요"
        404 -> "정보를 찾을 수 없어요"
        in 500..599 -> "서버에 문제가 있어요"
        else -> "요청을 처리하지 못했어요"
    }
    else -> "알 수 없는 오류가 발생했어요"
}

로컬 저장 — Room · DataStore

앱은 오프라인에서도 뭔가 보여 줘야 합니다. 구조화된 데이터는 Room(SQLite), 설정 같은 작은 값은 DataStore입니다.

고민이 길어지면 기준은 하나입니다 — 검색하거나 관계가 있으면 Room, 아니면 DataStore.

Room — Flow 를 돌려주는 DAO

@Entity(tableName = "orders")
data class OrderEntity(              // Room 은 data class 가 자연스럽다
    @PrimaryKey val id: Long,
    val orderNo: String,
    val status: String,
    val totalAmount: Long,
    @ColumnInfo(name = "created_at") val createdAt: Long,
)

@Dao
interface OrderDao {
    @Query("SELECT * FROM orders ORDER BY created_at DESC")
    fun observeAll(): Flow<List<OrderEntity>>      // ★ 데이터가 바뀌면 자동 방출

    @Query("SELECT * FROM orders WHERE id = :id")
    suspend fun find(id: Long): OrderEntity?

    @Upsert
    suspend fun upsertAll(items: List<OrderEntity>)

    @Query("DELETE FROM orders")
    suspend fun clear()

    @Transaction
    suspend fun replaceAll(items: List<OrderEntity>) { clear(); upsertAll(items) }
}

@Database(entities = [OrderEntity::class], version = 2, exportSchema = true)
abstract class AppDatabase : RoomDatabase() {
    abstract fun orderDao(): OrderDao
}

// 스키마 변경 — 마이그레이션을 반드시 작성 (안 하면 앱이 죽는다)
val MIGRATION_1_2 = object : Migration(1, 2) {

DataStore — SharedPreferences 의 후계

val Context.settings: DataStore<Preferences> by preferencesDataStore("settings")

class SettingsRepository @Inject constructor(
    @ApplicationContext private val context: Context,
) {
    private val darkModeKey = booleanPreferencesKey("dark_mode")

    val darkMode: Flow<Boolean> = context.settings.data
        .catch { if (it is IOException) emit(emptyPreferences()) else throw it }
        .map { it[darkModeKey] ?: false }

    suspend fun setDarkMode(on: Boolean) {
        context.settings.edit { it[darkModeKey] = on }
    }
}
SharedPreferences 를 새로 쓰지 마세요. apply()가 메인 스레드를 막는 경우가 있고 에러 처리가 없습니다. DataStore 는 코루틴 기반이라 안전합니다. 토큰·비밀번호는 EncryptedSharedPreferences나 Keystore 를 쓰세요.
오프라인 우선(offline-first) 구조 — 화면은 Room 의 Flow 를 보고, 앱이 시작되거나 당겨서 새로고침할 때 네트워크가 Room 을 갱신합니다. 이렇게 하면 비행기 모드에서도 앱이 동작하고, 화면 코드에서 로딩 처리가 단순해집니다.

            else -> launcher.launch(Manifest.permission.CAMERA)
        }
    }) { Text("사진 찍기") }

    if (showRationale) {
        AlertDialog(
            onDismissRequest = { showRationale = false },
            title = { Text("카메라 권한이 필요해요") },
            text = { Text("영수증을 촬영하려면 카메라 접근을 허용해 주세요.") },
            confirmButton = {
                TextButton(onClick = { context.openAppSettings() }) { Text("설정 열기") }
            },
        )
    }
}

출시 전 최소 점검

  • 화면 회전에서 상태가 유지되는가
  • 개발자 옵션 “활동 유지 안 함”으로 프로세스 종료 복구 확인
  • 다크 모드에서 글자가 보이는가
  • 글자 크기 최대로 키웠을 때 레이아웃이 깨지지 않는가
  • 비행기 모드에서 에러 화면과 재시도가 동작하는가
  • 느린 네트워크(에뮬레이터 설정)에서 로딩 표시가 뜨는가
  • 릴리스 빌드(R8)에서도 정상 동작하는가 — 난독화 문제는 여기서만 드러납니다
