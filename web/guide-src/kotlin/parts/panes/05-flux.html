FLUX 01

왜 WebFlux인가 — 그리고 언제 아닌가

WebFlux는 “더 빠른 스프링”이 아닙니다. 적은 스레드로 많은 커넥션을 유지하기 위한 모델이고, 그 대가로 전 구간이 논블로킹이어야 합니다. 한 군데라도 막히면 MVC보다 나빠집니다.

WebFlux의 이득은 커넥션이 아주 많을 때 나옵니다 — 그렇지 않다면 MVC가 더 단순하고 빠릅니다.

WebFlux 가 맞는 상황

  • 동시 커넥션이 수천~수만 — 채팅·알림·SSE·롱폴링
  • 게이트웨이·프록시 — 요청을 받아 다른 서비스로 넘기는 일이 대부분
  • 스트리밍 — 대용량 응답을 조금씩 흘려보내야 할 때
  • 전 구간 논블로킹이 가능 — R2DBC·논블로킹 HTTP 클라이언트만 사용

MVC 로 충분한 상황 (대부분)

  • JPA·JDBC 를 쓴다 — 어차피 블로킹이라 이득이 제한적
  • 초당 수백~수천 요청 — 톰캣 + 가상 스레드로 충분
  • 팀에 리액티브 경험이 적다 — 디버깅 비용이 큽니다
  • 트랜잭션이 복잡한 업무 시스템 — JPA 생태계의 이점이 큽니다
2026년의 현실적 판단 — “동시성”만 필요하면 MVC + 가상 스레드가 훨씬 싼 선택입니다. WebFlux 는 스트리밍·백프레셔·게이트웨이처럼 모델 자체가 필요한 곳에서 고르세요.
의존성 — implementation("org.springframework.boot:spring-boot-starter-webflux") · implementation("org.jetbrains.kotlinx:kotlinx-coroutines-reactor") (Reactor ↔ 코루틴 변환에 필수) · R2DBC 를 쓰면 spring-boot-starter-data-r2dbc
FLUX 02

Mono와 Flux — 최소한만

코틀린으로 쓸 거라면 Reactor 연산자를 전부 외울 필요가 없습니다. 이 두 타입이 무엇인지와 코루틴으로 바꾸는 법만 알면 됩니다.

두 타입의 뜻

타입뜻 · 코루틴 대응
Mono<T>0 또는 1개 → suspend fun (): T?
Flux<T>0..N 개 → Flow<T>
Mono<Void>완료 신호만 → suspend fun (): Unit
// Reactor 스타일 (자바에서 오던 코드)
fun findUser(id: Long): Mono<User> =
    repo.findById(id)
        .switchIfEmpty(Mono.error(NotFound(id)))
        .flatMap { u -> enrich(u) }
        .timeout(Duration.ofSeconds(3))
        .onErrorResume { Mono.just(User.GUEST) }

// 코틀린 코루틴 스타일 — 같은 일
suspend fun findUser(id: Long): User =
    withTimeoutOrNull(3.seconds) {
        val u = repo.findById(id).awaitSingleOrNull() ?: throw NotFound(id)
        enrich(u)
    } ?: User.GUEST

Cold·구독·백프레셔 — 개념은 Flow와 같다

  • 구독하기 전엔 아무 일도 없다 — Flow 의 collect와 같은 규칙
  • 백프레셔 — 소비자가 request(n)으로 속도를 조절. 코루틴 Flow 는 중단(suspend)으로 같은 효과를 냅니다
  • 연산자 체인 — Flow 의 map·filter·buffer와 대응
Mono 를 만들어 놓고 구독하지 않으면 아무 일도 일어나지 않습니다. repo.save(x)만 부르고 반환값을 버리는 코드가 대표적인 버그입니다 — 코루틴에서는 awaitSingle()을 부르지 않은 것과 같습니다.
FLUX 03

Reactor ↔ 코루틴 변환

실무에서 가장 많이 쓰는 표입니다. 경계에서만 변환하고 안쪽은 전부 코루틴으로 쓰는 것이 코틀린 WebFlux의 표준 전략입니다.

방향코드
Mono → 값mono.awaitSingle() · 비어 있을 수 있으면 awaitSingleOrNull()
Mono<Void> → Unitmono.awaitFirstOrNull() · mono.thenAwait()
Flux → Flowflux.asFlow()
Flux → Listflux.collectList().awaitSingle()
suspend → Monomono { getUser(id) }
Flow → Fluxflow.asFlux()
Publisher → Flowpublisher.asFlow()
Flow → Publisherflow.asPublisher()
@Service
class UserService(
    private val repo: UserR2dbcRepository,     // 리액티브 리포지터리
    private val client: WebClient,
) {
    // 안쪽은 전부 코루틴 — 읽기 쉽고 try-catch 가 통한다
    suspend fun profile(id: Long): Profile = coroutineScope {
        val user = async { repo.findById(id).awaitSingleOrNull() ?: throw NotFound(id) }
        val orders = async {
            client.get().uri("/orders?userId=$id")
                .retrieve()
                .bodyToFlux<Order>()
                .asFlow()
                .toList()
        }
        Profile(user.await(), orders.await())
    }

    // 스트리밍은 Flow 로 그대로
    fun stream(): Flow<Event> =
        repo.findAllByOrderByIdDesc()          // Flux<Event>
            .asFlow()
            .map { it.copy(seen = true) }
            .onEach { log.debug("이벤트 {}", it.id) }

    // 자바/Reactor 를 쓰는 쪽에 넘길 때만 되돌린다
    fun profileMono(id: Long): Mono<Profile> = mono { profile(id) }
}
변환 지점은 세 곳뿐입니다 — ① 리액티브 리포지터리에서 값을 꺼낼 때, ② WebClient 응답을 받을 때, ③ 프레임워크가 Mono·Flux 를 요구할 때 (스프링은 suspend·Flow를 이미 이해하므로 ③은 드뭅니다). 나머지 코드는 코루틴만 보이게 유지하세요.
FLUX 04

라우팅 — coRouter DSL

WebFlux는 애너테이션 방식과 함수형 라우팅 두 가지를 지원합니다. 코틀린에는 coRouter라는 코루틴용 DSL이 있어, 라우팅 규칙이 한 파일에서 한눈에 보입니다.

coRouter — 라우팅 정의

@Configuration
class OrderRoutes(private val handler: OrderHandler) {

    @Bean
    fun orderRouter() = coRouter {
        "/api/v1/orders".nest {
            accept(MediaType.APPLICATION_JSON).nest {
                GET("", handler::list)
                GET("/{id}", handler::get)
                POST("", handler::create)
                PATCH("/{id}", handler::update)
                DELETE("/{id}", handler::delete)
            }
            // SSE 스트리밍은 별도 accept
            accept(MediaType.TEXT_EVENT_STREAM).nest {
                GET("/stream", handler::stream)
            }
        }

        // 필터 — 이 라우터 전체에 적용
        filter { request, next ->
            val start = System.currentTimeMillis()
            next(request).also {
                log.info("{} {} {}ms", request.method(), request.path(),
                    System.currentTimeMillis() - start)
            }
        }

        onError<DomainException.NotFound> { _, _ ->
            ServerResponse.notFound().buildAndAwait()
        }
    }
}

핸들러 — suspend 함수

@Component
class OrderHandler(private val service: OrderService) {

    suspend fun list(req: ServerRequest): ServerResponse {
        val status = req.queryParamOrNull("status")
        val orders = service.list(status)
        return ServerResponse.ok().bodyValueAndAwait(orders)
    }

    suspend fun get(req: ServerRequest): ServerResponse {
        val id = req.pathVariable("id").toLong()
        val order = service.find(id)
            ?: return ServerResponse.notFound().buildAndAwait()
        return ServerResponse.ok().bodyValueAndAwait(order)
    }

    suspend fun create(req: ServerRequest): ServerResponse {
        val body = req.awaitBody<CreateOrderRequest>()
        val created = service.create(body)

            .bodyValueAndAwait(created)
    }

FLUX 05

WebClient — 코루틴으로

WebFlux 생태계의 HTTP 클라이언트입니다. MVC 프로젝트에서도 쓸 수 있고, 코루틴과 붙이면 await 한 단어로 끝납니다. 

@Configuration
class WebClientConfig {
    @Bean
    fun orderClient(builder: WebClient.Builder): WebClient =
        builder
            .baseUrl("https://api.internal/orders")
            .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
            .clientConnector(
                ReactorClientHttpConnector(
                    HttpClient.create(
                        ConnectionProvider.builder("orders")
                            .maxConnections(200)                       // 커넥션 풀
                            .pendingAcquireTimeout(Duration.ofSeconds(3))
                            .maxIdleTime(Duration.ofSeconds(20))       // 서버 keep-alive 보다 짧게!
                            .build()
                    ).responseTimeout(Duration.ofSeconds(3))
                        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000)
                )
            )
            .filter(ExchangeFilterFunction.ofRequestProcessor { req ->
                Mono.just(ClientRequest.from(req)
                    .header("X-Trace-Id", MDC.get("traceId") ?: "")
                    .build())
            })
            .build()
}

코루틴으로 부르기

@Service
class OrderClient(private val client: WebClient) {

    // 단건
    suspend fun get(id: Long): Order =
        client.get().uri("/{id}", id)
            .retrieve()
            .awaitBody<Order>()

    // 없을 수 있으면
    suspend fun findOrNull(id: Long): Order? =
        client.get().uri("/{id}", id)
            .retrieve()
            .onStatus({ it == HttpStatus.NOT_FOUND }) { Mono.empty() }
            .awaitBodyOrNull<Order>()

    // 목록 스트리밍
    fun stream(userId: Long): Flow<Order> =
        client.get().uri("/stream?userId=$userId")
            .accept(MediaType.TEXT_EVENT_STREAM)
            .retrieve()
            .bodyToFlux<Order>()
            .asFlow()

    // POST
    suspend fun create(req: CreateOrder): Order =
        client.post()
            .bodyValue(req)
            .retrieve()
            .awaitBody<Order>()

    // 응답 전체가 필요할 때 (헤더·상태 코드)
    suspend fun createWithStatus(req: CreateOrder): ResponseEntity<Order> =
        client.post().bodyValue(req).retrieve().awaitEntity<Order>()
}

에러 처리 · 재시도

suspend fun get(id: Long): Order =
    try {
        client.get().uri("/{id}", id)
            .retrieve()
            .onStatus({ it.is4xxClientError }) { res ->
                res.bodyToMono<ProblemDetail>().map { ClientError(it) }
            }
            .awaitBody<Order>()
    } catch (e: WebClientResponseException) {
        log.warn("주문 조회 실패 status={} body={}", e.statusCode, e.responseBodyAsString)
        throw DomainException.Conflict("주문 서비스 오류")
    }

// 재시도는 코루틴 쪽에서 하는 편이 읽기 쉽다
suspend fun getWithRetry(id: Long): Order = retry(times = 3) { get(id) }

// Reactor 연산자로도 가능
client.get().retrieve().bodyToMono<Order>()
    .retryWhen(Retry.backoff(3, Duration.ofMillis(200)).jitter(0.5))
    .awaitSingle()
maxIdleTime을 상대 서버의 keep-alive 보다 짧게 두세요. 서버가 먼저 끊은 커넥션을 재사용하면 PrematureCloseException이 간헐적으로 발생합니다 — WebClient 운영에서 가장 흔한 이슈입니다.
Spring 6 의 RestClient 와 비교 — RestClient는 블로킹이지만 WebClient 와 거의 같은 API 를 제공합니다. MVC + 가상 스레드 조합이라면 RestClient가 더 단순합니다. WebFlux 환경이거나 스트리밍이 필요하면 WebClient입니다.
FLUX 06

R2DBC — 논블로킹 DB 접근

WebFlux 의 이점을 실제로 얻으려면 DB 접근도 논블로킹이어야 합니다. R2DBC 는 그 자리를 채우지만, JPA 가 해 주던 것들을 스스로 해야 합니다.

엔티티와 리포지터리

// R2DBC 는 JPA 가 아니다 — 지연 로딩·영속성 컨텍스트·연관관계가 없다
@Table("orders")
data class Order(
    @Id val id: Long? = null,              // null 이면 INSERT, 값이 있으면 UPDATE
    val userId: Long,
    val status: String,
    val totalAmount: Long,
    @Column("created_at") val createdAt: LocalDateTime = LocalDateTime.now(),
)

// data class 를 그대로 써도 된다 (JPA 와 달리 프록시가 없다)

interface OrderRepository : CoroutineCrudRepository<Order, Long> {
    // 코루틴 리포지터리 — 반환이 suspend / Flow 다
    suspend fun findByIdAndUserId(id: Long, userId: Long): Order?
    fun findByUserIdOrderByIdDesc(userId: Long): Flow<Order>

    @Query("SELECT * FROM orders WHERE status = :status AND created_at >= :from")
    fun findRecent(status: String, from: LocalDateTime): Flow<Order>

    @Modifying
    @Query("UPDATE orders SET status = :status WHERE id = :id")
    suspend fun updateStatus(id: Long, status: String): Int
}

서비스에서 쓰기 · 연관 데이터

@Service
class OrderService(
    private val orders: OrderRepository,
    private val items: OrderItemRepository,
    private val template: R2dbcEntityTemplate,
) {
    suspend fun get(id: Long): OrderDetail = coroutineScope {
        val order = async { orders.findById(id) ?: throw NotFound(id) }
        val itemList = async { items.findByOrderId(id).toList() }
        OrderDetail(order.await(), itemList.await())   // 연관은 '직접 조회해서 조립'
    }

    // 동적 쿼리는 Criteria 로
    suspend fun search(status: String?, minAmount: Long?): List<Order> {
        var criteria = Criteria.empty()
        status?.let { criteria = criteria.and("status").`is`(it) }
        minAmount?.let { criteria = criteria.and("total_amount").greaterThanOrEquals(it) }
        return template.select(Order::class.java)
            .matching(Query.query(criteria).limit(100))
            .flow()
            .toList()
    }
}
JPA 에서 하던 것R2DBC 에서는
연관관계 매핑 · 지연 로딩없다 — 각각 조회해 코드에서 조립
영속성 컨텍스트 · 더티 체킹없다 — 바꾼 뒤 save()를 명시
N+1 문제대신 루프 안 조회를 조심 — findAllById로 묶기
QueryDSL 동적 쿼리Criteria · jOOQ(R2DBC 지원) 사용
@TransactionalTransactionalOperator · @Transactional(리액티브 매니저)
스키마 자동 생성없다 — Flyway·Liquibase 로 관리 (JDBC 로 실행)
2차 캐시없다 — 애플리케이션 캐시(Caffeine·Redis)로 직접
R2DBC 는 “JPA 의 리액티브 버전”이 아닙니다. 오히려 JdbcTemplate 에 가깝습니다. 도메인이 복잡하고 연관이 많은 업무 시스템이라면, JPA + MVC(가상 스레드)가 생산성 면에서 훨씬 나은 선택인 경우가 많습니다.
FLUX 07

리액티브 트랜잭션

리액티브 트랜잭션은 ThreadLocal 이 아니라 구독 컨텍스트를 따라다닙니다. 코루틴에서는 TransactionalOperator의 코루틴 확장을 쓰면 자연스럽게 이어집니다. 

@Service
class OrderService(
    private val orders: OrderRepository,
    private val items: OrderItemRepository,
    private val tx: TransactionalOperator,        // 주입
) {
    // 방법 1 — 코루틴 확장 (권장)
    suspend fun place(cmd: PlaceOrderCommand): Order = tx.executeAndAwait {
        val order = orders.save(Order(userId = cmd.userId, status = "NEW", totalAmount = cmd.total))
        cmd.items.forEach { items.save(it.toEntity(order.id!!)) }
        order
    }

    // 방법 2 — @Transactional 도 동작한다 (ReactiveTransactionManager 가 있을 때)
    @Transactional
    suspend fun cancel(id: Long) {
        val order = orders.findById(id) ?: throw NotFound(id)
        orders.save(order.copy(status = "CANCELED"))
        items.deleteByOrderId(id)
    }

    // 읽기 전용
    @Transactional(readOnly = true)
    suspend fun get(id: Long): Order? = orders.findById(id)
}

주의할 점

  • 같은 커넥션을 쓰는 작업만 하나의 트랜잭션입니다. async로 병렬 실행하면 다른 커넥션이 되어 같은 트랜잭션이 아닙니다
  • 중첩 트랜잭션·REQUIRES_NEW는 제약이 큽니다 — JPA 만큼 자유롭지 않습니다
  • 블로킹 작업이 섞이면 커넥션을 잡은 채 이벤트 루프가 막힙니다
  • 여러 서비스에 걸친 일관성이 필요하면 사가·아웃박스 패턴으로 (대규모 트래픽 탭에서 다룹니다)

트랜잭션 안에서 병렬 처리하기

// ❌ 트랜잭션이 갈라진다
tx.executeAndAwait {
    coroutineScope {
        launch { orders.save(a) }      // 다른 커넥션일 수 있다
        launch { items.save(b) }
    }
}

// ✅ 트랜잭션 안에서는 순차로, 병렬은 트랜잭션 밖에서
val (userInfo, coupon) = coroutineScope {
    async { userClient.get(id) } to async { couponClient.get(code) }
}.let { (a, b) -> a.await() to b.await() }

tx.executeAndAwait {
    orders.save(order)                  // 여기는 순차
    items.saveAll(itemList).collect()
}
FLUX 08

스트리밍 — SSE · NDJSON

WebFlux 를 쓰는 가장 확실한 이유입니다. 결과를 다 모으지 않고 오는 대로 흘려보내면 첫 응답이 빨라지고 메모리도 아낍니다.

스트리밍이 바꾸는 것은 총 시간이 아니라 첫 응답까지의 시간과 메모리입니다.

서버 — Flow 를 그대로 반환

@RestController
class EventController(private val service: EventService) {

    // Server-Sent Events
    @GetMapping("/api/events", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
    fun events(@RequestParam userId: Long): Flow<ServerSentEvent<EventDto>> =
        service.stream(userId)
            .map { e ->
                ServerSentEvent.builder(e)
                    .id(e.id.toString())
                    .event("order-update")
                    .build()
            }
            .onStart { log.info("스트림 시작 user={}", userId) }
            .onCompletion { log.info("스트림 종료 user={}", userId) }

    // NDJSON — 줄 단위 JSON (대용량 내보내기에 좋다)
    @GetMapping("/api/export", produces = [MediaType.APPLICATION_NDJSON_VALUE])
    fun export(): Flow<OrderRow> = service.exportAll()      // 100만 건도 메모리 안전

    // 하트비트 — 프록시가 유휴 커넥션을 끊지 못하게
    @GetMapping("/api/live", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
    fun live(): Flow<ServerSentEvent<String>> = merge(
        service.stream(0).map { ServerSentEvent.builder(it.toString()).build() },
        flow { while (true) { delay(15.seconds); emit(ServerSentEvent.builder("ping").comment("hb").build()) } },
    )
}

브로드캐스트 — SharedFlow 로

@Service
class EventService : DisposableBean {
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)

    private val _events = MutableSharedFlow<EventDto>(
        replay = 0, extraBufferCapacity = 256,
        onBufferOverflow = BufferOverflow.DROP_OLDEST,   // 느린 구독자 때문에 막히지 않게
    )

    fun publish(e: EventDto) { _events.tryEmit(e) }

    fun stream(userId: Long): Flow<EventDto> =
        _events.filter { it.userId == userId }

    override fun destroy() = scope.cancel()
}

// 여러 서버 인스턴스로 확장하려면 Redis Pub/Sub 을 앞에 둔다
// (한 인스턴스에 붙은 구독자에게만 전달되면 안 되므로)
느린 소비자를 반드시 고려하세요. 버퍼 정책이 없으면 구독자 하나가 느릴 때 서버 메모리가 계속 쌓입니다. DROP_OLDEST·conflate()·타임아웃 중 하나는 있어야 합니다.
클라이언트 쪽 — 브라우저는 EventSource로 SSE 를 바로 받습니다. 안드로이드·서버 간 통신이라면 WebClient 의 bodyToFlux+asFlow()로 받으면 됩니다. 연결이 끊겼을 때 마지막 이벤트 id 부터 재개(Last-Event-ID)하는 설계를 같이 하세요.
FLUX 09

WebSocket — 양방향 실시간

채팅·실시간 협업·게임 로비처럼 서버가 먼저 말을 걸어야 하는 기능입니다. WebFlux 에서는 세션 하나가 Flow 두 개(수신·송신)로 표현됩니다. 

@Component
class ChatHandler(private val room: ChatRoom) : WebSocketHandler {

    override fun handle(session: WebSocketSession): Mono<Void> = mono {
        val userId = session.handshakeInfo.uri.query
            ?.substringAfter("userId=")?.toLongOrNull()
            ?: return@mono session.close(CloseStatus.POLICY_VIOLATION).awaitFirstOrNull()

        coroutineScope {
            // 수신 — 클라이언트가 보낸 메시지
            val incoming = launch {
                session.receive().asFlow()
                    .map { it.payloadAsText }
                    .collect { text -> room.publish(ChatMessage(userId, text)) }
            }

            // 송신 — 방의 브로드캐스트를 이 세션으로
            val outgoing = launch {
                session.send(
                    room.messages()                       // Flow<ChatMessage>
                        .map { session.textMessage(it.toJson()) }
                        .asFlux()
                ).awaitFirstOrNull()
            }

            incoming.join()                                // 연결이 끊기면
            outgoing.cancel()                              // 송신도 정리
        }
        null
    }
}

@Configuration
class WebSocketConfig {
    @Bean
    fun handlerMapping(chat: ChatHandler) = SimpleUrlHandlerMapping(
        mapOf("/ws/chat" to chat), Ordered.HIGHEST_PRECEDENCE
    )
}

방(Room) 구현 — SharedFlow

@Component
class ChatRoom {
    private val _messages = MutableSharedFlow<ChatMessage>(
        replay = 20,                       // 새로 들어온 사람에게 최근 20개
        extraBufferCapacity = 256,
        onBufferOverflow = BufferOverflow.DROP_OLDEST,
    )
    fun messages(): Flow<ChatMessage> = _messages.asSharedFlow()
    suspend fun publish(m: ChatMessage) = _messages.emit(m)
}
서버가 여러 대면 이 방식은 한 인스턴스 안에서만 동작합니다. Redis Pub/Sub 이나 Kafka 를 앞에 두어 인스턴스 간 브로드캐스트를 해야 합니다 — 대규모 트래픽 탭에서 구조를 다룹니다.

운영에서 챙길 것

  • 인증 — 핸드셰이크 시점에 토큰 검증 (쿼리 파라미터·서브프로토콜 헤더)
  • 하트비트 — 유휴 커넥션을 프록시가 끊습니다. 핑/퐁 주기 설정
  • 재연결 — 클라이언트가 지수 백오프로 다시 붙게, 서버는 중복 세션 처리
  • 메시지 크기 제한 — maxFramePayloadLength를 넘기면 연결이 끊깁니다
  • 세션 수 지표 — 현재 연결 수를 메트릭으로 노출 (용량 산정의 기준)
  • 느린 클라이언트 — 송신 버퍼가 차면 끊거나 버려야 합니다
FLUX 10

복원력 — 타임아웃 · 재시도 · 서킷

게이트웨이 성격의 서비스일수록 남의 장애가 내 장애가 되는 구조입니다. 코루틴 기반으로 타임아웃 예산 · 재시도 · 서킷 브레이커를 겹쳐 씁니다.

세 장치는 겹쳐 써야 의미가 있습니다 — 하나만 쓰면 대부분 상황에서 부족합니다.
// resilience4j + 코루틴 (resilience4j-kotlin 모듈)
@Service
class PricingClient(
    private val client: WebClient,
    registry: CircuitBreakerRegistry,
) {
    private val cb = registry.circuitBreaker("pricing")

    suspend fun price(productId: Long): Long =
        withTimeoutOrNull(2.seconds) {                  // ① 예산
            cb.executeSuspendFunction {                  // ② 서킷
                retry(times = 2, initialDelay = 100.milliseconds) {   // ③ 재시도
                    client.get().uri("/price/$productId")
                        .retrieve().awaitBody<PriceResponse>().amount
                }
            }
        } ?: cachedPrice(productId)                      // 폴백

설정 예시

resilience4j:
  circuitbreaker:
    instances:
      pricing:
        slidingWindowSize: 50
        failureRateThreshold: 50          # 50% 실패면 열린다
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 5
        slowCallDurationThreshold: 1s
        slowCallRateThreshold: 80
  timelimiter:
    instances:
      pricing:
        timeoutDuration: 2s

폴백을 설계하는 법

  • 축소된 응답 — 추천 목록이 없으면 인기 상품으로 대체
  • 캐시된 마지막 값 — 가격·환율처럼 조금 오래돼도 되는 값
  • 기능 끄기 — 부가 기능이면 아예 빼고 200 을 돌려준다
  • 실패를 그대로 전달 — 결제처럼 거짓 성공이 더 위험한 경우
폴백이 없으면 서킷 브레이커의 의미가 절반입니다. “빨리 실패”만 하고 사용자에게 줄 것이 없다면 결국 에러 화면입니다.
FLUX 11

컨텍스트 전파 · 디버깅

리액티브에서 가장 답답한 순간은 스택 트레이스에 내 코드가 없을 때입니다. 코틀린 코루틴을 쓰면 크게 나아지지만, traceId 전파는 여전히 설정이 필요합니다.

traceId — 요청 전 구간에 유지

// WebFlux 필터에서 심는다 (서블릿 필터가 아니다)
@Component
class TraceIdFilter : WebFilter {
    override fun filter(exchange: ServerWebExchange, chain: WebFilterChain): Mono<Void> {
        val traceId = exchange.request.headers.getFirst("X-Trace-Id")
            ?: UUID.randomUUID().toString().take(8)
        exchange.response.headers.set("X-Trace-Id", traceId)
        return chain.filter(exchange)
            .contextWrite { it.put("traceId", traceId) }     // Reactor 컨텍스트
    }
}

// 코루틴에서 읽기 — Reactor 컨텍스트가 코루틴 컨텍스트로 이어진다
suspend fun currentTraceId(): String? =
    currentCoroutineContext()[ReactorContext]?.context?.getOrDefault("traceId", null)

테스트 — WebTestClient · Turbine

WebFlux 테스트는 WebTestClient가 중심입니다. Flow 는 Turbine, Reactor 타입은 StepVerifier로 검증합니다. 

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureWebTestClient
class OrderApiTest(@Autowired val client: WebTestClient) {

    @Test
    fun `주문을 생성한다`() {
        client.post().uri("/api/v1/orders")
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue(CreateOrderRequest(productId = 1, quantity = 2))
            .exchange()
            .expectStatus().isCreated
            .expectHeader().exists("Location")
            .expectBody<OrderResponse>()
            .consumeWith { assertEquals(24_000, it.responseBody?.totalAmount) }
    }

    @Test
    fun `스트림은 이벤트를 순서대로 보낸다`() {
        val events = client.get().uri("/api/events?userId=1")
            .accept(MediaType.TEXT_EVENT_STREAM)
            .exchange()
            .expectStatus().isOk
            .returnResult<EventDto>()
            .responseBody

        StepVerifier.create(events.take(3))
            .expectNextMatches { it.type == "created" }
            .expectNextCount(2)
            .thenCancel()
            .verify(Duration.ofSeconds(5))
    }
}

FLUX 13

운영 · 튜닝

WebFlux 운영에서 실제로 문제가 되는 것은 대개 스레드가 아니라 메모리와 커넥션입니다. Netty 의 다이렉트 메모리, 커넥션 풀, 파일 디스크립터를 봐야 합니다.

항목설정과 기준
이벤트 루프 스레드 수reactor.netty.ioWorkerCount — 기본 CPU 코어 수. 거의 안 바꾼다
다이렉트 메모리-XX:MaxDirectMemorySize — Netty 버퍼가 쓴다. OOMKilled 의 흔한 원인
커넥션 풀maxConnections · pendingAcquireTimeout — 대상 서비스별로 분리
유휴 커넥션maxIdleTime을 상대 keep-alive 보다 짧게
파일 디스크립터ulimit -n — 커넥션 수만큼 필요. 컨테이너 기본값이 낮은 경우가 많다
요청 본문 크기spring.codec.max-in-memory-size — 기본 256KB. 큰 JSON 은 여기서 막힌다
메모리 누수-Dio.netty.leakDetection.level=paranoid (개발에서만)
네이티브 트랜스포트리눅스면 netty-transport-native-epoll — 성능 이득

지표로 볼 것

  • 이벤트 루프 지연 — 루프가 막히고 있는지의 직접 증거
  • 커넥션 풀 사용률·대기 시간 — reactor.netty.connection.provider.*
  • 다이렉트 메모리 사용량 — 힙과 별도로 봐야 한다
  • p99 지연 · 활성 커넥션 수 — 용량 산정의 기준
  • 취소율 — 클라이언트가 끊는 비율이 높으면 타임아웃 설계를 재검토

흔한 장애 유형

증상원인
간헐적 502·PrematureClose유휴 커넥션 재사용 — maxIdleTime 조정
부하 시 지연 폭발블로킹 호출이 이벤트 루프에 — BlockHound
OOMKilled (힙은 여유)다이렉트 메모리 — 크기 지정·버퍼 릴리스 확인
PoolAcquireTimeout커넥션 풀 부족 또는 응답 지연 — 타임아웃과 함께 조정
대용량 요청 실패max-in-memory-size 초과
FLUX 14

선택 기준 · 체크리스트

이 탭의 결론입니다 — 무엇을 고를지와 고른 뒤 무엇을 지킬지.

상황권장
일반 CRUD + JPAMVC (+ 가상 스레드) — WebFlux 이득이 거의 없다
외부 API 여러 개 조합MVC + suspend 컨트롤러 + WebClient
SSE·WebSocket·롱폴링WebFlux — 커넥션 유지 비용이 결정적
게이트웨이·프록시WebFlux (Spring Cloud Gateway)
대용량 스트리밍 내보내기WebFlux + NDJSON
전 구간 논블로킹 가능WebFlux + R2DBC
팀에 리액티브 경험 없음MVC 로 시작 — 필요한 모듈만 WebFlux 로 분리

WebFlux 를 쓰기로 했다면

  • 코드는 코루틴 스타일로, Reactor 는 경계에서만
  • 블로킹 라이브러리를 클래스패스에서 확인 — JDBC·동기 HTTP·파일 IO
  • 불가피한 블로킹은 별도 디스패처로 격리 (Dispatchers.IO)
  • BlockHound를 개발·CI 에 켜기
  • 모든 외부 호출에 타임아웃 + 폴백
  • 스트리밍에는 버퍼 정책(느린 소비자 대비)
  • 커넥션 풀·다이렉트 메모리 지표를 대시보드에

자주 하는 실수

  • Mono 를 구독하지 않고 버리기 — 아무 일도 일어나지 않는다
  • block() 호출 — 이벤트 루프에서 부르면 예외 또는 데드락
  • subscribeOn으로 블로킹을 감쌌다고 안심 — 스레드만 옮겼을 뿐, 풀이 마르면 같다
  • WebFlux + JPA — 가장 흔한 잘못된 조합
  • flow 안에서 withContext — 컨텍스트 보존 위반, flowOn을 쓸 것
  • 취소 예외를 에러 로그로 — 클라이언트 이탈이 에러로 집계된다
다음 탭 예고 — 데이터 · JPA에서는 코틀린 엔티티 설계의 함정(data class·equals·지연 로딩), QueryDSL 대안, Exposed·jOOQ 같은 코틀린 친화 도구, 그리고 트랜잭션과 성능을 다룹니다.
