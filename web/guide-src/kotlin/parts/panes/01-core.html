KOTLIN 01

코틀린을 실행하는 법

코틀린은 JDK 위에서 도는 언어입니다. 자바를 지우고 시작하는 게 아니라, 쓰던 자바 프로젝트에 .kt 파일 하나를 섞어 넣는 것부터 시작할 수 있습니다.

한 문단 요약

2011년 젯브레인스(IntelliJ를 만든 회사)가 공개했고, 2017년 안드로이드 공식 언어, 2019년부터는 안드로이드 권장 언어가 됐습니다. JVM 바이트코드로 컴파일되므로 자바 라이브러리를 그대로 씁니다 — 스프링·JPA·Jackson·Netty 전부 코틀린에서 부를 수 있습니다.

그래서 도입 비용이 낮습니다. 자바 파일과 코틀린 파일이 같은 모듈 안에 섞여 있어도 컴파일이 됩니다. 새 클래스만 코틀린으로 쓰고 기존 코드는 그대로 두는 방식이 실무에서 가장 흔한 전환 경로입니다.

이 언어를 왜 쓰나 — 네 가지

얻는 것구체적으로
null 안전NPE가 컴파일 에러로 앞당겨집니다. 운영 장애 원인 1위를 문법이 막습니다
짧아짐DTO·getter·setter·builder가 사라집니다. 같은 기능이 대략 30~40% 적은 줄
코루틴비동기 코드를 동기처럼 씁니다. 콜백·CompletableFuture 지옥이 없습니다
한 코드 여러 곳서버·안드로이드·iOS·웹을 같은 코드베이스로 (KMP)
줄 수가 줄어드는 게 본질은 아닙니다 — 줄어든 자리가 대부분 실수가 나던 자리(equals 빠뜨림, null 검사 누락, 빌더 필드 누락)라는 게 핵심입니다.
코드 한 벌이 서버 · 안드로이드 · iOS · 웹으로 나갑니다 — 이 가이드는 네 갈래를 모두 다룹니다.

설치 — 세 가지만 있으면 됩니다

1. JDK 17 이상

# macOS · Linux (SDKMAN 권장)
sdk install java 21-tem
sdk install java 25-tem   # 최신 LTS

# Windows
winget install EclipseAdoptium.Temurin.21.JDK

java -version   # 확인

코틀린 자체는 JDK 8부터 돌지만, 스프링 부트 4가 JDK 17+를 요구합니다. 새로 시작한다면 21 또는 25를 고르세요.

2. IntelliJ IDEA

코틀린을 만든 회사가 만든 IDE라 지원 수준이 다릅니다. Community 판(무료)으로 충분하고, 코틀린 플러그인은 기본 내장입니다.

자바 → 코틀린 자동 변환이 있습니다. 자바 코드를 복사해 .kt 파일에 붙여 넣으면 변환할지 물어봅니다 (Ctrl+Alt+Shift+K). 배우는 데 가장 좋은 도구입니다 — 내가 아는 자바 코드가 코틀린으로 어떻게 바뀌는지 바로 보입니다.

3. Gradle (Kotlin DSL)

# 새 프로젝트는 IDE 마법사가
# gradlew 까지 만들어 줍니다.
./gradlew build    # 빌드 + 테스트
./gradlew run      # 실행
./gradlew --stop   # 데몬 재시작 (버전 꼬임 해결)

빌드 스크립트도 코틀린으로 씁니다(build.gradle.kts). 오타를 IDE가 잡아 주고 자동완성이 됩니다.

첫 코드 — 자바와 나란히

자바
// Hello.java — 파일명 = 클래스명
public class Hello {
    public static void main(String[] args) {
        System.out.println("안녕하세요");
    }
}

클래스로 감싸야 하고, public static void를 외워야 합니다.

코틀린
// Hello.kt — 파일명 자유. 클래스도 필요 없다
fun main() {
    println("안녕하세요")
}

최상위 함수가 됩니다. 컴파일하면 HelloKt 클래스가 자동으로 만들어지고 그 안의 static 메서드가 됩니다 — 자바와의 호환은 그대로입니다.

빌드 파일 — build.gradle.kts

// build.gradle.kts — 코틀린 JVM 프로젝트의 최소 형태
plugins {
    kotlin("jvm") version "2.2.0"          // 코틀린 컴파일러 플러그인
    application                             // ./gradlew run 을 쓰려면
}

repositories { mavenCentral() }

kotlin {
    jvmToolchain(21)      // 내 PC 에 21이 없어도 Gradle 이 받아 씁니다
}

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.10.2")
    testImplementation(kotlin("test"))
}

application { mainClass.set("com.example.MainKt") }   // 최상위 main 은 파일명 + Kt

tasks.test { useJUnitPlatform() }

기존 자바 프로젝트에 얹기

// 이미 있는 자바 Gradle 프로젝트라면 이 두 줄이면 끝
plugins {
    java
    kotlin("jvm") version "2.2.0"    // ← 추가
}

// src/main/java 와 src/main/kotlin 이 함께 컴파일된다.
// (코틀린 플러그인이 java 소스 폴더도 같이 봐 준다)
컴파일 순서가 재미있습니다 — 코틀린 컴파일러가 자바 소스를 먼저 읽고(컴파일은 하지 않음) 코틀린을 컴파일한 뒤, javac 가 그 결과물을 보고 자바를 컴파일합니다. 그래서 서로를 참조해도 됩니다.

버전 — 무엇이 언제 바뀌었나

버전무엇이 들어왔나
1.3코루틴 정식(2018). 그 전에는 실험 기능이었습니다
1.5value class · sealed interface
1.9구 컴파일러의 마지막. 지금도 레거시 프로젝트에 많습니다
2.0K2 컴파일러 기본 탑재(2024). 컴파일이 눈에 띄게 빨라지고 타입 추론이 정확해졌습니다
2.1~2.2when의 가드 조건, 비지역 break·continue, 컨텍스트 파라미터

새로 시작하면 2.x. 버전은 계속 오르므로 프로젝트를 만들 때 공식 릴리스 노트에서 최신 안정판을 확인하세요.

흔한 첫 실수 — 자바 프로젝트에 코틀린을 넣고 src/main/kotlin 폴더를 안 만들면 IDE가 파일을 알아보지 못합니다. 그리고 Gradle 데몬이 옛 코틀린 버전을 물고 있는 경우가 있어, 버전을 올린 뒤 설명 없는 에러가 나면 ./gradlew --stop 한 번이 답일 때가 많습니다.
KOTLIN 02

val · var · 타입

코틀린의 기본값은 “안 바뀐다”입니다. 변수도, 컬렉션도, 클래스도 — 바꾸고 싶으면 바꾸겠다고 적어야 합니다. 이 방향이 언어 전체를 관통합니다.

val — 다시 대입할 수 없는 이름

val name = "김현우"      // 타입 생략 — String 으로 추론
val age: Int = 34        // 적어도 된다
// name = "다른 이름"     // ❌ 컴파일 에러

var count = 0            // 바뀔 값만 var
count += 1               // ✅

// val 은 '내용이 불변'이 아니라 '다시 대입 불가' 다
val list = mutableListOf(1, 2)
list.add(3)              // ✅ 내용은 바뀐다
// list = mutableListOf() // ❌ 대입은 안 된다

자바의 final과 같은 자리지만, 기본으로 쓰게 만든 것이 차이입니다. val 이 먼저 손에 익으면 “이 값이 아래에서 바뀌었나?”를 확인하러 위로 올라가는 일이 사라집니다.

타입 추론 — 어디까지 생략하나

val a = 1                 // Int
val b = 1L                // Long
val c = 1.0               // Double
val d = 1.0f              // Float
val e = 'A'               // Char  (작은따옴표)
val f = "A"               // String(큰따옴표)
val g = true              // Boolean
val h = listOf(1, 2, 3)   // List<Int>
val i = mapOf("a" to 1)   // Map<String, Int>

// 함수 반환 타입은 '적는 편'이 낫다 (공개 API)
fun total(a: Int, b: Int): Int = a + b
기준 — 지역 변수는 생략, public 함수의 반환 타입은 명시. 추론에 맡기면 안쪽 구현을 고쳤을 때 공개 시그니처가 조용히 바뀝니다.

숫자 — 자동 형변환이 없습니다

자바 — 알아서 넓혀 준다
int i = 10;
long l = i;        // ✅ 자동 확대
double d = l;      // ✅

// 대신 이런 사고가 난다
int a = 1_000_000;
int b = a * 3000;  // 오버플로 (조용히 음수)
코틀린 — 직접 바꿔야 한다
val i: Int = 10
// val l: Long = i     // ❌ 컴파일 에러
val l: Long = i.toLong()   // ✅ 명시
val d: Double = l.toDouble()

// 리터럴은 문맥으로 판단해 준다
val ok: Long = 10          // ✅ 리터럴은 허용

왜 불편하게 만들었나 — 자바에서 int가 long으로, float이 double로 조용히 바뀌면서 생기는 정밀도 손실과 오버플로가 실제 금액 계산 사고의 단골이기 때문입니다. 코틀린은 바꾸는 지점을 코드에 남기게 합니다.

숫자 리터럴과 표기

val big = 1_000_000_000L    // 밑줄로 자릿수 구분
val hex = 0xFF              // 16진수 = 255
val bin = 0b1010_1010       // 2진수
val f   = 3.14f             // Float
val u   = 42u               // UInt (부호 없는 정수)

// 나눗셈 — 정수끼리는 정수 나눗셈
println(7 / 2)      // 3    (자바와 같다)
println(7 / 2.0)    // 3.5
println(7 % 2)      // 1

// 금액은 Long(원 단위) 또는 BigDecimal
val price: Long = 12_900L
val exact = java.math.BigDecimal("0.1") + java.math.BigDecimal("0.2")
println(exact)      // 0.3   (Double 이면 0.30000000000000004)

문자열 → 숫자, 안전하게

val ok  = "42".toInt()          // 42
// val no = "사십이".toInt()     // 💥 NumberFormatException

// 실패를 null 로 받는다 — 코틀린식
val n: Int? = "사십이".toIntOrNull()   // null
val safe = "사십이".toIntOrNull() ?: 0 // 0

// 실무: 쿼리 파라미터 파싱
fun page(raw: String?): Int =
    raw?.toIntOrNull()?.coerceAtLeast(1) ?: 1

println(page("3"))     // 3
println(page("abc"))   // 1
println(page(null))    // 1
...OrNull() 계열을 먼저 찾으세요. toIntOrNull·firstOrNull·singleOrNull· maxOrNull — 코틀린 표준 라이브러리의 일관된 규칙입니다.

Any · Unit · Nothing — 세 개의 특별한 타입

Nothing은 “절대 정상 반환하지 않는다”는 뜻입니다 — throw와 무한 루프의 타입입니다.

Any — 최상위

val x: Any = 42
val y: Any = "hello"
// Any 에는 equals·hashCode·
// toString 만 있다

// null 까지 담으려면 Any?
val z: Any? = null

자바의 Object 자리. 다만 Any는 null을 못 담습니다.

Unit — void 자리

fun log(m: String): Unit {
    println(m)
}
// Unit 은 생략 가능
fun log2(m: String) = println(m)

// void 와 다른 점: Unit 은 '값'이다
val u: Unit = log("hi")

값이라서 제네릭에 넣을 수 있습니다 — List<Unit>도 됩니다.

Nothing — 돌아오지 않음

fun fail(m: String): Nothing =
    throw IllegalStateException(m)

// 그래서 이게 컴파일된다
val name: String = user.name
    ?: fail("이름 없음")
// fail 이 Nothing 이라
// 아래로는 절대 안 내려온다

컴파일러에게 “여기서 끝”을 알려 주는 타입입니다.

상수 · 최상위 선언

// Config.kt — 클래스 없이 최상위에 둘 수 있다
const val MAX_RETRY = 3            // 컴파일 시점 상수 (자바의 static final)
val START_TIME = System.currentTimeMillis()   // 런타임에 정해짐 → const 불가

object AppConfig {                 // 묶어 두고 싶으면 object
    const val TIMEOUT_MS = 3_000L
    val allowedHosts = listOf("a.com", "b.com")
}

fun main() {
    println(MAX_RETRY)             // 그냥 이름으로 접근
    println(AppConfig.TIMEOUT_MS)
}
const val은 세 곳에만 쓸 수 있습니다 — 최상위 · object 안 · companion object 안. 그리고 기본 타입과 String만 됩니다. 컴파일 시점에 값이 코드에 박히기 때문입니다(자바의 static final과 같은 성질 — 라이브러리로 배포하면 쓰는 쪽을 다시 컴파일해야 값이 바뀝니다).
KOTLIN 03

null 안전성 — 코틀린의 심장

코틀린이 자바와 갈라지는 가장 큰 지점입니다. 타입에 ?가 없으면 그 값은 절대 null이 아닙니다 — 런타임 약속이 아니라 컴파일러가 강제하는 사실입니다.

같은 일을 하지만 비용을 치르는 시점이 다릅니다 — 이것이 코틀린 도입의 가장 큰 실익입니다.

타입 두 종류 — String과 String?

var a: String = "hello"
// a = null            // ❌ 컴파일 에러: Null can not be a value of a non-null type String

var b: String? = "hello"
b = null               // ✅ 허용

println(a.length)      // ✅ 바로 접근 가능 (null 일 수 없으니)
// println(b.length)   // ❌ 컴파일 에러: b 는 null 일 수 있다
println(b?.length)     // ✅ null 이면 통째로 null (Int? 반환)

네 가지 연산자 — 이것만 알면 끝

기호이름 · 뜻
?.안전 호출 — null이면 호출하지 않고 null 반환
?:엘비스 — 왼쪽이 null이면 오른쪽 값 사용 (기본값)
!!단언 — “null 아님” 강제. null이면 즉시 NPE
?.letnull이 아닐 때만 블록 실행

?:가 엘비스 연산자인 이유 — 옆으로 눕혀 보면 엘비스 프레슬리의 머리 모양이라서입니다. 농담이 아니라 공식 명칭입니다.

실제로 쓰는 모양

val user: User? = repo.find(id)

// 1) 체인 — 중간에 null 이면 전체가 null
val city: String? = user?.address?.city

// 2) 기본값
val name: String = user?.name ?: "이름없음"

// 3) 없으면 예외 (엘비스 + throw)
val u: User = user ?: throw NotFoundException(id)

// 4) 없으면 함수 종료 (엘비스 + return)
fun greet(user: User?): String {
    val n = user?.name ?: return "손님"
    return "$n 님"
}

// 5) 있을 때만 실행
user?.let { sendMail(it.email) }

스마트 캐스트 — 검사하면 타입이 바뀐다

자바 — 검사하고 또 캐스팅
if (obj instanceof String) {
    String s = (String) obj;   // 또 적는다
    System.out.println(s.length());
}

if (name != null) {
    // 그래도 IDE 는 계속 경고
    System.out.println(name.length());
}
코틀린 — 검사하면 그 뒤로 그 타입
if (obj is String) {
    println(obj.length)   // 이미 String 이다
}

if (name != null) {
    println(name.length)  // 이미 String 이다 (String? 아님)
}

// 이른 반환과도 잘 맞는다
fun f(s: String?) {
    if (s == null) return
    println(s.length)     // 아래 전부 String
}
스마트 캐스트가 안 되는 경우 — var 프로퍼티(클래스 멤버)는 검사한 뒤 다른 스레드가 바꿀 수 있어서 컴파일러가 거부합니다 (Smart cast to 'String' is impossible). 지역 val 에 담아서 쓰세요. 
class A(var name: String?) {
    fun f() {
        // if (name != null) println(name.length)  // ❌
        val n = name ?: return                     // ✅ 지역 val 로 고정
        println(n.length)
    }
}

!! 는 언제 쓰나 — “거의 쓰지 않는다”

이렇게 쓰면 코틀린을 자바처럼 쓰는 것

// ❌ 안티패턴 — 컴파일 에러를 지우려고 !! 를 붙임
val name = user!!.name!!.trim()!!

// 문제: 터졌을 때 '어느 !! 인지' 알기 어렵고,

상속 · 인터페이스

코틀린 클래스는 기본이 final입니다. 상속을 허용하려면 open을 직접 붙여야 합니다 — “상속은 설계해서 열거나, 막아야 한다”는 이펙티브 자바의 조언을 문법으로 굳힌 것입니다.

open · override — 둘 다 명시

open class Animal(val name: String) {       // open 없으면 상속 불가
    open fun speak() = "..."                 // open 없으면 재정의 불가
    fun sleep() = "zzz"                      // 재정의 못 함 (final)
}

class Dog(name: String) : Animal(name) {     // : 뒤에 부모 생성자 호출
    override fun speak() = "멍멍"            // override 필수 (자바의 @Override 는 선택)
}

// override 한 것을 더 못 막으려면
open class Puppy(name: String) : Dog(name) {
    final override fun speak() = "왈"        // 여기서 봉인
}

println(Dog("바둑이").speak())   // 멍멍
왜 기본이 final 인가 — 라이브러리 클래스를 남이 마음대로 상속해 버리면 내부 구현을 바꿀 수 없게 됩니다(취약한 기반 클래스 문제). 열어 둔 지점만 계약이 되도록 뒤집은 것입니다.

함수를 값처럼 주고받는 문법입니다. 코틀린에서는 함수가 일급 시민이라 타입에도 쓰고((Int) -> String), 변수에 담고, 인자로 넘깁니다. 

// 람다의 기본 형태 — 중괄호 { 인자 -> 몸통 }
val double: (Int) -> Int = { x -> x * 2 }
println(double(5))       // 10

// 인자가 하나면 이름을 생략하고 it 으로
val triple: (Int) -> Int = { it * 3 }

// 인자가 없으면
val hello: () -> Unit = { println("hi") }

// 여러 인자
val add: (Int, Int) -> Int = { a, b -> a + b }

// 마지막 줄이 반환값 (return 을 쓰지 않는다)
val grade: (Int) -> String = { score ->
    val g = if (score >= 90) "A" else "B"
    "등급: $g"        // ← 이 줄이 반환값
}

후행 람다 — 괄호 밖으로 뺀다

fun repeatN(n: Int, action: (Int) -> Unit) {
    for (i in 0 until n) action(i)
}

// 정석
repeatN(3, { i -> println(i) })

// 마지막 인자가 람다면 괄호 밖으로

nums.forEach { println(it) }

// 이 관례 덕분에 '내장 문법처럼' 보이는 API 가 나온다

고차 함수 만들기 — 반복되는 뼈대를 함수로

// 걸린 시간을 재는 공통 코드
inline fun <T> measured(name: String, block: () -> T): T {
    val start = System.nanoTime()
    try {
        return block()
    } finally {
        val ms = (System.nanoTime() - start) / 1_000_000
        println("[$name] ${ms}ms")
    }
}

val users = measured("사용자 조회") { repo.findAll() }

// 재시도 뼈대
inline fun <T> retry(times: Int = 3, block: (Int) -> T): T {
    var last: Throwable? = null
    repeat(times) { i ->
        try { return block(i) } catch (e: Exception) { last = e }
    }
    throw last!!
}

val body = retry(3) { attempt ->
    println("${attempt + 1}번째 시도")
    httpClient.get("/api/users")
}
inline을 붙인 이유 — 람다를 인자로 받으면 보통 함수 객체가 하나 생깁니다. inline은 컴파일 시점에 람다 본문을 호출 자리에 펼쳐 넣어 그 비용을 없앱니다. 표준 라이브러리의 forEach·let·filter가 전부 inline 입니다. (자세한 동작과 crossinline·reified는 Kotlin 고급 탭에서)

수신 객체가 있는 람다 — DSL의 기반

// String.() -> Unit  : 안에서 this 가 String 이 된다
fun buildMsg(block: StringBuilder.() -> Unit): String =
    StringBuilder().apply(block).toString()

val msg = buildMsg {
    append("안녕")       // this.append — this 생략
    append(" 코틀린")
}

// 이 문법 하나로 아래 같은 '설정 블록'이 만들어진다
// (Gradle KTS · Compose · Ktor 라우팅이 전부 이 원리)
data class Server(var host: String = "", var port: Int = 0)
fun server(block: Server.() -> Unit) = Server().apply(block)

val s = server {
    host = "0.0.0.0"
    port = 8080
}
람다 안의 return에 주의하세요. inline 함수(예: forEach) 안에서 return은 바깥 함수를 종료합니다(비지역 반환). 람다만 빠져나오려면 return@forEach처럼 라벨을 붙입니다. 이 성질은 유용하기도 합니다 — list.forEach { if (bad) return false }처럼 조기 종료를 자연스럽게 쓸 수 있으니까요.

스코프 함수 6종

let · run · with · apply · also — 하는 일이 비슷해 보여 헷갈리지만, 실은 두 가지 축으로 완전히 갈립니다: 안에서 뭐라 부르나(it / this)와 무엇을 돌려주나(자기 자신 / 람다 결과).

“결과가 필요한가, 객체가 필요한가”를 먼저 정하면 왼쪽·오른쪽이 정해집니다.

let — null 검사와 변환

val name: String? = getName()

// null 이 아닐 때만 실행
name?.let { println("이름: $it") }

// 변환 결과를 받는다
val len: Int = name?.let { it.length } ?: 0

// 이름을 붙이면 중첩이 읽기 쉬워진다
user?.let { u ->
    order?.let { o ->
        send(u.email, o.id)
    }
}

// 임시 변수를 없앤다
val ids = repo.findAll()
    .map { it.id }
    .let { idsToCsv(it) }

apply — 만들고 설정해서 돌려받기

// 자바 빌더가 없어도 되는 자리
val props = Properties().apply {
    setProperty("user", "admin")
    setProperty("timeout", "3000")
}

val intent = Intent(this, MainActivity::class.java).apply {
    putExtra("id", 1)
    flags = Intent.FLAG_ACTIVITY_NEW_TASK
}

// 반환값이 '그 객체'라서 바로 대입된다
val user = User().apply {
    name = "김현우"
    age = 34
}

run · with — 값을 계산해 돌려받기

// run: 객체.run { } — 안에서 this 생략, 마지막 줄이 결과
val summary = user.run {
    "$name($age) / $email"      // this. 없이 접근
}

// with: with(객체) { } — 같은 일, 문법만 다르다
val summary2 = with(user) {
    "$name($age) / $email"
}

// run 은 수신 객체 없이도 쓴다 — 지역 스코프 만들기
val config = run {
    val raw = loadFile()
    parse(raw)                  // 이 값이 config
}
// raw 는 밖으로 새지 않는다
run과 with의 차이는 문법뿐입니다. run은 ?.과 함께 쓸 수 있어(null 안전) 실무에서는 run을 더 자주 씁니다.

also · takeIf — 흘려보내며 곁다리 작업

// also: 값은 그대로, 중간에 로그·검증만 끼워 넣는다
val saved = repo.save(order)
    .also { log.info("주문 저장됨 id={}", it.id) }
    .also { metrics.increment("order.created") }

// 체인 중간 디버깅에 특히 좋다
val result = input
    .map { it.trim() }
    .also { println("정제 후: $it") }
    .filter { it.isNotEmpty() }

// takeIf: 조건에 맞으면 자신, 아니면 null
val valid = email.takeIf { it.contains("@") }
    ?: throw IllegalArgumentException("이메일 형식 오류")

// takeUnless: 반대
val nonBlank = input.takeUnless { it.isBlank() }

고르는 기준 — 한 문장씩

함수이럴 때 쓴다
letnull 이 아닐 때만 실행하고 결과를 받는다
run객체 멤버를 여러 번 써서 값 하나를 계산한다
withrun과 같지만 null 안전이 필요 없을 때
apply객체를 설정하고 그 객체를 그대로 쓴다

안티패턴 셋 — ① 중첩 let 3단: 읽기 어려우면 if (a == null) return으로 풀어 쓰세요. ② apply 안에서 값 계산: 반환값이 객체라 계산 결과가 버려집니다 — run을 쓰세요. ③ let 을 “그냥” 붙이기: value.let { it + 1 }은 value + 1보다 나쁩니다. 스코프 함수는 줄이는 도구가 아니라 뜻을 드러내는 도구입니다.

예외 · Result

코틀린에는 checked exception이 없습니다. throws를 적지 않고, 컴파일러가 try-catch를 강제하지도 않습니다. 대신 실패를 값으로 다루는 도구를 줍니다.

기본 — try 도 식이다

// 자바와 같은 모양
try {
    risky()
} catch (e: IllegalStateException) {
    log.warn("실패", e)
} catch (e: Exception) {
    throw ServiceException("처리 실패", e)
} finally {
    cleanup()
}

// 다만 try 가 '값'이다
val n: Int = try {
    input.toInt()
} catch (e: NumberFormatException) {
    0
}

// 여러 예외를 한 번에 잡으려면 (자바의 | 문법이 없다)
try { f() } catch (e: Exception) {
    when (e) {
        is IOException, is TimeoutException -> retry()
        else -> throw e
    }
}

왜 checked exception을 없앴나

자바에서 throws IOException이 강제되자 현장에서 가장 흔해진 코드는 빈 catch 블록이었습니다. 컴파일러를 통과시키려고 예외를 삼켜 버린 것이죠 — 원래 의도와 정반대의 결과입니다. 

// 코틀린은 강제하지 않는다. 대신 '지금 여기서 처리할 수 있나'만 판단하면 된다

    File(path).readText().let { parse(it) }

// 자바에서 이 함수를 부를 때 catch 를 하게 하려면
@Throws(IOException::class)

require · check · error — 표준 검증 3형제

fun transfer(from: Account, to: Account, amount: Long) {
    // require — '인자'가 잘못됨 → IllegalArgumentException
    require(amount > 0) { "금액은 양수여야 합니다: $amount" }

        "VIP" -> 0L
        "NORMAL" -> 500L
        else -> error("알 수 없는 등급: ${from.grade}")
    }

기본 사용

    if (e is TimeoutException) User.GUEST else throw e

주의할 점 두 가지

① runCatching은 CancellationException까지 잡습니다. 코루틴 안에서 쓰면 취소가 먹히지 않는 버그가 됩니다. 코루틴 코드에서는 다시 던지도록 감싸 주세요. 
// 코루틴 안전 버전
suspend fun <T> safeCatching(block: suspend () -> T): Result<T> =
    try { Result.success(block()) }
    catch (e: CancellationException) { throw e }   // 취소는 흘려보낸다
    catch (e: Exception) { Result.failure(e) }
② Result는 반환 타입으로 쓰기 불편합니다. (제약이 있어 fun f(): Result<T>를 막던 시절의 흔적이 남아 있고, 실패 타입이 Throwable로 고정입니다.) 도메인 실패는 sealed 클래스로 표현하는 편이 낫습니다 — 11 · sealed의 OrderError 예시가 그 형태입니다.

커스텀 예외

// 계층을 만들어 두면 상위에서 한 번에 잡을 수 있다
sealed class DomainException(
    message: String,
    cause: Throwable? = null,
) : RuntimeException(message, cause)

class NotFoundException(val id: Long) :
    DomainException("찾을 수 없음: $id")

class DuplicateException(val key: String) :
    DomainException("이미 존재: $key")

// 잡는 쪽
try { service.find(id) }
catch (e: DomainException) { toHttpError(e) }

실무 기준

  • 예상 가능한 실패(입력 오류·재고 없음)는 값으로 — sealed 나 nullable
  • 예상 못 한 실패(DB 끊김·NPE)는 예외로 위로 던지고 전역 핸들러가 잡는다
  • 절대 하지 말 것: catch (e: Exception) {} 빈 블록. 최소한 log.warn(e)는 남기세요
  • e.printStackTrace()는 로그 파일에 안 남습니다 — 로거를 쓰세요
스프링에서는 @RestControllerAdvice 한 곳에서 도메인 예외를 HTTP 상태로 바꾸는 것이 정석입니다 — Spring Boot 탭에서 다룹니다.

실무에서 코틀린을 처음 넣는 곳은 대개 이미 자바로 된 프로젝트입니다. 두 언어가 만나는 지점의 규칙을 알면 파일 하나씩 안전하게 옮길 수 있습니다.

플랫폼 타입 — null 안전성의 구멍

자바 라이브러리와 만나는 얇은 경계층에서 한 번만 검사하면, 안쪽 코드는 다시 안전해집니다.
// 자바: public String getName() { return null; }

val name = javaObj.getName()        // 타입은 String! (플랫폼 타입)
println(name.length)                 // 컴파일은 통과 → 런타임 NPE 💥

// ✅ 경계에서 명시한다
val name2: String? = javaObj.getName()
println(name2?.length ?: 0)          // 이제 컴파일러가 강제한다

// 자바 쪽에 애너테이션이 있으면 코틀린이 알아본다 (권장)
// @Nullable String getName();  → String?
// @NotNull  String getName();  → String
// (org.jetbrains.annotations · javax.annotation · JSpecify 등을 인식)
