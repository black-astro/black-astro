DEEP 01

K2 컴파일러 파이프라인

Kotlin 2.0 의 가장 큰 변화입니다. 프런트엔드가 FIR로 다시 쓰이면서 컴파일이 빨라지고 타입 추론이 정확해졌으며, 모든 타깃이 같은 프런트엔드를 씁니다.

이전에는 타깃마다 프런트엔드가 따로 있어 동작이 미묘하게 달랐습니다 — K2 가 그것을 통일했습니다.

K2 로 좋아진 것들

  • 스마트 캐스트가 더 똑똑해졌습니다 — 이전에 안 되던 상황(람다 안, || 조건 결합 등)에서도 됩니다
  • 컴파일 속도 — 큰 프로젝트에서 체감이 큽니다
  • 일관된 에러 메시지 — 타깃별 차이가 줄었습니다
  • 새 문법의 기반 — 가드 조건·컨텍스트 파라미터가 여기 위에서 나왔습니다

컴파일러 옵션 살펴보기

kotlin {
    compilerOptions {
        // 경고를 에러로 (CI 에서 유용)
        allWarningsAsErrors.set(true)

        // 컨텍스트 파라미터 같은 실험 기능
        freeCompilerArgs.addAll(
            "-Xjsr305=strict",
            "-Xcontext-parameters",
            "-Xjvm-default=all",             // 인터페이스 기본 구현을 자바 default 로
            "-Xlambdas=indy",                // 람다를 invokedynamic 으로 (기본값)
        )
        jvmTarget.set(JvmTarget.JVM_21)
    }
}

// 빌드 리포트로 어느 태스크가 느린지 보기
// ./gradlew build -Pkotlin.build.report.output=file
DEEP 02

코틀린 → 바이트코드

가장 실용적인 학습 도구입니다. Tools → Kotlin → Show Kotlin Bytecode → Decompile 한 번이면 “이 문법이 진짜 무엇인지”가 끝납니다.

data class 가 만드는 것

// 내가 쓴 코드
data class User(val name: String, val age: Int)

// 디컴파일 결과 (자바로 옮기면)
public final class User {
   private final String name;
   private final int age;
   public User(String name, int age) {
      Intrinsics.checkNotNullParameter(name, "name");   // ★ 널 검사가 삽입된다
      this.name = name; this.age = age;
   }
   public final String getName() { return this.name; }
   public final int getAge() { return this.age; }
   public final User copy(String name, int age) { ... }
   public String toString() { return "User(name=" + name + ", age=" + age + ")"; }
   public int hashCode() { return name.hashCode() * 31 + age; }
   public boolean equals(Object other) { ... }
   public final String component1() { return this.name; }
   public final int component2() { return this.age; }
}

확인해 볼 만한 것들

코틀린바이트코드에서 보이는 것
널 안전 파라미터Intrinsics.checkNotNullParameter
?. 체인분기(ifnull)로 펼쳐진다 — 객체 생성 없음
기본 인자foo$default(...) 합성 메서드 + 비트마스크
확장 함수수신 객체를 첫 인자로 받는 static 메서드
inline 함수호출 자리에 본문이 펼쳐져 있다
람다 (비-inline)Function1 구현 클래스 또는 invokedynamic
objectINSTANCE static 필드 + static 초기화
suspendContinuation 인자 + switch(label)
value class사라지고 원시 타입이 직접 쓰인다
// 기본 인자가 만드는 코드 — 왜 자바에서 못 쓰는지 알 수 있다
fun send(to: String, type: String = "일반", retry: Int = 3) { }

// 디컴파일
public static void send(String to, String type, int retry) { }        // 진짜 구현
public static void send$default(String to, String type, int retry,
                                int mask, Object marker) {
    if ((mask & 2) != 0) type = "일반";        // 비트마스크로 '안 넘긴 인자'를 판별
    if ((mask & 4) != 0) retry = 3;
    send(to, type, retry);
}
// 호출부: send$default("a@b.com", null, 0, 6, null)
// → 자바에서 이 시그니처를 직접 부르는 것은 사실상 불가능하다 (그래서 @JvmOverloads)
학습 루틴으로 추천합니다 — 새 문법을 배울 때마다 작은 예제를 만들고 디컴파일해 보세요. 문법이 “마법”에서 “평범한 자바 코드”로 바뀌고, 성능·상호운용에 대한 감각이 함께 생깁니다.
DEEP 03

코루틴 내부 — 디스패치와 스케줄러

상태 기계 변환은 코루틴 탭 19에서 봤습니다. 여기서는 그 다음 — 재개된 코루틴이 어느 스레드에서 어떻게 실행되는지입니다.

Default 와 IO 는 스레드 풀을 공유합니다 — 한도만 다르므로 전환 비용이 작습니다.

디스패치를 건너뛰는 경우

// 이미 올바른 스레드에 있으면 디스패치하지 않는다 (isDispatchNeeded)
withContext(Dispatchers.IO) {
    // 이미 IO 위라면 스레드 전환 없이 그냥 실행된다
}

// Unconfined — 재개한 스레드에서 즉시 이어 실행 (디스패치 없음)
launch(Dispatchers.Unconfined) {
    println(Thread.currentThread().name)   // main
    delay(1)
    println(Thread.currentThread().name)   // kotlinx.coroutines.DefaultExecutor
}

// UNDISPATCHED — 첫 중단점까지는 현재 스레드에서 즉시
launch(start = CoroutineStart.UNDISPATCHED) { println("바로 실행") }

// 성능이 정말 중요한 경로에서는 '전환 횟수'를 줄이는 것이 효과적이다
// (withContext 를 반복 호출하지 말고 한 블록으로 묶기)

코루틴 오버헤드의 실체

  • 객체 생성 — Continuation 인스턴스 하나(수십~수백 바이트)
  • 디스패치 — 큐 삽입 + 워커 깨우기 (전환이 있을 때만)
  • 상태 기계 — switch 분기 하나. 사실상 공짜
실무 감각 — 코루틴 하나 만드는 비용은 수백 나노초 수준입니다. DB 왕복 하나가 수 밀리초인 걸 생각하면 거의 무시할 수 있습니다. “코루틴을 너무 많이 만들면 느려진다”는 걱정보다 블로킹 호출이 섞여 있는지를 먼저 확인하세요.
DEEP 04

람다 · 인라인의 실제 비용

“람다는 객체를 만든다”는 말은 절반만 맞습니다. 인라인 여부, 캡처 여부, invokedynamic 여부에 따라 결과가 완전히 달라집니다. 

// ① 인라인 함수의 람다 — 객체가 생기지 않는다
list.forEach { println(it) }
// 디컴파일하면 그냥 for 루프다:
//   Iterator var = list.iterator();
//   while (var.hasNext()) { System.out.println(var.next()); }

// ② 비-인라인 + 캡처 없음 — 싱글턴으로 재사용된다
val f: (Int) -> Int = { it * 2 }
// invokedynamic (LambdaMetafactory) 로 처리 — 인스턴스 하나만 만들어져 재사용

// ③ 비-인라인 + 캡처 있음 — 호출마다 객체가 생긴다
fun makeAdder(n: Int): (Int) -> Int = { it + n }   // n 을 캡처
// 이 함수를 부를 때마다 새 인스턴스가 생성된다

// ④ 함수 참조 — 캡처 없으면 재사용
list.map(String::length)        // 가볍다
list.map { it.length }          // 같은 결과, 마찬가지로 가볍다

// ⑤ suspend 람다 — Continuation 을 상속한 클래스가 생성된다
launch { doWork() }             // 코루틴 하나당 객체 하나

JMH 로 직접 재기

@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Fork(1) @Warmup(iterations = 5) @Measurement(iterations = 10)
open class CollectionBenchmark {

    private val list = (1..10_000).toList()

    @Benchmark fun forLoop(): Long {
        var sum = 0L
        for (x in list) if (x % 2 == 0) sum += x.toLong() * 2
        return sum
    }

    @Benchmark fun sequence(): Long =
        list.asSequence().filter { it % 2 == 0 }.sumOf { it.toLong() * 2 }

    @Benchmark fun chain(): Long =
        list.filter { it % 2 == 0 }.sumOf { it.toLong() * 2 }
}

// build.gradle.kts: id("me.champeau.jmh")
// ./gradlew jmh

측정하기 전에 알아둘 것

  • JIT 워밍업 — 처음 수천 번은 인터프리터로 돕니다. 워밍업 없는 측정은 무의미합니다
  • 죽은 코드 제거 — 결과를 쓰지 않으면 JIT 가 통째로 지웁니다 (JMH 의 Blackhole이 이걸 막습니다)
  • 이스케이프 분석 — 지역에서만 쓰이는 객체는 아예 할당되지 않을 수 있습니다(스칼라 치환)
  • 결론은 대개 “차이 없음”입니다 — 수천~수만 건에서는 어느 방식이든 마이크로초 단위입니다
가장 흔한 잘못된 최적화 — “람다가 느리니까 for 루프로 바꾸자”. 실제 병목은 거의 항상 IO입니다. 프로파일러로 어디에 시간이 쓰이는지 확인한 뒤 고치세요 (다음 섹션들에서 도구를 다룹니다).
DEEP 05

널 안전성의 런타임 비용

코틀린의 널 안전성은 대부분 컴파일 시점에 처리되지만, 자바와 만나는 경계에는 실제 검사 코드가 들어갑니다. 그 위치와 비용을 봅니다. 

// 공개 함수의 파라미터에는 런타임 검사가 삽입된다
fun process(name: String, user: User) { }

// 디컴파일
public static final void process(String name, User user) {
    Intrinsics.checkNotNullParameter(name, "name");    // 자바에서 null 을 넘기면 여기서 즉시 실패
    Intrinsics.checkNotNullParameter(user, "user");
    // ...
}

// private 함수에는 삽입되지 않는다 (코틀린 안에서만 불리므로 컴파일러가 보장)
private fun internal(name: String) { }   // 검사 없음

// !! 는 이렇게 바뀐다
val x = nullable!!
// → Intrinsics.checkNotNull(nullable)

// 플랫폼 타입을 non-null 로 받으면 그 지점에 검사가 들어간다
val name: String = javaObj.getName()
// → Intrinsics.checkNotNullExpressionValue(...)  ← 여기서 터진다 (좋은 일이다)

비용과 제거

  • 비용은 사실상 0입니다 — JIT 가 대부분 제거하거나 분기 예측이 완벽하게 맞습니다
  • 정말 극한 상황이라면 -Xno-param-assertions·-Xno-call-assertions로 끌 수 있지만, 권하지 않습니다 — 자바에서 넘어온 null 이 더 깊은 곳에서 터집니다
  • 안드로이드 R8은 릴리스 빌드에서 이 검사를 일부 제거합니다(코드 크기 절감)
이 검사는 비용이 아니라 이득입니다. “어디서 null 이 들어왔는가”를 경계 지점에서 즉시 알려 주므로 디버깅 시간이 크게 줄어듭니다.

nullable 원시 타입의 진짜 비용

val a: Int = 1          // int — 원시 타입
val b: Int? = 1         // Integer — 박싱된 객체 ★

// 리스트도 마찬가지
val c: List<Int> = listOf(1, 2, 3)     // Integer 로 박싱된다
val d: IntArray = intArrayOf(1, 2, 3)  // int[] — 박싱 없음

// 수백만 건 수치 계산이라면 이 차이가 크다
// · 메모리: Integer 는 객체 헤더 포함 16바이트, int 는 4바이트
// · 캐시 지역성: 배열은 연속, 객체 리스트는 흩어져 있다

// 대안
// · IntArray · LongArray · DoubleArray
// · @JvmInline value class 는 박싱을 피한다 (nullable 로 쓰면 박싱됨)
DEEP 06

제네릭 소거 · value class

JVM 의 제약과 코틀린의 대응입니다. 언제 박싱이 일어나는지를 알면 성능이 중요한 코드에서 선택이 달라집니다. 

@JvmInline
value class UserId(val value: Long)

// 언제 원시 타입 그대로인가 (박싱 없음)
fun find(id: UserId) { }                  // → find(long id)
val id = UserId(1L)                       // → long id = 1L
listOf(1, 2).map { UserId(it.toLong()) }  // 리스트에 담기면? → 박싱된다

// 언제 박싱되는가
val nullable: UserId? = UserId(1)          // ← 박싱 (null 을 표현해야 하므로)
val list: List<UserId> = listOf(UserId(1)) // ← 박싱 (제네릭)
val any: Any = UserId(1)                   // ← 박싱
interface Repo { fun get(): UserId }       // 인터페이스 반환 → 상황에 따라 박싱

// 확인하는 법: 디컴파일해서 시그니처를 본다
// public static final void find-XXXXXX(long id)   ← 이름이 뒤틀린다(맹글링)
//   → 자바에서 부르기 어려운 이유이기도 하다

reified 가 하는 일

inline fun <reified T> parse(json: String): T =
    mapper.readValue(json, T::class.java)

// 호출: val u = parse<User>(text)
// 디컴파일하면 호출 자리에 이렇게 펼쳐진다:
//   mapper.readValue(text, User.class)
// → 컴파일 시점에 실제 타입이 박히므로 소거를 우회한다

// 그래서 이런 것은 불가능하다
inline fun <reified T> badExample(list: List<T>) {
    // list 가 List<String> 인지 List<Int> 인지는 여전히 알 수 없다
    // reified 는 '호출 시점에 명시된 T' 만 안다
}

소거가 만드는 실제 문제

// ① 같은 시그니처로 인식되는 오버로드
fun handle(list: List<String>) { }
// fun handle(list: List<Int>) { }     // ❌ 플랫폼 선언 충돌
@JvmName("handleInts")                   // ✅ 이름을 바꿔 회피
fun handle2(list: List<Int>) { }

// ② 실행 시점 타입 검사 불가
if (obj is List<String>) { }             // ❌ 경고 · 사실상 List 검사일 뿐
if (obj is List<*>) { }                  // ✅ 이건 된다

// ③ 제네릭 배열 생성 불가
// val arr = Array<T>(10) { ... }        // ❌
inline fun <reified T> makeArray(n: Int, init: (Int) -> T) = Array(n, init)  // ✅
DEEP 07

메모리 — 객체 레이아웃과 GC

코틀린 객체도 결국 JVM 힙 위의 객체입니다. 크기·정렬·수명을 알면 대용량 처리에서 메모리를 절반으로 줄일 수 있습니다.

객체 크기 재기 — JOL

// implementation("org.openjdk.jol:jol-core:0.17")
data class Point(val x: Int, val y: Int)

fun main() {
    println(ClassLayout.parseClass(Point::class.java).toPrintable())
}
// OFFSET  SIZE   TYPE
//      0    12   (object header)      ← 마크워드 8 + 클래스포인터 4(압축)
//     12     4   int Point.x
//     16     4   int Point.y
//     20     4   (padding)            ← 8바이트 정렬
// Instance size: 24 bytes

// 비교
// Point(int,int)         24 bytes
// data class with Long?  32+ bytes (박싱된 Long 참조 + Long 객체 24)
// IntArray(2)            24 bytes (헤더 16 + 4×2)

메모리를 줄이는 실전 기법

  • 원시 타입 배열 — List<Int> 100만 개 ≈ 20MB, IntArray ≈ 4MB
  • nullable 원시 타입 피하기 — Int?는 박싱. -1 같은 센티널이나 별도 플래그 고려
  • 문자열 중복 제거 — 같은 값이 많으면 intern()이나 자체 풀 (JVM 옵션 -XX:+UseStringDeduplication)
  • 컬렉션 초기 용량 지정 — 재할당·복사를 줄인다
  • 스트리밍 처리 — 전부 메모리에 올리지 않는다 (Sequence·Flow)
이스케이프 분석 — 메서드 밖으로 나가지 않는 객체는 JIT 가 아예 할당하지 않을 수 있습니다(스칼라 치환). 그래서 “객체를 만들면 무조건 GC 부담”이라는 생각은 정확하지 않습니다.

동시성 심화 — JMM과 원자성

코루틴을 써도 여러 스레드에서 실행된다는 사실은 변하지 않습니다. 자바 메모리 모델의 규칙이 그대로 적용됩니다.

가시성 — @Volatile

class Worker {
    // ❌ 다른 스레드가 바꾼 값을 영영 못 볼 수 있다
    private var running = true

    // ✅ 쓰기가 즉시 보이도록
    @Volatile private var running2 = true

    fun stop() { running2 = false }
    fun loop() { while (running2) { /* ... */ } }
}

// @Volatile 이 보장하는 것
// · 가시성 (다른 스레드가 최신 값을 본다)
// · 재배치 금지 (앞뒤 명령이 넘나들지 않는다)
// 보장하지 않는 것
// · 원자성 — count++ 는 여전히 안전하지 않다

원자 연산과 락프리

// 단순 카운터
val counter = AtomicLong()
counter.incrementAndGet()

// 경합이 심하면 LongAdder 가 훨씬 빠르다 (분산 카운팅)
val adder = LongAdder()
adder.increment()
val total = adder.sum()

// CAS 루프 — 복잡한 갱신
val ref = AtomicReference(State(0, emptyList()))
fun addItem(item: String) {
    while (true) {
        val cur = ref.get()
        val next = cur.copy(count = cur.count + 1, items = cur.items + item)
        if (ref.compareAndSet(cur, next)) return    // 실패하면 다시 읽고 재시도
    }
}

// kotlinx-atomicfu — 멀티플랫폼 원자 연산 (KMP 에서 유용)
private val count = atomic(0)
count.incrementAndGet()
문제코틀린에서의 대응
가시성@Volatile · 원자 타입 · Mutex
원자성Atomic* · Mutex.withLock · 단일 스레드 격리
경합 심한 카운터LongAdder
false sharing같은 캐시 라인의 인접 변수 — @Contended(JVM 옵션 필요)
안전 발행val + 생성자에서 완결 (코틀린 기본이 유리하다)
이중 검사 잠금by lazy 를 쓰면 된다 — 직접 구현하지 말 것
코틀린이 유리한 점 — val과 불변 data class를 기본으로 쓰면 안전 발행 문제가 대부분 사라집니다. JMM 의 어려운 규칙 대부분은 가변 공유 상태에서 나오는데, 코틀린은 그것을 줄이는 방향으로 설계돼 있습니다.
DEEP 10

컴파일러 플러그인

all-open·no-arg·serialization·Compose는 전부 컴파일러 플러그인입니다. 문법 자체를 바꾸거나 코드를 생성하는 층을 이해하면 프레임워크의 “마법”이 사라집니다.

플러그인하는 일
all-open지정 애너테이션이 붙은 클래스를 open으로 (스프링 프록시용)
no-arg기본 생성자를 바이트코드에 추가 (JPA)
kotlinx-serialization@Serializable 클래스의 시리얼라이저를 생성
Compose@Composable 함수에 재구성 스코프·안정성 추론을 주입
parcelize안드로이드 Parcelable 구현 생성
power-assert단언 실패 시 중간 값들을 함께 출력
atomicfu원자 연산을 플랫폼별 최적 형태로 변환
KSP(엄밀히는 프로세서) 새 파일을 생성만 한다 — 기존 코드는 못 바꾼다

KSP vs 컴파일러 플러그인

  • KSP — 새 파일 생성만 가능. API 가 안정적이고 만들기 쉽다. Room·Hilt·Moshi 가 이 방식
  • 컴파일러 플러그인 — 기존 코드를 변형할 수 있다. FIR/IR API 가 버전마다 바뀌므로 유지보수 부담이 크다
  • 선택 기준 — 코드 생성으로 되면 KSP. 문법을 바꿔야 하거나 기존 클래스를 수정해야 하면 컴파일러 플러그인
컴파일러 플러그인은 신중히 — 코틀린 버전을 올릴 때마다 깨질 수 있습니다. 사내 도구라면 KSP 로 해결되는지 먼저 확인하세요.

GraalVM 네이티브 + 코틀린

기동 수십 ms, 메모리 1/3~1/5. 서버리스·스케일아웃에서 실제 비용 차이를 만듭니다. 대신 리플렉션을 쓰는 코드가 문제가 됩니다.

네이티브는 “항상 빠르다”가 아니라 “기동이 빠르고 메모리가 적다”입니다.

코틀린에서 걸리는 지점

  • kotlin-reflect — 네이티브에서 제한적. 되도록 피한다
  • Jackson — 리플렉션 기반이라 힌트 등록이 많이 필요. kotlinx.serialization 이 훨씬 궁합이 좋다(컴파일 시점 생성)
  • 동적 프록시 — 스프링 AOP·Mockito 등은 힌트 필요
  • 리소스 로딩 — classpath: 패턴을 등록해야 한다
  • 코루틴은 잘 동작합니다 — 특별한 처리가 거의 없습니다

타입 시스템 심화

변성·타입 추론·컨텍스트 파라미터까지, 라이브러리를 설계할 때 알아야 할 코틀린 타입 시스템의 깊은 부분입니다. 

// ① 타입 추론의 한계 — 어디서 명시해야 하나
val a = listOf(1, "x")              // List<Any> — 의도한 게 맞나?
val b = if (flag) 1 else "x"        // Any — 대개 설계가 잘못된 신호

// 재귀 제네릭 (F-bounded) — 빌더·DSL 에서 쓴다
abstract class Builder<T : Builder<T>> {
    @Suppress("UNCHECKED_CAST")
    fun name(n: String): T { this.n = n; return this as T }
}
class UserBuilder : Builder<UserBuilder>() { fun build() = User(n) }

// ② 스타 프로젝션과 제네릭 함수의 차이
fun printAll(list: List<*>) { }          // 타입 인자를 모른다 (쓸 수 없다)
fun <T> printAll2(list: List<T>) { }     // T 를 알고 쓸 수 있다

// ③ 교차 타입 (컴파일러 내부적으로 만들어진다)
fun <T> pick(a: T, b: T): T = a
val r = pick(ArrayList<Int>(), LinkedList<Int>())
// r 의 타입은 AbstractList<Int> & RandomAccess ... 같은 교차 타입

// ④ 컨텍스트 파라미터 (2.2 실험) — 암시적으로 전달되는 의존성
context(logger: Logger)
fun process(order: Order) {
    logger.info("주문 처리 ${order.id}")     // 인자로 안 받아도 쓸 수 있다
}
// 호출부에서 컨텍스트가 있어야 한다
with(logger) { process(order) }

API 설계 관점

  • public API 는 반환 타입을 명시 — 추론에 맡기면 구현 변경이 시그니처를 바꿉니다
  • 변성은 선언 지점에 — 쓰는 쪽이 out·in을 안 써도 되게
  • Nothing 을 활용 — Result<Nothing>·List<Nothing>은 모든 타입 자리에 들어갑니다
  • 타입 파라미터를 줄이세요 — 셋을 넘으면 쓰는 사람이 헷갈립니다

함수형 심화 — 대수적 타입

sealed + data class 조합은 사실 대수적 데이터 타입(ADT)입니다. 이 관점을 가지면 “잘못된 상태를 표현할 수 없게” 설계할 수 있습니다.

잘못된 상태가 표현 가능한 모델
data class UiState(
    val isLoading: Boolean,
    val data: List<Item>?,
    val error: String?,
)

// 이런 상태들이 만들어질 수 있다 — 전부 말이 안 된다
UiState(isLoading = true, data = listOf(...), error = "오류")
UiState(isLoading = false, data = null, error = null)

// 그래서 화면 코드에 방어 코드가 늘어난다
if (state.isLoading) ...
else if (state.error != null) ...
else if (state.data != null) ...
else ???                                  // 이 경우는 뭐지?
불가능한 상태를 만들 수 없게
sealed interface UiState {
    data object Loading : UiState
    data class Success(val data: List<Item>) : UiState
    data class Error(val message: String) : UiState
}

// 세 가지만 존재한다. 그 외는 컴파일이 안 된다
when (state) {
    UiState.Loading -> Spinner()
    is UiState.Success -> List(state.data)   // data 가 non-null 임이 보장
    is UiState.Error -> ErrorView(state.message)
}
// 새 상태를 추가하면 이 when 이 컴파일 에러 → 고칠 곳을 알려 준다
// 상태 기계를 타입으로 — 잘못된 전이가 컴파일되지 않게
sealed interface Order {
    val id: Long

    data class Draft(override val id: Long, val items: List<Item>) : Order {
        fun place(): Placed = Placed(id, items, Clock.System.now())    // Draft → Placed 만 가능
    }
    data class Placed(override val id: Long, val items: List<Item>, val at: Instant) : Order {
        fun pay(txId: String): Paid = Paid(id, items, txId)
        fun cancel(reason: String): Canceled = Canceled(id, reason)
    }
    data class Paid(override val id: Long, val items: List<Item>, val txId: String) : Order {
        fun ship(tracking: String): Shipped = Shipped(id, tracking)
    }
    data class Canceled(override val id: Long, val reason: String) : Order    // 종료 상태
    data class Shipped(override val id: Long, val tracking: String) : Order
}

// draft.pay(...)  ← 컴파일 에러. 결제하려면 먼저 place() 해야 한다
// canceled.ship() ← 존재하지 않는 메서드. 취소된 주문은 배송할 수 없다
// 상태 전이 규칙이 '문서'가 아니라 '타입'이 된다

Arrow — 더 나아가고 싶다면

// Either — 실패 타입을 명시
suspend fun placeOrder(cmd: Cmd): Either<OrderError, Order> = either {
    val user = findUser(cmd.userId).bind()        // 실패면 즉시 Left 반환
    val stock = checkStock(cmd.items).bind()
    ensure(stock.enough) { OrderError.OutOfStock }
    save(user, cmd.items)
}

// Raise DSL (Arrow 2) — 코루틴처럼 자연스럽게
context(raise: Raise<OrderError>)
fun validate(cmd: Cmd) {
    ensure(cmd.quantity in 1..99) { OrderError.InvalidQuantity }
}
팀 합의 없이 도입하지 마세요. Arrow 는 강력하지만 리뷰어가 읽지 못하면 유지보수가 어려워집니다. sealed + Result 로도 대부분의 이득을 얻을 수 있습니다.

실무에서 쓸 만한 선

  • 불가능한 상태를 만들 수 없게 — sealed 로 모델링 (거의 언제나 이득)
  • 부수 효과를 경계로 — 순수 함수로 계산하고, IO 는 바깥에서
  • 실패를 값으로 — sealed 에러 타입 (예외는 진짜 예외 상황에만)
  • 불변 데이터 — val + copy
  • 여기까지가 대부분의 팀에서 순이득입니다

아키텍처 — 헥사고날 · DDD

코틀린은 도메인 모델을 표현하기 좋은 언어입니다. value class·sealed·불변 데이터가 DDD 의 개념들과 잘 맞습니다. 

// domain/ — 프레임워크를 모른다. 순수 코틀린
@JvmInline value class OrderId(val value: Long)
@JvmInline value class Money(val won: Long) {
    init { require(won >= 0) { "금액은 음수일 수 없습니다" } }
    operator fun plus(o: Money) = Money(won + o.won)
}

class Order private constructor(              // 생성자를 막고 팩토리로만
    val id: OrderId,
    val userId: UserId,
    private val _items: MutableList<OrderItem>,
    var status: OrderStatus,
) {
    val items: List<OrderItem> get() = _items.toList()
    fun total(): Money = _items.fold(Money(0)) { acc, i -> acc + i.subtotal() }

    fun cancel(now: Instant): DomainEvent {
        check(status.canCancel()) { "취소 불가 상태: $status" }
        status = OrderStatus.CANCELED
        return OrderCanceled(id, now)          // 도메인 이벤트를 돌려준다
    }

    companion object {
        fun place(userId: UserId, items: List<OrderItem>): Order {
            require(items.isNotEmpty()) { "빈 주문은 만들 수 없습니다" }
            return Order(OrderId(0), userId, items.toMutableList(), OrderStatus.NEW)
        }
    }
}

// application/ — 유스케이스. 포트(인터페이스)에만 의존한다
interface OrderRepository {                    // 포트
    fun findById(id: OrderId): Order?
    fun save(order: Order): Order
}

class CancelOrderUseCase(
    private val orders: OrderRepository,
    private val events: EventPublisher,
) {
    fun execute(id: OrderId) {
        val order = orders.findById(id) ?: throw NotFound(id)
        val event = order.cancel(Clock.System.now())
        orders.save(order)
        events.publish(event)
    }
}

// infrastructure/ — 어댑터. 여기서만 JPA·스프링을 안다
@Repository
internal class JpaOrderRepository(private val jpa: OrderJpaRepository) : OrderRepository {
    override fun findById(id: OrderId) = jpa.findByIdOrNull(id.value)?.toDomain()
    override fun save(order: Order) = jpa.save(order.toEntity()).toDomain()
}

과설계를 피하는 기준

  • 도메인 규칙이 실제로 있는가 — CRUD 뿐이면 계층을 나눌 이유가 적습니다
  • 기술을 바꿀 가능성이 있는가 — 없다면 포트/어댑터는 비용만 늘립니다
  • 팀이 여럿인가 — 경계는 사람 사이의 계약일 때 가장 값을 합니다
  • 시작은 단순하게 — 3계층으로 시작해 필요할 때 옮기는 편이 쌉니다
가장 큰 이득은 테스트입니다. 도메인이 프레임워크를 모르면 스프링 컨텍스트 없이 밀리초 단위로 도메인 규칙을 검증할 수 있습니다.
