QA 01

테스트 피라미드와 도구 선택 — 무엇을 어느 층에서 확인하나

테스트를 "많이" 쓰는 것보다 어느 층에 몇 개를 두느냐가 빌드 속도와 신뢰도를 정합니다. 코틀린에는 JUnit 5 와 Kotest 라는 두 갈래가 있고, 둘 다 같은 JUnit Platform 위에서 돌기 때문에 섞어 쓸 수도 있습니다. 먼저 층을 정하고, 그다음 도구를 고릅니다.

테스트 피라미드 — 넓이가 곧 권장 비율입니다. 통합 테스트가 단위보다 많다면 그 자체가 신호입니다.

JUnit 5 스타일 — 자바 팀이 바로 읽는다

class PriceCalculatorTest {

    private val calc = PriceCalculator(taxRate = 0.1)

    @Test
    fun `세금 10%가 붙는다`() {               // 백틱 이름 = 리포트에 그대로 찍힘
        assertEquals(1_100, calc.total(1_000))
    }

    @Nested
    @DisplayName("쿠폰이 있으면")
    inner class WithCoupon {                  // 상황별로 묶기
        @Test
        fun `할인 후에 세금이 붙는다`() {
            assertEquals(990, calc.total(1_000, coupon = 100))
        }
    }

    @ParameterizedTest
    @CsvSource("0, 0", "500, 550", "1000, 1100")
    fun `금액별 합계`(price: Long, expected: Long) {
        assertEquals(expected, calc.total(price))
    }
}
kotlin.test 를 쓰면 — assertEquals·assertFailsWith<T> 가 JUnit 5 위에서 그대로 돌고, 같은 코드를 KMP 공통 테스트로도 옮길 수 있습니다. assertFailsWith<OutOfStock> { ... } 는 예외를 반환하므로 메시지까지 확인할 수 있습니다.

Kotest 스타일 — 같은 테스트를 DSL 로

class PriceCalculatorSpec : FunSpec({

    val calc = PriceCalculator(taxRate = 0.1)

    test("세금 10%가 붙는다") {
        calc.total(1_000) shouldBe 1_100
    }

    context("쿠폰이 있으면") {
        test("할인 후에 세금이 붙는다") {
            calc.total(1_000, coupon = 100) shouldBe 990
        }
    }

    test("음수 금액은 거부한다") {
        val e = shouldThrow<IllegalArgumentException> {
            calc.total(-1)
        }
        e.message shouldContain "음수"
    }
})

실무에선 이렇게 — 목보다 가짜(fake) 구현이 나을 때 🔴 실무

인메모리 가짜 저장소

interface OrderRepository {
    suspend fun save(order: Order): Order
    suspend fun findById(id: Long): Order?
}

// 테스트 소스셋에 둔다 — 실제처럼 '동작'하는 대역
class FakeOrderRepository : OrderRepository {
    private val store = mutableMapOf<Long, Order>()
    private var seq = 0L

    override suspend fun save(order: Order): Order {
        val saved = if (order.id == null) order.copy(id = ++seq) else order
        store[saved.id!!] = saved          // 테스트 코드라 !! 허용 (qa09 정책)
        return saved
    }
    override suspend fun findById(id: Long) = store[id]

    fun all(): List<Order> = store.values.toList()   // 검증용 엿보기
}

언제 무엇을 — 대역 네 가지

대역쓰는 때
Fake저장 · 조회처럼 상태가 결과를 정할 때. 테스트가 "어떻게 불렀나"가 아니라 "결과가 뭔가"를 봐서 리팩터링에 강합니다
Mock호출 자체가 결과일 때 — 메일 발송 · 결제 요청 · 이벤트 발행
Stub정해진 값만 돌려주면 될 때 — MockK 의 every { } returns
Spy실제 객체 일부만 바꿀 때 — 거의 항상 설계 냄새 (02)
목 테스트가 리팩터링을 막는 순간 — 내부 호출 순서를 verifySequence 로 전부 고정하면 동작은 그대로인데 구현만 바꿔도 테스트가 깨집니다. 바깥으로 나가는 부수 효과만 검증하고 나머지는 결과값으로 확인하세요.
정리 — 단위 75 · 통합 20 · E2E 5 를 출발점으로 잡고, 도구는 JUnit 5 + kotlin.test + MockK 로 시작해 Kotest 단언을 얹는 것이 가장 무난합니다. Gradle 에서 태그로 빠른 테스트와 느린 테스트를 나누면 매 저장마다 도는 테스트가 몇 초로 유지됩니다. 기본 도구 목록은 🧰 실전 도구 탭(TOOL 04)에 있습니다.
QA 02

MockK 실전 — 녹화하고, 돌려주고, 확인한다

코틀린 클래스는 기본이 final 이라 Mockito 로는 목을 만들기 번거롭습니다. MockK 는 final · suspend · object · 확장 함수 · 생성자까지 목으로 바꿀 수 있는 코틀린 전용 도구입니다. 대신 힘이 센 만큼 잘못 쓰면 테스트가 구현에 묶여 리팩터링을 막습니다.

MockK 해부도 — co 접두사 · 매처 · 응답 · 검증 네 조각만 알면 문법의 90%입니다.

스텁 — 무엇을 돌려줄지 정하기

val repo = mockk<OrderRepository>()
val clock = mockk<Clock>()

every { clock.instant() } returns Instant.parse("2026-10-01T00:00:00Z")

coEvery { repo.findById(1L) } returns order(id = 1)       // 값이 정확히 1L 일 때
coEvery { repo.findById(any()) } returns null             // 그 밖 전부 (나중 등록이 우선)
coEvery { repo.findById(match { it < 0 }) } throws IllegalArgumentException("음수 id")

// 부를 때마다 다른 값 — 재시도 테스트에 필수
coEvery { client.fetch() } returnsMany listOf(fail(), fail(), ok())
coEvery { client.fetch() } throws IOException() andThen ok()

// 인자를 보고 계산해서 돌려주기
coEvery { repo.save(any()) } answers { firstArg<Order>().copy(id = 99) }

// Unit 반환 함수 — returns Unit 대신
justRun { audit.record(any()) }
coJustRun { mailer.send(any(), any()) }
스텁하지 않은 함수를 부르면 MockKException: no answer found — MockK 는 기본이 엄격합니다. Mockito 처럼 null·0 을 슬쩍 돌려주지 않아서 처음엔 귀찮지만, "부를 줄 몰랐던 호출"을 바로 드러내 줍니다.

relaxed — 엄격함을 언제 풀까

// ① 전부 느슨하게 — 스텁 안 한 함수는 0 · "" · 빈 목록 · 또 다른 목을 돌려줌
val logger = mockk<AuditLogger>(relaxed = true)

// ② Unit 함수만 느슨하게 — 값을 돌려주는 함수는 여전히 엄격 ★ 권장
val mailer = mockk<Mailer>(relaxUnitFun = true)

// relaxed 의 함정 — 반환값이 '조용히' 0 이 된다
val rate = mockk<RateProvider>(relaxed = true)
service.convert(1000, rate)    // rate.get() 이 0.0 → 결과 0원. 테스트는 통과할 수도 있다

// 어노테이션 방식 — JUnit 5 확장
@ExtendWith(MockKExtension::class)
@MockKExtension.ConfirmVerification        // 테스트마다 confirmVerified 자동
class OrderServiceTest {
    @MockK lateinit var repo: OrderRepository
    @RelaxedMockK lateinit var audit: AuditLogger
    @InjectMockKs lateinit var service: OrderService   // 생성자에 목을 꽂아 줌
}
규칙 하나 — 결과값에 영향을 주는 의존성은 절대 relaxed 로 두지 마세요. 로거 · 메트릭 · 감사 기록처럼 "불려도 그만, 안 불려도 그만"인 것에만 씁니다. 애매하면 relaxUnitFun = true 가 안전한 중간값입니다.

확인하기 — slot · capture · verify 의 강도 조절 🟡 중급

인자 캡처 — "무엇을 넘겼나"를 꺼내 보기

@Test
fun `결제 요청에는 할인 후 금액이 들어간다`() = runTest {
    val req = slot<ChargeRequest>()
    coEvery { pay.charge(capture(req)) } returns Receipt("R-1")

    service.place(cmd(price = 10_000, coupon = 1_000))

    req.captured.amount shouldBe 9_000L         // 캡처한 인자를 직접 검사
    req.captured.idempotencyKey.shouldNotBeBlank()
}

// 여러 번 불렸다면 리스트로
val sent = mutableListOf<Event>()
coEvery { publisher.publish(capture(sent)) } just Runs
service.closeDay()
sent.map { it.type } shouldContainExactly listOf("SETTLED", "REPORTED")

// 캡처 대신 verify 안에서 바로 조건 확인
coVerify { pay.charge(match { it.amount == 9_000L }) }
coVerify { pay.charge(withArg { it.amount shouldBe 9_000L }) }   // 실패 메시지가 더 친절

verify 계열 — 강할수록 깨지기 쉽다

함수확인하는 것
verify { }한 번 이상 불렸나 (기본 atLeast = 1)
verify(exactly = 0) { }안 불렸나 — 실패 경로 테스트의 핵심
verify(timeout = 1000) { }다른 스레드에서 1초 안에 불렸나
verifyOrder { }적힌 순서대로 불렸나 (사이에 다른 호출 허용)
verifySequence { }정확히 이 호출들만, 이 순서로 — 가장 강함
verifyAll { }이 호출들만 (순서 무관)
confirmVerified(mock)검증 안 한 호출이 남았으면 실패
verify { m wasNot Called }목 전체가 한 번도 안 불렸나
순서 검증은 순서가 '요구사항'일 때만 — "결제 성공 후에 재고 차감"처럼 업무 규칙이면 coVerifyOrder 가 맞습니다. 단지 지금 구현이 그 순서라서 고정한 것이라면, 그 테스트는 다음 리팩터링 때 거짓 경보를 냅니다.
대역 결정 흐름 — Fake 가 가능하면 Fake, 목은 밖으로 나가는 호출에만, spyk 는 마지막 수단입니다.

실무에선 이렇게 — spyk 함정과 object · 확장 함수 모킹 🔴 실무

spyk 의 세 가지 함정

val real = PriceService(rates)
val spy = spyk(real)                 // ① '복사본'이다 — real 의 필드를 복사해 새 객체를 만든다
real.discount = 0.3                  //    real 을 바꿔도 spy 는 모른다

every { spy.taxRate() } returns 0.0  // ② 일부만 교체, 나머지는 진짜 코드 실행
spy.total(1000)                      //    total() 안의 this.taxRate() 호출도 가로채진다

// ③ private 함수를 바꾸려면 문자열 이름 — 오타가 컴파일에 안 걸린다
val spy2 = spyk(real, recordPrivateCalls = true)
every { spy2["roundUp"](any<Double>()) } returns 0.0

// ✅ 대부분은 이렇게 푸는 게 낫다 — 바꾸고 싶은 부분을 의존성으로 뺀다
class PriceService(private val rates: RateProvider, private val tax: TaxPolicy)
val service = PriceService(rates, TaxPolicy { 0.0 })   // fun interface 면 람다로
spyk 에 진짜 DB · HTTP 클라이언트가 들어 있으면 스텁하지 않은 메서드가 실제로 나갑니다. 테스트가 운영 API 를 호출한 사고가 대부분 이 경로입니다.

object · 최상위 · 확장 함수 · 생성자

// object 싱글턴
mockkObject(FeatureFlags)
every { FeatureFlags.isOn("new-checkout") } returns true

// 최상위 함수 · 확장 함수 — 파일 클래스(XxxKt) 단위로 바꾼다
mockkStatic("com.shop.util.SlugKt")          // Slug.kt 파일
every { "주문 상세".toSlug() } returns "order-detail"
mockkStatic(String::toSlug)                  // 함수 참조로 — 오타 방지 ★

// 클래스 안에 선언된 확장 함수 — 그 클래스 목의 범위 안에서
val fmt = mockk<Formatter>()
with(fmt) { every { any<Money>().pretty() } returns "1,000원" }

// 함수 안에서 직접 생성하는 객체
mockkConstructor(SmtpClient::class)
every { anyConstructed<SmtpClient>().send(any()) } returns true

@AfterEach
fun tearDown() = unmockkAll()   // ★ 전역 상태 — 안 풀면 다음 테스트로 샌다
object · static 모킹은 '전역 변경'입니다 — 병렬로 도는 다른 테스트에도 보입니다. JUnit 병렬 실행을 켰다면 그런 테스트 클래스에 @Execution(SAME_THREAD) 를 붙이거나, 더 근본적으로는 FeatureFlags 를 인터페이스로 주입받게 바꾸세요.

suspend fun <T> retry(times: Int, initial: Duration, block: suspend () -> T): T {
    var wait = initial
    repeat(times - 1) {
        try { return block() } catch (e: IOException) { delay(wait); wait *= 2 }
    }
    return block()
}

로깅 — kotlin-logging · SLF4J · Logback 과 구조적 로그

장애가 나면 가장 먼저 여는 것이 로그입니다. 그런데 로그가 너무 많으면 비용이, 너무 적으면 맹목이, 문자열로만 남으면 검색 불가가 문제가 됩니다. 코틀린에서는 kotlin-logging 의 람다로 비용을 없애고, JSON 구조 로그로 검색을 살리고, 레벨 정책으로 양을 다룹니다.

코루틴과 MDC — traceId 가 사라지는 자리

MDC(Mapped Diagnostic Context)는 로그 한 줄마다 traceId · userId 를 자동으로 붙여 주는 장치인데, 내부가 ThreadLocal 입니다. 코루틴은 멈췄다 다른 스레드에서 재개되므로 MDC 가 그 스레드에 없으면 로그에서 traceId 가 빈칸이 됩니다. 요청 하나를 로그로 추적할 수 없게 되는 것입니다.

스윔레인 — 세로로 넘어가는 화살표마다 MDC 가 끊깁니다. 컨텍스트 요소로 실어 보내야 따라갑니다.

MDCContext — 지금의 MDC 를 코루틴에 싣기

// implementation("org.jetbrains.kotlinx:kotlinx-coroutines-slf4j:1.10.2")
import kotlinx.coroutines.slf4j.MDCContext

suspend fun handle(req: Request) {
    MDC.put("traceId", req.traceId)                 // 지금 이 스레드에만 붙음

    withContext(Dispatchers.IO + MDCContext()) {    // ★ 현재 MDC 를 복사해 실어 보냄
        logger.info { "DB 조회" }                    // traceId=abc
        delay(100)                                  // 다른 워커에서 재개돼도
        logger.info { "조회 끝" }                    // traceId=abc 그대로
    }
}

// 앱 범위 스코프에서 띄우는 작업도 마찬가지
appScope.launch(MDCContext()) {                     // launch 하는 시점의 MDC 를 캡처
    auditSender.send(event)
}
동작 원리 — MDCContext 는 ThreadContextElement 입니다. 코루틴이 스레드에 올라탈 때 그 스레드의 MDC 를 저장해 둔 맵으로 바꾸고, 내려올 때 원래대로 돌려놓습니다. 그래서 스레드 풀의 다른 작업에 traceId 가 새어 나가지도 않습니다.

함정 — 코루틴 안에서 MDC.put 하면 사라진다

launch(MDCContext()) {
    MDC.put("orderId", "42")      // ❌ 스레드의 MDC 만 바꿈 — 캡처된 맵은 그대로
    delay(10)                     // 재개되면 캡처된 맵으로 '복원'된다
    logger.info { "결제" }         // orderId 없음!
}

// ✅ 값을 더할 때는 새 MDCContext 로 감싼다
suspend fun <T> withMdc(
    vararg pairs: Pair<String, String>,
    block: suspend CoroutineScope.() -> T,
): T = withContext(MDCContext(MDC.getCopyOfContextMap().orEmpty() + pairs), block)

suspend fun pay(order: Order) = withMdc("orderId" to order.id.toString()) {
    logger.info { "결제 시작" }     // traceId + orderId
    pg.charge(order)               // suspend — 재개 후에도 둘 다 유지
    logger.info { "결제 끝" }
}
이 함정은 공식 문서에도 적혀 있습니다 — "코루틴 안에서 MDC 를 바꾸면 다음 재개 때 덮어써진다." 팀 공용 유틸로 withMdc 하나를 두고 MDC.put 을 직접 부르는 코드를 리뷰에서 막는 것이 가장 확실합니다.

@Component
class TraceIdFilter : CoWebFilter() {
    override suspend fun filter(exchange: ServerWebExchange, chain: CoWebFilterChain) {
        val traceId = exchange.request.headers.getFirst("X-Request-Id")
            ?: UUID.randomUUID().toString()
        exchange.response.headers.set("X-Request-Id", traceId)

        withContext(MDCContext(mapOf("traceId" to traceId))) {
            chain.filter(exchange)      // Spring 6.1+ : 이 컨텍스트가 suspend 핸들러까지 이어짐
        }
    }
}

//  → traceId · spanId 가 MDC 에 자동으로 들어가고 로그 패턴에도 찍힌다
//  → 코루틴으로 넘어갈 때는 관측 컨텍스트도 함께 실어 보낸다
import io.micrometer.core.instrument.kotlin.asContextElement

예외 처리 실무 — runCatching 이 취소를 삼키는 함정부터

코틀린에는 checked exception 이 없어서 "어디서 무엇이 터질지"를 타입이 알려 주지 않습니다. 여기에 코루틴이 취소도 예외(CancellationException)로 전달한다는 규칙을 더하면, 평범해 보이는 try-catch 와 runCatching 이 취소를 먹어 버리는 버그가 생깁니다. 예외를 어디서 잡고 · 무엇으로 표현하고 · 어디까지 퍼지게 할지를 정리합니다.

잡 트리 — 실패가 형제와 부모로 번지느냐, 그 자리에서 멈추느냐가 스코프 선택의 전부입니다.
runCatching 이 취소를 '성공한 실패'로 바꾼다
suspend fun loadProfile(id: Long): Profile? =
    runCatching { api.fetch(id) }          // suspend 호출
        .getOrNull()                       // 실패면 null

// 사용자가 화면을 떠나 viewModelScope 가 취소됨
//  → api.fetch 안의 delay/IO 가 CancellationException 을 던짐
//  → runCatching 이 잡아서 Result.failure 로 만듦
//  → 코루틴은 '취소됐는데도' 다음 줄을 계속 실행
//  → 이미 사라진 화면에 결과를 그리려다 크래시,
//     또는 취소된 요청이 재시도 루프를 돈다

try {
    repo.save(order)
} catch (e: Exception) {                   // 같은 문제 — Exception 이 취소도 잡는다
    logger.warn(e) { "저장 실패, 무시" }
}
취소는 다시 던지고, 나머지만 Result 로
// 팀 공용 유틸 — inline 이라 블록 안에서 suspend 호출 가능
inline fun <R> runSuspendCatching(block: () -> R): Result<R> =
    try {
        Result.success(block())
    } catch (e: CancellationException) {
        throw e                            // ★ 취소는 절대 삼키지 않는다
    } catch (e: Throwable) {
        Result.failure(e)
    }

suspend fun loadProfile(id: Long): Profile? =
    runSuspendCatching { api.fetch(id) }.getOrNull()

// try-catch 를 꼭 써야 한다면
try {
    repo.save(order)
} catch (e: Exception) {
    currentCoroutineContext().ensureActive()   // 취소된 상태면 여기서 다시 던짐
    logger.warn(e) { "저장 실패, 무시" }
}
withTimeout 도 같은 함정입니다 — 시간 초과 시 던지는 TimeoutCancellationException 은 CancellationException 의 자식이라, runCatching 안에 넣으면 "타임아웃 실패"가 아니라 이상한 취소로 번집니다. 값이 없으면 null 이 되는 withTimeoutOrNull 을 쓰세요. 취소 규칙 자체는 🌀 코루틴 탭(CORO 07 · 09)에 있습니다.

코루틴 장애는 대개 컴파일도 되고 테스트도 통과합니다. 트래픽이 붙어야 드러나고, 드러날 때는 "메모리가 계속 늘어난다", "가끔 응답이 수 초씩 멈춘다" 같은 증상으로 옵니다. 실제로 가장 많이 겪는 네 가지를 지표의 모양 → 원인 코드 → 고친 코드 → 진단 도구 순서로 봅니다.

@Component
class AppScope : CoroutineScope, DisposableBean {
    override val coroutineContext =
        SupervisorJob() + Dispatchers.Default + CoroutineName("app")
    override fun destroy() = cancel()      // 앱 종료 시 전부 취소
}

@Service
class SyncService(private val scope: AppScope, private val partner: PartnerClient) {
    private val jobs = ConcurrentHashMap<Long, Job>()

    fun requestSync(id: Long) {
        jobs.computeIfAbsent(id) {         // 같은 id 중복 실행 방지
            scope.launch(MDCContext()) {
                while (isActive) {         // 취소되면 루프 탈출
                    partner.push(id)
                    delay(5.seconds)       // 중단점 — 취소 확인 + 스레드 반납
                }
            }.also { job -> job.invokeOnCompletion { jobs.remove(id) } }
        }
    }
}

suspend fun crunch(rows: List<Row>) = withContext(Dispatchers.Default) {
    for (r in rows) { ensureActive(); heavyCompute(r) }   // 원소마다 취소 확인
}

null 안전성 실무 함정 — 컴파일러가 못 지키는 네 곳

코틀린의 null 안전성은 코틀린 코드끼리에서만 완벽합니다. 자바가 돌려준 값, 리플렉션으로 채워지는 객체(JPA · Jackson), !! 와 lateinit 으로 컴파일러에게 "믿어 달라"고 한 자리 — 이 네 곳에서 운영 NPE 가 나옵니다. 문법은 🟠 Kotlin 기초 탭(03 · 18)에 있고, 여기서는 정책과 사고 사례를 다룹니다.

직렬화 호환성 — 필드 하나 추가했을 뿐인데 옛 클라이언트가 깨진다

JSON 은 서버 · 앱 · 다른 서비스 · Kafka 에 남은 옛 메시지 · Redis 캐시가 서로 다른 버전으로 동시에 읽습니다. 배포는 한 번에 일어나지 않으므로 "새 코드가 옛 데이터를, 옛 코드가 새 데이터를" 읽을 수 있어야 합니다. kotlinx.serialization 과 Jackson 은 이 부분의 기본값이 서로 달라서 같은 변경이 한쪽에서만 깨집니다.

호환성 매트릭스 — 붉은 칸이 있는 변경은 한 번에 배포하면 안 됩니다. 회색 칸은 설정 한 줄이 생명줄입니다.

kotlinx.serialization — 호환을 위한 Json 설정

@OptIn(ExperimentalSerializationApi::class)
val AppJson = Json {
    ignoreUnknownKeys = true    // 새 필드가 와도 옛 코드가 안 깨짐 ★ (기본 false!)
    coerceInputValues = true    // null · 모르는 enum → 그 필드의 기본값으로
    explicitNulls = false       // null 은 안 씀 · 키가 없으면 null 로 읽음
    encodeDefaults = true       // 기본값도 씀 — 다른 언어 소비자를 위해
}

@OptIn(ExperimentalSerializationApi::class)
@Serializable
data class OrderEvent(
    val orderId: Long,
    val amount: Long,
    val currency: String = "KRW",               // v2 에서 추가 — 기본값 필수
    @JsonNames("user_id") val userId: Long,     // 옛 이름도 읽음 (쓸 때는 userId)
    val channel: Channel = Channel.UNKNOWN,     // coerceInputValues 와 짝
)

@Serializable
enum class Channel { WEB, APP, UNKNOWN }
encodeDefaults 의 기본값은 false 입니다 — 값이 기본값과 같으면 JSON 에서 필드가 빠집니다. 코틀린끼리는 문제없지만, 같은 메시지를 읽는 파이썬 · 자바 컨슈머는 "currency 가 없다"며 실패합니다.

Jackson (Spring Boot) — 직접 만든 ObjectMapper 가 다르다

// Spring Boot 가 주입하는 ObjectMapper
//   · jackson-module-kotlin 자동 등록 (기본값 · nullable 인식)
//   · FAIL_ON_UNKNOWN_PROPERTIES = false  ← Boot 가 꺼 둠
//

    .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
    .enable(DeserializationFeature.READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE)
    .build()

data class OrderDto(

배포 순서 — 읽는 쪽 먼저, 쓰는 쪽 나중

바꾸려는 것안전한 순서
필드 추가① 소비자: 기본값 있는 필드로 받기 → ② 생산자: 값 채워 보내기
필드 삭제① 소비자: 그 필드를 안 쓰게(기본값) → ② 생산자: 빼기
이름 변경① 새 이름 추가 + 옛 이름 별칭 → ② 둘 다 보내기 → ③ 옛 이름 제거
enum 값 추가① 소비자: 모르는 값 → UNKNOWN → ② 생산자: 새 값 사용
sealed 하위 타입 추가① 소비자: 모르는 타입 처리 경로 → ② 생산자 (판별자 type 이 바뀌지 않게)
남아 있는 데이터도 '옛 클라이언트'입니다 — Redis 에 직렬화해 둔 캐시, Kafka 의 보관 기간 안 메시지, 앱 스토어에서 업데이트 안 한 앱. 캐시는 키에 버전을 넣고(order:v3:42), 앱은 최소 지원 버전을 정해 그보다 옛 응답 모양을 유지합니다.
정리 — 새 필드에는 기본값, kotlinx 에는 ignoreUnknownKeys, Jackson 은 Boot 가 준 매퍼를 씁니다. 이름 변경 · 삭제는 두 번의 배포로 나누고, 과거 메시지를 골든 파일 테스트로 고정하면 호환성 사고는 PR 단계에서 걸립니다. 직렬화 기초는 🧰 실전 도구 탭(05)과 🍃 Spring Boot Web 탭(05)에 있습니다.

@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(BenchmarkTimeUnit.MICROSECONDS)
class ChainBenchmark {

    @Param("10", "1000", "100000")
    var size: Int = 0

    private lateinit var data: List<Int>

    @Setup
    fun setUp() { data = List(size) { it } }       // 입력은 상태 필드에서 — 상수 접기 방지

    @Benchmark                                     // 반환값을 돌려줘야 데드 코드 제거를 피한다
    fun listFirst(): Int = data.map { it * 2 }.filter { it % 3 == 0 }.first()

    @Benchmark
    fun seqFirst(): Int = data.asSequence().map { it * 2 }.filter { it % 3 == 0 }.first()

    @Benchmark
    fun listSum(): Int = data.map { it * 2 }.filter { it % 3 == 0 }.sum()

    @Benchmark
    fun seqSum(): Int = data.asSequence().map { it * 2 }.filter { it % 3 == 0 }.sum()
