STR 01

코틀린 프로젝트의 공통 바탕 — Gradle · 카탈로그 · 규모별 진화

코틀린 프로젝트는 유형이 달라도 파일 세 개가 뼈대입니다 — 모듈 목록을 적는 settings.gradle.kts, 모듈마다 하나씩 있는 build.gradle.kts, 버전을 한곳에 모은 gradle/libs.versions.toml. 각 파일의 문법은 설치 탭 SETUP 05 에 있으니 여기서는 어디에 무엇을 두는지와 커지면 어떻게 바뀌는지만 봅니다.

모듈 하나일 때 — 모든 유형의 출발점

shop/
├─ settings.gradle.kts      # 프로젝트 이름 · 저장소 · (나중에) 모듈 목록
├─ build.gradle.kts         # 플러그인 · 의존성
├─ gradle/
│  ├─ libs.versions.toml    # ★ 버전 카탈로그 — 버전은 여기에만
│  └─ wrapper/              # Gradle 버전 고정 (커밋)
├─ gradle.properties        # JVM 메모리 · 캐시 · 병렬 빌드 스위치
├─ src/
│  ├─ main/kotlin/          # 운영 코드 (자바 섞이면 main/java 도)
│  ├─ main/resources/       # 설정 · SQL · 정적 파일
│  └─ test/kotlin/          # 같은 패키지 이름으로 테스트
└─ build/                   # 산출물 — 커밋 금지

settings.gradle.kts — 블록 순서가 정해져 있습니다

pluginManagement {                       // 반드시 맨 위
    repositories { gradlePluginPortal(); google(); mavenCentral() }
}
dependencyResolutionManagement {
    // 모듈이 제멋대로 저장소를 추가하지 못하게
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories { google(); mavenCentral() }
}
rootProject.name = "shop"
include(":app", ":core:model", ":core:data")   // 커지면 여기만 늘어남
pluginManagement 는 첫 블록이어야 합니다 — rootProject.name 을 위에 쓰면 설정 단계에서 오류가 납니다. 저장소를 settings 에 모으는 것은 모듈이 수십 개가 됐을 때 "이 라이브러리 어디서 받았지?"를 막는 장치입니다.

    implementation(libs.kotlinx.coroutines.core)   // 하이픈 → 점

STR 02

Spring Boot + Kotlin — 기능별 패키지와 코틀린다운 파일 배치

스프링 서버의 구조는 자바와 거의 같습니다 — 루트 패키지에 메인 클래스, 그 아래 기능별 패키지. 코틀린이 바꾸는 것은 파일 단위입니다. 한 파일에 클래스 여러 개와 최상위 함수를 둘 수 있어서, "어떤 파일에 무엇을 묶나"라는 자바에 없던 결정이 생깁니다. 헥사고날로 더 나누는 법은 전문가 탭 DEEP 14 를 보세요.

기능별 패키지는 "함께 바뀌는 것을 함께 둔다"는 규칙입니다 — 나중에 모듈로 떼어 낼 때 경계가 이미 그어져 있습니다.

권장 트리 — 모듈 하나짜리 스프링 서버

shop-api/
├─ build.gradle.kts          # kotlin("plugin.spring") · kotlin("plugin.jpa")
└─ src/main/kotlin/com/example/shop/
   ├─ ShopApplication.kt     # @SpringBootApplication + fun main — 루트에
   ├─ order/                 # 기능 하나 = 패키지 하나
   │  ├─ OrderController.kt

internal 은 패키지가 아니라 모듈 경계 🟡 중급

❌ 기대 — "internal 이면 다른 패키지에서 못 쓴다"

모듈이 하나인 스프링 서버에서 order/ 의 클래스를 internal 로 해도 member/ 에서 그대로 보입니다. 코틀린에는 자바의 package-private 이 없고, internal 의 범위는 같은 Gradle 모듈(컴파일 단위) 전체입니다.

✅ 실제 — 모듈을 나눠야 경계가 생긴다

:order-core 를 별도 모듈로 떼고 구현을 internal 로 두면 다른 모듈의 접근이 컴파일 오류가 됩니다. 작은 서버라면 private + 파일 단위로 숨기고, 경계가 진짜 필요해지면 모듈로 승격합니다.

직접 돌려 본 결과 (kotlinc 2.3.20)

// :core 모듈
interface OrderRepository { fun find(id: Long): Order? }
internal class InMemoryOrderRepository : OrderRepository { /* … */ }
fun orderRepository(): OrderRepository = InMemoryOrderRepository()

// :app 모듈 — 공개 함수로 받으면 OK
val repo = orderRepository()
println(repo.find(1)?.label())       // 출력: #1 5000원

// :app 모듈 — 구현을 직접 부르면
val bad = InMemoryOrderRepository()
// error: cannot access 'class InMemoryOrderRepository : OrderRepository':
//        it is internal in file.

자바 · 스프링 쪽에서 보면

$ javap Svc.class        # -module-name order-core 로 컴파일
public final int helper$order_core();   ← internal fun helper()
public final int run();
internal 은 바이트코드에서 public 이 되고 멤버 이름이 이름$모듈 로 바뀝니다. 자바 코드나 리플렉션에서는 막히지 않으니 코틀린 컴파일러가 지키는 약속으로 이해하세요. 스프링 빈을 internal class 로 두는 것은 문제없습니다.
정리 — 스프링은 루트에 메인, 그 아래 기능별 패키지. 작은 클래스는 OrderDtos.kt 처럼 한 파일에 묶고, internal 경계는 모듈을 나눌 때부터 효과가 있습니다. 큰 모놀리스의 기능 경계 검사는 Spring Modulith(STR 10)로 넘깁니다.
STR 03

Ktor 서버 구조 — Application.module 은 조립만

Ktor 는 애너테이션도 컴포넌트 스캔도 없어서, 구조를 정하지 않으면 Application.kt 한 파일이 끝없이 길어집니다. 해법은 하나입니다 — 설정은 Application 확장 함수, 라우트는 Route 확장 함수로 쪼개고 module() 은 그것들을 부르는 목차로만 둡니다. 라우팅 · 플러그인 문법은 Ktor 탭 KTOR 03 · 04 에 있습니다.

Ktor 구조의 핵심은 Ktor 의존을 앞 세 칸에 가두는 것입니다 — 그러면 서비스는 순수 코틀린 단위 테스트로 끝납니다.

권장 트리 — 생성기 구조 + 기능 폴더

src/main/
├─ kotlin/com/example/
│  ├─ Application.kt        # main + Application.module() — 목차만
│  ├─ plugins/              # 플러그인 설정 (생성기가 만드는 자리)
│  │  ├─ Serialization.kt   # fun Application.configureSerialization()
│  │  ├─ Security.kt
│  │  ├─ Monitoring.kt
│  │  └─ Routing.kt         # 기능별 라우트 함수를 한데 모음
│  ├─ di/AppModule.kt       # Koin module { } — 객체 그래프 한 장
│  ├─ order/                # 기능 폴더
│  │  ├─ OrderRoutes.kt     # fun Route.orderRoutes(service)
│  │  ├─ OrderService.kt    # Ktor import 없음
│  │  └─ OrderRepository.kt # interface + Exposed 구현
│  └─ member/
└─ resources/

   └─ logback.xml

목차 · 라우트 · DI 를 각자 파일로

// Application.kt
fun main(args: Array<String>) = EngineMain.main(args)

fun Application.module() {
    configureSerialization()
    configureKoin()
    configureRouting()
}

// plugins/Routing.kt
fun Application.configureRouting() {
    val orders by inject<OrderService>()     // org.koin.ktor.ext.inject
    routing {
        route("/api") { orderRoutes(orders) }
    }
}

// order/OrderRoutes.kt
fun Route.orderRoutes(service: OrderService) = route("/orders") {
    get("/{id}") {
        val id = call.parameters["id"]?.toLongOrNull()
            ?: return@get call.respond(HttpStatusCode.BadRequest)
        val order = service.find(id)
            ?: return@get call.respond(HttpStatusCode.NotFound)
        call.respond(order)
    }
}

// di/AppModule.kt
val appModule = module {
    single<OrderRepository> { ExposedOrderRepository() }
    singleOf(::OrderService)
}
fun Application.configureKoin() {
    install(Koin) { slf4jLogger(); modules(appModule) }
}
규모구조Koin 모듈 위치
라우트 10개 미만plugins/ + Routing.kt 하나, 서비스는 루트Koin 없이 module() 에서 생성자 호출로 충분
기능 3개 이상위 트리 — 기능 폴더마다 Routes · Service · Repositorydi/AppModule.kt 한 장
기능 10개 이상 · 팀 2개기능 폴더를 Gradle 모듈로 (:order, :member), :server 가 조립모듈마다 orderModule 을 공개, :server 가 modules(...) 로 합침
application.yaml 의 modules 와 코드가 어긋나면 기동 시 ClassNotFoundException 이 납니다. 값은 com.example.ApplicationKt.module 처럼 파일명 + Kt 클래스를 가리킵니다 — Application.kt 의 이름을 바꾸면 yaml 도 같이 바꾸세요. Ktor 3.2 부터 자체 DI 플러그인도 생겼지만, 위치 규칙(di/ 한 곳에 그래프)은 같습니다.
정리 — module() 은 목차, 설정은 plugins/ 의 Application 확장 함수, URL 은 기능 폴더의 Route 확장 함수, 객체 그래프는 di/ 한 장. 서비스는 Ktor 를 import 하지 않게 둡니다.
STR 04

Android 앱 구조 — 공식 아키텍처 가이드를 폴더로 옮기기

안드로이드는 구글이 공식 권장 아키텍처(UI 계층 · 선택적 도메인 계층 · 데이터 계층)를 문서로 정해 두었습니다. 계층의 뜻과 ViewModel 코드는 Android 탭 AND 01, 앱 실전 탭 ANDX 01 에 있으니, 여기서는 그 계층이 모듈 하나짜리 앱에서 어떤 패키지 트리가 되는지와 각 클래스의 자리만 정리합니다.

DTO · EntityDataSource 옆에 두고 리포지터리 밖으로 내보내지 않음 — 밖에는 Article 같은 모델만
❌ 화면 이름으로 리포지터리를 만듦

FeedRepository · DetailRepository — 두 화면이 같은 기사 데이터를 쓰는데 캐시가 둘로 갈라지고, 상세에서 북마크한 것이 피드에 안 보입니다.

✅ 데이터 이름으로 하나

NewsRepository 하나가 기사의 단일 진실 공급원입니다. 화면은 그 Flow 를 관찰만 하므로 어디서 바꿔도 모든 화면이 따라옵니다.

모듈로 나눌 시점 — 화면이 열 개 안팎이 되거나 클린 빌드가 몇 분을 넘으면 이 패키지들이 그대로 :feature:feed · :core:data 모듈이 됩니다(STR 05). 패키지를 화면별 · 데이터별로 나눠 두었으면 폴더를 옮기기만 하면 됩니다.
정리 — ui/화면/ 에 Screen · ViewModel · UiState, data/데이터/ 에 Repository · DataSource, 도메인은 필요할 때만. 리포지터리는 화면이 아니라 데이터 이름으로 만듭니다.
STR 05

Android 모듈화 — :app · :feature:* · :core:*

구글 공식 샘플 Now in Android 가 사실상 표준이 된 모듈 배치입니다. 규칙은 단 하나로 요약됩니다 — 의존은 아래로만, feature 끼리는 서로 모른다. Hilt 로 모듈 사이를 잇는 코드는 앱 실전 탭 ANDX 01 에 있고, 여기서는 배치와 의존 규칙, 빌드 시간 효과를 봅니다.

Now in Android 식 모듈 그래프 — feature 는 형제끼리 모르고, 아래쪽 core 는 위쪽을 전혀 모릅니다.

모듈 트리와 각자의 책임

myapp/
├─ app/                     # Application · MainActivity · NavHost 조립
├─ feature/
│  ├─ order/                # 화면 + ViewModel (한 사용자 흐름)
│  └─ cart/
├─ core/
│  ├─ model/                # 순수 코틀린 data class — 안드로이드 의존 0
│  ├─ data/                 # Repository (network + database 조합)
│  ├─ network/              # Retrofit · Ktor client · DTO
│  ├─ database/             # Room · DAO · Entity
│  ├─ datastore/            # 설정 저장
│  ├─ ui/                   # 여러 feature 가 쓰는 화면 조각
│  ├─ designsystem/         # 테마 · 버튼 · 아이콘 (도메인 모름)
│  └─ testing/              # 가짜 리포지터리 · 테스트 규칙
├─ build-logic/             # 컨벤션 플러그인 (STR 06)
└─ gradle/libs.versions.toml

feature 끼리 이동은 함수로, 연결은 :app 이

// :feature:order — 자기 화면을 그래프에 붙이는 함수만 공개
fun NavGraphBuilder.orderScreen(onCartClick: () -> Unit) {
    composable<OrderRoute> { OrderRoute(onCartClick = onCartClick) }
}

// :app — 두 feature 를 아는 유일한 곳
NavHost(navController, startDestination = OrderRoute) {
    orderScreen(onCartClick = { navController.navigate(CartRoute) })
    cartScreen(onBack = navController::popBackStack)
}
// :feature:order/build.gradle.kts
plugins { id("myapp.android.feature") }        // STR 06
android { namespace = "com.example.feature.order" }
dependencies {
    implementation(projects.core.data)          // 타입 안전 프로젝트 접근자
    // implementation(projects.feature.cart)    ✗ 금지
}
projects.core.data 는 settings 에 enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS") 를 켜야 생깁니다. 안 켜면 project(":core:data") 문자열로 씁니다.

빌드 시간 효과 — implementation 이 벽이 됩니다 🟡 중급

바꾼 곳모듈 하나짜리 앱모듈로 나눈 앱
feature 내부 private 코드앱 전체 증분 컴파일그 feature 만 다시 컴파일, :app 은 링크만
:core:network 내부 구현앱 전체:core:network 만 — :core:data 가 implementation 으로 숨겼다면 위로 안 번짐
:core:model 공개 클래스앱 전체거의 전부 — 그래서 model 은 작고 안정적으로
병렬 빌드 · 캐시모듈 하나는 병렬화 단위가 하나서로 모르는 모듈은 동시에 빌드, CI 캐시 적중률도 오름
api(...) 를 습관적으로 쓰면 이 효과가 사라집니다 — 의존이 위로 그대로 새어 나가 아래 모듈 하나를 바꿔도 위쪽 전체가 다시 컴파일됩니다. 공개 시그니처에 그 타입이 실제로 나올 때만 api, 나머지는 전부 implementation. 모듈이 클래스 서너 개짜리라면 Gradle 오버헤드가 이득보다 큽니다(도구 탭 TOOL 02).
정리 — :app 이 조립, :feature:* 는 서로 모르고, :core:* 는 위를 모릅니다. feature 사이 이동은 NavGraphBuilder 확장 함수 + :app 연결, 의존은 implementation 기본 — 이 둘이 빌드 시간 이득의 전부입니다.
STR 06

build-logic · 컨벤션 플러그인 — 모듈 30개의 빌드 스크립트를 한 장으로

모듈이 열 개를 넘으면 build.gradle.kts 마다 compileSdk · jvmToolchain · Compose 설정 30줄이 복사됩니다. 하나를 올리려면 열 군데를 고쳐야 하고 꼭 하나를 빠뜨립니다. 해법은 "이 모듈은 안드로이드 feature 다"라는 한 줄로 설정 묶음을 입히는 컨벤션 플러그인입니다. 스크립트형(*.gradle.kts) 예제는 도구 탭 TOOL 02 에 있고, 여기서는 Now in Android 가 쓰는 클래스형과 폴더 배치를 봅니다.

컨벤션 플러그인은 코드 의존이 아니라 설정을 주입합니다 — 모듈 그래프(STR 05)와 별개의 축입니다.

폴더 배치와 연결

myapp/
├─ settings.gradle.kts       # pluginManagement { includeBuild("build-logic") }
├─ gradle/libs.versions.toml # 루트와 build-logic 이 함께 읽음
└─ build-logic/              # 독립된 Gradle 빌드 (포함 빌드)

         ├─ AndroidApplicationConventionPlugin.kt

class AndroidFeatureConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) {
        with(target) {
            pluginManager.apply("myapp.android.library")  // 다른 컨벤션 위에 쌓기
            pluginManager.apply("myapp.android.hilt")

STR 07

KMP 구조 — 공유 모듈과 앱 모듈의 경계

Kotlin Multiplatform 프로젝트는 공유 모듈(shared) 하나 + 플랫폼별 앱 진입점이 기본형입니다. 소스셋 계층(commonMain · androidMain · iosMain …)과 build.gradle.kts 는 KMP 탭 KMP 02 에 있으니, 여기서는 "이 코드는 어느 폴더에 두나"를 판단하는 법과 expect/actual 파일 배치 규칙만 봅니다.

기본값은 commonMain, 플랫폼 API 가 필요할 때만 선언은 공통 · 구현은 플랫폼으로 쪼갭니다.

경계가 보이는 트리

project/
├─ shared/                    # KMP 라이브러리 — 화면을 모름
│  └─ src/
│     ├─ commonMain/kotlin/   # 모델 · 리포지터리 · 유스케이스 · expect
│     ├─ androidMain/kotlin/  # actual · Context 가 필요한 구현
│     ├─ iosMain/kotlin/      # actual · NSUserDefaults 등
│     └─ commonTest/kotlin/   # 공통 로직 테스트는 여기 한 번
├─ androidApp/                # Activity · 안드로이드 UI (shared 의존)
├─ iosApp/                    # Xcode 프로젝트 — import Shared
└─ server/                    # (선택) Ktor — shared 의 jvm 타깃을 같이 씀
위저드 버전에 따라 안드로이드 진입점이 composeApp/ 안에 있기도 하고 androidApp/ 으로 분리되어 있기도 합니다. 최근 AGP 는 KMP 모듈과 안드로이드 앱 모듈을 분리하는 쪽을 권하는 흐름이니, 새로 만든다면 분리형이 무난합니다.

expect/actual 파일은 소스셋 이름을 꼬리로

// shared/src/commonMain/kotlin/com/example/Platform.kt
expect fun platformName(): String

// shared/src/androidMain/kotlin/com/example/Platform.android.kt
actual fun platformName(): String =
    "Android ${android.os.Build.VERSION.SDK_INT}"

// shared/src/iosMain/kotlin/com/example/Platform.ios.kt
import platform.UIKit.UIDevice
actual fun platformName(): String =
    UIDevice.currentDevice.systemName() + " " +
        UIDevice.currentDevice.systemVersion
패키지는 같게, 파일 이름에는 .android · .ios 꼬리 — 코틀린 공식 컨벤션입니다. JVM 쪽에서 같은 이름 파일이 둘이면 최상위 함수 클래스(PlatformKt)가 겹치기 때문입니다. 클래스가 필요하면 expect class(아직 Beta) 대신 commonMain 의 interface + DI 로 구현 주입이 더 다루기 쉽습니다.
경계 규칙이유
shared 는 화면을 모른다안드로이드 UI 와 SwiftUI 가 각자 그립니다 — UI 까지 공유하려면 Compose Multiplatform(STR 08)으로 명시적으로 넘어갑니다
앱 모듈에는 규칙을 두지 않는다할인 계산이 Swift 와 안드로이드 양쪽에 있으면 공유한 의미가 없습니다
iOS 에 내보낼 것만 publicpublic 선언이 전부 Objective-C 헤더로 나갑니다 — 나머지를 internal 로 두면 헤더와 바이너리가 작아집니다
shared 가 커지면 쪼개되 iOS 출구는 하나:shared:core · :shared:feature-x 로 나누고, iOS 프레임워크는 그것들을 묶는 umbrella 모듈 하나에서만 만듭니다
정리 — 기본은 commonMain, 플랫폼 API 는 interface/expect 는 공통 · 구현은 플랫폼. 파일은 Platform.android.kt 처럼 꼬리를 붙이고, 앱 모듈에는 화면만 둡니다.
STR 08

Compose Multiplatform — composeApp 하나로 데스크톱 · 웹까지

Compose Multiplatform 은 KMP 위에 UI 까지 공유하는 구조입니다. 그래서 모듈 이름부터 composeApp 이고, 화면 코드가 commonMain 으로 올라옵니다. 데스크톱(JVM)과 웹(Wasm)은 진입점 파일 하나씩만 따로 가집니다. 헷갈리는 것은 리소스 위치입니다 — 안드로이드의 res/ 가 아니라 composeResources/ 입니다.

공유하고 싶은 것은 전부 commonMain 으로 — 리소스도 commonMain/composeResources 에 둬야 모든 타깃이 봅니다.

트리와 진입점

composeApp/src/
├─ commonMain/
│  ├─ kotlin/com/example/
│  │  ├─ App.kt                 # @Composable fun App() — 모든 타깃 공통
│  │  └─ ui/home/ · ui/settings/ # 화면별 폴더 (STR 04 와 같은 규칙)
│  └─ composeResources/
│     ├─ drawable/logo.xml      # 벡터 · png
│     ├─ font/Pretendard-Regular.ttf
│     ├─ values/strings.xml     # 기본 문자열
│     ├─ values-ko/strings.xml  # 한정자로 지역화
│     └─ files/data.json        # 원본 그대로 읽는 파일
├─ jvmMain/kotlin/main.kt       # 예전 위저드는 desktopMain
├─ wasmJsMain/
│  ├─ kotlin/main.kt
│  └─ resources/index.html
├─ androidMain/                 # MainActivity · AndroidManifest
└─ iosMain/                     # MainViewController()
// jvmMain/kotlin/main.kt — 데스크톱
fun main() = application {
    Window(onCloseRequest = ::exitApplication, title = "MyApp") { App() }
}

// wasmJsMain/kotlin/main.kt — 웹
@OptIn(ExperimentalComposeUiApi::class)
fun main() {
    ComposeViewport(document.body!!) { App() }
}

정리 — composeApp/commonMain 에 화면과 composeResources/, 플랫폼 소스셋에는 진입점 파일 하나(main.kt · MainActivity · MainViewController). 커지면 STR 05 처럼 feature · designsystem 모듈로 쪼개고 리소스도 따라 옮깁니다.
STR 09

라이브러리 · 멀티 모듈 공개 API — internal · explicit API · apiDump

앱은 공개 범위를 실수해도 다음 빌드에서 고치면 그만이지만, 라이브러리는 한 번 공개한 시그니처가 약속입니다. 그래서 라이브러리 구조는 폴더보다 "무엇이 밖에서 보이나"를 관리하는 장치가 중심입니다. 배포(Maven Central) 절차는 도구 탭 TOOL 12 에 있습니다. 같은 장치는 사내 멀티 모듈의 :core 에도 그대로 씁니다.

라이브러리 저장소 트리

money-kt/
├─ money/                      # 핵심 아티팩트
│  ├─ api/money.api            # ★ apiDump 결과 — 커밋 대상
│  └─ src/main/kotlin/
├─ money-serialization/        # 선택 기능은 별도 아티팩트로
├─ money-test/                 # 사용자용 테스트 픽스처 · 가짜 객체
├─ money-bom/                  # 버전을 맞춰 주는 BOM (java-platform)
├─ samples/                    # 공개 API 만으로 쓰는 예 — 컴파일로 검증
└─ build-logic/                # 발행 · 서명 · explicitApi 를 한곳에
선택 기능을 핵심에 넣지 마세요 — kotlinx.serialization 을 쓰지 않는 사용자에게까지 의존성을 강요하게 됩니다. money-serialization 처럼 떼어 두면 필요한 사람만 받습니다.

// error: return type must be specified in explicit API mode.

// 통과하는 형태
public class Money(public val won: Long) {
    public operator fun plus(o: Money): Money = Money(won + o.won)
}
public fun won(v: Int): Money = Money(v.toLong())          // → MoneyKt.won
internal fun format(m: Money): String = "%,d원".format(m.won)  // .api 에 안 나옴
코틀린의 기본 가시성은 public 이라 아무것도 안 쓰면 전부 공개됩니다. explicit API 모드는 그 기본값을 없애 모든 공개 선언에 public 과 반환 타입을 강제합니다 — 실수로 새는 API 가 0 이 됩니다.

apiDump — 공개 API 를 파일로 고정 🟡 중급

apiDump 는 공개 API 를 사람이 읽는 파일로 만들고, apiCheck 는 그 파일과 다르면 빌드를 깨뜨립니다.

흐름 — 덤프 · 검사 · 리뷰

# 루트에 binary-compatibility-validator 플러그인 적용 후
./gradlew apiDump     # api/*.api 를 현재 코드로 갱신 → 커밋
./gradlew apiCheck    # check 에 묶여 CI 에서 자동 — 다르면 실패

# 의도한 변경이면: apiDump 후 .api diff 를 PR 에 함께 올림
# 의도하지 않은 변경이면: CI 가 막아 줌
Kotlin 2.2 부터 같은 기능이 Kotlin Gradle 플러그인 안에 실험 기능(abiValidation)으로 들어오고 있습니다. 태스크 이름이 버전마다 바뀌는 중이라 새 프로젝트라도 당장은 플러그인 쪽이 문서가 많습니다.

공개 범위를 다루는 장치 네 가지

장치쓰임

정리 — 라이브러리는 explicitApi() 로 공개를 강제로 선택하게 하고, apiDump 로 공개 API 를 파일에 고정해 CI 가 지키게 합니다. 선택 기능은 별도 아티팩트, 버전은 -bom 으로 맞춥니다.

구조 규칙을 도구로 강제하기 🔴 고급

Konsist — 코틀린 소스를 읽는 아키텍처 테스트

class ArchitectureTest {
    @Test
    fun `계층 의존 방향`() {
        Konsist.scopeFromProject().assertArchitecture {
            val domain = Layer("Domain", "com.example.domain..")
            val data = Layer("Data", "com.example.data..")
            val ui = Layer("UI", "com.example.ui..")
            domain.dependsOnNothing()      // 도메인은 아무것도 모름
            ui.doesNotDependOn(data)       // 화면이 DataSource 를 직접 못 봄
        }
    }

    @Test
    fun `ViewModel 은 ui 패키지에`() {
        Konsist.scopeFromProject()
            .classes()
            .withNameEndingWith("ViewModel")
            .assertTrue { it.resideInPackage("..ui..") }
    }
}
ArchUnit(전문가 탭 DEEP 14)은 바이트코드를 읽고, Konsist 는 코틀린 소스를 읽습니다. 그래서 Konsist 는 파일 이름 · 최상위 함수 · internal 같은 코틀린 고유 규칙도 검사할 수 있습니다. 메서드 이름은 버전마다 조금씩 바뀌니 쓰는 버전 문서를 확인하세요.

Gradle 에서 모듈 의존 규칙 막기

// build-logic — AndroidFeatureConventionPlugin.apply() 안에 추가
val me = target.path                       // 예: ":feature:order"
target.configurations.configureEach {
    dependencies.withType<ProjectDependency>().configureEach {
        // 여기서 path 는 의존 대상 모듈 경로 (Gradle 8.11+)
        if (path.startsWith(":feature:") && !path.endsWith(":api")) {
            throw GradleException("$me → $path : feature 끼리 직접 의존 금지")
        }
    }
}
