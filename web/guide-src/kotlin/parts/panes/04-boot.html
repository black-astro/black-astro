스프링은 자바를 전제로 설계됐고, 코틀린은 기본이 final·non-null입니다. 이 둘이 만나는 지점에 컴파일러 플러그인·프록시·널 처리라는 고유한 주제가 생깁니다. 이 탭은 그 지점들을 먼저 정리한 뒤, 코루틴 컨트롤러까지 실무 형태로 갑니다.

코틀린으로 스프링 시작하기

프로젝트를 만들 때 플러그인 세 개를 빠뜨리면 앱이 뜨지도 않습니다. 왜 필요한지까지 알고 넘어가면 나중에 원인 모를 에러에서 헤매지 않습니다.

plugin.spring — 왜 필요한가

코틀린 클래스는 기본이 final인데, 스프링은 @Transactional·@Cacheable 등을 CGLIB 프록시(상속)로 구현합니다. final 클래스는 상속할 수 없으니 프록시를 만들 수 없습니다. 

// 이 플러그인이 자동으로 open 을 붙여 준다
// @Component @Service @Repository
// @Controller @Configuration
// @SpringBootTest @Async @Transactional

// 없으면 이런 에러
// Cannot subclass final class

plugin.jpa — 기본 생성자

JPA 명세는 엔티티에 파라미터 없는 생성자를 요구합니다. 코틀린 class User(val name: String)에는 그런 생성자가 없습니다. 

// 대상: @Entity @Embeddable
//       @MappedSuperclass
// 바이트코드에만 생성자를 추가한다
// (코드에서는 여전히 못 부른다)

// 없으면
// No default constructor for entity

-Xjsr305=strict

스프링의 자바 API에는 @Nullable·@NonNull이 붙어 있습니다. 이 옵션을 켜면 코틀린이 그 표시를 플랫폼 타입이 아니라 진짜 타입으로 취급합니다.

켜 두는 것을 권합니다. 스프링 API 의 null 계약이 컴파일 단계에서 검사됩니다. (Spring Framework 7 은 JSpecify 애너테이션으로 이 정보를 훨씬 정밀하게 제공합니다)

BOOT 02

DI · 빈 — 코틀린식 주입

코틀린에서는 생성자 주입이 문법적으로도 최선입니다. val로 받으면 불변 + non-null + 테스트 가능이 한 번에 해결됩니다.

필드 주입 — 코틀린에서 특히 나쁘다

설정 — @ConfigurationProperties

@Value("\${...}")를 흩뿌리는 대신 data class 하나로 묶으면 타입 검사·기본값·검증·IDE 자동완성이 전부 따라옵니다.

불변 설정 클래스

@ConfigurationProperties(prefix = "app.order")
data class OrderProperties(
    val maxItems: Int = 100,
    val timeout: Duration = 3.seconds.toJavaDuration(),
    val currency: String = "KRW",

    data class Notify(
        val enabled: Boolean = true,

    notify:
      channels: [email, slack]

BOOT 04

REST 컨트롤러

코틀린 컨트롤러는 자바와 거의 같지만, 단일 표현식 함수와 suspend가 더해지면서 코드가 눈에 띄게 짧아집니다. 

@RestController
@RequestMapping("/api/v1/orders")
class OrderController(
    private val service: OrderService,
) {
    // 목록 — 단일 표현식으로 끝난다
    @GetMapping
    fun list(
        @RequestParam(defaultValue = "1") page: Int,
        @RequestParam(required = false) status: OrderStatus?,
        @PageableDefault(size = 20) pageable: Pageable,
    ): Page<OrderResponse> = service.list(status, pageable)

    // 단건 — 없으면 404 를 던지는 것은 서비스/예외 핸들러 책임
    @GetMapping("/{id}")
    fun get(@PathVariable id: Long): OrderResponse = service.get(id)

    // 생성 — 201 + Location 헤더
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    fun create(@Valid @RequestBody req: CreateOrderRequest): OrderResponse =
        service.create(req)

    // 수정
    @PatchMapping("/{id}")
    fun update(
        @PathVariable id: Long,
        @Valid @RequestBody req: UpdateOrderRequest,
    ): OrderResponse = service.update(id, req)

    // 삭제 — 본문 없음
    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    fun delete(@PathVariable id: Long) = service.delete(id)

    // 헤더 · 쿠키 · 인증 주체
    @GetMapping("/me")
    fun me(
        @RequestHeader("X-Trace-Id") traceId: String?,
        @AuthenticationPrincipal user: LoginUser,
    ): List<OrderResponse> = service.listOf(user.id)
}

suspend 컨트롤러 — 코루틴을 그대로

@RestController
class ProfileController(private val service: ProfileService) {

    // 함수에 suspend 만 붙이면 된다 (spring-web 이 지원)
    @GetMapping("/api/profile/{id}")
    suspend fun profile(@PathVariable id: Long): ProfileResponse =
        service.load(id)         // 안에서 async 로 병렬 호출

    // 스트리밍 응답 — Flow 를 그대로 반환
    @GetMapping("/api/events", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
    fun events(): Flow<ServerSentEvent<String>> = service.eventFlow()
}
Spring MVC 에서도 suspend 가 됩니다. 요청 스레드를 놓아 주고 비동기로 처리한 뒤 결과를 씁니다. 다만 내부에서 블로킹 JDBC 를 쓰면 이득이 제한적이므로, withContext(IO)로 감싸는 경계가 필요합니다 (10 · 코루틴과 스프링).

응답을 다루는 방법들

// 1) 그냥 객체 반환 — 200 OK (가장 깔끔)
@GetMapping("/{id}") fun get(@PathVariable id: Long) = service.get(id)

// 2) 상태 코드가 갈리면 ResponseEntity
@GetMapping("/{id}")
fun get2(@PathVariable id: Long): ResponseEntity<OrderResponse> =
    service.find(id)?.let { ResponseEntity.ok(it) }
        ?: ResponseEntity.notFound().build()

// 3) 생성 — Location 헤더까지
@PostMapping
fun create(@RequestBody req: CreateOrderRequest): ResponseEntity<OrderResponse> {
    val created = service.create(req)
    return ResponseEntity
        .created(URI.create("/api/v1/orders/${created.id}"))
        .body(created)
}

// 4) 파일 다운로드
@GetMapping("/{id}/receipt")
fun receipt(@PathVariable id: Long): ResponseEntity<ByteArray> =
    ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"r-$id.pdf\"")
        .contentType(MediaType.APPLICATION_PDF)
        .body(service.receiptPdf(id))
컨트롤러는 얇게. 검증은 @Valid에, 예외 변환은 @RestControllerAdvice에, 비즈니스 로직은 서비스에 둡니다. 컨트롤러에 if가 늘어나기 시작하면 대개 서비스로 내려야 할 로직이 올라온 것입니다.
BOOT 05

DTO · JSON 직렬화

코틀린 DTO에서 가장 자주 터지는 곳입니다 — null이 아닌 필드에 null이 들어오고, 기본값이 무시되고, Boolean 프로퍼티 이름이 바뀝니다. 원인과 해결을 정리합니다.

필수 — implementation("com.fasterxml.jackson.module:jackson-module-kotlin") (스프링 부트 스타터에 이미 포함되어 있으면 생략 가능하지만, 없으면 코틀린 data class 역직렬화가 깨집니다)
모듈이 없으면 생기는 일
data class CreateOrder(
    val productId: Long,
    val quantity: Int = 1,
)

// 요청: {"productId": 1}
// jackson-module-kotlin 이 없으면
//  · 기본 생성자가 없어 InvalidDefinitionException, 또는
//  · quantity 기본값이 무시되고 0 이 들어옴

// 요청: {"productId": null}
//  · non-null 필드에 null 이 들어가 NPE 가 '나중에' 터진다
모듈이 있으면
// · 주 생성자로 역직렬화한다
// · 기본값이 적용된다 (필드가 없을 때)
// · non-null 필드에 null 이 오면 MissingKotlinParameterException
//   → 400 Bad Request 로 변환 가능

// 스프링 부트는 클래스패스에 있으면 자동 등록한다.
// 직접 만들 때는
val mapper = jacksonObjectMapper().apply {
    registerModule(JavaTimeModule())
    disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
    setSerializationInclusion(JsonInclude.Include.NON_NULL)
}

실무 DTO 설계

// 요청 — 필수는 non-null, 선택은 nullable + 기본값
data class CreateOrderRequest(
    @field:NotNull val productId: Long,
    @field:Min(1) @field:Max(99) val quantity: Int = 1,
    val couponCode: String? = null,
    val memo: String? = null,

// 응답 — 도메인과 분리한다 (엔티티를 그대로 노출하지 않는다)
data class OrderResponse(
    val id: Long,
    val status: OrderStatus,
    val totalAmount: Long,
    val items: List<OrderItemResponse>,
    @JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ss")
    val createdAt: LocalDateTime,
) {
    companion object {
        fun from(o: Order) = OrderResponse(
            id = o.id, status = o.status, totalAmount = o.total(),
            items = o.items.map(OrderItemResponse::from),
            createdAt = o.createdAt,
        )
    }
}

// 또는 확장 함수로 (프레젠테이션 계층 안에 둔다)

이름·형식 관련 함정

문제해결
val isVip: Boolean 이 JSON 에서 vip 로 나감@get:JsonProperty("isVip")
필드 이름을 바꿔야 함@JsonProperty("order_id")

BOOT 06

검증 — Bean Validation

코틀린에서 검증 애너테이션이 “안 먹는” 일이 자주 생깁니다. 원인은 거의 항상 사용 지점(@field:)을 빠뜨린 것입니다.

코틀린에서 검증이 안 먹으면 십중팔구 @field: 누락입니다.

기본 사용

data class SignUpRequest(
    @field:NotBlank(message = "이름은 필수입니다")
    @field:Size(max = 20)
    val name: String,

    @field:Email(message = "이메일 형식이 아닙니다")
    val email: String,

    @field:Pattern(regexp = "^01\\d-\\d{3,4}-\\d{4}$")
    val phone: String,

전역 예외 처리

예외를 HTTP 응답으로 바꾸는 일은 한 곳에서 해야 합니다. 코틀린에서는 sealed 예외 계층 + when으로 매핑을 컴파일러가 검사하게 만들 수 있습니다. 

// 1) 도메인 예외를 sealed 로 묶는다
sealed class DomainException(message: String, cause: Throwable? = null) :
    RuntimeException(message, cause) {

    class NotFound(val entity: String, val id: Any) :
        DomainException("$entity 를 찾을 수 없습니다: $id")

    class Conflict(val reason: String) : DomainException(reason)

    class OutOfStock(val productId: Long, val left: Int) :
        DomainException("재고 부족 (남은 수량 $left)")

    class Forbidden(val action: String) : DomainException("권한이 없습니다: $action")
}

// 2) 한 곳에서 HTTP 로 변환 — when 이 모든 경우를 덮는지 컴파일러가 검사한다
@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(DomainException::class)
    fun handleDomain(e: DomainException): ResponseEntity<ProblemDetail> {
        val (status, code) = when (e) {
            is DomainException.NotFound -> HttpStatus.NOT_FOUND to "NOT_FOUND"
            is DomainException.Conflict -> HttpStatus.CONFLICT to "CONFLICT"
            is DomainException.OutOfStock -> HttpStatus.CONFLICT to "OUT_OF_STOCK"
            is DomainException.Forbidden -> HttpStatus.FORBIDDEN to "FORBIDDEN"
        }
        val body = ProblemDetail.forStatusAndDetail(status, e.message ?: "")
        body.setProperty("code", code)
        body.setProperty("traceId", MDC.get("traceId"))
        return ResponseEntity.status(status).body(body)
    }

    // 검증 실패 — 필드별 메시지를 그대로 내려 준다
    @ExceptionHandler(MethodArgumentNotValidException::class)
    fun handleValidation(e: MethodArgumentNotValidException): ResponseEntity<ProblemDetail> {
        val errors = e.bindingResult.fieldErrors.associate { it.field to (it.defaultMessage ?: "") }
        val body = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "입력값이 올바르지 않습니다")
        body.setProperty("errors", errors)
        return ResponseEntity.badRequest().body(body)
    }

    // 코틀린 require/check 에서 나오는 표준 예외
    @ExceptionHandler(IllegalArgumentException::class)
    fun handleIllegalArgument(e: IllegalArgumentException) =
        ResponseEntity.badRequest().body(
            ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, e.message ?: "잘못된 요청"))

    @ExceptionHandler(IllegalStateException::class)
    fun handleIllegalState(e: IllegalStateException) =
        ResponseEntity.status(HttpStatus.CONFLICT).body(
            ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.message ?: "처리할 수 없는 상태"))

    // 마지막 그물 — 스택 트레이스를 밖으로 내보내지 않는다
    @ExceptionHandler(Exception::class)
    fun handleAny(e: Exception): ResponseEntity<ProblemDetail> {
        log.error("처리되지 않은 예외", e)
        return ResponseEntity.internalServerError().body(
            ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "일시적인 오류입니다"))
    }
}

놓치기 쉬운 것들

  • 코루틴 컨트롤러의 예외도 @RestControllerAdvice가 잡습니다. 단 CancellationException(클라이언트 연결 끊김)은 에러 로그로 남기지 마세요

  • 필터 단계에서 난 예외는 Advice 가 못 잡습니다 — 시큐리티 예외는 AuthenticationEntryPoint로 따로 처리

    val items: List<OrderItem> get() = _items.toList()

    fun totalAmount(): Long = _items.sumOf { it.subtotal() }

    fun cancel(now: LocalDateTime) {

        status = OrderStatus.CANCELED
    }

    fun addItem(item: OrderItem) {
        check(status == OrderStatus.NEW) { "확정된 주문은 수정할 수 없습니다" }
        _items += item
    }
}

BOOT 09

트랜잭션 — 코틀린에서 특히 조심할 것

@Transactional은 프록시로 동작합니다. 코틀린의 final 기본값, 내부 호출, suspend 함수 세 가지가 각각 다른 방식으로 이 프록시를 무력화할 수 있습니다.

코틀린이든 자바든 같은 문제지만, 코틀린은 여기에 final과 suspend가 더해집니다.

세 가지 함정

@Service
class OrderService(private val repo: OrderRepository) {

    // ① final — plugin.spring 이 없으면 프록시 자체를 못 만든다
    //    (플러그인이 @Service 클래스를 열어 주므로 보통은 문제없다)
    //    단 '함수'는 열리지 않는 경우가 있어 open 이 필요할 수 있다

    @Transactional
    fun place(cmd: PlaceOrderCommand): Order {
        val order = repo.save(Order(cmd))
        // ② 내부 호출 — 이 호출에는 REQUIRES_NEW 가 걸리지 않는다
        writeAuditLog(order)
        return order
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    fun writeAuditLog(order: Order) { /* ... */ }
}
③ suspend 함수 + @Transactional 은 기본적으로 동작하지 않습니다. 스프링 트랜잭션은 ThreadLocal 기반인데 코루틴은 스레드를 옮겨 다니기 때문입니다. 아래 해법을 보세요.

코루틴에서 트랜잭션 쓰기

// 방법 1 — 트랜잭션 구간을 블로킹으로 가둔다 (JPA·JDBC 를 쓸 때 현실적)
@Service
class OrderService(
    private val tx: TransactionTemplate,
    private val repo: OrderRepository,
) {
    suspend fun place(cmd: PlaceOrderCommand): Order =
        withContext(Dispatchers.IO) {
            tx.execute { repo.save(Order(cmd)) }!!   // 한 스레드 안에서 시작·종료
        }
}

// 방법 2 — R2DBC(리액티브 DB)면 코루틴 트랜잭션이 그대로 된다
@Service
class ReactiveOrderService(private val operator: TransactionalOperator) {
    suspend fun place(cmd: PlaceOrderCommand): Order =
        operator.executeAndAwait { repo.save(Order(cmd)).awaitSingle() }
}

// 방법 3 — 블로킹 서비스(@Transactional)를 얇게 감싼다 (가장 흔한 구조)
@Service
class OrderFacade(private val blockingService: OrderService) {
    suspend fun place(cmd: PlaceOrderCommand) =
        withContext(Dispatchers.IO) { blockingService.place(cmd) }
}

@Service
class PaymentService(
    private val orderRepo: OrderRepository,
    private val paymentClient: PaymentClient,
    private val events: ApplicationEventPublisher,
) {
    // 읽기 전용 — 스냅숏·플러시 생략으로 성능 이득
    @Transactional(readOnly = true)
    fun get(id: Long): Order = orderRepo.findByIdOrNull(id)
        ?: throw DomainException.NotFound("주문", id)

    @Transactional(
        timeout = 5,
        rollbackFor = [Exception::class],       // 코틀린은 checked 구분이 없어 관례상 명시
    )
    fun pay(id: Long, amount: Long) {
        val order = orderRepo.findByIdOrNull(id) ?: throw DomainException.NotFound("주문", id)
        order.markPaid(amount)

        // ⚠️ 외부 API 호출을 트랜잭션 안에 두지 마세요 —
        //    커넥션을 잡은 채 수 초를 기다리게 됩니다
        events.publishEvent(OrderPaidEvent(order.id))   // 커밋 후 처리로 미룬다
    }
}

// 커밋 이후에만 실행 — 결제 알림·검색 색인 같은 후속 작업의 정석
@Component
class OrderEventListener(private val notifier: Notifier) {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun onPaid(e: OrderPaidEvent) = notifier.send("결제 완료 ${e.orderId}")
}
실무 규칙 셋 — ① 트랜잭션은 서비스 메서드 하나를 경계로, ② 외부 호출·긴 계산은 트랜잭션 밖으로, ③ 조회 전용 메서드에는 readOnly = true. 트랜잭션 전파·격리 수준은 데이터 · JPA 탭에서 더 깊이 다룹니다.

Spring Security — 코틀린 DSL

스프링 시큐리티는 코틀린 전용 DSL을 제공합니다. 자바 람다 체인보다 훨씬 읽기 좋고, 어떤 경로가 어떤 규칙인지가 한눈에 들어옵니다. 

@Configuration
@EnableWebSecurity
@EnableMethodSecurity           // @PreAuthorize 를 쓰려면
class SecurityConfig(
    private val jwtFilter: JwtAuthenticationFilter,
) {
    @Bean
    fun filterChain(http: HttpSecurity): SecurityFilterChain {
        http {
            csrf { disable() }                         // 토큰 기반 API 라면
            cors { }                                    // CorsConfigurationSource 빈 사용
            sessionManagement {
                sessionCreationPolicy = SessionCreationPolicy.STATELESS
            }
            authorizeHttpRequests {
                authorize("/actuator/health", permitAll)
                authorize("/api/auth/**", permitAll)
                authorize(HttpMethod.GET, "/api/products/**", permitAll)
                authorize("/api/admin/**", hasRole("ADMIN"))
                authorize("/api/**", authenticated)
                authorize(anyRequest, denyAll)          // 명시하지 않은 것은 막는다
            }
            addFilterBefore<UsernamePasswordAuthenticationFilter>(jwtFilter)
            exceptionHandling {
                authenticationEntryPoint = AuthenticationEntryPoint { _, res, _ ->
                    res.status = 401
                    res.contentType = "application/json"
                    res.writer.write("""{"code":"UNAUTHORIZED"}""")
                }
                accessDeniedHandler = AccessDeniedHandler { _, res, _ -> res.status = 403 }
            }
            headers { frameOptions { sameOrigin } }
        }
        return http.build()
    }

    @Bean
    fun passwordEncoder(): PasswordEncoder = BCryptPasswordEncoder()

@Component
class JwtAuthenticationFilter(
    private val jwt: JwtProvider,
) : OncePerRequestFilter() {

    override fun doFilterInternal(
        request: HttpServletRequest,
        response: HttpServletResponse,
        chain: FilterChain,
    ) {
        request.getHeader(HttpHeaders.AUTHORIZATION)
            ?.takeIf { it.startsWith("Bearer ") }
            ?.removePrefix("Bearer ")
            ?.let { token -> runCatching { jwt.parse(token) }.getOrNull() }
            ?.let { claims ->
                val auth = UsernamePasswordAuthenticationToken(
                    LoginUser(claims.userId, claims.roles),
                    null,
                    claims.roles.map { SimpleGrantedAuthority("ROLE_$it") },
                )
                SecurityContextHolder.getContext().authentication = auth
            }
        chain.doFilter(request, response)
    }
}

@Target(AnnotationTarget.FUNCTION, AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class Timed(val name: String = "")

@Aspect
@Component
class TimedAspect(private val registry: MeterRegistry) {

    @Around("@annotation(timed)")
    fun measure(pjp: ProceedingJoinPoint, timed: Timed): Any? {
        val name = timed.name.ifBlank { pjp.signature.toShortString() }
        val sample = Timer.start(registry)
        return try {
            pjp.proceed()
        } finally {
            sample.stop(registry.timer("method.timed", "name", name))
        }
    }
}

// 필터 — 요청/응답 전체를 감싼다
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class RequestLoggingFilter : OncePerRequestFilter() {
    override fun doFilterInternal(req: HttpServletRequest, res: HttpServletResponse, chain: FilterChain) {
        val start = System.currentTimeMillis()
        val traceId = req.getHeader("X-Trace-Id") ?: UUID.randomUUID().toString().take(8)
        MDC.put("traceId", traceId)
        res.setHeader("X-Trace-Id", traceId)
        try {
            chain.doFilter(req, res)
        } finally {
            log.info("{} {} {} {}ms", req.method, req.requestURI, res.status,
                System.currentTimeMillis() - start)
            MDC.clear()
        }
    }
}

코틀린에서 주의할 점

  • suspend 함수에는 @Cacheable이 동작하지 않습니다 — 반환 타입이 Object(Continuation 방식)이기 때문. 블로킹 함수로 감싸거나 캐시를 직접 다루세요
  • null 캐싱 — unless = "#result == null"을 안 주면 null 도 캐시됩니다(의도적이면 괜찮습니다)
  • 내부 호출은 캐시가 안 걸립니다 — 프록시 문제(09)
  • 캐시 키에 data class를 쓰면 equals/hashCode 가 자동이라 안전합니다

코루틴 캐시 — 직접 다루기

@Component
class ProductCache(private val repo: ProductRepository) {
    private val cache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(10.minutes.toJavaDuration())
        .build<Long, Product>()

    private val locks = ConcurrentHashMap<Long, Mutex>()

    // 캐시 스탬피드 방지 — 같은 키는 한 번만 조회
    suspend fun get(id: Long): Product? {
        cache.getIfPresent(id)?.let { return it }
        val mutex = locks.computeIfAbsent(id) { Mutex() }
        return mutex.withLock {
            cache.getIfPresent(id) ?: repo.findAsync(id)?.also { cache.put(id, it) }
        }.also { locks.remove(id) }
    }
}
