KMP 01

무엇을 공유할 것인가

KMP 는 “모든 것을 한 번에 만들자”가 아닙니다. 플랫폼과 무관한 로직만 공유하고 나머지는 각자 두는 점진적 방식이 핵심입니다.

한 번에 다 공유하려다 실패하는 경우가 많습니다 — 도메인부터 한 층씩 올리세요.

KMP 가 잘 맞는 경우

  • 같은 기능을 두 플랫폼에 동시에 내야 한다
  • 비즈니스 규칙이 복잡하다 (계산·검증·상태 전이)
  • 두 앱의 동작이 미묘하게 달라 버그 리포트가 갈린다
  • 안드로이드 팀이 iOS 도 지원해야 하는 인력 구조
  • 서버·앱이 모델을 공유하면 좋겠다 (JVM 타깃 추가)

KMP 가 부담이 되는 경우

  • iOS 개발자가 코틀린을 원치 않는다 — 조직의 동의가 먼저입니다
  • 플랫폼 고유 기능이 대부분인 앱 (카메라·AR·위젯 중심)
  • 앱이 아주 작다 — 공유 인프라 구축 비용이 더 큽니다
  • 빌드·디버깅 도구 성숙도가 네이티브만 못한 구간이 아직 있습니다
현실적인 시작 — 새 기능 하나를 공유 모듈로 만들어 보고, 팀이 감을 잡은 뒤 확장하는 방식이 성공률이 가장 높습니다.
KMP 02

프로젝트 구조 · 소스셋

KMP 프로젝트의 뼈대는 소스셋 계층입니다. commonMain에 쓴 코드는 모든 타깃으로 가고, 플랫폼별 폴더는 그 타깃에만 갑니다.

KMP 03

expect / actual

플랫폼마다 다르게 구현해야 하는 것을 잇는 장치입니다. 공통 코드는 “이런 게 있다”만 선언하고, 각 플랫폼이 실제 구현을 제공합니다. 

// commonMain — 선언만
expect class Platform() {
    val name: String
}
expect fun randomUUID(): String
expect val appVersion: String

// androidMain — 실제 구현
actual class Platform actual constructor() {
    actual val name: String = "Android ${Build.VERSION.SDK_INT}"
}
actual fun randomUUID(): String = java.util.UUID.randomUUID().toString()
actual val appVersion: String get() = BuildConfig.VERSION_NAME

// iosMain
actual class Platform actual constructor() {
    actual val name: String = UIDevice.currentDevice.systemName() + " " +
                              UIDevice.currentDevice.systemVersion
}
actual fun randomUUID(): String = NSUUID().UUIDString()
actual val appVersion: String get() =
    NSBundle.mainBundle.infoDictionary?.get("CFBundleShortVersionString") as? String ?: "?"

인터페이스로 푸는 편이 나을 때가 많다

// expect/actual 은 '타입 이름이 같아야' 해서 유연성이 떨어진다
// 의존성 주입을 쓴다면 인터페이스가 더 깔끔하다

// commonMain
interface KeyValueStore {
    suspend fun get(key: String): String?
    suspend fun put(key: String, value: String)
}

// androidMain — DataStore 로 구현
class AndroidKeyValueStore(private val context: Context) : KeyValueStore { /* ... */ }

// iosMain — NSUserDefaults 로 구현
class IosKeyValueStore : KeyValueStore {
    override suspend fun get(key: String) =
        NSUserDefaults.standardUserDefaults.stringForKey(key)
    override suspend fun put(key: String, value: String) =
        NSUserDefaults.standardUserDefaults.setObject(value, key)
}

// Koin 모듈에서 플랫폼별로 바인딩

기억할 규칙

  • 모든 타깃에 actual 이 있어야 컴파일됩니다 — 하나만 빠져도 에러
  • 기본값·기본 구현을 expect 쪽에 둘 수 있습니다(2.0+ 에서 개선)
  • expect 클래스는 실험적 경고가 뜰 수 있습니다 — 인터페이스 + DI 로 대체 가능하면 그쪽이 안정적입니다
  • 중간 소스셋(appleMain)에 actual 을 두면 iOS·macOS 가 함께 씁니다
  • typealias 로도 actual이 됩니다: actual typealias UUID = java.util.UUID

KMP 05

네트워크 — Ktor Client

공유해서 가장 이득이 큰 층입니다. API 스펙이 바뀌면 한 번만 고치면 되고, 두 앱의 에러 처리·재시도 정책이 자동으로 같아집니다. 

// commonMain — 엔진만 플랫폼별로 주입받는다
class ApiClient(engine: HttpClientEngine, private val tokenProvider: suspend () -> String?) {

    private val json = Json { ignoreUnknownKeys = true; encodeDefaults = true }

    private val client = HttpClient(engine) {
        install(ContentNegotiation) { json(json) }
        install(HttpTimeout) {
            requestTimeoutMillis = 15_000
            connectTimeoutMillis = 10_000
        }
        install(HttpRequestRetry) {
            retryOnServerErrors(maxRetries = 2)
            exponentialDelay()
        }
        install(Logging) { level = LogLevel.HEADERS }
        defaultRequest {
            url("https://api.example.com/")
            contentType(ContentType.Application.Json)
        }
    }

    private suspend fun HttpRequestBuilder.auth() {
        tokenProvider()?.let { header(HttpHeaders.Authorization, "Bearer $it") }
    }

    suspend fun orders(page: Int = 1): List<Order> =
        client.get("orders") { auth(); parameter("page", page) }.body()

    suspend fun order(id: Long): Order =
        client.get("orders/$id") { auth() }.body()

    suspend fun createOrder(req: CreateOrderRequest): Order =
        client.post("orders") { auth(); setBody(req) }.body()
}

// androidMain
actual fun httpEngine(): HttpClientEngine = OkHttp.create { /* 인터셉터 등 */ }
// iosMain
actual fun httpEngine(): HttpClientEngine = Darwin.create { /* NSURLSession 설정 */ }

에러 처리도 공유한다

// commonMain — 도메인 에러로 변환
sealed interface ApiError {
    data object Network : ApiError
    data object Timeout : ApiError
    data class Http(val code: Int, val message: String?) : ApiError
    data class Unknown(val cause: String?) : ApiError
}

suspend fun <T> apiCall(block: suspend () -> T): Result<T> =
    try { Result.success(block()) }
    catch (e: CancellationException) { throw e }
    catch (e: ClientRequestException) {
        Result.failure(ApiException(ApiError.Http(e.response.status.value, e.message)))
    }
    catch (e: HttpRequestTimeoutException) { Result.failure(ApiException(ApiError.Timeout)) }
    catch (e: IOException) { Result.failure(ApiException(ApiError.Network)) }
    catch (e: Throwable) { Result.failure(ApiException(ApiError.Unknown(e.message))) }

KMP 06

로컬 저장 — SQLDelight

SQL 파일을 쓰면 타입 안전한 코틀린 API 가 생성되고, 그 코드가 안드로이드·iOS·데스크톱에서 모두 돕니다.

스키마와 쿼리를 .sq 파일에

-- shared/src/commonMain/sqldelight/com/example/db/Order.sq

CREATE TABLE orderEntity (
    id INTEGER NOT NULL PRIMARY KEY,
    orderNo TEXT NOT NULL,
    status TEXT NOT NULL,
    totalAmount INTEGER NOT NULL,
    createdAt INTEGER NOT NULL
);

CREATE INDEX order_created ON orderEntity(createdAt DESC);

selectAll:
SELECT * FROM orderEntity ORDER BY createdAt DESC;

selectById:
SELECT * FROM orderEntity WHERE id = ?;

selectByStatus:
SELECT * FROM orderEntity WHERE status = :status ORDER BY createdAt DESC;

upsert:
INSERT OR REPLACE INTO orderEntity(id, orderNo, status, totalAmount, createdAt)
VALUES (?, ?, ?, ?, ?);

deleteAll:
DELETE FROM orderEntity;

생성된 API 를 코루틴으로

class OrderLocalSource(private val db: AppDatabase) {
    private val q = db.orderQueries

    // Flow 로 관찰 — 데이터가 바뀌면 자동 방출
    fun observeAll(): Flow<List<Order>> =
        q.selectAll().asFlow().mapToList(Dispatchers.IO).map { rows -> rows.map { it.toDomain() } }

    suspend fun replaceAll(orders: List<Order>) = withContext(Dispatchers.IO) {
        db.transaction {                       // 트랜잭션도 지원
            q.deleteAll()
            orders.forEach { o ->
                q.upsert(o.id, o.orderNo, o.status.name, o.totalAmount,
                         o.createdAt.toEpochMilliseconds())
            }
        }
    }
}

// 드라이버는 플랫폼별 (expect/actual 또는 DI)
// androidMain: AndroidSqliteDriver(AppDatabase.Schema, context, "app.db")
// iosMain:     NativeSqliteDriver(AppDatabase.Schema, "app.db")
// jvmMain:     JdbcSqliteDriver(JdbcSqliteDriver.IN_MEMORY)
Room 도 KMP 를 지원합니다(2.7+). 안드로이드에서 Room 을 쓰고 있었다면 전환 비용이 낮습니다. SQL 을 직접 쓰는 걸 선호하면 SQLDelight, 애너테이션 기반이 익숙하면 Room — 둘 다 실무에서 쓰입니다.

저장소를 합쳐 단일 소스 만들기

// commonMain — 안드로이드·iOS 가 똑같이 쓴다
class OrderRepository(
    private val remote: ApiClient,
    private val local: OrderLocalSource,
) {
    fun observe(): Flow<List<Order>> = local.observeAll()

    suspend fun refresh(): Result<Unit> = apiCall { remote.orders() }
        .onSuccess { local.replaceAll(it) }
        .map { }
}

KMP 07

iOS 연동 — Swift에서 부르기

KMP 의 가장 큰 마찰 지점입니다. 코틀린 코드는 Objective-C 헤더를 거쳐 Swift 에 노출되므로, 제네릭·sealed·기본값이 그대로 보이지 않습니다.

SKIE(Touchlab)를 붙이면 이 셋이 대부분 해결됩니다 — 다음 섹션에서 다룹니다.

Swift 쪽에서 본 모습

import Shared

// 코틀린: suspend fun order(id: Long): Order
// Swift : async 로 자동 변환된다 (Kotlin 1.9+)
let order = try await api.order(id: 1)

// 코틀린: class OrderRepository(remote:local:)
let repo = OrderRepository(remote: api, local: local)

// 코틀린 sealed → Swift 에서는 타입 검사로
switch state {
case is OrderUiStateLoading: showSpinner()
case let s as OrderUiStateSuccess: render(s.orders)
case let e as OrderUiStateError: showError(e.message)
default: break            // ← SKIE 없으면 default 가 강제된다
}

// Flow 수집 — 그대로는 번거롭다
FlowCollector(flow: repo.observe()) { orders in
    self.orders = orders as! [Order]
}

노출을 다듬는 기술

// ① Swift 에서 쓸 이름을 지정
@ObjCName(swiftName = "OrderRepo")
class OrderRepository { /* ... */ }

// ② 내부 구현은 숨긴다 — 노출 표면을 작게
internal class OfflineFirstRepository : OrderRepository

// ③ iOS 전용 파사드를 만들어 준다 (iosMain)
class IosOrderFacade(private val repo: OrderRepository) {
    private val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

    fun observeOrders(onEach: (List<Order>) -> Unit): Closeable {
        val job = repo.observe().onEach(onEach).launchIn(scope)
        return Closeable { job.cancel() }     // Swift 에서 해제할 수 있게
    }
}

// ④ 제네릭이 흐려지는 것을 피하려고 구체 타입으로 감싼다
class OrderList(val items: List<Order>)      // Flow<List<Order>> 대신
iOS 팀과의 협업이 성패를 가릅니다. 공유 모듈의 공개 API 를 iOS 개발자가 쓰기 편한 형태로 설계하지 않으면 “코틀린이 불편하다”는 반발이 나옵니다. Swift 스타일에 맞춘 파사드를 제공하는 것이 실무에서 가장 효과적인 완충 장치입니다.
KMP 08

코루틴을 Swift에서 · SKIE

Flow와 suspend를 iOS 에서 자연스럽게 쓰는 것이 관건입니다. SKIE 는 그 간극을 Swift 의 AsyncSequence·enum으로 메워 줍니다.

SKIE 없이
// Flow 수집이 번거롭다
let collector = Kotlinx_coroutines_coreFlowCollector { value in
    // 타입 캐스팅 필요
}
try await repo.observe().collect(collector: collector)

// sealed 도 switch 가 안 갈린다
switch state {
case is UiStateLoading: ...
default: break          // 컴파일러가 완전성을 보장하지 못한다
}
SKIE 를 붙이면
// Flow 가 AsyncSequence 가 된다
for await orders in repo.observe() {
    self.orders = orders
}

// sealed 가 Swift enum 으로 — 완전성 검사가 된다
switch onEnum(of: state) {
case .loading: showSpinner()
case .success(let s): render(s.orders)
case .error(let e): showError(e.message)
}          // default 불필요

// suspend 함수의 기본 인자도 살아난다
let orders = try await api.orders()

SKIE 설정

// build.gradle.kts
plugins {
    id("co.touchlab.skie") version "0.10.1"
}

skie {
    features {
        group {
            SealedInterop.Enabled(true)      // sealed → Swift enum
            FlowInterop.Enabled(true)        // Flow → AsyncSequence
            DefaultArgumentInterop.Enabled(true)
        }
    }
}
KMP 를 실제로 도입한 팀 대부분이 SKIE 를 씁니다. iOS 개발자의 체감 만족도가 눈에 띄게 달라지므로, 파일럿 단계에서 함께 넣어 평가하는 것을 권합니다.

iOS 에서 ViewModel 을 쓰는 형태

// SwiftUI 와 공유 ViewModel 연결
@MainActor
final class OrderListModel: ObservableObject {
    @Published var state: OrderUiState = OrderUiStateLoading()
    private let vm = SharedOrderViewModel()      // 공유 코틀린
    private var task: Task<Void, Never>?

    func start() {
        task = Task {
            for await s in vm.state {            // SKIE 덕분에 for await
                self.state = s
            }
        }
    }
    func stop() { task?.cancel(); vm.onCleared() }
}

struct OrderListView: View {
    @StateObject private var model = OrderListModel()
    var body: some View {
        content
            .onAppear { model.start() }
            .onDisappear { model.stop() }
    }
}
androidx.lifecycle ViewModel 도 KMP 를 지원합니다(2.8+). commonMain에서 ViewModel과 viewModelScope를 그대로 쓸 수 있어, 프레젠테이션 로직 공유가 예전보다 훨씬 쉬워졌습니다.

Compose Multiplatform — UI 공유

Jetpack Compose 를 iOS·데스크톱·웹에서도 돌리는 프레임워크입니다. 안드로이드 개발자가 아는 그 문법 그대로, 화면까지 한 번에 만듭니다. 

// composeApp/src/commonMain/kotlin/App.kt — 이 코드가 4개 플랫폼에서 돈다
@Composable
fun App(viewModel: OrderViewModel = koinViewModel()) {
    MaterialTheme {
        val state by viewModel.state.collectAsStateWithLifecycle()

        when (val s = state) {
            OrderUiState.Loading -> Box(Modifier.fillMaxSize(), Alignment.Center) {
                CircularProgressIndicator()
            }
            is OrderUiState.Error -> ErrorView(s.message, onRetry = viewModel::load)
            is OrderUiState.Success -> LazyColumn {
                items(s.orders, key = { it.id }) { order ->
                    ListItem(
                        headlineContent = { Text(order.orderNo) },
                        supportingContent = { Text(order.displayDate()) },
                        trailingContent = { Text("${order.totalAmount}원") },
                        modifier = Modifier.clickable { viewModel.onClick(order.id) },
                    )
                }
            }
        }
    }
}

fun MainViewController(): UIViewController = ComposeUIViewController { App() }

// Swift 쪽
struct ComposeView: UIViewControllerRepresentable {
    func makeUIViewController(context: Context) -> UIViewController { MainViewControllerKt.MainViewController() }
    func updateUIViewController(_ vc: UIViewController, context: Context) {}
}

KMP 10

UI 를 공유하지 않는 전략

가장 많이 쓰이는 구성입니다 — 로직은 코틀린으로 공유하고, UI 는 각 플랫폼 네이티브. 팀 갈등이 적고, 플랫폼 경험을 잃지 않습니다.

두 앱의 동작은 같고 겉모습만 다릅니다 — 버그가 한쪽에서만 나는 일이 사라집니다.

공유 ViewModel — 두 UI 가 같은 상태를 본다

// commonMain — androidx.lifecycle ViewModel (KMP 지원)
class OrderViewModel(private val repo: OrderRepository) : ViewModel() {

    private val _state = MutableStateFlow<OrderUiState>(OrderUiState.Loading)
    val state: StateFlow<OrderUiState> = _state.asStateFlow()

    init { observe(); refresh() }

    private fun observe() = viewModelScope.launch {
        repo.observe().collect { orders ->
            _state.value = OrderUiState.Success(orders)
        }
    }

    fun refresh() = viewModelScope.launch {
        repo.refresh().onFailure { _state.value = OrderUiState.Error(it.userMessage()) }
    }
}

각 플랫폼에서 붙이기

// Android — 그대로 쓴다
@Composable
fun OrderScreen(vm: OrderViewModel = koinViewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()
    // ...
}
// iOS — SwiftUI 로 감싼다 (SKIE 로 for await 가능)
@MainActor final class OrderStore: ObservableObject {
    @Published private(set) var state: OrderUiState = OrderUiStateLoading()
    private let vm = OrderViewModel(repo: Koin.shared.repo)

    func observe() async {
        for await s in vm.state { state = s }
    }
    func refresh() { vm.refresh() }
}
도입 순서 추천 — ① 도메인 모델·검증 규칙만 공유 → ② API 클라이언트 공유 → ③ 로컬 DB·Repository 공유 → ④ ViewModel 공유 → ⑤ (원한다면) UI 공유. 각 단계에서 멈춰도 이득이 남는다는 것이 이 전략의 장점입니다.
KMP 11

DI · 동시성 모델

KMP 에서는 Koin이 사실상 표준 DI 입니다. 그리고 Kotlin/Native 의 메모리 모델이 바뀌면서 예전의 “동결(freeze)” 제약이 사라졌습니다.

Koin — 공통 모듈 + 플랫폼 모듈

// commonMain
val commonModule = module {
    single { ApiClient(get(), get()) }
    single<OrderRepository> { OrderRepositoryImpl(get(), get()) }
    factory { OrderViewModel(get()) }
}

expect val platformModule: Module

// androidMain
actual val platformModule = module {
    single<HttpClientEngine> { OkHttp.create() }
    single { AndroidSqliteDriver(AppDatabase.Schema, get(), "app.db") as SqlDriver }
}

// iosMain
actual val platformModule = module {
    single<HttpClientEngine> { Darwin.create() }
    single { NativeSqliteDriver(AppDatabase.Schema, "app.db") as SqlDriver }
}

// 초기화
fun initKoin(extra: Module = module {}) = startKoin {
    modules(commonModule, platformModule, extra)
}
// Android: initKoin { single { androidContext() } }  (Application.onCreate)
// iOS:     KoinKt.doInitKoin()                       (AppDelegate)

새 메모리 모델 — 무엇이 달라졌나

  • freeze() 가 필요 없습니다 — 객체를 스레드 사이에서 자유롭게 공유합니다 (Kotlin 1.7.20 부터 기본)
  • InvalidMutabilityException 같은 옛 오류를 더는 만나지 않습니다
  • 대신 자바와 같은 동시성 문제가 생깁니다 — 공유 가변 상태에는 Mutex·AtomicReference가 필요합니다
  • iOS 의 Dispatchers.Main은 메인 큐, Dispatchers.Default는 워커 스레드 풀입니다 (Dispatchers.IO는 네이티브에 없어 Default.limitedParallelism이나 커스텀 디스패처를 씁니다)
// commonMain 에서 IO 를 쓰고 싶다면 expect/actual 로
expect val ioDispatcher: CoroutineDispatcher
// androidMain: actual val ioDispatcher = Dispatchers.IO
// iosMain:     actual val ioDispatcher = Dispatchers.Default

빌드 · 배포

공유 모듈을 iOS 프로젝트에 어떻게 전달할 것인가가 핵심입니다. 직접 참조·CocoaPods·SPM 세 가지 경로가 있고, 팀 구조에 따라 선택이 갈립니다.

방식특징 · 언제
직접 참조(모노레포)Xcode 빌드 단계에서 Gradle 실행 — 한 저장소에서 함께 개발할 때 가장 단순

SPM (XCFramework)바이너리를 배포 — iOS 팀이 코틀린 빌드를 안 하게 하고 싶을 때

jobs:

KMP 14

도입 판단 · 체크리스트

기술보다 조직의 결정이 더 큰 변수입니다. 실제로 도입할 때 확인할 것들을 정리합니다.

도입 전 확인

  • iOS 팀이 동의했는가 — 가장 중요한 항목입니다
  • 맥 빌드 환경이 있는가 (CI 포함)
  • 쓰는 라이브러리가 KMP 를 지원하는가
  • 파일럿 범위를 정했는가 (기능 하나 · 화면 하나)
  • 공유 모듈을 누가 유지보수하는가 (오너십)
  • 실패했을 때 되돌릴 수 있는가 (공유 모듈만 걷어내면 되게 설계)

운영하면서 지킬 것

  • 공개 API 는 Swift 친화적으로 — 제네릭·sealed 노출에 주의
  • SKIE 를 붙여 iOS 개발 경험을 지킨다
  • commonTest 를 두껍게 — 공유 코드의 신뢰가 곧 도입의 근거
  • 플랫폼 코드는 얇게 — 로직이 양쪽에 흩어지면 이득이 사라진다
  • 버전 업 시 Kotlin·Compose MP·SKIE 호환표를 확인
