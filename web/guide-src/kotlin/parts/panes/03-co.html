CORO 01

왜 코루틴인가

서버가 느려지는 가장 흔한 이유는 계산이 아니라 기다림입니다 — DB 응답, 외부 API, 파일. 스레드는 기다리는 동안 통째로 묶여 있고, 코루틴은 그 자리를 비워 줍니다.

핵심은 “빠르다”가 아니라 기다리는 동안 스레드를 붙잡지 않는다입니다.

콜백 지옥에서 나오는 길

// 콜백 — 세 단계만 되어도 읽기 어렵다
fun loadProfile(id: Long, cb: (Profile?) -> Unit) {
    api.getUser(id) { user ->
        if (user == null) { cb(null); return@getUser }
        api.getOrders(user.id) { orders ->
            api.getPoint(user.id) { point ->
                cb(Profile(user, orders, point))   // 에러 처리는 어디에?
            }
        }
    }
}

// 코루틴 — 동기 코드처럼 읽힌다
suspend fun loadProfile(id: Long): Profile {
    val user = api.getUser(id) ?: error("사용자 없음")
    val orders = api.getOrders(user.id)     // 여기서 '기다린다' (스레드는 안 묶임)
    val point = api.getPoint(user.id)
    return Profile(user, orders, point)
}
// try-catch 도 그냥 통한다. 취소도 자동으로 전파된다.

CORO 02

suspend 함수

suspend는 “이 함수는 중간에 멈췄다가 이어서 실행될 수 있다”는 표시입니다. 멈추는 동안 스레드를 점유하지 않는 것이 전부이고, 나머지는 컴파일러가 처리합니다. 

// suspend 를 붙이면 세 가지가 달라진다
suspend fun fetchUser(id: Long): User {
    delay(100)                    // ① suspend 함수를 부를 수 있다
    return api.get("/users/$id")  // ② 기다리는 동안 스레드를 반납한다
}                                 // ③ 코루틴 안에서만 부를 수 있다

fun main() {
    // fetchUser(1)               // ❌ Suspend function should be called only from a coroutine body
    runBlocking {                 // 코루틴을 시작하는 다리 (main 함수·테스트에서만)
        val u = fetchUser(1)      // ✅
        println(u)
    }
}

// main 자체를 suspend 로 만들 수도 있다
suspend fun main() {
    println(fetchUser(1))
}

delay 와 Thread.sleep 의 차이

runBlocking {
    val t = System.currentTimeMillis()
    // 코루틴 10만 개가 1초씩 기다린다
    val jobs = List(100_000) {
        launch { delay(1000) }        // 스레드를 반납하고 대기
    }
    jobs.joinAll()
    println("${System.currentTimeMillis() - t}ms")   // 약 1초대
}

// 스레드가 묶이므로 기본 디스패처의 스레드 수(=CPU 코어 수)만큼만 동시에 자고,
// 나머지는 줄을 서서 기다린다 → 수십 초 이상 걸린다
suspend 함수 안에서 블로킹 호출을 하면 이득이 통째로 사라집니다. JDBC·파일 IO·Thread.sleep은 withContext(Dispatchers.IO)로 감싸야 합니다 (17 · 블로킹 코드와 섞기).

무엇이 “중단점(suspension point)”인가

suspend fun work() {
    println("A")            // 여기까지 스레드 T1
    delay(100)              // ← 중단점. 여기서 반납
    println("B")            // 재개 — T1 이 아닐 수도 있다!
    val x = fetch()         // ← 중단점 (suspend 함수 호출)
    println("C $x")
}

// 중단점이 되는 것
// · delay() · yield()
// · 다른 suspend 함수 호출
// · Channel.send/receive · Flow.collect
// · Job.join() · Deferred.await() · Mutex.lock()

// 중단점이 아닌 것 (그냥 실행된다)
// · 일반 함수 호출 · 반복문 · 계산

재개될 때 다른 스레드일 수 있다는 점이 중요합니다 — ThreadLocal에 담아 둔 값(MDC·시큐리티 컨텍스트)이 사라지는 원인입니다 (11 · 코루틴 컨텍스트).

CORO 03

코루틴 빌더 — launch · async · runBlocking

코루틴을 시작하는 함수들입니다. 넷만 알면 되고, 언제 어느 것을 쓰는지가 실무에서 갈리는 지점입니다.

빌더반환쓰는 자리
launchJob결과가 필요 없는 작업 시작 (발사 후 잊기)
asyncDeferred<T>결과가 필요한 병렬 작업 — await()로 받는다
runBlockingT다리 — main 함수·테스트·레거시 진입점에서만
coroutineScopeTsuspend 함수 안에서 자식들을 묶어 기다린다
withContextT스레드(디스패처)를 바꿔서 실행하고 결과를 받는다
supervisorScopeT자식 하나가 실패해도 형제를 죽이지 않는다 (09)
fun main() = runBlocking {          // ① 진입점: 코루틴 세계로 들어가는 다리
    println("시작")

    // ② launch — 결과가 필요 없다. 즉시 반환하고 백그라운드로 진행
    val job = launch {
        delay(500)
        println("알림 전송 완료")
    }

    // ③ async — 결과를 받는다. 둘을 '동시에' 실행
    val userDeferred = async { fetchUser(1) }       // 여기서 바로 시작된다
    val ordersDeferred = async { fetchOrders(1) }
    val user = userDeferred.await()                 // 여기서 기다린다
    val orders = ordersDeferred.await()
    println("${user.name}: ${orders.size}건")

    job.join()                                       // launch 가 끝나기를 기다림
    println("끝")
}

순차 vs 병렬 — 실행 시간이 갈린다

suspend fun a(): Int { delay(1000); return 1 }
suspend fun b(): Int { delay(1000); return 2 }

// 순차 — 2초
suspend fun sequential(): Int {
    val x = a()      // 1초 기다림
    val y = b()      // 또 1초
    return x + y
}

// 병렬 — 1초
suspend fun parallel(): Int = coroutineScope {
    val x = async { a() }      // 시작만 하고 넘어간다
    val y = async { b() }
    x.await() + y.await()
}

// ⚠️ 흔한 실수 — 이건 여전히 2초다
suspend fun wrong(): Int = coroutineScope {
    val x = async { a() }.await()   // 시작하자마자 기다린다
    val y = async { b() }.await()
    x + y
}

// · 코루틴을 모르는 레거시 프레임워크와의 경계 (배치 잡 등)
runBlocking은 현재 스레드를 막습니다. 웹 요청 처리 스레드에서 부르면 코루틴을 쓰는 의미가 완전히 사라집니다 — 오히려 스레드 풀이 더 빨리 고갈됩니다.

시작 방식 — CoroutineStart

// 기본: DEFAULT — 즉시 스케줄된다
val j1 = launch { work() }

// LAZY — start() 나 await() 를 부를 때까지 시작하지 않는다
val j2 = launch(start = CoroutineStart.LAZY) { work() }
j2.start()

// ATOMIC — 시작 전에는 취소되지 않는다 (자원 정리를 보장해야 할 때)
val j3 = launch(start = CoroutineStart.ATOMIC) { openAndClose() }

// UNDISPATCHED — 첫 중단점까지는 현재 스레드에서 즉시 실행
val j4 = launch(start = CoroutineStart.UNDISPATCHED) { println("바로 찍힘") }
CORO 04

구조적 동시성

코루틴의 진짜 발명품입니다. 모든 코루틴은 부모를 가지고, 부모는 자식이 다 끝날 때까지 끝나지 않으며, 부모가 취소되면 자식도 전부 취소됩니다. “실행 중인지 아무도 모르는 작업”이 원천적으로 생기지 않습니다.

형제를 죽이고 싶지 않다면 supervisorScope를 씁니다 — 09 · 예외 처리에서 다룹니다.

coroutineScope — 다 끝나야 반환한다

suspend fun loadDashboard(): Dashboard = coroutineScope {
    val users = async { userApi.count() }
    val orders = async { orderApi.today() }
    val alerts = async { alertApi.pending() }

    // 셋이 모두 끝나야 이 줄이 실행된다
    Dashboard(users.await(), orders.await(), alerts.await())
}
// 이 함수가 반환되는 순간 '이 안에서 시작한 코루틴은 하나도 남아 있지 않다'
// 하나가 실패하면 나머지도 취소되고 예외가 위로 던져진다
이 보장이 왜 중요한가 — 함수가 반환됐는데 백그라운드에서 작업이 계속 도는 상황이 없어집니다. 자원 정리·로그 순서·테스트 안정성이 전부 여기서 나옵니다.

Job — 코루틴의 손잡이

val job = scope.launch { work() }

job.isActive       // 실행 중인가
job.isCompleted    // 끝났는가 (성공·실패·취소 모두)
job.isCancelled    // 취소됐는가
job.cancel()       // 취소 요청
job.join()         // 끝날 때까지 기다림 (suspend)
job.cancelAndJoin()// 취소하고 정리까지 기다림

job.invokeOnCompletion { cause ->
    if (cause != null) log.warn("실패/취소: $cause")
    else log.info("정상 완료")
}

// 자식 목록도 볼 수 있다
job.children.forEach { println(it) }

CORO 05

CoroutineScope · 생명주기

스코프는 “이 코루틴들이 언제 죽어야 하는가”를 정하는 그릇입니다. 화면이 닫히면, 요청이 끝나면, 서버가 내려가면 — 그 시점에 스코프를 취소하면 전부 정리됩니다. 

// 스코프 = Job + 디스패처(+ 이름 · 예외 핸들러 …)
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + CoroutineName("worker"))

scope.launch { work1() }
scope.launch { work2() }

scope.cancel()          // 안에서 시작한 코루틴이 전부 취소된다

// ⚠️ 한 번 cancel 한 스코프는 재사용할 수 없다 — 다시 만들어야 한다

대부분의 앱 코드에서는 스코프를 직접 만들 일이 없습니다. 플랫폼이 주는 스코프를 쓰거나, suspend 함수 안에서 coroutineScope를 쓰면 됩니다.

직접 만들어야 할 때 — 서버 컴포넌트

@Component
class OutboxPublisher(
    private val repo: OutboxRepo,
) : DisposableBean {

    // SupervisorJob: 작업 하나가 실패해도 다른 작업이 죽지 않게
    private val scope = CoroutineScope(
        SupervisorJob() + Dispatchers.IO + CoroutineName("outbox")
    )

    @PostConstruct
    fun start() {
        scope.launch {
            while (isActive) {                  // 취소되면 루프가 끝난다
                runCatching { publishBatch() }
                    .onFailure { log.error("발행 실패", it) }
                delay(1000)
            }
        }
    }

    override fun destroy() {
        scope.cancel()      // 애플리케이션 종료 시 정리
    }
}
클래스가 CoroutineScope를 구현(: CoroutineScope)하는 방식은 권하지 않습니다. 그 클래스의 모든 공개 메서드에서 launch가 보이게 되어, 밖에서 임의로 코루틴을 띄울 수 있습니다. 스코프는 private 필드로 갖는 편이 안전합니다.
CORO 06

디스패처 — 어느 스레드에서 돌 것인가

코루틴은 스레드가 아니지만 결국 어떤 스레드 위에서 돕니다. 그 스레드를 고르는 것이 디스패처이고, 잘못 고르면 성능이 통째로 무너집니다.

디스패처스레드 수쓰는 일
Dispatchers.DefaultCPU 코어 수 (최소 2)CPU 작업 — 정렬·파싱·이미지 처리·암호화
Dispatchers.IO기본 64개까지 확장블로킹 IO — JDBC·파일·레거시 HTTP 클라이언트
Dispatchers.Main1 (UI 스레드)안드로이드 UI 갱신 (별도 의존성 필요)
Dispatchers.Unconfined고정 없음거의 쓰지 않는다 — 테스트·특수 상황
newFixedThreadPoolContext지정전용 풀이 필요할 때 (닫아 줘야 한다)
asCoroutineDispatcher()—기존 ExecutorService를 디스패처로 변환
suspend fun processImage(file: File): Result {
    // ① 파일 읽기 — 블로킹 IO
    val bytes = withContext(Dispatchers.IO) { file.readBytes() }

    // ② 이미지 변환 — CPU
    val resized = withContext(Dispatchers.Default) { resize(bytes) }

    // ③ 업로드 — 논블로킹 HTTP 라면 디스패처를 안 바꿔도 된다
    val url = uploadClient.put(resized)

    return Result(url)
}

// withContext 는 '그 블록만' 스레드를 바꾸고 결과를 돌려준다.
// 블록이 끝나면 원래 디스패처로 돌아온다.

IO 와 Default 는 스레드를 공유한다

둘은 같은 스레드 풀을 쓰고 한도만 다릅니다. 그래서 Default → IO 전환은 스레드 교체 없이 일어나는 경우가 많아 비용이 작습니다. 

// IO 한도를 늘리려면 (기본 64)
// JVM 옵션: -Dkotlinx.coroutines.io.parallelism=200

// 특정 작업만 동시 실행 수를 제한하고 싶을 때
val limitedIo = Dispatchers.IO.limitedParallelism(10)
withContext(limitedIo) { legacyJdbcCall() }
// ↑ DB 커넥션 풀 크기에 맞추는 용도로 아주 유용하다

잘못 고르면 생기는 일

  • Default 에서 블로킹 IO — 코어 수만큼(예: 8개)만 스레드가 있으므로 전체 CPU 작업이 함께 멈춥니다. 가장 흔하고 치명적인 실수
  • IO 에서 무거운 CPU 작업 — 64개 스레드가 CPU를 두고 경쟁해 컨텍스트 스위칭만 늘어납니다
  • Main 에서 무거운 작업(안드로이드) — 화면이 멈추고 ANR
  • 디스패처를 계속 왕복 — 전환마다 스케줄링 비용. 한 번에 묶어서 withContext로 감싸세요
판단 기준 한 줄 — “이 코드가 스레드를 붙잡고 있는가?” 붙잡으면(JDBC · 파일 · Thread.sleep · 동기 HTTP) IO, 계산만 하면 Default, UI 를 만지면 Main입니다.
CORO 07

취소 — 협조적이다

코루틴 취소는 강제 종료가 아닙니다. “그만하라”는 표시를 남길 뿐이고, 코루틴 쪽이 그것을 확인해 줘야 실제로 멈춥니다. 이 성질을 모르면 “취소했는데 계속 도는” 상황을 만나게 됩니다.

취소가 안 되는 코드
val job = launch(Dispatchers.Default) {
    var i = 0
    while (i < 1_000_000_000) {    // 중단점이 없다
        i++                         // 계산만 한다
    }
    println("끝")
}
delay(10)
job.cancelAndJoin()   // 요청은 갔지만…
// 루프는 끝까지 돈다. 취소 상태를 아무도 확인하지 않기 때문
취소를 확인하는 코드
val job = launch(Dispatchers.Default) {
    var i = 0
    while (i < 1_000_000_000) {
        ensureActive()        // 취소됐으면 여기서 예외를 던진다
        i++
    }
}

// 또는
while (isActive) { /* ... */ }        // 조건으로 확인
// 또는 중간에 yield() 를 넣는다 (다른 코루틴에 양보 + 취소 확인)

취소를 알아채는 세 가지 방법

방법동작
ensureActive()취소됐으면 CancellationException을 던진다 (권장)
isActiveBoolean 검사 — 정리 후 정상 종료하고 싶을 때
yield()양보 + 취소 확인. 계산 루프에 넣기 좋다
모든 suspend 함수delay·await 등은 이미 취소를 확인한다
kotlinx.coroutines 의 suspend 함수는 전부 취소를 확인합니다. 그래서 IO 위주 코드는 따로 신경 쓸 필요가 없습니다 — 문제가 되는 건 중단점 없는 긴 계산 루프뿐입니다.

자원 정리 — finally 와 NonCancellable

val job = launch {
    val conn = openConnection()
    try {
        while (isActive) { process(conn) }
    } finally {
        // ⚠️ 취소된 코루틴에서는 suspend 함수를 부를 수 없다
        // conn.closeAsync()      // 즉시 CancellationException

        withContext(NonCancellable) {   // 이 블록만 취소를 무시한다
            conn.closeAsync()           // 정리는 반드시 끝내게
        }
    }
}

// use { } 도 그대로 통한다 (finally 기반)
suspend fun read() = File("a.txt").bufferedReader().use { it.readText() }

CancellationException — 잡으면 안 되는 예외

// ❌ 취소를 삼켜 버린다 — 취소가 먹지 않는 코드가 된다
launch {
    try {
        delay(1000)
    } catch (e: Exception) {          // CancellationException 도 여기 걸린다
        log.error("에러", e)          // 취소인데 에러로 기록되고, 아래로 계속 진행
    }
}

// ✅ 취소는 다시 던진다
launch {
    try {
        delay(1000)
    } catch (e: CancellationException) {
        throw e                        // 반드시 다시 던진다
    } catch (e: Exception) {
        log.error("진짜 에러", e)
    }
}

// runCatching 도 같은 문제가 있다 (17장·runCatching 주의 참고)
// coroutineContext.ensureActive() 를 catch 안에서 부르는 방법도 쓴다
실전에서 이 실수는 매우 흔합니다. 안드로이드에서 “화면을 나갔는데 네트워크 호출이 계속되는” 현상, 서버에서 “클라이언트가 끊었는데 쿼리가 계속 도는” 현상의 대부분이 catch (e: Exception)로 취소를 삼킨 것입니다. detekt 의 SwallowedException·TooGenericExceptionCaught 규칙으로 잡을 수 있습니다.
CORO 08

타임아웃 · 재시도

외부 시스템을 부르는 코드에 타임아웃이 없으면 장애가 그대로 전파됩니다. 코루틴은 타임아웃을 취소로 구현하기 때문에, 시간이 지나면 진짜로 작업이 멈춥니다. 

// 시간이 지나면 TimeoutCancellationException 을 던진다
val result = withTimeout(3.seconds) {
    api.slowCall()
}

// 예외 대신 null 을 받는다 — 실무에서 더 자주 쓴다
val result2: Data? = withTimeoutOrNull(3.seconds) {
    api.slowCall()
}
val data = result2 ?: fallbackData()

// 여러 단계에 예산을 나눠 준다 (타임아웃 예산 배분)
suspend fun handle(): Response = withTimeout(5.seconds) {   // 전체 예산
    val user = withTimeout(1.seconds) { userApi.get() }     // 단계별 예산
    val items = withTimeout(2.seconds) { itemApi.list() }
    Response(user, items)
}

재시도 — 지수 백오프

suspend fun <T> retry(
    times: Int = 3,
    initialDelay: Duration = 200.milliseconds,
    maxDelay: Duration = 5.seconds,
    factor: Double = 2.0,
    retryOn: (Throwable) -> Boolean = { it is IOException },
    block: suspend () -> T,
): T {
    var delayTime = initialDelay
    repeat(times - 1) {
        try {
            return block()
        } catch (e: CancellationException) {
            throw e                          // 취소는 재시도하지 않는다
        } catch (e: Throwable) {
            if (!retryOn(e)) throw e         // 재시도해도 소용없는 에러는 즉시 던진다
            log.warn("재시도 예정 {}ms: {}", delayTime, e.message)
        }
        delay(delayTime)
        delayTime = (delayTime * factor).coerceAtMost(maxDelay)
    }
    return block()                           // 마지막 시도는 예외를 그대로 전파
}

// 사용
val user = retry(times = 3) { api.getUser(id) }

주의할 점

  • 타임아웃은 취소로 동작합니다 — 블록 안에 중단점이 없으면 시간이 지나도 안 멈춥니다(07 참고)
  • withTimeout의 예외는 CancellationException의 자식입니다. 바깥에서 catch (e: Exception)으로 잡으면 취소와 구분되지 않습니다
  • 재시도에 지터(무작위 흔들림)를 넣으세요 — 모든 클라이언트가 같은 간격으로 재시도하면 동시에 다시 몰립니다
  • 결제·주문처럼 부작용이 있는 호출은 재시도 전에 멱등키가 있는지 확인해야 합니다
// 지터 추가
val jitter = Random.nextLong(0, delayTime.inWholeMilliseconds / 2)
delay(delayTime.inWholeMilliseconds + jitter)
서버라면 서킷 브레이커까지 — 재시도만 넣으면 장애 시 트래픽이 오히려 늘어납니다. 실패율이 높아지면 아예 호출을 끊는 서킷 브레이커(resilience4j)와 함께 써야 합니다 — 대규모 트래픽 탭에서 코루틴과 함께 쓰는 방법을 다룹니다.
CORO 09

예외 처리

코루틴에서 예외는 부모로 올라가면서 형제를 취소합니다. 이 규칙과 launch·async의 차이를 모르면 “예외가 안 잡힌다” 또는 “왜 다른 작업까지 죽었지”를 겪습니다.

supervisorScope는 부분 실패를 허용하는 자리에 씁니다 — 대시보드·목록 화면이 대표적입니다.

launch — 예외가 즉시 위로 간다

// 예외는 launch 블록 '안'에서 잡아야 한다
scope.launch {
    try {
        risky()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        log.error("실패", e)
    }
}

// ❌ 이렇게는 못 잡는다 — launch 는 즉시 반환하기 때문
try {
    scope.launch { risky() }
} catch (e: Exception) { }      // 절대 안 걸린다

// 스코프 전체의 최후 방어선
val handler = CoroutineExceptionHandler { ctx, e ->
    log.error("처리되지 않은 예외 [${ctx[CoroutineName]}]", e)
}
val scope = CoroutineScope(SupervisorJob() + handler)

async — await 할 때 던져진다

val deferred = scope.async { risky() }   // 여기서는 안 터진다

try {
    deferred.await()                      // 여기서 던져진다
} catch (e: Exception) {
    log.error("실패", e)
}

// ⚠️ 함정 — async 의 예외는 '부모에게도' 전파된다
// await 를 감싸도 부모 스코프가 취소될 수 있다
coroutineScope {
    val a = async { error("실패") }
    try { a.await() } catch (e: Exception) { }   // 잡았지만
    delay(100)                                    // 여기서 이미 취소되어 있다
}

// 부분 실패를 허용하려면 supervisorScope 안에서 async 를 쓴다
supervisorScope {
    val a = async { error("실패") }
    val b = async { ok() }
    val ra = runCatching { a.await() }.getOrNull()   // null
    val rb = b.await()                               // 정상
}

실전 — 부분 실패를 허용하는 대시보드

data class Dashboard(val user: User?, val orders: List<Order>, val ads: List<Ad>)

suspend fun loadDashboard(id: Long): Dashboard = supervisorScope {
    // 필수 데이터 — 실패하면 전체 실패가 맞다
    val userD = async { userApi.get(id) }

    // 부가 데이터 — 실패해도 화면은 떠야 한다
    val ordersD = async { orderApi.list(id) }
    val adsD = async { adApi.list() }

    Dashboard(
        user = userD.await(),                                   // 실패 시 예외 전파
        orders = runCatching { ordersD.await() }.getOrDefault(emptyList()),
        ads = runCatching { adsD.await() }
            .onFailure { log.warn("광고 로딩 실패", it) }
            .getOrDefault(emptyList()),
    )
}
규칙내용
launch 의 예외즉시 부모로 전파 → 형제 취소 → 최상위 핸들러
async 의 예외await() 시점에 던져짐 + 부모에게도 전파
CancellationException특별 취급 — 부모로 전파되지 않고 정상 취소로 처리
CoroutineExceptionHandler최상위 코루틴에만 동작. 자식에 달면 무시된다
supervisorScope자식 실패가 위로 안 감. 단 스코프 자체가 실패하면 자식은 취소
try-catch가장 확실하다 — 코루틴 블록 안에서 감싸기
CORO 10

병렬 패턴 — async 활용

실무에서 코루틴으로 얻는 가장 즉각적인 이득은 N개의 외부 호출을 동시에 보내는 것입니다. 응답 시간이 합계에서 최댓값으로 바뀝니다. 

// 1) 고정된 개수 병렬
suspend fun profile(id: Long): Profile = coroutineScope {
    val user = async { userApi.get(id) }
    val orders = async { orderApi.list(id) }
    val point = async { pointApi.get(id) }
    Profile(user.await(), orders.await(), point.await())
}

// 2) 목록을 병렬 처리 — map + async + awaitAll
suspend fun fetchAll(ids: List<Long>): List<User> = coroutineScope {
    ids.map { id -> async { userApi.get(id) } }.awaitAll()
}

// 3) 동시 실행 수 제한 — Semaphore (외부 API 가 429 를 주는 경우 필수)
suspend fun fetchLimited(ids: List<Long>, concurrency: Int = 10): List<User> = coroutineScope {
    val sem = Semaphore(concurrency)
    ids.map { id ->
        async { sem.withPermit { userApi.get(id) } }
    }.awaitAll()
}

// 4) 청크 단위로 나눠 처리 — 순서·부하를 함께 통제
suspend fun fetchChunked(ids: List<Long>): List<User> =
    ids.chunked(100).flatMap { chunk ->
        coroutineScope { chunk.map { async { userApi.get(it) } }.awaitAll() }
    }

// 5) 가장 먼저 오는 하나만 — select
suspend fun fastest(): String = coroutineScope {
    val a = async { mirrorA.fetch() }
    val b = async { mirrorB.fetch() }
    select {
        a.onAwait { it.also { b.cancel() } }
        b.onAwait { it.also { a.cancel() } }
    }
}

부분 실패를 담아 돌려주기

suspend fun fetchAllSafe(ids: List<Long>): Map<Long, Result<User>> =
    supervisorScope {
        ids.associateWith { id ->
            async {
                runCatching { userApi.get(id) }
            }
        }.mapValues { (_, d) -> d.await() }
    }

val results = fetchAllSafe(ids)
val ok = results.values.mapNotNull { it.getOrNull() }
val failed = results.filterValues { it.isFailure }.keys
log.warn("실패한 id: {}", failed)

병렬로 만들면 안 되는 것

  • DB 커넥션을 쓰는 작업 — 커넥션 풀 크기를 넘는 동시 실행은 풀 고갈로 이어집니다. limitedParallelism이나 세마포어로 제한하세요
  • 순서가 있는 작업 — 재고 차감 후 결제처럼 앞이 성공해야 뒤가 의미 있는 흐름
  • 같은 트랜잭션 안 — 스프링 트랜잭션은 스레드에 묶여 있어 다른 코루틴으로 넘어가면 같은 트랜잭션이 아닙니다 (자세한 내용은 Spring Boot 탭)
  • 상대 API 의 rate limit 을 넘는 호출 — 병렬로 보내면 429 폭탄
체감 효과 — 외부 API 3개를 각각 200ms에 부르던 화면이 600ms → 200ms가 됩니다. 코루틴 도입 초기에 가장 먼저 얻는 성과이고, 코드 변경량도 작습니다 (coroutineScope { async … await }로 감싸는 정도).
CORO 11

코루틴 컨텍스트 — 값 전파

코루틴은 실행 중 스레드가 바뀔 수 있습니다. 그래서 ThreadLocal에 담아 둔 traceId·사용자 정보가 사라집니다. 코루틴에는 그 자리를 대신하는 컨텍스트가 있습니다. 

// CoroutineContext = 요소들의 집합 (Map 과 비슷하고 + 로 합친다)
val ctx = Dispatchers.IO + CoroutineName("worker") + SupervisorJob() + exceptionHandler

launch(ctx) {
    println(coroutineContext[CoroutineName]?.name)     // worker
    println(coroutineContext[Job])                     // 현재 Job
    println(Thread.currentThread().name)               // DefaultDispatcher-worker-1

    // 자식은 부모 컨텍스트를 상속하고 필요한 것만 덮어쓴다
    launch(Dispatchers.Default) {
        println(coroutineContext[CoroutineName]?.name) // worker (그대로 상속)
    }
}

직접 만드는 컨텍스트 요소

// 요청 단위 정보를 코루틴 전체에 흘려보낸다
data class RequestContext(val traceId: String, val userId: Long?) :
    AbstractCoroutineContextElement(Key) {
    companion object Key : CoroutineContext.Key<RequestContext>
}

// 심는 쪽
suspend fun handle(req: Request) = withContext(RequestContext(req.traceId, req.userId)) {
    service.process()
}

// 읽는 쪽 — 어디서든
suspend fun currentTraceId(): String? =

    withContext(Dispatchers.IO) { jdbc.query(sql) }

실무에서 가장 자주 쓰는 동기화 도구가 Semaphore 입니다. “동시에 몇 개까지”라는 제약이 외부 API·DB·파일 시스템 어디에나 있기 때문입니다.
단일 스레드 디스패처는 만병통치약이 아닙니다. limitedParallelism(1)로 가두면 락은 없어지지만 처리량이 1로 제한됩니다. 상태 갱신이 아주 짧을 때만 이득이고, 그 안에서 IO 를 하면 전체가 줄을 섭니다.
CORO 17

블로킹 코드와 섞기

현실의 코드베이스에는 JDBC·레거시 SDK·콜백 API가 섞여 있습니다. 코루틴은 이들을 버리지 않고 감싸서 쓸 수 있게 설계돼 있습니다 — 그 경계 만드는 법입니다.

① 블로킹 함수 감싸기

// JDBC · 파일 · 동기 HTTP — 전부 IO 디스패처로
suspend fun findUser(id: Long): User? = withContext(Dispatchers.IO) {
    jdbcTemplate.queryForObject(SQL, User::class.java, id)
}

// 커넥션 풀 크기를 넘지 않게 제한하면 더 좋다
private val dbDispatcher = Dispatchers.IO.limitedParallelism(20)
suspend fun findAll(): List<User> = withContext(dbDispatcher) {
    jdbcTemplate.query(SQL, rowMapper)
}

// 취소를 지원하려면 인터럽트를 연결해 준다
suspend fun longQuery(): List<Row> = withContext(Dispatchers.IO) {
    runInterruptible { jdbc.query(HEAVY_SQL) }   // 취소 시 스레드 인터럽트
}

② 콜백 API → suspend

// 레거시 SDK 가 콜백을 준다면
suspend fun getLocation(): Location = suspendCancellableCoroutine { cont ->
    val callback = object : LocationCallback {
        override fun onSuccess(loc: Location) = cont.resume(loc)
        override fun onError(e: Throwable) = cont.resumeWithException(e)
    }
    manager.requestLocation(callback)

    // 코루틴이 취소되면 요청도 취소한다 — 이 줄이 핵심이다
    cont.invokeOnCancellation { manager.cancelRequest(callback) }
}

// OkHttp 예시
suspend fun Call.await(): Response = suspendCancellableCoroutine { cont ->
    enqueue(object : Callback {
        override fun onResponse(call: Call, res: Response) = cont.resume(res)
        override fun onFailure(call: Call, e: IOException) = cont.resumeWithException(e)
    })
    cont.invokeOnCancellation { cancel() }
}

CORO 18

코루틴 테스트

코루틴 테스트의 핵심은 가상 시간입니다. delay(10.minutes)가 있어도 테스트는 즉시 끝납니다 — 시간을 실제로 기다리지 않고 앞으로 감기 때문입니다.

의존성 — testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.10.2") · Flow 테스트에는 app.cash.turbine:turbine이 편합니다.
@Test
fun `재시도는 3번까지 한다`() = runTest {        // ← runBlocking 대신 runTest
    var calls = 0
    val result = retry(times = 3, initialDelay = 1.seconds) {
        calls++
        if (calls < 3) throw IOException("실패") else "성공"
    }
    assertEquals("성공", result)
    assertEquals(3, calls)
    // delay 가 총 3초였지만 테스트는 수 ms 만에 끝난다 (가상 시간)
}

@Test
fun `가상 시간을 직접 제어`() = runTest {
    val job = launch {
        delay(1000); println("1초 뒤")
        delay(1000); println("2초 뒤")
    }
    advanceTimeBy(1000)      // 1초 앞으로
    runCurrent()             // 지금 실행 가능한 것 실행
    advanceUntilIdle()       // 할 일이 없어질 때까지 전부 진행
    assertTrue(job.isCompleted)
    println(currentTime)     // 가상 시계 값
}

CORO 19

내부 동작 — CPS와 상태 기계

suspend는 마법이 아닙니다. 컴파일러가 함수를 상태 기계로 다시 씁니다. 이 변환을 이해하면 스레드가 바뀌는 이유, 스택 트레이스가 잘리는 이유, Continuation 이 무엇인지가 한 번에 풀립니다.

코루틴의 “상태”는 스레드 스택이 아니라 힙의 Continuation 객체에 있습니다 — 그래서 가볍습니다.
// 내가 쓴 코드
suspend fun getUser(id: Long): User

// 컴파일된 시그니처 (자바에서 본 모습)
// Object getUser(long id, Continuation<? super User> $completion)
//
// ① suspend 함수에는 Continuation 인자가 하나 몰래 붙는다 (CPS 변환)
// ② 반환 타입이 Object 인 이유 — 값을 바로 못 주면 COROUTINE_SUSPENDED 를 돌려준다
// ③ 자바에서 suspend 함수를 부르기 어려운 이유가 이것이다

// Continuation 인터페이스는 이게 전부다
public interface Continuation<in T> {
    val context: CoroutineContext
    fun resumeWith(result: Result<T>)     // 결과를 들고 '이어서 실행해'
}

IntelliJ → Tools → Kotlin → Show Kotlin Bytecode → [Decompile]

suspend 함수를 하나 만들고 디컴파일하면
  · ContinuationImpl 을 상속한 익명 클래스
  · switch (this.label) 로 시작하는 거대한 메서드
  · 지역 변수가 필드(L$0, L$1)로 저장되는 코드
가 그대로 보입니다.

"코루틴이 왜 스레드보다 가벼운가"의 답이 여기 있습니다 —
스택 1MB 대신 필드 몇 개짜리 객체 하나면 되기 때문입니다.

이 변환이 설명해 주는 것들

  • 재개 후 스레드가 바뀔 수 있다 — 스택이 아니라 힙에 상태가 있으니 어느 스레드든 이어받을 수 있습니다
  • ThreadLocal 이 사라진다 — 위와 같은 이유
  • 스택 트레이스가 짧다 — 호출 스택이 아니라 상태 기계 점프이기 때문. -Dkotlinx.coroutines.debug를 켜면 코루틴 경로가 복원됩니다
  • suspend 함수는 자바에서 부르기 어렵다 — Continuation 을 직접 만들어야 합니다. 자바용 API 는 CompletableFuture로 감싸 제공하세요
  • inline 함수 안의 suspend 는 비용이 없다 — 상태 기계가 호출 자리에 합쳐집니다
더 깊은 이야기는 전문가 탭에서 다룹니다 — 디스패처의 작업 훔치기(work-stealing) 스케줄러, DispatchedTask의 실행 경로, suspendCoroutineUninterceptedOrReturn 같은 저수준 API, 그리고 코루틴 성능을 측정하는 방법까지.

설계 규칙

함수를 만들 때

  • 공개 API 는 suspend fun f(): T 또는 fun f(): Flow<T>
  • 메인 세이프하게 — 디스패처 전환은 함수 안에서
  • 디스패처는 인자로 주입(기본값 제공) — 테스트를 위해
  • 긴 계산 루프에는 ensureActive()
  • 자원은 use·finally+NonCancellable로 반드시 정리

운영에서 볼 것

  • -Dkotlinx.coroutines.debug + CoroutineName으로 로그 추적
  • MDC 전파(MDCContext)로 traceId 유지 (11)
  • 디스패처별 스레드 수와 큐 길이를 지표로 노출
  • 블로킹 호출이 섞여 있는지 주기적으로 점검 (개발 환경에서 BlockHound로 탐지 가능)
  • 취소가 실제로 하위 시스템까지 전달되는지 확인 (DB 쿼리 취소 등)
