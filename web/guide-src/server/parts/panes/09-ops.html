SECTION 01

보안 헤더 7종

브라우저에게 "이렇게 지켜 줘"라고 부탁하는 한 줄들입니다. 설정만으로 여러 공격의 성공률을 크게 낮춥니다. 

# Nginx — server 블록에 (또는 snippets 로 빼서 include)
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header X-Frame-Options           "SAMEORIGIN" always;
add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
add_header Permissions-Policy        "geolocation=(), microphone=(), camera=()" always;
add_header Content-Security-Policy   "default-src 'self'; img-src 'self' data: https:; frame-ancestors 'self'" always;
add_header Cross-Origin-Opener-Policy "same-origin" always;

# 서버 정보 숨기기
server_tokens off;
헤더막는 것
Strict-Transport-Security HTTP 로 접속하려는 시도 자체를 브라우저가 차단 (SSL 스트리핑)
X-Content-Type-Options 브라우저의 MIME 타입 추측 — 업로드된 텍스트가 스크립트로 실행되는 것을 막습니다
X-Frame-Options 클릭재킹 — 우리 사이트를 남의 iframe 에 넣어 클릭을 가로채는 공격
Referrer-Policy 외부 사이트로 이동할 때 우리 URL(토큰이 포함될 수 있음)이 새는 것
Permissions-Policy 위치·카메라·마이크 등 브라우저 기능 접근 제한
Content-Security-Policy XSS 방어의 핵심 — 어디서 온 스크립트를 실행할지 통제
Cross-Origin-Opener-Policy 다른 출처 창과의 격리 (일부 사이드채널 공격 방어)
always 를 빠뜨리지 마세요. 없으면 2xx·3xx 응답에만 헤더가 붙고 4xx·5xx 오류 페이지에는 빠집니다. 오류 페이지도 공격 대상이 될 수 있으므로 모든 응답에 적용돼야 합니다.
또 Nginx 의 add_header 는 하위 블록에서 하나라도 쓰면 상위의 것이 전부 무효가 됩니다 — location 안에서 헤더를 추가할 때는 상위 헤더를 다시 써 주거나 include 로 관리하세요.

CSP — 가장 강력하지만 가장 까다롭습니다

# ① 먼저 리포트 전용으로 시작 (차단하지 않고 위반만 수집)
add_header Content-Security-Policy-Report-Only
  "default-src 'self'; report-uri /csp-report" always;

# ② 수집된 위반을 보고 정책을 다듬은 뒤
add_header Content-Security-Policy
  "default-src 'self';
   script-src 'self' https://cdn.example.com;
   style-src  'self' 'unsafe-inline';
   img-src    'self' data: https:;
   font-src   'self' data:;
   connect-src 'self' https://api.example.com;
   frame-ancestors 'self';
   base-uri 'self';
   form-action 'self'" always;
CSP 를 처음부터 강하게 걸면 사이트가 깨집니다.
① Report-Only 로 시작해 실제 위반을 수집하고
② 필요한 출처를 하나씩 허용한 뒤
③ 확신이 섰을 때 실제 정책으로 전환하세요
'unsafe-inline'·'unsafe-eval' 은 CSP 의 효과를 크게 떨어뜨리므로 가능하면 nonce·hash 방식으로 옮기세요. 
# Apache 는 mod_headers 로 같은 일을
Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains"
Header always set X-Content-Type-Options "nosniff"
Header always set X-Frame-Options "SAMEORIGIN"
Header always set Referrer-Policy "strict-origin-when-cross-origin"
Header unset Server
ServerTokens Prod
ServerSignature Off

공격자에게 정보를 주지 마세요. 정찰 단계를 어렵게 만듭니다.

# 지금 무엇이 노출되고 있는지 확인
curl -I https://example.com
HTTP/2 200 server: nginx/1.24.0 ← 버전 노출 (알려진 취약점을 바로 찾을 수 있습니다) x-powered-by: Express ← 프레임워크 노출 x-aspnet-version: 4.0.30319 ← 런타임 버전까지
# Nginx
server_tokens off;                          # "nginx/1.24.0" → "nginx"
proxy_hide_header X-Powered-By;             # 백엔드가 보낸 헤더 제거
proxy_hide_header X-AspNet-Version;
proxy_hide_header Server;

# 디렉터리 목록 금지 (기본값이지만 확인)

# 숨김 파일·백업 파일 차단
location ~ /\.(?!well-known) { deny all; }
location ~* \.(bak|old|sql|env|log|conf|ini|swp)$ { deny all; }
location ~* /(\.git|\.svn|\.env|composer\.(json|lock)|package-lock\.json)$ { deny all; }
실제로 자주 유출되는 것들
· /.git/ — 소스 코드 전체와 커밋 기록이 복원됩니다. 스캐너가 가장 먼저 찾습니다
· /.env — DB 비밀번호·API 키
· /backup.sql · /dump.sql — DB 전체
· /phpinfo.php — 서버 설정 전부
· /server-status · /nginx_status — 실시간 요청 정보
· 소스맵(.js.map) — 원본 코드 
# 우리 서버가 노출하고 있는지 직접 확인
for p in /.git/config /.env /backup.sql /phpinfo.php /server-status /.svn/entries; do
  code=$(curl -s -o /dev/null -w "%{http_code}" "https://example.com$p")
  echo "$code  $p"
done

SECTION 03

접근 제어 · IP 제한

관리자 경로는 인터넷 전체에 열어 둘 이유가 없습니다.

# IP 제한
location ^~ /admin/ {
    allow 10.0.0.0/8;              # 사내망
    allow 203.0.113.5;             # 사무실 고정 IP
    deny  all;

    proxy_pass http://backend;
}

# Basic 인증 추가 (이중 방어)
location ^~ /admin/ {
    allow 10.0.0.0/8;
    deny  all;

    auth_basic "Restricted";
    auth_basic_user_file /etc/nginx/.htpasswd;

    proxy_pass http://backend;
}

# 특정 메서드만 허용
location /api/public/ {
    limit_except GET HEAD { deny all; }
    proxy_pass http://backend;
}
# 비밀번호 파일 만들기
sudo apt install -y apache2-utils
sudo htpasswd -c /etc/nginx/.htpasswd admin
sudo chmod 640 /etc/nginx/.htpasswd
sudo chown root:www-data /etc/nginx/.htpasswd
프록시 뒤에서는 allow·deny 가 오작동합니다. $remote_addr 가 앞단 프록시의 IP 이기 때문입니다. CDN·LB 를 쓴다면 set_real_ip_from 으로 실제 IP 를 복원한 뒤에 접근 제어를 적용해야 합니다(🟩 Nginx n08).
이것을 놓치면 모든 요청이 차단되거나 모두 통과합니다.

더 나은 방법들

방법설명
VPN · 사설망★ 가장 확실합니다. 관리자 경로를 아예 인터넷에 노출하지 않습니다
SSH 터널 · 배스천점프 서버를 거쳐야만 접근 가능하게
IP 허용 목록고정 IP 가 있을 때. 재택근무면 관리가 번거롭습니다
mTLS클라이언트 인증서가 있어야 접근 (🔐 HTTPS s10)
제로트러스트 프록시Cloudflare Access 등 — SSO 인증 후 접근
공개 서비스에서도 제한할 것이 있습니다
· 관리자 페이지 · 모니터링 엔드포인트 (/actuator·/metrics)
· 개발용 문서 (/swagger·/graphql 플레이그라운드)
· 파일 업로드 경로의 실행 권한
· 내부 API (앞단에서만 호출되는 것)
SECTION 04

rate limit · DDoS 완화

서버에서 막을 수 있는 것과 막을 수 없는 것을 구분해야 합니다. 

# http 컨텍스트
limit_req_zone  $binary_remote_addr zone=general:10m rate=30r/s;
limit_req_zone  $binary_remote_addr zone=login:10m   rate=5r/m;
limit_conn_zone $binary_remote_addr zone=perip:10m;

limit_req_status  429;
limit_conn_status 429;

server {
    limit_req  zone=general burst=60 nodelay;
    limit_conn perip 20;

    # 로그인·인증은 강하게
    location = /api/login {
        limit_req zone=login burst=3 nodelay;
        proxy_pass http://backend;
    }

    # 헬스체크·정적은 제외
    location = /health { limit_req off; return 200 "ok\n"; }
}
공격 유형Nginx 로 막을 수 있나
단일 IP 폭주✓ limit_req
무차별 대입 (로그인)✓ rate limit + fail2ban
크롤러 폭주✓ User-Agent 필터 + rate limit
Slowloris (느린 연결 다수)✓ client_body_timeout·limit_conn
분산 DDoS (수만 IP)✗ 서버에 도달하기 전에 막아야 합니다 — CDN·클라우드 방화벽
대역폭 소진 공격✗ 회선이 먼저 막힙니다 — ISP·CDN 영역
대규모 DDoS 는 서버 설정으로 막을 수 없습니다. 수만 대에서 오는 트래픽이 회선을 가득 채우면 Nginx 가 아무리 빨라도 소용이 없습니다.
CDN·클라우드 DDoS 방어 서비스를 앞에 두는 것이 유일한 실효적 대책입니다. Nginx 의 rate limit 은 어뷰징과 소규모 공격에 효과적입니다.

fail2ban — 반복 실패 IP 차단

# /etc/fail2ban/jail.local
[nginx-limit-req]
enabled  = true
filter   = nginx-limit-req
logpath  = /var/log/nginx/error.log
maxretry = 10
findtime = 60
bantime  = 3600
action   = iptables-multiport[name=ReqLimit, port="http,https"]

[nginx-badbots]
enabled  = true
filter   = nginx-badbots
logpath  = /var/log/nginx/access.log
maxretry = 2
bantime  = 86400
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status nginx-limit-req
sudo fail2ban-client set nginx-limit-req unbanip 1.2.3.4    # 오탐 해제

Slowloris 방어

# 연결을 열어 두고 아주 천천히 보내는 공격
client_body_timeout   10s;      # 본문 수신 타임아웃
client_header_timeout 10s;      # 헤더 수신 타임아웃
send_timeout          10s;      # 응답 전송 타임아웃
limit_conn perip 20;            # IP 당 동시 연결 제한

# Nginx 는 이벤트 기반이라 구조적으로 Slowloris 에 강하지만
# 위 설정으로 자원 점유를 더 확실히 제한할 수 있습니다
SECTION 05

WAF (ModSecurity)

알려진 공격 패턴을 요청 단계에서 걸러 냅니다.

# Nginx + ModSecurity (동적 모듈)
sudo apt install -y libmodsecurity3 nginx-module-modsecurity   # 배포판에 따라 다름

# OWASP Core Rule Set (CRS) — 사실상 표준 규칙 모음
cd /etc/nginx
sudo git clone https://github.com/coreruleset/coreruleset.git modsec-crs
sudo cp modsec-crs/crs-setup.conf.example modsec-crs/crs-setup.conf
# nginx.conf 최상단
load_module modules/ngx_http_modsecurity_module.so;

server {
    modsecurity on;
    modsecurity_rules_file /etc/nginx/modsec/main.conf;
}

# /etc/nginx/modsec/main.conf
# Include /etc/nginx/modsec/modsecurity.conf
# Include /etc/nginx/modsec-crs/crs-setup.conf
# Include /etc/nginx/modsec-crs/rules/*.conf
# modsecurity.conf 의 핵심 설정
SecRuleEngine DetectionOnly        # ★ 처음에는 탐지만 (차단하지 않음)
# SecRuleEngine On                 # 검증 후 차단 모드로

SecAuditEngine RelevantOnly
SecAuditLog /var/log/nginx/modsec_audit.log
SecRequestBodyLimit 13107200       # 업로드 크기와 맞추세요
WAF 의 가장 큰 문제는 오탐(false positive)입니다. 정상 요청이 차단되어 사용자가 서비스를 못 쓰는 사고가 흔합니다.
· 반드시 DetectionOnly 로 시작해 감사 로그를 수집하고
· 오탐 규칙을 하나씩 예외 처리한 뒤
· 충분히 검증되면 차단 모드로 전환하세요
파일 업로드·리치 텍스트 에디터·JSON API 에서 오탐이 특히 잦습니다. 
# 오탐 예외 처리
# 특정 경로에서 특정 규칙 끄기
SecRule REQUEST_URI "@beginsWith /api/upload" \
    "id:1000,phase:1,pass,nolog,ctl:ruleRemoveById=942100"

# 특정 파라미터를 검사에서 제외
SecRule REQUEST_URI "@beginsWith /admin/post" \
    "id:1001,phase:2,pass,nolog,ctl:ruleRemoveTargetById=941100;ARGS:content"
WAF 를 도입하기 전에 — 애플리케이션 레벨 방어가 먼저입니다. 파라미터 바인딩(SQL 인젝션) · 출력 이스케이프(XSS) · CSRF 토큰이 제대로 돼 있다면 WAF 는 추가 방어층일 뿐입니다.
WAF 는 알려지지 않은 취약점의 시간을 벌어 주는 역할이고, 운영 비용(오탐 조정·성능)이 만만치 않습니다.
부담이 크다면 클라우드 WAF(관리형)를 쓰는 것이 현실적입니다.
SECTION 06

파일 업로드 보안

업로드 폴더에서 스크립트가 실행되면 서버가 통째로 넘어갑니다. 침해 사고의 대표적인 경로입니다. 

# ★ 업로드 폴더에서 실행 차단 (Nginx)
location ^~ /uploads/ {
    alias /var/data/uploads/;

    # PHP·CGI 실행 금지
    location ~ \.(php|phtml|php[0-9]|pl|py|cgi|sh|jsp|asp)$ { deny all; }

    # 브라우저에서 실행되지 않고 다운로드되게
    add_header Content-Disposition "attachment" always;
    add_header X-Content-Type-Options "nosniff" always;

    # HTML·SVG 도 위험합니다 (XSS)
    types { }
    default_type application/octet-stream;
}
SVG 는 이미지가 아니라 실행 가능한 문서입니다. SVG 안에 <script> 를 넣을 수 있어 같은 도메인에서 XSS 가 발생합니다.
· 사용자 업로드 SVG 는 별도 도메인에서 서빙하거나
· Content-Disposition: attachment 로 강제 다운로드하거나
· 서버에서 SVG 를 정제(sanitize) 하세요

업로드 보안 체크리스트

항목내용
저장 위치 ★ 문서 루트 밖에 저장하고 앱을 통해 제공하거나, 별도 스토리지(S3)를 쓰는 것이 가장 안전합니다
파일명 사용자 입력을 그대로 쓰지 말고 UUID 로 재생성. 경로 순회(../)와 널 바이트를 차단
확장자 검증 허용 목록으로. 차단 목록은 우회됩니다(.pHp·.php5·이중 확장자)
내용 검증 확장자만 믿지 말고 매직 넘버로 실제 형식을 확인
크기 제한 웹서버·앱 양쪽에 설정 (디스크 소진 방지)
실행 권한 저장된 파일은 chmod 644 · 폴더에 실행 비트 제거
이미지 재처리 이미지는 서버에서 다시 인코딩하면 내장된 악성 코드가 제거됩니다
바이러스 검사 파일 공유 서비스라면 ClamAV 등으로 검사
# 앱 레벨 검증 예 (Python)
import uuid, pathlib, imghdr

ALLOWED = {'.jpg', '.jpeg', '.png', '.gif', '.webp'}
MAX_SIZE = 10 * 1024 * 1024

def save_upload(file, dest_dir):
    ext = pathlib.Path(file.filename).suffix.lower()
    if ext not in ALLOWED:
        raise ValueError("허용되지 않은 확장자")
    if file.size > MAX_SIZE:
        raise ValueError("파일이 너무 큽니다")

    # ★ 실제 내용이 이미지인지 확인 (확장자만 믿지 않습니다)
    head = file.read(512); file.seek(0)
    if imghdr.what(None, head) is None:
        raise ValueError("이미지 파일이 아닙니다")

    # ★ 파일명을 새로 생성 (경로 순회·덮어쓰기 방지)
    name = f"{uuid.uuid4().hex}{ext}"
    path = pathlib.Path(dest_dir) / name
    path.write_bytes(file.read())
    path.chmod(0o644)
    return name

로그 관리 · 로테이션

로그를 방치하면 디스크가 가득 차서 서비스가 멈춥니다.

# /etc/logrotate.d/nginx (보통 패키지에 포함돼 있습니다)
/var/log/nginx/*.log {
    daily
    rotate 30                  # 30일 보관
    missingok
    notifempty
    compress
    delaycompress
    create 0640 www-data adm
    sharedscripts
    postrotate
        # ★ Nginx 에게 로그 파일을 다시 열라고 알립니다
        [ -f /var/run/nginx.pid ] && kill -USR1 $(cat /var/run/nginx.pid)
    endscript
}
로테이션 후 시그널을 보내지 않으면 Nginx 가 이름이 바뀐 옛 파일에 계속 씁니다. 새 파일은 0바이트로 남고 디스크는 계속 차오릅니다.
· Nginx — kill -USR1 (또는 nginx -s reopen)
· 톰캣 catalina.out — copytruncate 사용 
# 테스트 (실제로 돌려 보기)

sudo logrotate -f /etc/logrotate.d/nginx        # 강제 실행

# 가장 큰 로그 파일 찾기

롤링 배포 — Nginx 로

#!/usr/bin/env bash
set -euo pipefail
SERVERS=(10.0.1.11 10.0.1.12 10.0.1.13)

for s in "${SERVERS[@]}"; do
  echo "==== $s 배포 시작"

  # 1) LB 에서 제외 (해당 server 줄에 down 을 붙이고 reload)
  sudo sed -i "s|server $s:8080;|server $s:8080 down;|" /etc/nginx/conf.d/upstream.conf
  sudo nginx -t && sudo nginx -s reload

  # 2) 진행 중 요청이 끝나기를 기다림
  sleep 10

  # 3) 배포
  ssh "deploy@$s" 'sudo systemctl stop myapp && \
                   sudo cp /tmp/myapp.jar /opt/myapp/myapp.jar && \
                   sudo systemctl start myapp'

  # 4) 준비될 때까지 대기
  for i in $(seq 1 30); do
    curl -fsS "http://$s:8080/health" >/dev/null && break
    sleep 2
  done

  # 5) LB 에 복귀
  sudo sed -i "s|server $s:8080 down;|server $s:8080;|" /etc/nginx/conf.d/upstream.conf
  sudo nginx -t && sudo nginx -s reload

  echo "==== $s 완료"
  sleep 5
done

· DB 스키마 — 신구 버전이 동시에 도는 동안 양쪽 모두 동작해야 합니다 (확장-축소 패턴 → 🗄️ DB 가이드)

· 진행 중인 배치 — 종료 시 중단되면 데이터가 반만 처리될 수 있습니다

# Ansible 예시 — 여러 서버에 같은 설정을 재현 가능하게
- name: Nginx 설정 배포
  hosts: web
  become: yes
  tasks:
    - name: 설정 파일 템플릿
      template:
        src: nginx-site.conf.j2
        dest: /etc/nginx/sites-available/myapp
        owner: root
        mode: '0644'
      notify: reload nginx

    - name: 사이트 활성화
      file:
        src: /etc/nginx/sites-available/myapp
        dest: /etc/nginx/sites-enabled/myapp
        state: link
      notify: reload nginx

      # ★ 문법 검사를 먼저
      shell: nginx -t && systemctl reload nginx

컨테이너 · 쿠버네티스

쿠버네티스에서는 Ingress 가 Nginx 역할을 합니다. 개념은 그대로입니다. 

# Ingress — Nginx 의 server 블록에 해당합니다
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  annotations:
    # Nginx 설정을 애노테이션으로 지정합니다
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/limit-rps: "30"
    cert-manager.io/cluster-issuer: letsencrypt-prod    # 인증서 자동 발급
spec:
  ingressClassName: nginx
  tls:
    - hosts: [example.com]
      secretName: example-tls
  rules:
    - host: example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api-service, port: { number: 8080 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: web-service, port: { number: 80 } }
전통적 구성쿠버네티스
server 블록Ingress 리소스
upstreamService (엔드포인트 자동 관리)
locationIngress 의 path
certbotcert-manager (자동 발급·갱신)
systemd 재시작Deployment 롤링 업데이트
헬스체크 스크립트liveness · readiness Probe
Nginx 설정 파일Ingress Controller 의 애노테이션·ConfigMap
 
# 무중단 배포에 필요한 설정 — 이 셋이 핵심입니다
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 항상 최소 대수 유지
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: app
          readinessProbe:              # ★ 준비되기 전에는 트래픽을 안 보냄
            httpGet: { path: /health/ready, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:               # 죽었으면 재시작
            httpGet: { path: /health/live, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                # ★ LB 에서 빠질 시간을 벌어 줍니다
                command: ["sh", "-c", "sleep 10"]
preStop 의 sleep 이 필요한 이유 — 파드가 종료될 때 엔드포인트 목록에서 빠지는 것과 SIGTERM 을 받는 것이 동시에 일어납니다. 그래서 이미 라우팅된 요청이 종료 중인 파드에 도달해 502 가 납니다.
preStop 으로 몇 초를 벌면 그동안 LB 갱신이 완료됩니다.
기본기는 그대로입니다. 쿠버네티스를 쓰더라도 프록시·타임아웃·헤더·캐시·TLS 의 개념은 같습니다. Ingress Controller 대부분이 내부적으로 Nginx 를 씁니다. 이 가이드의 내용이 그대로 적용되며, 설정 방법만 애노테이션으로 바뀝니다.
SECTION 12

장애 대응 시나리오

자주 나는 유형과 대응 순서입니다. 당황하지 않는 것이 절반입니다.

증상확인 순서 → 조치
502 급증 ① error 로그에서 connect() failed 확인 → ② 앱 프로세스 상태(systemctl status) → ③ 앱에 직접 요청(curl localhost:8080) → ④ 앱 로그에서 OOM·예외 확인 → ⑤ 필요하면 앱 재시작
504 급증 ① 앱 응답 시간 확인 → ② 대개 DB 쿼리·외부 API 지연 → ③ DB 슬로우 쿼리·락 확인 → ④ 문제 기능을 일시 차단하는 것도 방법
전면 무응답 ① Nginx 프로세스 생존 확인 → ② ss -s 로 연결 상태 → ③ 디스크 여유(df -h) → ④ 파일 디스크립터 한계 → ⑤ 로드 애버리지·스왑
디스크 가득 참 ① du -sh /var/log/* /var/cache/* → ② 큰 로그를 지우지 말고 truncate(: > file) → ③ 로테이션 설정 점검 → ④ 근본 원인 제거
인증서 만료 ① certbot renew --force-renewal → ② reload → ③ 갱신 자동화가 왜 실패했는지 확인
특정 IP 폭주 ① access 로그에서 상위 IP 확인 → ② 임시 차단(deny + reload) → ③ rate limit 조정 → ④ fail2ban 규칙 추가
배포 후 오류 ① 먼저 롤백 → ② 그다음 원인 분석
원인을 찾느라 장애를 길게 끌지 마세요
# 장애 시 첫 5분에 실행할 명령 모음
systemctl status nginx myapp --no-pager
sudo tail -100 /var/log/nginx/error.log
sudo journalctl -u myapp --since "10 min ago" -p err --no-pager
df -h; free -h; uptime
ss -s
curl -sS -o /dev/null -w "%{http_code} %{time_total}\n" http://127.0.0.1:8080/health

# 상태 코드 분포 (최근 1000건)
tail -1000 /var/log/nginx/access.log | awk '{print $9}' | sort | uniq -c | sort -rn

# 응답이 느린 요청
tail -5000 /var/log/nginx/access.log | awk '$NF > 1 {print $NF, $7}' | sort -rn | head -20
장애 중에 하지 말아야 할 것
· 여러 조치를 동시에 — 무엇이 효과였는지 알 수 없게 됩니다
· 상태 수집 없이 재시작 — 원인이 사라지고 다시 같은 장애가 납니다
· 혼자 판단하고 되돌릴 수 없는 조치 — 데이터 삭제·강제 복구는 반드시 공유 후에
· 원인 분석을 먼저 — 서비스 복구가 우선입니다. 분석은 그다음
사후에 반드시 할 것 — 비난하지 않는 회고(blameless postmortem)를 씁니다. "왜 이 상황이 가능했는가", "왜 더 일찍 알지 못했는가", "다음에 같은 일이 생기면 자동으로 막히는가". 사람을 탓하면 진짜 원인이 숨겨집니다.

  • 가장 많이 호출되는 URL — 예상과 다른 것이 있는지
  • 4xx 급증 여부 (스캔·어뷰징 신호)
  • 로그·캐시 디스크 증가 추이

매월

  • 보안 패치 적용 — apt list --upgradable
  • 인증서 만료일 확인 (자동 갱신이 돌고 있어도 눈으로 한 번)
  • 불필요한 열린 포트 점검 (ss -lntp)
  • 접근 권한 검토 — SSH 키·계정·sudo 권한
  • 설정 파일이 git 과 일치하는지 (git status)

분기

  • 백업에서 실제로 복구해 보기 — 이것을 안 하면 백업은 없는 것과 같습니다
  • 부하 테스트로 현재 용량 재측정
  • SSL Labs 등급 재확인
  • 노출된 경로 점검 (/.git·/.env 등)
  • 장애 대응 절차 문서 갱신
#!/usr/bin/env bash
# 매일 돌리는 점검 스크립트 예시
echo "===== $(date) 점검 ====="

echo "-- 디스크"
df -h | awk '$5+0 > 80 {print "  경고: " $6 " " $5}'

echo "-- 서비스"
for s in nginx myapp; do
  systemctl is-active --quiet $s && echo "  $s: 정상" || echo "  $s: 중지됨 ★"
done

echo "-- 인증서"
for d in example.com api.example.com; do
  end=$(echo | openssl s_client -connect "$d:443" -servername "$d" 2>/dev/null \
        | openssl x509 -noout -enddate | cut -d= -f2)
  left=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
  [ "$left" -lt 21 ] && echo "  경고: $d ${left}일 남음 ★" || echo "  $d: ${left}일"
done

echo "-- 최근 1시간 5xx"
awk -v d="$(date -d '1 hour ago' '+%d/%b/%Y:%H')" '$4 ~ d && $9 ~ /^5/' \
  /var/log/nginx/access.log | wc -l
SECTION 14

취약점 대응 · 패치

"잘 돌아가니까 건드리지 말자"가 가장 위험한 태도입니다. 

# 현재 버전 확인
nginx -v
apachectl -v
java -version
node -v

# 업데이트 가능 목록
apt list --upgradable 2>/dev/null | grep -E 'nginx|apache|openssl|openjdk'

# 보안 업데이트만 적용 (Ubuntu)
sudo unattended-upgrade --dry-run -d
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

# 재시작이 필요한 서비스 확인
sudo apt install -y needrestart
sudo needrestart -r l
정보원내용
배포판 보안 공지Ubuntu USN · RHEL RHSA — 패키지 단위로 알려 줍니다
Nginx 보안 공지nginx.org/en/security_advisories.html
Apache 보안 공지httpd.apache.org/security_report.html
Tomcat 보안 공지tomcat.apache.org/security.html — CVE 가 자주 나옵니다
KISA · CERT국내 보안 공지
이미지 스캔Trivy · Grype — 컨테이너 이미지의 취약점 검사
# 컨테이너 이미지 취약점 스캔
trivy image nginx:1.28
trivy image --severity HIGH,CRITICAL myapp:latest

# CI 에 넣어 취약한 이미지가 배포되지 않게
trivy image --exit-code 1 --severity CRITICAL myapp:latest

패치 절차

1
영향 여부 확인 CVE 가 우리 버전·우리가 쓰는 기능에 해당하는지. 모든 CVE 가 우리에게 위험한 것은 아닙니다.
▼
2
스테이징에서 먼저 패치가 기존 동작을 깨뜨리지 않는지 확인합니다.
▼
3
롤백 계획을 준비하고 적용 이전 버전 패키지를 보관하거나 스냅숏을 떠 둡니다.
▼
4
재시작이 필요한지 확인 OpenSSL 같은 라이브러리는 이를 쓰는 모든 서비스를 재시작해야 반영됩니다.
라이브러리 패치의 함정 — libssl 을 업데이트해도 이미 실행 중인 프로세스는 옛 라이브러리를 메모리에 들고 있습니다. needrestart 나 lsof | grep DEL 로 재시작이 필요한 서비스를 찾아 반드시 재시작하세요.
"패치는 했는데 여전히 취약한" 상태가 실제로 자주 발생합니다.
현실적인 정책
· 보안 업데이트는 자동 적용(unattended-upgrades) — 대부분의 경우 안전합니다
· 메이저 업그레이드는 계획적으로 — 분기 단위로
· EOL(지원 종료) 버전은 쓰지 않기 — 패치 자체가 나오지 않습니다
· 컨테이너라면 베이스 이미지를 주기적으로 새로 빌드하세요
