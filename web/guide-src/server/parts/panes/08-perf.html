SECTION 01

성능 지표 읽기

평균은 거짓말을 합니다. 백분위(percentile)로 말해야 합니다.

지표의미
RPS · TPS초당 처리한 요청 수 — 처리량
지연 (latency)요청 하나에 걸린 시간 — 체감 속도
p50 (중앙값)절반의 사용자가 이보다 빠름
p95 · p99★ 상위 5%·1% 느린 요청 — 실제 불만이 여기서 나옵니다
동시 접속같은 시점에 열려 있는 연결 수
오류율5xx 비율 — 성능 문제는 오류로 나타나는 경우가 많습니다
포화도CPU·메모리·커넥션 풀의 사용률 — 한계에 얼마나 가까운가
왜 평균이 아니라 p99 인가 — 응답 시간 100건 중 99건이 50ms, 1건이 5초라면 평균은 99.5ms 로 훌륭해 보입니다. 그런데 그 1건을 겪은 사용자는 "사이트가 멈췄다"고 느낍니다.
페이지 하나가 요청 50개를 보낸다면, p99 가 5초일 때 사용자의 40%가 최소 한 번은 그 5초를 경험합니다. 꼬리 지연(tail latency)이 실제 체감을 지배합니다. 
# Nginx 로그에서 백분위 계산 (log_format 에 $request_time 이 있어야 합니다)
awk '{print $NF}' /var/log/nginx/access.log | sort -n | awk '
{ a[NR] = $1 }
END {
  printf "count=%d\n", NR
  printf "p50=%.3f\n", a[int(NR*0.50)]
  printf "p95=%.3f\n", a[int(NR*0.95)]
  printf "p99=%.3f\n", a[int(NR*0.99)]
  printf "max=%.3f\n", a[NR]
}'
count=48213 p50=0.042 p95=0.310 p99=1.850 ← 여기를 봐야 합니다 max=30.002

목표를 먼저 정하세요

나쁜 목표 : "빠르게 만들자"
좋은 목표 : "상품 목록 API 를 p95 200ms 이내로, 초당 300건 처리"

이렇게 정하면
· 달성했는지 판단할 수 있고
· 어디까지 최적화할지 멈출 지점이 생기고
· 부하 테스트 시나리오가 저절로 나옵니다
용량 산정의 기본 공식
필요 동시 처리 수 ≈ 목표 RPS × 평균 응답 시간(초)
목표 300 RPS · 평균 0.2초 → 동시 60건을 처리할 수 있어야 합니다. 여기에 여유 2배를 두고 워커·스레드·커넥션 풀을 설계합니다.
SECTION 02

worker 수와 커넥션

Nginx 의 가장 기본적인 용량 설정입니다.

worker_processes auto;             # CPU 코어 수만큼 (권장)
worker_rlimit_nofile 65535;        # 워커당 열 수 있는 파일·소켓 수

events {
    worker_connections 4096;       # 워커 하나가 다룰 최대 연결
    multi_accept on;
    use epoll;                     # 리눅스 기본 (명시 불필요)
}
동시 처리 가능 연결 수
worker_processes × worker_connections
다만 프록시는 연결을 2개 씁니다(클라이언트 1 + 업스트림 1). 그래서 실제 동시 사용자는 절반 정도로 봐야 합니다.
8코어 × 4096 = 32,768 → 프록시 기준 약 16,000 동시 요청
설정지침
worker_processes auto 로 두세요. 코어보다 많이 만들면 오히려 손해입니다
worker_connections Nginx 기본값은 512, 배포판 설정 파일은 보통 768~1024 → 4096~8192 로. worker_rlimit_nofile 보다 작아야 합니다
worker_rlimit_nofile 시스템 ulimit -n 을 넘을 수 없습니다 — systemd 설정도 함께(p10)
worker_cpu_affinity 워커를 특정 코어에 고정. 대부분 필요 없습니다
# 현재 상태 확인
nproc                                    # CPU 코어 수
ulimit -n                                # 열 수 있는 파일 수
cat /proc/$(pgrep -f 'nginx: master')/limits | grep 'open files'

# 실제 연결 수 (stub_status 활성화 필요 — o08 참고)
curl -s http://127.0.0.1/nginx_status
Active connections: 291 server accepts handled requests 16630948 16630948 31070465 Reading: 6 Writing: 179 Waiting: 106
읽는 법 — Active 가 worker_processes × worker_connections 에 가까워지면 한계입니다. Waiting 이 크면 keepalive 연결이 많다는 뜻으로 정상입니다. accepts 와 handled 가 다르면 연결을 거부한 것이므로 즉시 조치가 필요합니다.
같은 하드웨어에서 동시 연결 수가 수십 배 차이 나는 이유는 튜닝이 아니라 이 구조입니다.

서버별 동시성 모델 — 무엇을 쓰고 있는지 확인하세요

서버모델대략적 한계주의
Nginx이벤트 루프 (워커 = 코어 수)수만 연결블로킹 모듈을 넣으면 무너집니다
Caddy고루틴 (경량 스레드)수만 연결Go 런타임이 스케줄링
Apache event혼합 — 대기는 이벤트, 처리는 스레드수천~1만HTTP/2 는 이것이 필요
Apache worker프로세스 × 스레드수천—
Apache prefork연결당 프로세스수백mod_php 때문에 아직 쓰입니다

SECTION 03

keepalive 이해하기

연결을 끊지 않고 재사용하는 것입니다. 연결을 새로 맺는 비용이 생각보다 큽니다.

keepalive 없음
요청마다
  TCP 3-way 핸드셰이크 (1 RTT)
+ TLS 핸드셰이크        (1~2 RTT)
+ 실제 요청·응답        (1 RTT)
= 3~4 RTT

지연 50ms 환경이면 요청당 150~200ms 가
'연결 맺는 데만' 소모됩니다
keepalive 사용
첫 요청만 핸드셰이크
이후 요청은 실제 요청·응답만 (1 RTT)

페이지 하나에 요청 50개라면
차이가 압도적입니다
# ── 클라이언트 ↔ Nginx
keepalive_timeout 65s;             # 유휴 연결 유지 시간
keepalive_requests 1000;           # 한 연결로 처리할 최대 요청 수

# ── Nginx ↔ 백엔드 (★ 기본이 꺼져 있어 매번 새로 연결합니다)
upstream backend {
    server 127.0.0.1:8080;
    keepalive 64;                  # 워커당 유지할 유휴 연결 수
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;         # ★ 1.0 은 keepalive 미지원
        proxy_set_header Connection "";  # ★ 기본 'close' 헤더를 지웁니다
    }
}
업스트림 keepalive 는 세 가지를 모두 해야 동작합니다.
① upstream 블록에 keepalive N;
② proxy_http_version 1.1;
③ proxy_set_header Connection "";
하나라도 빠지면 매 요청마다 새 TCP 연결을 맺습니다. 이것만 고쳐도 지연이 눈에 띄게 줄어드는 경우가 많습니다.

트레이드오프

값을 늘리면효과
keepalive_timeout ↑ 재사용률 상승 · 유휴 연결이 자원을 점유
keepalive_requests ↑ 핸드셰이크 감소 · 한 연결에 편중될 수 있음
upstream keepalive ↑ 백엔드 연결 비용 감소 · 백엔드가 유지할 연결이 늘어남
백엔드 쪽 타임아웃과 맞추세요. 백엔드의 유휴 타임아웃이 Nginx 의 keepalive_timeout 보다 짧으면, Nginx 가 이미 끊긴 연결로 요청을 보내다 502 가 간헐적으로 발생합니다.
Nginx 쪽을 백엔드보다 짧게 잡는 것이 안전합니다.
SECTION 04

정적 파일 최적화

가장 값싸고 효과가 큰 최적화입니다. 요청 자체를 없앱니다.

http {
    sendfile on;                   # ★ 커널이 직접 전송 (유저 공간 복사 생략)
    tcp_nopush on;                 # 헤더와 본문을 모아서 전송
    tcp_nodelay on;                # keepalive 연결에서는 즉시 전송

    # 파일 메타데이터 캐시 (자주 요청되는 정적 파일에 효과적)
    open_file_cache          max=10000 inactive=60s;
    open_file_cache_valid    60s;
    open_file_cache_min_uses 2;
    open_file_cache_errors   on;
}

server {
    # 해시가 붙은 빌드 산출물 — 영구 캐시
    location ~* \.[0-9a-f]{8,}\.(js|css|woff2?|png|jpe?g|svg|webp|avif)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 일반 이미지
    location ~* \.(png|jpe?g|gif|svg|ico|webp|avif)$ {
        expires 30d;
        add_header Cache-Control "public";
        access_log off;
    }

    # HTML 은 캐시하지 않음
    location ~* \.html$ {
        add_header Cache-Control "no-store, must-revalidate";
    }
}
캐시 헤더동작
max-age=315360001년간 재요청하지 않음
immutable새로고침해도 재검증하지 않음 — 해시 붙은 파일에 필수
publicCDN·프록시도 캐시 가능
private브라우저만 캐시 (사용자별 응답)
no-store어디에도 저장 금지
must-revalidate만료되면 반드시 서버에 확인
stale-while-revalidate=60만료된 것을 주면서 뒤에서 갱신 (체감 속도 개선)
가장 빠른 요청은 보내지 않는 요청입니다. 캐시 헤더 한 줄로 재방문자의 요청 수십 개가 아예 발생하지 않습니다. 서버 부하도 줄고 사용자 체감도 개선되는, 드물게 양쪽 모두에 좋은 최적화입니다.

ETag 와 조건부 요청

etag on;                          # 기본값 (파일 크기+수정시각 기반)

# 브라우저가 If-None-Match 로 물으면 Nginx 가 304 Not Modified 로 응답
# → 본문 전송 없이 "안 바뀌었다"만 알려 줍니다

# 여러 서버가 같은 파일을 서빙할 때 ETag 가 달라지면 캐시 효율이 떨어집니다
# 이 경우 파일 해시 기반 파일명 + immutable 조합이 더 확실합니다
# 캐시가 실제로 동작하는지 확인
curl -I https://example.com/app.a1b2c3.js
# cache-control: public, immutable
# expires: ...

# 조건부 요청 테스트
curl -I -H 'If-None-Match: "abc123"' https://example.com/style.css
# HTTP/2 304   ← 본문을 안 보냄
SECTION 05

압축 전략

CPU 를 써서 전송량을 줄이는 거래입니다. 균형점이 있습니다.

gzip on;
gzip_vary on;                      # ★ Vary: Accept-Encoding
gzip_comp_level 5;                 # 1~9 · 5~6 이 최적
gzip_min_length 1024;              # 작은 파일은 압축 이득이 없습니다
gzip_proxied any;
gzip_types
    text/plain text/css text/xml
    application/json application/javascript application/xml+rss
    image/svg+xml font/ttf font/otf;

# 미리 압축된 파일이 있으면 그것을 사용 (CPU 0)
gzip_static on;

# brotli (모듈 필요) — gzip 보다 15~20% 더 작습니다
brotli on;
brotli_comp_level 5;
brotli_types text/plain text/css application/json application/javascript image/svg+xml;
brotli_static on;
레벨크기 감소CPU
gzip 1보통매우 낮음
gzip 5~6거의 최대치적정
gzip 96 대비 1~2% 추가몇 배 증가
brotli 5gzip 대비 15~20% 더 작음적정
brotli 11최대매우 높음 — 사전 압축 전용
이미 압축된 것을 또 압축하지 마세요. JPG·PNG·WebP·MP4·ZIP·woff2 는 이미 압축된 형식입니다. 다시 압축하면 CPU 만 쓰고 크기는 오히려 커질 수 있습니다. gzip_types 에 이미지·동영상을 넣지 마세요.

사전 압축 — 가장 좋은 방법

# 빌드 시점에 최고 레벨로 압축해 둡니다
find dist -type f \( -name '*.js' -o -name '*.css' -o -name '*.html' -o -name '*.svg' \) \
  -exec gzip -9 -k {} \; \
  -exec brotli -q 11 -k {} \;

# Nginx 는 요청 시 app.js.br · app.js.gz 를 찾아 그대로 전송합니다
# → 압축 CPU 0 · 압축률 최대
정적 파일은 사전 압축, 동적 응답은 실시간 압축(레벨 5). 이 조합이 CPU 와 전송량의 균형을 가장 잘 맞춥니다.
트래픽이 아주 많은 서버에서는 압축이 CPU 병목이 될 수 있으니 top 으로 Nginx 워커의 CPU 사용률을 확인하세요. 
# 압축이 적용되는지 확인
curl -H "Accept-Encoding: gzip, br" -I https://example.com/app.js | grep -i content-encoding

# 크기 비교
curl -s https://example.com/app.js | wc -c                          # 원본
curl -s -H "Accept-Encoding: gzip" https://example.com/app.js | wc -c  # 압축
SECTION 06

프록시 버퍼링

느린 클라이언트가 앱 워커를 붙잡지 못하게 막는 중요한 장치입니다.

버퍼링 없음
앱 → (느린 3G 사용자에게 직접 전송)

응답 1MB 를 보내는 데 10초가 걸리면
그동안 앱 워커가 계속 묶여 있습니다

워커 200개인데 느린 사용자 200명이면
서비스 전체가 멈춥니다
버퍼링 사용 (기본값)
앱 → Nginx 가 응답 전체를 즉시 받아 저장
     (앱 워커는 바로 풀려납니다)
Nginx → 느린 사용자에게 천천히 전송

앱은 빠른 Nginx 만 상대하면 됩니다
느린 클라이언트는 Nginx 가 흡수합니다
location / {
    proxy_pass http://backend;

    proxy_buffering on;              # 기본값 · 켜 두세요
    proxy_buffer_size 8k;            # 응답 헤더용 버퍼
    proxy_buffers 16 8k;             # 본문 버퍼 개수 × 크기 (= 128k)
    proxy_busy_buffers_size 16k;

    # 버퍼를 넘으면 임시 파일에 씁니다
    proxy_max_temp_file_size 1024m;
    proxy_temp_file_write_size 16k;
    proxy_temp_path /var/cache/nginx/proxy_temp;
}

버퍼링을 꺼야 하는 경우

# SSE · 실시간 스트리밍 — 버퍼링하면 이벤트가 모였다가 한꺼번에 갑니다
location /events {
    proxy_pass http://backend;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    add_header X-Accel-Buffering no;
}

# 대용량 업로드 — 요청 본문 버퍼링을 끄고 스트리밍
location /upload {
    proxy_pass http://backend;
    proxy_request_buffering off;
    client_max_body_size 500m;
}
앱에서 응답별로 끄는 방법 — 응답 헤더에 X-Accel-Buffering: no 를 넣으면 그 응답만 버퍼링이 꺼집니다. location 전체를 바꾸지 않아도 되어 편리합니다.
upstream sent too big header 오류가 나면 proxy_buffer_size 를 늘려야 합니다. 세션 쿠키가 많거나 헤더가 큰 응답에서 발생합니다.
proxy_buffer_size 16k; proxy_busy_buffers_size 24k; 
# 임시 파일이 많이 생기면 버퍼가 부족하다는 신호입니다
ls -l /var/cache/nginx/proxy_temp/ | head
watch -n1 'ls /var/cache/nginx/proxy_temp/ | wc -l'

# 디스크 IO 가 부담되면 proxy_buffers 를 늘려 메모리에서 처리하세요
SECTION 07

업스트림 커넥션 재사용

p03 의 keepalive 를 백엔드 쪽에 적용하는 이야기입니다. 효과가 큽니다.

upstream backend {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;

    keepalive 64;                  # ★ 워커당 유지할 유휴 연결 수
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
keepalive 값 정하기 — 워커당 값이므로 실제 유지 연결은 worker_processes × keepalive 입니다. 8코어에 keepalive 64 면 백엔드에 최대 512개 유휴 연결이 유지됩니다.
백엔드가 감당할 수 있는지 확인하세요 — 톰캣 maxConnections · Node 의 파일 디스크립터 한계에 걸릴 수 있습니다.

HTTPS 업스트림이라면

upstream backend_ssl {
    server backend.internal:443;
    keepalive 32;
}

location / {
    proxy_pass https://backend_ssl;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_ssl_session_reuse on;         # ★ TLS 세션 재사용 (핸드셰이크 생략)
    proxy_ssl_server_name on;           # SNI 전송
    proxy_ssl_name backend.internal;
    proxy_ssl_verify on;
    proxy_ssl_trusted_certificate /etc/ssl/certs/ca-bundle.crt;
}
업스트림이 HTTPS 면 매 연결마다 TLS 핸드셰이크가 추가됩니다. keepalive 와 proxy_ssl_session_reuse 를 함께 쓰지 않으면 지연이 크게 늘어납니다.
같은 사설망 안이라면 평문 HTTP 로 두고 망 자체를 보호하는 구성도 흔합니다 (다만 보안 요구사항에 따라 다릅니다). 
# 재사용이 되고 있는지 확인 — 백엔드의 연결 수를 보면 알 수 있습니다
ss -tn state established '( dport = :8080 )' | wc -l

# keepalive 설정 전후로 이 값을 비교해 보세요
# 설정 후에는 요청 수와 무관하게 연결 수가 안정적으로 유지됩니다
설정 세 줄로 지연이 눈에 띄게 줄고 TIME_WAIT 이 사라집니다 — 성능 튜닝 중 투입 대비 효과가 가장 좋은 축입니다.
keepalive 만 넣고 두 줄을 빠뜨리면 아무 효과가 없습니다.
proxy_http_version 1.1; — HTTP/1.0 은 연결 유지를 못 합니다
proxy_set_header Connection ""; — 안 지우면 close 가 전달돼 매번 끊깁니다
이 두 줄이 없으면 keepalive 64 를 적어 두고도 실제로는 매 요청 새 연결을 맺습니다. 설정을 넣은 뒤에는 반드시 ss -tan state time-wait | wc -l 로 실제로 줄었는지 확인하세요.

keepalive 값을 정하는 법

설정지침
keepalive워커당 유휴 연결 수. 실제 총합 = worker_processes × keepalive.
16~64 사이에서 시작해 백엔드 연결 수를 보며 조정하세요
keepalive_timeout백엔드의 유휴 타임아웃보다 짧게. 길면 백엔드가 먼저 끊어 502 가 납니다
keepalive_requests한 연결로 처리할 최대 요청 수(기본 1000). 그대로 두면 됩니다
백엔드 쪽Node server.keepAliveTimeout · Tomcat keepAliveTimeout ·
Kestrel KeepAliveTimeout 을 Nginx 값보다 크게
"간헐적 502 가 나는데 재현이 안 된다"의 대표적 원인이 이 타임아웃 불일치입니다. Nginx 가 유휴 연결을 재사용하려는 순간 백엔드가 방금 그 연결을 닫았다면, 요청이 허공에 나가 502 가 됩니다. Node 의 기본 keepAliveTimeout 은 5초라 Nginx 기본값과 어긋납니다 — 백엔드를 65초 정도로 올리는 것이 정석적인 해결입니다. proxy_next_upstream error timeout; 로 한 번 재시도를 열어 두면 남은 확률까지 흡수됩니다.

캐시 계층 설계

앞쪽에서 막을수록 좋습니다. 네 개의 층이 있습니다.

1 · 브라우저
가장 빠릅니다 — 네트워크를 아예 안 씁니다 Cache-Control 헤더로 제어. 정적 자원은 여기서 끝내는 것이 최선입니다.
▼ 없으면
2 · CDN
사용자와 가까운 엣지에서 응답 전 세계 지연이 크게 줄고 오리진 부하가 사라집니다.
▼ 없으면
3 · 웹서버
proxy_cache — 앱을 거치지 않고 응답 동적 응답도 캐시할 수 있습니다(🟩 Nginx n13).
▼ 없으면
4 · 앱 · Redis
계산 결과·DB 조회 결과를 캐시 여기까지 오면 이미 비용이 발생했습니다.
▼ 없으면
5 · DB
가장 비쌉니다 DB 내부 캐시(버퍼 풀)도 있지만 여기까지 오는 요청을 줄이는 것이 핵심입니다.

무엇을 어디에 캐시할까

대상위치와 TTL
해시 붙은 JS·CSS브라우저 + CDN · 1년 (immutable)
이미지브라우저 + CDN · 30일
index.html캐시 금지 (또는 매우 짧게)
공개 API 목록 (상품 목록 등)웹서버 proxy_cache · 1~10분
사용자별 응답공유 캐시 금지 — private 또는 캐시 안 함
DB 조회 결과앱 · Redis · 수 분
실시간 데이터 (재고·잔액)캐시하지 않음
가장 위험한 사고 — 개인화된 응답의 공유 캐시
로그인한 A 의 응답이 캐시되어 B 에게 그대로 전달되는 사고입니다. 실제로 대형 서비스에서 여러 번 발생했습니다.
기본을 "캐시하지 않음"으로 두고, 캐시할 것만 명시적으로 지정하세요. Authorization 헤더나 세션 쿠키가 있으면 무조건 우회하도록 설정합니다.

캐시 무효화 전략

전략설명
URL 에 버전·해시 ★ 가장 확실합니다. 내용이 바뀌면 URL 이 바뀌므로 무효화가 필요 없습니다
짧은 TTL 무효화 대신 금방 만료되게. 단순하고 안전합니다
stale-while-revalidate 만료된 것을 주면서 뒤에서 갱신 — 체감 속도가 좋습니다
명시적 퍼지 CDN API 로 삭제. Nginx 오픈소스는 선택 삭제 기능이 없습니다
캐시 설계의 원칙 — 무효화는 어렵습니다. 그래서 "무효화가 필요 없는 구조"(URL 버저닝)를 우선하고, 그다음이 "짧은 TTL", 마지막이 "명시적 퍼지"입니다.
"이 데이터가 5분 늦어도 괜찮은가?"를 기능별로 판단하세요.

커널 파라미터 튜닝

동시 접속이 아주 많아지면 OS 설정이 먼저 한계에 닿습니다.

# /etc/sysctl.d/99-webserver.conf

# ── 연결 대기열
net.core.somaxconn = 65535               # accept 대기열 (기본 4096)
net.ipv4.tcp_max_syn_backlog = 65535     # SYN 대기열
net.core.netdev_max_backlog = 65535      # NIC 수신 대기열

# ── 포트·연결 재사용
net.ipv4.ip_local_port_range = 10240 65535
net.ipv4.tcp_tw_reuse = 1                # TIME_WAIT 소켓 재사용 (클라이언트 방향)
net.ipv4.tcp_fin_timeout = 15

# ── keepalive
net.ipv4.tcp_keepalive_time = 300
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 3

# ── 파일 디스크립터
fs.file-max = 2097152

# ── 메모리 (대량 연결 시)
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# ── SYN flood 완화
net.ipv4.tcp_syncookies = 1

# 적용
# sudo sysctl --system
# sysctl -a | grep somaxconn   로 확인
net.ipv4.tcp_tw_recycle 을 쓰지 마세요. NAT 뒤의 여러 클라이언트가 연결에 실패하는 문제를 일으키며, 리눅스 커널 4.12 에서 제거됐습니다. 옛 튜닝 글에 자주 등장하니 주의하세요. tcp_tw_reuse 는 안전합니다. 
# Nginx 쪽에서도 백로그를 맞춰야 합니다
server {
    listen 80 backlog=65535 reuseport;
    # backlog 는 somaxconn 을 넘을 수 없습니다
    # reuseport 는 커널이 워커별로 연결을 분배 (로드 불균형 완화)
}
증상확인할 파라미터
연결이 거부됨 (피크 시)somaxconn · tcp_max_syn_backlog · Nginx backlog
TIME_WAIT 이 수만 개tcp_tw_reuse · 업스트림 keepalive(근본 해결)
포트 고갈ip_local_port_range · keepalive 로 연결 재사용
too many open filesfs.file-max · ulimit · systemd LimitNOFILE (p10)
# 현재 상태 확인
ss -s                                    # 소켓 상태 요약
ss -tan state time-wait | wc -l          # TIME_WAIT 개수
netstat -s | grep -i -E 'listen|overflow'  # 대기열 넘침 여부
cat /proc/net/netstat | grep -i listen
커널 튜닝은 마지막 카드입니다. 초당 수천 연결 이상을 다루는 서버가 아니라면 기본값으로도 충분합니다. 먼저 애플리케이션·쿼리·캐시를 개선하세요 — 효과가 훨씬 큽니다.
SECTION 10

파일 디스크립터 한계

too many open files — 트래픽이 늘면 반드시 만나는 오류입니다.

리눅스에서는 소켓도 파일입니다. 연결 하나가 파일 디스크립터 하나를 씁니다. 프록시는 연결당 2개(클라이언트 + 업스트림)를 쓰므로, 동시 1만 연결이면 2만 개 이상이 필요합니다. 
# 현재 한계 확인
ulimit -n                                        # 셸의 한계
cat /proc/$(pgrep -f 'nginx: master')/limits | grep 'open files'

# 실제 사용량
ls /proc/$(pgrep -f 'nginx: worker' | head -1)/fd | wc -l
lsof -p <pid> | wc -l

# 시스템 전체
cat /proc/sys/fs/file-nr    # 사용중 / 미사용 / 최대

세 곳을 모두 올려야 합니다

# ① 커널 전체
# /etc/sysctl.d/99-limits.conf
fs.file-max = 2097152

# ② 사용자 한계
# /etc/security/limits.conf
*       soft  nofile  65535
*       hard  nofile  65535
nginx   soft  nofile  65535
nginx   hard  nofile  65535
# ③ systemd 서비스 (★ 가장 자주 놓칩니다)
# limits.conf 는 systemd 서비스에 적용되지 않습니다!
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535

# sudo systemctl daemon-reload && sudo systemctl restart nginx
# ④ Nginx 설정에도
worker_rlimit_nofile 65535;
events { worker_connections 16384; }
# worker_connections 는 worker_rlimit_nofile 보다 작아야 합니다
/etc/security/limits.conf 만 고치면 안 됩니다. 이 파일은 PAM 을 거치는 로그인 세션에만 적용됩니다. systemd 로 실행되는 서비스는 유닛 파일의 LimitNOFILE 을 따릅니다. "설정했는데 안 올라간다"는 문제의 대부분이 이것입니다.
반드시 /proc/<pid>/limits 로 실제 프로세스의 값을 확인하세요. 
# 확인 (설정 후)
cat /proc/$(pgrep -f 'nginx: master')/limits | grep -i 'open files'
# Max open files            65535                65535                files
컨테이너에서는 도커·쿠버네티스 설정에서 지정합니다.
· Docker — --ulimit nofile=65535:65535
· Compose — ulimits: nofile: {soft: 65535, hard: 65535}
· 쿠버네티스 — 노드의 kubelet·컨테이너 런타임 설정을 따릅니다
SECTION 11

CDN 앞단 구성

전 세계 어디서든 가까운 곳에서 파일을 받게 합니다. 오리진 부하도 크게 줍니다.

사용자
가장 가까운 엣지 서버로 연결DNS 나 애니캐스트로 자동 라우팅됩니다.
▼ 캐시에 있으면 즉시 응답
CDN 엣지
캐시된 응답을 반환오리진까지 가지 않습니다 — 지연이 수십 ms 로 줄어듭니다.
▼ 없으면 (캐시 미스)
오리진
우리 Nginx · 앱응답을 만들어 주고, CDN 이 그것을 캐시합니다.
# 오리진(Nginx) 쪽 설정 — CDN 이 캐시할 수 있게 헤더를 정확히 보냅니다
location ~* \.[0-9a-f]{8,}\.(js|css|woff2?|png|jpe?g|svg|webp)$ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
    add_header Vary "Accept-Encoding";
}

# 개인화된 응답은 CDN 이 캐시하지 않게
location /api/me {
    add_header Cache-Control "private, no-store";
    proxy_pass http://backend;
}

# ★ CDN 뒤에서 실제 클라이언트 IP 복원
set_real_ip_from 173.245.48.0/20;      # CDN 대역 (제공자 문서에서 확인)
set_real_ip_from 103.21.244.0/22;
real_ip_header CF-Connecting-IP;        # 또는 X-Forwarded-For
real_ip_recursive on;
CDN 을 붙이면 실제 IP 가 가려집니다. set_real_ip_from 으로 CDN 대역을 신뢰하도록 설정하지 않으면
· 로그에 CDN IP 만 남고
· rate limit 이 전 사용자를 하나로 묶어 정상 트래픽까지 차단합니다
· 지역·IP 기반 로직이 전부 오동작합니다
CDN 제공자의 공식 IP 대역 목록을 주기적으로 갱신하세요.
확인 항목내용
오리진 보호 오리진 IP 가 노출되면 CDN 을 우회한 직접 공격이 가능합니다. 방화벽에서 CDN 대역만 허용하세요
캐시 키 쿼리스트링·쿠키·헤더 중 무엇을 키에 포함할지 — 잘못 설정하면 적중률 급락 또는 개인정보 유출
Vary 헤더 Accept-Encoding 은 필요하지만, User-Agent 를 넣으면 캐시가 사실상 무력화됩니다
퍼지 절차 배포 시 무효화가 필요한 경로와 방법을 미리 정해 두세요
HTTPS 구간 CDN ↔ 오리진 구간도 HTTPS 로 (Full Strict 모드)
CDN 없이도 할 수 있는 것 — 정적 자원에 긴 캐시 헤더를 붙이는 것만으로도 재방문자의 요청이 대부분 사라집니다. CDN 은 첫 방문자와 지리적 거리 문제를 해결합니다. 국내 사용자만 대상이라면 효과가 제한적일 수 있으니 측정 후 판단하세요.

부하 테스트에서 흔한 실수
· 운영 환경에 그대로 실행 — 실제 사용자에게 장애를 일으킵니다
· 워밍업 없이 측정 — JIT·캐시·커넥션 풀이 준비되기 전 수치는 의미가 없습니다
· 테스트 도구가 병목 — 부하 생성기의 CPU·네트워크를 함께 확인하세요
· 같은 데이터만 반복 요청 — 캐시에 다 걸려 실제보다 좋게 나옵니다
· 평균만 보기 — p95·p99 를 봐야 합니다

해석하는 법

동시 사용자를 늘려 가며 관찰합니다

    RPS
     │        ┌──────  ← 한계점(saturation): 여기서 더 늘려도 처리량이 안 늘어남
     │      ╱
     │    ╱                     이 지점의 동시 사용자 수가 '용량'입니다
     │  ╱
     └────────────── 동시 사용자

    p99
     │              ╱   ← 한계를 넘으면 지연이 급격히 치솟습니다
     │         ╱
     │ ────────
     └────────────── 동시 사용자

★ 처리량이 평평해지는 지점 = 한계
★ 그 지점 이후에는 지연만 늘고 처리량은 그대로입니다

병목 찾기 절차

감으로 고치지 마세요. 순서가 있습니다.

1
어디가 느린지 구간을 나눕니다 로그의 $request_time 과 $upstream_response_time 을 비교합니다. 둘 다 크면 앱, request_time 만 크면 네트워크·전송입니다.
▼
2
서버 자원을 봅니다 CPU · 메모리 · 디스크 IO · 네트워크 중 무엇이 포화인지 확인합니다.
▼
3
앱 안에서 다시 나눕니다 앱이 느리다면 DB 쿼리 · 외부 API · 로직 중 어디인지. APM·로그로 확인합니다.
▼
4
하나씩 바꾸고 재측정 여러 개를 동시에 바꾸면 무엇이 효과였는지 알 수 없습니다.
# ── 구간 나누기 (Nginx 로그에 request_time · upstream_response_time 필요)
awk '{print $(NF-1), $NF}' /var/log/nginx/access.log | tail -100
# 예: rt=1.234 urt=1.200  → 앱이 느림
#     rt=1.234 urt=0.020  → 전송이 느림 (큰 응답 · 느린 클라이언트)

# ── 자원 확인
top -o %CPU                              # CPU
free -h                                  # 메모리
iostat -x 1 5                            # 디스크 (%util 이 100 에 가까우면 포화)
vmstat 1 5                               # 종합 (si·so 가 있으면 스왑 발생 = 심각)
ss -s                                    # 소켓

# ── 어느 URL 이 느린가
awk '{print $NF, $7}' /var/log/nginx/access.log | sort -rn | head -20

# ── 어느 URL 이 많이 호출되는가 (총 부하 = 횟수 × 시간)
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

CPU 는 여유, 응답은 느림대기가 원인 — DB · 외부 API · 락 · IO
메모리 부족 · 스왑워커·프로세스 수 과다 · 앱 메모리 누수
디스크 IO 포화로그 과다 · 프록시 임시 파일 · 캐시 쓰기
간헐적 502업스트림 keepalive 불일치 · 앱 재시작 · 커넥션 한계
피크에만 느림커넥션 풀·스레드 풀 포화 · 대기열 적체
가장 흔한 진실 — 웹서버 튜닝으로 해결되는 문제는 생각보다 적습니다. 대부분의 병목은 앱과 DB에 있습니다.
느린 쿼리 하나가 전체 지연을 지배하는 경우가 압도적으로 많으니, 🗄️ DB 가이드의 튜닝 탭을 먼저 확인하는 것이 실제로는 더 빠른 길인 경우가 많습니다.

분류확인 항목

sendfile on · tcp_nopush on

OS LimitNOFILE 이 systemd 유닛에 설정됨
somaxconn 과 Nginx backlog 가 맞음
스왑이 발생하지 않음
관측 로그에 $request_time·$upstream_response_time 포함
