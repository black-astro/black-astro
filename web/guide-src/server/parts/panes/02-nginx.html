오늘날 웹 인프라의 앞단은 대부분 Nginx 입니다. 정적 파일 · 리버스 프록시 · HTTPS · 로드밸런싱 · 캐시 · 접근 제어를 한 프로그램이 처리합니다. 이 탭은 설정 문법부터 시작해 실무에서 실제로 쓰는 구성을 순서대로 쌓아 올립니다.

SECTION 01

마스터 · 워커 구조

Nginx가 적은 메모리로 수만 연결을 감당하는 이유가 여기 있습니다. 연결마다 스레드를 만들지 않습니다.

master
지휘자 — root 로 실행 80·443 포트를 잡고, 설정을 읽고, 워커를 만들고 관리합니다. 요청을 직접 처리하지는 않습니다.
▼ fork
worker × N
일꾼 — 일반 계정(www-data)으로 실행 실제 요청을 처리합니다. 보통 CPU 코어 수만큼 만들고, 워커 하나가 수천 개 연결을 동시에 다룹니다.
ps aux | grep nginx
# root     1234  nginx: master process /usr/sbin/nginx
# www-data 1235  nginx: worker process
# www-data 1236  nginx: worker process
# www-data 1237  nginx: cache manager process

왜 이 구조가 빠른가

전통적 방식 (연결당 스레드)
연결 10,000개 = 스레드 10,000개

· 스레드마다 메모리(수백 KB~수 MB)
· 컨텍스트 스위칭 비용 폭증
· 대부분의 스레드는 그냥 '기다리는 중'
Nginx (이벤트 기반)
연결 10,000개 = 워커 4개

· 각 워커가 epoll 로 "준비된 연결"만 처리
· 기다리는 연결은 자원을 거의 안 씀
· 메모리 사용량이 연결 수에 거의 비례하지 않음
대가도 있습니다 — 워커가 블로킹 작업(느린 디스크 읽기 등)을 만나면 그 워커가 담당하던 다른 수천 개 연결이 함께 멈춥니다. 그래서 Nginx 는 무거운 작업을 절대 직접 하지 않고 뒤로 넘기는 설계를 택합니다. (디스크 IO 는 aio·thread_pool 로 분리할 수 있습니다) 
# /etc/nginx/nginx.conf
user  www-data;
worker_processes  auto;            # CPU 코어 수만큼 자동 (권장)
worker_rlimit_nofile  65535;       # 워커당 열 수 있는 파일·소켓 수

events {
    worker_connections  4096;      # 워커 하나가 다룰 최대 연결
    multi_accept  on;              # 한 번에 여러 연결을 받아들임
    use epoll;                     # 리눅스 기본값 (명시하지 않아도 됨)
}

# 이론상 최대 동시 연결 = worker_processes × worker_connections
# 단, 프록시는 클라이언트 1 + 업스트림 1 = 연결 2개를 씁니다

SECTION 03

설정 문법

문법은 단순합니다 — 지시어와 블록 둘뿐입니다.

http {                                  # ── 컨텍스트(블록)
    gzip on;                            # ── 지시어 (세미콜론 필수)
    keepalive_timeout 65;

    server {                            # 안쪽 블록은 바깥 설정을 물려받습니다
        listen 80;
        server_name example.com;
        gzip off;                       # 여기서 다시 쓰면 이 server 안에서는 off

        location /api/ {
            proxy_pass http://app:3000;
        }
    }
}
컨텍스트담는 것
main (최상위)user · worker_processes · pid · error_log
events연결 처리 방식 — worker_connections
httpHTTP 전역 — 압축·로그 포맷·타임아웃·업스트림
server사이트 하나 — 포트·도메인·인증서
locationURL 경로별 처리
upstream백엔드 서버 그룹 (http 안에)
streamTCP·UDP 프록시 (HTTP 가 아닌 것 — DB·SMTP 등)

자주 쓰는 내장 변수

변수값
$host요청의 Host 헤더 (없으면 server_name)
$remote_addr접속한 클라이언트 IP
$request_uri원본 URI 전체 (쿼리스트링 포함)
$uri정규화된 URI (rewrite 로 바뀔 수 있음)
$args쿼리스트링
$schemehttp 또는 https
$request_time요청 전체 처리 시간 — 로그에 꼭 넣으세요
$upstream_response_time뒤쪽 앱이 쓴 시간 — 병목 판별의 핵심
$status응답 상태 코드
$http_user_agent임의 요청 헤더 — $http_<헤더명> 형식
가장 흔한 문법 실수
· 세미콜론 누락 — nginx: [emerg] directive "x" is not terminated by ";"
· 중괄호 짝이 안 맞음 — unexpected end of file
· 같은 지시어를 한 블록에 두 번 — directive is duplicate
· 경로 끝 슬래시 유무 — 특히 proxy_pass·alias 에서 동작이 완전히 달라집니다
고칠 때마다 nginx -t 를 습관으로 만드세요.
SECTION 04

server 블록 · 가상 호스트

서버 한 대에서 도메인 여러 개를 서비스합니다. 비용을 크게 줄이는 구성입니다.

# 사이트 A
server {
    listen 80;
    server_name a.example.com;
    root /var/www/a;
}

# 사이트 B
server {
    listen 80;
    server_name b.example.com www.b.example.com;    # 여러 개 가능
    root /var/www/b;
}

# 어디에도 안 걸리는 요청 처리 (직접 IP 접속·봇 등)
server {
    listen 80 default_server;
    server_name _;
    return 444;               # 아무 응답 없이 연결을 끊습니다 (Nginx 전용 코드)
}

server_name 매칭 우선순위

순위형태예
1정확히 일치example.com
2* 로 시작하는 와일드카드*.example.com
3* 로 끝나는 와일드카드www.example.*
4정규식 (설정 파일에 나온 순서)~^(?<sub>.+)\.example\.com$
5아무것도 안 걸리면default_server 로 지정된 블록
default_server 를 반드시 두세요. 지정하지 않으면 설정 파일에서 첫 번째로 나온 server 블록이 기본이 됩니다. 그래서 IP로 직접 접속하거나 알 수 없는 Host 헤더로 오는 요청이 엉뚱한 사이트로 연결됩니다. 봇 스캔에서 실제로 자주 일어납니다.

공통 설정을 파일로 빼기

# /etc/nginx/snippets/proxy-common.conf
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_http_version 1.1;
proxy_read_timeout 60s;

# 사용하는 쪽
location /api/ {
    include /etc/nginx/snippets/proxy-common.conf;
    proxy_pass http://app:3000;
}
같은 설정을 여러 사이트에 복붙하지 마세요. snippets/ 로 빼 두면 한 곳만 고쳐도 전부 반영됩니다. 보안 헤더·프록시 헤더·SSL 설정이 대표적인 대상입니다.
SECTION 05

location 매칭 규칙

Nginx 설정에서 가장 많이 헷갈리는 부분입니다. 순서대로 위에서 아래로 찾는 것이 아닙니다 — 우선순위 규칙이 따로 있습니다. 

server {
    location = /images/logo.png { … }      # ① 정확히 일치 (최우선 · 즉시 확정)
    location ^~ /static/       { … }       # ② 접두사 + 정규식 건너뛰기
    location ~ \.(jpg|png)$    { … }       # ④ 정규식 (대소문자 구분)
    location ~* \.(jpg|png)$   { … }       # ④ 정규식 (대소문자 무시)
    location /api/             { … }       # ③ 일반 접두사
    location /                 { … }       # ③ 가장 짧은 접두사 = 최후의 보루
}
경로를 눌러 어떤 location 이 걸리는지 확인

요청 경로

선택된 location

설정된 location 목록

①= /images/logo.png
②^~ /static/
④~ \.(jpg|png)$
④~* \.(jpg|png)$
③/api/
③/

규칙을 말로 풀면

  1. = 로 정확히 일치하는 것이 있으면 거기서 끝입니다
  2. 없으면 가장 길게 일치하는 접두사를 기억해 둡니다
  3. 그 접두사가 ^~ 였다면 정규식을 아예 보지 않고 확정합니다
  4. 아니면 정규식들을 설정 파일에 적힌 순서대로 검사해 처음 일치하는 것을 씁니다
  5. 정규식에 하나도 안 걸리면 2에서 기억해 둔 접두사 매칭을 씁니다
실무 요령
· 정적 파일 경로에는 ^~ 를 붙이세요 — 불필요한 정규식 검사를 건너뜁니다
· = 는 아주 자주 호출되는 한 경로에 (예: = /health, = /favicon.ico)
· 정규식은 최소한으로 — 개수가 많아지면 매 요청마다 순회 비용이 듭니다
· location / 는 반드시 하나 두세요 (없으면 404)
흔한 함정 — location /api(슬래시 없음)는 /apitest 도 걸립니다. 의도한 것이 /api/ 하위라면 끝에 슬래시를 붙이거나 location ^~ /api/ 로 명확히 하세요.
SECTION 06

정적 파일 · try_files

Nginx가 가장 잘하는 일입니다. SPA 새로고침 404 문제도 여기서 해결합니다.

root 와 alias — 가장 헷갈리는 한 쌍

root — 경로를 이어 붙입니다
location /static/ {
    root /var/www;
}

# 요청: /static/app.css
# 실제: /var/www + /static/app.css
#     = /var/www/static/app.css
alias — 경로를 바꿔치기합니다
location /static/ {
    alias /var/www/assets/;      # ★ 끝 슬래시 필수
}

# 요청: /static/app.css
# 실제: /var/www/assets/app.css
#     (location 부분이 alias 로 치환)
alias 는 끝 슬래시를 반드시 맞춰야 합니다. location /static/ 에는 alias /path/; (양쪽 다 슬래시). 한쪽만 있으면 경로가 어긋나 404가 납니다. 헷갈리면 root 를 쓰고 폴더 구조를 맞추는 편이 안전합니다.

try_files — 순서대로 찾기

# 파일 → 폴더 → 404
location / {
    root /var/www/html;
    try_files $uri $uri/ =404;
}

# ★ SPA (React·Vue) — 없는 경로는 전부 index.html 로
location / {
    root /var/www/spa;
    try_files $uri $uri/ /index.html;
}

# 파일이 없으면 앱으로 넘기기 (하이브리드)
location / {
    root /var/www/html;
    try_files $uri $uri/ @app;
}
location @app {
    proxy_pass http://127.0.0.1:3000;
}
SPA 배포의 정석 — React·Vue 로 만든 앱은 /about 같은 경로에 실제 파일이 없습니다(라우팅이 브라우저에서 일어남). 그래서 새로고침하면 404 가 납니다. try_files $uri $uri/ /index.html; 한 줄이 이 문제를 해결합니다.

정적 파일 캐시 설정

# 해시가 붙은 빌드 산출물 — 아주 길게 캐시
location ~* \.(?:css|js|woff2?)$ {
    root /var/www/spa;
    expires 1y;
    add_header Cache-Control "public, immutable";
    access_log off;                       # 정적 파일 로그는 꺼서 IO 절약
}

# 이미지
location ~* \.(?:png|jpe?g|gif|svg|ico|webp|avif)$ {
    root /var/www/spa;
    expires 30d;
    add_header Cache-Control "public";
}

# index.html 은 절대 캐시하면 안 됩니다 (새 배포가 반영되지 않습니다)
location = /index.html {
    root /var/www/spa;
    add_header Cache-Control "no-store, must-revalidate";
}
배포했는데 옛 화면이 보이는 이유가 대부분 이것입니다. index.html 이 캐시되면 새로 배포한 JS 파일을 가리키는 링크 자체가 갱신되지 않습니다.
· 해시가 붙은 파일(app.a1b2c3.js) → 영구 캐시
· index.html → 캐시 금지
이 조합이 프런트엔드 배포의 표준입니다.
SECTION 07

proxy_pass

요청을 뒤쪽 앱으로 넘깁니다. 주소 끝의 슬래시 하나가 동작을 완전히 바꿉니다.

슬래시의 차이 — 반드시 알아야 합니다

슬래시 없음 — 경로가 그대로 붙음
location /api/ {
    proxy_pass http://app:3000;
}

# 요청  : /api/users
# 전달  : http://app:3000/api/users
#         (location 경로가 그대로 유지)
슬래시 있음 — location 부분이 잘림
location /api/ {
    proxy_pass http://app:3000/;
}

# 요청  : /api/users
# 전달  : http://app:3000/users
#         (/api/ 가 / 로 치환)
외우는 법 — proxy_pass 뒤에 경로(슬래시 포함)가 있으면 치환, 호스트만 있으면 그대로 전달입니다. 앱이 /api 접두사를 모른다면 슬래시를 붙이고, 앱도 /api 로 라우팅한다면 붙이지 마세요.

실무에서 쓰는 완전한 형태

location /api/ {
    proxy_pass http://127.0.0.1:3000;

    # ── 원래 요청 정보를 앱에 전달 (n08 에서 자세히)
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host  $host;

    # ── HTTP/1.1 + keepalive (기본은 1.0 이라 매번 새 연결을 맺습니다)
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    # ── 타임아웃 (기본 60초)
    proxy_connect_timeout 5s;        # 연결 수립 — 짧게
    proxy_send_timeout   60s;
    proxy_read_timeout   60s;        # 앱 응답 대기 — 504 의 기준

    # ── 버퍼링 (기본 on)
    proxy_buffering on;
    proxy_buffer_size 8k;
    proxy_buffers 8 8k;
}

경로별로 다른 앱에 보내기

server {
    listen 80;
    server_name example.com;

    # 프런트엔드 정적 파일
    location / {
        root /var/www/spa;
        try_files $uri $uri/ /index.html;
    }

    # 자바 API
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        include /etc/nginx/snippets/proxy-common.conf;
    }

    # 파이썬 관리자
    location /admin/ {
        proxy_pass http://127.0.0.1:8000;
        include /etc/nginx/snippets/proxy-common.conf;
    }

    # 업로드된 파일 (앱을 거치지 않고 직접)
    location /uploads/ {
        alias /var/data/uploads/;
        add_header Content-Disposition "attachment";     # 브라우저에서 실행되지 않게
    }
}
주의할 점 두 가지
① 업스트림 주소에 변수를 쓰면 Nginx 가 시작 시점에 DNS 를 확인하지 않고 요청마다 해석합니다. resolver 지시어가 필요하고, 없으면 오류가 납니다.
② 도커 컴포즈 환경에서 앱 컨테이너가 재시작되면 IP 가 바뀝니다. Nginx 는 시작 시점의 IP 를 캐시하므로 502 가 계속 날 수 있습니다 — resolver 127.0.0.11 valid=10s; 와 변수 사용으로 해결합니다.
SECTION 08

X-Forwarded 헤더

프록시를 거치면 앱은 Nginx의 IP만 보게 됩니다. 진짜 방문자 정보를 알려면 헤더로 넘겨야 합니다.

헤더전달하는 정보
Host원래 요청한 도메인 — 앱이 URL 을 만들 때 필요합니다
X-Real-IP클라이언트 IP (바로 앞 단계)
X-Forwarded-For거쳐 온 IP 목록 — 클라이언트, 프록시1, 프록시2
X-Forwarded-Proto원래 http 였나 https 였나 — 리다이렉트 루프의 원인
X-Forwarded-Host원래 Host (프록시가 Host 를 바꾼 경우)
X-Forwarded-Port원래 포트
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

# $proxy_add_x_forwarded_for 는
#   기존 X-Forwarded-For 값이 있으면 ", $remote_addr" 를 덧붙이고
#   없으면 $remote_addr 만 넣습니다
X-Forwarded-Proto 를 안 넘기면 리다이렉트 무한 루프가 납니다.
① 브라우저가 HTTPS 로 접속 → ② Nginx 가 HTTP 로 앱에 전달 → ③ 앱이 "HTTP 네? HTTPS 로 가세요" 라며 리다이렉트 → ④ ①로 되돌아감
Spring Boot·Django·Rails 모두 이 헤더를 보고 판단합니다.

앱 쪽 설정도 필요합니다

Spring Boot
server.forward-headers-strategy=native
# 또는 = framework
# 프록시 뒤에 있을 때 반드시 설정하세요
Django
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
USE_X_FORWARDED_HOST = True
ALLOWED_HOSTS = ['example.com']
Express (Node)
app.set('trust proxy', 1);   // 앞단 프록시 1개를 신뢰
// req.ip · req.protocol 이 올바르게 동작합니다
FastAPI · Uvicorn
uvicorn main:app \
  --proxy-headers \
  --forwarded-allow-ips='127.0.0.1'
보안 — 헤더는 위조할 수 있습니다. 클라이언트가 직접 X-Forwarded-For: 1.2.3.4 를 보내면 앱이 그것을 진짜 IP 로 믿을 수 있습니다.
· Nginx 는 클라이언트가 보낸 값 뒤에 실제 IP 를 덧붙이므로, 앱은 맨 오른쪽부터 신뢰할 수 있는 프록시를 걷어내며 읽어야 합니다
· 또는 Nginx 에서 proxy_set_header X-Forwarded-For $remote_addr; 로 덮어써서 위조를 차단할 수 있습니다(프록시가 하나일 때)
자세한 내용은 🧬 전문가 z10 참고. 
# 앞단에 CDN·LB 가 또 있을 때 : 신뢰할 대역을 지정해 실제 IP 를 복원
set_real_ip_from 10.0.0.0/8;          # 사내 LB 대역
set_real_ip_from 173.245.48.0/20;     # CDN 대역 (예시)
real_ip_header X-Forwarded-For;
real_ip_recursive on;
# 이제 $remote_addr 자체가 진짜 클라이언트 IP 가 됩니다 (로그·rate limit 에 그대로 적용)
SECTION 09

로드 밸런싱 upstream

앱 서버를 여러 대로 늘려 트래픽을 나누고, 한 대가 죽어도 서비스를 유지합니다.

upstream backend {
    # 기본은 라운드 로빈 (순서대로 돌아가며)
    server 10.0.1.11:3000 weight=3;              # 3배 더 많이 받음
    server 10.0.1.12:3000;
    server 10.0.1.13:3000 max_fails=3 fail_timeout=30s;
    server 10.0.1.14:3000 backup;                # 다른 서버가 전부 죽으면 투입

    keepalive 32;                                # ★ 업스트림 연결 재사용
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";          # ★ keepalive 를 쓰려면 필수
        include /etc/nginx/snippets/proxy-common.conf;
    }
}

분산 방식

방식동작쓰는 곳
라운드 로빈 (기본)순서대로 돌아가며무상태 앱 — 대부분의 경우
least_conn연결 수가 가장 적은 서버로요청 처리 시간이 들쭉날쭉할 때
ip_hash클라이언트 IP 로 서버를 고정세션이 서버에 저장될 때 (권장하지 않음)
hash $key지정한 값으로 해시캐시 적중률을 높일 때
random two둘을 무작위로 뽑아 덜 바쁜 쪽서버가 아주 많을 때
ip_hash 로 세션을 유지하는 것은 임시방편입니다.
· 모바일은 IP 가 자주 바뀌어 로그인이 풀립니다
· NAT 뒤의 수천 명이 한 IP로 잡혀 분산이 안 됩니다
· 서버를 늘리거나 줄이면 해시가 재배치돼 전부 로그아웃됩니다
세션은 Redis 같은 외부 저장소에 두고 앱을 무상태로 만드는 것이 정답입니다.

장애 감지

upstream backend {
    server 10.0.1.11:3000 max_fails=3 fail_timeout=30s;
    # 30초 안에 3번 실패하면 30초간 그 서버를 제외합니다 (수동적 헬스체크)
}

server {
    location / {
        proxy_pass http://backend;

        # 어떤 상황에서 다음 서버로 재시도할지
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
        proxy_next_upstream_timeout 10s;
    }
}
재시도 대상에 http_500 을 넣지 마세요. 500 은 앱 코드의 오류이므로 다른 서버에서도 똑같이 실패합니다. 재시도는 부하만 늘립니다. 또 POST 같은 변경 요청을 재시도하면 중복 처리가 될 수 있으니 non_idempotent 를 함부로 넣지 마세요.
능동적 헬스체크(주기적으로 /health 를 찔러 보는 방식)는 상용판 Nginx Plus 기능입니다. 오픈소스에서는 ① 수동적 감지(max_fails)를 쓰거나 ② nginx_upstream_check_module 을 넣어 빌드하거나 ③ 쿠버네티스·클라우드 LB 의 헬스체크에 맡깁니다.
로드밸런싱을 본격적으로 하려면 ⚖️ 로드밸런싱 탭으로. 세션 문제(로그인 풀림)·HAProxy·무중단 배포·LB 이중화까지 확장의 전 과정을 따로 정리해 뒀습니다.
SECTION 10

HTTPS · HTTP/2 · HTTP/3

인증서 파일 두 개를 지정하면 끝입니다. 발급 방법은 🔐 HTTPS 탭에서 다룹니다.

# HTTP → HTTPS 리다이렉트 전용 서버
server {
    listen 80;
    server_name example.com www.example.com;

    # 인증서 갱신 요청은 통과시켜야 합니다
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# 실제 서비스
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                                    # 1.25.1+ 문법
    server_name example.com www.example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;               # TLS1.3 에서는 클라이언트 우선이 권장
    ssl_ciphers         ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

    ssl_session_cache   shared:SSL:10m;          # 재접속 시 협상 생략 → 지연 감소
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    ssl_stapling on;                             # OCSP 스테이플링 (인증서 검증 가속)
    ssl_stapling_verify on;
    resolver 1.1.1.1 8.8.8.8 valid=300s;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    root /var/www/html;
}
listen 443 ssl http2; 는 옛 문법입니다. Nginx 1.25.1 부터 http2 on; 을 별도 지시어로 씁니다. 옛 문법도 아직 동작하지만 경고가 나오며 향후 제거될 수 있습니다.

HTTP/3 (QUIC) 1.25+

server {
    listen 443 ssl;
    listen 443 quic reuseport;          # ★ UDP 443 — 방화벽도 열어야 합니다
    http2 on;
    http3 on;

    ssl_protocols TLSv1.3;              # HTTP/3 는 TLS1.3 필수

    # 브라우저에게 "HTTP/3 로도 접속할 수 있다"고 알림
    add_header Alt-Svc 'h3=":443"; ma=86400';
}
# UDP 443 을 여는 것을 잊지 마세요
sudo ufw allow 443/udp

# 지원 여부 확인
nginx -V 2>&1 | grep -o with-http_v3_module
HTTP/2·3 은 언제 효과가 있나
· HTTP/2 — 작은 파일이 많은 페이지에서 효과가 큽니다(요청을 한 연결에 다중화). 이미 번들링된 SPA 라면 체감 차이가 작을 수 있습니다
· HTTP/3 — 불안정한 모바일 네트워크에서 특히 유리합니다(패킷 손실에 강함). 유선 환경에서는 차이가 크지 않습니다
· 둘 다 HTTPS 가 전제입니다
자세한 원리는 🧬 전문가 z05 참고.
SECTION 11

rewrite · 리다이렉트

주소를 바꿔 보내거나 내부에서 다시 처리합니다.

# ── return : 가장 단순하고 빠릅니다 (가능하면 이것을 쓰세요)
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;      # 영구 이동
}

# www 를 붙이거나 떼기
server {
    server_name www.example.com;
    return 301 https://example.com$request_uri;
}

# ── rewrite : 정규식으로 경로를 바꿉니다
location / {
    rewrite ^/old/(.*)$ /new/$1 permanent;      # 301 리다이렉트 (브라우저 주소가 바뀜)
    rewrite ^/api/v1/(.*)$ /v1/$1 last;         # 내부 재처리 (주소는 그대로)
}
플래그동작
last재작성 후 location 매칭을 다시 수행 (내부 처리)
break재작성 후 현재 location 안에서 계속 진행
redirect302 임시 리다이렉트 (브라우저에 응답)
permanent301 영구 리다이렉트
301 과 302 를 정확히 구분하세요.
· 301 (영구) — 브라우저와 검색엔진이 캐시합니다. 한 번 잘못 설정하면 사용자 브라우저에서 지우기가 매우 어렵습니다
· 302 (임시) — 캐시되지 않습니다. 로그인 후 이동 등에 씁니다
도메인 이전은 301(SEO 를 위해), 테스트 중에는 302 로 시작하세요.

조건부 처리 — if 는 조심해서

# Nginx 의 if 는 location 안에서 예상 밖으로 동작할 수 있습니다
# (공식 위키에도 "If is Evil" 문서가 있습니다)

# ✗ 피할 것
location / {
    if ($http_user_agent ~* "bot") {
        return 403;
    }
    proxy_pass http://app;      # if 안에서 다른 지시어와 섞이면 문제가 생깁니다
}

# ✓ map 을 쓰세요 (http 컨텍스트에 정의)
map $http_user_agent $is_bot {
    default        0;
    "~*bot|crawl"  1;
}
server {
    location / {
        if ($is_bot) { return 403; }        # return 만 쓰는 if 는 안전합니다
        proxy_pass http://app;
    }
}
안전하게 쓸 수 있는 if — return 과 rewrite … last 뿐입니다. 그 외 지시어(proxy_pass·add_header 등)를 if 안에 넣으면 예상과 다르게 동작하거나 조용히 무시될 수 있습니다. 조건 분기는 map 이나 별도 location 으로 푸는 것이 정석입니다.
SECTION 12

gzip · brotli 압축

텍스트 응답을 압축하면 전송량이 1/3 이하로 줄어듭니다. 가장 값싼 최적화입니다.

# http 컨텍스트에
gzip on;
gzip_vary on;                    # ★ Vary: Accept-Encoding — 캐시가 압축본과 원본을 구분
gzip_comp_level 5;               # 1~9 · 5~6 이 적정 (9는 CPU 낭비)
gzip_min_length 1024;            # 1KB 미만은 압축해도 이득이 없습니다
gzip_proxied any;                # 프록시를 거친 요청도 압축
gzip_types
    text/plain text/css text/xml text/javascript
    application/json application/javascript application/xml+rss
    application/atom+xml image/svg+xml
    application/vnd.ms-fontobject font/ttf font/otf;
# text/html 은 항상 압축되므로 목록에 넣지 않습니다
이미 압축된 것을 또 압축하지 마세요. JPG·PNG·MP4·ZIP·woff2 는 이미 압축된 형식이라 다시 압축하면 CPU 만 쓰고 크기는 오히려 늘어날 수 있습니다. gzip_types 에 이미지·동영상을 넣지 마세요.

brotli — gzip 보다 15~20% 더 작게

# 모듈이 필요합니다 (nginx.org 공식 패키지 또는 직접 빌드)
brotli on;
brotli_comp_level 5;
brotli_min_length 1024;
brotli_types text/plain text/css application/json application/javascript image/svg+xml;

# gzip 과 함께 두면 브라우저가 지원하는 쪽을 자동으로 씁니다
# 모듈 설치 (nginx.org 저장소 기준)
sudo apt install -y nginx-module-brotli

# nginx.conf 최상단에
# load_module modules/ngx_http_brotli_filter_module.so;
# load_module modules/ngx_http_brotli_static_module.so;

미리 압축해 두기 (정적 파일)

# 빌드 시점에 app.js.gz · app.js.br 을 함께 만들어 두면
# 요청마다 압축하지 않고 그 파일을 그대로 보냅니다 (CPU 0)
gzip_static on;
brotli_static on;
# 빌드 후
find dist -type f \( -name '*.js' -o -name '*.css' -o -name '*.html' \) \
  -exec gzip -9 -k {} \; -exec brotli -9 -k {} \;
# 압축이 실제로 적용되는지 확인
curl -H "Accept-Encoding: gzip" -I https://example.com/app.js | grep -i content-encoding
# content-encoding: gzip
압축 레벨은 5~6이 최적입니다. 9로 올려도 크기는 1~2% 줄어드는데 CPU 는 몇 배를 씁니다. 트래픽이 많은 서버에서는 압축이 CPU 병목이 될 수 있으니 정적 파일은 미리 압축해 두는 방식을 권합니다.
SECTION 13

proxy_cache

Nginx가 응답을 기억해 뒀다가 그대로 돌려줍니다. 백엔드 부하를 수십 분의 일로 줄일 수 있습니다. 

# http 컨텍스트에 캐시 저장소 정의
proxy_cache_path /var/cache/nginx
                 levels=1:2
                 keys_zone=app_cache:100m      # 키 저장용 공유 메모리 (100MB ≈ 80만 개)
                 max_size=10g                  # 디스크 최대 사용량
                 inactive=60m                  # 60분간 접근 없으면 삭제
                 use_temp_path=off;

server {
    location /api/products {
        proxy_cache app_cache;
        proxy_cache_key "$scheme$request_method$host$request_uri";

        proxy_cache_valid 200 302  10m;        # 정상 응답은 10분
        proxy_cache_valid 404       1m;
        proxy_cache_valid any       30s;

        # 백엔드가 죽어도 옛 캐시로 응답 (아주 중요한 장치)
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        proxy_cache_background_update on;      # 만료된 캐시를 주면서 뒤에서 갱신
        proxy_cache_lock on;                   # 동시 요청 중 하나만 백엔드로 (스탬피드 방지)

        add_header X-Cache-Status $upstream_cache_status;   # HIT · MISS · EXPIRED · STALE

        proxy_pass http://backend;
    }
}
# 캐시가 먹는지 확인
curl -I https://example.com/api/products | grep -i x-cache-status
# X-Cache-Status: MISS   ← 첫 요청
# X-Cache-Status: HIT    ← 두 번째부터

캐시하면 안 되는 것

# 로그인 사용자별 응답은 절대 캐시하면 안 됩니다
# (다른 사람의 개인정보가 노출되는 심각한 사고가 됩니다)

proxy_cache_bypass $http_authorization $cookie_sessionid;   # 이 값이 있으면 캐시를 건너뜀
proxy_no_cache     $http_authorization $cookie_sessionid;   # 저장도 하지 않음

# 또는 캐시 키에 사용자 구분을 넣습니다 (적중률은 떨어집니다)
proxy_cache_key "$scheme$request_method$host$request_uri$cookie_sessionid";
가장 위험한 사고 유형 — 로그인한 A 사용자의 응답이 캐시되어 B 사용자에게 그대로 전달되는 것입니다. 실제로 대형 서비스에서 여러 번 발생한 사고입니다.
원칙 — 개인화된 응답은 캐시 대상에서 명시적으로 제외하고, 캐시 대상은 화이트리스트로 관리하세요.

캐시 무효화

# 오픈소스 Nginx 에는 선택적 삭제(purge) 기능이 없습니다
# ① 파일을 직접 지우기 (가장 단순)
sudo find /var/cache/nginx -type f -delete
sudo systemctl reload nginx

# ② 캐시 키에 버전을 넣어 통째로 갈아치우기
# proxy_cache_key "v2:$scheme$request_method$host$request_uri";

# ③ ngx_cache_purge 모듈을 넣어 빌드 (서드파티)
# ④ 짧은 TTL + stale-while-revalidate 로 운영
캐시 설계의 기본 원칙 — 무효화가 어려우므로 TTL 을 짧게 잡는 편이 안전합니다. "10분 지난 데이터를 보여도 괜찮은가"를 기능별로 판단하세요. 상품 목록은 5분, 재고 수량은 캐시 금지 같은 식입니다.
SECTION 14

업로드 용량 · 타임아웃

파일 업로드가 실패하는 원인은 거의 정해져 있습니다.

server {
    # 업로드 최대 크기 (기본값 1m — 매우 작습니다)
    client_max_body_size 50m;

    # 요청 본문을 읽는 타임아웃
    client_body_timeout 120s;
    client_header_timeout 30s;

    # 본문 버퍼 (넘으면 임시 파일에 씁니다)
    client_body_buffer_size 128k;
    client_body_temp_path /var/cache/nginx/client_temp;

    location /upload {
        proxy_pass http://app:3000;

        # 프록시 타임아웃도 함께 늘려야 합니다
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;

        # 큰 업로드는 버퍼링을 끄고 스트리밍으로 넘기는 편이 나을 수 있습니다
        proxy_request_buffering off;
    }
}
증상확인할 곳
413 Request Entity Too Large client_max_body_size — Nginx 에서 막힌 것입니다
업로드 중 끊김 client_body_timeout · proxy_read_timeout
Nginx 는 통과했는데 실패 앱 쪽 제한 — Spring max-file-size · PHP upload_max_filesize · Django DATA_UPLOAD_MAX_MEMORY_SIZE
디스크가 가득 참 임시 파일 경로 확인 — 큰 업로드는 디스크에 먼저 씁니다
메모리 부족 proxy_request_buffering off 로 스트리밍 전달
Nginx 와 앱 양쪽 제한을 함께 올려야 합니다. Nginx 만 올리면 앱에서 다시 막히고, 앱만 올리면 Nginx 에서 413 이 납니다. 둘 다 확인하는 것이 원칙입니다.

대용량 파일은 우회하는 것이 정답

수백 MB~GB 파일을 웹서버와 앱을 거쳐 올리는 것은 메모리·디스크·타임아웃 모두에 부담입니다. 실무에서는 클라이언트가 스토리지에 직접 업로드하는 방식을 씁니다. 

① 브라우저 → 앱 : "파일 올릴 건데 업로드 주소 좀"
② 앱 → 브라우저 : 서명된 임시 업로드 URL (presigned URL)
③ 브라우저 → S3 등 스토리지 : 파일을 직접 전송  ← 서버를 거치지 않습니다
④ 브라우저 → 앱 : "다 올렸어요, 이 키로 저장됐습니다"

· 서버 부하 0 · 타임아웃 문제 없음 · 확장에 유리

로그 포맷 커스터마이징

기본 로그에는 응답 시간이 없습니다. 성능 분석을 하려면 반드시 추가해야 합니다.

# http 컨텍스트에
log_format main_ext '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent" '
                    'rt=$request_time uct=$upstream_connect_time '
                    'uht=$upstream_header_time urt=$upstream_response_time '
                    'cache=$upstream_cache_status host=$host';

access_log /var/log/nginx/access.log main_ext;
변수의미
$request_time요청 전체 시간 — 클라이언트가 체감한 시간
$upstream_connect_time백엔드 연결 수립 시간
$upstream_header_time백엔드가 첫 응답 헤더를 줄 때까지 — 앱 처리 시간
$upstream_response_time백엔드 응답 완료까지
$upstream_cache_statusHIT · MISS · BYPASS · EXPIRED
$upstream_addr실제로 어느 백엔드로 갔나 (LB 디버깅에 필수)
$request_time 과 $upstream_response_time 의 차이가 핵심입니다.
· 둘 다 크면 → 앱이 느린 것
· request_time 만 크면 → 클라이언트 네트워크가 느린 것(응답 전송이 오래 걸림)
이 구분만으로 "서버가 느리다"는 민원의 절반이 정리됩니다.

JSON 로그 — 수집 도구와 연동할 때

log_format json_log escape=json
  '{'
    '"time":"$time_iso8601",'
    '"remote_addr":"$remote_addr",'
    '"method":"$request_method",'
    '"uri":"$request_uri",'
    '"status":$status,'
    '"bytes":$body_bytes_sent,'
    '"referer":"$http_referer",'
    '"ua":"$http_user_agent",'
    '"request_time":$request_time,'
    '"upstream_time":"$upstream_response_time",'
    '"host":"$host",'
    '"request_id":"$request_id"'
  '}';

access_log /var/log/nginx/access.json json_log;
escape=json 을 반드시 넣으세요. 없으면 User-Agent 에 큰따옴표가 들어올 때 JSON 이 깨져 로그 수집기가 통째로 파싱에 실패합니다.

로그를 줄이는 방법

# 정적 파일·헬스체크는 기록하지 않기
location = /health { access_log off; return 200 "ok\n"; }
location ~* \.(css|js|png|jpg|svg|woff2)$ { access_log off; expires 1y; }

    ~^[23]  0;      # 2xx · 3xx 는 기록 안 함

}
access_log /var/log/nginx/errors.log main_ext if=$loggable;

# 버퍼링으로 디스크 IO 줄이기 (트래픽이 아주 많을 때)
access_log /var/log/nginx/access.log main_ext buffer=32k flush=5s;
SECTION 16

rate limit

같은 IP가 폭주하면 자동으로 속도를 제한합니다. 로그인·API 보호의 기본입니다.

# http 컨텍스트에 존을 정의합니다
limit_req_zone  $binary_remote_addr zone=general:10m rate=30r/s;   # 일반 API
limit_req_zone  $binary_remote_addr zone=login:10m   rate=5r/m;    # 로그인 (분당 5회)
limit_conn_zone $binary_remote_addr zone=conn:10m;                 # 동시 연결 수

limit_req_status  429;                    # 기본은 503 — 429 가 의미상 정확합니다
limit_conn_status 429;

server {
    # 전체에 완만한 제한
    limit_req  zone=general burst=60 nodelay;
    limit_conn conn 20;

    # 로그인은 강하게
    location = /api/login {
        limit_req zone=login burst=3 nodelay;
        proxy_pass http://app;
    }

    # 헬스체크는 제외
    location = /health {
        limit_req off;
        return 200 "ok\n";
    }
}
옵션의미
rate=30r/s초당 30건 — 내부적으로는 33ms 에 1건 꼴로 균등하게 봅니다
burst=60순간적으로 60건까지는 큐에 넣어 허용
nodelay버스트 분을 지연 없이 즉시 처리 (없으면 순차 지연)
delay=2020건까지는 즉시, 그 이후 버스트는 지연 (절충안)
$binary_remote_addrIP 를 이진으로 저장 — 문자열보다 메모리를 적게 씁니다
프록시 뒤에 있다면 $binary_remote_addr 가 프록시 IP 입니다. 그러면 모든 사용자가 하나로 묶여 정상 트래픽까지 차단됩니다. set_real_ip_from 으로 실제 IP 를 복원하거나(n08), $http_x_forwarded_for 를 키로 쓰되 위조 가능성을 감안하세요.

그 밖의 방어 수단

# 대역폭 제한 (다운로드 서버)
location /downloads/ {
    limit_rate_after 10m;        # 처음 10MB 는 최고 속도로
    limit_rate 500k;             # 이후 500KB/s 로 제한
}

# 특정 User-Agent 차단
map $http_user_agent $blocked_ua {
    default              0;
    "~*(scrapy|curl|wget|python-requests)"  1;
}
server {
    if ($blocked_ua) { return 403; }
}

# 지역·IP 차단
location /admin/ {
    allow 10.0.0.0/8;
    allow 203.0.113.5;
    deny  all;
}
rate limit 은 만능이 아닙니다. 분산된 대규모 공격(DDoS)은 서버에 도달하기 전에 막아야 합니다 — CDN·클라우드 방화벽(WAF)·전용 서비스의 영역입니다. Nginx 의 rate limit 은 단일 IP 의 어뷰징과 크롤러 폭주를 막는 데 효과적입니다.
SECTION 17

WebSocket · SSE

실시간 통신을 프록시하려면 일반 HTTP와 다른 설정이 필요합니다. 기본 설정으로는 연결이 끊깁니다. 

# http 컨텍스트 — Upgrade 헤더를 조건부로 만듭니다
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    location /ws/ {
        proxy_pass http://app:3000;

        # ★ WebSocket 핸드셰이크에 필수
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host       $host;

        # ★ 유휴 연결이 끊기지 않게 (기본 60초면 1분마다 끊깁니다)
        proxy_read_timeout  3600s;
        proxy_send_timeout  3600s;

        # 버퍼링을 끄지 않으면 메시지가 모였다가 한꺼번에 갑니다
        proxy_buffering off;
    }
}
WebSocket 이 자꾸 끊긴다면
① proxy_read_timeout 이 기본값(60초)이라 유휴 연결이 잘립니다
② 앱에서 주기적으로 ping·pong 을 보내 연결을 살려 두세요 (권장)
③ 앞단에 클라우드 LB 가 있으면 거기에도 타임아웃 설정이 있습니다
④ proxy_buffering off 를 빠뜨리면 메시지 전달이 지연됩니다

SSE (Server-Sent Events)

location /events {
    proxy_pass http://app:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection '';       # keepalive 유지

    proxy_buffering off;                  # ★ 필수 — 없으면 이벤트가 안 나갑니다
    proxy_cache off;
    proxy_read_timeout 3600s;

    chunked_transfer_encoding off;
    add_header X-Accel-Buffering no;      # 앱에서 이 헤더를 보내도 됩니다
}
X-Accel-Buffering: no — 앱이 이 응답 헤더를 보내면 그 응답만 Nginx 버퍼링이 꺼집니다. location 전체를 바꾸지 않고 스트리밍 엔드포인트만 예외 처리할 때 유용합니다.

gRPC 프록시

server {
    listen 443 ssl;
    http2 on;                             # gRPC 는 HTTP/2 필수

    location / {
        grpc_pass grpc://app:50051;       # 평문
        # grpc_pass grpcs://app:50051;    # TLS
        grpc_read_timeout 3600s;
    }
}

명령동작

reload 는 어떻게 무중단이 되나

1
마스터가 새 설정을 읽습니다문법 오류가 있으면 여기서 멈추고 기존 상태를 유지합니다.
▼
2
새 설정으로 새 워커를 만듭니다새로 들어오는 요청은 새 워커가 받습니다.
▼
3
옛 워커는 새 요청을 받지 않고처리 중인 요청을 끝까지 마친 뒤 스스로 종료합니다.
reload 로 반영되지 않는 것도 있습니다. user·worker_processes 같은 일부 main 컨텍스트 설정과 새로 로드하는 모듈은 restart 가 필요합니다. 바꿨는데 반영이 안 되면 이것을 의심하세요.
