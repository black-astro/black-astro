SECTION 01

웹서버란 무엇인가

브라우저 주소창에 무언가를 치면, 어딘가의 컴퓨터가 그 요청을 받아 답을 돌려줍니다. 그 "받아서 돌려주는 프로그램"이 웹서버입니다.

정적과 동적 — 이 구분이 전부의 출발점

정적 (Static)
브라우저: /about.html 주세요
웹서버 : (디스크에서 파일을 읽어) 여기 있습니다

· HTML · CSS · JS · 이미지
· 누가 요청해도 같은 내용
· 웹서버 혼자서 처리 가능
· 매우 빠름
동적 (Dynamic)
브라우저: /orders/1234 주세요
웹서버 : (앱에게 물어봄) → 앱 → DB 조회
앱     : 이 사람의 주문 정보입니다
웹서버 : 여기 있습니다

· 사람마다 · 시점마다 내용이 다름
· 웹서버 혼자서는 못 만듦 → 앱이 필요
웹서버 · WAS · 앱 — 이름 정리
· 웹서버 — 요청을 받고 정적 파일을 돌려주며, 동적 요청은 뒤로 넘깁니다 (Nginx · Apache)
· WAS (웹 애플리케이션 서버) — 코드를 실행해 결과를 만듭니다 (Tomcat · Gunicorn · Node)
· 앱 — 우리가 작성한 프로그램 (Spring · Django · Express)
실무에서는 웹서버(앞) + WAS/앱(뒤) 조합이 표준입니다.

그냥 앱만 띄우면 안 되나요

됩니다. Node·Spring Boot·Django 모두 자체 서버 기능이 있어 혼자서도 요청을 받습니다. 실제로 개발 중에는 그렇게 씁니다. 그런데 실서비스에서는 거의 항상 앞에 웹서버를 둡니다. 이유는 이렇습니다.

앞단 웹서버가 하는 일안 두면 생기는 문제
정적 파일 서빙이미지·CSS 요청까지 앱이 처리하느라 정작 로직 처리가 밀립니다
HTTPS 처리앱마다 인증서를 관리해야 하고, 언어별로 방식이 제각각입니다
여러 앱 통합한 도메인에서 /api 는 자바, /admin 은 파이썬 같은 구성이 불가능해집니다
부하 분산앱 서버를 여러 대로 늘릴 수 없습니다
느린 클라이언트 흡수모바일 3G 사용자 한 명이 앱 워커를 수 초간 붙잡습니다
보안 · 접근 제어앱이 인터넷에 직접 노출됩니다
압축 · 캐시같은 응답을 매번 새로 만듭니다
한 문장 요약 — 웹서버는 앱이 로직에만 집중하게 해 주는 문지기입니다. 앱이 잘하는 일과 웹서버가 잘하는 일을 나누는 것이 좋은 구성의 시작입니다.
SECTION 02

요청이 흐르는 길

주소를 치고 화면이 뜨기까지 무슨 일이 일어나는지 — 이 길을 알아야 어디서 막혔는지 찾을 수 있습니다.

1 · DNS
도메인을 IP 주소로 바꿉니다 example.com → 93.184.x.x. 여기서 실패하면 "사이트를 찾을 수 없음".
▼
2 · TCP
그 IP의 포트로 연결을 맺습니다 HTTP는 80, HTTPS는 443. 방화벽에 막히면 여기서 무응답(timeout)이 됩니다.
▼
3 · TLS
암호화 통로를 만듭니다 (HTTPS일 때) 인증서를 확인하고 키를 교환합니다. 인증서 문제는 이 단계에서 드러납니다.
▼
4 · HTTP
요청을 보냅니다 GET /orders/1234 HTTP/1.1 + 헤더들. 이제야 "무엇을 원하는지" 전달됩니다.
▼
5 · 웹서버
정적 파일이면 직접, 아니면 뒤로 넘깁니다 이 판단이 location 설정입니다. 여기서 잘못되면 404.
▼
6 · 앱
코드가 실행되어 결과를 만듭니다 앱이 안 떠 있으면 502, 너무 느리면 504.
▼
7 · DB
데이터를 읽고 씁니다 대부분의 지연은 사실 여기서 발생합니다 → 🗄️ 데이터베이스 가이드
이 순서가 진단의 지도입니다.
· 사이트를 못 찾음 → 1 DNS
· 계속 로딩만 됨(무응답) → 2 방화벽·포트
· 인증서 경고 → 3 TLS
· 404 → 5 웹서버 경로 설정
· 502 · 504 → 6 앱
· 느림 → 6~7 (로그의 응답 시간으로 구분)

직접 확인해 보기

# 1. DNS 가 어디를 가리키나
dig +short example.com
nslookup example.com

# 2. 포트가 열려 있나
nc -zv example.com 443
telnet example.com 443

# 3. 인증서가 정상인가
openssl s_client -connect example.com:443 -servername example.com < /dev/null

# 4. 실제 응답 (헤더 포함)
curl -I https://example.com
curl -v https://example.com

# 5. 각 단계에 걸린 시간 ← 어디가 느린지 바로 보입니다
curl -w "dns:%{time_namelookup} connect:%{time_connect} tls:%{time_appconnect} \
first_byte:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s https://example.com
dns:0.004 connect:0.031 tls:0.087 first_byte:0.142 total:0.145
이 숫자를 읽는 법 — time_starttransfer(첫 바이트까지)가 크면 서버·앱·DB 처리가 느린 것이고, total 과의 차이가 크면 응답 본문 전송이 느린 것입니다(용량·네트워크). time_appconnect 가 크면 TLS 협상이 오래 걸린 것입니다.

설치 ① Linux

명령 한 줄이면 설치됩니다. 중요한 것은 설치 후 서비스를 켜고 자동 시작을 등록하는 것입니다. 

# ── Ubuntu · Debian ─────────────────────────────
sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx        # 지금 시작 + 부팅 시 자동 시작

# Apache 는 패키지 이름이 apache2
sudo apt install -y apache2
sudo systemctl enable --now apache2

# ── RHEL · Rocky · Alma ─────────────────────────
sudo dnf install -y nginx
sudo systemctl enable --now nginx

sudo dnf install -y httpd                # Apache 는 httpd
sudo systemctl enable --now httpd

# ── 확인 ────────────────────────────────────────
systemctl status nginx                   # active (running) 이어야 합니다
nginx -v
curl -I http://localhost                 # HTTP/1.1 200 OK
배포판마다 이름이 다릅니다. Apache 는 Ubuntu 계열에서 apache2, RHEL 계열에서 httpd 입니다. 설정 파일 경로도 /etc/apache2/ 와 /etc/httpd/ 로 다릅니다. 인터넷 문서를 볼 때 어느 계열 기준인지 먼저 확인하세요.

Tomcat — 자바가 먼저 필요합니다

# 자바 설치 (톰캣 11 은 자바 17 이상 필요)
sudo apt install -y openjdk-21-jdk
java -version

# 톰캣은 압축 파일을 받아 푸는 방식이 일반적입니다
cd /opt
sudo curl -LO https://dlcdn.apache.org/tomcat/tomcat-11/v11.0.x/bin/apache-tomcat-11.0.x.tar.gz
sudo tar xzf apache-tomcat-11.0.x.tar.gz
sudo mv apache-tomcat-11.0.x tomcat

# 전용 계정으로 실행 (root 로 돌리지 마세요)
sudo useradd -r -s /bin/false tomcat

sudo -u tomcat /opt/tomcat/bin/startup.sh
curl -I http://localhost:8080

SECTION 05

설치 ② Windows · Docker

학습·개발 환경이라면 도커가 가장 편합니다. PC를 더럽히지 않고 버전을 바꿔 가며 실험할 수 있습니다.

Docker — 한 줄로 띄우기

# Nginx (기본 페이지 확인용)
docker run -d --name web -p 8080:80 nginx:1.28

# 내 HTML 폴더를 연결
docker run -d --name web -p 8080:80 \
  -v "$PWD/html:/usr/share/nginx/html:ro" \
  nginx:1.28

# 설정 파일까지 연결
docker run -d --name web -p 8080:80 \
  -v "$PWD/html:/usr/share/nginx/html:ro" \
  -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.28

# Apache · Tomcat · Caddy
docker run -d --name ap -p 8081:80 httpd:2.4
docker run -d --name tc -p 8082:8080 tomcat:11-jdk21
docker run -d --name cd -p 8083:80 caddy:2.10

# 확인 · 로그 · 정리
docker ps
docker logs -f web
docker exec -it web bash
docker rm -f web

docker compose — 앞단 + 앱 한 번에

# compose.yaml
services:
  web:
    image: nginx:1.28
    ports: ["8080:80"]
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./html:/usr/share/nginx/html:ro
    depends_on: [app]

  app:
    build: ./app                     # 우리 애플리케이션
    expose: ["3000"]                 # 외부에 열지 않고 web 만 접근

# docker compose up -d
# docker compose logs -f web
# nginx.conf — 컨테이너 안에서는 서비스 이름이 곧 호스트명입니다
server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }

    location /api/ {
        proxy_pass http://app:3000;      # ← 'app' 이 컨테이너 이름
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
도커 컴포즈에서는 컨테이너 이름이 DNS 이름이 됩니다. proxy_pass http://app:3000 처럼 서비스 이름을 그대로 쓸 수 있어 IP 를 하드코딩할 필요가 없습니다. 앱 컨테이너는 expose 만 하고 ports 로 외부에 열지 마세요 — 프록시를 우회해 직접 접근하는 경로가 생깁니다.

Windows에 직접 설치

  • WSL2 + Ubuntu — 가장 권장합니다. 리눅스 명령이 그대로 통해 운영 환경과 같은 방식으로 연습할 수 있습니다
  • Nginx for Windows — 공식 배포판이 있지만 성능·기능에 제약이 있습니다(이벤트 모델이 다름). 학습용으로만
  • XAMPP — Apache + PHP + MySQL 묶음. PHP 학습에는 편하지만 운영 환경과 구성이 달라 실무 감각을 익히기엔 부족합니다
  • IIS — Windows Server 기본 웹서버. .NET 환경이라면 자연스러운 선택입니다
도커에서 자주 겪는 문제
· 포트 충돌 — bind: address already in use → 다른 포트로 매핑하세요
· 파일이 안 보임 — 볼륨 경로 오타. 윈도우는 절대 경로 표기가 다릅니다
· 설정이 반영 안 됨 — 컨테이너 재시작 필요: docker exec web nginx -s reload
· 권한 오류 — 컨테이너 안 사용자와 호스트 파일 소유자가 다를 수 있습니다
SECTION 06

첫 페이지 띄우기

내가 만든 HTML을 실제 서버로 서비스해 봅니다. 배포의 첫 성공 경험입니다.

# 1) 파일을 둘 폴더를 만들고
sudo mkdir -p /var/www/mysite
sudo chown -R $USER:$USER /var/www/mysite

# 2) HTML 을 하나 만듭니다
cat > /var/www/mysite/index.html <<'EOF'
<!DOCTYPE html>
<html lang="ko">
<head><meta charset="utf-8"><title>첫 페이지</title></head>
<body><h1>서버가 살아 있습니다 🎉</h1></body>
</html>
EOF
# 3) /etc/nginx/sites-available/mysite  (RHEL 계열은 /etc/nginx/conf.d/mysite.conf)
server {
    listen 80;
    server_name mysite.local;          # 도메인이 없으면 _ 를 써도 됩니다

    root /var/www/mysite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
# 4) 활성화 (Ubuntu 계열)
sudo ln -s /etc/nginx/sites-available/mysite /etc/nginx/sites-enabled/

# 5) ★ 문법 검사 — 이걸 빠뜨리면 서버가 안 뜹니다
sudo nginx -t
# nginx: configuration file /etc/nginx/nginx.conf test is successful

# 6) 반영 (접속을 끊지 않고)
sudo systemctl reload nginx

# 7) 확인
curl -H "Host: mysite.local" http://localhost
도메인이 없어도 테스트할 수 있습니다. 내 PC의 hosts 파일에 한 줄을 넣으면 브라우저에서도 열립니다.
· Linux · macOS — /etc/hosts
· Windows — C:\Windows\System32\drivers\etc\hosts (관리자 권한)
127.0.0.1 mysite.local

Apache · Caddy 로 같은 일 하기

Apache
# /etc/apache2/sites-available/mysite.conf
<VirtualHost *:80>
    ServerName mysite.local
    DocumentRoot /var/www/mysite

    <Directory /var/www/mysite>
        Require all granted
    </Directory>
</VirtualHost>

# sudo a2ensite mysite
# sudo apachectl configtest
# sudo systemctl reload apache2
Caddy
# /etc/caddy/Caddyfile
mysite.local {
    root * /var/www/mysite
    file_server
}

# sudo systemctl reload caddy
# 실제 도메인이면 HTTPS 까지 자동입니다
403 Forbidden 이 뜬다면 — 파일은 있는데 웹서버가 읽을 권한이 없는 것입니다.
① 폴더에 실행(x) 권한이 있어야 들어갈 수 있습니다: chmod 755 /var/www/mysite
② 파일은 읽기 권한: chmod 644 index.html
③ 상위 폴더 전부에 접근 권한이 있어야 합니다 (홈 디렉터리 아래에 두면 자주 막힙니다)
④ SELinux 가 켜진 RHEL 계열이면: sudo restorecon -Rv /var/www/mysite
SECTION 07

설정 파일 구조 읽는 법

남이 써 놓은 설정 파일을 열었을 때 당황하지 않으려면 구조의 규칙만 알면 됩니다.

Nginx — 블록의 중첩

# /etc/nginx/nginx.conf  (전역)
user  www-data;                      # 워커가 실행될 계정
worker_processes  auto;              # CPU 코어 수만큼

events {                             # 연결 처리 설정
    worker_connections  1024;
}

http {                               # HTTP 관련 전역 설정
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;
    sendfile      on;
    keepalive_timeout  65;

    include /etc/nginx/conf.d/*.conf;        # 여기서 개별 사이트 설정을 읽어 옵니다
    include /etc/nginx/sites-enabled/*;

    server {                         # 사이트 하나
        listen 80;
        server_name example.com;

        location / {                 # 경로별 설정
            root /var/www/html;
        }
    }
}
규칙내용
지시어이름 값; — 세미콜론으로 끝납니다. 빠뜨리면 문법 오류
블록이름 { … } — 안쪽이 바깥쪽 설정을 물려받습니다
덮어쓰기안쪽에서 같은 지시어를 다시 쓰면 안쪽이 이깁니다
주석# 로 시작
변수$host · $remote_addr 처럼 $ 로 시작
include다른 파일을 그 자리에 끼워 넣습니다 — 설정을 나눠 관리할 때

파일이 어디에 있나

서버주 설정 파일사이트별 설정
Nginx (Ubuntu)/etc/nginx/nginx.confsites-available/ → sites-enabled/ 심볼릭 링크
Nginx (RHEL)/etc/nginx/nginx.conf/etc/nginx/conf.d/*.conf
Apache (Ubuntu)/etc/apache2/apache2.confsites-available/ + a2ensite
Apache (RHEL)/etc/httpd/conf/httpd.conf/etc/httpd/conf.d/*.conf
Tomcat$CATALINA_HOME/conf/server.xmlconf/Catalina/localhost/*.xml
Caddy/etc/caddy/Caddyfile같은 파일 안에 사이트 블록으로
 
# 실제로 어떤 설정이 적용되고 있는지 확인
nginx -T                    # include 를 전부 펼친 최종 설정을 출력 ← 아주 유용합니다
apachectl -S                # 가상 호스트 목록과 우선순위
apachectl -M                # 로드된 모듈 목록
caddy adapt --config /etc/caddy/Caddyfile   # Caddyfile 을 JSON 으로 변환해 확인
nginx -T 는 문제 해결의 핵심 도구입니다. include 가 여러 겹이면 어느 파일의 설정이 실제로 적용되는지 헷갈립니다. 이 명령은 최종 결과를 한 번에 보여 줍니다.
SECTION 08

포트 · 방화벽 · 권한

서버가 안 뜨거나 접속이 안 될 때, 원인의 대부분이 이 셋 중 하나입니다.

포트

# 지금 누가 쓰고 있나
sudo ss -lntp | grep -E ':80|:443|:8080'
sudo lsof -i :80

# 포트를 이미 쓰고 있으면 이런 오류가 납니다
# nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)

# 범인을 찾아 정리하거나 다른 포트를 쓰세요
sudo systemctl stop apache2       # 아파치가 80 을 잡고 있는 경우가 흔합니다
1024 미만 포트는 관리자 권한이 필요합니다. 80·443 이 여기에 해당하므로, 일반 사용자로 띄우면 Permission denied 가 납니다.
· 웹서버는 root 로 시작해 포트를 잡은 뒤 워커는 일반 계정으로 낮춥니다 (기본 동작)
· 앱은 8000·3000 같은 높은 포트를 쓰고 웹서버가 프록시하는 것이 정석입니다
· 꼭 필요하면: sudo setcap 'cap_net_bind_service=+ep' /path/to/app

방화벽

# Ubuntu (ufw)
sudo ufw status
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 'Nginx Full'          # 프로파일로 한 번에

# RHEL 계열 (firewalld)
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload

# 클라우드라면 보안 그룹·네트워크 ACL 도 확인해야 합니다
# (서버 안 방화벽만 열어도 클라우드 쪽에서 막혀 있으면 안 됩니다)
연결 거부(refused)와 무응답(timeout)의 차이
· Connection refused — 서버까지는 닿았는데 그 포트에 아무도 없음. 웹서버가 안 떴거나 포트가 다릅니다
· 무응답 · 타임아웃 — 패킷이 중간에서 버려짐. 방화벽·보안 그룹 문제입니다
이 구분만으로 진단 시간이 크게 줄어듭니다.

권한

# 웹서버가 어떤 계정으로 도는지
ps aux | grep nginx
# root      … nginx: master process     ← 포트를 잡는 프로세스
# www-data  … nginx: worker process     ← 실제로 파일을 읽는 프로세스

# 그 계정이 파일을 읽을 수 있어야 합니다
sudo -u www-data cat /var/www/mysite/index.html    # 이게 되면 권한은 정상

# 표준 권한
sudo chown -R www-data:www-data /var/www/mysite
sudo find /var/www/mysite -type d -exec chmod 755 {} \;
sudo find /var/www/mysite -type f -exec chmod 644 {} \;
SELinux (RHEL·Rocky 계열) — 권한이 다 맞는데도 403 이 난다면 이것입니다.
sudo ausearch -m avc -ts recent 로 차단 로그를 확인하고, sudo restorecon -Rv /var/www/mysite 로 컨텍스트를 복구하세요. 프록시를 쓸 때는 sudo setsebool -P httpd_can_network_connect 1 도 필요합니다. SELinux 를 끄는 것은 마지막 수단이며 권장되지 않습니다.
SECTION 09

로그 읽기

문제가 생기면 로그부터 보세요. 추측으로 설정을 고치는 것보다 훨씬 빠릅니다.

로그내용위치 (Ubuntu 기준)
access log누가 무엇을 요청했고 어떻게 응답했나/var/log/nginx/access.log
error log왜 실패했나 — 문제 해결의 1순위/var/log/nginx/error.log
Apache같은 개념/var/log/apache2/{access,error}.log
Tomcat앱 표준출력 + 접근 로그$CATALINA_HOME/logs/catalina.out
systemd서비스 기동 실패 원인journalctl -u nginx -n 50

access 로그 한 줄 해부

192.0.2.10 - - [05/Aug/2026:14:32:11 +0900] "GET /api/orders?page=2 HTTP/1.1" 200 1543 "https://example.com/" "Mozilla/5.0 …"
└─ 접속 IP ─┘                └─ 시각 ─┘        └── 요청 ──┘  └상태┘└크기┘ └─ 어디서 왔나 ─┘ └─ 브라우저 ─┘
# 실시간으로 보기
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log

# 상태 코드별 집계 ← 가장 자주 쓰는 분석
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# 500 대 오류만
awk '$9 ~ /^5/' /var/log/nginx/access.log | tail -50

# 가장 많이 요청된 경로 상위 20
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 특정 IP 의 요청만
grep '^192.0.2.10' /var/log/nginx/access.log

# 요청이 많은 IP 상위 10 (어뷰징 탐지)
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10

error 로그의 심각도

레벨의미
emerg · alert서버가 못 뜨는 수준. 기동 실패는 여기
crit · error요청 처리 실패. 502·504 의 실제 원인이 여기 적힙니다
warn동작은 하지만 주의가 필요
notice · info · debug상세 정보. 평소에는 끄고 문제 추적 시에만
# 자주 보게 되는 error 로그와 그 뜻
connect() failed (111: Connection refused) while connecting to upstream
  → 뒤쪽 앱이 안 떠 있습니다 (502 의 원인)

upstream timed out (110: Connection timed out) while reading response header
  → 앱이 너무 느립니다 (504 의 원인)

open() "/var/www/html/x.png" failed (13: Permission denied)
  → 파일 권한 문제 (403)

open() "/var/www/html/x.png" failed (2: No such file or directory)
  → 경로가 틀렸습니다 (404)

client intended to send too large body
  → 업로드 용량 제한 (413) — client_max_body_size
error 로그의 메시지를 그대로 검색하세요. Nginx·Apache 의 오류 메시지는 정형화돼 있어 메시지 한 줄이면 원인과 해결책이 바로 나옵니다. 추측으로 설정을 바꾸기 전에 이 습관부터 들이세요.
SECTION 10

리버스 프록시란

웹서버가 요청을 받아 뒤쪽 앱에 대신 물어보고 결과를 돌려주는 구조입니다. 현대 웹 구성의 기본형입니다.

정방향 프록시 (Forward Proxy)
[사내 PC] → [프록시] → 인터넷

· 클라이언트를 대신해 나감
· 회사 인터넷 통제 · VPN
· 서버는 프록시의 IP 를 봄
리버스 프록시 (Reverse Proxy)
인터넷 → [Nginx] → [앱 서버들]

· 서버를 대신해 받음
· 클라이언트는 뒤에 뭐가 있는지 모름
· 이 가이드가 다루는 것
# 가장 단순한 리버스 프록시
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;         # 뒤쪽 앱

        # 앱이 원래 요청 정보를 알 수 있게 헤더로 넘겨줍니다
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

리버스 프록시가 해 주는 일

역할설명
앱 은닉앱의 실제 포트·주소가 외부에 노출되지 않습니다
TLS 종료HTTPS 복호화를 앞단에서 처리 — 앱은 평문 HTTP 만 다루면 됩니다
부하 분산앱 서버 여러 대에 요청을 나눠 줍니다
정적 파일 분리이미지·CSS 는 웹서버가 직접 — 앱 부담이 줄어듭니다
버퍼링느린 클라이언트가 앱 워커를 붙잡지 못하게 막습니다
경로별 라우팅/api 는 자바, /admin 은 파이썬처럼 한 도메인에 여러 앱
공통 처리압축·캐시·보안 헤더·rate limit 을 한 곳에서

전형적인 구성

                     ┌─────────────────────────────────────┐
사용자 ──HTTPS──▶  │ Nginx (443)                          │
                     │  · TLS 종료                          │
                     │  · /static/  → 파일 직접 서빙        │
                     │  · /api/     → 앱으로 프록시         │
                     │  · 압축 · 캐시 · 보안 헤더 · 로그    │
                     └────────┬────────────────────────────┘
                              │ HTTP (사설망)
                     ┌────────▼────────┐  ┌────────────────┐
                     │ 앱 서버 1 (3000)│  │ 앱 서버 2 (3000)│
                     └────────┬────────┘  └───────┬────────┘
                              └──────┬────────────┘
                                ┌────▼─────┐
                                │    DB     │
                                └───────────┘
앱은 127.0.0.1 에만 바인드하세요. 앱이 0.0.0.0:3000 으로 떠 있으면 프록시를 우회해 직접 접속할 수 있어 보안 설정이 전부 무력화됩니다. 같은 서버에 있다면 127.0.0.1, 다른 서버면 사설망 IP + 방화벽으로 제한하세요.
SECTION 11

오류 사전

증상이나 오류 코드로 검색하세요. 원인과 해결책이 바로 나옵니다.

증상으로 찾기
증상원인과 해결
502 Bad Gateway 뒤쪽 앱이 응답하지 않습니다. ① 앱이 떠 있나(ss -lntp) ② 포트가 맞나 ③ proxy_pass 주소 확인 ④ error 로그의 connect() failed 확인 ⑤ SELinux 라면 httpd_can_network_connect
504 Gateway Timeout 앱이 제 시간에 응답하지 못했습니다. ① 앱 처리 시간을 먼저 확인(대개 DB 쿼리) ② 임시로 proxy_read_timeout 을 늘릴 수 있지만 근본 해결은 앱 최적화
403 Forbidden 권한 문제. ① 파일·폴더 권한(755/644) ② 상위 폴더까지 접근 가능한지 ③ 웹서버 실행 계정 확인 ④ SELinux 컨텍스트 ⑤ Apache 라면 Require all granted
404 Not Found 경로가 틀렸습니다. ① root 와 실제 파일 위치 확인 ② root 와 alias 를 혼동하지 않았는지 ③ SPA 라면 try_files $uri /index.html 필요
413 Request Entity Too Large 업로드 용량 제한. Nginx 기본값이 1MB 입니다. client_max_body_size 50m; 을 추가하고 앱 쪽 제한도 함께 올리세요
400 Bad Request 헤더·쿠키가 너무 크거나 형식이 잘못됨. large_client_header_buffers 4 16k; 로 완화
upstream sent too big header 앱이 보낸 응답 헤더가 버퍼보다 큼(세션·쿠키가 많을 때). proxy_buffer_size 16k; proxy_busy_buffers_size 24k;
Address already in use 그 포트를 다른 프로세스가 쓰고 있습니다. sudo ss -lntp | grep :80 으로 찾아 정리하거나 포트를 바꾸세요
서버가 기동되지 않음 nginx -t · apachectl configtest 로 문법을 먼저 검사하고, journalctl -xeu nginx 로 상세 원인을 확인하세요
브라우저 인증서 경고 ① 만료 확인 ② 도메인 불일치 ③ 중간 인증서 누락(PC 는 되는데 모바일만 오류) → 🔐 HTTPS 탭 s08
한글이 깨짐 charset utf-8; 추가. HTML 의 <meta charset> 도 확인
로그에 프록시 IP 만 찍힘 X-Forwarded-For 를 전달하고 앱·웹서버에서 신뢰 설정 → 🟩 Nginx n08 · 🧬 전문가 z10
WebSocket 연결이 끊김 Upgrade·Connection 헤더 전달과 proxy_read_timeout 연장 필요 → 🟩 Nginx n17
리다이렉트 무한 반복 앞단에서 HTTPS 를 끝냈는데 앱이 그것을 모르는 경우. X-Forwarded-Proto 전달 + 앱 설정 → 🐱 Tomcat t13
전체적으로 느림 로그에 응답 시간을 추가해 웹서버·앱·DB 중 어디인지 먼저 특정 → ⚡ 성능 탭 p13
too many open files 동시 연결이 한계를 넘었습니다. worker_rlimit_nofile 과 systemd LimitNOFILE → ⚡ 성능 p10
진단의 기본 순서 — ① error 로그를 봅니다 ② curl -v 로 실제 응답을 확인합니다 ③ 앱에 직접 요청해 봅니다(curl localhost:3000) — 프록시 문제인지 앱 문제인지 갈립니다 ④ 설정을 최소 상태로 되돌려 하나씩 다시 붙입니다
