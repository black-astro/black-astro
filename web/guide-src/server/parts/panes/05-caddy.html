Caddy 의 존재 이유는 하나입니다 — HTTPS 를 설정 없이 자동으로. 도메인만 적으면 인증서를 발급받고 갱신까지 알아서 합니다. Go 로 만들어 바이너리 하나로 동작하고, 설정 문법이 압도적으로 간단합니다.

SECTION 01

자동 HTTPS 의 서버

Nginx 설정 30줄이 Caddy 에서는 3줄입니다. 비교해 보면 차이가 분명합니다.

Nginx — HTTPS 정적 사이트
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    root /var/www/html;
    index index.html;
}
# + certbot 설치 · 발급 · 갱신 타이머 설정
Caddy — 같은 결과
example.com {
    root * /var/www/html
    file_server
}

# 끝입니다.
# · 인증서 자동 발급
# · 자동 갱신
# · HTTP → HTTPS 리다이렉트 자동
# · HTTP/2 · HTTP/3 자동
# · 보안 기본값 적용

기본으로 켜져 있는 것들

  • 자동 HTTPS — Let's Encrypt(또는 ZeroSSL)에서 발급·갱신
  • HTTP → HTTPS 리다이렉트 — 별도 설정 없이
  • HTTP/2 · HTTP/3 — 기본 활성화
  • 안전한 TLS 기본값 — 취약한 프로토콜·암호가 처음부터 비활성
  • OCSP 스테이플링, 세션 재개
왜 이게 중요한가 — 인증서 만료로 서비스가 멈추는 사고는 정말 자주 일어납니다. 갱신 스크립트가 조용히 실패해도 90일 뒤에야 알게 되기 때문입니다. Caddy 는 이 문제를 구조적으로 없앱니다.

그럼에도 Nginx 가 여전히 주류인 이유

  • 자료와 사례의 양 — 문제가 생겼을 때 검색 결과가 압도적으로 다릅니다
  • 조직의 익숙함 — 운영팀이 아는 도구를 쓰는 것이 안전합니다
  • 대규모 운영 사례 — 초대형 트래픽 환경의 검증 사례가 Nginx 쪽이 훨씬 많습니다
  • 플러그인 방식 — Caddy 는 기능을 추가하려면 재빌드가 필요합니다
  • 세밀한 제어 — Nginx 가 제공하는 저수준 튜닝 옵션이 더 많습니다
현실적인 선택 — 개인 프로젝트·사내 도구·소규모 서비스라면 Caddy 가 시간을 크게 아껴 줍니다. 팀이 운영하는 서비스라면 조직이 익숙한 것을 쓰는 편이 낫습니다.
인증서 만료 장애를 겪어 본 사람에게 가장 설득력 있는 기능입니다.
SECTION 02

설치와 실행

바이너리 하나면 됩니다. 의존성이 없습니다.

# ── Ubuntu · Debian (공식 저장소)
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy

# ── 바이너리 직접 (어떤 리눅스에서든)
curl -fsSL "https://caddyserver.com/api/download?os=linux&arch=amd64" -o caddy
chmod +x caddy && sudo mv caddy /usr/local/bin/

# ── macOS
brew install caddy

# ── Docker
docker run -d -p 80:80 -p 443:443 -p 443:443/udp \
  -v caddy_data:/data -v caddy_config:/config \
  -v $PWD/Caddyfile:/etc/caddy/Caddyfile:ro \
  caddy:2.10
# 즉석 실행 (개발용)
caddy file-server --root ./public --listen :8080
caddy reverse-proxy --from :8080 --to 127.0.0.1:3000

# 설정 파일로 실행
caddy run --config /etc/caddy/Caddyfile
caddy start                          # 백그라운드
caddy stop

# 서비스로 (apt 설치 시 자동 등록됨)
sudo systemctl enable --now caddy
sudo systemctl reload caddy          # 무중단 반영

# 설정 검증·정리
caddy validate --config /etc/caddy/Caddyfile
caddy fmt --overwrite /etc/caddy/Caddyfile
중요한 경로
· 설정 — /etc/caddy/Caddyfile
· 인증서·상태 — /var/lib/caddy/.local/share/caddy/ (도커에서는 /data)
· 로그 — journalctl -u caddy
인증서 폴더는 반드시 보존하세요. 지우면 전부 재발급받게 되고, Let's Encrypt 발급 한도에 걸릴 수 있습니다.
Nginx·Apache 에서 certbot 설치 → 발급 → cron 갱신 → 리로드 로 하던 일이 도메인을 적는 것 하나로 끝납니다.

{
    acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
    email admin@example.com
}

# 내부망·사설 도메인 — Caddy 내부 CA 로 자체 서명

    reverse_proxy 127.0.0.1:3000
}

# 80 번 포트를 열 수 없는 환경 → DNS 챌린지 (와일드카드도 이 방식만 가능)
# ※ DNS 제공자 플러그인이 포함된 빌드가 필요합니다
#   xcaddy build --with github.com/caddy-dns/cloudflare
*.example.com {
    tls {
        dns cloudflare {env.CF_API_TOKEN}
    }
    reverse_proxy 127.0.0.1:3000
}
운영 도메인으로 시행착오를 하지 마세요. Let's Encrypt 는 같은 도메인 조합에 주 5회 제한이 있고, 한 번 걸리면 일주일간 인증서를 못 받습니다. 설정을 시험할 때는 반드시 스테이징 CA 로 먼저 확인하고, 통과한 뒤에 그 줄을 지우세요.
SECTION 03

Caddyfile 문법

세미콜론도 중괄호도 거의 없습니다. 들여쓰기로 구조를 만듭니다.

# 전역 옵션 (파일 맨 위에 한 번)
{
    email admin@example.com          # 인증서 만료 알림을 받을 주소
    admin off                        # 관리 API 끄기 (운영 권장)
    servers {
        protocols h1 h2 h3
    }
}

# 사이트 블록
example.com {
    root * /var/www/html
    file_server
    encode gzip zstd

    handle /api/* {
        reverse_proxy 127.0.0.1:3000
    }

    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        X-Content-Type-Options nosniff
        -Server                      # 헤더 제거는 앞에 -
    }

    log {
        output file /var/log/caddy/example.log
        format json
    }
}

# 여러 도메인
a.example.com, b.example.com {
    respond "Hello"
}

# HTTP 만 (인증서 발급 안 함)
http://internal.local {
    reverse_proxy 127.0.0.1:8080
}
지시어하는 일
root * /path문서 루트 (* 는 모든 경로에)
file_server정적 파일 서빙
reverse_proxy프록시
encode gzip zstd압축
header응답 헤더 조작
handle /path/*경로별 처리 (배타적 — 하나만 실행)
handle_path /api/*경로별 처리 + 접두사 제거
route { }지시어 실행 순서를 직접 지정
redir리다이렉트
respond즉시 응답 (헬스체크 등)
rewrite내부 경로 재작성
try_files순서대로 찾기 (SPA)
basicauth기본 인증
Caddy 는 지시어 순서를 자동으로 정합니다. Nginx 처럼 "위에서부터"가 아니라 미리 정해진 우선순위에 따라 실행됩니다. 그래서 파일에 적은 순서와 실제 실행 순서가 다를 수 있습니다. 순서를 직접 통제하려면 route { } 로 감싸세요. 
# SPA 배포 — 이 세 줄이면 됩니다
example.com {
    root * /var/www/spa
    try_files {path} /index.html
    file_server
}
SECTION 04

리버스 프록시 · 로드 밸런싱

한 줄이면 프록시가 되고, 서버를 더 적으면 자동으로 분산됩니다.

example.com {
    # 가장 단순한 형태 — X-Forwarded-* 헤더가 자동으로 붙습니다
    reverse_proxy 127.0.0.1:3000
}

# 여러 서버 = 자동 로드 밸런싱
example.com {
    reverse_proxy 10.0.1.11:3000 10.0.1.12:3000 10.0.1.13:3000 {
        lb_policy least_conn          # round_robin(기본) · ip_hash · random · first

        health_uri      /health       # ★ 능동적 헬스체크가 기본 기능입니다
        health_interval 10s
        health_timeout  3s
        health_status   2xx

        fail_duration   30s           # 실패한 서버를 제외할 시간
        max_fails       3

        transport http {
            keepalive 30s
            keepalive_idle_conns 32
            dial_timeout 5s
            read_timeout 60s
        }
    }
}
능동적 헬스체크가 오픈소스에 기본 포함되어 있습니다. Nginx 에서는 상용판(Plus) 기능이라, 이 점이 Caddy 의 실질적 장점입니다.

경로별 라우팅

example.com {
    # 정적 프런트엔드
    handle /static/* {
        root * /var/www
        file_server
        header Cache-Control "public, max-age=31536000, immutable"
    }

    # API — 접두사를 떼고 넘김 (/api/users → /users)
    handle_path /api/* {
        reverse_proxy 127.0.0.1:8080
    }

    # 웹소켓 (별도 설정이 필요 없습니다 — 자동 처리)
    handle /ws/* {
        reverse_proxy 127.0.0.1:3000
    }

    # 나머지는 SPA
    handle {
        root * /var/www/spa
        try_files {path} /index.html
        file_server
    }
}
WebSocket 은 별도 설정이 필요 없습니다. Caddy 의 reverse_proxy 는 Upgrade 헤더를 자동으로 처리합니다. Nginx 에서 map $http_upgrade 를 쓰던 것과 대조적입니다. 
# 프록시 세부 조정
reverse_proxy 127.0.0.1:3000 {
    header_up   X-Real-IP {remote_host}
    header_up   Host {upstream_hostport}
    header_down -Server                    # 백엔드가 보낸 Server 헤더 제거

    flush_interval -1                      # SSE·스트리밍 (버퍼링 끄기)
}

가장 큰 차이는 "기본값"입니다. Caddy 는 안전하고 현대적인 설정이 기본이고 필요한 것만 덧붙입니다. Nginx 는 비어 있는 상태에서 하나씩 채우는 방식이라, X-Forwarded-Proto 를 빠뜨려 백엔드가 리다이렉트 루프에 빠지는 식의 "안 적어서 생기는 사고"가 잦습니다. 반대로 세밀한 제어가 필요하면 Nginx 가 여전히 유리합니다.

실전에서 자주 쓰는 프록시 설정

example.com {
    # ── 1) 큰 파일 업로드 (기본 제한 없음 — 오히려 제한을 걸어야 합니다)
    request_body {
        max_size 50MB
    }

    # ── 2) 속도 제한이 필요하면 (플러그인)
    #   xcaddy build --with github.com/mholt/caddy-ratelimit

    # ── 3) 특정 경로만 인증 걸기
    @admin path /admin/*
    basic_auth @admin {
        # caddy hash-password 로 만든 bcrypt 해시
        alice $2a$14$Zkx19XLiW6VYouLHR5NmfOFU0z2GTNmpkT/5qqR7hx4IjWJPDhjvG
    }

    # ── 4) 백엔드가 죽었을 때 보여 줄 페이지
    handle_errors {
        @502 expression {err.status_code} == 502
        rewrite @502 /maintenance.html
        root * /var/www/static
        file_server
    }

    # ── 5) 요청이 실제로 어디로 갔는지 디버깅
    #   Caddyfile 맨 위 전역 블록에
    #   { debug }
    #   → 매처 판정과 라우팅 결정이 로그에 전부 찍힙니다

    reverse_proxy 127.0.0.1:3000 {
        # 백엔드가 느릴 때 — 기본은 무제한이라 반드시 잡아 주세요
        transport http {
            dial_timeout     5s
            response_header_timeout 30s
            read_timeout     300s      # SSE·스트리밍이면 길게
        }

        # 실패 시 다음 서버로 재시도
        lb_try_duration 5s
        lb_try_interval 250ms
    }
}
타임아웃이 기본적으로 무제한에 가깝습니다. 백엔드가 응답을 안 주면 연결이 계속 쌓입니다. dial_timeout 과 response_header_timeout 은 반드시 명시하세요 — 이것만으로 백엔드 장애가 프록시까지 무너뜨리는 것을 막을 수 있습니다.
Caddy 설정이 짧은 이유는 기본값이 실무 기본값이기 때문입니다.
SECTION 05

자동 인증서 발급 원리

어떻게 자동으로 되는지 알아야 실패했을 때 진단할 수 있습니다.

1
도메인이 이 서버를 가리키는지 확인 DNS A·AAAA 레코드가 이 서버 IP 여야 합니다.
▼
2
ACME 서버에 인증서를 요청 Let's Encrypt(기본) 또는 ZeroSSL 에 "이 도메인 인증서를 주세요"라고 요청합니다.
▼
3
도메인 소유를 증명 (챌린지) HTTP-01 — 80 포트로 특정 경로에 파일을 두고 확인받거나, TLS-ALPN-01 — 443 포트로 특별한 TLS 핸드셰이크를 수행합니다.
▼
4
인증서를 받아 저장하고 자동 적용 /var/lib/caddy/.local/share/caddy/ 에 저장되고, 만료 30일 전에 자동 갱신합니다.
자동 발급이 실패하는 이유 — 거의 이 넷입니다
① DNS 가 이 서버를 안 가리킴 — dig +short example.com 으로 확인
② 80·443 포트가 막힘 — 방화벽·보안 그룹·다른 프로세스 점유
③ 발급 한도 초과 — Let's Encrypt 는 도메인당 주간 발급 제한이 있습니다 (테스트 중 반복 재시작하면 걸립니다)
④ 인증서 폴더가 초기화됨 — 도커에서 볼륨을 안 붙인 경우 
# 로그에서 발급 과정을 확인
sudo journalctl -u caddy -f | grep -i -E 'certificate|acme|challenge'

# 테스트 중이라면 스테이징 서버를 쓰세요 (발급 한도가 훨씬 넉넉합니다)
# Caddyfile 전역 옵션에
# {
#     acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
# }
# ※ 스테이징 인증서는 브라우저에서 신뢰되지 않습니다 (경고가 뜹니다)

DNS 챌린지 — 와일드카드·내부 서버용

# *.example.com 같은 와일드카드는 DNS 챌린지만 가능합니다
# DNS 제공자 플러그인이 포함된 빌드가 필요합니다
# xcaddy build --with github.com/caddy-dns/cloudflare

*.example.com {
    tls {
        dns cloudflare {env.CLOUDFLARE_API_TOKEN}
    }
    reverse_proxy 127.0.0.1:3000
}
DNS 챌린지의 장점 — 80·443 포트를 열지 않아도 인증서를 받을 수 있습니다. 인터넷에 노출되지 않은 내부 서버에도 공인 인증서를 붙일 수 있어 유용합니다. 
# 직접 준비한 인증서를 쓰려면
example.com {
    tls /etc/ssl/certs/example.crt /etc/ssl/private/example.key
}

# 내부 CA (개발·사내용 자체 서명)
internal.local {
    tls internal
}

# 인증서 관리를 아예 끄기
example.com {
    tls off
}
인증서가 공짜가 된 이유는 가격 정책이 아니라 이 절차의 자동화입니다.

정적 사이트 · 파일 서버

개발 중 임시 서버로도, 실제 배포용으로도 씁니다.

# 지금 폴더를 즉시 서빙 (개발용)
caddy file-server --listen :8080 --browse

# --browse 를 주면 디렉터리 목록도 보여 줍니다 (운영에서는 쓰지 마세요)
example.com {
    root * /var/www/site
    file_server
    encode gzip zstd

    # 정적 자원 캐시
    @static {
        path *.css *.js *.woff2 *.png *.jpg *.svg *.webp
    }
    header @static Cache-Control "public, max-age=31536000, immutable"

    # index.html 은 캐시 금지
    @html path /index.html /
    header @html Cache-Control "no-store, must-revalidate"

    # 커스텀 오류 페이지
    handle_errors {
        rewrite * /{err.status_code}.html
        file_server
    }
}
@이름 은 매처(matcher)입니다. 조건에 이름을 붙여 두고 여러 지시어에서 재사용할 수 있습니다. Nginx 의 location 보다 유연합니다 — 경로·헤더·메서드·쿼리·표현식을 조합할 수 있습니다. 
# 매처 예시
@admin {
    path /admin/*
    not remote_ip 10.0.0.0/8
}
respond @admin "Forbidden" 403

@post method POST
@api header Content-Type application/json
@mobile header User-Agent *Mobile*

# 여러 조건은 AND · 하나라도 만족하려면 별도 매처를 여러 개

사전 압축 파일 사용

example.com {
    root * /var/www/site
    file_server {
        precompressed br gzip        # app.js.br · app.js.gz 가 있으면 그것을 전송
    }
}
사전 압축은 빌드 때 한 번만 하면 됩니다. 요청마다 압축하는 것과 결과는 같지만 CPU 를 쓰지 않고, brotli 최고 압축률(-11)을 쓸 수 있습니다 — 실시간 압축으로는 너무 느려서 못 쓰는 수준입니다. find dist -type f \( -name '*.js' -o -name '*.css' \) -exec brotli -k -q 11 {} \; 한 줄을 배포 스크립트에 넣으세요.

SPA 를 제대로 서빙하기 — 캐시 전략이 핵심입니다

example.com {
    root * /var/www/spa
    encode zstd gzip

    # ① 해시가 붙은 자원 — 영원히 캐시 (파일명이 바뀌면 새로 받습니다)
    @hashed path_regexp \.[a-f0-9]{8,}\.(js|css|woff2|png|jpg|svg|webp)$
    header @hashed Cache-Control "public, max-age=31536000, immutable"

    # ② index.html — 절대 캐시 금지
    #    이것을 캐시하면 배포해도 사용자가 옛 버전을 계속 봅니다
    @index path / /index.html
    header @index Cache-Control "no-cache, must-revalidate"

    # ③ 그 외 정적 파일 — 짧게
    @asset path /assets/*
    header @asset Cache-Control "public, max-age=3600"

    # ④ API 는 프록시로
    handle_path /api/* {
        reverse_proxy 127.0.0.1:8080
    }

    # ⑤ 나머지 경로는 전부 index.html (클라이언트 라우팅)
    handle {
        try_files {path} /index.html
        file_server
    }
}
파일Cache-Control이유
app.a1b2c3d4.jsmax-age=31536000, immutable내용이 바뀌면 이름이 바뀝니다 — 무한 캐시가 안전
index.htmlno-cache새 파일명을 알려 주는 유일한 문서
이미지(해시 없음)max-age=3600바뀔 수 있으나 자주는 아님
API 응답no-store 또는 짧게사용자별 데이터
manifest.json·sw.jsno-cache캐시되면 업데이트가 영원히 안 옵니다
"배포했는데 사용자에게 반영이 안 돼요"의 원인은 거의 항상 이것입니다. index.html 이 캐시되면 브라우저가 옛 파일명을 계속 요청합니다. 반대로 해시 붙은 자원에 캐시를 안 걸면 매번 다시 받아 느려집니다. 둘을 정확히 반대로 설정하는 것이 정답입니다 — no-cache 는 "캐시하지 마라"가 아니라 "쓰기 전에 서버에 물어봐라" 라는 뜻이라는 점도 기억해 두세요.

보안 헤더와 성능 설정을 간결하게 적용합니다.

example.com {
    header {
        # 보안 헤더
        Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
        X-Content-Type-Options    "nosniff"
        X-Frame-Options           "SAMEORIGIN"
        Referrer-Policy           "strict-origin-when-cross-origin"
        Permissions-Policy        "geolocation=(), microphone=(), camera=()"
        Content-Security-Policy   "default-src 'self'; img-src 'self' data:; frame-ancestors 'self'"

        # 서버 정보 제거
        -Server
        -X-Powered-By
    }

    encode {
        zstd
        gzip 5
        minimum_length 1024
        match {
            header Content-Type text/*
            header Content-Type application/json*
            header Content-Type application/javascript*
            header Content-Type image/svg+xml*
        }
    }
}
재사용할 설정은 스니펫으로 빼세요. 여러 사이트에 같은 보안 헤더를 적용할 때 편리합니다.

}

보안 헤더 — 무엇이 무엇을 막나

헤더막는 공격깨질 수 있는 것
Strict-Transport-Security중간자가 HTTP 로 끌어내리기되돌리기 어렵습니다 — 아래 warn
X-Content-Type-Options: nosniff업로드 파일을 스크립트로 실행Content-Type 이 틀린 파일
X-Frame-Options / frame-ancestors클릭재킹(투명 iframe)정상적인 iframe 임베드
Content-Security-PolicyXSS — 가장 강력합니다인라인 스크립트 · 외부 CDN
Referrer-PolicyURL 에 담긴 정보 유출유입 경로 분석
Permissions-Policyiframe 이 카메라·위치 사용지도·화상 기능
HSTS 는 되돌리기가 어렵습니다. 브라우저가 max-age 동안 그 도메인을 HTTPS 로만 접속하도록 기억합니다. 인증서가 잘못되면 사용자가 "안전하지 않음"을 무시하고 들어갈 방법조차 없어집니다. 처음에는 max-age=300 으로 시작해 문제가 없는 것을 확인한 뒤 늘리세요. preload 는 브라우저에 하드코딩되므로 제거에 몇 개월이 걸립니다 — 확신이 있을 때만 붙이세요. 서브도메인 전부가 HTTPS 여야 한다는 점도 확인이 필요합니다. 
# CSP 를 실제로 적용하는 순서 — 한 번에 켜면 사이트가 깨집니다
# ① 먼저 리포트 전용으로 (차단하지 않고 위반만 수집)
header Content-Security-Policy-Report-Only "default-src 'self'; report-uri /csp-report"

# ② 며칠간 리포트를 보고 필요한 출처를 추가
# ③ 위반이 사라지면 Report-Only 를 떼고 실제 적용
header Content-Security-Policy "
    default-src 'self';
    script-src  'self' https://cdn.example.com;
    style-src   'self' 'unsafe-inline';
    img-src     'self' data: https:;
    connect-src 'self' https://api.example.com wss://api.example.com;
    frame-ancestors 'none';
    base-uri 'self';
    form-action 'self'
"

압축 — 무엇을 압축하고 무엇을 하지 말아야 하나

종류압축이유
HTML · CSS · JS · JSON · SVG반드시70~85% 줄어듭니다
JPEG · PNG · WebP · MP4하지 말 것이미 압축됨 — CPU 만 쓰고 커지기도 합니다
woff2 폰트하지 말 것내부적으로 이미 압축
1KB 미만 응답하지 말 것헤더 오버헤드가 더 큽니다
스트리밍 · SSE주의버퍼링되어 실시간성이 깨집니다
zstd 를 gzip 보다 먼저 쓰세요. Caddy 는 클라이언트가 지원하는 것 중 먼저 적힌 것을 고릅니다. zstd 는 같은 압축률에서 gzip 보다 훨씬 빠르고, 지원 브라우저도 충분히 퍼졌습니다. encode zstd gzip 처럼 순서를 지켜 적으면 지원하는 브라우저는 zstd, 나머지는 gzip 으로 자동 분기합니다.

  • 문제 해결 자료가 중요할 때
🟣 함께 쓰기
  • 앞단 Caddy(TLS 자동) + 뒤 Nginx
  • 내부망 서비스만 Caddy
  • 개발 환경만 Caddy, 운영은 Nginx
  • 다만 두 개를 관리하는 비용도 고려하세요
솔직한 조언 — 이력서·실무 관점에서는 Nginx 를 먼저 익히는 것이 확실히 유리합니다. 채용 공고와 운영 사례가 압도적으로 많습니다. Caddy 는 "내 프로젝트를 빨리 띄우는 도구"로 알아 두면 충분합니다.
도구를 고를 때 마지막 질문은 늘 같습니다 — 누가 유지할 것인가.
SECTION 10

API · 플러그인 · 운영

Caddy 의 실제 설정 형식은 JSON 이고, Caddyfile 은 그것을 쉽게 쓰는 문법입니다.

# Caddyfile 이 실제로 어떤 JSON 이 되는지 확인
caddy adapt --config /etc/caddy/Caddyfile --pretty

# 관리 API (기본 localhost:2019)
curl localhost:2019/config/ | jq            # 현재 설정 조회
curl localhost:2019/config/apps/http/servers/srv0/routes | jq

# 설정을 API 로 교체 (무중단)
curl -X POST localhost:2019/load \
     -H "Content-Type: application/json" \
     -d @caddy.json
운영에서는 관리 API 를 끄거나 제한하세요. 기본적으로 localhost:2019 에만 열리지만, 컨테이너 안에서는 다른 컨테이너가 접근할 수 있습니다. 설정을 통째로 바꿀 수 있으므로 매우 위험합니다.
Caddyfile 전역 옵션에 admin off 를 넣으세요.

플러그인 — xcaddy 로 재빌드

# xcaddy 설치 (Go 필요)
go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest

# 필요한 플러그인을 넣어 빌드
xcaddy build \
  --with github.com/caddy-dns/cloudflare \
  --with github.com/greenpau/caddy-security \
  --with github.com/mholt/caddy-ratelimit

sudo mv caddy /usr/local/bin/caddy
caddy list-modules | grep -i cloudflare
플러그인하는 일
caddy-dns/*DNS 챌린지 (Cloudflare·Route53 등) — 와일드카드 인증서에 필수
caddy-ratelimit요청 속도 제한 (기본 기능에 없습니다)
caddy-security인증·인가 (OAuth·JWT)
caddy-docker-proxy도커 라벨로 설정 자동 생성
replace-response응답 본문 치환
플러그인 방식의 트레이드오프 — Nginx 는 동적 모듈을 로드하지만 Caddy 는 바이너리를 다시 빌드해야 합니다.
· 장점 — 단일 바이너리 유지, 의존성 없음, 배포가 단순
· 단점 — 플러그인 추가 시 재빌드·재배포 필요, 업데이트 시마다 다시 빌드
도커를 쓴다면 caddy:builder 이미지로 멀티스테이지 빌드를 구성하면 편합니다. 
# Dockerfile — 플러그인 포함 이미지 만들기
FROM caddy:2.10-builder AS builder
RUN xcaddy build --with github.com/caddy-dns/cloudflare

FROM caddy:2.10
COPY --from=builder /usr/bin/caddy /usr/bin/caddy
