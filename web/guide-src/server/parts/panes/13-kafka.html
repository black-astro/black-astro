SECTION 01

왜 Kafka 인가

직접 호출로 버티던 시스템이 무너지는 순간이 있습니다 — 받는 쪽이 못 따라올 때입니다.

Kafka 의 한 줄 정의 — 생산 속도와 소비 속도를 분리해 주는, 지워지지 않는 로그.

언제 필요한가 — 신호 세 가지

신호Kafka 가 해 주는 것
피크 때 하위 시스템이 밀림버퍼로 흡수 — 받는 쪽은 자기 속도로 (📈 대규모 트래픽 x06)
같은 데이터를 여러 곳이 원함한 번 발행 → 각자 구독. 발행자는 소비자를 모릅니다 (🧱 MSA m07)
이벤트 순서·재처리가 중요로그라서 과거로 되감아 다시 읽기가 됩니다 — 버그 수정 후 재처리
메시지 "큐"와 무엇이 다른가. RabbitMQ 같은 전통 큐는 꺼내면 사라집니다 — 일감 분배에 알맞습니다. Kafka 는 읽어도 남는 로그라 구독자가 몇이든, 언제 들어오든 처음부터 읽을 수 있습니다. 상세 비교는 k11 에서 다룹니다.
SECTION 02

핵심 구조 — 토픽 · 파티션 · 오프셋

Kafka 를 안다는 것은 이 그림 하나를 안다는 뜻입니다. 나머지는 전부 여기서 나옵니다.

외울 것은 세 문장 — 토픽은 파티션으로 나뉜다 · 순서는 파티션 안에서만 · 오프셋은 컨슈머가 기억한다.

용어 한 벌

용어뜻
브로커Kafka 서버 한 대. 보통 3대 이상 클러스터로 묶습니다
토픽메시지의 분류 채널 — orders · payments · click-logs
파티션토픽을 나눈 조각. 추가만 되는 로그이며 병렬성·순서의 단위
오프셋파티션 안에서 메시지의 번호. 컨슈머가 "어디까지 읽었나"를 이 번호로 저장
보존 기간읽든 안 읽든 설정한 기간(예: 7일) 보관 후 삭제 — 소비와 무관합니다
면접 단골 — "Kafka 는 왜 빠른가요?" ① 순차 쓰기 — 로그 끝에 붙이기만 해서 디스크에서도 빠릅니다 ② 제로카피 — 파일 → 소켓으로 커널이 직접 복사 (🧬 전문가 z05) ③ 배치·압축 — 메시지를 묶어서 보내고 저장합니다. "디스크라서 느리다"는 직관을 뒤집는 것이 포인트입니다.
SECTION 03

컨슈머 그룹 · 리밸런싱

"처리를 여러 대로 나누고 싶다"와 "같은 데이터를 여러 팀이 읽고 싶다"를 한 구조가 해결합니다.

확장 공식 — 처리량이 부족하면 파티션과 컨슈머를 함께 늘립니다. 컨슈머만 늘리면 노는 놈이 생깁니다.

랙(Lag) — 가장 중요한 운영 지표

랙 = 마지막 오프셋 − 컨슈머가 커밋한 오프셋, 즉 "밀린 메시지 수"입니다. 랙이 0 근처를 유지하면 실시간으로 따라가는 것이고, 계속 증가하면 소비가 생산을 못 따라가는 것입니다 — 파티션·컨슈머 증설이나 처리 로직 최적화가 필요한 신호입니다. 피크 때 잠깐 쌓였다가 줄어드는 것은 정상입니다(그러라고 쓰는 버퍼입니다).

리밸런싱 폭풍. 컨슈머가 max.poll.interval.ms(기본 5분) 안에 다음 poll 을 못 하면 죽은 것으로 간주되어 쫓겨나고 리밸런싱이 돕니다. 한 배치 처리가 5분을 넘는 무거운 로직이 흔한 원인 — 처리 후 리밸런싱 → 재배정 후 또 초과 → 무한 반복으로 소비가 0이 됩니다. 해법: 배치 크기(max.poll.records)를 줄이거나 처리를 비동기로 나눕니다.
SECTION 04

설치 · 첫 메시지

KRaft 모드(ZooKeeper 불필요) 기준으로 10분 안에 첫 메시지를 보냅니다. 

# docker-compose.yml — 개발용 단일 브로커 (KRaft 모드)
services:
  kafka:
    image: apache/kafka:3.8.0
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller          # KRaft — ZooKeeper 없음
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1       # 단일 브로커라서 1
docker compose up -d

# ① 토픽 만들기 — 파티션 3
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 1

# ② 보내기 (콘솔 프로듀서 · key:value 형식)
docker exec -it kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:
> user-7:주문 1건 15000원
> user-3:주문 1건 42000원

# ③ 받기 (콘솔 컨슈머 · 그룹 지정)
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic orders \
  --group settle --from-beginning

# ④ 랙 확인 — 운영에서 가장 자주 치는 명령
docker exec -it kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group settle
실험 두 가지를 꼭 해 보세요. ① 컨슈머를 같은 그룹으로 두 개 띄우기 → 파티션이 나뉘어 절반씩 받습니다. ② 다른 그룹 이름으로 하나 더 띄우기 → 처음부터 전부 다시 받습니다. k03 의 그림이 눈앞에서 재현됩니다.
운영 최소 구성은 브로커 3대 · 복제 3입니다(k08). 단일 브로커는 개발·학습 전용입니다. 운영에서는 MSK(AWS)·Confluent Cloud 같은 관리형을 쓰는 회사도 많습니다 — 구조 이해는 똑같이 필요합니다.
SECTION 05

프로듀서 제대로 — acks · 멱등성 · 키

기본 설정으로 보내면 유실도 중복도 생깁니다. 설정 네 개가 방어선입니다.

돈이 걸린 토픽의 공식 — acks=all · 멱등성 켜기 · 키 지정. 성능이 필요한 로그만 느슨하게 갑니다.
// Spring Kafka 프로듀서 설정 감각
spring:
  kafka:
    producer:
      acks: all                       # 유실 방지
      properties:
        enable.idempotence: true      # 재시도 중복 방지 (acks=all 필요)
        max.in.flight.requests.per.connection: 5   # 멱등성 켜면 순서도 유지
      compression-type: lz4           # 배치 압축 — 처리량↑ 비용↓

// 보내기 — 키를 반드시 지정 (같은 회원 = 같은 파티션 = 순서 보장)
kafkaTemplate.send("orders", String.valueOf(memberId), orderJson);
키 없이 보내면 라운드로빈으로 파티션에 흩어집니다 — 같은 주문의 "생성 → 취소" 이벤트가 다른 파티션에 들어가 순서가 뒤집힐 수 있습니다. "취소가 먼저 처리되고 생성이 나중에" — 실제로 나는 사고입니다. 엔티티 ID 를 키로 쓰는 것이 기본기입니다. 단, 특정 키에 트래픽이 몰리면(연예인 계정) 그 파티션만 뜨거워집니다 — 핫 파티션(k09).
SECTION 06

컨슈머 제대로 — 커밋 · 중복 · 멱등

"언제 읽었다고 기록하느냐"가 유실과 중복을 가릅니다. 공짜 정답은 없습니다.

외울 문장 — "정확히 한 번 전달"은 없다. "최소 한 번 + 멱등 처리 = 사실상 정확히 한 번"이 실무의 답입니다.
// Spring Kafka — 처리 성공 후 자동 커밋 (기본 동작이 이미 ②입니다)
@KafkaListener(topics = "orders", groupId = "settle")
public void handle(ConsumerRecord<String, String> rec) {
    settleService.process(rec);        // 여기서 예외가 나면 커밋되지 않고 재시도
}

// 멱등 처리의 전형 — 이벤트 ID 유니크 제약
INSERT INTO processed_events (event_id) VALUES (?)   -- 중복이면 여기서 실패
ON CONFLICT DO NOTHING;                              -- 이미 처리한 것 → 조용히 스킵
독약 메시지(poison pill) — 파싱조차 안 되는 메시지가 오면 "실패 → 재시도 → 실패"로 그 파티션 소비가 영원히 멈춥니다. N번 실패한 메시지는 DLQ(Dead Letter Queue) 토픽으로 치우고 넘어가도록 처음부터 설계하세요 (Spring Kafka: DefaultErrorHandler + DeadLetterPublishingRecoverer). DLQ 는 모니터링 대상입니다 — 쌓이는데 아무도 안 보면 조용한 데이터 유실입니다.
SECTION 07

DB 와 Kafka 를 함께 — 아웃박스 · CDC

"DB 커밋과 이벤트 발행, 둘 중 하나만 성공하면?" — MSA 면접의 최고 빈출 문제입니다.

기억할 구조 — 비즈니스 데이터와 이벤트를 같은 트랜잭션으로 남기고, 발행은 뒤에서 따라간다.

Kafka 트랜잭션(EOS)은 언제 쓰나

Kafka 자체 트랜잭션은 "Kafka 에서 읽어 → 가공 → Kafka 로 쓰는" 스트림 구간을 정확히 한 번으로 만들어 줍니다(Kafka Streams exactly_once_v2). 하지만 외부 세계(DB 저장·메일 발송·결제 API)까지는 묶지 못합니다. 그래서 경계의 답은 결국 — DB 와의 원자성은 아웃박스, 소비 측은 멱등 처리입니다.

면접 모범 답안 골격 — "DB 커밋과 발행 사이 유실은 아웃박스 패턴으로 막고, 그 대가로 생기는 재발행 중복은 소비 측 멱등 처리로 무해하게 만듭니다. Kafka 트랜잭션은 Kafka 안 스트림 처리에만 적용됩니다" — 이 세 문장이면 충분합니다.
SECTION 08

복제 · ISR — 브로커가 죽어도

"브로커 한 대가 내려가면 어떻게 되나요?" — 운영 면접의 단골이자, 실제 새벽의 일입니다.

가용성과 유실 방지는 트레이드오프입니다 — Kafka 의 기본값은 "유실 방지 우선"이고, 대개 그게 맞습니다.
운영 표준 설정의미
replication.factor=3파티션마다 복제본 3개 — 브로커 3대 이상
min.insync.replicas=2최소 2곳에 쓰여야 성공 — 1대 다운까지는 무중단·무유실
acks=all (프로듀서)위 둘과 한 세트 — 하나라도 빠지면 구멍이 생깁니다
컨트롤러 — 클러스터에서 "누가 리더인가"를 결정하는 브로커입니다. KRaft 모드(3.x 표준)에서는 컨트롤러들이 Raft 합의로 메타데이터를 관리합니다 — ZooKeeper 는 더 이상 없습니다. Raft 자체가 궁금하면 🎓 CS 가이드 분산 탭(d14)으로.
SECTION 09

운영 — 파티션 수 · 랙 · 보존

Kafka 운영의 세 가지 상시 질문 — 파티션 몇 개? 랙 왜 늘어? 디스크 왜 차?

파티션 수 정하기 — 실전 산식

필요 파티션 수 ≥ 목표 처리량 ÷ 컨슈머 1대의 처리량

예) 피크 10,000건/s, 컨슈머 1대가 1,000건/s 처리
    → 최소 10개. 성장 여유를 두어 12~15개로 시작

원칙
· 파티션은 늘릴 수는 있지만 줄일 수 없습니다
· 늘리면 key → 파티션 배정이 바뀝니다 (기존 키의 순서 연속성 끊김!)
  → 처음부터 여유 있게 잡는 이유
· 너무 많으면(수천 개) 리더 선출·메타데이터 부담 — 무한정 늘리는 것도 답이 아님

운영 체크 항목

항목내용
컨슈머 랙그룹별 랙 추이를 대시보드에 — "계속 증가"가 경보 조건입니다 (Burrow · kafka_exporter + Grafana)
보존 정책retention.ms(기간) · retention.bytes(용량). 디스크가 차는 것은 대부분 보존 과다
컴팩션cleanup.policy=compact — 키별 최신 값만 유지. 상태 스냅숏 토픽(재고 현황 등)에
핫 파티션특정 키 폭주로 한 파티션만 랙 증가 — 키 설계 변경(키에 버킷 붙이기)으로 해소
브로커 디스크·네트워크디스크 80% 경보 · 네트워크 포화 — 브로커 증설·파티션 재배치(reassign)
토픽·스키마는 계약입니다. 발행 측이 필드 하나 빼는 순간 소비 측이 줄줄이 깨집니다. Avro/Protobuf + 스키마 레지스트리로 하위 호환을 강제(BACKWARD)하는 것이 조직이 커졌을 때의 표준 장치입니다. JSON 을 쓰더라도 "필드는 더하기만 한다" 규칙은 지키세요.
재처리는 Kafka 의 특권입니다. 소비 로직 버그를 고친 뒤 kafka-consumer-groups.sh --reset-offsets --to-datetime … 으로 오프셋을 되감아 다시 읽으면 됩니다 — 단, 소비가 멱등해야 안전한 재처리가 됩니다(k06). 이 되감기가 필요해서라도 멱등 설계는 필수입니다.
SECTION 10

실전 파이프라인 — 스트림 · 데이터 흐름

Kafka 가 회사의 중앙 신경계가 되는 그림 — 대규모 데이터 처리의 표준 구도입니다.

이 그림이 "대규모 데이터 처리에 Kafka 를 쓴다"의 실체입니다 — 모든 데이터가 한 번은 Kafka 를 지나갑니다.

스트림 처리 — 흘러가면서 계산

// Kafka Streams — "최근 1분간 주문 금액 합계"를 흘러가면서 집계
KStream<String, Order> orders = builder.stream("orders");
orders
  .groupBy((k, v) -> v.category())
  .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
  .aggregate(() -> 0L, (k, v, sum) -> sum + v.amount())
  .toStream().to("orders-per-minute");   // 결과도 토픽으로 — 대시보드가 구독

// 배치와의 차이 — "다 모아서 밤에 계산"이 아니라 "지나갈 때 바로 계산"
// 더 큰 규모·복잡한 처리는 Flink 를 씁니다 (별도 클러스터)
이벤트 소싱과는 구분하세요. 이벤트 소싱은 "상태 대신 이벤트 전체를 진실의 원본으로 저장"하는 설계 패턴으로, 난도가 높아 정산·회계처럼 이력이 곧 가치인 도메인에서만 씁니다. Kafka 파이프라인(위 그림)은 이벤트 소싱 없이도 충분히 성립합니다 — 섞어 말하면 감점입니다.
