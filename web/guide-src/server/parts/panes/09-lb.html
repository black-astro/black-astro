서버 한 대로 버티던 서비스가 커지면 여러 대에 트래픽을 나누는 순간이 옵니다. 로드밸런서는 트래픽을 나누는 것뿐 아니라 죽은 서버를 숨기고, 배포 중에도 서비스를 살려 두는 핵심 장비입니다. 개념부터 Nginx·HAProxy 실전 구성, 이중화까지 순서대로 갑니다.

SECTION 01

왜 필요한가

서버 한 대의 한계는 반드시 옵니다. 문제는 어떻게 늘리느냐입니다.

수직 확장 (Scale-Up) — 더 좋은 한 대
CPU 4코어 → 32코어, RAM 8GB → 256GB

장점  코드·구조 변경이 전혀 없다
한계  ① 가격이 선형이 아니라 폭증한다
      ② 아무리 커도 상한이 있다
      ③ 그 한 대가 죽으면 → 전체 장애
      ④ 업그레이드하려면 → 내려야 한다
수평 확장 (Scale-Out) — 보통 여러 대
서버 1대 → 같은 앱을 3대, 5대, 10대로

장점  ① 값싼 서버를 필요한 만큼 추가
      ② 한 대가 죽어도 나머지가 받는다
      ③ 한 대씩 빼서 배포 → 무중단
전제  ★ 트래픽을 나눠 줄 무언가가 필요
      → 그것이 로드밸런서입니다

로드밸런서가 실제로 해 주는 세 가지

역할의미
① 분산 요청을 여러 서버에 나눠 한 대의 처리량 한계를 넘습니다
② 장애 숨김 죽은 서버를 자동으로 빼서 사용자는 장애를 모르게 합니다 (헬스체크 · b06)
③ 무중단 배포 한 대씩 빼서 새 버전을 올립니다 — 배포 중에도 서비스가 살아 있습니다 (b09)
이미 절반은 배웠습니다. 리버스 프록시(🧭 시작 w10)가 뒤쪽 서버를 여러 대로 늘린 것이 로드밸런서입니다. Nginx 를 쓰고 있다면 설정 몇 줄로 로드밸런서가 됩니다(b03).
수평 확장에는 숙제가 하나 따라옵니다 — 상태(state). 로그인 세션·업로드 파일이 서버 한 대의 메모리·디스크에 있으면, 다음 요청이 다른 서버로 가는 순간 사라진 것처럼 보입니다. 이 문제와 해법은 b05에서 자세히 다룹니다.
SECTION 02

큰 그림 — L4 와 L7

로드밸런서가 어디에 서고, 무엇을 보고 나누는지가 종류를 가릅니다.

사용자
  │  example.com
  ▼
[ DNS ]  ─ 도메인 → 로드밸런서의 IP
  │
  ▼
┌─────────────────────┐
│    로드밸런서        │   ★ 유일한 공개 진입점
│  (Nginx·HAProxy·ALB) │      TLS 종료 · 헬스체크 · 분산
└──────┬──────────────┘
       │  어느 서버로 보낼까? (알고리즘 · b04)
   ┌───┼───────┐
   ▼   ▼       ▼
 [앱1] [앱2]  [앱3]     ← 같은 앱 여러 대 (사설망 · 직접 노출 안 함)
   └───┴───┬───┘
           ▼
        [ DB · Redis ]  ← 상태는 공유 저장소에 (b05)

L4 vs L7 — 무엇을 보고 나누나

택배에 비유하면 — L4 는 소포의 겉면(주소·포트)만 보고 어느 창구로 보낼지 정하고, L7 은 소포를 열어 내용물(HTTP 경로·헤더·쿠키)까지 보고 정합니다.

항목L4 (전송 계층)L7 (애플리케이션 계층)
보는 것IP · 포트 (TCP/UDP)HTTP 경로 · 호스트 · 헤더 · 쿠키
할 수 있는 일연결 단위 분산/api 는 A 그룹, /static 은 B 그룹처럼 내용 기반 라우팅
TLS통과시킴 (내용을 못 봄)종료 가능 → 헤더 조작·캐시·압축 가능 (b07)
속도더 빠름 (패킷만 넘김)파싱 비용이 있지만 충분히 빠름
대표 제품NLB · LVS · HAProxy(tcp 모드)Nginx · HAProxy(http 모드) · ALB · Caddy
웹 서비스는 대부분 L7 로 시작하면 됩니다. 경로별 라우팅·헤더 추가·쿠키 기반 세션 유지가 전부 L7 기능입니다. L4 는 HTTP 가 아닌 트래픽(DB·게임 서버·MQTT)이나 극한의 성능이 필요할 때 선택합니다. 둘을 겹쳐 쓰기도 합니다 — 앞에 L4(NLB), 뒤에 L7(Nginx).

"DNS 라운드로빈으로 되지 않나요?"

# 한 도메인에 A 레코드를 여러 개 등록하는 방법
example.com  →  10.0.0.11
example.com  →  10.0.0.12
example.com  →  10.0.0.13
DNS 라운드로빈만으로는 부족합니다.
① 죽은 서버를 모릅니다 — 10.0.0.12 가 죽어도 1/3 의 사용자는 계속 그리 갑니다
② 캐시를 통제할 수 없습니다 — 통신사·브라우저가 제각각 캐시합니다
③ 분배 비율을 클라이언트가 결정합니다 — 균등을 보장하지 못합니다
그래서 DNS 라운드로빈은 로드밸런서 자체를 여러 개 두는 최상단(b10)에서 보조 수단으로 쓰고, 실제 분산은 로드밸런서가 맡는 것이 표준입니다.
SECTION 03

첫 로드밸런싱 — 10분 따라하기

서버 한 대 안에서 앱 2개 + Nginx 로 로드밸런싱을 직접 눈으로 확인합니다.

① 응답이 서로 다른 앱 두 개 띄우기

# 실습용 — 어느 서버가 응답했는지 보이는 초간단 앱 2개
mkdir -p /tmp/app1 /tmp/app2
echo 'server-1' > /tmp/app1/index.html
echo 'server-2' > /tmp/app2/index.html

python3 -m http.server 8001 --directory /tmp/app1 &
python3 -m http.server 8002 --directory /tmp/app2 &

# 각각 따로 확인
curl -s http://127.0.0.1:8001/   # server-1
curl -s http://127.0.0.1:8002/   # server-2

② upstream — 서버 그룹 정의

# /etc/nginx/sites-available/lb-test
upstream demo_pool {                # ★ 서버 그룹에 이름을 붙입니다
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    # 실전에서는 사설 IP — server 10.0.0.11:8080; 처럼 씁니다
}

server {
    listen 8080;

    location / {
        proxy_pass http://demo_pool;          # ★ 그룹 이름으로 프록시
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
sudo ln -s /etc/nginx/sites-available/lb-test /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

③ 분산 확인 — 번갈아 나오면 성공

for i in $(seq 1 6); do curl -s http://127.0.0.1:8080/; done
server-1 server-2 server-1 server-2 server-1 server-2 ← 기본 알고리즘(라운드로빈)이 정확히 번갈아 보냅니다

④ 한 대를 죽여 보기 — 장애 숨김 체험

# server-1 을 강제 종료
kill %1

for i in $(seq 1 4); do curl -s http://127.0.0.1:8080/; done
server-2 server-2 server-2 server-2 ← 죽은 서버를 빼고 모두 server-2 로. 사용자는 장애를 모릅니다
지금 일어난 일 — 첫 요청이 8001 에서 실패하자 Nginx 가 즉시 다음 서버로 재시도(기본 동작)하고, 8001 을 일정 시간 제외했습니다. 이 판정 규칙(max_fails·fail_timeout)은 b06 에서 정밀하게 다룹니다. 실험이 끝나면 kill %2 로 나머지 앱도 정리하세요.
SECTION 04

분산 알고리즘 고르기

아래 시뮬레이터에서 알고리즘을 바꿔 가며 요청을 보내 보세요. 분배가 어떻게 달라지는지 보입니다.

분산 시뮬레이터 — 서버 3대 (③번은 처리가 느린 서버)
알고리즘동작 · 언제 쓰나
라운드로빈 (기본) 순서대로 한 번씩. 서버 성능이 같고 요청 처리 시간이 비슷하면 이것으로 충분합니다
weight (가중치) 성능이 다른 서버 혼용 시 — weight=3 인 서버가 3배 받습니다
least_conn ★ 현재 연결이 가장 적은 서버로. 파일 업로드·리포트 생성처럼 요청마다 처리 시간이 들쭉날쭉하면 이것으로 바꾸세요
ip_hash 같은 IP 는 항상 같은 서버로. 세션 유지용이지만 임시방편입니다 (b05)
hash $키 임의 키(URL·헤더) 기준 고정. consistent 를 붙이면 서버 증감 시 재배치를 최소화 — 캐시 서버 분산에 씁니다 (🧬 전문가 z11)
random 무작위. random two least_conn; — 둘을 뽑아 연결 적은 쪽으로 (대규모에서 유용)
upstream backend {
    least_conn;                          # 알고리즘은 첫 줄에 (기본은 라운드로빈)

    server 10.0.0.11:8080 weight=3;      # 성능 좋은 새 서버 — 3배 받기
    server 10.0.0.12:8080 weight=2;
    server 10.0.0.13:8080;               # weight 생략 = 1
    server 10.0.0.14:8080 backup;        # ★ 평소엔 안 쓰고, 전원 장애 시에만
    server 10.0.0.15:8080 down;          # 점검 중 — 목록엔 두고 제외
}
ip_hash 의 함정 두 가지
① IPv4 는 앞 세 옥텟만 해시합니다 — 같은 회사·통신사 대역이 몽땅 한 서버로 몰릴 수 있습니다
② 회사 방화벽·모바일 통신사 뒤의 수천 명이 같은 공인 IP 로 나옵니다 — 분산이 심하게 기웁니다
세션 때문에 ip_hash 를 고려한다면 먼저 b05 를 읽어 보세요.
실무 요약 — 라운드로빈으로 시작 → 응답 시간 편차가 크면 least_conn → 서버 사양이 다르면 weight 병용. 분배가 잘 되는지는 접속 로그의 $upstream_addr(🟩 Nginx n17)로 확인합니다.
SECTION 05

세션 문제 — "로그인이 풀려요"

서버를 2대로 늘린 날부터 생기는 가장 흔한 사고입니다. 원인은 단순합니다.

1. 사용자가 로그인 → 요청이 [앱1] 로 → 세션이 앱1 메모리에 저장
2. 다음 요청이 [앱2] 로 분산됨
3. 앱2: "세션? 그런 거 없는데요" → 로그인 화면으로 튕김 ✗

문제의 본질: 상태(세션)가 서버 한 대에 갇혀 있다
임시방편 — 세션 고정 (sticky)
# 같은 사용자를 같은 서버로 계속 보낸다
upstream backend {
    ip_hash;                # IP 기준 고정
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
}

# 한계
# · 그 서버가 죽으면 → 그 사용자들 세션 전멸
# · 분산이 기운다 (b04 의 ip_hash 함정)
# · 서버를 빼는 순간 세션 소실 → 무중단 배포 방해
# · 쿠키 기반 sticky 는 Nginx Plus·HAProxy 기능
✓ 근본 해결 — 세션을 밖으로
# 세션을 모든 서버가 공유하는 저장소로
[앱1] [앱2] [앱3]
   \    |    /
    ▼   ▼   ▼
   [ Redis ]  ← 세션은 여기에

· 어느 서버로 가든 같은 세션을 본다
· 서버 추가·제거가 자유로워진다
· 앱 재시작에도 로그인이 유지된다

Spring   spring-session-data-redis
Django   SESSION_ENGINE = "...cached_db"
Express  connect-redis
PHP      session.save_handler = redis

아예 세션을 없애는 선택 — 토큰 (JWT)

방식특징
서버 세션 + Redis ★ 전통적·안전. 즉시 강제 로그아웃 가능. Redis 운영이 추가됩니다
JWT (무상태 토큰) 상태 저장이 아예 없어 수평 확장이 가장 쉽습니다. 대신 발급한 토큰을 즉시 무효화하기 어렵다는 대가가 있습니다 (만료를 짧게 + 갱신 토큰으로 보완)
세션 말고도 서버에 갇히는 상태가 있습니다.
· 업로드 파일 — 로컬 디스크에 저장하면 다른 서버에서 안 보입니다 → S3 같은 오브젝트 스토리지 또는 공유 볼륨으로
· 로컬 캐시·인메모리 큐 — 서버마다 내용이 달라집니다 → Redis 로
서버를 늘리기 전에 "이 앱이 로컬에 쌓는 것이 무엇인가"를 먼저 점검하세요.
순서 제안 — ① 세션을 Redis 로 옮기고 ② 업로드를 오브젝트 스토리지로 빼면 앱이 무상태(stateless)가 됩니다. 그다음부터 서버 수는 그냥 숫자일 뿐입니다. 쿠버네티스·오토스케일링도 이 전제 위에서 동작합니다.
SECTION 06

헬스체크 — 죽은 서버 빼기

로드밸런서의 진짜 가치는 분산보다 장애를 숨기는 것에 있습니다.

방식동작
수동적 (passive) 실제 사용자 요청이 실패하는 것을 보고 제외 — Nginx 오픈소스의 기본 방식. 공짜지만 최소 한 명은 실패를 겪습니다 (재시도로 가려 줌)
능동적 (active) ★ 주기적으로 /health 를 미리 찔러보고 제외 — 사용자가 실패를 만나기 전에 뺍니다. HAProxy·Caddy·클라우드 LB 기본, Nginx 는 Plus 기능

Nginx 수동적 헬스체크 — 정확히 이해하기

upstream backend {
    # 10초(fail_timeout) 안에 3번(max_fails) 실패하면
    # → 그 서버를 10초간(같은 fail_timeout) 제외
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
}

server {
    location / {
        proxy_pass http://backend;

        # '실패'로 칠 조건과 다음 서버 재시도 규칙
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;         # 최대 2대까지 시도
        proxy_next_upstream_timeout 10s;     # 재시도에 쓸 총 시간

        proxy_connect_timeout 3s;            # 연결 자체는 빨리 포기
    }
}
재시도가 항상 안전한 것은 아닙니다. proxy_next_upstream 은 기본적으로 POST 같은 비멱등 요청을 timeout 시 재시도하지 않습니다 — 결제가 두 번 나가는 사고를 막기 위해서입니다. non_idempotent 옵션으로 풀 수 있지만, 그 API 가 두 번 실행돼도 안전한지(멱등 키 등) 확인한 뒤에만 쓰세요.

능동적 헬스체크 — HAProxy · Caddy

HAProxy
backend app
    option httpchk GET /health
    http-check expect status 200
    default-server inter 3s fall 3 rise 2
    #  inter 3s : 3초마다 검사
    #  fall 3   : 3연속 실패 → 제외
    #  rise 2   : 2연속 성공 → 복귀
    server app1 10.0.0.11:8080 check
    server app2 10.0.0.12:8080 check
Caddy
reverse_proxy 10.0.0.11:8080 10.0.0.12:8080 {
    health_uri      /health
    health_interval 3s
    health_timeout  2s
    health_status   200
    # 능동 헬스체크가 오픈소스에 기본 내장
}

/health 엔드포인트는 어떻게 만드나

수준내용
liveness (살았나) ★ 프로세스가 응답하는지만 — DB 를 건드리지 않는 가벼운 200 응답. LB 헬스체크는 보통 이것이면 충분합니다
readiness (받을 수 있나) DB·캐시 연결까지 확인. 무겁고, DB 순단 시 전 서버가 동시에 제외되는 위험이 있어 신중하게 설계합니다 (🧬 전문가 z12)
헬스체크 요청은 로그에서 빼세요. 3초마다 × 서버 수만큼 쌓여 로그를 오염시킵니다. Nginx 라면 location /health { access_log off; return 200; } 처럼 앱까지 가지 않고 끊는 방법도 있습니다 — 단, 이건 Nginx 의 생존만 보장할 뿐이니 LB 가 앱을 검사할 때는 앱의 /health 를 쓰는 것이 맞습니다.
SECTION 07

HTTPS 는 어디서 끝내나

서버가 여러 대가 되면 인증서를 어디에 둘지 결정해야 합니다.

표준 구성 — TLS 종료(termination)를 로드밸런서에서

사용자 ══ HTTPS ══▶ [ 로드밸런서 ] ── HTTP ──▶ [앱1·앱2·앱3]
                    인증서는 여기 한 곳에만!

· 인증서 발급·갱신을 LB 한 곳에서만 관리 (🔐 HTTPS 탭)
· 앱 서버는 TLS 부담이 없어 가볍다
· LB 가 내용을 보므로 L7 라우팅·캐시·압축 가능
대신 두 가지를 반드시 챙겨야 합니다.
① 앱은 자신이 HTTP 로 받았으므로 "지금 HTTPS 접속인가"를 모릅니다 → X-Forwarded-Proto 헤더로 알려 줘야 리다이렉트 루프·secure 쿠키 문제가 없습니다
② LB→앱 구간이 평문입니다 — 반드시 사설망이어야 하고, 규정상 내부도 암호화해야 하면 재암호화(아래)를 씁니다 
# Nginx 를 LB 로 쓸 때 — 앱에 원본 정보를 전달
server {
    listen 443 ssl;
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;    # ★ https 임을 전달
    }
}

세 가지 방식 비교

방식설명
TLS 종료 (LB 에서 끝) ★ 표준. 관리 한 곳 · 앱 가벼움. LB→앱은 사설망 전제
재암호화 (종료 후 다시 TLS) 사용자→LB, LB→앱 둘 다 암호화. 내부 암호화 규정(금융·의료)이 있을 때. 내부용 인증서는 사설 CA 로 (🔐 HTTPS s11)
통과 (passthrough) LB 가 TLS 를 풀지 않고 TCP 로 흘려보냄(L4). 앱까지 종단간 암호화되지만 L7 기능(경로 라우팅·헤더)을 전부 포기합니다
TLS 종료 위치별 성능·구조 심화는 🧬 전문가 z06, 다단 프록시에서 실제 방문자 IP 를 지키는 법은 🧬 전문가 z10 에서 이어집니다.
SECTION 08

HAProxy — 전용 로드밸런서

Nginx 로 시작해도 되지만, 로드밸런싱만큼은 HAProxy 가 더 깊습니다. 능동 헬스체크·정밀한 통계·드레인이 오픈소스에 다 들어 있습니다. 

sudo apt install -y haproxy
haproxy -v                                   # 설치 확인
sudo systemctl enable --now haproxy

haproxy.cfg 해부 — 구조는 넷뿐입니다

# /etc/haproxy/haproxy.cfg
global                                # ① 프로세스 전역 (로그·보안·한계치)
    log /dev/log local0
    maxconn 20000
    user haproxy
    group haproxy

defaults                              # ② 아래 모든 블록의 기본값
    mode http                         #    L7 모드 (tcp 로 바꾸면 L4)
    log global
    option httplog
    timeout connect 5s                #    백엔드 연결 수립 제한
    timeout client  30s               #    클라이언트 무응답 제한
    timeout server  30s               #    백엔드 무응답 제한

frontend web_in                       # ③ 받는 곳 — 어디로 듣고 어디로 넘길까
    bind *:80
    # 경로 기반 라우팅 (L7 의 힘)
    acl is_api path_beg /api
    use_backend api_pool if is_api
    default_backend web_pool

backend web_pool                      # ④ 보내는 곳 — 서버 그룹 + 헬스체크
    balance roundrobin                #    leastconn · source 등
    option httpchk GET /health
    http-check expect status 200
    default-server inter 3s fall 3 rise 2
    server web1 10.0.0.11:8080 check
    server web2 10.0.0.12:8080 check

backend api_pool
    balance leastconn
    option httpchk GET /health
    server api1 10.0.0.21:8080 check
    server api2 10.0.0.22:8080 check
# 문법 검사 → 무중단 반영 (nginx -t && reload 와 같은 습관)
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy

stats 페이지 — 상태가 눈에 보인다

listen stats
    bind *:8404
    stats enable
    stats uri /stats
    stats refresh 5s
    stats auth admin:비밀번호변경     # ★ 반드시 변경 + 내부망·IP 제한
# → http://LB주소:8404/stats 에서
#   서버별 상태(UP/DOWN)·연결 수·응답 시간·에러가 실시간으로 보입니다
항목Nginx (오픈소스)HAProxy
능동 헬스체크✗ (Plus 전용)✓ 기본
쿠키 기반 sticky✗ (Plus 전용)✓ 기본 (cookie SRV insert)
상태 대시보드stub_status (숫자 몇 개)stats 페이지 — 서버별 상세
드레인 (서서히 빼기)down + reload 로 대응런타임 API 로 재시작 없이
정적 파일 · 캐시✓ 강함✗ (프록시 전용)
역할 요약웹서버 + 준수한 LBLB 특화 — 그 외엔 관심 없음
고르는 법 — 이미 Nginx 를 쓰고 규모가 작다면 그대로 Nginx 로 충분합니다. 서버가 늘고 능동 헬스체크·정밀 드레인·상태 가시성이 아쉬워지는 시점에 HAProxy 를 앞단에 세우세요. 실무에서는 HAProxy(LB) → Nginx(웹서버) → 앱 처럼 겹쳐 쓰는 구성도 흔합니다.
SECTION 09

무중단 배포 — LB 로 하는 법

로드밸런서가 있으면 배포 중에도 503 이 안 나는 구성이 가능해집니다.

롤링 배포 — 한 대씩 빼서 올린다

1
앱1 을 분리 (drain) 새 요청은 안 보내고, 처리 중인 요청은 끝나게 둡니다.
▼
2
앱1 에 새 버전 배포 → 자체 확인 LB 를 거치지 않고 curl http://10.0.0.11:8080/health 로 직접 확인합니다.
▼
3
앱1 복귀 → 앱2 로 반복 전체가 끝날 때까지 사용자는 구버전 또는 신버전 중 하나를 항상 받습니다.
Nginx — down + reload 로 드레인
upstream backend {
    server 10.0.0.11:8080 down;   # ← 배포할 서버에 down
    server 10.0.0.12:8080;
}
# sudo nginx -t && sudo systemctl reload nginx
#
# reload 는 기존 연결을 끊지 않으므로(n18)
# '새 요청 차단 + 진행 중 요청 완료' = 드레인이 됩니다
# 배포 후 down 을 지우고 다시 reload
HAProxy — 재시작 없이 런타임 API
# global 에 stats socket 을 열어 두면
#   stats socket /run/haproxy/admin.sock mode 660 level admin
echo "set server web_pool/web1 state drain" \
  | sudo socat stdio /run/haproxy/admin.sock

# 배포 후 복귀
echo "set server web_pool/web1 state ready" \
  | sudo socat stdio /run/haproxy/admin.sock

블루-그린 배포 — 전체를 통째로 전환

# 구버전(blue)과 신버전(green)을 나란히 띄워 두고 한 번에 전환
upstream blue  { server 10.0.0.11:8080; server 10.0.0.12:8080; }
upstream green { server 10.0.0.21:8080; server 10.0.0.22:8080; }

server {
    location / {
        proxy_pass http://blue;      # ← 이 한 단어를 green 으로 바꾸고 reload
    }
}
# 장점: 전환·롤백이 즉시 (다시 blue 로 reload)
# 대가: 서버가 2배로 필요 (전환하는 동안만)
전략특징
롤링★ 추가 서버 불필요. 배포 중 구·신버전이 공존합니다 — DB 스키마·API 는 하위 호환이어야 안전합니다
블루-그린전환·롤백 즉시. 서버 2배. 공존 시간이 짧아 호환성 부담이 적습니다
카나리신버전에 5% 만 먼저 (weight=1 vs weight=19) → 지표 확인 후 확대. 대규모 서비스의 표준
배포 자동화 전 필수 점검
① 드레인 없이 그냥 껐다면 — 처리 중이던 요청이 그대로 502 가 됩니다
② 새 버전이 뜨자마자 트래픽을 받으면 — 워밍업 전이라 첫 요청들이 느립니다 (헬스체크 통과 후 복귀시키세요)
③ 세션이 서버에 있다면(b05) — 빼는 순간 그 서버 사용자들이 로그아웃됩니다
reload 신호의 내부 동작은 🟩 Nginx n18, 톰캣의 graceful 종료는 🐱 Tomcat t14 참고.
SECTION 10

LB 자체가 죽으면? — 이중화

서버를 아무리 늘려도 로드밸런서가 한 대면 거기가 단일 장애점(SPOF)입니다. 

keepalived (VRRP) — 가상 IP 로 LB 를 2대로

            사용자는 이 IP 만 안다
                  │
            VIP 10.0.0.100        ← 가상 IP (떠다니는 IP)
             ┌────┴────┐
        ┌────▼───┐ ┌───▼────┐
        │  LB-1  │ │  LB-2  │
        │ MASTER │ │ BACKUP │   ← 평소엔 MASTER 가 VIP 를 소유
        └────────┘ └────────┘
             │  1초마다 "나 살아있어" (VRRP 광고)
             ▼
        MASTER 가 죽으면 BACKUP 이 수 초 안에 VIP 를 가져간다
        → 사용자 입장에선 IP 가 그대로라 아무 일도 없던 것처럼 보인다
# /etc/keepalived/keepalived.conf  (LB-1 · MASTER 쪽)
vrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"    # 프로세스 생존 확인
    interval 2
    weight -20                              # 죽으면 우선순위를 깎아 강등
}

vrrp_instance VI_1 {
    state MASTER                 # LB-2 는 BACKUP
    interface eth0
    virtual_router_id 51         # ★ 두 대가 반드시 같은 값
    priority 100                 # LB-2 는 90 (낮게)
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 비밀문자열
    }
    virtual_ipaddress {
        10.0.0.100/24            # ★ 이 VIP 를 DNS 에 등록합니다
    }
    track_script { chk_haproxy }
}
핵심 그림 — DNS 는 VIP 하나만 가리키고, VIP 는 살아 있는 LB 를 따라다닙니다. HAProxy 가 죽어도(track_script), 머신이 통째로 죽어도(광고 중단) 자동 전환됩니다. 같은 L2 네트워크(같은 서브넷)에서 동작하는 방식이라 온프레미스·IDC 구성에서 씁니다.
방법설명
keepalived (VRRP) ★ 온프레미스 표준. VIP 자동 전환 · 수 초 내 복구
DNS 다중 A + 헬스체크 Route 53 등 헬스체크 연동 DNS 로 죽은 LB 를 응답에서 제외 — 지역 간(멀티 리전) 분산에 적합. TTL 만큼 전환이 느립니다
관리형 LB (클라우드) ★ ALB·NLB 는 이중화가 내장돼 있습니다 — 클라우드라면 고민 자체가 사라집니다 (b11)
이중화를 만들었으면 반드시 죽여 보세요. MASTER 의 haproxy 를 systemctl stop haproxy 로 내리고 VIP 가 BACKUP 으로 넘어가는지, 서비스가 몇 초 만에 복구되는지 실측해야 진짜 이중화입니다. 테스트해 본 적 없는 페일오버는 없는 것과 같습니다.

SECTION 12

규모별 구성 레시피

지금 단계에 맞는 구성을 골라 그대로 쓰세요. 과한 구성은 그 자체가 비용입니다.

🟢 1단계 — 서버 1대 (아직 LB 불필요)
  • Nginx(리버스 프록시) + 앱 + HTTPS
  • 지금 할 일: 앱을 무상태로 만들어 두기 (b05)
  • 그래야 2단계 전환이 설정 몇 줄로 끝납니다
🟡 2단계 — 앱 2~5대 (이 탭의 핵심)
  • Nginx upstream + least_conn (b03·b04)
  • 세션 → Redis · 업로드 → 오브젝트 스토리지 (b05)
  • 헬스체크 + 드레인 배포 (b06·b09)
  • TLS 는 LB 에서 종료 (b07)
🔴 3단계 — 그 이상 (고가용성)
  • HAProxy 승격 또는 관리형 LB (b08·b11)
  • LB 이중화 — keepalived VIP (b10)
  • 카나리 배포 + 지표 기반 롤백 (b09)
  • 내부 구조 심화 → 🧬 전문가 z11·z12

배포 전 체크리스트

서버를 늘리기 전에
① 세션·업로드·캐시가 서버 밖으로 나갔는가 (b05)
② /health 엔드포인트가 있는가 (b06)
③ 앱 로그에 실제 방문자 IP 가 남는가 — X-Forwarded-For (b07 · 🟩 n08)
LB 를 세운 뒤에
④ 서버 한 대를 죽여도 서비스가 사는가 (b03 실험을 실전에서)
⑤ 드레인 배포가 실제로 무중단인가 — 배포 중 curl 루프로 확인 (b09)
⑥ 분배가 기울지 않는가 — 접속 로그의 $upstream_addr 집계
⑦ LB 자체의 장애 대책이 있는가 (b10)
다음 갈 곳 — 알고리즘·일관된 해싱의 내부 원리는 🧬 전문가 z11, 서킷 브레이킹·장애 전파 차단은 🧬 전문가 z12, 성능 관점의 커널·커넥션 튜닝은 ⚡ 성능 탭에서 이어집니다.
