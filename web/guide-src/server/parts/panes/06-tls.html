HTTPS · TLS 1.3 · LET'S ENCRYPT · 인증서 운영

HTTPS —
발급부터
갱신까지

HTTPS 는 이제 선택이 아닙니다. 브라우저가 HTTP 사이트에 "안전하지 않음"을 표시하고, HTTP/2·3 과 여러 브라우저 API 가 HTTPS 를 요구합니다. 다행히 Let's Encrypt 덕분에 무료이고 자동화도 어렵지 않습니다. 인증서 만료로 서비스가 멈추는 사고만 피하면 됩니다.

SECTION 01

HTTPS는 무엇을 지키나

자물쇠 아이콘이 보장하는 것은 세 가지입니다.

보장없으면 생기는 일
기밀성
(암호화)		 같은 와이파이의 누구나 비밀번호·쿠키·개인정보를 그대로 볼 수 있습니다
무결성
(변조 방지)		 중간에서 내용을 바꿔치기할 수 있습니다 — 광고 삽입·악성 스크립트 주입이 실제로 있었습니다
인증
(신원 확인)		 가짜 사이트에 접속해도 알 수 없습니다 (피싱)
HTTPS 가 보장하지 않는 것도 알아야 합니다.
· 사이트가 안전하다는 뜻이 아닙니다 — 피싱 사이트도 HTTPS 를 씁니다
· 서버가 해킹되지 않는다는 뜻이 아닙니다 — 전송 구간만 보호합니다
· 어느 사이트에 접속했는지는 숨겨지지 않습니다 — 도메인은 노출됩니다(SNI)
· 데이터는 서버에 도착한 뒤에는 평문입니다

HTTPS 가 필수인 실질적 이유

  • 브라우저 경고 — HTTP 폼에 입력하면 "안전하지 않음" 경고가 뜹니다
  • HTTP/2 · HTTP/3 — 사실상 HTTPS 에서만 동작합니다
  • 브라우저 API 제한 — 위치·카메라·서비스워커·클립보드 등이 보안 컨텍스트에서만 동작합니다
  • 검색 순위 — 검색엔진이 HTTPS 를 순위 요소로 반영합니다
  • 쿠키 보안 속성 — Secure·SameSite=None 이 HTTPS 를 요구합니다
"내부 서버라 HTTP 로 충분하다"는 판단은 재검토하세요. 사내망 침해 후 내부 트래픽을 엿보는 공격이 일반적입니다. 내부 서버도 사설 CA 나 DNS 챌린지로 HTTPS 를 적용할 수 있습니다(s11 · 🔒 Caddy c05).
자물쇠 아이콘의 정확한 뜻은 "내용이 중간에서 새거나 바뀌지 않았다" 입니다 — 상대가 믿을 만한지는 말해 주지 않습니다.

HTTP 로 두면 실제로 무엇이 막히나

기능HTTP 에서
서비스 워커 · PWA등록 자체가 안 됩니다(localhost 예외)
위치 · 카메라 · 마이크권한 요청이 차단됩니다
클립보드 API동작하지 않습니다
HTTP/2 · HTTP/3브라우저가 HTTPS 에서만 씁니다 → 느립니다
Secure 쿠키설정해도 전송되지 않습니다
SameSite=NoneSecure 가 함께 필요 → 크로스 사이트 인증 불가
비밀번호 입력란주소창에 "안전하지 않음" 경고
혼합 콘텐츠HTTPS 페이지에서 HTTP 자원은 차단됩니다
"우리 사이트는 로그인이 없어서 HTTP 로 충분하다"는 이제 성립하지 않습니다. 현대 웹 기능의 상당수가 보안 컨텍스트를 전제로 설계돼 있어서, HTTP 로 두면 기능이 안 되는 쪽이 문제가 됩니다. 비용도 사실상 0 입니다 — Let's Encrypt 는 무료이고, Caddy 는 도메인만 적으면 끝나며, certbot 도 명령 한 줄입니다. 안 할 이유를 찾기가 더 어렵습니다.
SECTION 02

TLS 핸드셰이크

접속할 때 무슨 대화가 오가는지 알면 인증서 오류와 지연을 진단할 수 있습니다.

1
ClientHello 브라우저가 "지원하는 TLS 버전·암호 목록"과 접속하려는 도메인(SNI)을 보냅니다. SNI 는 아직 암호화되지 않아 어느 사이트인지 노출됩니다.
▼
2
ServerHello + 인증서 서버가 암호 방식을 고르고 인증서(서버+중간)를 보냅니다. 여기서 중간 인증서가 빠지면 일부 클라이언트에서 오류가 납니다(s08).
▼
3
인증서 검증 브라우저가 ① 신뢰하는 CA 가 서명했나 ② 도메인이 맞나 ③ 만료되지 않았나 ④ 폐기되지 않았나 를 확인합니다.
▼
4
키 교환 → 대칭키 확정 이후 실제 데이터는 빠른 대칭키 암호로 주고받습니다. 공개키 암호는 이 키를 안전하게 나누는 데만 씁니다.
TLS 1.3 이 빠른 이유 — 1.2 는 핸드셰이크에 왕복 2회(2-RTT)가 필요했지만 1.3 은 1회(1-RTT) 로 줄였고, 재접속 시에는 0-RTT 도 가능합니다. 지연이 큰 모바일 환경에서 체감 차이가 큽니다.
다만 0-RTT 는 재전송 공격 위험이 있어 GET 같은 안전한 요청에만 쓰도록 제한됩니다. 
# 실제 핸드셰이크 관찰
openssl s_client -connect example.com:443 -servername example.com < /dev/null

# 협상된 프로토콜·암호만 확인
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | grep -E 'Protocol|Cipher'

# TLS 단계별 소요 시간
curl -w "tls:%{time_appconnect}s connect:%{time_connect}s total:%{time_total}s\n" \
     -o /dev/null -s https://example.com
Nginx 는 fullchain.pem, Apache 2.4.8+ 도 fullchain.pem — 서버 인증서 하나만 지정하는 실수가 가장 흔합니다.

핸드셰이크에서 나는 오류 — 증상별

증상원인 · 확인
일부 기기에서만 인증서 오류중간 인증서 누락 — fullchain.pem 을 쓰고 있는지
NET::ERR_CERT_COMMON_NAME_INVALID인증서의 도메인과 접속 도메인이 다름 — www 포함 여부
ERR_CERT_DATE_INVALID만료 · 서버 시각이 틀림(NTP 확인)
다른 사이트 인증서가 나옴SNI 미매칭 — server_name·ServerName 확인
구형 기기만 접속 실패TLS 1.0/1.1 차단 · 최신 암호만 허용
첫 접속만 유난히 느림OCSP 스테이플링 미설정 → 브라우저가 CA 에 직접 문의
갱신했는데 옛 인증서reload 안 함 — 가장 흔합니다
사내망에서만 오류SSL 검사 장비가 인증서를 바꿔치기 — 사내 루트 CA 신뢰 필요
# ① 체인이 완전한지 — 가장 먼저 확인할 것
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 \
  | grep -A20 "Certificate chain"
# 서버 인증서 → 중간 인증서까지 나와야 정상입니다 (루트는 안 보내도 됩니다)

# ② 검증 결과
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 \
  | grep "Verify return code"
# "0 (ok)" 가 아니면 문제입니다

# ③ 중간 인증서 없이도 되는지 시험 (엄격 검증)
openssl s_client -connect example.com:443 -servername example.com \
  -verify_return_error -CApath /etc/ssl/certs < /dev/null

# ④ 협상 결과 — 프로토콜과 암호
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | grep -E "Protocol|Cipher|Server Temp Key"

# ⑤ 어느 단계가 느린지 숫자로
curl -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} \
ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s https://example.com
# tls - tcp 가 핸드셰이크 시간입니다. 100ms 를 크게 넘으면 OCSP 를 의심하세요.
OCSP 스테이플링을 켜면 첫 접속이 눈에 띄게 빨라집니다. 켜지 않으면 브라우저가 인증서가 폐기됐는지 CA 서버에 직접 물어봅니다 — 해외에 있는 CA 라면 수백 ms 가 그대로 더해지고, CA 가 느리면 우리 사이트가 느려 보입니다. 스테이플링은 서버가 그 답변을 미리 받아 인증서와 함께 건네주는 방식입니다. Nginx ssl_stapling on;, Apache SSLUseStapling on 한 줄입니다.
SECTION 03

인증서의 종류와 구성

파일이 여러 개인데 각각 무엇인지 헷갈립니다. 여기서 정리합니다.

파일내용
privkey.pem개인키 — 절대 유출되면 안 됩니다. 권한 600
cert.pem서버 인증서 (내 도메인용)
chain.pem중간 인증서 — CA 와 내 인증서를 잇는 다리
fullchain.pem★ cert + chain — Nginx·Apache 에는 이것을 지정합니다
*.p12 · *.jks자바용 키스토어 (톰캣)
Nginx·Apache 에는 fullchain.pem 을 쓰세요. cert.pem 만 지정하면 중간 인증서가 빠져 PC 브라우저에서는 되는데 모바일·구형 클라이언트에서 오류가 납니다(s08).

신뢰 체인

루트 CA (브라우저·OS에 미리 내장)
      │ 서명
      ▼
중간 CA (Let's Encrypt R11 등)   ← chain.pem
      │ 서명
      ▼
내 서버 인증서 (example.com)      ← cert.pem

브라우저는 이 체인을 위로 따라가
'내가 아는 루트'에 닿아야 신뢰합니다.
중간 인증서가 빠지면 체인이 끊깁니다.

인증서 종류

구분내용
DV (도메인 검증)도메인 소유만 확인. Let's Encrypt 가 이것 · 무료 · 자동
OV (조직 검증)기업 실체를 확인. 유료
EV (확장 검증)엄격한 심사. 유료. 브라우저 주소창의 회사명 표시는 대부분 사라졌습니다
단일 도메인example.com 하나
SAN (멀티 도메인)여러 도메인을 한 인증서에 (Let's Encrypt 는 최대 100개)
와일드카드*.example.com — DNS 챌린지가 필요합니다
암호화 강도는 DV·OV·EV 가 모두 같습니다. 차이는 발급 전 신원 확인 절차뿐입니다. EV 인증서가 브라우저에 회사명을 표시하던 기능은 주요 브라우저에서 제거됐으므로, 대부분의 서비스에는 무료 DV 로 충분합니다. (금융·공공 등 규정상 OV·EV 가 요구되는 경우는 예외) 
# 인증서 내용 확인
openssl x509 -in fullchain.pem -noout -text | head -30
openssl x509 -in fullchain.pem -noout -subject -issuer -dates
openssl x509 -in fullchain.pem -noout -ext subjectAltName    # 포함된 도메인 목록

# 개인키와 인증서가 짝이 맞는지 (해시가 같아야 합니다)
openssl x509 -noout -modulus -in fullchain.pem | openssl md5
openssl rsa  -noout -modulus -in privkey.pem   | openssl md5
고민이 길어지면 DV + 필요한 이름 전부면 대부분 끝납니다.
SECTION 04

Let's Encrypt · certbot

무료 인증서를 발급받습니다. 명령 한 번이면 됩니다.

전제 조건
① 도메인이 이 서버 IP 를 가리켜야 합니다 (dig +short example.com)
② 80 포트가 인터넷에서 접근 가능해야 합니다 (HTTP-01 챌린지)
③ 와일드카드(*.example.com)는 DNS 챌린지가 필요합니다 
# 설치
sudo apt install -y certbot python3-certbot-nginx      # Nginx 플러그인
sudo apt install -y python3-certbot-apache             # Apache 플러그인

# ── 방법 ① 웹서버 설정까지 자동으로 (가장 쉬움)
sudo certbot --nginx -d example.com -d www.example.com

# ── 방법 ② 인증서만 받고 설정은 직접
sudo certbot certonly --nginx -d example.com

# ── 방법 ③ 웹서버를 잠시 멈추고 (standalone)
sudo certbot certonly --standalone -d example.com

# ── 방법 ④ 실행 중인 서버의 문서 루트를 이용 (무중단)
sudo certbot certonly --webroot -w /var/www/html -d example.com

# ── 방법 ⑤ DNS 챌린지 (와일드카드·포트를 못 여는 경우)
sudo certbot certonly --manual --preferred-challenges dns -d '*.example.com'
# 안내에 따라 DNS 에 TXT 레코드를 추가해야 합니다
# webroot 방식을 쓰려면 이 location 이 열려 있어야 합니다
server {
    listen 80;
    server_name example.com;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
        allow all;                        # ★ 인증 없이 접근 가능해야 합니다
    }

    location / {
        return 301 https://$host$request_uri;
    }
}
발급 한도에 주의하세요. Let's Encrypt 는 등록 도메인당 주 50건, 동일한 도메인 조합은 주 5건의 제한이 있습니다. 테스트하다 반복 실패하면 일주일간 발급이 막힙니다.
테스트에는 반드시 --dry-run 또는 스테이징 서버를 쓰세요: certbot certonly --dry-run --nginx -d example.com 
# 발급된 인증서 확인
sudo certbot certificates
sudo ls -l /etc/letsencrypt/live/example.com/

# 도메인 추가·변경 (기존 인증서를 확장)
sudo certbot --nginx -d example.com -d www.example.com -d api.example.com --expand

# 인증서 폐기·삭제
sudo certbot revoke --cert-path /etc/letsencrypt/live/example.com/cert.pem
sudo certbot delete --cert-name example.com
SECTION 05

따라하기 — 발급부터 적용까지

도메인 하나를 HTTP 상태에서 HTTPS 완성까지 한 번에 갑니다. 단계마다 확인 명령이 있으니 그대로 순서대로 실행하면 됩니다. (Nginx 기준 · 소요 약 15분)

STEP 0
준비물 점검 도메인 · 서버(공인 IP) · Nginx 설치 완료 · 80/443 포트 개방. 하나라도 없으면 아래 0단계에서 먼저 해결합니다.
▼
STEP 1
DNS 를 서버로 연결 도메인의 A 레코드가 이 서버 IP 를 가리키게 합니다. 전파 확인 전에는 다음 단계로 가지 마세요.
▼
STEP 2
HTTP(80) 서버 블록 준비 인증 요청이 들어올 자리를 만듭니다. 이 시점에는 아직 HTTP 사이트입니다.
▼
STEP 3
certbot 으로 발급 + 자동 설정 인증서를 받으면서 443 블록·리다이렉트까지 certbot 이 만들어 줍니다.
▼
STEP 4
적용 확인 브라우저 자물쇠 · 체인 · 리다이렉트 · 등급을 확인합니다.
▼
STEP 5
자동 갱신 확인 여기까지 마쳐야 90일 뒤에도 서비스가 살아 있습니다.

STEP 0 — 준비물 점검

# Nginx 가 떠 있나
systemctl status nginx --no-pager | head -3

# 80·443 포트가 열려 있나 (ufw 기준)
sudo ufw status | grep -E '80|443'
sudo ufw allow 'Nginx Full'                 # 안 열려 있으면

# 클라우드(AWS·GCP 등)라면 보안 그룹에서도 80·443 인바운드를 열어야 합니다
# 내 서버의 공인 IP 확인
curl -4 -s ifconfig.me; echo

STEP 1 — DNS 연결과 전파 확인

도메인 관리 콘솔(가비아·후이즈·Cloudflare·Route 53 등)에서 A 레코드를 추가합니다: example.com → 서버 공인 IP, 필요하면 www 도 함께. 

# 도메인이 내 서버 IP 를 가리키는지 (STEP 0 의 IP 와 같아야 합니다)
dig +short example.com
dig +short www.example.com

# 아직 예전 값이 나오면 TTL 만큼 기다립니다 (보통 수분~1시간)
# 여러 지역에서의 전파 상태는 dnschecker.org 에서 확인할 수 있습니다
DNS 가 전파되기 전에 certbot 을 실행하면 실패합니다. Let's Encrypt 서버가 도메인으로 접속해 확인하는 방식이기 때문입니다. 실패를 반복하면 발급 한도(s04)에 걸려 일주일간 막힐 수 있으니 dig 결과가 맞을 때까지 기다렸다가 진행하세요.

STEP 2 — HTTP 서버 블록 준비

# /etc/nginx/sites-available/example.com
server {
    listen 80;
    server_name example.com www.example.com;   # ★ 발급받을 도메인과 정확히 일치

    root /var/www/example.com;

}
sudo mkdir -p /var/www/example.com
echo '<h1>It works</h1>' | sudo tee /var/www/example.com/index.html

sudo ln -s /etc/nginx/sites-available/example.com /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 확인 — HTTP 로 접속되는지 (여기까지가 HTTPS 이전의 마지막 모습입니다)
curl -I http://example.com

STEP 3 — 발급 + 자동 설정 (핵심 한 줄)

sudo apt install -y certbot python3-certbot-nginx

# 이 한 줄이 ①발급 ②443 블록 생성 ③인증서 지정 ④HTTP→HTTPS 리다이렉트까지 합니다
sudo certbot --nginx -d example.com -d www.example.com

# 처음 실행하면 이메일(만료 경고 수신용)과 약관 동의를 묻습니다
# "Congratulations!" 가 나오면 성공입니다
certbot 이 내 설정을 어떻게 바꿨는지 봐 두세요. sites-available/example.com 을 다시 열면 443 server 블록과 ssl_certificate 두 줄, 그리고 80 블록의 301 리다이렉트가 추가돼 있습니다. 자동 수정이 싫다면 certbot certonly 로 인증서만 받고 s07 의 서버별 설정을 직접 쓰면 됩니다.

STEP 4 — 적용 확인

# ① HTTPS 응답 확인

# ② HTTP → HTTPS 리다이렉트 확인 (301 + Location: https:// 가 나와야 합니다)
curl -I http://example.com

# ③ 체인이 완전한지 (0 과 1 두 개가 보여야 정상 — s08)

  | grep -A 5 'Certificate chain'

# ④ 모바일 실기기 브라우저에서도 한 번 열어 보세요 (PC 는 체인 문제를 감춰 줍니다)
# ⑤ ssllabs.com/ssltest 에서 등급 확인 — A 이상이면 합격

STEP 5 — 자동 갱신 확인 (빠뜨리면 90일 뒤 장애)

# 갱신 타이머가 걸려 있나
systemctl list-timers | grep certbot

# 갱신 리허설 — 전 과정을 실제 발급 없이 검증합니다
sudo certbot renew --dry-run
# "Congratulations, all simulated renewals succeeded" 가 나오면 완료입니다
여기까지 하면 HTTPS 적용은 끝입니다. 더 깊게 가려면 —
· 갱신 후 reload 훅과 타이머 구조 → s06
· Apache · Tomcat · Caddy 에 적용 → s07 (Caddy 는 이 전 과정이 자동입니다 · 🔒 Caddy c05)
· 보안 등급 올리기(TLS 버전 · HSTS) → s09 · s10
· 만료 감시 알람 → s12
자주 나는 실패 3가지
① DNS problem: NXDOMAIN — DNS 전파 전에 실행 (STEP 1 로)
② Connection refused — 80 포트가 닫혀 있음 (STEP 0 방화벽·보안 그룹)
③ unauthorized — 도메인이 다른 서버를 가리키고 있음 (dig 로 IP 재확인)
SECTION 06

갱신 자동화

Let's Encrypt 인증서는 90일짜리입니다. 자동 갱신이 조용히 실패하면 어느 날 갑자기 서비스가 멈춥니다. 

# 패키지로 설치하면 타이머가 이미 등록돼 있습니다
systemctl list-timers | grep certbot
sudo systemctl status certbot.timer

# 갱신 테스트 (실제로 갱신하지 않고 전 과정을 검증)
sudo certbot renew --dry-run

# 수동 갱신 (만료 30일 이내인 것만 실제로 갱신됩니다)
sudo certbot renew

# 강제 갱신 (테스트 외에는 쓰지 마세요 — 발급 한도 소모)
sudo certbot renew --force-renewal
갱신은 됐는데 적용이 안 되는 경우가 가장 흔합니다. 파일은 새로 받았지만 웹서버가 옛 인증서를 메모리에 들고 있어 만료된 인증서를 계속 내보냅니다. 갱신 후 반드시 reload 를 걸어야 합니다. 
# 갱신 성공 시 자동으로 실행될 훅
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-web.sh <<'EOF'
#!/usr/bin/env bash
set -e
systemctl reload nginx    || true
systemctl reload apache2  || true
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-web.sh
훅 종류실행 시점
renewal-hooks/pre/갱신 시도 전 (예: standalone 을 위해 웹서버 중지)
renewal-hooks/deploy/★ 갱신 성공 시에만 — reload 는 여기에
renewal-hooks/post/갱신 시도 후 (성공·실패 무관)

직접 타이머를 만든다면

# /etc/systemd/system/certbot-renew.service
[Unit]
Description=Certbot renewal
[Service]
Type=oneshot
ExecStart=/usr/bin/certbot renew --quiet --deploy-hook "systemctl reload nginx"

# /etc/systemd/system/certbot-renew.timer
[Unit]
Description=Run certbot twice daily
[Timer]
OnCalendar=*-*-* 03,15:00:00
RandomizedDelaySec=3600        # ★ 서버가 많으면 분산 (CA 부하 방지)
Persistent=true
[Install]
WantedBy=timers.target
하루 두 번 실행하는 이유 — 갱신은 만료 30일 이내일 때만 실제로 수행되므로 자주 돌려도 무해합니다. 한 번 실패해도 다음 시도가 곧 있어 여유가 생깁니다. 랜덤 지연은 전 세계 서버가 정각에 몰리는 것을 막기 위한 배려입니다.
인증서 장애는 예고가 있습니다 — 다만 보고 있어야 보입니다.
SECTION 07

서버별 설치 방법

같은 인증서라도 서버마다 지정 방식이 다릅니다.

Nginx
server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
}
# sudo nginx -t && sudo systemctl reload nginx
Apache
<VirtualHost *:443>
    ServerName example.com
    SSLEngine on
    SSLCertificateFile    /etc/letsencrypt/live/example.com/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/example.com/privkey.pem
    SSLProtocol -all +TLSv1.2 +TLSv1.3
</VirtualHost>
# sudo apachectl configtest && sudo systemctl reload apache2
Tomcat · Spring Boot
# PEM → PKCS12 변환이 필요합니다
openssl pkcs13 -export \
  -in  /etc/letsencrypt/live/example.com/fullchain.pem \
  -inkey /etc/letsencrypt/live/example.com/privkey.pem \
  -out keystore.p12 -name tomcat \
  -passout pass:changeit

# application.properties
# server.ssl.key-store=/opt/app/keystore.p12
# server.ssl.key-store-type=PKCS12
# server.ssl.key-alias=tomcat
Caddy
example.com {
    # 아무것도 안 써도 자동 발급·갱신됩니다

    # 직접 준비한 인증서를 쓰려면
    # tls /path/cert.pem /path/key.pem
}
파일 권한을 확인하세요. privkey.pem 은 600(소유자만 읽기)이어야 합니다. Nginx·Apache 는 root 로 시작한 마스터 프로세스가 인증서를 읽으므로 워커 계정에 권한을 줄 필요가 없습니다.
반면 톰캣·Spring Boot 는 앱 계정으로 읽어야 하므로 키스토어 파일 소유자를 앱 계정으로 바꿔야 합니다.

여러 도메인 · SNI

# 한 IP 에서 여러 도메인에 각각 다른 인증서
server {
    listen 443 ssl;
    server_name a.example.com;
    ssl_certificate     /etc/letsencrypt/live/a.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/a.example.com/privkey.pem;
}
server {
    listen 443 ssl;
    server_name b.example.com;
    ssl_certificate     /etc/letsencrypt/live/b.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/b.example.com/privkey.pem;
}
# SNI 덕분에 가능합니다 — 클라이언트가 핸드셰이크에서 도메인을 알려 주기 때문입니다
SNI 를 지원하지 않는 아주 오래된 클라이언트는 첫 번째 인증서를 받게 되어 이름 불일치 오류가 납니다. Windows XP·Android 2.x 수준이므로 현실적으로는 고려하지 않아도 됩니다.
SECTION 08

체인 · 중간 인증서

"PC 에서는 되는데 모바일에서만 오류" — 이 증상의 원인은 거의 항상 이것입니다.

✗ 중간 인증서 누락
ssl_certificate /etc/letsencrypt/live/x/cert.pem;

# 서버가 보내는 것: [내 인증서] 만
# 브라우저: "이걸 서명한 중간 CA 를 모르겠는데?"
#
# PC 브라우저는 캐시나 AIA fetch 로
# 중간 인증서를 알아서 구해 오는 경우가 있어
# 문제를 못 느낍니다 (그래서 발견이 늦습니다)
✓ fullchain 사용
ssl_certificate /etc/letsencrypt/live/x/fullchain.pem;

# 서버가 보내는 것:
#   [내 인증서] + [중간 CA 인증서]
#
# 모든 클라이언트가 체인을 완성할 수 있습니다
# 체인이 제대로 나가는지 확인
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | grep -A 5 'Certificate chain'
Certificate chain 0 s:CN = example.com i:C = US, O = Let's Encrypt, CN = R11 ← 내 인증서 1 s:C = US, O = Let's Encrypt, CN = R11 i:C = US, O = Internet Security Research Group, CN = ISRG Root X1 ← 중간 인증서 ✓
0 만 있고 1 이 없으면 체인이 빠진 것입니다. cert.pem 대신 fullchain.pem 을 지정하세요.
Apache 2.4.8 미만에서는 SSLCertificateChainFile 로 따로 지정했지만, 2.4.8 이상은 SSLCertificateFile 에 fullchain 을 넣으면 됩니다.

순서도 중요합니다

fullchain.pem 의 올바른 순서

-----BEGIN CERTIFICATE-----   ← ① 서버 인증서 (내 도메인)
...
-----END CERTIFICATE-----
-----BEGIN CERTIFICATE-----   ← ② 중간 CA
...
-----END CERTIFICATE-----

★ 순서가 뒤바뀌면 일부 클라이언트가 거부합니다
★ 루트 CA 는 넣지 않아도 됩니다 (클라이언트가 이미 갖고 있음)
  넣어도 동작하지만 전송량만 늘어납니다
진단 도구
· SSL Labs(ssllabs.com/ssltest) — 체인 문제를 "Chain issues: Incomplete" 로 명확히 알려 줍니다
· openssl s_client -showcerts — 실제로 나가는 인증서 전부를 봅니다
· 모바일에서 직접 테스트 — PC 브라우저는 문제를 감춰 줄 수 있습니다
"내 브라우저에서는 되는데" 라는 HTTPS 문제의 단골 원인입니다.
SECTION 09

TLS 버전 · 암호 스위트

보안 점검에서 등급이 낮게 나오는 이유는 대부분 여기입니다.

버전상태
SSL 2.0 · 3.0폐기 — 절대 쓰면 안 됩니다
TLS 1.0 · 1.12021년 주요 브라우저에서 지원 종료 — 비활성화하세요
TLS 1.2현재 표준 — 호환성을 위해 켜 둡니다
TLS 1.3★ 최신 · 더 빠르고 안전 — 반드시 켜세요
# Nginx — 권장 설정 (현대적 호환성)
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;         # TLS1.3 에서는 클라이언트 우선이 권장됩니다
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

# 세션 재개 (재접속 지연 감소)
ssl_session_cache   shared:SSL:10m;
ssl_session_timeout 1d;
ssl_session_tickets off;               # 티켓 키 관리가 어렵다면 끄는 편이 안전

# OCSP 스테이플링 (인증서 폐기 확인을 서버가 대신)
ssl_stapling on;
ssl_stapling_verify on;
ssl_trusted_certificate /etc/letsencrypt/live/example.com/chain.pem;
resolver 1.1.1.1 8.8.8.8 valid=300s;
resolver_timeout 5s;
암호 스위트를 직접 고르지 마세요. Mozilla SSL Configuration Generator(ssl-config.mozilla.org)에서 서버 종류와 버전을 고르면 검증된 설정을 만들어 줍니다.
· Modern — TLS 1.3 만. 최신 클라이언트만 지원
· Intermediate — 대부분의 서비스에 권장
· Old — 아주 오래된 클라이언트 지원 (보안 약화)

알아 둘 개념

  • 전방 비밀성 (Forward Secrecy) — 개인키가 나중에 유출돼도 과거 트래픽을 복호화할 수 없게 하는 성질. ECDHE 로 시작하는 암호가 이를 제공합니다
  • AEAD — 암호화와 무결성 검증을 함께 하는 방식(GCM·CHACHA20-POLY1305). TLS 1.3 은 AEAD 만 씁니다
  • ECDSA vs RSA — ECDSA 인증서가 더 작고 빠릅니다. 둘 다 발급해 클라이언트에 맞게 제공할 수도 있습니다
# 우리 서버가 어떤 프로토콜·암호를 지원하는지 점검
nmap --script ssl-enum-ciphers -p 443 example.com

# 특정 버전만 시도해 보기
openssl s_client -connect example.com:443 -tls1_2 < /dev/null
openssl s_client -connect example.com:443 -tls1_1 < /dev/null   # 실패해야 정상
SECTION 10

HSTS · 혼합 콘텐츠

HTTPS 를 켜는 것만으로는 부족합니다. HTTP 로 새는 경로를 막아야 합니다.

HSTS — 브라우저에게 HTTPS 를 강제

# Nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

# preload 목록에 등록하려면 (아래 경고를 반드시 읽으세요)
# add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
HSTS 가 막는 것 — 사용자가 example.com 을 입력하면 브라우저는 먼저 HTTP 로 접속했다가 리다이렉트를 받습니다. 그 첫 요청이 가로채기(SSL 스트리핑)에 노출됩니다. HSTS 헤더를 한 번 받으면 브라우저는 그다음부터 HTTP 를 아예 시도하지 않습니다.
preload 는 신중하게. 브라우저에 내장되어 배포되므로 되돌리는 데 수개월이 걸립니다.
· 모든 서브도메인이 HTTPS 를 지원하는지 확인하고
· max-age 를 짧게(300초) 시작해 점진적으로 늘린 뒤
· 확신이 섰을 때만 preload 를 신청하세요
내부용 서브도메인 하나가 HTTP 라면 그것도 접속이 막힙니다.

혼합 콘텐츠 (Mixed Content)

HTTPS 페이지 안에서 HTTP 리소스를 불러오면 브라우저가 차단하거나 경고합니다. 이미지·스크립트·CSS·폰트가 모두 대상입니다. 

<!-- ✗ 차단됨 -->
<script src="http://cdn.example.com/lib.js"></script>

<!-- ✓ 명시적 HTTPS -->
<script src="https://cdn.example.com/lib.js"></script>

<!-- ✓ 프로토콜 상대 경로 (현재는 그냥 https 를 쓰는 편이 낫습니다) -->
<script src="//cdn.example.com/lib.js"></script>
# 임시 대응 — 브라우저에게 HTTP 요청을 HTTPS 로 바꿔 달라고 요청
add_header Content-Security-Policy "upgrade-insecure-requests" always;
# 근본 해결은 코드에서 URL 을 고치는 것입니다
혼합 콘텐츠를 찾는 법 — 브라우저 개발자 도구 콘솔에 경고가 출력됩니다. 또는 CSP 의 report-uri 를 설정해 실제 사용자 환경에서 수집할 수도 있습니다.
앱이 HTTPS 를 인식하지 못해 HTTP URL 을 생성하는 경우도 흔합니다 — X-Forwarded-Proto 설정을 확인하세요(🟩 Nginx n08).
HTTPS 적용은 서버 설정 절반, 페이지 안의 주소 절반입니다.
SECTION 11

mTLS 상호 인증

서버뿐 아니라 클라이언트도 인증서로 신원을 증명합니다.

# Nginx — 클라이언트 인증서 요구
server {
    listen 443 ssl;
    server_name api-internal.example.com;

    ssl_certificate     /etc/ssl/server.crt;
    ssl_certificate_key /etc/ssl/server.key;

    # 클라이언트 인증서 검증
    ssl_client_certificate /etc/ssl/ca.crt;      # 클라이언트를 서명한 CA
    ssl_verify_client on;                        # on · optional · off
    ssl_verify_depth 2;

    location / {
        # 검증 결과를 앱에 전달
        proxy_set_header X-SSL-Client-Verify $ssl_client_verify;
        proxy_set_header X-SSL-Client-DN     $ssl_client_s_dn;
        proxy_set_header X-SSL-Client-Serial $ssl_client_serial;

        proxy_pass http://backend;
    }
}
# 사설 CA 와 클라이언트 인증서 만들기
# 1) CA 키·인증서
openssl req -x509 -newkey rsa:4096 -days 3650 -nodes \
  -keyout ca.key -out ca.crt -subj "/CN=Internal CA"

# 2) 클라이언트 키·CSR
openssl req -newkey rsa:2048 -nodes \
  -keyout client.key -out client.csr -subj "/CN=service-a"

# 3) CA 로 서명
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -out client.crt -days 365

# 4) 사용
curl --cert client.crt --key client.key https://api-internal.example.com/

· 클라이언트가 100개면 인증서도 100개 — 발급·배포·갱신·폐기 체계가 필요합니다
· 만료 관리가 서버 인증서보다 훨씬 어렵습니다
· 폐기 목록(CRL·OCSP) 운영도 필요합니다
일반 서비스라면 API 키·OAuth 토큰이 운영 부담이 훨씬 적습니다. 쿠버네티스 환경이라면 서비스 메시(Istio·Linkerd) 가 이를 자동화해 줍니다.

mTLS 의 실질적 강점은 "네트워크에 붙는 것만으로는 아무것도 못 한다" 는 점입니다. 사내망이 뚫려도 유효한 클라이언트 인증서와 개인 키가 없으면 API 를 못 부릅니다. IP 허용 목록은 같은 대역에 발을 들이면 무력화되지만, mTLS 는 그렇지 않습니다. 반대로 키가 유출되면 IP 제한보다 나을 것이 없어지므로, 키를 어디에 어떻게 두는지가 이 방식의 전부입니다. 
# 경로별로 다르게 — API 만 mTLS, 문서는 공개
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/server.crt;
    ssl_certificate_key /etc/ssl/server.key;

    ssl_client_certificate /etc/ssl/ca.crt;
    ssl_verify_client optional;              # ★ 요구하되 거부하지는 않음

    # 공개 문서 — 인증서 없어도 통과
    location /docs/ {
        root /var/www;
    }

    # API — 검증 성공한 경우만
    location /v1/ {
        if ($ssl_client_verify != SUCCESS) { return 403; }

        proxy_set_header X-Client-CN     $ssl_client_s_dn_cn;
        proxy_set_header X-Client-Serial $ssl_client_serial;
        proxy_set_header X-Client-Verify $ssl_client_verify;
        proxy_pass http://backend;
    }
}

인증서 수명을 짧게 잡고 자동 갱신을 먼저 만드세요. 1년짜리 인증서 100장을 수동으로 관리하겠다는 계획은 반드시 실패합니다 — 갱신을 잊은 날 서비스가 멈추고, 그것도 대개 연휴에 일어납니다.
클라이언트가 몇 개 안 되고 갱신 자동화를 만들 여력이 없다면, mTLS 대신 API 키 + IP 제한 + 짧은 수명 토큰이 현실적으로 더 안전합니다. 운영할 수 없는 보안 장치는 보안이 아닙니다.
쿠버네티스라면 직접 만들지 마세요. cert-manager 가 발급·갱신·배포를 자동화하고, Istio·Linkerd 는 파드 간 통신에 mTLS 를 코드 변경 없이 자동 적용합니다 (사이드카가 대신 처리합니다). 직접 CA 를 운영하는 것은 그 자동화가 안 되는 환경에서만 선택하세요.
"비밀번호 없이 기기만으로 막는" 방법입니다 — 대신 인증서 운영이 따라옵니다.
SECTION 12

만료 감시

인증서 만료로 서비스가 멈추는 사고는 대기업에서도 매년 일어납니다. 감시가 유일한 예방책입니다. 

# 남은 일수 확인 (한 줄)
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -enddate

# 파일에서 확인
openssl x509 -in /etc/letsencrypt/live/example.com/fullchain.pem -noout -enddate

# 30일 이내면 실패로 처리 (모니터링·CI 에 붙이기 좋습니다)
openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -checkend $((30*86400)) \
  && echo "OK: 30일 이상 남음" || echo "WARNING: 30일 이내 만료"
#!/usr/bin/env bash
# 여러 도메인을 한 번에 점검하는 스크립트
DOMAINS=(example.com api.example.com admin.example.com)
WARN_DAYS=21

for d in "${DOMAINS[@]}"; do
  end=$(echo | openssl s_client -connect "$d:443" -servername "$d" 2>/dev/null \
        | openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2)
  if [ -z "$end" ]; then
    echo "ERROR  $d : 인증서를 가져오지 못했습니다"
    continue
  fi
  left=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
  if   [ "$left" -lt 0  ];          then echo "EXPIRED $d : ${left}일"
  elif [ "$left" -lt $WARN_DAYS ];  then echo "WARN    $d : ${left}일 남음"
  else                                   echo "OK      $d : ${left}일 남음"
  fi
done
