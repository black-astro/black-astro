SECTION 01

백엔드 서버란 — 웹서버 뒤의 세계

웹서버가 주문을 받는 홀이라면, 백엔드는 요리를 만드는 주방입니다.

이 가이드의 앞 탭들은 웹서버(Nginx·Apache) — 요청을 받아 정적 파일을 주거나 뒤로 넘기는 프로그램을 다뤘습니다. 그 "뒤"가 백엔드 서버입니다. Spring Boot·Django·Express·FastAPI 로 만든 앱이 전부 백엔드 서버이고, 언어가 무엇이든 내부 구조는 놀랄 만큼 비슷합니다.

웹서버는 어떻게 전달하나를, 백엔드는 무엇을 할 것인가를 담당합니다.

언어별 이름 대조 — 같은 것을 다르게 부릅니다

컨트롤러@RestControllerViewRouter · Handler

요청 처리 모델이 성능 특성을 정합니다. 스레드풀 방식(Java)은 요청 하나가 스레드 하나를 점유합니다 — DB 응답을 기다리는 동안에도. 이벤트 루프(Node)는 기다림 없이 다음 요청을 받지만 CPU 작업 하나가 전체를 멈춥니다. 이 차이가 ⚡ 성능 탭과 🧬 전문가 탭(z02·z03)의 주제입니다.

백엔드 서버의 세 갈래 — 웹 서버 · 게임 서버 · 처리 엔진 서버

“백엔드”라고 다 같은 구조가 아닙니다. 시간을 다루는 방식이 다르면 설계가 통째로 달라집니다 — 웹 서버는 요청이 올 때만 일하고, 게임 서버는 요청이 없어도 시간이 흐르며, 엔진 서버는 큐에서 꺼낸 작업을 계속 갈아 냅니다.

틱 예산을 넘기면 한 명이 아니라 그 방 전원이 느려집니다 — 게임 서버 성능 문제의 단위는 요청이 아니라 방입니다.

게임 · 실시간 서버 설계의 다섯 기둥

  • ① 프로토콜 — 위치처럼 최신값만 중요한 데이터는 UDP(잃어도 다음 틱이 덮음), 인벤토리·결제처럼 빠지면 안 되는 것은 TCP/신뢰 채널. 웹 기반이면 WebSocket + 델타 압축.
  • ② 권위(authority)는 서버에 — 클라이언트가 보낸 “나 여기로 이동”은 요청이지 사실이 아닙니다. 서버가 판정하고 클라이언트는 예측·보간으로 숨깁니다(치트 방어의 뿌리).
  • ③ 관심 영역(AOI) — 1,000명 방에서 전원에게 전원 상태를 보내면 패킷이 n² 으로 폭발합니다. 보이는 범위만 구독시키는 격자·그리드가 필수.
  • ④ 상태 저장의 두 층 — 매 틱 바뀌는 것은 메모리에만, 잃으면 안 되는 것(레벨·아이템)만 주기 스냅숏 + 이벤트 로그로 DB에. 매 틱 DB 를 치는 순간 게임 서버는 죽습니다.
  • ⑤ 재접속 프로토콜 — 모바일은 반드시 끊깁니다. “세션 토큰으로 방 찾기 → 스냅숏 재전송 → 이후 델타”가 처음부터 설계에 있어야 합니다.

전체 그림 — 게임도 결국 MSA 로 갑니다

   ▼

핵심 통찰 — 게임 백엔드의 대부분(로그인·상점·랭킹·우편)은 그냥 웹 서버이고, 상태ful 틱 루프가 필요한 건 전투 그 자체뿐입니다. “어디까지가 웹이고 어디부터가 실시간인가”를 먼저 긋는 것이 게임 서버 설계의 첫 단추입니다. 실시간 채팅·알림 정도면 게임 서버가 아니라 WebSocket + Redis Pub/Sub(📈 대규모 탭)로 충분합니다.
SECTION 02

모놀리스 — 잘 만든 한 덩어리

MSA 를 배우기 전에 분명히 할 것 — 모놀리스는 열등한 구조가 아닙니다.

모놀리스는 모든 기능이 한 프로세스 안에 있는 구조입니다. 배포 파일이 하나, DB가 하나, 함수 호출로 모든 기능에 닿습니다. 쿠팡도 배민도 토스도 모놀리스로 시작했습니다. 문제는 덩어리 자체가 아니라 내부 경계 없이 뒤엉키는 것입니다.

같은 한 덩어리라도 경계가 있느냐가 미래를 가릅니다. 경계 없는 코드는 쪼갤 수도 없습니다.

모놀리스가 정답인 경우

상황이유
팀이 10명 미만MSA 는 서비스마다 배포·모니터링·온콜이 붙습니다. 사람이 안 됩니다
도메인 경계가 아직 불확실잘못 쪼개면 서비스 둘을 항상 같이 고치게 됩니다 — 최악의 결과
트래픽이 한 대로 감당됨모놀리스도 여러 대 복제(⚖️ 로드밸런싱)로 충분히 확장됩니다
빠른 실험이 중요기능 하나에 서비스 셋을 고치는 구조는 실험 속도를 죽입니다
면접 포인트 — "MSA 경험 있나요?"의 좋은 답은 "무조건 MSA"가 아니라 "모듈러 모놀리스로 경계를 만들고, 이 조건이 되면 쪼갠다"는 판단 기준을 말하는 것입니다. 그 조건이 m03·m11 입니다.
SECTION 03

MSA — 무엇을 기준으로 쪼개나

마이크로서비스는 따로 배포할 수 있는 작은 서비스들의 협력입니다. 쪼개는 기준이 전부입니다.

MSA 의 핵심 규칙 — 서비스마다 자기 DB, 남의 데이터는 API 로 부탁해서 얻습니다.

무엇을 얻고 무엇을 지불하나

얻는 것
① 독립 배포 — 주문 팀은 하루 20번,
   회원 팀은 주 1번. 서로 안 기다린다
② 독립 확장 — 상품 조회만 10대로
③ 장애 격리 — 추천이 죽어도 주문은 산다
④ 기술 자유 — 서비스마다 다른 언어·DB 가능
⑤ 팀 자율 — 작은 팀이 끝까지 책임진다

⑤ 디버깅 — 로그가 여러 서버에 흩어진다 (m10)

쪼개는 기준 — 바운디드 컨텍스트

DDD(도메인 주도 설계)의 바운디드 컨텍스트가 실무 표준 기준입니다. 같은 "상품"이라도 주문 맥락(가격·재고)과 전시 맥락(이미지·설명)은 다른 데이터입니다. 말이 달라지는 경계, 함께 바뀌는 것들의 묶음이 서비스 경계입니다. 실용적 신호: ① 이 기능만 배포 주기가 다르다 ② 이 기능만 트래픽 패턴이 다르다 ③ 이 기능만 다른 팀이 만진다 — 셋 중 둘이면 쪼갤 후보입니다.

최악의 결과 — 분산 모놀리스. 쪼갰는데 서비스 A 를 고칠 때마다 B 도 같이 배포해야 한다면, 모놀리스의 단점(결합)과 MSA 의 단점(네트워크·운영)을 둘 다 가진 것입니다. 원인은 대부분 ① 잘못된 경계 ② DB 공유 ③ 동기 호출 사슬(m06)입니다.
SECTION 04

API 게이트웨이 · BFF

서비스가 여럿이 되는 순간, 클라이언트가 어디로 요청해야 하는지부터 문제가 됩니다.

게이트웨이가 없으면 모든 서비스가 인증·CORS·리밋 코드를 복붙하게 됩니다 — 그게 신호입니다.

도구 선택

도구특징 · 쓰는 곳
Nginx이미 알고 있는 것으로 시작 — 라우팅·리밋·TLS 는 충분합니다
Spring Cloud Gateway자바 진영 표준. 필터로 인증·로깅을 코드로 제어
Kong · APISIX플러그인 생태계(인증·리밋·변환). 언어 무관 전용 게이트웨이
클라우드 관리형AWS API Gateway · ALB — 운영을 맡기고 기능만 씁니다

BFF — 클라이언트별 전용 백엔드

앱은 화면 하나에 필요한 것만 작게, 웹 관리자는 한 번에 많이 — 클라이언트마다 원하는 모양이 다릅니다. 하나의 범용 API 로 모두 만족시키려다 비대해지는 대신, 클라이언트 종류마다 전용 집계 서버(BFF, Backend For Frontend)를 둡니다. BFF 는 여러 서비스를 호출해 그 화면에 맞는 모양으로 합쳐서 돌려줍니다. 프런트 팀이 직접 소유하는 경우가 많습니다.

게이트웨이에 비즈니스 로직을 넣지 마세요. "주문 금액이 5만 원 이상이면…" 같은 규칙이 게이트웨이에 들어가는 순간, 게이트웨이가 모두가 함께 배포를 기다리는 병목이 됩니다. 게이트웨이는 인증·라우팅·리밋 같은 공통 관심사만 다룹니다.
SECTION 05

서비스 디스커버리 · 중앙 설정

서비스가 늘고 줄면 IP 가 계속 바뀝니다. 주소를 코드에 적는 순간 끝입니다.

쿠버네티스에서는 이 전부가 Service 라는 내장 기능입니다 — http://member-service 로 부르면 끝.

중앙 설정 · 시크릿

문제해법
설정이 서비스 20개에 흩어짐중앙 설정 서버 — Spring Cloud Config · Consul KV · k8s ConfigMap
DB 비밀번호가 코드·이미지에 박힘시크릿 저장소 — Vault · AWS Secrets Manager · k8s Secret. 코드에는 절대 금지
설정 하나 바꾸는데 전체 재배포설정 서버 + 갱신 신호(actuator refresh · 재시작 롤링)
환경(dev·stage·prod)마다 값이 다름같은 이미지 + 환경별 설정 주입 — 12-factor 원칙
순서를 기억하세요 — 코드가 아니라 환경에서. 같은 빌드 산출물(이미지)이 dev 와 prod 에서 다른 설정을 주입받아 도는 것이 정석입니다. "prod 용으로 다시 빌드"하는 순간, 테스트한 것과 배포한 것이 달라집니다.
SECTION 06

동기 통신 — REST · gRPC

서비스 간 호출의 기본형. 단, 사슬이 길어질수록 느려지고 약해집니다.

동기 호출은 가장 느린 서비스가 전체 속도가 되고, 가장 약한 서비스가 전체 가용성이 됩니다.

REST vs gRPC

REST + JSONgRPC
형식텍스트(JSON) — 사람이 읽음바이너리(Protobuf) — 작고 빠름
계약OpenAPI 문서 (선택).proto 파일이 강제 계약 — 코드 생성
전송HTTP/1.1 (보통)HTTP/2 — 멀티플렉싱·스트리밍
쓰는 곳외부 공개 API · 브라우저내부 서비스 간 · 성능 민감 구간
// member.proto — 계약이 곧 문서이자 코드입니다
service MemberService {
  rpc GetMember (GetMemberRequest) returns (Member);
}
message GetMemberRequest { int64 id = 1; }
message Member { int64 id = 1; string name = 2; string grade = 3; }
// → protoc 가 Java·Python·Go 클라이언트/서버 코드를 생성
실무 구도 — 외부는 REST, 내부는 gRPC 가 흔한 조합입니다. 다만 내부도 REST 로 통일해 단순함을 택하는 회사가 많습니다. 성능보다 계약 관리(스키마 버전, 하위 호환)가 진짜 승부처입니다 — 필드 삭제·타입 변경은 추가만 하는 변경으로 바꿔 배포 순서 문제를 피하세요.
SECTION 07

비동기 통신 — 이벤트

"주문 완료를 알려만 주고 내 갈 길 간다" — 결합을 끊는 가장 강한 도구입니다.

핵심 질문 — "이 결과를 지금 알아야 응답할 수 있나?" 아니라면 이벤트가 정답입니다.

결제 승인 결과가 있어야 주문 응답 가능동기 — 응답에 결과가 필요하면 어쩔 수 없습니다
주문 완료 후 알림·적립·통계이벤트 — 주문 응답과 무관합니다
재고 차감 (틀리면 안 됨)동기 + 실패 시 거절, 또는 예약-확정 사가(m08)
다른 시스템에 데이터 복사·동기화이벤트 — CDC·아웃박스 (k07)
이벤트의 대가 — 최종 일관성. 이벤트 처리 전까지 잠깐 데이터가 어긋난 상태가 존재합니다 (주문은 됐는데 적립금이 아직). 화면에 "적립 예정"처럼 어긋남을 설계에 포함하세요. 또한 소비자는 같은 이벤트를 두 번 받아도 안전해야 합니다(멱등 처리 — k06).
SECTION 08

데이터 분리 — 사가 패턴

DB 가 갈라지면 ROLLBACK 이 없습니다. 되돌리는 것도 직접 설계해야 합니다.

모놀리스에서는 주문 저장·재고 차감·결제를 한 트랜잭션으로 묶고 실패하면 통째로 롤백했습니다. MSA 에서는 세 작업이 서로 다른 서비스의 서로 다른 DB에서 일어납니다. 분산 트랜잭션(2PC)은 느리고 조정자가 죽으면 전체가 멈춰 실무에서 안 씁니다. 대신 사가(Saga) — 로컬 트랜잭션의 연쇄 + 실패 시 보상 트랜잭션으로 되돌립니다.

사가의 본질 — 롤백을 공짜로 받지 못하니, 되돌리는 작업을 직접 만든다.

두 가지 진행 방식

코레오그래피 — 이벤트로 릴레이
주문 → [주문생성됨] → 재고가 구독해 차감
     → [재고차감됨] → 결제가 구독해 승인
     → [결제실패됨] → 각자 보상 실행

장점  중앙 조정자가 없다 — 결합 최소
단점  전체 흐름이 코드 어디에도 없다
      → 서비스 5개 넘으면 추적 불가
적합  단계 2~3개의 단순한 흐름
오케스트레이션 — 지휘자가 지시
주문 사가 오케스트레이터가
  ① 재고에 차감 명령 → 응답
  ② 결제에 승인 명령 → 실패!
  ③ 재고에 복원 명령 (보상)

장점  흐름이 한 곳에 — 상태 추적 쉬움
단점  오케스트레이터가 비대해질 수 있음
적합  단계 많고 보상 복잡한 핵심 흐름
도구  Temporal · AWS Step Functions
실무 감각 — 주문·결제처럼 돈이 걸린 핵심 사가는 오케스트레이션으로 상태를 명시적으로 관리하고, 알림·통계처럼 부수 효과는 코레오그래피로 흘리는 조합이 흔합니다. 그리고 "이벤트 발행과 DB 커밋을 어떻게 원자적으로 하나"가 남는데 — 그 답이 아웃박스 패턴(📨 Kafka 탭 k07)입니다.
SECTION 09

장애 격리 — 서킷브레이커

MSA 최대 리스크는 연쇄 장애입니다. 두꺼비집처럼 선을 끊어서 막습니다.

서킷의 목적은 둘 — 내 스레드를 지키고(즉시 실패), 상대에게 회복할 틈을 줍니다.

타임아웃 · 재시도 — 함께 써야 완성

도구규칙
타임아웃모든 원격 호출에 예외 없이. 연결 1s · 응답은 p99 기준 + 여유. "무한 대기"가 스레드 고갈의 주범입니다
재시도멱등한 호출에만(조회 O · 결제 X). 지수 백오프 + 지터. 최대 2~3회
재시도 폭풍 주의느려진 서비스에 재시도가 몰리면 부하가 배로 — 서킷과 반드시 함께
벌크헤드호출 대상별로 스레드풀·커넥션풀 분리 — 한 대상이 느려도 다른 호출은 산다
# Resilience4j 설정 감각 (Spring Boot application.yml)
resilience4j:
  circuitbreaker:
    instances:
      memberService:
        slidingWindowSize: 20            # 최근 20번 기준
        failureRateThreshold: 50         # 실패 50% 넘으면 OPEN
        waitDurationInOpenState: 30s     # 30초 쉬고 HALF-OPEN
        permittedNumberOfCallsInHalfOpenState: 3
  timelimiter:
    instances:
      memberService:
        timeoutDuration: 2s              # 응답 타임아웃
폴백이 없는 서킷은 반쪽입니다. 회원 등급 조회가 열렸을 때 — 주문을 전부 거절할 건가요, "기본 등급으로 진행"할 건가요? 장애 시 무엇을 포기하고 무엇을 지킬지는 기술이 아니라 비즈니스 결정입니다. 미리 정해 두지 않으면 새벽 장애 때 개발자가 즉석에서 정하게 됩니다.
SECTION 10

관측 가능성 — 로그 · 메트릭 · 트레이싱

"주문이 느려요" — 서비스 10개 중 어디가 느린지 5분 안에 찾을 수 있어야 합니다.

트레이싱이 없으면 이 그림을 서비스 10개의 로그를 이어 붙여 손으로 그려야 합니다 — 새벽에.

세 기둥 — 각자 답하는 질문이 다릅니다

기둥답하는 질문도구
메트릭"지금 얼마나 나쁜가?" — RPS · 에러율 · p99Prometheus + Grafana
로그"그때 정확히 무슨 일이 있었나?"Loki · ELK — 중앙 수집 필수
트레이싱"어느 구간이 느렸나?"OpenTelemetry + Tempo·Jaeger
전제는 상관관계 ID 입니다. 게이트웨이에서 요청마다 traceId 를 만들어 모든 서비스가 로그에 함께 남기고, 다음 호출에 헤더로 전달합니다(W3C traceparent 표준). OpenTelemetry 를 쓰면 전파·수집이 자동입니다 — 직접 만들지 마세요. 로그는 JSON 구조화로 남겨야 검색이 됩니다.
알람은 "골든 시그널" 넷이면 시작할 수 있습니다 — 지연(p99) · 트래픽(RPS) · 에러율 · 포화도(CPU·커넥션풀). "CPU 80%" 같은 원인 알람보다 "주문 API p99 가 1초를 넘었다" 같은 증상 알람이 먼저입니다. 원인은 그다음에 파고드는 것입니다. (🛡️ 보안·운영 o13)
