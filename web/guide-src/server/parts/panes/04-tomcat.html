APACHE TOMCAT 11 · 서블릿 컨테이너 · SPRING BOOT

Tomcat —
자바 앱을
실행하는 엔진

Tomcat 은 웹서버가 아니라 WAS(웹 애플리케이션 서버)입니다. 자바 서블릿·JSP 를 실행하며, 실무에서는 거의 항상 Nginx 뒤에 둡니다. Spring Boot 를 쓴다면 이미 톰캣이 앱 안에 들어 있습니다 — 그래서 톰캣을 아는 것이 곧 자바 웹 운영을 아는 것입니다.

SECTION 01

Tomcat은 무엇인가

"Nginx 가 있는데 왜 Tomcat 이 또 필요한가요?" — 역할이 다르기 때문입니다.

웹서버 (Nginx · Apache)
· 요청을 받고 응답을 보냄
· 정적 파일을 디스크에서 읽어 전달
· HTTPS · 압축 · 캐시 · 로드밸런싱
· 자바 코드는 실행하지 못함
WAS (Tomcat)
· 자바 서블릿·JSP 를 실행
· 요청마다 스레드를 배정해 코드 실행
· 세션 · 트랜잭션 · 커넥션 풀 관리
· 정적 파일도 줄 수는 있지만 비효율
브라우저
https://example.com/orders/1HTTPS 요청
▼
Nginx :443
TLS 종료 · 정적 파일 처리 · 프록시 /static/ 은 직접 응답, 나머지는 톰캣으로 넘깁니다.
▼ HTTP
Tomcat :8080
서블릿 실행 스레드 풀에서 스레드 하나를 꺼내 우리 코드(Controller)를 실행합니다.
▼ JDBC
DB
데이터 조회·저장커넥션 풀에서 커넥션을 빌려 씁니다.

서블릿 컨테이너란

자바에는 서블릿(Servlet)이라는 표준 규격이 있습니다. "HTTP 요청을 받으면 이런 형태의 객체로 전달하고, 이런 형태로 응답을 돌려준다"는 약속입니다. Tomcat 은 이 규격을 구현한 프로그램이고, Spring 은 그 위에서 도는 프레임워크입니다.

구현체특징
Tomcat가장 널리 쓰임 · Spring Boot 기본값 · 자료가 압도적
Jetty가볍고 임베디드에 적합 · 비동기 처리에 강점
Undertow논블로킹 · 낮은 메모리 · WildFly 기반
WebLogic · WebSphere · JEUS상용 WAS — 대기업·금융 기간계. 톰캣보다 많은 기능(EJB·JTA 등)
Jakarta EE 이름 변경 — 오라클이 Java EE 를 재단에 넘기면서 패키지 이름이 javax.servlet → jakarta.servlet 으로 바뀌었습니다.
· Tomcat 9 이하 — javax.*
· Tomcat 10 이상 — jakarta.*
이 때문에 WAR 를 톰캣 10 이상으로 그냥 옮기면 동작하지 않습니다. Spring Boot 3 이상은 jakarta.* 기준입니다.
톰캣을 이해하는 한 문장 — HTTP 를 자바 객체로 바꿔 주는 층입니다.
SECTION 02

설치와 디렉터리

압축을 푸는 것이 곧 설치입니다. 폴더 네 개만 알면 됩니다.

# 자바 먼저 (Tomcat 11 은 Java 17 이상)
sudo apt install -y openjdk-21-jdk
java -version

# 톰캣 내려받기
cd /opt
sudo curl -LO https://dlcdn.apache.org/tomcat/tomcat-11/v11.0.x/bin/apache-tomcat-11.0.x.tar.gz
sudo tar xzf apache-tomcat-11.0.x.tar.gz
sudo mv apache-tomcat-11.0.x tomcat

# 전용 계정 (★ root 로 실행하지 마세요)
sudo useradd -r -s /bin/false tomcat
sudo chown -R tomcat:tomcat /opt/tomcat

# 실행
sudo -u tomcat /opt/tomcat/bin/startup.sh
curl -I http://localhost:8080
sudo -u tomcat /opt/tomcat/bin/shutdown.sh
폴더내용
bin/실행 스크립트 — startup.sh · shutdown.sh · catalina.sh
conf/설정 — server.xml · context.xml · web.xml · tomcat-users.xml
webapps/애플리케이션 — WAR 를 여기 넣으면 자동 배포
logs/로그 — catalina.out · localhost_access_log
lib/공용 라이브러리 (JDBC 드라이버 등)
temp/ · work/임시 파일 · JSP 컴파일 결과 (문제 시 지워도 됩니다)

systemd 서비스로 등록

# /etc/systemd/system/tomcat.service
[Unit]
Description=Apache Tomcat 11
After=network.target

[Service]
Type=forking
User=tomcat
Group=tomcat

Environment="JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64"
Environment="CATALINA_HOME=/opt/tomcat"
Environment="CATALINA_BASE=/opt/tomcat"
Environment="CATALINA_PID=/opt/tomcat/temp/tomcat.pid"
Environment="CATALINA_OPTS=-Xms512m -Xmx1024m -XX:+UseG1GC"

ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh

Restart=on-failure
RestartSec=10
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now tomcat
sudo journalctl -u tomcat -f
CATALINA_HOME 과 CATALINA_BASE — 한 톰캣 설치본(HOME)으로 여러 인스턴스(BASE)를 돌릴 수 있습니다. BASE 에 conf·webapps·logs 만 두면 업그레이드 시 HOME 만 교체하면 됩니다. 한 서버에 여러 앱을 올리는 환경에서 유용합니다.

server.xml 해부

톰캣의 심장입니다. 구조만 알면 어렵지 않습니다.

<Server port="8005" shutdown="SHUTDOWN">          <!-- 종료 명령을 받는 포트 -->

  <Service name="Catalina">

    <!-- 요청을 받는 창구 -->
    <Connector port="8080"
               protocol="org.apache.coyote.http11.Http11NioProtocol"
               connectionTimeout="20000"
               maxThreads="200"
               minSpareThreads="10"
               acceptCount="100"
               maxConnections="8192"
               URIEncoding="UTF-8"
               compression="off"
               redirectPort="8443" />

    <Engine name="Catalina" defaultHost="localhost">

      <Host name="localhost" appBase="webapps"
            unpackWARs="true" autoDeploy="true">

        <!-- 접근 로그 -->
        <Valve className="org.apache.catalina.valves.AccessLogValve"
               directory="logs" prefix="localhost_access_log"
               suffix=".txt"
               pattern="%h %l %u %t &quot;%r&quot; %s %b %D" />

        <!-- 프록시 뒤에서 실제 IP 복원 -->
        <Valve className="org.apache.catalina.valves.RemoteIpValve"
               remoteIpHeader="X-Forwarded-For"
               protocolHeader="X-Forwarded-Proto"
               internalProxies="127\.0\.0\.1|10\.\d+\.\d+\.\d+" />

      </Host>
    </Engine>
  </Service>
</Server>
요소역할
Server톰캣 전체. port="8005" 는 종료 명령용
Service커넥터들과 엔진을 묶는 단위
Connector요청을 받는 창구 — 포트·프로토콜·스레드 (t04)
Engine요청을 처리할 호스트를 고름
Host가상 호스트 — appBase 가 앱이 놓이는 폴더
Context앱 하나 — 보통 자동 인식되므로 직접 쓸 일은 적습니다
Valve요청 처리 중간에 끼어드는 필터 (로그·IP 복원·접근 제어)
종료 포트(8005)를 반드시 막으세요. 이 포트에 SHUTDOWN 문자열을 보내면 누구나 톰캣을 종료시킬 수 있습니다.
· port="-1" 로 아예 비활성화하거나
· shutdown 문자열을 추측 불가능한 값으로 바꾸고
· 방화벽에서 외부 접근을 차단하세요
SECTION 04

Connector — HTTP · AJP

동시 처리 능력이 여기서 결정됩니다.

속성의미기본값
maxThreads동시에 처리할 최대 요청 수200
minSpareThreads미리 만들어 두는 스레드10
acceptCount스레드가 다 찼을 때 대기열 길이 — 넘치면 연결 거부100
maxConnections동시에 유지할 연결 수 (NIO 기준)8192
connectionTimeout연결 후 요청이 오기까지 대기 (ms)60000
keepAliveTimeout유휴 연결 유지 시간connectionTimeout 과 동일
maxHttpHeaderSize헤더 최대 크기 — 쿠키가 크면 늘려야 합니다8192
URIEncodingURL 인코딩UTF-8 (8.0+)

프로토콜 구현체

구현설명
NIO (Http11NioProtocol)기본값. 논블로킹 IO — 대부분 이것을 씁니다
NIO2비동기 IO. 특정 워크로드에서 이점이 있으나 차이가 크지 않습니다
APR/nativeOpenSSL 기반 네이티브. 10.1 에서 폐기 예고 → 11 에서 제거됐습니다
AJPApache 전용 이진 프로토콜 — 보안 이슈로 기본 비활성화
 
<!-- 프록시 뒤에 있을 때의 권장 설정 -->
<Connector port="8080"
           protocol="org.apache.coyote.http11.Http11NioProtocol"
           address="127.0.0.1"                <!-- ★ 외부에서 직접 접근 차단 -->
           maxThreads="200"
           acceptCount="200"
           connectionTimeout="20000"
           keepAliveTimeout="20000"
           maxHttpHeaderSize="16384"
           URIEncoding="UTF-8"
           compression="off"                   <!-- 압축은 Nginx 가 담당 -->
           enableLookups="false"               <!-- ★ DNS 역조회 끄기 (성능) -->
           server="server"                     <!-- 서버 정보 숨김 -->
           proxyName="example.com"             <!-- 앞단 도메인 -->
           proxyPort="443"
           scheme="https"
           secure="true" />
address="127.0.0.1" 을 반드시 설정하세요. 기본값은 모든 인터페이스에 바인드되어 누구나 서버IP:8080 으로 프록시를 우회해 접속할 수 있습니다. Nginx 의 보안 설정·rate limit·접근 제어가 전부 무력화됩니다.
enableLookups="false" 는 꼭 확인하세요. true 면 request.getRemoteHost() 호출 시 DNS 역조회를 수행해 요청당 수십~수백 ms 가 추가될 수 있습니다. 기본값은 false 이지만 옛 설정에서 true 인 경우가 있습니다.
튜닝의 첫 질문은 "어느 관문이 가장 좁은가" 입니다 — 그 밖의 숫자를 만지는 것은 대부분 헛수고입니다.

프록시 뒤에 둘 때 꼭 맞춰야 하는 값

설정안 맞추면 생기는 일
address="127.0.0.1"8080 포트가 인터넷에 노출 — 프록시의 보안 설정이 전부 우회됩니다
keepAliveTimeoutNginx 값보다 짧으면 간헐적 502 — 재사용하려는 순간 톰캣이 끊습니다
proxyName·proxyPort·scheme앱이 만든 리다이렉트 URL 이 http://127.0.0.1:8080 으로 나갑니다
RemoteIpValve접근 로그와 앱의 IP 가 전부 프록시 주소로 찍힙니다
maxHttpHeaderSize쿠키·JWT 가 크면 431 Request Header Fields Too Large
compression="off"Nginx 와 이중 압축 — CPU 만 쓰고 이득이 없습니다
<!-- server.xml 의 <Host> 안 — 실제 클라이언트 IP 를 복원합니다 -->
<Valve className="org.apache.catalina.valves.RemoteIpValve"
       remoteIpHeader="X-Forwarded-For"
       protocolHeader="X-Forwarded-Proto"
       internalProxies="127\.0\.0\.1|10\.\d+\.\d+\.\d+" />
<!-- ★ internalProxies 를 반드시 지정하세요.
     안 하면 클라이언트가 X-Forwarded-For 를 위조해
     IP 기반 접근 제어를 헤더 한 줄로 우회할 수 있습니다. -->
# Spring Boot 내장 톰캣이면 설정 파일 한 곳에서 끝납니다
server.address=127.0.0.1
server.port=8080
server.tomcat.threads.max=200
server.tomcat.accept-count=200
server.tomcat.max-connections=8192
server.tomcat.connection-timeout=20s
server.tomcat.keep-alive-timeout=65s      # ★ Nginx keepalive_timeout(60s) 보다 길게
server.tomcat.max-http-form-post-size=10MB
server.max-http-request-header-size=16KB

# 프록시 헤더 신뢰 — 이 한 줄이면 RemoteIpValve 가 자동 등록됩니다
server.forward-headers-strategy=native
server.tomcat.remoteip.internal-proxies=127\\.0\\.0\\.1|10\\.\\d+\\.\\d+\\.\\d+

# 접근 로그 (기본 꺼져 있습니다 — 켜 두세요)
server.tomcat.accesslog.enabled=true
server.tomcat.accesslog.pattern=%h %l %u %t "%r" %s %b %D
#   %D = 처리 시간(ms) ★ 이게 없으면 "어느 요청이 느린가"를 못 봅니다
keepAliveTimeout 을 Nginx 보다 짧게 두면 간헐적 502 가 납니다. Nginx 가 유휴 연결을 재사용하려는 바로 그 순간 톰캣이 연결을 닫으면, 요청이 허공에 나가 502 로 끝납니다. 재현이 안 되고 부하가 낮을 때 오히려 자주 나는 것이 특징입니다 (유휴 시간이 길어야 생기므로). 백엔드 쪽을 항상 더 길게 잡는 것이 원칙입니다.
SECTION 05

WAR 배포 · 컨텍스트

WAR 파일을 webapps/ 에 넣으면 자동으로 풀려서 배포됩니다.

# 배포
sudo cp myapp.war /opt/tomcat/webapps/
# → /opt/tomcat/webapps/myapp/ 로 자동 압축 해제
# → 접속 주소: http://localhost:8080/myapp

# 루트 경로(/)로 배포하려면 파일 이름을 ROOT.war 로
sudo cp myapp.war /opt/tomcat/webapps/ROOT.war

# 제거 — WAR 를 지우면 폴더도 함께 삭제됩니다
sudo rm /opt/tomcat/webapps/myapp.war
WAR 파일명접속 경로
ROOT.war/
myapp.war/myapp
myapp##1.2.0.war/myapp — 버전 표기(병렬 배포용)
api#v1.war/api/v1 — # 이 / 로

경로를 직접 지정하기 — context 파일

<!-- conf/Catalina/localhost/myapp.xml -->
<!-- 파일 이름이 곧 컨텍스트 경로가 됩니다 -->
<Context docBase="/opt/apps/myapp" reloadable="false">

  <!-- 앱에서 쓸 DB 커넥션 풀 -->
  <Resource name="jdbc/mydb"
            auth="Container"
            type="javax.sql.DataSource"
            driverClassName="org.postgresql.Driver"
            url="jdbc:postgresql://db:5432/shop"
            username="app"
            password="${DB_PASSWORD}"
            maxTotal="20" maxIdle="10" maxWaitMillis="3000"
            validationQuery="SELECT 1" testOnBorrow="true" />
</Context>
reloadable="true" 는 운영에서 쓰지 마세요. 클래스 파일 변경을 주기적으로 감시하느라 자원을 쓰고, 재로딩 시 메모리 누수(PermGen·Metaspace)가 쌓입니다. 개발 환경에서만 쓰세요.

배포 방식 비교

방식설명
파일 복사가장 단순. CI 에서 scp 후 재시작
Manager 앱웹 UI·API 로 배포. 보안 위험이 크므로 운영에서는 제거 권장
병렬 배포##버전 표기로 신구 버전을 동시에 두고 세션이 끝나면 옛 버전 제거
컨테이너 교체★ 요즘 표준 — 이미지를 새로 빌드해 컨테이너를 갈아 끼웁니다
"주소에 /shop 이 왜 붙지"의 답은 파일 이름입니다 — 최상위로 쓰려면 ROOT.war 입니다.
SECTION 06

Spring Boot 내장 톰캣

Spring Boot 는 톰캣을 jar 안에 품고 있습니다. 그래서 java -jar 하나로 서버가 뜹니다. 

# application.properties — 내장 톰캣 설정
server.port=8080
server.address=127.0.0.1                       # ★ 프록시 뒤라면 로컬만

# 스레드 풀
server.tomcat.threads.max=200
server.tomcat.threads.min-spare=20
server.tomcat.accept-count=200
server.tomcat.max-connections=8192

# 타임아웃
server.tomcat.connection-timeout=20s
server.tomcat.keep-alive-timeout=20s

# 프록시 뒤에서 실제 IP·프로토콜 인식 (★ 매우 중요)
server.forward-headers-strategy=native
server.tomcat.remoteip.remote-ip-header=X-Forwarded-For
server.tomcat.remoteip.protocol-header=X-Forwarded-Proto
server.tomcat.remoteip.internal-proxies=127\\.0\\.0\\.1|10\\.\\d+\\.\\d+\\.\\d+

# 접근 로그
server.tomcat.accesslog.enabled=true
server.tomcat.accesslog.directory=/var/log/myapp
server.tomcat.accesslog.pattern=%h %l %u %t "%r" %s %b %D

# 업로드 크기
spring.servlet.multipart.max-file-size=50MB
spring.servlet.multipart.max-request-size=50MB

# 우아한 종료 (무중단 배포에 필수)
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s

# 오류 응답에서 정보 노출 줄이기
server.error.include-stacktrace=never
server.error.include-message=never

실행 방식

# 기본
java -jar myapp.jar

# JVM 옵션과 함께 (운영 권장)
java -Xms512m -Xmx1g \
     -XX:+UseG1GC \
     -XX:MaxRAMPercentage=75 \
     -Dspring.profiles.active=prod \
     -Dfile.encoding=UTF-8 \
     -jar myapp.jar

# 환경 변수로 설정 주입 (설정 파일에 비밀번호를 넣지 마세요)
export SPRING_DATASOURCE_PASSWORD='...'
java -jar myapp.jar

Spring Boot 의 정적 자원은 jar 안에 있습니다. src/main/resources/static/ 의 파일은 jar 에 포함되므로 Nginx 가 직접 읽을 수 없습니다.
· 방법 ① — 빌드 시 정적 파일을 별도 폴더로 복사해 배포
· 방법 ② — 프런트엔드를 완전히 분리해 별도 빌드·배포 (권장)
· 방법 ③ — CDN·오브젝트 스토리지에 업로드
업로드 파일은 절대 앱을 거쳐 내려주지 마세요. 수 MB 파일 하나가 스레드를 수 초간 점유합니다. Nginx 의 X-Accel-Redirect(내부 리다이렉트)를 쓰면 권한 검사는 앱이 하고 파일 전송은 Nginx 가 하는 구성이 가능합니다.

X-Accel-Redirect — 권한은 앱이, 전송은 Nginx 가

// 앱은 권한만 확인하고 "이 파일을 보내라"고 지시만 합니다 — 전송은 안 합니다
@GetMapping("/files/{id}")
public ResponseEntity<Void> download(@PathVariable Long id, @LoginUser Member me) {

    Attachment att = attachmentService.findAccessible(id, me);   // 권한 검사

    return ResponseEntity.ok()
        // ★ Nginx 만 이해하는 내부 경로 — 브라우저에는 안 나갑니다
        .header("X-Accel-Redirect", "/protected/" + att.storedName())
        .header(HttpHeaders.CONTENT_DISPOSITION,
                ContentDisposition.attachment()
                    .filename(att.originalName(), StandardCharsets.UTF_8).build().toString())
        .header(HttpHeaders.CONTENT_TYPE, att.contentType())
        .build();   // ★ 본문 없음 — 스레드가 즉시 반납됩니다
}
location /protected/ {
    internal;                       # ★ 외부에서 직접 접근 불가 — 앱을 거쳐야만
    alias /var/data/uploads/;
    sendfile on;
    sendfile_max_chunk 512k;        # 큰 파일이 워커를 독점하지 않게
}
100MB 파일 1000명 동시 다운로드결과
앱이 직접 스트리밍스레드 1000개 필요 — maxThreads 200 이면 즉시 포화
X-Accel-Redirect앱 스레드는 수 ms 만 사용 — 전송은 Nginx 가 이벤트 루프로
Apache 에도 같은 기능이 있습니다 — X-Sendfile(mod_xsendfile). S3 같은 오브젝트 스토리지를 쓴다면 서명된 URL(presigned URL)이 같은 역할을 합니다 — 앱이 권한을 확인하고 짧은 수명의 URL 만 발급하면 파일은 스토리지가 직접 내보냅니다. 어떤 방식이든 원칙은 하나입니다 — 앱 스레드로 바이트를 나르지 마세요.

SECTION 09

스레드 풀 튜닝

maxThreads 를 무작정 올리면 오히려 느려집니다. 근거를 갖고 정해야 합니다.

왜 무작정 늘리면 안 되나 — 스레드는 각각 스택 메모리(기본 1MB)를 차지하고, 개수가 많아지면 컨텍스트 스위칭 비용이 커집니다. 또 뒤쪽 DB 커넥션 풀이 20개인데 톰캣 스레드가 500개면 480개는 커넥션을 기다리며 대기할 뿐입니다. 병목은 스레드가 아니라 그 뒤에 있는 경우가 대부분입니다.

산정하는 법

필요한 스레드 수 ≈ 목표 RPS × 평균 응답 시간(초)

예) 목표 500 RPS · 평균 응답 0.2초
    → 500 × 0.2 = 100 스레드

여기에 여유 1.5~2배 → maxThreads = 150~200

※ 응답 시간이 대부분 'DB 대기'라면
   스레드를 늘려도 DB 커넥션이 병목이라 효과가 없습니다
   → DB 커넥션 풀과 함께 조정해야 합니다
# Spring Boot
server.tomcat.threads.max=200
server.tomcat.threads.min-spare=20
server.tomcat.accept-count=200          # 스레드가 다 차면 여기에 대기
server.tomcat.max-connections=8192

# DB 커넥션 풀과 균형을 맞추세요
spring.datasource.hikari.maximum-pool-size=20
증상원인과 조치
응답이 갑자기 느려짐 스레드 포화. 스레드 덤프로 어디서 막혔는지 확인 (대개 DB·외부 API 대기)
연결이 거부됨 acceptCount 대기열까지 가득 참. 근본 원인은 처리 속도
스레드를 늘려도 안 빨라짐 정상입니다. 병목이 다른 곳에 있다는 신호
OOM · 메모리 부족 스레드가 너무 많음. 스레드당 스택 1MB × 개수를 계산해 보세요

가상 스레드 Java 21+

# Spring Boot 3.2+ · Java 21+
spring.threads.virtual.enabled=true

# 요청마다 가상 스레드를 만들어 처리합니다
# · 블로킹 IO 대기 중에는 OS 스레드를 반납 → 수만 동시 요청 가능
# · maxThreads 제약에서 사실상 자유로워집니다
가상 스레드가 만능은 아닙니다.
· synchronized 블록 안에서 블로킹하면 캐리어 스레드가 고정(pinning)됩니다
· DB 커넥션 풀이 여전히 병목입니다 — 스레드가 늘어도 커넥션은 20개
· ThreadLocal 을 많이 쓰면 메모리 사용이 늘 수 있습니다
자세한 내용은 ☕ 자바 가이드의 고급·동시성 탭을 보세요.

스레드 풀과 DB 풀을 함께 맞추기

서비스 성격maxThreadsDB 풀 · 근거
DB 위주 CRUD100~200풀 10~20 — 요청 대부분이 DB 를 씁니다. 풀보다 스레드를 크게 잡아도 대기만 늘어납니다
외부 API 호출 위주200~400풀 10 — DB 는 거의 안 쓰고 네트워크 대기가 깁니다
계산 위주코어 수 × 2풀 5 — 더 늘리면 문맥 전환만 늘어납니다
정적 · 프록시—애초에 톰캣까지 오면 안 됩니다(t07)
가상 스레드
Java 21+		제약 없음풀이 유일한 상한이 됩니다 — 풀 크기를 반드시 재검토
DB 커넥션 풀은 크게 잡을수록 좋은 것이 아닙니다. HikariCP 문서의 권장 공식은 커넥션 수 = (코어 수 × 2) + 디스크 수 정도입니다 — 4코어면 10 안팎이 출발점입니다. DB 도 결국 코어 수만큼만 동시에 일할 수 있어서, 커넥션을 100개 열면 DB 내부에서 경합이 생겨 오히려 전체가 느려집니다. 앱 서버 대수 × 풀 크기가 DB 의 max_connections 를 넘지 않는지도 함께 확인하세요. 
# ① 지금 스레드가 몇 개 쓰이고 있나 (JMX)

jcmd <pid> Thread.print > dump.txt
grep -c 'java.lang.Thread.State: BLOCKED'       dump.txt   # 락 경합

grep -A3 '"http-nio-8080-exec' dump.txt | grep -o 'at [a-z.]*' | sort | uniq -c | sort -rn | head
#   → 톰캣 워커 스레드들이 공통으로 멈춰 있는 지점이 곧 병목입니다

# ③ 30초 간격으로 3번 떠서 비교하면 "계속 같은 곳"인지 알 수 있습니다
hikaricp.connections.pending 이 0 이 아니면 스레드를 늘려도 소용없습니다. 이 값은 커넥션을 못 받아 대기 중인 스레드 수입니다. 여기에 숫자가 쌓여 있다는 것은 병목이 DB 풀이라는 확정적인 증거입니다. 이때 할 일은 maxThreads 상향이 아니라 느린 쿼리 개선 · N+1 제거 · 캐시 · 풀 크기 재조정 순입니다. 지표를 안 보고 스레드 수부터 올리는 것이 가장 흔한 잘못된 대응입니다.
가상 스레드를 켜면 병목의 위치가 옮겨 갑니다. 톰캣 스레드 제약이 사라지는 대신, DB 풀·외부 API 커넥션 풀·메모리가 새로운 상한이 됩니다. 켜기 전에 maximum-pool-size 를 다시 검토하고, 속도 제한(rate limit)을 함께 두세요 — 수만 요청이 한꺼번에 들어와 DB 를 밀어붙이는 구조가 될 수 있습니다.
스레드를 늘려 해결되는 문제는 드뭅니다 — 대개 붙잡는 시간이 문제입니다.

JVM 메모리와 GC

자바는 메모리를 미리 잡아 씁니다. 컨테이너에서는 반드시 명시해야 합니다. 

# 기본 옵션
java -Xms1g -Xmx1g \                    # 초기·최대 힙 (같게 잡으면 리사이징 비용 없음)
     -XX:+UseG1GC \                     # Java 9+ 기본
     -XX:MaxGCPauseMillis=200 \
     -XX:+HeapDumpOnOutOfMemoryError \  # ★ OOM 시 힙 덤프 저장
     -XX:HeapDumpPath=/var/log/myapp/ \
     -Xlog:gc*:file=/var/log/myapp/gc.log:time,uptime:filecount=5,filesize=10M \
     -jar myapp.jar
컨테이너에서는 -Xmx 대신 비율을 쓰세요.
-XX:MaxRAMPercentage=75
컨테이너 메모리 제한이 바뀌어도 자동으로 따라갑니다. 고정값을 쓰면 제한을 올렸는데 힙은 그대로이거나, 제한을 내렸는데 힙이 커서 OOMKilled 가 됩니다.

컨테이너 메모리 배분

컨테이너 메모리 2GB 일 때

  힙 (Xmx)              1.4GB   (70%)
  메타스페이스           ~200MB   (클래스 정보)
  스레드 스택            ~200MB   (200 스레드 × 1MB)
  다이렉트 버퍼·코드 캐시 ~150MB
  여유                   ~50MB
  ────────────────────────────
  합계                   2GB

★ 힙만 보고 2GB 를 다 주면 OOMKilled 가 납니다
  (컨테이너는 힙 밖 메모리도 함께 셉니다)

# JVM 이 인식한 컨테이너 자원 확인
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'
메모리 문제의 진단 순서 — ① GC 로그에서 Full GC 빈도를 봅니다 (잦으면 힙 부족 또는 누수) ② 힙 덤프를 떠서 어떤 객체가 많은지 확인합니다 (MAT·VisualVM) ③ 힙은 여유 있는데 컨테이너가 죽으면 힙 밖 메모리를 의심합니다 (다이렉트 버퍼·네이티브 라이브러리·스레드 수)
"가끔 몇 초씩 멈춰요"의 대부분은 Old 영역 수집입니다.
SECTION 11

로그 설정

catalina.out 은 계속 커지기만 하는 파일입니다. 방치하면 디스크가 찹니다.

로그내용
catalina.out표준 출력·에러 전부. 로테이션이 안 됩니다
catalina.YYYY-MM-DD.log톰캣 자체 로그 (날짜별로 나뉨)
localhost_access_log.*.txt접근 로그 (AccessLogValve)
localhost.YYYY-MM-DD.log애플리케이션 오류
# /etc/logrotate.d/tomcat — catalina.out 로테이션
/opt/tomcat/logs/catalina.out {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate           # ★ 톰캣을 재시작하지 않고 잘라냅니다
    su tomcat tomcat
}
copytruncate 를 쓰는 이유 — 톰캣은 파일 핸들을 계속 열고 있어서, 파일을 이름만 바꾸면 계속 옛 파일에 씁니다(디스크는 그대로 차오릅니다). copytruncate 는 내용을 복사한 뒤 원본을 0바이트로 잘라 이 문제를 피합니다. (아주 짧은 순간의 로그 유실 가능성은 있습니다)

접근 로그

<Valve className="org.apache.catalina.valves.AccessLogValve"
       directory="logs"
       prefix="access" suffix=".log"
       pattern="%h %l %u %t &quot;%r&quot; %s %b %D &quot;%{User-Agent}i&quot; %{X-Request-Id}i"
       rotatable="true"
       maxDays="30" />
<!-- %D = 처리 시간(ms) · %{헤더}i = 요청 헤더 -->

Spring Boot 라면 로그백으로

<!-- logback-spring.xml -->
<configuration>
  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>/var/log/myapp/app.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>/var/log/myapp/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>100MB</maxFileSize>
      <maxHistory>30</maxHistory>
      <totalSizeCap>5GB</totalSizeCap>
    </rollingPolicy>
    <encoder>
      <pattern>%d{ISO8601} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n</pattern>
    </encoder>
  </appender>
  <root level="INFO"><appender-ref ref="FILE"/></root>
</configuration>
컨테이너 환경에서는 파일이 아니라 표준 출력으로 로그를 내보내세요. 도커·쿠버네티스가 수집·로테이션을 알아서 처리합니다. 파일에 쓰면 컨테이너가 사라질 때 로그도 함께 사라집니다.

Nginx + Tomcat 연동

실무 표준 구성입니다. 처음부터 끝까지 만들어 봅니다.

# /etc/nginx/sites-available/myapp
upstream tomcat {
    server 127.0.0.1:8080;
    keepalive 32;                     # ★ 연결 재사용
}

server {
    listen 80;
    server_name example.com;
    location ^~ /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 보안 헤더
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;

    # 업로드 크기
    client_max_body_size 50m;

    # 정적 자원
    location ^~ /static/ {
        alias /opt/myapp/static/;
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 헬스체크 (로그 제외)
    location = /actuator/health {
        proxy_pass http://tomcat;
        access_log off;
    }

    # 관리 엔드포인트는 내부에서만
    location ^~ /actuator/ {
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://tomcat;
    }

    # 애플리케이션
    location / {
        proxy_pass http://tomcat;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port  $server_port;

        proxy_http_version 1.1;
        proxy_set_header Connection "";

        proxy_connect_timeout 5s;
        proxy_read_timeout   60s;
        proxy_send_timeout   60s;
    }
}

server.address=127.0.0.1
server.port=8080
server.forward-headers-strategy=native

# Actuator 는 별도 포트로 빼는 것도 좋은 방법입니다
management.server.port=8081
management.server.address=127.0.0.1
management.endpoints.web.exposure.include=health,info,metrics,prometheus
확인 절차
① curl -I http://127.0.0.1:8080/ — 톰캣이 직접 응답하나
② sudo nginx -t && sudo systemctl reload nginx
③ curl -I https://example.com/ — 전체 경로가 동작하나
④ 앱 로그에 실제 클라이언트 IP 가 찍히나
⑤ 정적 파일이 Nginx 로그에만 남고 톰캣 로그에는 없는지
이 구성의 사고는 거의 전부 헤더 전달 설정에서 납니다.
SECTION 13

HTTPS 처리 위치

암호화를 어디서 풀지 결정해야 합니다. 대부분 앞단에서 끝냅니다.

구성설명평가
Nginx 에서 종료
(TLS Termination)		 Nginx 가 복호화하고 톰캣에는 평문 HTTP ★ 가장 흔함 — 인증서 관리가 한 곳
재암호화
(Re-encryption)		 Nginx 가 복호화 후 톰캣에 다시 HTTPS 망 구간까지 암호화가 필요할 때 (금융·공공)
통과
(TLS Passthrough)		 Nginx 가 그대로 흘려보내고 톰캣이 복호화 Nginx 가 내용을 못 보므로 라우팅·캐시 불가
앞단 종료 방식에서 가장 흔한 사고 — 리다이렉트 무한 루프
① 브라우저가 HTTPS 로 접속 → ② Nginx 가 HTTP 로 톰캣에 전달 → ③ Spring Security 가 "HTTP 네? HTTPS 로 가세요" 리다이렉트 → ④ 반복
해결 — X-Forwarded-Proto 헤더 전달 + server.forward-headers-strategy=native 
# Spring Boot — 프록시 뒤에 있을 때 반드시
server.forward-headers-strategy=native

# 쿠키에 Secure 플래그 (HTTPS 에서만 전송)
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax
<!-- 순수 톰캣이라면 RemoteIpValve -->
<Valve className="org.apache.catalina.valves.RemoteIpValve"
       remoteIpHeader="X-Forwarded-For"
       protocolHeader="X-Forwarded-Proto"
       protocolHeaderHttpsValue="https"
       internalProxies="127\.0\.0\.1|10\.\d+\.\d+\.\d+|172\.1[6-9]\.\d+\.\d+" />
<!-- 이 밸브가 request.isSecure() 와 getRemoteAddr() 을 올바르게 만들어 줍니다 -->

톰캣에 직접 HTTPS 를 붙여야 한다면

# Let's Encrypt 인증서를 자바 키스토어(PKCS12)로 변환
sudo openssl pkcs12 -export \
  -in  /etc/letsencrypt/live/example.com/fullchain.pem \
  -inkey /etc/letsencrypt/live/example.com/privkey.pem \
  -out /opt/tomcat/conf/keystore.p12 \
  -name tomcat -passout pass:changeit
# Spring Boot
server.port=8443
server.ssl.key-store=/opt/myapp/keystore.p12
server.ssl.key-store-type=PKCS12
server.ssl.key-store-password=${KEYSTORE_PASSWORD}
server.ssl.key-alias=tomcat
server.ssl.enabled-protocols=TLSv1.2,TLSv1.3
갱신이 번거롭습니다. Let's Encrypt 는 90일마다 갱신되는데, 갱신할 때마다 키스토어를 다시 만들고 톰캣을 재시작해야 합니다. 이것이 앞단에서 TLS 를 끝내는 구성을 선호하는 실질적인 이유입니다.
종료 위치를 정하는 기준은 성능이 아니라 어디까지 신뢰할 수 있는 망인가입니다.

① 우아한 종료 (Graceful Shutdown)

# 2) 처리 중인 요청을 최대 30초까지 기다림

② LB 에서 먼저 빼기 (드레인)

#!/usr/bin/env bash
set -euo pipefail

# 1) 헬스체크를 실패시켜 LB 가 이 서버를 제외하게 합니다
curl -fsS -X POST http://127.0.0.1:8081/actuator/shutdown-prepare || true
#    (또는 파일 플래그를 두고 헬스 엔드포인트가 그것을 보게 합니다)

# 2) LB 가 인지할 시간을 줍니다 (헬스체크 주기 × 실패 임계값)
sleep 15

# 3) 이제 종료해도 새 요청이 오지 않습니다
sudo systemctl stop myapp

# 4) 새 버전 배포 후 기동
sudo cp myapp-new.jar /opt/myapp/myapp.jar
sudo systemctl start myapp

# 5) 준비될 때까지 기다린 뒤 LB 에 복귀
until curl -fsS http://127.0.0.1:8081/actuator/health | grep -q '"UP"'; do sleep 2; done

③ 롤링 배포 (서버가 여러 대일 때)

# Nginx : 한 대씩 빼면서 배포합니다
upstream tomcat {
    server 10.0.1.11:8080 max_fails=2 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=2 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=2 fail_timeout=10s;
}

#   server 10.0.1.11:8080 down;

무중단 배포에서 놓치기 쉬운 것
· DB 스키마 변경 — 신구 버전이 동시에 도는 동안 양쪽 모두 동작해야 합니다 (확장-축소 패턴 → 🗄️ DB 가이드 a09)
· 세션 — 서버에 세션이 있으면 그 서버를 내리는 순간 로그아웃됩니다 (t08)
· 진행 중인 배치·스케줄러 — 종료 시 중단되면 데이터가 반만 처리될 수 있습니다
· 캐시 워밍업 — 새 인스턴스는 캐시가 비어 있어 초기에 느립니다
쿠버네티스라면 이 과정을 플랫폼이 해 줍니다. readinessProbe(트래픽 받을 준비) · preStop 훅(드레인 대기) · terminationGracePeriodSeconds(종료 유예)를 설정하면 롤링 업데이트가 자동으로 무중단이 됩니다 → 🛡️ 운영 탭 o11.

SECTION 16

문제 진단

응답이 없거나 느릴 때 무엇을 봐야 하는지 순서대로 정리합니다.

스레드 덤프 — 어디서 멈췄나

# 프로세스 ID 찾기
jps -l
# 또는 ps aux | grep java

# 스레드 덤프 (3~5초 간격으로 3회 뜨는 것이 정석)
jstack <pid> > /tmp/dump1.txt
sleep 5; jstack <pid> > /tmp/dump2.txt
sleep 5; jstack <pid> > /tmp/dump3.txt

# 또는
jcmd <pid> Thread.print > /tmp/dump.txt

# 상태별 개수 세기
grep 'java.lang.Thread.State' /tmp/dump1.txt | sort | uniq -c
142 java.lang.Thread.State: WAITING (parking) 45 java.lang.Thread.State: BLOCKED (on object monitor) ← 락 경합! 13 java.lang.Thread.State: RUNNABLE
상태의미
RUNNABLE실행 중 또는 IO 대기
BLOCKED락을 기다림 — 많으면 동기화 병목
WAITING다른 스레드를 무한 대기 (커넥션 풀 대기 등)
TIMED_WAITING시간 제한 대기 (sleep·poll)
3회를 뜨는 이유 — 같은 스레드가 세 번 모두 같은 위치에 있으면 진짜 막힌 것이고, 위치가 계속 바뀌면 정상적으로 일하는 중입니다. 덤프 하나만 보고 판단하면 틀립니다.

증상별 진단표

증상확인 순서
응답 없음 (행) ① 스레드 덤프 3회 → ② BLOCKED·WAITING 이 몰린 지점 확인 → ③ 대개 DB 커넥션 풀 고갈이나 외부 API 대기
OutOfMemoryError ① 힙 덤프 분석(MAT) → ② 어떤 객체가 많은지 → ③ 캐시·컬렉션 무한 증가 의심
Metaspace OOM 이면 클래스 로딩 누수(핫 리로드 반복)
CPU 100% ① top -H -p <pid> 로 바쁜 스레드 ID 확인 → ② 16진수로 변환 → ③ 덤프에서 nid=0x… 로 검색
흔한 원인: 무한 루프 · 잦은 Full GC · 정규식 폭주
점점 느려짐 GC 로그에서 Full GC 빈도와 회수량 확인 — 회수가 안 되면 메모리 누수
기동 실패 catalina.out 의 맨 앞 예외를 보세요. 뒤의 것은 연쇄 오류입니다
# CPU 를 많이 쓰는 스레드 찾기
top -H -p <pid>                       # TIME 이 큰 스레드의 PID 확인
printf '%x\n' <스레드PID>              # 16진수로 변환 → nid 값
grep -A 20 'nid=0x<16진수>' /tmp/dump.txt

# JFR 로 상세 프로파일링 (운영에서도 부하가 낮습니다)
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr
# JDK Mission Control 로 열어 봅니다

# 실시간 지표
jcmd <pid> VM.native_memory summary    # -XX:NativeMemoryTracking=summary 필요
jstat -gcutil <pid> 1000
더 깊은 JVM 진단은 ☕ 자바 가이드의 🔬 전문가 · JVM 내부 탭에서 다룹니다 — GC 내부·JFR·힙 덤프 분석·네이티브 메모리 추적까지 정리돼 있습니다.
