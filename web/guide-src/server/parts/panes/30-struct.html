STR 01

인프라도 코드다 — 저장소에 둘 것 · 두지 않을 것 · 규모별 진화

인프라를 저장소에 두는 이유는 하나입니다. 서버가 지금 왜 이렇게 생겼는지를 git log 로 답하려고입니다. 그러려면 "무엇을 넣고 무엇을 빼는지"가 먼저 정해져야 합니다. 설정과 절차는 넣고, 비밀과 상태는 뺍니다.

작은 팀의 인프라 저장소 한 벌

infra/
├─ README.md            # 저장소 지도 · 처음 온 사람이 읽을 순서
├─ nginx/               # 서버 설정 (STR 02)
├─ compose/             # 서버 1~3대 단계의 배포 단위 (STR 03)
├─ k8s/                 # 매니페스트 · Kustomize (STR 04)
├─ terraform/           # 클라우드 자원 (STR 05)
├─ runbooks/            # 장애 대응 절차 — 알림마다 한 장 (STR 10)
├─ docs/adr/            # 왜 이렇게 정했나 — 결정 기록
├─ .github/workflows/   # 검사 · 배포 파이프라인 (STR 09)
├─ .pre-commit-config.yaml
└─ .gitignore           # 비밀 · 상태 파일 차단 — 첫 커밋 전에
처음부터 이 폴더가 다 필요하지는 않습니다. 서버 한 대면 nginx/ 와 runbooks/ 만으로 시작하고, 아래 진화 단계를 따라 늘립니다.

넣는 것 · 빼는 것

렌더 결과 · DB 덤프 · 로그❌ 뺌다시 만들 수 있는 것은 넣지 않습니다
인프라 구조도 신호가 올 때 한 칸씩 — 서비스 세 개에 쿠버네티스 여러 클러스터는 비용만 큽니다.

STR 02

Nginx 설정 구조 — nginx.conf · conf.d · snippets · 템플릿

블록 중첩과 파일 위치는 🧭 시작 탭 w07 "설정 파일 구조 읽는 법"에, 공통 프록시 조각은 🟩 Nginx 탭 n04 에 있습니다. 여기서는 사이트가 열 개를 넘을 때 저장소 안에서 어떻게 나누는지만 봅니다. 핵심은 사이트당 파일 하나, 공통은 snippets/, 환경 차이는 템플릿입니다.

저장소 안의 nginx/

nginx/
├─ nginx.conf             # 전역 · events · http — 거의 안 바뀜
├─ conf.d/                # ★ 사이트(server 블록) 하나 = 파일 하나
│  ├─ 00-default.conf     # 모르는 Host 는 444 로 끊기
│  ├─ api.conf
│  └─ admin.conf
├─ snippets/              # 여러 사이트가 include 하는 조각
│  ├─ tls.conf            # 프로토콜 · 세션 캐시
│  ├─ headers.conf        # 보안 헤더
│  └─ proxy-common.conf   # 프록시 헤더 · 타임아웃 (🟩 n04)
├─ templates/             # 환경마다 다른 값 — envsubst 로 렌더
│  └─ upstream.conf.template
└─ certs/                 # .gitignore — 인증서는 밖에서 주입

sites-available 냐 conf.d 냐

방식어디서저장소에 둘 때
sites-available/ + sites-enabled/Debian · Ubuntu 패키지켜기 = 심볼릭 링크 — git 과 컨테이너에서 다루기 번거롭습니다
conf.d/*.confnginx.org 패키지 · 공식 Docker 이미지권장 — 파일이 있으면 켜짐, 지우면 꺼짐
Ubuntu 기본 nginx.conf 는 둘 다 include 합니다. 한 서버에서 두 방식을 섞으면 같은 server_name 이 두 번 잡혀 conflicting server name 경고가 나옵니다 — 하나로 통일하세요.
nginx.conf → conf.d → snippets 의 세 겹 — 사이트 파일이 짧을수록 리뷰가 쉽습니다.

사이트 파일 — 다른 점만 남긴다

# conf.d/api.conf
server {
    listen 443 ssl;
    http2 on;                       # nginx 1.25.1+ 문법
    server_name api.example.com;

    ssl_certificate     /etc/nginx/certs/api.crt;
    ssl_certificate_key /etc/nginx/certs/api.key;
    include snippets/tls.conf;      # 상대 경로 = /etc/nginx 기준
    include snippets/headers.conf;

    location / {
        proxy_pass http://api_upstream;   # templates/ 에서 렌더
        include snippets/proxy-common.conf;
    }
}
add_header 는 상속되지 않을 때가 있습니다. location 안에 add_header 가 하나라도 있으면 server 레벨의 headers.conf 헤더가 그 location 에서는 통째로 사라집니다. 그런 location 에는 headers.conf 를 다시 include 하세요.

환경마다 다른 값 — 공식 이미지의 템플릿

# templates/upstream.conf.template
#  → 시작 때 /etc/nginx/conf.d/upstream.conf 로 렌더
upstream api_upstream {
    server ${API_HOST}:${API_PORT};
    keepalive 32;
}
# compose.yaml 일부
services:
  nginx:
    image: nginx:stable-alpine
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/snippets:/etc/nginx/snippets:ro
      - ./nginx/templates:/etc/nginx/templates:ro
      - ./nginx/conf.d/api.conf:/etc/nginx/conf.d/api.conf:ro
    environment:
      API_HOST: api
      API_PORT: "8080"
공식 이미지의 시작 스크립트는 정의된 환경 변수만 치환하므로 $host 같은 nginx 변수는 그대로 남습니다. conf.d 폴더 전체를 마운트하면 렌더 결과를 쓸 수 없으니 파일 단위로 마운트합니다. 검사는 docker compose run --rm nginx nginx -t.
❌ 사이트마다 복사
conf.d/api.conf     # ssl_protocols 6줄 + 헤더 8줄
conf.d/admin.conf   # 같은 14줄 (한 곳만 TLSv1 남음)
conf.d/shop.conf    # 같은 14줄 (헤더 하나 빠짐)
✅ 조각은 한 곳
snippets/tls.conf       # 여기만 고치면
snippets/headers.conf   # 모든 사이트에 반영
conf.d/*.conf           # include 두 줄 + 자기 location
정리 — 저장소에서는 conf.d/ 에 사이트당 파일 하나, 공통은 snippets/, 환경 차이는 templates/ + envsubst. 배포 전에 항상 nginx -t.
STR 03

Docker Compose 프로젝트 — 공통 파일 + override + profiles

Compose 문법과 완본 예제는 ☸️ 도커 · 쿠버네티스 탭 d04 에, 관측 스택 한 벌은 🔭 관측 탭 y12 에 있습니다. 여기서는 서비스가 늘어날 때 파일을 어떻게 쪼개고 Dockerfile 을 어디에 두는지를 봅니다. 원칙은 공통은 compose.yaml 하나, 환경 차이는 덧씌우는 파일, 가끔 쓰는 도구는 profile입니다.

서비스 서너 개짜리 Compose 저장소

shop/
├─ compose.yaml            # 공통 — 서비스 · 이미지 · 볼륨 · 네트워크
├─ compose.override.yaml   # 개발 — 소스 마운트 · 디버그 포트 (자동 적용)
├─ compose.prod.yaml       # 운영 — restart · 리소스 · 로그 (-f 로 명시)
├─ .env.example            # 변수 이름만 — 커밋
├─ .env                    # 실제 값 — .gitignore
├─ services/
│  ├─ api/
│  │  ├─ Dockerfile        # ★ 서비스 코드 옆에 — 빌드 컨텍스트가 작아짐
│  │  ├─ .dockerignore
│  │  └─ src/
│  └─ worker/
│     └─ Dockerfile
├─ nginx/                  # STR 02 의 구조 그대로
└─ ops/
   ├─ backup.sh            # 볼륨 백업 (☸️ d04)
   └─ deploy.sh            # pull → up -d → 헬스 확인

파일마다 무엇을 쓰나

파일넣는 것읽히는 때
compose.yaml이미지 · 의존 · 헬스체크 · 볼륨항상
compose.override.yaml소스 마운트 · 포트 공개 · 디버거-f 없이 실행할 때만
compose.prod.yamlrestart · 자원 한도 · 로그 회전-f 로 지정할 때
.envcompose 파일 안 ${변수} 값항상 (셸 변수가 이김)
.env 는 compose 파일을 치환하는 용도이고 컨테이너 안으로 자동으로 들어가지 않습니다. 컨테이너에 넣으려면 environment: 에 적거나 env_file: 로 지정합니다.
덧씌우기 구조 — 공통 파일에는 모든 환경에서 같은 것만. 환경 하나에만 필요한 값이 공통에 있으면 뺄 방법이 없습니다.

compose.yaml — 공통

name: shop
services:
  api:
    build: ./services/api        # Dockerfile 은 서비스 폴더 안
    image: registry.example.com/shop/api:${API_TAG:-dev}
    environment:
      DB_HOST: db
      DB_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD 가 .env 에 필요}
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: shop
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD 가 .env 에 필요}
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shop -d shop"]
      interval: 5s
      retries: 10
  adminer:                       # 가끔 쓰는 도구
    image: adminer
    profiles: [debug]            # --profile debug 일 때만 뜸
    ports: ["8081:8080"]
volumes:
  db-data:

덧씌우는 두 파일과 실행 명령

# compose.override.yaml — 개발 (자동)
services:
  api:
    build:
      target: dev                # Dockerfile 의 dev 단계
    volumes:
      - ./services/api/src:/app/src
    ports:
      - "8080:8080"

# compose.prod.yaml — 운영 (-f 로 명시)
services:
  api:
    restart: unless-stopped
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }
    logging:
      driver: json-file
      options: { max-size: "10m", max-file: "3" }
  db:
    restart: unless-stopped
docker compose up -d                          # 공통 + override
docker compose -f compose.yaml -f compose.prod.yaml config   # 합친 결과 확인
docker compose -f compose.yaml -f compose.prod.yaml up -d    # 운영
docker compose --profile debug up -d          # adminer 까지
운영 서버의 .env 에 COMPOSE_FILE=compose.yaml:compose.prod.yaml 를 적어 두면 -f 두 개를 매번 치지 않아도 됩니다 (Windows 는 구분자가 ;).

서비스가 열을 넘으면 — include 로 쪼개기 🟡 중급

# compose.yaml — 팀별 파일을 불러 붙임 (Compose 2.20+)
include:
  - path: ./services/order/compose.yaml
  - path: ./services/payment/compose.yaml
  - path: ./observability/compose.yaml
services:
  nginx:
    image: nginx:stable-alpine
include 된 파일 안의 상대 경로는 그 파일이 있는 폴더 기준이라, 각 팀이 자기 폴더에서 독립적으로 작성할 수 있습니다. 이름이 겹치는 서비스는 오류가 납니다. 이 단계에서 서버가 셋을 넘고 무중단이 필요하다면 Compose 를 더 키우기보다 쿠버네티스로 넘어갈 신호입니다 (STR 01).
❌ 환경마다 통째 복사
docker-compose.dev.yml    # 140줄
docker-compose.stg.yml    # 138줄 — 어디가 다른지 diff 로만 앎
docker-compose.prod.yml   # 141줄 — 헬스체크가 하나 빠짐
✅ 공통 하나 + 차이만
compose.yaml              # 120줄 — 모든 환경 공통
compose.override.yaml     # 12줄 — 개발 차이
compose.prod.yaml         # 15줄 — 운영 차이
정리 — compose.yaml 은 공통, override 는 개발, prod 파일은 -f. Dockerfile 은 서비스 폴더 안에, 가끔 쓰는 도구는 profiles, 커지면 include — 그다음은 쿠버네티스입니다.
STR 04

쿠버네티스 매니페스트 — Kustomize base/overlays vs Helm 차트

Helm 차트 구조와 Kustomize 기본형, 둘 중 고르는 표는 ☸️ 도커 · 쿠버네티스 탭 d12 에 있습니다. 여기서는 한 걸음 더 — 서비스가 여럿일 때 폴더를 어떻게 반복하고, 환경 사이의 공통 조각을 어디에 두는지를 봅니다.

Kustomize — 서비스마다 같은 모양을 반복

k8s/
├─ components/               # 일부 환경에만 켜는 조각
│  ├─ hpa/                   # 오토스케일 (stg · prod)
│  └─ pdb/                   # PodDisruptionBudget (prod)
└─ services/
   ├─ api/
   │  ├─ base/               # 순수 YAML — 환경 공통
   │  │  ├─ kustomization.yaml
   │  │  ├─ deployment.yaml
   │  │  └─ service.yaml
   │  └─ overlays/
   │     ├─ dev/             # replicas 1 · 로그 debug
   │     ├─ stg/
   │     └─ prod/            # replicas 4 · hpa · pdb
   │        ├─ kustomization.yaml
   │        └─ replicas.yaml
   └─ worker/                # 같은 모양 반복 — 찾기 쉬움
      ├─ base/
      └─ overlays/{dev,stg,prod}/

Helm — 차트는 하나, 값 파일이 환경

charts/
├─ common/                   # type: library — 라벨 · 프로브 공통 템플릿
└─ api/
   ├─ Chart.yaml             # dependencies: common
   ├─ values.yaml            # 기본값 — 모든 환경 공통
   ├─ values-dev.yaml        # ★ 환경 차이만
   ├─ values-stg.yaml
   ├─ values-prod.yaml
   └─ templates/
      ├─ deployment.yaml
      ├─ service.yaml
      └─ _helpers.tpl
# values.yaml 은 자동, 환경 파일만 -f 로 덧씌움
helm upgrade --install api ./charts/api \
  -n shop-prod -f charts/api/values-prod.yaml
helm template api ./charts/api -f charts/api/values-prod.yaml  # 렌더만
서비스마다 템플릿을 복사하지 말고 library 차트(type: library)로 공통 템플릿을 묶습니다. 라이브러리 차트는 단독 설치가 안 되고 다른 차트가 가져다 씁니다.
우리 앱은 Kustomize, 남의 것은 Helm — 섞어 쓰는 것이 가장 흔한 실무 조합입니다.

overlay 하나 — 다른 점만

# services/api/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: shop-prod
resources:
  - ../../base
components:
  - ../../../../components/hpa
  - ../../../../components/pdb
patches:
  - path: replicas.yaml
images:
  - name: shop-api                    # base 의 image 이름
    newName: registry.example.com/shop/api
    newTag: "1.8.2"                   # CI 가 바꾸는 유일한 줄
labels:
  - pairs:
      env: prod
# services/api/overlays/prod/replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 4

component — 환경 몇 개에만 켜는 조각

# components/hpa/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1alpha1
kind: Component
resources:
  - hpa.yaml
어디에 두나기준
base/모든 환경에서 같은 것 — 이미지 이름 · 포트 · 프로브
overlays/<env>/그 환경만 다른 것 — replicas · 자원 · 태그
components/환경 둘 이상이 공유하는 선택 기능 — hpa · pdb
components 경로는 overlay 폴더 기준 상대 경로입니다. 위 예는 k8s/services/api/overlays/prod 에서 네 칸 올라가 k8s/components 를 가리킵니다. 깊이가 다르면 kubectl kustomize 가 바로 오류를 냅니다.
정리 — 서비스마다 base/ + overlays/<env>/ 를 같은 모양으로 반복하고, 몇 환경에만 켜는 조각은 components/. 남에게 줄 패키지·서드파티는 Helm, 공통 템플릿은 library 차트로.
STR 05

Terraform / IaC — modules/ 와 live/ · 상태를 어디서 자르나

Terraform 저장소의 구조는 결국 상태(state) 파일을 몇 개로, 어디서 자르느냐의 문제입니다. 상태 하나가 클수록 plan 이 느려지고, 실수 한 번이 건드릴 수 있는 범위(blast radius)가 커집니다. 그래서 재사용할 코드(modules/)와 실제로 적용하는 곳(live/ 또는 environments/)을 나누고, 적용하는 곳을 환경 × 층으로 쪼갭니다.

modules/ + live/ — 가장 흔한 배치

terraform/
├─ modules/                  # 재사용 코드 — 여기서는 apply 하지 않음
│  ├─ network/
│  │  ├─ main.tf
│  │  ├─ variables.tf        # 입력 — 타입 · 설명 · 검증
│  │  ├─ outputs.tf          # 출력 — 다른 층이 쓰는 값만
│  │  ├─ versions.tf         # required_providers
│  │  └─ README.md
│  ├─ k8s-cluster/
│  └─ postgres/
└─ live/                     # ★ 상태 하나 = 폴더 하나
   ├─ prod/
   │  ├─ network/            # backend.tf · main.tf · terraform.tfvars
   │  ├─ cluster/
   │  └─ data/
   └─ stg/
      ├─ network/
      ├─ cluster/
      └─ data/

규칙 다섯 가지

규칙이유
apply 는 live/ 에서만modules/ 는 함수 정의, live/ 는 호출 — 상태는 호출하는 쪽에 생깁니다
상태 = 환경 × 층prod 네트워크와 stg 앱이 같은 상태에 있으면 stg 작업이 prod 를 잠급니다
층끼리는 출력으로만terraform_remote_state 나 data 소스로 읽고, 리소스를 직접 참조하지 않습니다
변수는 타입 · 설명 · 검증잘못된 값이 plan 단계에서 걸러집니다
모듈 버전 고정저장소가 갈라지면 ?ref=v1.4.0 태그로 — 모듈 수정이 모든 환경에 동시에 번지지 않게
environments/ · live/ · envs/ 는 이름만 다른 같은 개념입니다. live/ 는 Terragrunt 문서에서 퍼진 이름이고, 어느 쪽이든 팀 안에서 하나로 통일하면 됩니다.
상태 분리의 기준은 변경 주기와 피해 범위 — 같이 바뀌는 것끼리만 한 상태에 둡니다.

live/prod/network — 백엔드 · 모듈 호출

# live/prod/network/backend.tf
terraform {
  required_version = ">= 1.10"
  backend "s3" {
    bucket       = "myorg-tfstate"
    key          = "prod/network/terraform.tfstate"  # 폴더 경로와 같게
    region       = "ap-northeast-2"
    encrypt      = true
    use_lockfile = true    # 1.10+ S3 자체 잠금 — DynamoDB 표 불필요
  }
}

# live/prod/network/main.tf
module "network" {
  source = "../../../modules/network"
  name   = "shop-prod"
  cidr   = "10.20.0.0/16"
  azs    = ["ap-northeast-2a", "ap-northeast-2c"]
}

output "private_subnet_ids" {
  value = module.network.private_subnet_ids
}

모듈 입력 검증 · 다른 층에서 읽기

# modules/network/variables.tf
variable "cidr" {
  type        = string
  description = "VPC CIDR 블록"
  validation {
    condition     = can(cidrnetmask(var.cidr))
    error_message = "cidr 는 10.20.0.0/16 같은 IPv4 CIDR 이어야 합니다."
  }
}

# live/prod/cluster/main.tf — 네트워크 층의 출력만 읽음
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "myorg-tfstate"
    key    = "prod/network/terraform.tfstate"
    region = "ap-northeast-2"
  }
}

module "cluster" {
  source     = "../../../modules/k8s-cluster"
  subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids
}
terraform_remote_state 는 상대 상태 전체를 읽을 권한이 필요합니다. 권한을 더 좁히고 싶으면 태그로 찾는 data 소스(예: aws_subnets)나 SSM 파라미터에 출력을 써 두고 읽는 방식을 씁니다.
❌ 상태 하나에 전부
terraform/main.tf          # 3,000줄 · 리소스 600개
# plan 한 번 8분 · 누가 apply 중이면 전원 대기
# 대시보드 고치다 count 바꿔 서브넷 재생성 위험
# workspace 로 환경 구분 → 지금 어느 workspace 인지 실수
✅ 환경 × 층으로 쪼갬
live/prod/network/   # 리소스 40개 · 1년에 몇 번
live/prod/cluster/   # 리소스 60개
live/prod/apps/      # 리소스 120개 · 매주
# 폴더 = 상태 = 권한 단위 — 경로만 봐도 무엇을 건드리는지 앎
정리 — modules/ 는 정의, live/ 는 적용. 상태는 환경 × 층으로 잘라 폴더 하나에 하나, 층끼리는 출력으로만 연결합니다. 상태 파일은 원격 백엔드에 두고 잠금을 켭니다.
STR 06

GitOps 저장소 — 앱 저장소와 설정 저장소 · app-of-apps · ApplicationSet

Argo CD 의 Application · sync · prune 개념과 "매니페스트 저장소를 분리하라"는 결론은 ☸️ 도커 · 쿠버네티스 탭 d12 에 있습니다. 여기서는 그 설정 저장소 안을 어떻게 배치하는지, 서비스가 수십 개일 때 Application 을 손으로 만들지 않는 법, 그리고 이미지 태그가 바뀌는 흐름을 봅니다.

설정(config) 저장소 한 벌

deploy-config/
├─ bootstrap/
│  └─ root.yaml              # 사람이 딱 한 번 kubectl apply
├─ argocd/                   # root 가 가리키는 곳 = Argo CD 자기 설정
│  ├─ projects/              # AppProject — 팀별 권한 · 대상 네임스페이스
│  ├─ platform.yaml          # 플랫폼 Application 들 (app-of-apps)
│  └─ services-appset.yaml   # 서비스는 ApplicationSet 이 자동 생성
├─ platform/                 # 클러스터 공통 — 플랫폼 팀 소유
│  ├─ cert-manager/          # Helm 값 파일
│  ├─ ingress/
│  └─ monitoring/
└─ services/                 # 앱 팀 소유 — STR 04 의 모양 그대로
   ├─ api/
   │  ├─ base/
   │  └─ overlays/{dev,stg,prod}/
   └─ worker/

왜 앱 저장소와 나누나

이유한 저장소였다면
배포 이력코드 커밋 사이에 태그 변경이 섞여 "prod 에 지금 뭐가 떠 있나"를 찾기 어렵습니다
권한앱 개발자 전원이 prod 매니페스트를 바꿀 수 있게 됩니다
CI 루프CI 가 태그를 커밋 → 그 커밋이 다시 CI 를 깨움
여러 앱 한 번에"api 1.8 과 worker 2.3 을 같이" 를 커밋 하나로 못 묶습니다
서비스 하나 · 팀 하나라면 앱 저장소의 deploy/ 폴더로 시작해도 됩니다. 두 번째 서비스나 두 번째 팀이 생기면 나눌 신호입니다.
GitOps 의 배포 흐름 — CI 는 저장소까지, 클러스터는 Argo CD 가 끌어옵니다.

ApplicationSet — 폴더가 생기면 앱이 생긴다

# argocd/services-appset.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: services-prod
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - git:
        repoURL: https://github.com/myorg/deploy-config
        revision: main
        directories:
          - path: services/*/overlays/prod
  template:
    metadata:
      name: '{{index .path.segments 1}}-prod'   # api-prod
    spec:
      project: services
      source:
        repoURL: https://github.com/myorg/deploy-config
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{index .path.segments 1}}-prod'
      syncPolicy:
        automated: { prune: true, selfHeal: true }   # 승인은 머지 전에 (STR 09)
        syncOptions:
          - CreateNamespace=true

root 하나 — 나머지는 저장소가 만든다

# bootstrap/root.yaml — 이것만 손으로 apply
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/deploy-config
    targetRevision: main
    path: argocd            # 이 폴더의 Application · ApplicationSet 을 적용
    directory:
      recurse: true
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
방식맞는 곳
app-of-apps플랫폼처럼 앱마다 설정이 제각각 — Application 파일을 하나씩
ApplicationSet서비스처럼 모양이 같은 것 수십 개 · 클러스터 여러 개(cluster 생성기)
정리 — 앱 저장소는 코드와 이미지, 설정 저장소는 "무엇이 어디에 떠 있어야 하나". root 하나만 손으로 적용하고, 플랫폼은 app-of-apps, 같은 모양의 서비스는 ApplicationSet 으로 폴더에서 자동 생성합니다.
STR 07

MSA 저장소 전략 — 모노레포 vs 폴리레포 · 서비스 템플릿 · 공유 라이브러리

서비스를 무엇으로 쪼갤지는 🧱 백엔드 · MSA 탭 m03 에, 도입하지 말아야 할 때는 m11 에 있습니다. 여기서는 쪼갠 서비스들의 코드를 저장소 몇 개에 담을지, 그리고 서비스가 늘어도 헬스체크 · 로그 · Dockerfile 이 제각각이 되지 않게 하는 법을 봅니다.

모노레포 — 서비스 전부 한 저장소

shop/
├─ services/
│  ├─ order/            # 서비스마다 Dockerfile · deploy/ 동일한 모양
│  ├─ payment/
│  └─ catalog/
├─ libs/                # 공유 라이브러리 — 버전 없이 소스로 참조
│  ├─ observability/    # 로그 형식 · 트레이스 · 메트릭 이름
│  └─ api-contracts/    # OpenAPI · proto — 계약은 한 곳
├─ templates/service/   # 새 서비스 견본 (아래)
├─ .github/
│  ├─ CODEOWNERS        # 경로별 리뷰 책임
│  └─ workflows/        # 바뀐 서비스만 빌드 (STR 09)
└─ README.md

폴리레포 — 서비스마다 저장소

github.com/myorg/
├─ order-service        # 코드 · Dockerfile · CI
├─ payment-service
├─ catalog-service
├─ lib-observability    # 공유 라이브러리 — semver 로 배포
├─ api-contracts        # 계약 저장소 — 생성 코드를 패키지로
├─ service-template     # 새 저장소의 출발점
└─ deploy-config        # 설정 저장소 (STR 06) — 어느 쪽이든 따로
# .github/CODEOWNERS — 모노레포에서 권한을 경로로 나눔
/services/payment/   @myorg/payments-team
/libs/               @myorg/platform-team
/.github/workflows/  @myorg/platform-team
모노레포는 빌드 도구로, 폴리레포는 템플릿과 버전 규율로 비용을 냅니다.

서비스 템플릿 — 새 서비스가 첫날부터 같은 모양

templates/service/
├─ Dockerfile            # 멀티스테이지 · 비루트 사용자 · 고정 베이스 이미지
├─ .dockerignore
├─ src/
│  ├─ health.*           # /healthz (살아 있나) · /readyz (받을 수 있나)
│  └─ logging.*          # JSON 로그 · trace_id 필드 · 레벨은 환경 변수
├─ deploy/
│  ├─ base/              # 프로브 · 자원 요청 · 라벨 규칙이 이미 들어 있음
│  └─ overlays/{dev,stg,prod}/
├─ .github/workflows/ci.yml   # 공용 재사용 워크플로를 부르는 10줄
└─ README.md             # 온콜 · 대시보드 · 런북 링크 칸

공유 라이브러리 버전 규칙

상황규칙
모노레포소스로 참조 · 바꾸면 쓰는 서비스를 같은 PR 에서 같이 고침
폴리레포semver 로 배포 · 깨는 변경은 메이저 올림 · Renovate 같은 봇으로 갱신 PR
무엇을 넣나로그 · 트레이스 · 인증 검증처럼 모두가 똑같아야 하는 것만
넣지 말 것도메인 모델 — 공유하면 서비스가 다시 한 덩어리로 묶입니다
템플릿은 복사하는 순간부터 표류합니다. 템플릿 도구(cookiecutter · copier · Backstage 소프트웨어 템플릿 등)로 찍어 내고, 공통 부분은 재사용 워크플로 · library 차트처럼 참조로 두어야 고칠 곳이 하나로 유지됩니다.
정리 — 팀이 몇 개 안 되고 공유 코드가 많으면 모노레포 + CODEOWNERS, 팀과 배포 주기가 확실히 갈라지면 폴리레포 + 템플릿 + semver. 어느 쪽이든 설정 저장소는 따로, 공유 라이브러리에는 도메인 모델을 넣지 않습니다.
STR 08

환경 · 비밀 분리 — 디렉터리 vs 브랜치 · 시크릿 도구의 자리 · 값 우선순위

Sealed Secrets · SOPS · External Secrets 의 동작과 비교표는 ☸️ 도커 · 쿠버네티스 탭 d08 에 있습니다. 여기서는 저장소 안 어디에 무엇이 놓이는지와, 환경을 브랜치가 아니라 디렉터리로 나눠야 하는 이유를 봅니다.

환경은 디렉터리, 승격은 같은 digest 를 다음 overlay 에 적는 커밋 — 차이가 diff 한 화면에 보입니다.

비밀이 놓이는 자리 — 도구별

services/api/
├─ base/
│  └─ external-secret.yaml     # ① External Secrets — "어디서 가져오나"만
└─ overlays/
   ├─ dev/
   │  └─ secrets.enc.yaml      # ② SOPS — 값은 암호화, 키 이름은 평문
   └─ prod/
      └─ sealed-secret.yaml    # ③ Sealed Secrets — 그 클러스터 공개키로 봉인

.sops.yaml                     # SOPS 규칙 — 저장소 루트
# 평문 Secret · .env · 키 파일은 어디에도 없음 (STR 01 .gitignore)
한 저장소에서 셋을 섞어 쓰라는 뜻이 아니라 도구마다 놓이는 자리를 보인 것입니다. 하나를 골라 통일하세요 — 규모가 커지면 External Secrets 쪽으로 모이는 경우가 많습니다 (☸️ d08).

SOPS — 경로마다 다른 키

# .sops.yaml — 위에서부터 처음 맞는 규칙 하나가 적용
creation_rules:
  - path_regex: overlays/prod/.*\.enc\.yaml$
    encrypted_regex: ^(data|stringData)$   # 값만 암호화
    age: age1...prod-공개키...             # prod 키는 운영자만
  - path_regex: overlays/(dev|stg)/.*\.enc\.yaml$
    encrypted_regex: ^(data|stringData)$
    age: age1...dev-공개키...
sops -e -i services/api/overlays/prod/secrets.enc.yaml   # 제자리 암호화
sops services/api/overlays/prod/secrets.enc.yaml          # 편집기로 열기

설정 값 우선순위 — 아래가 위를 이깁니다

순출처저장소 위치넣는 값
1코드 기본값앱 저장소어디서나 안전한 값 — 타임아웃 · 페이지 크기
2공통 설정 (ConfigMap · values.yaml)base/환경과 무관한 운영 값
3환경별 덮어쓰기overlays/<env>/replicas · 로그 레벨 · 외부 주소
4비밀 (Secret 으로 주입)참조 · 암호화 파일만DB 비밀번호 · API 키
5실행 시 인자 · 긴급 플래그없음 — 기록을 남기고 곧 저장소로장애 중 임시 조치
5번이 오래 남으면 drift 입니다. 장애 때 kubectl set env 로 바꾼 값은 Argo CD selfHeal 이 켜져 있으면 곧 되돌려지고, 꺼져 있으면 저장소와 클러스터가 영영 달라집니다. 어느 쪽이든 같은 날 저장소에 반영하는 것이 규칙입니다.
정리 — 환경은 브랜치가 아니라 디렉터리, 승격은 같은 digest. 저장소에는 비밀의 참조나 암호문만 두고, 값은 코드 기본값 → base → overlay → Secret 순으로 덮어씁니다.
STR 09

CI/CD 파이프라인 파일 — 재사용 워크플로 · 환경 승인 · 아티팩트 흐름

빌드 · 스캔 · 푸시 워크플로 한 벌과 배포 체크리스트는 ☸️ 도커 · 쿠버네티스 탭 d13 에 있습니다. 서비스가 늘면 같은 YAML 이 저장소마다 복사되고 조금씩 달라집니다. 여기서는 .github/workflows 를 공용 조각과 호출부로 나누고, 빌드는 한 번, 승격은 digest 로 흐르게 하는 배치를 봅니다.

.github/ 정리 — 공용 조각과 호출부

.github/
├─ workflows/                # 하위 폴더 불가 — 이 폴더에 평평하게
│  ├─ _build-image.yml       # 재사용 (workflow_call) — 밑줄은 팀 관례
│  ├─ _bump-tag.yml          # 설정 저장소의 태그 갱신
│  ├─ api.yml                # 호출부 — 서비스당 20줄 안팎
│  ├─ worker.yml
│  └─ infra-checks.yml       # kubeconform · conftest · tflint (STR 10)
├─ actions/
│  └─ setup-tools/action.yml # 여러 단계 묶음 = composite action
└─ CODEOWNERS                # workflows/ 는 플랫폼 팀 리뷰
재사용 워크플로는 job 전체를, composite action 은 step 몇 개를 묶습니다. 여러 저장소가 쓰면 myorg/ci-templates 같은 저장소로 옮기고 @v1 태그로 고정해 부릅니다.

호출부 — 서비스는 무엇만 다른가

# .github/workflows/api.yml
name: api
on:
  push:
    branches: [main]
    paths: ["services/api/**"]      # 모노레포 — 바뀐 서비스만
jobs:
  build:
    uses: ./.github/workflows/_build-image.yml
    with:
      service: api
    permissions:
      contents: read
      packages: write
  stg:
    needs: build
    uses: ./.github/workflows/_bump-tag.yml
    with:
      service: api
      stage: stg
      digest: ${{ needs.build.outputs.digest }}
    secrets: inherit
  prod:
    needs: [build, stg]
    uses: ./.github/workflows/_bump-tag.yml
    with:
      service: api
      stage: prod
      digest: ${{ needs.build.outputs.digest }}
    secrets: inherit
빌드는 한 번, 승인은 prod 앞 한 번 — 나머지는 전부 자동으로 흐릅니다.

재사용 워크플로 — 승인 게이트는 여기에

# .github/workflows/_bump-tag.yml
name: bump-tag
on:
  workflow_call:
    inputs:
      service: { type: string, required: true }
      stage:   { type: string, required: true }
      digest:  { type: string, required: true }
jobs:
  bump:
    runs-on: ubuntu-latest
    environment: ${{ inputs.stage }}   # prod 환경에 필수 리뷰어 → 여기서 대기
    steps:
      - uses: actions/checkout@v5
        with:
          repository: myorg/deploy-config
          token: ${{ secrets.DEPLOY_CONFIG_TOKEN }}
      - name: digest 고정 커밋
        working-directory: services/${{ inputs.service }}/overlays/${{ inputs.stage }}
        run: |
          kustomize edit set image shop-${{ inputs.service }}=ghcr.io/myorg/shop-${{ inputs.service }}@${{ inputs.digest }}
          git config user.name "ci-bot"
          git config user.email "ci-bot@users.noreply.github.com"
          git diff --quiet || git commit -am "deploy(${{ inputs.stage }}): ${{ inputs.service }}"
          git push

규칙 네 가지

규칙이유
빌드는 한 번stg 와 prod 가 같은 바이너리 — 환경마다 빌드하면 검증이 무의미해집니다
태그보다 digest태그는 다시 밀어 넣을 수 있고 digest 는 내용의 해시입니다
environment 는 재사용 쪽에재사용 워크플로를 부르는 job 에는 environment: 를 쓸 수 없습니다
권한은 최소로job 마다 permissions: · 설정 저장소 토큰은 그 저장소에만
_build-image.yml 은 on: workflow_call 아래 outputs.digest 를 선언하고 docker/build-push-action 의 digest 출력을 그대로 넘깁니다. 빌드 · 푸시 단계 자체는 ☸️ d13 의 것을 그대로 옮기면 됩니다.
정리 — .github/workflows 는 밑줄 붙은 재사용 조각 + 서비스별 짧은 호출부. 이미지는 한 번 빌드해 digest 로 승격하고, 사람의 승인은 재사용 워크플로의 environment 에 겁니다.
STR 10

한 장 요약 — 유형 · 규모별 권장 구조 · 운영 문서 · 규칙을 도구로 강제하기

구조는 문서로 정하면 석 달 안에 무너집니다. 마지막 섹션은 앞의 아홉 섹션을 표 한 장으로 줄이고, 운영 문서를 어디에 두는지, 그리고 정한 규칙을 pre-commit 과 CI 가 지키게 하는 법으로 끝냅니다. 전체 아키텍처 그림은 🧬 전문가 탭 z14, 트래픽 규모별 견본은 📈 대규모 탭 x09 를 보세요.

유형 · 규모권장 구조지키는 도구다음 단계 신호
서버 1대nginx/conf.d + snippets/ · runbooks/ (STR 02)nginx -t 를 CI 에서서버 2대째 · 설치가 달라짐
서버 1~3대 · 서비스 5개compose.yaml + override + prod (STR 03)docker compose config무중단 · 자동 복구 필요
클러스터 1 · 팀 1앱 저장소 deploy/ base + overlays (STR 04)kubeconform · conftest서비스 2개째 · 팀 2개째

클러스터 · 리전 여럿terraform modules/ + live/ (환경 × 층) (STR 05)tflint · PR 에 plan플랫폼 팀 분리
MSA 코드모노레포 + CODEOWNERS 또는 폴리레포 + 템플릿 (STR 07)재사용 워크플로 (STR 09)팀 · 배포 주기가 갈라짐
질문 셋이면 시작 구조가 정해집니다 — 대부분은 Compose 나 deploy/ + Kustomize 에서 출발합니다.

③ 조직 규칙 — conftest (Rego)

# policy/deployment.rego — conftest 는 기본으로 package main 을 읽음
package main

deny contains msg if {
  input.kind == "Deployment"
  some c in input.spec.template.spec.containers
  not c.resources.limits.memory
  msg := sprintf("%s/%s: memory limit 이 없습니다", [input.metadata.name, c.name])
}

deny contains msg if {
  input.kind == "Deployment"
  some c in input.spec.template.spec.containers
  endswith(c.image, ":latest")
  msg := sprintf("%s/%s: latest 태그 금지", [input.metadata.name, c.name])
}
도구잡는 것
kubeconform스키마 위반 · 오타 필드 (-strict) — CRD 는 스키마 위치를 따로 지정
conftest / OPA"limit 필수 · latest 금지" 같은 우리 규칙
tflint잘못된 인스턴스 타입 · 안 쓰는 변수 · 명명 규칙
gitleaks커밋에 섞인 토큰 · 키
이 도구들은 이 PC 에 설치하지 않아 실행하지 않았고, 설정은 각 공식 문서 기준입니다. Rego 는 OPA 1.0 문법(contains · if)이라 예전 conftest 에서는 맨 위에 import rego.v1 이 필요할 수 있습니다. 위반이 이미 많은 저장소는 새 위반만 막는 것부터 시작하세요.
정리 — 시작은 대부분 Compose 나 deploy/ + Kustomize, 서비스와 팀이 늘면 설정 저장소, 클러스터가 늘면 Terraform 층 분리. 정한 규칙은 pre-commit · kubeconform · conftest · tflint 로 사람 대신 도구가 지키게 합니다.
