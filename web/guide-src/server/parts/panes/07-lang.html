SECTION 01

웹서버와 앱은 어떻게 대화하나

방식은 세 가지뿐입니다. 언어마다 관례가 다를 뿐입니다.

방식설명쓰는 곳
HTTP 프록시 웹서버가 앱에 HTTP 요청을 그대로 다시 보냅니다 ★ Node · Spring Boot · Go · Python(Gunicorn) — 가장 흔합니다
FastCGI 이진 프로토콜로 앱 프로세스에 전달 PHP-FPM
유닉스 소켓 TCP 대신 파일 형태의 소켓으로 (같은 서버 안에서만) Gunicorn · PHP-FPM — 약간 더 빠르고 안전
(AJP) Apache ↔ Tomcat 전용 이진 프로토콜 보안 이슈로 요즘은 잘 안 씁니다
공통 구조
어떤 언어든 결국 같습니다 ① 앱을 프로세스로 띄운다 → ② 프로세스 관리자가 죽으면 되살린다 → ③ 앞에 웹서버를 두고 프록시한다 → ④ 정적 파일은 웹서버가 처리한다
언어앱 실행프로세스 관리웹서버 연결

이 구조를 이해하면 어떤 언어든 배포할 수 있습니다. 새로운 언어를 만나도 "이 언어는 앱을 어떻게 띄우지?"만 찾으면 나머지(웹서버 설정·systemd·정적 파일 분리)는 거의 동일합니다.
"파이썬 배포"·"Node 배포"를 따로 배울 필요가 없는 이유입니다 — 다른 것은 실행 명령 한 줄뿐입니다.

어떤 언어든 쓰는 systemd 템플릿

# /etc/systemd/system/myapp.service
[Unit]
Description=My App
After=network.target
# 의존 서비스가 있으면
# Requires=postgresql.service

[Service]
Type=simple
User=myapp                          # ★ 전용 계정 — root 로 돌리지 마세요
Group=myapp
WorkingDirectory=/opt/myapp

# ── 이 줄만 언어별로 바뀝니다 ─────────────────────
ExecStart=/usr/bin/java -jar app.jar              # Java
# ExecStart=/opt/myapp/venv/bin/gunicorn -c gunicorn.conf.py app:app   # Python
# ExecStart=/usr/bin/node server.js                # Node
# ExecStart=/opt/myapp/bin/myapp                   # Go · Rust
# ────────────────────────────────────────────────

Environment=NODE_ENV=production
EnvironmentFile=-/etc/myapp/env     # 비밀은 파일로 (권한 600)

Restart=always                      # 죽으면 되살림
RestartSec=3
StartLimitBurst=5                   # 5회 연속 실패하면 포기(무한 재시작 방지)
StartLimitIntervalSec=60

# 그레이스풀 종료 — 진행 중 요청을 마치게
KillSignal=SIGTERM
TimeoutStopSec=30

# 리소스 한계
LimitNOFILE=65535
MemoryMax=2G

# 보안 강화 — 넣어 두면 침해 시 피해가 줄어듭니다
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/myapp/data /var/log/myapp

StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
sudo journalctl -u myapp -f           # 로그 실시간
sudo journalctl -u myapp --since "10 min ago" -p err   # 오류만

# 무중단 재시작이 되는지 (앱이 SIGTERM 을 제대로 처리하는지)
while true; do curl -s -o /dev/null -w "%{http_code} " localhost:8080/health; sleep 0.2; done &
sudo systemctl restart myapp
#  → 200 사이에 000·502 가 섞이면 그레이스풀 종료가 안 되고 있는 것입니다
앱을 0.0.0.0 에 바인딩하면 웹서버를 우회할 수 있습니다. 방화벽으로 막았다고 생각해도, 클라우드 보안 그룹 설정 하나가 어긋나면 8080 포트가 인터넷에 그대로 열립니다 — TLS 도 없고 웹서버의 접근 제어도 안 거칩니다. 127.0.0.1:8080 또는 유닉스 소켓에만 바인딩하는 것이 원칙이고, ss -tlnp 로 실제로 그런지 확인하세요.
Restart=always 만 넣어도 운영 안정성이 크게 올라갑니다. 다만 StartLimitBurst 를 함께 넣으세요 — 설정 오류로 즉시 죽는 앱을 무한히 재시작하면 로그가 초당 수백 줄씩 쌓여 디스크를 채웁니다. 5회 실패 후 멈추게 해 두면, 감시 도구가 "죽어 있음"을 정확히 알려 줍니다.
SECTION 02

Java ① WAR 배포

전통적인 방식입니다. 기존 시스템에서 여전히 많이 쓰입니다.

# 빌드
./gradlew clean bootWar        # 또는 mvn clean package

# 배포
sudo systemctl stop tomcat
sudo cp build/libs/myapp.war /opt/tomcat/webapps/ROOT.war
sudo rm -rf /opt/tomcat/webapps/ROOT      # 옛 압축 해제 폴더 제거
sudo systemctl start tomcat

# 로그로 기동 확인
sudo tail -f /opt/tomcat/logs/catalina.out
// Spring Boot 를 WAR 로 만들려면
@SpringBootApplication
public class MyApplication extends SpringBootServletInitializer {

    @Override
    protected SpringApplicationBuilder configure(SpringApplicationBuilder b) {
        return b.sources(MyApplication.class);
    }

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
# build.gradle
plugins { id 'war' }

dependencies {
    // 내장 톰캣은 provided 로 (외부 톰캣이 제공하므로)
    providedRuntime 'org.springframework.boot:spring-boot-starter-tomcat'
}
Tomcat 10 이상으로 옮길 때 주의 — 패키지가 javax.* → jakarta.* 로 바뀌었습니다. Spring Boot 2.x 로 만든 WAR 는 Tomcat 10+ 에서 동작하지 않습니다. Spring Boot 3 이상으로 올려야 합니다.
새로 만든다면 WAR 가 아니라 jar 를 쓰세요. 톰캣을 따로 설치·관리할 필요가 없고, 컨테이너 이미지로 만들기도 쉽습니다 → 다음 섹션. WAR 를 유지하는 이유는 기존 WAS 인프라·조직 정책 정도입니다.

WAR vs 실행 가능 jar — 실제 차이

항목WAR (외부 톰캣)실행 jar (내장)
배포 단위WAR 파일 + 톰캣 설치jar 하나
버전 관리앱과 톰캣을 따로앱에 포함 — 함께 올라갑니다
로컬 실행톰캣 설치 필요java -jar 한 줄
컨테이너화번거로움기본 이미지 + jar 복사
한 서버에 여러 앱webapps 에 여러 개포트를 나눠 여러 프로세스
무중단 배포톰캣 재시작 필요(또는 병렬 배포)인스턴스 단위 롤링
설정 위치server.xml·context.xmlapplication.yml
메모리여러 앱이 JVM 하나를 공유앱마다 JVM — 더 씁니다
 
# 실행 jar 방식 — 이 정도면 배포 전체입니다
./gradlew clean bootJar
scp build/libs/app.jar deploy@server:/opt/myapp/app.jar.new

ssh deploy@server '
  sudo mv /opt/myapp/app.jar /opt/myapp/app.jar.prev   # 롤백용으로 남기기
  sudo mv /opt/myapp/app.jar.new /opt/myapp/app.jar
  sudo systemctl restart myapp
  sleep 5
  curl -fsS localhost:8080/actuator/health || {
      echo "기동 실패 — 되돌립니다"
      sudo mv /opt/myapp/app.jar.prev /opt/myapp/app.jar
      sudo systemctl restart myapp
      exit 1
  }
'
# JVM 옵션 — 컨테이너·systemd 어느 쪽이든 이 정도는 챙기세요
Environment=JAVA_OPTS=" \
  -XX:MaxRAMPercentage=75.0 \        # ★ -Xmx 대신 비율로 (컨테이너 메모리 인식)
  -XX:+UseG1GC \
  -XX:+HeapDumpOnOutOfMemoryError \  # ★ OOM 시 덤프 — 원인 추적의 유일한 단서
  -XX:HeapDumpPath=/var/log/myapp/ \
  -XX:+ExitOnOutOfMemoryError \      # OOM 이면 죽고 재시작 (반쯤 살아있는 상태 방지)
  -Djava.security.egd=file:/dev/./urandom \
  -Duser.timezone=Asia/Seoul \
  -Dfile.encoding=UTF-8"
컨테이너에서 -Xmx 를 고정값으로 주지 마세요. 메모리 한도를 바꿔도 JVM 이 옛 값을 그대로 써서, 한도보다 힙이 커지면 컨테이너가 통째로 강제 종료(OOMKilled)됩니다. -XX:MaxRAMPercentage 를 쓰면 JVM 이 cgroup 한도를 읽어 알아서 맞춥니다. "잘 돌다가 갑자기 재시작되는데 로그에 아무것도 없다"면 대부분 이것입니다 — dmesg | grep -i kill 이나 파드 이벤트에서 확인할 수 있습니다.
WAR 를 유지해야 한다면 병렬 배포(parallel deployment)를 알아 두세요. ROOT##002.war 처럼 ##버전 을 붙여 넣으면 톰캣이 기존 세션은 옛 버전에서 마치게 하고 새 요청만 새 버전으로 보냅니다. 재시작 없이 전환되므로, 외부 톰캣 환경에서 가장 현실적인 무중단 수단입니다.

Java ② Spring Boot + Nginx

요즘 자바 배포의 표준입니다. jar 하나 + systemd + Nginx.

# 1) 빌드
./gradlew clean bootJar
# → build/libs/myapp-1.0.0.jar

# 2) 서버로 전송
scp build/libs/myapp-1.0.0.jar deploy@server:/opt/myapp/myapp.jar

# 3) 전용 계정 (한 번만)
sudo useradd -r -s /bin/false appuser
sudo mkdir -p /opt/myapp /var/log/myapp
sudo chown -R appuser:appuser /opt/myapp /var/log/myapp
# /etc/systemd/system/myapp.service
[Unit]
Description=My Spring Boot Application
After=network.target

[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/opt/myapp

# 비밀은 파일로 (권한 600) — 명령줄 인자에 넣으면 ps 로 다 보입니다
EnvironmentFile=/etc/myapp/env
Environment="JAVA_OPTS=-Xms512m -Xmx1g -XX:+UseG1GC -XX:MaxRAMPercentage=75"

ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/myapp/myapp.jar

SuccessExitStatus=143            # SIGTERM 종료를 정상으로 취급
Restart=on-failure
RestartSec=10
LimitNOFILE=65535

# 로그는 journald 로
StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapp

[Install]
WantedBy=multi-user.target
# /etc/myapp/env  (chmod 600)
SPRING_PROFILES_ACTIVE=prod
SERVER_PORT=8080
SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/shop
SPRING_DATASOURCE_USERNAME=app
SPRING_DATASOURCE_PASSWORD=...
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
sudo systemctl status myapp
sudo journalctl -u myapp -f
# Nginx
upstream myapp { server 127.0.0.1:8080; keepalive 32; }

server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    client_max_body_size 20m;

    location / {
        proxy_pass http://myapp;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
반드시 확인할 세 가지
① server.address=127.0.0.1 — 앱이 외부에 직접 노출되지 않게
② server.forward-headers-strategy=native — 프록시 인식
③ server.shutdown=graceful — 배포 시 요청 유실 방지
SECTION 04

Python ① WSGI vs ASGI

파이썬 웹 배포에서 가장 먼저 이해해야 할 개념입니다. 내 프레임워크가 어느 쪽인지에 따라 실행 방법이 달라집니다.

WSGI — 동기
# 요청 하나를 워커 하나가 끝까지 처리
def application(environ, start_response):
    start_response('200 OK', [('Content-Type','text/plain')])
    return [b'Hello']

# 프레임워크 : Django · Flask
# 서버      : Gunicorn · uWSGI
# 특징      : 단순 · 안정 · 라이브러리 호환성 최고
ASGI — 비동기
async def app(scope, receive, send):
    await send({'type':'http.response.start','status':200})
    await send({'type':'http.response.body','body':b'Hello'})

# 프레임워크 : FastAPI · Starlette · Django(비동기 뷰)
# 서버      : Uvicorn · Hypercorn · Granian
# 특징      : WebSocket 지원 · IO 대기 중 다른 요청 처리
상황선택
Django 웹 애플리케이션WSGI + Gunicorn (비동기 뷰를 쓴다면 ASGI 도 가능)
Flask APIWSGI + Gunicorn
FastAPIASGI + Uvicorn
WebSocket 이 필요ASGI 필수
외부 API 호출이 많은 서비스ASGI 가 유리 (IO 대기 중 다른 요청 처리)
CPU 연산이 많은 서비스둘 다 GIL 제약 — 프로세스를 늘리는 것이 핵심
ASGI 를 쓴다고 자동으로 빨라지지 않습니다. 비동기 프레임워크에서 동기 라이브러리를 그대로 호출하면 이벤트 루프가 통째로 멈춰 오히려 더 느려집니다. (예: FastAPI 에서 requests · 동기 DB 드라이버 사용)
비동기 전용 라이브러리(httpx·asyncpg)를 쓰거나 run_in_executor 로 분리해야 합니다. 자세한 내용은 🐍 파이썬 가이드의 대규모 트래픽 탭에 있습니다.

워커 수를 정하는 법 — 가장 자주 틀리는 설정

# gunicorn.conf.py — WSGI (Django · Flask)
import multiprocessing

bind = "unix:/run/myapp/gunicorn.sock"   # 유닉스 소켓이 TCP 보다 조금 빠릅니다
workers = multiprocessing.cpu_count() * 2 + 1     # ★ CPU 바운드 기준 출발점
worker_class = "gthread"                 # IO 대기가 많으면 스레드를 함께
threads = 4                              # 워커당 스레드

timeout = 30                             # 이 시간을 넘으면 워커를 죽이고 재시작
graceful_timeout = 30                    # 종료 신호 후 마무리 시간
keepalive = 65                           # ★ Nginx 보다 길게 (502 방지)

max_requests = 1000                      # ★ 메모리 누수 대비 — 주기적으로 워커 교체
max_requests_jitter = 100                #   동시에 교체되지 않게 흔들기

preload_app = True                       # 메모리 절약(fork 전에 로드)
accesslog = "-"
errorlog  = "-"
# ASGI (FastAPI) — uvicorn 워커를 gunicorn 이 관리하는 구성이 안정적입니다
gunicorn app:app \
  -k uvicorn.workers.UvicornWorker \
  -w 4 \
  -b unix:/run/myapp/uvicorn.sock \
  --timeout 30 --graceful-timeout 30 --keep-alive 65

# 또는 uvicorn 단독 (컨테이너에서는 이쪽이 단순합니다)
uvicorn app:app --host 127.0.0.1 --port 8000 --workers 4 --timeout-keep-alive 65
서비스 성격워커 설정
CPU 연산 중심workers = 코어 수 — 더 늘려도 GIL 때문에 이득이 없습니다
DB·API 대기 중심 (WSGI)workers = 코어×2+1 + gthread·threads 4~8
DB·API 대기 중심 (ASGI)workers = 코어 수 — 대기는 이벤트 루프가 흡수합니다
메모리를 많이 쓰는 앱워커 수 × 워커당 메모리가 서버 메모리를 넘지 않게
컨테이너(코어 제한)cpu_count() 가 호스트 코어를 반환할 수 있습니다 — 값을 직접 지정
워커를 늘릴수록 좋다는 생각이 가장 흔한 실수입니다. 워커 하나가 앱과 라이브러리를 통째로 메모리에 올립니다(Django 는 보통 100~300MB). 2GB 서버에 워커 16개를 띄우면 메모리가 터지거나 스왑으로 빠져 오히려 훨씬 느려집니다. 그리고 워커 수만큼 DB 커넥션이 늘어나 DB 쪽이 먼저 무너지는 경우도 많습니다 — 워커 수 × 커넥션 풀 크기가 DB 의 최대 접속 수를 넘지 않는지 반드시 확인하세요.
max_requests 는 파이썬 배포에서 특히 유용합니다. 라이브러리의 미묘한 누수로 메모리가 며칠에 걸쳐 서서히 오르는 일이 흔한데, 워커를 1000요청마다 교체하면 원인을 못 찾아도 운영은 안정됩니다. 근본 해결은 아니지만, 새벽에 OOM 으로 깨는 것보다는 훨씬 낫습니다. jitter 를 함께 주어 워커가 동시에 교체되지 않게 하는 것을 잊지 마세요.

import multiprocessing

# bind = "127.0.0.1:8000"

threads = 1                        # gthread 일 때만 의미가 있습니다

timeout = 30                       # 이 시간을 넘으면 워커를 죽이고 재시작
graceful_timeout = 30
keepalive = 5

# 메모리 누수 대비 — 일정 요청 수마다 워커를 재시작

max_requests_jitter = 100          # 동시에 재시작하지 않게 분산

accesslog = "-"                    # 표준 출력 (systemd·컨테이너 로그로)
errorlog  = "-"
loglevel  = "info"
access_log_format = '%(h)s %(l)s %(u)s %(t)s "%(r)s" %(s)s %(b)s "%(f)s" "%(a)s" %(L)s'

preload_app = True                 # 메모리 절약 (fork 전에 앱 로드)
# ※ preload 를 켜면 DB 커넥션을 fork 전에 만들면 안 됩니다

    listen 443 ssl;

    root /var/www/example/public;
    index index.php index.html;

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_read_timeout 60s;
        fastcgi_buffer_size 16k;
        fastcgi_buffers 8 16k;
    }

    # ★ 업로드 폴더에서 PHP 실행 금지 (매우 중요)

    # 숨김 파일 차단

}
업로드 폴더의 PHP 실행 차단은 필수입니다. 공격자가 shell.php 를 업로드하고 그것을 실행할 수 있으면 서버가 통째로 넘어갑니다. 워드프레스 침해의 전형적인 경로입니다.

pm.status_path = /fpm-status
pm.max_children 산정 — (가용 메모리 × 0.8) ÷ PHP 프로세스 하나의 평균 메모리
프로세스 메모리는 ps --sort -rss -eo rss,comm | grep php-fpm 로 확인합니다.
너무 크게 잡으면 스왑이 발생해 서버 전체가 느려집니다.

log_errors = On

SECTION 11

React · Vue 정적 배포

빌드하면 그냥 HTML·JS 파일 덩어리입니다. 앱 서버가 필요 없습니다. 

# 빌드
npm run build
# → dist/ 또는 build/ 폴더에 정적 파일이 생성됩니다

# 서버로 전송
rsync -avz --delete dist/ deploy@server:/var/www/spa/
server {
    listen 443 ssl;
    http2 on;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    root /var/www/spa;
    index index.html;

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;

    # ★ 해시가 붙은 빌드 산출물 — 영구 캐시
    location ~* \.[0-9a-f]{8,}\.(js|css|woff2?|png|jpe?g|svg|webp)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # ★ index.html 은 캐시 금지 (새 배포가 즉시 반영되게)
    location = /index.html {
        add_header Cache-Control "no-store, must-revalidate";
    }

    # ★ SPA 라우팅 — 없는 경로는 index.html 로
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 는 백엔드로
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
배포했는데 옛 화면이 보이는 이유 — index.html 이 캐시되면 새 JS 파일을 가리키는 링크 자체가 갱신되지 않습니다.
· 해시 붙은 파일(app.a1b2c3d4.js) → 영구 캐시 (내용이 바뀌면 이름이 바뀌므로 안전)
· index.html → 캐시 금지
이 조합이 프런트엔드 배포의 표준입니다.

Next.js 처럼 서버가 필요한 경우

# 완전 정적으로 내보낼 수 있으면 (SSG)
next build && next export      # → out/ 폴더를 그대로 서빙

# SSR·API 라우트를 쓴다면 Node 프로세스가 필요합니다
pm2 start npm --name web -- start
# → Nginx 가 3000 포트로 프록시 (l09 참고)
더 나은 선택 — CDN·정적 호스팅
순수 정적 SPA 라면 Cloudflare Pages · Netlify · Vercel · S3+CloudFront 같은 정적 호스팅이 더 빠르고 저렴합니다. 서버를 운영할 필요 자체가 없어집니다.
API 만 별도 서버에 두고 CORS 를 설정하는 구성이 요즘 흔합니다.
SECTION 12

systemd 서비스 등록

터미널을 닫아도 앱이 계속 돌게 하고, 서버가 재부팅돼도 자동으로 뜨게 만듭니다. 

# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
Documentation=https://github.com/me/myapp
After=network-online.target
Wants=network-online.target
# DB 가 같은 서버에 있다면
# After=postgresql.service

[Service]
Type=simple                      # simple · forking · notify · oneshot
User=appuser
Group=appuser
WorkingDirectory=/opt/myapp

Environment="NODE_ENV=production"
EnvironmentFile=/etc/myapp/env   # 비밀은 여기에 (권한 600)

ExecStartPre=/usr/bin/test -f /opt/myapp/app.js
ExecStart=/usr/bin/node /opt/myapp/app.js
ExecReload=/bin/kill -HUP $MAINPID

Restart=on-failure
RestartSec=5
StartLimitIntervalSec=60
StartLimitBurst=5                # 60초에 5번 실패하면 포기 (무한 재시작 방지)

TimeoutStopSec=30                # 종료 유예
KillSignal=SIGTERM

LimitNOFILE=65535                # 파일 디스크립터 한계

# 보안 강화 (선택이지만 권장)
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/log/myapp /var/data/myapp

StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapp

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload        # ★ 유닛 파일을 고칠 때마다
sudo systemctl enable --now myapp
sudo systemctl status myapp

sudo journalctl -u myapp -f          # 실시간 로그
sudo journalctl -u myapp --since "1 hour ago"
sudo journalctl -u myapp -p err      # 오류만
sudo journalctl -u myapp --no-pager -n 100

sudo systemctl restart myapp
sudo systemctl reload myapp          # ExecReload 가 정의돼 있어야 동작
Type언제
simpleExecStart 가 포그라운드로 계속 실행될 때 — 대부분 이것
forking프로세스가 백그라운드로 빠질 때 (톰캣 startup.sh)
notify앱이 준비 완료를 알려 줄 때 (Gunicorn)
oneshot한 번 실행하고 끝나는 작업
흔한 실수
· daemon-reload 를 안 함 — 유닛 파일을 고쳤는데 반영이 안 됩니다
· 상대 경로 사용 — ExecStart 는 절대 경로여야 합니다
· 환경 변수 부재 — 로그인 셸의 PATH·환경이 없습니다. 명시적으로 지정하세요
· 가상환경 미지정 — 파이썬은 venv/bin/ 안의 실행 파일을 절대 경로로
· 비밀번호를 ExecStart 인자로 — ps 로 누구나 볼 수 있습니다
SECTION 13

소켓 vs 포트 · 권한

같은 서버 안이라면 유닉스 소켓이 조금 더 빠르고 안전합니다.

TCP 포트
proxy_pass http://127.0.0.1:8000;

장점
· 설정이 단순
· 다른 서버로 옮기기 쉬움
· 디버깅이 쉬움 (curl 로 직접 호출)

단점
· TCP 스택을 거침 (약간의 오버헤드)
· 0.0.0.0 에 바인드하면 외부 노출 위험
유닉스 소켓
proxy_pass http://unix:/run/app/app.sock;

장점
· TCP 스택을 건너뜀 (약간 빠름)
· 네트워크로 노출될 수 없음 (구조적 안전)
· 파일 권한으로 접근 통제

단점
· 같은 서버 안에서만
· 권한 설정이 필요 (자주 막힙니다)
# 권한 문제 진단
ls -l /run/myapp/gunicorn.sock
# srw-rw---- 1 appuser www-data 0 Aug  5 14:00 gunicorn.sock
#             └ 소유자    └ 그룹 (Nginx 계정이 여기 있어야 합니다)

# Nginx 실행 계정 확인
ps aux | grep nginx | head -2

# Nginx 가 소켓을 읽을 수 있는지 직접 테스트
sudo -u www-data test -r /run/myapp/gunicorn.sock && echo OK || echo "권한 없음"
502 Bad Gateway + Permission denied 조합은 소켓 권한 문제입니다.
· 앱 프로세스의 그룹을 www-data 로 하거나
· UMask=0007 로 그룹 쓰기 권한을 주거나
· Gunicorn 에 --umask 007 옵션을 주세요
또 상위 폴더(/run/myapp)에도 접근 권한이 필요합니다. 
# systemd 로 소켓 폴더를 안전하게 관리
[Service]
User=appuser
Group=www-data                    # ★ Nginx 그룹
RuntimeDirectory=myapp            # /run/myapp 을 자동 생성 (서비스 종료 시 정리)
RuntimeDirectoryMode=0750
UMask=0007                        # 소켓이 660 으로 생성됩니다

SELinux 환경 (RHEL 계열)

# 권한이 다 맞는데도 502 라면 SELinux 를 의심하세요
sudo ausearch -m avc -ts recent | tail -20

# Nginx 가 네트워크로 프록시할 수 있게
sudo setsebool -P httpd_can_network_connect 1

# 유닉스 소켓 사용 허용
sudo setsebool -P httpd_can_network_relay 1

# 소켓 파일 컨텍스트
sudo semanage fcontext -a -t httpd_var_run_t "/run/myapp(/.*)?"
sudo restorecon -Rv /run/myapp
어느 쪽을 쓸까 — 같은 서버 + 성능이 중요하면 유닉스 소켓, 나중에 앱 서버를 분리할 가능성이 있거나 디버깅 편의가 중요하면 TCP. 성능 차이는 대부분의 서비스에서 체감되지 않으므로, 운영 편의로 결정해도 무방합니다.
SECTION 14

배포 체크리스트

언어와 무관하게 빠뜨리기 쉬운 항목을 모았습니다.

분류확인 항목
보안 앱이 127.0.0.1 에만 바인드돼 있나 (외부 직접 접근 차단)
비밀번호·키가 코드·명령줄이 아니라 환경 변수·파일에 있나 (권한 600)
디버그 모드가 꺼져 있나 (DEBUG=False · NODE_ENV=production)
오류 페이지에 스택 트레이스가 노출되지 않나
프록시 X-Forwarded-Proto 를 전달하고 앱이 인식하나
앱 로그에 실제 클라이언트 IP 가 찍히나
업로드 용량 제한을 웹서버와 앱 양쪽에 설정했나
정적 파일 웹서버가 직접 서빙하나 (앱을 거치지 않나)
해시 붙은 파일은 영구 캐시, index.html 은 캐시 금지인가
업로드 폴더에서 스크립트 실행이 차단돼 있나
프로세스 죽으면 자동 재시작되나 (systemd·PM2·컨테이너)
서버 재부팅 후 자동 시작되나 (systemctl enable)
우아한 종료가 설정돼 있나 (배포 시 요청 유실 방지)
로그 로그가 어디에 쌓이는지 알고 있나
로테이션이 설정돼 있나 (디스크 가득 참 방지)
응답 시간이 로그에 포함돼 있나
운영 헬스체크 엔드포인트가 있나 (/health)
인증서 자동 갱신과 만료 감시가 걸려 있나
설정 파일이 버전 관리되고 있나

배포 후 확인 명령

# 1) 서비스가 떴나
systemctl status myapp nginx

# 2) 포트가 열렸나 · 어디에 바인드됐나
sudo ss -lntp | grep -E ':80|:443|:3000|:8080'

# 3) 앱에 직접 요청 (프록시 문제인지 앱 문제인지 구분)
curl -sS http://127.0.0.1:3000/health

# 4) 전체 경로로 요청
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://example.com/health

# 5) 로그에 오류가 없나
sudo journalctl -u myapp --since "5 min ago" -p warning
sudo tail -50 /var/log/nginx/error.log

# 6) 인증서
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates
배포 스크립트로 만들어 두세요. 수동 배포는 매번 다르게 하게 되고, 실수하면 재현이 어렵습니다. 간단한 셸 스크립트라도 절차를 고정하면 사고가 크게 줄어듭니다. 나아가 CI/CD 파이프라인으로 옮기면 누가 언제 무엇을 배포했는지까지 남습니다.
