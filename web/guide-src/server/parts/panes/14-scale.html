SECTION 01

대규모의 기준 — 숫자 감각

"대규모 트래픽 경험"을 말하려면 먼저 숫자로 환산하는 감각이 필요합니다. 

DAU(하루 사용자)  →  평균 RPS 환산 감각

DAU 100만 · 1인당 하루 요청 50개
= 5,000만 요청/일 ÷ 86,400초 ≈ 평균 580 RPS

피크는 평균의 5~10배               →  3,000~6,000 RPS
이벤트(쿠폰 오픈)는 평균의 100배+  →  수만~수십만 RPS 가 몇 분에 집중

서버 한 대의 감각 (충분히 튜닝했을 때)
· Nginx 정적 파일        수만 RPS
· 백엔드 앱 (가벼운 API)  수백~수천 RPS
· DB 단순 조회            수천~수만 QPS · 쓰기는 훨씬 작음
대규모 설계의 제1원칙 — 안쪽(DB)을 지키기 위해 바깥(CDN·캐시)에서 끝낸다.
면접에서 숫자를 먼저 물으세요. "대규모 트래픽 처리 설계해 보세요"가 나오면 DAU·피크 RPS·읽기/쓰기 비율·응답 목표(p99)부터 확인하는 것이 시작입니다. 숫자 없이 아키텍처부터 그리면 과잉 설계로 흐릅니다 — 그 자체가 감점 포인트입니다.
SECTION 02

무상태 설계 — 확장의 전제

서버를 100대로 늘리려면 먼저 어느 대에 요청이 가도 같게 만들어야 합니다.

스티키 세션은 임시방편입니다 — 서버가 죽으면 그 세션은 끝. 상태 외부화가 정공법입니다.

서버 밖으로 빼야 하는 것들

상태보내는 곳
로그인 세션Redis (세션 스토어) — 또는 JWT 로 상태 자체를 토큰에
업로드 파일S3 · 오브젝트 스토리지 — 로컬 디스크 금지
캐시Redis — 로컬 캐시는 서버마다 달라져 정합성 문제 (x04)
스케줄 작업분산 락 또는 전용 워커 — 안 하면 N대가 같은 배치를 N번 돌립니다
순번·카운터Redis INCR · DB — 메모리 변수는 서버마다 따로 셉니다
세션 vs JWT — 세션(Redis)은 즉시 강제 로그아웃이 되지만 매 요청 조회가 필요하고, JWT 는 조회가 없지만 만료 전 무효화가 어렵습니다. 실무 절충: 수명 짧은 액세스 토큰(JWT) + 리프레시 토큰(서버 저장). "JWT 로그아웃 어떻게 처리하나요?"는 면접 단골입니다 — 블랙리스트 또는 짧은 만료가 답의 골격.
SECTION 03

캐시 계층 ① — 브라우저 · CDN

가장 빠른 요청은 서버에 도착하지 않는 요청입니다.

이벤트 페이지의 정답 — 페이지 전체를 정적으로 만들어 CDN 에 얹는 것. 서버는 열리는 순간의 API 만 받습니다.
# 원본(Nginx)에서 캐시 헤더 지정 — CDN 과 브라우저가 이것을 따릅니다
location /static/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location = /index.html {
    add_header Cache-Control "no-cache";          # 매번 재검증 (ETag 로 304)
}
location /api/products {
    add_header Cache-Control "public, s-maxage=30, stale-while-revalidate=60";
    # CDN 이 30초 캐시 — 상품 목록 API 부하가 1/N 로
}
개인화 응답을 CDN 에 태우면 사고입니다. Cache-Control: private 없는 "내 주문 목록"이 CDN 에 캐시되면 남의 주문이 보입니다 — 실제로 반복되는 유형의 사고입니다. 쿠키·Authorization 이 붙는 응답은 기본 private, no-store 로 두고, 캐시할 것만 명시적으로 여세요.
SECTION 04

캐시 계층 ② — Redis 패턴과 함정

DB 앞의 마지막 방패. 그리고 대규모 장애의 단골 출발점이기도 합니다. 

# Cache-Aside — 실무 표준 패턴
def get_product(pid):
    data = redis.get(f"product:{pid}")
    if data:                     # 히트 — DB 안 감
        return json.loads(data)
    row = db.query(...)          # 미스 — DB 조회
    redis.setex(f"product:{pid}", 300, json.dumps(row))   # TTL 필수!
    return row

# 쓰기 시 — 갱신하지 말고 지우세요 (다음 조회가 다시 채움)
def update_product(pid, ...):
    db.update(...)
    redis.delete(f"product:{pid}")   # 갱신(set)은 동시성 순서 꼬임 위험
TTL 에 지터(무작위 ±10%)를 더하는 것도 기본기 — 같은 시각 일괄 만료를 애초에 막습니다.

그 밖의 함정들

함정내용 · 해법
캐시 관통존재하지 않는 키(악의적 무작위 ID) 조회는 매번 DB 로 — "없음"도 짧게 캐시 · 블룸 필터
핫 키단일 키에 초당 수십만 조회 → Redis 한 노드 한계 — 로컬 캐시 1~2초를 앞에 겹칩니다
빅 키수 MB 값·수십만 원소 컬렉션 — 조회·삭제가 Redis 를 블로킹. 쪼개 두세요
전멸 대비Redis 가 통째로 죽으면 전 요청이 DB 로 — 그 순간의 DB 보호가 x07(유량 제어)입니다
무엇을 캐시하나 — 우선순위 공식. 조회 빈도 × 생성 비용 ÷ 변경 빈도가 큰 것부터. 상품 상세·랭킹·설정처럼 "많이 읽고, 만들기 비싸고, 가끔 변하는" 데이터가 1순위입니다. 잔액처럼 틀리면 안 되는 데이터는 캐시 대상이 아니라 DB 가 진실입니다.
SECTION 05

DB 확장 — 레플리카 · 샤딩

캐시로도 막을 수 없는 트래픽이 오면, 마지막 병목 DB 자체를 늘려야 합니다.

순서를 지키세요 — 인덱스·쿼리 튜닝 → 캐시 → 레플리카 → 파티셔닝 → 샤딩. 샤딩은 마지막입니다.

샤딩 전에 알아야 할 것

주제내용
샤드 키 선택대부분의 쿼리에 포함되는 키(회원ID·주문ID). 잘못 고르면 모든 샤드를 뒤지는 쿼리가 됩니다
해시 vs 범위해시 — 균등 분산·범위 조회 불리 / 범위 — 시계열 유리·최신 샤드 과열
크로스 샤드전체 집계·검색은 별도 경로로 — 통계 DB·검색 엔진에 CDC 로 복제해 처리 (📨 k07)
대안 먼저Vitess·Citus 같은 샤딩 미들웨어, 또는 처음부터 분산 DB — 직접 구현은 최후입니다
더 깊게 — 복제 지연의 원리와 대처는 🗄️ DB 가이드(MySQL 복제·심화 탭), 파티셔닝 vs 샤딩 구분도 그쪽에서 다룹니다. 여기서는 "언제 무엇을 꺼내 드는가"의 순서가 핵심입니다.
SECTION 06

큐로 피크 흡수 — 비동기 전환

"지금 다 처리"를 포기하면 10배의 피크가 평지가 됩니다.

면접 표현 — "쓰기 피크는 큐로 평탄화(leveling)하고, 사용자에게는 접수·완료를 나눠 알립니다."
선착순의 진실 — 선착순 쿠폰 1만 장의 정답 구조는 ① Redis 원자 연산(INCR·Lua)으로 순번만 즉시 판정 ② 당첨 요청만 큐로 넘겨 발급은 비동기 ③ DB 에는 워커가 차분히 기록. "DB 로 1만 동시 UPDATE" 를 피하는 것이 설계의 전부입니다. (x12 에서 전체 답안)
SECTION 07

유량 제어 — Rate Limit · 셰딩

한계는 반드시 옵니다. 전부 죽는 것과 일부를 거절하는 것 중에 골라야 합니다.

429 는 실패가 아니라 시스템을 지키는 설계된 응답입니다 — 전면 장애보다 백 배 낫습니다.

함께 쓰는 방어 도구

도구내용
부하 셰딩과부하 신호(큐 길이·p99)가 뜨면 덜 중요한 요청부터 즉시 거절 — 추천은 버리고 주문은 지킵니다
백프레셔"밀린다"는 신호를 상류로 전파해 유입 자체를 늦춥니다 — 무한 버퍼는 지연 폭탄일 뿐입니다 (🧬 z09)
대기열 시스템티켓팅의 "대기표" — 초과 유입을 순번 페이지에 세워 두고 처리량만큼만 입장시킵니다
기능 플래그비상시 무거운 기능(실시간 랭킹·추천)을 스위치로 끕니다 — 성능 예산을 핵심에 몰아주기
클라이언트 재시도까지 설계에 넣으세요. 429·503 을 받은 클라이언트가 즉시 재시도하면 부하는 배가 됩니다. 응답에 Retry-After 를 담고, 앱·웹 클라이언트는 지수 백오프 + 지터로 재시도하게 합니다 — 서버와 클라이언트가 한 팀으로 움직여야 진짜 방어입니다.
SECTION 08

오토스케일링 — 늘어나는 인프라

"미리 넉넉히"는 비용 낭비, "부족하면 수동 증설"은 새벽 호출입니다. 자동이 답입니다.

스케일링 신호는 CPU 만이 아닙니다 — 워커라면 큐 랙 기준(KEDA)이 훨씬 정확합니다 (x06).

현실 체크리스트

항목내용
급증은 못 따라갑니다새 파드 뜨는 데 수십 초~수 분 — 예고된 이벤트는 사전 증설(스케줄 스케일링)이 정답
하한을 두세요min replicas 를 피크 직전 수준으로 — 0→100 은 자동화로도 못 버팁니다
아래층도 함께앱만 늘면 DB 커넥션 풀이 곱해집니다 — 커넥션 수·캐시·DB 용량을 같이 계산
비용 상한max replicas + 비용 알람 — 오토스케일링 사고는 요금 고지서로 옵니다
서버리스(람다)는? 트래픽이 0↔폭증을 오가는 보조 기능(썸네일 생성·웹훅)에 좋습니다. 상시 대량 트래픽의 코어 API 는 컨테이너 + HPA 가 비용·지연 면에서 무난한 표준입니다. 콜드 스타트와 DB 커넥션 문제(프록시 필요)가 서버리스의 대표 함정입니다.
SECTION 09

규모별 아키텍처 견본 — 1만 · 10만 · 100만

동시 접속 규모마다 꺼내 드는 도구가 다릅니다. 한 장으로 정리합니다.

중요한 것은 순서입니다 — 1만 규모에 샤딩·MSA 를 꺼내는 것은 설계가 아니라 낭비입니다.
면접에서 이 그림을 쓰는 법 — 요구 숫자를 확인하고(x01), 해당 열의 구성으로 시작해 "병목이 관측되면 다음 도구를 추가한다"는 진화 서사로 설명하세요. 처음부터 100만 아키텍처를 그리는 것보다 단계별 확장 근거를 말하는 쪽이 항상 높은 평가를 받습니다.
SECTION 10

부하 테스트 — 한계를 미리 잰다

"몇 RPS 까지 버티나요?"에 측정값으로 답하는 사람과 감으로 답하는 사람의 차이입니다. 

// k6 — 코드로 쓰는 부하 테스트 (설치: brew/choco install k6)
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "2m", target: 200 },    // 2분에 걸쳐 200 VU 까지 증가
    { duration: "5m", target: 200 },    // 5분 유지 — 안정 구간 관측
    { duration: "2m", target: 1000 },   // 피크 시나리오
    { duration: "2m", target: 0 },      // 회복 관측 (이것도 중요!)
  ],
  thresholds: {
    http_req_duration: ["p(99)<500"],   // p99 500ms 넘으면 실패 처리
    http_req_failed:   ["rate<0.01"],   // 에러율 1% 미만
  },
};

export default function () {
  const res = http.get("https://stage.example.com/api/products?page=1");
  check(res, { "200": (r) => r.status === 200 });
  sleep(1);   // 실제 사용자처럼 간격 — 없으면 비현실적 최대치만 나옵니다
}

읽는 법 — 평균은 버리고 꼬리를 봅니다

지표의미
p50 / p99평균 80ms 여도 p99 가 3초면 100명 중 1명은 3초 — 사용자 경험은 꼬리가 정합니다
무릎점부하를 올리다 지연이 급격히 꺾이는 지점 — 그 직전이 실용 한계 용량입니다
에러율 변화어느 RPS 부터 5xx·타임아웃이 시작되나 — 그때 어느 자원(CPU·풀·DB)이 먼저 소진됐는지가 병목
회복부하를 내렸을 때 정상으로 돌아오나 — 못 돌아오면(풀 고갈·좀비 커넥션) 더 심각한 문제입니다
테스트의 3원칙. ① 운영과 같은 구성의 스테이징에서 (캐시 끈 로컬 테스트는 무의미) ② 시나리오는 실제 트래픽 믹스로 (조회 90 : 쓰기 10, 로그인 흐름 포함) ③ 병목을 하나 고치면 다음 병목이 나타납니다 — 측정→개선→재측정의 반복이 튜닝입니다 (⚡ 성능 탭 p13).
도구 선택 — k6(코드 기반·CI 통합, 추천) · JMeter(GUI·레거시 표준) · nGrinder(네이버 오픈소스, 국내 기업 채용공고 단골) · wrk(단일 URL 최대치 측정). 이력서에는 도구 이름보다 "p99 를 몇에서 몇으로, 무엇을 고쳐서"가 백 배 강합니다.
SECTION 11

폭주 당일 — 운영 시나리오

설계가 끝이 아닙니다. 이벤트 D-day 를 어떻게 준비하고 넘기는가가 진짜 경험입니다.
