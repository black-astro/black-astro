K8S 01

컨테이너가 푸는 문제 — "제 PC 에서는 됐는데요"

기술을 배우기 전에 어떤 고통을 없애려고 만든 물건인지부터 봅니다. 이걸 모르면 도커는 그냥 "명령어 외우기"가 됩니다.

컨테이너의 한 줄 정의 — 앱 + 그 아래 실행 환경을 한 파일로 묶어 통째로 옮기는 것.

VM 과 컨테이너 — 무엇이 진짜 다른가

가상 머신(VM)은 가짜 하드웨어 위에 운영체제를 통째로 하나 더 올립니다. 커널·부팅 과정·systemd 가 전부 따로라 기동에 수십 초가 걸리고 메모리도 GB 단위로 먹습니다. 컨테이너는 호스트의 커널을 그대로 빌려 쓰면서, 프로세스에게 "너만의 세상"으로 보이게 속이는 기술입니다. 커널이 새로 뜨지 않으니 기동이 수십 밀리초입니다.

교환 조건 — 컨테이너는 가볍지만 커널을 공유합니다. 커널 취약점 하나면 격리가 뚫릴 수 있습니다.

속이는 방법 — 네임스페이스 · cgroup 🟡 중급

"컨테이너"라는 리눅스 기능은 존재하지 않습니다. 커널 기능 세 개를 조합해 프로세스 하나를 격리한 결과에 붙인 이름일 뿐입니다. 이걸 알면 docker exec 로 들어갔을 때 왜 프로세스가 몇 개 안 보이는지, 왜 컨테이너 안에서 free -m 이 호스트 전체 메모리를 보여 주는지가 설명됩니다.

커널 기능하는 일
네임스페이스
(namespace)		"안 보이게" 합니다. pid 네임스페이스를 나누면 컨테이너 안 첫 프로세스가 PID 1 이 되고 호스트의 다른 프로세스는 아예 보이지 않습니다. net(네트워크 인터페이스)·mnt(파일시스템)·uts(호스트명)·ipc·user 도 각각 나뉩니다
cgroup
(control group)		"못 넘게" 합니다. CPU·메모리·디스크 I/O 사용량에 상한을 걸고 초과하면 스로틀하거나 죽입니다. 쿠버네티스의 limits 가 결국 이 값으로 내려갑니다(d10)
오버레이 FS
(overlayfs)		"쌓아서 겹쳐" 보이게 합니다. 읽기 전용 이미지 레이어 여러 장 위에 쓰기 가능한 얇은 층 한 장을 얹어 하나의 파일시스템처럼 보여 줍니다 — 이미지 레이어의 정체입니다(d02·d03)
capabilities
seccomp · AppArmor		"못 하게" 합니다. root 라도 커널 모듈 적재·시간 변경 같은 위험한 시스템 콜을 막습니다. 컨테이너 보안의 기본선입니다
# 컨테이너가 "그냥 프로세스"라는 증거 — 호스트에서 그대로 보입니다
docker run -d --name demo nginx:1.29
ps -ef | grep nginx        # 호스트의 프로세스 목록에 nginx 가 그대로 있습니다

# 컨테이너 안에서 본 프로세스 — 자기 자신뿐 (pid 네임스페이스)
docker exec demo ps -ef
# PID 1 이 nginx 입니다. 호스트의 systemd·sshd 는 존재조차 보이지 않습니다

# cgroup 상한 확인 — 512MB 를 걸면 커널이 그 값을 들고 있습니다
docker run -d --name lim --memory 512m nginx:1.29
docker exec lim cat /sys/fs/cgroup/memory.max      # 536870912

# 주의 — free 는 cgroup 을 모릅니다. 호스트 전체를 보여 줍니다
docker exec lim free -m    # 컨테이너 상한이 아니라 호스트 메모리가 나옵니다
PID 1 의 함정 — 컨테이너가 Ctrl+C 로 안 죽는 이유. 리눅스에서 PID 1 은 시그널 기본 동작이 없습니다. 애플리케이션이 SIGTERM 핸들러를 등록하지 않으면 종료 신호를 그냥 무시하고, 10초 뒤 SIGKILL 로 강제 종료됩니다 — 처리 중이던 요청이 통째로 날아갑니다. 쿠버네티스의 무중단 배포가 안 되는 흔한 원인이 바로 이것입니다(d09).
해법 ① 앱이 SIGTERM 을 받아 graceful shutdown 하도록 구현 ② 그게 어려우면 docker run --init 또는 Dockerfile 에 tini 를 넣어 시그널을 대신 중계하게 합니다.

이미지와 컨테이너 — 클래스와 인스턴스

이미지 (image)

읽기 전용 템플릿입니다. 레이어 여러 장 + 메타데이터(시작 명령·환경 변수·포트)로 되어 있고, 내용의 해시가 곧 신원(sha256:...)입니다. 한 번 만들면 절대 바뀌지 않습니다 — 고치려면 새로 빌드해 새 이미지를 만듭니다.

비유 — 자바의 class, 파이썬의 클래스 정의.

컨테이너 (container)

이미지를 실행한 상태입니다. 이미지 레이어 위에 쓰기 가능한 얇은 층 한 장이 얹히고, 그 안에서 벌어진 변경(로그 파일·임시 파일)은 전부 그 층에 쌓입니다. 컨테이너를 지우면 그 층이 통째로 사라집니다 — 데이터가 날아가는 이유입니다(d02 볼륨).

비유 — new 로 만든 인스턴스. 하나의 이미지에서 100개를 띄울 수 있습니다.

언제 컨테이너를 안 쓰는 게 나은가 🟡 중급

도입 결정에서 가장 중요한 질문입니다. 컨테이너는 공짜가 아니라 빌드 파이프라인 · 레지스트리 · 이미지 관리 · 새 장애 유형이라는 비용을 청구합니다.

안 쓰는 게 나은 상황
  • 서버 1대 · 앱 1개 · 배포 월 1회 — systemd 서비스 하나가 훨씬 단순합니다(🔗 언어 연동 l12)
  • 커널 기능에 깊게 의존 — 특수 드라이버·커널 모듈·실시간 스케줄링
  • GPU·특수 하드웨어를 독점 사용 — 되긴 하지만 설정 비용이 큽니다
  • 상태 있는 DB 를 직접 운영 — 컨테이너로 못 하는 건 아니지만, 관리형 DB 나 전용 서버가 사고 확률이 낮습니다
  • 팀에 아무도 컨테이너를 모름 + 마감이 다음 주 — 배울 시간이 없으면 장애 대응이 불가능합니다
쓰면 확실히 이득인 상황
  • 서비스가 2개 이상이고 각각 다른 런타임 버전을 씀
  • 배포가 잦음(주 1회 이상) — 롤백이 이미지 태그 교체로 끝납니다
  • 서버가 여러 대 — 서버마다 손으로 설치하는 순간 환경이 갈라집니다
  • CI 에서 테스트를 돌림 — 테스트 환경 = 운영 환경이 됩니다
  • 오토스케일이 필요 — 대수를 늘리는 단위가 있어야 자동화가 가능합니다(d10)
  • 신입이 자주 들어옴 — docker compose up 하나로 온보딩이 끝납니다
중간 단계도 있습니다. "컨테이너는 쓰되 쿠버네티스는 안 쓰기"가 아주 흔하고 합리적인 선택입니다. 서버 1~3대라면 Docker Compose + 리버스 프록시(d04)로 충분하고, 그다음 단계가 필요해지면 관리형 쿠버네티스(EKS·GKE·NKS)로 갑니다. 쿠버네티스는 서비스 수 · 서버 수 · 배포 빈도가 셋 다 늘었을 때 값을 합니다(d06).
K8S 02

도커 기본기 — run · ps · logs · exec

명령 여섯 개면 컨테이너의 일생을 전부 다룰 수 있습니다. 나머지는 이 여섯 개의 옵션일 뿐입니다.

외울 문장 — 컨테이너의 쓰기 층은 임시입니다. 남아야 할 것은 전부 볼륨으로 빼세요.

명령 여섯 개 — 이것만으로 90% 가 됩니다

# ① run — 만들고 바로 실행. 가장 많이 치는 명령
docker run -d --name api -p 8080:3000 \
  -e NODE_ENV=production -e TZ=Asia/Seoul \
  -v api-data:/app/data \
  --restart unless-stopped \
  ghcr.io/myorg/api:1.4.2
#   -d   백그라운드(detached). 빼면 터미널이 붙잡힙니다
#   -p   호스트포트:컨테이너포트  ← 순서를 뒤집는 실수가 가장 흔합니다
#   -e   환경 변수 주입
#   -v   볼륨 연결 (이름있는볼륨:컨테이너경로)
#   --restart unless-stopped   서버 재부팅 후에도 자동 기동

# ② ps — 지금 뭐가 돌고 있나
docker ps                       # 실행 중만
docker ps -a                    # 멈춘 것까지 전부 (디스크 먹는 범인 찾기)
docker ps --format '{{.Names}} · {{.Status}} · {{.Ports}}'

# ③ logs — 첫 번째 진단 도구
docker logs -f --tail 100 api           # 실시간으로 마지막 100줄부터
docker logs --since 10m api             # 최근 10분만
docker logs api 2>&1 | grep -i error    # 표준 에러까지 합쳐서 검색

# ④ exec — 돌고 있는 컨테이너 안으로 들어가기
docker exec -it api sh          # alpine 계열은 bash 가 없어 sh
docker exec api env             # 환경 변수가 제대로 들어갔는지 확인
docker exec api cat /etc/hosts  # 명령만 실행하고 나오기

# ⑤ stop / start / restart
docker stop api                 # SIGTERM → 10초 대기 → SIGKILL
docker stop -t 30 api           # 종료에 30초까지 기다려 주기
docker restart api

# ⑥ rm / rmi — 지우기
docker rm api                   # 멈춘 컨테이너 삭제
docker rm -f api                # 돌고 있어도 강제 삭제
docker rmi ghcr.io/myorg/api:1.4.2
포트 매핑의 방향을 헷갈리지 마세요. -p 8080:3000 은 "호스트의 8080 으로 들어오면 컨테이너의 3000 으로 보내라"입니다. 왼쪽이 밖, 오른쪽이 안입니다. 그리고 컨테이너 안의 앱이 127.0.0.1:3000 에 바인딩하면 밖에서 절대 못 들어옵니다 — 컨테이너의 localhost 는 호스트의 localhost 가 아니기 때문입니다. 반드시 0.0.0.0:3000 으로 리스닝해야 합니다. 이건 신입이 반드시 한 번 겪습니다.

  tar czf /backup/pgdata-$(date +%F).tgz -C /data .

# 복원
docker run --rm -v pgdata:/data -v "$PWD":/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/pgdata-2026-08-01.tgz -C /data"

디스크가 찼습니다 — docker system prune 🟡 중급

도커를 쓰는 서버에서 가장 흔한 장애가 디스크 풀입니다. 빌드할 때마다 옛 이미지 레이어·중간 캐시·멈춘 컨테이너·고아 볼륨이 쌓이는데 아무도 지워 주지 않습니다. CI 서버는 며칠이면 100GB 를 먹습니다. 

# 무엇이 얼마나 먹고 있나 — 진단이 먼저
docker system df
docker system df -v            # 이미지별·볼륨별 상세

# 안전한 청소 (멈춘 컨테이너 · 안 쓰는 네트워크 · dangling 이미지 · 빌드 캐시)
docker system prune -f

# 태그 없는 것뿐 아니라 "아무 컨테이너도 안 쓰는 이미지" 까지 (주의)
docker system prune -a -f

# 볼륨까지 (★★ 위험 — DB 데이터가 날아갈 수 있습니다)
docker system prune -a --volumes -f

# 실무 타협안 — 168시간(7일) 넘은 것만 정리. cron 에 걸어 둡니다
docker system prune -af --filter "until=168h"
docker builder prune -af --filter "until=168h"
--volumes 는 손이 떨려야 정상입니다. "아무 컨테이너도 참조하지 않는 볼륨"을 지우는데, 컨테이너를 잠깐 지우고 다시 만드는 중이었다면 그 볼륨은 고아로 판정됩니다. 운영 서버 DB 볼륨이 이렇게 날아간 사례가 실제로 있습니다. 운영에서는 --volumes 없이 돌리고, 볼륨은 docker volume ls -f dangling=true 로 눈으로 확인한 뒤 하나씩 지우세요.

쿠버네티스는 2022년(1.24)에 도커 지원을 뗐습니다 — 그런데 왜 도커 이미지가 돌까요? 떼어 낸 것은 도커 데몬을 통해 컨테이너를 실행하던 중간 다리(dockershim)이지 이미지 형식이 아닙니다. 이미지는 OCI 표준이라 도커로 빌드한 이미지를 containerd 가 그대로 실행합니다. "도커가 죽었다"는 말은 오해입니다 — 빌드는 도커로, 실행은 containerd 로가 지금의 표준 조합입니다.
웹서버 컨테이너를 실제로 띄우는 실습은 이 가이드 🧭 시작 w05 에 Nginx·Apache·Tomcat·Caddy 예제로 이미 있습니다. 여기서는 내 애플리케이션을 이미지로 만드는 것(d03)부터 이어 갑니다.
K8S 03

Dockerfile 잘 쓰기 — 캐시와 멀티스테이지

"돌아가는 Dockerfile"은 10분이면 씁니다. 문제는 그게 빌드 5분 · 이미지 1.1GB 라는 것입니다. 줄 순서만 바꿔도 빌드 20초 · 이미지 186MB 가 됩니다.

Dockerfile 최적화의 8할 — 의존성 설치와 소스 복사를 분리하는 것 하나입니다.

멀티스테이지 빌드 — 빌드 도구를 결과물에서 지우기 🟡 중급

컴파일러·빌드 도구·테스트 라이브러리는 빌드할 때만 필요하고 실행할 때는 쓰레기입니다. 그런데 한 스테이지로 만들면 그게 전부 최종 이미지에 남습니다 — JDK 포함 이미지가 1.14GB 인 이유입니다. 멀티스테이지는 빌드 결과물만 깨끗한 이미지로 복사합니다.

멀티스테이지의 진짜 이득은 크기가 아니라 공격 표면 축소입니다 — 셸도 없는 이미지가 목표입니다.

Java (Spring Boot) — 계층 분리까지

# syntax=docker/dockerfile:1
FROM gradle:8.10-jdk21 AS builder
WORKDIR /src
# ① 의존성 목록만 먼저 — 캐시가 살아남습니다
COPY build.gradle settings.gradle ./
RUN gradle dependencies --no-daemon || true
# ② 소스는 그다음
COPY src ./src
RUN gradle bootJar --no-daemon -x test

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
# ③ 비루트 사용자 — root 로 돌리지 않습니다
RUN addgroup -S app && adduser -S -G app app
COPY --from=builder /src/build/libs/*.jar app.jar
USER app
EXPOSE 8080
# ④ exec 형식(대괄호)이어야 SIGTERM 이 앱까지 갑니다
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-jar","/app/app.jar"]
MaxRAMPercentage — JVM 은 컨테이너 메모리 상한을 인식합니다(Java 10+). 고정 -Xmx 대신 비율로 주면 리소스 조정 시 같이 따라옵니다(d10).

Python — 가상환경을 통째로 옮기기

# syntax=docker/dockerfile:1
FROM python:3.13-slim AS builder
WORKDIR /app
ENV PIP_NO_CACHE_DIR=1
# 컴파일이 필요한 패키지용 빌드 도구 (최종 이미지엔 안 남습니다)
RUN apt-get update && apt-get install -y --no-install-recommends \
      build-essential && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN python -m venv /opt/venv && \
    /opt/venv/bin/pip install -r requirements.txt

FROM python:3.13-slim
ENV PATH=/opt/venv/bin:$PATH \
    PYTHONUNBUFFERED=1          # ★ 로그가 안 나오는 원인 1위
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY app ./app
RUN useradd -u 10001 -m app

CMD ["gunicorn","-w","4","-k","uvicorn.workers.UvicornWorker",
     "-b","0.0.0.0:8000","app.main:app"]
PYTHONUNBUFFERED=1 은 필수입니다. 없으면 파이썬이 stdout 을 버퍼링해 docker logs 에 아무것도 안 나옵니다 — "앱이 죽은 줄 알았는데 로그만 안 나온" 사고가 흔합니다.

WORKDIR /src

COPY src ./src
# ★ 캐시 마운트 — 레이어에는 안 남지만 빌드 간에 유지됩니다

    mvn -B package -DskipTests

RUN --mount=type=secret,id=npmtoken \
    NPM_TOKEN=$(cat /run/secrets/npmtoken) npm ci
# 빌드와 크기 실측 — 개선했다고 말하려면 숫자가 있어야 합니다
docker build -t api:before -f Dockerfile.old .
docker build -t api:after  .
docker images api --format '{{.Tag}} · {{.Size}}'
#  before · 1.14GB
#  after  · 186MB

# 이미지 안에 뭐가 들었나 — 레이어별 크기
docker history api:after --no-trunc | head -20

# 시크릿이 레이어에 남았는지 검사 (dive · 또는 tar 로 풀어서)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive:latest api:after

# 멀티 아키텍처 빌드 (Apple Silicon 개발 → x86 서버 배포)
docker buildx build --platform linux/amd64,linux/arm64 \

정리 — Dockerfile 은 순서(캐시) · 스테이지 분리(크기) · 비루트(보안) · exec 형식 ENTRYPOINT(종료) 네 가지만 지키면 실무 수준입니다.
K8S 04

Docker Compose — 여러 컨테이너를 한 번에

앱 하나만 컨테이너로 만들면 별 이득이 없습니다. 앱 + DB + 캐시 + 프록시가 up -d 한 줄로 뜨는 순간부터 세상이 달라집니다.

compose 의 핵심 두 가지 — 서비스 이름 = DNS 이름, ports 는 진짜 외부에 열 것만.

완본 — 앱 + PostgreSQL + Redis + Nginx

# compose.yaml  (예전 이름 docker-compose.yml 도 그대로 동작합니다)
name: myapp

services:
  proxy:
    image: nginx:1.29-alpine
    ports:
      - "80:80"                       # ★ 밖으로 여는 유일한 포트
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      app:
        condition: service_healthy    # 앱이 "건강"해진 뒤에 뜹니다
    restart: unless-stopped

  app:
    build:
      context: .
      dockerfile: Dockerfile
      target: prod                    # 멀티스테이지의 특정 스테이지 지정
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/appdb
      REDIS_URL: redis://redis:6379/0
      TZ: Asia/Seoul
    expose:
      - "3000"                        # 네트워크 안에서만 열림
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 30s               # ★ 기동이 느린 앱은 이걸 넉넉히
    restart: unless-stopped

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./initdb:/docker-entrypoint-initdb.d:ro   # 최초 1회 실행 SQL
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:
depends_on 만으로는 부족합니다. 기본 depends_on 은 "컨테이너가 시작됐다"까지만 보장합니다 — PostgreSQL 프로세스가 뜨는 것과 접속을 받을 준비가 되는 것은 다릅니다. 그래서 앱이 먼저 붙었다가 connection refused 로 죽는 일이 생깁니다. condition: service_healthy + 대상의 healthcheck 를 짝으로 써야 진짜 순서가 보장됩니다. 그래도 앱 쪽에 재시도 로직은 넣어 두세요 — 쿠버네티스에는 depends_on 자체가 없습니다(d09).

.gitignore 에 .env 를 넣었는지 지금 확인하세요. 유출 사고의 절반이 여기서 납니다.

개발용과 운영용 분리 — override 파일 🟡 중급

개발에서는 소스를 바인드 마운트해 저장하면 바로 반영되게 하고, 운영에서는 이미지를 고정하고 소스를 마운트하지 않습니다. 같은 파일을 두 벌 관리하면 반드시 어긋나므로 기본 + 덮어쓰기 구조를 씁니다.

compose.override.yaml (개발 · 자동 적용)

# up 할 때 자동으로 합쳐집니다 — 개발자는 아무것도 안 해도 됩니다
services:
  app:
    build:
      target: dev                 # 개발 스테이지
    command: ["npm", "run", "dev"]
    volumes:
      - ./src:/app/src            # 코드 즉시 반영
    environment:
      LOG_LEVEL: debug
    ports:
      - "3000:3000"               # 프록시 우회 직접 접속(디버깅용)
  db:
    ports:
      - "5432:5432"               # DB 툴로 직접 붙기 (개발에서만!)

compose.prod.yaml (운영 · 명시 지정)

services:
  app:
    image: ghcr.io/myorg/api:${APP_IMAGE_TAG}   # 빌드 안 함 — 이미지 고정
    build: !reset null
    deploy:
      resources:
        limits: { cpus: "1.0", memory: 512M }
    logging:
      driver: json-file
      options: { max-size: "20m", max-file: "5" }   # ★ 로그 로테이션
# 운영에서는 override 를 끄고 prod 파일을 명시합니다
docker compose -f compose.yaml -f compose.prod.yaml up -d

# 배포 = 태그 바꾸고 다시 up
APP_IMAGE_TAG=1.4.3 docker compose \
  -f compose.yaml -f compose.prod.yaml up -d
로그 로테이션을 빼면 json-file 드라이버가 무한히 커져 디스크를 다 먹습니다. 운영 compose 의 필수 항목입니다.

볼륨 백업 — 컨테이너를 지워도 데이터가 남게

#!/bin/sh
# backup.sh — cron 에 매일 03:00 으로 걸어 둡니다
set -eu
DATE=$(date +%F)
OUT=/backup

# ① DB 는 파일 복사 말고 논리 덤프로 (파일 복사는 깨질 수 있습니다)
docker compose exec -T db pg_dump -U app -Fc appdb > "$OUT/appdb-$DATE.dump"

# ② 업로드 파일 볼륨은 tar
docker run --rm -v myapp_uploads:/data -v "$OUT":/backup alpine \
  tar czf "/backup/uploads-$DATE.tgz" -C /data .

# ③ 7일 지난 백업 삭제
find "$OUT" -name '*.dump' -mtime +7 -delete
find "$OUT" -name '*.tgz'  -mtime +7 -delete

# ④ ★ 복원 테스트를 안 한 백업은 백업이 아닙니다 — 월 1회는 실제로 복원해 보세요
# docker compose exec -T db pg_restore -U app -d appdb_test < appdb-2026-08-01.dump
compose 로 어디까지 갈 수 있나. 서버 1~2대 · 서비스 5개 이하 · 배포 주 1~2회 규모는 compose + Nginx + 백업 스크립트로 몇 년을 무리 없이 운영합니다. 한계가 오는 지점은 명확합니다 — ①서버가 죽으면 수동 복구 ②배포 중 다운타임 ③트래픽 급증에 수동 증설 ④서버 여러 대에 걸친 배치. 이 넷 중 둘 이상이 아프면 그때가 쿠버네티스를 볼 때입니다(d06).
정리 — compose 는 서비스 이름 DNS · healthcheck 로 순서 · .env 로 비밀 분리 · override 로 환경 분리 네 개면 실무에서 씁니다. 이 개념이 그대로 쿠버네티스로 이어집니다.

K8S 06

쿠버네티스 개념 지도 — 왜 필요한가

명령을 외우기 전에 이 물건이 무슨 문제를 대신 풀어 주는지부터 봅니다. 한 문장으로 줄이면 — "원하는 상태를 적어 두면 계속 그렇게 맞춰 주는 기계"입니다.

한 문장 정의 — 쿠버네티스는 "원하는 상태"와 "현재 상태"의 차이를 끝없이 메우는 루프입니다.

클러스터의 구조 — 컨트롤 플레인과 노드

모든 것은 API 서버를 통합니다 — 사용자도, 컨트롤러도, kubelet 도 전부 API 서버에게 말을 겁니다.
구성 요소하는 일죽으면
API 서버모든 요청의 유일한 입구. 인증·인가·검증 후 etcd 에 기록새 배포·조회 불가. 이미 도는 파드는 계속 돕니다
etcd클러스터의 모든 상태를 담은 키·값 저장소. 여기가 진실클러스터가 사실상 마비. 백업이 생명줄입니다
스케줄러새 파드를 어느 노드에 놓을지 결정(리소스·제약 고려, d10)새 파드가 Pending 에서 안 움직입니다

kubelet노드마다 하나. 자기 노드의 파드를 띄우고 상태·프로브를 보고그 노드가 NotReady → 파드가 다른 노드로 옮겨집니다

kind: Deployment
metadata:
  name: api
  labels: { app: api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }        # ★ 이 라벨로 파드를 소유합니다 (나중에 못 바꿉니다)
  template:                          # ↓ 여기부터가 "파드 설계도"
    metadata:
      labels: { app: api }           # ★ selector 와 반드시 일치
    spec:
      containers:
        - name: api
          image: ghcr.io/myorg/api:1.4.2

            - containerPort: 3000

            - name: TZ
              value: Asia/Seoul
          resources:                 # ★ 없으면 스케줄링·안정성이 무너집니다 (d10)
            requests: { cpu: 100m, memory: 256Mi }
            limits:   { memory: 512Mi }
          readinessProbe:            # 준비되기 전엔 트래픽을 안 받습니다 (d09)
            httpGet: { path: /healthz/ready, port: 3000 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz/live, port: 3000 }
            periodSeconds: 10
            failureThreshold: 3
          securityContext:           # 보안 기본선
            runAsNonRoot: true
            runAsUser: 10001
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true

      volumes:
        - name: tmp
          emptyDir: {}               # readOnlyRootFilesystem 을 켜면 /tmp 가 필요합니다
# k8s/service.yaml — 파드들에게 "바뀌지 않는 주소"를 줍니다
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP                    # 기본값 — 클러스터 안에서만 보임
  selector:
    app: api                         # ★ 이 라벨을 가진 파드로 보냅니다
  ports:
    - name: http
      port: 80                       # 서비스가 받는 포트
      targetPort: 3000               # 파드가 듣는 포트
---
# k8s/ingress.yaml — 클러스터 밖 → 안으로 들어오는 문
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "20m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
spec:
  ingressClassName: nginx
  rules:

        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api

핵심 — Service 의 대상 목록은 "Ready 인 파드"입니다. readiness 프로브가 곧 트래픽 스위치입니다.

Service 타입 네 가지 — 언제 뭘 쓰나

타입동작쓰는 곳
ClusterIP클러스터 내부 전용 가상 IP. 기본값거의 항상 이것. 앱끼리의 통신은 전부 ClusterIP
NodePort모든 노드의 같은 포트(30000~32767)를 열어 전달로컬 실습·임시 확인. 운영에는 부적합(포트 번호가 지저분하고 노드 IP 노출)
LoadBalancer클라우드에 실제 로드밸런서를 생성하고 공인 IP 를 붙임클라우드에서 외부 노출. 서비스마다 LB 가 생겨 비용이 붙습니다 → 그래서 Ingress 하나로 모읍니다
Headless
(clusterIP: None)		가상 IP 없이 DNS 가 파드 IP 목록을 직접 반환StatefulSet(d08)·Kafka·DB 클러스터처럼 개별 파드를 직접 지목해야 할 때
Ingress 는 왜 따로 있나. 서비스가 20개인데 전부 LoadBalancer 로 열면 클라우드 LB 가 20개 생기고 요금도 20배입니다. Ingress 는 LB 하나 뒤에 L7 라우터(nginx) 한 벌을 두고 도메인·경로로 나눠 보냅니다. 이 가이드의 🟩 Nginx 탭에서 배운 server·location 개념이 그대로 host·path 로 옮겨온 것뿐입니다. (Nginx 설정과의 1:1 대응표는 🛡️ 보안·운영 o11 에 있습니다.)

첫날 반드시 겪는 실수 세 가지. ① selector 와 template.metadata.labels 불일치 — 파드는 뜨는데 Service 엔드포인트가 비어 502 가 납니다. ② targetPort 를 앱이 실제 듣는 포트와 다르게 씀 — connection refused. ③ 앱이 127.0.0.1 에 바인딩 — 파드 밖에서 못 붙습니다. 0.0.0.0 으로 리스닝해야 합니다(d02와 같은 함정).

"DB 를 쿠버네티스에 올릴 것인가"는 신중히 결정하세요. StatefulSet 으로 PostgreSQL 을 띄우는 것 자체는 어렵지 않습니다. 어려운 것은 백업·복원·페일오버·버전 업그레이드·디스크 확장입니다. 팀에 전담 인력이 없다면 관리형 DB(RDS·Cloud SQL) 를 쓰고 앱만 쿠버네티스에 올리는 조합이 사고 확률이 훨씬 낮습니다. 꼭 클러스터 안에 둬야 한다면 오퍼레이터(CloudNativePG · Strimzi)를 쓰세요 — 백업·페일오버가 코드로 들어 있습니다.
ConfigMap 을 고쳤는데 반영이 안 됩니다. 환경 변수로 주입했다면 정상 동작입니다 — 프로세스 시작 시 값이 복사되기 때문입니다. 해법은 ① 파일 마운트로 바꾸고 앱이 다시 읽게 하거나 ② ConfigMap 내용의 해시를 파드 어노테이션에 넣어 내용이 바뀌면 파드가 새로 뜨게 하는 것입니다. Helm 에서는 checksum/config 어노테이션 패턴으로 씁니다(d12). 급하면 kubectl rollout restart deploy/api 로 무중단 재시작합니다.
정리 — 이미지는 하나, 설정은 환경마다가 원칙입니다. 평문은 ConfigMap, 비밀은 외부 저장소 참조, 남아야 할 데이터는 PVC — 이 세 갈래로 나누면 환경 이동이 쉬워집니다.

무중단 배포 · 프로브 제대로 쓰기

"쿠버네티스를 쓰면 무중단"이 아닙니다. 프로브 세 개와 종료 처리를 제대로 쓸 때만 무중단입니다. 대부분의 배포 중 502 는 여기 설정이 틀려서 납니다.

한 줄 원칙 — readiness 는 넉넉하게 자주, liveness 는 보수적으로 드물게.

프로브 설정 — 실전 값

containers:
  - name: api
    # ① 기동 보호 — 최대 5분(6초 × 50회)까지 기다립니다
    startupProbe:
      httpGet: { path: /healthz/live, port: 3000 }
      periodSeconds: 6
      failureThreshold: 50
    # ② 트래픽 스위치 — 자주 확인, 빨리 빼고 빨리 넣기
    readinessProbe:
      httpGet: { path: /healthz/ready, port: 3000 }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3          # 15초 이상 나쁘면 제외
      successThreshold: 1
    # ③ 최후 수단 — 관대하게
    livenessProbe:
      httpGet: { path: /healthz/live, port: 3000 }
      periodSeconds: 15
      timeoutSeconds: 3
      failureThreshold: 5          # 75초 넘게 먹통일 때만 재시작
gRPC · TCP 도 됩니다. grpc: { port: 9090 } 또는 tcpSocket: { port: 5432 }. 명령 실행형 exec 는 비용이 크니 꼭 필요할 때만.

// /healthz/live — 프로세스가 살아 있나. 의존성은 절대 확인하지 않습니다

종료 처리 — 502 가 나는 진짜 이유

무중단의 마지막 조각 — preStop 지연 + 앱의 graceful shutdown. 둘 중 하나만 있어도 502 가 남습니다.
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0            # ★ 용량이 줄지 않게
  minReadySeconds: 10              # Ready 후 10초는 더 지켜본 뒤 다음으로
  progressDeadlineSeconds: 600     # 10분 안에 못 끝내면 실패 처리
  template:
    spec:
      terminationGracePeriodSeconds: 45     # preStop + 종료가 이 안에 끝나야
      containers:
        - name: api
          lifecycle:
            preStop:
              exec:
                command: ["sh","-c","sleep 5"]    # 엔드포인트 전파 대기
          # (프로브는 위 예시와 동일)
// graceful shutdown — Node.js 예. 언어가 달라도 순서는 같습니다
let shuttingDown = false;
const server = app.listen(3000);

process.on('SIGTERM', async () => {
  shuttingDown = true;              // ① readiness 를 503 으로 — 새 트래픽 차단
  await sleep(3000);                // ② LB·엔드포인트 갱신 여유
  server.close(async () => {        // ③ 진행 중 요청이 끝나기를 기다림
    await db.end();                 // ④ DB 커넥션 반납
    await redis.quit();
    process.exit(0);
  });
  // ⑤ 안전장치 — 30초 넘으면 그냥 종료
  setTimeout(() => process.exit(0), 30_000).unref();
});
Spring Boot 는 설정 두 줄이면 됩니다. server.shutdown=graceful 과 spring.lifecycle.timeout-per-shutdown-phase=30s 를 켜면 SIGTERM 에 진행 중 요청을 마치고 종료합니다. 단 이미지에서 ENTRYPOINT 를 셸 형식(ENTRYPOINT java -jar app.jar)으로 쓰면 시그널이 자바까지 안 갑니다 — 반드시 배열(exec) 형식으로 쓰세요(d03).

# ★ 주의: replicas 2 에 minAvailable 2 를 걸면 drain 이 영원히 멈춥니다
---
# 파드를 서로 다른 노드·존에 흩기 — 노드 하나 죽어도 전멸하지 않게
spec:
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector: { matchLabels: { app: api } }
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector: { matchLabels: { app: api } }
      # 특정 노드 그룹에만 배치 (GPU 노드 · 고사양 노드)
      nodeSelector: { workload: general }
      tolerations:
        - key: "gpu"
          operator: "Equal"
          value: "true"
          effect: "NoSchedule"
taint 와 toleration 을 한 문장으로. taint 는 노드가 붙이는 "출입 금지 표시"이고, toleration 은 파드가 가진 "출입증"입니다. GPU 노드에 taint 를 걸어 두면 일반 파드가 비싼 GPU 노드를 차지하는 일이 없고, GPU 워크로드만 toleration 을 달고 들어갑니다. nodeSelector/affinity 는 "어디로 가고 싶다", taint 는 "아무나 오지 마라" — 방향이 반대입니다. 보통 둘을 같이 씁니다.
오토스케일 사고 3종. ① 비용 폭발 — maxReplicas 를 안 걸어 무한 증설(요금 고지서로 알게 됩니다) ② DB 커넥션 고갈 — 파드가 30개로 늘면 커넥션 풀도 30배. DB 가 먼저 죽습니다 ③ 재시작 폭풍 — 축소 시 드레인 없이 죽여 처리 중 요청이 유실. 앱만 늘리는 오토스케일은 반쪽입니다 — 아래층(DB·캐시·외부 API 쿼터)을 같이 계산하세요 (📈 대규모 트래픽 x08 에 규모 산정 관점이 더 있습니다).
정리 — requests 를 측정해서 적고 · 메모리는 limits 를 같게 · CPU limits 는 신중히 · HPA 는 min 을 충분히. 이 넷이 안정성과 비용을 동시에 잡습니다.

관측 — 로그 · 메트릭 · 추적

① 로그 — 파일이 아니라 표준 출력으로

          expr: |
            sum(rate(http_requests_total{job="api",status=~"5.."}[5m]))
            / sum(rate(http_requests_total{job="api"}[5m])) > 0.02
          for: 5m                      # ★ 5분 지속될 때만 — 순간 스파이크 무시
          labels: { severity: page }
          annotations:
            summary: "API 5xx 비율 2% 초과"
            runbook: "https://wiki/runbook/api-5xx"    # ★ 대응 문서 링크

        - alert: PodCrashLooping
          expr: increase(kube_pod_container_status_restarts_total[15m]) > 3
          for: 5m
          labels: { severity: page }
알림은 "사람이 지금 일어나야 하는 것"만 페이지로 보냅니다. SLO 기반(사용자가 느끼는 에러율·지연)으로 3~5개만 두고, 나머지는 대시보드나 티켓으로 보냅니다. 알림이 하루 50개 오면 전부 무시하게 되고 그중에 진짜가 섞여 있어도 못 봅니다 — 이것이 알림 피로(alert fatigue)입니다. 모든 알림에 런북 링크를 붙이는 것도 규칙으로 두세요.

③ 분산 추적 — 어느 구간이 느린가 🟡 중급

"주문 API 가 3초 걸립니다"까지는 메트릭이 알려 줍니다. "그 3초 중 2.4초가 재고 서비스의 DB 쿼리였다"는 추적만 알려 줍니다. 서비스가 3개를 넘으면 추적 없이 원인을 찾는 것이 사실상 불가능해집니다(🧱 MSA m10). 

# 앱에 코드를 거의 안 고치고 붙이는 법 — 자동 계측
spec:
  template:
    metadata:
      annotations:
        instrumentation.opentelemetry.io/inject-java: "true"   # 자바 에이전트 자동 주입
    spec:
      containers:
        - name: api
          env:
            - name: OTEL_SERVICE_NAME
              value: api
            - name: OTEL_EXPORTER_OTLP_ENDPOINT
              value: http://otel-collector.observability:4317
            - name: OTEL_TRACES_SAMPLER
              value: parentbased_traceidratio
            - name: OTEL_TRACES_SAMPLER_ARG
              value: "0.05"        # ★ 5% 샘플링 — 100% 는 비용이 감당 안 됩니다
            - name: OTEL_RESOURCE_ATTRIBUTES
              value: "service.version=1.4.2,deployment.environment=prod"
샘플링 전략. 전부 저장하면 저장 비용이 로그보다 큽니다. 실무 조합은 ①기본 1~10% 확률 샘플링 + ②에러·느린 요청은 무조건 저장(tail sampling) 입니다. OTel Collector 에 tail_sampling 프로세서를 두면 "지연 1초 초과 또는 에러 상태면 100% 저장"을 만들 수 있습니다 — 정작 보고 싶은 요청은 다 남습니다.

무엇부터 붙일까 — 순서

순서붙이는 것이유
1주차로그 집계 (Loki + Fluent Bit) + JSON 로깅파드가 죽어도 로그가 남습니다. 이것 없이는 아무것도 못 합니다
2주차메트릭 + 알림 3개 (5xx · 지연 p95 · CrashLoop)"장애를 사용자보다 먼저 아는" 상태가 됩니다
3주차대시보드 — 서비스별 RED + 노드/파드 리소스배포 후 5분간 볼 화면. 있으면 배포 자신감이 생깁니다
4주차~추적 (OTel + Tempo) · trace_id 로그 연결서비스 간 호출이 얽히기 시작할 때 진가가 나옵니다
그다음SLO·에러 예산 · 프로파일링(Pyroscope) · 비용 가시화(OpenCost)여기까지 오면 관측이 문화로 자리 잡은 것입니다
관측 스택 자체가 클러스터를 죽이는 일이 있습니다. Prometheus 는 메모리를 많이 먹고(시계열 수에 비례), 로그 수집은 디스크 I/O 를 씁니다. ①관측 스택에 별도 노드 그룹을 주고 ②라벨 카디널리티를 통제하세요 — user_id 같은 무한한 값을 라벨로 넣으면 시계열이 폭발해 Prometheus 가 OOM 으로 죽습니다. 그러면 장애가 났을 때 볼 것이 없어집니다. 규모가 커지면 관리형(Grafana Cloud · Datadog · 클라우드 네이티브 서비스)이 총비용에서 유리한 지점이 옵니다.
정리 — 구조화된 로그 → 알림 3개 → 대시보드 → 추적 순서로 붙이세요. 관측이 없는 쿠버네티스는 계기판 없는 비행기입니다.

패키징 · GitOps — Helm · Kustomize · Argo CD

환경이 dev·stg·prod 셋이 되는 순간 YAML 복사본이 세 벌 생기고, 곧 서로 달라집니다. 템플릿으로 묶고 · git 을 유일한 진실로 삼는 것이 해법입니다.

GitOps 한 줄 — "클러스터의 상태는 git 저장소가 정의한다". 사람은 git 만 고칩니다.

Helm vs Kustomize — 어느 쪽

기준선택
남에게 배포할 패키지Helm — 버전·의존성·배포 채널이 필요합니다
우리 앱의 환경 분기Kustomize — 결과가 그냥 YAML 이라 읽기 쉽습니다
서드파티 설치Helm — 대부분 차트로 배포됩니다
조건·반복이 많음Helm — Kustomize 는 로직이 없습니다
YAML 을 그대로 보고 싶다Kustomize
섞어 써도 됩니다. 서드파티는 Helm 으로 설치하고, 우리 앱은 Kustomize 로 관리하는 조합이 흔합니다. Argo CD 는 둘 다 지원하고, Helm 차트를 렌더한 뒤 Kustomize 로 덮어쓰는 방식도 됩니다.

Argo CD — 선언형 배포 🟡 중급

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/deploy-manifests
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true        # git 에서 지운 리소스는 클러스터에서도 삭제
      selfHeal: true     # ★ 손으로 고친 것을 git 상태로 되돌림
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true
    retry:
      limit: 3
      backoff: { duration: 15s, factor: 2, maxDuration: 3m }
개념뜻
Syncgit 상태를 클러스터에 반영. 자동/수동을 환경별로 다르게 둡니다(dev 자동 · prod 수동 승인)
Drift(어긋남)클러스터가 git 과 달라진 상태. Argo CD 화면에 OutOfSync 로 뜹니다
Self-heal어긋나면 자동으로 git 상태로 되돌림. 급한 손수정이 지워지므로 켜기 전에 팀 합의가 필요합니다
Prunegit 에서 삭제된 리소스를 클러스터에서도 삭제. 안 켜면 유령 리소스가 쌓입니다
App of AppsApplication 을 관리하는 Application. 서비스가 수십 개일 때 한 곳에서 관리합니다
Sync Wave적용 순서 지정(예: DB 마이그레이션 Job 을 앱보다 먼저). argocd.argoproj.io/sync-wave 어노테이션

환경 구성 전략 — 저장소를 어떻게 나누나

흔한 실수
  • 환경별로 브랜치(dev·stg·prod 브랜치) — 체리픽 지옥이 되고 무엇이 어디에 있는지 아무도 모르게 됩니다
  • 앱 코드와 매니페스트를 한 저장소에 두고 CI 가 같은 저장소에 커밋 — 무한 빌드 루프가 돌기 쉽습니다
  • 운영만 손으로 다르게 손질 — drift 가 쌓여 재현 불가능해집니다
실무에서 안정적인 구성
  • 매니페스트 저장소를 분리(deploy-manifests) — 앱 저장소는 코드와 이미지 빌드만
  • 브랜치는 main 하나, 환경은 디렉터리(overlays/dev · stg · prod)로 구분
  • CI 는 이미지 태그 한 줄만 커밋 → PR → 머지 시 Argo CD 가 반영
  • prod 는 수동 sync 또는 승인 필요, dev·stg 는 자동
  • 클러스터 공통 요소(ingress·모니터링·정책)는 플랫폼 저장소로 또 분리
DB 마이그레이션은 GitOps 로 안 풀립니다. 스키마 변경은 되돌릴 수 없는 작업이라 "선언형"과 궁합이 나쁩니다. 실무 패턴은 ①마이그레이션을 항상 하위 호환으로 작성(컬럼 추가만, 삭제는 두 배포 뒤) ②Argo CD PreSync Hook 또는 Job 으로 앱 배포 전에 실행 ③실패 시 배포 중단입니다. "코드 롤백해도 스키마는 안 돌아간다"를 전제로 설계하세요.
정리 — Helm/Kustomize 로 환경 차이를 흡수하고, Argo CD 로 git 을 진실로 만드는 것이 오늘날의 표준입니다. 배포 이력이 git log 가 되는 순간 운영이 훨씬 조용해집니다.
K8S 13

CI/CD — 커밋에서 배포까지 한 줄로

여기까지의 조각(이미지 · 태그 · 매니페스트 · GitOps)을 하나의 파이프라인으로 잇습니다. 완성되면 머지 → 5분 뒤 스테이징 반영 → 승인 → 운영 배포가 자동으로 흐릅니다.

좋은 파이프라인의 기준 — 롤백이 배포만큼 쉬울 것. 그래야 배포가 무섭지 않습니다.

GitHub Actions — 빌드 · 스캔 · 푸시

# .github/workflows/build.yml
name: build
on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:

permissions:
  contents: read
  packages: write          # GHCR push 에 필요
  id-token: write          # cosign 키리스 서명에 필요

concurrency:               # 같은 브랜치의 이전 실행은 취소 — 큐가 밀리지 않게
  group: build-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm       # ★ 의존성 캐시 — 빌드 시간의 절반이 여기서 줄어듭니다
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage

  build:
    needs: test
    runs-on: ubuntu-latest
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}     # 별도 발급 불필요

      - id: meta                                    # 태그를 규칙대로 자동 생성
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=sha-,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha                      # ★ 레이어 캐시를 Actions 에 저장
          cache-to: type=gha,mode=max
          provenance: true

      - name: Trivy scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ghcr.io/${{ github.repository }}@${{ steps.push.outputs.digest }}
          severity: HIGH,CRITICAL
          ignore-unfixed: true
          exit-code: '1'                            # 취약점 있으면 실패

      - name: Sign image
        run: |
          cosign sign --yes \
            ghcr.io/${{ github.repository }}@${{ steps.push.outputs.digest }}
# .github/workflows/deploy.yml — 매니페스트 저장소의 태그를 올려 GitOps 를 촉발
name: deploy
on:
  workflow_run:
    workflows: [build]
    types: [completed]

jobs:
  bump-staging:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          repository: myorg/deploy-manifests
          token: ${{ secrets.DEPLOY_REPO_TOKEN }}   # 최소 권한 PAT 또는 App 토큰
      - name: bump image tag
        run: |
          cd overlays/stg
          kustomize edit set image \
            ghcr.io/myorg/api=ghcr.io/myorg/api:sha-${GITHUB_SHA::7}
      - name: commit
        run: |
          git config user.name  "ci-bot"
          git config user.email "ci-bot@myorg.dev"
          git commit -am "stg: api sha-${GITHUB_SHA::7}"
          git push
      # 이후는 Argo CD 가 알아서 반영합니다(d12)

  deploy-prod:
    needs: bump-staging
    runs-on: ubuntu-latest
    environment: production        # ★ 여기서 사람 승인을 요구합니다
    steps:
      - uses: actions/checkout@v4
        with: { repository: myorg/deploy-manifests, token: '${{ secrets.DEPLOY_REPO_TOKEN }}' }
      - run: |
          cd overlays/prod
          kustomize edit set image ghcr.io/myorg/api=ghcr.io/myorg/api:${{ github.event.release.tag_name }}
          git commit -am "prod: api ${{ github.event.release.tag_name }}" && git push
항목실무 기준
시크릿 관리저장소 Secrets 대신 OIDC 연동을 우선(AWS·GCP 는 임시 자격 증명 발급이 됩니다). 장기 토큰은 만료일과 담당자를 명시
권한permissions: 를 워크플로마다 최소로 선언. 기본 write-all 을 끄는 것이 첫 단계
캐시언어 의존성 캐시 + 도커 레이어 캐시(type=gha). 5분 → 90초가 흔한 개선폭입니다
태그 기반 릴리스git tag v1.4.2 → 이미지 1.4.2 생성 → 운영은 릴리스 태그로만 배포
승인GitHub Environment protection rule 로 운영에 리뷰어 지정. Argo CD 를 수동 sync 로 두는 방식도 동일 효과
롤백매니페스트 저장소에서 revert 커밋 하나. kubectl rollout undo 는 임시 조치일 뿐(다음 sync 때 되돌아갑니다)
GitOps 에서 kubectl 로 직접 고치면 안 되는 이유. Argo CD 의 selfHeal 이 켜져 있으면 몇 분 뒤 git 상태로 되돌아갑니다 — 새벽에 급하게 고친 설정이 조용히 원복되어 장애가 재발합니다. 급할 때는 ①Argo CD 에서 해당 앱의 자동 sync 를 잠시 끄고 손을 대거나 ②그냥 git 에 핫픽스 커밋을 올리는 것이 낫습니다. 후자가 이력도 남고 다음 사람도 압니다.

배포 승인과 릴리스 절차 — 사람 몫

배포 전 체크(자동화 가능한 것)

  • 테스트·린트·타입 검사 통과
  • 이미지 취약점 CRITICAL 0(예외는 문서화)
  • kubectl diff 또는 helm diff 결과를 PR 코멘트로 자동 첨부
  • 스테이징에서 스모크 테스트(핵심 API 5개 + 로그인)
  • DB 마이그레이션이 하위 호환인지 확인

배포 직후 5분(사람이 봐야 할 것)

  • kubectl rollout status 가 완료로 끝났는가
  • 5xx 비율이 배포 전 수준인가(d11 대시보드)
  • 지연 p95가 튀지 않았는가
  • 파드 재시작 카운트가 0 인가
  • 에러 로그에 새로운 문구가 등장하지 않았는가
이 다섯 줄을 대시보드 한 화면에 모아 두면 배포 담당자가 볼 곳이 하나가 됩니다.
GitHub Actions 가 아니어도 구조는 같습니다. GitLab CI · Jenkins · Tekton · Buildkite 어느 것을 쓰든 ①테스트 ②이미지 빌드·불변 태그 ③스캔 ④매니페스트 갱신 ⑤GitOps 반영 ⑥승인이라는 뼈대는 동일합니다. 도구를 바꿀 때 옮겨야 하는 것은 문법뿐입니다.
정리 — 파이프라인의 목표는 속도가 아니라 "안심하고 자주 배포하는 것"입니다. 불변 태그 · 자동 검증 · 쉬운 롤백 셋이 그 안심을 만듭니다.

실전 문제 해결 — 증상에서 원인까지

장애가 났을 때 필요한 것은 지식이 아니라 순서입니다. 이 섹션은 그대로 따라 치면 원인이 좁혀지는 절차와 증상 사전입니다.

순서를 지키세요 — get → describe(이벤트) → logs(--previous) → exec/debug. 이 순서로 90% 가 잡힙니다.

증상흔한 원인확인·해결

진단 명령 모음 — 순서대로

# ── 1단계: 전체 파악 ──────────────────────────
kubectl get pods -n prod -o wide
kubectl get events -n prod --sort-by=.lastTimestamp | tail -30
kubectl get deploy,svc,ing,hpa -n prod

# ── 2단계: 문제 파드 파고들기 ──────────────────
POD=$(kubectl -n prod get pod -l app=api -o name | head -1)
kubectl -n prod describe $POD                 # ★ Events 섹션을 끝까지 읽습니다
kubectl -n prod logs $POD --previous          # ★ 죽기 직전 로그
kubectl -n prod logs $POD -c sidecar          # 사이드카가 있으면 컨테이너 지정
kubectl -n prod logs -l app=api --since=10m --prefix   # 여러 파드 한 번에

# 종료 코드·재시작 이유 한눈에 보기
kubectl -n prod get pod -o custom-columns=NAME:.metadata.name,REASON:.status.containerStatuses[0].lastState.terminated.reason,CODE:.status.containerStatuses[0].lastState.terminated.exitCode

# ── 3단계: 안에서 확인 ────────────────────────
kubectl -n prod exec -it $POD -- sh
kubectl -n prod exec $POD -- env | sort       # 환경 변수가 제대로 들어갔나
kubectl -n prod exec $POD -- ls -l /etc/app   # 마운트가 됐나

# 셸이 없는 이미지(distroless)는 임시 디버그 컨테이너를 붙입니다
kubectl -n prod debug $POD -it --image=nicolaka/netshoot --target=api

# ── 4단계: 네트워크 확인 ──────────────────────
kubectl -n prod get endpointslice -l kubernetes.io/service-name=api
kubectl -n prod run net --rm -it --image=nicolaka/netshoot --restart=Never -- bash
#   안에서:
#   nslookup api.prod.svc.cluster.local        # DNS 가 도나
#   curl -v http://api.prod.svc/healthz/ready  # 서비스로 붙나
#   curl -v http://10.244.1.5:3000/healthz     # 파드 IP 로 직접 붙나

# ── 5단계: 리소스·노드 ────────────────────────
kubectl top pods -n prod --sort-by=memory
kubectl top nodes
kubectl describe node NODE | grep -A10 'Allocated resources'
DNS 문제 판별 3단 논법. ① 파드 IP 로 직접 curl 이 되면 앱은 정상입니다. ② Service 이름으로 안 되면 DNS 또는 엔드포인트 문제입니다. ③ nslookup 이 실패하면 CoreDNS 를 봅니다 (kubectl -n kube-system logs -l k8s-app=kube-dns). 참고로 클러스터 안 정식 이름은 서비스이름.네임스페이스.svc.cluster.local 이고, 같은 네임스페이스면 서비스 이름만으로 붙습니다.
"일단 재시작"의 유혹. kubectl delete pod 로 문제가 사라지는 경우가 많지만 원인은 그대로 남아 다시 옵니다. 급할 때 재시작으로 서비스를 살리는 것은 맞지만, 죽기 직전 로그(--previous)와 describe 출력을 먼저 저장하고 재시작하세요. 파드를 지우면 그 증거가 함께 사라집니다.

실전 배포 체크리스트 — 운영에 올리기 전

이미지 · 컨테이너

  • 불변 태그(SemVer 또는 SHA) — latest 아님
  • 멀티스테이지 · slim/distroless 베이스
  • 비루트 실행 + readOnlyRootFilesystem
  • .dockerignore 에 .env·.git
  • ENTRYPOINT 가 exec(배열) 형식
  • 취약점 스캔 CRITICAL 0

워크로드 · 안정성

  • requests 를 실측해서 지정, 메모리는 limits 와 동일
  • readiness · liveness · startup 세 프로브
  • maxUnavailable: 0 + preStop 지연
  • 앱의 SIGTERM graceful shutdown 구현
  • replicas ≥ 2 + PDB + 노드/존 분산
  • HPA 의 min 은 피크 직전, max 는 비용 상한

설정 · 보안

  • 비밀은 이미지·git 에 없음(외부 시크릿 참조)
  • ServiceAccount 최소 권한(RBAC), 기본 SA 토큰 자동 마운트 끄기
  • NetworkPolicy 로 필요한 통신만 허용
  • Ingress HTTPS 강제 + cert-manager 자동 갱신(🔐 HTTPS 탭)
  • 네임스페이스별 ResourceQuota · LimitRange

운영 준비

  • 로그가 JSON + stdout, 수집기에 들어옴
  • 알림 3개 이상(5xx · 지연 · CrashLoop)과 런북 링크
  • 롤백 절차를 실제로 한 번 해 봤음
  • PVC·DB 백업과 복원 테스트 완료
  • etcd 백업(자체 운영 시) 또는 관리형 클러스터 사용
  • 노드 업그레이드 시 drain 이 PDB 로 안전한지 확인
