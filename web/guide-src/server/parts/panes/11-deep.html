SECTION 01

소켓부터 — accept 와 커넥션

연결은 웹서버가 받기 전에 커널의 대기줄에 먼저 쌓입니다. 이 줄이 넘치면 접속이 거부됩니다.

1
SYN 도착 → SYN 큐 3-way 핸드셰이크가 진행 중인 연결이 여기 쌓입니다. 크기는 tcp_max_syn_backlog.
▼ 핸드셰이크 완료
2
accept 큐 (완성 큐) 연결은 이미 성립됐지만 애플리케이션이 아직 accept() 하지 않은 상태. 크기는 min(somaxconn, listen backlog).
▼ nginx 가 accept()
3
워커가 처리 이제부터 epoll 이 관리하는 연결이 됩니다.
accept 큐가 넘치면 커널이 연결을 조용히 버리거나 RST 를 보냅니다. 클라이언트는 타임아웃 또는 connection reset 을 보게 됩니다.
이때 웹서버 로그에는 아무것도 안 남습니다 — 요청이 도달하지 못했으니까요. "서버는 멀쩡한데 접속이 안 된다"는 상황의 원인입니다. 
# 큐 넘침 확인
netstat -s | grep -i -E 'listen|overflow'
# 12345 times the listen queue of a socket overflowed    ← 이 값이 증가하면 문제
# 12345 SYNs to LISTEN sockets dropped

# 현재 큐 상태 (Send-Q = 큐 최대 크기, Recv-Q = 대기 중인 연결 수)
ss -lnt
# State   Recv-Q  Send-Q  Local Address:Port
# LISTEN  0       511     0.0.0.0:80              ← Send-Q 가 backlog

# 커널 설정
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog
# 세 곳을 맞춰야 합니다
# ① 커널
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535

# ② Nginx listen 지시어
listen 80 backlog=65535;
# ★ backlog 는 somaxconn 을 넘을 수 없습니다 (조용히 잘립니다)

# ③ 앱 서버 (톰캣 acceptCount · Node backlog 등)
Nginx 의 기본 backlog 는 511 입니다(리눅스). 피크 트래픽이 크다면 이 값이 병목이 될 수 있습니다. 다만 큐를 키우는 것은 근본 해결이 아닙니다 — 처리 속도가 따라오지 않으면 대기 시간만 길어질 뿐입니다. 큐 넘침이 계속되면 워커·서버를 늘리는 것이 답입니다.
"연결이 가끔 안 된다" 는 신고의 단골 원인이 이 줄의 길이입니다.
SECTION 02

이벤트 루프 · epoll

워커 하나가 수천 연결을 다루는 비결입니다. "준비된 것만 알려 줘"가 핵심입니다.

select · poll — 옛 방식
"이 1000개 소켓 중 준비된 게 있나?"
→ 커널이 1000개를 전부 검사
→ 매 호출마다 O(n)

연결이 10,000개면 매번 10,000개 검사
select 는 1024개 제한도 있습니다
epoll — 리눅스
epoll_create()  감시 목록을 커널에 만들고
epoll_ctl()     관심 소켓을 등록해 두면
epoll_wait()    준비된 것만 돌려받습니다
                → O(준비된 개수)

연결이 10,000개여도
실제로 데이터가 온 10개만 처리
# Nginx 워커의 개념적 루프
while (true) {
    events = epoll_wait(epfd, ...)          // 준비된 이벤트만 받음 (블로킹)

    for (ev in events) {
        if (ev is 새 연결)      accept() 후 epoll 에 등록
        else if (ev is 읽기 가능) 요청을 읽고 파싱
        else if (ev is 쓰기 가능) 응답을 조금 보냄
    }

    타이머 처리 (타임아웃된 연결 정리)
}
이 구조의 치명적 약점 — 블로킹
루프 안에서 블로킹 작업(느린 디스크 읽기·DNS 조회·동기 연산)이 일어나면 그 워커가 담당하는 수천 개 연결이 전부 멈춥니다.
그래서 Nginx 는 무거운 작업을 절대 직접 하지 않고 뒤로 넘깁니다. Node.js 의 이벤트 루프도 같은 원리이며, 동기 함수 하나가 서버 전체를 멈추는 이유가 이것입니다. 
# 디스크 IO 를 별도 스레드 풀로 분리 (파일이 크고 캐시 미스가 잦을 때)
thread_pool default threads=32 max_queue=65536;

location /downloads/ {
    aio threads=default;        # 비동기 파일 읽기
    directio 4m;                # 4MB 넘는 파일은 페이지 캐시를 우회
    sendfile off;               # aio 와 함께 쓸 때
}
다른 OS 의 대응 기술 — BSD·macOS 는 kqueue, Solaris 는 event ports, Windows 는 IOCP. Nginx 는 이를 자동으로 선택합니다. 최신 리눅스에는 io_uring 이라는 더 발전된 방식도 있습니다.
select 의 1024개 제한도 사라집니다 — 연결 수와 처리 비용이 분리되는 것이 이 설계의 전부입니다.

이벤트 루프를 멈추게 하는 것들

블로킹 원인영향과 대응
디스크 읽기 (캐시 미스)워커가 통째로 멈춤 → aio threads 로 분리
DNS 조회proxy_pass 에 도메인을 쓰면 발생 → resolver 설정 · IP 직접 지정
gzip 고압축CPU 점유 → 압축 레벨 5 이하 · 사전 압축
정규식 백트래킹복잡한 location ~ · map → 접두사 매칭 우선
Lua·third-party 모듈동기 호출이 섞이면 치명적 → 비동기 API 만 사용

# 워커가 실제로 어디서 시간을 쓰는지 — 블로킹 지점을 직접 찾습니다
sudo strace -c -f -p $(pgrep -f 'nginx: worker' | head -1) & sleep 10; kill %1
#   → 호출별 누적 시간이 나옵니다. read/openat 이 크면 디스크 블로킹입니다.

# 워커가 멈춰 있는 순간을 잡기
sudo perf top -p $(pgrep -f 'nginx: worker' | head -1)

# 응답 지연의 분포 (평균이 아니라 꼬리를 보세요)
awk '{print $(NF)}' /var/log/nginx/access.log | sort -n | \
  awk '{a[NR]=$1} END {print "p50:"a[int(NR*0.5)], "p95:"a[int(NR*0.95)], "p99:"a[int(NR*0.99)]}'
#   (로그 포맷에 $request_time 이 마지막 필드로 있다고 가정)
로그를 버퍼링하면 디스크 지연이 응답에 새는 것을 막습니다. access_log /var/log/nginx/access.log main buffer=64k flush=5s; 한 줄이면 됩니다. 기본 설정은 요청마다 디스크에 쓰기라, 디스크가 잠깐 느려지는 순간 모든 응답이 함께 느려집니다 — 네트워크 스토리지를 쓰거나 로그가 많은 서버에서 실제로 겪는 문제입니다. 대신 서버가 갑자기 죽으면 마지막 몇 초의 로그를 잃습니다.
SECTION 03

Nginx 워커 모델 내부

워커가 여러 개일 때 연결을 어떻게 나눠 갖는지가 성능에 영향을 줍니다.

방식동작
accept_mutex 워커들이 순서대로 돌아가며 accept. 예전 기본값 — 지연이 생길 수 있습니다
모든 워커가 대기 연결 하나에 모든 워커가 깨어나는 문제(thundering herd). 현대 커널은 대부분 완화돼 있습니다
SO_REUSEPORT ★ 커널이 직접 분배 — 워커마다 독립된 리슨 소켓. 경합이 없고 분배가 고릅니다
events {
    accept_mutex off;               # 1.11.3+ 기본값 (off)
}

server {
    listen 80 reuseport;            # ★ SO_REUSEPORT 활성화
    # 워커마다 커널이 별도 큐를 만들어 연결을 나눠 줍니다
}
reuseport 는 같은 주소·포트에 한 번만 써야 합니다. 여러 server 블록에서 같은 listen 80 을 쓸 때 첫 블록에만 붙이세요. 여러 곳에 쓰면 설정 오류가 납니다.
또 reload 시 짧은 순간 연결이 유실될 수 있다는 보고가 있으므로, 무중단이 극도로 중요한 환경에서는 검증 후 도입하세요.

워커 간 불균형

# 워커별 연결 수 확인
for pid in $(pgrep -f 'nginx: worker'); do
  echo "$pid : $(ls /proc/$pid/fd 2>/dev/null | wc -l) fds"
done
워커마다 연결 수가 크게 다르면 분배가 고르지 않은 것입니다. keepalive 연결이 특정 워커에 몰리면 그 워커만 바빠집니다. reuseport 가 이 문제를 상당히 개선합니다.

공유 메모리 존

# 워커는 별도 프로세스라 메모리를 공유하지 않습니다
# rate limit · 캐시 키 · SSL 세션은 '공유 메모리 존'에 둡니다

limit_req_zone $binary_remote_addr zone=req:10m rate=30r/s;   # 모든 워커가 공유
ssl_session_cache shared:SSL:10m;                              # shared: 접두사
proxy_cache_path /var/cache/nginx keys_zone=cache:100m ...;

# shared 가 아닌 builtin 캐시를 쓰면 워커마다 따로 관리되어
# 실제 제한이 '워커 수 × 설정값' 이 되어 버립니다
존 크기 계산 — 10m 은 대략 16만 개의 IP 상태를 담습니다 ($binary_remote_addr 기준 항목당 약 64바이트). 존이 가득 차면 오래된 항목부터 제거되며, 심하면 limit_req 가 제대로 동작하지 않습니다.
SECTION 04

Apache MPM 내부 비교

Apache 가 메모리를 더 쓰는 이유를 구조로 설명합니다.

MPM연결 1000개일 때메모리 추정
prefork프로세스 1000개프로세스당 20~50MB → 수십 GB
worker프로세스 40개 × 스레드 25개스레드 스택 + 프로세스 → 수 GB
eventworker 와 같지만 유휴 연결은 전담 스레드가 관리worker 보다 크게 절약
(Nginx)워커 4개수십~수백 MB
event MPM 이 개선한 지점 — HTTP keepalive 로 연결은 열려 있지만 아무 요청도 없는 상태가 대부분입니다. prefork·worker 는 그동안에도 프로세스·스레드를 붙잡고 있었습니다. event MPM 은 이 유휴 연결을 전담 리스너 스레드에 넘겨 작업 스레드를 즉시 반납합니다. 
# 실제 메모리 사용 측정
ps -ylC apache2 --sort:rss | awk '{sum+=$8; n++} END {print "평균 " sum/n/1024 " MB · 프로세스 " n "개"}'

# MaxRequestWorkers 계산
# (가용 메모리 MB × 0.8) ÷ 프로세스당 평균 MB
free -m | awk '/^Mem:/ {print "가용: " $7 " MB"}'
PHP 를 쓰면 event MPM 을 못 쓰는 경우가 있습니다. mod_php 는 스레드 안전하지 않아 prefork 를 강제합니다.
해결 — mod_php 를 끄고 PHP-FPM + proxy_fcgi 로 전환하면 event MPM 을 쓸 수 있고 메모리 사용이 크게 줄어듭니다. 이것이 현대 Apache + PHP 구성의 표준입니다. 
# 왜 Nginx 가 메모리를 적게 쓰나

Apache prefork : 연결 = 프로세스
  · 각 프로세스가 PHP 인터프리터·모듈 전체를 메모리에 적재
  · 연결이 늘면 메모리가 선형으로 증가

Nginx : 연결 = 자료구조 (수 KB)
  · 워커 프로세스 수는 고정 (CPU 코어 수)
  · 연결이 늘어도 메모리는 완만하게 증가
  · 대신 동적 언어를 직접 실행하지 못합니다 (항상 프록시)

★ 트레이드오프입니다. Apache 는 '한 프로세스가 전부 처리',
  Nginx 는 '나는 전달만 하고 실행은 남에게'

MaxRequestWorkers 를 실제로 계산하기

# ① 프로세스 하나가 실제로 쓰는 메모리 (RSS 는 공유분이 중복 계산됩니다)
sudo smem -t -P apache2 -k | tail -1        # PSS 기준 — 더 정확합니다
# smem 이 없으면 근사치로
ps -ylC apache2 --sort:rss | awk 'NR>1 {s+=$8; n++} END {printf "평균 %.0f MB · %d개\n", s/n/1024, n}'

# ② 앱과 캐시를 뺀 가용 메모리
free -m | awk '/^Mem:/ {printf "가용 %d MB\n", $7}'

# ③ MaxRequestWorkers = (가용 × 0.7) ÷ 프로세스당 MB
#    예) 8000MB × 0.7 = 5600, 프로세스당 40MB → 140
# prefork — 메모리가 상한을 정합니다
<IfModule mpm_prefork_module>
    StartServers             8
    MinSpareServers          8
    MaxSpareServers         20
    MaxRequestWorkers      140     # ★ 위에서 계산한 값
    MaxConnectionsPerChild 10000   # 누수 대비 주기적 교체 (0 = 무제한)
</IfModule>

# event — 스레드가 상한을 정합니다
<IfModule mpm_event_module>
    StartServers             4
    MinSpareThreads         50
    MaxSpareThreads        150
    ThreadsPerChild         25     # 프로세스당 스레드
    MaxRequestWorkers      400     # = ServerLimit × ThreadsPerChild
    ServerLimit             16     # ★ MaxRequestWorkers ÷ ThreadsPerChild
    AsyncRequestWorkerFactor 2     # 유휴 연결을 몇 배까지 받을지
    MaxConnectionsPerChild   0
</IfModule>
MaxRequestWorkers 를 크게 잡는 것이 오히려 서버를 죽입니다. 메모리를 넘기면 스왑으로 빠지고, 스왑에 들어간 순간 응답 시간이 수십 배가 됩니다. 그러면 요청이 더 쌓이고, 워커가 더 늘고, 더 스왑되는 악순환이 시작됩니다.
메모리가 부족하면 워커를 줄이고 대기시키는 편이 낫습니다 — 일부 요청이 조금 기다리는 것과 서버 전체가 죽는 것은 다른 차원의 문제입니다. 스왑을 아예 끄고(vm.swappiness=1) 한계를 명확히 하는 구성도 흔합니다.

Apache 를 고를 이유가 남아 있는 곳

상황이유
.htaccess 가 필요공유 호스팅 · 앱이 배포 시 규칙을 생성 — Nginx 에는 대응물이 없습니다
정교한 접근 제어Require expr · 인증 모듈 생태계가 훨씬 넓습니다
LDAP·Kerberos 인증모듈이 성숙 — 사내 시스템 연동에 유리
레거시 모듈 의존수십 년 축적된 모듈이 그대로 동작합니다
동적 콘텐츠를 직접 실행mod_php·mod_wsgi — 다만 권장되지 않습니다
대량 동시 연결Nginx·Caddy 가 낫습니다 — 구조적 차이입니다
실무에서 가장 흔한 답은 "둘 다"입니다. 앞에 Nginx 를 두어 정적 파일·TLS·연결 관리를 맡기고, 뒤에 Apache 를 두어 .htaccess 와 기존 모듈을 그대로 쓰는 구성입니다. Nginx 가 동시 연결을 흡수해 주므로 Apache 는 실제 처리 중인 요청만 상대하면 됩니다 — prefork 라도 워커 수를 훨씬 적게 잡을 수 있게 됩니다.

서버 푸시없음있었으나 사실상 폐기없음
HOL (Head-of-Line) 블로킹 — HTTP/2 는 한 TCP 연결에 여러 스트림을 실어 보내는데, 패킷 하나가 유실되면 TCP 가 재전송을 기다리며 그 연결의 모든 스트림이 멈춥니다.
HTTP/3 은 QUIC(UDP 기반)으로 스트림마다 독립적으로 처리해 이 문제를 해결했습니다. 패킷 손실이 잦은 모바일에서 차이가 큽니다.

언제 효과가 있나

🟢 HTTP/2 효과 큼
  • 작은 파일이 많은 페이지
  • 지연이 큰 네트워크
  • 번들링하지 않은 사이트
  • 이미지가 많은 페이지
🔵 효과 작음
  • 이미 번들링된 SPA (파일 2~3개)
  • 대용량 파일 하나를 받는 경우
  • 빠른 유선 네트워크
  • CDN 이 이미 앞에 있는 경우
🟣 HTTP/3 이 유리
  • 모바일 · 불안정한 네트워크
  • 패킷 손실이 있는 환경
  • 네트워크 전환이 잦은 사용자
  • 전 세계 대상 서비스
HTTP/2 를 켠 뒤 오히려 느려지는 경우
· 도메인 샤딩(정적 파일을 여러 도메인에 분산)을 그대로 두면 HTTP/2 의 다중화 이점이 사라집니다 — 한 도메인으로 합치는 것이 맞습니다
· 스프라이트 이미지·인라인 CSS 같은 HTTP/1.1 시대 최적화도 HTTP/2 에서는 불필요하거나 역효과일 수 있습니다
· 서버 푸시는 브라우저에서 제거됐으므로 쓰지 마세요
버전마다 어디가 막혀 있었는지를 알면 왜 바뀌었는지가 보입니다.
SECTION 06

TLS 종료 위치와 성능

암호화를 어디서 푸느냐가 성능과 구조를 좌우합니다.

위치장단점
CDN·LB 에서 사용자와 가장 가까워 핸드셰이크 지연이 최소. 인증서 관리가 한 곳.
뒤쪽 구간이 평문이면 내부망 보안에 의존
웹서버(Nginx)에서 가장 흔한 구성. 앱은 평문만 다루면 됩니다
앱에서 인증서 관리가 앱마다 필요. 언어별 방식이 달라 번거롭습니다
재암호화 구간 전체 암호화. CPU 비용이 두 배, 지연도 늘어납니다

TLS 비용은 어디서 발생하나

① 핸드셰이크 (연결당 1회)
   · 비대칭키 연산 (RSA·ECDSA 서명·검증) ← 비쌉니다
   · RSA 2048 서명 1회 ≈ ECDSA P-256 의 여러 배
   · 세션 재개(session resumption)로 생략 가능 ★

② 대칭키 암복호화 (모든 데이터)
   · AES-GCM 은 현대 CPU 의 AES-NI 명령으로 매우 빠름
   · 실질적 부담은 크지 않습니다

★ 결론 : TLS 비용의 대부분은 '핸드셰이크'입니다
  → keepalive 와 세션 재개가 가장 효과적인 최적화입니다
# 핸드셰이크 비용 줄이기
ssl_session_cache shared:SSL:50m;      # 서버 측 세션 캐시 (약 20만 세션)
ssl_session_timeout 1d;
ssl_session_tickets off;               # 티켓 키를 안전하게 순환할 수 없다면 끄세요

keepalive_timeout 65s;                 # 연결 재사용 = 핸드셰이크 자체를 줄임

ssl_stapling on;                       # OCSP 응답을 서버가 미리 받아 전달
ssl_stapling_verify on;                # (클라이언트의 별도 검증 왕복을 없앰)
resolver 1.1.1.1 8.8.8.8 valid=300s;

# ECDSA 인증서가 RSA 보다 가볍습니다 (둘 다 발급해 병행 제공도 가능)
# ssl_certificate     ecdsa.crt;  ssl_certificate_key ecdsa.key;
# ssl_certificate     rsa.crt;    ssl_certificate_key rsa.key;
세션 티켓의 트레이드오프 — ssl_session_tickets on 은 서버가 상태를 저장하지 않아도 되어 편리하지만, 티켓 키가 유출되면 과거 세션이 복호화될 수 있습니다(전방 비밀성 약화).
키를 주기적으로 순환할 수 없다면 끄는 편이 안전합니다. 여러 서버가 있다면 세션 캐시 공유가 어려우므로 티켓 + 키 순환이 현실적입니다.
측정 방법 — curl -w "%{time_appconnect}" 로 TLS 구간 시간을 재고, 같은 연결로 여러 요청을 보냈을 때 이 값이 0에 가까워지는지 확인하세요. 세션 재개가 동작하면 두 번째 접속부터 크게 줄어듭니다.
SECTION 07

제로카피 · sendfile

정적 파일 전송이 왜 그렇게 빠른지, 커널 수준에서 봅니다.

일반적인 파일 전송
read(file, buf)   디스크 → 커널 버퍼 → 유저 버퍼
write(sock, buf)  유저 버퍼 → 커널 소켓 버퍼 → NIC

복사 4회 · 컨텍스트 스위치 4회
1MB 파일이면 그만큼의 메모리 대역폭 소모
sendfile — 제로카피
sendfile(sock, file)
  디스크 → 커널 버퍼 → (직접) NIC

유저 공간을 거치지 않습니다
복사 2회 · 컨텍스트 스위치 2회
CPU 와 메모리 대역폭을 크게 절약
sendfile on;
tcp_nopush on;        # sendfile 과 함께 — 헤더와 파일 시작을 한 패킷에 모아 전송
tcp_nodelay on;       # keepalive 연결에서는 지연 없이 즉시 전송

# 큰 파일은 청크로 나눠 보내 다른 연결을 굶기지 않게
sendfile_max_chunk 512k;

# 매우 큰 파일 — 페이지 캐시를 오염시키지 않게 우회
directio 8m;
output_buffers 2 512k;
sendfile 이 동작하지 않는 경우
· gzip 압축을 하는 경우 — 내용을 변형해야 하므로 유저 공간을 거칩니다
· TLS 를 쓰는 경우 — 암호화가 필요하므로 마찬가지 (커널 TLS 인 kTLS 를 쓰면 가능하지만 설정이 까다롭습니다)
· 프록시 응답 — 파일이 아니므로 해당 없음
즉 HTTPS + 압축이 기본인 요즘에는 sendfile 의 이득이 예전만큼 크지 않습니다. 사전 압축 파일을 서빙할 때는 여전히 유효합니다. 
# 실제로 sendfile 이 호출되는지 확인
sudo strace -f -e trace=sendfile,write -p $(pgrep -f 'nginx: worker' | head -1) 2>&1 | head -20

# kTLS 지원 여부 (1.21.4+ · OpenSSL 3.0+ · 커널 4.13+)
nginx -V 2>&1 | grep -o ssl_conf_command
# ssl_conf_command Options KTLS;  로 활성화
HTTPS 가 기본인 지금은 kTLS 를 켜야 이 이득이 살아납니다 — 아니면 사전 압축 파일을 쓰는 편이 실질적입니다.

언제 켜고 언제 무의미한가

상황sendfile 효과
정적 파일 · 평문 HTTP큼 — 그대로 커널이 보냅니다
정적 파일 + 사전 압축(.br·.gz)큼 — 이미 만들어진 파일을 그대로
정적 파일 + 실시간 gzip없음 — 내용을 만들어야 합니다
HTTPS (kTLS 없음)없음 — 암호화가 유저 공간에서
HTTPS + kTLS큼 — 커널이 암호화까지
프록시 응답해당 없음 — 파일이 아닙니다
대용량 다운로드큼 — sendfile_max_chunk 를 함께
sendfile_max_chunk 를 안 주면 큰 파일 하나가 워커를 독점합니다. 이벤트 루프는 한 번에 하나씩 처리하므로, 1GB 파일을 한 번에 밀어 넣으면 그 워커의 다른 연결이 전부 기다립니다. sendfile_max_chunk 512k; 를 주면 조금씩 나눠 보내며 사이사이 다른 연결을 처리합니다. 다운로드 서버에서 "큰 파일을 받는 사람이 있으면 사이트가 느려진다"는 현상의 원인이 대개 이것입니다.
정적 파일 성능의 대부분은 sendfile 이 아니라 "페이지 캐시에 있느냐"로 결정됩니다. 자주 요청되는 파일은 커널이 메모리에 들고 있어서 디스크를 안 건드립니다 — 이것이 sendfile 보다 훨씬 큰 요인입니다. free -m 의 buff/cache 가 충분한지, vmstat 1 의 bi(블록 입력) 가 0 에 가까운지 확인하세요. 디스크를 계속 읽고 있다면 메모리를 늘리는 것이 어떤 설정보다 효과적입니다.
SECTION 08

백프레셔와 버퍼

보내는 쪽이 빠르고 받는 쪽이 느릴 때 어떻게 되는지 — 버퍼가 그 완충 장치입니다.

백엔드
1MB 응답을 즉시 생성로컬 네트워크라 순식간에 전송할 수 있습니다.
▼
Nginx 버퍼
응답을 통째로 받아 보관 백엔드는 여기서 즉시 해방됩니다. 버퍼를 넘으면 임시 파일에 씁니다.
▼ 느리게
느린 클라이언트
3G 로 10초에 걸쳐 수신 그동안 붙잡히는 것은 Nginx 의 가벼운 연결 자료구조뿐입니다.
이것이 리버스 프록시의 숨은 가치입니다. 앱 워커(스레드·프로세스)는 비쌉니다(메모리 수십 MB). Nginx 의 연결은 쌉니다(수 KB). 비싼 자원을 빨리 해방시키고 싼 자원이 기다리게 하는 것이 프록시 버퍼링의 본질입니다.

Slowloris — 이 구조를 역이용하는 공격

공격자가 연결을 수천 개 열고
헤더를 아주 천천히(1분에 한 글자씩) 보냅니다

Apache prefork : 연결마다 프로세스 → 수천 프로세스 → 자원 고갈
Nginx          : 연결마다 수 KB → 구조적으로 훨씬 강합니다

그래도 방어 설정은 필요합니다:
  client_header_timeout 10s;
  client_body_timeout   10s;
  limit_conn perip 20;

스트리밍에서는 버퍼링이 방해가 됩니다

# SSE · 실시간 로그 · 대용량 다운로드 스트리밍
location /events {
    proxy_pass http://backend;
    proxy_buffering off;              # 오는 대로 즉시 전달
    proxy_cache off;
    chunked_transfer_encoding off;
    proxy_read_timeout 3600s;
}

# 앱에서 응답별로 제어
# 응답 헤더에 X-Accel-Buffering: no 를 넣으면 그 응답만 버퍼링이 꺼집니다
버퍼링을 끄면 느린 클라이언트가 앱을 붙잡습니다. 스트리밍이 꼭 필요한 엔드포인트에만 적용하고, 동시 스트리밍 연결 수에 제한을 두세요. 수천 개의 SSE 연결이 앱 워커를 하나씩 붙잡으면 서비스가 멈춥니다. 이 때문에 실시간 기능은 비동기 프레임워크(ASGI·Node·WebFlux)로 만드는 것이 좋습니다.
버퍼는 속도 차를 흡수하는 통입니다 — 무한한 통은 메모리 사고가 됩니다.
SECTION 09

커넥션과 파일 디스크립터

연결을 오래 유지하면 빠르지만 자원을 계속 차지합니다.

프록시 구성에서 요청 하나가 쓰는 파일 디스크립터

  클라이언트 ↔ Nginx      : 1개
  Nginx      ↔ 백엔드     : 1개
  (+ 로그 파일 · 캐시 파일 등)

동시 10,000 요청 = 최소 20,000개
여기에 keepalive 유휴 연결까지 더해집니다
설정영향
keepalive_timeout ↑ 재사용률 상승 ↔ 유휴 연결이 FD 를 점유
upstream keepalive ↑ 백엔드 연결 비용 감소 ↔ 백엔드도 그만큼 FD 사용
worker_connections ↑ 동시 처리 증가 ↔ FD 한계에 걸릴 수 있음
# 실시간 FD 사용량
for pid in $(pgrep -f 'nginx: worker'); do
  echo "worker $pid : $(ls /proc/$pid/fd 2>/dev/null | wc -l)"
done

# 한계 확인
cat /proc/$(pgrep -f 'nginx: master')/limits | grep 'open files'

# 시스템 전체
cat /proc/sys/fs/file-nr       # 사용중  미사용  최대

# 소켓 상태 분포
ss -s
ss -tan state established | wc -l
ss -tan state time-wait  | wc -l
TIME_WAIT 이 수만 개 쌓인다면 연결을 계속 새로 맺고 끊고 있다는 신호입니다.
· 근본 해결 — 업스트림 keepalive 활성화 (연결 재사용)
· 완화 — net.ipv4.tcp_tw_reuse = 1
· tcp_tw_recycle 은 쓰지 마세요 — NAT 환경에서 연결 실패를 일으키며 커널에서 제거됐습니다
포트 고갈 — Nginx 가 백엔드로 연결할 때 로컬 포트를 하나씩 씁니다. 기본 범위가 약 28,000개이므로 초당 수천 연결을 새로 맺으면 TIME_WAIT 과 겹쳐 포트가 고갈됩니다.
net.ipv4.ip_local_port_range = 10240 65535 로 넓히고, keepalive 로 연결 자체를 줄이는 것이 정답입니다.

FD 한계는 네 곳에 있습니다 — 하나만 올리면 소용없습니다

계층설정확인
① 시스템 전체fs.file-maxsysctl fs.file-max
② 프로세스(systemd)LimitNOFILEsystemctl show nginx -p LimitNOFILE
③ Nginx 워커worker_rlimit_nofilecat /proc/PID/limits
④ 연결 상한worker_connections③보다 작아야 합니다

# ① 커널
sudo tee /etc/sysctl.d/99-nginx.conf <<'EOF'
fs.file-max = 2097152
net.ipv4.ip_local_port_range = 10240 65535
net.ipv4.tcp_tw_reuse = 1

net.ipv4.tcp_max_syn_backlog = 8192
net.core.netdev_max_backlog = 16384
net.ipv4.tcp_fin_timeout = 15

sudo sysctl --system

# ② systemd

sudo tee /etc/systemd/system/nginx.service.d/limits.conf <<'EOF'
[Service]
LimitNOFILE=65535
EOF
sudo systemctl daemon-reload

# ③④ nginx.conf
#   worker_rlimit_nofile 65535;
#   events { worker_connections 16384; }

sudo systemctl restart nginx

# ★ 실제로 반영됐는지 반드시 확인 — 설정만 보고 믿지 마세요

ulimit -n 을 셸에서 올려도 systemd 서비스에는 적용되지 않습니다. /etc/security/limits.conf 는 로그인 세션에만 작용하고, systemd 로 뜬 프로세스는 LimitNOFILE 을 따릅니다. "설정을 다 올렸는데 여전히 Too many open files 가 난다"면 거의 항상 이 지점입니다 — /proc/PID/limits 로 실제 값을 확인하세요.

connection reset by peer백엔드가 먼저 끊음 — keepalive 타임아웃 불일치
SSL_do_handshake() failed프로토콜·암호 불일치 — 구형 클라이언트
연결 수를 늘리기 전에 "왜 이렇게 많은가"를 먼저 보세요. ss -tan state established | wc -l 이 예상보다 훨씬 크다면, 클라이언트가 연결을 안 닫고 있거나(모바일 앱의 흔한 버그), 업스트림 keepalive 가 없어 연결이 계속 새로 생기거나, 죽은 연결이 정리되지 않는 것입니다. 한계를 올리는 것은 시간을 버는 조치일 뿐, 원인을 그대로 두면 더 큰 숫자에서 같은 일이 반복됩니다.
SECTION 10

프록시 프로토콜 · 실제 IP

프록시를 여러 번 거치면 진짜 방문자 IP 를 잃어버립니다. 게다가 위조도 가능합니다. 

사용자(1.2.3.4) → CDN(5.6.7.8) → LB(10.0.0.1) → Nginx → 앱

앱이 보는 것 : 10.0.0.1  (바로 앞 프록시)
X-Forwarded-For: 1.2.3.4, 5.6.7.8, 10.0.0.1
                 └ 진짜 ┘  └── 거쳐 온 프록시들 ──┘

★ 문제 : 클라이언트가 직접 X-Forwarded-For 를 넣어 보낼 수 있습니다
  "X-Forwarded-For: 8.8.8.8" 로 보내면
  최종 헤더는 "8.8.8.8, 1.2.3.4, 5.6.7.8, 10.0.0.1"
  → 맨 앞을 그대로 믿으면 위조된 IP 를 진짜로 인식합니다
맨 앞 값을 그대로 믿으면 안 됩니다. 오른쪽부터 신뢰할 수 있는 프록시를 하나씩 걷어내고 처음 만나는 신뢰하지 않는 값이 실제 클라이언트 IP 입니다.
이것을 틀리면 IP 기반 차단·rate limit·지역 판별이 전부 우회됩니다. 
# Nginx 가 이 계산을 대신해 줍니다
set_real_ip_from 10.0.0.0/8;          # 우리 LB 대역
set_real_ip_from 172.16.0.0/12;
set_real_ip_from 173.245.48.0/20;     # CDN 대역 (제공자 문서에서)
real_ip_header X-Forwarded-For;
real_ip_recursive on;                 # ★ 신뢰 대역을 재귀적으로 걷어냄

# 이제 $remote_addr 자체가 실제 클라이언트 IP 가 됩니다
# → 로그 · rate limit · allow/deny 가 전부 올바르게 동작합니다

PROXY protocol — 더 확실한 방법

# L4 로드밸런서(TCP 레벨)는 HTTP 헤더를 넣을 수 없습니다
# 대신 연결을 맺자마자 '누가 접속했는지'를 먼저 알려 주는 방식

server {
    listen 443 ssl proxy_protocol;        # ★ PROXY protocol 수신

    set_real_ip_from 10.0.0.0/8;
    real_ip_header proxy_protocol;

    location / {
        proxy_pass http://backend;
        proxy_set_header X-Real-IP $proxy_protocol_addr;
    }
}
proxy_protocol 을 켜면 일반 연결은 전부 실패합니다. 앞단이 반드시 PROXY protocol 을 보내야 하며, 직접 접속하면 broken header 오류가 납니다.
따라서 앞단 LB 설정과 반드시 짝을 맞춰 적용하고, 전환 시 순간적인 장애가 없도록 별도 포트로 먼저 검증하세요.
보안 원칙 — 신뢰 대역을 명시적으로 지정하지 않은 헤더는 믿지 마세요. set_real_ip_from 없이 real_ip_header 만 쓰면 누구나 IP 를 위조할 수 있습니다. 앱 쪽에서도 마찬가지입니다 — Express 의 trust proxy: true, Uvicorn 의 --forwarded-allow-ips '*' 는 모두 위험한 설정입니다.
IP 기반 제한은 실제 IP 가 정확할 때만 의미가 있습니다.
SECTION 11

로드밸런싱 알고리즘

상황마다 정답이 다릅니다. 각각의 성질을 알아야 고를 수 있습니다. (기초 개념·구성 실습은 ⚖️ 로드밸런싱 탭에서 — 여기서는 내부 성질을 파고듭니다)

알고리즘동작과 성질
라운드 로빈 순서대로. 요청 처리 시간이 비슷할 때 가장 고르게 분산됩니다
가중 라운드 로빈 서버 성능이 다를 때 weight 로 비율 조정
least_conn 연결 수가 적은 곳으로. 처리 시간이 들쭉날쭉할 때 유리합니다
ip_hash IP 로 서버 고정. 서버 수가 바뀌면 대부분 재배치됩니다
hash $key consistent 일관된 해싱 — 서버가 바뀌어도 재배치가 최소화됩니다
random two 둘을 무작위로 뽑아 덜 바쁜 쪽. 서버가 아주 많을 때 유리합니다

일관된 해싱이 중요한 이유

일반 해시 : server = hash(key) % N

  서버 3대 → 4대가 되면 N 이 바뀌어
  거의 모든 키의 배정이 달라집니다
  → 캐시 서버라면 캐시 전체가 무효화됩니다 ★

일관된 해싱 : 원형 공간에 서버와 키를 배치

  서버 하나를 추가하면
  그 구간의 키만 이동합니다 (약 1/N)
  → 캐시 적중률이 유지됩니다
# 캐시 서버 계층에 유용합니다
upstream cache_servers {
    hash $request_uri consistent;      # 같은 URL 은 항상 같은 서버로
    server cache1:8080;
    server cache2:8080;
    server cache3:8080;
}

# 사용자별 고정이 필요하면 (세션이 서버에 있을 때)
upstream app {
    hash $cookie_sessionid consistent;
    server app1:8080;
    server app2:8080;
}
세션 고정(sticky)은 근본 해결이 아닙니다.
· 서버가 죽으면 그 서버에 붙어 있던 사용자는 로그아웃됩니다
· 부하가 고르게 분산되지 않습니다
· 배포·확장이 어려워집니다
세션을 Redis 등 외부에 두고 앱을 무상태로 만드는 것이 정답입니다.
실무 기본값 — 앱이 무상태라면 라운드 로빈으로 시작하세요. 응답 시간 편차가 크면(파일 업로드·리포트 생성 등) least_conn 으로 바꿉니다. 캐시 계층에는 일관된 해싱을 씁니다.
SECTION 12

헬스체크 · 서킷 브레이킹

죽은 서버에 요청을 계속 보내지 않게 하고, 장애 전파를 막습니다.

방식설명
수동적 (passive) 실제 요청이 실패하면 그 서버를 잠시 제외. Nginx 오픈소스의 방식
능동적 (active) 주기적으로 /health 를 호출해 미리 판단. Nginx Plus · Caddy · 클라우드 LB 가 제공
# Nginx 오픈소스 — 수동적 헬스체크
upstream backend {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=30s;
}

location / {
    proxy_pass http://backend;

    proxy_next_upstream error timeout http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 10s;

    proxy_connect_timeout 3s;      # ★ 짧게 — 죽은 서버를 빨리 감지
    proxy_read_timeout   30s;
}
재시도 대상에 http_500 을 넣지 마세요. 500 은 앱 코드의 오류라 다른 서버에서도 똑같이 실패합니다. 재시도는 부하만 3배로 만듭니다.
또 POST·PUT 같은 변경 요청의 재시도는 중복 처리를 일으킬 수 있으니 non_idempotent 를 함부로 넣지 마세요.

헬스체크 엔드포인트 설계

구분해서 만드세요

/health/live   — "프로세스가 살아 있나"
  · 단순히 200 만 반환
  · 실패하면 → 재시작

/health/ready  — "트래픽을 받을 준비가 됐나"
  · DB 연결 · 캐시 · 필수 외부 의존성 확인
  · 실패하면 → LB 에서 제외 (재시작하지 않음)

★ 이 둘을 구분하지 않으면
  DB 가 잠시 느릴 때 앱이 계속 재시작되는 재앙이 벌어집니다
# 헬스체크는 로그에서 제외하고 rate limit 도 면제
location = /health/live {
    access_log off;
    limit_req off;
    proxy_pass http://backend;
}

서킷 브레이커 — 장애 격리

개념 — 특정 백엔드가 계속 실패하면 일정 시간 아예 호출하지 않습니다.
· 닫힘(Closed) — 정상. 요청을 통과시킵니다
· 열림(Open) — 실패가 임계치를 넘으면 즉시 실패 응답(빠른 실패)
· 반열림(Half-Open) — 일정 시간 후 일부 요청만 시험적으로 통과
왜 필요한가 — 죽은 서비스를 계속 호출하면 타임아웃을 기다리느라 우리 스레드까지 고갈되어 장애가 전파됩니다.
Nginx 의 max_fails 는 단순한 형태의 서킷 브레이커이고, 본격적인 구현은 애플리케이션(Resilience4j 등)이나 서비스 메시에서 합니다. 자세한 패턴은 ☕ 자바 가이드의 대규모 트래픽 탭에 있습니다.
헬스체크는 누구에게 보낼지, 서킷 브레이커는 보낼지 말지를 정합니다.
SECTION 13

관측 가능성 · 추적 ID

서버가 여러 대면 로그가 흩어집니다. 요청 하나를 끝까지 따라갈 방법이 필요합니다. 

# Nginx 가 요청마다 고유 ID 를 만들어 전달합니다
log_format traced '$remote_addr - [$time_local] "$request" $status '
                  'rt=$request_time urt=$upstream_response_time '
                  'rid=$request_id';

server {
    access_log /var/log/nginx/access.log traced;

    location / {
        proxy_set_header X-Request-Id $request_id;     # ★ 앱에 전달
        add_header       X-Request-Id $request_id;     # 응답에도 (사용자 문의 대응)
        proxy_pass http://backend;
    }
}
# 이제 로그가 이렇게 이어집니다

Nginx : rid=a1b2c3d4 "GET /api/orders/123" 200 rt=1.234
앱    : [a1b2c3d4] OrderController.get(123) 시작
앱    : [a1b2c3d4] OrderService.find(123)
DB    : [a1b2c3d4] SELECT * FROM orders WHERE id=123  (1.1s) ← 범인
앱    : [a1b2c3d4] 응답 완료 1.2s

★ 사용자가 "느려요"라고 하면
  응답 헤더의 X-Request-Id 만 받아 이 전체를 재구성할 수 있습니다
Spring Boot (MDC)
@Component
public class RequestIdFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req,
      HttpServletResponse res, FilterChain chain) throws Exception {
    String id = req.getHeader("X-Request-Id");
    MDC.put("requestId", id != null ? id : UUID.randomUUID().toString());
    try { chain.doFilter(req, res); }
    finally { MDC.clear(); }
  }
}
// logback 패턴에 %X{requestId} 추가
Python (contextvars)
import contextvars, logging
request_id = contextvars.ContextVar("request_id", default="-")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id.get()
        return True

# 미들웨어에서
# request_id.set(request.headers.get("X-Request-Id", uuid4().hex))
# 포맷: "%(asctime)s [%(request_id)s] %(message)s"

한 단계 위 — 분산 추적

OpenTelemetry 는 요청 ID 를 넘어 구간별 소요 시간까지 추적합니다.
· Trace — 요청 하나의 전체 여정
· Span — 그 안의 각 구간(HTTP 처리 · DB 쿼리 · 외부 API)
· W3C Trace Context — traceparent 헤더로 서비스 간 전파
Jaeger·Tempo·Zipkin 같은 도구로 어느 구간이 느린지 그림으로 볼 수 있습니다. 마이크로서비스 환경에서는 사실상 필수입니다. 
# 외부에서 온 추적 헤더가 있으면 그것을 이어받고, 없으면 새로 만듭니다
map $http_x_request_id $req_id {
    default   $http_x_request_id;
    ""        $request_id;
}

location / {
    proxy_set_header X-Request-Id  $req_id;
    proxy_set_header traceparent   $http_traceparent;   # W3C 표준 전파
    proxy_pass http://backend;
}
