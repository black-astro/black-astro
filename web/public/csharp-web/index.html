C# 01

C# 을 실행하는 법

설치부터 Hello, World 까지 5분. 어디서 어떻게 도는지도 함께 봅니다.

SDK 하나면 끝납니다

# .NET SDK 설치 (Windows·macOS·Linux 공통)
# https://dotnet.microsoft.com/download

dotnet --version          # 10.0.x 가 나오면 준비 끝

dotnet new console -o hello    # 콘솔 프로젝트 만들기
cd hello
dotnet run                     # 빌드 + 실행

# 자주 쓰는 템플릿
dotnet new console        # 콘솔 프로그램
dotnet new classlib       # 라이브러리
dotnet new webapi         # 웹 API
dotnet new xunit          # 테스트 프로젝트
dotnet new sln            # 솔루션(프로젝트 묶음)
// Program.cs — 최상위 문(top-level statements)
// Main 메서드를 적지 않아도 됩니다. 컴파일러가 만들어 줍니다.
Console.WriteLine("Hello, World!");

var name = Console.ReadLine();
Console.WriteLine($"반갑습니다, {name}님");
Visual Studio 가 없어도 됩니다. VS Code + C# Dev Kit 확장이면 충분하고, Rider(JetBrains)는 Unity 개발에서 특히 강합니다. Windows 에서 Visual Studio Community 는 무료이며 WPF·MAUI 디자이너가 붙습니다.

어디서 도는가 — 런타임 지도

.NET
서버 · 콘솔 · 데스크탑 최신 .NET 10. 크로스 플랫폼이고 성능이 가장 좋습니다. 웹 API · 게임 서버 · WPF 가 여기서 돕니다.
Unity
게임 엔진 안의 C# Unity 6 은 .NET Standard 2.1 수준 + 자체 런타임(Mono·IL2CPP). 최신 C# 문법 중 일부는 못 씁니다 — 버전 확인이 필요합니다.
.NET Framework
옛 윈도우 전용 (4.8) 레거시 사내 시스템에서 아직 만납니다. 새 프로젝트는 절대 여기서 시작하지 마세요.

C# 02

변수 · 타입 · var

C# 은 정적 타입 언어입니다. 타입을 적는 순간 컴파일러가 실수를 대신 잡아 줍니다.

기본형과 var

int    hp    = 100;          // 32비트 정수
long   gold  = 9_000_000_000; // 64비트 (밑줄로 자릿수 구분 가능)
float  speed = 5.5f;          // Unity 에서 가장 많이 쓰는 실수형
double ratio = 0.75;          // 기본 실수형 (정밀도 ↑)
decimal price = 19_900m;      // ★ 돈 계산은 무조건 decimal
bool   alive = true;
char   grade = 'S';
string name  = "용사";

// var — '타입을 안 쓰는 것'이 아니라 '컴파일러가 추론'하는 것
var count = 10;               // int 로 확정 (나중에 문자열 대입 불가)
var items = new List<string>();

// 상수
const int MaxLevel = 99;      // 컴파일 시점 고정
readonly int seed;            // 생성자에서 한 번만 대입 가능
돈에 float · double 을 쓰면 틀립니다. 0.1 + 0.2 != 0.3 이기 때문입니다. 금액·수량 정산은 decimal, 게임의 좌표·속도처럼 오차가 허용되는 값은 float 이 정답입니다.

값 타입 vs 참조 타입 — 이 구분이 성능을 가릅니다

값 타입 (struct)
  • int · float · bool · Vector3
  • 스택에 놓이고 복사됩니다
  • GC 부담이 없습니다 — 게임 루프에서 중요
참조 타입 (class)
  • string · 배열 · List · 내가 만든 class
  • 힙에 놓이고 주소가 복사됩니다
  • 많이 만들면 GC 가 돌며 프레임이 튑니다
struct Point { public int X, Y; }
class   Node  { public int Value; }

var p1 = new Point { X = 1 };
var p2 = p1;  p2.X = 99;        // 복사본만 바뀐다
Console.WriteLine(p1.X);        // 1

var n1 = new Node { Value = 1 };
var n2 = n1;  n2.Value = 99;    // 같은 객체를 가리킨다
Console.WriteLine(n1.Value);    // 99  ← 함께 바뀐다
Unity 의 Vector3·Quaternion 은 struct 입니다. 그래서 transform.position.x = 1; 이 컴파일되지 않습니다 — 복사본을 고쳐 봐야 원본이 안 바뀌기 때문입니다. transform.position = new Vector3(1, y, z); 처럼 통째로 넣어야 합니다.

// ③ 원시 문자열 리터럴 (C# 11+) — JSON·SQL 을 그대로

    { "id": 1, "name": "칼" }
    """;

// 비교 — 대소문자·문화권을 명시하는 습관

// 비어 있음 검사

루프 안에서 +=

C# 04

조건 · 반복 · switch 식

C# 의 switch 는 값을 돌려주는 식입니다. 여기부터 코드가 짧아집니다.

반복문 네 가지

for (int i = 0; i < 10; i++) { }

foreach (var e in enemies) { }        // 가장 많이 씁니다

while (hp > 0) { }
do { } while (retry);

// 인덱스가 함께 필요하면
foreach (var (item, i) in items.Select((x, i) => (x, i))) { }

// 범위·인덱스 문법 (C# 8+)
var last  = arr[^1];       // 마지막
var first3 = arr[..3];     // 앞 3개
var mid   = arr[2..5];     // 2~4
foreach 중에 컬렉션을 고치면 예외가 납니다. 지울 대상은 따로 모았다가 루프 밖에서 지우거나, for 문을 뒤에서 앞으로 돌리세요. 게임에서 "죽은 적 제거" 코드가 여기서 자주 터집니다.

switch 식 · 패턴 매칭

// 값을 돌려주는 switch — if/else 사슬이 사라집니다
string Grade(int score) => score switch
{
    >= 90 => "S",
    >= 80 => "A",
    >= 70 => "B",
    _      => "F",          // _ 는 나머지 전부
};

// 타입으로 분기
decimal Damage(IWeapon w) => w switch
{
    Sword s when s.IsCritical => s.Power * 2,
    Sword s                   => s.Power,
    Bow { Arrows: 0 }         => 0,          // 속성 패턴
    Bow b                     => b.Power * 0.8m,
    null                      => throw new ArgumentNullException(nameof(w)),
    _                         => 1,
};

// 튜플 패턴 — 가위바위보
string Result(int me, int you) => (me, you) switch
{
    (0, 2) or (1, 0) or (2, 1) => "승",
    var (a, b) when a == b     => "무",
    _                          => "패",
};
모든 경우를 다 적으면 _ 없이도 됩니다. enum 을 switch 할 때 _ 를 빼 두면, 나중에 enum 에 값을 추가했을 때 컴파일러가 경고해 줍니다 — 빠뜨린 분기를 사람이 찾지 않아도 됩니다.
C# 05

클래스 · 구조체 · record

셋 다 "데이터 묶음"이지만 쓰는 자리가 다릅니다. 고르는 기준을 정리합니다.

클래스 — 기본 선택지

public class Player
{
    // 자동 속성
    public string Name { get; }              // 읽기 전용
    public int    Hp   { get; private set; } // 밖에서는 못 바꿈
    public int    Level { get; set; } = 1;   // 기본값

    // 주 생성자 (C# 12+)
    public Player(string name, int hp) => (Name, Hp) = (name, hp);

    public void TakeDamage(int dmg)
    {
        Hp = Math.Max(0, Hp - dmg);
        if (Hp == 0) Died?.Invoke(this);
    }

    public event Action<Player>? Died;       // 이벤트 (c09 에서)

    public override string ToString() => $"{Name}(Lv.{Level})";
}

record 와 struct 는 언제

// record — '값으로 비교되는' 데이터 묶음 (DTO·설정·이벤트)
public record ItemDto(int Id, string Name, int Price);

var a = new ItemDto(1, "칼", 100);
var b = new ItemDto(1, "칼", 100);
Console.WriteLine(a == b);           // True ← 내용이 같으면 같다
var c = a with { Price = 200 };      // 일부만 바꾼 복사본

// struct — 작고 많이 만들어지는 값 (좌표·색·ID)
public readonly record struct Tile(int X, int Y);   // 값 타입 record

내용이 같으면 같은 것으로 보고 싶다record

C# 06

상속 · 인터페이스

게임 코드가 커질 때 가장 먼저 무너지는 곳입니다. 상속은 얕게, 인터페이스는 작게.

문법

public abstract class Enemy               // 추상 — 직접 생성 불가
{
    public abstract int Hp { get; }       // 자식이 반드시 구현
    public virtual void OnSpawn() { }     // 자식이 바꿔도 되고 안 바꿔도 됨

static async Task<T> RetryAsync<T>(Func<Task<T>> act, int max = 3)
{
    for (int i = 0; ; i++)
    {
        try { return await act(); }
        catch (Exception e) when (i < max && IsTransient(e))
        {
            var wait = TimeSpan.FromMilliseconds(
                Math.Pow(2, i) * 200 + Random.Shared.Next(100));
            await Task.Delay(wait);
        }
    }
}

private int _count;
public void Add() => _count++;      // ✗ 원자적이지 않다 (읽기→더하기→쓰기)

// ① lock — 가장 쉽고 대부분 충분
private readonly object _gate = new();
public void Add() { lock (_gate) { _count++; } }

// ② Interlocked — 단순 연산은 락 없이
Interlocked.Increment(ref _count);
Interlocked.CompareExchange(ref _state, 1, 0);   // 0이면 1로

// ③ 동시 컬렉션
private readonly ConcurrentDictionary<int, Session> _sessions = new();
_sessions.TryAdd(id, s);
_sessions.AddOrUpdate(id, s, (_, old) => old.Merge(s));
lock 안에서 await 는 불가능합니다. 비동기 구간을 보호해야 하면 SemaphoreSlim(1,1) 을 쓰세요. 그리고 락을 잡은 채 외부 호출(DB·HTTP)을 하지 마세요 — 전체가 그 속도에 묶입니다.

Channel — 생산자·소비자의 표준

// 게임 서버에서 '패킷 수신 → 처리' 를 잇는 가장 깔끔한 방법
var ch = Channel.CreateBounded<Packet>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // 밀리면 오래된 것부터 버림
    SingleReader = true,
});

// 생산자 — 네트워크 스레드
await ch.Writer.WriteAsync(packet, ct);

// 소비자 — 로직 스레드 하나 (락이 필요 없어집니다)
await foreach (var p in ch.Reader.ReadAllAsync(ct))
    Handle(p);
락을 줄이는 가장 좋은 방법은 "공유하지 않는 것"입니다. 게임 룸마다 스레드(또는 액터) 하나가 그 룸만 처리하게 만들면 룸 안의 데이터에는 락이 필요 없습니다 — 상용 게임 서버가 널리 쓰는 구조입니다(🌐 게임 서버 탭).
ADV 04

Span<T> · Memory<T> — 복사 없는 처리

배열을 자르지 않고 들여다보는 방법. 패킷 파싱·문자열 처리에서 할당을 0으로 만듭니다.

쓰는 법

// Substring 은 새 문자열을 만든다 → 할당
var head = text.Substring(0, 4);          // ✗ 힙 할당

// Span 은 '창'만 만든다 → 할당 0
ReadOnlySpan<char> span = text.AsSpan(0, 4);   // ✓

// 패킷 파싱 (게임 서버의 핵심 경로)
static bool TryParse(ReadOnlySpan<byte> buf, out Header h)
{
    if (buf.Length < 8) { h = default; return false; }
    h = new Header(
        Id:   BinaryPrimitives.ReadInt32LittleEndian(buf),
        Size: BinaryPrimitives.ReadInt32LittleEndian(buf[4..]));
    return true;
}

// 스택에 임시 버퍼 (작은 크기만!)
Span<byte> tmp = stackalloc byte[128];

규칙과 한계

  • Span<T> 는 필드에 저장할 수 없습니다 — 스택 전용(ref struct)
  • async 메서드에서 쓸 수 없습니다 — 그때는 Memory<T>
  • stackalloc 은 루프 안에서 금지 — 스택이 넘칩니다
  • 큰 버퍼는 ArrayPool<T>.Shared 에서 빌려 쓰고 돌려주세요
var buf = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    var n = await stream.ReadAsync(buf.AsMemory(), ct);
    Process(buf.AsSpan(0, n));
}
finally { ArrayPool<byte>.Shared.Return(buf); }   // ★ 반드시 반납
모든 코드에 Span 을 바를 필요는 없습니다. 효과가 큰 곳은 초당 수천 번 도는 경로(패킷 수신·직렬화·로그 파싱)입니다. 나머지는 가독성이 더 중요합니다.
ADV 05

GC 와 할당 줄이기

"게임이 가끔 뚝뚝 끊긴다"의 범인은 대개 GC 입니다. 메모리를 아끼는 게 아니라 새로 만드는 횟수를 줄이는 것이 핵심입니다.

어디서 몰래 할당되는가

void Update()
{
    // ① 문자열 — 매 프레임 새 객체
    label.text = "HP " + hp;                     // ✗

    // ② 박싱 — 값 타입이 object 로 변할 때
    object o = 3;                                // ✗
    Debug.Log(string.Format("{0}", hp));         // ✗ 박싱

    // ③ 람다가 바깥 변수를 잡을 때(클로저)
    list.ForEach(x => x.Add(offset));            // ✗ offset 캡처

    // ④ LINQ · foreach on interface
    var alive = enemies.Where(e => e.Hp > 0);    // ✗ 반복자 객체

    // ⑤ params · 배열
    Log("a", "b");                               // params → 배열 생성
}
이 다섯 개만 잡아도 프레임 튐의 대부분이 사라집니다. Unity 라면 Profiler 의 GC Alloc 열을 켜고 0 B 가 아닌 줄을 위에서부터 지워 나가세요.

고치는 법

// ① 값이 바뀔 때만 갱신 + 캐시
private int _shownHp = -1;
void Update()
{
    if (_shownHp == hp) return;
    _shownHp = hp;
    label.SetText("HP {0}", hp);      // TMP 의 할당 없는 API
}

// ② 재사용 버퍼
private readonly List<Collider> _hits = new(32);
_hits.Clear();
Physics.OverlapSphereNonAlloc(pos, r, _buffer);   // NonAlloc 계열

// ③ 구조체 + 정적 람다

// ④ 오브젝트 풀

ADV 09

네이티브 상호운용 — P/Invoke

C·C++ 로 된 기존 자산을 그대로 씁니다. 게임의 물리·오디오·플랫폼 SDK 연동에 필요합니다.

DllImport

using System.Runtime.InteropServices;

internal static partial class Native
{
    // C# 12+ — 소스 제너레이터 방식(빠르고 AOT 안전)
    [LibraryImport("user32.dll", StringMarshalling = StringMarshalling.Utf16)]
    [return: MarshalAs(UnmanagedType.Bool)]
    internal static partial bool MessageBeep(uint type);

    [LibraryImport("mylib", EntryPoint = "compute")]
    internal static partial int Compute(
        ReadOnlySpan<float> input, Span<float> output, int len);
}
경계를 넘는 비용은 공짜가 아닙니다. 한 번에 큰 덩어리를 넘기세요 — 루프 안에서 한 값씩 부르면 네이티브가 아무리 빨라도 전체는 느려집니다.

지켜야 할 것

  • 구조체 레이아웃을 [StructLayout(LayoutKind.Sequential)] 로 고정
  • 포인터로 넘길 배열은 고정(fixed)하거나 Span 사용 — GC 가 옮기면 터집니다
  • 네이티브가 준 메모리는 누가 해제하는지 문서로 남기세요
  • 플랫폼별 바이너리(.dll·.so·.dylib)를 전부 배포해야 합니다
Unity 에서는 더 조심해야 합니다. 네이티브 플러그인은 에디터에서 한 번 로드되면 안 내려갑니다 — DLL 을 교체하려면 에디터를 재시작해야 하고, 플러그인이 죽으면 에디터가 통째로 죽습니다.

ADV 12

자주 하는 실수 모음

코드 리뷰에서 반복해서 지적하게 되는 것들을 모았습니다.

언어 · 런타임

  • DateTime.Now 대신 DateTimeOffset.UtcNow — 서버는 UTC 로 저장하고 표시할 때만 변환
  • new Random() 을 반복 생성 — 같은 값이 나옵니다. Random.Shared
  • IDisposable 을 안 닫음 — using 을 습관으로
  • 예외를 흐름 제어로 사용 — 느리고 의도가 흐려집니다
  • == 로 문자열 비교 시 문화권 이슈 — StringComparison 명시
  • float 비교를 == 로 — 오차 범위로 비교하세요

서버 · 게임

  • 클라이언트를 믿는 것 — 좌표·데미지·재화는 서버가 계산합니다(🌐 게임 서버 탭)
  • 동기 API 를 서버에서 호출 — .Result 하나로 처리량이 무너집니다
  • Update 안의 GetComponent·Find — Awake 에서 캐시
  • 로그를 문자열로 조립 — 구조적 로깅(log.Info("x {A}", a))

게임오브젝트는 빈 상자입니다. 무엇을 할 수 있는지는 붙인 컴포넌트가 정합니다.

using UnityEngine;

public class Player : MonoBehaviour       // ← 컴포넌트가 되려면 상속

  • Raycast Target 끄기 — 클릭이 필요 없는 이미지·텍스트는 전부 해제
  • 텍스트는 TextMeshPro — 기본 Text 는 화질·성능 모두 불리합니다
  • 비활성화보다 캔버스 그룹 — alpha 0 + blocksRaycasts false 가 더 쌉니다
  • 레이아웃 그룹 남용 금지 — 중첩되면 계산 비용이 급증합니다
UI Toolkit(새 UI 시스템)은 에디터 툴과 정적 UI 에 강합니다. 게임 내 HUD 는 아직 uGUI 가 현실적인 선택인 경우가 많습니다.

GAME 02

오브젝트 풀링 — 프레임 튐의 1순위 대책

Instantiate/Destroy 를 반복하면 GC 가 돌고, 그때 화면이 멈칫합니다.

총알·이펙트·적·데미지 텍스트 — 반복해서 나타났다 사라지는 것은 전부 풀 대상입니다.

직접 만들기 (원리)

public class BulletPool : MonoBehaviour
{
    [SerializeField] private Bullet prefab;
    [SerializeField] private int prewarm = 50;

    private readonly Stack<Bullet> _idle = new();

    void Awake()
    {
        for (int i = 0; i < prewarm; i++)     // ★ 로딩 때 미리 만든다
        {
            var b = Instantiate(prefab, transform);
            b.gameObject.SetActive(false);
            _idle.Push(b);
        }
    }

    public Bullet Get(Vector3 pos, Quaternion rot)
    {
        var b = _idle.Count > 0 ? _idle.Pop() : Instantiate(prefab, transform);
        b.transform.SetPositionAndRotation(pos, rot);
        b.gameObject.SetActive(true);
        return b;
    }

    public void Release(Bullet b)
    {
        b.gameObject.SetActive(false);
        b.ResetState();                        // ★ 상태 초기화를 잊지 마세요
        _idle.Push(b);
    }
}

놓치기 쉬운 것

  • 상태 초기화 — 속도·남은 시간·트레일이 남아 있으면 "이상하게 동작하는 총알"이 됩니다
  • 파티클은 Stop(true, ClearBehaviour.Clear) 로 잔상 제거
  • 코루틴은 비활성화되면 멈춥니다 — 재활성화 시 다시 시작해야 합니다
  • 이벤트 구독은 OnEnable/OnDisable 짝으로
  • 최대 개수 상한을 두세요 — 무한히 늘면 그냥 메모리 누수입니다
씬 로딩 때 미리 채워 두는 것(prewarm)이 핵심입니다. 전투 중에 처음 50개를 만들면 바로 그 순간 멈칫합니다. 로딩 화면에서 미리 만들어 두면 사용자는 알아채지 못합니다.
풀이 만능은 아닙니다. 가끔 한 번 나오는 오브젝트까지 풀에 넣으면 메모리만 잡아먹습니다. 기준은 "초당 여러 번 생성되는가" 입니다.

GAME 04

그래픽 최적화 — 드로우콜 · 배칭

GPU 가 아니라 "몇 번 그리라고 시켰는가" 가 병목인 경우가 대부분입니다.

배칭 — 여러 개를 한 번에

  • Static Batching — 안 움직이는 물체에 Static 체크. 메모리를 쓰지만 효과가 큽니다
  • SRP Batcher — URP 기본. 같은 셰이더면 재질이 달라도 묶입니다
  • GPU Instancing — 같은 메시·재질을 수백 개 (풀·나무·적)
  • 텍스처 아틀라스 — 여러 이미지를 한 장으로 합쳐 재질 수를 줄입니다
배칭을 깨는 것들 — 런타임에 material.color = ... 로 재질을 건드리면 그 오브젝트만 별도 재질(인스턴스)이 되어 배칭에서 빠집니다. 색을 바꾸려면 MaterialPropertyBlock 을 쓰세요. 
private static readonly int ColorId = Shader.PropertyToID("_BaseColor");
private MaterialPropertyBlock _mpb;

void Awake() => _mpb = new MaterialPropertyBlock();

void SetColor(Color c)
{
    _renderer.GetPropertyBlock(_mpb);
    _mpb.SetColor(ColorId, c);
    _renderer.SetPropertyBlock(_mpb);   // 재질 복제 없이 색만 변경
}

  • LOD — 멀리 있는 모델은 저해상도로 교체
  • 오클루전 컬링 — 벽 뒤 물체를 아예 안 그림

GAME 05

Addressables — 메모리와 다운로드 관리

모든 에셋을 앱에 넣으면 설치 용량이 폭발합니다. 필요할 때 받아서 쓰는 구조로 바꿉니다.

기본 사용

using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

private AsyncOperationHandle<GameObject> _handle;

async void LoadBoss()
{
    _handle = Addressables.LoadAssetAsync<GameObject>("Boss_Dragon");
    var prefab = await _handle.Task;
    Instantiate(prefab);
}

void OnDestroy()
{
    // ★ 반드시 해제 — 안 하면 메모리에 계속 남습니다
    if (_handle.IsValid()) Addressables.Release(_handle);
}

// 인스턴스까지 한 번에 (해제도 함께)
var go = await Addressables.InstantiateAsync("Boss_Dragon").Task;
Addressables.ReleaseInstance(go);

운영 관점

  • 초기 설치 용량을 줄입니다 — 스토어 상한(구글 150MB 등)을 넘기지 않게
  • 콘텐츠만 갱신 가능 — 앱 심사 없이 이벤트 에셋 교체(원격 카탈로그)
  • 중복 제거 — 여러 번들이 같은 텍스처를 물면 메모리가 두 배가 됩니다
  • 다운로드 진행률을 사용자에게 보여 주세요
// 다운로드 크기 확인 후 진행
var size = await Addressables.GetDownloadSizeAsync(label).Task;
if (size > 0)

using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;
using Unity.Mathematics;

[BurstCompile]                                  // ★ 네이티브 수준으로 컴파일
public struct MoveJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Dir;
    public NativeArray<float3> Pos;
    public float Dt;

    public void Execute(int i) => Pos[i] += Dir[i] * Dt;
}

// 실행
var job = new MoveJob { Pos = _pos, Dir = _dir, Dt = Time.deltaTime };

handle.Complete();                              // 결과가 필요한 시점에
Job 안에서는 Unity 오브젝트를 못 씁니다. Transform·GameObject·Debug.Log 전부 불가. 순수한 숫자 계산만 가능하며, 데이터는 NativeArray 로 넘기고 반드시 Dispose 해야 합니다.

언제 도입할 것인가

효과가 큰 경우

  • 오브젝트가 수십 개뿐
  • UI · 게임 로직 대부분
  • 팀이 ECS 를 처음 접함 (학습 비용이 큽니다)

    public ushort Seq;        // 이 패킷의 번호
    public ushort Ack;        // 내가 마지막으로 받은 번호
    public uint   AckBits;    // 그 앞 32개를 받았는지 비트로
    public byte   Channel;    // 0=비신뢰 1=신뢰 2=순서보장
}
  • 재전송 — Ack 가 안 오면 다시 보냅니다(신뢰 채널만)
  • 순서 — 필요할 때만 (전부 순서를 지키면 TCP 와 같아집니다)
  • 조각화 — MTU(약 1200바이트)를 넘으면 나눠 보냅니다
  • 혼잡 제어 — 손실률이 높으면 전송 주기를 낮춥니다
직접 구현하지 마세요. 위 네 가지를 제대로 만드는 데 몇 달이 걸리고 미묘한 버그가 남습니다. LiteNetLib·ENet·Netcode 의 UnityTransport 같은 검증된 라이브러리를 쓰고, 이 구조를 이해한 상태로 튜닝하는 것이 목표입니다.

소켓 서버 — .NET 으로 직접

수천 명을 한 프로세스에서 받는 서버의 뼈대. 할당 없는 수신 루프가 핵심입니다.

TCP 수신 루프

var listener = new TcpListener(IPAddress.Any, 7777);
listener.Start(backlog: 512);

while (!ct.IsCancellationRequested)
{
    var client = await listener.AcceptTcpClientAsync(ct);
    client.NoDelay = true;                 // ★ Nagle 끄기 (지연 40ms 제거)
    _ = HandleAsync(client, ct);           // 세션마다 독립 처리
}

static async Task HandleAsync(TcpClient c, CancellationToken ct)
{
    var buf = ArrayPool<byte>.Shared.Rent(16 * 1024);
    try
    {
        var stream = c.GetStream();
        var filled = 0;
        while (true)
        {
            var n = await stream.ReadAsync(buf.AsMemory(filled), ct);
            if (n == 0) break;             // 연결 종료
            filled += n;

            // ★ TCP 는 '메시지 경계'가 없다 — 길이 헤더로 잘라야 한다
            var offset = 0;
            while (filled - offset >= 4)
            {
                var len = BinaryPrimitives.ReadInt32LittleEndian(
                              buf.AsSpan(offset));
                if (len <= 0 || len > 64 * 1024) throw new InvalidDataException();
                if (filled - offset - 4 < len) break;      // 아직 덜 왔다
                Dispatch(buf.AsSpan(offset + 4, len));
                offset += 4 + len;
            }
            Buffer.BlockCopy(buf, offset, buf, 0, filled - offset);
            filled -= offset;
        }
    }
    finally { ArrayPool<byte>.Shared.Return(buf); c.Dispose(); }
}

반드시 챙길 것

  • 메시지 경계 — TCP 는 스트림입니다. 길이 헤더로 직접 자르세요. 이걸 빼먹으면 "가끔 패킷이 깨진다" 가 됩니다
  • 길이 상한 — 헤더의 길이를 그대로 믿고 버퍼를 잡으면 메모리 폭탄 공격에 당합니다
  • NoDelay = true — 안 켜면 작은 패킷이 40ms 씩 지연됩니다
  • 연결 상한 · 유휴 타임아웃 — 접속만 하고 아무것도 안 하는 연결을 끊으세요
  • ArrayPool — 세션마다 버퍼를 새로 잡으면 GC 가 무너집니다
더 높은 성능이 필요하면 System.IO.Pipelines 를 보세요. 버퍼 관리·역압(backpressure)을 대신 해 주어 위 코드의 복잡한 부분이 사라지고 할당도 거의 0 이 됩니다.

룸 · 세션 · 게임 루프

서버도 게임처럼 일정 주기로 도는 루프가 있습니다. 락을 없애는 구조가 여기서 나옵니다.

룸 하나 = 스레드 하나

public sealed class GameRoom
{
    private readonly Channel<IPacket> _inbox =
        Channel.CreateUnbounded<IPacket>(new() { SingleReader = true });

    public ValueTask PushAsync(IPacket p) => _inbox.Writer.WriteAsync(p);

    public async Task RunAsync(CancellationToken ct)
    {
        var tick = TimeSpan.FromMilliseconds(50);      // 20Hz
        var next = DateTime.UtcNow;

        while (!ct.IsCancellationRequested)
        {
            // ① 들어온 입력을 전부 처리 (이 룸의 데이터는 나만 만진다 → 락 불필요)
            while (_inbox.Reader.TryRead(out var p)) Handle(p);

            // ② 게임 로직 한 틱
            Simulate((float)tick.TotalSeconds);

            // ③ 상태 방송
            Broadcast();

            next += tick;
            var wait = next - DateTime.UtcNow;
            if (wait > TimeSpan.Zero) await Task.Delay(wait, ct);
            else next = DateTime.UtcNow;               // 밀렸으면 따라잡지 않는다
        }
    }
}

이 구조의 장점

  • 락이 사라집니다 — 룸 데이터는 그 루프만 만집니다
  • 재현이 쉽습니다 — 입력 순서가 정해져 있어 버그 재현이 가능합니다
  • 수평 확장이 자연스럽습니다 — 룸을 다른 서버로 옮기면 됩니다
  • 틱 시간을 측정해 룸당 부하를 바로 알 수 있습니다
루프 안에서 DB·HTTP 를 기다리지 마세요. 한 룸의 20Hz 가 무너지고 그 방 전원이 렉을 느낍니다. 저장은 큐에 넣고 다른 곳에서 처리하세요. 
// 저장은 비동기로 흘려보낸다

// 세션 정리 — 끊긴 연결을 방치하면 룸이 안 닫힙니다
if (now - p.LastPacketAt > TimeSpan.FromSeconds(20)) Kick(p, "timeout");
틱 시간 모니터링이 게임 서버의 핵심 지표입니다. 20Hz 라면 한 틱 50ms 안에 끝나야 합니다. 평균이 아니라 최대값을 보세요 — 한 번의 100ms 가 렉으로 체감됩니다.

public sealed class MatchMaker
{
    private readonly List<Ticket> _queue = new();

    public void Enqueue(Ticket t) { lock (_queue) _queue.Add(t); }

    // 주기적으로 돌며 짝을 맞춘다
    public void Tick()
    {
        lock (_queue)
        {
            _queue.Sort((a, b) => a.Rating.CompareTo(b.Rating));

            for (int i = 0; i + 1 < _queue.Count; )
            {
                var (a, b) = (_queue[i], _queue[i + 1]);

                {
                    CreateRoom(a, b);
                    _queue.RemoveRange(i, 2);
                }
                else i++;
            }
        }
    }
}

string IssueToken(Player p)
{
    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub, p.Id.ToString()),
        new Claim("nick", p.Nickname),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
    };
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    var token = new JwtSecurityToken(issuer, audience, claims,

API 08

게임 백엔드 설계 — 재화 · 인벤토리

여기서 실수하면 아이템이 복사되거나 사라집니다. 트랜잭션과 멱등성이 전부입니다.

구매 — 한 트랜잭션으로

public async Task<BuyResult> BuyAsync(int playerId, int itemId, int count,
                                       string idempotencyKey, CancellationToken ct)
{
    // ① 같은 요청이 두 번 오면 이전 결과를 그대로 (네트워크 재시도 대비)
    if (await _db.Receipts.FindAsync([idempotencyKey], ct) is {} done)
        return done.Result;

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    // ② 가격은 서버가 조회 — 클라이언트 값은 쓰지 않는다
    var item = await _db.ItemDefs.FindAsync([itemId], ct)
               ?? throw new NotFoundException();
    var cost = item.Price * count;

    // ③ 재화 차감은 조건부 UPDATE 로 (동시 요청에도 음수가 되지 않게)
    var affected = await _db.Players
        .Where(p => p.Id == playerId && p.Gold >= cost)
        .ExecuteUpdateAsync(s => s.SetProperty(p => p.Gold, p => p.Gold - cost), ct);
    if (affected == 0) return BuyResult.NoGold;

    // ④ 지급 · 영수증 · 로그를 같은 트랜잭션에
    _db.Inventories.Add(new Inventory { PlayerId = playerId, ItemId = itemId, Count = count });
    _db.Receipts.Add(new Receipt { Key = idempotencyKey, Result = BuyResult.Ok });
    _db.GoldLogs.Add(new GoldLog { PlayerId = playerId, Delta = -cost, Reason = "buy" });

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return BuyResult.Ok;
}

지켜야 할 원칙

  • 재화 변동은 반드시 로그 — 문의·환불·치트 조사의 유일한 근거입니다
  • 조건부 UPDATE — WHERE gold >= cost 로 DB 가 판정하게
  • 멱등 키 — 같은 요청이 두 번 와도 한 번만 처리
  • 지급과 차감은 같은 트랜잭션 — 중간에 죽으면 둘 다 취소
  • 수량 상한 — 인벤토리·우편함 한도를 서버가 강제
  • 시간은 서버 기준 — 클라이언트 시각으로 일일 보상을 주면 조작됩니다
"읽고 → 계산하고 → 쓰기"는 동시 요청에서 깨집니다. 골드 100 인 플레이어가 동시에 두 번 구매하면 둘 다 "충분함"으로 읽어 골드가 음수가 됩니다. 조건부 UPDATE 나 낙관적 동시성(RowVersion)으로 막으세요.

SCALE 01

규모의 감각 잡기

"동시접속 10만"이 실제로 초당 몇 요청이고 서버 몇 대인지 계산해 봅니다.

숫자로 환산하기

동시접속(CCU) 10,000 인 모바일 RPG 가정

일반 API (로비·상점·인벤토리)
  사용자당 분당 6요청 → 10,000 × 6 / 60 = 1,000 RPS
  한 요청 20ms → 서버 1대(4코어)가 대략 500~1,000 RPS
  → 앱 서버 2~4대 + 여유

실시간 전투 (20Hz 동기화)
  방당 4명 · 초당 20틱 · 인당 200B
  4 × 20 × 200 = 16 KB/s per room
  방 2,500개(1만 명) → 40 MB/s = 320 Mbps ★ 대역폭이 먼저 한계

DB
  쓰기 초당 200건 · 읽기 800건
  → 읽기는 캐시로 90% 흡수, 쓰기는 단일 인스턴스로도 가능
병목은 대개 순서가 정해져 있습니다. ① DB 커넥션 → ② 캐시 없는 반복 조회 → ③ 대역폭 → ④ CPU. 먼저 무너질 곳부터 대비하세요.

먼저 정할 것

  • 목표 지표(SLO) — 예: "API p99 200ms · 가용성 99.5%"
  • 예상 CCU 의 3배로 부하 테스트 — 오픈 첫날은 항상 예상을 넘습니다
  • 비용 한도 — 무한 확장은 가능하지만 돈이 듭니다
  • 줄일 수 있는 기능 — 부하가 폭주하면 무엇을 끌 것인가(랭킹·상세 통계)
"일단 만들고 나중에 확장"은 절반만 맞습니다. 무상태(stateless)·멱등성·수평 확장 가능한 세션 — 이 셋은 처음부터 지켜야 합니다. 나중에 바꾸려면 사실상 다시 만들게 됩니다.

분산 락

// 여러 서버 중 하나만 실행해야 할 때 (일일 정산 · 스케줄)
public async Task<bool> TryRunOnceAsync(string key, TimeSpan ttl, Func<Task> work)
{
    var token = Guid.NewGuid().ToString();
    if (!await db.StringSetAsync(key, token, ttl, When.NotExists))
        return false;                     // 다른 서버가 잡았다

    try { await work(); return true; }
    finally
    {
        // ★ 내가 잡은 락만 푼다 (TTL 만료 후 남의 락을 푸는 사고 방지)
        const string lua = @"
            if redis.call('get', KEYS[1]) == ARGV[1]
            then return redis.call('del', KEYS[1]) else return 0 end";
        await db.ScriptEvaluateAsync(lua, [key], [token]);
    }
}
락 TTL 보다 작업이 오래 걸리면 두 대가 동시에 돕니다. TTL 을 넉넉히 잡고, 작업 자체를 멱등하게 만들어 두 번 실행돼도 결과가 같게 설계하세요 — 이것이 더 근본적인 해법입니다.
Redis 도 단일 장애점입니다. 세션을 Redis 에만 두면 Redis 가 죽을 때 전원 로그아웃됩니다. 영속화 설정·복제·클러스터를 검토하고, 죽었을 때 어떻게 동작할지를 정해 두세요.

캐시 스탬피드

인기 있는 키가 만료되는 순간, 그 키를 기다리던 수천 요청이 동시에 DB 로 몰립니다. 평소에는 캐시가 막아 주던 부하가 한꺼번에 터지는 것입니다. 
// ① 하나만 계산하게 만든다 (나머지는 기다렸다 결과를 공유)
private static readonly SemaphoreSlim _gate = new(1, 1);

async Task<T> GetAsync<T>(string key, Func<Task<T>> load, TimeSpan ttl)
{
    if (_cache.TryGetValue(key, out T? hit)) return hit!;

    await _gate.WaitAsync();
    try
    {
        if (_cache.TryGetValue(key, out hit)) return hit!;   // 이중 확인
        var v = await load();
        // ② 만료 시각을 흩뿌린다 (한꺼번에 만료되지 않게)
        var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
        _cache.Set(key, v, ttl + jitter);
        return v;
    }
    finally { _gate.Release(); }
}

방식설명주의
TTL시간이 지나면 자동 삭제가장 단순 · 잠깐 옛 값
쓰기 시 삭제변경하면 키를 지움지울 키를 빠뜨리기 쉬움
버전 키shop:v12 처럼 번호를 올림옛 키는 TTL 로 정리
핫키 문제 — 랭킹 1페이지처럼 모두가 보는 키는 Redis 노드 하나에 부하가 몰립니다. 앱 메모리에 1초짜리 로컬 캐시를 한 겹 더 두면 Redis 호출이 수천 분의 일로 줄어듭니다.
재화·인벤토리는 캐시하지 마세요. "골드가 잘못 보인다"는 신뢰를 잃는 버그입니다. 읽기 성능이 필요하면 캐시 대신 읽기 전용 복제본을 쓰세요.

public sealed class NodeReporter(IRedis redis) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await redis.Db.HashSetAsync($"node:{NodeId}",
            [
                new("rooms", RoomManager.Count),
                new("cpu",   Cpu.Percent()),
                new("state", _draining ? "draining" : "ready"),
            ]);
            await redis.Db.KeyExpireAsync($"node:{NodeId}", TimeSpan.FromSeconds(15));
            await Task.Delay(5000, ct);
        }
    }
}

축소가 더 어렵습니다

사람이 붙어 있는 서버를 끌 수 없습니다. 웹은 요청이 끝나면 그만이지만, 게임은 30분짜리 판이 돌고 있습니다. 축소는 항상 draining → 자연 종료 순서여야 합니다.

private CancellationTokenSource? _cts;

private async Task SearchAsync()
{
    _cts?.Cancel();                       // 이전 검색 취소
    _cts = new CancellationTokenSource();
    var ct = _cts.Token;

    try
    {
        await Task.Delay(300, ct);        // 디바운스 — 타이핑이 멈춘 뒤 실행
        var rows = await _repo.FindAsync(Keyword, ct);
        if (ct.IsCancellationRequested) return;
        Apply(rows);
    }
    catch (OperationCanceledException) { /* 정상 취소 */ }
}

DEEP 01

CLR 구조 · JIT

C# 코드가 CPU 명령이 되기까지. 두 번 컴파일된다는 사실이 출발점입니다.

벤치마크에서 첫 실행을 버리는 이유가 여기 있습니다.

JIT 이 해 주는 일

  • 인라이닝 — 작은 메서드 호출을 본문으로 펼칩니다(속성 접근이 공짜인 이유)
  • 경계 검사 제거 — for (i = 0; i < arr.Length; i++) 형태를 알아보고 검사 제거
  • 죽은 코드 제거 — 상수 조건 분기를 통째로 삭제
  • 계층형 컴파일 — 자주 실행되면 더 좋은 코드로 교체(OSR)
  • 제네릭 특수화 — 값 타입은 타입마다 전용 코드를 만듭니다
arr.Length 를 변수에 담는 최적화는 이제 손해입니다. JIT 이 패턴을 인식해 경계 검사를 지우는데, 변수에 담으면 그 패턴이 깨져 오히려 검사가 남습니다.

DEEP 02

메모리 배치 — 스택 · 힙 · 참조

"값 타입은 스택"은 절반만 맞습니다. 정확한 그림을 잡습니다.

실제 규칙

void M()
{
    int a = 1;              // 스택 (지역 변수)
    var p = new Point();    // 스택 (struct 지역 변수)
    var n = new Node();     // 참조는 스택, 객체 본체는 힙

    var list = new List<Point>();
    list.Add(p);            // ★ 이 Point 는 힙에 있습니다 (배열 안)
}

class Holder
{
    Point _p;               // ★ 이 struct 는 힙에 있습니다 (객체의 일부)
}
정확한 규칙 — 값 타입은 "자신이 놓인 곳"에 있습니다. 지역 변수면 스택, 객체의 필드면 힙, 배열 원소면 힙. "복사되는가"(값 의미)가 struct 의 본질이고, 스택/힙은 그 결과일 뿐입니다.

객체 하나의 비용

64비트에서 class 인스턴스
  객체 헤더(동기화 블록)   8 바이트
  메서드 테이블 포인터     8 바이트
  ─────────────────────── 최소 24 바이트 (정렬 포함)

즉 int 하나만 든 class 도 24바이트,
같은 내용의 struct 는 4바이트.
→ 작고 많은 데이터일수록 struct 가 유리한 이유
// 메모리 레이아웃 확인 (ObjectLayoutInspector)
TypeLayout.PrintLayout<Player>();

// 필드 순서만 바꿔도 크기가 줄어듭니다 (패딩)
struct Bad  { byte A; long B; byte C; }   // 24바이트
struct Good { long B; byte A; byte C; }   // 16바이트
struct 라고 항상 빠른 것은 아닙니다. 16~24바이트를 넘으면 복사 비용이 커져 오히려 class 가 낫습니다. 큰 struct 를 넘길 때는 in 매개변수로 복사를 막으세요.
DEEP 03

GC 내부 — 세대 · LOH · 서버 GC

언제 멈추고 얼마나 멈추는지. 게임의 프레임 튐과 서버의 p99가 여기서 결정됩니다.

세대 가설

Gen 0
갓 만들어진 객체 — 대부분 금방 죽는다 수집이 매우 쌉니다(밀리초 이하). 자주 일어납니다.
Gen 1
Gen0 을 한 번 살아남은 것 완충 지대. 여전히 쌉니다.
Gen 2
오래 사는 객체 — 캐시·싱글턴 수집이 비쌉니다. 여기가 자주 돌면 문제입니다.
LOH
85KB 이상 — 큰 배열·버퍼 Gen2 와 함께 수집되고 기본적으로 압축하지 않습니다(단편화).

public IDisposable Subscribe(Action<int> h)
{
    Changed += h;
    return new Unsubscriber(() => Changed -= h);
}

        {
            case -1:
                _awaiter = LoadAsync().GetAwaiter();
                if (!_awaiter.IsCompleted)      // ★ 이미 끝났으면 그냥 진행
                {
                    _state = 0;
                    _builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);
                    return;                     // 스레드를 놓는다
                }
                goto case 0;
            case 0:
                var a = _awaiter.GetResult();
                _builder.SetResult(a + 1);
                return;
        }
    }
}

여기서 나오는 실무 결론

  • 이미 완료된 작업은 상태 기계를 타지 않습니다 — 캐시 히트가 많으면 ValueTask 가 유효합니다
  • async 메서드마다 상태 기계 객체가 생깁니다 — 아주 뜨거운 경로에서는 이것도 비용입니다
  • await 이후는 다른 스레드일 수 있습니다 — ThreadStatic·UI 접근에 주의
  • SynchronizationContext 가 있으면 원래 컨텍스트로 돌아옵니다 (UI·Unity). 서버(ASP.NET Core)에는 없습니다
// 라이브러리 코드라면 컨텍스트 복귀를 끄는 것이 표준
await SomethingAsync().ConfigureAwait(false);

// 앱 코드(ASP.NET Core)에서는 컨텍스트가 없어 붙일 필요가 없습니다
"async 를 쓰면 스레드가 늘어난다"는 오해입니다. 오히려 스레드를 덜 쓰기 위해 쓰는 것입니다. 대기 중에는 어떤 스레드도 그 작업을 붙잡고 있지 않습니다.
DEEP 06

스레드 풀 · 기아 현상

서버가 갑자기 전부 느려지는 현상의 대표적인 원인입니다.

무슨 일이 일어나는가

스레드 풀 기아(starvation) — .Result 로 비동기를 기다리는 코드가 여럿이면 스레드가 전부 대기 상태로 묶입니다. 풀은 1초에 1~2개씩만 스레드를 늘리므로 회복이 매우 느리고, 그동안 모든 요청이 지연됩니다. 
// 증상 확인
ThreadPool.GetAvailableThreads(out var worker, out var io);
Console.WriteLine($"여유 스레드 {worker}");

// 지표로 감시 (급증하면 기아)
dotnet-counters monitor -p <PID> \
  System.Runtime[dotnet.threadpool.queue.length,dotnet.threadpool.thread.count]

고치는 법

  • 동기 차단 제거 — .Result·.Wait()·lock 안의 IO
  • 동기 API 는 동기 스레드로 — 레거시 라이브러리는 전용 큐로 분리
  • 최소 스레드 상향은 임시방편 — 근본 원인을 고치세요
  • CPU 작업을 요청 스레드에서 하지 말고 Task.Run 으로
// 임시 완화 (진짜 해결이 아님을 알고 쓰세요)
ThreadPool.SetMinThreads(workerThreads: 200, completionPortThreads: 200);
게임 서버에서는 다른 각도로도 옵니다. 룸 루프를 Task.Run 으로 수백 개 띄우면 풀 스레드를 전부 점유합니다. 장시간 도는 루프는 전용 스레드 (new Thread { IsBackground = true })로 만드세요.
DEEP 07

메모리 모델 · 락 프리

CPU 와 컴파일러는 순서를 바꿉니다. 멀티스레드 버그의 근원입니다.

재배치와 가시성

// 이 코드는 '영원히 끝나지 않을 수' 있습니다
private bool _stop;              // ✗
public void Run() { while (!_stop) { } }     // JIT 이 레지스터에 캐시
public void Stop() => _stop = true;

// ① volatile — 항상 메모리에서 읽고 쓴다
private volatile bool _stop;     // ✓

// ② Interlocked — 원자적 연산
Interlocked.Increment(ref _count);
Interlocked.Exchange(ref _state, 1);
var prev = Interlocked.CompareExchange(ref _state, 1, 0);   // 0이면 1로

// ③ lock — 가장 쉽고 안전 (진입·탈출 시 메모리 장벽)
lock (_gate) { _count++; }
volatile 은 원자성을 주지 않습니다. _count++ 는 읽기+더하기+쓰기 세 단계라 volatile 을 붙여도 경쟁이 그대로 남습니다. 수치 연산은 Interlocked, 복합 로직은 lock 입니다.

락 프리는 최후에

// CAS 루프 — 성공할 때까지 재시도
public void AddMax(ref long field, long value)
{
    long cur;
    do
    {
        cur = Volatile.Read(ref field);
        if (value <= cur) return;
    }
    while (Interlocked.CompareExchange(ref field, value, cur) != cur);
}

// 카운터는 전용 타입이 훨씬 빠릅니다 (경합이 심할 때)
private readonly PaddedCounter _hits;   // false sharing 방지 패딩
락 프리 코드는 검증이 매우 어렵습니다. ABA 문제·false sharing·메모리 장벽을 모두 고려해야 하고, 틀려도 대부분의 실행에서는 잘 동작합니다. 측정으로 락이 병목임을 확인한 뒤에만 손대세요.
더 나은 방법은 공유를 없애는 것입니다. 게임 서버의 룸 하나 = 스레드 하나 구조처럼 데이터를 나눠 가지면 동기화 자체가 필요 없어집니다.
DEEP 08

캐시 라인 · 데이터 지역성

요즘 CPU 에서 느린 것은 계산이 아니라 메모리에서 값을 가져오는 시간입니다.

배열 vs 객체 배열

// 객체 배열 — 메모리에 흩어져 있다 (캐시 미스)
class Enemy { public float X, Y; public int Hp; /* ... 그 밖에 많은 필드 */ }
Enemy[] enemies;                       // 참조 배열 → 실제 객체는 여기저기

foreach (var e in enemies) e.X += 1;   // 매번 다른 메모리로 점프

// 구조 배열(SoA) — 붙어 있다
float[] xs, ys;                        // 좌표만 연속으로
for (int i = 0; i < xs.Length; i++) xs[i] += 1;   // 순차 접근 · 캐시 적중
Unity 의 DOTS/ECS 가 빠른 이유가 정확히 이것입니다. 같은 종류의 데이터를 연속된 메모리에 모아 캐시 미스를 없애고 SIMD 를 쓸 수 있게 합니다 (🕹️ Unity 실전 탭 06).

false sharing

// 서로 다른 스레드가 '같은 캐시 라인(64B)'의 값을 만지면
// 실제로는 관계없는 데이터인데도 캐시가 계속 무효화됩니다
class Counters
{
    public long A;     // 스레드 1이 증가
    public long B;     // 스레드 2가 증가  ← 같은 라인에 있으면 서로 방해
}

// 패딩으로 떼어 놓기
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedLong { [FieldOffset(64)] public long Value; }
  • 증상 — 코어를 늘렸는데 오히려 느려짐
  • 확인 — 스레드별 카운터를 따로 두고 마지막에 합치기로 바꿔 비교
  • 대안 — ThreadLocal<T> · 파티션별 집계
이 최적화는 마지막에 하세요. 알고리즘·할당·IO 를 먼저 잡고, 프로파일러가 메모리 대기(stall)를 가리킬 때만 의미가 있습니다.
DEEP 09

Native AOT · 트리밍

JIT 없이 미리 기계어로. 시작이 즉시이고 메모리가 적습니다 — 대신 제약이 있습니다.

쓰는 법과 효과

<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
  <StripSymbols>true</StripSymbols>
</PropertyGroup>
일반 게시     시작 120ms · 메모리 40MB · 배포 70MB
Native AOT    시작   8ms · 메모리 14MB · 배포 12MB

→ 서버리스 · CLI 도구 · 컨테이너 밀집 배치에서 큰 이득

포기해야 하는 것

  • 런타임 리플렉션이 제한됩니다 — 타입을 문자열로 찾는 코드가 깨집니다
  • 동적 코드 생성(Emit) 불가 — 일부 ORM·목 라이브러리가 못 돕니다
  • 플러그인 로딩(Assembly.LoadFrom) 불가
  • 빌드 시간이 길어집니다
// AOT 에서 안전한 방식 — 소스 제너레이터로 미리 만들어 둔다
[JsonSerializable(typeof(PlayerDto))]
internal partial class AppJson : JsonSerializerContext { }

var json = JsonSerializer.Serialize(dto, AppJson.Default.PlayerDto);
Unity 의 IL2CPP 도 같은 부류입니다. 그래서 모바일 빌드에서만 터지는 리플렉션 오류가 나옵니다. AOT 를 염두에 둔 코드(소스 제너레이터·명시적 등록)를 쓰면 두 환경 모두에서 안전해집니다.
DEEP 10

프로파일링 실전

운영 중인 프로세스에서 재시작 없이 원인을 찾는 절차입니다.

도구 순서

dotnet tool install -g dotnet-counters
dotnet tool install -g dotnet-trace
dotnet tool install -g dotnet-dump
dotnet tool install -g dotnet-gcdump

# ① 무엇이 이상한지 (실시간 지표)
dotnet-counters monitor -p <PID> --counters System.Runtime,Microsoft.AspNetCore.Hosting

# ② CPU 가 어디서 쓰이는지 (30초 샘플)
dotnet-trace collect -p <PID> --duration 00:00:30 \
  --providers Microsoft-DotNETCore-SampleProfiler

# ③ 멈춰 있다면 (스레드가 무엇을 기다리는지)
dotnet-dump collect -p <PID>
> clrstack -all
> syncblk                      # 락 경합 확인

# ④ 메모리 (타입별 크기)
dotnet-gcdump collect -p <PID>

증상 → 도구

증상먼저 볼 것
CPU 100%dotnet-trace → 뜨거운 함수
CPU 낮은데 느림dump → clrstack(대기 지점)
메모리 증가gcdump 두 개 비교 → gcroot

Unity 프로파일링은 별개 세계입니다. Unity Profiler + Deep Profile, 네이티브까지 보려면 Superluminal·Xcode Instruments 를 씁니다 (🕹️ Unity 실전 탭 03).
DEEP 11

보안 — 역직렬화 · 공급망

내가 쓴 코드보다 가져다 쓴 패키지와 남이 보낸 데이터가 더 위험합니다.

역직렬화

타입 정보를 데이터가 정하게 하면 원격 코드 실행이 됩니다. BinaryFormatter 는 .NET 9 에서 제거되었고, TypeNameHandling.All(Newtonsoft) 도 같은 위험을 만듭니다. 
// ✗ 절대 금지
var obj = new BinaryFormatter().Deserialize(stream);
JsonConvert.DeserializeObject(json,
    new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.All });

// ✓ 받을 타입을 코드가 정한다
var dto = JsonSerializer.Deserialize<PlayerDto>(json, _opt);

// 크기·깊이 상한도 두세요
var opt = new JsonSerializerOptions { MaxDepth = 16 };

DEEP 12

최적화의 순서

여기까지 온 도구를 어떤 순서로 쓸 것인가. 순서를 틀리면 시간을 버립니다.

단계

1
측정 — 어디가 느린가 프로파일러 없이 시작하지 마세요. 체감 문제부터 정의합니다(프레임 튐? p99? 시작 시간?).
2
없애기 — 아예 안 하기 불필요한 호출·중복 계산·과한 로그. 가장 큰 효과가 여기서 나옵니다.
3
줄이기 — 덜 하기 캐시 · 배칭 · 페이징 · AOI. 알고리즘과 데이터 양의 문제입니다.
4
빠르게 — 같은 일을 싸게 Span · 풀링 · struct · SIMD. 여기까지 와야 미시 최적화가 의미가 있습니다.
4번부터 시작하는 것이 가장 흔한 실수입니다. 전체의 0.1% 를 5배 빠르게 만들어도 체감은 0 입니다.
